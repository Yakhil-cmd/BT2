### Title
Webhook signature verification key is selected from an unverified payload field, decoupling the authenticated organization from the repository actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to verify the incoming signature against by reading `repository.owner.login` (or `organization.login`) directly out of the still-unauthenticated JSON body, before the signature has been checked. Once verification passes, the entire raw, attacker-influenced payload (including `repository.full_name`, which is what the event handlers actually use to locate the `Stack` to mutate) is dispatched unchanged to the handlers. This breaks the intended binding "organization that authenticated == repository that is written," matching the report's core bug class (a field enforced/authenticated against one thing while a different, unchecked field drives the state-changing action).

### Finding Description
In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Shipit explicitly supports being configured with **multiple GitHub organizations, each with its own `webhook_secret`**, as documented in `docs/setup.md` ("Using Multiple Github Applications") and exercised by the `secrets_double_github_app.yml` fixture and `Shipit.github`/`github_app_config` lookup logic: [2](#0-1) [3](#0-2) 

`Shipit.github(organization:)` uses the string extracted by `repository_owner` purely as a lookup key to select which org's `GitHubApp`/`webhook_secret` performs `verify_webhook_signature`: [4](#0-3) 

Once `verified` is true, the controller hands the *entire, still fully attacker-controlled* `params` hash (parsed straight from `request.raw_post`) to every registered handler for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

Handlers such as the push handler resolve the target `Stack` from `repository.full_name` in that same JSON body (confirmed indirectly by the corresponding test, which enqueues a `GithubSyncJob` for the stack matching the payload's repository, independent of any re-check against the organization used for verification): [6](#0-5) 

The root problem: `repository.owner.login` selects *which secret authenticates the request*, while `repository.full_name` (a sibling, equally attacker-supplied field inside the same signed body) selects *which repository/stack is acted upon*. Nothing enforces that these two values refer to the same GitHub organization/repository. Concretely, if Shipit is configured with two organizations `OrgOne` and `OrgTwo` (each with distinct `webhook_secret`s, as the documented multi-tenant setup allows), a party who legitimately knows `OrgOne`'s webhook secret (e.g., an admin of the GitHub App installed on `OrgOne`, or anyone who can trigger a real, validly-signed webhook delivery for `OrgOne`) can craft/replay a JSON body where:
- `repository.owner.login` = `"OrgOne"` (so `Shipit.github(organization: "OrgOne")` is selected and the HMAC verifies successfully with `OrgOne`'s secret), while
- `repository.full_name` = `"OrgTwo/some-stack"` (a repository/stack actually tracked under a completely different, unrelated organization in the same Shipit instance).

Because signature verification never re-validates that the organization it authenticated against matches the repository the handler subsequently mutates, the forged/replayed event is accepted as authentic and dispatched against `OrgTwo`'s stack.

### Impact Explanation
This allows cross-organization/cross-repository event injection: an entity trusted only for `OrgOne` can trigger state changes (e.g. `GithubSyncJob`, PR merge-queue state transitions via `pull_request`/`status`/`check_suite` handlers, membership/team changes via `membership` events) against stacks that belong to a different GitHub organization it has no authorization over. Depending on which webhook handler is reached, this can drive unauthorized commit ingestion into a foreign stack's deploy history, unauthorized merge-queue processing (`ProcessMergeRequestsJob` → `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request`), or team/membership tampering for `OrgTwo` — i.e., cross-repository/cross-organization writes and possibly unauthorized merges, which map to the Critical/High impact classes defined in scope (cross-repository writes, unauthorized merge).

### Likelihood Explanation
Exploitation requires the attacker to already possess a valid webhook secret for *some* organization configured in the Shipit instance — not necessarily the target organization. In any deployment following Shipit's documented multi-org pattern, that secret is held by whoever administers the GitHub App for that one organization (or is otherwise able to produce a validly-signed delivery for it, e.g., a compromised or malicious GitHub App installer for `OrgOne`). This is a materially weaker requirement than compromising the target organization (`OrgTwo`) itself, and the code path (`repository_owner` → `Shipit.github` → `verify_webhook_signature` → unchecked dispatch of `params`) is exercised on every webhook request, making it directly and repeatably reachable once such access exists.

### Recommendation
After signature verification succeeds for the `GitHubApp` selected via `repository_owner`, re-validate that every organization-identifying field actually acted upon by the downstream handler (e.g., `repository.full_name`'s owner, `organization.login`) is consistent with the organization whose secret validated the signature, and reject (422) any payload where they diverge. Alternatively, iterate/verify against the exact `GitHubApp` that owns the target `Stack`/repository rather than trusting an org name taken from the unauthenticated body to select the verification key.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `OrgOne` and `OrgTwo`, each with a distinct `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section) — a supported, real-world configuration.
2. As an entity that knows/controls `OrgOne`'s webhook secret (e.g., the GitHub App admin for `OrgOne`, or by replaying/crafting a validly-HMAC'd delivery for `OrgOne`), submit a `push` (or other handled) event to `POST /webhooks` with:
   - `X-Github-Event: push`
   - `X-Hub-Signature`: HMAC-SHA1 of the raw body computed with `OrgOne`'s `webhook_secret`
   - Body JSON: `repository.owner.login = "OrgOne"`, but `repository.full_name = "OrgTwo/victim-stack"` (the repository/stack Shipit tracks for `OrgTwo`), with an `after` SHA of the attacker's choosing.
3. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and successfully verifies the signature against `OrgOne`'s secret.
4. `Shipit::Webhooks.for_event('push')` handler(s) receive the full `params`, locate the `Stack` by `repository.full_name` ("OrgTwo/victim-stack"), and enqueue `GithubSyncJob`/process the event against `OrgTwo`'s stack — despite the attacker never having proven any authorization for `OrgTwo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
