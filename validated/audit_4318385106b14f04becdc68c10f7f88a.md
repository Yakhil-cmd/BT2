### Title

Accrual overflows the i128 RAY valuation ceiling and permanently freezes an oversized market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

`accrue_step` values total borrowed and supplied shares in `i128` RAY before applying the configured index ceilings. [1](#0-0)  Once either stored share balance multiplied by its stored index exceeds `i128::MAX`, `scaled_to_original` panics with `MathOverflow`, even though `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY` have not been reached. [2](#0-1) [3](#0-2)  Because every market mutation performs this accrual first, the market can enter an irreversible state where repayment, withdrawal, liquidation, revenue claims, and index updates all revert. [4](#0-3) [5](#0-4) 

### Finding Description

The borrow and supply indexes are nominally capped at `1e36` raw RAY units. [3](#0-2)  However, the overflow occurs before the new capped index is useful: `accrue_step` first computes `borrowed * borrow_index` and `supplied * supply_index` through `scaled_to_original`, then derives utilization and the next index. [1](#0-0)  `Ray::mul` returns a checked `i128` value, so an otherwise valid large position can make this intermediate valuation unrepresentable even when the index itself remains below its cap. [6](#0-5) [7](#0-6) 

An unprivileged account can create the required condition through normal `supply` and `borrow` operations if a configured market permits a sufficiently large position and the market later remains at high utilization for enough accrual periods. [8](#0-7)  The repository’s regression test demonstrates this state using one billion 18-decimal tokens supplied and 98% borrowed: the borrow index remains below `MAX_BORROW_INDEX_RAY`, but the next accrual panics with `MATH_OVERFLOW`. [9](#0-8) 

### Impact Explanation

This is permanent freezing of funds for the affected market because pool mutations always run `global_sync`, and `global_sync` calls the overflowing `accrue_step` before executing the requested operation. [10](#0-9)  The regression test confirms that the state blocks both `withdraw` and `repay` after the overflow threshold is crossed. [11](#0-10) 

Suppliers cannot recover their deposits, borrowers cannot repay or unwind debt, liquidators cannot process the market, and accrued revenue is inaccessible while ledger time keeps advancing. [12](#0-11) [13](#0-12)  There is no unprivileged path that skips accrual, and decreasing ledger time is impossible, so the condition cannot be repaired by a later normal market operation. [5](#0-4) 

### Likelihood Explanation

The issue requires an extremely large market position and sustained high utilization long enough for the index to grow beyond the value ceiling, so it is not reachable from an ordinary-sized market immediately. [14](#0-13)  Nevertheless, all actions used to create the state are ordinary permissionless lending actions, and the test demonstrates that the configured index cap does not prevent the earlier valuation overflow. [15](#0-14) [16](#0-15) 

The strongest severity classification is **Medium**: the impact is market-wide permanent freezing, but the likelihood depends on very high liquidity, permissive caps, and sustained accrual. [14](#0-13) 

### Recommendation

Enforce a value-domain invariant that is derived from the actual share balances, not only from the fixed index constants. [17](#0-16)  In particular, cap index growth at `floor(i128::MAX * RAY / borrowed)` for debt valuation and `floor(i128::MAX * RAY / supplied)` for supply valuation before calling any multiplication that returns `Ray`. [18](#0-17) 

Alternatively, perform total-debt and total-supply valuation in a wider internal representation and use explicit saturation at the protocol’s accounting ceiling rather than allowing `MathOverflow` to abort all future entrypoints. [19](#0-18) [20](#0-19)  The invariant should also be enforced at supply and borrow mint boundaries so a position cannot be created with a share balance that is already incompatible with the permitted index range. [21](#0-20) 

### Proof of Concept

The repository already contains a deterministic reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`. [22](#0-21) 

```text
1. Create an 18-decimal BIG18 market with the XLM rate curve.
2. The same unprivileged account supplies:
   - BIG18 liquidity: 1_000_000_000 * 10^18 base units
   - COL collateral sufficient to borrow BIG18
3. Borrow BIG18 equal to 98% of the supplied principal:
   debt = principal * 98 / 100
4. Allow ledger time to advance through yearly accrual chunks.
5. Invoke controller `update_indexes` for [BIG18].
6. Observe `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
7. Attempt `withdraw` and `repay`; both panic with `MATH_OVERFLOW`
   because each mutation runs `global_sync` first.
```

The test’s expected failure is `errors::MATH_OVERFLOW`, with `borrow_index` still below the configured cap, proving that the cap does not rescue the arithmetic-domain violation. [23](#0-22)  The subsequent assertions show that withdrawals and repayments hit the same panic after the accrual cliff. [11](#0-10)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}

/// Converts a Ray-denominated `fee` into scaled supply-index shares
/// (`fee / supply_index`), floor-rounded and saturating on overflow. Caps the
/// result so that adding it to `supplied` cannot overflow `i128::MAX`.
pub fn protocol_fee_shares(env: &Env, fee: Ray, supply_index: Ray, supplied: Ray) -> Ray {
    let raw = fp_core::mul_div_floor_saturating(env, fee.raw(), RAY, supply_index.raw());

    let headroom = i128::MAX.saturating_sub(supplied.raw());
    Ray::from(raw.min(headroom))
}
