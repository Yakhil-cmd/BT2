### Title
`membership` webhook lets any organization onboarded to Shipit hijack an existing `Team` (and thus `Shipit.github_teams` authorization) belonging to a different organization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using an **attacker-controlled** field of the payload itself (`organization.login`), while `MembershipHandler` subsequently mutates a `Team` record looked up by a **separate, unrelated, attacker-controlled** field (`team.id`) with no check that the team actually belongs to the organization whose secret was used to authenticate the request.

### Finding Description
`WebhooksController#verify_signature` derives the organization to authenticate against directly from the request body: [1](#0-0) [2](#0-1) 

For a `membership` event there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')` — a value fully controlled by whoever crafts the payload. `Shipit.github(organization: repository_owner)` then supplies the `webhook_secret` used for HMAC verification: [3](#0-2) .

Shipit explicitly supports multiple GitHub organizations sharing one instance, each with its own `webhook_secret` set independently by that organization's own administrator: [4](#0-3) 

So an unprivileged-with-respect-to-Shipit but legitimate admin of "OrgA" (onboarded to the same Shipit instance) knows OrgA's own `webhook_secret` and can produce a validly-signed `membership` webhook whose body they fully control.

`MembershipHandler` then processes the event using `params.team.id` — not the authenticated `organization.login` — to find or create the `Team` and add a member to it: [5](#0-4) 

`Team.find_or_create_by!(github_id: params.team.id)` only sets `organization` when the record doesn't already exist; if a `Team` row already exists for that `github_id` (created earlier by a legitimate `membership` webhook from the real, privileged organization, e.g. one listed in `oauth.teams`), the lookup returns that existing row regardless of which organization's secret authenticated the current request: [6](#0-5) 

Team membership is exactly what gates `User#authorized?`, which is the sole check performed by `force_github_authentication` to decide whether a logged-in GitHub user is allowed to use the whole Shipit instance: [7](#0-6) [8](#0-7) 

The binding that is broken is: `organization whose webhook_secret authenticated the request == organization owning the team being written to`. The verification step and the mutation step consult two different, independently attacker-controllable fields of the same payload (`organization.login` vs. `team.id`), and nothing ties them together.

### Impact Explanation
By sending one crafted, self-signed `membership` webhook (`action: "added"`, `team.id: <victim team's real GitHub team ID>`, `member.login: <attacker's own Shipit login>`), an attacker who merely administers/owns any organization already onboarded to the shared Shipit instance can add their own `User` to a `Team` whose `id` is included in `Shipit.github_teams` (built from `oauth.teams` in `secrets.yml`) — [9](#0-8) . This flips `authorized?` to `true` for that user, granting them full access to the Shipit instance (viewing/triggering deploys, rollbacks, locks, stack settings) for every organization served by that installation — an escalation into `Shipit.github_teams` authorization, one of the explicitly in-scope High-impact categories.

### Likelihood Explanation
Requires only (a) the target Shipit installation to be configured for multiple GitHub organizations (documented, supported configuration) and (b) the attacker to control/administer one of those onboarded, less-trusted organizations (and thus know that org's own `webhook_secret`) and to know or guess the numeric GitHub team ID of a privileged team in another org (discoverable via the GitHub API for public/known org team slugs, or observable from prior legitimate webhook traffic/logs). No GitHub App private key, Shipit session, or API token is required — only the ability to POST a crafted, correctly-HMAC-signed JSON body to the shared `/github/webhooks` endpoint.

### Recommendation
In `MembershipHandler`, bind the authenticated organization to the team lookup/mutation: reject or ignore the event unless `params.organization.login` matches the `organization` column of the resolved `Team` (and never allow `find_or_create_by!` to attach an existing team belonging to a different `organization` to the event). More generally, `WebhooksController#verify_signature` should authenticate every webhook against the organization that owns the specific resource being mutated (team/repository), not an attacker-supplied field of the same unauthenticated body, and downstream handlers should re-validate that the org/repo they act on is consistent with the org used for signature verification.

### Proof of Concept
1. Shipit instance configured with two organizations, `OrgA` (attacker-administered, onboarded normally) and `OrgB` (privileged; `OrgB/security-team`, GitHub team id `999`, is listed in `oauth.teams` and thus in `Shipit.github_teams`), per [4](#0-3) .
2. `OrgB/security-team`'s `membership` webhook has previously fired at least once for a real member, so `Team.find_by(github_id: 999)` exists with `organization: "orgb"`.
3. Attacker, who controls `OrgA`'s webhook secret, POSTs to the shared webhooks endpoint with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `OrgA`'s `webhook_secret`, and body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Security Team", "slug": "security-team", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "OrgA"},
  "member": {"login": "attacker-shipit-login"}
}
```
4. `verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates (attacker knows this secret) — [1](#0-0) .
5. `MembershipHandler#process` finds the existing `Team` with `github_id: 999` (belonging to `OrgB`) and calls `team.add_member(User.find_or_create_by_login!("attacker-shipit-login"))` — [10](#0-9) .
6. Attacker logs into Shipit via GitHub OAuth as `attacker-shipit-login`; `authorized?` now returns `true` because their user is a member of a team in `Shipit.github_teams` — [7](#0-6) , bypassing the intended team-based access restriction on the whole application.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      if current_user.logged_in? && current_user.requires_fresh_login?

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))

        end

      end
