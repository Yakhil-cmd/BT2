### Title
Webhook Signature Is Verified Against the Payload's `repository.owner.login`/`organization.login` While Handlers Act on the Independent `repository.full_name` Field, Allowing Any Configured GitHub Org to Forge Events for Another Org's Stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the incoming webhook HMAC using `repository_owner`, which is read from `payload.dig('repository','owner','login')` (falling back to `payload.dig('organization','login')`). All downstream event handlers, however, resolve the `Stack`/`Repository` they act on from a completely different, independently attacker-controlled field: `payload.dig('repository','full_name')` via `Handler#repository_name`/`#stacks`. In a multi-org Shipit deployment (explicitly supported and documented), an attacker who legitimately controls one configured GitHub organization can sign a payload with their own org's `webhook_secret` while setting `repository.full_name` to point at a *different* org's repository, causing Shipit to accept and process the forged event against a stack it does not own.

### Finding Description
`verify_signature` computes:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it solely to select which `Shipit.github(organization:)` app/secret validates the HMAC signature. [1](#0-0) [2](#0-1) 

The HMAC check itself is a straight `secure_compare` over the raw JSON body against the secret for that resolved organization: [3](#0-2) 

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire* parsed JSON to handlers, and every base handler resolves the acted-upon repository via a separate, unrelated JSON field: [4](#0-3) 

`PushHandler`, for example, uses `stacks` (derived from `repository.full_name`) to find stacks and call `stack.sync_github(expected_head_sha: params.after)` — an attacker-chosen SHA — for whichever stacks match that `full_name`: [5](#0-4) 

Because the signature check only proves "this body was signed by organization X's secret," and never proves "and organization X owns `repository.full_name`," an attacker who legitimately controls org X can forge a signature over a payload whose `repository.full_name` names org Y's repository. The engine explicitly supports multiple independently-configured GitHub organizations in one instance, each with its own `webhook_secret`, which is the precondition for this cross-org binding failure: [6](#0-5) 

This is the same trust-binding failure class as the reported `EigenLSTRestaking.invoke()` bug: the entity whose credential is checked (the organization owner/secret) is not the entity the operation is actually performed against (the repository/stack in `repository.full_name`).

### Impact Explanation
Using this gap, an attacker who owns/administers any one GitHub organization configured in the shared Shipit instance can:
- Forge `push` events that trigger `stack.sync_github(expected_head_sha:)` for another org's stacks with an attacker-chosen SHA [5](#0-4) , which can drive continuous deployment/sync behavior on repositories they do not control.
- Forge `status` events to inject fabricated commit statuses for another org's tracked commits (state/context/target_url are taken straight from the payload, matched only by SHA against `stacks` resolved via `repository.full_name`), which can be used to satisfy `ci.require` gating and enable an unauthorized deploy of code that never actually passed CI.

This crosses the "unauthorized deploy" / "cross-repository writes" bar defined as Critical impact, because the write (sync, status creation, and any autodeploy triggered from it) lands on a repository/stack the attacker's authenticated organization does not own.

### Likelihood Explanation
Exploitability requires only that the attacker control one legitimately configured GitHub organization in a multi-org Shipit deployment (a supported, documented configuration) and be able to send an arbitrary HTTP POST to the public `/webhooks` endpoint — no Shipit session, API client token, or victim secret is needed, since the attacker signs with their *own* legitimate secret. The only constraint is that both organizations must be configured in the same Shipit instance, which is a normal multi-tenant setup per the docs.

### Recommendation
Bind the signature-verification identity to the same field used for repository resolution. Concretely:
- In `WebhooksController#repository_owner`, derive the organization strictly from `repository.full_name`'s owner segment (or otherwise verify that `repository.owner.login`/`organization.login` matches the owner of `repository.full_name`) before selecting the verification secret.
- In `Handler#repository_name`/`#stacks`, additionally assert that the resolved repository's owner matches the organization whose secret verified the webhook, rejecting the event otherwise.
- More generally, avoid using two independently-attacker-controlled JSON fields for two different security-relevant decisions (which secret verifies vs. which resource is mutated) within the same request.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `orgA` (attacker-controlled) and `orgB` (victim), per the multi-org setup: [6](#0-5) 
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. Attacker signs the raw body with `orgA`'s own `webhook_secret` (which they legitimately possess) and sets `X-Hub-Signature`/`X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `orgA`, fetches `Shipit.github(organization: 'orgA')`, and the HMAC check passes because the attacker signed with the correct `orgA` secret. [1](#0-0) 
5. `PushHandler` then resolves stacks from `repository.full_name = "orgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `orgB`'s stack — an operation the attacker was never authorized to trigger. [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
