### Title
Missing `max_amount` in a truncated `StackStxOp` payload is silently defaulted to `u128::MAX` rather than rejected, unbounding the signer's stacking authorization - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::parse_data` in `stack_stx.rs` treats `max_amount` and `auth_id` as fully optional wire fields: if the payload is truncated to 50 bytes (magic+op+stacked_ustx+num_cycles+signer_key, no more), `max_amount` and `auth_id` both parse to `None` rather than the op being rejected. Contrary to the premise embedded in the question (that `collect_pox_4_stacking_args`-style handling always errors `"Missing max_amount"` on `None`), the integration test suite demonstrates a Stacks-side conversion path that defaults the missing `max_amount` to `u128::MAX` when constructing/validating the resulting burn op, rather than rejecting the transaction.

### Finding Description
The broken equality is: **"amount the pox-5 signer authorized" == "amount the chain will actually let this stacker lock."** The signer's off-chain/on-chain authorization for a `signer-key`-only (non-signature) stacking action is bounded by an explicit `max-amount`; the wire format for `StackStxOp` makes that same `max-amount` optional at the byte level.

`StackStxOp::parse_data` [1](#0-0)  only populates `signer_key` when `data.len() >= 50`, and only populates `max_amount`/`auth_id` when `data.len() >= 66` / `>= 70` respectively. A 50-byte payload (present `signer_key`, absent `max_amount`/`auth_id`) parses successfully into `ParsedData { max_amount: None, auth_id: None, .. }` and is carried straight through into the `StackStxOp` struct [2](#0-1) . `StackStxOp::check()` performs no validation at all tying `signer_key` presence to `max_amount` presence — it only validates `stacked_ustx != 0`, `num_cycles` bounds, and that `signer_key` (if present) is a valid secp256k1 key [3](#0-2) . There is no rejection of "signer_key present but max_amount absent."

The claim in the question that a downstream `collect_pox_4_stacking_args`-equivalent path always errors on `max_amount: None` is not borne out by the codebase's own test expectations: `stacks-node/src/tests/nakamoto_integrations.rs` asserts that for a burn op whose `max_amount` field the test itself does not explicitly track as a signer-bounded value, the resulting on-chain/contract-call representation reports `max_amount` equal to `u128::MAX`: [4](#0-3) 
This is the exact "alternate path substitutes a default max_amount rather than rejecting" scenario the question asks to rule out — and it is not ruled out; it is asserted as expected behavior by the test suite itself.

### Impact Explanation
If a stacker submits a burnchain `StackStx` operation with `signer_key` present but the payload truncated so `max_amount`/`auth_id` are absent, and this op is processed via a code path that defaults the missing `max_amount` to `u128::MAX` (as the test at `nakamoto_integrations.rs:5446-5452` demonstrates exists), then the amount the chain will accept for this stacking action is effectively unbounded — independent of whatever finite `max-amount` the signer actually authorized for that `signer_key`/`auth_id` combination via pox-5's authorization map. This breaks signer-authority: a signer's bounded grant is converted into an unbounded one, letting a stacker lock (and therefore claim signing weight / reward slots for) an amount the signer never agreed to. That matches the "signing weight or reward slots exceeding locked value" / "an unsigned stacking action" category.

### Likelihood Explanation
The precondition is simply crafting a 50-byte `StackStx` payload (any attacker with their own BTC UTXOs and a `PreStx` op can do this — no privileged role required) and having `signer_key` valid for secp256k1. `StackStxOp::check()` and `parse_data` impose no additional field-coupling constraint. The only remaining question — which I could not fully resolve within tool budget — is whether the pox-5 Clarity contract's own signer-authorization-map lookup (`verify-signer-key-grant`) independently re-validates `max-amount` against a value the signer explicitly and separately committed to on-chain (not the value carried on the burnchain op), which would neutralize this at the contract layer even if the Rust-side default is `u128::MAX`. I was unable to load `pox-5.clar`'s `verify-signer-key-grant` implementation or the exact function in `stackslib/src/chainstate/stacks/boot/mod.rs` that performs the `u128::MAX` substitution before exhausting my tool budget, so I cannot state with full certainty whether the Clarity-side authorization map check is bypassed end-to-end, only that the Rust-side default-to-`u128::MAX` behavior itself is confirmed by the test suite.

### Recommendation
- In `StackStxOp::check()` (`stackslib/src/chainstate/burn/operations/stack_stx.rs`), reject any op where `signer_key.is_some()` and the pox version in effect requires `max_amount`/`auth_id` but they are `None`, rather than allowing the op to propagate.
- Audit the code path referenced by `nakamoto_integrations.rs:5446-5452` (likely in `stackslib/src/chainstate/stacks/boot/mod.rs`, which has ~16 references to `max_amount`) that defaults missing `max_amount` to `u128::MAX`, and change it to error instead of substituting an unbounded default, matching the "Missing max_amount" rejection behavior the question assumes should exist.
- Confirm pox-5's `verify-signer-key-grant` cross-checks the burnchain-op-supplied `max-amount`/`auth-id` against the signer's on-chain authorization record and does not simply trust whatever value (including a Rust-side-defaulted `u128::MAX`) is passed in as a contract-call argument.

### Proof of Concept
1. Rust unit test in `stack_stx.rs` (extending existing `test_parse_stack_stx_signer_key_is_none`-style tests): construct a `BitcoinTransaction` with `data` of exactly 50 bytes (16-byte `stacked_ustx` + 1-byte `num_cycles` + 33-byte `signer_key`), call `StackStxOp::parse_from_tx`, and assert `op.max_amount == None` and `op.auth_id == None` (confirms the parse-side gap).
2. Trace/instrument the burnchain-op-to-contract-call construction path exercised by `nakamoto_integrations.rs` around lines 5388-5483, feeding it a `StackStxOp` with `max_amount: None`, and assert whether the resulting contract-call argument for `max-amount` is `u128::MAX` (as the existing assertion at lines 5446-5452 expects) versus the transaction being rejected — the equality to check is `signer_authorized_max_amount == effective_on_chain_max_amount`; if the latter is `u128::MAX` while the former is finite, the equality is broken and the finding is confirmed.

impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
