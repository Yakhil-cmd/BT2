### Title
Webhook signature is verified against the payload's `organization`/`owner.login`, but the write action targets `repository.full_name` — allowing cross-organization/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization credentials to use for HMAC verification based on `repository.owner.login` (or `organization.login`) in the *unverified* JSON body, then verifies the signature with that organization's secret. Once verification passes, the event is dispatched to handlers that determine *which repository/stack to act on* using a **different** field of the same untrusted payload: `repository.full_name`. Because the field used to select the verifying key and the field used to select the target repository are independent and both attacker-controlled prior to verification, an attacker who legitimately controls a webhook secret for one organization can forge a payload that verifies under that organization's key while directing writes at a stack belonging to a completely different repository/organization.

### Finding Description
`WebhooksController` computes the organization used for signature verification like this: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). `Shipit.github(organization: repository_owner)` resolves to that organization's configured GitHub App/webhook secret, and `verify_webhook_signature` authenticates the raw body against it.

Once verification succeeds, `create` dispatches the same raw payload to the registered handlers: [3](#0-2) 

Every handler resolves the target repository from a **different** field of the same body — `repository.full_name` — not `repository.owner.login`: [4](#0-3) 

For example, `PushHandler` uses `stacks` (derived from `full_name`) to look up and mutate Stack records and enqueue sync jobs: [5](#0-4) 

The `PullRequest` handlers do the same, resolving `repository` via `params.repository.full_name` to load or archive `review_stacks`: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization used to select/verify the signing secret (repository.owner.login / organization.login)` == `repository whose stacks/review-stacks are mutated (repository.full_name)`.

Before the attack: for genuine GitHub-issued webhooks, these two fields always describe the same repository, so the binding trivially holds.
After the attack: an attacker who has legitimate access to configure a webhook (and therefore knows the shared secret) for Organization A can submit a raw JSON body where `repository.owner.login = "OrgA"` (satisfies HMAC check against OrgA's secret) but `repository.full_name = "OrgB/victim-repo"` (a stack belonging to an unrelated, more privileged organization/repository already registered in this Shipit instance). The signature check passes, and the handler logic operates on OrgB's stack — enqueueing `GithubSyncJob`, creating/archiving review stacks, or writing commit statuses for a repository the attacker does not control.

### Impact Explanation
This crosses the exact trust boundary the signature check exists to enforce (repository/organization identity claimed vs. verified), enabling forged, attacker-crafted webhook events to act on another organization's/repository's stacks — a cross-repository write, meeting the Critical bar defined in scope.

### Likelihood Explanation
Requires only that the attacker control (or know) a valid webhook secret for *any* organization configured in this Shipit deployment (a routine, low-privilege capability for anyone permitted to register a repository/organization with the instance) — no `ApiClient` token, GitHub App private key, or repository write access to the *victim* repository is needed. This is a realistic multi-tenant deployment scenario, directly analogous to the "organization authenticated vs. repository written" mismatch class.

### Recommendation
After signature verification, cross-check that the organization used to select the verifying secret is consistent with the repository/organization the handler is about to act on (e.g., verify that `Repository.from_github_repo_name(payload.dig('repository','full_name'))` belongs to the same organization as `repository_owner`), and reject the event if they diverge.

### Proof of Concept
1. Attacker has legitimate control of Organization A's GitHub App/webhook secret in this Shipit instance (a supported, unprivileged capability — e.g., they registered their own org/repo).
2. Attacker crafts a raw JSON body: `{"ref":"refs/heads/master","after":"<sha>","repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature` using OrgA's webhook secret and posts to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the signature verifies successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on a stack that has nothing to do with OrgA, demonstrating a forged cross-repository write.
