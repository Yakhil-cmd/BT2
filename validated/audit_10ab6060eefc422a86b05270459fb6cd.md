**Analysis:**

The scenario described — resubmitting a keyless signature captured for one `RawTransaction` after mutating a field (e.g., `expiration_timestamp_secs`) — is already covered and correctly rejected by the existing verification logic and is directly tested by `test_keyless_openid_txn`.

The ephemeral signature verification path is `AccountAuthenticator::verify` → `SingleKeyAuthenticator::verify` → `AnySignature::verify` → `AnySignature::verify_keyless_ephemeral_signature`, which reconstructs `TransactionAndProof { message, proof }` from the **currently submitted** `message` (the raw transaction passed into `verify`), not from a cached/prior copy: [1](#0-0) 

Because `message` is the live `RawTransaction` under verification, any mutation to a field like `expiration_timestamp_secs` after the ephemeral signature was originally produced changes the serialized bytes that `ephemeral_signature.verify(&txn_and_zkp, &signature.ephemeral_pubkey)` checks against, so a signature captured over the old transaction will not verify over the mutated one. This is explicitly exercised by the existing regression test, which signs a raw transaction, verifies success, then mutates `expiration_timestamp_secs` and asserts `signed_txn.verify_signature().is_err()`: [2](#0-1) 

The same binding pattern holds for the Groth16 (ZK) keyless path as well: [3](#0-2) 

The `exp_date_secs`/JWT-claims-liveness check (verified separately on-chain via `keyless_validation.rs`, e.g. `verify_keyless_signature_without_ephemeral_signature_check`) is a distinct check from the ephemeral-signature-to-raw_txn binding, and does not weaken the raw_txn binding itself: [4](#0-3) 

Since the ephemeral signature is verified against the exact current transaction bytes at admission time, an attacker cannot reuse a valid keyless signature over a mutated `RawTransaction` — the described exploit path does not exist in this code.

    fn verify_keyless_ephemeral_signature<T: Serialize + CryptoHash>(
        message: &T,
        signature: &KeylessSignature,
    ) -> Result<()> {
        // Verifies the ephemeral signature on (TXN [+ ZKP]). The rest of the verification,
        // i.e., [ZKPoK of] OpenID signature verification is done in
        // `AptosVM::run_prologue`.
        //
        // This is because the JWK, under which the [ZKPoK of an] OpenID signature verifies,
        // can only be fetched from on chain inside the `AptosVM`.
        //
        // This deferred verification is what actually ensures the `signature.ephemeral_pubkey`
        // used below is the right pubkey signed by the OIDC provider.

        let mut txn_and_zkp = TransactionAndProof {
            message,
            proof: None,
        };

        // Add the ZK proof into the `txn_and_zkp` struct, if we are in the ZK path
        match &signature.cert {
            EphemeralCertificate::ZeroKnowledgeSig(proof) => txn_and_zkp.proof = Some(proof.proof),
            EphemeralCertificate::OpenIdSig(_) => {},
        }

        signature
            .ephemeral_signature
            .verify(&txn_and_zkp, &signature.ephemeral_pubkey)
    }
