### Title
`flash_position()` permanently locks callback-delivered tokens omitted from `refund_assets` - ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
The controller only snapshots and processes two caller-declared token sets during `flash_position()`: collateral assets and refund assets. A receiver contract can transfer any other token to the controller during `execute_flash_position`; the operation succeeds if the declared collateral minimums and account checks pass, but the extra token is neither credited nor returned.

### Finding Description
`process_flash_position()` snapshots only `collaterals` and `refund_assets` before invoking the receiver. After the callback, it deposits only the declared collateral deltas and refunds only the listed refund-asset deltas.

Relevant flow in `contracts/controller/src/strategies/flash_position.rs`:

```rust
let collateral_before = snapshot_balances(
    env,
    &controller,
    collaterals.iter().map(|(hub_asset, _)| hub_asset.asset),
);
let refund_before = snapshot_balances(env, &controller, refund_assets.iter());
invoke_receiver(...);
```

Then:

```rust
let deposits = collect_collateral_deposits(env, &controller, collaterals, &collateral_before);
process_deposit(env, &controller, &mut account, &deposits, &mut cache);
refund_listed_assets(env, caller, refund_assets, &refund_before);
```

`refund_listed_assets()` iterates exclusively over `refund_assets` and calls `refund_controller_balance_delta()`. There is no catch-all reconciliation over other token balance increases.

### Impact Explanation
An unprivileged caller can create a flash-position account and use its own receiver contract. If that receiver accidentally or deliberately sends an extra token to the controller without declaring it in `refund_assets`, the token remains held by the controller after successful settlement. The sender loses the funds and receives no position credit or compensation for them.

This is a permanent freezing of user funds for assets that cannot be reached through any subsequent declared refund delta.

### Likelihood Explanation
Likelihood is moderate. Exploitation does not require privileged access or a protocol failure, but it does require the callback to send a token omitted from both declaration lists. This can occur through receiver bugs, incorrect callback accounting, or treating `controller` as a generic return/refund address. The issue is analogous to sending ETH along a path that does not consume it: the function accepts the value even though the settlement logic ignores it.

### Recommendation
During callback settlement, either:

1. Reject any positive controller token balance delta for an asset not present in `collaterals` or `refund_assets`, or
2. Snapshot a bounded set of accepted tokens and automatically refund every positive non-collateral delta.

The first option is preferable because it prevents accidental or unexpected callback payments instead of silently retaining them.

### Proof of Concept
1. Alice calls `flash_position()` with:
   - `caller = alice`
   - `account_id = 0`
   - `debt = USDC market`
   - `collaterals = [(XLM market, required_xlm)]`
   - `refund_assets = []`
   - `receiver = alice_receiver`
2. The controller mints USDC debt and forwards the received USDC to `alice_receiver`.
3. In `execute_flash_position()`, `alice_receiver` transfers:
   - `required_xlm` XLM to the controller, satisfying the declared collateral minimum;
   - `100` USDC or another token to the controller, omitted from `refund_assets`.
4. The controller deposits the XLM delta, iterates over the empty `refund_assets` list, and ignores the extra token transfer.
5. `flash_position()` completes successfully, while the extra token remains in the controller and is not credited to Alice's position or refunded.
