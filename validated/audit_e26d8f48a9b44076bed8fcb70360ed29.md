### Title
Stack-scoped `ApiClient` token bypasses its stack restriction in `CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be created with a `stack_id`, which is meant to restrict the token to reading/writing only that one stack. `Shipit::Api::BaseController` enforces this by scoping the `stack` lookup through the `stacks` helper, but `Shipit::Api::CCMenuController` overrides `stack` to bypass that scoping entirely, letting any valid `read:stack` token read the CI/deploy status of any stack in the installation, not just the one it was issued for.

### Finding Description
`ApiClient` belongs to an optional `stack` and exposes only a coarse operation:scope permission check: [1](#0-0) 

`Shipit::Api::BaseController` is the base for all API endpoints and defines the canonical, scoped lookup: [2](#0-1) 

`stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated client has a `stack_id` set, which is exactly how a stack-scoped token (e.g. `here_come_the_walrus`, fixture with `stack: shipit`, `permissions: [read:stack]`) is meant to be confined to a single stack: [3](#0-2) 

`Shipit::Api::CCMenuController`, however, re-implements `stack` without going through `stacks`, and only guards access with `require_permission :read, :stack`, which merely checks the presence of the `read:stack` string in the token's permission list, not which stack it is bound to: [4](#0-3) 

`require_permission!` / `check_permissions!` never consult `current_api_client.stack_id`: [5](#0-4) [6](#0-5) 

This is precisely the "misuse of a two-step trust binding" pattern from the report: the token's authorization is established relative to one stack (`api_client.stack_id`), but the controller consumes a different, attacker-supplied stack identifier (`params[:stack_id]`) without re-checking the binding — analogous to `newToken`'s cached value being consumed independently of the caller's intended DAO in the Dandelion report.

`CCMenuUrlController#client` does create client-independent, unscoped tokens for its own generated URLs (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`), which only strengthens the case that the *intended* model is: a scoped token (`stack_id` present) must remain restricted to that stack everywhere, while `CCMenuController` silently drops that restriction for any caller who reaches it directly with a stack-scoped token and Basic Auth or bearer credentials rather than the URL Shipit itself generated.

### Impact Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` credential (created deliberately to restrict a token/integration to one stack, e.g. via `CCMenuUrlController`'s flow or the `ApiClientsController` UI) can read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, activity) of every other stack in the Shipit installation by supplying a different `stack_id` to `GET /:stack_id/ccmenu.xml`. This is an unauthenticated-for-that-resource read of stack state that the requester was never granted, matching the "High" bucket: escalation past the token's authorized scope into reading stack state for repositories/environments the credential holder should have no visibility into.

### Likelihood Explanation
Exploitation only requires possessing any valid stack-scoped `read:stack` `ApiClient` token — a token intentionally handed to lower-trust integrations/build-status widgets scoped to a single stack — and knowing or guessing another stack's `stack_id`/path parameter. No additional privilege, secret, or race condition is needed; this is a straightforward authorization-scoping bug reachable via a single request.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` go through the scoped `stacks` helper (as `BaseController` and `StacksController` do) instead of `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so a stack-scoped token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to stack `A` with `permissions: ['read:stack']` (e.g. via the "CCMenu Client" flow generated by `CCMenuUrlController`, or via `ApiClientsController`), and record its `authentication_token`.
2. Send `GET /:owner/:repo-of-B/:env-of-B/ccmenu.xml?token=<token-scoped-to-A>` (or via Basic Auth) targeting a different stack `B` that the token was never granted access to.
3. `CCMenuController#authenticate_api_client` authenticates the token; `require_permission :read, :stack` passes because the token does have `read:stack` in its permission list; `stack` resolves `B` directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction.
4. The response renders stack `B`'s build/deploy status even though the token is only supposed to authorize stack `A`.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
