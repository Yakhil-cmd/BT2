### Title
Hookify PreToolUse hook fails open on any error, silently allowing Bash/Edit/Write/MultiEdit operations that should be blocked - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
`plugins/hookify/hooks/pretooluse.py` is designed to fail open: any import error at module load, or any exception raised while parsing stdin/loading rules/evaluating rules inside `main()`, is caught and converted into an `exit(0)` with an advisory `systemMessage`, meaning the protected tool call (Bash/Edit/Write/MultiEdit) is always allowed to proceed regardless of what the rule engine intended to enforce. This is explicit, intentional behavior encoded in comments (`# If imports fail, allow operation and log error`, `# ALWAYS exit 0 - never block operations due to hook errors`), and it converts hookify from a hard security boundary into a best-effort advisory system.

### Finding Description
Two distinct fail-open surfaces exist in `main()`:

1. Import guard (lines 25-32): if `hookify.core.config_loader` or `hookify.core.rule_engine` fail to import (e.g. `CLAUDE_PLUGIN_ROOT` misconfiguration, sys.path pollution, corrupted plugin files), the script prints `{"systemMessage": "Hookify import error: ..."}` and calls `sys.exit(0)` before any rule is ever evaluated [1](#0-0) . Note this branch executes unconditionally at process start and is not reachable purely by crafting stdin/hook JSON — it depends on the host's environment/plugin installation, so the specific "hook JSON induces an import error" causal chain in the question is not directly demonstrable.

2. Runtime guard (lines 37-70): `input_data = json.load(sys.stdin)`, `load_rules(event=event)`, and `engine.evaluate_rules(rules, input_data)` are wrapped in a blanket `try/except Exception`, and the `finally` block always calls `sys.exit(0)` [2](#0-1) . Any malformed stdin JSON, any exception in the config loader while parsing `.claude/hookify.*.local.md` rule files (which are ordinary repository content an attacker with PR/commit access to the repo could alter), or any bug in `RuleEngine.evaluate_rules` results in the hook printing an error message but returning normally — the calling Claude Code harness then treats this as "no decision" and permits the Bash/Edit/Write/MultiEdit call to execute.

Because the design goal of hookify is to block dangerous tool calls before they execute, an attacker who can influence the repository-controlled rule files or trigger a parsing/evaluation exception (via unusual but valid-looking tool-call JSON shapes, or malformed rule markdown/frontmatter) can turn a would-be `deny` decision into a silent `allow`.

### Impact Explanation
This breaks the invariant that hook startup/runtime failures must not silently disable a required security boundary. Any bug or malformed input that reaches the exception handlers causes the guard to be bypassed rather than fail closed, which matches "Logic-level service disruption caused by bypassing a required guard or misbinding security state." The severity is bounded by the fact that hookify is a local, opt-in developer safety net (not a remote-attacker-facing trust boundary) and the same fail-open pattern is repeated across `posttooluse.py`, `stop.py`, and `userpromptsubmit.py` per the plugin's stated philosophy.

### Likelihood Explanation
Triggering the import-error branch requires control of the local plugin installation/environment, which an unprivileged remote attacker relying only on repository content cannot achieve directly. Triggering the runtime `except Exception` branch is more plausible: an attacker who can influence a repo's `.claude/hookify.*.local.md` rule definitions or induce a code path with malformed/edge-case data could cause `load_rules`/`evaluate_rules` to raise, and the fail-open finally-block guarantees the operation proceeds. This requires some ability to plant or corrupt hookify rule files in the target repo, which is a stronger precondition than "attacker controls hook JSON" as stated in the question.

### Recommendation
Distinguish "no rules configured" from "rule evaluation failed": on `ImportError` or any exception during rule loading/evaluation, the hook should fail closed for security-relevant rule categories (or at minimum surface a `permissionDecision: "ask"`/deny with a clear error rather than silently allowing), instead of unconditionally `sys.exit(0)` with only an advisory `systemMessage`. Add regression tests asserting that a broken rule file or a rule-engine exception does not result in an allow decision when a matching rule would have denied the operation.

### Proof of Concept
Unit test plan (pytest):
1. Monkeypatch `hookify.core.config_loader.load_rules` to raise `Exception("boom")`.
2. Provide stdin JSON: `{"tool_name": "Bash", "tool_input": {"command": "rm -rf /"}}`.
3. Run `pretooluse.main()` and capture stdout/exit code.
4. Assert: exit code is `0` and stdout contains `{"systemMessage": "Hookify error: boom"}` — demonstrating the dangerous Bash command is allowed to proceed instead of being blocked, confirming the fail-open bypass.
5. Repeat with a genuinely malformed `.claude/hookify.bash.local.md` rule file (e.g., invalid frontmatter) to show `load_rules` raising in the real (non-mocked) code path, and confirm the same fail-open `exit(0)` behavior.

```python
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
