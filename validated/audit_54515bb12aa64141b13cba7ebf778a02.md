### Title
DenyReserveTransferToRelayChain lacks DenyRecursively wrapping, allowing nested-instruction bypass of the relay-chain reserve-transfer deny filter - ([File: system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs])

### Summary
The `Barrier` on Asset Hub Polkadot wraps `DenyReserveTransferToRelayChain` directly inside `DenyThenTry`, without the `DenyRecursively` adapter that other system chains in this same codebase (bridge-hub-polkadot, bulletin-polkadot) use for the identical deny rule. `DenyReserveTransferToRelayChain` only pattern-matches instructions at the top level of the XCM instruction slice passed to the barrier, so a `DepositReserveAsset`/`TransferReserveAsset`/`InitiateReserveWithdraw` instruction targeting the Relay Chain nested inside `SetAppendix`/`SetErrorHandler` (or other wrapping instructions) is not inspected by the deny check, letting it execute later without a second barrier pass.

`DenyReserveTransferToRelayChain` (from `xcm-builder`) matches specific top-level instruction variants (`InitiateReserveWithdraw`, `DepositReserveAsset`, `TransferReserveAsset`) whose `dest`/`reserve` equals the Relay Chain, walking only the linear instruction slice of the message being checked. It does not descend into the nested `Xcm` programs carried inside instructions such as `SetAppendix`, `SetErrorHandler`, or `ExecuteWithOrigin`. `DenyRecursively` was introduced upstream specifically to close this gap by recursively scanning nested XCM programs for the same denied patterns. Asset Hub Polkadot (and Asset Hub Kusama, Collectives, Coretime, Encointer, and the People chains) still use the non-recursive form.

The `Barrier::should_execute` is invoked once, at the start of message processing via `XcmExecutor`; instructions inside an appendix/error-handler set via `SetAppendix`/`SetErrorHandler` are executed inline by the executor after the main program completes, without a fresh call into `Barrier`. Therefore an unprivileged user who can submit an arbitrary local XCM program (e.g. via the `pallet_xcm::execute` extrinsic, or a proxy calling it, or via `pallet_xcm::send`-then-self-target flows) can construct a program whose top-level instructions pass `DenyReserveTransferToRelayChain` and the rest of `DenyThenTry`'s allow-list, but whose `SetAppendix`/`SetErrorHandler` payload contains a `DepositReserveAsset`/`TransferReserveAsset`/`InitiateReserveWithdraw` targeting the Relay Chain location, which then executes when the appendix runs.

### Impact Explanation
If reached, this would defeat the explicit safety measure that these system chains implement to prevent reserve-transfers of the Relay Chain's native asset back to the Relay Chain (a case the emulator test suite explicitly asserts must fail, e.g. `reserve_transfer_dot_from_asset_hub_to_relay_fails`-style tests). Whether this becomes an actual asset-duplication/mint issue depends on whether the Relay Chain's own `IsReserve`/`IsTeleporter` configuration would accept an incoming `ReserveAssetDeposited` from Asset Hub for its native DOT — that downstream trust boundary is out of scope for this file, but at minimum the finding shows the local deny-barrier invariant on Asset Hub Polkadot can be structurally bypassed for nested reserve-transfer-to-relay instructions, which is exactly the vulnerability class `DenyRecursively` was created to close on sibling system chains.

### Likelihood Explanation
The precondition is only that an unprivileged, signed account can submit an XCM program for local execution (e.g. `pallet_xcm::execute`) containing a `SetAppendix`/`SetErrorHandler` instruction whose inner program includes a relay-chain-targeted reserve instruction, and that the top-level program otherwise satisfies one of the `Allow*` barriers (e.g. `AllowTopLevelPaidExecutionFrom<Everything>` by paying local fees). This does not require any privileged origin, governance action, or malicious peer — it is a standard, attacker-controlled extrinsic path. The asymmetry between chains in the same repository (some wrapped with `DenyRecursively`, some not) demonstrates the gap is a real, reproducible configuration difference rather than a hypothetical.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` with `DenyRecursively` in `Barrier` on Asset Hub Polkadot (and audit/update Asset Hub Kusama, Collectives, Coretime, Encointer, and People chains identically), matching the pattern already used on Bridge Hub Polkadot/Kusama and Bulletin Polkadot:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... )
    >,
>;
```

### Proof of Concept
xcm-emulator integration test plan:
1. On `AssetHubPolkadot`, as `AssetHubPolkadotSender` (unprivileged signed account), call `PolkadotXcm::execute` with a hand-crafted `Xcm` program:
   - `WithdrawAsset` (DOT from own balance) into holding,
   - `BuyExecution` for local fee payment (to satisfy `AllowTopLevelPaidExecutionFrom<Everything>`),
   - `SetAppendix(Xcm(vec![DepositReserveAsset { assets: Wild(All), dest: Parent.into(), xcm: Xcm(vec![]) }]))`,
   - `ClearOrigin`/no-op tail instruction to complete the main program normally.
2. Assert the top-level `execute` call succeeds (i.e., is NOT filtered), and that a `ReserveAssetDeposited`-style message is queued/sent toward the Relay Chain (checked via `ParentDownwardMessageQueue`/dmp queue mock or `assert_expected_events!` for XCM sent).
3. Contrast with the direct `limited_reserve_transfer_assets` extrinsic call (as in existing `reserve_transfer_dot_from_asset_hub_to_relay_fails`), which correctly fails with `Filtered`, to demonstrate the deny filter is bypassed only via the nested-appendix path.
4. Add a unit test on the `Barrier` type directly: build `Xcm(vec![SetAppendix(Xcm(vec![DepositReserveAsset{ dest: RelayChainLocation, .. }]))])`, call `Barrier::should_execute`, and assert it currently returns `Ok(())` (bypass) instead of `Err(ProcessMessageError::Unsupported)`.
