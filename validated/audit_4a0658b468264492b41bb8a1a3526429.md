### Title
AA bounce mechanism traps all trigger assets when a non-transferable/spender-attested asset among them cannot legally be returned - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) needs to refund a trigger's funds (bounce), it builds one atomic response unit that returns *every* asset the trigger sent, including base bytes. If any single one of those assets cannot legally be paid back to the trigger's sender (e.g. it is `is_transferrable=false` and neither party is the asset definer, or it requires `spender_attested`/`cosigned_by_definer`, or it is a private asset), unit validation or payload composition for that asset fails. Because the bounce logic treats the whole set of asset refunds as a single all-or-nothing unit, this single blocked asset causes the AA to abandon the refund entirely — losing/trapping not just the blocked asset but also the base bytes and any other, otherwise-returnable assets that were part of the same trigger.

### Finding Description
`bounce()` iterates over every asset present in `trigger.outputs` and builds one payment message per asset to send it back to `trigger.address` in a single unit, then calls `sendUnit(messages)`: [1](#0-0) 

`sendUnit()` processes each asset message with `storage.loadAssetWithListOfAttestedAuthors`, and explicitly bails out for private assets ("it'll fail validation anyway due to lack of spend_proofs"): [2](#0-1) 

If any of these per-message checks fails, `async.eachSeries` returns an error to the outer callback, which calls `bounce(err)` again: [3](#0-2) 

Critically, `bounce()` guards re-entry with `bBouncing`: once bouncing has started, any subsequent failure (including a failure that occurs while trying to build the bounce unit itself) causes it to `finish(null)` — i.e., give up with no response unit at all: [4](#0-3) 

Even after the messages pass composition, the resulting unit still has to pass full network validation via `validateAndSaveUnit`, which enforces asset transferability rules (`is_transferrable`, `cosigned_by_definer`, `spender_attested`): [5](#0-4) [6](#0-5) 

If that validation fails (e.g. because the returned asset is not transferable and neither the AA nor `trigger.address` is the asset's definer), `bounce(err)` is invoked, and since `bBouncing` is already `true`, the AA calls `finish(null)` with no messages sent at all: [7](#0-6) 

Meanwhile, the AA has already credited its balance with the trigger's incoming assets during `updateInitialAABalances` before the bounce attempt, and that balance update is not reverted when the bounce fails to build a valid unit. This means all assets sent along with the trigger — bytes and any other, legitimately-transferable assets — become permanently stuck in the AA's balance with no way to recover them, purely because one of the assets bundled in the same trigger unit happens to be non-transferable, attestation-restricted, cosigned-by-definer, or private.

This is the same root-cause class as the external report: bundling multiple assets into a single all-or-nothing operation means a transfer restriction on just one asset prevents recovery/settlement of the rest.

### Impact Explanation
Any user (or attacker) can send a trigger unit to any AA that includes bytes plus a restricted asset (an asset they define themselves with `is_transferrable=false`, `cosigned_by_definer=true`, or `spender_attested=true` without the AA/trigger-address being attested, or even a private asset). If the AA's evaluation needs to bounce (due to any error condition — insufficient balance, invalid data, formula error, etc.), the entire bounce fails silently, and all bytes and all assets sent in that trigger unit — not just the restricted one — become permanently locked in the AA's balance. This is a direct fund-freezing/fund-loss impact for the trigger's author, and it can be deliberately triggered by any AA caller, making it reachable without any privileged role.

### Likelihood Explanation
This requires no special privileges: any address can define an asset with `is_transferrable=false`/`cosigned_by_definer=true`/`spender_attested=true`, issue it to itself, and send it (with some bytes) to any AA in a trigger unit crafted to force a bounce (e.g., by sending insufficient bytes for the AA's expected logic, or malformed `data`). This is easily reproducible and does not depend on the AA's own definition/logic being flawed — it is a systemic property of the bounce composition path in `aa_composer.js`.

### Recommendation
Change the bounce mechanism so that a transfer failure for one asset does not abort refunds for the others: attempt to compose/validate each asset's refund payment independently (or in a way that a rejection for one asset removes only that asset's message rather than aborting the whole bounce), and only forfeit/keep assets that genuinely cannot be returned (e.g. non-transferable ones lacking a valid recipient), while still returning bytes and other unaffected assets to the sender.

### Proof of Concept
1. Define an asset A with `is_transferrable: false`, `issued_by_definer_only: true`, and yourself as definer/issuer.
2. Issue some units of A to your own address.
3. Send a trigger unit to a target AA containing both bytes (say, an amount below the AA's expected trigger.data threshold, guaranteeing a bounce) and some amount of asset A as payment outputs to the AA.
4. The AA evaluation fails and calls `bounce()`, which builds messages returning both bytes and asset A to your address.
5. Because A `is_transferrable=false` and neither your address nor the AA is A's definer, `validateAndSaveUnit` rejects the composed bounce unit (`aa_composer.js:1405-1411`, `validation.js:2616-2629`).
6. `bounce(err)` is called a second time; `bBouncing` is already `true`, so `finish(null)` executes (`aa_composer.js:923-927`) with no response unit produced.
7. Result: the bytes and asset A sent in step 3 remain credited to the AA's balance (per `updateInitialAABalances`) with no way for you to retrieve them — permanent fund loss triggered entirely by your own choice of asset A's parameters.
