Confirmed: `Handler#repository_name` resolves the target repository purely from `payload.dig('repository', 'full_name')` [1](#0-0)  while `WebhooksController#verify_signature` selects which organization's GitHub App/webhook secret to validate the HMAC against using a *different* field, `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [2](#0-1) , [3](#0-2) . Both fields come from the same unauthenticated, attacker-controlled JSON body, and nothing cross-checks that `repository.owner.login` matches `repository.full_name`'s owner segment before the signature is deemed "verified" and the payload is dispatched to handlers such as `PushHandler` [4](#0-3) , which looks up the target `Stack` via `Repository.from_github_repo_name(repository_name)` [5](#0-4) .

### Title
Webhook signature verification checks a different organization than the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization deployments (`Shipit.github(organization:)` per-org config), the webhook signature check authenticates the payload against the GitHub App/secret belonging to `repository.owner.login`, but the actual write target (which `Stack`/`Repository` gets synced, has its commit `status` updated, etc.) is derived from the separate `repository.full_name` field. Since both fields are attacker-supplied JSON before verification, an attacker who controls (or has installed the Shipit GitHub App on) one organization can forge a valid signature using that organization's known webhook secret while setting `repository.full_name` to point at a victim organization's repository, causing Shipit to process the forged event as if GitHub had sent it for the victim's stack.

### Finding Description
The comparison bug class described in the report is: two computed values are supposed to be equal/tied to a single ground truth, but the code lets an attacker manufacture a mismatch that resolves in their favor. Here the analogous binding is:
`organization whose webhook secret authenticated the request == organization that owns the repository actually written to by the handler`.

- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to pick `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is used to validate `X-Hub-Signature` over the raw body [6](#0-5) .
- `Handler#repository_name` (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) independently reads `payload.dig('repository', 'full_name')` to resolve the `Repository`/`Stack` to act on [1](#0-0) .
- `Repository.from_github_repo_name` just splits `full_name` on `/` and looks the record up by `owner`/`name` columns, with no relation back to which GitHub App validated the request [5](#0-4) .

Because these two lookups read different sub-paths of the same unauthenticated JSON body, and the signature only proves "this body was HMAC-signed with organization X's secret," not "this body's `repository.full_name` belongs to organization X," an attacker who knows any configured organization's `webhook_secret` (e.g., because they administer that org's own Shipit-integrated GitHub App installation, a legitimate but low-trust org) can compute a valid `X-Hub-Signature` for a crafted body where `repository.owner.login` is their own org but `repository.full_name` names a victim org's stack.

### Impact Explanation
This breaks the "organization authenticated versus repository written" binding required by the rules, and the outcome is a cross-organization forged webhook affecting a repository the attacker does not control. Depending on the event type dispatched, this enables:
- `push`: force a `GithubSyncJob`/`sync_github` call on the victim's `Stack` with an attacker-chosen `expected_head_sha`, potentially triggering deploy pipeline state changes on a stack the attacker has no access to.
- `status`: write forged commit statuses onto the victim's commits, which can gate/unblock deploys depending on `shipit.yml` required statuses.
This is a cross-organization write triggered by an unprivileged party who is not a collaborator on the victim repository, matching the "cross-repository writes" / "unauthorized deploy" high-impact bar.

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for *some* organization configured in the multi-org `github:` secrets block — realistic in the documented "Using Multiple Github Applications" setup where different orgs/teams each run their own GitHub App with their own secret [7](#0-6) . An org owner who is legitimately entitled to know their own org's webhook secret is exactly the "unprivileged attacker relative to the victim org" scenario the rules ask for. No GitHub App private key, session, or `ApiClient` token is needed — only the raw HTTP POST to `/webhooks` with a forged `X-Hub-Signature`.

### Recommendation
After computing `repository_owner` for GitHub App selection, also derive the owner from `repository.full_name` (or `organization.login`) and reject the request (`head 422`) unless they match the configured organization whose secret validated the signature. Alternatively, resolve the target `Repository`/`Stack` using the same `repository_owner` value that was authenticated, rather than independently re-parsing `full_name` in `Handler#repository_name`.

### Proof of Concept
1. Attacker registers/owns GitHub organization `attacker-org` and installs Shipit's GitHub App there per the documented multi-org setup, thereby learning `webhook_secret` for `attacker-org`.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(body, attacker-org's webhook_secret)>` and POSTs to `Shipit::Engine`'s `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` reads `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC verifies successfully since the attacker used the correct secret for that org [2](#0-1) .
5. `WebhooksController#create` dispatches to `PushHandler`, which resolves `repository_name = "victim-org/victim-repo"` and calls `sync_github` on the victim stack — a write on a repository the attacker never authenticated against [4](#0-3) , [1](#0-0) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
