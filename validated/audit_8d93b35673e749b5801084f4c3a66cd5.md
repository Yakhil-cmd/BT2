### Title
Uncaught `throw Error` in oscript selector/dot-path evaluation crashes the node process on a malformed but validation-passing AA trigger `data` payload - (File: formula/evaluation.js)

### Summary
`formula/evaluation.js`'s `selectSubobject()` (used to resolve `.field` / `[[...]]` selector chains such as `trigger.data.foo` or `$x.messages[[...]]`) has a final `else` branch that unconditionally does `throw Error("unknown type of subobject: " + value)` instead of routing the failure through the `cb`/`setFatalError` mechanism used everywhere else in the same function. This is directly analogous to CVE-2024-31227: a syntactically well-formed, "authorized" input (a Redis ACL selector / here, an oscript selector operating on ordinary JSON `data`) reaches a code path that was not defensively handling every possible value, causing an unhandled panic/crash instead of a graceful rejection.

### Finding Description
`trigger.data` payloads attached to a `data` message are raw, attacker-controlled JSON, and `isObjectWellFormed()` in `validation.js` only rejects lone surrogates / NUL bytes — it explicitly allows any other JSON value, including `null`. [1](#0-0) 

When an AA (Autonomous Agent) formula dereferences a field of `trigger.data` via a dot-path (e.g. `trigger.data.foo`) or a bracket selector (e.g. `$x.messages[[...]].field`), `selectSubobject()` walks the object graph key by key: [2](#0-1) 

After the key walk completes, the result is dispatched by `typeof`:
```
else if (typeof value === 'object' && value !== null) { ... }
else
    throw Error("unknown type of subobject: " + value);
``` [3](#0-2) 

If the resolved `value` is `null` (a perfectly legal JSON value that any user can put into a `data` message payload, e.g. `{"foo": null}`), none of the preceding branches (`boolean`, `number`, `Decimal`, `string`, `object && !== null`) match, and the function falls into the unconditional `throw Error(...)`. Unlike every other failure path in `evaluate()`/`selectSubobject()`, which reports errors through `cb(err)` / `setFatalError(...)` so the AA gracefully bounces, this throw is a synchronous JS exception raised deep inside an `async.eachSeries` callback chain. It is not wrapped in a `try/catch` at this call site or in the callers (`aa_composer.js`'s `handleTrigger`/`replace`, or the top-level `exports.evaluate`), so it propagates up the call stack as an uncaught exception during unit/AA-trigger processing rather than being converted into a formula error.

### Impact Explanation
This is reachable by any unprivileged unit poster: simply send a payment to an AA together with a `data` message whose payload contains a `null` value at a path that the AA's own formula dereferences (many published AAs use `trigger.data.<field>` patterns, and the field name/shape is controlled by the AA author but the *value* supplied in `trigger.data` is controlled by the triggering unit's author). Triggering the uncaught throw during trigger processing (`handleTrigger`/`aa_composer.js`) crashes the Node.js process handling that unit for every full node evaluating the AA, i.e. a network-wide denial of service against nodes running that AA (an authenticated-poster, in-scope attack surface, not a network/p2p/mocked path). This matches the "node unable to confirm new units" impact criterion — a corrupted/killed node cannot continue validating and closing MC, and repeated posting can be used to keep taking down nodes that host the AA.

### Likelihood Explanation
Likelihood is high for any AA that exposes a `trigger.data.<field>` access without first checking for `none`/`is_array`/typeof: an attacker only needs to post a normal `data` app message with a `null`-valued JSON field targeting an existing, unprivileged, publicly triggerable AA. No special privileges, keys, or races are required, and the malformed value passes all current unit/JSON well-formedness checks in `validation.js` before reaching formula evaluation.

### Recommendation
In `selectSubobject()`'s final dispatch (`formula/evaluation.js` ~line 2967-2974), explicitly handle `value === null` (and any other non-enumerated type) by routing to `cb(false)`/`setFatalError(...)` the same way other malformed intermediate results are handled elsewhere in the function, instead of `throw Error(...)`. Additionally, wrap the top-level `formulaParser.evaluate` invocation paths in `aa_composer.js` (`handleTrigger`, `replace`, `evaluateAA`) with defensive `try/catch` so that any future unexpected internal throw degrades to an AA bounce rather than crashing the node process.

### Proof of Concept
1. Publish (or use an existing) publicly-triggerable AA whose `messages` template dereferences `trigger.data` with a bare dot-path, e.g.:
```
{ app: 'payment', payload: { asset: 'base', outputs: [ { address: "{trigger.address}", amount: "{trigger.data.amount}" } ] } }
```
2. Send a trigger unit to this AA with:
```
messages: [
  { app: 'payment', payload: { outputs: [ { address: AA_ADDRESS, amount: 10000 } ] } },
  { app: 'data', payload: { amount: null } }
]
```
3. `trigger.data.amount` resolves through `selectSubobject()`; the final key lookup yields `value = null`, none of the `typeof` branches match, and `throw Error("unknown type of subobject: null")` fires uncaught inside the AA trigger handling pipeline, crashing the processing node instead of bouncing the AA response as intended.

(Note: I was not able to execute this PoC against a running node in this environment; the trace is derived purely from static code reading of `formula/evaluation.js`, `aa_composer.js`, and `validation.js`. Confirming whether an outer `try/catch` elsewhere in the process (e.g. a top-level `uncaughtException` handler) mitigates the crash to a "log and continue" versus a hard process exit would require running the code, which I could not verify with the tools available.)
