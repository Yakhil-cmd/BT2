### Title
Automatic status transition to `dispute_resolved`/`in_appeal` permanently blocks `complete()`, trapping arbiter-contract funds - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` implements a client-side finite-state machine for arbiter-mediated contracts whose funds sit in a shared (multisig) address. The only function that composes the payment releasing those funds to the winner, `complete()`, requires `objContract.status === "paid" || objContract.status === "in_dispute"`. However, as soon as the arbiter posts its resolution unit, an automatic event listener force-transitions the contract's local status to `dispute_resolved` — a status `complete()` explicitly rejects — with no code path that ever moves the contract back to `paid`/`in_dispute` or otherwise triggers a valid `complete()` call. The same is true for the `in_appeal`/`appeal_approved`/`appeal_declined` terminal states reached via `appeal()`. This mirrors the GoGoPool bug class: a state-machine "no man's land" is reached automatically/by a third party, after which the fund-release function's precondition can never be satisfied again.

### Finding Description
The relevant status values are declared in `wallet_arbiter_contracts.status` CHECK constraint: `pending, revoked, accepted, signed, declined, paid, in_dispute, dispute_resolved, in_appeal, appeal_approved, appeal_declined, cancelled, completed` [1](#0-0) .

Funds are moved into the shared contract address by `pay()`, which sets status to `paid` [2](#0-1) .

`complete()` is the only function that composes and sends the payment releasing funds from the shared address to the winning party, and it gates on the status field: [3](#0-2) 

When an arbiter posts a resolution unit (a `data_feed` message naming the winning address), a `new_my_transactions` listener automatically detects it and unconditionally overwrites the contract's status to `dispute_resolved`, regardless of whether `complete()` has already been invoked: [4](#0-3) 

Once `status` is `dispute_resolved`, `complete()`'s guard (`status !== "paid" && status !== "in_dispute"`) rejects any further call, so the payment can never be composed by this function again. The state machine's `appeal()` function offers a further path out of `dispute_resolved` into `in_appeal`, and the peer/arbstore device-message handler in `wallet.js` allows `in_appeal` to transition into terminal `appeal_approved`/`appeal_declined` states: [5](#0-4) 

None of `dispute_resolved`, `in_appeal`, `appeal_approved`, or `appeal_declined` are ever accepted by `complete()`'s status check, and no other function in `arbiter_contract.js` composes/sends the release payment. There is no reachable code path that returns the FSM to `paid`/`in_dispute` from these states.

### Impact Explanation
Once the arbiter's resolution unit is received (an event entirely outside the winning party's control — it happens automatically upon `new_my_transactions`), the local wallet software's only mechanism for building the fund-release transaction becomes permanently unusable for that contract. The funds previously sent to the shared multisig contract address (built via `pay()`) can no longer be swept out through `arbiter_contract.js`'s intended, well-formed payment composition (which — for the non-private-asset path — reads the shared address definition to correctly split peer/arbstore amounts, see `complete()` lines 752–773 in `arbiter_contract.js`). This is a fund-freezing state-machine bug analogous to the referenced GoGoPool finding: an automatically/externally triggered transition into a state the withdraw function's guard doesn't recognize, permanently blocking the legitimate fund-release path for a paired-device counterparty in a private or public arbiter contract.

### Likelihood Explanation
Likelihood is high for any contract that goes to dispute: as soon as the arbiter (a third party outside the local wallet's control) posts its verdict on-chain, the automatic listener fires and flips the status before the recipient's wallet necessarily has a chance to call `complete()`. No malicious behavior by a hub, node, or operator is required — this occurs during the contract's normal, intended dispute-resolution flow, triggered purely by data already reaching the wallet through the standard `new_my_transactions` event.

### Recommendation
Update `complete()`'s valid-status check to also accept `dispute_resolved`, `in_appeal` (post cosigner-approved appeal outcome), `appeal_approved`, and `appeal_declined`, mirroring the C4 mitigation pattern of adding the missing state-transition guard (`requireValidStateTransition`) so a resolved/appealed contract's counterparty can still withdraw funds. Alternatively, have the resolution/appeal-outcome listeners automatically invoke `complete()` (or a dedicated release function) once the final winner is known, instead of leaving the status in a dead-end state that no function will ever act upon.

### Proof of Concept
1. Payer calls `pay()` — funds move to the shared contract address, status becomes `paid`.
2. Payee opens a dispute (`openDispute()`), status → `in_dispute`.
3. Arbiter posts its resolution unit naming a winner.
4. The `new_my_transactions` listener at `arbiter_contract.js:879-896` fires automatically and sets status → `dispute_resolved` before the payee calls `complete()`.
5. Payee (or payer) calls `complete(hash, ...)`; it fails at the guard `objContract.status !== "paid" && objContract.status !== "in_dispute"` [6](#0-5)  because status is now `dispute_resolved`.
6. No other exported function in `arbiter_contract.js` composes the release payment, and no listener returns status to `paid`/`in_dispute` — funds in the shared address remain unclaimed via the intended workflow.
