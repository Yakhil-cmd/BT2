### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independently attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of the RIPEMD160 bug: the precompile used one pointer (`start`) to *authorize* a dictionary-finalize operation while a different, unsynchronized pointer (`x`) was actually operated on, breaking the invariant that both must reference the same object. In `Shipit::WebhooksController`, the field used to select *which* GitHub App/organization secret authenticates the incoming webhook (`repository.owner.login`, or the `organization.login` fallback) is a different JSON field than the one every event handler uses to decide *which* `Repository`/`Stack` the payload is allowed to mutate (`repository.full_name`). Nothing enforces that these two attacker-suppliable fields describe the same repository/organization.

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret to validate the request with based on a value taken directly out of the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) and is used to look up which `Shipit.github(organization:)` app config (and thus which `webhook_secret`) must validate `X-Hub-Signature`.

Once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches the same raw payload to handlers such as `PushHandler`, `StatusHandler`, and the `PullRequest::*` handlers. Every one of these resolves the target `Repository`/`Stack` from a *different* field of the same body — `repository.full_name`: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler` is especially significant because it writes attacker-supplied `state`/`description`/`context`/`created_at` directly to a `Status` row for any commit matching `params.sha` (a globally-scoped `Commit.where(sha:)`, not scoped by repository at all), and creating a `Status` with `state: 'success'` schedules continuous delivery: [6](#0-5) [7](#0-6) 

and `Stack#trigger_continuous_delivery` will `trigger_deploy` (i.e. execute `shipit.yml` deploy steps on the deploy host) once a commit is deemed deployable: [8](#0-7) 

**Broken invariant (equality that should hold but doesn't):**
`organization_used_to_select_webhook_secret (params.repository.owner.login / params.organization.login)` MUST equal `organization_that_owns_the_repository_the_handler_writes_to (derived from params.repository.full_name)`. The controller never checks this; it only checks that *some* organization's secret validates the raw body, then blindly lets the handler trust `full_name`, `sha`, `state`, etc., from the same body.

This is the deployment-trust binding named in the rules: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Any party who legitimately administers a GitHub App/organization already onboarded into this Shipit instance (Shipit explicitly supports multiple GitHub orgs, each with its own `webhook_secret` per `test/dummy/config/secrets_double_github_app.yml`) knows their own org's webhook secret, since they configured it themselves as part of onboarding. That party can then:
1. Set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` picks their own known secret and the HMAC passes.
2. Set `repository.full_name`, `sha`, `state`, etc. to point at a victim repository/stack tracked by the same Shipit instance, owned by a *different* organization.

For `push`, this only triggers a resync against real GitHub state (lower impact). For `status`, the handler creates a `Status` row directly from attacker-controlled payload fields for any `Commit` row matching `sha` across the whole instance, with no ownership check tying the commit to the forger's org — this can flip a victim stack's commit to `success`, which (if continuous deployment is enabled) causes Shipit to execute the victim's `deploy` steps from `shipit.yml` on the deploy host: an unauthorized deploy triggered by a party with no privileges over the victim organization/repository/stack.

### Likelihood Explanation
Medium-to-High for tenants running Shipit with multiple onboarded GitHub organizations (a documented, supported configuration). The only precondition is possessing a legitimate webhook secret for *any one* organization configured in the same Shipit instance — no access to the victim's secret, `GITHUB_TOKEN`, or a Shipit session/API token is required, matching the "unprivileged attacker" framing.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), require that the organization/owner used to select the verifying `webhook_secret` be reconciled against the owner implied by `repository.full_name` before any handler processes the payload — e.g., derive both from the same trusted source, or reject the payload if `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, scope `StatusHandler`'s `Commit.where(sha:)` lookup by the resolved, verified repository/stack rather than allowing a global cross-repository match.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which is configured in this Shipit instance with its own `webhook_secret_A` (a supported multi-org deployment, per `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha tracked by victim-org/victim-repo stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` with `webhook_secret_A` (known to them) and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully against `webhook_secret_A`.
5. `Shipit::Webhooks.for_event("status")` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` — creating a `success` status on the victim's commit regardless of which org "authenticated" the request.
6. If `victim-org/victim-repo`'s stack has `continuous_deployment: true`, this status change schedules and can trigger an actual deploy of the victim's application.
