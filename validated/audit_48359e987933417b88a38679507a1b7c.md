Based on my investigation, I found a concrete admission-boundary mismatch in the multisig transaction payload validation flow.

### Title
Multisig transaction execution can bypass on-chain approved payload when `abort_if_multisig_payload_mismatch` feature is disabled - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`validate_multisig_transaction` — the prologue function invoked both during mempool/VM admission and at the start of execution for `MultisigTransaction` payloads — is supposed to bind the executed payload to the payload that owners actually approved. However, when the full payload was stored on-chain (via `create_transaction`) and the feature flag `abort_if_multisig_payload_mismatch_enabled` is not enabled, the code path that checks the submitted payload against the stored, owner-approved payload is entirely skipped.

### Finding Description
In `validate_multisig_transaction`: [1](#0-0) 

the payload-match check is gated by `features::abort_if_multisig_payload_mismatch_enabled()`:
```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
```
If this feature is disabled, an owner who has met the k-of-n approval quorum for `sequence_number` (verified earlier via `can_be_executed`/`can_execute`) can call `execute_multisig_transaction`-style entry with the transaction's `payload_hash` unset and a *different* `payload` than the one that owners actually approved and that is stored on-chain in `transaction.payload`, because:
1. The `payload_hash.is_some()` branch is skipped (it's `None` when the full payload was stored via `create_transaction`).
2. The `payload == *stored_payload` branch is skipped entirely because the feature flag is off.

The only remaining binding is `assert_transaction_exists`/quorum count on `sequence_number` — none of which validates *which* payload is being executed. The VM-side caller (`run_multisig_prologue`/`execute_multisig_transaction` in `aptos-move/aptos-vm/src/aptos_vm.rs`) constructs `provided_payload` directly from the submitted transaction's executable and feeds it into `validate_multisig_transaction`/`get_next_transaction_payload`, so the actual bytes executed come from the submitter, not exclusively from on-chain approved state: [2](#0-1) [3](#0-2) 

This breaks the core multisig invariant documented in the module ("Transaction execution will first check with this module that the transaction payload has gotten enough signatures"): the approvals are counted for `sequence_number`, but the actual bytes that get executed as the multisig account are not verified to be the payload that received those approvals when this specific feature flag is off and only a hash was not used.

### Impact Explanation
This is a wrong-payload-under-quorum admission bypass: an owner (who is authorized to execute, but only for the specific payload the other owners approved) can substitute an entirely different entry function / script to run under the multisig account's signer, as long as they alone control the executed transaction's `EntryFunction`/`Script` executable and the on-chain transaction only stored a full payload (not a hash). This is a state-transition-under-wrong-authorization issue: funds/permissions controlled by the multisig account could be moved or modified via a payload the k-of-n owners never approved, effectively executing under an unauthorized approval set for the actual computation performed.

### Likelihood Explanation
The exploitability is entirely gated on `features::abort_if_multisig_payload_mismatch_enabled` being disabled on the target network/chain. I could not verify from the code snippets retrieved whether this flag is enabled by default on mainnet/testnet in the current framework release (feature default state lives in `aptos-move/framework/move-stdlib/sources/configs/features.move` / genesis feature configuration, which I did not fully inspect). Given the flag's name and its being explicitly gated (a "fix flag" pattern common in Aptos framework upgrades), it is plausible this defends against exactly this scenario and may already be enabled in current mainnet genesis — in which case current risk is low/mitigated, matching the "recently fixed, low residual risk" pattern seen in the external USDC report. Without confirming the on-chain/genesis default enablement of this flag, I cannot assert current live exploitability with full confidence; this should be verified against genesis/feature-flag defaults before treating it as an active vulnerability.

### Recommendation
- Make the payload-match assertion unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate) whenever `transaction.payload.is_some()`, regardless of the feature flag, so submitted payload bytes are always checked against the on-chain approved payload.
- Alternatively, if backward compatibility requires the flag, ensure it is enabled by default in genesis for all networks and add a defense-in-depth check requiring `payload` to be non-empty whenever `transaction.payload.is_some()`.
- Add an explicit e2e/unit test asserting that executing a multisig transaction with a payload different from the stored `transaction.payload` fails regardless of feature-flag state.

### Proof of Concept
1. Owner A creates a multisig account requiring 2-of-3 signatures.
2. Owner A calls `create_transaction(multisig_account, PAYLOAD_A)` — a benign transfer — which stores the full `PAYLOAD_A` on-chain (no hash-only variant) and auto-approves as creator.
3. Owner B calls `approve_transaction(multisig_account, seq)`, reaching the 2-of-3 quorum for `seq`.
4. On a network where `abort_if_multisig_payload_mismatch_enabled` is disabled, Owner A (or any owner who can execute) submits the actual `MultisigTransaction` with a `PAYLOAD_B` (e.g., draining funds to their own address) as the transaction executable instead of `PAYLOAD_A`.
5. `validate_multisig_transaction` checks quorum against `seq` (passes, since owner B approved `seq`, not knowing which payload would run), skips the hash check (`payload_hash` is `None`), and skips the payload-match check (feature disabled).
6. `execute_multisig_transaction` in `aptos_vm.rs` executes `PAYLOAD_B` as the multisig account signer, despite only `PAYLOAD_A` having been approved by the required owners.

pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };

    session
        .execute_function_bypass_visibility(
            &MULTISIG_ACCOUNT_MODULE,
            VALIDATE_MULTISIG_TRANSACTION,
            vec![],
            serialize_values(&vec![
                MoveValue::Signer(txn_data.sender),
                MoveValue::Address(multisig_address),
                MoveValue::vector_u8(provided_payload),
            ]),
            &mut UnmeteredGasMeter,
            traversal_context,
            module_storage,
        )
        .map(|_return_vals| ())
        .map_err(expect_no_verification_errors)
        .or_else(|err| convert_prologue_error(err, log_context))
}
