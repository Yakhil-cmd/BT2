### Title
Webhook signature verification keys off `repository.owner.login` while the acted-upon repository comes from `repository.full_name` — cross-organization webhook forgery when any configured org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a webhook against using `repository.owner.login` (or `organization.login`) taken from the **same untrusted JSON body**. However, every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name` and subclasses like `PushHandler`) resolves the repository/stack that is actually acted upon using a **different** field from that same body: `repository.full_name`. These two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "the repository that gets written to" are two independently attacker-controlled values, exactly the binding-break pattern described in the reference report (one accounted value diverging from another value that is actually acted upon).

### Finding Description [1](#0-0) 

`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`verify_webhook_signature` short-circuits to `true` whenever the selected org's `webhook_secret` is blank:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Meanwhile, every handler that decides which `Stack`/`Repository` the payload acts on uses a **different** payload field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 
and, e.g., the push handler:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

Shipit explicitly supports hosting multiple GitHub organizations in one instance, each with its own (optional) `webhook_secret`, as documented and reflected in the config format: [6](#0-5) 
The setup docs describe the webhook secret as "optional": [7](#0-6) 

Because `repository_owner` (used to select the verification key) and `repository.full_name` (used to select the repository that is actually written to) are two unrelated fields of the same attacker-supplied JSON body, an attacker can:
1. Set `repository.owner.login` to the name of any configured organization that has **no `webhook_secret` set** (a legitimate, documented configuration state — the field is optional and many example configs ship with it blank, e.g. `webhook_secret: # nil`), causing `verify_webhook_signature` to return `true` unconditionally, without needing to know any secret at all.
2. Set `repository.full_name` to the full name of a repository belonging to a **different, secured** organization, whose stacks are internally provisioned in Shipit.

The request then bypasses signature verification entirely (step 1) while resolving to and acting on a completely different repository's `Stack` records (step 2), e.g. triggering `GithubSyncJob` for the target stack, which fetches new commits via `stack.github_api` (a legitimately privileged, App-installed credential unrelated to the attacker) and can subsequently invoke `CacheDeploySpecJob` and continuous-delivery scheduling. [8](#0-7) 

### Impact Explanation
This breaks the equality that should hold: `organization_that_authenticated_the_webhook == organization_owning_the_repository_being_acted_upon`. When it doesn't hold, an unauthenticated network attacker (the `/webhooks` endpoint is intentionally public and skips CSRF protection: `skip_before_action :verify_authenticity_token`) can inject synthetic GitHub events (push, status, check_suite, pull_request, membership, etc.) against a target stack belonging to an org whose secret they never possessed, as long as at least one *other* configured org in the same Shipit instance has no webhook secret configured. Depending on the target stack's configuration (e.g. `continuous_deployment: true`), this can escalate to triggering unauthorized syncs and downstream deploy scheduling for a repository the attacker has no legitimate relationship with — matching the "unauthorized deploy" / "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability depends entirely on the deployment having at least one configured organization with a blank `webhook_secret` — which is exactly the state shown by the maintainers' own example configs (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) and explicitly called "optional" in setup docs. Any multi-org Shipit deployment that follows this documented pattern and leaves the secret unset for even one org (e.g., a low-value/staging org) creates the bypass for every other org hosted on the same instance. No credentials, tokens, or sessions are required — only network access to the public `/webhooks` endpoint.

### Recommendation
Do not select the verification key using an attacker-controlled field. Options:
- Bind webhook verification to the repository via `Repository.from_github_repo_name(params.dig('repository','full_name'))&.owner` rather than `repository.owner.login`/`organization.login` taken directly from the body, so the org used to fetch the secret is derived from Shipit's own persisted repository/stack mapping, not from the request body alone.
- Alternatively, once the repository/stack is resolved via `full_name`, re-verify that `repository.owner.login` matches the actually-configured owning organization for that repository before proceeding, rejecting mismatches.
- Require every configured GitHub App entry to have a non-blank `webhook_secret` (remove the "optional" `return true unless webhook_secret` bypass, or restrict it to single-org deployments only), since the "no secret" fallback becomes unsafe as soon as multiple orgs with differing trust levels share one Shipit instance.

### Proof of Concept
Given a `secrets.yml` with two orgs:
```yaml
production:
  github:
    TrustedOrg:
      webhook_secret: real-secret
      ...
    UnsecuredOrg:
      webhook_secret:   # left blank, e.g. a low-priority/staging org
      ...
```
An attacker with no credentials sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/main",
  "after": "<attacker-influenced-sha-that-exists-in-target-repo>",
  "repository": {
    "owner": { "login": "UnsecuredOrg" },
    "full_name": "TrustedOrg/secure-repo"
  }
}
```
- `repository_owner` resolves to `"UnsecuredOrg"`.
- `Shipit.github(organization: "UnsecuredOrg").verify_webhook_signature(...)` returns `true` immediately because `UnsecuredOrg`'s `webhook_secret` is blank — no valid signature is required.
- `PushHandler#repository_name` resolves `"TrustedOrg/secure-repo"`, looks up its `Stack`s, and calls `stack.sync_github(expected_head_sha: "<attacker-influenced-sha>")`, causing `GithubSyncJob` to run against `TrustedOrg`'s repository using Shipit's own privileged GitHub App credentials for that stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
