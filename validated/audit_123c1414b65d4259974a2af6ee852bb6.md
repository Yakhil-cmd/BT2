### Title
Silent dict-continuation field drop on 2-space indentation in `extract_frontmatter()` produces empty-pattern Conditions that always-match or never-match, corrupting hookify rule scope - ([File: plugins/hookify/core/config_loader.py])

### Summary
The hand-rolled YAML parser in `extract_frontmatter()` only treats an indented line under a list dict-item as a continuation field when `indent > 2`, so a continuation line indented with exactly 2 spaces (the same indentation as the `- key: value` marker itself) is silently dropped instead of being merged into `current_dict`. When the dropped field is `pattern`, `Condition.from_dict()` defaults it to `''`, and `_regex_match('', text)` (via `re.compile('').search(text)`) matches virtually any non-empty field value, silently converting a narrowly scoped rule into an always-match (or, for `equals`, into an effectively never-match) rule.

### Finding Description
`extract_frontmatter()` parses `.claude/hookify.*.local.md` rule files with a custom line-based state machine instead of a real YAML parser <cite repo="Ellentat/claude-code--017" path="plugins/hookify/core/config_loader.py" start="105="/>. Two relevant branches:

- A list item beginning with `-` starts a `current_dict` for a multi-field condition entry: [1](#0-0) 
- A "continuation" line (a second/third field of the same dict item, e.g. `operator:` / `pattern:` on the line after `- field: command`) is only merged into `current_dict` when `indent > 2`: [2](#0-1) 

If a rule author writes the continuation field with exactly 2 spaces of indentation (the same level as the `-` marker itself, e.g. `  - field: command` followed by `  pattern: "rm -rf"`), the line fails every branch of the `if/elif` chain: it isn't a top-level key (`indent != 0`), it isn't a new list item (`stripped` doesn't start with `-`), and it fails the continuation check (`indent > 2` is false for `indent == 2`). The line is therefore silently ignored — no exception, no warning — and `current_dict` never receives the `pattern` key.

That truncated dict eventually gets appended to `current_list` and returned as part of `frontmatter['conditions']`. `Condition.from_dict()` fills the missing key with a default: `pattern=data.get('pattern', '')` [3](#0-2) . Then in `RuleEngine._check_condition()`, the `regex_match` operator calls `_regex_match('', field_value)`, and `re.compile('').search(text)` matches any string, including at position 0 of an empty string [4](#0-3) ; `contains` similarly always returns True (`'' in field_value` is always true) [5](#0-4) . Because `_rule_matches()` requires *all* conditions to pass, a broadened condition means the whole rule now fires unconditionally for any input hitting that field/tool/event combination [6](#0-5) . Conversely, for the `equals` operator, a lost `pattern` narrows the rule to only match an empty field value, silently disabling an intended blocking rule (deny bypass).

No validation, schema check, or parser error surfaces this — `load_rule_file()` only catches `IOError/ValueError/KeyError/AttributeError/TypeError`, none of which are raised by this silent-drop path [7](#0-6) .

### Impact Explanation
This is a genuine parser-differential bug in project-configuration parsing reachable through ordinary repository content (a `.claude/hookify.*.local.md` file added via a normal PR). Depending on the operator used and which field is dropped:
- A narrowly scoped `block` rule (e.g., intended to block `rm -rf` only) can silently become an always-match rule, blocking every matching tool call — a denial-of-service against Claude Code's ability to execute `Bash`/`Edit`/`Write` operations.
- A rule using `equals` intended to catch a specific dangerous value can silently become unreachable (deny bypass), letting the exact input it was meant to block through unblocked, defeating the intended enforcement/trust boundary.

Either outcome is a silent divergence between the rule author's visible intent and actual enforced behavior, without any error being surfaced to reviewers or operators.

### Likelihood Explanation
Feasible and repeatable: it requires no privilege beyond being able to author/merge a `.claude/hookify.*.local.md` file (ordinary plugin/config content), and the visual difference (2 vs. 4 spaces of indentation on a continuation line) is subtle and easy to overlook during review, especially since the file otherwise "looks like" valid YAML. The bug is deterministic given the exact indentation.

### Recommendation
Replace the hand-rolled state machine with a real YAML parser (e.g., `yaml.safe_load`) for frontmatter parsing, or at minimum make the continuation-detection strict and fail loudly (raise `ValueError`) when an indented line under a dict item cannot be unambiguously attributed to the current item, rather than silently discarding it. Additionally, `Condition.from_dict()` should reject/raise on a missing/empty `pattern` for `regex_match`/`equals`/`contains` operators rather than silently defaulting to `''`.

### Proof of Concept
Differential unit test comparing `extract_frontmatter()` against PyYAML for a 2-space-indented continuation field:

```python
import yaml
from plugins.hookify.core.config_loader import extract_frontmatter, Condition

md = """---
name: rm-guard
event: bash
action: block
conditions:
  - field: command
  pattern: "rm -rf"
---
Blocks rm -rf.
"""

fm, _ = extract_frontmatter(md)
ref = yaml.safe_load(md.split('---')[1])

# PyYAML sees pattern merged (or raises on inconsistent indent) -
# whereas extract_frontmatter silently drops it.
cond = Condition.from_dict(fm['conditions'][0])
assert cond.pattern == ''          # bug: pattern silently lost
assert 'pattern' in ref['conditions'][0]  # PyYAML preserves/flags it differently

from plugins.hookify.core.rule_engine import RuleEngine
engine = RuleEngine()
assert engine._regex_match(cond.pattern, "ls -la") is True  # always matches now
```
Expected (fixed) behavior: either `extract_frontmatter()` raises/logs a parse error for the malformed indentation, or it correctly attaches `pattern` to the dict item, so `cond.pattern == "rm -rf"` and `_regex_match` only matches commands containing `rm -rf`.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None
    except UnicodeDecodeError as e:
        print(f"Error: Invalid encoding in {file_path}: {e}", file=sys.stderr)
        return None
    except Exception as e:
        print(f"Error: Unexpected error parsing {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
        return None
