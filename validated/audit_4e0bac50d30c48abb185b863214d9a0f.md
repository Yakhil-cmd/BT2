### Title
Query-string parameter injection decouples the org used for webhook signature verification from the repository whose commit status is written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, which reads from the framework `params` object (query string + JSON body merged). The actual event data handed to handlers, however, is read directly from `JSON.parse(request.raw_post)` in `create`. Because Rails merges query and body parameters with a **shallow, top-level merge**, a top-level key that is absent from the JSON body is *not* overridden by the body and is taken from the query string instead. `StatusHandler`, which processes the `status` webhook event, never requires a `repository` or `organization` field and resolves the target commit purely by `sha` across the entire installation (`Commit.where(sha: params.sha)`), with no scoping to the org that was used to verify the signature.

### Finding Description
`repository_owner` is defined as: [1](#0-0) 

and is used to pick the GitHub App config used for signature verification: [2](#0-1) 

`repository_owner` calls `params.dig(...)`, which is `ActionController`'s merged parameters object (query string + parsed body). Rails' `ActionDispatch::Http::Parameters#parameters` merges these as `query_parameters.dup.merge!(request_parameters)` — a shallow, top-level merge. If the top-level key (`repository` or `organization`) is **absent from the JSON body**, a same-named key supplied via the query string is not overwritten and is used instead.

The actual event payload used by handlers is taken independently, straight from the raw body, not from the merged `params`: [3](#0-2) 

`StatusHandler`, which handles the `status` event, does not require a `repository` or `organization` key at all, and resolves the affected record purely by commit SHA, with no org/repo scoping: [4](#0-3) 

This breaks the binding: **the organization whose secret authenticated the request ≠ the repository/commit that is actually written**. An attacker who legitimately controls (or is a low-trust tenant of) any GitHub organization configured in the shared Shipit instance — a supported, documented multi-org configuration (`secrets.yml` with multiple GitHub orgs, e.g. `test/dummy/config/secrets_double_github_app.yml`) — can:
1. Send a POST to `/webhooks` with a JSON body containing only `{"sha": "<victim-commit-sha>", "state": "success", ...}` (no `repository`/`organization` key, satisfying `StatusHandler`'s schema).
2. Append a query string `?organization[login]=<attacker-controlled-org>` so `repository_owner` resolves to an org for which the attacker knows the `webhook_secret` (their own org's secret, which they legitimately possess as its owner).
3. Sign the raw body with that known secret, so `verify_webhook_signature` succeeds for that org.
4. `create` then re-parses the raw body and dispatches it to `StatusHandler`, which updates the CI status for `sha` — a commit that may belong to a **completely different tenant's stack/repository** on the same Shipit installation, since `Commit.where(sha:)` is not scoped by org/repo at all.

### Impact Explanation
`Commit#statuses`/`create_status_from_github!` feeds into the stack's `required_statuses`/`blocking_statuses`/CI-gating logic (`ci.require` in `shipit.yml`) which gates automatic and human-triggered deploys. By forging a passing CI status for a commit belonging to another tenant's repository, a low-privilege attacker (who only controls their own onboarded GitHub org on the shared Shipit instance, not the victim org, not any `ApiClient` token, and not the victim's `webhook_secret`) can mark an unreviewed/failing commit as CI-green for a repository they do not own, enabling that commit to pass the CI gate and be deployed — an **unauthorized deploy** condition of another organization's stack, which is explicitly in-scope Critical/High impact.

### Likelihood Explanation
Requires the attacker to have legitimate signing capability for at least one GitHub org configured on the same shared Shipit installation (their own org), which is an unprivileged-attacker scenario relative to the victim org/repo — no compromise of the victim's credentials, `ApiClient` tokens, or `webhook_secret` is needed. This is only exploitable on deployments serving multiple GitHub organizations from one Shipit instance (a supported configuration), and only for events whose handler does not require `repository`/`organization` in its schema — currently only `status` (`StatusHandler`) fits this exactly.

### Recommendation
- Verify the webhook signature using the same exact body-derived data that will subsequently be dispatched to handlers (i.e., derive `repository_owner` from `JSON.parse(request.raw_post)` directly, not from merged `ActionController::Parameters`), eliminating the query-string/body decoupling.
- Have `StatusHandler` (and any other handler lacking repository/org scoping) validate that the resolved commit's `stack.repository` belongs to the organization that authenticated the webhook, rejecting cross-organization matches.

### Proof of Concept
Given a Shipit instance configured with two orgs, `attacker-org` (secret known to the attacker) and `victim-org` (hosting stack whose commit sha `abc123...` exists):

```
POST /webhooks?organization[login]=attacker-org
X-Github-Event: status
X-Hub-Signature: sha1=<hmac(webhook_secret_of_attacker_org, body)>
Content-Type: application/json

{"sha":"abc123...victim-commit","state":"success"}
```

1. `verify_signature` computes `repository_owner` from merged `params`; since the JSON body has no `organization` key, the query string's `attacker-org` is used unchanged.
2. `Shipit.github(organization: 'attacker-org')` is fetched and `verify_webhook_signature` succeeds because the attacker signed with their own known secret.
3. `create` re-parses the raw body and calls `StatusHandler`, which finds `Commit.where(sha: "abc123...victim-commit")` — belonging to `victim-org`'s stack — and marks it with a forged `success` status, with no check that this commit belongs to `attacker-org`. [5](#0-4) [4](#0-3) [6](#0-5)

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
