### Title
Webhook organization used for signature verification is decoupled from the repository the event actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify the HMAC signature against using `repository_owner`, a value read straight out of the **unauthenticated** JSON body (`params.dig('repository','owner','login')`). Every downstream `Webhooks::Handlers::Handler` (e.g. `PushHandler`), however, resolves the `Stack`/`Repository` to act on using a *different* payload field, `payload.dig('repository','full_name')`, via `Repository.from_github_repo_name`. Because these two fields are never cross-checked, the organization whose secret authenticated the request is not bound to the repository that is actually written to.

### Finding Description
`verify_signature` picks the verifying `GithubApp` this way: [1](#0-0) [2](#0-1) 

`repository_owner` comes straight from the JSON body that has not yet been verified at the time it's read (the signature check consumes it to pick the secret). `GithubApp#verify_webhook_signature` additionally short-circuits entirely when no secret is configured for that organization: [3](#0-2) 

Once the request is accepted, the actual handler resolves the target repository/stack from a **separate, independent** field of the same payload: [4](#0-3) [5](#0-4) 

`PushHandler` then triggers a sync for every matching, non-archived stack using the attacker-controlled `after` sha as `expected_head_sha`: [6](#0-5) 

The equality that the code implicitly assumes but never enforces is:
`organization used to verify signature (repository.owner.login)` == `organization/repo whose Stack is acted upon (repository.full_name)`

Since nothing ties these two fields together, an attacker who can produce *any* valid signature for *any one* configured GitHub organization on the Shipit instance (including one whose `webhook_secret` is simply left blank/unset, which is explicitly supported and unconditionally trusted per the `return true unless webhook_secret` line) can forge a payload whose `repository.owner.login` names that low/no-secret organization while `repository.full_name` names a completely different, fully-configured stack's repository. The signature check passes against the attacker's chosen organization, but the handler dispatches the event against the victim stack.

### Impact Explanation
This lets an attacker who has no privileged token, no repository write access, and no knowledge of the victim organization's `webhook_secret`, forge `push` (and other) webhook events that are processed as if legitimately originating from the target stack's repository. For `push`, this forces `GithubSyncJob` to run against the victim stack with an attacker-chosen `expected_head_sha`, causing spurious sync/fetch cycles against arbitrary stacks the attacker doesn't control. Other handlers keyed the same way (status, check_suite, membership, pull_request) are equally exposed, letting an attacker inject spoofed commit statuses, check-run refresh triggers, or membership changes against a target repository's stack without ever proving control of, or credentials for, that repository/organization. This is a cross-repository/cross-organization authorization bypass in the trust binding between "who signed the request" and "what repository is acted on."

### Likelihood Explanation
Requires only that the Shipit instance be configured for more than one GitHub organization/app (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications") where at least one configured organization has no `webhook_secret` set (also documented as optional) or one whose secret has otherwise leaked/weak. No repository access, session, or API token is required — only the ability to POST to the public `/webhooks` endpoint. This is a realistic multi-tenant deployment shape.

### Recommendation
Bind the verified organization to the repository actually acted upon: after computing `repository_owner` used for signature verification, require that the owner segment of `repository.full_name` (or `organization.login`) matches `repository_owner` before dispatching to handlers, rejecting the event (422) on mismatch. Additionally, do not treat an absent `webhook_secret` as automatic verification success in multi-organization deployments; consider making `webhook_secret` mandatory whenever more than one GitHub organization is configured.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-app example: `attacker-org` (no `webhook_secret` configured) and `victim-org` (has a stack tracking `victim-org/app`, with its own `webhook_secret`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
No `X-Hub-Signature` needed (or any value), because `verify_webhook_signature` returns `true` unconditionally for `attacker-org` (`webhook_secret` blank) per [7](#0-6) .
3. `verify_signature` passes using `attacker-org`'s (non-existent) secret check, per [1](#0-0) .
4. `Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves the stack via `repository.full_name = "victim-org/app"` per [4](#0-3)  and enqueues `GithubSyncJob` for the victim stack with the attacker's forged `after` sha, per [6](#0-5) , even though the attacker never authenticated as, or held credentials for, `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
