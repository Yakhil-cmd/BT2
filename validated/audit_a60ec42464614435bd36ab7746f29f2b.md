### Title
Cross-repository webhook forgery via mismatched organization used for signature verification vs. repository used for event processing - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, which is read from the *same untrusted, attacker-controlled JSON payload* that is later used by `Webhooks::Handlers::Handler#repository_name` to decide which `Repository`/`Stack` the event actually acts on. These two payload fields (`repository.owner.login` and `repository.full_name`) are never checked for consistency.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to pick which org's webhook secret authenticates the delivery:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
``` [2](#0-1) 

Once verified, the actual event handler (`PushHandler`, status handlers, etc.) resolves the target `Repository`/`Stack` from a *different* field of the same payload:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Because the entire request body is attacker-supplied and only the HMAC over the raw body is checked (using whichever org's secret `repository_owner` happens to select), nothing enforces that `repository.owner.login` (used to pick the verification secret) is the same organization that owns `repository.full_name` (used to pick the `Stack` that gets acted upon). This breaks the intended trust binding: `organization that authenticated == repository that is written`.

An attacker who legitimately administers Org A's Shipit webhook configuration (and therefore knows Org A's `webhook_secret`) can send Shipit a webhook whose `repository.owner.login` is `"OrgA"` (so the signature verifies against Org A's secret) but whose `repository.full_name` is `"OrgB/some-repo"` (an unrelated stack the attacker does not control). The HMAC check passes because it is computed with Org A's own secret over Org A's attacker-crafted body, and `verify_signature` never checks that the resolved repository actually belongs to Org A.

### Impact Explanation
For a `push` event, `PushHandler#process` finds all non-archived stacks for the spoofed `full_name` and calls `stack.sync_github(expected_head_sha:)` [4](#0-3) , which enqueues `GithubSyncJob` [5](#0-4) . For stacks with `continuous_deployment` enabled, newly synced commits are automatically picked up for deployment via `Stack.schedule_continuous_delivery`. This lets an attacker who only controls Org A's webhook secret force Org B's stack to sync/deploy an arbitrary commit sha of the attacker's choosing (any sha reachable in Org B's real repository history, since the actual git data still comes from Org B's GitHub API/installation credentials) without ever having write access to Org B's repository or organization — an unauthorized deploy triggered across a repository/organization boundary the attacker is not authorized for.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` for at least one organization configured in the Shipit instance (a low-privilege, legitimate webhook-admin capability for that org only) and knowledge of another org/repo's `full_name` that is also configured as a stack in the same Shipit instance — realistic in any multi-tenant/multi-org Shipit deployment. No GitHub App private key, session, or `ApiClient` token is needed.

### Recommendation
After signature verification, validate that the repository actually referenced by the payload (`repository.full_name`) belongs to the same GitHub organization/owner (`repository.owner.login` or `organization.login`) whose secret was used to verify the signature, rejecting the request (422) on mismatch, before any handler resolves or mutates state for that repository/stack.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (secret `secretA`, attacker-controlled) and `OrgB` (secret `secretB`, victim), each with at least one existing `Stack` (e.g., `OrgB/victim-repo` with `continuous_deployment: true`).
2. Attacker crafts a `push` JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha that exists in OrgB/victim-repo>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` using the secret they legitimately control for `OrgA`.
4. POST to `/github/webhooks` (Shipit webhook endpoint) with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` → `"OrgA"`, verifies HMAC against `secretA`, succeeds.
6. `PushHandler` resolves stack via `full_name` = `OrgB/victim-repo`, and triggers `sync_github`/continuous deployment for `OrgB`'s stack — a deploy the attacker never had authorization to trigger.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
