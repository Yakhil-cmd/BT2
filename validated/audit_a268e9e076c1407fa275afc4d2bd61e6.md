### Title
Attacker-crafted issue input triggers unhandled `throw Error` inside `checkForDoublespends`, crashing all full nodes on that unit - (File: `validation.js`)

### Summary
This is an analog to JLSEC-2026-895 (ImageMagick `WriteImages` assertion failure on a NULL image list, in `MagickWand/operation.c`, causing DoS). The bug class is: an attacker supplies crafted, unprivileged input that violates an internal invariant assumed by the program, hitting a hard `assert`/`throw` path instead of a graceful error, crashing the process. In `ocore`, unit validation contains several `throw Error(...)` statements that assume "this state is impossible" while validating attacker-controlled double-spend/input data. Because `process.on('uncaughtException', ...)` in `network.js` deliberately re-throws to crash the process [1](#0-0) , any code path that reaches one of these `throw` statements is a full node crash triggerable by a single posted unit — the same denial-of-service impact class as the ImageMagick bug.

### Finding Description
`checkForDoublespends()` is the generic conflict/double-spend detector used both for spend-proof checks and for divisible-asset input double-spend checks [2](#0-1) . It assumes two invariants that "must" hold for any row returned by its SQL query:

1. The address of any conflicting record found by the query must always be one of the current unit's author addresses — otherwise it does `throw Error("conflicting "+type+" spent from another address?")` [3](#0-2) .
2. If the conflicting record is included in this unit's parents and already final ('good' sequence) it should have been rejected earlier; reaching that state again is treated as `throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit)` [4](#0-3) .
3. If the record is NOT included in parents, the conflicting address must always be listed in `objValidationState.arrAddressesWithForkedPath`; otherwise `throw Error("double spending "+type+" without double spending address?")` [5](#0-4) .

This function is invoked for the `issue` type of asset inputs, where the double-spend WHERE clause is built dynamically and, notably, **only includes an `address=?` filter when the asset is not `issued_by_definer_only`** [6](#0-5) . For assets that *are* `issued_by_definer_only`, the double-spend SQL query for `issue` inputs has no address restriction at all, so `checkForDoublespends` can return a conflicting row whose `address` differs from the current unit's author address — directly triggering the "conflicting … spent from another address?" throw at `validation.js:1673`, which is exactly the class of "this state is impossible, so we must have a null/violated invariant → hard crash" bug described in the ImageMagick report.

### Impact Explanation
When the `throw Error` fires inside the `conn.query` callback of `checkForDoublespends`, it happens outside any `try/catch` supervised by the validation error-handling logic (`validate()`'s callbacks), so it becomes an uncaught exception. `network.js`'s global handler intentionally re-throws to crash the process rather than continue in "an inconsistent state" [1](#0-0) . Any full node (hub, or any node handling the joint, including AA-composer-driven validation paths that call the same `validation.validate` / `checkForDoublespends` code [7](#0-6) ) that processes the crafted unit will crash. Because units are broadcast/forwarded to all subscribed peers via `forwardJoint` [8](#0-7) , a single posted unit propagating through the network can crash many/most full nodes simultaneously — a network-wide denial-of-service that matches "a network unable to confirm new units" in the accepted-impact list.

### Likelihood Explanation
Reaching this path requires: (a) an asset flagged `issued_by_definer_only` (issuable via ordinary asset-definition messages, so an attacker can define such an asset themselves, or piggyback on an existing one) and (b) two competing `issue` inputs for that asset from different addresses that are not both authors of the checked unit. The attacker fully controls the crafted unit's authors/inputs and the asset's definition, so triggering the specific SQL/branch combination that produces an address mismatch is within reach of a normal, unprivileged unit poster — no special network position, hub role, or leaked keys required.

### Recommendation
Replace the invariant-violation `throw Error(...)` calls inside `checkForDoublespends` (`validation.js:1673`, `:1688`, `:1692`) with `return cb(err_message)`/`return cb2(err_message)` so they become ordinary unit validation errors (`ifUnitError`) instead of process-crashing exceptions. Additionally, restore a consistent `address=?` constraint in the `issue`-input double-spend query even for `issued_by_definer_only` assets (or otherwise ensure the returned address set is always compared against author addresses before assuming the invariant), so that unexpected addresses can never reach the `checkForDoublespends` assumption in the first place.

### Proof of Concept
1. Attacker composes and posts a unit defining an asset `A` with `issued_by_definer_only: true` (definer address = `D`).
2. Attacker (as `D` or via any author path allowed by the definition) posts unit `U1` from address `X` issuing serial_number `1` of asset `A`.
3. Attacker crafts a conflicting unit `U2`, authored by a different address `Y` (also satisfying whatever "definer" gating exists, or exploiting timing/order so the check runs before serial issuer restriction fully resolves), issuing the same `serial_number` for asset `A`. Because the `issued_by_definer_only` branch omits the `AND address=?` filter in the double-spend SQL [9](#0-8) , the query in `checkForDoublespends` can return `U1`'s row (`address = X`) while validating `U2` whose author list is `[Y]`.
4. `checkForDoublespends` executes `arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1` → true (since `X` is not among `U2`'s authors `[Y]`) → `throw Error("conflicting divisible input spent from another address?")` fires inside the DB callback, becomes an uncaught exception, and crashes the validating node process via the `uncaughtException` handler in `network.js`.

Note: full exploitability depends on exact reachability of step 3's authorship/definer constraints, which could not be fully re-verified against `validateAssetDefinition`'s complete field constraints within the available indexed context; a Devin session with full file access is recommended to confirm the precise conditions under which two different addresses can both post competing `issue` inputs for an `issued_by_definer_only` asset that reach `checkForDoublespends` in the same validation window.

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}
						else{ // arrAddressesWithForkedPath is not set when validating private payments
							if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
								throw Error("double spending "+type+" without double spending address?");
							cb2();
						}
					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);
				}
			);
		}
	);
}
