No vulnerability found for this question.

**Rationale:** The Tezos/Dexter bug class is specific to Michelson smart contracts, where *every* contract entrypoint implicitly accepts an "amount sent" (`AMOUNT`/tez transferred with the call) regardless of whether the entrypoint logic uses it, and Dexter failed to reject non-zero amounts on functions that don't expect payment (`approve`, `removeLiquidity`, `tokenToXtz`, `tokenToToken`, `updateTokenPool`, `setBaker`, default). This is a property of the Tezos/Michelson calling convention itself: contract calls always carry an implicit native-currency transfer field that the contract can choose to ignore.

FRAME/Substrate dispatchables do not have this implicit "value sent" semantics. A pallet extrinsic only moves a native-currency amount if the pallet's `Call` variant explicitly declares a `value`/`amount` parameter and the dispatch logic acts on it (e.g. `pallet_contracts`/`pallet_revive`'s `call`/`instantiate` extrinsics take an explicit `value: BalanceOf<T>` parameter that is deliberately chosen by the caller and always transferred into the callee's account as part of `initial_transfer`, e.g. [1](#0-0)  and benchmarked in [2](#0-1) ). There is no unrelated, always-present "amount" field attached to every extrinsic call by the runtime dispatch mechanism itself; extrinsics that don't need a balance transfer simply have no such parameter, so there is no equivalent "forgot to check msg.amount==0" foot-gun across the general set of FRAME dispatchables.

The closest related areas I inspected — XCM's `AssetsTrapped`/`ClaimAsset` mechanism for assets that end up unclaimed after a program aborts ( [3](#0-2) ), and `pallet-revive`'s value-forwarding on `call`/`instantiate`/`terminate` ( [4](#0-3) ) — are all cases where the value/amount is an explicit, intentional, caller-controlled parameter of the specific call, not an implicit side-channel attached to unrelated entrypoints. None of these match the invariant violated in the report (an entrypoint silently accepting and swallowing funds it has no logic to use or return).

Since no FRAME/XCM/pallet-contracts/pallet-revive entry point exhibits the "accepts native currency it does not need or track, with no explicit parameter or check, causing accidental fund loss" pattern, there is no demonstrable Polkadot SDK analog to this Tezos/Dexter finding.

	fn initial_transfer(&self) -> DispatchResult {
		let frame = self.top_frame();

		// If it is a delegate call, then we've already transferred tokens in the
		// last non-delegate frame.
		if frame.delegate_caller.is_some() {
			return Ok(());
		}

		let value = frame.value_transferred;

		// Get the account id from the caller.
		// If the caller is root there is no account to transfer from, and therefore we can't take
		// any `value` other than 0.
		let caller = match self.caller() {
			Origin::Signed(caller) => caller,
			Origin::Root if value.is_zero() => return Ok(()),
			Origin::Root => return DispatchError::RootNotAllowed.into(),
		};
		Self::transfer(Preservation::Preserve, &caller, &frame.account_id, value)

/// 1. deploy Terminate contract

		}

				.build_and_unwrap_contract();
