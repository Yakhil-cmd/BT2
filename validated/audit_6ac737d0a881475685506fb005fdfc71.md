This confirms the mechanism precisely: `compute_burnt` from `signature_verification_cost` is accounted into `processing_state.total.compute` on whatever shard hosts the **relayer/signer's** account at transaction-conversion time (`process_transaction`, `runtime/runtime/src/lib.rs:2180-2184` adding `outcome.outcome.compute_usage` derived from `TransactionCost.compute_burnt` computed in `tx_cost`/`calculate_tx_cost` at `runtime/runtime/src/config.rs:400-441`). The actual expensive `verify()` call happens later in `apply_delegate_action` (`runtime/runtime/src/actions.rs:422-433`) when the resulting receipt is applied on the shard hosting `delegate_action.sender_id` — a different account, and potentially a different shard, from the outer transaction's signer. ### Title
Meta-transaction ML-DSA-65 signature verification compute is charged on the relayer's shard but the expensive variable-time verify executes uncharged on the receiver's shard - ([File: runtime/runtime/src/actions.rs])

### Summary
`signature_verification_cost` (the ML-DSA-65 verify surcharge) is burnt as gas/compute exclusively at transaction-conversion time on the shard that processes the outer `SignedTransaction` (the relayer's shard), via `calculate_tx_cost` in `runtime/runtime/src/config.rs:400-441`. The actual variable-time `verify()` call for the inner `DelegateAction` signature happens later, at receipt-apply time in `apply_delegate_action` on the shard hosting `delegate_action.sender_id`, and this shard's compute budget (`processing_state.total.compute`, checked against `compute_limit` in `process_receipts`, `runtime/runtime/src/lib.rs:2612-2636`) is never debited for that verify call.

### Finding Description
A meta-transaction flows as: `SignedTransaction { signer_id: relayer, receiver_id: sender_id, actions: [Delegate(SignedDelegateAction)] }`. When the relayer's shard processes this transaction (`process_transaction`, `runtime/runtime/src/lib.rs`), `tx_cost`/`calculate_tx_cost` (`runtime/runtime/src/config.rs:400-441`) computes `signature_verification_cost` (`runtime/runtime/src/config.rs:512-526`), which looks up the inner delegate's signer key type via `signature_kind` and adds the ML-DSA-65 surcharge (`ml_dsa_65_verification_cost`, 100 Ggas, `core/parameters/res/runtime_configs/85.yaml:15`) to `burnt`. This `compute_burnt` is added to `processing_state.total.compute` on the relayer's shard (`runtime/runtime/src/lib.rs:2180-2184`), which is checked against that shard's `compute_limit`.

The resulting `ActionReceipt` (carrying the still-unverified `SignedDelegateAction`) is then sent as an outgoing/incoming receipt to the shard hosting `delegate_action.sender_id` (per NEP-366, `receiver_id` of the outer tx). When that receipt is applied there, `apply_delegate_action` (`runtime/runtime/src/actions.rs:422-433`) calls `signed_delegate_action.verify()` — which invokes `SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify` (`core/primitives/src/action/delegate.rs:83-90, 210-214`) — performing the actual ~80µs-mean/1.3ms-tail ML-DSA-65 verification (per `docs/architecture/how/post_quantum_signatures.md:140-163`). The code comment at `runtime/runtime/src/actions.rs:479-481` explicitly acknowledges that costs for work "potentially on a different shard" are not charged at this point, but this framing is about the *inner actions'* execution cost, not the verify cost itself — and no compute is ever added for the verify call in `apply_delegate_action`. Only `required_cost` and `prepaid_send_fees` are added to `result.gas_used`/`result.compute_usage` there.

Because the compute budget check in `process_receipts` (`processing_state.total.compute >= compute_limit`, `runtime/runtime/src/lib.rs:2329, 2407, 2519, 2643`) on the receiving shard never reflects the ML-DSA-65 verify cost, an attacker can spread many MLDSA65-signed `DelegateAction`s (each cheaply chargeable once at conversion on the relayer's own shard) targeting many distinct sender accounts on a single target shard, forcing that shard to spend real wall-clock time on `verify()` calls during `apply_delegate_action` without any corresponding compute debit slowing further receipt intake on that shard.

### Impact Explanation
This maps to the "chain stall / node crash or unbounded resource use" bounty class: an unprivileged attacker can burn real CPU cycles on chunk-producers applying receipts to a shard they don't control the compute budget of, because the verify cost is priced and debited on the sender-tx's own shard rather than on the shard that actually executes the expensive verification. This creates an accounting mismatch between "who pays" (relayer's shard budget) and "who performs the work" (target shard performing `apply_delegate_action`), a metering-completeness violation: the compute is charged before/elsewhere, not proportional to where it's actually spent, letting an attacker degrade one shard's throughput while depleting compute budget on a shard of their choosing (their own account's shard) rather than the target's. ### Likelihood Explanation
Feasibility is high: it only requires an unprivileged relayer account with sufficient balance and ability to create MLDSA65 access keys for arbitrary `sender_id` accounts it controls (or that opt in as relayed users), and submitting many `Delegate` transactions targeting a chosen shard. No special permissions, validator status, or protocol-version-gating bypass is needed — `PostQuantumSignatures` simply needs to be enabled (which is the feature under audit). Repeatability is straightforward since verify time is deterministic/bench-documented and does not require crafted malicious signatures (verified flat across signature hint-weights per `core/crypto/benches/ml_dsa_worst_case.rs`).

### Recommendation
Charge (or reserve) compute for the delegate-inner-signer ML-DSA-65 verification against the compute budget of the shard that actually performs `apply_delegate_action`/`verify()`, not (only) the relayer's shard at conversion time. Concretely, add `signature_verification_costs[MlDsa65]`-equivalent compute to `result.compute_usage` inside `apply_delegate_action` (`runtime/runtime/src/actions.rs:422-433`) before/at the point `verify()` is called, so `process_receipts`'s `compute_limit` check on the receiving shard reflects this cost and can defer/reject further receipts accordingly. If double-charging gas is undesirable (since the relayer already paid the gas), consider splitting the parameter into a gas component charged at conversion (payment) and a compute-only component charged at apply time (budget accounting), mirroring the already-existing `{gas, compute}` independent-pricing mechanism in `signature_verification_costs: EnumMap<SignatureKind, ParameterCost>`.

### Proof of Concept

1. Builds N `Delegate` receipts, each with a distinct MLDSA65-signed inner `DelegateAction`, all targeting distinct `sender_id` accounts on a single shard, with a fixed low `apply_state.gas_limit`/`compute_limit`.
