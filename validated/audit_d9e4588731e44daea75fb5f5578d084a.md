### Title
Unhandled exception (node crash) when processing a duplicate divisible private-asset payment with multiple outputs - ([File: private_payment.js])

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain()` performs a duplicate-detection query before validating an incoming private payment chain. For divisible assets the duplicate-check query does not filter by `output_index`, so it can legitimately return more than one row whenever the referenced message has more than one output (e.g. a normal payment + change output). The code treats `rows.length > 1` as an impossible/invariant-violating condition and does `throw Error(...)`, exactly mirroring the NEAR pattern of asserting an invariant (recomputed value must match) that does not actually hold for a valid, reachable case (there, the genesis chunk's empty receipts root; here, a divisible-asset message with >1 stored outputs). Any private-payment counterparty (or the hub relaying/duplicating traffic) can trigger this simply by re-sending an already-processed private payment chain for a divisible asset whose message has 2+ outputs — a routine, expected occurrence that the surrounding code even anticipates ("we could have this output already but the address is still hidden").

For indivisible assets (`objAsset.fixed_denominations === true`) the query filters by `output_index`, so it correctly targets a single output row. For divisible assets, however, `output_index` is intentionally **not** appended to the `WHERE` clause, meaning the query returns *all* outputs belonging to the given `(unit, asset, message_index)` — which is exactly the set of outputs of one payment message. A single divisible-asset payment message commonly has 2+ outputs (e.g., recipient output + change output back to the sender), all sharing the same `unit`, `asset`, and `message_index`.

Consequently, the very first time such a message is stored, `outputs` already contains 2 (or more) rows for that `(unit, asset, message_index)`. If the same private payment chain is delivered again — a routine occurrence, since this exact code path is designed to *tolerate* duplicate deliveries (see the comment "we could have this output already but the address is still hidden" and the subsequent de-duplication logic at [3](#0-2) ) — the duplicate-check query returns more than one row, hitting the `throw Error("more than one output ...")` invariant check before the intended de-duplication logic ever runs.

This `throw` occurs inside an asynchronous `db.query` callback with no surrounding `try/catch` in the call chain from `network.handleOnlinePrivatePayment` / `wallet.js:handlePrivatePaymentChains`, so the exception is unhandled and crashes the Node.js process, exactly like the referenced NEAR bug where an assertion designed for the "normal" case failed to account for a legitimately different (but valid) structure (genesis chunk's empty root vs. divisible asset messages with multiple outputs).

### Impact Explanation
Any wallet/full node that processes private payments (a normal, unprivileged protocol reachable from any device the user pays or receives from, or via the hub relaying private payment chains) can be crashed by a private-payment counterparty simply re-sending (deliberately or as a natural retry/duplicate-hub-relay event) a previously-accepted private payment chain for a divisible private asset whose message contains more than one output. This is a remotely triggerable denial-of-service against the receiving node/wallet process, requiring no privileged access, no malicious peer/network-level behavior, and no compromise of keys — only the ability to send a private payment message that the target has already processed once.

### Likelihood Explanation
Divisible payments with more than one output (payment + change) are the normal case for any divisible private asset, and re-delivery of the same private-payment chain is an expected and already-anticipated scenario in the code itself (duplicate detection is explicitly implemented for it, but the crashing check runs before that logic can apply for divisible assets). This makes the crash trivially and reliably reproducible by any legitimate private-payment counterparty, without requiring any race condition or unusual timing.

### Recommendation
For divisible assets, include `output_index` in the duplicate-check `WHERE` clause (mirroring the indivisible-asset branch), or otherwise restrict the query to compare against the specific output referenced by the incoming private element before deciding whether `rows.length > 1` is truly anomalous. At minimum, replace the `throw Error(...)` with a graceful `transaction_callbacks.ifError(...)` so a query returning multiple legitimate rows does not crash the process.

### Proof of Concept
1. Party A sends Party B a divisible private-asset payment in a single message that produces two outputs for the same `(unit, asset, message_index)` (e.g., payment output to B and change output back to A) — this is standard divisible-asset payment behavior.
2. B's node processes and stores this payment via `assetModule.validateAndSavePrivatePaymentChain`, resulting in 2 rows in `outputs` for that `(unit, asset, message_index)`.
3. A (or the hub relaying on A's behalf) re-sends the same private payment chain a second time (e.g., via `handlePrivatePaymentChains` in `wallet.js`, or `handleOnlinePrivatePayment` in `network.js`).
4. B's node re-enters `validateAndSavePrivatePaymentChain` in `private_payment.js`; because the asset is divisible (`fixed_denominations` false), the duplicate-check SQL has no `output_index` filter and returns 2 rows.
5. `if (rows.length > 1) throw Error(...)` fires inside the unguarded `db.query` callback, producing an unhandled exception that crashes B's Node.js process.
