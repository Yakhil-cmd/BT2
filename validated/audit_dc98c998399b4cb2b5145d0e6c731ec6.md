### Title
`provision?` operator precedence bypasses `review_stacks_enabled` gate - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses `&&`/`||` in a way that only gates the `allow_all` branch on `repository.review_stacks_enabled`, leaving the `allow_with_label` and `prevent_with_label` branches unguarded. An attacker who opens a PR with the configured provisioning label against a repository configured with `provisioning_behavior: allow_with_label` can trigger `ReviewStack` creation even when the operator has `review_stacks_enabled: false`.

### Finding Description
The broken binding: the code should enforce `repository.review_stacks_enabled == true` before any `ReviewStack` creation, but as written that constraint only applies to one of three OR-ed clauses. [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this expression parses as:
```
(review_stacks_enabled && allow_all?) ||
(allow_with_label? && has_label?) ||
(prevent_with_label? && !has_label?)
```
So when `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, and the PR carries the configured label, `provision?` returns `true` regardless of `review_stacks_enabled`. `process` then calls `ReviewStackAdapter#find_or_create!`, which calls `create!`, creating a `Shipit::ReviewStack` record and enqueueing it via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [2](#0-1) [3](#0-2) [4](#0-3) 

Attacker's exact request: a webhook `pull_request` `opened` event for a repository the attacker controls (owner of the fork/PR) targeting a Shipit-tracked repository row with `review_stacks_enabled: false`, `provisioning_behavior: allow_with_label`, where `params.pull_request.labels` contains a label whose name equals `repository.provisioning_label_name`. No signature bypass is needed for the analysis of this specific logic bug — the flaw exists purely in the boolean condition once the webhook reaches the handler; the label and PR content are fully attacker-controlled (label applied by the PR author on their own PR, or in many workflows by anyone with write access to the fork). No existing guard (`respond_to_pull_request_opened?`, `ExplicitParameters` schema, or model validations) checks `review_stacks_enabled` independently — it is only referenced inside the flawed `provision?` expression.

### Impact Explanation
This causes an unauthorized `Shipit::ReviewStack` (and its underlying `Stack`) to be created and queued for provisioning (`ReviewStackProvisioningQueue.add`) on a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`). This is a record written for a repository configuration that did not authorize it, matching the "unauthorized deploy" / write-outside-of-scope class of Critical impact — an operator who disabled review stacks entirely can still have stacks provisioned, consuming provisioning resources and creating stack/task infrastructure tied to attacker-supplied branch refs (`params.pull_request.head.ref`). This is repeatable for any repository configured with `allow_with_label`, by any attacker who can label a PR on that repo.

### Likelihood Explanation
Preconditions are non-trivial but plausible: the repository row must exist in Shipit's database with `provisioning_behavior: 'allow_with_label'` and `review_stacks_enabled: false` — a configuration combination that is likely unintentional (operators who set a label-gated behavior probably intend for it to only take effect when review stacks are enabled) but is not prevented by any validation on the `Repository` model. The attacker needs only to open a PR and apply/have the provisioning label applied, which is low-cost and does not require any Shipit credentials — assuming they can already emit `opened`/labeled webhook events for that repo (webhook signature verification is a separate, out-of-scope-for-this-question control gating webhook ingestion generally, not this specific logic path).

### Recommendation
Fix operator precedence in `provision?` by explicitly parenthesizing so `review_stacks_enabled` gates all three branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
minitest plan in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
1. Create a `Shipit::Repository` fixture/record with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'deploy-preview'`.
2. Build `opened` event params with `pull_request.labels: [{ name: 'deploy-preview' }]` and matching `repository.full_name`.
3. Assert before: `repository.review_stacks_enabled == false` and `Shipit::Stack.count == 0` / `Shipit::ReviewStack.count == 0`.
4. Call `OpenedHandler.new(...).process` (or dispatch through the webhook processor entry point).
5. Assert after: `Shipit::ReviewStack.count == 1` (or `Shipit::Stack.count` increased) — proving a stack was created despite `review_stacks_enabled: false`, confirming the binding `review_stacks_enabled == true` was violated.
