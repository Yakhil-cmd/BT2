### Title
CCMenuController#stack bypasses ApiClient stack scoping, allowing cross-stack disclosure of deploy state via token reuse - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::StacksController` and the base controller resolve stacks through `stacks.from_param!`, where `stacks` is scoped to `current_api_client.stack_id` when the token was minted for a specific stack. `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, discarding that scoping entirely, so any token with the `read:stack` permission can read any stack's CI status by changing the URL's `stack_id` segment.

### Finding Description
The binding that should hold is: `current_api_client.stack_id.nil? || current_api_client.stack_id == stack_resolved_from(params[:stack_id]).id`.

In `Shipit::Api::BaseController`, this is implemented correctly via: [1](#0-0) 
`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client has a bound `stack_id`, and `stack` resolves through that scoped relation, so a token bound to stack A raises `RecordNotFound` (via `from_param!`) when asked for stack B.

`Shipit::Api::CCMenuController`, however, redefines `stack` independently: [2](#0-1) 
This calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model, never consulting `current_api_client.stack_id`. The only authorization check applied is `require_permission :read, :stack`, which merely checks that `'read:stack'` is present in the token's `permissions` array — it never compares the token's bound stack to the requested stack: [3](#0-2) 

`CCMenuUrlController#fetch` is the legitimate way tokens are minted for CCMenu URLs; it creates a client with `permissions: %w[read:stack]` but does **not** set `stack:` on the `ApiClient`, so the resulting `authentication_token` is stack-agnostic by construction: [4](#0-3) 
Even if an operator did scope a client to a single stack (`stack_id` set), `CCMenuController#show` would still ignore that scoping because of the overridden `stack` method.

Attack flow: attacker legitimately obtains (or is handed) a CCMenu URL/token for stack A (e.g., via `CCMenuUrlController#fetch` on a stack they can view), then issues `GET /api/stacks/B/cc.xml?token=<token>` for arbitrary/private stack B. `authenticate_api_client` succeeds because the token verifies independent of `stack_id`, `require_permission!(:read, :stack)` passes because the token has `read:stack`, and `stack` resolves B unconditionally. `#show` then renders `stack.deploys_and_rollbacks.last`, exposing B's build status, commit SHA/label, and timing.

None of the existing guards intercept this: `verify_signature`/webhook checks are irrelevant (this is the API path, not webhooks); `ExplicitParameters` only validates parameter types, not authorization scope; `force_github_authentication` doesn't apply to token-based API auth; and `require_permission!` only checks the permission string, not stack identity.

### Impact Explanation
An attacker with any valid `read:stack` API token (including a stack-agnostic CCMenu token they were legitimately given for one stack) can enumerate/read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel` containing the deployed SHA, `lastBuildTime`, `webUrl`) of any other stack in the installation by varying the `stack_id` path/URL segment, repeatably and at will. This is an unauthenticated-relative-to-target-stack read of stack/task state, matching the "unauthenticated read of stack state, task streams or deploy output" High-severity category (the write-up frames it as "cross-repository" but the actual disclosed data is limited to CI status metadata rendered in CCMenu XML, not task logs or credentials — no write, deploy, rollback, or credential exfiltration occurs).

### Likelihood Explanation
Preconditions are modest but real: the attacker needs any valid `ApiClient` token bearing `read:stack` — which is exactly what `CCMenuUrlController#fetch` mints for any user able to view one stack's CCMenu URL. Because that controller does not bind the client to `stack:`, the resulting token works for every stack in the installation by design of the current code, not just a hypothetical narrow case. The attacker only needs to know or guess another stack's `owner/repo/env` identifier used in `Stack.from_param!` (these are often visible in the Shipit UI as public-ish routing segments, not secrets). Exploitation cost is a single HTTP GET; it is trivially repeatable against arbitrary stacks.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController`, or make it use the inherited scoped `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!`, so tokens are constrained the same way as in `StacksController`. Additionally, `CCMenuUrlController#fetch` should mint the `ApiClient` bound to the specific `stack:` (not just permissions), ensuring CCMenu tokens are inherently stack-scoped rather than relying solely on controller-side checks.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token minted for stack A cannot read stack B's CI status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')
  client = ApiClient.create!(creator: shipit_users(:walrus), name: 'CCMenu Client',
                              permissions: %w[read:stack], stack: stack_a)

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Broken binding today: this currently returns :ok and renders stack_b's data.
  # Expected (fixed) binding: current_api_client.stack_id (stack_a.id) must equal
  # the resolved stack's id (stack_b.id) -- they don't match, so this should 404/403.
  assert_response :not_found # or :forbidden, depending on chosen fix
end
```
This demonstrates that `current_api_client.stack_id == stack_a.id` while the resolved `stack.id == stack_b.id`, and the controller currently permits the mismatch to reach `#show`.
