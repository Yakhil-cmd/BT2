### Title
Cross-organization webhook forgery bypasses per-org signature scoping and forges CI status to enable unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify against using an attacker-controlled field of the *unverified* payload (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, and especially `StatusHandler#process`) key off a *different* field (`repository.full_name`) or, in the case of status events, off no repository scoping at all. This breaks the binding "organization whose secret authenticated the request == repository/stack that is written," letting an operator of one legitimate GitHub organization onboarded to a multi-tenant Shipit instance forge events for any other organization's stacks.

### Finding Description
`verify_signature` computes the org used to pick the webhook secret from the raw JSON body before any authenticity check has occurred: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The secret used for HMAC comparison is selected via `Shipit.github(organization: repository_owner)` → `github_app_config(organization)`, which supports per-organization secrets for multi-tenant deployments as documented: [3](#0-2) [4](#0-3) 

Once the signature passes (using whichever org's secret matches `repository.owner.login`), the raw body is dispatched to handlers: [5](#0-4) 

Handlers resolve the target repository/stack from a *different* field, `repository.full_name`: [6](#0-5) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) is consistent with `repository.full_name` (used to select the target stack) — they are independent JSON fields under full attacker control in a forged request.

Worse, `StatusHandler#process` doesn't even use the `stacks`/repository scoping helper at all — it updates commit statuses purely by SHA, globally: [7](#0-6) 

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

So an attacker who legitimately administers **their own** organization on a shared/multi-tenant Shipit install (and therefore knows *that* organization's `webhook_secret`) can send a signed `status` event where `sha` is the SHA of a commit belonging to a completely different, victim organization's stack. The signature validates fine (it's checked against the attacker's own org's secret, selected via the attacker-controlled `repository.owner.login`/`organization.login` field), yet the status write hits `Commit` rows across every stack/org sharing that SHA — a cross-repository/cross-organization write.

`PushHandler` and `CheckSuiteHandler` do scope through `stacks` (derived from `repository.full_name`), but since `full_name` is also attacker-supplied and decoupled from the field used for secret selection, an attacker can pick `full_name` to target any victim stack configured on the instance while still passing signature verification with their own org's secret.

### Impact Explanation
Commit status is a first-class safety gate for deploys: `Commit#deployable?` requires `success?` (derived from statuses) and stacks/merge-queues consult `required_statuses`/`blocking_statuses` computed from these same status records: [8](#0-7) 

By forging a `status` webhook with `state: "success"` for a victim's pending/failing commit SHA (SHAs are not secret — they are visible via GitHub, PRs, or CI logs), an attacker on a different tenant organization can flip a victim commit to `deployable?`, enabling operators (or continuous deployment) on the victim stack to ship code that never actually passed CI — an unauthorized deploy. This matches the "High" impact bucket ("escalation into `Shipit.github_teams` authorization" analog is not this, but "unauthorized deploy" under the Critical bucket is directly implicated), and independently satisfies "cross-repository writes," since `StatusHandler` writes `Commit`/`Status` rows for any stack sharing the SHA regardless of tenant.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration — `docs/setup.md` "Using Multiple Github Applications"), and (2) the attacker legitimately controls one of those organizations (and thus its `webhook_secret`), which is the expected operating model for a shared internal deploy tool. No repository write access, no Shipit session, and no other org's secrets are needed — only knowledge of the target commit SHA, which is generally public. This is a realistic, unprivileged-attacker (relative to the victim org) scenario.

### Recommendation
- Bind the webhook-secret-selection to the same trusted, already-scoped context used for processing, or verify the signature independent of any payload field, then re-derive/validate that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` before further processing, rejecting mismatches.
- Scope `StatusHandler#process` (and any other handler that doesn't already) through `stacks`/`Repository.from_github_repo_name(repository_name)` rather than a bare `Commit.where(sha:)` lookup, so a status update can only affect commits belonging to the repository whose secret verified the request.
- Consider signing/verifying per-installation using GitHub's `X-GitHub-Hook-Installation-Target-ID` or similar installation-scoped identifiers rather than trusting payload-embedded `owner.login`/`organization.login` for secret selection.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two organizations, `attacker-org` (secret known to attacker, who legitimately administers it) and `victim-org` (a separate tenant with stacks configured, e.g. `victim-org/app`).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker-org webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the HMAC matches — request passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (belonging to `victim-org/app`), and calls `create_status_from_github!`, marking it `success` regardless of `victim-org`'s real CI state, potentially unblocking a deploy on the victim's stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
