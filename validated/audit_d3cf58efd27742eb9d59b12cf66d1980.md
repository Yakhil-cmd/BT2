### Title
Webhook Signature Verified Against `repository.owner.login`/`organization.login` But Write Target Resolved From Independent `repository.full_name` Field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects which GitHub App/organization's `webhook_secret` to verify the inbound HMAC signature against using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Once the signature check passes, every webhook handler resolves the actual `Repository`/`Stack` to mutate using a *separate* field from the same attacker-controlled JSON body: `payload.dig('repository','full_name')`. In a multi-organization Shipit deployment (one `webhook_secret` per GitHub org, as supported by `Shipit.github_app_config`), these two fields are never checked for consistency, breaking the binding: `organization authenticated == repository written`.

### Finding Description
`WebhooksController#verify_signature` picks the app/secret like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up a *per-organization* config, including a distinct `webhook_secret`, from `Shipit.github_app_config` — this is the multi-tenant schema exercised by `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`, each with its own `webhook_secret`). [3](#0-2) 

Once `verify_signature` passes (HMAC valid for the org selected by `repository_owner`), `WebhooksController#create` dispatches to handlers with the raw, unvalidated JSON: [4](#0-3) 

Every handler then resolves the repository/stack to act on from a *different* field of the same attacker-supplied body — `repository.full_name` — never cross-checked against the value used for signature routing (`repository.owner.login`): [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

The same pattern repeats in every pull-request handler (`OpenedHandler`, `ReopenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.), all resolving `Repository.from_github_repo_name(params.repository.full_name)` independently of `repository.owner.login`: [6](#0-5) 

`Repository.from_github_repo_name` simply splits the string on `/` and does a DB lookup — it has no relationship to which org's secret validated the request: [7](#0-6) 

**Equality broken:** organization authenticated (`repository.owner.login`, used to pick `webhook_secret`) != repository written (`repository.full_name`, used to find the `Stack`/`Repository` to mutate). Because the entire JSON body is attacker-controlled (only the raw bytes are HMAC'd, not individual field bindings between `owner.login` and `full_name`), an operator holding the `webhook_secret` for **any one** organization configured on the Shipit instance can forge a signature that authorizes acting on a **different** organization's repository, simply by making the `repository.owner.login`/`organization.login` field say "OrgA" (the one whose secret they hold) while `repository.full_name` says "OrgB/target-repo".

### Impact Explanation
This allows cross-repository/cross-organization writes without ever needing an `ApiClient` token, session, or GitHub write access to the target org — only knowledge of a `webhook_secret` belonging to *any* other org tracked by the same Shipit install (which is a much lower-privilege boundary: e.g., an org admin/CI operator of an unrelated, less-trusted org onboarded to the same shared Shipit instance). Depending on the handler reached, the attacker can:
- Force `Repository#stacks` lookups to enqueue `GithubSyncJob` for another org's stack (push handler).
- Archive/unarchive another org's review stacks, create phantom `PullRequest`/`Shipit::User` records, or mutate labels/state on stacks belonging to a repository the attacker has no legitimate relationship to.

This matches the "cross-repository writes" Critical-tier impact bucket, since it lets one authenticated-but-unrelated org's credential drive state changes on another org's repositories/stacks.

### Likelihood Explanation
Requires only:
1. The deployment to configure more than one GitHub organization (the documented, supported multi-tenant `github:` config schema with per-org `webhook_secret`), and
2. The attacker to control (or have legitimately received, e.g. as a GitHub org admin who configured the integration) the `webhook_secret` for **one** of those organizations — not the target one.

No GitHub-side signature spoofing is needed since the attacker computes the HMAC themselves with the secret they legitimately hold; they simply mismatch the `owner.login`/`organization.login` field from the `full_name` field in the crafted JSON body sent directly to Shipit's `/github_webhooks` endpoint. This is a straightforward, low-cost forgery for anyone who is a legitimate webhook-secret holder for any one tenant org.

### Recommendation
After resolving `github_app`/verifying the signature via `repository_owner`, explicitly assert that `repository.full_name`'s owner component matches `repository_owner` (or, more robustly, look up the `Repository`/`Stack` scoped to the authenticated organization only) before dispatching to handlers. Reject the webhook (422) on mismatch, mirroring the recommendation from the referenced report: explicitly correlate the field used for authentication (`organization`) with the field used to select the mutated resource (`repository.full_name`), instead of trusting them independently.

### Proof of Concept
Given a Shipit instance configured with two orgs, `OrgA` (attacker-known `webhook_secret_A`) and `OrgB` (repo `OrgB/prod-app` tracked as a Shipit stack, secret unknown to attacker):

1. Attacker crafts JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/prod-app" },
  "organization": { "login": "OrgA" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist in OrgB/prod-app>"
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>`.
3. POST to `/github_webhooks` with header `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner => "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the signature verifies successfully.
5. `Shipit::Webhooks.for_event('push')` handler resolves the target stack via `Repository.from_github_repo_name("OrgB/prod-app")`, enqueuing `GithubSyncJob`/deploy-related side effects against `OrgB`'s stack — despite the request only being authenticated as originating from `OrgA`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
