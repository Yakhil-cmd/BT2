### Title
Unbounded query for AA-owned outputs in `sendUnit()` allows dust-spam DoS/freezing of AA payment responses - (File: `aa_composer.js`)

### Summary
When an autonomous agent (AA) responds to a trigger with a `payment` message, `aa_composer.js`'s `sendUnit()` builds the payment's `inputs` by querying **all** unspent outputs owned by the AA address and iterating over them in JavaScript until enough value is accumulated. Unlike the general wallet coin-selection code path (`inputs.js:pickDivisibleCoinsForAmount`), which bounds the number of candidate outputs with `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2`, the AA-specific queries `readStableOutputs()` and `readUnstableOutputsSentByAAs()` have **no `LIMIT`** clause. An attacker who is an unprivileged unit poster can permissionlessly send an unbounded number of tiny-but-valid outputs to any AA address, forcing every subsequent AA response (and every node validating/replaying it) to fetch and iterate over a huge, attacker-grown output set.

For the base asset, a dust filter of `amount>=FULL_TRANSFER_INPUT_SIZE` (~60 bytes) is applied (line 1149), but for **any custom asset** there is no such floor at all — the `WHERE` clause for a non-base asset is simply `asset=? AND is_spent=0 ...` with no minimum amount. Anyone can pay a small amount of bytes to issue thousands/millions of 1-unit outputs of a custom asset to the AA's address (or thousands of 60-byte-and-up byte outputs for the base asset case, which is still economically cheap relative to the load it creates), permanently growing the "unspent outputs of address X" set that every future AA response must re-query and re-scan.

This mirrors the reported bug class: `getLockedFunds()` in the report loops over an attacker-inflatable, permissionless list (`depList`) every time a privileged action (`refundDeposit`) is attempted, eventually causing an out-of-gas/DoS. Here, the analogous unbounded, attacker-inflatable list is "all unspent outputs owned by the AA address," and the analogous privileged action is "the AA composing any payment message that spends its own balance" — something that runs on **every single trigger** sent to that AA, not just an occasional refund.

Contrast this with the hardened wallet-side function `pickDivisibleCoinsForAmount`, which explicitly bounds the candidate set: [4](#0-3) 

The AA composer path lacks this same protection.

### Impact Explanation
- Every time the targeted AA needs to send bytes/asset back to a trigger address (a core, ubiquitous AA behavior), the node must query and iterate a result set that an attacker fully controls the size of.
- As the dust-output count grows unbounded, the query and the linear JS scan in `iterateUnspentOutputs()` become increasingly expensive (I/O, memory, CPU), which can push AA-response composition well beyond acceptable single-request bounds — a JS-engine analog of "reaching the out-of-gas state," causing computation to stall or the node process to become unresponsive while composing the response.
- Because AA trigger handling must complete deterministically and be reproduced identically by all full nodes validating the resulting response unit, sufficiently degraded/failed composition on some nodes vs. others risks nodes disagreeing on whether a valid AA response was produced, and in the worst case can prevent the AA from ever successfully responding — effectively freezing the AA's ability to move its own funds (a permanent DoS on the AA, matching the "AA fund loss or freezing" impact class).
- The attack is cheap: for non-base assets, there is no dust floor whatsoever, and issuing many 1-unit outputs to the target AA address costs only ordinary base-byte issuance fees on the attacker's side.

### Likelihood Explanation
Any unit poster can trigger this without special privileges: they simply issue a custom asset (or find one) and send a very large number of tiny outputs to the target AA's address, or repeatedly send many small base-byte outputs (each ≥ 60 bytes to pass the dust filter, which is still trivially cheap to produce at scale over time). No cooperation from the AA operator, witnesses, or any other party is required, and the condition compounds over time since spent outputs from past sends do not need to be reused — the attacker can keep growing the set indefinitely as long as the AA doesn't fully drain/consume all of them (and consuming them costs the AA more inputs = more resources on each response too).

### Recommendation
Bound the AA output-selection queries the same way the general wallet coin-selection code does:
- Add a `LIMIT` to `readStableOutputs()` and `readUnstableOutputsSentByAAs()` in `aa_composer.js` similar to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, iterating/paginating if more inputs are genuinely required.
- Apply the existing dust-amount floor (`FULL_TRANSFER_INPUT_SIZE`-equivalent) uniformly to non-base assets as well, not just the base asset, to prevent economically-free dust inflation of an AA's output set.
- Consider tracking/limiting the number of live unspent outputs per (address, asset) at write time (e.g., in `writer.js`) to cap the worst-case fan-in any address can be forced to accumulate.

### Proof of Concept
1. Attacker defines (or uses an existing) custom asset `X`.
2. Attacker issues and sends `N` (e.g., 100,000+) separate 1-unit outputs of asset `X` to the address of a target AA that is known to hold/spend asset `X` in its payment logic (or repeatedly sends many ≥60-byte base outputs if targeting the base-asset code path).
3. Trigger the AA (or wait for it to be triggered by normal use) such that it needs to send out a payment in asset `X` (or bytes).
4. In `sendUnit()` → `completePaymentPayload()` → `readStableOutputs()`/`readUnstableOutputsSentByAAs()`, the SQL query returns all `N` dust outputs (no `LIMIT`), and `iterateUnspentOutputs()` linearly scans through them in JS, growing without bound as `N` grows — degrading or stalling response composition for that AA on every node that processes the trigger.
