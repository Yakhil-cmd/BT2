### Title
Stack-scoped API tokens can read any stack's CCMenu status via unbound `stack_id` param - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` re-implements the private `stack` helper to load `Stack.from_param!(params[:stack_id])` directly, discarding the `stacks` scoping that `Api::BaseController` normally applies to restrict a stack-scoped `ApiClient` to only its own `stack_id`.

### Finding Description
`Api::BaseController#stacks` filters the queryable `Stack` collection to `current_api_client.stack_id` when the authenticated `ApiClient` is bound to one [2](#0-1) . Every other API controller relies on `stack` calling into this scoped `stacks` relation, so a stack-scoped token cannot address any other stack.

`Api::CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, never going through `current_api_client`-derived `stacks` [1](#0-0) . The only authorization gate left is `require_permission :read, :stack`, which merely checks that the `ApiClient#permissions` array contains `"read:stack"` [4](#0-3)  — it says nothing about *which* stack the client is entitled to.

This breaks the binding: `stack a token authorises == stack it touches`. Before the attacker's request, a stack-scoped token (e.g. `here_come_the_walrus`, bound to stack `shipit`, permission `read:stack` only) can only legitimately read the `shipit` stack's CCMenu XML. After the attacker supplies a different `stack_id` in the URL/route param (`/ccmenu/:owner/:repo/:environment/ccmenu` — see route at `config/routes.rb:28`), `CCMenuController#stack` resolves and returns that unrelated stack's build/deploy status, even though the token was never authorized for it.

### Impact Explanation
This allows unauthenticated (relative to the target stack) read of stack state — the CCMenu response includes `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, and lock state [7](#0-6)  — for any stack in the installation, using a token that was only meant to be scoped to one repository/environment. This matches the in-scope High-impact category "unauthenticated read of stack state."

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped `ApiClient` token (e.g. one handed to a third-party CI dashboard integration for a single stack, as created by `ApiClientsController`) can trivially perform this by changing the `stack_id` segment of the CCMenu URL — no additional secrets, privilege escalation, or session state are required beyond the token itself.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (i.e., delegate to `super` or call `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so stack-scoped tokens cannot address stacks outside their `stack_id` binding.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to stack `acme/webapp/production` with permission `read:stack` only (mirrors fixture `here_come_the_walrus`).
2. Compute `token = api_client.authentication_token`.
3. Send `GET /api/stacks/other-org/other-repo/production/ccmenu` (a stack the client was never granted access to) using Basic auth with `token` (or `?token=` per `CCMenuController#authenticate_api_client`).
4. Observe a `200 OK` with the other stack's build/deploy XML, even though the token's `stack_id` only covers `acme/webapp/production`.
