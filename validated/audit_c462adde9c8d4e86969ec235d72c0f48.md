### Title
Unbounded HTTP pagination loop driven entirely by attacker-controlled response data enables denial-of-service in `gh api --paginate` - (File: pkg/cmd/api/api.go)

### Summary
`gh api --paginate` loops indefinitely based solely on values taken from the response returned by the target host: the REST `Link` header (`rel="next"`) or the GraphQL `pageInfo.hasNextPage`/`endCursor` fields. There is no cap on the number of pages, no revisited-URL detection, and no total output/iteration limit, so a malicious or compromised host that a user points `gh api` at (via `--hostname`, a GraphQL Enterprise endpoint, or any GHES-style backend) can trap the CLI in a loop of unbounded HTTP requests and output growth, mirroring the "attacker-controlled configuration value drives an infinite loop" bug class from the report (there, `SplitOpts` fields controlled the loop bound; here, the server-controlled `Link`/`endCursor` values control it).

`hasNextPage` is set purely from `findNextPage(resp)` (REST) or from `endCursor != ""` (GraphQL), both of which are values that are entirely under the control of the responding server: [2](#0-1) [3](#0-2) 

Nothing in this loop:
- Caps the number of iterations/pages fetched.
- Detects a `next` URL that repeats a previously-seen URL (self-referencing pagination).
- Bounds the cumulative amount of data written via `bodyWriter`/`tmpl`.

The same unguarded pattern (Link-header-driven `for {}` with no iteration cap) also exists in `internal/codespaces/api/api.go`'s `ListCodespaces` and `GetOrgMemberCodespace` and in `pkg/search/searcher.go`'s `nextPage`, but those talk to a fixed, presumably-trusted `github.com`/GHES host configured by the authenticated session, so they are lower risk. `pkg/cmd/api/api.go`, by contrast, is explicitly designed to let a user target an arbitrary `--hostname`, making the "attacker-controlled host" precondition directly reachable through a normal, unprivileged `gh` invocation.

### Impact Explanation
If a user runs `gh api --paginate <endpoint> --hostname <attacker-controlled-or-compromised-host>` (or against a GraphQL Enterprise host that is malicious/compromised), the server can:
- Keep returning a `Link: <same-or-new-url>; rel="next"` header (or, for GraphQL, `hasNextPage: true` with an ever-present `endCursor`) forever.
- Cause `gh` to issue unbounded outbound HTTP requests and accumulate unbounded output through `bodyWriter`, tying up the CLI process indefinitely and consuming increasing memory/CPU/network resources — a client-side denial-of-service condition analogous to the livelock described in the source report, where an attacker-influenced value that should bound a loop is used unchecked.

This is a lower-severity analog than the original crash-the-prover bug (no panic path here, and the “attacker” must be the host the user is intentionally querying), but it is a legitimate resource-exhaustion/DoS class rooted in the same root cause: trusting an externally-supplied value to terminate a loop without any independent bound.

### Likelihood Explanation
Reachable by any unprivileged user simply running `gh api --paginate` against a host they don't fully trust (a third-party GHES mirror, a proxy, or a compromised/malicious GraphQL endpoint) — no elevated privileges, MITM position, or leaked token are required beyond normal use of the `--hostname`/GraphQL query features that `gh api` explicitly supports.

### Recommendation
- Add a hard cap on the number of pages/requests performed during pagination (e.g., a configurable `--paginate-max` limit or a sane hardcoded default).
- Track visited "next" URLs (REST) or cursors (GraphQL) and abort with an error if a previously seen value repeats.
- Bound total bytes written by `bodyWriter`/`tmpl` during a paginated run, and surface an explicit error/warning if the limit is exceeded rather than looping forever.

### Proof of Concept
1. Stand up a malicious/compromised HTTP server that responds to any GET with `200 OK` and a `Link` header of `<https://attacker.example/next>; rel="next"` (or, for a `graphql` request, a JSON body with `pageInfo: {hasNextPage: true, endCursor: "x"}` every time).
2. Run `gh api --paginate --hostname attacker.example some/endpoint` (REST) or `gh api graphql --paginate -f query=... --hostname attacker.example` (GraphQL).
3. Observe that `apiRun`'s loop in `pkg/cmd/api/api.go:429-466` never terminates: `findNextPage`/`endCursor` keep returning truthy pagination signals, and `gh` continues issuing requests and buffering/emitting output indefinitely, consuming increasing CPU, memory, and network resources until the process is killed.

func findNextPage(resp *http.Response) (string, bool) {
	for _, m := range linkRE.FindAllStringSubmatch(resp.Header.Get("Link"), -1) {
		if len(m) > 2 && m[2] == "next" {
			return m[1], true
		}
	}
	return "", false
}

func findEndCursor(r io.Reader) string {
	dec := json.NewDecoder(r)

	var idx int
	var stack []json.Delim
	var lastKey string
	var contextKey string

	var endCursor string
	var hasNextPage bool
	var foundEndCursor bool
	var foundNextPage bool

loop:
	for {
		t, err := dec.Token()
		if err == io.EOF {
			break
		}
		if err != nil {
			return ""
		}

		switch tt := t.(type) {
		case json.Delim:
			switch tt {
			case '{', '[':
				stack = append(stack, tt)
				contextKey = lastKey
				idx = 0
			case '}', ']':
				stack = stack[:len(stack)-1]
				contextKey = ""
				idx = 0
			}
		default:
			isKey := len(stack) > 0 && stack[len(stack)-1] == '{' && idx%2 == 0
			idx++

			switch tt := t.(type) {
			case string:
				if isKey {
					lastKey = tt
				} else if contextKey == "pageInfo" && lastKey == "endCursor" {
					endCursor = tt
					foundEndCursor = true
					if foundNextPage {
						break loop
					}
				}
			case bool:
				if contextKey == "pageInfo" && lastKey == "hasNextPage" {
					hasNextPage = tt
					foundNextPage = true
					if foundEndCursor {
						break loop
					}
				}
			}
		}
	}

	if hasNextPage {
		return endCursor
	}
	return ""
}
