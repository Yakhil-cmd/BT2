## Analysis

The bug-class from the report — a security-critical field (`safeAddress`) that is used to gate authorization but is excluded from what the signature actually binds — has a direct analog in `Shipit::WebhooksController`.

### The binding that should hold but doesn't

`Shipit.github(organization: repository_owner)` selects **which org's secret** is used to verify `X-Hub-Signature`, and `repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). [1](#0-0) [2](#0-1) 

Signature verification itself is a raw HMAC over the whole request body using the secret configured for whichever org happens to be named by that field: [3](#0-2) 

But every event handler that actually mutates state resolves the **target repository/stack** from a *different* JSON field — `repository.full_name` — via `Handler#repository_name`/`#stacks`: [4](#0-3) 

Nothing cross-validates that `repository.owner.login` (used to pick the verifying secret) is the actual owner prefix of `repository.full_name` (used to pick the mutated stack). Both fields sit in the same signed byte-blob, so a party who legitimately knows the webhook secret for *any one* org configured on the instance (Shipit explicitly supports multi-org deployments, e.g. `test/dummy/config/secrets_double_github_app.yml` with `OrgOne`/`OrgTwo`) can self-sign an arbitrary payload where `repository.owner.login` = "their org" (so their own secret is selected and the HMAC check passes) while `repository.full_name` = "victim-org/victim-repo" (so a handler mutates a stack that belongs to a completely different, unrelated GitHub org on the same Shipit install).

This mirrors the report precisely: **the signature covers the payload bytes, but the specific field that authorizes routing (`owner.login`) is disjoint from the field that authorizes the write (`full_name`)** — exactly like `safeAddress` being checked for approval count but omitted from the actual signed digest.

### Concrete high-impact handler

`Shipit::Webhooks::Handlers::StatusHandler` (registered for the `status` event) creates a `Status` from unverified webhook content scoped only by `repository.full_name` lookup. Creating a `success` status is known to synchronously enqueue `ProcessMergeRequestsJob` and, for stacks with continuous deployment enabled, actually enqueue `ContinuousDeliveryJob` / trigger a real deploy: [5](#0-4) [6](#0-5) 

So an attacker holding only the webhook secret for *their own* (weakly-trusted / low-value) org can forge a `status` event naming a victim stack in `repository.full_name`, get it past `verify_signature` using their own org's secret, and trigger an unauthorized deploy on a stack belonging to a different organization entirely.

Similarly `PushHandler` can force a resync to an attacker-chosen `expected_head_sha` on the victim stack: [7](#0-6) , and PR handlers can archive/unarchive review stacks for repos they don't own.

### Title
Webhook signature-selection field (`repository.owner.login`) is disjoint from the mutation-target field (`repository.full_name`), enabling cross-organization forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against using `repository.owner.login`/`organization.login`, but every downstream `Handler` resolves the stack/repository to mutate using the independent `repository.full_name` field from the same JSON body. Because these two fields are never cross-checked, a party who legitimately possesses the webhook secret for one GitHub organization configured on a multi-org Shipit instance can self-sign a payload that names their own org for signature purposes while targeting a `full_name` belonging to an entirely different organization's stack.

### Finding Description
`verify_signature` derives the org used to look up `Shipit.github(organization:)`/`webhook_secret` from `params.dig('repository', 'owner', 'login')` [8](#0-7) , and passes/fails purely on `OpenSSL::HMAC` over the raw body with that org's secret [3](#0-2) . `Handler#stacks`/`#repository_name`, used by every registered handler (`push`, `status`, `check_suite`, `pull_request/*`), instead resolves the target purely from `repository.full_name` [4](#0-3) . An attacker who is a legitimate (low-privilege) admin of one org hosted on the same Shipit instance knows that org's `webhook_secret` (per setup docs, the admin generates and keeps it) and can therefore self-sign arbitrary bodies, decoupling "who the signature authenticates" from "what gets written."

### Impact Explanation
A cross-org forged `status` event with `state: success` can trigger `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` and cause an unauthorized deploy on a victim organization's stack; forged `push`/`pull_request` events can force resyncs or archive/unarchive review stacks belonging to a repository the attacker never had legitimate access to. This meets the Critical bar of "an unauthorized deploy, rollback, or merge" performed against a repository/stack outside the attacker's authorized organization.

### Likelihood Explanation
Requires only that the attacker be a legitimate admin/holder of a `webhook_secret` for *any* org configured on a shared, multi-tenant Shipit instance (a documented, supported configuration) — no Shipit session, API token, or GitHub App private key for the victim org is needed.

### Recommendation
Bind signature verification to the same identity used for mutation: verify that `repository.full_name`'s owner segment matches the org whose secret validated the signature (or better, verify signatures per-repository rather than per-owner-login), and have `Handler#stacks` cross-check `repository.owner.login`/`organization.login` against the resolved `Stack`'s actual GitHub organization before acting.

### Proof of Concept
1. Attacker is an admin of `OrgA`, configured in the same multi-org Shipit `secrets.yml` (e.g. as in `test/dummy/config/secrets_double_github_app.yml`), and knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `status` webhook JSON body: `{"repository": {"full_name": "OrgB/victim-repo", "owner": {"login": "OrgA"}}, "sha": "<head_sha_of_victim_stack>", "state": "success", ...}`.
3. Attacker computes `sha1=` HMAC of this exact body using `OrgA`'s known `webhook_secret` and sends it as `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GithubApp`, and the HMAC matches → request passes. [1](#0-0) 
5. `StatusHandler`/`Handler#stacks` resolves the stack via `repository.full_name` = `"OrgB/victim-repo"`, unrelated to `OrgA`, and creates the forged success status, potentially triggering an unauthorized deploy on `OrgB`'s stack. [4](#0-3)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
