### Title
Webhook signature verification binds the wrong organization to the payload, letting an attacker forge CI status / push events for stacks belonging to a different organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to check the HMAC signature against using only `repository.owner.login` (or `organization.login`) from the *unauthenticated* JSON body. The handlers that actually act on the payload (`StatusHandler`, `PushHandler`, `CheckSuiteHandler`) then resolve their target `Commit`/`Stack` using a *different* field (`repository.full_name`, or for `StatusHandler` no repository scoping at all). The signature never binds "the organization whose secret validated this request" to "the repository/commit the handler will mutate," breaking the required equality: organization authenticated == repository written.

### Finding Description
`verify_signature` computes the org to authenticate against purely from attacker-controlled payload fields: [1](#0-0) [2](#0-1) 

It calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. Critically, `verify_webhook_signature` is a no-op that returns `true` whenever that organization's `webhook_secret` is blank: [3](#0-2) 

`webhook_secret` is explicitly documented/templated as optional and defaults to nil in every setup path (`config/secrets.development.example.yml`, `template.rb`, `docs/setup.md`), so in many real deployments — and definitely for any additional org added to a multi-org config without a secret — this check is a pure no-op.

Once `create` passes the check, the full raw JSON `params` (unmodified, attacker-controlled) is dispatched to handlers: [4](#0-3) 

The base `Handler` resolves target stacks from `payload.dig('repository', 'full_name')` — a field completely independent from the `repository.owner.login`/`organization.login` field used for signature-org selection: [5](#0-4) 

`PushHandler` and `CheckSuiteHandler` use this `stacks` helper to sync/refresh arbitrary stacks: [6](#0-5) [7](#0-6) 

`StatusHandler` is worse: it does not scope by repository/full_name at all, only by commit SHA, globally across the entire install: [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization used to select/validate the webhook secret` == `owner of the repository whose Stack/Commit the handler mutates`.

Before the attack: signature check is scoped to org X (chosen by attacker via `repository.owner.login`/`organization.login`), and separately the handler acts on whatever `repository.full_name` (or bare `sha`) says, which can name a completely different org/repo/commit.

After the attack: an attacker who only needs *any* organization configured on the instance to have a blank `webhook_secret` (the documented default) can craft a POST to `/webhooks` whose `repository.owner.login` is that blank-secret org (passing `verify_signature` trivially) while `repository.full_name` (for push/check_suite) or `sha` (for status) targets a stack/commit that belongs to an entirely different, securely-configured organization.

### Impact Explanation
- `StatusHandler`: `Commit.where(sha: params.sha)` is unscoped by owner/repository; an attacker can forge a `success` CI status for any commit SHA in the database. For stacks with `continuous_deployment: true`, this can trigger an automatic, unauthorized deploy of a commit that never actually passed CI on GitHub — a genuine unauthorized-deploy path with no privileged account, `ApiClient` token, or GITHUB_TOKEN required. See `Commit#deployable?`/`required_statuses` gating logic referenced in `test/models/commits_test.rb`.
- `PushHandler`/`CheckSuiteHandler`: forged push/check-suite events cause `sync_github`/`schedule_refresh_check_runs!` to run for arbitrary stacks using attacker-supplied `expected_head_sha`, letting an attacker manipulate which commit Shipit believes is "at HEAD" for someone else's stack.
- All of this requires no repository write access, no GitHub App private key, no `ApiClient`/session token — only that one configured org on the instance (attacker's own, or any decoy org) omits `webhook_secret`, which is the shipped default in every setup template.

This satisfies the Critical bar ("unauthorized deploy") without crossing any excluded boundary (no webhook_secret of the *target* org is needed, only the trivial blank-secret bypass of signature verification for an unrelated org name chosen by the attacker).

### Likelihood Explanation
High. `webhook_secret: # nil` is the literal example/default across `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, and `template.rb`; the setup docs describe it as merely "optional." Any Shipit instance with even one configured organization lacking a webhook secret (a common oversight, especially in multi-org configs where a secondary org is added later) exposes this cross-org confusion to any unauthenticated internet client capable of POSTing to `/webhooks`.

### Recommendation
Bind the payload's actual target repository to the same identity used for signature verification: after selecting the GitHub App/org for signature verification, re-derive `repository_owner` (and require it to be present) and enforce that `payload.dig('repository', 'full_name')`'s owner segment (and any commit's owning repository, for `StatusHandler`) matches the verified organization before invoking handlers. Additionally, require `webhook_secret` to be present for all configured organizations (fail closed / refuse to boot or log a strong warning) rather than treating a blank secret as automatically verified.

### Proof of Concept
1. Configure (or exploit an existing) Shipit deployment with two GitHub orgs, e.g. `victim-org` (has `webhook_secret` set, hosts a stack with `continuous_deployment: true`) and `attacker-org` (added later, `webhook_secret` left blank per the default template).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<sha_of_victim_org_commit>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which returns `true` immediately because `attacker-org`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `victim-org`'s stack, and creates a `success` status for it, regardless of what CI on GitHub actually reported for that commit.
5. If that stack has continuous deployment enabled, the forged success status can trigger an automatic deploy of that commit.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
