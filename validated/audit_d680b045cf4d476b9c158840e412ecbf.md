## Title
Asset Issuer/Attestor-Controlled `spender_attested` Gate Enables Permanent Freezing of Recipient Funds - ([File: validation.js])

### Summary
Assets defined with `spender_attested: true` can only be spent by addresses that appear on an attestor-approved allow-list. The attestor list itself is entirely controlled by the asset's `definer_address` (who alone may add/replace attestors), and the actual per-address attestation is issued solely by those attestor addresses via `attestation` messages. There is no on-chain mechanism forcing attestors to attest a given recipient, nor any way for a payment recipient to force inclusion. This mirrors the reported centralization risk: a privileged party (definer/attestor, analogous to the "admin" setting the Merkle root) unilaterally decides who can access already-received funds, and an excluded/omitted recipient has no recourse and their tokens become permanently unspendable.

### Finding Description
When an asset is defined with `spender_attested: true`, `validatePayment` in `validation.js` requires that either the issuer (for `issue` inputs) or all payment authors be present in `objAsset.arrAttestedAddresses` before a payment message referencing that asset is considered valid: [1](#0-0) 

`arrAttestedAddresses` is computed by `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses`, which checks the `attestations` table for rows where `attestor_address` is one of `objAsset.arrAttestorAddresses` (the definer-controlled attestor set): [2](#0-1) 

The attestor list (`asset_attestors`) that gates who is allowed to attest can only be modified by the asset's `definer_address`, enforced in `validateAttestorListUpdate`: [3](#0-2) 

Because attestation is a separate, independently-authored `attestation` message controlled solely by whichever addresses the definer designated as attestors, a recipient who legitimately receives outputs of a `spender_attested` asset (e.g. as change, as a transfer, or through an AA payout) can be permanently excluded from ever spending those funds if the definer/attestors never attest their address — whether by oversight, negligence, or malicious intent. There is no cryptographic proof or verifiable allow-list (unlike a Merkle proof scheme) that lets the excluded party independently demonstrate eligibility; inclusion is purely at the attestor/definer's discretion, and the recipient cannot self-attest.

This is architecturally identical to the reported issue: a single privileged party fully controls the "distribution/eligibility list" that gates access to funds already assigned to a recipient, and an omitted recipient has no way to claim what is otherwise theirs.

### Impact Explanation
Any holder of a `spender_attested` asset (which can be created permissionlessly by any unit poster, including via AA `asset` message emission as seen in `aa_validation.js` asset field validation) is at risk of having their asset balance permanently frozen if the definer/attestors decline or fail to attest their address. This is a concrete "AA fund loss or freezing" scenario: funds are received but can never move, indefinitely, at the sole discretion of the definer/attestor set — a direct centralization risk with real economic impact for excluded users, and this is a built-in design feature reachable by any user who is issued or transferred such an asset.

### Likelihood Explanation
Any address can define a `spender_attested` asset (as author of an `asset` message) or an AA can programmatically define one via the `asset` app message; nothing prevents a definer from designating only a small/whitelisted attestor set or omitting arbitrary recipients from ever being attested. This requires no special privilege beyond being the asset's definer, and payments to arbitrary addresses under that asset are otherwise unrestricted by validation — so the freeze condition triggers naturally whenever any address receives such an asset without being (or ever becoming) attested.

### Recommendation
- Document explicitly (and surface via wallet/UX warnings) that `spender_attested` assets grant the definer/attestor set unilateral, revocable control over spendability of a recipient's balance, so senders/recipients can make informed trust decisions.
- Consider adding a way for asset definitions to specify a deterministic/verifiable attestation policy (e.g., attestation via a published, provable rule such as a Merkle proof against a committed list, or a data-feed/oracle condition) rather than free-form `attestation` messages, reducing reliance on continued, unaccountable goodwill of specific attestor addresses.
- Provide fallback/expiry semantics (e.g., automatic transferability after a timeout with no attestation decision) to bound the freezing risk for good-faith recipients.

### Proof of Concept
1. Author A defines an asset with `is_transferrable: true, spender_attested: true, attestors: [A]` (A designates itself as sole attestor) via an `asset` message, validated by `validateAssetDefinition`/`checkAttestorList`.
2. A issues asset to a set of addresses; recipient B receives asset outputs in a transfer.
3. B attempts to spend/transfer these asset outputs; `validatePayment` requires B ∈ `arrAttestedAddresses`.
4. A never publishes an `attestation` message for B (deliberately or through neglect); B's tokens can never pass validation since `filterAttestedAddresses` never returns B.
5. B's funds are permanently frozen — no on-chain mechanism, proof, or timeout allows B to reclaim spendability, replicating the "admin excludes a recipient" centralization risk from the original report.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
