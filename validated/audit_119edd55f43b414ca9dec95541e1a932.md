### Title
Unbounded git submodule recursion depth allows disk/resource exhaustion (git-bomb) via a malicious remote repository - (File: main.go)

### Summary
`git-sync`'s default `--submodules=recursive` behavior invokes `git submodule update --init --recursive` with no cap on nesting depth or submodule count. Because the set of submodules and how deeply they nest is entirely determined by the `.gitmodules` content of the remote repository being synced, an attacker who controls (or can get merged into) that upstream content can construct a submodule chain that expands to an enormous amount of data/inodes on every sync, exhausting disk space on the shared volume and causing `git-sync` to fail or hang — a persistent denial of the sync service. This mirrors the "no max" class of bug in the referenced report: an unbounded, attacker-influenced parameter (submodule recursion) is used directly in a high-cost operation (`git submodule update --recursive`) with no configured or hard-coded ceiling.

### Finding Description
In `configureWorktree`, submodule handling is driven purely by the `--submodules` flag value and the repo's own `.gitmodules` files, with no limit on recursion depth or total submodule count: [1](#0-0) 

The `--submodules` flag defaults to `"recursive"`: [2](#0-1) 

`--depth` only bounds commit history, not submodule fan-out or nesting, and defaults to `1` (still unbounded submodule tree size): [3](#0-2) 

Because `git submodule update --init --recursive` will recurse through every `.gitmodules` file transitively (nested submodules referencing other nested submodules, potentially referencing each other or huge chains of empty/large repos), the total amount of data fetched and the number of worktree directories created scale with whatever the untrusted remote repository author defines — with no cap enforced by `git-sync`. The e2e test suite exercises nested submodules (`sub` -> `nested-sub`) confirming this recursive behavior is fully content-driven: [4](#0-3) 

Unlike `--max-failures`/`--init-max-failures`, which do bound retry counts, there is no analogous `--max-submodule-depth` or size/count guard for submodule expansion.

### Impact Explanation
A malicious or compromised upstream repository (or a compromised branch/PR that gets synced) can define deeply nested or numerous submodules, causing each sync cycle to fetch and check out an attacker-controlled, effectively unbounded amount of data into `--root`. This can exhaust disk space on the shared volume used by the Kubernetes sidecar pattern that `git-sync` is designed for, causing sync failures, application read errors, and a persistent denial of the git-sync service (repeated sync failures or crash-looping). This matches the "persistent sync denial" and "publishing wrong or partial content" impact categories.

### Likelihood Explanation
Likelihood is moderate: it requires the synced `--repo` (or a submodule reachable from it) to contain attacker-influenced content, e.g. a mirrored public repository, a PR-based CI mirror, or any workflow where `git-sync` follows a ref that includes third-party-controlled submodule references. No special git-sync privileges are needed — only the ability to influence `.gitmodules` content of what is synced, which is a realistic scenario for `git-sync` given its purpose (mirroring potentially external repos, submodules over SSH/HTTP with distinct credentials as shown in the e2e tests).

### Recommendation
- Add a configurable cap on submodule recursion depth and/or total number of submodules processed per sync (e.g. `--max-submodule-depth`, `--max-submodule-count`), rejecting or truncating expansion beyond the limit.
- Consider combining `--depth` enforcement with submodules by default (already partially done) and warn/fail loudly when `--submodules=recursive` is combined with `--depth=0` (full history) on an unknown/untrusted repo.
- Monitor and enforce a disk-usage or file-count budget for the `--root` directory, failing the sync (rather than silently filling the disk) when exceeded.

### Proof of Concept
1. Create a chain of N git repositories `sub_1 .. sub_N`, each adding the next as a submodule (`git submodule add`), simulating what an attacker-controlled upstream project could set up.
2. Point the top-level repo's `.gitmodules` at `sub_1`, and have the victim run:
   ```
   git-sync --repo=<attacker-controlled-repo> --root=/mnt/git --link=link --submodules=recursive
   ```
3. Each sync invokes `git submodule update --init --recursive` (as shown at [5](#0-4)  ), which recursively clones the entire N-deep chain with no depth/count limit, consuming disk proportional to N and the size of each submodule, which the attacker fully controls.
4. Repeating this with a sufficiently large N (or large blobs in leaf submodules) exhausts the shared volume, causing subsequent syncs to fail (`cleanup`/`configureWorktree` errors) and the sidecar to enter a persistent failure state.
