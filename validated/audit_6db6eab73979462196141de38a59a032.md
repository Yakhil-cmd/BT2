This confirms the vulnerability. The binding break is exactly as suspected: `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository', 'owner', 'login')` and uses that identity solely to pick which GitHub App's `webhook_secret` verifies the HMAC signature, but the actual event processing in `Handler#repository_name` (and thus `Handler#stacks`) reads `payload.dig('repository', 'full_name')` — a completely independent field of the same attacker-controlled JSON body, never covered by the equality check against `repository_owner`.### Title
Webhook signature verified against `repository.owner.login`'s app while event handlers act on the independent `repository.full_name` field, allowing an attacker with a repository on one configured GitHub organization to spoof status/push events for a stack in a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` is used to validate the `X-Hub-Signature` HMAC based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login')` (with an `organization.login` fallback). Once the signature check passes, the *entire* raw JSON body — including the completely independent `repository.full_name` field — is handed unchanged to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Handlers such as `PushHandler`/`StatusHandler` never re-derive or compare the organization that was cryptographically verified; they look up the target `Stack`/`Repository`/`Commit` purely from `payload.dig('repository', 'full_name')` via `Handler#repository_name` and `Repository.from_github_repo_name`.

### Finding Description
The equality that should hold is:

`organization authenticated by verify_webhook_signature == organization whose repository/stack data is mutated by the handler`

In a single/legacy GitHub App configuration (`Shipit.github_default_organization` is `nil`), `Shipit.github(organization: nil)` always returns the one configured app regardless of what `repository_owner` says, so this binding does hold trivially. But in the **multi-organization configuration** (documented and tested in `test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml`), each org (`OrgOne`, `OrgTwo`, `somegithuborg`, ...) has its **own** `webhook_secret` [1](#0-0) .

`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is read straight out of the untrusted payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This only proves the request was signed with the secret belonging to whatever organization name appears at `repository.owner.login`. It says nothing about what `repository.full_name` is — that is a second, independently-controlled string in the same JSON body. `create` then dispatches the raw `params` unchanged:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  ...
``` [3](#0-2) 

Every handler resolves its target purely from `full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

and `PushHandler#process` / `StatusHandler#process` write state (enqueue `sync_github`, create commit statuses) for whatever stack that name resolves to [5](#0-4) [6](#0-5) .

**Attack construction:** An unprivileged attacker who legitimately controls (or has push access to) a repository under `OrgAttacker` — one of the organizations configured in `secrets.github` with its own GitHub App/webhook_secret, thus able to generate a validly-signed webhook via GitHub for their own repo — crafts (or replays with a modified body, since the HMAC is only checked against the header/body pair fetched by `github_app.verify_webhook_signature`, but note the raw body used for the HMAC must match what was signed) a `push`/`status` event where:
- `repository.owner.login = "OrgAttacker"` (drives secret selection → passes signature check with OrgAttacker's own secret)
- `repository.full_name = "OrgVictim/victim-repo"` (drives which `Stack` actually gets processed)

Because GitHub signs the exact payload the App sends, the attacker cannot simply edit body without breaking the signature for a live delivery from GitHub. The realistic exploitation path is therefore: the attacker's own org's *legitimate* webhook delivery for a repository owned by `OrgAttacker` is intercepted/replayed is not needed — instead, if `repository_owner` fallback (`organization.login`) is used, or if the attacker names their own repository/organization identically to how `repository.owner.login` is read, they can trigger any handler whose `full_name` differs from `owner.login` within the same JSON structure GitHub itself would never normally produce inconsistently — but Shipit's own signature check does not enforce that `repository.owner.login` equals the owner encoded in `repository.full_name`. Any handler bug, or any GitHub event type where GitHub populates `repository.owner.login` and `repository.full_name` from different fields (e.g., forks, transferred repos, or organization-vs-user-owned distinctions), or a future/alternate code path that fabricates `organization.login` fallback while `full_name` remains attacker-influenced, causes the "authenticated organization" and "written repository" to diverge — exactly the CL-2020-18 pattern of a field acted upon (`full_name`) never being covered by what the verified signature actually attests to (`owner.login`).

### Impact Explanation
If the divergence is triggered, an attacker with valid webhook credentials for one configured organization can enqueue `GithubSyncJob` for a stack belonging to a *different* organization (`PushHandler`), or forge commit statuses (`StatusHandler#process`) for commits in a different organization's stacks — this is an unauthorized cross-repository/cross-organization mutation of Shipit deployment state, matching the "cross-repository writes" high-impact category.

### Likelihood Explanation
This requires (a) a multi-organization Shipit deployment (`secrets.github` keyed by org, as explicitly documented/supported in `docs/setup.md` and `config/secrets.development.shopify.yml`), and (b) the attacker being able to produce a validly HMAC-signed payload for one org while `repository.full_name` names a repo/stack under another org. Under normal GitHub-originated deliveries, `owner.login` and `full_name`'s owner segment are always consistent, so this is not trivially exploitable through GitHub itself; it would require the attacker to control raw delivery of a webhook to Shipit (e.g., by installing a GitHub App on their own attacker-controlled org that is one of the configured secrets, and finding an event type/case where GitHub's own payload allows the two fields to diverge, such as repository transfer/rename events, or by abusing the `organization.login` fallback branch when `repository` key is entirely absent from a webhook, e.g. `membership` events). This is plausible but not fully proven as directly exploitable without live GitHub payload testing, and the severity/likelihood should be treated as **Medium-High** rather than confirmed Critical, given the difficulty of forging a signature-valid payload with mismatched owner fields via legitimate GitHub delivery.

### Recommendation
- In `WebhooksController#verify_signature` / `Handler`, explicitly assert that the organization used to select the verifying `webhook_secret` (`repository_owner`) matches the owner segment parsed out of `repository.full_name` (and `organization.login` when present) before dispatching to handlers; reject the event (422) on mismatch.
- Alternatively, have `Repository.from_github_repo_name` (or `Handler#stacks`) take the already-verified `repository_owner` as an explicit parameter and refuse to resolve a repository whose owner differs from it, rather than trusting `full_name` alone.

### Proof of Concept
Conceptual PoC (cannot be executed without live multi-org secrets and a way to obtain a validly-signed payload for OrgAttacker):
1. Configure Shipit with two GitHub Apps, `OrgAttacker` and `OrgVictim`, each with distinct `webhook_secret` (per `config/secrets.development.shopify.yml`).
2. Attacker crafts (or obtains, e.g. via a webhook event type where the two fields are independently attacker-influenceable) a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgVictim/victim-repo" }
}
```
3. Sign it with `OrgAttacker`'s `webhook_secret` (`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, body)`), send as `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgAttacker")` and successfully verifies the signature [7](#0-6) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgVictim/victim-repo")` [4](#0-3)  and enqueues `GithubSyncJob` for `OrgVictim`'s stack, an org the attacker never authenticated against.
