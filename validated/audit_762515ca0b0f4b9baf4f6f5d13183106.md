### Title
Webhook signature verified against `repository.owner.login`, but repository resolution for stack writes uses the unrelated `repository.full_name` field, allowing cross-organization stack sync/write - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization secret to check the HMAC signature using `repository_owner`, which is read from the attacker-controlled JSON body field `repository.owner.login` (falling back to `organization.login`) [1](#0-0) . Separately, every webhook `Handler` (e.g. `PushHandler`) resolves which `Repository`/`Stack` records to act on using a *different* field of the same body, `repository.full_name` [2](#0-1) . Nothing ties these two fields together, so the field that authenticates the request (owner login used to pick the per-org webhook secret) is not the field that is actually acted upon (full_name used to look up the target repository/stack).

### Finding Description
In a multi-organization Shipit configuration (`Shipit.github(organization: ...)`, see `lib/shipit.rb#github_app_config`), each GitHub organization has its own independent `webhook_secret` [3](#0-2) . The webhook signature check is:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

This means the HMAC is validated against whichever organization's secret the *attacker names* in `repository.owner.login`. Once verification succeeds, `WebhooksController#create` dispatches the whole raw JSON `params` to the registered handlers [5](#0-4) . Handlers such as `PushHandler` determine which `Stack`s to sync purely from `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) [6](#0-5) 

Because `repository.owner.login` (used to select the secret for authentication) and `repository.full_name` (used to select the repository whose stacks get written to) are two independent, attacker-supplied strings in the same JSON body, an attacker who legitimately administers one organization's GitHub App integration on Shipit (and therefore knows/controls that org's `webhook_secret`) can forge a signed payload where `repository.owner.login = "attacker-org"` (so the signature validates against the attacker's own known secret) while `repository.full_name = "victim-org/victim-repo"`. The signature check passes because it is bound to the attacker's own organization, yet the actual database write/side effect (queuing `GithubSyncJob`, appending fabricated commits via `stack.commits.create_from_github!`, etc.) is performed against the victim organization's tracked stack, entirely decoupled from the identity that was actually authenticated.

This is the same class of bug as the reported issue: two related fields in a signed/verified payload are expected to be consistent, but only one of them is checked/trusted while the other one, which drives the actual privileged action, is left unchecked against the verified identity.

### Impact Explanation
This breaks the trust binding "the organization that authenticated the webhook == the repository that is written," letting a user who controls one org's Shipit GitHub App webhook secret trigger `GithubSyncJob`/commit ingestion against another organization's stacks. Depending on which handler receives the crafted payload and what data it writes (e.g., commits, statuses, check runs), this could corrupt stack history, inject unauthorized commit metadata, or otherwise cause unauthorized state changes in a stack that does not belong to the attacker's organization — a cross-repository/cross-organization write performed without proper authorization, matching the report's "Critical — cross-repository writes" impact bucket.

### Likelihood Explanation
Exploitability requires the attacker to already have legitimate administrative access over at least one organization onboarded to the same multi-org Shipit deployment (so they know that org's `webhook_secret`) — this is a real, foreseeable configuration for larger Shipit deployments that manage multiple GitHub orgs (as documented in `docs/setup.md`/`config/secrets.development.example.yml`'s multi-org schema). Given that access, forging the payload is trivial (a single HTTP POST with a valid HMAC and mismatched `owner.login`/`full_name` fields); no other secret or session is required. Likelihood is moderate-to-high in any deployment using the multi-organization GitHub app configuration.

### Recommendation
In `WebhooksController#verify_signature` (and/or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select/verify the webhook secret matches the owner encoded in `repository.full_name` (and in `organization.login` for org-scoped events) before dispatching to handlers — e.g., reject the request if `repository.full_name.split('/').first.casecmp(repository_owner) != 0`. More generally, handlers should derive the target repository from the same authenticated organization value rather than re-reading an independent, unauthenticated field from the payload.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `attacker-org` (secret known to the attacker, who administers that org's GitHub App) and `victim-org` (tracks a Shipit stack, e.g. `victim-org/victim-repo`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact raw body and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully since the attacker used the correct secret for `attacker-org` [7](#0-6) .
5. `PushHandler#process` resolves `stacks` from `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, and queues `GithubSyncJob`/commit ingestion for the victim's stack [6](#0-5) , despite the request never being authenticated against `victim-org`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
