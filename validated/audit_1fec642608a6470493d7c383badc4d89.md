### Title
Cross-tenant Team/Membership write via self-selected webhook signing organization - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify a payload against using an attacker-controlled field in that same payload (`repository.owner.login` or `organization.login`), rather than any value tied to the actual HTTP endpoint/config that received the request. Combined with `MembershipHandler#find_or_create_team!` using only the GitHub-global `team.id` (not `organization.login`) to locate the `Team` record to mutate, an attacker who controls any single onboarded organization's webhook secret can send a `membership` event that is "self-signed" but targets a `Team` row belonging to a completely different organization.

### Finding Description
The broken binding: `organization_that_signed_the_payload == organization_that_owns_the_Team_being_mutated` must hold, but nothing enforces it.

- `repository_owner` falls back to `params.dig('organization', 'login')` when there's no `repository` key [2](#0-1) .
- `verify_signature` calls `Shipit.github(organization: repository_owner)` and then verifies the signature using *that same organization's* `webhook_secret` [3](#0-2) . Since GitHub App configs are keyed per-organization in `secrets.github` [1](#0-0) , an attacker who legitimately controls `attacker-org` (and thus its `webhook_secret`) can pick `organization.login = 'attacker-org'`, sign the raw body with `attacker-org`'s own secret, and the check trivially passes — it never confirms that `attacker-org` has anything to do with the entity the payload is about to mutate.
- `MembershipHandler#find_or_create_team!` resolves the target `Team` purely by `github_id: params.team.id`, a GitHub-global numeric ID unrelated to `organization.login` [4](#0-3) . If a `Team` with that `github_id` already exists (belonging to a different org, e.g. a real target org onboarded to Shipit), `find_or_create_by!` returns the existing record *without* running the block that would set `organization`/`name`/`slug` — so the pre-existing target `Team` is returned unmodified, and then `process` calls `team.add_member(member)` on it, using an attacker-supplied `member.login` [5](#0-4) . This creates a `Membership` row linking an arbitrary GitHub user to another organization's `Team`, using a signature that only proves control of an unrelated organization.
- Attack request: `POST /webhooks` with `X-Github-Event: membership`, body `{"action":"added","team":{"id":<TARGET_TEAM_GITHUB_ID>,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"}}`, `X-Hub-Signature` computed with `attacker-org`'s own `webhook_secret`.
- Why existing guards fail: `drop_unhandled_event` and `check_if_ping` don't inspect payload semantics; `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not cross-field consistency between `organization.login` and the resolved `Team.organization` [6](#0-5) ; `GithubOrganizationUnknown` only guards against orgs absent from `secrets.github`, not organization/team mismatch.
- Escalation path: if the collided `Team` is one of the `Team` records referenced by `Shipit.github_teams` (the org's access-gating teams, matched by local `id`, not `github_id`, in `User#authorized?`) [7](#0-6) , the attacker's own GitHub user gets a `Membership` in that gating team, which is fetched/created via `User.find_or_create_by_login!` even for a brand-new user, and this bypasses `force_github_authentication`'s team check entirely [8](#0-7) .

### Impact Explanation
An unprivileged attacker who merely controls one onboarded organization's webhook secret (their own, unrelated org) can inject a `Membership` row associating an arbitrary GitHub login with any pre-existing `Team` in Shipit's database, as long as they know/guess that target `Team`'s numeric GitHub `github_id`. If that `Team` happens to be one of the teams configured in `Shipit.github_teams`, this becomes an authentication/authorization bypass: the attacker's GitHub account becomes "authorized" to use the Shipit deploy UI without ever being a real member of the gating GitHub team, matching "escalation into `Shipit.github_teams` authorization." This is repeatable per target `github_id` and is a cross-tenant write not restricted to the attacker's own organization's data.

### Likelihood Explanation
Preconditions: attacker needs their own organization onboarded to Shipit (`Shipit.secrets.github` entry with a `webhook_secret` they know, standard for orgs given self-service Shipit access), and must know/guess the numeric `github_id` of the target `Team` row (assigned by GitHub when the team was created; not directly exposed by Shipit, so this is the main obstacle to reliable exploitation, though feasible if the ID is discoverable through other GitHub API surfaces or reused across environments). No Shipit session, API token, or GitHub App private key is required — only a webhook secret the attacker legitimately possesses. The request is a single unauthenticated POST, fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization: params.organization.login` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/no-op if a `Team` with that `github_id` exists under a *different* organization. Additionally, `WebhooksController#verify_signature` should not trust `organization.login`/`repository.owner.login` from the payload as the sole selector for which secret verifies it without any additional binding to the endpoint/installation that is supposed to receive that organization's events.

### Proof of Concept
```ruby
test ":membership from org A's own webhook_secret cannot mutate org B's pre-existing Team" do
  org_b_team = shipit_teams(:shopify_developers) # belongs to organization "shopify"

  # simulate an attacker-controlled org "attacker-org" onboarded to Shipit with its own secret
  attacker_app = Shipit.github(organization: 'attacker-org') # requires 'attacker-org' key in secrets.github fixture
  raw_body = {
    action: 'added',
    team: { id: org_b_team.github_id, name: 'x', slug: 'x', url: 'https://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json
  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_app.webhook_secret, raw_body)}"

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  User.any_instance.stubs(:find_or_create_by_login!) # avoid live GitHub call
  assert_no_difference -> { Team.count } do
    post :create, body: raw_body, as: :json
    assert_response :ok
  end

  # BROKEN BINDING: org_b_team.organization ("shopify") was mutated by a signature
  # that only proves control of "attacker-org"
  assert_includes org_b_team.reload.members.map(&:login), 'attacker-login'
end
```
Both sides of the binding — `repository_owner`/`organization.login` used to select the verifying secret ("attacker-org") vs. `Team.organization` of the row actually mutated ("shopify") — diverge, confirming the vulnerability.

    # Backward compatibility
