### Title
Asset issuer can permanently freeze existing holders' balances of a `spender_attested` asset by rotating the attestor list - (File: `validation.js`, `storage.js`)

### Summary
Assets defined with `spender_attested: true` require that the owner of any input/output be "attested" by one of the asset's currently-designated attestors before a payment can spend or receive that asset. The attestor list is not fixed once a holder acquires the asset — the definer can post an `asset_attestors` message at any time to change it, and validation always checks against the **latest** attestor list rather than the list that was in force when the funds were received. This mirrors the reported RocketPool pattern: a mutable, externally/administratively-controlled parameter (attestor set / deposit delay) that funds are silently subject to can change and retroactively block spending of funds users already hold, freezing them with no recourse.

### Finding Description
When an asset has `spender_attested: true`, `storage.readAsset` -> `addAttestorsIfNecessary` always fetches the **most recent stable** `asset_attestors` unit for the asset and uses only that list (`objAsset.arrAttestorAddresses`) going forward: [1](#0-0) 

Attestor list updates can be posted at any time by the asset definer alone via `validateAttestorListUpdate`, which only checks that the author is the asset's definer and that the list is well formed — there is no restriction preventing removal of previously-listed attestors or replacement with an entirely new attestor set: [2](#0-1) 

During payment validation, both the issuer/output owner and every input owner are checked against the *current* attestor-derived attested-address set, not the set that applied when the coins were received: [3](#0-2) [4](#0-3) [5](#0-4) 

`storage.filterAttestedAddresses` only counts an address as attested if some attestor in the **current** `objAsset.arrAttestorAddresses` has attested it: [6](#0-5) 

Consequently, once the definer publishes a new attestor list, any address that holds a balance of the asset but has not been (re-)attested by one of the *new* attestors immediately loses the ability to spend that balance — even though the funds were legitimately acquired while the address was fully compliant/attested under the previous list. This is structurally identical to the RocketPool `rETH` deposit-delay issue: an externally mutable parameter that funds depend on for spendability can be changed by a party other than the fund holder, unilaterally converting previously-spendable funds into frozen funds.

### Impact Explanation
Any holder of a `spender_attested` asset — including an Autonomous Agent that received the asset as part of its balance (e.g., a DEX, escrow, or vault AA) — can have that balance permanently frozen the moment the asset definer rotates or narrows the attestor list, whether deliberately (issuer misbehavior / compliance change) or accidentally (e.g., migrating to a new attestor service before existing holders are re-attested). Because the check is against the live attestor list rather than the list valid at receipt time, there is no way for an already-attested, honest holder to protect funds already received: the freeze is retroactive and immediate upon the next stable `asset_attestors` unit. For an AA holding such an asset, this results in AA fund freezing with no on-chain recovery path (the AA cannot re-attest itself), matching the "AA fund loss or freezing" impact bar.

### Likelihood Explanation
The precondition is simply that an asset is defined with `spender_attested: true` (a supported, documented asset feature) and that the definer posts a single self-authored `asset_attestors` message — an ordinary, always-available action requiring no special network position, cosigning, or malicious node/peer behavior. Any protocol or DeFi construct built on ocore that accepts a `spender_attested` asset as payment (bridges, AA-based exchanges, escrow) is exposed to this the moment the issuer changes its attestor set, so likelihood is directly tied to adoption of `spender_attested` assets in economically significant AAs.

### Recommendation
Bind spendability checks to the attestor list (or explicit attestation) that was valid at the time the specific output was created, rather than always resolving against the definer's latest attestor list; alternatively, require attestation validity to be evaluated using a snapshot recorded at receipt time, or grandfather previously-attested addresses when the attestor list changes so that existing balances remain spendable even after a rotation.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and attestor `X`.
2. Attestor `X` attests address `H`; `H` receives a payment in asset `A` and now holds a spendable balance.
3. Definer posts an `asset_attestors` message for asset `A` listing only attestor `Y` (dropping `X`).
4. `H` attempts to spend its balance of asset `A`. `storage.readAsset` resolves `objAsset.arrAttestorAddresses = [Y]`; `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` finds no attestation of `H` by `Y`, so `objAsset.arrAttestedAddresses` excludes `H`.
5. `validatePaymentInputsAndOutputs` rejects the transfer with "owner address is not attested" per [5](#0-4) , permanently freezing `H`'s (or an AA's) previously legitimate balance until `Y` independently attests `H`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
