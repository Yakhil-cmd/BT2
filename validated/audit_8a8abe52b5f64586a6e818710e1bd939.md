Based on my analysis of the multisig transaction admission path, I found a concrete analog to the report's root cause ("code trusted a stale/mismatched approval binding instead of the actual value at execution time").

### Title
Feature-gated skip of on-chain payload verification lets an executor run a different transaction than the one owners approved - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`validate_multisig_transaction`, invoked by the VM prologue for every multisig-account transaction, is supposed to guarantee that the `payload` an executing owner actually submits matches what was approved by the required quorum of owners. When the transaction was created via `create_transaction` (full payload stored on-chain, `payload_hash` is `None`), the check that the submitted `payload` equals the `stored_payload` is only performed **if the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on**. If that flag is disabled (its default/rollout state), an owner who has quorum approval to execute *some* transaction can substitute an arbitrary different payload at execution time and it will still pass admission.

### Finding Description [1](#0-0) 

The function performs two payload-integrity checks:
1. If `transaction.payload_hash.is_some()` — i.e., the transaction was created with only a hash reference — it always asserts `sha3_256(payload) == payload_hash`. This path is safe.
2. If `transaction.payload.is_some()` (the full payload was stored on-chain at creation, which is the common/default `create_transaction` flow), the equality check `payload == stored_payload` is **only executed when `features::abort_if_multisig_payload_mismatch_enabled()` returns true**.

This means the binding between "what owners voted to approve" (`transaction.payload`, set once at `create_transaction` time and voted on by owners via `approve_transaction`/`reject_transaction`) and "what actually gets executed" (`payload`, passed by the VM from the transaction currently being submitted for execution) is only enforced conditionally on a feature flag, not unconditionally. This directly matches the report's root cause pattern: the protocol assumes a value fixed at approval/deposit time will still be the value used at execution time, but the code path that would catch a mismatch is optional/disableable rather than an invariant.

Owners approve a `MultisigTransaction` by voting on its `sequence_number`/hash-of-intent, believing the specific `payload` recorded on-chain is what will run. If the mismatch check is off, any owner with sufficient authorization to execute the pending sequence number can pass a **different serialized payload** through the entry point (`execute_transaction`-style Move entry that plumbs into `validate_multisig_transaction` as `payload: vector<u8>`), and the VM will proceed to execute that owner-supplied payload rather than the one that was actually approved, since the mismatch is never asserted.

### Impact Explanation
This breaks the multisig approval-set invariant that is the entire security guarantee of `multisig_account.move`: quorum approval of transaction A should never let an executor run transaction B. If the flag is off, an owner (not even necessarily malicious in intent, but capable of exploiting this) can:
- Get owners to approve a benign-looking transaction (e.g., "transfer 1 APT to X").
- At execution time, submit `execute_transaction` with a different payload (e.g., "transfer all funds to attacker", or "rotate owners", or "remove another owner") for the same approved `sequence_number`.
- The VM prologue accepts it because the payload-match assertion is skipped when the feature is disabled, and execution proceeds under the multisig account's authority.

This is unauthorized transaction execution under the multisig account's signer, i.e., exactly the "wrong approval set" / "pre-validation mismatch causing execution of an unapproved transaction" impact category. Given multisig accounts often custody pooled treasury/vault funds, the impact is direct theft or arbitrary state manipulation with only the executor's own key, bypassing the owner-quorum protection entirely.

### Likelihood Explanation
This depends entirely on the runtime state of the `abort_if_multisig_payload_mismatch_enabled` feature flag, which I could not fully confirm to be permanently and universally enabled in production for this checked-out version — it is gated behind `features::abort_if_multisig_payload_mismatch_enabled()`, implying it is (or was) a rollout flag rather than an always-on invariant. If it is disabled on any live network/testnet, or can regress (e.g., via network downgrade, a bug in flag propagation, or a fork/instance that hasn't enabled it), full exploitation is straightforward and requires no other precondition beyond being an owner who can trigger `execute_transaction`-style calls once quorum has already approved *some* transaction at that sequence number. I was not able to independently verify from the available code/index whether this flag is unconditionally forced to `true` at genesis or in all current mainnet configurations — this should be confirmed before treating the finding as immediately exploitable on production. If the flag is indeed always on for the target deployment, the practical severity of this specific candidate is reduced to defense-in-depth for the `payload_hash` path only.

### Recommendation
Make the payload-match assertion for on-chain-stored payloads unconditional (remove the feature-flag gate), matching the same strong invariant already applied to the `payload_hash` branch:
```move
if (transaction.payload.is_some()) {
    let stored_payload = transaction.payload.borrow();
    assert!(
        payload.is_empty() || payload == *stored_payload,
        error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
    );
};
```
i.e., only allow an empty `payload` (meaning "use the stored one") to bypass the check, never a non-matching non-empty payload — and never gate this behind a feature flag that can be off.

### Proof of Concept
Conceptual PoC (Move-level), assuming `abort_if_multisig_payload_mismatch_enabled` is disabled:
1. Owners of a k-of-n multisig account call `create_transaction(owner, multisig_account, payload_A)` where `payload_A` transfers a small amount to a benign address; `payload_A` gets stored fully on-chain (`transaction.payload = Some(payload_A)`, `transaction.payload_hash = None`).
2. Sufficient owners call `approve_transaction` to reach quorum for this `sequence_number`.
3. A malicious/self-serving executing owner submits a real Aptos transaction of type `TransactionPayload::Multisig(Multisig { multisig_address, transaction_payload: Some(payload_B) })` where `payload_B` drains the vault to the attacker's address, for the same pending `sequence_number`.
4. VM prologue calls `validate_multisig_transaction(owner, multisig_account, payload_B_bytes)`.
5. `can_execute`/`can_be_executed` and quorum checks pass (quorum was reached for the *sequence number*, not tied to payload content by this check).
6. Since `transaction.payload_hash` is `None`, the first check is skipped.
7. Since `features::abort_if_multisig_payload_mismatch_enabled()` is false, the second check (`payload == stored_payload`) is skipped entirely.
8. `payload_B` executes as the multisig account, despite only `payload_A` having been approved by owners.

I was not able to fully trace, within the available tool budget, the exact Rust-side VM code path that maps `TransactionPayload::Multisig.transaction_payload` into the `payload: vector<u8>` argument passed to `validate_multisig_transaction` (relevant code is in `aptos-move/aptos-vm/src/aptos_vm.rs`, which I could not fully pull), nor did I confirm the current on-chain/genesis default value of `abort_if_multisig_payload_mismatch_enabled`. These two points should be verified with a live Devin session/full-repo access before treating this as a confirmed, immediately-exploitable finding, since if the flag is hard-enabled at genesis for all target networks the risk becomes a defense-in-depth gap rather than a currently exploitable bug.
