### Title
Uncharged trie lookup in `has_yield_id_mapping` allows disproportionate CPU cost for repeated `yield_create` duplicate-id calls - (File: `runtime/runtime/src/ext.rs`, `core/store/src/utils/mod.rs`)

### Summary
`RuntimeExt::create_promise_yield_receipt_with_id` calls `has_yield_id_mapping` to check for a duplicate `YieldId` before creating a promise-yield receipt [1](#0-0) . Unlike every other trie access in the same file (`storage_get`, `storage_set`, `storage_remove`, `storage_has_key`), which explicitly route through `AccessOptions::contract_runtime(&self.trie_access_tracker)` and manually commit TTN (touch-trie-node) deltas to the `StorageAccessTracker` for gas/compute charging [2](#0-1) , the `has_yield_id_mapping` helper calls `trie.contains_key(..., AccessOptions::DEFAULT)` with no accounting tracker wired in at all [3](#0-2) .

### Finding Description
`create_promise_yield_receipt_with_id` is reached from a contract calling the `yield_create`-style host function exposed through `near_vm_runner::logic::External`. Every call performs:
1. `has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)` — a full trie lookup keyed on `TrieKey::YieldIdToDataId`.
2. If found, returns `Ok(None)` immediately without creating a receipt, without calling `set_yield_id_mapping`, and — critically — without the lookup's trie-node touch cost (`db_reads`/`mem_reads`, translated into `touching_trie_node` / `read_cached_trie_node` gas) being registered against the caller.

Contrast this with `storage_has_key` in the same file, which performs conceptually the same "does this key exist" trie check but explicitly threads the operation through `AccessOptions::contract_runtime(&self.trie_access_tracker)`, snapshots `get_counts()` before and calls `commit_counts_since(..., access_tracker)` after, feeding the delta into `access_tracker.trie_node_touched(...)` / `cached_trie_node_access(...)` [2](#0-1) . `has_yield_id_mapping` performs none of this bookkeeping — it uses `AccessOptions::DEFAULT`, which is the "generic" trie access mode used across the store utilities for internal bookkeeping reads (e.g. `has_received_data`, `has_promise_yield_receipt`, `has_promise_yield_status`) rather than the contract-metered path [4](#0-3) .

Because the actual gas charge for the `yield_create` host call is a fixed VM-logic-level cost applied in `runtime/near-vm-runner/src/logic/logic.rs` (a per-call base cost, independent of whether the trie lookup hits disk or memory), an attacker who repeatedly submits the same (or a colliding) `user_yield_id` inside one function call pays only that fixed per-call gas price while the runtime still performs the full trie descent for `contains_key` each time — and that descent's actual I/O cost is not reflected back into the metering counters the way a normal `storage_has_key` call's cost would be.

### Impact Explanation
This falls under gas/compute metering bypass: an attacker can cause the validator/chunk-producer to perform real trie I/O (potentially disk reads for cold data) that is not counted by the `AccountingState`/`StorageAccessTracker` mechanism the same way equivalent `storage_has_key` calls are. Repeated at scale within a receipt's gas budget, this results in CPU/I/O work that does not correspond 1:1 with metered `touching_trie_node`/`read_cached_trie_node` costs for this specific lookup, which is the mechanism the rest of `ext.rs` relies on for "charge before compute." However, the actual bytes read here are small (a `CryptoHash` sized value) and the number of distinct trie keys involved is bounded by receipt-level input size and yield_id space, so the amplification factor is the ratio between an uncharged `contains_key` and the flat per-call VM cost, not an unbounded multiplier.

### Likelihood Explanation
Reaching this path only requires an ordinary account deploying a contract that calls the yield-create host function repeatedly with the same/colliding `user_yield_id`, which is trivial and fully within an unprivileged attacker's capability (no special permissions, no reliance on validator/node-operator behavior). Determinism of `YieldId` derivation is not verified here since its generation isn't shown in the reviewed files, but reusing an identical literal id (e.g., `0`) across calls within one function call already triggers the duplicate path per the code comment "TrieUpdate also reflects writes from earlier calls within the same function call" [5](#0-4) .

### Recommendation
Route `has_yield_id_mapping` (and symmetrically `get_data_id_for_yield_id`/`get_yield_id_for_data_id` used in the resume path) through `AccessOptions::contract_runtime(&self.trie_access_tracker)` in `RuntimeExt`, mirroring the `storage_get`/`storage_has_key` pattern, so that TTN deltas are committed to the `StorageAccessTracker` and charged as `touching_trie_node`/`read_cached_trie_node` gas before the duplicate check short-circuits. Alternatively, charge an explicit fixed "yield id lookup" ext-cost inside `create_promise_yield_receipt_with_id` prior to invoking `has_yield_id_mapping`, sized to cover worst-case trie descent cost.

### Proof of Concept
Integration test plan (in `runtime/runtime/src/ext.rs` or a runtime-level gas-accounting test):
1. Set up a `TrieUpdate` with a large number of pre-existing `YieldIdToDataId` entries at varying trie depths to force non-trivial descent.
2. Call `RuntimeExt::create_promise_yield_receipt_with_id` N times with the same duplicate `user_yield_id`, recording via a test `StorageAccessTracker` implementation how many `trie_node_touched`/`cached_trie_node_access` calls are registered — expect it to remain at `0` for all N calls, contradicting the invariant that every trie touch must be charged.
3. Compare against N calls to `storage_has_key` on an equivalent key set and assert those correctly report `db_reads/mem_reads > 0` proportional to actual trie descents.
4. Assert (bug reproduction): total gas charged for the `has_yield_id_mapping` path does not scale with the number of trie nodes visited, while wall-clock/db read count does — demonstrating the metering/charging gap.

    fn storage_has_key(
        &mut self,
        access_tracker: &mut dyn StorageAccessTracker,
        key: &[u8],
    ) -> ExtResult<bool> {
        let start_ttn = self.trie_access_tracker.state.get_counts();
        let storage_key = self.create_storage_key(key);
        let mode = match self.storage_access_mode {
            StorageGetMode::FlatStorage => KeyLookupMode::MemOrFlatOrTrie,
            StorageGetMode::Trie => KeyLookupMode::MemOrTrie,
        };
        let result = self
            .trie_update
            .get_ref(&storage_key, mode, AccessOptions::contract_runtime(&self.trie_access_tracker))
            .map(|x| x.is_some())
            .map_err(wrap_storage_error);
        let _delta =
            self.trie_access_tracker.state.commit_counts_since(start_ttn, access_tracker)?;
        #[cfg(feature = "io_trace")]
        tracing::trace!(
            target: "io_tracer",
            storage_op = "exists",
            key = base64(&key),
            tn_mem_reads = _delta.mem_reads,
            tn_db_reads = _delta.db_reads,
        );
        Ok(result?)
    }
