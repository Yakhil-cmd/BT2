### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from one repository mutate CI state of a commit belonging to a different stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by bare SHA (`Commit.where(sha: params.sha)`), unlike sibling handlers (`push_handler.rb`, `check_suite_handler.rb`, the `pull_request/*` handlers) which resolve `stacks` from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`Repository.from_github_repo_name`. Because commit `sha` is not globally unique to one repository (forks, shared history, or any repo that happens to contain an identical commit will produce matching `Commit` rows in different stacks), a validly-signed status webhook from repository A can flip CI status for a `Commit` record belonging to stack/repository B, triggering `Stack`'s continuous-delivery/merge logic (`schedule_continuous_delivery`, `stack.schedule_merges`) which executes deploys under the stack's configured `bot_login` (`Shipit.user`) identity.

### Finding Description
The broken binding: the invariant that should hold is `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` mutated by a status webhook. This is enforced by other handlers via `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb`, `stacks` method, lines 32-38) which scopes to `Repository.from_github_repo_name(repository_name)&.stacks`. `StatusHandler#process` violates this: it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb`, lines 20-24) with no reference to `repository_name`/`stacks` at all.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb`, lines 24-49) only verifies that the signature matches the GitHub App/organization named in `payload.dig('repository','owner','login')` — it proves the webhook genuinely came from *some* repository under that organization, not that the `sha` inside the payload belongs only to that repository. Since `Commit` rows are looked up globally by `sha` (a 40-hex string, not namespaced per repository) in `StatusHandler`, any repository that can send a legitimately signed status webhook (e.g., an attacker's own repo/fork under an org with the Shipit GitHub App installed, or any org whose webhook secret the attacker can trigger through) can affect any other stack's `Commit` records that happen to share that SHA — most plausibly the victim's stack tracking a fork/upstream sharing commit history with the attacker's repository.

`Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb`, lines 366-386) recomputes `status`, and if `previous_status.simple_state != new_status.simple_state`, calls `stack.schedule_merges if new_status.pending? || new_status.success?`, and `Commit#schedule_continuous_delivery` (lines 281-287) enqueues `ContinuousDeliveryJob` when `deployable?` and `stack.continuous_deployment?`. Deploys triggered this way run using the stack's configured deploy actor (`bot_login`/`Shipit.user`), so an attacker can force a required `ci/test` status to `success` on the victim's tracked commit (if the SHA collision exists) and trigger an unauthorized deploy, or force it to `error`/`failure` to block a legitimate deploy — a denial/ship-or-block impact regardless of the victim repository's own CI state.

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `force_github_authentication`, `User#authorized?`) close this gap because they operate at the webhook-authentication layer (which org/repo sent this payload) rather than at the data-scoping layer (which stack's commit rows may be mutated for a given `sha`). Only `StatusHandler` skips the `stacks`/`repository_name` scoping used elsewhere in the same handler hierarchy.

### Impact Explanation
An attacker with push/webhook control over any repository that can produce a validly signed `status` webhook (their own repo, provided its owning org's GitHub App/webhook secret is what's checked) can write `Shipit::Status` rows for `Commit` records in a completely different repository's stack whenever the SHA values coincide. This can flip `ci/test` (or any required status context) to `success`, causing `Stack#schedule_merges`/`ContinuousDeliveryJob` to run and deploy attacker-influenced code under the stack's `bot_login` identity — an unauthorized deploy of a payload for one repository mutating another repository's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit ... or an unauthorized deploy"). It can equally be used to force a `failure`/`error` state and block deploys of a victim's legitimate release (denial via CI state manipulation).

### Likelihood Explanation
Preconditions: the attacker needs to be able to produce a status webhook signed for *some* organization known to Shipit (e.g., they push code/CI to their own repository within an org that has the Shipit GitHub App installed, or exploit a shared commit history/fork situation so the same `sha` exists in the victim's tracked stack). This is a realistic scenario in public/OSS setups where forks or PR branches share commit SHAs with the upstream repo tracked by Shipit, and any contributor with CI on their fork can emit a status for that SHA. No Shipit session, API token, or GitHub secret for the *victim* org is required — only the ability to get a genuinely signed webhook fired for a commit SHA that also exists in the victim stack. The `bot_login`/`Shipit.user` amplification (deploys run as the configured bot) makes the impact severe once the SHA collision is achieved.

### Recommendation
Scope `StatusHandler#process` (and any other handler using `Commit.where(sha:)`/similar bare lookups) to the requesting repository, mirroring the pattern used by `push_handler.rb`/`check_suite_handler.rb`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and restrict the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or join through `stack.repository`) before calling `create_status_from_github!`.

### Proof of Concept

1. Create `repo_a` (`Shipit::Repository`, e.g. `owner/repo-a`) and `stack_a` with `bot_login` set to a configured `Shipit.user`, and required status `ci/test`.
2. Create `repo_b` (`owner/repo-b`) and `stack_b`, unrelated to `stack_a`.
3. Create a `Commit` under `stack_a` with `sha = "aaaa...aaaa"` (the "victim" commit), currently pending/blocked.
4. Simulate an attacker-controlled webhook payload: `{ "sha" => "aaaa...aaaa", "state" => "success", "context" => "ci/test", "repository" => { "full_name" => "owner/repo-b", "owner" => { "login" => "owner" } } }`, signed correctly for `repository_owner = "owner"` (bypassing only the org-level signature, not any repo_a-specific check).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert equality-violation: before, `commit_a.reload.status.state != "success"`; after processing, `commit_a.reload.status.state == "success"` even though the payload's `repository.full_name` (`owner/repo-b`) does not equal `stack_a`'s repository full name — proving the invariant `commit.stack.repository.full_name == payload['repository']['full_name']` is violated.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
