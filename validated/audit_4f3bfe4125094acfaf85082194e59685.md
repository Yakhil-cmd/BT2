### Title
Webhook signature verification fails open for organizations without a configured `webhook_secret`, allowing unauthenticated forgery of GitHub events (including `membership`) - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb])

### Summary
The C4 report's root cause is a "trust the wrong field" bug: code that acts on data which is not actually covered by verification. The equivalent binding break in this engine is in `WebhooksController#verify_signature` / `GithubApp#verify_webhook_signature`: when an organization's `webhook_secret` is blank (an explicitly documented, supported configuration state), signature verification is skipped entirely, so **any** unauthenticated request claiming to be a GitHub webhook for that organization is accepted and dispatched to handlers, including the `membership` handler that mutates `Team`/`Membership`/`User` records.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config for the organization named in the *unverified* payload (`repository_owner`), then asks that app to verify the signature: [1](#0-0) 

`GithubApp#verify_webhook_signature` implements verification as: [2](#0-1) 

Note `return true unless webhook_secret`. The `webhook_secret` is a documented, optional per-organization setting — the setup docs and example configs explicitly show it as commented/`nil`: [3](#0-2) [4](#0-3) 

So the equality the app relies on — "request accepted" == "request cryptographically verified as originating from GitHub for this org" — does **not** hold whenever an operator configures an org without a `webhook_secret` (a first-class, documented state, not a misconfiguration outside the engine's design). In that state, `repository_owner` (attacker-supplied, from the JSON body) selects the app config, verification trivially returns `true`, and the raw JSON body is dispatched unauthenticated to `Shipit::Webhooks.for_event(event)` handlers: [5](#0-4) 

One of the dispatched event types is `membership`, whose handler creates teams/users and adds/removes `Membership` records purely from payload content, as shown by the controller's own test suite: [6](#0-5) 

`Shipit.github_teams` membership is the authorization gate used to grant access to the whole application: [7](#0-6) [8](#0-7) 

### Impact Explanation
An unauthenticated, unprivileged network attacker who knows (or guesses) the organization login of any Shipit-configured org that has no `webhook_secret` set can POST a forged `membership` webhook to the public `/github/webhooks` endpoint, adding an arbitrary GitHub login to a `Team` that is included in `Shipit.github_teams`. That directly escalates into `Shipit.github_teams` authorization — a listed High-severity impact — and, depending on team wiring, can chain to deploy/merge/rollback privileges for stacks gated by that team, i.e., an unauthorized deploy/merge path (Critical-adjacent impact).

### Likelihood Explanation
This does not require any GitHub App private key, `webhook_secret`, `api_clients_secret`, session, or repository write access — it only requires that the target organization's Shipit config has no webhook secret set, which is an explicitly supported and documented state (not a deviation from documented deployment). Any operator following the example configs with `webhook_secret:` left blank is exposed. The attack itself is a single unauthenticated HTTP POST with attacker-chosen JSON.

### Recommendation
Do not fail open when `webhook_secret` is blank. Either (a) require `webhook_secret` to be present for any configured GitHub App/org and refuse to serve webhooks otherwise, or (b) bind the signature verification to a value that cannot be forged even when unset (e.g., reject all webhooks for orgs without a secret configured, rather than accepting them unconditionally).

### Proof of Concept
1. Configure Shipit for org `Acme` with `webhook_secret` left blank, as shown in the documented example config.
2. As an outside attacker (no credentials), POST to `/github/webhooks` with header `X-Github-Event: membership` and a JSON body:
```json
{
  "action": "added",
  "team": { "id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com" },
  "member": { "login": "attacker-login" },
  "organization": { "login": "Acme" }
}
```
3. `verify_signature` resolves `repository_owner` = `"Acme"` from the body, calls `Shipit.github(organization: "Acme").verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank.
4. The `membership` handler creates the team (if missing) and a `Membership` linking `attacker-login`'s `User` record to that team — matching the behavior asserted in `test/controllers/webhooks_controller_test.rb` lines 129-165.
5. If `"Ouiche Cooks"`/the targeted team is listed in `Shipit.github_teams`, the attacker's account (once it logs in via OAuth) is now `authorized?` per `app/models/shipit/user.rb` lines 80-82, granting it full application access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
