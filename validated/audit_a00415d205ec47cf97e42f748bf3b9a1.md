### Title
Missing owner authentication in `force_socialize_bad_debt` lets any unprivileged caller write down supplier shares on any insolvent account regardless of remaining collateral - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
The Helidon CVE class is "missing authentication on a state-modifying operation": an unauthenticated remote party reaching a privileged write. XOXNO Lending has a direct analog in `process_force_socialize_bad_debt`, which performs the uncapped bad-debt socialization path (`BadDebtGate::InsolventOnly`) that the code comments explicitly mark as **owner-only**, yet the entrypoint performs neither `require_auth` on a caller nor an ownership check on the target account. Any unprivileged address can force the full supply-index write-down — the operation intended to be gated to the account owner — on any account where `total_debt > total_collateral`, skipping the `DustCapped` cap that constrains the genuinely permissionless path.

### Finding Description
`process_clean_bad_debt` correctly authenticates its caller and applies the `DustCapped` gate: socialization is only allowed when the account is insolvent **and** its remaining collateral is at or below the dust threshold (line 196-200, 229-235).

`process_force_socialize_bad_debt` is the stronger path: `BadDebtGate::InsolventOnly` admits any account with `total_debt > total_collateral` (line 233), with no cap on how much collateral the account still holds. Its own doc comment states this gate is "Owner-only: insolvent alone, with no cap on the collateral left behind" (line 207-208). But the function body only calls `validation::require_not_flash_loaning(env)` (line 246-248) — there is no `caller` parameter at all, no `require_auth`, and no `account.owner == caller` or NFT-owner check. The "Owner-only" precondition documented in the code is simply not enforced.

The result: the most damaging socialization mode — one that seizes all remaining collateral of any size toward the debt and writes the entire shortfall into the supply index (haircutting every supplier in that spoke market via `bad_debt::execute_bad_debt_cleanup` / the supply-index write-down, without minting shares) — is reachable permissionlessly by any address, at any time, outside a flash loan.

### Impact Explanation
The uncapped path is deliberately restricted to the owner because it destroys the account's remaining collateral position and immediately crystallizes a loss for all suppliers of the borrowed market (supply-index write-down). Letting an arbitrary third party trigger it removes the owner's ability to choose liquidation timing/order: a forced cleanup executes before normal liquidations can run, so the collateral is consumed without paying a liquidation bonus and the residual shortfall hits suppliers in one step. For accounts that are only marginally insolvent (debt barely above collateral), premature forced socialization locks in a write-down that orderly liquidation flows — or a price recovery / repayment by the owner — might have avoided or reduced. This is a permanent loss of user funds (supplier principal and unclaimed accrued yield) caused by an unauthorized privileged state transition, matching the CVE class of unauthenticated data manipulation.

### Likelihood Explanation
Reachability is trivial: the entrypoint takes only `env` and `account_id`, so any unprivileged address can call `controller.force_socialize_bad_debt(account_id)` the instant any account's cached-price health dips below insolvency — a routine condition in volatile markets, and one an attacker can also manufacture transiently is not needed since the condition persists. No capital, no authorization, and no flash loan is required; the only gate (`require_not_flash_loaning`) merely excludes callback contexts. The trigger condition (`total_debt > total_collateral`) occurs organically whenever liquidation is slower than price movement. Likelihood is bounded mainly by how often accounts sit insolvent-but-not-yet-cleaned, and the impact per invocation is a genuine loss rather than an unbounded drain.

### Recommendation
Add the missing authorization to the uncapped path, consistent with its documented "Owner-only" contract: accept a `caller: Address`, call `caller.require_auth()`, and verify the caller is the account owner (or an authorized delegate) before invoking `socialize_bad_debt(env, account_id, BadDebtGate::InsolventOnly)` — e.g., resolve the account's NFT owner via `storage::try_account_owner` and compare, or reuse `account::require_owner_or_delegate`. Alternatively, if the uncapped path is meant to be permissionless, delete it and rely solely on `DustCapped` cleanup plus normal liquidation; the current state silently exposes a gate the design comments say is restricted.

// Attacker: any address with no position and no authorization relationship
// to `victim_account_id`.
// Precondition: victim account has total_debt > total_collateral
// (e.g., after a price move, before any liquidator acts).

let victim_account_id: u64 = /* insolvent account with large residual collateral */;

// No auth is requested or checked; caller is not even a parameter.
controller_client.force_socialize_bad_debt(&victim_account_id);

// Effect:
//  - socialize_bad_debt admits via BadDebtGate::InsolventOnly (line 233),
//    bypassing the dust cap in is_socializable_bad_debt.
//  - bad_debt::execute_bad_debt_cleanup seizes all remaining collateral and
//    writes the full shortfall into the supply index, permanently
//    haircutting every supplier — a transition the code marks "Owner-only"
//    (line 207) but never actually restricts.
// Contrast: the permissionless sibling requires caller.require_auth() and the
// DustCapped gate (lines 196-200).
