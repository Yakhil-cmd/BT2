Based on my investigation, I found a genuine local candidate: `MultiKey` (in `types/src/transaction/authenticator.rs`) does not appear to reject duplicate public keys within the same multi-key set, and this is actually demonstrated (not just theorized) in the crate's own test suite.

### Title
`MultiKey`/`MultiKeyAuthenticator` accepts duplicate public keys, allowing a single private key to satisfy a multi-signature threshold alone - (File: types/src/transaction/authenticator.rs)

### Summary
`MultiKeyAuthenticator::new` only checks that a signature index is within range and not duplicated in the bitmap [1](#0-0) , but never checks whether the underlying `public_keys` vector (the `MultiKey`) itself contains duplicate keys. If the same public key is listed at two different indices in a `MultiKey`, an attacker holding just that one private key can produce two distinct-index signatures (same signature reused for both indices, or two signatures from the same key) and satisfy a `signatures_required` threshold of 2 while controlling only one private key.

### Finding Description
The verification path `MultiKeyAuthenticator::to_single_key_authenticators` → `verify` checks: (1) that the number of signatures meets `signatures_required`, and (2) that each signature verifies against its corresponding index's public key, via `self.public_keys.public_keys[idx]` [2](#0-1) . Nothing in this path, nor in `MultiKeyAuthenticator::new`, asserts that the `public_keys` in the `MultiKey` are pairwise distinct.

This is directly exercised by the crate's own unit test `verify_multi_key_auth`: a `MultiKey` is constructed with keys `[sender0, sender1, sender1]` (index 1 and index 2 are the *same* key) and `signatures_required = 2` [3](#0-2) . The test then builds `mk_auth_12` using `signature1` (from `sender1`) at both index 1 and index 2, and this two-signature multikey authenticator successfully verifies against a `signatures_required = 2` policy [4](#0-3)  — despite only one private key (`sender1`) ever having produced a signature.

Because `AuthenticationKey::multi_key(multi_key)` derives the on-chain account address directly from this `MultiKey` bytes [5](#0-4) , any account owner is free to register a `MultiKey` account with duplicate entries. Whoever controls that one duplicated key can then admit and sign transactions from that account as if 2-of-N independent approvals were present, when in fact only 1 distinct key participated.

### Impact Explanation
This breaks the core signer-set admission invariant for `MultiKey`-authenticated accounts: a transaction that should require N independent approving keys to be admitted/executed can instead be authenticated by a single controlling key holding a duplicated public-key slot. For any application or wallet that treats `signatures_required` as a guarantee of independent-key quorum (e.g., social recovery, "2 devices must both sign", "N-of-M guardians"), this allows a single compromised/malicious key to unilaterally authorize transactions that should have required multiple independent approvals — i.e., unauthorized transaction admission/execution under a false signer-set guarantee. This is a boundary condition at authenticator-parsing / public-key binding, matching the admission pivot around "Authenticator ... multisig ... approval validation accepting the wrong ... approval set."

### Likelihood Explanation
High likelihood of exploitability once a victim (or an attacker controlling account creation) sets up a `MultiKey` account with a duplicated key entry — the account address itself is derived from this `MultiKey`, so nothing prevents its creation, and the verification logic in `authenticator.rs` never rejects it. The scenario requires the account's `MultiKey` to contain a duplicate, which could arise either from a malicious account creator (self-attack, low value) or, more importantly, from any tooling/dApp that builds `MultiKey` accounts programmatically without itself deduplicating keys — the framework offers no defense-in-depth check.

### Recommendation
Add a uniqueness check for public keys in `MultiKey` construction (both in `types/src/transaction/authenticator.rs`'s `MultiKey` and its Move-side counterpart `aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move`), rejecting duplicate `AnyPublicKey` entries at `MultiKey::new`/construction time, analogous to how `MultiEd25519PublicKey` and `multisig_account.move`'s owner list already guard against duplicate entries.

### Proof of Concept
The existing test `verify_multi_key_auth` in `types/src/transaction/authenticator.rs` is itself the PoC: it constructs `MultiKey::new(vec![any_sender0_pub, any_sender1_pub, any_sender1_pub], 2)`, then builds `mk_auth_12` with `sender1`'s signature at indices 1 and 2, and asserts `signed_txn.verify_signature().unwrap()` succeeds [4](#0-3)  — proving a 2-of-3 threshold is satisfied using only one distinct private key (`sender1`), with `sender0`'s key never participating.

impl MultiKeyAuthenticator {
    pub fn new(public_keys: MultiKey, signatures: Vec<(u8, AnySignature)>) -> Result<Self> {
        ensure!(
            public_keys.len() < (u8::MAX as usize),
            "Too many public keys, {}, in MultiKeyAuthenticator.",
            public_keys.len(),
        );

        let mut signatures_bitmap = aptos_bitvec::BitVec::with_num_bits(public_keys.len() as u16);
        let mut any_signatures = vec![];

        for (idx, signature) in signatures {
            ensure!(
                (idx as usize) < public_keys.len(),
                "Signature index is out of public key range, {} < {}.",
                idx,
                public_keys.len(),
            );
            ensure!(
                !signatures_bitmap.is_set(idx as u16),
                "Duplicate signature index, {}.",
                idx
            );
            signatures_bitmap.set(idx as u16);
            any_signatures.push(signature);
        }

        Ok(MultiKeyAuthenticator {
            public_keys,
            signatures: any_signatures,
            signatures_bitmap,
        })
    }

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }
