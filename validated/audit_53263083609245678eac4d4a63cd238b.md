### Title
StatusHandler#process trusts global sha lookup without asserting repository_name binding, allowing cross-tenant status writes - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` iterates `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, without ever calling `Handler#stacks` (which scopes to `Repository.from_github_repo_name(repository_name)`) or otherwise checking that `repository_name(payload) == commit.stack.repository.full_name`. This is unlike sibling handlers (e.g. `CheckSuiteHandler`, all `PullRequest::*Handler`s) which resolve `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack-scoped data.

### Finding Description
Binding claimed broken, stated as equality: `repository_name(payload) == commit.stack.repository.full_name` for every `commit` in `Commit.where(sha: params.sha)`.

Code path: `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches to `Shipit::Webhooks.for_event('status')` → `StatusHandler.call(params)` → `Handler.call` → `new(payload).process` (`app/models/shipit/webhooks/handlers/handler.rb:15-24`) → `StatusHandler#process`: [1](#0-0) 

`Handler` defines a `stacks` helper that scopes by `repository_name`: [2](#0-1) 

`StatusHandler#process` never calls `stacks` or `repository_name`; it queries `Commit` globally by `sha` and then calls `commit.create_status_from_github!(params)`, which delegates through `add_status` to `statuses.replicate_from_github!(stack_id, github_status)` using whatever `stack_id` the matched `Commit` row happens to belong to: [3](#0-2) 

`verify_signature` in the controller only checks that the HMAC signature is valid for the GitHub App/org identified by `repository_owner` in the payload — it authenticates that "this payload really came from an app installed on org X," not that the specific `sha` referenced belongs to a repo owned by org X: [4](#0-3) 

Because git commit SHAs are content-addressed, an attacker who forks or mirrors a victim's public repository will possess commits with byte-identical SHAs to commits already recorded in the victim's `Stack`'s `Commit` table. The attacker's own GitHub App installation (on `attacker/own-repo`) can legitimately emit a signed `status` webhook with `sha: S`, `repository.full_name: 'attacker/own-repo'`, and an arbitrary `state`. `StatusHandler` will match `Commit` rows by `sha` alone across all tenants and write a `Status` against the victim's `Stack`, regardless of which repository actually authenticated the webhook.

No other guard closes this gap: `drop_unhandled_event`, `ExplicitParameters` schema validation, and `verify_signature` all operate at the org/signature level, not at the individual-commit/repository-ownership level, and `Commit.where(sha:)` has no `stack_id`/`repository_id` filter tying it to the authenticated payload.

### Impact Explanation
An attacker-controlled webhook (fully authenticated for `attacker/own-repo`) can create a `Shipit::Status` row on a `Commit` belonging to an arbitrary victim `Stack`, as long as a `Commit` with the same `sha` exists there — trivially achievable by forking/mirroring the victim's public repository, since shared git history produces identical SHAs across the fork and the origin. This lets an attacker inject fabricated `success`/`failure` CI statuses onto a victim's stack's commits, which (per `Commit#add_status`/`schedule_continuous_delivery`) can influence `deployable?` and trigger `ContinuousDeliveryJob`, potentially causing an unauthorized/incorrect deploy decision on the victim's stack. This is a cross-repository write into another tenant's data from a payload authenticated only for the attacker's own repository — matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Preconditions: victim's repo must be public (or otherwise forkable/mirrorable) so the attacker can obtain a `Commit` with an identical SHA; attacker needs their own repo with a GitHub App installation configured in Shipit (webhook secret known to them because it's their own installation) — no victim secrets, sessions, or team membership required. Attacker cost is low: fork the victim repo, register/point their own Shipit-configured repo's webhook, and POST a `status` event referencing the shared SHA. This is repeatable against any stack that has ingested commits also present in a public fork, and scales to any number of shared commits (initial commit, common ancestor commits, cherry-picked commits, etc., not just contrived empty-tree collisions).

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the authenticated repository, e.g. use `stacks.flat_map(&:commits)` or join through `stack: :repository` and filter `repository: { full_name: repository_name }`/`stack_id: stacks.pluck(:id)` before calling `create_status_from_github!`, mirroring the `repository.from_github_repo_name(...)` pattern already used in `CheckSuiteHandler` and the `PullRequest::*` handlers.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` with `repository` `owner: 'attacker', name: 'own-repo'` and `stack_b` with `repository` `owner: 'victim', name: 'real-repo'`.
2. Create `commit_b = stack_b.commits.create!(sha: 'S', ...)` (no commit with sha `S` under `stack_a`).
3. Sign a `status` webhook payload `{sha: 'S', state: 'success', repository: {full_name: 'attacker/own-repo', owner: {login: 'attacker'}}}` using the webhook secret configured for the `attacker` org/app (as the controller's `verify_signature` would accept).
4. POST to `/webhooks` with `X-Github-Event: status` and the valid signature header.
5. Assert before: `repository_name(payload) == 'attacker/own-repo'` and `commit_b.stack.repository.full_name == 'victim/real-repo'` — i.e. `'attacker/own-repo' != 'victim/real-repo'`.
6. Assert after: `commit_b.reload.statuses.count == 1` and the created `Status#stack_id == stack_b.id`, proving a status was written to `stack_b` (victim) from a webhook authenticated only for `attacker/own-repo`, with no live GitHub calls needed since the equality never held and no code path enforced it.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
