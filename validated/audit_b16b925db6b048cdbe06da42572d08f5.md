### Title
Headers-commission split rounding lets a unit poster mint extra bytes via `earned_headers_commission_recipients` - ([File: headers_commission.js])

### Summary
`calcHeadersCommissions()` splits a fixed headers-commission amount (`full_amount`, i.e. the constant `headers_commission` field paid by a parent unit) among multiple addresses listed in `earned_headers_commission_recipients` using `Math.round(full_amount * share / 100.0)` for each recipient independently, exactly the same rounding-up-per-share pattern flagged in the WadRayMath report. Because each recipient's share is rounded independently rather than the leftover being tracked/truncated, the sum of the rounded per-recipient amounts can exceed `full_amount`, creating extra spendable bytes that were never actually paid by the commission-paying unit.

### Finding Description
When a unit has more than one author, or the author explicitly sets `earned_headers_commission_recipients`, the unit's headers-commission "winnings" are split proportionally among the listed addresses: [1](#0-0) 

and, in the "not faster" verification branch that recomputes from the DB, the same rounding is applied per recipient before summation: [2](#0-1) 

The only validation performed on `earned_headers_commission_recipients` is that shares are positive integers, addresses are sorted, and they sum to exactly 100 — there is no requirement that the rounding be conservative or that leftover be accounted for: [3](#0-2) 

An unprivileged unit author fully controls this array for their own unit (it's part of the signed unit content, validated in `validateHeadersCommissionRecipients` and persisted in `writer.js`): [4](#0-3) 

Because `Math.round` rounds `.5` up (not truncation and not bankers' rounding), an attacker can choose N recipient addresses (all of which they control) with shares such as `100/N` (e.g., `25,25,25,25`) so that for a headers_commission value `full_amount` where `full_amount/N` lands exactly on `.5` or close to it, each recipient's `Math.round(full_amount*share/100)` rounds up, and the sum of all N rounded shares exceeds `full_amount`. E.g., with `full_amount=2` and 4 recipients each with `share=25`, each individual amount is `Math.round(2*0.25)=Math.round(0.5)=1`, giving a total distributed amount of `4`, double the actual `full_amount=2` that was ever deducted anywhere from any payer's balance.

The resulting inflated per-recipient amounts are written straight into `headers_commission_contributions` and then aggregated into `headers_commission_outputs`: [5](#0-4) [6](#0-5) 

`headers_commission_outputs` rows are directly spendable base-asset value (bytes) once later referenced as `headers_commission` type inputs and validated via `mc_outputs.calcEarnings`: [7](#0-6) 

There is no global invariant check enforced during consensus validation that the sum of `headers_commission_contributions`/`headers_commission_outputs` for a payer unit must equal that unit's declared `headers_commission` field — the aggregate stats function (`readAllUnspentOutputs`) is informational only and not part of consensus validation.

### Impact Explanation
This allows any single unit author to mint spendable bytes beyond what was actually paid as fees, i.e. base-asset supply inflation, by choosing a set of recipient addresses/shares in their own `earned_headers_commission_recipients` array that maximizes rounding-up drift relative to the true `headers_commission` amount won. Since these extra bytes end up as real, spendable `headers_commission_outputs`, this is a genuine (if bounded per unit) unauthorized creation of value, satisfying the "supply inflation" impact bar.

### Likelihood Explanation
Reachable purely by posting an ordinary unit with a crafted `earned_headers_commission_recipients` field — no privileged role, hub cooperation, or network timing is required; only that the unit ends up winning at least one headers-commission race (a routine, expected event for any unit with children). The magnitude per occurrence is small (bounded by roughly `N/2` bytes for `N` recipients), but it is repeatable indefinitely by the same attacker across many units, and is a systemic rounding defect rather than a one-off edge case.

### Recommendation
Replace independent per-recipient rounding with an amount-conserving distribution algorithm: compute floor-truncated shares for all but the last recipient, and assign the last recipient `full_amount - sum(previous truncated shares)` (or use a "largest remainder" method) so the sum of distributed amounts always equals `full_amount` exactly. Apply the same fix consistently between the RAM path and the SQL/verification path in `headers_commission.js`, and consider adding an assertion that the sum of distributed contributions for a payer unit equals its `headers_commission` field.

### Proof of Concept
1. Attacker controls addresses `A1..A4`.
2. Attacker posts a unit with 4 authors (or a single author, since address list needn't equal authors) and sets:
   `earned_headers_commission_recipients = [{address:A1,share:25},{address:A2,share:25},{address:A3,share:25},{address:A4,share:25}]` (sum = 100, passes `validateHeadersCommissionRecipients`).
3. Attacker crafts/positions this unit so that it wins a headers-commission race against a parent unit whose `headers_commission` (`full_amount`) is such that `full_amount * 25 / 100` lands on `.5` (e.g. `full_amount = 2`, or more generally any `full_amount ≡ 2 (mod 4)`).
4. `calcHeadersCommissions()` computes, for each of A1..A4: `Math.round(full_amount*0.25) = Math.round(0.5) = 1`, for a total of `4`, double the real `full_amount = 2`.
5. These 4 amounts are inserted into `headers_commission_contributions` and aggregated into `headers_commission_outputs`, becoming spendable bytes for A1..A4 that were never actually paid by any payer unit — net new base-asset supply of `2` bytes per exploited unit, repeatable at will.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
