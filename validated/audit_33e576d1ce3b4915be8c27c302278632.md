### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's webhook signature verification authenticates *which organization* a GitHub webhook payload came from, but the `status` event handler never checks that the commit it mutates actually belongs to that organization's repository. It looks up commits globally by `sha` alone, so a webhook correctly signed for organization A can be crafted to write a CI status onto a commit that lives in a stack belonging to a completely unrelated organization/repository B that is also configured in the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the organization to authenticate against directly from the payload body, then verifies the HMAC using that organization's own configured `webhook_secret`: [1](#0-0) [2](#0-1) 

Once the signature is verified, the controller dispatches the *entire, attacker-controlled* payload to the registered handler for the event with no further repository/organization binding: [3](#0-2) 

For the `status` event, `StatusHandler#process` resolves the target `Commit` purely by `sha`, with no scoping to the repository or organization whose signature was just verified: [4](#0-3) 

Contrast this with the base `Handler` class, which *does* provide repository-scoped lookup helpers (`repository_name`, `stacks`) used by other handlers such as `PushHandler`: [5](#0-4) [6](#0-5) 

`StatusHandler` bypasses this scoping entirely and calls `commit.create_status_from_github!(params)` for *every* `Commit` record in the database matching the given `sha`, regardless of which repository/stack that commit belongs to.

**Binding broken:** the organization authenticated by the webhook signature ≠ the repository/organization whose data (`Commit#statuses`) is actually mutated. This is exactly the analog class called out in the rules: "an organization that authenticated versus the repository that is written."

Because git commit SHA-1 hashes are content-addressed and not namespaced per-repository, an attacker who has ordinary (unprivileged, from Shipit's perspective) push/fork access to *any* GitHub repository belonging to *any* organization configured in this multi-tenant Shipit instance can:
1. Fork or clone a victim repository managed by a different team/org in the same Shipit deployment (or otherwise obtain a commit object that is byte-identical, hence hash-identical, to a commit already tracked by Shipit for that victim stack).
2. Push that identical commit object to their own attacker-controlled repository under an organization that Shipit is configured to trust (i.e., has a legitimate `webhook_secret`/GitHub App for).
3. Trigger (or synthesize, since a signature-valid request only requires the correct HMAC for their own org's secret, which GitHub will compute for them automatically when it delivers the webhook for their own repo) a `status` webhook event with that `sha`.

Shipit will verify the signature against the attacker's own organization's secret (succeeds, since it is a legitimate webhook from their own org), then `StatusHandler` will apply the attacker-supplied `state`, `description`, `target_url`, and `context` to the victim's `Commit` record, because the lookup is `Commit.where(sha: params.sha)` with no repository filter.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker with no privilege over the victim's repository or stack can forge a CI status (e.g., mark a commit `success`) on a commit belonging to a completely different, unrelated stack managed by the same Shipit instance. Shipit uses commit status/CI state to gate deploy eligibility (`deployable?`) and merge-queue eligibility elsewhere in the app, so a forged "green" status can be used to make an otherwise non-deployable/non-mergeable commit appear deployable, i.e., contribute to an unauthorized deploy or merge decision for a repository the attacker does not control. This matches the "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured with more than one trusted GitHub organization (a supported, documented configuration, since `Shipit.github(organization:)` explicitly handles multiple orgs and raises `GithubOrganizationUnknown` otherwise), and (b) the attacker to have ordinary push/webhook-delivery capability in at least one such trusted organization, and (c) the ability to reproduce a byte-identical commit object (trivial via fork/clone-and-repush of a public or accessible victim commit) so the SHA matches. All of this is achievable without any Shipit credentials, session, or elevated GitHub permissions on the victim repository — it only requires normal GitHub usage (forking/cloning) plus being a legitimate, low-trust member of any org already onboarded to the shared Shipit instance.

### Recommendation
Scope the `Commit` lookup in `StatusHandler` (and any other handler that trusts payload-embedded identifiers) to the repository that was actually authenticated for the webhook — i.e., filter `Commit` through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`/`stacks`, consistent with how `Handler#stacks` and `PushHandler` already scope lookups, rather than matching on `sha` alone across the entire database.

### Proof of Concept
1. Configure a Shipit instance with two trusted organizations, `org-a` and `org-b`, each with its own registered stack and `webhook_secret`.
2. As a member of `org-a` (unprivileged w.r.t. `org-b`), fork/clone a public repository whose commit is tracked by a stack under `org-b`, and push that identical commit object into a repository under `org-a`.
3. Trigger (via GitHub, or by directly POSTing to `/webhooks` with a payload correctly HMAC-signed using `org-a`'s `webhook_secret`) a `status` event where `sha` equals the shared commit hash and `repository.owner.login` = `org-a`, but `state`/`description`/`target_url` are attacker-chosen.
4. Observe that `WebhooksController#verify_signature` succeeds (valid signature for `org-a`), and `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) writes the forged status onto the `Commit` row that actually belongs to `org-b`'s stack, since the lookup `Commit.where(sha: params.sha)` is not scoped to `org-a`'s repository.
