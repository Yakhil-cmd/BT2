## Title
Cross-organization webhook forgery via `repository.owner.login` vs `repository.full_name` binding break - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and its HMAC secret) used to authenticate an incoming webhook based on `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), but every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) resolves the *target* repository/stack from a completely different field: `payload.dig('repository', 'full_name')`. Because `webhook_secret` is documented and coded as optional per organization (`lib/shipit/github_app.rb:76-77`: `return true unless webhook_secret`), any Shipit installation configured with multiple GitHub organizations (`docs/setup.md` "Using Multiple Github Applications") where at least one organization has no `webhook_secret` set lets an unauthenticated attacker forge a signature-free webhook whose `owner.login` matches the secret-less org (to pass `verify_signature`) while `repository.full_name` names a repository belonging to a different, fully-secured organization tracked by the same Shipit instance. The handler then acts on that victim repository's stacks with no further ownership check.

### Finding Description
`verify_signature` picks the trust anchor from the org field: [1](#0-0) [2](#0-1) 

Signature verification is a no-op whenever the resolved organization's `webhook_secret` is blank: [3](#0-2) 

Every handler, however, resolves which stacks/repositories to mutate using an unrelated payload field: [4](#0-3) 

For example the push handler triggers a GitHub sync against any stack matching `repository.full_name` + branch: [5](#0-4) 

The `check_suite` handler similarly acts on stacks resolved via `repository.full_name`: [6](#0-5) 

Multi-org deployments are an explicitly supported and documented configuration, with `webhook_secret` marked "(optional)": [7](#0-6) 

Sample secrets configs in the repo itself default `webhook_secret` to nil per org: [8](#0-7) 

**Binding broken:** `repository.owner.login` (the identity that authenticates the request, i.e. which org's — possibly unset — secret is used) `==` `repository.full_name`'s owner (the repository whose stacks/commits/pull-requests actually get mutated). The controller/handler pipeline never asserts these two are the same organization; it authenticates against one field and acts on a disjoint one.

### Impact Explanation
An attacker with no Shipit session, no API token, and no knowledge of any secret can send a crafted `push`, `check_suite`, or `pull_request` webhook to the public `/webhooks` endpoint. If any org configured on the instance has an unset `webhook_secret` (an officially supported, documented state), the attacker sets `repository.owner.login` to that org to sail through `verify_signature`, while setting `repository.full_name` to `victim-org/target-repo` — a repository belonging to a different, secured organization also hosted on the same Shipit instance. This lets the attacker force out-of-band GitHub syncs, check-run refresh scheduling, or pull-request state transitions (open/close/label/reopen) against the victim org's stacks — a cross-repository/cross-organization write that crosses the intended per-org authentication boundary, without ever needing that org's real webhook secret, session, or GitHub credentials.

### Likelihood Explanation
Likelihood is contingent on: (1) the instance being configured with multiple GitHub organizations (a documented, supported topology), and (2) at least one of them not having a `webhook_secret` configured (also documented as optional, and the value used in the project's own multi-org test fixtures). Given the project explicitly ships sample configs with `webhook_secret: # nil` for multi-org setups, this is a realistic misconfiguration, not a contrived edge case, though it does require the operator not to have set secrets on every configured org.

### Recommendation
In `WebhooksController#verify_signature`, after establishing the authenticating organization, cross-check that `repository.full_name`'s owner segment matches `repository_owner` (or the `organization.login` used to select the GitHub App) before dispatching to handlers, rejecting mismatches with `422`. Additionally, consider requiring `webhook_secret` to be present for every configured organization (fail fast at boot / raise instead of silently allowing unsigned webhooks) rather than treating it as fully optional.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.yml`: `orgA` (no `webhook_secret`) and `victim-org` (with a real `webhook_secret`), both with stacks tracked.
2. Send, unauthenticated, with no `X-Hub-Signature` header:
```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "victim-org/target-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler#process` runs `stacks` derived from `payload.dig('repository', 'full_name')` = `"victim-org/target-repo"`, and schedules `GithubSyncJob`/commit ingestion against the victim org's stack, despite the request never being authenticated by `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
