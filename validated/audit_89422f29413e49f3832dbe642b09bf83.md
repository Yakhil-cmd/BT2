### Title
Webhook signature is verified against `repository_owner`/`organization.login` while handlers resolve the target repo from `repository.full_name`, letting an unsigned/mis-keyed webhook mutate an unrelated victim stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org secret to check the HMAC signature against using `repository_owner`, which falls back to `params.dig('organization','login')` whenever `params.dig('repository','owner','login')` is absent — a case fully permitted by `LabelCapturingHandler`'s schema, since it only `requires :repository, :full_name` and never requires `repository.owner`. The handler itself resolves the actual target `Repository`/`Stack` purely from `params.repository.full_name`, a field completely independent of whichever org's key verified the request. In Shipit's supported multi-org configuration (as exercised by `test/dummy/config/secrets_double_github_app.yml`, which sets `webhook_secret:` to nil for each org), `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no secret is configured for the selected org, so an attacker who references an org with a blank webhook secret authenticates a forged event while pointing `repository.full_name` at a completely different, victim-configured repository.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner == owner_of(params.repository.full_name)`, but nothing enforces this equality.

- `repository_owner` is computed as: [1](#0-0) 
which reads `repository.owner.login`, falling back to `organization.login` if that dig chain returns `nil` (e.g., `repository` present but missing an `owner` sub-object).

- That value selects the verification key/org here: [2](#0-1) 
which calls `Shipit.github(organization: repository_owner)` and then `verify_webhook_signature`.

- In multi-org mode, `Shipit.github` looks up per-org config keyed by that org name: [3](#0-2) 
and `GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that org: [4](#0-3) 

- Meanwhile `LabelCapturingHandler`'s schema requires only `repository.full_name`, not `repository.owner`: [5](#0-4) 
and it resolves the actual `Repository`/`Stack` purely from that field: [6](#0-5) 
completely independent of `repository_owner`/`organization.login` used for signature verification.

Exploit request: attacker POSTs to `/webhooks` with `X-Github-Event: pull_request` and a JSON body such as:
```
{
  "action": "unlabeled",
  "number": 1,
  "pull_request": { ...valid schema fields..., "labels": [{"name": "ATTACKER_INJECTED_KEY"}] },
  "repository": { "full_name": "victim-org/victim-repo" },
  "organization": { "login": "org-with-no-webhook-secret" },
  "sender": { "login": "attacker" }
}
```
No `repository.owner` key is present, so `repository_owner` resolves to `"org-with-no-webhook-secret"`. `Shipit.github(organization: "org-with-no-webhook-secret")` returns a `GitHubApp` with `webhook_secret` nil, so `verify_webhook_signature` returns `true` for any (or no) `X-Hub-Signature` header. The request passes `verify_signature`, and `LabelCapturingHandler` then loads `Repository.from_github_repo_name("victim-org/victim-repo")`, updates `stack.pull_request.labels` with attacker-chosen label names on the victim's review stack. Those label names become `PullRequest#labels`, and per the question's downstream chain, get uppercased into `ReviewStack#env` and, combined with `ignore_ci: true` short-circuiting `Commit#deployable?`, enable an unauthorized deploy path.

Why existing guards fail: `verify_signature` never checks that the org it used for verification matches the owner embedded in `repository.full_name`; `drop_unhandled_event` only checks event type presence; the `ExplicitParameters` schema for this handler never requires `repository.owner`, so a payload lacking it is fully valid; `GithubOrganizationUnknown` only protects against org names not present in config at all — it does nothing if the org exists but simply has no `webhook_secret` set, a state explicitly present in this codebase's own multi-org test fixture [7](#0-6) .

### Impact Explanation
An attacker who can identify (or simply guess, since org names/dummy tenants are often discoverable) any org configured in Shipit's multi-org GitHub App setup without a `webhook_secret` can forge webhook events that mutate any other repository's stacks that Shipit tracks — writing attacker-controlled PR label data into the victim's `PullRequest`/`ReviewStack` state. Combined with `ignore_ci: true` on the victim stack (which makes `Commit#deployable?` bypass CI checks entirely: [8](#0-7) ) and label-derived environment variables reaching deploy commands, this is a genuine cross-tenant "payload for one repository mutating another's stack" scenario — matching the Critical impact bucket. It is repeatable against any tracked repository/stack as long as one org in the multi-org config lacks (or the attacker somehow obtains) a webhook secret.

### Likelihood Explanation
This requires the Shipit deployment to run in **multi-org mode** (`secrets.github` keyed by multiple org names rather than the single top-level schema) **and** at least one of those configured orgs to have a blank/missing `webhook_secret`. This is not a purely theoretical state — the repo's own test fixture `secrets_double_github_app.yml` models exactly this (two orgs, both `webhook_secret: nil`), showing the configuration is directly supported and plausible in real deployments. In the far more common single-org/legacy config (`github_default_organization.nil?`), `Shipit.github` ignores the `organization:` argument entirely and always uses the single top-level secret [9](#0-8) , so the divergence has no effect there — the attacker still needs the one global secret. Thus exploitability is conditional on multi-org + weak-secret configuration, not universal, but the underlying code defect (verification-key selection decoupled from the resource-selection field) is unconditionally present.

### Recommendation
1. In `WebhooksController#verify_signature`, require `repository.owner.login` to be present and match the eventual target repository's owner before dispatching to handlers; reject payloads that use the `organization.login` fallback for any event that also carries a `repository` object.
2. In `GitHubApp#verify_webhook_signature`, do not silently return `true` when `webhook_secret` is blank — treat a missing secret as a hard misconfiguration (raise/refuse) rather than "verification passed."
3. In each handler (e.g., `LabelCapturingHandler`), assert that the resolved `Repository#full_name`'s owner matches the org/repository owner that authenticated the webhook (`repository_owner`), rejecting mismatches before mutating any stack state.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (added test)
test "pull_request unlabeled webhook cannot mutate victim stack via organization fallback + org without webhook_secret" do
  victim_repo = shipit_repositories(:shipit) # owns victim-org/repo, ignore_ci: true
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(ignore_ci: true)
  victim_pr = victim_stack.create_pull_request!(...) # existing PR fixture

  # Precondition binding under test:
  # claim: repository_owner (verifier selector) == owner_of(params.repository.full_name)
  # Before: verifier org = "org-with-no-secret" != "victim-org" (owner of victim_repo)

  payload = {
    action: 'unlabeled',
    number: victim_pr.number,
    pull_request: {
      id: 1, number: victim_pr.number, url: 'http://x', title: 't', state: 'open',
      additions: 1, deletions: 1,
      head: { sha: 'a' * 40, ref: 'branch' },
      user: { login: 'attacker' },
      assignees: [],
      labels: [{ name: 'ATTACKER_INJECTED_ENV_KEY' }]
    },
    repository: { full_name: victim_repo.github_repo_name }, # no owner sub-key -> triggers fallback
    organization: { login: 'org-with-no-secret' },
    sender: { login: 'attacker' }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  # deliberately wrong/absent signature
  @request.headers['X-Hub-Signature'] = 'sha1=0000000000000000000000000000000000000000'

  Shipit.stubs(:github).with(organization: 'org-with-no-secret')
    .returns(Shipit::GitHubApp.new('org-with-no-secret', { webhook_secret: nil }))

  assert_changes -> { victim_pr.reload.labels }, from: [], to: ['ATTACKER_INJECTED_ENV_KEY'] do
    post :create, body: payload, as: :json
  end
  assert_response :ok

  # Assert the equality was violated: verifier org != victim repo owner, yet victim stack was mutated
  refute_equal 'org-with-no-secret', victim_repo.owner
end
```
This demonstrates the divergence: the field used to select the signature-verification key (`organization.login` → `"org-with-no-secret"`) differs from the field used to select the mutated resource (`repository.full_name` → the victim repo's owner), and the request nonetheless succeeds and mutates the victim's `PullRequest`/`ReviewStack` state.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

  end

  end
