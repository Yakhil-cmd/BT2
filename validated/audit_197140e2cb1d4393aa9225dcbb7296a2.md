### Title
Webhook signature verified against the wrong organization's secret while the handler acts on an attacker-chosen repository — cross-tenant forgery via mismatched `repository.owner.login` / `repository.full_name` fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to validate an incoming webhook using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Every event handler that actually mutates state, however, resolves the target `Repository`/`Stack` using a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Because the HMAC only proves the payload was signed with *some* organization's secret — the one named by `repository.owner.login` — and not that `repository.full_name` belongs to that same organization, an attacker who legitimately administers one tenant/org in a multi-tenant Shipit deployment (and therefore knows that org's `webhook_secret`, which is not itself a privileged Shipit credential/session) can forge a payload whose `owner.login` names their own org (passing signature verification) while `full_name` names a victim org's repository, causing Shipit to act on the victim's `Stack`.

### Finding Description
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) does:
  ```ruby
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ```
  where `repository_owner` (lines 59-62) reads `params.dig('repository', 'owner', 'login')`.
- Every handler that performs the actual work (push sync, PR review-stack unarchiving, etc.) derives the target repository independently via `Handler#repository_name` (app/models/shipit/webhooks/handlers/handler.rb:36-38):
  ```ruby
  def repository_name
    payload.dig('repository', 'full_name')
  end
  ```
  and `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) uses `stacks` (built from `repository_name`) to call `stack.sync_github`.
- Nothing ties `repository.owner.login` (used to choose the verifying secret) to `repository.full_name` (used to choose the object mutated). The HMAC only certifies "this body was signed by *the org named in `repository.owner.login`*" — it says nothing about which org's data the same body claims to reference in `repository.full_name`.
- Shipit explicitly supports multiple, independently configured GitHub orgs/apps in one instance, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml:5-23`: `somegithuborg`, `someothergithuborg`, each with independent `webhook_secret`). An operator/attacker who legitimately controls one tenant org's GitHub App knows that org's `webhook_secret` as a normal part of operating their own integration — this is not a privileged Shipit credential, session, or `api_clients_secret`.
- Attack: attacker sets `repository.owner.login = "attacker-org"` (an org whose secret they know) and `repository.full_name = "victim-org/victim-repo"` in the same JSON body, computes a valid `X-Hub-Signature` with attacker-org's `webhook_secret`, and POSTs to `/github/webhooks`. `verify_signature` passes (secret matches, since it only checks against `attacker-org`). The `push` handler then resolves `stacks` for `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: ...)`, and PR handlers (e.g. `ReopenedHandler`) can call `stack.unarchive!` on victim review stacks — all cross-tenant, without ever knowing victim-org's secret.

### Impact Explanation
This breaks the trust binding "an organization that authenticated versus the repository that is written," matching the rules' explicit list of in-scope bindings. It allows an attacker who is a legitimate tenant of a shared, multi-org Shipit instance to trigger state changes (sync jobs, commit ingestion, stack unarchiving) against another tenant's stacks/repositories they have no authorization over — a cross-repository/cross-tenant write inside Shipit's own database and job queue, satisfying the "cross-repository writes" Critical-impact criterion. Depending on stack configuration (e.g. `continuous_deployment` enabled), a forced/duplicated `GithubSyncJob` run can also feed into automatic deploy triggering for a stack the attacker does not own.

### Likelihood Explanation
Likelihood is limited to deployments that host multiple GitHub organizations/tenants in a single Shipit instance (a supported, documented configuration per `config/secrets.development.shopify.yml` and `lib/shipit/github_app.rb`'s per-organization secret handling). Within such a deployment, exploitation requires no Shipit session, API token, or knowledge of the victim's secret — only knowledge of the attacker's *own* tenant's `webhook_secret`, which they are expected to know as the operator of that org's GitHub App integration.

### Recommendation
Cross-check that `repository.full_name`'s owner segment matches the `repository_owner` (or `organization.login`) value used to select the verifying secret before dispatching to handlers, e.g. in `WebhooksController#verify_signature`/`#create`, reject the request (422) if `params.dig('repository','full_name')&.split('/')&.first != repository_owner`. Alternatively, have handlers resolve the target repository/organization from the same trusted field that was used for signature verification, rather than independently trusting `repository.full_name`.

### Proof of Concept
1. Configure two tenant orgs in Shipit: `attacker-org` (secret `S_A`, known to attacker) and `victim-org` (secret `S_V`, unknown to attacker), per `config/secrets.development.shopify.yml` style config.
2. Craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<sha attacker wants recorded>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>`.
4. `POST /github/webhooks` with `X-Github-Event: push` and the above signature/body.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully against `S_A`.
6. `PushHandler#process` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github` for a stack the attacker does not administer, confirming cross-tenant, unauthorized state mutation with only the attacker's own tenant secret. module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
