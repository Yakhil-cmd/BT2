### Title
Native value sent alongside an `IERC20::transfer`/`approve` call to a pallet-assets ERC20 precompile is permanently unrecoverable - ([File: substrate/frame/assets/precompiles/src/lib.rs])

### Summary
`pallet-revive` lets a caller attach a native currency `value` to any `call`/`bare_call`, including calls targeting a precompile address [1](#0-0) . The `ERC20` precompile that wraps `pallet-assets` (`TrustBackedAssets`, `PoolAssets`, `ForeignAssets` on Asset Hub) never checks or uses that native `value`; it only performs asset-pallet operations such as `transfer`/`approve`/`transferFrom` [2](#0-1) . If a caller mistakenly sends non-zero native `value` together with an ERC20 `transfer` call (analogous to mistakenly passing `msg.value` in the Solidity `receiveFunds`), that native currency is credited to the precompile's backing account and has no code path to be returned to the caller.

### Finding Description
In `Pallet::run` (via `CallStack::run`), before the precompile is invoked, `transfer_from_origin` unconditionally moves `frame.value_transferred` (the native `value` passed by the caller) into the destination `account_id`, regardless of whether the destination is a real contract, a plain wallet, or a precompile:
```
if frame.delegate.is_none() {
    Self::transfer_from_origin(&self.origin, &caller, account_id, frame.value_transferred, ...)?;
}
``` [1](#0-0) 

This happens *before* the precompile's `call()` is dispatched, so the precompile has no opportunity to reject a non-zero `value` before the funds are already moved. The `ERC20` precompile's `call()` dispatcher only inspects the ABI-decoded `IERC20Calls` and routes to functions like `transfer`, `approve`, `transferFrom`, `permit`, etc. — none of which read or validate `env.value()` [2](#0-1) . The `transfer` implementation exclusively moves the wrapped fungible asset via `pallet_assets::Pallet::do_transfer`, never touching the native `Currency` balance that was just credited to the precompile's account [3](#0-2) .

The account that receives this stray native value is the account_id backing the precompile's fixed address (e.g. `0x0000053900000000000000000000000001200000` style prefix addresses used for asset ids). Because this address is not derived from any real user's public key, `AddressMapper::to_account_id` resolves it to the stateless "fallback account" — a 32-byte `AccountId32` built by suffixing the 20-byte address with `0xEE` bytes [4](#0-3) . There is no private key, mapping, or precompile logic that lets anyone dispatch a transaction as this synthetic account to withdraw the stuck native balance: `dispatch_as_fallback_account` only lets a *signed origin* act as the fallback account for *its own* keccak-derived address, not an arbitrary precompile address chosen independently of any keypair [5](#0-4) . This is structurally the same defect as the reported OpenQ bug: a function that branches on "is this a native-token operation or a token operation" credits/loses `msg.value`/native `value` in the token branch without validating or forwarding it, and the loss becomes irrecoverable because the accounting path for retrieving native funds (`refundDeposit` in OpenQ, ordinary signed calls in `pallet-revive`) is keyed to the wrong asset/account and can never reach the stray native balance.

### Impact Explanation
Any ordinary user (no privileged role required) who calls the pallet-assets `ERC20` precompile (e.g. `IERC20::transfer`) via `pallet_revive::Pallet::call`/`bare_call` and mistakenly (or through wallet/tooling error, since EVM tooling commonly lets users set a "value" field independent of the ABI call data) attaches a non-zero native `value` loses that native currency permanently. There is no extrinsic, precompile function, or governance-free mechanism to recover it, since the receiving account is a stateless, keyless fallback account. This is a direct, permanent loss of user funds through a fully user-reachable, unprivileged, signed-extrinsic entry point (`pallet_revive::Call::call`), matching the severity class of the original finding (funder loses native token, no way to reclaim).

### Likelihood Explanation
Likelihood is Medium/Low-to-Medium: it requires user error (attaching a native `value` while intending a pure ERC20 token transfer), similar to the original OpenQ report's precondition. However, this is a realistic mistake given that EVM-compatible wallets/tools routinely expose a separate "value" (ETH-equivalent) field alongside contract call data, and nothing in the runtime, the precompile ABI, or wallet UX inherently prevents or warns against setting both when targeting `pallet-revive` precompiles. Unlike a typical EOA-to-EOA ETH transfer mistake (recoverable because the recipient is a real account), here the destination is a synthetic prefix address with no real owner, making the mistake unrecoverable rather than merely inconvenient.

### Recommendation
Add an explicit guard in `pallet-revive`'s precompile dispatch path (or in each stateful precompile, starting with the `ERC20`/asset-conversion/vesting/XCM precompiles) that rejects calls carrying non-zero `value` unless the specific precompile function is documented to consume native currency. Concretely:
- In `CallStack::run` (`substrate/frame/revive/src/exec.rs`), before transferring `frame.value_transferred` into a precompile account, check whether the target `executable.as_precompile()` declares that it accepts value (e.g. add a `const ACCEPTS_VALUE: bool = false` similar to `HAS_CONTRACT_INFO`), and revert with an error such as `PrecompileValueNotAccepted` if a non-zero value is attached and the precompile does not opt in.
- Alternatively/additionally, have `ERC20::call` in `substrate/frame/assets/precompiles/src/lib.rs` check `env.value().is_zero()` at the top of `call()` and return `Error::Revert` otherwise, mirroring the OpenQ recommendation of adding `require(msg.value == 0, ...)` in the ERC20 branch.

### Proof of Concept
This is reported as an analog derived from source-code analysis; no live/integration test was executed as part of this analysis. Supporting evidence for the mechanism (not a full end-to-end repro) exists in the repository's own test suite: `pure_precompile_works` demonstrates that native `value` sent to a precompile address is credited to that address's balance (`Pallet::<Test>::evm_balance(&precompile_addr) == 100` after sending `value = 100`) [6](#0-5) , confirming that `transfer_from_origin` moves native value into precompile accounts unconditionally. A minimal reproduction to fully confirm the claim would:
1. Deploy/use an `ERC20`-precompiled asset on a test runtime (e.g. `substrate/frame/assets/precompiles/src/tests.rs::precompile_transfer_works` setup) [7](#0-6) .
2. Call `pallet_revive::Pallet::<Test>::bare_call` targeting the asset's precompile address with `value = X` (X > 0) and `data` encoding `IERC20::transferCall`.
3. Assert the ERC20 transfer still succeeds (confirming the value is ignored/not validated) and that `Balances::free_balance` of the precompile's fallback account increased by `X` with no extrinsic available to withdraw it back to the original caller.

This last step (step 3, proving unrecoverability) was not executed against the codebase in this analysis; it is inferred from the `AddressMapper`/fallback-account code paths reviewed (`substrate/frame/revive/src/address.rs`, `substrate/frame/revive/src/lib.rs::dispatch_as_fallback_account`) rather than from an executed test. A background engineering session with terminal/test access would be needed to run this concrete repro and confirm the exact failed-guard behavior and final balances.

		address: &[u8; 20],
		input: &Self::Interface,
		env: &mut impl Ext<T = Self::T>,
	) -> Result<Vec<u8>, Error> {
		frame_support::ensure!(
			!env.is_delegate_call(),
			pallet_revive::Error::<Self::T>::PrecompileDelegateDenied,
		);

		let asset_id = PrecompileConfig::AssetIdExtractor::asset_id_from_address(address)?.into();
		let contract_addr = H160::from(*address);

		match input {
			// State-changing calls - check read-only
			IERC20Calls::transfer(_) |
			IERC20Calls::approve(_) |
			IERC20Calls::transferFrom(_) |
			IERC20Calls::permit(_)
				if env.is_read_only() =>
			{
				Err(Error::Error(pallet_revive::Error::<Self::T>::StateChangeDenied.into()))
			},

			// ERC20 functions
			IERC20Calls::transfer(call) => Self::transfer(asset_id, call, env),
			IERC20Calls::totalSupply(_) => Self::total_supply(asset_id, env),
			IERC20Calls::balanceOf(call) => Self::balance_of(asset_id, call, env),
			IERC20Calls::allowance(call) => Self::allowance(asset_id, call, env),
			IERC20Calls::approve(call) => Self::approve(asset_id, call, env),
			IERC20Calls::transferFrom(call) => Self::transfer_from(asset_id, call, env),

			// ERC20Permit functions (EIP-2612)
			IERC20Calls::permit(call) => Self::permit(asset_id, contract_addr, call, env),
			IERC20Calls::nonces(call) => Self::nonces(contract_addr, call, env),
			IERC20Calls::DOMAIN_SEPARATOR(_) => {
				Self::domain_separator(asset_id, contract_addr, env)
			},

			// ERC20Metadata functions
			IERC20Calls::name(_) => Self::name(asset_id, env),
			IERC20Calls::symbol(_) => Self::symbol(asset_id, env),
			IERC20Calls::decimals(_) => Self::decimals(asset_id, env),
		}
	}

	fn to_account_id(address: &H160) -> AccountId32 {

	fn to_fallback_account_id(address: &H160) -> AccountId32 {
		let mut account_id = AccountId32::new([0xEE; 32]);
		let account_bytes: &mut [u8; 32] = account_id.as_mut();
		account_bytes[..20].copy_from_slice(address.as_bytes());
		account_id
	}

			mut origin: OriginFor<T>,
			call: Box<<T as Config>::RuntimeCall>,
		) -> DispatchResultWithPostInfo {
			Self::ensure_non_contract_if_signed(&origin)?;
			let account_id = origin.as_signer().ok_or(DispatchError::BadOrigin)?;
