### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but repository resolution uses the independent, unchecked `repository.full_name` field, enabling cross-repository stack/PR mutation - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/repository.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/webhook secret to validate the HMAC signature using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), while all downstream handlers resolve the actual `Repository`/stacks to act on via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. These two payload fields are never cross-checked against each other, so a valid signature from organization A's own webhook secret can be replayed with a `repository.full_name` pointing at organization B's repository, causing Shipit to act on organization B's stacks/review stacks/PRs.

### Finding Description
The binding that should hold is: `Repository.from_github_repo_name(payload.dig('repository','full_name')).owner == repository_owner` (the value used in `verify_signature`, i.e., `params.dig('repository','owner','login')` / `params.dig('organization','login')`). This equality is never checked anywhere in the code.

Trace:
- `app/controllers/shipit/webhooks_controller.rb:24-49` `verify_signature` computes `repository_owner` from the JSON body and calls `Shipit.github(organization: repository_owner)` to obtain the `GitHubApp` instance whose `webhook_secret` is used in `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`), which is a straight HMAC-SHA1 check over the *entire raw body* using that organization's configured secret.
- `create` then dispatches the full parsed `params` (the whole JSON body) to handlers (`app/controllers/shipit/webhooks_controller.rb:10-15`).
- Every handler (e.g. `app/models/shipit/webhooks/handlers/handler.rb:36-38`, `pull_request/closed_handler.rb:49-53`) resolves the repository/stacks using `payload.dig('repository', 'full_name')` fed into `Repository.from_github_repo_name`, which just lowercases and splits the string and does an exact `find_by(owner:, name:)` (`app/models/shipit/repository.rb:53-56`).

Because HMAC verification authenticates that *the body's bytes* were signed by a specific org's secret, not that the body's `repository.full_name` value belongs to that org, an attacker who legitimately owns/administers a repository under organization A (and therefore knows or can set organization A's registered webhook secret in their own GitHub webhook configuration, since GitHub webhook secrets are chosen by whoever configures the webhook) can craft an arbitrary JSON body where:
- `organization.login` / `repository.owner.login` = `"org-a"` (attacker's own org, used only for signature-key selection)
- `repository.full_name` = `"org-b/victim-repo"` (any other repository already registered in this Shipit instance)

They sign this body with org A's secret and POST it to `/webhooks`. `verify_signature` picks org A's `GitHubApp`, the HMAC matches, and the request is accepted. The dispatched handler then resolves `Repository.from_github_repo_name("org-b/victim-repo")`, finds the real victim `Repository`/`Stack`, and executes the handler's action against it (e.g. `PullRequest::ClosedHandler#process` calls `review_stack.archive!` on the victim's review stack; `PushHandler`/`StatusHandler`/`CheckSuiteHandler` similarly act on stacks resolved purely from the attacker-chosen `full_name`).

None of the existing guards prevent this: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schemas only validate shape/types of fields, not cross-field consistency; `verify_signature`'s only check is HMAC validity for the org derived from `owner.login`; `Repository.from_github_repo_name` performs an exact-match lookup with no relation to `repository_owner` at all.

### Impact Explanation
An attacker who administers one repository/organization already onboarded to a multi-tenant Shipit instance can forge webhook payloads that are accepted as authentic (signature check passes) but whose `repository.full_name` targets a different tenant's repository. Depending on which webhook events are wired to handlers, this allows: archiving/closing another tenant's review stacks (`PullRequest::ClosedHandler`), and other handler classes (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) similarly resolve stacks from the same unchecked `full_name` field, meaning commit status updates, CI check state changes, or stack-triggering pushes attributed to the victim repository's stacks can be spoofed. This is a payload for one repository mutating another repository's stack/task/review-state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: the Shipit instance must be configured with multiple GitHub organizations/apps (multi-tenant), and the attacker must control at least one repository/org already registered with Shipit (so they can configure its webhook and know its secret) — this matches the stated attacker model ("verifying org... is an org the attacker legitimately controls"). No Shipit credentials, GitHub App private key, or `secret_key_base` are needed. The attack is a single unauthenticated HTTP POST to `/webhooks` with a crafted, self-signed body, fully repeatable against any repository/stack already known to `Repository.from_github_repo_name`, for every event type whose handler resolves its target purely from `repository.full_name`.

### Recommendation
Cross-validate the two payload fields before dispatching to handlers: after `verify_signature` succeeds, assert that the repository resolved from `repository.full_name` (or `repository_owner`/`organization.login` used for the signature) match the literal `owner` of the record produced by `Repository.from_github_repo_name`. Concretely, in `WebhooksController#verify_signature` (or immediately in `create`), extract `repo_owner, _ = payload.dig('repository','full_name')&.downcase&.split('/')` and require `repo_owner == repository_owner`; reject (422) on mismatch. Additionally, `Repository.from_github_repo_name` could accept and enforce an expected owner argument, or handlers could receive the verified `repository_owner` and pass it in, so any org-name/full_name divergence is rejected before any handler executes.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in test secrets, `org-a` (attacker-controlled, secret `SECRET_A`) and `org-b` (victim, secret `SECRET_B`), each with a `Repository` and `Stack`/`ReviewStack` fixture (`org-a/repo-a`, `org-b/repo-b`).
2. Build a `pull_request` "closed" webhook JSON body with:
   - `organization.login` / `repository.owner.login` = `"org-a"`
   - `repository.full_name` = `"org-b/repo-b"`
   - a valid `pull_request` matching an existing `org-b` review stack's PR number/head sha.
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', SECRET_A, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: pull_request`.
5. Assert response is `200 OK` (signature accepted) — demonstrating `repository_owner == "org-a"` while `Repository.from_github_repo_name(payload.dig('repository','full_name')).owner == "org-b"`, i.e. the two sides of the binding differ (`"org-a" != "org-b"`), yet the request is processed.
6. Assert the `org-b` review stack was archived (`review_stack.reload.archived?`) despite the request never being signed by `org-b`'s secret — proving cross-repository mutation without the victim org's cooperation.
