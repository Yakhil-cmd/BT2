### Title
Persistent sync denial via attacker-controlled recursive/nested submodules in `configureWorktree` - ([File: main.go])

### Summary
`git-sync`'s per-cycle `configureWorktree` unconditionally runs `git submodule update --init --recursive` against whatever `.gitmodules` content is present in the fetched commit, with no cap on submodule count, nesting depth, or per-submodule size. This mirrors the `TraceTx` bug class (attacker-supplied, unbounded input driving repeated, expensive server-side work) but the "predecessor list" analog here is the submodule graph embedded in attacker-influenced repository content.

### Finding Description
On every sync pass, once a new commit hash is fetched, `git-sync` calls `configureWorktree`, which performs `git reset --hard` followed by a submodule step: [1](#0-0) 

If `--submodules` is not set to `off` (the default is `recursive`), this issues `git submodule update --init --recursive`, which recursively clones every submodule and nested submodule declared in `.gitmodules` for the currently synced commit, with no limit on the number of submodules, recursion depth, or the size/complexity of each submodule repository (a `--depth` flag only bounds commit history depth per repo, not fan-out or recursion count): [2](#0-1) 

Anyone who can influence the content that ends up in the synced ref (e.g. a PR merged into the tracked branch/tag, or a compromised/attacker-controlled upstream that the operator points `--repo`/`--ref` at) controls the `.gitmodules` file and can declare an arbitrarily large or deeply/circularly nested submodule tree. Because the sync loop re-runs this same recursive submodule update on every `--period` tick (and again on process restart via `initRepo`/`SyncRepo`), the resource cost is not one-shot — it recurs indefinitely as long as that malicious commit remains the target ref, unlike a single expensive gRPC call. This is directly analogous to the `TraceTx` finding, where an attacker-controlled input list (`req.Predecessors`) triggers repeated, unbounded server-side computation; here the "predecessor list" is the submodule graph rather than a request field, and the untrusted-content vector is the repository itself rather than an RPC parameter.

### Impact Explanation
A malicious or compromised upstream commit can force the `git-sync` sidecar to spend excessive CPU, memory, disk, and network resources cloning/recursing through a huge submodule tree on every sync cycle, potentially exhausting the container's resources or the shared filesystem, and preventing legitimate future syncs from completing within `--sync-timeout` — a persistent sync denial. This matches the accepted impact category of "persistent sync denial."

### Likelihood Explanation
Likelihood is moderate to high in any deployment where `--submodules` is left at its default (`recursive`) and the tracked ref/branch can receive content from parties outside full operator trust (e.g., a repo accepting external contributions that get merged into the synced branch, or a mutable/less-trusted upstream). No credentials or special git-sync flags are required beyond the default submodule behavior; the attacker only needs the ability to get a commit with a crafted `.gitmodules` onto the synced ref.

### Recommendation
- Consider bounding submodule recursion (e.g., limiting depth or refusing to recurse into submodules of submodules) or making `--submodules=off`/`shallow` the safer default for untrusted sources.
- Document and/or enforce a submodule count/size guard before invoking `git submodule update --init --recursive`.
- Ensure `--sync-timeout` reliably bounds the total work of `SyncRepo` (including submodule updates) per cycle so a single malicious commit cannot indefinitely stall the sync loop, and surface clear failure/backoff metrics distinguishing this from transient network errors.

### Proof of Concept
1. Operator configures `git-sync --repo=<repo> --ref=<branch> --submodules=recursive` (the default).
2. An attacker who can land a commit on `<branch>` (e.g., via merged PR, compromised fork, or compromised upstream account) adds a `.gitmodules` file with a very large number of submodule entries, or a submodule chain that itself recursively adds further submodules many levels deep — as exercised structurally (without malicious intent) by the nested-submodule e2e tests: [3](#0-2) 
3. On the next fetch, `git-sync`'s `SyncRepo` detects the new hash and calls `configureWorktree`, which runs the unbounded `git submodule update --init --recursive` against this crafted tree: [4](#0-3) 
4. Every subsequent `--period` tick (and every process restart) repeats this expensive recursive clone against the same malicious commit until the ref is changed, denying reliable service from the sidecar.
