### Title
Webhook signature verification org (`repository.owner.login`) is never bound to the routed repository org (`repository.full_name`), allowing cross-tenant `GithubSyncJob` injection - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to verify a webhook's HMAC using `repository_owner` = `params.dig('repository', 'owner', 'login')`, while `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` (and thus every handler, including `PushHandler`) resolves the target repository/stack using an entirely independent field, `payload.dig('repository', 'full_name')`. These two values are never checked for consistency anywhere in the request path, so a signature that is valid for org A can authorize a mutation against org B's repository/stack.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:

`organization_whose_secret_verified_the_request (repository.owner.login)` **==** `organization_owning_the_stack_being_mutated (repository.full_name.split('/').first)`

Trace:
- `verify_signature` picks the app/secret via `repository_owner` [1](#0-0)  and derives `repository_owner` purely from `repository.owner.login` (or `organization.login`) [2](#0-1) .
- Once verification passes, `create` parses the raw body and dispatches to handlers with the full, attacker-controlled payload, unmodified [3](#0-2) .
- `Handler#stacks` and `#repository_name` derive the target repository strictly from `payload.dig('repository', 'full_name')`, with no reference to `repository.owner.login` or to which org's secret verified the request [4](#0-3) .
- `PushHandler#process` uses that `stacks` scope, filters by branch, and calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack [5](#0-4) , which is documented/tested to enqueue `GithubSyncJob` for that stack.
- `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a DB lookup by owner/name, with no relation to the verified organization [6](#0-5) .

Root cause: nothing in `verify_signature`, `create`, or `Handler` cross-checks that `repository.owner.login` (the value used to pick the verifying `webhook_secret`) matches the owner segment of `repository.full_name` (the value used to select the mutated stack). GitHub itself would never emit such an inconsistent payload for a real event, but nothing in this engine's code enforces that a forged/synthetic payload be internally consistent.

Attacker request: An attacker who administers their own org/app installation per the documented "Using Multiple Github Applications" setup (`docs/setup.md`, "Using Multiple Github Applications" section) knows their own `github.<attacker-org>.webhook_secret`. They POST `/webhooks` with header `X-Github-Event: push`, a valid `X-Hub-Signature` HMAC-signed with their own secret over a body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"` and `after`/`ref` set to target the victim's tracked branch.

Existing guards do not prevent this:
- `verify_signature` only checks that the *signature* is valid for whichever org's secret is chosen by `repository_owner` — it never inspects `full_name` [7](#0-6) .
- `ExplicitParameters` schemas for handlers (e.g., `PushHandler`) only validate presence/type of `ref`/`after`, not any cross-field consistency [8](#0-7) .
- `drop_unhandled_event` and `check_if_ping` are unrelated to this binding.
- No model validation on `Repository`/`Stack` catches this, since the payload never creates/loads a `Repository` keyed by `owner.login` — only by `full_name`.

### Impact Explanation
An unprivileged attacker who controls only their own org's webhook secret can force Shipit to enqueue `GithubSyncJob` (and by extension trigger sync/deploy pipeline activity) against a stack belonging to a completely different, victim-owned repository/org — a payload for one repository mutating another repository's stack, matching the "Critical" impact category defined in the rules. This works for any victim repository/stack that exists in Shipit's database, regardless of tenant boundary, and is repeatable per push-like event for other handlers that also key off `full_name` (e.g., `status`, `check_suite`, PR handlers), broadening blast radius across all "push"/"status"/PR webhook types that route through `Handler#stacks`/`repository_name` or the various `Repository.from_github_repo_name(params.repository.full_name)` call sites in the PR handlers.

### Likelihood Explanation
Preconditions are realistic: multi-tenant Shipit deployments following `docs/setup.md`'s "Using Multiple Github Applications" section are exactly the documented use case, and any org owner onboarded this way legitimately possesses their own `webhook_secret`. The attack requires no compromise of victim secrets, no session, no API token — only crafting a JSON payload with mismatched `owner.login`/`full_name` fields and computing an HMAC with a secret the attacker already legitimately owns. Cost is a single crafted HTTP POST, fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization used to verify the signature is consistent with the organization embedded in `repository.full_name` — e.g., derive `repository_owner` from `full_name` itself (or require `full_name.split('/').first.downcase == repository.owner.login.downcase` before verification/dispatch), and reject the request (422) on mismatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "push payload with owner.login != full_name org must not sync a different org's stack" do
  attacker_secret = 'attacker-secret'
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GithubApp.new('attacker-org', webhook_secret: attacker_secret)
  )
  victim_stack = shipit_stacks(:shipit) # owner/name resolves via victim-org/victim-repo

  body = JSON.parse(payload(:push_master))
  body['repository']['owner']['login'] = 'attacker-org'
  body['repository']['full_name'] = victim_stack.repository.github_repo_name
  json = body.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, json)

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = signature

  # Binding under test:
  # LHS: org whose secret verified signature == 'attacker-org'
  # RHS: org owning the mutated stack == victim_stack.repository.owner
  # These must be equal for the request to legitimately affect victim_stack.

  assert_no_enqueued_jobs do
    post :create, body: json, as: :json
  end
  # Currently FAILS: assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, ...])
  # succeeds instead, proving the LHS != RHS divergence is exploitable.
end
```

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
    end
