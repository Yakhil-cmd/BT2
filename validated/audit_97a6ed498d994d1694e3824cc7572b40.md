## Title
Race condition in `shrinkCache()` unconditional cache eviction can corrupt live unit-props caches and crash node validation - (File: `storage.js`)

### Summary
`storage.js`'s `shrinkCache()` releases the `"write"` mutex before all of its asynchronous `db.query()` eviction callbacks have completed, so `delete assocKnownUnits[...]`, `delete assocCachedUnits[...]`, `delete assocStableUnits[...]`, `delete assocCachedUnitAuthors[...]`, and `delete assocCachedUnitWitnesses[...]` execute *outside* the lock that is supposed to serialize all mutation of these in-memory caches. This mirrors the btrfs bug class: an unconditional, key-based delete of a shared cache/xarray entry races against a concurrent path that legitimately re-populates the same key, and the eviction wins, silently dropping a live entry instead of leaving it intact.

### Finding Description
`shrinkCache()` takes the global write lock, then queries the DB in `CHUNK_SIZE` batches to find which cached units are "old enough" to be purged, and calls `unlock()` immediately after issuing the last `db.query()` call in the loop — not after the query callbacks run: [1](#0-0) 

Because `db.query` is asynchronous, `unlock()` fires and the write mutex is released while the `for` loop's `db.query(...)` callbacks (which do the actual `delete assocKnownUnits[row.unit]; delete assocCachedUnits[row.unit]; ...`) are still pending. Any other write-path code that runs after `unlock()` — most importantly `readUnitProps()`, which is invoked while validating/writing units and unconditionally trusts and mutates `assocStableUnits`/`assocUnstableUnits`/`assocCachedUnits` — can interleave with these deferred deletes: [2](#0-1) 

`readUnitProps()` explicitly re-populates `assocStableUnits[unit]` and validates it against the DB row, throwing an `Error` if the cached copy doesn't match, or throwing `"no unstable props of "+unit` if `assocUnstableUnits[unit]` is missing when it is expected to exist: [3](#0-2) 

If the deferred `shrinkCache` eviction callback deletes `assocStableUnits[unit]` / `assocCachedUnits[unit]` for a unit that was concurrently (and legitimately) re-cached by `readUnitProps()`/`readStaticUnitProps()`/`readUnitAuthors()` for a unit being actively validated (e.g. an AA trigger unit, a payment being processed, or a unit on the hot validation path right after the DB write lock was momentarily free), the entry can vanish or become inconsistent with what other in-flight callbacks still hold references to. Because the same JS objects (`props`) are shared by reference across the whole codebase (`assocUnstableUnits[unit]` objects are mutated in place elsewhere, e.g. `is_free`, `sequence`), losing the xarray-equivalent binding for a unit that is still "live" reproduces exactly the btrfs failure mode: a live object becomes unreachable from the index that other code paths rely on to find it, while dependent bookkeeping (best children updates, `fixIsFreeAfterForgettingUnit`, delayed props checks) still expects it to be there.

### Impact Explanation
The immediate observable effect on ocore is not a kernel soft-lockup, but the closest reachable failure: a full node process crash via the deep-equality throw in `readUnitProps()`/`readPropsOfUnits()`, or an `assocUnstableUnits[unit]` lookup throwing `"no unstable props of "+unit`. Both are unconditional `throw Error(...)`, which in Node.js crashes the process unless something catches it up the stack (most of these call sites are inside plain callbacks with no surrounding try/catch that would allow graceful recovery). A crash of a witness/full node during active unit validation directly translates to "a network unable to confirm new units" for that node, and if hit broadly (since `shrinkCache` runs every 300s via `setInterval(shrinkCache, 300*1000)` on every non-light node) can cause repeated crash loops that degrade the ability of the DAG to progress and reach stability consensus.

### Likelihood Explanation
The window is narrow (the time between the last `db.query()` call in `shrinkCache`'s loop and its callback firing), but `shrinkCache` runs on a fixed 5-minute timer on every full/non-light node, and unit validation traffic (units, AA triggers) posted by ordinary unprivileged peers is continuous, so the racing access pattern (validate a unit whose props are about to be purged from cache right as `shrinkCache` is mid-flight) is realistically reachable without any privileged access — it only requires normal unit/trigger posting timed against the periodic cache-shrink tick, which an attacker can approximate by flooding units around the known 5-minute boundary.

### Recommendation
Restructure `shrinkCache()` so `unlock()` is only called after all the per-chunk `db.query()` callbacks have completed (e.g., via `async.eachSeries`/`Promise.all` over the chunks before invoking `unlock()`), ensuring the entire cache-eviction pass is atomic with respect to the write lock, analogous to using a compare-and-delete (only delete if the cached entry is still the one that was scheduled for eviction, otherwise skip) as was done for the btrfs fix via `__xa_cmpxchg()`.

### Proof of Concept
1. Run a full node long enough / with clocks adjusted so `setInterval(shrinkCache, 300*1000)` fires while `arrPropsUnits`/`arrStableUnits` exceed `MAX_ITEMS_IN_CACHE`.
2. Concurrently, have an unprivileged peer post a stream of ordinary units/AA triggers that reference units whose `main_chain_index` sits right at `top_mci`, so they are borderline candidates in `shrinkCache`'s chunked `SELECT unit FROM units WHERE unit IN(?) AND main_chain_index<top_mci ...` query.
3. Because `unlock()` in `shrinkCache` (`storage.js:2293`) fires before the chunk's `db.query` callback (`storage.js:2277-2291`) deletes cache entries, a concurrent `readUnitProps()` call for one of those units can repopulate `assocStableUnits[unit]`/`assocUnstableUnits[unit]` in the gap, after which the deferred `shrinkCache` callback unconditionally deletes it.
4. A subsequent `readUnitProps()`/`readPropsOfUnits()` call for the same unit either throws `"no unstable props of "+unit` (`storage.js:1542`) or the deep-equality check fails (`storage.js:1547-1550`, `storage.js:1602-1605`), crashing the node process during unit validation.
