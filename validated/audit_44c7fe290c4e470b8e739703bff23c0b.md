### Title
Cross-repository CI status forgery via unscoped `StatusHandler` commit lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler` resolves the target `Commit` purely by `sha`, without checking that the commit belongs to the repository the webhook was authenticated for. This breaks the trust binding that GitHub webhook signature verification is supposed to establish: *the organization whose secret signed the payload* should equal *the repository/stack that is written to*. This lets an org/repository legitimately onboarded to a multi-tenant Shipit instance forge a `success` CI status on a commit that belongs to a completely different tracked repository, which can flip `ci.require` gates and enable an unauthorized deploy.

### Finding Description
Webhook authenticity in this engine is verified per-organization: `WebhooksController#verify_signature` selects the GitHub App/secret to use based on the organization embedded in the *unverified* payload (`repository_owner`), then verifies the HMAC over the raw body with that org's `webhook_secret`. [1](#0-0) [2](#0-1) 

This proves only that *some organization X configured in Shipit* sent the payload — it does not, by itself, prove anything about which repository's data the payload is allowed to affect. That binding is supposed to be enforced downstream, by scoping database writes to the repository named in the payload. The base `Handler` class does this correctly for most events, by resolving the target stacks via `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 

`PushHandler` uses this scoped `stacks` helper before acting: [4](#0-3) 

`StatusHandler`, however, never calls `stacks`/`repository_name` at all. It looks up commits globally by SHA and writes a status onto every match, regardless of which repository the webhook actually came from: [5](#0-4) 

Because git commit SHAs are content-addressed and deterministic (same tree/parent/author/committer/timestamps ⇒ same SHA1), an attacker who controls (or mirrors commits into) any repository/organization already onboarded to this Shipit instance can locally reconstruct a commit object identical to one that exists in another org's *tracked* (and possibly private) repository, then push/import it and have GitHub fire a `status` webhook for it. That webhook is correctly signed by the attacker's own org's `webhook_secret`, passes `verify_signature`, and is handed to `StatusHandler`, which then attaches the forged status to the victim's commit — in a repository/org the attacker's webhook secret was never meant to authorize writes to.

### Impact Explanation
Commit statuses gate deploys: `shipit.yml`'s `ci.require`/`ci.blocking` configuration determines whether a commit is `deployable?` based on its `CommitStatus` rows. An attacker who can inject a forged `success` status onto another team's commit (via their own, legitimately signed webhook from an unrelated onboarded repository) can make an otherwise CI-failing or CI-pending commit appear deployable, leading to an unauthorized deploy of that commit for a stack/repository the attacker does not control. This falls under "cross-repository writes" / "an unauthorized deploy," matching the Critical impact bucket, since a boundary between organizations (each with its own webhook secret and repository scope) is broken by a write that is unscoped to the authenticated repository.

### Likelihood Explanation
This requires the Shipit deployment to track more than one GitHub organization/repository (a documented, supported "Using Multiple GitHub Applications" configuration), and requires the attacker to control at least one onboarded repository/org's `status` webhooks (e.g., by owning a repo added to the instance) plus the ability to reproduce the exact target commit's SHA. Reproducing an existing SHA is feasible when the target repository is public (all commit metadata needed to reconstruct an identical commit object is visible), making this a realistic attack surface rather than a purely theoretical one, even though it requires the attacker to already be a legitimate but lower-privileged tenant of the same Shipit instance.

### Recommendation
`StatusHandler#process` should scope its `Commit` lookup to the repository named in the webhook payload (using the same `stacks`/`repository_name` pattern as `Handler`/`PushHandler`), e.g. filter to `stacks.flat_map(&:commits).where(sha: params.sha)` or otherwise join through `Repository.from_github_repo_name(repository_name)` before updating any commit's status, so a status webhook can only affect commits belonging to the repository that was actually authenticated.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs/apps: `org-victim` (tracks a private stack) and `org-attacker` (onboarded by the attacker, who has push access there).
2. Attacker observes/obtains the exact commit object of a commit `C` already tracked under `org-victim`'s stack (e.g., because the victim repo is public, or was previously public, or the SHA leaked via CI logs, PR pages, etc.).
3. Attacker reconstructs an identical commit object (same tree, parent, author, committer, timestamps) in their own `org-attacker` repository (e.g. via `git commit-tree`/`git replace`/direct object push) so it has the identical SHA1 as `C`.
4. Attacker triggers/causes a GitHub `status` event for that commit in `org-attacker`'s repository (e.g., via their own CI reporting a `success` status), which GitHub signs with `org-attacker`'s `webhook_secret`.
5. `WebhooksController#verify_signature` looks up `org-attacker`'s app config from `repository_owner` in the payload and validates the HMAC — it succeeds because the payload really did come from `org-attacker`'s GitHub App. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches `C` in `org-victim`'s stack (SHA collision by construction), and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto `org-victim`'s commit. [5](#0-4) 
7. If `org-victim`'s `shipit.yml` gates deploys on that status context via `ci.require`, commit `C` now appears deployable, enabling an unauthorized deploy triggered by anyone with deploy access to `org-victim`'s stack, despite the attacker never having any credentials for `org-victim`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
