### Title
Frontmatter delimiter split allows attacker-influenced `pattern`/message text to silently downgrade `action: block` rules to `warn` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` splits the entire rule-file content on the literal 3-character substring `---` (`content.split('---', 2)`) instead of matching only lines that are exactly `---`, unlike the reference shell implementation in the repo that anchors with `^---$`. If a `---` sequence appears anywhere inside a frontmatter field value (e.g. an auto-generated `pattern:` derived from an attacker-influenced Bash command/text via `/hookify`'s conversation-analyzer flow), the parser treats it as the closing delimiter, truncating the parsed frontmatter dict before the `action: block` line is reached. Because `Rule.action` defaults to `"warn"` when the key is absent, a rule the maintainer intended to be blocking silently becomes non-blocking.

### Finding Description
`extract_frontmatter` (`plugins/hookify/core/config_loader.py:87-195`) requires the content to start with `---` and then does:
```python
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
``` [1](#0-0) 
This is a naive substring split with `maxsplit=2`: it does not require the delimiter to occupy its own line, so any inner occurrence of the 3 characters `---` (e.g., inside a `pattern:` value that itself contains `---`, or inside example text embedded in the frontmatter) is consumed as the second/closing delimiter. Everything after that point — including a later `action: block` line — is pushed into `message` and never parsed into the `frontmatter` dict.

`Rule.from_dict` then reads `action` with a default of `'warn'`:
```python
action=frontmatter.get('action', 'warn'),
``` [2](#0-1) [3](#0-2) 
so a truncated frontmatter block silently yields a `warn` rule instead of the intended `block` rule, and `RuleEngine.evaluate_rules` (`plugins/hookify/core/rule_engine.py:53-58`) routes it to `warning_rules` instead of `blocking_rules`, allowing the dangerous tool call to proceed with only a `systemMessage`, not a deny. [4](#0-3) 

Reachability: `/hookify` (`plugins/hookify/commands/hookify.md`) generates `.claude/hookify.{name}.local.md` files by asking an LLM/agent (`plugins/hookify/agents/conversation-analyzer.md`) to extract "pattern"/"context" text directly from the conversation, including literal attacker/user-supplied command text, and embed it into YAML frontmatter fields with no sanitation instructions for delimiter-breaking characters. [5](#0-4) [6](#0-5) 
If the extracted pattern/context text contains a `---` sequence (e.g., a Bash command like `curl ---evil` or any text with three consecutive dashes), the generated rule file's frontmatter is truncated before `action: block`, and the resulting rule silently becomes a `warn`-only rule at load time via `load_rule_file` → `extract_frontmatter` → `Rule.from_dict` (`plugins/hookify/core/config_loader.py:244-274`). [7](#0-6) 

No validation exists anywhere in `load_rules`/`load_rule_file` to detect that the frontmatter was truncated, or to warn that an expected `action: block` key was dropped; failures are swallowed generically (`except (ValueError, KeyError, AttributeError, TypeError)` etc.), and the hooks (`pretooluse.py`/`posttooluse.py`) always `exit(0)` regardless of outcome (fail-open by design), so there is no fallback enforcement. [8](#0-7) 

### Impact Explanation
This can silently degrade a maintainer's intended `block` rule (e.g., blocking `rm -rf`, exfil commands, `.env` edits) into a mere `warn`, allowing the dangerous `Bash`/`Edit`/`Stop` action to execute despite the deny-rule invariant. This matches "Unauthorized local command execution that bypasses Claude Code approval/deny controls," though the impact is scoped to hookify's own custom local-config enforcement layer, not Claude Code's core permission system.

### Likelihood Explanation
The primary trigger requires the rule file's frontmatter to be generated (or edited) with attacker/user-influenced text containing a literal `---` substring positioned before the `action:` line — this is plausible when `/hookify`'s conversation-analyzer pulls raw command/context text into `pattern:`/message fields, but it depends on the LLM agent verbatim-copying such a string into the frontmatter block before the `action` key, which is a probabilistic/generation-dependent condition rather than a fully deterministic attacker-controlled trigger. It is not reachable purely from "malformed YAML frontmatter delimiters" supplied externally without some role in authoring or influencing the rule file's frontmatter content order.

### Recommendation
Replace the substring-based split in `extract_frontmatter` with line-anchored delimiter detection (e.g., only treat a line that is exactly `---` after stripping trailing whitespace as a delimiter, matching the `^---$` semantics used in `parsing-techniques.md`/`parse-frontmatter.sh`). Additionally, make `Rule.from_dict` fail closed (reject/refuse to load, rather than default to `warn`) when a rule file appears malformed/truncated or when `action` is ambiguous for what looks like a security-relevant rule, and add an explicit warning/error when the parsed frontmatter dict lacks expected keys the file textually appears to contain.

### Proof of Concept
Unit test for `plugins/hookify/core/config_loader.py`:
```python
def test_inner_triple_dash_truncates_frontmatter_before_action():
    content = (
        "---\n"
        "name: block-rm\n"
        "event: bash\n"
        'pattern: "rm -rf ---force"\n'   # embeds literal '---'
        "action: block\n"
        "---\n"
        "Blocked!\n"
    )
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Expected (if parser were correct): action == 'block'
    # Actual (bug): action defaults to 'warn' because the inner '---' inside
    # `pattern` is consumed as the closing delimiter, pushing
    # "force\"\naction: block\n---\nBlocked!" into the message body.
    assert rule.action == "block", (
        f"Deny rule downgraded to '{rule.action}': "
        f"invariant 'deny rule must never be parsed into a non-blocking configuration' violated"
    )
```
Integration assertion: feed the same file into `load_rules(event='bash')`/`RuleEngine.evaluate_rules` with `tool_input={"command": "rm -rf /"}` and assert the response contains `hookSpecificOutput.permissionDecision == "deny"` (expected) versus the actual `systemMessage`-only warn response (observed bug).
