### Title
Stale delegate grants silently reactivate when the account NFT returns to the granting owner - (contracts/controller/src/storage/account.rs)

### Summary
CVE-2016-3067 is a "permissions not re-evaluated when the user identity changes" bug. XOXNO Lending has the same shape in its delegate model: `DelegateGrant` entries are stamped with the address that granted them (`granted_by`), so a transfer of the position NFT to a new owner makes the old owner's grants inert — but they are *not deleted*. If the NFT ever returns to the original owner (sale back, gift, transfer through an intermediary), `grant.granted_by == owner` is true again and every previously granted delegate silently regains full owner-level authority over the account without any new authorization.

### Finding Description
Ownership is resolved live from the position NFT (`try_account_owner` / `account_owner` in `contracts/controller/src/storage/account.rs:35-44`). Delegate checks go through `is_owner_or_delegate` in `contracts/controller/src/account.rs:115-127`:

```rust
active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
```

`get_delegates` (storage/account.rs:176-181) filters the stored `DelegateGrant` on `grant.granted_by == *owner`. The comment at storage/account.rs:224-225 explicitly acknowledges the reactivation risk: "Deletes stale grants but returns false, preventing those grants from reactivating if the NFT returns to their original owner." But that cleanup only runs inside `remove_delegate`, which requires `caller` to be the *current* NFT owner (`require_account_owner`, account.rs:143-148). NFT transfers happen entirely on the `position-nft` contract (`transfer`/`transfer_from`); the controller is never notified, so nothing purges `ControllerKey::Delegates(account_id)` on change of holder. There is no epoch, generation counter, or grant invalidation hook.

Attack path (single unprivileged flow, no privileged call):
1. Alice calls `controller::add_delegate(alice, account_id, M)` where `M` is an active governance-approved position manager (or a contract the attacker controls that has manager status).
2. Alice transfers the NFT to Bob via `position-nft::transfer`. The grant is now inert but still stored.
3. Bob never calls `remove_delegate` (he may not even know the grant exists — there is no obligation or incentive).
4. The NFT returns to Alice (Bob sells/gifts it back, or Alice uses a second address as Bob). `grant.granted_by == Alice` again → `M` is an active delegate with zero re-authorization.
5. `M` calls owner/delegate-gated entrypoints — `borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend` — on `account_id`, passing `require_owner_or_delegate` (account.rs:130-140) even though Alice intended the delegation to die with the transfer.

### Impact Explanation
A previously-revoked-in-spirit delegate regains spending authority over the account: it can draw new borrows against Alice's collateral, route swaps through attacker-chosen venues via the strategy entrypoints, and force collateral into unfavorable liquidations — theft of user funds. The damage is bounded only by `MAX_DELEGATES` stale managers per account and the account's collateral.

### Likelihood Explanation
Requires the NFT to round-trip back to the grantor, which happens naturally in any sale-and-repurchase or transfer-between-own-addresses flow. No timing race, no privileged assistance, and no victim action after step 4 — the grant reactivates purely from storage shape.

### Recommendation
Invalidate grants on any ownership change, not just on an owner-initiated `remove_delegate`. Options: store an owner/transfer-generation epoch in `AccountMeta` (bumped on the first controller touch after `owner` changes, with `DelegateGrant` keyed by that epoch), or have `try_account_owner` consumers detect `grant.granted_by != current_owner` and eagerly delete the key in `get_delegates` so reactivation is impossible even if `remove_delegate` is never called.

### Proof of Concept
1. `controller.add_delegate(alice, acct, manager_M)` — stores `DelegateGrant{granted_by: alice, delegates:[M]}`.
2. `position_nft.transfer(alice, bob, acct)` — `account_owner(acct) == bob`; `get_delegates(acct, bob)` returns empty (filter mismatch), grant still in storage.
3. `position_nft.transfer(bob, alice, acct)` — `account_owner(acct) == alice`; `get_delegates(acct, alice)` now returns `[M]` again.
4. `controller.borrow(M, acct, hub_asset, amount, ...)` passes `require_owner_or_delegate` — `M` was never re-authorized by Alice.
