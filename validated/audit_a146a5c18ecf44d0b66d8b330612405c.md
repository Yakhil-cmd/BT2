### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon repository is selected from the unrelated `repository.full_name` field, allowing a valid signature from one organization's app to authorize writes to any other organization's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports hosting multiple GitHub Apps, one per GitHub organization, each with its own `webhook_secret` [4](#0-3) . `WebhooksController#verify_signature` picks which organization's secret to verify the HMAC signature against by reading `repository_owner` from the **unverified** JSON body, before the signature has been validated [5](#0-4) :

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signature itself is only a keyed HMAC over the raw body (`OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message)` in `GitHubApp#verify_webhook_signature`), never over which secret was chosen. Once signature verification passes, the actual event handler (e.g. `PushHandler`) looks up the target `Repository`/`Stack` using a **separate** field of the same body — `repository.full_name` — via `Handler#repository_name` and `Handler#stacks` [2](#0-1) .

Because the attacker fully controls the JSON body (only the raw bytes are covered by the signature, not any binding between `repository.owner.login` and `repository.full_name`), an attacker who legitimately controls one onboarded GitHub organization (e.g. `OrgOne`, with its own real `webhook_secret`) can sign a payload with `repository.owner.login = "OrgOne"` (so it authenticates against `OrgOne`'s secret) while setting `repository.full_name = "OrgTwo/victim-repo"` (so the handler acts on a completely different organization's stack).

### Finding Description
The equality that should hold but doesn't: `organization whose webhook_secret authenticated the request == organization that owns the repository being written to`.

- **Before the attack**: `Shipit.github(organization: repository_owner)` uses `params.dig('repository','owner','login')` purely to pick a secret to verify against [6](#0-5) . This value is attacker-controlled and is never cross-checked against anything else in the payload.
- **After signature verification passes**: control flows to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create` [7](#0-6) , and handlers such as `PushHandler` resolve the target stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from `payload.dig('repository', 'full_name')` — a different JSON key than the one used for authentication [2](#0-1) .

Nothing in `GitHubApp#verify_webhook_signature` binds the signature to a specific repository or organization name — it only proves the raw bytes were signed by *some* known secret. Since the attacker who owns `OrgOne`'s installation controls the entire raw body they send (this is a real webhook delivery from their own GitHub App installation, not a forgery of GitHub's own signature), they can freely set `repository.full_name` to any other onboarded org/repo pair while keeping `repository.owner.login` set to their own org so the signature check passes.

### Impact Explanation
This breaks the tenant/organization isolation multi-GitHub-App configuration is meant to provide (`docs/setup.md`'s "Using Multiple Github Applications" section explicitly exists so that separate orgs cannot interfere with each other). A malicious or compromised organization admin who has legitimate access to configure/trigger their own GitHub App's webhook deliveries can:
- Trigger `PushHandler` for another organization's stack with an arbitrary `after` SHA, forcing `GithubSyncJob` to run against a foreign stack [8](#0-7) .
- Similarly manipulate `status`, `check_suite`, `pull_request`, `membership`, etc. handlers cross-organization, since all of them resolve their target via the same unverified `repository.full_name` (or `organization.login`) field rather than the field used for signature selection.

This is a cross-repository/cross-organization write achieved purely by crafting a payload — no `ApiClient` token, GitHub App private key, or repository write access to the *victim* org is required, only ownership of any one onboarded organization's app installation.

### Likelihood Explanation
Any organization admin capable of configuring their own onboarded GitHub App's webhook payload (a normal, low-privilege action within their own org) can construct and POST a payload directly to Shipit's `/webhooks` endpoint (this controller does not require a Shipit session or ApiClient — it's only gated by the HMAC signature) with mismatched `owner.login` / `full_name` fields.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or `organization.login`) and confirm it matches the organization whose secret authenticated the request, e.g.:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  return head(422) unless github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  return head(422) unless authenticated_owner_matches_target_repository?
  ...
end
```

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `OrgOne` and `OrgTwo`, each with its own installed app and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the operator of `OrgOne`'s GitHub App, craft a `push` event payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "deadbeef",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
   }
   ```
3. Sign the raw body with `OrgOne`'s real `webhook_secret` and set `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "OrgOne")` and verifies successfully.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgTwo/victim-repo")` and enqueues `GithubSyncJob` against `OrgTwo`'s stack, entirely without `OrgTwo`'s knowledge or consent.
