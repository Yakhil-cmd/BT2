### Title
Attacker-controlled swap route can inject an unauthorized token transfer into the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
XOXNO controller strategy calls accept caller-controlled `swap` route bytes and invoke the configured router while the caller’s authorization is active. Although the controller grants the router authority to transfer only the exact routed input amount, an unallowlisted contract addressed by the route can execute below that call and request `caller.require_auth()` for an unrelated token transfer. Soroban records this as a child of the caller’s controller authorization; if simulation returns that tree and the caller signs it, the host accepts the unrelated transfer. This maps the reported malicious-data/code-injection class onto XOXNO’s route-program execution path.

### Finding Description
`swap_tokens` snapshots the controller’s input and output balances, authorizes one exact input-token transfer to the configured router, and calls `router.execute_strategy(controller, amount_in, swap)` [1](#0-0) . The `swap` argument is opaque strategy data supplied through strategy entrypoints such as `swap_collateral`; it is not restricted by the controller to known pool or venue addresses [2](#0-1) . Consequently, route-selected contract code runs while the original caller’s authorization tree is being assembled.

A harness reproduction models this authorization behavior with a router that invokes the route-selected pool and a rogue pool that calls `token.transfer(victim, attacker, amount)` on an unrelated wallet token [3](#0-2) [4](#0-3) . Simulation records that unrelated transfer as a child of Alice’s `swap_collateral` authorization and executes it when she signs the returned tree [5](#0-4) . The same test shows that signing the poisoned child transfers the wallet token to the attacker [6](#0-5) .

The measured-output checks do not prevent this theft. They only verify that the controller spent no more than `amount_in` and received positive `token_out`; they do not bound what route-selected code asks the caller to authorize through a separate token contract [7](#0-6) .

### Impact Explanation
An attacker who gets a victim to execute an attacker-constructed route can steal tokens completely unrelated to the lending position, up to amounts present in the victim’s wallet and listed in the signed authorization tree. The route can still return a valid output and satisfy the controller’s measured receipt and solvency checks, so the transaction appears successful while performing the extra transfer. This is direct theft of user funds, not merely poor swap execution or route quality.

### Likelihood Explanation
The attacker must persuade the victim to sign a simulated transaction whose authorization tree contains the malicious child transfer. This is plausible where wallets or integrations display the root controller call but do not clearly expose every child authorization. No privileged role, leaked key, contract upgrade, malformed token, or dishonest oracle is required; the attacker only supplies a malicious route contract and payload. Because exploitation depends on victim transaction signing rather than purely permissionless execution against an existing authorization, this is High rather than Critical.

### Recommendation
Do not allow route payloads to select arbitrary executable contracts under a user-authorized strategy call. Restrict executable hop addresses to a governance-managed allowlist of known venue contracts, or restructure routing so venue calls cannot request additional authorization from the user’s root authorization tree. At minimum, the signed route should bind every executable address and every expected token authorization, and wallets/integrations must reject a controller strategy authorization containing any child beyond the exact expected input transfer. Ideally enforce this in-protocol rather than relying on client-side inspection.

### Proof of Concept
1. Alice supplies USDC and has a debt-free account. She also holds an unrelated token that the lending protocol does not list.
2. An attacker deploys a contract whose route hook calls `token.transfer(alice, attacker, alice_wallet_balance)` on that unrelated token.
3. The attacker constructs a strategy route that names the malicious contract as a hop while still producing enough output token to satisfy the controller’s positive-output and position-risk checks.
4. Alice calls `swap_collateral(account_id, usdc_key, amount_in, eth_key, malicious_swap_xdr)` and simulates it.
5. The controller authorizes only the exact USDC input transfer to the router, then invokes the route [8](#0-7) .
6. During route execution, the malicious contract invokes the unrelated token’s `transfer`, which calls `alice.require_auth()` and is recorded beneath Alice’s `swap_collateral` authorization [9](#0-8) .
7. Alice signs the returned authorization tree. The unrelated wallet token moves to the attacker while the controller still records the expected swap output [10](#0-9) [11](#0-10) .

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
