### Title
Cross-Repository CI Status Forgery in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` applies GitHub `status` webhook payloads to commits by matching only the commit SHA, with no check that the commit belongs to the repository whose organization signed the webhook. Every other webhook handler in the same directory (`PushHandler`, `CheckSuiteHandler`) scopes its side effects through `stacks`, which is derived from `payload.dig('repository', 'full_name')`. `StatusHandler` omits this scoping entirely, breaking the binding "organization authenticated by the webhook signature == repository whose commit status is written," which mirrors the reported CDP bug class where a caller-controlled field (`minter`) is acted on without verifying it against the authenticated principal.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/organization to verify the signature against using `repository_owner`, taken from the payload's `repository.owner.login` field, and rejects the request if the signature doesn't match that organization's webhook secret. [1](#0-0) 

Once verified, the controller dispatches the parsed payload to all handlers registered for the event, with no re-check that the handler's writes stay within the authenticated repository: [2](#0-1) 

The base `Handler` class exposes a `stacks` helper that scopes lookups to the repository named in the payload: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` correctly use this scoping before acting: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, queries `Commit` globally by `sha` alone, with no reference to `stacks`/`repository_name`, so it writes a CI status to any commit in the entire Shipit installation that happens to share that SHA, regardless of which repository/organization the signed webhook actually belongs to: [6](#0-5) 

Applying the status directly mutates commit/stack CI state and gates deploys: [7](#0-6) [8](#0-7) 

**Binding broken:** organization authenticated by `verify_webhook_signature` (via `repository_owner`) == repository whose `Commit` rows get a new `Status` written. Before the fix that other handlers apply, this equality is enforced (`stacks` filters by `repository_name`); in `StatusHandler` it is not enforced at all — any org with a valid webhook installation on this Shipit instance can push a `status` event that sets CI status on commits belonging to a different repository/stack, purely by matching SHA.

### Impact Explanation
CI status controls `Commit#schedule_continuous_delivery` and `enable_ci_on_stack`, which gate whether Shipit considers a commit deployable/mergeable in continuous-delivery-enabled stacks. An attacker who controls (or has push/admin rights to) any repository whose organization has the Shipit GitHub App installed pointed at the same Shipit instance can forge a `success` status for a commit SHA in a completely unrelated stack they have no access to, potentially unblocking or triggering an unauthorized deploy — matching the report's "Critical: unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be able to produce a validly-signed `status` webhook event for *some* organization/repository connected to the same Shipit instance (i.e., they need write access somewhere in the GitHub App's installation scope, but zero access to the victim stack/repository). No credentials from the victim stack are needed, and the only constraint is guessing/matching an existing SHA, which is feasible if the attacker can observe the target repository's public commit history (SHAs are not secret) and issue a `status` update referencing that SHA via GitHub's status API from their own controlled repo.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: restrict the query to commits belonging to `stacks` (derived from `payload.dig('repository', 'full_name')`) instead of a bare, repository-unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker has admin/write access to `attacker/repo`, whose GitHub organization has the Shipit GitHub App installed against the target Shipit instance (any org onboarded to this instance qualifies; the attacker does not need access to the victim's stack).
2. Attacker learns the SHA of a commit in `victim/repo` (public commit history) that Shipit is currently blocking from deploy due to a `pending`/`failure` status.
3. Attacker uses GitHub's Statuses API (`POST /repos/attacker/repo/statuses/{sha}`) to set state `success` for that SHA. GitHub delivers a signed `status` webhook for `attacker/repo`'s organization to `WebhooksController#create`.
4. `verify_signature` succeeds because the signature is valid for `attacker/repo`'s organization: `app/controllers/shipit/webhooks_controller.rb` lines 24-49.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (`app/models/shipit/webhooks/handlers/status_handler.rb` lines 20-24) and finds the matching commit in `victim/repo`'s stack, calling `create_status_from_github!` on it — writing a forged "success" status that was never scoped to, or authorized by, `victim/repo`'s organization.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
