## Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, allowing a stack-scoped token to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, bypassing the `stacks`/`stack` scoping helpers defined in `Shipit::Api::BaseController` that restrict lookups to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a single stack.

### Finding Description
`BaseController` defines the authorization-scoping binding that every other API controller relies on: [1](#0-0) 

This ensures a stack-scoped `ApiClient` (one created with a `stack_id`, e.g. the `here_come_the_walrus` fixture used for CCMenu tokens) can only resolve `stack`/`stacks` to the single stack it was authorized for — as exercised by the test `"an api client scoped to a stack will only see that one stack"`: [2](#0-1) 

`CCMenuController`, however, overrides `stack` and calls `Stack.from_param!` directly instead of going through the inherited, scoped `stacks` collection: [3](#0-2) 

`require_permission :read, :stack` (a `before_action`) only calls `current_api_client.check_permissions!('read', 'stack')`, i.e. it checks that the token *has* the `read:stack` permission string — it never checks whether the requested `stack` is the one the token is bound to: [4](#0-3) [5](#0-4) 

The equality that should hold for every stack-scoped endpoint is:
`stack requested via params[:stack_id]` == `stack authorized by current_api_client.stack_id` (when `current_api_client.stack_id?` is true).

For `Api::DeploysController`, `Api::RollbacksController`, `Api::StacksController`, etc., this equality is enforced because `stack` is resolved via `stacks.from_param!` (the scoped collection). In `Api::CCMenuController` it is not: `stack` is resolved directly against the global `Stack` relation, so a token scoped to stack A can view CCMenu output for any stack B, as long as it has the `read:stack` permission bit set (which is the default and only permission granted to CCMenu tokens, per `CCMenuUrlController#client`). [6](#0-5) 

### Impact Explanation
An `ApiClient` intentionally scoped to a single, presumably lower-sensitivity stack (this is exactly the scoping mechanism the codebase provides, exercised by the `here_come_the_walrus` fixture/token) can be replayed against `/api/stacks/:other_stack_id/ccmenu` to read build/deploy status (`stack.deploys_and_rollbacks.last`) for any other stack in the Shipit instance, including private or restricted stacks the token holder was never authorized to see. This is an unauthenticated-read/authorization-bypass class issue: it breaks the "a stack a token authorises versus a stack it touches" binding explicitly called out as in-scope, allowing cross-stack read of deploy/task state via a token that was only supposed to be usable for one stack.

### Likelihood Explanation
Any holder of a CCMenu token (these are routinely embedded in CI dashboard tools and are not treated as highly secret, and per `ccmenu_url_controller.rb` they are generated per-user/reused across stacks) can trivially exploit this by changing the `stack_id` segment of the URL. No special privilege beyond possessing one legitimately-issued, stack-scoped token is required, and the request needs no interactive session — just an HTTP GET with the known token.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` collection inherited from `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`, so that a token scoped to `current_api_client.stack_id` cannot resolve stacks outside that scope, consistent with `DeploysController`, `RollbacksController`, and `StacksController`.

### Proof of Concept
1. Attacker/legit CCMenu user obtains a stack-scoped `read:stack` `ApiClient` token for `stack_A` (e.g. via `GET /ccmenu/*stack_A` → `CCMenuUrlController#fetch`, which mints/reuses an `ApiClient` with `permissions: ['read:stack']`, `creator: current_user`, but does not persist a `stack:` association tying the client to `stack_A` in every path, and even if scoped, `CCMenuController` ignores it).
2. Attacker issues `GET /api/stacks/*stack_B/ccmenu?token=<token_for_stack_A>` where `stack_B` is a different stack the token was never meant to expose.
3. `authenticate_api_client` (overridden in `CCMenuController`) authenticates the token successfully via `ApiClient.authenticate(params[:token])`.
4. `require_permission :read, :stack` passes because the token has the `read:stack` permission string, with no check that `stack_B == current_api_client.stack`.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` directly against `stack_B`, and the controller renders `stack_B`'s latest deploy/rollback status — successfully leaking cross-stack build state to a token scoped for a different stack.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
