### Title
AA-based multi-asset vaults can permanently freeze all depositors' funds if a single oracle used for shared value calculations stops posting - (File: `formula/evaluation.js`)

### Summary
Autonomous Agents (AAs) in ocore can be written to pool deposits across several underlying assets/markets and expose a single withdrawal branch whose exchange-rate/valuation math depends on `data_feed[[...]]` calls to one or more oracle addresses shared by the whole pool. Because the `data_feed` formula operator aborts (bounces) the *entire* trigger response whenever the requested value cannot be found, an AA that computes a pooled share price atomically across all its underlying assets is fully "bricked" the moment any one of the referenced oracles stops posting — even for withdrawals that logically concern only the healthy assets in the pool. This mirrors the Sherlock M-16 finding for Perennial's `BalancedVault`, where a single failed market made `_maxRedeemAtEpoch` revert and blocked withdrawal of collateral for markets that were still healthy.

### Finding Description
In `formula/evaluation.js`, the `data_feed` operator is implemented so that if no matching feed value is found (and no `ifnone` fallback is supplied), it returns a fatal error that bounces the whole AA response: [1](#0-0) 

This same abort-on-missing-value behavior is explicitly relied upon in the shipped sample contracts, where the comment states "data_feed will abort if the exchange rate not posted yet": [2](#0-1) 

If an AA author builds a "balanced vault"-style AA that pools several assets and needs a *shared* valuation (e.g., total portfolio value or an aggregated exchange rate) to compute each user's proportional share on withdrawal, that valuation formula must reference the oracle(s) for every underlying asset. Because oscript formulas execute atomically per trigger and the whole response bounces on the first fatal error, a permanent stall of any single referenced oracle (compromised keys, discontinued feed, halted market) makes every subsequent withdrawal computation bounce, regardless of whether the requesting user's share is backed by the still-healthy assets. There is no built-in primitive in oscript for a "partial/emergency" per-asset withdrawal that bypasses the shared valuation step — the AA author would have to explicitly design one, exactly as recommended in the original report ("implement a partial/emergency withdrawal or acknowledge the risk clearly").

### Impact Explanation
Any AA implementing a pooled/diversified vault pattern (multiple assets, shared share-price calculation via `data_feed[[...]]`) inherits an all-or-nothing failure mode: the permanent unavailability of a single oracle used anywhere in the shared valuation path freezes every depositor's funds in the AA, not just those exposed to the broken asset. Since AA balances are pooled and controlled solely by the AA's own bytecode (there is no external/administrative bypass), this constitutes AA fund freezing for the entire user base of the vault, disproportionate to the actual risk any individual depositor should bear.

### Likelihood Explanation
This requires an AA author to deliberately design a multi-asset/multi-market vault with a single shared valuation formula spanning all oracles (a natural and common pattern, as shown in the shipped `futures_contract.oscript`/market-maker-style samples). Any trigger sender (ordinary user attempting to withdraw) then reaches the frozen state as soon as one of the underlying oracles permanently stops posting — a scenario outside the control of the AA or its users. No special privileges are needed to trigger the freeze; it is an emergent property of ordinary use once the oracle stalls.

### Recommendation
- Document explicitly (in AA/oscript developer guidance) that any `data_feed[[...]]` reference without an `ifnone` fallback can permanently bounce all future triggers that depend on it, and warn against building shared valuation formulas that span multiple independently-failing oracles.
- Encourage/require AA authors implementing pooled multi-asset vaults to isolate valuation and withdrawal logic per-asset where possible, or to provide an `ifnone` degraded-mode fallback (e.g., last known price, or a per-asset emergency withdrawal branch that does not require the failed oracle) so a single broken price feed cannot freeze deposits unrelated to it.
- Consider adding an oscript pattern/helper for "circuit-breaker" style partial withdrawals that do not require the aggregated/shared valuation path.

### Proof of Concept
1. An AA author defines a vault AA holding assets A and B, using a case such as:
   `if: "{$total_value = balance[base]*data_feed[[oracles='ORACLE_A', feed_name='A_PRICE']] + balance[assetB]*data_feed[[oracles='ORACLE_B', feed_name='B_PRICE']]; ...}"` to compute share price for withdrawal, following the same pattern as `test/samples/futures_contract.oscript` lines 69-93 which explicitly notes "data_feed will abort if the exchange rate not posted yet".
2. Users deposit into the vault and receive shares.
3. `ORACLE_B` (for asset B) is compromised or discontinued and permanently stops posting `B_PRICE`.
4. Any user attempting to withdraw — even one whose economic exposure is entirely in asset A — triggers evaluation of `$total_value`, which calls `data_feed[[oracles='ORACLE_B', ...]]`; since the value is never found, `formula/evaluation.js` (lines 644-663) causes the response to bounce with "data feed B_PRICE not found".
5. Because every withdrawal must go through the same shared `$total_value` formula, this bounce is permanent and universal: no depositor, including those unaffected by asset B, can ever withdraw again, unless the AA was designed in advance with a per-asset emergency exit path. [1](#0-0) [2](#0-1)
