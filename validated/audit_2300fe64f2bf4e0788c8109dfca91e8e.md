### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while handlers act on `repository.full_name` from the same untrusted payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/webhook secret to validate a delivery against using `repository_owner`, a value read directly out of the still-unverified JSON body [1](#0-0) . It then verifies the raw body against that org's secret [2](#0-1) , but the subsequent `create` action dispatches the *entire* parsed payload — including whatever `repository.full_name` the attacker put in it — to the event handlers [3](#0-2) , without re-checking that the resolved repository actually belongs to the organization whose secret was used to authenticate the delivery.

### Finding Description
Shipit supports multiple GitHub Apps/organizations configured with independent `webhook_secret` values, as shown by the `OrgOne`/`OrgTwo` fixture [4](#0-3)  and `Shipit.github(organization:)` lookup used in `verify_signature`. `verify_webhook_signature` trivially returns `true` when the resolved org has no `webhook_secret` configured [5](#0-4) .

Because `repository_owner` is derived from the same untrusted body (`params.dig('repository', 'owner', 'login')` or the `organization.login` fallback) *before* signature verification decides which secret to check, an attacker can craft a payload where `repository.owner.login` names an org that has no (or a known/weak) webhook secret configured, while `repository.full_name` (used later by the handlers, e.g. `GithubSyncJob`/status handlers, to resolve the actual `Stack`/`Repository` record) names a *different*, secret-protected repository. The equality that should hold — "organization whose secret authenticated the delivery" == "repository whose state gets mutated" — is broken: verification is bound to `owner.login`, while the handler side effects are bound to `full_name`, and nothing in `WebhooksController#create` or `#verify_signature` cross-checks the two.

### Impact Explanation
An unauthenticated network attacker (webhook endpoint requires no session/API token, `skip_before_action :verify_authenticity_token`) could forge push/status/check_suite/membership events for a protected repository by routing verification through an unprotected or attacker-known org config in the same Shipit install, then supplying a `repository.full_name` pointing at the protected repo. Depending on which handler runs, this can spoof commit statuses used for deploy gating, trigger sync jobs that write fabricated commits/refs into a tracked repository's stack, or inject team memberships — i.e., unauthorized writes to stack state without ever possessing the protected repository's real webhook secret.

### Likelihood Explanation
Requires: (1) the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration), and (2) at least one configured org lacks a webhook secret or its secret is otherwise attacker-obtainable. This is a plausible admin misconfiguration rather than the default single-org, secret-required setup, so likelihood is moderate rather than trivial.

### Recommendation
After resolving the target repository/stack from the payload, verify that its owning organization matches the `repository_owner` value that was used to select the verification secret; reject the webhook if they differ. Alternatively, always require and verify a webhook secret per organization and refuse any org with a blank secret unless explicitly opted in for local/dev testing only.

### Proof of Concept
Conceptual (not fully verified against handler internals due to a tool error in this session — flag for confirmation before treating as fully proven):
1. Configure Shipit with two orgs: `unsecured-org` (no `webhook_secret`) and `secured-org` (`webhook_secret: S`), both having repos tracked in the same Shipit instance.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
   ```json
   { "repository": { "owner": { "login": "unsecured-org" }, "full_name": "secured-org/protected-repo" }, "after": "<attacker-chosen-sha>", "ref": "refs/heads/main" }
   ```
   No `X-Hub-Signature` needed since `verify_webhook_signature` short-circuits to `true` for `unsecured-org` [6](#0-5) .
3. `WebhooksController#create` passes the full `params` (containing `secured-org/protected-repo`) to the registered push handlers [3](#0-2) , causing them to act on the protected repository despite the delivery never being authenticated with `secured-org`'s secret.

If a re-verification of this handler-side repository resolution shows it in fact keys strictly off `repository.owner.login` (matching the same field used for verification) rather than `full_name`, this analog would not hold — I was not able to confirm this with certainty in the available tool calls.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
