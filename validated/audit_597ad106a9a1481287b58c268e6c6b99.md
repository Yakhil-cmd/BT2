### Title
Webhook signature verification binds to `repository.owner.login` while the write path binds to `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / webhook secret to validate a request against based on `repository.owner.login` (or `organization.login`) parsed from the unauthenticated request body, `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`. But the handler that actually performs the write (`Handler#stacks`) resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`. The equality the code implicitly assumes — "the org whose secret verified this payload" == "the org/repo that gets written to" — is never enforced. This mirrors the ThrusterTreasure bug class: a field that is used to authorize an action (`_numWinners`/owner-derived secret) is decoupled from the field the action actually operates on (prize payout/`repository.full_name`).

### Finding Description
- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and looks up `Shipit.github(organization: repository_owner)` to get that organization's configured `webhook_secret`, then HMAC-verifies the raw body against it, `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally if the org has no `webhook_secret` configured, `lib/shipit/github_app.rb:76-83`. Leaving `webhook_secret` blank is a documented, supported configuration (`config/secrets.development.example.yml:11,24,33`, `test/dummy/config/secrets.yml:13`), which several setups use per-organization when multiple GitHub Apps are configured (`config/secrets.development.shopify.yml`).
- Once `verify_signature` passes (trivially, for an org with no secret), the actual event handler resolves the affected `Repository`/`Stack` purely from `repository.full_name` in the same JSON body (`Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`), with no check that this repository belongs to the organization that was used for signature selection.
- Consequence: in any multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` (an explicitly supported/documented configuration), an unauthenticated attacker can POST to `/webhooks` with `repository.owner.login` set to the secret-less org (so verification is skipped) and `repository.full_name` set to any other tracked repository (e.g., one belonging to an org that *does* have a secret). The handler will act on that other repository's stack, e.g. enqueue `GithubSyncJob`, create commit `Status` records, or drive the merge queue, `app/models/shipit/webhooks/handlers/push_handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/*`.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," matching the required High-impact class (unauthenticated write of stack/task state via forged webhook events) once a mixed-secret multi-org config exists. Handlers can create bogus commit statuses, trigger sync jobs, or manipulate merge-queue state (`merge_status`, `pull_request` handlers) for a repository/stack that the attacker was never authorized to speak for, without needing a Shipit session, ApiClient token, or GitHub credentials of the targeted org.

### Likelihood Explanation
Requires: (a) a multi-tenant Shipit install with `github:` configured for multiple organizations (documented, supported pattern), and (b) at least one of those organizations configured with a blank `webhook_secret` (also explicitly documented/allowed, e.g. `webhook_secret: # nil`). Given the setup docs treat `webhook_secret` as "(optional)" per-organization (`docs/setup.md:30`), this is a realistic operational configuration, not a theoretical one, and requires zero credentials from the attacker.

### Recommendation
- Do not select the signing/verification secret from an attacker-controlled field independent of the field used to resolve the target repository. Verify that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` used to select the webhook secret before trusting the payload.
- Do not allow `verify_webhook_signature` to return `true` unconditionally when `webhook_secret` is unset in any organization within a multi-org configuration; require a secret for every configured organization, or reject payloads whose target repository does not belong to the organization whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgA` (no `webhook_secret`) and `OrgB` (with `webhook_secret` set), each with tracked repositories/stacks.
2. Attacker (no credentials) sends `POST /webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature`, and body:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
     "after": "<attacker-chosen-sha>",
     ...
   }
   ```
3. `verify_signature` resolves `repository_owner = "OrgA"`, looks up `OrgA`'s `GitHubApp`, and since `OrgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature header, `lib/shipit/github_app.rb:76-83`.
4. `PushHandler` (subclass of `Handler`) resolves `stacks` from `repository.full_name = "OrgB/target-repo"`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`, and processes the forged push for `OrgB`'s stack, enqueuing `GithubSyncJob` with attacker-supplied `expected_head_sha` (analogous flow can be seen in `test/controllers/webhooks_controller_test.rb:23-32`).       return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
