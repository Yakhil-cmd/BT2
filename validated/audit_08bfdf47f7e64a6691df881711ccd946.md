### Title
Webhook organization used for signature verification is decoupled from the repository actually written, allowing forged CI status/push events to be injected across repositories when any configured GitHub org lacks a webhook secret - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using `repository_owner`, computed independently from the field (`repository.full_name`) that the actual event handlers use to select which `Repository`/`Stack` gets written to. These two attacker-controlled JSON fields are never bound to each other, and if any configured organization has no `webhook_secret` (a documented, supported configuration), the signature check is a no-op for that organization, letting an unauthenticated requester pick which secured repository is written to.

### Finding Description
`repository_owner` is derived purely from the untrusted JSON body, before any signature is verified: [1](#0-0) 

It is used only to pick which `GitHubApp` config (and thus which `webhook_secret`) to validate against: [2](#0-1) 

`verify_webhook_signature` is a deliberate no-op when the selected organization has no `webhook_secret` configured: [3](#0-2) 

This is a supported, documented setup — the docs and example secrets files explicitly allow `webhook_secret` to be blank/nil per organization: [4](#0-3) [5](#0-4) 

Crucially, once the request reaches a handler, the *repository being written to* is resolved from a completely separate field of the same unauthenticated body, with no requirement that it match `repository_owner`: [6](#0-5) 

Because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the target `Stack`) are independent, uncorrelated JSON fields, an attacker can set `repository.owner.login`/`organization.login` to any configured organization that has no `webhook_secret`, while setting `repository.full_name` to the full name of a stack belonging to a completely different, secured organization. The signature check trivially passes (`return true unless webhook_secret`), yet the handler dispatch for that event operates on the targeted, secured repository's `Stack`, e.g. the push handler: [7](#0-6) 

The same decoupling applies to the `status` event handler, which creates/updates a `Status`/`CommitStatus` record directly from unauthenticated payload fields (sha, state, description, context, target_url) scoped to whatever repository/commit `repository.full_name` resolves to, as exercised in: [8](#0-7) 

### Impact Explanation
This breaks the required trust binding: `organization that authenticated == repository that is written`. In a multi-organization Shipit deployment where at least one configured org has no `webhook_secret` (an explicitly documented, valid configuration, not a misconfiguration of the engine), an unauthenticated attacker can forge webhook deliveries that are dispatched against a *different, secured* organization's repositories/stacks. Via the `status` handler this allows injecting a fabricated "success" CI status for an arbitrary commit on a targeted stack, which can satisfy `require_ci`/deployability gates used elsewhere (e.g. `Api::DeploysController#create`'s `commit.deployable?` check), enabling an unauthorized deploy of a commit that never actually passed CI. This matches the "unauthorized deploy" impact category.

### Likelihood Explanation
Requires only that the operator has configured more than one GitHub organization/app (a supported and documented feature, see `secrets_double_github_app.yml`) and that at least one of those organizations has not set a `webhook_secret` — which the docs explicitly present as optional. No credentials, sessions, or repository access are needed by the attacker; the `/webhooks` endpoint is unauthenticated by design and reachable by anyone who can reach the Shipit instance.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization (fail closed instead of `return true unless webhook_secret`).
- Cryptographically or structurally bind the organization used to verify the signature to the repository/stack the handler subsequently writes to (e.g., re-derive `repository_owner` strictly from `repository.full_name`'s owner segment, and reject payloads where `organization.login` and `repository.owner.login` disagree, or where the verified org doesn't own the target repository).

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `SecuredOrg` (has `webhook_secret` set, owns stack `SecuredOrg/critical-repo`) and `OpenOrg` (no `webhook_secret` set), per the multi-org config format in `config/secrets.development.shopify.yml`/`secrets_double_github_app.yml`.
2. Send an unauthenticated `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<commit sha on SecuredOrg/critical-repo>",
  "state": "success",
  "description": "forged",
  "context": "ci/forged",
  "target_url": "https://evil.example.com",
  "repository": { "full_name": "SecuredOrg/critical-repo", "owner": { "login": "OpenOrg" } }
}
```
3. `verify_signature` resolves `repository_owner` = `"OpenOrg"`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of any (or no) `X-Hub-Signature` header.
4. `StatusHandler` processes the event against `repository.full_name` = `"SecuredOrg/critical-repo"`, creating a forged successful CI status on a commit the attacker never actually built, which can then be used to satisfy CI gating for an unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
