### Title
Unauthorized `DepositDelegatorRewards` permanently blocks victim vote-account withdrawal/close because `pending_delegator_rewards` is never decremented - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
`deposit_delegator_rewards` allows *any* unprivileged signer to increase a victim vote account's `pending_delegator_rewards` field without the vote account's authorized withdrawer's consent, simply by naming the victim's vote account and transferring lamports into it. `withdraw` unconditionally rejects any withdrawal that would leave `remaining_balance == 0` while `pending_delegator_rewards > 0`, and no code path in the entire vote/reward pipeline ever decrements `pending_delegator_rewards`, making this a permanent, attacker-triggerable denial of the victim's ability to fully withdraw or close their own vote account.

### Finding Description
`deposit_delegator_rewards` in [1](#0-0)  only requires the *source* account to sign (`verify_authorized_signer(&source_address, signers)`); it performs no check that the caller is the vote account's authorized withdrawer or otherwise controls the vote account named in `vote_account_index`. Any attacker can invoke `VoteInstruction::DepositDelegatorRewards` naming an arbitrary initialized V4 vote account belonging to a victim and transfer even 1 lamport, which unconditionally increments `pending_delegator_rewards` via `add_pending_delegator_rewards` ( [2](#0-1) ).

`withdraw` in [3](#0-2)  checks `pending_delegator_rewards` *before* the `reject_active_vote_account_close`/`epoch_credits` logic, and unconditionally rejects any withdrawal that would zero the account:
```
if remaining_balance == 0 {
    if pending_delegator_rewards > 0 {
        return Err(InstructionError::InsufficientFunds);
    }
    ...
}
```
A repo-wide search for all writes to `pending_delegator_rewards` shows the only production code paths are: initialization to 0 (`VoteStateV4::new`) and increment via `add_pending_delegator_rewards` in `deposit_delegator_rewards`. No production code (vote program, `runtime/src/bank/partitioned_epoch_rewards/*`) ever decrements or resets `pending_delegator_rewards`; the only place it is set back to 0 is inside unit tests (e.g. [4](#0-3) ) which directly mutate account state and are not reachable from any instruction. `calculate_block_reward` ( [5](#0-4) ) only *reads* `pending_delegator_rewards` to compute a distribution amount; the resulting `block_reward` is credited to the stake accounts in `build_updated_stake_reward` ( [6](#0-5) ), but there is no corresponding debit of the vote account's lamports or of its `pending_delegator_rewards` field anywhere in `distribution.rs`.

Consequently, once any attacker sets `pending_delegator_rewards > 0` on a victim's vote account, `withdraw` will forever return `InstructionError::InsufficientFunds` for any attempt to bring the account to zero balance/deinitialize it, and the partial-withdraw branch also permanently reserves `pending_delegator_rewards` lamports (`min_balance = min_rent_exempt_balance + pending_delegator_rewards`), so the reserved amount can never be recovered by the legitimate authorized withdrawer.

### Impact Explanation
This is a permanent, unprivileged, victim-targeted denial of service against a vote account: the legitimate authorized withdrawer can never fully close/deinitialize the vote account, and a portion of its lamports (`pending_delegator_rewards`) becomes permanently unwithdrawable. This matches the "permanently frozen accounts" bounty category for vote accounts described in scope.

### Likelihood Explanation
Highly feasible and fully unprivileged: requires only SIMD-0123 active, the victim vote account initialized as V4, and one `DepositDelegatorRewards` transaction from any funded attacker account naming the victim's vote account and transferring as little as 1 lamport. No signature or authorization from the victim is required. The lock is permanent because no reachable instruction decrements `pending_delegator_rewards`.

### Recommendation
- Restrict `deposit_delegator_rewards` to only be invocable via privileged/program-controlled call sites (e.g. verify caller is the stake/reward-distribution program or add an explicit allow-list), or require the vote account's authorized withdrawer/node authority to co-sign/approve deposits.
- Implement an explicit, audited decrement of `pending_delegator_rewards` as part of the reward-distribution flow (`store_stake_accounts_in_partition`/`build_updated_stake_reward`) whenever `block_reward` is actually paid out of the vote account, ensuring the vote account's lamports and `pending_delegator_rewards` are debited in lock-step with `calculate_block_reward`'s computed amount.
- Add a unit/integration test asserting that after full reward distribution, `pending_delegator_rewards` returns to 0 and `withdraw` can fully close the account.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
