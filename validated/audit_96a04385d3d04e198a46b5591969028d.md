### Title
Attacker-pushed commit content can cause `SyncRepo` to fail indefinitely, permanently halting synchronization ([File: main.go])

### Summary
Analogous to the beacon-chain bug where a single invalid Deposit signature causes the state-transition function to hard-error and block every subsequent proposer, `git-sync`'s `SyncRepo` has no mechanism to skip a "bad" upstream commit. If the tracked ref's HEAD (attacker-controlled repo content) points to a commit that makes checkout/submodule/configuration steps fail, `SyncRepo` returns a hard error on every single sync loop iteration forever, because the same broken commit is re-fetched and re-attempted every time with no fallback or skip logic.

### Finding Description
`SyncRepo` fetches the current remote HEAD for the configured ref and, if it differs from what's currently published, creates a new worktree and configures it via `configureWorktree` (submodule update, sparse-checkout, `reset --hard`): [1](#0-0) 

`configureWorktree` propagates any failure from git subcommands (`sparse-checkout init`, `reset --hard`, `submodule update --init [--recursive]`) directly as a hard error with no retry-with-fallback or skip-and-continue logic: [2](#0-1) 

Because `fetch()` in `SyncRepo` always pulls whatever the remote ref currently resolves to, and there is no state that marks a specific commit as "known-bad" to skip, every subsequent loop iteration re-fetches the identical malicious/broken commit and re-attempts (and re-fails) the exact same operation: [3](#0-2) [4](#0-3) 

This failure is caught in the outer sync loop, which increments `failCount` and eventually calls `os.Exit(1)` once `--max-failures` is reached, crash-looping the container while never publishing any update: [5](#0-4) 

The previously published symlink target (last good worktree) is left untouched, so existing consumers keep the stale content, but no forward progress is ever possible until an operator intervenes (e.g., force-pushing a fix upstream, or raising `--max-failures`) — mirroring the "each next proposer will be unable to propose a block" cascading-halt pattern in the source report, translated to "each next sync attempt will fail identically forever."

### Impact Explanation
This satisfies the "persistent sync denial" impact criterion: an untrusted, attacker-controlled commit (pushed to the tracked branch/tag that `git-sync` follows) can permanently stall the sidecar's ability to deliver new content, and can additionally force the container into a crash-loop once the failure counter exceeds `--max-failures`, requiring manual operator remediation. No file corruption outside `--root`, credential leak, or code execution is achieved — only availability of the sync pipeline is affected.

### Likelihood Explanation
Likelihood depends on the attacker's ability to push such a commit to the repository/ref that `git-sync` is configured to follow (the "attacker-pushed commit" scenario from the rules). Any commit whose checkout, submodule initialization, or sparse-checkout application legitimately fails under git (e.g., an invalid/unreachable submodule URL, a corrupted object, or a sparse-checkout pattern conflict) will trigger this every single sync cycle, since `git-sync` performs no content-level pre-validation or single-bad-commit skip logic before treating checkout failures as fatal to the whole sync attempt.

### Recommendation
Introduce a bounded skip/backoff-to-last-good-state mechanism analogous to the recommended Ethereum fix: when `configureWorktree` (or the underlying checkout/submodule/sparse-checkout step) fails for a specific target hash, do not retry that identical hash indefinitely as a blocking condition. Instead, log/alert distinctly, keep serving the last known-good published worktree (already the current behavior), and consider tracking the failing hash so it isn't silently retried at the same fixed cadence with the same fatal-after-N-failures behavior — or clearly surface via metrics/readiness that the sidecar is stuck on a specific bad commit so operators can distinguish "transient network failure" from "poisoned ref requiring upstream remediation."

### Proof of Concept
1. Configure `git-sync --repo=<attacker-writable-or-influenced-repo> --branch=main --root=/git --link=current`.
2. Attacker pushes a commit to `main` that introduces a `.gitmodules` entry with a submodule URL that will fail during `git submodule update --init` (e.g., pointing to an unreachable host), or a tree/blob that fails `git reset --hard` (e.g., a path git refuses to check out on the underlying filesystem).
3. `git-sync`'s next `SyncRepo` cycle fetches this new HEAD (`fetch()` at [6](#0-5) ), detects `changed`, creates a worktree, and calls `configureWorktree`, which fails at the submodule/reset step.
4. `SyncRepo` returns the error; the main loop logs `"error syncing repo, will retry"` and increments `failCount`; every subsequent loop repeats the exact same fetch/checkout/failure sequence since the remote ref is unchanged.
5. Once `failCount >= --max-failures`, `main.go` calls `os.Exit(1)`, and the container crash-loops indefinitely until the malicious commit is reverted or removed upstream.

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}
