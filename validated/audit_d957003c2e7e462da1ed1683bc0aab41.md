### Title
Cross-tenant forged commit statuses via organization/repository binding mismatch in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook using the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`), but the downstream event handlers act on data that is not bound to that same organization/repository. For the `status` event in particular, `StatusHandler#process` looks up commits **globally by SHA alone**, with no repository scoping at all, letting an attacker who controls a legitimately onboarded (but unrelated) GitHub organization forge CI status for any commit SHA hosted under any other tenant of the same Shipit instance.

### Finding Description
`verify_signature` computes the org used for HMAC verification purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

The signature check (`GitHubApp#verify_webhook_signature`) only proves that *some* HMAC secret configured for the organization named in `repository.owner.login` was used to sign the raw body — it says nothing about which repository's data the body actually contains: [3](#0-2) 

Once signature verification passes, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, whose `process` method resolves target `Commit` records purely by `sha`, with no join or filter on `repository`/`stack` ownership: [4](#0-3) 

`Commit.where(sha: params.sha)` is an unscoped, instance-wide query — SHAs are not unique per-tenant in this schema (only unique in combination with `stack_id` conceptually), so any commit anywhere in the Shipit database whose SHA matches the attacker-chosen value will be updated: [5](#0-4) 

Compare this to the other handlers (`PushHandler`, `PullRequest::*Handler`), which correctly derive the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`Handler#repository_name`, scoping all downstream effects to the repository named in the payload: [6](#0-5) [7](#0-6) 

The binding broken is: **`organization authenticated by verify_signature` ≠ `repository/commit actually written by the handler`**. Nothing forces `repository.owner.login` (used to select the verifying secret) to correspond to the `repository.full_name`/`sha` that the handler subsequently mutates. For `status`, the mismatch is total — the handler does not even reference `repository.full_name`, only `sha`.

Before the attacker's request: the victim's commit (in `victim-org/victim-repo`, a stack on the same multi-tenant Shipit instance) has whatever CI status GitHub actually reported (e.g., pending/failure). Requirement: it be `success` and unlocked for the stack to be `deployable?`.

After the attacker's request: `attacker-org` (an org the attacker legitimately administers and for which they therefore know the GitHub App's `webhook_secret`, since App owners set that secret themselves) sends a POST to the webhooks endpoint with `X-Github-Event: status`, `X-Hub-Signature` computed with their own `webhook_secret`, and a body whose `repository.owner.login` = `"attacker-org"` but `sha` set to the victim commit's SHA and `state` = `"success"`. Signature verification passes (it only checks the attacker's own secret against the attacker's own org name in the payload). `StatusHandler` then matches `Commit.where(sha: ...)` against the victim's commit row (found solely by SHA, cross-tenant) and calls `create_status_from_github!`, injecting a forged "success" status: [8](#0-7) 

### Impact Explanation
A forged `success` status directly feeds `Commit#deployable?`, which gates whether a commit can be shipped/continuously delivered: [9](#0-8) 
and also triggers `schedule_continuous_delivery`, which can enqueue a `ContinuousDeliveryJob` for the victim stack once the (forged) status makes the commit deployable: [10](#0-9) 

This lets an attacker who legitimately owns one tenant's GitHub App/organization within a multi-org Shipit instance falsify CI results for an unrelated tenant's commit, unlocking an **unauthorized deploy/continuous-delivery** of a commit that never actually passed its real CI checks — satisfying the "unauthorized deploy" bar in the rules. This is High/Critical depending on whether continuous deployment is enabled for the victim stack, since it can result in code that never passed CI being shipped to production without any legitimate deploy authorization on the victim repo.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications"), and (2) the attacker legitimately administers one such onboarded organization (and thus knows its own `webhook_secret`, since that secret is chosen by whoever creates the GitHub App). No access to the victim org, no `ApiClient` token, and no Shipit session is required — only knowledge of the target commit's SHA (public if the victim repo is public, or discoverable via Shipit's own UI). This is a realistic scenario for any shared/multi-tenant Shipit deployment.

### Recommendation
In `StatusHandler` (and any other handler that trusts payload-provided identifiers), scope the lookup by the repository named in the payload, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` instead of a global `Commit.where(sha:)`. More fundamentally, `WebhooksController#verify_signature` should also assert that the organization used to authenticate the signature is consistent with the repository being acted upon (i.e., cross-check `repository.owner.login` derived org against the resolved `Repository`'s stored owner) before dispatching to handlers.

### Proof of Concept
1. Attacker administers `attacker-org`, onboarded into a shared Shipit instance alongside `victim-org` (per `docs/setup.md` multi-org config), and knows `attacker-org`'s `webhook_secret`.
2. Attacker finds the SHA of a commit on a `victim-org/victim-repo` stack tracked by the same Shipit instance (public repo or visible via Shipit UI).
3. Attacker crafts JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required",
  "repository": {"owner": {"login": "attacker-org"}}
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and POSTs to the webhooks endpoint with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully against the attacker's own known secret — see `app/controllers/shipit/webhooks_controller.rb#L24-30` and `lib/shipit/github_app.rb#L76-83`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit purely by SHA (`app/models/shipit/webhooks/handlers/status_handler.rb#L20-24`, `app/models/shipit/commit.rb#L11-16`), creating a forged `success` status on it regardless of which org authenticated the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
