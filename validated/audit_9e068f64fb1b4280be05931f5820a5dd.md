### Title
Webhook signature verification authenticates `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug-class analog to the deposit-contract frontrunning report is a "field acted upon but not covered by the trust check that authorized the action." Here, the org whose secret is checked (`repository.owner.login`) is not the org whose repository is actually written to (`repository.full_name`), because both come from the same attacker-controlled JSON body and are never cross-validated against each other.

### Finding Description
`WebhooksController#verify_signature` reads `repository_owner` straight out of the untrusted, not-yet-verified JSON body to decide which `Shipit.github(organization:)` app (and therefore which `webhook_secret`) must validate the HMAC signature: [4](#0-3) . Once that HMAC check passes, `create` parses the same raw body and dispatches it to handlers [5](#0-4) .

Every handler that mutates state (`push_handler.rb`, `status_handler.rb`, `pull_request/*`, `check_suite_handler.rb`) inherits `stacks`/`repository_name` from the base `Handler`, which looks up the target `Stack` using `payload.dig('repository', 'full_name')` — a *different* JSON key than the one used to select the verifying secret: [1](#0-0) .

Because both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside a single JSON body, an attacker who legitimately owns a GitHub org/repo integrated with this Shipit instance (and therefore knows/can compute a valid HMAC using their own org's `webhook_secret`, exactly the way a validator legitimately owns its signing key in the deposit-contract analog) can craft a payload where:
- `repository.owner.login` = the attacker's own org (so `Shipit.github(organization: repository_owner)` picks the attacker's own webhook_secret and the HMAC — computed over the attacker's own payload — verifies successfully), while
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler resolves and mutates the victim's `Stack`).

This mirrors the reported binding break exactly: "an organization that authenticated versus the repository that is written."

### Impact Explanation
A successful forged delivery lets an external, unprivileged attacker (who only administers their own unrelated GitHub org/app registered with this Shipit instance) inject fabricated `push`, `status`, `check_suite`, or `pull_request` events against a victim organization's stack. Depending on handler, this can: fabricate commits/CI status used by `MergeRequest#reject_unless_mergeable!`/`all_status_checks_passed?` to bypass CI gating and get bad code merged or deployed (cross-repository, cross-organization write with unauthorized effect on ship/merge decisions), or falsify team/membership state via `membership_handler.rb`. This lines up with the report's High/Critical criteria: escalation into repository state that should only be writable by an authenticated owner of that specific repository, and can lead to an unauthorized deploy/merge decision downstream.

### Likelihood Explanation
Requires the attacker to control (or register) at least one GitHub organization/App entry that this specific Shipit instance already trusts (has a `webhook_secret` configured for) — a real but non-trivial precondition, similar to how the deposit-contract issue required the validator to be malicious/attacker-controlled. Once that precondition holds, forging the cross-repository payload is trivial (just set two independent JSON fields inconsistently) and requires no session, no `ApiClient` token, and no privileged Shipit account.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the acting organization strictly from the verified `repository_owner`/`organization.login` used for secret selection, and require `payload.dig('repository', 'full_name')` (and any org login embedded in nested handler logic) to match that same, already-authenticated organization before any `Handler` is allowed to resolve or mutate a `Stack`/`Repository`. Reject the delivery (422) if the two disagree.

### Proof of Concept
1. Attacker registers/owns GitHub org `attacker-org`, which is configured in this Shipit instance with `webhook_secret = S`.
2. Attacker computes `sha1=HMAC(S, body)` over a crafted JSON body where `body['repository']['owner']['login'] = "attacker-org"` but `body['repository']['full_name'] = "victim-org/victim-repo"`, event header `X-Github-Event: status`.
3. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the HMAC validates because the attacker legitimately knows `S` [3](#0-2) .
4. `create` dispatches to `Shipit::Webhooks.for_event('status')`, whose handler calls `stacks`, which resolves via `Repository.from_github_repo_name("victim-org/victim-repo")` [1](#0-0) , and the forged status is recorded against the victim's commit/stack.

Note: I could not fully trace every downstream handler-specific mutation path (e.g., exact GitHub API calls triggered per event type) within the available index; a Devin session with full repo access would be needed to enumerate every affected handler and confirm the complete blast radius.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
