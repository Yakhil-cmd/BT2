## Title
Webhook signature is verified against `repository.owner.login`, but writes are scoped by `repository.full_name` / global `sha` — cross-repository forgery of commit statuses and stack syncs - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App's `webhook_secret` to check the HMAC against using `repository_owner`, taken from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0)  Once the signature is accepted, every registered `Handlers::Handler` subclass determines *what* to write using a different, independently-controlled field of the same JSON body: `payload.dig('repository', 'full_name')` for `Repository.from_github_repo_name` lookups, [2](#0-1)  or, in the case of `StatusHandler`, no repository scoping at all — just a global `Commit.where(sha: params.sha)` lookup. [3](#0-2) 

### Finding Description
This is the same bug class as the `RemoraToken` report: the code checks/authenticates one thing (`from`'s whitelist status / unlock amount using `value`, the full transfer amount) but acts on a different, independently derived quantity (unlocking `value` instead of the true deficit), causing the two to diverge. Here the divergence is between the field used to select the *authenticating secret* (`repository.owner.login` / `organization.login`) and the field(s) used to select the *target of the write* (`repository.full_name`, or nothing at all for `StatusHandler`).

`Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` config, each with its own `webhook_secret`, exactly as documented for multi-org deployments. [4](#0-3)  Nothing in `WebhooksController` or `Handler` ties the org whose secret validated the signature to the repository the handler subsequently mutates:

- `PushHandler`/other handlers resolve `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository','full_name')`. [2](#0-1)  An attacker who controls one configured organization ("attacker-org", with its own GitHub App and thus its own known `webhook_secret`) can set `repository.owner.login = "attacker-org"` (so `verify_signature` picks attacker-org's secret and the HMAC computed by the attacker over their own crafted body validates) while setting `repository.full_name = "victim-org/victim-repo"`. The handler then acts on stacks belonging to `victim-org/victim-repo`, a repository the attacker has no relationship with. [5](#0-4) 
- `StatusHandler` is worse: it never consults `repository` at all, matching purely by `sha` across the entire installation. [3](#0-2)  Any org whose webhook secret the attacker knows lets them forge a `status` event that creates a commit status via `commit.create_status_from_github!(params)` on *any* commit belonging to *any* stack in the whole Shipit instance, regardless of repository ownership.

This breaks the binding the deployment trusts: `organization authenticated (secret owner) == repository/commit actually written`.

### Impact Explanation
For `StatusHandler`, forging arbitrary CI statuses (`success`/`failure`) on commits belonging to repositories the attacker doesn't own can satisfy `ci.require` checks configured in another team's `shipit.yml`, unblocking or masking failed CI and enabling an **unauthorized deploy** of that victim stack — a Critical-tier impact per the engine's own criteria. For `PushHandler`, forcing `stack.sync_github` on an unrelated victim stack can trigger stack state refresh / continuous-deployment flows on a repository the attacker has no legitimate access to.

### Likelihood Explanation
Requires the attacker to control (be able to set the webhook secret for) at least one of the GitHub organizations configured in Shipit's multi-org `github:` secrets block — a realistic scenario in any Shipit install serving multiple orgs/teams, since each org's GitHub App admin independently manages that org's `webhook_secret` yet all webhooks land on the same shared `/webhooks` endpoint and shared `Commit`/`Repository` tables. No GitHub App private key, `ApiClient` token, or Shipit session is required — only knowledge of one legitimately-issued webhook secret for any onboarded organization.

### Recommendation
After signature verification, re-derive the acting repository from the same field(s) used to select the verifying secret (`repository.owner.login`/`organization.login`) and require it to match `repository.full_name`'s owner before dispatching to handlers; reject the webhook otherwise. `StatusHandler` (and any other handler that doesn't already scope by `repository.full_name`) must additionally filter `Commit.where(sha: ...)` by the repository resolved from the verified organization, not by `sha` alone.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.example.yml` multi-org example).
2. Attacker, who administers `attacker-org`'s GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success"
   }
   ```
   signing the raw body with `attacker-org`'s known `webhook_secret` in `X-Hub-Signature`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and validates successfully. [6](#0-5) 
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — which finds the victim commit regardless of repository — and calls `create_status_from_github!`, forging a CI status on `victim-org/victim-repo`'s commit. [3](#0-2)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
