### Title
Unbounded in-memory buffering of `git` subprocess output enables remote memory-exhaustion DoS - (File: pkg/cmd/cmd.go)

### Summary
`git-sync`'s command runner captures the entire stdout and stderr of every invoked `git` subprocess into unbounded, dynamically growing `bytes.Buffer` objects with no size cap. Several of these invocations (most notably `git fetch`) operate on content that is fully controlled by the remote repository owner/pusher — the entity `--repo` points at. A malicious or compromised upstream repo can be crafted to make `git` emit an extremely large amount of output (e.g., via a huge number of refs/branches combined with `--verbose`), which `git-sync` reads entirely into memory before it can even inspect or reject it, analogous to the CKB advisory's pattern of accumulating untrusted, attacker-influenced data into an unbounded in-memory collection.

### Finding Description
All git subprocess execution funnels through `runWithStdin` in [1](#0-0) , which allocates two `bytes.Buffer` instances (`outbuf`, `errbuf`) and wires them as `cmd.Stdout`/`cmd.Stderr`: [2](#0-1) 

There is no `io.LimitReader`, size cap, or streaming/discard mechanism — the buffers grow to accommodate however much data the subprocess writes, and the full contents are then materialized as Go `string`s (`outbuf.String()`, `errbuf.String()`), doubling the resident memory footprint of that output.

This is invoked by `git.fetch`, which runs `git fetch <repo> <ref> --verbose --no-progress --prune --no-auto-gc [...]` against the untrusted, attacker-controlled `--repo` on every sync cycle: [3](#0-2) 

`git fetch --verbose` output size scales with the number of refs/branches and objects on the remote — entirely under the control of whoever owns or can push to the tracked repository. An attacker who controls the source repository (a scenario explicitly in-scope, as `git-sync`'s whole purpose is syncing from a repo whose content is "untrusted" in the threat model, e.g. a webhook-triggered sync of a shared/multi-tenant repo) can inflate this output arbitrarily (e.g., pushing tens of thousands of branches/tags) to force `git-sync` to buffer gigabytes of verbose fetch output per sync attempt, repeated on every `--period` tick.

This mirrors the root cause of the CKB advisory: an operation over externally-supplied/attacker-influenced data accumulates results into an unbounded in-memory container without any deduplication, cap, or streaming discard, before the data is used or discarded.

### Impact Explanation
Because `runWithStdin` is the single choke point for all `git` invocations and has no output-size ceiling, a hostile upstream repository (or a compromised legitimate one) can drive the `git-sync` process's memory usage arbitrarily high, purely through the content/shape of refs it exposes over the network. Since `git-sync` re-runs `fetch` on every sync period, this is not a one-shot memory spike but a sustained, repeated allocation pattern, and can result in OOM-kill of the sidecar container, causing persistent sync denial for the workload depending on it — matching one of the explicitly accepted impacts ("persistent sync denial").

### Likelihood Explanation
Reaching this path requires no special privileges beyond controlling (or compromising) the content of the repository that `--repo` points to, which is the normal operator-configured, but externally-hosted and often shared/multi-tenant, sync target. No flags beyond the default `git fetch` invocation are required to trigger buffering of verbose output; `--depth`/`--filter` reduce object transfer but do not bound the size of the verbose ref-listing text itself, which scales with the number of refs on the remote regardless of shallow/partial clone settings.

### Recommendation
- Cap the amount of output captured from `git` subprocesses in `runWithStdin` (e.g., wrap `cmd.Stdout`/`cmd.Stderr` with a bounded writer that truncates or errors past a configurable limit, such as via `io.MultiWriter` combined with a counting/limiting `io.Writer`).
- Avoid `--verbose` on `git fetch` in production paths, or discard/stream stderr instead of buffering it fully when it is only used for logging.
- Consider streaming subprocess output to a temp file with a size cap instead of an unbounded in-memory buffer, especially for commands whose output size is a function of untrusted repository content (fetch, ls-remote, log).

### Proof of Concept
1. Stand up an upstream git server (`file://` or `http://`) that the attacker controls or can push to.
2. Push a very large number of branches/tags to that repo (e.g., 100k lightweight refs), each requiring negligible on-disk storage but expanding the `git fetch --verbose` ref-update summary line-count proportionally.
3. Point `git-sync --repo=<attacker-repo> --root=... --link=...` at it.
4. Observe that `runWithStdin` in `pkg/cmd/cmd.go` (invoked from `git.fetch` in `main.go`) buffers the entire verbose fetch output into `outbuf`/`errbuf` in memory before returning, with RSS growing roughly linearly with the number of refs the attacker pushed, and repeating on every `--period` sync tick.

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
}

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}
