### Title
Cross-repository `Status` forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up `Commit` records by `sha` alone, with no filter tying the match back to the repository whose `webhook_secret` authenticated the request. Because git commit SHAs are content-addressed and can be identical across independently-owned repositories (via forks/shared history or fabricated commit objects), an attacker who controls repository A can send a validly-signed status webhook for A that writes a `Status` onto a `Commit` belonging to an unrelated stack tracking repository B, without ever authenticating against B.

### Finding Description
The broken binding is: `payload.dig('repository', 'full_name')` (the org verified by `webhook_secret` in `WebhooksController#verify_signature`) should equal `commit.stack.repository.full_name` for every `Commit` mutated by the handler. It never does.

`WebhooksController#verify_signature` derives `repository_owner` from the payload and checks the signature against `Shipit.github(organization: repository_owner)`'s secret: [1](#0-0) 
This only proves the request came from GitHub on behalf of the org named in `payload['repository']['owner']['login']` — i.e., the attacker's own org A, since GitHub computes this signature itself when the attacker triggers a delivery for their own repository.

The base `Handler` class provides a `stacks` scoping helper based on `repository_name` (`payload.dig('repository', 'full_name')`): [2](#0-1) 
`PushHandler#process` correctly uses this scope (`stacks.not_archived.where(branch:)`) so pushes only affect stacks for the authenticated repository: [3](#0-2) 

`StatusHandler#process`, however, bypasses this scoping entirely and queries `Commit` globally by `sha`: [4](#0-3) 
For every `Commit` row matching `params.sha` — regardless of which `Stack`/repository it belongs to — it calls `commit.create_status_from_github!(params)`, which writes directly into that commit's own `statuses` association (bound to `commit.stack_id`), with no re-check of repository ownership: [5](#0-4) 

Exploit flow:
1. Victim's Shipit stack B tracks repository B (e.g. a public open-source project). It contains a `Commit` row with `sha = S` (any historical commit, e.g. an old ancestor commit shared with forks, or any commit whose metadata — tree, parents, author/committer identities, timestamps, message — is knowable/reproducible).
2. Attacker owns/administers repository A (e.g. a fork of B, or any repo they registered with Shipit as its own tenant), which is already onboarded to Shipit with a valid, GitHub-managed webhook pointing at Shipit's `/webhooks` endpoint. Attacker does not need to know A's `webhook_secret` value — GitHub computes and attaches the signature automatically when delivering real events for A.
3. Attacker pushes/creates a commit with `sha = S` into repository A (trivial if A shares history with B via fork, or via constructing an identical commit object with `git commit-tree` reproducing the same hash) and triggers a `status` event for it with `state: 'success'`.
4. GitHub delivers the webhook to Shipit with `X-Hub-Signature` valid for org A. `verify_signature` passes because it only checks org A's secret.
5. `StatusHandler#process` runs `Commit.where(sha: S)`, matches the victim's `Commit` under stack B, and calls `create_status_from_github!`, writing a `success` `Status` under stack B — a repository/org the attacker never authenticated against.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) do not catch this because they validate signature/schema shape, not the semantic binding between the authenticated repository and the target `Commit`'s actual stack/repository.

### Impact Explanation
A forged `success` status written to an unrelated stack's commit can satisfy `Commit#deployable?` / `required_statuses` gating logic, enabling `stack.schedule_merges` and continuous delivery (`schedule_continuous_delivery`) to proceed for a commit whose real CI never passed — this is a cross-tenant mutation of another repository's `Commit`/`Stack` state that can lead to an unauthorized deploy, matching the Critical category ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy"). The attack is repeatable against any `sha` the attacker can reproduce, and generalizes to any Shipit instance tracking multiple repositories/orgs (multi-tenant blast radius).

### Likelihood Explanation
Preconditions: the attacker must own/administer at least one repository already onboarded as a Shipit-tracked stack (so a real webhook with a valid, GitHub-computed signature can be delivered), and must be able to get a commit with a target SHA into that repository — trivial for forks of public repos (shared ancestor SHAs) and feasible in general via fabricated commit objects with matching metadata. No Shipit secrets, sessions, or API tokens are required. This is a low-cost, repeatable attack limited only by SHA reproducibility.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the authenticated repository, mirroring `PushHandler`'s use of the `stacks` helper, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or filter `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`), so only commits belonging to stacks of the org verified by `webhook_secret` can be mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub / WebMock)
test "status webhook from attacker repo cannot write status to victim stack" do
  victim_stack = shipit_stacks(:shipit) # tracks "org-b/repo-b"
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'org-a/repo-a', 'owner' => { 'login' => 'org-a' } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  refute_equal victim_stack.id, victim_commit.reload.statuses.last&.stack_id,
    "attacker-signed webhook for org-a must not write a Status onto victim stack (org-b)'s commit"
end
```
Expected today: `Status.last.stack_id == victim_stack.id` even though the payload's `repository.full_name` (`org-a/repo-a`) never equals `victim_commit.stack.repository.full_name` (`org-b/repo-b`), confirming the WEBHOOK PROVENANCE binding is violated.
