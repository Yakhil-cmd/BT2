## Analysis

The report's bug class — an unvalidated, unbounded "tree depth" that lets a prover walk a hash chain of arbitrary length and treat non-leaf ("phantom"/intermediate) values as if they were tree members — has a direct analog in ocore's `in merkle` spending-condition authentifier.

### Title
Unbounded, Uncommitted Merkle Proof Depth in `in merkle` Authentifier Enables Node-as-Leaf Forgery Attempts - (File: `merkle.js`, `definition.js`)

### Summary
The `in merkle` address-definition authentifier lets a unit author satisfy a spending condition by supplying a serialized merkle proof for a fixed `element`, which is verified against a root that must equal a value previously posted by a designated oracle as a data feed. Neither the proof format nor the runtime authentifier evaluator binds or limits the number of hashing rounds ("depth") used to reach that root, and the code itself already flags the resulting ambiguity as the "Node-as-Leaf issue."

### Finding Description
`merkle.verifyMerkleProof` recomputes a chain of hashes from the caller-supplied `element` using an attacker-controlled `proof.siblings` array and `proof.index`, then simply compares the final hash to the attacker-supplied `proof.root`: [1](#0-0) 

The function's own comment acknowledges the underlying weakness: `// Node-as-Leaf issue might matter in some cases`, at [2](#0-1) 

Nothing in the proof format records the depth or size of the tree that the oracle actually built when computing the root it posted; depth is implicitly whatever `proof.siblings.length` the prover chooses to submit.

In `definition.js`, the `in merkle` authentifier deserializes this fully attacker-supplied proof from `assocAuthentifiers[path]`, calls `verifyMerkleProof` with no depth/size cap of any kind, and if it matches, only then checks whether the resulting `proof.root` was ever posted by the oracle under `feed_name`: [3](#0-2) 

This is unlike the sibling implementation in the formula engine's `is_valid_merkle_proof`, which — after the `bPostPemCurvesFix` upgrade — explicitly caps `objProof.siblings.length` to 50 and validates that all siblings are non-empty strings: [4](#0-3) 

No equivalent cap or structural validation exists in the `in merkle` authentifier path in `definition.js`, and the definition-time syntax check for `in merkle` only validates the *format* of the fixed `element` string and oracle addresses, not anything about proof depth at spend time: [5](#0-4) 

Consequently:
1. The prover fully controls how many hashing rounds occur and what value is hashed at every round (`proof.siblings[i]`), with no upper bound, unlike the report's L2 case where `leafIndex` at least constrained provable depth to 32 bits.
2. Because the oracle's posted root carries no depth/size commitment, `verifyMerkleProof` cannot distinguish a genuine leaf-level proof from a proof that starts at an intermediate/internal tree node (already itself `hash(child1+child2)`) and is walked further to match a previously posted root — exactly the "Node-as-Leaf" ambiguity flagged in the code comment.
3. There is no complexity/ops charge tied to `proof.siblings.length` in the `in merkle` authentifier evaluation (unlike other definition operators, which increment `complexity`/`count_ops` per unit of work), so this unbounded hashing work is also unmetered during unit validation.

### Impact Explanation
If successfully exploited, an attacker satisfying an `in merkle` condition without genuine membership in the intended committed set would let them spend from an address protected by that authentifier without authorization — a concrete unauthorized-spending outcome. Even short of a full forgery, the complete lack of depth binding removes the structural safeguard that would otherwise make such forgeries provably as hard as breaking the underlying hash function at a *fixed* depth; here the search space (arbitrary depth, arbitrary sibling choice at every level, arbitrary target among however many values a given oracle has ever posted under `feed_name`) is strictly larger and unconstrained by protocol rules, matching Medium severity for a missing security boundary in an authentication primitive.

### Likelihood Explanation
Exploitation still fundamentally requires finding a hash-chain collision against SHA-256, so practical exploitation is not trivial — mirroring the original report's own caveat that this class of issue is "not significantly easier than finding second preimages." However, likelihood of the *design flaw* being present and reachable by any ordinary unit author using `in merkle` (a documented, user-accessible oscript feature) is high, and the missing cap also means the validating node performs unbounded work per submitted unit, which is inconsistent with every other complexity-metered operator in `definition.js`.

### Recommendation
- Bind and validate merkle tree depth: extend `getMerkleProof`/`verifyMerkleProof` (and the oracle's data-feed posting flow) to include an explicit depth or leaf-count field, and reject verification if the supplied `proof.siblings.length` does not match the depth recorded/committed for that root.
- Enforce a maximum depth for `in merkle` proofs in `definition.js`'s authentifier evaluation, mirroring the `siblings.length > 50` cap already used in `formula/evaluation.js`'s `is_valid_merkle_proof`.
- Charge `complexity`/`count_ops` proportional to `proof.siblings.length` in the `in merkle` case so that arbitrarily long proofs cannot bypass complexity accounting used elsewhere in `definition.js`.

### Proof of Concept
1. Owner creates an address whose definition includes `['in merkle', [[oracleAddr], 'feed', 'FIXED_ELEMENT']]`, per the `in merkle` case at [5](#0-4) .
2. Oracle posts many different `feed` values over time via ordinary data feed units (standard oracle usage, not required to be malicious).
3. Attacker, without possessing a genuine inclusion proof for `FIXED_ELEMENT` in any tree the oracle actually built, offline-searches for a `(siblings, index)` pair such that repeatedly applying `merkle.verifyMerkleProof`'s hash-chaining logic to `FIXED_ELEMENT` terminates in some value `R` that matches any value ever posted under `feed`, exploiting the fact that neither the number of rounds nor the sibling values are constrained: [1](#0-0) .
4. Attacker submits a spending unit whose authentifier at the `in merkle` path is `serializeMerkleProof({index, siblings, root: R})`; `validateAuthentifiers`'s `in merkle` case accepts it purely because `verifyMerkleProof` returns true and `dataFeeds.dataFeedExists` finds `R` among posted feed values, per [6](#0-5) , without ever confirming `FIXED_ELEMENT` was a real leaf of the tree that produced `R`.

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
