### Title
Bad-debt write-down floors the supply index but leaves residual debt, pushing utilization above 100% and inflating the deposit rate until supplier claims exceed backing - (File: contracts/pool/src/interest.rs)

### Summary
The pool computes the supplier deposit rate as `utilization * borrow_rate * (1 - reserve_factor)`, and while `calculate_annual_borrow_rate` clamps utilization to `RAY`, `calculate_deposit_rate` multiplies by the **unclamped** utilization. `apply_bad_debt_to_supply_index` floors the written-down supply index at `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) instead of zeroing it, so after `clean_bad_debt` burns a bad-debt position the market can be left with `borrowed_value >> supplied_value` — utilization far above 1. From then on every accrual grows the supply index faster than the borrow index, re-inflating the very supplier claims the write-down was supposed to destroy, funded by nothing. This is the XOXNO analog of the report's "utilization invariant broken → deposit rate inflation → drain the pool" class: the state that should be unreachable (utilization > 1 with surviving supply claims) is reachable through an unprivileged path and is then amplified by the rate engine.

### Finding Description
Two facts combine:

1. `apply_bad_debt_to_supply_index` caps the reduction at total supplied value but then floors the result at `SUPPLY_INDEX_FLOOR_RAW`. When `bad_debt >= total_supplied_value`, `reduction_factor` is 0 yet the index is set to `RAY/1000`, leaving `supplied_value = supplied * 0.001` while only the *seized* position's debt is burned. Any other outstanding debt (healthy borrowers, or other bad-debt accounts not yet cleaned) remains intact. [1](#0-0) [2](#0-1) 

2. `calculate_deposit_rate` is called with the raw utilization and does not clamp it, whereas `calculate_annual_borrow_rate` clamps `utilization` to `Ray::ONE` before the curve. So once utilization exceeds 1, suppliers accrue strictly more than borrowers pay; at utilization of e.g. 500 the deposit APR is ~500x the capped borrow APR, and the supply index races toward `MAX_SUPPLY_INDEX_RAY` while the borrow index moves at the capped borrow rate. [3](#0-2) [4](#0-3) 

The utilization guard does not prevent this state: `require_utilization_below_max` is a gate on new borrows/withdrawals, not an invariant maintained by accrual or seize, and `docs/reference/invariants.md` explicitly states accrual and bad-debt writeoff can exceed the ceiling. `seize_positions` runs no utilization guard at all. [5](#0-4) [6](#0-5) 

Reachability for an unprivileged attacker: `clean_bad_debt` (controller) is permissionless per the scope rules and drives `seize_positions(AccountPositionType::Borrow)`. Bad debt is created naturally by any liquidation that leaves an unpaid remainder, which an attacker can manufacture with their own underwater position (e.g. crashing a collateral price via their own Aquarius/Soroswap trade, then self-liquidating incompletely, or simply leaving dust debt above the cleanup threshold while residual debt exists in the market).

### Impact Explanation
Once utilization sits above 1, each accrual mints supplier value out of thin air relative to borrower accrual:

- The write-down is undone: supplier shares regain value with no corresponding cash or debt backing, recreating the bad debt the cleanup was meant to socialize.
- When re-inflation pushes `supplied * supply_index` back up, utilization falls below the cap again, withdrawals re-enable, and early withdrawers drain `cash` that no longer covers remaining claims — late suppliers/holders get `InsufficientLiquidity` / `PoolInsolvent`, i.e. theft of user funds and permanent freezing of residual funds.
- An attacker holding supply shares through the cleanup is paid the inflated index for free — direct theft of pool cash at the expense of other suppliers.

### Likelihood Explanation
Requires a market state where a `clean_bad_debt` (or liquidation seize) writes down the supply index to the floor while other debt survives — i.e. bad debt roughly equal to total supply, which occurs in thinly-supplied markets or after a sharp price move, precisely the conditions the write-down path exists for. The trigger (`clean_bad_debt`, `liquidate`) is permissionless; the attacker can construct the preconditions with their own position and own DEX trades. No privileged action, no timing luck beyond normal liquidation mechanics. Rated Medium-High: the damage (insolvency/frozen funds) is severe but depends on a market reaching a nearly-fully-impaired state.

### Recommendation
- Clamp utilization to `RAY` inside `calculate_deposit_rate` (or pass the clamped value from `accrue_step`), so suppliers can never accrue faster than borrowers on the same market.
- Alternatively, when `apply_bad_debt_to_supply_index` hits `SUPPLY_INDEX_FLOOR_RAW`, treat the remaining shortfall explicitly (e.g. force the market into a halted/`PoolInsolvent` state requiring `recapitalize`) rather than letting accrual silently re-inflate claims.
- Add a regression test: seize bad debt >= supply value with residual debt, advance time, assert `supply_index` growth never exceeds `borrow_index` growth and `backing_shortfall` does not grow.

### Proof of Concept
Conceptual flow (pool-level, owner = controller):

1. Market `(hub, X)`: Alice supplies 100 X (`supplied`, `cash = 100`). Bob borrows 99 X (healthy collateral elsewhere). Carol borrows 1 X of dust that later becomes unbacked bad debt (price crash / partial self-liquidation leaving `debt` with no collateral).
2. Anyone calls controller `clean_bad_debt` for Carol → `seize_positions` with `side = Borrow`. `bad_debt ≈ 1`, but with supplied value drawn down to ~1 by prior state (or a second seize where bad debt ≥ remaining supply), `apply_bad_debt_to_supply_index` sets `supply_index = RAY/1000` while Bob's 99 X debt survives. Result: `supplied_value ≈ 0.1`, `borrowed_value ≈ 99` → utilization ≈ 990.
3. Call `update_indexes` (permissionless) after one accrual step: `accrue_step` uses `calculate_deposit_rate(util≈990, borrow_rate≤max_borrow_rate, rf)` → supply index multiplies by up to ~990× the per-ms borrow rate while Bob's debt compounds at the capped rate.
4. `backing_shortfall(cache)` grows monotonically; Alice's written-down shares recover and exceed `cash + debt`. `supply` reverts `PoolInsolvent`, `claim_revenue`/`withdraw` race for the 1 X of cash; whoever exits first takes it, everyone else is permanently frozen at `InsufficientLiquidity`/`PoolInsolvent` unless governance recapitalizes.

Key snippet (`common/src/rates/curve.rs`): `calculate_deposit_rate` line 93 multiplies unclamped `utilization` by the already-clamped `borrow_rate`; contrast with lines 22–26 where the borrow rate itself clamps `utilization` to `Ray::ONE`.

Uncertainty note: I verified the rate math, the write-down floor, and the guard table, but did not fully trace the controller's `clean_bad_debt`/`seize_positions` batch to confirm whether it forces cleanup of *all* impaired accounts in one call (which would remove residual debt and shrink the window). If cleanup is forced atomically market-wide, the residual-debt precondition narrows, but the same util>1 state is also reachable via liquidation withdrawals, which explicitly skip `require_utilization_below_max`.

```rust
pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
}
```

```rust
pub fn calculate_deposit_rate(
    env: &Env,
    utilization: Ray,
    borrow_rate: Ray,
    reserve_factor: Bps,
) -> Ray {
    if utilization == Ray::ZERO {
        return Ray::ZERO;
    }

    if !(0..BPS).contains(&reserve_factor.raw()) {
        return Ray::ZERO;
    }

    let rate_x_util = utilization.mul(env, borrow_rate);
    let supplier_share = Bps::from(BPS - reserve_factor.raw());
    supplier_share.apply_to_ray(env, rate_x_util)
}
```

```rust
pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );
}
```
