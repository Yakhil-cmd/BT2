### Title
Webhook secret selected by unverified `repository.owner.login` is not bound to the `repository.full_name` acted on by handlers — cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook using `repository_owner`, taken straight out of the unverified JSON body, then every event handler independently re-reads `repository.full_name` from that same body to decide which `Stack`/`Repository` to mutate. Nothing ties the two together, so a secret that is valid for one configured GitHub organization can be used to sign a payload naming a different tracked repository.

### Finding Description
`verify_signature` selects the GitHub App config (and thus the `webhook_secret`) with: [1](#0-0) 
where `repository_owner` is: [2](#0-1) 
i.e. it is read from the same untrusted, attacker-controlled JSON body whose signature is only checked afterwards, and it exists purely to pick *which* per-organization secret (`Shipit.github(organization: ...)`) to HMAC-verify against, per the multi-org setup documented in `docs/setup.md` (`config/secrets.yml` keyed by organization, each with its own `webhook_secret`).

Once `verify_signature` passes, `create` hands the entire parsed body to every registered handler for the event: [3](#0-2) 

Every handler then resolves the target `Repository`/`Stack` independently using `repository.full_name` from that body, e.g. the shared base class: [4](#0-3) 
`PushHandler`, which triggers a GitHub sync/deploy pipeline for the resolved stacks: [5](#0-4) 
and pull-request handlers that archive/unarchive review stacks or update pull request records, e.g.: [6](#0-5) 

The binding that should hold is: `organization used to select the webhook_secret == organization that owns repository.full_name acted on`. Nothing in `WebhooksController` or `Handler` enforces this — `repository_owner` (for secret selection) and `repository.full_name` (for the mutated resource) are two independently-controlled fields inside one unsigned-at-selection-time JSON blob, and the HMAC only proves "this body was signed by *some* configured organization's secret," not "this body's target repository belongs to that organization."

### Impact Explanation
In any multi-organization Shipit deployment (explicitly supported and documented for organizations that don't trust each other's GitHub Apps), an attacker who administers/operates their own onboarded GitHub App (and therefore knows its `webhook_secret`) can forge a webhook with `repository.owner.login`/`organization.login` set to their own org (so the secret lookup and HMAC succeed) while setting `repository.full_name` to any other tracked repository/stack on the same Shipit instance. This lets them:
- Trigger `GithubSyncJob`/deploy pipeline activity on a victim stack via a forged `push` event.
- Forge `status`/`check_suite` events to manipulate commit statuses gating merges/deploys on a victim repo.
- Archive/unarchive or otherwise mutate a victim's review stacks via forged `pull_request` events.

This crosses a repository/organization trust boundary using only a secret the attacker legitimately possesses for an unrelated, less-trusted organization — matching the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the target instance to host more than one GitHub organization/app configuration (a documented, supported configuration) and requires the attacker to control one of those less-privileged organizations' webhook secret — which is normal for any org onboarding to a shared Shipit instance, not a privileged Shipit account or GITHUB_TOKEN. No Shipit session or `ApiClient` token is needed.

### Recommendation
After selecting the GitHub App/secret via `repository_owner`, verify that the resolved organization actually matches the owner of `repository.full_name` (or the org named in the payload's `organization`/`installation` object) before dispatching to handlers, or scope handler repository resolution to only repositories confirmed to belong to the organization whose secret validated the signature.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `AttackerOrg` and `VictimOrg`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications").
2. Attacker knows `AttackerOrg`'s `webhook_secret` (they administer that GitHub App).
3. Attacker crafts a `push` webhook JSON body with `repository.owner.login = "AttackerOrg"` (or `organization.login`) but `repository.full_name = "VictimOrg/victim-repo"`, and computes `X-Hub-Signature` using `AttackerOrg`'s secret.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and the HMAC check passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `stack.sync_github(...)`, triggering sync/deploy activity on a repository the attacker does not own.
