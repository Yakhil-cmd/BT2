### Title
Unbounded `pendingRequestEvent` Queue Allows Attacker to Permanently Delay Legitimate Bridge Value Transfers — (`node/sc/sub_event_handler.go`, `node/sc/bridge_manager.go`)

---

### Summary

The Kaia service-chain bridge's `BridgeInfo.pendingRequestEvent` queue is initialized with no hard size limit (`UnlimitedItemSortedMap`). Any user can call the permissionless `requestKLAYTransfer` (or `requestERC20Transfer`) function on the child-chain bridge contract to flood the queue. The soft-cap eviction logic in `AddRequestValueTransferEvents` silently drops events whose nonce is ≥ the current maximum nonce in the queue. Because the attacker's events arrive first and hold the lowest nonces, all subsequent legitimate users' events are evicted and never processed by the bridge operator goroutine. The developer explicitly acknowledged this gap with a `TODO` comment. The recovery mechanism introduces a multi-round delay and can itself be overwhelmed, allowing a sustained DOS of bridge value transfers at the cost of only gas fees.

---

### Finding Description

**Root cause — `pendingRequestEvent` initialized as unlimited:**

`NewBridgeInfo` creates the queue with `bridgepool.UnlimitedItemSortedMap` (value `-1`), meaning the underlying `ItemSortedMap` enforces no size limit at the data-structure level. [1](#0-0) 

**Acknowledged gap — no size management in `ProcessRequestEvent`:**

The event handler that feeds the queue carries an explicit developer `TODO` admitting the size limitation is unmanaged: [2](#0-1) 

**Soft-cap eviction logic drops high-nonce (legitimate) events:**

`AddRequestValueTransferEvents` applies a soft cap of `maxPendingNonceDiff = 1000`. When the queue is full, it evicts the event with the **highest** nonce and inserts the new event only if its nonce is **strictly less than** the current maximum. Because the bridge contract's `requestNonce` counter is global and monotonically increasing, an attacker who sends the first 1 000 requests occupies nonces 0–999 (maxNonce = 999). Every subsequent legitimate event (nonce ≥ 1 000) satisfies `ev.Nonce() >= maxNonce` and is silently dropped via `continue`: [3](#0-2) 

**Permissionless trigger — `requestKLAYTransfer`:**

The bridge contract's KLAY transfer request function has no access control. Any externally-owned account can call it by sending KAIA: [4](#0-3) 

**Processing loop — bounded but still drains bridge-operator nonce:**

`processingPendingRequestEvents` pops up to `maxPendingNonceDiff / 2 = 500` events per invocation and submits one on-chain `HandleKLAYTransfer` / `HandleERC20Transfer` transaction per event, consuming the bridge operator's nonce and KAIA balance for each: [5](#0-4) 

---

### Impact Explanation

1. **Bridge value-transfer DOS**: Legitimate users' `RequestValueTransfer` events are silently evicted from the queue and never processed by the bridge operator goroutine. Their KAIA/ERC-20/ERC-721 assets are locked in the source bridge contract until the recovery mechanism re-discovers them.
2. **Bridge operator nonce/KAIA exhaustion**: The operator must submit one counterpart-chain transaction per attacker event (up to 500 per second), consuming gas. If the operator's KAIA balance is drained, the bridge halts entirely.
3. **Sustained attack**: The attacker recovers their KAIA via the bridge (the bridge operator processes the attacker's own requests and sends KAIA back). The net cost to the attacker is only gas fees, making the attack economically sustainable.

---

### Likelihood Explanation

- `requestKLAYTransfer` is permissionless and requires only a small KAIA value (plus fee).
- The attacker recovers the principal via the bridge, so the sustained cost is only gas.
- Filling the queue to 1 000 events requires 1 000 transactions, feasible in a single block on a low-fee chain.
- The developer's own `TODO` comment confirms awareness that the size limitation is unresolved.

---

### Recommendation

1. **Hard-cap the queue at the data-structure level**: Change the `pendingRequestEvent` initialization from `UnlimitedItemSortedMap` to a fixed limit (e.g., `maxPendingNonceDiff`), so `ItemSortedMap.Put` returns `ErrSizeLimit` and the event is rejected before it can displace a legitimate entry. [1](#0-0) 

2. **Fix the eviction direction**: When the queue is full, evict the **lowest**-nonce event (already processed or stale) rather than the highest-nonce event. This prevents an attacker who holds the lowest nonces from permanently blocking higher-nonce legitimate events.

3. **Rate-limit per-sender requests**: Track per-address request counts within a sliding window in the event handler and reject events that exceed a threshold before they enter the queue.

4. **Resolve the TODO**: Remove the `TODO-Kaia need to manage the size limitation of pending event list.` comment only after a hard limit is enforced. [6](#0-5) 

---

### Proof of Concept

```
1. Attacker calls requestKLAYTransfer(attacker, 1 KAIA, "") × 1 000 on the child-chain bridge.
   → Bridge contract emits RequestValueTransfer events with requestNonce 0–999.
   → SubBridge goroutine calls ProcessRequestEvent for each, which calls
     AddRequestValueTransferEvents. Queue fills to 1 000 entries (nonces 0–999).

2. Legitimate user calls requestKLAYTransfer(victim, 1 KAIA, "").
   → Bridge emits RequestValueTransfer with requestNonce 1 000.
   → AddRequestValueTransferEvents: Len() = 1 000 > maxPendingNonceDiff (1 000).
     maxNonce = 999. ev.Nonce() = 1 000 >= 999 → `continue` (event DROPPED).

3. Bridge operator goroutine (every 1 s) calls processingPendingRequestEvents:
   → Pops 500 attacker events (nonces 0–499), submits HandleKLAYTransfer × 500.
   → Attacker receives 500 KAIA back on the parent chain.

4. Attacker immediately sends 500 more requestKLAYTransfer calls to refill the queue.
   → Legitimate user's event (nonce 1 000) continues to be dropped on every insertion.

5. Legitimate user's transfer is stuck until valueTransferRecovery detects the gap
   (requires two consecutive recovery rounds with no progress), introducing a
   multi-minute delay. Attacker repeats step 4 to prevent recovery from catching up.
``` [7](#0-6) [8](#0-7)

func (bi *BridgeInfo) GetPendingRequestEvents() []IRequestValueTransferEvent {
	ready := bi.pendingRequestEvent.Pop(maxPendingNonceDiff / 2)
	readyEvent := make([]IRequestValueTransferEvent, len(ready))
	for i, item := range ready {
		readyEvent[i] = item.(IRequestValueTransferEvent)
	}
	vtPendingRequestEventCounter.Dec((int64)(len(ready)))
	return readyEvent
}

// processingPendingRequestEvents handles pending request value transfer events of the bridge.
func (bi *BridgeInfo) processingPendingRequestEvents() {
	ReadyEvent := bi.GetReadyRequestValueTransferEvents()
	if ReadyEvent == nil {
		return
	}

	logger.Trace("Get ready request value transfer event", "len(readyEvent)", len(ReadyEvent), "len(pendingEvent)", bi.pendingRequestEvent.Len())

	for idx, ev := range ReadyEvent {
		if ev.GetRequestNonce() < bi.lowerHandleNonce || bi.handledEvent.Exist(ev.GetRequestNonce()) {
			logger.Trace("handled requests can be ignored", "RequestNonce", ev.GetRequestNonce(), "lowerHandleNonce", bi.lowerHandleNonce)
			continue
		}

		if err := bi.handleRequestValueTransferEvent(ev); err != nil {
			bi.AddRequestValueTransferEvents(ReadyEvent[idx:])
			logger.Error("Failed handle request value transfer event", "err", err, "len(RePutEvent)", len(ReadyEvent[idx:]))
			return
		}
	}
}

func (bi *BridgeInfo) AddRequestValueTransferEvents(evs []IRequestValueTransferEvent) {
	for _, ev := range evs {
		if bi.pendingRequestEvent.Len() > maxPendingNonceDiff {
			flatten := bi.pendingRequestEvent.Flatten()
			maxNonce := flatten[len(flatten)-1].Nonce()
			if ev.Nonce() >= maxNonce || bi.pendingRequestEvent.Exist(ev.Nonce()) {
				continue
			}
			bi.pendingRequestEvent.Remove(maxNonce)
			vtPendingRequestEventCounter.Dec(1)
			logger.Trace("List is full but add requestValueTransfer ", "newNonce", ev.Nonce(), "removedNonce", maxNonce)
		}

		bi.SetRequestNonceFromCounterpart(ev.GetRequestNonce() + 1)
		bi.pendingRequestEvent.Put(ev)
		vtPendingRequestEventCounter.Inc(1)
	}
