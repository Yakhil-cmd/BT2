### Title
Webhook signature verification selects the GitHub App by `repository.owner.login`, while event handlers act on an unrelated `organization.login`/`repository.full_name` field, letting a foreign org's App secret authorize privileged mutations on another org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` picks which GitHub App (and thus which `webhook_secret`) is used to validate the incoming webhook HMAC based on `repository.owner.login` (or `organization.login` as fallback) taken from the raw JSON payload. The event handlers that actually perform privileged mutations (e.g. `MembershipHandler`, `PushHandler`, all the `PullRequest::*Handler`s) read a *different* identity field from the very same payload (`organization.login` or `repository.full_name`) to decide what to modify, with no cross-check that it matches the org whose secret validated the request. This breaks the trust binding "organization whose signature was verified == organization/repository being mutated."

### Finding Description
`WebhooksController#verify_signature` resolves the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` first looks at `repository.owner.login`, falling back to `organization.login` only if `repository` is absent — both fields are attacker-controlled JSON keys within the same POST body that must be self-consistent for a *genuine* GitHub-generated webhook, but nothing stops a forger who knows *any* configured org's `webhook_secret` from putting one org in `repository.owner.login` (used only to select the verification key) and a different org/repo in the fields the handler actually consumes.

`Shipit.github(organization:)` resolves per-organization App config (including its own distinct `webhook_secret`) exactly as documented for the "Using Multiple GitHub Applications" deployment mode: [3](#0-2) 

Each organization's own App/secret is set up by that organization's own (lower-privileged, relative to other tenants) Shipit administrator - see the two-tenant example fixture: [4](#0-3) 

Once the signature check passes using `OrgTwo`'s secret, the dispatched handler is chosen solely by the `X-Github-Event` header, and the handler re-parses the same payload using its own field path, independent of which org's secret validated the request. `MembershipHandler`, for example, mutates global team membership (which drives `Shipit.github_teams` authorization) using `organization.login` and `member.login`, without any tie back to the `repository.owner.login` used for signature selection: [5](#0-4) 

`Team#add_member` here feeds directly into the global authorization check: [6](#0-5) 

**Binding broken:** `org authenticated by verify_signature (repository.owner.login)` ≠ `org/team whose state the handler mutates (organization.login / member.login)`. Before the attacker's forged request, the equality holds for any real GitHub-emitted webhook (GitHub sets both fields consistently). After the forged request, the two diverge: the HMAC is valid for `OrgTwo`, but the mutated `Team`/membership belongs to `OrgOne`.

### Impact Explanation
This directly escalates into `Shipit.github_teams` authorization (the High-severity bucket explicitly listed): an attacker who legitimately administers a second, unrelated GitHub App/org configured in the same Shipit instance (and thus knows *that* org's `webhook_secret`) can forge a `membership` webhook, valid under their own org's secret, that adds an arbitrary GitHub login as a member of a `Team` belonging to a completely different, victim organization. If that team is one of the teams configured in `Shipit.github_teams`, the attacker becomes `authorized?` for the whole Shipit instance, gaining session-level access to stacks/deploys they should never see. The same header/body field split (`repository.owner.login` for auth vs `repository.full_name` for effect) also lets a similarly-positioned attacker trigger `GithubSyncJob`/`RefreshCheckRunsJob` etc. against a foreign org's stacks, though those handlers primarily just re-fetch real data through the victim's own GitHub credentials and are lower impact.

### Likelihood Explanation
Requires the deployment to use the documented "multiple GitHub Applications" mode (explicitly supported and documented) and requires the attacker to control (or have created) at least one of the configured GitHub Apps/orgs — i.e., they know that org's `webhook_secret`, which is a normal, unprivileged-relative-to-other-tenants position in a shared multi-tenant Shipit instance. No `ApiClient` token, GitHub App private key, or repository write access to the victim org is required — only the ability to POST a self-signed HTTP request to `/webhooks`.

### Recommendation
- Require that all identity fields used across signature verification and handler logic within a single request agree: verify the org derived from `repository.owner.login`/`organization.login` matches every other org/repo-identifying field read later by the dispatched handler for that event type, and reject the request otherwise.
- In `WebhooksController`, resolve and store a single canonical "authenticated organization" for the request and pass it into `Handler#call`/`Handler#initialize`, having each handler (`MembershipHandler`, `PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`) assert that the resource it is about to mutate (`repository.full_name`'s owner, `organization.login`) equals that authenticated organization before acting.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App configuration (`secrets.github.OrgOne`, `secrets.github.OrgTwo`, each with distinct `webhook_secret`), as shown in `test/dummy/config/secrets_double_github_app.yml`.
2. As the administrator of `OrgTwo`'s own GitHub App (a legitimate, unprivileged-relative-to-`OrgOne` actor), compute `sha1=HMAC(OrgTwo_webhook_secret, body)` for the following body:
```json
{
  "action": "added",
  "team": { "id": <OrgOne_team_github_id>, "name": "Deploy", "slug": "deploy", "url": "https://example.com" },
  "organization": { "login": "OrgOne" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "OrgTwo" } }
}
```
3. `POST /webhooks` with header `X-Github-Event: membership` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` = `"OrgTwo"` and validates against `OrgTwo`'s secret → passes.
5. `MembershipHandler.process` runs using `organization.login = "OrgOne"`, creating/finding `OrgOne`'s `Team` and calling `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
6. If that team id is included in `OrgOne`'s configured `oauth_teams`, `User#authorized?` now returns `true` for the attacker's account against the shared Shipit instance, without any real GitHub membership in `OrgOne`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
