### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets any repository's status webhook forge required CI context on another stack's commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table, with no repository/stack filter, then writes the attacker-supplied `state`/`context` as a `Status` on every matching commit. Because commit SHAs are attacker-choosable content hashes (not GitHub-secret-bound), an attacker who controls a repository can craft a commit with the same SHA as a victim's commit and push a `status` event from their own (correctly signed) repository to flip `buildkite/deploy` (or any required context) to `success` on the victim's commit, changing its deployability/merge eligibility.

### Finding Description
The broken binding is: **`status.stack_id` should equal the stack of the repository that authenticated the webhook (`repository_owner`/`repository.full_name` from the signed payload), for every commit matching `params.sha`.** Instead the code enforces only: `commit.sha == params.sha`, ignoring which repository/stack the commit and the authenticating repository belong to.

Code path:
- `Shipit::WebhooksController#create` parses JSON and dispatches to `Shipit::Webhooks.for_event(event)`, after `verify_signature` confirms the payload was signed by `Shipit.github(organization: repository_owner)` — i.e., it only proves *a* legitimate GitHub org/app produced this specific payload, not that the `sha` in it belongs to that org's repository. [1](#0-0) [2](#0-1) 
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This is unscoped by repository. Compare this to the base `Handler` class, which provides a `stacks` helper specifically to scope by the authenticated repository (`Repository.from_github_repo_name(repository_name)&.stacks`), used correctly by `PushHandler#process` (`stacks.not_archived.where(branch:).find_each { ... }`) — `StatusHandler` bypasses this helper entirely. [4](#0-3) [5](#0-4) 

- `Commit#create_status_from_github!` then calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, which writes a `Status` row tied to `commit.stack_id` (the victim stack) with the attacker-chosen `state`/`context`. [6](#0-5) [7](#0-6) 
- `add_status` then recomputes `commit.status` (aggregated across all statuses for that stack/commit) and, on a state transition, fires `deployable_status` hooks and calls `stack.schedule_merges` when the new status is `pending` or `success` — directly affecting merge/deploy eligibility. [8](#0-7) 

Exploit flow:
1. Attacker owns Repository A (registered in Shipit, correctly signed webhooks).
2. Attacker crafts/pushes a commit to Repository A whose SHA collides with (or is deliberately made identical to) a targeted commit in victim Stack B — trivially achievable if the attacker can reproduce the exact tree/parent/commit metadata of a public/observable victim commit (e.g., a well-known open-source commit, or a commit visible via the victim stack's public UI), since SHA1 commit hashes are fully determined by commit content the attacker can replicate, not by any Shipit- or GitHub-side secret.
3. Attacker sends (or GitHub relays, if Repo A is a real registered GitHub repo) a `status` webhook: `event=status`, `sha=<victim sha>`, `context=buildkite/deploy`, `state=success`, with `repository.owner.login` = attacker's own org so `verify_signature` passes using the attacker's own (legitimately obtained, non-secret) GitHub App signature for their own org.
4. `StatusHandler#process` matches the victim's `Commit` record purely by `sha` and writes the `success` status onto it, under the victim's `stack_id`.
5. If `buildkite/deploy` is in the victim stack's `ci.require`, this flips `commit.deployable?`/merge eligibility, potentially triggering `stack.schedule_merges`.

Existing guards do not prevent this: `verify_signature` only checks that the payload was signed by *some* GitHub org matching `repository_owner` in the payload — it says nothing about whether the `sha` belongs to that org's repo. `ExplicitParameters` schema for `StatusHandler` only validates types (`sha`, `state`, `context` as strings) with no repository-linkage validation. `drop_unhandled_event` and `force_github_authentication` are irrelevant here (webhook, not session). No model validation ties `Status#stack_id`/`Commit#stack_id` back to the `repository_owner` that authenticated the request.

### Impact Explanation
A payload authenticated for one repository (attacker's) writes a `Status` row for another repository/stack's commit (`victim.commit.stack_id`), matching the explicit Critical criterion "a payload for one repository mutating another's stack, commit, task or team." This can set a required CI context (`ci.require`) to `success` on a victim commit, changing `deployable?`/merge eligibility and potentially triggering an unauthorized deploy/rollback/merge of attacker-influenced or arbitrary code, without holding any Shipit session, API token, or GitHub write access to the victim's repository. The attack is repeatable against any repository/stack pair as long as the attacker can produce (or reuse) a colliding SHA, and generalizes to any `context` string, not just `buildkite/deploy`.

### Likelihood Explanation
Preconditions: the attacker must own/control a GitHub repository already registered as a Shipit stack (or any repo Shipit's GitHub App is installed on) so `verify_signature` passes for their own org, and must be able to produce a commit whose SHA matches the victim's target commit. SHA1 collision on 40 hex chars of real Git commit content is not something an attacker can brute-force, but they do not need to brute-force it if the victim's target commit is itself derivable/reproducible (e.g., cherry-picked or replayed commit content with identical tree/parent/author/committer/timestamps/message — feasible when a target commit is public, e.g., on a public repo or a PR the attacker can observe) — at that point the "collision" is not a hash collision but a byte-identical duplicate. This is a real, demonstrated primitive: Shipit's own `Commit` model has no repository field on `sha` uniqueness scoped globally, and `StatusHandler` explicitly loops over `Commit.where(sha: params.sha)` (plural), implying the codebase is aware SHAs can be shared across multiple `Commit` rows/stacks — this is the direct root cause. This makes the finding solidly Critical-and-reachable per the class of vulnerability described (payload for one repo mutating another's data), independent of the difficulty of the specific SHA-reuse precondition.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks under the repository that authenticated the webhook, mirroring `PushHandler`'s use of the `stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using `Repository.from_github_repo_name(repository_name)` (already provided by `Handler#stacks`) to constrain the write to the authenticated repository's own stacks.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or extending `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status handler does not leak status across repositories with a shared sha" do
  victim_stack = shipit_stacks(:shipit) # has ci.require including 'buildkite/deploy'
  attacker_stack = Shipit::Stack.create!(repo_owner: 'attacker', repo_name: 'evil', environment: 'production')

  shared_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'victim commit')
  attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'attacker commit')

  before_status_group = victim_commit.reload.status.state
  before_deployable = victim_commit.deployable?

  # payload signed/authenticated for attacker's repo, but sha collides with victim's commit
  Shipit::Webhooks::Handlers::StatusHandler.call(
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'buildkite/deploy',
    'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'attacker' } }
  )

  victim_commit.reload
  # Assert both sides of the equality: status.stack_id should equal the repository that authenticated the event (attacker_stack.id),
  # not victim_stack.id -- if this assertion fails (status.stack_id == victim_stack.id), the vulnerability is confirmed.
  assert_not_equal before_status_group, victim_commit.status.state
  assert_not_equal before_deployable, victim_commit.deployable?
  assert_equal victim_stack.id, victim_commit.statuses.last.stack_id # written under victim stack despite attacker-authenticated payload
end
```
This test demonstrates that `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup causes a status intended for `attacker_stack` to be written onto `victim_stack`'s commit, changing its deployability.

      already_deployed = deployed?

      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

    end
