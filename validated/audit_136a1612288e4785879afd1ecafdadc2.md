### Title
Webhook signature verified against attacker-chosen organization while the payload's `repository.full_name` is used to select the repository/stack acted on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate the HMAC signature against using a field taken directly from the still-unverified JSON body, while every event handler later selects the `Repository`/`Stack` to mutate using a different field (`repository.full_name`) from that same untrusted body. When Shipit is configured with multiple GitHub organizations (the documented "Using Multiple Github Applications" setup), these two fields are never cross-checked, so a payload can be crafted to authenticate as organization A while writing to a repository belonging to organization B.

### Finding Description
`verify_signature` resolves the signing secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — i.e., from the raw, attacker-supplied JSON body, before the signature check has run. `Shipit.github(organization: repository_owner)` then looks up the `GitHubApp` (and its `webhook_secret`) configured for that org name, and `verify_webhook_signature` is checked against `request.raw_post` using that secret: [3](#0-2) 

Multi-org configuration is a first-class, documented feature (`config/secrets.*` `github:` keyed by organization name), each with its own `webhook_secret`: [4](#0-3) [5](#0-4) 

Once the signature is accepted, the raw parsed payload is handed unmodified to every registered handler: [6](#0-5) 

All handlers resolve the target `Repository`/`Stack` from a **different** payload field, `repository.full_name`, via the base `Handler` class: [7](#0-6) 

For example, `PushHandler` calls `stack.sync_github` for every matching stack under that resolved repository: [8](#0-7) 

and `StatusHandler` writes forged commit statuses onto commits of any tracked repo whose sha matches: [9](#0-8) 

Nothing anywhere compares `repository.owner.login` (used to select the verifying secret) with `repository.full_name`'s owner segment (used to select the entity that gets written). This is exactly the reported bug class: the field validated (`amountToRequest`/here, the org used for signature verification) is not the field acted upon (`_amount`/here, `repository.full_name` used for the actual write).

### Impact Explanation
An attacker who can configure/trigger a GitHub webhook for **any one** organization that Shipit trusts (i.e., knows that organization's configured `webhook_secret` — a normal, expected capability for whoever sets up that org's webhook, not a Shipit privilege) can forge the JSON body so that `repository.owner.login`/`organization.login` names their own organization (to pass signature verification with their own known secret) while `repository.full_name` names a repository belonging to a **different**, unrelated organization also configured in the same Shipit instance. This crosses the "organization that authenticated vs. repository that is written" trust boundary and yields cross-repository/cross-organization writes:
- Forged `push` events (`ref`/`after`) invoke `stack.sync_github(expected_head_sha: ...)` on stacks of an org the attacker doesn't control, and syncing can feed into `ContinuousDeliveryJob#perform`, which calls `stack.trigger_continuous_delivery` for stacks with `continuous_deployment?` enabled — i.e., an unauthorized deploy trigger on another org's stack. [10](#0-9) 
- Forged `status`/`check_suite` events can write fake commit statuses or trigger `RefreshCheckRunsJob` against commits belonging to another organization's repository, potentially satisfying deploy-gating checks and enabling further unauthorized deploys.
- Forged `pull_request`/`membership` events create/mutate `ReviewStack`, `Team`, and membership records scoped to an organization the attacker never authenticated as.

This matches the report's "High"/"Critical" bar (unauthorized deploy trigger, cross-repository writes) once continuous deployment or status-gated deploys are enabled on the victim organization's stack.

### Likelihood Explanation
Requires the target instance to run Shipit's documented multi-organization configuration (`github:` keyed by org) and requires the attacker to control a legitimate webhook delivery (and its secret) for at least one of the configured organizations — a routine, low-privilege setup step, not requiring any Shipit session, API token, or GitHub App private key. Given that, forging the JSON body fields is trivial since the attacker fully controls the raw POST body they send (as long as the HMAC over that exact body matches their own known secret).

### Recommendation
In `WebhooksController`, after `verify_signature` succeeds, re-derive the organization actually used for verification and assert it matches the owner embedded in `repository.full_name` (and `organization.login` where present) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, have each `Handler` re-validate that the resolved `Repository#owner` equals the `repository_owner` that was used to select the verifying `GitHubApp`, rather than trusting `repository.full_name` in isolation.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` (attacker-controlled webhook, secret `S1` known to attacker) and `OrgTwo` (victim org, tracked stack `victim/repo`), per `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha already present as a valid commit on victim/repo>",
     "repository": { "full_name": "victim/repo", "owner": { "login": "OrgOne" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S1, raw_body)` using `OrgOne`'s known secret and POSTs to `/github/webhooks`.
4. `WebhooksController#repository_owner` returns `"OrgOne"` from the crafted `repository.owner.login`; `Shipit.github(organization: "OrgOne")` finds `S1`; `verify_webhook_signature` succeeds. [1](#0-0) 
5. `PushHandler` resolves `repository_name` as `"victim/repo"` (from the same crafted payload) and calls `stack.sync_github` on `OrgTwo`'s stack, despite the signature only proving knowledge of `OrgOne`'s secret. [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
