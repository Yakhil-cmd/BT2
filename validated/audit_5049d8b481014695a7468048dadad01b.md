### Title
Tokens sent directly to the LiquidityPool are unaccounted for and permanently locked — (File: contracts/pool/src/guards.rs)

### Summary
The pool's `cash` field is an internal accounting book that is deliberately independent of the contract's actual token balance. Any tokens transferred directly to the pool contract outside of a controller-driven flow credit no shares, no cash, and no revenue, and there is no sweep or recovery entrypoint in `LiquidityPoolInterface`. Such tokens are permanently locked.

### Finding Description
Soroban has no `msg.value`, but the analog is a user calling `Token::transfer(user → pool)` directly, which is a permissionless path explicitly allowed in scope ("direct token transfers to the pool or controller"). The pool documentation states: "Cash is an accounting book, separate from the token balance" (contracts/pool/src/lib.rs:34-36). Booked cash only moves via owner-gated mutation legs (`supply`, `repay`, `recapitalize`, `flash_loan`, `claim_revenue`), all `#[only_owner]` where the owner is the controller (lib.rs:91-96, 130-252).

A direct transfer inflates the token balance but changes nothing in the books:

- `backing_shortfall` is computed purely from `cash + debt` vs `supply`, never from `token::Client::balance` (contracts/pool/src/guards.rs:61-66), so a donation does not reduce any shortfall.
- `claim_revenue` pays `min(cash, revenue shares)` (lib.rs:243-252); donated tokens are neither cash nor revenue shares.
- `recapitalize` credits `min(amount, backing_shortfall)` and refunds the remainder to the payer (contracts/pool/src/ops/recapitalize.rs:52-57) — it cannot surface pre-existing idle balance.
- The interface exposes no `sweep`/`recover`/`skim` function (lib.rs:99-326).

Consequence: when the market is solvent (`token balance >= cash`), a directly-sent token never becomes withdrawable cash and no entrypoint can move it — the user's tokens sit in the contract unaccounted forever, exactly matching the FeeBuyback bug class.

### Impact Explanation
Permanent freezing/loss of the sending user's funds. The tokens are unspendable by the pool (not booked as cash, so they cannot be lent out or paid as withdrawals/revenue) and unrecoverable by the user (no claim shares minted, no refund path). Mirrors the source finding's "ETH held unaccounted for and lost."

### Likelihood Explanation
Reachable by any unprivileged address with a single `transfer` call. Requires user error (sending to the pool address instead of calling `supply` via the controller), so likelihood is moderate but non-trivial — users interacting with tokens rather than the controller UI, or mistaken contract addresses, can hit it. Medium severity, consistent with the source report.

### Recommendation
Either provide a documented recovery path or make the donation productive:

1. Add an owner-gated `sweep(hub_asset)` entrypoint that computes `excess = token_balance - unscale_supply_floor(supplied) - pending obligations` and either books it as protocol revenue shares or returns it to a designated address, or
2. Document and enforce that stray balance is credited to cash in `recapitalize`/`claim_revenue` flows so it can at least back the market, and emit events making stuck funds observable.
3. Alternatively, accept the donation as an implicit `recapitalize`-style cash credit (without minting shares) so it reduces any future shortfall rather than being inert.

### Proof of Concept
1. Deploy pool + controller; create market `(hub_id, USDC)`; a supplier supplies 1000 USDC via `controller.supply` so `cash = 1000`, `token_balance = 1000`.
2. An unprivileged user calls `Token::transfer(user → pool, 500 USDC)`. Now `token_balance = 1500`, `cash = 1000`, `supply = 1000` — the 500 USDC credits nothing.
3. `get_reserves` still reports 1000; `claim_revenue` pays only booked revenue; `recapitalize` computes `backing_shortfall = max(0, 1000 - (1000 + 0)) = 0`, so it cannot touch the extra 500.
4. No entrypoint in `LiquidityPoolInterface` can move the 500 USDC; even full withdrawal of all supply leaves them trapped. Permanent loss confirmed.
