### Title
`Api::CCMenuController` bypasses per-token stack scoping, letting a stack-scoped `ApiClient` token read the deploy/build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The bug-class hint (Pyth confidence interval being computed/verified but silently ignored by the consuming code) maps onto a binding-vs-check mismatch in this engine: an `ApiClient` token is *scoped* to a single stack (`api_client.stack_id`), and `Api::BaseController` enforces that scope everywhere through its `stacks`/`stack` helpers — except in `Api::CCMenuController`, which re-implements `stack` and drops the scoping. The permission check (`require_permission :read, :stack`) still runs, but it only checks the *permission bit*, not *which* stack the token is bound to, so the enforced binding `token.stack ⇐⇒ stack acted on` is broken for this one endpoint.

### Finding Description
`Api::BaseController` defines the canonical, scope-respecting accessors: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` only within that restricted set. Every other controller that reads `params[:stack_id]` (e.g. `Api::HooksController`) goes through this `stack` method, so a scoped token can only ever "touch" the one stack it was issued for.

`Api::CCMenuController` overrides `stack` and bypasses the scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model rather than on the caller's `stacks` collection. `require_permission :read, :stack` (declared at the top of the controller) only calls `current_api_client.check_permissions!(:read, :stack)`: [3](#0-2) 

That method checks the string `"read:stack"` against the client's `permissions` array; it has no notion of *which* stack. So the equality that should hold — `stack_the_token_authorizes == stack_the_request_acts_on` — is enforced by `BaseController#stack`/`#stacks` but is broken specifically in `CCMenuController`, where any `stack_id` supplied in the URL is resolved regardless of `current_api_client.stack_id`.

Before the (hypothetical) fix: a token created with `stack_id: shipit_stack` and permission `read:stack` can call `GET /api/1/stacks/:any_other_stack_id/cc.xml` and receive that other stack's latest deploy/rollback status (`show` action renders `latest_deploy` via the CCMenu XML view), even though `Stack.where(id: current_api_client.stack_id)` (i.e., `stacks`) would have excluded it. The test fixture `here_come_the_walrus` API client is exactly a stack-scoped, `read:stack`-only client, demonstrating the intended scoping model that `CCMenuController` fails to honor: [4](#0-3) [5](#0-4) 

Note `CCMenuController` also independently re-authenticates using `params[:token]` rather than HTTP Basic auth (for CCTray client compatibility): [6](#0-5) 

This is a deliberate, documented deviation for the CCTray protocol, but it makes the missing stack-scope check in `#stack` the only thing standing between "authenticated for stack A" and "read status of stack B."

### Impact Explanation
This is an unauthenticated-scope escalation: "escalation into `Shipit.github_teams` authorization" is not applicable, but it matches "unauthenticated read of stack state, task streams or deploy output" at the High tier — a token deliberately restricted to one stack's `read:stack` permission can read build/deploy status (pass/fail, latest activity, deploy link) of stacks it was never granted access to, by only knowing (or guessing/enumerating) another stack's `stack_id`/repo path. This breaks the tenant-isolation guarantee that per-stack `ApiClient` tokens are supposed to provide.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment that issues stack-scoped API tokens (e.g., to give a specific team or CI integration `read:stack` visibility on one stack only, as shown by the `here_come_the_walrus` fixture) and exposes the CCMenu (CCTray) endpoint, which is commonly polled by build-status dashboards/widgets using bare tokens in the URL. No privileged access is required beyond possession of *any* valid, even minimally-scoped, `read:stack` token — exactly the credential this endpoint's own `authenticate_api_client` override accepts via `params[:token]`.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (as `Api::StacksController#stack` and `Api::BaseController#stack` do), i.e. `@stack ||= stacks.from_param!(params[:stack_id])`, so the stack a token authorizes is always the stack it is allowed to touch.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (mirrors fixture `here_come_the_walrus`).
2. Generate its token via `ApiClient#authentication_token`.
3. Request `GET /api/1/stacks/:B/cc.xml?token=<token>` where `B` is a different stack the client is not scoped to.
4. `CCMenuController#stack` resolves `B` via `Stack.from_param!` (unscoped), `require_permission :read, :stack` passes because the token has the `read:stack` bit, and the response renders `B`'s latest deploy status — demonstrating the token reads a stack outside the `stack_id` it was authorized for. Contrast with `Api::StacksController#show`, where the same token requesting stack `B` would raise `ActiveRecord::RecordNotFound` because `stacks` filters to `stack_id: A` first.
