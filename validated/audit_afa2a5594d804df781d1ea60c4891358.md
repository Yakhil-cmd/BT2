### Title
Disabled trust check on indirect correspondents allows a low-privilege paired device to invoke privileged wallet/shared-address/signing message handlers - (File: wallet.js)

### Summary
`handleMessageFromHub()` in `wallet.js` receives every device message routed through the hub and dispatches it by `subject` to privileged wallet handlers (shared-address creation/approval, multisig `sign` requests, unpairing, etc.). The code that was meant to restrict which subjects an *indirect* (lower-trust) correspondent may send is commented out, so any device classified as `is_indirect=1` is treated exactly like a fully, directly-paired/trusted correspondent for all subjects.

### Finding Description
`device.js`'s hub-message handler classifies the sender as `is_indirect` from the `correspondent_devices` table and passes `bIndirectCorrespondent` into `handleMessageFromHub`: [1](#0-0) 

In `wallet.js`, the intended authorization boundary between direct and indirect correspondents is explicitly disabled: [2](#0-1) 

Because this check never executes, `bIndirectCorrespondent` is not consulted anywhere else in `doHandle()`, so an indirect correspondent can reach every subject handler in the same `switch(subject)` block that a fully-trusted, directly-paired device can reach, including:
- `create_new_shared_address` / `approve_new_shared_address` / `reject_new_shared_address` (shared multisig address setup) [3](#0-2) 
- `sign` (a request to co-sign a unit for a multisig/shared address on this device) [4](#0-3) 
- `removed_paired_device` (device removal/unpairing flow) [5](#0-4) 

"Indirect" correspondents are devices that were never directly paired/verified by the local user but were learned about transitively (e.g., introduced as a cosigner's device during shared-address setup). The commented-out gate was the mechanism meant to keep such lower-trust devices restricted to only a small allow-list of setup subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`), analogous to the InLong flaw where a valid-but-unprivileged, authenticated session was able to reach privileged endpoints that should have required a higher trust level. Here the "session" is the device-message channel and the "privilege boundary" is direct vs. indirect correspondent, but the enforcement was removed while the classification and comment describing the intended restriction remain in the code.

### Impact Explanation
An indirect (lower-trust) paired device can drive the full wallet-message state machine as though it were a directly-trusted correspondent: it can initiate/approve shared-address creation flows, submit `sign` requests for multisig/shared addresses, and trigger unpairing logic — flows that were designed to be gated to a smaller, safer subset of subjects for indirect correspondents. Depending on downstream handler logic (`walletDefinedByAddresses`, `findAddress`), this weakens the intended trust segregation between wallet participants and can facilitate social-engineering-free protocol-level abuse of multisig/shared-address coordination, which is the direct wallet/contract-message-handling attack surface explicitly in scope.

### Likelihood Explanation
Reaching this code path only requires being classified as `is_indirect=1` in `correspondent_devices`, which happens automatically via existing wallet flows that add correspondents introduced by other parties (multisig/shared-address setup, arbiter-contract cosigner exchange, etc.) — no explicit user pairing confirmation is needed for the device to be treated as fully trusted here. This makes the condition realistically reachable for participants already interacting in a shared-address/contract context.

### Recommendation
Restore and enforce the intended authorization check: for `bIndirectCorrespondent`, only allow the minimal safe subject set (or explicitly define a narrower vetted allow-list per subject's sensitivity, e.g., disallow `sign`, `approve_new_shared_address`, `removed_paired_device` from indirect correspondents) and reject all other subjects with `callbacks.ifError(...)`, matching the original design intent documented in the removed comment.

### Proof of Concept
1. Get added as an `is_indirect=1` correspondent of the victim (e.g., by being introduced as a cosigner device during a shared-address/arbiter-contract flow so `addIndirectCorrespondents`/equivalent inserts a `correspondent_devices` row with `is_indirect=1`).
2. Send a `hub/message` to the victim's hub with `subject: "sign"` (or `create_new_shared_address`/`approve_new_shared_address`) properly signed with the indirect device's own key, targeted at the victim (`objDeviceMessage.to = victim`).
3. `device.js` validates the signature/hash and looks up `is_indirect` from `correspondent_devices`, finds the sender known, and calls `handleMessage(rows[0].is_indirect)` → `handleMessageFromHub(ws, json, pubkey, true, callbacks)`. [6](#0-5) 
4. In `wallet.js`, the `bIndirectCorrespondent` gate is commented out, so execution proceeds directly into the `switch(subject)` handler for `sign`/shared-address subjects exactly as it would for a directly trusted correspondent. [7](#0-6)
