### Title
Cross-repository CI status forgery via unscoped `StatusHandler` webhook lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
In a multi-organization Shipit deployment, GitHub webhook signatures are verified per-organization using an org-derived field from the request body, but the `status` event handler applies its effect (attaching a commit status) using a global, repository-unscoped lookup keyed only on the commit SHA. This breaks the binding between "the organization whose secret authenticated this webhook" and "the repository/commit the webhook is allowed to write to."

### Finding Description
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the signature against based on a value read out of the still-unverified JSON body: [1](#0-0) [2](#0-1) 

This organization-scoped secret model is an explicitly supported configuration documented for multi-org installs, where each GitHub organization has its own `webhook_secret`: [3](#0-2) 

After the signature check passes (proving only that *some configured organization's* secret matches), the raw, unvalidated `params` are dispatched to event handlers: [4](#0-3) 

The `status` event's handler, `Shipit::Webhooks::Handlers::StatusHandler`, only requires `sha` and `state` — it does **not** require or check any `repository` field at all — and resolves the target commit(s) with a global, cross-stack, cross-repository query: [5](#0-4) 

Compare this to every other handler (`PushHandler`, the `pull_request/*` handlers), which explicitly scope to the repository named in the payload via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`: [6](#0-5) [7](#0-6)  The base `Handler` class even provides a `stacks`/`repository_name` helper for this scoping that `StatusHandler` does not use: [8](#0-7) 

**The equality that is supposed to hold:**
`organization whose webhook_secret authenticated the request == organization/repository whose commit is being written`

**What actually happens for `status` events:**
`organization whose webhook_secret authenticated the request` is derived from `repository.owner.login` in the payload, but `Commit.where(sha: params.sha)` matches *any* commit in *any* stack across *any* organization configured in the Shipit instance, with no re-check that the commit's repository/organization matches the one that produced the valid signature.

Because git commit SHAs are not secrets (they are visible via GitHub's public/authenticated API, PRs, CI logs, `git log`, etc.), an attacker who can get GitHub to deliver *any* legitimately signed `status` webhook to the shared Shipit endpoint — e.g., by holding push/CI access to a repository under one of the (possibly many) organizations configured in `secrets.yml`, or by controlling a commit-status-setting integration on that org — can set `repository.owner.login` to their own org (so `verify_signature` passes with their own valid `webhook_secret`) while setting `sha` to a commit SHA that belongs to a completely different organization's stack. Shipit will then attach the attacker-chosen `state`/`context` to that unrelated commit.

### Impact Explanation
Commit status directly feeds `Commit#add_status`, which:
- Emits `deployable_status` / schedules merges via `stack.schedule_merges` when the state becomes `pending` or `success`: [9](#0-8) 
- Determines `Commit#deployable?`, which gates deploys (the API explicitly checks `commit.deployable?` when `require_ci` is set): [10](#0-9)  and is used as the CI gate documented for `ci.require`: [11](#0-10) 
- Feeds `schedule_continuous_delivery` on commit creation, which can drive fully automatic deploys for stacks that have continuous delivery configured: [12](#0-11) 

By forging a `success` status from one organization's authenticated webhook onto a commit belonging to a *different* organization's stack, an attacker can make an otherwise CI-gated or continuous-delivery-gated commit appear deployable, enabling an unauthorized deploy/merge decision on a stack outside the authenticated organization's scope. This matches the "unauthorized deploy/merge, cross-repository write" impact class.

### Likelihood Explanation
This requires:
1. A Shipit instance configured with multiple GitHub organizations (a documented, supported configuration), and
2. The attacker being able to get GitHub to deliver a validly-signed `status` webhook for at least one of the configured organizations (e.g., ordinary CI/commit-status write access to a repo in one org they participate in — no Shipit session, API token, or `webhook_secret` compromise required, since GitHub itself computes the signature for genuine deliveries).
3. Knowledge of a target SHA in another org's tracked stack, which is generally discoverable (SHAs are not secret).

This is a moderate-likelihood scenario limited to multi-org deployments, but the primitive itself (missing repository scoping in `StatusHandler`) is a clear code-level defect independent of how hard it is to trigger in a given deployment.

### Recommendation
Scope `StatusHandler` (and any other handler lacking repository scoping) the same way `PushHandler` and the `pull_request/*` handlers do: require `repository.full_name` in the params schema, resolve the repository via `Shipit::Repository.from_github_repo_name`, and restrict the `Commit` lookup to `stacks` belonging to that repository (`Commit.where(sha: params.sha, stack: repository.stacks)` or equivalent), rather than a global `Commit.where(sha: ...)` across the whole instance. Additionally, consider re-validating that `repository.owner.login` in the payload used to select the webhook secret matches the repository actually referenced by the event's own repository field, closing any residual gap between "authenticated org" and "acted-upon repository."

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` (per `docs/setup.md`'s multi-org example).
2. `org-a` has a Shipit stack tracking commit `deadbeef...` which currently has no successful CI status and is not `deployable?`.
3. As a contributor with ordinary commit-status write access to a repository under `org-b`, trigger (or directly call GitHub's Statuses API for) a `status` event whose JSON body is:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/whatever",
  "repository": { "owner": { "login": "org-b" } }
}
```
GitHub signs this payload with `org-b`'s real `webhook_secret` and delivers it to Shipit's shared `/github/webhooks` endpoint.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-b")` and successfully verifies the signature (it is genuinely `org-b`'s payload/secret pair).
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, which matches the `org-a` commit (there is no repository check), and calls `commit.create_status_from_github!(params)`, attaching a `success` status to it.
6. `org-a`'s commit now appears `deployable?`/eligible for merge-queue or continuous-delivery processing, despite the status having been injected via a completely different organization's credentials.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
