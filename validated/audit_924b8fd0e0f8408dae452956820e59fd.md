### Title
Webhook signature validated against `repository.owner.login`'s secret while the event is dispatched against `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  Once the signature is accepted, the actual event handlers resolve the target `Repository`/`Stack` using a completely different, unrelated field of the same payload: `payload.dig('repository', 'full_name')`. [3](#0-2)  Nothing cross-checks that `repository.owner.login` (used to pick the signing secret) actually matches the owner encoded in `repository.full_name` (used to pick the acted-upon repository).

### Finding Description
Shipit supports multiple independent GitHub organizations, each with its own App/webhook secret configured under `Shipit.github(organization:)`. [4](#0-3)  `verify_webhook_signature` performs a straightforward HMAC comparison of the raw body against the secret belonging to whichever organization name was extracted from the payload. [5](#0-4) 

The binding that should hold is: *the organization whose secret authenticated the signature* == *the repository/organization the event actually writes to*. This binding is broken because:
- The signature-selection field (`repository.owner.login` / `organization.login`) and the dispatch field (`repository.full_name`) are both attacker-supplied JSON fields inside the same unauthenticated HTTP body, but only the former is used to pick the secret and only the latter is used to resolve the `Repository` acted upon. [2](#0-1) [3](#0-2) 
- `Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up any matching repository record in the database, with no verification that this repository belongs to the organization that signed the request. [6](#0-5) 

An organization admin who legitimately owns a GitHub App/webhook secret for their own organization ("OrgA") — a credential they are expected to hold and configure themselves, not a stolen or privileged Shipit credential — can therefore forge a webhook whose `X-Hub-Signature` is valid for OrgA (because `repository.owner.login`/`organization.login` = `"OrgA"`) while `repository.full_name` names a repository/stack belonging to a completely different, victim organization ("OrgB") that they do not control.

### Impact Explanation
Handlers keyed off `full_name` (e.g. `push`, `status`, `check_suite`, `pull_request`) will resolve the victim's `Stack`/`Repository` and act on it as if the event genuinely came from GitHub for that repository — e.g. queuing `GithubSyncJob`, creating/mutating `Status` records for a victim commit, or driving check-run/PR state used by Shipit's merge-safety and deployability checks. This lets an attacker who only controls their own organization's webhook secret forge CI/status/push state for a repository they don't own, corrupting the signals Shipit relies on to gate deploys and merges — a cross-organization/cross-repository write achieved purely by exploiting the mismatch between the field verified by the signature check and the field used for dispatch.

### Likelihood Explanation
The `/webhooks` endpoint is intentionally public and unauthenticated by design (protected only by the HMAC signature), so no session, `ApiClient` token, or GitHub App private key is required. The only prerequisite is administering any one organization already configured in this Shipit instance and knowing that organization's own webhook secret — something the org admin necessarily possesses because they configured it. Constructing a payload with mismatched `repository.owner.login` vs `repository.full_name` requires no special tooling beyond crafting JSON and computing an HMAC-SHA1 over it.

### Recommendation
After selecting the signing organization from the payload, verify that `repository.full_name`'s owner segment matches the same organization used to select the webhook secret (or, better, verify the signature using the secret associated with the *repository* actually referenced by `full_name`, and reject if that repository's org doesn't match the signer). Reject any webhook where these two fields diverge.

### Proof of Concept
1. Attacker administers `OrgA`, a legitimate organization onboarded to the shared Shipit instance, and knows `OrgA`'s configured `webhook_secret`.
2. Attacker crafts a `push` (or `status`/`check_suite`) JSON payload where:
   - `repository.owner.login` = `"OrgA"` (and/or `organization.login` = `"OrgA"`)
   - `repository.full_name` = `"OrgB/victim-repo"` (a repository belonging to another org already tracked by Shipit)
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret. [1](#0-0) 
5. `Shipit::Webhooks.for_event('push')` handlers run and resolve `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, acting on the victim's stack despite the request never having been signed by `OrgB`. [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
