### Title
No upper-bound validation on `timestamp`/`mci`/`age` values in asset `issue_condition`/`transfer_condition` lets an asset issuer permanently freeze transferability of an already-issued asset - (File: definition.js)

### Summary
The reported bug is that `AuctionRebalanceModuleV1.startRebalance` accepts an unbounded `_rebalanceDuration` from the manager with no maximum check, so a misconfigured (or malicious) duration can lock a `setToken` for an unbounded period with no recovery path for holders. The analogous weakness in `ocore` is in the validation of asset spending conditions: an asset issuer can attach an `issue_condition`/`transfer_condition` using the `timestamp`, `mci`, or `age` operators with an arbitrarily large numeric bound, and `ocore` performs no sanity/maximum check on that value. Because asset definitions (and their conditions) are immutable once published, this can permanently prevent all future transfers (or issuance) of the asset for as long as the issuer chooses — effectively forever from a practical standpoint — with no protocol-level safety valve, exactly mirroring the "misconfigured duration locks funds with no recourse" bug class.

### Finding Description
When an asset is defined, `validateAssetDefinition` in `validation.js` validates the optional `issue_condition`/`transfer_condition` fields via `Definition.validateDefinition(...)`: [1](#0-0) 

Inside `validateDefinition`, the `timestamp`, `mci`, and `age` operators are validated only for having a valid relation string and a non-negative integer value — there is no upper bound at all on the numeric value: [2](#0-1) 

At spend time, `validatePaymentInputsAndOutputs` evaluates this same `issue_condition`/`transfer_condition` via `Definition.evaluateAssetCondition`, and if it is not satisfied, the transfer or issuance is rejected outright with no alternative path: [3](#0-2) 

The actual evaluation for `timestamp`/`mci` conditions simply compares against `last_ball_timestamp`/`last_ball_mci` of the unit being validated: [4](#0-3) 

Since an asset's `issue_condition`/`transfer_condition` is fixed permanently at asset-definition time (there is no mechanism analogous to `address_definition_change` for asset conditions), an issuer can set, e.g., `['timestamp', ['>', 99999999999]]` (a date far in the future) as the `transfer_condition`. Every subsequent transfer of that asset will fail this asset condition check until that timestamp is reached, freezing all holders' balances of the asset indefinitely — just like the reported `AuctionRebalanceModuleV1` case where an unbounded `_rebalanceDuration` locks the `setToken` with no way for affected parties to recover.

### Impact Explanation
Any holder who receives units of an asset defined with such a misconfigured (or intentionally malicious) `transfer_condition`/`issue_condition` has their asset balance permanently frozen — they cannot transfer, and if `issue_condition` is likewise unbounded, no further issuance is possible either. This is a direct "AA/asset fund freezing" outcome reachable purely by an asset issuer defining the asset (a role explicitly permitted as an in-scope actor), with the protocol offering no maximum bound, expiry cap, or override mechanism to protect downstream unprivileged holders, matching the Medium severity of the original report (no safety check on an attacker/manager-controlled duration parameter that can lock funds).

### Likelihood Explanation
Likelihood is Medium: this requires the asset issuer to deliberately or mistakenly set the condition value, similar to how the original bug requires the SetToken manager to mis-set `_rebalanceDuration`. Because `ocore`'s protocol performs no validation to prevent such absurd values, and asset definitions can't be amended afterward, this is trivially triggerable by any account that defines an asset via a `payment`/`asset` message (or an AA issuing an asset), and users receiving the asset would only discover the freeze when attempting to transfer.

### Recommendation
Add a sanity upper bound (and possibly a maximum look-ahead window relative to current network time or MCI) for `timestamp`/`mci`/`age` values used inside `issue_condition`/`transfer_condition` validation in `definition.js`, similar to other numeric caps already enforced elsewhere in the same function (e.g., `MAX_COMPLEXITY`, `weight <= 1000`, `formula` length limits). Alternatively, document this as an inherent, expected risk of asset conditions and require wallets to warn users before accepting assets with such conditions.

### Proof of Concept
1. Author A defines a new asset with:
```
{
  app: 'asset',
  payload: {
    is_private: false,
    is_transferrable: true,
    auto_destroy: false,
    fixed_denominations: false,
    issued_by_definer_only: true,
    cosigned_by_definer: false,
    spender_attested: false,
    transfer_condition: ['timestamp', ['>', 99999999999]]
  }
}
```
This passes `validateAssetDefinition`/`validateDefinition` because only `isNonnegativeInteger(value)` is checked (`definition.js:480-495`).
2. Author A issues units of this asset to holder B.
3. Holder B attempts to transfer the asset to anyone. `validatePaymentInputsAndOutputs` calls `Definition.evaluateAssetCondition`, which evaluates `timestamp > 99999999999` against `last_ball_timestamp` (`definition.js:1036-1048`) — always false until the year 5138 — so the transfer is rejected with `"transfer or issue condition not satisfied"` (`validation.js:2652-2653`).
4. Because there is no mechanism to alter an asset's `transfer_condition` post-definition, holder B's balance of that asset is permanently frozen.
