### Title
Missing `return` after caught exception in private-payment hash validation lets an attacker-supplied payload crash the whole node - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments()` computes a hash over an attacker-controlled private-payment payload inside a `try`, but the `catch` block does not `return` after handling the error, so execution falls through and continues to use the (now undefined) hash result and to re-enter the validation/callback flow a second time. This mirrors the emmett-core advisory pattern: untrusted, attacker-formattable input (there, a raw Cookie header; here, the JSON payload of a private payment message) is fed into a parser/hasher whose exception path is only partially handled, letting a single malformed message reach code that was never designed to run twice, ultimately triggering the node's `uncaughtException` handler, which intentionally re-throws and crashes the process (`network.js:4530-4543`).

### Finding Description
`network.js` stores private-payment chains received from any peer (hub, direct peer, or later replayed from the `unhandled_private_payments` table) without deep structural validation of the payload — `handleOnlinePrivatePayment()` only checks that `arrPrivateElements` is a non-empty array and that unit/message_index/output_index look superficially valid [1](#0-0) . The raw, attacker-supplied JSON is persisted as-is (`JSON.stringify(arrPrivateElements)`), then later re-read and processed by `handleSavedPrivatePayments()`:

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
``` [2](#0-1) 

`objectHash.getBase64Hash` internally throws whenever the payload contains structures that `getSourceString`/`cleanNulls`/well-formedness checks reject (e.g. disallowed types, lone-surrogate strings, or objects that don't match the expected canonical shape) — this is exactly the class of "unexpected characters break a strict parser" bug the emmett-core advisory describes for `SimpleCookie.load()`.

Because the `catch` block is missing a `return`, after handling the error (which already invokes `deleteHandledPrivateChain(..., cb)` — completing the `async.each` iteration once) the function *continues* and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which will eventually invoke the same iteration's `cb` a second time through one of its `ifOk`/`ifError`/`ifWaitingForChain` callbacks. `async.each`'s per-item callback is a "call-once" guarded callback; invoking it twice throws (`Callback was already called`) synchronously from inside a nested DB/network callback with no surrounding `try/catch`. This uncaught exception is not caught anywhere in the call chain and reaches the global `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws to crash the process:
```js
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [3](#0-2) 

### Impact Explanation
Any unauthenticated peer (or hub-relayed sender) can send a private-payment message whose payload is structurally invalid enough to make `objectHash.getBase64Hash` throw, but is otherwise accepted by the shallow checks in `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` [4](#0-3) . Once such a payload is queued into `unhandled_private_payments` and later processed by `handleSavedPrivatePayments`, the missing `return` causes a double-callback invocation that crashes the receiving full node or wallet process. This is a remote, single-message, unauthenticated denial-of-service against any node/wallet that accepts private payments — directly comparable in class and reachability to the emmett-core CookieError DoS (unauthenticated request → unhandled exception in strict parsing/hashing code → process failure), except here the crash is the entire ocore process rather than a single HTTP request, making it more severe (a node unable to confirm/relay anything until restarted).

### Likelihood Explanation
Likelihood is high for any full node or wallet that processes private payments (a core, exposed feature, not an admin-only or light-proof-only path): the attacker only needs to construct a payload that objectHash's canonicalization rejects (well within reach given the shallow field-presence checks performed before this code runs), and send it via the normal `private_payment`/`private_payments` message flow that any peer or hub client can invoke.

### Recommendation
Add a `return` (or restructure with an `if/else`) after the `catch` block in `validateAndSave()` inside `handleSavedPrivatePayments()` so that once the error path (`deleteHandledPrivateChain(..., cb)`) has been taken, the function does not fall through to also call `privatePayment.validateAndSavePrivatePaymentChain(...)` with an undefined `json_payload_hash`. Additionally, consider validating the private-payment payload with `string_utils.isObjectWellFormed`/canonical-shape checks (similar to `isObjectWellFormed` used for units) before calling `objectHash.getBase64Hash`, so malformed input is rejected earlier with a controlled error rather than an exception.

### Proof of Concept
1. As any peer (or via `handlePrivatePaymentChains`/`private_payments` hub message), send a `private_payment`/`private_payments` message whose head element's `payload` contains a value that `objectHash.getBase64Hash` cannot canonicalize (e.g., a value type not accepted by `getSourceString`, or a lone-surrogate string) while still satisfying the superficial checks in `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` (non-empty array, valid unit hash length, non-negative `message_index`, non-empty `payload.asset`/`inputs`/`outputs`).
2. The malformed chain is stored in `unhandled_private_payments` and later picked up by `handleSavedPrivatePayments()`.
3. `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws inside the `try`; the `catch` runs `deleteHandledPrivateChain(...)` but does not return.
4. Execution falls through to call `privatePayment.validateAndSavePrivatePaymentChain(...)`, which eventually invokes the `async.each` iteration's `cb` a second time.
5. The double invocation throws `Callback was already called`, which is uncaught and reaches `process.on('uncaughtException')`, which re-throws and crashes the node process.

(Note: I was not able to directly inspect `object_hash.js`'s exact throw conditions for `getBase64Hash`/`getSourceString` within the available index snippets, so the precise malformed-payload shape needed to trigger the throw should be confirmed by a developer with full source access; the control-flow bug (missing `return`) and its consequence via `async.each`'s call-once guard are confirmed from the cited code.)
