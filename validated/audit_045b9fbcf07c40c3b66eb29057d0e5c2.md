### Title
`verifySeals` Pre-Permissionless Quorum Undercount Enables Single-Seal Block Acceptance on Sync Nodes — (`blockchain/block_validator.go`)

### Summary

`verifySeals` uses `2*sealer.F()+1` to compute the committed-seal threshold for pre-permissionless blocks. `sealer.F` mirrors `calcFaultTolerance` exactly, but `calcFaultTolerance` was designed for the `ceil(2N/3)` quorum regime. When the effective committee size is `< 4`, the consensus core switches to a stricter rule (`quorum = effectiveSize`), but `sealer.F` does not. For `CommitteeSize=3, qualifiedLen>3`, `sealer.F` returns `0`, giving a `verifySeals` threshold of `1`, while `calcQuorumSize` returns `3`. A single malicious qualified validator can craft a block with one committed seal that passes `verifySeals` on every sync node, causing a chain split.

### Finding Description

In `blockchain/block_validator.go`, the pre-permissionless branch of `verifySeals` computes the required committed-seal count as:

```go
if validSeal < 2*v.sealer.F(blockNum, qualifiedLen, committeeSize)+1 {
    return istanbul.ErrInvalidCommittedSeals
}
``` [1](#0-0) 

`sealer.F` is implemented as:

```go
func (m *IstanbulSealer) F(_ uint64, qualifiedLen, committeeSize int) int {
    if qualifiedLen > int(committeeSize) {
        return int(math.Ceil(float64(committeeSize)/3)) - 1
    }
    return int(math.Ceil(float64(qualifiedLen)/3)) - 1
}
``` [2](#0-1) 

With `qualifiedLen=10, committeeSize=3`: `ceil(3/3)-1 = 0`, so the threshold is `2*0+1 = 1`.

The consensus core uses `calcQuorumSize`:

```go
func calcQuorumSize(qualifiedLen int, committeeSize uint64) int {
    size := min(qualifiedLen, int(committeeSize))
    if size < 4 {
        return size   // returns 3, not 1
    }
    return int(math.Ceil(float64(2*size) / 3))
}
``` [3](#0-2) 

The effective size `min(10,3)=3` is `< 4`, so the consensus core requires all 3 committee members to sign. `sealer.F` does not implement this small-committee special case, producing a threshold that is 3× too low.

Additionally, the pre-permissionless author check only verifies membership in the qualified set, not that the author is the actual elected proposer for that block:

```go
if !qualifiedSet.Contains(author) {
    return consensus.ErrUnauthorized
}
``` [4](#0-3) 

Committed seals are validated against the full council, not the 3-member committee: [5](#0-4) 

### Impact Explanation

A single malicious qualified validator can:
1. Construct a block at the correct height with a valid parent hash.
2. Sign it as author (proposer seal — valid because they are in `qualifiedSet`).
3. Include only their own committed seal (1 council-member signature).
4. Broadcast it via P2P to syncing nodes.

Syncing nodes call `validateHeader` → `verifySeals`. The check `validSeal (1) < 2*F(10,3)+1 (1)` evaluates to `false`, so the block is accepted. Live consensus nodes, which use `calcQuorumSize(10,3)=3`, would never have finalized such a block. The result is **consensus divergence**: sync nodes accept a block that honest live-consensus nodes never produced, causing a permanent chain split.

This falls squarely within the allowed impact: *"Invalid state transition, invalid block/proof/snapshot acceptance, or consensus divergence on honest nodes."*

### Likelihood Explanation

- Requires a single malicious qualified validator — not majority collusion, not a compromised key, not an external service.
- The governance configuration `CommitteeSize=3` with `qualifiedLen>3` is a valid and reachable state (governance voters can set `CommitteeSize` to any value ≥ 1).
- The P2P sync path is a standard public-facing surface; any node syncing from a malicious peer is exposed.
- No cryptographic break is required; the attacker uses their own legitimate signing key.

### Recommendation

Fix `sealer.F` to mirror the small-committee branch of `calcQuorumSize`. When `effectiveSize = min(qualifiedLen, committeeSize) < 4`, the quorum is `effectiveSize`, so `f` must satisfy `2f+1 = effectiveSize`, i.e., `f = effectiveSize - 1`. The corrected implementation:

```go
func (m *IstanbulSealer) F(_ uint64, qualifiedLen, committeeSize int) int {
    size := min(qualifiedLen, committeeSize)
    if size < 4 {
        return size - 1   // 2f+1 == size (all members required)
    }
    if qualifiedLen > committeeSize {
        return int(math.Ceil(float64(committeeSize)/3)) - 1
    }
    return int(math.Ceil(float64(qualifiedLen)/3)) - 1
}
```

Alternatively, unify the threshold computation by calling `calcQuorumSize` (or an equivalent exported helper) directly from `verifySeals` instead of reconstructing it via `2*F+1`.

### Proof of Concept

```go
// Demonstrates: calcQuorumSize(10,3)=3 but 2*F(10,3)+1=1
func TestQuorumMismatch(t *testing.T) {
    sealer := istanbul.NewSealerImpl(params.MainnetChainConfig, nil)
    qualifiedLen, committeeSize := 10, 3

    f := sealer.F(1, qualifiedLen, committeeSize)
    verifySealsThreshold := 2*f + 1
    coreQuorum := calcQuorumSize(qualifiedLen, uint64(committeeSize))

    // verifySealsThreshold == 1, coreQuorum == 3
    assert.Equal(t, 1, verifySealsThreshold)  // passes
    assert.Equal(t, 3, coreQuorum)            // passes
    assert.Equal(t, verifySealsThreshold, coreQuorum) // FAILS — mismatch
}
```

A full integration test would:
1. Set up a chain with `CommitteeSize=3` and 10 qualified validators (pre-permissionless, pre-Randao).
2. Have a single validator craft a block with 1 committed seal (their own).
3. Call `BlockValidator.verifySeals` on that block.
4. Assert it returns `nil` — confirming a block that honest consensus would never produce is accepted by the sync validator.
