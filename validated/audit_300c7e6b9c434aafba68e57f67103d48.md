### Title
Webhook signature verification is keyed by an attacker-controlled organization field that is decoupled from the repository/commit actually written — cross-repository forged CI statuses and syncs - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification from a field inside the unauthenticated request body itself (`repository.owner.login` / `organization.login`). The event handlers that subsequently act on the same body, however, use a *different* field — `repository.full_name` (or, for status events, no repository field at all, only `sha`) — to decide what Stack/Commit to mutate. Because the field used to pick the verification key is never checked for consistency with the field used to select the write target, an attacker can freely mix organizations/repositories within one payload, exactly the "data vs. dataLength" decoupling described in the report: one part of the payload is used to authorize, a different, unchecked part is used to act.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is taken straight from the JSON body being verified — it is attacker-controlled data, not something Shipit already trusts. `Shipit.github(organization: repository_owner)` returns the `GitHubApp` instance configured for whatever org name the attacker put in the payload.

`lib/shipit/github_app.rb#verify_webhook_signature`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

The setup docs explicitly document `webhook_secret` as **optional** per organization, and the sample multi-org config (`config/secrets.development.shopify.yml`) shows several orgs each independently configured, with `webhook_secret` possibly left blank: [3](#0-2) [4](#0-3) 

If any single organization configured on the instance has no `webhook_secret` set, then choosing that org's name for `repository.owner.login` makes `verify_signature` unconditionally pass, regardless of the actual `X-Hub-Signature` header (or its absence).

Once verification passes, `Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers against the *same* raw JSON, but the handlers key off a different field:

`app/models/shipit/webhooks/handlers/handler.rb`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`repository.full_name` is never required to correspond to `repository.owner.login` used for the signature check. For the `push` handler: [6](#0-5) 

Worse, `StatusHandler` doesn't even use the repository field — it acts purely on the attacker-supplied `sha`, across every commit in the database, regardless of stack/repo:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

That forged status directly feeds `Commit#deployable?`, which gates whether a commit can be shipped: [8](#0-7) 

### Impact Explanation
- **Binding broken**: "an organization that authenticated" (`repository.owner.login`, used to pick the verifying `webhook_secret`) `≠` "the repository/commit that is written" (`repository.full_name` for push/PR handlers, or bare `sha` for status handler, with no owner check at all).
- An unprivileged attacker with **no credentials whatsoever** can send a POST to `/webhooks` claiming `repository.owner.login` = any organization on the multi-tenant instance that has no `webhook_secret` configured (an explicitly supported/optional configuration per `docs/setup.md`), which trivially satisfies `verify_webhook_signature`.
- The same forged body's `repository.full_name`/`sha` can reference a *completely different, victim* organization's repository/commit that does have proper GitHub-side protections. The attacker can:
  - Forge a `status` event to create a fake "success" `Status` for any known commit `sha` on any stack instance-wide, satisfying `ci.require` and unblocking `Commit#deployable?` — leading to an **unauthorized deploy**.
  - Forge `push` events to trigger `stack.sync_github(expected_head_sha:)` on a victim's stack, or forge `pull_request` events to archive/unarchive/create review stacks belonging to a repository the attacker never proved control over.
- This matches the Critical impact bar of "an unauthorized deploy" and the High bar of unauthenticated manipulation of stack/commit state.

### Likelihood Explanation
Exploitability only requires that at least one organization/app entry in the Shipit deployment's multi-org GitHub config omit `webhook_secret` — a state explicitly presented as valid/optional in the setup documentation and sample config. Any instance serving more than one organization (a supported, documented use case) is exposed; no attacker credentials, tokens, or GitHub access are needed, only knowledge of a target commit SHA or repository full name (both public, observable information on GitHub).

### Recommendation
- Cross-check that the organization used to select the verifying secret (`repository.owner.login`/`organization.login`) matches the owner encoded in `repository.full_name` before dispatching to handlers, rejecting mismatches.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; either require a secret for every configured organization or fail closed.
- In `StatusHandler`, scope `Commit.where(sha:)` lookups to commits belonging to the repository identified in `repository.full_name` (and confirm that repository's owner matches the organization used for signature verification), instead of matching on `sha` alone across the entire instance.

### Proof of Concept
1. Instance is configured with two orgs, e.g. `orgA` (no `webhook_secret` set) and `victim-org` (has a `webhook_secret`, deploys `victim-org/app`), per the supported multi-org pattern shown in `config/secrets.development.shopify.yml`.
2. Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: status
(no X-Hub-Signature required)

{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/whatever" },
  "sha": "<sha of an undeployed commit on victim-org/app that is missing required CI>",
  "state": "success",
  "context": "ci/required-context"
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`; since `orgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (looked up purely by `sha`, with no repository scoping), and calls `create_status_from_github!`, injecting a forged "success" status for `ci/required-context`.
5. The victim commit's `deployable?` now returns `true`, allowing an operator (or continuous deployment) to ship a commit that never actually passed CI — an unauthorized deploy enabled purely by an unauthenticated cross-organization webhook forgery.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
