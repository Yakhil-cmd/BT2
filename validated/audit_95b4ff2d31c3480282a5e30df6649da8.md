### Title
Webhook signature is verified against `repository.owner.login`, but repository/stack resolution uses the unverified `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (via `repository_owner`), but the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`) resolve the target `Repository`/`Stack` using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a signature that is valid for organization A's webhook secret can carry a payload whose `full_name` points at organization B's repository.

### Finding Description
`WebhooksController` picks the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-organization app config (each with its own independent `webhook_secret`) via `github_app_config`: [3](#0-2) 

Once the signature "passes" for whichever organization's app matches `repository.owner.login`, the raw parsed JSON is handed unchanged to the event handlers: [4](#0-3) 

But the base `Handler` class — used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. — resolves which `Stack`s to operate on using `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `full_name` into `owner/name` and looks it up directly: [6](#0-5) 

This is exactly the same bug class as the reported analog: two related pieces of data are supposed to describe the same source, but only one (`repository.owner.login`, used to pick the verifying secret) is covered by the cryptographic check, while the other (`repository.full_name`, used to pick the actually-affected `Stack`) is trusted unchecked. The binding that should hold — "the GitHub organization whose secret authenticated the request == the repository whose stacks are written" — is broken.

`PushHandler` uses `stacks` to trigger a re-sync: [7](#0-6) 

and, from the existing test suite, `status` events are handled by writing `Status` attributes (`target_url`, `state`, `description`, `context`) taken straight from the payload onto the commit of whatever stack `full_name` resolves to: [8](#0-7) 

### Impact Explanation
An attacker who administers (or otherwise knows the `webhook_secret` for) any single GitHub organization/app that is configured in this Shipit instance's multi-org `github:` config (a normal, unprivileged capability — they only need to run their own small GitHub App/org, not compromise Shipit) can:
1. Set `repository.owner.login` in the JSON body to their own organization (so `verify_signature` selects their own known `webhook_secret` and the HMAC check passes).
2. Set `repository.full_name` to `victim-org/victim-repo`, an arbitrary repository already onboarded as a Shipit `Stack` belonging to a completely different organization.

Because `repository_owner`/signature selection and `repository_name`/stack resolution are independent, the forged, validly-signed webhook is dispatched to handlers as if it legitimately came from the victim repository. For the `status` event, this lets the attacker inject arbitrary commit statuses (e.g. force a required CI check to "success") on a victim stack's commit — directly undermining `ci.require`/blocking-status safety gates that are used to prevent unsafe deploys — which can facilitate an unauthorized deploy. This satisfies the "Critical: unauthorized deploy" and related cross-repository-write impact bar defined by the rules. (Note: I was not able to open `app/models/shipit/webhooks/handlers/status_handler.rb` directly in this session before running out of tool calls; the described status-write behavior is inferred from `test/controllers/webhooks_controller_test.rb` lines 42-58, which shows a `status` webhook payload's fields being written verbatim onto a `Status` record. It should be double-checked, but the same "owner vs full_name" mismatch also affects `push` and `check_suite` handlers regardless.)

### Likelihood Explanation
Likelihood is high in the documented multi-organization deployment mode (`docs/setup.md` "Using Multiple Github Applications"), which is an explicitly supported and encouraged Shipit configuration. `WebhooksController` requires no Shipit session, `ApiClient` token, or any privileged credential — the only gate is a valid HMAC for *any one* of the configured organizations. Because signature validation and repository resolution use different, independent fields of the same attacker-supplied JSON body, exploitation only requires knowledge of one organization's `webhook_secret` (or, per `verify_webhook_signature`'s `return true unless webhook_secret`, no secret at all if that organization was configured without one), not the victim's.

### Recommendation
Verify that `repository.owner.login` (or `organization.login`) used to select the signing app matches the `owner` portion of `repository.full_name` before dispatching to handlers; alternatively, have `Handler#repository_name`/`stacks` also authenticate against the organization implied by the app whose secret validated the signature, rejecting payloads where the two disagree.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` (attacker knows/controls its `webhook_secret`) and `victim-org` (onboarded stack `victim-org/victim-repo`), per `docs/setup.md`'s multi-app example.
2. Craft a `status` webhook JSON body:
```json
{
  "sha": "<real sha of a commit on victim-org/victim-repo>",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body, per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb` lines 76-83).
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` selects `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and the signature verifies successfully.
6. `StatusHandler`/`Handler#stacks` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and writes the forged status onto the victim stack's commit, potentially satisfying `ci.require` and enabling an otherwise-blocked deploy.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
