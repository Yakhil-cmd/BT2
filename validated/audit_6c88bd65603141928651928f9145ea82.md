### Title
Missing `return` after caught exception in `handleSavedPrivatePayments` lets an attacker-crafted private-payment payload double-process a chain and reach the process-crashing exception handler - ([File: network.js])

### Summary
The Adminer report shows a persistent, unauthenticated DoS caused by (1) attacker-controlled data reaching a code path that performs no type/shape validation on a field before it's used in a "hard" operation (`openssl_verify()`), and (2) the resulting `TypeError` being thrown uncaught, taking down request handling for *all* subsequent users until the poisoned state is manually cleared. The structural analog in `ocore--021` is `network.js`'s handling of privately-sent payment chains (`handleSavedPrivatePayments`) combined with the global `process.on('uncaughtException', ...)` handler in the same file, which explicitly re-throws to **crash the whole node process** [1](#0-0) .

### Finding Description
In `handleSavedPrivatePayments`, each queued private-payment chain (originally submitted by an unprivileged private-payment counterparty via `hub/deliver` / `private_payments`, then queued in `unhandled_private_payments` and reprocessed later) is hashed to build a dedup/event key: [2](#0-1) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...});
```

The `catch` block has no `return`. `objectHash.getBase64Hash()` throws for objects it cannot deterministically stringify/hash (e.g. malformed nested structures, non-well-formed content) — exactly the "unexpected type/shape reaches a strict serializer" pattern from the Adminer bug. When this throws:
1. `deleteHandledPrivateChain(...)` is invoked (asynchronously, with the same `cb`), **and**
2. execution falls through to build `key` with `json_payload_hash === undefined` and to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` a **second time** on the same malformed data, using the same `cb` from `async.each`.

Calling `cb` twice inside the same `async.each` iterator, combined with a second, un-awaited `validateAndSavePrivatePaymentChain` execution racing the deletion issued in the catch block, produces overlapping asynchronous DB work over the same `arrPrivateElements`/`row` identifiers (SELECT/INSERT/UPDATE/DELETE races against `unhandled_private_payments` and related tables). Any of the many un-try/catched `throw Error(...)` assertions along that second path (e.g. `"more than one output "..."`, `"more than one output..."` in `private_payment.js`, or downstream assertions in `indivisible_asset.js`/`divisible_asset.js`) can now fire from unexpected/duplicated state instead of being suppressed by normal error callbacks, and unlike ordinary `ifError` callbacks these `throw` statements are not routed through the `ifError` callback chain — they propagate as an uncaught exception.

Because `network.js` installs a top-level `process.on('uncaughtException', ...)` that deliberately re-throws to terminate the process ("crash the process to avoid ending up in an inconsistent state") [1](#0-0) , any uncaught exception reached from this reprocessing path brings the entire node down — this is the same "attacker input bypasses validation → unhandled exception → outage affecting all future requests/units" shape as the Adminer report, except here the effect is a full node crash rather than one poisoned file.

### Impact Explanation
A node that goes down via the `uncaughtException` handler stops relaying/validating/serving units for all its peers and light clients until manually restarted — this is a "network unable to confirm new units" condition for anyone relying on that node (hub, witness, relay), satisfying the required concrete impact bar. Because the trigger is a private-payment message that any correspondent/private-payment counterparty (an allowed unprivileged threat actor) can send repeatedly and cheaply (no unit is broadcast, no fees, only a device message), this is a low-cost, repeatable DoS against relays and hubs that process such messages.

### Likelihood Explanation
Reaching `objectHash.getBase64Hash()`'s throw path requires crafting a `payload` object that the hashing/canonicalization logic cannot serialize deterministically (analogous to sending an array where a scalar/string is expected upstream, or content that fails `isObjectWellFormed`-style checks). Exploitability depends on finding at least one payload shape that (a) passes the loose type gate in `handlePrivatePaymentChains` (`isNonemptyObject`/`isNonemptyString`/`isNonemptyArray` checks only — no recursive type or well-formedness enforcement) and (b) still throws inside `getBase64Hash`. Given the codebase separately tracks "lone surrogate or null byte" and "too deeply nested" checks as known hash-hazards elsewhere (`isObjectWellFormed`, `isTooDeeplyNestedOrHasTooManyNodes` in `validation.js`), and neither check is applied to the private-payment payload before hashing here, this is plausible but not proven with a concrete payload in this review — full confirmation would require dynamic testing against `object_hash.js`'s `getBase64Hash` implementation, which was not inspected in this pass.

### Recommendation
- Add `return` immediately after the `catch` block in `handleSavedPrivatePayments` so that a failed hash calculation cannot fall through to a second `validateAndSavePrivatePaymentChain` call or a double invocation of `cb`.
- Apply the same well-formedness/depth checks used for units (`isObjectWellFormed`, `isTooDeeplyNestedOrHasTooManyNodes`) to `arrPrivateElements`/`headElement.payload` before any hashing, in both `handlePrivatePaymentChains` (wallet.js) and `handleOnlinePrivatePayment`/`handleSavedPrivatePayments` (network.js).
- Audit `object_hash.getBase64Hash` for all conditions under which it can throw and ensure every call site on network-supplied data wraps it in `try/catch` with an explicit `return` on error, rather than relying on the top-level `uncaughtException` handler as a safety net.

### Proof of Concept
Not independently reproduced. The chain of reasoning is: (1) craft a private-payment `payload` (in the JSON body of a `private_payments`/`hub/deliver` message) that passes the shallow `isNonemptyObject`/`isNonemptyString`/`isNonemptyArray` checks in `handlePrivatePaymentChains` but contains a value shape that makes `objectHash.getBase64Hash()` throw (e.g., unwell-formed strings, or structures identified as invalid by the DAG unit hashing rules that are not separately re-validated for private elements); (2) submit it so it lands in `unhandled_private_payments` and is later reprocessed by `handleSavedPrivatePayments`; (3) observe the missing `return` causing duplicate processing/`cb` calls and, if the second path hits any of the un-guarded `throw Error(...)` assertions in `private_payment.js`/`indivisible_asset.js`, the node crashes via the `uncaughtException` handler. Confirming the exact payload that makes `getBase64Hash` throw requires direct inspection/testing of `object_hash.js`, which was not available in this session — this should be validated in a live/test environment before relying on this finding for a fix priority decision.
