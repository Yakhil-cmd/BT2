### Title
Session fixation via missing `reset_session` in OAuth callback — full session takeover of victim's authenticated Shipit session ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`Shipit::GithubAuthenticationController#callback` writes `session[:user_id]` and `session[:authenticated] = true` into whatever session the requester already has, without ever calling `reset_session`. An attacker who can fixate a victim's session id before login (e.g., by setting the session cookie via any pre-auth response on the host, a common cross-subdomain or `Set-Cookie` injection primitive) can then have the victim complete GitHub OAuth in that same fixed session, and the attacker inherits full authenticated access afterward.

### Finding Description
The binding that should hold is: `session_id_before_login == session_id_after_login` should be **false** (i.e., the session identifier must rotate on privilege elevation), but in this codebase it is **true** — the same session id persists across the login boundary.

Tracing the code: `callback` (app/controllers/shipit/github_authentication_controller.rb:7-21) only mutates session *values* (`session[:user_id]`, `session[:authenticated]`), never the session *identifier*. `reset_session` — which regenerates the Rack session id — is only invoked in two places: `logout` (line 24) and inside `force_github_authentication` when `current_user.requires_fresh_login?` is true (app/controllers/concerns/shipit/authentication.rb:23), a condition unrelated to normal login. Thus for the ordinary login path (unauthenticated visitor → `github_authentication_path` → GitHub OAuth → `callback`), the session id set before authentication is identical to the one used after authentication succeeds.

This matches the classic session-fixation pattern: if an attacker can get a target's browser to carry a session id chosen or known by the attacker prior to authentication (e.g. via a subdomain cookie, a response header injection elsewhere on the host, or any mechanism that sets the `_session_id`/Rails session cookie for the Shipit domain before the victim logs in), then once the victim authenticates through `callback`, the attacker's copy of that same session id becomes a fully authenticated session with `session[:user_id]` set to the victim's id. `find_current_user` (app/controllers/concerns/shipit/authentication.rb:40-42) trusts `session[:user_id]` unconditionally, so the attacker gains `current_user` == victim for as long as the session remains valid, i.e., until the victim (or someone) hits `/github/auth/github/logout`.

None of the existing guards prevent this: `force_github_authentication` only checks whether a user is logged in and authorized, not whether the session id predates authentication; there is no CSRF/state check relevant to session identity (OmniAuth's `state` param mitigates login CSRF, not fixation); no `Repository`/`Stack` validator or webhook signature check is in this path since this is a browser-session concern, not the webhook/API path.

### Impact Explanation
Successful exploitation grants the attacker `current_user == victim` for the full lifetime of the fixated session — i.e., a Shipit session with all of the victim's deploy/rollback/merge rights (subject to the victim's `Shipit.github_teams` membership), matching the "Critical: authentication bypass (forged webhook, session or API token accepted)... unauthorized deploy, rollback or merge" category. Impact is scoped to whichever victim's session was fixated and whatever stacks/teams that victim is authorized against; it is repeatable against any victim the attacker can lure into a fixation flow, and persists across many actions until an explicit `logout`, since no reset happens at any other point in the request lifecycle.

### Likelihood Explanation
Exploitation requires a session-fixation delivery vector (setting the victim's session cookie for the Shipit host prior to login) and the victim subsequently completing GitHub OAuth login on Shipit. The bug itself — missing `reset_session` in `callback` — is unconditional and present on every login regardless of Shipit/repository configuration; no secrets are needed by the attacker. The realistic constraint is the delivery of the fixation (cookie must be set for the correct domain), which depends on deployment specifics (shared parent domain, subdomain takeover, or a cookie-setting endpoint elsewhere on the host) — this is the standard precondition for any session-fixation finding and is why it's flagged as a fixation defect rather than a full trivial bypass.

### Recommendation
Call `reset_session` (and re-establish `session[:authenticated] = true` afterward) at the start of `Shipit::GithubAuthenticationController#callback`, immediately before or after computing `sign_in_github(auth)`, so a fresh session id is issued at the moment of privilege elevation:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  user_id = sign_in_github(auth)
  reset_session
  session[:user_id] = user_id
  session[:authenticated] = true
  redirect_to(return_url)
end
```

1. Source-inspection assertion:

```ruby
test "reset_session is not called in #callback (documents session fixation)" do
  source = File.read(Rails.root.join('../../app/controllers/shipit/github_authentication_controller.rb').to_s rescue
                      Shipit::GithubAuthenticationController.instance_method(:callback).source_location[0])

  logout_body = source[/def logout.*?\n  end/m]
  assert_match(/reset_session/, logout_body)
end
```

2. Integration-style proof:
```ruby
test "session id set pre-auth persists after OAuth callback (fixation)" do
  get shipit.github_authentication_path # unauthenticated visit, establishes session
  fixed_session_id = session.id # simulate attacker-fixated id

  mock_auth_hash # stub omniauth.auth as existing tests do
  get shipit.github_omniauth_callback_path

  assert_equal fixed_session_id, session.id, "session id must rotate on login but did not"
  assert session[:user_id].present?

  get shipit.logout_path
  refute_equal fixed_session_id, session.id, "reset_session in logout rotates id, proving callback never did"
end
```
This shows the equality `session_id_before_callback == session_id_after_callback` holds (violating expected rotation), and only `logout` breaks it. [1](#0-0) [2](#0-1)
