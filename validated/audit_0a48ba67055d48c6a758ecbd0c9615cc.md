## Analysis

The Astaria bug class is: **a privileged status is attached to an address only after some later event (contract deployment / definition posting), but the address itself is deterministic and can be computed in advance; anything sent/transferred to that address *before* it acquires its privileged role gets silently absorbed into the privileged entity's accounting once it goes live, corrupting the entity's internal state (reserves, balances, ratios).**

The exact structural analog in ocore is the way Autonomous Agent (AA) addresses work: an AA's address is `chash160(definition)` — fully deterministic from the definition/params, so it can be computed and even sent funds to *before* the AA is officially posted/activated. `storage.js`'s `insertAADefinitions` explicitly reconciles this by scanning all pre-existing unspent outputs sent to that address and merging them into `aa_balances` once the AA becomes active:

<cite repo="Camomtat/ocore--001" path="storage.js" start="944="961" /> [1](#0-0) 

This merge is unconditional on *who* sent the funds — it is not restricted to the AA's own factory/creator, so any unprivileged unit poster can pre-fund a not-yet-existing (but predictable) AA address, and that balance becomes indistinguishable from legitimate deposits once the AA activates and begins evaluating `balance[this_address][asset]` in its oscript formulas. [2](#0-1) 

### Title
Pre-funding of a deterministically-derived, not-yet-active AA address corrupts its initial `balance[]` accounting (address-role front-running) - (File: `storage.js`, `aa_composer.js`, `formula/evaluation.js`)

### Summary
AA addresses are pure hashes of their definition (`objectHash.getChash160(arrDefinition)`), so any future AA's address — including auto-generated child AAs created by factories, or parameterized AAs (`base_aa` + `params`) — is fully predictable before the AA is ever posted on the DAG. Because ocore reconciles all outputs previously sent to that address into `aa_balances` the moment the AA becomes active, an attacker can front-run the legitimate creation flow by sending funds directly to the predicted address beforehand. When the AA later reads `balance[this_address][asset]` (a common oscript idiom, e.g. bonding-curve/AMM-style AAs, funds-splitting AAs, or factories) to determine its own state on first activation, the attacker's donation is silently included, exactly mirroring the Astaria bug where a privileged recipient's accounting variables (yIntercept/slope) get corrupted by a value the recipient never legitimately "owned" or expected.

### Finding Description
- AA address derivation is deterministic: `objectHash.getChash160(arrDefinition)` [3](#0-2) .
- Factories/parent AAs routinely compute a child AA's address ahead of its `definition` message being posted and immediately send it funds within the same trigger chain, as shown in the `chash160($child_aa)` pattern [4](#0-3) . This demonstrates the address is knowable and spendable-to before the AA formally exists.
- When the AA's `definition` message is finally processed, `storage.insertAADefinitions` back-fills `aa_balances` from *all* unspent outputs previously sent to that address, not just ones from the legitimate creator: `WHERE address=? AND is_spent=0 AND sequence='good' AND (main_chain_index<? ...)` [5](#0-4) .
- Once active, oscript's `balance[address][asset]` formula simply reads whatever is in `aa_balances` (or `objValidationState.assocBalances`) with no notion of provenance [2](#0-1) .
- `updateInitialAABalances` in `aa_composer.js` further adds the current trigger's own outputs on top of this same undistinguished balance state [6](#0-5) .

The root cause parallels the Astaria report precisely: the framework identifies "the AA at this address" purely by reaching that address, with no analog of `s.lienMeta[id].originOwner` to distinguish legitimately-received vs. attacker-injected value. Any AA logic that treats `balance[this_address][asset]` as equal to "funds legitimately deposited by known parties" (as opposed to explicitly tracked state variables like `var['total_deposited']`) is vulnerable to this address-role front-running, because the balance existed before the AA's privileged role (its own code/logic) was even attached to the address.

### Impact Explanation
Any AA design that bootstraps its state from `balance[this_address][asset]` on first activation (e.g., a liquidity-pool style AA computing an implied exchange rate, or a proportional-share fund-splitter computing shares based on total balance) can have its initial invariants corrupted by an attacker who predicts the address and donates funds before the AA goes live. This can lead to skewed reserve ratios, incorrect share/fee calculations, or fund loss/freezing for legitimate later depositors — the same category of "corrupt multiple key properties" impact described in the original finding, now targeting AA-based decentralized-finance style contracts built on ocore.

### Likelihood Explanation
The attack requires only: (1) predicting a deterministic AA address from a known `definition`/`base_aa`+`params` template (often published/observable ahead of activation, e.g. via a factory AA's `init` formula or public documentation of a parameterized AA family), and (2) posting an ordinary payment to that address before the AA is defined — both of which are actions any unprivileged unit poster can perform. No special node/hub/network privilege is required.

### Recommendation
AA authors should never rely on `balance[this_address][asset]` to reconstruct "amount legitimately received" for initial-state computations; they should track deposits explicitly via `var[]` state variables updated only through controlled trigger paths (as already demonstrated by the safe pattern `response['received_amount'] = trigger.output[[asset=base]]` used in some official AA templates [7](#0-6) ). At the protocol level, consider flagging/warning when `aa_balances` reconciliation for a newly-activated AA finds pre-existing balance contributed by senders other than the AA's declared parent/factory trigger chain, so wallets/IDEs can surface this risk to AA developers.

### Proof of Concept
1. Attacker observes a factory AA's `init` formula that will deterministically create `$child_aa = ['autonomous agent', {...}]` and compute `$child_aa_address = chash160($child_aa)` before ever posting its `definition` message (pattern shown in `test/aa_composer.test.js` lines 944-976).
2. Because the definition template (and therefore the hash) is derivable from publicly known code/parameters, the attacker computes `child_aa_address` independently and sends a payment there in an earlier unit, well before the factory's trigger executes.
3. When the factory eventually posts the `definition` message for `child_aa`, `storage.insertAADefinitions` reconciles all prior unspent outputs sent to `child_aa_address` — including the attacker's — into `aa_balances` [5](#0-4) .
4. If `child_aa`'s oscript uses `balance[this_address][asset]` (rather than an explicit tracked state variable) to determine, e.g., an initial pool ratio or first-depositor share, the attacker's injected balance skews that computation in the attacker's favor once the AA becomes live and processes further triggers.
