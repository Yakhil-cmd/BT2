### Title
Unauthorized STX lock via attacker-chosen `PreStxOp`/`StackStxOp` sender not tied to a private key - (File: `stackslib/src/chainstate/burn/operations/stack_stx.rs`)

### Summary
`PreStxOp::parse_from_tx` (lines 105-127) derives the `output` field solely from the first Bitcoin output's address, with no requirement that the transaction's signer controls that address. `StackStxOp::from_tx`/`parse_from_tx` (lines 249-350) then reuses this attacker-supplied address as `sender`, which is subsequently used as the Clarity `tx-sender` when invoking the PoX contract's `stack-stx`.

### Finding Description
The broken equality is: `PreStxOp.output` (later `StackStxOp.sender`) == "the Stacks identity that authorized this lock via a private key." In reality, `output` is simply `outputs[0].address.try_into_stacks_address()` [1](#0-0) , i.e., whatever legacy Bitcoin address the first transaction output pays to. Since paying BTC to an address requires no private key from the recipient, an attacker can construct a `PreStxOp` whose first output pays a small amount to an address whose hash160 equals a victim's Stacks-address hash160, while the second output (spent later) is the attacker's own change, which they do control.

`Burnchain::classify_transaction` looks up the `PreStxOp` purely by `txid` from `StackStxOp::get_sender_txid` (which only checks that the spent vout is 1) and passes `pre_stack_stx.output` straight through as `sender` to `StackStxOp::from_tx` [2](#0-1) . No code path checks that the party constructing/spending the `StackStxOp` chain actually holds the private key behind the `PreStxOp`'s first output.

Downstream, `StacksChainState::process_stacking_ops` executes the PoX contract call using this `sender` directly as the Clarity `tx-sender`: `tx.run_contract_call(&sender.clone().into(), None, &boot_code_id(active_pox_contract, mainnet), "stack-stx", &args, ...)` [3](#0-2) . Inside `pox-4.clar`'s `stack-stx`, the only checks against `tx-sender` are that it isn't already stacking/delegating and has sufficient balance: `(asserts! (>= (stx-get-balance tx-sender) amount-ustx) (err ERR_STACKING_INSUFFICIENT_FUNDS))` [4](#0-3) . There is no signature check binding `tx-sender` to the entity that crafted the burnchain operation — the `signer-sig`/`consume-signer-key-authorization` logic verifies the PoX *signer key*'s consent, not the stacker's own authorization to lock their STX.

Existing guards (`check-caller-allowed`, `is-none (get-stacker-info tx-sender)`, balance check) do not address this gap because they all operate on the already-attacker-controlled `tx-sender` value; none of them verify that the address was legitimately derived from a key the burnchain-op submitter possesses.

### Impact Explanation
An attacker who knows a victim's Stacks address (public information) and has BTC funds to construct two chained Bitcoin transactions can cause the victim's un-stacked STX balance to be locked into PoX for an attacker-chosen `num_cycles`, `signer_key`, and `reward_addr`, without the victim's Stacks private key ever signing anything. This is a Critical impact: unauthorized (temporary, up to `num_cycles`) freezing of a third party's STX and diversion of their PoX rewards to an attacker-controlled reward address, bounded only by the victim's spendable STX balance. It is repeatable against any address that is not already stacking/delegating, once per victim per cycle (subject to `is-none (get-stacker-info tx-sender)`).

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: the victim must simply hold unstacked, unlocked STX and not already be in `stacking-state`/`delegation-state`. The attacker needs only: (1) the victim's known Stacks address, (2) enough BTC to pay for two chained on-chain transactions (dust output to the derived legacy address plus a spend of the change output carrying the `StackStxOp` payload). No privileged role, no compromised keys, no signer/miner cooperation is required — this matches the "unprivileged attacker with own BTC/STX" threat model. This is highly feasible and repeatable across many victim addresses.

### Recommendation
Require the `PreStxOp`'s first output (and thus the resulting `sender`/stacker identity) to be cryptographically tied to the actual signer of the Bitcoin transaction — e.g., derive `sender` from the recovered public key(s) of the transaction's own inputs (as is done for other key-derived burnchain identities) rather than trusting an arbitrary output address, or require an accompanying Stacks-signed authorization (analogous to `signer-sig`) proving the named `sender` consents to the lock.

### Proof of Concept
Rust integration test outline (extends the existing `stackslib/src/burnchains/tests/db.rs` PreStx/StackStx test scaffolding):
1. Generate `attacker_key` (funds inputs/fees) and `victim_addr` (a `StacksAddress` for which the test does **not** hold a private key, representing a funded victim account in a simulated Clarity chainstate).
2. Build `pre_stx_tx`: input signed by `attacker_key`; `outputs[0]` = legacy Bitcoin address whose `Hash160` equals `victim_addr`'s hash160 (pay a small dust amount there — no victim key needed); `outputs[1]` = attacker's own change address.
3. Run `PreStxOp::parse_from_tx(...)` and assert `op.output == victim_addr` (equality check #1: attacker forced `output == victim_addr` despite never touching victim's key).
4. Build `stack_stx_tx` spending `outputs[1]` of `pre_stx_tx` (vout=1, satisfying `get_sender_txid`), signed only by the attacker's change key, embedding StackStx op data.
5. Run `Burnchain::classify_transaction` (or `StackStxOp::from_tx` directly with `sender = &victim_addr`), assert `op.sender == victim_addr`.
6. Feed the resulting `StackStxOp` into `StacksChainState::process_stacking_ops` against a chainstate where `victim_addr` has a positive, unlocked STX balance and is not currently stacking.
7. Assert `resp.committed == true` and that `STXBalance` for `victim_addr` now shows `amount_locked > 0` and `unlock_height` set — i.e., the victim's STX became locked — while asserting the victim never produced any Stacks-signed transaction or private-key-derived signature authorizing this. This demonstrates the broken equality: `sender (attacker-chosen) == STX-locking authority`, when it should require `sender == entity that signed via a held private key`.
