### Title
`StoreCredentials` approves credentials at host-level scope instead of per-URL, causing credential leakage to unintended repos on the same host - (File: main.go)

### Summary
Git-sync's `StoreCredentials` function approves every username/password pair it is given via `git credential approve` without ever configuring `credential.useHttpPath`. Git's default credential-cache matching key is `protocol://host[:port]` only (path is ignored unless `credential.useHttpPath=true`). Because git-sync configures `credential.helper` as `cache --timeout 3600` and never sets `credential.useHttpPath`, when more than one credential is approved for the same host but different repository paths (a documented, supported use case for `--credential` with submodules), the cache will hand out whichever credential was most recently approved for that host to *any* path on that host — including paths controlled by an attacker via a malicious `.gitmodules` entry pointing at the same host. This is the direct analog of the reported Solidity bug: an "approval" is granted at a scope broader than what is actually required (host-wide instead of the specific URL/path), enabling credential disclosure to an unintended recipient.

### Finding Description
`StoreCredentials` simply calls `git credential approve` with the given `url`/`username`/`password`: [1](#0-0) 

The global git config that governs how these approvals are looked back up is set once in `SetupDefaultGitConfigs`, which sets `credential.helper` to `cache --timeout 3600` but never sets `credential.useHttpPath`: [2](#0-1) 

Per git's documented behavior, `git-credential-cache` (and the underlying credential subsystem) matches stored credentials by `protocol`, `host`, and (if present) `port` — the `path` component of the URL is deliberately ignored unless `credential.useHttpPath` is explicitly enabled. Git-sync's own docs acknowledge that `--credential` exists precisely to support "more than one username and password ... for specific URLs, for example when using submodules," and that all of these pairs are fed into `git credential approve`: [3](#0-2) 

The refresh loop iterates every configured `--credential` entry and calls `StoreCredentials` for each one, one after another, all sharing the same global, path-insensitive cache: [4](#0-3) 

Because approval is granted at host granularity rather than the specific URL/path that was actually authorized, the most-recently-approved credential for a host will be transparently reused by git for *any* other path on that host — including a submodule URL under attacker control that happens to share the same host as a legitimately-configured private repository. This is functionally identical to the reported bug class: approving a broader scope (max/host-wide) than the amount actually needed (the single specific URL), which "could potentially be dangerous."

### Impact Explanation
If an operator uses `--credential` to authenticate to multiple repositories/submodules that share the same host (a scenario the README explicitly documents as supported, e.g. self-hosted git servers hosting several private repos), and the synced repository's `.gitmodules` is later modified (by any contributor with push/PR-merge access to the tracked ref) to add a submodule pointing at a different, attacker-controlled path on that same host, git-sync's credential cache will transmit the credentials intended for the legitimate private repository to the attacker-controlled path when git attempts to fetch it. This results in credential/token disclosure to an unintended recipient — one of the explicitly accepted impacts for this analog.

### Likelihood Explanation
This requires: (1) the operator to configure more than one `--credential` for URLs sharing the same host (a supported, documented pattern for submodules), and (2) the synced ref's `.gitmodules` to be modifiable by a less-trusted party (e.g. a contributor able to open commits/PRs that get merged into the tracked branch, or any writer to the tracked ref). Given that submodule support and multi-credential configuration are first-class, documented git-sync features, and the vulnerable default behavior of `git-credential-cache` is not compensated for anywhere in the code (no `credential.useHttpPath=true`), likelihood is moderate — it depends on operator topology (multiple credentials sharing a host) rather than being universally exploitable.

### Recommendation
Set `credential.useHttpPath=true` in `SetupDefaultGitConfigs` (or configure it per-URL where credential caching is used) so that approvals are scoped to the full URL/path that was actually authorized, not just the host — mirroring the fix recommended for `approveAndCall` (approve only what's needed, not the maximum/broadest scope). Alternatively, avoid the shared process-wide `cache` helper for multi-credential configurations and instead use a mechanism (e.g. `git credential-store` per URL, or `insteadOf`/per-remote config) that inherently binds each credential to its specific URL.

### Proof of Concept
1. Configure git-sync with two `--credential` entries pointing at the same host but different paths, e.g.:
   - `--credential='{"url":"https://git.example.com/org/private-repo","username":"tok","password":"SECRET_A"}'`
   - This is approved via `StoreCredentials`/`git credential approve` as shown in [1](#0-0)  using the global `cache --timeout 3600` helper configured in [5](#0-4) .
2. The tracked repository's `.gitmodules` is updated (e.g. via a merged PR) to add a submodule at `https://git.example.com/attacker/evil-repo` — same host, different path, no `useHttpPath` configured.
3. During `git submodule update`, git needs credentials for `https://git.example.com/attacker/evil-repo`. Because `credential.useHttpPath` is unset, `git-credential-cache` matches purely on `https://git.example.com` and returns the cached `SECRET_A`, sending it to the attacker-controlled endpoint in the HTTP Basic-Auth request — disclosing the credential intended only for `org/private-repo`.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
