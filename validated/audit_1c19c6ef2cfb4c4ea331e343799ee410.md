### Title
Webhook signature verification is keyed by `repository.owner.login` while event handlers act on the unrelated `repository.full_name` field, allowing cross-organization status/webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository_owner`, computed from the *same* untrusted JSON body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up the App/webhook secret configured for that organization key (per `docs/setup.md`, Shipit supports a distinct `app_id`/`webhook_secret` per GitHub organization) and `verify_webhook_signature` HMACs the raw request body against that specific secret. [3](#0-2) 

Once the signature check passes, the controller dispatches the *same raw payload* to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 

Every handler determines which `Stack`/`Repository` to act on using a **different** field of the payload — `repository.full_name` — via the shared base class: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Nothing enforces that `repository.owner.login` (used to pick the verification secret) and the owner segment embedded in `repository.full_name` (used to pick the target repository/stack) refer to the same organization — they are two independent JSON fields inside the same attacker-influenced payload, and only the raw bytes as a whole are HMAC-protected, not any semantic relationship between these two fields.

This breaks the binding: *the organization that authenticated the request (via the secret selected by `repository.owner.login`) ≠ the repository that is actually written to (selected via `repository.full_name`)*.

Concretely: `StatusHandler` uses this to create/update a `Status` on an arbitrary `sha` for whatever repository `full_name` resolves to, regardless of which org's secret validated the request.

### Impact Explanation
An attacker who has legitimate webhook delivery ability for **one** organization configured in this Shipit instance (i.e., they can produce a validly-signed webhook payload for Org A's own repositories — the normal case for any repo owner) can set `repository.owner.login` to `"OrgA"` while setting `repository.full_name` to `"OrgB/some-repo"`, where OrgB is an unrelated organization/stack also tracked by the same Shipit instance. `verify_signature` validates the HMAC against OrgA's secret (which is legitimately known/derivable by the attacker for their own org's webhooks) and the request is accepted; `Handlers::StatusHandler` then writes a forged commit `Status` (e.g., CI "success") against an arbitrary commit `sha` in OrgB's repository. If OrgB's stack has `ci.require` configured, this forged status can satisfy the deploy gating check and enable an **unauthorized deploy** of a commit that never actually passed CI in OrgB — matching the High-impact criterion of "escalation ... unauthorized deploy."

### Likelihood Explanation
This requires the attacker to control webhook delivery for at least one organization already configured in the shared Shipit instance — a realistic scenario for any multi-tenant Shipit deployment tracking several GitHub organizations, since Shipit explicitly documents per-organization `webhook_secret` configuration. No repository write access, session, or `ApiClient` token is needed for the target organization; the attacker only needs delivery capability for their own org's webhook endpoint, which is not out-of-scope under the stated rules (the rule excludes attacks requiring possession of *the target's* `webhook_secret`, not an attacker's own legitimately-obtained one for a different org they control on the same instance).

### Recommendation
Bind the fields used for authentication and for action: after verifying the signature, re-derive the acting organization strictly from the same field/context used for verification (`repository_owner`), and reject or ignore any handler-side lookup where the owner segment of `repository.full_name` (or `organization.login`) does not match `repository_owner`. Alternatively, verify the signature per-repository (using the repository actually resolved from `full_name`) instead of per raw "owner" field pulled from an separate part of the payload.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config).
2. Attacker controls a repo/webhook under `OrgA` and thus can compute a valid `X-Hub-Signature` for `OrgA`'s `webhook_secret`.
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "<arbitrary-sha-in-OrgB-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
4. Attacker signs the raw body with `OrgA`'s webhook secret and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s secret, and the signature matches → request accepted.
6. `Handlers::StatusHandler.process` resolves the target via `payload.dig('repository', 'full_name')` = `"OrgB/target-repo"`, and creates/updates a `Status` record with `state: "success"` on the arbitrary sha inside `OrgB`'s stack — a repository the attacker never authenticated against.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
