### Title
ERC20Transactor credits nominal transfer amount into XCM holding without verifying actual balance delta, enabling accounting desync for fee-on-transfer/rebasing ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
The `ERC20Transactor` used by Asset Hub Westend's XCM `AssetTransactors` bridges XCM asset semantics to `pallet-revive` ERC20 contracts. On `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, it calls `IERC20::transfer(to, amount)` via `pallet_revive::Pallet::<T>::bare_call` and, if the ABI-decoded return value is `true`, unconditionally credits/consumes exactly the nominal `amount` in `AssetsInHolding` — the XCM executor's internal ledger — with no verification that the ERC20 contract's real balance state actually moved by `amount`. This is structurally identical to the Morpheus finding: an internal ledger (`depositPool.deposited`/`lastUnderlyingBalance`, here `AssetsInHolding`) is updated using the *requested* transfer amount rather than the *actual* balance delta produced by an external token contract that can legitimately transfer less than requested (fee-on-transfer, rebasing, or rounding tokens).

### Finding Description
`withdraw_asset_with_surplus` (lines 150-216) performs: [1](#0-0) 

It never reads `balanceOf` before/after the call on the checking account; it trusts the boolean return of `transfer()` and mints an `Erc20Credit(amount)` into `AssetsInHolding` for the full nominal `amount`.

`deposit_asset_with_surplus` (lines 218-306) mirrors this on the withdraw side: it calls `checking_account.transfer(beneficiary, amount)` and, on `Ok(true)`, treats the deposit as fully successful for `amount`, consuming that much from the XCM holding: [2](#0-1) 

Any real-world ERC20 with legitimate, non-full-value-preserving transfer semantics — e.g. a fee-on-transfer / deflationary token, or a rebasing token analogous to stETH's rounding — will move less than `amount` real tokens on the checking account, yet the XCM system will believe `amount` was moved. Since `ERC20TransfersCheckingAccount` (a single well-known account, `PalletId(*b"py/revch")`) is shared across *all* ERC20 contracts registered for XCM, any registered token with such fee/rounding behavior desynchronizes the XCM-tracked "credit" for that token from the checking account's real on-chain balance. This is directly analogous to the Morpheus bug where `Distributor::supply()` recorded the nominal `amount_` in `depositPool.deposited`/`lastUnderlyingBalance` instead of the actual balance delta observed after a stETH transfer, later causing an underflow/DoS and yield miscounting in `distributeRewards()`.

Registering an arbitrary contract as `AccountKey20` in an XCM `Asset` id is permissionless — any user can reference any deployed contract address as an ERC20 asset in `withdraw_asset`/`deposit_asset` instructions (confirmed by the existing test suite in `asset-hub-westend/tests/tests.rs`, which freely instantiates arbitrary contracts and uses their address as `AssetId(AccountKey20{key, ..})`). No governance/whitelisting step gates use of the transactor for a given token address.

### Impact Explanation
For any legitimate fee-on-transfer/rounding ERC20 registered and used by multiple parties for XCM asset transfers through this transactor:
- Repeated withdraw operations will over-credit `AssetsInHolding` relative to the real balance accumulated in the shared checking account, since each withdraw's `Erc20Credit(amount)` is larger than the actual amount received by the checking account.
- This produces a growing gap between "XCM-recognized" supply of that ERC20 asset and the real balance backing it in the checking account.
- Eventually, honest depositors' funds back other users' over-credited withdrawals: a user can withdraw more in aggregate XCM credit than they truly contributed to the checking account, at the expense of other legitimate holders of the same registered ERC20 asset — a value-extraction/loss-of-funds scenario for other users of that asset, and/or deterministic failure (deposit calls reverting due to insufficient real balance in the checking account) causing a DoS of the transactor for that asset, mirroring the Medium-severity DoS+reward-loss impact in the original report.

This is Medium severity under the same rationale as the original finding: it does not enable arbitrary unauthorized dispatch or a full theft of Balances/Assets-pallet-native funds, but it does break the accounting invariant "1 unit of XCM-tracked ERC20 credit == 1 unit of real, checking-account-held ERC20 balance," which can result in the deterministic failure of the ERC20 XCM transactor for that specific token and/or misallocation of real token balances among the token's holders.

### Likelihood Explanation
Fee-on-transfer and rebasing ERC20 tokens are a well-known, common real-world token class (not a purely hypothetical/malicious contract) — any user can deploy or reference such a contract for use with `ERC20Transactor` without any privileged step, since the matcher (`assets_common::ERC20Matcher`) treats any `AccountKey20` location as a valid ERC20 asset id. The entry point (`pallet-xcm::execute`/`send` dispatched by a signed account, as exercised in the existing `withdraw_and_deposit_erc20s` test) is a standard, permissionless, signed extrinsic path — no privileged role, governance, or malicious external chain/relayer is required.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the checking account's (or beneficiary's) ERC20 balance via `balanceOf` before and after the `transfer` call, and credit/consume `AssetsInHolding` using the *actual* balance delta rather than the caller-supplied nominal `amount` — exactly mirroring the pattern already used correctly in `DepositPool::_stake()` from the referenced report (`balanceAfter_ - balanceBefore_`). Alternatively, restrict the transactor to a governance-curated allow-list of ERC20 contracts known not to deviate from standard fixed-supply, non-fee transfer semantics.

### Proof of Concept
Not executed. I was not able to run a live Rust/FRAME integration test in this session (no sandbox/terminal access), so this remains a code-level analysis rather than a verified reproduction. A concrete PoC, following the existing `withdraw_and_deposit_erc20s` test harness in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`, would:
1. Deploy a minimal Solidity ERC20 fixture whose `transfer()` moves `amount - 1` real balance to `to` but returns `true` for the full `amount` (simulating a fee-on-transfer/rounding token, analogous to stETH's rounding-down behavior).
2. Execute an XCM `withdraw_asset`/`deposit_asset` program through `PolkadotXcm::execute` referencing this contract as `AccountKey20`, as in the existing `withdraw_and_deposit_erc20s` test.
3. Assert that `AssetsInHolding`'s tracked credit for the asset differs from `<Revive as fungibles::Inspect<_>>::balance(erc20_address, &checking_account)`, and that repeated cycles cause the checking account's real balance to be insufficient to satisfy a subsequent, legitimately-credited deposit (reverting with an ERC20 "transfer failed" `XcmError::FailedToTransactAsset`).

This PoC is not included as executed evidence — it is a proposed reproduction plan based on the code paths cited above, following the required guard failures (`is_success`/`did_revert` checks that pass while no real balance check against `Inspect::balance` is performed).
