### Title
Cross-tenant PullRequest mutation via `EditedHandler#pull_request` scoped by an org-unverified `repository.full_name` - ([File: app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to verify the HMAC signature by reading `repository.owner.login` (or `organization.login`) from the raw JSON body, while `EditedHandler#repository` resolves the target `Repository` from the independent `repository.full_name` field of the same body. Because these two fields are never cross-checked for consistency, an attacker who controls a legitimate org's `webhook_secret` can forge a payload whose `repository.owner.login` matches their own org (so the signature verifies) but whose `repository.full_name` names a victim org/repo, causing `EditedHandler#pull_request` to update the victim's `PullRequest` row.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `repository_owner` (the field used to pick the verifying `webhook_secret`) MUST equal `owner_of(params.repository.full_name)` (the field used to resolve the `Repository` row acted upon) — but no code enforces this.

Trace:
- `WebhooksController#verify_signature` picks the app config via `Shipit.github(organization: repository_owner)` and verifies the raw HMAC signature against that org's secret: [1](#0-0) [2](#0-1) 
- `repository_owner` is read from `params.dig('repository','owner','login')`, a field fully controlled by whoever crafts the raw JSON body (the attacker, since this is not a real GitHub-originated request but any POST to `/webhooks`).
- `Shipit.github(organization:)` looks up a per-organization config/secret (`github_app_config(organization)`), meaning each org has (or can have) a distinct `webhook_secret`: [3](#0-2)  and the HMAC check itself: [4](#0-3) 
- Separately, `EditedHandler#repository` resolves the acted-upon repository from `params.repository.full_name`: [5](#0-4) , via `Repository.from_github_repo_name` which just splits `"owner/name"` and does a `find_by`: [6](#0-5) 
- `EditedHandler#pull_request` then scopes strictly by `repositories.id: repository.id` (this repository, resolved above) joined with attacker-chosen `number`: [7](#0-6) , and `process` unconditionally writes attacker-supplied `params.pull_request` into that row if found: [8](#0-7) 

Exploit flow: attacker (owner of org `attacker-org`, knows their own `webhook_secret`) crafts a JSON body with `repository.owner.login = "attacker-org"` (so `verify_signature` selects and validates against `attacker-org`'s secret, which the attacker controls) but `repository.full_name = "victim-org/victim-repo"` and `number = 42` matching a real victim `PullRequest`. `X-Github-Event: pull_request`, `action: edited`. Since `respond_to_pull_request_edited?` only checks `action == "edited"` (no repository-consistency check): [9](#0-8) , and `repository.id` resolves to the real `victim-org/victim-repo` `Repository` row, the `find_by` join scopes to the victim's stacks/repository and — if the victim has a `PullRequest` numbered 42 — updates it with attacker-controlled `github_pull_request` JSON.

Existing guards checked and found insufficient: `drop_unhandled_event` only checks event type presence, not payload consistency; `verify_signature`'s `GithubOrganizationUnknown` rescue only guards against an unknown org name, not against `repository.owner.login` disagreeing with `repository.full_name`; the `ExplicitParameters` schema (`params do ... end`) only validates types/presence of fields, never cross-field consistency; no model validation on `PullRequest`/`Repository`/`Stack` enforces that a webhook's claimed org matches the repository named in the same payload.

### Impact Explanation
Any org onboarded to this multi-tenant Shipit instance can, using only their own `webhook_secret`, forge writes into another tenant's `PullRequest.github_pull_request` column by naming that tenant's `repository.full_name` and a correct/guessed PR `number`. This is a cross-tenant data-integrity break authenticated only by the attacker's own credentials — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius covers every `PullRequest` row across every repository/stack on the instance, repeatable at will since `number` values are small sequential integers and repo/org names are typically public.

### Likelihood Explanation
Requires: the Shipit instance to be configured for multiple GitHub organizations/apps each with distinct `webhook_secret` values (the multi-org `Shipit.github(organization:)` path), the attacker to own/administer one such onboarded org (which the threat model treats as an "unprivileged" GitHub user who can still run their own webhook against `/webhooks`), and knowledge of a victim `full_name` + PR `number` (both easily obtainable/guessable). No Shipit session, API token, or victim secret is needed. This is straightforward and repeatable — a single crafted HTTP POST per target PR.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the GitHub App config, explicitly verify that the resolved organization matches the owner of `params.dig('repository','full_name')` (and/or `params.dig('organization','login')`) before proceeding; reject (422) on mismatch. Alternatively, resolve the target `Repository` using the already-authenticated `repository_owner` rather than trusting `repository.full_name` independently in every `pull_request` handler (`EditedHandler`, `AssignedHandler`, `ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `OpenedHandler`), since all share the same pattern.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/edited_handler_test.rb` style, adapted):
1. Configure two orgs with distinct `webhook_secret`s (`attacker-org`, `victim-org`) in test credentials/secrets, or stub `Shipit.github_app_config` accordingly.
2. Create `Repository` fixtures `attacker-org/repo-a` and `victim-org/repo-b`, each with a `Stack` and a `PullRequest` numbered `42` (`title: "Attacker PR"` / `title: "Victim PR"`).
3. Build a payload: `{"action":"edited","number":42,"pull_request":{...,"title":"HACKED"},"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/repo-b"},"sender":{"login":"attacker"}}`.
4. Sign it with `attacker-org`'s known `webhook_secret` (`sha1=` HMAC) and POST to `/webhooks` with `X-Github-Event: pull_request`.
5. Assert response is `:ok` (signature accepted).
6. Assert: `victim_pull_request.reload.title == "HACKED"` (equality broken — victim row mutated) and `attacker_pull_request.reload.title != "HACKED"` (attacker's own row untouched), proving the write landed on the wrong tenant's repository despite verification succeeding only via the attacker's own secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
