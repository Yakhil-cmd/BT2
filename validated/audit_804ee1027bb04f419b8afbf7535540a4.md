Based on my research, the strongest analog to CVE-2022-1623's bug class (an out-of-bounds/invalid-length read reached through insufficiently validated attacker-controlled length data in a decoder) is in `chash.js`'s address-checksum verification path.

### Title
Uncaught exception in `isChashValid` from unvalidated decoded-buffer length crashes node on malformed address string - (File: chash.js)

### Summary
`isChashValid()` in `chash.js` decodes a user-supplied address string with `base32.decode()` (for 32-char c-hashes) inside a `try/catch`, but the subsequent processing of the decoded buffer — `buffer2bin()` and `separateIntoCleanDataAndChecksum()` — is executed *outside* that `try/catch` block. `separateIntoCleanDataAndChecksum()` throws a hard `Error` if the resulting bit-string length is not exactly 160 or 288 bits, which is exactly the "decoded structure length not what the length-driven algorithm expects" bug class behind CVE-2022-1623 (LZW decoder trusting an internal code/length without bounds validation before use).

### Finding Description [1](#0-0) 

`isChashValid` only length-checks the encoded string (32 or 48 chars) and wraps the *decode* call in `try/catch`: [2](#0-1) 

However, `base32.decode()` (from the `thirty-two` package) does not guarantee that its output buffer is exactly 20 bytes (160 bits) for a 32-character input — depending on padding/invalid characters handled leniently by the library, it can return a buffer of a different byte length without throwing. That buffer is then fed to: [3](#0-2) 
which calls `separateIntoCleanDataAndChecksum(binChash)`: [4](#0-3) 
This function throws an **uncaught** `Error("bad length=...")` whenever `bin.length` (i.e., `8 * decodedBuffer.length`) is not exactly 160 or 288 — a case not excluded by the try/catch above, since the throw happens after the try block has already exited.

This is invoked via `validation_utils.isValidAddress`/related address-shape validators, which are used to validate:
- unit author addresses,
- payment/output addresses,
- AA/asset issuer addresses,
- and definitions,

i.e., data supplied directly by an unprivileged unit poster (any address string embedded in a posted unit, message, or AA definition).

### Impact Explanation
If a crafted, non-standard base32 string causes `base32.decode` to succeed but yield a buffer whose bit-length isn't 160/288, the resulting uncaught exception propagates up through address validation, which — if not defensively wrapped in the caller — crashes the validating process. Because address-syntax checks run on every incoming unit/message from the network, a single malformed but "decodable" c-hash string could trigger a denial-of-service across full nodes/hubs processing that unit, preventing validation and thus confirmation of units, matching the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Exploitability depends entirely on whether `thirty-two`'s `base32.decode` can be coerced into returning a buffer of unexpected byte length without throwing (e.g. due to lenient handling of padding/case or invalid characters) — I was not able to fully verify this because the `thirty-two` package's own decoding internals are outside this repository's indexed code and thus outside what I can confirm. If such lenient decoding is possible, likelihood is high since crafting an arbitrary 32/48-character string is trivial for any unit poster. This is the main uncertainty in this finding.

### Recommendation
Wrap the entire body of `isChashValid` (not just the decode call) in `try/catch`, and additionally explicitly validate `chash.length` (in bytes) equals 20 (160-bit) or 36 (288-bit) immediately after decoding, before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, so malformed inputs return `false` instead of throwing.

### Proof of Concept
Conceptual (not fully verified against the actual `thirty-two` decoder behavior):
```js
const chash = require('./chash.js');
// craft a base32 string of the correct outer length (32 chars) but using
// characters/padding that `thirty-two`'s decoder accepts leniently, producing
// a decoded buffer whose bit length differs from 160.
chash.isChashValid('SOME-CRAFTED-32-CHAR-STRING'); // throws uncaught Error("bad length=...")
```

**Caveat:** I could not fully confirm from the indexed code whether `base32.decode` from the `thirty-two` package can actually be induced to return a buffer of unexpected length for a 32-character input without throwing — this depends on the library's internal decoding logic, which is not part of this repository and thus not something I could verify with the available tools. If `base32.decode` reliably enforces exact output length for valid-length inputs, this finding does not hold, and no other analog matching the strict CVE-2022-1623 bug class (decoder trusting internal length data without bounds checks, causing OOB read) with the required Medium+ ocore-specific impact was found in the reachable, in-scope code I could inspect (PEM parsing in `signature.js`, merkle proof deserialization in `merkle.js`, and JSON/oscript evaluation paths all have defensive length/format checks or are wrapped in try/catch that prevent an analogous crash or corruption).
