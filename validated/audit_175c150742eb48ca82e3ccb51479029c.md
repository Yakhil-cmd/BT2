## Title
API clients can impersonate any registered Shipit user via the unauthenticated `X-Shipit-User` header, breaking the binding between authorized token and attributed actor - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Api::BaseController#current_user` derives the acting-user identity from an unauthenticated, attacker-controlled request header (`X-Shipit-User`) rather than from any credential tied to the authenticated `ApiClient`. Any holder of a valid `ApiClient` token (which only proves *authorization to call the API with certain permissions*) can set this header to the login of any pre-existing `Shipit::User` to have privileged actions (locking/unlocking stacks, requesting merges, triggering deploys, aborting tasks) attributed to that arbitrary user, rather than to the actual caller. This mirrors the report's bug class: the entity whose credential is verified (the `ApiClient`/operator) is not the entity the action is actually performed as/for (the impersonated `Shipit::User`/investor), because the acting identity is taken from an unverified field instead of being derived from the verified credential.

### Finding Description
`Api::BaseController#authenticate_api_client` verifies a signed `ApiClient` token (`ApiClient.authenticate`) and binds it to `@current_api_client`: [1](#0-0) 

Separately, `current_user` — used throughout the API controllers to attribute actions to a `Shipit::User` — is computed from a plain HTTP header with no signature or ownership check: [2](#0-1) 

`identify_user` performs a case-insensitive lookup of `User` by `login` using only `request.headers['X-Shipit-User']`, a value fully controlled by the caller and never validated against the authenticated `ApiClient`'s `creator` or any other trusted identity source.

This `current_user` value is then used to attribute privileged, audited actions:
- Locking/unlocking a stack: [3](#0-2) 
- Requesting a pull-request merge (`merge_requested_by`), which is later embedded in the merge commit message via `MERGE_REQUEST_FIELD` and can itself feed back into user attribution of future commits: [4](#0-3) [5](#0-4) [6](#0-5) 
- Deploys/tasks/aborts attribute `user_id`/`aborted_by` to `current_user`, which is later surfaced into the executed deploy script's environment as `SHIPIT_USER`, `EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`: [7](#0-6) 

The equality that should hold is: `identity attributed to the action == identity that authenticated the API call` (or at least an identity provably controlled by the caller). Instead, the code enforces only: `ApiClient token is valid` (authorization scope), while `current_user == arbitrary existing Shipit::User chosen by attacker via header` (attribution). These are two different bindings and the code conflates them, exactly analogous to the reported issue where `msg.sender` (operator) was substituted for the investor address without any parameter binding the two.

### Impact Explanation
Any party holding a valid `ApiClient` token — even one scoped to minimal permissions (e.g., only `lock:stack` or `deploy:stack`) — can forge the `X-Shipit-User` header to impersonate any existing Shipit user (including administrators or trusted committers) for the purposes of:
- Locking/unlocking deploy stacks under a false identity, hiding who actually performed the action.
- Injecting a false `merge_requested_by` into the merge queue, and by extension into merge commit messages via `Merge-Requested-By:`, which is later trusted to establish commit *authorship* by `User.find_or_create_author_from_github_commit`.
- Attributing deploys/rollbacks/task aborts to another user, corrupting the audit trail that Shipit relies on for accountability (`SHIPIT_USER`, `aborted_by`, `merge_requested_by`).

This does not, on its own, grant new permissions beyond what the `ApiClient`'s scope already allows (`check_permissions!` still gates the operation type), but it breaks the identity/audit-trail integrity relied upon for accountability of "who did what," and can be leveraged to forge authorship attribution on merges and deploys.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token with the relevant permission (e.g., `lock:stack`, `deploy:stack`, or `read`/`deploy:stack` for merge requests) and knowledge of an existing user's login — no special privilege beyond having *some* API token is required to set an arbitrary header value. The header is read unconditionally on every API request with no additional check, making this trivially and reliably exploitable by any authenticated API caller.

### Recommendation
Do not derive `current_user` from an untrusted client-supplied header. Bind the acting user to the authenticated credential instead — e.g., use `current_api_client.creator` as the attributed user, or require a separately-authenticated, verifiable proof of the acting user (such as a scoped, signed token per user) rather than a bare header value that can be set to any string by the caller.

### Proof of Concept
1. Obtain any valid `ApiClient` token scoped with, e.g., `lock:stack` permission (`ApiClient#authentication_token`).
2. Send: `PUT /api/stacks/:owner/:repo/:env/lock` with `Authorization: Basic <token>` and header `X-Shipit-User: <victim_login>` where `<victim_login>` is any existing `Shipit::User#login` (e.g., an admin's login, discoverable via commit history/PRs).
3. `identify_user` resolves `current_user` to the victim's `User` record via `User.where('lower(login) = ?', ...)`, and `stack.lock(params.reason, current_user)` records the lock as performed by the victim — see `app/controllers/shipit/api/locks_controller.rb` lines 11-26 and `app/controllers/shipit/api/base_controller.rb` lines 65-72.
4. Repeat against `Api::MergeRequestsController#update` or `Api::TasksController` endpoints to attribute merge requests, deploys, or task aborts to the impersonated user.

**Note on uncertainty:** I could not fully trace every downstream consumer of `current_user`/`Task#user`/`merge_requested_by` in this pass (e.g., whether any authorization decisions, beyond audit attribution, are made based on the impersonated user's team membership). If `current_user`'s team membership (`authorized?`, `Shipit.github_teams`) is consulted anywhere in the API path to grant additional privileges beyond the `ApiClient`'s own `permissions`, the impact would be more severe (privilege escalation rather than pure attribution forgery); I did not find such a code path in the reviewed API controllers, but a full audit of all `current_user` usages in `app/controllers/shipit/api/**` would be needed to rule this out with certainty.
