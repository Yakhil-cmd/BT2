### Title
Cross-tenant check-run refresh via payload field confusion between `repository.owner.login` (signature scope) and `repository.full_name` (stack lookup) - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `payload.dig('repository', 'owner', 'login')`, while `Handler#repository_name` (used by every handler, including `CheckSuiteHandler`) resolves the target stack using `payload.dig('repository', 'full_name')`. These are two independently attacker-controlled fields in a self-crafted JSON body, and nothing enforces that `full_name` starts with `owner.login`. An attacker who owns a GitHub org (and thus knows their own valid `webhook_secret`) can sign a payload with `repository.owner.login` set to their own org (so signature verification passes) while setting `repository.full_name` to `victim-org/victim-repo`, causing `CheckSuiteHandler#process` to schedule `RefreshCheckRunsJob`/`schedule_refresh_check_runs!` on a victim commit.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`org whose secret verified the payload (derived from payload['repository']['owner']['login'])` == `org owning the stack/commit affected (derived from payload['repository']['full_name'])`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches `Shipit.github(organization: repository_owner)`, then verifies the raw body against that org's `webhook_secret` [1](#0-0) .
- `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then dispatches the *same* raw JSON body to `CheckSuiteHandler` [2](#0-1) .
- `Handler#repository_name` reads a **different** field, `payload.dig('repository', 'full_name')`, to resolve the affected `Repository`/`Stack` [3](#0-2) .
- `CheckSuiteHandler#process` uses that resolved `stacks` scope to find the branch/sha and call `schedule_refresh_check_runs!` [4](#0-3) .

Because the JSON body is entirely attacker-authored (this is a raw HTTP POST to `/webhooks`, not a GitHub-mediated call), the attacker can set `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"` in the same object. `verify_signature` only ever inspects `owner.login`; it never checks that `full_name` is consistent with it, and no model validation (`Repository#full_name` is server-side derived from stored `owner`/`name`, not from the payload) closes this gap. `Repository.from_github_repo_name` blindly splits `full_name` on `/` and looks up by `owner`/`name` columns, with no cross-check against the verified signer [5](#0-4) .

Attacker request: a POST to `/webhooks` with header `X-Github-Event: check_suite`, `X-Hub-Signature` computed with the attacker's own valid `webhook_secret` over a body containing:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "check_suite": { "head_sha": "<victim commit sha>", "head_branch": "<victim branch>" }
}
```
`verify_signature` succeeds (attacker-org's secret matches, since attacker fully controls both the body and the signature). `CheckSuiteHandler#process` then resolves `victim-org/victim-repo`'s stacks and enqueues `RefreshCheckRunsJob` for a victim commit.

None of the listed guards prevent this: `verify_signature` verifies bytes against a secret keyed by a field the attacker also controls independently of `full_name`; `ExplicitParameters` only validates presence/type of `check_suite.head_sha`/`head_branch`, not repository ownership consistency; there is no `force_github_authentication`/session check on this unauthenticated webhook endpoint by design.

### Impact Explanation
This lets an attacker who registers/owns any GitHub organization configured in `Shipit.github_teams`/`Shipit.github(organization: ...)` (i.e., anyone with their own org and its `webhook_secret`, which is not a Shipit secret) force `schedule_refresh_check_runs!` to run against an arbitrary tracked commit in **any other tenant's** repository, purely by naming it in `repository.full_name`. This matches "a payload for one repository mutating another's stack/commit" (Critical category): it forces re-evaluation of check-run/merge-gating state for a commit the attacker doesn't own or control, repeatable against any victim stack/branch/sha combination the attacker can guess or observe (branch names and SHAs are often public via GitHub UI/API). The blast radius spans all tenants hosted by the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker needs one legitimate GitHub organization already configured in Shipit's github_app config (so `Shipit.github(organization: repository_owner)` resolves and gives them a real `webhook_secret` to sign with — this is plausible in multi-tenant Shipit deployments where many orgs are configured), and the victim stack must have a tracked commit matching a branch/sha the attacker names. No Shipit session, API token, or victim secret is required. Cost is a single crafted HTTP POST; fully repeatable and automatable across arbitrary victim repos/branches/shas.

### Recommendation
In `Handler#repository_name` (or centrally in `WebhooksController`), require that `payload.dig('repository', 'full_name')` is consistent with the verified `repository_owner` (e.g., assert `full_name.split('/').first.casecmp?(repository_owner)` before dispatching to handlers), or better, derive the target repository owner strictly from the same verified field used for signature verification rather than trusting `full_name` independently.

### Proof of Concept
Minitest plan (webhooks_controller_test.rb style):
1. Configure two orgs in test github config: `attacker-org` (secret `SECRET_A`) and `victim-org` (secret `SECRET_V`, distinct).
2. Create `shipit_repository` for `victim-org/victim-repo` with a `stack` tracking `branch: "main"`, and a `commit` with `sha: "<victim_sha>"` on that stack.
3. Build payload: `{"repository" => {"owner" => {"login" => "attacker-org"}, "full_name" => "victim-org/victim-repo"}, "check_suite" => {"head_sha" => "<victim_sha>", "head_branch" => "main"}}`.
4. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', SECRET_A, payload.to_json)`.
5. Assert:
   - `Shipit.github(organization: 'attacker-org').verify_webhook_signature` returns true for this signature (attacker-org side of the equality).
   - `Repository.from_github_repo_name('victim-org/victim-repo')` returns the victim repository (full_name side of the equality) — i.e., the two sides of the binding (`attacker-org` vs `victim-org`) are unequal yet both accepted.
   - `post :create` with `X-Github-Event: check_suite` and the signature above returns `:ok`, and `assert_enqueued_with(job: RefreshCheckRunsJob)` (or equivalent) fires for the victim commit, proving cross-tenant mutation without possession of `victim-org`'s `webhook_secret`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
