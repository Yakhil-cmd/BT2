### Title
Weak / Predictable Randomness via `number_from_seed()` in Oscript AA Formulas - (File: `formula/evaluation.js`)

### Summary
Ocore's Autonomous Agent (AA) formula language exposes a `number_from_seed()` primitive that derives a "random" number purely by hashing an author-supplied seed with SHA-256. If an AA developer builds a betting/lottery/raffle-style contract that seeds this function with values that are fully known or fully controlled by the unit poster before the triggering unit is even broadcast (e.g. `trigger.unit`, `trigger.address`, `trigger.data`, `timestamp`, or any expression composed from these), the resulting "random" outcome can be computed off-chain by the poster before they commit to submitting the unit. This mirrors the ATM BlindBox bug class: a settlement/outcome value is derived from inputs that the caller can evaluate in advance and then selectively decide whether to submit (or to withhold/regenerate) the triggering transaction, biasing the game in their favor.

### Finding Description
`number_from_seed` is implemented as:
```
case 'number_from_seed':
    ...
    var seed = evaluated_params[0];
    var hash = crypto.createHash("sha256").update(seed.toString(), "utf8").digest("hex");
    var head = hash.substr(0, 16);
    var nominator = new Decimal("0x" + head);
    ...
``` [1](#0-0) 

This is a deterministic, unsalted hash of a single seed value chosen by the AA author. The oscript grammar allows this seed to be any expression, including trigger-controlled fields such as `trigger.unit`, `trigger.address`, `trigger.data`, `timestamp`, and `mci`, all of which are exposed as first-class formula operands. [2](#0-1) 

Crucially, `trigger.unit` is simply `objUnit.unit` — the hash of the unit the caller composes and signs themselves before broadcasting: [3](#0-2) 

Because unit composition, hashing, and signing all happen locally on the poster's side before the unit is ever sent to a hub or witness, a malicious unposted-unit author can:
1. Compose a candidate trigger unit (choosing parents, timestamp, message content, data fields).
2. Compute the exact resulting unit hash (and thus `trigger.unit`) locally.
3. Evaluate `number_from_seed(trigger.unit, ...)` (or whatever combination the AA uses) exactly as the AA logic would, off-chain, to see what outcome it produces.
4. Only broadcast the unit if the precomputed outcome is favorable (e.g., "win"); otherwise silently discard it and re-compose a new candidate (varying nonce data, parents, or timestamp) until a winning hash is found.

This is functionally identical to the ATM BlindBox pattern: the vulnerable contract's random outcome fell back to `keccak256(block.prevrandao, betId, block.timestamp)`, values the attacker could compute and check before submitting the winning settlement transaction. Here, the ocore analog is a seed built from trigger-controlled data that the trigger's own author fully knows before ever broadcasting the unit — an even stronger form of grinding since the attacker never has to "gamble" a submission at all; they simply never publish unfavorable attempts.

The validation layer (`formula/validation.js`) restricts `number_from_seed`'s argument count/types but does not restrict the *source* of the seed to anything unpredictable/unbiasable such as a signature or externally-supplied unpredictable value: [4](#0-3) 

Note that ocore does provide a legitimate unbiasable primitive, `vrf_verify`, for verifiable random functions, but nothing in AA validation prevents an AA author from using the weaker `number_from_seed` with a predictable/attacker-chosen seed instead. [5](#0-4) 

### Impact Explanation
Any AA that implements gambling, lotteries, raffles, blind-box style mechanics, or any other chance-based fund distribution using `number_from_seed()` seeded (directly or indirectly) by trigger-controlled/pre-known data is exploitable by an unprivileged trigger sender. The attacker can grind for favorable outcomes with zero on-chain cost for failed attempts (since unfavorable candidate units are simply never broadcast), draining the AA's balance over repeated interactions — a direct AA fund-loss scenario analogous to the 13M ATM token loss in the referenced report.

### Likelihood Explanation
Likelihood is high for any AA built on this exposed primitive with commonly-used seed material (`trigger.unit`, `trigger.address`, `trigger.data`, `timestamp`), because:
- Unit hashes and content are fully known to the composer before broadcast, with no cost to discard "bad" units.
- `number_from_seed` is a public, documented AA formula function reachable by any AA author, and any resulting AA is reachable by any unprivileged trigger sender.
- The framework offers no automated warning/validation preventing weak-seed usage, only providing a stronger `vrf_verify` alternative that is opt-in.

### Recommendation
- Add AA validation-time or documentation-level warnings when `number_from_seed`'s seed expression references trigger-controlled/pre-known fields (`trigger.unit`, `trigger.address`, `trigger.data`, `timestamp`, `mci`) without also mixing in unpredictable data unknown to the poster at compose time (e.g., a value only known after MC-unit stabilization, or a committed-then-revealed secret).
- Strongly recommend (in docs and getter/validation tooling) that AAs requiring unbiasable randomness use `vrf_verify` or a commit-reveal scheme spanning multiple triggers, rather than `number_from_seed` on attacker-controlled inputs.
- Consider making `number_from_seed`'s seed require inclusion of a value that is unknown to the trigger sender at compose time, such as a subsequent stable MC unit content only knowable after the trigger's ball is stabilized.

### Proof of Concept
Conceptually (oscript AA using the vulnerable pattern):
```
{
  $r = number_from_seed(trigger.unit, 0, 99);
  if ($r >= 50) {
    // payout message
  } else {
    // no payout, keep stake
  }
}
```
An attacker composes the triggering unit locally, computes its unit hash (`trigger.unit`) exactly as `aa_composer.getTrigger()` would derive it, evaluates `number_from_seed` off-chain via the same SHA-256-based logic in `formula/evaluation.js`'s `number_from_seed` case, and broadcasts only when `$r >= 50`. Because composing, hashing, and discarding unposted units costs nothing on ocore, the attacker can grind indefinitely for a winning seed before ever submitting a transaction, guaranteeing wins against any AA using this construction.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
