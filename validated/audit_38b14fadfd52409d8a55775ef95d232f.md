### Title
Webhook signature verification binds to `repository.owner.login` while every event handler acts on the unverified `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1)  Once the HMAC signature check passes for that organization's secret, the raw JSON body is dispatched unmodified to every registered handler. Every handler, however, resolves the target repository/stack from a *different* JSON field: `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3)  This is the same class of bug as the Hyperdrive finding: the field that is verified (`repository.owner.login`, used to pick the signing secret) is not the field that is actually acted upon (`repository.full_name`, used to locate the target `Repository`/`Stack`). Nothing in the JSON payload forces these two fields to agree — the signature only proves the raw bytes came from someone holding the secret for the org named in `repository.owner.login`.

### Finding Description
Shipit is explicitly designed as a multi-tenant engine: `config/secrets.*.yml` allows configuring multiple independent GitHub organizations, each with its own `app_id`, `installation_id`, and `webhook_secret`. [5](#0-4)  `Shipit.github(organization:)` looks up the app config for the org named in the payload, and `GitHubApp#verify_webhook_signature` performs a constant-time HMAC comparison using that org's own secret. [6](#0-5) 

The binding that should hold is:

`organization_that_signed(payload) == organization_owning(repository_acted_on(payload))`

but the controller only enforces:

`verify(secret_for(payload.repository.owner.login), signature) == true`

while the handlers use:

`repository_acted_on(payload) = Repository.from_github_repo_name(payload.repository.full_name)`

Because `repository.owner.login` and `repository.full_name` are two independent strings inside the same attacker-supplied JSON body, an attacker who legitimately controls (or has been granted) a GitHub App installation on **any** one organization configured on the Shipit instance — and therefore legitimately possesses that org's `webhook_secret` — can:
1. Set `repository.owner.login` (and `organization.login`) to their own controlled org, so `verify_signature` picks their own org's secret and the HMAC check succeeds.
2. Set `repository.full_name` (and other repository-identifying fields used deeper in specific handlers, e.g. `Shipit::Webhooks::Handlers::PullRequest::ClosedHandler#repository` at `params.repository.full_name`) to `victim-org/victim-repo`, a repository belonging to a completely different, unrelated tenant/org on the same Shipit instance. [7](#0-6) 
3. Send the forged, correctly-signed request to `/webhooks`.

The signature check in `verify_signature` never re-validates that `repository.full_name`'s owner matches `repository.owner.login`, and no handler cross-checks the two fields either — `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and all `PullRequest::*Handler`s trust `repository.full_name` (or `params.repository.full_name`) directly. [8](#0-7) 

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," matching the accepted analog class in scope. Concretely, on a multi-tenant Shipit instance, a low-privilege attacker who is merely an admin of their own small GitHub App installation/org can forge webhook events acting on a victim organization's repositories/stacks that they have no access to, causing state changes such as:
- Forcing `PushHandler` to enqueue `GithubSyncJob` for a victim `Stack` with an attacker-chosen `expected_head_sha`, causing Shipit to sync/advance the victim stack's head based on attacker-controlled input. [9](#0-8) 
- Archiving a victim's review stack via the forged `pull_request` `closed` event. [10](#0-9) 
- Injecting fabricated commit statuses/check-suite results for a victim's commits, which Shipit may treat as CI/deployability signals gating deploys.

This is capable of an unauthorized state change to a repository the attacker does not control, aligning with the "unauthorized deploy/rollback" impact category, without needing any Shipit session, `ApiClient` token, or the victim org's own `webhook_secret`.

### Likelihood Explanation
Requires the attacker to have legitimate access to *some* organization's GitHub App webhook secret configured on the shared Shipit instance (a realistic scenario for any shared/self-hosted multi-tenant Shipit deployment, as explicitly supported by `config/secrets.*.yml`). No access to the victim org's secret, no Shipit session cookie, and no `ApiClient` token are needed — only network access to the public `/webhooks` endpoint and one legitimately-issued webhook secret for an unrelated org.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select/verify the signing secret matches the owning organization of the repository the handlers will act on — e.g., derive `repository_owner` from the same field used later (`repository.full_name`'s owner segment), or explicitly assert `params.dig('repository','full_name')&.split('/')&.first&.casecmp?(repository_owner)` before dispatching to handlers, rejecting mismatches with `422`.

### Proof of Concept
1. Attacker legitimately administers a GitHub App for `attacker-org`, configured in Shipit's `secrets.yml` with `webhook_secret: "attackersecret"`.
2. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attackersecret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"` (from `repository.owner.login`), fetches `attacker-org`'s `GitHubApp`, and the signature check succeeds. [11](#0-10) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")`, which is unrelated to `attacker-org`, and enqueues `sync_github(expected_head_sha: "deadbeef...")` against the victim stack, all under a signature that only proves knowledge of `attacker-org`'s secret. [3](#0-2) [9](#0-8)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
