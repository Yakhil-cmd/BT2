### Title
Cross-repository/cross-stack status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by matching `sha` across the entire `commits` table, with no check that the payload's reporting repository (`params['name']`/`params['repository']['full_name']`) matches the repository owning the `Stack` that the matched `Commit` belongs to. Any commit row anywhere in the install that happens to share a SHA with the webhook's `sha` gets a new `Status` created against it, letting a status legitimately reported for one repository silently overwrite `Stack#branch_status`/`Stack#merge_status` for a completely different stack/repository.

### Finding Description
The binding that should hold is: `payload.repository == commit.stack.repository` for every `Status` created from a webhook. This is never checked.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#create` dispatches the parsed JSON `status` event to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which authenticates the *organization* (via `Shipit.github(organization: repository_owner)`), not the specific *repository*. Critically, per `lib/shipit.rb#github`/`#github_default_organization`, in the common single-GitHub-App configuration (`github_default_organization` is `nil`), the `organization:` argument is ignored entirely and the single shared `secrets.github` config/secret is used for every request regardless of what repository/org name is embedded in the payload: [1](#0-0) 
- `app/models/shipit/webhooks/handlers/status_handler.rb#process` then looks up commits solely by `sha`, iterating **every** matching `Commit` row system-wide and writing a `Status` for each: [2](#0-1) 
- `Commit#create_status_from_github!` -> `Status.replicate_from_github!` creates the `Status` scoped to `commit.stack_id` (the matched commit's own stack), not to any repository named in the incoming payload: [3](#0-2) [4](#0-3) 
- `Stack#branch_status` and `Stack#merge_status` then aggregate over `undeployed_commits`, using `commit.status.simple_state`, so the forged `Status` row directly flips the aggregate: [5](#0-4) 

Root cause: the GitHub status webhook payload carries the originating repository as a top-level `name` field (e.g. `"name": "baxterthehacker/public-repo"`, see fixture) as well as `repository.full_name`, but `StatusHandler`'s `ExplicitParameters` schema doesn't even require/accept those fields, and `process` never cross-checks them against `commit.stack.repository`: [6](#0-5) 

Exploit flow: if two `Stack`s in the same Shipit install (very common: a single GitHub App/org tracking many repositories, or a repository that was forked/split and shares git history) each have a `Commit` row with the same `sha` (trivially achievable because git SHAs are content hashes shared identically across forks up to the point of divergence — an attacker only needs to reference an existing shared ancestor commit, not forge a hash collision), then any legitimately-signed `status` webhook for Repo A's commit (triggered simply by the attacker opening a PR/pushing a branch whose head is that shared ancestor commit, which naturally causes CI to post a real `success`/`failure` status for that SHA) will also be applied to the identical `Commit` row tracked under victim's Stack B. No signature forgery is required at all — the webhook is real, correctly signed, and about the attacker's own repository; the vulnerability is that Shipit doesn't scope the resulting `Status` write to the repository the webhook actually authenticated.

Existing guards do not catch this:
- `verify_signature` only authenticates the *organization*/app config, not a specific repository, and in the (common) single-app configuration it doesn't even use the organization value at all.
- `drop_unhandled_event`, `ExplicitParameters` schema validation, and model validations on `Status`/`Commit` only check field types/presence, not repository ownership.
- Nothing in `StatusHandler#process` or `Commit#create_status_from_github!` filters by `stack.repository`.

### Impact Explanation
A status write is made against `victim`'s `Stack` (a record the attacker's authenticated request never legitimately concerned) purely because of a coincidental/shared commit SHA — this is "a payload for one repository mutating another's stack/commit," listed as Critical impact. Concretely: `Stack#branch_status` flips from `'failure'` to `'success'`, `Stack#merge_status` follows suit, and `Stack#allows_merges?` (`app/models/shipit/stack.rb:380-382`) can now return `true`, unblocking merge-queue processing for the victim's PRs despite a real, unresolved CI failure — misleading operators/dashboards and enabling an unauthorized/incorrect merge decision. This is repeatable against any pair of stacks that share a commit SHA (fork relationships, repo splits/renames, monorepo extraction, mirrored repos), and scales to any tenant sharing the Shipit instance's GitHub App/org.

### Likelihood Explanation
Requires: (1) a multi-stack/multi-repo Shipit install (typical), (2) the attacker being able to legitimately trigger a real, correctly-signed `status` webhook for *some* repository tracked (or seen) by the instance (trivial — any contributor triggering CI on a PR/branch), and (3) a SHA collision between that repository's commit and one already recorded in the victim's stack's `commits` table (realistic in fork/split/mirrored-repo scenarios, and can be engineered by the attacker by simply pointing their PR/branch at a pre-existing shared ancestor commit rather than a hash collision attack). No secrets, tokens, or privileged roles are needed for this path — the flaw is a missing authorization/scoping check inside the engine's own webhook-processing code, independent of signature validity.

### Recommendation
In `StatusHandler#process`, require and validate the payload's repository identity (`params.dig('repository','full_name')` or `params['name']`) and only apply the status to commits whose `commit.stack.repository.full_name` (case-insensitively) matches. Reject/ignore commits that don't match rather than iterating unscoped across `Commit.where(sha: ...)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or via `WebhooksControllerTest`):
1. Create `victim_stack` (`shipit_stacks(:shipit)` or similar) with a `Commit` `shared_sha` that is the most recent undeployed commit, and give it a `Status` with `state: 'failure'`. Assert `victim_stack.branch_status == 'failure'` and `victim_stack.merge_status == 'failure'`.
2. Create a second, unrelated `attacker_stack` pointing at a different `Repository` (`attacker/repo`), with its own `Commit` row using the same `shared_sha`.
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `sha == shared_sha`, `state: 'success'`, and `repository`/`name` fields identifying `attacker/repo` (not victim's repository), with signature verification stubbed as in existing tests (`GithubHook.any_instance.stubs(:verify_signature).returns(true)` / mocking `Shipit.github(...).verify_webhook_signature` to return true, mirroring `test/controllers/webhooks_controller_test.rb`).
4. Assert `victim_stack.reload.branch_status` changed from `'failure'` to `'success'`, and `victim_stack.merge_status` changed from `'failure'` to `'success'`, even though the POST's repository field never named `victim_stack`'s repository — proving `payload.repository != commit.stack.repository` yet the state was mutated.

    def merge_status(backlog_leniency_factor: 2.0)
      return 'locked' if locked?
      return 'failure' if %w[failure error].freeze.include?(branch_status)
      return 'backlogged' if backlogged?(backlog_leniency_factor:)

      'success'
    end

    def backlogged?(backlog_leniency_factor: 2.0)
      maximum_commits_per_deploy && (undeployed_commits_count > maximum_commits_per_deploy * backlog_leniency_factor)
    end

    def branch_status
      undeployed_commits.each do |commit|
        state = commit.status.simple_state
        return state unless %w[pending unknown missing].freeze.include?(state)
      end
      'pending'
    end
