### Title
A borrower can permanently shield an underwater account from liquidation and bad-debt cleanup by holding a dust Aquarius-LP collateral leg whose pool the attacker drains below `min_pool_value_wad` - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The price-aggregator's Aquarius LP provider fails closed whenever the pool's total value falls below the configured `min_pool_value_wad` floor, and the controller's risk pipeline prices **every** supply leg of an account unconditionally. Supplying new collateral requires no price read, so an underwater borrower can permissionlessly attach a dust Aquarius LP leg to their own account and then withdraw their own liquidity from that Aquarius pool, driving its value under the floor. From that point on, every valuation of the account reverts: `liquidate`, `clean_bad_debt`, `update_account_threshold`, and governance's force-socialization path all call `calculate_account_risk_totals`, which panics on the missing price. The debt accrues interest while being permanently unliquidatable, converting a temporarily unhealthy position into protocol bad debt.

### Finding Description
The bug class from JLSEC-2026-20 is "a missing/uncustomizable bound that an unprivileged party can push past a hard limit to deny service." Here, the Aquarius LP source enforces a hard floor:

- `read()` in `contracts/price-aggregator/src/providers/aquarius.rs` returns `OracleError::InsufficientAquariusLiquidity` when `pool_value_wad < lp.min_pool_value_wad` (lines 118–122), and `NoLastPrice` when pool reads fail.
- `Context::cached_price` in `contracts/controller/src/context.rs:154-160` panics (`OracleNotConfigured`/propagated aggregator error) when a price is absent — there is no skip or zero-price fallback for a leg.
- `calculate_account_risk_totals` in `contracts/controller/src/risk/totals.rs:157-201` iterates **all** `supply_positions` and calls `cache.cached_price(&hub_asset.asset)` for each, so one unpriceable dust leg aborts the whole valuation.
- `build_liquidation_plan` (`contracts/controller/src/positions/liquidation/plan.rs:34-44`) calls `calculate_account_risk_totals` before any leg selection; a liquidator cannot exclude the poisoned collateral leg.
- Supply entry requires no price (per `docs/explanation/threat-model.md` DoS.1: "Supply needs no price, so an indebted borrower can add a dust leg of any listed collateral"), so the leg can be added even while the account is already underwater.
- The Aquarius pool itself is a permissionless AMM; `min_pool_value_wad` values in `configs/mainnet/markets.json` (e.g., 200,000–1,000,000 USD WAD for the listed LP markets) are achievable for an attacker who supplies the majority of a smaller pool's liquidity, or for any LP withdrawing from an already thin pool.

The same leg also blocks `clean_bad_debt`/force-socialization (which re-values the account), so even the insolvency-resolution path is bricked while the pool stays below the floor.

### Impact Explanation
Permanent freezing of the liquidation path for the attacker's account leading to protocol insolvency: the debt can never be liquidated nor socialized while the pool stays drained, interest keeps accruing, and the loss is ultimately borne by suppliers via index write-down once the position becomes unrecoverable bad debt — or the debt simply sits unbacked indefinitely. Cost to the attacker is the dust collateral plus temporarily parking liquidity outside the pool (they can re-add it later or use a pool they already dominate). This meets the "permanent freezing of funds / protocol insolvency" acceptance bar.

### Likelihood Explanation
Fully unprivileged: `supply` of a listed LP asset, `borrow`, and Aquarius `withdraw_liquidity` are all permissionless entrypoints. The attacker needs to control enough of the Aquarius pool's liquidity to pull its value under `min_pool_value_wad`; since the floors are fixed at listing and thin pools exist, this is a capital cost, not a permission barrier. No privileged role, leaked key, oracle dishonesty, or parameter misconfiguration is required — the fail-closed behavior is the intended floor enforcement, turned into a shield. The threat model itself registers this as DoS.1, so the scenario is a known shape, but the concrete attack sequence (borrow → add dust LP leg → drain own pool) remains reachable in the shipped code.

### Recommendation
Treat an unpriceable collateral leg as zero-value rather than aborting the whole valuation when computing liquidation eligibility/seizure — e.g., in `calculate_account_risk_totals`, catch a missing/failed price for a supply leg and contribute `0` to `total_collateral`/`weighted_collateral` (with the leg excluded from the seizure plan), while keeping fail-closed pricing for debt legs and for borrow/withdraw risk gates. Alternatively, let `build_liquidation_plan` tolerate per-leg price failures by dropping only the affected collateral legs from `calculate_seized_collateral`, and give `clean_bad_debt` a path that values collateral as zero when a feed is provably dead. A `min_pool_value_wad` floor alone cannot distinguish "pool too thin to trust" from "attacker-chosen shield," so the liquidation pipeline must degrade gracefully per leg.

### Proof of Concept
1. Attacker provides the majority of liquidity to an Aquarius pool whose LP token is listed as collateral (e.g., hub 3 `AQUAUSDC_LP` / `XLMAQUA_LP` in `configs/mainnet/markets.json`), receiving LP shares.
2. Attacker calls `supply(attacker, lp_token, X)` plus a normal collateral, then `borrow(...)` near the LTV limit.
3. Market moves or interest accrual push `HF < 1` (or the attacker borrows to the edge and waits).
4. Attacker calls `supply` again with a dust amount of the LP token — supply is not price-gated, so this succeeds even while underwater — adding the LP leg to `account.supply_positions`.
5. Attacker calls `withdraw_liquidity` on the Aquarius pool, reducing `pool_value_wad` below `lp.min_pool_value_wad`.
6. Any liquidator calling `liquidate(liquidator, account_id, payments, SeizeMode::Transfer)` reverts: `providers::aquarius::read` returns `InsufficientAquariusLiquidity` → aggregator yields no usable price → `Context::cached_price` panics → `calculate_account_risk_totals` aborts before the HF check. `clean_bad_debt` and the governed force-socialization runbook revert identically.
7. The attacker re-pumps the pool only if they want to exit; otherwise the position sits unliquidatable while debt grows, and suppliers absorb the eventual write-down. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
