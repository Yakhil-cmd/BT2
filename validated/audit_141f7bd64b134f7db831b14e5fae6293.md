CVE-2017-11728 describes a heap-based buffer over-read in libming's SWF bytecode decompiler (`decompile.c`, function `OpCode`) — a C library for creating/parsing Flash files, entirely unrelated to blockchain runtime logic. There is no genuine architectural analog in the Polkadot SDK: this is not a case of forcing an unrelated bug class onto FRAME/XCM/contracts.

Investigation of the closest conceptually-related code (bytecode/opcode parsing and buffer reads reachable from user-supplied contract code) shows consistent bounds checking rather than a matching flaw:

- `read_sandbox_memory_into_buf` in pallet-contracts uses `memory.get(ptr..ptr + buf.len())` which safely returns `None`/error instead of over-reading on out-of-range access [1](#0-0) .
- The `pallet-revive` PolkaVM code-upload validator (`limits::code::enforce`) parses the untrusted blob with `polkavm::ProgramBlob::parse`, propagating parse errors as `CodeRejected` rather than reading unchecked memory, and iterates instructions from the validated parse result [2](#0-1) .
- The EVM interpreter's `ExtBytecode::read_slice`/`relative_jump`/`absolute_jump` use `unsafe` pointer arithmetic but rely on `debug_assert!` bound checks that are asserted to be enforced by callers (opcode length is derived from the bytecode's own validated table, not attacker-supplied length) [3](#0-2) .
- `decode_bytes` in the precompile ABI decoding utility reads from fixed, hardcoded offsets (`input[28..32]`, `input[60..64]`) rather than attacker-controlled offsets driving the slice bounds directly [4](#0-3) , though this particular function trusts `bytes_len`/`offset` from `input` for the final slice — this is inside `uapi` helper code used by precompile implementations, not exposed as a directly attacker-reachable path without further downstream validation, and no such call site was found wiring raw untrusted external call data into `decode_bytes` without prior length checks in the reachable code found.

None of these constitute a demonstrable, exploitable heap over-read reachable via a real signed extrinsic/contract-call entry point analogous to the Ming `decompileSETMEMBER`/`OpCode` missing-bounds-check pattern. Given the requirement to reject forced or unsupported analogies rather than invent a finding, no qualifying vulnerability is reported.

pub fn decode_bytes(input: &[u8], out: &mut [u8]) -> usize {
	let mut buf = [0u8; 4];
	buf[..].copy_from_slice(&input[28..32]);
	let offset = u32::from_be_bytes(buf) as usize;

	let mut buf = [0u8; 4];

	// `bytes = offset (32 bytes) | len (32 bytes) | data`
	out[..bytes_len].copy_from_slice(&input[32 + offset..32 + offset + bytes_len]);
