### Title
Webhook authenticity check can be bypassed by attacker-chosen organization, decoupling "organization whose secret authenticated the request" from "repository/stack actually written" - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to verify the HMAC signature against using a field taken straight from the unauthenticated JSON body, before any signature check has happened. Combined with the fact that signature verification is a no-op when the selected organization has no `webhook_secret` configured, an attacker who can reach the public `/webhooks` endpoint can pick, via the payload itself, which "identity" is used to authenticate the request — breaking the intended binding between *the organization that authenticates the webhook* and *the repository/stack that ends up being written to*.

### Finding Description
This is the same bug class as the reported `activeValidatorCount` issue: a value that is supposed to gate a security-relevant decision is effectively never enforced, so a check that looks present in the code is trivially satisfiable.

- The controller derives the signing organization from the payload itself, before any verification: `repository_owner` is read via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and this value is passed to `Shipit.github(organization: repository_owner)` to pick which `GitHubApp`/secret to verify against. [1](#0-0) [2](#0-1) 

- Multi-organization configuration is an explicitly supported schema (`github_organizations`, `github_app_config(organization)`), each org optionally carrying its own `webhook_secret` (documented as optional in `docs/setup.md`/`config/secrets.development.example.yml`). [3](#0-2) 

- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that organization has no configured `webhook_secret`: [4](#0-3) 

Putting these together: the binding the system relies on is `verified_identity == repository_owner_acted_upon`. Before the fix, that binding never holds, because `verified_identity` is picked from the same untrusted field that later drives which repository/stack/commit gets mutated. An attacker who wants to forge an event for stack `real-org/real-repo` (which does have a strong secret) can set `repository.owner.login` (used only for secret selection) to any other GitHub org configured on the same Shipit instance that has *no* `webhook_secret`, while keeping `repository.full_name`/other payload fields pointing at the real target repository/commit that the handler will act on. `verify_signature` then trivially passes (`return true unless webhook_secret`), and `Shipit::Webhooks.for_event(event)` handlers run on a completely attacker-controlled body with no HMAC ever validated for the data actually consumed. [5](#0-4) 

This is analogous to `activeValidatorCount` being read to gate `remainingProofs`/`creditedNodeETH` logic while never actually being tied to the real state it's supposed to track — here, the "authorization" gate (HMAC secret selection) is tied to an attacker-chosen field instead of the actual identity of the repository being mutated.

### Impact Explanation
An unauthenticated network attacker (no Shipit session, no GitHub token, no `webhook_secret` knowledge — they rely on the *absence* of a secret on an unrelated configured org) can inject arbitrary GitHub events for any tracked stack: fake `status`/`check_suite` results (used by Shipit to gate deploys/merges via `deployable_status`/`merge_status`), fake `membership`/`team` changes (`Team`/`Membership` records created/deleted per the `membership` handler), or push events. This crosses the authentication boundary the webhook signature is meant to enforce and can feed forged CI/status state into stacks that legitimately gate deploy/merge decisions — i.e., an authentication bypass on the webhook ingress path.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (a supported, documented configuration) and that at least one of those configured organizations has no `webhook_secret` set (explicitly documented as optional). No credentials, sessions, or secrets are needed by the attacker — only network access to the public `/webhooks` endpoint, which is unauthenticated by design (`skip_before_action :verify_authenticity_token`). [6](#0-5) 

### Recommendation
Do not let the payload itself select which secret is used to authenticate that same payload. Either (a) require every configured organization to have a non-blank `webhook_secret` and refuse to boot/serve requests otherwise, removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`, or (b) bind the webhook endpoint to a single, statically configured organization/secret per route/installation instead of deriving it from `params.dig('repository', 'owner', 'login')`, so the value used to select the verification secret cannot be influenced by the untrusted request body.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `real-org` (with a strong `webhook_secret`) and `side-org` (no `webhook_secret`, as allowed by the documented optional field). [7](#0-6) 
2. Send `POST /webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<victim commit sha in real-org/real-repo>",
  "state": "success",
  "branches": [{"name": "master"}],
  "repository": {"owner": {"login": "side-org"}, "full_name": "real-org/real-repo"}
}
```
3. `verify_signature` resolves the organization to `side-org` via `repository_owner` and calls `Shipit.github(organization: 'side-org').verify_webhook_signature(...)`. [8](#0-7) 
4. Because `side-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (absent/incorrect) `X-Hub-Signature` header, and the `status` handler creates a forged successful `Status` for the victim commit in `real-org/real-repo` without any valid signature ever having been checked for that repository's actual secret. [4](#0-3)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
