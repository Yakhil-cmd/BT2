### Title
Stack-scoped API tokens can read CCMenu deploy status for any stack, not just the authorized one - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via its `stack` association, and every other API endpoint enforces that scope through `Api::BaseController#stacks`. `Api::CCMenuController#stack`, however, bypasses that shared scoping method and resolves the target stack directly from the request parameter, so a token that is only supposed to authorize one stack can be used to read the deploy/build status of any stack in the installation.

### Finding Description
`Shipit::ApiClient` has an optional `stack` association [1](#0-0) , and this scoping is a real, exercised feature: the `here_come_the_walrus` fixture is a client tied to a specific stack with `read:stack` permission [2](#0-1) .

The scoping is enforced centrally in `Api::BaseController#stacks`, which restricts the visible stack set to `current_api_client.stack_id` when the client is scoped: [3](#0-2) . Controllers such as `Api::StacksController` correctly go through this scoped method (`stacks.from_param!(params[:id])`) [4](#0-3) .

`Api::CCMenuController`, however, defines its own `stack` resolver that ignores the scoping entirely and looks the stack up globally: [5](#0-4) . The action-level authorization only checks the permission string via `require_permission :read, :stack`, which calls `ApiClient#check_permissions!` — a check that only inspects the `permissions` array, not `stack_id` [6](#0-5) . Because `check_permissions!` never consults `stack_id`, and `CCMenuController#stack` never consults it either, the one place that was supposed to bind "the stack this token is authorized for" to "the stack actually being read" is missing.

The equality broken is: **stack a token authorizes (`ApiClient#stack_id`) ≠ stack it actually touches (`params[:stack_id]` resolved via `Stack.from_param!`)**. Before the attacker's request, the token's authorization is (by design) `{stack_id: A}`; after hitting `GET /api/stacks/:stack_id/ccmenu.xml` with `stack_id=B` and the same token, the controller serves stack `B`'s data with no error.

### Impact Explanation
This allows an attacker holding any token with the `read:stack` permission scoped to a single stack — including tokens issued through the low-privilege `CCMenuUrlController#fetch` flow (`ApiClient.create_with(permissions: %w[read:stack])`) [7](#0-6)  — to read deploy/build state (latest deploy id, status, timing) for any other stack in the Shipit instance by simply changing the `stack_id` URL parameter, matching the "unauthenticated/unauthorized read of stack state" High-impact category: the token authorization boundary that the rest of the API enforces is not honored by this endpoint.

### Likelihood Explanation
Any actor who can obtain or is issued a stack-scoped, read-only API token (a routine, low-privilege credential meant for CI dashboard integration) can trivially exploit this by changing one URL parameter — no additional privileges, signatures, or write access are required.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the shared, scope-aware `stacks` method (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped token cannot escape its authorized stack.

### Proof of Concept
1. Obtain a stack-scoped API token authorized only for stack `A` with `read:stack` permission (e.g., an `ApiClient` with `stack_id = A.id`, as modeled by the `here_come_the_walrus` fixture).
2. Send `GET /api/stacks/:B_id/ccmenu.xml?token=<token>` where `B` is a different stack the token was never scoped to.
3. `Api::CCMenuController#authenticate_api_client` authenticates the token; `require_permission :read, :stack` passes because the token has the `read:stack` permission string; `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])`, ignoring `stack_id` scoping, and returns stack `B`'s deploy status — data the token was never authorized to see.
