### Title
Hash Collision in `arbiter_contract.getHashSrc` Due to Delimiter-less Field Concatenation - (File: `arbiter_contract.js`)

### Summary
`arbiter_contract.js`'s `getHashSrc()` builds the source string for the contract's identifying `hash` by concatenating multiple free-form and numeric fields. For any contract whose `creation_date` is not after `exports.NEW_HASH_DATE` ('2026-11-01'), the function falls back to naive concatenation with **no delimiter** between fields, exactly the bug class described in the Mimc report where variable-length inputs can be re-partitioned to produce an identical digest.

### Finding Description [1](#0-0) 

```js
function getHashSrc(contract) {
	...
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
```

The developers clearly recognized the ambiguity risk and introduced `exports.DELIMITER = "[|#|]"` for hashes computed on-or-after `NEW_HASH_DATE`, but the branch taken for `creation_date <= NEW_HASH_DATE` still joins `title`, `text`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, and `asset` with `""` (no separator at all). Because `creation_date` is stamped by `createAndSend()` with the current time (`new Date().toISOString()...`, `arbiter_contract.js:23`), and today's date (2026-09-15) is before `NEW_HASH_DATE` (2026-11-01), **every contract created right now uses the vulnerable delimiter-less path**.

This is functionally identical to the Mimc bug: because the fields are variable-length strings/numbers with no framing, a byte sequence produced by one partition of `(title, text, payer_name, arbiter_address, payee_name, amount, asset)` can be exactly reproduced by a different partition of those logical fields (e.g. shifting characters across the `title`/`text` boundary, or across the `amount`/`asset` boundary since `amount` is coerced to a decimal string with no separator before `asset`). Two semantically different contracts can therefore hash to the same `sha256` digest.

This `hash` is not just a display label — it is embedded directly in the on-chain data message and cross-checked cryptographically: [2](#0-1) [3](#0-2) 

and is used to construct the dispute-resolution data-feed key that determines fund release: [4](#0-3) [5](#0-4) 

### Impact Explanation
`hash` is the sole binding between the off-chain-negotiated contract terms (amount, asset, party names, arbiter, title/text) and the on-chain artifacts (`contract_text_hash` payload, the `"CONTRACT_"+hash` data-feed key the arbiter uses to declare a dispute winner). If two different logical term sets collide to the same hash, a malicious counterparty (the offeror, who is fully in control of `title`/`text`/`amount` inputs before sending them via `arbiter_contract_offer`) can:
- Present terms to the counterparty that, once serialized, are byte-identical to a different term set (e.g., a different `amount`/`asset` split or a different `title`/`text` split), while both hash to the same `contract.hash`.
- Later leverage the ambiguity to dispute what was actually agreed (repudiation), since the cryptographic commitment (`contract_text_hash`) cannot distinguish between the colliding term sets — undermining the arbiter's/dispute resolution's ability to bind the correct amount/party terms to the escrowed funds, which is the actual mechanism releasing escrowed base/asset funds (`pay`/`complete`/dispute flow in `arbiter_contract.js`).

This directly threatens the integrity of the arbiter-escrow fund-release logic (a "private-payment counterparty"-reachable flow named explicitly in scope), potentially enabling a counterparty to cause the wrong terms (amount/party) to be treated as authoritative during dispute resolution, i.e., unauthorized diversion of escrowed funds.

### Likelihood Explanation
The vulnerable code path is not hypothetical or legacy-only: given the hardcoded `NEW_HASH_DATE = '2026-11-01'` and today's date of 2026-09-15, **all currently-created contracts use the unpatched, delimiter-less hash**. The offeror (an unprivileged paired-device counterparty) fully controls the raw field values sent in the `arbiter_contract_offer` device message, making a crafted collision straightforward to construct (e.g., shifting a digit between `amount` and `asset`, or characters between `title` and `text`).

### Recommendation
Immediately apply the delimiter-based `getHashSrc` (or an unambiguous, length-prefixed encoding) unconditionally, without depending on `creation_date > NEW_HASH_DATE`. If backward compatibility with old hashes is required, this must be handled via explicit versioning rather than a future opt-in date, since the "fix" as written leaves the vulnerable path live for all new contracts until the future cutover date.

### Proof of Concept
Given the pre-`NEW_HASH_DATE` path: `[title, text, creation_date, payer_name, arbiter_address, payee_name, amount, asset].join("")`.

Two different logical contracts:
- Contract A: `amount = 100`, `asset = "0BTC"` → concatenated fragment `"1000BTC"`
- Contract B: `amount = 1000`, `asset = "BTC"` → concatenated fragment `"1000BTC"`

With all other fields identical, `getHashSrc(A) === getHashSrc(B)`, so `getHash(A) === getHash(B)` — two contracts with different agreed amounts produce an identical `sha256` commitment hash, exactly analogous to the Mimc `lastChunk` shift bug where different `calldata` produced the same `mimcHash`.

*Note: I was unable to fully verify within the remaining iterations whether `wallet.js`'s `arbiter_contract_offer` handler independently re-validates the full field set against the received hash before storing/displaying the contract — this could be an important additional mitigating or aggravating factor and would benefit from further review in a full Devin session.*

		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){

			return;
		}
		winner = message.payload[key];
	});
