## Analysis Result

### Title
CCMenu API tokens scoped to a single stack can be replayed to read the build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The Shipit CCMenu integration issues per-user API tokens intended to expose the CI status of a *single* stack (used for CCTray-style dashboards). The token is meant to be scoped to that one stack via `ApiClient#stack_id`, but `Api::CCMenuController` never checks that binding when resolving the stack to render, so any valid CCMenu token can be replayed against `stack_id` for an arbitrary stack.

### Finding Description
`CCMenuUrlController#client` creates the `ApiClient` used for the CCMenu feed without setting a `stack`, and reuses the same client for every stack a user requests a URL for (lookup is keyed only on `creator` + `name`, not `stack`): [1](#0-0) 

Because `stack:` is never part of `create_with`, the resulting `ApiClient#stack_id` is `nil`, so `stack_id?` is false and, per `Api::BaseController#stacks`, this client would normally be treated as unscoped (`Stack.all`) rather than limited to one stack: [2](#0-1) 

Even setting that aside, `Api::CCMenuController` overrides the base `stack` accessor and resolves the stack purely from the request's `stack_id` param, bypassing the `stacks` scoping helper (and therefore any `current_api_client.stack_id` restriction) entirely: [3](#0-2) 

The only authorization check performed is the coarse permission-name check `require_permission :read, :stack`, which validates that `read:stack` is in the token's permission list but never validates *which* stack the token is scoped to: [4](#0-3) 

This is the same trust-binding failure pattern as the report's frontrunning bug: a credential (the permit / the CCMenu token) is verified for its class of authorization (owner of funds / `read:stack` permission) but never checked against the specific object it was actually minted for (the specific permit's owner / the specific stack it was issued for).

### Impact Explanation
Anyone in possession of one CCMenu token (these URLs are designed to be pasted into third-party CI dashboard widgets, browser extensions, status boards, etc., i.e., environments with weaker confidentiality guarantees than the main Shipit UI) can substitute any other `stack_id` in the URL and read build/deploy status (`lastBuildStatus`, `activity`, `lastBuildLabel`, `webUrl`) for every stack in the Shipit instance, not just the one the token was generated for. This is an authorization-boundary break where a token's authorized scope (single stack) diverges from the stack it can actually touch (all stacks), matching the "unauthenticated/unauthorized read of stack state" High-impact category.

### Likelihood Explanation
Exploitation requires only a single, previously issued CCMenu token (obtainable from any dashboard/widget where such tokens are commonly embedded) and knowledge or guessing of another stack's `to_param` (owner/repo/environment/branch), which is generally not secret. No privileged Shipit session, `webhook_secret`, or GitHub App key is needed — only a leaked/legitimate CCMenu token.

### Recommendation
In `Api::CCMenuController`, resolve the stack the same way `Api::BaseController#stack` does — via the `stacks` helper scoped to `current_api_client.stack_id` — rather than an unscoped `Stack.from_param!`. Additionally, `CCMenuUrlController#client` should create/find a distinct `ApiClient` per `(creator, stack)` pair (include `stack:` in both the `create_with` attributes and the `find_or_create_by!` lookup key) so each token is durably bound to exactly one stack.

### Proof of Concept
1. User A visits a stack's page and Shipit generates a CCMenu URL, e.g. `GET /api/owner/repo/staging/ccmenu?token=<T>`, backed by an `ApiClient` with `permissions: ["read:stack"]` and no stack restriction enforced by the controller.
2. An attacker who obtains `<T>` (e.g., scraped from a public CI dashboard where such feeds are commonly embedded) sends `GET /api/other-owner/other-repo/production/ccmenu?token=<T>`.
3. `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly, ignoring the token's intended scope, so the request succeeds and returns build status for `other-owner/other-repo/production`, a stack the token was never authorized for. [5](#0-4)
