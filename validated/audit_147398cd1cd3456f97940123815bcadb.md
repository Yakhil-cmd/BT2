### Title
Duplicate members in `r of set` / `weighted and` address definitions allow a single keyholder to satisfy a multi-party signing threshold - (File: definition.js)

### Summary
The external report describes a bug class where an entity can be inserted into a list multiple times because no de-duplication check exists, letting that single entity be credited multiple times by downstream logic that assumes each list entry represents a distinct party. The analogous pattern exists in ocore's address-definition validator: the `r of set` and `weighted and` operators accept a `set` array of sub-expressions/members without any uniqueness check, so the same signer (same `sig`/`address` sub-expression) can be listed more than once in the set.

### Finding Description
`validateDefinition()` in `definition.js` validates the `r of set` operator by only checking array length and that `required <= args.set.length`, with no check that the elements of `set` are distinct: [1](#0-0) 

The same absence of a uniqueness check applies to `weighted and`: [2](#0-1) 

At authentication time, `validateAuthentifiers()` evaluates each `set` member independently at its own signing path (`path+'.'+index`) and simply counts how many members produced a valid signature, requiring `count >= args.required`: [3](#0-2) 

If the definition author places the same `["sig", {pubkey}]` (or `["address", X]`) sub-expression at two different indices of the `set`, the holder of that single key can independently produce two valid signatures (one for each index/path) and thereby satisfy two "slots" of the `required` count — using only one real signer. This is directly analogous to the reported bug: a missing uniqueness/duplicate check on a list whose members are assumed to represent distinct entities (users/dividend recipients in the original report; independent cosigners here), letting one entity count multiple times toward an outcome that should depend on multiple distinct participants (dividend payout count vs. multisig signature threshold count).

By contrast, the codebase does enforce strict uniqueness for a similarly-shaped list elsewhere (asset attestor lists), showing the missing check for `r of set`/`weighted and` is an inconsistency rather than an intentional relaxation: [4](#0-3) 

### Impact Explanation
Shared/multisig addresses created via `wallet_defined_by_addresses.js`/`wallet_defined_by_keys.js` build their definitions from `r of set` templates (e.g., `createMultisigWallet`): [5](#0-4) 

If any single member of that set (e.g., a malicious or unreliable cosigner who controls how the definition/template is composed, or a hosting party that reuses the same underlying key/address entry twice while presenting the wallet as an "M-of-N with N distinct signers") ends up listed twice in `args.set`, that party alone can satisfy the `required` threshold and spend funds from the address without cooperation of the other intended cosigners. This is unauthorized spending from what other parties believe is a genuine multi-party-controlled address — the exact “duplicate entry credited multiple times” bug class from the report, mapped onto ocore's address-authentication engine instead of a dividends ledger.

### Likelihood Explanation
Address definitions (including `r of set`/`weighted and`) are fully user-authored and validated purely by `definition.js`/`validation.js` logic with no server-side or protocol-level requirement that set members be distinct; any unit poster or address-definer can construct such a definition, and it will pass `validateDefinition` unchanged. The exploit only requires that at address-creation time the duplicate entry goes unnoticed by the other intended cosigners (e.g., embedded in a definition template shared during shared-wallet setup).

### Recommendation
Add an explicit uniqueness check for the members of `set` in both `r of set` and `weighted and` (e.g., compare canonical hash/serialization of each `args.set[i]` sub-expression, similar to the sorted/uniqueness enforcement already done for `checkAttestorList`), rejecting definitions where two or more set members are structurally identical.

### Proof of Concept
1. Generate a single keypair and its `sig` definition: `innerDefinition = ["sig", {pubkey}]`.
2. Construct `arrDefinition = ["r of set", {required: 2, set: [innerDefinition, innerDefinition, ["sig", {pubkey: otherPubkey}]]}]` — presented to cosigners as a 2-of-3 wallet.
3. `validateDefinition` accepts this definition (no duplicate check), and the resulting address is created/shared as a "2-of-3" wallet.
4. The holder of `pubkey` signs the same unit twice, once at path `r.0` and once at path `r.1`, satisfying `count >= args.required` in `validateAuthentifiers` without any input from the third (`otherPubkey`) cosigner, spending funds unilaterally.
