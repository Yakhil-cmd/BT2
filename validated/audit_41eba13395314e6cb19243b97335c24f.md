### Title
Global unscoped `Commit.where(sha:)` lookup lets one status webhook mutate every stack sharing that sha - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by `sha` alone with no repository/stack scoping, unlike every other handler (`PushHandler`, the `PullRequest::*Handler`s) which all filter through `stacks`/`Repository.from_github_repo_name`. Since `sha` is only unique per `(stack_id, sha)` pair (not globally), a single verified status webhook whose `sha` happens to collide with commits in unrelated stacks will write a forged `Status` to all of them.

### Finding Description
The broken binding is: **one verified webhook payload for repository R == a mutation of exactly the Commit rows belonging to R's stack(s)**. Instead, the actual code enforces: **one verified payload for repository R == a mutation of every Commit row across every stack whose `sha` matches params.sha**, because: [1](#0-0) 

calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no join/filter against `repository` or `stacks`. Contrast with `PushHandler`, which correctly scopes through `stacks.not_archived.where(branch:)` [2](#0-1)  and the base `Handler#stacks` helper which resolves the repository from the payload before ever touching records [3](#0-2) . `StatusHandler` never calls `stacks` or checks `repository_name` at all.

The DB schema confirms `sha` is unique only per `(sha, stack_id)`, not globally: [4](#0-3) . So multiple `Commit` rows across different stacks legitimately can, and by design are expected to, share the same `sha` (e.g., a shared library commit merged/cherry-picked into multiple stacks, or two repos that happen to produce an identical commit hash such as templated "initial commit" content with identical tree/author/committer/timestamp).

`create_status_from_github!` then creates a `Status` row scoped to `commit.stack_id` (the *victim's* stack, not the attacker's) and fires `enable_ci_on_stack`, `schedule_continuous_delivery`, and deployable-status webhooks on that unrelated stack: [5](#0-4)  and [6](#0-5) .

Existing guards do not prevent this: `verify_signature` only checks that the payload was signed by the correct GitHub organization's webhook secret [7](#0-6)  and [8](#0-7)  — it authenticates *which org sent the webhook*, not *which repository/stack the sha belongs to*. Nothing in `ExplicitParameters` schema, `drop_unhandled_event`, or the handler itself cross-checks `params.repository.full_name`/`repository_owner` against the stack(s) that own the matched `Commit` rows before mutating them.

### Impact Explanation
A single valid status event (from a repository the attacker legitimately controls/triggers, e.g. their own repo or fork under the same GitHub App installation) causes `create_status_from_github!` to run against every `Commit` row in the database that shares that `sha`, regardless of which stack/repository owns it. This can flip a commit's state to `success`, which enables `enable_ci_on_stack` and schedules `ProcessMergeRequestsJob`/continuous delivery on a stack the attacker never touched — i.e., a payload for one repository mutates another repository's `Commit`/`Status` records and can influence that stack's auto-merge/deploy pipeline. This matches the "payload for one repository mutating another's stack/commit" Critical category. Blast radius is every stack that happens to contain a `Commit` row with the colliding sha, not just two — it is a live SQL query with no `LIMIT` or scope, so it fans out to all matches in a single request.

### Likelihood Explanation
The attacker needs: (1) the ability to trigger a genuine, signed status webhook (achievable if they control a repository within an org/installation whose GitHub App webhook secret Shipit trusts, per the stated attacker capabilities), and (2) a `sha` collision between their own commit and one or more `Commit` rows already persisted in other stacks' history. True cryptographic SHA-1 collision is infeasible, but the described vector (empty/templated commits with identical tree, author, committer and timestamp producing identical commit hashes across unrelated repositories) is a documented, non-cryptographic collision path and requires no secret material — only crafting a commit with a specific, reproducible content/timestamp. This is a real but narrower precondition than a fully generic collision; feasibility depends on such a match existing/being creatable, which is plausible but was not experimentally verified here.

### Recommendation
Scope the lookup by repository, mirroring the other handlers: resolve `stacks` from `params.repository.full_name` (via the existing `Handler#stacks`/`Repository.from_github_repo_name` helper) and constrain the commit query, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each { ... }`, so a status payload can only ever mutate commits belonging to the stacks tied to the repository that emitted the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not leak status to commits in unrelated stacks sharing the same sha" do
  colliding_sha = "a" * 40

  stack_a = shipit_stacks(:shipit)
  stack_b = create_stack(repository: create_repository(name: "unrelated-repo"))

  commit_a = stack_a.commits.create!(sha: colliding_sha, message: "m", author: shipit_users(:walrus),
                                      committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  commit_b = stack_b.commits.create!(sha: colliding_sha, message: "m", author: shipit_users(:walrus),
                                      committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  params = { sha: colliding_sha, state: "success", context: "ci", branches: [], repository: { full_name: stack_a.repository.github_repo_name } }

  assert_difference -> { commit_a.statuses.count }, 1 do
    assert_no_difference -> { commit_b.statuses.count } do
      Shipit::Webhooks::Handlers::StatusHandler.call(params.stringify_keys.deep_stringify_keys)
    end
  end
end
```
Before the fix this test fails because `commit_b.statuses.count` also increments by 1 (cross-stack write); after scoping the query by `stacks`/repository it passes.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
