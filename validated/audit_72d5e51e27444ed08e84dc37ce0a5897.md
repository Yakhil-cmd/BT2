### Title
Session fixation via missing `reset_session` in OAuth callback - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` authenticates the user and writes `session[:user_id]`/`session[:authenticated]` into the existing session without first calling `reset_session`, so a pre-existing (attacker-known) session id is preserved and elevated to an authenticated identity. This is a textbook session-fixation flaw.

### Finding Description
Broken binding: `session_id_before_login == session_id_after_login` should be false (the session identifier must be rotated on privilege change), but in this code it is true, because no `reset_session` (which in Rails discards the old session id and issues a new one) is invoked in `#callback` [2](#0-1) .

Path: an attacker who can plant/observe a session cookie value in the victim's browser (e.g. via a subdomain-scoped cookie under the same registrable domain, since Rails' default `ActionDispatch::Session::CookieStore`/`ActiveRecord::SessionStore` session cookies are typically scoped by domain, not path, and Shipit does not set `session[:_csrf_token]` rotation or session-id regeneration anywhere else that could intervene) causes the victim's browser to carry that known session id into `/github/callback`. When the victim completes GitHub OAuth, `sign_in_github(auth)` resolves/creates the `User` and `#callback` stores `user.id` into `session[:user_id]` of that same session object [4](#0-3) . The attacker, already holding that session id, can now present it to Shipit and be treated as the victim by `current_user`/`find_current_user`, which simply looks up `User.find_by(id: session[:user_id])` [5](#0-4) .

The only place `reset_session` is called is in `#logout` [3](#0-2) , and in `force_github_authentication` — but only for the "requires fresh login" branch of an *already logged-in* user, not for the initial anonymous→authenticated transition performed by `#callback` [1](#0-0) . None of `force_github_authentication`, `User#authorized?`, or the `stacks` scope mitigates this, because they operate after the session is already trusted as belonging to the victim; the compromise happens at the moment of session-id reuse, not at the authorization check.

### Impact Explanation
Once the fixation succeeds, the attacker's browser (holding the same session id) is granted the victim's authenticated Shipit session, including whatever teams/permissions the victim has under `Shipit.github_teams`. This lets the attacker trigger deploys, rollbacks, or other stack mutations as the victim — an authentication bypass / session takeover, matching the "High: session fixation / forced OAuth completion" category (and potentially Critical impact depending on the victim's role, since it enables unauthorized deploys/rollbacks). It is repeatable against any victim whose session cookie the attacker can prime before the victim authenticates.

### Likelihood Explanation
Requires the attacker to be able to set or predict a session cookie value in the victim's browser prior to the victim visiting `/github/callback` — feasible via a subdomain cookie-planting vector (if Shipit or a co-hosted app shares a parent domain) or by sending the victim a link/cookie that pre-seeds the session store entry (e.g., via `Set-Cookie` on an unauthenticated Shipit response reusing a session id the attacker already visited with). No Shipit secrets, GitHub credentials, or privileged role are needed by the attacker; the only requirement is the ability to get a known session id into the victim's cookie jar and then have the victim complete a normal GitHub login. This is a standard, well-understood attack class for apps that don't rotate session ids on login.

### Recommendation
Call `reset_session` at the start of `#callback` before writing `session[:user_id]`/`session[:authenticated]`, preserving `omniauth.origin` (which is read from `request.env`, not `session`) across the reset:

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

### Proof of Concept
Minitest integration test (`ActionDispatch::IntegrationTest`) under `test/controllers/github_authentication_controller_test.rb` (not shown here since it's out of scope to author, but the plan is):
1. Perform a request to any Shipit page to establish an initial (anonymous) session and capture `pre_id = request.session.id`.
2. Stub `request.env['omniauth.auth']` (via OmniAuth test mode) and `User.find_or_create_from_github` to simulate a successful GitHub login, then `get '/github/callback'` using the same cookie jar.
3. Assert `assigns` or a subsequent request shows `session[:user_id]` set to the authenticated user's id, and assert `request.session.id != pre_id` — which currently **fails** (they are equal), proving no rotation occurs.
