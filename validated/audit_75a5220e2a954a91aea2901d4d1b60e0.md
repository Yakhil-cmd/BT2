### Title
Explicit `conditions:` hookify rules can silently no-op due to unvalidated `field` names, while equivalent legacy `pattern:` rules reliably block - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Condition.from_dict` accepts any attacker-supplied `field`/`operator`/`pattern` string with no validation against the set of fields `rule_engine.py` actually knows how to resolve, whereas the legacy `pattern:` path in `Rule.from_dict` always derives a field name known to be resolvable from the `event` type. A hookify rule expressed with an explicit `conditions:` list (e.g. from `/hookify` generation or a repo-shipped `.claude/hookify.*.local.md` file) can therefore declare `action: block` with a convincing security message while using a `field` value that `RuleEngine._extract_field` can never resolve, causing the "block" rule to silently never match.

### Finding Description
`Rule.from_dict` has two ways to populate `conditions`:
- Legacy: `simple_pattern = frontmatter.get('pattern')` with the field auto-derived from `event` (`command`/`new_text`/`content`) — [1](#0-0) , guaranteed to be one of the field names `RuleEngine._extract_field` understands.
- Explicit: `conditions = [Condition.from_dict(c) for c in cond_list]` — [2](#0-1) , where `Condition.from_dict` performs zero validation of `field`, `operator`, or `pattern` values: [3](#0-2) .

In `RuleEngine._check_condition`, if the resolved field value is `None` the condition — and therefore, via the AND-only semantics of `_rule_matches` — the whole rule silently fails to match: [4](#0-3)  and [5](#0-4) . `_extract_field` only resolves a hardcoded, narrow set of field names per tool type (`command` for Bash; `content`/`new_text`/`old_text`/`file_path` for Write/Edit; a few for MultiEdit) and returns `None` for anything else: [6](#0-5) . There is no logging, warning, or exception when a `field` is unrecognized — it fails open (i.e., the block rule simply never fires) with no observable signal to the user.

Because a hookify rule file's frontmatter can be produced by `/hookify` generation (LLM-authored, and thus influenceable by prompt-injectable repo content the model is summarizing/acting on) or shipped directly as a repo file loaded by `load_rules()`/`load_rule_file()` ( [7](#0-6) ), an attacker who can influence that frontmatter can plant a `conditions:`-based rule that looks like a legitimate `action: block` protection (e.g. "blocks dangerous rm -rf commands") but references a field name that is never populated for the targeted tool/event (e.g. `field: file_content` instead of `content`, or a Write-only field name used on a `bash` event). The equivalent rule expressed with legacy `pattern:` syntax for the same event would have worked correctly, since the field is auto-derived and always valid. This is exactly the "legacy vs explicit divergence" the question describes: the same intended policy, expressed in the two supported rule forms, produces different effective enforcement — one blocks, the other is a permanent no-op — with no error surfaced to the user who believes protection is active.

### Impact Explanation
A user (or an automated `/hookify` flow) who believes a `block` rule is protecting a workspace against a dangerous operation (e.g. destructive file writes, `rm -rf`, reading secrets) can be silently unprotected if the rule was authored/generated using the explicit `conditions:` form with a subtly wrong `field` value. Any subsequent tool call matching the *intended* dangerous pattern proceeds without being blocked, since `RuleEngine.evaluate_rules` returns `{}` (allow) for a rule whose condition field never resolves. This can lead to unauthorized file read/write outside the user-approved scope, since the safety net the user relied on is not actually enforced — matching the "Unauthorized file read or write outside the user-approved workspace or target scope" impact category.

### Likelihood Explanation
Feasibility depends on the attacker's ability to get a broken-but-convincing `conditions:`-style rule into `.claude/hookify.*.local.md` (via a repo-shipped file, or by influencing what `/hookify` generates from untrusted repo content/instructions). This is realistic in supply-chain-style scenarios (malicious/compromised repo ships a hookify rule file, or a PR description/comment used as generation input for `/hookify`). No admin privileges are required — only the ability to place or influence content that becomes an in-repo rule file, which is within the stated "repo-shipped rule file" and "/hookify generation" attacker-control assumptions. The bug is deterministic and 100% repeatable once such a rule file exists: the condition will never resolve for the mismatched field.

### Recommendation
- Validate `field` (and `operator`) in `Condition.from_dict` against an explicit allowlist of known-resolvable field names per event/tool combination; reject or fail loudly (raise/log a hard error, not silently continue) on unknown fields rather than allowing `_extract_field` to silently return `None`.
- Make `_check_condition`/`_rule_matches` treat an unresolved field for a `block`-action rule as a configuration error surfaced to the user (e.g., print a stderr warning at load time in `load_rule_file`), rather than a silent pass.
- Add a `load_rules()`-time self-test/dry-run that verifies each `block` rule's conditions can resolve a non-`None` field for at least one plausible tool_input shape matching its `event`, so misconfigured "security theater" rules are caught at load time.

### Proof of Concept
Unit test to add to a hookify test suite:

```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

def test_legacy_vs_explicit_block_rule_divergence():
    engine = RuleEngine()

    # Legacy form: pattern auto-maps to a resolvable field ("command") for event=bash
    legacy_rule = Rule.from_dict({
        "name": "block-rm-rf-legacy",
        "enabled": True,
        "event": "bash",
        "pattern": r"rm\s+-rf",
        "action": "block",
    }, "Blocked dangerous rm -rf")

    # Explicit form: attacker/LLM-authored rule with a field name that never resolves
    # for Bash tool_input (only "command" is resolvable per _extract_field).
    explicit_rule = Rule.from_dict({
        "name": "block-rm-rf-explicit",
        "enabled": True,
        "event": "bash",
        "action": "block",
        "conditions": [
            {"field": "file_content", "operator": "regex_match", "pattern": r"rm\s+-rf"}
        ],
    }, "Blocked dangerous rm -rf")

    tool_input = {"tool_name": "Bash", "tool_input": {"command": "rm -rf /"}}

    legacy_result = engine.evaluate_rules([legacy_rule], tool_input)
    explicit_result = engine.evaluate_rules([explicit_rule], tool_input)

    # Legacy correctly blocks
    assert legacy_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

    # Explicit "block" rule silently fails to block the same dangerous command
    assert explicit_result == {}  # demonstrates the security-semantics divergence
```

Expected result: `legacy_result` denies the operation while `explicit_result` is empty (allows it), demonstrating that two rule forms intended to express the same block policy produce different effective enforcement, confirming the invariant violation.

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules


def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None
    except UnicodeDecodeError as e:
        print(f"Error: Invalid encoding in {file_path}: {e}", file=sys.stderr)
        return None
    except Exception as e:
        print(f"Error: Unexpected error parsing {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
        return None

    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields
            if field == 'reason':
                return input_data.get('reason', '')
            elif field == 'transcript':
                # Read transcript file if path provided
                transcript_path = input_data.get('transcript_path')
                if transcript_path:
                    try:
                        with open(transcript_path, 'r') as f:
                            return f.read()
                    except FileNotFoundError:
                        print(f"Warning: Transcript file not found: {transcript_path}", file=sys.stderr)
                        return ''
                    except PermissionError:
                        print(f"Warning: Permission denied reading transcript: {transcript_path}", file=sys.stderr)
                        return ''
                    except (IOError, OSError) as e:
                        print(f"Warning: Error reading transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')

        # Handle special cases by tool type
        if tool_name == 'Bash':
            if field == 'command':
                return tool_input.get('command', '')

        elif tool_name in ['Write', 'Edit']:
            if field == 'content':
                # Write uses 'content', Edit has 'new_string'
                return tool_input.get('content') or tool_input.get('new_string', '')
            elif field == 'new_text' or field == 'new_string':
                return tool_input.get('new_string', '')
            elif field == 'old_text' or field == 'old_string':
                return tool_input.get('old_string', '')
            elif field == 'file_path':
                return tool_input.get('file_path', '')

        elif tool_name == 'MultiEdit':
            if field == 'file_path':
                return tool_input.get('file_path', '')
            elif field in ['new_text', 'content']:
                # Concatenate all edits
                edits = tool_input.get('edits', [])
                return ' '.join(e.get('new_string', '') for e in edits)

        return None
