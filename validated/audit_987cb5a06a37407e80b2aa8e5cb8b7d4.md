### Title
Webhook signature verification is keyed on an attacker-controlled `repository.owner.login` field that is independent of the field(s) actually used to select the data written, allowing forged CI status / sync events for stacks belonging to a different GitHub organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret) used to authenticate an inbound webhook based on the JSON field `repository.owner.login` (or `organization.login`) taken straight from the unauthenticated request body [1](#0-0) . The actual data-mutating handlers never re-check that field: `Handler#repository_name` resolves the target repository from a *different*, equally attacker-controlled field, `repository.full_name` [2](#0-1) , and `StatusHandler` does not scope by repository at all - it matches globally on `Commit.where(sha: params.sha)` [3](#0-2) . Because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured [4](#0-3) , and this is a documented, supported configuration (multiple orgs, some without a webhook secret) [5](#0-4) , an attacker can pick any weakly-configured org's name for the auth-selection field while pointing the actual write at a completely unrelated, sensitive repository/stack.

### Finding Description
The equality that should hold is: `organization whose secret authenticated the request == organization that owns the repository/commit being written`. This binding is broken:

1. `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)` to check `X-Hub-Signature` [1](#0-0) [6](#0-5) .
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` if that organization has no `webhook_secret` set: `return true unless webhook_secret` [7](#0-6) . Multiple-org deployments with a mix of secured/unsecured orgs are explicitly documented and shown in fixtures/config examples (`webhook_secret: # nil`) [8](#0-7) [9](#0-8) .
3. After the request is treated as "verified" this way, `Shipit::Webhooks.for_event(event)` dispatches handlers that operate on payload fields that were never covered by any real signature check tied to the org used in step 1:
   - `PushHandler`/other handlers resolve the target repository via `payload.dig('repository','full_name')` [10](#0-9) , then trigger `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on that branch [11](#0-10) .
   - `StatusHandler` does not check repository ownership at all; it matches any `Commit` row in the entire installation by `sha` and calls `commit.create_status_from_github!(params)`, letting the attacker set arbitrary `state`/`context`/`description` for that commit [3](#0-2) .

An unprivileged, unauthenticated attacker (no Shipit session, no `ApiClient` token, no GitHub App key) can therefore:
- Send a POST to `/webhooks` with header `X-Github-Event: status`.
- Set the body's `repository.owner.login` to any GitHub organization configured on the instance that has `webhook_secret` unset (satisfying `verify_signature` trivially, regardless of the actual `X-Hub-Signature` header value).
- Set `sha` to the real HEAD commit SHA of an entirely different, target repository/stack (public information on GitHub), `state: "success"`, and `context` matching a check name required by that stack's `ci.require` in `shipit.yml`.

This forges a passing CI status for a commit belonging to a repository/organization that was never authenticated by the actual signature check.

### Impact Explanation
CI status checks gated by `ci.require` in `shipit.yml` are used by Shipit to decide whether a commit is safe/deployable. Forging a successful status for an arbitrary commit lets an unauthorized external actor satisfy that gate for a target stack, contributing to an unauthorized deploy of an unreviewed or unintended commit - this matches the Critical impact category "unauthorized deploy" defined in scope. It also demonstrates a broken authentication/authorization binding: the credential (webhook secret) that "authenticated" the request belongs to an organization completely disjoint from the repository/commit actually mutated, which is exactly the "organization authenticated vs. repository written" trust boundary called out in the rules.

### Likelihood Explanation
Likelihood depends on the deployment having at least one configured GitHub organization without a `webhook_secret` while another organization/stack in the same instance is the intended target - a configuration explicitly presented as valid in `docs/setup.md`'s multi-org example and in the shipped dev/test secrets fixtures. No repository write access, no session, no API token, and no knowledge of any real webhook secret is required; only knowledge of a valid target commit SHA (public on GitHub) and one org name lacking a webhook secret.

### Recommendation
- Do not let `verify_signature`'s organization selection be fully independent from the data the handlers subsequently act upon; derive both from the same verified field, or explicitly bind the verified organization to the resolved `Repository`/`Stack` before dispatching to handlers.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; require an explicit "insecure/legacy" opt-in per organization, and reject requests when the signature can't be cryptographically checked.
- Scope `StatusHandler` (and any other handler) lookups by the repository resolved from the same authenticated organization, not merely by global `sha`, i.e. join through `Repository`/`Stack` rather than `Commit.where(sha: ...)` unscoped.

### Proof of Concept
Given a Shipit instance configured with two GitHub orgs, `weak-org` (no `webhook_secret`) and `victim-org` (has stacks with `ci.require: ["ci/checks"]`), an attacker who knows a real commit SHA `abc123` on a `victim-org` stack can send:

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything-invalid

{
  "repository": { "owner": { "login": "weak-org" }, "full_name": "weak-org/some-repo" },
  "sha": "abc123",
  "state": "success",
  "context": "ci/checks",
  "target_url": "https://attacker.example/fake",
  "created_at": "2026-09-01T00:00:00Z"
}
```

`verify_signature` looks up `Shipit.github(organization: "weak-org")`, finds no `webhook_secret`, and returns `true` regardless of the bogus `X-Hub-Signature` [7](#0-6) . `StatusHandler#process` then matches `Commit.where(sha: "abc123")` — a commit that actually belongs to `victim-org` — and creates a fabricated successful `ci/checks` status on it [3](#0-2) , satisfying `victim-org`'s CI gating despite the request never being validated against `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
