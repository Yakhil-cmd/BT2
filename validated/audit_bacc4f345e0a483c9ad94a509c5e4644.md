### Title
Pre-Randao Block Proposer Can Bias PRNG Seed to Skew Proposer-List Slot Allocation and KAIA Reward Distribution — (`kaiax/valset/impl/getter_proposers.go`, `kaiax/valset/impl/getter_context.go`)

---

### Summary

In the pre-Randao code paths (`WeightedRandom` before the Randao hardfork, and `RoundRobin`/`Sticky` at all times), the PRNG seed used to shuffle the proposer list and the committee is derived directly from the block hash of a block the attacker proposes. Because the Istanbul `HeaderHash` (the canonical block hash used by the chain) excludes committed seals but includes the proposer's own seal, the proposer knows the final hash of their block before it is committed. By varying transaction selection and ordering, the proposer can search for a block hash whose first 60 bits produce a PRNG shuffle that over-represents them in the next interval's proposer list, directly inflating their share of KAIA block rewards.

---

### Finding Description

**Root cause — `generateProposerListWeighted` / `generateProposerListUniform`**

Every `ProposerUpdateInterval` blocks, `calcBaseProposers` is called to generate the proposer schedule for the next interval. The PRNG seed is derived from the hash of the "proposer update block":

```go
// kaiax/valset/impl/getter_proposers.go:56-62
if v.Chain.Config().Rules(...).IsKore {
    list = generateProposerListUniform(qualified, updateHeader.Hash())
} else {
    list = generateProposerListWeighted(qualified, si, useGini, updateHeader.Hash())
}
```

Both functions extract the seed as the first 60 bits of the block hash:

```go
// kaiax/valset/address_set.go:218-221
func HashToSeedLegacy(hash common.Hash) int64 {
    n8 := binary.BigEndian.Uint64(hash[:8])
    return int64(n8 >> 4)
}
```

The seed is then fed into a linear congruential PRNG to shuffle the proposer list:

```go
// kaiax/valset/address_set.go:186-198
func (as *AddressSet) ShuffledListLegacy(seed int64) []common.Address {
    r := rand.New(rand.NewSource(seed))
    for i := range shuffled {
        j := r.Intn(len(shuffled))
        shuffled[i], shuffled[j] = shuffled[j], shuffled[i]
    }
    return shuffled
}
```

**The proposer controls the block hash.** The Istanbul `HeaderHash` — which is what `Header.Hash()` resolves to via `HeaderHashFn` — is the RLP hash of the header *with* the proposer seal but *without* committed seals:

```go
// consensus/istanbul/sealer.go:290-295
func (m *IstanbulSealer) HeaderHash(header *types.Header) common.Hash {
    if filtered := istanbulFilteredHeader(header, true); filtered != nil {
        return RLPHash(filtered)
    }
    return RLPHash(header)
}
```

The proposer creates their own seal, so they know the exact final `HeaderHash` before the block is committed. By varying the set and ordering of transactions included in the block (which changes `TxHash`, `GasUsed`, `Root`, `ReceiptHash`, `Bloom`), the proposer can generate a large search space of valid block hashes and select the one whose first 60 bits produce the most favorable PRNG shuffle — i.e., the shuffle that places them in the most proposer slots for the next `ProposerUpdateInterval` blocks.

**Same root cause in `selectRandomCommittee`**

The committee for block N is seeded from `prevBlockHash` = `c.prevHeader.Hash()`:

```go
// kaiax/valset/impl/getter_context.go:112
return selectRandomCommittee(c.qualified, c.pset.CommitteeSize, c.prevHeader.Hash(), currProposer, nextDistinctProposer), nil
```

```go
// kaiax/valset/impl/getter_context.go:153
seed := valset.HashToSeedLegacy(prevBlockHash)
shuffled := qualified.ShuffledListLegacy(seed)
```

The proposer of block N-1 can similarly bias which validators appear in the committee for block N.

---

### Impact Explanation

The proposer of the "proposer update block" (a block at a multiple of `ProposerUpdateInterval`) can search over valid transaction sets to find a block hash that over-represents their address in the shuffled proposer list for the next interval. Each extra slot in the proposer list translates directly to an additional block reward (KAIA minting + transaction fees) that the attacker receives at the expense of other validators. The bias is bounded by the search space the proposer can explore within the block time, but even a modest increase in slot frequency compounds over many intervals.

The corrupted value is the `proposerList` array returned by `generateProposerListWeighted` / `generateProposerListUniform`, which determines the sequence of block proposers — and thus the sequence of KAIA block reward recipients — for the entire next interval.

---

### Likelihood Explanation

- The attacker must be the scheduled proposer of a "proposer update block" (every `ProposerUpdateInterval` blocks, typically 3600 on mainnet). This is a semi-trusted role reachable by any registered validator.
- The attack requires no collusion with other validators.
- The proposer can vary transaction inclusion/ordering offline before broadcasting, making the search computationally cheap.
- The attack is indistinguishable from normal block production; there is no on-chain evidence.
- This path is active for all networks that have not yet activated the Randao hardfork (`IsRandao == false`), and for `RoundRobin`/`Sticky` policies at all hardfork levels.

---

### Recommendation

**Short term:** Document that the pre-Randao proposer list and committee selection carry a block-hash-grinding trust assumption. Warn integrators and network operators that validators proposing "update blocks" have a statistical advantage.

**Long term:** The Randao hardfork (`SelectRandaoCommittee` / `SelectRandaoProposer`) already eliminates this attack by replacing the block-hash seed with a BLS-signature-based RANDAO `MixHash` that is uniquely determined by the proposer's BLS key and the block number — the proposer cannot search over it. Ensure all production networks activate the Randao hardfork. Consider deprecating or gating the `SelectRandomCommittee` and `generateProposerListWeighted`/`generateProposerListUniform` code paths behind a strict pre-fork guard so they cannot be reached on post-Randao chains.

---

### Proof of Concept

1. Attacker is validator `V` and knows they are the proposer of block `U` (a proposer update block, `U % ProposerUpdateInterval == 0`).

2. Before proposing, `V` builds a set of candidate blocks `{B_1, B_2, ..., B_k}` each containing a different valid subset/ordering of mempool transactions.

3. For each candidate `B_i`, `V` computes `HeaderHash(B_i)` (deterministic, since `V` knows their own proposer seal) and then simulates `generateProposerListUniform(qualified, HeaderHash(B_i))` locally.

4. `V` selects the candidate `B_j` whose resulting proposer list maximises `V`'s slot count for the next `ProposerUpdateInterval` blocks.

5. `V` proposes `B_j`. The committee signs it. The canonical proposer list for the next interval is now biased in `V`'s favour.

6. Over the next interval, `V` is selected as proposer more frequently than their fair share, collecting the corresponding KAIA block rewards (minting + fees) that would otherwise have gone to other validators.

func selectRandomCommittee(qualified *valset.AddressSet, committeeSize uint64, prevBlockHash common.Hash, currProposer, nextDistinctProposer common.Address) []common.Address {
	qualified = qualified.Copy()
	qualified.Remove(currProposer)
	qualified.Remove(nextDistinctProposer)

	seed := valset.HashToSeedLegacy(prevBlockHash)
	shuffled := qualified.ShuffledListLegacy(seed)
	committee := []common.Address{currProposer, nextDistinctProposer}
	committee = append(committee, shuffled[:committeeSize-2]...)
	return committee
}
