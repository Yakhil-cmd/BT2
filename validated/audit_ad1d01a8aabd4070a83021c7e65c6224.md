### Title
Webhook signature bypass when `webhook_secret` is unset lets an unauthenticated attacker forge `membership` events and self-escalate into `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the organization derived from the inbound payload. Because `webhook_secret` is documented and treated as optional, an attacker who knows (or guesses) a configured GitHub organization name can send a completely unauthenticated, unsigned `membership` webhook to `/webhooks` and have `Shipit::Webhooks::Handlers::MembershipHandler` add an arbitrary GitHub login as a member of any `Shipit::Team`, including a team listed in `Shipit.github_teams`, which is exactly the authorization gate used by `Shipit::Authentication#force_github_authentication`.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration to verify against purely from the untrusted payload: [1](#0-0) 

and [2](#0-1) 

The verification itself is: [3](#0-2) 

Note `return true unless webhook_secret` — if the organization's `webhook_secret` config value is blank/nil, the signature check is bypassed entirely and *any* payload is accepted, regardless of the `X-Hub-Signature` header value. The setup docs explicitly mark `webhook_secret` as optional: [4](#0-3) [5](#0-4) 

This is structurally the same class of bug as the NftPort report: a trust-critical operation (`signedOnly`) has a code path where the "signature" check silently degrades to no-check, and there is no independent parameter that ties the authenticated organization to the specific privileged action being performed. Here, the "signature" (webhook HMAC) does not actually gate `membership` events when the secret is absent, and the org used to pick the (absent) secret is taken from the same untrusted JSON body that then drives privileged state changes.

Once past `verify_signature`, `WebhooksController#create` dispatches to handlers based solely on the `X-Github-Event` header and JSON body: [6](#0-5) 

The `membership` event handler trusts the body outright: [7](#0-6) 

It creates/looks up a `Team` by the attacker-supplied `team.id`/`organization.login`, creates/looks up a `User` by the attacker-supplied `member.login`, and — for `action == 'added'` — calls `Team#add_member`: [8](#0-7) 

`Shipit.github_teams` is the authorization allow-list checked on every request: [9](#0-8) [10](#0-9) 

and `User#authorized?` simply checks team membership: [11](#0-10) 

So the binding that is supposed to hold is: *"organization whose secret authenticated the webhook" == "organization whose membership/team state is mutated."* When `webhook_secret` is unset for that organization, the left side of that equality is vacuously satisfied (verification always passes), while the right side is fully attacker-controlled from the JSON body — breaking the trust binding described in the rules ("an organization that authenticated versus the repository/organization that is written").

### Impact Explanation
An unauthenticated network attacker can:
1. POST a forged `membership` webhook (`action: 'added'`, arbitrary `member.login`, arbitrary `team` matching one of `Shipit.github_teams`, `organization.login` matching a configured-but-secretless org) to `/webhooks`.
2. `verify_signature` passes because `webhook_secret` is blank for that org.
3. `MembershipHandler` creates a `User` for the attacker's chosen GitHub login and adds it to the required `Team`.
4. If that attacker also controls (or creates) a GitHub account with that login and completes OAuth sign-in via `GithubAuthenticationController#callback`, `User#authorized?` now returns true, granting full authenticated access to Shipit (view/trigger deploys, rollbacks, tasks, environment variables, etc.).

This is a direct escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes.

### Likelihood Explanation
Requires only that some configured GitHub organization in `Shipit.github` secrets omits `webhook_secret` — a state the project's own example configs and setup docs present as normal/optional (`webhook_secret: # nil`). No credentials, tokens, or prior access are needed; the `/webhooks` endpoint is unauthenticated by design (it's meant to be hit by GitHub) and `verify_signature` is the only gate. Any operator who follows the documented "optional" guidance for even one org, in a single- or multi-org deployment, exposes this path.

### Recommendation
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank; instead treat a missing secret as a hard misconfiguration and reject the webhook (or refuse to boot/serve `/webhooks` for that org).
- Independently validate that the `organization.login` used to pick the verification secret in `WebhooksController#repository_owner` matches the organization actually referenced by `team.organization`/`repository.full_name` inside privileged handlers like `MembershipHandler`, `PushHandler`, etc.
- Make `webhook_secret` mandatory in `docs/setup.md` / example secrets files, or fail closed with a clear error if it is absent for any configured organization that has hooks enabled (`Team::REQUIRED_HOOKS`).

### Proof of Concept
1. Configure Shipit with `Shipit.github_teams` including `myorg/deployers`, and configure the `myorg` GitHub App entry with `webhook_secret:` left blank (as shown in `config/secrets.development.example.yml`).
2. As an unauthenticated attacker, send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 999, "name": "deployers", "slug": "deployers", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "myorg" },
  "member": { "login": "attacker-gh-login" }
}
```
No `X-Hub-Signature` header is required — `github_app.verify_webhook_signature(nil, raw_post)` still returns `true` at [12](#0-11)  because `webhook_secret` is blank.
3. `MembershipHandler#process` runs, creating/finding `Team(organization: "myorg", slug: "deployers")` and adding `User(login: "attacker-gh-login")` to it via `Team#add_member`.
4. Attacker signs in through the normal OAuth flow at `/github/auth/github` using a GitHub account with login `attacker-gh-login`; `GithubAuthenticationController#callback` creates/updates the `User` record and sets `session[:user_id]`.
5. `User#authorized?` now returns `true` because the user is a member of the required team, granting full Shipit access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
