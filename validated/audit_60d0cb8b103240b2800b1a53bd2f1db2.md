Nothing restricts who can post a top-level unit containing an `app: "definition"` message — any regular (non-AA) unit author can post one, validated purely by `payload.address === objectHash.getChash160(payload.definition)` [1](#0-0) . This is the root cause that maps to the Lens bug class: an unprivileged actor is able to permissionlessly claim a deterministic identifier (an AA address) that a *different, unrelated future actor* (a factory AA generating a nested/child AA at trigger time) may need to claim exclusively, and the storage layer's "already exists" handling permanently skips/ignores the legitimate claim instead of letting the rightful definer proceed.

### Title
Unprivileged unit poster can pre-claim a deterministic AA address and permanently break definition/funding of a legitimately factory-generated child AA - (File: `storage.js`, `validation.js`)

### Summary
Any regular (non-AA) unit author can post a top-level `app: "definition"` message defining an arbitrary Autonomous Agent whose address is fully attacker-computable in advance (address = `chash160(definition)`), exactly as demonstrated in the built-in test/factory pattern where an AA computes `$child_aa_address = chash160($child_aa)` deterministically before ever posting its own `definition` message [2](#0-1) . Because the `definition` app is validated generically for both AA and non-AA units with no owner/permission check beyond the hash match [1](#0-0) , an unprivileged actor can pre-post the exact same definition from a normal wallet unit before the intended factory-AA response reaches the same address.

### Finding Description
`insertAADefinitions()` in `storage.js` is the single choke point that records an AA's address into `aa_addresses` for both regular (author-posted) and AA-response-posted (`bForAAsOnly`) definitions [3](#0-2) . When the INSERT reports `affectedRows === 0` (i.e., the address already exists) and the call originates from an AA's own response (`bForAAsOnly === true`), the code takes the "ignore" branch unconditionally: `console.log("ignoring repeated definition of AA " + address + " in AA unit " + unit); return cb();` [4](#0-3) . There is no check of *who* defined the address first — a regular non-AA unit author racing ahead of the factory AA is treated identically to a legitimate re-post, and the factory AA's `definition` message is silently dropped from being (re)recorded as originating from that unit.

Because the resulting output/payment message inside the factory AA response still targets the very same deterministic address (`{$child_aa_address}` computed from the same definition array) [5](#0-4) , and `aa_composer.js`'s trigger-handling logic assumes it is defining a brand-new AA at that step (setting `message.payload.address = objectHash.getChash160(message.payload.definition)` when finalizing the message) [6](#0-5) , the previously-squatted address now behaves inconsistently between the case where the factory truly defines it first (its own AA-response gets `mci`/`unit` bookkeeping tied to the factory's trigger) versus the case where a non-AA unit defined it first (bookkeeping, balance-recalculation logic, and `getUnconfirmedAADefinitionsPostedByAAs` lookups keyed on `assocUnstableMessages` for AA-only units never match a plain user-posted `definition` message) [7](#0-6) .

This is architecturally the same bug class as the Lens finding: a broadly-reachable, weakly-gated "claim" operation (`mintHandle` / posting a `definition` message from any unit) operates on the *same identifier namespace* that a privileged/structured migration or factory flow (`batchMigrateProfiles` / nested-AA-definition-in-response) needs exclusive first-claim rights to, and the system's duplicate-handling logic silently no-ops rather than preserving correctness for the rightful claimant.

### Impact Explanation
Any user (no whitelisting needed, unlike the Lens report where only whitelisted profile creators had this power — making the ocore analog *more* exposed) can pre-claim the address of a to-be-created child AA whose definition is deterministic and computable off-chain from a public factory AA's oscript/bytecode (a very common, encouraged pattern in ocore — factory AAs that spin up new sub-AAs, as documented and tested in `aa_composer.test.js`). If the address collides, the intended child AA never gets its own defining unit/mci correctly attributed via the factory's trigger path; balances/funds sent to that address as part of the factory's response can be mis-accounted for (the `aa_balances` recompute logic keyed on `bAlreadyPostedByUnconfirmedAA` is skipped) and dependent application logic that expects `unit[response_unit].messages[[.app='definition']].payload.address` to equal the freshly-created AA (as used by real oscript patterns, e.g. `var['new_aa'] = unit[response_unit].messages[[.app='definition']].payload.address;` [8](#0-7) ) can permanently desynchronize from the intended child AA's actual funded state — a denial-of-service/fund-misattribution against any dApp relying on this AA-factory pattern.

### Likelihood Explanation
Medium-High. No privilege is required at all (lower bar than the Lens finding's "whitelisted creator" requirement). The only prerequisite is that the child-AA definition be deterministic/predictable ahead of the factory trigger, which is the standard and encouraged way to write AA factories in ocore (as shown in the shipped test suite). An attacker just needs to read the factory AA's public oscript source (always public on-chain) and post one ordinary unit with an `app: "definition"` message before the victim's trigger executes.

### Recommendation
Track which specific `unit` (and whether it was posted by a non-AA author vs. by an AA response) first claimed an `aa_addresses` entry, and when a genuine AA-response definition subsequently targets the same address, either (a) reject/bounce the response deterministically instead of silently ignoring it, or (b) require that `insertAADefinitions` distinguish "claimed by a plain unit" vs "claimed by the expected factory flow" and treat the two as non-fungible, surfacing an explicit bounce/error to the factory AA rather than proceeding as if the definition succeeded. At minimum, `getUnconfirmedAADefinitionsPostedByAAs`/`insertAADefinitions`'s ignore-branch in `storage.js` (lines 922-939) should differentiate "same content, legitimately re-posted by the same causal chain" from "pre-claimed by an unrelated non-AA unit," and any downstream oscript reference (`unit[response_unit].messages[[.app='definition']].payload.address`) should reflect the failure so dependent application logic does not silently operate on a squatted/mis-attributed address.

### Proof of Concept
1. Deploy a factory AA identical to the one in `test/aa_composer.test.js` ("AA with generated definition of new AA and immediately sending to this new AA"), whose `init` formula deterministically computes `$child_aa` and `$child_aa_address = chash160($child_aa)` from constants embedded in its own (public) definition [9](#0-8) .
2. Off-chain, any user computes the same `child_aa` array (copy from the public factory definition) and its `chash160`.
3. That user posts an ordinary unit containing `messages: [{ app: "definition", payload: { definition: child_aa } }]` from a normal wallet — this passes validation solely via the `payload.address === chash160(payload.definition)` check [1](#0-0) , with no ownership/authorization constraint tying it to the intended factory.
4. Trigger the factory AA. Its response also emits the identical `app: "definition"` message for the same address; `insertAADefinitions` sees `affectedRows === 0` (already exists) and, since `bForAAsOnly` is true and the previous claim wasn't from an unconfirmed AA-posted definition, logs `"ignoring repeated definition of AA ... in AA unit ..."` and returns without error [4](#0-3) , while the factory nonetheless proceeds to send its payment output to that same address as if the child AA it "created" is the one now receiving funds.
