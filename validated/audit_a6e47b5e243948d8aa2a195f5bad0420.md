### Title
Unbounded UTXO-set iteration when an AA spends a dust-flooded asset balance can freeze AA funds / cause oversized-unit failures - ([File: aa_composer.js])

### Summary
The bug report flags Incentives.sol functions that loop over an unbounded `allTokens` array, risking excessive gas and hitting block gas limits. The closest analog in ocore is the payment-assembly logic used when an Autonomous Agent (AA) sends funds in response to a trigger: `completePaymentPayload`/`iterateUnspentOutputs` in `aa_composer.js` loops over every unspent output row returned for the AA's address/asset, with no cap on the number of rows processed, and the normal per-message input-count limit is explicitly disabled for AA-generated payments.

### Finding Description
When an AA composes an outgoing payment, `completePaymentPayload` calls `readStableOutputs`/`readUnstableOutputsSentByAAs` to fetch all unspent outputs owned by the AA for a given asset, then feeds every row into `iterateUnspentOutputs`, which pushes one input per row until the target amount is reached: [1](#0-0) 

For the base asset, tiny dust outputs are filtered out by an `amount>=FULL_TRANSFER_INPUT_SIZE` clause, but for any custom (non-base) asset there is no minimum-amount filter at all: [2](#0-1) 

Any unprivileged unit poster can pay a custom asset to an AA address split into an arbitrarily large number of minimal-amount outputs (a single payment message can carry many outputs, and this can be repeated across many units/messages, since custom-asset outputs have no per-output minimum). Each of these outputs becomes an unspent row against the AA's address/asset pair.

When the AA later needs to pay out that asset (e.g., returning a user's deposit, or forwarding a balance), `iterateUnspentOutputs` must consume UTXOs one at a time until `total_amount >= target_amount`. If the balance is fragmented into thousands of dust outputs, the resulting `payload.inputs` array grows correspondingly large. Critically, the network-wide limit meant to bound the number of inputs per payment message is bypassed for AA-authored units: [3](#0-2) 

`!objValidationState.bAA` in that condition means `MAX_INPUTS_PER_PAYMENT_MESSAGE` is not enforced when the unit is produced by an AA, so there is no protocol-level backstop against an oversized `inputs` array once `aa_composer.js` has already assembled the payload.

### Impact Explanation
An attacker can dust-flood an AA's balance of a specific asset with many minimal-value outputs at negligible cost (custom assets have no dust filter, unlike the base asset). Later, when the AA's own oscript logic triggers a payment of that asset (e.g., refunding a user, rebalancing, or forwarding proceeds), `completePaymentPayload` is forced to walk through and include a very large number of these dust inputs to reach the required amount. This can:
- produce a unit so large that it fails the general unit-size limits during composition/validation (`objUnit.payload_commission`, oversize-fee/size ceilings), causing the AA response to bounce/fail, effectively freezing the funds the AA is supposed to pay out and denying service to legitimate users of that AA for that asset;
- consume disproportionate database/CPU work on every full node reading and validating the resulting inputs array (SQL query scans, double-spend checks per input in `validatePaymentInputsAndOutputs`), degrading node performance when validating AA responses network-wide.

This matches the "functions may become unexecutable due to a huge array" bug class: instead of a `tokens` array, the unbounded collection here is the AA's own unspent-output set for an asset, and the unbounded loop is in the AA's automatic payment composer, with the normal input-count safety limit explicitly disabled for AAs.

### Likelihood Explanation
Likelihood is moderate-to-high: no special privilege is needed — any address can send a custom asset to an AA in many small increments (bounded only by the sender's own fee budget for creating many outputs/units, which is comparatively cheap per unit versus the damage done to the target AA's future response). AAs that accept arbitrary custom-asset deposits and later pay out based on accumulated balances (a common oscript pattern, e.g. exchanges, pools, vouchers) are directly exposed. The exemption of AA payments from `MAX_INPUTS_PER_PAYMENT_MESSAGE` in `validation.js` line 2137 removes the one existing safety net for this exact scenario.

### Recommendation
- Apply a minimum-amount (dust) filter for custom-asset unspent outputs in `readStableOutputs`/`readUnstableOutputsSentByAAs`, analogous to the existing `FULL_TRANSFER_INPUT_SIZE` floor used for the base asset, so dust-fragmented balances cannot force huge input sets.
- Enforce an explicit cap on the number of inputs `iterateUnspentOutputs` may accumulate for a single AA-composed payment (independent of the `bAA` exemption in `validation.js`), and have the AA composer bounce/fail gracefully (or split into multiple secondary-trigger payments) rather than silently building an oversized `inputs` array.
- Re-evaluate the `!objValidationState.bAA` exemption from `MAX_INPUTS_PER_PAYMENT_MESSAGE` in `validation.js` (line 2137); if AA-authored payments must exceed the human-authored limit, use a distinct, still-finite AA-specific ceiling rather than no ceiling at all.

### Proof of Concept
1. Deploy an AA that accepts deposits of a custom asset and later pays out the accumulated balance to a user on some trigger condition (a common oscript pattern).
2. As an attacker, send that custom asset to the AA's address split across a very large number of separate outputs with minimal per-output amounts (no dust floor applies to non-base assets per `aa_composer.js` line 1149).
3. Trigger the AA's payout logic for that asset. `completePaymentPayload`/`iterateUnspentOutputs` (`aa_composer.js` lines 1102-1138) must walk through and include a correspondingly large number of these dust inputs to reach the target payout amount, unconstrained by `MAX_INPUTS_PER_PAYMENT_MESSAGE` because `objValidationState.bAA` is true (`validation.js` line 2137).
4. Observe that the resulting unit either fails to validate/publish due to size limits (causing the AA's response to bounce and the requested payout to be lost/stuck) or imposes outsized validation cost on the network when processing the AA's response unit.
