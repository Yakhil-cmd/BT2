### Title
Webhook signature verification org-selection is decoupled from the repository the payload actually mutates, enabling cross-organization forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` used to validate an inbound webhook's HMAC signature based on `repository.owner.login` (or `organization.login`) taken directly from the *unauthenticated* JSON body. The event handlers that actually act on the payload, however, resolve the target `Repository`/`Stack` from a *different* field in the same body: `repository.full_name`. Nothing binds these two fields together, so a webhook signed with one organization's secret can carry a `repository.full_name` pointing at a completely different organization's repository/stack.

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it to select the app whose secret verifies the signature: [1](#0-0) [2](#0-1) 

Once the signature passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers such as `PushHandler`, PR handlers, etc. [3](#0-2) 

All of these handlers inherit `repository_name` / `stacks` from the base `Handler`, which reads `repository.full_name` — a field entirely independent of `repository.owner.login`: [4](#0-3) 

`PushHandler#process` then acts on whatever `Stack` is resolved from that `full_name`: [5](#0-4) 

The same disjoint-field pattern also drives PR review-stack archive/unarchive handlers via `Repository.from_github_repo_name(params.repository.full_name)`: [6](#0-5) 

Shipit explicitly supports multi-tenant deployments where each GitHub organization has its own distinct `webhook_secret`, as documented for the "Using Multiple Github Applications" configuration: [7](#0-6) 
and implemented via `Shipit.github(organization:)` / `github_app_config`: [8](#0-7) 

**The broken binding:** the organization that authenticates the webhook (via `repository.owner.login`/`organization.login`, matched against `webhook_secret`) must equal the organization whose repository is actually written to (via `repository.full_name`, used to resolve `Repository`/`Stack`). Because the signature is computed over the whole raw body, an attacker who legitimately owns/administers Org A (and therefore knows Org A's `webhook_secret`, e.g. by configuring their own GitHub App webhook) can freely set `repository.full_name` inside that same signed body to `"victim-org/victim-repo"`, while keeping `repository.owner.login` as `"org-a"` so the verifier selects and successfully validates against Org A's secret.

### Impact Explanation
This crosses a repository/organization trust boundary that the multi-app model is meant to enforce. An attacker who controls only their own organization's Shipit-linked GitHub App can forge webhooks that:
- Trigger `stack.sync_github` on victim-org stacks via `PushHandler`.
- Archive/unarchive/provision review stacks belonging to a victim org's repository via the PR handlers and `ReviewStackAdapter`, which schedules deprovisioning/provisioning actions.

This is a cross-organization write against Shipit-managed state (`Stack`, `ReviewStack`) that the attacker has no legitimate authorization over, matching the "cross-repository writes" / unauthorized deploy-adjacent impact category.

### Likelihood Explanation
Requires only that the Shipit instance is configured with multiple GitHub organizations (a documented, supported setup) and that the attacker has legitimate control of a webhook secret for at least one configured org (their own org's GitHub App installation) — no access to the victim org's secret, GitHub App, or Shipit session/API token is needed. Crafting the payload is trivial (set `repository.full_name` to the victim repo while keeping `owner.login`/`organization.login` pointing at the attacker's own org).

### Recommendation
Bind signature-org selection to the same repository/organization the handlers act on: derive `repository_owner` from `repository.full_name`'s owner segment (or require the two to match) rather than trusting `repository.owner.login`/`organization.login` independently, and reject requests where they disagree before calling `verify_signature`.

### Proof of Concept
1. Shipit is configured with two orgs, `org-a` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` multi-app setup).
2. Attacker knows `org-a`'s `webhook_secret` (e.g. they administer `org-a`'s GitHub App).
3. Attacker POSTs to `/github/webhooks` with `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "org-a" }
  }
}
```
4. `X-Hub-Signature` is computed as `sha1=` + `HMAC-SHA1(org-a_webhook_secret, raw_body)`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret.
6. `Shipit::Webhooks.for_event("push")` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github` on the victim's stacks — despite the request never being signed by `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
