### Title
Cross-repository status webhook triggers unauthorized continuous deployment via global SHA lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves commits with `Commit.where(sha: params.sha)`, a lookup that is not scoped to the repository that authenticated the webhook. Because webhook signature verification only proves the request was signed by *some* organization's `webhook_secret` (chosen based on the payload's `repository.owner.login`), and never checked against the stack that owns the matched commit, an attacker who controls a repository sharing a commit SHA with a victim stack (e.g. via a fork, which reuses identical commit objects/SHAs for unmodified history) can post a legitimate, correctly-signed `status` webhook from their own repo and cause Shipit to write a `success` status onto the victim's commit, triggering `deployable_status`/`schedule_merges` and, if `continuous_deployment` is enabled, an unauthorized deploy of the victim's stack.

### Finding Description
The broken binding as an equality that must hold but doesn't:
`payload.repository.full_name (attacker's repo B) == commit.stack.repository.full_name (victim's stack A)`.

Trace:
- `WebhooksController#verify_signature` only checks that the raw body is HMAC-signed with the secret configured for `repository_owner` (`params.dig('repository','owner','login')`), i.e. it authenticates "this request came from GitHub for organization X," not "this request pertains to stack A." [1](#0-0) 
- `StatusHandler#process` then looks up commits purely by `sha`, globally across the entire `commits` table, with no filter on repository/stack ownership: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1) 
- `create_status_from_github!` -> `add_status` creates a `Status` scoped to `commit.stack_id` — always the pre-existing owning stack, regardless of which org/repo the webhook actually came from — and, on a meaningful state transition, emits `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges`. [3](#0-2) [4](#0-3) 
- `Status` has an `after_commit ... :schedule_continuous_delivery` callback that calls `commit.schedule_continuous_delivery`, which checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.perform_later(stack)` — again entirely based on the victim's own stack state, with the attacker-controlled webhook merely supplying the triggering "success" status. [5](#0-4) [6](#0-5) [7](#0-6) 
- `ContinuousDeliveryJob#perform` re-checks `stack.continuous_deployment?`, schedule window, and `stack.occupied?`, but not the webhook's originating repository (it has no way to, since that information was never threaded through). [8](#0-7) 

Root cause: `sha` is globally unique-ish by convention but not enforced or scoped per-repository at the model/query level for webhook processing, and no code path in `StatusHandler`, `Commit#create_status_from_github!`, or `Commit#add_status` cross-checks the webhook payload's `repository` field against `commit.stack.repository`.

Attacker's exact request: attacker owns/forks a public repository that shares commit objects (hence identical SHAs) with the victim's tracked repository (a common occurrence for forks with unmodified upstream history). Attacker calls the real GitHub Statuses API (`POST /repos/{attacker}/{repo}/statuses/{sha}`) with `state: success` on a SHA that is shared with a commit in victim stack A. GitHub delivers a webhook to Shipit, correctly signed with the attacker-organization's own `webhook_secret` (a secret the attacker's org legitimately possesses because it's a Shipit-configured GitHub App installation for their own org/repo). `verify_signature` passes because it only validates against attacker's own org's secret. `StatusHandler#process` then matches the shared SHA to the victim's `Commit`, and the rest of the pipeline proceeds as if it were a legitimate CI signal for stack A.

Existing guards checked and found insufficient: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate the sender's own org, never cross-check the target repository; `drop_unhandled_event` is irrelevant (status events are handled); the `ExplicitParameters` schema in `StatusHandler` only validates types, not repository identity; there is no `require_permission!`/`stacks` scope check in this webhook flow at all, since webhooks are inherently unauthenticated-as-a-user by design and rely solely on signature+content binding, which is missing here.

### Impact Explanation
This is a payload for one repository (attacker's) mutating another repository's stack/commit state and, when `continuous_deployment` is enabled and CI is not ignored, triggering an unauthorized deploy of a completely unrelated organization's stack — matching the "Critical: unauthorized deploy" / "payload for one repository mutating another's stack, commit... task" category. The blast radius spans tenants: any Shipit installation tracking multiple organizations/repos is affected wherever a SHA collision (e.g., shared fork history) can be arranged between an attacker-controlled repo and a victim stack. Repeatable per shared commit; an attacker could specifically fork a target repo, then push a new "identical" commit that inherits the same SHA as an existing upstream commit and immediately mark it `success` to fast-track it as deployable in the victim's continuous delivery pipeline.

### Likelihood Explanation
Preconditions: the attacker must control a GitHub repository already onboarded to the same Shipit instance (so that a `webhook_secret` exists for their org and `verify_webhook_signature` succeeds), and must find/produce a SHA collision with a commit tracked by the victim stack — most practically achieved by forking the victim's public repository, which reuses identical commit objects (and thus identical SHAs) for any unmodified history. Given that, the attack cost is low: sending one GitHub status API call on their own repository, no Shipit credentials, sessions, or GitHub secrets of the victim needed. The precondition that both attacker and victim repos are configured in the same Shipit deployment with continuous_deployment enabled and `ignore_ci` false does narrow applicability, but it is a realistic multi-tenant/multi-org Shipit deployment scenario, and the technique (forking to inherit SHAs) is a standard git behavior, not exotic.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers, e.g. check-run/check-suite handlers) to the repository that authenticated the webhook: join/filter `Commit` through `Stack#repository` matching `params.dig('repository','full_name')` (or owner/name) before applying the status, rather than a bare `Commit.where(sha: params.sha)`. Additionally, consider enforcing SHA scoping at the schema/model level so a commit is only ever resolved within the context of its own stack's repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, new test — not the existing suite):
```ruby
test "status webhook from unrelated repo B triggers deploy of victim stack A via shared sha" do
  stack_a = shipit_stacks(:shipit) # victim, has continuous_deployment: true, ignore_ci: false
  stack_a.update!(continuous_deployment: true, ignore_ci: false)
  commit = stack_a.commits.last
  commit.statuses.destroy_all
  commit.update!(locked: false)
  assert_not commit.reload.deployable?

  # Binding under test, stated explicitly before tracing:
  # payload.repository.full_name ("attacker/repoB") == commit.stack.repository.full_name ("shopify/shipit-engine")
  # This should be false, and no deploy of stack_a should occur.

  attacker_repo_payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker/repoB', 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(stub(verify_webhook_signature: true))

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_a]) do
    request.headers['X-Github-Event'] = 'status'
    post :create, body: attacker_repo_payload.to_json, as: :json
  end

  assert_predicate commit.reload, :deployable?
  assert_not_equal attacker_repo_payload['repository']['full_name'], stack_a.repository.full_name
end
```
This demonstrates that despite `payload.repository.full_name != stack_a.repository.full_name`, `ContinuousDeliveryJob` is enqueued for `stack_a`, proving the WEBHOOK_PROVENANCE binding is violated.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
