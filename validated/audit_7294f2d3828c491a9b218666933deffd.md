### Title
Cross-organization Team hijack via `github_id` collision in `MembershipHandler#find_or_create_team!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up/creates a `Team` solely by `github_id`, with no check that the payload's verified organization matches the `organization` already stored on that `Team` row. An attacker who owns their own GitHub org (and thus its own valid webhook secret) can send a `membership` webhook whose `team.id` collides with a pre-existing privileged `Team` from a different org (e.g. `shopify/developers`), causing `team.add_member(member)` to add an attacker-chosen GitHub login to that real team.

### Finding Description
The intended binding is: **organization whose `webhook_secret` verified the request bytes == organization that owns the `Team` row being mutated**.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from the payload (`params.dig('repository','owner','login') || params.dig('organization','login')`) and calls `Shipit.github(organization: repository_owner)` to fetch the secret used for HMAC verification [1](#0-0) [2](#0-1) .
- For `membership` events there is no `repository` key, so `repository_owner` is exactly `params.organization.login`, an attacker-controlled field. An attacker owning `attacker-org` can set `organization.login = 'attacker-org'` and sign the payload with `attacker-org`'s own genuine `webhook_secret` — this passes `verify_webhook_signature` legitimately, no secret of Shopify's is needed [3](#0-2) .
- `MembershipHandler#process` then calls `find_or_create_team!`, which does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [4](#0-3) 
`find_or_create_by!` only runs the block on **creation**. If a `Team` row already exists with `github_id` equal to the attacker-supplied `params.team.id` (e.g. the real `shopify/developers` team, created previously by a legitimate `shopify`-signed webhook or by `Team.find_or_create_by_handle`), the block is skipped entirely — `organization` is never re-checked or re-assigned, and the returned `team` is the pre-existing privileged row, not a new attacker-owned row.
- `process` then unconditionally calls `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)`, an attacker-controlled login [5](#0-4) . `Team#add_member` appends the member with no ownership check [6](#0-5) .

After the request: the equality is broken — the `Team` row mutated (`shopify/developers`, `organization: 'shopify'`) does not match the organization whose secret verified the request (`attacker-org`). No code path re-validates `team.organization == repository_owner` before calling `add_member`.

Existing guards do not catch this:
- `verify_signature` only proves the request bytes belong to *some* configured org (attacker-org), not that the *contents* (team id) belong to that org.
- `find_or_create_team!`'s `find_or_create_by!` block is a create-only hook; it provides no update/validation semantics for the found-row branch.
- `User#authorized?` trusts `teams` membership directly: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , so once a `Membership` row is created for the attacker-controlled login, `authorized?` becomes true for that user if `shopify/developers` is in `Shipit.github_teams`.

### Impact Explanation
An attacker who controls only their own GitHub org and its webhook (an unprivileged actor by the threat model) can grant an arbitrary, attacker-chosen GitHub login membership in any `Team` row whose `github_id` they can guess or learn, including teams referenced by `Shipit.github_teams`. This directly escalates into Shipit's authorization system (`User#authorized?`), letting the attacker-controlled account pass `require_permission!`/authorization checks used to gate deploys, rollbacks and stack actions. This is repeatable against any privileged team as long as its `github_id` is known, and is a cross-tenant issue: an attacker-owned organization mutates state (`Membership`) belonging to a completely different organization's `Team`. This matches the "escalation into `Shipit.github_teams` authorization" Critical/High impact category.

### Likelihood Explanation
Preconditions: (1) a `Team` row for the target privileged team (e.g. `shopify/developers`) must already exist in the DB with a known `github_id` — plausible since Shipit creates such rows automatically the first time a legitimate `membership` webhook or `Team.find_or_create_by_handle` runs, and GitHub team ids are not normally treated as secrets; (2) the attacker must control an org with its own valid `webhook_secret` configured in Shipit (i.e. their own org's webhook is registered against this Shipit instance), which is a normal deployment scenario for multi-tenant Shipit installs. Attacker cost is low: craft one JSON payload, sign it with their own secret, and POST to `/webhooks`. No Shipit credentials, sessions, or GitHub secrets are required beyond the attacker's own webhook secret, consistent with the stated unprivileged-attacker model.

### Recommendation
In `find_or_create_team!`, after finding or creating the `Team`, verify that `team.organization == params.organization.login` (i.e., the verified `repository_owner`) before proceeding; raise/reject the webhook if they diverge instead of silently reusing the existing row. Additionally, consider scoping the `find_or_create_by!` lookup by both `github_id` and `organization`, and treat `github_id` collisions across differing organizations as a hard error rather than a silent match.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb
test "membership webhook verified under one org cannot add members to another org's Team" do
  privileged_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 48
  Shipit.stubs(:github_teams).returns([privileged_team])

  payload = {
    'action' => 'added',
    'team' => { 'id' => 48, 'name' => 'Developers', 'slug' => 'developers', 'url' => 'https://api.github.com/...' },
    'organization' => { 'login' => 'attacker-org' }, # verified org != team's real org
    'member' => { 'login' => 'attacker' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).process

  attacker = Shipit::User.find_by!(login: 'attacker')
  assert Shipit::Membership.exists?(team_id: privileged_team.id, user_id: attacker.id)
  assert privileged_team.reload.organization == 'shopify' # still shopify's team
  assert attacker.authorized? # attacker now escalated via shopify's privileged team
end
```
Both sides of the equality — `repository_owner` used for verification (`attacker-org`) vs. `team.organization` mutated (`shopify`) — mismatch after the request, confirming the binding is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
