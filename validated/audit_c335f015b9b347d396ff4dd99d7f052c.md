### Title
Webhook signature is verified against an organization derived from a payload field that is never cross-checked against the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate an inbound webhook's HMAC against using `repository_owner`, a value read straight out of the attacker-supplied JSON body. The event handlers, however, resolve the `Repository`/`Stack` to act on using a *different* field of the same body: `payload.dig('repository', 'full_name')`. Because both fields live in the same attacker-controlled payload and only one of them is checked for "does this org own this webhook_secret", an operator of any org onboarded to a multi-tenant Shipit instance can forge a fully-valid HMAC (using their own org's `webhook_secret`) over a payload whose `repository.owner.login` names their own org but whose `repository.full_name` names a completely different, victim repository/stack.

### Finding Description
`Shipit.github(organization:)` looks up a per-organization config (`app_id`, `webhook_secret`, etc.) from `secrets.github[org]` [1](#0-0) . `WebhooksController#verify_signature` derives that organization key from the payload itself, not from any trusted/pre-registered identity: [2](#0-1) 

The signature check (`github_app.verify_webhook_signature`) only proves the raw body was HMAC-signed with *some* configured `webhook_secret` — it says nothing about which repository the payload's other fields describe [3](#0-2) .

Once the signature passes, `create` blindly dispatches the parsed JSON to the registered handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . Every handler resolves its target `Stack`s via `Repository.from_github_repo_name(repository_name)`, where `repository_name` is `payload.dig('repository', 'full_name')` — a field completely independent of the `repository.owner.login`/`organization.login` field used for signature routing: [5](#0-4) 

`Repository.from_github_repo_name` simply splits this string and does a DB lookup with no relation back to the verified organization [6](#0-5) .

This is the same class of bug as the report: the code trusts one facet of untrusted input (here, `repository.owner.login`, analogous to `sharePrice`'s assumed decimals) to stand in for a property (org identity) it does not actually guarantee, while a second, independently-controlled facet (`repository.full_name`, analogous to the token amount) is used for the real state-changing computation, with no invariant tying the two together.

Concretely: for a Shipit deployment onboarding multiple GitHub orgs (as documented/supported by `secrets.github` keyed per-organization, see `config/secrets.development.shopify.yml` and `TOP_LEVEL_GH_KEYS`/`github_app_config` in `lib/shipit.rb`), an attacker who legitimately administers their own org's GitHub App installation on this Shipit instance knows that org's `webhook_secret`. They can POST to `/webhooks` a JSON body they fully control:

```json
{
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  ...
}
```
signed with `HMAC-SHA1(attacker-org's webhook_secret, raw_body)`. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s app config, and the signature checks out. `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github! }` against `victim-org/victim-repo`'s commits — with no re-derivation of org identity from `full_name` [7](#0-6) . The same applies to `PushHandler` (triggers `stack.sync_github(expected_head_sha:)`) and `CheckSuiteHandler` (schedules check-run refresh) for arbitrary victim stacks/branches [8](#0-7) [9](#0-8) .

### Impact Explanation
Forging `status` events lets the attacker write arbitrary commit statuses (`create_status_from_github!`) onto any tracked victim commit, including marking required CI contexts (`ci.require`/`ci.blocking`, see README) as `success`. Since Shipit's deploy gating and continuous-delivery logic depend on these stored `Status` records, this is a direct path to causing an unauthorized deploy of a commit that never actually passed CI on the victim repository — matching the "unauthorized deploy" Critical-impact criterion. It also lets an attacker force spurious `GithubSyncJob`/check-run refresh activity against a victim stack they have no access to.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator of at least one GitHub organization onboarded to the same multi-tenant Shipit instance (i.e., they know their own org's `webhook_secret`, which they configured themselves) — no repository write access, no Shipit session, and no privileged Shipit account is needed. The `repository.owner.login`/`full_name` mismatch is purely a matter of crafting the JSON body, which is trivial once a valid HMAC key is available.

### Recommendation
After verifying the signature, re-derive the trusted organization from the same field the signature was checked against, and reject (or scope) any handler lookup where `repository.full_name`'s owner segment does not match the verified `repository_owner`. Concretely, `Handler#repository_name`/`stacks` should receive the verified organization from the controller and assert `full_name.split('/').first == verified_organization` before resolving `Repository.from_github_repo_name`.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `attacker-org` (attacker knows `webhook_secret_a`) and `victim-org` (has a stack tracking `victim-org/victim-repo`).
2. Attacker computes `sig = HMAC-SHA1(webhook_secret_a, body)` where `body` is:
```json
{"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},
 "sha":"<victim sha>","state":"success","context":"ci/required"}
```
3. POST to `/webhooks` with header `X-Github-Event: status`, `X-Hub-Signature: sha1=<sig>`, body as above.
4. `WebhooksController#verify_signature` resolves `repository_owner` from `repository.owner.login = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature verifies successfully (per `lib/shipit/github_app.rb#verify_webhook_signature`).
5. `StatusHandler#process` looks up commits by `sha` on `victim-org/victim-repo` (resolved via `full_name`, per `Handler#repository_name`) and writes a forged `success` status, independent of `attacker-org`'s verified identity.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
