### Title
Unrestricted submodule URLs allow attacker-controlled code execution via `git submodule update --init --recursive` - (File: `main.go`, function `configureWorktree`)

### Summary
`git-sync` fetches and checks out an untrusted, attacker-influenced remote repository and, when `--submodules` is not `off`, automatically runs `git submodule update --init [--recursive]` against whatever `.gitmodules` content is present in that repo, with no validation, allow-listing, or protocol restriction on submodule URLs. This is analogous to the MarginSwap finding in that a downstream component (`git`) is handed fully attacker-controlled parameters (submodule URLs/paths) without any entry/content check, letting the party who controls the synced repo drive execution of `git` against arbitrary targets.

### Finding Description
`git-sync`'s worktree configuration step unconditionally runs submodule initialization once a new commit has been checked out: [1](#0-0) 

The `submodulesArgs` (`submodule update --init` and optionally `--recursive`) are executed against the working tree that was just checked out from the remote, meaning `.gitmodules` — including submodule `url` entries — comes entirely from the untrusted upstream content. There is no check anywhere in `main.go` that:
- restricts submodule URL schemes (e.g., no `protocol.allow`/`GIT_ALLOW_PROTOCOL` configuration is set — confirmed absent via search of `main.go`),
- validates submodule paths (no `safe.directory`/path canonicalization for submodule targets),
- or whitelists/verifies submodule content before invoking `git submodule update`.

This mirrors the "M-03" pattern: a function (`crossSwapTokensForExactTokens`/here, `configureWorktree`) blindly forwards externally-supplied structured data (`pairs`/tokens, here `.gitmodules` URLs) into a powerful downstream call (`pair.swap`/here, `git submodule update`) without validating the content's identity or safety, allowing the attacker who supplies that content to control what gets invoked.

Historically, this exact code path in `git` itself has been the vector for multiple submodule-related CVEs (e.g., CVE-2017-1000117 SSH option injection via submodule URLs, CVE-2022-39253 disclosure of arbitrary host files through local submodule clones with `file://`, and hook-execution issues via case-insensitive `.git` paths in submodules on some filesystems). Because `git-sync` does not add its own allow-list or `protocol.*`/`GIT_ALLOW_PROTOCOL` restriction before delegating to `git submodule update --init --recursive`, it inherits full exposure to whichever of these submodule-URL behaviors the installed `git` binary permits, with the additional property that the untrusted content originates from whatever repo/ref the operator configured `git-sync` to sync (or, in the compromised-upstream/attacker-controlled-branch scenario, from a ref an attacker can push to).

### Impact Explanation
If an attacker can get content into the synced ref (e.g., a compromised upstream, a mirror, an unprotected branch that `--ref` tracks, or a supply-chain injection), they can add or modify `.gitmodules` to point at attacker-chosen URLs/protocols. Depending on the `git` version and any recursive nested-submodule chaining, this can result in:
- SSRF/arbitrary outbound connections initiated by the git-sync sidecar's network identity,
- disclosure of local files or credentials configured for git-sync (e.g., via `file://` submodule tricks or credential helper invocation against attacker URLs),
- in vulnerable `git` versions, command/argument injection or code execution during `submodule update`.

This is a real "code execution / credential disclosure / file write outside root" class impact when `--submodules` is enabled (which is the default, `submodulesRecursive`), matching the accepted impact categories.

### Likelihood Explanation
Likelihood depends on the attacker's ability to influence the synced repo's content (push access, compromised upstream, or an unpinned/mutable ref) — this is the standard git-sync threat model of "attacker-pushed commit or ref." No additional privilege on the git-sync process itself is required; the submodule processing is automatic and unconditional whenever a new hash is picked up, with `--submodules` defaulting to recursive processing. The likelihood is moderated by needing a vulnerable/permissive `git` binary version or an environment where the resulting protocol/URL leads to an observable impact (e.g., outbound network access, or an old `git` lacking modern submodule URL protections).

### Recommendation
- Before invoking `git submodule update`, set `protocol.file.allow=user`/`false` and `GIT_ALLOW_PROTOCOL` (or `protocol.allow`) restricting submodule fetches to the same protocol family as the top-level `--repo` (e.g., disallow `ext::`, `file://`, and arbitrary `ssh://` hosts unless explicitly permitted).
- Provide (and document) an explicit `--submodules-allow-url-pattern` (or similar) flag so operators can whitelist acceptable submodule URL prefixes.
- Pin/verify the installed `git` version to one with submodule URL hardening, and consider running the submodule step with reduced network/credential scope.

### Proof of Concept
1. Configure `git-sync` with `--repo=<attacker-influenced-repo>` and default `--submodules` (recursive).
2. In the source repo, add a `.gitmodules` entry with a URL such as `ext::sh -c 'touch /tmp/pwned'` (on vulnerable git versions) or `file:///etc/passwd`-style path abuse, and commit it.
3. On the next sync cycle, `git-sync` checks out the new hash and calls `configureWorktree`, which runs: [2](#0-1) 
   invoking `git submodule update --init --recursive` against the attacker-supplied `.gitmodules`, with no protocol/URL restriction applied by git-sync.
4. Depending on the `git` version, this either executes the injected command/protocol handler or performs an unintended fetch, demonstrating that git-sync passes untrusted submodule content straight to `git` without an entry check — the git-sync analog of MarginSwap's unchecked `pairs`/`tokens` parameters reaching `pair.swap`.

Note: I could not find any git-config hardening (e.g., `protocol.allow`, `GIT_ALLOW_PROTOCOL`) applied anywhere in `main.go` for the submodule path via my searches; if such hardening exists elsewhere (e.g., in a config file not indexed), this finding's severity should be reassessed against that mitigation.
