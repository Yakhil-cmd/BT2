This confirms the multi-organization deployment model — `Shipit.github(organization:)` in `lib/shipit.rb` looks up a distinct config (including a distinct `webhook_secret`) per organization key in `secrets.github`, keyed by exactly the login string used in `github_app_config`. This validates the analog described below: the field used to select which secret verifies the HMAC (`repository.owner.login` / `organization.login`) is never cryptographically bound to the field later used to decide which `Repository`/`Stack` gets mutated (`repository.full_name`).

### Title
Webhook signature is verified against `repository.owner.login`, but repository mutation is driven by the independent, unverified `repository.full_name` field, allowing any onboarded org to forge events for another org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) directly out of the untrusted, attacker-suppliable raw JSON body: [1](#0-0) [2](#0-1) 

Each organization in a multi-tenant Shipit deployment has its own independent `webhook_secret`, looked up by exactly this login string: [3](#0-2) 

Once the signature check passes, `create` dispatches the entire raw payload, unmodified, to the registered event handlers: [4](#0-3) 

Every handler resolves the target `Repository`/`Stack` to mutate using a *different* payload field, `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name`: [5](#0-4) [6](#0-5) 

`PushHandler`, for instance, uses this repository resolution to call `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack: [7](#0-6) 

Because `repository.owner.login` (used only for secret selection) and `repository.full_name` (used only for the actual write target) are two independent JSON fields inside the same signed body, and the HMAC only proves "this body was signed by whichever org's secret was selected using field A," nothing proves that field A and field B refer to the same repository. An org onboarded to the same Shipit instance — who legitimately knows their *own* webhook secret because they configured their own GitHub App/organization webhook — can craft a raw POST body where `repository.owner.login` is set to their own org login (so the signature verifies against their known secret) while `repository.full_name` is set to `"victim-org/victim-repo"`. The equality the code implicitly assumes is:
`organization authenticated by verify_signature == repository owner mutated by the handler`
This equality is never enforced, breaking the deployment-trust binding.

### Impact Explanation
This lets an attacker who controls (or is an authenticated member/admin of) any organization onboarded to the multi-tenant Shipit instance forge GitHub webhook events for a target repository/stack belonging to a completely different organization, without ever needing that victim organization's `webhook_secret`. Depending on which handler is targeted this can: trigger `stack.sync_github` on victim stacks (`push`), flip pull-request/review-stack archive/unarchive/provisioning state (`pull_request` handlers), inject fabricated commit statuses (`status` handler), or manipulate `Team`/`Membership` records cross-organization (`membership` handler). Forced `sync_github` and status/PR-state manipulation are steps that materially influence what gets merged/deployed, which is why this rises to a cross-repository write against Shipit's own trust boundary — the whole point of per-organization webhook secrets is to guarantee that a payload claiming to be about org X's repository was actually sent by org X.

### Likelihood Explanation
Requires only that the attacker legitimately administers or has webhook-signing capability for *some* organization/repository already onboarded to the same multi-tenant Shipit instance (a normal, unprivileged tenant, not the victim, and not requiring any Shipit session, `ApiClient` token, or the victim's secret). This is a realistic configuration for any Shipit deployment serving more than one GitHub organization, which the `github_app_config`/`TOP_LEVEL_GH_KEYS` multi-org schema explicitly supports.

### Recommendation
Bind signature verification to the exact same field used to resolve the write target. Concretely, `verify_signature` should derive `repository_owner` from `payload.dig('repository', 'full_name')` (or otherwise ensure `repository.owner.login` and the owner segment of `repository.full_name` are identical) before dispatching to handlers, and reject the request if they disagree. Alternatively, verify the signature once using the app-level secret and then independently confirm, per handler, that the resolved `Repository`'s owner matches the organization whose secret validated the request.

### Proof of Concept
1. Deploy a multi-org Shipit instance with `secrets.github` containing both `attacker-org: { webhook_secret: "s1", ... }` and `victim-org: { webhook_secret: "s2", ... }` (or with `victim-org` simply having its own stacks configured under the standard multi-tenant schema).
2. As the operator/admin of `attacker-org` (an unprivileged tenant relative to `victim-org`), craft a raw JSON body for a `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to Shipit, e.g. an old/malicious commit>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Sign the body with `s1` (the attacker's own legitimately-known `webhook_secret` for `attacker-org`) using HMAC-SHA1, and send it as `X-Hub-Signature` to `POST /github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against `s1`.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on victim-org's stacks, despite the request never being signed by `victim-org`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations

  end
