### Title
Cross-tenant CI status forgery via organization/commit-sha binding mismatch in webhook signature verification - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret`) used to authenticate an inbound webhook purely from the payload's `repository.owner.login` (or `organization.login`) field [2](#0-1) [3](#0-2) . For `status` events, the handler that actually mutates state, `StatusHandler#process`, ignores the repository/organization entirely and looks up target `Commit` records purely by `sha`, globally, with no scoping to the organization whose secret validated the request [4](#0-3) .

### Finding Description
In a multi-tenant Shipit install (the documented "Using Multiple Github Applications" configuration, where each organization has its own `app_id`/`webhook_secret` [5](#0-4) ), each organization's GitHub App owner legitimately possesses their own valid `webhook_secret` and can therefore produce a validly-signed webhook body for their own org.

The equality that should hold is: **organization authenticated == organization whose data is written**. Instead:
- Authentication side: `repository_owner` (from `repository.owner.login`/`organization.login`) selects `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is used in `verify_webhook_signature` [2](#0-1) [6](#0-5) .
- Write side: `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never checks `repository.owner.login`, `repository.full_name`, or any organization/stack scoping [1](#0-0) .

An attacker who controls a legitimately-installed (even brand-new, free) GitHub App on their own organization ("attacker-org") can compute a valid HMAC over a JSON body of their choosing using their own `webhook_secret`, set `X-Github-Event: status`, and set `repository.owner.login` (or `organization.login`) to `attacker-org` so `verify_signature` succeeds against their own secret. The `sha` field inside that same signed body, however, can be set to any commit SHA already tracked by any *other* tenant's stack in the same Shipit instance — `StatusHandler` will happily create a forged `success`/`failure` `Status` for that commit, because it performs no cross-check against the authenticated organization.

### Impact Explanation
Commit statuses drive Shipit's deploy/merge gating logic: `Commit#deployable?`/`StatusChecker` and the merge queue's `all_status_checks_passed?`/`any_status_checks_failed?` consult exactly these `Status` records to decide if a commit can be deployed or a pull request merged [7](#0-6) , and creating/transitioning a `Status` schedules `ProcessMergeRequestsJob`/continuous delivery [8](#0-7) . By forging a passing `success` status for a victim organization's commit, a completely unrelated tenant (an attacker with no access to the victim's repository, GitHub App, or Shipit session) can satisfy `ci.require`/`merge.require` checks and trigger an unauthorized deploy or an unauthorized pull-request merge for that victim's stack — meeting the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires only that the target Shipit instance is configured with the documented multi-organization GitHub App layout (explicitly documented and supported) and that the attacker be able to install (or already control) any one GitHub App on any organization pointed at the same Shipit instance — no access to the victim organization, no `ApiClient` token, no Shipit session, and no GitHub write access to the victim repo are required. The only work is computing an HMAC-SHA1 over a crafted JSON body with a secret the attacker legitimately owns, which is straightforward.

### Recommendation
Bind the authenticated organization to the record being mutated: `StatusHandler` (and other handlers that resolve state independent of `repository`) must restrict the lookup to commits/stacks belonging to the same organization/repository that was cryptographically authenticated in `WebhooksController#verify_signature`, e.g., by scoping `Commit.joins(:stack => :repository).where(sha: params.sha, repositories: { owner: repository_owner })`, and by rejecting events whose `repository.full_name`/`organization.login` do not match a repository actually associated with that authenticated organization before dispatching to any handler.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `attacker-org` and `victim-org` (per the documented multi-org layout).
2. As the owner of `attacker-org`'s GitHub App, obtain its `webhook_secret` (legitimately available to any org admin).
3. Identify a tracked commit `sha` belonging to a `victim-org` stack (visible e.g. via Shipit's public UI/API for that stack).
4. Craft a JSON body:
```json
{ "sha": "<victim-commit-sha>", "state": "success", "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" } } }
```
5. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates successfully against the attacker's own secret [2](#0-1) .
7. `StatusHandler#process` finds the `victim-org` commit by `sha` alone and creates a forged `success` status on it [1](#0-0) , potentially unblocking an unauthorized deploy/merge on `victim-org`'s stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
