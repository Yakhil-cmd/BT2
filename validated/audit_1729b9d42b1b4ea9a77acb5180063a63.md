### Title
`CCMenuUrlController#client` mints a stack-unscoped `ApiClient` token reusable to read any stack's CCMenu status - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` calls `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` without ever setting `stack:` in either the lookup keys or the `create_with` attributes, so the created/reused `ApiClient` always has `stack_id == nil`. Because `Api::BaseController#stacks` treats a nil `stack_id` as "no scope" (`Stack.all`), the resulting CCMenu token is valid for reading the CCMenu status of every stack on the install, not just the one the user requested it for.

### Finding Description
The claimed binding `client.stack_id == stack.id` does not hold: `stack` is computed at [1](#0-0)  but is never passed into `client`'s lookup at [2](#0-1) . The first time any user calls `fetch` for any stack, an `ApiClient` row is created with `creator: current_user, name: 'CCMenu Client', permissions: ['read:stack']` and `stack_id` left at its default `nil` (the column is `optional: true` per [3](#0-2) ). Every subsequent call to `client` — for any other stack — matches that same row via `find_or_create_by!(creator:, name:)` and returns the identical `authentication_token`.

Downstream, `Api::BaseController#stacks` explicitly treats a client with no `stack_id` as globally scoped: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` at [4](#0-3) . `Api::CCMenuController` only enforces the permission string via `require_permission :read, :stack` at [5](#0-4) , which is checked by `check_permissions!` at [6](#0-5)  — this only checks that `'read:stack'` is in the permissions array, it does not check that the requested stack matches `stack_id`. Worse, `CCMenuController` defines its own `stack` method at [7](#0-6)  which calls `Stack.from_param!(params[:stack_id])` directly instead of the inherited `stacks.from_param!` (the scoped lookup at [8](#0-7) ), so even a properly stack-scoped token's scoping would never be enforced by this controller anyway.

Attacker flow: an authenticated low-privilege Shipit user with legitimate read access to Stack A visits `/stacks/:A/ccmenu_url`, receives a token (`GET /stacks/:A/ccmenu_url` → `authentication_token`). That token, because `stack_id` is `nil`, is accepted by `Api::CCMenuController#show` for `/api/stacks/:B/ccmenu.xml?token=...` for any Stack B they have no access to, since `stacks` resolves to `Stack.all` when `stack_id?` is false.

### Impact Explanation
The exposed data is deploy/build status (latest deploy id and its `ended_at`/running state) for any stack on the install, rendered by `Api::CCMenuController#show` at [9](#0-8) . This is a cross-tenant unauthorized read of stack state: a token intended (by the endpoint's design/comment) to be scoped to one stack is valid for all stacks. This matches the "High - ... unauthenticated read of stack state, task streams or deploy output" category: the token bypasses the app's per-stack read authorization once minted, and is fully repeatable against arbitrary stack IDs by any authenticated user who can reach `fetch` for at least one stack they can read.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be an authenticated Shipit user with legitimate read access to any single stack (the normal precondition to even reach `/stacks/:id/ccmenu_url`). No secrets, GitHub credentials, or elevated Shipit roles are required. The attack is a single GET request plus token reuse against a different stack ID — trivially repeatable, deterministic, and does not depend on race conditions or timing.

### Recommendation
Include `stack` in the `find_or_create_by!` lookup keys (and in `create_with`), e.g. `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`, so each stack gets a distinct, stack-scoped client/token. Additionally, remove `Api::CCMenuController`'s local override of `stack` and rely on the inherited `stacks.from_param!` scoping so that even a correctly-scoped token cannot be used against a stack it wasn't issued for.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb
test "tokens minted for different stacks are stack-scoped and not shared" do
  user = shipit_users(:walrus)
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack the user should not gain access to

  session[:user_id] = user.id

  get :fetch, params: { stack_id: stack_a.to_param }
  token_a = extract_token_from_response

  get :fetch, params: { stack_id: stack_b.to_param }
  token_b = extract_token_from_response

  client_a = Shipit::ApiClient.authenticate(token_a)
  client_b = Shipit::ApiClient.authenticate(token_b)

  assert_not_equal client_a.id, client_b.id, "expected distinct ApiClient rows per stack"
  assert_equal stack_a.id, client_a.stack_id
  assert_equal stack_b.id, client_b.stack_id
end
```
Currently this assertion fails: `client_a.id == client_b.id` and both have `stack_id == nil`, demonstrating the token from `fetch(stack_a)` also authenticates against `stack_b` in `Api::CCMenuController#show`.
