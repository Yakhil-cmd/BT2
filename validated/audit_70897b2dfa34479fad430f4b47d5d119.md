### Title
Burned position NFT permanently blocks liquidation and bad-debt cleanup, masking protocol insolvency - (File: contracts/controller/src/storage/account.rs)

### Summary
`storage::get_account` resolves NFT ownership as a mandatory leg of every liquidation and cleanup path. The position NFT's `burn` removes the `Owner(token_id)` entry permanently, and token IDs are never reused, so `try_account_owner` returns `None` forever. Any account whose NFT is burned becomes permanently unliquidatable and un-socializable: `process_liquidation`, `clean_bad_debt`, and `force_socialize_bad_debt` all abort with `AccountNotFound`. An account owner can therefore freeze an underwater position's debt and collateral in place indefinitely, leaving the pool's bookkeeping to count an uncollectible debt as backing.

### Finding Description
The NULL-deref crash class maps here onto a permanently-unreachable ownership read. `get_account` requires `try_account_owner` to resolve:

`try_account_owner` fails closed on a missing `Owner` entry. `socialize_bad_debt` calls `get_account` before applying either the permissionless dust gate or the owner-forced gate, so both cleanup paths revert with `AccountNotFound`. [3](#0-2) 

The burn side is asymmetric and permanent: `nft_burn_call` only guards the `u64`→`u32` widening, and the NFT itself removes `Owner(token_id)` on burn with no restore path — a burned ID can never be re-minted or resurrected. [4](#0-3) [5](#0-4) 

The in-repo test pins exactly this failure shape: after `burn(&token_id)` deletes `Owner` while all controller-side account state stays live, a liquidation on a below-1 HF account fails with `AccountNotFound`, and the same test documents that `clean_bad_debt`/`force_socialize_bad_debt` fail identically. [6](#0-5) 

### Impact Explanation
An attacker opens an account, supplies collateral, borrows, waits for (or arranges across thin markets) insolvency, then calls `PositionNft::burn` on their own token. From that point:

- `liquidate` reverts with `AccountNotFound` — no liquidator can seize the collateral or repay the debt.
- `clean_bad_debt` and `force_socialize_bad_debt` revert — the bad debt can never be written down and the collateral can never be reclassified as revenue.
- The pool keeps counting `borrowed` shares and the frozen `supplied` shares. `backing_shortfall` treats ceiled debt value as backing, so an uncollectible debt masks real insolvency; withdrawal reserve checks (`require_reserves`, `require_backed_market`) see a phantom healthy market while the underlying cash was already borrowed out.
- The NFT ID can never be re-minted, so this is not recoverable by restore or governance — it is a permanent state, not a TTL/archival issue. [7](#0-6) 

Result: permanent freezing of the account's collateral (nobody, including the protocol, can route it to suppliers), and a permanently un-socializable bad debt that leaves later suppliers bearing the loss — i.e., protocol insolvency that the designed cleanup mechanism can never resolve without recapitalization funded by third parties.

### Likelihood Explanation
Fully unprivileged: the attacker only needs to own the position NFT, which is true of every account. `burn` is reachable by the token owner at any time, including while the account is deeply underwater. It costs the attacker nothing extra beyond the already-lost collateral. The only mitigation is that the attacker cannot profit directly — the payoff is griefing/insolvency-hiding rather than theft — which caps the severity at Medium. A self-burn after taking max borrow is a single transaction with no prerequisites beyond a normal account.

### Recommendation
Do not let `burn` orphan live controller state. Either (a) have the controller gate NFT burns on the account having zero supply and zero debt (NFT burn would call into the controller, or the controller would expose a `close_account` that burns only after positions are empty), or (b) make the cleanup/liquidation paths tolerate a missing owner — e.g., `socialize_bad_debt` and `process_liquidation` could use `try_get_account_meta` + position maps without requiring `try_account_owner`, since neither path needs the owner's address. Option (b) is the smaller change: ownership resolution is only needed for auth-gated actions, not for permissionless liquidation/cleanup of an already-insolvent account.

/// Burns the NFT; IDs outside the mintable `u32` domain fail with `AccountNotFound`.
pub(crate) fn nft_burn_call(env: &Env, nft: &Address, account_id: u64) {
    let token_id = u32::try_from(account_id)
        .unwrap_or_else(|_| panic_with_error!(env, GenericError::AccountNotFound));
    PositionNftClient::new(env, nft).burn(&token_id);
}

/// Returns current NFT ownership. Out-of-range IDs, missing tokens, and failed
/// lookups return `None`, so ownership checks fail closed.
pub(crate) fn nft_try_owner_of_call(env: &Env, nft: &Address, account_id: u64) -> Option<Address> {
    let token_id = u32::try_from(account_id).ok()?;
    match PositionNftClient::new(env, nft).try_owner_of(&token_id) {
        Ok(Ok(owner)) => Some(owner),
        _ => None,
    }
}

**Token ids are never reused.** Ids come from `increment_token_id`, a
monotonic instance counter. `burn` does not decrement it. A burned id can never
be minted again, so a deleted account id cannot be resurrected.

fn partial_liquidation_resolves_nft_ownership() {

/// Asset units by which supplier claims exceed cash + debt (0 if solvent).
pub(crate) fn backing_shortfall(cache: &Cache) -> i128 {
    let supplied_claim = cache.unscale_supply_floor(cache.supplied());
    let outstanding_debt = cache.unscale_borrow_ceil(cache.borrowed());
    let backing = cache.cash().saturating_add(outstanding_debt);
    supplied_claim.saturating_sub(backing).max(0)
}

/// Panics with `PoolInsolvent` if supplied is zero while borrowed debt is non-zero.
pub(crate) fn require_supply_for_debt(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO && cache.borrowed() != Ray::ZERO {
        panic_with_error!(env, CollateralError::PoolInsolvent);
    }
}
