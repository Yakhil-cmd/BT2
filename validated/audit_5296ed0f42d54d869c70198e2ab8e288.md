This confirms the vulnerability chain. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) resolves target commits globally by `Commit.where(sha: params.sha)` with **no repository/organization scoping at all** — not even the `repository.full_name` field is checked, let alone the org used for signature verification. Combined with the webhook verification using a payload-derived org, this creates a clear cross-tenant trust break in a documented, in-scope multi-org deployment.

### Title
Cross-Organization Webhook Forgery via Payload-Derived Signature Org Selection - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a webhook's HMAC signature against using a field taken from the **same untrusted, attacker-supplied JSON body** it is trying to authenticate. In a multi-organization Shipit deployment (explicitly documented and supported via `docs/setup.md` "Using Multiple Github Applications" and `config/secrets.development.shopify.yml`), an operator who administers one configured GitHub organization (and therefore legitimately knows that organization's `webhook_secret`) can craft an arbitrary payload, sign it with their own org's secret, and have Shipit apply it to any *other* tenant repository/stack tracked by the same instance, because none of the webhook handlers re-validate that the payload's target repository belongs to the organization whose secret was used for verification.

### Finding Description
`WebhooksController#verify_signature` computes the organization used for signature verification directly from the incoming payload, before the signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` is read via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — fields inside the raw, unverified POST body. `Shipit.github(organization: repository_owner)` then looks up the corresponding `GitHubApp` config (and its distinct `webhook_secret`) from `Shipit.secrets.github`, per the multi-org schema: [3](#0-2) 

This multi-org layout is a first-class, documented feature (not an undocumented/unsupported mounting configuration): [4](#0-3) [5](#0-4) 

Once the signature passes (correctly, because it was computed with the org the attacker actually controls), `WebhooksController#create` dispatches the *entire unmodified payload* — including any other, inconsistent `repository` fields — to the registered handlers: [6](#0-5) 

Handlers resolve which `Stack`/`Repository`/`Commit` to act on using a *different* field of the same payload — `repository.full_name` — with no cross-check against `repository.owner.login` (the field used for signature-org selection): [7](#0-6) [8](#0-7) 

The `status` handler is the most severe: it does not scope by repository/organization at all, matching purely on commit SHA across the entire database: [9](#0-8) 

This breaks the trust equality the signature is supposed to enforce: `organization authenticated by signature == organization owning the repository the payload acts on`. Nothing in the request pipeline enforces that equality; the attacker fully controls both sides once they administer any single org whose GitHub App is configured in the same Shipit instance.

### Impact Explanation
An attacker who legitimately administers Organization A's GitHub App integration (and thus genuinely knows Org A's `webhook_secret`, since they configured it when onboarding to a shared/multi-tenant Shipit instance) can forge a `status` event body with any `sha` belonging to a commit tracked under Organization B's stacks. Because `StatusHandler#process` performs `Commit.where(sha: params.sha)` with no organization scoping, this fabricated status is written directly via `commit.create_status_from_github!(params)`, which is the exact code path that also drives continuous deployment: `Status#schedule_continuous_delivery` → `commit.schedule_continuous_delivery` → triggers `ContinuousDeliveryJob` and ultimately `Stack#trigger_deploy` when `continuous_deployment?` is enabled. An attacker outside Org B can therefore inject a fake "success" CI status for a victim commit and cause Shipit to autonomously execute an unauthorized deploy against Org B's infrastructure — this satisfies the Critical "unauthorized deploy" bar. Weaker variants (forged `push`, `check_suite`, `pull_request` events) let the attacker trigger `GithubSyncJob`, review-stack provisioning, or archiving/unarchiving stacks belonging to a repository they do not own.

### Likelihood Explanation
This requires the attacker to be a legitimate administrator of at least one GitHub organization/App integration configured within the same shared Shipit instance — a realistic and explicitly supported deployment topology per `docs/setup.md`'s "Using Multiple Github Applications" section. No compromise of `GITHUB_TOKEN`, `api_clients_secret`, session cookies, or the victim org's own secret is needed; the attacker only needs the secret of an org *they legitimately administer*, and standard HMAC/JSON crafting tools to fabricate the request.

### Recommendation
After `verify_signature` succeeds, cross-check that the `repository.owner.login` (or `organization.login`) used to select the verifying GitHub App actually matches the owner of `repository.full_name` referenced by the handler dispatch, and reject the request otherwise. Additionally, `StatusHandler` (and any other handler that scopes only by SHA) should filter matched `Commit`/`Stack` records by the repository/organization verified in `verify_signature`, not merely by SHA equality across the whole database.

### Proof of Concept
1. Configure/observe a Shipit instance using the multi-org schema (`github: { OrgA: {...}, OrgB: {...} }`), where the attacker legitimately administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
2. Identify a target commit SHA belonging to a repository/stack under `OrgB` tracked by the same Shipit instance (e.g., via the public Shipit UI or `git log` on the public repo).
3. Craft a JSON body:
```json
{"sha": "<OrgB target commit sha>", "state": "success", "context": "ci/travis", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
5. POST to `/github/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the attacker-computed signature.
7. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and finds the `OrgB` commit (no org filter applied), creating a forged "success" status; if `OrgB`'s stack has `continuous_deployment` enabled, this autonomously triggers an unauthorized deploy.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end
