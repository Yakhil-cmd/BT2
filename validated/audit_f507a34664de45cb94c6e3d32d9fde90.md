### Title
Front-runnable/delayable vault `initialize` allows first-depositor share-price manipulation before minimum-liquidity seeding - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The Zest v0 vault contracts expose a public, unprotected `initialize` function whose sole purpose is to seed `MINIMUM-LIQUIDITY` shares to a burn address (`NULL-ADDRESS`) as a defense against the classic ERC4626 first-depositor share-inflation attack. Because `initialize` can be called by anyone at any time (guarded only by a boolean `initialized` flag, exactly analogous to the `zAuction.init()` unprotected-initializer bug class) and there is no barrier preventing `deposit` from being called *before* `initialize`, an attacker can front-run or simply race the deployer's `initialize` call by calling `deposit` first with a minimal amount, becoming the first depositor at a 1:1 share rate, and then donating underlying assets directly to the vault to inflate `total-assets` relative to `total-supply`. Any subsequent legitimate depositor's shares are rounded down (potentially to zero) by `convert-to-shares-preview`, allowing the attacker to redeem a disproportionate share of the pooled assets.

### Finding Description
`initialize` is declared as an ordinary public function guarded only by an `initialized` data-var, with no `tx-sender`/DAO check: [1](#0-0) 

The purpose of `initialize` is to seed `MINIMUM-LIQUIDITY` (u1000) worth of shares to `NULL-ADDRESS`, which is the standard ERC4626 mitigation for the first-depositor inflation attack — permanently locking a base amount of shares so `total-supply` is never zero-to-near-zero when a real user makes the first meaningful deposit.

However, nothing in the vault prevents `deposit` from being invoked before `initialize` runs. The share-conversion logic explicitly special-cases the zero-supply case as a 1:1 mint: [2](#0-1) 

Because `initialize` is unprotected, an attacker monitoring the mempool for the vault's deployment/initialization transaction (or simply racing a slow deployer) can:
1. Call `deposit` directly with a small amount before the deployer's `initialize` transaction lands, receiving shares 1:1 while `total-supply` is still `0`.
2. Transfer/donate a large amount of the underlying asset directly to the vault (inflating `total-assets` via `ubalance`/`assets` var without minting corresponding shares).
3. When the deployer's `initialize` call now executes (or a legitimate user deposits), `convert-to-shares-preview` computes `mul-div-down amount ts ta` with an artificially inflated `ta`, rounding the legitimate depositor's shares down — in the worst case to zero — while the attacker holds shares whose redeemable value has grown by the donated amount.

This is the same root-cause bug class as the report: an initialization routine intended to run exactly once, atomically, and first, is instead a free-for-all public entry point with no ordering guarantee relative to other state-mutating public functions (`deposit`). The victim is any subsequent legitimate depositor into the vault; the shared state is the vault's `total-supply`/`total-assets` ratio consumed by `convert-to-shares-preview`.

### Impact Explanation
Subsequent depositors can have their deposited principal effectively donated to the attacker because their minted shares are rounded down disproportionately to the value they contributed — this is a direct theft of user funds at rest (principal, not merely yield), landing in the **Critical** impact category (direct theft of user funds).

### Likelihood Explanation
The attack requires only a single well-timed `deposit` call ahead of the deployer's `initialize` transaction and a subsequent direct transfer of the underlying asset to the vault — both are ordinary permissionless operations requiring no privileged access, and the attacker only needs to observe the pending `initialize` transaction (or the vault's deployment) in the mempool, mirroring the front-running vector described in the reference report.

### Recommendation
Restrict `initialize` to be callable only by the DAO/deployer (e.g., via `check-dao-auth`) or replace the flag-based one-shot `initialize` pattern with an atomic constructor-equivalent that seeds `MINIMUM-LIQUIDITY` in the same transaction as contract activation, and additionally gate `deposit`/`borrow`/other state-mutating entry points behind the `initialized` flag so no economic activity can occur in the window before minimum liquidity is seeded.

### Proof of Concept
1. Vault contract `v0-vault-stx` is deployed; `initialized` is `false`, `total-supply` is `0`.
2. Attacker observes the deployer's pending `initialize` transaction (or simply acts before it is broadcast) and submits `deposit` with amount `u1` before it is mined; per `convert-to-shares-preview` (lines 308-315) at `ts == u0`, the attacker receives `u1` share 1:1.
3. Attacker transfers a large amount of the underlying token directly into the vault (increasing `assets`/`ubalance` without minting shares).
4. Deployer's `initialize` call (or the next legitimate user's `deposit`) now executes against an inflated `total-assets` and unchanged low `total-supply`; `convert-to-shares-preview` rounds the new depositor's shares down toward zero.
5. Attacker redeems their single share, extracting a proportional (now inflated) share of `total-assets`, capturing the donated/deposited value that legitimate depositors lost.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
