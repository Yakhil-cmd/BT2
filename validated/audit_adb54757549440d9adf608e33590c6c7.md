### Title
`--allow-escape-sequences` globally disables `IOStreams` content sanitization before any file-type check, silently defeating the markdown-render sanitization comment - ([File: pkg/cmd/gist/view/view.go])

### Summary
In `viewRun`, `opts.IO.SetContentSanitization(false)` is invoked unconditionally at line 85 the moment `--allow-escape-sequences` is set, before the gist is even fetched and before the per-file `render()` closure decides whether a file is markdown or raw. Because `iostreams.Untrusted` (`content := iostreams.NewUntrusted(gf.Content)`) derives its sanitization behavior from this same `IOStreams` instance's global state, the markdown branch's `content.String()` call at line 173 loses the sanitization the adjacent comment claims it retains ("its input is sanitized here").

### Finding Description
`viewRun` sets the sanitization flag once, globally, for the entire `IOStreams` used by the command: [1](#0-0) 

This happens before `shared.GetGist` is even called, so it applies indiscriminately to every file in the gist regardless of type. The `render` closure later wraps each file's content in `iostreams.NewUntrusted(gf.Content)` and, for markdown files, feeds `content.String()` straight into `markdown.Render`, relying on an inline comment that claims this path is "sanitized here": [2](#0-1) 

The raw-dump branch further reinforces that the sanitization toggle is meant to be scoped to a specific file/condition — it conditionally calls `SetContentSanitization(false)` again, per-file, only when piping and only for the raw path: [3](#0-2) 

This confirms the design intent was for sanitization to be controlled on a per-content/per-branch basis, but the flag actually lives on the shared `IOStreams` object and is flipped globally and early for `--allow-escape-sequences`, contradicting that intent. A victim who runs `gh gist view --allow-escape-sequences` on a multi-file gist expecting to just unblock viewing one raw file will, according to the code path, have sanitization disabled for the whole invocation — including the markdown-render output path that the code comments assert is independently protected.

### Impact Explanation
If markdown content is rendered without its assumed sanitization guarantee, an attacker who controls gist content (any public gist is attacker-controlled, requiring no privilege) can embed raw terminal escape sequences in a markdown file within a multi-file gist. When a victim uses `--allow-escape-sequences` to view an unrelated raw file in that same gist, the escape sequences in the markdown file could reach the victim's terminal unsanitized, enabling terminal escape-sequence injection (e.g., title-bar spoofing, cursor manipulation, or terminal-emulator-specific exploits) — this falls under the "output sanitization bypass leading to terminal injection" class.

### Likelihood Explanation
Confirming actual exploitability requires verifying that `iostreams.NewUntrusted(...).String()` and `.Raw()`/`.RawBytes()` accessors actually consult the `IOStreams`-level sanitization flag set by `SetContentSanitization` (in `pkg/iostreams/untrusted.go`), which I was unable to fully inspect before running out of tool budget. The control-flow evidence in `view.go` (global flip before file-type branching, plus the redundant per-branch flip in the raw path) strongly suggests the flag is shared/global rather than scoped, but I could not verify the exact implementation of `Untrusted.String()`/`.Raw()` in `pkg/iostreams/untrusted.go` to confirm whether it reads that global state at call time versus capturing it at construction, or whether `markdown.Render`'s output written via `fmt.Fprint(opts.IO.Out, ...)` is itself gated by the same flag on the `Out` writer.

### Recommendation
Scope sanitization control to the specific content/branch that needs it rather than mutating a shared `IOStreams`-level flag. For example, pass an explicit "allow escape sequences" argument into `iostreams.NewUntrusted` per file/branch (only for the raw-dump path when `opts.AllowEscapeSequences` is true), and construct/handle the markdown-rendering content independently so its sanitization state can never be affected by flags intended only for the raw path. Avoid any global, invocation-wide mutable sanitization state on `IOStreams`.
