### Title
Stack-Scoped API Token Can Read CCMenu Build Status For Any Stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` overrides the stack-scoping logic defined in the base API controller, allowing an `ApiClient` token that is authorized for only one stack to fetch build-status data for **any** stack in the installation.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through the `stacks` helper: if the authenticated `ApiClient` has a `stack_id` set, only that stack is visible; the `stack` method used by every other API controller (e.g. `Api::StacksController`) resolves the requested resource through this scoped relation: [1](#0-0) [2](#0-1) 

`Api::CCMenuController`, however, defines its own `stack` method that queries `Stack.from_param!(params[:stack_id])` directly, bypassing the `stacks` scoping relation entirely: [3](#0-2) 

`require_permission :read, :stack` only checks that the `read:stack` permission string is present on the token via `ApiClient#check_permissions!`; it never checks *which* stack the permission applies to: [4](#0-3) 

The binding that should hold is: **stack a token authorizes == stack the request touches**. In `CCMenuController#show`, the left side is enforced (`stack_id` on the `ApiClient` row, checked everywhere else via `stacks`), but the right side is not — `params[:stack_id]` can name any stack in the installation, and `Stack.from_param!` will happily resolve it.

### Impact Explanation
An `ApiClient` deliberately scoped to a single stack (e.g. created via `CCMenuUrlController#client`, which always creates a `stack`-scoped, `read:stack`-only token) can be used to read the CCTray/CCMenu XML for every other stack on the instance — build status (`lastBuildStatus`), activity, last build time/label, and the stack's URL: [5](#0-4) [6](#0-5) 

This is an authorization-scope escalation: a token limited to one stack is used to read state belonging to arbitrary other stacks, matching the "unauthorized read of stack state" category.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped CCMenu token (these tokens are embedded in plain URLs distributed to CI dashboards/build monitors, per `CCMenuUrlController`) can trivially change the `stack_id` segment of the request path to any other stack slug. No additional privileges, secrets, or session are required beyond the token they already legitimately hold for their own stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (as `BaseController#stack` and `Api::StacksController#stack` already do), e.g. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot resolve stacks outside its `stack_id`.

### Proof of Concept
Using the test fixtures already present in the repo (`shipit_api_clients(:here_come_the_walrus)` is scoped to stack `shipit` with only `read:stack` permission):
```ruby
authenticate!(:here_come_the_walrus)   # token scoped to stack "shipit"
get :show, params: { stack_id: Shipit::Stack.where.not(id: shipit_stacks(:shipit).id).first.to_param }
# => 200 OK, returns CCMenu XML build status for a stack the token was never authorized for,
# instead of the 403 that Api::StacksController#show would return for the same token/stack mismatch.
```
Compare with the existing scoping test for `Api::StacksController`, which confirms the intended behavior that a scoped client should only see its own stack: [7](#0-6)
