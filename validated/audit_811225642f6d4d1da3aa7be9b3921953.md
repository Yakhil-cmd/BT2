### Title
Fee payer signature count excluded from MAX_NUM_OF_SIGS admission gate in `TransactionAuthenticator::verify` - (File: types/src/transaction/authenticator.rs)

### Summary
`TransactionAuthenticator::verify` computes `num_sigs` as `sender().number_of_signatures() + secondary_signers().map(number_of_signatures).sum()` and rejects the authenticator if this exceeds `MAX_NUM_OF_SIGS` (32). For the `FeePayer` variant, `fee_payer_signer` is a separate field that is never included in this sum, so an unprivileged submitter can attach an arbitrarily large `AccountAuthenticator` (e.g. a `MultiEd25519` or `MultiKey`/keyless authenticator packed with up to `MAX_NUM_OF_SIGS` signatures, or more if the inner authenticator type itself doesn't cap signature count) as the `fee_payer_signer` while `sender` + `secondary_signers` stay within/at the limit, causing the effective total signature count verified to exceed the intended cap. [3](#0-2) 

### Finding Description
`sender()` and `secondary_signers()` are accessor methods that, for the `FeePayer` variant, return the `sender` and `secondary_signers` fields respectively — `fee_payer_signer` is a distinct field not reachable through either accessor. The `verify` function's admission-gate computation at lines 161-166 therefore structurally cannot see the fee payer's signature count. Even though `fee_payer_signer` still gets cryptographically verified later (lines 211, 219-221), it is verified *after* the signature-count gate has already passed, meaning the CPU-cost bound intended by `MAX_NUM_OF_SIGS` is not actually enforced across all signer roles for `FeePayer` transactions.

### Impact Explanation
This lets an unprivileged transaction submitter (who only needs to be their own sender/fee-payer — no privileged key required) construct a `FeePayer` authenticator where `fee_payer_signer` alone carries up to `MAX_NUM_OF_SIGS` (or more, depending on the concrete `AccountAuthenticator` variant used, e.g. `MultiKey`) signatures, while `sender`+`secondary_signers` are also near the cap, causing the actual verification workload during admission (mempool/vm-validator/VM) to exceed the intended 32-signature bound. This is a scoped, concrete miscount in the admission gate's arithmetic — not merely generic DoS — since it directly violates the documented invariant "Maximum number of signatures supported... across all `AccountAuthenticator`s included."

### Likelihood Explanation
High likelihood of exploitability: constructing a `FeePayer` transaction with a maximal `fee_payer_signer` requires no privileged access — any account can act as its own fee payer, and secondary signers/fee payer signers are populated entirely by the submitter's own client-side transaction-building code before submission. No cryptographic secrets beyond the submitter's own keys are needed.

### Recommendation
Include `fee_payer_signer.number_of_signatures()` in the `num_sigs` computation for the `FeePayer` variant, e.g.:
```rust
let num_sigs: usize = self.sender().number_of_signatures()
    + self.secondary_signers().iter().map(|a| a.number_of_signatures()).sum::<usize>()
    + self.fee_payer_signer().map(|a| a.number_of_signatures()).unwrap_or(0);
```
This requires adding an accessor for `fee_payer_signer` (analogous to `sender()`/`secondary_signers()`) and including it uniformly in the bound check so `MAX_NUM_OF_SIGS` applies to the total across all signer roles.

### Proof of Concept
1. Build a `RawTransaction` `raw_txn` for account `A`.
2. Construct `fee_payer_signer = AccountAuthenticator::multi_ed25519(pk, sig)` where the underlying `MultiEd25519Signature`/`MultiEd25519PublicKey` encodes 32 sub-signatures (i.e., `number_of_signatures() == 32`).
3. Set `sender` to a simple `AccountAuthenticator::ed25519(...)` (`number_of_signatures() == 1`) and `secondary_signers` empty.
4. Build `TransactionAuthenticator::FeePayer { sender, secondary_signer_addresses: vec![], secondary_signers: vec![], fee_payer_address: A, fee_payer_signer }`.
5. Call `authenticator.verify(&raw_txn)`. Expected (per the `MAX_NUM_OF_SIGS` invariant, since total real signatures = 1 + 32 = 33 > 32): should be rejected with `AuthenticationError::MaxSignaturesExceeded`. Actual: `num_sigs` computed as `1 + 0 = 1`, gate passes, and verification proceeds to fully validate the 32-signature `fee_payer_signer`, consuming disproportionate CPU relative to what the admission gate believes it authorized.
