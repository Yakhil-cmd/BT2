This confirms the mechanism precisely: when the AA lacks enough balance of a capped asset, `issueAsset()` is invoked, and for `objAsset.cap` assets it checks `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` — if that asset was ever issued before, it returns `'already issued'` [1](#0-0)  which propagates up to `return cb('not enough funds for ' + target_amount + ' of asset ' + asset)` [2](#0-1) , causing the whole response unit to bounce via `bounce(err)` [3](#0-2) .

### Title
Capped/unique-asset bounty AAs can be permanently bricked by a self-front-run issuance, denying payout to legitimate claimants who already did off-chain work - ([File: aa_composer.js])

### Summary
An AA (Autonomous Agent) that pays out a capped, quantity-limited asset (`cap` set on the `asset` message, functionally equivalent to an NFT — a single, non-fungible unit) as a bounty/reward for off-chain work can be rendered permanently non-functional. The AA definer (who is an "asset issuer"/AA author, an unprivileged actor from the protocol's point of view) can trigger the AA themselves first, causing the one-time issuance of the capped asset to be consumed. Every subsequent, legitimate claim trigger that reaches the same payment message will fail with `"already issued"`, causing the whole AA response unit to bounce, exactly mirroring the OpenQ bug where an NFT deposited-then-refunded causes every subsequent claim to revert.

### Finding Description
When an AA's oscript issues payment messages referencing an asset it doesn't currently hold enough of, `sendUnit`'s inner `completePaymentPayload` first looks for existing unspent outputs owned by the AA (`readStableOutputs`/`readUnstableOutputsSentByAAs`), and only if none are found does it call `issueAsset()` [4](#0-3) .

`issueAsset()` handles capped assets specially: because a capped asset can only ever be issued once in the entire lifetime of the asset, it queries `inputs` for any prior `type='issue'` row for that asset, and if one exists, it unconditionally fails with `'already issued'`, with no way to distinguish "issued by a legitimate claim we should have paid out" from "issued by an attacker front-running their own bounty" [1](#0-0) .

This failure is not scoped to a single output/claim — it aborts the entire outgoing message batch for the trigger via `cb('not enough funds ...')` → `bounce(err)` [2](#0-1) [5](#0-4) , discarding all state changes for that response (`objStateUpdate = null` and state var/balance rollback in `bounce()`).

An AA author (acting as a malicious "bounty poster", directly analogous to the OpenQ issuer) can define a bounty AA whose `messages` pay a capped, cap=1 asset (the NFT-like reward) to `trigger.address` when a claim condition is met (e.g. `trigger.data.claim_id` matches an expected proof). Because the trigger condition is satisfiable by anyone who submits the right `data`, and the payout asset is capped, the attacker can:
1. Fund the AA with attractive bytes/other-asset rewards and a long-running claim window.
2. Submit a trigger themselves (or via a colluding address) that satisfies the claim condition trivially/early, causing the AA to self-issue and immediately consume the single unit of the capped reward asset — analogous to depositing then refunding the NFT in OpenQ.
3. Any subsequent trigger from a genuine claimant — who has already completed real off-chain work (e.g., a GitHub PR, as in the OpenQ scenario, or any equivalent off-chain deliverable required by `trigger.data`) — reaches the same payment message, finds the AA's balance of that asset at 0, attempts to re-issue, hits `"already issued"`, and the entire response bounces.
4. The victim's payout (including any bundled bytes/other assets in the same message batch) is lost; the AA is now permanently unable to fulfill the advertised bounty for this asset for any future claimant.

This is architecturally the same root cause as the OpenQ bug: the code that pays out a unique/limited-supply reward has no way to verify, at claim time, that the reward is genuinely available to the claimant who did the work — the reward's availability was silently and irrevocably consumed earlier by the (malicious) party who controls the trigger conditions.

### Impact Explanation
Legitimate claimants are induced to perform real off-chain work expecting payment from a specific AA/bounty, but every subsequent claim after the attacker's self-triggered consumption permanently bounces, with the AA unable to ever issue the promised capped reward again (capped assets are issue-once for the lifetime of the asset, enforced at `aa_composer.js:1196`). This is a fund-loss/asset-freezing condition for legitimate users and a denial-of-service for the AA's core payout feature — matching a "High" severity classification, consistent with the original report's rationale that victims are effectively robbed of already-completed off-chain work.

### Likelihood Explanation
The AA definer is inherently the party best positioned to also control (or collude with) an address that triggers the AA first — no special privilege or race condition against other nodes is required, since capped-asset issuance is a simple SQL check on the AA's own `inputs` history, deterministic and not subject to network races. Any AA design that pays a capped/limited asset as a reward for a data-triggered condition is vulnerable, and this pattern (unique-token payouts, lottery/raffle prizes, one-of-a-kind collectible rewards) is a natural and encouraged use case of oscript's `asset` message with `cap`.

### Recommendation
- AA authors should avoid relying on "cap-then-issue-on-demand" semantics for security-critical, one-time reward payouts triggered by external data; instead they should issue the capped asset once (e.g., at AA definition/initialization) into the AA's own balance and pay it out from that pre-existing balance, so a `"not enough funds"` bounce (rather than "already issued" specifically) is guaranteed to reflect genuine unavailability, and, more importantly, defenders should be aware that unlimited-issue conditions defined purely in terms of `trigger.data` matching are trivially self-triggerable by the AA author.
- Consider a protocol-level safeguard/documentation warning in `aa_composer.js`'s `issueAsset()` (`aa_composer.js:1175-1212`) and in AA-authoring guidance that flags this "self-front-run capped issuance" pattern, since the current behavior silently and permanently exhausts a capped asset's supply on the first trigger that reaches the issuing payment message, regardless of who triggered it.

### Proof of Concept
1. Define AA `Bounty` with an `asset` message issuing a `cap: 1` reward asset at definition/init time (or on first qualifying trigger), and a payout branch: `if: "{trigger.data.solution == $expected_hash}", messages: [{app:'payment', payload:{asset:"{var['reward_asset']}", outputs:[{address:"{trigger.address}", amount:1}]}}]`.
2. Attacker (the AA's own definer) submits a trigger from an address they control with `trigger.data.solution` equal to `$expected_hash` (which they know since they wrote the AA) before publishing the bounty/claim widely. This is the first trigger that reaches the payment message; `issueAsset()` at `aa_composer.js:1195-1201` succeeds (no prior `type='issue'` row exists yet) and mints/sends the single unit of the capped asset to the attacker's own address.
3. A genuine solver later finds/derives the real solution through legitimate off-chain effort and submits a trigger with the correct `trigger.data.solution`.
4. `completePaymentPayload` finds zero unspent output of the reward asset owned by the AA, calls `issueAsset()` again, which now finds the prior issue row and returns `'already issued'` (`aa_composer.js:1196-1198`), causing `cb('not enough funds for ... of asset ...')` (`aa_composer.js:1239`) and `bounce(err)` (`aa_composer.js:944`/`1348`), rolling back any bundled bytes reward and the "claimed" state update.
5. The genuine solver receives nothing despite having done the required off-chain work, and the AA can never pay out this reward asset to anyone else again.
