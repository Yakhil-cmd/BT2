### Title
`StatusHandler#process` resolves commits by bare SHA with no repository scoping, letting a foreign repo's status webhook forge `Commit#deployable?` for an unrelated stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` across the entire `commits` table with no filter tying the match back to the webhook's own `repository.full_name`, unlike every other handler (`PushHandler`, `PullRequest::*Handler`) which scope through `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`). Any commit sharing that SHA in a different, unrelated stack (e.g. a fork sharing git history with the target repo) receives a `Status` row, which feeds directly into `Commit#deployable?` and thus the API's `require_ci` safety check.

### Finding Description
The broken binding: for a `status` webhook whose payload's `repository.full_name` is repo A, the equality that must hold is `commit.stack.repository.full_name == repository_name_from_payload` for every `commit` that gets a new `Status` created. In `StatusHandler#process`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

there is no use of the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers rely on to scope work to the webhook's own repository: [2](#0-1) [3](#0-2) 

`Status.replicate_from_github!` uses `commit.stack_id` (the commit's real owning stack), so the created `Status` is correctly attributed to the matched commit's actual stack - but the *matching* itself is done purely on `sha`, ignoring which repository originated the webhook: [4](#0-3) [5](#0-4) 

This status then determines `Commit#deployable?`:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [6](#0-5) 

which is exactly what `Api::DeploysController#create` consults for its `require_ci` safety gate:
```ruby
param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?
...
deploy = stack.trigger_deploy(commit, current_user, ...)
``` [7](#0-6) 

**Exploit path:** An attacker who has (or self-registers, where Shipit supports self-service stack creation) their own GitHub repository/fork A tracked as a Shipit stack has a legitimate `GithubHook` with its own organization-scoped webhook secret. If repo A shares git history with target repo B (e.g. A is a fork of B, or simply contains a commit whose SHA happens to already exist as an undeployed commit in B), the attacker can set a `success` commit status on that shared SHA within their *own* repo A (using their own GitHub permissions - no privilege over B needed). GitHub signs and delivers this webhook using repo A's own organization's `webhook_secret`, so `WebhooksController#verify_signature` passes legitimately (it validates only that the signature matches the org named in the payload, `Shipit.github(organization: repository_owner)`, not that the org/repo has any relationship to any specific target stack): [8](#0-7) 

`StatusHandler#process` then finds the commit row with that SHA belonging to stack B and writes a `success` `Status` against it - with no check that the payload's `repository.full_name` matches stack B's repository. `commit.deployable?` for the stack-B commit now returns `true`, and a subsequent `POST /api/stacks/B/deploys` with `require_ci: true` passes the check and calls `stack.trigger_deploy`, ultimately reaching `Command#start`/`PTY.spawn` via `lib/shipit/stack_commands.rb`.

Existing guards do not stop this: `verify_signature` only proves the payload was really sent by GitHub for *some* org that owns a `GithubHook` (repo A's org) - it says nothing about repo B; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`/`state`/etc., not repository ownership; there is no `Repository`/stack-relationship check anywhere in `StatusHandler#process`.

### Impact Explanation
This is an authentication/authorization bypass: the CI-success signal that a real, holder-of-a-legitimate-but-restricted `ApiClient` token relies on (via `require_ci: true`) can be forged by a completely unrelated, unprivileged party controlling a different repository. It results in `Stack#trigger_deploy` executing real deploy commands (`Command#start`/`PTY.spawn`) for code that never passed stack B's actual CI, i.e., an unauthorized deploy triggered on a target repository using a webhook scoped to an unrelated repository - matching the "Critical" category ("a payload for one repository mutating another's stack/commit ... an unauthorized deploy"). It is repeatable against any pair of stacks that ever share a commit SHA (most commonly forks/mirrors, but also any commit whose SHA is echoed via `sha` string collision or shared history), and each repetition can flip `deployable?` for one target commit per forged status.

### Likelihood Explanation
Preconditions: (1) attacker needs at least one repository tracked by Shipit with its own configured `GithubHook`/webhook secret (self-service stack registration or an existing stack they control satisfies this - no membership in `Shipit.github_teams` or maintainer role on the *target* repo B is required); (2) a commit SHA collision/overlap between the attacker's repo and the target stack's repo, which is trivially achievable via forking the target repo (shared ancestry commits share SHAs) or by using an old/shared SHA already present as an undeployed commit on stack B. Attacker cost is low: create/own a repo, set a commit status via the standard GitHub API on their own repo, then call the public deploy API with a valid (even narrowly-scoped) `ApiClient` token. No Shipit secrets, GitHub App keys, or elevated roles are needed.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`PullRequest*Handler`: resolve the target stack(s) via `Repository.from_github_repo_name(repository_name)` (i.e., use the inherited `stacks` helper) and restrict the `Commit.where(sha: ...)` lookup to `stacks.commits` (or filter matched commits by `commit.stack.repository.full_name == repository_name`) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not create a status for a commit belonging to an unrelated stack sharing the same sha" do
  stack_a = shipit_stacks(:cyclimse) # attacker-controlled/attacker-owned repo tracked as a Shipit stack
  stack_b = shipit_stacks(:shipit)   # unrelated target stack

  shared_sha = "a" * 40
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared history commit")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => stack_a.repository.owner } }
  }

  # Equality that must hold: commit.stack.repository.full_name == payload['repository']['full_name']
  refute_equal commit_b.stack.repository.full_name, payload['repository']['full_name']

  assert_no_difference -> { commit_b.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  refute commit_b.reload.deployable?
end
```

```ruby
# test/controllers/api/deploys_controller_test.rb
test "#create rejects require_ci deploy when commit's deployable? was set via a forged cross-repo status webhook" do
  stack_b = shipit_stacks(:shipit)
  commit_b = stack_b.commits.create!(sha: "b" * 40, message: "undeployed on B")
  refute commit_b.deployable?

  # Simulate the forged webhook path directly through the handler (unit-level proof of the binding break)
  forged_payload = {
    'sha' => commit_b.sha,
    'state' => 'success',
    'context' => 'ci/attacker-repo',
    'repository' => { 'full_name' => 'attacker/unrelated-fork', 'owner' => { 'login' => 'attacker' } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  # Expected (fixed) behavior: still not deployable, sha belongs to a different repo
  refute commit_b.reload.deployable?

  post :create, params: { stack_id: stack_b.to_param, sha: commit_b.sha, require_ci: true }
  assert_response :unprocessable_entity
end
```

If `StatusHandler#process` is left unpatched, the first test's `assert_no_difference` fails (a `Status` is created) and `commit_b.deployable?` becomes `true`, causing the second test's final `post :create` to return `202 Accepted` instead of `422`.
