### Title
Unbounded `eventBus` listener accumulation in private-payment-chain handling leads to memory exhaustion - (File: wallet.js)

### Summary
The EVerest CVE stems from a handler that, on every incoming session-establishing request, allocates new per-request state (`Session`, `IConnection`, file descriptors) without ever releasing the state from the previous request, causing unbounded resource growth until the process runs out of descriptors/memory. `wallet.js`'s `handlePrivatePaymentChains()` has an analogous pattern: every private-payment-chain message from a paired correspondent that ends up in the "queued/waiting" state permanently registers a one-shot `eventBus` listener keyed by unit/payload hash, and nothing guarantees that key is ever emitted, so the listener (and the closure state it retains) is never released.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` [1](#0-0)  iterates over `body.chains` (attacker-controlled, arriving from a paired correspondent device via `subject: "private_payment_chains"`) and, for each chain, calls `network.handleOnlinePrivatePayment`. This registers `eventBus.once(key, ...)` where `key` is derived from the unit hash, payload hash and output index of the head element of the chain [3](#0-2) . That listener is only ever removed in two ways: (1) the corresponding `key` event fires later when `handleSavedPrivatePayments` in `network.js` finishes validating the underlying unit/chain [4](#0-3) , or (2) `cancelAllKeys()` is invoked if a *different* chain in the *same* batch fails [5](#0-4) .

Crucially, `unit` is attacker-supplied and does not need to correspond to a unit that actually exists or will ever be delivered. A sender can craft `body.chains` referencing a non-existent (or never-to-be-downloaded) `unit`/`payload_hash` combination; `handleOnlinePrivatePayment` will store the payment in `unhandled_private_payments` and return `ifQueued` (light client path) [6](#0-5) , but if the referenced unit is never retrieved (e.g. `requestNewMissingJoints`/`rerequestLostJointsOfPrivatePayments` never succeed, or the "cleanBadSavedPrivatePayments" full-node cleanup — which itself doesn't run on light clients/never fires the event) the `key` event is never emitted. The `eventBus.once` listener therefore lives forever, retaining the closure (`assocValidatedByKey`, `cb`, `from_address`, `arrChains`, etc.) for the lifetime of the process.

There is also a low, static cap on `EventEmitter` listeners (`eventEmitter.setMaxListeners(40)` in `event_bus.js`) [7](#0-6) , which does not prevent registration — Node only logs a `MaxListenersExceededWarning` — so nothing structurally stops unbounded growth of dangling listeners as more distinct fake chains are sent.

This mirrors the CVE's root cause class: state objects (here, `eventBus.once` closures instead of `Session`/`IConnection` objects) are created per incoming request/message and never destroyed/reclaimed if the expected completion event doesn't happen, letting an unprivileged remote party (any paired correspondent, or the hub relaying such a message) accumulate leaked state indefinitely.

### Impact Explanation
A single paired correspondent (or a hub relaying crafted device messages on its behalf) can repeatedly send `private_payment_chains` messages containing chains that reference fabricated, never-resolvable head units. Each such message permanently leaks one `eventBus.once` listener plus its retained closure (chain arrays, callback references) for a light-wallet node. Repeated over time this grows heap usage without bound, eventually exhausting process memory and causing a crash — a denial of service consistent with CWE-401/CWE-772 (missing resource release), matching the CVE's classification (`AC:L/PR:N/UI:N ... A:H`).

### Likelihood Explanation
The `private_payment_chains` message path is reachable by any paired device correspondent without requiring any privileged access, and light wallet clients (the majority of end-user Obyte/ocore wallets) exercise the `ifQueued` branch as their normal code path, since the chain elements are rarely already locally verified. Producing chains that will never resolve (bogus `unit` hashes, or units that are never propagated to the victim) is straightforward for the sending correspondent, making the leak trivially and repeatably triggerable.

### Recommendation
- Track outstanding `eventBus.once(key, …)` registrations in a map together with a timeout; if the corresponding validation event doesn't fire within a bounded period, explicitly call `eventBus.removeListener(key, handler)` and reject/expire the pending private payment (mirroring the existing `unhandled_private_payments` cleanup already done for full nodes in `cleanBadSavedPrivatePayments`, but also applied for light clients and tied to listener cleanup).
- Cap the number of concurrently pending/queued private-payment validations per correspondent, rejecting excess chains instead of registering unbounded listeners.
- Consider replacing the ad hoc `eventBus.once(key, …)` pattern with a dedicated pending-request registry that supports explicit cancellation/expiry, rather than relying solely on the event being emitted from a separate code path.

### Proof of Concept
1. Pair a malicious device with the victim's light wallet (normal pairing flow via `device.handlePairingMessage`).
2. From the malicious device, send repeated `private_payment_chains` messages, each with a `body.chains` array whose single chain has a distinct, syntactically valid but non-existent `unit` value (and correspondingly fabricated `payload`/`inputs`/`outputs` satisfying the shape check in `handlePrivatePaymentChains`) so it passes the structural validation.
3. Each message causes `network.handleOnlinePrivatePayment` to store the record in `unhandled_private_payments` and call `ifQueued`, and `wallet.js` registers a new permanent `eventBus.once(key, …)` listener for a `unit` that will never be found/downloaded.
4. Repeat with new fabricated units; observe unbounded growth of `eventBus`'s internal listener array and retained closures over time (heap growth, eventually `MaxListenersExceededWarning` and continued memory growth until OOM/crash).
