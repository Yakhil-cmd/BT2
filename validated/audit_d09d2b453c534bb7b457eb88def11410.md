### Title
Signature verification binds trust to `repository.owner.login`, but every webhook handler resolves the target `Stack`/`Repository` from the unauthenticated `repository.full_name` field, allowing a legitimate multi-tenant organization to forge webhook events for another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the same untrusted JSON body being verified. Once verification passes, every `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Stack`/`Repository` to act on using a *different* field from that same body: `repository.full_name`. Because Shipit supports multiple onboarded GitHub organizations sharing one instance (`Shipit.github(organization:)` / `github_app_config`), an organization that legitimately controls its own `webhook_secret` can sign an arbitrary payload where `repository.owner.login` names its own org (to pass signature verification) while `repository.full_name` names a completely different, victim organization's repository (to select which `Stack` is mutated).

### Finding Description
The controller derives the verification key purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`app_id`, `webhook_secret`, etc.) via `github_app_config`, supporting a multi-tenant deployment where several distinct GitHub organizations are onboarded to one Shipit instance: [3](#0-2) 

`verify_webhook_signature` only checks that the HMAC over the raw body matches the secret for whichever organization was named in `repository.owner.login`: [4](#0-3) 

After verification succeeds, every handler resolves the target repository/stacks from a *separate* field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated via repository.owner.login` (used to pick the secret/App) `== organization that owns the repository.full_name` (used to select the `Stack`/`Repository` mutated).

Because the entire raw JSON body is attacker-crafted (this is a direct HTTP POST to `/webhooks`, not something GitHub guarantees internal consistency for), an org that legitimately owns its own `webhook_secret` can set `repository.owner.login = "their-org"` and `repository.full_name = "victim-org/victim-repo"` in the same signed body. The signature only proves "signed by an org onboarded to this Shipit instance," not "this payload concerns that org's own repository."

### Impact Explanation
This is a High-severity cross-tenant/cross-repository write:
- `PushHandler` calls `stack.sync_github(expected_head_sha:)` on the victim's stacks, forging pushes.
- `StatusHandler` calls `commit.create_status_from_github!`, which creates a `Status` record; through `Commit#add_status` this can flip a commit to `success`, and `Status#schedule_continuous_delivery` / `stack.schedule_merges` can trigger continuous-delivery deploy scheduling and unblock the merge queue for a commit the attacker does not own: [8](#0-7) [9](#0-8) 
- `PullRequest` handlers can archive/unarchive review stacks and mutate `PullRequest` records tied to the victim's repository.

None of this requires a Shipit session, `ApiClient` token, `api_clients_secret`, a GitHub App private key, or repository write access on GitHub for the *victim* repo - only possession of the attacker's own `webhook_secret` for their own onboarded organization, which is a normal, low-privilege credential for any org admin who has legitimately set up a webhook/App against this shared Shipit instance.

### Likelihood Explanation
Requires: (1) the deployment configures more than one organization under `secrets.github` (a supported, documented multi-tenant configuration path via `github_app_config`), and (2) the attacker controls one legitimate onboarded org's `webhook_secret`. Given that condition, exploitation is a single crafted POST with no further access needed - likelihood is Medium-to-High wherever multi-org configuration is used, and not applicable to single-org deployments (`github_default_organization.nil?`).

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after verifying the HMAC, cross-validate that the organization used to select the signing secret (`repository.owner.login` / `organization.login`) matches the organization implied by `repository.full_name` before dispatching to handlers. Reject the webhook (422) on mismatch.

### Proof of Concept
Given a Shipit instance configured with two onboarded organizations, `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), unknown to the attacker:

1. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC_SHA1(S_A, body)>` using their own known `S_A`.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `S_A`.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: "deadbeef")` on the victim's stack, despite the attacker never having authenticated as `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
