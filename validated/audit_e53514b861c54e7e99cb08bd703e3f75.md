### Title
Webhook signature verified against the org derived from `repository.owner.login`, but handlers act on the attacker-controlled `repository.full_name` — cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using a value taken directly out of the untrusted JSON body (`repository.owner.login` or `organization.login`), and only checks that *some* secret configured for that claimed org validates the raw POST body. Every downstream `Shipit::Webhooks::Handlers::Handler` then looks up the `Stack`/`Repository` to mutate using a *different* field of that same untrusted body — `repository.full_name` — with no re-check that this repository actually belongs to the organization whose secret was used to authenticate the request. This is the same class of bug as the reported `PythPriceFeedUpdate` issue: a field that drives privileged behaviour (`repository.full_name`, used to select the stack that gets synced/archived/provisioned) is never bound to the trust anchor (the organization secret) that is supposed to authorize the request.

### Finding Description
`verify_signature` computes `repository_owner` purely from request JSON and uses it to fetch the corresponding `GithubApp`/secret: [1](#0-0) 

`repository_owner` itself is taken from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`: [2](#0-1) 

`verify_webhook_signature` then confirms that the raw body's HMAC matches the secret configured for *that claimed org*: [3](#0-2) 

Because HMAC verification only proves "whoever built this exact byte stream knows organization X's `webhook_secret`," and Shipit supports multiple independently configured organizations each with their own `webhook_secret` (see `config/secrets.development.shopify.yml`), a person with legitimate control over their own organization's GitHub App installation (i.e., knowledge of *their own* `webhook_secret`) can freely construct the JSON body, including the `repository` object used by handlers. `repository.owner.login` (used only for auth) and `repository.full_name` (used for the actual DB lookup) are two independent, attacker-supplied fields inside the same signed blob — nothing forces `repository.full_name`'s owner segment to equal `repository_owner`.

Every handler resolves the target `Repository`/`Stack` from `repository.full_name`: [4](#0-3) 

For example, `PushHandler` uses this resolved `stacks` scope to trigger a GitHub sync (which updates commit history, potentially triggers continuous deployment): [5](#0-4) 

Other handlers use it to archive/unarchive/provision review stacks belonging to *any* repository, e.g. `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`: [6](#0-5) [7](#0-6) 

So the equality that should hold — "organization that authenticated the webhook == owner of the repository that gets mutated" — is never enforced. Before the attack: a webhook is only accepted and acted upon if it was actually signed by the org that owns the target repo. After the attack: any org configured in the multi-tenant Shipit instance can sign an arbitrary payload naming a *different* organization's repository in `repository.full_name`, and Shipit will process it as if GitHub had sent it for that other repository, causing writes (`stack.sync_github`, `stack.archive!`, `stack.unarchive!`, `Team`/`Membership`/`User` creation via the `membership` event, etc.) against a repository/stack the attacker does not control.

### Impact Explanation
This is a cross-repository/cross-tenant write: an org admin who only controls their own organization's GitHub App webhook secret can force Shipit to sync, archive, unarchive, or otherwise mutate the state of stacks belonging to a completely different, unrelated repository/organization also hosted on the same Shipit instance, by simply setting `repository.full_name` in the forged payload to the victim's repo. This satisfies the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Exploitation requires only that the attacker control (or be granted) one organization's webhook secret in a Shipit deployment that serves multiple organizations/tenants — a routine, low-privilege scenario for any Shipit instance shared across teams/orgs, and far less privileged than needing GitHub write access to the victim repository itself. No signature forgery, key compromise, or MITM is needed — the attacker legitimately possesses a valid secret, just not for the repository they target.

### Recommendation
After `verify_signature` succeeds, re-derive the repository owner strictly from `repository.full_name` (or whichever field a handler will use for lookups) and assert it matches the `repository_owner`/`organization` value used to select the verifying secret. Reject the request (422) if they diverge, rather than trusting the two independent fields to agree.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `orgA` and `orgB`, each with a distinct `github.webhook_secret` (as in `config/secrets.development.shopify.yml`), and with `orgB/victim-repo` set up as a tracked `Repository`/`Stack`.
2. As a legitimate owner/admin of `orgA`'s GitHub App, craft a `push` event JSON body: set `repository.owner.login` to `"orgA"` (so `verify_signature` picks `orgA`'s secret) but set `repository.full_name` to `"orgB/victim-repo"`.
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` and POST it to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` passes because the signature matches `orgA`'s secret for this exact body. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(...)` — mutating `orgB`'s stack despite the request only having been authenticated as coming from `orgA`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
