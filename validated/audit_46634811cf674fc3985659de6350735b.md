## Analysis

This maps to the report's bug class: a value used for authorization (`agentBalance`) differs from the value actually acted upon (`record.shares`). The equivalent binding in Shipit is: **the organization whose webhook secret authenticates the request (`repository.owner.login`)** vs **the repository that the handler actually acts on (`repository.full_name`)**. These two payload fields are never cross-checked, even though both are inside the same signed raw body.

### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon repository is taken from an unvalidated `repository.full_name` field, allowing cross-organization CI status/sync forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate a webhook's HMAC using `repository.owner.login` (or `organization.login`), but the handler that actually mutates state (`StatusHandler`, `PushHandler`, etc.) resolves its target `Repository`/`Stack` from the independent, unauthenticated `repository.full_name` field of the same JSON body. In a multi-organization Shipit deployment (`Shipit.github_organizations`, distinct per-org `webhook_secret`s), an attacker who knows (or can trigger) a valid signature for organization A can set `repository.owner.login = "org-A"` while setting `repository.full_name = "org-B/victim-repo"`, forging an event against a stack belonging to a completely different, unauthenticated organization.

### Finding Description
The equality that should hold is: `organization authenticated by verify_signature == organization of the repository actually written to by the handler`. Concretely, the check computes `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login')` [2](#0-1) , and validates the raw body's HMAC against that org's `webhook_secret` [8](#0-7) . Once verification passes, `Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked with the raw, unvalidated `params` [9](#0-8) . Every concrete handler resolves its target repository via `Handler#stacks`, which reads `payload.dig('repository', 'full_name')` — a completely separate string, never cross-checked against `repository.owner.login` [4](#0-3) , then looks it up with `Repository.from_github_repo_name` which just splits on `/` [5](#0-4) .

Because the HMAC covers the entire raw body (including both fields), the signature *is* cryptographically valid — but it only proves the payload came from someone possessing organization A's secret, not that organization A's owner matches the `full_name`'s owner. Nothing in `verify_signature` or in the handlers enforces `repository.full_name.split('/').first == repository.owner.login`.

### Impact Explanation
This breaks the deployment-trust boundary between separately-configured GitHub organizations in a multi-org Shipit install:
- `StatusHandler#process` matches commits purely by `sha` across the whole database and creates a CI status from attacker-controlled `state`/`description`/`target_url` [6](#0-5) . An attacker holding org A's webhook secret can mark any known commit `sha` belonging to org B's stack as `state: "success"`, satisfying required-status-check gating and enabling an **unauthorized deploy**.
- `PushHandler#process` can force `stack.sync_github(expected_head_sha:)` on org B's stacks using an attacker-chosen `after` sha [7](#0-6) , interfering with sync state of a repository the attacker does not own.

This matches the "High" impact bucket (escalation across authorization boundaries / unauthorized deploy), reachable by an unprivileged external attacker who only needs to control (or possess) the webhook secret for any single organization configured on the same Shipit instance — no Shipit session or `ApiClient` token is required.

### Likelihood Explanation
High: exploitation only requires the ability to know/derive one organization's webhook_secret configured on the instance (e.g. because the attacker administers a GitHub App/repo under org A and can read its own webhook secret, or because `webhook_secret` is blank for org A, in which case `verify_webhook_signature` returns `true` unconditionally regardless of signature — see `return true unless webhook_secret` at `lib/shipit/github_app.rb`) and send a single crafted POST to `/webhooks` with mismatched `repository.owner.login` / `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#stacks`), enforce that the organization used to select the signing key equals the owner segment of `repository.full_name` (and of `organization.login` when present), rejecting the webhook with `422` if they diverge:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified && repository_owner_matches_full_name?
end
```

### Proof of Concept
1. Deploy Shipit with two organizations configured, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`) [10](#0-9) .
2. Attacker knows/derives `webhook_secret` for `org-A` (owns a repo there / installed the app themselves).
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim-commit-sha-in-org-B>",
  "state": "success",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` HMAC-SHA1 of the raw body using `org-A`'s secret and POSTs to `/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "org-A")` and validates successfully against `org-A`'s secret.
6. `StatusHandler#process` matches the commit belonging to `org-B/victim-repo` purely by `sha` and creates a `success` status for it, despite the request never being authenticated by `org-B`'s credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
