### Title
Use-after-free-style cache corruption from concurrent AA dry-run trigger execution racing real AA trigger stabilization - ([File: aa_composer.js])

### Summary
`aa_composer.dryRunPrimaryAATrigger` mutates the shared, process-global in-memory unit cache (`storage.assocUnstableUnits`, `assocBestChildren`, etc.) via `handleTrigger`/`revertResponsesInCaches`/`storage.forgetUnit`, but unlike the real trigger-execution path it does not take any of the mutex keys (`aa_triggers`, `write`, `handleJoint`) that serialize access to those structures. Any unprivileged unit that posts a payment to an AA address can cause a dry run to be scheduled from `network.js`, running concurrently with genuine `handleAATriggers()`/`handleTrigger()` executions that mutate the very same shared objects, analogous to the CVE's race between an async, lock-free commit path and a concurrently running teardown/mutation path on shared state.

### Finding Description
`network.js`'s `handleJoint` `ifOk` callback, on receiving *any* newly-validated non-ball unit that targets an AA address, triggers a dry run when `conf.bDryRunNewTriggers` is enabled: [1](#0-0) 

This call happens for every unit an unprivileged poster submits to an AA address, before `writer.saveJoint` and before the `validation_unlock`/outer `mutex.lock(['handleJoint'])` is released: [2](#0-1) 

`dryRunPrimaryAATrigger` takes its own independent DB connection/transaction and invokes `handleTrigger` directly, without acquiring `mutex.lock(['aa_triggers'])`, `mutex.lock(['write'])`, or `mutex.lock(['handleJoint'])`: [3](#0-2) 

Inside `handleTrigger`, on rollback/bounce it calls `revertResponsesInCaches`, which directly deletes shared in-memory unit objects via `storage.forgetUnit` and adjusts parent linkage via `storage.fixIsFreeAfterForgettingUnit`: [4](#0-3) [5](#0-4) 

`storage.forgetUnit` mutates the globally shared `assocUnstableUnits`, `assocBestChildren`, `assocCachedUnits`, etc., and is not designed to be reentrant/concurrent — it walks `assocBestChildren[parent_unit]` arrays and prunes entries by object identity: [6](#0-5) 

Meanwhile, the *authoritative* AA-trigger execution path (`handleAATriggers` → `handlePrimaryAATrigger` → `handleTrigger`) is properly serialized under `mutex.lock(['aa_triggers'])`, and further wrapped by `mutex.lock(['handleJoint'])` when it runs from `writer.saveJoint`'s post-stabilization step: [7](#0-6) [8](#0-7) 

Because the dry-run path bypasses these locks entirely while touching the same global maps that the locked, authoritative path also mutates (adding/forgetting in-memory unit-props objects, splicing `assocBestChildren` arrays, flipping `is_free`), two logically independent async flows — one attacker-triggered dry run, one legitimate stabilization-driven trigger execution — can interleave arbitrarily on Node's single event loop across their `await`/callback boundaries (both paths span multiple DB round-trips and callback continuations). This is the direct analog of the kernel bug class: a "nonblocking" (lock-free) commit-like operation racing a privileged teardown/mutation operation on the same live object graph, corrupting or referencing already-forgotten in-memory objects (e.g. `assocBestChildren[parent_unit]` entries pointing to props objects that a concurrently running `forgetUnit` already deleted, or `fixIsFreeAfterForgettingUnit` flipping `is_free` on a parent that the real trigger path is simultaneously reading/writing).

### Impact Explanation
Corruption of `storage.assocUnstableUnits`/`assocBestChildren`/`is_free` flags is exactly the shared consensus-critical state used by `main_chain.js` to compute best-parent chains, stability, and the AA-trigger set for main-chain-index stabilization. A corrupted or stale in-memory cache diverging from the DB is guarded elsewhere by hard `throw Error` consistency checks (e.g. `storage.js:1547-1550`, `main_chain.js:114-115`), meaning the practical outcome of a hit race is most likely a node crash (denial of the local node's ability to process/confirm further units) rather than silent invalid state — but a crash mid-stabilization/mid-AA-trigger-execution can also leave that node unable to reach the same stability/validity conclusions as peers who didn't crash, i.e., node disagreement on validity/stability for units affecting AA responses and their descendant units, satisfying the "network unable to confirm new units" / "node disagreement" impact bar.

### Likelihood Explanation
Reachability is trivial and fully unprivileged: any unit poster sending a payment message to any AA address triggers the dry run path (gated only by node operator config `conf.bDryRunNewTriggers`, not by the attacker). Hitting the exact interleaving window with real `handleAATriggers` execution (which only runs when an MCI actually stabilizes and had AA triggers) requires timing, but an attacker can post AA-triggering units continuously while the network is naturally stabilizing MCIs with AA activity, making the race practically achievable over time on any active hub/full node running with `bDryRunNewTriggers` enabled. This is a config-gated feature, which somewhat limits applicability to deployments where it is turned on.

### Recommendation
Serialize `dryRunPrimaryAATrigger` (and any other caller of `handleTrigger`/`revertResponsesInCaches` that mutates `storage.assocUnstableUnits`/`assocBestChildren`) behind the same mutex key(s) used by the authoritative trigger path (`aa_triggers` and/or `write`/`handleJoint`), or have the dry-run path operate on a cloned/isolated snapshot of the relevant in-memory unit-props objects instead of the live shared caches, so that speculative dry runs can never observe or mutate objects that the real stabilization pipeline is concurrently creating, updating, or forgetting.

### Proof of Concept
Conceptual PoC (requires a node with `conf.bDryRunNewTriggers = true`):
1. Attacker continuously posts units with `payment` messages whose outputs target a live AA address, causing `network.js` to call `aa_composer.dryRunPrimaryAATrigger` for each on the `ifOk` path (network.js:1271-1281) — none of this takes the `aa_triggers`/`write`/`handleJoint` locks.
2. In parallel, the node naturally advances its main chain and stabilizes an MCI that contains real triggers to the same or a related AA, invoking `handleAATriggers` → `handlePrimaryAATrigger` under `mutex.lock(['aa_triggers'])`, which itself calls `handleTrigger`/`revertResponsesInCaches`/`storage.forgetUnit` on the shared `assocUnstableUnits`/`assocBestChildren` maps (aa_composer.js:59-150, 1900-1916; storage.js:2209-2232).
3. Because step 1's dry run holds no lock, its own `handleTrigger` invocation (via `bDryRun: true`, aa_composer.js:272-306) can interleave its callback continuations with step 2's mutation of the same global objects — e.g., a `revertResponsesInCaches` call from the dry run runs `storage.forgetUnit` on a unit while the locked real-trigger flow is mid-way through reading/pushing into `assocBestChildren[parent_unit]` for the same parent, producing either a `throw Error` consistency-check crash (storage.js:1547-1550, main_chain.js:114-115) or a corrupted `assocBestChildren`/`is_free` state that diverges from the DB.

I was not able to fully trace every downstream consumer of `assocBestChildren`/`is_free` in a single pass (e.g. `addResponse`'s exact cache-mutation code in `aa_composer.js` was not retrieved before the tool budget ran out), so the precise crash/corruption trigger sequence should be confirmed by a Devin agent with fuller repo access before treating this as fully proven; the locking asymmetry between `dryRunPrimaryAATrigger` and `handleAATriggers`/`handlePrimaryAATrigger` on the same shared caches is, however, clearly established from the cited code.
