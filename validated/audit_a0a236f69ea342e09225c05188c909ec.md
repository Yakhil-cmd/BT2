### Title
`unarchive?` operator-precedence bug lets `review_stacks_enabled=false` be bypassed, letting attacker-controlled PR branch populate `stack_attributes[:branch]` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` combines `repository.review_stacks_enabled` with the provisioning-behavior checks using `&&`/`||` in a way that only gates the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`. As a result, a repository administrator's decision to disable review stacks (`review_stacks_enabled = false`) does not prevent stack creation, and `ReviewStackAdapter#stack_attributes` still sets `branch: params.pull_request.head.ref` straight from the attacker's PR payload.

### Finding Description
The claimed invariant is: `unarchive? == false` whenever `repository.review_stacks_enabled == false` (i.e., disabling review stacks should prevent any stack, and thus any branch, from being adopted).

The actual code in `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`: [1](#0-0) 

is, due to Ruby `&&`/`||` precedence, equivalent to:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```
`review_stacks_enabled` is only ANDed into the first disjunct. If the repository's `provisioning_behavior` is `prevent_with_label` (the case where a PR lacking the label is auto-approved) or `allow_with_label` with the label present, `unarchive?` returns `true` **regardless of `review_stacks_enabled`**.

When `unarchive?` is true and no stack currently exists, `process` calls `stack.unarchive!` → `ReviewStackAdapter#unarchive!`, which calls `create!`: [2](#0-1) 

`create!` builds the stack from `stack_attributes`, which sets the branch directly from the pull request payload with no validation that it corresponds to an approved/production ref: [3](#0-2) 

Attack flow: an attacker forks the tracked repository, opens a PR from a branch of their choosing (potentially shadowing a sensitive name), closes it, then reopens it (or simply opens it, since `OpenedHandler` shares the same `unarchive?`/behavior logic pattern). If the target repository happens to have `review_stacks_enabled=false` (feature "disabled") but still has `provisioning_behavior` set to `prevent_with_label` (a plausible leftover state, e.g., an admin toggling the enabled flag off without also resetting behavior) or `allow_with_label` and the attacker can label their own PR, `unarchive?` returns `true` and a `ReviewStack` is created/unarchived with `branch == params.pull_request.head.ref`, i.e., the attacker's own branch, entirely bypassing the intended `review_stacks_enabled=false` gate.

None of the existing guards catch this: `verify_signature`/webhook signature checks only authenticate that GitHub sent the event, not that the branch is authorized; the `ExplicitParameters` schema only validates payload shape; there is no model validation on `ReviewStack#branch` restricting it to approved refs. The only test coverage (`test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`) always sets `review_stacks_enabled: provisioning_enabled` defaulting to `true` in every scenario exercising `allow_with_label`/`prevent_with_label`, so the `review_stacks_enabled=false` + non-`allow_all` combination is never exercised, hiding the precedence bug. [4](#0-3) 

### Impact Explanation
A created/unarchived `ReviewStack` whose `branch` is attacker-controlled feeds the normal Shipit deploy/provisioning pipeline (`Shipit::ReviewStackProvisioningQueue`, tasks, `Command#start` → `PTY.spawn`), which runs `shipit.yml` steps checked out from that branch. Since `stack.branch` should only ever originate from a ref explicitly approved through an enabled review-stacks workflow, this bypass allows execution of attacker-supplied code on the deploy host for any repository misconfigured with `review_stacks_enabled=false` + `provisioning_behavior in {allow_with_label, prevent_with_label}` — a Critical RCE per the stated impact categories. It is repeatable against any repository in this configuration state, one PR per stack/environment slot (`pr#{number}`).

### Likelihood Explanation
Exploitation requires: (1) the target repository is tracked by Shipit, (2) `review_stacks_enabled=false` while `provisioning_behavior` is `prevent_with_label` (no label needed by attacker at all) or `allow_with_label` (attacker needs to label their own PR, assumed possible per the stated attacker capabilities). Condition (2) is an operator-configuration precondition rather than something the attacker sets, but it is a plausible/likely real-world state (e.g., disabling the feature via the toggle while leaving the previously-configured behavior in place), and the bug is 100% deterministic once that state exists — no race condition, no privileged access needed beyond opening/labeling one's own PR.

### Recommendation
Fix the boolean grouping in `unarchive?` (and audit `OpenedHandler`/`LabeledHandler`/`UnlabeledHandler` for the same pattern) so `review_stacks_enabled` gates all three provisioning-behavior branches, e.g.:
```ruby
def unarchive?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, add:
```ruby
test "does NOT create/unarchive stacks when review_stacks_enabled is false, even for prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  stack = repository.review_stacks.find_by(environment: "pr#{payload['number']}")
  assert_nil stack, "Expected no stack to be created when review_stacks_enabled=false"
end
```
With current code, this assertion fails: `stack` is created and `stack.branch == payload["pull_request"]["head"]["ref"]`, demonstrating the bypass.
