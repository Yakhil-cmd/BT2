Based on the investigation, the strongest analog in this codebase is the plaintext logging of decrypted device-message content in `device.js`'s `decryptPackage()` function, which mirrors the Linkis bug class (sensitive decoded content written to logs on decode/decrypt paths reachable by an external actor).

### Title
Plaintext logging of decrypted device messages exposes private keys, payment data, and correspondence in log files - ([File: device.js])

### Summary
`decryptPackage()` in `device.js` logs the full plaintext of every successfully decrypted device message via `console.log("decrypted: "+decrypted_message)`, unconditionally, before the message is validated or acted upon. Any paired (or even just key-aware) correspondent who can send this node an encrypted device message can force sensitive plaintext — including private payment chain data, shared-address private keys exchanged during pairing/`wallet_fully_approved` flows, textcoin mnemonics, and chat content — into the node's log output.

### Finding Description
`decryptPackage(objEncryptedPackage, depth)` derives the shared secret and decrypts the AES-GCM payload, then does: [1](#0-0) 
```
	var decrypted_message_buf = Buffer.concat([decrypted1, decrypted2]);
	var decrypted_message = decrypted_message_buf.toString("utf8");
	console.log("decrypted: "+decrypted_message);
```
This happens for every message this device successfully decrypts through `hub/message` handling in `handleJustsaying()`, which validates only the hash/signature of the *outer* envelope before decryption — not the semantic content: [2](#0-1) . Once decrypted, the raw JSON (`json`) is used for pairing, `my_xpubkey`, `wallet_fully_approved`, private payment chains, and other message subjects: [3](#0-2) .

The decrypted payloads used throughout the wallet layer routinely carry highly sensitive data: private payment chain elements (asset spend proofs and addresses), shared-address definitions/pubkeys established during pairing, and `wallet_fully_approved` handshake data. Because `console.log` writes to stdout/log files unconditionally on every successful decryption (not just on error, unlike the Linkis case), this is a broader, always-on version of the same bug class: sensitive decoded/decrypted content being persisted to logs.

This is directly analogous to the Apache Linkis issue where `HiveUtils.decode()` logs the full input string on Base64 decode failure, leaking a plaintext credential (e.g., `javax.jdo.option.ConnectionPassword`) into log files. Here the equivalent "decode" step (`decryptPackage`) logs the decoded plaintext unconditionally — an even larger blast radius since it is not restricted to only failure paths.

### Impact Explanation
Anyone who knows this node's device pubkey (obtainable from any prior pairing code, correspondent list, or on-chain interaction) can send an encrypted device message and have their chosen decrypted plaintext content appear in this node's logs. More importantly, *legitimate* correspondents' private payment chains, shared multi-sig address private key material shared during pairing, and textcoin mnemonics sent to this device will be written to disk in plaintext on every use. If log files are later exposed (backups, misconfigured log shipping, debugging support requests, shared hosting), this leaks private keys and unspent private payment proofs, enabling unauthorized spending of private assets or compromise of shared/multisig addresses tied to this device.

### Likelihood Explanation
Likelihood is high relative to the Linkis case because logging occurs on the normal success path of every decrypted message, not only on a rare decode failure. Any correspondent (or attacker who has obtained the device's public key through normal pairing flows, which are commonly shared via QR/links) can trigger this by simply sending a device message with sensitive content, and the node operator's log-retention practices determine actual exposure.

### Recommendation
Remove or heavily redact the `console.log("decrypted: "+decrypted_message)` line in `decryptPackage()` (device.js line 466). If debug visibility is needed, log only the message `subject`/type and length, never the raw decrypted body, and gate any content logging behind an explicit, opt-in debug flag that defaults to off.

### Proof of Concept
1. Node A pairs with Node B (or otherwise learns Node B's permanent/temp device pubkey).
2. Node A sends Node B a `hub/message` containing a `private_payment` or `pairing` subject payload with sensitive fields (e.g., a shared-address private key blob, or a private payment chain).
3. Node B's `decryptPackage()` decrypts the message and executes `console.log("decrypted: "+decrypted_message)`, writing the full plaintext JSON — including the sensitive fields — to Node B's stdout/log file.
4. Anyone with read access to Node B's logs (support staff, backup admins, log-aggregation systems) can recover the sensitive plaintext long after the fact. [4](#0-3)
