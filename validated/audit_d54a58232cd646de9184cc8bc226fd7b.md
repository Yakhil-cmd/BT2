## Analysis

The upstream advisory concerns unescaped control characters being written to console output, which can hide or spoof what a user actually sees before they act on it. The closest reachable analog in `ocore--022` is in the **prosaic/arbiter contract** flow, where a paired device (an unprivileged peer, exactly the actor class permitted by the scan rules) can freely set the `title` and `text` fields of a contract offer that is later displayed to the counterparty for review and signing, with no filtering of control characters.

### Title
Unsanitized contract `title`/`text` from a paired device enables display spoofing that can trick a counterparty into signing/funding a different contract than shown - (File: `prosaic_contract.js`, `wallet.js`)

### Summary
`wallet.js` handles the `prosaic_contract_offer` device message from any paired correspondent and only checks that `title`, `text`, `creation_date` are present and that dates/addresses are well-formed; it performs no filtering of control characters (e.g. `\r`, backspace, ANSI escapes, RTL/LTR override characters) before storing and relaying the contract for display.

### Finding Description
When a paired device sends a `prosaic_contract_offer`, the handler validates only structural fields: [1](#0-0) 

There is no check that `body.title` or `body.text` consist only of printable characters. `prosaic_contract.getHash()` simply hashes the raw strings: [2](#0-1) [3](#0-2) 

Critically, only `title` is what gets cryptographically signed by the accepting counterparty (`objSignedMessage.signed_message != objContract.title`): [4](#0-3) 

The `text` field (the actual substantive contract terms that presumably govern a later arbiter dispute) is never itself signed — only its hash is bound via `getHash()`, which concatenates `title + text + creation_date`. Since both `title` and `text` are attacker-controlled free-form strings from an unprivileged paired device, and neither the storage layer (`prosaic_contracts.title`/`text`, declared as `VARCHAR`/`TEXT` with no character-class constraint) nor the message handler filters control characters, a malicious peer can embed characters such as carriage returns (`\r`), backspaces, or Unicode bidirectional override characters into `title`/`text`. When the wallet UI renders these fields to the victim for review before they approve the contract and fund the resulting shared address, the injected control characters can overwrite or hide substantive portions of the displayed text, causing the victim to see contract terms that differ from the raw bytes that were actually hashed, stored, and (for `title`) signed.

### Impact Explanation
A victim who reviews a spoofed rendering of the contract may approve and fund a prosaic/arbiter shared address believing they agreed to different terms than what is actually recorded. Because dispute resolution and fund release for these contracts are driven by the stored/hashed `text`/`title` (not by what was displayed), the victim's escrowed bytes can be paid out under terms they never actually consented to see, resulting in unauthorized loss of the victim's funds held in the shared address once a dispute is resolved (or once the victim signs based on the spoofed display and the true text governs actual behavior/arbitration).

### Likelihood Explanation
Any paired device (a normal correspondent relationship required for wallet usage) can send a `prosaic_contract_offer`/`arbiter_contract` message with arbitrary `title`/`text` content; no privileged access or protocol-level cooperation from a hub or node operator is required. The only requirement is that the victim opens the incoming contract review dialog, which is the expected/normal flow for this feature.

### Recommendation
Strip or escape control characters (C0/C1 control codes, bidirectional override characters, and other non-printable code points) from `title` and `text` before storing and before rendering them to the user in `prosaic_contract.js`/`arbiter_contract.js`/`wallet.js`, and consider including the full `text` (not just `title`) in the cryptographically signed content so that what is displayed, hashed, and signed are provably the same bytes.

### Proof of Concept
1. Attacker pairs with victim's wallet as a normal correspondent device.
2. Attacker sends a `prosaic_contract_offer` device message where `text` contains benign-looking content followed by control characters (e.g. `\r` sequences) that, when rendered in the wallet's contract viewer, visually overwrite the earlier bytes with different terms than what is actually stored/hashed.
3. Victim reviews the spoofed rendering, believes the terms are favorable, and signs/funds the shared address per `wallet.js:455-480` and `prosaic_contract.js:respond`.
4. The real (hidden) `text` bytes are what get hashed/stored and used downstream (e.g., in dispute handling), diverging from what the victim was shown, at the cost of the victim's escrowed funds.
