### Title
CCMenu API endpoint bypasses `ApiClient#stack_id` scoping, allowing a stack-scoped token to read build status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces "the stack a token authorises" by resolving `stack`/`stacks` through `current_api_client.stack_id`: `Stack.where(id: current_api_client.stack_id)` when a client is scoped to a single stack. [1](#0-0)  `CCMenuController`, however, overrides `stack` to resolve the record directly with `Stack.from_param!(params[:stack_id])`, never touching `current_api_client.stack_id`, and also overrides `authenticate_api_client` to authenticate purely from a `token` query parameter. [2](#0-1) 

### Finding Description
The binding that should hold is: **stack a token authorises == stack it touches**. `ApiClient` can be scoped to a single stack via its `stack` association and `stack_id`; the base controller's `stacks`/`stack` helpers are the single choke point that enforces this scope for every other API controller (`StacksController`, `DeploysController`, `TasksController`, `LocksController`, etc.), all of which call `stack` from the base controller. [1](#0-0) 

`CCMenuController` requires only `read:stack`: `require_permission :read, :stack`. [3](#0-2)  `check_permissions!` only checks that the client's `permissions` array contains `"read:stack"` — it never compares the requested stack against `current_api_client.stack_id`. [4](#0-3)  The stack-scope enforcement therefore depends entirely on the controller-level `stack`/`stacks` helper, and `CCMenuController` supplies its own `stack` method that performs an unscoped lookup: `Stack.from_param!(params[:stack_id])`. [5](#0-4) 

As a result, an `ApiClient` created with `stack: <stack A>` (e.g. the `here_come_the_walrus` fixture, which is scoped to the `shipit` stack and only has `read:stack`) [6](#0-5)  can authenticate against `CCMenuController#show` using `?token=<its token>` while supplying a *different* `stack_id` in the URL, and the controller will happily render that other stack's data because the lookup never checks `stack.id == current_api_client.stack_id`.

### Impact Explanation
`CCMenuController#show` renders the stack name, last build status, activity ("Building"/"Sleeping"), last build time/label, and the deploy web URL for whatever stack is resolved. [7](#0-6)  This is exactly the impact category "unauthenticated read of stack state, task streams or deploy output" reachable by an attacker holding only a narrowly-scoped API token (one meant to be limited to a single stack), letting them enumerate build/deploy activity of stacks they were never granted access to — a genuine break of the token-to-stack authorization binding, not merely a best-practice nit.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` API token (a legitimate, low-privilege credential type explicitly supported by the engine's `ApiClient.stack_id` design) can trigger this by simply changing the `stack_id` segment of the CCMenu URL — no additional secrets, GitHub access, or session are required beyond the token itself, which the rules permit as the "unprivileged" starting credential for this class of finding since the vulnerability is that the token's own declared scope is not honored by this specific controller.

### Recommendation
Have `CCMenuController` reuse the base controller's scoped `stack`/`stacks` helpers instead of defining an unscoped `Stack.from_param!` lookup, so the resolution goes through `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, consistently with every other API controller.

### Proof of Concept
1. As an admin, create (or use the fixture) an `ApiClient` scoped to Stack A (`stack: A`, `permissions: ['read:stack']`) and obtain its token via `authentication_token`. [8](#0-7) 
2. Send `GET /api/<stack_B_param>/cc.xml?token=<Stack-A-scoped-token>` where Stack B is a stack the client was never granted access to.
3. `authenticate_api_client` in `CCMenuController` authenticates the client purely from the token (ignoring which stack it's scoped to). [9](#0-8) 
4. `require_permission :read, :stack` passes because the client's `permissions` include `read:stack`, regardless of which stack is requested. [4](#0-3) 
5. `stack` resolves Stack B directly via `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` scoping used everywhere else. [5](#0-4) 
6. The response renders Stack B's name, last build status, activity, and deploy URL — data the Stack-A-scoped token was never authorized to read. [10](#0-9)
