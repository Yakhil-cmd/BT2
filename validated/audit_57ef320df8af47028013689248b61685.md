### Title
AA bounce logic forfeits an already-sufficient base-currency payment when a secondary asset sent in the same trigger fails to cover its own `bounce_fees` entry - (File: aa_composer.js)

### Summary
`handleTrigger`'s `bounce()` function is the single refund path used whenever a primary AA trigger fails (bad formula, unmet `if` condition set, insufficient funds, etc.). When a poster funds a trigger unit with **both** base bytes and a non-base asset in the same unit (exactly the "native + token together" pattern from the reference report), and the AA's `bounce_fees` template defines a minimum for that non-base asset, an amount below that per-asset threshold causes the *entire* bounce/refund to be abandoned - even the base-byte portion that was fully sufficient to pay the bounce fee and would otherwise have been returned.

### Finding Description
`getTrigger()` aggregates every payment message addressed to the AA into `trigger.outputs`, keyed by asset (`'base'` or asset unit) [1](#0-0) . A single unit can legally carry a base-currency payment message and an asset payment message to the same AA address at once, exactly mirroring the `msg.value` + ERC-20 transfer combination described in the reference report.

Before evaluating the AA, `handleTrigger` checks bounce-fee sufficiency per asset:
```
if ((trigger.outputs.base || 0) < bounce_fees.base) { return bounce('received bytes are not enough to cover bounce fees'); }
for (var asset in trigger.outputs) { // if not enough asset received to pay for bounce fees, ignore silently
    if (bounce_fees[asset] && trigger.outputs[asset] < bounce_fees[asset]) {
        return bounce('received ' + asset + ' is not enough to cover bounce fees');
    }
}
``` [2](#0-1) 

Any evaluation failure (bounced `if`, formula error, insufficient AA balance, etc.) also funnels through the same `bounce()` call [3](#0-2) [4](#0-3) .

Inside `bounce()`, the refund is computed asset-by-asset, but a single asset whose received amount is below its configured `bounce_fees[asset]` aborts the refund of **all** assets, not just that one:
```
if ((trigger.outputs.base || 0) < bounce_fees.base) return finish(null);
var messages = [];
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    if (fee > amount)
        return finish(null);
    if (fee === amount)
        continue;
    var bounced_amount = amount - fee;
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
}
if (messages.length === 0)
    return finish(null);
sendUnit(messages);
``` [5](#0-4) 

The line `if (fee > amount) return finish(null);` exits the loop entirely on the *first* under-funded asset it encounters, discarding the `messages` array already built for other, fully-refundable assets (including base bytes, which had already passed the earlier `bounce_fees.base` check). `finish(null)` sends no response unit at all, so the sender never gets any of their funds back - the base bytes (and any other adequately funded asset) that were correctly above their thresholds are silently absorbed into the AA's balance instead of being bounced back, with no notification or accounting distinguishing this "stuck" state from a normal top-up.

### Impact Explanation
An unprivileged unit poster who triggers an AA with an under-defined `bounce_fees` map for a secondary asset (a config choice made by the AA author, not the poster) can lose the entirety of an otherwise-refundable base-currency payment merely by attaching a small amount of that secondary asset alongside it. This is a direct AA fund loss/freezing bug: value that the protocol's own accounting logic determined was refundable ends up permanently absorbed by the AA contract instead of returned to the sender, with no path to recover it through the bounce mechanism (the funds are only recoverable if the AA's own business logic happens to spend them out again, which most simple/bounce-focused AAs like the "just_a_bouncer" pattern do not do).

### Likelihood Explanation
Any AA that defines `bounce_fees` for more than the `base` asset (a documented and tested feature - see `template.bounce_fees` handling in `aa_validation.js` and the composer/test suite) is exposed. A poster only needs to send a trigger unit containing a base payment plus a token payment where the token amount is smaller than the AA's configured fee for that asset; this can happen accidentally (fat-fingered amount) or be deliberately exploited by a griefer against other users' funds sent to the same AA in the same unit, or by the AA operator's own users experiencing silent fund loss during normal use whenever a secondary-asset threshold isn't met.

### Recommendation
In `bounce()`, do not abort the whole refund when a single asset fails its `bounce_fees` check. Instead, skip (forfeit) only the under-funded asset's amount and continue building refund messages for all other assets in `trigger.outputs` that do meet their thresholds:
```
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    if (fee >= amount)
        continue; // forfeit only this asset, don't abort the whole refund
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: amount - fee}]}});
}
```
This preserves the intended "insufficient bounce fee for this asset" forfeiture semantics without penalizing unrelated, adequately funded assets sent in the same trigger unit.

### Proof of Concept
1. Deploy an AA with:
```
{
  bounce_fees: { base: 10000, <asset_unit>: 1000 },
  messages: [ { app: 'payment', if: '{trigger.data.foo}', payload: { asset: 'base', outputs: [...] } } ] // some condition that will bounce
}
```
2. Post a trigger unit to this AA in a single unit containing:
   - a base-currency payment message with `amount = 50000` (well above `bounce_fees.base = 10000`)
   - an asset payment message for `<asset_unit>` with `amount = 500` (below `bounce_fees[<asset_unit>] = 1000`)
   - trigger data that fails the AA's `if` condition (forcing a bounce), or omit the required field entirely.
3. `handleTrigger` calls `bounce()`. The per-asset loop reaches `<asset_unit>` first (or regardless of order), finds `fee (1000) > amount (500)`, and calls `finish(null)` immediately - discarding the base-currency refund message that would have sent back `50000 - 10000 = 40000` bytes.
4. Result: no response unit is created; the full `50000` bytes and `500` asset units remain in the AA's balance with no refund to the trigger address, even though the base amount alone was clearly sufficient to be bounced back.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
