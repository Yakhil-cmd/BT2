### Title
ReDoS-heuristic bypass in `_has_redos_structure` allows a committed `security-patterns.yaml` regex to hang the PostToolUse hook on every edit - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_validate_pattern` only rejects regexes whose *textual shape* matches `_REDOS_SHAPES`/`_ALT_UNDER_REP` (a nested-quantifier-immediately-followed-by-`[+*?]`, or an overlapping two-branch alternation under `+`/`*`). A committed `.claude/security-patterns.yaml` can carry a regex that produces catastrophic/super-linear backtracking while structurally avoiding those exact shapes (e.g. a bounded `{m,n}` outer repetition instead of `+`/`*`, or multiple sibling unbounded quantifiers over the same character class with no enclosing group at all). Because `check_patterns` calls `re.search` with no timeout, such a regex hangs the PostToolUse hook indefinitely on attacker-chosen file content.

### Finding Description
The load path is: `load_for_session` → `_load_user_patterns` (`plugins/security-guidance/hooks/extensibility.py:147-168`) → `_validate_pattern` (`extensibility.py:199-244`), which gates custom regexes solely with `_has_redos_structure` (`extensibility.py:272-289`) before `re.compile`. `_has_redos_structure` only checks two fixed shapes: [1](#0-0) 

- `_REDOS_SHAPES[0]` requires a parenthesized group containing `+`/`*` to be *immediately* followed by `[+*?]` — i.e. it only catches `(a+)+`/`(a*b)*`-style shapes where the **outer** repetition operator is literally `+`, `*`, or `?`.
- `_REDOS_SHAPES[1]` only catches `(.*)*`/`(.*)+`.
- `_ALT_UNDER_REP` only catches alternation under `+`/`*` where one literal branch text is a prefix of another.

These are purely textual pattern-matches on the regex source, not an actual analysis of backtracking complexity, as the docstring itself concedes ("Static check, not a proof"). Two evasion classes bypass all three checks while still exhibiting the same catastrophic-backtracking mechanics:

1. **Bounded-quantifier nested group**: `(a+){2,40}b` (or `(a+){40}b`) is structurally identical to `(a+)+b` (nested unbounded quantifier inside a repeated group) but the outer repetition is `{2,40}` rather than `+`/`*`/`?`, so `_REDOS_SHAPES[0]`'s trailing `[+*?]` check does not match and the pattern is accepted.
2. **Non-nested sibling quantifiers** (classic polynomial/"quadratic-plus" ReDoS): a pattern like `^(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)c$` has no group nested inside another group's quantifier and no alternation, so it triggers neither `_REDOS_SHAPES` nor `_ALT_UNDER_REP`, yet forces the regex engine to enumerate an enormous number of ways to partition the run of `a`s across the ten `*` groups when the trailing `c` fails to match.

Once such a rule is accepted, it is merged into `SECURITY_PATTERNS` via `user_patterns()` and evaluated by `check_patterns` at `plugins/security-guidance/hooks/security_reminder_hook.py:417-422`: [2](#0-1) 

`re.search` here is wrapped only in a bare `try/except Exception`, which does not bound execution time — a hang inside `re.search` is not an exception. `check_patterns` is invoked for every `Edit`/`Write`/`MultiEdit`/`NotebookEdit` PostToolUse event with the tool's own content (`security_reminder_hook.py:2124-2129`), so any file edit whose content matches the crafted rule's `path_filter`/extension and contains an adversarial near-miss substring (e.g. many `a`s followed by a non-`c` character for evasion class 2) will make that specific PostToolUse hook invocation hang.

### Impact Explanation
This is a repo-controlled denial-of-service against the security-guidance PostToolUse hook: an attacker who can land a `.claude/security-patterns.yaml` in the repository (an ordinary PR/commit, no special privilege) can cause any subsequent `Edit`/`Write` whose content happens to trip the crafted pattern to hang the hook process. Since the hook mediates the security reminder pipeline, a hang there stalls or times out that tool call and — depending on how many edits touch matching content — can degrade or effectively disable security-pattern reminders for the remainder of the session, matching a scoped availability/DoS impact against Claude Code's PostToolUse enforcement path.

### Likelihood Explanation
Feasible and repeatable: the only precondition is the ability to commit a `.claude/security-patterns.yaml` file (or its `.local` variant) to the project — explicitly an in-scope "project, committed" trust boundary per the module's own docstring, which asserts custom regexes are "validated at load for catastrophic-backtracking structure and skipped ... if they look ReDoS-prone." The two evasion shapes above are standard, well-documented ReDoS constructions that do not require anything exotic; both are static-analysis-detectable by a fuzzer that generates regex ASTs, filters for those *not* matching `_REDOS_SHAPES`/`_ALT_UNDER_REP`, and times `re.search` against constructed near-miss content.

### Recommendation
Do not rely solely on shape-based heuristics for untrusted regex content. Concrete fixes:
- Enforce a hard wall-clock timeout around every `re.search`/`re.match` call in `check_patterns` for user-supplied patterns (e.g. run in a subprocess/thread with `signal.alarm`, or use a regex engine with guaranteed linear-time matching such as Google's `re2` for user patterns).
- Broaden `_has_redos_structure` to also flag bounded repetition (`{m,n}` with `m`/`n` beyond a small threshold, or any `{...}` at all) wrapping a group containing `+`/`*`, not just `[+*?]`.
- Detect the "N sibling unbounded quantifiers over overlapping character classes" shape (or simply cap the total count of `+`/`*`/`{}` quantifiers permitted in a single user-supplied regex).
- As defense in depth, cap `content` length passed to user-pattern regex checks, since backtracking blowups are a function of input length.

### Proof of Concept
Unit/fuzz test to add to the security-guidance test suite:

```python
import re, time
from extensibility import _has_redos_structure, _validate_pattern

# Evasion 1: bounded-quantifier nested group
regex1 = r"(a+){2,35}b"
assert _has_redos_structure(regex1) is False  # bypasses the heuristic
rule1 = _validate_pattern(
    {"rule_name": "evil1", "reminder": "x", "regex": regex1}, source="Project"
)
assert rule1 is not None  # accepted despite ReDoS shape

evil_content = "a" * 35 + "!"  # non-matching tail forces backtracking
start = time.monotonic()
re.search(regex1, evil_content)
assert time.monotonic() - start < 1.0  # EXPECTED TO FAIL: hangs

# Evasion 2: sibling unbounded quantifiers, no nesting/alternation
regex2 = r"^(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)c$"
assert _has_redos_structure(regex2) is False
rule2 = _validate_pattern(
    {"rule_name": "evil2", "reminder": "x", "regex": regex2}, source="Project"
)
assert rule2 is not None

evil_content2 = "a" * 30 + "d"  # never matches trailing 'c'
start = time.monotonic()
re.search(regex2, evil_content2)
assert time.monotonic() - start < 1.0  # EXPECTED TO FAIL: hangs
```

Expected result: both `_has_redos_structure` calls return `False` (heuristic bypassed) and both `re.search` calls exceed the 1-second bound by orders of magnitude, demonstrating that a committed `security-patterns.yaml` regex reaches `check_patterns`'s unguarded `re.search` in `security_reminder_hook.py:419` and hangs the PostToolUse hook.
