### Title
`ReviewStack#env` merges PR labels into env unfiltered by `EnvironmentVariables.permit`, allowing `GIT_SSH_COMMAND` injection into `git fetch` - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` merges `pull_request.labels` directly into the environment hash returned to `StackCommands#env`, with no call to `Shipit::EnvironmentVariables.permit`. Since `StackCommands#fetch`/`#fetch_commit` pass this env straight to `Command`, whose `unbundled_env` merges it over `BASE_ENV` before `PTY.spawn`, an attacker who can label their own PR can set `GIT_SSH_COMMAND` (or other transport-influencing variables) for every `git fetch`/`clone` executed against that stack's cache.

### Finding Description
The intended binding is: every environment variable reaching `Command#unbundled_env`/`PTY.spawn` must have passed through `Shipit::EnvironmentVariables.permit(variable_definitions)` — as enforced for deploy params via `Stack#build_deploy`'s `env: filter_deploy_envs(env.to_h)` [1](#0-0) . That binding does not hold for `ReviewStack#env`: it takes `super` (the base `Stack#env`) and merges in `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` with no `permit`/whitelist step at all [2](#0-1) .

This env is consumed by `StackCommands#env`, which does `super.merge(@stack.env)` [3](#0-2) , and is then passed as the `env:` kwarg into `git('fetch', ..., env:, chdir: @stack.git_path)` and `git_clone(..., env:, ...)` in `#fetch_commit` and `#fetch` [4](#0-3) . `Command#unbundled_env` then does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` before `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [5](#0-4) [6](#0-5) . Because labels are unfiltered strings uppercased directly into the env key, any label an attacker's PR carries (e.g. `git_ssh_command`) becomes an environment variable name spawned into `git fetch`'s process — a value the attacker fully controls comes from the label itself (`"true"` fixed value per current code, but the *key* is attacker chosen with no whitelist).

Attacker path: attacker opens a PR against a repo with review stacks enabled and adds a label named `git_ssh_command` to their own PR (or any PR on that repo, since `LabelCapturingHandler` captures labels on labeled/opened/reopened events for any known, non-archived review stack) [7](#0-6) . This label persists on `stack.pull_request.labels`, and is picked up unconditionally by `ReviewStack#env` on every subsequent `fetch`/`fetch_commit` for that stack, including fetches of other commits/PR pushes to that same review stack.

Existing guards do not close this: `EnvironmentVariables#permit` exists and is applied for `build_deploy`'s user-supplied `env` param via `filter_deploy_envs` [8](#0-7) , but this whitelist call is never invoked in the `ReviewStack#env` / `StackCommands#env` path. Model validations, controller-level env rejection (`test/controllers/deploys_controller_test.rb`) and `drop_unhandled_event` are irrelevant here since the injection occurs at the git-fetch layer, not through the deploy-form env params.

### Impact Explanation
An unprivileged GitHub user able to label their own PR can inject an attacker-chosen environment-variable *name* into every `git fetch`/`git clone` invocation on the deploy host for that review stack. While the current label-capturing code fixes the *value* to the literal string `"true"`, the vulnerability is that the *key itself* is fully attacker-controlled and unfiltered — variables like `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_ASKPASS`, or `LD_PRELOAD` (if git or a git-fetch helper honors it) could be set with an attacker-controlled name to disrupt or hijack the transport used for fetching, at minimum breaking fetch behavior and at worst providing a lever for command substitution if the attacker discovers a variable whose semantics let a fixed value ("true") be interpreted as a command (e.g. `GIT_SSH_COMMAND=true` executes the `true` binary as SSH transport, silently breaking auth but demonstrating attacker control of the transport program name via env). This affects the specific stack the attacker's PR is labeling and any commit fetched into that stack's shared git cache, matching a git-transport-hijack / command-execution-adjacent finding on the deploy host.

### Likelihood Explanation
Preconditions: review stacks feature enabled and the repository provisioning behavior allows the attacker to have or trigger a review stack for their PR (as demonstrated by `create_stack` in the label-capturing test using `provisioning_behavior = :allow_all`). Attacker cost is trivial — labeling a PR requires only standard GitHub permissions the attacker already has as a PR author on a public/forkable repo; no Shipit credentials are needed. The label-capturing webhook handler is triggered by ordinary `pull_request` webhook events, which are already authenticated by GitHub webhook signature verification upstream of this code (`GitHubApp#verify_webhook_signature`), so this is a fully unauthenticated-to-Shipit exploitation vector once the PR/label exists.

### Recommendation
Apply `Shipit::EnvironmentVariables.permit` (or an equivalent explicit whitelist keyed to a `deploy_variables`/`review_variables` definition) to the labels-derived hash inside `Shipit::ReviewStack#env` before merging it with `super`, exactly as `Stack#build_deploy` does via `filter_deploy_envs`. Alternatively, restrict label-derived env vars to a fixed, non-conflicting namespace/prefix (e.g. `SHIPIT_LABEL_<NAME>`) that cannot collide with security-sensitive variables like `GIT_SSH_COMMAND`, `LD_PRELOAD`, `GIT_PROXY_COMMAND`, `PATH`, etc., and additionally deny-list any key colliding with git/ssh transport-control variables.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (new test)
test "labels cannot inject transport-control environment variables into git fetch" do
  stack = shipit_review_stacks(:some_review_stack) # or create via ReviewStackAdapter as in label_capturing_handler_test
  stack.pull_request.labels = ['git_ssh_command']
  stack.pull_request.save!

  commands = Shipit::StackCommands.new(stack)

  # Binding under test: every key in commands.env must have passed EnvironmentVariables.permit
  assert_raises(Shipit::EnvironmentVariables::NotPermitted) do
    Shipit::EnvironmentVariables.with(commands.env).permit(Shipit::Stack::DEPLOY_VARIABLES) # or equivalent whitelist
  end

  # Demonstrates current (broken) behavior: no exception raised and key reaches Command
  refute_nil commands.env['GIT_SSH_COMMAND']
end
```
This asserts the two sides of the intended equality — `commands.env.keys` should equal `EnvironmentVariables.permit(...).keys` — and currently diverge because `GIT_SSH_COMMAND` reaches `commands.env` without ever being validated against a whitelist.
