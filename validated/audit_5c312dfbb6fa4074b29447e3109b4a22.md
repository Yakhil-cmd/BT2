### Title
Unbounded, un-partitioned epoch-reward *calculation* pass over all network stake delegations can stall the epoch-boundary block across all validators - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Agave already anticipated the exact bug class from the Hubble report — an operation whose cost scales with the number of unprivileged, permissionlessly-creatable objects (markets ↔ stake accounts) and that is executed as a single, un-chunked unit of work. For *distributing* rewards, Agave explicitly partitions the work across many blocks precisely to avoid this problem [1](#0-0) . However, the *calculation* phase that runs immediately before distribution begins is **not** partitioned: it iterates over every stake delegation on the network in one synchronous pass during the creation of the very first block of each epoch, on every validator, before any transaction in that block is processed.

### Finding Description
At the start of every epoch, `process_new_epoch` calls `compute_new_epoch_caches_and_rewards`, which calls `calculate_rewards`, which computes `calculate_rewards_for_partitioning` synchronously as part of `Bank::new_from_parent`/replay for the epoch-boundary slot [2](#0-1) [3](#0-2) .

Inside this call chain, `calculate_reward_points_partitioned` and `calculate_stake_rewards_and_commissions` both iterate over the **entire** `stake_delegations` vector — i.e., every stake account that has ever been delegated on the network — in a single call, with no chunking across blocks: [4](#0-3) [5](#0-4) 

This is functionally the same shape as `settleFunding`'s unbounded loop over "all markets": `stake_delegations_len` grows unboundedly as more unprivileged users create stake accounts (bounded only by the 1 SOL minimum delegation plus rent-exempt reserve, which is trivially affordable) [6](#0-5) , and every increase in that count directly increases the work done in this single synchronous call.

By contrast, once the calculation phase finishes, `begin_partitioned_rewards` explicitly splits the *distribution* of the resulting rewards across up to 10% of the epoch's slots, exactly the kind of "array of markets, distributed over multiple calls" mitigation the C4 report recommended: [1](#0-0) [7](#0-6) 

That mitigation covers writing/crediting stake accounts, but it does **not** cover the up-front points/rewards *calculation* pass, which remains a single unbounded O(N) operation over all stake delegations, run inline on the epoch-boundary block for every validator (leader and replaying followers alike), gated only by a per-fork memoization cache keyed on parent hash [8](#0-7) , which does not help the first computation on a given fork.

### Impact Explanation
Because `calculate_stake_rewards_and_commissions`/`calculate_reward_points_partitioned` run to completion before the epoch-boundary block can otherwise be considered processed, an unbounded growth in the number of stake delegations (fully permissionless, achievable by any user for ~1 SOL + rent per account) increases the wall-clock time every validator must spend, in lock-step, at every epoch boundary, before that block's transactions can be executed. If this computation grows large enough relative to the slot/epoch time budget, it can push epoch-boundary block production/replay past the target slot time, causing validators to fall behind, forks to diverge in timing, or — in the worst case — a cluster-wide slowdown/stall at the epoch boundary. This matches the "epoch-boundary halt" impact class explicitly listed as in-scope.

### Likelihood Explanation
Creating additional stake accounts is entirely permissionless and only requires paying the minimum delegation (1 SOL) plus rent-exempt reserve per account; there is no admission-control or governance approval analogous to Hubble's "DAO governance has to be careful with not adding too many markets." Any actor or coordinated set of actors can grow the stake-delegation set over time, continuously increasing the cost of this synchronous calculation pass, with no additional per-transaction cost proportional to the ongoing burden it imposes on all validators every epoch thereafter (the cost is paid once at account creation, but the calculation burden recurs every epoch, forever, for the life of the network).

### Recommendation
Partition the reward *calculation* phase the same way the *distribution* phase already is: compute per-chunk points/stake-rewards across multiple blocks (or incrementally, e.g. maintaining running per-vote-account point totals as stake changes occur rather than a full O(N) rescan at the epoch boundary), so that the up-front, single-block cost of `calculate_reward_points_partitioned`/`calculate_stake_rewards_and_commissions` does not grow unboundedly with the total number of stake delegations on the network.

### Proof of Concept
Not applicable / not independently reproducible from static analysis alone: this is a scaling/DoS-class concern rather than a state-corrupting bug, and confirming its real-world severity would require benchmarking `calculate_stake_rewards_and_commissions`/`calculate_reward_points_partitioned` against a network-scale (multi-million) stake-delegation set to measure actual wall-clock cost relative to the epoch-boundary slot time budget — data not available via static code review. Existing benchmarks in `runtime/benches/epoch_turnover.rs` exercise this path with up to 1,000,000 stake accounts [9](#0-8)  and would be the natural place to measure current cost and confirm whether it already approaches problematic levels or has headroom before mitigation is required.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
