### Title
Webhook signature verification is keyed off an unverified, attacker-controlled `repository.owner.login` field, decoupling the organization that "authenticates" the request from the repository/stack the handlers actually write to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using a field taken straight out of the untrusted, not-yet-verified JSON body (`repository.owner.login`, with fallback to `organization.login`). If that particular organization has no `webhook_secret` configured, `GithubApp#verify_webhook_signature` unconditionally returns `true`. The event handlers that follow, however, act on a *different* field of the very same body — `repository.full_name` — to decide which `Stack`/`Repository`/`Commit` to mutate. This is the same class of bug as the C4 report: a value that gates a security decision (which org "authenticates" the payload) is not bound to the value that is actually acted upon (which repository gets written to), so a low-trust input can make a high-trust write succeed.

### Finding Description
`WebhooksController` runs `verify_signature` as a `before_action`, before any application logic: [1](#0-0) 

It computes the signing organization purely from body content that has not yet been authenticated: [2](#0-1) 

That organization name is passed to `Shipit.github(organization: ...)` to obtain a `GithubApp` instance, whose secret is then used to check the `X-Hub-Signature` header against `request.raw_post`: [3](#0-2) 

Note the short-circuit on line 77: `return true unless webhook_secret`. Multiple independent GitHub App configs (one per organization) are an explicitly supported, documented feature, each with its own, independently-optional `webhook_secret`: [4](#0-3) [5](#0-4) 

If any onboarded organization has `webhook_secret` left blank (a valid, undocumented-as-dangerous configuration state), then any request that names that organization in `repository.owner.login` (or `organization.login`) is treated as "verified" **regardless of the actual signature header value**.

Once "verified", `create` re-parses the same raw body and dispatches it to event handlers: [6](#0-5) 

Every handler resolves the target `Stack`/`Repository` from a *different* field of the same payload — `repository.full_name` — not from `repository.owner.login`: [7](#0-6) [8](#0-7) 

Nothing enforces that `repository.owner.login` (the org whose secret "authenticated" the request) matches the owner encoded in `repository.full_name` (the repo that is actually mutated). An attacker can therefore submit a payload where:
- `repository.owner.login` = `unsecured-org` (an org onboarded to this Shipit instance with no `webhook_secret`), so verification always passes, and
- `repository.full_name` = `victim-org/real-tracked-repo` (any other repository/stack actually tracked by this Shipit instance),

and the handlers will act on `victim-org/real-tracked-repo` as if GitHub had sent it. This breaks the same equality the report describes for Nouns Builder — a value used to gate a check (there: `quorumVotes`, computed from stale/low-trust state; here: the signing org, read from unverified body) has no real effect on, and is disconnected from, the entity actually written to (there: the executed proposal; here: the target `Stack`/`Repository`/`Commit`).

### Impact Explanation
Concretely reachable, unprivileged-attacker consequences, depending on which handler is hit for the spoofed repository:
- `status` event → `Handlers::StatusHandler` creates a `Status` record on an arbitrary real commit of the victim stack with an attacker-chosen `state`, `context`, and `target_url`. Since deploy gating checks (`commit.deployable?`, used by `require_ci`) are driven by such `Status` records, an attacker can forge a passing CI status for a commit that never actually passed CI, enabling an unauthorized deploy of that stack.
- `push` event → `PushHandler` queues a `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha`, forcing a sync operation unrelated to any real push on that repository.
- `check_suite`, `membership`, `pull_request` handlers are reachable the same way, letting an attacker inject fabricated team/membership or PR-lifecycle events for repositories they do not control.

This lands squarely in the Critical bucket defined by the rules ("unauthorized deploy, rollback, or merge") because a forged passing CI status can unblock deploys that should have been blocked, and in the High bucket ("unauthenticated ... task streams or deploy output" adjacent effects) for the sync/PR-state manipulation paths.

### Likelihood Explanation
Requires only:
1. That the deployment has more than one GitHub App/org configured (a documented, supported feature — `docs/setup.md`), and
2. That at least one of those orgs was configured without a `webhook_secret` (the fixture `test/dummy/config/secrets_double_github_app.yml` shows this is an accepted, non-error configuration; the code path (`return true unless webhook_secret`) treats "no secret" as "trust everything" rather than "reject").

No credentials, GitHub App private key, or session are required — a bare unauthenticated POST to `/webhooks` (mounted per `config/routes.rb`, `resources :webhooks, only: :create`) is sufficient. The likelihood is conditioned on this specific multi-org / blank-secret configuration existing, which is plausible in any Shipit-engine deployment serving several organizations where an operator didn't set a secret for one of them (e.g., staging or newly onboarded orgs).

### Recommendation
- Verify the webhook signature using the secret associated with the repository actually referenced by `repository.full_name` (or reject if that repository/org is not the same one used to pick the signing secret), not a secret picked from an as-yet-unauthenticated `repository.owner.login`/`organization.login` field.
- Treat a missing `webhook_secret` for an organization as "reject all webhooks for this org" rather than "accept all webhooks claiming to be for this org" — i.e., invert the short-circuit in `GithubApp#verify_webhook_signature` so a blank secret fails closed, not open.
- After verifying the signature, re-derive `repository_owner` from the verified payload and cross-check it equals the owner segment encoded in `repository.full_name` before dispatching to handlers, closing the gap between "who authenticated" and "what gets written."

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (no `webhook_secret` set) and `OrgB` (real tracked stack `OrgB/victim-repo`, has a real `webhook_secret`) — mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and any (or no) `X-Hub-Signature` value, and body:
```json
{
  "sha": "<real-sha-of-victim-commit>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example.com",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. `verify_signature` computes `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`) regardless of the (possibly absent/garbage) `X-Hub-Signature`.
4. `create` dispatches to `Handlers::StatusHandler`, which resolves the target stack via `repository.full_name` = `OrgB/victim-repo` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and creates a forged `Status(state: "success")` on the real victim commit — despite the request never being signed by `OrgB`'s secret.
5. A subsequent `deploy` request with `require_ci: true` for that commit now passes the `commit.deployable?` check because of the forged status, per `app/controllers/shipit/api/deploys_controller.rb:22`.

Note: I was unable to fully inspect `lib/shipit.rb`'s `Shipit.github` resolver implementation within the available iterations (only confirmed via tests/docs that it resolves per-organization config and can raise `GithubOrganizationUnknown` for entirely unknown organizations). The exact behavior for organizations that are *known but have a blank secret* is confirmed via `GithubApp#verify_webhook_signature`'s explicit short-circuit and the `secrets_double_github_app.yml` fixture, which is sufficient to establish the vulnerability, but a full session with file access would let a background agent confirm there is no additional guard elsewhere in `lib/shipit.rb`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
