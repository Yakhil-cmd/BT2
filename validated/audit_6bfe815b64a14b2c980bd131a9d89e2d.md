### Title
Cross-repo commit-status forgery via unscoped SHA lookup triggers victim stack's `deployable_status` hook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire database, with no check that the commit's stack actually corresponds to the repository that the incoming webhook was authenticated for. An attacker who controls a repository sharing a commit SHA with a victim stack (e.g. via forking a public repo) can send a legitimately-signed `status` webhook for their own repository and force `Hook.emit(:deployable_status, ...)` to fire for the victim's `Stack`.

### Finding Description
The broken binding, stated explicitly: **the repository that `verify_signature` cryptographically authenticated the webhook for** (`repository_owner` / `params.dig('repository', ...)` in `app/controllers/shipit/webhooks_controller.rb:59-62`) **must equal the repository owned by `commit.stack`** for every `commit` on which `Hook.emit` is triggered. It does not.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload was signed by the GitHub App/org matching `params['repository']['owner']['login']`. It never checks that this repository matches the repository owned by any `Stack`/`Commit` the handler subsequently touches.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This query is scoped **only by `sha`**, not by repository/stack. Since Git SHAs are computed from commit content and are only guaranteed unique within a single history, a SHA can legitimately exist in two different repositories that share ancestry (e.g., a fork of a public victim repo, or a repo seeded with the same initial commits). For every `Commit` record with a matching SHA — regardless of which `Stack`/repository it belongs to — `create_status_from_github!` is called, which calls `add_status`:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [2](#0-1) 

and `add_status` fires:
```ruby
Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
``` [3](#0-2) 

Here `stack` is `commit.stack` — i.e., **whatever stack happens to own the commit row with the matching SHA**, not the stack that corresponds to the repository the webhook was authenticated for.

**Exploit flow:**
1. Attacker forks (or otherwise obtains a repo sharing history/SHAs with) the victim's public repository tracked by Shipit Stack A.
2. Attacker installs/uses their own GitHub App installation or webhook configuration for their own repo B (a normal, unprivileged action any repo owner/GitHub user can perform), or otherwise causes GitHub to emit a `status` event for repo B, signed correctly for repo B's owner.
3. This webhook hits `POST /webhooks` with `repository.owner.login` = attacker's org, `sha` = the shared SHA, and an attacker-chosen `state`/`description`/`target_url`.
4. `verify_signature` succeeds because the signature is valid for repo B's owner — this is exactly what it's designed to check.
5. `StatusHandler#process` finds the `Commit` row belonging to **Stack A** (because `sha` matches, without any repo filter), applies the attacker-controlled status to it, and `Hook.emit(:deployable_status, stack_A, ...)` fires, hitting Stack A's real Slack/webhook integrations with attacker-influenced payload content.

None of the existing guards prevent this: `verify_signature` authenticates the webhook's *originating repository*, not the *target stack/commit* being mutated; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `StatusHandler.params` only validates shape, not repository ownership; there is no `github_repo_name`/`full_name` comparison anywhere in `StatusHandler` or `Commit#create_status_from_github!`.

### Impact Explanation
A payload authenticated for repository B triggers state changes and hook emissions for Stack A's commit/status/hook state — this is a payload-for-one-repository-mutating-another's-stack scenario, matching the **Critical** impact category. Concretely: Stack A's commit status is overwritten with attacker-supplied `state`/`description`/`target_url`, and Stack A's real `Hook` subscribers (Slack, generic webhooks, etc., configured by Stack A's legitimate owner) receive a `deployable_status` event driven entirely by attacker input from an unrelated repository. Since `deployable?` is influenced by status state, this can also affect `schedule_continuous_delivery` and merge-scheduling logic (`stack.schedule_merges`) for Stack A. This is repeatable against any stack whose tracked repo shares a SHA with an attacker-controlled repo (most easily achieved via forking a public repo).

### Likelihood Explanation
Preconditions: Stack A must track a repository whose commit history can be duplicated/shared by the attacker (trivial for any public repo via fork — forks share full commit SHAs with upstream by default). The attacker needs no Shipit credentials, no access to Stack A's Hook config, and no privileged GitHub role — only the ability to own/control a repository and cause GitHub to send a correctly-signed `status` webhook for it (a normal unprivileged GitHub capability). This makes the attack cheap, fully repeatable, and requires no secrets belonging to Shipit or the victim.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) by the stack's repository, not by SHA alone — e.g. resolve the repository from the payload (`params['repository']['full_name']`) and only update commits belonging to stacks whose `github_repo_name` matches that repository before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (no live GitHub):
```ruby
test "StatusHandler does not emit deployable_status for a stack whose repository does not match the webhook payload" do
  stack_a = shipit_stacks(:shipit) # repo "shopify/shipit-engine"
  stack_b_repo_full_name = "attacker/forked-repo"

  shared_sha = "deadbeef" * 5
  commit = stack_a.commits.create!(sha: shared_sha, message: "shared history commit")

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'description' => 'forged',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => stack_b_repo_full_name, 'owner' => { 'login' => 'attacker' } },
  }

  Shipit::Hook.expects(:emit).with(:deployable_status, stack_a, anything).never

  Shipit::Webhooks::Handlers::StatusHandler.new.process(ExplicitParameters::Parameters.new(payload))
end
```
Assertion of the broken binding: `payload['repository']['full_name'] (== "attacker/forked-repo") != stack_a.github_repo_name (== "shopify/shipit-engine")`, yet current code still calls `Hook.emit(:deployable_status, stack_a, ...)` because `Commit.where(sha: params.sha)` ignores repository entirely — the test should fail against current code and pass once the fix scopes the lookup by repository.
