### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized merge queue merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no repository or stack scoping, unlike every other webhook handler which scopes via `Repository.from_github_repo_name`. An attacker who owns any repository can create a commit with an identical sha to a victim's PR head commit, then send a `status` webhook signed by their own org to attach a forged `success` status to the victim's commit record, which `MergeRequest#all_status_checks_passed?` will read and trust.

### Finding Description
The broken binding: `webhook.repository_owner` (the org that signed/authenticated the payload) MUST equal `commit.stack.repository.owner` (the org whose merge gate the status satisfies). In `Shipit::WebhooksController#verify_signature`, the signature is checked against `Shipit.github(organization: repository_owner)`, where `repository_owner` comes from the payload's own `repository.owner.login`/`organization.login` field [4](#0-3) . This only proves the payload was signed by *some* org matching the attacker-controlled `repository` field in their own payload (attacker's org) — it says nothing about which `Commit` rows get mutated.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This is a global, unscoped lookup across the entire `commits` table, spanning every stack/repository in the Shipit instance. Contrast with the base `Handler#stacks` helper used by other handlers (e.g. pull_request handlers), which correctly scopes via `Repository.from_github_repo_name(repository_name)` [3](#0-2) . `StatusHandler` does not use this helper at all, so it never checks that the commit's owning stack belongs to the same repository/org that signed the webhook.

Attack flow:
1. Attacker pushes a commit to `attacker/evil` whose content (tree, parents, author/committer info, message, timestamps) is identical to `victim/prod`'s PR head commit, producing an identical SHA (not a hash break — just data duplication, e.g. cherry-picking the exact same commit object).
2. Victim's PR is queued (`merge_queue_enabled?` true, `!locked?`, `merge_status == 'success'`), and a `MergeRequest` exists in `pending` state with `head.sha` == the colliding sha, with no genuine passing status (would be rejected as `ci_missing`/`ci_failing`).
3. Attacker POSTs `POST /webhooks` with `X-Github-Event: status`, a payload where `repository.owner.login == attacker`, `sha == <colliding sha>`, `state: success`, signed correctly with `attacker`'s webhook secret (which the attacker legitimately possesses for their own repo).
4. `verify_signature` succeeds (attacker really did sign for their own org).
5. `StatusHandler#process` finds **all** `Commit` rows with that sha — including the victim's `Commit` belonging to `victim/prod`'s stack — and calls `commit.create_status_from_github!(params)`, attaching a forged `success` status to the victim's commit.
6. `Commit#statuses_and_check_runs` now includes the forged status [5](#0-4) .
7. `ProcessMergeRequestsJob` (or `add_status`'s `stack.schedule_merges` triggered by the new success status, [6](#0-5) ) re-evaluates the merge request; `MergeRequest#all_status_checks_passed?` calls `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?` [7](#0-6) , which now returns true due to the forged status.
8. `MergeRequest#merge!` is invoked, calling `stack.github_api.merge_pull_request` [8](#0-7) , merging the victim's PR using the victim stack's own GitHub App/token — an unauthorized merge caused entirely by an attacker-signed webhook for an unrelated repository.

Existing guards fail because: `verify_signature` only authenticates "this org signed this payload," not "this org owns the commit being mutated"; `drop_unhandled_event` doesn't filter by repository; the `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`/`state`, not ownership; and `StatusHandler` bypasses the `stacks`/`repository_name`-scoped lookup pattern used elsewhere in the handler hierarchy.

### Impact Explanation
A forged webhook from an attacker-owned repository can inject a fabricated CI status onto a commit belonging to a different, victim-owned stack, and because `add_status` triggers `stack.schedule_merges` on new success states, this can directly cause `MergeRequest#merge!` to execute `stack.github_api.merge_pull_request` using the victim stack's credentials — an unauthorized merge of a PR that would otherwise be rejected as `ci_missing`/`ci_failing`. This is a cross-tenant integrity violation: one repository's webhook mutates another repository's stack/commit/merge-request state and triggers a privileged GitHub API action. This matches "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions are real but non-trivial: (1) `victim_stack.allows_merges?` must be true (merge queue enabled, unlocked, `merge_status == 'success'`); (2) a pending `MergeRequest` must exist for the victim PR; (3) the attacker must produce a commit with an identical SHA to the victim's PR head — feasible without any hash break if the attacker can literally cherry-pick/reuse the exact same commit object (same tree, parents, author/committer timestamps, message) into their own repo, e.g. because the head commit itself originated from a public/shared source, or the attacker colludes with/observes the victim's PR commit and replays it verbatim into a repo they control. This is a repeatable technique that costs the attacker nothing beyond owning a GitHub repository and being able to send one webhook POST; no privileged Shipit access, secrets, or GitHub App keys are needed.

### Recommendation
Scope `StatusHandler#process` (and equivalently `CheckRunHandler` if it has the same pattern) to only update commits belonging to the same repository that signed the webhook, mirroring the `Handler#stacks`/`repository_name` pattern:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status webhook can only mutate commits/statuses for stacks whose `Repository` matches the payload's authenticated `repository.full_name`, closing the cross-repository sha-collision path.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create `victim_repo` (`Shipit::Repository`) with owner `victim`, and `victim_stack` on it with `merge_queue_enabled: true`, unlocked, `merge_status: 'success'`.
2. Create a `Shipit::Commit` for `victim_stack` with `sha: 'deadbeef...'` and no passing statuses.
3. Create a pending `Shipit::MergeRequest` for `victim_stack` whose `head` is that commit.
4. Assert baseline: `merge_request.all_status_checks_passed?` is `false`, and `merge_request.reject_unless_mergeable!` would reject with `'ci_missing'`.
5. Build a `status` webhook payload: `{ repository: { full_name: 'attacker/evil', owner: { login: 'attacker' } }, sha: 'deadbeef...', state: 'success', context: 'ci' }`, sign it with `attacker`'s configured webhook secret (a repo the attacker legitimately owns in test fixtures), and POST it to `/webhooks` with `X-Github-Event: status`.
6. Reload `victim_commit`; assert `victim_commit.statuses_and_check_runs` now contains a `success` status (proving the binding `webhook.repository_owner == commit.stack.repository.owner` was violated — `attacker != victim` yet the write succeeded).
7. Assert `merge_request.reload.all_status_checks_passed?` is now `true`.
8. Call `ProcessMergeRequestsJob.perform_now(victim_stack)` (or invoke the merge path directly) and assert `merge_request.merge!` is invoked / `stack.github_api` receives `merge_pull_request` (stub `github_api`), proving an unauthorized merge occurred as a result of a cross-repository forged status.
