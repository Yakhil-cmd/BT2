## Title
Webhook signature is verified against the org derived from `repository.owner.login`/`organization.login`, but handlers act on the repository derived from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) is used to HMAC-verify an inbound webhook based on `repository_owner`, a value read directly from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). [1](#0-0) [2](#0-1)  Once verification passes, `create` dispatches the same raw payload to event handlers, which independently derive the *acted-upon* repository from a different field, `repository.full_name`. [3](#0-2)  Because Shipit supports multi-tenant GitHub App configuration (`Shipit.github(organization:)` looks up per-organization config, each with its own `webhook_secret`), the field used to select the verification secret (`repository.owner.login`/`organization.login`) is independent of the field used to select the target repository (`repository.full_name`) within the same JSON body. [4](#0-3)  An attacker who controls one tenant's GitHub App webhook secret (e.g. their own organization's app in this Shipit instance) can craft a payload that authenticates as their own organization while pointing `repository.full_name` at a different tenant's repository, causing Shipit to act on that other repository's stacks.

### Finding Description
The equality that should hold is: **organization that authenticated == organization owning the repository being written**. This breaks down as follows:

- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, both fully attacker-controlled fields in the raw JSON body. [1](#0-0) [2](#0-1) 
- `Shipit.github(organization:)` resolves per-tenant GitHub App configuration (`app_id`, `webhook_secret`, etc.) keyed by that organization name via `github_app_config`. [4](#0-3) 
- HMAC verification (`verify_webhook_signature`) only checks that the raw body is signed with *some* organization's configured `webhook_secret` - it says nothing about which repository the body describes. [5](#0-4) 
- Once verification succeeds, `WebhooksController#create` parses the body and dispatches it to handlers using the same JSON, unconditionally. [6](#0-5) 
- Handlers determine the actual repository/stacks to operate on via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — a separate field from the one used for signature-key selection. [3](#0-2) 
- `PushHandler#process`, for example, uses this resolved `stacks` scope to trigger `stack.sync_github(expected_head_sha: params.after)` on real stacks. [7](#0-6) 

Because `repository.owner.login`/`organization.login` and `repository.full_name` are two independently-controlled fields in the same unsigned-at-parse-time JSON body, an attacker who is a legitimate tenant of a multi-org Shipit deployment (and therefore knows their own org's `webhook_secret`) can sign a payload where `organization.login` (or `repository.owner.login`) is their own org, but `repository.full_name` names a different tenant's repository. The signature check passes because it only validates against the attacker's own secret; the handler then acts on the victim tenant's repository because it trusts `full_name` from the same already-"verified" body.

This is the direct analog of the reported bug class: PreviewRedeem verifies/looks up fee parameters keyed by one address (`_addr`) while computing the value from a different implicit context (`account`), letting an attacker manipulate which parameters apply to a transaction that is not actually theirs. Here, the "verified identity" (organization used for HMAC key lookup) and the "value acted upon" (repository derived from `full_name`) are similarly decoupled.

### Impact Explanation
This lets a tenant of one organization spoof pushes/statuses/check-suite/PR events for stacks belonging to another organization's repository in the same Shipit deployment, since `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `PullRequest::*Handler` classes all resolve their target `Repository`/`stacks` from the same cross-controllable `full_name`/`repository.full_name` field. This can trigger unauthorized deploy-triggering actions (`stack.sync_github`, PR merge bookkeeping, etc.) against a repository the attacker does not own — an unauthorized deploy/action performed under another tenant's identity, matching the Critical impact bar ("unauthorized deploy... cross-repository writes").

### Likelihood Explanation
Requires the Shipit instance to be configured for multi-tenant GitHub Apps (`secrets.github` keyed by multiple organizations rather than the single top-level schema) — this is an explicitly supported configuration path in `lib/shipit.rb`. [8](#0-7)  Any tenant onboarded to such a deployment (who legitimately knows their own org's `webhook_secret`, an unprivileged credential relative to other tenants) can attempt this without needing any Shipit session, API token, or elevated access — satisfying the "unprivileged attacker breaking a deployment-trust binding" criterion (organization authenticated vs. repository written).

### Recommendation
After signature verification succeeds for `repository_owner`, cross-check that `repository_owner` matches the owner encoded in `repository.full_name` (and reject mismatches), or better, resolve the target `Repository` first and verify the signature using the webhook secret configured for that repository's *actual* owner rather than a value picked from the same untrusted, potentially inconsistent payload.

### Proof of Concept
1. Deploy Shipit with two tenant organizations configured under `secrets.github`, e.g. `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `lib/shipit.rb#github_app_config`).
2. Attacker, as the legitimate owner of the `attacker-org` GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a JSON push-event body where:
   - `organization.login` = `"attacker-org"` (used only by `repository_owner` for secret selection, per `app/controllers/shipit/webhooks_controller.rb:59-62`)
   - `repository.full_name` = `"victim-org/victim-repo"` (used by `Handler#repository_name`, `app/models/shipit/webhooks/handlers/handler.rb:36-38`)
   - `ref` / `after` set to the branch/commit the attacker wants synced.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies successfully against attacker's own secret. [1](#0-0) 
6. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(...)` on victim's stacks, all without the attacker ever knowing `victim-org`'s webhook secret. [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
