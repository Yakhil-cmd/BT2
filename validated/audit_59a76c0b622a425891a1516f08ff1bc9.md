### Title
`StatusHandler#process` matches commits by SHA alone with no repository binding, allowing cross-repository status forgery - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Finding Description
The claimed binding is: `state == 'success'` visually trusted by an operator on `victim/repo`'s commit == a status actually produced by `victim/repo`'s own CI provider for that exact commit in that exact repository. Tracing the code shows this binding is never enforced at the point where GitHub `status` webhooks are written into the database.

`Shipit::Webhooks::Handlers::Handler` defines a `stacks` helper that scopes lookups to the repository named in the payload via `Repository.from_github_repo_name(repository_name)` [1](#0-0) , and other handlers (`PushHandler`, `PullRequest::*`) use this scoping. `StatusHandler`, however, does not use `stacks` or `repository_name` at all — it looks up commits purely by SHA across the entire `commits` table:

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`create_status_from_github!` unconditionally writes the incoming `state`/`context`/`target_url` as a `Status` row tied to `commit.stack_id`, and can flip `commit.state` to `success`: `add_status`/`create_status_from_github!` [3](#0-2) . `Commit#deployable?` then reads `success? && !blocked?` off exactly that forged status: `def deployable? !locked? && (stack.ignore_ci? || (success? && !blocked?)) end` [4](#0-3) .

**Exploit path (does not even require a genuine SHA-1 collision):**
1. Attacker owns (or administers) any GitHub repository/org that is already configured in this Shipit instance with a `webhook_secret` (`secrets.github[org]`), which is a normal, unprivileged multi-tenant setup — the attacker only has rights over their own repo/org, not the victim's.
2. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` comes straight from the attacker-controlled payload (`repository.owner.login` / `organization.login`) [5](#0-4) [6](#0-5) . Signature verification only checks that the HMAC matches the secret configured for **that** organization [7](#0-6)  — i.e., it authenticates "this request really came from `attacker/repo`'s webhook," not "this status really describes `attacker/repo`'s commit."
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org, `repository.full_name = "attacker/repo"`, and `sha` set to the victim's real, publicly-known commit SHA (from `victim/repo`, tracked by a different stack on the same Shipit instance), `state: "success"`.
4. `StatusHandler.process` finds the `Commit` row by SHA regardless of which repository it belongs to and calls `commit.create_status_from_github!(params)`, writing a fabricated `success` status onto the **victim's** commit, under the **victim's** `stack_id`.
5. `Commit#deployable?` on the victim stack now returns `true` for that commit, `stack.next_expected_commit_to_deploy` / `next_commit_to_deploy` will pick it up, and either continuous delivery (`schedule_continuous_delivery`) or a human operator clicking "Deploy" in `DeploysController#create` → `Stack#trigger_deploy` will act on it — neither re-verifies the commit's real CI/provider/repository at deploy time.

**Why existing guards fail:** `verify_signature` validates the wrong binding (organization-of-sender, not repository-of-commit). `drop_unhandled_event` and `ExplicitParameters` only validate payload *shape* (`sha`, `state` as strings), not repository ownership of the SHA. There is no model validation or uniqueness constraint tying a `sha` to a single `Repository`/`Stack` — commits across different stacks can legitimately share row-level independence, and `StatusHandler` never checks `commit.stack.repository` against the payload's `repository.full_name`.

### Impact Explanation
A forged CI status is written for a commit belonging to a repository/stack the attacker does not control, directly satisfying the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy... of unverified code." The operator relying on the green check (or the continuous-delivery scheduler) can deploy or merge code that never passed the victim repository's actual CI. This is repeatable against any commit SHA the attacker can learn (commit SHAs are frequently public via GitHub PRs/branches), for any stack hosted on the same Shipit instance, as long as the attacker has any onboarded repo/org of their own to source a validly-signed webhook from.

### Likelihood Explanation
Preconditions: a multi-tenant Shipit deployment (multiple `secrets.github` org entries or multiple stacks), the attacker controlling at least one such repo/org's webhook secret (trivial — they set it themselves when adding the webhook to their own repo), and knowledge of the victim commit's SHA (usually public). No SHA-1 collision is actually required by this code path — `Commit.where(sha:)` matches on exact SHA equality across all stacks, so the attacker simply reuses the victim's real SHA. This makes the attack considerably more feasible than the SHA-collision premise in the question implies, and does not require attacker access to GitHub App private keys, `webhook_secret` of the victim's org, or any Shipit session/API token.

### Recommendation
Scope `StatusHandler#process` to the reporting repository the same way other handlers do, e.g. restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (using the `Handler#stacks`/`repository_name` helper already defined on the base class), so a status can only be applied to commits belonging to stacks whose `Repository` matches the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "status webhook cannot forge success status onto a commit from a different repository" do
  victim_stack = shipit_stacks(:shipit)             # repo: shopify/shipit-engine
  victim_commit = shipit_commits(:fifth)            # not yet deployed, currently pending/no status
  refute_predicate victim_commit, :deployed?
  refute_predicate victim_commit, :deployable?

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' } # attacker's own, differently-owned repo
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  refute_predicate victim_commit, :deployable?, # binding must hold: forged status must NOT make it deployable
    "status reported against attacker/unrelated-repo must not satisfy CI for victim commit"
end
```
Currently this assertion **fails** (i.e. `victim_commit.deployable?` becomes `true`) because `StatusHandler#process` matches `Commit.where(sha: params.sha)` without checking `params['repository']['full_name']` against `victim_commit.stack.repository.full_name`, confirming the vulnerability described above.
