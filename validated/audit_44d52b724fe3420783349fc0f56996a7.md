### Title
Platform-Dependent secp256k1 Implementation (Native vs. `elliptic` JS Fallback) Can Cause Signature-Verification Disagreement Between Full Nodes and Browser/Light Clients - (File: package.json, signature.js)

### Summary
`ocore`'s `package.json` remaps the `secp256k1` dependency to its pure-JavaScript `elliptic`-based implementation for browser/bundled builds, while Node.js/desktop full nodes use the native C-binding implementation of the same package. This is the same bug class as CVE-2023-1160 (CWE-1103, "Use of Platform-Dependent Third Party Components"): identical application logic silently relies on two different underlying cryptographic implementations depending on the runtime platform. All ECDSA signature verification used for unit authentifiers and PEM-based secp256k1 signatures funnels through `signature.js`, which calls the same `secp256k1` API (`ecdsaVerify`, `signatureNormalize`, `signatureImport`) without any platform-specific normalization guarantee. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The `browser` field in `package.json` maps `"secp256k1": "secp256k1/elliptic"`, meaning any bundler-built target (webpack/browserify used for light wallets, mobile/Cordova apps — `conf.js` explicitly detects `bCordova` and switches to light mode) resolves `secp256k1` to its bundled `elliptic.js` fallback instead of the native `bindings.js`/libsecp256k1 C addon used by desktop Node.js full nodes/hubs. [1](#0-0) [4](#0-3) 

`signature.js` (used by `definition.js`'s `'sig'` authentifier evaluator, by device-message and temp-pubkey verification in `network.js`, and by `is_valid_sig`/PEM secp256k1 verification in the oscript formula evaluator) performs verification purely through this swappable module:
- `verify()` calls `ecdsa.ecdsaVerify(signature, hash, pubkey)` directly.
- `verifyMessageWithSecp256k1PemPubKey()` normalizes imported DER signatures via `ecdsa.signatureNormalize()` before calling `ecdsaVerify`. [5](#0-4) [3](#0-2) 

Native libsecp256k1 bindings and the `elliptic` JS fallback are different, independently-implemented codebases and are not guaranteed to accept or reject exactly the same byte-for-byte inputs (e.g., malformed DER edge cases in `signatureImport`, treatment of borderline `r`/`s` values, or低-level parsing quirks). Because `ecore` never rejects malformed/edge-case signatures with a single canonical rule enforced independently of the crypto backend — it simply forwards to whichever `secp256k1` variant the bundler resolved — the same signature bytes can be accepted by one platform build and rejected by another. This directly reproduces the CWE-1103 pattern from the reported advisory: security-relevant behavior (accept/reject) is delegated to a platform-selected third-party component whose behavior is assumed, but not verified, to be identical across platforms.

Full unit signature verification (`'sig'` authentifier check in `definition.js`) only executes inside `validation.js`'s full/non-light `validate()` path; light nodes short-circuit before reaching authentifier checks (`conf.bLight` branch returns early). However, `signature.js`'s `verify()`/`sign()` are also invoked directly and unconditionally (regardless of `conf.bLight`) for device-message/temp-pubkey authentication in `network.js`, and for `is_valid_sig`/signed-package verification used by AA formulas and private payment/signed-message flows that light or mobile wallets do execute locally. ### Impact Explanation
If the `elliptic` fallback accepts a signature (e.g., a crafted/malformed DER encoding or borderline `s` value) that native libsecp256k1 rejects, or vice versa, then a browser/mobile-bundled wallet (light client, private-payment counterparty, or device-message recipient) can reach a different validity conclusion than a full node/hub for the exact same signed message. This can let a counterparty in a private payment or signed-package exchange believe they hold a validly-authenticated, spendable payment/message while the referencing unit or authentifier would actually be rejected as invalid on a genuine full node — a form of unauthorized/fraudulent private-payment acceptance and node disagreement on validity, matching the medium-severity impact class from the source advisory (platform-dependent behavior causing incorrect acceptance of an operation that should have been rejected).

### Likelihood Explanation
The likelihood is moderate: an attacker needs to craft a boundary-case ECDSA signature (non-canonical `s`, ambiguous DER encoding, etc.) that produces divergent accept/reject outcomes between libsecp256k1 (native) and `elliptic` (JS). Both libraries are widely used and mostly compatible, so producing a concrete divergent input requires careful signature construction/fuzzing of `signatureImport`/`ecdsaVerify` edge cases; this was not proven with a concrete PoC signature in this analysis — only the architectural exposure (two different crypto backends silently swapped per platform, feeding the same validation logic) was confirmed in the code.

### Recommendation
- Pin/force a single JS implementation of secp256k1 verification (or vendor a strict, canonicalized wrapper) regardless of build target, instead of relying on `package.json`'s `browser` field substitution to silently swap native vs. `elliptic` implementations.
- Add an explicit signature-canonicalization/validation layer (reject non-canonical `s`, strictly validate DER structure per BIP-66) in `signature.js` before calling into the underlying `secp256k1` implementation, so behavior is deterministic independent of which backend is loaded.
- Add cross-implementation differential test vectors (edge-case DER/compact signatures) run against both the native and `elliptic` code paths in CI to detect divergence before release.

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
}
