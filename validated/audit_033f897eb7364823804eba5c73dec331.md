## Title
Sequential division truncation in migration-epoch reward calculation causes precision loss / lost stake rewards - (`runtime/src/inflation_rewards/mod.rs`)

### Summary
The migration-epoch branch of `calculate_stake_rewards` computes a staker's tower-portion reward by performing **two separate divide operations** in sequence — first dividing `tower_points * point_value.rewards` by `point_value.points`, and then multiplying that truncated intermediate result by `num_tower_slots` and dividing again by `total_slots` — instead of combining all multiplications before a single final division.

### Finding Description
In `calculate_stake_rewards`, the `AlpenglowEpochType::MigrationEpoch` arm computes: [1](#0-0) 

```rust
let total_slots = (num_tower_slots + num_ag_slots) as u128;
let tower_points = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points)
    .unwrap()
    .checked_mul(*num_tower_slots as u128)
    .unwrap()
    .checked_div(total_slots)
    .unwrap();
tower_points + ag_points
```

The mathematically correct (precision-preserving) formula is:

`tower_points * point_value.rewards * num_tower_slots / (point_value.points * total_slots)`

i.e. all multiplications should occur before the single division. Instead, this code performs `div` → `mul` → `div`, meaning the first division (`.checked_div(point_value.points)`) can truncate the result to a small integer (or to `0`) *before* it is scaled by `num_tower_slots` and reduced by `total_slots`. This is the exact "division before multiplication" precision-loss pattern described in the referenced Ajna report: an intermediate quotient is computed and then further scaled/divided, compounding rounding error and potentially collapsing a legitimately non-zero reward to zero.

This differs from the sibling `Tower` branch a few lines above, which performs a single `mul` then `div` and is correctly ordered: [2](#0-1) 

Contrast this also with the `calculate_alpenglow_points` function's `ag_points` scaling, which correctly multiplies first and divides once (`earned_credits * stake_amount / total_stake`): [3](#0-2) 

### Impact Explanation
This code path runs for every delegated stake account during the one-time Tower→Alpenglow migration epoch, as part of the core inflation reward redemption flow (`redeem_rewards` → `calculate_stake_rewards` → this migration branch), which is reached from `redeem_delegation_rewards` in the epoch-rewards distribution logic used for all stakers, not just validator/operator roles: [4](#0-3) 

Because the first division by `point_value.points` (a network-wide total that can be very large relative to any individual staker's points) executes before the subsequent `* num_tower_slots / total_slots` scaling, small-to-mid-size stake accounts can have their computed tower-portion reward rounded down to a smaller value than intended, or to zero, purely due to arithmetic ordering rather than because they earned no reward. This results in permanently lost/misattributed lamports for affected stakers during the migration epoch's reward distribution — rewards that should have been paid are silently dropped due to truncation, matching the "rewards lost (0)" impact of the referenced report.

### Likelihood Explanation
This code executes unconditionally and automatically for every stake account during the migration epoch's reward calculation — it requires no special privileges, attacker action, or unusual configuration, only that a migration epoch with non-zero `tower_points` occurs (which is expected to happen exactly once during the Alpenglow migration, and is exercised in the codebase's own migration tests, e.g. `test_migration_epoch_dust_split_advances_credits`): [5](#0-4) 

Because stake amounts, credits, and slot ratios vary widely across the network, some non-trivial fraction of stakers with proportionally small `tower_points` relative to `point_value.points` will hit this precision loss during the single migration epoch.

### Recommendation
Combine the four operations into a single multiplication chain followed by one division, mirroring the fix pattern for the original Ajna finding:

```rust
let tower_points = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .and_then(|v| v.checked_mul(*num_tower_slots as u128))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points.checked_mul(total_slots).unwrap())
    .unwrap();
```

Verify that `point_value.points * total_slots` does not overflow `u128` given realistic bounds (points already fits in `u128` from staking totals; extra margin should be checked), and add a regression test exercising a case where the previous two-step division would have truncated to zero while the combined single-division approach yields a non-zero reward.

### Proof of Concept
Consider values (illustrative, within plausible network ranges):
- `tower_points = 1_000`
- `point_value.rewards = 1_000_000`
- `point_value.points = 2_000_000_000` (aggregate network points)
- `num_tower_slots = 3`
- `total_slots = 432_000` (slots in the migration epoch)

Current (buggy) sequential computation:
1. `1_000 * 1_000_000 = 1_000_000_000`
2. `1_000_000_000 / 2_000_000_000 = 0` (integer division truncates)
3. `0 * 3 = 0`
4. `0 / 432_000 = 0`

Result: **0** reward lamports for the tower portion.

Correct (multiply-first) computation:
1. `1_000 * 1_000_000 * 3 = 3_000_000_000`
2. `2_000_000_000 * 432_000 = 864_000_000_000_000`
3. `3_000_000_000 / 864_000_000_000_000 = 0` (still 0 in this specific example, but demonstrates the compounding truncation)

With larger `num_tower_slots` or `tower_points` relative to `point_value.points`, the two-division version truncates to zero at step 2 in cases where the combined single-division formula would still yield a small non-zero value, causing avoidable loss of staker rewards purely from computation order.
