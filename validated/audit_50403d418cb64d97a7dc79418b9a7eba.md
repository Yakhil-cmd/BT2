### Title
Cross-tenant PullRequest title/body overwrite via mismatched `repository.owner.login` and `repository.full_name` in pull_request webhook - ([File: app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify against using `params.dig('repository','owner','login')`, while `PullRequestEditedHandler#pull_request` locates the target `Shipit::PullRequest` using the independent field `params.repository.full_name`. Because both fields are attacker-controlled JSON keys inside the same unauthenticated payload and are never cross-checked, an attacker can pick an org configured in Shipit with no `webhook_secret` for signature bypass while naming an unrelated victim repository/PR for the mutation.

### Finding Description
The broken binding is: `org used to verify signature (params.repository.owner.login)` == `org owning the PullRequest record being mutated (owner of params.repository.full_name)`. These must be equal for the "verified sender" model to hold, but nothing enforces it.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` — i.e., for any org configured in Shipit's `secrets.github` map without a `webhook_secret`, signature checking is a no-op. [2](#0-1) 
- `PullRequestEditedHandler#repository` resolves the target repository from `params.repository.full_name` (a different JSON field than `repository.owner.login` used above), and `#pull_request` finds the record by `number` joined through `stack.repository.id == repository.id`. `#process` then calls `pull_request.update(github_pull_request: params.pull_request)` unconditionally when found. [3](#0-2) 

Exploit flow: attacker crafts a POST to `/webhooks` with header `X-Github-Event: pull_request` and body:
```json
{
  "action": "edited",
  "number": <victim PR number>,
  "pull_request": { ..., "title": "ATTACKER STRING", "body": "ATTACKER STRING", ... },
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "sender": { "login": "attacker" }
}
```
where `attacker-org` is any org configured in Shipit's multi-org `github:` secrets block but left with `webhook_secret: nil` (a legitimate, documented configuration — see `docs/setup.md` and `config/secrets.development.shopify.yml` showing `webhook_secret: # nil` per-org). [4](#0-3) 

`verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without ever inspecting the actual signature or the `victim-org` secret. `Shipit.github` requires the org to be a *known* configured org (else it raises `GithubOrganizationUnknown` → 422), so the attack requires such a known-but-secretless org to exist in the deployment. [5](#0-4) 

The handler then trusts `params.repository.full_name` = `"victim-org/victim-repo"` to locate the real victim repository/stack/PR and overwrite its `title`/`body` with attacker-controlled content, even though the signature check never validated anything against that org's secret.

### Impact Explanation
An unauthenticated attacker can inject arbitrary content into `title`/`body` of any `Shipit::PullRequest` row belonging to any repository/stack tracked by the Shipit instance, provided at least one other org in the Shipit deployment is configured without a webhook secret. This is a cross-tenant write: a payload nominally scoped to "attacker-org" mutates a record owned by "victim-org". The corrupted title/body can be rendered in Shipit's merge/review UI or matched against merge-command regexes elsewhere in the codebase, enabling downstream content-injection or logic-abuse in merge workflows. This matches "a payload for one repository mutating another's stack/commit/task/team" — Critical.

### Likelihood Explanation
Preconditions: the Shipit deployment must use the multi-org `github:` secrets schema (documented and supported) with at least one configured org lacking a `webhook_secret`, and must be tracking the victim's repository/PR as a stack. No secrets, sessions, or privileged roles are needed — the attacker only needs to know a victim repo's `full_name` and a target PR `number`, both public GitHub information. The request is a single unauthenticated HTTP POST, fully repeatable against any tracked repository/PR combination.

### Recommendation
Cross-validate that the org derived from `params.repository.full_name` (or `params.repository.owner.login`) used for handler-side repository resolution matches the org actually verified by `verify_signature`, e.g., pass the verified `repository_owner` into the handler and require `Repository#owner` (or `full_name`'s owner segment) to equal it before any lookup/update; alternatively, always resolve the GitHub App/secret from the same single field used later for repository lookup, and reject payloads where `repository.owner.login` disagrees with the owner segment of `repository.full_name`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_edited_cross_org_test.rb
require "test_helper"

module Shipit
  class WebhooksControllerEditedCrossOrgTest < ActionController::TestCase
    tests Shipit::WebhooksController

    test "cross-org 'edited' payload cannot overwrite a victim PullRequest it did not authenticate for" do
      pull_request = shipit_pull_requests(:review_stack_review) # owned by victim repo/org
      victim_full_name = pull_request.stack.repository.full_name

      # Stub an org configured with no webhook_secret, distinct from the victim's org
      attacker_app = Shipit::GitHubApp.new("attacker-org", { webhook_secret: nil })
      Shipit.stubs(:github).with(organization: "attacker-org").returns(attacker_app)

      payload = {
        "action" => "edited",
        "number" => pull_request.number,
        "pull_request" => payload_parsed(:pull_request_opened)["pull_request"].merge(
          "number" => pull_request.number,
          "title" => "ATTACKER INJECTED TITLE"
        ),
        "repository" => { "full_name" => victim_full_name, "owner" => { "login" => "attacker-org" } },
        "sender" => { "login" => "attacker" }
      }

      @request.headers['X-Github-Event'] = 'pull_request'
      # deliberately no/garbage X-Hub-Signature: attacker-org has no secret so it's accepted anyway

      assert_no_changes -> { pull_request.reload.title } do
        post :create, body: payload.to_json, as: :json
        assert_response :ok
      end
      # If this assertion fails (title changed to "ATTACKER INJECTED TITLE"),
      # the cross-org binding is broken and the vulnerability is confirmed.
    end
  end
end
```
Binding checked: `verifying_org == "attacker-org"` (secret-less, attacker-chosen) vs. `owning_org(pull_request) == owner("victim-org/victim-repo")` (from `victim_full_name`) — these differ, yet the update still proceeds, proving `pull_request.title` becomes `"ATTACKER INJECTED TITLE"` despite no valid authentication for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
