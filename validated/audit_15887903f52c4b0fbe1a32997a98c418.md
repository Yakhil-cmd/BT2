### Title
Webhook signature verified against the payload's `repository.owner.login` while handlers act on the untrusted `repository.full_name` field, allowing cross-organization webhook forgery in multi-tenant Shipit deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook against based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body. Every downstream `Handler` subclass (e.g. `PushHandler`) instead resolves the target `Stack`/`Repository` using a completely different field of the same untrusted body: `repository.full_name`. Because HMAC verification is bound to one field while the write-target is bound to another, unequal field, an attacker who legitimately controls a GitHub App/secret for **one** organization configured in a multi-org Shipit instance can forge a validly-signed webhook whose `repository.owner.login` matches their own org (so the HMAC check passes) but whose `repository.full_name` points at a stack belonging to a **different** organization/tenant hosted on the same Shipit instance.

### Finding Description
`verify_signature` picks the `GitHubApp`/secret used for HMAC validation from `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks the App config up by exactly this attacker-supplied organization name in multi-app configurations: [3](#0-2) 

The base `Handler` class (used by `PushHandler` and all other webhook handlers) resolves the affected repository/stack from a different, independent field of the same JSON body — `repository.full_name` — not `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because both fields are attacker-controlled JSON body content and only `repository.owner.login`/`organization.login` is bound by the signature check, an attacker who owns/administers a GitHub App for `OrgB` (and therefore legitimately possesses `OrgB`'s `webhook_secret`, as documented for multi-org setups) can sign a payload with `repository.owner.login = "OrgB"` (passes `verify_signature`) but `repository.full_name = "OrgA/some-repo"`. The `PushHandler` will then use `full_name` to locate `OrgA`'s `Repository`/`Stack` and enqueue `GithubSyncJob` with attacker-chosen `params.after`: [6](#0-5) 

`GithubSyncJob` fetches real commits via the stack's own (OrgA) GitHub API/App and appends them, then may trigger `CacheDeploySpecJob` and, subsequently, continuous delivery: [7](#0-6) [8](#0-7) 

The multi-org configuration this depends on is explicitly documented and supported: [9](#0-8) 

The break in the trust binding: **the organization whose secret authenticated the request ≠ the repository whose stack is written to by the handler**, because verification is keyed on `repository.owner.login`/`organization.login` while execution is keyed on `repository.full_name`.

### Impact Explanation
In multi-organization Shipit installations, an attacker holding a legitimate webhook secret for one tenant (their own organization's GitHub App) can force Shipit to enqueue `GithubSyncJob`/`CacheDeploySpecJob` (and potentially trigger `ContinuousDeliveryJob`) for a stack belonging to an entirely different tenant/organization hosted on the same Shipit instance, at a time of the attacker's choosing, and bypassing the intent of per-organization webhook secret isolation. This is an authorization boundary violation between tenants (an unauthorized cross-repository/cross-organization interaction and potential trigger of an unauthorized deploy pipeline action), which the multi-org feature is specifically meant to prevent.

### Likelihood Explanation
Requires the attacker to already control a legitimate GitHub App/webhook secret for at least one organization configured on the target Shipit instance (a supported, documented "Using Multiple Github Applications" configuration). This is a real precondition in shared/multi-tenant Shipit deployments where different organizations each run their own low-trust GitHub App while sharing one Shipit installation — the attacker does not need any Shipit account, API token, or access to the victim organization.

### Recommendation
Bind the webhook-secret selection and the handler's target-repository resolution to the *same* verified field. Concretely, `WebhooksController` should re-verify (or the `Handler` base class should independently re-derive and cross-check) that `repository.full_name`'s owner segment matches the `repository_owner`/`organization.login` value that was used to select the signing secret, rejecting the webhook if they differ.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the attacker administering `OrgB`'s GitHub App, craft a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-that-exists-on-github>",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" }
}
```
3. Sign the raw body with `OrgB`'s known `webhook_secret` using HMAC-SHA1, and set `X-Hub-Signature`/`X-Github-Event: push`.
4. POST to `/github/webhooks`. `verify_signature` calls `Shipit.github(organization: "OrgB")` and succeeds because the signature matches `OrgB`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgA/victim-repo")`, unrelated to `OrgB`, and enqueues `GithubSyncJob` for `OrgA`'s stack — an action never authorized by `OrgA`'s own webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
