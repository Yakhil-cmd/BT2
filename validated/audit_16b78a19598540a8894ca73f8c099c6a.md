### Title
Cross-repository status forgery leading to unauthorized deploy via `StatusHandler` global commit lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the **organization** derived from the payload (`repository.owner.login` / `organization.login`), selecting the matching `GitHubApp`/`webhook_secret` for that org. Nothing in the controller or in `Webhooks::Handlers::StatusHandler` binds the verified organization/repository to the actual database rows that get mutated for the `status` event. `StatusHandler#process` looks up commits **globally** by SHA (`Commit.where(sha: params.sha)`), across every stack/repository/organization configured in the Shipit instance, and creates a `Status` for each match.

### Finding Description
`WebhooksController#verify_signature` selects the signing secret using only the repository owner name found in the payload: [1](#0-0) [2](#0-1) 

This proves the payload was signed with *some* organization's `webhook_secret` (as configured in `config/secrets.yml`, which supports [multiple GitHub Apps per organization](https://github.com/Jortegata/shipit-engine--025/blob/main/docs/setup.md)). It does **not** prove that the commit SHA referenced elsewhere in the same payload actually belongs to a repository/stack under that organization.

Unlike `Webhooks::Handlers::Handler#stacks`, which scopes lookups to the repository named in the payload: [3](#0-2) 

`StatusHandler#process` bypasses this scoping entirely and queries `Commit` globally by SHA only: [4](#0-3) 

`Commit#create_status_from_github!` then creates a `Status` row, which (via `Commit#add_status` and `Commit#schedule_continuous_delivery`) can enqueue a real deploy if the target stack has continuous deployment enabled: [5](#0-4) [6](#0-5) 

The broken binding, stated as an equality that the code fails to enforce:
`organization authenticated by verify_signature (repository.owner.login)` == `organization owning the commit/stack mutated by StatusHandler (Commit#stack)`

Before the attacker's request: only GitHub, holding the real per-org `webhook_secret`, can produce a validly signed `status` event for a given org, and that event's `sha` is guaranteed by GitHub to belong to the repository named in that same event.

After the attacker's request: anyone who knows (or administers) the `webhook_secret` for **any one** organization/App configured in the Shipit instance can sign an arbitrary JSON body with `repository.owner.login` set to their own org (satisfying `verify_signature`) while setting `sha`/`state` to reference a commit belonging to a **completely different** stack/organization tracked by the same Shipit instance. `StatusHandler` will happily create a `success` status on that unrelated commit.

### Impact Explanation
If the targeted stack has `continuous_deployment` enabled, forging a `success` status for the tip commit causes `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` to enqueue a real deploy of a repository/stack the attacker has no legitimate access to — an **unauthorized deploy**, which matches the Critical impact bucket ("an unauthorized deploy, rollback, or merge"). It also lets an attacker with only one org's webhook credentials write arbitrary CI/status history (state, description, target_url) onto commits of unrelated repositories, which is itself a cross-repository write. The required precondition — knowledge of the sha of an already-tracked commit — is generally satisfiable because commit SHAs are public GitHub data (visible in PRs, commit URLs, CI logs, etc.), not secret.

### Likelihood Explanation
Exploitability requires the attacker to control (or know) a valid `webhook_secret` for at least one organization/App configured in the multi-org `github:` section of `config/secrets.yml` — this is a realistic scenario for any Shipit deployment serving more than one organization/team where each org's admins set up and know their own App's webhook secret, since the engine's authentication model treats "signed by org A's secret" as authorization only for org A's own traffic, but the handler does not enforce that scope. This is a code-level authorization gap independent of any GitHub-side misconfiguration, and is triggered by a single crafted POST to `/webhooks`.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks resolved for the payload's `repository.full_name` (i.e., reuse `Handler#stacks`) instead of querying `Commit` globally by SHA, e.g. `stacks.each { |stack| stack.commits.find_by(sha: params.sha)&.create_status_from_github!(params) }`. More generally, every webhook handler should derive the target stack from the same repository identity that was used to select/verify the webhook signature, and `WebhooksController#verify_signature` should additionally assert that the repository named in the payload actually belongs to the organization whose secret verified the signature.

### Proof of Concept
1. Assume Shipit is configured with multiple GitHub orgs (per `docs/setup.md`, "Using Multiple Github Applications"), and the attacker controls `webhook_secret` for `org-attacker` (e.g., they administer the corresponding GitHub App on their own org).
2. Identify the SHA of a commit belonging to `org-victim/some-repo`, a stack tracked by the same Shipit instance, with `continuous_deployment: true` (SHAs are public on GitHub).
3. POST to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "repository": { "owner": { "login": "org-attacker" } },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged"
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-attacker webhook_secret, raw_body)>` and send.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-attacker")`, verifies successfully with the attacker's own known secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit (belonging to a different org/stack entirely), creating a `success` `Status` on it, which can trigger `ContinuousDeliveryJob` for `org-victim/some-repo`.

Note: Full confirmation of exploitability in the single-org default configuration (where `Shipit.github(organization:)` may resolve to the same App/secret regardless of the `organization` argument) was not verified from `lib/shipit.rb`'s selection logic within the available index; the multi-org case, documented in `docs/setup.md`, is the clearest concrete instance of this trust-boundary break.
