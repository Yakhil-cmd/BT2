### Title
Forged CI status webhook bypasses org-signature binding to force auto-deploy on an arbitrary stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` binds a webhook's authenticity to a GitHub *organization* (resolved from `repository.owner.login`), but `StatusHandler#process` writes a CI status to *any* `Commit` row in the entire database that matches the attacker-supplied `sha`, with no repository/stack/organization scoping. Because `GithubApp#verify_webhook_signature` trivially returns `true` whenever no `webhook_secret` is configured for that organization (the documented/example default), an attacker can drive this handler with no credentials at all, forging a passing CI status on any commit and triggering an unauthorized deploy via continuous delivery.

### Finding Description
Webhook authenticity is anchored to an organization, not to the repository/commit actually mutated: [1](#0-0) 

The organization used for verification is taken from the attacker-controlled JSON body itself (`repository.owner.login` / `organization.login`): [2](#0-1) 

Signature verification is a no-op whenever the organization's `webhook_secret` is blank: [3](#0-2) 

and the setup docs/config templates ship with `webhook_secret: # nil` as the default, meaning many installs never configure it: [4](#0-3) 

Once past this check, the `status` event is routed to `StatusHandler`, which resolves the target purely by `sha` — a value from the same unverified payload — across **all** stacks/repositories, with no reference back to `repository.full_name` or the organization used for signing: [5](#0-4) 

Contrast this with `PushHandler`, which at least re-derives the target via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`: [6](#0-5) 

`StatusHandler` skips that indirection entirely and matches on `sha` alone, so it is not even consistently scoped to the repository named in the same payload, let alone to the organization whose (possibly absent) secret gated the request.

**Trust binding broken (equality that should hold but doesn't):**
`organization authenticated by signature` == `repository/commit whose CI status is written`.

Before the attacker's request: only GitHub, using the org's real webhook secret, can produce a status update for commits belonging to that org's repositories.
After: anyone who can reach the public `/github/webhooks` endpoint can set `state: "success"` for `context: "ci/travis"` (or whatever `ci.require` expects) on any known commit `sha` tracked by Shipit, regardless of which org/repo it belongs to, as long as either (a) the org has no `webhook_secret` configured, or (b) the attacker picks a `repository.owner.login`/`organization.login` value that maps to an org whose secret is unset/known.

### Impact Explanation
A forged, passing CI status directly feeds `Commit#deployable?`/`Stack#next_commit_to_deploy` and, for stacks with `continuous_deployment: true`, is picked up by `Stack#trigger_continuous_delivery` to automatically build and run a deploy: [7](#0-6) [8](#0-7) 

This lets an unauthenticated, unprivileged network attacker force Shipit to consider an untested/otherwise-blocked commit "deployable" and cause an unauthorized deploy to run against production infrastructure — matching the "unauthorized deploy" Critical-impact criterion. It also lets an attacker manipulate `merge_status`/PR merge-queue decisions for repositories they have no access to.

### Likelihood Explanation
Likelihood is Medium-to-High in the common configuration where `webhook_secret` is left unset (the value shipped in every example/dev secrets file in this repo is `# nil`), which requires zero attacker credentials. Even where a secret is configured for the org that legitimately owns the target commit, an attacker only needs *any* other organization configured in the same Shipit instance (or one with no secret) to pass `verify_signature`, since the actual write path (`StatusHandler`) never checks that the authenticated organization matches the commit's repository.

### Recommendation
- In `StatusHandler#process` (and any other handler doing raw lookups), scope the query by the repository derived from `repository.full_name` in the payload (as `PushHandler`/`Handler#stacks` already do), not by `sha` alone.
- In `WebhooksController#verify_signature`, fail closed instead of returning `true` when `webhook_secret` is blank (`lib/shipit/github_app.rb#verify_webhook_signature`), or require operators to always configure a secret.
- Cross-check that the organization used to select the signing secret matches the organization actually referenced by `repository.full_name`/`repository.owner.login` before processing any handler that mutates commit/stack state.

### Proof of Concept
1. Identify (or leave default) a Shipit-configured GitHub organization, `OrgX`, with no `webhook_secret` set (default per `config/secrets.development.example.yml`), and note the sha of a commit tracked under a *different* org/repo's stack (`OrgY/app`) that is currently blocked from deploy (missing/pending required CI context, e.g. `ci/travis`).
2. `POST /github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<target commit sha in OrgY/app>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "OrgX" } }
}
```
No valid `X-Hub-Signature` is required because `OrgX` has no `webhook_secret`; `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-38`) passes trivially via `GithubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds the commit by `sha` alone and creates the forged success status on it, with no check that it belongs to `OrgX`.
4. If the `OrgY/app` stack has `continuous_deployment: true`, `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`) picks up the now-"deployable" commit on its next scheduling pass and enqueues an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
