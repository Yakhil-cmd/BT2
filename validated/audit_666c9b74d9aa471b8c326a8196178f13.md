### Title
Denial of Service via Slowloris-style resource exhaustion on git-sync's HTTP endpoint due to missing server timeouts - ([File: main.go])

### Summary
`git-sync`'s optional HTTP endpoint (enabled via `--http-bind`) is served with `http.Serve(ln, mux)` on a bare `net.Listener`, which uses Go's zero-value `http.Server` internally. That configuration sets no `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, or `IdleTimeout`, so accepted TCP connections can be held open indefinitely by a client that sends data slowly or not at all. This is the same class of bug as CVE-2020-8251: unbounded connection lifetime allows an unauthenticated remote attacker to exhaust the process's file descriptors/goroutines with a small number of slow connections, denying service to the liveness, metrics, and pprof endpoints — and, because `http.Serve`'s returned error triggers `os.Exit(1)`, potentially crashing the whole `git-sync` process.

### Finding Description
The HTTP endpoint is set up in `main()`: [1](#0-0) 

Key details:
- `ln, err := net.Listen("tcp", *flHTTPBind)` creates a raw listener, and `http.Serve(ln, mux)` is called directly instead of constructing an `http.Server{}` with explicit `ReadHeaderTimeout`/`ReadTimeout`/`WriteTimeout`/`IdleTimeout` fields.
- Go's `http.Serve` uses an implicit `http.Server` with all timeout fields at their zero value (no timeout), which is functionally identical to the Node.js `server.timeout = 0` scenario described in the report: sockets are never considered idle by the runtime, so a client that trickles bytes (or sends nothing after connecting) keeps the connection — and the goroutine/file descriptor backing it — alive indefinitely.
- There is no `MaxHeaderBytes` override, no request/connection concurrency limiter, and no `context.WithTimeout` wrapping applied at the listener/server level, so an attacker can open many such connections without ever completing an HTTP request.
- If `http.Serve` does return an error (e.g., resource exhaustion causing `Accept` to fail, such as `EMFILE`), the goroutine calls `os.Exit(1)`, terminating the entire `git-sync` process — not just the HTTP subsystem: [2](#0-1) 

This endpoint is reachable by any network peer that can route to `--http-bind` (commonly bound to `:PORT`, i.e., all interfaces, per the flag's own documented examples), making it attacker-reachable without git repository push access or credentials.

### Impact Explanation
An attacker who can reach the configured `--http-bind` address can open a moderate number of slow/incomplete HTTP connections (classic Slowloris pattern) to keep goroutines and file descriptors pinned indefinitely. Once the process runs out of file descriptors:
- The `/` liveness endpoint stops responding, which in Kubernetes will cause the pod to be marked unhealthy/restarted (persistent sync denial via probe failure/restart loop).
- `Accept()` failures on the listener trigger `os.Exit(1)` in the goroutine at `main.go:890-894`, killing the entire `git-sync` sidecar process, not merely the HTTP feature — this converts a purely observational subsystem outage into full sync denial for the workload depending on `git-sync`.
- Descriptor/goroutine exhaustion in the same process can also interfere with concurrent git operations (which also require file descriptors and network sockets), compounding the denial-of-service effect.

### Likelihood Explanation
`--http-bind` is a commonly-enabled, documented feature (used for Kubernetes liveness probes and metrics) and is explicitly exercised in the project's own e2e tests. No authentication is required to reach it, and exploitation requires only standard TCP connections with slow/partial writes — well within reach of any attacker with network access to the pod/port. The likelihood is high in any deployment where the HTTP endpoint is exposed beyond a fully trusted network boundary.

### Recommendation
Replace the bare `http.Serve(ln, mux)` call with an explicit `http.Server{}` that sets conservative timeouts, e.g.:
```go
srv := &http.Server{
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,
    ReadTimeout:       10 * time.Second,
    WriteTimeout:      10 * time.Second,
    IdleTimeout:       60 * time.Second,
}
go func() {
    err := srv.Serve(ln)
    log.Error(err, "HTTP server terminated")
    os.Exit(1)
}()
```
Additionally, consider avoiding `os.Exit(1)` on transient `Accept` errors so a temporary resource spike on the HTTP listener doesn't take down the whole sync process, and consider limiting max concurrent connections.

### Proof of Concept
1. Run `git-sync` with `--http-bind=:8080` (or any bind address reachable by the attacker).
2. From an attacking host, open many raw TCP connections to port 8080 (e.g., using a Slowloris tool or a simple script), sending only a partial HTTP request line/headers, one byte every 10–30 seconds, per connection, and never completing the request.
3. Because `http.Serve` applies no `ReadHeaderTimeout`/`ReadTimeout`, none of these connections are ever closed by the server.
4. Repeat until the process's open file descriptor limit is reached; observe that legitimate requests to `/` (liveness probe) start timing out or hanging, and/or that `http.Serve` returns an `Accept` error, causing the process to call `os.Exit(1)` at [2](#0-1) , terminating `git-sync` entirely.
