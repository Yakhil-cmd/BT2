### Title
Route-specified contract addresses execute arbitrary code inside the caller's signed authorization tree, draining wallet tokens far beyond `total_in` - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
CVE-2010-1622 is a code-injection class bug: attacker-controlled HTTP parameters bound to `class.classLoader.URLs[0]` let the framework load and execute attacker-chosen code under the victim's authority. The structural analog in XOXNO Lending is the swap-aggregator's venue dispatch: the swap payload names arbitrary `pool` and `token` contract addresses, `dispatch_hop` invokes them via `env.invoke_contract` while the transaction still runs under `sender.require_auth()`, and any `token.transfer(sender, attacker, amount)` issued by that code is recorded by `simulateTransaction` as a child of the sender's authorization entry. A victim who signs the simulation-produced tree (the normal wallet flow) authorizes transfers of any token in their wallet, unbounded by `total_in`, `total_min_out`, or the controller's `RouterOverspend`/`NoSwapOutput` guards.

### Finding Description
`execute_strategy` authenticates the sender once and then executes the payload-supplied program at `contracts/swap-aggregator/src/execute/mod.rs:51-52` (`sender.require_auth()`), building `SwapHop` values whose `pool`, `token_in`, and `token_out` fields are raw addresses taken from `ctx.assets` with no allowlist at `execute/mod.rs:152-158`. `venues::dispatch_hop` at `contracts/swap-aggregator/src/venues/mod.rs:34-40` then invokes venue adapters that call `env.invoke_contract(&hop.pool, ...)`, e.g. Aquarius at `venues/aquarius/pool.rs:34`, Phoenix at `venues/phoenix.rs:23-25`, Comet at `venues/comet.rs:30-34`. Every measurement guard (`ZeroOutput`, `InvalidAmount` at `venues/mod.rs:42-56`, and the controller's `RouterOverspend`/`NoSwapOutput` at `contracts/controller/src/strategies/swap.rs:41-54`) only bounds what the router *contracts* observe — the router's own balances. Nothing bounds what the invoked contract does with the *sender's* ambient authority.

Soroban authorization semantics make this exploitable: any `require_auth(sender)` invoked by third-party code on the call stack is satisfied by a matching child in the sender's signed auth tree, and `simulateTransaction` (recording mode) automatically appends that child. The repo's own harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the full chain end-to-end through `controller.swap_collateral`: a `RogueHopPool` contract deployed by the attacker calls `token.transfer(alice, attacker, WALLET_BALANCE)` for a token the protocol never listed; simulation records it under Alice's `swap_collateral` entry (lines 195-227) and the signed poisoned tree executes the theft (lines 229-269). The threat model documents the same exposure at `docs/explanation/threat-model.md:154-165`: "a route can put third-party code on the call stack below the caller's authorization... the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it."

The direct `execute_strategy` path has identical exposure for any wallet that submits an attacker-supplied `routeXdr` — e.g., one served by a malicious quote or front-end — because the signed authorization tree is produced by simulating the very transaction that contains the rogue pool.

### Impact Explanation
Theft of user funds. The attacker gains transfers of arbitrary amounts of any token held by the victim's wallet (the test moves `WALLET_BALANCE = 77_770_000_000` of an unlisted token while the swap itself routes only `SWAP_IN_USDC`). The loss is capped only by the victim's wallet balances, not by the swap amount, and is reachable from every route-bearing entrypoint: `execute_strategy` directly, and `controller.swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position` — anywhere a `StrategySwap`/`routeXdr` is consumed via `swap_tokens`/`swap_tokens_or_passthrough`.

### Likelihood Explanation
Exploitation requires the victim to sign a transaction built around an attacker-crafted route, which is the standard quoting flow: users routinely sign simulation-produced envelopes whose `swap_xdr` was computed off-chain. The attacker's cost is deploying one contract and serving the crafted XDR; no privileged role, oracle manipulation, or timing dependence is needed. The one mitigating factor is that a diligent client can decode the route and reject auth trees with unexpected children (the documented mitigation in `skills/xoxno-swap-aggregator/payload.md` and `threat-model.md`), but nothing in-protocol enforces this, and the recorded rogue child is added silently by simulation. Consistent with the Medium severity of the source advisory.

### Recommendation
Constrain what code a route can put under the caller's authorization:

- Maintain a governance/owner-managed allowlist of pool (and hop token) addresses in the swap-aggregator, and reject hops whose `hop.pool` is not registered, in `dispatch_hop` or at `execute_op` decode time.
- Alternatively/additionally, restrict the `sender` authorization surface: have `execute_strategy` pull `total_in` via a narrow authorization and require venues to interact only with router-held balances, then document that any non-allowlisted hop is rejected rather than relying on clients to audit signed auth trees.
- At minimum, surface a machine-readable "expected child authorizations" descriptor so wallets can hard-fail when simulation records children beyond the single input `transfer`.

### Proof of Concept
Already present in-repo: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Attacker deploys `RogueHopPool` (lines 51-72), storing `(victim = Alice, wallet_token, attacker, amount = WALLET_BALANCE)`; its `swap` calls `token::Client::transfer(victim, attacker, amount)`.
2. Attacker crafts a route whose `hop_pool` is that contract, wrapped in `swap_xdr`, and induces Alice to call `controller.swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)` (lines 134-164).
3. In recording mode (`mock_all_auths`, simulating `simulateTransaction`), the rogue transfer is recorded as a child of Alice's `swap_collateral` auth entry and executes: Alice's wallet token balance goes to 0, the attacker receives `WALLET_BALANCE` (lines 195-227).
4. In enforcing mode with the honest root-only tree the call correctly reverts with "Unauthorized function call for address" (lines 239-256); but signing the simulation-produced (poisoned) tree makes the same call succeed and move the funds (lines 258-269).
5. The same mechanism applies to a direct `Router::execute_strategy(sender, total_in, swap_xdr)` call, where `sender` is an externally-owned account — the rogue transfer rides the sender's auth tree identically.
