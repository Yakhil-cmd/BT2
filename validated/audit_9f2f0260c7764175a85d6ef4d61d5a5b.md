### Title
Webhook signature is validated against the secret of `repository.owner.login`, but the stack that gets written is resolved from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC against using `repository_owner` (`repository.owner.login` or `organization.login`), while every handler that actually performs a write (`PushHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the target `Stack`/`Repository` using a completely different field, `repository.full_name`. Nothing enforces that `repository.full_name` belongs to the same organization whose secret was used to validate the signature.

### Finding Description
`verify_signature` derives the signing org from the payload and fetches that org's `GitHubApp`/secret: [1](#0-0) 

The org used for secret selection comes only from `repository.owner.login`/`organization.login`: [2](#0-1) 

But every handler that mutates state resolves the affected `Stack` via `repository.full_name`, a sibling field inside the very same JSON body, with no cross-check against `repository.owner.login`: [3](#0-2) [4](#0-3) [5](#0-4) 

The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being written to`. Because these two lookups read from two independent, unauthenticated-until-verified fields of the same attacker-shaped JSON body, an attacker who legitimately controls a webhook secret for **their own** organization/installation (Org A) can forge a payload where `repository.owner.login = "orgA"` (so the signature check picks Org A's known secret and validates, since HMAC is computed over the raw body they control and sign themselves) while `repository.full_name = "orgB/some-repo"` — a stack belonging to a completely different, unrelated organization (Org B) configured on the same Shipit instance. `GitHubApp` and `Shipit.github(organization:)` are explicitly built for multi-organization configurations with per-organization secrets/apps, so this cross-org mismatch is a real configuration this engine supports: [6](#0-5) [7](#0-6) 

This is the direct structural analog of the DAI-permit issue: two fields inside one signed message are supposed to be equal for the authorization to be meaningful (there, `nonce`/holder used for approval vs. actually consumed fields; here, "authenticated organization" vs. "repository actually written"), but the code never enforces that equality — it just trusts whichever field is convenient at each call site.

### Impact Explanation
An attacker who runs their own GitHub organization/repo that is also configured as a tenant of this Shipit instance (i.e., holds a legitimate webhook secret only for their own org) can trigger unauthorized writes against stacks belonging to **other** organizations hosted on the same instance: forcing `GithubSyncJob` runs, injecting fabricated commit `Status` rows, or scheduling `RefreshCheckRunsJob` for arbitrary repositories/branches they don't own. This is a cross-repository/cross-organization write performed without holding that target organization's webhook secret, matching the "cross-repository writes" impact bucket.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately controls at least one configured organization (and thus its webhook secret), and knowledge that the target stack's `full_name` exists in the same instance. No repository write access, session, or API token is needed to exploit — only the ability to send a raw HTTP POST to `/github/webhooks` with a self-signed payload using their own org's secret. This is a plausible but non-trivial precondition (multi-tenant install + attacker holding one tenant's secret).

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), after determining `repository_owner` and validating the signature, also verify that the resolved `Repository`/`Stack` for `repository.full_name` actually belongs to that same `repository_owner`/organization before dispatching to handlers; reject the webhook with `422` otherwise.

### Proof of Concept
1. Attacker controls Org A, configured in Shipit with `webhook_secret_A`, and knows Org B's repo `orgB/target-repo` is also hosted on the same Shipit instance.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "orgB/target-repo",
    "owner": { "login": "orgA" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` using their own known `webhook_secret_A`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates successfully against `webhook_secret_A`.
5. `PushHandler.process` runs `stacks` derived from `Repository.from_github_repo_name("orgB/target-repo")`, triggering `stack.sync_github(expected_head_sha: ...)` on Org B's stack — a write the attacker was never authorized to perform.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
