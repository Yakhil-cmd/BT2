### Title
Constant-precision Decimal arithmetic in the oscript formula engine causes silent precision loss that AMM-style AAs can exploit to drain reserves via round-trip swaps - (File: formula/common.js)

### Summary
The Obyte formula/AA evaluation engine fixes `Decimal.js` precision to only 15 significant digits for every arithmetic operation performed inside oscript formulas (`init`, `messages[].state`, `bounce` conditions, etc.). Any AA that implements a constant-product/AMM-style swap — the pattern officially shipped as an example in `test/samples/uniswap_like_market_maker.oscript` — multiplies two large reserve balances together (`$p = $asset_balance * $bytes_balance`) and then divides the product back by one of the reserves to compute the new balance. Because the product of two large integers routinely exceeds 15 significant digits, the result is silently rounded to 15 significant digits by the shared `Decimal.set({precision:15, ...})` configuration before the division, producing a `$new_asset_balance`/`$new_bytes_balance` that does not satisfy the exact invariant `x*y=k`. This is the same class of bug reported externally: rounding error in a swap formula allows a user to swap a negligible amount in one direction and then swap back in the other direction for a disproportionate profit, draining the AA's reserves.

### Finding Description
Every oscript arithmetic operator (`+ - * / % ^`) and every `round/ceil/floor` call is evaluated through `formula/evaluation.js`, which converts operands to `Decimal` objects and performs `prevV[f](res)` using the global Decimal context configured once in `formula/common.js`: [1](#0-0) 

This precision setting (15 significant digits) is applied globally to *every* Decimal operation executed by *any* AA on the network, including intermediate results of multiplications that are never displayed but are used to derive fund-moving amounts. The official constant-product market-maker sample distributed with the codebase computes: [2](#0-1) [3](#0-2) 

Here `$p = $asset_balance * $bytes_balance` is the constant-product invariant `k`. Once reserves grow into ranges common for real tokens (e.g., balances in the range of 10^9–10^12, whose product exceeds 10^18–10^24), the multiplication result is truncated to 15 significant digits by the engine before `round($p / balance[...])` is evaluated. This introduces a rounding/truncation error in the *intermediate* value `$p`, not just in the final rounding of the output amount, which is a materially different (and larger) error than a standard "round the last digit" AMM implementation would have. Depending on the exact reserve ratios, this truncation can bias the computed `$new_asset_balance`/`$new_bytes_balance` in the attacker's favor and can be repeated: swap a negligible (e.g., 1-unit) amount in one direction, then reverse the swap, and the two roundings do not cancel out, yielding a net profit — precisely the "attackers can steal funds by swapping in both directions" bug class from the external report.

The `round`/`ceil`/`floor` opcode implementation itself also performs its output rounding using `res.toDecimalPlaces(dp.toNumber(), roundingMode)` against the already-precision-reduced `res`, compounding the loss: [4](#0-3) 

The engine explicitly documents that it matches double-precision behavior ("double precision is 15.95") rather than exact integer/rational arithmetic, and every division, multiplication and rounding call funnels through this fixed 15-digit context: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any AA author who deploys a constant-product (or similarly reserve-ratio-based) AMM using oscript — as directly demonstrated by the codebase's own `uniswap_like_market_maker.oscript` sample — inherits this rounding behavior from the shared formula engine. An unprivileged AA trigger sender can post a trigger unit that performs a negligible "asset → bytes" swap followed by a "bytes → asset" swap (or vice versa), each computed via the 15-significant-digit-truncated product `$p`. Because the truncation of `$p` is not guaranteed to be conservative in both directions, a sequence of round-trip swaps can extract more value than was deposited, draining the AA's `base`/asset reserves over repeated triggers — a direct AA fund loss reachable purely by posting ordinary payment/trigger units, matching the "concrete unauthorized spending / AA fund loss" impact bar.

### Likelihood Explanation
The precision limitation is deterministic and applies to every AA that performs multiply-then-divide arithmetic on large reserve balances; it requires no privileged access, no data feed manipulation, and no cooperation from other parties — only an unprivileged sender crafting trigger units with specific amounts (analogous to the external report's "1 wei in / large amount out" trigger sequence). Any Obyte AA implementing an AMM-like exchange (the codebase ships one as a canonical example) is exposed once reserve magnitudes push intermediate products past 15 significant digits, which is easily reached with moderate token supplies/liquidity.

### Recommendation
- Short term: audit `uniswap_like_market_maker.oscript` and any similar shipped/example AA logic for cases where an intermediate product/division can lose precision under the fixed 15-significant-digit `Decimal` context; add explicit bounds/invariant checks (e.g., require the new invariant `x'*y' >= x*y` with integer-safe arithmetic, or reformulate swap math to avoid computing `$asset_balance * $bytes_balance` directly) in `formula/evaluation.js`/`formula/common.js`-consuming code.
- Long term: consider raising the working precision for AMM-style computations (or providing a documented integer-safe multiplication/division primitive for oscript) and add fuzz tests that repeatedly execute a swap and its inverse to detect any net profit/loss asymmetry caused by rounding, mirroring the recommendation in the external report.

### Proof of Concept
Using the shipped sample `test/samples/uniswap_like_market_maker.oscript` as the AA:
1. Attacker seeds the pool with an initial deposit (asset + bytes) establishing large `$asset_balance`/`$bytes_balance` reserves such that `$asset_balance * $bytes_balance` exceeds 15 significant digits.
2. Attacker triggers the "exchange bytes to asset" case with a minimal `trigger.output[[asset=base]]` amount just above `1e5`, computing `$p = $asset_balance * $bytes_balance` (truncated to 15 significant digits by the global `Decimal` precision setting) and `$new_asset_balance = round($p / balance[base])`.
3. Attacker immediately triggers the reverse "exchange asset to bytes" case with the asset just received, computing a new truncated `$p` and `$new_bytes_balance = round($p / balance[$asset])`.
4. Because the two truncations of `$p` are computed against different (post-first-swap) reserve values, they do not cancel; repeating steps 2–3 nets the attacker more `base`/asset than they put in, draining the AA over multiple iterations — directly analogous to the external report's `1 asset -> 1 quote -> 10000000001 asset` round-trip drain. function isFiniteDecimal(val) {
	return (Decimal.isDecimal(val) && val.isFinite() && isFinite(val.toNumber()));
}

function toDoubleRange(val) {
	// check for underflow
	return (val.toNumber() === 0) ? new Decimal(0) : val;
}

function createDecimal(val) {
	return toDoubleRange(new Decimal(val).times(1));
}

// reduces precision to 15 digits to calculate the same result as Oscript would calculate
function toOscriptPrecision(num) {
	return (new Decimal(num).times(1)).toString();
}
