### Title
Poll `question` field has no length limit, causing an INSERT failure/divergence on MySQL/MyRocks full nodes - ([File: validation.js])

### Summary
The `poll` message type accepts an unbounded `question` string. Unlike every other free-text field in the protocol (`data_feed` names/values, `MAX_CHOICE_LENGTH` for poll choices, `MAX_PROFILE_FIELD_LENGTH`/`MAX_PROFILE_VALUE_LENGTH` for attestation profiles), `question` has no dedicated `MAX_*` constant and no length check in `validateInlinePayload`. The only real ceiling is the overall unit size limit `constants.MAX_UNIT_LENGTH` (default `5e6` bytes), so an attacker can post a poll with a question of up to several megabytes.

### Finding Description
In `validation.js`, the `poll` case only checks that `question` is a string and trimmed, but never checks its length: [1](#0-0) 

Every other similarly free-form field in the same function enforces an explicit length cap, e.g. poll choices (`MAX_CHOICE_LENGTH`) and data feeds (`MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH`): [2](#0-1) [3](#0-2) 

Once a unit passes validation, the writer persists the question verbatim into the `polls` table: [4](#0-3) 

The schema, however, defines this column with a fixed width in every SQL backend, including the MySQL/MyRocks schemas used by full/hub nodes: [5](#0-4) 

SQLite (used by light clients and some full nodes) does not strictly enforce `VARCHAR` length limits due to its dynamic typing, but MySQL/MariaDB does enforce `VARCHAR(4096)` and will either truncate the value (non-strict SQL mode) or throw a data-too-long error (strict SQL mode) when the validated `question` exceeds 4096 characters. Because validation never rejects an over-long question, a single unit can be accepted by validation logic yet fail, be silently truncated, or diverge in on-disk representation at the storage layer depending on the backend/SQL mode in use — the exact "improper validation of specified quantity in input" root cause the external GitLab report describes for its oversized token-name field.

### Impact Explanation
On MySQL/MyRocks-backed full nodes running in strict SQL mode, the `INSERT INTO polls` query in `writer.js` will fail for a poll whose `question` exceeds 4096 bytes, after the unit has already passed `validation.js` and is mid-way through `saveJoint`. This can abort/rollback the write, effectively causing that node to be unable to save and therefore stall on a unit that other nodes (e.g., SQLite-backed light or full nodes, or MySQL nodes in non-strict mode) accept and continue processing normally. The result is a consensus-relevant divergence: some full nodes cannot persist/confirm the unit while others do, which is a node disagreement on validity/stability of the DAG — directly matching the accepted impact categories (node disagreement on validity or stability / a network unable to confirm new units for the affected nodes).

### Likelihood Explanation
Any single unprivileged unit poster can trigger this by simply crafting a `poll` message with a very long `question` string (bounded only by `MAX_UNIT_LENGTH`, ~5MB) and posting it as a normal unit — no special privileges, AA logic, or asset ownership required, and the message otherwise passes all existing checks (non-empty, trimmed, has valid choices).

### Recommendation
Add an explicit length check for `payload.question` in the `poll` case of `validateInlinePayload` (and the mirrored check in `aa_validation.js` for AA-triggered polls), introducing a `constants.MAX_POLL_QUESTION_LENGTH` matching the `question VARCHAR(4096)` schema column width, consistent with how `MAX_CHOICE_LENGTH` and `MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH` are enforced.

### Proof of Concept
1. Craft a unit with a single message of `app: "poll"` and `payload.question` set to a string of ~4200+ characters (well under `MAX_UNIT_LENGTH`), with valid non-empty `choices`.
2. Submit the unit to the network; `validateInlinePayload`'s `poll` case in `validation.js` (lines 1784-1812) accepts it because there is no length check on `question`.
3. On a MySQL/MyRocks full node running with strict SQL mode, `writer.js`'s `INSERT INTO polls (unit, message_index, question) VALUES(?,?,?)` (line 195) fails against the `question VARCHAR(4096) NOT NULL` column, while a SQLite-backed node accepts and stores the same unit without error, producing storage-layer divergence between nodes for the same accepted unit.
