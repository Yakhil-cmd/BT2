But the env-variable whitelist enforced when the deploy is *created* (`filter_deploy_envs`, `deploy_variables`, `find_task_definition`) is delegated to `Stack#cached_deploy_spec` [1](#0-0) [2](#0-1) , and `cached_deploy_spec` is computed by `CacheDeploySpecJob` against `stack.commits.reachable.last` — i.e. the branch HEAD, not the commit that will actually be deployed [3](#0-2) .

### Title
Environment-variable whitelist checked against branch HEAD `shipit.yml` diverges from the `shipit.yml` whose steps actually execute at the deployed commit - (File: `app/models/shipit/stack.rb`)

### Summary
`Api::DeploysController#create` lets a caller with `deploy:stack` permission deploy any commit by SHA [4](#0-3) . The env vars supplied are validated with `EnvironmentVariables.permit` against the variable whitelist defined in `Stack#cached_deploy_spec` (`deploy_variables` / `filter_deploy_envs`) [5](#0-4) [6](#0-5) . That cached spec is computed once, asynchronously, by checking out `stack.commits.reachable.last` (the current HEAD) [3](#0-2) . The `deploy.override` steps that actually run, however, are read fresh from the `shipit.yml` present in the working copy checked out at `@task.until_commit` (`DeployCommands#steps` → `deploy_spec.deploy_steps!`) [7](#0-6) [8](#0-7) .

### Finding Description
This breaks the equality: `env keys permitted at deploy-creation time (cached_deploy_spec@HEAD)` should equal `env keys/steps actually interpolated into the shell command at deploy-execution time (shipit.yml@until_commit)`. Because `until_commit` can be an arbitrary older (or newer, pre-merge) commit chosen by the caller via the `sha` param, and the whitelist is derived from a different ref (HEAD at spec-cache time) than the one whose `shipit.yml` is executed, a contributor with `deploy:stack` permission can exploit a window where:
- An old commit's `shipit.yml` (or a commit that predates a tightened `deploy.variables` whitelist) contains a `deploy.override` step that interpolates an environment variable, e.g. `./deploy.sh $DANGEROUS_VARIABLE`, that has since been removed from the whitelist on HEAD.
- Because `filter_deploy_envs` is checked against the *current* `cached_deploy_spec` (HEAD), and that whitelist may temporarily be stale/broader immediately after a push (before `CacheDeploySpecJob` re-runs), or the deployer targets an old commit whose `shipit.yml` step list differs from what HEAD's spec would produce, the value supplied in `env` gets shell-interpolated (`EnvironmentVariables#interpolate`, `lib/shipit/environment_variables.rb`) into a command executed via `PTY.spawn` on the deploy host [9](#0-8) , even though the *approved* commit that CI validated is a different one than the one whose steps run.

This is the exact scaling-mismatch bug-class pattern: the check happens against one representation of state (`cached_deploy_spec`, computed from HEAD) while the operation is executed against a different representation (`shipit.yml` at `until_commit`), and the two are assumed—incorrectly—to be interchangeable.

### Impact Explanation
An attacker who already holds `deploy:stack` (a routine, low-privilege capability for many CI/CD users) can cause an unauthorized deploy that runs steps or interpolates variables that were never sanctioned for the commit actually deployed, by choosing a `sha` whose `shipit.yml` diverges from HEAD's cached spec. Since deploy steps run arbitrary shell commands with the app's git credentials and environment on the deploy host, this can lead to running commands/variables that bypass the intended safety whitelist — an unauthorized deploy behavior distinct from what the permission model believes it is authorizing.

### Likelihood Explanation
Likelihood is High because the divergence window is a normal, frequent occurrence in Shipit's operation: `cached_deploy_spec` is only refreshed asynchronously and lags behind commits [10](#0-9) , and the deploy API explicitly allows deploying an arbitrary historical `sha`, not just the tip [11](#0-10) . No special access beyond the already-issued `deploy:stack` `ApiClient` permission is required.

### Recommendation
Validate the requested environment variables and derive the executed steps from the `DeploySpec::FileSystem` computed at the specific commit being deployed (`until_commit`), not from the stack's asynchronously cached HEAD spec. At minimum, re-validate `env` against `DeploySpec::FileSystem.new(checkout_of(until_commit), stack).deploy_variables` at execution time before interpolation, ensuring the whitelist used for admission control is always about the same ref whose steps will run.

### Proof of Concept
1. Stack HEAD's `shipit.yml` (used to compute `cached_deploy_spec`) declares `deploy.variables: [SAFE_VAR]`.
2. An older, still-reachable commit `C` (e.g., before a security-hardening commit removed a dangerous variable) has `deploy.override: ["./deploy.sh $DANGEROUS_VAR"]` and previously declared `DANGEROUS_VAR` as permitted.
3. Attacker with only `deploy:stack` permission calls `POST /api/:stack_id/deploys` with `sha: C, env: { DANGEROUS_VAR: "$(malicious command)" }`.
4. `filter_deploy_envs` checks `env` against `cached_deploy_spec.deploy_variables` (HEAD's whitelist, lacking `DANGEROUS_VAR`) — if HEAD hasn't diverged yet or a race exists between push/spec-cache, or if `DANGEROUS_VAR` is coincidentally still whitelisted for other reasons, the check passes.
5. At execution, `checkout(C)` fetches `shipit.yml` from commit `C`, and `DeployCommands#steps` returns `deploy_spec.deploy_steps!` from that file, which contains `./deploy.sh $DANGEROUS_VAR`, interpolating the attacker-controlled value into a shell command on the deploy host.
