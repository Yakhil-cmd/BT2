### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App secret to validate an inbound webhook using the `repository.owner.login` (or `organization.login`) field taken from the request body, then dispatches the parsed payload to per-event handlers. [1](#0-0) [2](#0-1)  For the `status` event, `StatusHandler#process` never re-checks that the commit it mutates actually belongs to the repository/organization whose secret validated the webhook — it looks the commit up globally by `sha` alone. [3](#0-2) 

### Finding Description
Signature verification only proves the payload was signed by the webhook secret associated with the organization named in the payload's own `repository`/`organization` field: [4](#0-3) . In a multi-organization Shipit deployment (`config/secrets.yml` `github:` keyed by org, as documented) [5](#0-4) , each organization has its own webhook secret, and `Shipit.github(organization: repository_owner)` resolves to that organization's own `GitHubApp`/secret. [6](#0-5) 

The base `Handler` class does define a repository-scoped helper (`repository_name`/`stacks`, built from `payload.dig('repository', 'full_name')`) [7](#0-6) , and `PushHandler` correctly uses it to scope which stacks can be synced. [8](#0-7)  `StatusHandler`, however, ignores this scoping entirely and resolves the target purely from the globally-unique `sha` parameter:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This breaks the trust binding: `organization_authenticated (via repository.owner.login used to pick the verifying secret) == repository_that_is_written (the stack/repository owning the mutated Commit)`. Before the attack, a status webhook signed with OrgA's secret can only be sent by someone possessing OrgA's webhook secret (i.e., an entity legitimately onboarded to Shipit for OrgA's own repositories). After the attack, that same OrgA-signed payload can carry an arbitrary `sha` value that happens to match a commit belonging to OrgB's (or any other onboarded org's) repository, and `StatusHandler` will happily create/update a `CommitDeploymentStatus`/`Status` on that unrelated commit — because the lookup is `Commit.where(sha: params.sha)` with no repository/organization filter, while the signature only proved authorization for OrgA.

### Impact Explanation
This allows a party with legitimate webhook-sending capability for one onboarded organization/repository to forge commit statuses for commits in a completely different, unrelated organization/repository also hosted on the same Shipit instance — a cross-repository write. Forged/poisoned commit statuses can influence merge/deploy gating logic elsewhere in Shipit (status checks gating deploys, `Stack` status aggregation), so this can indirectly enable an unauthorized deploy decision on a repository the attacker does not control. Commit SHAs are not secret (visible via GitHub UI/API, CI logs, PR pages), making them easy to obtain for a target repo.

### Likelihood Explanation
Requires the attacker to already have webhook-sending capability for at least one organization configured in a multi-org Shipit deployment (i.e., they can produce a validly-signed `status` webhook for their own org). Given that, exploitation only requires knowledge of a target commit SHA in a different, unrelated repository — a low bar since SHAs are public. No other Shipit credential (session, API token) is needed.

### Recommendation
In `StatusHandler#process` (and any other handler that resolves objects purely by attacker-supplied identifiers), scope the `Commit` lookup to the repository verified for the webhook, e.g. restrict to `stacks`/`Repository.from_github_repo_name(repository_name)` before matching by `sha`, mirroring the pattern already used in `Handler#stacks` and `PushHandler`.

### Proof of Concept
1. Deploy Shipit configured with multiple GitHub organizations (per `docs/setup.md`), OrgA and OrgB, each with its own `webhook_secret`.
2. Obtain (or control) the ability to send a webhook signed with OrgA's `webhook_secret` (e.g., because you administer an OrgA repo connected to Shipit).
3. Find a public commit SHA belonging to a repository owned by OrgB that is also tracked by this Shipit instance.
4. Send a `status` event webhook with `repository.owner.login = "OrgA"` (so `verify_webhook_signature` validates against OrgA's secret) but `sha` set to the OrgB commit SHA, `state`, `context`, etc. as desired, signed with OrgA's secret.
5. `WebhooksController#verify_signature` succeeds (valid OrgA signature). `StatusHandler#process` executes `Commit.where(sha: <OrgB sha>)` [3](#0-2)  and creates/updates a status on the OrgB commit despite the request never being authorized for OrgB.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
