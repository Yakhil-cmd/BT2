### Title
Weak/grindable PRNG via `number_from_seed()` seeded with attacker-controlled trigger data enables biased "random" outcomes in AAs - (File: formula/evaluation.js)

### Summary
The oscript function `number_from_seed()` derives a pseudo-random number by hashing a caller-supplied seed with SHA-256 and mapping the digest to a range. When an Autonomous Agent uses trigger-supplied values (e.g. `trigger.data`, `trigger.unit`, `trigger.address`) as that seed — a common and expected pattern for AA lotteries, raffles, games, or randomized selection — the "randomness" is fully computable and grindable by the party who composes and signs the triggering unit, before it is ever broadcast.

### Finding Description
`number_from_seed` is implemented as: [1](#0-0) 
It hashes `seed.toString()` with SHA-256 and turns the first 16 hex chars into a float in `[0,1)`, then optionally scales to `[min,max]`.

The natural source of a "seed" in an AA is trigger-derived data, since it is the only per-call variable input available to formulas. `getTrigger()` builds this data straight from the message content of the unit the caller composes: [2](#0-1) 
Here, `trigger.data` is taken verbatim from the `data`-app message payload the sender puts in their own unit, and `trigger.unit` is that same unit's hash. Both values are entirely chosen and known by the sender prior to submission — nothing server-side, hub-side, or MC-derived is mixed in unless the AA author explicitly does so (e.g. combining with `mc_unit`, `response_unit`, or a later-arriving previous AA response, none of which are enforced by the language).

Because the sender fully controls the content of `trigger.data` (arbitrary JSON fields) and can locally compute `sha256(trigger.data.whatever)` for as many candidate payloads as they like before broadcasting, they can grind for a data payload/unit whose resulting `number_from_seed()` output yields a favorable outcome (e.g., "you win", a favorable index into a payout table, or a favorable branch in `if`/`case` messages) and only ever submit that one candidate. This mirrors the classic block-hash/miner-grindable lottery seed anti-pattern that the source report describes for on-chain modulo-based generation: the entity that controls the input to a "random" derivation can pre-compute and select for outcomes.

### Impact Explanation
Any AA that implements a lottery, raffle, random payout multiplier, random-fee reduction, or similar mechanic using `number_from_seed()` fed (directly or indirectly, without an unpredictable/unbiasable component such as data unknown to the sender at signing time) by trigger-controlled data is exploitable: the triggering address can bias the "random" result deterministically in its own favor, draining AA funds through guaranteed-win payouts. This is a concrete AA fund-loss vector — not a core protocol bug, but a footgun baked into the only source of entropy oscript formulas expose to AA authors, so essentially every naive random-based AA built on this primitive inherits the flaw.

### Likelihood Explanation
High for any AA that uses `number_from_seed()` seeded by trigger-controlled values (a very natural, and in the absence of alternative entropy sources in oscript, nearly unavoidable pattern for building "randomized" AAs). The attacker only needs local computation (no special access) to grind seeds prior to submission, and the "AA trigger sender" role fits squarely in the reachable-from-unprivileged-poster threat model.

### Recommendation
- Document prominently (and ideally enforce via linting/static analysis tooling) that `number_from_seed()` must never be seeded solely with data controlled by the trigger sender (`trigger.data`, `trigger.unit`, `trigger.address`) if used for anything with economic consequence.
- Encourage/require mixing in values unknown to the sender at signing time, such as `mc_unit`/`response_unit` of a future stable unit, or a commit-reveal scheme (two-step trigger where the seed-affecting reveal happens after the commitment is stable and unchangeable) so the seed cannot be precomputed and selected for.
- Consider adding a built-in "unbiasable randomness" primitive to oscript (e.g., derived from the eventual stable DAG state / MC unit hash unknown at trigger-composition time) so AA authors are not forced to build their own (breakable) entropy source from trigger data.

### Proof of Concept
1. An AA is defined to pay out a bonus if `number_from_seed(trigger.data.seed, 0, 99) < 10` (i.e., "10% chance to win").
2. The attacker, off-chain, tries many candidate values for `seed` (any string/number field they can freely choose) and computes `sha256(seed)` locally, replicating exactly the calculation in `formula/evaluation.js` lines 1893-1898, until finding one where the derived number is `< 10`.
3. The attacker composes and broadcasts a unit whose `data` message carries that winning `seed` value, targeting the AA as in `getTrigger()` (`aa_composer.js` lines 375-397), so `trigger.data.seed` equals the attacker's chosen winning value.
4. The AA formula evaluates `number_from_seed` deterministically per lines 1893-1898 of `formula/evaluation.js`, producing the pre-computed favorable result every time, guaranteeing the "random" bonus payout and draining AA funds. [3](#0-2) [2](#0-1)

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
