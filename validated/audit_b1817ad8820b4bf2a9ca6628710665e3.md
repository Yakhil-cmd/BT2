### Title
Concurrent stability-cache mutation across mismatched mutex scopes can desynchronize node state / halt confirmation - ([File: main_chain.js])

### Summary
The Zebra advisory fixed a class of bugs where concurrent access to shared consensus-state data structures (history tree, sprout tree) without a single consistent lock caused panics and cache corruption. ocore has an analogous pattern: the in-memory consensus caches `storage.assocStableUnits`, `storage.assocStableUnitsByMci`, and `storage.assocUnstableUnits` are mutated from multiple code paths that are guarded by *different, non-overlapping* mutex keys, allowing genuinely concurrent unsynchronized writes to the same shared state.

### Finding Description
`writer.saveJoint` mutates `storage.assocStableUnits` / `storage.assocUnstableUnits` / `storage.assocStableUnitsByMci` while holding the `"write"` mutex key [1](#0-0) , and later, still inside the same `"write"`-locked call, invokes `main_chain.advanceMcStability` to push the stability point further [2](#0-1) .

However, `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag` — invoked from `validation.js` during ordinary unit validation (`validateParents`) — takes a *different* lock, `"handleJoint"`, not `"write"`, before calling `stabilizeMci()` which mutates the exact same caches via `markMcIndexStable` (`storage.assocStableUnits[...]`, `storage.assocStableUnitsByMci[mci]`, deletions from `storage.assocUnstableUnits`) [3](#0-2) [4](#0-3) .

Crucially, `validation.validate()` itself is only guarded by `mutex.lock(arrAuthorAddresses, ...)` — a lock keyed on the *unit's author addresses*, not on `"write"` or `"handleJoint"` [5](#0-4) . This means two units from different, unrelated authors can be validated fully in parallel. If unit A's validation reaches `validateParents` and triggers `determineIfStableInLaterUnitsAndUpdateStableMcFlag` (taking the `"handleJoint"` lock and calling `stabilizeMci`, which touches `storage.assocStableUnits`/`assocUnstableUnits` on its own independent db connection/transaction) at the same wall-clock moment that `writer.saveJoint` for a different, previously-validated unit B is running under the `"write"` lock and mutating the very same JS objects (`storage.assocStableUnits[objUnit.unit] = ...`, `storage.assocUnstableUnits[objUnit.unit] = ...`, and the `advanceMcStability` call inside it) [6](#0-5) , there is no mutual exclusion between the `"write"` and `"handleJoint"` critical sections. Both concurrently iterate/mutate the shared `assocUnstableUnits`/`assocStableUnits`/`assocStableUnitsByMci` associative maps from Node's single-threaded event loop but interleaved across asynchronous callbacks and separate DB connections/transactions, exactly the class of "history tree"/"sprout tree" concurrency bug fixed upstream (concurrent readers/writers manipulating a shared consensus tree/cache guarded by inconsistent lock scopes, leading to state corruption rather than a hard crash in a single-threaded JS runtime, but with the same root cause: a shared state object mutated under two different lock names that don't exclude each other).

Additionally, `storage.resetMemory` — which fully clears and re-derives `assocStableUnits`/`assocUnstableUnits` on a write-rollback error path — is invoked from inside `writer.saveJoint`'s `"write"`-locked commit handler [7](#0-6) , but nothing prevents an in-flight `"handleJoint"`-locked `stabilizeMci` call (from a concurrent validation of another unit) from reading/writing the same caches while they are being wiped and rebuilt, since `resetMemory` does not take the `"handleJoint"` lock, nor does `stabilizeMci`/`determineIfStableInLaterUnitsAndUpdateStableMcFlag` take the `"write"` lock.

### Impact Explanation
If two independent mutation paths race on `assocStableUnits`/`assocUnstableUnits`/`assocStableUnitsByMci`, the in-memory view of which units are stable/unstable, and their `sequence` (good/final-bad) and `main_chain_index` fields, can become inconsistent with the database or with what other nodes compute, for example: a unit could be dropped from `assocUnstableUnits` (marked stable) by one interleaved call while a `saveJoint` in progress for a sibling/child unit reads stale `assocUnstableUnits`/`assocBestChildren` state to compute `is_free`, best-parent chains, or double-spend/sequence resolution (`findStableConflictingUnits`, `propagateFinalBad` in `markMcIndexStable`) [8](#0-7) . This can lead to a node computing a different stability/sequence decision than a canonical single-writer execution would produce, i.e., node disagreement on unit validity/stability or on which of two competing (double-spend) inputs is "good" — the exact class of impact the Validate rules call out (node disagreement on validity or stability). Because `assocStableUnits`/`assocUnstableUnits` back consensus-critical decisions (double-spend resolution, `is_free` freeing of parents, AA-trigger enumeration via `assocUnstableMessages`), corruption here can propagate to accepting/serializing conflicting spends differently across nodes.

### Likelihood Explanation
The race requires validation of one unit (by author addresses unrelated to any unit currently being written) to reach `validateParents`'s stability-advance branch at the same time `writer.saveJoint` for another unit is executing its post-validation write-and-stabilize sequence — both are routine, frequent operations during normal DAG growth (any time the last-ball unit is stable in the parents' view but not yet marked stable in the DB) [9](#0-8) . Since `mutex.lock(arrAuthorAddresses, ...)` deliberately allows unrelated units to validate concurrently (that is its purpose — parallelism), and Node.js's callback/promise interleaving means the two independent async chains (`"write"` and `"handleJoint"`) can genuinely interleave their cache mutations between `await`/callback boundaries, this is plausible under moderate network load rather than a purely theoretical race.

### Recommendation
Unify the locking discipline so that any code path that mutates `storage.assocStableUnits`, `storage.assocUnstableUnits`, `storage.assocStableUnitsByMci`, or `storage.assocUnstableMessages` acquires the same mutex key (e.g., always take `"write"` before `"handleJoint"`-triggered stabilization, or fold `"handleJoint"` into `"write"` for the cache-mutating sections) so that `writer.saveJoint`'s stabilization/cache mutation and `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag`/`stabilizeMci`'s cache mutation can never interleave. At minimum, `stabilizeMci`/`markMcIndexStable` and `storage.resetMemory` should be required to hold the `"write"` lock (not just `"handleJoint"`) before touching the shared caches, matching the existing comment in `writer.js` ("without this locking, we get frequent deadlocks from mysql") that shows the authors are already aware locking here is fragile and was partially disabled [10](#0-9) .

### Proof of Concept
Not independently reproducible from static analysis alone (requires a live multi-connection DB/timing harness to force the interleaving of the `"write"`-locked `writer.saveJoint`→`advanceMcStability` path with a concurrently validating unit's `"handleJoint"`-locked `determineIfStableInLaterUnitsAndUpdateStableMcFlag`→`stabilizeMci` path). The control-flow evidence establishing the race window is cited above: mismatched lock keys (`"write"` in `writer.js` vs `"handleJoint"` in `main_chain.js`) guarding mutation of the same shared objects (`storage.assocStableUnits`, `storage.assocUnstableUnits`, `storage.assocStableUnitsByMci`).
