## Finding: Multisig quorum-approval binding can be bypassed via payload substitution when a mismatch-prevention feature flag is not yet enabled

### Title
Multisig transaction execution can substitute an unapproved payload for the one owners voted on - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction` — the function invoked by the VM prologue during both mempool admission and execution — only checks that the *executed* payload matches the payload the quorum of owners approved when a **feature flag** (`abort_if_multisig_payload_mismatch_enabled`) is turned on. When the flag is off, an owner submitting the execution transaction can supply an arbitrary `payload` argument that differs from the `MultisigTransaction.payload` stored on-chain when the transaction was created with `create_transaction` (full payload, no hash), and the mismatched payload is accepted at admission and executed.

### Finding Description
`validate_multisig_transaction` is the admission/prologue gate for multisig execution: [1](#0-0) 

Two payload-binding paths exist, corresponding to the two ways a transaction can be created:
- `create_transaction_with_hash`: only a `sha3_256` hash is stored (`payload_hash`). At execution, `sha3_256(payload) == *payload_hash` is unconditionally enforced — this path is sound.
- `create_transaction`: the full `payload` is stored on-chain (`transaction.payload`), with no hash. In this path the code only enforces a match between the supplied execution `payload` and the stored `transaction.payload` **if** `features::abort_if_multisig_payload_mismatch_enabled()` is true:

```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
```

If this feature is disabled, an owner who has accumulated the required number of approvals (`num_signatures_required`) for sequence number `N` can call the execution entrypoint with a `payload` different from the one the other owners actually voted for, and `validate_multisig_transaction` will not reject it — the approvals recorded against the *original* payload are treated as authorizing whatever `payload` is provided at execution time.

This breaks the "approval set validation accepting the wrong approval set" invariant required at the admission boundary: the multisig quorum approves resource X, but the executable transaction that is admitted and committed is for resource Y.

### Impact Explanation
Any owner (not necessarily privileged beyond being one of N owners, potentially the minority who never actually gets quorum on their own preferred payload) can, once *some* payload has accumulated k-of-n approvals under `create_transaction`, execute a **different**, unapproved payload through the multisig account — effectively state transition under the wrong "signer set"/approval binding for a privileged multisig-controlled account. This can be used to drain funds, rotate keys, or perform arbitrary module calls that were never actually approved by the multisig owners, entirely bypassing the human-review/voting guarantee the multisig contract is designed to provide.

### Likelihood Explanation
Exploitability depends entirely on whether `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is enabled on the target network. I was not able to determine the on-chain default/rollout status of this specific feature flag within this session (I found its definition in `move-stdlib/sources/configs/features.move` and its registration in `aptos-release-builder`, but not its enabled/disabled default for mainnet/testnet in the code visible to me). If the flag is disabled by default or not yet activated via governance on some deployment, this is directly and trivially exploitable by any single owner holding a stake in reaching quorum with a decoy payload. Given the flag's very name ("abort if mismatch") and that it guards an `assert!` that would otherwise clearly be considered mandatory, this strongly suggests the check was retrofitted after an initial gap and is being rolled out gradually — meaning some deployments/time windows are exposed.

### Recommendation
Make the payload-match assertion unconditional (remove the feature-flag gate) whenever `transaction.payload.is_some()` and a non-empty `payload` is supplied, rather than only performing it under the flag. If backward compatibility must be preserved during rollout, ensure the flag is enabled everywhere before any `create_transaction`-based (full-payload) multisig flows are considered safe to use.

### Proof of Concept
1. Owners A, B, C create a multisig account requiring 2 signatures.
2. Owner A calls `create_transaction(multisig_account, payload_X)` (the "safe transfer" payload), which stores `payload_X` in `transaction.payload` (no hash) and implicitly registers A's approval.
3. Owner B calls `approve_transaction`, reaching the 2-of-3 threshold for `payload_X`.
4. On the feature-disabled network, Owner A (or any owner) submits the execution transaction with `MultisigTransactionPayload` field set to `payload_Y` (e.g., a transfer of funds to attacker's address) instead of `payload_X`.
5. `validate_multisig_transaction` passes: `can_execute`/`can_be_executed` and quorum checks only look at vote counts for sequence number N, not at the actual submitted payload; `transaction.payload_hash` is `None` so that check is skipped; and the payload-match `assert!` under `abort_if_multisig_payload_mismatch_enabled()` is skipped because the flag is off.
6. `payload_Y` executes and is committed, despite never having received the required 2 approvals.

**Note on confidence**: I could not verify the exact on-chain enabled/disabled status of `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` for the networks this codebase deploys to, so I cannot definitively state this is exploitable *today* on any live network — only that the code path itself contains this conditional gap, and the finding should be validated against the flag's actual activation state before assuming full exploitability.

    /// Called by the VM as part of transaction prologue, which is invoked during mempool transaction validation and as
    /// the first step of transaction execution.
    ///
    /// Transaction payload is optional if it's already stored on chain for the transaction.
    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }
