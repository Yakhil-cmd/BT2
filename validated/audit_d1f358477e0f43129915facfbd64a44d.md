## Title
`is_valid_sig()` accepts malleable (high-S) secp256k1 signatures via forced normalization, enabling signature-based replay in Autonomous Agents - (File: signature.js)

### Summary
The oscript primitive `is_valid_sig()` — reachable by any AA trigger sender who can get an AA to evaluate an attacker- or user-supplied signature — verifies secp256k1 PEM-key signatures through `signature.verifyMessageWithSecp256k1PemPubKey`. Unlike the platform's primary unit-authentifier signature check (`ecdsaSig.verify`, backed directly by libsecp256k1's `ecdsaVerify`, which natively rejects non-normalized "high-S" signatures), this helper explicitly force-normalizes the signature with `ecdsa.signatureNormalize()` before calling `ecdsaVerify`. This means both the canonical (low-S) signature and its malleable high-S counterpart (`n - s`) validate as "true" for the exact same message and public key — the classic ECDSA malleability the tbtc report warns about, deliberately re-introduced here by normalizing instead of rejecting.

`is_valid_sig()` is a documented oscript primitive intended for verifying externally-produced off-chain authorizations (vouchers, attestations, one-time claims) inside AAs. A common and expected AA pattern for such flows is to record the raw signature string (or its hash) in AA state as a "used" marker to prevent the same authorization from being replayed, since the AA author has no other natural unique identifier for a bare `(message, pubkey, signature)` tuple — the message itself may be reused (e.g., "claim reward" with a fixed payload) and only the signature is expected to be unique per submission.

### Impact Explanation
Because the secp256k1 branch of `is_valid_sig` accepts two different byte-strings (`s` and `n-s`) as valid proofs for the same authorization, any AA that uses the signature value itself (or a hash of it) as an anti-replay nonce can be tricked into treating a flipped-S resubmission as a "new" signature. A trigger sender who intercepts (or was the original recipient of) a valid signed authorization can derive the malleated counterpart signature without needing the private key, and resubmit it in a second trigger to pass `is_valid_sig()` again while bypassing the "already used" check keyed on the raw signature bytes. This can cause the AA to disburse funds or perform its authorized action a second time for a single legitimate authorization, resulting in AA fund loss.

### Likelihood Explanation
Deriving the malleated signature (`s' = n - s`) requires no private key and is a pure, cheap, deterministic elliptic-curve computation available to anyone who has observed one valid `(message, signature)` pair — including the legitimate recipient of a voucher/attestation. Any AA that follows the natural pattern of keying replay-protection state on the signature bytes (rather than on the message/nonce content) is directly exploitable by its own users/trigger senders.

### Recommendation
In `verifyMessageWithSecp256k1PemPubKey` (and any other secp256k1 signature verification path reachable from oscript/AA evaluation), reject non-normalized ("high-S") signatures instead of silently normalizing them — mirroring the behavior already relied upon in `signature.verify()`/`ecdsaSig.verify`. If normalization must be retained for compatibility, document clearly (and ideally canonicalize automatically) that `is_valid_sig` cannot be used as a unique nonce by AA authors, or expose a canonical hash of the verified `(message, pubkey)` pair for replay protection instead of the raw signature bytes.

### Proof of Concept
1. Sign a message `M` with a secp256k1 private key, producing signature `(r, s)` with `s` in the *upper* half of the curve order (a signer can always choose to publish the non-canonical form, or an observer can compute `s' = n - s` from any published `(r, s)`).
2. Submit an AA trigger with `is_valid_sig(M, pem_pubkey, sig_with_high_s)` — evaluation passes because `verifyMessageWithSecp256k1PemPubKey` normalizes `s` before calling `ecdsaVerify`.
3. If the AA records `var[sig] = 1` (or `sha256(sig)`) to block replay and the attacker later resubmits the same message signed with the *complementary* `s` value (`n - s` relative to whichever one was used first), `is_valid_sig` again returns `true` while the AA's replay-guard key (based on the differing raw signature bytes) does not match the first submission, allowing the payout/action to execute a second time.
