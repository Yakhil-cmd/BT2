### Title
Webhook signature verification is keyed by an attacker-controlled organization field, letting any configured GitHub organization forge `status` events for commits belonging to other organizations' stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate a delivery against using a field taken directly from the unauthenticated request body, not from any binding to the actual repository the payload claims to mutate. Because `Shipit::Webhooks::Handlers::StatusHandler` then acts on a commit found purely by `sha` (with no repository/org scoping at all), an org that legitimately owns one configured GitHub App/secret in a multi-org Shipit deployment can forge webhook deliveries that write CI status for commits belonging to a completely different organization's stacks — this breaks the binding "organization that authenticated == repository/stack that is written."

### Finding Description
`verify_signature` resolves the org used to pick a webhook secret from the request payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (fallback `organization.login`) — both fields live inside the same signed raw body, but they are attacker-authored content, and Shipit supports registering **independent per-organization webhook secrets**: [3](#0-2) 

Documented explicitly for multi-tenant setups: [4](#0-3) 

So `Shipit.github(organization: repository_owner)` returns the `GitHubApp` (and its `webhook_secret`) belonging to whatever org the attacker names in `repository.owner.login`. If that org is one the attacker legitimately administers (they created/installed their own GitHub App per the setup doc and thus know its `webhook_secret`), `verify_webhook_signature` succeeds using **that** org's secret over the full raw body — even though the body's `repository.full_name` / `sha` can reference an entirely different organization's stack.

The dispatched handler for `status` events does no such scoping — it looks up commits **globally by `sha`**, with no reference to `repository_owner`, `repository.full_name`, or any stack ownership check: [5](#0-4) 

Compare with the base `Handler` class, which *does* expose a `repository_name` helper based on `repository.full_name` — but `StatusHandler` doesn't use it at all, and even if it did, `repository.full_name` is just another payload field not bound to the verified org. [6](#0-5) 

The equality the code should — but does not — enforce is:
`organization whose webhook_secret validated the signature == organization owning the stack/commit the handler mutates`

Instead, the only binding enforced is: `organization named in payload.repository.owner.login == organization whose secret validated the HMAC` — a value fully controlled by the sender, disconnected from which commit/stack is actually written.

### Impact Explanation
Creating a forged `Status` record directly affects deploy-gating logic: [7](#0-6) [8](#0-7) [9](#0-8) 

`add_status` schedules `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` and fires `deployable_status`; `Commit#deployable?` treats `success?` (derived from the forged `Status.state`) as authorization to deploy. A forged `state: "success"` status with a `context` matching a stack's required CI check can make an unrelated organization's commit appear deployable, unblocking continuous deployment/merge-queue processing (`Stack#trigger_continuous_delivery`, `Stack#schedule_merges`) — this is an unauthorized-deploy-class impact reachable purely from an unprivileged sender who owns a different, legitimately-configured org in the same multi-tenant Shipit instance.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with multiple GitHub organizations (explicitly documented and supported), (2) the attacker controls (or has previously legitimately configured) one such org's GitHub App and therefore knows its own `webhook_secret`, and (3) knowledge of a target commit `sha` in another org's stack (git SHAs are frequently public/guessable via forks, PRs, or public commit history). No access to the victim org's secret, no Shipit session, and no `ApiClient` token are required — the trust boundary broken is purely the org‑to‑repository binding inside `WebhooksController`/`StatusHandler`.

### Recommendation
- After signature verification, re-derive the organization solely from a value that is cryptographically tied to the correct secret (i.e., verify the signature per-organization, but then also assert that `repository.owner.login`/`repository.full_name` used for verification matches the repository actually mutated by the handler).
- In `StatusHandler#process` (and any handler using `Commit.where(sha:)`), scope commit lookups to stacks whose `Repository` matches the same organization that validated the webhook signature, e.g. join through `stacks: :repository` filtered by `repository_owner`.
- Consider signing/validating per-organization webhook secrets against a canonical repository field established before signature verification, rather than trusting attacker-supplied `repository.owner.login` to select which secret to check against.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `orgA` (attacker-controlled, webhook secret known to attacker) and `orgB` (victim, tracks stack `victim/repo` with commit `abc123` requiring status context `ci/travis`).
2. Attacker crafts a JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "orgA" }, "full_name": "attacker/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` using their own known `orgA` secret.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner == "orgA"`, fetches `orgA`'s `GitHubApp`, verifies successfully against the attacker's own known secret.
6. `StatusHandler#process` runs `Commit.where(sha: "abc123")` — matches the victim's commit in `orgB`'s stack regardless of the `orgA` owner field — and creates a forged `success` `Status`, potentially unblocking that stack's continuous deployment/merge queue.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
