### Title
Webhook signature is verified against the wrong organization boundary, allowing any configured organization's secret to forge commit statuses for repositories/commits belonging to other organizations - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate a payload signature against by reading `repository.owner.login` (or `organization.login`) out of the same untrusted JSON body it is trying to authenticate [1](#0-0) [2](#0-1) . Once the signature passes, the actual event handler that mutates data does not re-check that same organization/repository at all: `StatusHandler#process` looks up commits **globally by `sha`** with no repository or organization scoping whatsoever [3](#0-2) . This is the same class of bug as the referenced report: the field used to authorize the request ("organization that authenticated") is not the field (or entity) that ends up being written ("repository/commit that is written").

### Finding Description
Shipit supports multi-tenant configuration where several distinct GitHub organizations each get their own `webhook_secret`, `oauth`, etc. [4](#0-3) . `Shipit.github(organization:)` looks up the per-organization config and builds a `GitHubApp` scoped to that org's secret [5](#0-4) .

`WebhooksController#verify_signature` picks the organization to verify against purely from the untrusted request body:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

So a sender who legitimately knows **any one** configured organization's `webhook_secret` (e.g. because they administer that org's own GitHub App integration with this Shipit instance) can HMAC-sign an arbitrary JSON body as long as `repository.owner.login` in the body matches that organization. The signature check only proves "this body was signed with OrgA's secret" — it proves nothing about which repository/commit the body's other fields describe.

Once past `verify_signature`, `create` dispatches the parsed body to handlers unmodified [7](#0-6) . `StatusHandler#process` never looks at `repository` or `organization` fields at all — it resolves target rows purely by commit `sha`, which is a global, cross-tenant identifier:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This breaks the binding `organization_authenticated == repository_written`: the org whose secret validated the HMAC (OrgA) has no relationship enforced with the `Commit`/`Stack`/`Repository` (potentially OrgB's) that actually gets mutated.

### Impact Explanation
An attacker who legitimately controls (or has been issued) the `webhook_secret` for one organization configured in this Shipit instance can forge a `status` event naming any commit `sha` known to exist in *any other* organization's stack tracked by the same instance, and inject an arbitrary commit status (`state`, `context`, `description`, `target_url`) for that commit — with no relation to their own organization or repository. If deploy/merge gating in this Shipit instance relies on `Commit` statuses (`deployable_status`, required status checks) to decide whether a commit is deployable, this allows an attacker outside of OrgB to fabricate a passing CI status on an OrgB commit, which is the exact precondition needed to make an otherwise non-deployable commit deployable — i.e., an unauthorized deploy path, satisfying the "unauthorized deploy" Critical impact criterion.

### Likelihood Explanation
Exploitability requires: (1) Shipit configured for more than one GitHub organization (a documented, supported multi-tenant deployment mode, evidenced by the sample multi-org secrets file), and (2) the attacker legitimately possesses a `webhook_secret` for at least one of those organizations (which is not privileged relative to any *other* tenant organization — it's simply their own tenant's integration secret, not a Shipit session/API token or GitHub App private key for the victim org). Given this, the attack is a single crafted HTTP POST with a correctly computed HMAC — no additional privilege escalation, session, or GitHub write access is required against the victim organization.

### Recommendation
- In `WebhooksController#verify_signature`, after determining which organization's secret validated the signature, cross-check that every subsequent handler operation stays scoped to that same organization/repository — do not allow handlers to resolve records purely by attacker-supplied identifiers (like `sha`) without also constraining by the authenticated repository/organization.
- In `StatusHandler#process` (and any other handler that resolves `Commit`/`Stack` by a payload field independent of `repository.full_name`), require and validate `payload.dig('repository','full_name')` against the repositories owned by the authenticated organization before touching any `Commit` records, e.g. scope `Commit.where(sha: params.sha)` to `stacks: { repositories: { owner: repository_owner } }`.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with distinct `webhook_secret`s (as in `config/secrets.development.shopify.yml`).
2. As an operator who only administers `orga`'s Shipit GitHub App integration (and thus knows only `orga`'s `webhook_secret`), find/guess a commit `sha` already tracked in one of `orgb`'s stacks (e.g., from public commit history or a previous legitimate status webhook).
3. Build a JSON body:
```json
{
  "sha": "<orgb-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orga" } }
}
```
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(orga_webhook_secret, body)` and POST it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"orga"`, verifies successfully against `orga`'s secret [1](#0-0) .
6. `StatusHandler#process` matches `Commit.where(sha: "<orgb-commit-sha>")`, ignoring which organization authenticated the request, and creates a fabricated "success" status on `orgb`'s commit [3](#0-2) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
