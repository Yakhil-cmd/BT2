### Title
Missing origin/domain binding check in WebAuthn assertion verification allows cross-origin signing material acceptance - (File: types/src/transaction/webauthn.rs)

### Summary
The `PartialAuthenticatorAssertionResponse::verify_arbitrary_msg` function (and its caller `verify`) parses `CollectedClientData` from the attacker-supplied `client_data_json` and validates only the `challenge` field against the expected transaction hash, then performs signature verification over `authenticator_data || SHA256(client_data_json)`. The `origin` field of `CollectedClientData` is deserialized but never compared against any expected relying-party origin/domain.

### Finding Description
`verify_arbitrary_msg` in [1](#0-0)  does the following: it deserializes `client_data_json` into a `CollectedClientData` struct, checks only that `collected_client_data.challenge` matches the expected SHA3-256 digest of the raw transaction signing message, builds `verification_data` from `authenticator_data` and the SHA-256 hash of the raw `client_data_json` bytes, and verifies the signature over that concatenation. The `origin` field, defined in the `CollectedClientData` struct [2](#0-1)  and populated by `collected_client_data_to_json_bytes` [3](#0-2) , is read but is not compared against any expected/allow-listed domain anywhere in the verification path. A repository-wide search for `rp_id`, `expected_origin`, `allowed_origin`, or `relying_party` checks in the WebAuthn code found none — the only test usages simply hard-code an arbitrary origin string (e.g. `"http://localhost:5173"` or `"http://localhost:4000"`) with no server-side check against it [4](#0-3) .

Because the origin is unchecked, any client_data_json (with any arbitrary or even fabricated origin string) that has a matching `challenge` and is signed by the holder's private key over `authenticator_data || SHA256(client_data_json)` will verify successfully — the origin binding property that WebAuthn is designed to enforce (i.e., that the assertion was generated by an authenticator/browser scoped to a specific relying-party origin) is not enforced by Aptos's admission logic.

### Impact Explanation
This corrupts the domain-binding invariant of WebAuthn: the whole point of `origin` in `CollectedClientData` is to bind an assertion cryptographically to the origin that solicited it, preventing signatures/credentials scoped to one origin (e.g., a phishing site or a different dApp) from being reused elsewhere. Since Aptos never checks `origin`, any correctly-challenge-bound and correctly-signed assertion is accepted regardless of which origin (or an empty/malformed one) it claims to have been generated for. However, note that the actual authorization guarantee that matters for transaction admission — the ECDSA/secp256r1 signature over `authenticator_data || SHA256(client_data_json)` — still requires possession of the private key corresponding to the account's public key. The missing origin check does not by itself let an attacker without the private key forge a valid transaction; it removes a defense-in-depth control that is supposed to prevent phishing/cross-origin credential misuse at the browser/authenticator layer, and it deviates from the WebAuthn spec's required relying-party verification step (§7.2, step 10 "Verify that the value of C.origin matches the Relying Party's origin").

### Likelihood Explanation
Any unprivileged party who can obtain a signed WebAuthn assertion (e.g., by tricking a passkey holder into signing via a look-alike or malicious website, or by capturing an assertion generated by unrelated software that reuses the same passkey) can resubmit it to Aptos with an arbitrary `origin` value and it will pass admission checks, since no domain verification step exists in `verify_arbitrary_msg`/`verify`.

### Recommendation
Add an explicit check in `verify_arbitrary_msg`/`verify` that compares `collected_client_data.origin` against an expected/allow-listed relying-party origin (or origin set) before accepting the assertion, consistent with WebAuthn §7.2 step 10.

### Proof of Concept
Using the existing test scaffolding in [5](#0-4) , construct a `CollectedClientData` with an arbitrary/attacker-chosen `origin` (e.g., `"https://evil.example"` or an empty string) while keeping `challenge` set to the correct SHA3-256 digest of the raw transaction. Sign `authenticator_data || SHA256(client_data_json)` with the account's private key as usual and submit the resulting `SignedTransaction`. `PartialAuthenticatorAssertionResponse::verify`/`verify_arbitrary_msg` [1](#0-0)  will return `Ok(())` regardless of the `origin` value, demonstrating the missing domain-binding check.

    pub fn verify_arbitrary_msg(&self, message: &[u8], public_key: &AnyPublicKey) -> Result<()> {
        let collected_client_data: CollectedClientData =
            serde_json::from_slice(self.client_data_json.as_slice())?;
        let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())
            .map_err(|e| anyhow!("Failed to decode challenge bytes {:?}", e))?;

        // Check if expected challenge and actual challenge match. If there's no match, throw error
        challenge_bytes
            .as_slice()
            .eq(message)
            .then_some(())
            .ok_or(CryptoMaterialError::ValidationError)?;

        // Generates binary concatenation of authenticator_data and hash(client_data_json)
        let verification_data = generate_verification_data(
            self.authenticator_data.as_slice(),
            self.client_data_json.as_slice(),
        );

        // Note: We must call verify_arbitrary_msg instead of verify here. We do NOT want to
        // use verify because it BCS serializes and prefixes the message with a hash
        // via the signing_message function invocation
        match (&public_key, &self.signature) {
            (
                AnyPublicKey::Secp256r1Ecdsa { public_key },
                AssertionSignature::Secp256r1Ecdsa { signature },
            ) => signature.verify_arbitrary_msg(&verification_data, public_key),
            _ => Err(anyhow!(
                "WebAuthn verification failure, invalid key, signature pairing"
            )),
        }
    }

    fn get_collected_client_data(raw_transaction: &RawTransaction) -> CollectedClientData {

        let sha3_256_raw_txn = HashValue::sha3_256_of(signing_message.as_slice());
        let sha3_256_raw_txn_bytes = Bytes::from(sha3_256_raw_txn.to_vec());

            cross_origin: None,
            unknown_keys: Default::default(),
        }
    }

    fn sign_webauthn_transaction(
        raw_txn: &RawTransaction,
        collected_client_data: CollectedClientData,
        authenticator_data: &[u8],
        private_key: &Secp256r1EcdsaPrivateKey,
    ) -> SignedTransaction {
        let public_key = Secp256r1EcdsaPublicKey::from(private_key);

        let client_data_json = serde_json::to_vec(&collected_client_data).unwrap();
        let client_data_hash = sha256(client_data_json.as_slice());

        let signature_material = [authenticator_data, &client_data_hash].concat();
        let signature = private_key.sign_arbitrary_message(signature_material.as_slice());
        let assertion_signature = AssertionSignature::Secp256r1Ecdsa { signature };

        let partial_authenticator_assertion_response = PartialAuthenticatorAssertionResponse::new(
            assertion_signature,
            authenticator_data.to_vec(),
            client_data_json,
        );
        let public_key = AnyPublicKey::Secp256r1Ecdsa { public_key };
        let signature = AnySignature::WebAuthn {
            signature: partial_authenticator_assertion_response,
        };
        let authenticator = SingleKeyAuthenticator::new(public_key, signature);
        let account_authenticator = AccountAuthenticator::SingleKey { authenticator };
        let txn_authenticator = TransactionAuthenticator::SingleSender {
            sender: account_authenticator,
        };
        SignedTransaction::new_signed_transaction(raw_txn.clone(), txn_authenticator)
    }
