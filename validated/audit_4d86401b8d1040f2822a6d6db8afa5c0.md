### Title
Attacker-controlled `AccountKey20` in XCM `Asset.id` lets `ERC20Transactor::deposit_asset_with_surplus` make the pallet's checking account the caller into an arbitrary contract - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor` (used as an `AssetTransactor` in Asset Hub Westend/Rococo XCM configs) treats the 20-byte key embedded in an XCM `Asset`'s `Location` as the address of an ERC20 contract and directly calls `IERC20::transfer` on it, using a privileged, pallet-controlled account (`TransfersCheckingAccount`) as `msg.sender`, without ever verifying that this address corresponds to a contract that was legitimately registered/created as a real ERC20 asset.

### Finding Description
`ERC20Transactor::deposit_asset_with_surplus` extracts `asset_contract_id` from the incoming `AssetsInHolding` via `Matcher::matches_fungibles(&asset)` [1](#0-0) , and then issues a `bare_call` to that address using `TransfersCheckingAccount` as the signed origin/`msg.sender`: [2](#0-1) 

Similarly, `withdraw_asset_with_surplus` calls `IERC20::transfer` on the attacker-influenced `asset_id` using the XCM-derived `who` as origin: [3](#0-2) .

Per the feature's own PRDoc, the matched address is exactly the `key` field of an `AccountKey20` junction supplied inside the XCM message's `Asset` location — there is no lookup against a registry of "real" ERC20 contracts deployed via `pallet-revive`'s factory/instantiate path: [4](#0-3) . This is structurally identical to the Rolla `Controller::_qTokenPermit` bug: a privileged/asset-bearing account (there, the `Controller`; here, `TransfersCheckingAccount`) is made to call into an address taken directly from unauthenticated user/message input, without checking `IOptionsFactory::isQToken`-equivalent registry membership (e.g. `isContract`/registered-asset check).

`ERC20Transactor` is wired into `AssetTransactors` in `asset-hub-westend`'s `xcm_config.rs`: [5](#0-4) , so it is reachable through any XCM path that ultimately calls `deposit_asset`/`withdraw_asset` for an asset whose `Location` matches the ERC20 matcher (e.g. a `ReserveAssetDeposited`/`WithdrawAsset` XCM instruction from a permitted origin, or through pallet-xcm's public `transfer_assets`/teleport/reserve-transfer extrinsics if the asset ID is attacker-chosen).

### Impact Explanation
Because `TransfersCheckingAccount` is a fixed pallet-controlled account (`PalletId(*b"py/revch")` [6](#0-5) ) that legitimately holds real ERC20 balances backing bridged/reserved assets, if an attacker can get the executor to treat an arbitrary attacker-deployed contract address as the "ERC20 asset contract" (bypassing the intended matcher restriction), they can make `TransfersCheckingAccount` invoke arbitrary logic in their contract as `msg.sender`. Depending on what checks/filters actually constrain which `Location`s reach this transactor (which I could not fully verify — see below), this could range from a harmless failed/no-op call (if strict registry/matcher checks fully prevent unregistered contracts from matching) up to funds-draining or unauthorized actions if the attacker's contract can, e.g., read `msg.sender == TransfersCheckingAccount` to unlock a real reserve or otherwise abuse the privileged caller identity in a downstream integration.

### Likelihood Explanation
I was **not able to fully verify** the exact implementation of `assets_common::ERC20Matcher` (the `Matcher` type parameter used in Asset Hub Westend's config) within the available index — specifically whether it validates that the derived `H160` corresponds to a contract that was actually instantiated/registered as an ERC20 asset (e.g. checking `pallet_revive::ContractInfoOf` or a dedicated ERC20 asset registry) before allowing the transactor to act, or whether it purely performs a location→address conversion as the PRDoc's description implies ("the corresponding transfer function will be called in the smart contract whose address is `key`", with no registry check mentioned). This uncertainty is central to whether this is exploitable as described or is safely gated elsewhere (e.g. by `IsReserve`/`IsTeleporter`/`Barrier` filters restricting which asset `Location`s are ever allowed to reach the executor's asset-in/asset-out logic in the first place).

### Recommendation
Locate `assets_common::ERC20Matcher`'s implementation and confirm whether it validates that the target `H160` address is a genuinely tracked/registered ERC20 contract (e.g., via `pallet_revive::AccountInfoOf`/`ContractInfoOf` lookup, or an explicit asset registry) before `ERC20Transactor` calls into it as `TransfersCheckingAccount`. If no such check exists, add one (analogous to the Rolla fix's `IOptionsFactory::isQToken` probe) so that only contracts genuinely deployed/registered as ERC20 assets can be targeted by the privileged checking account.

### Proof of Concept
Not executed. A full PoC would require: (1) confirming `ERC20Matcher`'s source to determine whether arbitrary `AccountKey20` locations pass matching without registry validation, and (2) constructing an XCM message (via `pallet_xcm::transfer_assets` or an XCM `Transact`/`DepositAsset` reaching `AssetTransactors`) whose `Asset.id` encodes an attacker-deployed contract address, then observing whether `deposit_asset_with_surplus` invokes that contract with `TransfersCheckingAccount` as caller. This reproduction was not carried out due to tool/index limitations; a Devin session with full repository access would be needed to inspect `ERC20Matcher`'s source and run an integration test against `asset-hub-westend-runtime`.
