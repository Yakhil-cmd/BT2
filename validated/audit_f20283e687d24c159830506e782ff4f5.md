### Title
Unvalidated swap-route venues can attach unauthorized wallet transfers to a signed strategy - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller treats the user-supplied `swap` payload as an opaque route and delegates venue selection to the configured router. Although the controller authorizes only one exact input transfer, a malicious venue named by that route can issue another `token.transfer(victim, attacker, amount)` under the same caller authorization tree. If the victim signs the poisoned simulated authorization tree, the route succeeds while stealing unrelated wallet funds. The test harness demonstrates this exact authorization behavior and fund movement. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and its optional conversion path all pass caller-controlled route bytes into `swap_tokens`. For example, `swap_collateral(caller, account_id, current, amount, new, swap)` authenticates only the account owner/delegate and forwards `swap` without venue validation. [3](#0-2) [4](#0-3) 

Inside `swap_tokens`, the controller snapshots input/output balances, authorizes `token_in.transfer(controller, router, amount_in)`, invokes `router.execute_strategy`, refunds unused input, and requires positive measured output. These checks constrain only the controller-held input and output; they do not constrain contracts invoked by the router or additional caller-authorized actions performed by those contracts. [5](#0-4) 

The harness router decodes a route-selected `hop_pool` and invokes it before returning a fair output. A malicious pool can then invoke an unrelated token's `transfer` from the victim to the attacker. [6](#0-5) [2](#0-1) 

Simulation records that unrelated wallet transfer as a child of the victim's `swap_collateral` authorization entry. Enforced authorization rejects it if the victim signs only the honest root invocation, but executes it when the victim signs the poisoned tree returned by simulation. [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker can steal arbitrary tokens held by the victim, including assets never listed by the protocol. The demonstrated route leaves a fair protocol swap output and a valid resulting position, so the strategy's balance-delta and solvency checks do not detect the unrelated wallet transfer. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
Any unprivileged user can submit the malicious `swap` bytes because route payloads are arguments to public strategy entrypoints, and the route's venue address is decoded by the router rather than validated by the controller. Exploitation requires the victim to submit/sign a maliciously constructed route and its simulated authorization tree, analogous to signing a malicious package build configuration; wallets or clients that do not inspect nested authorization invocations can expose the transfer as part of the expected signature. [3](#0-2) [11](#0-10) 

### Recommendation
Require all route venues and invoked pool contracts to come from an explicit protocol-controlled allowlist, or redesign routing so venue bytecode cannot request additional `caller` authorization beneath the strategy root. Until venue containment exists, the router/controller interface should expose a machine-readable manifest of every nested authorization that a route may request, and clients must reject any authorization tree beyond the exact expected strategy and input-transfer invocations. [1](#0-0) [8](#0-7) 

### Proof of Concept
The repository already contains a runnable analog:

1. Configure the controller to use a router whose payload contains `hop_pool`, `token_in`, `token_out`, and `min_out`.
2. Give Alice protocol collateral plus a separate unlisted wallet token.
3. Build `swap` bytes naming an attacker-controlled `hop_pool`.
4. During `swap_collateral`, the router invokes the malicious pool's `swap` function.
5. That function calls `token.transfer(Alice, attacker, WALLET_BALANCE)`.
6. Simulation places the transfer under Alice's `swap_collateral` authorization entry; signing that tree drains all `77_770_000_000` wallet tokens while returning fair swap output. [12](#0-11) [13](#0-12) [7](#0-6)
