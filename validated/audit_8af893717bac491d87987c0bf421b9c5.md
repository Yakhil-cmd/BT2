### Title
`data_feed()` oscript function can throw an uncaught exception in `readDataFeedValue`, crashing every node processing the AA trigger - (File: data_feeds.js)

### Summary
The MongoDB CVE-2020-7923 describes a crafted `geoNear` query that violates an internal invariant of the query subsystem, causing the server process to crash (assertion failure / DoS). The ocore analog is the `arrCandidates.sort()` comparator inside `data_feeds.js`'s `readDataFeedValue()`, which is used by the `data_feed()` oscript function available to any Autonomous Agent (AA). When it cannot determine an ordering between two ambiguous unstable AA data-feed candidates, it executes `throw Error("can't sort candidates "+a+" and "+b)` instead of returning a graceful error. Because ocore installs a global `uncaughtException` handler that re-throws to intentionally crash the process (`network.js`), this uncaught error brings down every full node that evaluates the offending AA formula while validating the triggering unit — a network-wide denial of service, exactly analogous to how a malformed `geoNear` query crashed `mongod`.

### Finding Description
`data_feed()` (and its sibling `in_data_feed`) is a standard oscript function that any AA definition author can call, and it is evaluated for every unit that triggers that AA — i.e., by any unprivileged unit poster who sends a payment/trigger to the AA's address. When called from within AA formula evaluation (`bAA` truthy), the evaluator invokes: [4](#0-3) 

which calls `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, ...)`. Inside `readDataFeedValue`, when `unstable_opts` (here, the boolean `bAA`) is truthy but not the literal string `'all_unstable'`, `bIncludeUnstableAAs` is `true` while `bIncludeAllUnstable` stays `false`: [5](#0-4) 

The function then scans `storage.assocUnstableMessages` for every currently-unstable AA-response unit authored by one of the queried "oracle" addresses, and, for every `data_feed` message whose `feed_name` matches and whose value equals the queried `value` (or any value if `value === null`), pushes a candidate `{value, latest_included_mc_index, level, unit}`: [6](#0-5) 

If more than one such candidate exists and `ifseveral` is not `'abort'`, the code tries to rank candidates by `latest_included_mc_index` then by `level`. If two candidates have both fields equal — a realistic scenario for two AA response units on parallel/sibling DAG branches that were both unstable at query time — and `bIncludeAllUnstable` is `false` (always the case from this call path since `bAA` is a boolean, never the string `'all_unstable'`), the comparator throws: [2](#0-1) 

This `throw` occurs synchronously inside `Array.prototype.sort`'s comparator, deep inside the async validation/AA-execution call chain (`aa_composer.js` → `formula/evaluation.js` → `data_feeds.js`), with no enclosing `try/catch` to convert it into a formula-level `fatal_error`/bounce. It therefore propagates as an uncaught exception. ocore's `network.js` installs a global handler that explicitly re-throws any uncaught exception to crash the process: [1](#0-0) 

Since AA-trigger processing (and thus this code path) is deterministic and executed identically by every full node that validates/receives the triggering unit, all such nodes crash when they process it.

### Impact Explanation
A crash triggered this way halts a node's ability to validate and confirm any further units until it is manually restarted, and because the condition is deterministic, every full node in the network that processes the crafted trigger unit crashes identically — a network-wide denial of service preventing confirmation of new units. This matches the "network unable to confirm new units" impact bar required for this class of finding.

### Likelihood Explanation
Exploitation requires an unprivileged unit poster to author (or use) an AA whose definition calls `data_feed()` referencing some oracle address(es)/feed name, then arrange for that same AA/oracle combination to emit two distinct unstable AA-response units carrying `data_feed` messages with equal (or matching) values, where those two response units happen to share the same `latest_included_mc_index` and `level` — achievable by crafting two independent triggers on parallel DAG branches processed before either becomes stable. This requires deliberate crafting but no special privileges, elevated keys, or trusted role, making it feasible for any network participant able to post units and define/trigger AAs.

### Recommendation
Replace the `throw Error(...)` in the sort comparator in `data_feeds.js` (`readDataFeedValue`) with a deterministic tie-breaking rule (e.g., fall back to comparing `unit` hash lexicographically, mirroring the `bIncludeAllUnstable` "sort randomly" branch) so that ambiguous candidates never throw. More generally, any code reachable from AA/unit validation should return errors through the existing `fatal_error`/callback mechanism rather than `throw`, given that the process is configured to crash on any uncaught exception.

### Proof of Concept
1. Deploy an AA whose formula calls `data_feed[oracles="ORACLE_ADDR", feed_name="x"]` (value omitted, so `value === null`, matching any feed value) inside a `bounce`/response formula that runs for every trigger.
2. Have `ORACLE_ADDR` (which can be any AA/address able to emit `data_feed` messages, including the same AA acting as its own oracle in different branches) post two units, each containing a `data_feed` message named `x` with any values, arranged on two independent (non-descendant) DAG branches so neither is included in the other's `parent_units` chain, and such that both become unstable simultaneously with identical `level` and `latest_included_mc_index` (achievable by symmetric parent selection when composing both units against the same tip set).
3. Send a trigger unit to the AA while both `data_feed`-posting units are still unstable.
4. During `handleTrigger` → `evaluateAA`/`replace` → `formula/evaluation.js`'s `data_feed` case → `dataFeeds.readDataFeedValue`, `arrCandidates` will contain the two ambiguous entries; the `.sort()` comparator throws `Error("can't sort candidates ...")`.
5. The exception is uncaught, reaches `process.on('uncaughtException', ...)` in `network.js`, and the handler re-throws, crashing the node. Every node that validates the trigger unit experiences the same crash.
