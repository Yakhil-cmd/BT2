### Title
Webhook signature verification binds to `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, enabling cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using `repository.owner.login` (or `organization.login`), but the HMAC only proves the payload was signed by *that* organization's secret — it never constrains which repository the payload can target. The actual event handlers (`PushHandler`, `PullRequest::*Handler`) look up the `Stack`/`Repository` to act on using a *different* JSON field, `repository.full_name`, via `Repository.from_github_repo_name`. Because Shipit supports multi-organization configuration (each org with its own independent `webhook_secret`), an attacker who legitimately controls the webhook secret for one configured organization can forge a payload where `repository.owner.login` names their own org (so signature verification passes) while `repository.full_name` names a stack belonging to a *different* configured organization, causing Shipit to sync/deploy/archive that other org's stack.

### Finding Description
The binding broken is:
```
authenticated_organization (repository.owner.login, verified by HMAC)
        ≠
acted_upon_repository (repository.full_name, used to resolve the Stack)
```

`WebhooksController#verify_signature` derives the signing organization solely from the payload itself, not from any independent, unforgeable identifier: [1](#0-0) [2](#0-1) 

The HMAC (`verify_webhook_signature`) only proves the raw body was signed by the secret configured for that org — it says nothing about what repository the payload is allowed to reference: [3](#0-2) 

Multiple organizations, each with an independently-configured `webhook_secret`, are explicitly supported: [4](#0-3) [5](#0-4) 

Once the signature passes, `create` dispatches the *entire* raw payload — including whatever `repository.full_name` the attacker chose — to every registered handler for the event: [6](#0-5) 

Handlers resolve the target repository purely from `repository.full_name`, independent of `repository.owner.login`: [7](#0-6) [8](#0-7) [9](#0-8) 

The same pattern (repository resolved from `params.repository.full_name`, unrelated to signature-selecting owner) recurs in the pull-request handlers: [10](#0-9) [11](#0-10) 

Nowhere is `repository.owner.login` checked against the owner segment of `repository.full_name`, so the two fields can diverge arbitrarily inside one signed payload.

### Impact Explanation
This crosses the "cross-repository writes / unauthorized deploy" boundary called out as Critical impact. An attacker who controls the webhook secret for organization A (a value scoped only to that org's GitHub App configuration) can forge a `push` payload signed with OrgA's secret but targeting `repository.full_name = "orgB/target-repo"`. If OrgB has `continuous_deployment` enabled, this can trigger `GithubSyncJob` and cause deploys/rollbacks on OrgB's stack; for pull-request events it can archive/unarchive review stacks or manipulate PR-driven state for repositories the attacker has no legitimate access to. This is a genuine credential/organization-boundary violation: "possessing organization A's webhook secret" is treated as sufficient authorization to mutate organization B's stacks.

### Likelihood Explanation
Requires the host to have configured more than one organization in `secrets.yml` (a documented, supported configuration) and requires the attacker to possess (or have leaked) one configured org's `webhook_secret` — not GitHub credentials for the target org. Given webhook secrets are lower-value, more widely distributed credentials (shared with whoever configures the GitHub App per org) than full repository/GitHub App admin access, this is a plausible attacker profile distinct from a "privileged account with repository write access" that the rules exclude.

### Recommendation
In `WebhooksController#verify_signature`, after determining `repository_owner` and verifying the HMAC, additionally assert that `repository_owner` matches the owner segment of `params.dig('repository', 'full_name')` (and of `organization.login` if present) before allowing the payload to be dispatched to handlers. Reject (422) any payload whose `repository.owner.login` does not match the owner derived from `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with a distinct `webhook_secret` (per `docs/setup.md` multi-org example).
2. As an attacker who knows `orgA`'s `webhook_secret` (e.g. a former or malicious admin of OrgA's GitHub App, without any access to OrgB), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-controlled or real head sha for orgB stack>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner = "orgA"`, calls `Shipit.github(organization: "orgA")`, and the signature verifies successfully (attacker knows OrgA's secret).
6. `create` dispatches the parsed body to `PushHandler`, which resolves `Repository.from_github_repo_name("orgB/target-repo")` and enqueues `GithubSyncJob` against OrgB's stack — a stack the attacker was never authorized to trigger via OrgA's credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
