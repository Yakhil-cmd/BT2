### Title
Cross-repository forged CI status via webhook — the organization whose secret authenticates the request is never bound to the commit/repository whose status gets written - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify a webhook against using an attacker-supplied field of the very payload it is about to validate. Once verified, `Shipit::Webhooks::Handlers::StatusHandler` writes a CI status to any `Commit` in the entire Shipit installation that matches the payload's `sha`, with no check that the commit belongs to the repository/organization that supplied the signing secret. This breaks the equality "organization that authenticated == repository that is written," allowing an attacker who controls one Shipit-integrated GitHub organization to forge CI statuses on commits belonging to a completely different, unrelated stack/repository in the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, which is read straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, looked up via `Shipit.github(organization: ...)`, and each app's secret is used only for `verify_webhook_signature`: [3](#0-2) [4](#0-3) 

An operator running one Shipit instance for several organizations (a documented, code-supported configuration) has one legitimate `webhook_secret` per organization. An attacker who administers *their own* organization's GitHub App installation knows *their own* secret and can craft an arbitrary, self-signed `status` webhook payload. `verify_signature` only checks that the signature matches the secret belonging to whatever `repository.owner.login` the attacker put in the payload — it never checks that this organization actually owns the commit referenced elsewhere in the same payload.

After the signature passes, `StatusHandler#process` looks up commits **globally**, by `sha` only, with no repository/stack scoping at all: [5](#0-4) 

Contrast this with `PushHandler` and `CheckSuiteHandler`, which correctly scope to `stacks` derived from `repository.full_name` before acting: [6](#0-5) [7](#0-6) [8](#0-7) 

`StatusHandler` has no such scoping — the binding "organization that signed the request" vs. "repository whose commit is mutated" is entirely absent for this event type.

### Impact Explanation
Any commit `sha` collision across repositories tracked by the same Shipit instance lets the attacker's own, validly-signed `status` event write a fabricated CI status (`state`, `context`, `target_url`, `description`) onto a commit belonging to a victim stack they have no access to. If that victim stack's `shipit.yml` / required statuses gate deploys on that context being green (`CommitChecks`), the attacker can flip a pending/failing check to `success` and enable an **unauthorized deploy** on a repository outside their control — a cross-repository write achieved purely through an authentication boundary the attacker legitimately owns for a different organization. This satisfies the in-scope Critical impact bar ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Requires: (1) a Shipit instance configured for multiple GitHub organizations (a supported, code-backed configuration, not a special/rare setup), and (2) the attacker controlling one such organization's own GitHub App installation and thus its `webhook_secret` — something entirely within their own authority, requiring no access to the victim repository. The only remaining requirement is a `sha` collision/target commit whose value is often predictable (commits are frequently public, and shas are often known from PRs, CI, or public commit history). No privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repo is needed.

### Recommendation
In `StatusHandler` (and any other handler that writes state keyed only by `sha`), scope the query to the repository/organization that produced the verified signature, not just by `sha`. Concretely, thread the authenticated `repository_owner`/`full_name` through to handlers and restrict `Commit.where(sha: params.sha)` to `Repository.from_github_repo_name(repository_name).stacks.commits.where(sha: ...)`, mirroring what `PushHandler`/`CheckSuiteHandler` already do via `Handler#stacks`.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (supported multi-org configuration).
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that org/app).
3. Attacker finds/knows a commit `sha` that exists in a stack belonging to `victim-org` (e.g., from a public PR or leaked commit hash).
4. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body `{"repository":{"owner":{"login":"attacker-org"}, "full_name":"attacker-org/anything"}, "sha":"<victim-sha>", "state":"success", "context":"required-ci-check"}`, signed with `attacker-org`'s webhook secret.
5. `verify_signature` resolves `repository_owner` to `"attacker-org"`, verifies successfully against that org's secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim's commit regardless of repository, and calls `commit.create_status_from_github!(params)`, writing a fabricated `success` status onto the victim's commit — potentially satisfying a deploy-gating check the attacker never had permission to influence.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
