### Title
Multisig timelock protection can be silently bypassed for already-queued transactions - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`multisig_account.move` implements an optional per-account timelock (`MultisigAccountTimeLock`) that is meant to force a minimum waiting period before an approved multisig transaction can execute, giving owners a window to react to a malicious/compromised approval. The elapsed time used for this check is computed from the transaction's `creation_time_secs` (set once, at `create_transaction` time), not from when the timelock was configured. As a result, adding or increasing a timelock provides **no protection at all** for any transaction that was already created and is already sitting in the pending queue, if that transaction is older than the new `timelock_period`. Such a transaction can be executed immediately after `upsert_timelock` takes effect, exactly as if no timelock had ever been added — even though the intent of enabling the timelock was to delay execution.

### Finding Description
`validate_multisig_transaction`, which is invoked by the VM as part of the transaction prologue for multisig execution, gates execution on `can_execute_with_timelock`: [1](#0-0) 

```move
inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
    if (exists<MultisigAccountTimeLock>(multisig_account)) {
        ...
        let pending_transaction = get_transaction(multisig_account, sequence_number);
        let elapsed = now_seconds() - pending_transaction.creation_time_secs;
        (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
    } else {
        true
    }
}
```

`creation_time_secs` is fixed at the moment `create_transaction`/`create_transaction_with_hash` is called and never updated afterward. `upsert_timelock_internal` (which publishes/updates `MultisigAccountTimeLock`) does not touch any pending `MultisigTransaction`: [2](#0-1) 

The developers' own doc comment even acknowledges a related but narrower timing quirk, explicitly framing it as an "acceptable, operator-visible risk": [3](#0-2) 

However, the actual exposure is broader than described: if a transaction was created **more than `timelock_period` seconds before `upsert_timelock` is called**, `elapsed >= timelock` is already true the instant the timelock takes effect. The newly configured timelock delivers *zero* delay for that transaction — it can be executed in the very next transaction after `upsert_timelock` commits, defeating the entire purpose of adding the timelock (e.g., as an emergency response after owners suspect a stored transaction is malicious and want time to organize a rejection).

This is a pre-validation/admission mismatch: the intended admission policy ("this multisig transaction may not execute until `timelock_period` seconds have elapsed since the protection was enabled/updated") is not what `validate_multisig_transaction` actually enforces ("...since the transaction was originally queued"), allowing a transaction that should be blocked from executing under the newly-configured policy to pass admission and commit.

### Impact Explanation
Timelocks on multisig accounts are a security control specifically meant to protect against a scenario where a quorum of owner keys is compromised or colludes to push through a malicious transaction (e.g., draining treasury funds, rotating owners, changing signature thresholds). The entire value of the feature is the guaranteed minimum delay it is supposed to add once configured. Because the delay is computed from `creation_time_secs` rather than from the time the timelock was (re)configured, an attacker who has already queued a malicious transaction long enough in advance (or an operator who reactively enables a timelock too late) gets no protection whatsoever — the "protected" transaction executes exactly as it would have without any timelock. Since this directly undermines a security control gating fund-moving/governance-changing multisig execution with no error surfaced to the caller, this is a high-impact logic flaw in an on-chain approval-set validation mechanism.

### Likelihood Explanation
This triggers automatically and deterministically any time `upsert_timelock` is used on an account that has one or more pending transactions older than the newly set `timelock_period` — no special privilege or race condition is required, and it is the expected, common case for reactive use of the feature (adding a timelock after suspicious approvals appear). No exploit crafting is needed beyond normal usage of the documented multisig timelock API.

### Recommendation
Compute the effective start time for the timelock check from `max(pending_transaction.creation_time_secs, timelock_activation_time)`, where `timelock_activation_time` is recorded in `MultisigAccountTimeLock` at the time the timelock is created/updated via `upsert_timelock_internal`. This ensures that any transaction pending at the moment protection is enabled/strengthened is subject to the full configured delay, rather than inheriting an already-expired age.

### Proof of Concept
1. Owner creates multisig account with no timelock, `num_signatures_required = 2` of 3 owners.
2. At `t=0`, owner A creates transaction #1 (`creation_time_secs = 0`) and it accumulates 2 approvals (quorum met) but is not yet executed (e.g., waiting for gas or batching).
3. At `t=10000` (well over an hour later), owners notice transaction #1 looks malicious/unexpected and call `upsert_timelock(multisig_signer, 3600 /* 1 hour */, option::none())` intending to buy time to reject it.
4. Immediately after, any owner calls execution of transaction #1: `elapsed = now_seconds() - 0 = 10000 >= 3600`, so `can_execute_with_timelock` returns `true` and `validate_multisig_transaction` permits execution right away — the newly added 1-hour timelock provided no delay at all, despite being configured specifically to stop this transaction.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    fun upsert_timelock_internal(
        multisig_account: &signer,
        timelock_period: u64,
        override_threshold: Option<u64>,
    ) {
        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);

        assert!(
            timelock_period >= MIN_TIMELOCK_PERIOD && timelock_period <= MAX_TIMELOCK_PERIOD,
            error::invalid_argument(EINVALID_TIMELOCK_DURATION)
        );

        let multisig_account_resource = &MultisigAccount[multisig_address];
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required,
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length(),
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );

        if (exists<MultisigAccountTimeLock>(multisig_address)) {
            let multisig_account_resource = &mut MultisigAccountTimeLock[multisig_address];
            multisig_account_resource.timelock_period = timelock_period;
            multisig_account_resource.override_threshold = override_threshold;
        } else {
            move_to(multisig_account, MultisigAccountTimeLock::V1 {
                timelock_period,
                override_threshold,
            });
        }

        emit(TimelockUpdated {
            multisig_account: multisig_address,
            timelock_period,
            override_threshold,
        });
    }
