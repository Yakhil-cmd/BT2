### Title
Arbitrary swap-route contracts can abuse a caller-signed authorization tree to drain unrelated wallet tokens - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
High: user-controlled `swap` payloads allow route execution to reach attacker-deployed contracts beneath the caller’s `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization, and those contracts can append unrelated token transfers to the authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` accepts an opaque `swap: Bytes` argument and passes it into the collateral withdrawal-and-swap flow after normal account authorization. [3](#0-2) [4](#0-3) 

`swap_tokens` forwards that payload to the configured router through `execute_strategy`; it snapshots and bounds only the controller’s `token_in` balance and requires only a positive measured `token_out` receipt. [5](#0-4) [6](#0-5) 

The controller’s own authorization is narrowly scoped to one exact token transfer with no nested invocations, but that bound does not constrain third-party code reached through the route beneath the user’s authorization. [7](#0-6) [8](#0-7) 

A route can therefore invoke an attacker-deployed venue, and that venue can request `token.transfer(victim, attacker, amount)` for any unrelated token held by the caller. [9](#0-8) [10](#0-9) 

### Impact Explanation
This permits theft of user funds outside the funds committed to the strategy: simulation records the rogue transfer as a child of the victim’s controller authorization, and a wallet or interface that signs that tree authorizes the transfer. [11](#0-10) 

The enforced-auth test demonstrates that the same route succeeds once the simulated poisoned child invocation is signed, transferring the victim’s entire unrelated wallet-token balance to the attacker while the collateral swap still completes. [12](#0-11) 

The protocol’s balance-delta checks cannot detect this loss because they measure only the controller’s `token_in` spend and `token_out` receipt, not unrelated debits from the caller’s wallet. [13](#0-12) [6](#0-5) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious hop contract and supply a route through a poisoned interface, compromised route provider, or malicious transaction-building flow; the victim remains an unprivileged caller and only needs to sign the authorization tree produced by simulation. [14](#0-13) [15](#0-14) 

The same opaque route argument is exposed by all controller strategy entrypoints that perform routed swaps, so the issue is not confined to `swap_collateral`. [16](#0-15) 

### Recommendation
Do not execute arbitrary route-selected contracts while the transaction carries the user’s authorization: constrain route hops to governance- or protocol-allowlisted venue contracts, or make the router execute only known venue implementations that cannot invoke caller-selected code. [1](#0-0) [2](#0-1) 

Until routes are structurally constrained, transaction builders and wallets must reject any controller strategy authorization tree containing child invocations other than the protocol’s expected input transfer. [7](#0-6) [17](#0-16) 

### Proof of Concept
1. Deploy `RogueHopPool` with `(victim, unrelated_wallet_token, attacker, victim_balance)` as its stored plan. [18](#0-17) 
2. Build a route whose `hop_pool` is the malicious contract and whose `min_out` still returns a valid output token amount. [14](#0-13) 
3. Have the victim call `controller.swap_collateral(caller=victim, account_id, current=usdc_key, amount, new=eth_key, swap=route)`. [3](#0-2) 
4. During router execution, invoke the malicious `hop_pool.swap`, which calls `unrelated_wallet_token.transfer(victim, attacker, victim_balance)`. [9](#0-8) [10](#0-9) 
5. Simulation records that transfer as a child of the victim’s controller authorization; signing the returned tree executes the theft while the swap produces valid output. [19](#0-18) 
6. The repository’s regression test confirms the result: the victim’s unrelated token balance becomes zero, the attacker receives it, and the victim receives the expected swap collateral. [20](#0-19)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
