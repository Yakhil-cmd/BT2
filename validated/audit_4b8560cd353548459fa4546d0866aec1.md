## Title
Webhook Signature Verification Authenticates the Claiming Organization, Not the Repository/Commit the Event Actually Mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App secret of the *organization named in the payload* [1](#0-0) , using `repository_owner` derived from `params.dig('repository', 'owner', 'login')` or the fallback `params.dig('organization', 'login')` [2](#0-1) . Once that HMAC check passes, the entire raw `params` hash is handed unmodified to event handlers [3](#0-2) . Several handlers then act on repository/commit identifiers taken from *other, independently-attacker-controlled fields of the same payload* that are never checked against the organization that produced a valid signature.

### Finding Description
The binding that should hold is:
`organization whose webhook secret produced a valid HMAC == organization/repository the handler subsequently mutates`

This binding is not enforced:

- `StatusHandler` looks up commits **globally by SHA with no repository scoping at all**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . Nothing ties `params.sha` back to `repository_owner`, the field the signature was verified against.
- `PushHandler`, `pull_request/OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc. resolve the target repository from `payload.dig('repository', 'full_name')` [5](#0-4) , a JSON field completely separate from `repository.owner.login`/`organization.login` used by `verify_signature`.
- `GithubApp#verify_webhook_signature` HMACs the raw payload bytes with the secret for whichever organization `repository_owner` names [6](#0-5) ; it never checks that `repository.full_name` (or any commit `sha`) actually belongs to that organization. `Repository.from_github_repo_name` performs a simple owner/name split against the DB with no relation to the authenticating org [7](#0-6) .

Because Shipit is explicitly designed to host multiple organizations side by side (see `config/secrets.development.shopify.yml`'s `somegithuborg`/`someothergithuborg` and `TOP_LEVEL_GH_KEYS`) [8](#0-7) , an attacker who is a legitimate, unprivileged member/owner of *their own* low-privilege organization onboarded to the same Shipit instance knows a valid webhook secret for that org (they configured/installed the GitHub App themselves). They can craft a JSON body where:
- `repository.owner.login` (or `organization.login`) = their own org → passes `verify_signature`.
- `repository.full_name` / `sha` = a value belonging to a **different, victim-owned** stack tracked by the same Shipit instance.

`verify_signature` only proves "this attacker-controlled organization signed this bag of bytes"; it never proves "this organization owns the repository/commit referenced inside those bytes." That equality is the binding described in the report's `_ineligible()` analogy — a value (`repository`/`sha`) is acted upon by the handler but is never covered by the check (`verify_signature`) that is supposed to authorize the action.

### Impact Explanation
Using the `status` webhook, the attacker can forge a `success` (or any) CI status for an arbitrary commit `sha` belonging to a completely unrelated, victim stack [4](#0-3) . If that victim stack has `continuous_deployment` enabled and gates auto-ship on required CI statuses, this forged status can trigger an **unauthorized deploy** — one of the explicitly listed Critical impacts. Using the `push` webhook with a spoofed `repository.full_name`, the attacker can also force `GithubSyncJob` to run against a victim stack with an attacker-chosen `expected_head_sha` [9](#0-8) , and via the pull-request handlers can create/archive/unarchive review stacks belonging to a repository the attacker does not own [10](#0-9) .

### Likelihood Explanation
Requires only: (1) the target Shipit instance to onboard more than one GitHub organization (documented, supported multi-tenant configuration), and (2) the attacker to control/own one of those low-privileged organizations (a normal, unprivileged position — no repository write access or Shipit session needed for the victim's repo). The commit SHA needed for the `status` path is public GitHub information. No `ApiClient` token, `webhook_secret` of the victim, or GitHub App private key is required — only the attacker's own legitimately-issued webhook secret.

### Recommendation
Require every handler to cross-check the repository/organization referenced inside the payload (`repository.full_name`, or the repository owning the target commit `sha`) against the organization whose secret validated the signature, rejecting the event when they diverge. Concretely, `WebhooksController` should carry the verified `repository_owner` (or its resolved `GitHubApp`) into handler dispatch, and `Handler#stacks`/`StatusHandler#process` should filter to stacks/commits whose `Repository#owner` matches that verified value rather than trusting `repository.full_name` or `sha` unscoped.

### Proof of Concept
1. Attacker legitimately installs a GitHub App for their own org `attacker-org` on a Shipit instance that also tracks a victim stack `victim-org/prod-app` (multi-org config as in `config/secrets.development.shopify.yml`).
2. Attacker obtains the public commit SHA `deadbeef...` of the current HEAD of `victim-org/prod-app`'s deploy branch (visible on GitHub).
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker computes `X-Hub-Signature` with their own known `webhook_secret` for `attacker-org` and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner => "attacker-org"`, verifies successfully [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` with no ownership check [4](#0-3) , finding the victim's commit and creating a forged `success` status on it, potentially unblocking continuous deployment for `victim-org/prod-app`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
