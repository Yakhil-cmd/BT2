### Title
Down-then-up rounding chain in `liquidate`'s remaining-debt check causes premature bad-debt socialization onto all suppliers - (File: `contracts/market/market.clar` / `contracts/market/v0-4-market.clar`)

### Summary
`liquidate`'s decision to trigger full bad-debt socialization (`no-collateral-left`) depends on `other-debt-repayable`/`remaining-debt-to-repay`, values obtained by chaining a down-rounded USD→token→scaled conversion and only rounding up at the very last step. This mirrors the audited `MagnetarHelper.getFractionForAmount` bug class: two logically-equivalent conversions (the "true" remaining value vs. the value used to gate a critical branch) use inconsistent rounding, so the gating check can be wrong. Here the miscalculation doesn't just affect the caller — it decides whether *all suppliers* of the debt-asset vault absorb socialized bad debt.

### Finding Description
In `liquidate`, once the requested debt/collateral pair is processed, the code checks whether the borrower has other collateral whose USD value could still repay the remaining debt: [1](#0-0) 

and again, after execution, using `other-coll-usd`/`other-debt-repayable`: [2](#0-1) 

Both computations chain: `div-bps-down` → `mul-div-down` (USD→tokens) → `mul-div-down` (tokens→scaled) → `mul-div-up` (scaled→tokens, final step only). Every intermediate conversion rounds the estimate of "value the other collateral could repay" **down**, and only the last step rounds up — the same "round up in one place, round down in another" pattern flagged in the referenced report. This asymmetry biases the final `other-debt-repayable` toward under-estimating how much of the remaining debt the borrower's other collateral can actually cover, making it spuriously reach `u0` in edge cases (small residual collateral, tight debt/price ratios) where the borrower in fact still holds sufficient value.

When `other-debt-repayable` (or `remaining-debt-to-repay`) resolves to `u0`, `no-collateral-left` becomes true: [3](#0-2) 

and the code forces socialization of the borrower's *entire remaining debt list* — not just the debt asset being liquidated — via `socialize-debt-asset`/`vault-socialize-debt`, which writes down the vault's liquidity index for that asset (`local-testing/contracts/vault/vault-*.clar`, `socialize` matches), directly reducing the redeemable value backing every zToken holder in that vault: [4](#0-3) 

### Impact Explanation
Victim: all depositors/suppliers holding the vault's zTokens for the socialized debt asset(s) (unprivileged principals with no relation to the liquidated borrower). Attacker: the liquidator (or any user triggering `liquidate` at the right moment) — an ordinary, unprivileged caller. Shared state: the vault's `total-borrowed`/liquidity index that backs all zToken share prices.

- Without the bug: `other-debt-repayable` correctly reflects the borrower's remaining collateral value; if genuinely sufficient, `no-collateral-left` stays false and no debt is written off — the borrower simply keeps an under-collateralized-but-covered position, later liquidatable normally.
- With the rounding-biased computation: `other-debt-repayable` can round to `0` even though real residual collateral value is nonzero, forcing `bad-debt-socialized = true` and writing down the vault index, socializing debt that should have remained with the borrower. This is a temporary/permanent freezing-and-loss of supplier funds (reduced redeemable value), matching the "socialization charged to all suppliers" impact class.

### Likelihood Explanation
This triggers only in edge cases at the margin of `no-collateral-left` — when a borrower has one other small collateral position whose USD value, after the down-rounded chain, computes to a repayable amount of exactly `0` token/scaled units due to truncation, while the un-rounded (or up-rounded) computation would be nonzero. This requires small residual balances/decimal-precision edge cases (more likely for low-decimal or low-price assets), so likelihood is low-to-medium and needs precise numeric conditions, but is fully triggerable by an ordinary liquidator without any privileged access.

### Recommendation
Make the "does other collateral cover remaining debt" check conservative in the correct direction for a socialization gate: round the **debt-repayable estimate up** (or equivalently, round the borrower's coverage down consistently) at every step of the chain (`div-bps-down`, `mul-div-down` USD→tokens, `mul-div-down` tokens→scaled, `mul-div-up` scaled→tokens) so the socialization branch is never taken while real repayable value remains nonzero — i.e., ensure the reported `other-debt-repayable`/`remaining-debt-to-repay` never under-reports the borrower's true residual coverage.

### Proof of Concept
1. Set up a borrower position with two collateral assets: the primary one being liquidated (fully or partially seized) and a small residual "other" collateral position whose USD value, when pushed through `div-bps-down` → `mul-div-down` (USD→debt tokens) → `mul-div-down` (tokens→scaled units), truncates to `0` scaled units, even though the true (un-truncated) value is nonzero (e.g., choose amounts just below the rounding boundary for the debt asset's `INDEX-PRECISION`/decimals).
2. Call `liquidate` against the primary collateral/debt pair so that `coll-removed` fully drains that asset (`coll-remaining` for the primary asset becomes 0) while the "other" collateral asset remains with the small residual balance above.
3. Because `other-scaled` truncates to `0` before the final `mul-div-up`, `other-debt-repayable` resolves to `0`, satisfying `no-collateral-left`.
4. Observe `bad-debt-socialized: true` in the emitted event and the vault's liquidity index for the debt asset written down via `vault-socialize-debt`, reducing the redeemable value of all zToken holders in that vault — despite the borrower's other collateral still holding real (non-zero) USD value that should have covered the remaining debt without socialization.
