This bug class (mismatched parameters producing an economically exploitable but "validly authenticated" outcome) has a concrete structural analog in this engine's webhook trust model: the field used to select/verify the cryptographic signature is not the same field the event handlers use to determine which `Stack`/`Repository`/`Commit` the event acts on.

### Title
Webhook signature verified against `repository.owner.login`, but handlers act on the unrelated `repository.full_name`/`sha` fields — cross-organization forgery of stack, commit-status and check-run events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the HMAC against using `repository_owner`, itself read from the unverified JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes for *that* organization's secret, the very same request body is handed unmodified to `Shipit::Webhooks.for_event(event)` handlers. Those handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`) select the target `Stack`/`Commit` using a *different* field of the same payload — `repository.full_name` (via `Handler#repository_name`) or a bare `sha` (in `StatusHandler`) — that is never cross-checked against `repository.owner.login`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (lines 59-62) is `params.dig('repository','owner','login') || params.dig('organization','login')`.

`lib/shipit/github_app.rb:76-83` shows `verify_webhook_signature` only checks that the HMAC of the raw bytes matches the secret configured for *that resolved organization* — it says nothing about whether the rest of the payload is self-consistent with that organization.

Handlers in `app/models/shipit/webhooks/handlers/handler.rb:32-38` resolve the actual object to mutate from a **different** payload key:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
`PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) uses this to call `stack.sync_github`. `StatusHandler#process` doesn't even consult `repository` at all — it matches purely on a global `sha` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), and `CheckSuiteHandler#process` matches on `head_sha`/`head_branch` scoped only by `stacks` derived from `repository.full_name` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`).

The binding that is broken: **organization authenticated (used to pick the webhook secret) ≠ repository/commit actually written (used by the handler to select the mutated record)**. Because `Shipit` supports multiple GitHub Apps/orgs with independent `webhook_secret`s in the same instance (see `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "multiple Github applications for different Github organizations"), an attacker who legitimately controls one configured organization's webhook secret (e.g., because they own/administer that GitHub App/org) can produce a request that:
1. sets `repository.owner.login` (or `organization.login`) to *their own* org, so `verify_signature` resolves and validates against their own known secret and passes, and
2. sets `repository.full_name` to an **arbitrary other tracked repository/stack**, or for `status` events supplies an arbitrary `sha` with no repository field at all.

Nothing in the controller or `Handler` re-derives or re-checks that `repository.full_name`'s owner equals `repository_owner`.

### Impact Explanation
With a validly-signed-but-mismatched payload, the attacker can, without any Shipit session, `ApiClient` token, or credentials belonging to the target organization/repository:
- Force `StatusHandler#process` to attach an arbitrary CI status (e.g. `state: "success"`) to any `Commit` in the system matching a chosen `sha`, across any stack/organization, since `Commit.where(sha:)` is completely unscoped by repository/org. This directly forges the green-CI signal Shipit's deploy-safety checks depend on (`release_status?`/`deployable?` logic elsewhere in `Stack`), which can enable an unauthorized deploy of a commit that never actually passed CI.
- Force `CheckSuiteHandler`/`PushHandler` to schedule check-run refreshes or GitHub resyncs on stacks belonging to organizations the attacker has no access to, i.e., cross-organization/cross-repository actions triggered under someone else's trust boundary.

This satisfies the "High" bar (escalation into authorization gating a deploy) and, in the CI-status-forgery case, plausibly the "Critical" bar (unauthorized deploy), since Shipit's deploy gating explicitly consults commit `Status`/`CheckRun` records that this path lets an outsider write.

### Likelihood Explanation
Exploitation requires only: (a) the Shipit instance is configured with more than one GitHub App/org (an explicitly documented, supported configuration — `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), and (b) the attacker legitimately controls one of those orgs' webhook secret (e.g., they administer their own GitHub App/org that is also configured on the same Shipit instance, a realistic scenario for shared/internal Shipit deployments serving multiple teams/orgs). No GitHub App private key, `ApiClient` token, or Shipit session is needed — only knowledge of a signature secret for *any one* configured organization. This is a directly reachable, unauthenticated-relative-to-the-victim-org HTTP endpoint (`/webhooks`).

### Recommendation
In `Handler#repository_name` / `Handler#stacks`, and in every handler that scopes by commit `sha` (`StatusHandler`), require that the payload's `repository.full_name`'s owner matches the organization that was actually used to verify the signature (`WebhooksController#repository_owner`), and reject (422) on mismatch. Pass the verified `repository_owner` (not just the raw payload) down to handlers so they can assert this binding explicitly, rather than re-deriving it from unverified fields, before performing any stack lookup or commit mutation.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` (attacker-administered, secret `S_A` known to attacker) and `OrgB` (victim, tracks stack for `OrgB/victim-repo`), per `test/dummy/config/secrets_double_github_app.yml`'s multi-org schema.
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<sha of a commit on OrgB/victim-repo that attacker wants marked green>",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` using their own known `S_A`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and `verify_webhook_signature` succeeds because the HMAC matches `S_A` — the body was never claimed to be about `OrgA`'s repository content in any way the signature covers beyond raw bytes.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — unscoped by organization — and calls `create_status_from_github!`, writing a forged "success" status onto the victim commit belonging to `OrgB`, an organization/repository the attacker has no legitimate relationship with.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
