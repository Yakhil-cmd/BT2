### Title
Cross-organization webhook forgery escalates into `Shipit.github_teams` authorization via unscoped `Team.find_or_create_by!(github_id:)` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook against whichever organization is named in the payload's `organization.login`/`repository.owner.login`, using that organization's own `webhook_secret`. `MembershipHandler#find_or_create_team!` then looks up the target `Team` purely by the numeric `github_id`, with no check that the authenticated organization matches the `organization` column on the matched `Team` row, allowing an attacker who controls a *second* organization already configured in Shipit's multi-org `secrets.github` to add themselves as a member of a `Team` belonging to a different, privileged organization.

### Finding Description
The broken binding: `organization_that_verified_signature (params.organization.login, authenticated via that org's webhook_secret in Shipit.github(organization: repository_owner))` **must equal** `team.organization (the organization column on the Team row mutated by find_or_create_team!)`, but this equality is never checked.

Path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . For a `membership` event, there is no `repository` key, so `repository_owner` is `params.organization.login` — fully attacker-controlled and equal to whatever org the attacker names.
- `Shipit.github(organization:)` resolves to a per-organization `GitHubApp` from `secrets.github` and raises `GithubOrganizationUnknown` if that organization isn't configured at all [3](#0-2) . So the attacker must control an organization that a Shipit operator has *already configured* in the multi-org `secrets.github` (i.e., has its own `webhook_secret`/App config) — this is the only real precondition, and it is independent of whether that org is listed in `Shipit.github_teams`.
- `GitHubApp#verify_webhook_signature` only HMACs against that specific org's `webhook_secret` [4](#0-3) , which the attacker legitimately possesses for their own configured org.
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`, matching on `github_id` alone; the `organization` assignment only happens in the `do |team| ... end` block that runs **only on creation**, not on match [5](#0-4) . If a `Team` row with that `github_id` already exists (e.g., a privileged team belonging to org `O_victim` that is a member of `Shipit.github_teams`), the existing row is returned unchanged, and `team.add_member(...)` inserts the attacker's own login as a member [6](#0-5) , [7](#0-6) .
- `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) , so becoming a member of that `Team` row (regardless of which org's webhook created the membership) grants full authorization.

None of the existing guards prevent this: `verify_signature` only proves "this payload was signed by *some* org's secret," not that it was signed by the org that owns the target `Team`; `find_or_create_team!` has no organization-scoped lookup (e.g., `find_or_create_by!(github_id:, organization:)`); `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not cross-org binding.

### Impact Explanation
An attacker who administers *any* second organization that a Shipit operator has configured in `secrets.github` (even one with no privileged teams) can forge a `membership` webhook naming a `team.id` that matches a `Team.github_id` belonging to a privileged organization listed in `Shipit.github_teams`, and add their own GitHub login as a member of that team. This flips `User#authorized?` to `true` for that attacker, granting full Shipit access (deploys, rollbacks, task execution) — an authorization-bypass escalation. The blast radius is any Shipit deployment configured with multiple GitHub organizations sharing one Shipit instance, where the attacker controls at least one of the non-privileged configured orgs; it is repeatable per team/user pair and does not require guessing secrets, only the numeric `team.id`, which is discoverable via prior legitimate traffic or is a small sequential integer.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-org `secrets.github` schema and at least two organizations onboarded, (2) the attacker controls the webhook/App configuration for one of those configured (but non-privileged) organizations, and (3) knowledge of the target `Team`'s numeric `github_id`. Precondition (2) is a real operational configuration in multi-tenant Shipit deployments (the engine explicitly supports `github_organizations`/`github_app_config` for multiple orgs). Given that, the attack costs a single signed HTTP POST with no other privileged secret. This is feasible in any such multi-org deployment.

### Recommendation
Scope the team lookup/creation to the authenticated organization, e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally assert in `MembershipHandler#process` that `team.organization == params.organization.login` before calling `add_member`/`members.delete`, raising/dropping the event otherwise so that a webhook signed by org A can never mutate a `Team` belonging to org B.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from a different configured organization cannot join a team belonging to another org" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 48 (say)
  attacker_org = 'attacker-org' # must be present in secrets.github with its own webhook_secret

  @request.headers['X-Github-Event'] = 'membership'
  # Signature is valid for attacker_org's own webhook_secret (attacker legitimately controls it)
  body = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker_login' }
  }.to_json

  assert_no_difference -> { victim_team.reload.members.count } do
    post :create, body:, as: :json
  end
  # Binding assertion: authenticated org (attacker_org) != victim_team.organization ('shopify')
  refute_equal attacker_org, victim_team.reload.organization
  refute victim_team.members.exists?(login: 'attacker_login')
end
```
Under current code, this test fails: `find_or_create_by!(github_id:)` matches `victim_team`, `add_member` runs, and `User.find_by(login: 'attacker_login').authorized?` becomes `true` once `victim_team.id` is in `Shipit.github_teams`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
