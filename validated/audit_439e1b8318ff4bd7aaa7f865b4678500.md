### Title
Webhook signature verification is scoped to `repository.owner.login`/`organization.login` while the acted-upon repository is resolved from a different field (`repository.full_name`), allowing cross-organization writes in multi-tenant configs - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (multiple GitHub Apps configured under `secrets.github`, each with its own `webhook_secret`, as documented in `config/secrets.development.shopify.yml`), the webhook controller selects which organization's secret to verify a payload's signature against using `repository.owner.login`/`organization.login`, but the handlers that actually act on the payload resolve the target `Repository`/`Stack` using the *separate* `repository.full_name` field. These two fields are not cryptographically bound together, so a payload can be crafted where they disagree.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify with based on `repository_owner`: [1](#0-0) [2](#0-1) 

That HMAC check is performed with the `webhook_secret` belonging to whatever org is named in the `repository.owner.login` (or `organization.login`) field: [3](#0-2) 

However, once the signature is validated, the dispatched handler (e.g. `PushHandler`) determines *which repository/stack to act on* using `payload.dig('repository', 'full_name')`, an entirely different JSON path that is not cross-checked against `repository.owner.login`: [4](#0-3) [5](#0-4) 

Both org and app configs are looked up per-organization from a single shared secrets file, one entry per tenant: [6](#0-5) 

The binding that should hold is: `organization authenticated by webhook_secret == organization owning the repository actually written to`. Because `repository.owner.login` (used to pick/verify the secret) and `repository.full_name` (used to pick the target Repository/Stack) come from the same untrusted, attacker-controlled JSON body and are never cross-validated against each other, an attacker who legitimately controls one tenant org's GitHub App (and therefore knows/can produce a valid signature for that org's `webhook_secret`) can set `repository.owner.login` to their own org (so the correct secret is selected and the HMAC passes) while setting `repository.full_name` to `"other-org/other-repo"` (a repository belonging to a different tenant configured on the same Shipit instance). The push handler will then look up and act on the victim repository's stacks and enqueue a `GithubSyncJob`/trigger syncing for a repo the attacker's org has no relationship to.

### Impact Explanation
This breaks the deployment-trust binding between "which org's signing key authenticated this request" and "which repository's state gets modified." In a shared/multi-tenant Shipit install, an attacker with control over their own org's webhook delivery (i.e., they can send arbitrary HTTP webhook requests signed with a secret they possess) can force sync/status-update behavior against another organization's repository records, i.e. cross-repository writes across trust boundaries that should not be reachable without that other organization's own webhook secret. This matches the "cross-repository writes" Critical impact class defined in scope.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured for multiple GitHub organizations (the documented multi-org `secrets.github` schema), and (2) the attacker controlling/administering one of those configured orgs' GitHub App/webhook secret (not privileged access to Shipit itself, not the victim org's secret, and not any Shipit session/API token). This is a realistic configuration supported and documented by the engine (`config/secrets.development.shopify.yml`), and no other credential (Shipit login, `ApiClient` token, GitHub App private key of the victim org) is required to attempt it — only a legitimately-obtained webhook secret for a different, unrelated tenant org on the same instance.

### Recommendation
Bind signature verification and repository resolution to the same trusted value: after selecting the GitHub App by `repository_owner` and verifying the HMAC, re-derive/validate that `repository.full_name` actually belongs to the same `repository_owner`/organization used for verification (e.g., assert `full_name.split('/').first.casecmp?(repository_owner)`) before dispatching to handlers, or have `Handler#repository_name`/`stacks` resolution take the already-verified organization as an explicit, separately-authenticated parameter rather than trusting an unrelated field from the same unverified-at-that-point JSON body.

### Proof of Concept
Conceptual request (not executed, no filesystem/terminal access available in this environment):
1. Shipit configured with two orgs in `secrets.github`: `attacker-org` (attacker controls the GitHub App and knows its `webhook_secret`) and `victim-org` (unrelated tenant, different repos).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha attacker controls or knows>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this exact raw body (they possess this secret legitimately).
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s GitHub App, and verifies successfully since the signature matches that secret: [1](#0-0) [3](#0-2) 
5. `PushHandler#process` (via `Handler#repository_name`/`stacks`) resolves the target using `full_name = "victim-org/victim-repo"`, an org the attacker does not control, and triggers `stack.sync_github(...)` against that repository's stacks: [4](#0-3) [5](#0-4) 

Note: I was unable to trace further downstream what `sync_github`/`GithubSyncJob` does to confirm the full extent of resulting side effects (e.g., whether it merely queries GitHub or triggers deploy-affecting state changes), due to index size limits on file coverage. A Devin session with full repository access would be needed to fully trace `Stack#sync_github` and `GithubSyncJob` to precisely bound the write impact.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
