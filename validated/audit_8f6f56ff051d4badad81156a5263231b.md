## Analysis

The Uniswap report's root cause is a security-critical numeric comparison performed against the wrong quantity/unit, silently breaking an invariant that was supposed to gate behavior. I found a directly analogous pattern in the Sui native bridge's **V2 rate-limiter bypass** feature, which is a bespoke addition layered on top of the standard bridge code in this repository (see `bridge/SUI_NATIVE_BRIDGE_PRIMER.md` "Limiter Bypass V2 Update").

### Title
Unit mismatch (seconds vs. milliseconds) between EVM `timestampSeconds` and Move `timestamp_ms` collapses the 48h bridge rate-limiter bypass window, allowing near-instant, unlimited-value token claims on Sui - (File: `crates/sui-framework/packages/bridge/sources/bridge.move`, `bridge/evm/contracts/utils/BridgeUtilsV2.sol`)

### Summary
Sui's bridge V2 flow lets a claim on Sui bypass `TransferLimiter::check_and_record_sending_transfer` entirely once the deposit message is deemed "mature" (>48h old), on the theory that any exploit would already have been detected by then [1](#0-0) . The maturity check on the Move side is:
```
bypass_limiter = clock.timestamp_ms() > timestamp + 48 * 3600000;
``` [2](#0-1) 
which expects `timestamp` to be **milliseconds**, matching `TokenTransferPayloadV2::timestamp_ms` [3](#0-2) .

For deposits originating on Ethereum, that timestamp value is produced by `bridgeERC20V2`/`bridgeETHV2`, which emit `block.timestamp` — standard EVM **seconds** — as the payload timestamp field, itself named `timestampSeconds`:
```solidity
emit TokensDepositedV2(..., recipientAddress, block.timestamp);
``` [4](#0-3) [5](#0-4) 

Symmetrically, the EVM-side maturity check for the opposite direction (Sui→Eth) explicitly treats the payload as milliseconds and *divides by 1000* before comparing in seconds:
```solidity
_transferTokensFromVault(..., tokenTransferPayload.timestampMs / 1000);
...
return currentTimestamp > messageTimestamp + 48 * 3600; // seconds
``` [6](#0-5) [7](#0-6) 

There is no equivalent `/1000` (or `*1000`) unit-normalization step visible on the Move side when the Ethereum-sourced timestamp (seconds) is packed into the `timestamp_ms`-typed field consumed by `bridge.move`'s bypass comparison.

### Finding Description
`create_token_bridge_message_v2`/`extract_token_bridge_payload_v2` and `claim_token_internal` treat the wire timestamp field uniformly as **milliseconds** for the bypass comparison against `clock.timestamp_ms()` [8](#0-7) . However, the value that actually originates from an Ethereum deposit (`bridgeERC20V2`/`bridgeETHV2`) is `block.timestamp`, i.e., **seconds**, and is explicitly documented on the EVM side as `timestampSeconds` [9](#0-8) . If the off-chain relaying/signing pipeline (BridgeOrchestrator/BridgeActionExecutor, per the primer's flow diagram [10](#0-9) ) forwards this seconds-denominated value directly into the Move message's `timestamp_ms` slot without multiplying by 1000, then for any real ETH→Sui deposit:

- `timestamp` (interpreted as ms) ≈ current Unix time in **seconds** (~1.7×10⁹)
- `clock.timestamp_ms()` ≈ current Unix time in **milliseconds** (~1.7×10¹²)
- `timestamp + 48*3600000` ≈ 1.7×10⁹ + 1.728×10⁸ ≈ 1.87×10⁹, which is trivially smaller than `clock.timestamp_ms()` (~1.7×10¹²)

so `bypass_limiter` evaluates to `true` essentially immediately after deposit, not after 48 hours. This is the exact bug-class match to the report: a security check is evaluated against a variable/quantity that does not represent what the guard logic assumes it represents (wrong unit instead of wrong variable), silently defeating the intended gating condition.

### Impact Explanation
If this mismatch is present in the live relayer, `check_and_record_sending_transfer` — the only per-route/per-hour USD-denominated cap on the amount of bridged assets that can be minted/released on Sui — would be bypassed for virtually all V2 claims from Ethereum, regardless of freshness. Because `TransferLimiter` exists specifically to bound worst-case loss while an incident is triaged [11](#0-10) , its unconditional bypass converts every committee-approved claim into an unconstrained mint call (`inner.treasury.mint<T>(amount, ctx)` [12](#0-11) ). This directly matches the Critical bar for "state corruption from unauthorized...package upgrade" style bridge issues in the allowed-impact gate: bridge message/limit forgery that enables illegitimate mint beyond the governed cap.

### Likelihood Explanation
Medium-to-uncertain. I confirmed both ends of the unit inconsistency in the Solidity/Move source in this repository, and confirmed the Move-side test helpers (`FORTY_EIGHT_HOURS_MS`, `bridge_to_sui_v2`) always operate in consistent milliseconds, so the Move unit tests would not catch a bad conversion happening in the off-chain relayer/signing service. I was **not able to locate and verify the exact Rust glue code** (in `crates/sui-bridge`) that reads the EVM `TokensDepositedV2.timestampSeconds` log field and packs it into the signed Move `BridgeMessage` payload consumed by `create_token_bridge_message_v2`; due to index size limits I could not confirm within available tool calls whether that code performs the required `*1000` conversion. This is the critical missing piece to fully confirm exploitability versus a merely confusingly-named-but-correctly-converted field.

### Recommendation
1. Audit the Rust relayer code path that constructs the V2 Move bridge message from the Ethereum `TokensDepositedV2` event and confirm/enforce that `timestampSeconds` is multiplied by 1000 before being embedded as `timestamp_ms` in `create_token_bridge_message_v2`.
2. Add an explicit unit assertion/sanity bound in Move (`assert!(timestamp_ms > SOME_MIN_PLAUSIBLE_MS)` or cross-check against `clock.timestamp_ms()` at signing time) so a seconds/milliseconds mixup cannot silently zero out the 48h maturity window.
3. Add an integration test that feeds a raw Ethereum-style `block.timestamp` (seconds) end-to-end through the real relayer serialization code (not just the Move-only test harness) to `claim_token_internal`, and assert `bypass_limiter == false` immediately after deposit.

### Proof of Concept
Not independently reproducible from this analysis because the concrete off-chain construction code was not locatable in the available index; the arithmetic PoC is the unit-mismatch computation shown above (`clock.timestamp_ms() > timestamp + 48*3600000` becomes true almost immediately once `timestamp` is populated with a seconds-scale integer instead of a milliseconds-scale one). A concrete PoC would need to be built with a background Devin session that reads `crates/sui-bridge/src/sui_client.rs`/`sui_transaction_builder.rs` (both flagged in the earlier grep as touching `create_token_bridge_message_v2`) to confirm or refute the conversion, and if missing, exercise `bridge_tests.move`'s V2 harness with a raw seconds-scale timestamp fed through simulated relayer serialization.

## Limiter Bypass V2 Update

Commits after `fe3abe3a8c (VM Limiter Bypass)` introduce a timestamp-aware "V2" bridge flow. The **purpose of the limiter is to give the system time to respond to bugs outside the VM layer**. Fresh transfers (< 48h old) are rate-limited to allow time for issue detection, while mature transfers (> 48h old) can bypass the limiter since any problems would have been identified by then.

**Key principle:** Fresh messages (< 48h) → APPLY limiter; Mature messages (> 48h) → BYPASS limiter.
