### Title
Cross-organization Team hijack via `Team.find_or_create_by!(github_id:)` in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that the request was signed with the `webhook_secret` belonging to whatever organization is named in the payload's `organization.login`/`repository.owner.login` field; it does not tie that organization to any particular `Team` row. `MembershipHandler#find_or_create_team!` looks up teams solely by the GitHub-global `github_id`, so an attacker who owns any GitHub organization with its own valid Shipit App/webhook_secret can send a signed `membership` webhook claiming a `team.id` that collides with a `Team` already persisted for a different organization, and get themselves inserted as a member of that other org's team.

### Finding Description
The claimed binding is: `organization.login` (the org whose `webhook_secret` verified the request) `==` `Team#organization` for the `Team` row identified by `github_id: params.team.id`.

Tracing the code:
- `WebhooksController#verify_signature` resolves `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then verifies the signature using `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . This only checks "was this payload signed by the App/secret installed for `org_b`" — it says nothing about which `Team` row the payload is allowed to mutate.
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; ... }` [3](#0-2) . `find_or_create_by!` first performs a `find_by(github_id: ...)`; if a row already exists (created for `org_a`), the block — which is the only place `organization` is set — never runs, and the pre-existing `org_a`-owned `Team` object is returned unchanged.
- `MembershipHandler#process` then unconditionally calls `team.add_member(member)` for `action == 'added'` [4](#0-3) , and `Team#add_member` appends to `members` (i.e. inserts a `Shipit::Membership` row) with no re-check of `organization` [5](#0-4) .
- Nowhere in this path is `team.organization` compared against `params.organization.login`. The `ExplicitParameters` schema for `MembershipHandler` only validates types/presence, not cross-org consistency [6](#0-5) .

Exploit flow: attacker administers `org_b`, installs a Shipit GitHub App there (legitimately obtaining `org_b`'s real `webhook_secret`). They discover/guess a GitHub team numeric ID `T` that Shipit already persisted as `Team(github_id: T, organization: 'org_a')` (e.g. one of the teams listed in `Shipit.github_teams`, which are fetched and cached as `Team` rows via `Shipit.github_teams` → `Team.find_or_create_by_handle` [7](#0-6) ). They POST `/webhooks` with `X-Github-Event: membership`, body `{action:'added', team:{id:T,...}, organization:{login:'org_b'}, member:{login:'attacker'}}`, signed with `org_b`'s webhook_secret. `verify_signature` passes because it only checks the `org_b` secret against the `org_b`-claimed payload. `find_or_create_team!` finds the existing `org_a` `Team` by `github_id` and returns it as-is. `team.add_member(User.find_or_create_by_login!('attacker'))` inserts a `Membership` linking the attacker's `User` to `org_a`'s `Team`.

This matches the test scaffolding already present: `test/controllers/webhooks_controller_test.rb`'s `":membership creates the mentioned team on the fly"` and `"can append an user membership"` tests [8](#0-7)  show the exact same code path (`team.id` reused against `shipit_teams(:shopify_developers)`, `organization.login` fixed to `'shopify'`) with no assertion that `organization.login` must match the found team's stored `organization`.

### Impact Explanation
`User#authorized?` is `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) . If the hijacked `Team` row is one of the teams in `Shipit.github_teams` (the org's authorization allowlist), the attacker becomes `authorized?` and passes `force_github_authentication` [10](#0-9) , gaining full access to the Shipit instance (stacks, deploys, API client creation) without ever being a real member of `org_a`'s GitHub team and without GitHub ever reporting this membership. This is a genuine cross-tenant authorization bypass — Critical severity per the rubric ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Preconditions: (1) Shipit configured for at least one org (`org_a`) whose team is in `Shipit.github_teams`/persisted as a `Team`; (2) attacker independently controls a separate GitHub org (`org_b`) with its own Shipit App installation, giving them a legitimate `webhook_secret` for `org_b` — this is explicitly granted by the threat model; (3) attacker must learn/guess the numeric GitHub team `id` for the target `Team` (team IDs are global, sequential integers on GitHub and are often discoverable via GitHub's API/UI for any team the attacker can view, or via prior legitimate webhook traffic/logs). Cost is low: a single crafted, self-signed HTTP POST, fully repeatable and requiring no live GitHub interaction to demonstrate.

### Recommendation
Scope the team lookup/creation by both `github_id` and the verified organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally assert (or hard-fail) if an existing `Team` with that `github_id` has a different `organization` than the one whose webhook secret verified the request — treat that as a conflict rather than silently reusing the row.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest` or `ActionController::TestCase` style consistent with `test/controllers/webhooks_controller_test.rb`):
```ruby
test "membership webhook from org_b cannot hijack a team belonging to org_a" do
  org_a_team = shipit_teams(:shopify_developers) # organization == 'shopify' (org_a)
  assert_equal 'shopify', org_a_team.organization

  Shipit.github(organization: 'org_b').stubs(:verify_webhook_signature).returns(true)

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: org_a_team.github_id, name: org_a_team.name, slug: org_a_team.slug, url: org_a_team.api_url },
    organization: { login: 'org_b' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'org_b' } }
  }.to_json

  post :create, body: payload, as: :json
  assert_response :ok

  org_a_team.reload
  assert_equal 'shopify', org_a_team.organization, "organization must remain org_a"
  attacker = User.find_by(login: 'attacker')
  refute Membership.exists?(team: org_a_team, user: attacker),
    "attacker should not be added to org_a's team via an org_b-signed webhook"
end
```
Before the fix, this assertion fails: `Membership.exists?(team: org_a_team, user: attacker)` is `true` and, if `org_a_team` is listed in `Shipit.github_teams`, `attacker.authorized?` also becomes `true`, confirming the escalation.
