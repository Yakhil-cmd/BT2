### Title
Webhook signature check keys off `repository.owner.login`/`organization.login` while every event handler dispatches on `repository.full_name` from the same untrusted payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the closest in-scope analog to H-31's root cause: two different fields inside the *same* attacker-influenced structure are used for two different trust decisions, and the field that authorizes the action does not match the field the code actually acts on.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to check the HMAC signature against based on `repository_owner`, which is read straight from the untrusted JSON body: [1](#0-0) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Crucially, `verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: [3](#0-2) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Shipit explicitly supports multiple GitHub organizations configured side by side, each with its own (optional) `webhook_secret`: [4](#0-3) 

Once `verify_signature` passes, the controller dispatches the *entire raw payload* to every handler for the event: [5](#0-4) 

But every handler resolves which `Stack`/`Repository` to act on using a **different** field of that same payload — `repository.full_name` — not `repository.owner.login`: [6](#0-5) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because signature verification is keyed on `repository.owner.login`/`organization.login` while the actual write target is resolved from `repository.full_name`, an attacker only needs one organization in the multi-tenant Shipit config to have `webhook_secret` unset (which is the documented default/placeholder value, see `webhook_secret: # nil` in the setup template) to make `verify_webhook_signature` return `true` for any payload claiming that org as the owner — while freely setting `repository.full_name` to point at a completely different, secret-protected organization's repository/stack. This breaks the intended binding "organization that authenticated == repository that is written."

### Impact Explanation
An unprivileged external attacker who can reach the public `/webhooks` endpoint (no session, no `ApiClient` token, no GitHub App private key required) can forge events such as `push`, `status`, `check_suite`, `pull_request`, or `merge_status` against a stack belonging to an organization they have no relationship with, as long as any other configured org in the same Shipit instance has no webhook secret set. This can be used to:
- Trigger `GithubSyncJob`/`stack.sync_github` via the forged `push` handler, causing the target stack's commit history/state to be resynced on attacker-chosen input [7](#0-6) .
- Forge commit statuses / check runs that gate `commit.deployable?`, which the deploys API relies on to allow deployment (`param_error!(:require_ci, ...) if params.require_ci && !commit.deployable?`), potentially unlocking an unauthorized deploy path [8](#0-7) .
- Manipulate merge/pull-request handlers gating the merge queue.

This matches the High/Critical bar ("escalation ... unauthenticated ... or an unauthorized deploy, rollback or merge") because it crosses the trust boundary between organizations without any credential belonging to the victim organization.

### Likelihood Explanation
Requires only that the Shipit deployment configures more than one GitHub organization and that at least one has no `webhook_secret` set — a configuration explicitly shown as the default/example value in the shipped setup templates. No attacker-side secret, session, or repository access is needed; only network reachability to the public webhook endpoint.

### Recommendation
Verify the signature using the secret belonging to the organization/repository that the payload's `repository.full_name` actually resolves to (i.e., derive the signing org from the resolved `Repository`/`Stack` record, not from an attacker-suppliable `repository.owner.login`/`organization.login` field), and require a non-blank `webhook_secret` for every configured organization (fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `org-a` (no `webhook_secret`) and `org-b` (has a stack and a `webhook_secret`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/private-repo" }
}
```
3. `verify_signature` resolves `repository_owner` to `org-a`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header.
4. `PushHandler#process` resolves the target via `payload.dig('repository','full_name')` = `org-b/private-repo`, and calls `stack.sync_github` on `org-b`'s stack — a forged webhook accepted for an organization the attacker never authenticated against.

      verified = github_app.verify_webhook_signature(

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
