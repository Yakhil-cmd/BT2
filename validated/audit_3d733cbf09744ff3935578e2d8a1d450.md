### Title
`StatusHandler#process` matches commits by SHA only, ignoring `repository.full_name`, allowing a validly-signed webhook for one repository to inject a `success` status onto another stack's commit — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Every other webhook handler in this engine (e.g. `PushHandler`) scopes itself to the repository named in the payload via `Handler#stacks` → `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. `StatusHandler#process` does not use this scoping at all; it runs `Commit.where(sha: params.sha)` against the whole `commits` table and writes a `Status` for every matching row via `commit.create_status_from_github!`, using each matched commit's own `stack_id`. `verify_signature` in `WebhooksController` only authenticates that the payload came from the GitHub organization named in `repository.owner.login` — it never checks that the specific `repository.full_name` in the payload is the repository tracked by the stack whose commit gets updated.

### Finding Description
Binding claimed broken: `{context strings that satisfy Stack B's required checks} == {context strings Shipit will accept as satisfying Stack B's checks regardless of which repository's webhook signed the request}`.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and calls `verify_webhook_signature`, an HMAC check keyed **only by organization**, not by repository. [1](#0-0) 
- `Handler#stacks`, used correctly by `PushHandler`, resolves the target stacks strictly via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. [2](#0-1) [3](#0-2) 
- `StatusHandler#process` does not use `stacks`/`repository_name` at all; it looks up commits purely by `sha`, across every stack in the database: [4](#0-3) 
- `Commit#create_status_from_github!` then creates a `Status` scoped to `stack_id` (the pre-existing commit's own stack, i.e. Stack B), using attacker-supplied `state`/`context`/`description` values verbatim. [5](#0-4) 
- `Commit` rows are only unique per `(stack_id, sha)` (migration `20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally unique by `sha`, so the same SHA can legitimately exist under multiple stacks (e.g., a fork, mirror, or monorepo relationship tracked as a separate Shipit stack).
- `Status#blocking?`/`#required?` (`app/models/shipit/status/common.rb:46-52`) and `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) key purely off `context` string membership in `stack.required_statuses`/`blocking_statuses` — they trust whatever `Status` row exists for that commit, with no re-validation of provenance.

Exploit flow: Stack B (org "acme", repo "acme/repo-b") already has a `Commit` row for SHA `X` and a `shipit.yml`/UI-configured required context `ci/important`. Any GitHub App installed at the organization level typically signs webhook deliveries for **every repository under that installation** with the same organization-scoped `webhook_secret`. An attacker who has ordinary (non-Shipit, non-maintainer) write/status access to *any other repository* in the same org/installation — e.g. a fork of repo-b sharing ancestor commit `X`, or an unrelated sandbox repo whose history happens to include commit `X` — can create a GitHub commit status via the standard Statuses API on their own repository with `sha=X`, `context=ci/important`, `state=success`. GitHub signs and delivers this event to Shipit exactly as it would any legitimate status event; `verify_signature` passes because it only checks the organization, not `repository.full_name`. `StatusHandler#process` then finds Stack B's `Commit` row with `sha=X` and writes a `success` `Status` scoped to Stack B, satisfying `required?`/clearing `blocking?` for that context — with no requirement that the event actually originated from `acme/repo-b`.

Why guards fail: `verify_signature`/`GitHubApp#verify_webhook_signature` authenticate the organization-level channel, not the specific repository; `ExplicitParameters` schema in `StatusHandler` validates types only, not repository identity; there is no `drop_unhandled_event`/`stacks` scoping equivalent applied to this handler, unlike `PushHandler`.

### Impact Explanation
A repository the attacker does not maintain and did not authenticate for (Stack B) gets a `Status` record written that satisfies its `required_statuses`/`blocking_statuses`, directly enabling `Commit#blocked?` to return `false` and `Commit#deployable?`/merge-queue checks to pass, i.e. an unauthorized deploy/merge gate bypass on a victim stack — this is a "payload for one repository mutating another's stack/commit" per the Critical impact category. Blast radius: any stack whose organization shares a GitHub App/webhook installation with a repository the attacker can influence, and repeatable for every SHA the attacker can get a status delivered for.

### Likelihood Explanation
Requires: (1) Stack B and the attacker-influenced repository share the same Shipit-configured GitHub organization (common in single-org or shared-installation deployments — this repo's own `github_app.rb`/`docs/setup.md` show config is keyed per-organization, one secret covering potentially many repos); (2) a SHA collision opportunity between the attacker's repo and Stack B's tracked history (trivially achievable via forking, since forks share identical commit objects for unmodified ancestor commits) or another repo the attacker can set statuses on that happens to reference the same SHA (e.g., cherry-pick/rebase-preserved commit, submodule, monorepo mirror). No Shipit secrets, sessions, or maintainer rights are needed — only ordinary GitHub write/status permissions on an unrelated in-org repository. This makes the attack feasible without any privileged credential, though it does require the organization-sharing precondition to hold.

### Recommendation
In `StatusHandler#process` (and any other handler that queries `Commit`/`Status` by attributes alone), scope the lookup by the repository named in the payload, mirroring `Handler#stacks`: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, restrict to that repository's stacks, and only update `Commit` rows belonging to those stacks (e.g. `commit.stack.github_repo_name == repository_name`) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook for repo A cannot satisfy repo B's required check via shared SHA" do
  stack_b = shipit_stacks(:shipit) # repo "shopify/shipit-engine"
  stack_b.cached_deploy_spec = DeploySpec.new('ci' => { 'require' => ['ci/important'] })
  stack_b.save!

  shared_sha = 'deadbeef' * 5
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)

  # Attacker's unrelated repo (repo A) shares the org's GitHub App installation
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/important',
    'repository' => { 'full_name' => 'shopify/attacker-repo', 'owner' => { 'login' => 'shopify' } }
  }

  # Binding under test:
  # required_context_that_satisfies_B = 'ci/important' (from B's shipit.yml)
  # context_accepted_for_any_signed_repo_in_org = 'ci/important' (from status_handler, no repo check)
  refute_predicate commit_b.reload, :blocked? rescue nil # baseline: missing required status -> blocked/pending

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit_b.reload
  assert_equal 'success', commit_b.statuses.last.state
  assert_equal 'ci/important', commit_b.statuses.last.context
  refute_predicate commit_b, :blocked? # FAILS today: false negative, bypass confirmed
end
```
This demonstrates that a status event whose `repository.full_name` does not match Stack B's tracked repository still writes a satisfying `Status` onto Stack B's commit, flipping `blocked?` to `false` for the victim stack.
