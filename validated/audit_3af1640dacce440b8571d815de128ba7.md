### Title
CCMenu API endpoint ignores an ApiClient's stack scope, allowing a stack-scoped token to read the deploy status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts which `Stack` an `ApiClient` may act on by scoping lookups through `stacks`, which filters to `current_api_client.stack_id` when the client is stack-scoped. [1](#0-0)  `Shipit::Api::CCMenuController` bypasses this scoping entirely by overriding `stack` to query the global `Stack` model directly instead of the scoped `stacks` relation, while still only checking the generic `read:stack` permission string. [2](#0-1) [3](#0-2) 

### Finding Description
The trust binding that should hold is: `current_api_client.stack_id == stack.id` whenever a stack-scoped `ApiClient` is used to touch a stack, exactly as enforced in the base controller for every other stack-scoped endpoint (`StacksController`, `DeploysController`, `TasksController`, etc., which all inherit `BaseController#stack`). [1](#0-0) 

`CCMenuController` breaks this binding. It only requires the permission string `read:stack` to be present on the client (`require_permission :read, :stack`), and then resolves the target stack with `Stack.from_param!(params[:stack_id])` — a direct, unscoped lookup against the whole `Stack` table, not through `stacks`. [2](#0-1) [3](#0-2)  `ApiClient#check_permissions!` only checks whether the permission string is present in the client's `permissions` array; it never compares the requested stack to `stack_id`. [4](#0-3) 

This mirrors the Wormhole/Spoke bug class: the code that authorizes the operation (`check_permissions!` verifying `read:stack`) covers a different scope than the code that actually acts (`Stack.from_param!(params[:stack_id])`, an attacker-controlled route parameter). The permission check "signs off" on the operation class but not on which specific stack object is touched, so the `stack_id` parameter is effectively a field "acted on but never covered" by the authorization check — analogous to the dust amount that bypasses the Wormhole bridge's trim-then-forward accounting.

Any `ApiClient` scoped to one stack (e.g., the `here_come_the_walrus` fixture, `stack: shipit`, `permissions: [read:stack]`, or a token minted by `CCMenuUrlController` for a specific stack) can be replayed against `GET /api/stacks/:owner/:repo/:environment/ccmenu?token=...` for a *different* `stack_id` path segment and will successfully render that other stack's latest deploy/rollback status. [5](#0-4) [6](#0-5) 

### Impact Explanation
This is an authorization-scope escape: a token that is only supposed to authorize reads for one stack can be used to read state (last deploy/rollback status, running state, timestamps) of any other stack in the installation, including stacks the client's creator has no legitimate access to. This matches the "High" impact category of unauthenticated/out-of-scope read of stack state and deploy output via escalation beyond the credential's intended authorization boundary.

### Likelihood Explanation
Exploitation requires only a previously-issued, narrowly-scoped `ApiClient` token (the exact kind that `CCMenuUrlController` mints on behalf of ordinary users for CI-dashboard integrations) and knowledge/guessing of another stack's `owner/repo/environment` path — no elevated privileges, no signature bypass, and no interaction with GitHub credentials are needed. Because CCMenu tokens are routinely embedded in third-party CI status tools and URLs, they are more likely to leak or be shared than primary session credentials, increasing the practical likelihood of misuse.

### Recommendation
Make `CCMenuController#stack` resolve through the same scoped `stacks` relation used by `BaseController`, e.g. `stacks.from_param!(params[:stack_id])`, so that `current_api_client.stack_id` (when set) is enforced identically to every other API endpoint.

### Proof of Concept
1. As an authorized user of Stack A, call `CCMenuUrlController#fetch` for Stack A; this creates/reuses an `ApiClient` with `permissions: ['read:stack']` (in the general case, also apply this to any explicitly stack-scoped `ApiClient`, e.g. one created via `/api_clients` with `stack: A`) and returns a CCMenu URL containing `token=<A-scoped-token>`. [7](#0-6) 
2. Take that `token` and issue `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu?token=<A-scoped-token>` targeting unrelated Stack B.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (`ApiClient.authenticate`), `require_permission :read, :stack` passes because the token has `read:stack`, and `stack` resolves Stack B directly via `Stack.from_param!` — bypassing any `stack_id` restriction. [8](#0-7) [9](#0-8) 
4. The response renders Stack B's latest deploy/rollback status, which the token was never authorized to access.
