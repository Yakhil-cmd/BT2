### Title
Unvalidated, permanently-immutable `pool_creator` address can permanently freeze creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` lets any unprivileged `payer` set the pool's `creator` account to an arbitrary, unchecked `Pubkey` that is never required to sign and is never validated to be a controllable address. That value is written once into `PoolState.pool_creator` and, like the Keystore `rootHash` bug, can never be updated afterward, permanently bricking creator‑fee collection if the wrong address is supplied.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as an `UncheckedAccount<'info>` with no signer, ownership, or address‑derivation constraint [1](#0-0) . `initialize_with_permission` then writes it directly into `PoolState` via `pool_state.initialize(...)`, using `ctx.accounts.creator.key()` as `pool_creator` [2](#0-1) . Inside `PoolState::initialize`, `pool_creator` is set once and there is no subsequent function in `PoolState` (or any in-scope instruction) that lets it be corrected [3](#0-2) .

Both fee-withdrawal paths are hard-gated on this immutable value:
- `CollectCreatorFee` requires `creator` to be a `Signer` whose key equals `pool_state.load()?.pool_creator` [4](#0-3) .
- `CollectCreatorFeePermissionless` similarly constrains the recipient `creator` account to `pool_state.load()?.pool_creator` [5](#0-4) .

If `pool_creator` is set (accidentally, via a buggy pool-creation script, a copy/paste error, or a burn-style address with no known private key) to a pubkey nobody controls, `CollectCreatorFee` can never be signed by the correct party, and `CollectCreatorFeePermissionless` will simply keep routing accumulated `creator_fees_token_0/1` into an ATA owned by an address nobody can ever spend from. This is functionally the same bug class as the Keystore `rootHash` issue: an unvalidated value is committed once at creation time with no recovery mechanism, permanently bricking a core account function (fee withdrawal) for the life of the pool.

### Impact Explanation
`creator_fees_token_0` / `creator_fees_token_1` are subtracted from the swappable vault balance in `vault_amount_without_fee` [6](#0-5) , meaning these tokens are real, segregated pool assets. Once `pool_creator` is unreachable, this fee balance grows indefinitely and can never be withdrawn by anyone — a permanent freeze of pool funds. This qualifies as medium risk because it does not enable theft of other users' principal, but it does permanently lock real token balances tied to the pool.

### Likelihood Explanation
Reaching this state requires only a single call to `initialize_with_permission` with an attacker-chosen (or accidentally wrong) `creator` account — no elevated privileges beyond holding a valid `permission` PDA are needed, and the instruction is otherwise a normal, expected pool-creation flow. A tooling bug, front-end bug, or fat-fingered address is sufficient to trigger it, making the likelihood non-trivial for any deployment relying on scripted/automated pool creation.

### Recommendation
Require `creator` to either be a `Signer` in `InitializeWithPermission`, or otherwise cryptographically prove control of the address at creation time, so a wrong non-signing address cannot be committed. Additionally, consider adding an authorized/allowed update path (e.g., permissioned by the current `pool_creator` if reachable, or by the current `AmmConfig` fund owner as a fallback) that can rotate `pool_creator` if the original value is proven unreachable, analogous to the recovery mechanism recommended for the Keystore `rootHash` issue.

### Proof of Concept
1. Caller (any `payer` holding a valid `permission` PDA) invokes `initialize_with_permission`, passing an arbitrary `creator` pubkey they do not control (e.g., a random keypair's public key with no known private key, or a mistyped address) [7](#0-6) .
2. `pool_state.initialize(...)` permanently stores this pubkey as `pool_creator` [2](#0-1) .
3. Swaps accrue `creator_fees_token_0` / `creator_fees_token_1` in `PoolState` over time.
4. `collect_creator_fee` cannot be called because no one can produce a valid signature for `creator` == `pool_creator` [4](#0-3) .
5. `collect_creator_fee_permissionless` can technically be invoked by anyone, but the tokens land in an ATA owned by the unreachable `pool_creator` address, permanently inaccessible [8](#0-7) .
6. The accumulated creator-fee balance is permanently frozen inside the pool vault with no code path to recover it.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
