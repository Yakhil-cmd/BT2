Untrusted investigate-stage candidate fields embedded unescaped into refute-stage prompt enable adjudication-flipping prompt injection - (File: plugins/security-guidance/hooks/llm.py)

### Summary
`agentic_review`'s investigate stage produces `candidates` whose `vulnerableCode`/`explanation`/`category` fields are populated by an LLM reading attacker-supplied repository content, and the code explicitly acknowledges this is untrusted: the iter2 exclusion path defines a local `_scrub()` helper specifically to neutralize instruction-injection before re-embedding candidate text into a later prompt [1](#0-0) . That same defensive posture is not evidently applied when candidates are serialized for the refute stage, since `_scrub` is defined as a function-local closure scoped only to the iter2 block and is not reused elsewhere in the file [2](#0-1) .

### Finding Description
`candidates` is built directly from the investigate-stage structured output (`inv.get("findings")`), which is generated by an agent with `Read`/`Grep`/`Glob` tools over the attacker's own repository checkout [3](#0-2) [4](#0-3) . Because the investigate LLM is instructed to "quote the exact line(s)" and provide explanations sourced from repo content, an attacker can craft repository text designed to be echoed verbatim into a finding's `vulnerableCode`/`explanation` field. The code comment at the iter2 exclusion path states explicitly: "Pass-1 outputs are derived from the untrusted diff, so treat them as data when embedding into pass-2's prompt" [5](#0-4) , and implements `_scrub()` to collapse whitespace, truncate to 120 chars, and HTML-entity-escape `&`, `<`, `>` before interpolating candidate fields into `iter2_prompt` [6](#0-5) .
