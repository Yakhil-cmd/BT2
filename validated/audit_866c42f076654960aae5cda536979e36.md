## Title
Missing recursion-depth guard in AA formula evaluation allows stack-consumption/DoS during oscript execution - (File: formula/evaluation.js)

### Summary
`rust-miniscript`'s CVE-2024-44073 stems from a Miniscript AST that is parsed/processed recursively without tracking tree depth, letting an attacker craft a deeply nested script that exhausts the call stack. Ocore's AA/oscript formula engine has the same architectural weakness: the *validation* path (`formula/validation.js`) was hardened with an explicit depth counter, but the *evaluation* path (`formula/evaluation.js`), which actually executes formulas at every AA trigger, never adopted the same guard.

### Finding Description
`formula/validation.js`'s `evaluate()` function explicitly tracks recursion depth and rejects formulas whose AST exceeds 100 levels of nesting: [1](#0-0) 

This guard, however, is conditionally gated behind an mci upgrade (`constants.pemCurvesFixMci`) for backward compatibility with formulas that were already validated (and potentially deployed as AA definitions) before this fix was introduced: [2](#0-1) 

In contrast, `formula/evaluation.js`'s `evaluate()` — the function that actually walks the AST and executes the AA/oscript formula every time an AA is triggered, or a formula-based address/asset condition is authenticated — contains **no depth tracking at all**. It only interrupts the JS call stack every 100 total node visits via `setImmediate`, based on a flat `count` counter, not on nesting depth: [3](#0-2) 

The `count % 100` interruption only fires periodically for a "flat" sequence of evaluate() calls; it does not bound the depth of a single, synchronously nested recursive chain (e.g. deeply nested arrays/objects/expressions such as `[[[[...1...]]]]`, `if(1){if(1){...}}`, or nested `+`/`max()` expressions), because sub-expressions are evaluated by direct nested calls inside the same synchronous callback chain rather than always deferring through `setImmediate`. This is corroborated by the project's own regression tests, which construct 2000-deep nested arrays, dictionaries, `max()` calls and `if` statements specifically to probe this class of bug: [4](#0-3) 

Because `formula/evaluation.js` (unlike `formula/validation.js`) has no analogous `depth > 100` cutoff, any AA definition or formula-based address/asset definition whose formula was accepted under the pre-fix validation rules (mci < `pemCurvesFixMci`), or any code path that reaches `exports.evaluate` without first re-validating depth, can drive the evaluator into effectively unbounded native recursion, mirroring the exact bug class described in the Miniscript advisory: recursive processing of an attacker-supplied tree without properly tracking/limiting its depth.

### Impact Explanation
A stack-overflow/crash in `formula/evaluation.js` during AA trigger processing is not merely a crash of an isolated request — because AA execution and formula-based address/asset authentication happen synchronously as part of unit/DAG validation (`aa_validation.js`, `definition.js`'s `'formula'` case calling `formulaParser.validate`, and the actual authentifier/trigger execution path calling `exports.evaluate`), an uncaught `RangeError: Maximum call stack size exceeded` (or an engine crash) during consensus-critical evaluation can:
- crash/abort a full node process while it is validating a unit or executing an AA response, denying it the ability to process further units (network unable to confirm new units for that node), or
- cause divergent behavior between nodes if the crash is not deterministic across engines/versions, leading to disagreement on unit/AA validity.

Given that any unprivileged user can post a trigger unit to an AA, define an address/asset with a `formula` condition, or send private/AA payloads that end up being run through `exports.evaluate`, this is reachable by a single unprivileged unit poster or trigger sender — matching the required threat model.

### Likelihood Explanation
Likelihood is constrained by the fact that `formula/validation.js` now enforces the 100-level depth cap for all newly-validated formulas post-`pemCurvesFixMci`, so freshly authored AA definitions/formula conditions are pre-filtered. However:
- The compatibility carve-out (`mci >= constants.pemCurvesFixMci || getMinRetrievableMci() >= constants.pemCurvesFixMci`) means that formulas defined before that upgrade point are validated *without* the depth check and can still be executed today via `formula/evaluation.js`, which has zero depth protection.
- Even for newly-validated formulas, the modulo-100 `setImmediate` interruption in `evaluation.js` is not equivalent to a strict per-branch depth counter; deeply nested but "cheap" (low `count_ops`/complexity) constructs can still build a long synchronous call chain before the interruption triggers, since the interruption is based on a global op-count, not on current recursion depth.

### Recommendation
Add the same explicit depth-tracking guard used in `formula/validation.js` (the `depth`/`orig_cb`/`cb` wrapper introduced with `pemCurvesFixMci`) to `formula/evaluation.js`'s `evaluate()` function, unconditionally (not gated behind an mci check, since evaluation happens live and must be safe regardless of when the underlying formula was originally validated). This closes the gap between validation-time and execution-time recursion limits and prevents unbounded native recursion during AA/oscript execution.

### Proof of Concept
1. Construct (or locate, for a pre-`pemCurvesFixMci` AA) a formula/oscript AST with several thousand levels of nesting, e.g. an oscript formula string such as `${'['.repeat(N)}1${']'.repeat(N)}` or `${'max('.repeat(N)}1${')'.repeat(N)}` with `N` large enough to exceed V8's default stack (the project's own tests already use `N=2000` to probe exactly this in `test/formula.test.js:6415-6462`).
2. Ensure the formula is accepted by `formula/validation.js` — trivially true for AAs defined before the `pemCurvesFixMci` upgrade (depth check inactive), or achievable for new formulas by structuring nesting such that recursion inside `evaluation.js`'s per-op handling (rather than the counted top-level `evaluate` chain) grows deeper than validation's 100-level cap allows for, if such a bypass exists in a specific op handler.
3. Submit a trigger unit to the AA (or a payment referencing the formula-based address/asset condition) so that `formula/evaluation.js`'s `exports.evaluate` is invoked on the malicious formula during real unit/AA validation.
4. Observe that, absent a depth guard in `evaluation.js`, the recursive `evaluate()` calls can exceed the JS engine's call stack, crashing the node process handling validation — a concrete denial-of-service against AA/unit validation.
