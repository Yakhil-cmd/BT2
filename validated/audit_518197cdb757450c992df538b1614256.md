**Analysis:** The premise is incorrect. Simulation only bypasses signature verification, not business logic checks like `ENO_CAPABILITIES` in `managed_coin::mint` [1](#0-0) . `AptosSimulationVM::create_vm_and_simulate_signed_transaction` asserts the transaction has an *invalid* signature as a precondition, and then runs the exact same `execute_user_transaction` path used for real execution against the actual signer derived from `txn.sender()` [2](#0-1) . Since the Move-level capability check (`ENO_CAPABILITIES`) is enforced inside the entry function body — not in prologue/authenticator logic — it runs identically whether simulated or executed for real, so an unauthorized `mint` call aborts with the same `VMStatus`/abort code in both paths.

The only thing simulation intentionally diverges on is signature verification (explicitly required to be invalid, precisely to prevent tricking a relayer into broadcasting a "successful" simulation that was actually signed and could be replayed) [3](#0-2) . The `TRANSACTION_SIMULATION_ENHANCEMENT` feature flag only affects skipping authentication-key checks for secondary signers/fee payer in the prologue when the corresponding key hash is `None`, not entry-function-level capability asserts [4](#0-3) .

There is no code path where simulation would report `mint<CoinType>` as successful for an unauthorized signer while real execution aborts — both converge on the same abort. This does not meet the admission-impact gate (no unauthorized execution/state transition, no replay/sequence/domain break, no authenticator confusion); it is at most a theoretical "wasted gas via forced execution" concern that isn't even realizable here, and is explicitly out of scope as generic/non-impactful.
