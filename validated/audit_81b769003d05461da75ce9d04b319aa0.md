### Title
Webhook signature verification is bound to `repository.owner.login`, but handlers act on the independently-attacker-supplied `repository.full_name` — cross-tenant/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`), but every event `Handler` resolves the repository/stack it actually mutates from a *different, independently attacker-controlled* field: `repository.full_name`. Because these two fields are never checked for consistency, an attacker who can produce a validly-signed payload for *any* org configured in this Shipit instance (e.g. their own org in a multi-tenant `secrets.yml`, per `docs/setup.md` "Using Multiple Github Applications") can set `repository.full_name` to point at a *different* org/repo hosted on the same instance, causing Shipit to sync, status-update, or otherwise mutate a repository/stack it was never authenticated for.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) 
using `repository_owner`: [2](#0-1) 
i.e. `Shipit.github(organization: repository_owner)`, which selects the per-organization `webhook_secret` from `config/secrets.yml` (multi-org schema documented in `docs/setup.md:182-209` and `test/dummy/config/secrets_double_github_app.yml`). The signature is verified with `GitHubApp#verify_webhook_signature`, using that org's secret only: [3](#0-2) 

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw JSON payload* to handlers. Every handler derives the repository/stack it will act on from `repository.full_name`, not from `repository.owner.login`: [4](#0-3) 
`Repository.from_github_repo_name` simply splits `owner/name` from that string and looks up the `Repository` record — with no cross-check against the organization that the signature was verified for: [5](#0-4) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the write) are two independent JSON fields inside the same HMAC-covered payload, an attacker who can legitimately sign a payload for organization A (e.g. because they administer their own GitHub App/org installed on this shared Shipit instance, or because org A has no `webhook_secret` configured — `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank, see line 77) can still set `repository.full_name` to `"orgB/some-repo"` for a victim organization B that is *also* configured on the same instance. The signature check only ever consults org A's secret; nothing ties the verified signer to the `full_name` actually processed by the handler.

This is the direct analog of the reported bug class: the binding "organization authenticated == repository written" is broken — the code authenticates one field (`repository.owner.login`/`organization.login`) but acts on another (`repository.full_name`) without ever asserting they match.

### Impact Explanation
Exploiting this lets an attacker who controls (or has a validly-signed/unsigned webhook path for) one organization on a shared Shipit deployment trigger writes against another organization's `Stack`/`Repository`/`Commit` data without ever being authenticated for that target repository:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha:)` on stacks resolved via the forged `full_name`, forcing (or spoofing) a sync against a repository the attacker is not authorized for. [6](#0-5) 
- `StatusHandler#process` writes fabricated CI status onto commits of the victim repository (`commit.create_status_from_github!`), which can subsequently gate/unblock deploy eligibility in the victim's pipeline. [7](#0-6) 

This is a cross-repository/cross-tenant write achieved purely by breaking the auth↔action binding, matching the Critical impact bucket ("cross-repository writes").

### Likelihood Explanation
This requires a multi-organization Shipit deployment (explicitly documented and supported, `docs/setup.md:182-209`) where the attacker legitimately administers one of the configured GitHub Apps/organizations (so they can produce a validly-signed webhook for their own org), or where any configured org has `webhook_secret` left blank (explicitly allowed — `webhook_secret: # nil` — in both the single-org and multi-org example configs, and treated as "always verified" by `verify_webhook_signature`). Given Shipit's documented support for hosting multiple independent organizations behind one instance, this is a realistic deployment-trust boundary that the current code does not enforce.

### Recommendation
After `verify_signature` resolves the authenticated organization, propagate it into event dispatch and have `Handler` (or `Repository.from_github_repo_name`) assert that the `repository.owner.login` derived from `full_name` matches the organization the signature was actually verified against, rejecting (422) any payload where they diverge. Equivalently, look up the repository using the pre-authenticated organization rather than trusting `repository.full_name` verbatim.

### Proof of Concept
1. Shipit is deployed with the multi-org schema (`config/secrets.yml` containing `github.OrgA` and `github.OrgB`, mirroring `test/dummy/config/secrets_double_github_app.yml`), each with its own GitHub App/webhook secret; `OrgB/victim-repo` is a stack tracked by Shipit.
2. Attacker administers `OrgA`'s GitHub App (or `OrgA` has `webhook_secret` unset) and can therefore produce a webhook request whose `X-Hub-Signature` is valid for `OrgA` (or valid unconditionally, per `lib/shipit/github_app.rb:76-78`).
3. Attacker crafts a `push` payload body with `repository.owner.login = "OrgA"` (so `WebhooksController#repository_owner` resolves to `OrgA` and signature check passes against `OrgA`'s config) but `repository.full_name = "OrgB/victim-repo"` and `ref`/`after` pointing at attacker-chosen values.
4. `WebhooksController#create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack — a write against `OrgB`'s repository the attacker was never authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
