### Title
Uncaught `throw Error("no src_coin")` DoS in private indivisible-asset payment validation - (File: validation.js)

### Summary
`validatePaymentInputsAndOutputs` in `validation.js` assumes that for a "transfer" input of a private, fixed-denomination asset, `objValidationState.src_coin` (and its nested fields) has already been populated by the caller. When this precondition is not met, instead of returning a validation error through the normal callback-based error channel (as every other check in this function does), the code executes a bare `throw Error(...)`. This is the same bug class as the TensorFlow `CHECK`-fail: a code path assumes an internal invariant about the shape/presence of attacker-influenced data without validating it, and instead of a graceful, recoverable error, an unconditional native assertion/exception is used, crashing the process.

### Finding Description
In `validation.js`, inside the `"transfer"` case of the input-processing loop:
```javascript
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    var src_coin = objValidationState.src_coin;
    if (!src_coin.src_output)
        throw Error("no src_output");
    if (!isPositiveInteger(src_coin.denomination))
        throw Error("no denomination in src coin");
    if (!isPositiveInteger(src_coin.amount))
        throw Error("no src coin amount");
``` [1](#0-0) 

This code path is reached from `validatePayment` → `validatePaymentInputsAndOutputs`, which is the same generic payment validator used for both on-chain public payments and private payment chains. [2](#0-1) 

For private, fixed-denomination assets, `objValidationState.src_coin` is expected to be pre-populated by `indivisible_asset.js`'s `validatePrivatePayment`, but only in the branch that handles a `"transfer"` type input:
```javascript
arrFuncs.push(validateSourceOutput);
objValidationState.src_coin = {
    src_output: src_output,
    denomination: payload.denomination,
    amount: prev_hidden_output.amount
};
``` [3](#0-2) 

Nothing in `validatePaymentInputsAndOutputs` re-verifies that `input.type` in the *revealed* payment payload actually matches the type that `indivisible_asset.js` used to decide whether to set `src_coin`. `validatePrivatePayment` builds a `partially_revealed_payload` via `_.cloneDeep(payload)` and hands it to `validation.validatePayment` without re-checking `input.type` against the outer `payload.inputs[0].type` that was already consumed to select the `"transfer"` vs `"issue"` branch:
```javascript
arrFuncs.push(function(cb){
    var partially_revealed_payload = _.cloneDeep(payload);
    var our_output = partially_revealed_payload.outputs[objPrivateElement.output_index];
    our_output.address = objPrivateElement.output.address;
    our_output.blinding = objPrivateElement.output.blinding;
    validation.validatePayment(conn, partially_revealed_payload, objPrivateElement.message_index, objPartialUnit, objValidationState, cb);
});
``` [4](#0-3) 

Because `payload` (and hence `partially_revealed_payload.inputs[0]`) is fully attacker-controlled data delivered over the wire as a `private_payment`/`private_payments` message (handled in `network.js`'s `handleOnlinePrivatePayment` and `wallet.js`'s `handlePrivatePaymentChains`), an attacker who is the sender/counterparty of a private payment can construct a chain element whose `input.type` differs between what is used to branch in `validatePrivatePayment` and what ultimately reaches `validatePaymentInputsAndOutputs`'s `"transfer"` case without `src_coin` set — reaching the `throw Error("no src_coin")` (or the sibling throws for `src_output`/`denomination`/`amount`) with no surrounding try/catch on this synchronous call path. [5](#0-4) [6](#0-5) 

Unlike essentially every other invalid-input case in `validatePaymentInputsAndOutputs`/`validatePrivatePayment`, which return an error string through `cb`/`callbacks.ifError` (e.g. `return cb("...")` throughout the surrounding code) — the equivalent of TensorFlow returning an `InvalidArgument` status — this particular invariant violation is enforced with a hard `throw`, i.e. the equivalent of a `CHECK` failure. `validation.validate`'s public entry points do not wrap this call in a try/catch, so an uncaught exception propagates up through the event loop and crashes the node process, exactly the "CHECK-fail causes denial of service" pattern in the report.

### Impact Explanation
A crafted private-payment message (indivisible/fixed-denomination private asset, e.g. blackbytes-style assets) sent to a counterparty (wallet or hub) can trigger an uncaught exception during validation of the payment chain, crashing the receiving node process. This is a concrete denial-of-service against any full node or wallet that processes private payment chains from a counterparty, matching the "network unable to confirm new units"/node-crash class of impact this scan accepts (crash of the receiving node, not merely a caught validation error).

### Likelihood Explanation
Reachable by any private-payment counterparty without needing to compromise the network — private payment chains are attacker-authored JSON structures sent directly to a peer's wallet/hub connection (`private_payment`/`private_payments` device/network messages). The only requirement is constructing a payload whose input `type` diverges between the branch-selection point in `indivisible_asset.js` and the fields consumed later in `validation.js`'s `"transfer"` branch, which is plausible because the payload is cloned and reused rather than being fully re-validated against the exact same conditions before the second call.

### Recommendation
Replace all four `throw Error(...)` invariant checks in the private, fixed-denomination `"transfer"` branch of `validatePaymentInputsAndOutputs` (`validation.js` lines ~2416–2424) with normal `return cb("...")` error returns, exactly like every other validation failure in this function. Additionally, harden `indivisible_asset.js`'s `validatePrivatePayment` to re-validate that the `input.type` seen when preparing `objValidationState.src_coin` is consistent with the `input.type` actually present in the payload passed to `validation.validatePayment`, so that these two code paths cannot diverge.

### Proof of Concept
Conceptual reproduction (requires wiring into an attacker-controlled `private_payment` message to a victim wallet/hub):
1. Define a private, fixed-denomination asset (`is_private: true`, `fixed_denominations: true`).
2. Construct a private payment chain element whose outer input is processed as `"issue"` by `indivisible_asset.js`'s `validatePrivatePayment` (so `objValidationState.src_coin` is never set), while the `partially_revealed_payload.inputs[0].type` that reaches `validation.validatePayment` is `"transfer"` (or missing/falsy so it defaults to `"transfer"` in `validatePaymentInputsAndOutputs`), e.g. by manipulating fields that are not covered by the pre-hash equality checks in `validatePrivatePayment` before `_.cloneDeep`.
3. Send this chain as a `private_payment`/`private_payments` message to a peer.
4. Peer's `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` → `indivisibleAsset.validatePrivatePayment` → `validation.validatePayment` → `validatePaymentInputsAndOutputs` reaches the `"transfer"` branch with `objValidationState.src_coin` undefined, executing `throw Error("no src_coin")` uncaught, crashing the process.

Note: exact crafting of the divergent `input.type` requires further experimentation against the live code (not confirmable purely from static reading); the specific line-level unguarded `throw` inside a normally callback-driven validator is confirmed and is the root cause supporting this finding.
