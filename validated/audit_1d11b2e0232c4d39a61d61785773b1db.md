## Analysis

The invariant to test is: **`current_api_client.stack_id == stack.id`** must hold (or `current_api_client.stack_id` must be nil, meaning unscoped) before any stack-scoped resource is returned to a token holder.

**On `GET /api/stacks` (index) itself, this invariant holds.** `Api::StacksController#index` builds its result set from the `stacks` helper defined in `Api::BaseController`: [1](#0-0) [2](#0-1) 

`stacks` restricts the relation to `Stack.where(id: current_api_client.stack_id)` when the token is stack-scoped, so `GET /api/stacks` for a token scoped to stack A can never return stack B. The test suite confirms this: `"an api client scoped to a stack will only see that one stack"` [3](#0-2) , backed by the `here_come_the_walrus` fixture scoped to stack `shipit` [4](#0-3) .

**The bug described in the exploit idea is real, but it lives on a different route — `GET /api/stacks/*stack_id/ccmenu` (`Api::CCMenuController#show`), not on `GET /api/stacks` (index).** `Api::CCMenuController` resolves its `stack` directly against the unscoped `Stack` model instead of the token-scoped `stacks` relation: [5](#0-4) 

`require_permission :read, :stack` only checks that the token has the `read:stack` permission string [6](#0-5)  — it never checks that the *specific* `stack_id` in the URL matches `current_api_client.stack_id`. So a token scoped to stack A with `read:stack` (e.g. `here_come_the_walrus`) can hit `GET /api/stacks/<owner>/<repo>/<env>/ccmenu` for **any other stack B** and receive its latest deploy/rollback status via `stack.deploys_and_rollbacks.last`. The existing `CCMenuControllerTest` only exercises the unscoped `spy` client, so this cross-stack disclosure is untested [7](#0-6) .

### Title
Stack-scoped API token can read any stack's build status via `GET /api/stacks/*stack_id/ccmenu` — (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`GET /api/stacks` (index) correctly restricts results to a token's scoped stack via the `stacks` helper, so the invariant holds there. However, the sibling route `GET /api/stacks/*stack_id/ccmenu`, served by `Api::CCMenuController#show`, resolves the target stack with `Stack.from_param!(params[:stack_id])` — bypassing the token-scoped `stacks` relation entirely — so a token scoped to one stack can read the CI/deploy status of any other stack.

### Finding Description
The broken binding is: `current_api_client.stack_id == stack.id` (or the token being unscoped) must hold for any stack read to succeed. `Api::BaseController#stack` enforces this via `stacks.from_param!(params[:stack_id])` [8](#0-7) , and controllers like `DeploysController`, `TasksController`, `OutputsController`, `LocksController`, `CommitsController`, `RollbacksController` and `ReleaseStatusesController` all inherit and use this scoped `stack`. `Api::CCMenuController` overrides `stack` and calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model [9](#0-8) , so the equality is never checked. `require_permission :read, :stack` [10](#0-9)  only calls `ApiClient#check_permissions!`, which checks the permission string, not the target instance [6](#0-5) .

Attacker request: authenticate with a token scoped to stack A (`read:stack` permission, e.g. via basic auth or `?token=`), then request `GET /api/stacks/<other-owner>/<other-repo>/<other-env>/ccmenu`. `CCMenuController#authenticate_api_client` accepts `params[:token]` directly [11](#0-10) , `require_permission!` passes because the token has `read:stack`, and `stack` returns the unrelated stack B's record, exposing its last deploy/rollback status via the rendered CCMenu XML.

### Impact Explanation
The attacker (holder of any stack-scoped ccmenu-capable token) can enumerate/disclose deploy status ("Success"/"Failure", last build label/time, web URL) for any stack in the Shipit instance, not just the one their token is scoped to. This is a cross-tenant disclosure of deploy/build state, matching the "High — unauthenticated/unauthorized read of stack state or deploy output" category, though the attacker must already hold a valid (even minimally scoped) ccmenu token — it is not achievable by a fully anonymous internet user.

### Likelihood Explanation
Requires possession of any valid `ApiClient` token with `read:stack` permission (even one legitimately scoped to a single stack, such as tokens created by `CCMenuUrlController#client` for ordinary users [12](#0-11) ). Given the rules state the attacker holds no `ApiClient` token, this bug does not satisfy the "unprivileged attacker" precondition defined for this audit — it requires an already-issued, legitimately-scoped Shipit API credential to exploit against other stacks.

### Recommendation
Change `Api::CCMenuController#stack` to use the token-scoped `stacks` relation, matching `Api::BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
minitest (`test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "a stack-scoped token cannot read a ccmenu for a different stack" do
  scoped_client = ApiClient.create!(creator: @user, name: 'Scoped', stack: @stack, permissions: %w[read:stack])
  other_stack = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')

  request.headers['Authorization'] = nil
  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

  # Binding under test: current_api_client.stack_id == stack.id (@stack.id) must hold, or the request must be rejected.
  assert_not_equal scoped_client.stack_id, other_stack.id
  assert_response :not_found # currently fails: returns :ok with other_stack's data
end
```
