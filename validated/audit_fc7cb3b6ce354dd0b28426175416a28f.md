### Title
Stale Signed Price/Order Replay in AA Order-Matching Pattern Due to Missing Freshness Check on `is_valid_signed_package` Orders - (File: test/samples/order_book_exchange.oscript)

### Summary
Ocore's `is_valid_signed_package()` oscript function and the `signed_message.js` validator only prove that a signed message (e.g., a price/order) was authentically signed by an address and, optionally, that it was created no earlier than a given `last_ball_unit` reference point — they enforce no upper bound on staleness (no expiry field, no monotonically increasing price/order counter). The bundled reference AA `test/samples/order_book_exchange.oscript`, which demonstrates the canonical pattern for building a decentralized order book / price-oracle-driven exchange on top of `is_valid_signed_package`, explicitly omits any freshness check (`// to do check expiry`, line 36), reproducing exactly the bug class described in the external report: a validly signed price/order can be replayed and matched at any time after signing, regardless of how stale the embedded price has become.

### Finding Description
The order-execution branch of the AA (`test/samples/order_book_exchange.oscript:27-65`) accepts two counterparty orders (`trigger.data.order1`, `trigger.data.order2`), each a `signed_package` containing a `price` field chosen by the signer at signing time [1](#0-0) . Before checking `is_valid_signed_package`, the code computes deduplication IDs and checks `executed_` flags, but the only comment addressing staleness is `// to do check expiry` — no expiry/freshness logic is actually implemented [2](#0-1) .

`is_valid_signed_package` ultimately relies on `signed_message.validateSignedMessage`, which validates the signature and, if `last_ball_unit` is present, binds the message to the definition/state as of that unit's MCI [3](#0-2) . Nothing in this validation logic imposes any maximum age or requires the referenced `last_ball_unit` to be "recent" relative to current MC — as long as the unit is a valid stable unit on the DAG, the signed package (and the price frozen inside it by the signer) remains perpetually valid [4](#0-3) . This mirrors the StakingKo bug precisely: the message hash/signature carries a price with no invalidation counter, so any previously issued signature remains acceptable indefinitely (here, effectively forever, since ocore's framework doesn't even provide an expiry timestamp field for this use case, unlike StakingKo's `_expriedTime`).

Consequently, a counterparty (or the original signer acting adversarially) can hold on to an old signed order and submit it to the AA trigger whenever the embedded price becomes favorable relative to current market conditions, executing a trade at a stale price against an unsuspecting counterparty's order.

### Impact Explanation
This directly causes AA fund loss for a counterparty: because the order-matching logic performs no freshness/expiry check on the `price` embedded in the signed order, an attacker can wait until the true market price of the traded asset diverges significantly from the price recorded in an old signed order and then submit that stale order to be matched against the counterparty's currently posted balance, extracting value from the AA's `var[$sell_key]`/`var[$buy_key]` balances at an off-market rate. Since the AA moves real, previously-deposited on-chain asset/byte balances (`var['balance_'+address+'_'+asset]`) between users based on this price, this is concrete unauthorized value transfer / fund loss for the disadvantaged counterparty, matching the "AA fund loss" impact bar. This is Medium severity, consistent with the original report's rating, because exploitation requires favorable price movement within the (unbounded) validity window of a signed order, not an instantly guaranteed profit.

### Likelihood Explanation
Likelihood is moderate: the AA is a reference sample intended to be reused/adapted by dApp developers building order-book exchanges on ocore, and the missing check is explicitly flagged as a TODO in the shipped code, meaning developers who copy this pattern (as sample/template AAs commonly are) inherit the vulnerability directly. Any two-sided order matching where one party's counterparty offer is signed off-chain and can be submitted to the AA at an arbitrary later time is naturally exposed to this class of stale-price exploitation, especially in volatile markets, exactly as described in the original StakingKo report.

### Recommendation
Add an explicit freshness/expiry mechanism to signed orders and to the generic `is_valid_signed_package`/`signed_message` pattern used for oracle-like price data:
- Include an `expiry_ts` or `expiry_mci` field inside the signed message payload and validate `trigger.data.orderN.signed_message.expiry_ts > timestamp` (or MCI equivalent) before matching, removing the `// to do check expiry` TODO in `test/samples/order_book_exchange.oscript`.
- Alternatively/additionally, incorporate a monotonically increasing nonce/sequence number per signer address, tracked in AA state (`var['order_seq_'||address]`), and reject any signed order whose sequence number is not strictly greater than the last one accepted from that signer, so that a signer's updated (newer) order supersedes and invalidates older signed orders.
- Document this requirement prominently in the `is_valid_signed_package` documentation/samples so that AA developers building oracle- or order-driven AAs do not omit freshness validation, since `signed_message.js` itself does not and cannot enforce application-level staleness semantics.

### Proof of Concept
1. Alice signs an order (`order1`) at time T0 offering to sell asset X at price P0 (favorable to her at the time), using `signMessage`/`is_valid_signed_package` conventions, with `last_ball_unit` pointing to a then-current stable unit.
2. Time passes; the market price of asset X moves substantially away from P0 (e.g., X becomes worth much more).
3. Bob, holding a copy of Alice's still-validly-signed `order1` (e.g., obtained during an earlier failed/partial negotiation, or replayed from a public mempool/history), posts a trigger unit with `trigger.data.order1 = <Alice's old signed order>` and `trigger.data.order2 = <Bob's new order priced to exploit the stale rate>`.
4. The AA's `if` condition in `test/samples/order_book_exchange.oscript:27-65` validates `is_valid_signed_package(trigger.data.order1, $order1.address)` successfully (signature checks out, `last_ball_unit` is still a valid historical reference), and since no expiry check exists, the trade executes at Alice's stale price P0, transferring value from Alice's AA balance to Bob's at an off-market rate [5](#0-4) .

Note: I could not find any expiry/nonce enforcement anywhere in `signed_message.js` or in the `is_valid_signed_package` formula implementation (`formula/evaluation.js`), confirming that any staleness protection must be implemented entirely at the application/oscript level and is absent from the shipped reference sample.
