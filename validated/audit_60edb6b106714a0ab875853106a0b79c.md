### Title
Accrual-overflow freeze: RAY-valued market totals exceed `i128` before the index ceiling, permanently freezing withdraw/repay/liquidate — (File: contracts/pool/src/interest.rs)

### Summary
The MySQL CVE is a crash/complete-DOS class bug. The XOXNO Lending analog is an arithmetic-overflow crash in interest accrual: when the RAY-denominated value of a market's scaled debt or supply overflows `i128`, `accrue_step` panics with `GenericError::MathOverflow`. Because every market mutation runs `interest::global_sync` before mutating (`contracts/pool/src/interest.rs:20-33`), the panic propagates into every verb — supply, withdraw, repay, borrow, seize, recapitalize — freezing the market and all user funds held against it. Crucially, the cliff is reachable through the permissionless controller entrypoint `update_indexes`, and the protocol's own regression test demonstrates the freeze end-to-end.

### Finding Description
`Cache::load` on any market op triggers `global_sync`, which loops `accrue_chunk` → `common::rates::accrue_step`, computing new indexes and revenue shares from `borrowed`/`supplied` RAY totals (`contracts/pool/src/interest.rs:20-53`). Per `docs/reference/formulas.md:421-437`, "Accrued position values and market totals must independently fit the RAY domain; valid caps and bounded indexes do not guarantee that future accrual fits. Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first." The `borrow_index` cap (`MAX_BORROW_INDEX_RAY`, 10^9 × RAY) never engages before the value-overflow panic because `scaled_to_original`-style value conversion inside accrual overflows first.

The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-362`) proves the end state: `update_indexes` returns `MATH_OVERFLOW`, `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, and both `try_withdraw_raw` and `try_repay` subsequently revert with the same `MATH_OVERFLOW` — the market is permanently frozen.

### Impact Explanation
Once accrued market totals cross the `i128` RAY-value ceiling, every state-changing path on that market reverts: suppliers cannot withdraw (`withdraw` accrues first via `Cache::load` → `global_sync`), borrowers cannot repay, liquidators cannot liquidate, and `clean_bad_debt`/`recapitalize` also accrue. This is permanent freezing of all supplier funds and unclaimed revenue in that market — an availability/insolvency-class impact matching the accepted categories (permanent freezing of funds; contract unable to operate).

### Likelihood Explanation
Reachability is real but conditional. An unprivileged attacker must bootstrap a very large market (the PoC uses ~10^27 raw units of an 18-decimal token — economically enormous but reachable on tokens with large supplies/low unit prices, or on low-decimal markets where the RAY-normalization factor `10^(27-d)` inflates totals). The attacker drives utilization high via `borrow`, then any address — including the attacker — can call the permissionless controller `update_indexes` (pool-side it is `#[only_owner]` but the controller exposes it openly, as listed in scope) each period until accrual overflows. No governance action, upgrade, or leaked key is required. Likelihood is Medium-low given the capital requirement and multi-year accrual horizon in the test (though cheaper on steeper rate curves / higher-decimal tokens); severity of consequence is permanent.

### Recommendation
Make accrual saturate rather than panic: when the next accrued value would exceed the representable RAY domain, clamp `borrow_index`/`supply_index` to the largest values that keep `borrowed × borrow_index` and `supplied × supply_index` within `i128`, or halt index growth at the cliff while still allowing `repay`/`withdraw`/`seize_positions` to proceed on stored indexes. Alternatively, cap per-market `supplied`/`borrowed` RAY totals at creation/supply time so `total × MAX_BORROW_INDEX_RAY` can never overflow — i.e., enforce the bound `docs/reference/formulas.md` documents as implicit, instead of relying on it.

### Proof of Concept
The repo contains the PoC: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`.

```rust
// setup: 18-decimal market at XLM curve, caps lifted
let principal = BILLION * 10i128.pow(18);          // ~1e27 raw units supplied
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // 98% utilization
// permissionless poke: update_indexes each simulated year
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// => MATH_OVERFLOW, borrow_index < MAX_BORROW_INDEX_RAY
// market frozen:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),  errors::MATH_OVERFLOW);
```

Attacker path, permissionless throughout: `supply` huge principal → `borrow` to ~98% utilization → repeatedly call `update_indexes` until `accrue_chunk` panics in `accrue_step` on `MathOverflow`. From that ledger onward, all withdraw/repay/liquidate calls on the market revert, permanently locking every supplier's funds.

Note: the docs describe this as an "arithmetic limit, not a deployment proof," which could be argued a documented bound; however the freeze outcome (no exit path, index cap never engages) is an unstated consequence, not an ADR choice, so it warrants reporting.
