### Title
Unsanitized PR label names become process environment variable keys reaching `PTY.spawn`, allowing simultaneous `PATH`/`BUNDLE_GEMFILE`/`RUBYLIB` injection - (File: `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`LabelCapturingHandler#capture_labels` persists the raw, attacker-supplied GitHub label names verbatim into `PullRequest#labels` with no allowlist or denylist check. `ReviewStack#env` turns every one of those names into an uppercased environment-variable key, which flows through `TaskCommands#env` into `Command#unbundled_env` and ultimately `PTY.spawn`, with the label-derived hash able to reach and override interpreter/loader-relevant keys such as `PATH`, `BUNDLE_GEMFILE`, and `RUBYLIB` at once.

### Finding Description
The broken binding: the set of column values persisted into `PullRequest#labels` should be disjoint from `{PATH, BUNDLE_GEMFILE, RUBYLIB, LD_PRELOAD, ...}` (interpreter/loader-controlling names), but no code enforces `PullRequest#labels ∩ reserved_env_names == ∅`.

Code path:
1. `LabelCapturingHandler`'s `params` schema only validates that each label's `name` is a `String` — no content restriction: `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:29-31`.
2. `#capture_labels` writes the array unsanitized: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` at `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`, gated only by `labeled_active_stack?` (`stack.present? && !stack.archived?`) — no ownership/authorization check beyond that, and no relation to `Shipit.github_teams` or repository maintainers.
3. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) unconditionally merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the stack env, with no allowlist filtering (`EnvironmentVariables#permit`, defined at `lib/shipit/environment_variables.rb:13-18`, is never invoked on this data).
4. `TaskCommands#env` merges `@stack.env` early in the chain, before `deploy_spec.machine_env` and `@task.env` (`lib/shipit/task_commands.rb:33-48`), so label-derived keys persist unless a later merge step happens to redefine the same key.
5. `Command#unbundled_env` merges `@env.stringify_keys` **last**, after `BASE_ENV` and after the explicitly constructed `'PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` (`lib/shipit/command.rb:103-105`), so a label named `PATH` silently overwrites Shipit's carefully constructed `PATH`, and labels named `BUNDLE_GEMFILE`/`RUBYLIB` are freely injected as new keys into the exact hash passed to `PTY.spawn` at `lib/shipit/command.rb:92`.

Attacker action: an unprivileged GitHub user opens their own PR (creating/updating a review stack) and applies labels literally named `PATH`, `BUNDLE_GEMFILE`, and `RUBYLIB` in a single `labeled` webhook, satisfying only `labeled_active_stack?`.

Important caveat found during tracing: the *value* assigned to each of these keys is always the fixed literal string `"true"` (`label_name.upcase => "true"`), not attacker-controlled content. This means the attacker controls the **variable names** injected into the deploy host's process environment, but not arbitrary values. Practical exploitation therefore depends on how downstream tools treat a fixed `"true"` value:
- `PATH="true"` replaces Shipit's constructed PATH with an invalid path segment, breaking command resolution (`Errno::ENOENT` path in `Command#start`, `lib/shipit/command.rb:94-95`) rather than directly enabling arbitrary binary execution.
- `BUNDLE_GEMFILE="true"` causes Bundler to resolve a Gemfile at the relative path `true` under the task's working directory. Since Bundler's Gemfile is Ruby code evaluated via `instance_eval`, if the attacker also commits a file literally named `true` in their own PR branch, and a `bundle install`/`bundle exec` step from the deploy spec's dependency steps executes with the checked-out PR content as its working directory, that file would be evaluated as Ruby, achieving code execution on the deploy host. I was **not able to fully confirm** within the available iterations that the default `dependencies_steps!` always invoke `bundle` with `chdir` set to the attacker-controlled checkout directory in the review-stack path — this chain is plausible from the code I reviewed (`lib/shipit/task_commands.rb#install_dependencies`, `steps_directory`) but requires further verification of `DeploySpec#dependencies_steps!` defaults and exact `chdir` resolution.
- `RUBYLIB="true"` alone does not execute code; it only adds an invalid path to `$LOAD_PATH`, and would only matter if chained with a subsequent `require` of an attacker-named library — no such chain was confirmed in this codebase.

Existing guards checked and found insufficient: `ExplicitParameters` only validates type, not content, on `labels[].name`; `labeled_active_stack?` only checks the stack is present/not archived, not label content; `EnvironmentVariables#permit`'s allowlist exists but is never called on `stack.env`/`pull_request.labels` before merging into `Command`'s env; there is no `Repository`/`Stack` model validation restricting label-derived environment key names.

### Impact Explanation
This allows an unauthenticated-to-Shipit GitHub user (any PR author on a repository with review stacks enabled) to inject arbitrary environment-variable **names** — including `PATH` — into the exact hash passed to `PTY.spawn` for their own review stack's deploy/task commands. The confirmed, demonstrable impact is corruption/override of the deploy host's `PATH` for that stack's task execution, breaking Shipit's intended `Shipit.shell_paths` precedence (an integrity violation of the constructed command environment). The `BUNDLE_GEMFILE`-relative-file RCE chain is plausible given the code path but not fully verified end-to-end (specifically the `chdir` used for dependency-install commands relative to attacker-controlled repository content), so I present it with reduced confidence rather than as fully demonstrated. The blast radius is scoped to the attacker's own review stack/task execution (self-inflicted on their own PR's pipeline); no cross-tenant or cross-repository mutation was found in this path, since `labeled_active_stack?` and `review_stack.stack` scope resolution key off `params.repository.full_name` matched against the target repository's own stacks.

### Likelihood Explanation
Preconditions are low-cost for the attacker: review stacks must be enabled for the target repository (`repository.review_stacks_enabled`) and the PR's stack must be present and not archived — both are common, default-adjacent configurations, and the attacker needs no Shipit credentials, only the ability to open/label their own PR. Sending the crafted `labeled` webhook is trivial for an attacker who controls their own repository (webhooks are repository-owned and sent automatically by GitHub on label events on the attacker's own PR). The harder-to-confirm `BUNDLE_GEMFILE` RCE chain additionally requires that the deploy spec's dependency-install step run `bundle` with a working directory equal to the attacker's checked-out PR content and that no later env merge step (`deploy_spec.machine_env`, `@task.env`) redefines `BUNDLE_GEMFILE`.

### Recommendation
Before merging `pull_request.labels` (or any PR-derived data) into any environment hash reaching `Command`, apply an explicit denylist/allowlist: reject or drop label names that collide with reserved/interpreter-significant variables (`PATH`, `BUNDLE_GEMFILE`, `BUNDLE_PATH`, `RUBYLIB`, `RUBYOPT`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `GEM_HOME`, `GEM_PATH`, etc.), e.g. in `ReviewStack#env` (`app/models/shipit/review_stack.rb`) before the `.upcase =>` merge, and/or route the label-derived hash through `EnvironmentVariables#permit` against an explicit allowlist rather than accepting arbitrary uppercased label names as env keys.

### Proof of Concept
Minitest plan (extending the existing `test/models/shipit/review_stack_test.rb` and `label_capturing_handler_test.rb` patterns):
```ruby
test "capture_labels persists reserved env-variable names unsanitized" do
  stack = create_stack
  payload = payload_parsed(:pull_request_labeled)
  payload["pull_request"]["labels"] = [
    { "name" => "PATH" }, { "name" => "BUNDLE_GEMFILE" }, { "name" => "RUBYLIB" }
  ]

  LabelCapturingHandler.new(payload).process

  assert_equal ["PATH", "BUNDLE_GEMFILE", "RUBYLIB"], stack.reload.pull_request.labels
end

test "ReviewStack#env surfaces reserved names and overrides constructed PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["PATH", "BUNDLE_GEMFILE", "RUBYLIB"]

  env = stack.env
  assert_equal "true", env["PATH"]
  assert_equal "true", env["BUNDLE_GEMFILE"]
  assert_equal "true", env["RUBYLIB"]
end

test "Command#unbundled_env lets label-derived env override the constructed PATH" do
  command = Shipit::Command.new("true", env: { "PATH" => "true" }, chdir: ".")
  assert_equal "true", command.unbundled_env["PATH"]
end
```
These assert both sides of the binding: `PullRequest#labels` equals the raw unsanitized webhook array, and `ReviewStack#env`/`Command#unbundled_env` surface every reserved name as an uppercased key with no filtering, confirming the missing disjointness enforcement. (Full end-to-end confirmation of Bundler evaluating an attacker-controlled `true` file for RCE would require an additional integration test driving `TaskCommands#install_dependencies` with a checked-out fixture repo containing a file named `true`, which I was not able to complete in this session.)     def permit(variable_definitions)
      return {} unless @env
      raise "A whitelist is required to sanitize environment variables" unless variable_definitions

      sanitize_env_vars(variable_definitions)
    end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    private

    def initialize(env)
      @env = env
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
