### Title
Cross-repository status forgery flips `UndeployedCommit#deploy_disallowed?` to enable deploys of a victim commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commit(s) to attach a forged GitHub status to using only `Commit.where(sha: params.sha)`, with no scoping by the repository that sent the webhook. Because SHA is not guaranteed unique across repositories/stacks, an attacker who owns any GitHub repository can create a commit with the same SHA as a victim commit (or exploit an actual SHA collision/shared-history commit that exists in two different stacks, e.g. via forking/rebasing) and send a `status` webhook from their own repository that GitHub will sign correctly, causing Shipit to apply the "success" status to the victim's `Commit` row and flip `Commit#deployable?` / `UndeployedCommit#deploy_disallowed?` to `false` for a stack the attacker never contributed to.

### Finding Description
The broken binding, stated as an equality that the code assumes but does not enforce:

`repository_that_sent_the_webhook.full_name == commit.stack.github_repo_name` for every `Commit` row matched by `params.sha`.

Trace:
- `StatusHandler#process` at `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` does:
  ```ruby
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ``` [1](#0-0) 
  This query is global across the entire `commits` table — it is not scoped to `params.repository` (or any owner/name field carried by the GitHub webhook envelope). Any `Commit` record in any stack, for any tenant, whose `sha` column matches the value the attacker supplied is updated.
- `Commit#create_status_from_github!` -> `statuses.replicate_from_github!` writes a real `Status` row tied to that commit/stack, and `Commit#status` recomputes `Status::Group.compact` from it. [2](#0-1) [3](#0-2) 
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, delegating `success?`/`state` to `status`. [4](#0-3) 
- `UndeployedCommit#deploy_disallowed?` is `!deployable? || !stack.deployable?`. [5](#0-4) 
- `UndeployedCommit#deploy_state` likewise starts from `deployable? ? 'allowed' : status.state`. [6](#0-5) 

None of the standard webhook guards protect against this because they operate at a different layer: the signature check (`verify_webhook_signature`) only proves the payload came from *some* GitHub repository that the app's webhook secret is registered against (or the attacker's own repository, if per-repo webhook secrets are used and the attacker owns a repository wired into Shipit as a stack) — it says nothing about *which* repository's commits the `sha` in the payload is allowed to touch. The `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`/etc. as strings; it does not require or cross-check a repository identifier against the matched `Commit#stack`. There is no `require_permission!`/`current_user`/`stacks` scope involved at all, because webhook delivery is unauthenticated-by-design (secret-signed only) and is expected to be trusted solely on the basis of the sending repository, which this handler never checks.

Contrast with `PushHandler`, which is expected to scope work to the repository indicated by the payload (branch/repo matching a specific `Stack`); `StatusHandler` breaks this pattern by keying only on `sha`.

Attack surface: SHA collision is not required in the cryptographic sense — it is enough for the attacker to get the identical 40-hex-character SHA string recorded in two different `Commit` rows. This is achievable without any secret because: (a) the same commit can legitimately be pushed to multiple repositories (forks, mirrors, cherry-picks preserving the same tree+parents+author date recreate the same SHA), or (b) an attacker who forks or mirrors the victim's repository and pushes the exact same commit history (which is public if the victim repo is public, or which the attacker can otherwise obtain) will produce commits with SHAs identical to the victim's, then trigger a `status` event from their own repo/webhook against that SHA.

### Impact Explanation
An attacker-controlled webhook write mutates `Status` state for a `Commit` belonging to a stack/repository the attacker does not control, directly flipping `Commit#deployable?` and `UndeployedCommit#deploy_disallowed?` from `true` (blocking) to `false` (allowing) for that victim commit. This satisfies the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" category: the operator-facing `deploy_button`/`redeploy_button` state (driven by `deploy_disallowed?`) becomes enabled based on a forged precondition, and a legitimate operator who trusts the UI can trigger a real `Deploy` of code whose CI status was never actually validated by the systems Shipit believes it was. This is repeatable against any commit whose SHA the attacker can reproduce and is not limited to a single tenant — any stack in the same Shipit instance is affected. Severity: Critical, matching "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy."

### Likelihood Explanation
Preconditions: the attacker needs a `Commit` row to exist in Shipit's DB with the target SHA in the victim's stack (i.e., Shipit must already have synced that commit, which happens automatically for any tracked stack), and needs to get a `status` webhook delivered and signature-verified for a SHA equal to that value — either by owning a repository that shares real commit history with the victim (fork/mirror scenario, requiring only that the victim repo be forkable/public) or by controlling a repository whose CI reports back on an identical commit. No Shipit session, API token, or GitHub team membership is required, consistent with the attacker model. Feasibility is moderate-to-high for public/forked repos and is fully repeatable per-SHA.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed handler) to commits belonging to stacks whose `github_repo_name`/repository matches the webhook's source repository, e.g. resolve the target `Stack`(s) from `params.repository` (owner/name) before selecting `Commit` rows, instead of a bare global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/undeployed_commit_test.rb (new test)
test "#deploy_disallowed? is only flipped by a status from the commit's own repository" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = Shipit::Stack.create!(
    repository: Shipit::Repository.create!(owner: 'attacker', name: 'evil-repo'),
    environment: 'production'
  )
  shared_sha = 'a' * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim work', author: shipit_users(:walrus))
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'attacker work', author: shipit_users(:walrus))

  undeployed = Shipit::UndeployedCommit.new(victim_commit, index: 0)
  assert undeployed.deploy_disallowed?, "expected victim commit to be undeployable before any status"

  # Attacker sends a `status` webhook for their own repository/commit, but the shared SHA
  # causes StatusHandler to update the victim commit too.
  Shipit::Webhooks::Handlers::StatusHandler.new(
    payload: {
      sha: shared_sha,
      state: 'success',
      context: 'ci/attacker',
      repository: { full_name: 'attacker/evil-repo' }, # attacker's own, legitimately signed webhook
    }.stringify_keys
  ).process

  victim_commit.reload
  undeployed_after = Shipit::UndeployedCommit.new(victim_commit, index: 0)
  refute undeployed_after.deploy_disallowed?, "victim commit became deployable due to a foreign-repository webhook"
end
```
This demonstrates `deploy_disallowed?` transitioning `true -> false` for the victim commit solely because of a status event carrying a different repository's identity, with no interaction from the victim's own CI or repository.
