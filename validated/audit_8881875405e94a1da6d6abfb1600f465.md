## Analysis

The pattern described in the external report — external token transfer executed *before* the state that guards against double-spend is cleared — has a direct analog in this codebase in `collect_creator_fee` and `collect_creator_fee_permissionless`.

### Title
Checks-Effects-Interactions violation in `collect_creator_fee`/`collect_creator_fee_permissionless` allows re-entrant double-collection of creator fees - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
Both `collect_creator_fee` and `collect_creator_fee_permissionless` read the accrued `creator_fees_token_0`/`creator_fees_token_1` counters, perform two external CPI token transfers (`transfer_from_pool_vault_to_user`) using those amounts, and only *afterwards* zero out the counters in `pool_state`. This is the exact same "check → interact → effect" ordering flagged in the source report for `Distributor.distributeFor`.

### Finding Description
In `collect_creator_fee`, the flow is:
1. Read `creator_fees_token_0`/`creator_fees_token_1` from `pool_state` (check).
2. CPI-transfer both amounts out of the vaults to the creator's token accounts (interaction) via `transfer_from_pool_vault_to_user`.
3. Only then zero the counters in `pool_state` (effect). [1](#0-0) 

The permissionless variant follows the identical ordering, and can be triggered by *any* signer (`payer`), not just the pool creator, since fees always flow to the fixed `pool_creator` address: [2](#0-1) 

The transfer itself goes through `transfer_checked` on the Token-2022 program: [3](#0-2) 

If the pool's token mint carries a Token-2022 `TransferHook` extension, `transfer_checked` will CPI into the hook program mid-transfer, before the second transfer and before the zeroing of `creator_fees_token_0`/`creator_fees_token_1`. A hook program controlled by (or colluding with) the attacker could re-enter `collect_creator_fee_permissionless` within that CPI window, re-reading the still-nonzero fee counters and re-triggering another pair of transfers — draining vault funds beyond the actually accrued fee amount.

### Impact Explanation
If reachable, repeated re-entrant collection would drain pool vault token balances beyond the legitimately accrued creator fees, directly stealing LP/pool funds — a concrete theft of user funds, matching the severity class of the original report.

### Likelihood Explanation
This is the main caveat, and I could not fully confirm it within the scope investigated: whether a mint using the `TransferHook` extension can actually be set as `token_0_mint`/`token_1_mint` for a pool. There is a separate whitelist utility, `is_supported_mint`, that restricts allowed Token-2022 extensions to `TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, and `ScaledUiAmount` — notably *excluding* `TransferHook` [4](#0-3) . I was not able to confirm within the available iterations whether this check is enforced at pool `initialize`/`initialize_with_permission` time for `token_0_mint`/`token_1_mint`, or only at `deposit` time for a separate support-mint registry. If the whitelist is enforced at pool creation, hook-based mints cannot be used and this reentrancy path is not reachable via ordinary SPL Token or non-hook Token-2022 transfers (which do not CPI back into the caller). This is a genuine likelihood gap that would need to be resolved by an engineer with direct file access.

### Recommendation
Regardless of the mint-whitelist enforcement question, the code should not rely on extension-allowlisting alone to prevent reentrancy: apply Checks-Effects-Interactions directly in `collect_creator_fee` and `collect_creator_fee_permissionless` by zeroing `pool_state.creator_fees_token_0`/`creator_fees_token_1` *before* issuing the `transfer_from_pool_vault_to_user` CPIs (the same fix pattern already used correctly in `collect_protocol_fee`, which reads/decrements fee state inside a scoped block before transferring [5](#0-4) ).

### Proof of Concept
1. Confirm/relax whether a pool can be initialized with a `TransferHook`-extension mint as `token_0_mint` or `token_1_mint` (this is the unresolved precondition).
2. If so, deploy a transfer-hook program that, upon invocation during the vault→creator transfer, issues a CPI back into `collect_creator_fee_permissionless` for the same pool.
3. Call `collect_creator_fee_permissionless` once with nonzero `creator_fees_token_0`; the hook fires during the token_0 transfer, re-entering the instruction while `pool_state.creator_fees_token_0` is still unzeroed, causing a second transfer of the same amount before the original call's zeroing effect executes.
4. Repeat until the vault is drained beyond the legitimately accrued fee.

Because I could not verify the mint-extension gating with certainty, this should be treated as a code-pattern finding requiring confirmation of exploitability against the actual mint-validation enforcement in `initialize.rs`/`initialize_with_permission.rs`.

pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;

    Ok(())
}

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
