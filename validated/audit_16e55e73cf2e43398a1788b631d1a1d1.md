### Title
First-Depositor Share-Price Manipulation in Sample "Uniswap-like Market Maker" AA — (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `uniswap_like_market_maker.oscript` reference AA template mints `mm_asset` shares to liquidity providers using a formula that is structurally identical to the vulnerable `calcrMintQty` pattern in the Kyber report: new-share issuance for a depositor is computed as `round(investor_share_of_prev_balance * outstanding_shares)`, where `outstanding_shares` (an analog of `rTotalSupply`) and the pool's actual reserve balances (an analog of `reinvestL`/`baseL`) can be driven out of proportion by the address that makes the very first deposit. Once that ratio is skewed, later depositors' contributions round down to zero newly-issued shares while their funds are absorbed into the AA's reserves, silently transferring value to the existing shareholder(s) — the same "steal swap/liquidity fees from later LPs" impact described in the report.

### Finding Description
The relevant state machine lives entirely in the `uniswap_like_market_maker.oscript` AA definition, parsed and validated by ocore's oscript/ojson pipeline and executed on-chain by `aa_composer.js` when triggered: [1](#0-0) 

The "invest in MM" case computes the pool's pre-trigger reserves (`$asset_balance`, `$bytes_balance`), and — except for the very first ("initial deposit") case — issues new `mm_asset` shares to the depositor as:

```
$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance;
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
```

This is the direct analog of Kyber's `rMintQty = rTotalSupply * (contribution) / reserve`. The initial-deposit branch is:

```
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
``` [2](#0-1) 

Because this branch fires whenever *either* reserve is zero (not both), and unconditionally sets `$issue_amount = balance[base]` (the full post-trigger byte balance, not the pre-trigger reserve used elsewhere), the first party to interact with the AA fully controls the initial exchange rate between `mm_asset_outstanding` and the AA's real bytes/asset reserves — exactly as the first LP in the Kyber Pool controls the initial `reinvestLLast`/`rTotalSupply` relationship. An attacker can seed the pool with a large `mm_asset_outstanding` relative to actual reserves (or otherwise push the outstanding/reserve ratio to an extreme via successive invest/divest operations, each subject to independent `round()` calls at lines 43 and 47), and subsequent depositors' `$issue_amount = round(investor_share_of_prev_balance * mm_asset_outstanding)` then rounds down to `0` for any deposit that is small relative to the inflated `mm_asset_outstanding`. Their base/asset payment is still accepted into the AA (it becomes part of `balance[base]`/`balance[$asset]`), but they receive no `mm_asset` shares in return, so the value is captured by the existing shareholder set on divestment: [3](#0-2) 

This mirrors the Kyber root cause precisely: a mint-quantity formula of the form `total_supply * contribution / reserve`, with `round()`/floor-style division, that a single controlling actor can pre-condition (via the first deposit and/or repeated round-trip invest/divest calls) so that it evaluates to zero for future depositors, permanently diverting their funds to the existing supply holders.

### Impact Explanation
Any depositor who trusts and uses this shipped reference AA as-is (or a fork/derivative built from it, which is the AA's stated purpose) can have their contributed bytes/asset silently absorbed into the pool with zero shares issued, i.e., unrecoverable fund loss for the depositor and an unearned appreciation of the attacker's existing shares — a direct AA fund-loss/theft impact reachable by a single posted trigger unit, matching the "concrete unauthorized spending / AA fund loss" bar.

### Likelihood Explanation
The attack requires only that the attacker be the first (or an early, large) depositor into a freshly-defined instance of this AA, which is the default deployment path for anyone who deploys/uses this exact template unmodified — no privileged role, no network-level assumptions, and no cross-node disagreement is needed, only ordinary trigger units authored by the attacker.

### Recommendation
The template should not allow a single trigger to set an unconstrained initial exchange rate: require the "initial deposit" branch to mint shares 1:1 based on a fixed baseline (e.g., always defined together with the asset in the same trigger, with a minimum-liquidity lock similar to Uniswap's `MINIMUM_LIQUIDITY`), and add a floor/minimum-shares check so that `$issue_amount` computed via `round()` can never legitimately settle to `0` for a nonzero deposit — bounce instead of silently accepting the payment when the computed share amount rounds to zero.

### Proof of Concept
1. Attacker triggers `define` to create `mm_asset`.
2. Attacker sends the first "invest" trigger with `trigger.output[[asset=base]]` = X bytes and 0 of `$asset`; hits the "initial deposit" branch, receiving `$issue_amount = balance[base]` (all pool bytes) as shares, establishing `mm_asset_outstanding = X`.
3. Attacker repeats small invest/divest round-trips exploiting `round()` on lines 43/47 (`$expected_asset_amount` and `$issue_amount`), each time growing `mm_asset_outstanding` faster than the real reserve growth (favorable rounding), further skewing the outstanding/reserve ratio.
4. A normal user (`userB`) later sends a modest deposit; `$investor_share_of_prev_balance * mm_asset_outstanding` rounds to `0`, so `userB` receives `0` `mm_asset` shares while their bytes are added to `balance[base]`.
5. Attacker calls "divest MM shares," redeeming their (unchanged) share count against the now-larger `balance[base]`/`balance[$asset]`, capturing `userB`'s contribution. [4](#0-3) [3](#0-2)
