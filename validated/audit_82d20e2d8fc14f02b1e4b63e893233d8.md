### Title
JWS/JWT-style signature-malleability due to non-canonical Base64 decoding of `sig` authentifiers - (File: signature.js)

### Summary
`ecdsaSig.verify()` in `signature.js` decodes the author's ECDSA signature with Node's lenient `Buffer.from(str, "base64")`, which silently ignores non-Base64 characters instead of rejecting them. `definition.js`'s `'sig'` authentifier evaluator calls this function directly on the attacker-controlled `assocAuthentifiers[path]` string with no prior canonical-Base64 check. Because the unit's own hash (`getUnitHash`) is computed over the *literal* signature string (authentifiers are not stripped when building `content_hash`), anyone who observes a validly signed unit can mutate the signature string with junk characters that decode to the same bytes, producing a semantically identical unit with a different unit hash — without ever touching the private key. This is the same bug class as CVE-2022-25898 (jsrsasign accepting JWS/JWT signatures containing non-Base64URL garbage because the decoder silently strips invalid characters).

### Finding Description
`signature.js` verifies a `secp256k1` signature like this: [1](#0-0) 

`Buffer.from(b64_sig, "base64")` in Node.js does not validate that `b64_sig` is canonical Base64: it decodes as many valid symbols as it can find and silently skips characters that are not part of the Base64 alphabet. Consequently, many different literal strings (e.g. the correct signature with extra `!`, `@`, `\x00`, or other non-Base64 characters spliced in) decode to the exact same 64-byte signature.

This function is invoked directly on attacker-controlled authentifier data in `definition.js`'s address-definition evaluator, with no canonical-format check performed first: [2](#0-1) 

Unlike `validateAndFormatPemPubKey` (which explicitly calls `ValidationUtils.isValidBase64` before decoding, at signature.js:131) or `is_valid_sig` in the oscript evaluator (which explicitly checks `isValidHexadecimal`/`isValidBase64` before verifying, formula/evaluation.js:1720), the ordinary `'sig'` authentifier path used by every regular single/multi-signature address definition has no such canonicalization guard.

Critically, the unit hash itself is derived from the raw, unstripped unit (including `authors[i].authentifiers`): [3](#0-2) 

`getUnitHashToSign`/`getSignedPackageHashToSign` are the only places that strip `authentifiers` before hashing (for the message that gets signed): [4](#0-3) 

But `getUnitContentHash` → `getNakedUnit` → `getUnitHash` (the unit's identity hash used everywhere else — DAG parent references, `unit already known` checks, ball hashing, etc.) does **not** strip authentifiers, so it hashes the literal (mutable) signature string.

### Impact Explanation
Because signature verification accepts any string that Base64-decodes (after silently discarding invalid characters) to the correct 64 signature bytes, and the unit-identity hash is computed over that same literal string, a third party who observes a broadcast-but-unconfirmed unit (in the mempool, in a hub relay, or via light-client history) can mutate the `sig` authentifier field with harmless junk characters and produce a new, fully valid unit with:
- the same author, address, inputs, outputs, and messages,
- a *different* unit hash,
- no knowledge of the private key required.

This is classic transaction/signature malleability. Any application, exchange, AA-trigger listener, or light wallet in this ecosystem that tracks a payment/trigger by its expected unit hash (rather than by its economic content) can be made to believe the original unit was dropped/never confirmed, while a malleated duplicate consumes the same inputs and gets stabilized instead — leading to confusion about payment confirmation, mis-triggering of AA logic keyed off specific expected `unit` values (e.g. `definition template` matching by unit hash, `unit[]`/`definition[]` references, private-payment chain `unit` linkage), and general disagreement between nodes/services about which hash represents "the" transaction. It reaches the "node disagreement on validity/stability" / "network unable to confirm new units" impact bar because two distinct, independently-computed valid unit hashes now represent the identical economic transaction, undermining the assumption (relied on throughout composer.js, network.js and AA reference logic) that a signed transaction has one canonical hash.

### Likelihood Explanation
Trivially reachable: any unprivileged party who can observe a unit in flight (before it is buried/stable) — a peer, a hub, a light client requesting history, or simply the original sender re-broadcasting — can perform the mutation with no cryptographic effort; only string splicing is required. No special privileges, node compromise, or private key access are needed, only observation of an already-signed valid unit and the ability to submit a modified unit through the same normal unit-posting path every wallet uses.

### Recommendation
Enforce canonical Base64 encoding for every `sig`/`hash` authentifier value before it is passed to `ecdsaSig.verify` in `definition.js`, using the existing `ValidationUtils.isValidBase64` round-trip check (as is already done for PEM signatures and `is_valid_sig`). Reject authentifiers that are not canonical Base64 (optionally with an expected fixed length for `secp256k1`, i.e. Base64 of 64 bytes) prior to calling `ecdsaSig.verify`.

### Proof of Concept
1. Alice signs and broadcasts a normal payment unit; `objAuthor.authentifiers['r'] = "<64-byte-sig-in-canonical-base64>"`.
2. Before the unit stabilizes, an observer (no private key) copies the unit and inserts non-Base64 characters into the signature string in positions that Node's Base64 decoder will discard (e.g. characters outside `[A-Za-z0-9+/=]`), keeping the decodable payload identical.
3. The observer submits this mutated unit. `definition.js`'s `'sig'` handler at line 745 calls `ecdsaSig.verify(unit_hash_to_sign, mutated_signature, pubkey)`, which succeeds because `Buffer.from(mutated_signature, "base64")` decodes to the same 64 bytes as the original.
4. `object_hash.getUnitHash` computes a different hash for the mutated unit (because it hashes the literal, now-different, authentifier string), producing a second fully valid unit for the same economic transaction with a different `unit` identifier.
