### Title
Webhook signature verification is scoped to the wrong field, allowing cross-organization forgery of GitHub events (status/push) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the `webhook_secret` of the organization named in `repository.owner.login` (or `organization.login`), but the event handlers that actually act on the payload resolve the target `Repository`/`Stack` from a completely different, unauthenticated field: `repository.full_name`. Since these two payload fields are never cross-checked, an attacker who possesses the `webhook_secret` of *any* organization configured in the Shipit instance can forge a webhook whose `repository.owner.login` matches their own org (making signature verification succeed) while `repository.full_name` points at a stack belonging to a different organization, causing Shipit to act on a repository the attacker's credentials do not cover.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

`verify_signature` derives the organization purely from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), fetches that organization's GitHub App config via `Shipit.github(organization: repository_owner)`, and validates `X-Hub-Signature` against that org's own `webhook_secret`: [3](#0-2) 

Handlers, however, resolve which `Repository`/`Stack` to operate on from an entirely separate field, `repository.full_name`, with no reference to the organization used to authenticate the request: [4](#0-3) 

For example, `PushHandler#process` calls `sync_github` on whatever stacks belong to `Repository.from_github_repo_name(repository_name)`: [5](#0-4) 

Multi-organization installs are supported natively (`Shipit.github_app_config`, `Shipit.github_organizations`), each org having its own distinct `webhook_secret`: [6](#0-5) 

This is directly analogous to the reported bug class: a value the code trusts as "verified" (here, the organization that authenticated the request) is silently decoupled from the value the code actually acts on (here, the repository/stack targeted by `repository.full_name`), exactly as VaultTracker trusted a stale `maturityRate` decoupled from the live, mutable `exchangeRate`.

### Impact Explanation
Because signature verification checks `repository.owner.login` while the handler resolves the target stack from the independent `repository.full_name` field, an attacker who legitimately controls the `webhook_secret` for one onboarded organization ("org A") can forge a webhook that authenticates as org A but is processed as an event for a stack/repository belonging to an unrelated organization ("org B"). Concretely:

- Forging a `status` event lets the attacker inject a fabricated commit status (e.g. marking a required CI context as `success`) for any commit SHA in a victim repository the attacker doesn't control, bypassing `ci.require` checks and enabling an **unauthorized deploy** of a commit that never actually passed CI.
- Forging a `push`/`check_suite` event can trigger `sync_github`/`RefreshCheckRunsJob` against arbitrary victim stacks, polluting their commit/CI state.

This breaks the binding "an organization that authenticated versus the repository that is written," which the assignment explicitly calls out as an in-scope, unprivileged-attacker-relevant deployment-trust binding, and lands in the allowed High/Critical impact bucket (unauthorized deploy / cross-repository writes to stack state).

### Likelihood Explanation
Exploitation requires only:
1. A Shipit deployment onboarding more than one GitHub organization (a documented, supported configuration via `github_app_config`).
2. Knowledge of the `webhook_secret` for *any one* of those organizations (which the attacker may legitimately hold if they administer that org's GitHub webhook settings, or if that secret has otherwise leaked) — no access to the victim organization is required.

No GitHub App private key, `api_clients_secret`, or Shipit session/API token is needed; the attacker only crafts an HTTP POST with a mismatched `repository.owner.login` vs `repository.full_name` and a correctly-signed body. This is a design flaw in field binding, not a brute-force or DoS technique, so it is reliably reproducible.

### Recommendation
In `WebhooksController#verify_signature`/`Handler#repository_name`, ensure the organization used to select the `webhook_secret` is the same organization embedded in `repository.full_name` (e.g., require `repository.owner.login == repository.full_name.split('/').first`, and reject the request otherwise), or better, resolve the target `Repository` first and always verify the signature using that repository's own owning organization's `webhook_secret`, never a value independently supplied elsewhere in the payload.

### Proof of Concept
1. Attacker administers (or otherwise possesses the `webhook_secret` for) organization `attacker-org`, which is one of several organizations configured on a shared Shipit instance.
2. Attacker crafts a `status` webhook body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "required-ci-check",
  "target_url": "https://ci.example.com/1",
  "branches": [{ "name": "main" }]
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and sends `POST /webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `attacker-org`, fetches `attacker-org`'s app config, and the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `StatusHandler` (a `Handler` subclass) computes `repository_name` from `repository.full_name` → `victim-org/victim-repo` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and records a passing CI status for `victim-org/victim-repo`'s commit, even though the attacker has no credentials tied to `victim-org`.
6. If `victim-org`'s `shipit.yml` gates deploys on that status context (`ci.require`), the forged status can enable an unauthorized deploy of a commit that never actually passed CI.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
