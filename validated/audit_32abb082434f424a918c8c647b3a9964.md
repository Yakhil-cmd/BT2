### Title
Unprivileged trigger sender can key/update another address's state variables (e.g., lock/timestamp gates) without consent - ([File: formula/evaluation.js], analog demonstrated in [File: test/aa.test.js])

### Summary
The oscript `state` message engine lets an AA definition build the *key* of a `var[...]` write from an arbitrary formula, including data taken straight from `trigger.data` supplied by whoever sent the triggering unit. There is no built-in restriction forcing state-variable keys that represent "per-user" data (balances, lock timestamps, deposit records) to be derived from `trigger.address` (the actual sender/depositor). This mirrors the `TradingVault.deposit()` bug: any caller can update a piece of state that gates another user's ability to withdraw, without that user's consent, simply by supplying the victim's address in the trigger payload.

### Finding Description
`getTrigger()` in [1](#0-0)  exposes `trigger.data` verbatim from the `data` message of the triggering unit — this is fully attacker-controlled content, distinct from `trigger.address`, which is the actual signer/sender of the unit. Nothing in the AA execution pipeline (`handleTrigger`, `aa_composer.js`) prevents a `state` message from using `trigger.data.<field>` (rather than `trigger.address`) as the key of a `var[...]` write.

This is not hypothetical: the test suite explicitly validates and executes AA definitions that do exactly this — writing/updating a per-address counter keyed by an address supplied in `trigger.data` rather than the actual `trigger.address`: [2](#0-1) [3](#0-2) 

`var[trigger.data.address||'_count'] = var[trigger.data.address||'_count'] + 1;`

This shows the formula engine and AA validator (`validateAA`) both accept and successfully execute a `state` write whose target key is chosen from data supplied by an unrelated, unprivileged sender. Compare this to the safe pattern used elsewhere in the codebase, where state that must reflect only the actual counterparty is explicitly bound to a cryptographically verified address (e.g. the order-book sample keys balances via `$order1.address`, taken from a `signed_message` verified with `is_valid_signed_package`, not from unauthenticated `trigger.data`): [4](#0-3) 

If an AA author instead writes an unguarded pattern such as a "deposit for user" or "stake for user" case that updates `var['last_deposit_' || trigger.data.user] = timestamp` (analogous to Solidity's `userLastDepositTime[user] = block.timestamp`) based on an address taken from `trigger.data` rather than requiring `trigger.address == trigger.data.user` or a signed authorization, any unprivileged trigger sender can:
- Post a unit with a trivial payment/trigger and `data.user = <victim address>` to force-update the victim's lock/deposit timestamp,
- Repeatedly grief the victim's stake/lock state, resetting cooldowns and blocking their withdrawal `if` conditions from ever being satisfied — exactly the DoS class described in the source report (`userLastDepositTime` griefing).

Because state vars, balances, and other AA data model are the *only* persistent state gating fund release in oscript-based contracts, an AA that (intentionally or by oversight) keys withdrawal-gating variables off attacker-suppliable data instead of the verified `trigger.address` reproduces the exact vulnerability class from the report at the ocore AA layer.

### Impact Explanation
Any unprivileged unit poster can act as an unauthorized "depositor on behalf of" another address for AAs that key locking/cooldown/timestamp state off `trigger.data` fields. This can:
- Perpetually reset another user's withdrawal-eligibility timer, freezing their funds inside the AA (AA fund freezing/loss of availability),
- Be exploited via collusion or unilaterally to deny service to a targeted address, exactly as flagged as "Medium" in the source report for the analogous Solidity contract.

### Likelihood Explanation
Likelihood is entirely dependent on the specific AA template's design. The oscript engine imposes no restriction preventing this pattern, and the test suite demonstrates it as a supported, validated construct (`var[trigger.data.address...]`), so any AA author copying convenience patterns from `trigger.data` for user-identifying keys (rather than binding to `trigger.address` or a verified signature, as is correctly done in the order-book sample) will reintroduce this bug. Given that oscript templates are commonly written by third-party developers with varying security awareness (per the acknowledged report, "careful vetting" is required), this is a realistic recurring risk across the AA ecosystem built on ocore rather than a one-off engine bug.

### Recommendation
- Document and lint against (or add a static-analysis warning in `formula/validation.js`) usage of `trigger.data.*` values as keys or content of state variables that gate withdrawals/locks for the corresponding address, unless the address is verified via `is_valid_signed_package` or explicitly equals `trigger.address`.
- Provide/require AA template authors to bind all "on behalf of user" operations either to `trigger.address` directly, or to an address extracted from a payload validated with a signature (as in `order_book_exchange.oscript`), before permitting a caller to mutate another address's lock/timestamp state.
- Emit a compiler/validator hint when a `state` message assigns to `var[<expr containing trigger.data>]` without a corresponding signature check in the same `case`.

### Proof of Concept
1. Deploy an AA whose `deposit` case does:
```
messages: [
  { app: 'state', state: `{
      var['balance_' || trigger.data.user] += trigger.output[[asset=base]];
      var['last_deposit_ts_' || trigger.data.user] = timestamp;
  }` }
]
```
(directly analogous to the pattern already exercised in `test/aa.test.js` at lines 308-311/455-458, `var[trigger.data.address||'_count'] = ...`).
2. Attacker Eve posts a unit containing 1 output to the AA (minimal amount) and `data: { user: '<Victim_Address>' }`.
3. The AA trigger handler (`aa_composer.js::handleTrigger`) executes the `state` formula using `trigger.data.user` (Eve-supplied) as the key, updating `last_deposit_ts_<Victim>` even though Victim never authored or authorized the unit.
4. If Victim's withdrawal case checks `timestamp > var['last_deposit_ts_' || trigger.address] + lock_period`, Eve can repeat step 2 indefinitely to keep resetting Victim's lock timer, permanently denying Victim's ability to withdraw — reproducing the `userLastDepositTime` DoS from the source report at the AA layer.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
