### Title
Missing zero-address (`Pubkey::default()`) validation on `creator` in `initialize_with_permission` permanently freezes creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission` accepts an unchecked `creator` account that is written directly into `PoolState.pool_creator` without verifying it is not the Solana zero-value pubkey (`Pubkey::default()`), the on-chain analog of Solidity's `address(0)`. Unlike the standard `Initialize` instruction, which forces `creator` to be a `Signer` (making a zero/unownable address practically impossible), `initialize_with_permission` lets the caller pass an arbitrary `creator` pubkey with no signature and no non-default check.

### Finding Description
In `Initialize`, `creator` must sign the transaction: [1](#0-0) 

In `InitializeWithPermission`, `creator` is only an `UncheckedAccount` with a `CHECK:` comment and no constraint at all: [2](#0-1) 

This value flows unchecked into `pool_state.initialize(...)`, which stores it as `pool_creator`: [3](#0-2) [4](#0-3) 

`pool_creator` is later relied upon in two fee-collection paths. `collect_creator_fee` requires a `Signer` matching `pool_creator`: [5](#0-4) 

`collect_creator_fee_permissionless` is callable by anyone and creates an associated token account whose `authority` is the (unchecked) `creator`, then transfers accumulated fees to it: [6](#0-5) [7](#0-6) [8](#0-7) 

If `creator` is set to `Pubkey::default()` (or any other pubkey nobody controls a private key for) at pool creation time via `initialize_with_permission`, `pool_creator` in `PoolState` becomes that unownable value. This exactly mirrors the reported bug class: an address field that should be validated as non-zero is written unchecked, leading to unrecoverable state — here, permanently inaccessible LP/creator funds instead of an inconsistent `AccountSystem` username mapping.

### Impact Explanation
Once `pool_creator == Pubkey::default()` (or any unownable pubkey):
- `collect_creator_fee` can never succeed because no signer can ever satisfy `address = pool_state.load()?.pool_creator` for a keyless pubkey.
- `collect_creator_fee_permissionless` will still execute (anyone can call it), creating/using an ATA owned by `Pubkey::default()` and irreversibly transferring all accumulated `creator_fees_token_0`/`creator_fees_token_1` into it.
- Because nobody holds the private key for `Pubkey::default()`, those tokens become permanently frozen/unrecoverable — a direct loss of pool-creator fee funds, satisfying "permanent freezing of user or LP funds."

### Likelihood Explanation
The instruction is reachable by any payer holding a `Permission` PDA (a pool-creator persona explicitly in scope) calling `initialize_with_permission` with `creator` set to `Pubkey::default()` or any other unowned pubkey — no privileged signature over `creator` itself is required, and no runtime check rejects the default/zero pubkey. This can happen either through attacker intent or integration error, and once triggered the fee-freezing effect is deterministic on every subsequent `collect_creator_fee_permissionless` call.

### Recommendation
Add an explicit check in `initialize_with_permission` (mirroring the fix pattern in the referenced report) that rejects `creator == Pubkey::default()` before calling `pool_state.initialize(...)`, e.g.:
```rust
require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default(), ErrorCode::InvalidInput);
```
placed before `create_pool`/`pool_state.initialize` in `programs/cp-swap/src/instructions/initialize_with_permission.rs`.

### Proof of Concept
1. A payer holding a valid `Permission` PDA calls `initialize_with_permission`, passing `creator = Pubkey::default()` as the `creator` account (an `UncheckedAccount`, no signature needed).
2. `pool_state.initialize(...)` stores `pool_creator = Pubkey::default()`.
3. Swaps accrue `creator_fees_token_0`/`creator_fees_token_1` in `PoolState` as usual.
4. Anyone calls `collect_creator_fee_permissionless`; an ATA with `authority = Pubkey::default()` is created (if needed) and the accumulated fees are transferred into it via `transfer_from_pool_vault_to_user`.
5. Because no private key exists for `Pubkey::default()`, the transferred fees are permanently unrecoverable, and `collect_creator_fee` (the signer-gated path) can never be used to retrieve them either.
