## Title
Weak/non-constant-time elliptic curves reachable via `is_valid_sig`/`vrf_verify` before the PEM-curves fix MCI - ([File: signature.js])

### Summary
`signature.js` implements `is_valid_sig()` and `vrf_verify()`, two oscript functions that any AA trigger sender or AA author can invoke by supplying an attacker-controlled PEM-encoded public key (`pem_key`), message, and signature/proof. `validateAndFormatPemPubKey()` accepts dozens of legacy elliptic curves (Brainpool `brainpoolP160r1/t1`...`brainpoolP512t1`, `secp128r1/r2`, `secp160k1/r1/r2`, many `sect*` binary curves, etc.) defined in `objSupportedPemTypes` [1](#0-0) , and dispatches verification to Node's generic `crypto.createVerify('SHA256').verify({key: pem_key}, ...)` path (OpenSSL) whenever the key isn't a "safe" curve [2](#0-1) . This is exactly the bug class described in the Dragonblood report: WPA3/EAP-pwd's Dragonfly handshake remained vulnerable to timing/cache side-channel dictionary attacks specifically because of non-constant-time arithmetic on Brainpool and other exotic curves (CVE-2019-13377).

### Finding Description
`objSupportedPemTypes` lists curve OIDs that are accepted by `validateAndFormatPemPubKey` [3](#0-2) . Only a small subset — P-256, P-224, P-384, secp256k1, and RSA — is deemed safe in `objSafePemTypes` [4](#0-3) . The remainder (Brainpool curves, small/legacy `secp1xx*`/`sect*` curves) are gated only by a network-wide switch `bPostPemCurvesFix`, tied to `constants.pemCurvesFixMci`, which is passed down from `formula/evaluation.js`'s `is_valid_sig`/`vrf_verify` handlers into `validateAndFormatPemPubKey` and `verifyMessageWithPemPubKey` [5](#0-4) [6](#0-5) .

Before `bPostPemCurvesFix` is true (i.e., for MCIs earlier than `pemCurvesFixMci`, and for any code path/historical replay/light-client validation still operating on that pre-fix range), an unprivileged AA trigger sender can supply a Brainpool or other legacy-curve PEM key and have `is_valid_sig`/`vrf_verify` perform ECDSA verification through OpenSSL's generic EC codepath rather than the constant-time `secp256k1` library used elsewhere in the codebase (`ecdsaSig.verify` in `definition.js`'s `sig` authentifier uses the dedicated `secp256k1` npm module [7](#0-6) , which is not affected). OpenSSL's non-secp256k1 EC verification for Brainpool/legacy curves is not guaranteed constant-time, mirroring the Dragonblood CVE-2019-13377 root cause.

### Impact Explanation
If an AA's bytecode uses `is_valid_sig`/`vrf_verify` with a Brainpool/legacy curve key to gate a payment, escrow release, or oracle acceptance (a realistic pattern, since these opcodes exist specifically so AAs can verify externally-signed data), an adversary able to measure verification timing (e.g., by controlling trigger timing/repeated triggers against a node they run, or observing local execution timing side-channels) could gain information to mount a dictionary/forgery-style attack against the private key controlling that AA's fund-release logic, potentially resulting in AA fund loss. This satisfies the "AA fund loss" impact category. However, this requires (a) an AA that specifically chooses one of these weak curves for a security-critical check, and (b) exploitation only remains possible for the pre-fix MCI range, since `pemCurvesFixMci` already disables use of unsafe curves going forward.

### Likelihood Explanation
Low-to-uncertain. The maintainers have already identified and mitigated this exact class of issue via `pemCurvesFixMci`/`bPostPemCurvesFix`/`objSafePemTypes`, restricting new AA logic (post-fix MCI) to safe curves only [8](#0-7) . I could not conclusively determine, within tool budget, (1) the exact numeric value of `constants.pemCurvesFixMci` and whether it has already passed on the live network (which would close the exploitation window entirely), or (2) whether any code path (e.g. light wallet/historical unit re-validation, or `main_chain.js`/`storage.js` usages of `pemCurvesFixMci`) still permits post-fix-MCI evaluation with `bPostPemCurvesFix=false`. Since existing AAs deployed before the fix that reference these curves would still need to be validated with the pre-fix rules for consensus consistency, there may be a legitimately-required backward-compatibility window that isn't itself a new bug — this needs further, deeper repo/history inspection to confirm whether any exploitable gap remains today.

### Recommendation
- Confirm `constants.pemCurvesFixMci` has been safely rolled out network-wide, and audit all code paths that compute `bPostPemCurvesFix` (`aa_composer.js`, `main_chain.js`, `storage.js`, `validation.js`) to ensure no manipulable value (e.g., attacker-chosen `last_ball_unit`) can force `bPostPemCurvesFix=false` for newly-composed AA logic after the fix MCI, as already partly enforced in the `is_valid_signed_package` last_ball MCI checks [9](#0-8) .
- Consider fully removing support for Brainpool/legacy curves from `is_valid_sig`/`vrf_verify` after the fix MCI has safely passed, rather than only warning against them, to eliminate any residual risk from historical unit replay/validation.

### Proof of Concept
Not constructible without confirming the live value of `pemCurvesFixMci` and current MCI, and without confirming a live AA that gates funds using a Brainpool/legacy-curve `is_valid_sig`/`vrf_verify` check. The `test/pem_sig.test.js` suite already demonstrates that Brainpool/legacy-curve signatures are verifiable through `is_valid_sig` pre-fix [10](#0-9) , confirming the code path is reachable by design; a concrete timing-attack PoC against OpenSSL's Brainpool implementation would require offline benchmarking that is out of scope for static code review.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}
