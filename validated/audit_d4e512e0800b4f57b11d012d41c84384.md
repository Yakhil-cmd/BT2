### Title
`flash_position` permanently strands callback-pushed tokens that are neither declared collateral nor listed in `refund_assets` — there is no recovery path - ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
`process_flash_position` mints fee-free debt, forwards it to a caller-supplied receiver contract, and then settles the callback by *balance delta*: declared `collaterals` are measured and deposited, and `refund_assets` deltas are returned to the caller. Any other token the receiver pushes to the controller is neither credited nor refunded, and the controller exposes no sweep/rescue endpoint, so those tokens are frozen on the controller balance forever. This is the same bug class as the reported `MarketplaceUniversalRouterZap.swap1155` issue: a user operational mistake about which asset/token-kind the flow handles leaves funds permanently stuck on a contract balance.

### Finding Description
In `contracts/controller/src/strategies/flash_position.rs`, settlement after the receiver callback is strictly opt-in per asset:

- Lines 125–130 snapshot controller balances only for the declared `collaterals` assets and the caller-supplied `refund_assets` list.
- Line 145–146 `collect_collateral_deposits` + `process_deposit` credit only the declared collateral deltas.
- Line 148 `refund_listed_assets` returns deltas only for tokens in `refund_assets`.

`validate_refund_assets` (lines 217–256) only enforces uniqueness, listing in the spoke/hub, bound by `max_supply_positions`, and disjointness from `collaterals` — it does not enumerate what the receiver will actually push. A receiver that transfers a token absent from both lists (e.g., a swap route outputting an unexpected token, a callback that pushes the wrong SAC, or a dust of a third asset) leaves that balance on the controller. `payments.rs::refund_controller_balance_delta` refunds only the delta since the pre-callback snapshot for listed assets, preserving prior balances, and nothing else ever touches the stranded amount. The endpoint reference confirms: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (`docs/reference/endpoints.md` L86), and the threat model notes the controller has no recovery path for stranded assets.

Unlike `multiply`/`swap_*` router paths — which refund the measured unspent input — the flash-position callback can deliver arbitrary assets, and only whitelisted deltas are returned.

### Impact Explanation
Permanent freezing of tokens on the controller balance. Any token (listed or unlisted for refund) pushed by the receiver but not declared becomes unrecoverable protocol dust; the caller's funds are lost with no admin or governance rescue function. Impact is high for the affected user; it is a fund freeze, not a protocol solvency issue.

### Likelihood Explanation
Low-to-moderate: it requires an operational mistake by the receiver contract — pushing an asset it did not declare as collateral nor include in `refund_assets`. This is plausible for generic swap-and-push receivers whose routes can emit intermediate or unexpected tokens, exactly the "user supplies the wrong token type" scenario in the original report. Reachable by any unprivileged caller via `flash_position` with their own receiver contract.

### Recommendation
Add an unconditional post-callback reconciliation: either (a) require the receiver to declare every asset it may push (superset check), or (b) sweep-refund any controller balance delta of *any* token attributable to the callback — e.g., snapshot a bounded set of assets or verify that undeclared pushes revert. At minimum, provide a rescue path (or have the pool/controller credit stray balances to the caller) so callback-delivered tokens cannot be permanently locked.

### Proof of Concept
1. Alice deploys a receiver that, inside `execute_flash_position`, transfers `collateral_amount` of the declared collateral token **plus** `X` units of an undeclared token `T` to the controller (e.g., a route that yields a second output asset).
2. Alice calls `flash_position(caller=Alice, account_id=0, spoke_id, mode=Multiply, debt, amount, receiver, data, collaterals=[(collateral, min)], refund_assets=[T omitted])`.
3. The call succeeds: collateral delta is deposited, refund list is empty/disjoint.
4. `token::Client(T).balance(controller)` increases by `X`; no entrypoint (`repay`, `recapitalize`, `claim_revenue`, any sweep) ever moves it — `refund_controller_balance_delta` only refunds listed-asset deltas and preserves the pre-existing controller balance, so the `X` units are frozen permanently.
