### Title
`StatusHandler#process` writes commit statuses without scoping to the webhook-authenticated repository/organization - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly from the attacker-controlled JSON body (`repository.owner.login`). `StatusHandler#process` then looks up commits with `Commit.where(sha: params.sha)` with no filter on stack, repository, or organization, and calls `create_status_from_github!` on every match. Because the base `Handler` class already provides a `stacks`/`repository_name` scoping mechanism (used correctly by other handlers such as `PullRequest::OpenedHandler`) that `StatusHandler` never invokes, a signature valid for organization X's webhook secret is sufficient to mutate `Commit`/`Status` rows belonging to organization Y's stack whenever a sha collision (or simply a known/leaked sha) exists.

### Finding Description
Binding claimed and verified broken: `webhook_secret organization` (the org whose secret produced a valid `X-Hub-Signature`) **==** `organization owning the Commit row(s) mutated by `create_status_from_github!``. Before the fix, these are *not* enforced to be equal:

- `WebhooksController#verify_signature` computes the signing org from the payload itself: [1](#0-0) [2](#0-1) 
This means `repository_owner` — the org whose `webhook_secret` is used to verify the signature — is fully attacker-supplied JSON, not derived from any authenticated source.

- `StatusHandler#process` never consults `repository`/`repository_owner`/`stacks` at all; it globally matches by `sha`: [3](#0-2) 
Its `params` schema doesn't even require a `repository` field, unlike sibling handlers.

- The base `Handler` class exposes exactly the scoping primitive that would fix this (`stacks` / `repository_name` derived from `payload.dig('repository', 'full_name')`), and other handlers use the analogous pattern (`Repository.from_github_repo_name(params.repository.full_name)`): [4](#0-3) [5](#0-4) 
`StatusHandler` simply omits this step.

- `Commit` belongs to a single `stack`, and shas are not required to be globally unique across stacks in the schema/model: [6](#0-5) 

Attacker flow: the attacker legitimately owns/operates organization X in this Shipit instance (multi-org configuration is supported, e.g. `test/dummy/config/secrets_double_github_app.yml`), so they know X's real `webhook_secret`. They send `POST /webhooks` with header `X-Github-Event: status`, a body containing `repository.owner.login = "X"` (so `verify_signature` checks against X's secret, which the attacker can correctly sign), but `sha` set to a commit sha that also exists in victim organization Y's stack (either a genuine sha collision they engineer, or simply a publicly known/observed sha of Y's commit — commit shas are not secrets). `verify_signature` passes because it only validates that *some* known org's secret signed the payload, not that the signature matches the commit's actual owning org. `StatusHandler#process` then finds Y's `Commit` row purely by `sha` match and calls `commit.create_status_from_github!(params)`, writing a `Status` (e.g., `state: success`) onto Y's commit despite X never having any relationship to Y's repository or secret.

None of the existing guards catch this: `drop_unhandled_event` and `check_if_ping` only gate on event type; `ExplicitParameters` (`params do ... end`) only validates presence/types of `sha`/`state`, not repository ownership; there is no `force_github_authentication`, `require_permission!`, or stack-scoping check anywhere in this code path for the `status` webhook event.

### Impact Explanation
A forged/self-signed webhook from an attacker-controlled organization writes a `Status` record (`create_status_from_github!` → `add_status` → `statuses.replicate_from_github!`) onto a commit belonging to a stack the attacker does not control. Flipping a commit to `state: 'success'` can make `Commit#deployable?` true and can trigger downstream automation such as `ProcessMergeRequestsJob` (enqueued on transition to `success`, confirmed at `test/models/commits_test.rb:773`) or continuous-delivery scheduling on the commit's actual stack. This is a cross-tenant authentication bypass: a payload authenticated for organization X mutates organization Y's commit/task state, matching the "Critical" category ("a payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy"). It is repeatable against any commit sha the attacker can discover, across every stack hosted on the same Shipit instance, not just one.

### Likelihood Explanation
Requires: (1) the Shipit instance hosts more than one organization with independent `webhook_secret`s (supported configuration, as shown by `secrets_double_github_app.yml`), and (2) the attacker legitimately controls at least one of those organizations (their own GitHub App/webhook), which they do by construction, so they know a *valid* secret without needing to steal anything. (3) The attacker needs a target `sha` that exists in the victim's stack — commit shas are not secret values (visible on GitHub commit pages, PRs, CI logs, or the Shipit UI itself for public/viewable stacks), so this is a low-cost precondition, not a cryptographic collision requirement. Given these are typically metadata that's easy to obtain, exploitation is a single crafted HTTP POST, fully repeatable.

### Recommendation
Scope `StatusHandler` (and any other sha/commit-based handler) to the repository actually authenticated by the signature: require and use `repository.full_name` from the payload (mirroring other handlers' `Repository.from_github_repo_name`), restrict the `Commit.where(sha: ...)` lookup to `stacks` (or the specific `Repository`'s stacks) resolved from that authenticated repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of a global `Commit.where(sha:)`. Additionally, consider binding `verify_signature`'s resolved organization to the actual owning organization of any resource mutated later in the request, rather than trusting `repository.owner.login` from the body alone for downstream authorization decisions.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "a status webhook signed for org X can mutate a commit belonging to stack in org Y" do
  # Setup: org X and org Y each have their own webhook_secret configured via Shipit.github(organization: ...)
  victim_commit = shipit_commits(:y_repo) # belongs to a stack under organization Y
  victim_commit.update!(sha: 'deadbeef' * 5) # 40-char sha
  before_count = victim_commit.statuses.count

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'X' } } # attacker's own org
  }.to_json

  signature = Shipit::Hook::DeliverySigner.new(x_org_webhook_secret).sign(payload) # attacker computes with their own known secret
  request.headers['X-Github-Event'] = 'status'
  request.headers['X-Hub-Signature'] = "sha1=#{signature}"

  post :create, body: payload, as: :json

  assert_equal before_count + 1, victim_commit.reload.statuses.count # BUG: mutated despite signature being for org X, not Y
end
```
This demonstrates that `Commit.where(sha:)` in `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:21-23`) is reachable and mutates a commit outside the organization whose secret authenticated the request, with no live GitHub calls required (signature computed locally with a known/configured secret, matching test patterns already used in `test/controllers/webhooks_controller_test.rb:94-107`).
