### Title
CCMenu API endpoint bypasses per-token stack scoping, allowing a stack-scoped ApiClient token to read deploy status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` lookup helper used by every other API controller with an unscoped lookup, breaking the binding between the stack an `ApiClient` token is authorized for (`ApiClient#stack_id`) and the stack the request actually touches.

### Finding Description
Every other controller inheriting from `Shipit::Api::BaseController` resolves the requested stack through the scoped helper: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a single stack, and `stack` resolves `params[:stack_id]` against that scoped relation - this is the binding: *the stack a token authorizes* == *the stack a request may act on*.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 
`Stack.from_param!(params[:stack_id])` resolves against the entire `Stack` table regardless of `current_api_client.stack_id`. The controller's authorization check is only: [3](#0-2) 
`require_permission :read, :stack`, which only checks that the client's `permissions` array contains `read:stack` via `ApiClient#check_permissions!`: [4](#0-3) 
This check is stack-agnostic - it never consults `current_api_client.stack_id`. Every legitimate `ApiClient` with `read:stack` permission (regardless of whether it was created scoped to a single stack) can therefore pass `params[:stack_id]` for **any** stack in the installation and have it resolved.

This is exactly the kind of tokens-vs-stack-touched binding described in the report's bug class: the report is about a value ("price") being verified/authorized under one assumption (regularly-updated observations) but acted upon under a weaker one (arbitrary staleness); here, an `ApiClient` is authorized ("this token may only touch stack X") but the `CCMenuController#show` action acts on whatever stack is supplied in the request, independent of that authorization.

### Impact Explanation
An attacker holding any valid `ApiClient` token scoped to a single stack (e.g., a stack-specific CI integration credential, or the token minted by `CCMenuUrlController#fetch` for a given user) can call `GET /api/stacks/:stack_id/ccmenu.xml` with a different `stack_id` and read the deploy/rollback status (`latest_deploy`, success/failure, timestamps) of stacks that token was never authorized to see. This is an unauthenticated-relative-to-target-stack read of stack state/deploy output, matching the report's "High - unauthenticated read of stack state, task streams or deploy output" impact bucket, since the token's scope guarantee (`ApiClient#stack_id`) is silently bypassed for this one endpoint while it's correctly enforced everywhere else in the API namespace.

### Likelihood Explanation
Likelihood is high for any holder of a legitimately-issued, stack-scoped `ApiClient` credential: no additional privilege is required beyond possessing a token with `read:stack` permission (which is the normal permission granted to any created `ApiClient`, including the automatically-created "CCMenu Client" in `CCMenuUrlController`). The only action needed is substituting a different `stack_id` in the URL - no signature, secret, or session is involved beyond the token itself.

### Recommendation
Remove the `stack` override in `CCMenuController` and rely on the inherited, scoped `BaseController#stack`/`#stacks` helpers so that `params[:stack_id]` is always resolved against `current_api_client.stack_id`-restricted relation, consistent with every other API controller.

### Proof of Concept
1. Obtain (or be issued) a stack-scoped `ApiClient` token authorized only for `stack A` with `read:stack` permission (e.g., analogous to fixture `here_come_the_walrus`, which is scoped to `stack: shipit`) - see `test/fixtures/shipit/api_clients.yml` for the shape of such a scoped client.
2. Send `GET /api/stacks/<stack_B_id>/ccmenu.xml?token=<stackA_token>`, where `stack_B` is a different stack the token was never granted access to.
3. `CCMenuController#authenticate_api_client` authenticates the token; `require_permission :read, :stack` passes because the token has `read:stack` in its generic permission list.
4. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly against `stack_B`, bypassing the `current_api_client.stack_id == stack_A` restriction that `BaseController#stacks` would have enforced.
5. The response renders `stack_B`'s latest deploy/rollback status, disclosing deploy state for a stack the token was never authorized to touch.
