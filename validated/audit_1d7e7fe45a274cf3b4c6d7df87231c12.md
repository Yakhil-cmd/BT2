### Title
Unhandled null pointer dereference on `storage.assocStableUnits[trigger.unit]` crashes AA processing during primary trigger handling - (File: aa_composer.js)

### Summary
`handleTrigger()` in `aa_composer.js` accesses `storage.assocStableUnits[trigger.unit].count_aa_responses` without first checking that `storage.assocStableUnits[trigger.unit]` exists. If the cache entry for the triggering unit is missing at the time this line executes, JavaScript throws `TypeError: Cannot read properties of undefined (reading 'count_aa_responses')`. This is the same bug class as CVE-2021-44921 (gpac `gf_isom_parse_movie_boxes_internal`): a parser/processor dereferences an internal structure pointer that is assumed to be non-null while processing externally-influenced input, causing an unhandled crash.

### Finding Description
In `aa_composer.js`, `handleTrigger()` is the core function that executes an AA in response to a trigger unit sent by any unprivileged user (a "trigger" is simply a payment to an AA address, postable by anyone). Near the end of the balance/fee checks: [1](#0-0) 

```
if (!bSecondary) {
    ...
    // skip this check for dry-run which uses genesis unit as trigger unit
    if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
        return bounce('a second primary trigger from the same unit is not allowed');
}
```

The code dereferences `storage.assocStableUnits[trigger.unit]` and immediately reads `.count_aa_responses` off it, with no guard for the case where `storage.assocStableUnits[trigger.unit]` is `undefined`. Every other place in the codebase that reads from `assocStableUnits`/similar caches first checks for existence, e.g. in `handlePrimaryAATrigger`: [2](#0-1) 

```
let objUnitProps = storage.assocStableUnits[unit];
if (!objUnitProps)
    throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
```

showing the developers were aware this cache entry can be absent for a stable trigger unit under some conditions (cache eviction/pruning, light vs. full node state, catching-up nodes, or unit-cache management), yet the parallel check at line 1861 omits that guard. There is no `try/catch` around this specific access inside `handleTrigger`'s trigger-processing path, so a thrown `TypeError` here propagates as an unhandled exception in the middle of processing an AA-response batch write pipeline (`handlePrimaryAATrigger` → `handleTrigger` → `updateInitialAABalances` callback), which is not caught anywhere in that call chain based on the surrounding code shown.

This is invoked purely by posting a unit with a payment to any AA address (i.e., by an unprivileged unit/trigger sender) — the same reachability class required by the rules (AA trigger sender). It is the direct oscript/AA-processing analog of the gpac null-pointer dereference: an internal cache/structure entry is assumed present while handling attacker-influenced input (the trigger unit) and is dereferenced without a null check.

### Impact Explanation
If `storage.assocStableUnits[trigger.unit]` is undefined when this line executes for a legitimate primary AA trigger (e.g., due to cache eviction on long-running full nodes, or divergent cache states across nodes at different points in sync/catch-up), the resulting uncaught `TypeError` aborts AA-response processing for that trigger unit on the affected node. Because `handleAATriggers` processes rows sequentially with `async.eachSeries` and the exception is unhandled at this depth, this can stop `handleAATriggers` from completing the full trigger-processing pass, which is directly on the path that produces AA response units and marks batch writes/commits. A node that crashes/hangs mid-processing of a stable AA trigger cannot proceed to advance the DAG for that response, which — if the divergence is state-dependent (some nodes have the cache entry, some don't) — can lead nodes to disagree on which AA responses are produced/committed, i.e., a form of node disagreement on validity/processing outcome for AA units, matching the required impact bar (node disagreement on validity/stability) rather than merely a resource/DoS issue.

### Likelihood Explanation
Reachability requires only sending ordinary payments (a primary AA trigger) to any AA address; no privileged access is needed. Whether the null dereference actually fires depends on `storage.assocStableUnits[trigger.unit]` being absent for a unit already recorded as stable and already having a pending trigger row — a condition tied to internal cache lifecycle/pruning that isn't visible from a single-file review, so likelihood of naturally hitting this state on a healthy, fully-synced node is uncertain. It is more likely to manifest on nodes that recently caught up, restarted, or otherwise have a partially warmed cache for that unit while an "aa_triggers" row for it already exists.

### Recommendation
Add an explicit existence check for `storage.assocStableUnits[trigger.unit]` before accessing `.count_aa_responses`, mirroring the guard already used in `handlePrimaryAATrigger` (throw/handle explicitly, or treat a missing cache entry as `count_aa_responses === 0`/refresh from DB), so a missing cache entry cannot produce an unhandled exception during AA trigger processing.
