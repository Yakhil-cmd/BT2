### Title
Cross-organization forgery of webhook events via unbound `repository.owner.login` (signature key selection) vs `repository.full_name` (write target) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub organization's `webhook_secret` to validate the inbound HMAC against using `repository.owner.login` from the JSON body, while every `Webhooks::Handlers::Handler` subclass (and `StatusHandler` in particular) determines *what gets written* using a completely different field — `repository.full_name`, or for `status` events, an unscoped global `sha` lookup. Because the HMAC only proves "whoever sent this raw body knows *some* organization's secret," not "the `full_name`/target this body claims to act on belongs to that organization," an operator of one legitimately configured GitHub organization in a multi-org Shipit deployment can forge events that are authenticated as their own org but mutate state belonging to a different org's stack.

### Finding Description
`verify_signature` picks the signing key by `repository_owner`, computed only from `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GithubApp` configured for that org name (see `docs/setup.md`'s "Using Multiple Github Applications" section, which is a supported, documented deployment topology), and `verify_webhook_signature` HMACs the *entire raw body* with that org's secret: [3](#0-2) 

Once the signature is accepted, the base `Handler` (used by `PushHandler`, `CheckSuiteHandler`, and all `PullRequest::*` handlers) determines the target repository/stack from an entirely different field, `repository.full_name`: [4](#0-3) 

`StatusHandler` is even less scoped — it doesn't consult `repository` at all, just a global `sha` lookup across every `Commit` in the database: [5](#0-4) 

Nothing anywhere cross-checks that the org used to select the signing secret (`repository.owner.login`) actually owns the repository named in `repository.full_name`, or owns the stack containing a commit with a matching `sha`. An attacker who is a legitimate admin of "OrgA" (and therefore knows OrgA's `webhook_secret`, which is inherent to running their own GitHub App as documented) can:

1. Build a JSON body with `repository.owner.login = "OrgA"` (so `verify_signature` selects OrgA's secret) and `repository.full_name = "OrgB/victim-repo"`.
2. Sign the raw body with OrgA's known secret and send it to `/webhooks` with `X-Github-Event: push`.
3. `verify_signature` succeeds (OrgA's secret matches the raw body it was computed over).
4. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on OrgB's stack — a stack the attacker has no privilege over.

For the `status` event, the same signature-selection trick lets the attacker forge a `state: 'success'` status for **any known commit SHA in the entire Shipit database**, regardless of which stack/org it belongs to, because `StatusHandler` never checks `repository` at all: [6](#0-5) 

`Commit#create_status_from_github!` → `add_status` re-evaluates the commit's aggregate status and, if it becomes `success` on a stack with `continuous_deployment` enabled, schedules `ContinuousDeliveryJob`: [7](#0-6) [8](#0-7) 

This breaks exactly the binding class called out by the rules: **an organization that authenticated (via `repository_owner`/webhook secret selection) versus the repository/stack that is actually written (via `repository.full_name` or unscoped `sha`)**.

### Impact Explanation
An attacker with legitimate ownership of one org's GitHub App/webhook secret (zero privilege on the victim org, no Shipit session, no `ApiClient` token, no `api_clients_secret`, no GitHub App private key for the victim, no repository write access to the victim repo) can:
- Force out-of-band `GithubSyncJob` runs against arbitrary stacks belonging to unrelated organizations (`push` event).
- Inject forged CI/status data (`status` event, completely unscoped by repository) for any commit SHA it can learn (SHAs are typically public), which can flip a target commit's aggregate state to `success` and trigger an **unauthorized deploy** via `ContinuousDeliveryJob` on stacks with `continuous_deployment` enabled — matching the Critical impact criterion "unauthorized deploy."
- Manipulate `merge_status`/PR provisioning state via `PullRequest::*` handlers on repos it doesn't own (archive/unarchive review stacks, capture forged labels, etc.).

This is a direct analog of the reported bug class: a value used for one binding check (`reserve0` checked twice instead of `reserve0`/`reserve1`) that silently drops enforcement of the second, distinct value — here, "authenticate as org X" is silently divorced from "act on repo/commit belonging to org X."

### Likelihood Explanation
Requires only that the target deployment configures more than one GitHub organization (an explicitly documented, supported configuration in `docs/setup.md`), and that the attacker legitimately controls one of those orgs' GitHub Apps (their own `webhook_secret`, obtainable from their own App's settings — not the victim's). No privileged Shipit credentials, TLS interception, or social engineering are needed; the attacker only crafts and signs an HTTP POST to the public `/webhooks` endpoint.

### Recommendation
After signature verification succeeds, verify that the organization used to select the signing secret (`repository_owner`) matches the owner encoded in every field the handlers subsequently trust (`repository.full_name`, and any commit/stack resolved via `sha`). Concretely:
- In `WebhooksController`, reject the request if `repository_owner` does not match the owner portion of `repository.full_name` (when both are present).
- In `Handlers::StatusHandler`, scope the `Commit.where(sha:)` lookup by the repository derived from the verified organization (join through `stack.repository.owner`), rather than searching the whole database.
- More generally, make every handler validate that the resolved `Repository`'s `owner` equals the organization whose secret validated the request.

### Proof of Concept
Illustrative forged `status` webhook (assuming attacker knows their own org "attacker-org"'s `webhook_secret`, and knows a victim commit SHA `abcdef123456` belonging to `victim-org/victim-repo`'s Shipit stack with `continuous_deployment: true`):

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1 of body using attacker-org's known webhook_secret>

{
  "sha": "abcdef123456",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```

`verify_signature` resolves `repository_owner = "attacker-org"`, fetches attacker-org's `GithubApp`, and the signature validates because the attacker legitimately knows that secret. `StatusHandler#process` then runs `Commit.where(sha: "abcdef123456")` with no relation to `attacker-org` at all, applying the forged `success` status to the victim commit and potentially triggering `ContinuousDeliveryJob` on `victim-org`'s stack: [5](#0-4) [9](#0-8)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
