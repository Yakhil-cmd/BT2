### Title
`StatusHandler#process` updates `Commit#status` for every stack sharing a SHA, bypassing webhook repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` globally instead of scoping to the webhook-authenticated repository's stacks via `Handler#stacks`. Any signed `status` webhook from a repository the attacker controls can create a `Status` on commits belonging to unrelated stacks/tenants that happen to share the same commit SHA.

### Finding Description
The intended binding is: `Handler#stacks` (i.e., `Repository.from_github_repo_name(repository_name).stacks`, scoped by the webhook's authenticated `repository.full_name`) should equal the set of stacks whose `Commit` rows receive a new `Status`.

Tracing the code:
- `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
- `verify_signature` only checks that the payload's signature matches the secret for `repository_owner` (`params.dig('repository','owner','login')`) — it authenticates that *some* repository under that owner sent a legitimately signed payload for that owner's app installation, but does not further restrict what data the handler is allowed to touch [2](#0-1) .
- `Handler` base class defines `stacks`, explicitly scoped to `Repository.from_github_repo_name(repository_name)&.stacks`, i.e., the repository named in the payload [3](#0-2) .
- However, `StatusHandler#process` never calls `stacks`. It instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a query across the entire `commits` table with no repository/stack filter at all [4](#0-3) .
- `Commit#create_status_from_github!` unconditionally creates a `Status` row via `statuses.replicate_from_github!(stack_id, github_status)` and triggers `Hook.emit(:commit_status, ...)` / `stack.schedule_merges` for whichever stack that commit belongs to [5](#0-4) [6](#0-5) .

Root cause: the binding `stacks == { stacks of commits receiving new Status }` is false. `stacks` (repository-scoped) is computed by the base `Handler` but ignored by `StatusHandler`; the actual set of affected stacks is `Commit.where(sha: params.sha).map(&:stack)`, which can include stacks belonging to entirely different repositories/tenants whenever a `Commit.sha` collides — most trivially with well-known, byte-identical SHAs like the empty tree/initial commit `4b825dc642cb6eb9a060e54bf8d69288fbee490`, but also possible whenever two different forks/branches happen to record the same commit (e.g., a shared upstream commit imported into multiple stacks, or a cherry-pick/rebase producing identical SHAs across repos tracked as separate stacks).

None of the existing guards prevent this: `verify_signature` only proves payload authenticity for the sending repository's owner, not that the handler's DB writes are scoped to that repository; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in `StatusHandler.params` validates `sha`/`state`/etc. types but has no repository-scoping constraint; there is no `require_permission!` or repository check inside `StatusHandler#process` itself.

### Impact Explanation
An attacker who owns/controls any GitHub repository configured with Shipit (or any repo whose webhook can reach the Shipit `/webhooks` endpoint with a valid signature for that repo's owner) can send a `status` event referencing a SHA that also exists as a `Commit` row in another tenant's stack. This causes a `Status` (e.g., `state: success`) to be written against that unrelated stack's commit, potentially marking it deployable and triggering `stack.schedule_merges` / continuous delivery for a stack the attacker never authenticated against. This is a cross-tenant write: "a payload for one repository mutating another's stack, commit... " — matching the Critical impact category. The blast radius scales with the number of stacks sharing a commit (N stacks), and is repeatable for every subsequent webhook the attacker sends.

### Likelihood Explanation
Preconditions: the attacker needs a webhook that passes `verify_signature` for *some* repository owner they control (easy — any repo they own with Shipit's GitHub App/webhook configured), and a target `Commit.sha` that also exists in another stack's `commits` table. The empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee490` is deterministic and identical across all git repositories, so simply creating an empty initial commit in a stack under attacker control guarantees a SHA collision with any other stack that also happens to have recorded that same commit (common for repos initialized without `--initial-branch` history divergence, or any commit cherry-picked identically). Even absent the empty-commit trick, any commit shared across forks (common in monorepo/fork workflows) collides. Cost to the attacker is minimal: one signed webhook POST, no privileged Shipit session or team membership required.

### Recommendation
Scope `StatusHandler#process` to only operate on commits belonging to the webhook-authenticated repository's stacks, e.g., filter by `stacks` (as defined in the base `Handler`) in addition to `sha`:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This enforces the same repository-scoping invariant already established by `Handler#stacks` and used by other handlers.

### Proof of Concept
Minitest plan (under `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack` fixtures backed by two different `Repository` records with different `github_repo_name` (e.g., `owner-a/repo-a` and `owner-b/repo-b`).
2. Create a `Commit` row under each stack with the identical `sha` (e.g., `4b825dc642cb6eb9a060e54bf8d69288fbee490`).
3. POST a signed `status` webhook payload referencing `repository.full_name = owner-a/repo-a`, `sha = 4b825dc642cb6eb9a060e54bf8d69288fbee490`, `state: success` to `/webhooks`, with a valid signature for `owner-a`.
4. Assert the equality that should hold but doesn't: `stacks_from_payload = Repository.from_github_repo_name('owner-a/repo-a').stacks` (size 1) vs. `stacks_receiving_status = Commit.where(sha: sha).map(&:stack).uniq` (size 2).
5. Assert `commit_a.reload.status.success?` is true (expected, same repo) AND `commit_b.reload.status.success?` is also true (unexpected — `commit_b` belongs to `owner-b/repo-b`, which never sent/authenticated this webhook), proving the cross-tenant write.
