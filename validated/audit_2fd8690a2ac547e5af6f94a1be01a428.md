### Title
Webhook signature verification is scoped by `repository.owner.login` while event handlers act on the unrelated `repository.full_name`, letting an attacker who controls one onboarded GitHub organization forge events (including CI status) against any other tracked stack — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate the inbound webhook HMAC based on `repository_owner`, a field read out of the very same untrusted JSON body being verified. [1](#0-0)  That field is `params.dig('repository', 'owner', 'login')` (or `organization.login` as fallback). [2](#0-1)  Every webhook handler, however, resolves the target repository/stack from a *different* key of the same payload: `payload.dig('repository', 'full_name')`. [3](#0-2)  The signature never binds these two fields together, so the "organization that authenticated" and the "repository that is written" can be made to diverge.

### Finding Description
Shipit supports multiple GitHub Apps, one per organization, each with its own `webhook_secret` configured under `github.<org>.webhook_secret`. [4](#0-3)  A person who legitimately owns/administers one such organization's GitHub App (an "unprivileged attacker" with respect to every *other* org tracked by the same Shipit instance) knows that org's `webhook_secret` and can compute a valid `X-Hub-Signature` HMAC over an arbitrary raw body of their own choosing.

`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login')`. [5](#0-4)  An attacker sets this field to their own org, so `Shipit.github` returns their own `GithubApp` instance, and their self-computed HMAC over the full attacker-chosen JSON body verifies successfully.

Once verification passes, `create` dispatches the **entire raw payload** to handlers unmodified:
```ruby
params = JSON.parse(request.raw_post)
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [6](#0-5)  Handlers derive the *target* repository from `repository.full_name`, not `repository.owner.login`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

Because nothing checks that `repository.owner.login` (used to pick the signing key) is consistent with `repository.full_name` (used to pick the acted-upon repository), the attacker can set `repository.owner.login` to their own org (to pass signature verification) and `repository.full_name`/`sha` to values belonging to a completely different, victim organization's stack.

The most severe consequence is via `StatusHandler`, which is fully global and doesn't even need `repository.full_name` to match — it looks up commits **by SHA across the entire install**:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [8](#0-7)  The attacker fully controls `params.state` (e.g. `"success"`), since the only thing gating the request is a signature computed with the attacker's *own* org secret. Creating a `Status` record fires:
```ruby
after_create :enable_ci_on_stack
after_commit :schedule_continuous_delivery, :broadcast_update, on: :create
``` [9](#0-8)  `schedule_continuous_delivery` is exactly the trigger used to kick off automatic deployment when CI turns green. [10](#0-9)  This lets an attacker forge a "green CI" signal for any commit SHA already known to them (e.g. discoverable from a stack's public commit history) belonging to a victim stack in an unrelated organization, and have Shipit enqueue a continuous-delivery/deploy for that stack — despite never having compromised that victim organization's GitHub App, webhook secret, or Shipit credentials.

### Impact Explanation
This crosses the exact organization-boundary binding called out by the rules: the organization whose key authenticated the HTTP request is not required to equal the repository/stack the request is allowed to mutate. The concrete outcome — forging a passing CI status to trigger `schedule_continuous_delivery` on a stack owned by an organization the attacker has no access to — is an **unauthorized deploy**, which is explicitly listed as a Critical impact.

### Likelihood Explanation
Any user who is legitimately an admin of even one GitHub organization onboarded to a shared, multi-org Shipit instance (a completely unprivileged position with respect to every other org on that instance) can exploit this with a single crafted HTTP POST to `/webhooks`; no GitHub write access, Shipit session, or `ApiClient` token is required. The only prerequisite is knowledge of the victim commit SHA, which is typically public (commit hashes are visible in PRs/branches) or can be inferred from status/push events the attacker already receives for stacks visible to them.

### Recommendation
Bind webhook-event handling to the organization/app that actually verified the signature: derive the repository owner used for the App lookup from the same value used for stack resolution (e.g., verify that `repository.owner.login` used for signature selection equals the owner portion of `repository.full_name`, or better, have handlers resolve the target stack scoped to the already-verified organization instead of trusting `repository.full_name` independently). Reject any request where these fields disagree.

### Proof of Concept
1. Attacker administers `attacker-org`, which is legitimately configured in `config/secrets.yml` under `github.attacker-org.webhook_secret`.
2. Attacker builds a JSON body:
```json
{
  "sha": "<victim-stack-known-commit-sha>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org-webhook-secret, body)`.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and the above signature/body.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches the attacker's own `GithubApp`, and the HMAC validates successfully. [5](#0-4) 
6. `StatusHandler#process` matches `Commit.where(sha: ...)` against the victim's commit (irrespective of the `attacker-org` used for signing) and creates a `success` `Status`, triggering `schedule_continuous_delivery` on the victim's stack. [8](#0-7) [9](#0-8)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
