### Title
Attacker-controlled PR label named `ENVIRONMENT` overwrites the review stack's real `ENVIRONMENT` deploy variable - (File: `app/models/shipit/review_stack.rb`)

### Summary
`Shipit::ReviewStack#env` merges GitHub PR labels (upper-cased, unfiltered attacker input) on top of the base `Shipit::Stack#env` hash. Because label names become env-var keys with the fixed value `"true"`, an attacker who labels their own PR `ENVIRONMENT` overwrites the trusted `'ENVIRONMENT' => environment` entry, and that clobbered value is carried unfiltered through `TaskCommands#env`/`DeployCommands#env` into `Command#unbundled_env` and `Command#interpolate_environment_variables`, changing what `$ENVIRONMENT` expands to in any deploy step.

### Finding Description
The broken binding: the value interpolated for `$ENVIRONMENT` in a deploy step should equal `stack.environment` (e.g. `"pr123"`), the value assigned at review-stack provisioning time. This equality is broken as follows:

- `Shipit::Stack#env` builds the canonical env hash including `'ENVIRONMENT' => environment` [1](#0-0) .
- `Shipit::ReviewStack#env` calls `super` to get that hash, then merges in a hash derived from `pull_request.labels`, using each label name upcased as the key and the literal string `"true"` as the value, with no filtering of key names against reserved keys: [2](#0-1) .
- `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` writes the raw label names from the incoming, attacker-controlled webhook payload (`pull_request.labels[].name`) directly onto `pull_request.labels` with no name transformation, blocklist, or reserved-word check: [3](#0-2) . This handler fires on `opened`/`labeled`/`unlabeled`/`reopened` PR actions against any active (non-archived) review stack, requiring only that the attacker control a pull request against the repo (e.g. their own fork's PR, or their own repo if they're testing against it) — no Shipit session, token, or team membership.
- `TaskCommands#env` merges `@stack.env` into the full command environment without any whitelist/permit step: [4](#0-3) . `DeployCommands#env` further merges on top without restoring `ENVIRONMENT`: [5](#0-4) .
- `Command#interpolate_environment_variables` / `EnvironmentVariables#interpolate` substitute `$ENVIRONMENT` in any command-line argument using this same overwritten `@env` hash before `PTY.spawn`: [6](#0-5) [7](#0-6) [8](#0-7) .

Why existing guards don't help: `EnvironmentVariables#permit`/`sanitize_env_vars` is only invoked via `filter_deploy_envs`/`filter_task_envs` on the **user-supplied override** passed to `trigger_deploy`/`trigger_task` (`Stack#build_deploy`, `Stack#trigger_task`), which becomes `@task.env` — a separate, later merge key in `TaskCommands#env`. The base `@stack.env` (where the label-clobbered `ENVIRONMENT` lives) is merged earlier and is never passed through `permit`/whitelist logic at all, so there is no filtering step that would catch or block the collision. The webhook signature check (`verify_signature`) only authenticates that the payload came from GitHub for the target repo — it does not, and cannot, prevent an authorized PR author from choosing the label text `ENVIRONMENT` on their own PR.

Attacker request: on a repository with Shipit review stacks enabled, open (or already have open) a PR and add a label literally named `ENVIRONMENT` (any case, since `.upcase` normalizes it) via the standard GitHub UI/API, which GitHub relays to Shipit's `pull_request` webhook (`labeled` action). No Shipit credentials are needed — only permission to label your own PR, which any contributor to a repo (or owner of the repo in scope) has.

### Impact Explanation
Once the label is applied, any subsequent deploy/rollback/task step for that review stack that interpolates `$ENVIRONMENT` (e.g. `cap $ENVIRONMENT deploy`) executes with `ENVIRONMENT=true` instead of `ENVIRONMENT=pr<number>`, causing Capistrano (or any interpolating tool) to run against a stage named `true` or whatever stage capistrano falls back/resolves to — potentially a shared/default stage or another tenant's stage name if it happens to collide. This is an unauthorized deploy/rollback target executed on the deploy host, matching the "unauthorized deploy, rollback" Critical category. It is repeatable on every deploy/task run of that review stack for as long as the label remains, and requires no elevated privileges — only the ability to label a PR in a repo with review stacks enabled.

### Likelihood Explanation
Preconditions are modest: the repository must have review stacks configured (a common Shipit feature), the attacker needs permission to label a PR (trivial for repo collaborators, and for open-source repos sometimes any contributor via triage-level access or bot labeling), and a deploy step in the `.shipit.yml` deploy spec that interpolates `$ENVIRONMENT`. No secrets, tokens, or Shipit-side authentication bypass are needed. Cost to the attacker is a single GitHub label action.

### Recommendation
In `Shipit::ReviewStack#env`, reject/strip label-derived keys that collide with reserved stack env keys (`ENVIRONMENT`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `LAST_DEPLOYED_SHA`, `BRANCH`), or merge labels first and `Stack#env` second (i.e., `super.merge(labels_hash)` → swap merge order so the canonical values always win), or namespace label-derived variables (e.g. prefix with `LABEL_`) so they cannot collide with reserved names.

### Proof of Concept
In `test/models/shipit/review_stack_test.rb` (or a new deploy_commands test), add a minitest:

```ruby
test "#env: a label named ENVIRONMENT overwrites the stack's real ENVIRONMENT value" do
  stack = shipit_stacks(:cyclimse) # or any ReviewStack fixture with environment == "pr123"
  stack.pull_request.update!(labels: ['ENVIRONMENT'])

  assert_equal 'true', stack.env['ENVIRONMENT']
  refute_equal stack.environment, stack.env['ENVIRONMENT']
end

test "DeployCommands#env carries the clobbered ENVIRONMENT through to Command interpolation" do
  deploy = shipit_deploys(:review_stack_deploy) # deploy on a ReviewStack fixture
  deploy.stack.pull_request.update!(labels: ['ENVIRONMENT'])

  commands = DeployCommands.new(deploy)
  assert_equal 'true', commands.env['ENVIRONMENT']

  command = Command.new('cap $ENVIRONMENT deploy', env: commands.env, chdir: '/tmp')
  assert_equal 'cap true deploy', command.interpolate_environment_variables('cap $ENVIRONMENT deploy')
end
```

Both assertions demonstrate the equality `stack.env['ENVIRONMENT'] == stack.environment` (expected) is broken to `stack.env['ENVIRONMENT'] == 'true'` (actual) purely via an attacker-controlled PR label, with the divergence flowing unmodified into the interpolated command line executed via `PTY.spawn`.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
