### Title
Uncapped per-partition stake-reward-distribution work at high delegation counts due to `MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH` clamp in `get_reward_distribution_num_blocks` - ([File: runtime/src/bank/partitioned_epoch_rewards/mod.rs])

### Summary
`get_reward_distribution_num_blocks` computes `num_partitions` as `total_stake_accounts.div_ceil(stake_account_stores_per_block)`, but then clamps this value to a maximum of `slots_per_epoch / 10`. Once the number of delegated stake accounts grows large enough that the "ideal" chunk count exceeds this cap, the returned `num_partitions` stops scaling with `total_stake_accounts`, while `hash_rewards_into_partitions`/`epoch_rewards_hasher::hash_rewards_into_partitions` still scatters *all* stake rewards pseudo-randomly across that fixed, capped number of buckets, so the average (and each) partition's size grows unboundedly with `total_stake_accounts` instead of staying near `stake_account_stores_per_block`.

### Finding Description
The distribution-block count is computed in `get_reward_distribution_num_blocks`: [1](#0-0) 

`num_chunks` is the number of blocks needed if each block stored exactly `stake_account_stores_per_block` accounts, but the final `.clamp(1, slots_per_epoch/10)` throws away that relationship once `total_stake_accounts` is large enough. `num_partitions` (the clamped value) is what's stored in the `EpochRewards` sysvar and later fed into `hash_rewards_into_partitions`, both at initial calculation time (`begin_partitioned_rewards`) and at recalculation time (`recalculate_stake_rewards`): [2](#0-1) [3](#0-2) 

`hash_rewards_into_partitions` assigns each stake reward to one of exactly `num_partitions` buckets via `EpochRewardsHasher::hash_address_to_partition`, with no per-bucket size limit: [4](#0-3) 

Each of the resulting `num_partitions` buckets is then processed as a single "partition" of work in exactly one block by `distribute_partitioned_epoch_rewards`/`store_stake_accounts_in_partition`, with no re-chunking or additional per-block cap applied at that stage: [5](#0-4) 

Because `num_partitions` is capped at `slots_per_epoch / 10` regardless of how large `total_stake_accounts` becomes, once `total_stake_accounts > stake_account_stores_per_block * (slots_per_epoch / 10)`, the average partition size is `total_stake_accounts / (slots_per_epoch / 10)`, which grows linearly and unboundedly with the number of stake accounts an attacker creates. The `stake_account_stores_per_block` constant (`MAX_PARTITIONED_REWARDS_PER_BLOCK` = 4096, or a smaller derived value for shorter slot-time configurations) is therefore only an effective per-block bound while `total_stake_accounts` is below the cap threshold; above it, the invariant "epoch-boundary work is bounded and cannot be inflated by attacker-created delegations" no longer holds. `get_minimum_delegation` shows the current minimum stake needed to create a valid delegated stake account is 1 SOL (or effectively 1 lamport when the v5 stake program feature is inactive), plus the rent-exempt reserve, meaning an attacker with sufficient (but bounded, non-privileged) capital can create enough stake accounts to push `total_stake_accounts` far past the cap threshold and inflate per-block work in the mandatory reward-distribution phase that every validator must execute at the epoch boundary: [6](#0-5) 

The signer/authority/rent-exemption checks on stake-account creation and delegation are irrelevant here — the exploit does not bypass any of them; it merely uses unprivileged, protocol-legal actions (create N stake accounts, delegate minimum stake) at scale, and the vulnerable clamp logic then fails to keep per-block work bounded.

### Impact Explanation
Because `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` runs unconditionally as part of block production/replay at the epoch boundary (not subject to a normal transaction compute-unit budget), and every partition must be fully processed within its single allotted block, an attacker who inflates the average partition size well beyond `stake_account_stores_per_block` can cause that block's reward-distribution work to take substantially longer than the 400 ms-class budget the constant was designed around. This is a cluster-liveness class issue: slow/incomplete processing of the mandatory reward-distribution block can cause block-production delays, cross-node timing divergence (since the same deterministic partitioning work must be done by every validator, but the wall-clock cost scales with attacker-inflated delegation count rather than the intended fixed bound) or contribute to the network stalling/halting at scale.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: fund and own N stake accounts, delegate the minimum viable amount to any vote account, and wait for the epoch boundary — all via ordinary `CreateAccount`/`DelegateStake` instructions, no validator/leader/gossip control needed. Feasibility scales with capital: at `MINIMUM_DELEGATION_SOL = 1` plus rent-exempt reserve per account, inflating partitions meaningfully beyond the cap threshold (`stake_account_stores_per_block * slots_per_epoch/10`, e.g. 4096 * 43200 = ~177M for a full 432,000-slot epoch) requires very large numbers of accounts and correspondingly large capital/rent outlay, making this a real but capital-intensive attack; it is fully repeatable, deterministic, and does not depend on timing races, since any validator can independently create the accounts across as many slots as needed before the epoch boundary.

### Recommendation
Remove or redesign the `slots_per_epoch / 10` upper clamp on `num_partitions` so that the number of reward-distribution blocks continues to scale with `total_stake_accounts` (bounded instead by a hard maximum number of blocks combined with a hard maximum accounts-per-block, with any excess spread across additional blocks rather than compressed into the capped block count), or otherwise ensure that `hash_rewards_into_partitions` never produces a bucket larger than `stake_account_stores_per_block`, splitting oversized buckets into multiple sub-partitions/blocks if the epoch does not have enough slots to keep per-block work bounded. Any solution must guarantee `avg_partition_size = total_stake_accounts / num_partitions <= stake_account_stores_per_block` independent of `total_stake_accounts`.

### Proof of Concept
Rust unit test (extending existing tests in `runtime/src/bank/partitioned_epoch_rewards/mod.rs`, following `test_get_reward_distribution_num_blocks_cap`):
```rust
#[test]
fn test_get_reward_distribution_num_blocks_unbounded_partition_size() {
    // Use a small epoch so the 10% cap kicks in early.
    let (mut genesis_config, _mint_keypair) = create_genesis_config(1_000_000 * LAMPORTS_PER_SOL);
    genesis_config.epoch_schedule = EpochSchedule::custom(32, 32, false);

    let mut accounts_db_config: AccountsDbConfig = ACCOUNTS_DB_CONFIG_FOR_TESTING;
    accounts_db_config.partitioned_epoch_rewards_config =
        PartitionedEpochRewardsConfig::new_for_test(10); // stake_account_stores_per_block = 10

    let bank = Bank::new_from_genesis(
        &genesis_config, Arc::new(RuntimeConfig::default()), Vec::new(), None,
        accounts_db_config, None, Some(SlotLeader::new_unique()), Arc::default(), None, None,
    );
    // cap = slots_per_epoch / 10 = 3 blocks max

    let check = |num_stakes: u64| {
        let stake_rewards = (0..num_stakes)
            .map(|_| Some(PartitionedStakeReward::new_random()))
            .collect::<PartitionedStakeRewards>();
        let num_partitions = bank.get_reward_distribution_num_blocks(&stake_rewards);
        let avg_partition_size = num_stakes / num_partitions.max(1);
        (num_partitions, avg_partition_size)
    };

    // At small scale, average per-partition size stays <= stake_account_stores_per_block (10).
    let (_, avg_small) = check(30);
    assert!(avg_small <= 10);

    // At attacker-inflated scale (e.g. 1,000,000 stake accounts), num_partitions
    // is still capped at 3, so avg_partition_size vastly exceeds 10 -- demonstrating
    // that per-block work is NOT bounded by stake_account_stores_per_block.
    let (num_partitions_large, avg_large) = check(1_000_000);
    assert_eq!(num_partitions_large, 3); // capped, independent of attacker-created count
    assert!(avg_large > 10); // invariant violated: per-block work exceeds configured bound
    assert!(avg_large >= 300_000); // grows linearly with attacker-created delegation count
}
```
Expected result: this test demonstrates that `num_partitions` saturates at the epoch-based cap while `avg_partition_size` (and hence the work `store_stake_accounts_in_partition` must do in a single block) grows without bound as a function of attacker-created stake-account count, violating the intended invariant that `stake_account_stores_per_block` bounds per-block work regardless of the number of attacker-created delegations. A companion integration test could drive `create_reward_bank_with_specific_stakes` with a very small `stake_account_stores_per_block` and a large synthetic delegation count, then measure wall-clock time of `distribute_partitioned_epoch_rewards` for the first distribution block to confirm it scales with total delegation count rather than staying near the configured per-block baseline.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

pub(in crate::bank::partitioned_epoch_rewards) fn hash_rewards_into_partitions(
    stake_rewards: &PartitionedStakeRewards,
    parent_blockhash: &Hash,
    num_partitions: usize,
) -> Vec<Vec<usize>> {
    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

    for (i, reward) in stake_rewards.enumerated_rewards_iter() {
        // clone here so the hasher's state is reused on each call to `hash_address_to_partition`.
        // This prevents us from re-hashing the seed each time.
        // The clone is explicit (as opposed to an implicit copy) so it is clear this is intended.
        let partition_index = hasher
            .clone()
            .hash_address_to_partition(&reward.stake_pubkey);
        indices[partition_index].push(i);
    }
    indices
}
