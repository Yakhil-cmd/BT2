### Title
Webhook signature verification keys on `repository.owner.login` while all event handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository.owner.login` (with a fallback to `organization.login`) taken from the unauthenticated request body. Every event handler, however, resolves the target `Stack`/`Repository` using a *different* field from the very same JSON body: `repository.full_name`. Because the signature only proves "this byte-stream was HMAC-signed with organization X's secret," and never binds `repository.owner.login` to `repository.full_name`, an attacker who knows (or controls) one organization's `webhook_secret` can craft a payload whose `owner.login` matches that organization (so verification passes) while `full_name` names a repository belonging to a completely different, unrelated organization onboarded onto the same Shipit instance.

### Finding Description
- `verify_signature` looks up `repository_owner` from the unverified body and uses it purely to pick which app config's secret to check the signature against: [1](#0-0) [2](#0-1) 
- `Shipit.github(organization:)` looks up per-organization app config only when the multi-org schema is in use (`github_default_organization` is non-nil, i.e. `config/secrets.yml` has multiple top-level org keys as documented in `docs/setup.md`): [3](#0-2) 
- `GitHubApp#verify_webhook_signature` only proves the raw body bytes were HMAC-signed by whichever secret was selected — it says nothing about which fields of that body should be trusted for downstream authorization decisions: [4](#0-3) 
- Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) inherits `Handler#stacks`/`#repository_name`, which resolves the target repository from `repository.full_name` — a field never checked against `repository.owner.login`: [5](#0-4) 
- `Repository.from_github_repo_name` splits `owner/name` straight out of that `full_name` string and looks up the DB record with no cross-check to the org used for signature verification: [6](#0-5) 

This is the same "guard checks A but the acted-upon value is B" pattern as the Curve reentrancy report: the signature "passing" is treated as proof that the whole payload is trustworthy for organization X, but the field actually consumed downstream (`full_name`) is never covered by that binding. The equality that should hold and does not is: `organization whose secret verified the signature == organization that owns the repository the handler mutates state for`.

### Impact Explanation
An operator running Shipit with the multi-organization GitHub App schema (`config/secrets.yml` with per-org `webhook_secret`s, as documented for supporting multiple orgs) onboards Organization A and Organization B onto the same instance. A user who legitimately controls Organization A's GitHub App/webhook configuration (i.e., knows Org A's `webhook_secret`) can POST directly to `/github/webhooks` with a body where `repository.owner.login` = `"orga"` (so `Shipit.github(organization: "orga")`'s secret verifies) but `repository.full_name` = `"orgb/target-repo"`. This lets the attacker:
- Trigger `PushHandler#process` → `stack.sync_github(expected_head_sha:)` for Org B's stacks, forcing sync/build against an attacker-chosen `after` SHA. [7](#0-6) 
- Forge CI status for Org B's commits via `StatusHandler#process`/`Commit#create_status_from_github!`, which can flip commits to `success` and unblock continuous delivery gating for a repository the attacker has no access to. [8](#0-7) 

This crosses the repository/organization trust boundary the signature is supposed to enforce and can lead to spoofed CI signals feeding into unattended/continuous deploys of a stack the attacker does not own — this is a cross-repository write / unauthorized deploy trigger.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with the multi-organization GitHub App schema, and (2) the attacker knowing/controlling at least one onboarded organization's `webhook_secret` (which is normal for any org that legitimately integrates with a shared Shipit instance, since they must supply that secret when their GitHub App is configured). No repository write access, `ApiClient` token, or session on Shipit is needed — only the ability to send a raw HTTP POST with a self-crafted, self-signed body. This is a realistic misconfiguration-adjacent scenario for the documented multi-org deployment mode, though not applicable to the single-org/default schema where `organization:` is ignored.

### Recommendation
Bind the two fields at verification time: require that `repository.full_name.split('/').first` matches `repository.owner.login` (or `organization.login`) before accepting the payload, or better, derive the verifying organization strictly from `repository.full_name`'s owner segment so a single value in the payload governs both signature-key selection and downstream repository resolution.

### Proof of Concept
1. Configure Shipit with multi-org schema, Org A (`orga`, `webhook_secret: secretA`) and Org B (`orgb`) both having stacks configured.
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(secretA, body)>` (attacker knows `secretA` because it is Org A's own webhook secret).
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` selects `Shipit.github(organization: "orga")`, verifies successfully against `secretA` [1](#0-0) .
6. `PushHandler` resolves `Repository.from_github_repo_name("orgb/target-repo")` and calls `sync_github` on Org B's stacks [7](#0-6)  — despite the signature only proving knowledge of Org A's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
