Confirmed root cause: the webhook signature-verification step and the repository-resolution step in this engine derive their trust decision from **two different, independently-controlled fields of the same unauthenticated JSON payload**, and nothing binds them together.

### Title
Webhook organization used for signature verification is never bound to the `repository.full_name` acted upon, allowing cross-tenant event forgery in multi-org installs - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit installation (`Shipit.github_organizations` > 1, i.e. `secrets.github` keyed by org), `WebhooksController#verify_signature` picks which `GitHubApp`/`webhook_secret` to validate the HMAC against using `repository_owner`, which is read directly from the **unauthenticated** JSON body (`params.dig('repository','owner','login')`), before the signature has been checked. The handlers that subsequently act on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`, `PushHandler`, `StatusHandler`, `PullRequest::*Handler`) resolve the target `Stack`/`Repository` from a **separate** field of the same payload, `payload.dig('repository','full_name')`. Nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository being mutated.

### Finding Description [1](#0-0) 
`verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)`. `repository_owner` is: [2](#0-1) 
i.e. taken from `repository.owner.login` in the raw body itself — a value the sender fully controls.

`Shipit.github` resolves per-org config purely by that string: [3](#0-2) 

Handlers never re-check that the organization used to select the webhook secret matches the repository they operate on; they derive the target repository independently from `repository.full_name`: [4](#0-3) 

This is structurally identical to the reported bug class: the code path that performs the "authorization" check (HMAC verification keyed by claimed-org) and the code path that performs the "write" (resolving/mutating a `Stack` for `repository.full_name`) consume different fields of attacker-controlled input, and the binding `authenticated_organization == acted_upon_repository_owner` is never asserted — exactly the “organization that authenticated versus the repository that is written” inequality called out in scope.

### Impact Explanation
An attacker who legitimately owns/administers **their own** GitHub organization/App installation on the same Shipit instance (and therefore knows *their own* `webhook_secret`) can craft a webhook payload where `repository.owner.login` is set to their own org (so `verify_webhook_signature` succeeds against their own secret) while `repository.full_name` is set to `victim-org/victim-repo`. Because the two fields are never cross-checked, this forged, validly-"signed" payload is dispatched to handlers that resolve and mutate state for the victim repository's `Stack` — e.g. `PushHandler`/`GithubSyncJob` triggers a resync of commits for that stack, `StatusHandler` creates commit statuses on arbitrary commits, `PullRequest::*Handler`s manipulate `MergeRequest`/`PullRequest` records and labels for the victim stack, and `MembershipHandler` can create/delete `Team`/`Membership` records. This is a cross-repository/cross-tenant write achieved without ever possessing the victim organization's secret, satisfying the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (`secrets.github` with multiple org keys, per `github_default_organization`/`github_app_config`), and requires the attacker to control at least one legitimate GitHub App installation/org configured on that same instance — a realistic scenario for shared/hosted Shipit deployments serving multiple tenants. No repository write access, Shipit session, or API token is needed; only knowledge of the attacker's own webhook secret, which they are entitled to as an org admin of their own tenant.

### Recommendation
In `WebhooksController#verify_signature` / `Handler#stacks`, enforce that the organization used to resolve the `GitHubApp` (and thus the webhook secret) equals the owner of `repository.full_name` (and equals `organization.login` for org-level events) before dispatching to handlers. Concretely, compare `repository_owner` against `payload.dig('repository','full_name')&.split('/')&.first` (and `payload.dig('organization','login')`) and reject (422) on mismatch, so the authenticated tenant cannot spoof a different tenant's repository.

### Proof of Concept
1. Attacker administers GitHub org `attacker-org`, installed on the shared Shipit instance with `webhook_secret = S`.
2. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<victim commit sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker signs the raw body with `S` and sets `X-Hub-Signature: sha1=<hmac>`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `verify_webhook_secret` succeeds because the attacker used their own valid secret `S`.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which uses `Handler#stacks` → `Repository.from_github_repo_name("victim-org/victim-repo")` — acting on the victim's stack despite the signature having been validated for `attacker-org`, not `victim-org`. [4](#0-3) [5](#0-4)

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
