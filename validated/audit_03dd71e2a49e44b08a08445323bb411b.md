### Title
`pull_request` webhook signature verified against attacker-chosen no-secret org while handler mutates a different org's stack - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/org config to use for HMAC verification based solely on `params.dig('repository','owner','login')`, while every `pull_request` handler (including `LabelCapturingHandler` and `ReopenedHandler`) resolves the actual target repository/stack from the independent field `params.repository.full_name`. Since `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org has no `webhook_secret` configured, an attacker can pick an unconfigured/no-secret org as `repository.owner.login` to trivially pass signature verification, while pointing `repository.full_name` at a victim org's repo whose stack is then mutated.

### Finding Description
The broken binding is: `repository_owner (used to select signing secret) == repository.full_name's owning org (whose stack is mutated)`. These are two independently attacker-controlled JSON fields with no consistency check between them.

Code path:
1. `WebhooksController#verify_signature` picks the GitHub App config via `Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` if that org's config has no `webhook_secret` set: `return true unless webhook_secret`. [3](#0-2) 
3. Once verification passes, `WebhooksController#create` dispatches the full raw JSON `params` (not filtered by owner) to every registered `pull_request` handler. [4](#0-3) 
4. Handlers such as `LabelCapturingHandler` and `ReopenedHandler` resolve the target `Repository`/`Stack` exclusively from `params.repository.full_name`, never re-checking `repository.owner.login`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. [5](#0-4) [6](#0-5) 
5. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` directly onto the resolved `PullRequest`. [7](#0-6) 
6. `ReviewStack#env` later folds those persisted label names into environment variables merged into deploy/task execution: `labels[label_name.upcase] = "true"`. [8](#0-7) 
7. `ReopenedHandler#process` calls `stack.unarchive!` on the resolved (victim) stack when the payload's `action == "reopened"`. [9](#0-8) [10](#0-9) 

Attack: attacker registers/controls org `NoSecretOrg` that has no `webhook_secret` in Shipit's GitHub app configuration (or any org for which the operator hasn't configured a secret), and crafts a `pull_request` webhook body with `repository.owner.login = "NoSecretOrg"` but `repository.full_name = "victim-org/victim-repo"`, `action = "reopened"`, and arbitrary `pull_request.labels`. Because `repository_owner` resolves to `NoSecretOrg`, `verify_webhook_signature` returns `true` without ever checking a real signature. The handlers then act on `victim-org/victim-repo`'s stack: capturing attacker-chosen labels onto the victim `PullRequest` and unarchiving/reactivating the review stack, which (per existing review-stack provisioning/deploy automation, run under the configured `bot_login`/`Shipit.user` identity) can trigger deploy actions using attacker-controlled env vars derived from the labels.

Existing guards do not catch this: `drop_unhandled_event` only checks event type presence, not repository consistency; `ExplicitParameters` schemas validate types/presence of `repository.full_name` but never cross-check it against `repository.owner.login`; there is no model validation tying the two fields together in the webhook path. The `GithubOrganizationUnknown` rescue only triggers if the org name is entirely unrecognized — a legitimately configured (but secretless) org bypasses it cleanly.

### Impact Explanation
An unauthenticated attacker, with no Shipit credentials, can write persistent state (`PullRequest#labels`) for a repository/stack they do not own or control, and drive stack-level actions (`unarchive!`) that feed into automated deploy execution running under the target stack's configured bot identity. This is a payload for one repository mutating another repository's stack — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). Since any org lacking a configured `webhook_secret` can serve as the bypass vector, the attack is repeatable against any victim stack whose full_name the attacker knows, regardless of that victim's own secret configuration.

### Likelihood Explanation
Preconditions: (a) at least one org configured in Shipit's GitHub app settings without a `webhook_secret` (or an org the attacker fully controls and can leave unconfigured on their own end if operators allow dynamic per-org config), and (b) knowledge of the victim's `full_name` (public information for any public GitHub repo). No GitHub App private key, `webhook_secret`, or session is needed. The attacker only needs to send a raw HTTP POST to `/webhooks` with a forged JSON body and any `X-Hub-Signature` value (or none) — verification is skipped entirely due to the secretless branch. This is inexpensive and fully repeatable/scriptable against arbitrary stacks.

### Recommendation
Bind signature verification to the same repository that handlers act on: derive the org used for `Shipit.github(organization: ...)` from the repository actually resolved via `params.repository.full_name` (or require `repository.owner.login` and the owner-prefix of `full_name` to match) before verification, and reject requests where they diverge. Additionally, avoid a permissive `return true unless webhook_secret` default — if organizations are meant to be always-secured, missing secret configuration should not silently pass; and require the split of `full_name` to be enforced as `"#{repository.owner.login}/..."` inside `verify_signature`.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb`, using a minitest without live GitHub:
1. Configure fixture github orgs so that org `no-secret-org` has no `webhook_secret` in `Shipit.github_configs`/`Shipit.github(organization:)`, while `shopify` (the fixture victim org owning `shipit_stacks(:shipit)`/its review stack) does have one configured, or use the default `Shipit.github` fixture app that returns `true` without a secret to simulate a "no-secret" org.
2. Build a `pull_request` payload: `{ action: 'reopened', number: <victim pr number>, repository: { owner: { login: 'no-secret-org' }, full_name: 'shopify/<victim-repo>' }, pull_request: { ..., labels: [{name: 'MALICIOUS_ENV'}] }, sender: { login: 'attacker' } }`.
3. Set `request.headers['X-Github-Event'] = 'pull_request'`; POST with no/garbage `X-Hub-Signature`.
4. Assert `assert_response :ok` (signature check passed for `no-secret-org` despite the payload targeting `shopify/<victim-repo>`).
5. Assert the victim `PullRequest#labels` was overwritten to `['MALICIOUS_ENV']` and/or the victim `ReviewStack` was unarchived — demonstrating that `repository_owner` used for signing ≠ the org whose stack (`shopify/<victim-repo>`) was mutated, violating the invariant "a `pull_request` event only affects the repository/stack whose secret authenticated it."

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
