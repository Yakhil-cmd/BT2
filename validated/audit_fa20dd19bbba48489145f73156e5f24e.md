### Title
Unchecked asset lookup causes crash in AA payment composition - (File: aa_composer.js)

### Summary
`completePaymentPayload()` inside `aa_composer.js`'s `sendUnit()` looks up asset metadata from the local `assetInfos` map by an asset identifier taken directly from the AA-composed payment message (`payload.asset`, which ultimately comes from oscript-evaluated data controlled by the AA author / trigger data), and dereferences the lookup result without checking it exists — the same bug class as the reported Linux kernel CVE-2022-49104 (`find_service_by_handle` can return `NULL` and the caller dereferences it unconditionally).

### Finding Description
In `aa_composer.js`, `completePaymentPayload()` uses the asset string from a payment message the AA is about to send, and does a raw `assetInfos[asset]` lookup in three places without a null/undefined check before accessing properties on the result: [1](#0-0) [2](#0-1) [3](#0-2) 

`issueAsset()` is the clearest case: `var objAsset = assetInfos[asset]; if (objAsset.issued_by_definer_only ...)` — if `assetInfos[asset]` is `undefined` (i.e., the asset key was never populated in the `assetInfos` cache for whatever reason — e.g. a stale/incomplete cache population path, an asset referenced only through a formula-computed string that bypasses the code path that populates `assetInfos`, or any other code path in the AA response/payment composition pipeline that fails to guarantee the map is fully populated before `sendUnit` runs), the subsequent `objAsset.issued_by_definer_only` access throws a `TypeError: Cannot read properties of undefined`.

This mirrors the kernel bug class exactly: a handle/key-based lookup (`find_service_by_handle` ↔ `assetInfos[asset]`) that can return `NULL`/`undefined`, followed by an unchecked dereference of the result.

### Impact Explanation
`sendUnit()` executes inside `handleTrigger()`, which is invoked for every AA trigger during unit validation/response composition on **every full node** processing the same unit (it's deterministic, consensus-critical code, not sandboxed per-request). An uncaught `TypeError` thrown deep inside this synchronous call chain (inside a `conn.query` callback, i.e., outside of `try/catch`-guarded oscript evaluation) is not converted into a bounce message — it becomes an unhandled exception. In Node.js this either crashes the node process or (if caught by a top-level handler) desyncs AA response computation, which is consensus-critical: if triggered deterministically by a posted unit, it can cause a chain-wide inability to finalize/confirm the affected MC segment, i.e., a network unable to confirm new units.

### Likelihood Explanation
The `asset` value reaching `completePaymentPayload` originates from AA-authored payment messages that can, in principle, reference asset strings computed from oscript expressions (state vars, trigger data, remote AA responses) rather than being restricted to assets already validated and cached earlier in the same execution. Because the exact set of conditions under which `assetInfos` fails to contain a referenced asset before this stage was not confirmed in the available code index (the population site of `assetInfos` and whether an upstream check strictly guarantees full coverage could not be located/verified within this session), the concrete triggering condition is **not fully proven** — this should be treated as a plausible, high-severity crash path requiring further code tracing (specifically locating every call site that builds `assetInfos` and confirming whether any AA-controlled asset string can escape that population step) before being treated as a confirmed exploit.

### Recommendation
Add explicit existence checks before dereferencing `assetInfos[asset]` in all three locations (`aa_composer.js` lines ~1142, ~1159, ~1176), and if missing, either fail gracefully (bounce the AA trigger with an error) or throw a caught, well-formed validation error instead of allowing an unchecked `TypeError` to propagate out of consensus-critical code.

### Proof of Concept
Not fully reproducible from static analysis alone: reaching the crash requires confirming a concrete path by which `sendUnit()` composes a payment message whose `asset` is not already a key of `assetInfos` at the time `completePaymentPayload` runs (e.g., an AA definition that computes an asset id via `concat`/state var and passes it to a `payment` message with an amount matching a `send-all`/issue scenario). This exact upstream data flow into `assetInfos` was not located within the indexed code in this session, so the PoC is a conceptual/structural one based on the missing null check rather than a confirmed end-to-end exploit trace. A background Devin session with full repository access (in particular tracing every writer of `assetInfos` in `aa_composer.js`) would be needed to confirm or rule out reachability.
