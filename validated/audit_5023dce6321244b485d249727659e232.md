### Title
Webhook signature verification binds to `repository.owner.login`, not the `repository.full_name` actually acted upon, allowing cross-repository webhook forgery for any org with an unset `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to check the HMAC signature against using one field of the JSON payload, while the event handlers that actually act on the webhook (e.g. `PushHandler`, `CheckSuiteHandler`) resolve the **target repository/stack** from a *different* field of the same payload. Because `verify_webhook_signature` trivially returns `true` when an organization has no `webhook_secret` configured, an attacker who can reach the public webhook endpoint can pick any such unconfigured/blank-secret organization to satisfy signature verification, then point the payload's `repository.full_name` at a completely different (fully protected) repository/stack to have Shipit act on it.

### Finding Description
`repository_owner` — the value used to pick which org's webhook secret authenticates the request — is read directly from the untrusted, not-yet-verified body: [1](#0-0) 

That value is passed into `Shipit.github(organization: repository_owner)` and its `verify_webhook_signature` is invoked: [2](#0-1) 

`verify_webhook_signature` short-circuits to `true` when the selected organization has no configured secret: [3](#0-2) 

Once verification passes (trivially, for a secret-less org), the same raw body is dispatched to handlers, which resolve the *actual* target repository from a **different** JSON field, `repository.full_name`, completely independent of the `repository.owner.login`/`organization.login` field used for the auth decision: [4](#0-3) 

`PushHandler` uses that repository resolution to sync any matching stack to an attacker-chosen commit SHA: [5](#0-4) 

`CheckSuiteHandler` similarly triggers check-run refreshes for a stack/commit chosen purely from payload content unrelated to the field that satisfied signature verification: [6](#0-5) 

This breaks the trust binding: **the organization whose secret authenticated the webhook ≠ the repository whose stack is written/acted on**. Multi-tenant Shipit deployments (multiple orgs configured under `Shipit.github`) commonly have organizations with no `webhook_secret` set — the shipped sample configs demonstrate this is an accepted/expected state, not an edge case: [7](#0-6) [8](#0-7) 

### Impact Explanation
An unprivileged, unauthenticated network attacker who knows (a) the login of any organization configured in this Shipit instance with a blank `webhook_secret`, and (b) the `full_name` of a tracked repository belonging to a different, secured organization, can POST a forged `push` or `check_suite` event to `/webhooks`. The forged event passes signature verification (because the chosen org has no secret) yet is dispatched against the victim repository's stacks, causing Shipit to sync stack state / refresh check runs at attacker-chosen SHAs for repositories the attacker has no legitimate access to. Where a stack has continuous deployment (merge queue) enabled, this out-of-band manipulation of synced commit/check-run state can influence which commits Shipit considers ready to auto-merge/deploy — an unauthorized-deploy-adjacent escalation, and at minimum an unauthenticated write into stack/task state that should require GitHub-verified authenticity.

### Likelihood Explanation
Any Shipit deployment onboarding multiple GitHub organizations is likely to have at least one organization pending secret configuration (the packaged sample configs ship with `webhook_secret: null`/commented out). The webhook endpoint is unauthenticated by design (it exists specifically to accept unauthenticated GitHub-signed callbacks), so exploitation requires no credentials — only knowledge of a target repo's `full_name`, which is typically public.

### Recommendation
- Do not fall back to `true` when `webhook_secret` is blank in `Shipit::GithubApp#verify_webhook_signature`; require an explicit "trusted, no-secret" opt-in in config instead, separate from "not yet configured."
- Bind the field used to select the verifying organization to the field used to resolve the acted-upon repository: after choosing the secret via `repository_owner`, verify that `payload.dig('repository','full_name')`'s owner matches `repository_owner` before dispatching to handlers in `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`.

### Proof of Concept
1. Identify an organization `orgA` configured in this Shipit instance's `Shipit.github` config with no `webhook_secret` (e.g., newly onboarded, matching the shipped sample configs).
2. Craft a `push` webhook JSON body where `repository.owner.login` (or `organization.login`) is `orgA`, but `repository.full_name` is `victim-org/protected-repo` (a repository tracked by Shipit under a different, secured org), with an attacker-chosen `after` SHA and `ref`.
3. POST to `/webhooks` with header `X-Github-Event: push` and any `X-Hub-Signature` value (or omit it) — `verify_signature` resolves `repository_owner` to `orgA`, calls `Shipit.github(organization: 'orgA').verify_webhook_signature(...)`, which returns `true` because `orgA.webhook_secret` is blank.
4. `PushHandler.call(params)` runs and resolves stacks via `Repository.from_github_repo_name('victim-org/protected-repo')`, calling `stack.sync_github(expected_head_sha: <attacker SHA>)` on the victim's stack — despite the request never being validated against `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
