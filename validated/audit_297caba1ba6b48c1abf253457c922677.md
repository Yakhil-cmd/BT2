### Title
Hookify `RuleEngine._extract_field` silently drops Write-tool content for `new_text`/`new_string` conditions, letting `action: block` rules miss dangerous file writes - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
Hookify rules that target file-write content use the field name `new_text`/`new_string` (either via the legacy `pattern` shorthand, which auto-infers `field: new_text` for `event: file`, or via explicit `conditions`). `RuleEngine._extract_field` resolves this field only against `tool_input['new_string']`, which exists for the `Edit` tool but not for `Write`. For `Write` invocations the lookup silently returns `''` instead of the actual file content, so any regex/contains condition on that field can never match, and a configured `action: block` rule never fires for `Write` even though the rule's `event: file` scope and the hook dispatch (`pretooluse.py`) both treat `Write` as an in-scope tool.

### Finding Description
`load_rules(event='file')` in `plugins/hookify/hooks/pretooluse.py` is invoked for `tool_name in ['Edit', 'Write', 'MultiEdit']` [1](#0-0) , so a user-authored `event: file` rule is expected to be evaluated against all three tools identically.

For legacy simple-pattern rules, `Rule.from_dict` infers the condition field as `new_text` whenever `event == 'file'`, with no distinction between tools [2](#0-1) . Documentation (`README.md`, `writing-rules/SKILL.md`) also instructs authors to write explicit conditions with `field: new_text` for file-content checks intended to cover Edit/Write/MultiEdit uniformly [3](#0-2) .

In `RuleEngine._extract_field`, the direct-key lookup (`if field in tool_input`) fails for `new_text` since neither tool ever names a key `new_text`. Execution falls through to the tool-specific branch:
```
elif field == 'new_text' or field == 'new_string':
    return tool_input.get('new_string', '')
``` [4](#0-3) 

`Write`'s `tool_input` schema only contains `file_path` and `content` — it has no `new_string` key. Thus for a `Write` call this branch returns `''` (empty string, not `None`), so `_check_condition` proceeds to evaluate the configured operator (`regex_match`, `contains`, etc.) against an empty string rather than the real file content [5](#0-4) . A block rule such as the documented sensitive-file example (`field: new_text`, `pattern: KEY`, `action: block`) will therefore never trigger for `Write`, while the identical rule correctly blocks the same content delivered via `Edit` (which does populate `new_string`).

This is a genuine representation-mismatch bug: the rule engine's tool-matching/scoping (`event: file`) says "cover Edit, Write, MultiEdit" but the field-extraction aliasing only implements the Edit representation for `new_text`/`new_string`, so a single tool representation (Write) silently escapes enforcement despite being nominally in scope.

### Impact Explanation
Any project relying on hookify `action: block` rules keyed on `new_text`/`new_string` for `event: file` (the officially documented pattern for catching secrets, dangerous code, or destructive content in file writes) will fail to block malicious or accidental writes performed via the `Write` tool while still blocking the same content via `Edit`. In a prompt-injection or compromised-context scenario where the agent is induced to call `Write` instead of `Edit` to introduce secrets, malicious code, or overwrite protected files, the intended safety block is bypassed, resulting in unauthorized file mutation that the user explicitly configured a rule to prevent. This matches the "dangerous operation misses the intended rule because tool matching accepts only one representation" impact class — a wrong-target/unintended mutation reaching disk despite an active block rule.

### Likelihood Explanation
No special privileges are required — this triggers under normal operation any time a `Write` tool call is made while an `event: file` block rule is configured with `new_text`/`new_string` field (the primary documented rule style for file-content checks). It is 100% reproducible and deterministic; no timing, race, or credential requirements exist. The only precondition is that the target rule uses `new_text`/`new_string` against a `Write` call rather than `Edit`, which is exactly the scenario the plugin advertises as supported (`event: file` → Edit/Write/MultiEdit).

### Recommendation
In `_extract_field`, make the alias resolution tool-aware and complete for `Write`:
```python
elif tool_name in ['Write', 'Edit']:
    if field in ('content', 'new_text', 'new_string'):
        return tool_input.get('content') or tool_input.get('new_string', '')
    elif field in ('old_text', 'old_string'):
        return tool_input.get('old_string', '')
    elif field == 'file_path':
        return tool_input.get('file_path', '')
```
i.e., treat `new_text`/`new_string` as synonyms for "the content being written" and fall back to `content` for `Write`, exactly as already done for the `content` field alias. Add a regression test asserting that a block rule with `field: new_text` triggers identically for `Write` and `Edit` tool_input payloads containing the same dangerous string.

### Proof of Concept
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-api-key",
    enabled=True,
    event="file",
    action="block",
    conditions=[Condition(field="new_text", operator="contains", pattern="API_KEY")],
    message="Blocked: API key detected"
)
engine = RuleEngine()

# Edit tool: correctly blocked
edit_input = {
    "tool_name": "Edit",
    "tool_input": {"file_path": "secrets.py", "old_string": "", "new_string": "API_KEY=xxx"}
}
assert engine.evaluate_rules([rule], edit_input).get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Write tool: SAME dangerous content, but bypasses the block (bug)
write_input = {
    "tool_name": "Write",
    "tool_input": {"file_path": "secrets.py", "content": "API_KEY=xxx"}
}
result = engine.evaluate_rules([rule], write_input)
assert result == {}  # currently passes — demonstrates the bypass; should instead deny
```
Expected (fixed) behavior: both `Edit` and `Write` invocations with equivalent dangerous content should produce `permissionDecision: deny`; currently only `Edit` is blocked, confirming the tool-representation bypass.
