### Title
`provision?` operator precedence bug allows review stack provisioning to bypass `review_stacks_enabled` gate - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with the three provisioning-behavior branches using `&&`/`||` without parentheses, so `review_stacks_enabled` only gates the `allow_all` branch due to Ruby operator precedence. When a repository has `review_stacks_enabled: false` but `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`, an attacker's pull request can still cause `provision?` to return `true`, triggering `ReviewStackAdapter#find_or_create!` and enqueueing the stack for provisioning.

### Finding Description
The claimed invariant is: `provision? == true` `<=>` `repository.review_stacks_enabled == true`. That equality is false in the code: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

`&&` has higher precedence than `||` in Ruby, so this parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` is only ANDed into the first disjunct. The second and third disjuncts (the label-based behaviors) are evaluated completely independently of `review_stacks_enabled`. Concretely, with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label`, any opened pull request that does *not* carry the configured provisioning label (the default state for an unlabeled PR) makes `provision?` return `true` even though the repository has explicitly disabled review stacks.

Reachable path: an unprivileged attacker (any GitHub user who can open a PR against the tracked repository, or make GitHub emit the `pull_request` `opened` webhook) triggers `POST /webhooks`, which dispatches to `OpenedHandler#process` [2](#0-1) . `respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?` [3](#0-2) , so no other guard (signature verification, `drop_unhandled_event`, `ExplicitParameters` schema) checks `review_stacks_enabled`; the schema only validates payload shape, not this authorization decision. Once `provision?` is (incorrectly) true, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` runs, creating a `Shipit::ReviewStack` and enqueueing it (`enqueue_for_provisioning`), which is later picked up by `ReviewStackProvisioningQueue#work` → `stack.provision` [4](#0-3) , i.e., actual provisioning commands run for a repository whose operator explicitly turned review-stack provisioning off.

The existing test suite does not catch this because `configure_provisioning_behavior` defaults `provisioning_enabled: true` in every test exercising the label-based branches [5](#0-4) ; the only `provisioning_enabled: false` test uses `behavior: :allow_all` [6](#0-5) , which happens to be the one branch that *is* correctly gated, masking the bug for the two branches that are not.

### Impact Explanation
An attacker who can open a pull request against a repository that is tracked by Shipit but has explicitly disabled review-stack auto-provisioning (`review_stacks_enabled: false`) with `provisioning_behavior: prevent_with_label` can still force Shipit to create a `Shipit::ReviewStack` record and enqueue it for provisioning, causing provisioning commands to execute for that repository despite the operator's configuration disabling the feature. This is repeatable against any repository configured this way and requires no special GitHub permissions beyond opening a PR (not adding a label, since the default no-label state is what triggers the bypass for `prevent_with_label`). This matches "a command running that should not" / unauthorized stack provisioning for a repository that did not authorize it.

### Likelihood Explanation
Preconditions: the target repository must exist in Shipit with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible transitional/misconfiguration state — e.g., an operator disables review stacks but leaves a prior label-based behavior configured). Attacker cost is trivial: open a normal pull request (or, for `prevent_with_label`, simply don't add the label, which is the default). No secrets, tokens, or elevated GitHub roles are required.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three branches:

```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
Add a minitest table-driven test directly invoking `send(:provision?)` on a stubbed `OpenedHandler`, iterating all 8 combinations of `review_stacks_enabled` × `provisioning_behavior` (mapped through the three predicate methods) × label presence, asserting the invariant `provision? => review_stacks_enabled` (i.e. `refute provision? if !review_stacks_enabled`). For example:

```ruby
test "provision? is false whenever review_stacks_enabled is false" do
  [:allow_all, :allow_with_label, :prevent_with_label].each do |behavior|
    [true, false].each do |label_present|
      repository = shipit_repositories(:shipit)
      repository.update!(review_stacks_enabled: false, provisioning_behavior: behavior, provisioning_label_name: "l")
      payload = payload_parsed(:pull_request_opened)
      payload["pull_request"]["labels"] = label_present ? [{ "name" => "l" }] : []
      handler = OpenedHandler.new(payload)
      handler.instance_variable_set(:@repository, repository)
      refute handler.send(:provision?), "behavior=#{behavior} label=#{label_present} should not provision when review_stacks_enabled is false"
    end
  end
end
```

This test fails today for `behavior: :prevent_with_label, label_present: false` and `behavior: :allow_with_label, label_present: true`, confirming the bypass.
