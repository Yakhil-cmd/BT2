## Finding

### Title
Webhook organization used for signature verification is not bound to the repository the event payload writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug-class hint ("safeTransfer/safeTransferFrom without a code-existence check silently reports success for a target that was never actually acted on") maps to a real trust-binding gap in `WebhooksController`: the GitHub organization used to *verify* the webhook signature is resolved from one payload field (`repository.owner.login` / `organization.login`), while the downstream event handlers act on a completely different, unverified payload field (`repository.full_name`) to decide which `Stack`/repository is actually mutated. Just like the token contract in the report is never checked to correspond to the funds actually moved, the organization whose secret is checked here is never checked to correspond to the repository whose state is actually changed.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization config purely from the JSON payload, before any cryptographic guarantee exists that the payload is authentic for that org: [1](#0-0) [2](#0-1) 

The signature is checked with `github_app.verify_webhook_signature`, whose implementation trusts an organization implicitly when no `webhook_secret` is configured for it: [3](#0-2) 

`Shipit.github(organization: ...)` supports per-organization configuration (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), where each org can independently have a `webhook_secret` set or left blank: [4](#0-3) 

Because `verify_signature` only checks the signature against the secret of the organization named in `repository.owner.login`/`organization.login`, and that check trivially passes (`return true unless webhook_secret`) for any org that has no secret configured, an attacker only needs to identify (or create, in an enterprise multi-org install) one configured organization with a blank `webhook_secret`. They can then submit an unsigned/arbitrarily-signed POST body where:
- `repository.owner.login` (or `organization.login`) = the org with no secret (verification trivially succeeds),
- `repository.full_name` = `<victim-org>/<victim-repo>` — a repository that belongs to a *different*, properly-secured organization.

`verify_signature` never re-checks that `repository.owner.login` matches the owner embedded in `repository.full_name`; there is no code path enforcing `verified_organization == full_name.split('/').first`. Once `head(422)` is not triggered, `create` dispatches the entire attacker-controlled `params` (including the victim `full_name`) to the registered handlers: [5](#0-4) 

Handlers such as the push handler resolve the target `Stack`/repository from `repository.full_name` in the payload (confirmed by the enqueue-with-`stack_id` behavior exercised in `test/controllers/webhooks_controller_test.rb`): [6](#0-5) 

This breaks the trust equality that should hold: `organization whose signature was verified == organization owning the repository the handler writes to`. The signature-verified identity and the identity of the mutated resource diverge, exactly mirroring the report's core defect: a check that reports success/authenticity for one entity while a *different* entity is the one actually affected.

### Impact Explanation
An unprivileged network attacker (no Shipit session, no `ApiClient` token, no GitHub repo write access) can forge `push`, `status`, `check_suite`, or `membership` events for any repository tracked by Shipit, as long as any organization configured on the instance lacks a `webhook_secret` (a supported, documented configuration state — see `config/secrets.development.example.yml`, which ships with `webhook_secret: # nil`). Consequences include:
- Forged `push` events advancing a stack's known head commit and, combined with `continuous_deployment`, triggering an **unauthorized deploy**.
- Forged `status` events marking required CI checks as passing on a victim repository/commit, bypassing `ci.require` and clearing the way for auto-merge/auto-deploy.
- Forged `membership`/`team` events creating or mutating `Team`/`Membership`/`User` records used by `Shipit::User#authorized?` for team-gated access control.

This satisfies the "Critical" bar of an unauthorized deploy/rollback triggered without any legitimate GitHub-side signature covering the targeted repository.

### Likelihood Explanation
Exploitability only requires that at least one configured GitHub organization on the instance has no `webhook_secret` set — a state explicitly supported and shown as the default/example in shipped configuration templates (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`). No credentials, sessions, or repository access are needed; the attacker just POSTs to the public `/webhooks` endpoint with a crafted `X-Github-Event` header and JSON body.

### Recommendation
- After resolving `repository_owner` and verifying the signature, re-derive the organization from `repository.full_name` (or `organization.login`) and require they match before dispatching to handlers.
- Do not treat a missing `webhook_secret` as an implicit "verified" state; either require a secret for all configured organizations or explicitly scope/log which organizations are unauthenticated and refuse to let their webhooks affect resources owned by other organizations.
- Add a check in `WebhooksController#verify_signature` (or in each handler) that the resolved/verified organization equals the owner segment of `repository.full_name` before any `Stack` lookup/mutation occurs.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgA` (no `webhook_secret`) and `VictimOrg` (properly secured, tracked repository `VictimOrg/prod-app`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": { "login": "OrgA" },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "VictimOrg/prod-app" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
No `X-Hub-Signature` header is required (or any value works) because `Shipit.github(organization: "OrgA")` has a blank `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
3. `WebhooksController#create` dispatches the payload to `PushHandler`, which resolves and updates the `Stack` for `VictimOrg/prod-app` using the forged `after` SHA, exactly as it would for a legitimately signed `VictimOrg` webhook — despite the signature only ever having been checked against `OrgA`'s (absent) secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
