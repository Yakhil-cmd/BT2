### Title
Post-creation mutation of `output_data_receivers` can push a receipt above `max_receipt_size` after size validation - (File: `runtime/runtime/src/lib.rs`, validated via `core/primitives/src/receipt.rs`)

### Summary
The runtime validates new receipt size via `validate_receipt` (`runtime/runtime/src/verifier.rs`) at the moment a receipt is produced by `apply_action`, comparing `borsh::object_length(receipt)` against `limit_config.max_receipt_size`. However, in `apply_action_receipt` (`runtime/runtime/src/lib.rs`), after this check, `output_data_receivers` are subsequently appended to an already-created/returned receipt (the `ReceiptEnum::Action(new_action_receipt) ... output_data_receivers.extend_from_slice(...)` path at `runtime/runtime/src/lib.rs:1019-1037`), which can push the final serialized receipt size above `max_receipt_size` without re-validation.

### Finding Description
`validate_receipt` in `runtime/runtime/src/verifier.rs` enforces the `ReceiptSizeExceeded` check only for `ValidateReceiptMode::NewReceipt`, computed via `borsh::object_length(receipt)` [1](#0-0) . This check runs inside `apply_action_receipt` immediately after each action produces `new_receipts`, before those receipts are potentially mutated [2](#0-1) .

The code that appends `output_data_receivers` to a newly created receipt runs later in the same function, and is explicitly documented in the codebase as a known bug (tracked as near/nearcore#12606): "A function call will generate a new receipt... `output_data_receivers` will be modified and the receipt's size will go above `max_receipt_size`. The receipt should be rejected, but currently isn't because of a bug" [3](#0-2) . The mutation itself occurs at `runtime/runtime/src/lib.rs:1019-1037` [4](#0-3) .

The codebase itself documents this exact bug in `ValidateReceiptMode::ExistingReceipt`'s doc comment: "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed. See https://github.com/near/nearcore/issues/12606 for details." [5](#0-4) . A similar acknowledgment and partial mitigation exists in `try_forward` in `runtime/runtime/src/congestion_control.rs`, which clamps the observed `size` to `max_receipt_size` when forwarding, specifically to avoid oversized receipts getting stuck, again citing issue #12606 [6](#0-5) .

Test coverage in `test-loop-tests/src/tests/max_receipt_size.rs` (`test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`) demonstrates the exploit path is reachable via ordinary contract calls (`promise_batch_action_*`-driven promise DAGs and returned values), and both tests assert that an oversized receipt does occur on-chain (`assert_oversized_receipt_occurred`), confirming the invariant "receipt encoded size is bounded" is currently violated [7](#0-6) [8](#0-7) .

### Impact Explanation
This allows an unprivileged attacker (any contract-calling account) to produce and successfully propagate a receipt whose serialized size exceeds the protocol's `max_receipt_size` (4 MiB) hard limit, without their transaction being rejected. Because state-witness size budgeting (per the documented ~17 MiB total budget in `docs/misc/state_witness_size_limits.md`) assumes all receipts are ≤ `max_receipt_size`, oversized receipts can inflate `ChunkStateWitness` size beyond expected bounds, increasing bandwidth/compute costs for validators disproportionately to gas charged (an underpriced-resource-consumption scenario). This matches the "greatly increasing the computational cost of the network" impact class. However, the codebase has already applied mitigations that prevent unbounded growth or chain death: `try_forward` clamps size to `max_receipt_size` for outgoing-limit accounting so receipts don't get permanently stuck, and `ValidateReceiptMode::ExistingReceipt` deliberately tolerates already-existing oversized receipts to keep the runtime from panicking/dying. These mitigations bound the blast radius to "receipt size limit can be exceeded, but the chain keeps operating and doesn't crash," rather than unbounded resource exhaustion.

### Likelihood Explanation
High feasibility and repeatability: this is a genuine, deterministic bug reachable via ordinary `FunctionCall` actions that create a promise DAG with `promise_return`/output data receivers, or via returning large values, as demonstrated by the existing integration tests in `test-loop-tests/src/tests/max_receipt_size.rs`. No special privileges are required — only standard contract deployment and calls through public RPC.

### Recommendation
Re-validate receipt size (via `validate_receipt` with `ValidateReceiptMode::NewReceipt`) after all post-creation mutations are applied — specifically after `output_data_receivers` are extended onto a reused receipt in `apply_action_receipt` (`runtime/runtime/src/lib.rs:1019-1037`) — rather than only immediately after `apply_action` returns. Alternatively, restructure the logic so the `output_data_receivers` extension always creates/validates a fresh receipt rather than mutating a receipt that already passed the size check. This should be done under a new protocol feature/version gate to preserve backward compatibility with existing state, consistent with how `ValidateReceiptMode::ExistingReceipt` already handles legacy oversized receipts.

### Proof of Concept
Existing tests already reproduce this:
- `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs:129-208`: builds a promise DAG `[A -then-> B]` where A returns a new promise `C` sized to exactly `max_receipt_size`; C's `output_data_receivers` are then extended, pushing it over the limit, and `assert_oversized_receipt_occurred` confirms an on-chain receipt exceeds `max_receipt_size`.
- `test_max_receipt_size_value_return` (`:215-267`): returns a value sized at `max_receipt_size`, which gets wrapped in a `DataReceipt`, again exceeding the limit and being confirmed via `assert_oversized_receipt_occurred`.

To close the loop as suggested by the question, add an analogous case in `runtime/runtime/src/tests/apply.rs` using `cargo test -p node-runtime --features test_features` that: constructs a `FunctionCall` action producing an outgoing/local receipt sized at `max_receipt_size - epsilon`, attaches `output_data_receivers`, applies the receipt, and asserts (a) `borsh::object_length` of the resulting receipt exceeds `limit_config.max_receipt_size`, and (b) the balance checker/gas totals still reconcile (showing the size-limit bypass doesn't itself cause fund/gas accounting divergence, only bypasses the size invariant).

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
