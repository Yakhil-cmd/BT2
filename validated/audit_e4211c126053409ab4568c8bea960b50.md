Found a strong analog. In `wallet.js`, `receiveTextCoin()` is the function used to redeem an Obyte "textcoin" (a coin sent to a throwaway single-key address derived from a mnemonic, analogous to the OpenQ bounty contract holding multiple deposit types). When the recipient claims it, the code inspects what was deposited on that address and, if the deposit is a **private asset**, it deliberately claims **only the first asset** found, silently skipping any other value (bytes or other assets) sitting on the same address — an exact analog of `ClaimManagerV1` claiming ERC-20 payout while skipping the NFT payout.

### Title
`receiveTextCoin()` claims only the first private asset and silently abandons any other value (bytes/other assets) on the same textcoin address - (File: `wallet.js`)

### Summary
`receiveTextCoin()` is the recipient-side redemption function for textcoins (single-use addresses generated from a mnemonic). When such an address has received **more than one kind of value** (e.g. a private asset plus bytes, or a private asset plus another asset) and the first one selected happens to be private, the function only builds and sends a payment for that single asset, never touching the remaining balances on the address.

### Finding Description
`checkStability()` inside `receiveTextCoin` queries all unspent, good-sequence balances on the textcoin address, grouped by asset: [1](#0-0) 

It then picks `row = rows[0]` (the first asset in descending order) and branches on whether that single asset is private: [2](#0-1) 

For the non-private case, the code correctly aggregates **all** rows (all assets plus `base`) into `outputs_by_asset` so every deposited value is claimed in one payment: [3](#0-2) 

But for the private-asset case, the comment itself states the limitation — "claim only the 1st asset" — and only `asset = assets[0]` and `amount = row.amount` are used to build the single payment; no `base_outputs`/`outputs_by_asset` covering the remaining rows (extra bytes or additional assets that may also sit on the same address) is composed: [4](#0-3) 

Because the payment for the private asset uses `opts.fee_paying_addresses = [addrInfo.address]` (the same throwaway address) rather than distributing all balances to `addressTo`, any bytes/other assets left over after fee deduction remain on `addrInfo.address`, which is not tracked or re-claimed anywhere else in the flow.

### Impact Explanation
If a textcoin address ends up holding a private asset together with other value (bytes above what's needed for fees, or another asset — e.g. from repeated/duplicate sends to the same mnemonic, or partial sends via `sendMultiPayment` with `outputs_by_asset`), the recipient's single redeem action via `receiveTextCoin` only recovers the private asset. The rest of the funds are effectively frozen on a single-key address that the wallet UI/flow has no further automatic mechanism to sweep, since the redemption is treated as complete once the private-asset payment succeeds (transaction history marks the textcoin as "claimed" once any output is spent). This is a fund-freezing bug analogous to the reported issue: a claim function that handles one type of deposit but skips others held on the same object/address.

### Likelihood Explanation
This requires a textcoin address to hold heterogeneous deposits (private asset + something else), which is a supported but less common scenario (e.g., sending more than one payment/asset to the same generated textcoin recipient, or a sender topping up an already-generated textcoin address). It doesn't require an attacker — it's a functional gap reachable by any ordinary user composing multi-asset or repeated textcoin payments, matching the "unprivileged... AA trigger sender / private-payment counterparty" reachability requirement.

### Recommendation
When the selected asset is private, still aggregate the remaining rows (other assets and any leftover `base`) into supplementary payments (or explicitly document/enforce a hard restriction that a textcoin address must contain only a single asset/denomination, validating this earlier and refusing/warning on additional deposits) so that no value silently remains stranded on the throwaway address after redemption.

### Proof of Concept
1. Generate a textcoin address via `sendMultiPayment` with `outputs_by_asset` sending a private asset amount to the textcoin address (wallet.js flow at [5](#0-4)  generates the mnemonic-derived address).
2. Send a second, independent payment of bytes or another asset to the same derived address (possible since the address is a normal Obyte address, reachable by anyone who knows it, or by the same sender adding more outputs).
3. Recipient calls `receiveTextCoin(mnemonic, addressTo, ...)`; `checkStability()` selects the private asset as `rows[0]` and only claims that asset via the `is_private` branch [6](#0-5) .
4. The bytes/other-asset balance remains on `addrInfo.address`; the recipient has no follow-up call in this flow to retrieve it, and normal wallet UX treats the textcoin as fully claimed.
