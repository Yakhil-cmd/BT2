**Reasoning:**

The premise of "O(key_len) `common_prefix` calls at O(key_len) trie levels producing O(key_len²) cost" is incorrect based on how `NibbleSlice::common_prefix`/`starts_with` are used in `lookup_from_state_column`.

At each trie level, `key.starts_with(&existing_key)` only compares the current suffix of the lookup key against the extension/leaf key stored at that specific node [1](#0-0) . Because trie extension/leaf keys at successive levels are non-overlapping nibble segments of the same overall key (branch nodes consume exactly 1 nibble, extensions consume a contiguous run of nibbles, and `key = key.mid(existing_key.len())` advances past the consumed portion), the total number of nibble comparisons summed across the *entire* path from root to leaf is bounded by the total key length, not by (levels × key_len). This is fundamentally the same partition property used in the `TrieConstructor`/insert-delete code where `common_prefix_len` and `.mid(common_prefix_len)` calls partition, rather than repeat, work across a key [2](#0-1) . So a single lookup does O(key_len) nibble-comparison work total, not O(key_len²).

This matches how gas is charged: `storage_write_key_byte` / `storage_read_key_byte` are charged once per byte of the key for the whole call [3](#0-2) [4](#0-3) , and `touching_trie_node` gas is charged per unique trie node accessed, which is bounded by the number of levels in the path [5](#0-4) . The estimator's methodology explicitly measures the marginal per-node cost including the nibble-matching work at each node by varying key length and dividing by touched-node count [6](#0-5) , so the linear-in-key-length matching cost is already incorporated into `storage_write_key_byte`/`touching_trie_node`.

Additionally, `max_length_storage_key` independently caps the key at a small bound (2048 bytes as of protocol upgrade 53, previously 4,194,304) [7](#0-6) , and this limit is enforced before any trie traversal in `storage_write`/`storage_read`/`storage_has_key` [8](#0-7) [9](#0-8) .

Given that (1) the actual algorithmic cost of a trie lookup/write is linear, not quadratic, in key length, and (2) the gas model charges linearly per key byte plus per touched node (calibrated via benchmarks that include the nibble-comparison cost), there is no gas-underpriced superlinear CPU cost here. The `max_length_storage_key` cap further bounds any worst case. No metering-completeness violation is present in `NibbleSlice::common_prefix`/`starts_with` or `lookup_from_state_column`.
