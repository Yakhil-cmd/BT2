### Title
Pull-request label names flow unfiltered into deploy/task process environment, allowing `BASH_ENV` injection via `ReviewStack#env` — (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` turns every pull-request label name into an environment variable (`label.upcase => "true"`) with no allowlist, and `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook body with only a `String` type check. `TaskCommands#env` (used by `DeployCommands`, which drives the `deploy.variables`/`deploy.override` steps) merges this unfiltered `@stack.env` directly into the environment handed to `Shipit::Command`, which is then passed straight into `PTY.spawn`. Unlike the deploy form's `env` field, this path is never run through `EnvironmentVariables#permit`, so a label literally named `bash_env` becomes `BASH_ENV=true` in the spawned shell's environment.

### Finding Description
The broken invariant is:

`TaskCommands#env` ⊇ `@stack.env` (all pull_request label-derived keys, unfiltered) **should equal** `TaskCommands#env` ⊇ only the keys declared in `deploy_spec.deploy_variables`/`rollback_variables` (i.e., filtered by `EnvironmentVariables#permit`). These two sets are NOT equal — the former is what the code actually does.

Path:
1. `LabelCapturingHandler#capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` straight from the webhook payload, with schema validation only enforcing `String` type on `name` — no character/content restriction. [1](#0-0) 
2. `ReviewStack#env` merges every label name, upcased, mapped to `"true"`, into the stack's base env with no allowlist at all: [2](#0-1) 
3. `TaskCommands#env` (parent of `DeployCommands#env`, used for `deploy.variables`/`deploy.override` steps) does `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` — `@stack.env` (containing the label-derived keys) is merged in unfiltered; only `@task.env` (the deploy's own whitelisted `env` column) is filtered via `filter_deploy_envs`/`EnvironmentVariables#permit`, and that filtering has no effect on keys like `BASH_ENV` that don't collide with a declared deploy variable. [3](#0-2) 
4. `Shipit::Command#unbundled_env` merges `@env` (this same hash) on top of `BASE_ENV`, and `#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, spawning the deploy step with this environment. [4](#0-3) 

Existing tests explicitly demonstrate that arbitrary label-derived keys reach the process environment unrestricted (`WIP`, `BUG` examples), confirming no allowlist exists on this path, unlike the `deploy.variables` feature which is explicitly protected by `EnvironmentVariables#permit`/`filter_deploy_envs`: [5](#0-4) [6](#0-5) [7](#0-6) 

Why guards fail: `filter_deploy_envs`/`EnvironmentVariables#permit` only sanitizes the `Deploy#env` attribute (the user-submitted form/API field, restricted via `deploy_params` in `DeploysController` to `@stack.deploy_variables.map(&:name)`), not `Stack#env`/`ReviewStack#env`. `Stack#env` and `ReviewStack#env` are considered "system-derived" and are merged unconditionally by `TaskCommands#env`, so nothing in the request-handling or `ExplicitParameters` validation layer intercepts this divergence.

### Impact Explanation
An attacker who can get a label applied to their review-stack's pull request (labels are captured on `opened`, `labeled`, `unlabeled`, `reopened` events by `LabelCapturingHandler`, regardless of the `prevent_with_label`/`allow_with_label` provisioning label itself) can set `BASH_ENV` (or `ENV`, `LD_PRELOAD`, `PYTHONSTARTUP`, `PERL5OPT`, etc.) in the environment of every subsequent deploy/task command run for that review stack. If any deploy step invokes `bash` non-interactively (directly, via a shebang, or via tools like `cap`/`bundle` that shell out), `BASH_ENV` causes bash to source an attacker-named file before running the real command — a path to arbitrary code execution on the Shipit deploy host. This is scoped to the affected review stack's own deploy/task processes (not automatically other tenants' stacks), but it is fully repeatable for every deploy of that stack and matches the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category.

### Likelihood Explanation
Preconditions: `review_stacks_enabled` on the repository (any `provisioning_behavior`, since label capture runs independent of the provisioning label), and the ability to attach a label to the PR. Per the audit's stated attacker model, the attacker can label their own PR. No Shipit secrets, sessions, or GitHub write access beyond that assumption are required. The label name itself is entirely attacker-controlled text with only a `String` type constraint enforced by `ExplicitParameters`, so crafting `bash_env` is trivial and repeatable across any number of PRs/labels.

### Recommendation
Apply an explicit allowlist/denylist to `ReviewStack#env` (and any other label-derived env merge) before it is combined into `TaskCommands#env`/`Command`. At minimum: reject or filter out reserved/dangerous variable names (`BASH_ENV`, `ENV`, `LD_PRELOAD`, `PATH`, `IFS`, `PERL5OPT`, etc.), and ideally require declared, whitelisted variable definitions (similar to `deploy_variables`) for any pull-request-label-derived environment injection, sanitizing through `EnvironmentVariables#permit` rather than merging unconditionally.

### Proof of Concept
```ruby
# test/lib/shipit/deploy_commands_test.rb (extend existing test)
test "#env does not leak BASH_ENV from a pull request label" do
  stack = shipit_stacks(:review_stack)
  deploy = stack.trigger_continuous_delivery
  stack.pull_request.labels = ["bash_env"]  # attacker-controlled label name from webhook

  env = Shipit::DeployCommands.new(deploy).env

  # Binding under test: deploy.variables/deploy.override step process env
  # should NOT contain a fork-controllable BASH_ENV key.
  refute env.key?("BASH_ENV"), "BASH_ENV must not be settable via a PR label"
end
```
Running this against current code fails: `env["BASH_ENV"]` equals `"true"`, proving the label-controlled key reaches the environment that `Command#start` passes to `PTY.spawn`.
