### Title
Cross-organization Team escalation via `MembershipHandler#find_or_create_team!` looking up teams only by GitHub `team.id` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
Shipit supports multi-organization GitHub App configuration where each organization has its own `webhook_secret` [1](#0-0) , and the webhook signature is verified per-organization using the org derived from the payload itself [2](#0-1) . For `membership` events (which carry no `repository` key), that org is taken from `params.dig('organization', 'login')` [3](#0-2) . However, `MembershipHandler` resolves/creates the `Team` record purely by the attacker-controlled numeric `team.id` field, with no check that this team actually belongs to the organization whose signature was verified [4](#0-3) .

### Finding Description
The binding that should hold is: **organization that authenticated the webhook == organization that owns the team being mutated**. It is broken as follows.

`WebhooksController#verify_signature` picks the GitHub App/secret to verify against using `repository_owner`, which for events without a `repository` payload key (like `membership`) falls back to `params.dig('organization', 'login')`: [5](#0-4) 

This value is fully attacker-controlled content signed by the attacker's *own* configured GitHub App/organization (Shipit explicitly supports per-organization `webhook_secret`s, see `Shipit.github_app_config` / `github_organizations`) [6](#0-5) .

`MembershipHandler#process` then does:
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
```
and
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [7](#0-6) 

`ActiveRecord#find_or_create_by!` only executes the block (which sets `team.organization`) when it *creates* a new record; if a `Team` with that `github_id` already exists, it is simply returned unmodified, ignoring `params.organization.login` entirely. `team.id` (the GitHub numeric team ID) in the request body is otherwise unauthenticated, attacker-supplied data — it is never checked against the organization that produced a valid signature.

`Team#add_member` then unconditionally appends the attacker-named `User` (created via `User.find_or_create_by_login!`, itself driven by the attacker-supplied `member.login` string) to that team's `members` [8](#0-7) .

Authorization gating is `Shipit.github_teams` (a configured allow-list of `Team` objects) and `User#authorized?`, which checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) .

**Attack path:** an attacker who administers *their own* GitHub organization/App that is one of the configured `secrets.github` entries (they legitimately possess that org's `webhook_secret`) can:
1. Discover/guess the numeric GitHub `team.id` of a privileged team already present in the victim's `Shipit.github_teams` allow-list (team IDs are visible via GitHub's public API for any team the attacker can view, or simply by having once been a member/observer).
2. Send a `membership` webhook, correctly HMAC-signed with their own org's `webhook_secret`, with `organization.login` = their own org (so it passes `verify_webhook_signature`), but `team.id` = the victim's privileged team's GitHub ID, and `member.login` = an attacker-controlled GitHub username, `action: 'added'`.
3. `WebhooksController#verify_signature` authenticates this as valid (it is — for the attacker's own org).
4. `MembershipHandler#find_or_create_team!` finds the pre-existing privileged `Team` row by `github_id` (ignoring that the request came from a different org) and adds the attacker's user as a member.
5. That user is now `authorized?` and passes `Shipit::Authentication#force_github_authentication`, gaining full application access [10](#0-9) .

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization — explicitly listed as a High-severity impact category. An external, unprivileged (relative to the victim organization) attacker who merely controls their own GitHub App/organization installation of Shipit gains membership in a privileged team gating access to the whole Shipit instance (stacks, deploy triggers, secrets exposure via task logs, etc.), without ever needing credentials, GitHub membership, or write access to the victim organization or repository.

### Likelihood Explanation
Requires only: (a) a Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration [1](#0-0) ), (b) the attacker legitimately controlling one of those organizations (which does not need to be privileged relative to the victim), and (c) knowledge of a target team's numeric GitHub `id`, which is not secret. No signature forgery, no compromise of the victim's secrets, and no host-application misconfiguration is needed — this is exploitable purely through the standard, documented webhook flow.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` (i.e., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that the resolved/created team's `organization` matches `params.organization.login` before applying membership mutations, rejecting the webhook otherwise.

### Proof of Concept
Given a multi-org Shipit config where organization `attacker-org` has webhook secret `S_attacker` and organization `victim-org` owns a `Team` with `github_id: 999` that is included in `Shipit.github_teams`:

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC(S_attacker, body)>

{
  "action": "added",
  "team": { "id": 999, "name": "Anything", "slug": "anything", "url": "https://example.com" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-controlled-user" }
}
```
`verify_signature` succeeds because the signature and `organization.login` both correspond to `attacker-org`'s own valid secret [2](#0-1) . `MembershipHandler` then finds the existing team `github_id: 999` (belonging to `victim-org`) and adds `attacker-controlled-user` to it [7](#0-6) , granting that user `authorized?` status for the whole instance.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
