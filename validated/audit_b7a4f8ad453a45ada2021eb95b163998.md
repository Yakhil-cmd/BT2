Confirmed: `Shipit.github(organization:)` supports a multi-org credential map, where each org key in `secrets.github` has its own independent `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which org's secret to verify against using `repository_owner`, which is read from the payload's `repository.owner.login`, falling back to `organization.login` [2](#0-1) , but every downstream `Handler` (e.g. `PushHandler`, `ClosedHandler`, `LabeledHandler`) resolves the actual target `Stack`/`Repository` independently via `payload.dig('repository', 'full_name')` [3](#0-2) [4](#0-3) . Nothing cross-checks that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` used for signature verification — these are two independent JSON fields in the same signed body, and the signature only proves "some registered org's secret signed this exact byte string," not "this org owns this repository."

### Title
Webhook signature verified against attacker-controlled `repository.owner`/`organization` field allows cross-repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to check the HMAC against based on a field taken directly from the unauthenticated request body (`repository.owner.login` or `organization.login`), while every webhook `Handler` resolves the entity actually acted upon (the `Stack`/`Repository`) from a different, independently-controlled field in the same body (`repository.full_name`). Because the signature only certifies "signed with org X's secret," not "this payload's actions apply to org X's repositories," an operator/holder of one organization's legitimate `webhook_secret` can forge a payload whose `repository.owner.login` matches their own org (passing verification) while `repository.full_name` points at an unrelated organization's repository, causing Shipit to act on that unrelated repository/stack.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches per-organization secrets:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`Shipit.github(organization:)` maintains a per-organization secret map (`github_app_config(organization)` keyed by the org name), confirming that different organizations configured in `secrets.github` have distinct `webhook_secret`s and distinct trust domains [1](#0-0) .

However, once the HMAC check passes, the event is dispatched to handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create` [6](#0-5) ), and every handler picks its target repository from `repository.full_name`, e.g.:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 
and `PushHandler#process` calls `stack.sync_github(...)` for every not-archived stack under that repository/branch [7](#0-6) ; PR handlers similarly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and archive/unarchive/provision review stacks [8](#0-7) [9](#0-8) .

This breaks the equality that should hold: `organization authenticated by verify_signature == organization owning the repository the handlers act on`. The two fields (`repository.owner.login` used for signature selection, and `repository.full_name` used for the actual write) are both attacker-supplied in the same unsigned-until-verified body, and are never cross-validated against each other after verification.

### Impact Explanation
This maps to the "cross-repository writes" / "unauthorized deploy" Critical/High impact category. A party who legitimately controls only one organization's Shipit webhook configuration (and thus its `webhook_secret`) can forge webhook deliveries that are verified as authentic (because the org name they control passes HMAC verification) but whose payload content targets a *different* organization's repositories/stacks, triggering `GithubSyncJob` enqueues, review-stack archival/unarchival/provisioning, or commit status writes on that other tenant's stacks.

### Likelihood Explanation
Exploitation requires the attacker to possess a `webhook_secret` for at least one organization configured in the multi-tenant `secrets.github` map — this is a realistic scenario for any Shipit deployment shared across multiple organizations/teams, since webhook secrets are typically distributed to each org's repository admins to configure GitHub's webhook delivery, not held solely by the Shipit operator. No GitHub App private key, `ApiClient` token, or Shipit session is required — only knowledge of one tenant's own webhook secret, which by design is meant to scope trust to that tenant's own repositories.

### Recommendation
After verifying the signature, re-derive/require that `repository.full_name`'s owner matches the `repository_owner`/organization used to select and verify the signing secret, rejecting (422) any payload where they differ, before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit configured with two organizations in `secrets.github`, `org-a` and `org-b`, each with its own `webhook_secret` (as supported by `github_app_config`) [10](#0-9) .
2. As an administrator with access only to `org-a`'s webhook secret, craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Sign the raw body with `org-a`'s `webhook_secret` using the same HMAC-SHA1 scheme as `DeliverySigner`/`verify_webhook_signature` and set it as `X-Hub-Signature`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` to `org-a`, verifies successfully against `org-a`'s secret, and `PushHandler` then acts on `org-b/victim-repo`'s stacks via `Repository.from_github_repo_name('org-b/victim-repo')` [3](#0-2) , enqueuing `GithubSyncJob` for a stack the attacker does not control.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
