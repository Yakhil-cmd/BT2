### Title
Cross-organization webhook forgery bypasses commit-status trust binding via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against a single GitHub organization's app secret, selected from an attacker-controlled field, but `StatusHandler#process` then applies the payload to a commit lookup that is completely unscoped to that organization or repository. The binding "organization whose secret verified the signature" == "repository/stack the payload is applied to" is never enforced.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization secret to check the signature against using `repository_owner`, itself taken straight from the JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), not from anything cryptographically tied to the payload: [1](#0-0) [2](#0-1) 

`Shipit` explicitly supports multiple independently-configured GitHub organizations, each with its own (optionally blank) `webhook_secret`: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as automatically verified: `return true unless webhook_secret`. [5](#0-4) 

Once the signature step passes (for whichever org name the attacker put in the JSON body), `WebhooksController#create` dispatches the *same raw payload* to the registered handler for the event, with no re-validation that the payload's `repository` actually belongs to the org that was used to authenticate it: [6](#0-5) 

Most handlers scope themselves to a specific repository via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — a field independent from the `repository_owner`/`organization.login` field used for authentication: [7](#0-6) 

`StatusHandler`, however, does not use `stacks`/repository scoping at all. It looks up commits **globally by SHA** across the entire Shipit instance and writes a GitHub-reported CI status onto them: [8](#0-7) 

This status directly feeds into deploy-eligibility logic (`Commit#deployable?`, `Status::Common#required?/#blocking?`), which gates whether a commit can be deployed and whether required/blocking CI contexts are satisfied: [9](#0-8) [10](#0-9) 

**The broken binding, as an equality**: `organization authenticated by verify_signature (repository_owner from payload)` should equal `organization/repository the status write is applied to`, but for `StatusHandler` there is no organization/repository check at all — the write only depends on `sha`, which is attacker-supplied and globally unscoped.

### Impact Explanation
An attacker who can produce a valid signature for **any one** configured GitHub organization on the instance (e.g., an org intentionally left with `webhook_secret: nil`, as shown as a supported/documented configuration, or any org whose secret they otherwise know) can send a forged `status` webhook. Because `verify_signature` only checks the payload against that one org's secret, and `StatusHandler` never re-checks which repository/org the target commit belongs to, the attacker can set a fabricated `state: 'success'` CI status (with arbitrary `context`) on **any commit SHA already known to Shipit, in any other, unrelated, higher-value repository/organization** managed by the same Shipit instance. This can satisfy `ci.require`/`ci.blocking` checks and flip `Commit#deployable?` to true for a commit that never actually passed CI, enabling an unauthorized deploy path for a repository the attacker has no legitimate write access to. This crosses the authentication boundary the code is meant to enforce (org signature → org's own repositories) and falls under the "unauthorized deploy" / cross-repository-write impact category.

### Likelihood Explanation
Requires: (1) Shipit configured with multiple GitHub organizations (a documented, supported configuration in `docs/setup.md`), (2) at least one of them having a blank/absent `webhook_secret` (also shown as a valid example configuration) — or the attacker otherwise knowing one org's secret — and (3) knowledge/guessing of a target commit SHA in another org's repository (SHAs are often public/predictable via GitHub itself). No Shipit session, API token, or repository write access is needed — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body and a matching (or unnecessary) `X-Hub-Signature` header.

### Recommendation
In `WebhooksController`/`Handler`, after signature verification, cross-check that the repository named in the payload (`repository.full_name`) actually belongs to the same organization (`repository.owner.login`) used to select the verifying `github_app`, and reject the request otherwise. Additionally, `StatusHandler#process` should scope its `Commit` lookup by the payload's `repository.full_name` (via `stacks`), not by a bare, cross-tenant `Commit.where(sha:)` query, so a status update can never be applied to a commit outside the authenticated organization's repositories.

### Proof of Concept
1. Configure/observe a Shipit instance using the multi-org `github:` schema with at least one org (`OrgLowValue`) that has `webhook_secret` unset (a documented valid config, see `test/dummy/config/secrets_double_github_app.yml` / `docs/setup.md`).
2. Identify a commit SHA `S` already synced into Shipit for a victim stack under `OrgHighValue/critical-repo` (SHAs are visible via GitHub/PRs).
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/circleci",
  "organization": {"login": "OrgLowValue"},
  "repository": {"owner": {"login": "OrgLowValue"}, "full_name": "OrgLowValue/throwaway"}
}
```
No valid `X-Hub-Signature` is needed because `verify_webhook_signature` returns `true` for `OrgLowValue` (blank secret).
4. `WebhooksController#verify_signature` passes (verified against `OrgLowValue`); `StatusHandler#process` executes `Commit.where(sha: 'S')`, which matches the commit belonging to `OrgHighValue/critical-repo`, and calls `commit.create_status_from_github!`, marking it `success` for `ci/circleci` regardless of actual CI outcome — potentially unlocking a deploy that should have been blocked.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
