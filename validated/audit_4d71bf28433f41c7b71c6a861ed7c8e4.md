### Title
Overpaid storage deposit permanently stuck in `AddressRegistrar::register` due to `<` check instead of exact-match / refund - (File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs)

### Summary
The `AddressRegistrar::register` method, part of the NEAR Wallet Contract's ETH-implicit-account support, accepts any `attached_deposit` that is `>= required_deposit` for storage. On the successful (`Entry::Vacant`) path it never refunds the excess portion of the deposit, unlike the collision (`Entry::Occupied`) path which explicitly refunds the full `given_deposit`. Any excess NEAR sent by a caller beyond the exact storage cost is permanently absorbed into the contract's balance with no withdrawal mechanism exposed.

### Finding Description
`register` computes `required_deposit` from the byte cost of storing the `(address, account_id)` pair, then checks only `given_deposit < required_deposit` (panicking if insufficient) — allowing any deposit `>= required_deposit` to pass: [2](#0-1) 

On the success path (`Entry::Vacant`), the full `given_deposit` is retained by the contract; only `required_deposit` was actually needed to cover storage, yet no refund of the excess (`given_deposit - required_deposit`) is issued to the caller or `predecessor_account_id`: [3](#0-2) 

This is asymmetric with the failure/collision path, which explicitly refunds the entire deposit back via a `Transfer` promise, confirming the contract authors intended deposits to be returned when not consumed by storage, but omitted the "consume-only-what's-needed, refund-the-rest" logic on the success branch: [4](#0-3) 

There is no other method on `AddressRegistrar` (`lookup`, `get_address`) that can move funds out of the contract, so any stuck excess is permanently locked. The contract is a real deployed dependency of the Wallet Contract (`ADDRESS_REGISTRAR_ACCOUNT_ID = "address-map.near"`), which is deployed as a global contract for all ETH-implicit accounts: [5](#0-4) [6](#0-5) 

The Wallet Contract itself invokes `register`-adjacent flows (`lookup`) as part of relayer-honesty checks, and test/tooling code demonstrates `register` being called with an explicit deposit amount chosen by the caller, e.g. `deposit(NearToken::from_millinear(1))`, which is exactly the "user picks a deposit, possibly overestimating storage cost" scenario the external report describes: [7](#0-6) 

### Impact Explanation
Any caller (any unprivileged account, since `register` is `#[payable]` and open to anyone) who attaches more NEAR than the exact storage byte-cost required — e.g., due to estimating deposit conservatively, using a rounded/standard deposit amount, or a change in `storage_byte_cost` between quote and execution — has the excess permanently locked in the `AddressRegistrar` contract's balance with no code path to reclaim it. This is a direct, unconditional value leak on the success path (not merely hypothetical network-delay timing, since `storage_byte_cost` can also change between transaction construction and execution, and callers commonly send round-number deposits like the `1 milliNEAR` seen in test code rather than computing the exact byte cost). Funds are not stolen by another party but are irrecoverably burnt from the user's perspective — a concrete "unauthorized loss of user funds" / underpriced-refund class issue.

### Likelihood Explanation
Likelihood is moderate-to-high: `register` is a straightforward, publicly callable `#[payable]` method that will be invoked whenever a new NEP-141 token or named account needs to be registered in the address map to support ETH transaction emulation via the Wallet Contract. Callers who don't precisely compute `bytes_to_store * storage_byte_cost` (which requires knowing the exact `account_id` byte length and current storage price) and instead attach a conservative/rounded deposit will trigger the bug on every successful registration, not just in an edge-case race condition.

### Recommendation
On the `Entry::Vacant` success path, compute `excess = given_deposit - required_deposit` and, if `excess > 0`, issue a `Transfer` promise (identical to the pattern already used in the `Entry::Occupied` branch) refunding the excess to `env::predecessor_account_id()`. Alternatively, restrict `register` to require an exact deposit match (`given_deposit == required_deposit`) and reject overpayment outright, forcing callers to compute the precise cost.

### Proof of Concept
1. Deploy `AddressRegistrar` (as done in `TestContext::deploy_address_registrar` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/utils/test_context.rs`). [8](#0-7) 
2. Call `register` with an `account_id` whose exact required storage deposit is computable (e.g. a short `account_id` requiring only a few yoctoNEAR per byte), but attach a deliberately larger deposit, e.g. `.deposit(NearToken::from_millinear(1))` as in the existing relayer test: [9](#0-8) 
3. Observe that `register` succeeds (`Entry::Vacant` branch taken) and returns the hex address, but query the contract account's NEAR balance before and after the call — the balance increase equals the full `given_deposit`, not the smaller `required_deposit`, and there is no method to withdraw the difference; repeating this with any account that has already been registered (to hit `Entry::Occupied`) shows, by contrast, that the entire deposit is refunded via `promise_batch_action_transfer`, confirming the asymmetry and the stuck-excess bug on the success path.
