### Title
Attacker-controlled PR labels override `PATH` in spawned command environment via case-insensitive collapse - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` builds env entries directly from `pull_request.labels` by upcasing each label name and setting it to `"true"`, with no charset validation, allow-list, or collision handling anywhere in the chain (`PullRequest#labels` is an unvalidated serialized `Array` column). An attacker who labels their own PR `path` (or any case-variant) causes `env['PATH'] = 'true'` to be merged into `TaskCommands#env`, which flows unfiltered into `Command#unbundled_env`, overriding the safe `PATH` value that is deliberately set before merging `@env`.

### Finding Description
The broken binding: `Command#unbundled_env`'s permitted/safe key set is claimed to equal `machine_env`/`VariableDefinition`'s permitted set, but in practice `Command#unbundled_env` does `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` [1](#0-0) , meaning any key in `@env` — including `PATH` — silently overrides the safe value, with no allow-list check at this point at all.

Path traced:
1. Webhook `pull_request` event with `action: "labeled"` (or `opened`/`unlabeled`/`reopened`) is handled by `LabelCapturingHandler#process`, which calls `capture_labels` unconditionally for any active stack's PR [2](#0-1) . `capture_labels` fully replaces `pull_request.labels` with whatever label names GitHub reports as currently attached to the PR — no dedup, no charset/format validation.
2. `PullRequest#labels` is a plain serialized `Array` column with zero validations [3](#0-2) .
3. `ReviewStack#env` does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [4](#0-3) . Any label whose upcased form is `PATH` (`path`, `Path`, `PATH`, etc.) sets `env['PATH'] = 'true'`. Since `each_with_object` just overwrites the hash key, duplicate-casing labels collapse to a single `'PATH' => 'true'` entry regardless of how many casings were present — the collapse itself changes nothing material to exploitability, it's simply confirmatory.
4. `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` includes the label-derived overrides) directly into the environment used to build every `Command` for `install_dependencies` and `steps` [5](#0-4) . Unlike `Stack#trigger_task`, which filters user-supplied `env` via `definition.filter_envs(env)` [6](#0-5) , there is no equivalent filtering of `stack.env`/label-derived keys anywhere before `TaskCommands#env`.
5. `Command#initialize` stores `@env` as-is [7](#0-6) , and `start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [8](#0-7) , so the attacker-controlled `PATH` value is what the spawned shell actually uses.

No guard in the request path (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) inspects label content, and no model validation on `PullRequest#labels` or `Stack#env` restricts label-derived keys — the `EnvironmentVariables#permit`/`VariableDefinition` allow-list mechanism is never invoked for `stack.env` in `TaskCommands#env`.

### Impact Explanation
Once a review stack's next task (install dependencies or any step) runs, the shell environment's `PATH` is attacker-set to the literal string `"true"` (or any other value derived from other same-upcase label names), breaking or hijacking command resolution for every subsequent binary invocation in that task's `Command` instances, which run via `PTY.spawn` on the deploy host. Because `PATH` is a `Command`-critical variable and the override is fully attacker-controlled through PR labels on their own repository, this reaches Critical severity (RCE on deploy host) for review-stack-enabled repositories where install/step commands invoke non-absolute-path binaries. Blast radius is scoped to the review stack's own task execution environment, which shares the deploy host with other stacks/tenants.

### Likelihood Explanation
Precondition: the repository must have review stacks enabled (`ReviewStack` model in use) and have GitHub webhooks configured to this Shipit instance (already required for the engine to function). The attacker needs only to open a PR on their own fork/repo and add a label named `path` (any casing) — a fully unprivileged, repeatable action requiring no Shipit credentials, no `webhook_secret`, and no repository maintainer status.

### Recommendation
Filter/allow-list keys derived from `pull_request.labels` in `ReviewStack#env` before merging (e.g., prefix all label-derived keys, such as `LABEL_#{name.upcase}`, instead of using the bare upcased label name as the key), and/or run `stack.env`/`ReviewStack#env` output through the same `EnvironmentVariables#permit`/`VariableDefinition` allow-list used for user-supplied task env before it reaches `TaskCommands#env` and `Command#unbundled_env`.

### Proof of Concept
```ruby
test "review stack env allows PR label to override PATH" do
  stack = shipit_stacks(:review_stack) # or create a ReviewStack fixture
  pull_request = stack.pull_request
  pull_request.update!(labels: ['path'])

  assert_equal 'true', stack.env['PATH']

  # Confirm this flows unfiltered to Command
  command = Shipit::Command.new('echo hi', chdir: '/tmp', env: stack.env)
  assert_equal 'true', command.unbundled_env['PATH']
end
```
