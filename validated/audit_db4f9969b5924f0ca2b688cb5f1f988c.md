### Title
Webhook signature verification is bound to a caller-controlled `organization`/`repository.owner.login` field, but every event handler acts on the independent `repository.full_name` (or a global `sha`) field — allowing forged commit statuses / syncs against any tracked repository once *any* configured GitHub org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `params.dig('repository','owner','login')` (fallback `organization.login`) [1](#0-0) . Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, determines *which* repository/stack/commit to mutate from a completely different, unchecked field of the same JSON body — `repository.full_name` for `Handler#repository_name` [2](#0-1) , or, worse, no repository scoping at all for `StatusHandler`, which looks up `Commit.where(sha: params.sha)` globally across the entire instance [3](#0-2) . The equality the code implicitly assumes — "the organization whose secret verified this signature" == "the repository/commit the handler is about to write to" — is never enforced.

### Finding Description
`verify_signature` picks the app config via `Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)` [4](#0-3) . In `GithubApp#verify_webhook_signature`, if that organization's `webhook_secret` is blank, verification is unconditionally skipped: `return true unless webhook_secret` [5](#0-4) . `webhook_secret` is explicitly documented and templated as optional (`webhook_secret: # nil`) both for single-org and multi-org setups [6](#0-5) [7](#0-6) , and multi-org configuration (several GitHub Apps for different orgs sharing one Shipit instance) is a first-class, documented feature [8](#0-7) .

Once *one* configured organization key has no `webhook_secret`, an unauthenticated caller can `POST /webhooks` with `X-Github-Event` and a body whose `repository.owner.login` (or `organization.login`) equals that unsecured organization's name — verification then auto-passes regardless of the `X-Hub-Signature` header value or the rest of the payload. The `event()` dispatcher then routes the fully attacker-controlled body to `Shipit::Webhooks.for_event(event)` handlers [9](#0-8) , none of which re-validate that `repository.full_name` (or the bare `sha`) belongs to the organization that was actually verified.

Concretely, for a `status` event, `StatusHandler#process` finds commits purely `Commit.where(sha: params.sha)` — with zero repository/org scoping — and calls `commit.create_status_from_github!(params)` for every matching commit in the entire Shipit database, across every tracked repo/org [3](#0-2) . This directly feeds `Commit#create_status_from_github!` → `Status.replicate_from_github!` [10](#0-9) , which is exactly the signal used by `Commit#deployable?` and `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` once `deployable? && stack.continuous_deployment? && stack.deployable?` [11](#0-10) . Tests confirm a `success` status transition on a continuous-deployment-enabled stack directly creates a `Deploy` [12](#0-11) .

For a `push` event, `PushHandler#process` uses `stacks` (scoped by `Repository.from_github_repo_name(repository_name)`, i.e. `repository.full_name`) and calls `stack.sync_github(expected_head_sha: params.after)` for any non-archived stack matching the forged branch [13](#0-12) , letting an attacker who only controls the unsecured org's name resync/trigger GitHub state refresh for a target repository under a *different*, properly-secured organization.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written." An attacker needs no Shipit session, no `ApiClient` token, and no actual webhook secret — they only need to know the name of any GitHub organization configured in the Shipit instance without a `webhook_secret` (a supported/documented configuration, including the common single-org quick-start template). With that, they can forge `status` events for arbitrary commit SHAs belonging to unrelated, fully-secured repositories/stacks tracked by the same Shipit instance, artificially marking commits `success` for CI. Combined with `continuous_deployment`, this results in an **unauthorized deploy** of a commit/branch that never actually passed CI, and can also unblock manual deploys gated by `ci.require`/`Commit#deployable?`. This meets the Critical bar ("an unauthorized deploy") defined in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in realistic deployments: the only precondition is one organization entry in `config/secrets.yml` lacking `webhook_secret`, which the engine's own setup docs and templates present as optional and safe to skip, making this a plausible real-world configuration rather than an edge case. No credentials, GitHub App keys, or session cookies are required — a bare unauthenticated HTTP POST to `/webhooks` suffices.

### Recommendation
- Do not treat a blank `webhook_secret` as an automatic pass; either require a secret for any organization capable of affecting production data, or scope trust strictly to that organization's own repositories.
- After signature verification, re-derive and enforce that `repository.full_name`'s owner matches the `repository_owner`/`organization.login` used for verification before dispatching to handlers.
- In `StatusHandler` (and any other handler that doesn't scope by `Handler#repository_name`), scope commit/status lookups by the verified repository rather than a global `sha` lookup.

### Proof of Concept
1. Configure Shipit with two orgs in `config/secrets.yml`, e.g. `acme` (has a real `webhook_secret`) and `demo` (no `webhook_secret`, as the docs show is valid) — both installed on the same Shipit instance, with stacks tracking `acme/prod-app` (continuous_deployment enabled) and `demo/scratch-repo`.
2. Attacker, with no credentials, sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "sha": "<sha of the target unreleased commit on acme/prod-app>",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "demo" }, "full_name": "irrelevant/anything" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "demo")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [5](#0-4) .
4. `StatusHandler#process` finds the commit purely by `sha` (no ownership check) and records a `success` status on it [3](#0-2) .
5. If `acme/prod-app`'s stack has `continuous_deployment: true`, `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, deploying the attacker-selected commit without it ever having passed real CI [11](#0-10) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
