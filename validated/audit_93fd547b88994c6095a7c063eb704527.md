Based on my investigation, I've confirmed a concrete analog vulnerability distinct from the Uniswap router mismatch, but matching the same bug class: **a value used to select the trust anchor (which webhook secret validates the signature) is never bound to the value that is actually acted upon**.

### Title
Webhook signature is verified against the organization from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-repository forged webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. However, once the signature check passes, the actual event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolve the target repository/stack from a *different* JSON field: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together.

### Finding Description [1](#0-0) 

verifies the raw request body's signature using the GitHub App config for the organization named in `repository.owner.login`: [2](#0-1) 

Meanwhile, every handler resolves the target repository independently via `full_name`: [3](#0-2) 

`PushHandler` uses this to look up and act on stacks: [4](#0-3) 

Since Shipit supports per-organization configuration with independent `webhook_secret` values (config schema shown in `config/secrets.development.example.yml`), an attacker who controls (or has installed the Shipit GitHub App integration for) *any one* configured organization knows that organization's `webhook_secret` and can compute a valid signature for a payload where they set `repository.owner.login` to their own org (so `verify_signature` picks their own known secret) while setting `repository.full_name` to `"victim-org/victim-repo"` — a completely different repository/stack managed by the same Shipit instance. The signature check in `verify_signature` never confirms that `repository.owner.login` corresponds to the owner encoded in `repository.full_name`.

This is the exact class of bug in the referenced report: the value used to select/authorize (UniV2 router address / signing organization) is disconnected from the value the code actually operates on (UniV2 calls / the acted-upon repository).

### Impact Explanation
A successfully-signed but "wrong-organization" payload lets an attacker who only controls one configured GitHub organization forge `push`, `status`, `check_suite`, `pull_request`, or `membership` events attributed to a repository belonging to a completely different organization/team on the same Shipit instance. For `push`, this triggers `stack.sync_github(expected_head_sha: params.after)` on the victim's stacks with an attacker-chosen SHA — i.e., cross-repository writes/state manipulation without any credential belonging to the victim org. This matches the "cross-repository writes" / "unauthorized deploy" criteria (Critical/High impact band) because the org boundary that the signature is meant to enforce is bypassed by field confusion.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration per `config/secrets.development.example.yml`), and requires the attacker to control one of those organizations' webhook delivery (i.e., know that org's `webhook_secret`, which they legitimately do as the org's own GitHub App installer/admin). No access to the victim org, its secret, or any Shipit session/API token is required — only knowledge of a `full_name` value that maps to an actual `Repository` in the Shipit database (e.g., discoverable from the public Shipit UI).

### Recommendation
Bind the two fields together: after successfully verifying the signature for `repository_owner`, re-derive/require that `payload.dig('repository', 'full_name')` (or `organization.login` for org-level events) shares the same owner as `repository_owner`, and reject (422) the request otherwise. Alternatively, always look up the GitHub App configuration for verification using the exact same field (`full_name`'s owner segment) that handlers subsequently use to resolve the target repository, so a single field is both authenticated and authorized against.

### Proof of Concept
1. Shipit instance is configured with two GitHub App entries, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (per multi-org config shown in `config/secrets.development.example.yml`).
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that GitHub App/organization).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac using attacker-org secret over raw body>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-38`).
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — despite the attacker never having any credential or authorization tied to `victim-org`.
