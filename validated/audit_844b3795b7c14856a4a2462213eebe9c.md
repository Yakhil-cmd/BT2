### Title
Loss of attached deposit in `AddressRegistrar::register` due to missing refund of overpayment - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `register` function of the `AddressRegistrar` contract is a `#[payable]` method that any unprivileged NEAR account can call by attaching a deposit via a `FunctionCall` action. The function validates only that `attached_deposit >= required_deposit` (the exact storage cost), but never refunds the surplus when the deposit exceeds what is required. In the eth-implicit rejection branch it does not refund anything at all, even though no storage was written.

### Finding Description
`register` computes an exact `required_deposit` based on the bytes needed to store the `address -> account_id` mapping, and checks only a lower bound against `env::attached_deposit()`: [1](#0-0) 

If the check passes and the address is new (`Entry::Vacant`), the contract stores the mapping and returns the address, but the surplus `given_deposit - required_deposit` is never returned to the caller — the excess $NEAR is silently absorbed into the contract's balance: [2](#0-1) 

This mirrors exactly the Pyth `updatePriceFeeds` overpayment bug class: a caller attaches `msg.value`/`attached_deposit` intending to pay a fee/cost that can only be known precisely by the callee, the callee validates only `>=`, and any excess is not refunded, resulting in a permanent loss of funds for the caller.

There is an even more severe instance of the same root cause: if `is_eth_implicit(&account_id)` is true, the function returns `None` immediately, **before** even computing or checking the deposit, and any attached deposit is fully retained by the contract with zero value delivered and zero refund: [3](#0-2) 

By contrast, the collision branch (`Entry::Occupied`) does correctly refund the *entire* deposit back to the predecessor, demonstrating that the developers were aware refunds are needed in this contract but missed the success path and the early-return path: [4](#0-3) 

This is reachable directly from an ordinary, unprivileged `FunctionCall` action/receipt with an attached deposit — no validator or protocol privilege is required — and results in unauthorized retention of a caller's balance by the contract, i.e., a concrete state/balance change not intended or accounted for by the caller.

### Impact Explanation
Any user who overestimates the exact storage-byte cost (e.g., due to `storage_byte_cost` changing, incorrect off-chain fee calculation, or simply attaching a safety margin) permanently loses the excess deposit — it becomes stuck in the `AddressRegistrar` contract's balance with no code path to recover it. In the eth-implicit rejection case the entire attached deposit is lost regardless of amount, which can affect any caller who mistakenly (or is tricked into) calling `register` with an eth-implicit `account_id`. This is a direct, unauthorized balance loss for unprivileged callers — medium impact, since funds are not stolen by an attacker but are irrecoverably locked/absorbed by the contract.

### Likelihood Explanation
Likelihood is medium: this is a naturally occurring user error (attaching more deposit than the exact required storage cost, which is not trivial to compute off-chain precisely, especially if `storage_byte_cost` changes) and requires no adversarial conditions — an honest caller using the wallet-contract's registration flow with a slightly generous deposit, or any caller that (by mistake or through an integration bug) passes an eth-implicit `account_id`, will trigger the loss.

### Recommendation
- In the `Entry::Vacant` success branch, compute the exact `required_deposit` and, if `given_deposit > required_deposit`, issue a `promise_batch_action_transfer` refunding the difference to `env::predecessor_account_id()`, mirroring the pattern already used in the `Entry::Occupied` branch.
- In the `is_eth_implicit` early-return branch, refund the full `env::attached_deposit()` to the predecessor before returning `None`, since no storage is written in that path either.

### Proof of Concept
1. An unprivileged account submits a `FunctionCall` action to `AddressRegistrar::register` with `account_id = "alice.near"` and an attached deposit significantly larger than the computed `required_deposit` (e.g., 10x).
2. `register` succeeds (`Entry::Vacant` branch executes), the mapping is stored, and `Some(address)` is returned.
3. Observe that the caller's account balance decreased by the full attached deposit, while only `required_deposit` was needed for storage — the surplus remains in the `AddressRegistrar` contract account with no receipt refunding it.
4. Separately, submit `register` with `account_id = "0x1234...abcd"` (a valid eth-implicit account string) and any nonzero attached deposit; observe `None` is returned and the entire attached deposit is retained by the contract with no refund receipt generated.
