### Title
Use of Reverted/Uncached AA Response Units in Autonomous Agent Rollback Path Without Existence Validation - (File: aa_composer.js)

### Summary
The GIMP CVE-2025-14424 pattern is a use-after-free from operating on an object without validating its existence beforehand. The closest reachable analog in ocore is `revertResponsesInCaches()` in `aa_composer.js`, called from `revert()` and `dryRunPrimaryAATrigger()`, which dereferences `storage.assocUnstableUnits[first_unit].parent_units` and calls `storage.forgetUnit()` on cached in-memory unit objects without first checking that those cache entries still exist, mirroring the "no validation before performing operation on the object" root cause of the external report.

### Finding Description
`revertResponsesInCaches()` reads the first AA response unit and immediately dereferences its cached props: [1](#0-0) 
```
var objFirstUnit = storage.assocUnstableUnits[first_unit];
var parent_units = objFirstUnit.parent_units;
arrResponseUnits.forEach(storage.forgetUnit);
storage.fixIsFreeAfterForgettingUnit(parent_units);
```
There is no check that `storage.assocUnstableUnits[first_unit]` actually exists before `.parent_units` is accessed. `storage.forgetUnit()` itself has the identical unguarded-access pattern: [2](#0-1) 
```
function forgetUnit(unit){
	console.log('forgetting unit '+unit);
	if (!conf.bLight){
		console.log('parents', assocUnstableUnits[unit].parent_units);
		...
	}
	delete assocKnownUnits[unit];
	...
}
```
`forgetUnit` deletes a unit's cache entries (`assocUnstableUnits`, `assocCachedUnits`, `assocBestChildren`, etc.) without confirming the unit is still present in `assocUnstableUnits`. This code runs on the AA execution/revert path, which is reachable by any unprivileged unit poster whose payment or data trigger causes a bounce/revert of secondary AA responses (`revert()` at [3](#0-2) , invoked when "one of secondary AAs bounced with error"). If a response unit referenced in `arrResponses` has already been forgotten from the cache by a concurrent path (e.g., `shrinkCache()` [4](#0-3)  or another `forgetUnit` call), `objFirstUnit` is `undefined` and `.parent_units` throws a TypeError, crashing the node process handling AA execution — a stale/removed in-memory object reference being dereferenced without existence validation, the same root-cause class as the reported CVE (missing existence check before operating on an object).

### Impact Explanation
A crash in the AA-trigger execution path (triggered inside `handleTrigger`/`revert`/`revertResponsesInCaches`, which runs synchronously while holding the `write` mutex and inside an open DB transaction) causes the node to throw an uncaught exception during unit/AA processing. Because this occurs mid-transaction and mid-mutex-hold, it can leave the node unable to process further units, effectively halting further stabilization/confirmation of new units on that node — matching the "network unable to confirm new units" impact class. This is reachable by any user who posts a payment/data unit that triggers an AA whose secondary AA call bounces, requiring no special privilege.

### Likelihood Explanation
Triggering the specific race (an AA response unit being forgotten from cache by a background sweep like `shrinkCache` or an overlapping `forgetUnit` call in exactly the window between response creation and revert) requires a specific timing window and is not trivially forced by external input alone; it is a defense-in-depth/reliability gap rather than a directly and deterministically attacker-forced RCE-equivalent bug. The missing existence guard is a genuine code defect matching the report's root-cause pattern, but exploitability is probabilistic/timing-dependent rather than guaranteed on a single crafted unit.

### Recommendation
Add existence checks before dereferencing cached unit objects in `revertResponsesInCaches()` and `forgetUnit()`:
```js
var objFirstUnit = storage.assocUnstableUnits[first_unit];
if (!objFirstUnit)
    return console.log('revertResponsesInCaches: unit already forgotten: ' + first_unit);
```
and in `forgetUnit()`, guard the `!conf.bLight` block with `if (assocUnstableUnits[unit]) { ... }` before accessing `.parent_units`, treating a missing cache entry as a no-op rather than an implicit crash.

### Proof of Concept
1. Set up an AA network scenario where a primary AA trigger causes a chain of secondary AA calls (as in the existing test `test/aa_composer.test.js` secondary-trigger tests).
2. Arrange for one of the secondary AAs to bounce after a response unit has already been created and added to `storage.assocUnstableUnits`, while concurrently a cache-shrink/forget cycle (`storage.forgetUnit`) removes that same unit from `assocUnstableUnits` (e.g., via `shrinkCache()`'s periodic `setInterval(shrinkCache, 300*1000)`), such that when `revert()` → `revertResponsesInCaches(arrResponses)` executes, `storage.assocUnstableUnits[first_unit]` is `undefined`.
3. Observe the resulting `TypeError: Cannot read properties of undefined (reading 'parent_units')` thrown synchronously inside the AA execution/mutex-held path, crashing the node process before it can commit/process further units.
