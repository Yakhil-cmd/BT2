Based on my investigation, I found a concrete instance of the exact bug class the report describes (an unindexed/unverified field being trusted for a security-relevant decision) manifesting as a signature-binding gap in `WebhooksController`.

### Title
Webhook signature is verified against the wrong organization key when `repository.owner.login` and `organization.login` diverge, allowing cross-tenant event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which per-organization `webhook_secret` to HMAC-verify against using `repository_owner`, which falls back from `repository.owner.login` to `organization.login`. But the event-processing handlers (e.g. `PushHandler`) that mutate state operate on the `repository.full_name` field from the same payload, which is never itself covered by the signature check logic beyond being used to pick the secret. In a multi-organization deployment (`Shipit.github(organization:)` keyed config), the field used to select the verifying secret is not cryptographically bound to the field used to resolve the target repository/stack.

### Finding Description
`WebhooksController#verify_signature` computes:
```
app/controllers/shipit/webhooks_controller.rb:59-62
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

and uses it to fetch the org-specific `GitHubApp` and its `webhook_secret`:
```
app/controllers/shipit/webhooks_controller.rb:24-30
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up per-org secrets via `github_app_config(organization)` [3](#0-2) . Handlers such as `PushHandler` then act on `stacks`, which resolve the target `Repository`/`Stack` from the full payload (`repository.full_name`), independent of which field was used to choose the verifying secret [4](#0-3) .

The equality that should hold is: `organization key used to select webhook_secret == owner of the repository the handler subsequently writes to`. Because `repository_owner` falls back to the top-level `organization.login` field when `repository.owner.login` is absent, and because the HMAC only proves the payload was signed by *some* configured org's secret (not that the org matches the repository being acted upon), an attacker who controls (or compromises) one tenant's GitHub App installation/webhook secret in a multi-org Shipit deployment can craft a payload whose `organization.login` matches their own org (so it passes signature verification against their own secret) while `repository.full_name` addresses a stack belonging to a *different* tenant/org configured in the same `secrets.github` map, since `Repository.from_github_repo_name` / stack lookups are keyed purely by owner/name strings in the payload without re-checking that the repository's owner equals the organization whose secret validated the request.

### Impact Explanation
This is a cross-repository/cross-tenant write: a party who legitimately holds a valid webhook secret for one organization configured in `Shipit.github` can inject validated events (e.g. `push`, triggering `GithubSyncJob` and downstream deploy state changes) against a *different* organization's stacks, because the field proving authenticity (`organization`/`repository.owner`) is not the same field the handler trusts for targeting. This matches the report's "collisions/binding mismatch" bug class and crosses the tenant/repository trust boundary Shipit is meant to enforce between GitHub organizations sharing one instance.

### Likelihood Explanation
This requires the deployment to be configured with multiple organizations in `secrets.github` (the per-org keyed schema, see `github_default_organization`) [5](#0-4) , and requires the attacker to already possess a valid webhook secret for at least one of those organizations (e.g., as an org admin of one tenant sharing the Shipit instance, or via leak of one org's secret). It does not require compromising the target organization's own secret. This is a realistic misconfiguration/multi-tenant scenario but not exploitable by a fully anonymous, credential-less attacker against a single-org deployment.

### Recommendation
Bind the verified field directly to the resolved target: after computing `repository_owner` and verifying the signature, re-derive the acting `Repository`/`Stack` strictly from `params.dig('repository','owner','login')` (never falling back silently to `organization.login` for anything other than org-only events like `membership`), and reject/short-circuit any event whose `repository.owner.login` does not match the `organization.login` when both are present. Alternatively, verify the signature using a per-repository derived organization strictly matched against the repository the handler will subsequently mutate, rather than allowing two different payload fields to independently drive "which secret to check" versus "which repository to write to."

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `orgA` (attacker-controlled, webhook_secret known to attacker) and `orgB` (victim, has a tracked stack `orgB/victim-repo`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "organization": { "login": "orgA" },
  "repository": { "full_name": "orgB/victim-repo", "owner": {} }
}
```
   Note `repository.owner.login` is intentionally absent so `repository_owner` falls back to `organization.login` = `orgA` [1](#0-0) .
3. Attacker signs the raw body with `orgA`'s known `webhook_secret` and sends it with `X-Hub-Signature`.
4. `verify_signature` fetches `Shipit.github(organization: 'orgA')` and successfully verifies the HMAC against the attacker's own secret.
5. `PushHandler#process` still resolves and processes stacks for `orgB/victim-repo` from the full payload body, since handler logic works from the full JSON, not from `repository_owner` [4](#0-3) , triggering `sync_github`/deploy-related side effects on a stack the attacker does not control.

**Caveat**: I could not fully trace every handler's exact repository-resolution code path (e.g., `Handler` base class field parsing) within the available index to confirm 100% of handlers use `repository.full_name` independently of `repository_owner` in every case; this may require deeper verification of `app/models/shipit/webhooks/handlers/handler.rb` and each handler's `stacks` resolution, which the index only partially surfaced.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
