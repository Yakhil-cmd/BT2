### Title
`provision?` operator-precedence bug lets stale `provisioning_behavior` bypass a disabled `review_stacks_enabled` flag - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` ANDs `repository.review_stacks_enabled` with only the `allow_all?` branch; because Ruby's `&&` binds tighter than `||`, the `allow_with_label`/`prevent_with_label` branches are evaluated independently of `review_stacks_enabled`. On any repository where an admin disabled review stacks (`review_stacks_enabled == false`) but left `provisioning_behavior` at a previously configured `allow_with_label` or `prevent_with_label` value, an unprivileged PR author who opens/labels a pull request can still cause `Shipit::Stack`/`Shipit::ReviewStack` creation and enqueue provisioning.

### Finding Description
The binding the code is supposed to enforce is: `review_stacks_enabled == true` must gate every provisioning path. The actual code is: [1](#0-0) 

```ruby
def respond_to_pull_request_opened?
  params.action == "opened" &&
    provision?
end

def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby operator precedence (`&&` > `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` is only part of the first disjunct. If `review_stacks_enabled == false` and `provisioning_behavior == allow_with_label` (or `prevent_with_label`), the first term is `false`, but the second (or third) term is fully independent of `review_stacks_enabled` and can still evaluate to `true` based solely on whether the PR carries the configured label.

Path: `process` calls `respond_to_pull_request_opened?` → `provision?`, and if truthy, calls `ReviewStackAdapter#find_or_create!`, which creates a `Shipit::ReviewStack` and calls `Shipit::ReviewStackProvisioningQueue.add(stack)` to enqueue actual provisioning. [2](#0-1) [3](#0-2) 

The attacker's action is entirely within their own PR: opening a PR against the targeted (already-tracked) repository, and either adding the repo's configured `provisioning_label_name` (for `allow_with_label`) or omitting it (for `prevent_with_label`). Existing guards (`verify_signature`/`verify_webhook_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) all operate correctly here — they authenticate that the webhook genuinely originates from GitHub for that repository, they do not (and are not meant to) validate the business-logic correctness of `provision?`. `Repository` model validations only constrain `owner`/`name` format, not the `provisioning_behavior`/`review_stacks_enabled` combination.

The DB default confirms this is a realistic, not merely theoretical, state: `review_stacks_enabled` defaults to `false` and `provisioning_behavior` defaults to `allow_all`, but nothing prevents (or resets) a stale `allow_with_label`/`prevent_with_label` value being left in place after `review_stacks_enabled` is toggled off, since these are two independently settable fields on the same settings form. [4](#0-3) 

### Impact Explanation
Given the described repository state (owner-controlled, not attacker-controlled), an unauthenticated-to-Shipit but repo-owning attacker can cause `Shipit::Stack`/`Shipit::ReviewStack` records to be created and queued for actual provisioning (`ReviewStackProvisioningQueue.add` → eventual `stack.provision` → deploy) for a repository whose owner explicitly disabled this feature. This is an unauthorized deploy/provisioning action against a repository's intent, matching the Critical category ("unauthorized deploy... a payload for one repository mutating another's stack"). It is repeatable against any repository matching the precondition (`review_stacks_enabled == false` and `provisioning_behavior != allow_all`), and scales across all tenants sharing this stale configuration pattern.

### Likelihood Explanation
Requires a specific, non-default repository configuration: `review_stacks_enabled == false` combined with a leftover `provisioning_behavior` of `allow_with_label` or `prevent_with_label` (i.e., the feature was enabled once, configured with a behavior/label, then disabled without resetting the behavior selector back to `allow_all`). This is plausible given the settings UI exposes both fields independently with no coupling/reset logic. Attacker cost is minimal (open a PR, optionally add a label they can set on their own PR) and fully repeatable once the precondition holds.

### Recommendation
Add explicit parentheses/grouping so `review_stacks_enabled` gates all three branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style (minitest):
```ruby
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label + matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label + no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
With the current code, both assertions fail (`Shipit::Stack.count` increases), proving `review_stacks_enabled == false` does not block provisioning for `allow_with_label`/`prevent_with_label` behaviors — confirming the broken binding `review_stacks_enabled == true required for all branches` vs. the actual code where it only guards the `allow_all?` branch.
