### Title
Unvalidated `device_address` in shared-address signer map lets a co-signer misroute multisig signing requests - ([File: wallet_defined_by_addresses.js])

### Summary
CVE-2024-51407 describes a Floodlight SDN controller flaw where a local host can register a false broadcast port mapping, causing the controller to misroute inter-host traffic. The analogous class of bug — an endpoint being able to assert an unverified routing/location binding for another party that the system then trusts for future communication — exists in ocore's shared (multisig) address setup, specifically in `handleNewSharedAddress` in [1](#0-0) .

### Finding Description
When a shared/multisig address is created, participants exchange a `signers` map (`assocSignersByPath`) that binds each signing path in the address definition to a member `address` and the `device_address` where that member's signing key allegedly lives. `handleNewSharedAddress` validates that:
- the `definition` hashes to the claimed `address` [2](#0-1) ,
- each `signerInfo.address` is a syntactically valid address [3](#0-2) ,
- the `address` at each path matches what `extractAddressPathsFromDefinition` derives from the definition itself [4](#0-3) .

It never validates `signerInfo.device_address` against anything authoritative (e.g., that the sender is only allowed to claim device addresses for keys it actually controls, or that a previously-known device_address for that member address is not being overwritten by an unrelated peer). The only self-protecting check is `determineIfIncludesMeAndRewriteDeviceAddress`, which rewrites the device_address entries that correspond to the *local* device's own addresses [5](#0-4) ; it does nothing to validate device_address values claimed for *other* members. The whole signer map, including these unverified device addresses, is then persisted verbatim in `shared_address_signing_paths` via `addNewSharedAddress` [6](#0-5) .

This `device_address` binding is authoritative for future device-to-device signing coordination: the comment in `approvePendingSharedAddress` states explicitly that when a signature is needed later, "we'll send unsigned unit to row.device_address and it'll forward the request to signing_device_address" [7](#0-6) . Because the initial binding is taken on faith from whichever peer proposes/forwards the shared address, any single participant in a multi-party address-creation exchange can insert a wrong or attacker-controlled `device_address` for a co-signer's path. This is the ocore analog of the CVE's "false broadcast port": one peer asserts a false address→location binding that the rest of the system will use to route subsequent inter-party messages, without any independent verification of the mapping's authenticity.

### Impact Explanation
Because the resulting `shared_address_signing_paths.device_address` value determines where cosigning requests for later payments from the multisig address are routed:
- A malicious or compromised participant who helps create a shared address can bind a legitimate co-signer's `address` to a device address they control. When funds later need to move from the shared address, other legitimate parties will send the unsigned payment/signing request to the attacker-controlled device instead of the real co-signer, denying that co-signer the ability to see/approve/sign — causing loss of coordination and effectively freezing (or wrongfully diverting the negotiation of) funds held under the multisig address (AA fund loss/freezing analog: node/wallet disagreement on where authorization must come from).
- This does not directly allow the attacker to forge signatures (private keys are still required), so it does not enable unauthorized spending by itself, but it does degrade the multisig protocol's core security assumption — that the correct parties are notified to co-sign — matching the CVE's theme of "inter-host communication anomalies" causing operational disruption rather than a confidentiality break.

### Likelihood Explanation
Reachable by any unprivileged wallet counterparty during normal shared/multisig-address setup: `handleNewSharedAddress` is invoked directly from the network-facing `new_shared_address` device message handler in `wallet.js`, so no special privilege beyond being a wallet correspondent/counterparty is required to supply a malicious `signers` map. The check performed on the data is limited to definition/address consistency and does not touch `device_address`, so exploitation requires no cryptographic break — only sending a manipulated `signers` object during the pairing/shared-address exchange.

### Recommendation
Validate `device_address` claims in the `signers` map before trusting them:
- Require that a peer can only assert its own `device_address` for paths whose `address` it can prove control of (e.g., matches the sender's own address or is corroborated by the actual owner of that address, not merely by the initiator of the shared-address proposal).
- Cross-check any previously known `device_address`-to-`address` binding (e.g., from `correspondent_devices` or an existing `shared_address_signing_paths` entry) and reject/flag conflicting updates from a non-owning peer.
- Consider requiring that the device_address→address binding be confirmed directly by the owning device out-of-band, rather than solely relayed by another participant in the multisig setup.

### Proof of Concept
1. Alice, Bob, and Mallory agree to create a 2-of-3 (or `and`) shared address where Bob's public address is `BOB_ADDR`.
2. Mallory, acting as the forwarding/initiating device (or as a compromised participant relaying `new_shared_address`), constructs the `signers` object so that the path corresponding to `BOB_ADDR` has `device_address: MALLORY_DEVICE` instead of Bob's real device address, while keeping `address: BOB_ADDR` unchanged (so it still matches the definition-derived address and passes `handleNewSharedAddress`'s checks).
3. Alice's node receives this message via `handleMessageFromHub` → `case "new_shared_address"` → `handleNewSharedAddress`, which accepts it because only `address` (not `device_address`) is checked against the definition, and stores `(BOB_ADDR, MALLORY_DEVICE)` into `shared_address_signing_paths`.
4. When Alice later needs to spend from the shared address, her signing-request logic sends the co-signing request to `MALLORY_DEVICE` instead of Bob's device, per the routing logic described in `approvePendingSharedAddress`'s comment. Bob never receives the request; the transaction cannot complete (fund freeze), or Mallory gains visibility into the pending transaction intended for Bob's device.

Note: I could not fully trace the exact runtime path in `wallet_defined_by_keys.js`/composer code that consumes `shared_address_signing_paths.device_address` at spend time (grep found references in `wallet.js`, `wallet_defined_by_keys.js`, `arbiter_contract.js`, but their full bodies were not returned by search) — this should be verified in a live session for a complete call-path confirmation, though the persisted binding and its documented intended use (per the code comment) support the finding above.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
