### Title
Webhook signature verified against organization derived from an unverified payload field, decoupled from the repository actually written to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login` read directly out of the unverified request body, while the downstream event handlers resolve the `Stack`/`Repository`/`Commit` to mutate using a different field from the same body, `repository.full_name`. Nothing binds these two values together, so in a multi-tenant deployment (multiple GitHub Apps, one per organization, each with its own `webhook_secret`) a party who knows only their own tenant's `webhook_secret` can forge a validly-signed webhook whose `repository.full_name` names a different tenant's repository, causing Shipit to write commit statuses / trigger syncs against that other tenant's stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the secret used to verify `X-Hub-Signature`) using: [1](#0-0) [2](#0-1) 

`repository_owner` is computed from `params.dig('repository', 'owner', 'login')`, i.e. directly from the raw, not-yet-verified JSON body. `Shipit.github(organization:)` then loads that organization's app config (`webhook_secret`, credentials) to verify the signature: [3](#0-2) 

Once the signature check passes, the event is dispatched to a `Handler`, and every handler resolves the target repository using a *different* field of the same body, `repository.full_name`: [4](#0-3) 

For example, `PushHandler` triggers a GitHub sync for the resolved stack: [5](#0-4) 

And `StatusHandler` writes a CI status onto commits matched purely by `sha`, with no repository scoping at all: [6](#0-5) 

The engine documents that separate GitHub Apps (one per organization, each with its own `webhook_secret`) are a supported deployment model for multi-tenant use. In that configuration, the identity that successfully authenticates the request (`repository.owner.login`, matched to a known org's secret) is never checked against the identity of the repository that is actually acted upon (`repository.full_name`). This is the same bug class as the referenced report: two values that are supposed to be kept consistent (a "supply" checkpoint used both to compute and to divide) are instead read independently and never cross-validated, breaking an implicit invariant the code relies on. Here the invariant broken is:

`organization whose secret validated X-Hub-Signature` == `organization owning the repository referenced by repository.full_name`

### Impact Explanation
An attacker who administers one tenant organization's GitHub App (and therefore legitimately possesses that org's `webhook_secret`) can craft a raw POST body where `repository.owner.login` is their own org (so the HMAC they compute with their own secret is accepted) but `repository.full_name` names a victim tenant's repository. Because handlers key off `full_name`, not the field used for authentication, this lets the attacker:
- Inject fabricated commit statuses (`state`, `context`, `description`) onto real commits belonging to another tenant's repository (`StatusHandler`), which can influence `release_status?`/deployability checks used by continuous deployment, potentially causing an unauthorized deploy of a commit that hasn't actually passed CI.
- Force a `GithubSyncJob` / `sync_github` to run against another tenant's stack (`PushHandler`).
- Drive pull-request/review-stack state transitions (archive/unarchive, provisioning) for another tenant's repositories via the pull_request handlers, all of which resolve the repository via `full_name`.

This is a cross-tenant write achieved purely by forging a request body, without any repository access, Shipit session, or the victim's credentials - matching the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Likelihood is Low: it requires the multi-organization GitHub App deployment mode (distinct `webhook_secret` per org) and requires the attacker to legitimately control at least one tenant org's GitHub App/secret in that shared Shipit deployment - a real but narrower precondition than a fully public attacker. No repository push access, Shipit session, or `ApiClient` token is required, and no interception of GitHub's traffic is needed since the attacker submits their own forged request directly to the public webhook endpoint.

### Recommendation
In `WebhooksController#verify_signature` / the `Handler` base class, cross-validate that the organization used to select the verifying secret (`repository.owner.login` / `organization.login`) matches the owner encoded in the repository actually being resolved (`repository.full_name`'s owner segment) before allowing any handler to mutate state. Alternatively, resolve the target `Repository`/`Stack` using the same field that was used to pick the verifying secret, and reject the webhook if the two disagree.

### Proof of Concept
1. Deploy Shipit with per-organization GitHub Apps as documented ("Using Multiple GitHub Applications"), e.g. `OrgA` and `OrgB`, each with distinct `webhook_secret`s and both having repositories tracked in the same Shipit instance.
2. As an operator/admin of `OrgA`'s GitHub App, obtain `OrgA`'s `webhook_secret`.
3. Craft a JSON body for a `push` (or `status`) event where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST it to `/github/webhooks` with `X-Github-Event: push` (or `status`).
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, loads OrgA's app, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `PushHandler`/`StatusHandler` then resolve the target via `repository.full_name = "OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and mutate `OrgB`'s stack/commit records, even though `OrgB` never authorized or produced this request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
