Based on the retrieved code, there is a plausible analog to the `EIP-150` bug class: a value used to select the **authentication credential** is taken from the same untrusted payload as the value used to determine **what gets written**, and the two are never checked for consistency.

### Title
Webhook Signature Verified Against an Attacker-Chosen Organization While the Payload's `repository.full_name` Drives the Actual Write - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to authenticate a webhook against based on a field pulled from the *same, not-yet-verified* JSON body, then hands that whole body to event handlers which act on a *different* field of that body to decide what Stack/Repository is touched.

### Finding Description
`verify_signature` derives the organization used for HMAC verification purely from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization secret from `secrets.github`, keyed by whatever `repository_owner` resolves to: [3](#0-2) 

The HMAC check itself only proves that the raw request body was signed with the secret configured for that resolved organization — it says nothing about whether other fields inside that same body (notably `repository.full_name`, which handlers such as `PushHandler` use to locate stacks) actually belong to that organization: [4](#0-3) [5](#0-4) 

In a multi-tenant Shipit deployment (one instance, multiple GitHub organizations each with their own `webhook_secret` entry under `secrets.github`), an operator who legitimately controls Organization A's webhook secret can hand-craft a raw JSON body where `repository.owner.login` (or `organization.login`) is set to `"OrgA"` — so `Shipit.github(organization: "OrgA")` resolves to a secret they know and the HMAC passes — while `repository.full_name` is set to `"OrgB/some-repo"`, a repository they do not control. The signature check never re-validates that `repository.owner.login` and `repository.full_name`'s owner segment agree.

This is the exact shape of the reported bug class: the value that is *checked* (`repository_owner`, feeding the signature/authentication decision) is not the value that is *acted upon* (`repository.full_name`, feeding the Stack/Repository lookup and subsequent job enqueue), and nothing binds them together cryptographically or logically.

I was not able to inspect the shared `Shipit::Webhooks::Handlers::Handler` base class (not returned by search) to confirm the exact method used to scope `stacks` from `params`; the `PushHandler#process` call to `stacks.not_archived.where(branch:)` implies a `stacks` scope defined in that base class, presumably derived from `repository.full_name`/`repository.name`. This detail should be confirmed by whoever investigates further, since it determines exactly which repositories/stacks can be desynced.

### Impact Explanation
If confirmed, this allows a party who legitimately administers one organization's webhook secret within a shared, multi-tenant Shipit instance to forge webhook events (e.g. `push`) that get attributed to a different organization's repository, triggering `GithubSyncJob` for a `Stack` they do not own: [6](#0-5) 
This can desynchronize commit history/state for stacks belonging to organizations the attacker does not control, and depending on further downstream logic (continuous deployment triggers, deploy spec caching) could influence what gets deployed — an unauthorized-deploy-adjacent impact, though I could not trace this all the way to a guaranteed unauthorized `Task`/deploy creation without the missing `Handler` base class context.

### Likelihood Explanation
Requires the attacker to already be a legitimate GitHub App/organization admin for at least one organization onboarded to the same Shipit instance (i.e., they know that organization's configured `webhook_secret`), and requires the deployment to be multi-tenant (`secrets.github` configured with multiple organization keys, per `github_app_config`). This is a real, supported configuration mode per `Shipit.github_organizations`/`github_app_config`, but is a narrower precondition than a fully unprivileged external attacker.

### Recommendation
Cross-validate that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, or better, verify the signature using a secret bound unambiguously to the repository actually referenced by `repository.full_name` rather than a separately-extracted `repository.owner.login` field, so no field of the JSON body can select one trust boundary while another field of the same body is acted upon.

### Proof of Concept
1. Deploy Shipit with `secrets.github` containing two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret`.
2. As an administrator of `OrgA`'s GitHub App installation (attacker has `OrgA`'s `webhook_secret`, no access to `OrgB`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST it to `/github/webhooks`.
4. `verify_signature` resolves `repository_owner` to `"OrgA"`, verifies successfully against `OrgA`'s secret, and `PushHandler` is invoked against a payload claiming `OrgB/target-repo`, enqueueing `GithubSyncJob` for stacks scoped to `OrgB`'s repository — without ever having proven the request originated from anyone with knowledge of `OrgB`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
