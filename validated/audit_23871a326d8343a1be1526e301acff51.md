### Title
Unhandled `throw` in private-asset transfer-input validation can crash a full node processing a public unit — CWE-20 improper input handling analog to Fleet `PublishLogs` crash ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains a code path for `type: "transfer"` inputs of private, fixed-denomination assets that assumes `objValidationState.src_coin` has already been populated by the private-chain-specific caller (`indivisible_asset.js`). When this assumption is violated, the code executes `throw Error("no src_coin")` synchronously, outside of any try/catch, which is never caught anywhere up the call stack for the normal joint-broadcast path.

### Finding Description
In the `transfer` case of the input-type switch: [1](#0-0) 
```
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    ...
    if (!isPositiveInteger(src_coin.denomination))
        throw Error("no denomination in src coin");
    if (!isPositiveInteger(src_coin.amount))
        throw Error("no src coin amount");
```
`src_coin` is only ever populated by `indivisible_asset.js` when it drives `validation.validatePayment` through the dedicated *private chain* validation flow: [2](#0-1) 

This means the assumption "we always come here through the private chain flow" only holds for that specific caller. However, `validatePaymentInputsAndOutputs` is reached from the generic public `validate()` entry point (`network.js` → `validation.validate` → `validateMessages` → `validatePaymentInputsAndOutputs`) for **every ordinary broadcast/posted unit**, including one authored by any unprivileged unit poster that references a private, `fixed_denominations` asset as `payload.asset` with a `transfer`-type input. In that normal flow `objValidationState.src_coin` is never set, so the `throw Error("no src_coin")` (or the subsequent throws on missing `denomination`/`amount`) fires synchronously.

Crucially, the outer `validate()` function only wraps the initial unit-hash computation in try/catch: [3](#0-2) 
The subsequent `async.series` chain that calls `validateMessages` → `validatePaymentInputsAndOutputs` is **not** wrapped in try/catch: [4](#0-3) 

A synchronous `throw` inside that chain therefore propagates as an uncaught exception all the way to the process-level handler in `network.js`, which deliberately re-throws to kill the process: [5](#0-4) 

This is the exact bug class described in the Fleet advisory: an authenticated/normal actor (any unit poster — no special privilege needed) submits a syntactically valid but semantically unexpected message, an "unexpected input value is not handled gracefully," and the server process (here, the ocore full node / hub) terminates.

### Impact Explanation
Because the crash happens inside the mandatory unit-validation pipeline that every full/relay node runs on every broadcast unit, the same trigger unit, when relayed, will independently crash every full node that attempts to validate it. This is not merely "this one connection dies" — it is the shared, deterministic validation logic; any node (miner-equivalent/witness, hub, or ordinary full node) that receives and validates the crafted unit will hit the identical uncaught throw and self-terminate via the `process.on('uncaughtException')` handler. A single posted unit can therefore be used to repeatedly knock full nodes/hubs off the network, preventing them from continuing to validate and confirm subsequent units until manually restarted — i.e., the network's ability to confirm new units is degraded/halted wherever this unit propagates, satisfying the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Likelihood is high: constructing the malicious unit requires only (a) creating (or using an already-existing) asset with `is_private: true` and `fixed_denominations: true`, and (b) posting an ordinary unit whose payment message sets `payload.asset` to that asset and includes a `type: "transfer"` input pointing at any (even invalid) unit/message_index/output_index. No special key, node-cooperation, or race condition is needed — this is reachable purely through the standard unit-posting path (`post_joint`/`handlePostedJoint` → `handleJoint` → `validation.validate`), exactly analogous to how the Fleet vulnerability was reachable via a single authenticated gRPC call from any enrolled Launcher host.

### Recommendation
- Add an explicit, non-throwing validation check before entering the private/fixed-denomination transfer branch: if `objAsset.is_private && objAsset.fixed_denominations` and `objValidationState.src_coin` is not already populated (i.e., we are not inside the private-chain validation flow), return a normal validation error via `cb(...)` instead of throwing.
- More generally, wrap the `async.series` validation pipeline in `validate()` (or each message-type validator) in a try/catch that converts unexpected exceptions into `ifUnitError`/`ifJointError` callbacks rather than letting them escape as uncaught exceptions.
- Add a regression test that posts a public unit referencing a private, fixed-denomination asset with a bare `transfer` input and asserts that validation returns a graceful error instead of crashing the process.

### Proof of Concept
1. Create/observe an asset unit with `is_private: true`, `fixed_denominations: true` (already achievable by any asset issuer).
2. Craft and post (via `post_joint`) a new unit whose `payment` message sets `payload.asset` to that private asset's unit id, with `payload.inputs = [{ type: "transfer", unit: <any_valid_length_unit_hash>, message_index: 0, output_index: 0 }]` and a matching `outputs` array, signed normally by the attacker's own address (no special privilege required).
3. When this unit reaches `handlePostedJoint` → `handleJoint` → `validation.validate` → `validateMessages` → `validatePaymentInputsAndOutputs`, the code reaches the `transfer` case, sees `objAsset.is_private && objAsset.fixed_denominations` is true, finds `objValidationState.src_coin` unset (because this is the ordinary public-unit path, not the `indivisible_asset.js` private-chain path), and executes `throw Error("no src_coin")` synchronously.
4. This exception is not caught by any surrounding try/catch in `validate()`'s `async.series` chain, propagates up through `network.js`'s `handleJoint`/`mutex.lock` callback, and is caught only by the top-level `process.on('uncaughtException')` handler, which re-throws and crashes the entire node process — reproducing the "single authenticated request crashes the server" pattern from the Fleet advisory, but here reachable by any ordinary unit poster and impacting every node that validates the propagated unit.
