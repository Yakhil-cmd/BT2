### Title
CCMenu API token stack-scope bypass allows reading arbitrary stack's build/deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`CCMenuController#stack` resolves the target stack directly from `params[:stack_id]` instead of going through the stack-scoped lookup that every other API controller uses, so an `ApiClient` token that is scoped to a single stack (`current_api_client.stack_id`) can be reused to read the build/deploy status of any other stack in the instance.

### Finding Description
`Shipit::Api::BaseController` defines the standard, scope-aware accessor: it restricts the visible stacks to the ones the token is authorized for before resolving the requested `stack_id`. [1](#0-0) 

`Shipit::Api::CCMenuController` overrides `stack` and bypasses this scoping entirely, resolving the stack directly from the global `Stack` relation: [2](#0-1) 

The controller's only authorization gate is the generic `require_permission :read, :stack`, which only checks that the token has the `read:stack` permission string, not that the permission applies to *this* stack: [3](#0-2) [4](#0-3) 

This reproduces the report's bug class exactly: the binding "stack a token authorizes" (`ApiClient#stack_id`) is checked and enforced everywhere else (`BaseController#stacks`/`#stack`) but is never covered when the actual per-request stack is resolved in `CCMenuController`. Just like the audited protocol providers assumed rewards would "never resume" and hard-coded that assumption instead of building a generic claim path, `CCMenuController` assumes it will only ever be called with the caller's own stack and hard-codes an unscoped lookup instead of reusing the scoped one.

The `CCMenuUrlController` that mints these tokens for users is consistent with the intended model of "one token, one stack": it requests `read:stack`-only permission and generates a URL bound to a specific `stack_id`: [5](#0-4) 
Note also that `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` does not pass `stack:` to `create_with`, so the underlying `ApiClient` created this way is not stack-scoped at all in this codebase version — this widens exposure further since even the "legitimate" ccmenu token already has `stacks == Stack.all` per `BaseController#stacks`. Regardless of that, any `ApiClient` that an administrator does explicitly scope to one stack via the web UI (`ApiClient belongs_to :stack, optional: true`) is still not protected by `CCMenuController`, because its `stack` method never consults `current_api_client.stack_id`.

### Impact Explanation
CCMenu tokens are designed to be distributed to third parties/embedded tools (CCTray dashboards, status badges) and are explicitly meant to be stack-scoped, lower-trust credentials. Because `CCMenuController#stack` ignores `current_api_client.stack_id`, holding any valid `read:stack`-permissioned token (however narrowly scoped it was intended to be) is sufficient to read the deploy/rollback status (`stack.deploys_and_rollbacks.last`) of every stack in the Shipit instance by supplying a different `stack_id` parameter. This is an unauthenticated-relative-to-scope read of stack state/deploy output, matching the High-severity class "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation only requires possession of any single valid API token with `read:stack` permission — including a token an operator deliberately restricted to one stack — and knowledge or guessing of another stack's `to_param` (which is typically `owner/repo/environment`, often discoverable/public). No privileged account, GitHub credentials, or session is needed beyond the leaked/legitimate ccmenu token, which is exactly the kind of token expected to circulate outside fully trusted parties.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the stack-scope binding enforced elsewhere in the API is also enforced here.

### Proof of Concept
1. Admin creates (or the app auto-creates via `CCMenuUrlController#fetch`) an `ApiClient` intended to be scoped to `stack_id = A` with permission `read:stack`.
2. Attacker obtains this token (e.g., from a public CI badge URL, embedded CCTray config, or leaked link) — token: `T`.
3. Attacker requests `GET /api/stacks/<STACK_B>/ccmenu.xml?token=T` where `STACK_B` is a different stack than the one the token was meant for.
4. `CCMenuController#authenticate_api_client` authenticates `T` successfully; `require_permission :read, :stack` passes because `T` has the `read:stack` string permission; `stack` resolves `STACK_B` via unscoped `Stack.from_param!`, and the response discloses `STACK_B`'s latest deploy/rollback status — despite `T` never being authorized for `STACK_B`.
