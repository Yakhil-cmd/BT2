### Title
Webhook signature is verified against the organization in `repository.owner.login`, but the repository actually acted upon is taken from the unrelated `repository.full_name` field, allowing cross-organization stack manipulation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the incoming webhook signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1)  However, once the signature passes, the event handlers that actually act on the payload (e.g. `PushHandler`, `CheckSuiteHandler`) resolve the target repository from a completely different field of the same JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2) [4](#0-3) 

### Finding Description
The verification step and the action step trust two different, uncorrelated fields:
- Signature verification binds trust to `repository.owner.login` (or `organization.login`) to pick the per-organization webhook secret via `Shipit.github(organization: repository_owner)`. [5](#0-4) 
- The handler that performs the actual write (triggering `stack.sync_github` for `PushHandler`, or scheduling check-run refreshes for `CheckSuiteHandler`) resolves the affected `Repository`/`Stack` using `repository.full_name` via `Handler#repository_name` / `#stacks`. [3](#0-2) 

Because `verify_webhook_signature` only checks the HMAC of the raw body against the secret configured for whatever organization `repository.owner.login` names, an actor who legitimately controls (or knows the webhook secret of) Organization A's app configuration can craft a raw payload where `repository.owner.login` = `"org-a"` (to select and pass verification with Org A's secret) while `repository.full_name` = `"org-b/some-tracked-repo"` (a Stack belonging to a different, unrelated organization). The controller never cross-checks that these two fields refer to the same repository/organization before dispatching to handlers. [6](#0-5) 

This breaks the intended binding: "organization authenticated == repository written." The signature authenticates *an* organization's app, but the write target (which `Stack` gets `sync_github` called on, which commits get check-runs refreshed, etc.) is controlled by an independent, unauthenticated-relative-to-org field in the same body.

### Impact Explanation
If Shipit is configured with multiple GitHub organizations/apps (each with its own `webhook_secret`, as supported by `Shipit.github(organization:)` / `GithubOrganizationUnknown` handling [7](#0-6) ), a party trusted with Org A's webhook secret can trigger unauthorized actions against Org B's tracked stacks (e.g., forcing `sync_github` on an arbitrary branch/stack, or check-run refresh jobs) purely because the "owner" field used for signature routing is decoupled from the "full_name" field used for the actual DB lookup. This is an authorization-boundary violation between tenants/organizations within the same Shipit instance, matching the "organization authenticated versus repository written" analog explicitly called out as in-scope.

### Likelihood Explanation
Exploitation requires the attacker to already possess a valid webhook secret for at least one organization configured in the Shipit instance (a precondition inherent to any multi-org GitHub App setup, not requiring a Shipit session, API token, or privileged account) and knowledge that another organization's repository is tracked by the same instance. Given these two engine-level identity handling functions are the ones enforcing the trust boundary and neither cross-validates `owner.login` against `full_name`'s prefix, exploitation is a straightforward crafted-payload replay once the org-A secret is known.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select/verify the webhook secret is the same organization that owns the repository ultimately acted upon — e.g., assert that `payload.dig('repository', 'full_name')` starts with `"#{repository_owner}/"`, or resolve `repository_owner` directly from `repository.full_name` instead of a separately-nested `owner.login`/`organization.login` field.

### Proof of Concept
1. Shipit instance tracks stacks for both `org-a/repo` and `org-b/repo`, each organization configured with its own GitHub App/`webhook_secret`.
2. Attacker holds `org-a`'s webhook secret (e.g., a legitimate but limited integrator for Org A).
3. Attacker crafts a `push` payload body:
   ```json
   { "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/repo" },
     "ref": "refs/heads/master", "after": "<attacker-chosen sha>" }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org_a_secret, raw_body)` and POSTs to `/github/webhooks`.
5. `verify_signature` computes `repository_owner == "org-a"`, fetches Org A's `github_app`, and the HMAC matches → verification passes. [5](#0-4) 
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on Org B's stack, despite the request never being authenticated by Org B's secret. [4](#0-3)
