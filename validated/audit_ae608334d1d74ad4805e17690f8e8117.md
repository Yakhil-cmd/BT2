### Title
Stale `account.owner` grants post-transfer spending authority: `require_owner_or_delegate` validates the stored owner instead of the live position-NFT owner - (File: contracts/controller/src/account.rs)

### Summary
The Mastodon report describes a controller that validated access against the wrong policy namespace, letting an unauthorized user reach privileged data. The analog here is an authority-namespace split in the controller: account spending operations authenticate against the `owner` field stored in the `Account` struct at mint time, while account metadata operations authenticate against the live NFT owner via `storage::account_owner`. If the stored `Account.owner` is not re-synchronized when the position NFT is transferred — and there is no transfer callback from `position-nft` into the controller that would do so — the previous NFT holder retains full owner/delegate spending authority over the account forever, and the new holder is locked out of (or unable to fully control) the position they just bought.

### Finding Description
`Account` is created with `owner` fixed at mint time and never rewritten (`create_account_with` stores `owner: owner.clone()`). All value-moving entrypoints (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) gate on `require_owner_or_delegate(env, account_id, caller, &account.owner)`, which passes whenever `caller == account.owner` — the stored, mint-time owner. Separately, `require_account_owner` (used by `renew_account`, `add_delegate`, `remove_delegate`) checks `storage::account_owner(env, account_id)`, i.e., the current NFT `owner_of`. So the codebase itself acknowledges two different notions of "account owner," but applies the stale one to the endpoints that move funds. Delegation compounds this: `is_owner_or_delegate` resolves the delegate list under the stored owner (`get_delegates(env, account_id, owner)`), so delegates the prior owner granted keep authority after transfer, while any delegates the new owner adds via `add_delegate` are recorded under the new owner key and never match `account.owner` on the spending path.

### Impact Explanation
An address that transfers (sells, or is phished into transferring) its position NFT retains the ability to call `withdraw`/`borrow`/`swap_collateral`/`repay_debt_with_collateral` against `account_id`: `caller.require_auth()` succeeds (they sign), and `require_owner_or_delegate` succeeds because `account.owner` still equals their address. They can drain all collateral and max out borrows, leaving the new NFT holder with a hollowed or liquidated account. This is theft of user funds reachable by a single unprivileged address. (Severity caveat: if a sync mechanism exists that I did not surface — e.g., `storage::get_account` resolving `owner` live — the finding collapses; the split between `account.owner` and `storage::account_owner` usage is confirmed, the absence of a resync is the unverified premise.)

### Likelihood Explanation
Position NFTs are transferable/approvable by design (`transfer`/`approve` are in the allowed reachability list). Secondary-market transfers or wallet migrations are ordinary events, and a prior owner exploiting retained authority requires only signing one `withdraw` call — no race, no privileged role, no oracle manipulation.

### Recommendation
Resolve spending authority from the live NFT owner: in `is_owner_or_delegate`/`require_owner_or_delegate`, replace the `owner` argument taken from the stored `Account` with `storage::account_owner(env, account_id)` (as `require_account_owner` already does), and key the delegate map to the current owner, or migrate delegates on transfer. Alternatively, remove the redundant `owner` field from `Account` so only one authority source exists.

### Proof of Concept
1. Alice supplies collateral and opens an account; `account_id` NFT is minted to Alice (`account.owner = Alice`).
2. Alice transfers the position NFT to Bob (or an attacker contract buys it on a marketplace).
3. Alice calls `controller.withdraw(caller=alice, account_id, …)` (or `borrow` with `receiver=alice`).
4. `alice.require_auth()` passes; `require_owner_or_delegate` compares `alice == account.owner` → true, since `account.owner` was never updated.
5. Collateral/debt proceeds go to Alice's receiver; Bob's NFT now fronts an empty or deeply leveraged account.

Supporting code: `create_account_with` fixes `owner` at mint ( [1](#0-0) ), spending guards use the stored `account.owner` ( [2](#0-1) ), `is_owner_or_delegate` accepts `caller == owner` and reads delegates under that stored owner ( [3](#0-2) ), while `require_account_owner` correctly uses the live NFT owner, proving the two namespaces diverge ( [4](#0-3) ).

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
