## Title
Webhook signature verified against the payload's `organization`/`owner.login` field while the mutated `Stack` is selected by the payload's separate `repository.full_name` field, allowing cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC against using `repository_owner`, a value read directly from the unauthenticated JSON body (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, the actual event handlers (`Handler#stacks`) resolve the `Stack`/`Repository` to act on using a *different* field from the same unauthenticated body: `repository.full_name`. Because Shipit supports multiple GitHub organizations, each with its own webhook secret [1](#0-0) , nothing binds the organization whose secret validated the signature to the organization actually written to.

## Finding Description
`verify_signature` computes the signing key from `repository_owner`: [2](#0-1) [3](#0-2) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization key in `secrets.github` [1](#0-0) , confirming that in the documented multi-org configuration each org has an independently held webhook secret (see `docs/setup.md`'s "Using Multiple Github Applications" section).

After the signature check passes, `create` dispatches the *entire, unvalidated* JSON body to the registered handler for the event [4](#0-3) . Handlers resolve the target `Stack`s via `Handler#stacks`, which looks up the `Repository` using `repository.full_name` — a field independent from the `repository.owner.login` used to pick the verifying secret: [5](#0-4) 

`PushHandler#process`, for example, uses this `stacks` scope to trigger `stack.sync_github` for any matching stack: [6](#0-5) 

This mirrors the reported bug class exactly: the report's `unstake_percent` fed three independent floor divisions that should have been derived from one another (`delta_share`), so a value could be manipulated to satisfy one check while breaking an implicit invariant on another. Here, `repository.owner.login`/`organization.login` (used for authentication) and `repository.full_name` (used for authorization/target selection) are two independently attacker-supplied fields inside the same unauthenticated JSON body that are never checked for consistency — the HMAC only proves "this body was signed with organization X's secret," not "the `repository.full_name` inside this body belongs to organization X."

An attacker who legitimately controls a GitHub repository/organization onboarded to the same Shipit instance (and therefore possesses that org's webhook secret via GitHub's webhook settings UI, which display the secret is write-only but the attacker as repo admin can freely reconfigure/resend deliveries and can craft arbitrary bodies signed with a secret they set) can produce a validly-signed payload where `repository.owner.login` is their own org, but `repository.full_name` names a `victim-org/other-repo` tracked by Shipit under a different, unrelated GitHub App/secret.

## Impact Explanation
If exploitable, this breaks the binding: `organization authenticated by webhook_secret` == `repository written by handler`. Depending on handler, consequences include forcing `GithubSyncJob`/`sync_github` on an arbitrary victim stack (`PushHandler`), injecting fabricated `Status`/`check_suite` results influencing merge-queue and deploy gating (`StatusHandler`, `CheckSuiteHandler`), or manipulating `pull_request`/`membership` state for a repository the attacker does not control. This falls under "cross-repository writes" from the given impact list, since a webhook authenticated for org A causes state changes to a stack that belongs to org B's repository.

## Likelihood Explanation
Exploitability strictly requires the attacker to already have legitimate GitHub webhook-secret possession for *some* org/repo that is separately configured in the same Shipit instance's multi-org config — i.e., this only matters for Shipit deployments serving multiple, mutually-untrusting GitHub organizations sharing one instance (the documented "Using Multiple Github Applications" mode). Under that documented deployment model, no additional privilege beyond configuring one's own org's webhook (which the attacker already legitimately controls) is needed to cross into another org's data — this is exactly an "unprivileged attacker" relative to the victim org.

## Recommendation
After verifying the HMAC signature with the secret selected via `repository_owner`, cross-check that the `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, resolve the target `Repository`/`Stack` first and verify the signature using the secret configured for *that* resolved repository's organization, not a value taken from an independent, unauthenticated field) before dispatching to handlers.

## Proof of Concept
1. Configure Shipit in multi-org mode with two orgs, `attacker-org` and `victim-org`, each with independent `webhook_secret`s, both tracking stacks in the same Shipit instance [7](#0-6) .
2. Attacker, who administers a GitHub repo under `attacker-org` with a Shipit webhook already configured, crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "victim-org/some-repo", "owner": { "login": "attacker-org" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully validates the signature [2](#0-1) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/some-repo")` [5](#0-4)  and triggers `sync_github` on `victim-org`'s stack, despite the request never being signed with `victim-org`'s secret.

**Note on verification confidence:** I was not able to inspect `StatusHandler`, `CheckSuiteHandler`, or `MembershipHandler` bodies in full within this pass to confirm each one's exact write-impact, nor could I confirm whether GitHub's own webhook delivery/replay UI would realistically let an attacker set an arbitrary `repository.full_name` inconsistent with the delivering repo (GitHub-originated webhooks always set these fields consistently — this analog requires the attacker to forge/replay a raw HTTP request directly, not merely use GitHub's "redeliver" UI). This is a structural code-level gap (unauthenticated fields used inconsistently across signature-scoping and object-resolution) rather than a confirmed field-replay exploit against real GitHub webhook delivery semantics.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

  github:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
