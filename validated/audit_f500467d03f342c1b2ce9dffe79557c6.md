### Title
Webhook signature is bound to the wrong org identity, letting an unauthenticated caller forge CI status on any stack served by the same Shipit instance - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/secret to verify a webhook against using `repository.owner.login` (or `organization.login`), but every event handler that actually mutates state picks the target `Repository`/`Stack`/`Commit` using the independent `repository.full_name` field of the same JSON body [1](#0-0) . Because `GithubApp#verify_webhook_signature` unconditionally returns `true` when the resolved org has no `webhook_secret` configured [2](#0-1) , and a blank `webhook_secret` is a documented, supported configuration [3](#0-2) [4](#0-3) , an attacker with no GitHub credentials at all can satisfy `verify_signature` by naming a "no-secret" org in `repository.owner.login`, while pointing `repository.full_name` (and other event fields) at a completely unrelated org/repository hosted on the same instance.

### Finding Description
The binding that should hold is: *the organization whose signature was verified == the repository the handler is allowed to act on*. It does not.

- Signature check uses `repository_owner`: [5](#0-4) 
- `verify_webhook_signature` trivially passes for orgs configured without a `webhook_secret`: [2](#0-1) 
- Every `Handler` subclass instead resolves the acted-upon repository/stack from `repository.full_name`, a sibling field of the same attacker-controlled payload, never cross-checked against `repository_owner`: [6](#0-5) 
- `StatusHandler` is even more permissive: it looks up commits **globally by SHA**, with no repository scoping whatsoever, and writes a `Status` record from fully attacker-controlled fields (`state`, `description`, `target_url`, `context`): [7](#0-6) 

Those `Status` records feed directly into deploy/merge-gating logic: `MergeRequest::StatusChecker` and `all_status_checks_passed?` / `any_status_checks_failed?` decide whether a pull request is `pending`/mergeable purely from the `Status` rows attached to the commit [8](#0-7) , and `merge!` calls `stack.github_api.merge_pull_request` once `not_mergeable_yet?` is false [9](#0-8) .

### Impact Explanation
Because the org authenticated by the signature (`repository.owner.login`) is never the same value verified against the repository the handler mutates (`repository.full_name`), an attacker who is not a member, collaborator, or credential-holder for a target org/stack can:
- Inject fake "success" CI statuses on real commits of a stack they have no access to (via `StatusHandler`, which is entirely unscoped by repository), causing the merge queue to consider a PR mergeable and Shipit to call `merge_pull_request` — an unauthorized merge/deploy path, one of the explicit Critical impacts in scope.
- Trigger `GithubSyncJob`/webhook-driven side effects (push/check_suite/pull_request handlers) against stacks belonging to organizations the attacker has no relationship with, as long as any org on the instance is configured with a blank `webhook_secret` (a state the shipped documentation and default secrets templates actively encourage/allow).

This requires no `ApiClient` token, no Shipit session, no GitHub App private key, and no repository write access — only knowledge that some org on the instance has `webhook_secret` unset, which is visible from the same public docs shipped with the engine.

### Likelihood Explanation
Multi-org Shipit deployments are an explicitly documented, first-class configuration [3](#0-2) , and `webhook_secret` is shown as optional/nilable in the same docs and in the shipped secrets templates [10](#0-9) . Any operator who configures at least one org without a webhook secret (e.g., during setup, testing, or because that org has no webhook-triggered automation) unknowingly opens every other org/stack on the same instance to unauthenticated status/webhook forgery — no special conditions or races are needed, unlike the front-run timing required in the Napier analog.

### Recommendation
- Bind the verified webhook identity to the resource the handler is allowed to act on: after `verify_signature` succeeds for `repository_owner`, require that every field used by handlers to select a `Repository`/`Stack`/`Commit` (`repository.full_name`, `organization.login`, etc.) matches that same verified owner before dispatching to `Shipit::Webhooks.for_event(event)`.
- Scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to the verified repository/organization, not globally by SHA.
- Do not allow `verify_webhook_signature` to unconditionally return `true` when `webhook_secret` is blank for a configured org; either require a secret for every org or refuse to process any webhook naming a repository owned by a different org than the one whose secret matched.

### Proof of Concept
1. Configure Shipit with two orgs: `orgA` (attacker-known, `webhook_secret: nil`) and `orgB` (victim, has a stack with merge-queue enabled and a pending PR whose CI status is currently `pending`/`failure`).
2. Attacker sends, without any credentials:
```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "sha": "<victim PR head sha in orgB>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
3. `verify_signature` resolves `repository_owner` = `"orgA"`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature` [11](#0-10) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit in `orgB` regardless of the `repository` block content — and creates a forged `success` status on it [12](#0-11) .
5. The victim's merge queue now sees the required check as passing and proceeds to `merge!`, merging/deploying code the attacker never had access to trigger.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
