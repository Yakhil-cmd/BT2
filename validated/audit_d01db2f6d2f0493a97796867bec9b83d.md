### Title
Webhook signature verified against attacker-controlled organization while the acted-upon repository is read from a different unchecked field, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-GitHub-App Shipit deployment (`secrets.github` keyed by organization, as documented in `docs/setup.md`), each organization has its own `webhook_secret`. `WebhooksController#verify_signature` picks which secret to verify against using `repository_owner`, a value read straight out of the unauthenticated JSON body, then verifies the raw body against that org's HMAC. Every webhook handler, however, determines the actual `Repository`/`Stack` to mutate using a *different* JSON field, `repository.full_name`, with no cross-check that it belongs to the same organization whose secret validated the request.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

`lib/shipit.rb#github` returns a per-organization `GitHubApp` instance (and thus a distinct `webhook_secret`) keyed by that same organization string:

The binding the code implicitly assumes is: `organization authenticated by webhook_secret == organization owning the repository the handler operates on`. Nothing enforces this. The signature check proves only "this body was signed with OrgA's webhook secret" — not "this body's `repository.full_name` belongs to OrgA."

### Impact Explanation
In a `secrets.github` multi-org configuration (as documented in `docs/setup.md` "Using Multiple Github Applications"), an attacker who legitimately controls one onboarded organization (OrgA — e.g., they administer that GitHub App/organization and thus know or can generate a valid signature with OrgA's `webhook_secret`) can send a crafted webhook body where `repository.owner.login = "OrgA"` (satisfying `verify_signature`) but `repository.full_name = "OrgB/some-repo"` (a repository belonging to a completely different, unrelated organization managed by the same Shipit instance). Because the handlers key exclusively off `repository.full_name`, this forged, fully attacker-controlled payload (arbitrary `ref`, `after` SHA, PR state, labels, sender login, etc.) is applied to OrgB's stacks — triggering `GithubSyncJob`/deploy pipeline sync, review-stack provisioning/archival, or label-driven behavior for a repository the attacker never had legitimate access to. This is a cross-organization write into stack state driven entirely by attacker-supplied data, crossing an authentication boundary the system was designed to enforce per-organization.

### Likelihood Explanation
This requires the deployment to use the documented multi-org GitHub App configuration and requires the attacker to legitimately control at least one of the configured organizations' GitHub App/webhook secret — a realistic scenario for Shipit instances that centrally manage deploys for many orgs/teams, since "controlling one onboarded org" is a normal, unprivileged position for many of its users, not a privileged Shipit account or leaked infra secret.

### Recommendation
After signature verification, re-derive the repository from the same `repository_owner` used to pick the signing organization (or otherwise verify `repository.full_name`'s owner segment equals the `organization` whose secret validated the request) before dispatching to any handler; reject the webhook if they disagree.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, both managing stacks in the same Shipit instance (per `docs/setup.md` multi-app setup).
2. Attacker controls `OrgA`'s GitHub App/webhook secret (legitimately, as its org admin) and crafts a `push` event JSON body: `repository.owner.login = "OrgA"`, `repository.full_name = "OrgB/target-repo"`, `ref = "refs/heads/master"`, `after = "<attacker-chosen sha>"`.
3. Attacker computes `X-Hub-Signature` using OrgA's known `webhook_secret` over the raw body and POSTs to the Shipit webhook endpoint.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and passes, since the HMAC matches OrgA's secret.
5. `PushHandler` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and enqueues `GithubSyncJob`/deploy sync for OrgB's stack using the attacker's chosen `ref`/`after`, despite the attacker having no relationship to OrgB.
