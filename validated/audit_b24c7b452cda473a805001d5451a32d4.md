### Title
Cross-organization commit-status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` binds the HMAC signature check to the organization named in the payload's `repository.owner.login` field, selecting the corresponding `Shipit.github(organization:)` app/secret for verification. But once verification succeeds, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that binding: it looks up commits purely by SHA, globally, across every stack/repository/organization tracked by the installation, and writes a GitHub-sourced status onto whatever `Commit` rows match.

### Finding Description
The signature check in `app/controllers/shipit/webhooks_controller.rb` derives the organization from the payload and verifies against that organization's webhook secret: [1](#0-0) [2](#0-1) 

This establishes the binding: *organization that authenticated the signature == organization whose commits should be mutated by this payload*.

`StatusHandler`, however, does not use `repository_name`/`stacks` scoping at all (unlike `PushHandler`, which does scope via `stacks.not_archived.where(branch:)`): [3](#0-2) 

It queries `Commit.where(sha: params.sha)` unscoped by repository or organization, and calls `commit.create_status_from_github!(params)` for every match found anywhere in the database: [4](#0-3) 

Because `Commit#stack` (and thus its owning `Repository`/organization) is not checked, if any two stacks tracked by the same Shipit instance (e.g., different organizations, or a fork with shared history) happen to contain a `Commit` row with the same `sha` — which is very plausible for forked/mirrored repositories, cherry-picks, or squash-merged commits shared across repos — a `status` webhook whose signature was validated against Organization A's webhook secret can write a fabricated CI status onto a commit that actually belongs to Organization B's stack.

`Handler#stacks`/`Handler#repository_name` exist and are used by other handlers (`PushHandler`) precisely to enforce this binding, confirming that its absence in `StatusHandler` is the root cause: [5](#0-4) [6](#0-5) 

### Impact Explanation
A forged/legitimate-but-misattributed `success` status can flip `Commit#deployable?` for a commit belonging to a different organization's stack: [7](#0-6) 

Combined with `continuous_deployment`, this can trigger `schedule_continuous_delivery`/`ContinuousDeliveryJob`, causing Shipit to autonomously deploy a commit whose CI status was manipulated by an actor who only controls a different, unrelated organization's webhook — i.e., an unauthorized deploy triggered across an organization boundary that the signature was supposed to isolate.

### Likelihood Explanation
Requires the attacker to control (or already receive genuine, signed) `status` webhook deliveries for at least one organization installation tracked by the same Shipit deployment (a legitimate, unprivileged scenario for any repo owner using shared/multi-tenant Shipit), and requires a SHA collision between a commit under attacker's own organization and a commit tracked under the victim stack. This is realistic for forked repositories, mirrors, or repositories that share commit history (common in multi-org monorepo-style setups), making this a credible medium-to-high likelihood path rather than a purely theoretical one.

### Recommendation
Scope `StatusHandler#process` (and any other handler using raw SHA/global lookups) to the repository named in the payload, exactly as `PushHandler` does via `stacks`/`repository_name`, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or equivalently filter `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))` before applying the status.

### Proof of Concept
1. Shipit tracks `stackA` (org `Attacker`) and `stackB` (org `Victim`), both containing a `Commit` row with identical `sha` `"c0ffee..."` (e.g., because `stackB`'s repo was forked into `Attacker`'s org, sharing history).
2. Attacker triggers (or has GitHub emit) a real `status` webhook for their own repo `Attacker/repo` referencing commit `c0ffee...` with `state: "success"`.
3. `WebhooksController#verify_signature` succeeds because it correctly verifies against `Attacker`'s webhook secret (`repository_owner` = `Attacker`).
4. `StatusHandler#process` runs `Commit.where(sha: "c0ffee...")`, which returns **both** `stackA`'s and `stackB`'s commit rows, and creates a "success" status on `stackB`'s commit belonging to `Victim`.
5. If `stackB.continuous_deployment?` is enabled and this was the blocking status, Shipit deploys the `Victim` commit as deployable — an unauthorized deploy driven entirely by a webhook signed for the `Attacker` organization.
