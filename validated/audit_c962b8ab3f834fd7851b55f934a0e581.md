### Title
`DenyReserveTransferToRelayChain` in Asset Hub Kusama's Barrier does not recurse into `SetAppendix`/`SetErrorHandler` nested programs, allowing the reserve-transfer-to-relay deny rule to be bypassed - (File: system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs)

### Summary
Asset Hub Kusama's `Barrier` wraps the deny-filter as plain `DenyReserveTransferToRelayChain`, not `DenyRecursively<DenyReserveTransferToRelayChain>`. [1](#0-0)  Other chains in the same codebase (e.g. Bridge Hub Polkadot, Bulletin Polkadot) explicitly wrap the same filter with `DenyRecursively` to close exactly this gap, confirming the base filter alone is insufficient against nested instructions. [2](#0-1) [3](#0-2) 

### Finding Description
`DenyReserveTransferToRelayChain::should_execute` scans only the top-level slice of `Instruction`s passed to the barrier, matching `InitiateReserveWithdraw`, `DepositReserveAsset`, and `TransferReserveAsset` variants whose destination/reserve is `Location { parents: 1, interior: Here }` (the Relay Chain). It does not descend into the nested `Xcm<Call>` payloads carried by `SetAppendix(xcm)` or `SetErrorHandler(xcm)` instructions — those payloads are separate instruction vectors invisible to a flat iterator over the outer instruction slice.

The XCM executor's barrier (`Barrier::should_execute`) is only invoked once, against the top-level program submitted via `pallet_xcm::execute` (or via XCMP/UMP ingestion), before execution begins. When the executor later runs the appendix (`SetAppendix`) or the error handler (`SetErrorHandler`) as part of normal instruction processing, it does **not** re-invoke the `Barrier` on those nested instruction lists. This means any reserve-transfer instruction hidden inside a `SetAppendix`/`SetErrorHandler` payload is executed without ever being checked by `DenyReserveTransferToRelayChain`.

The codebase itself demonstrates awareness of this exact gap: Bridge Hub Polkadot and Bulletin Polkadot wrap the filter as `DenyRecursively<DenyReserveTransferToRelayChain>`, whose purpose is specifically to recurse into `SetAppendix`/`SetErrorHandler` nested programs at admission time and re-apply the inner deny rule. [2](#0-1)  Asset Hub Kusama (along with Asset Hub Polkadot, Collectives, Coretime and People chains, and Bridge Hub Kusama) uses only the non-recursive form. [4](#0-3) [5](#0-4) 

Attacker path: a signed AssetHub account calls `pallet_xcm::execute` (permitted for any local signed origin via `LocalSignedOriginToLocation`/`EnsureXcmOrigin`). [6](#0-5)  The submitted top-level program satisfies `AllowTopLevelPaidExecutionFrom<Everything>` (e.g. `WithdrawAsset` + `BuyExecution`) so the barrier admits it — the top-level instruction list contains no directly-matching `DepositReserveAsset{dest: Parent, ..}` instruction, only a `SetAppendix([DepositReserveAsset{dest: Parent, ..}])` instruction, which the flat deny-scan does not recognize. [7](#0-6)  Once admitted, the executor runs the main program (loading KSM into holding via `WithdrawAsset`) and subsequently executes the appendix, which performs `DepositReserveAsset{dest: Parent, ..}` against the Relay Chain sovereign/reserve account without ever re-checking the deny filter.

### Impact Explanation
An unprivileged signed AssetHub user can perform a reserve-asset transfer of KSM to the Relay Chain sovereign account despite the runtime's explicit intent (enforced everywhere else via `DenyReserveTransferToRelayChain`) to disallow this asset-routing path, violating the intended reserve-transfer routing invariant for Asset Hub ↔ Relay Chain KSM movement. This does not create a fund-duplication bug by itself, but it defeats an intended safety/routing control that the runtime relies on to prevent KSM reserve transfers back to the Relay Chain (a path the Relay Chain does not expect and could interact incorrectly with Relay Chain accounting/migration assumptions).

### Likelihood Explanation
The precondition is only a signed account with a small KSM balance (to cover `BuyExecution` and the transferred amount) and access to `pallet_xcm::execute`, which is a standard, permissionless, already-supported extrinsic path. [8](#0-7)  No governance, proxy abuse, or privileged origin is required, and the technique (wrapping deny-triggering instructions in `SetAppendix`/`SetErrorHandler`) is a well-known, previously-identified pattern in the polkadot-sdk ecosystem (hence the existence of `DenyRecursively` and its use on other chains in this very repository), making the exploit straightforward and repeatable.

### Recommendation
Wrap the deny filter in `DenyRecursively` for Asset Hub Kusama (and Asset Hub Polkadot, Collectives, Coretime, People, and Bridge Hub Kusama, which have the same gap), matching the pattern already used in `bridge-hub-polkadot` and `bulletin-polkadot`:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... )
    >,
>;
```

### Proof of Concept
xcm-emulator integration test plan (in `integration-tests/emulated/tests/assets/asset-hub-kusama/src/tests/reserve_transfer.rs` style):
1. Fund a signed AssetHub Kusama test account with KSM.
2. Construct via `pallet_xcm::execute`:
```rust
Xcm(vec![
    WithdrawAsset((Parent, amount).into()),
    BuyExecution { fees: (Parent, fee).into(), weight_limit: Unlimited },
    SetAppendix(Xcm(vec![
        DepositReserveAsset {
            assets: Wild(All),
            dest: Location::parent(),
            xcm: Xcm(vec![]),
        },
    ])),
])
```
3. Assert the call succeeds (`assert_ok!`) despite reserve-transfer-to-relay being intended to be denied, and assert the Relay Chain sovereign/derived account balance increases by `amount` — proving the deny rule was bypassed.
4. Contrast with a direct top-level `DepositReserveAsset{dest: Parent, ..}` (no `SetAppendix` wrapping), which is correctly rejected with `ProcessMessageError`/`Filtered`, to demonstrate the discrepancy is specifically due to the nested-instruction bypass.
