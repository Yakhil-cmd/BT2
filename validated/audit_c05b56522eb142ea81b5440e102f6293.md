### Title
Cross-organization team confusion in `MembershipHandler` grants unauthorized `Shipit.github_teams` membership - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the target `Team` purely by the numeric `team.id` supplied in the webhook body, without verifying that the webhook's authenticated organization (the one whose `webhook_secret` produced a valid `X-Hub-Signature`) actually owns that team. An attacker who controls any organization already onboarded to a multi-tenant Shipit instance (and thus knows/controls that org's own webhook secret) can forge a `membership` webhook naming a `team.id` belonging to a *different* organization and add themselves to that team's `Membership` table, escalating into `Shipit.github_teams` authorization.

### Finding Description
The binding that must hold is: `Team#organization` for the team identified by `params.team.id` == `repository_owner`/`params.organization.login` that authenticated the current webhook request (i.e., the org whose `webhook_secret` produced `verify_signature`'s HMAC match).

The actual code path:
- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from the payload itself (`params.dig('organization', 'login')` for membership events) and calls `Shipit.github(organization: repository_owner)`. This only succeeds if that organization has a statically configured entry in `secrets.github` (`lib/shipit.rb#github_app_config`); otherwise `GithubOrganizationUnknown` is raised and the request is rejected with 422. So the attacker must control an organization that is a legitimately configured Shipit tenant, but for a multi-org Shipit deployment the attacker (as the real admin of their own onboarded org) can legitimately know their own org's `webhook_secret`.
- Once the signature check passes (using the attacker's own org's secret), `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) calls `find_or_create_team!` (`membership_handler.rb:38-43`), which does `Team.find_or_create_by!(github_id: params.team.id)`. This lookup is **global by `github_id` only** — it never checks `params.organization.login` against the found team's `organization` column.
- If the attacker sets `params.team.id` to the numeric GitHub team ID of an existing `Shipit::Team` belonging to a *different* organization (one already present in `Shipit.github_teams`), `find_or_create_by!` returns that existing record instead of creating a new one.
- `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) then inserts a `Membership` row linking the attacker's real `User` (created via `User.find_or_create_by_login!`) to that team.
- Later, when the attacker completes a normal OAuth login, `User#authorized?` (`app/models/shipit/user.rb:80-82`) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, which now returns true because of the forged `Membership`, even though the attacker was never actually added to that team on GitHub.

None of the existing guards catch this: `verify_signature` only authenticates *which organization's secret* signed the request, not *which team* the payload may reference; the `ExplicitParameters` schema only validates types/presence, not cross-field organization ownership; `find_or_create_team!` has no equality check between `params.organization.login` and the resolved `team.organization`.

### Impact Explanation
This is a **Critical authentication/authorization bypass** matching the "escalation into `Shipit.github_teams` authorization" category. A user who is not a genuine member of any team gated by `Shipit.github_teams` can grant themselves membership in an existing gated team by forging one webhook against their own (legitimately configured) organization, then logging in normally via OAuth — `force_github_authentication`/`authorized?` will treat them as authorized. This is repeatable for any team whose numeric `github_id` the attacker can learn, and it works across every stack protected by that team's authorization, effectively giving the attacker deploy/rollback/admin capabilities across the whole Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment where more than one GitHub organization is configured with its own `webhook_secret` in `secrets.github`, (2) the attacker being a legitimate admin/owner of one such configured org (so they know its webhook secret), and (3) knowledge of the numeric `github_id` of the target team (obtainable via GitHub's team API for teams the attacker can view, prior webhook payloads, or brute-forcing small integer IDs). Given these preconditions the attack is a single forged HTTP POST plus a normal OAuth login — cheap and fully repeatable.

### Recommendation
In `find_or_create_team!`, require that `params.organization.login` matches the resolved team's `organization` (case-insensitively) before allowing `add_member`/`remove`; if it doesn't match, reject the payload (e.g., raise/log and return without mutating membership). Alternatively, scope the `Team.find_or_create_by!` lookup to `github_id: params.team.id, organization: params.organization.login` and treat organization mismatches as an error rather than silently reusing the pre-existing record from a different org.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
