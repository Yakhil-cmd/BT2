### Title
CCMenu API token is a global, unscoped `read:stack` credential usable against `Api::StacksController`/`Api::TasksController` for ANY stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` mints a single, reusable `ApiClient` per user with `permissions: %w[read:stack]` but never binds it to the requested stack (`stack:` is never passed), so the token is not scoped by `ApiClient#stack_id`. Because `Api::BaseController#stacks`/`#stack` only restrict results when `current_api_client.stack_id?` is true, this "CCMenu Client" token authenticates as a fully generic `read:stack` credential against every `read:stack`-gated JSON endpoint (`Api::StacksController`, `Api::TasksController`, `Api::MergeRequestsController`, etc.) for **all** stacks in the instance, not just the one the badge URL was generated for.

### Finding Description
Binding claimed to hold: `token.authorized_scope == {stack: A, action: CCMenu#show}`. Actual binding in code: `token.authorized_scope == {stack: ANY (stack_id nil), action: ANY read:stack action}`.

Path:
1. An authenticated Shipit user (with read access to stack A) visits stack settings and triggers `CCMenuUrlController#fetch` [1](#0-0) .
2. `#client` does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` attribute is set, so `stack_id` is `nil` on this record, and the same record is reused/shared for every stack that user ever requests a CCMenu URL for [2](#0-1) .
3. The resulting URL (`.../ccmenu?token=<signed id>`) is handed out by the operator as a "public CI badge" link, i.e., treated as unauthenticated by design.
4. `Api::CCMenuController#authenticate_api_client` accepts this same token via `params[:token]` [3](#0-2) , but the token itself is indistinguishable from a normal Basic-Auth `ApiClient` credential — `ApiClient.authenticate` just verifies the signed id and returns the same `ApiClient` record used everywhere else [4](#0-3) .
5. Anyone holding that token (e.g., copied from the badge `<img src>`/link) can send `Authorization: Basic base64(token)` to `Api::StacksController#show`/`#index` or `Api::TasksController#index`/`#show`, which only require `read:stack` [5](#0-4) [6](#0-5) .
6. `check_permissions!` only matches the `operation:scope` string; it has no notion of action-scoping [7](#0-6) , and `BaseController#stacks` only narrows results `if current_api_client.stack_id?` [8](#0-7) . Since this token's `stack_id` is `nil`, `Stack.all` is exposed — full JSON read access across every stack in the Shipit instance, not just stack A.

Existing guards (`require_permission!`, `check_permissions!`, `stacks` scoping) do not prevent this because they were designed around per-client permission sets, and the CCMenu-specific client creation path simply never sets `stack_id`, so the intended narrowing never activates.

### Impact Explanation
Any party who obtains a CCMenu badge URL for one stack (which the operator/UI presents as a read-only, embeddable CI status widget) gains a bearer credential valid for `Api::StacksController#index/show`, `Api::TasksController#index/show`, `Api::MergeRequestsController#index/show`, etc., for **every** stack visible in the instance (not merely stack A), exposing stack configuration, deploy/task metadata, and merge-request state without any further authentication. This matches "High - unauthenticated read of stack state ... or deploy output," since the badge is effectively a public/unauthenticated artifact per the operator's intent, and the blast radius extends to all stacks rather than being confined to the one stack the URL nominally represents.

### Likelihood Explanation
Requires only that (a) a Shipit user generates and publicly shares/embeds a CCMenu URL (a documented, supported feature intended for public CI badges) and (b) an unprivileged party extracts the `token` query parameter from that URL — no Shipit session, GitHub credentials, or secret material is needed by the attacker. This is low-cost and fully repeatable: the "CCMenu Client" is `find_or_create_by!`'d and long-lived, so the token keeps working for all stacks the creating user can generate CCMenu URLs for.

### Recommendation
Scope the `ApiClient` created in `CCMenuUrlController#client` to the specific stack (e.g., `find_or_create_by!(creator: current_user, stack: stack, name: "CCMenu Client (#{stack.to_param})")` and set `stack: stack` in `create_with`), and additionally make `Api::CCMenuController#stack` honor `stacks` scoping (using `current_api_client`'s stack restriction) rather than `Stack.from_param!` directly, so a leaked CCMenu token cannot be replayed against unrelated stacks or unrelated `read:stack` JSON endpoints beyond the intended badge use.

### Proof of Concept
Add to `test/controllers/api/ccmenu_controller_test.rb` (or a new integration test):
```ruby
test "a CCMenu token for stack A grants full JSON access to stack B via Api::StacksController" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar2"), branch: 'main')

  # Simulate CCMenuUrlController#client for stack_a
  user = shipit_users(:walrus)
  client = ApiClient.create_with(permissions: %w[read:stack])
                     .find_or_create_by!(creator: user, name: 'CCMenu Client')

  # Assert token is NOT scoped to stack_a
  assert_nil client.stack_id

  # Use the "CCMenu-only" token via Basic Auth against StacksController for stack_b
  @controller = Shipit::Api::StacksController.new
  request.headers['Authorization'] = "Basic #{Base64.encode64(client.authentication_token)}"
  get :show, params: { id: stack_b.to_param }

  assert_response :ok
  assert_json 'id', stack_b.id   # full JSON for an UNRELATED stack, not just XML CI status for stack_a
end
```
This demonstrates that the equality `token.authorized_scope == {stack: A, action: CCMenu#show}` does not hold; the token instead satisfies `token.authorized_scope == {stack: ANY, action: ANY read:stack}`.
