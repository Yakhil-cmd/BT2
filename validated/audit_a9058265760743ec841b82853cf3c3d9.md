### Title
CCMenu API endpoint lets a stack-scoped `ApiClient` token read any stack's status, bypassing token scope binding - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The stack a caller's `ApiClient` token *authorizes* (`ApiClient#stack_id`) diverges from the stack the `CCMenuController` actually *touches* (`params[:stack_id]`), because this controller resolves the target stack directly via `Stack.from_param!` instead of the scoped `stacks.from_param!` helper every other API controller uses.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through the `stacks` helper: if the authenticated `ApiClient` has a `stack_id`, only that one stack is in scope; otherwise all stacks are. [1](#0-0) 
`Shipit::Api::StacksController` (and other API controllers) rely on this scoped `stacks.from_param!` when resolving `stack`, so a scoped token can never touch a stack other than the one it was issued for. [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `stacks` scoping method, while still only checking the generic `read:stack` permission via `require_permission :read, :stack` (which just verifies the permission string is present, not that the stack matches the token's `stack_id`). [3](#0-2) 

`CCMenuUrlController` mints exactly this kind of scoped token — `permissions: %w[read:stack]` bound to one specific stack via the URL that is generated — intended to be embedded in third-party CCTray/CI-dashboard tooling. [4](#0-3) 

Because `CCMenuController#stack` does not consult `current_api_client.stack_id`, any holder of a valid `read:stack` token — even one scoped to a single stack — can substitute an arbitrary `stack_id` in the `/ccmenu/*stack_id` route (mounted publicly, authenticated only via a `token` query parameter) and read status for every other stack in the installation. [5](#0-4) 

This is the same class of bug as the reported issue: a binding that is supposed to hold end-to-end (token's authorized stack ⇔ stack the code operates on) is silently broken by one code path using a different, unscoped resolution mechanism than the one that establishes/enforces the binding elsewhere in the same trust boundary.

### Impact Explanation
An attacker in possession of any single-stack-scoped `read:stack` API token (these tokens are, by design, embedded in externally shared CCMenu URLs, e.g. pasted into CI dashboards, monitoring tools, chat messages, or browser history) can enumerate `owner/repo/environment` stack identifiers and read `merge_status`, build activity, and deploy timing/state for every stack hosted by the Shipit instance, not just the one the token was scoped to. This is unauthorized/unauthenticated-scope read of stack state across stacks the token was never meant to access, matching the "High" impact bucket ("unauthenticated read of stack state, task streams or deploy output").

### Likelihood Explanation
Likelihood is Medium-to-High: exploitation requires only a single leaked/observed CCMenu token (no privileged account, no GitHub credentials, no session) and a guessable/known `owner/repo/environment` stack identifier, both trivial to obtain since CCMenu URLs are explicitly designed to be shared with external tooling and stack identifiers are just repo/environment names.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped helper, exactly like the rest of the API controllers:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the invariant that a token's `stack_id` binding is enforced on every code path that resolves a stack from a token-authenticated request.

### Proof of Concept
1. As a legitimate user, request `GET /ccmenu/*stack_id` via `CCMenuUrlController#fetch` for `stack_a` (`owner/repoA/production`), obtaining a URL like `.../api/stacks/owner/repoA/production/ccmenu?token=<T>`, where `<T>` authenticates an `ApiClient` with `permissions: ['read:stack']` and `stack_id = stack_a.id`.
2. An attacker who observes/obtains `<T>` (e.g., from a shared CI dashboard config) requests `GET /api/stacks/owner/repoB/staging/ccmenu?token=<T>` for an unrelated `stack_b`.
3. `CCMenuController#authenticate_api_client` successfully authenticates `<T>` via `ApiClient.authenticate(params[:token])`; `require_permission :read, :stack` passes because `<T>` has the `read:stack` permission string.
4. `CCMenuController#stack` calls `Stack.from_param!('owner/repoB/staging')` directly (ignoring that `<T>.stack_id == stack_a.id`), returning `stack_b`.
5. The response renders `stack_b`'s `merge_status`, activity, and last deploy info — data the token was never authorized to access.

module Shipit

        end

        end

      private

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
