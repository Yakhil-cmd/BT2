### Title
Multi-oracle `data_feed`/`in data feed` lookups can silently select a value from a stale, unsynchronized oracle among several listed - ([File: data_feeds.js])

### Summary
Oscript/AA logic that references a data feed can list several oracle addresses in a single `oracles` parameter (e.g. `"oracle1:oracle2"` in `data_feed[[...]]` or `['in data feed', [addr1, addr2], ...]` in an address/AA definition). Both the low-level `readDataFeedValue`/`readDataFeedByAddress` machinery and the `dataFeedExists` machinery treat this list as a single pool and pick a result ("last" posted value, or "any" match) without requiring the listed oracles to agree or to be in sync with each other, mirroring the Perennial issue where two products of the same market could silently diverge because they each maintained an independently-updatable oracle reference.

### Finding Description
When an AA or address-definition author lists multiple oracle addresses for the same logical feed (a common redundancy/fallback pattern), `readDataFeedValue` iterates the addresses with `async.eachSeries` and, for `ifseveral === 'last'`, keeps whichever record has the highest `mci`, comparing across the whole combined address set rather than per-oracle: [1](#0-0) 
This same "pick most recent across all addresses" logic is repeated for the unstable/AA-visible candidates in `readDataFeedValue`, where candidates from different oracle addresses are pooled together and the sort simply orders by `latest_included_mc_index`/`level`, again with no requirement that the listed oracles be posting in lock-step: [2](#0-1) 
Similarly, `dataFeedExists` (used by the `in data feed` address-definition operator and the `in_data_feed` oscript function) treats the address list as an OR across independently posting oracles - a match from any single oracle in the list, regardless of whether the others have caught up, satisfies the condition: [3](#0-2) 
Address definitions and AA definitions can build such lists directly from validated but unrelated oracle addresses: [4](#0-3) 
and formulas accept an arbitrary `:`-joined oracle list the same way: [5](#0-4) 

Because none of these code paths verify that the listed oracles are mutually consistent/synchronized before a value is consumed, an AA (e.g. a lending/perpetual/vault-style AA) that intentionally lists two or more oracles for the same asset - expecting them to represent the same, synchronized price - can instead receive a value driven entirely by whichever oracle happened to post most recently. This is the exact same root cause as the Perennial report: two logically-equivalent price sources for the same asset can update independently, and the consuming contract has no mechanism to detect or reject the resulting skew.

### Impact Explanation
If an AA's collateralization, liquidation, or settlement logic reads a price via a multi-oracle `data_feed`/`in data feed` reference expecting the oracles to be synchronized, an attacker (or simply normal asynchronous oracle operation) can cause the AA to act on a stale or momentarily divergent value from one of the listed oracles while the "true"/consensus price (as reflected by the other oracle(s)) has already moved. This can trigger incorrect liquidations, incorrect payouts, or allow a party to time a trigger unit to land when the most-recently-updated oracle is favorable to them, causing fund loss or unfair freezing/liquidation within the AA - the same class of impact described in the source report (unintended liquidation and unpredictable deposit/withdrawal behavior due to unsynchronized oracle updates).

### Likelihood Explanation
This requires an AA author to have designed a multi-oracle feed for redundancy/quorum purposes (a supported and expected pattern, e.g. `oracles="O1:O2"`), and for the oracles to update at different times/blocks - a routine occurrence in any real oracle setup, not a rare edge case. Any user who can time posting of an AA-trigger unit relative to oracle updates can exploit the resulting price divergence without needing to compromise any oracle or node.

### Recommendation
For multi-oracle feed reads intended to represent one synchronized value, require that all listed oracles report values within an acceptable MCI/timestamp window (or the same MCI) before the value is trusted, and expose a way for `data_feed`/`in data feed`/`dataFeedExists` callers to detect and explicitly handle disagreement/staleness among the listed oracles (e.g., an "any mismatch aborts" mode), rather than silently taking the most recent single-oracle post or matching against any oracle in the list.

### Proof of Concept
1. An AA defines its price feed as `data_feed[[oracles="OracleA:OracleB", feed_name="PRICE", ifseveral="last"]]`, intending OracleA and OracleB to be redundant/synchronized sources for the same price.
2. OracleA posts an updated price reflecting a market move; OracleB has not yet posted its corresponding update (independent posting schedules, no protocol-level sync).
3. A user posts an AA-trigger unit at this moment. `readDataFeedValue` pools both oracles' postings and returns the value with the highest `mci` - OracleA's fresh (or, in the opposite ordering, OracleB's stale) value - per [1](#0-0) .
4. The AA computes collateralization/liquidation/settlement using this skewed single-oracle value even though it was designed around the assumption of a synchronized multi-oracle feed, producing an outcome (liquidation, mispriced settlement, fund loss) inconsistent with the "true" synchronized price - directly analogous to the reported Perennial vault issue.
