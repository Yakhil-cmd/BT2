### Title
Organization used to select the webhook-verification secret is not bound to the repository the webhook payload writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against using a value taken from the untrusted, unverified JSON body itself, before the signature has been checked. If that self-declared organization happens to have no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` fails open and accepts the request as "verified," after which the event handlers act on a different repository/stack identified by another field of the same forged payload. This is the same bug class as the Twav report: a decision (the “if” gate that governs whether the request is trusted) is driven by a data field that is not itself proven authentic, letting a corner case (missing secret) slip past a check that was meant to guarantee authenticity for everything that follows.

### Finding Description
`repository_owner` is computed purely from the raw, still-unverified request body: [1](#0-0) 

That value is then used to select which configured GitHub App (and which `webhook_secret`) will be used to verify the very same request: [2](#0-1) 

`GitHubApp#verify_webhook_signature` fails open when the selected organization has no secret configured: [3](#0-2) 

Shipit explicitly supports multiple, independently configured GitHub Apps/organizations, each with its own optional `webhook_secret` (confirmed by the multi-org fixture and by `docs/setup.md` describing `webhook_secret` as something you copy in "if you've set" one): [4](#0-3) [5](#0-4) 

The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository/stack the handler subsequently writes to`.

Because `repository_owner` is read from `repository.owner.login` (or `organization.login`) inside the same forged, not-yet-verified body, and because the downstream handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) independently resolve the target stack/repository from other fields of that same body (e.g. `repository.full_name`, used across the `pull_request` handlers), an attacker can pick an organization with no configured `webhook_secret` to satisfy `verify_signature` for free, while pointing the repository/stack-resolution fields at a completely different, victim organization's repository. `verify_signature` never re-checks that the "authenticating" organization matches the organization actually acted upon.

### Impact Explanation
If any configured organization in a multi-app Shipit deployment has no `webhook_secret` set (an explicitly supported, documented configuration), an unauthenticated external attacker can forge arbitrary webhook payloads (`push`, `status`, `pull_request`, `check_suite`, `membership`) that are accepted as fully verified, then made to reference a victim organization's repository/stack via the payload fields the handlers key off of. Depending on event type this can enqueue sync jobs against a victim stack, create fabricated commit `Status` records (which can be used to satisfy CI-gate requirements before an unauthorized deploy), or manipulate team/pull-request state cross-repository — i.e. writes/actions that were meant to be exclusively gated behind a valid organization signature land on a repository whose organization never authenticated the request. This maps to "cross-repository writes" / "unauthorized deploy" in the impact criteria.

### Likelihood Explanation
Exploitation requires only network access to the public `Shipit::WebhooksController#create` endpoint and knowledge that at least one configured GitHub App/organization in the deployment has no `webhook_secret` (a legitimate, documented, non-privileged configuration state, not a misuse of the engine). No token, session, or GitHub credential is needed — this is exactly the "unprivileged attacker breaking a trust binding" class the scan is looking for.

### Recommendation
Do not let any field inside the unverified request body decide trust before the signature has been checked. Verify the webhook against every organization the app is configured for (or require a globally-mandatory secret) and reject the request unless the org whose secret validated the payload is provably the same org that the resolved repository/stack belongs to. Consider making `webhook_secret` mandatory for every configured GitHub App, and re-derive/validate `repository_owner` from the same field the handlers use for stack resolution, not a field chosen ad hoc for verification purposes.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps as in `secrets_double_github_app.yml` style config: `OrgA` (attacker-controlled/no `webhook_secret`) and `OrgVictim` (has stacks, `webhook_secret` set).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgVictim/victim-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `repository_owner` resolves to `"OrgA"`; `Shipit.github(organization: "OrgA")` has `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally per [6](#0-5) , with no valid `X-Hub-Signature` required.
4. The request passes `verify_signature` and is dispatched to the `push` handler, which resolves the target stack from `full_name` = `"OrgVictim/victim-repo"`, enqueuing a sync/job against the victim organization's stack despite `OrgVictim` never having authenticated this request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
