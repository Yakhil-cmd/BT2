## Title
Push-style AA-to-AA payments allow a malicious recipient AA to permanently DoS the sender AA via cascading `revert()` - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) sends a payment to another address as part of its response messages, if that recipient address is itself an AA, a **secondary trigger** is synchronously invoked on it as part of the *same* unit-processing flow. If that secondary AA bounces (fails), the entire top-level (primary) trigger response — including any state variables already updated and prior sibling AA responses — is rolled back via `revert()`. This is the oscript-native analog of Solidity's "push" refund DoS: any AA logic that forwards funds to a caller/beneficiary-controlled address (e.g., "refund the previous highest bidder", "forward to referrer", "pay out to a data-supplied address") can be permanently bricked if the attacker registers that address as a malicious AA designed to always bounce.

### Finding Description
`handleSecondaryTriggers()` looks up every payment-output address that is itself a registered AA (`aa_addresses`) and recursively calls `handleTrigger()` on it as a secondary trigger: [1](#0-0) 

If any of those secondary AAs bounces, the error is propagated back through `async.eachSeries`, and for a **primary** (non-secondary) trigger this triggers a full `revert()` of the whole unit that was about to be composed/saved — not just the failed sub-call: [2](#0-1) 

`revert()` rolls back all AA state changes and all previously accumulated responses for the entire trigger chain (`revertResponsesInCaches`, `ROLLBACK TO SAVEPOINT initial_balances`, clearing `stateVars`), then calls `bounce(err)` on the primary trigger, so the primary AA's whole action (including any prior side effects like recording a new highest bid, updating a counter, etc.) never takes effect: [3](#0-2) 

Critically, bounce-fee requirements (meant to make bouncing "costly" and guarantee liveness) are explicitly *not* enforced for secondary triggers, so an attacker-controlled recipient AA can be engineered to bounce unconditionally at zero cost: [4](#0-3) 

This mirrors the reported Solidity bug class exactly: a contract (`_createBid`) pushes funds to an externally-influenced address (the previous highest bidder) as part of its own state-changing call; if that recipient reverts, the whole call reverts and the auction is stuck. In ocore, any AA that composes a `payment` message whose destination address is derived from trigger data, stored state (e.g., `var['highest_bidder']`), or a prior participant's address, is exposed to the same pattern: the attacker deploys a "bouncer" AA at the address they will submit as bidder/beneficiary, causing all subsequent triggers on the victim AA that must pay out to that address to be reverted forever.

### Impact Explanation
Any AA implementing an auction, marketplace, escrow, referral-payout, or "refund previous participant" pattern that forwards funds to an address supplied via `trigger.data`/`trigger.address`/state can be permanently frozen: once the malicious address becomes the mandatory payout target (e.g., "current highest bidder"), every subsequent legitimate trigger that needs to pay it is reverted in full, blocking all further state progress (new bids, deposits, or fund release) indefinitely. This is a fund-freezing / availability failure of the AA, matching a High-severity denial-of-service impact.

### Likelihood Explanation
Any unprivileged user can define and post a malicious AA definition (no privilege required — this only needs `aa_addresses`/`autonomous agent` definitions, which anyone can post), and then act as a normal trigger sender (e.g., a "bidder") using that AA's address. As soon as the victim AA is designed to forward/refund funds to a caller-influenced address (a very common oscript pattern, as seen in `test/samples/fundraising_proxy.oscript` "refund" case and `just_a_bouncer.oscript`/`bounce_half_of_balance.oscript` push-to-`trigger.address` patterns), the attack is straightforward and repeatable at low cost. [5](#0-4) 

### Recommendation
Avoid unconditionally reverting the entire primary trigger chain when only a downstream secondary AA bounces. Options:
- Treat a bounced secondary AA payment like a bounced trigger to a normal address (i.e., let the funds be received/held by the recipient AA's own bounce-fee/bounce-payment logic) instead of cascading a full `revert()` of the sender's already-valid state changes.
- Alternatively, require AAs that forward funds to caller-controlled addresses to use a pull-based claim mechanism (record a claimable balance in state instead of pushing an immediate payment), so a failing recipient cannot block state progression for other participants.

### Proof of Concept
1. Attacker posts a malicious AA definition at address `M` whose `messages` always evaluate to bounce (e.g., an `init` clause with `bounce('always fail')` unconditionally, or invalid/self-contradictory payment logic), relying on the fact that bounce-fee coverage is not required for secondary triggers (`aa_composer.js:1850-1863`).
2. Attacker submits a trigger unit from address `M` to a victim "auction-style" AA (structured like `fundraising_proxy.oscript`'s refund case or a bidding AA that stores `var['highest_bidder'] = trigger.address`), becoming the current highest bidder/beneficiary.
3. A legitimate user posts a new, higher bid trigger to the victim AA. The victim AA's response messages include a `payment` output refunding the previous highest bidder `M`.
4. Because `M` is a registered AA, `handleSecondaryTriggers()` invokes it as a secondary trigger (`aa_composer.js:1702-1720`); `M` bounces immediately.
5. The `async.eachSeries` callback receives the bounce error and, since the trigger being processed is primary, calls `revert(err)` (`aa_composer.js:1743-1749`), which rolls back the victim AA's entire response — including the new bidder's payment and any state updates — via `ROLLBACK TO SAVEPOINT initial_balances` (`aa_composer.js:1759-1783`).
6. Every subsequent bid attempt against the victim AA fails identically, permanently freezing the auction/AA at the attacker-controlled state.
