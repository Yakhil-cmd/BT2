### Title
Webhook signature verification is keyed off `repository.owner.login`, but downstream handlers act on `repository.full_name`, allowing repository/stack confusion when any configured GitHub App organization has no webhook secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which HMAC secret) to validate a webhook against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once "verified," the raw payload is dispatched unchanged to handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`). Those handlers — `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the base `Handler#stacks`/`#repository_name` — resolve the target repository/stack from a *different* field: `payload.dig('repository', 'full_name')`, via `Repository.from_github_repo_name`. Nothing enforces that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` used for signature verification. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This mirrors the reported splay-tree bug class: a value used to authorize/verify an operation (`right_leftmost_parent_node.left`, sentinel-assigned without considering the still-referenced right child) diverges from the value that is actually acted upon later. Here, the "authorizing" field is `repository.owner.login` (used to pick the webhook secret for HMAC verification), while the "acted upon" field is `repository.full_name` (used to pick which `Stack`/`Repository` receives the push/status/check_suite event).

`GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when no `webhook_secret` is configured for that organization: [4](#0-3) 

Because `webhook_secret` is documented and configured as optional per organization (`docs/setup.md`, `config/secrets.development.shopify.yml`, `template.rb` all show `webhook_secret:` left blank as a valid config), an operator can legitimately run a multi-organization Shipit instance (as tested in `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne` and `OrgTwo` simultaneously) where one organization has no secret set. [5](#0-4) [6](#0-5) 

An unauthenticated attacker who knows (or guesses) that such an unsecured organization is registered in `Shipit.github` can submit a forged webhook request where:
- `repository.owner.login` (or `organization.login`) = the unsecured organization → causes `verify_signature` to pick that org's `GitHubApp`, whose `verify_webhook_signature` returns `true` unconditionally (no HMAC needed).
- `repository.full_name` = `"<victim-org>/<victim-repo>"` for any repository/stack actually hosted on the instance, regardless of organization.

The request is accepted, and the raw `params` (with the attacker-controlled `full_name`) are handed to handlers, which resolve the target `Stack` purely via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`. This lets the attacker trigger `push` events (`GithubSyncJob`), forge `status` updates, or `check_suite` refreshes against arbitrary stacks that have nothing to do with the unsecured organization. [7](#0-6) 

### Impact Explanation
This breaks the equality that should hold: `organization whose secret validated the request == organization owning the repository being acted upon`. Before the attack, only GitHub itself (holding the real per-org webhook secret) can trigger sync/status/check_suite jobs for a given stack. After the attack, anyone can trigger these for any stack on the instance by routing the "authenticating org" field to an org lacking a secret while pointing the "acted-upon repository" field at the real target. Concretely this can:
- Force `GithubSyncJob` to run for arbitrary stacks (fetching/deploy-spec caching side effects, `mark_as_inaccessible!`/`mark_as_accessible!` state flips).
- Inject fabricated commit `Status` records for arbitrary commits on any tracked repository (`StatusHandler`), which can influence CI-gated deploy checks (`ci.require`/`ci.blocking` in `shipit.yml`), potentially unlocking or misleading deploy decisions.
- Trigger `RefreshCheckRunsJob` for stacks unrelated to the attacker's claimed organization.

This maps to "High - unauthenticated read/manipulation of stack state" and, through CI-status forgery feeding deploy gating logic, has a path toward influencing unauthorized deploy decisions.

### Likelihood Explanation
Requires only that the deployed Shipit instance configures more than one GitHub organization (a supported, documented configuration per `docs/setup.md` and `template.rb`) and that at least one configured organization has left `webhook_secret` blank (explicitly presented as "optional" in setup docs). No credentials, tokens, or repository access are required by the attacker — the webhook endpoint (`/webhooks`) is unauthenticated by design and reachable by anyone who can send an HTTP request to it. This is a realistic misconfiguration risk rather than a purely theoretical one, since the docs actively suggest secrets are optional.

### Recommendation
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank; require a webhook secret for every configured GitHub App, or fail closed instead of returning `true`.
- Independent of secret configuration, cross-check that the organization used to select/verify the webhook (`repository.owner.login`/`organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. mirroring `test/dummy/config/secrets_double_github_app.yml`, where `OrgOne` has `webhook_secret:` set and `OrgTwo` has `webhook_secret:` left blank.
2. Create/track a stack for a repository under `OrgOne`, e.g. `OrgOne/target-repo`.
3. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/target-repo"
  }
}
```
No `X-Hub-Signature` header is required, since `Shipit.github(organization: "OrgTwo")` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
4. `verify_signature` passes; `PushHandler` resolves the target via `payload.dig('repository', 'full_name')` = `"OrgOne/target-repo"`, and enqueues `GithubSyncJob` for that stack — despite the request never being validated against `OrgOne`'s secret.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
