### Title
Webhook signature key-selection uses an unverified `repository.owner.login` field, allowing cross-organization/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, a value read straight out of the unverified request body. The actual event handlers, however, resolve the target `Stack`/`Repository` using a *different* field of that same unverified body, `repository.full_name`. Because these two fields are never checked for consistency, and because a signature only proves the request matches whichever organization's secret was selected for verification, an attacker who can produce a valid signature for *any one* configured organization (including one intentionally left without a `webhook_secret`) can forge webhook events that are dispatched against a *different* organization's repository/stack.

### Finding Description
- `WebhooksController#verify_signature` picks the GitHub App config to verify against via `repository_owner`, computed as `params.dig('repository', 'owner', 'login')`: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` verifies the raw body against the secret belonging to whatever organization was selected, and unconditionally returns `true` when that organization has no configured `webhook_secret` (documented as optional): [3](#0-2) 

- After signature verification passes, `create` dispatches the full unverified JSON body to the registered handlers: [4](#0-3) 

- Handlers resolve the actual target `Stack` using `repository.full_name`, an entirely separate JSON field from the one used to select the verification secret: [5](#0-4) [6](#0-5) 

- Multi-organization Shipit deployments are explicitly supported, each with its own independently optional `webhook_secret`: [7](#0-6) [8](#0-7) 

This is the exact analog of the report's root cause: the report shows `totalSupply()` acting on a decoded value taken from the wrong slice of `returnData`, breaking the binding between the value that was verified/expected and the value actually used. Here, the field used to select/verify the signing secret (`repository.owner.login`) is disjoint from the field used to determine which repository is actually written to (`repository.full_name`), breaking the binding "organization that authenticated == repository that is written."

### Impact Explanation
An attacker with no Shipit session, no API token, and no legitimate webhook secret for the *target* organization can:
1. Craft a JSON body where `repository.owner.login` names an organization configured in Shipit with no `webhook_secret` (or one whose secret the attacker otherwise knows), while `repository.full_name` names a stack belonging to a *different*, properly-secured organization.
2. Send this to `/webhooks` with `X-Github-Event: push` (or `status`). `verify_signature` resolves the GitHub App for the harmless organization, whose `verify_webhook_signature` trivially returns `true` (no secret configured), or is bypassed with a computable signature.
3. `PushHandler`/`StatusHandler` then act on `repository.full_name`, i.e., the *other* organization's real `Stack`/`Commit`, triggering `stack.sync_github` or fabricating a `Status` (`create_status_from_github!`) on that stack's commits — content the attacker fully controls, and never authenticated by that organization's actual GitHub App secret.

This is a cross-repository/cross-organization write reachable by an unauthenticated network attacker, matching the Critical "cross-repository writes" / unauthorized deploy trigger criteria (forged CI status or sync can gate or trigger downstream deploy automation).

### Likelihood Explanation
Requires only that the Shipit instance host more than one GitHub organization (a documented, supported configuration) and that at least one of those organizations has no `webhook_secret` configured — a state explicitly presented as valid/optional in the setup documentation and example secrets files. No credentials, sessions, or GitHub write access are needed; the request is a single unauthenticated HTTP POST.

### Recommendation
Bind the field used to select/verify the webhook signature to the same field used for repository/stack resolution. Concretely, derive the organization used for `Shipit.github(organization: ...)` from `repository.full_name`'s owner segment (the same value `Repository.from_github_repo_name` will use), not from a separate, independently attacker-controlled `repository.owner.login`/`organization.login` field. Additionally, consider requiring `webhook_secret` to be present for all configured organizations in multi-tenant mode, since an organization without a secret degrades verification to an unconditional pass-through that can be leveraged against sibling organizations sharing the same instance.

### Proof of Concept
Given a multi-org config:
```yaml
github:
  attacker_org:
    app_id: ...
    webhook_secret: # nil - intentionally unset
  victim_org:
    app_id: ...
    webhook_secret: real-secret
```

Attacker sends (no signature required, since `attacker_org` has no secret):
```
POST /webhooks
X-Github-Event: push

{
  "repository": {
    "full_name": "victim_org/production-app",
    "owner": { "login": "attacker_org" }
  },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
`verify_signature` resolves `Shipit.github(organization: 'attacker_org')`, whose `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`). `PushHandler#stacks` then resolves `Repository.from_github_repo_name('victim_org/production-app')` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim organization's real stack — a cross-organization write triggered without ever validating against `victim_org`'s actual webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
