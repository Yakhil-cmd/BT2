### Title
Webhook signature verification selects the trusted GitHub App/secret from an attacker-controlled field, but event handlers act on a different, unverified field in the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which per-organization `webhook_secret` to validate a request against using `repository.owner.login` (or `organization.login`) taken straight out of the still-unauthenticated JSON body. Once that check passes, `create` dispatches the *entire* parsed body (including `repository.full_name`, `ref`, `pull_request`, etc.) to the registered handlers, which use those other fields — not the field used to pick the secret — to locate the target `Repository`/`Stack` and perform actions (sync, status updates, PR/merge-queue handling).

### Finding Description
Shipit supports multiple GitHub Apps, one per GitHub organization, each with its own independent `webhook_secret`: [1](#0-0) 

Signature verification is implemented as: [2](#0-1) 

and the organization used to select the app/secret is derived from the body itself: [3](#0-2) 

`verify_webhook_signature` HMACs the *entire* raw request body against the secret for that derived organization: [4](#0-3) 

Because the attacker constructs the whole HTTP request (this is not a GitHub-relayed webhook, it's a direct POST to Shipit's `/webhooks` endpoint), anyone who knows the `webhook_secret` for *one* configured organization (e.g. an admin who set up Shipit's GitHub App for their own org — a low-privilege actor relative to any other org/stack hosted on the same Shipit instance) can craft an arbitrary raw body, sign it correctly for their own org, and put unrelated values in the other fields of that same body — e.g. `repository.owner.login: "attacker-org"` (used only to pick the secret) while `repository.full_name`, `pull_request`, `ref`, etc. reference a completely different repository/stack: [5](#0-4) 

Handlers such as `PushHandler`, the `pull_request` handlers, `CheckSuiteHandler`, and `StatusHandler` then look up the `Stack`/`Repository` using `repository.full_name` (as confirmed by the existing test constructing a payload with an arbitrary `repository.full_name` to exercise stack creation/sync) and act on it — enqueuing `GithubSyncJob`, updating commit statuses/check-runs, or driving the merge-queue/PR lifecycle for that stack: [6](#0-5) 

This breaks the intended binding: **the organization whose secret authenticated the request must equal the repository the handlers act upon**. Instead, the field used for authentication (`repository.owner.login`) and the field used for authorization-by-effect (`repository.full_name`, PR/commit data) are independent, attacker-controlled values inside the same unauthenticated payload.

### Impact Explanation
An operator who legitimately controls one organization's GitHub App/`webhook_secret` on a shared Shipit instance can forge webhook events that are accepted as authentic for a *different* organization's repositories/stacks. Depending on the handler exercised, this can drive `GithubSyncJob`, tamper with commit/check-run status used for deployability gating, or manipulate pull-request/merge-queue handlers (`opened`, `closed`, `labeled`, etc.) for a stack they do not own — potentially causing an unauthorized merge or corrupting the deployability state that gates deploys, which matches the Critical/High classes of "unauthorized deploy/merge" or "unauthenticated ... task streams/stack state" manipulation. This is a direct analog of the reported bug class: a value that gates trust (the org used to pick the verification secret) is not the same value the subsequent logic actually operates on (the repository/PR data acted on by handlers).

### Likelihood Explanation
Requires only knowledge of a `webhook_secret` for *any* one organization configured on the shared Shipit instance — no repository write access, no `ApiClient` token, and no privileged Shipit account are needed, since the request is a raw unauthenticated HTTP POST to the webhooks endpoint. In multi-org Shipit deployments, this credential is held by the far less trusted "organization admin who registered a GitHub App," making the crossing of the intended per-organization trust boundary plausible.

### Recommendation
After signature verification succeeds, re-validate that every repository-identifying field actually used by the downstream handler (`repository.full_name`, `repository.owner.login` used for stack lookup, PR base repo, etc.) belongs to the same organization/app whose secret validated the signature, rejecting the event otherwise. Consider deriving the app/secret lookup key from a value outside attacker control (e.g., a routed/URL segment identifying the org, verified independently) rather than purely from the JSON body being authenticated.

### Proof of Concept
Conceptual PoC (not executed, no tool/file access to fully trace `PushHandler`'s repository resolution beyond the confirmed test showing `repository.full_name` drives stack lookup):
1. Attacker legitimately owns/administers `attacker-org`'s GitHub App on the shared Shipit instance and knows `webhook_secret_attacker_org`.
2. Attacker builds a JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/main", ...}`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_attacker_org, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `attacker-org`'s app, and validates the signature successfully (since it was correctly computed with that org's secret over that exact raw body).
5. `create` dispatches `params` (containing `victim-org/victim-repo`) to `PushHandler`, which resolves and acts on the `victim-org/victim-repo` stack (e.g., enqueues `GithubSyncJob`) despite the request never being authenticated for `victim-org`. [7](#0-6)

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
