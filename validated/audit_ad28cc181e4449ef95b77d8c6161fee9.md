### Title
Reserve-depletion re-triggers "initial deposit" branch, allowing share-inflation / fund-drain in the Uniswap-like market-maker AA - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `uniswap_like_market_maker.oscript` sample AA (an oscript/AA definition shipped and validated by ocore's AA/oscript pipeline) mints its `mm_asset` liquidity-share token using a flawed "initial deposit" detection that can be re-triggered after the AA has already been seeded, letting an attacker mint shares equal to the *entire* current pool balance instead of only their newly contributed amount. This mirrors the classic ERC-4626/AMM "first depositor / exchange-rate manipulation" inflation attack described in the external report, but is reachable purely by posting ordinary payment triggers to a live AA — no privileged role required.

### Finding Description
In the "invest in MM" case, the AA decides whether this is the very first deposit by checking if either side of the reserve is zero: [1](#0-0) 

```
{ // invest in MM
    if: `{$mm_asset AND trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0}`,
    init: `{
        $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
        $bytes_balance = balance[base] - trigger.output[[asset=base]];
        if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
            $issue_amount = balance[base];
            return;
        }
        ...
```

`$issue_amount = balance[base]` is only correct when the pool was truly empty before this trigger (so `balance[base]` equals just the amount just deposited). But the condition uses an `OR`: it is also satisfied whenever *either* reserve side happens to be exactly `0`, which can occur later in the AA's life after normal trading activity drains one side of the constant-product pool via rounding in the swap branches: [2](#0-1) 

```
{ // exchange bytes to asset
    if: `{trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] == 0 AND var['mm_asset_outstanding']}`,
    init: `{
        $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
        $bytes_balance = balance[base] - trigger.output[[asset=base]];
        $p = $asset_balance * $bytes_balance;
        $new_asset_balance = round($p / balance[base]);
        $amount = $asset_balance - $new_asset_balance;
```

By choosing swap sizes such that `round($p / balance[base])` (or the symmetric byte-side formula) evaluates to `0`, an attacker can force one side of the AA's reserves to hit exactly zero while the *other* side still holds a large, non-zero balance (e.g., all of the bytes the attacker itself just sent in via the swap). Immediately afterward, the attacker (or anyone) sends a follow-up "invest in MM" trigger; because one reserve reads `0`, the AA re-enters the "initial deposit" branch and mints `$issue_amount = balance[base]` — the **entire current byte balance of the AA**, not merely the marginal amount contributed in this trigger — and adds it on top of the already-outstanding `mm_asset_outstanding` (which is never reset): [3](#0-2) 

Because divestment pays out proportionally to `mm_asset` holdings versus `mm_asset_outstanding`: [4](#0-3) 

the attacker, holding this freshly and grossly over-minted `mm_asset`, can then redeem it to claim a share of the pool far larger than what they actually contributed, diluting or fully draining legitimate liquidity providers — the exact "exchange-rate manipulation / inflation attack" outcome described in the external report, just achieved through reserve-zeroing instead of direct balance donation (which the AA's mandatory case-dispatch otherwise prevents).

### Impact Explanation
Any unprivileged sender who can post payment triggers to this AA can manipulate the internal accounting so that share issuance is decoupled from actual contribution, resulting in unauthorized inflation of the `mm_asset` supply and consequent drain of pooled Bytes/asset funds belonging to other depositors — a direct AA fund-loss scenario.

### Likelihood Explanation
The attack requires only ordinary triggers (a swap sized to zero one reserve via rounding, followed by an "invest" trigger) that any address can send; it does not require any privileged role, hub/node cooperation, or leaked keys, making it straightforward to execute once the AA has any liquidity and is actively used for swaps.

### Recommendation
Detect "initial deposit" only by checking that the pool was truly empty on *both* sides simultaneously (e.g., `$asset_balance == 0 AND $bytes_balance == 0`, or better, gate on `!var['mm_asset_outstanding']`), and always compute `$issue_amount` from the marginal contribution relative to `mm_asset_outstanding` and reserves rather than the AA's total balance. Consider bootstrapping the pool with a minimum permanent liquidity deposit (mirroring the report's recommendation of seeding an initial controlled deposit at deployment) so that reserves can never legitimately reach zero while `mm_asset_outstanding > 0`.

### Proof of Concept
1. Attacker sends `define` trigger to deploy `mm_asset`.
2. Attacker performs the first "invest in MM" with modest amounts (e.g., 200000 bytes + 1 unit of `$asset`), receiving `mm_asset_outstanding = 200000` shares, becoming sole holder.
3. Attacker sends a large bytes-only swap sized so that, by the constant-product formula, `round($p / balance[base])` rounds the asset side down to `0` (feasible with a tiny existing asset reserve, e.g. only 1 unit), extracting nearly the entire asset reserve while dumping a large amount of bytes into the AA.
4. Attacker immediately sends another "invest in MM" trigger with a small extra `$asset` amount (≥1) plus >1e5 bytes; since `$asset_balance` (pre-trigger) is `0`, the AA re-enters the initial-deposit branch and sets `$issue_amount = balance[base]` — the full, now-large byte balance — minting it as new `mm_asset` and adding to `mm_asset_outstanding`.
5. Attacker calls "divest MM shares" with their now vastly inflated `mm_asset` balance, redeeming a share of `balance[$asset]`/`balance[base]` far exceeding their real net contribution, draining value from the pool at the expense of any other liquidity providers.
