### Title
Webhook signature verification binds to `repository.owner.login` while status/commit handlers act globally on `sha` — cross-organization forgery of CI status enables unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify the HMAC against based on `repository.owner.login`/`organization.login` read out of the *same untrusted JSON body* it is trying to authenticate. In a multi-org Shipit deployment (a documented, supported configuration), an attacker who legitimately controls one configured GitHub organization can produce a validly-signed webhook whose other payload fields (e.g. `sha`) target a completely different, victim organization's commit. `StatusHandler` then acts on that field with no repository/organization scoping at all, since `Commit.where(sha: params.sha)` is a global lookup.

### Finding Description
`verify_signature` computes the organization to authenticate against directly from attacker-controlled payload data: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the per-organization config (webhook secret, private key, etc.) from `secrets.github`, a schema explicitly designed to support multiple independent GitHub organizations/apps in one Shipit instance: [3](#0-2) 

This means the HMAC signature is verified against whichever organization's secret the attacker names in the JSON body — not against the organization/repository whose data the handler will actually act on. The event handlers use a *different* payload field to determine what to write: [4](#0-3) 

Crucially, `StatusHandler` doesn't even use `repository_name`/org scoping — it looks up commits **globally by `sha`** across the entire database: [5](#0-4) 

So the equality the engine implicitly (and wrongly) assumes is:
`organization authenticated by X-Hub-Signature (repository.owner.login field)` == `organization/repository whose Commit rows get mutated (global sha lookup)`

Before the attack: only GitHub's own signed delivery for organization "OrgA" can produce a valid HMAC for OrgA's `webhook_secret`, and legitimately that delivery only ever contains OrgA's own commit data.
After the attack: an attacker who owns/controls a GitHub App installed on OrgA (their own org, fully legitimate, requires no privileged Shipit access, no `ApiClient` token, and no compromise of any victim secret) knows OrgA's real `webhook_secret`. They craft an arbitrary JSON body with `event: status`, `repository.owner.login: "OrgA"` (so the correct/known secret is selected and the HMAC passes), but `sha` set to a real, pending commit SHA belonging to a victim stack under a completely different organization, and `state: "success"`. `Commit.where(sha: params.sha)` finds that commit regardless of organization and creates a forged success `CommitStatus` on it.

### Impact Explanation
Forged commit statuses are used by Shipit to satisfy `ci.require` gating in `shipit.yml`, which controls whether a commit is considered deployable and whether continuous-deployment-enabled stacks will auto-deploy it (see the `ci.require` documentation in README.md and the CI-status pipeline pointed to by `Commit#statuses`/`stack.required_statuses`). By injecting a fake "success" status for a victim's pending commit using nothing more than a signature valid for the attacker's own, unrelated GitHub organization, an attacker can make a commit appear CI-green and get it deployed by Shipit's automation — i.e., an **unauthorized deploy** through the engine's own webhook trust boundary, which is explicitly listed as a Critical impact in scope.

### Likelihood Explanation
Likelihood is realistic but requires two preconditions that limit but do not eliminate exploitability: (1) the Shipit instance must be configured with the documented multi-organization GitHub App schema (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Using Multiple Github Applications"), and (2) the attacker must control at least one of the configured organizations/apps (which they can do simply by being a legitimate participant/customer whose org is also configured on the shared Shipit instance — no privileged access to the victim org is required). Given this is a documented, supported deployment pattern for exactly this kind of shared-instance use case, the precondition is not unusual.

### Recommendation
- In `WebhooksController#verify_signature`, do not let the payload dictate which organization's secret authenticates the request without also cross-checking that every payload field acted on later (`repository.full_name`, `sha`, etc.) belongs to that same authenticated organization.
- In `StatusHandler` (and any other handler using a global lookup), scope `Commit.where(sha: ...)` by the repository/organization that was actually authenticated for this specific delivery, rejecting/dropping any status update whose owning stack's repository does not match the authenticated organization.
- Consider deriving the verifying organization from Shipit's own installation-to-org mapping (which app/installation ID delivered this webhook) rather than from attacker-supplied `repository.owner.login`/`organization.login` fields in the same JSON body.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App configuration (as in `test/dummy/config/secrets_double_github_app.yml`), with `OrgA` (attacker-controlled) and `OrgB`/victim (e.g. "shopify") both configured, each with its own `webhook_secret`.
2. Attacker creates/owns a GitHub App installed on `OrgA` and thus knows `OrgA`'s real `webhook_secret`.
3. Attacker identifies a pending (not-yet-CI-green) commit SHA belonging to a stack under `OrgB`, e.g. from the public repo or Shipit's UI.
4. Attacker builds a JSON body:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/attacker-repo" }
}
```
5. Attacker computes `sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs it to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=...`.
6. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully (attacker knows this secret), and `StatusHandler#process` creates a `success` `CommitStatus` on the victim's commit via the unscoped `Commit.where(sha: params.sha)` lookup — even though the request was never authenticated for `OrgB`.
7. If that commit's stack has continuous deployment enabled and this was the last required CI check, Shipit deploys it automatically. [6](#0-5) [7](#0-6) [3](#0-2)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks

          requires :state, String

          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do

          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
```
