### Title
Mutable `spender_attested` attestor list lets an asset definer retroactively freeze already-issued/held asset units - (File: `validation.js`, `storage.js`)

### Summary
An asset created with `spender_attested: true` records an initial attestor list, but that list is not immutable: the definer can publish a follow-up `asset_attestors` message at any time to replace it. Every subsequent payment validation of that asset (including spending of outputs that were issued or received under the *previous* attestor list) re-resolves the attestor list to the *most recently* published one and requires the payer/issuer to be attested by an attestor on that current list. This mirrors the reported `StakingRewards.rewardToken` bug class: a privileged, single-signer-controlled parameter that governs disposition of already-outstanding value is left mutable via an exposed setter, and updating it can retroactively strip already-accrued rights from existing holders/holdings.

### Finding Description
When an asset is defined with `spender_attested: true`, `validateAssetDefinition` (`validation.js:2725-2755`) requires an initial `attestors` array via `checkAttestorList`. The definer can later post a new `asset_attestors` message; the only authorization check is that the posting address equals `objAsset.definer_address` (`validateAttestorListUpdate`, `validation.js:2829-2848`) — there is no restriction on how many times, or how late, this can be updated, and no grandfathering of holders who were valid under an earlier list.

Whenever a payment of the asset is later validated, `storage.readAsset` (`storage.js:1898-1957`) computes the attestor list to use via `addAttestorsIfNecessary`, which explicitly queries for the **latest** `asset_attestors` unit before `last_ball_mci` (`storage.js:1917-1946`, `ORDER BY level DESC LIMIT 1`), not the list that was current when the asset units in question were issued or transferred to their current owner. `loadAssetWithListOfAttestedAuthors`/`filterAttestedAddresses` (`storage.js:1959-1992`) then check the *current* payment's author addresses against attestations issued by attestors on that latest list, and `validatePayment` (`validation.js:2115-2122`) rejects the payment ("none of the authors is attested") if none of the authors are attested under the live list.

Because attestor-list membership is evaluated at spend time against the current (mutable) list rather than pinned at issuance/receipt time, a definer can:
1. Publish an asset with `spender_attested: true` and an attestor A.
2. Let users receive/hold asset units after being attested by A.
3. Later publish `asset_attestors` removing A (or replacing it with an attestor the definer controls), instantly making all previously-attested holders unable to move their already-held balances — with no recourse, since address definitions/authentifiers still validate correctly but the payment message itself is now rejected by validation.

This is structurally the same bug class as the report: a mutable, definer/owner-controlled field (`rewardToken` / attestor list) that is read live rather than pinned, letting the privileged party retroactively alter the effective rights over funds that other parties already legitimately hold.

### Impact Explanation
Holders of a `spender_attested` asset can have their already-received, previously-spendable balances made permanently unspendable by a unilateral action of the asset definer, at any time, with no cap on frequency. This is a fund-freezing/denial-of-availability impact directly reachable by any ordinary asset issuer role (an unprivileged, in-scope actor per the task's actor list) against arbitrary counterparties holding that asset — satisfying "AA/asset fund loss or freezing" and "node disagreement on validity" is not needed since this is deterministic and reproducible by all full nodes (it's a consensus-valid state transition, not a bug in disagreement, but a design gap enabling attacker-controlled retroactive freezing).

### Likelihood Explanation
Any address can be an asset definer (`composeAssetDefinitionJoint`, `composer.js:119-121`) and any definer can issue `asset_attestors` updates (`composeAssetAttestorsJoint`, `composer.js:123-125`) with a single signed unit, requiring no special network role or race condition — only ordinary DAG posting rights, matching the "unprivileged unit poster / asset issuer" reachability bar in scope.

### Recommendation
Pin the attestor list applicable to a given payment to the list that was in effect when the asset units being spent were issued/received (analogous snapshot semantics), or disallow post-issuance updates to `asset_attestors` entirely for units already outstanding, similar to the recommended fix in the referenced report ("do not allow updating" of the mutable authorization parameter). At minimum, require that removal of an attestor cannot retroactively invalidate authors who were validly attested at the time they received their current balance.

### Proof of Concept
1. Definer `D` posts an `asset` message with `spender_attested: true, attestors: [A]` (validated by `validateAssetDefinition`, `validation.js:2725-2755`; stored per `writer.js:218-234`).
2. `D` issues units of the asset to address `U`, which has been attested by `A` (`attestation` app message, `writer.js:205-217`).
3. `U` successfully spends/holds the asset, validated per `validatePayment` (`validation.js:2115-2122`) using the attestor list resolved by `storage.readAsset`.
4. `D` posts `asset_attestors` with a new list `[B]` (`composeAssetAttestorsJoint`), validated only against `D == definer_address` (`validation.js:2829-2848`).
5. `U` (never attested by `B`) attempts to spend the previously-received balance; `storage.readAsset`'s `addAttestorsIfNecessary` now resolves the attestor list to `[B]` (`storage.js:1917-1946`), `filterAttestedAddresses` returns an empty set for `U` (`storage.js:1959-1974`), and `validatePayment` rejects the unit with `"none of the authors is attested"` (`validation.js:2118-2119`), freezing `U`'s previously valid holdings indefinitely.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
