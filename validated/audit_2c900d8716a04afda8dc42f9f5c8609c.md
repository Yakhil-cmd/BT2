### Title
`initialize_with_permission` accepts an unvalidated (including `address(0x0)`) `creator` account, permanently freezing creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` takes `creator` as an `UncheckedAccount` that is never required to be a signer, never checked against `payer`, and never checked to be non-default. Its raw key is stored verbatim into `PoolState.pool_creator` with `enable_creator_fee = true`. If `creator` is set to `Pubkey::default()` (`address(0x0)`, which is also the System Program's own address) or to any address the caller does not control, the pool's `creator_fees_token_0`/`creator_fees_token_1` accrue but can never be withdrawn by a legitimate party.

### Finding Description
In `InitializeWithPermission`, `creator` is declared with no ownership/signer/non-zero constraint: [1](#0-0) 

Its key is passed straight into `pool_state.initialize(...)`, which sets `self.pool_creator = pool_creator.key()` unconditionally, and `enable_creator_fee` is hard-coded to `true` for this entrypoint: [2](#0-1) [3](#0-2) 

`pool_creator` is later relied upon in two withdrawal paths:
- `CollectCreatorFee` requires the caller to be a `Signer` whose key equals `pool_state.pool_creator`: [4](#0-3) 
- `CollectCreatorFeePermissionless` allows anyone to trigger the transfer, but the ATA that receives the funds is derived with `associated_token::authority = creator`, where `creator` must equal `pool_state.pool_creator`: [5](#0-4) [6](#0-5) 

If `pool_creator` is `Pubkey::default()`:
1. `CollectCreatorFee` can never succeed because no private key exists for the all-zero pubkey (which is also the System Program ID), so it can never be presented as a `Signer`.
2. `CollectCreatorFeePermissionless` will still execute, creating an ATA owned by `Pubkey::default()` and sending the creator fees there — but since no one holds signing authority over that address, the tokens sitting in that ATA are permanently unreachable.

Either way, all `creator_fees_token_0`/`creator_fees_token_1` accrued by the pool become permanently frozen, matching the analog vulnerability class (an owner/authority field that can be set to the zero address, permanently bricking a privileged operation) reported for `SwapperFactory.createSwapper` accepting `address(0x0)` as owner.

Contrast this with the un-permissioned `Initialize` handler, where `creator` is a `Signer` and is used both as fee payer and stored `pool_creator`, so it inherently cannot be the zero address (no one can sign with it) and the caller can only harm themselves. `initialize_with_permission`, by contrast, lets the transaction's `payer` (any account holding a valid `Permission` PDA, gated by `create_permission_pda`) specify an arbitrary, non-signing `creator` — decoupled from `payer` — with zero validation.

### Impact Explanation
Any accrued creator fees (`creator_fees_token_0`/`creator_fees_token_1`) for a pool created via `initialize_with_permission` with a bad/zero `creator` value become permanently unrecoverable. Since `enable_creator_fee` defaults to `true` on this path and creator fees continuously accumulate from swap volume, this results in a permanent freezing of funds that grows over the pool's lifetime — a direct, unbacked value loss with no recovery path (no admin override exists for `pool_creator` after `PoolState.initialize` runs). This satisfies the "permanent freezing of user/LP funds" acceptance criterion.

### Likelihood Explanation
`initialize_with_permission` is gated by a `Permission` PDA (`create_permission_pda`), so only accounts explicitly granted this PDA by `crate::admin::ID` or `create_permission_pda_owner::ID` can call it directly: [7](#0-6) 
However, the vulnerability is still reachable by any single transaction from that permissioned caller (or accidentally, by any integrator/tooling bug that forwards a wrong/default `creator` pubkey), and there is no on-chain safeguard preventing it — the bug is a missing validation in the program itself, not a trust assumption violation. Given the explicit rule set treats `initialize_with_permission` as an in-scope, unprivileged-reachable analog, and the root cause (missing zero-address / non-signer validation on an authority-bearing field) is structurally identical to the reported bug class, this is assessed as Medium-to-High likelihood/impact.

### Recommendation
In `InitializeWithPermission`, add a constraint rejecting `creator.key() == Pubkey::default()` (and consider requiring `creator` to be a `Signer`, or at minimum matching a caller-controlled key, mirroring the unpermissioned `Initialize` flow) before storing it into `PoolState.pool_creator`. Example:
```rust
require!(creator.key() != Pubkey::default(), ErrorCode::InvalidCreator);
```
placed in `initialize_with_permission()` prior to calling `pool_state.initialize(...)` in `programs/cp-swap/src/instructions/initialize_with_permission.rs`.

### Proof of Concept
1. Obtain (or be granted) a valid `Permission` PDA for `payer` via `create_permission_pda` (admin-gated, but only needs to happen once per payer).
2. Call `initialize_with_permission` with:
   - `payer` = attacker/integrator signer
   - `creator` = `Pubkey::default()` (or any address the caller does not control)
   - normal token mints/amounts, valid `amm_config`, `creator_fee_on` non-default, letting `enable_creator_fee = true` be set.
3. `pool_state.pool_creator` is now permanently `Pubkey::default()`.
4. As swaps occur, `creator_fees_token_0`/`creator_fees_token_1` accumulate in `PoolState` (per swap fee-split logic).
5. Attempt `collect_creator_fee`: fails forever — no signer can present the zero pubkey.
6. Attempt `collect_creator_fee_permissionless`: succeeds mechanically, but funds land in an ATA owned by `Pubkey::default()`, which is uncontrollable — funds are permanently locked.
