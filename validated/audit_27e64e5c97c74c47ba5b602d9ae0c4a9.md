### Title
API Client Stack-Scoping Bypass in CCMenu Endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` resolves the target stack directly via `Stack.from_param!(params[:stack_id])` instead of going through the stack-scoped `stacks` collection defined in `Api::BaseController`, allowing an `ApiClient` token that is scoped to one stack to read build/deploy status for any other stack.

### Finding Description
The base API controller enforces that a stack-scoped `ApiClient` can only see the single stack it is bound to: [1](#0-0) 
`stacks` filters `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` is derived from that filtered collection via `stacks.from_param!(params[:stack_id])`. Every other API controller (`Api::TasksController`, `Api::DeploysController`, etc.) inherits this `stack` method, so the binding "the stack a token authorizes == the stack it touches" holds for them.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!` on the unscoped `Stack` model, not on `stacks`. The controller still declares `require_permission :read, :stack`, which only checks that the token has the `read:stack` permission bit — it never verifies the requested `stack_id` matches `current_api_client.stack_id`: [3](#0-2) 

This breaks the equality:
`stack(s) a token is authorized for == stack(s) the endpoint actually reads`

Before the fix, an `ApiClient` scoped to stack A can supply `stack_id=B` in the CCMenu route (`GET /api/stacks/*stack_id/ccmenu`, defined at [4](#0-3) ) and successfully retrieve stack B's latest deploy/rollback status via `stack.deploys_and_rollbacks.last`: [5](#0-4) 

### Impact Explanation
This is an authenticated-but-out-of-scope read of stack state (deploy status, last build result) for repositories/stacks the token was never granted access to. It matches the High-severity category of "unauthenticated/unauthorized read of stack state, task streams or deploy output" since the token's authorization is scoped to a single stack but the code path lets it read another stack's deploy state.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` authentication token that is stack-scoped and has `read:stack` permission (a routine, low-privilege API client, e.g. one created via `CCMenuUrlController` itself, which auto-creates a `read:stack`-scoped client — see [6](#0-5) ). No special privilege beyond a standard scoped token is needed, and the request is a simple `GET` with an attacker-chosen `stack_id`.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection, consistent with the rest of `Api::BaseController`'s subclasses:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures a stack-scoped token can never resolve a `stack_id` outside the one it's bound to.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id = A` with permission `read:stack` (e.g., via `CCMenuUrlController#fetch` for stack A, which creates such a client, see [7](#0-6) ).
2. Using that client's `authentication_token`, issue `GET /api/stacks/<owner>/<repo>/<branch-of-stack-B>/ccmenu?token=<token>` where stack B is any other stack in the installation.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!` (unscoped) rather than `stacks.from_param!`, the request succeeds and returns stack B's build/deploy status XML, even though the token is only authorized for stack A.
