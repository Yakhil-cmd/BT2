Investigating the repo's `sanityCheckWorktree`/`SyncRepo` logic further to confirm the exact mismatch and reachability from attacker-controlled repo content (e.g., large blobs).### Title
Worktree sanity check accepts incomplete checkouts, allowing persistent publication of partial/corrupted content - (main.go, `sanityCheckWorktree`)

### Summary
The reported PoolTogether bug is a case of *trusting a nominal quantity without verifying the actual quantity delivered*: `TwabRewards` assumes the full `tokensPerEpoch * numberOfEpochs` was received and never checks the real balance, so a fee-on-transfer token silently under-delivers and later claimants find the "accounted for" funds don't actually exist. The closest reachable analog in `git-sync` is `sanityCheckWorktree`, which likewise treats a worktree as "fully and correctly synced" based on cheap, non-exhaustive signals (HEAD hash + connectivity-only fsck) instead of verifying that the actual working-tree content matches what was supposed to be checked out.

### Finding Description
`sanityCheckWorktree` explicitly documents its own limitation: [1](#0-0) 

It only checks that the directory is non-empty, that `git rev-parse HEAD` matches the expected hash, and that `git fsck --connectivity-only` succeeds: [2](#0-1) 

`fsck --connectivity-only` validates the object graph (that all referenced objects exist and are reachable) — it says nothing about whether the *working tree* files were fully written out. If the `git reset --hard hash` performed in `configureWorktree` is interrupted partway (e.g., the process is killed, the container is OOM-killed/evicted, or disk space is exhausted while writing a large attacker-supplied blob), the object database can still be fully populated and consistent (so fsck passes) while the checked-out files on disk are truncated, missing, or stale.

This check gates the "no-op" fast path in `SyncRepo`: when `currentHash == remoteHash`, git-sync trusts `sanityCheckWorktree` to decide whether to keep the existing worktree as-is or discard and recreate it: [3](#0-2) 

Because the check can pass even for a worktree where "git could have died halfway through," a partially-written worktree that happens to have the correct commit object and connectivity can be judged "good" and left in place indefinitely — precisely analogous to the ERC20 case, where the contract has "enough" recorded state (`promotion.tokensPerEpoch`) but the real underlying resource (files on disk / token balance) is short.

### Impact Explanation
If a partially checked-out worktree passes `sanityCheckWorktree`, it will either:
- remain published via the symlink (if it was already the current link target), causing consumers to permanently read **wrong or partial content**, or
- be reused as the "current" worktree on subsequent sync loops with no remote hash change, so git-sync never repairs it — a **persistent sync denial** for correct content, since the repair path is only triggered when the sanity check fails.

This matches the accepted impact categories: publishing wrong/partial content and persistent sync denial, both without any control-plane or credential compromise.

### Likelihood Explanation
Triggering requires an interrupted checkout mid-`reset --hard`. This is a realistic, unprivileged scenario for a Kubernetes sidecar: pod eviction, OOM-kill, or disk-pressure eviction can happen at any time, and it is exacerbated by an attacker who controls the synced repository content — e.g., pushing a very large blob/commit designed to exhaust available disk (`--root` disk) mid-checkout. No special git-sync flags beyond normal shallow/full sync are required; the race is inherent to the two-step nature of `git worktree add --no-checkout` followed by `git reset --hard` in `configureWorktree`, and the weak verification is a documented, acknowledged gap rather than a hypothetical one.

### Recommendation
Strengthen `sanityCheckWorktree` (or add a post-`configureWorktree` verification step) to confirm the working tree actually matches the target commit, e.g. via `git status --porcelain` (expecting no unexpected diffs) or `git diff --quiet <hash> --` against the working tree, not just object-graph connectivity and HEAD hash. Alternatively, treat any process interruption during `configureWorktree` as fatal and force worktree recreation on the next sync attempt (e.g., write/clear a marker file before/after checkout completes) rather than relying solely on `fsck --connectivity-only`.

### Proof of Concept
1. Attacker pushes a commit to the synced branch containing a huge blob sized to exceed the available space on the `--root` volume.
2. `git-sync` fetches successfully (fetch only transfers objects, and with `--depth`/`--filter` this can succeed even for a huge tree) and calls `createWorktree` + `configureWorktree`, which runs `git reset --hard <hash>`.
3. Mid-`reset --hard`, the volume fills up (`ENOSPC`) or the pod is evicted/OOM-killed due to disk pressure, killing the git-sync process before the working tree is fully populated. The commit object itself, however, is already in the object database (fetched earlier), so `rev-parse HEAD` and `fsck --connectivity-only` both succeed on restart.
4. On the next sync loop, `currentHash == remoteHash` (no new remote change), so `SyncRepo` calls `sanityCheckWorktree`, which returns `true` despite the working tree being incomplete: [3](#0-2) .
5. The stale/partial worktree remains the target of the published symlink (or is reused untouched), and consumers of `--link` continue to read incomplete data indefinitely until the remote ref changes again.

```go
// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

	// Make sure it is synced to the right commmit.
	stdout, _, err := git.Run(ctx, worktree.Path(), "rev-parse", "HEAD")
	if err != nil {
		git.log.Error(err, "can't get worktree HEAD", "path", worktree.Path())
		return false
	}
	if stdout != worktree.Hash() {
		git.log.V(0).Info("worktree HEAD does not match worktree", "path", worktree.Path(), "head", stdout)
		return false
	}

	// Consistency-check the worktree.  Don't use --verbose because it can be
	// REALLY verbose.
	if _, _, err := git.Run(ctx, worktree.Path(), "fsck", "--no-progress", "--connectivity-only"); err != nil {
		git.log.Error(err, "worktree fsck failed", "path", worktree.Path())
		return false
	}

	return true
}
```
