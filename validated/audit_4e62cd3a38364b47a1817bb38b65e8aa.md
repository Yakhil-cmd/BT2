### Title
Premature update of `appTokenExpiry` before credential persistence succeeds causes persistent auth failures / sync denial - ([File: main.go])

### Summary
`RefreshGitHubAppToken()` in `main.go` mirrors the reported "state not cleared/committed atomically with the guarded action" bug class from the `finishWithdrawal()` report. Instead of a withdrawal record that should be deleted only after successful payout, here the "gate" is `repoSync.appTokenExpiry`, which is written to *before* the corresponding credential (`git credential approve`) is actually persisted. If persistence fails after the expiry timestamp is updated, the surrounding refresh-gating logic believes a valid token is available and skips re-issuing/re-storing it for up to the full GitHub App token lifetime.

### Finding Description
`repoSync.appTokenExpiry` is used as a time-based gate in the credential-refresh closure built in `main()`: [1](#0-0) 

This mirrors the withdrawal delay `MIN_WITHDRAWAL_DELAY`/request pattern: a piece of state (`appTokenExpiry`) is checked to decide whether the "request" (token refresh) needs to be executed again.

In `RefreshGitHubAppToken`, the expiry field is mutated as soon as the GitHub token response is decoded, but the credential store call that actually makes the new token usable happens afterward and can fail independently: [2](#0-1) 

Because `git.appTokenExpiry = tokenResponse.ExpiresAt` executes unconditionally before `git.StoreCredentials(...)`, if `StoreCredentials` returns an error (e.g., transient `git config`/`git credential approve` failure, disk pressure, permission issue on the credential store), the function returns an error to the caller — but the "gate" state (`appTokenExpiry`) has already been advanced to the new, future expiration time (commonly ~1 hour for GitHub App installation tokens). On the very next sync cycle, `refreshCreds` re-evaluates `git.appTokenExpiry.Before(time.Now().Add(30 * time.Second))`, finds it false, and skips calling `RefreshGitHubAppToken` again — exactly analogous to the reported bug where the "already executed" state was never cleared/rolled back, letting a stale/incomplete state be reused across a delay window it should not have survived.

### Impact Explanation
This causes `git-sync` to keep using whatever credential was last actually stored (which may be an expired or previously-valid-but-now-rotated token, or none at all) for authenticating `git fetch`/`ls-remote` against the remote. Every sync attempt in that window will fail authentication, producing a **persistent sync denial** until the real GitHub-issued token expiry passes and the gate check finally evaluates true again — at which point the refresh is retried. In `--max-failures`/`--init-max-failures` configurations, this can also cause `git-sync` to abort (`os.Exit(1)`) via the failure-counting loop, since fetches will keep failing during the (up to ~1 hour) window where refresh is wrongly skipped.

### Likelihood Explanation
Likelihood is Medium: it requires the `StoreCredentials` call to fail transiently while the HTTP call to GitHub's installation-token endpoint still succeeds — plausible under disk-full conditions, a `git config`/global config write failure, concurrent process interference, or any other environment-level fault affecting the local git credential store but not outbound HTTPS to GitHub. No attacker action on the synced repository is required; this is a self-inflicted logic bug reachable purely through normal GitHub App authentication operation (`--github-app-*` flags), matching the allowed "credential/token handling" analog category.

### Recommendation
Only update `git.appTokenExpiry` after `StoreCredentials` has succeeded, e.g.:
```go
if err := git.StoreCredentials(ctx, git.repo, username, password); err != nil {
    return err
}
git.appTokenExpiry = tokenResponse.ExpiresAt
```
This ensures the refresh-gate state is only advanced once the guarded action (persisting the new credential) has actually completed, consistent with the recommendation in the original report to only clear/update stateful gates after the corresponding action executes successfully.

### Proof of Concept
1. Configure `git-sync` with `--github-app-private-key-file`, `--github-app-application-id`/`--github-app-client-id`, and `--github-app-installation-id`.
2. Cause `git credential approve` (invoked inside `StoreCredentials`) to fail on one sync cycle — e.g., make the global git config file or credential cache path temporarily unwritable/read-only, or interrupt the process during that call.
3. Observe that `RefreshGitHubAppToken` returns an error (sync attempt reported failed), but `git.appTokenExpiry` has already been set to the fresh `tokenResponse.ExpiresAt` (~1 hour in the future).
4. Restore write access. On the next sync loop iteration, `refreshCreds`'s check `git.appTokenExpiry.Before(time.Now().Add(30*time.Second))` evaluates to `false`, so `RefreshGitHubAppToken` is not called again, and the stale/never-actually-stored credential continues to be used.
5. All subsequent `git fetch`/`ls-remote` calls fail authentication until the real token expiry elapses, producing persistent sync denial (and potential process abort if `--max-failures` is exceeded).
