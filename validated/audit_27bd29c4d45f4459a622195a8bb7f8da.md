### Title
Webhook organization used for signature verification is never bound to the repository whose stack is mutated - cross-tenant `PullRequest#labels` write - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the signing GitHub App/organization from `params.dig('repository','owner','login')`, while every PR handler (including `LabelCapturingHandler`) resolves the target `Stack` from a *different* field, `params.repository.full_name`, via `Repository.from_github_repo_name`. Nothing enforces that these two fields describe the same repository, so a payload correctly signed by organization A's webhook secret can carry `repository.full_name` pointing at organization B's repository, letting the handler mutate B's stack/PR data using A's authentication.

### Finding Description
The broken binding, stated as an equality that the code assumes but never checks:
`organization_that_signed(params.repository.owner.login) == organization_owning(Repository.from_github_repo_name(params.repository.full_name))`

Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and does `Shipit.github(organization: repository_owner)` to fetch that org's `webhook_secret`, then HMAC-verifies the raw body against it. [1](#0-0) 
- `Shipit.github_app_config` keys secrets per-organization, so different orgs legitimately have different `webhook_secret`s that only their own admins/operators know. [2](#0-1) 
- The handler's `ExplicitParameters` schema for `LabelCapturingHandler` only requires `repository.full_name`; it never requires or reads `repository.owner`. [3](#0-2) 
- `repository` is resolved purely from `full_name`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and `Repository.from_github_repo_name` blindly splits the string on `/` to get owner/name and does a DB lookup — with no cross-check against the org that signed the request. [4](#0-3) [5](#0-4) 
- `stack` is then `review_stack.stack`, where `ReviewStackAdapter#stack` is `scope.find_by(environment:)` scoped to `repository.review_stacks` (the victim repository's stacks). [6](#0-5) 
- `labeled_active_stack?`/`unlabeled_active_stack?`/`reopened_active_stack?` only require `stack.present? && !stack.archived?` — no repository/org check at all — and `capture_labels` writes `pull_request.update!(labels: ...)` on that resolved stack's `PullRequest`. [7](#0-6) 

Attacker's request: a POST to `/webhooks` with header `X-Github-Event: pull_request`, correctly signed with the webhook secret of an organization the attacker legitimately controls ("attacker-org"), but with body:
```json
{
  "action": "labeled",
  "number": <victim PR number>,
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "pull_request": { ..., "labels": [{"name": "attacker-label"}] },
  "sender": {"login": "attacker"}
}
```
`repository_owner` resolves to `attacker-org`, so `verify_signature` checks the signature against `attacker-org`'s own secret (which the attacker legitimately possesses), passing verification. The handler then resolves `victim-org/victim-repo`'s `Repository`, finds the victim's active (non-archived) review stack for that PR number, and overwrites its `PullRequest#labels`.

Existing guards do not stop this: `verify_signature` only checks the raw-body HMAC, it performs no equality check between `repository.owner.login` and `repository.full_name`'s owner segment; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for this handler never even requires `repository.owner`; and `capture_labels?`/`labeled_active_stack?`/`unlabeled_active_stack?` check only `action`, `stack.present?`, and `!stack.archived?` — none of which reference the authenticating organization.

### Impact Explanation
An attacker who legitimately controls one Shipit-registered organization can, with a single crafted, correctly-self-signed POST, overwrite the `labels` on the `PullRequest` record backing any other tenant's non-archived review stack, as long as they can guess/know the victim's `owner/repo` and PR number (both are public GitHub information). This is a cross-tenant write of state ("a payload for one repository mutating another's stack") and is repeatable against arbitrary repositories/stacks with no rate limiting beyond normal HTTP throughput — each request can target a different victim stack. It also affects the sibling handlers `LabeledHandler`/`UnlabeledHandler`/`OpenedHandler`/`ReopenedHandler` which share the identical `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` pattern and can archive/unarchive/provision victim stacks, extending blast radius beyond just labels, though this question is scoped to `LabelCapturingHandler`.

### Likelihood Explanation
Preconditions: the victim stack must exist and be non-archived; the attacker must control at least one organization already onboarded to the target Shipit instance (i.e., they know that organization's own `webhook_secret`, which they would in any self-service or many-org GitHub App deployment) — the attack does not require any Shipit session, API token, or the victim's own secret. Given that precondition, the attacker's cost per request is a single crafted HTTP POST with a correctly-computed HMAC over attacker-controlled bytes, fully scriptable and repeatable against any repository name/PR number.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after computing `repository_owner`, also derive the owner embedded in `repository.full_name` and reject the request (HTTP 422) if they diverge before dispatching to any handler. Alternatively, have every handler (or a shared base method) assert that `Repository.from_github_repo_name(params.repository.full_name).owner == repository_owner` (the value used to verify the signature) before resolving/mutating any stack, failing closed if they don't match.

### Proof of Concept
Minitest plan (controller-level, no live GitHub):
1. Create `victim_repo` (owner "victim-org") with an active, non-archived review stack for PR number `N`, with an initial `PullRequest#labels` value.
2. Stub `Shipit.github(organization: "attacker-org").verify_webhook_signature` (or the underlying `GitHubApp#verify_webhook_signature`) to return `true` for the exact payload/signature used, simulating a correctly-signed request from "attacker-org" (do not stub anything for "victim-org").
3. POST to `/webhooks` with `X-Github-Event: pull_request`, body `action: "labeled"`, `number: N`, `repository: {owner: {login: "attacker-org"}, full_name: "victim-org/victim-repo"}`, `pull_request.labels: [{name: "forged-label"}]`.
4. Assert response is `:ok` and `victim_stack.reload.pull_request.labels == ["forged-label"]`, proving the payload authenticated as `attacker-org` mutated `victim-org`'s stack — i.e. assert `params.repository.owner.login ("attacker-org") != Repository.from_github_repo_name(params.repository.full_name).owner ("victim-org")` yet the write still succeeded.
