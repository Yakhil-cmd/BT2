### Title
Opaque swap routes allow route-selected contracts to consume unrelated caller authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary

Controller strategy entrypoints accept opaque route bytes and forward them to the configured swap router without constraining which contracts the route can invoke. Although the controller authorizes only the expected input-token transfer and measures its own output, a malicious route can place additional attacker-selected calls beneath the caller's `require_auth` entry. If the victim signs the simulated authorization tree, a route-selected contract can transfer unrelated wallet tokens to an attacker. The regression test demonstrates this path through `swap_collateral` and confirms that the stolen transfer executes when included in the signed tree. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`swap_collateral` accepts a caller-controlled `swap: Bytes` argument and passes it to `process_swap_collateral` without decoding or constraining route destinations. [1](#0-0) 

After authenticating the caller, the strategy withdraws collateral and reaches `swap_tokens`, which invokes `SwapAggregatorClient::execute_strategy(&controller, &amount_in, swap)` with the opaque bytes unchanged. [4](#0-3) [5](#0-4) 

The controller's checks are limited to its own balances: it authorizes one exact input transfer, rejects router overspend, refunds the measured unused input, and requires a positive measured output. [6](#0-5) 

Those checks do not constrain which additional contracts the route places on the call stack or what those contracts do under the outer caller's authorization. The harness demonstrates a payload-selected `RogueHopPool` that calls `wallet_token.transfer(victim, attacker, amount)` during the route. [7](#0-6) [8](#0-7) 

### Impact Explanation

A malicious route can steal arbitrary wallet tokens held by the account owner, not merely the collateral amount intentionally supplied to the strategy. [9](#0-8) 

The test gives Alice an unrelated wallet-token balance, routes a valid `swap_collateral` call through an attacker-selected contract, and ends with Alice's wallet token balance reduced to zero while the attacker receives the full balance. [10](#0-9) 

The same result occurs in enforced authorization once the victim signs the poisoned tree containing the rogue `transfer` child. [3](#0-2) 

### Likelihood Explanation

An unprivileged attacker can deploy the malicious route target and supply its address through the opaque route payload; no protocol role or privileged operation is needed. [11](#0-10) 

The attack is not fully unilateral because the victim must sign a transaction whose simulated authorization tree includes the unexpected child transfer. [12](#0-11) 

This interaction requirement is realistic because users receive opaque route bytes and commonly rely on wallet simulation output; the test shows that simulation records the malicious transfer as a child of the otherwise expected `swap_collateral` authorization. [13](#0-12) 

### Recommendation

Do not let route-selected external code execute beneath the caller's broad strategy authorization. The controller should either require router execution through an authorization context that cannot inherit unrelated caller transfers, or require a route manifest/venue allowlist that rejects attacker-selected destinations before invoking the router. Clients should additionally fail any transaction whose authorization tree contains children other than the expected input transfer. [5](#0-4) [14](#0-13) 

### Proof of Concept

1. Alice supplies `10_000 USDC` and owns `77_770_000_000` units of an unrelated token; the attacker controls a deployed route target. [9](#0-8) 

2. The route payload names the attacker's `RogueHopPool`; during execution, that contract calls `token::transfer(Alice, attacker, WALLET_BALANCE)`. [11](#0-10) [8](#0-7) 

3. Simulation records that wallet transfer as a child authorization beneath Alice's `swap_collateral` call rather than rejecting it during route processing. [13](#0-12) 

4. Without the child authorization, enforcing mode correctly rejects the call; with the child authorization, the call succeeds, Alice loses all `WALLET_BALANCE`, and the attacker receives it. [15](#0-14)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
