### Title
Missing `cap` + `issued_by_definer_only` Cross-Check in AA Asset Definition Validation Enables Capped-Asset Supply Inflation - (File: aa_validation.js)

### Summary
`aa_validation.js`'s validation of the AA-embedded `asset` message (used when an Autonomous Agent's own definition issues a new asset) omits the invariant that a capped asset must be `issued_by_definer_only`. This invariant is present for ordinary (non-AA) asset definitions in `validation.js:validateAssetDefinition`, and `aa_composer.js:issueAsset()` relies on it silently, assuming any capped asset is safe from double-issuance because "only our AA can issue." Any unprivileged user who posts an AA definition (an AA author) can craft an AA whose definition includes an `asset` message with `cap` set and `issued_by_definer_only` false (or a formula that can evaluate to false), bypassing the invariant that the rest of the system depends on.

### Finding Description
`validation.js:validateAssetDefinition` (lines 2725–2827) enforces, for plain asset-defining units:
```
if (payload.cap && !payload.issued_by_definer_only)
    return callback("if capped, must be issued by definer only");
``` [1](#0-0) 

This check exists because the double-spend protection for `issue` inputs is address-scoped, not asset-scoped, when `issued_by_definer_only` is false:
```
if (objAsset && !objAsset.issued_by_definer_only){
    doubleSpendWhere += " AND address=?";
    doubleSpendVars.push(address);
}
``` [2](#0-1) 

For a capped asset that requires the issue amount to equal the cap exactly (`if (objAsset.cap && !objAsset.fixed_denominations && input.amount !== objAsset.cap) return cb("issue must be equal to cap")`), the only thing preventing *every* address in the network from independently issuing the *entire cap* is `issued_by_definer_only` restricting issuance to a single address. [3](#0-2) 

The analogous validation for an asset message nested inside an *AA definition* (`aa_validation.js`, `case 'asset':`) does **not** contain this cross-field check — it validates `cap`, `issued_by_definer_only`, `is_private`, `fixed_denominations` etc. as independent fields, but never rejects `cap` set together with `issued_by_definer_only` false/absent: [4](#0-3) 

Meanwhile, `aa_composer.js`'s asset-issuance logic for AA-issued assets explicitly assumes the capped case is protected purely because it's capped, with the comment "only our AA can issue, no unstable consensus-breaking issues possible":
```
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
``` [5](#0-4) 

This code checks only whether the asset has *ever* been issued globally (by any address, serial_number=1), assuming that check is sufficient to prevent duplicate issuance — an assumption that only holds if `issued_by_definer_only=true` is enforced. If an AA definer author defines an asset with `cap` set but `issued_by_definer_only` false, other unrelated addresses can each independently post `issue` inputs for the full cap amount (their own address, serial_number=1), since the double-spend scoping in `validation.js` at line 2370-2373 scopes by address specifically *because* `issued_by_definer_only` is false — allowing N different addresses to each mint the full cap, producing `N × cap` total supply for what was declared a capped asset.

### Impact Explanation
This is a supply-inflation vulnerability: a capped asset (which users and other AAs will treat as having a fixed maximum supply, per the on-chain `cap` metadata) can be minted far beyond its declared cap by any address, not just the AA. Downstream AAs, exchanges, or asset-holders that rely on the `cap` field as a supply-inflation guarantee (a common oscript/AA design pattern for token-style assets) would be silently defrauded, and this directly maps to the required "supply inflation" impact category for this analysis.

### Likelihood Explanation
Reachability is trivial and matches the "unprivileged unit poster / AA author" threat model exactly: anyone can post an AA definition unit (no special permission is required to define AAs on this DAG), and can include an `asset` message that sets `cap` and omits/falsifies `issued_by_definer_only`. `aa_validation.validateAADefinition` is the sole gate for this message shape and, as shown, lacks the cross-check that `validateAssetDefinition` performs for regular units — so the definition passes validation and becomes minable/postable. Exploitation (having a second, unrelated address issue the same capped asset) requires only posting an ordinary `issue` payment unit for that asset, which is the standard mechanism already used for any non-definer-restricted asset.

### Recommendation
Add the same invariant enforced in `validation.js:validateAssetDefinition` (`if (payload.cap && !payload.issued_by_definer_only) return cb2("if capped, must be issued by definer only")`) to the `case 'asset':` validation branch of `aa_validation.js`'s `validateAADefinition`, including handling for the formula case (i.e., when `cap` or `issued_by_definer_only` are formulas rather than literal booleans/numbers, either reject the combination outright or defer/re-validate the constraint at AA-response-generation time in `aa_composer.js` before an asset definition message is actually broadcast).

### Proof of Concept
1. Attacker (unprivileged AA author) posts an AA definition unit containing:
```json
["autonomous agent", {
  "messages": [{
    "app": "asset",
    "payload": {
      "cap": 1000000,
      "is_private": false,
      "is_transferrable": true,
      "auto_destroy": false,
      "fixed_denominations": false,
      "issued_by_definer_only": false,
      "cosigned_by_definer": false,
      "spender_attested": false
    }
  }]
}]
```
`aa_validation.js`'s `case 'asset':` block accepts this because it never checks `cap && !issued_by_definer_only` together. [4](#0-3) 
2. When the AA is triggered, `aa_composer.js` sends the response unit defining this asset (with the resulting asset "unit" as its `asset` id), matching the assumption of `objAsset.cap` implying safety at line 1195. [5](#0-4) 
3. Multiple unrelated addresses (not the AA) each post ordinary `payment` units with an `issue` input for that asset, `amount = cap`, `serial_number = 1`, `address = <their own address>`. Because `objAsset.issued_by_definer_only` is false, `validation.js` scopes the double-spend check per-address (`doubleSpendWhere += " AND address=?"`), so each of these units passes independently. [2](#0-1) 
4. Each such unit is validated and accepted as long as `input.amount === objAsset.cap` (line 2345), so N different addresses each successfully mint the declared "capped" supply, producing total circulating supply of `N × cap` instead of `cap`. [3](#0-2)
