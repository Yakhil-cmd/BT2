### Title
Webhook signature verification keys off `repository.owner.login` while handlers scope mutations by `repository.full_name`, letting an Org A-signed payload mutate Org B's stacks/commits - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate `X-Hub-Signature` using `params.dig('repository','owner','login')`, but every handler (`PushHandler`, `CheckSuiteHandler`, `Handler#stacks`) resolves the repository/stack to mutate using the independent field `payload.dig('repository','full_name')`. Because both fields live in the same attacker-controlled JSON body and are never cross-checked, an attacker who legitimately controls Org A's webhook secret can sign a payload where `repository.owner.login` = "OrgA" (so Org A's secret verifies) but `repository.full_name` = "OrgB/target-repo", causing the handler to load and mutate Org B's `Repository`/`Stack`/`Commit` records.

### Finding Description
The claimed binding: `Shipit.github(organization: repository_owner).webhook_secret` used to verify the signature must equal the webhook secret of the organization owning every `Repository`/`Stack`/`Commit` the invoked handler mutates from the same payload — i.e. `params.dig('repository','owner','login') == Repository.from_github_repo_name(payload.dig('repository','full_name')).owner`.

Tracing the code:
- `verify_signature` picks the app/secret via `repository_owner`, defined as `params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) [2](#0-1) 
- On success, `create` re-parses the same raw body and dispatches to all registered handlers for the event with the full unsigned `params` hash. [3](#0-2) 
- `Handler#stacks`/`#repository_name` resolve the target `Repository` using `payload.dig('repository', 'full_name')`, a field entirely independent of `repository.owner.login`. [4](#0-3) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack of that repository matching the attacker-chosen branch. [5](#0-4) 
- `CheckSuiteHandler#process` similarly scopes by `stacks.where(branch: ...)` (derived from `full_name`) and calls `schedule_refresh_check_runs!` on Org B's commits. [6](#0-5) 
- `PullRequest::OpenedHandler`/`LabelCapturingHandler` likewise resolve `repository` solely from `params.repository.full_name`, never re-validating against the org whose secret verified the request. [7](#0-6) 

No code anywhere compares `repository_owner` (used for auth) against the repository actually mutated (`full_name`'s owner segment). `drop_unhandled_event`, `check_if_ping`, and `ExplicitParameters` schemas only validate presence/type of fields, not cross-field consistency, so none of them block this divergence.

Exploit flow: attacker controls a GitHub webhook configuration for a repository in Org A (so they know/can trigger delivery signed with Org A's `webhook_secret`, e.g. via GitHub's "Redeliver" UI after editing the payload, or by directly POSTing to `/webhooks` with a manually HMAC-signed body using the secret they configured for their own org's integration). They craft a `push` event JSON with `repository.owner.login = "OrgA"`, `repository.full_name = "OrgB/target-repo"`, `ref = "refs/heads/<victim-branch>"`, and `after = "<attacker-chosen-sha>"`, sign it with Org A's secret, and POST to `/webhooks`. `verify_signature` passes (Org A secret matches), then `PushHandler` loads Org B's actual `Stack` and calls `sync_github(expected_head_sha:)` with the attacker-supplied SHA, mutating Org B's stack/commit state without Org B ever authenticating this request.

### Impact Explanation
This lets a party who controls only their own organization's webhook integration force GitHub-sync operations against an arbitrary victim organization's `Stack`/`Repository`/`Commit` records purely by naming that victim's `full_name` in a forged payload signed with the attacker's own credentials. This is a direct violation of the tenant-isolation invariant Shipit relies on (one webhook secret per organization authorizing mutation of only that organization's repositories) and matches the "payload for one repository mutating another's stack, commit, task or team" Critical impact category. It is repeatable against any organization/repository/branch the attacker can name, without any interaction from or knowledge required from the victim.

### Likelihood Explanation
Preconditions: attacker must have configured (or otherwise possess) a valid `webhook_secret` for at least one organization/app registered in `Shipit.github`, which per the threat model they are assumed to hold for "their own org." No Shipit session, GitHub token, or victim-org secret is required. Constructing the payload and computing the HMAC with a known secret is trivial and fully repeatable per request; the only constraint is that a stack must exist for the spoofed branch/repository in the target org, which is public/discoverable information.

### Recommendation
Bind the authorized organization to the mutation target: after (or as part of) `verify_signature`, extract the owner from `payload.dig('repository','full_name')` and reject the request (422) unless it matches `repository_owner`/the organization whose secret validated the signature. Alternatively, have handlers receive the already-verified organization and assert `Repository.from_github_repo_name(full_name).owner == verified_organization` before performing any mutation, raising instead of silently proceeding on mismatch.

### Proof of Concept
Minitest plan (WebMock/Mocha, no live GitHub):
1. Stub `Shipit.github(organization: "org-a")` to return a `GithubApp` double whose `webhook_secret` is a known value `SECRET_A`, and stub `Repository.from_github_repo_name("org-b/target-repo")` to return a real `shipit_repository(:github)` fixture belonging to org "org-b" with an existing `Stack` on branch `master`.
2. Build a `push` payload: `{"ref"=>"refs/heads/master","after"=>"deadbeef","repository"=>{"owner"=>{"login"=>"org-a"},"full_name"=>"org-b/target-repo"}}`.
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', SECRET_A, body)`.
4. POST to `/webhooks` with header `X-Github-Event: push` and the computed signature.
5. Assert response is `200 OK` (i.e., `verify_signature` succeeded using Org A's secret — left side of the binding: `repository_owner == "org-a"`).
6. Assert that `Stack#sync_github` was invoked (via `Stack.any_instance.expects(:sync_github)` or checking a resulting `Commit`/sync state change) on the org-b stack — right side of the binding: mutated repository owner == `"org-b"` ≠ `"org-a"`, proving the equality the system should enforce is violated.
7. The test should currently fail (mutation occurs) demonstrating the vulnerability; after the fix, the same request should return `422` and no mutation should occur on the org-b stack.
