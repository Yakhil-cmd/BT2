### Title
`StatusHandler` writes commit statuses across repository boundaries because the SHA lookup is not scoped to the webhook-authenticated repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`), then dispatches the raw JSON to the matching handler. `StatusHandler`, unlike `PushHandler` and `CheckSuiteHandler`, never re-derives the target `Stack`/`Repository` from that same `repository.full_name` field — it queries `Commit` globally by `sha` alone, so the binding "organization whose webhook secret authenticated the request" == "repository whose data is written" is broken.

### Finding Description
`WebhooksController#verify_signature` selects the `GithubApp` instance to verify the HMAC signature via `repository_owner`, itself read straight out of the untrusted payload (`params.dig('repository','owner','login')`): [1](#0-0) [2](#0-1) 

This proves only that the sender knows the webhook secret configured for *that org's* GitHub App installation — it does not restrict which `Stack`/`Repository` records the handler is allowed to mutate. The base `Handler` class does provide a correctly scoped helper, `stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository','full_name')`: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` both use this scoped `stacks` accessor before touching any commit: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, entirely omits this scoping and looks up commits globally by `sha` across every `Stack` in the installation: [6](#0-5) 

`Commit#create_status_from_github!` then unconditionally writes a new `Status` row tied to whichever `Stack`/`Commit` matched that `sha`, regardless of which repository/org's app actually signed the payload: [7](#0-6) 

Because Git objects are content-addressed, the same commit `sha` legitimately exists in multiple Shipit-tracked repositories whenever repositories share history (forks of a shared upstream, mirrored/synced repos, monorepo splits, etc. — a very common Shipit deployment pattern). An attacker who controls (or has push/collaborator rights on) *any* repository whose GitHub App/organization is registered in this Shipit instance can, on their own repo, create a real GitHub commit `status` event for a `sha` that is shared with an unrelated victim repository's tracked commit. GitHub signs and delivers that webhook using the attacker's own org's `webhook_secret`, which passes `verify_signature` (it authenticates the *sender org*, not the *target repository*). `StatusHandler#process` then finds and mutates the victim's `Commit` (any stack, any org) purely by `sha`, writing an attacker-chosen `state`/`description`/`target_url` (see `StatusHandler` params) onto it.

This directly maps to the report's bug class: `mTOFTReceiver` conflated "message type accepted" with "operation actually completing," breaking the invariant that a validated input type must correspond to the intended execution path. Here, Shipit conflates "signature verified for org X" with "write authorized for repository X," breaking the equality `organization authenticated == repository written`.

### Impact Explanation
This is a cross-repository write: an entity legitimately trusted only for its own repository/org can inject or forge commit-status data (`Status` records) for a `Commit` belonging to a completely different, unrelated stack. Since `Commit#status` (and `deployable?`, `blocked?`) is derived from `statuses`, and `add_status` triggers `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` when the aggregated state flips to success/pending, a forged "success" status on a shared-history commit can flip a victim stack's commit into a deployable/mergeable state, and can trigger continuous delivery (`schedule_continuous_delivery`) — i.e., an unauthorized deploy pathway on a repository the attacker was never authenticated for. This satisfies the Critical bar: "cross-repository writes" / "an unauthorized deploy."

### Likelihood Explanation
Requires: (1) the attacker to have push/collaborator access on *some* repository whose org's GitHub App is registered on the target Shipit instance (a normal, unprivileged-relative-to-the-victim condition — many Shipit deployments serve multiple orgs/teams), and (2) a shared commit `sha` between the attacker's repo and the victim's tracked repo/stack (realistic for forks, mirrors, or repos split from a common history — a common real-world topology). No Shipit session, `ApiClient` token, or GitHub App private key is needed; the attacker only relies on GitHub's own webhook delivery/signing for their own legitimately-owned repository.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository derived from the signed webhook payload (`repository.full_name`), analogous to `PushHandler`/`CheckSuiteHandler`'s use of `stacks`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the invariant that a webhook can only mutate commits belonging to the repository/organization that actually authenticated the request.

### Proof of Concept
1. Attacker owns/administers `attacker-org/repo-fork`, a fork (or mirrored split) of `victim-org/monorepo`, sharing commit history/SHAs, with the same Shipit GitHub App installed and configured with `attacker-org`'s `webhook_secret`.
2. `victim-org/monorepo` has a tracked `Stack` in Shipit with a `Commit` record for shared commit `abc123...` that is currently pending/blocked.
3. Attacker uses the GitHub Statuses API (normal collaborator permission on their own fork) to set a `success` status on commit `abc123...` in `attacker-org/repo-fork`.
4. GitHub delivers a `status` webhook to Shipit, signed with `attacker-org`'s secret; `WebhooksController#verify_signature` passes because `repository_owner` resolves to `attacker-org`.
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which matches the `victim-org/monorepo`'s `Commit` row (same sha), and calls `create_status_from_github!`, writing a forged `success` status onto the victim's commit — potentially flipping `deployable?` to true and triggering `schedule_continuous_delivery` / `Hook.emit(:deployable_status, ...)` on `victim-org`'s stack, entirely outside the attacker's authenticated scope.
