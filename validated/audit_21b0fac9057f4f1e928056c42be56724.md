### Title
Webhook authenticity is decided against `repository.owner.login`, but the acted-upon repository is taken from the independent, unsigned `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The ParaSpace report shows that a signature is verified over a structure that omits the field ("MarketplaceAddress") which actually determines what gets executed, letting an attacker mix a valid signature with an unrelated target. The same "authenticate-on-field-A, act-on-field-B" pattern exists in Shipit's webhook pipeline. The GitHub App/secret used to *verify* an inbound webhook is selected from `repository.owner.login` (or `organization.login`) taken straight out of the **unverified** raw request body, while the record that actually gets mutated is looked up from the independent `repository.full_name` field inside the very same unsigned body. Neither field is cross-checked against the other, and the org-selection field itself is never covered by any signature at the time the trust decision is made.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the HMAC secret) to validate against using a value pulled out of the request body before any authenticity check has occurred: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` then only checks the HMAC **if** that particular app has a `webhook_secret` configured; otherwise it unconditionally returns `true`: [3](#0-2) 

Shipit explicitly supports running with several independent GitHub Apps/organizations behind one instance, each with its own (optional) `webhook_secret`, selected via `Shipit.github_app_config(organization)`: [4](#0-3) 

Once `verify_signature` passes (for any reason, including the "no secret configured" fallback), `WebhooksController#create` dispatches the **entire raw payload** to the handlers, unmodified: [5](#0-4) 

Handlers never look at `repository.owner.login` again - they resolve the target `Repository`/`Stack` purely from `repository.full_name`: [6](#0-5) [7](#0-6) 

Because the attacker fully controls the JSON body of an unsigned request, they can set `repository.owner.login` (or `organization.login`) to any organization configured in the same Shipit instance that has *no* `webhook_secret` set - a state the project's own setup docs present as a normal, optional configuration for multi-org installs: [8](#0-7) [9](#0-8) 

That choice makes `verify_webhook_signature` return `true` unconditionally, while `repository.full_name` in the same forged body can name an entirely different, properly-secured organization's repository. The binding that should hold is:

`organization whose secret authenticated the request == organization whose repository is mutated`

but the code instead lets the attacker set these independently, breaking the equality exactly like the ParaSpace `Credit` struct let the taker substitute an `orderId`/marketplace unrelated to what the maker's signature actually covered.

### Impact Explanation
An attacker with no credentials can forge GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) for any repository/stack tracked by a co-hosted, properly-secured GitHub organization, as long as any other organization configured on the same Shipit instance lacks a webhook secret. Depending on which handler is invoked, this can:
- fabricate CI `Status`/`check_suite` state for arbitrary commits (`app/models/shipit/webhooks/handlers/status_handler.rb`), feeding directly into `MergeRequest#reject_unless_mergeable!`'s CI checks used to gate auto-merge,
- trigger `stack.sync_github` (push handler) causing Shipit to act on an attacker-chosen `expected_head_sha`,
- create/label/archive review stacks and pull requests.

Because this can be leveraged to falsify the CI signals that gate the merge queue, it can escalate into an unauthorized merge - a Critical-tier impact per the engine's own severity bar (unauthorized deploy/rollback/merge). At minimum it is an unauthenticated-write path into stack/commit/PR state for repositories the attacker has no access to, which is High-tier (unauthenticated manipulation of stack/task state).

### Likelihood Explanation
Likelihood is proportional to how common multi-org Shipit deployments with a mix of secured/unsecured GitHub Apps are; the feature and its optional-secret configuration are both documented and directly supported by the code (`Shipit.github_app_config`, `TOP_LEVEL_GH_KEYS`), so this is not a hypothetical/future code path — it is present and reachable today whenever more than one GitHub App is configured and even one of them omits `webhook_secret`. No credentials, session, or GitHub write access are required; only knowledge of another configured organization's name (which is typically public).

### Recommendation
Do not let any field extracted from the unauthenticated body decide which secret is used to authenticate that same body's target repository. Concretely:
- After verifying the signature with the app that matches `repository_owner`, re-validate that the acted-upon `repository.full_name`'s owner matches `repository_owner`/the organization whose app performed the verification, rejecting on mismatch.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank for a given organization in multi-org mode; either require a secret for every configured org or explicitly fail closed rather than silently trusting unsigned payloads.

### Proof of Concept
Preconditions: Shipit configured with two GitHub Apps, `orgA` (has `webhook_secret` set, hosts the real target stack `orgA/target-repo`) and `orgB` (installed but `webhook_secret` left blank, as shown as a valid config in `docs/setup.md`).

1. Attacker crafts an unsigned POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "orgA/target-repo",
    "owner": { "login": "orgB" }
  }
}
```
2. `WebhooksController#repository_owner` reads `"orgB"` from the unsigned body.
3. `Shipit.github(organization: "orgB")` returns the `GitHubApp` configured for `orgB`, whose `webhook_secret` is `nil`.
4. `verify_webhook_signature` returns `true` immediately (`return true unless webhook_secret`) regardless of the (absent/garbage) `X-Hub-Signature` header.
5. `create` dispatches the full payload to `PushHandler`, which resolves the target via `Repository.from_github_repo_name("orgA/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the real `orgA` stack — fully bypassing `orgA`'s configured `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers

        params do
          requires :ref
          requires :after
```
