### Title
Hookify rule config can be self-disabled by the same Edit/Write tool call it is meant to gate, allowing an agent (steered by prompt injection) to bypass its own safety rule before performing the guarded action - (File: plugins/hookify/core/config_loader.py, plugins/hookify/hooks/pretooluse.py)

### Summary
The `hookify` plugin implements a user-configurable safety gate: `PreToolUse` hooks read rule definitions from `.claude/hookify.*.local.md` files at the moment each tool call is evaluated, and block/warn based on `enabled`/`pattern` fields in that file's frontmatter [1](#0-0) . Because the rule file itself is just a normal file on disk and no rule (or any other mechanism) protects `.claude/hookify.*.local.md` from being edited by the same `Edit`/`Write` tool the hook is meant to gate, an agent whose context has been poisoned (e.g. via a prompt-injected file, fetched web content, or malicious repo instructions) can simply edit the rule file to set `enabled: false` (or delete/blank the `pattern`) and then immediately perform the previously-blocked dangerous action. This mirrors the ERC20 report's root cause: a privileged safeguard is trivially defeated because the same actor being restricted can also edit the whitelist/config the restriction depends on.

### Finding Description
`load_rules()` re-reads and re-parses every `.claude/hookify.*.local.md` file on every `PreToolUse` invocation, live from disk, with no integrity check, no separate storage location, and no self-protection rule [2](#0-1) . A rule is only enforced `if rule.enabled` [3](#0-2) , and `enabled` is a plain YAML boolean parsed straight from the file's frontmatter with no signing or write-protection [4](#0-3) .

The `pretooluse.py` hook fires on `Bash`, `Edit`, `Write`, and `MultiEdit` tool calls, and evaluates the *current* set of loaded rules against the input of the *current* call [5](#0-4) . There is nothing in `rule_engine.py`'s `_rule_matches`/`_check_condition` logic that treats edits to `.claude/hookify.*.local.md` specially or refuses to allow a rule file's own `enabled` flag to be flipped by an `Edit`/`Write` call [6](#0-5) .

Concretely: suppose a project has a hookify rule blocking `rm -rf` via `pattern: rm\s+-rf` [7](#0-6) . An attacker who can influence the agent's instructions (prompt injection from a fetched web page, an untrusted file the agent reads, or a malicious commit message) can direct the agent to:
1. `Edit .claude/hookify.dangerous-rm.local.md` and change `enabled: true` to `enabled: false` (this Edit call itself passes the PreToolUse hook, since no rule protects the hookify config directory itself).
2. Immediately run the now-unguarded `rm -rf ...` (or any other pattern that was gated), which the hook no longer flags because `load_rules()` re-reads the file fresh and finds the rule disabled.

This is structurally identical to the Paladin `recoverERC20` finding: the privileged operation (`recoverERC20`) is nominally protected by a whitelist check (`minAmountRewardToken[token] != 0`), but the same privileged actor (`owner`) can first call `updateRewardToken` to zero out the whitelist entry, then call the "protected" function to defeat its own safeguard. Here, the "owner" role is played by whichever party can direct Claude's tool calls (the LLM agent acting on attacker-influenced input), the "whitelist" is the hookify rule's `enabled` flag, and the "protected function" is the dangerous Bash/Edit/Write action the rule exists to catch.

### Impact Explanation
Hookify is explicitly marketed as a way for users to "prevent unwanted behaviors" and "block dangerous commands" without needing to write full `hooks.json` configurations [8](#0-7) . If a project or user relies on hookify rules as a safety net against destructive commands, secret exposure, or policy violations, that safety net is self-defeating: any code path that can make the agent issue an `Edit`/`Write` tool call against the hookify config (including via prompt injection from untrusted content the agent reads) can silently neutralize the rule before triggering the guarded behavior. The impact is a full bypass of a user-configured guardrail, potentially enabling destructive Bash commands, unauthorized file writes, or disclosure actions that the user believed were blocked — a workspace/tool-authorization bypass consistent with the "hook bypass" trust boundary in scope.

Note this is distinct from the built-in `permissions.deny`/managed-settings enforcement path (which the changelog shows has been repeatedly hardened, e.g. `PreToolUse hooks returning "allow" bypassing deny permission rules` fixes [9](#0-8) ); hookify is a separate, plugin-level, best-effort convenience layer with no such protections at all.

### Likelihood Explanation
Likelihood is moderate-to-high in any workflow where the agent processes untrusted content (fetched web pages, cloned repos with malicious files/commit messages, issue trackers, etc.) while a hookify rule is relied upon for safety, since:
- No special permission is required beyond the ordinary `Edit`/`Write` capability the agent already has.
- The rule file's own path is not excluded from any rule matching, and rules only match by `pattern`/`conditions` chosen by the rule author — a rule author is unlikely to think to write a rule that protects the rule files themselves.
- The hook reloads rules from disk on every invocation with no caching/versioning that would detect or reject a same-turn modification.

### Recommendation
- Have `pretooluse.py` (or the hook engine) treat writes to `.claude/hookify.*.local.md` as a protected operation by default: require an explicit "meta" rule/hard-coded check that blocks or requires human confirmation before allowing `Edit`/`Write`/`MultiEdit` against hookify's own config files.
- Snapshot the set of enabled rules at the start of a turn (or session) rather than re-reading on every tool call within the same turn, so a rule cannot be disabled and then immediately exploited within the same reasoning chain.
- Consider storing hookify rule "enabled" state outside the agent-writable workspace (e.g., under a path excluded from the agent's file tools, or requiring the human operator's out-of-band approval) rather than in a plain markdown file the agent itself can edit.
- Emit a warning/audit log entry whenever a hookify rule file is modified, and surface this prominently to the user, similar to how `settings.json` permission changes are surfaced elsewhere in the product.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```markdown
---
name: block-rm
enabled: true
event: bash
pattern: rm\s+-rf
---
⚠️ Dangerous rm command blocked.
```
2. Confirm a direct `rm -rf /tmp/test` is blocked/warned by hookify's `PreToolUse` hook (per `pretooluse.py` → `load_rules(event='bash')` → `RuleEngine.evaluate_rules`) [10](#0-9) .
3. Have the agent (e.g., steered by a prompt-injected instruction in a file it reads) issue an `Edit` tool call on `.claude/hookify.block-rm.local.md` changing `enabled: true` to `enabled: false`. This `Edit` call itself passes the hook because no rule in the repo protects the hookify config path.
4. Immediately issue `rm -rf /tmp/test` again in the same session — `load_rules()` re-reads the file, finds `rule.enabled == False`, excludes it from the loaded rule set [3](#0-2) , and the dangerous command now executes with no warning or block.

**Uncertainty:** I was not able to fully verify whether any *other* layer of Claude Code (e.g., core `permissions.deny` rules configured separately in `settings.json`, or `sandbox.filesystem` restrictions) would independently block edits to `.claude/hookify.*.local.md` in a default installation — the index does not show any such rule shipped by default with the hookify plugin itself, but a user could add one manually. If such a rule is not configured by the user, the bypass described above applies directly to the hookify plugin's own logic as shown in the cited files.

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```

    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True

```

## Overview

The hookify plugin makes it easy to create custom hooks that prevent unwanted behaviors. Instead of editing `hooks.json` files, users create simple markdown configuration files that define patterns to watch for.

## How It Works

### 1. Hook System

Hookify installs generic hooks that run on these events:
- **PreToolUse**: Before any tool executes (Bash, Edit, Write, etc.)
- **PostToolUse**: After a tool executes
- **Stop**: When Claude wants to stop working
- **UserPromptSubmit**: When user submits a prompt

These hooks read configuration files from `.claude/hookify.*.local.md` and check if any rules match the current operation.
