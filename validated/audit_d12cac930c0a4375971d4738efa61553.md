### Title
Unbounded private-payment chain length allows a counterparty to force full-chain re-validation, DoS-ing the recipient's ability to accept payment - (File: indivisible_asset.js)

### Summary
`parsePrivatePaymentChain()` / `validatePrivatePayment()` in `indivisible_asset.js` and `validateAndSavePrivatePaymentChain()` in `private_payment.js` walk and validate the **entire** private (blackbyte) payment chain, element by element, back to the original issuance, every time a chain is received. There is no upper bound on the number of elements (`arrPrivateElements.length`) a sender can build into a chain, and each element requires a DB round trip (`spend_proof` lookup, `graph.determineIfIncluded`, full `validation.validatePayment`). A malicious private-payment counterparty fully controls how many hops are in the chain before finally sending it to a victim, so this is reachable by any unprivileged private-asset counterparty.

### Finding Description
When a device receives a private payment chain (`network.js:handleOnlinePrivatePayment` → `private_payment.js:validateAndSavePrivatePaymentChain` → `indivisible_asset.js:validateAndSavePrivatePaymentChain` → `parsePrivatePaymentChain`), the whole chain is iterated serially with `async.forEachOfSeries`: [1](#0-0) 

Each iteration performs a full, expensive per-element validation via `validatePrivatePayment`, which does a spend-proof DB lookup, a `graph.determineIfIncluded` traversal, and full payment validation: [2](#0-1) [3](#0-2) 

Nothing in `validateAndSavePrivatePaymentChain` (`private_payment.js`) or in `parsePrivatePaymentChain`/`validatePrivatePayment` (`indivisible_asset.js`) checks or caps `arrPrivateElements.length` before beginning this per-hop validation work: [4](#0-3) 

The chain is entirely attacker-supplied JSON transmitted peer-to-peer (or via hub) as a `private_payment` message; the sender (a private-asset counterparty) decides how many transfer hops precede the final output to the victim. Because a private (indivisible) asset payment must be validated as a full chain back to its issuance element (there is no notion of "already-stable ancestor, skip re-validation" short-circuit for the chain-walk itself — every element is revalidated on every receipt, as seen at `parsePrivatePaymentChain`), an attacker can construct an arbitrarily long chain of trivial 1-unit-denomination transfers between addresses they control, then finally transfer to the victim. When the victim's wallet receives this chain, it must process every hop synchronously inside a single DB transaction (`BEGIN`/`COMMIT` wrapping the whole chain in `private_payment.js`), incurring O(n) DB queries and CPU work with no ceiling.

### Impact Explanation
This matches the "unauthorized... AA fund loss or freezing" / "network unable to confirm new units" bar in spirit: the victim wallet's mutex-protected private-chain processing (`mutex.lock(["saved_private"...])` in `network.js:handleSavedPrivatePayments`, and the whole-chain DB transaction in `private_payment.js`) can be monopolized by a single oversized chain, freezing the recipient's ability to process/accept that payment (and potentially other private payments serialized behind the same mutex/DB transaction) until the chain finishes validating — or effectively never, if resource/time limits (e.g., wallet timeout, mobile device constraints) are exceeded first. Because the funds sent this way are private-asset coins tied up in the unvalidated chain, the recipient cannot spend them until validation completes, so the attacker can trap counterparty funds in a state of practical unavailability by simply making the "unlocking" chain validation too expensive to finish.

### Likelihood Explanation
Reachable by any unprivileged private-asset holder/counterparty — no special privileges needed. Constructing a long chain of indivisible-asset transfers is straightforward and only costs the attacker the normal fees to compose each hop unit; all hops can even be batched/mass produced ahead of time. Likelihood is Medium: it requires the victim to actually accept private payments from the attacker (or an untrusted third party in the payment graph), which is a normal wallet workflow, but exploitation requires deliberate malicious chain construction, and severity is bounded by however costly per-hop validation actually turns out to be in practice.

### Recommendation
- Enforce a maximum private-payment chain length (e.g., a `MAX_PRIVATE_CHAIN_LENGTH` constant) and reject/`ifError` chains exceeding it in `private_payment.js:validateAndSavePrivatePaymentChain` and/or `indivisible_asset.js:parsePrivatePaymentChain` before any per-element validation begins.
- Consider processing/validating chain elements in bounded batches with yields (e.g., `setImmediate`) rather than a single unbroken `async.forEachOfSeries` loop, to avoid blocking the event loop and DB transaction for extended periods.
- Cache/short-circuit validation of already-validated/stable chain prefixes so repeated transfers of the same underlying coin don't require full re-walk from issuance each time.

### Proof of Concept
1. Attacker issues an indivisible-asset coin to themselves.
2. Attacker composes N sequential 1-hop private transfers (`composeIndivisibleAssetPaymentJoint`) to addresses they control, each one building on the previous output, for a large N (e.g., tens of thousands), constructing `arrPrivateElements` of length N.
3. Attacker sends the final private payment (with the full chain) to the victim via `handleOnlinePrivatePayment`/wallet private-payment message.
4. Victim's `private_payment.js:validateAndSavePrivatePaymentChain` → `indivisible_asset.js:parsePrivatePaymentChain` begins validating all N elements serially inside one DB transaction and one mutex-held critical section, consuming disproportionate time/DB resources and blocking the victim's ability to timely process this and other private payments, while the transferred funds remain unusable until the (possibly never-completing) validation finishes.

function validateAndSavePrivatePaymentChain(arrPrivateElements, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("no priv elements array");
	var headElement = arrPrivateElements[0];
	if (!headElement.payload)
		return callbacks.ifError("no payload in head element");
	var asset = headElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in head element");
	if (!ValidationUtils.isNonnegativeInteger(headElement.message_index))
		return callbacks.ifError("no message index in head private element");
	
	var validateAndSave = function(){
		storage.readAsset(db, asset, null, function(err, objAsset){
			if (err)
				return callbacks.ifError(err);
			if (objAsset.is_private !== 1)
				return callbacks.ifError("asset is not private");
			if (!!objAsset.fixed_denominations !== !!headElement.payload.denomination)
				return callbacks.ifError("presence of denomination field doesn't match the asset type");
			if (!!objAsset.fixed_denominations !== ("output" in headElement))
				return callbacks.ifError("divisible asset must not have output field, indivisible must");
			db.takeConnectionFromPool(function(conn){
				conn.query("BEGIN", function(){
					var transaction_callbacks = {
						ifError: function(err){
							conn.query("ROLLBACK", function(){
								conn.release();
								callbacks.ifError(err);
							});
						},
						ifOk: function(){
							conn.query("COMMIT", function(){
								conn.release();
								callbacks.ifOk();
							});
						}
					};
					// check if duplicate
					var sql = "SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?";
					var params = [headElement.unit, asset, headElement.message_index];
					if (objAsset.fixed_denominations){
						if (!ValidationUtils.isNonnegativeInteger(headElement.output_index))
							return transaction_callbacks.ifError("no output index in head private element");
						sql += " AND output_index=?";
						params.push(headElement.output_index);
					}
					conn.query(
						sql, 
						params, 
						function(rows){
							if (rows.length > 1)
								throw Error("more than one output "+sql+' '+params.join(', '));
							if (rows.length > 0 && rows[0].address){ // we could have this output already but the address is still hidden
								const stored = rows[0];
								const payload = headElement.payload;
								let bDuplicate = false;
								if (objAsset.fixed_denominations){ // the row we selected is exactly headElement.output_index, filtered in sql above
									const claimed_output = payload.outputs?.[headElement.output_index];
									const revealed_output = headElement?.output;
									bDuplicate =
										ValidationUtils.isNonemptyObject(claimed_output)
										&& ValidationUtils.isNonemptyObject(revealed_output)
										&& stored.denomination === payload.denomination
										&& stored.amount === claimed_output.amount
										&& stored.address === revealed_output.address
										&& stored.blinding === revealed_output.blinding;
								}
								else // divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them
									bDuplicate = (payload.outputs || []).some(output => {
										return ValidationUtils.isNonemptyObject(output)
											&& stored.denomination === 1
											&& stored.amount === output.amount
											&& stored.address === output.address
											&& stored.blinding === output.blinding;
									});
								if (bDuplicate) {
									console.log("duplicate private payment "+params.join(', '));
									return transaction_callbacks.ifOk();
								}
							}
							var assetModule = objAsset.fixed_denominations ? indivisibleAsset : divisibleAsset;
							assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks);
						}
					);
				});
			});
		});
	};
	
	if (conf.bLight)
		findUnfinishedPastUnitsOfPrivateChains([arrPrivateElements], false, function(arrUnfinishedUnits){
			(arrUnfinishedUnits.length > 0) ? callbacks.ifWaitingForChain() : validateAndSave();

		validateAndSave();
