Confirmed: `Api::StacksController#stack` correctly scopes lookups through the shared `stacks` helper (`stacks.from_param!(params[:id])`, [1](#0-0) ), which in `BaseController` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is stack-scoped, [2](#0-1) . `Api::CCMenuController`, however, overrides `stack` to bypass that scoping entirely and resolve any stack from the raw `params[:stack_id]`: `Stack.from_param!(params[:stack_id])`, [3](#0-2) .

### Title
Stack-scoped ApiClient token can read any stack's CI status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
This is a confused-deputy analog of the ERC20 approve/transferFrom binding-mismatch bug class: the entity that authorization is checked *against* (the stack a token is scoped to) is not the entity the action actually operates on (the stack whose CI status is disclosed).

### Finding Description
`ApiClient` tokens can be scoped to a single `stack` (`belongs_to :stack, optional: true`) so that a client only sees/acts on that one stack, [4](#0-3) . `Api::BaseController` enforces this binding through the `stacks` helper used by every other API controller: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, then `stack ||= stacks.from_param!(params[:stack_id])`, [2](#0-1) . `Api::StacksController` and `Api::TasksController` rely on this shared, correctly-scoped `stack`/`stacks` helper.

`Api::CCMenuController` redefines `stack` independently as `Stack.from_param!(params[:stack_id])`, completely skipping `current_api_client.stack_id` filtering, [3](#0-2) . The `require_permission :read, :stack` check only verifies the client has the `read:stack` permission string, [5](#0-4)  — it never checks *which* stack the client is authorized for. Consequently the authenticated binding is `token authorizes stack A`, but the binding actually enforced/acted upon is `token can read any stack B` — exactly the "stack a token authorizes vs stack it touches" mismatch called out as in-scope in the rules.

The `/ccmenu` endpoint's own `authenticate_api_client` override further lowers the bar: it accepts the token via a plain query-string `params[:token]` (rather than only HTTP Basic auth), [6](#0-5) , and this URL/token is explicitly generated and handed out by `CCMenuUrlController` to any logged-in Shipit user for their own stack, with a client scoped to that one stack: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, [7](#0-6) .

### Impact Explanation
Any holder of a legitimately-issued, single-stack-scoped CCMenu token (e.g., a contributor with access to only one stack's CCMenu URL) can substitute a different `stack_id` in the request and read another stack's deploy/rollback status, build outcome (`lastBuildStatus`), lock status, and stack name for any stack in the instance — an unauthenticated (relative to that stack) read of stack state, which matches the "High" impact category ("unauthenticated read of stack state, task streams or deploy output").

### Likelihood Explanation
High. The `stack_id` is a URL path parameter fully controlled by the requester (`scope '/ccmenu/*stack_id'`, [8](#0-7) ), the token itself does not encode which stack it is scoped to (it's just a signed `ApiClient` id, [9](#0-8) ), and no additional privilege or session is required beyond possessing one legitimately-issued CCMenu URL/token. This requires no `webhook_secret`, no privileged account, and no GitHub App key — only an already-issued CCMenu token, which by design is meant to be narrowly scoped to a single stack.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the same scoped `stacks` helper used elsewhere (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot resolve any stack outside `current_api_client.stack_id`.

### Proof of Concept
1. A legitimate user requests their own stack's CCMenu URL via `GET /*stack_id/ccmenu_url` for `stack A`; this creates/returns an `ApiClient` scoped to `stack: A` with `permissions: ['read:stack']` and a signed token, [10](#0-9) .
2. That user (or anyone who obtains this URL, e.g. from a CI dashboard) issues `GET /ccmenu/<owner_B>/<repo_B>/<env_B>?token=<token_for_stack_A>` substituting any other stack `B`'s identifier as `stack_id`.
3. `authenticate_api_client` accepts the token for the client scoped to stack A, [6](#0-5) ; `require_permission :read, :stack` passes since the client has `read:stack`; `stack` then resolves stack B directly from `params[:stack_id]` with no ownership check, [3](#0-2) .
4. The response discloses stack B's build/lock status even though the token was never authorized for stack B.
