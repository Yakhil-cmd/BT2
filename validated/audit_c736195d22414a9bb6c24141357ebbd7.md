### Title
Webhook authentication binds only the *organization* selecting the signing secret, not the *repository* the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against using the payload's `repository.owner.login` (falling back to `organization.login`). That authenticated value is never checked against the field the event handlers actually act on: `repository.full_name`. When no `webhook_secret` is configured for the resolved organization, verification degenerates into a no-op that accepts any request, letting an unauthenticated caller pick an arbitrary `repository.full_name` for the handler to operate on.

### Finding Description
`verify_signature` derives the org used to pick the GitHub App/secret purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

That org name is fed into `Shipit.github(organization: repository_owner)`, whose `verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

Configuring a Shipit organization without a `webhook_secret` is an explicitly supported, documented state, not a deviation from the setup docs — it is the default in the packaged example configs: [4](#0-3) [5](#0-4) 

Once `verified` is (trivially) true, `create` dispatches the *entire raw payload* to every handler for the event, unmodified: [6](#0-5) 

Handlers resolve the `Stack`/`Repository`/`Commit` they mutate from a completely different payload field, `repository.full_name`, with no re-check that it corresponds to the organization that was "authenticated" during `verify_signature`: [7](#0-6) 

For example, `PushHandler` triggers a GitHub sync (git fetch + commit ingestion) for whatever stack matches `repository.full_name`: [8](#0-7) 

and `StatusHandler` writes arbitrary commit statuses (often used to gate deploy safety) for any commit matching the attacker-chosen `sha`, again scoped by no organization check: [9](#0-8) 

**The binding that breaks:** `repository_owner` (the field authenticated by `verify_signature`) ≠ `repository.full_name` (the field the handlers use to select the `Stack`/`Repository`/`Commit` they mutate). Nothing in `WebhooksController` or `Handler` enforces that these two payload fields agree, and when the resolved organization has no `webhook_secret`, the "authentication" step is a no-op, so the attacker fully controls both fields independently.

### Impact Explanation
Any organization configured in Shipit without a `webhook_secret` becomes a skeleton key for the whole installation: an unauthenticated caller can pick `repository.owner.login`/`organization.login` to hit that unconfigured org (bypassing signature checks entirely) while setting `repository.full_name` to any *other* stack's repository tracked by Shipit. This allows forging `push` events (triggering `Stack#sync_github` with an attacker-chosen `expected_head_sha`) and `status` events (writing arbitrary commit statuses) against repositories the attacker has no relationship to, which can influence commit ingestion and deploy-safety signals used to gate deploys — an unauthorized-deploy-adjacent impact achieved with zero credentials.

### Likelihood Explanation
Requires only that at least one organization in the multi-org (or single) Shipit configuration have no `webhook_secret` set — an explicitly supported and exemplified configuration in this repo's own reference configs, not a misconfiguration outside the documented setup. No token, session, or GitHub credential is needed.

### Recommendation
Bind the authenticated identity to the data being mutated: after `verify_signature` resolves `repository_owner`, require that `payload.dig('repository', 'owner', 'login')` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, and reject webhooks when the resolved organization has no `webhook_secret` configured rather than treating that as an automatic pass.

### Proof of Concept
1. Configure Shipit with an organization entry that has `webhook_secret: nil` (as shipped in `config/secrets.development.example.yml` / `test/dummy/config/secrets.yml`), alongside a separately tracked victim stack `victim-org/victim-repo` (which does have its own secret).
2. Send, with no signature header at all:
```
POST /webhooks
X-Github-Event: push

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "unconfigured-org" }
  }
}
```
3. `repository_owner` resolves to `"unconfigured-org"`, whose `github_app.verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`), so `verified` passes with no signature check performed.
4. `PushHandler` (dispatched via `create`) resolves the stack via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on the victim's stack despite the "authenticated" organization being unrelated to it.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
