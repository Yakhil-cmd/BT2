### Title
Fixed-weight benchmarking of `remote_proxy`/`remote_proxy_with_registered_proof` allows unbounded garbage-node proof to exceed charged computation weight - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
`RemoteProxyProof::RelayChain { proof: Vec<Vec<u8>>, .. }` is passed unbounded (in node count) into `sp_trie::StorageProof::new(proof).into_memory_db(...)` inside `do_remote_proxy`, which hashes and inserts every single node before any trie-path validation happens. The dispatched weight (`WeightInfoOf::<T,I>::remote_proxy()`) is a fixed constant produced by benchmarking against a minimal, single/two-node proof (`create_remote_proxy_proof`), so it does not scale with the number of proof nodes an attacker can supply within the extrinsic/block length limit.

### Finding Description
`do_remote_proxy` in [1](#0-0)  builds a `MemoryDB` from the caller-supplied `proof: Vec<Vec<u8>>` via `sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>()` and only afterward calls `sp_trie::read_trie_value`. `into_memory_db` iterates over every node in the vector, hashes it, and inserts it into the backing hashmap — this cost is incurred for *all* supplied nodes regardless of whether they form a valid path to the target key, and regardless of whether the subsequent `read_trie_value` call ever touches them.

The pre-dispatch weight for the `remote_proxy` call is computed via the `#[pallet::weight]` attribute as `WeightInfoOf::<T, I>::remote_proxy()` plus the inner call's weight, shown in [2](#0-1) . The concrete benchmarked implementation is a **constant**, unparameterized by proof size or node count: [3](#0-2) 

This constant was derived from the benchmarking helper `create_remote_proxy_proof`, which builds a trie with exactly one key inserted, producing a minimal (1-2 node) proof: [4](#0-3) . Nothing in the benchmark or weight function scales with `proof.len()` (node count) or with the size of each node, and there is no pallet-level bound (e.g. `BoundedVec`) on the `proof` field itself — it is a plain `Vec<Vec<u8>>` as declared in [5](#0-4) . The only limits are the outer extrinsic/block length limits, which bound total encoded bytes but not the number of (tiny) sub-vectors an attacker can pack into that budget.

Because the weight is a fixed constant independent of the actual number of hash/insert operations `into_memory_db` performs, an attacker can submit `proof` with a very large number of small garbage byte-vectors (not forming a valid trie path) that still decode/encode within block length limits, forcing significantly more hashing work than the benchmarked case while paying the same (cheap, fixed) weight.

### Impact Explanation
Each `remote_proxy` extrinsic can force many more hash computations during `into_memory_db` than the weight system accounts for. Since weight is what bounds how many extrinsics/how much work fits in a block, an attacker submitting multiple such extrinsics (each cheap in charged weight but expensive in real node-hashing work) can inflate actual block execution time beyond what the weight limit is supposed to guarantee, risking block-time overruns and potential slot misses — matching the scoped "execution-time DoS / block execution time overrun" impact. The existing check (`Error::InvalidProof` on failed lookup) only rejects the call *after* the expensive `into_memory_db` construction has already run, so it does not prevent the cost.

### Likelihood Explanation
Preconditions are trivial: `remote_proxy` requires only a signed origin (`ensure_signed(origin)?` in [6](#0-5) ) and a syntactically valid `RemoteProxyProof::RelayChain` value with an unknown/garbage node set — no proxy relationship or valid trie path is required to reach the expensive `into_memory_db` call, since that happens before the lookup fails with `InvalidProof`. An attacker only needs to craft many small `Vec<u8>` entries and pick a real `block` value with a known `BlockToRoot` entry (`BlockToRoot::<T,I>::get()` is public state, populated automatically via `on_validation_data`) so the code path reaches the trie-proof construction rather than failing earlier on `UnknownProofAnchorBlock`. This is repeatable across a block by submitting many such extrinsics up to the block length limit.

### Recommendation
Bound the `proof` field's node count (and/or total encoded size) with an explicit `MaxProofNodes`/`BoundedVec` type enforced at decode time, and make the benchmarked weight for `remote_proxy`/`remote_proxy_with_registered_proof` scale with the worst-case node count (parameterize the benchmark over `n` proof nodes rather than a fixed 1-node trie), charging per-node hashing cost so the metered weight bounds the real `into_memory_db` cost regardless of whether the proof is valid.

### Proof of Concept
Rust integration test plan (extends `pallets/remote-proxy/src/tests.rs`):
1. Construct `proof_small`: the valid single-key proof as in `remote_proxy_works` ( [7](#0-6) ).
2. Construct `proof_garbage`: a `Vec<Vec<u8>>` with N (e.g. 100_000) small pseudo-random byte vectors (each a few bytes, syntactically valid SCALE-encodable nodes but not part of any real trie), sized so total encoded length stays within `BlockLength` limits.
3. Call `RemoteProxy::do_remote_proxy` (or the public `remote_proxy` extrinsic) with `proof_garbage` and assert it still returns `Err(Error::<Test>::InvalidProof)` (confirming failure happens only after node processing).
4. Measure wall-clock time of step 3 vs. wall-clock time of the same call with `proof_small`, and vs. the constant weight returned by `WeightInfo::remote_proxy()`; assert that the wall-clock ratio (`proof_garbage` time / `proof_small` time) grows roughly linearly with N while the charged weight stays constant, demonstrating the divergence between charged weight and actual verification cost.

				block: 1,
			},
