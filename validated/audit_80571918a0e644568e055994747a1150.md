### Title
Cross-organization team hijack via `MembershipHandler#process` — `find_or_create_team!` matches solely on `github_id` without re-validating `team.organization` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` purely by `params.team.id` (`github_id`) and only sets `team.organization` on the creation path of `find_or_create_by!`. If a `Team` row already exists with that `github_id` (e.g. one legitimately created for a victim organization used in `Shipit.github_teams`), a `membership` webhook signed by a *different*, attacker-controlled organization's own `webhook_secret` can reuse that same numeric `github_id` and call `team.add_member(member)` on the victim's `Team` record, granting the attacker's GitHub account membership in that team without ever authenticating against the victim organization.

### Finding Description
The binding that must hold is: `team.organization == params.organization.login` for the `Team` record that `add_member` operates on. Trace:

1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-38`) resolves the GitHub App/secret via `Shipit.github(organization: repository_owner)`, and for a `membership` event, `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) falls back to `params.dig('organization', 'login')` because there is no `repository` key in a membership payload. So the signature check only proves the request was signed with the secret configured for **the organization named in the payload's own `organization.login` field** — i.e. it proves "attacker-org signed this", not "victim-org signed this."
2. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) calls `find_or_create_team!`, which does:
   ```ruby
   Team.find_or_create_by!(github_id: params.team.id) do |team|
     team.github_team = params.team
     team.organization = params.organization.login
   end
   ```
   The block (which sets `organization`) only executes when a *new* record is created. On the found-record path, `Team.find_or_create_by!` returns the existing record as-is, and the code never checks that `team.organization == params.organization.login`.
3. If a `Team` already exists with `github_id: 999, organization: 'victim-org'` (e.g. legitimately synced earlier and referenced by `Shipit.github_teams`), an attacker who controls `attacker-org` (which has its own valid, separately configured `webhook_secret` in Shipit's GitHub Apps config — Shipit explicitly supports multiple orgs, see `test/dummy/config/secrets_double_github_app.yml`) can send a `membership` `added` event signed with `attacker-org`'s secret, with `organization.login: "attacker-org"`, `team.id: 999`, and `member.login: "attacker"`.
4. `verify_signature` passes because it validates against `attacker-org`'s own secret. `find_or_create_team!` returns the pre-existing victim `Team(github_id: 999)` (block skipped). `member = User.find_or_create_by_login!("attacker")` creates/finds the attacker's `User`. `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) unconditionally appends the attacker to `team.members`.
5. `User#authorized?` (`app/models/shipit/user.rb:80-82`) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` — membership in that `Team` row (by internal id, not by verifying real GitHub org membership) now grants the attacker authorization anywhere `Shipit.github_teams` gates access (e.g. `require_permission!` in stacks/deploy authorization flows).

None of the existing guards catch this: `verify_signature` only proves which org's secret signed the payload, not that the referenced `team.id` belongs to that org; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not cross-field organizational consistency; `force_github_authentication`/`require_permission!` operate downstream and simply trust `User#authorized?`, which trusts the tainted `Team#members` relation.

### Impact Explanation
A GitHub user who merely controls a separate organization with its own legitimate app installation (not a Shipit operator, not a member of `Shipit.github_teams`) can grant themselves membership in an arbitrary pre-existing `Team` record used for authorization, by guessing/enumerating its `github_id` (team IDs are small sequential integers, easily enumerable or guessable). This directly escalates into `Shipit.github_teams` authorization gates, matching the "High" impact category (escalation into `Shipit.github_teams` authorization). It is repeatable against any team whose `github_id` the attacker can supply, across any stacks/permissions gated by that team.

### Likelihood Explanation
Preconditions: Shipit must be configured to serve webhooks for more than one GitHub organization (a supported, documented configuration — multiple GitHub Apps/orgs each with their own `webhook_secret`), and a `Team` record for the victim org must already exist with a known/guessable `github_id`. The attacker needs no victim-org credentials, no Shipit session, and no API token — only control of their own GitHub org's app installation/secret, which is attacker-controlled by definition. This is a low-cost, fully repeatable HTTP POST to `/webhooks`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after fetching/creating the team, verify `team.organization == params.organization.login` before proceeding, and raise/drop the event (or refuse `add_member`) on mismatch. E.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "organization mismatch for team #{team.github_id}" unless team.organization == params.organization.login
  team
end
```

### Proof of Concept
Minitest plan (no live GitHub):
```ruby
test "membership webhook cannot add a member to a team belonging to a different organization" do
  victim_team = shipit_teams(:...).tap { |t| t.update!(github_id: 999, organization: 'victim-org') }
  # or: victim_team = Team.create!(github_id: 999, organization: 'victim-org', name: 'core', slug: 'core', api_url: 'https://api.github.com/teams/999')

  payload = {
    action: 'added',
    team: { id: 999, name: 'core', slug: 'core', url: 'https://api.github.com/teams/999' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }

  assert_raises(ArgumentError) do
    Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload) # or however Handler is invoked in tests
  end

  attacker = Shipit::User.find_by(login: 'attacker')
  refute victim_team.reload.members.include?(attacker)
end
```
Assert before/after: `team.organization` ("victim-org") vs `params.organization.login` ("attacker-org") — must be equal for `add_member` to run; currently they diverge and the code proceeds anyway.
