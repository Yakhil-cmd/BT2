## Analog Finding

### Title
Improper lock ordering in private-asset double-spend resolution allows two conflicting spends to both be accepted as unique - (File: `validation.js`)

### Summary
`validation.validate()` serializes concurrent unit validations only by the set of *author addresses* of the unit being validated (`mutex.lock(arrAuthorAddresses, ...)` at [1](#0-0) [2](#0-1) ). Two units authored by different addresses (e.g. a private-asset spender colluding with, or racing, another author/device) can therefore be validated *fully in parallel*. Inside that per-unit validation path, `checkInputDoubleSpend()` reads the current `is_unique` state of a private-asset input, decides whether to "accept" the observed doublespend, and only *afterwards* takes a global `mutex.lock(["private_write"])` to perform the corresponding `UPDATE inputs SET is_unique=NULL ...` [3](#0-2) . The read/decision (`checkForDoublespends` → `onAcceptedDoublespends`) happens completely outside of the `"private_write"` lock, so the lock only protects the final write, not the read-decide-write sequence that determines correctness.

### Finding Description
This mirrors the CVE-2020-27066 bug class: a shared mutable resource (`inputs.is_unique` rows for a private asset) is protected by a lock that is acquired *after* the code has already inspected and decided to act on that resource's state, rather than around the full check-then-act sequence. In the kernel bug, `xfrm6_tunnel_free_spi` freed/mutated shared state without holding the lock that guarded concurrent readers/writers of the same object, producing a use-after-free. Here, `checkInputDoubleSpend` performs `checkForDoublespends()` — which reads the `inputs`/`units` table state and, via `graph.determineIfIncludedOrEqual`, decides the doublespend is "acceptable" — entirely without any lock, then only takes `mutex.lock(["private_write"])` immediately before the `UPDATE ... SET is_unique=NULL` [4](#0-3) . Because validation of two different units proceeds under disjoint `mutex.lock(arrAuthorAddresses, ...)` locks (line 357) whenever the units have different authors, two units that both spend the same private-asset output can run `checkForDoublespends` concurrently against the same pre-update DB snapshot, both conclude that the doublespend is acceptable, and both queue an update under `"private_write"` — each unmarking the other's input as unique. Since private-asset doublespend acceptance is written immediately (bypassing `objValidationState.arrAdditionalQueries`, which is the path used for the public-asset case and is deferred to commit time inside the *same* unit's transaction) [5](#0-4) , this direct, immediately-committed write for private assets is exactly the kind of state mutation that should be guarded end-to-end by a single lock, not just its final step.

### Impact Explanation
If both conflicting private-asset spends end up marked `is_unique=NULL` (i.e., both non-unique / both accepted as forks) instead of the second one being correctly resolved against the first, nodes can end up disagreeing on which spend is valid, or a private-asset holder can present the same private output to two different counterparties, each validating it independently against a stale/pre-lock snapshot. This is a concrete double-spend/fund-loss risk for private-payment counterparties, reachable purely by an unprivileged unit poster crafting two conflicting private-asset spending units with different authors sent close together.

### Likelihood Explanation
Exploitation requires: 1) constructing two units spending the same private-asset output, authored by different addresses so the outer `arrAuthorAddresses` locks don't serialize them, and 2) timing them so both validations reach `checkForDoublespends` before either has taken `"private_write"`. This is achievable by a determined attacker controlling both sides of a private payment (e.g., paying two different counterparties from the same UTXO in quick succession), making it a realistic, self-triggerable race rather than a purely theoretical one.

### Recommendation
Acquire the `"private_write"` mutex (or a per-asset/per-output lock) *before* calling `checkForDoublespends()` for private assets, and hold it through the read-decide-write sequence, not just around the final `UPDATE`. Alternatively, re-validate the doublespend condition (re-run the `SELECT`) after acquiring `"private_write"` and abort the accept-path if the state has changed since the initial check.

### Proof of Concept
1. Create a private, fixed-denomination asset output owned by address A.
2. From address A, compose two private payment chains spending the same output to two different recipients, each producing units authored by two different addresses (e.g. multi-device/multi-authored setups) B and C respectively.
3. Submit both units to a node (or two devices to overlapping hubs) at nearly the same time so that `validation.validate()` for the B-authored unit and the C-authored unit run concurrently (different `arrAuthorAddresses` locks).
4. Both validations independently execute `checkForDoublespends` against the pre-write DB state for the shared output, both reach `acceptDoublespends`, and both eventually flip `is_unique` for the other's conflicting input under the same `"private_write"` lock but based on stale pre-lock decisions — resulting in both private spends being accepted as non-conflicting instead of one being rejected/marked final-bad.
