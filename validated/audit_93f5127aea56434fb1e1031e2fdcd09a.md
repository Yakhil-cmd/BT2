### Title
Webhook signature verification selects the signing organization from `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field in the same payload, allowing cross-organization forgery of GitHub events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) is used to validate the inbound HMAC signature based on `repository_owner`, a value read straight out of the attacker-supplied JSON body. Every downstream event handler, however, resolves the repository/stack to mutate using a *different* field from that same body: `repository.full_name`. Nothing binds these two fields together, so a party who knows (or legitimately controls) one organization's webhook secret can sign a payload that declares itself to belong to that organization while pointing `repository.full_name` at a totally different, unrelated organization's repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

It calls `Shipit.github(organization: repository_owner)`, which in multi-tenant configurations looks up a distinct `webhook_secret` per organization key: [3](#0-2) 

The signature is verified against the *entire raw body* using whichever org's secret `repository_owner` happens to select: [4](#0-3) 

Once `verified` is true, `create` dispatches the parsed body to every handler for the event type, with no re-validation that the repository the handler will act on has anything to do with the organization whose secret validated the request: [5](#0-4) 

Handlers uniformly resolve their target using `repository.full_name`, a sibling field of `repository.owner.login` inside the same JSON object, but semantically independent from it: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

Because the attacker fully controls the JSON body before signing it with a secret they legitimately possess (any organization onboarded to the same Shipit instance, e.g. their own org), they can set `repository.owner.login` to their own organization (satisfying `verify_signature`) while setting `repository.full_name` to `"other-org/other-repo"` — a repository belonging to a different, unrelated tenant of the same Shipit install. The equality this breaks is:

`organization that authenticated the webhook (repository.owner.login → webhook_secret used)` ≠ `repository that gets written to (repository.full_name → Stack/Repository acted upon)`

Before the attack: signature verification and the acted-upon repository are implicitly assumed to be the same tenant. After a crafted request: the two are decoupled, letting a valid-but-foreign webhook sender act on any tracked repository/stack regardless of which organization's secret it used.

### Impact Explanation
Concretely reachable handlers on the forged `repository.full_name`:
- `StatusHandler` calls `commit.create_status_from_github!(params)` for any commit matching `params.sha` tracked by Shipit, letting the attacker inject an arbitrary (e.g. fabricated "success") CI status for a victim organization's commit [7](#0-6) . If that stack's deploy/merge gating or continuous delivery relies on commit status, this can enable an **unauthorized deploy**.
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for stacks matching the forged repo/branch, forcing an unrelated tenant's stack to resync at a time chosen by the attacker [8](#0-7) .
- `PullRequest::ClosedHandler`/`ReopenedHandler`/`UnlabeledHandler` archive or unarchive review stacks belonging to the forged repository [9](#0-8) .

This matches the "unauthorized deploy" impact category, achieved without the attacker ever holding push access, an `ApiClient` token, or the victim organization's `webhook_secret` — only a valid webhook secret for any org configured on the same Shipit instance.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate webhook sender for at least one organization/repository registered with the Shipit instance (i.e., they can generate a validly signed GitHub-style webhook, as any real integrator or a compromised low-privilege repo under a different org would be able to). This is a realistic scenario for any Shipit deployment onboarding multiple organizations/tenants through the multi-org `github` secrets schema (`github_app_config`), since `repository_owner` used for secret selection is entirely attacker-controlled payload content, decoupled from `repository.full_name` used for the actual mutation.

### Recommendation
After signature verification, re-derive the organization from the same trusted source used for verification and assert that `repository.full_name`'s owner segment matches `repository_owner` before dispatching to handlers, or verify the signature using the secret of the organization that owns the target repository (looked up from the `Repository` record) rather than from `repository.owner.login`/`organization.login` supplied in the payload.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (multi-org schema per `lib/shipit.rb#github_app_config`).
2. Attacker has legitimate access to sign webhooks for `attacker-org` (e.g., is a maintainer there and knows/can trigger its webhook secret via a real GitHub App delivery, or replays a captured delivery).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha tracked by Shipit>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this exact raw body.
5. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the signature.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, creating a forged "success" status for a `victim-org` commit the attacker has no access to, potentially unlocking an automated/continuous deploy gate on that unrelated stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
