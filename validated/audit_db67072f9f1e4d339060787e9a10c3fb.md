### Title
Malformed/typo'd frontmatter keys silently load a rule with zero conditions, causing it to never trigger while appearing enabled - (File: plugins/hookify/core/config_loader.py, plugins/hookify/core/rule_engine.py)

### Summary
`config_loader.extract_frontmatter` is a hand-rolled, case-sensitive YAML-subset parser, and `Rule.from_dict` only recognizes the exact lowercase keys `pattern` and `conditions`. If a rule file's frontmatter key is misspelled or mis-cased (e.g. `Pattern:` instead of `pattern:`, or a `conditions:` block the mini-parser fails to parse into a list of dicts), `Rule.from_dict` silently produces `conditions=[]` with no error, `load_rule_file` returns a valid `Rule` object, and `RuleEngine._rule_matches` unconditionally returns `False` for it forever via `if not rule.conditions: return False`.

### Finding Description
`extract_frontmatter` in [1](#0-0)  is a custom minimal parser that only recognizes exact-case top-level keys; there is no schema validation, no unknown-key detection, and no normalization of key casing. `Rule.from_dict` then looks for the literal keys `'conditions'` and `'pattern'`: [2](#0-1) . If a user/attacker-controlled rule file supplies `Pattern:` (wrong case) or a `conditions:` block that the custom parser doesn't turn into a list of dicts (e.g., an inline malformed continuation that the indentation-based state machine mis-parses), the resulting frontmatter dict simply won't contain a usable `pattern` or `conditions` value under the exact expected key, so `conditions` stays `[]`.

`load_rule_file` only errors out if the file is missing frontmatter entirely (`if not frontmatter:`) [3](#0-2) ; it does not validate that a `Rule` has usable match criteria. The rule is then treated as valid and, if `enabled: true` (which is easy to set, and even defaults to `True` if omitted per `frontmatter.get('enabled', True)`), gets included by `load_rules` [4](#0-3) .

At evaluation time, `RuleEngine._rule_matches` explicitly treats an empty `conditions` list as a permanent non-match: [5](#0-4) . This means the rule is loaded without any error/warning, appears "enabled" in `/hookify:list` and `/hookify:configure` output (which only reads `name`/`enabled` fields, not condition validity — see [6](#0-5)  and [7](#0-6) ), yet can never fire on any `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` event.

### Impact Explanation
This is a fail-open design in the hook-enforcement layer: a rule intended to `block` dangerous operations (e.g., `rm -rf`, edits to `.env`/credentials files) can be rendered permanently inert by a single subtle typo, with no error surfaced anywhere in the loader, hook output, or the `/hookify:list`/`/hookify:configure` UI. Users/CI relying on hookify for defense-in-depth against dangerous commands or secret leakage would have a false sense that protection is active. However, note the scope constraint: exploiting this requires the malformed rule file to actually be placed into the victim's `.claude/` directory (e.g., via a malicious PR contributing a "helpful" hookify rule, or an AI-generated rule with a typo that a user doesn't scrutinize) — hookify itself provides no privileged trust boundary; it's a best-effort, opt-in local safety net, not a security control enforced against an untrusted actor. This is closer to a robustness/reliability defect (silent misconfiguration) than a direct compromise of Claude Code, since no code execution, file mutation, or approval bypass is directly caused by the bug itself — it only removes a self-imposed guard the user believed was there.

### Likelihood Explanation
High feasibility for the parsing failure itself (trivial to reproduce with a case-typo or malformed `conditions:` block), but requires an external step (a malformed rule file being authored/merged and trusted) to have any real safety impact. The `/hookify` generation flow itself always emits lowercase `pattern`/`conditions` keys per the documented format [8](#0-7) , so this mainly affects manually-authored or third-party-contributed rule files.

### Recommendation
- In `Rule.from_dict` / `load_rule_file`, validate that the resulting `Rule` has at least one usable condition (or a legacy `pattern`); if not, raise a `ValueError` so `load_rule_file`'s existing exception handling surfaces a loud "Warning: rule X has no valid conditions and will never match" instead of silently returning a dead rule.
- Make `extract_frontmatter` key lookups case-insensitive or add a normalization/validation pass that flags unrecognized/unexpected top-level keys.
- Have `/hookify:list` and `/hookify:configure` explicitly show "⚠️ INACTIVE (no conditions)" status for any loaded rule with `conditions == []` and no legacy `pattern`.

### Proof of Concept
Unit test in `plugins/hookify/core` (pytest style):
```python
from hookify.core.config_loader import extract_frontmatter, Rule
from hookify.core.rule_engine import RuleEngine

def test_typo_key_creates_dead_rule():
    content = """---
name: block-dangerous-rm
enabled: true
event: bash
Pattern: rm\\s+-rf
action: block
---

Should block rm -rf
"""
    fm, msg = extract_frontmatter(content)
    rule = Rule.from_dict(fm, msg)
    # BUG: rule loads successfully with enabled=True but no usable conditions
    assert rule.enabled is True
    assert rule.conditions == []  # demonstrates silent no-op

    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /"}
    }
    result = engine.evaluate_rules([rule], input_data)
    assert result == {}  # dangerous command NOT blocked despite enabled:true block rule
```
Expected fix behavior: `Rule.from_dict`/`load_rule_file` should raise/log loudly and exclude the rule (or normalize the key) rather than silently returning a `Rule` with empty `conditions` that `evaluate_rules` treats as a no-op.

```python
def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.
    """
    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content

    frontmatter_text = parts[1]
    message = parts[2].strip()

    # Simple YAML parser that handles indented list items
    frontmatter = {}
    lines = frontmatter_text.split('\n')

    current_key = None
    current_list = []
    current_dict = {}
    in_list = False
    in_dict_item = False

    for line in lines:
        # Skip empty lines and comments
        stripped = line.strip()
        if not stripped or stripped.startswith('#'):
            continue

        # Check indentation level
        indent = len(line) - len(line.lstrip())

        # Top-level key (no indentation or minimal)
        if indent == 0 and ':' in line and not line.strip().startswith('-'):
            # Save previous list/dict if any
            if in_list and current_key:
                if in_dict_item and current_dict:
                    current_list.append(current_dict)
                    current_dict = {}
                frontmatter[current_key] = current_list
                in_list = False
                in_dict_item = False
                current_list = []

            key, value = line.split(':', 1)
            key = key.strip()
            value = value.strip()

            if not value:
                # Empty value - list or nested structure follows
                current_key = key
                in_list = True
                current_list = []
            else:
                # Simple key-value pair
                value = value.strip('"').strip("'")
                if value.lower() == 'true':
                    value = True
                elif value.lower() == 'false':
                    value = False
                frontmatter[key] = value
```
