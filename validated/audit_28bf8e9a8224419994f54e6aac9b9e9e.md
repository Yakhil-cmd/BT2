### Title
Unhandled exception in async dry-run of AA triggers permanently deadlocks the `handleJoint` mutex - (File: network.js)

### Summary
In `network.js`, the `ifOk` callback passed to `validation.validate()` inside `handleJoint()` is declared `async` and, when `conf.bDryRunNewTriggers` is enabled, iterates over AA addresses targeted by a freshly-validated unit and calls `await aa_composer.dryRunPrimaryAATrigger(...)` in a plain `for` loop with no `try/catch` around it [1](#0-0) . The inline comment even acknowledges the call can throw ("if it would crash, let it crash now") but no code guards against that, and the exception is never caught anywhere up the call chain.

### Finding Description
`handleJoint()` acquires the global `['handleJoint']` mutex before invoking `validation.validate()` [2](#0-1) . The `ifOk` handler only calls `unlock()` (releasing the `handleJoint` mutex) and `validation_unlock()` (releasing the per-validation lock) *after* the dry-run loop completes, inside the `writer.saveJoint(...)` completion callback [3](#0-2) . If `aa_composer.dryRunPrimaryAATrigger()` throws (synchronously or via a rejected promise) for any address in `rows`, execution never reaches `writer.saveJoint`, so `unlock()` and `validation_unlock()` are never invoked. Because `ifOk` is `async` and is invoked as a plain callback (`callbacks.ifOk(objAAValidationState, unlock)`) without the caller awaiting it or attaching a `.catch()`, the thrown error becomes a rejected promise that is discarded, i.e., an unhandled rejection — matching the analog bug class of "asynchronous functions called in a loop without proper error handling" from the external report. The concrete, ocore-specific effect is materially worse than a silent failure: since `['handleJoint']` is a single, global mutex key used to serialize *all* joint handling on the node, failing to release it stalls processing of every subsequent unit/joint (own or peer-relayed) indefinitely.

The dry-run path is reachable by any peer that posts (or gets relayed) a unit whose payment message targets an AA address, since `objValidationState.count_primary_aa_triggers` is set purely from `validateAATrigger()` based on payment outputs to `aa_addresses` [4](#0-3) , without any privilege check on the sender. An attacker only needs to craft/trigger a unit and definition combination that makes `aa_composer.dryRunPrimaryAATrigger()` throw during simulated execution (e.g., an oscript/AA definition edge case not otherwise guarded, or a `JSON.parse(definition)` producing input that trips an internal assertion inside the AA composer) to hit the unguarded `await` in the loop.

### Impact Explanation
A successful trigger permanently deadlocks the node's single `handleJoint` mutex, so no further units — whether locally composed, relayed from peers, or received during catch-up — can ever be validated or saved again. This directly matches the required impact class "a network unable to confirm new units": every node running with `conf.bDryRunNewTriggers` enabled that processes the crafted unit stops confirming any new unit permanently until restarted.

### Likelihood Explanation
The path is triggered purely by posting a normal payment unit that has an output to an existing AA address, no special privileges, malicious peer/hub role, or leaked keys required — this is the exact "unprivileged unit poster / AA trigger sender" surface explicitly in scope. The remaining requirement is that `aa_composer.dryRunPrimaryAATrigger()` actually throws for some payload; this depends on edge cases in AA/oscript execution but the code's own comment ("if it would crash, let it crash now, not when we execute the trigger for real") confirms the authors expect this call can legitimately throw, making the precondition realistic rather than purely theoretical. This is gated behind the `conf.bDryRunNewTriggers` config flag, so it only affects nodes running with that option enabled.

### Recommendation
Wrap the dry-run loop in `try/catch` (or attach `.catch()`), log the failure, and unconditionally proceed to call `validation_unlock()`/`unlock()` (e.g., via a `finally` block or explicit error path) regardless of whether the dry run succeeds, so a crashing AA simulation can never leave the global `handleJoint` mutex locked:
```js
if (conf.bDryRunNewTriggers && !conf.bLight && !objJoint.ball && objValidationState.count_primary_aa_triggers) {
    try {
        const rows = await db.query(...);
        for (let { address, definition } of rows) {
            const trigger = aa_composer.getTrigger(objJoint.unit, address);
            await aa_composer.dryRunPrimaryAATrigger(trigger, address, JSON.parse(definition));
        }
    } catch (e) {
        console.log('dry run of AA trigger crashed: ' + e);
        // continue to saveJoint/unlock regardless
    }
}
```

### Proof of Concept
1. Run a node with `conf.bDryRunNewTriggers = true` (and `conf.bLight = false`).
2. Craft/post a unit that pays to an existing AA address whose definition, when combined with the trigger data, causes `aa_composer.dryRunPrimaryAATrigger()` to throw during simulated execution (an internal assertion/exception in AA formula evaluation reachable via unit/trigger content).
3. Broadcast this unit to the target node so `handleJoint()` processes it and reaches the `ifOk` branch that performs the dry run [5](#0-4) .
4. Observe that the thrown/rejected error is never caught, `validation_unlock()`/`unlock()` in the `writer.saveJoint` callback are never reached [3](#0-2) , and the `['handleJoint']` mutex remains held.
5. Post any subsequent unit (from any sender) and observe it never gets processed, confirming the node can no longer confirm new units.
