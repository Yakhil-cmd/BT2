### Title
Cross-organization request forgery lets an attacker-controlled org's blank `webhook_secret` authorize `check_suite` mutations against a victim org's `Stack`/`Commit` records - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the organization used for HMAC verification from `params.dig('repository','owner','login')`, while `Handler#stacks` (used by `CheckSuiteHandler`) independently derives the repository to mutate from `payload.dig('repository','full_name')`. Nothing enforces that these two attacker-supplied fields refer to the same repository, so an attacker who names an org with no `webhook_secret` configured in Shipit's YAML in `repository.owner.login` can put an arbitrary victim `repository.full_name` in the same payload and pass signature verification trivially, causing the handler to operate on the victim's `Stack`/`Commit` records.

### Finding Description
The claimed binding is: `repository_owner` (the field used to select the `GitHubApp` for signature verification) `==` `owner(Repository.from_github_repo_name(payload['repository']['full_name']))` (the field used to select the repository whose stacks get mutated).

Tracing the code:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`, where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`) — fully attacker-controlled JSON.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally `unless webhook_secret` — i.e., if the org named in `repository.owner.login` has no `webhook_secret` configured in Shipit's secrets YAML, **any** signature (or none) is accepted.
- `Handler#stacks` / `#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) independently reads `payload.dig('repository', 'full_name')` — from the same raw, unvalidated JSON payload — and does `Repository.from_github_repo_name(repository_name)` to find the repository whose `stacks` are operated on. `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-16`) uses this to enumerate `stacks.where(branch: ...)` and call `stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!)`.
- Critically, `CheckSuiteHandler`'s `params do ... end` schema (`check_suite_handler.rb:7-12`) does not even declare/require a `repository` key, so `ExplicitParameters` performs no validation on it at all — the handler reads it straight off the raw `payload`, completely decoupled from whatever `repository.owner.login` said.

There is no code anywhere that cross-checks `repository.owner.login` against `repository.full_name`'s owner segment. An attacker's exact request: POST `/webhooks` with header `X-Github-Event: check_suite` and body:
```json
{
  "check_suite": {"head_sha": "<victim commit sha>", "head_branch": "<victim branch>"},
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}
}
```
where `attacker-org` is any organization configured in Shipit's `github:` YAML with a blank/unset `webhook_secret` (a documented "optional" setting per `docs/setup.md:30`, and the default in the shipped example configs, e.g. `test/dummy/config/secrets.yml:13`, `secrets.development.example.yml:11`). `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, which returns `true` from `verify_webhook_signature` regardless of the signature header. `Shipit::Webhooks.for_event('check_suite')` then invokes `CheckSuiteHandler.call(params)`, whose `stacks` method resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and operates on the victim's real `Stack`/`Commit` records.

Existing guards do not prevent this: `drop_unhandled_event` only checks the event is registered; `verify_signature` only checks the *named* org's secret, never that the named org matches the repository being mutated; `ExplicitParameters` validates types/presence but not cross-field consistency, and `CheckSuiteHandler`'s schema doesn't even declare `repository`.

### Impact Explanation
A payload authenticated (trivially, due to a blank secret) under one organization mutates another organization's `Stack`/`Commit` records — this is the "payload for one repository mutating another's stack, commit, task or team" critical category. Concretely, `CheckSuiteHandler` calls `Commit#schedule_refresh_check_runs!`, which enqueues `RefreshCheckRunsJob` (`app/jobs/shipit/refresh_check_runs_job.rb`) to call `Commit#refresh_check_runs!` against the victim's real commit — an attacker can force status/check-run refresh cycles on arbitrary victim commits at will, and any other handler with the same `Handler#stacks`/`repository_name` pattern (e.g. `PushHandler`, `StatusHandler`) is equally exposed to organization/repository confusion, since none of them validate that the resolved repository actually belongs to the org that was cryptographically verified. This is repeatable against any repository name the attacker chooses, for as long as at least one configured org in the Shipit deployment has no `webhook_secret` set (common in single-org/default deployments per the shipped documentation and example configs).

### Likelihood Explanation
Preconditions: (1) the Shipit deployment has at least one configured GitHub organization with a blank `webhook_secret` in its YAML — this is explicitly documented as "optional" and shown as the default in shipped example/test configs; (2) the attacker knows that org's name, which is public/discoverable (it's whatever org Shipit is configured for, visible via the app's UI/URLs) and (3) knows or guesses the victim's `owner/repo` name, also public information. No GitHub secrets, session, or API token are required — the attacker POSTs directly to `/webhooks` as an anonymous internet user. This is low cost and fully repeatable.

### Recommendation
In `Handler#repository_name` (or centrally, before dispatching to any handler), require that the owner segment of `payload.dig('repository', 'full_name')` matches the verified `repository_owner`/organization used in `WebhooksController#verify_signature`, and reject the payload otherwise. Additionally, `CheckSuiteHandler` (and any handler using `Handler#stacks`) should declare and validate `repository.full_name` (and ideally `repository.owner.login`) in its `params` schema rather than reading directly from the unvalidated `payload`, and the controller should pass the already-verified organization down to handlers instead of letting each handler independently re-derive the repository/org from attacker-controlled JSON.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "check_suite payload with mismatched repository.owner and repository.full_name mutates the wrong org's stacks" do
  # Precondition: 'attacker-org' is configured in secrets.github with no webhook_secret
  # (simulate via Shipit.github(organization: 'attacker-org') stub or fixture config)
  victim_stack = shipit_stacks(:shipit)  # belongs to victim-org/victim-repo
  victim_commit = shipit_commits(:first)
  victim_stack.update!(branch: 'master')
  victim_commit.update!(sha: 'deadbeef', stack: victim_stack)

  request.headers['X-Github-Event'] = 'check_suite'
  body = {
    check_suite: { head_sha: 'deadbeef', head_branch: 'master' },
    repository: { owner: { login: 'attacker-org' }, full_name: victim_stack.repository.github_repo_name }
  }.to_json

  # verify_webhook_signature returns true unconditionally because attacker-org has no webhook_secret
  assert_enqueued_with(job: RefreshCheckRunsJob, args: [{ commit_id: victim_commit.id }]) do
    post :create, body:, as: :json
    assert_response :ok
  end
  # Equality broken: repository_owner ('attacker-org') != owner of the resolved Repository ('victim-org'),
  # yet the victim's commit was scheduled for refresh.
end
```
