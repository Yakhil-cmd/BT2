## Analog Found: `spender_attested` Asset Restriction Only Checks Output Addresses, Never the Actual Spender

### Title
KYC/Attestation-gated Assets (`spender_attested`) Can Be Bypassed by Revoked/Non-Attested Spenders Because Only Output Addresses Are Verified - (File: `validation.js`)

### Summary
The external report describes a role (`SOFT_RESTRICTED_STAKER_ROLE`) that is meant to prevent an address from directly depositing funds, but because only the deposit side is restricted (not other operations like transferring/holding), the restricted party can route funds through another address they control to bypass the intended restriction. Ocore has a structurally identical asset-level access-control primitive: `spender_attested`, whose very name implies that whoever spends (holds/transfers) the asset must be attested by a trusted attestor. However, the validation code only ever checks that the **output/recipient** addresses of a payment are attested — it never checks whether the **input/spending** addresses are (still) attested.

### Finding Description
When an asset is defined with `spender_attested: true`, its definer publishes a list of trusted `attestors` [1](#0-0) . Every payment or issuance of that asset is checked in `validatePaymentInputsAndOutputs`: [2](#0-1) 

This block calls `storage.filterAttestedAddresses(conn, objAsset, objValidationState.last_ball_mci, arrOutputAddresses, ...)` and fails the payment only if some **output** address is not attested. `filterAttestedAddresses` itself only ever receives and filters `arrOutputAddresses`: [3](#0-2) 

Nowhere in `validatePaymentInputsAndOutputs` is `arrInputAddresses` passed through this attestation filter — the array is only used for balance/transferability checks [4](#0-3) . This means the field named "spender_attested" (with the DB comment "must subsequently publish and update the list of trusted attestors") does not actually verify that the spender (the address consuming the inputs) is attested at the time it spends — it only verifies that the address receiving the new output is attested at the time the coins land there.

Consequently, once an address has been attested a single time and has received the asset, an attestor can later revoke/blacklist that address (e.g. by publishing a new `asset_attestors` list that excludes it, or simply never re-attesting it), and it will make no difference: the address can continue to freely spend/transfer the already-held coins forward, as long as it routes them to any address that is currently attested — including another address the same holder controls that happens to still be (or gets freshly) attested. This is exactly the Sybil/bypass pattern from the external report: the restriction only gates one side of the operation (who can receive), so a restricted/blacklisted holder simply moves value through an address they own that satisfies the check on the other side.

### Impact Explanation
`spender_attested` is the mechanism asset issuers rely on for regulatory/KYC gating of who is permitted to hold and move a Bytecoin/Obyte asset (e.g., a security token or stablecoin requiring KYC). Because the input side is never re-validated, a holder who has since been de-attested/blacklisted by the attestor retains full, unrestricted ability to keep transacting the asset as long as they can find or create an attested counterpart address, defeating the entire purpose of the control. This is a medium-severity access-control/compliance bypass: it doesn't cause double-spends or fund loss in the base-layer accounting sense, but it allows continued unauthorized use/circulation of an asset whose issuer has explicitly revoked an address's authorization, which is the exact "role bypass" class flagged in the source report.

### Likelihood Explanation
This requires no special privileges beyond owning two addresses (one that was attested at some point, or acquiring attestation once) and constructing an ordinary `payment` message for the `spender_attested` asset — a standard, unprivileged operation any unit poster can perform. The only "attacker" precondition is having previously obtained attestation (a one-time KYC pass) or already holding a balance; after that, the bypass is available indefinitely since the input side is never checked again.

### Recommendation
In `validatePaymentInputsAndOutputs` (validation.js), when `objAsset.spender_attested` is true, also run `storage.filterAttestedAddresses` against `arrInputAddresses` (in addition to `arrOutputAddresses`) and reject the payment if any input address is not currently attested, ensuring that spenders — not just recipients — must hold a valid, non-revoked attestation at `last_ball_mci`.

### Proof of Concept
1. Issuer defines an asset with `spender_attested: true` and attestor list `[A]`.
2. Attestor `A` attests address `X`. `X` receives a payment of the asset (valid, since output `X` is attested).
3. Attestor `A` later publishes a new `asset_attestors` update that no longer includes `X` in effect (or simply revokes trust off-chain and stops considering `X` valid).
4. `X` still holds a balance of the asset. `X` constructs a payment sending the asset to `Y`, an address that `X` also controls and that is (or becomes) attested by `A`.
5. `validatePaymentInputsAndOutputs` checks only that `Y` (output) is attested via `filterAttestedAddresses` [2](#0-1)  — it never checks that `X` (input) is still attested — so the payment validates successfully, letting the de-attested `X` continue circulating the restricted asset indefinitely.

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\

			0)",
