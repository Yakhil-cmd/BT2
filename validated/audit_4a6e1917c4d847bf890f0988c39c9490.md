## #Analog Found

### Title
Rounding-to-zero in order-matching formula allows draining a counterparty's remaining order amount for free - ([File: test/samples/order_book_exchange.oscript])

### Summary
The `order_book_exchange.oscript` AA (shipped in the ocore repo as a reference AA template) matches two signed orders and computes the counter-amount owed to each side by multiplying the remaining sell amount by a price and rounding to an integer, exactly the same `amount * rate` truncation pattern that produced the Cooler.sol `collateralFor` bug. Because the multiplier (`price`) and the multiplicand (`$amount_left1`, the *remaining* unfilled quantity of an order) are both attacker-influenceable — either directly, by crafting one's own order with an extreme price, or indirectly, by choosing when to match a resting order after it has been partially filled down to a small remainder — the computed `$buy_amount1` can round down to `0` while the full `$amount_left1` of the other side's asset is still transferred.

### Finding Description
In the "execute orders" case, the AA computes:
```
$buy_amount1 = round($amount_left1 * $order1.price);
...
var[$sell_key1] = var[$sell_key1] - $amount_left1;
var[$sell_key2] = var[$sell_key2] - $buy_amount1;
var[$buy_key1]  = var[$buy_key1]  + $buy_amount1;
var[$buy_key2]  = var[$buy_key2]  + $amount_left1;
``` [1](#0-0) [2](#0-1) 

`$amount_left1` is the *remaining* unfilled quantity of order1, which shrinks with each partial fill:
```
$amount_left1 = var['amount_left_' || $id1] otherwise $order1.sell_amount;
``` [3](#0-2) 

Because `round()` truncates fractional results and there is no minimum-amount / non-zero check on `$buy_amount1`, a trade where `$amount_left1 * $order1.price < 0.5` makes `$buy_amount1 = 0`. The state update then debits `var[$sell_key2]` by `0` (order2 gives up nothing) while crediting `var[$buy_key2]` with the *full* `$amount_left1` (order2 receives order1's entire remaining balance) and debits `var[$sell_key1]` by the full `$amount_left1` with `var[$buy_key1]` credited only `0`. This is functionally identical to the Cooler.sol issue: a party (here the "matcher"/relayer submitting the AA trigger, who supplies both signed orders in `trigger.data`) can choose *when* to submit the match — after a resting order's remainder has shrunk enough, or by crafting their own extreme-price order — so that the multiplication-then-rounding step zeroes out the compensation owed to one side while the other side's full balance is still moved.

The check that exists, `if ($expected_buy_amount2 > $amount_left1) return false;`, only protects order2 from receiving *less* than their own price implies; it does not protect either side from the primary `$buy_amount1` rounding to zero, which is the actual value-transfer step.

### Impact Explanation
An unprivileged AA trigger sender (anyone can call this AA with two previously-signed orders, since matching only requires `is_valid_signed_package` on data the caller supplies) can engineer a match where one order's remaining balance is transferred to the other party's account inside the AA's internal balance ledger while giving up nothing in return. Because these are AA-tracked internal balances that back real on-chain asset/byte withdrawals via the "withdraw funds" case, this results in real, permanent fund loss for the disadvantaged order owner and a free credit for the attacker-controlled counter-order — i.e., concrete unauthorized value transfer / AA fund loss.

### Likelihood Explanation
Exploitation only requires: (1) a resting order whose remaining amount has been driven down by prior partial fills (a normal, expected AA state, not requiring any protocol bug), and (2) the attacker supplying/matching an order (their own, or another party's cooperatively/obliviously signed one) with a price such that `remaining_amount * price < 0.5`. No special privileges are needed — any address can submit the AA trigger with both signed order packages, making this trivially reachable and repeatable by watching the order book state.

### Recommendation
Add an explicit check that rejects the match (or clamps/rejects the trade) when `round($amount_left1 * $order1.price) == 0` (and symmetrically for `$expected_buy_amount2`) so that a nonzero amount can never be exchanged for zero compensation. Alternatively, enforce a minimum tradable remainder/price precision so rounding cannot fully erase the counter-amount, mirroring the standard DeFi fix of rejecting trades where either leg computes to zero.

### Proof of Concept
1. Owner A posts order1: `sell_asset = X`, `sell_amount = 1,000,000`, `price = 0.0000004` (deliberately tiny, or arrived at after prior partial fills leaving `amount_left1` very small).
2. Attacker (as order2 owner or as a colluding matcher) posts/matches order2 offering `buy_asset = X`, with `sell_amount`/`price` chosen so `$amount_left2 >= $amount_left1` and `$expected_buy_amount2 <= $amount_left1` (trivially satisfied since `$buy_amount1` will be 0, making `$expected_buy_amount2 = round(0 * order2.price) = 0 <= $amount_left1`).
3. Attacker submits the AA trigger with `trigger.data.order1` and `trigger.data.order2`.
4. `$buy_amount1 = round(1,000,000 * 0.0000004) = round(0.4) = 0`.
5. State update executes: `var[$sell_key1] -= 1,000,000` (owner A loses all remaining asset X credit), `var[$sell_key2] -= 0` (attacker gives up nothing), `var[$buy_key2] += 1,000,000` (attacker gains 1,000,000 of asset X in their AA balance for free), which the attacker can then withdraw via the "withdraw funds" case.
