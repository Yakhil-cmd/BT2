### Title
Cross-organization webhook forgery via `repository_owner`/`repository.full_name` mismatch in multi-tenant GitHub App config - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`Shipit.github(organization:)` config keyed by org, per `lib/shipit.rb#github`/`github_app_config`), `WebhooksController#verify_signature` selects which organization's webhook secret to verify the incoming payload against using `repository_owner`, a value read straight out of the unauthenticated, attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`). The event handlers that actually mutate state (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using a *different* field from that same body: `payload.dig('repository', 'full_name')` (see `app/models/shipit/webhooks/handlers/handler.rb#repository_name`). Nothing enforces that `repository.owner.login` is a true prefix of `repository.full_name`, so the organization whose secret authenticates the request and the organization whose repository is written to are two independently attacker-controlled fields.

### Finding Description
`WebhooksController#verify_signature` [1](#0-0)  does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` [2](#0-1)  is derived purely from the JSON payload the caller controls.

`GitHubApp#verify_webhook_signature` [3](#0-2)  returns `true` unconditionally whenever that organization's config has no `webhook_secret` set (`return true unless webhook_secret`). The example/dummy configs in this repo show `webhook_secret` is explicitly optional per-organization (`webhook_secret: # nil`) — a documented, supported configuration, not a misuse of the engine [4](#0-3) .

Meanwhile, the handler that performs the actual write — e.g. `PushHandler#process` — resolves the target `Repository`/`Stack` via `Handler#stacks`/`#repository_name`, which reads `payload.dig('repository', 'full_name')`, a completely independent field of the same JSON body [5](#0-4) [6](#0-5) .

Equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login)` == `organization whose repository/stack is mutated by the handler (repository.full_name's owner)`

Before the attacker's request: for a legitimately signed webhook, both fields come from the real GitHub payload for the real repository, so they always match.
After the attacker's crafted request: the attacker sets `repository.owner.login` to an organization configured in Shipit **without** a `webhook_secret` (so `verify_webhook_signature` trivially returns `true` with zero credentials), while setting `repository.full_name` to `"OtherOrg/some-repo"` — any other onboarded organization's real repository, whose stacks then get processed by `PushHandler` (triggering `stack.sync_github(expected_head_sha: ...)`) or other event handlers that also key exclusively off `repository.full_name` (e.g. `pull_request` handlers' `Repository.from_github_repo_name(params.repository.full_name)`), with no unauthorized credential of the target org involved at all.

This exactly matches the required binding-break pattern: "an organization that authenticated versus the repository that is written."

### Impact Explanation
This allows an unauthenticated external attacker to forge GitHub events (`push`, `pull_request`, `status`, `check_suite`, `membership`, etc. — anything in `Shipit::Webhooks.for_event`) targeting any stack belonging to *any* organization onboarded to the Shipit instance, as long as at least one other onboarded organization is configured without a `webhook_secret`. Concretely for `push`, this can force `GithubSyncJob`/`sync_github` to run against arbitrary head SHAs for another org's stack, and for `pull_request` events it can archive/unarchive review stacks or trigger provisioning behavior for repositories the attacker does not control. This crosses an authentication boundary (no organization credential of the targeted org is required) and can trigger unauthorized deploy-related state transitions on repositories/stacks that belong to a different, victim organization — satisfying the "unauthorized deploy/rollback" bar for High-severity impact.

### Likelihood Explanation
Likelihood depends on deployment: it requires a multi-organization Shipit configuration (`github_app_config` keyed by org) where at least one configured organization has `webhook_secret` unset — a state explicitly supported and shown as valid in this repo's own example configs (`webhook_secret: # nil`). No credentials, GitHub App keys, or session are needed; the attacker only needs network access to `WebhooksController#create` and knowledge of the victim's repository full name (public information). This makes exploitation straightforward once the deployment condition is met, though it does not apply to the common single-organization Shipit deployment where `github_default_organization` is `nil` (in that case there is only one `GitHubApp`, so `repository_owner` cannot select a different config).

### Recommendation
Do not use an attacker-supplied payload field (`repository.owner.login`) to select which organization's secret validates the signature independently of the field (`repository.full_name`) used to resolve the target repository/stack. At minimum:
- Require `repository.full_name` to start with the same owner used for `repository_owner`/signature selection, rejecting the request otherwise.
- Do not allow `verify_webhook_signature` to silently return `true` when no `webhook_secret` is configured for a given organization in multi-org mode; require every onboarded organization to define a webhook secret, or fail closed and refuse to process events for organizations lacking one.

### Proof of Concept
Given a Shipit instance configured with two organizations, `secretless-org` (no `webhook_secret`) and `victim-org` (has stacks and a `webhook_secret`):
```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, no secret configured for secretless-org

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "secretless-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `repository_owner` resolves to `"secretless-org"` → `Shipit.github(organization: "secretless-org")` has no `webhook_secret` → `verify_webhook_signature` returns `true` unconditionally [7](#0-6) .
- `PushHandler` then resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: params.after)` for a repository the attacker never authenticated for [8](#0-7) .

**Note on scope/uncertainty:** I was unable to fully inspect `app/models/shipit/webhooks.rb` (the event-to-handler registry) in this session, so I cannot enumerate the complete list of handlers reachable via this path beyond `PushHandler` and the `pull_request` family already cited; other registered handlers keyed the same way (`repository.full_name`) would be equally affected. This finding also depends on a specific multi-org deployment configuration (at least one org without a webhook secret); it does not apply to the default single-organization setup.

      return true unless webhook_secret
