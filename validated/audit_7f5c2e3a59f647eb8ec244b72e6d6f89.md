### Title
Unvalidated attacker-controlled `authentifiers` string parsed by `merkle.deserializeMerkleProof`/`verifyMerkleProof` can crash a validating node - (File: `merkle.js`, `definition.js`)

### Summary
`jhead`'s CVE is a wild-address-read caused by parsing an attacker-controlled binary structure (a MakerNote directory) without bounds checking on offsets/counts taken from the file itself. The closest reachable analog in ocore is the `in merkle` address-definition operator, which parses an attacker-supplied `authentifiers[path]` string with `merkle.deserializeMerkleProof()` and then walks it in `merkle.verifyMerkleProof()` without validating its structure, size, or types before use, unlike the equivalent oscript `is_valid_merkle_proof()` path which was hardened later.

### Finding Description
An address that uses an `in merkle` spending condition is verified in `validateAuthentifiers()`: [1](#0-0) 

The `serialized_proof` comes straight from `assocAuthentifiers[path]`, which is populated from the `authentifiers` field of a unit that any unit poster controls (the message author supplies arbitrary strings as "signatures"/authentifiers for each definition path). This string is passed unchecked into: [2](#0-1) 

`deserializeMerkleProof` blindly splits the attacker string on `-`, pops the last piece as `root`, shifts the first piece as `index` (kept as a raw string, never validated as numeric or bounded), and treats everything else as `siblings` with no cap on array length or element size. This is then fed into: [3](#0-2) 

`verifyMerkleProof` loops `proof.siblings.length` times, computing `index % 2` and `Math.floor(index / 2)` on a value that may not be a well-formed integer, and hashing arbitrarily large/attacker-chosen sibling strings on each iteration. Compare this to the oscript `is_valid_merkle_proof` path in `formula/evaluation.js`, which — after a network upgrade (`bPostPemCurvesFix`) — explicitly caps `siblings.length <= 50` and requires each sibling to be a non-empty string before calling `merkle.verifyMerkleProof`: [4](#0-3) 

No equivalent size/type validation exists in the `definition.js` `in merkle` authentifier path before `merkle.deserializeMerkleProof`/`verifyMerkleProof` are invoked, meaning a single crafted unit that references an address using an `in merkle` definition with an oversized or malformed `authentifiers[path]` string reaches the unguarded parsing path during ordinary unit validation (`validateAuthentifiers` is called on every unit spending from/authored by such an address). While `verifyMerkleProof` wraps its logic in a `try/catch` so a thrown exception is caught and turned into `false`, the missing bound on `proof.siblings.length` and sibling string sizes still allows an attacker to force each validating node to perform an unbounded amount of hashing work per validated unit, and the raw non-numeric `index` handling represents the same class of "parse first, validate never" bug that produced the wild-read crash in jhead's `ProcessCanonMakerNoteDir`.

### Impact Explanation
Every full node (and any node evaluating `in merkle` address definitions during ordinary DAG validation) must run `validateAuthentifiers` for units spending from addresses that use this definition type. Because the merkle-proof string is parsed and iterated with no length ceiling before hashing, a unit author can supply a single authentifier string with an extremely large number of `-`-separated components, forcing disproportionate CPU work per validated unit and creating a risk of node slowdown/DoS on the validation hot path — the same "crash/DoS from unvalidated attacker input" bug class as the CVE, though here mitigated by the `try/catch` from throwing an uncaught exception.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to accept/relay a unit spending from (or authored by) an address whose definition contains an `in merkle` clause with an oversized authentifier, which any address owner can pre-arrange for their own address and then broadcast; no special privileges beyond posting an ordinary unit are needed.

### Recommendation
Add the same guards used in `formula/evaluation.js` (`bPostPemCurvesFix`-style checks) directly inside `merkle.deserializeMerkleProof`/`verifyMerkleProof`, or in the `in merkle` branch of `definition.js`: cap `siblings.length` (e.g. ≤ 50), require each sibling to be a bounded non-empty string, and validate/parse `index` as a non-negative integer before use, rejecting the definition/authentifier as invalid otherwise.

### Proof of Concept
1. Create an address whose definition includes `['in merkle', [[oracleAddr], 'feed', 'expected_value']]`.
2. Post a unit authored by/spending from that address with `authentifiers[path]` set to a string containing tens of thousands of `-`-separated dummy segments (e.g. `"0-" + "AAAA-".repeat(100000) + "root"`).
3. Broadcast the unit; every node performing `validateAuthentifiers` on it calls `merkle.deserializeMerkleProof` then `merkle.verifyMerkleProof`, which iterates and SHA-256-hashes across the full (unbounded) sibling list for that single unit, consuming disproportionate CPU relative to a normal unit.

*(Note: I could not fully confirm from the indexed code whether `authentifiers` values undergo any prior length restriction elsewhere in `validation.js` before reaching `Definition.validateAuthentifiers`, since the index does not expose the complete `validateAuthentifiers`/message-processing call chain; a Devin session with full repo access would be needed to verify this end-to-end and confirm there is no earlier size cap on the `authentifiers` object's string values.)*

```javascript
function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}
```

```javascript
function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
```
