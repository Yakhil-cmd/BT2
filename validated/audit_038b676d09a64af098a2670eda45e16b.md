### Title
Session Fixation on GitHub OAuth Callback — Authenticated Identity Bound to Pre-Existing, Attacker-Controlled Session ID ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
The Parity multisig bug is a class of "binding never (re-)established at the trust-transition point" flaw: `initWallet` could be invoked post-deployment to bind arbitrary ownership because the contract never enforced that the privileged action only occurs once, at the intended initialization boundary. The equivalent boundary in Shipit is the OAuth login callback, where a GitHub identity is supposed to be freshly bound to a newly-issued session. `Shipit::GithubAuthenticationController#callback` writes `session[:user_id]` directly into whatever session already exists on the request, without ever calling `reset_session` (or otherwise rotating the session id) before establishing the authenticated identity.

### Finding Description
`callback` is the sole place authentication state is created: [1](#0-0) 

It reads the OmniAuth auth hash, resolves/creates a `User`, and sets `session[:user_id] = sign_in_github(auth)` plus `session[:authenticated] = true` — but it never resets or regenerates the session identifier before doing so. Contrast this with `logout`, which explicitly calls `reset_session`: [2](#0-1) 

and with `force_github_authentication`, which calls `reset_session` when forcing a re-login due to stale credentials: [3](#0-2) 

`current_user` elsewhere in the app is derived purely from `session[:user_id]`: [4](#0-3) 

The binding that should hold is: `session_id_after_login == freshly-issued session_id`, i.e., the cookie identifying the session must not be attacker-controllable across the unauthenticated → authenticated transition. Because `callback` never rotates the session id, if an attacker can set/fixate a session cookie value in a victim's browser prior to the victim completing GitHub OAuth (e.g., via a subdomain, a response-header injection elsewhere, or simply because the app previously issued the attacker a session cookie that they replay to the victim), the victim's subsequent authentication will write their `user_id` into that same, attacker-known session record. The attacker can then present the same session cookie and be recognized as the now-authenticated victim by `find_current_user`.

Note: `GithubAuthenticationController` inherits directly from `ActionController::Base` (not `ShipitController`, which sets `protect_from_forgery with: :exception`), so it also lacks the CSRF hardening applied elsewhere in the engine, though the primary defect here is the missing session-id rotation at the authentication boundary.

### Impact Explanation
This maps to the explicitly listed High-severity category: "session fixation / forced OAuth completion." A successful exploitation results in unauthorized access to a legitimate user's authenticated Shipit session — allowing the attacker to act as that user in the web UI (create API clients, trigger deploys/rollbacks, manage merge queue entries, etc.), which is an authentication/session-integrity bypass reachable by a completely unprivileged, unauthenticated attacker (no ApiClient token, webhook secret, or GitHub App key required).

### Likelihood Explanation
Exploitation requires the attacker to get a chosen/known session identifier into the victim's browser before the victim completes the OAuth flow (classic session-fixation precondition), and it depends on Rails' default `ActionDispatch::Session::CookieStore`/session id issuance behavior and whether the deployer's proxy/cookie configuration allows session fixation to begin with. I could not fully verify from the available code whether any additional Rack middleware (outside `lib/shipit/engine.rb` and `app/controllers/**`) mitigates this, since session-store configuration in a real deployment is defined by the host Rails application, not solely by the engine. This is a real gap in the engine's own controller logic, but the practical exploitability also depends on host-app configuration not covered by this repository.

### Recommendation
In `Shipit::GithubAuthenticationController#callback`, call `reset_session` (preserving `omniauth.origin`/`return_url` before doing so) immediately prior to setting `session[:user_id]` and `session[:authenticated]`, mirroring the pattern already used in `logout` and `force_github_authentication`. Additionally, consider inheriting from `ApplicationController`/`ShipitController` or explicitly adding `protect_from_forgery` to this controller for defense in depth.

### Proof of Concept
1. Attacker obtains/sets a session cookie value `S` (e.g., by visiting the Shipit instance and capturing the session cookie issued before authentication, since no rotation occurs anywhere except `reset_session` calls).
2. Attacker fixates cookie `S` into the victim's browser (e.g., via a shared subdomain, network position, or any mechanism that lets a cookie be set for the target domain).
3. Victim visits Shipit, completes GitHub OAuth; `GithubAuthenticationController#callback` fires and sets `session[:user_id] = victim.id` on the *same* server-side session record referenced by cookie `S`, per [5](#0-4) , because no `reset_session` occurs.
4. Attacker replays cookie `S` and is now recognized as the victim by `find_current_user`, per [6](#0-5) .

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
