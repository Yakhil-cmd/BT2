### Title
Cross-organization webhook forgery via decoupled signature-verification identity and processed-repository identity - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a webhook signature using `repository_owner`, which is read from the *unverified* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the signature check against that org's secret passes, the entire raw payload — including a completely independent field, `repository.full_name` — is handed unchanged to `Shipit::Webhooks::Handlers::Handler#repository_name`, which is used to look up the target `Repository`/`Stack` and mutate it (e.g. trigger a sync/deploy pipeline). The org whose secret authenticated the request and the org whose repository is actually written to are never checked for equality.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from the payload itself, then does `Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(signature, raw_post)`. [1](#0-0) [2](#0-1) 
- `Shipit.github_app_config`/`Shipit.github` support multiple GitHub App configurations, one per organization, each with its own independently configured `webhook_secret` (which is explicitly documented as *optional*). [3](#0-2) [4](#0-3) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that particular organization's `webhook_secret` is blank: `return true unless webhook_secret`. [5](#0-4) 
- After signature verification succeeds for the org derived from `repository.owner.login`, `create` re-parses the same raw body and dispatches the *whole* payload to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [6](#0-5) 
- `Handler#repository_name` reads a **different** field, `payload.dig('repository', 'full_name')`, to resolve the target `Repository`/stacks, and `PushHandler#process` acts on those stacks by calling `stack.sync_github(expected_head_sha: params.after)`, an attacker-controlled SHA. [7](#0-6) [8](#0-7) 
- `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain DB lookup with no cross-check against `repository.owner.login` or the org used to verify the signature. [9](#0-8) 

Since `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository/stack) are two independent, attacker-supplied fields inside the same unsigned JSON body prior to verification, nothing forces them to refer to the same organization. In a multi-org Shipit deployment (the `TOP_LEVEL_GH_KEYS`/per-org `github_app_config` scheme), if *any one* configured organization has no `webhook_secret` set (an explicitly supported, documented configuration), an attacker can craft a payload with `repository.owner.login` = that org (or `organization.login` fallback) so verification trivially passes (`return true unless webhook_secret`), while setting `repository.full_name` to `"<victim-org>/<victim-repo>"` for a *different*, securely configured organization's repository. The push handler will then act on the victim org's stack using attacker-chosen data (e.g. `after` SHA), even though the signature never authenticated anything belonging to that victim organization.

This is the direct analog of the reported bug class: a value used for one binding decision (which secret authorizes the request) is decoupled from the value that is actually acted upon (which repository/stack is mutated), exactly as the original report describes slippage-protection parameters not being bound to the actual execution deadline/tx.

### Impact Explanation
This breaks the equality that should hold: `organization that signed/authenticated the webhook == organization whose repository/stack is written`. An unprivileged external actor — with no Shipit session, no `ApiClient` token, no legitimate webhook secret for the victim org — can forge push (or other) webhook events targeting any stack registered under any other configured organization, as long as one organization in the multi-tenant configuration has a blank `webhook_secret`. This can trigger unauthorized syncs (`GithubSyncJob`) that fabricate commits/head SHAs for a stack, and depending on continuous-delivery configuration, cascade into an unauthorized deploy — matching the "unauthorized deploy" high/critical impact criteria.

### Likelihood Explanation
Requires a specific but realistic and documented deployment shape: multiple GitHub organizations configured on one Shipit instance (supported natively via `github_app_config`) where at least one org has no webhook secret configured (webhook secret is explicitly optional per `docs/setup.md`). Given that configuration, exploitation requires only crafting an HTTP POST to `/webhooks` with a self-consistent-looking but cross-referencing JSON body — no credentials, tokens, or GitHub write access needed.

### Recommendation
After signature verification, re-derive the acted-upon repository/organization strictly from the same field(s) that were cryptographically verified (or verify that `repository.owner.login`/`organization.login` equals the owner encoded in `repository.full_name`) before dispatching to handlers. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for one org while other orgs in the same deployment have secrets configured — either require all-or-none configuration, or reject requests whose resolved org has no secret rather than treating it as "verified."

### Proof of Concept
1. Deploy Shipit with two organizations configured: `weak-org` (no `webhook_secret`) and `victim-org` (with `webhook_secret` set), both onboarded per `github_app_config`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "weak-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `repository_owner` = `"weak-org"`, calls `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of (or absent) `X-Hub-Signature`.
4. `create` dispatches the full payload to `PushHandler`, which resolves `repository_name` = `"victim-org/victim-repo"` via `payload.dig('repository', 'full_name')`, looks up that `Repository`'s stacks, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` — mutating a stack under `victim-org` despite the request never being authenticated for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
