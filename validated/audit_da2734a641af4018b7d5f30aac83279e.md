### Title
Cross-organization webhook forgery via mismatched signature-verification scope vs. handler write scope - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App secret to validate the HMAC signature against using a value taken *from inside the same untrusted JSON payload* (`repository.owner.login` / `organization.login`), but once the signature check passes, the *entire* raw payload — including any other repository/commit-identifying fields — is handed unchanged to the event handlers, with no re-check that those other fields belong to the organization whose secret validated the signature.

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — i.e. attacker-controlled data in the very payload being verified. This value is used only to pick *which* per-organization `webhook_secret` (`Shipit.github(organization: repository_owner)`) is used for the HMAC comparison. Shipit explicitly supports multiple GitHub Apps/secrets, one per organization, as documented and configured: [3](#0-2) [4](#0-3) 

After `head(422) unless verified` is (non-halting — note the method doesn't call `return` after `head(422)`, but assume the framework halts the filter chain), `create` dispatches the full JSON body to handlers keyed only by event type: [5](#0-4) 

Handlers (e.g. the `status` handler) locate the target commit/stack using other fields of the same payload — in the exercised test, a `status` payload is looked up purely by its `sha`, independent of any org/repo scoping: [6](#0-5) 

This is the structural analog of the reported bug class: a value is validated in one scope (the signature is checked against the secret for `repository.owner.login`, i.e. "organization that authenticated") while the actual write/action is performed against a different, unchecked scope taken from the same payload (the `sha`/commit/stack actually targeted, i.e. "the repository that is written"). Because the organization identifier used for verification is attacker-supplied payload content rather than something bound to the secret/transport (e.g., a URL path segment or header set by GitHub per-installation), an attacker who legitimately administers **their own** organization/repository in a multi-tenant Shipit install (and thus legitimately possesses that organization's `webhook_secret`) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org so the HMAC check succeeds using their own secret.
2. Populate the remaining payload fields (`sha`, `state`, `target_url`, `description`, commit ranges, etc.) to reference a commit/stack belonging to a **different** organization hosted on the same Shipit instance.

Because the handler never re-validates that the targeted commit/stack/repository actually belongs to the same organization that authenticated the request, the forged event is processed as if it legitimately came from GitHub for that other organization's repository.

### Impact Explanation
The clearest concrete impact is via the `status` event: an attacker can forge a commit-status webhook (`state: "success"`) for a commit belonging to another organization's stack. Shipit's deploy safety mechanism gates deploys on required CI statuses (`ci.require`) associated with a commit; a forged, cross-tenant "green" status can satisfy that gate and allow an unauthorized deploy of a commit that never actually passed CI — an unauthorized deploy triggered outside the trust boundary of the org that owns the repository, satisfying the Critical impact bar (unauthorized deploy) defined in scope.

### Likelihood Explanation
Exploitability only requires the attacker to control one legitimate, low-privilege organization/installation on a shared multi-org Shipit deployment (a realistic, documented configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`). No privileged Shipit account, API token, or access to the victim organization's secret is required — only knowledge of the attacker's own org's `webhook_secret`, which they legitimately hold.

### Recommendation
Bind organization identity to the transport/config layer rather than payload content — e.g., use a per-organization webhook URL/path or a header set independently of the JSON body, and re-validate that every repository/commit/stack referenced deeper in the payload actually belongs to the organization that was used to select and validate the HMAC secret before any handler acts on it.

### Proof of Concept
1. Attacker is a legitimate installer of Shipit's GitHub App on `OrgA` and knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a commit belonging to OrgB's tracked stack>",
  "state": "success",
  "description": "forged",
  "target_url": "https://attacker.example/fake-ci",
  "context": "required-ci-context",
  "repository": {"owner": {"login": "OrgA"}}
}
```
3. Attacker computes `X-Hub-Signature` with `OrgA`'s webhook secret over the raw JSON body and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app/secret, and the HMAC check passes.
5. The `status` handler processes the payload and writes a passing status to `OrgB`'s commit (as shown by the field-level behavior in `test/controllers/webhooks_controller_test.rb:42-59`), potentially unblocking a deploy gated on that CI status for `OrgB`'s repository, which the attacker never legitimately controls.

*Note: I was unable to retrieve the exact contents of the `status`/`push` handler implementation files directly (tool access ran out before I could open `app/models/shipit/webhooks/handlers/status_handler.rb` or `push_handler.rb`) — the commit-lookup-by-`sha`-only behavior is inferred from the controller test's payload construction rather than direct handler source. If further verification is desired, a Devin session with full filesystem access should read those handler files to confirm the exact lookup/scoping logic.*

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
