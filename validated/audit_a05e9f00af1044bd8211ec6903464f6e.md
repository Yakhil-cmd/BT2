### Title
`handleERC20Transfer` / `handleERC721Transfer` Accept Unregistered Token Addresses, Enabling Unauthorized Mint or Bridge-Fund Drain — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

The Kaia ServiceChain bridge enforces token registration on the **outgoing** path (`_requestERC20Transfer` / `_requestERC721Transfer`) via the `onlyRegisteredToken` modifier, but applies **no equivalent check** on the **incoming** path (`handleERC20Transfer` / `handleERC721Transfer`). Any registered operator can call the handle functions with an arbitrary, unregistered `_tokenAddress`. With the default operator threshold of 1, a single operator can immediately execute the transfer, either minting unbacked tokens (in `modeMintBurn = true` mode) or draining any ERC-20 token held by the bridge (in `modeMintBurn = false` mode).

---

### Finding Description

`BridgeTokens.sol` maintains a token whitelist (`registeredTokens`, `registeredTokenList`, `indexOfTokens`) and exposes two modifiers:

```solidity
modifier onlyRegisteredToken(address _token) {
    require(registeredTokens[_token] != address(0), "not allowed token");
    _;
}
``` [1](#0-0) 

The outgoing path correctly applies this guard:

```solidity
function _requestERC20Transfer(...) internal
    onlyRegisteredToken(_tokenAddress)
    onlyUnlockedToken(_tokenAddress)
``` [2](#0-1) 

The incoming path does **not**:

```solidity
function handleERC20Transfer(...) public onlyOperators {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    ...
    if (modeMintBurn) {
        require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
    } else {
        IERC20(_tokenAddress).safeTransfer(_to, _value);
    }
}
``` [3](#0-2) 

The same asymmetry exists in `handleERC721Transfer`: [4](#0-3) 

The `_voteValueTransfer` function uses `keccak256(msg.data)` as the vote key, so different `_tokenAddress` values produce independent vote slots. The default threshold is **1**:

```solidity
constructor() internal {
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        operatorThresholds[uint8(i)] = 1;
    }
``` [5](#0-4) 

With threshold = 1, a single operator's call to `handleERC20Transfer` with a fresh nonce and an unregistered `_tokenAddress` passes `_voteValueTransfer` immediately and proceeds to the token action.

The Go-side relay (`bridge_manager.go`) does check token registration before dispatching, but this is not enforced at the contract level: [6](#0-5) 

The on-chain contract is independently callable by any operator, bypassing the Go-side guard entirely.

---

### Impact Explanation

**`modeMintBurn = true` (child-chain bridge, deployed with `local = true`):**
An operator calls `handleERC20Transfer(fakeTxHash, attacker, attacker, childTokenAddr, largeAmount, freshNonce, blockNum, "")`. The bridge holds the minter role for child-chain tokens. The call mints `largeAmount` of `childTokenAddr` to `attacker` with no corresponding lock on the parent chain. This is an **unauthorized mint of bridged assets**.

**`modeMintBurn = false` (parent-chain bridge):**
An operator calls `handleERC20Transfer(fakeTxHash, attacker, attacker, anyERC20InBridge, amount, freshNonce, blockNum, "")`. The bridge transfers `amount` of any ERC-20 it holds (including registered tokens deposited by users) to `attacker`. This is an **unauthorized transfer of bridge-managed funds**.

In both cases the `lowerHandleNonce` and `upperHandleNonce` state is permanently advanced, corrupting the replay-protection accounting for legitimate future transfers.

---

### Likelihood Explanation

The default `operatorThresholds[ValueTransfer] = 1` means a single operator can trigger the exploit unilaterally. Operators are registered by the bridge owner and are semi-trusted (not the owner themselves). A compromised, malicious, or mistaken operator key is sufficient. The contract is deployed on-chain and callable directly, independent of the Go relay's own validation.

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)` modifiers to `handleERC20Transfer` and `handleERC721Transfer`, mirroring the guards already present on the outgoing path:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD
    onlyUnlockedToken(_tokenAddress)     // ADD
{
```

Apply the same fix to `handleERC721Transfer`.

### Proof of Concept

**Setup:** Child-chain bridge deployed with `modeMintBurn = true`, threshold = 1 (default), operator = `op1`, child token = `childToken` (bridge has minter role).

1. `op1` calls:
   ```solidity
   bridge.handleERC20Transfer(
       bytes32(0),          // fake requestTxHash
       op1,                 // _from
       op1,                 // _to  (attacker)
       childToken,          // _tokenAddress — NOT in registeredTokens
       1_000_000e18,        // _value
       999,                 // _requestedNonce (fresh, > lowerHandleNonce)
       block.number,
       ""
   );
   ```

2. `_lowerHandleNonceCheck(999)` passes (999 ≥ lowerHandleNonce).

3. `_voteValueTransfer(999)` returns `true` immediately (threshold = 1, fresh vote key).

4. `ERC20Mintable(childToken).mint(op1, 1_000_000e18)` executes — 1 million tokens minted to `op1` with no parent-chain lock.

5. `lowerHandleNonce` advances past nonce 999, permanently consuming that replay-protection slot. [3](#0-2) [1](#0-0) [5](#0-4) [7](#0-6)
