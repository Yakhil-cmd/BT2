## Analysis

I confirmed the mismatch: `WebhooksController#verify_signature` selects the GitHub App/webhook secret to check the HMAC against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` from the *unverified* JSON body [1](#0-0) [2](#0-1) . Separately, every webhook `Handler` (e.g. `PushHandler`) resolves which `Repository`/`Stack` to act on using `payload.dig('repository', 'full_name')` [3](#0-2) , and `Repository.from_github_repo_name` simply splits that string on `/` to get owner/name and looks up the DB record [4](#0-3) .

These are two independent fields inside the same JSON body: `repository.owner.login` (used only to pick the HMAC secret) and `repository.full_name` (used only to pick the target `Repository`/`Stack`). Nothing ties them together. In a multi-organization Shipit deployment (`Shipit.github(organization:)` supports per-org secrets, documented in `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), a sender who legitimately knows Org A's `webhook_secret` (e.g., an admin/developer of Org A's GitHub App settings) can sign a payload with Org A's secret while setting `repository.owner.login = "OrgA"` (so `verify_signature` picks and validates against Org A's secret) but `repository.full_name = "OrgB/some-repo"` (so the handler acts on Org B's stack). The signature passes because it is checked against the correct raw body and correct secret for "OrgA", but the actual write target is a repository belonging to an entirely different, unrelated GitHub organization also hosted on the same Shipit instance.

This is the precise analog required by the rules: *"an organization that authenticated versus the repository that is written."* I was not able to fully trace every downstream consumer of `repository_name`/`full_name` across all handlers (e.g. `pull_request` handlers, `membership_params`) in the time available, but `PushHandler`, `StatusHandler`-style flows, and `PullRequest` handlers all follow the same `Handler#repository_name` / `Repository.from_github_repo_name` pattern, so the cross-tenant write is not limited to `push` events.

### Title
Cross-organization webhook forgery via decoupled `repository.owner.login` (signature-selection) and `repository.full_name` (action target) fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate the HMAC signature against using `repository.owner.login` from the unauthenticated JSON body, while the actual webhook `Handler` classes resolve the `Repository`/`Stack` to act on using the separate `repository.full_name` field from the same body. Because the signature only proves "this body was signed by the secret belonging to the organization named in `repository.owner.login`," and the acted-upon repository comes from a different, uncorrelated field, a sender who knows one organization's webhook secret can forge webhook events that mutate stacks belonging to a completely different organization hosted on the same Shipit instance.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON body and uses it to fetch the corresponding `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`, then verifies the raw POST body's HMAC against that secret: [5](#0-4) 

`repository_owner` is read directly from the untrusted payload: [2](#0-1) 

Once verification succeeds, `create` dispatches the same JSON body to registered handlers: [6](#0-5) 

Every `Handler` resolves the target `Stack`/`Repository` using a *different* field, `repository.full_name`, not `repository.owner.login`: [3](#0-2) 

`Repository.from_github_repo_name` naively splits `full_name` on `/` to look up the DB record, with no cross-check against `repository.owner.login`: [4](#0-3) 

`PushHandler` then triggers a real state-mutating action (`stack.sync_github`) against whatever stack `full_name` resolves to: [7](#0-6) 

Shipit explicitly supports hosting multiple, independently-secreted GitHub organizations from one instance, each with its own `webhook_secret`: [8](#0-7) [9](#0-8) 

Binding broken (as an equality): the engine implicitly assumes `verified_organization(repository.owner.login) == organization_that_owns(repository.full_name)`, but nothing enforces this. An attacker who is a legitimate, low-privilege participant in Org A (knows Org A's `webhook_secret`, e.g., as a developer with access to Org A's GitHub App settings) can sign a body with `repository.owner.login = "OrgA"` (satisfying `verify_signature`) and `repository.full_name = "OrgB/some-repo"` (satisfying the handler's stack lookup), causing Shipit to treat the forged payload as authentic for a repository it never actually authenticated for.

### Impact Explanation
This crosses the "Critical: cross-repository writes" bar defined in scope. A signature that is valid only for Org A's secret is used to authorize a write (e.g. triggering `GithubSyncJob`, closing/archiving review stacks, updating PR/check state, creating team `membership`) against Org B's stack/repository, which the attacker never had credentials for. This is a cross-organization/cross-repository write achieved purely by manipulating two decoupled fields inside one HTTP body relative to the app's own signature-selection logic — it does not require any Shipit session, `ApiClient` token, or GitHub App private key belonging to the target org.

### Likelihood Explanation
Medium-to-High for multi-organization Shipit deployments (explicitly documented and supported): any actor with access to one onboarded organization's GitHub App `webhook_secret` (which may be shared more broadly than admin-only, e.g. multiple engineers configuring the GitHub App) can construct the forged request directly with `curl`, no GitHub UI interaction or webhook delivery replay needed. For single-organization deployments (`github_default_organization` returns `nil` and a single top-level secret is used) this specific cross-org vector does not apply, since there is only one secret/organization; it is specific to the documented multi-tenant configuration.

### Recommendation
Bind the field used for signature-secret selection to the field used for the actual DB lookup: e.g., resolve the target `Repository` first (or derive both from the exact same sub-object/path), and reject the webhook if `repository.owner.login` does not case-insensitively match the `owner` segment of `repository.full_name` (or the organization payload for org-scoped events). Alternatively, verify the signature using the Repository's persisted owner and its configured `GitHubApp`, rather than trusting a payload-supplied owner field independent from the field the handler will use to select the mutated record.

### Proof of Concept
Given a Shipit instance configured with two organizations (per `docs/setup.md`'s "Using Multiple Github Applications"): `OrgA` (secret known to attacker) and `OrgB` (hosts stack `OrgB/victim-repo`, unrelated to attacker):

```
body = {
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },       # used only by verify_signature to select secret
    "full_name": "OrgB/victim-repo"     # used only by PushHandler to select the Stack
  }
}.to_json

signature = "sha1=" + HMAC_SHA1(OrgA_webhook_secret, body)

POST /webhooks
X-Github-Event: push
X-Hub-Signature: <signature>
Body: body
```

`verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates the HMAC successfully (attacker knows this secret) [1](#0-0) . `PushHandler#process` then looks up `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on Org B's real stack [7](#0-6) , despite the request never being signed by anything belonging to Org B.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
