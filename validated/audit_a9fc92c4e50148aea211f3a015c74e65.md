### Title
Unscoped `Commit.where(sha:)` write in `StatusHandler#process` lets an attacker's authenticated webhook flip a `ci/coverage` status on any other stack's commit sharing that SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` updates status for every `Commit` row matching the raw `sha` from the payload, with no repository/stack scoping, unlike the `stacks` helper provided by the base `Handler` class for exactly this purpose. Because `Commit.sha` is only unique per `(sha, stack_id)` and not globally, a webhook that is cryptographically authenticated only for the attacker's own repository/org can still write a `ci/coverage` success status onto a commit belonging to an unrelated victim stack that happens to share the same SHA, and that write can trigger `stack.schedule_merges` and ultimately `merge!` on a `merge_queue_enabled` stack.

### Finding Description
The broken binding: the code assumes `authenticated_repository(payload) == repository_whose_commit_gets_written`, but the actual code enforces no such equality for statuses.

- `Shipit::WebhooksController#verify_signature` only checks that the webhook is validly signed for `repository_owner` (the org/owner derived from `params.dig('repository','owner','login')`), i.e. it authenticates the *sender's* repo/org, not the specific commit's owning stack: [1](#0-0) 
- The `Handler` base class exposes a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, which is the mechanism intended to enforce "a status affects only the repository that authenticated it": [2](#0-1) 
- `StatusHandler#process` does not use `stacks` at all. It queries `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every match: [3](#0-2) 
- `Commit.sha` has a unique index only on `(sha, stack_id)`, not on `sha` alone, meaning identical SHAs legitimately exist across different stacks (e.g., shared/forked/mirrored commits): [4](#0-3) 
- `Commit#create_status_from_github!` writes the status and `add_status` triggers merge scheduling on `success`: `stack.schedule_merges if new_status.pending? || new_status.success?`: [5](#0-4) [6](#0-5) 

Exploit flow: An attacker owns (or controls webhooks for) some repository/org where the GitHub App is installed, satisfying `verify_signature` for that org. The attacker sends `POST /webhooks` with header `X-Github-Event: status` and a JSON body whose `repository.full_name`/`repository.owner.login` matches the attacker's own authenticated repo, but whose `sha` field equals a SHA that also exists as a `Commit` row on a victim's `merge_queue_enabled` stack (e.g., a shared upstream commit, a commit cherry-picked or common to a fork tracked by both stacks). Because `StatusHandler#process` ignores `payload['repository']` for the actual write and matches purely on bare `sha`, the victim's `Commit` gets a new `ci/coverage: success` status, `add_status` fires `stack.schedule_merges`, and the merge queue in the victim stack advances/`merge!`s based on attacker-forged CI data. This bypasses the intended invariant because the only authentication check (`verify_signature`) validates the sender's org, not which stack's data is mutated - a check that `stacks` scoping (already implemented in `Handler`, but unused here) would have enforced.

### Impact Explanation
An attacker-authenticated webhook for their own repository can cause a required status (`ci/coverage`) to flip to `success` on a commit belonging to a different, victim-owned stack, without ever authenticating for that stack's repository. On a `merge_queue_enabled` stack this can advance the merge queue and trigger `merge!`, i.e., an unauthorized merge/ship decision driven by forged CI data for a repository that never actually reported it. This matches the Critical impact category: "a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge." The attack is repeatable against any stack/commit pair sharing a SHA, though it is gated on the precondition of a shared SHA existing between the attacker's authenticated repo and the victim stack.

### Likelihood Explanation
Preconditions: (1) the GitHub App/webhook signing must be configured for a repo/org the attacker controls (readily achievable - anyone can register a repo/org with the app if the Shipit instance is open to it, or the attacker already owns such a repo tracked by Shipit); (2) a `Commit` row with an identical SHA must exist in a victim's `merge_queue_enabled` stack. This second condition is the limiting factor - it requires SHA collision at the content level, which realistically happens via shared history (forks, mirrors, vendored/cherry-picked commits, monorepo splits) rather than arbitrary attacker choice of SHA. Given that precondition, the exploit is cheap (single unauthenticated-content HTTP POST) and fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and any other handler bypassing the `stacks` helper) to only update commits belonging to stacks of the repository that authenticated the webhook, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces the invariant that a status only affects the repository/stack that authenticated it, consistent with how `Handler#stacks` is designed to be used.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `repository_a` (attacker's, e.g. `owner/attacker-repo`) with `stack_a` (`merge_queue_enabled: false`) and `repository_b` (victim's, e.g. `owner/victim-repo`) with `stack_b` (`merge_queue_enabled: true`, requiring `ci/coverage`).
2. Create `commit_a` on `stack_a` and `commit_b` on `stack_b` with the identical `sha: "deadbeef..."` (simulating a shared/forked commit).
3. Assert before state: `commit_b.deployable?` is `false` (missing required `ci/coverage`), and `stack_b`'s merge queue has not advanced (`stack_b.merge_queue` unchanged / no `merge!` invoked) — i.e. `authenticated_repository == "owner/attacker-repo"` while `commit_b.stack.repository.full_name == "owner/victim-repo"`, so they are not equal.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => commit_a.sha, 'state' => 'success', 'context' => 'ci/coverage', 'repository' => { 'full_name' => 'owner/attacker-repo', 'owner' => { 'login' => 'owner' } })` directly (bypassing signature verification, which is orthogonal to this bug since it validates org-level authenticity only).
5. Assert after state: `commit_b.reload.statuses.last.context == 'ci/coverage'` and `commit_b.deployable?` is now `true`, and `stack_b.schedule_merges`/merge queue advancement was triggered — demonstrating that a webhook authenticated only for `owner/attacker-repo` mutated `stack_b`'s (`owner/victim-repo`) commit and deployability/merge state, violating the claimed invariant.
