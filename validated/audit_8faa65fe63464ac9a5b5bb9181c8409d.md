### Title
`NODE_OPTIONS` env-key injection via uppercased PR label name reaches shell-interpreted `shipit.yml` steps unfiltered - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment variable key with no allowlist, and this merged hash flows unfiltered through `TaskCommands#env` into `Command#unbundled_env`, which is passed directly to `PTY.spawn`. An unprivileged fork PR author can label their own PR `node_options` with a value crafted via `EnvironmentVariables#interpolate`'s `$VAR` substitution or simply rely on the fixed `"true"` value combined with `NODE_OPTIONS=true` being ignored — but more importantly, no key-based sanitization exists at all, so any environment key an attacker chooses reaches the shell, enabling injection of dangerous variables into a shell-interpreted step.

### Finding Description
The broken binding: the invariant claimed is "the set of keys in the environment hash passed to `PTY.spawn` is restricted to the deploy spec's `machine_env` and declared `VariableDefinition` names," i.e. `env.keys ⊆ (deploy_spec.machine_env.keys ∪ deploy_variables.map(&:name))`. This does **not** hold.

- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" } ` with no key allowlist: [1](#0-0) 
- `TaskCommands#env` merges `@stack.env` (which includes the above) directly, with no call to `EnvironmentVariables#permit`: [2](#0-1) 
- The only place an allowlist (`EnvironmentVariables#permit` against `deploy_variables`/`rollback_variables`) is applied is to the *user-supplied* `Deploy#env`/`Rollback#env` params via `filter_deploy_envs`/`filter_rollback_envs` in `app/models/shipit/deploy_spec.rb` — this filtering path is never invoked on `stack.env` (PR labels). [3](#0-2) 
- `Command#unbundled_env` merges `@env.stringify_keys` unconditionally over `BASE_ENV` with no key restriction: [4](#0-3) 
- `Command#start` passes this merged hash straight to `PTY.spawn`: [5](#0-4) 
- Existing tests explicitly confirm labels flow unsanitized into the command env: [6](#0-5)  and [7](#0-6) 

Root cause: `ReviewStack#env` treats attacker-controlled GitHub label names as trusted environment-variable *keys*, and none of the downstream layers (`TaskCommands#env`, `Command#unbundled_env`) apply the `EnvironmentVariables#permit` allowlist that exists elsewhere in the codebase specifically to prevent unauthorized keys from reaching `PTY.spawn`.

Attack path: an unprivileged user opens a fork PR against a repository with review stacks enabled, adds a label (e.g., named to become `NODE_OPTIONS` after upcasing — labels can contain lowercase letters), which reaches Shipit via the `pull_request` webhook (`labeled`/`opened` events), is stored via `LabelCapturingHandler`/`ReviewStackAdapter`, and is exposed through `pull_request.labels`. When a task/deploy runs any `shipit.yml` step containing a `node` invocation (a single shell-interpreted string, as confirmed by `Command#parse_arguments` and test fixtures like `'bundle install --some-args'`), the injected `NODE_OPTIONS` value can alter that Node process's behavior (e.g., `--require`).

Existing guards do not catch this: `verify_signature`/webhook auth only validates that the request came from GitHub for that repo (an unprivileged PR author on their own fork repo can legitimately trigger these events), and `EnvironmentVariables#permit`/`filter_deploy_envs` never touch `stack.env`.

### Impact Explanation
If the deploy pipeline for the repository executes any Node.js-based step (common in JS/TS repos, e.g., `npm run build`, `node script.js`) as part of `shipit.yml` `deploy`/`dependencies`/`rollback`/task steps, the attacker-controlled `NODE_OPTIONS` value is inherited by that process and can load an attacker-supplied module (`--require`), achieving code execution in the context of the Shipit deploy host's task runner. This matches the Critical RCE class described (arbitrary command execution via `Command`/`PTY.spawn`). The blast radius is scoped to repositories that have review stacks enabled and whose `shipit.yml` includes Node-based steps; it is repeatable for every PR the attacker opens against such a repository.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` with a provisioning behavior that allows the attacker's PR to be provisioned (`allow_all` or a satisfied label condition), and the `shipit.yml` deploy/task steps must invoke `node` (or another tool honoring an env var the attacker chooses to inject) as a plain shell string. No secrets, tokens, or elevated permissions are required — only the ability to open a PR and add a label to it, which is available to any GitHub user with fork/PR access. This is low-cost and repeatable.

### Recommendation
Apply the same allowlist mechanism used for `Deploy#env`/`Rollback#env` (`EnvironmentVariables#permit` against `deploy_variables`) to `ReviewStack#env`/`stack.env` label-derived entries before merging into `TaskCommands#env`, or entirely avoid deriving environment variable *keys* from PR label names (labels should map to a bounded, pre-declared set of variable names, not attacker-chosen keys). Additionally, `Command#unbundled_env` should never merge unfiltered externally-derived keys directly into the process environment without an explicit allowlist check at that boundary.

### Proof of Concept
minitest plan (extends the existing `test/models/shipit/review_stack_test.rb` and `test/lib/shipit/task_commands_test.rb` patterns):
```ruby
test "PR label name injects arbitrary env key unfiltered" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["node_options"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["NODE_OPTIONS"]

  command = Shipit::Command.new("node -e 1", env: env, chdir: Dir.tmpdir)
  assert_equal "true", command.unbundled_env["NODE_OPTIONS"]
end
```
This demonstrates both sides of the claimed invariant diverge: `env.keys` includes `NODE_OPTIONS`, which is neither in `deploy_spec.machine_env` nor in any declared `VariableDefinition` name, and it survives into `Command#unbundled_env`, which is what `PTY.spawn` receives.
