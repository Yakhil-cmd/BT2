### Title
Webhook signature verification is bound to `repository.owner.login`, but event processing acts on the independent `repository.full_name` field, allowing cross-organization forgery of commit statuses/pushes in multi-tenant Shipit deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used to check `X-Hub-Signature`) based on `params.dig('repository', 'owner', 'login')`. All webhook handlers (`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`) instead resolve the `Repository`/`Stack` to act on using the independent JSON field `payload.dig('repository', 'full_name')`. In a multi-tenant Shipit instance (multiple GitHub organizations each configured with their own `webhook_secret`, as documented in `docs/setup.md` "Using Multiple Github Applications" and exercised by `test/dummy/config/secrets_double_github_app.yml`), these two fields are never checked for consistency. An attacker who legitimately administers a GitHub App for their own organization (and therefore knows that organization's own `webhook_secret` — an unprivileged, self-service configuration step) can forge an arbitrarily-crafted webhook body whose `repository.owner.login` names their own org (so signature verification passes) while `repository.full_name` names a completely different, victim organization's repository that has a Stack configured in the same shared Shipit instance.

### Finding Description
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does:
  ```ruby
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ```
  where
  ```ruby
  def repository_owner
    params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
  end
  ``` [1](#0-0) 

- Every handler resolves what to act on via a *different* field of the same payload:
  ```ruby
  def stacks
    @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
  end

  def repository_name
    payload.dig('repository', 'full_name')
  end
  ``` [2](#0-1) 

- `Repository.from_github_repo_name` simply splits `owner/name` and looks up any matching `Repository` row, with no cross-check against the organization whose secret authenticated the request:
  ```ruby
  def self.from_github_repo_name(github_repo_name)
    repo_owner, repo_name = github_repo_name.downcase.split('/')
    find_by(owner: repo_owner, name: repo_name)
  end
  ``` [3](#0-2) 

- Shipit natively supports hosting multiple GitHub organizations in one instance, each with its own independent `webhook_secret`:
  ```ruby
  def github(organization: github_default_organization)
    ...
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
    ...
  end
  ``` [4](#0-3) 
  documented at "Using Multiple Github Applications" in `docs/setup.md:182-209` and exercised by `test/dummy/config/secrets_double_github_app.yml` (OrgOne / OrgTwo, each with distinct `webhook_secret`) [5](#0-4) .

Because `repository_owner` (used to pick the verifying secret) and `repository_name`/`repository.full_name` (used to pick the acted-upon `Repository`/`Stack`) are two unrelated JSON keys inside a body the attacker fully controls (an HMAC over raw bytes only proves *some* org's secret was used — it says nothing about which repository fields the signed body claims), any organization onboarded onto a shared Shipit instance can forge events attributed to any *other* onboarded organization's repository/stack.

The equality that should hold and is broken:
`organization authenticated by X-Hub-Signature == owner of the repository whose Stack is mutated`
is replaced by two independently attacker-supplied strings within the same signed blob that are never compared to each other.

Concretely, the `Status` webhook path is the most damaging: `Commit#create_status_from_github!` creates a `Status` record via `statuses.replicate_from_github!(stack_id, github_status)` using attacker-controlled `state`/`description`/`target_url`/`context`/`created_at` for a `sha`/stack resolved purely from the forged `repository.full_name`. `Status` creation runs `after_commit :schedule_continuous_delivery` [6](#0-5)  and `enable_ci_on_stack` [7](#0-6) , so a forged "success" status on a victim organization's commit can trigger the victim stack's continuous-delivery/merge-queue machinery for a commit the attacker never had permission to touch.

### Impact Explanation
This lets an unprivileged actor (who only administers their own onboarded org's GitHub App, a self-service action requiring no access to the victim org, no Shipit session, and no `webhook_secret` belonging to anyone else) inject forged GitHub events — pushes, `status`, `check_suite`, `pull_request` label/open/close events — against any *other* organization's repositories that happen to be configured as Stacks in the same shared Shipit instance. The most severe consequence is forging a passing CI `Status`/`CheckRun` for an arbitrary commit sha of a victim stack, which can trigger `schedule_continuous_delivery` and satisfy CI gating relied upon by continuous deployment/merge-queue logic — i.e., an unauthorized deploy/merge path. This matches the Critical/High bar in the rules ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only that (a) the Shipit instance is configured for multiple GitHub organizations (a documented, supported and encouraged configuration for multi-tenant SaaS-style Shipit deployments), and (b) the attacker controls/administers a GitHub App installation for one of those organizations (their own — a normal, unprivileged setup they perform themselves, not requiring compromise of the victim or of Shipit). No GitHub write access to the victim repo, no Shipit account, and no knowledge of the victim's `webhook_secret` are needed — only the attacker's own webhook secret and knowledge that the victim repository is also hosted on the same shared instance (discoverable, e.g., via the public `/repositories` UI, which lists owner/name pairs). This is a straightforward, deterministic exploitation path rather than a race condition requiring precise timing.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the `GitHubApp` and verifying the signature, cross-check that the organization used for verification (`repository_owner`) matches the owner embedded in `repository.full_name` (and any other org identifiers used by downstream handlers, e.g. `organization.login`) before allowing `Handler#stacks`/`Handler#repository_name` to resolve a `Repository`. Reject (422) any payload where these fields disagree. More robustly, have handlers receive the verified organization from the controller and require that `Repository.from_github_repo_name` results belong to that verified organization.

### Proof of Concept
Assume a shared Shipit instance configured with two organizations, `OrgOne` (attacker-administered) and `OrgTwo` (victim), each with a distinct `webhook_secret`, per `docs/setup.md`'s "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`. `OrgTwo/victim-repo` is a Stack in this instance; the attacker has no access to it.

1. Attacker knows `OrgOne`'s own `webhook_secret` (they configured it themselves).
2. Attacker crafts a raw JSON body for a `status` event:
   ```json
   {
     "sha": "<victim commit sha the attacker wants marked green>",
     "state": "success",
     "description": "forced-green",
     "target_url": "https://attacker.example.com",
     "context": "ci/attacker",
     "created_at": "2026-09-01T00:00:00Z",
     "repository": {
       "full_name": "OrgTwo/victim-repo",
       "owner": { "login": "OrgOne" }
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, raw_body)>` and sends:
   ```
   POST /webhooks
   X-Github-Event: status
   X-Hub-Signature: sha1=<computed above>
   Content-Type: application/json
   <raw_body>
   ```
4. `verify_signature` computes `repository_owner = "OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the signature verifies successfully (attacker's own secret matches attacker's own signed body). The request is not blocked. [8](#0-7) 
5. The status handler resolves the target repository/stack via `payload.dig('repository', 'full_name')` = `"OrgTwo/victim-repo"`, finds the real `OrgTwo` Stack, and creates a `Status` for the given `sha` with `state: "success"`, triggering `schedule_continuous_delivery`. [9](#0-8) [6](#0-5) 

This demonstrates that authenticating against `OrgOne` grants the ability to write CI status/state for `OrgTwo`'s repository, breaking the intended "authenticated organization == written repository" binding.

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
