### Title
API `X-Shipit-User` header lets any ApiClient token impersonate an arbitrary Shipit user for deploys, rollbacks, aborts, locks and merges - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::Api::BaseController#current_user` derives the acting user's identity purely from a client-supplied `X-Shipit-User` HTTP header, looked up by login string with no cryptographic or session binding to that identity. This value is then trusted as the authenticated actor for high-impact actions: triggering deploys, rollbacks, task aborts, locks and merge requests.

### Finding Description
The web UI's session-based `current_user` is only set after a verified GitHub OAuth handshake (`sign_in_github` sets `session[:user_id]` from `auth.extra.raw_info`) and is subsequently required to pass team-membership authorization (`current_user.authorized?`): [1](#0-0) [2](#0-1) 

However, the API layer's `current_user`, used by the same `Stack`/`Task`/`Deploy` write paths, is computed entirely differently: [3](#0-2) 

This method takes the raw `X-Shipit-User` request header, looks up any existing `User` row by case-insensitive login match, and returns it — with **no proof that the request actually originates from that GitHub-authenticated individual**. The only real authentication performed on this path is `authenticate_api_client`, which validates an `ApiClient` bearer token (`ApiClient.authenticate`) and then checks coarse-grained permission scopes (`read:stack`, `write:stack`, `deploy:stack`, `lock:stack`, etc.) via `require_permission`: [4](#0-3) [5](#0-4) 

This breaks the binding: `GitHub identity (verified via OAuth) == User bound to the acting session`. The API path substitutes an unauthenticated, attacker-chosen login string for that binding. Any holder of a valid `ApiClient` token that was granted only `deploy:stack` (or `lock:stack`) — a scope that says nothing about *who* may act — can set `X-Shipit-User: <any-existing-login>` and have every downstream write action recorded and executed "as" that user:

- `DeploysController#create` → `stack.trigger_deploy(commit, current_user, ...)` [6](#0-5) 
- `TasksController#trigger` / `#abort` → `stack.trigger_task(..., current_user, ...)`, `task.abort!(aborted_by: current_user)` [7](#0-6) 
- `RollbacksController#create` → `deploy.trigger_rollback(current_user, ...)`, `active_task.abort!(aborted_by: current_user, ...)` [8](#0-7) 
- `LocksController#create`/`#update` → `stack.lock(params.reason, current_user)` [9](#0-8) 
- `MergeRequestsController#update` → `MergeRequest.request_merge!(stack, params[:id], current_user)` [10](#0-9) 

Downstream, the impersonated user's identity flows into the executed deploy environment (`SHIPIT_USER`, `EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL` used as git committer for merges/commits) via `TaskCommands#env`: [11](#0-10) 

### Impact Explanation
This qualifies as an unauthorized deploy, rollback or merge (Critical, per the accepted impact list). An `ApiClient` scoped only to `deploy:stack`/`lock:stack` — which by design is not equivalent to a specific human's GitHub-team authorization — can forge the acting identity for any registered `User`, including privileged/team-authorized users. Effects include:
- Deploys/rollbacks are attributed to and effectively performed "as" a spoofed identity, defeating audit trails (`aborted_by`, `SHIPIT_USER`, git committer identity).
- Any identity-gated business logic (e.g., checklist self-confirmation, locking under another person's name, merge-request approval attributed to someone who never made the request) can be bypassed by supplying that person's login in the header.
- Because `ApiClient` tokens are commonly handed to CI/automation systems with narrow scopes, this converts a narrowly-scoped automation credential into the ability to impersonate any interactive Shipit user for write operations.

### Likelihood Explanation
Any party in possession of a valid `ApiClient` token with `deploy:stack` or `lock:stack` permission (a normal, non-privileged automation credential, not an admin/session credential) can exploit this in a single request by adding the `X-Shipit-User` header — no additional secrets, GitHub access, or session are required beyond the token itself, which the rules treat as the baseline unprivileged-attacker capability for this analysis.

### Recommendation
Do not trust a client-supplied header for user identity. Bind the "acting user" for API-triggered writes to the `ApiClient`'s own `creator`, or require a signed/verified assertion of identity (e.g., a per-user API token whose ownership is cryptographically verified, similar to `ApiClient.authenticate`), and re-validate that the resolved user still passes `authorized?`/team-membership checks before attributing privileged actions to them.

### Proof of Concept
1. Obtain any `ApiClient` token scoped only to `deploy:stack` (e.g., an existing CI token, or self-issued if `write:hook`/`api_clients` UI access is available to a low-privilege user; at minimum any token that already exists for automation qualifies as the "unprivileged attacker" baseline).
2. Send:
```
POST /api/stacks/:id/deploys
Authorization: Basic <base64(token)>
X-Shipit-User: some-admin-login
Content-Type: application/json

{ "sha": "<deployable sha>" }
```
3. `authenticate_api_client` accepts the token; `identify_user` returns the `User` row for `some-admin-login` purely from the header value; `DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)`, producing a `Deploy` record whose `user_id`, environment (`SHIPIT_USER`, `EMAIL`, `GIT_COMMITTER_NAME/EMAIL`) and audit trail all reflect `some-admin-login`, despite that request never having been authenticated as, or approved by, that person.       def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
