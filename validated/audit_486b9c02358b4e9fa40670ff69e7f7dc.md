### Title
DoS of AA-controlled capped-asset issuance if the asset is issued outside the AA first - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `issueAsset()` helper, used when an AA executes an `[issue]` statement for an asset it defines, assumes it is the only entity that will ever issue a capped asset. For capped assets it checks only "has *anyone* issued this asset yet" instead of "has the AA already issued it", and hardcodes `serial_number = 1`. If the asset's `issued_by_definer_only` flag is `false` (a legal, definer-controlled asset property), any unprivileged unit author can post an `issue` input for that same capped asset with `serial_number=1` before the AA's own trigger executes, permanently blocking the AA from ever issuing its capped token.

### Finding Description
When an AA runs an `[issue]` action, `issueAsset()` is invoked with `objAsset = assetInfos[asset]`: [1](#0-0) 

For a capped asset the function does not filter by issuer address:
```
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
``` [2](#0-1) 

The comment "only our AA can issue" is an assumption, not an enforced invariant: it is only guaranteed when the asset was defined with `issued_by_definer_only = true` and the AA is the definer. Whether that flag is set is controlled by whoever authored the `asset` definition message (which can be the AA's own bound definition, but the asset properties themselves, including `issued_by_definer_only`, are simply message-payload fields validated in `validation.js`), and nothing in `aa_composer.js` re-checks it before relying on the "no one else can issue" assumption for the DB query.

The unit-level validation only guarantees that a capped asset's `serial_number` must be `1` and that the uniqueness constraint on issue inputs is `(asset, denomination, serial_number, address, is_unique)` — i.e., it is scoped per issuing **address**: [3](#0-2) [4](#0-3) 

So protocol-level uniqueness would in principle allow two different addresses to each post a `serial_number=1` issue for the same capped asset (they don't collide on the composite key that includes `address`). But `aa_composer.js`'s check ignores the issuer address entirely for capped assets — it treats *any* prior `issue` input for that `asset`, from *any* address, as proof that "it's already issued," and permanently returns `'already issued'` from then on.

This is functionally the same bug class as the reported `MeritDutchAuction.mint()` issue: the contract/AA hardcodes a rigid identifier (`serial_number = 1` here, minted-NFT id there) and assumes it is the sole entity able to produce it, so if that identifier is ever produced by any other actor first, the intended issuer is permanently locked out.

### Impact Explanation
Any AA that defines a capped asset with `issued_by_definer_only=false` (an entirely legal asset configuration exposed to AA authors via `[asset]`/`[definition]` templates) and expects to issue that capped supply itself via an `[issue]` action can be permanently denied that issuance by an unprivileged third party who races an `issue` unit for the same asset before the AA's trigger fires. Once `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` returns a row, the AA's `issueAsset()` will return `'already issued'` forever, bouncing every future trigger that depends on this issuance. This freezes AA functionality that depends on the token supply being minted (e.g., a bonding-curve/ICO-style AA that must issue its own share/token asset on first use), and any bytes/base-asset sent to trigger that issuance are consumed by response/bounce fees, causing AA fund loss and functional freezing.

### Likelihood Explanation
Exploitation requires only posting a single, ordinary `issue` payment unit for the target asset with `serial_number=1` and an amount not exceeding `constants.MAX_CAP` — something any unprivileged unit poster can do, with no special permission needed, as long as the asset was defined with `issued_by_definer_only=false`. AA authors who use the `[asset]` template without explicitly restricting `issued_by_definer_only=true` for a capped asset they intend to self-issue are directly exposed. This is a realistic AA-authoring mistake (the AA developer may reasonably assume, per the code comment, that "only our AA can issue" a capped asset it "owns").

### Recommendation
In `aa_composer.js`'s `issueAsset()`, do not rely solely on "any issue exists" for capped assets. Either:
- Restrict the capped-asset issuance check to `type='issue' AND asset=? AND address=?` (scoped to the AA's own address), matching the uncapped branch's pattern, and separately validate at asset-definition time (or reject at AA-deployment time) any capped asset intended for AA self-issuance that has `issued_by_definer_only=false`; or
- Enforce that AAs may only issue capped assets that are defined with `issued_by_definer_only=true` and where the AA itself is the definer, rejecting `[issue]` attempts otherwise instead of silently depending on an unenforced assumption.

### Proof of Concept
1. An AA author writes `[asset]` bound with `cap: N`, `issued_by_definer_only: false` (or a template that omits it, defaulting it in a way that permits any issuer), intending to have the AA itself later run `[issue]` to mint the capped supply into circulation.
2. After the asset unit is stable but before the AA's issuing trigger is sent, an unprivileged attacker posts a normal payment unit with an `issue` input: `{type:"issue", amount:<=cap-or-N, serial_number:1}`, authored by the attacker's own address. This passes validation because `issued_by_definer_only=false` places no restriction on which address may issue, and `serial_number=1` satisfies the capped-asset rule. [5](#0-4) 
3. Once this attacker unit is included, any subsequent AA trigger that reaches `issueAsset()` for this asset executes `SELECT 1 FROM inputs WHERE type='issue' AND asset=?`, finds the attacker's row, and returns `'already issued'` unconditionally and permanently. [2](#0-1) 
4. The AA can never issue its own capped asset again; every trigger depending on this issuance bounces indefinitely, freezing the AA's intended token-issuance functionality and burning trigger fees sent to it.
