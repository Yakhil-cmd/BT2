### Title
Webhook signature verification is scoped to the payload's `repository.owner.login`, but every event handler resolves the target Stack from the independently-controlled `repository.full_name` field, allowing cross-organization writes in multi-app Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-GitHub-App Shipit deployment (`docs/setup.md:181-216`), `Shipit.github(organization: ...)` selects a distinct `webhook_secret` per onboarded organization. `WebhooksController#verify_signature` picks which organization's secret to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body. But once the signature check passes, `create` dispatches the very same raw body to handlers (`PushHandler`, `PullRequest::OpenedHandler/ClosedHandler/ReopenedHandler/UnlabeledHandler`, etc.) which instead resolve the target repository/stack via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`. These two fields are never checked for consistency.

### Finding Description
- `verify_signature` derives the signing organization solely from `repository.owner.login`: [1](#0-0) [2](#0-1) 
- All handlers instead look up the target `Repository`/`Stack` using `repository.full_name` from the same body: [3](#0-2) [4](#0-3) 
- `Repository.from_github_repo_name` simply splits `owner/name` out of that `full_name` and looks the repo up, with no relation enforced back to the `repository.owner.login` field used for signing: [5](#0-4) 
- Multi-organization support is explicitly documented, meaning distinct organizations legitimately hold distinct `webhook_secret`s configured on the same Shipit instance: [6](#0-5) [7](#0-6) 

The equality that should hold but does not:
`organization whose webhook_secret authenticated the request` == `owner of the repository the handler mutates`.

Because the signature only covers the raw byte string (proving *some* onboarded organization signed this exact JSON) and `repository_owner` used for key selection is read from a field (`repository.owner.login`) that is separate from the field used for stack resolution (`repository.full_name`), an organization onboarded onto the shared Shipit instance can forge a payload where `repository.owner.login` names *its own* org (so its own valid `webhook_secret` verifies) while `repository.full_name` names a repository belonging to a *different* onboarded organization. The request passes signature verification and is then dispatched to handlers that mutate the other organization's `Stack`/`ReviewStack` records (triggering `sync_github`, archiving/unarchiving review stacks, updating pull request state, etc.), even though the attacker never possessed that other organization's secret.

### Impact Explanation
This lets one legitimate-but-malicious tenant organization on a multi-org Shipit instance forge webhook-driven state transitions (sync a branch, archive/unarchive a review stack, mutate pull_request records) for a Stack it does not own and has no GitHub-side access to, purely by crafting the JSON body's `repository.owner.login` vs `repository.full_name` mismatch. This is a cross-repository/cross-organization write achieved by exploiting a broken binding between the credential used to authenticate the webhook and the resource the webhook payload is allowed to affect — matching the "unauthorized deploy/rollback" and "cross-repository writes" impact classes, since `PushHandler#process` can trigger `stack.sync_github` (feeding into deploy/CD flows) on a stack outside the attacker's own organization.

### Likelihood Explanation
Requires only that the Shipit instance is configured for more than one GitHub organization (a documented, supported configuration) and that the attacker already controls one legitimate onboarded org's app/webhook secret for their own repos — they do not need any credential, private key, or write access belonging to the victim organization. No social engineering, TLS interception, or privileged Shipit account is needed; the request is a normal unauthenticated HTTP POST to `/webhooks` with a crafted body and a valid signature computed with the attacker's own webhook secret.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after computing which organization's secret validated the signature, assert that `repository.full_name`'s owner segment (and/or `organization.login`) matches the same organization used for verification before dispatching to handlers; reject (422) any payload where these fields disagree.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md:181-209`).
2. Attacker computes a valid `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over a crafted JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. POST this to `/webhooks` with `X-Github-Event: push` and the computed signature.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully since the signature matches `attacker-org`'s secret over the exact raw body [1](#0-0) .
5. `create` dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: ...)` on `victim-org`'s stack [8](#0-7) , despite the request never being signed by `victim-org`'s secret.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
