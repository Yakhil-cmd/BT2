The n8n-mcp SSRF centers on a network-facing service that accepts attacker-supplied URLs (via `N8N_API_URL`, webhook trigger tool arguments, or the `x-n8n-url` header) and issues outbound HTTP requests, returning the response body to the caller — enabling access to internal services/cloud metadata endpoints. I searched the Polkadot SDK for an analogous pattern: a real user entry point (signed extrinsic, XCM message, or proof submission) that causes the node to make an outbound network request to an attacker-supplied URL and return the response data to the attacker.

The only HTTP-client capability in the codebase is the offchain worker HTTP API [1](#0-0)  and its implementation in `sc_offchain`'s `HttpApi::request_start` [2](#0-1) . This is fundamentally different from the n8n-mcp bug class:

- Offchain worker code executes locally on the node operator's own machine, driven by the runtime logic the operator has chosen to run — it is not a network-facing multi-tenant service invoked by a remote, unprivileged, authenticated caller.
- There is no consensus-relevant, fee-paying, signed-extrinsic entry point in the scanned code that takes an attacker-supplied URL and causes the node to fetch it and return the response body to the attacker over the network, the way `n8n_trigger_webhook_workflow` or `N8N_API_URL`/`x-n8n-url` do in n8n-mcp.
- The other URL-like configuration surfaces found (`TelemetryEndpoints`, chain-spec `telemetryEndpoints`, `--telemetry-url` CLI param) are node-operator-controlled startup configuration, not attacker-reachable via a permitted extrinsic, XCM message, or proof submission [3](#0-2) [4](#0-3) .

Since SSRF requires an attacker-controlled input reaching a request-issuing sink through a genuine remote/authenticated entry point, and no such wiring exists in FRAME/Substrate/Polkadot/Cumulus runtime or client code reachable via a signed extrinsic, XCM execution, or proof submission, forcing this bug class onto the Polkadot SDK would not be a real analog.
