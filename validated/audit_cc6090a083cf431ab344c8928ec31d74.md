### Title
AA payments/bounces of spender_attested assets permanently freeze funds when the recipient loses attestation - (File: aa_composer.js)

### Summary
`spender_attested` assets in ocore require every payment **output** address to be on the asset's current attestor-approved list, checked via `storage.filterAttestedAddresses` during unit validation [1](#0-0) . When an Autonomous Agent (AA) sends a payment of such an asset, it always directs the response to `trigger.address` (or another `AA`-computed address) with no ability to substitute a different recipient, and if that same address is later removed from the attestor list (the ocore analog of being "blacklisted"), the payment fails validation, `bounce()` is invoked, and because `bounce()` refunds the very same `trigger.address`, the retry fails identically — leaving the funds permanently stuck inside the AA.

### Finding Description
An AA's `sendUnit()` builds outgoing payment messages and, for non-base assets, loads attestation info via `storage.loadAssetWithListOfAttestedAuthors` [2](#0-1) . If unit construction succeeds but `validateAndSaveUnit` later rejects the unit (e.g., because `spender_attested` output-address check fails, per `validation.js`), the failure propagates back up to `bounce(err)` [3](#0-2) .

`bounce()` always constructs its refund messages targeting `trigger.address` — the exact address that just failed the attestation/output check — using the same asset: [4](#0-3) 

Since the refund uses the identical asset and identical recipient address, it fails the same `spender_attested` validation check in `validatePaymentInputsAndOutputs`: [1](#0-0) 

This calls `bounce(err)` a second time, but the `bBouncing` guard prevents a second retry and simply calls `finish(null)`, silently eating the funds with no successful response unit and no state rollback of the asset balance already credited to the AA: [5](#0-4) 

The same permanent freeze condition applies to attested-asset transfers in general: any output address that becomes unattested after being trusted once can never receive further transfers of that asset while it's held by an AA or across payment chains, because `filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` are re-evaluated against the *current* on-chain attestor list at spend time, not the list valid at deposit time [6](#0-5) [7](#0-6) .

### Impact Explanation
A user who deposits (or is credited with, e.g. via a swap AA) a `spender_attested` asset into an AA, and is subsequently de-attested by the asset's attestor (analogous to being placed on a compliance blacklist), can never retrieve that asset balance from the AA: every attempt to pay it out targets the user's own (now unattested) address, fails validation identically on both the primary attempt and the bounce-refund attempt, and the AA silently keeps/burns the funds (`finish(null)`), with no owner-controlled or protocol-level mechanism to redirect the payout to an alternate, still-attested address. This is a concrete, unrecoverable freeze of user funds inside the contract, matching the impact class described in the reference report.

### Likelihood Explanation
This requires only: (1) an AA that handles a `spender_attested` asset (a supported, in-scope asset feature), and (2) the attestor revoking/rotating the attestor list to exclude a previously-attested address, which is a normal, permitted, unprivileged-from-the-user's-perspective attestor action already supported by `asset_attestors` messages. No malicious peer/hub/node behavior is needed — only a legitimate change in the asset's attestor list combined with normal AA payment/bounce logic, which is deterministic and always reachable this way.

### Recommendation
- Do not treat a failed bounce-refund as final loss: when `bounce()`'s own refund payment fails the same validation the original payment failed, either (a) retain the asset in the AA's tracked balance/state so a future state-changing trigger (or an admin/user-specified alternate address) can retrieve it once re-attested, or (b) allow the AA definition/state to redirect refunds to an alternate address supplied by the trigger unit rather than hardcoding `trigger.address`.
- More generally, avoid silently discarding funds on double-bounce failure (`finish(null)` in `bounce()`); log/flag this as an unrecoverable-funds condition rather than treating it as an ordinary bounce.
- Consider decoupling "spender_attested" checks for a return-to-sender/change output from checks for a fresh transfer, since a change/refund output logically belongs to the payer.

### Proof of Concept
1. Attestor `T` defines asset `X` with `spender_attested: true` and attests address `U`.
2. `U` sends `X` to AA `A` (valid, since `U` is attested at the time).
3. `T` publishes a new `asset_attestors` list for `X` that no longer includes `U`.
4. `U` triggers `A` to pay `X` back to `U` (`trigger.address = U`).
5. In `sendUnit()`, `A` composes a payment message with output `{address: U, amount: ...}` for asset `X` [8](#0-7) .
6. `validateAndSaveUnit` rejects the unit at `validatePaymentInputsAndOutputs` because `filterAttestedAddresses` no longer includes `U` [1](#0-0) .
7. `bounce(err)` fires, builds a refund message to `trigger.address` (still `U`) for the received `X` [4](#0-3) , which fails the same check.
8. `bBouncing` is already `true`, so `finish(null)` is called: `A` keeps `U`'s `X` balance permanently, with no path for `U` to recover it [5](#0-4) .

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;

	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
