### Title
Uncaught `throw Error()` in oscript `ifelse` evaluation crashes the entire node process instead of failing the AA gracefully - (File: `formula/evaluation.js`)

### Summary
`quicly`'s bug class is a remotely triggerable `assert()`/invariant-violation that crashes the whole process instead of being handled as a normal protocol error. `ocore` has several places where a `throw Error(...)` is used instead of the graceful error path, and any such throw during unit/AA processing is fatal to the whole node because of the global `uncaughtException` handler in `network.js` that deliberately re-throws to kill the process: [1](#0-0) 

The most directly attacker-reachable instance of this pattern is in the oscript formula evaluator used to run Autonomous Agents, which is invoked for every AA trigger sent by any unprivileged user: [2](#0-1) 

### Finding Description
In `evaluate()`'s `'ifelse'` case, the test expression is evaluated and then classified: `wrappedObject` instances are coerced to `true`, `Decimal` values are converted to boolean, and any other type is expected to be a string/boolean. If `res` falls through to `typeof res === 'object'` — i.e., a raw (non-`wrappedObject`) JS object slipping past the `isValidValue(res)` guard just above it — the code does not call `setFatalError` (the normal, safe AA-failure path used everywhere else in this file) but instead does a hard `throw Error("test evaluated to object " + res)`: [3](#0-2) 

This is exactly the assertion-failure bug class described in the QUIC advisory: an internal "this should never happen" invariant, reachable with attacker-controlled input, that is enforced with a raw `throw` rather than a recoverable error path. Every other adjacent branch (`'and'`, `'or'`, `'comparison'`, `'ternary'`) uses `setFatalError(...)` for the analogous "unrecognized type" condition, which safely bounces the AA trigger; only `'ifelse'` uses a fatal, uncaught `throw`.

Because AA trigger processing runs inside the node's main validation/writer pipeline (`aa_composer.js` → `validation.validate` → `writer.saveJoint`), and any exception thrown synchronously inside that call stack is not caught by `try/catch`, it propagates up as an uncaught exception. `network.js`'s global handler intentionally re-throws it to crash the process: [1](#0-0) 

### Impact Explanation
Any AA whose definition contains an `ifelse` construct whose test can evaluate to an unwrapped object value (rather than the normalized `wrappedObject`, `Decimal`, `boolean`, or `string`) will crash every full node that executes that AA's response to a trigger. Since AA triggers can be sent by any unprivileged user (this is one of the explicitly allowed attack surfaces — "AA trigger sender"), and AAs are executed deterministically by all full nodes processing the DAG, a single crafted trigger against a vulnerable AA can crash the entire network of full nodes simultaneously — a "network unable to confirm new units" denial-of-service, matching the accepted-impact bar for this analysis.

### Likelihood Explanation
Reachability requires only: (1) an existing AA definition whose oscript logic contains an `ifelse` test expression capable of yielding a raw (non-wrapped) object value, and (2) an unprivileged user sending a trigger unit to that AA that drives evaluation down that path. AA authors can freely author decentralized, permissionless contracts, so the presence of such a code path in a widely-used AA is plausible but depends on the specific oscript operators used in that AA's `ifelse` test (i.e., some operator returning an un-wrapped object). I was not able to fully enumerate, within the available tool budget, exactly which oscript operator(s) can produce a raw (non-`wrappedObject`) object result reaching this branch — this would need further investigation (e.g., testing `map`, `reduce`, JSON-parsing ops, or similar array/object-returning constructs) to construct a concrete working exploit AA/oscript snippet.

### Recommendation
Replace the raw `throw Error("test evaluated to object " + res)` in the `'ifelse'` branch of `formula/evaluation.js` with the same `setFatalError(...)` pattern used by the sibling branches (`'and'`, `'or'`, `'comparison'`, `'ternary'`), so that an unexpected/unwrapped object result bounces the AA trigger instead of crashing the process. More broadly, audit `formula/evaluation.js`, `aa_composer.js`, and `validation.js` for other raw `throw Error(...)` calls that sit on code paths reachable from externally supplied units/triggers (as opposed to being wrapped in `setFatalError`, `callback(err)`, or genuinely "cannot happen" internal-consistency checks that are unreachable by external input) and convert them to non-fatal error handling.

### Proof of Concept
Not fully constructed: a concrete AA `oscript` definition string containing an `ifelse` whose test expression yields a raw JS object at runtime (bypassing normalization to `wrappedObject`) would need to be identified experimentally by exercising the various operators in `formula/evaluation.js`, then triggered via a normal trigger unit from an unprivileged address. This step could not be completed within the current investigation and is flagged as an open item for further verification.
