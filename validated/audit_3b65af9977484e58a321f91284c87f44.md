### Title
Unbounded iteration over unspent outputs when composing an AA payment response can be exploited to freeze funds locked in an AA - (File: aa_composer.js)

### Summary
The reported bug class is that a per-user storage array is iterated in full on every withdrawal, so an attacker (or an unlucky heavy user) can grow that array large enough that the withdrawal transaction can never complete, permanently freezing the user's funds. The closest reachable analog in ocore is the coin-selection loop that an Autonomous Agent (AA) runs every time it needs to send a payment in response to a trigger: `iterateUnspentOutputs()` inside `sendUnit()` in `aa_composer.js`, which walks through *all* unspent outputs sitting on the AA's address without any bound on how many rows/inputs it will consume.

### Finding Description
When an AA response message contains a `payment` app, `sendUnit()` builds the payment payload by repeatedly querying the AA address's unspent outputs and pushing each one into `payload.inputs` until the target amount is reached: [1](#0-0) 

The rows come from two unbounded queries, `readStableOutputs()` and `readUnstableOutputsSentByAAs()`, which select *every* matching output for the AA's address with no `LIMIT`: [2](#0-1) 

There is a dust-filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) intended to stop an attacker from spamming the AA address with many *tiny* outputs, as the comment states: "spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond" [3](#0-2) . However, this filter only rejects outputs smaller than `FULL_TRANSFER_INPUT_SIZE` bytes-equivalent; it does not cap the *number* of outputs an attacker can create above that threshold, nor the number of outputs sent to the AA by other AAs via `readUnstableOutputsSentByAAs()` (which has no size filter for non-base assets and only excludes auto-destroy assets). Any unprivileged unit poster can pay many small-but-not-dust outputs (or, for an asset, outputs of any size) to a known AA address before a trigger executes. Because `iterateUnspentOutputs()` has no cap on `payload.inputs.length` and no message-count check against `constants.MAX_MESSAGES_PER_UNIT` while accumulating inputs, the resulting payment message can require far more inputs than can fit in a single valid unit, or the accumulation loop/DB round trip becomes prohibitively expensive before the AA can ever assemble a valid response.

This mirrors the reported bug class exactly: a storage collection tied to an address (here, "unspent outputs owned by the AA address," analogous to `userLocks`/`userEarnings` in the original report) is iterated in full on every withdrawal-like operation (`sendUnit`'s payment composition on every trigger that requires the AA to pay out), and an unprivileged actor (any unit poster) can grow that collection arbitrarily by sending many small payments to the AA address.

### Impact Explanation
If an AA's payout logic depends on collecting enough unspent outputs of its own address to fulfill a `payment` message (a common pattern for AAs that hold and later disburse user funds, e.g., escrow/lending/exchange-style AAs), an attacker can pollute the AA's own output set with many low-value, non-dust outputs. Once the number of usable outputs required to satisfy a payout exceeds what can fit in a single unit (`MAX_MESSAGES_PER_UNIT`/message size limits), every subsequent trigger that needs the AA to send a payment will fail to compose a valid unit, causing the AA response to bounce indefinitely. Any user funds already held by the AA that require this composed payment path to be released become permanently stuck — an AA fund-freezing condition, matching the "medium-risk, certain users affected" classification of the original report.

### Likelihood Explanation
Exploitation only requires being able to post ordinary payment units to a public AA address, something any unprivileged unit poster can do (no special privilege, no witness/hub/peer compromise needed). The dust filter mitigates but does not eliminate the issue because it filters by amount, not by count, and it doesn't cover outputs sent to the AA by other AAs for arbitrary assets. The likelihood of an attacker deliberately targeting a specific high-value AA is plausible but requires the AA's own payout logic to be structured such that it collects many small self-owned outputs to fund payments, which is an AA-author choice, not a protocol-wide default — this makes the exploit AA-specific rather than universally applicable across all AAs.

### Recommendation
Cap the number of inputs collected in `iterateUnspentOutputs()`/`sendUnit()` to a safe number well under `constants.MAX_MESSAGES_PER_UNIT`, and if the target amount cannot be reached within that cap, either bounce with a clear error or split the response across multiple secondary triggers instead of silently failing/growing unbounded. Consider also limiting or rate-limiting the number of unspent outputs a single external unit (or the aggregate of external units) can add to any given address between AA payouts.

### Proof of Concept
1. Deploy an AA that, on trigger, attempts to pay out a stored balance by having the engine auto-select inputs from its own address's unspent outputs (relying on `sendUnit()`'s default payment coin-selection rather than caller-supplied `inputs`).
2. As an unprivileged unit poster, send many small payments (each above the `FULL_TRANSFER_INPUT_SIZE` dust threshold, e.g., a few thousand bytes each) directly to the AA's address over many units, accumulating hundreds/thousands of small unspent outputs owned by the AA.
3. Trigger the AA in a way that requires it to send out an amount that can only be satisfied by summing across most/all of these many small outputs.
4. Observe that `iterateUnspentOutputs()` (`aa_composer.js:1102-1137`) keeps adding inputs from `readStableOutputs`/`readUnstableOutputsSentByAAs` without a bound; once the required `payload.inputs.length` exceeds what fits in a valid unit, the AA can no longer construct a valid response and the trigger permanently bounces, freezing the funds it was supposed to pay out.
