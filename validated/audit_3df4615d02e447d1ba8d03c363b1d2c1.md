### Title
Stack-scoped ApiClient token can read CI/build status of any stack via CCMenuController - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method inherited from `Shipit::Api::BaseController` with an unscoped lookup, so the per-token stack restriction enforced everywhere else in the API is silently dropped for this endpoint. The binding that breaks is: *the stack an `ApiClient` token authorizes access to* ≠ *the stack the request actually touches*.

### Finding Description
`Shipit::Api::BaseController` defines the authorization scope for any `ApiClient` token that has been assigned to a specific stack: [1](#0-0) 

Every other API controller that resolves the current stack does so through this scoped `stacks`/`stack` helper (e.g. `Shipit::Api::StacksController`, `Shipit::Api::DeploysController`, `Shipit::Api::TasksController` all inherit `stack` unchanged from `BaseController`), which raises/returns nothing if `params[:stack_id]` does not match the stack the token is bound to.

`CCMenuController`, however, defines its own private `stack` method that bypasses this scoping entirely and resolves the stack directly from the URL parameter with no relation to `current_api_client.stack_id`: [2](#0-1) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission bit via `ApiClient#check_permissions!`: [3](#0-2) 

It never checks *which* stack the permission applies to — that check only happens implicitly through `BaseController#stacks`/`#stack`, which `CCMenuController` does not use. As a result, a token created with `stack_id` set to stack A and permission `read:stack` (the minimal, least-privileged token type intended to expose only stack A's status, e.g. to a CI dashboard) can be replayed against `/api/stacks/*stack_id/ccmenu` for any other stack B, C, etc., and will successfully render that stack's build status, lock state, and last build label/time.

### Impact Explanation
This is an authorization-scope escape: a token intentionally restricted to one stack (`ApiClient.stack_id` present) discloses build/deploy state — including lock reason/author, last build status/label/time, and stack name — of every other stack in the Shipit instance, without any additional credential. This matches the "unauthenticated read of stack state" bucket for `High` severity, since the disclosure occurs for stacks the token was never authorized to touch, effectively defeating the stack-scoping feature that is the entire point of `ApiClient.stack_id`.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (a supported, encouraged pattern per `app/models/shipit/unlimited_api_client.rb` vs. scoped `ApiClient`, and exercised in `test/controllers/api/stacks_controller_test.rb`'s "an api client scoped to a stack will only see that one stack" test). Any holder of such a token — which by design is meant to be handed out more broadly/with less trust than an unscoped token — can trivially enumerate other stacks' IDs (stack ids are `owner/repo/environment` strings, easily guessable/discoverable) and query this endpoint.

### Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is enforced identically to every other API controller.

### Proof of Concept
1. Create a stack-scoped `ApiClient` bound to `stack_id: A.id` with permission `read:stack` (as done via `resources :api_clients` / admin UI, or directly via the model, matching the fixture pattern `here_come_the_walrus` used in `test/controllers/api/stacks_controller_test.rb:188-198` which is described as scoped "will only see that one stack").
2. Using that token's `authentication_token` as HTTP Basic credentials, request:
   `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu`
   where `<other-repo>/<other-env>` is a stack B that the token was never granted access to.
3. Observe that the response is `200 OK` with a `<Project>` XML payload describing stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, and lock state — contrasted with `Shipit::Api::StacksController#show` for the same token/stack B, which would return `404 Not Found` because it correctly uses the scoped `stack` helper.
