### Title
Cross-organization forged CI status via unscoped `Commit.where(sha:)` in `StatusHandler` bypasses `MergeRequest#reject_unless_mergeable!` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository/organization that authenticated the webhook. This lets a status event correctly signed for one organization's GitHub App write a `Status` row onto any `Commit` record in the entire database that happens to share that sha, including a completely unrelated victim stack's `MergeRequest#head`, which is then read unmodified by `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?`.

### Finding Description
The binding that should hold is: `commit.stack.repository.owner == payload.dig('repository','owner','login')` for every `Commit` mutated by a status webhook. This binding is broken because `StatusHandler#process` does: [1](#0-0) 
which queries `Commit.where(sha: params.sha)` across the whole table with no join/filter on `stack`, `repository`, or the `repository_owner` derived in `WebhooksController#repository_owner`, unlike `Handler#stacks`, which does scope by `Repository.from_github_repo_name(repository_name)`: [2](#0-1) 

Webhook signature verification (`WebhooksController#verify_signature`) only proves the payload was signed with the `webhook_secret` of the organization named in the payload's own `repository.owner.login`/`organization.login` field — it says nothing about which `Commit` rows get touched by the handler: [3](#0-2) 

An attacker who owns/administers any organization or repository onboarded to this Shipit instance (or any org configured without a `webhook_secret`, since `verify_webhook_signature` returns `true` when no secret is configured) can send a `status` event whose `repository` field names their own org (so it passes signature verification) but whose `sha` is the public head SHA of a victim's pull request tracked by a different stack in a different organization. `StatusHandler` finds the victim's `Commit` purely by SHA collision and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `state: 'success'` status onto it.

`MergeRequest#all_status_checks_passed?` and `#any_status_checks_failed?` then construct `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)` from the victim's `head` commit — this reads the forged status with no re-validation that it came from the victim's own organization: [4](#0-3) 

`ProcessMergeRequestsJob#perform` then calls `refresh!`, `reject_unless_mergeable!` (which no longer sees `any_status_checks_failed?`/`any_status_checks_missing?` as true because of the forged success status), and proceeds to `merge!`: [5](#0-4) [6](#0-5) 

No other guard intervenes: `drop_unhandled_event` and `verify_signature` only gate on event type and the *attacker's own* organization's secret; `ExplicitParameters` schema only validates types, not repository ownership; `StatusHandler` never consults `stacks`/`repository_name` at all.

### Impact Explanation
An attacker who controls any organization/repo onboarded into this Shipit instance can inject a fabricated "success" CI status onto an arbitrary victim commit in a different tenant's stack, provided they know (or guess) that commit's SHA — which is public on GitHub for any PR. This can cause `MergeRequest#merge!` to proceed and Shipit to merge a pull request in the victim's repository, and can also corrupt `Commit#state`/status displays and downstream deploy gating that consult `Status::Group`/`StatusChecker` for that commit. This is a payload for one repository (attacker's) mutating another repository's records (victim's `Commit`/`MergeRequest`), matching the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions: the Shipit instance must host more than one organization/repository (multi-tenant), and the attacker must control (or have been granted) a legitimate webhook-signing identity for at least one of those organizations (i.e., own/administer an org already configured in Shipit's `github_apps`/organizations, or exploit an org configured with no `webhook_secret`, in which case `verify_webhook_signature` trivially returns `true`). The attacker needs the victim's commit SHA, which is public GitHub information for any PR/branch. No Shipit session, API token, or GitHub App private key is required, and the attack is fully repeatable against any known SHA in any stack on the instance — this is a low-cost, highly repeatable cross-tenant attack once the attacker has any onboarded org identity.

### Recommendation
Scope `StatusHandler#process` (and analogously `CheckSuiteHandler`/other handlers that resolve records purely by SHA) to only touch commits belonging to stacks whose repository matches the authenticated `repository_name`/`repository_owner` from the payload, e.g. via `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit` to `Stack`/`Repository` and filtering by the verified organization, mirroring the pattern already used in `Handler#stacks`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from attacker org cannot forge status on a victim commit in another org" do
  victim_stack = shipit_stacks(:shipit) # repository owner "shopify"
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, branch: victim_stack.branch)
  merge_request = victim_stack.merge_requests.create!(number: 1, head: victim_commit, merge_status: 'pending')

  refute merge_request.all_status_checks_passed?

  # payload signed for a *different* org that the attacker owns/controls
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/required',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  merge_request.reload
  assert merge_request.all_status_checks_passed?, "forged cross-org status incorrectly satisfied victim's CI check"
  refute merge_request.reject_unless_mergeable!, "victim MergeRequest was not rejected despite status not originating from its own org/CI"
end
```
This demonstrates the equality `commit.stack.repository.owner == payload_owner` is violated: the commit belongs to `shopify`/`victim_stack` but the status write is accepted from a payload whose `repository.owner.login` is `attacker-org`, because `StatusHandler.process` at [1](#0-0)  never checks repository ownership before calling `commit.create_status_from_github!`.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
