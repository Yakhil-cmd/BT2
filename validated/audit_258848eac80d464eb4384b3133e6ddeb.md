### Title
`Shipit::Webhooks::Handlers::StatusHandler#process` applies GitHub status webhooks to commits by SHA only, with no repository check, letting a webhook for one repository write a `Status` on another stack's commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` and calls `commit.create_status_from_github!(params)` on every match, regardless of which repository the webhook payload belongs to. Because `Commit#blocking_statuses`/`blocked?` are keyed off `stack.blocking_statuses`, a status webhook that is authentically signed for organization/repo A can create a `Status` row against a `Commit` that belongs to stack B, as long as both stacks happen to contain a `Commit` record with the same `sha` (e.g. a shared git ancestor between a fork and the upstream repository).

### Finding Description
The broken binding is: **`params.dig('repository','full_name')` (the repository that authenticated/originated the webhook) must equal `commit.stack.repository.full_name` (the repository whose blocking gate is being cleared)**. Tracing the code shows this equality is never checked:

- `Shipit::WebhooksController#verify_signature` only verifies the HMAC signature against the webhook secret for the *organization* derived from `params.dig('repository','owner','login')` [1](#0-0) . This proves the payload came from GitHub for that org/app installation - it does not bind the payload's `sha` to any specific repository's commit graph.
- `StatusHandler#process` never uses `params.repository` at all; its params schema doesn't even declare a `repository` field, and it resolves target commits purely by SHA: [2](#0-1) 
- Every other handler in this codebase (e.g. `PullRequest::OpenedHandler`, `LabeledHandler`) explicitly resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting [3](#0-2) , and the base `Handler` class even provides a `stacks` helper scoped by repository [4](#0-3)  - `StatusHandler` simply doesn't use it.
- `Commit#create_status_from_github!` writes the status using the commit's own `stack_id`, not anything derived from the webhook's repository: [5](#0-4) 
- `Commit#blocked?` re-evaluates using `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)` [6](#0-5) , and `Status::Common#blocking?` checks `commit.blocking_statuses.include?(context)` [7](#0-6)  - both delegate to the *commit's own stack*, so a status planted on the victim commit via the wrong-repo webhook directly changes the victim stack's gate.

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: status`, a validly-signed payload for a repository/organization the attacker can legitimately trigger webhooks for, with `sha` equal to a commit SHA that also exists (same SHA1, e.g. shared ancestor commit from a fork) in `victim`'s stack, `state: 'success'`, `context: 'ci/required'`. Signature verification passes because it is scoped to the organization/app installation from the payload, not to the specific stack being mutated. `StatusHandler#process` then matches `Commit.where(sha: ...)` across **all** stacks sharing that SHA and calls `create_status_from_github!` on each, writing a `Status` with `stack_id` equal to the victim stack. This flips `blocking?` to false for the victim's previously-blocking ancestor commit, and `blocked?`/`deployable?` on later victim commits change as a result.

Existing guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) only validate the org-level HMAC and payload shape - none of them check that the commit being mutated belongs to a stack whose repository matches the webhook's repository field.

### Impact Explanation
An attacker who can get a genuinely-signed `status` webhook delivered (for any repository under an organization/app installation configured in Shipit) can write a `Status` record against a commit belonging to a *different* stack, provided the two repositories share a commit with an identical SHA (realistic for forks/shared history). This clears a blocking-status gate the victim stack relies on, causing `Commit#deployable?` to flip to true for undeployed commits and enabling an unauthorized deploy to proceed - "a payload for one repository mutating another's stack/commit" and contributing to an unauthorized deploy, matching the Critical impact category.

### Likelihood Explanation
Exploitation requires: (1) the victim stack has `blocking_statuses` configured and an undeployed ancestor commit currently blocking on a missing/failing context (stated precondition); (2) the attacker can get GitHub to deliver a validly-signed `status` webhook (i.e., they control or can trigger events from a repository under an organization/app installation Shipit trusts); and (3) a commit SHA collision/shared-ancestor exists between the attacker-controlled repository and the victim's repository (most realistically via a fork of the victim repo, since forks share identical commit objects/SHAs with their upstream for unmodified history). Condition (3) is the main constraining factor - it is not exploitable against arbitrary, unrelated repositories, only ones sharing git history with the victim (forks). This narrows likelihood but does not eliminate it, since forking a public repository is a normal, low-cost, unprivileged action.

### Recommendation
In `StatusHandler#process` (and `create_status_from_github!`/`refresh_statuses!` call sites), scope the commit lookup to the repository the webhook actually belongs to, e.g. restrict to `stacks` (via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) before matching by `sha`, mirroring the pattern already used by `PullRequest` handlers and the `Handler#stacks` helper.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook for repo A does not unblock a commit in repo B's stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit) # repository shopify/shipit-engine
  victim_stack.update!(cached_deploy_spec: DeploySpec.new('ci' => { 'blocking' => ['ci/required'] }))

  shared_sha = 'deadbeef' * 5
  blocking_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'ancestor')
  later_commit = victim_stack.commits.create!(sha: 'cafebabe' * 5, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'later')
  later_commit.statuses.create!(stack: victim_stack, state: 'success', context: 'ci/travis')

  assert_predicate blocking_commit, :blocking? rescue nil
  refute_predicate later_commit, :deployable? # blocked because ancestor missing ci/required

  # attacker-controlled payload for an unrelated repository, but same sha (e.g. shared fork ancestor)
  attacker_params = { 'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/required',
                       'repository' => { 'full_name' => 'attacker/unrelated-fork' } }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_params)

  refute later_commit.reload.blocked? # gate incorrectly cleared for victim stack
end
```
This demonstrates that a webhook whose `repository.full_name` never matches `victim_stack`'s repository still mutates `victim_stack`'s commit status and clears its blocking gate, confirming the broken repository-scope binding in `StatusHandler#process`.
