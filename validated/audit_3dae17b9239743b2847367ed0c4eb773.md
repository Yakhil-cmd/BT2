### Title
Cross-repository status corruption via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes a GitHub `status` webhook payload to `Commit.where(sha: params.sha)`, matching against the global `commits` table with no repository/stack scoping. If two different repositories (an attacker-owned repo and a victim's stack) ever contain a `Shipit::Commit` row with the same SHA, a webhook authenticated for the attacker's own repository/org will still be applied to the victim's commit record.

### Finding Description
The broken binding is: **a status webhook, once signature-verified for `repository_owner = attacker_org`, should only ever mutate `Commit` rows belonging to stacks whose `Repository#owner/name == attacker_org/attacker_repo`.** Instead, the actual write path is:

- `Shipit::WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event('status')` → `Handlers::StatusHandler.call(params)` [1](#0-0)  after `verify_signature` checks the signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the attacker-controlled JSON body itself (`params.dig('repository','owner','login')`) [2](#0-1) .
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This is the only handler among push/pull_request that does **not** use the `stacks`/`Repository.from_github_repo_name(repository_name)` scoping helper defined on the base `Handler` class [4](#0-3) . All other handlers resolve `stacks` via `Repository.from_github_repo_name(repository_name)&.stacks`, which is scoped to the exact `owner/name` pair from the payload; `StatusHandler` instead queries `Commit` globally by bare `sha`.

`create_status_from_github!` then unconditionally calls `add_status`, which creates a `Status`, recomputes `commit.status`, and can fire `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` [5](#0-4) [6](#0-5) . Since `Commit` has no uniqueness constraint enforced across stacks by SHA (it's scoped per `stack_id`, but the `where(sha:)` lookup ignores `stack_id` entirely), any commit row anywhere in the database with a matching SHA is mutated, regardless of which stack/repository it belongs to.

The signature verification only proves the payload was signed by the GitHub App/webhook secret associated with `repository_owner` (the org named inside the payload) — it does **not** prove that the `sha`/`context` being reported is scoped to that org's repositories. An attacker who controls their own GitHub org/repo registered in Shipit (with their own legitimate webhook secret) can freely choose `sha` and `context` in a real, validly-signed `status` event from their own repository. If that `sha` happens to also exist as a `Commit` row in a victim's stack (e.g., because of a shared git history, a fork, a cherry-pick, or a colliding/empty commit), the attacker's own valid webhook writes a `sonarqube` status onto the victim's commit.

Existing guards do not prevent this: `verify_signature` validates *who signed*, not *what stack the sha belongs to*; `ExplicitParameters` only validates JSON shape (`sha`, `state`, `context`, etc.), not ownership; there is no `Repository.from_github_repo_name` check in `StatusHandler` as there is in every other handler.

### Impact Explanation
An attacker who owns any repository registered with Shipit (a low bar — many Shipit deployments allow self-service repository onboarding) can send a validly-signed `status` webhook from their own repo/org. If the `sha` collides with a commit that exists in a victim stack, `Commit#create_status_from_github!` writes a `Status` row against the victim's commit, potentially flipping its aggregate `status.state` (e.g. required `sonarqube` context now reports `success`), unblocking `deployable?`/`blocked?` checks, and triggering `stack.schedule_merges` / continuous deployment for the victim stack — this is a payload from one repository mutating another's commit/stack state, matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. The write is deterministic and repeatable against any stack for which a SHA collision can be produced or found.

### Likelihood Explanation
Exploitability is gated entirely on the precondition of a shared/colliding SHA between the attacker's repo and the victim's stack commit table — the question's own framing assumes this as given ("shared commit SHA with attacker repo"). Producing an actual SHA collision against an arbitrary victim commit is not generally feasible (SHA-1 preimage/collision against a fixed target is not practical), but shared SHAs do occur legitimately in real-world Shipit deployments — forks of the same upstream repo, monorepo mirrors, or repos that share commit history — where the same commit is synced into multiple `Stack`s' `Commit` tables. In those legitimate-collision scenarios, no attacker "capability" is required beyond controlling one of the sharing repositories' webhook delivery, which is exactly the unprivileged capability described (owning/pushing to a repo that emits webhooks). The root cause — missing repo scoping in `StatusHandler#process` — is a code defect independent of how the collision arises, and is trivially reproducible in any environment where two stacks reference the same SHA.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks of the repository that authenticated the webhook, mirroring the pattern used by every other handler:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the inherited `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) so that a status update can never cross repository boundaries regardless of SHA collisions.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):

1. Create `attacker_repository` (`owner: 'attacker', name: 'evil'`) with its own `Stack` and a `Commit` with `sha: 'deadbeef...'`.
2. Create `victim_repository` (`owner: 'victim', name: 'app'`) with a `Stack` requiring context `sonarqube`, and a `Commit` with the **same** `sha: 'deadbeef...'` (simulating the shared-SHA precondition), whose current aggregate status is `pending`/`unknown` (deploy blocked).
3. Stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (valid signature for attacker's own org).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: 'deadbeef...', state: 'success', context: 'sonarqube', repository: { full_name: 'attacker/evil', owner: { login: 'attacker' } } }`.
5. Assert:
   - `victim_commit.reload.statuses.where(context: 'sonarqube').count == 1` (the victim commit received a status it never authenticated) — **this should be `0`** if the binding held.
   - `victim_commit.reload.status.state == 'success'` and `victim_commit.deployable?` flips to `true` / `stack.schedule_merges` enqueued for the **victim** stack — demonstrating cross-repo deploy/merge unblocking caused entirely by the attacker's own signed request.
   - Compare both sides of the equality: expected `commit.stack.repository.full_name == 'attacker/evil'` for any commit mutated by this webhook; actual, the victim commit with `stack.repository.full_name == 'victim/app'` is also mutated — the mismatch proves the vulnerability.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
