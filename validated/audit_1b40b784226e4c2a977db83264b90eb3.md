### Title
Unbounded growth of `aa_balances` rows per address lets an unprivileged asset issuer DoS an AA's trigger processing - (File: aa_composer.js)

### Summary
Every AA trigger execution reloads **all** asset balances ever recorded for the target AA address with `SELECT asset, balance FROM aa_balances WHERE address=?` and then iterates over every returned row. Because anyone can freely define new assets and send them (even in trivial amounts) to any AA address, an attacker can inflate the number of distinct `(address, asset)` rows in `aa_balances` for a victim AA without limit, making every future trigger of that AA progressively more expensive to process — mirroring the Canto coinswap `GetAllBalances` DoS pattern, where iterating over an attacker-inflated coin list degrades or breaks a shared/pooled resource.

### Finding Description
When a unit is posted to trigger an AA, `handleTrigger()` calls `updateInitialAABalances()`: [1](#0-0) 
which issues `SELECT asset, balance FROM aa_balances WHERE address=?` and then does `rows.forEach(...)` over **every asset ever received** by that AA address, not just the assets relevant to the current trigger: [2](#0-1) 

`aa_balances` has one row per `(address, asset)` pair ever credited to the address (schema: `PRIMARY KEY (address, asset)`), and rows are only ever added, never pruned: [3](#0-2) 

Adding a new row is cheap and requires no special privilege: any user can post an `asset` definition message (`validateAssetDefinition` / AA `case "asset"`) with almost no restrictions beyond basic structural checks and the normal size fee, and then issue+transfer a tiny amount of that asset to the target AA in a `payment` message: [4](#0-3) 

Because `getTrigger()` only tracks the outputs sent to the AA in the current unit, an attacker can repeatedly create brand-new assets and send each one (in separate low-cost transactions) to the same AA address. Each such transaction is itself a valid trigger for the AA (any output to an AA address invokes it), so with every new asset the attacker forces:
1. an `INSERT` into `aa_balances` for the new asset (line 523),
2. permanent growth of the row set that must be loaded and iterated on **every subsequent** trigger of that AA, forever.

Over time this makes `updateInitialAABalances`'s query and `rows.forEach` loop (and the associated `_.difference` computation against `arrExistingAssets`, line 516-517) scale linearly with the number of distinct assets ever donated to the AA — an amount fully controlled by the attacker and with no upper bound enforced anywhere in the code shown (`MAX_DENOMINATIONS_PER_ASSET_DEFINITION` bounds only denominations within one asset, not the number of distinct assets an address can accumulate balances for).

This is structurally the same bug class as the Canto coinswap issue: a keeper/module functionality reads "all balances of an address" via unbounded iteration (`GetAllBalances` there, `SELECT ... WHERE address=?` + `forEach` here), and an attacker who can freely mint/transfer new token types (here: new Obyte assets, unlike Canto's whitelisted-denom pools) can inflate that set arbitrarily, degrading or eventually preventing normal use of the shared resource (the coinswap pool there; the AA's ability to process triggers economically here).

### Impact Explanation
Every trigger sent to a targeted AA — including from *legitimate* users, not just the attacker — must pay the cost of loading and scanning the attacker-inflated `aa_balances` row set. As the row count grows, per-trigger latency and DB/CPU work for that AA increase without bound, degrading throughput of the AA and, at scale, threatening the node's ability to process the AA's triggers within normal time constraints (analogous to the "swap or RemoveLiquidity might fail" outcome noted for the confirmed Canto duplicate). Since AA execution is embedded in a DB transaction, an unusually slow trigger also holds locks / resources longer, and the write amplification (new rows) permanently increases storage and future work — the condition never self-heals. This can render a widely-used AA (e.g. a DEX, bonding-curve, or DeFi AA holding funds for many users) progressively unusable, which is a fund-locking/availability impact consistent with a Medium-severity finding, matching the accepted severity of the original report.

### Likelihood Explanation
Any user can trigger this without any privilege: defining a new asset only requires the standard unit fees, and sending it to an AA address is a normal payment message that automatically becomes a trigger. There is no whitelist restricting which assets can reach an AA (unlike Canto's pool-creation whitelist that the judges noted mitigated the analogous risk there — Obyte has no such restriction on asset creation/transfer to AA addresses). The attack is entirely economically bounded by ordinary transaction fees on the attacker's side, and can be executed incrementally over an extended period to slowly poison a target AA, making it highly likely to be exploitable by a motivated actor with modest capital.

### Recommendation
- Do not unconditionally load and iterate the full set of historical `aa_balances` rows for an address on every trigger. Restrict `updateInitialAABalances`'s query to only the assets relevant to the current trigger (`trigger.outputs`) plus any assets the AA's formula might need (mirroring the "query only specific coins" mitigation Canto adopted for `GetPoolBalances`), e.g. `SELECT asset, balance FROM aa_balances WHERE address=? AND asset IN (?)`.
- If bulk loading is required for `readAABalances`/state-var consistency checks, add pagination/limits, and consider capping the number of distinct assets an address may accumulate zero/near-zero balances for, or lazily pruning zero-balance rows for assets not referenced by the AA's own definition.
- Consider a minimum-amount threshold or asset-issuance rate limiting to make "dust spam with brand-new assets" economically unattractive.

### Proof of Concept
1. Deploy or identify a target AA address `AA1`.
2. Attacker repeatedly, in separate low-fee units:
   a. Defines a new asset `assetN` (`app: 'asset'`, minimal fields, e.g. `is_transferrable: true`, no cap).
   b. Issues 1 unit of `assetN` to self, then sends `1` unit of `assetN` as a `payment` output to `AA1`.
3. Each such payment is a valid AA trigger; `updateInitialAABalances` executes, inserting a new `(AA1, assetN)` row into `aa_balances` (aa_composer.js lines 515-524).
4. Repeat step 2 thousands of times (feasible with automated scripting, bounded only by standard byte fees).
5. Observe that every subsequent trigger to `AA1` (from any user) now must run `SELECT asset, balance FROM aa_balances WHERE address=?` returning thousands of rows and iterate all of them (aa_composer.js lines 494-524), with cost growing linearly and unboundedly with the number of distinct assets the attacker has created — degrading `AA1`'s responsiveness over time with no remediation path in the current code.
