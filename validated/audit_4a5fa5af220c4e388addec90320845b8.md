### Title
`review_stacks_enabled` does not gate provisioning due to operator-precedence bug in `provision?`/`unarchive?` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
The intended binding is `review_stacks_enabled == true` for every repository that enters `Shipit::ReviewStackProvisioningQueue`. In `OpenedHandler#provision?` and `ReopenedHandler#unarchive?`, missing parentheses cause Ruby's operator precedence (`&&` binds tighter than `||`) to detach `repository.review_stacks_enabled` from the `allow_with_label`/`prevent_with_label` branches, so those branches can evaluate `true` even when `review_stacks_enabled` is `false`.

### Finding Description
Broken binding: `stack.repository.review_stacks_enabled == true` for every stack for which `Shipit::ReviewStackProvisioningQueue.add(stack)` is called.

In [1](#0-0) , `provision?` is written as:
```
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
Because `&&` has higher precedence than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` only guards the `allow_all` branch — it does **not** guard the `allow_with_label` or `prevent_with_label` branches. The same pattern exists in `ReopenedHandler#unarchive?` at [2](#0-1) .

By contrast, `LabeledHandler` gets this right by gating the whole `archive?/unarchive?` disjunction explicitly: `repository.review_stacks_enabled && (archive? || unarchive?)` at [3](#0-2) .

Exploit path: `Repository#review_stacks_enabled` and `Repository#provisioning_behavior` are independent boolean/enum columns writable together via `RepositoriesController#update_params` at [4](#0-3) ; nothing validates that `provisioning_behavior == allow_with_label` implies `review_stacks_enabled == true`. If a repository ends up in that state (e.g. an operator flips `review_stacks_enabled` off while `provisioning_behavior` remains `allow_with_label`), any PR author who can attach the configured `provisioning_label_name` to their own open PR causes the `opened` webhook to satisfy `provision?`, and `ReviewStackAdapter#create!` calls `Shipit::ReviewStackProvisioningQueue.add(stack)` at [5](#0-4) , even though `review_stacks_enabled` is `false`.

Signature verification (`verify_signature`) and `ExplicitParameters` schema validation do not check this application-level authorization invariant; they only validate webhook authenticity and payload shape, not the review-stacks feature flag logic, so they do not block this divergence.

### Impact Explanation
A stack is created and queued for provisioning on a repository whose `review_stacks_enabled` flag is `false`, which is supposed to be the master off-switch preventing any review-stack provisioning/task execution for that repository. Once queued, downstream processing (the provisioning worker driving `TaskCommands`) proceeds as if review stacks were enabled, effectively bypassing the repository-level authorization gate. This is scoped to the specific misconfigured repository (it does not let one repository affect another tenant's stack), but for that repository it results in unauthorized provisioning/task execution that the operator explicitly intended to disable. Note the queue/dequeue mechanics and worker processing itself were not fully traced in this session (the queue model and `TaskCommands#perform` internals were not retrieved before the tool budget ran out), so the exact command-execution consequences of a queued stack should be independently confirmed.

### Likelihood Explanation
Exploitation requires the specific repository configuration `review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) — a state reachable through normal, independent form fields with no cross-field validation. Given that state, the only attacker action needed is opening/reopening a PR and applying (or omitting) a label they control on their own PR/repository — no secrets, sessions, or elevated GitHub permissions required. This is a plausible but non-default misconfiguration (`review_stacks_enabled` defaults to disabling all review-stack behavior in the intended design), so likelihood depends on this operator-configuration edge case existing.

### Recommendation
Add explicit parentheses to bind `repository.review_stacks_enabled` across the entire disjunction in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?`, e.g.:
```ruby
repository.review_stacks_enabled &&
  (repository.provisioning_behavior_allow_all? ||
   (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
   (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
```
matching the correct pattern already used in `LabeledHandler#respond_to_label_change?`.

### Proof of Concept
Minitest plan under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
1. Create a `Shipit::Repository` with `review_stacks_enabled: false` and `provisioning_behavior: "allow_with_label"`, `provisioning_label_name: "deploy-preview"`.
2. Build an `opened` pull_request webhook payload for that repository whose `pull_request.labels` includes `{ "name" => "deploy-preview" }`.
3. Process the payload through `OpenedHandler`.
4. Assert the binding:
   - Before: `repository.review_stacks_enabled` is `false`.
   - After: `Shipit::ReviewStackProvisioningQueue.queued?(Shipit::ReviewStack.find_by(environment: "pr#{number}"))` is `true` — demonstrating the stack entered the provisioning queue despite `review_stacks_enabled == false`, breaking the intended equality `review_stacks_enabled == true` for all queued stacks.
