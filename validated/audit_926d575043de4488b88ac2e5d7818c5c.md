### Title
`OpenedHandler#provision?` operator precedence bypasses `review_stacks_enabled` for label-based provisioning behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` mixes `&&` and `||` without parentheses grouping `review_stacks_enabled` against all provisioning behaviors. Due to Ruby operator precedence, `review_stacks_enabled` only gates the `allow_all?` branch; the `allow_with_label?` and `prevent_with_label?` branches are evaluated independently of it. An attacker who can label their own pull request can therefore trigger Review Stack creation on a repository where an operator explicitly disabled `review_stacks_enabled`.

### Finding Description
The broken binding: the settings UI and docs present `repository.review_stacks_enabled` as a master switch equal to "any dynamic stack provisioning is permitted for this repository" — i.e. `review_stacks_enabled == false` should imply `provision? == false` for all Pull Requests, regardless of `provisioning_behavior`. This equality is violated.

The code is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Ruby's `&&` binds tighter than `||`, so this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.

Consequently, when `repository.provisioning_behavior == "allow_with_label"` and the repository owner sets `review_stacks_enabled = false` (intending to disable all dynamic provisioning while still configuring a label for future use, or simply misconfiguring/leaving stale settings), any pull request carrying the label matching `repository.provisioning_label_name` still causes `provision?` to return `true`. The same applies to `prevent_with_label`: an attacker just needs to *not* add the label.

Call path: `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` (true) → `ReviewStackAdapter.new(...).find_or_create!` [2](#0-1)  → stack creation and provisioning queueing, eventually reaching `ProvisioningHandler`/`Command`/`PTY.spawn` execution for the new stack's provisioning task, exactly as the question describes.

`repository.provisioning_label_name` is attacker-known/guessable (visible on the repo's settings page or simply on prior PRs of the same repo) — an attacker who owns a fork and opens a PR against the target repo, or whose PR is opened against the target repo, can add any label matching that name themselves since GitHub allows any collaborator with label-write permission, and in many default GitHub configurations PR authors from forks can still have labels applied by the base repo (or, more critically, an attacker with write access to their own PR/fork triggering the webhook does not need write access to add pre-existing labels if the repo permits label application via PR events from external actors, or if this is a same-repo branch push). Regardless of the exact GitHub label-permission nuance, the engine-side defect is that `review_stacks_enabled` fails to gate the `allow_with_label` and `prevent_with_label` code paths at all — this is a pure logic bug in this engine, independent of how the label got applied.

None of the existing guards prevent this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` [3](#0-2) ; there is no additional check on `review_stacks_enabled` anywhere else in the call path before `find_or_create!` is invoked. The existing test suite only covers `review_stacks_enabled: false` combined with `behavior: :allow_all` [4](#0-3) , and never tests `review_stacks_enabled: false` combined with `allow_with_label` or `prevent_with_label`, which is why this divergence went undetected.

### Impact Explanation
An attacker can force creation and provisioning of a `Shipit::ReviewStack` (and downstream execution of the repository's configured provisioning/deploy commands via `ProvisioningHandler`/`Command`/`PTY.spawn`) on a repository for which the operator explicitly disabled dynamic stack provisioning (`review_stacks_enabled = false`). This is an unauthorized deploy/task execution triggered purely by an attacker-controlled PR label, bypassing the operator's authorization control. This matches the "Critical - unauthorized deploy" and "RCE on the deploy host via `Command`/`PTY.spawn`" impact categories. The blast radius is scoped to repositories configured with `provisioning_behavior_allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled: false` — it does not cross repository/tenant boundaries beyond the targeted repo, but is fully repeatable against any such repository, on every PR open event.

### Likelihood Explanation
Preconditions required: the target repository must have `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) with `review_stacks_enabled = false` — a configuration combination that is plausible (an operator toggling off review stacks temporarily while leaving behavior/label configured) and requires no attacker access to secrets. Attacker cost is minimal: open a pull request and ensure the label matching `provisioning_label_name` is present (or absent, for `prevent_with_label`) — no authentication, tokens, or privileged GitHub role needed beyond opening a PR. It is fully repeatable.

### Recommendation
Fix the operator precedence so `review_stacks_enabled` gates all three behavior branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to the analogous `provision?` methods in `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler` if they share this pattern.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style, added as a new test):
```ruby
test "does not create stacks for repos with review_stacks_enabled: false, even with allow_with_label and label present" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `Shipit::Stack.count` increments by 1 (a `ReviewStack` is created and queued for provisioning via `ReviewStackAdapter#find_or_create!` and `Shipit::ReviewStackProvisioningQueue.add`), despite `review_stacks_enabled == false` on both sides of the intended equality (`review_stacks_enabled == false` should imply `provision? == false`).
