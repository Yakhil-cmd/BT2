### Title
Multisig transaction payload substitution bypasses admission control when `abort_if_multisig_payload_mismatch` feature is not enabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the VM-invoked prologue/admission check for multisig-account transactions, only verifies that the payload supplied at execution time matches the payload that owners actually voted on when a feature flag (`features::abort_if_multisig_payload_mismatch_enabled()`) is turned on. For transactions created via `create_transaction` (the common path, which stores the full payload on-chain rather than a hash), if that flag is disabled the admission check silently skips payload matching entirely, allowing the executing owner to substitute an arbitrary different payload for the one that received quorum approval.

### Finding Description
`create_transaction` stores the full payload on-chain and leaves `payload_hash` as `None`: [1](#0-0) 

The VM-only admission function `validate_multisig_transaction` — documented as being "called by the VM as part of transaction prologue, which is invoked during mempool transaction validation and as the first step of transaction execution" — performs two separate payload-binding checks: [2](#0-1) 

1. If `transaction.payload_hash.is_some()` (the `create_transaction_with_hash` path), the provided payload's SHA3-256 hash is asserted equal to the stored hash — this binding always holds.
2. If `transaction.payload.is_some()` (the `create_transaction` path, where the full payload was stored and approved by owners), the match between the provided execution payload and the stored, voted-on payload is only asserted **when `features::abort_if_multisig_payload_mismatch_enabled()` returns true**.

Since quorum approval (`approve_transaction`/`vote_transanction`) is recorded against the *stored* `transaction.payload` (and its content is what owners see and vote on off-chain via `payload_hash`-less transactions or via viewing the stored payload), there is no cryptographic binding forcing the payload actually executed by the VM to equal the one approved, unless that specific feature is enabled. This is the same class of bug as the audit seed report — a value the admission layer should treat as authoritative (`_loan.protocolFee` / approved payload) is bypassed in favor of an unchecked, attacker/caller-supplied value (current `protocolFee.fraction` / execution-time `payload` argument) — because the "use the recorded, approved value" check is conditionally gated rather than unconditional.

### Impact Explanation
If `abort_if_multisig_payload_mismatch` is not enabled on a given chain/network (or during any window before it is activated), an executing owner of a multisig account can call the entry point that drives `validate_multisig_transaction` with a payload different from the one that other owners approved via `create_transaction`, and the VM will accept and execute that unauthorized payload as though it had quorum approval. This is a direct violation of the "approval validation accepting the wrong approval set" admission invariant: the transaction that executes and commits is not the one that was actually voted on/authorized by the owner set.

### Likelihood Explanation
Likelihood depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active in the target deployment. The presence of a dedicated feature flag whose sole purpose is to enable this exact payload-match assertion strongly suggests it was added later as a fix/hardening for previously-unchecked payload binding, implying there was (and, on any environment where the flag remains off, still is) a window where this mismatch is entirely unchecked for `create_transaction`-created multisig transactions. I could not verify the current default/activation state of this specific feature flag on mainnet within the available searches, so likelihood should be treated as uncertain pending confirmation of the flag's rollout status.

### Recommendation
Make the payload match assertion for `transaction.payload.is_some()` unconditional (not gated behind `abort_if_multisig_payload_mismatch_enabled`), mirroring the unconditional hash check already used for the `payload_hash` path, so a stored full payload is always authoritative and cannot be substituted regardless of feature-flag state.

### Proof of Concept
1. Multisig account with owners A, B, C, threshold 2.
2. Owner A calls `create_transaction(owner=A, multisig_account, payload=P1)` — `P1` is stored fully on-chain (`payload_hash = None`).
3. Owner B reviews `P1` (e.g., "transfer 1 APT to X") and calls `approve_transaction`, bringing approvals to 2/3.
4. On a network where `abort_if_multisig_payload_mismatch_enabled()` is false, the executing owner submits the multisig-transaction entry function with a *different* payload `P2` (e.g., "transfer 1000 APT to attacker").
5. In `validate_multisig_transaction`, `transaction.payload_hash.is_some()` is false (skipped), and the `abort_if_multisig_payload_mismatch_enabled()` gate is false, so the `payload == *stored_payload` check at [3](#0-2)  is never executed.
6. The VM proceeds to execute `P2` even though only `P1` received quorum approval, committing an unauthorized state transition.

Note: this PoC's real-world exploitability hinges on the activation status of `abort_if_multisig_payload_mismatch_enabled`, which I was unable to fully confirm in this pass — a Devin session with repo-wide search/build access should verify the flag's current default and rollout status before treating this as exploitable on a live network.

        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.

            && transaction.payload.is_some()
            && !payload.is_empty()

            let stored_payload = transaction.payload.borrow();
