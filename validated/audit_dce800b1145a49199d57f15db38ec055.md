### Title
Webhook signature verification is keyed to `repository.owner.login`, but repository resolution/action is keyed to the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the inbound HMAC signature against using `repository.owner.login` (or `organization.login`) from the JSON body, but every `Webhooks::Handlers::Handler` subclass (used to look up the `Repository`/`Stack` to act on) reads a *different* field, `repository.full_name`, without ever cross-checking that it belongs to the same owner that was cryptographically verified.

### Finding Description
`verify_signature` computes the trust anchor for the whole request from one field: [1](#0-0) [2](#0-1) 

The signature check itself trivially returns `true` whenever the resolved `GithubApp` has no `webhook_secret` configured, which the setup docs explicitly describe as *optional*: [3](#0-2) [4](#0-3) 

Meanwhile, every handler resolves the `Repository`/`Stack` that will actually be mutated from a completely different JSON field — `repository.full_name` — with no relationship enforced back to `repository.owner.login`: [5](#0-4) [6](#0-5) 

Concretely, `PushHandler` triggers a stack sync for whatever stacks match `full_name`+branch: [7](#0-6) 

`CheckSuiteHandler` schedules check-run refreshes for whatever stack matches `full_name`: [8](#0-7) 

`PullRequest::ClosedHandler` archives a review stack for whatever repository matches `full_name`: [9](#0-8) 

Multiple GitHub Apps (one per organization) can be configured simultaneously, each independently deciding whether to set a `webhook_secret`: [10](#0-9) 

This exactly parallels the report's bug class: a field that gates the trust decision (`nftInfos[tokenId]` existence / `powerCalcStartTimestamp` in the analog; here, `repository.owner.login` used to pick the verifying secret) is never actually the field that the state-changing logic operates on (`newPower`/`totalPower` in the analog; here, `repository.full_name` used to find the `Repository`/`Stack` to mutate). The equality that should hold — "the organization whose signature was verified == the repository whose stacks/state are written" — is never enforced.

**Attack path:** if the deployment configures multiple GitHub organizations and any one of them (`OrgA`) has no `webhook_secret` set (an explicitly documented "optional" setting), an unauthenticated attacker can POST directly to `/webhooks` with `X-Github-Event: push` (or `check_suite`, `pull_request`, etc.) and a body where `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`, satisfying `verify_signature`, which auto-passes because `webhook_secret` is blank) while `repository.full_name = "OrgB/private-repo"` — an entirely unrelated, secret-protected organization's repository. Because handlers only ever consult `full_name`, this forged, unsigned-for-OrgB payload triggers real state changes (`GithubSyncJob` deploy-branch syncs, check-run refresh scheduling, `ReviewStack#archive!`) against `OrgB`'s stacks despite never having proven authenticity for `OrgB`.

### Impact Explanation
This breaks the intended per-organization authentication boundary and yields cross-repository writes: an attacker with knowledge of only one (possibly secret-less) org's webhook configuration can drive stack sync jobs, review-stack archival, and check-run refresh for stacks belonging to a completely different, properly-secured organization, without ever supplying a valid signature for that organization. This matches the "Critical - cross-repository writes" impact bar.

### Likelihood Explanation
Requires: (a) a multi-org Shipit deployment (explicitly documented and supported), and (b) at least one configured organization operating with `webhook_secret` unset (explicitly documented as optional). Given no other prerequisite (no session, no `ApiClient` token, no repository access) is needed to reach `WebhooksController#create`, this is exploitable by any unauthenticated network attacker once that documented, permitted configuration exists.

### Recommendation
After resolving `repository_owner` for signature verification, also derive/require that `repository.full_name`'s owner segment matches `repository_owner` (and `organization.login`, where present) before dispatching to handlers; reject the payload with `422` otherwise. Handlers should not resolve `Repository`/`Stack` purely from an unauthenticated payload field independent of the field used to select the verifying secret.

### Proof of Concept
Given a `config/secrets.yml` with two orgs, `OrgA` (no `webhook_secret`) and `OrgB` (secret configured, hosting the real target stack):

```
POST /webhooks HTTP/1.1
X-Github-Event: push

{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/private-repo"
  }
}
```
`verify_signature` looks up `Shipit.github(organization: "OrgA")`, finds no `webhook_secret`, and `verify_webhook_signature` short-circuits to `true` regardless of any `X-Hub-Signature` header. `PushHandler#stacks` then resolves `Repository.from_github_repo_name("OrgB/private-repo")` and enqueues `GithubSyncJob` for its stacks — a write action against `OrgB` that was never authenticated for `OrgB`.     def verify_signature
```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
```
