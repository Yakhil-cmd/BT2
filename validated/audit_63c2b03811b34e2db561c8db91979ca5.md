### Title
`StatusHandler` fires cross-repository status/deployable_status hooks by matching commit SHA globally, without scoping to the reporting repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves affected commits with a global `Commit.where(sha: params.sha)` query instead of scoping through `stacks` (which is derived from `payload.dig('repository', 'full_name')`), unlike every sibling handler (`PushHandler`, `CheckSuiteHandler`). This means a validly-signed `status` webhook from *any* GitHub organization/repository that has the Shipit GitHub App installed can update the status, and trigger `commit_status`/`deployable_status` `Hook.emit` calls, for a commit belonging to a completely unrelated stack, as long as the sha matches.

### Finding Description
The broken binding: the question's implicit invariant is `payload.repository.full_name == commit.stack.repository.full_name` (i.e., a webhook should only mutate commits belonging to the reporting repository). This invariant is enforced in `PushHandler#process` (`stacks.not_archived.where(branch:)`) and `CheckSuiteHandler#process` (`stacks.where(branch: ...).each { stack.commits.where(sha: ...) }`), both of which derive `stacks` from `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` using `payload.dig('repository', 'full_name')` [1](#0-0) .

`StatusHandler#process`, however, never calls `stacks` at all:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This queries the `commits` table across **every stack in the Shipit instance**, matching purely on `sha`, with no `repository`/`stack` filter. `Commit#create_status_from_github!` calls the private `add_status`, which yields to `statuses.replicate_from_github!(stack_id, github_status)`, then emits `Hook.emit(:commit_status, stack, ...)` and, on a meaningful state transition, `Hook.emit(:deployable_status, stack, ...)` — using the *commit's own* `stack` (the victim stack), not the reporting repository's stack [3](#0-2) .

Root cause: git commit SHAs are content-addressed and not scoped to a single repository. The same commit object (e.g. a shared library commit, a commit from a common upstream, a cherry-picked/rebased commit that happens to produce the same tree+metadata, or simply a commit that exists in two repositories tracked by two different Shipit stacks) can legitimately exist as a row in `commits` for multiple different stacks belonging to different repositories/organizations, since `commits` is only uniquely indexed on `(stack_id, sha)` [4](#0-3) , not globally unique on `sha`.

Attack flow:
1. Attacker controls (or has push/CI access to) any repository in any GitHub organization that has the Shipit GitHub App installed (this is the only "binding" — `verify_signature` only checks that the HMAC signature matches the GitHub App secret for `repository_owner`, i.e., that *some* org's app sent it — it does not check that the sha/commit belongs to that org) [5](#0-4) .
2. Attacker triggers (via their own CI, or a custom GitHub status API call within their own authorized repo) a `status` event with an arbitrary `state` and a `sha` value equal to a commit sha that they know exists in a victim stack (commit shas are visible in the victim's public UI/API, PRs, or git history — no secret required).
3. GitHub signs and forwards this webhook using the attacker's own org's app secret; `verify_signature` passes because it is checking against the attacker's own organization, which is legitimate.
4. `StatusHandler#process` runs `Commit.where(sha: <attacker-chosen sha>)`, finds the victim's `Commit` row (unrelated stack), and calls `create_status_from_github!` on it, causing `Hook.emit(:commit_status, victim_stack, ...)` and potentially `Hook.emit(:deployable_status, victim_stack, ...)` to fire against the victim stack's configured webhook URLs, with attacker-controlled `state`/`description`/`context`/`target_url` fields.

Why existing guards fail: `verify_signature` authenticates *which organization* sent the webhook, not *which repository/stack the payload's sha is allowed to affect*; the `ExplicitParameters` schema in `StatusHandler` only validates types, not ownership; `drop_unhandled_event` and `force_github_authentication` are irrelevant here since this is an unauthenticated-by-design webhook endpoint gated only by signature; there is no `stacks` scoping call as used elsewhere in the same module.

### Impact Explanation
An attacker who controls any repository whose org has the Shipit app installed can, per request, forge a status transition (e.g. `unknown -> success` or `success -> failure`) on any commit sha they can discover in any other stack in the same Shipit instance, and trigger that victim stack's `commit_status`/`deployable_status` outgoing webhooks with attacker-influenced `state`/`description`/`context` data — a payload from one repository mutating another repository's stack/commit state and causing side effects (outbound hook delivery to internal endpoints, and `stack.schedule_merges` being enqueued via `ProcessMergeRequestsJob` when the forged state is `pending`/`success`) [6](#0-5) . This is repeatable against arbitrary stacks/commits within the same Shipit instance, satisfying the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: (a) the attacker needs access to any repository in an org that has the Shipit GitHub App installed (this may be a broad set in multi-tenant Shipit deployments serving many orgs/teams); (b) the attacker needs to know a target commit sha belonging to the victim's stack, which is typically discoverable via GitHub (commit shas are not secrets); (c) the victim stack must have a `commit_status`/`deploy_status` hook configured, as stated in the question's preconditions. Attacker cost is low — sending a real GitHub status event from an owned repo (or directly crafting the request if they can get any valid signature for some org, which GitHub does for real events). This is feasible without any Shipit credentials, session, or secrets.

### Recommendation
Scope `StatusHandler#process` through the reporting repository, matching the pattern used by `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restricts the searched/mutated commits to stacks belonging to `payload.dig('repository', 'full_name')`, restoring the `payload.repository.full_name == commit.stack.repository.full_name` invariant that every other handler already enforces.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_test.rb (new)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status event from repo A does not mutate a commit belonging to repo B's stack" do
          victim_stack = shipit_stacks(:shipit) # e.g. repo "shopify/shipit-engine"
          attacker_stack = shipit_stacks(:cyclimse) # different repository/org, e.g. "attacker/other-repo"

          victim_commit = victim_stack.commits.create!(sha: 'a' * 40, author: shipit_users(:walrus), authored_at: Time.now, committer: shipit_users(:walrus), committed_at: Time.now)

          payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'ci/travis',
            'created_at' => Time.now.to_s,
            'repository' => { 'full_name' => attacker_stack.repo_name }, # attacker's own repo, correctly signed
          }

          expect_no_hook(:commit_status) do
            expect_no_hook(:deployable_status) do
              StatusHandler.call(payload)
            end
          end

          assert_equal 'unknown', victim_commit.reload.state
        end
      end
    end
  end
end
```
Before the fix, this test fails: `StatusHandler#process`'s `Commit.where(sha: params.sha)` matches `victim_commit` regardless of `payload['repository']['full_name']`, `Hook.emit(:commit_status, victim_stack, ...)` fires, and `victim_commit.state` becomes `success`. After scoping via `stacks` (derived from `attacker_stack`'s repository), the victim's commit is not found/mutated and no hook fires, matching every other handler's behavior.
