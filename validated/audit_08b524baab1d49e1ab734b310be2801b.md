### Title
Cross-organization webhook forgery: signature-verified organization vs. the repository/commit actually written - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification purely from attacker-supplied JSON in the unauthenticated request body: `repository_owner` is read via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and that string is passed to `Shipit.github(organization: repository_owner)` to pick the secret to verify against. [1](#0-0) [2](#0-1) 

Once the signature check passes (using whichever org's secret matched the attacker-chosen `owner.login`/`organization.login` value), the actual event handlers never re-check that the payload's operative fields belong to the same organization/repository that was authenticated. In particular, `StatusHandler` looks up commits purely `Commit.where(sha: params.sha)` — globally, across all stacks/repositories in the Shipit instance — and directly persists a `Status` from attacker-controlled `state`/`context`/`description` fields, with no cross-check against `repository.full_name`, `repository_owner`, or the org whose secret validated the request: [3](#0-2) 

Similarly, `Webhooks::Handlers::Handler#stacks`/`#repository_name` and `PushHandler` resolve the target repository from `payload.dig('repository', 'full_name')` — a field independent of the `owner.login` field used for the signature/secret lookup: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to select the verification secret) and `repository.full_name` / `sha` (used by the handler to decide what to mutate) are two independently attacker-controlled JSON keys inside the same body, and GitHub App webhook secrets are per-organization and optional (`config[:webhook_secret].presence`), `verify_webhook_signature` trivially returns `true` for any body whenever the organization corresponding to the (attacker-chosen) `owner.login` has no `webhook_secret` configured: [6](#0-5) [7](#0-6) 

This breaks the intended binding: **organization whose secret authenticated the request == organization/repository whose state is written**. In a multi-organization Shipit deployment (`Shipit.github(organization:)` / `github_app_config`) where at least one configured organization has no webhook secret set, an attacker needs zero credentials to forge a webhook: set `X-Github-Event: status`, put the unsecured organization's login in `repository.owner.login`, and put the sha of any commit belonging to a *different, protected* organization's stack. The signature check passes trivially (no secret configured for the named org), and `StatusHandler` writes a forged `success` status for a target commit it never validated belongs to that org. [8](#0-7) 

### Impact Explanation
A forged `success`/passing status on an arbitrary commit can satisfy `Commit#deployable?` requirements (`required_statuses`, `ci.require`) and, for stacks with `continuous_deployment: true`, will directly trigger `ContinuousDeliveryJob` and an unattended deploy of that commit — as shown by the existing test demonstrating that creating a `success` status enqueues `ContinuousDeliveryJob` and creates a `Deploy`: [9](#0-8) [10](#0-9) 

This satisfies the "unauthorized deploy" Critical-impact criterion: an unauthenticated attacker can cause a legitimate, protected stack to deploy a commit whose CI status was never genuinely reported by GitHub for that repository.

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment (config keyed by organization, per `github_default_organization`/`github_app_config`), (2) at least one configured organization with no `webhook_secret` set — explicitly documented as "optional" — while another organization hosts the protected, continuously-deployed stack, and (3) the attacker knowing/guessing the sha of a commit in the target stack (visible on the public Shipit UI/API for that stack, or on GitHub if the repo is public). Given the documented optionality of `webhook_secret` per org and that this is purely a body-content trick (no signature forgery needed once the condition holds), this is a realistic misconfiguration-triggered vulnerability, analogous in structure to the referenced Olympus finding: a boundary check (`wallSpread_ > 10000` vs. `>=`) that fails to close an edge case allowing an attacker-reachable path to corrupt trusted state (price/beat) — here, a missing binding check that fails to tie the authenticated organization to the repository/commit actually mutated.

### Recommendation
- After `verify_signature` resolves `github_app`/organization from the payload, re-validate that `payload.dig('repository','owner','login')` matches `payload.dig('repository','full_name')`'s owner segment, and reject if they diverge.
- In every `Webhooks::Handlers::Handler` (especially `StatusHandler`), scope lookups by the verified organization/repository (e.g., join `Commit` through `Stack -> Repository` filtered by the repository confirmed during signature verification) instead of a global `Commit.where(sha:)`.
- Consider requiring `webhook_secret` to be present for every configured organization (fail closed) rather than allowing per-organization opt-out of signature verification.

### Proof of Concept
Preconditions: Shipit multi-org config has organization `unsecured-org` (no `webhook_secret`) and organization `victim-org` (has `webhook_secret`) with a stack whose `continuous_deployment` is `true` and a known undeployed commit `sha = abc123...` requiring `ci/required` status.

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "unsecured-org/some-repo"
  }
}
```
No `X-Hub-Signature` header (or an arbitrary one) is required, because `Shipit.github(organization: "unsecured-org")` resolves a `GitHubApp` with `webhook_secret` blank, so `verify_webhook_signature` short-circuits to `true`: [6](#0-5) 

`StatusHandler#process` then runs `Commit.where(sha: "abc123...")` unconditionally, matching the commit that actually belongs to `victim-org`'s stack, and calls `commit.create_status_from_github!(params)`, writing the forged `success` status and potentially triggering an unauthorized deploy via `schedule_continuous_delivery`. [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
