### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login`, while every handler dispatches on the unrelated, unverified `repository.full_name` field — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. All subsequent event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, all `PullRequest::*Handler`s, etc.) instead resolve the target `Stack`/`Repository` from a *different* field in the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Because the HMAC only proves "this body was signed with organization X's secret," not "the org whose secret signed this request is the org named in `repository.full_name`," an attacker who legitimately controls webhook delivery for one configured GitHub organization (knows that organization's `webhook_secret`) can craft a raw payload where `repository.owner.login`/`organization.login` names their own org (to pass signature verification) while `repository.full_name` names a *different* organization's repository configured on the same Shipit instance. This breaks the intended binding: `organization that authenticated == repository that is written`.

### Finding Description
- Signature check: `app/controllers/shipit/webhooks_controller.rb` lines 24-30 loads `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`, where `repository_owner` (line 59-62) is read straight from the untrusted JSON body:
  ```ruby
  def repository_owner
    params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
  end
  ``` [1](#0-0) [2](#0-1) 

- `verify_webhook_signature` (in `lib/shipit/github_app.rb`) is a pure HMAC-SHA1 comparison against the raw body using the secret configured for whichever organization `repository_owner` names:
  ```ruby
  def verify_webhook_signature(signature, message)
    return true unless webhook_secret
    algorithm, signature = signature.split("=", 2)
    return false unless algorithm == 'sha1'
    SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
  end
  ``` [3](#0-2) 
  This only proves the *whole body* was signed with that organization's secret — it does not constrain any individual field's value, including `repository.full_name`.

- Dispatch/target resolution: once signature verification passes, `create` forwards the full parsed body to every handler for the event:
  ```ruby
  def create
    params = JSON.parse(request.raw_post)
    Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
    head(:ok)
  end
  ``` [4](#0-3) 
  The base `Handler` (and every concrete handler such as `PushHandler`, `StatusHandler`, `PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) determine the repository/stack to act on from a wholly different field:
  ```ruby
  def stacks
    @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
  end

  def repository_name
    payload.dig('repository', 'full_name')
  end
  ``` [5](#0-4) 
  `PushHandler#process` then directly syncs the resolved stack from the (attacker-chosen) `after` sha: [6](#0-5) 
  `StatusHandler#process` writes a commit status onto any local `Commit` matching the attacker-supplied `sha`, independent of which repo it belongs to, taken verbatim from the body: [7](#0-6) 

Because `repository_owner` (used for auth) and `repository.full_name` (used for target resolution) are never cross-checked, this is an equality violation of the form:
**`organization whose secret authenticated the request` ≠ `repository/stack the handler actually writes to`.**

In a multi-tenant Shipit deployment (`config/secrets.*.yml` supports keying by multiple GitHub orgs, e.g. `secrets.development.shopify.yml`), any organization admin who has installed the Shipit GitHub App on their own org (and therefore knows their own `webhook_secret`) can sign an arbitrary payload with their own secret while setting `repository.full_name` to point at a repository owned by a *different* configured organization, and have Shipit act on that other organization's stack.

### Impact Explanation
This is a cross-repository write: an attacker who is only authorized for organization A's webhook delivery can forge events that mutate state belonging to organization B's stacks, e.g.:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` on a foreign stack with an attacker-chosen sha.
- `StatusHandler` calls `commit.create_status_from_github!(params)`, writing arbitrary CI status (`state`, `context`, `description`, `target_url`) onto commits of a foreign stack — which can be used to falsify CI check results Shipit relies on (`ci.require`) to gate deploys, potentially enabling an unauthorized deploy by a legitimate user of the victim organization who trusts the (forged) green status.
- `PullRequest::*Handler`s can archive/unarchive/create review stacks belonging to the foreign organization.

This matches the "Critical — cross-repository writes / unauthorized deploy" and "High — unauthenticated action on stack state" impact classes.

### Likelihood Explanation
Requires only that the attacker (a) run/administer a GitHub organization that is legitimately configured as a tenant on the same Shipit instance (so they know that org's `webhook_secret`), and (b) the instance be configured for multiple organizations (as explicitly supported by `config/secrets.development.shopify.yml` and `Shipit.github(organization:)`). No GitHub App private key, no `api_clients_secret`, no session, and no privileged Shipit account is needed — only a raw HTTP POST to `/webhooks` with a crafted JSON body and correctly computed `X-Hub-Signature` header.

### Recommendation
Bind the field used for signature-key selection to the field used for target resolution. Concretely, after computing `repository_owner`, re-validate that `Repository.from_github_repo_name(payload.dig('repository','full_name'))` belongs to the same organization used to select the webhook secret (e.g. compare the repository's owner/org against `repository_owner`), and reject the request (422) on mismatch, before dispatching to any handler. Alternatively, have handlers resolve the repository strictly from data already authenticated by that same organization's webhook secret rather than trusting `repository.full_name` independently of `repository.owner.login`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an attacker who administers `OrgA` (and thus knows `OrgA`'s `webhook_secret`), craft a `push` payload body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner == "OrgA"`, loads `OrgA`'s secret, and the signature matches → request passes.
6. `PushHandler#process` resolves the target stack via `payload.dig('repository','full_name') == "OrgB/victim-repo"` and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `OrgB`'s stack — despite the request never having been authenticated with `OrgB`'s secret.
