### Title
Bridge ERC20 Transfer Uses Caller-Supplied Amount Without Verifying Actual Received Balance — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge's `requestERC20Transfer` and `onERC20Received` functions accept a caller-supplied `_value` and emit a `RequestValueTransfer` event with that exact amount, without measuring the actual token balance change in the bridge contract. For fee-on-transfer ERC20 tokens, the bridge receives fewer tokens than `_value + _feeLimit`, yet the counterpart bridge is instructed to release the full `_value`. This drains the bridge's liquidity pool over time, making it unable to fulfill legitimate withdrawals.

---

### Finding Description

**Two-step path (`requestERC20Transfer`):**

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge calls `safeTransferFrom` for `_value + _feeLimit`, then immediately passes the caller-supplied `_value` into `_requestERC20Transfer`. If the token deducts a transfer fee, the bridge receives `(_value + _feeLimit) * (1 - r)` where `r` is the fee rate. The bridge's actual balance is `_value * (1 - r)` after the internal fee/refund accounting in `_payERC20FeeAndRefundChange`, but the emitted `RequestValueTransfer` event carries `_value`.

**One-step path (`onERC20Received` via `ERC20ServiceChain.requestValueTransfer`):**

```solidity
// ERC20ServiceChain.sol L44-47
function requestValueTransfer(uint256 _amount, address _to, uint256 _feeLimit, bytes calldata _extraData) external {
    require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
    IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
}
``` [2](#0-1) 

The token transfers `_amount + _feeLimit` to the bridge (bridge receives less due to fee), then calls `onERC20Received` with the original `_amount`. The bridge trusts this caller-supplied value.

**`_payERC20FeeAndRefundChange` also uses nominal amounts:**

```solidity
// BridgeFee.sol L68-88
function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
    uint256 fee = feeOfERC20[_token];
    ...
    IERC20(_token).safeTransfer(feeReceiver, fee);
    ...
    IERC20(_token).safeTransfer(from, feeRefund);
``` [3](#0-2) 

These outbound transfers also lose tokens to the fee, compounding the shortfall.

**Counterpart bridge releases the full `_value`:**

```solidity
// BridgeTransferERC20.sol L68-72
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [4](#0-3) 

The counterpart bridge mints or transfers the full `_value` to the recipient, regardless of how much was actually locked on the source chain.

---

### Impact Explanation

**Lock/unlock mode (non-`modeMintBurn`):** The source bridge holds `_value * (1 - r)` tokens but has committed to releasing `_value` tokens on the counterpart chain. Each bridging transaction creates a shortfall of `_value * r`. Repeated use drains the bridge's liquidity pool, causing legitimate withdrawal requests to fail (bridge insolvency). This is an unauthorized unlock of bridged assets on the counterpart chain.

**Mint/burn mode:** The burn of `_value` from the bridge's balance would revert because the bridge only holds `_value * (1 - r)` after receiving the fee-reduced transfer. This path self-protects via revert, but the lock/unlock path does not.

The corrupted value is: `counterpart_released = _value` vs `source_locked = _value * (1 - r)`. The difference `_value * r` is an unearned cross-chain credit per transaction.

---

### Likelihood Explanation

- Any user can call `requestERC20Transfer` or `requestValueTransfer` on any registered token.
- Token registration is controlled by the bridge owner, but tokens can be upgraded post-registration to add transfer fees (e.g., upgradeable proxy tokens).
- Some legitimate tokens (e.g., certain DeFi tokens, reflection tokens) natively implement transfer fees.
- No guard exists in the bridge to detect or reject fee-on-transfer tokens.
- The attack is passive: any normal user of a fee-on-transfer token inadvertently drains the bridge; a malicious actor can accelerate it by repeatedly bridging.

---

### Recommendation

Measure the actual balance change instead of trusting the caller-supplied `_value`:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived >= _value.add(_feeLimit), "fee-on-transfer token not supported");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Alternatively, explicitly document and enforce that only non-fee-on-transfer tokens may be registered, and add a validation check in `registerToken`.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token with a 5% transfer fee.
2. Register the token with the source-chain bridge (owner action, or assume it was registered before the fee was added via upgrade).
3. User calls `requestERC20Transfer(token, recipient, 1000, 0, "0x")`.
4. Bridge calls `safeTransferFrom(user, bridge, 1000)` — bridge receives 950 tokens (5% fee deducted).
5. `_payERC20FeeAndRefundChange` runs with `_feeLimit=0`, no fee/refund transfers.
6. Bridge holds 950 tokens. `RequestValueTransfer` event emitted with `valueOrTokenId = 1000`.
7. Counterpart bridge operators call `handleERC20Transfer(..., 1000, ...)`.
8. Counterpart bridge transfers 1000 tokens to recipient.
9. Net: source bridge lost 950 tokens, counterpart bridge released 1000 tokens. **50-token shortfall per transaction.**
10. After 19 such transactions, the source bridge is fully insolvent (950 × 20 = 19,000 locked, 1000 × 20 = 20,000 committed).
