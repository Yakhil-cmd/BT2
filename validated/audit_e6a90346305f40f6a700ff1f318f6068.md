## Analysis

The external report describes a bug class where an actor exploits **predictable ordering of two related transactions** to manipulate a ratio-based metric that is recomputed "live" at execution time, extracting value while restoring the metric to its original (safe) value once the second, larger transaction lands. The reachable analog in `ocore` is in the **Autonomous Agent (AA) trigger execution engine**, combined with the **sample AMM/bonding-curve AA cookbook** that ships with the repo, which computes reserve ratios from `balance[asset]` read at the moment each trigger executes.

AA triggers that become eligible in the same MCI are collected and executed in a **fully deterministic order**: `ORDER BY units.level, units.unit, address` [1](#0-0)  and the same ordering is used again when re-reading pending triggers in `handleAATriggers` [2](#0-1) . Because `level` is a property that the unit's own author controls (by choosing which free/eligible parent units to build on, before the unit and its trigger have stabilized), an attacker can compose their own trigger unit so that its `level` sorts strictly before (or after) a specific victim unit that is already visible on the DAG but not yet stable. This gives an unprivileged unit poster the ability to guarantee that their AA trigger is processed immediately before or after a target trigger to the same AA — the DAG analog of "front-running" a pending mempool transaction.

Any AA whose response/state-update formula computes value based on the *current* `balance[...]` of the AA (rather than a value fixed at trigger-composition time) is vulnerable to being sandwiched this way. The AMM sample shipped in the repo's cookbook demonstrates exactly this pattern: on `invest`/`exchange`, the ratio is computed as
```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
$current_ratio = $asset_balance / $bytes_balance;
``` [3](#0-2) , and `divest`/withdrawal is likewise priced off `balance[$asset]`/`balance[base]` at execution time [4](#0-3) . Because these balances are only known at the moment the primary trigger actually executes (post-stabilization), and because trigger execution order across pending units is attacker-influenceable via level selection, an attacker can:
1. Post a large "invest"/"divest" trigger ordered immediately before a victim's large trade, shifting `balance[asset]`/`balance[base]` to move `$current_ratio`/`$investor_share` in their favor.
2. Let the victim's trigger execute against the manipulated ratio.
3. Immediately reverse their own position with a second trigger ordered right after, restoring the AA's balances/ratio to (near) their original state — extracting the victim's slippage as profit while leaving the AA's externally-observable ratio unaffected, exactly mirroring the "restore metric to 1 while extracting value" pattern in the original report.

This is reachable by any address that can post units and send triggers to a deployed AA (no special privilege needed), and the root cause — deterministic, poster-influenceable ordering of same-MCI triggers feeding into balance-ratio formulas evaluated at execution time — is a structural property of `aa_composer.js`/`main_chain.js`, not specific to the sample script.

### Title
Sandwichable AA balance-ratio formulas due to poster-controllable, deterministic same-MCI trigger ordering - (File: aa_composer.js / main_chain.js)

### Summary
AA triggers that land in the same MCI are executed in a deterministic order keyed on `(level, unit, address)`, and `level` is chosen by the trigger's own author via parent selection before stabilization. Any AA whose payout/ratio formula reads `balance[asset]` at execution time (as in the shipped Uniswap-like market-maker AA) can be sandwiched: an attacker orders a manipulating trigger immediately before a victim's trigger and a reversing trigger immediately after, extracting value while restoring the AA's state to its prior ratio — the same "manipulate-then-instantly-restore" pattern described in the source report.

### Finding Description
`markMcIndexStable` inserts all AA triggers that become eligible in a stabilizing MCI with a fixed, computable ordering key `ORDER BY units.level, units.unit, address` [1](#0-0) , and `handleAATriggers` in `aa_composer.js` re-reads and executes them with the same ordering `ORDER BY aa_triggers.mci, level, aa_triggers.unit, address` [2](#0-1) . `level` is a DAG property that a unit's author determines when selecting parent units for their own unit, prior to that unit's MCI being finalized; an attacker who observes a not-yet-stable victim unit destined for an AA can craft a companion trigger unit with a level chosen to sort immediately before (or after) the victim's trigger in the same MCI's execution batch.

AA response/state-update formulas are evaluated using `balance[...]`/`var[...]` values current at the moment each trigger actually executes (see `executeStateUpdateFormula` and the `var`/`balance` opcode handling in `formula/evaluation.js` [5](#0-4) ), not values snapshotted when the trigger unit was composed. The bundled market-maker sample AA prices invests/divests purely from these live balances [6](#0-5) , so whichever trigger executes first sets the price for the one that executes next within the same MCI.

### Impact Explanation
An attacker who controls ordering of their own triggers relative to a victim's pending trigger can extract value from any AA whose payout formula depends on live balance ratios (AMMs, staking/pool-style AAs, share-issuance AAs), while restoring the AA's externally-visible state to its prior value — precisely negating any protocol-level incentive or penalty tied to that ratio, and causing direct fund loss to the sandwiched counterparty. This is an AA fund-loss / unauthorized value-extraction class of impact.

### Likelihood Explanation
Any address can post units and AA triggers; no elevated privilege or witness/hub role is required. Because DAG unit composition (parent/level selection) happens client-side before broadcast, and because stabilization batches process all currently pending triggers in a deterministic, computable order, a motivated attacker monitoring the DAG for large pending trades against ratio-based AAs (the exact deployment pattern demonstrated by the shipped cookbook AA) has a concrete, repeatable path to sandwich them.

### Recommendation
For AA templates and any core guidance around AA-based AMMs/pools, avoid pricing formulas that read live `balance[...]` mutable by other triggers processed in the same batch; instead, snapshot/commit to a price or use time/step-weighted averaging, minimum-output slippage checks (already partially present via bounce on `wrong ratio of amounts`), or oracle-based pricing decoupled from same-block balance changes. At the protocol level, consider giving AA authors a mechanism to require the trigger to be the sole primary trigger executing against them within an MCI window for economically sensitive formulas, and document the ordering guarantees (or lack thereof) of `level`-based trigger sequencing so AA developers do not assume attacker-independent ordering.

### Proof of Concept
1. Deploy the sample Uniswap-like market-maker AA (`test/samples/uniswap_like_market_maker.oscript`) with `$asset`/`base` reserves.
2. Attacker observes a victim's large "invest" or "exchange" unit on the DAG that references the AA but has not yet stabilized.
3. Attacker composes and broadcasts their own trigger unit choosing parents so its `level` sorts before the victim's unit for the same forthcoming MCI, sending a large one-sided deposit that skews `$current_ratio`/`$p` computed from `balance[$asset]`/`balance[base]` [7](#0-6) .
4. Once the MCI stabilizes, `handleAATriggers`/`markMcIndexStable` execute the attacker's trigger first per the deterministic ordering [2](#0-1) , moving the price against the victim's trigger, which executes next in the same batch.
5. Attacker composes a third trigger (again level-ordered to execute right after the victim's) to divest/exchange back, restoring reserves to close to the pre-attack ratio while pocketing the victim's slippage — mirroring the original report's "manipulate then instantly restore" exploit.
