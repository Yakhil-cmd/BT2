### Title
Unset accumulator makes `claim_revenue` permanently revert until governance intervention - (File: `contracts/controller/src/markets.rs`)

### Summary
The controller constructor does not initialize the revenue accumulator, while the permissionless `claim_revenue` path requires `ControllerKey::Accumulator` to already exist. Any caller calling `claim_revenue(caller, assets)` before `set_accumulator` executes receives `OracleError::NoAccumulator`, so accrued protocol revenue cannot be moved to its intended destination. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Controller::__constructor(admin)` initializes ownership, position limits, the minimum borrow collateral floor, the app version, and the paused flag, but it accepts no accumulator argument and never calls `config::registry::set_accumulator`. [4](#0-3) [1](#0-0) 

The public interface exposes `claim_revenue(caller, assets)` without an administrative restriction, and the implementation authorizes `caller` before processing each supplied `HubAssetKey`. [5](#0-4) [6](#0-5) 

For the first asset, `claim_revenue_for_asset` reads `storage::try_get_accumulator` and immediately panics with `OracleError::NoAccumulator` when the instance-storage entry is absent. [3](#0-2) [7](#0-6) 

Because the accumulator lookup precedes `pool_claim_revenue_call`, the entire transaction reverts before any revenue is burned or transferred. [8](#0-7) [9](#0-8) 

### Impact Explanation
This causes temporary freezing of unclaimed protocol yield: positive revenue remains claimable in pool accounting, but every unprivileged `claim_revenue` call reverts until governance sets the missing address. [8](#0-7) [10](#0-9) 

The accumulator can only be initialized through the administrative `set_accumulator` entrypoint, so users cannot resolve the condition themselves through the affected entrypoint. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
The deployment sequence can omit `set_accumulator` because the constructor neither requires nor validates that address. [4](#0-3) [1](#0-0) 

Once a market has accrued claimable revenue, any single authorized caller can trigger the revert by submitting `claim_revenue` with that market's `HubAssetKey`. [2](#0-1) [3](#0-2) 

### Recommendation
Pass the accumulator into `Controller::__constructor`, validate it as part of initialization, and store it before markets can be used. [4](#0-3) [1](#0-0) 

Alternatively, atomically require the accumulator in the same initialization/configuration operation that activates the controller and reject activation while `ControllerKey::Accumulator` is absent. [13](#0-12) [12](#0-11) 

### Proof of Concept
1. Deploy the controller with `Controller::__constructor(admin)`; this writes ownership, position limits, borrow floor, app version, and paused state, but not `ControllerKey::Accumulator`. [4](#0-3) [1](#0-0) 
2. Configure a market and let it accrue positive claimable revenue, which `pool_claim_revenue_call` would otherwise burn and pay to the controller. [10](#0-9) 
3. As an unprivileged caller, invoke `claim_revenue(caller, vec![HubAssetKey { hub_id, asset }])` with a valid caller authorization. [5](#0-4) [2](#0-1) 
4. The call panics at the unset `ControllerKey::Accumulator` lookup with `OracleError::NoAccumulator`, before the pool claim or accumulator transfer executes. [8](#0-7) [13](#0-12)

/// Returns the instance accumulator address, or `None` when unset.
pub(crate) fn try_get_accumulator(env: &Env) -> Option<Address> {

/// Stores the accumulator address in instance storage.
pub(crate) fn set_accumulator(env: &Env, addr: &Address) {
    env.storage()
        .instance()
        .set(&ControllerKey::Accumulator, addr);
