## Title
AA payments can permanently lock restricted-transfer assets (`cosigned_by_definer`, `spender_attested`, `is_transferrable:false`) because `aa_composer.js` never checks these asset properties before building outgoing payments - ([File: aa_composer.js])

### Summary
Obyte's asset model lets an asset definer attach transfer-time restrictions that are conceptually equivalent to an SPL token's freeze authority: `cosigned_by_definer` (every transfer must be co-signed by the definer address), `spender_attested` (every payee must be on an attestor whitelist), and `is_transferrable:false` (transfers are only allowed to/from the definer). These conditions are enforced in `validation.js`'s `validatePaymentInputsAndOutputs`, but Autonomous Agents that accept and later forward arbitrary assets (a very common pattern - vaults, exchanges, "trading pools" that echo back collateral/deposits) never check these flags before constructing their outgoing payment messages in `aa_composer.js`.

### Finding Description
When an AA sends a payment in a non-base asset, `aa_composer.js`'s `sendUnit`/`completePaymentPayload` path only inspects two asset properties before composing the message: [1](#0-0) 
```
storage.loadAssetWithListOfAttestedAuthors(conn, asset, mci, [address], true, function (err, objAsset) {
    ...
    if (objAsset.fixed_denominations) // will skip it later
        return cb();
    if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs
        return cb("sending private asset from AA");
    completePaymentPayload(payload, 0, function (err) { ... });
});
```
It never checks `objAsset.cosigned_by_definer`, `objAsset.spender_attested`, or `objAsset.is_transferrable`. Those properties are only enforced later, at consensus-validation time in `validation.js`, when the response unit is validated: [2](#0-1) 
```
if (!objAsset.is_transferrable){ // the condition holds for issues too
    if (arrInputAddresses.length === 1 && arrInputAddresses[0] === objAsset.definer_address
       || arrOutputAddresses.length === 1 && arrOutputAddresses[0] === objAsset.definer_address
       ...
    ) { /* good */ }
    else
        return callback("the asset is not transferrable");
}
async.series([
    function(cb){
        if (!objAsset.spender_attested) return cb();
        storage.filterAttestedAddresses(conn, objAsset, objValidationState.last_ball_mci, arrOutputAddresses,
            function(arrAttestedOutputAddresses){
                if (arrAttestedOutputAddresses.length !== arrOutputAddresses.length)
                    return cb("some output addresses are not attested");
                cb();
            });
    },
    ...
], callback);
```
and cosign enforcement in `validatePayment`: [3](#0-2) 
```
if (objAsset.cosigned_by_definer && arrAuthorAddresses.indexOf(objAsset.definer_address) === -1)
    return callback("must be cosigned by definer");
```
Because an AA response unit is single-authored by the AA address (`objUnit.authors = [{ address: address }]`, see `aa_composer.js` line 1374), an AA can *never* satisfy `cosigned_by_definer` on its own (it cannot co-sign with an external definer address), and can only satisfy `spender_attested`/`is_transferrable:false` if the recipient happens to already be attested/the definer - conditions the AA has no way to guarantee for arbitrary trigger senders.

Any unprivileged user can define such an asset (`validateAssetDefinition` in `validation.js` only enforces internal consistency of these flags, not that an AA-receiving asset is well-behaved), then send it as a "deposit"/"collateral" to any AA that accepts and later echoes/refunds/repays that asset (a pattern used throughout the codebase's own AA samples, e.g. `test/samples/a_bank_without_percent.oscript`, `test/samples/sell_asset_for_bytes.oscript`, `test/samples/bouncer_infinite_cycle.oscript`, `test/samples/fundraising_proxy.oscript`, all of which build payment outputs back to `trigger.address` for whatever asset was received, mirroring exactly the pattern in `aa_composer.js`).

When the AA subsequently tries to build the response payment, `aa_composer.js` composes an output back to the depositor without any of these checks, and the resulting unit either:
- fails `validation.js`'s checks and is rejected, or
- triggers the AA's own bounce fallback, which reuses the same unchecked `sendUnit`/`completePaymentPayload` path (`bounce()` at `aa_composer.js` lines 910-945), so the bounce itself fails identically and `bBouncing` short-circuits to `finish(null)` — i.e., no response/refund unit is produced at all.

The deposited asset balance is already credited to the AA's on-chain address (the incoming trigger unit's payment was already validated and stable), but the AA can never again move it out, because the built-in restriction (functionally a "freeze") can't be satisfied by an autonomous, self-authored unit.

### Impact Explanation
Funds (arbitrary user-defined assets used as deposits/collateral/payment in any AA) become permanently locked inside the AA's address, unreachable by the depositor and by the AA's own logic, with no bounce/refund possible. This is exactly the class of harm described in the external report: an asset with (analog-of) "freeze" semantics renders an account/balance permanently unusable, hurting innocent counterparties (whoever deposited that asset into the AA) even though the AA's own code and consensus rules are each individually "correct" — the bug is the missing cross-check between AA-level asset acceptance and the definer-imposed transfer restrictions. Because this can affect any AA (widely used pattern of "accept any asset, echo/refund it"), and results in concrete, permanent loss of user funds with no recovery path, this rises to Medium/High severity, consistent with the judge's assessment in the referenced report (avoidable, rare but real fund-freezing condition).

### Likelihood Explanation
Likelihood is non-trivial but not universal: it requires (1) an asset definer to publish an asset with `cosigned_by_definer:true`, `spender_attested:true`, or `is_transferrable:false`, and (2) a victim (or the definer acting maliciously) to send that asset to an AA that forwards balances back to depositors without validating asset flags first. Given AA authors overwhelmingly do not filter incoming assets by these properties (as shown by the codebase's own sample AAs), and any user (not just privileged/protocol roles) can define such an asset and send it to a target AA, this is reachable by an ordinary AA-trigger sender / asset issuer acting alone.

### Recommendation
Before constructing any outgoing payment for a non-base asset, `aa_composer.js`'s `sendUnit`/`completePaymentPayload` logic (around `aa_composer.js` lines 1323-1330) should also inspect `objAsset.cosigned_by_definer`, `objAsset.spender_attested`, and `objAsset.is_transferrable`, and either:
- refuse to build a response with that asset (`bounce`/skip the message) when the AA cannot guarantee the transfer will validate (e.g., recipient not the definer for non-transferrable assets, `cosigned_by_definer` true, or recipient not attested for `spender_attested` assets), and/or
- document/require that AA authors explicitly opt into accepting such "restricted" assets, and provide oscript-level primitives (e.g., an asset-property getter) so AA logic can reject deposits of assets it cannot later move, before crediting them to AA state.

### Proof of Concept
1. Define an asset `A` with `cosigned_by_definer: true` (single-author-only requirement) via a standard `asset` message, per `validateAssetDefinition` in `validation.js`.
2. Send asset `A` to any deployed AA that accepts arbitrary assets and later attempts to pay them back to the sender (e.g. a bank/vault pattern like `test/samples/a_bank_without_percent.oscript`, or any DeFi-style AA implementing deposit/withdraw with an unrestricted asset parameter).
3. Trigger the AA's withdrawal/repay logic for asset `A`.
4. `aa_composer.js` builds the payment message for asset `A` without checking `cosigned_by_definer` (lines 1323-1330); the resulting single-author AA response unit is then rejected by `validatePayment` in `validation.js` ("must be cosigned by definer", lines 2112-2113), since the AA cannot co-sign with the definer.
5. The AA's `bounce()` fallback (`aa_composer.js` lines 910-945) attempts to refund via the same unchecked path and fails the same way; `bBouncing` prevents infinite retries and the response unit is never created (`finish(null)`).
6. Asset `A`'s balance remains permanently held at the AA's address with no code path able to move it out, freezing the depositor's funds.
