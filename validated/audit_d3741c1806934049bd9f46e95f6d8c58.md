## Analysis

The audit report's root cause — a protocol crediting/minting balances based on the **amount parameter passed to a transfer call** rather than the **amount actually received**, breaking accounting for fee-on-transfer (deflationary) tokens — has a direct structural analog in the Polkadot SDK's XCM `ERC20Transactor`. [1](#0-0) 

`withdraw_asset_with_surplus` calls the ERC20 contract's `transfer(checking_address, amount)` and, purely on seeing the ABI-decoded boolean return value `true` (no revert), unconditionally constructs an `Erc20Credit(amount)` and inserts it into the XCM holding register — it never checks the checking account's actual ERC20 balance delta: [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` blindly calls `transfer(beneficiary, amount)` from the checking account for the `amount` taken from the XCM asset descriptor/holding credit, again trusting only the boolean success return: [3](#0-2) 

This transactor is reachable by any signed user without privilege: it is wired into `AssetTransactors` on Asset Hub Westend and driven via `PolkadotXcm::execute` with a user-supplied XCM program: [4](#0-3) [5](#0-4) 

Critically, the `Matcher` that decides which contracts are ERC20-transactable via XCM (`ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`) accepts **any** `AccountKey20` location with no allowlist/governance gate: [6](#0-5) 

So any user can deploy their own (or use any existing) ERC20 contract — including one with fee-on-transfer/deflationary `transfer()` semantics (a legal, common real-world ERC20 pattern, exactly the bug class cited in the report) — and interact with it through this transactor.

### Title
XCM `ERC20Transactor` credits/moves the requested `amount` instead of the actual ERC20 balance delta, permanently freezing funds for fee-on-transfer tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` perform `IERC20::transfer` calls and treat the call as having moved exactly the passed `amount` whenever the contract returns `true`, without ever checking the counterpart account's actual balance change. For a fee-on-transfer/deflationary ERC20 (a legitimate ERC20 pattern, e.g. tokens that burn or redirect a fee on `transfer`), the checking account receives `amount - fee` on withdraw but the XCM executor's holding register is credited with the full `amount`.

### Finding Description
In `withdraw_asset_with_surplus`, the executor withdraws by transferring `amount` from the user to the shared `TransfersCheckingAccount`; on success it creates `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` [7](#0-6) . If the ERC20 contract implements a transfer fee, the checking account's real balance increase is `amount - fee`, but the holding register — and thus every subsequent XCM instruction operating on that holding (e.g. `DepositAsset`) — believes it holds the full `amount`.

When the corresponding `deposit_asset_with_surplus` later executes for that credited `amount`, it calls `transfer(beneficiary, amount)` from the checking account [8](#0-7) . Because the checking account only actually holds `amount - fee`, this second `transfer` reverts/fails at the ERC20 level (insufficient balance), which surfaces as `XcmError::FailedToTransactAsset` and aborts the deposit instruction. The already-withdrawn (real, fee-deducted) tokens sitting in the checking account become orphaned: the XCM executor's bookkeeping (and any resulting `AssetsTrapped` record) reflects the inflated `amount`, not the `amount - fee` actually recoverable, so a subsequent `ClaimAssets` attempt for the trapped assets will also fail (the checking account never has the inflated amount), permanently freezing the user's real tokens.

This is exactly the class of bug in the report: accounting is driven by the parameter passed to the transfer call, not the balance actually received/moved, and the fix pattern (record actual balance-before/balance-after deltas rather than the nominal `amount`) is identical to the audit's recommendation.

### Impact Explanation
Real user funds (ERC20 tokens legitimately transferred via XCM through `pallet-revive`) become permanently stuck whenever the underlying ERC20 implements any fee/burn/tax-on-transfer logic — a real-world token pattern, not a contrived edge case. This qualifies as irreversible freezing of user assets, which the assessment brief classifies as High-severity impact.

### Likelihood Explanation
Any user can trigger this by using an ERC20 contract with fee-on-transfer semantics through the permissionless `ERC20Matcher`/`IsLocalAccountKey20`, which accepts any `AccountKey20` location without registration or governance approval [6](#0-5) . No privileged role, governance action, or malicious validator/collator is required — only a normal signed `pallet_xcm::execute` extrinsic with a `withdraw_asset`/`deposit_asset` program referencing the fee-on-transfer contract, exactly as exercised by the existing `withdraw_and_deposit_erc20s` test harness [5](#0-4) .

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, snapshot the relevant account's actual ERC20 balance (via a `balanceOf` call or equivalent) before and after the `transfer` call, and credit/require the holding register with the measured delta rather than the nominal `amount` argument. Alternatively, reject assets whose `Matcher` cannot statically guarantee 1:1 transfer semantics (e.g., require an allowlist of vetted, non-fee-on-transfer ERC20 contracts rather than accepting any `AccountKey20`).

### Proof of Concept
Reproduction requires: (1) deploying a minimal ERC20 fixture (e.g., based on the existing `MyToken`/`MyTokenFake` fixtures already used in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`) whose `transfer()` deducts a fee before moving tokens but still returns `true`; (2) reusing the `withdraw_and_deposit_erc20s` test scaffold [5](#0-4)  to execute `withdraw_asset` + `deposit_asset` for that fee-charging token via `PolkadotXcm::execute`, and (3) asserting that the deposit step fails (`XcmError::FailedToTransactAsset("ERC20 contract transfer failed")`) while the checking account retains the fee-deducted real balance with no path to recover it via `ClaimAssets`. This reproduction was not executed in this session (no sandbox access); it is offered as the minimal integration test needed to confirm the finding, built entirely on the repository's existing fixture/test infrastructure referenced above.

		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

fn withdraw_and_deposit_erc20s() {

		// Fund all accounts involved.

		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),

		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
