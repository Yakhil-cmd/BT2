### Title
`provision?` operator precedence lets `allow_with_label`/`prevent_with_label` bypass `review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with the provisioning-behavior checks using `&&`/`||`, and Ruby's operator precedence only applies the `review_stacks_enabled &&` guard to the first disjunct (`provisioning_behavior_allow_all?`). The second and third disjuncts (`allow_with_label` and `prevent_with_label`) are evaluated independently of `review_stacks_enabled`, so a repository with `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` (or `prevent_with_label`) will still auto-provision a review stack for a PR that carries (or lacks) the configured label.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` is required for every branch of `provision?` that returns `true`. Tracing `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb` lines 65-69:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

In Ruby, `&&` binds tighter than `||`, so this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The `review_stacks_enabled` guard only applies to the `allow_all?` branch. If `review_stacks_enabled == false` and `provisioning_behavior == allow_with_label`, the PR still provisions as long as it carries the configured label — the binding does not hold for that branch. This is confirmed by `Shipit::Repository#provisioning_behavior_allow_with_label?` being a plain enum predicate with no dependency on `review_stacks_enabled`. [2](#0-1) 

`respond_to_pull_request_opened?` gates `process` only on `params.action == "opened" && provision?`; there's no other `review_stacks_enabled` check on this path. [3](#0-2) 

Attacker flow: an attacker who owns/controls a fork or branch of the target repo opens a PR against it and adds the label named in `repository.provisioning_label_name` to their own PR (label-adding requires only write access to their own PR/issue metadata on GitHub, which an outside contributor typically has on their own PR in many repo configurations, or via a repo they own that is nonetheless registered in Shipit). The webhook fires `pull_request.opened`, `provision?` evaluates true via the second disjunct, and `ReviewStackAdapter#create!` builds a new `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` from attacker-controlled data. [4](#0-3) 

The stack is then queued for provisioning (`Shipit::ReviewStackProvisioningQueue.add(stack)`), which eventually clones the attacker's branch and executes `shipit.yml`-defined provisioning commands via `TaskCommands`/`Command#start`/`PTY.spawn`, giving the attacker code execution using content from their own branch.

### Impact Explanation
This is Critical: a repository owner enabling `allow_with_label` (or `prevent_with_label`) provisioning without setting `review_stacks_enabled: true` unintentionally allows any contributor able to label a PR (or omit a label) to trigger automatic review-stack creation and provisioning, resulting in execution of attacker-supplied `shipit.yml`/provisioning commands on the deploy host — the "review stacks disabled" configuration provides no actual protection for these two behavior modes. The blast radius is scoped to that repository (per the `Repository#full_name` lookup), but it is repeatable for every PR/label event and for every repository configured this way.

### Likelihood Explanation
This requires the repository to have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` — a plausible but non-default operator misconfiguration (the intent of `review_stacks_enabled` as a master toggle is defeated). Given that misconfiguration, exploitation cost is trivial: open a PR and add/omit a label, both actions available to any contributor with issue/PR-label permissions on their own PR. This is a real code defect (operator-precedence bug) independent of attacker sophistication, but its exploitability is entirely conditional on this specific, non-default repository configuration.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to any sibling handlers with the same pattern (e.g., `reopened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb` — confirmed via grep results showing similar `provisioning_behavior` usage in those files) if they replicate this expression.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does NOT create stacks for allow_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert the binding both ways: before the fix, `Shipit::Stack.count` increases (violating `repository.review_stacks_enabled == false` implying no provisioning); after applying the recommended fix, `assert_no_difference` passes, confirming `review_stacks_enabled == false` blocks provisioning for all `provisioning_behavior` values, not just `allow_all`.
