### Title
Operator-precedence bug in `provision?` bypasses `review_stacks_enabled: false` for `prevent_with_label` repositories - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` combines four boolean terms with mixed `&&`/`||` without parentheses grouping the leading `review_stacks_enabled` check across all provisioning-behavior branches. Because Ruby's `&&` binds tighter than `||`, only the `allow_all` branch is gated by `review_stacks_enabled`; the `prevent_with_label` branch evaluates independently and returns `true` whenever the PR lacks the provisioning label, even if the repository owner disabled review stacks entirely.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == false` should imply `provision? == false` for all provisioning behaviors. Tracing the code: [1](#0-0) 

This parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. If `review_stacks_enabled = false` and `provisioning_behavior = 'prevent_with_label'` and the incoming PR carries no matching label, the third disjunct alone evaluates to `true`, making the whole expression `true` regardless of the first term.

`respond_to_pull_request_opened?` calls `provision?` directly and, if true, `process` calls: [2](#0-1) 

which invokes `ReviewStackAdapter#find_or_create!`, which calls `create!` when no stack exists yet: [3](#0-2) [4](#0-3) 

`create!` persists a new `ReviewStack` and enqueues it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`, which downstream triggers actual command execution (`ProvisioningHandler`/`Command`).

No existing guard prevents this: `repository.review_stacks_enabled` is only read once, inside the first disjunct — it is never applied to the `prevent_with_label` branch. There is no model validation preventing a repository from being saved with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'` simultaneously; the settings form [5](#0-4)  allows setting these two fields independently. The `params` schema only validates payload shape, not business logic. The existing test suite covers `prevent_with_label` only with `review_stacks_enabled` at its default value of `true` (via `configure_provisioning_behavior`'s default `provisioning_enabled: true`) [6](#0-5) , so this specific combination (`false` + `prevent_with_label`) is untested and the bug is undetected.

The attacker's exact action: open a pull request with zero labels against a repository they can open PRs on. This is an entirely unprivileged, self-serve GitHub action (opening a PR triggers a legitimate, correctly-signed `pull_request` webhook from GitHub itself), while the repository owner's intent (`review_stacks_enabled: false`) has been explicitly set to opt out of dynamic review stack provisioning.

### Impact Explanation
For any repository misconfigured with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'`, any unprivileged contributor opening an unlabeled PR causes Shipit to create a `ReviewStack` record and enqueue it for provisioning — triggering command execution against attacker-controlled branch/ref data despite the repository owner's explicit opt-out. This is repeatable for every unlabeled PR opened against every repository with this configuration, and matches the Critical category: "a payload for one repository mutating another's stack" analog — here it's an unauthorized deploy/provisioning action against a repository that revoked consent for stack creation, and downstream provisioning runs `Command`/build steps derived from PR data.

### Likelihood Explanation
Preconditions: a repository must be configured with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'` — a plausible, non-adversarial admin configuration (e.g., an owner disabling review stacks while leaving a previously-configured provisioning behavior in place, since the UI does not couple these fields). No secrets or elevated privileges are needed by the attacker; opening a PR is a normal, low-cost action available to anyone who can create a PR (including from a fork). The bug is deterministic and triggers on every matching event.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false, even for prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_equal false, repository.reload.review_stacks_enabled
  assert_equal "prevent_with_label", repository.provisioning_behavior

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Both sides of the binding (`review_stacks_enabled == false` implies `Stack.count` unchanged) diverge with the current code — the test fails because a stack is created — confirming the bug.
