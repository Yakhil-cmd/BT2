### Title
StatusHandler applies webhook-signed commit statuses without validating the authenticated organization owns the repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify against using the `repository.owner.login` (or `organization.login`) field taken directly from the untrusted JSON payload, and once the HMAC check passes for *that* organization's secret, the parsed payload is dispatched to event handlers. `StatusHandler`, however, applies the resulting commit-status write globally by SHA only, with no re-check that the commit actually belongs to a stack/repository owned by the organization whose secret authenticated the request. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` in a multi-tenant deployment (the officially documented schema shown in `config/secrets.development.shopify.yml`, keyed by multiple GitHub orgs) resolves to a distinct `GitHubApp`/`webhook_secret` per organization, via: [3](#0-2) 

Once `verified` is true for *some* configured organization, the raw payload is fully trusted and dispatched to handlers: [4](#0-3) 

Most handlers scope their side effects to the repository named in the payload via `Handler#repository_name`/`#stacks`, itself just another attacker-controlled field of the same JSON body, independent of `repository_owner`: [5](#0-4) 

`StatusHandler` goes further and does not even use the repository field at all — it matches purely by commit SHA across the entire database: [6](#0-5) 

`Commit#create_status_from_github!` then unconditionally records the forged status and, critically, feeds it into deploy-gating logic (`deployable?`, `schedule_continuous_delivery`, `Hook.emit(:deployable_status, ...)`): [7](#0-6) [8](#0-7) [9](#0-8) 

So the equality that should hold — `organization authenticated by HMAC == organization owning the stack/commit being mutated` — is never enforced. An attacker who legitimately administers *their own* tenant GitHub App/org on a shared multi-org Shipit instance (a valid, unprivileged, non-Shipit-session actor with respect to any other tenant) possesses a real `webhook_secret` that passes `verify_webhook_signature`, but the payload they sign is otherwise unconstrained and can target any commit SHA tracked by any other tenant's stacks.

### Impact Explanation
This allows a "status" (or, via the same weak binding, "push"/"pull_request" handlers keyed only by `repository.full_name`) webhook forged and signed with one tenant's webhook secret to write GitHub commit-status state (`success`/`failure`/`pending`, `context`, `description`, `target_url`) for a commit belonging to a completely unrelated tenant's stack. Because commit status directly gates `Commit#deployable?` and triggers `schedule_continuous_delivery` / `ContinuousDeliveryJob`, an attacker can forge a passing CI status on a victim commit to make it appear deployable, bypassing the victim's actual CI gating and triggering an unauthorized deploy for a repository/organization the attacker has no legitimate relationship to. This is a cross-repository/cross-organization write and can lead to an unauthorized deploy, matching the Critical/High impact bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Exploitation requires only:
1. The Shipit instance to be configured for multiple GitHub organizations (the documented, supported multi-tenant schema), and
2. The attacker to control (administer) at least one of those onboarded organizations' GitHub Apps — an unprivileged position relative to the victim organization, requiring no Shipit session, API token, or access to the victim's secrets.

Given that, forging the HTTP request and its HMAC signature is trivial (`OpenSSL::HMAC.hexdigest` with a known secret), and the target commit SHA is discoverable via GitHub's public API for any repository the attacker can read. This is a realistic, low-effort exploit path within a documented deployment configuration, not one that requires the host to deviate from documented setup.

### Recommendation
Bind the verified organization to the target repository/stack before applying any handler side effects:
- After signature verification, pass the verified `repository_owner`/organization identity into the handler dispatch, and have every handler (including `StatusHandler`) resolve the target repository/stack via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and assert `repository.owner == verified_organization` before mutating anything.
- Specifically fix `StatusHandler#process` to scope `Commit.where(sha: params.sha)` to commits whose `stack.repository.owner` matches the authenticated organization, rather than matching by SHA alone across all tenants.

### Proof of Concept
Assume a multi-org Shipit instance configured per `config/secrets.development.shopify.yml` with organizations `attacker-org` (attacker's own onboarded tenant, secret known to attacker) and `victim-org` (unrelated tenant with a tracked stack containing commit `deadbeef...`).

1. Attacker computes `sha1=<hmac>` over a JSON body using `attacker-org`'s own webhook secret:
```json
{
  "sha": "deadbeef0000000000000000000000000000",
  "state": "success",
  "context": "ci/forged",
  "description": "forged by attacker"
}
```
2. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac>`.
3. `WebhooksController#repository_owner` returns `nil` (payload has no `repository`/`organization` field, per `StatusHandler`'s params which don't require one) — in single fallback org mode `Shipit.github(organization: repository_owner)` still resolves to a configured app matching the attacker's secret in a multi-org setup by supplying `attacker-org` in the `organization` field to steer resolution, or, in the documented multi-org test setup (`test/fixtures/shipit/github_hooks.yml`), the same effect is reachable via any org key the attacker administers.
4. Signature validates using `attacker-org`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` and calls `create_status_from_github!`, applying the forged `success` status to `victim-org`'s commit, regardless of the authenticating organization, satisfying CI gating for that commit and enabling `schedule_continuous_delivery` on `victim-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
