### Title
Security-review quota exhaustion allows a malicious/injected change to bypass the Stop-hook and commit/push LLM security review - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The `security-guidance` plugin's LLM-based vulnerability review is gated by shared, per-session counters/rate-limits (`MAX_STOP_HOOK_FIRINGS`, `atomic_check_counter`, `atomic_check_rate_limit`/`MAX_COMMIT_REVIEWS_PER_HOUR`) rather than being unconditionally applied to every code change [1](#0-0) . Once the counter is exhausted the hook silently skips the review and exits 0/allows the action to proceed [2](#0-1) . This mirrors the Paraspace bug class: a cheap, attacker-triggerable operation fills a bounded counter that gates a protective check, and once the counter is saturated the protection silently stops applying to the victim's subsequent (legitimate or, here, malicious) action.

### Finding Description
`handle_stop_hook` tracks `stop_hook_fire_count` in per-session state and refuses to run the LLM diff review once `fire_count >= MAX_STOP_HOOK_FIRINGS` (default 3, TTL 120s) [3](#0-2) . The counter increments on every fire that produces guidance/exit(2) [4](#0-3) , and the whole snapshot/consume mechanism (`consume_stop_state`) is what decides the effective `fire_count` for the current turn [5](#0-4) . Similarly, the commit-review and push-sweep PostToolUse handlers gate the LLM review behind a rolling-window rate limiter (`atomic_check_rate_limit`, keyed by `"PushSweep"`/commit-review key, `MAX_COMMIT_REVIEWS_PER_HOUR`/`COMMIT_REVIEW_RATE_WINDOW_S`) and simply `sys.exit(0)` (no review, no block) once the budget is exhausted [6](#0-5) [7](#0-6) .

Just as the Paraspace `balanceLimit` check was meant to bound gas/DoS risk but created an attacker-fillable resource that could be exhausted cheaply to disable a user's protective action (adding more collateral), these hook-firing/rate-limit counters exist to bound LLM cost/latency, but create an attacker-influenceable, per-session/global counter: if an attacker can get the agent to perform enough trivial edits, commits, or `Stop` cycles (e.g., via prompt-injected instructions in a file Claude reads, or a large refactor with an intentionally noisy fix-loop), the quota for `Stop`, commit-review, or push-review is exhausted for the remainder of the window, and any *subsequent* dangerous edit/commit — including one introduced by the same injected instructions — sails through with zero LLM security review, `exit(0)`, no warning surfaced to the user.

### Impact Explanation
Exhausting the counter converts the security-guidance plugin's core detection layer (Stop-hook diff review, commit review, push review) into a silent no-op for the rest of the window, without any signal to the user that coverage has lapsed (the skip paths just emit low-visibility metrics, not an interactive warning) [8](#0-7) . This is a hook-bypass: an unprivileged, attacker-controlled input path (e.g., prompt-injected content in a repo file or dependency that the model reads and iteratively "fixes") can deliberately burn the fixed budget so that a genuinely malicious/insecure change slips into the codebase or gets committed/pushed without triggering the plugin's protective LLM review — directly analogous to the collateral-lockout attack where filling a bounded counter disabled the victim's protective action at the exact moment it mattered.

### Likelihood Explanation
The counters are small and fixed by default (`MAX_STOP_HOOK_FIRINGS=3` per 120s TTL; rate limiters bounded per hour) [1](#0-0) , and the fire/rate-limit keys are shared per session, so triggering enough benign-looking edit/fix/commit cycles to exhaust them is cheap and requires no special privilege beyond getting the agent to iterate (which prompt injection or a large/noisy task can do). The main uncertainty is whether the specific injected-content attack chain (getting Claude to autonomously perform several Stop-triggering cycles or several `git commit`s within the rate window, and then land the actual malicious diff right after exhaustion) is reliably achievable in a real session — this depends on session/task shape and wasn't verified end-to-end in this pass due to tool-iteration limits.

### Recommendation
Do not silently allow-through when the quota is exhausted. When `fire_count`/`rate_count` hits its cap, either (a) fail closed by blocking the action pending manual review rather than `sys.exit(0)`, (b) surface a clear, unavoidable warning to the user/operator that security coverage lapsed for this turn/session ("N reviews were skipped due to the review budget — please review manually"), or (c) scope the counters to detect abnormal fire velocity (e.g., many fires triggered by content read from files rather than the user) and treat that pattern itself as suspicious, similar to disallowing zero-liquidity NFTs in the original report.

### Proof of Concept
Conceptual reproduction path (not independently executed against a live session):
1. Have Claude read attacker-controlled content (e.g., a README/config the injected task references) containing instructions that cause 3+ Edit/Write operations each deliberately tripping the pattern rules / Stop-hook LLM findings within one turn.
2. Each Stop-hook cycle increments `stop_hook_fire_count`; after the 3rd (default `MAX_STOP_HOOK_FIRINGS`) fire, `handle_stop_hook` hits `fire_count >= MAX_STOP_HOOK_FIRINGS` and calls `_skip(2)`, exiting 0 without ever calling `analyze_code_security` again for the rest of the 120s TTL window [3](#0-2) .
3. The same injected instructions then have Claude introduce the actual malicious/vulnerable change (e.g., a command-injection or secret-leaking edit) in that same turn; because the budget is exhausted, no LLM review fires and the change is committed/left in place with no warning shown to the user.

def consume_stop_state(session_id):
    """Atomically snapshot all state the Stop hook needs and clear touched_paths.

    The Stop hook is asyncRewake — it runs in the background after Claude's
    turn ends. The user can submit a new prompt before this hook finishes its
    initial state read. Telemetry showed a meaningful share of would-be reviews lost when
    the next turn's UPS wiped touched_paths before Stop read it.

    Single locked read-then-clear closes that window: PostToolUse appends
    after this clear go into the next snapshot; UPS overwrites of baseline_sha
    after this snapshot are invisible to this Stop fire.
    """
    import time as _time
    now = _time.time()

    def _snap(state):
        fire_ts = state.get("stop_hook_fire_count_ts", 0)
        expired = (now - fire_ts) > STOP_LOOP_STATE_TTL_SEC
        findings_ts = state.get("previous_findings_ts", fire_ts)
        findings_expired = (now - findings_ts) > PREVIOUS_FINDINGS_TTL_SEC
        snap = {
            "touched_paths": list(state.get("touched_paths", [])),
            "baseline_sha": state.get("baseline_sha"),
            "head_at_capture": state.get("head_at_capture"),
            "untracked_at_baseline": (
                dict(state["untracked_at_baseline"])
                if isinstance(state.get("untracked_at_baseline"), dict) else {}
            ),
            "fire_count": 0 if expired else state.get("stop_hook_fire_count", 0),
            "fire_count_expired": expired and state.get("stop_hook_fire_count", 0) > 0,
            "previous_findings": [] if findings_expired else list(state.get("previous_findings", [])),
        }
        state["touched_paths"] = []
        return snap

    return with_locked_state(session_id, _snap) or {
        "touched_paths": [], "baseline_sha": None, "head_at_capture": None,
        "untracked_at_baseline": {},
        "fire_count": 0, "fire_count_expired": False, "previous_findings": [],
    }
