## Vulnerability Analog Found

### Title
Missing existence check on `base_aa` in parameterized AA definitions crashes the node on trigger execution - (File: aa_composer.js)

### Summary
`aa_validation.js`'s `validateAADefinition()` only checks that `template.base_aa` is a syntactically valid address; it never verifies that an actual AA definition exists (or will ever exist) at that address before allowing the AA definition unit to be accepted. When a payment later triggers this parameterized AA and the referenced `base_aa` still has no AA definition, `aa_composer.js`'s `handleTrigger()` throws an uncaught `Error`, analogous to the reported `Timelock.sol` bug where a missing zero-address check on a privileged/constructor-bound parameter permanently bricks contract functionality — here it permanently bricks (crashes) AA-trigger processing on every full node.

### Finding Description
Any unprivileged unit poster can define a parameterized AA whose `base_aa` field points to any syntactically valid but non-existent (or never-to-be-defined) AA address: [1](#0-0) 
This validation path only calls `isValidAddress(template.base_aa)` — it never checks that `template.base_aa` currently is, or will become, a real AA definition.

Later, when any user (even the AA definer themselves) sends a trigger payment to this AA's address, `aa_composer.js` resolves `base_aa` via `storage.readAADefinition` and, if it's not found, throws an unguarded `Error`: [2](#0-1) 
This code runs inside a database-callback (`storage.readAADefinition(conn, template.base_aa, mci, function (arrBaseDefinition) {...})`) invoked from `handlePrimaryAATrigger`/`handleAATriggers`, which is called synchronously as part of main-chain stabilization: [3](#0-2) [4](#0-3) 
There is no try/catch around this call chain, so the `throw` becomes an uncaught exception in the Node.js process, crashing the full node while it is stabilizing main-chain units — the exact moment new units are being confirmed.

The codebase itself acknowledges the risk of this exact crash: an optional, config-gated dry run exists specifically to pre-emptively trigger any such crash before real execution ("if it would crash, let it crash now, not when we execute the trigger for real"): [5](#0-4) 
However, this mitigation is gated behind `conf.bDryRunNewTriggers` and only covers units received live over the network before they are stabilized — it does not protect the mandatory `handleAATriggers()` call performed during real MC stabilization (`main_chain.js`/`writer.js`), nor does it prevent the AA definition (with the bad `base_aa`) from ever being accepted in the first place.

### Impact Explanation
Once such a parameterized AA is defined and later triggered, every full node that executes `handleAATriggers()` at MC stabilization time hits the same unguarded `throw`, crashing the node process. Since this occurs deterministically during main-chain stabilization (not a per-node/light-client-only code path), any full/witness node processing this MCI is affected identically — a network-wide denial of service preventing the network from confirming subsequent units, matching the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Likelihood is high: any unprivileged unit poster can define such a parameterized AA (defining an AA is a standard, permissionless `definition` message), and any unprivileged sender (including the definer) can trigger it with a simple payment. No special privileges, timing races, or witness collusion are required — only a `base_aa` address that legitimately never resolves to an on-chain AA definition (e.g., a fresh random valid-looking chash, or an address whose AA definition unit never gets confirmed).

### Recommendation
In `handleTrigger` (aa_composer.js), replace the `throw Error("base AA not found: " + template.base_aa)` with a graceful bounce/error response for the AA response instead of an unguarded throw. Additionally, consider tightening `validateAADefinition` in `aa_validation.js` to reject `base_aa` values that cannot resolve to an existing AA at validation time when possible, and audit other `throw Error(...)` calls inside `handleTrigger`'s async callback chains for similar unguarded crash risks that are reachable purely from unprivileged AA definitions/triggers.

### Proof of Concept
1. Post a unit defining a parameterized AA: `['autonomous agent', { base_aa: '<VALID_BUT_NEVER_DEFINED_ADDRESS>', params: {...} }]`. This passes `validateAADefinition` because only `isValidAddress` is checked (aa_validation.js:734-744).
2. Ensure `<VALID_BUT_NEVER_DEFINED_ADDRESS>` never receives an actual AA definition unit before the trigger's MCI stabilizes.
3. Send any payment to the parameterized AA's address.
4. When this unit's MCI stabilizes, `main_chain.js`'s `handleAATriggers()` inserts the trigger and `writer.js` invokes `aa_composer.handleAATriggers()`, which calls `handleTrigger` → `storage.readAADefinition(conn, template.base_aa, mci, ...)` → `arrBaseDefinition` is null → `throw Error("base AA not found: " + template.base_aa)` (aa_composer.js:437-438), crashing the node process with an uncaught exception during unit confirmation.
