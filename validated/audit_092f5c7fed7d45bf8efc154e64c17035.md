### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` and payload-derived signature verification - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify a webhook against using a value taken from the *unverified* request body itself (`repository.owner.login` / `organization.login`). In a multi-organization Shipit deployment (explicitly documented under "Using Multiple Github Applications"), each org has its own independently configured `webhook_secret`. An attacker who legitimately administers one configured org's GitHub App (and therefore knows that org's `webhook_secret`) can forge a `status` webhook whose `repository.owner.login` claims to be their own org (so their own secret is used for verification) while `sha` refers to a commit belonging to a *different* organization's repository. `StatusHandler#process` looks up the target commit with `Commit.where(sha: params.sha)`, which is not scoped to the organization/repository that was authenticated at all, so the forged status is applied to any commit in the entire Shipit instance sharing that sha.

selects the verifying `GitHubApp` via `repository_owner`, which is computed from [2](#0-1) 
i.e. straight from the JSON body fields `repository.owner.login` / `organization.login`, before any authenticity check has occurred on that body.

Multi-org configuration, where each organization owns a distinct GitHub App and thus a distinct `webhook_secret`, is a supported and documented setup: [3](#0-2) 
and is exercised in `Shipit.github(organization:)`: [4](#0-3) 

Once signature verification passes (using whichever org's secret matches the attacker-controlled `repository_owner` field), the raw payload is dispatched to handlers unmodified: [5](#0-4) 

`StatusHandler` then resolves the target purely by commit SHA, with no organization or repository scoping at all: [6](#0-5) 

This breaks the intended binding: **the organization whose credential authenticated the request** (`repository_owner` from the payload, verified against that org's `webhook_secret`) **≠ the repository/commit that is actually written** (any commit anywhere in the instance matching `params.sha`, from any organization/stack). Most other handlers (`PushHandler`, `PullRequest::*Handler`) at least re-derive the target repository from `repository.full_name` via `Repository.from_github_repo_name`, limiting blast radius to a specific repo record (still attacker-influenced, but bounded to an existing `Repository`). `StatusHandler` has no such scoping whatsoever.

### Impact Explanation
Commit statuses drive Shipit's deployability logic (`deployable_status` hook event) and the merge queue. By forging a `status` event authenticated with a secret they legitimately control, an attacker who administers one configured GitHub App/organization on a shared Shipit instance can inject a fabricated "success" status (arbitrary `state`, `context`, `description`, `target_url`) onto a commit belonging to a completely unrelated organization/repository whose commit SHA they merely need to know (often public information). This can mark a commit "deployable" or satisfy required-status checks it never actually passed, enabling an **unauthorized deploy or merge** in a tenant the attacker has no legitimate access to — matching the Critical impact bar (unauthorized deploy/merge across a trust boundary).

### Likelihood Explanation
Requires: (a) a multi-org Shipit deployment (explicitly documented/supported configuration), (b) the attacker legitimately controls at least one configured organization's GitHub App/webhook secret (a normal, unprivileged position relative to the victim org), and (c) knowledge of a target commit SHA in the victim repo (typically public via GitHub). No access to the victim org, no `ApiClient` token, and no privileged Shipit account is required — only the ability to send an HTTP POST to `/webhooks` with a body they sign themselves.

### Recommendation
Do not derive the organization used for signature verification from the unauthenticated request body. Bind webhook verification and the affected repository/organization to a value the app controls out-of-band (e.g., a per-organization/per-app webhook endpoint or a value cross-checked against the resolved `Repository`/`Stack` record, not the raw payload). Additionally, scope `StatusHandler` (and any other handler that trusts `params.sha`/`repository.full_name`) to the same organization identity that was actually verified for that request, e.g. by joining through `Repository`/`Stack` and asserting the verified organization matches the stack's owning repository before mutating commit state.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgVictim`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md` multi-org instructions).
2. As the (legitimate, unprivileged w.r.t. `OrgVictim`) administrator of `OrgA`, obtain `OrgA`'s `webhook_secret`.
3. Find a public commit SHA `S` belonging to a stack tracked under `OrgVictim`.
4. POST to `/webhooks` with `X-Github-Event: status` and body:
   ```json
   { "sha": "S", "state": "success", "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" } } }
   ```
5. Compute `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>`.
6. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully against `OrgA`'s secret.
7. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the `OrgVictim` commit (unscoped), and creates a forged "success" status on it — despite the request never being authenticated by anything belonging to `OrgVictim`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
