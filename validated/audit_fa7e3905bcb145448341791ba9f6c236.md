### Title
Stack-scoped ApiClient tokens can read any stack via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` resolves the target stack directly from the request parameter instead of going through the stack-scoping helper that every other API controller uses, so a token that is supposed to be restricted to a single stack can be used to read the deploy status of any stack on the instance.

### Finding Description
`Shipit::Api::BaseController` defines a `stacks` helper that enforces per-token scoping: if the authenticated `ApiClient` has a `stack_id`, only that stack is visible; otherwise all stacks are visible. `#stack` is built on top of it: [1](#0-0) 

`Api::CCMenuController` overrides `#stack` with its own implementation that calls `Stack.from_param!` directly, completely bypassing the `stacks` scoping helper: [2](#0-1) 

The controller only checks that the presented `ApiClient` has the generic `read:stack` permission — it never checks that the resolved stack equals (or is contained in) the client's `stack_id`: [3](#0-2) 

Meanwhile, tokens minted specifically to be stack-scoped exist in the codebase: `CCMenuUrlController` (an authenticated, session-based, low-privilege UI action available to any logged-in Shipit user who can view a stack) creates/find an `ApiClient` with `read:stack` permission for that single stack and hands the caller a URL containing the bearer token: [4](#0-3) 

`ApiClient#check_permissions!` only validates the operation/scope string (`"read:stack"`), never the specific stack: [5](#0-4) 

This breaks the equality that should hold: `stack the token authorizes == stack the token touches`. Before the flaw: a `read:stack`-permitted, `stack_id`-scoped `ApiClient` token is expected to only ever resolve `stack A` (its own `stack_id`) in any API endpoint. After the flaw: when that same token/param pair is presented to `Api::CCMenuController#show`, the controller ignores `current_api_client.stack_id` and resolves whatever `stack_id` is in the request, e.g. `stack B`, `stack C`, etc. — i.e., the trust binding "authorized stack" vs "accessed stack" is broken specifically in this controller.

### Impact Explanation
This matches the High-impact category "unauthenticated read of stack state": an attacker who obtains any single-stack-scoped `read:stack` bearer token (which, by design, is meant to be a narrow, low-trust credential distributed via CCMenu URLs for one stack) can use `Api::CCMenuController#show` (authenticated only by a query-string token, no session) to enumerate the deploy/rollback status of every stack in the Shipit instance, not just the one the token was issued for. This is a cross-stack information disclosure that undermines the entire purpose of per-stack `ApiClient` scoping.

### Likelihood Explanation
Likelihood is moderate-to-high: any regular, non-privileged Shipit user who has access to at least one stack's "CCMenu URL" feature obtains a real bearer token via a normal, unprivileged UI flow (`CCMenuUrlController#fetch`), and can trivially replay that token against `Api::CCMenuController#show` with a different `stack_id` parameter to read data outside its intended scope. No special permissions, secrets, or GitHub credentials are needed beyond a token that the application itself hands out for ordinary use.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) exactly as `BaseController#stack` does, so a stack-scoped `ApiClient` can only ever resolve its own stack. Additionally, consider validating in `ApiClient#check_permissions!` (or an added `check_stack!` method) that any stack-scoped client's `stack_id` matches the stack being acted upon, defensively, in every controller that overrides the default `#stack` resolution.

### Proof of Concept
1. As any Shipit user with access to `stack-A`, call `GET /stacks/*stack-A/ccmenu_url` (routed to `CCMenuUrlController#fetch`) to obtain `{ ccmenu_url: ".../api/*stack-A/ccmenu.xml?token=<TOKEN>" }`. This creates (or reuses) an `ApiClient` with `permissions: ["read:stack"]` and `stack: stack-A` bound to the requesting user. [6](#0-5) 
2. Send `GET /api/*stack-B/ccmenu.xml?token=<TOKEN>` where `stack-B` is any other stack on the instance that the attacker has no access to.
3. `Api::CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`: [7](#0-6) 
4. `require_permission :read, :stack` only checks the string permission `read:stack`, which the token has, and `#stack` resolves `stack-B` directly via `Stack.from_param!`, ignoring that the token's `stack_id` is `stack-A`: [8](#0-7) 
5. The response renders `stack-B`'s latest deploy/rollback status, which the attacker was never authorized to view.
