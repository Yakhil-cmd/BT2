### Title
API client stack-scope bypass in CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via the `stack_id` column, and `Shipit::Api::BaseController` enforces that scope by resolving stacks through the `stacks`/`stack` helper methods. `Shipit::Api::CCMenuController` overrides `stack` to bypass this scoping entirely, breaking the binding "a stack a token authorises versus a stack it touches."

### Finding Description
`ApiClient` belongs to an optional `stack` and the base API controller is designed to restrict a stack-scoped client to only the stacks it is authorized for: [1](#0-0) [2](#0-1) 

`stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` when the authenticated client is stack-scoped, and `stack` resolves the requested id through that restricted relation via `from_param!`. Every other API controller (e.g. `StacksController`) relies on this shared `stack`/`stacks` method to enforce the scope.

`CCMenuController`, however, defines its own `stack` method that ignores the scoping relation entirely: [3](#0-2) 

It calls `Stack.from_param!(params[:stack_id])` directly against the full `Stack` table instead of `stacks.from_param!(...)`. The `require_permission :read, :stack` before_action only checks that the client holds the `read:stack` permission string via `ApiClient#check_permissions!`, which never inspects which stack is targeted: [4](#0-3) 

So the equality that should hold — `stack the token authorizes == stack the token touches` — fails here: a token scoped to stack A (`current_api_client.stack_id == A.id`) can still fetch CCMenu status/deploy state for any stack B by supplying `stack_id=B` in the route, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
An attacker holding any valid `read:stack`-permitted `ApiClient` token — including one deliberately scoped to a single, low-sensitivity stack — can enumerate and read deploy/build status (`running?`, `ended_at`, deploy id) for every stack in the Shipit instance, not just the one it is scoped to. This is a scope/authorization escalation: it grants cross-stack read of stack/deploy state to a credential that was explicitly restricted to one stack, matching the "escalation into `Shipit.github_teams`/API scope authorization" / "unauthenticated read of stack state" class of High-severity impact once the token boundary is crossed.

### Likelihood Explanation
Any actor with an existing, narrowly-scoped API client token (a normal, low-privilege credential meant to be usable in CI dashboards such as CCMenu) can trivially exploit this by changing the `stack_id` path segment of the request — no additional secrets, signatures, or privileges are required beyond possessing that one token.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited, scope-aware resolution instead of querying `Stack` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so stack-scoped API clients cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Provision (or reuse) an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (as in `here_come_the_walrus` fixture) and obtain its `authentication_token`.
2. Issue: `GET /api/stacks/*B/ccmenu?token=<token>` where `B` is a different stack the client is not scoped to.
3. Observe `Api::CCMenuController#show` renders `B`'s deploy status successfully instead of being denied, because `stack` resolves via unscoped `Stack.from_param!` rather than the client-scoped `stacks` relation. [5](#0-4)
