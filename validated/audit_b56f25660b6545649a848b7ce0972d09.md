### Title
Stack-scoped ApiClient tokens can read the build/deploy status of any stack via the CCMenu API endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolver used by every other API controller and looks up the target `Stack` without applying the per-`ApiClient` stack scope, so a token that is supposed to be restricted to a single stack can be replayed against any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` establishes the security boundary that binds an `ApiClient` token to a specific `Stack`: `#stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `#stack` resolves the requested record through that restricted relation: [1](#0-0) 

This scoping is the documented and tested authorization contract — an `ApiClient` created with `belongs_to :stack, optional: true` and a non-nil `stack_id` (see fixture `here_come_the_walrus` with `stack: shipit`) is expected to only ever see that one stack, as asserted by: [2](#0-1) 

`Api::CCMenuController`, however, defines its own private `stack` method that ignores this scope entirely and resolves the stack directly from `Stack.from_param!(params[:stack_id])`, i.e. against the full, unfiltered `Stack` relation: [3](#0-2) 

The controller only enforces the coarse-grained `read:stack` permission via `require_permission :read, :stack`, not the per-token stack binding: [4](#0-3) 

The broken equality is: `stack(s) the ApiClient token authorizes` (`current_api_client.stack_id`) `≠` `stack the request actually touches` (`params[:stack_id]` resolved against `Stack.from_param!` with no scope filter). Every other API controller (`Api::StacksController`, `Api::DeploysController`, `Api::TasksController`, etc.) inherits `BaseController#stack` and is therefore correctly scoped; `CCMenuController` alone re-implements the lookup and drops the scope check.

### Impact Explanation
Any holder of a valid, deliberately narrow-scoped `ApiClient` token (e.g. one created and distributed for a single stack's CCMenu integration) can use that same token to query `/api/stacks/:stack_id/ccmenu` for any other stack in the Shipit installation, regardless of the `stack_id` the token was scoped to. This exposes another stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, activity, lock status) — an unauthorized read of stack state that the token was never meant to access. This matches the "High" impact category of escalation into unauthorized read of stack state via a token that should be confined to one stack.

### Likelihood Explanation
Exploitation requires only a legitimately-issued, stack-scoped `ApiClient` token (no privileged account, no secret compromise, no session) and a single unauthenticated-in-effect GET request with a different `stack_id` path parameter — the same trust level already assumed elsewhere in the engine (holding *some* API token, scoped to a *specific* stack). The scoping bypass is a straightforward method-override oversight, not a byzantine chain, making it easy to trigger once such a token is held.

### Recommendation
Remove the private `stack` override in `Shipit::Api::CCMenuController` (and the equivalent one in `Shipit::CCMenuUrlController`) so it falls back to the inherited, scope-aware `BaseController#stack`, which resolves the stack via `stacks.from_param!` and thus respects `current_api_client.stack_id`.

### Proof of Concept
1. As an admin, create (or have the system create via `CCMenuUrlController#fetch`) an `ApiClient` scoped to Stack A (`stack_id` set to A's id, `permissions: ['read:stack']`), and obtain its `authentication_token`.
2. Using that token as Basic Auth credentials, send: `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu` where `owner/repo-B/env-B` identifies Stack B, a stack the token was never scoped to.
3. Observe the request succeeds (HTTP 200) and returns Stack B's CCMenu XML (build status/label/lock state), because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly, bypassing the `current_api_client.stack_id` restriction that `Api::StacksController#show` (using the inherited `stack` method) would have enforced and rejected with a 404.
