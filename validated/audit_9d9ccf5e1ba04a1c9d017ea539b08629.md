### Title
CCMenu client token has no stack scope and grants read access to all stacks via `Shipit::Api::BaseController#stacks` - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::CCMenuUrlController#client` mints an `ApiClient` with `read:stack` permission but never assigns `stack`, leaving `stack_id` `nil`. [1](#0-0) 
`Shipit::Api::BaseController#stacks` treats a client with no `stack_id` as unrestricted and returns `Stack.all` instead of denying or scoping the request, so any endpoint gated only by `read:stack` (e.g. `Api::StacksController#index`) is fully accessible with that token. [2](#0-1) 

### Finding Description
The intended binding is: `token(stack A).authorised_scope == {stack A}`. The actual binding after tracing the code is: `token(stack A).authorised_scope == Stack.all`.

- `CCMenuUrlController#fetch` calls `client`, which does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`. `create_with` only sets `permissions`; `stack` (an optional `belongs_to`) is never set, so every CCMenu client created for a given user has `stack_id == nil`, regardless of which stack's CCMenu URL triggered its creation. [1](#0-0) [3](#0-2) 
- Because `find_or_create_by!` matches only on `creator` and `name: 'CCMenu Client'`, the *same* `ApiClient` record (and therefore the same `authentication_token`) is reused for every stack that user requests a CCMenu URL for. There is no per-stack token at all.
- `Api::BaseController#stacks` is the sole gate used by `require_permission :read, :stack` endpoints such as `Api::StacksController#index`: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. With `stack_id` nil, it falls through to `Stack.all`. [2](#0-1) 
- `ApiClient#check_permissions!` only checks the string `"read:stack"` is present in `permissions`; it has no concept of which stack, so it does not stop this. [4](#0-3) 

Exploit flow: a user (or anyone who obtains a CCMenu URL, e.g. a viewer of stack A) takes the `token` query parameter from `GET /:stack_id/ccmenu.json` (or wherever `fetch` renders the URL) and uses it as HTTP Basic auth against `GET /api/stacks` (`api_stacks_url`, routed to `Api::StacksController#index`, guarded by `require_permission :read, :stack`). Because `stacks` resolves to `Stack.all`, the response enumerates every stack in the Shipit instance — including stacks the token holder has no legitimate visibility into — rather than being confined to the single stack the CCMenu badge was minted for. [5](#0-4) 

No existing guard intercepts this: `authenticate_api_client` only verifies the token signature via `ApiClient.authenticate`, and `require_permission!`/`check_permissions!` check only the operation:scope string, never the stack binding. [6](#0-5) 

### Impact Explanation
Any holder of a single CCMenu token (intended to expose only one stack's CI badge XML via `Api::CCMenuController#show`) can instead authenticate to any `read:stack`-gated API endpoint and enumerate/read every stack in the instance (name, repository, branch, environment, lock state, etc., via `Api::StacksController#index`/`#show`). This is an unauthenticated-scope-escalation read of stack state across tenants/repositories that the token was never authorized for — matching the "High: unauthenticated read of stack state" impact category. The same client/token is reusable indefinitely and works identically against any stack in the instance, so blast radius is the entire Shipit deployment's stack list, not just stack A.

### Likelihood Explanation
Preconditions are trivial and already satisfied by normal product usage: any current user who has ever viewed a CCMenu badge URL for one stack has a valid `read:stack` token whose `stack_id` is nil by construction (no special config needed). No secrets, GitHub credentials, or elevated Shipit roles are required — only possession of a previously issued CCMenu token, which is embedded directly in a URL query string that is often shared or logged. This is repeatable indefinitely against the same token and against every stack the instance hosts.

### Recommendation
Set `stack: stack` when creating the CCMenu `ApiClient` in `CCMenuUrlController#client`, include `stack` in the `find_or_create_by!` lookup keys so a distinct token is minted per stack, and change `Api::BaseController#stacks` (or `ApiClient`) so a client with `permissions` limited to a single stack but `stack_id` nil is treated as "no stacks" rather than "all stacks" — i.e., invert the fallback so only clients explicitly intended to be unrestricted (e.g. via a distinct flag, not merely a nil `stack_id`) can see `Stack.all`.

### Proof of Concept
In `test/controllers` (not modifying anything under `test/**` for the final PR, but as the required proof):
1. Create `stack_a = create(:stack)`, `user = create(:user)`.
2. Simulate `CCMenuUrlController#fetch` logic: `client = ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: user, name: 'CCMenu Client')`.
3. Assert `client.stack_id.nil?`.
4. Create `stack_b = create(:stack)`.
5. Instantiate `Api::BaseController` (or hit `Api::StacksController#index` with HTTP Basic auth using `client.authentication_token`) and assert the returned stack set (`controller.send(:stacks)` or the JSON body of `GET /api/stacks`) includes both `stack_a` and `stack_b`, proving the token minted for one stack context authorizes reading all stacks (`Stack.all` rather than `Stack.where(id: stack_a.id)`).
