### Title
Global unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets any authenticated fork mutate another repository's commit status - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no constraint on the repository/stack that the webhook was authenticated for. Because `verify_signature` in `WebhooksController` only proves that the payload was signed by *some* organization (`repository_owner`, taken from the attacker-controlled `repository.owner.login`/`organization.login` field), and does not confirm that the `sha` referenced actually belongs to a commit of *that* repository, an attacker who owns a fork sharing history with a monitored upstream can flip `Commit#state` for a victim's `Shipit::Commit` row that they never authenticated for.

### Finding Description
The broken binding is: `repository authenticating webhook (attacker's fork org) == repository owning the Commit row mutated (victim's Shipit-tracked repo)`. In code these are never actually compared.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) calls `Shipit.github(organization: repository_owner)` and verifies the HMAC signature against that org's webhook secret. `repository_owner` is read directly from the untrusted payload (`params.dig('repository', 'owner', 'login')`), so this only proves "the payload was signed by whichever org's secret matches the attacker-controlled `repository_owner` field" — i.e., it authenticates the attacker's own fork/org, not any relationship to the victim's repo. [1](#0-0) [2](#0-1) 

- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This performs a **global** lookup by `sha` across all `Shipit::Commit` rows in the entire database, with no `repository_id`/`stack_id` filter tying it back to the repository that was actually authenticated in `verify_signature`. [3](#0-2) 

- The base `Handler` class already provides a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, showing the framework has the concept of "repository that authenticated this webhook," but `StatusHandler` deliberately/accidentally bypasses it and queries `Commit` unscoped. [4](#0-3) 

Exploit flow: attacker forks the victim's monitored upstream (shared git history, so an old commit sha exists identically in both repos and in Shipit's `commits` table for the victim's stack). Attacker sends `POST /webhooks` with header `X-Github-Event: status`, a body whose `repository.owner.login` (and `repository.full_name`) refer to the attacker's own fork, signed with the attacker's own webhook secret (which the attacker legitimately controls since it's their own GitHub App/webhook config for their fork), `sha` set to the shared old commit, and `state: 'failure'`. `verify_signature` succeeds (attacker authenticated as themselves, which is all it checks). `StatusHandler#process` finds the victim's `Commit` row by the shared `sha` (since the query is global) and calls `create_status_from_github!`, writing a `Status` and updating `Commit#state`, blocking `Commit#deployable?` and gating `Stack#trigger_continuous_delivery` on the victim's stack — despite the attacker never having been authorized for the victim's repository/org.

None of the listed guards prevent this: `verify_signature` authenticates the signer's own org, not a link between signer and the target `Commit`'s repository; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape, not repository ownership of the `sha`; there is no `require_permission!`/`stacks` scoping applied inside `StatusHandler`.

### Impact Explanation
A payload authenticated for repository A (attacker's fork) mutates `Shipit::Commit`/`Status` state belonging to repository B (victim's stack) — this is exactly the "payload for one repository mutating another's commit/stack" Critical category. It can flip a victim's commit from `success` to `failure`/`error`, blocking `Commit#deployable?` and gating `Stack#trigger_continuous_delivery`, i.e., denial of legitimate deploys, or (in the reverse direction, not audited here but structurally identical) forging a `success` status to unlock deployability without any real CI having run on the victim's actual commit. This is a cross-tenant control-plane compromise: any attacker with a fork sharing history with a Shipit-tracked upstream can target any other Shipit-tracked repository/stack that also has commits with the same shas, repeatably, for every shared sha in the shared history.

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: own a public fork of a repo Shipit tracks (or of any repo that shares commit history/ancestry with a Shipit-tracked repo), configure your own webhook/App on your own fork (standard, unprivileged GitHub action), and send a `status` event referencing an old shared sha. No Shipit secret, session, API token, or GitHub team membership is required — only a signature valid for the attacker's own org, which the attacker legitimately possesses. This is trivially repeatable against any shared/ancestor commit and any number of victim stacks.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository that authenticated the webhook, e.g. restrict to `stacks`' commits (using the `Handler#stacks`/`repository_name` helper already defined in the base class) instead of a bare `Commit.where(sha: params.sha)`, so a status can only be applied to commits belonging to the repository identified by `repository.full_name` in the same payload that was signature-verified for that org.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, not to be placed under OUT OF SCOPE test/ path in real fix, illustrative only)
test "status webhook only authenticated for attacker's fork cannot mutate a commit belonging to a different, unrelated stack" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "shared ancestor commit")
  attacker_repo_full_name = "attacker/fork" # different Repository, never linked to victim_stack

  assert_equal "success", victim_commit.state # baseline: victim commit currently green

  payload = {
    "repository" => { "full_name" => attacker_repo_full_name, "owner" => { "login" => "attacker" } },
    "sha" => victim_commit.sha,
    "state" => "failure",
    "context" => "ci/attacker",
  }

  # Binding under test: repository authenticating webhook (attacker/fork)
  #                  != repository owning the Commit row (victim_stack.repository)
  refute_equal payload["repository"]["full_name"], victim_stack.repository.full_name

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  assert_equal "failure", victim_commit.state # currently flips despite no relation to attacker's org
  refute victim_commit.deployable?
end
```
