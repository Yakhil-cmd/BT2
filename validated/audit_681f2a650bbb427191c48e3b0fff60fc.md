### Title
Webhook secret selection uses `repository.owner.login`/`organization.login` while event handlers act on unchecked repository fields in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* webhook secret to validate the HMAC signature against based on an attacker-influenced field extracted from the JSON body itself, while the handlers that subsequently act on the payload consume other, uncorrelated repository-identifying fields from that same body. In a multi-organization GitHub App configuration, this breaks the intended binding "organization whose secret authenticated the request == repository that gets written to."

### Finding Description
`verify_signature` derives the organization used to look up the webhook secret directly from the untrusted request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` then resolves a **different GitHubApp/webhook_secret per organization** when a multi-org config schema is used (i.e. when `github_default_organization` is not nil): [3](#0-2) 

This means the secret used to validate the signature is chosen from a field (`repository.owner.login` / `organization.login`) that lives *inside* the very payload being verified. Because HMAC verification only checks that `HMAC(secret_for(repository_owner), raw_post) == signature`, an attacker who legitimately controls one organization's GitHub App installation (and therefore knows that organization's own `webhook_secret`, since organization admins configure it themselves when creating the App) can construct an arbitrary `raw_post` whose `repository.owner.login` equals their own org (so the correct, known secret is selected) while other fields consumed by the actual event handlers (e.g. `repository.full_name`, `sha`, `pull_request` payload, `team`/`organization` blocks used by `MembershipHandler`) reference a *different* repository or org entirely. Nothing in `verify_signature` or the handlers cross-checks that the field used to select the secret matches the field(s) the handler subsequently writes state for: [4](#0-3) 

This is the structural analog of the reported bug: one value (`vars.currentFlow`/flow limiter data keyed by an assumption) is trusted to bound a computation, while the actual balance consumed comes from an unrelated, uncapped source. Here, the "authorization" value (`repository_owner`, used to pick the trusted secret) is not the same value that determines what gets acted upon (the actual repository/stack/team targeted by the handler).

### Impact Explanation
An attacker who is an administrator of any organization that has installed the Shipit GitHub App (a normal, legitimate, unprivileged position relative to any *other* org tracked by the same Shipit instance) can forge webhook deliveries that are processed as if they came from GitHub for a **different** repository or organization. Depending on handler, this can:
- Enqueue `GithubSyncJob`/`RefreshCheckRunsJob` for another stack, injecting forged commit `status`/`check_suite` state that satisfies `ci.require` in `shipit.yml`, letting an unrelated actor manipulate deploy gating on a repository they do not own.
- Trigger `MembershipHandler` to add/remove memberships on `Team` records tied to `Shipit.github_teams`, potentially escalating into `authorized?` team-based authorization used by `Shipit::Authentication`.
This crosses a repository/organization trust boundary that the signature check is supposed to enforce, matching the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" impact categories.

### Likelihood Explanation
This requires the multi-organization GitHub App configuration path (`github_app_config`) to be in use, and requires the attacker to control (or be an admin of) at least one organization that has its own installed Shipit-integrated GitHub App with a known webhook secret — a legitimate, unprivileged-relative-to-other-orgs position, not requiring any Shipit account, `ApiClient` token, or the target org's own secret. This does not require compromising `webhook_secret`, `api_clients_secret`, or the GitHub App private key of the *targeted* organization/repository, only of the attacker's own organization, which is squarely in scope per the rules ("organization that authenticated versus the repository that is written").

### Recommendation
After verifying the HMAC signature, cross-validate that every organization/repository-identifying field consumed by the dispatched handler (`repository.full_name`, `repository.owner.login`, `organization.login`, `team.*`) is consistent with the `repository_owner` value used to select the webhook secret, and reject the request if they diverge. Alternatively, bind the webhook secret lookup to the `Stack`/`Repository`/`Team` record resolved from the *processed* payload rather than a raw, unvalidated field read before verification.

### Proof of Concept
1. Configure Shipit with the multi-organization GitHub config schema (`secrets.github` keyed by organization), e.g. `EvilOrg` and `VictimOrg` both have Shipit-tracked stacks.
2. As an admin of `EvilOrg`, create/own the GitHub App installation for `EvilOrg` and note its `webhook_secret` (self-configured, legitimately known).
3. Craft a `push` (or `status`/`check_suite`/`membership`) webhook JSON body where `repository.owner.login` (or `organization.login`) = `"EvilOrg"` but `repository.full_name` (and other handler-consumed fields) = `"VictimOrg/victim-repo"`.
4. Compute `X-Hub-Signature` as `sha1=` + `HMAC-SHA1(EvilOrg_webhook_secret, raw_post)` and POST it to `/webhooks` with `X-Github-Event` set accordingly.
5. `verify_signature` resolves `Shipit.github(organization: "EvilOrg")`, validates the HMAC successfully (since it was signed with `EvilOrg`'s known secret over this exact body), and the corresponding handler processes the forged event against `VictimOrg/victim-repo`'s stack/team state.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
