### Title
Trigger sender permanently loses all sent assets when bounce() aborts on the first insufficiently-fee-covering asset - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `bounce()` function is supposed to return the trigger sender's funds (minus configured `bounce_fees`) when an AA rejects/bounces a trigger. It iterates over every asset the trigger sent and builds up refund `messages`, but if *any single asset* in that iteration has `bounce_fees[asset] > amount_sent`, the function immediately returns `finish(null)` for the *whole* bounce — discarding all previously-built refund messages for other assets that were sufficient to cover their own fees. This mirrors the reported `PayoutStrategy` class of bug: funds legitimately deposited into a contract/AA get permanently stranded because a single-branch check (token vs ETH, or here per-asset fee check) short-circuits the withdrawal path for everything else that was otherwise recoverable.

### Finding Description
`handleTrigger()`'s `bounce(error)` builds the refund unit: [1](#0-0) 

```
if ((trigger.outputs.base || 0) < bounce_fees.base)
    return finish(null);
var messages = [];
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    if (fee > amount)
        return finish(null);
    if (fee === amount)
        continue;
    var bounced_amount = amount - fee;
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
}
if (messages.length === 0)
    return finish(null);
sendUnit(messages);
```

The loop order is `for (var asset in trigger.outputs)`, i.e. it iterates over *all* assets the trigger unit paid to the AA (base bytes plus any other assets included in the same unit, per `assocBalances`/`trigger.outputs` construction seen in `sendDummyUnit` at [2](#0-1)  and the AA-level bounce-fee validation in [3](#0-2) , which shows `bounce_fees` is a per-asset map an AA author can set arbitrarily for any asset).

If the trigger sender pays enough `base` (bytes) to satisfy `bounce_fees.base` (already checked at line 928) but also includes a second asset in the same payment message whose amount is smaller than the AA's `bounce_fees[asset]` for that asset, the loop hits `fee > amount` on that asset and calls `return finish(null)` — abandoning the entire bounce, including the `base` refund that had *already* been computed as sufficient and pushed (or would have been pushed) into `messages`. `finish(null)` sends no unit back at all: none of the sender's bytes or assets are returned.

Crucially, the funds were already credited into the AA's `assocBalances[address]` before validation/bounce runs (this is standard AA processing — funds are attributed to the AA address as soon as the trigger unit is stable, independent of whether the AA logic succeeds). Once `bounce()` takes the `finish(null)` path, those funds simply remain part of the AA's on-chain balance with no messages ever composed to return them. Unless the AA's own state-machine (author-written `messages`/`cases`) happens to have an unrelated code path that later sweeps unexpected assets back to depositors — which most AAs do not, since they are typically written to handle only the specific data/asset combinations the author anticipates — those funds are unrecoverable by the sender. The sender has no way to reach into the AA's balance and force a withdrawal; only the AA's deterministic bytecode logic can emit a payment message, and the aborted `bounce()` path is exactly the mechanism meant to do that.

This is directly analogous to the Sherlock finding: `PayoutStrategy` accepted ETH via `receive()` unconditionally, but `withdrawFunds()` only handled a single asset type at a time (governed by `tokenAddress`), so ETH sent while a token was configured became permanently locked. Here, `bounce()` accepts multi-asset triggers unconditionally (any asset, any amount) but the refund logic is all-or-nothing per invocation and aborts on the very first per-asset shortfall it meets, stranding funds of assets that were otherwise sufficient/refundable.

### Impact Explanation
An unprivileged trigger sender can lose 100% of funds sent to an AA in a single unit (not just the shortfall on one asset) any time:
1. The AA definition sets a non-zero `bounce_fees` entry for some asset other than `base` (a perfectly normal, author-controlled configuration — `checkAAOutputs`/`readAADefinitions` in `aa_addresses.js` shows `bounce_fees` is an arbitrary per-asset map read straight from the AA definition), and
2. the sender's trigger includes that asset with an amount below the configured fee (e.g. by mistake, using a stale/rounded value, or an AA that legitimately expects variable amounts), while also sending enough `base` bytes to have otherwise qualified for a base refund.

The result is an unconditional, irreversible loss of the sender's bytes and asset funds — "AA fund loss/freezing" per the accepted impact classes — triggered purely by a single already-deposited unit, with no cooperation needed from any other party.

### Likelihood Explanation
Likelihood is meaningful whenever an AA sets `bounce_fees` for a non-base asset (common in AAs that accept custom-asset deposits, e.g. token-swap/DEX AAs, subscription/staking AAs) and a legitimate depositor sends slightly less of that asset than the configured fee in the same unit as their base-byte payment — a very plausible user/UX error, since the sender only needs to satisfy `bounce_fees.base`, not necessarily be aware of a secondary asset's fee floor. No malicious actor or race condition is required; this is a straightforward self-inflicted (or AA-author induced) loss condition reachable by any normal user interacting with an AA that has multi-asset bounce fees.

### Recommendation
Change the `bounce()` refund loop so a shortfall in one asset only excludes that asset's refund instead of aborting the entire bounce:
```javascript
var messages = [];
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    if (fee >= amount)
        continue; // skip this asset only, don't abort the whole bounce
    var bounced_amount = amount - fee;
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
}
if (messages.length === 0)
    return finish(null);
sendUnit(messages);
```
This preserves the intended behavior (assets that can't cover their own bounce fee are forfeited as a fee, matching the design's existing per-asset "silently ignore" comment elsewhere in the codebase) while still refunding every other asset — including `base` — that was sufficient.

### Proof of Concept
1. Deploy an AA with `bounce_fees: { base: 10000, "SOME_ASSET": 5000 }` and a `messages`/`cases` block that bounces (returns an error) for the trigger under test (e.g. missing required trigger data).
2. Send a trigger unit to the AA containing:
   - `base`: 20000 (well above `bounce_fees.base`)
   - `SOME_ASSET`: 1000 (below `bounce_fees["SOME_ASSET"]` of 5000)
3. AA execution fails validation and calls `bounce(error)`.
4. In the loop, `asset = 'base'` is processed fine (or `asset = 'SOME_ASSET'` is hit first depending on JS object key iteration order for the trigger.outputs map) — as soon as `SOME_ASSET` is evaluated, `fee(5000) > amount(1000)` triggers `return finish(null)`.
5. No refund unit is ever built or sent; both the 20000 base bytes and the 1000 units of `SOME_ASSET` remain credited to the AA's balance permanently, with no mechanism for the original sender to reclaim them, matching the "concrete... AA fund loss or freezing" outcome required by the validation criteria.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
