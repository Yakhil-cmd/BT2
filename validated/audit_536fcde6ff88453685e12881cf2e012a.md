### Title
Stack-Scoped API Client Tokens Bypass Stack Authorization in CCMenu Endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` resolves the target `stack` via `Stack.from_param!(params[:stack_id])` instead of the shared, scope-enforcing `stacks.from_param!(params[:stack_id])` helper used by every other API controller. As a result, an `ApiClient` token that was deliberately restricted to a single stack (`ApiClient#stack_id`) can be used to read the build/CI status of *any* stack in the Shipit instance, not just the one it was authorized for.

### Finding Description
`Shipit::Api::BaseController` defines the authorization-scoping accessor used across the API: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client is scoped to one, otherwise `Stack.all`. Every other API controller (`Api::StacksController`, etc.) reaches individual stacks through this scoped relation.

`Api::CCMenuController` instead overrides `stack` to call `Stack.from_param!` directly on the unscoped `Stack` model, completely bypassing the `stacks` scoping helper: [2](#0-1) 

The controller only enforces `require_permission :read, :stack`, i.e. it checks that the token *has* the `read:stack` permission string via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` never inspects whether the requested `stack_id` matches the client's own `stack_id` — that check only happens inside the `stacks` scope helper the controller failed to use. The `ApiClient` model and its fixtures confirm that stack-scoping is an intended, first-class authorization boundary (e.g. `here_come_the_walrus` is scoped to a single stack with `read:stack` permission only): [4](#0-3) 

This is the same class of bug as the reported `_mint`/`_update` issue: a security check (`FULL_RESTRICTED_STAKER_ROLE` in the report, stack-scope authorization here) is correctly implemented and enforced on the "normal" code path (`stacks.from_param!` used by `BaseController#stack` and other controllers), but a different internal path (`CCMenuController#stack`) reaches the same privileged resource while skipping the check — breaking the binding `stack the token authorizes == stack the token touches`.

### Impact Explanation
Any holder of a valid, stack-scoped `read:stack` `ApiClient` token can enumerate/read build state (activity, last build status/label/time, lock status) of every stack managed by the Shipit instance by simply changing `stack_id` in the request to `Api::CCMenuController#show`, regardless of the stack the token was actually provisioned for. This is an authorization-scope escalation: unauthenticated (with respect to the target stack) read of stack state, matching the High-severity class "escalation into ... unauthorized read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token that has the `read:stack` permission scoped to some stack (a low-privilege, narrowly-scoped credential intentionally handed out, e.g., embedded in CI-status-monitor URLs). No admin/session access or additional secrets are needed — just changing the `stack_id` path/query parameter.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the record through the scoped relation, consistent with the rest of the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This reuses the `BaseController#stacks` scoping (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) so a stack-scoped token can only ever resolve to its own stack.

### Proof of Concept
1. Provision (or obtain) a `read:stack` `ApiClient` token scoped to `stack_id: A` (e.g., via the `here_come_the_walrus`-style fixture/flow that sets `ApiClient#stack_id`).
2. Call `GET /api/stacks/:stack_id/cc_menu.xml?token=<token>` where `:stack_id` is set to a *different* stack `B` that the token was never granted access to.
3. Observe that `Api::CCMenuController#show` renders `B`'s CI/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state) successfully, because `stack` resolves via unscoped `Stack.from_param!` instead of the client-scoped `stacks.from_param!`, even though the same token would be denied stack `B` on every other `Api::*` endpoint.
