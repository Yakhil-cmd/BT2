### Title
`review_stacks_enabled` fails to gate `allow_with_label`/`prevent_with_label` provisioning due to `&&`/`||` precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with the provisioning-behavior checks using Ruby operator precedence that binds `&&` tighter than `||`, so `review_stacks_enabled` only gates the `allow_all` branch and not `allow_with_label`/`prevent_with_label`. A repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` will still provision a `ReviewStack` if the incoming `pull_request.opened` webhook's PR carries the configured label.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == false` should imply `provision? == false` for all provisioning behaviors. The code: [1](#0-0) 

parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. With `review_stacks_enabled=false`, `provisioning_behavior=:allow_with_label`, `provisioning_label_name='deploy-preview'`, and a PR carrying the `deploy-preview` label, the second disjunct evaluates true, making `provision?` return `true` independent of `review_stacks_enabled`.

`respond_to_pull_request_opened?` gates `process`, which calls `ReviewStackAdapter#find_or_create!` scoped to `repository.review_stacks` [2](#0-1) . Since no `stack` exists yet, `create!` runs, persisting a new `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` (attacker's fork branch) and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) . The `ReviewStack` state machine subsequently triggers `stack.provisioner.up` on provisioning, executing deploy-time automation against the attacker-controlled branch [4](#0-3) .

The attacker's path: open a pull request from their own fork against the target repository (a normal, unprivileged GitHub action), get the `deploy-preview` label applied to that PR, and let GitHub deliver the resulting legitimate, correctly-signed `pull_request`/`opened` webhook. Webhook signature verification (`verify_webhook_signature`) is not bypassed and does not need to be, because the webhook is a real one from GitHub — the flaw is purely in the authorization logic inside `provision?`, not in request authentication.

### Impact Explanation
This causes creation and provisioning of a `Shipit::ReviewStack` bound to attacker-controlled branch content for a repository whose operator explicitly disabled review-stack automation (`review_stacks_enabled: false`). Provisioning invokes the configured `ProvisioningHandler`, meaning deploy-time commands/tasks run against a branch the attacker controls, satisfying "unauthorized deploy... against attacker-controlled branch." This is repeatable for any repository misconfigured with `review_stacks_enabled: false` plus a non-`allow_all` `provisioning_behavior`, by any external contributor able to open a PR and get the trigger label applied.

### Likelihood Explanation
Preconditions: repository has `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` — a plausible misconfiguration since these settings are exposed independently in the repository settings UI [5](#0-4) . Attacker cost is low: open a PR from a fork and (for `allow_with_label`) have the label applied, or (for `prevent_with_label`) simply not apply the label, then let GitHub deliver the webhook. No secrets, tokens, or privileged roles are required.

### Recommendation
Fix operator precedence in `provision?` so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In a minitest `ActiveSupport::TestCase` (e.g. extending `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` patterns): create a `Shipit::Repository` with `review_stacks_enabled: false`, `provisioning_behavior: :allow_with_label`, `provisioning_label_name: 'deploy-preview'`. Build `params` for a `pull_request.opened` event whose `pull_request.labels` includes `{name: 'deploy-preview'}` and `head.ref` set to an attacker branch. Instantiate `OpenedHandler.new(params)` and call `#process`. Assert:
- `repository.review_stacks_enabled == false` (left side of binding)
- `Shipit::Stack.count` increases by 1 and `Shipit::ReviewStack.last.branch` equals the attacker's `head.ref` (right side proving the binding is violated)
- `Shipit::ReviewStackProvisioningQueue.add` is invoked (mock/stub and assert called) for the newly created stack.
