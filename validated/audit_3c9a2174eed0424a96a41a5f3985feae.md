### Title
Unhandled `unwrap()` panics on attacker-influenced arithmetic/state values in swap, deposit, and withdraw paths - (`programs/cp-swap/src/instructions/swap_base_input.rs`, `programs/cp-swap/src/utils/token.rs`)

### Summary
The referenced CVE describes a data submessage that reaches `Fast-CDR`'s deserializer with a malformed value, hitting a code path that calls an unchecked, panicking primitive (`BadParamException`/`assert`) instead of returning a graceful error, crashing the process. The closest reachable analog in this program is the pervasive use of `.unwrap()` on values that are derived from attacker-influenceable inputs (swap amounts, vault balances, and Token-2022 mint extension data) inside `swap_base_input`, `swap_base_output`, `deposit`, and `withdraw`, as well as inside the shared fee-calculation helpers in `utils/token.rs`. If any of these `unwrap()` calls is fed a value that legitimately produces `None`/`Err` (overflow, type-conversion failure, or an `Err` from the SPL Token-2022 fee-math routines), the instruction panics instead of returning a Solana/Anchor `Result::Err`.

### Finding Description
`swap_base_input` computes `constant_before`/`constant_after` via `checked_mul(...).unwrap()` on values derived directly from vault balances and the curve-calculator output [1](#0-0) , and repeatedly narrows `u128` curve results back to `u64` with `u64::try_from(...).unwrap()` for `input_amount`, `output_amount`, `protocol_fee`, `fund_fee`, `creator_fee`, and `trade_fee` [2](#0-1) . None of these conversions is checked with a graceful `ok_or(ErrorCode::...)`; a value that doesn't fit or that overflows the multiplication will abort the transaction with a Rust panic rather than a controlled Anchor error.

Separately, the Token-2022 transfer-fee helpers that are invoked from every swap/deposit/withdraw instruction unconditionally `.unwrap()` the result of `TransferFeeConfig::calculate_epoch_fee` / `calculate_inverse_epoch_fee`, which are `Result`-returning calls that can legitimately return `Err` (e.g. on fee-math overflow) depending on the *mint's own extension data* — data that is attacker/pool-creator controlled when a Token-2022 mint with a `TransferFeeConfig` extension is used as the pool's token: [3](#0-2)  and [4](#0-3) . The inverse-fee path is partially guarded against the `MAX_FEE_BASIS_POINTS` division-by-zero case, but `get_transfer_fee` and the `checked_add(...).unwrap()` used to build the "double-check" fee value in `get_transfer_inverse_fee` are not defensively checked at all.

### Impact Explanation
Because `get_transfer_fee`/`get_transfer_inverse_fee` are called on every `swap_base_input`, `swap_base_output`, `deposit`, and `withdraw` for a given pool whenever either mint is a Token-2022 mint with a `TransferFeeConfig` extension, a value in that extension (or in the caller-supplied swap amount that participates in the fee/curve arithmetic) that drives one of these `unwrap()`s to `None`/`Err` will make **every** subsequent instruction against that pool panic and revert. Repeated, reliable panics on a specific pool amount to a denial-of-service that can prevent liquidity providers and swappers from ever completing operations on the affected pool, which is a form of permanent freezing of the funds held in that pool's vaults, matching the "unhandled exception from malformed data" bug class in the reference CVE.

### Likelihood Explanation
Exploitability is uncertain and could not be fully confirmed from static review alone. The `calculate_epoch_fee`/`calculate_inverse_epoch_fee` overflow conditions in `spl_token_2022` are unlikely to be triggered by ordinary `u64` amounts and `u16` basis-point values because the intermediate math is performed in `u128`, and the `MAX_FEE_BASIS_POINTS` edge case is already special-cased in `get_transfer_inverse_fee`. Likewise, the `checked_mul(...).unwrap()` for `constant_before`/`constant_after` in `swap_base_input` multiplies two `u64` vault-balance values widened to `u128`, which is very unlikely to overflow a `u128`. Whether an unprivileged actor can actually construct a combination of a crafted Token-2022 mint extension (as a pool creator/LP) and swap parameters that drives one of these `unwrap()` calls to `None`/`Err` was **not confirmed** with a concrete proof-of-concept; it depends on precise `spl_token_2022` fee-math internals that are outside the indexed repository and were not verified here.

### Recommendation
Replace every `unwrap()`/`ok_or` panic path in `programs/cp-swap/src/instructions/swap_base_input.rs`, `swap_base_output.rs`, `deposit.rs`, `withdraw.rs`, and `programs/cp-swap/src/utils/token.rs` with checked arithmetic that returns a dedicated Anchor `ErrorCode` (e.g., `ArithmeticOverflow`, `TransferFeeCalculationFailed`) instead of panicking, matching the pattern already used for the `TransferFeeCalculateNotMatch` check.

### Proof of Concept
Not available — reaching the panic requires precise `spl_token_2022` `TransferFeeConfig` fee-math internals (to force `calculate_epoch_fee`/`calculate_inverse_epoch_fee` to return `Err`) or a `u128` overflow on vault-balance products, neither of which was demonstrated to be reachable with realistic on-chain values in this review. This should be validated dynamically (e.g., with a local validator and a custom Token-2022 mint with extreme `TransferFeeConfig` parameters) before treating it as a confirmed exploit.

/// Calculate the fee for output amount
pub fn get_transfer_inverse_fee(mint_info: &AccountInfo, post_fee_amount: u64) -> Result<u64> {
    if *mint_info.owner == Token::id() {
        return Ok(0);
    }
    if post_fee_amount == 0 {
        return err!(ErrorCode::InvalidInput);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    let fee = if let Ok(transfer_fee_config) = mint.get_extension::<TransferFeeConfig>() {
        let epoch = Clock::get()?.epoch;

        let transfer_fee = transfer_fee_config.get_epoch_fee(epoch);
        if u16::from(transfer_fee.transfer_fee_basis_points) == MAX_FEE_BASIS_POINTS {
            u64::from(transfer_fee.maximum_fee)
        } else {
            let transfer_fee = transfer_fee_config
                .calculate_inverse_epoch_fee(epoch, post_fee_amount)
                .unwrap();
            let transfer_fee_for_check = transfer_fee_config
                .calculate_epoch_fee(epoch, post_fee_amount.checked_add(transfer_fee).unwrap())
                .unwrap();
            if transfer_fee != transfer_fee_for_check {
                return err!(ErrorCode::TransferFeeCalculateNotMatch);
            }
            transfer_fee
        }
    } else {
        0
    };
    Ok(fee)
}

            .unwrap()
    } else {
        0
    };
    Ok(fee)
}
