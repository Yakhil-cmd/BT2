### Title
Stack-scoped API tokens can read CI status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup method inherited from `BaseController` in a way that bypasses the `ApiClient`'s stack scoping, letting a token that is authorized (`stack_id`) for only one stack read build/CI status (`lastBuildStatus`, `lastBuildLabel`, lock status, deploy history metadata) of any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` computes the set of stacks a token may see from the client's `stack_id` binding: [1](#0-0) 

`stacks` is `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a single stack, otherwise `Stack.all`, and `stack` resolves the requested `params[:stack_id]` **within that scoped relation** via `stacks.from_param!(...)`. This is the binding the whole API authorization model relies on: *`ApiClient#stack_id` (the stack the token authorizes) == the stack actually resolved and acted upon in the request*.

`Shipit::Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, which only checks the `read:stack` **permission bit** — it does not check which stack it applies to. The controller then re-defines `stack` itself: [2](#0-1) 

This resolves the stack directly from `Stack.from_param!(params[:stack_id])` against the *entire* `Stack` table, completely ignoring `current_api_client.stack_id`. The equality the base controller enforces (`current_api_client.stack_id == resolved stack`) is broken here: the token's authorized stack and the stack actually touched can now be different tenants/repositories.

An `ApiClient` scoped to a single stack (e.g. created via `CCMenuUrlController#client`, which creates a client with only `read:stack` and no stack restriction is intentionally scoped by callers who pass a `stack_id` on creation — see `test/fixtures/shipit/api_clients.yml`'s `here_come_the_walrus` fixture with `stack: shipit`) can therefore be replayed against `GET /api/<any-other-stack>/ccmenu.xml?token=...` and successfully return that other stack's status, in violation of the intended per-stack authorization scope. [3](#0-2) 
`check_permissions!` only validates the operation/scope string (`read:stack`), never the specific stack — the stack restriction is supposed to be enforced purely through the `stacks`/`stack` helper in `BaseController`, which `CCMenuController` circumvents.

The existing test suite only exercises the case with an unscoped (`spy`) client and never verifies that a `stack`-scoped client is denied access to a different stack via this controller, so the gap is untested: [4](#0-3) 

### Impact Explanation
This meets the High bar for "unauthenticated/unauthorized read of stack state, task streams or deploy output": a token deliberately restricted to a single stack (a common integration pattern — CI dashboards, status badges, embeds shared with third parties) can read build status, lock reason, and last-deploy metadata of every other stack managed by the Shipit instance, including private/internal repositories the token holder was never granted access to. This is a cross-stack authorization bypass caused entirely by the engine's own controller code, not by GitHub or any external dependency.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API tokens (which is exactly what `CCMenuUrlController` is designed to produce and hand out, e.g. embedded in a CI status URL shared externally). Exploitation requires no privileged access beyond possessing one valid, narrowly-scoped token — the attacker only needs to change the `stack_id` route/query parameter to a different stack's identifier.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` relation inherited from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `ApiClient#stack_id` binding is enforced consistently across all API controllers.

### Proof of Concept
1. Create (or have the app create via `CCMenuUrlController`) an `ApiClient` scoped to `stack_id: <Stack A>.id` with permission `read:stack`, and obtain its `authentication_token`.
2. Note the `to_param` of a different `Stack B` that this token was never granted access to.
3. Send `GET /api/<Stack B path>/ccmenu.xml?token=<Stack A's token>` (or with `Authorization: Basic` using that token).
4. Observe that the request succeeds (200 OK) and returns Stack B's build status/lock state, even though the token is only authorized for Stack A — confirming the `stacks` scoping enforced in `BaseController#stack` (app/controllers/shipit/api/base_controller.rb:74-80) is bypassed by `CCMenuController#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31).
