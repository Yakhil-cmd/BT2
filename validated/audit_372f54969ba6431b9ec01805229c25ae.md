The migration name `index_commits_on_stack_id_and_sha` confirms `sha` uniqueness/indexing is scoped to `(stack_id, sha)`, not globally unique — i.e., the schema itself permits identical `sha` values to exist across many different stacks (this is expected, since forks/templates share commit history). This is the exact condition the vulnerability depends on.

### Title
`StatusHandler#process` writes `Status` rows to every stack whose commits share a SHA, regardless of the webhook's own repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table and calls `create_status_from_github!` on every match, with no filter on the repository named in the webhook payload. Combined with `Status.replicate_from_github!`'s `find_or_create_by!` key (`stack_id, state, description, target_url, context, created_at` — no `sha`), a single validly-signed "status" webhook from one tenant's repository can create `Status` rows, flip commit CI state, and trigger `ProcessMergeRequestsJob` merges on every other stack that happens to contain a commit with the same SHA.

### Finding Description
Binding claimed: "number of repositories a single verified webhook is entitled to mutate (1, the repository named in its own payload) == number of repositories actually mutated (N)". Tracing the code shows this binding is broken.

`WebhooksController#verify_signature` only authenticates that the payload was HMAC-signed by the GitHub org identified by `repository_owner` (`params.dig('repository','owner','login')`) [1](#0-0) . This proves *who sent the event*, not *which repository/stack is entitled to be mutated*.

Every other GitHub-payload handler (`PullRequest::OpenedHandler`, `ClosedHandler`, `LabelCapturingHandler`, etc.) explicitly requires `repository.full_name` in its param schema and resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack [2](#0-1) . `StatusHandler` does not:

```
params do
  requires :sha, String
  requires :state, String
  accepts :description, String
  accepts :target_url, String
  accepts :context, String
  accepts :created_at, String
  accepts :branches, Array do
    requires :name, String
  end
end

def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

There is no `repository` requirement, and `Commit.where(sha:)` is unscoped by stack or repository. The base `Handler` class even exposes a `stacks`/`repository_name` scoping helper [4](#0-3)  that `StatusHandler` simply doesn't use.

The `commits` table's uniqueness index is `(stack_id, sha)` (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the same `sha` can legitimately exist across many unrelated stacks (forks, shared template history, cherry-picked/rebase-preserved commits). For each matching `Commit`, `create_status_from_github!` delegates to `statuses.replicate_from_github!(stack_id, github_status)`, which is keyed on `(stack_id, state, description, target_url, context, created_at)` — again no `sha`/`commit_id` — so a single crafted payload deterministically creates one `Status` per colliding stack: [5](#0-4) [6](#0-5) 

Each created `Status` runs `add_status`, which flips the commit's CI state, emits `commit_status`/`deployable_status` hooks, and calls `stack.schedule_merges` (→ `ProcessMergeRequestsJob`) when the new state is `pending`/`success`: [7](#0-6) [8](#0-7) 
`ProcessMergeRequestsJob` will merge any pending merge request whose status checks now pass: [9](#0-8) 

Existing guards do not stop this: `verify_signature` only checks the sender's org identity, not the target repository [10](#0-9) ; `ExplicitParameters` for `StatusHandler` never requires or validates `repository` at all; and neither `Status` nor `Commit#create_status_from_github!` assert that the commit's stack corresponds to the payload's repository.

Attack: attacker owns/administers a repository whose org is already onboarded to this Shipit instance (a legitimate low-privilege tenant). That repo shares one or more commit SHAs with victim stacks (fork of a popular template, or a fork of the victim repo itself, both of which preserve identical commit SHAs). Attacker uses their normal push/write access to that repository to set a commit status (via GitHub's status API, or by pushing a commit that triggers CI to post a status) with `state`, `description`, `context`, `created_at` chosen to match. GitHub delivers one genuinely-signed webhook to Shipit's `/webhooks` for that event. `StatusHandler#process` then iterates `Commit.where(sha:)` across all stacks matching that SHA — including victim stacks in unrelated repositories/orgs — and writes a `Status` row and runs merge-processing side effects on each of them.

### Impact Explanation
A webhook authenticated for one repository/org mutates commit/CI state, and can trigger unauthorized merges, in stacks belonging to unrelated repositories and tenants. This matches the Critical category explicitly listed in scope ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The blast radius is every stack across every tenant of a shared Shipit instance whose commit history intersects (by SHA) with the attacker-controlled repository — repeatable per crafted SHA/state/description/context/created_at combination, and amplifiable by iterating known public commit SHAs from popular templates.

### Likelihood Explanation
Preconditions: attacker must control (push/admin) a repository already integrated with the target Shipit instance (so GitHub will deliver a genuinely HMAC-signed "status" webhook for their org), and one or more victim stacks must contain a `Commit` row with a matching `sha` (realistic via forks of the victim repo or shared bootstrapping/template commits, since git preserves SHAs across forks and identical-content-and-metadata commits hash identically). No secrets, sessions, or elevated GitHub permissions are required beyond ordinary write access to the attacker's own repository. This is feasible in any multi-tenant Shipit deployment and is fully repeatable/scriptable (iterate known SHAs, replay per victim).

### Recommendation
Scope `StatusHandler` the same way as the other webhook handlers: require `repository.full_name` in the params schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `repository.stacks.commits.where(sha: params.sha)` (or equivalent join through `stack: :repository`) instead of the unscoped `Commit.where(sha:)`. Additionally, include `commit_id`/`sha` in `Status.replicate_from_github!`'s uniqueness key so idempotency is enforced per-commit rather than per attribute tuple.
