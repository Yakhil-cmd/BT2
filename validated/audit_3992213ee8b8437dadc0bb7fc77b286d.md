### Title
Attacker-Controlled `github-repo` Frontmatter Metadata Silently Redirects `gh skill install` to an Arbitrary Repository - (File: `pkg/cmd/skills/install/install.go`)

### Summary
`gh skill install` trusts the `github-repo` metadata field embedded in a remote `SKILL.md` file — content fully controlled by the repository the user is installing from — to decide whether to redirect the install to a different, attacker-named "upstream" repository. When `--upstream` is passed (or the user picks the offered choice interactively), `gh` fetches and installs skill content from whatever repository the untrusted frontmatter names, without any cryptographic or ownership verification that this "upstream" is legitimate.

### Finding Description
`installRun` calls `checkUpstreamProvenance` after discovering a matching skill in the user-specified repository [1](#0-0) . This function fetches the skill's `SKILL.md` from the GitHub Contents API and parses its YAML frontmatter for a `github-repo` key that the *source repository itself* supplies: [2](#0-1) 

If that field differs from the current repo, the parsed value is treated as an authoritative "upstream" location and, when `--upstream` is set, `gh` immediately swaps `opts.repo` and recursively re-runs the whole install flow against it — fetching and writing that repository's files to disk instead of the one the user actually specified on the command line: [3](#0-2) [4](#0-3) 

`ParseRepoURL`/`ParseMetadataRepo` perform no validation beyond syntactic parsing of `OWNER/REPO` — they do not verify that the named "upstream" actually owns/authored the skill, nor that it corresponds to any real provenance relationship: [5](#0-4) .

This mirrors the structure of the referenced Aave finding: a resource-consuming operation (claiming rewards / installing a skill) defers its access-control decision (who is authorized to claim / which repo is the "real" source) to a third party's self-declared, unauthenticated state (the `RewardsController` emission manager's claimer list / the installed repo's own frontmatter), rather than to something the invoking user or protocol actually controls. In both cases, an untrusted party can unilaterally redirect a privileged action toward a destination of their choosing.

### Impact Explanation
An attacker who controls a "re-publisher" repository (e.g. one that ranks well in `gh skill search`, or one a victim is lured into installing from) can embed a `github-repo:` metadata value pointing to any repository they name — including another repository they control that looks trustworthy (a similarly-named org/repo, or one they've dressed up to look "official"). With `--upstream` used non-interactively (a documented, supported flag: [6](#0-5) ), the install silently follows that pointer and installs unreviewed files (including scripts, per `skills/gh-skill/SKILL.md`) from the attacker-chosen destination. The installed content is written to a skills directory an agent later reads and may execute/interpret prompts from, which the codebase's own disclaimer explicitly flags as risky: [7](#0-6) 

Because the redirect target is entirely self-declared by the source repo and not cross-checked with any authoritative signal (no ownership proof, no attestation, no allow-list), this is a trust/provenance bypass: it lets untrusted content assert its own upstream and have that assertion acted upon automatically.

### Likelihood Explanation
Exploitation requires a victim to run `gh skill install <attacker-repo> <skill> --upstream` (or accept the interactive "upstream" choice) against a repository the attacker controls or has manipulated. This is a normal, documented `gh` command path (no special privileges needed by the attacker beyond publishing a public GitHub repo with a crafted `SKILL.md`), making it an unprivileged, remote-attacker-reachable path through ordinary `gh skill install` usage. Interactive users are shown a prompt distinguishing "re-publisher" vs "upstream" and a general "not verified by GitHub" disclaimer, which reduces but does not eliminate risk in interactive use; non-interactive/automated use with `--upstream` (e.g., in CI or agent self-management flows described in `skills/gh-skill/SKILL.md`) redirects without further confirmation.

### Recommendation
- Do not treat repository-supplied `github-repo` frontmatter as authoritative for redirecting the install source. At minimum, require the redirect target to be independently confirmed (e.g., only redirect to repos explicitly allow-listed by the user, or the same owner/org, or a target with reciprocal provenance metadata pointing back).
- Surface the actual repository/owner difference more prominently before any file is written, and require explicit interactive confirmation even when `--upstream` is passed, or add a distinct `--upstream-confirm`-style safeguard for non-interactive automation.
- Consider validating that the claimed upstream in a "re-publisher" repo is cryptographically/organizationally linked (e.g., via a GitHub-verified topic/attestation) rather than a bare-text frontmatter field.

### Proof of Concept
1. Attacker creates public repo `attacker/lure-skills` containing `skills/git-commit/SKILL.md` with:
   ```yaml
   ---
   name: git-commit
   description: Writes commits
   metadata:
     github-repo: https://github.com/attacker/payload-skills
   ---
   ```
2. `attacker/payload-skills` contains a malicious `git-commit` skill (e.g. a `scripts/setup.sh` with harmful commands, as supported by the publish/install flow: [8](#0-7) ).
3. Victim runs (e.g. scripted/CI): `gh skill install attacker/lure-skills git-commit --upstream --force`.
4. `checkUpstreamProvenance` detects the `github-repo` mismatch, prints "Redirecting install to attacker/payload-skills...", and `installRun` recurses against the attacker-chosen repo [9](#0-8) , installing the payload's files onto disk without further verification.

**Uncertainty note:** I could not verify whether any additional server-side (GitHub API) restriction exists that would prevent an attacker from freely naming an arbitrary `github-repo` value pointing to a repo they don't own, beyond the client-side parsing/validation shown above — this appears to be purely client-trusted metadata based on the code reviewed.

// ParseRepoURL parses a repository URL stored in skill metadata.
func ParseRepoURL(raw string) (ghrepo.Interface, error) {
	raw = strings.TrimSpace(raw)
	if raw == "" {
		return nil, fmt.Errorf("repository URL is empty")
	}

	repo, err := ghrepo.FromFullName(raw)
	if err != nil {
		return nil, fmt.Errorf("invalid repository URL %q: %w", raw, err)
	}

	return repo, nil
}

// ParseMetadataRepo extracts repository information from skill metadata.
func ParseMetadataRepo(meta map[string]interface{}) (ghrepo.Interface, bool, error) {
	if meta == nil {
		return nil, false, nil
	}

	repoValue, _ := meta["github-repo"].(string)
	if repoValue == "" {
		return nil, false, nil
	}

	repo, err := ParseRepoURL(repoValue)
	if err != nil {
		return nil, true, err
	}

	return repo, true, nil
}
