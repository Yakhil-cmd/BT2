### Title
Cross-stack read of build/deploy status via `Api::CCMenuController#stack` bypassing the API token's stack scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` records can be scoped to a single `Stack` (`stack_id`), and `Shipit::Api::BaseController#stacks`/`#stack` enforce that scope by restricting the queryable set to `Stack.where(id: current_api_client.stack_id)` before resolving `params[:stack_id]`. `Api::CCMenuController` overrides `#stack` and resolves it directly against the global `Stack` relation, discarding the scoping performed by the base class, so a token that is only authorised for one stack can be used to read CI/deploy status data for any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the authorization-scoping primitives used by every API endpoint: [1](#0-0) 

`stacks` restricts the visible set of stacks to the one the `ApiClient` is bound to (`current_api_client.stack_id`), and `stack` resolves `params[:stack_id]`/`params[:id]` only within that restricted relation. This is the mechanism that turns "a token that authorises stack A" into "a stack the code will actually touch is stack A".

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely and resolve the requested stack against the full, unscoped `Stack` relation: [2](#0-1) 

The only authorization gate that remains is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 

This check is purely a bitmask/allow-list check against the string `read:stack` — it never consults `stack_id`. As demonstrated by the fixture and test suite, a client can legitimately be created scoped to exactly one stack: [4](#0-3) 

and the tests confirm that the `stacks`/`index` endpoints correctly restrict such a client to its single authorised stack: [5](#0-4) 

But because `CCMenuController#stack` re-implements the lookup with `Stack.from_param!(params[:stack_id])` instead of calling the inherited `stacks.from_param!`, the `stack_id`-scoping property is dropped for this one controller. The route is registered globally under `/ccmenu/*stack_id`: [6](#0-5) 

so any holder of a valid, deliberately narrow-scoped `read:stack` token (e.g. one distributed to a CI dashboard for a single project, as created by `CCMenuUrlController`) can substitute an arbitrary other stack's identifier in the URL and receive that stack's CCMenu XML (name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) as shown by `Api::CCMenuController#show`: [7](#0-6) 

The equality that should hold is: `stack authorised by token (current_api_client.stack_id)` == `stack acted on by the request (params[:stack_id])`. `CCMenuController` breaks this equality by resolving the latter without checking the former.

### Impact Explanation
This is an authorization-scope violation: a legitimately-issued, deliberately-restricted API credential (created via the "CCMenu Client" flow with `permissions: %w[read:stack]` and bound to one stack) can be replayed against any other stack's CCMenu endpoint to read that stack's deploy/build status information cross-tenant. This falls under "unauthenticated [or under-privileged authenticated] read of stack state" for stacks the credential was never authorised to see, matching the High-impact category of escalation beyond the credential's granted scope.

### Likelihood Explanation
High. No special conditions are required beyond possessing any valid `read:stack`-scoped `ApiClient` token bound to a single stack (these tokens are handed out routinely, e.g. by `CCMenuUrlController#client`, to embed in CI badges/URLs which are often shared or exposed). The attacker only needs to change the `stack_id` segment of the otherwise-public CCMenu URL.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scoped lookup instead of querying `Stack` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction from `BaseController#stacks` is honored, consistent with every other API controller.

### Proof of Concept
1. As an admin, create (or have created) a scoped `ApiClient` bound to `Stack A` with permission `read:stack` only (mirrors the `here_come_the_walrus` fixture / `CCMenuUrlController#client`), and obtain its `authentication_token`.
2. Use that token to request `GET /ccmenu/<StackA-owner>/<StackA-name>/<StackA-env>?token=<token>` — succeeds as expected, returns Stack A's CCMenu XML.
3. Reuse the same token to request `GET /ccmenu/<StackB-owner>/<StackB-name>/<StackB-env>?token=<token>` where Stack B is a different stack the token was never scoped to.
4. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (unscoped) rather than `stacks.from_param!` (scoped to `current_api_client.stack_id`), the request succeeds and returns Stack B's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), even though the token is only authorised for Stack A.
