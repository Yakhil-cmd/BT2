### Title
Cross-organization webhook can hijack any existing `Shipit.github_teams` team membership by `github_id` collision - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves a `Team` purely by the attacker-supplied integer `params.team.id` (`github_id`), with no check that the `params.organization.login` in the payload—whose signature is verified against that same attacker-named organization's own webhook secret—actually owns that `github_id`. An attacker who legitimately controls one configured Shipit tenant organization can therefore sign a valid membership webhook naming their own org, but set `team.id` to the `github_id` of an unrelated, privileged team (one of `Shipit.github_teams`), causing `team.add_member(member)` to add an arbitrary GitHub login to that privileged team and pass `User#authorized?`.

### Finding Description
The claimed binding is: every `github_id` passed to `find_or_create_team!` == a `github_id` that the organization named in the same webhook (and whose secret validated the signature) truly owns on GitHub. This binding is **not enforced** anywhere in the code path.

- `WebhooksController#verify_signature` derives `repository_owner` from the payload itself: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and validates the signature using `Shipit.github(organization: repository_owner)`'s webhook secret [2](#0-1) . For a `membership` event there is no `repository` key, so `repository_owner` is simply `organization.login`, an attacker-controlled field naming *their own* legitimately-configured tenant org.
- `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [3](#0-2) . The block (which sets `organization`) only runs on **create**; when `github_id` collides with an existing `Team` row, the existing row (with its true `organization`) is returned untouched, but `team.add_member(member)` / `team.members.delete(member)` still executes unconditionally against it [4](#0-3) [5](#0-4) .
- `Shipit.github_teams` (the authorization allowlist) is built once from configured `oauth.teams` handles resolved to real `github_id`s via the GitHub API [6](#0-5) , and `User#authorized?` grants access purely by checking membership in one of those team IDs [7](#0-6) .

Attack: attacker controls tenant org "attacker-org" (has installed the Shipit GitHub App there and thus can produce valid HMAC signatures with that org's `webhook_secret`, but is not a member of `Shipit.github_teams`). Attacker POSTs a signed `membership` webhook with `organization.login = "attacker-org"`, `action: "added"`, `member.login = "attacker"`, and `team.id` equal to the `github_id` of a real, privileged team belonging to a different, victim organization (team IDs are enumerable/guessable integers, visible via GitHub's own team API or brute force). `verify_signature` passes because it validates against attacker-org's own secret. `find_or_create_team!` finds the existing victim team by `github_id` and `team.add_member(attacker_user)` runs, silently granting the attacker's Shipit user membership in that privileged team and thus `authorized? == true`.

None of the existing guards prevent this: `verify_signature` only proves the request came from *some* configured org, not that the org owns the specific `team.id` referenced in the body; `drop_unhandled_event` doesn't apply (membership is handled); the `ExplicitParameters` schema only requires `Integer`/`String` types with no range/ownership constraint; there is no model validation tying `Team#organization` to `Team#github_id` on lookup.

### Impact Explanation
The attacker gains unauthenticated-relative-to-GitHub-team escalation: their Shipit `User` record becomes a member of a `Shipit.github_teams`-configured team without ever actually belonging to that GitHub team, bypassing the entire team-based authorization model (`User#authorized?`). This is repeatable against any team whose `github_id` the attacker can enumerate/guess, and is cross-tenant (a payload signed by one organization's secret mutates team membership belonging to a completely different organization). This matches the "High - escalation into `Shipit.github_teams` authorization" impact category.

### Likelihood Explanation
Preconditions: Shipit must be configured for multiple GitHub organizations (an explicitly documented and supported feature) and the attacker must control at least one of those configured, less-privileged organizations (i.e., have installed the Shipit GitHub App there, giving them their own valid `webhook_secret`). GitHub team `id` values are small sequential integers and are exposed via GitHub's own team/org APIs, making them trivial to enumerate or guess. Given these preconditions, the attack is a single signed HTTP POST, fully repeatable, with no rate limiting or additional secrets required.

### Recommendation
In `find_or_create_team!`, verify that `params.organization.login` matches the `organization` already stored on any existing `Team` with that `github_id` before mutating membership (reject/alert on mismatch instead of silently reusing the record), and/or bind webhook processing to the organization that owns the specific `team`/`repository` referenced in the payload rather than trusting the payload's `organization.login` alone for secret selection.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb` style, illustrative — not executable as-is since it targets excluded `test/**`, but describes the exact assertions):
1. Fixture: `shipit_teams(:developers)` with `github_id: 1042`, `organization: "victim-org"`.
2. Stub `Shipit.github(organization: "attacker-org")` to return a `GitHubApp` whose `verify_webhook_signature` returns `true` (simulating attacker's own valid, unrelated webhook secret).
3. POST `X-Github-Event: membership` payload: `{ action: "added", team: { id: 1042, name: "x", slug: "x", url: "https://x" }, organization: { login: "attacker-org" }, member: { login: "attacker" } }`.
4. Assert before: `shipit_teams(:developers).members.map(&:login)` does not include `"attacker"`.
5. Assert after `post :create`: `shipit_teams(:developers).reload.members.map(&:login)` includes `"attacker"`, and `Team.count` unchanged (no new team created) — proving the payload signed for `"attacker-org"` mutated `"victim-org"`'s team, violating the binding "every `github_id` accepted == a `github_id` owned by the verified requesting organization."
