### Title
`repository_owner` verification-selector diverges from `repository.full_name` handler-target, allowing cross-organization webhook forgery on `pull_request`/`reopened` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify a webhook against using `repository_owner`, which falls back from `params.dig('repository','owner','login')` to `params.dig('organization','login')` when the repository owner is absent. `ReopenedHandler` (and all other `PullRequest` handlers), however, resolve the target stack from an entirely different field, `params.repository.full_name`. In a multi-organization Shipit deployment (`Shipit.github_organizations` / per-org `secrets.github` config, as exercised by `test/dummy/config/secrets_double_github_app.yml`), an attacker who controls a payload for one configured organization can pick which org's secret verifies the request while pointing the actual mutation at a different org's repository/stack.

### Finding Description
The broken binding: the code implicitly assumes
`repository_owner (used to select the verifying GitHubApp/secret) == repository.full_name.split('/').first (used by the handler to select the target Repository/Stack)`.

Trace:
- `Shipit::WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the raw request body against that org's `webhook_secret` [1](#0-0) .
- `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .
- `Shipit.github(organization:)` looks up per-organization config via `github_app_config(organization)`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that organization's `webhook_secret` is blank/unset: `return true unless webhook_secret` [3](#0-2) . The dummy multi-org fixture demonstrates that organizations can legitimately have `webhook_secret: # nil` configured [4](#0-3) .
- `ReopenedHandler`, by contrast, resolves the target `Repository`/`ReviewStack` solely from `params.repository.full_name`, completely independent of `organization.login` or `repository.owner.login`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , then `stack.unarchive!` in `process` [6](#0-5) .

Exploit flow: attacker crafts a `pull_request` webhook with `action: "reopened"`, `repository.full_name` set to the victim org's repo (satisfying the handler's `ExplicitParameters` schema, which only `requires :repository { requires :full_name }` and never requires `repository.owner.login`) [7](#0-6) , while omitting `repository.owner.login` and setting `organization.login` to an org that the attacker knows/controls or that has a weak/absent `webhook_secret`. `repository_owner` then resolves to that other org, `verify_signature` passes trivially (no secret, or a secret the attacker knows), and the handler still unarchives/recreates the victim's `ReviewStack` for the named `repository.full_name`. Because the victim stack has `bot_login` configured, any subsequent auto-deploy runs as that bot identity (`Shipit.user` → `User.find_or_create_by_login!(github.bot_login)` [8](#0-7) ), amplifying impact into an unauthorized deploy performed under the bot's authority.

Why existing guards don't stop this: `verify_signature`'s only failure mode is `GithubOrganizationUnknown` (422) when the fallback organization isn't configured at all [9](#0-8) ; it does not cross-check that the organization used for verification matches the owner embedded in `repository.full_name` that the handler will actually act on. `ExplicitParameters` only validates presence/types of declared fields, not cross-field consistency. No handler re-validates that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name`.

### Impact Explanation
This is a payload-for-one-repository (or one org's weak/no-secret config) causing a mutation on another org's/repo's stack — the `Critical` category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." Concretely, the attacker can unarchive/recreate a `ReviewStack` for an arbitrary repository configured in the same Shipit instance without ever presenting that repository's own webhook secret, provided any other organization in the same Shipit deployment has no `webhook_secret` configured (a real, supported configuration per the fixture) or a secret the attacker can obtain independently. This is repeatable against any repository/stack reachable via `Repository.from_github_repo_name`, and since `unarchive!`/provisioning can trigger auto-deploys under the configured `bot_login`, the blast radius extends to unauthorized deploy execution.

### Likelihood Explanation
This requires a specific precondition: the Shipit instance must be configured with multiple GitHub organizations (`secrets.github` keyed by org) where at least one organization's `webhook_secret` is unset/weak, OR the attacker otherwise knows/leaks that org's `webhook_secret` (out of scope per rules, since obtaining secrets is excluded). Single-organization deployments (the common case, `github_default_organization` non-`nil` only path or single legacy config) are not exploitable this way because there is only one `webhook_secret` to verify against regardless of which field is read. The engine's own code permits and ships fixtures for the multi-org, weak-secret configuration, so the divergence is a genuine engine defect, but real-world exploitability is gated on that specific multi-tenant misconfiguration existing.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, derive the organization used for signature verification from the same field the downstream handler will use to resolve the target repository/stack — i.e., use `repository.full_name`'s owner segment (or require `repository.owner.login` to be present and match `organization.login` when both exist) rather than falling back to `organization.login` alone. Additionally, handlers such as `ReopenedHandler`/`OpenedHandler`/`ClosedHandler`/`LabeledHandler`/`UnlabeledHandler` should verify that the resolved `Repository`'s owner matches the organization that authenticated the request before mutating any `ReviewStack`.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, under a multi-org fixture like `secrets_double_github_app.yml`):
1. Configure two orgs, `OrgOne` (victim, has a real `webhook_secret`) and `OrgTwo` (attacker-reachable, `webhook_secret: nil`).
2. Create `shipit_repository` for `OrgOne/victim-repo` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`, and a `bot_login` configured; create an archived `ReviewStack`/pull request for it.
3. POST `/webhooks` with `X-Github-Event: pull_request`, body:
```json
{
  "action": "reopened",
  "number": 1,
  "pull_request": { ... "state": "open", "labels": [] },
  "repository": { "full_name": "OrgOne/victim-repo" },
  "organization": { "login": "OrgTwo" },
  "sender": { "login": "attacker" }
}
```
No `repository.owner.login` present; no valid `X-Hub-Signature` for `OrgOne`'s secret.
4. Assert both sides of the binding before tracing: `repository_owner` resolves to `"OrgTwo"` (`params.dig('repository','owner','login') || params.dig('organization','login')` → `nil || "OrgTwo"`), while the handler's target owner is `"OrgOne"` (from `params.repository.full_name.split('/').first`) — the two values are unequal.
5. Assert `response.status == 200` (verification passed via `OrgTwo`'s nil secret) and that the `OrgOne/victim-repo` `ReviewStack.archived?` transitioned to `false` (i.e., `stack.unarchive!` executed), demonstrating a request authenticated by `OrgTwo` mutated a stack belonging to `OrgOne`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
