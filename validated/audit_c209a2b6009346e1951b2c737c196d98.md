### Title
Server-Side Request Forgery via unvalidated Arbstore URL in arbiter contract flow - (File: arbiter_contract.js)

### Summary
The arbiter-contract feature lets any wallet address be nominated as `arbiter_address` in a private, peer-to-peer contract offer. When the contract reaches dispute/appeal/completion stages, the local wallet resolves this address to a URL via the hub (`hub/get_arbstore_url`) and then makes raw outbound HTTP requests to that URL, carrying JSON payloads that include contract and payment details. Neither the URL received from the hub nor the request-issuing code validates the scheme, host, or IP range before connecting, which is a classic SSRF pattern (CWE-918), analogous to the kityminder `ImageCapture` SSRF where an attacker-influenced URL is fetched without validation.

### Finding Description
`arbiter_contract.js` resolves the arbstore endpoint purely from the attacker-nominatable `arbiter_address` and then performs raw HTTP requests to whatever URL is returned, with no scheme/host allow-listing or private-IP blocking: [1](#0-0) [2](#0-1) 

`arbiters.js` has the same pattern for `getArbstoreInfo`/`requestInfoFromArbStore`, which is invoked from `deriveSharedAddress` while composing the arbiter-contract's shared address (a step driven by the peer-supplied `arbiter_address`): [3](#0-2) 

Crucially, `arbiter_address` — the value that ultimately determines which URL gets contacted — is accepted from the untrusted counterparty in the `arbiter_contract_offer` device message and is only checked for being a syntactically valid address, not for being a legitimate/trusted arbstore operator: [4](#0-3) 

Because anyone can generate an address and register it with a hub as an "arbiter" (pointing `hub/get_arbstore_url` to any URL of their choosing, e.g. `http://127.0.0.1:PORT/...`, `http://169.254.169.254/...`, or an internal service), a malicious private-payment counterparty can:
1. Propose (or induce acceptance of) an arbiter contract naming an `arbiter_address` they control.
2. Have that address registered on the (non-malicious) hub with an attacker-chosen URL.
3. Wait for the victim to call `openDispute`, `appeal`, `getAppealFee`, or `deriveSharedAddress`/`complete`, all of which trigger `httpRequest`/`requestInfoFromArbStore` to fetch/post to that URL — with no validation that the destination is a legitimate external, public HTTPS endpoint.

This matches the report's root cause exactly: a URL originating from user-influenced input is fetched/POSTed to without any SSRF hardening (no protocol restriction, no private/link-local IP blocking, no destination allow-list).

### Impact Explanation
The victim's wallet process will issue outbound HTTP(S) requests (GET in `arbiters.js`, POST with contract JSON — including `contract_hash`, addresses, encrypted contract package, and for private assets the payment `amount`/`asset` — in `arbiter_contract.js`) to an attacker-chosen destination. This can be used to:
- Probe/attack internal network services or cloud metadata endpoints reachable from the victim's host (classic SSRF exploitation), which is a significant confidentiality/integrity risk within the "wallet and contract message handling" reachable surface named in scope.
- Exfiltrate contract/payment data (via the POST body) to an attacker-controlled or internal endpoint, since the wallet blindly serializes contract state (`data`/`dataJSON`) and POSTs it to the resolved URL.

This does not directly cause double-spend/inflation/consensus divergence, but it does allow a low-privilege private-payment counterparty to weaponize the victim's own node for network reconnaissance/exfiltration and against internal infrastructure, satisfying the "Medium/High/Critical" severity bar via unauthorized data exposure and internal network reach, consistent with the reported CVSS (AC:L/PR:N/UI:N/C:H).

### Likelihood Explanation
Likelihood is High: the `arbiter_address` field of a contract offer is entirely attacker-supplied and only address-format-validated (`wallet.js:617-654`); no capability or reputation check on the "arbiter" role is performed before the wallet trusts the hub-provided URL and issues requests to it. Any user can act as an "arbiter" from the protocol's point of view, and the exploitation requires no compromise of the hub — it only requires the attacker to register their own arbiter identity, a normal user action.

### Recommendation
- Validate URLs returned by `hub/get_arbstore_url`/`hub/get_arbstore_url_by_address` before use in `arbiters.js` and `arbiter_contract.js`: enforce `https:` scheme, reject requests to loopback/link-local/private IP ranges (127.0.0.0/8, ::1, 169.254.0.0/16, RFC1918 ranges, etc.), and resolve DNS before connecting to prevent DNS-rebinding.
- Maintain an explicit allow-list/registry of trusted arbstore hosts rather than trusting any hub-returned URL tied to an arbitrary user-nominated address.
- Apply the same hardening to `uri.js`'s `fetchUrl` used for `https://` definition URLs in the `byteball:`/`obyte:` URI scheme.
- Consider requiring user confirmation before the wallet performs any outbound network request to a newly-seen arbstore host, and surface the resolved host to the user for review prior to sending contract data.

### Proof of Concept
1. Attacker creates a wallet address `A` and registers it as an arbiter with the (legitimate) hub, providing `hub/get_arbstore_url` → `http://169.254.169.254/latest/meta-data/` (or any internal address the attacker wants the victim to probe/POST to).
2. Attacker, as a private-payment counterparty, sends an `arbiter_contract_offer` to the victim with `arbiter_address = A` (`wallet.js:617-654` only checks it's a syntactically valid address).
3. Victim accepts the contract, pays, and later calls `openDispute` (or `appeal`/`getAppealFee`/`complete`, all in `arbiter_contract.js`), or the wallet internally calls `arbiters.getArbstoreInfo`/`getInfo` during `deriveSharedAddress`.
4. The wallet resolves the URL via the hub and calls `httpRequest`/`requestInfoFromArbStore`, sending an HTTP GET/POST — containing contract metadata in the POST body for the dispute/appeal flows — to the attacker-controlled/internal target with no scheme or IP-range validation, demonstrating SSRF. function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();

function getInfo(address, cb) {
	cb = cb || function() {};
	db.query("SELECT device_pub_key, real_name FROM wallet_arbiters WHERE arbiter_address=?", [address], function(rows){
		if (rows.length && rows[0].real_name) { // request again if no real name
			cb(null, rows[0]);
		} else {
			device.requestFromHub("hub/get_arbstore_url", address, function(err, url){
				if (err) {
					return cb(err);
				}
				if (!validationUtils.isNonemptyString(url))
					return cb("invalid url received from hub");
				requestInfoFromArbStore(url+'/api/arbiter/'+address, function(err, info){
					if (err) {
						return cb(err);
					}
					if (!validationUtils.isNonemptyObject(info))
						return cb("invalid arbiter info received from arbstore");
					db.query("REPLACE INTO wallet_arbiters (arbiter_address, device_pub_key, real_name) VALUES (?, ?, ?)", [address, info.device_pub_key, info.real_name], function() {cb(null, info);});
				});
			});
		}
	});
}
