### Title
Gas/complexity mispricing in oscript AA formula evaluation allows cheap, unbounded-cost cloning to exceed the intended compute budget - ([File: formula/evaluation.js])

### Summary
`ocore`'s AA formula language enforces a `MAX_OPS`/`MAX_COMPLEXITY` budget at validation time (`formula/validation.js`, `aa_validation.js`) so that a single trigger's total execution cost is bounded before it is allowed to run [1](#0-0) . However, `count_ops`/`complexity` are counted per AST node/operation, not per unit of actual work performed by that operation. Several operations (`cloneDeep` of stateVars/wrappedObjects, `json_stringify` key-sorting, array/dictionary building, `map`/`filter`/`reduce`/`foreach`) do work proportional to the size of the underlying object, yet are billed as a small, roughly constant number of ops — the code itself flags this as an unresolved risk. This mirrors the reported wasmvm issue where some operations cost far more real CPU time than their assigned gas/op price, allowing a malicious actor to make execution ~10x more expensive than budgeted and temporarily DoS block processing.

### Finding Description
The AA formula interpreter maintains two static-analysis counters, `complexity` and `count_ops`, computed by `formula/validation.js` and checked against `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` before a formula is allowed to execute [2](#0-1) . These counters are supposed to act as a proxy for real execution cost, analogous to a gas metering scheme.

The evaluator itself contains an explicit acknowledgment that this metering is inaccurate for cloning-heavy operations: [3](#0-2) 
This TODO states that cloning large objects is expensive and this expense is "multiplied by MAX_OPS and amplifiable via getters (which can also amplify other expensive ops)" — i.e., the actual CPU cost of a formula can scale far beyond what the `count_ops`/`complexity` budget represents, exactly as in the referenced wasmvm advisory ("some operations take significantly more [gas] than benchmarks indicated").

Concretely, operations such as `array`, `dictionary`, `keys`/`reverse`, `map`/`filter`/`reduce`, and `json_stringify` call `string_utils.cloneDeep` on their operands each time they execute, but are priced with only a fixed or linear-in-count `count_ops`/`complexity` charge: [4](#0-3) [5](#0-4) 
For `map`/`filter`/`reduce`/`foreach`, validation charges `complexity` and `count_ops` proportional only to `count * funcProps.complexity` / `count * funcProps.count_ops` (with `count` capped at 100 via `readCount`) [6](#0-5) , but each iteration internally clones/copies elements (`string_utils.cloneDeep`) regardless of the size of the nested value being iterated, so the real per-iteration cost is not the fixed unit assumed by the pricing model.

Remote getter calls compound this: `remote_func_call`/`func_call` cross-AA calls only add `getter.complexity + 1` / `getter.count_ops` to the caller's budget [7](#0-6) , and a chain of such calls (each doing its own cloning of state vars/response vars) can be nested up to the complexity ceiling, amplifying the underinstrumented cloning cost across multiple AA executions triggered by one posted unit.

### Impact Explanation
Because the `count_ops`/`MAX_OPS` budget is meant to bound the real-world CPU time every validating/witnessing node spends executing an AA trigger, an attacker who crafts a formula that maximizes cloning/serialization work relative to its charged ops (e.g., nested `map`/`filter`/`array`/`dictionary`/`json_stringify` calls on the largest permitted objects, chained through remote getter calls) can make a single trigger unit cost substantially more CPU time than the protocol's cost model assumes. Since AA evaluation is mandatory, deterministic, consensus-critical work performed by every full node processing the unit, this allows an attacker to temporarily degrade node throughput / slow confirmation for a given fee cost — the same "network unable to confirm new units at expected rate" class of impact called out in the validation rules, at a cost disproportionately lower than intended by the gas/op design.

### Likelihood Explanation
Any address can post an AA trigger unit; AA definitions and formulas are attacker-controlled data reachable by an unprivileged trigger sender. The pricing gap is not a theoretical edge case — it is explicitly flagged as a known-unaddressed concern in the code comment at `formula/evaluation.js:27`, indicating the developers themselves recognize cloning cost is not accurately reflected in the op/complexity accounting and can be amplified via getters. Exploitability requires only constructing formulas within existing size limits (`MAX_AA_STRING_LENGTH`, 100-item array/dictionary caps, `MAX_COMPLEXITY`/`MAX_OPS`), which are already achievable by a normal user without special privileges.

### Recommendation
- Price cloning/serialization operations (`cloneDeep`, `getJsonSourceString`, array/dictionary construction, `map`/`filter`/`reduce`/`foreach` element copies) proportionally to the actual size of the object being cloned/serialized rather than a fixed per-node charge.
- Track a running "real cost" budget (e.g., total bytes cloned/serialized) during evaluation, not just at static-validation time, and enforce it as evaluation proceeds so that dynamically-sized objects (state vars, wrapped objects) can't cheat the static estimate.
- Extend the remote-getter cost model so that cloning-heavy costs incurred in a nested/remote call are fully reflected in the caller's op budget, not just `complexity + 1`.
- Add fuzz/benchmark testing (similar to the wasmvm advisory's benchmarking effort) comparing declared `count_ops`/`complexity` against wall-clock execution time for cloning-heavy formulas, and recalibrate constants (`MAX_OPS`, `MAX_COMPLEXITY`, per-op costs) accordingly.

### Proof of Concept
Conceptual (bounded by existing size limits, no special privileges required):
1. Post a unit triggering an AA whose formula builds nested arrays/dictionaries near the 100-element/4096-byte limits and repeatedly applies `map`/`filter`/`json_stringify`/`keys`/`reverse` to them, each of which internally calls `string_utils.cloneDeep` [4](#0-3) [5](#0-4) .
2. Chain several `remote_func_call`/getter invocations to other AAs performing the same cloning-heavy pattern, since remote calls only add `getter.complexity + 1` to the budget [7](#0-6)  while each remote evaluation independently performs its own full cloning work.
3. Because `count_ops`/`complexity` for these operations don't scale with the real cost of the cloning work performed, the crafted formula passes the `MAX_OPS`/`MAX_COMPLEXITY` check at validation time [1](#0-0)  while consuming disproportionately more wall-clock time on every node evaluating the unit than a "normal" formula with the same declared op count, in line with the underlying gas-mispricing bug class.

Note: I could not execute or benchmark this in the sandbox (no filesystem/terminal access), so the actual real-world slowdown factor is not empirically verified here — this assessment is based on the code's own acknowledgment of the issue and static analysis of the metering logic.
