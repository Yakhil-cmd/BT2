### Title
`flash_loan` pulls repayment via `transfer_from` from an attacker-chosen `receiver` address, draining standing allowances held by third-party flash receivers - (File: contracts/pool/src/ops/flash.rs)

### Summary
`flash::collect_repayment` calls `asset.transfer_from(pool, receiver, pool, &terms.total_repayment)` where `receiver` is a fully caller-controlled argument of the permissionless `flash_loan` entrypoint. Because the spender is the pool contract itself (invoker-contract auth is implicit), the `from` leg needs only a live `receiver → pool` allowance — the victim never signs anything. Any contract that exposes `execute_flash_loan` and has granted the pool a standing token allowance can be forced to pay the flash fee repeatedly, losing `fee` per call until its allowance or balance is exhausted.

### Finding Description
In `apply`, the pool first transfers `amount` of the asset to `receiver` (`asset.transfer(&pool, &receiver, &amount)`), invokes `receiver.execute_flash_loan(...)`, then calls `collect_repayment` (contracts/pool/src/ops/flash.rs:60-67). `collect_repayment` checks `asset.allowance(receiver, pool) >= terms.total_repayment` and then executes `transfer_from(pool, receiver, pool, total_repayment)` (contracts/pool/src/ops/flash.rs:173-179).

`receiver` comes straight from the entrypoint arguments; the only constraints are `require_wasm_receiver` and that the `execute_flash_loan` invocation succeeds (contracts/pool/src/ops/flash.rs:49,140-163). Nothing ties `receiver` to `initiator` or requires `receiver.require_auth()`. This is the exact shape of the reported bug class: an arbitrary `from` passed to `transferFrom` where the pool's own authorization satisfies the spender check.

The net effect per call on the victim `receiver`: +`amount` (payout), −`amount + fee` (pulled) = −`fee`. The attacker needs a deployed contract that (a) implements `execute_flash_loan` successfully and (b) holds `allowance(victim, pool) > 0`. Legitimate flash receivers commonly `approve` the pool for repayment inside their callback; any receiver that approves with headroom, approves before the call, or has a failed/aborted earlier loan leaving residual allowance is exposed. Note the allowance check reads the *live* allowance, so the attack is bounded by whatever allowance exists.

### Impact Explanation
Theft of user funds: every invocation transfers `fee` worth of the market asset from the victim contract to the pool's accounting cash/revenue without the victim's authorization. Repeatable until the victim's allowance to the pool (or balance) is exhausted. The attacker can maximize `fee` by choosing the largest `amount` the pool's cash reserves allow, since `fee = bps(amount)` (contracts/pool/src/ops/flash.rs:107-121).

### Likelihood Explanation
Requires a third-party `execute_flash_loan` receiver contract with a stale or oversized allowance to the pool. Correctly written receivers approve exactly `amount + fee` inside the callback and the pool consumes it all in the same transaction, leaving zero residual allowance — so in the common case there is nothing to steal. However, receivers that pre-approve, over-approve, or survive a reverted-but-committed allowance state exist in practice, and the code gives the pool no defense: it consumes any allowance any contract ever grants it. Medium likelihood of finding an exposed allowance, with per-call profit capped by the flash fee.

### Recommendation
Do not repay via `transfer_from` from `receiver`. Inside `invoke_receiver`, require the callback to *push* repayment with `asset.transfer(receiver, pool, total_repayment)` — `transfer` requires `receiver.require_auth()`, so only the receiver's own code (executing under its own contract auth) can settle. Then in `collect_repayment`, replace the `transfer_from` + allowance pattern with a post-callback balance assertion (`balance == balance_after_repayment`, already present via `require_balance`) and delete the allowance check entirely. Alternatively, keep `transfer_from` but require `receiver == initiator`-bound authorization by having `initiator.require_auth_for_args` cover the receiver argument — the push-based fix is simpler and removes the arbitrary-`from` surface completely.

### Proof of Concept
1. Deploy a flash receiver contract `V` that implements `execute_flash_loan` benignly (e.g., records the call and returns). Fund `V` with the market asset and have `V` call `approve(V → pool, X)` once (e.g., an integration that pre-approved, or leftover allowance from an earlier loan).
2. Attacker calls `controller.flash_loan(initiator: attacker, receiver: V, amount: A, ...)` on a flashloanable market with cash ≥ `A`.
3. Pool transfers `A` to `V`; `V.execute_flash_loan` succeeds trivially; `collect_repayment` sees `allowance(V, pool) ≥ A + fee` and `transfer_from`s `A + fee` from `V` to the pool. `V` never authorized this call — the spender is the pool itself.
4. Net result: `V` loses `fee`; pool books `fee` as revenue. Repeat while `allowance(V, pool) ≥ A' + fee'` for decreasing `A'`.
