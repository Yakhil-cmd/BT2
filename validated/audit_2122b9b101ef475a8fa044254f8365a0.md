### Title
Webhook signature verification is scoped to `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field — allowing cross-organization webhook forgery when any configured organization has no `webhook_secret` set - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, computed from `payload.dig('repository','owner','login')` (falling back to `payload.dig('organization','login')`). The event handlers that actually mutate state, however, resolve the target `Stack`/`Repository` using a *different* field of the same payload — `payload.dig('repository','full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. These two fields are never cross-checked against each other. Since `GithubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for the resolved organization, an attacker can pick `repository.owner.login` to be any organization onboarded to the Shipit instance that has no webhook secret configured (documented in `docs/setup.md` as "optional"), while setting `repository.full_name` to point at a Stack that belongs to an entirely different, secret-protected organization. No signature check ever runs, yet the forged event is processed against the victim organization's stack.

### Finding Description
The binding that should hold is: **organization authenticated by `verify_signature` == organization owning the repository actually written to by the handler**.

- `WebhooksController#verify_signature` resolves the authenticating organization purely from `repository_owner`: [1](#0-0) [2](#0-1) 

- `GithubApp#verify_webhook_signature` is a no-op ("always verified") whenever the resolved organization has no `webhook_secret` configured: [3](#0-2) 

- Once past this filter, `Handler#stacks`/`Handler#repository_name` (used by every concrete handler, e.g. `PushHandler`) locates the target `Stack` using an *independent* field of the same JSON body — `repository.full_name` — with no re-validation that its owner segment matches `repository_owner` used above: [4](#0-3) [5](#0-4) 

Because the JSON `repository` object simply contains independent `owner.login` and `full_name` string fields (there's no requirement that `full_name` starts with `owner.login`), an attacker who knows (or picks) an organization with no `webhook_secret` configured can submit:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-with-no-secret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`repository_owner` resolves to `"org-with-no-secret"`, `Shipit.github(organization: "org-with-no-secret")` returns a `GithubApp` whose `webhook_secret` is blank, `verify_webhook_signature` short-circuits to `true`, and the request proceeds to `create`, which dispatches to `PushHandler` using `repository.full_name == "victim-org/victim-repo"` to locate and mutate the real, secret-protected stack.

This is the structural analog of the reported `recipientsCounter`/`recipientToStatusIndexes` bug: one value (`recipientsCounter` / `repository_owner`) is used to derive an authorization/index decision, while a second, related-but-distinct value (`recipientToStatusIndexes[recipientId]` / `repository.full_name`) is what actually gets acted upon, and the two are never reconciled.

### Impact Explanation
This lets an unauthenticated network attacker inject forged GitHub events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) for **any** tracked Stack in the Shipit instance, as long as at least one onboarded GitHub organization has an unset `webhook_secret` — a configuration explicitly documented as optional. Depending on which handler is targeted this enables:
- Forged `push` events causing `GithubSyncJob` to sync a victim stack against an attacker-chosen `expected_head_sha`.
- Forged `status`/`check_suite` events writing fake commit statuses/check runs against a victim repository's commits, which `DeploySpec#required_statuses`/`ci.require` gating relies on to permit deploys — enabling an unauthorized deploy to proceed by faking green CI on a victim stack.
- Forged `pull_request`/`membership` events mutating review-stack provisioning state or team membership for organizations the attacker never authenticated against.

This satisfies the High/Critical bar: unauthenticated write of stack/commit state and a path to an unauthorized deploy via forged CI status, achieved with zero credentials (no session, no ApiClient token, no webhook secret, no GitHub App key).

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment, and plausible even in single-org deployments where the admin left `webhook_secret` unset (explicitly presented as optional in `docs/setup.md`). The attacker needs no secret, no account, and no prior access — only the public `/webhooks` endpoint and knowledge of a victim `full_name` (visible from the Shipit UI/API for any stack).

### Recommendation
- Reject webhooks whose `repository.full_name` organization segment does not match `repository_owner`/`organization.login` used for signature verification, regardless of whether a secret was configured.
- Require `webhook_secret` to be present for every configured organization (fail closed rather than "return true unless webhook_secret" in `GithubApp#verify_webhook_signature`), or at minimum refuse to process any repository whose owner differs from the authenticated organization.
- Add regression tests asserting that a payload with `repository.owner.login` != the owner segment of `repository.full_name` is rejected even when the resolved organization has no secret configured.

### Proof of Concept
1. Ensure the Shipit instance has organization `org-with-no-secret` configured (any org with `Shipit.github(organization:)` resolvable) but with a blank `webhook_secret`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "org-with-no-secret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No `X-Hub-Signature` header is required.
3. Observe `verify_signature` passes (`repository_owner` → `"org-with-no-secret"` → blank secret → `verify_webhook_signature` returns `true`), and `PushHandler` enqueues `GithubSyncJob` against the real `victim-org/victim-repo` stack, per [4](#0-3)  and [6](#0-5) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
