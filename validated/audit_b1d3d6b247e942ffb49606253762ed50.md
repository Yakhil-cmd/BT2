### Title
Cross-organization webhook spoofing: signature bound to `repository.owner.login` but repo/stack resolution bound to a different field, `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's webhook secret to validate an inbound webhook against based on `repository.owner.login` (falling back to `organization.login`), while the actual event handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve the target `Stack`/`Commit` using the independent `repository.full_name` field of the same JSON body. In Shipit's supported multi-organization configuration, these two fields are not required to agree, so a signature valid for organization A's webhook secret can be used to authorize a payload that acts on organization B's repository. [1](#0-0) [2](#0-1) 

### Finding Description
Shipit supports hosting several GitHub organizations from a single instance, each with its own GitHub App config (including its own `webhook_secret`), selected by an `organization` key: [3](#0-2) 

When a webhook arrives, `verify_signature` determines *which* organization's app/secret to use for HMAC validation purely from the payload itself:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

If the signature is valid for that organization's secret, `create` dispatches the raw payload to all registered handlers for the event unconditionally:

```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

However, every handler resolves the *target* repository/stack from a **different** JSON field, `repository.full_name`, not `repository.owner.login`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`repository.owner.login` and `repository.full_name` are independent strings inside the same signed body; nothing enforces `full_name` to start with `owner.login`. Consequently, the equality the security model actually needs — "the organization whose secret validated this request" == "the organization that owns the repository being acted upon" — is never checked. An attacker who is an authorized sender for **any one** organization configured on the shared Shipit instance (i.e., they legitimately know that organization's own `webhook_secret`, e.g. because they administer their own GitHub App installation pointed at the same Shipit deployment) can sign a payload where `repository.owner.login` is their own organization (so the correct secret is picked and verification passes) while `repository.full_name` names a completely unrelated organization/repository's stack. Handlers such as `PushHandler` and `StatusHandler` will then act on that unrelated stack: [6](#0-5) [7](#0-6) 

This is the direct analog of the report's root cause: a value used to satisfy a security check (TWAP price freshness / here, org identity backing the HMAC) is silently treated as authoritative for a different, unguarded consequence (price used in a swap / here, the repository written to), even though the two should be bound together and are not.

### Impact Explanation
Using this gap, the attacker can:
- Forge a `push` webhook naming a victim org/repo's stack with an attacker-chosen `after` SHA, forcing `Stack#sync_github` to run for that stack via `GithubSyncJob`.
- Forge a `status` webhook that injects a fabricated commit status (e.g., `state: success`) for a `sha` on a victim stack via `Commit#create_status_from_github!`. If that stack has `continuous_deployment` enabled and CI-status gating configured, this can influence whether a commit is considered deployable, contributing to an unauthorized deploy path.
- Forge `check_suite` events to trigger `RefreshCheckRunsJob` against a victim stack.

None of this requires possession of the victim organization's webhook secret, a Shipit session, an `ApiClient` token, or repository write access on GitHub for the victim repo — only knowledge of a webhook secret belonging to *any* organization hosted on the same multi-tenant Shipit instance, which is a much weaker/unprivileged position relative to the victim.

### Likelihood Explanation
This requires a specific, but supported and documented, deployment pattern: a single Shipit instance configured with more than one GitHub organization (`Shipit.github_app_config`/`TOP_LEVEL_GH_KEYS` multi-org schema). In that configuration, the flaw is deterministic and requires no race condition or timing — any org's secret is sufficient to sign a payload targeting any other hosted org's repository, since `repository_owner` and `repository_name` are read from independent, unconstrained fields.

### Recommendation
- In `Handler#repository_name` / `Handler#stacks`, cross-check that the organization used to resolve/authorize the webhook secret (`repository.owner.login`/`organization.login`) matches the organization prefix of `repository.full_name` before acting, rejecting the event if they diverge.
- Alternatively, pin the GitHub App per-repository/stack (looked up first from `full_name`) and verify the signature using *that* repository's owning organization's secret, rather than deriving the secret-selection organization from a separate, unverified field.

### Proof of Concept
Preconditions: Shipit instance configured with two organizations, `attacker-org` (which the PoC author administers/controls the GitHub App webhook secret for) and `victim-org` (hosting a Shipit stack for `victim-org/victim-repo`), both connected to the same Shipit deployment as per the multi-org schema in `lib/shipit.rb`.

1. Build a push payload naming `attacker-org` as the signing owner but `victim-org/victim-repo` as the acted-upon repository:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org-webhook-secret, body)>` using the webhook secret the attacker legitimately knows for `attacker-org`.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `attacker-org`'s secret [8](#0-7) .
5. `PushHandler` resolves stacks via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack [9](#0-8) , despite the attacker never having proven any relationship to `victim-org`.

Note: I was unable to fully trace `Stack#sync_github`/`GithubSyncJob` and the continuous-deployment gating logic to the end (index/content limits truncated deeper inspection of `app/models/shipit/stack.rb` and `app/jobs/shipit/github_sync_job.rb`), so the exact downstream blast radius (e.g., whether this alone can trigger an unauthorized deploy versus only a stale/incorrect sync or a spoofed CI status) could not be fully confirmed from the indexed code. If precise confirmation of `sync_github`/continuous-delivery gating behavior is needed, a full Devin session with complete file access would be required.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
