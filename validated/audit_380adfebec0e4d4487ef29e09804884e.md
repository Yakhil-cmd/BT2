### Title
Webhook signature verification is scoped to `repository.owner.login`, but event handlers act on the independent `repository.full_name` field — allowing cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using `repository_owner`, a value read straight out of the untrusted JSON body. Every downstream event handler, however, resolves the actual repository/stack to act on using a *different* field of the same body, `repository.full_name`. Because these two payload fields are never cross-checked against each other, verifying "this request is legitimately signed for organization X" does not guarantee that the repository the handlers subsequently mutate actually belongs to organization X.

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is derived purely from attacker-suppliable JSON: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` config (and thus the `webhook_secret` used for HMAC verification) keyed by that same attacker-controlled string. Per the documented multi-org setup, each organization has its **own, independently optional** `webhook_secret`: [3](#0-2) [4](#0-3) 

and verification is a no-op whenever no secret is configured for the resolved organization: [5](#0-4) 

Meanwhile, every webhook handler (push, pull_request, membership, etc.) resolves the repository/stack to operate on from a **completely separate** field, `repository.full_name`, with no linkage back to `repository_owner`/the organization that was authenticated: [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold is:
`organization authenticated by verify_signature (repository_owner) == organization that owns the repository the handler writes to (repository.full_name)`

This equality is never enforced. An attacker crafts one payload where `repository.owner.login` names an organization configured on this Shipit instance with no `webhook_secret` (or one the attacker otherwise controls/knows), while `repository.full_name` names a *different* organization's/repo's stack that is registered on the same Shipit instance (e.g. `"OtherOrg/victim-repo"`). `verify_signature` resolves the GitHub App for the harmless/unsecured org, short-circuits (`return true unless webhook_secret`), and the request proceeds. The handler then acts on `OtherOrg/victim-repo` using data entirely fabricated by the attacker — e.g. triggering `GithubSyncJob` for arbitrary SHAs via `PushHandler`, forging `pull_request` events that archive/unarchive review stacks, or forging `membership`/`status` events for a stack it never authenticated against.

### Impact Explanation
This breaks the deployment-trust binding between "which GitHub organization's credentials were validated" and "which repository's Shipit state is mutated," enabling **cross-repository/organization writes** without any real GitHub-signed webhook for the targeted repository. This falls under the Critical impact category ("cross-repository writes, or an unauthorized deploy, rollback or merge") because forged `push` events can drive `Stack#sync_github`/deploy pipelines, and forged `pull_request`/`membership` events can alter review-stack lifecycle and team membership for a repository the attacker was never authorized against.

### Likelihood Explanation
Exploitability depends on operational configuration: it requires (a) a multi-organization Shipit deployment (explicitly documented as supported) and (b) at least one configured organization with `webhook_secret` left blank, or an organization value that is unconfigured/mismatched in a way that isn't rejected before the handler dispatch. Given `webhook_secret` is explicitly documented as "(optional)" in the setup guide, this is a realistic, low-effort misconfiguration rather than a purely theoretical one, and does not require possessing any secret — only knowledge that a given org is unprotected or exploiting the fact the two fields are independently attacker-controlled in a forged, un-replayed request.

### Recommendation
In `WebhooksController#verify_signature` (and in `Shipit::Webhooks::Handlers::Handler#repository_name`), enforce that the organization used to resolve the signing `GitHubApp`/secret is the same organization that owns `repository.full_name`, e.g. derive `repository_owner` from `repository.full_name.split('/').first` rather than a separately supplied `repository.owner.login`/`organization.login` field, and reject the request if the two are inconsistent. Additionally, consider making `webhook_secret` mandatory (or at minimum warn/refuse dispatch) for any organization configured in a multi-org Shipit deployment.

### Proof of Concept
Cannot be fully demonstrated without a live multi-organization Shipit deployment and its `config/secrets.yml`; the following illustrates the forged-request shape based on the code paths cited above:

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<valid-or-absent-signature-for-"UnprotectedOrg">

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "UnprotectedOrg" },   // used only for verify_signature
    "full_name": "VictimOrg/victim-repo"       // used by PushHandler/Handler#repository_name
  }
}
```

`verify_signature` resolves `Shipit.github(organization: "UnprotectedOrg")`; if that org has no `webhook_secret` configured, `verify_webhook_signature` returns `true` unconditionally [9](#0-8) , after which `PushHandler#process` operates on stacks belonging to `VictimOrg/victim-repo` [10](#0-9) , `Repository.from_github_repo_name(repository_name)` — a name never checked against the authenticated org.

**Uncertainty note:** I was not able to inspect `Shipit.github`/`Shipit.github_teams` implementation in `lib/shipit.rb` in full (index truncation stopped before reaching the `github(organization:)` method body), so I could not confirm whether it performs additional normalization/whitelisting of unknown organizations beyond raising `GithubOrganizationUnknown` for names absent from `config/secrets.yml`. If it strictly rejects any organization not explicitly configured, the exploit is limited to Shipit instances that have deliberately configured at least one organization without a `webhook_secret`, which somewhat narrows likelihood versus what's stated above. A Devin session with full repository access would be needed to confirm this exact behavior in `lib/shipit.rb`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
