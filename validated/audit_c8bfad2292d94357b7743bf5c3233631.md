### Title
Webhook signature is verified against `repository.owner.login`, but the event is processed against `repository.full_name` — organization-authenticated vs. repository-written binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` is used to validate the HMAC signature based on `repository.owner.login` (or `organization.login`) taken straight from the untrusted JSON body. Once the HMAC checks out, the raw `params` (including a completely separate `repository.full_name` field) are handed to the event handlers unmodified. The handlers, however, resolve the `Repository`/`Stack` to act on using `repository.full_name`, not `repository.owner.login`. Nothing cross-validates that these two fields refer to the same repository, so a payload that is validly signed for one organization can carry a `full_name` that points at a stack owned by a completely different organization.

### Finding Description
- Signature verification binds trust to the organization derived from the payload itself: [1](#0-0) [2](#0-1) 

- The signature/HMAC check itself just compares the header against `HMAC(webhook_secret_of_that_org, raw_body)`: [3](#0-2) 

- After verification, the full raw params (untouched) are dispatched to handlers: [4](#0-3) 

- Every handler resolves which `Stack`/`Repository` to mutate using `repository.full_name`, a sibling field of `repository.owner.login` that is never compared against it: [5](#0-4) 

This is structurally identical to the Rubicon rounding bug: two independent computations over the same payload (fee-controller's `mulDivUp` vs. `ProtocolFees`' `mulDivDown`) are expected to agree but aren't cryptographically or logically tied together — here, "which secret verifies the request" (`owner.login`) and "which repository the request writes to" (`full_name`) are two independent reads of the same JSON body with no equality enforced between them.

Binding that should hold: `organization_that_authenticated(payload) == organization_that_owns(repository_acted_upon(payload))`. Because `owner.login` and `full_name`'s owner segment are read independently and never compared, this equality can be false while the signature still verifies successfully.

Concrete example of the break, given a multi-tenant Shipit deployment (as documented, with per-organization `webhook_secret` entries, e.g. `somegithuborg` / `someothergithuborg` in `config/secrets.development.shopify.yml`):
- Before: attacker (an administrator/owner of their own onboarded GitHub organization "attacker-org", who legitimately knows their own org's `webhook_secret`) can only affect `attacker-org`'s own stacks.
- After: attacker crafts a raw POST to `/webhooks` with body `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, ...}` and `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)`. `verify_signature` computes `repository_owner == "attacker-org"`, loads `attacker-org`'s `webhook_secret`, and the HMAC matches — verification passes. The event is then dispatched with the full payload, and handlers resolve the target repository via `full_name`, i.e., `victim-org/victim-repo`, executing the event against the victim's stack.

### Impact Explanation
This breaks a cross-tenant repository boundary using only credentials the attacker legitimately possesses for their own organization, an unprivileged-attacker path relative to the victim organization:
- `StatusHandler#process` looks commits up by bare `sha` with no repository scoping at all, so a forged `status` event can attach an arbitrary CI status (`state: "success"`) to any commit sharing that sha across any stack in the installation, which can flip `Commit#deployable?` gating and enable an unauthorized deploy of a victim stack.
- `PushHandler#process` can trigger `stack.sync_github(expected_head_sha: ...)` against a victim's stack/branch.
- The `pull_request/*` handlers (`closed_handler.rb`, `labeled_handler.rb`, etc.) can close/label/merge review-stack-linked PRs belonging to the victim repository.

This satisfies the "cross-repository writes" / "unauthorized deploy" Critical/High impact bar defined in scope.

### Likelihood Explanation
Likelihood depends on the deployment being multi-tenant (multiple organizations configured under `Shipit.github` with distinct `webhook_secret`s, as shown in the shipped `secrets.development.shopify.yml` example and `docs/setup.md`). In such setups, any org onboarded to the shared Shipit instance can reach this bug purely by crafting an HTTP POST with a body they control and a signature computed from their own legitimately-held secret — no access to the victim's secret, session, or `ApiClient` token is required. For a single-tenant deployment (one org, one secret) this specific analog collapses (the "wrong org" case can't arise), which is the main uncertainty in assessing real-world exposure; I could not find any code in the engine that restricts or validates that `repository.owner.login` and `repository.full_name` agree, or that scopes a verified webhook to only the stacks belonging to the verified organization.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after selecting the organization used to validate the signature, assert that `repository.full_name`'s owner segment (or `organization.login`) equals the same `repository_owner`/`organization` value used to pick the verifying `webhook_secret`, and reject (422) the request if they differ. Additionally, `StatusHandler` should scope its `Commit` lookup by the repository resolved from the verified organization rather than a bare `sha`.

### Proof of Concept
1. Configure two organizations in `secrets.yml`, e.g. `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with a stack.
2. As an admin of `attacker-org`, compute `sig = "sha1=" + HMAC-SHA1(S_A, body)` for:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests"
}
```
3. POST to `/webhooks` with headers `X-Github-Event: status`, `X-Hub-Signature: sig`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), successfully verifies the HMAC using `S_A`, and lets the request through.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, attaching a forged `"success"` status to the victim's commit — independent of `attacker-org` even being the true owner of that commit/repository — which can satisfy `ci.require` checks and enable deploying the victim stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
