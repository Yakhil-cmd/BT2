### Title
`StatusHandler#process` looks up commits globally by `sha` instead of scoping to the reporting repository's stacks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which is completely unscoped by the webhook's `repository.full_name`. Unlike the PR handlers, it never calls `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`), so a validly-signed `status` webhook for repository A can write a `Status` onto a `Commit` that actually belongs to a stack for repository B, as long as the shas match.

### Finding Description
Binding claimed and confirmed broken: the correct scope should be `stacks.joins(:commits).where(commits: { sha: params.sha })` (equivalent to iterating `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`), scoped to `Repository.from_github_repo_name(params.repository.full_name)`. Instead, the actual code is: [1](#0-0) 

`Commit.where(sha: params.sha)` queries the entire `commits` table across every `Repository`/`Stack` in the Shipit instance, with no join or filter against the repository that sent the webhook. Contrast this with `Handler#stacks`, which exists precisely for this purpose and is used correctly by `PullRequest::OpenedHandler`, `ClosedHandler`, and `LabeledHandler` via `repository.review_stacks`: [2](#0-1) 

`Commit belongs_to :stack`, and each `Stack` belongs to exactly one `Repository`, so a `sha` collision across two different repositories' stacks is the only requirement for cross-tenant writes: [3](#0-2) 

**Attack path:** GitHub webhook signature verification (in `WebhooksController`) only proves the request was signed with *some* valid webhook secret — typically the secret configured for the attacker's own onboarded repository. It says nothing about whether the `sha`, `state`, `context`, `description`, or `target_url` fields inside the JSON body actually correspond to a commit in that repository. An attacker who owns a repository with a Shipit-tracked stack (and therefore knows/controls that repo's webhook secret) can hand-craft a `status` event payload with `repository.full_name` set to their own repo but `sha` set to a real commit sha belonging to a different, victim repository's stack (commit shas are public information visible on GitHub). They compute a valid HMAC signature themselves and `POST` directly to `/webhooks`. Because `StatusHandler#process` never checks that the resolved `Commit` actually belongs to a stack of the repository named in the payload, the forged status (`state: 'success'`, arbitrary `context`) is written via `commit.create_status_from_github!(params)` onto the **victim's** commit.

This can influence `Commit#deployable?`/`Commit#blocked?` and `schedule_continuous_delivery`, potentially causing an unrelated repository's continuous deployment pipeline to treat a commit as CI-passing based on forged status data supplied by an unrelated, unprivileged party.

Existing guards do not prevent this: webhook signature verification authenticates "a sender with a valid secret for some repo," not "the sender is authorized for the repo named in the payload"; `ExplicitParameters` only validates types/shapes of `sha`/`state`/etc., not repository ownership; and there is no `stacks`/`repository` scoping applied anywhere in `StatusHandler`.

### Impact Explanation
A payload nominally for repository A (attacker-owned) writes a `Status` record for a commit that actually belongs to repository B's stack (victim). This is a cross-tenant write matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any commit sha the attacker can discover (public commit shas are trivially enumerable from GitHub), and the blast radius spans every repository/stack pair sharing a sha value, including deliberately-colliding commits an attacker constructs by mirroring/cherry-picking identical tree+parent+metadata into their own repo to obtain a matching sha for a targeted victim commit.

### Likelihood Explanation
Preconditions: attacker must control a repository onboarded into the target Shipit instance (own repo + own webhook secret is a low bar — Shipit onboarding is typically self-service for any repo the user administers), and must know or be able to construct a sha shared with the victim commit (trivial for public repos, or via crafting an identical commit for a chosen parent/tree). No Shipit session, API token, or GitHub App secret is required. This is fully repeatable — a scripted attacker can loop over many known victim commit shas.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the reporting repository's stacks, mirroring the `Handler#stacks` pattern used by the PR handlers, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, out-of-scope path noted only to illustrate the expected assertions — actual test file to be added by engineering):
1. Create `stack_a` under `repository_a` and `stack_b` under `repository_b`, each with a `Commit` sharing the same `sha` value ("collided-sha").
2. Build a `status` payload with `repository.full_name = repository_a.full_name` and `sha = "collided-sha"`.
3. Assert the binding equality before/after: expected `StatusHandler.new(payload).send(:stacks)` (i.e. `stack_a` only) vs. actual `Commit.where(sha: "collided-sha")` returning both `stack_a`'s and `stack_b`'s commits.
4. Call `StatusHandler.call(payload)` and assert that `stack_b`'s commit (belonging to `repository_b`, unrelated to the payload's `repository_a`) received a new `Status` record — demonstrating the cross-tenant write.
5. Additionally, stub `Handler#stacks` to `raise` and show `process` still succeeds and still writes the `Status`, proving `stacks` is never consulted.
