### Title
Cross-Organization/Cross-Repository CI Status Injection via Unscoped `StatusHandler` Enables Unauthorized Deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` GitHub webhook handler writes commit CI status records by matching only on the commit `sha`, with no scoping to the repository or organization that the webhook signature was verified against. Any organization onboarded onto a shared Shipit instance can therefore inject a fabricated CI status onto a commit belonging to a completely different, unrelated repository/stack, potentially satisfying that stack's required-status checks and triggering an unauthorized continuous deployment.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the request against based on an attacker-controlled payload field, `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

This establishes a binding: "signature is valid for organization X" ⇒ "the payload may be trusted **for organization X's repositories**". Every other webhook handler in the codebase (`PushHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) respects this binding by resolving the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` before acting, via the shared `Handler#stacks` helper: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler`, however, breaks this binding. It looks up commits solely by `sha`, across the entire Shipit installation, with no repository/organization scoping whatsoever: [6](#0-5) 

Creating a status via `Commit#create_status_from_github!` is not a passive log entry — `Status` records trigger `after_commit` callbacks that can advance the commit's CI state and schedule continuous delivery: [7](#0-6) [8](#0-7) [9](#0-8) 

Because a `sha` is content-addressed and publicly visible (e.g., on GitHub commit/PR pages, or in another stack's Shipit UI), an attacker does not need to know it — they only need to observe it. The equality that should hold is:

`organization whose webhook_secret verified the request == organization owning the repository/commit that the status write affects`

In `StatusHandler`, the right-hand side is never checked, so the equality is broken: verification is scoped per-organization, but the write (`Commit.where(sha: params.sha)`) is global across all organizations/repositories/stacks hosted on the same Shipit instance.

### Impact Explanation
This is a cross-repository/cross-organization write: an organization that is legitimately onboarded to a shared Shipit instance (with its own valid `webhook_secret`, which is a normal, non-privileged onboarding artifact for that org, not a breach of another org's secret) can forge a signed `status` webhook that injects a fabricated `success` (or any) status onto a commit belonging to an entirely different organization's stack. If that status satisfies a required check context for continuous deployment, it can trigger `schedule_continuous_delivery` and an unauthorized deploy of a stack the attacker has no legitimate access to. This matches the "Critical — unauthorized deploy" impact category, and structurally mirrors the reported bug class: a coarse authorization check (webhook signature valid for *some* organization) is used to permit an action (status write) that is not actually bound to that organization's own resources — the same class of "authorization check granularity too coarse relative to the object being mutated" defect as the reported burn-instruction issue (VRT supply check instead of per-ticket ownership check).

### Likelihood Explanation
Any second organization onboarded to the same Shipit deployment (a supported, documented configuration — see the multi-org example in `docs/setup.md` / `config/secrets.*.yml`) can exploit this with only their own legitimate webhook credentials and public knowledge of a target commit's SHA. No compromise of the victim organization's secret, GitHub account, or Shipit session is required.

### Recommendation
Scope `StatusHandler#process` (and any future handler that mutates commit state) to the repository/organization that the signature was verified against — e.g., resolve commits only within `stacks` (as `PushHandler`/`CheckSuiteHandler` already do) using `payload.dig('repository', 'full_name')`, rather than a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Organization "attacker-org" is legitimately onboarded to the shared Shipit instance with its own `webhook_secret_A`.
2. Attacker observes the SHA of a commit belonging to "victim-org/victim-repo" (public GitHub info, e.g. from a PR URL or the Shipit UI).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a payload of `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim-sha>", "state": "success", "context": "<victim's required CI context>"}`, correctly HMAC-signed with `webhook_secret_A`.
4. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against the attacker's own secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (unscoped to attacker-org), and writes a fabricated success status. [6](#0-5) 
6. If this satisfies the victim stack's required checks, `schedule_continuous_delivery` fires and the victim commit may be auto-deployed.
