## Title
Alpenglow block-reward recalculation after snapshot restore uses live (post-epoch-boundary) stake amounts against a frozen reward-epoch denominator, letting a staker inflate their own block-reward share via `Merge` before a validator resumes from a mid-distribution snapshot — ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
This is a direct agave analog of the reported DeFi bug class: reward share must be computed from the balance/stake that existed when the reward pool was fixed, not from a balance that the user increased afterward. In agave's Alpenglow block-reward (SIMD-0123) path, the per-account numerator used during **reward recalculation after snapshot restore** is read from the live `StakesCache` instead of the frozen reward-epoch snapshot, while the denominator is correctly frozen. A staker who increases their already-fully-activated delegation (e.g. via `Merge`, which requires no warm-up) between the epoch-boundary calculation and a validator's snapshot-restore-triggered recalculation gets an inflated share of the vote account's fixed `pending_delegator_rewards` pool.

### Finding Description
`calculate_block_reward` computes a delegator's block reward as:
```
pending_delegator_rewards * stake / total_active_stake
``` [1](#0-0) 

- `total_active_stake` (the denominator) comes from `reward_epoch_delegated_stakes`, a value frozen exactly once at the epoch boundary via `RewardEpochDelegatedStakes::set` and persisted so it survives snapshot restore [2](#0-1) .
- `stake` (the numerator) is `delegation_effective_stake(delegation, rewarded_epoch, ...)`, where `delegation` is *not* taken from that same frozen snapshot — it is taken from whatever `Delegation` currently exists in the live `StakesCache` at the time `calculate_block_reward` runs [3](#0-2) .

This live-vs-frozen data feed happens in two places that both call `calculate_block_reward`:
1. The original epoch-boundary calculation.
2. `recalculate_stake_rewards`, invoked from `initialize_after_snapshot_restore` whenever a validator restarts from a snapshot taken while partitioned reward distribution is still active [4](#0-3) [5](#0-4) .

`recalculate_stake_rewards` sources delegations via `get_epoch_params_for_recalculation`, which explicitly uses the *current* `StakesCache`, not a frozen one:
```rust
let stake_delegations = stakes.stake_delegations_vec();
``` [6](#0-5) 

Because a fully-activated stake account's effective stake for *any* epoch (including a past `rewarded_epoch`) is derived from its **current** raw `delegation.stake` value scaled by the warm-up ratio — not from a historically pinned lamport amount — any operation that raises `delegation.stake` on an already-matured account (such as merging in another fully-active stake account, which the stake program permits without a new warm-up period) is retroactively reflected in `delegation_effective_stake(..., rewarded_epoch, ...)` [7](#0-6) .

The code even acknowledges the resulting mismatch, but only patches the single-account symptom, not the root cause:
```rust
// During recalculation, if stake account has already received rewards,
// it's possible to have `stake > total_active_stake`. ... This is
// harmless in practice, but we clamp it just to be safe
``` [8](#0-7) 

The existing regression test only covers the case where the increase comes from *already-distributed inflation rewards* (a self-consistent, bounded increase), not from a staker deliberately merging in extra stake between the epoch boundary and the restart point [9](#0-8) . That test asserts the *unpaid* reward for an unrelated account is unaffected by another account's paid reward — it does not exercise a staker deliberately increasing their own delegation via `Merge` before restart.

### Impact Explanation
`pending_delegator_rewards` on the vote account is a fixed pool intended to be split proportionally to `total_active_stake` (the frozen snapshot). If one delegator's numerator is inflated post-hoc while the denominator stays fixed, that delegator's clamped `min(pending_delegator_rewards)` share increases at the expense of correct proportional attribution to other delegators of the same vote account — this is a misattribution-of-rewards bug, and if multiple affected accounts each clamp near the full pool, the sum of block rewards paid out for that vote account can exceed the amount the epoch-boundary calculation accounted for, i.e., an unintended over-issuance relative to the reward budget recorded in the `EpochRewards` sysvar (`total_rewards`/`total_points`). This matches the "misattributed or duplicated rewards" / "minting of lamports" impact categories.

### Likelihood Explanation
This requires: Alpenglow block-reward (SIMD-0123) active, a validator restart from a snapshot taken while the partitioned distribution phase for an epoch is still in progress (a normal, tested, and explicitly supported operational path — `initialize_after_snapshot_restore` / `recalculate_partitioned_rewards_if_active`), and a staker performing a `Merge` of an already fully-activated stake account into their delegation in the window between the epoch-boundary calculation and the snapshot restore point. None of these preconditions require any special validator/operator role — `Merge` is an ordinary unprivileged stake-program instruction. The timing window (multi-block partitioned distribution, snapshot cadence) makes this reachable, though it depends on restart timing coinciding with an in-progress distribution.

### Recommendation
During recalculation, the per-account `stake` numerator used in `calculate_block_reward` should be sourced from the same frozen reward-epoch snapshot used for the denominator (e.g., persist per-delegation stake amounts, or the specific delegations included in `reward_epoch_delegated_stakes`, at the epoch boundary) rather than from the live `StakesCache` in `get_epoch_params_for_recalculation`. Alternatively, disallow/ignore delegation changes (via `Merge` or otherwise) that occur on accounts already included in a pending `PartitionedStakeReward`/`RewardEpochDelegatedStakes` set until that account's block reward has actually been recalculated and distributed from the same frozen basis as the original calculation.

### Proof of Concept
1. Enable Alpenglow (SIMD-0123 block-revenue-sharing) and reach an epoch boundary; the reward-epoch denominator (`RewardEpochDelegatedStakes`) is frozen for each vote account.
2. In a block after the epoch boundary but before all reward-distribution partitions have been applied, the attacker calls `Merge` to fold a second, fully-activated stake account into their delegated stake account, instantly increasing `delegation.stake` (no warm-up needed since both are fully active).
3. The validator restarts from a snapshot taken after step 2 but still within the active distribution window.
4. `initialize_after_snapshot_restore` → `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards` recomputes rewards using `get_epoch_params_for_recalculation`, which reads the attacker's now-inflated `delegation.stake` from the live `StakesCache`, while `total_active_stake` remains the pre-merge frozen value.
5. `calculate_block_reward` computes `pending_delegator_rewards * inflated_stake / frozen_total_active_stake`, giving the attacker a larger share of the vote account's block-reward pool than their frozen stake share entitles them to, at the expense of correct proportional distribution to the other delegators of that vote account.

#[inline]
pub(crate) fn delegation_effective_stake<T: StakeHistoryGetEntry>(
    delegation: &Delegation,
    epoch: Epoch,
    history: &T,
    new_rate_activation_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,

    if use_fixed_point_stake_math {
        delegation.stake_v2(epoch, history, new_rate_activation_epoch)
    } else {
        #[allow(deprecated)]
        delegation.stake(epoch, history, new_rate_activation_epoch)
    }
}
