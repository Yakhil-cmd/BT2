### Title
Webhook signature verification is keyed on the attacker-supplied `organization`/`repository.owner.login` field, not on the `repository.full_name` the handlers actually act on, and silently no-ops when that organization has no `webhook_secret` configured - allowing forged push/status events to be injected for stacks belonging to a *different*, secret-protected organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Position._borrowLimit` in the referenced report only used collateral tied to the specific `_bathToken` being borrowed against and ignored other collateral the account actually held, breaking the equality between "collateral counted" and "collateral the account holds." The analogous binding in Shipit is: **the GitHub organization whose secret is used to verify a webhook signature** must equal **the organization owning the repository whose stacks the payload is allowed to mutate**. `WebhooksController` breaks that binding by selecting the verification key from an unauthenticated field and by treating "no secret configured for that org" as automatic success, while the handlers act on a separate, unverified `repository.full_name` field.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which webhook secret) to verify the signature against using `repository_owner`, which is read straight out of the untrusted, not-yet-verified JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` then trivially returns `true` whenever that selected organization has no `webhook_secret` configured: [3](#0-2) 

This is a documented, supported configuration state — `webhook_secret` is explicitly optional per-organization in multi-org setups (`docs/setup.md`, `config/secrets.development.shopify.yml`), so an installation with several GitHub organizations configured (one strict, one without a secret) is a normal deployment, not a misconfiguration: [4](#0-3) 

Once `verify_signature` passes (because the attacker picked an org with no secret), `WebhooksController#create` dispatches the *entire, still-untrusted* payload to the event handlers: [5](#0-4) 

The handlers, however, do not re-check that the payload's organization matches anything — they resolve the target `Stack`/`Repository` from a completely independent field, `repository.full_name`: [6](#0-5) 

So the field that gated the signature check (`repository.owner.login` / `organization.login`) and the field that determines which repository's stacks get mutated (`repository.full_name`) are two different, independently attacker-controlled JSON fields in the same unsigned request. Nothing forces them to refer to the same repository/organization.

`PushHandler#process` then calls `stack.sync_github(expected_head_sha:)` for every matching, non-archived stack: [7](#0-6) 

and `StatusHandler#process` writes a `Status` for any commit matching the attacker-supplied `sha`, which is used by Shipit to gate whether merges/deploys are allowed to proceed: [8](#0-7) 

**Equality broken:** organization‑authenticated‑by‑signature (`repository_owner` used to pick the `webhook_secret`) ≠ repository‑whose‑stacks‑are‑written (`repository.full_name` used by `Handler#stacks`). The report's flaw ("collateral counted for token A ignores collateral actually held for token B") maps directly onto "signature verified for org A is treated as authorization to write org B's repository."

### Impact Explanation
An attacker who can reach the public `/webhooks` endpoint (no session, no API token, no GitHub write access required — this is exactly the unauthenticated entrypoint Shipit exposes for GitHub events) can craft a JSON body where `repository.owner.login`/`organization.login` names an organization configured in Shipit *without* a `webhook_secret` (a supported, documented state), while `repository.full_name` names a repository belonging to a completely different, secret-protected organization that Shipit tracks. Because the signature check short-circuits to `true` for the org lookup key alone, the forged payload is accepted, and the `push`/`status` handlers act on the unrelated target stack: enqueuing `GithubSyncJob` for arbitrary `expected_head_sha`, or writing forged commit `Status` records that other parts of Shipit consult when deciding whether a commit is safe to deploy/merge. This crosses a repository-write boundary without valid authentication for that repository — matching the "unauthorized deploy/rollback" and "cross-repository writes" impact bar.

### Likelihood Explanation
Requires only: (1) the target Shipit installation to be running the documented multi-org GitHub App configuration with at least one organization lacking a `webhook_secret` (explicitly presented as a normal, optional setup in `docs/setup.md`), and (2) knowledge/guessing of that organization's login name, which is generally discoverable (it is the organization that installed the app, visible via GitHub itself). No secrets, tokens, or GitHub write access are needed — only the ability to POST to the public webhook endpoint.

### Recommendation
Verify the signature using the secret associated with the organization that actually owns `repository.full_name` (or explicitly reject payloads where `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`), and stop treating a missing `webhook_secret` as an automatic pass — instead, require every configured organization to either have a secret or be explicitly whitelisted as intentionally open, and never let a payload's own fields select which trust boundary protects a different field in that same payload.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `trusted-org` (has `webhook_secret` set, has a Shipit `Stack` tracking `trusted-org/critical-repo`) and `open-org` (no `webhook_secret` configured, per the documented optional multi-org schema).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "trusted-org/critical-repo" },
  "organization": { "login": "open-org" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
No `X-Hub-Signature` needed (or any value) since `verify_webhook_signature` returns `true` for `open-org`.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'open-org')`, whose `webhook_secret` is blank, so verification passes unconditionally.
4. `PushHandler#stacks` resolves via `Repository.from_github_repo_name('trusted-org/critical-repo')`, finds the real, secret-protected stack, and enqueues `stack.sync_github(expected_head_sha: 'attacker-chosen sha')` — a write against `trusted-org`'s stack triggered by a payload that was never authenticated against `trusted-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
