### Title
Autonomous Agent dust-asset outputs bypass the dust-attack filter, allowing DOS of an AA's send-all/full-balance responses - (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s coin-selection logic for AA-generated payments explicitly filters out dust *base* (bytes) outputs to avoid a known dust-attack vector, but applies no equivalent filter to non-base asset outputs. Combined with the fact that AA-generated payment messages are exempt from the normal `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_UNIT_LENGTH` checks, an attacker can post many tiny-amount transfers of a custom asset to an AA address to force any subsequent "send-all"/full-balance response by that AA in that asset to consume every dust output as an input, inflating the response unit's size and byte fees to the point that the AA cannot pay them from its own balance. This is analogous to the `MarginTradingHook.refundNative` finding: unconditional cleanup/refund logic is triggered by unrelated dust deposits and can force reverts/failures of legitimate operations.

### Finding Description
When an AA sends a payment message, `sendUnit()`/`completePaymentPayload()` collects unspent outputs to use as inputs via `readStableOutputs()` and `readUnstableOutputsSentByAAs()`: [1](#0-0) 

The SQL explicitly adds a minimum-amount filter only for the base asset (`asset IS NULL AND amount>=FULL_TRANSFER_INPUT_SIZE`), with a comment stating this exists specifically "to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond." No such `amount>=` condition exists for non-base assets (`asset=<escaped_asset>` branch has no lower bound).

`iterateUnspentOutputs()` walks these rows and, for a "send-all" output (no `amount` specified, e.g. `{address: "{trigger.address}"}` — a pattern used throughout the AA templates in this repo, e.g. `test/samples/send_all.oscript`, `bounce_half_of_balance.oscript`, `just_a_bouncer.oscript`, and the `MM/uniswap`-style samples that divest "balance[$asset]"), continues (rather than stopping) through *all* rows so it can add up the entire balance: [2](#0-1) 

Because non-base asset dust is never filtered out, an attacker can post an arbitrary number of 1-unit (or otherwise economically negative) transfers of a custom asset to the AA's address. Any subsequent AA logic that responds with a send-all payment of that asset (a very common oscript idiom, e.g. `{address: "{trigger.address}"}` with no amount, as seen in `test/samples/send_all.oscript`) is forced to pull in every single dust UTXO as an input.

Unlike ordinary wallet-composed units, AA-generated units are explicitly exempted from the input-count and unit-size caps that would normally bound this kind of abuse: [3](#0-2) [4](#0-3) 

The resulting unit's actual byte size/fees are computed only after all inputs are gathered: [5](#0-4) 

If the accumulated headers/payload commission (paid out of the AA's own base/byte balance) exceeds what the AA can afford, the AA's payment attempt fails and the whole trigger is bounced: [6](#0-5) [7](#0-6) 

This mirrors the reported bug class exactly: unconditional balance-draining/refund-style logic (`refundNative`/here, mandatory consumption of every UTXO of an asset for a send-all response) is triggered regardless of whether it is relevant to the current call, and a third party can cheaply force it to fail by pre-seeding dust, causing legitimate, unrelated calls to be denied service (bounced) even though the caller did nothing wrong.

### Impact Explanation
Any AA whose oscript logic responds with a send-all (or otherwise balance-dependent) payment in a non-base asset can be permanently or intermittently DOSed by an attacker spending a negligible amount to create large numbers of dust outputs of that asset at the AA's address (this asset can even be one the attacker controls/issues, since AAs will accept and later have to sweep any asset sent to them). Once enough dust accumulates, honest users' legitimate triggers that require the AA to respond with the accumulated asset balance will bounce, causing:
- Loss of the user's bounce fee with no service rendered (funds are consumed but the expected response is never produced).
- Persistent inability of the AA to execute its documented behavior (freezing of AA functionality), since new dust can keep arriving.
This satisfies "AA fund loss or freezing" per the validation criteria.

### Likelihood Explanation
Likelihood is fairly high for any AA that uses a "send-all" or full-asset-balance payment pattern for a non-base asset (a documented, encouraged pattern in the codebase's own oscript samples, e.g. `test/samples/send_all.oscript`, market-maker/divest examples). The attack only requires posting ordinary payment units transferring tiny amounts of the target asset to the AA address — something any unprivileged unit poster can do — and no special asset attributes or privileges are required. The lack of a dust filter for non-base assets (present only for base bytes) appears to be an oversight rather than an intentional design choice, since the comment in the code shows the developers were aware of and specifically fixed this exact problem class for the base asset.

### Recommendation
Apply the same (or an asset-aware, denomination-adjusted) minimum-input-amount filter used for base outputs to non-base asset outputs in `readStableOutputs()`/`readUnstableOutputsSentByAAs()` in `aa_composer.js`, or otherwise cap/limit the number of dust inputs an AA-generated payment can silently absorb for a given asset, and reintroduce a byte-size/input-count ceiling for AA units (or fail gracefully with a bounce that doesn't consume state) before spending down the AA's fee balance on excessive inputs.

### Proof of Concept
1. Deploy/observe an AA whose response logic includes a send-all payment for a custom asset (pattern: `{address: "{trigger.address}"}` with no `amount`), matching the pattern in `test/samples/send_all.oscript`.
2. As an attacker, issue a large number of separate outputs of that asset to the AA's address, each far smaller than the effective per-input byte cost (analogous to the base-asset `FULL_TRANSFER_INPUT_SIZE` threshold that is enforced only for bytes, per the comment/code at `aa_composer.js:1144-1155`).
3. Trigger the AA normally (or wait for another user to trigger it) so that it must respond with the full asset balance.
4. Observe `sendUnit()`/`completePaymentPayload()` (`aa_composer.js:1102-1245`) pull in every dust UTXO as an input because the "send-all" continuation logic (line ~1119-1120) does not stop early and no amount filter excludes the dust for non-base assets, and because AA units bypass `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_UNIT_LENGTH` (`validation.js:2137-2140`, `267-268`).
5. If the resulting headers/payload commission exceeds the AA's spendable base balance, the payment fails and the AA bounces (`aa_composer.js:975-978`, `1346-1348`), denying legitimate service to the triggering user.
