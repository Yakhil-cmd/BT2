### Title
CCMenu API client is created without a stack scope, letting a leaked per-stack CI-status token read every stack's state, task streams and deploy output - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` and hands the caller a token embedded in a per-stack CCMenu URL. The intent, expressed by the endpoint's own parameterization (`stack_id: stack.to_param`), is that the resulting token authorizes read access to that one stack. But the `ApiClient` is created without a `stack` association, so the token is unscoped and, combined with `Api::CCMenuController` bypassing the normal client-scoped stack lookup, the same token can be replayed to read the state, task streams, and deploy output of *any* stack on the installation.

### Finding Description
`CCMenuUrlController#client` builds the client like this: [1](#0-0) 

Only `permissions: %w[read:stack]` is set — `stack:` is never assigned, even though the controller already has `stack` (`Stack.from_param!(params[:stack_id])`) available and the generated URL is stack-specific: [2](#0-1) 

`ApiClient#stack` is optional, and authorization scoping in `Api::BaseController` only restricts to a single stack when `stack_id` is present; otherwise it defaults to *all* stacks: [3](#0-2) 

Because the CCMenu client's `stack_id` is nil, `current_api_client.stack_id?` is false, so `stacks` resolves to `Stack.all` for this token everywhere `BaseController#stack`/`#stacks` is used — e.g. `Api::TasksController` (task list, task show, and `tail`, which streams task output) and `Api::StacksController#index`/`#show`, all of which only require the `read:stack` permission the CCMenu client already has: [4](#0-3) 

Authentication of this token is not restricted to the CCMenu XML endpoint: `Api::BaseController#authenticate_api_client` accepts the same token via HTTP Basic auth on every API controller that inherits from it, using `ApiClient.authenticate`: [5](#0-4) [6](#0-5) 

Separately, `Api::CCMenuController` (the XML consumer of this specific token) also does not use the client-scoped `stacks` helper at all — it resolves the stack directly and unconditionally from the URL parameter: [7](#0-6) 

So even a hypothetical stack-scoped CCMenu client would still let its token be reused for any `stack_id` on the CCMenu XML endpoint, because that controller never checks the token's own `stack_id` against the requested one.

Binding broken: **the stack a CCMenu token is meant to authorize (the single stack named in the URL the user requested) ≠ the stack(s) the token actually authorizes (all stacks, via `Stack.all` and the unscoped CCMenu lookup).**

### Impact Explanation
CCMenu tokens are designed to be embedded in third-party, often unauthenticated consumers (desktop widgets, browser extensions, build-status dashboards) — see `test/controllers/ccmenu_controller_test.rb`'s use of query-string tokens. That makes them inherently more likely to leak (browser history, referrer headers, shared dashboards, saved bookmarklets) than a full account token. If such a token leaks, the holder gains unauthenticated read access — via Basic Auth on the general API — to every stack's metadata, and via `Api::TasksController#tail`/`#show` to task and deploy output logs across the entire Shipit instance, not just the one stack the user intended to share. This matches the specified High-severity criterion of "unauthenticated read of stack state, task streams or deploy output" reached through a credential the deployment-trust model did not intend to authorize that broadly.

### Likelihood Explanation
No privileged action beyond obtaining a leaked/observed CCMenu token is required; the vulnerable code path (`ApiClient.create_with(permissions: %w[read:stack])` without `stack:`) executes on every legitimate use of the CCMenu-URL feature, so every token minted through this flow is over-scoped by construction. Exploitation only requires the attacker to obtain one such token (a realistic outcome given the feature's purpose is to be embedded in low-trust external tools).

### Recommendation
Scope the CCMenu client to the requested stack when it is created (`ApiClient.create_with(permissions: %w[read:stack], stack:)`), and enforce that scope on the consuming side: make `Api::CCMenuController#stack` use the client-scoped `stacks.from_param!` (as `BaseController` does) instead of `Stack.from_param!`, and additionally verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
1. As a legitimate stack maintainer, visit the CCMenu widget URL generator for `stack A`, e.g. `GET /stacks/:owner/:repo/:branch/ccmenu`. `CCMenuUrlController#fetch` creates an `ApiClient` with `permissions: ['read:stack']` and no `stack` set, and returns a URL containing `token=<t>`.
2. This URL/token is embedded in a third-party CI-status widget (its intended, documented use).
3. An attacker who observes `<t>` (e.g., via the widget, logs, or network capture) issues:
   `GET /api/stacks/otherOwner/otherRepo/otherBranch/ccmenu.xml?token=<t>` — succeeds and returns build/status data for stack B, which the token was never meant to expose.
4. The same attacker also authenticates with `<t>` as HTTP Basic credentials against `GET /api/stacks` and `GET /api/stacks/:stack_id/tasks/:id/tail` for any stack in the instance, retrieving task/deploy output logs the user never intended to share via the CCMenu link.
