### Title
StatusHandler#process performs a global, repository-unscoped `Commit` lookup, allowing cross-organization status forgery - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)`, a query with no repository or stack scoping, and writes a `Status` onto every matching row regardless of which organization the request was signed for. Because `WebhooksController#verify_signature` selects the signing secret to check based on `repository.owner.login`/`organization.login` taken directly from the attacker-controlled JSON body, an attacker who owns any onboarded GitHub org can sign a payload with their own org's secret while naming an arbitrary sha belonging to a different org's commit, and have a `success` status written to that victim commit.

### Finding Description
The broken binding is: the org whose `webhook_secret` verified the payload (`repository_owner` derived from `params.dig('repository','owner','login')` in `app/controllers/shipit/webhooks_controller.rb:59-62`) should equal the org that owns the `Commit` row being mutated (`commit.stack.repository`). These are never checked to be equal.

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) calls `Shipit.github(organization: repository_owner)` and verifies the signature using that org's `webhook_secret`. `repository_owner` is read straight from the request body's `repository.owner.login` (or `organization.login`), which is fully attacker-controlled content inside a payload the attacker is signing themselves. So an attacker who owns "OrgA" in Shipit's config can put `"repository": {"owner": {"login": "OrgA"}}` in the body and sign with OrgA's own known secret — verification succeeds legitimately for OrgA, as expected.
2. `WebhooksController#create` then dispatches to `Shipit::Webhooks::Handlers::StatusHandler.call(params)` (`app/models/shipit/webhooks.rb:19`, `app/controllers/shipit/webhooks_controller.rb:10-12`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
   ```ruby
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ```
   This is a bare, global lookup by `sha` with no join/filter on `Repository`/`Stack`, and no call to the `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) that other handlers such as `CheckSuiteHandler` use to scope work to the repository named in the payload.
4. If the attacker supplies the sha of a commit that happens to exist under "OrgB"'s stack (learnable via OrgB's public commit history/GitHub), `Commit.where(sha: ...)` returns OrgB's `Commit` row and `create_status_from_github!` creates a `Status` (`success`, arbitrary `context`) on it — attributed to whatever org signed the request (OrgA), not OrgB.

No existing guard catches this: `verify_signature` only proves the payload was signed by *some* configured org matching the attacker-controlled `repository_owner` field, not that the org owns the commit being mutated; `drop_unhandled_event` and `ExplicitParameters` schema (`requires :sha`, `:state`, etc.) only validate shape, not ownership; and unlike `CheckSuiteHandler`, `StatusHandler` never calls `stacks` to restrict `Commit` lookups to the requesting repository's stacks.

### Impact Explanation
A single crafted, self-signed webhook lets an attacker who controls any one onboarded GitHub organization write a forged CI `Status` (e.g., `state=success`, `context=ci/required-check`) onto an arbitrary commit belonging to a different organization's stack, as long as they know that commit's sha (typically public). This is a cross-tenant write: a payload authenticated for org A mutates a `Commit`/`Status` record belonging to org B's stack. If org B's deploy pipeline gates deploys via required-status checks matching that context, this can unblock an unauthorized deploy — matching the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" Critical impact categories. The attack is repeatable against any sha across any tenant stack in the same Shipit instance, and requires no privilege beyond owning/being able to send webhooks from one configured org.

### Likelihood Explanation
Preconditions: the attacker needs their own org (or any org whose `webhook_secret` they know) configured in the same Shipit instance as the victim org, and the victim commit's sha (obtainable from public GitHub history in most OSS/typical cases). No Shipit session, API token, or victim secret is required — the attacker only ever uses their own org's `webhook_secret`, since `verify_signature` picks the verification key from attacker-controlled JSON. This is a low-cost, fully repeatable attack: one crafted HTTP POST per forged status per target sha.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository the webhook actually claims to be for, similar to `CheckSuiteHandler`'s use of `Handler#stacks`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, and additionally ensure `verify_signature` cannot be tricked into using a different org's secret than the one that actually owns the resource being mutated (i.e., cross-check that the signing org's repositories/stacks are the only ones a given handler is allowed to touch).

### Proof of Concept
Minitest plan (controller/integration test, no live GitHub):
```ruby
test "status webhook signed for OrgA cannot forge a status on OrgB's commit" do
  org_a_secret = 'org-a-secret'
  org_b_stack  = shipit_stacks(:cyclimse) # belongs to "OrgB" in fixtures
  victim_commit = org_b_stack.commits.create!(sha: 'deadbeef' * 5, ...)

  # Configure Shipit.github(organization: 'OrgA') to use org_a_secret
  # (stub Shipit.github as needed, or use fixture github_hooks for OrgA)

  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/required-check',
    'repository' => { 'owner' => { 'login' => 'OrgA' }, 'full_name' => 'OrgA/some-repo' },
    'branches' => [{ 'name' => org_b_stack.branch }]
  }.to_json

  request.headers['X-Github-Event'] = 'status'
  request.headers['X-Hub-Signature'] = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', org_a_secret, body)}"

  assert_difference 'victim_commit.statuses.count', 1 do
    post :create, body:, as: :json
  end

  status = victim_commit.statuses.last
  assert_equal 'success', status.state
  assert_equal 'ci/required-check', status.context
  # Equality that should have held but didn't:
  # repository_owner-that-signed ("OrgA") == owner of victim_commit.stack.repository ("OrgB") -> false, yet write succeeded
end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
