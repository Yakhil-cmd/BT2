### Title
Webhook signature verification keyed on `repository.owner.login` allows cross-organization stack takeover via a valid webhook secret from an unrelated GitHub App - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify the HMAC signature against based solely on `repository.owner.login` (or `organization.login`) taken from the request body, while the actual event handlers act on the repository identified by the independent `repository.full_name` field of the very same body. Because Shipit supports multiple GitHub App configurations (one per organization, see `Shipit.github(organization:)` / `lib/shipit/github_app.rb`), an attacker who legitimately controls one onboarded organization's GitHub App webhook secret can craft a payload whose `repository.owner.login` matches their own organization (so the correct/known secret validates the HMAC) but whose `repository.full_name` names a stack belonging to a *different* onboarded organization. The signature check only binds trust to `repository.owner.login`; the write path binds to `repository.full_name`.

### Finding Description
`verify_signature` computes: [1](#0-0) [2](#0-1) 

It looks up `Shipit.github(organization: repository_owner)` and verifies `request.headers['X-Hub-Signature']` against `request.raw_post` using that organization's `webhook_secret` via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` dispatches the *entire raw body* to the registered handlers: [4](#0-3) 

Handlers, however, resolve the target repository/stack independently, using `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` derives the repository purely from the `owner/name` string embedded in `full_name`: [7](#0-6) 

Since the JSON body is otherwise unconstrained (nothing ties `repository.owner.login` to `repository.full_name`'s owner segment), an attacker who has HMAC-signing capability for **Organization A** (because they administer that org's GitHub App/webhook, a legitimate, unprivileged relationship to Shipit) can:
1. Set `repository.owner.login` = `"OrgA"` (or `organization.login` = `"OrgA"` if `repository` is omitted) so `verify_signature` selects OrgA's app/secret.
2. Set `repository.full_name` = `"OrgB/some-repo"` — a stack registered under a completely unrelated organization, OrgB, that the attacker has no access to.
3. Sign the raw body with OrgA's `webhook_secret`.

The signature validates (it is only checked against OrgA's secret and the raw bytes, with no requirement that the signed owner match the acted-upon repository), and the `push`/`status`/`check_suite`/`pull_request` handlers act on OrgB's stack (e.g. `PushHandler` calls `stack.sync_github(expected_head_sha:)`, effectively forcing a stack refresh/sync pointing at an attacker-chosen `after` SHA for a repository the attacker never has legitimate rights over).

This is the same class of bug as the reported "global vetoes circumvented by strategist controlled calldata" issue: the code validates one field (`globalHooksVetoed`/`repository.owner.login`) but permits an action scoped by a *different, unguarded* field (`strategyHooksVetoed`/`repository.full_name`) inside the same attacker-controlled payload — the verified binding (organization that authenticated) does not equal the binding actually acted upon (repository that is written).

### Impact Explanation
This breaks the equality `organization that authenticated == repository that is written`. It allows an attacker who is the legitimate administrator of one Shipit-onboarded GitHub organization/App to inject forged webhook events (push/status/check_suite/pull_request/membership) against stacks belonging to any *other* onboarded organization, without ever needing that other organization's webhook secret, an `ApiClient` token, or repository write access there. Depending on handler behavior this can force unauthorized `GithubSyncJob`/status/check-run refresh cycles, corrupt commit status/CI state used for deploy gating, or manipulate review-stack lifecycle (archive/unarchive) for a repository entirely outside the attacker's control — a cross-organization/cross-repository integrity violation reachable purely through the public `/webhooks` endpoint.

### Likelihood Explanation
Exploitability requires only that Shipit be configured to host multiple GitHub organizations/Apps (a documented, supported configuration — see `Shipit.github_organizations`/`github_app_config`), and that the attacker administers at least one of them (a normal, unprivileged relationship — they simply need to be allowed to install their own org's GitHub App on their own org, which is the intended per-tenant boundary). No Shipit credentials, session, or the victim organization's secret are needed. This makes the attack straightforward for anyone who is a legitimate tenant of the multi-org Shipit instance.

### Recommendation
Bind the verified signing identity to the exact resource acted upon. After signature verification, re-derive the organization solely from `repository.full_name`'s owner segment (or explicitly cross-check that `repository.owner.login`/`organization.login` used for secret selection equals the owner segment of `repository.full_name`) and reject the webhook if they differ. Alternatively, verify the signature using the app configuration resolved from the same field the handlers use to select the target repository/stack, so a single canonical field determines both signing-key selection and the acted-upon resource.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `OrgA` (secret `SECRET_A`, attacker-administered) and `OrgB` (secret `SECRET_B`, victim), each with stacks registered, e.g. `OrgA/repo-a` and `OrgB/repo-b`.
2. Attacker builds a push-event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attacker chosen sha",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/repo-b" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>` (they legitimately know `SECRET_A`).
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` → validates against `SECRET_A` → succeeds.
6. `Shipit::Webhooks::Handlers::PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/repo-b")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` for OrgB's stack, despite the attacker having no relationship to `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
