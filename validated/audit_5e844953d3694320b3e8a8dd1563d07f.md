## Title
Malicious actors can permanently freeze all contributed funds in the "51% attack game" AA by inflating `balance[base]` with team-creation fees that are never counted toward any team's contribution total - ([File: test/samples/51_attack_game.oscript])

## Summary
The shipped `51_attack_game.oscript` Autonomous Agent decides whether a team has "won" by comparing a per-team tracked counter (`var['team_'||trigger.data.team||'_amount']`) against `balance[base] * 0.51`, where `balance[base]` is the AA's *raw* total byte balance read via the `balance[]` oscript operator. This is the exact analog of the Fei `GenesisGroup` bug: a threshold check is performed against the contract/AA's actual balance instead of an internally tracked, protected total. Because every "create a new team" call permanently donates a `5000`-byte fee into the AA that is added to `balance[base]` but never added to any team's `_amount` counter, an unprivileged unit poster can cheaply and repeatedly inflate the denominator used in the 51% check, making it impossible for any team to ever reach the winning threshold and permanently freezing all funds already contributed to the AA.

## Finding Description
The AA tracks per-team contributions in dedicated state variables: [1](#0-0) 

The win condition compares this tracked value to the AA's live, unprotected balance:
```
var['team_' || trigger.data.team || '_amount'] > balance[base]*0.51
``` [2](#0-1) 

`balance[base]` is not a value the AA controls or accumulates itself - it is computed by reading the AA address's real on-chain balance, which is credited by `aa_composer.js` from every payment output routed to the AA (both trigger payments and fee residues), independent of whether that value is reflected in any of the AA's own tracked totals: [3](#0-2) [4](#0-3) 

Crucially, the "create a new team" case charges a `$team_creation_fee` of `5000` bytes that is *retained* by the AA (any excess above the fee is refunded, but the fee itself stays) and is never added to any `team_..._amount` counter: [5](#0-4) 

Anyone can call `create_team` from an arbitrary number of distinct addresses (the only restriction is "you already have a team" per calling address), so an attacker can create unlimited teams, each contributing `5000` bytes that permanently raises `balance[base]` without ever raising any team's contribution total used in the 51% numerator. This is structurally identical to the Fei report: a balance-based threshold check that can be inflated by a party who bypasses the "intended" accounting path (there, `selfdestruct`; here, repeatedly paying the team-creation fee), causing the launch/threshold condition to become permanently unreachable and locking funds already deposited (there, `FEI`/`TRIBE`; here, all bytes held by the game AA, since the "pay out the winnings" case is gated on `var['finished']`, which is only set once a team reaches the now-unreachable 51% threshold): [6](#0-5) 

## Impact Explanation
If the 51% threshold becomes practically unreachable, `var['winner']` and thus `var['finished']` are never set, so the "pay out the winnings" case (the only exit path for funds) never activates. All bytes contributed by legitimate users to any team become permanently stuck inside the AA, with no code path to withdraw them - directly matching the "lock all FEI and TRIBE" impact described in the source report.

## Likelihood Explanation
The attack requires only ordinary, unprivileged unit-posting capability (anyone able to send a trigger unit to the AA with `trigger.data.create_team = true`), a modest amount of bytes per team (`5000` plus network fees), and no special timing or race condition. An attacker with a moderate budget can create enough decoy teams to keep `balance[base]*0.51` growing faster than the honest contributions to any real team, indefinitely delaying or permanently blocking any team from reaching the winning threshold.

## Recommendation
Do not use the AA's raw `balance[base]` as the denominator for the win threshold. Instead, maintain a dedicated state variable (e.g., `var['total_contributed']`) that is incremented only by legitimate team contributions (and decremented on refunds/payouts), and compare against that tracked total instead of `balance[base]`. Additionally, either route the team-creation fee into a specific team's contribution total or otherwise account for it explicitly so it cannot be used to inflate an unrelated threshold denominator.

## Proof of Concept
1. Attacker posts unit A: trigger `{ create_team: true }` from address `Addr1`, sending `5000+` bytes. AA mints a team asset for `Addr1`'s team, keeps `5000` bytes; `balance[base]` increases by `5000`, no `team_..._amount` increases.
2. Attacker repeats step 1 from `Addr2`, `Addr3`, ... `AddrN`, each time creating a new team and adding `5000` bytes to `balance[base]` with zero effect on any team's `_amount`.
3. Meanwhile, legitimate users contribute to a real team via `{ team: <team_address> }`, incrementing `var['team_<team>_amount']` and `balance[base]` in lockstep by the same amount.
4. Because the attacker's `create_team` calls add to `balance[base]` without adding to any team's `_amount`, the required threshold `team_amount > balance[base]*0.51` requires progressively larger legitimate contributions to overcome the attacker-inflated denominator. With enough decoy teams (cost scales linearly and cheaply at `5000` bytes per team), the threshold becomes unreachable for any real team, per the code at: [2](#0-1) 
5. `var['finished']` is never set, so the payout case in lines 116-148 never executes, and all funds contributed to the AA are permanently locked, exactly mirroring the impact described in the referenced Fei report.
