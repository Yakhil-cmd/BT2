### Title
Reachable unhandled `throw Error` on duplicate/re-sent private payment output causes wallet/hub process crash - ([File: private_payment.js])

### Summary
CVE-2018-20551 describes a reachable assertion (`Object::getString`) in Poppler that a remote attacker can trigger by constructing an invalid asset object, crashing the process. The analogous pattern in `ocore` is a reachable, un-caught `throw Error(...)` statement inside a database-query callback in the private-payment handling code, which an unprivileged private-payment counterparty can trigger by (re)sending a private payment chain, crashing the wallet/hub Node.js process (denial of service).

### Finding Description
`validateAndSavePrivatePaymentChain` in `private_payment.js` runs a duplicate-detection query before validating and saving a newly received private payment chain: [1](#0-0) 

For a divisible (non-fixed-denomination) private asset, the duplicate-check SQL does **not** filter by `output_index`:
```
sql = "SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?"
```
Because a single payment message legitimately has multiple outputs, this query can legitimately return more than one row once the corresponding unit/message has already been (partially) saved with revealed addresses — e.g. after the same private chain was already accepted once and is then received again (retransmission from the hub, another cosigner path, or an attacker-controlled peer deliberately re-sending the same `private_payment` content, which is exactly the kind of message an unprivileged private-payment counterparty can send, per `handleOnlinePrivatePayment` in `network.js`): [2](#0-1) 

When `rows.length > 1`, the code does not return an error through the normal `callbacks.ifError` path — it unconditionally throws:
```js
if (rows.length > 1)
    throw Error("more than one output "+sql+' '+params.join(', '));
``` [3](#0-2) 

This `throw` executes inside the asynchronous callback of `conn.query(...)`, which is invoked from the SQLite driver's own callback chain (see `sqlite_pool.js`), not inside any `try/catch` in the call stack that leads back to `network.js`'s message dispatcher. There is no `process.on('uncaughtException', ...)` handler wrapping this specific code path that would gracefully recover it (the two `uncaughtException` references in `network.js` are unrelated top-level handlers, but a synchronous throw from inside a DB driver callback in Node.js is not reliably caught by those and typically terminates the event loop / crashes the process, exactly analogous to a reachable `assert`/exception aborting the Poppler process).

This is directly analogous to the Poppler bug class: a well-formed-looking but "invalid" input (here, a duplicate/replayed private-payment message causing an unexpected multi-row result) reaches a hard assertion (`throw Error`) that is not converted into a normal validation error, and the resulting unhandled exception aborts the whole process rather than merely rejecting the one bad unit.

### Impact Explanation
Any private-payment counterparty (or a peer who can resend previously-seen `private_payment` network messages, which requires no special privilege — `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` are reachable from any connected peer) can cause the receiving wallet or hub process to hit this code path and crash with an uncaught exception. This is a network-triggerable denial of service against a node/wallet process — "a network unable to confirm new units" for that node/hub, and repeated crash-on-restart can be used to persistently deny service to a wallet/hub that keeps re-receiving the same/duplicated private-payment data (e.g., from `unhandled_private_payments` reprocessing in `handleSavedPrivatePayments`, which re-invokes the exact same vulnerable function on every retry cycle). [4](#0-3) 

### Likelihood Explanation
The conditions to reach the throw are realistic: a private payment message with more than one output for the same `unit`/`asset`/`message_index` is a normal, legitimate divisible-asset payment shape. All that's needed is for the same chain to be observed a second time after the outputs have already been written with revealed addresses (duplicate resend by the hub itself, a legitimate second recipient/cosigner processing path, or a malicious peer deliberately replaying previously observed `private_payment` traffic). No cryptographic forgery or privileged access is required — only sending/replaying a `private_payment`/`private_payment_chains` message that an unprivileged peer is already permitted to send.

### Recommendation
- Replace the `throw Error(...)` at `private_payment.js:75` with a call to `transaction_callbacks.ifError(...)`, so an unexpected multi-row result is treated as a rejectable/duplicate condition instead of crashing the process.
- Add an `output_index` (or equivalent) discriminator to the duplicate-check SQL for divisible assets so multiple legitimate outputs of the same message do not spuriously match as "more than one output."
- Audit other `throw Error` statements embedded inside `conn.query` callbacks reachable from network-supplied data (e.g., `indivisible_asset.js` chain-building queries, `validation.js` input/output lookup queries) and convert them to callback-based error paths rather than synchronous throws, since these callbacks execute outside any protective `try/catch` in the calling stack.

### Proof of Concept
1. Attacker/peer sends a `private_payment` message containing a divisible-asset private chain whose head element has two or more outputs, targeting the victim node/wallet, via `handleOnlinePrivatePayment` (`network.js:2375`).
2. The victim processes and saves it normally the first time (`private_payment.js` → `assetModule.validateAndSavePrivatePaymentChain`), writing multiple output rows with revealed `address`.
3. Attacker/peer re-sends the identical `private_payment` content again (or it is naturally re-delivered via `handleSavedPrivatePayments`'s retry logic).
4. `validateAndSavePrivatePaymentChain` runs the duplicate-check SQL without an `output_index` filter, and now `rows.length > 1` for the already-saved multi-output message.
5. `throw Error("more than one output "...)` fires inside the `conn.query` callback with no enclosing `try/catch`, producing an uncaught exception that crashes the Node.js process handling private payments — denial of service for that wallet/hub node.

function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	if (!ValidationUtils.isValidBase64(unit, constants.HASH_LENGTH))
		return callbacks.ifError("invalid unit");
	if (!ValidationUtils.isNonnegativeInteger(message_index))
		return callbacks.ifError("invalid message_index");
	if (!(ValidationUtils.isNonnegativeInteger(output_index) || output_index === -1))
		return callbacks.ifError("invalid output_index");

	var savePrivatePayment = function(cb){
		// we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device.
		// in this case, we also receive the same (unit, message_index, output_index) twice - as cosigner and as recipient.  That's why IGNORE.
		db.query(
			"INSERT "+db.getIgnore()+" INTO unhandled_private_payments (unit, message_index, output_index, json, peer) VALUES (?,?,?,?,?)", 
			[unit, message_index, output_index, JSON.stringify(arrPrivateElements), bViaHub ? '' : ws.peer], // forget peer if received via hub
			function(){
				callbacks.ifQueued();
				if (cb)
					cb();
			}
		);
	};
	
	if (conf.bLight && arrPrivateElements.length > 1){
		savePrivatePayment(function(){
			updateLinkProofsOfPrivateChain(arrPrivateElements, unit, message_index, output_index);
			rerequestLostJointsOfPrivatePayments(); // will request the head element
		});
		return;
	}

	joint_storage.checkIfNewUnit(unit, {
		ifKnown: function(){
			//assocUnitsInWork[unit] = true;
			privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
				ifOk: function(){
					//delete assocUnitsInWork[unit];
					callbacks.ifAccepted(unit);
					eventBus.emit("new_my_transactions", [unit]);
				},
				ifError: function(error){
					//delete assocUnitsInWork[unit];
					callbacks.ifValidationError(unit, error);
				},
				ifWaitingForChain: function(){
					savePrivatePayment();
				}
			});
		},
		ifNew: function(){
			savePrivatePayment();
			// if received via hub, I'm requesting from the same hub, thus telling the hub that this unit contains a private payment for me.
			// It would be better to request missing joints from somebody else
			requestNewMissingJoints(ws, [unit]);
		},
		ifKnownUnverified: savePrivatePayment,
		ifKnownBad: function(){
			callbacks.ifValidationError(unit, "known bad");
		}
	});
}
