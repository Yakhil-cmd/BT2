### Title
Reward-points overflow panic in `calculate_stake_rewards` can halt epoch reward processing for a legitimately large, long-unclaimed stake account - (File: `runtime/src/inflation_rewards/mod.rs`)

### Summary
The reported Bond.sol issue is a `mulDivDown` overflow that freezes bond redemption because the multiplication `bonds * paidAmount` (or `bonds * nonPaidAmount`) can exceed `2**256` for legitimately large but permitted bond supplies, and the contract has no guard rail limiting the issuance size to keep that multiplication safe. The Agave analog is the Tower reward-scaling arithmetic in `calculate_stake_rewards`, where `tower_points` (itself an unbounded accumulation of `stake_amount * earned_credits` across every un-redeemed epoch) is multiplied by `point_value.rewards` and the intermediate result is `.expect()`-unwrapped rather than clamped/handled, so an unusually large but reachable combination of stake size and unredeemed-epoch count panics instead of failing gracefully.

### Finding Description
`tower_epoch_credits_iter` accumulates `points += stake_amount * earned_credits` for every un-redeemed epoch of a Tower-era stake account: [1](#0-0) . Because `points` is a plain `u128` addition with no `checked_add`, and each term can already be close to `u64::MAX * u64::MAX`, a stake account that goes unredeemed for many epochs (which is explicitly supported — the code comments describe "Tower collects everything from t=0") can accumulate `tower_points` approaching `u128::MAX`.

That `tower_points` value is then multiplied by `point_value.rewards` (a `u64`) and unwrapped with an `.expect()` rather than propagated as an error: [2](#0-1) 

The same unchecked-then-expect pattern repeats for the `MigrationEpoch` branch: [3](#0-2) 

This is confirmed by the codebase's own regression tests, which assert that specific large `(stake, rewards, credits)` combinations panic rather than error: [4](#0-3) 

This function, `calculate_stake_rewards`, is invoked from `redeem_stake_rewards`/`redeem_rewards`, which is called from `calculate_stake_rewards_and_commissions` for every stake delegation during epoch-boundary reward calculation: [5](#0-4) . This reward-calculation pass runs deterministically on every validator processing the epoch boundary (inside a `rayon` parallel iterator over all stake delegations), so any panic here is not local/recoverable — it aborts the bank's reward computation for that epoch on every node that reaches it.

This is the direct structural analog of the Bond report: an unguarded multiplication of two attacker/user-influenced magnitudes (`stake` and accumulated `credits`) that is only safe as long as neither operand grows large enough, with no factory/protocol-level cap analogous to the recommended `bonds * bonds` safety check, and the failure mode is a hard revert/panic instead of a value that saturates or errors gracefully.

### Impact Explanation
Where the Bond.sol bug merely freezes an individual user's redemption, this Agave analog is reachable inside the deterministic, network-wide epoch-rewards computation. A stake account whose owner (any unprivileged delegator) never redeems rewards while accumulating enough weighted credits, combined with a sufficiently large `stake` amount, can push `tower_points.checked_mul(point_value.rewards)` (or the u128→u64 downcast of the final `rewards` split) past its bound. Because the overflow is handled via `.expect()`/`.unwrap()` panics rather than a checked/saturating conversion, this crashes the bank's reward-distribution code path — which every validator executes identically at the epoch boundary — producing a cluster-wide halt rather than an isolated user-facing revert.

### Likelihood Explanation
Likelihood depends on whether realistic stake sizes and epoch counts can actually reach the overflow threshold of `u128` (~3.4×10^38) for `tower_points`, and `u64` for the final reward split. Each accumulated term is bounded by `u64::MAX * u64::MAX` (~3.4×10^38) per epoch already, so even a handful of epochs with large stake and large credit deltas can approach or exceed `u128::MAX`, and the final `rewards` value must still fit `u64` after the commission split. This is a legacy ("Tower") code path — the codebase is migrating to Alpenglow where the analogous accumulation is avoided — so exploitability is limited to networks/epochs still running the Tower/MigrationEpoch reward math, and to stake accounts that intentionally avoid redeeming for very long periods with unusually large delegations. This narrows likelihood relative to the original report but the reachable path and unguarded arithmetic are concretely present in code, not theoretical.

### Recommendation
Replace the `.expect()`/`.unwrap()` calls in the Tower and MigrationEpoch branches of `calculate_stake_rewards` (`runtime/src/inflation_rewards/mod.rs` lines ~299-329) with saturating or checked arithmetic that returns a graceful `None`/error (consistent with how `calculate_block_reward` already clamps its analogous u128 computation via `.unwrap_or(u64::MAX).min(...)`, see `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` lines 227-230). Additionally, consider bounding the accumulation in `tower_epoch_credits_iter` (`runtime/src/inflation_rewards/points.rs` lines 205-222) with `checked_add`/`saturating_add` so that pathological long-unredeemed accounts fail safely rather than panicking the bank during epoch-boundary processing.

### Proof of Concept
The codebase's own test harness already demonstrates the panic condition: [6](#0-5) 
`calculate_rewards_tests(1, u64::MAX, u64::MAX)` panics with `"Rewards should fit within u64"`, and `calculate_rewards_tests(u64::MAX, 1_000, u64::MAX)` panics with `"Rewards intermediate calculation should fit within u128"`, confirming that reaching these input magnitudes through normal stake/credits accumulation (rather than through a crafted single call) causes an unrecoverable panic inside the reward-calculation code path invoked at every epoch boundary.
