### Title
Global `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status event authenticated for one repository/org write a Status onto a Commit belonging to a different stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)` [1](#0-0)  with no scoping by repository/organization, even though the webhook was authenticated only against the organization derived from `params['repository']['owner']['login']` in `WebhooksController#verify_signature`/`#repository_owner` [2](#0-1) . Because `Commit` rows are globally unique only on `sha` text and are tied to a fixed `stack_id` set at creation time (`belongs_to :stack`) [3](#0-2) , a payload whose HMAC was verified using org R2's `webhook_secret` can still match and mutate a `Commit` that belongs to stack R1, writing a `Status` (and cascading side effects) for R1 using R2-authenticated, attacker-influenced data. This constitutes a cross-tenant write not authorized by the party that authenticated the request.

### Finding Description
The intended binding is: **org(R2) whose `webhook_secret` verified the payload == org(R1) whose Stack/Commit/MergeRequest gets mutated**. Tracing the code shows this binding is never enforced:

1. `WebhooksController#verify_signature` picks `Shipit.github(organization: repository_owner)` using only `params.dig('repository','owner','login')` and validates the signature against **that org's** secret [4](#0-3) . This proves the payload came from R2 (the repo named in the payload), and nothing else.
2. `StatusHandler#process` then ignores `params.repository` entirely and does a **global** lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . There is no `stack_id`/`repository` filter tying the lookup back to R2.
3. `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` using the **found commit's own `stack_id`** (i.e., R1's stack, if that's the matching row) [5](#0-4) , and `add_status` triggers `stack.schedule_merges` when the new status is `success`/`pending` [6](#0-5) .
4. `MergeRequest#all_status_checks_passed?` reads `head.statuses_and_check_runs` off that same `head` Commit object [7](#0-6) , and `ProcessMergeRequestsJob#perform` calls `merge_request.merge!` once `all_status_checks_passed?` is true [8](#0-7) .

For this chain to fire, a `Commit` row with an identical `sha` string must already exist for stack R1 — i.e., the same 40-hex-character sha value must be present in both R1's and R2's git history/commit table. Git SHA1 commit ids are content-addressed (tree, parents, author/committer identity and timestamps, message) but are **plain strings in Shipit's database with no repository binding at the value level**; the model performs no verification that a "matching" sha actually originated from the git object graph of R1's repository. Duplicate shas across unrelated repos legitimately occur in forks/shared history, and nothing in this code path checks that the org that authenticated the webhook (R2) owns the repository that the matched Commit's stack (R1) tracks.

None of the existing guards mitigate this:
- `verify_signature` / `GitHubApp#verify_webhook_signature` only prove which org's secret matches — they say nothing about which `Commit`/`Stack` rows may be touched [9](#0-8) .
- `drop_unhandled_event` only checks the event type is handled, not the repository scope.
- `ExplicitParameters` (`params do ... end` block in `StatusHandler`) validates the shape of `sha`/`state`/etc., not tenant ownership [10](#0-9) .
- `Commit.by_sha` (used elsewhere, e.g. merge request head resolution) is scoped via `stack.commits.by_sha`, but `StatusHandler#process` bypasses that scoping entirely by querying the bare `Commit` model.

### Impact Explanation
An attacker who controls repository R2 (any GitHub org/repo they own, with Shipit installed as a GitHub App on it) can cause a `Status` row to be written on stack R1's `Commit` for a sha that also exists in R1's history, using R2's own webhook delivery (properly signed with R2's secret). If that sha is the `head` of a pending `MergeRequest` in R1, this can flip `all_status_checks_passed?` to `true` and cause `ProcessMergeRequestsJob` to invoke `merge_request.merge!`, merging a pull request in R1 without R1's own CI having reported success — an unauthorized merge, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The blast radius is bounded by needing a genuinely shared/colliding sha between R1 and R2 (e.g., via forks, cherry-picks, or shared upstream history reproducing identical commit metadata), which is a real but non-trivial precondition; it is not a hash-collision requirement in the cryptographic sense, but requires the two repos to actually contain byte-identical commit objects.

### Likelihood Explanation
Preconditions: (1) Shipit hosts stacks for both R1 and R2 (or R2 need not even have a Shipit stack — only R1 does, and R2 just needs a webhook_secret with Shipit installed as its GitHub App so `verify_signature` succeeds); (2) a commit with an identical sha must exist in R1's Shipit `commits` table already (e.g., because the PR branch was rebased from/forked from a public commit, or the attacker engineered identical tree/parent/author/committer/timestamp/message to reproduce R1's target sha in their own repo — feasible for forks sharing history, harder for unrelated repos). Given those preconditions, the attack is cheap and repeatable: any status webhook (`push`, "status", or check-run-equivalent) from R2 with the colliding sha and `state: success` reaches `StatusHandler#process` unauthenticated with respect to R1. Feasibility is highest in fork-based workflows where sha collisions across repos naturally occur.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the analogous check-run handler if present) to commits belonging to stacks whose repository matches the authenticated `repository_owner`/`repository.full_name` from the webhook payload, e.g. `Commit.joins(:stack).merge(Stack.where(repository_owner: ..., repository_name: ...)).where(sha: params.sha)`, so a Status can only be attached to commits of the repository that actually authenticated the webhook.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, minitest)
test "status webhook authenticated for R2 must not affect a MergeRequest queued in R1" do
  stack_r1 = shipit_stacks(:shipit) # repo_owner: 'org1', repo_name: 'repoA'
  stack_r2 = shipit_stacks(:cyclimse) # repo_owner: 'org2', repo_name: 'repoB', different org

  sha = 'a' * 40
  commit_r1 = stack_r1.commits.create!(sha: sha, message: 'shared commit')
  merge_request = stack_r1.merge_requests.create!(number: 42, head: commit_r1, merge_status: 'pending')

  assert_equal false, merge_request.all_status_checks_passed?

  # Binding under test: org(R2) authenticated == org(R1) mutated
  authenticating_org = 'org2'      # verified via R2's webhook_secret
  mutated_org        = stack_r1.repository_owner # 'org1'
  refute_equal authenticating_org, mutated_org

  params = Shipit::Webhooks::Handlers::StatusHandler.const_get(:Params).new(
    sha: sha, state: 'success', context: 'ci', repository: { owner: { login: 'org2' }, name: 'repoB' }
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.process(params) # or POST /webhooks signed with org2 secret

  merge_request.reload
  # If vulnerable: this now returns true even though R1's own CI never ran.
  assert merge_request.all_status_checks_passed?
end
```
This demonstrates the pre/post state of the binding (`authenticating_org != mutated_org`) and shows `all_status_checks_passed?` flips for the R1 `MergeRequest` from an R2-authenticated payload.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
