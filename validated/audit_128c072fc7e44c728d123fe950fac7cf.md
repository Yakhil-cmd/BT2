## Title
Unhandled crash in AA-trigger dry-run when a unit mixes a public and a private payment message - ([File: network.js])

### Summary
`CVE-2023-37010` crashes Open5GS MME with an unhandled assertion when a remotely-sent S1AP message omits a field (`MME_UE_S1AP_ID`) that the parser assumes is always present. The structural analog in `ocore--025` is in the `ifOk` handler of `handleJoint` in `network.js`, which — when `conf.bDryRunNewTriggers` is enabled — unconditionally assumes every `payment` message in an accepted unit carries an inline `payload.outputs` array, even though a `payment` message can legitimately have `payload_location: "none"` (a private payment) with no inline `payload` at all.

### Finding Description
Any unprivileged unit poster can build and broadcast a unit containing:
1. one public `payment` message with at least one output to an AA address (needed to satisfy `validateAATrigger`, [1](#0-0) , which only requires ≥1 payment output addressed to an AA), and
2. a second `payment` message using `payload_location: "none"` (a private payment), which per validation rules is legal as long as `spend_proofs` are supplied and does not require an inline `payload` — [2](#0-1)  only requires spend proofs, not an outputs field.

Such a unit passes `validation.validate()` normally, since `validateMessage`/`validateInlinePayload` treats `payload_location !== "inline"` as legitimately payload-less. Once validation succeeds and the `ifOk` callback runs, if `conf.bDryRunNewTriggers` is turned on, the following code executes unconditionally on **every** payment message, without checking `payload_location` or the existence of `msg.payload`:

```js
const outputAddresses = objJoint.unit.messages
    .filter(msg => msg.app === 'payment')
    .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
``` [3](#0-2) 

Because the private `payment` message has no `payload` property, `msg.payload.outputs` throws a `TypeError: Cannot read properties of undefined (reading 'outputs')`. This throw happens synchronously inside the `async function ifOk(...)` [4](#0-3) , so it becomes an unhandled promise rejection rather than being routed to any of the `ifUnitError`/`ifJointError`/`ifTransientError` callbacks that normally sanitize bad input. Node.js versions that terminate the process on unhandled rejections (the modern default) will crash the entire node.

This mirrors the CVE root cause exactly: a message type that is legitimately allowed to omit a "required-looking" field (`MME_UE_S1AP_ID` in the S1AP case, `payload`/`outputs` here) is dereferenced without a presence check in a code path that is reachable directly from attacker-controlled network input.

The same file even documents the assumption that `getTrigger()` can crash by design ("if it would crash, let it crash now, not when we execute the trigger for real" [5](#0-4) ), but the crash actually occurs one line earlier, before `getTrigger` is even reached, from the naive `.reduce()` over all payment messages including ones without `payload`.

### Impact Explanation
Any node (full node or hub) that runs with `conf.bDryRunNewTriggers = true` can be crashed by any peer, or even by a self-composed and broadcast unit, sending a single unit with one public payment output to a known AA address plus one private/no-payload payment message. Since this is a synchronous throw before `writer.saveJoint` is invoked, it can be repeated on demand to keep crashing the process — resulting in denial of service for the affected node(s), consistent with the CVE's "repeatedly crash ... resulting in denial of service" impact. This is a node-disagreement/availability risk to the network's ability to confirm/relay units through the crashing node.

### Likelihood Explanation
Likelihood is Medium: the crash path is trivially reachable by any actor able to compose a valid unit (an unprivileged unit poster), requires no special privileges, and needs only a known AA address plus the ability to attach one private payment message alongside a public one — both of which are ordinary, supported unit-construction features in ocore. The only mitigating factor is that the vulnerable code path is gated by the `conf.bDryRunNewTriggers` configuration flag, which is not confirmed to be enabled by default in this codebase (it appears only in `network.js` with no other references found, suggesting it is an opt-in feature for certain deployments, e.g., hubs wanting early-crash detection). Nodes/hubs that do enable this flag are fully exposed.

### Recommendation
In the `ifOk` handler in `network.js`, filter/guard the `payment` message reduction to only consider messages with inline payloads before accessing `.outputs`:
```js
const outputAddresses = objJoint.unit.messages
    .filter(msg => msg.app === 'payment' && msg.payload && Array.isArray(msg.payload.outputs))
    .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
```
Additionally, wrap the entire `bDryRunNewTriggers` block (including `getTrigger` and `dryRunPrimaryAATrigger` calls) in a `try/catch` so that any unexpected internal assertion failure is logged and safely ignored rather than crashing the node, since this block is explicitly a best-effort "dry run" and should never be allowed to bring down unit acceptance.

### Proof of Concept
1. Identify (or deploy) a node running with `conf.bDryRunNewTriggers = true`.
2. Identify any existing AA address `AA_ADDR` on the DAG.
3. Compose and sign a unit with two messages:
   - `{ app: 'payment', payload_location: 'inline', payload: { outputs: [{ address: AA_ADDR, amount: <bounce_fee_or_more> }] } }`
   - `{ app: 'payment', payload_location: 'none', spend_proofs: [{ spend_proof: <valid_base64_hash> }] }` (a private payment referencing a real private-payment chain the attacker controls, satisfying `validateSpendProofs`)
4. Broadcast the unit to the target node via the standard `post_joint`/network relay path.
5. The unit passes `validation.validate()` (both payment messages are individually valid). In `ifOk`, the `.reduce()` over payment messages hits the private payment message with `msg.payload === undefined`, throwing `TypeError: Cannot read properties of undefined (reading 'outputs')`, which surfaces as an unhandled promise rejection inside the async `ifOk` handler and crashes the node process.

**Note on verification**: I was not able to fully confirm whether `conf.bDryRunNewTriggers` defaults to `true` or `false` in the shipped configuration files (`conf.js`/`conf.json`), or in which deployment profiles (hub vs. full node vs. light) it is typically enabled, since no matching entries were found outside `network.js` in the indexed codebase. If precise confirmation of the default value is needed, a Devin session with full repository access would be required to inspect `conf.js` and any deployment-specific configuration overlays.
