### Title
Cross-repository status forgery via unscoped SHA lookup enables blocked?/deployable? manipulation - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `Commit` table, with no repository/stack scoping, unlike every other webhook handler (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) which resolve `stacks` from `payload.dig('repository','full_name')` via `Handler#stacks`. Because `verify_signature` only authenticates that a webhook genuinely originated from the repository named in its own payload, a status event that is legitimately signed for repository A is written to every `Commit` row in the database sharing that SHA, including commits belonging to a victim stack B whose commits share history (e.g., forks) with repository A.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.github_repo_name == payload['repository']['full_name']`, but `StatusHandler#process` never checks this: [1](#0-0) 

writes to `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — matching on `sha` alone, with no `stack_id`/repository filter. Compare with `Handler#stacks`, used by other handlers, which correctly scopes to the repository that authenticated the webhook: [2](#0-1) 

`verify_signature` in `WebhooksController` only verifies that the request signature matches the GitHub App/secret associated with `repository_owner` taken from the payload itself — it verifies *a* valid webhook, not that the referenced SHA belongs to that repository: [3](#0-2) 

Once `create_status_from_github!` runs, it calls `add_status`, which recomputes `Commit#status`, and since `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)`: [4](#0-3) 

a forged `success` status for a `blocking_statuses`-configured context clears that context's ability to block, directly changing `Commit#blocked?`: [5](#0-4) 

and thus `Commit#deployable?`, which gates continuous delivery and merges: [6](#0-5) [7](#0-6) 

Exploit flow: An attacker forks the victim's GitHub repository (forks share identical SHAs with the upstream for all commits at fork time and for any commits cherry-picked/rebased identically). The attacker installs/configures a webhook or GitHub App on their own fork (something they can legitimately do as owner of their own repository) so that a `status` event they trigger via the GitHub API on their own fork (setting `context: security/scan`, `state: success` on a shared SHA) is delivered to the Shipit host with a signature that legitimately validates for the attacker's own repository owner. `StatusHandler#process` then finds any `Commit` row anywhere in the database with that SHA — including the victim stack's commit — and writes the forged status onto it, flipping `blocking?`/`blocked?`/`deployable?` for the victim's stack without ever authenticating against the victim's repository.

Existing guards do not prevent this: `verify_signature` authenticates the sender as *some* legitimate repository/owner, but never checks that the owner matches the repository owning the target `Commit` record; `drop_unhandled_event` and `ExplicitParameters` only validate payload shape, not repository identity; there is no `require_permission!`/`stacks` scoping call in `StatusHandler` at all.

### Impact Explanation
A single unprivileged actor who owns a fork of a victim repository (or otherwise can produce/replay a commit with an identical SHA, e.g. via cherry-pick/rebase reproducing the same tree/parent/author/timestamp) can inject or clear blocking/required statuses on a completely different tenant's stack. This can force `Commit#blocked?` to `false` (unblocking a stack that has unresolved required checks, enabling an unauthorized deploy) via `success`-driven state changes that clear `blocking?`, and can also trigger `stack.schedule_merges` for merge queues. This matches "a payload for one repository mutating another's stack/commit" — Critical, cross-tenant state manipulation leading to unauthorized deploy.

### Likelihood Explanation
Preconditions: victim stack must have `blocking_statuses` (or `required_statuses`) configured for some context, and the target commit SHA must be shared between the attacker-controlled repository and the victim repository (trivial for forks, achievable by construction for any repo since git commit metadata, including SHA1, can be replicated by copying tree/parent/author/committer/timestamp/message). The attacker needs no Shipit credentials, no GitHub organization membership in the victim's org, and no maintainer role — only ownership of a repository that can be validly webhooked to the Shipit host. This is inexpensive and repeatable against any stack whose commits overlap in history/SHA with an attacker-owned repo.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `Handler#stacks`: resolve commits only through `stacks.flat_map(&:commits).where(sha: params.sha)` (or join `Commit` through `Stack`/`Repository` filtered by `repository_name`), and skip/no-op when no matching stack exists for that repository.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually):
1. Create `repository_a` (`full_name: "attacker/repo"`) and `repository_b` (`full_name: "victim/repo"`), each with its own `Stack`.
2. Configure `stack_b`'s deploy spec with `blocking_statuses: ["security/scan"]`.
3. Create `commit_b` on `stack_b` with `sha: "deadbeef..."` and a prior blocking status (e.g. `error` for `security/scan`) so `commit_b.blocked?` is initially `true` and `commit_b.deployable?` is `false`.
4. Assert before: `commit_b.blocked? == true`.
5. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha: "deadbeef..."`, `context: "security/scan"`, `state: "success"` (simulating the attacker's own, validly-signed webhook).
6. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, which is orthogonal — it only authenticates repository A, not repository B).
7. Assert after: `commit_b.reload.blocked? == false` and `commit_b.deployable?` changed, even though the webhook's `repository.full_name` never matched `repository_b.full_name` — proving the write crossed repository boundaries.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
