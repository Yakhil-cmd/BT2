### Title
Impersonation of any Shipit user via unauthenticated `X-Shipit-User` header when triggering API deploys/tasks - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
`Shipit::Api::BaseController` authenticates a *request* using an `ApiClient` token via HTTP Basic Auth, but the *identity credited for the action* (`current_user`) is derived from the unauthenticated, attacker-controlled `X-Shipit-User` header. This breaks the binding "the credential that authorizes the API call" = "the identity recorded as having performed the privileged action," letting any holder of a valid (even minimally-scoped) API token impersonate an arbitrary registered Shipit user for deploys, task triggers, and task aborts.

### Finding Description
`ApiClient.authenticate` verifies a signed token via HTTP Basic Auth and sets `@current_api_client`, which is checked against `PERMISSIONS` like `deploy:stack` [1](#0-0) . However, the `current_user` used for crediting the action is computed independently from a raw request header supplied by the caller, with **no cryptographic binding to the authenticated ApiClient**:

```ruby
def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
``` [2](#0-1) 

This `current_user` is passed straight into privileged operations:
- `Shipit::Api::DeploysController#create` → `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- `Shipit::Api::TasksController#trigger` and `#abort` → `stack.trigger_task(params[:task_name], current_user, ...)` / `task.abort!(aborted_by: current_user)` [4](#0-3) 
- `Shipit::Api::MergeRequestsController#update` → `MergeRequest.request_merge!(stack, params[:id], current_user)` [5](#0-4) 

`Stack#trigger_task` / `#build_deploy` persist `user_id: user.id` onto the `Task`/`Deploy` record with no further check that this user is who actually authenticated [6](#0-5) . This behavior is explicitly exercised by the test suite, confirming it is intended: `request.headers['X-Shipit-User'] = @user.login; ...; assert_equal @user, deploy.user` [7](#0-6) , and similarly for task-abort attribution [8](#0-7) .

This is analogous to the reported bug class: the authentication boundary (ApiClient signature/permission check) is separate from — and does not cover — the field (`X-Shipit-User`) that determines whose identity is bound to the resulting privileged record. Just as `checkTransaction` let anyone reset state the guard was supposed to protect, here any caller possessing *a* valid API token (even one scoped to a single low-privilege stack) can set the `X-Shipit-User` header to the login of any other registered user (e.g. an admin/approver) and have Shipit's database and audit trail record that other user as the author/approver/aborter of the action, without that user's `github_access_token`, session, or knowledge.

### Impact Explanation
This does not bypass the `ApiClient`'s permission scope (an attacker still needs a token with `deploy:stack`), but it defeats accountability/attribution controls that Shipit relies on for audit, review workflows, and any downstream logic keyed off `user` identity (e.g. `SHIPIT_USER`/`GIT_COMMITTER_NAME` environment injected into deploy scripts, and merge-request "requested by" attribution used in `MergeRequest.request_merge!`). Falsifying the deploy/task author or merge-requester identity of a privileged/trusted user constitutes an identity-spoofing/authorization-record forgery within the scope of "escalation into authorization" for actions gated on user identity, though it stops short of outright unauthenticated deploy since a valid, permissioned API token is still required.

### Likelihood Explanation
High for any environment that issues more than one `ApiClient` token (a common real-world setup, e.g. per-integration or per-team tokens as documented in `docs/setup.md` and the API client UI). Any token holder can trivially set an HTTP header; no additional secret or race condition is needed.

### Recommendation
Cryptographically bind the acting user's identity to the authenticated request instead of trusting a client-supplied header, e.g.:
- Sign/verify `X-Shipit-User` (or equivalent) together with the `ApiClient` token, or
- Restrict which logins an `ApiClient` may claim (e.g. via an allow-list tied to the `ApiClient` record, similar to `stack_id` scoping), and
- Require an explicit `write:hook`/impersonation permission before honoring `X-Shipit-User`, defaulting to attributing actions to the `ApiClient`'s `creator` otherwise.

### Proof of Concept
1. Create (or obtain) any `ApiClient` with only `deploy:stack` permission scoped to a single stack (e.g. via `/api_clients`) — no admin rights needed for the impersonated identity.
2. Send:
```
POST /api/stacks/org/repo/env/deploys
Authorization: Basic <base64(api_client_token)>
X-Shipit-User: some-privileged-user-login
sha=<valid_sha>
```
3. The resulting `Deploy` record's `user` is `some-privileged-user`, as directly demonstrated by the existing test `"#create use the claimed user as author"` [9](#0-8) , with no verification that the requester is in fact that user.

    def trigger_task(definition_id, user, env: nil, force: false)
      definition = find_task_definition(definition_id)
      env = env.to_h

      definition.variables_with_defaults.each do |variable|
        env[variable.name] ||= variable.default
      end

      commit = last_deployed_commit.presence || commits.first
      task = tasks.create(
        user_id: user.id,
        definition:,
        until_commit_id: commit.id,
        since_commit_id: commit.id,
        env: definition.filter_envs(env),
        allow_concurrency: definition.allow_concurrency? || force,
        ignored_safeties: force
      )
      task.enqueue
      task
    end
