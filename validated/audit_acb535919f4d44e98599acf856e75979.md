### Title
Cross-repository/cross-tenant commit status mutation via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)`, with no join or filter on `repository`/`stack`, unlike the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)`) that every other handler is expected to use. Because commit SHAs are not guaranteed unique across tracked repositories/stacks, a genuine, correctly-signed `status` webhook from one organization's repository can mutate the CI status of a commit belonging to an entirely different tracked repository/stack that happens to share the same SHA.

### Finding Description
The binding that should hold is: `organization that produced/verified the webhook signature (repository_owner in payload)` == `organization owning every Commit row mutated by commit.create_status_from_github!(params)`.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from the *attacker's own* payload (`params.dig('repository','owner','login')`). This only proves the request is a genuine webhook from that organization's app installation — it says nothing about which commit rows may be touched.
- `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) exists precisely to scope handler effects to `Repository.from_github_repo_name(repository_name)` — i.e., to the repository named in the same payload that was signature-verified.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does **not** use `stacks` or any repository/stack filter at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) creates/replicates a status row and `add_status` (commit.rb:366-386) can trigger `Hook.emit(:commit_status/:deployable_status, stack, ...)` and `stack.schedule_merges` — i.e., it can change deployability/merge scheduling for the *victim* stack.

Because `sha` is a global string with no per-repository namespace in the `commits` table, any two repositories tracked by the same Shipit instance can contain a `Commit` row with an identical SHA (e.g., identical initial/empty commits, cherry-picked/rebased commits, or repos sharing history via forks). An attacker who owns a legitimate repository already onboarded to this Shipit instance can trigger (or directly craft, since they control their own repo's commits) a real, validly-signed `status` event naming a SHA equal to a commit that also exists under a victim repository/stack. `verify_signature` passes because the signature is valid for the attacker's own organization; `drop_unhandled_event` and `ExplicitParameters` schema checks pass because the payload is well-formed. Nothing then checks that the resolved `Commit` rows belong to a stack under the verified `repository_owner`/`repository_name`.

### Impact Explanation
The attacker's genuine webhook for their own repository writes a `CommitStatus`/state onto a `Commit` belonging to a different, unrelated tenant's stack, which can flip that commit from pending/failure to success (or vice versa), and can trigger `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)` for the victim stack — i.e., a payload for one repository mutating another repository's commit/stack state, which can influence continuous-delivery/merge decisions. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." Repeatable against any repository pair that shares a colliding SHA, and blast radius spans all tenants/stacks hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: attacker must control (or push to) a repository already connected to this Shipit instance so they can emit a genuinely-signed `status` webhook (per the stated attacker capabilities, this is allowed — "emit webhooks from a repository they own"). The hard constraint is finding/producing a SHA collision with a targeted victim commit; natural git SHA1 collisions across unrelated content are not attacker-controllable, but identical commits (e.g., empty initial commits, common upstream commits shared via fork lineage, or commits with identical tree+message+timestamps) are realistic in practice, especially between a fork and its upstream (both are commonly tracked by CI/Shipit). Given such a collision, the exploit costs a single webhook POST with no additional privilege.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload, mirroring the `stacks` helper, e.g. resolve target commits via the stacks belonging to `Repository.from_github_repo_name(repository_name)` rather than a bare `Commit.where(sha:)` across the entire table:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

### Proof of Concept
Minitest plan (test/models/shipit/webhooks/handlers/status_handler_test.rb):
1. Create `repo_a = shipit_repositories(:shipit)` (or a factory repository) with `stack_a` and `commit_a = create(:commit, stack: stack_a, sha: 'deadbeef'*5)`.
2. Create a second, unrelated `repo_b`/`stack_b` and `commit_b = create(:commit, stack: stack_b, sha: 'deadbeef'*5)` (same SHA, different stack/repository).
3. Build `payload` whose `repository.full_name` matches `repo_a` only, with `sha: 'deadbeef'*5`, `state: 'success'`, `context: 'ci'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
5. Assert: `commit_a.reload.status.state == 'success'` (expected — repo_a authenticated this event) AND assert `commit_b.reload.statuses.count > 0` / `commit_b.reload.status.state == 'success'` (this should be false/unchanged if the binding held, but currently succeeds, proving cross-repository mutation from a single request naming only `repo_a`).
