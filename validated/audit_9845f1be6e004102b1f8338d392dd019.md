### Title
Independent per-recipient rounding in headers-commission distribution can inflate or lose network fee tokens - ([File: headers_commission.js])

### Summary
`calcHeadersCommissions()` splits a won headers-commission `full_amount` among multiple `earned_headers_commission_recipients` by independently computing `Math.round(full_amount * share / 100.0)` for each recipient, without ever verifying that the sum of the rounded per-recipient amounts equals `full_amount`. This is the exact bug class described in the external report: dividing a fixed pool among N recipients by percentage share and rounding each portion separately, without redistributing/accounting for the rounding remainder.

### Finding Description
When an author defines `earned_headers_commission_recipients` (allowed whenever the field is present, required only when there are multiple authors, but not restricted to that case) with shares summing to exactly 100 (enforced in `validateHeadersCommissionRecipients` at [1](#0-0) ), the actual coin distribution performed later in `calcHeadersCommissions` computes each recipient's share independently: [2](#0-1) 

and, in the SQL/db-driven path used when `conf.bFaster` is false: [3](#0-2) 

Because `Math.round()` is applied to each recipient's fractional share separately, the sum of the resulting integer amounts is not guaranteed to equal `full_amount`. Depending on the chosen shares and the parity of `full_amount`, the total paid out can be either:
- **less than `full_amount`** (dust is lost — funds become unspendable, since `full_amount` was reserved from the payer unit's `headers_commission` field but the sum of `headers_commission_contributions` inserted is smaller), or
- **more than `full_amount`** (extra coins minted from nothing, since the payer unit's `headers_commission_outputs` will end up crediting recipients with more total value than the fee actually paid by that unit — a supply-inflation effect).

Concrete example (analogous to the report's 33/500/500 case): `full_amount = 33`, two recipients each with `share = 50`. `Math.round(33*50/100) = Math.round(16.5) = 17` for each recipient (JavaScript's `Math.round` rounds `.5` toward positive infinity), so `17 + 17 = 34`, one unit more than the `33` actually available — an over-distribution. A different split (e.g., 3 recipients at 33/33/34 with an odd `full_amount`) can instead under-distribute, leaving 1 unit permanently unspendable/lost. The same unchecked, independently rounded distribution pattern for TPS fee deltas exists at [4](#0-3) , where `Math.floor(total_tps_fees_delta * share / 100)` is applied per recipient without accounting for the rounding remainder.

Note that `earned_headers_commission_recipients` is a value chosen and signed by the unit's own author(s) — an unprivileged unit poster can freely select the share values (any positive integers summing to 100, sorted by address) to trigger a rounding pattern that benefits or harms the recipients, entirely within the normal unit-posting workflow.

### Impact Explanation
- **Underpayment case**: coins are permanently lost/frozen — the payer unit's headers-commission fee is fully consumed (removed from spendable balance as a fee) but the recipients collectively receive less than that amount, with no path to reclaim the difference.
- **Overpayment case**: this is a supply-inflation bug — recipients collectively receive more units than the fee actually paid by the payer unit, i.e., value is created without being backed by an equivalent debit elsewhere. This directly matches the "concrete supply inflation" impact bar.

Both consequences occur automatically and deterministically as part of ordinary DAG processing (headers-commission winner calculation), so no attacker collusion with witnesses/hubs is required — an author simply chooses shares/timing such that an odd `full_amount` interacts unfavorably with the chosen percentage splits.

### Likelihood Explanation
Any unit author that specifies multiple `earned_headers_commission_recipients` (e.g., to split earnings among several of their own addresses, a legitimate and commonly-supported feature since >1 author requires it and single-author units may also use it) can encounter this whenever the headers-commission `full_amount` they win is not evenly divisible by the chosen percentage splits — a very common occurrence given `full_amount` values vary per unit and are not round numbers. No special privileges, timing races, or network-level manipulation are needed; it manifests purely from the arithmetic in `calcHeadersCommissions`/`updateTpsFees`.

### Recommendation
Do not round each recipient's share independently. Instead:
1. Compute each recipient's amount using floor/round consistently and track the running total already distributed.
2. Assign the last recipient (in the sorted/deterministic order) the remainder: `full_amount - sum(previous_amounts)`, ensuring the total distributed always exactly equals `full_amount`.
3. Apply the same remainder-aware distribution logic to both the in-memory (`assocEarnedHeadersCommissionRecipients`) path and the SQL-driven `profit_distribution_rows` path in `headers_commission.js`, as well as to the TPS fee delta distribution loop in `storage.js`'s `updateTpsFees`, to keep both code paths (and both databases in dual-write mode) consistent and prevent divergence between `arrValuesRAM` and `arrValues` that today only trigger a non-fatal integrity warning (`throwError`) rather than being structurally prevented.

### Proof of Concept
1. An author (or a set of co-authors) posts a unit that will win headers commission from a parent unit whose `headers_commission` (`full_amount`) is an odd number relative to the intended split — e.g., `full_amount = 33`.
2. That unit's `earned_headers_commission_recipients` field specifies two recipient addresses with `earned_headers_commission_share: 50` each (valid per `validateHeadersCommissionRecipients`, since `50 + 50 = 100`).
3. Once the unit becomes the winning child in `calcHeadersCommissions`, the code computes `Math.round(33 * 50 / 100) = 17` for each of the two recipients [5](#0-4) , inserting `17 + 17 = 34` total into `headers_commission_contributions`/`headers_commission_outputs`, one unit more than the `33` actually available from the payer unit — demonstrating unbacked coin creation. Choosing splits/`full_amount` combinations that round down instead demonstrates the complementary "funds lost" case.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
