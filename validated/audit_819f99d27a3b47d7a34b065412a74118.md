### Title
Cross-organization commit-status forgery via webhook signature/routing mismatch enables unauthorized deploy approval - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a GitHub webhook against using an attacker-controlled field of the same JSON payload it is trying to authenticate, while the actual event handler that mutates state (`StatusHandler`) never re-checks that binding and operates globally across every stack/repository in the Shipit instance.

### Finding Description
On every inbound webhook, Shipit derives the "organization" used to fetch the GitHub App/webhook secret directly from the untrusted payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a per-organization config (including its own `webhook_secret`) when Shipit is configured for multiple GitHub organizations/tenants: [3](#0-2) 

Once the signature is verified against the org derived from `repository.owner.login`, the raw JSON body is dispatched by the `X-Github-Event` header to the corresponding handler: [4](#0-3) 

`StatusHandler#process` never re-derives or checks the repository/organization at all — it looks up matching commits **globally** by SHA across the entire Shipit database and writes a new status record: [5](#0-4) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

The signature check binds "which secret authenticated the request" to `repository.owner.login`, but the write path binds "which commit gets a new status" to a completely different, attacker-supplied field (`sha`) with no cross-check against the organization that authenticated the payload. Because the two fields (`repository.owner.login` used for auth, and `sha`/no repository scoping at all used for the write) live in the same attacker-controlled JSON body and are never cross-validated, an entity that only knows the webhook secret for **one** tenant organization configured in a multi-org Shipit deployment can forge a signature for that organization while writing a commit status against a SHA belonging to **any other tenant's stack**.

This directly matches the required binding-break pattern: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Commit status directly drives `Commit#deployable?`: [6](#0-5) 

```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
```

and feeds `stack.schedule_merges` / continuous delivery when the new status is `success`: [7](#0-6) 

By injecting a forged `success` status for a target commit SHA in a victim stack that the attacker does not control, the attacker can mark a commit "deployable" and trigger automatic continuous-delivery merges/deploys, bypassing the CI-gating that Shipit relies on for authorizing deploys. This is an unauthorized-deploy class impact, matching the "Critical" tier ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires: (1) a Shipit instance configured with more than one GitHub organization/tenant (`secrets.github` keyed by multiple orgs, each with its own `webhook_secret`), and (2) the attacker knowing the `webhook_secret` for at least one of those organizations (e.g., because they are a legitimate but unprivileged member/admin of a lower-trust tenant repo onboarded into the same Shipit instance). No GitHub write access to the victim repository, no Shipit session, and no `ApiClient` token are needed — only knowledge of one tenant's webhook secret, which is a materially weaker credential than access to the victim's own resources. This is plausible in any shared/multi-tenant Shipit deployment, though it does not apply to single-organization deployments (where `repository_owner` always resolves to the same, single configured secret).

### Recommendation
After signature verification, re-validate that the organization/owner used to authenticate the webhook (`repository.owner.login`) matches the actual repository/organization that the event payload claims to mutate (`repository.full_name`'s owner segment), and reject the request (422) on mismatch. Additionally, scope `StatusHandler#process` (and any other handler that looks up records without going through `stacks`/`Repository.from_github_repo_name`) to the repository identified in the payload rather than performing a global `Commit.where(sha:)` lookup, so a verified webhook can only affect commits belonging to the organization whose secret validated it.

### Proof of Concept
1. Configure Shipit (hypothetically) with two tenant organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` in `secrets.github`.
2. Attacker knows `attacker-org`'s `webhook_secret` (e.g. they administer a repo in `attacker-org` that is legitimately onboarded to this Shipit instance).
3. Attacker crafts a `status` webhook JSON payload:
```json
{
  "sha": "<sha-of-a-commit-in-victim-org/victim-repo>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s secret, and the signature verifies successfully — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit purely by SHA, with no organization/repository check — and calls `create_status_from_github!`, marking the victim commit `success` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`, `app/models/shipit/commit.rb:165-169,227-229,379-386`).
7. If `victim-org`'s stack has continuous delivery enabled, this can trigger an automatic deploy of the now-"deployable" commit.

Note: I could not directly confirm from the indexed code whether Shipit deployments in practice commonly run multi-org configurations with independently-trusted, lower-privileged tenants (this depends on deployment/operator choices outside `app/**`/`lib/shipit/**`), so the real-world likelihood of an attacker possessing a second tenant's webhook secret is an assumption based on the multi-org support present in `lib/shipit.rb`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
