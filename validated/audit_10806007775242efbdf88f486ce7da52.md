### Title
Denial-of-Service via unbounded growth of `unhandled_private_payments` from unauthenticated private-payment chains - (File: network.js)

### Summary
`network.handleOnlinePrivatePayment()` unconditionally persists every incoming private-payment chain element into the `unhandled_private_payments` table before any real validation of its content, keyed only by an attacker-supplied `(unit, message_index, output_index)` triple. Because the `unit` field only needs to pass a cheap format check (valid base64 hash length) and never has to correspond to a unit that is actually broadcast/paid for, a private-payment counterparty (or any paired device sending `private_payments`) can generate unlimited unique keys and JSON blobs that get written to persistent storage and are purged only once a day (and only from full/hub nodes, not light wallets in the interim). This mirrors the Django session-store DoS (CVE-2015-5143 / GHSA-h582-2pch-3xv3): free, unauthenticated requests with unique keys accumulate persistent storage that isn't cheaply reclaimed.

### Finding Description
`handleOnlinePrivatePayment()` performs only shallow format validation of the head element (`unit` is a valid base64 hash of the right length, `message_index`/`output_index` are non-negative integers) before calling `savePrivatePayment()`, which does an `INSERT ... IGNORE INTO unhandled_private_payments (unit, message_index, output_index, json, peer)`: [1](#0-0) 

The insert happens on the `ifNew` branch (i.e., whenever the `unit` referenced by the attacker is not yet a known unit) without requiring the caller to actually post/pay-for that unit, and without limiting the number of distinct fake units or chain elements a caller can submit: [2](#0-1) 

This path is reachable from a paired device via the wallet protocol: `wallet.handlePrivatePaymentChains()` accepts a `private_payments` message from any correspondent device, only checks the shape of the JSON (non-empty arrays/strings), and forwards every chain element to `network.handleOnlinePrivatePayment()`: [3](#0-2) 

The `arrChains` and their inner `payload.inputs`/`payload.outputs` arrays are attacker-controlled in size and content (only "non-empty object/array/string" checks are performed), so each submission can carry a large JSON payload while still using a fresh, never-before-seen fake `unit`.

Cleanup exists, but is weak and delayed:
- On full/hub nodes, `cleanBadSavedPrivatePayments()` runs once every 300 seconds after coming online and deletes rows only if `creation_date < -1 DAY` AND the referenced `unit` still doesn't exist in `units`: [4](#0-3) 
- On light clients, the analogous cleanup (`requestUnfinishedPastUnitsOfPrivateChains`) similarly only deletes rows after querying light-vendor history and applying a 1-day age threshold: [5](#0-4) 

In the interim (up to 24 hours), the rows persist. The `unhandled_private_payments` table has no size cap and no per-peer/per-address quota: [6](#0-5) 

### Impact Explanation
An attacker with an established device pairing (or acting as a "private-payment counterparty" per the private-payment protocol) can repeatedly submit `private_payments` messages, each referencing a distinct, never-to-be-posted fake `unit` and carrying a sizeable JSON payload (multiple chain elements with many inputs/outputs). Every submission results in a durable database row that survives for up to a day regardless of validity, since the record is written before checking that the referenced unit will ever actually exist. Sustained abuse fills local storage (SQLite/MySQL/RocksDB) on the recipient's wallet or on a hub relaying to it, consuming disk space and degrading database performance (larger tables, slower scans in `handleSavedPrivatePayments`, `cleanBadSavedPrivatePayments`, and `rerequestLostJointsOfPrivatePayments`, all of which do full/JOIN scans over this table). This is a storage/availability DoS analogous to the Django session-store exhaustion: the resource cost to the victim vastly exceeds the (near-zero) cost to the attacker, and unlike posting a real unit, no bytes fee or proof of value is required to add an entry.

### Likelihood Explanation
The barrier to triggering this is very low: it only requires being a paired correspondent device (a routine, low-privilege relationship, not requiring trust of unit validity) or being on the private-payment path as a counterparty. No fee, no valid unit, and no cryptographic proof of a real transaction is required at insertion time — only shallow shape/format checks. The purge logic runs infrequently (5-minute interval after coming online, 1-day age threshold) and is easily outpaced by an attacker sending messages faster than that.

### Recommendation
- Rate-limit and cap the number of `unhandled_private_payments` rows accepted per correspondent/device address and enforce a maximum total table size.
- Require stronger validation before persisting (e.g., verify signatures/limits on payload size, bound `arrPrivateElements` length and per-element input/output counts) before writing to the database, or persist to a small bounded in-memory queue instead of straight to disk.
- Reduce the cleanup interval/age threshold for full nodes and add an equivalent proactive cleanup path for light clients that doesn't depend on `comeOnline()` timing.
- Consider requiring proof that the referenced `unit` was actually broadcast to a peer/hub (e.g., existence in `unhandled_joints`/`dependencies`) before accepting the private-payment placeholder row.

### Proof of Concept
1. Pair a device with the victim wallet (or act as an in-protocol private-payment counterparty).
2. Repeatedly send `private_payments` device messages (`wallet.js` `handlePrivatePaymentChains`) where each chain's head element has:
   - a syntactically valid but never-broadcast `unit` (random 44-char base64 string),
   - a large `payload.inputs`/`payload.outputs` array to inflate JSON size,
   - a fresh `message_index`/`output_index` each time to avoid the `INSERT IGNORE` de-duplication.
3. Each message causes an unconditional `INSERT INTO unhandled_private_payments` in `network.handleOnlinePrivatePayment()` (network.js:2393-2395) before the referenced unit is ever verified to exist.
4. Repeat at high frequency; because the referenced units never arrive, the rows survive until the daily cleanup sweep, causing the table (and the JSON blobs it stores) to grow unbounded, consuming disk/database resources on the victim node.

function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))

		// we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device.

function requestUnfinishedPastUnitsOfPrivateChains(arrChains, onDone){
	mutex.lock(["private_chains"], function(unlock){
		function finish(){
			unlock();
			if (onDone)
				onDone();
		}
		privatePayment.findUnfinishedPastUnitsOfPrivateChains(arrChains, true, function(arrUnits){
			if (arrUnits.length === 0)
				return finish();
			breadcrumbs.add(arrUnits.length+" unfinished past units of private chains");
			requestHistoryFor(arrUnits, [], err => {
				if (err) {
					console.log(`error getting history for unfinished units of private payments`, err);
					return finish();
				}
				// get units that are still new or unstable after refreshing the history
				storage.filterNewOrUnstableUnits(arrUnits, async arrMissingUnits => {
					if (arrMissingUnits.length === 0) return finish();
					console.log(`will delete unhandled private payments whose units are not known after 1 day`, arrMissingUnits);
					await db.query(`DELETE FROM unhandled_private_payments WHERE unit IN(${arrMissingUnits.map(db.escape).join(', ')}) AND creation_date < ${db.addTime('-1 DAY')}`);
					finish();
				});
			});
		});
	});
}
