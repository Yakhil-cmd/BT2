### Title
Hookify PreToolUse/Stop hooks fail open (silently allow) on any rule-evaluation error, defeating configured `block` rules - (File: plugins/hookify/hooks/pretooluse.py, plugins/hookify/hooks/stop.py)

### Summary
The hookify plugin's hook executors (`pretooluse.py`, `stop.py`, `posttooluse.py`, `userpromptsubmit.py`) wrap the entire rule-loading and rule-evaluation pipeline in a single blanket `try/except Exception`, and in every branch — success, caught exception, or `finally` — they unconditionally `sys.exit(0)`. This mirrors the ERC20 bug class: a safety-critical operation (here, the `block` decision meant to deny a dangerous Bash/Edit/Write operation or halt a Stop event) can silently fail-open instead of enforcing the intended denial, exactly as an unchecked ERC20 `transfer`/`transferFrom` can silently fail instead of reverting.

### Finding Description
`pretooluse.py` is the enforcement point for hookify's `action: block` rules, which are documented as blocking dangerous Bash commands (e.g. `rm -rf`, `chmod 777`) or sensitive file writes [1](#0-0) . Its `main()` catches `RuleEngine.evaluate_rules()` and `load_rules()` in one broad `except Exception`, and regardless of outcome, the `finally` block always calls `sys.exit(0)`, explicitly commented "ALWAYS exit 0 - never block operations due to hook errors" [2](#0-1) . On any exception during evaluation, the except handler discards the actual rule decision and returns only a `systemMessage`, which carries no `permissionDecision: deny` — this is functionally identical to allowing the tool call [3](#0-2) .

While `load_rules()`/`load_rule_file()` in `config_loader.py` do catch and skip per-file parsing errors so a single malformed rule doesn't crash the whole loader [4](#0-3) , the `RuleEngine.evaluate_rules()`/`_rule_matches()`/`_check_condition()` call chain in `rule_engine.py` has no such per-condition exception isolation outside of `_regex_match`'s narrow `re.error` catch [5](#0-4) . Any other exception raised while evaluating a condition (e.g., a `KeyError`/`TypeError` from an unexpected `tool_input` shape, or `glob.glob` raising on an unreadable `.claude` directory) propagates up to the hook's outer `except Exception`, which converts what should be a `deny` into a plain informational message and exits 0 — silently allowing the operation exactly the rule was configured to block.

### Impact Explanation
Users who configure hookify `block` rules to prevent destructive or sensitive operations (per the plugin's own documented use cases: blocking `rm -rf`, `chmod 777`, writes to `.env`/credential files) get a false sense of enforcement. Any transient or edge-case error in the evaluation pipeline (malformed `tool_input`, an unusual condition field, an environment issue reading `.claude/`) causes the intended `block` decision to be silently downgraded to allow, and the tool call proceeds without any explicit warning that enforcement was bypassed (only a generic `systemMessage`, easily missed) — an unprivileged-user analog to the ERC20 bug's "issue project tokens even though the incoming transfer failed": the downstream effect (tool execution) proceeds even though the guarding check failed.

### Likelihood Explanation
Likelihood is moderate: the failure requires an exception in `evaluate_rules`/`_rule_matches` that is not one of the already-handled per-file parsing errors. Because `_check_condition`/`_rule_matches` access `input_data`/`tool_input` fields without defensive type/key validation, any hook payload shape mismatch (e.g., a tool_input field expected to be a string arriving as a dict/list, or a custom `field:` in a `conditions:` entry referencing a nonexistent nested key) is a realistic trigger, and the design explicitly optimizes for "never block operations due to hook errors" rather than failing closed.

### Recommendation
Apply the "safe transfer helper" analog here: make the enforcement path fail closed, not open, for `block`-type rules. Concretely: (1) narrow the outer `except Exception` in `pretooluse.py`/`stop.py` so it does not swallow errors raised while evaluating rules whose `action == 'block'`; on such errors, return a hard `permissionDecision: deny` (or `decision: block` for Stop) with a clear "hookify evaluation error — denying by default" message rather than defaulting to allow; (2) add defensive type checks in `RuleEngine._check_condition` for each accessed field before comparison, so malformed `tool_input` shapes raise a caught, logged, but fail-closed condition rather than an uncaught exception; (3) keep `warn`-only rules fail-open (as today) since they carry no security guarantee, but treat `block` rules as security-critical and fail-closed.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md` with a `block` rule matching Bash commands, e.g. pattern `rm\s+-rf` on `event: bash`.
2. Trigger a `PreToolUse` Bash call whose `tool_input` is shaped so that `_check_condition` (in `rule_engine.py`) raises an unhandled exception when reading the configured `field` — e.g., a condition with `field: command.nested` referencing a key path that doesn't exist as a plain string in `tool_input`, causing a `TypeError`/`KeyError` inside `_rule_matches`/`_check_condition` (not caught by the narrow `re.error` handler in `_regex_match`).
3. Observe that `pretooluse.py`'s outer `except Exception` catches this, logs only `{"systemMessage": "Hookify error: ..."}` with no `permissionDecision: deny`, and the process exits 0 via the `finally` block [2](#0-1) .
4. Confirm the dangerous `rm -rf` Bash command that the `block` rule was meant to deny is allowed to execute — the guard fails open instead of denying, matching the ERC20 report's "silent failure instead of the expected revert/deny" bug class.
