## Title
Webhook signature verification uses the payload's `repository.owner.login`, while the handler resolves the target repository from the payload's `repository.full_name` — the two fields are never cross-checked, letting a valid signer for one GitHub organization act on stacks belonging to a different organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC against based on `repository_owner`, which is read straight out of the untrusted JSON body: `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

Once the HMAC check passes, the actual work is dispatched to handlers (`PushHandler`, `StatusHandler`, etc.) that resolve the target `Stack`/`Commit` using a *different* field of the same payload: `repository.full_name`, via `Repository.from_github_repo_name`. [3](#0-2) [4](#0-3) 

Nothing in the controller or in `Handler` verifies that `repository.owner.login` (used to pick the signing secret) matches the owner segment of `repository.full_name` (used to find the actual stack/commit that gets mutated).

### Finding Description
Shipit supports multiple GitHub Apps/organizations configured simultaneously, each with its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml`, `OrgOne` / `OrgTwo`). [5](#0-4)  `Shipit.github(organization: repository_owner)` fetches the app/secret configured for whatever organization name appears in `repository.owner.login` (or `organization.login`) of the incoming JSON body. [6](#0-5) 

The equality that should hold is:
`organization whose secret authenticated the delivery == owner of the repository that PushHandler/StatusHandler act on`

Because both values are attacker-controlled fields inside the same JSON body, and only the first one is bound to the signature check, an attacker who is a legitimate GitHub App installation owner for `OrgTwo` (and therefore knows/can trigger deliveries signed with `OrgTwo`'s `webhook_secret`) can send a webhook whose `repository.owner.login` is `"OrgTwo"` (so `verify_signature` picks `OrgTwo`'s secret and the HMAC passes) but whose `repository.full_name` is `"OrgOne/victim-repo"`. `PushHandler` then looks up `Repository.from_github_repo_name("OrgOne/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on stacks that belong to `OrgOne`, or `StatusHandler` sets an arbitrary CI status (`state`, `context`, `sha`) on any `Commit` matching the forged `sha`, regardless of which organization actually owns it. [7](#0-6) [8](#0-7) 

`sync_github` (via `GithubSyncJob`) causes Shipit to fetch the tip of the branch from GitHub for the (attacker-chosen) repository/branch and register/deploy commits, and forged commit `status` webhooks can flip CI status checks (`shipit/foo` contexts) that gate merges/deploys for a completely different organization's stack. Since Shipit's core deploy/merge safety gates rely on these two webhook types, an attacker who legitimately controls one tenant/org configured in the same Shipit instance can inject falsified push/status events that are attributed to (and acted upon as) another organization's repository.

### Impact Explanation
This crosses the "authenticated organization vs. repository actually written" trust boundary called out in scope: the signature only proves the payload came from a holder of `OrgTwo`'s webhook secret, not that the payload is really about an `OrgTwo` repository. The consequence is a cross-repository/cross-organization write: fabricated push syncs and forged commit statuses land on stacks/commits belonging to a repository the attacker does not control, which can influence deploy/merge decisions (status checks gating `shipit/*` context) for that other organization. This matches the "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization/App (a documented, supported configuration — see `secrets_double_github_app.yml` and per-organization `Shipit.github(organization:)` lookups used throughout `Repository#github_app`, `GitHubApp`). Any attacker who is a legitimate webhook sender for *one* configured organization (i.e., controls a repository/App installation in that org) can immediately mount the attack with a hand-crafted payload — no repository write access, no Shipit session, and no secrets beyond their own org's webhook secret are needed. This is a straightforward, deterministic exploit given multi-org deployment, not merely theoretical.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), require that the owner segment of `repository.full_name` matches `repository.owner.login`/`organization.login` used to select the verifying secret, and reject (422) any payload where they diverge before dispatching to handlers. Additionally, `Repository.from_github_repo_name`/`Handler#stacks` should cross-check that the resolved `Repository#owner` corresponds to the organization that produced a valid signature for this specific request.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own GitHub App and `webhook_secret` (supported configuration, cf. `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls a repository under `OrgTwo` with the GitHub App installed, so GitHub will deliver (or the attacker can independently HMAC-sign, since they know `OrgTwo`'s secret) a `push` webhook.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` with `OrgTwo`'s known `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgTwo"`, fetches `OrgTwo`'s app, and the HMAC check passes. [1](#0-0) 
6. `PushHandler#process` resolves stacks via `payload.dig('repository', 'full_name')` = `"OrgOne/victim-repo"`, and calls `stack.sync_github` on `OrgOne`'s stack, even though the request was authenticated as belonging to `OrgTwo`. [3](#0-2) [7](#0-6)
