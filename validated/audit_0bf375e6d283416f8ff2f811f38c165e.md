### Title
Unauthorized `DepositDelegatorRewards` griefing permanently blocks vote account closure/full withdrawal - (File: programs/vote/src/vote_state/mod.rs)

### Summary
Any unprivileged transaction sender can call the `DepositDelegatorRewards` vote instruction, transferring an arbitrary (even minimal, e.g. 1 lamport) amount into any V4 vote account and incrementing that vote account's `pending_delegator_rewards` field, with no relationship to the vote account's authorized withdrawer, staker, or delegator required. This is directly analogous to the reported MochiVault griefing bug, where anyone depositing a tiny amount resets a state variable (`lastDeposit[_id]`) that blocks the legitimate owner from withdrawing. Here, the attacker-controlled `pending_delegator_rewards > 0` state permanently blocks the vote account's authorized withdrawer from closing (fully withdrawing) the account via `Withdraw`.

### Finding Description
`deposit_delegator_rewards` at `programs/vote/src/vote_state/mod.rs` (lines 940-993) only verifies that the `source_address` (the lamport sender) is a signer via `verify_authorized_signer(&source_address, signers)`, not that the caller has any relationship to the target `vote_address`. Any signer with a small amount of lamports can therefore call this instruction against any validator's vote account to set `pending_delegator_rewards` to a nonzero value.

Subsequently, `withdraw()` (lines 1067-1134) enforces:
- If the withdrawer attempts to fully withdraw/close the account (`remaining_balance == 0`), the withdrawal is rejected with `InstructionError::InsufficientFunds` whenever `pending_delegator_rewards > 0` (lines 1090-1097).
- Even for partial withdrawals, the minimum retained balance is raised by `pending_delegator_rewards` (lines 1117-1126), reducing the amount withdrawable.

Since an attacker can repeat this deposit (analogous to the "deposit a tiny amount every N minutes" pattern in the original report) at negligible cost, and there is no cooldown/expiry/authorization tying the deposit to the account's own operator, the withdrawer's ability to fully close/withdraw the vote account can be blocked indefinitely by a completely unrelated, unprivileged party.

### Impact Explanation
This is a griefing/denial-of-funds-access vulnerability: the legitimate authorized withdrawer of a vote account can be permanently prevented from closing their vote account and reclaiming the full balance, because an attacker can always ensure `pending_delegator_rewards > 0` right before (or after) any withdrawal attempt for the cost of one lamport transfer plus fees. This does not directly steal funds but denies the account owner control over their own funds/account lifecycle, which is a legitimate protocol-level fund-access-blocking impact.

### Likelihood Explanation
High. The instruction is reachable by any signer with minimal lamports, requires no special authority, and the griefing cost (1 lamport + transaction fee) is far lower than the value being locked. It can be repeated indefinitely and is not rate-limited by delay logic (unlike the MochiVault case) — there isn't even a cooldown window to exploit; the mere existence of `pending_delegator_rewards > 0` at withdrawal time is sufficient to block full withdrawal.

### Recommendation
Restrict `DepositDelegatorRewards` so that lamport deposits/`pending_delegator_rewards` increments can only originate from an authorized source (e.g., the stake/rewards distribution mechanism or accounts with a delegation relationship to the vote account), or decouple the full-withdrawal-blocking check from an amount that can be trivially manipulated by third parties — e.g., allow the authorized withdrawer to withdraw the vote account balance net of `pending_delegator_rewards` while still permitting account closure, or require the withdrawer to first sweep/distribute `pending_delegator_rewards` themselves rather than being blocked outright.

### Proof of Concept
1. Attacker A creates a system account with 1 lamport of spare balance.
2. Attacker A submits a `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` instruction targeting victim's vote account `V`, signed only by A's own source account (`vote_state::deposit_delegator_rewards`, `programs/vote/src/vote_state/mod.rs:940-993`). This succeeds since only `source_address` must sign.
3. `V`'s `pending_delegator_rewards` becomes `>= 1`.
4. Victim (authorized withdrawer of `V`) submits `Withdraw(<full balance>)` to close the account; it fails with `InstructionError::InsufficientFunds` due to the check at lines 1090-1097.
5. Attacker repeats step 2 whenever needed (or simply never lets `pending_delegator_rewards` reach zero), permanently denying the victim's ability to close/fully withdraw the vote account.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
