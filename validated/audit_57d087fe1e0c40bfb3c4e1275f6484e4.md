### Title
Unchecked null dereference on `storage.assocStableUnits[trigger.unit]` in AA trigger processing can crash the node - (File: aa_composer.js)

### Summary
`handleTrigger()` in `aa_composer.js` directly dereferences `storage.assocStableUnits[trigger.unit].count_aa_responses` without checking whether the cache entry exists, mirroring the Gogs GHSA-cr88-6mqm-4g57 pattern where a lookup that can legitimately return "not found" is dereferenced as if it always succeeds, crashing the process.

### Finding Description
In `aa_composer.js`, when a primary AA trigger is executed, the double-trigger guard is: [1](#0-0) 

```
// skip this check for dry-run which uses genesis unit as trigger unit
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
```

This assumes `storage.assocStableUnits[trigger.unit]` is always a populated object. Contrast this with the same file's other access to the same map, only a few hundred lines later, which explicitly guards against the entry being missing and only then throws a controlled error: [2](#0-1) 

```
conn.query("DELETE FROM aa_triggers WHERE mci=? AND unit=? AND address=?", [mci, unit, address], async function(){
    await conn.query("UPDATE units SET count_aa_responses=IFNULL(count_aa_responses, 0)+? WHERE unit=?", [arrResponses.length, unit]);
    let objUnitProps = storage.assocStableUnits[unit];
    if (!objUnitProps)
        throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
```

The `assocStableUnits` cache entry for a stabilized unit is not permanent: `shrinkCache()` in `storage.js` periodically deletes entries for units whose `main_chain_index` is older than `top_mci` (a function of `min_retrievable_mci` and `last_stable_mci`), running every 300 seconds: [3](#0-2) 

AA triggers, however, are processed from the `aa_triggers` table by `handleAATriggers()`, sequentially, under a mutex, and can be delayed by backlog: [4](#0-3) 

If trigger processing for a particular `unit` lags long enough (e.g., a large backlog of queued AA triggers built up by an unprivileged unit poster who sends many payments to AA addresses), `shrinkCache()` can evict the `assocStableUnits[trigger.unit]` entry for that unit's `main_chain_index` before `handleTrigger()` runs the guard at line 1861. At that point `storage.assocStableUnits[trigger.unit]` is `undefined`, and `.count_aa_responses` throws a `TypeError: Cannot read properties of undefined`. Because this occurs deep inside an asynchronous callback chain (inside `updateInitialAABalances`'s callback, inside `handleTrigger`), there is no enclosing try/catch, so the exception becomes an uncaught exception that crashes the Node.js process for every full node executing the trigger — this is precisely the "if err != nil, m is always nil" class of bug from the report: a lookup path that can return "not found" is dereferenced without a guard, on a path reachable by any unprivileged unit poster.

### Impact Explanation
An uncaught `TypeError` inside AA-trigger handling crashes the running `ocore` node process. Because AA-trigger processing runs under a global write mutex (`aa_triggers`) and touches the shared `batch`/`conn` for that MCI, a crash mid-trigger can also leave the DB transaction/kvstore batch inconsistent, jeopardizing the node's ability to process/confirm subsequent units after restart. This matches the "node unable to confirm new units" / node crash impact bar described in the task.

### Likelihood Explanation
Reaching this code path requires only posting ordinary payment units to an existing AA address — no special privileges. Triggering the race (cache eviction happening before the delayed trigger is processed) requires the attacker to induce a sufficiently large backlog of unprocessed AA triggers relative to the depth guarded by `min_retrievable_mci`/`COUNT_MC_BALLS_FOR_PAID_WITNESSING`, which is achievable by an unprivileged attacker flooding many payments to many AA addresses across many main-chain indices in a short time (analogous to the "spam mirror-sync" loop in the original PoC that widened the TOCTOU race window). This is a timing/backlog-dependent bug, so likelihood is moderate rather than trivial, but does not require any privileged position.

### Recommendation
Add a defensive null check before dereferencing the cache entry at aa_composer.js:1861, e.g.:
```js
var objTriggerUnitProps = storage.assocStableUnits[trigger.unit];
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && objTriggerUnitProps && objTriggerUnitProps.count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
```
If the cache entry is missing, fall back to reading `count_aa_responses` from persistent storage (`storage.readUnitProps`) rather than assuming zero or throwing, to preserve the double-trigger protection without crashing the process. Additionally, consider excluding units that still have pending `aa_triggers` rows from `shrinkCache()`'s eviction criteria so the invariant "a queued trigger's unit stays cached until processed" is actually enforced.

### Proof of Concept
1. Attacker repeatedly posts payment units from many addresses to one or more AA addresses across a wide range of main-chain indices, causing many rows to accumulate in the `aa_triggers` table faster than `handleAATriggers()` (a serialized, mutex-guarded loop) can drain them.
2. As the main chain advances, `updateMinRetrievableMciAfterStabilizingMci` / periodic `shrinkCache()` (runs every 300s) computes `top_mci` and deletes `storage.assocStableUnits[unit]` entries for units whose `main_chain_index` is older than that threshold — this can include units whose triggers are still queued if the queue is sufficiently backlogged.
3. When `handleAATriggers()` eventually reaches the delayed trigger and calls `handleTrigger()`, execution reaches:
   `storage.assocStableUnits[trigger.unit].count_aa_responses` — since the entry was evicted, `storage.assocStableUnits[trigger.unit]` is `undefined`, and the property access throws an uncaught `TypeError`, crashing the node process.

Note: I was not able to fully trace every code path that populates `assocStableUnits` for every unit at stabilization time (only its eviction via `shrinkCache` and one insertion site were directly located in this pass), so the exact minimum backlog/timing needed to trigger the eviction race could not be precisely quantified from the indexed code alone; a Devin session with full repository access would be needed to confirm the exact timing window and whether any other code path re-populates the cache entry before `handleTrigger` runs.
