### Title
Frontmatter list/dict parser silently drops `pattern`/other fields on adversarial indentation, corrupting `Condition` into always-match or never-match, breaking hookify rule enforcement - (File: plugins/hookify/core/config_loader.py)

### Summary
The hand-rolled YAML-like parser in `extract_frontmatter` uses a hard-coded `indent > 2` check to recognize dict-item continuation lines inside a `conditions:` list. Continuation lines indented at exactly 2 spaces (a perfectly ordinary YAML style) match none of the parser's branches and are silently discarded, and continuation lines at indent 0 are worse — they are misinterpreted as new top-level keys, prematurely closing the `conditions` list with an incomplete dict. Both cases yield a `Condition` whose `pattern` (and/or `operator`) is empty, which downstream in `RuleEngine._check_condition`/`_regex_match` behaves as an unconditional match (or, for `equals`/`not_contains`, an unconditional non-match).

### Finding Description
`extract_frontmatter` (plugins/hookify/core/config_loader.py, lines 106-195) implements a minimal state machine with `in_list`/`in_dict_item`/`current_dict`. For a list item beginning with `-` it enters `in_dict_item` mode and expects subsequent fields of the same dict on lines whose leading-whitespace count satisfies `indent > 2`: [1](#0-0) 

Two adversarial indentation cases break this:

1. **Continuation at indent == 2.** Given
```
conditions:
- field: command
  operator: equals
  pattern: rm -rf
```
the `- field: command` line (indent 0) is correctly parsed via the list-item branch and sets `in_dict_item=True`, `current_dict={'field': 'command'}` (lines 173-177). The next two lines have `indent == 2`, so they fail every `elif`: not `indent == 0`, not `startswith('-')`, and not `indent > 2`. There is no `else` clause, so the lines are silently skipped — `operator` and `pattern` are never merged into `current_dict`, and the final dict appended is just `{'field': 'command'}`.

2. **Continuation at indent == 0 (worse).** If a continuation line has *no* leading indentation (e.g. a `pattern:` line accidentally left unindented), it is caught by the top-level-key branch at line 125 (`indent == 0 and ':' in line and not line.strip().startswith('-')`). That branch first flushes the in-progress `current_dict` into `current_list` and closes `frontmatter['conditions']` (lines 127-134), then treats the line as a brand-new top-level `frontmatter['pattern'] = value`, discarding it from the condition entirely.

In both cases the resulting dict passed to `Condition.from_dict` (lines 22-29) is missing `pattern` (or `operator`), so `data.get('pattern', '')` yields `''`.

That empty pattern reaches `RuleEngine._check_condition` (plugins/hookify/core/rule_engine.py, lines 144-180): [2](#0-1) 
For `regex_match`, `contains`, `starts_with`, `ends_with`, an empty pattern always matches (`re.search('', text)`, `'' in text`, `text.startswith('')`, `text.endswith('')` are all always-true). For `equals`/`not_contains`, an empty pattern almost always fails to match. Since `_rule_matches` (lines 96-125) requires **all** conditions to match, this single corrupted field flips the whole rule to either "matches every tool call" or "never matches."

No warning or exception is raised anywhere in this path — the corruption is completely silent; `load_rule_file`/`load_rules` (lines 244-265, 198-241) only catch I/O and structural exceptions, not semantic data loss.

### Impact Explanation
This directly violates the intended "deny means deny" invariant for hookify rules:
- If a `block`-action rule's condition pattern is dropped and the surviving operator is `regex_match`/`contains`/`starts_with`/`ends_with`, the rule becomes an unconditional match for its `event` scope (e.g. every `Bash` command, every file edit). Combined with `RuleEngine.evaluate_rules`'s blocking path (plugins/hookify/core/rule_engine.py, lines 60-79), this causes every matching tool call to be denied — a denial-of-service against all legitimate operations of that event type until the file is fixed/removed.
- If the surviving operator is `equals`/`not_contains` (or the intended security-relevant condition simply loses its discriminating pattern), the rule silently becomes inert — a security/警告 rule intended to block dangerous commands (e.g. `rm -rf`, secrets exposure) never fires again, defeating its protective purpose without any error being surfaced to the user.
- Because rule `message` bodies are injected verbatim into Claude's `systemMessage`/block `reason` on every match (plugins/hookify/core/rule_engine.py, lines 62-70, 88-91), an always-matching corrupted rule also means attacker-authored message text gets surfaced on every single tool call — amplifying any prompt-injection content in the rule body far beyond its intended narrow trigger.

### Likelihood Explanation
The only precondition is that a `.claude/hookify.*.local.md` file with a `conditions:` list uses 2-space (or 0-space) continuation indentation for dict fields under a list item — a natural and common YAML authoring style, not an obscure or contrived one. Such a file reaching the repository (e.g., via an ordinary PR, since these `.local.md` files are only "recommended" to be gitignored, not enforced) is sufficient; no special privileges, keys, or social engineering are required. The bug triggers deterministically and silently every time `load_rules()`/`load_rule_file()` parses the file, on every tool invocation the hook scripts run.

### Recommendation
Rewrite `extract_frontmatter` to track the indentation of the current list item explicitly (e.g., store the indent level of the `-` marker) and treat *any* line with `indent > list_item_indent` as a continuation, regardless of exact spacing, while also detecting indentation that is `<=` the list's base indent as a definite exit from `in_dict_item` mode (rather than silently dropping or misrouting the line). At minimum, add validation after parsing (or in `Condition.from_dict`/`Rule.from_dict`) that rejects/warns on conditions with an empty `pattern`, so a corrupted rule fails loudly (and is excluded/logged) instead of silently becoming a universal match or permanent no-op. Preferably, replace this hand-rolled parser with a real YAML library (e.g., `yaml.safe_load`) to eliminate this entire class of indentation-sensitivity bugs.

### Proof of Concept
Unit test to add near `plugins/hookify/core/config_loader.py` tests:
```python
def test_extract_frontmatter_drops_pattern_on_2space_indent():
    content = """---
name: block-rm
enabled: true
event: bash
action: block
conditions:
- field: command
  operator: equals
  pattern: rm -rf
---
Blocked!
"""
    frontmatter, _ = extract_frontmatter(content)
    conditions = frontmatter.get('conditions', [])
    assert conditions, "conditions list should be populated"
    cond = Condition.from_dict(conditions[0])
    # BUG: pattern/operator silently dropped -> empty pattern
    assert cond.pattern != '', f"pattern was corrupted to empty string: {cond}"

def test_extract_frontmatter_unindented_continuation_misparsed():
    content = """---
name: block-rm
enabled: true
event: bash
action: block
conditions:
  - field: command
    operator: equals
pattern: rm -rf
---
Blocked!
"""
    frontmatter, _ = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, "Blocked!")
    # BUG: legacy 'pattern' is silently discarded because conditions is non-empty,
    # and the condition itself never received the pattern value.
    assert all(c.pattern for c in rule.conditions), rule.conditions
```
Both assertions fail against the current implementation, demonstrating that `Condition.pattern` ends up `''` even though the source file specified a non-empty pattern. A fuzz-test variant should randomize indentation (0, 1, 2, 3, 4 spaces) for continuation lines across many generated `conditions:` blocks and assert `Condition.pattern` is always non-empty whenever the source YAML-like text specifies a non-empty `pattern:` value for that item.
