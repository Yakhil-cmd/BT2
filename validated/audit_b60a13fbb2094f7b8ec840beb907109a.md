### Title
Stale `signer-rewards-per-token-for-cycle` snapshot lets new stakers claim sBTC rewards accrued before they staked - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`settle-rewards` only advances the per-signer reward-per-token accumulator `signer-rewards-per-token-for-cycle` when the signer's own `shares > 0` at that moment, but a staker's reward baseline is always snapshotted from that same (possibly stale) map when they join. When a signer regains nonzero shares later, the accumulator jumps directly to the current global value, retroactively crediting newly-joined stakers for reward growth that occurred while the signer had zero shares.

### Finding Description
The claimed equality is: `sBTC paid to a new staker for (signer, staker, cycle) == rewards accrued only during the staker's actual staked window`. This equality is broken by the interaction of two functions:

1. `settle-rewards` conditionally updates the per-signer accumulator only if the signer currently has nonzero shares: [1](#0-0) 
Meanwhile, in the same function, `signer-rewards-per-token-settled-for-cycle` (used for the signer's *own* aggregate earned) is updated unconditionally: [2](#0-1) 
This means the signer's own earned total correctly reflects zero accrual while `shares == 0`, but the shared per-token key handed down to stakers (`signer-rewards-per-token-for-cycle`) is frozen instead of tracking the global accumulator.

2. When a staker is (re)added to a signer's STX-only pool, `settle-rewards` is invoked with the pre-update (possibly zero) shares, and the staker's baseline `staker-rewards-per-token-settled-for-cycle` is then set to whatever `signer-rewards-per-token-for-cycle` currently holds — the stale value, not the true global `rewards-per-token-for-cycle`: [3](#0-2) [4](#0-3) 
The equivalent bond path does the same at: [5](#0-4) 

3. Later, when the signer's shares become nonzero again (from this new staker or any other), `settle-rewards`'s guard finally passes and jumps `signer-rewards-per-token-for-cycle` straight to the current global value (which may have grown from *other* signers' activity while this signer had zero shares). At the next `claim-staker-rewards-for-signer` → `settle-staker-rewards`, the earned calculation uses this jumped value against the new staker's baseline (frozen at the old value): [6](#0-5) [7](#0-6) 

The result: `earned = new-staker-shares * (rpt-jumped - rpt-stale) / PRECISION`, which includes reward growth that occurred while the signer had zero shares (i.e., growth the signer itself never earned, per its own correctly-zero-gated aggregate accounting) and/or growth that occurred before the staker joined. None of the existing guards (`validate-no-reentrancy`, `verify-not-prepare-phase`, `check-pox-lock-period`, `<=` comparisons, `parse_pox_stake_result`) address this accounting divergence — they guard unrelated invariants (reentrancy, cycle-phase, lock periods).

### Impact Explanation
A staker who joins a signer during (or right after) a period where that signer had zero locally-staked shares is credited sBTC rewards that were never actually earned by the signer for that gap (the signer's own `signer-unclaimed-rewards-for-cycle` total, computed via the unconditionally-updated `signer-rewards-per-token-settled-for-cycle`, does not contain a matching amount). This is a theft of sBTC — value is paid out of the shared reward pool/reserve to a staker who did not commit STX during the accrual window, i.e., a reward interval is effectively double-counted (once implicitly excluded from the signer's own pot, once explicitly paid to the new staker). This matches the Critical category: "theft of ... sBTC rewards ... double-counting a commitment or reward." It is repeatable across every cycle and every signer that experiences a zero-then-nonzero shares transition, which is a routine, non-privileged occurrence (e.g., the normal start of a new reward cycle before any STX-only staker has joined a given signer).

### Likelihood Explanation
Preconditions are ordinary, not exotic: a signer simply needs to have zero STX-only-staked shares at some point in a cycle (the default/starting state for any signer before its first STX-only staker arrives, or after all such stakers temporarily leave) and then gain a staker later in the same cycle. No privileged role is required — any account can become that "new staker" via the normal `stake`/`stake-update` (`add-staker-to-signer-for-cycle`) or bond-registration (`add-staker-to-bond-for-cycle`) flow, and any signer routinely calls `claim-rewards`/`update-claimable-rewards`, which invokes `settle-rewards` and can trigger the retroactive jump. The attacker's cost is simply staking normally; the exploit requires no special transaction ordering beyond staking into a signer whose local accumulator is currently behind the global one.

### Recommendation
Remove the `if (> shares u0)` gating in `settle-rewards` for `signer-rewards-per-token-for-cycle`, and instead always advance it to the current global `rewards-per-token-for-cycle` (mirroring `signer-rewards-per-token-settled-for-cycle`'s unconditional update), OR compute an independently-accrued local delta while shares are zero. Any staker's baseline must be initialized to a value guaranteeing zero earned for reward growth that happened before they had nonzero shares — this requires the local accumulator to never "skip" global growth while frozen.

### Proof of Concept
Clarity/TS integration test plan (extending the existing `contrib/core-contract-tests/tests/pox-5/pox-5.test.ts` harness):
1. Register a signer with zero STX-only stakers for reward cycle N.
2. Fund the contract with sBTC and call `calculate-rewards` to grow the global `rewards-per-token-for-cycle` for cycle N (assert `get-rewards-per-token-for-cycle(N, none) > 0`).
3. Have the signer call `claim-rewards([], N)` while it still has zero STX-only shares; assert `get-signer-rewards-per-token-for-cycle(signer, N, none)` stays at its pre-call (stale, e.g. `0`) value even though the global accumulator is nonzero.
4. Stake a new staker (attacker) with this signer via `stake`/`stake-update` in the same cycle; assert `get-staker-rewards-per-token-settled-for-cycle(signer, N, none, attacker)` equals the stale value from step 3, not the current global value.
5. Call `calculate-rewards` again (further accruing rewards from other signers/stakers), then trigger another `settle-rewards` for this signer with nonzero shares (e.g., via another `stake` or `claim-rewards`); assert `get-signer-rewards-per-token-for-cycle` jumps to the current global rpt.
6. Call `claim-staker-rewards-for-signer` for the attacker and assert `get-earned-staker-rewards(signer, N, none, attacker) > attacker-shares * (accrual strictly after they staked) / PRECISION`, proving they were credited for pre-staking accrual — breaking the target equality.
