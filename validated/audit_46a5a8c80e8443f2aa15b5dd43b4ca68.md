### Title
Cross-organization webhook forgery via mismatched signature-selection field and repository-resolution field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-tenant Shipit deployment (the documented "Using Multiple Github Applications" configuration, `docs/setup.md`), each GitHub organization has its own webhook secret. `WebhooksController#verify_signature` selects *which* secret to verify the inbound webhook against using the `repository.owner.login` (or `organization.login`) field of the JSON payload, but every event handler that actually mutates state resolves the target repository/stack using the *different* `repository.full_name` field. Because both fields live inside the same attacker-supplied JSON body, and only the byte-stream itself (not any binding between these two fields) is HMAC-covered, a party holding the webhook secret for organization A can forge a signed payload that claims `repository.owner.login = "orgA"` (to pass signature verification with A's known secret) while setting `repository.full_name = "orgB/some-repo"` (to make the handlers act on organization B's stacks).

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp`/secret using only the owner/organization login found in the untrusted payload: [1](#0-0) [2](#0-1) 

`Shipit.github_app_config` resolves that organization key case-insensitively against the configured multi-org secrets: [3](#0-2) 

Signature verification is a pure HMAC over the raw body using the secret selected for the org named in `repository.owner.login`: [4](#0-3) 

Every dispatched handler, however, determines the repository/stack that gets written to using the *separate* `repository.full_name` field of the very same payload, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

For example, the push handler will run `stack.sync_github` against whichever stack resolves from `repository.full_name`: [7](#0-6) 

The pull-request handlers (archive/unarchive review stacks, close review stacks, update PR metadata) follow the same pattern, resolving `Shipit::Repository.from_github_repo_name(params.repository.full_name)`: [8](#0-7) [9](#0-8) 

Because these two fields (`repository.owner.login` used to pick the verifying secret, and `repository.full_name` used to pick the acted-upon repository) are never cross-checked against each other, and both are fully attacker-controlled JSON keys inside the payload they craft and sign themselves, the equality the application implicitly relies on — *"the organization whose secret authenticated this request" == "the repository the handlers write to"* — is not enforced anywhere in the request path.

### Impact Explanation
Any party that legitimately possesses one organization's webhook secret (any org onboarded onto the shared multi-tenant Shipit instance, as documented) can forge webhook deliveries that are cryptographically valid for their own org but whose `repository.full_name` names a *different* organization's repository. This allows:
- Triggering a `GithubSyncJob`/deploy pipeline update (`stack.sync_github`) for another organization's stack via a forged `push` event.
- Archiving/unarchiving another organization's review stacks via forged `pull_request` `labeled`/`unlabeled`/`closed`/`reopened` events.
- Injecting fabricated commit statuses for another organization's commits.

This is a cross-organization/cross-repository write achieved without any credential or access to the victim organization, satisfying the "cross-repository writes" / "unauthorized deploy or rollback" critical-impact bar.

### Likelihood Explanation
This requires the attacker to control at least one organization's webhook secret in a multi-org Shipit deployment — a configuration explicitly documented and supported (`docs/setup.md`, "Using Multiple Github Applications"). Any such organization's operator/administrator (an "unprivileged attacker" with respect to any *other* tenant organization on the same Shipit instance) can exploit this simply by POSTing a crafted JSON body with a correctly computed `X-Hub-Signature` to the public `/webhooks` endpoint — no GitHub App installation on the victim org, no Shipit session, and no API token are needed.

### Recommendation
Bind the repository/organization actually acted upon to the same field used for secret selection. Concretely, `WebhooksController#verify_signature`/handlers should derive both the verifying secret and the acted-upon repository from the same trusted value (e.g. always resolve `repository.full_name` first, derive the owner segment from it, and use that exact derived owner for `Shipit.github(organization:)`), or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Deploy Shipit in multi-org mode with `orgA` and `orgB` configured, each with its own `webhook_secret` (per `docs/setup.md`).
2. As an operator who legitimately knows `orgA`'s webhook secret, craft a payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "full_name": "orgB/victim-repo",
    "owner": { "login": "orgA" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"orgA"`, fetches `orgA`'s `GitHubApp`, and the signature validates successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")`, which belongs to `orgB`, and triggers `stack.sync_github` on `orgB`'s stack — despite the request only ever having been signed with `orgA`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
