### Title
Webhook signature is verified against an organization chosen from unauthenticated payload data, decoupled from the repository actually mutated - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to use for HMAC verification from fields inside the still-unverified JSON body itself. The event handlers that subsequently execute the write (e.g. `PushHandler`, `StatusHandler`, etc.) pick the target repository/stack from a *different* field of that same unverified body. Because Shipit supports multiple independently configured GitHub organizations (each with its own `webhook_secret`), an attacker who legitimately controls one configured organization's app secret can forge a payload whose "signing organization" field points to their own org (so the signature check passes) while the "target repository" field points to a completely different, victim organization's repository. This is directly analogous to the reported bug class: a value ("USDC == USD") is trusted/assumed equal to another value without being itself verified by the cryptographic check that is meant to authorize the whole operation.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-supplied JSON, before any signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both are plain fields of the untrusted `request.raw_post` JSON, read before `verify_webhook_signature` runs. The chosen `Shipit.github(organization: repository_owner)` selects the app config (and therefore the `webhook_secret`) used to HMAC-verify the body: [3](#0-2) 

Crucially, the HMAC only proves "this body was signed with organization X's secret" — it does not bind that organization to any other field inside the same body. Once `verify_signature` passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs, and every handler resolves its *actual* target repository from a separate field, `repository.full_name`: [4](#0-3) [5](#0-4) 

Nothing forces `repository.owner.login`/`organization.login` (used to pick the verifying secret) to correspond to `repository.full_name` (used to pick the stack/repository that is mutated). GitHub itself always produces payloads where both are consistent, but an attacker crafting the raw HTTP request directly is not constrained by that — they only need to know one configured organization's `webhook_secret` (e.g., because they are the legitimate GitHub App owner/admin for that one, smaller organization onboarded onto the shared Shipit instance) to sign an arbitrary JSON body, including one whose `repository.full_name` names a stack belonging to an unrelated organization.

This breaks the binding: *organization that authenticated the webhook* ⇔ *repository that is written to by the handler*. The equality the code implicitly (and wrongly) assumes is:
`repository_owner (used for HMAC secret selection) == owner(repository.full_name) (used for the mutation)`.

### Impact Explanation
Once signature verification passes using OrgA's secret, any registered handler runs unconstrained against whatever `repository.full_name`/stack the forged payload names:
- `push` → `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on any stack matching the forged branch/repo, letting the attacker drive `GithubSyncJob` for a stack in a repository they do not own. [6](#0-5) 
- `status`/other events can inject fabricated CI status/commit state for a foreign repository's commits, which feed into merge-queue and deploy gating logic (`MergeRequest#all_status_checks_passed?`, deploy triggers), potentially causing an unauthorized deploy/merge decision to be made on cross-organization data. [7](#0-6) 

This satisfies the "cross-repository writes / unauthorized deploy" impact bar: an attacker who is unprivileged with respect to the victim organization, but is a legitimate app owner for one other org configured on the same Shipit instance, can cause the engine to act on the victim org's stacks.

### Likelihood Explanation
Requires the attacker to control the `webhook_secret` of at least one organization configured in the multi-org `github:` section of Shipit's `secrets.yml` — this is plausible in shared/multi-tenant Shipit deployments where several independent teams/orgs each provision and configure their own GitHub App and are not otherwise trusted with each other's repositories. Given that fact, forging the raw JSON body and computing a valid HMAC with the known secret is trivial; no other credential (session, `ApiClient` token, GitHub OAuth) is needed.

### Recommendation
Do not select the verification secret from unauthenticated payload content that is also used later to select the write target. Verify the signature against the same value that will subsequently gate the write, and once a secret is chosen, refuse to act on payload fields (`repository.full_name`, `organization.login`) that don't correspond to that same organization. Concretely:
1. After selecting `webhook_secret` via `repository_owner`, additionally assert that `repository.full_name`'s owner segment equals the same `repository_owner`/organization used to verify the signature before dispatching to handlers.
2. Prefer iterating over all configured organizations' secrets and verifying against the one whose resulting authenticated identity matches the repository actually referenced, rather than trusting the payload to name its own authenticator.

### Proof of Concept
1. Shipit is configured with two organizations, `orga` (attacker-controlled GitHub App, attacker knows `webhook_secret_a`) and `orgb` (victim, has stacks tracked by Shipit).
2. Attacker builds a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "orgb/victim-repo", "owner": { "login": "orga" } }
}
```
3. Attacker computes `sha1=HMAC-SHA1(webhook_secret_a, raw_body)` and sends `POST /webhooks` with `X-Github-Event: push` and `X-Hub-Signature` set to that value.
4. `repository_owner` resolves to `"orga"`, `Shipit.github(organization: "orga")` is used, and `verify_webhook_signature` succeeds because the body was indeed HMAC'd with `orga`'s real secret. [1](#0-0) 
5. `PushHandler#process` then looks up stacks via `Repository.from_github_repo_name("orgb/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `orgb`'s stack — a write the attacker had no authorization to trigger. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
