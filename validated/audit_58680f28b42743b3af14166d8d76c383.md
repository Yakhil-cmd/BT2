### Title
Webhook signature is verified against an organization derived from an unvalidated payload field, decoupled from the repository that handlers actually act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read directly out of the *unverified* JSON body [1](#0-0) . That same body is later dispatched to event handlers which resolve the actual `Repository`/`Stack` to mutate using a *different* field of the same untrusted body, `repository.full_name` [2](#0-1) . Nothing ties these two fields together, so the organization whose secret validated the signature is not guaranteed to be the organization/repository that gets written to.

### Finding Description
`verify_signature` computes the org to authenticate against like this:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `config/secrets.yml` (the multi-org config schema explicitly supports one `webhook_secret` per organization) [4](#0-3) [5](#0-4) . The signature is a valid HMAC as long as it matches *that org's* secret — an attacker who legitimately controls (or has leaked) the `webhook_secret` for **any one** configured organization can produce a request that passes `verify_signature`, simply by setting `repository.owner.login` in the JSON body to that organization's name.

The handler layer, however, never re-checks `repository.owner.login`. It resolves the target repository purely from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Since `owner.login` and `full_name` are independent keys in the same attacker-supplied JSON body, an attacker can set `repository.owner.login = "org-they-control"` (to pass `verify_signature` with their own valid secret) while setting `repository.full_name = "victim-org/victim-repo"` (to target any stack tracked by Shipit). This breaks the intended binding: *organization authenticated* (`repository.owner.login`, checked in `verify_signature`) ≠ *repository written* (`repository.full_name`, used by every handler, e.g. `PushHandler`) [6](#0-5) .

The most impactful consequence is via the `status` event: the controller test confirms a `Status` record is created straight from the payload's `sha`/`state`/`context`/`repository` fields, again scoped only by `repository.full_name`+`sha`, not by the organization whose secret validated the request [7](#0-6) . `Stack#deployable?`/`branch_status` consult these `Status` rows to decide whether continuous delivery may proceed [8](#0-7) [9](#0-8) , and `trigger_continuous_delivery` will actually call `trigger_deploy` once checks pass [10](#0-9) .

### Impact Explanation
An attacker who only holds a valid `webhook_secret` for one configured organization (e.g. their own low-trust org installed on the same multi-tenant Shipit instance) can forge signed `status` (or `push`) webhooks that name an unrelated, victim-owned stack via `repository.full_name`. This lets them inject a fabricated "success" CI status for a commit in a stack they do not own, which — combined with `continuous_deployment` — can cause `trigger_continuous_delivery` to run an **unauthorized deploy** of that stack. This satisfies the Critical bar ("unauthorized deploy") defined by the rules, because a credential/authentication boundary (org A's webhook secret) is used to write state belonging to org B's repository.

### Likelihood Explanation
Requires the operator to run Shipit with the multi-organization GitHub App config (explicitly documented and supported) and for the attacker to control/leak one organization's `webhook_secret` while another organization's stack has `continuous_deployment` enabled with status-based checks. This is a realistic configuration for shared/multi-tenant Shipit deployments, but not the default single-org setup, so likelihood is moderate rather than trivial.

### Recommendation
In `WebhooksController#verify_signature` and in `Shipit::Webhooks::Handlers::Handler`, cross-validate that the organization whose secret verified the signature actually matches the owner segment of `repository.full_name` (or `organization.login`) used to resolve the target `Repository`/`Stack`. Reject the webhook if these disagree, rather than treating `repository.owner.login` and `repository.full_name` as independent, unrelated fields.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `attacker-org` (secret known/controlled by attacker) and `victim-org` (tracks a stack with `continuous_deployment: true`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<real sha of a commit on victim-org/victim-repo awaiting CI>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "created_at": "2026-09-02T00:00:00Z"
}
```
signed with `attacker-org`'s `webhook_secret` via `X-Hub-Signature`.
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the HMAC using the attacker's own secret [1](#0-0) .
4. `StatusHandler` (via `Handler#repository_name`) resolves the target repository as `victim-org/victim-repo` from `repository.full_name` and writes a forged passing `Status` for that commit [2](#0-1) .
5. On the victim stack's next `trigger_continuous_delivery` cycle, `deployment_checks_passed?`/`branch_status` see the forged success status and an unauthorized deploy is triggered [10](#0-9) .

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     someothergithuborg:

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
