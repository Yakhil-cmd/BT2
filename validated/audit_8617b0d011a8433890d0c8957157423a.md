### Title
Webhook signing-key selection uses `repository.owner.login`, decoupled from the `repository.full_name` actually acted upon, enabling cross-organization stack manipulation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` picks the GitHub App / `webhook_secret` used to validate the HMAC signature based solely on `repository.owner.login` (or `organization.login`) from the unauthenticated JSON body, then hands the *entire* raw payload — including an independently-controlled `repository.full_name` field — to event handlers that resolve the target `Stack`/`Repository` from that `full_name`. Nothing ties the two fields together, so a payload can be signed with one organization's secret while acting on a different organization's repository.

### Finding Description
`verify_signature` computes `repository_owner` from the request body and fetches the corresponding `Shipit.github(organization: repository_owner)` app to verify the HMAC-SHA1 signature: [1](#0-0) [2](#0-1) 

In the multi-organization configuration explicitly supported by this engine, each organization has its own separate GitHub App, `app_id`, and `webhook_secret`, all supplied by that organization's own administrator when creating the App: [3](#0-2) [4](#0-3) 

Once signature verification passes, `WebhooksController#create` dispatches the *raw* JSON body to handlers: [5](#0-4) 

Every handler resolves the target repository/stack from `payload.dig('repository', 'full_name')` — a completely different field from the one used for signature-org selection: [6](#0-5) [7](#0-6) [8](#0-7) 

There is no validation anywhere that `repository.owner.login` (the field used to choose the signing secret) matches the owner segment of `repository.full_name` (the field used to select the stack that is mutated). An organization admin who legitimately knows their own org's `webhook_secret` (they set it themselves when creating their org's GitHub App, per `docs/setup.md`) can therefore forge an HTTP POST to `/webhooks` with a valid `X-Hub-Signature` for their own org while setting `repository.full_name` to `some-other-org/some-repo`.

This directly parallels the reported bug class: a payload field (`full_name`) is acted upon by downstream logic but is never covered by — or bound to — the field the signature verification actually authenticates (`owner.login`), breaking the binding "organization that authenticated == repository that is written."

### Impact Explanation
With a forged `push` event, `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the target branch of the victim repository: [9](#0-8) 

This enqueues `GithubSyncJob`, which fetches commits and mutates `stack.commits`/deploy-spec cache for the victim's stack: [10](#0-9) 

Other handlers such as `LabeledHandler`/`OpenedHandler`/`ClosedHandler` similarly `archive!`/`unarchive!` review stacks or create/close them for the victim organization's repository, using only `params.repository.full_name`: [11](#0-10) [12](#0-11) 

This lets an attacker who controls only their own organization's GitHub App/webhook_secret (an "unprivileged" party with respect to the victim organization, no GitHub access to the victim repo, no Shipit session/token) force state changes — stack sync, review-stack archive/unarchive/provisioning — on a stack belonging to a repository/organization they do not control. Depending on downstream continuous-delivery behavior driven by synced commits (`Stack#sync_github_if_necessary`, `schedule_continuous_delivery`), this can influence undeployed-commit tracking and continuous delivery triggers for another organization's stack — a cross-repository / cross-organization state-mutation, matching the "cross-repository writes" impact bar.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured for multi-organization GitHub Apps (documented, supported feature), and (2) the attacker administers a GitHub App for some organization already installed on that Shipit instance — a materially weaker requirement than compromising the victim org, a Shipit account, or an `ApiClient` token. The `/webhooks` endpoint is public and unauthenticated aside from the per-org HMAC check, which the attacker can satisfy with their own known secret.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), require that `repository.owner.login`/`organization.login` (the field used to select the verifying `webhook_secret`) match the owner segment of `repository.full_name` (the field used to resolve the target `Repository`/`Stack`) before dispatching to handlers; reject payloads where they diverge.

### Proof of Concept
1. Configure Shipit with two organizations in multi-org mode, e.g. `victim-org` and `attacker-org`, each with its own `webhook_secret` (per `config/secrets.development.example.yml`).
2. As the admin of `attacker-org`, compute `sha1=HMAC(attacker-org's webhook_secret, body)` over a crafted body:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha the attacker wants recorded>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=...`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and verifies successfully against the attacker's own known secret [1](#0-0) .
5. `PushHandler` resolves the stack via `payload.dig('repository','full_name') == "victim-org/victim-repo"` [6](#0-5)  and enqueues `GithubSyncJob` against the victim's stack, despite the request never being signed by `victim-org`'s secret.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
