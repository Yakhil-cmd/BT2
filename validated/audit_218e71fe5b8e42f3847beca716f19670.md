### Title
Unvalidated pull request label names are injected as arbitrary environment variable keys into git subprocesses - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` builds a hash from every PR label name (uppercased) with no key allowlist and merges it into the environment used for all `git` invocations (`fetch`, `clone`, `checkout`, etc.) for that review stack, and `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook body with no format restriction. Because `Command#unbundled_env` merges this attacker-influenced `@env` last, on top of `BASE_ENV`/`PATH`, a PR author can inject any environment-variable *name* (e.g. `GIT_CONFIG_GLOBAL`) into the `git checkout` subprocess spawned by `TaskCommands#checkout`, even while the review stack is under `prevent_with_label`.

### Finding Description
The broken binding: the environment passed to `PTY.spawn` for `git checkout` should equal `Command::BASE_ENV` merged only with operator/Shipit-controlled values; instead it equals `BASE_ENV.merge(stack.env)` where `stack.env` includes `{ LABEL_NAME.upcase => "true" }` for every label on the PR, with no allowlist.

Trace:
- `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) sets `pull_request.labels` directly from `params.pull_request.labels.map(&:name)`, i.e. attacker-controlled webhook body strings (verified by the existing test that even emoji label names are accepted unmodified).
- `capture_labels?` (`label_capturing_handler.rb:51-56`) fires on `opened`, `labeled`, `unlabeled`, `reopened` for any non-archived stack — this check is independent of `provisioning_behavior`, so it still runs under `prevent_with_label`.
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into `super` with no key filtering/allowlist.
- `StackCommands#env` (`lib/shipit/stack_commands.rb:13-15`) and `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) both merge `@stack.env`, so the label-derived hash flows straight into the env used for `TaskCommands#checkout` (`lib/shipit/task_commands.rb:50-59`), `clone`, and `StackCommands#fetch`/`fetch_commit`.
- `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — `@env` (containing the label-derived keys) is merged **last**, so it overrides anything in `BASE_ENV`, and this exact hash is passed to `PTY.spawn` (`lib/shipit/command.rb:92`).

This is directly demonstrated by the existing passing tests `test/models/shipit/review_stack_test.rb:59-65` and `test/lib/shipit/task_commands_test.rb` which show label `"wip"` becomes `env["WIP"] == "true"` with no restriction on which key names are allowed — the same mechanism accepts `"GIT_CONFIG_GLOBAL"` as a label, producing `env["GIT_CONFIG_GLOBAL"] == "true"` reaching the `Command` for `git checkout`.

Important caveat I could not fully resolve: the *value* injected is always the hardcoded literal string `"true"`, not an attacker-chosen arbitrary value (only the *key* is attacker-controlled). For `GIT_CONFIG_GLOBAL=true` to cause git to load an attacker-authored config file (defining a malicious `core.fsmonitor`/`core.hooksPath` hook), git would need to resolve `true` as a relative path against the process's current working directory (`@task.working_directory`) and find a file literally named `true` there at the moment `git checkout` starts — before the same invocation replaces the tree with the target commit. Whether a file named `true` is actually present in that directory at that point depends on state (git cache default branch content, whether `deploy_spec.clear_working_directory?` causes reuse of a prior checkout of the attacker's own branch) that I was not able to conclusively verify in this trace. What is conclusively verified is the env-key injection itself; the exact RCE mechanics via `GIT_CONFIG_GLOBAL` specifically are plausible but not fully proven end-to-end here.

Existing guards do not prevent this: `verify_signature`/webhook signature checking authenticates that the webhook came from GitHub for the registered organization, but does not restrict label *content*; the attacker is assumed (per the threat model) able to legitimately label their own PR, so a genuine, correctly-signed GitHub webhook carries the malicious label name. No model validation constrains `PullRequest#labels` format, and no allowlist exists in `ReviewStack#env` or `Command#unbundled_env`.

### Impact Explanation
Confirmed impact: unauthenticated-by-repo-owner PR label names become arbitrary environment-variable *keys* (fixed value `"true"`) inherited by every `git` subprocess (`fetch`, `clone`, `checkout`) for that review stack, overriding `PATH` and any other base environment variable of the same name. This is a genuine "git subprocess inherits fork-controllable variable" violation of the stated invariant. Whether this specific mechanism escalates to full Critical RCE via `GIT_CONFIG_GLOBAL` depends on unverified working-directory state at checkout time, so I can confirm the environment-injection primitive with high confidence but cannot fully confirm the RCE chain to Critical severity without further verification of `deploy_spec.clear_working_directory?` defaults and working-directory reuse across tasks for the same review stack.

### Likelihood Explanation
Low attacker cost: open a PR on a repository with review stacks enabled, apply/attach a label whose name is a sensitive env var name (e.g. `GIT_CONFIG_GLOBAL`) to the PR (assumed to be within attacker capability per the stated threat model), which is captured on the ordinary `labeled`/`opened`/`reopened` webhook regardless of `provisioning_behavior`. Repeatable per PR, per label.

### Recommendation
Restrict `ReviewStack#env`'s label-to-env-var mapping to an explicit allowlist of safe key names (or a fixed prefix such as `SHIPIT_LABEL_`), reject/normalize label names that collide with reserved environment variable names (`GIT_*`, `PATH`, `LD_*`, `BUNDLE_*`, etc.), and ensure `Command#unbundled_env` cannot have `PATH`/`GIT_*`/other security-sensitive variables overridden by task/stack-level `env`.

### Proof of Concept
minitest plan (mirrors existing `test/models/shipit/review_stack_test.rb:59-65` pattern):
```ruby
test "#env allows a pull request label to inject GIT_CONFIG_GLOBAL" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_config_global"]

  assert_equal "true", stack.env["GIT_CONFIG_GLOBAL"]
end

test "TaskCommands#checkout inherits label-injected GIT_CONFIG_GLOBAL" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_config_global"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  command = Shipit::TaskCommands.new(task).checkout(task.until_commit)

  assert_equal "true", command.env["GIT_CONFIG_GLOBAL"]
end
```
