### Title
Missing global replay protection for L1 BTC lockup outpoints allows double-counting a single Bitcoin lockup across multiple `register-for-bond` calls - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` accepts a Bitcoin L1 lockup proof (`btc-lockup`) as an alternative to depositing sBTC, and credits the staker `sats-total` sats of backing based on that proof via `verify-l1-lockups`/`validate-l1-lockup`. The only duplicate-outpoint protection (`seen-outpoints`) is scoped to the single call's `fold`, and is never persisted anywhere, so the same Bitcoin UTXO can be presented again in a later, separate transaction to mint another `sats-total` credit without any new BTC being locked.

### Finding Description
`register-for-bond` computes `sats-total` from the caller-supplied BTC lockup proof: [1](#0-0) 

`verify-l1-lockups` folds over the outputs, building a fresh, in-memory `seen-outpoints` list that starts empty every call: [2](#0-1) 

`validate-l1-lockup` only checks the outpoint against this same call's `seen-outpoints` accumulator (`(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)`), then appends it to the temporary list that is discarded once the fold/response returns: [3](#0-2) [4](#0-3) 

There is no contract-level map that records an outpoint as "already claimed" beyond the lifetime of a single transaction. I searched `pox-5.clar` for any persistent outpoint registry (`outpoint`, `used-lockup`, `spent-outpoint`, etc.) and found none besides this transient `seen-outpoints` list. Consequently, once a `register-for-bond` call succeeds and credits `sats-total` for a given BTC outpoint (and later the staker unstakes/rolls out of that bond, or the same outpoint is submitted by a colluding second account before the first is even settled), the identical `(txid, output-index)` pair can be resupplied in a brand-new `register-for-bond` call and will again pass `validate-l1-lockup`'s checks (script/amount/merkle proof are historical facts about the Bitcoin chain and remain true forever), minting a fresh `sats-total` credit that is applied to `protocol-bonds-total-staked` and `staker-shares-staked-for-cycle`: [5](#0-4) 

This breaks the intended equality that the sats credited to the protocol's bond accounting must correspond 1:1 with sats actually locked on Bitcoin — the same locked BTC can be double- (or N-times-) counted as backing for multiple, sequential/parallel bond memberships.

Note: `validate-l1-lockup` derives `expected-script-hash` via a call to a lockup-script-construction routine keyed in part by `(get staker accumulator)`, which is bound to the calling `tx-sender`. I was not able to locate the definition of that routine (`construct-lockup-output-script`) in the indexed portion of `pox-5.clar` to confirm whether the script encoding is staker-specific in a way that would block a *different* principal from reusing the same outpoint. Regardless of that detail, the lack of any persistent replay protection means the *same* staker can resupply their own previously-used outpoint in a later `register-for-bond` call (e.g., after unstaking/rolling out of the earlier bond, or via a second parallel bond index) and receive credit again for BTC that is still locked to that one lockup output, since Bitcoin-side spending of the UTXO is never checked either.

### Impact Explanation
This allows unbacked minting of protocol-bond "sats" credit — a staker's sats-backed stake accounting (`protocol-bonds-total-staked`, `staker-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`) can be inflated using a single real BTC lockup replayed across multiple registrations, without any corresponding new Bitcoin lock. This directly falls under "sats credited by an L1 proof that were never locked on Bitcoin" / "double-counting a commitment," classified as Critical (unbacked minting of locked value) per the rules, since it lets a staker claim STX-unlock eligibility and reward-slot weight in excess of the BTC actually collateralizing the protocol.

### Likelihood Explanation
The path is reachable by any allow-listed staker (an "unprivileged account" relative to the bond admin) simply by calling the public `register-for-bond` function twice with the same BTC proof across two separate transactions/bonds (e.g., roll out of bond A, then re-register into bond B with the same lockup proof). No special privileges, miner cooperation, or additional Bitcoin transactions are required — the exploit only needs the fixed 80-byte header/merkle proof for a lockup transaction that already occurred once.

### Recommendation
Persist a global (not per-call) map keyed by `(txid, output-index)` (or the full outpoint) that records once an outpoint has been consumed by `register-for-bond`, and reject reuse (`ERR_DUPLICATE_LOCKUP_OUTPOINT`) across all past calls, not just within the current call's fold. This map should be checked and updated atomically inside `validate-l1-lockup`/`verify-l1-lockups` before any credit is applied to bond accounting.

### Proof of Concept
1. Staker A locks `N` sats to the canonical timelock P2WSH output described in `construct-lockup-output-script`.
2. Staker A calls `register-for-bond` with a proof referencing that output; `verify-l1-lockups` validates it and credits `sats-total = N` to `protocol-bonds-total-staked` for bond 0, locking STX per [5](#0-4) .
3. After the bond's rollover window opens (or once staker A unstakes), staker A calls `register-for-bond` again — for a different bond index, or after their membership ends — supplying the exact same lockup proof (same `tx`, `header`, `output-index`, `leaf-hashes`, etc.).
4. `validate-l1-lockup`'s checks (unlock height, script hash, amount, merkle proof) all pass again since they only assert historical facts about the Bitcoin chain state, and `seen-outpoints` is freshly initialized to `(list)` for this new call per [2](#0-1) , so the second registration is credited another `sats-total = N`, even though no new BTC was locked.
