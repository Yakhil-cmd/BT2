### Title
Stack-scoped ApiClient tokens bypass their stack restriction on the CCMenu API endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` enforces that a stack-scoped `ApiClient` can only touch the one stack it is bound to, by routing all stack lookups through the `stacks` scoping helper. `Api::CCMenuController` overrides the `stack` accessor and loads the stack directly from the request parameter instead, without ever consulting `current_api_client.stack_id`. This breaks the binding `stack a token authorizes == stack the request touches`.

### Finding Description
`ApiClient` has an optional `belongs_to :stack` association, and `BaseController#stacks` uses it to scope every stack lookup to just that one stack when the client is bound: [1](#0-0) 

This scoping is what test suites rely on (e.g. "an api client scoped to a stack will only see that one stack"): [2](#0-1) 

`Api::CCMenuController` inherits from `BaseController` but re-defines the private `stack` method to bypass the `stacks` scoping helper entirely, resolving the stack straight from `Stack.from_param!(params[:stack_id])`: [3](#0-2) 

`authenticate_api_client` in this controller only verifies the token's signature (`ApiClient.authenticate(params[:token])`), which only checks that the token was signed with `Shipit.api_clients_secret` and resolves to an existing `ApiClient` record — it performs no stack-membership check: [4](#0-3) 

Because `require_permission :read, :stack` only checks the client's `permissions` array (`check_permissions!`), not which stack it is allowed to see: [5](#0-4) 

the combination means: a token that is only supposed to authorize reads of stack A (because `ApiClient#stack_id == A.id`) can be replayed with an arbitrary `stack_id` parameter pointing at stack B, and `CCMenuController#show` will happily render B's deploy/lock status.

**Binding equality broken:** `stack the ApiClient.stack_id authorizes` ≠ `stack that Api::CCMenuController#show actually reads`, because the controller's local `stack` override never intersects the requested `stack_id` with the client's bound stack, unlike every other controller derived from `BaseController#stack`.

### Impact Explanation
This allows an attacker holding any valid, minimally-scoped (`read:stack`) `ApiClient` token — even one deliberately restricted by an operator to a single, non-sensitive stack — to read the deploy/lock status of any other stack in the installation via the CCMenu XML feed (`Api::CCMenuController#show`), disclosing stack name, lock status, and last build status/label/time for repositories the token holder was never meant to see. This matches the High-severity class of "unauthenticated (out-of-scope) read of stack state."

### Likelihood Explanation
Any party who legitimately possesses a stack-scoped `read:stack` token (a normal, low-privilege credential explicitly designed to be restricted to one stack — see `CCMenuUrlController`'s own creation of scoped clients) can trivially exploit this by changing the `stack_id` route/query parameter of the CCMenu endpoint. No additional privilege, session, or secret is required beyond the token itself, which is the exact credential class this control is meant to constrain.

### Recommendation
Have `Api::CCMenuController#stack` reuse the same scoping used by `BaseController#stack`/`#stacks` (i.e. `stacks.from_param!(params[:stack_id])`) instead of loading `Stack.from_param!` unscoped, so that a stack-bound `ApiClient` cannot resolve any stack other than the one it is bound to.

### Proof of Concept
1. Operator creates (or the system creates, as `CCMenuUrlController` already does) an `ApiClient` bound to `stack_id = A` with `permissions: ['read:stack']`.
2. Attacker obtains that client's `authentication_token` (e.g., it's embedded in a CCMenu URL shared with a monitoring dashboard for stack A).
3. Attacker issues `GET /api/1.0/stacks/:stack_id/ccmenu.xml` (or equivalent CCMenu route) with `stack_id` set to stack B's identifier and `token=<A's token>`.
4. `authenticate_api_client` verifies only the signature and resolves the `ApiClient` record, `require_permission :read, :stack` passes because the client does have `read:stack`, and `stack` in `CCMenuController` loads stack B directly via `Stack.from_param!`, ignoring that the client is bound to stack A.
5. The response renders stack B's `deploys_and_rollbacks.last` status, lock state, etc., which the token was never authorized to view.
