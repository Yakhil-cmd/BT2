### Title
Membership webhook mutates a `Team` without checking that the verified webhook organization matches the team's recorded owner - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id)`, whose block (which sets `team.organization`) only runs on record creation, not on find. Because nothing in the webhook pipeline checks that the currently-verified organization equals the existing `Team#organization`, a second, genuinely-signed membership event from a different org can add members to a `Team` it does not own.

### Finding Description
The broken binding is: `verify_signature`'s verified org (`Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.organization.login` for membership events, per `app/controllers/shipit/webhooks_controller.rb`) must equal `team.organization` for the `Team` record being mutated in `process`. [1](#0-0)  This is never checked.

`MembershipHandler#process` calls `find_or_create_team!`, then unconditionally calls `team.add_member(member)` or removes a member, based only on `params.action`: [2](#0-1) 

`find_or_create_team!` is: [3](#0-2)  — the `do |team| ... team.organization = params.organization.login end` block only executes on `ActiveRecord`'s `find_or_create_by!` when a *new* record is built; on a found record it is skipped entirely, so `team.organization` keeps its original value.

Exploit flow:
1. Org A's genuinely-signed membership webhook creates `Team(github_id: X, organization: 'org-a')`.
2. Attacker, who legitimately controls Org B (and can emit validly-signed webhooks for it), sends a membership `added` event with `team.id == X` and `organization.login == 'org-b'` and `member.login` set to an attacker-controlled GitHub login.
3. `verify_signature` verifies the signature against Org B's webhook secret using `repository_owner == 'org-b'` and succeeds — the request is legitimately signed.
4. `find_or_create_team!` finds the existing Team X (still `organization: 'org-a'`); the org-assignment block is skipped.
5. `team.add_member(member)` runs unconditionally, adding the attacker's user to Team X's roster — a team that Org B never owned or vouched for.

None of the existing guards catch this: `verify_signature` only confirms the request was signed by *some* org matching the payload's own `organization.login`/`repository.owner.login` — it does not compare that org against the target `Team`'s stored `organization`. `drop_unhandled_event`, the `ExplicitParameters` schema, and `Team` model validations likewise perform no such cross-check. [4](#0-3) 

### Impact Explanation
If Team X's `id` is included in `Shipit.github_teams`, then `User#authorized?` grants access based on membership in that team: [5](#0-4)  An attacker who can emit a validly-signed membership webhook for *any* organization (including one they legitimately own) can add an arbitrary GitHub user to any pre-existing `Team` record by guessing/matching that team's numeric `github_id`, thereby escalating that user into `Shipit.github_teams` authorization — this matches the High-severity "escalation into `Shipit.github_teams` authorization" category. It is repeatable for every `added`/`removed` action and is not limited to one team, provided the attacker knows or can determine the target team's GitHub team `id`.

### Likelihood Explanation
Preconditions: (1) the target `Team` record must already exist in Shipit's database with a known `github_id`; (2) the attacker must control (or be able to genuinely sign webhooks for) some GitHub organization; (3) GitHub team IDs are globally unique and assigned by GitHub, not attacker-chosen, so the attacker must know or discover the exact numeric `github_id` of the victim team (e.g., via a public team listing, prior webhook logs, or brute force) rather than mint their own team with a colliding ID. This constrains real-world exploitability to cases where the target team ID is discoverable, but the code-level authorization gap itself requires no secrets, sessions, or privileged roles — only a genuinely-signed webhook from any org and knowledge of the target `github_id`.

### Recommendation
In `MembershipHandler#find_or_create_team!`/`#process`, verify that `params.organization.login == team.organization` before performing any membership mutation; if the verified organization does not match the team's recorded organization, drop/reject the event instead of mutating the roster. Do not rely on `find_or_create_by!`'s block semantics to keep `organization` authoritative once a `Team` exists.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/membership_handler_test.rb` (minitest, `ActiveSupport::TestCase`):
```ruby
test "membership event from a different organization cannot add members to an existing team" do
  team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  assert_equal 'shopify', team.organization

  payload = {
    'action' => 'added',
    'team' => { 'id' => team.github_id, 'name' => team.name, 'slug' => team.slug, 'url' => team.api_url },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'evil-user' }
  }

  Shipit::User.expects(:find_or_create_by_login!).with('evil-user').returns(users(:evil_user))

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  team.reload
  assert_equal 'shopify', team.organization, "team.organization must not silently diverge from verified org"
  refute team.members.include?(users(:evil_user)),
    "member added via a webhook verified for 'attacker-org' must not be added to a team owned by 'shopify'"
end
```
Before the fix this test fails because `team.members` includes `evil_user` despite the payload's `organization.login` (`attacker-org`) never matching `team.organization` (`shopify`).
