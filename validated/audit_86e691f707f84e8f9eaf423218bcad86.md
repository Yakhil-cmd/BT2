### Title
Webhook signature is verified against an attacker-chosen organization while the payload's `repository.full_name` field determines which repository/stack is actually written — organization-authenticated ≠ repository-written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read directly out of the *unverified* JSON body. The handler that actually performs the write (`Handler#stacks` / `Handler#repository_name`) looks up the target `Repository` using a *different* field of the same unverified JSON body: `repository.full_name`. Because the signature only proves the request was signed with the secret belonging to the organization named in `repository.owner.login`/`organization.login`, but does not constrain which repository the event is applied to, an attacker who can produce a valid signature for any one configured organization can forge events that write to stacks belonging to a **different** organization.

### Finding Description
In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This picks the `GithubApp` instance (and therefore the `webhook_secret` used for HMAC verification) purely from the attacker-supplied `repository.owner.login` field of the raw body. The corresponding `verify_webhook_signature` implementation:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

only checks that the full raw body was signed with *that organization's* secret (or is unconditionally accepted if that organization has no `webhook_secret` configured — a supported configuration shown in `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`).

Once verification passes, `create` re-parses the same body and dispatches it to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers resolve the target repository/stacks from a *different* field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

and act on it directly (e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the branch) [5](#0-4) , and `MembershipHandler#process` mutates `Team`/`Membership` records using `params.organization.login` and `params.member.login`, both taken from the same unconstrained body [6](#0-5) .

Nothing ties the value used to select the verifying secret (`repository.owner.login` / `organization.login`) to the value used by the handler to select the entity being mutated (`repository.full_name`, or the `organization`/`team`/`member` sub-objects for membership events). In a multi-organization Shipit deployment (explicitly supported — see `Shipit.github(organization:)`, `test/dummy/config/secrets_double_github_app.yml`), this is the binding-break called out by the rules: *the organization that authenticated versus the repository that is written*. A payload can claim to be from `OrgA` (satisfying signature verification against `OrgA`'s app) while its `repository.full_name` (or `membership` `organization`/`team`) references a stack that actually belongs to `OrgB`, whose stack is then synced/mutated without ever validating against `OrgB`'s credentials.

### Impact Explanation
This crosses the "unauthorized deploy/mutation across repositories" boundary called out as High/Critical impact: an event that is only proven to originate from the holder of one organization's webhook credentials can trigger `GithubSyncJob`, commit-status writes, or team/membership mutations for a stack under a completely different, unrelated organization tracked by the same Shipit instance — a cross-repository/cross-organization write that the signature check was supposed to prevent.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (a documented, supported configuration), and (2) the attacker being able to produce a request whose HMAC is valid for at least one configured organization (which, per the code's own explicit "return true unless webhook_secret" fallback, is trivially satisfied if any one configured organization omits `webhook_secret` — again a documented supported configuration, e.g. `config/secrets.development.example.yml`). No repository write access, GitHub App key, or session is needed to exploit this once such a configuration exists; the flaw is that the *code* never re-derives or cross-checks the acting organization against the field the handlers use to identify the mutated repository.

### Recommendation
Bind the two fields together: after `verify_signature` succeeds for organization `O`, `create`/`Handler` should independently verify that the resolved `repository.full_name` (or `organization.login`/`team.organization`) actually belongs to organization `O` before performing any write, rejecting the payload otherwise. Alternatively, sign/verify a canonical subset of fields (organization + repository full name) explicitly rather than trusting the raw body alone to imply consistency between the two.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (webhook_secret unset/blank — a documented valid configuration) and `OrgB` (webhook_secret set, tracking stack `OrgB/critical-repo`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push`, no/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/critical-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` immediately since `OrgA` has no `webhook_secret` [7](#0-6) .
4. `create` dispatches the parsed body to `PushHandler`, which resolves `Repository.from_github_repo_name("OrgB/critical-repo")` from `payload.dig('repository','full_name')` [8](#0-7)  and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for the `OrgB` stack [5](#0-4)  — a write to `OrgB`'s stack performed under a signature check that only ever validated `OrgA`.
