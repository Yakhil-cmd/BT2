### Title
Reachable `throw Error("no src_coin")` CHECK-style crash in `validatePaymentInputsAndOutputs` - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs` in `validation.js` contains hard `throw Error(...)` assertions that assume `objValidationState.src_coin` has already been populated whenever a payment references a private, fixed-denomination asset. That precondition is only guaranteed when validation is driven through the private-payment-chain code path (`indivisible_asset.js` → `validatePrivatePayment`), which explicitly sets `objValidationState.src_coin` before calling `validation.validatePayment`. However, a normal unit (posted directly to the network and processed by `validate()`/`validateMessages()`) can also declare a `payment` message for a private, fixed-denomination asset with `payload_location:"inline"` and a `transfer`-type input. In that path `objValidationState.src_coin` is never set, so the code reaches the unconditional `throw Error("no src_coin")` (and the following `throw`s for `src_output`/`denomination`/`amount`) inside an async `conn.query` callback with no enclosing `try/catch`, analogous to the reachable `CHECK`-fail in TensorFlow's `TensorByteSize`.

### Finding Description
In `validation.js`, `validatePaymentInputsAndOutputs` handles the `"transfer"` input case for assets that are `is_private && fixed_denominations`: [1](#0-0) 

```
// for private fixed denominations assets, we can't look up src output in the database 
// because we validate the entire chain before saving anything.
// Instead we prepopulate objValidationState with denomination and src_output 
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    ...
```

`objValidationState.src_coin` is set only inside `indivisible_asset.js`'s `validatePrivatePayment`, right before it calls `validation.validatePayment` for a chain-transfer element: [2](#0-1) 

That is the *only* place in the codebase that populates `src_coin`. The generic unit-validation path (`validate()` → `validateMessages()` → `validateInlinePayload()` → `validatePayment()`) never sets it. The gating logic that restricts `payment` messages for private assets does not forbid `payload_location:"inline"`; it only requires spend proofs when `payload_location === "none"`: [3](#0-2) 

```
if (objMessage.app === "payment"){ // special requirements for payment
    if (objMessage.payload_location !== "inline" && objMessage.payload_location !== "none")
        return callback("payment location must be inline or none");
    if (objMessage.payload_location === "none" && !objMessage.spend_proofs)
        return callback("private payment must come with spend proof(s)");
}
```

`validatePayment()` itself loads the asset and, for any asset (private or not), simply forwards to `validatePaymentInputsAndOutputs` once basic field checks pass — it does not reject `is_private` assets that arrive with an inline payload: [4](#0-3) 

Consequently, an attacker can compose a syntactically valid unit whose payment message:
- references an existing private, `fixed_denominations` asset,
- uses `payload_location: "inline"` (so the payload passes the standard hash-of-inline-payload checks),
- has a `transfer`-type input (not `issue`),

and post it to any node. When that node's `validate()` reaches `validatePaymentInputsAndOutputs` for that message, `objAsset.is_private && objAsset.fixed_denominations` is true and `objValidationState.src_coin` is `undefined`, hitting `throw Error("no src_coin")` inside the `conn.query`/`async.forEachOfSeries` callback chain, with no surrounding `try/catch` in `validate()`'s async flow. An uncaught exception thrown from inside a Node.js callback that isn't wrapped in a `try/catch` propagates as an uncaught exception and crashes the Node.js process (default Node.js behavior for uncaught exceptions in callbacks not associated with a Promise).

### Impact Explanation
Any peer that receives and validates such a unit (full nodes doing normal unit validation, not just private-payment recipients) will crash. Because `validate()` is invoked whenever a new unit/joint arrives from the network for any node, a single, cheaply crafted malformed unit posted by an unprivileged user is sufficient to crash a validating node's process — this is a network-wide denial-of-service vector (an attacker can broadcast one bad unit that crashes every full node that processes it), matching the "network unable to confirm new units" / node-availability impact category.

### Likelihood Explanation
The preconditions are simple to satisfy for anyone able to post a unit referencing an existing private, fixed-denomination asset (such assets and their public issuance definitions are visible on-DAG): craft a payment message with `payload_location:"inline"`, `asset` set to that private asset's hash, `denomination` set, and a `transfer` input pointing at any arbitrary/garbage source unit/message_index/output_index (the code throws before even doing an output lookup, since it goes into the private-asset branch, not the generic `conn.query` src-output lookup branch). No prior state manipulation, special privileges, or timing is required — the throw is unconditional once the private+fixed_denominations branch is entered without `src_coin`.

### Recommendation
- In `validatePaymentInputsAndOutputs` (`validation.js`), replace the `throw Error("no src_coin")` / `throw Error("no src_output")` / `throw Error("no denomination in src coin")` / `throw Error("no src coin amount")` assertions with graceful `return callback(...)` error returns, since these conditions are reachable from externally-supplied unit data, not just internal invariants.
- Additionally/alternatively, explicitly reject `payment` messages that reference an `is_private && fixed_denominations` asset when `payload_location === "inline"` at the top of `validateMessage`/`validatePayment`, since such payments are only intended to be validated via the private-payment-chain flow (`payload_location: "none"` with spend proofs), never inline.
- Audit other `throw Error(...)` calls inside `validatePaymentInputsAndOutputs` and sibling functions (`validation.js` lines ~2417-2476) that are reachable from attacker-controlled unit fields but currently assume internal-only invariants, and convert them to recoverable validation errors.

### Proof of Concept
1. On-chain, identify (or as attacker, first issue) a private asset definition with `fixed_denominations: true`, `is_private: true` (asset hash `ASSET_HASH`), with a known denomination `D`.
2. Craft a unit `U` with a single `payment` message `m` where:
   - `m.payload_location = "inline"`
   - `m.payload = { asset: ASSET_HASH, denomination: D, inputs: [{ type: undefined /* transfer */, unit: "<any 44-char base64 placeholder>", message_index: 0, output_index: 0 }], outputs: [{ address: <valid address>, amount: D, output_hash: "<any 44-char base64>" }] }`
   - Ensure `m.payload_hash` matches the computed hash of `m.payload` (standard hashing, no cryptographic obstacle since the attacker fully controls the payload).
3. Sign `U` with a valid author/definition so it passes author/signature checks, and post it to a full node (`validate(objJoint, ...)`).
4. Execution reaches `validatePayment` → `validatePaymentInputsAndOutputs`; because the referenced `asset` is `is_private && fixed_denominations` and the input is a `transfer`, and `objValidationState.src_coin` was never populated (this is the plain unit-validation path, not the private-chain path), the code executes `throw Error("no src_coin")` inside the `async.forEachOfSeries`/query callback, crashing the receiving node process.

Note: Because the private-payment-chain-only code paths (`indivisible_asset.js`, `private_payment.js`) were not fully traceable end-to-end for every guard that might exist elsewhere in the codebase (e.g., possible additional filtering in message-type-specific pre-checks not surfaced by search), full confirmation would benefit from a live/instrumented test run of `validate()` against the crafted unit described above.
