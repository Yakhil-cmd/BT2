### Title
`MembershipHandler#process` trusts webhook-declared team membership without verifying it against GitHub - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` links a `User` into a `Team` purely from the fields of an inbound `membership` webhook, and `find_or_create_team!` resolves the target `Team` by `github_id` alone, with no check that the team belongs to the organization whose signature was verified, and no callback to the GitHub API to confirm the claimed membership actually exists. This lets any org whose own `webhook_secret` is known (any tenant configured under `Shipit.github(organization: ...)`) attach an arbitrary login to any pre-existing `Team` record system-wide, including a privileged one referenced by `Shipit.github_teams`.

### Finding Description
The broken binding is:
`Shipit::User(login = L)` is a member of `Shipit::Team(github_id = T)` **iff** GitHub itself reports `L` as a member of team `T`'s real organization.

Tracing the code shows this never holds:

- `WebhooksController#verify_signature` derives the signing organization solely from the payload: `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then verifies the HMAC using that org's configured `webhook_secret` via `Shipit.github(organization: repository_owner).verify_webhook_signature` [2](#0-1) . This only proves the request was signed by *some* configured org's secret — it never checks that the `team` referenced in the same payload actually belongs to that org.
- `MembershipHandler#find_or_create_team!` resolves the team purely by the numeric `github_id` supplied in the payload, with no organization scoping: `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g. a privileged team referenced in `Shipit.github_teams`), the `find_or_create_by!` block (which would set `organization`) never runs, and the pre-existing team is returned unconditionally.
- `MembershipHandler#process` then creates/reuses a `User` purely from `params.member.login` via `User.find_or_create_by_login!`, which itself only calls `Shipit.github.api.user(login)` (a lookup, not a membership check) [4](#0-3) , and unconditionally calls `team.add_member(member)` [5](#0-4) , `Team#add_member` [6](#0-5) . At no point does the handler call GitHub's team-membership endpoint to confirm `member.login` is genuinely on that team.
- `User#authorized?` grants access purely from `Shipit.github_teams` membership: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , so once linked, the forged user is authorized.

Exploit flow: the attacker, holding a valid `webhook_secret` for an org they legitimately control in a multi-org Shipit configuration, POSTs `X-Github-Event: membership` with `{"action":"added","team":{"id":<privileged_team_github_id>,...},"organization":{"login":"<attacker_org>"},"member":{"login":"<attacker_login>"}}`, signed with their own secret. `verify_signature` passes because the signature matches the attacker's own org config. `find_or_create_team!` resolves to the pre-existing privileged `Team` row by `github_id` regardless of which org signed the request. `User.find_or_create_by_login!` creates the attacker's `User`. `team.add_member` links them. No guard (`verify_signature`, `find_or_create_team!`, `User.find_or_create_by_login!`, `authorized?`) ever calls back to GitHub to confirm the attacker's login is actually on that team in that team's real organization.

### Impact Explanation
The attacker's crafted `User` gains membership in a `Shipit::Team` tracked by `Shipit.github_teams`, making `authorized?` return `true` and granting full application authorization (stack access, deploy/rollback/merge triggering) without ever having been added to the real GitHub team. This is repeatable for any team whose `github_id` the attacker can learn (team IDs are not treated as secrets and are enumerable via GitHub's team API for teams the attacker can see). Blast radius spans the whole Shipit installation since `Team` records and `Shipit.github_teams` are not partitioned per signing organization. This matches "High - escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately controls one configured organization (and thus its `webhook_secret`), and knowledge of the target privileged `Team`'s numeric `github_id` (obtainable via public GitHub team APIs or by observing existing Shipit team fixtures/config). No Shipit session, API token, or the target org's own secret is required. The request is a single POST to `/webhooks`, trivially repeatable and scriptable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the `Team` lookup by both `github_id` and `organization` (matching the signature-verified `repository_owner`/`organization.login`), and reject/log when they diverge. Additionally, before calling `team.add_member`, perform a server-side confirmation call to GitHub's team membership endpoint (e.g. `GET /orgs/:org/teams/:team_slug/memberships/:username`) rather than trusting the webhook body alone.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership cannot bind an attacker-controlled org into a privileged team from another org" do
  privileged_team = shipit_teams(:shopify_developers) # github_id belongs to 'shopify' org
  attacker_org = 'attacker-org'

  Shipit.stubs(:github).with(organization: attacker_org).returns(
    stub(verify_webhook_signature: true)
  )
  Shipit.github.api.stubs(:user).with('attacker').returns(
    stub(id: 999, login: 'attacker', name: 'Attacker', email: nil, avatar_url: '', url: '')
  )

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker' }
  }.to_json

  post :create, body: payload, as: :json
  assert_response :ok

  attacker_user = Shipit::User.find_by(login: 'attacker')
  Shipit.stubs(:github_teams).returns([privileged_team])

  # Broken binding: Shipit believes attacker is on privileged_team, but no GitHub call ever confirmed it.
  assert attacker_user.teams.include?(privileged_team), "expected attacker linked to privileged team via forged webhook"
  assert attacker_user.authorized?, "expected authorized? true despite no real GitHub membership check"
end
```
