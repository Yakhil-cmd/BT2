### Title
Cross-Repository Commit Status Forgery via Webhook Signature/Repository-Binding Mismatch - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook's signature verification is bound to the `repository.owner.login` field (used to select which configured GitHub App/organization secret to check against), but the actual side effect of the `status` event — updating a `Commit`'s CI status — is bound only to `params.sha`, a payload field that is never cross-checked against the repository/organization that authenticated the request. An attacker who administers *any* GitHub organization onboarded to a multi-org Shipit instance (and therefore legitimately knows that organization's `webhook_secret`) can forge a signed `status` payload whose `sha` belongs to a commit in a completely different, unrelated stack/repository, injecting a forged "success" CI status for that foreign commit.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the `GitHubApp` (and its `webhook_secret`) to validate the incoming signature against using `repository_owner`, derived purely from the JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization app config (`webhook_secret`, etc.) from `secrets.github`, supporting multiple independent GitHub App installations/orgs in one Shipit instance: [3](#0-2) 

Once the HMAC signature is verified against the *claimed* organization's secret (`GitHubApp#verify_webhook_signature`, computed only over the raw payload — it never re-validates that the payload's other fields, such as `sha` or a target repository, actually belong to that organization): [4](#0-3) 

`Shipit::Webhooks::Handlers::StatusHandler#process` then acts on `params.sha` with **no repository/stack scoping whatsoever** — it looks up commits globally by SHA across the entire Shipit instance: [5](#0-4) 

This is the same bug class as the reported `Verifier.sol` issue: a value is authenticated/verified (the pairing-check result / the webhook signature tied to `repository.owner.login`), but a *different* value that is actually acted upon (the pairing outputs used downstream / `params.sha` used to select which `Commit` row to mutate) is never checked against what was verified. The binding that should hold is:

`organization whose secret produced a valid signature == organization owning the repository/commit being mutated`

but this binding is never enforced. The webhook signature only proves "the sender knows organization X's webhook secret"; it proves nothing about which commit SHA, across the entire multi-tenant Shipit deployment, is referenced in the JSON body.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker who legitimately controls one onboarded GitHub organization (and thus its `webhook_secret`) can forge a valid signature and inject arbitrary CI/status data (`state: "success"`, fabricated `context`, `description`, `target_url`) for a commit belonging to a stack/repository owned by a completely different, victim organization also hosted on the same Shipit instance. Commit statuses recorded this way feed into `Shipit::Commit`/`Shipit::CommitChecks`/`Shipit::Stack` deployability logic, meaning an attacker could make Shipit believe required CI checks passed for a victim's commit, undermining deploy-gating and merge-queue safety guarantees for repositories the attacker does not own or have write access to. This matches the "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Likelihood is contingent on the deployment actually using the multi-organization GitHub App configuration schema (`config/secrets.yml` with per-org `webhook_secret` sub-keys), which is a documented and supported setup: [6](#0-5) 

In that documented, supported configuration, no repository ownership check exists anywhere in the `status` event path between signature verification and the DB mutation, so exploitation requires only knowledge of one onboarded organization's webhook secret (which that organization's own administrators legitimately possess) and a guessable/known target commit SHA (commit SHAs are public information on GitHub). No privileged Shipit account, API token, or the target organization's own secret is required.

### Recommendation
Bind the entity used for signature verification to the entity actually mutated: `StatusHandler` (and any other handler that does not scope lookups by repository) should resolve the target `Commit`/`Stack` only within the repository identified in the payload (`params.repository.full_name` / the handler's own `stacks` scope, as already used by `PushHandler` and the `PullRequest` handlers via `Handler#repository_name`/`#stacks`), and that repository's owner must be verified to match the organization whose secret validated the signature before any state is mutated. Concretely, scope `Commit.where(sha: params.sha)` to commits under stacks belonging to `repository_name`'s owner, and reject/ignore the event if the resolved repository's owner does not match `repository_owner` used during signature verification.

### Proof of Concept
1. Shipit is configured with two organizations, `AttackerOrg` and `VictimOrg`, each with its own GitHub App and `webhook_secret` (per the documented multi-org config in `docs/setup.md`).
2. Attacker, who administers `AttackerOrg`'s GitHub App, knows `AttackerOrg`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha-in-VictimOrg-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `AttackerOrg`'s `webhook_secret` over the raw body.
5. POST to `/webhooks` with `X-Github-Event: status`. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and the signature validates successfully.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged `success` status onto the victim's commit — a repository the attacker never authenticated for and does not own.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
```
