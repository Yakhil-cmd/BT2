### Title
`Api::CCMenuController` lets any scoped `ApiClient` token read build status for a stack outside its authorized scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The bug-class in the external report is a missing consistency check before an action is performed: a value is mutated without validating it against the state that was supposed to gate the operation. The equivalent trust binding in `shipit-engine` is: **"a stack a token authorises" == "the stack a controller action touches."** `Api::BaseController` enforces this binding for every other API resource via its `stacks` scope, but `Api::CCMenuController` overrides the `stack` accessor and bypasses that scope entirely, breaking the binding for scoped `ApiClient` tokens.

### Finding Description
`Api::BaseController#stacks` is the mechanism that ties an `ApiClient`'s authorization scope to the stacks it may touch: [1](#0-0) 

Every other API controller (e.g. `Api::TasksController`, `Api::HooksController`) resolves the target stack through this scoped `stacks` collection (`stacks.from_param!`, or via `stack.id` derived from it), so a token created with `stack_id` set is confined to that one stack: [2](#0-1) [3](#0-2) 

`Api::CCMenuController`, however, defines its own `stack` method that resolves directly from the global `Stack` relation, never consulting `current_api_client.stack_id`: [4](#0-3) 

The only authorization check applied is `require_permission :read, :stack`, which merely checks that the token's `permissions` array contains `"read:stack"` — it does not check `stack_id`: [5](#0-4) [6](#0-5) 

So the "authorized stack" (what `current_api_client.stack_id` says the token may touch) and the "stack the action touches" (`Stack.from_param!(params[:stack_id])`) are two different, unreconciled values — exactly the missing-equality-check pattern that the CashManager report is about, just for a stack-scoping binding instead of a balance value.

Note: `CCMenuUrlController#client` shows that `ApiClient`s are routinely created scoped to a single stack via `create_with(permissions: %w[read:stack]) ... find_or_create_by!(creator:, name: 'CCMenu Client')` (this call does not set `stack:` here, but the intended usage pattern of a stack-scoped, read-only token is clearly supported by the model, e.g. `stack_id?`/`stacks` scoping in `BaseController`): [7](#0-6) [8](#0-7) 

### Impact Explanation
This is a scope-confinement bypass: any `ApiClient` (Basic-Auth token) that was deliberately restricted to one stack via `stack_id` and given only `read:stack` permission can query `GET /api/stacks/:stack_id/ccmenu.xml` for **any** stack ID, not just the one it was authorized for. That controller returns build/deploy status (`name`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), i.e. unauthenticated-for-that-stack read of deploy/task state. Per the rules this maps to the High-severity category "unauthenticated read of stack state, task streams or deploy output" achieved via broken per-token stack scoping — it does not require session, webhook secret, or admin access, only possession of a validly-issued, narrowly-scoped `ApiClient` token (which by design is meant to be handed to less-trusted integrations, e.g. CI dashboards).

### Likelihood Explanation
High likelihood: exploitation requires only a legitimately obtained, stack-scoped `ApiClient` credential (which is the intended low-privilege use case for this endpoint, as shown by `CCMenuUrlController` auto-provisioning `read:stack`-only clients) and knowledge/guessing of another stack's `:stack_id` param (predictable, e.g. `owner/repo/environment` slugs, which are often public GitHub repo names). No race condition or timing dependency is needed, unlike the original report — this is a straightforward missing-scope-check bug, always reproducible.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` method (i.e., `stacks.from_param!(params[:stack_id])`) exactly like every other API controller, instead of querying `Stack` directly. This restores the binding that the token's authorized `stack_id` scope must equal (or be checked against) the stack the request actually touches.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to `stack_id = A` with only `read:stack` permission (this is exactly what `CCMenuUrlController#client` / the "CCMenu Client" flow produces for read-only integrations).
2. Using that client's Basic-Auth token, send `GET /api/stacks/:B_stack_id/ccmenu.xml` where `B` is a different stack the token was never granted access to.
3. Observe that `Api::CCMenuController#stack` resolves `B` via `Stack.from_param!(params[:stack_id])` (bypassing the `stacks` scope used everywhere else), `require_permission :read, :stack` passes because it only checks the `"read:stack"` string is in `permissions`, and the response renders `B`'s build status — even though the token's `stack_id` binds it to `A`.
