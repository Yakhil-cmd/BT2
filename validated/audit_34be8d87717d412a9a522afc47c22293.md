### Title
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves commits by SHA across all stacks/repositories with no repository-ownership check, letting a forged status from an attacker-controlled repo satisfy a victim stack's `merge_request_required_statuses` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` for every match, without ever checking that the incoming webhook's repository matches the repository owning that commit/stack. Since git commit SHAs are content-addressed and not secret, an attacker who reproduces the exact commit object (trivial for a public repo's already-known commit) in a repository they own can emit a `status` webhook that writes a `Shipit::Status` row attached to the victim's `Commit`, with any `context`/`state` they choose.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `Status#context/state/sha row consulted by StatusChecker` must satisfy `status.originating_repository == commit.stack.github_repo_name`, but the code never establishes or checks this equality anywhere on the write path.

Code path:
- `Shipit::Webhooks::Handlers::StatusHandler#process` [1](#0-0)  iterates `Commit.where(sha: params.sha)` — a global, cross-stack, cross-repository lookup keyed only on `sha` — and unconditionally calls `commit.create_status_from_github!(params)` on every match.
- The handler's `params` schema only requires `:sha`, `:state`, and optionally `:description`, `:target_url`, `:context`, `:created_at`, `:branches` [2](#0-1) . There is no `:repository` field required or cross-checked against the commit's own `stack.github_repo_name`.
- `Commit#create_status_from_github!` forwards straight into `statuses.replicate_from_github!(stack_id, github_status)` with no repository verification [3](#0-2) .
- Once written, this `Status` row is fully trusted by `Shipit::Commit#status` (`Status::Group.compact`) [4](#0-3)  and by `Shipit::MergeRequest::StatusChecker`, which matches `required_statuses`/`ignored_statuses` purely by `context` string, scoped to the victim stack's deploy spec but never validating the row's provenance [5](#0-4) .
- `MergeRequest#any_status_checks_failed?` / `#any_status_checks_missing?` / `#all_status_checks_passed?` all build a `StatusChecker` from `head.statuses_and_check_runs` and rely on this compromised data to decide mergeability [6](#0-5) .

Exploit flow: Commit SHAs are content-addressed and not secret — the victim's queued PR head commit is publicly visible via the GitHub API/UI. An attacker can reconstruct byte-identical commit metadata (tree, parents, author/committer timestamps, message) in a repository they own (e.g., using `git commit-tree`/`git commit --date`), producing the identical SHA1 in their own repo. They then trigger (or directly send) a `status` event from their own repository naming a `context` that matches an entry in the victim's `shipit.yml` `merge_request_required_statuses` (public information), `state: 'success'`, `sha: <victim's queued head sha>`. `StatusHandler` finds the victim's `Commit` row purely by SHA match and writes the forged `Status`, with no comparison of `params`'s originating repository to `commit.stack.github_repo_name`.

Existing guards do not stop this: webhook signature verification (`verify_signature`/GitHub App signature check) only proves the payload came from *some* repository with a valid webhook configuration — it does not, and cannot by itself, prove the payload's repository matches the specific `Commit` row being updated, because that check is simply never performed in `StatusHandler`. The `ExplicitParameters` schema on the handler likewise has no `repository` binding to enforce.

### Impact Explanation
A successfully forged `success` status satisfying `merge_request_required_statuses` causes `MergeRequest#any_status_checks_failed?` and `#any_status_checks_missing?` to return `false`, defeating `reject_unless_mergeable!`'s CI gating and allowing `MergeRequest#merge!` to proceed and call `stack.github_api.merge_pull_request` [7](#0-6) . This is an unauthorized merge of a pull request whose real CI never passed, on a victim stack the attacker does not control — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The attack is repeatable against any stack/repository that uses `merge_request_required_statuses`, since the bug is a structural gap (missing repository check) in `StatusHandler#process`, not tied to any single victim.

### Likelihood Explanation
Preconditions: victim stack sets `merge_request_required_statuses` in `shipit.yml` (a documented, common feature) and has a merge request queued with a known head SHA (visible via public GitHub PR pages/API). Attacker cost is low: they need only a GitHub account and a repository they control (public or private) capable of emitting a signed `status` webhook to the Shipit host for a commit object with a specific SHA — achievable by reproducing the commit's exact git object and pushing/tagging it, or by any other means of getting GitHub to emit a `status` event with that `sha` from a repo they own. No Shipit credentials, session, or secrets are required at any point.

### Recommendation
In `Shipit::Webhooks::Handlers::StatusHandler#process`, scope the `Commit` lookup by the webhook payload's repository (e.g., `Commit.joins(:stack).merge(Stack.where(repository: ...)).where(sha: params.sha)` using the `repository.full_name` from the webhook payload), and reject/ignore any status event whose payload repository does not match `commit.stack.github_repo_name` before calling `create_status_from_github!`. Apply the same repository-provenance check to `CheckSuiteHandler`/`PushHandler` and any other handler that resolves records purely by SHA.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from a foreign repository is accepted for a commit belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/required-check',
    'repository' => { 'full_name' => 'attacker/forged-repo' } # never checked
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(nil, payload).process

  status = victim_commit.statuses.last
  assert_equal 'success', status.state
  # Binding under test: status.originating_repository should equal victim_stack.github_repo_name
  # but no such field/check exists -- the row was written unconditionally.
  refute status.respond_to?(:originating_repository) # demonstrates provenance was never recorded/checked

  checker = Shipit::MergeRequest::StatusChecker.new(
    victim_commit, victim_commit.statuses_and_check_runs, victim_stack.cached_deploy_spec
  )
  assert checker.success? # forged status alone satisfies required_statuses
end
```
