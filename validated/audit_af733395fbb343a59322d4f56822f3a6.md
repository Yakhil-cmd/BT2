### Title
Cross-Organization Webhook Forgery: Signature Verified Against `repository.owner.login` While Handlers Act on `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multi-tenant GitHub App configuration, where each organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using the field `repository.owner.login` (falling back to `organization.login`) taken from the *same* JSON body being verified [2](#0-1) [3](#0-2) . Once the signature passes, every event handler resolves the target repository using an entirely different field, `repository.full_name` [4](#0-3) , e.g. in `PullRequest::OpenedHandler#repository` and the sibling closed/labeled/reopened/unlabeled/assigned/edited handlers [5](#0-4) [6](#0-5) .

### Finding Description
This is the same bug class as the report's `_MIN_FEE`/`_MAX_FEE` mismatch: two values that are supposed to move together are validated independently, so an attacker can make one satisfy the check while the other drives the actual effect.

Binding that should hold: `organization_used_for_signature_verification == organization_of_repository_written_by_handler`.

Concretely:
- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)` to get that organization's `webhook_secret`, then HMAC-verifies the raw body against it [2](#0-1) .
- The handler layer never consults `repository.owner.login`; it derives the acted-upon repository purely from `repository.full_name` via `Repository.from_github_repo_name` [4](#0-3) , and `Repository.from_github_repo_name` simply splits `owner/name` out of that string with no cross-check against the verifying organization [7](#0-6) .

Since both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside the same JSON body, and the webhook_secret is a per-organization config value (multiple organizations can be configured, e.g. `OrgOne`/`OrgTwo`) [8](#0-7) , any tenant that possesses a valid webhook secret for *their own* organization can craft an arbitrary raw POST body directly to `/webhooks` (this endpoint is not restricted to genuine GitHub-origin deliveries; it is HTTP-reachable and authenticated only by HMAC) where:
- `repository.owner.login = "attacker-org"` (or `organization.login`) — selects `attacker-org`'s own secret for verification, which the attacker controls and can sign correctly.
- `repository.full_name = "victim-org/victim-repo"` — is what every downstream handler (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`, `assigned_handler.rb`, `edited_handler.rb`, and `stacks` lookup in `handler.rb`) uses to resolve the target `Repository`/`Stack`/`PullRequest`/`ReviewStack`.

The signature check therefore authenticates *an* organization, not *the* repository that the rest of the pipeline operates on — exactly the equality break the report's fee-bound bug represents (`min <= max` never enforced together).

### Impact Explanation
This lets an attacker who is a legitimate member/owner of one tenant organization configured in Shipit (no special Shipit privileges, no `ApiClient` token, no GitHub App private key) forge pull-request lifecycle events for a completely unrelated victim repository/organization also hosted on the same Shipit instance. Depending on handler and stack configuration this can:
- Auto-provision, archive, or unarchive a victim's review stack (`OpenedHandler#process`, `ClosedHandler#process`, `LabeledHandler#handle`, `ReopenedHandler#process`) [9](#0-8) [10](#0-9) .
- Overwrite stored `github_pull_request` metadata and labels for a victim's tracked PR (`AssignedHandler#process`, `EditedHandler#process`, label capture) [11](#0-10) .

Because review-stack archive/unarchive state directly gates deployability, this can be leveraged toward an unauthorized deploy/rollback state change on a stack the attacker has no legitimate access to — satisfying the "unauthorized deploy/rollback" impact bar. This maps to the Critical impact bucket (cross-repository writes / unauthorized deploy state manipulation) since the write lands on a repository/stack the caller was never authorized against.

### Likelihood Explanation
Likelihood is High for any deployment where more than one GitHub organization/tenant is configured (a documented, supported configuration per `test/dummy/config/secrets_double_github_app.yml` and `github_app_config`) [1](#0-0) . The attacker only needs to be a member of one tenant org with knowledge of (or ability to obtain) that org's webhook secret — no repository write access, no Shipit account, no `ApiClient` token is required. The forged request is a simple, directly-craftable HTTP POST with a correctly computed HMAC; no exotic timing or race condition is needed.

### Recommendation
Bind the field used for signature-key selection to the field used for repository resolution: after selecting the organization from `repository.owner.login`/`organization.login`, require that `repository.full_name`'s owner segment matches that same organization before dispatching to handlers, e.g. in `WebhooksController#verify_signature`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  owner_from_full_name = params.dig('repository', 'full_name')&.split('/')&.first
  head(422) unless verified && (owner_from_full_name.nil? || owner_from_full_name.casecmp?(repository_owner))
  ...
end
```
Alternatively, resolve the repository/stack purely from the verified `repository_owner` field, and reject payloads whose `repository.full_name` owner segment disagrees with it.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (a supported, documented multi-tenant setup).
2. Attacker, a member of `attacker-org`, knows/derives `attacker-org`'s `webhook_secret`.
3. Attacker builds a `pull_request` "opened" event JSON body:
   ```json
   {
     "action": "opened",
     "number": 1,
     "pull_request": { "...": "valid PR shape" },
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     },
     "sender": { "login": "attacker" }
   }
   ```
4. Attacker computes `sha1=HMAC(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: pull_request` and `X-Hub-Signature` set to that value.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own known secret [2](#0-1) .
6. `PullRequest::OpenedHandler#repository` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` [5](#0-4)  and, if provisioning conditions are met, creates/finds and mutates the victim's review stack — despite the request never being authenticated against `victim-org`.
