### Title
Bridge KAIA transfer to reverting recipient permanently locks bridged funds and stalls `lowerHandleNonce` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge updates all nonce-tracking state and emits the `HandleValueTransfer` event **before** attempting the actual KAIA push-transfer to `_to`. If the low-level call to `_to` fails (e.g., `_to` is a contract whose fallback reverts), the trailing `require(ok, ...)` causes the entire transaction to revert, rolling back every state mutation. Because there is no mechanism to skip or redirect a permanently-failing nonce, the KAIA is locked in the bridge forever and `lowerHandleNonce` can never advance past the stuck nonce.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

```
_lowerHandleNonceCheck(_requestedNonce)          // guard
_voteValueTransfer(_requestedNonce)              // sets closedValueTransferVotes[N] = true
_setHandledRequestTxHash(_requestTxHash)         // sets handledRequestTx[hash] = true
handleNoncesToBlockNums[N] = _requestedBlockNumber
_updateHandleNonce(N)                            // advances lowerHandleNonce / upperHandleNonce
emit HandleValueTransfer(...)
(bool ok,) = _to.call.value(_value)("")          // ← actual KAIA push
require(ok, "handleKLAYTransfer: transfer failed") // ← reverts entire tx on failure
``` [1](#0-0) 

When `_to` is a contract whose `receive`/fallback reverts (or has no payable fallback at all), step 8 always fails. Solidity reverts the entire call frame, so every mutation from steps 2–6 is rolled back:

- `closedValueTransferVotes[N]` → `false` again
- `handledRequestTx[hash]` → `false` again
- `handleNoncesToBlockNums[N]` → `0` again
- `lowerHandleNonce` / `upperHandleNonce` → unchanged [2](#0-1) 

Because `_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting at `lowerHandleNonce`, nonce N is never recorded, so `lowerHandleNonce` is permanently stuck at N. [3](#0-2) 

There is no owner/admin function to force-skip a nonce or force-advance `lowerHandleNonce`. The value-transfer recovery system (`vt_recovery.go`) uses `recoveryBlockNumber`, which is updated only inside `_updateHandleNonce`; with N stuck, `recoveryBlockNumber` is also frozen, causing the off-chain recovery daemon to re-scan from the same stale block indefinitely. [4](#0-3) 

The same structural flaw exists in `handleERC20Transfer` (safeTransfer/mint after nonce update) and `handleERC721Transfer` (transferFrom/mintWithTokenURI after nonce update). [5](#0-4) [6](#0-5) 

---

### Impact Explanation

- **Unauthorized asset lock**: KAIA deposited on the source chain is permanently trapped in the destination bridge contract. The user's funds are irrecoverable with no admin escape hatch.
- **Bridge nonce corruption**: `lowerHandleNonce` is frozen at the stuck nonce. All subsequent nonces can still be individually handled (the `_lowerHandleNonceCheck` only requires `lowerHandleNonce <= _requestedNonce`), but `lowerHandleNonce` never advances, so `recoveryBlockNumber` is also frozen. The off-chain recovery daemon will loop over the same block range indefinitely, wasting operator gas and potentially causing duplicate handle attempts for nonces above N.

---

### Likelihood Explanation

A user on the source chain specifies `_to` freely when calling `requestKLAYTransfer`. Setting `_to` to any contract without a payable fallback — including common multisig wallets, proxy contracts, or a purpose-built griefing contract — is sufficient to trigger the stuck state. This requires no special privilege: any bridge user can do it. It can also occur accidentally when a user mistakenly specifies a non-payable contract address. [7](#0-6) 

---

### Recommendation

Replace the push-transfer pattern with a **pull-payment** (claim) pattern: record `pendingWithdrawals[_to] += _value` and mark the nonce as handled unconditionally. Provide a separate `claimKLAY()` function for recipients to withdraw. Alternatively, wrap the low-level call in a success check and, on failure, emit a `TransferFailed` event and still mark the nonce as handled so `lowerHandleNonce` can advance. An admin `skipNonce(uint64)` escape hatch would also mitigate stuck states.

---

### Proof of Concept

```solidity
// Deploy on destination chain
contract RevertOnReceive {
    receive() external payable { revert("no KAIA"); }
}
```

1. On the source chain, call `requestKLAYTransfer(address(revertOnReceive), value, "")`. The bridge emits `RequestValueTransfer` with nonce N and locks `value` KAIA.
2. Bridge operators call `handleKLAYTransfer(txHash, from, address(revertOnReceive), value, N, blockNum, "")` on the destination bridge.
3. The call reaches line 98: `(bool ok,) = revertOnReceive.call.value(value)("")` → `ok = false`.
4. Line 99: `require(ok, ...)` reverts the entire transaction.
5. All state (votes, nonce maps) is rolled back. Operators retry — always revert.
6. `lowerHandleNonce` stays at its pre-N value; `recoveryBlockNumber` is frozen.
7. The `value` KAIA is permanently locked in the bridge contract with no recovery path. [8](#0-7) [9](#0-8)

        if (_requestedNonce > upperHandleNonce) {
