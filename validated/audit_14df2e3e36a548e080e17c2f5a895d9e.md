## Title
Wallet Contract's `rlp_execute_callback` fails to forward refunds returned by the target contract on success, causing relayer/caller fund loss — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract` acts as a wrapper that forwards an externally-supplied deposit (`attached_deposit`) to an arbitrary target contract via a `FunctionCall`/`Transfer` action, in the same "wrapper forwards funds to an external call" pattern as the Sudoswap `SofamonExchange` wrapper. Just like the reported bug where `swapTokenForSpecificNFTs` may return unused funds that the wrapper drops, the wallet contract only tracks and refunds the caller's deposit when the forwarded promise **fails**; if the forwarded call **succeeds** but the target contract itself returns unused/excess NEAR (e.g. a marketplace-style contract that refunds surplus attached deposit), that refund lands on the wallet contract's own account balance instead of being routed back to the external caller who supplied the deposit.

### Finding Description
`rlp_execute` accepts a deposit from `predecessor_account_id` and constructs a `CallerDeposit` to remember who to refund and how much, but only for the failure path: [1](#0-0) [2](#0-1) 

The deposit is forwarded verbatim to the target account through `action_to_promise`, which just creates a `FunctionCall`/`Transfer` promise with the given deposit and does not reserve any mechanism for the target to communicate back unused funds: [3](#0-2) 

The only place refunds are handled is `rlp_execute_callback`, and it exclusively refunds `caller_deposit` when `PromiseResult::Failed`. On `PromiseResult::Successful`, the response is returned as-is with no attempt to relay any excess/refunded balance back to the original depositor: [4](#0-3) 

Since NEAR's native protocol-level deposit refund only fires automatically when a *receipt* fails (per `docs/RuntimeSpec/Refunds.md`), any application-level refund transfer that a successfully-executing target contract sends back (e.g., a contract that accepts a deposit and refunds the unspent portion, mirroring Sudoswap's `swapTokenForSpecificNFTs`) is simply a `Transfer` action addressed to the wallet contract's `current_account_id` (the direct predecessor of that inner call), not to the external caller of `rlp_execute`. That transfer silently increases the wallet contract's own balance instead of being routed to whichever account fronted the deposit for this particular call: [5](#0-4) 

This is functionally the same bug class as the report: a wrapper that forwards funds to an external call, and does not account for a legitimate refund coming back from that call on the success path — it only handles the failure path.

### Impact Explanation
When a relayer/caller other than the wallet owner submits `rlp_execute` with an attached deposit intended to cover the target contract's requirements (e.g. NEP-141 `ft_transfer_call`, marketplace purchase, or any target that partially consumes and refunds excess deposit), and the underlying call *succeeds*, any refund the target sends back is absorbed into the wallet contract's own account balance rather than returned to the caller who supplied it. This is a fund-loss vulnerability for the external caller/relayer whenever a target contract's success path returns unused deposit — impact is Medium since it requires interacting with a target contract that performs such refunds and the caller must be different from the wallet owner (external relayer scenario is explicitly supported and tested, see `test_caller_refunds`).

### Likelihood Explanation
Likelihood is Medium: it requires (1) an external, non-self caller providing the deposit (already a first-class supported use case per `CallerDeposit::new`'s "external caller" check), and (2) a target contract whose success path refunds unused/excess deposit back to its direct caller. Many real contracts (marketplaces, AMMs, some NEP-141 wrappers) do exactly this, so the precondition is realistic though not universal.

### Recommendation
Track any balance change on the wallet contract account attributable to the forwarded call and forward it to `caller_deposit.account_id` in the `PromiseResult::Successful` branch of `rlp_execute_callback`, not only in the `PromiseResult::Failed` branch — analogous to how the Sudoswap wrapper fix requires checking for and forwarding refunds from `swapTokenForSpecificNFTs` regardless of outcome.

### Proof of Concept
1. An external relayer account (not the wallet owner) calls `rlp_execute` on the wallet contract, attaching a deposit `D`, with an RLP-encoded transaction whose `target` is a contract `X` that on success only consumes `D' < D` and transfers `D - D'` back to its predecessor.
2. `inner_rlp_execute` records `CallerDeposit { account_id: relayer, yocto_near: D }` and forwards the full deposit `D` to `X` via `action_to_promise`/`FunctionCall` action. [6](#0-5) 
3. `X`'s call succeeds and it sends a `Transfer` of `D - D'` back to its predecessor, i.e., the wallet contract's `current_account_id`.
4. `rlp_execute_callback` observes `PromiseResult::Successful` and returns `ExecuteResponse{success:true,...}` without forwarding any refund to `relayer`. [7](#0-6) 
5. The relayer permanently loses `D - D'`, which is now part of the wallet contract account's own balance, confirmed by contrast with the existing `test_caller_refunds` test which only asserts refund behavior for the failure case. [8](#0-7)

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
