The External Report's bug class ("a field the endpoint trusts as an authorization boundary is validated far too loosely, letting one actor act on another actor's resource") maps directly onto how the webhook signature check authenticates an organization/repository but `StatusHandler` then writes to any commit matching a bare SHA, regardless of which repository/stack that SHA actually belongs to.

### Title
Cross-repository commit status forgery leading to unauthorized merges/deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` only proves that an incoming GitHub `status` webhook was signed with the secret belonging to *some* configured organization (derived from `repository.owner.login` in the very same payload). It does **not** prove that the `sha` field inside that payload belongs to the repository/stack the signature was issued for. `StatusHandler#process` then applies the status to every `Commit` row in the whole installation that shares that SHA, with no repository/stack scoping at all, unlike the sibling `PushHandler`/`CheckSuiteHandler` which scope via `stacks`.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate against using `repository_owner`, taken from the unverified JSON body, and only checks that the whole raw body's HMAC matches that organization's secret: [1](#0-0) [2](#0-1) 

This proves the payload came from a legitimate GitHub `status` event for *some* repository whose owning organization's webhook secret matches — but it says nothing about which specific commit/stack the event is entitled to affect.

`StatusHandler#process` then updates any commit in the entire Shipit database matching the raw `sha`, without any repository or stack scoping: [3](#0-2) 

Contrast this with the other handlers, which correctly resolve the target stacks through the `repository.full_name` in the payload before acting: [4](#0-3) [5](#0-4) [6](#0-5) 

Because Git commit SHAs are content-addressed and identical across forks/mirrors that share history, an attacker who has legitimate push/status-creation rights on *any* repository sharing commit history with a Shipit-tracked repository (e.g., a public fork) can trigger a genuine, correctly-signed GitHub `status` webhook whose `sha` matches a commit that also exists in a completely different, unrelated Shipit stack. `StatusHandler` will happily attach that forged status (e.g., `state: success`) to the victim stack's commit.

Applying a status is not inert: `Commit#create_status_from_github!` runs `add_status`, which — on a transition to `pending`/`success` — schedules the merge queue for that commit's real stack: [7](#0-6) 

That scheduled `ProcessMergeRequestsJob` treats the forged status as a genuine passing CI check when deciding whether pending merge requests are mergeable: [8](#0-7) [9](#0-8) 

The equality that should hold — "the repository the signature authenticates == the repository/stack whose commit gets written" — is broken: the signature authenticates an organization/repository, but `StatusHandler` writes to any stack in the database whose commit table happens to contain that SHA.

### Impact Explanation
This allows an unprivileged attacker (any user able to create/receive a signed `status` webhook for a repo sharing commit history with the victim, e.g. a public fork with push or status-creation access) to inject a fabricated "success" CI status onto a commit belonging to a stack they do not control. Since a `success`/`pending` status transition schedules `ProcessMergeRequestsJob`, and `MergeRequest#all_status_checks_passed?` relies on exactly these `Status` records, this can cause an **unauthorized merge** of a pull request that never actually passed CI in the target repository — matching the required Critical/High impact criteria ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only: (1) commit-history overlap between an attacker-controlled repository and the victim's tracked repository (trivially achievable via a public fork of an open-source project), and (2) the ability to trigger a `status` webhook event for that shared SHA, which any collaborator/CI integration on the attacker's fork can normally do. No Shipit credentials, API tokens, or webhook secrets need to be known by the attacker — they rely entirely on their own repo's legitimately configured GitHub App/webhook signing.

### Recommendation
Scope `StatusHandler#process` (and any other handler) to the stacks resolved from the webhook's own `repository.full_name`, exactly as `PushHandler` and `CheckSuiteHandler` do, e.g. `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })...` instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Fork a public repository that is tracked as a Shipit stack (`victim/repo`), so the fork (`attacker/repo`) shares commit SHAs with `victim/repo`'s history.
2. Configure Shipit's GitHub App/webhook on `attacker/repo`'s organization (or use an org that already has Shipit installed and where the attacker has status-creation rights).
3. Use the GitHub Statuses API (`POST /repos/attacker/repo/statuses/:sha`) with `:sha` set to a commit SHA that is also the head of a pending merge request in `victim/repo`'s Shipit stack, setting `state: success` for whatever context the target stack's `shipit.yml` requires.
4. GitHub delivers a correctly signed `status` webhook to Shipit's `/webhooks` endpoint; `verify_signature` passes because the signature is valid for the attacker's own organization/app config.
5. `StatusHandler#process` finds the matching `Commit` row belonging to `victim/repo`'s stack (via `Commit.where(sha: ...)`, unscoped) and records the forged `success` status, triggering `ProcessMergeRequestsJob`, which can merge the pull request despite it never having a real passing CI run in `victim/repo`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
