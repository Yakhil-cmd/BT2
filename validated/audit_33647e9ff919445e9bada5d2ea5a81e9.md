### Title
Unchecked ERC721 `transferFrom` Return in Bridge Deposit Path Enables Unauthorized Cross-Chain NFT Claim — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721` uses raw `IERC721.transferFrom` calls with no success verification in both the deposit path (`requestERC721Transfer`) and the withdrawal path (`handleERC721Transfer`). The ERC20 bridge counterpart (`BridgeTransferERC20`) was explicitly hardened with `SafeERC20`, but the ERC721 bridge received no equivalent protection. A non-standard ERC721 token whose `transferFrom` silently no-ops (does not revert) allows an attacker to emit a valid `RequestValueTransferEncoded` event and increment `requestNonce` without the bridge ever taking custody of the NFT, causing the counterpart bridge to release an NFT from its liquidity pool to the attacker's recipient.

---

### Finding Description

`BridgeTransferERC20` declares `using SafeERC20 for IERC20` and routes every token movement through `safeTransfer` / `safeTransferFrom`: [1](#0-0) [2](#0-1) 

`BridgeTransferERC721` has no such wrapper. The deposit entry-point calls the raw interface directly: [3](#0-2) 

After that call returns (whether or not the NFT moved), `_requestERC721Transfer` is invoked unconditionally. In non-`modeMintBurn` mode it emits `RequestValueTransferEncoded` and increments `requestNonce` with no guard: [4](#0-3) 

The withdrawal path has the same defect — the bridge updates its nonce and emits `HandleValueTransfer` before the raw `transferFrom` to the recipient, and never checks whether the NFT actually left the contract: [5](#0-4) 

`ERC721Burnable.burn` does provide an implicit guard in `modeMintBurn` mode because it calls `_isApprovedOrOwner(msg.sender, tokenId)` and reverts if the bridge is not the owner: [6](#0-5) 

This means `modeMintBurn = true` is incidentally protected, but `modeMintBurn = false` (lock-and-release mode) is fully exposed.

---

### Impact Explanation

**Deposit path (line 129) — unauthorized cross-chain NFT claim:**

An attacker registers (or exploits an already-registered) non-standard ERC721 whose `transferFrom` silently no-ops. They call `requestERC721Transfer`. The bridge never receives the NFT, but `RequestValueTransferEncoded` is emitted with a valid `requestNonce`. Bridge operators on the counterpart chain observe the event and call `handleERC721Transfer`. In non-`modeMintBurn` mode the counterpart bridge executes `IERC721.transferFrom(address(this), _to, _tokenId)` from its own liquidity pool, delivering a real NFT to the attacker's chosen recipient. The attacker obtains a bridged NFT without depositing anything — an **unauthorized transfer of bridged assets**.

**Withdrawal path (line 69) — permanent NFT lock:**

If the counterpart bridge's `transferFrom` to the recipient silently fails, the nonce is consumed and the event is emitted, but the NFT remains locked in the bridge with no recovery path. This is a **permanent loss of a bridged asset** for the recipient.

---

### Likelihood Explanation

The token must be registered on the bridge. Bridge operators may register tokens without auditing their `transferFrom` revert behavior, especially for tokens that behave correctly under normal conditions but silently fail under edge cases (insufficient approval, paused state, blacklisted address). The ERC721 standard requires `transferFrom` to throw on failure, but non-standard or upgradeable tokens may violate this. The attack requires no special privilege beyond submitting a transaction to a public function.

---

### Recommendation

1. **Deposit path**: After `IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId)`, assert custody was actually transferred:
   ```solidity
   IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
   require(IERC721(_tokenAddress).ownerOf(_tokenId) == address(this), "ERC721 transfer failed");
   ```
2. **Withdrawal path**: Apply the same post-condition check after the `transferFrom` to `_to`.
3. **Consistency**: Mirror the `SafeERC20` pattern used in `BridgeTransferERC20` — introduce a `SafeERC721` helper or inline ownership assertions for every external ERC721 call.

---

### Proof of Concept

```
Precondition: Bridge deployed with modeMintBurn = false.
              A non-standard ERC721 "SilentToken" is registered on the bridge.
              SilentToken.transferFrom() emits no event and does not revert.
              Counterpart bridge holds tokenId=42 of a legitimate ERC721 in its pool.

1. Attacker calls:
     BridgeTransferERC721.requestERC721Transfer(
         SilentToken, attackerRecipient, tokenId=1, ""
     )

2. SilentToken.transferFrom(attacker, bridge, 1) silently no-ops.
   Bridge balance of tokenId=1: unchanged (attacker still owns it).

3. _requestERC721Transfer executes:
   - modeMintBurn == false → no burn attempted
   - emit RequestValueTransferEncoded(..., requestNonce=N, ...)
   - requestNonce++

4. Counterpart bridge operators observe the event and call:
     handleERC721Transfer(txHash, attacker, attackerRecipient,
                          legitimateERC721, 42, N, blockNum, "", "")

5. Counterpart bridge executes:
     IERC721(legitimateERC721).transferFrom(address(this), attackerRecipient, 42)

Result: attackerRecipient receives tokenId=42 of the legitimate ERC721
        from the counterpart bridge's pool.
        Attacker deposited nothing.
        Bridge's NFT liquidity is drained one token per request.
