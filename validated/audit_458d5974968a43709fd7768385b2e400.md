### Title
AA responses containing fixed-denomination assets are silently dropped, permanently freezing deposited denominational (NFT-like) tokens - (File: aa_composer.js)

### Summary
In `aa_composer.js`'s `sendUnit()` function, payment messages that specify a `fixed_denominations` asset (Obyte's non-fungible/indivisible token analog to an "NFT") are intentionally skipped during output completion and then permanently filtered out of the response unit, so an Autonomous Agent can never actually pay out such assets to users, even though the AA logic can construct a message intending to do so.

### Finding Description
When an AA response is built, each `payment` message is processed to fill in `outputs`/`inputs`. For any asset, `storage.loadAssetWithListOfAttestedAuthors` is used to fetch `objAsset`, and if `objAsset.fixed_denominations` is true, the code explicitly skips completing the payload "to skip it later": [1](#0-0) 

After the per-message pass, the code performs a second-pass filter that removes *every* payment message whose asset is a fixed-denomination asset from the final message set that becomes the response unit: [2](#0-1) 

If that filtering empties out all messages, the code treats it as a "successful empty response" — the state changes still execute and the trigger's incoming funds are consumed/accepted — but the intended NFT/fixed-denomination payout to the recipient never happens: [2](#0-1) 

This mirrors the OpenQ root cause: a payout path exists for one class of asset (ERC20/regular divisible assets), but the code path for another asset class (fixed-denomination/NFT-like assets) is unconditionally excluded from distribution logic, even though such assets can be legitimately deposited into and issued by the AA (see `asset` message validation supporting `fixed_denominations` payloads): [3](#0-2) 

### Impact Explanation
Any AA that is designed to hold or issue fixed-denomination assets (Obyte's closest analog to NFTs — non-fungible, indivisible tokens with fixed serial "denominations") and attempts to distribute them to users as part of a response will have those payment messages silently dropped. The AA's on-chain state can still update as if payout succeeded (since the state-update formula and other messages proceed), but the recipient never receives the fixed-denomination asset. Funds/tokens of this type held by the AA become effectively frozen/stuck inside the AA address — unauthorized inability to spend for legitimate recipients, and value loss/freezing for the AA and its users. This satisfies "AA fund loss or freezing" impact criteria.

### Likelihood Explanation
This is deterministic and always triggers whenever an AA's `messages` template includes a `payment` message with an asset whose definition has `fixed_denominations: true`. No attacker action or malicious peer is required — a normal, legitimate AA author who wants to build a bounty/marketplace/lottery AA that distributes NFT-like fixed-denomination assets to closers/winners would hit this every time such logic is triggered, exactly as OpenQ's `_claimOngoingBounty` unconditionally omits the NFT branch.

### Recommendation
Add proper handling for `fixed_denominations` assets in `sendUnit()`'s payment-completion path instead of skipping/filtering them out: implement the equivalent of `completePaymentPayload` for denominational assets (selecting appropriate denomination-output combinations and/or issuing new fixed-denomination units) so that AA-composed payment messages referencing fixed-denomination assets are actually included and completed in the response unit, rather than being dropped in the second-pass filter at line 1356.

### Proof of Concept
1. Deploy an AA whose response template includes:
   - An `asset` message that issues a `fixed_denominations` asset (as permitted by `aa_validation.js` lines 225–229), and
   - Later, upon a trigger, a `payment` message paying out units of that fixed-denomination asset to `trigger.address`.
2. Send a trigger that satisfies the payout condition.
3. Observe in `aa_composer.js` `sendUnit()`: the payment message for the fixed-denomination asset is skipped in the per-message loop (`aa_composer.js:1327-1328`) and then removed entirely by the filter (`aa_composer.js:1356`).
4. If no other non-fixed-denomination messages remain, `handleSuccessfulEmptyResponseUnit(null)` is invoked (`aa_composer.js:1358-1360`) — the trigger is accepted, state vars are committed, but the intended fixed-denomination asset payout never reaches the recipient, leaving it stuck at the AA address indefinitely. [4](#0-3)
