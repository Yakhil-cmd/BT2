### Title
StatusHandler#process ignores repository binding, allowing cross-repo commit-status injection that unblocks another stack's `Commit#blocked?` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone (`Commit.where(sha: params.sha)`), with no join or check against `payload['repository']['full_name']`, unlike the base `Handler#stacks` helper (which scopes by `Repository.from_github_repo_name(repository_name)`) that every other handler uses. Since `Shipit::Commit` rows are keyed by `sha` but are not globally unique across stacks/repositories (each stack tracks its own `Commit` records, and identical git objects — e.g. from a fork or a locally reconstructed commit with matching tree/parents/message/timestamps — produce identical SHAs), a webhook correctly signed for attacker-owned repo A can create a `Status` on a `Commit` row belonging to victim stack B whenever a commit with a matching SHA exists in B.

### Finding Description
The broken binding is: **repository that authenticated the payload (verified via `WebhooksController#verify_signature` against `repository_owner`/`params.dig('repository','full_name')`) MUST equal the repository whose `Stack#blocking_statuses` config is being evaluated for the resulting `Status`.** Concretely: `payload['repository']['full_name'] == commit.stack.repository.full_name` is expected but never checked.

Code path:
- `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses `request.raw_post`, dispatches to `Shipit::Webhooks.for_event('status')`, which is `[Handlers::StatusHandler]` (`app/models/shipit/webhooks.rb:19`).
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload was signed by `repository_owner`'s GitHub App secret — it proves *who sent it*, not *which commit/stack it may affect*.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```ruby
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ```
  This never calls the base `Handler#stacks`/`repository_name` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that every other handler (e.g. `PullRequest::OpenedHandler`, which explicitly resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` at `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`) uses to scope the mutation to the authenticated repository.
- `Commit#create_status_from_github!` creates a `Status` on that commit regardless of stack/repo origin.
- `Status::Common#blocking?` (`app/models/shipit/status/common.rb:46-48`) is `!success? && commit.blocking_statuses.include?(context)`, and `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) walks `stack.commits.reachable...any?(&:blocking?)`. `blocking_statuses` is delegated from `Commit` to `Stack` (`app/models/shipit/commit.rb:57-58`), so a `state: success` status with a matching `context` posted against victim stack B's commit flips that commit's `blocking?` to false, and if it was the only blocking commit, `Commit#blocked?` on stack B becomes `false`.

Attacker's exact request: attacker owns/controls repo A (with a valid webhook signature for A, which they legitimately receive as the repo owner). They arrange for a commit with SHA `S` to exist in both repo A (their own repository/fork) and be already tracked as a `Shipit::Commit` in victim stack B (e.g. because B tracked the same upstream commit before a fork divergence, or because git SHAs are content-derived and reproducible). They send `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` for repo A, and body `{"sha": S, "state": "success", "context": "<victim's blocking status context>", "repository": {"full_name": "attacker/repo-a", ...}}`. `verify_signature` passes (it's genuinely signed by A). `StatusHandler#process` finds `Commit.where(sha: S)`, which returns B's commit row (not A's), and records a `success` `Status` under B's stack context, un-blocking B.

Existing guards do not stop this: `verify_signature` only authenticates the sender, not the target; `drop_unhandled_event`/`check_if_ping` are irrelevant; `ExplicitParameters` schema only validates payload shape, not repo scoping; there is no `stacks`/repository filter anywhere in `StatusHandler`.

### Impact Explanation
An attacker who controls any repository configured with a Shipit webhook (trivially satisfied by being an unprivileged GitHub user who owns a public repo and installs/receives the app's webhook for it, or by controlling any repo whose webhook secret is otherwise available to them as its owner) can inject arbitrary `success`/`failure`/`pending` `Status` records onto a **different** stack's commits, as long as a matching SHA exists there. This directly un-blocks `Commit#blocked?` and can make an otherwise-blocked commit `deployable?` in victim stack B (`Commit#deployable? = !locked? && (stack.ignore_ci? || (success? && !blocked?))`, `app/models/shipit/commit.rb:227-229`), enabling an unauthorized deploy of a commit that should have been gated by a required/blocking status (e.g. security compliance checks like `soc/compliance` from the README example). This is a cross-tenant record write for a repository that did not authenticate it, and can lead to unauthorized deploys — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Preconditions: the attacker must control a repository configured with a Shipit webhook (owning any tracked repo, low bar for an "unprivileged" actor by the threat model's own definition of "any internet user who can send HTTP requests... including POST /webhooks", though the signature does need to be valid for *some* repo they control) and must find/produce a SHA collision with a commit in the victim's tracked history. SHA collision is feasible: forks of the victim repo naturally share ancestor commit objects with identical SHAs, or an attacker can locally construct a commit object with identical tree, parents, author/committer identities and timestamps, and message to reproduce an existing SHA exactly (git commit hashing is fully determined by these fields, none of which require secrets). This is repeatable per request and against any stack that happens to share a SHA with an attacker-influenced repo.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository that authenticated the webhook, mirroring the base `Handler#stacks` pattern used by other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
so that `commit.stack.repository == Repository.from_github_repo_name(payload['repository']['full_name'])` is enforced before any `Status` is written.

### Proof of Concept
minitest plan (to add under `test/models/shipit/webhooks/handlers/status_handler_test.rb` or extend `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status webhook for repo A cannot unblock a commit belonging to stack B" do
  stack_a = shipit_stacks(:shipit)          # attacker-controlled, signed repo
  stack_b = shipit_stacks(:cyclimse)        # victim stack
  shared_sha = 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'

  # Commit with the SAME sha tracked under the victim stack B, currently blocking.
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'x', author: nil)
  stack_b.stubs(:blocking_statuses).returns(['soc/compliance'])
  commit_b.statuses.create!(stack: stack_b, state: 'pending', context: 'soc/compliance')

  assert commit_b.blocked?, "sanity: commit_b should be blocked before attack"

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  body = {
    sha: shared_sha,
    state: 'success',
    context: 'soc/compliance',
    repository: { full_name: stack_a.repository.full_name, owner: { login: stack_a.repository.owner } }
  }.to_json

  post :create, body:, as: :json
  assert_response :ok

  commit_b.reload
  refute commit_b.blocked?, "BUG: repo A's status payload unblocked stack B's commit"
end
```
Both sides of the equality to assert: before the request, `commit_b.stack.repository.full_name` ("cyclimse/...") != the signed `repository.full_name` in the payload ("shopify/shipit-engine"), yet the `Status` still gets attached to `commit_b` and `commit_b.blocked?` flips from `true` to `false`, proving the divergence.
