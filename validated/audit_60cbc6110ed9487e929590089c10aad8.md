## Title
Webhook signature verification uses the org derived from the payload while event handlers act on an independently-controlled `repository.full_name` field, allowing repository-confused webhook forgery when *any* configured GitHub org has no `webhook_secret` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App config (and therefore the `webhook_secret` used for HMAC verification) based on `repository.owner.login`, falling back to `organization.login`, both read directly from the untrusted, attacker-supplied JSON body. [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that org: [3](#0-2) 

Meanwhile, `Shipit::Webhooks::Handlers::Handler#repository_name` — used by every event handler (push, status, check_suite, deployable_status, merge_status, pull_request, etc.) to select which `Repository`/`Stack` to act on — reads a *separate* field, `payload.dig('repository', 'full_name')`: [4](#0-3) 

These two lookups are not bound together by the signature: the field used to pick the verification secret (`repository.owner.login` / `organization.login`) is not cryptographically tied to the field used to pick the acted-upon repository (`repository.full_name`).

### Finding Description
The binding that should hold is:
```
organization used to select webhook_secret for HMAC verification == organization that owns the repository the handler subsequently mutates
```
In a genuine GitHub delivery this holds because GitHub signs the exact payload with the secret configured for the repository's actual owner. But Shipit's engine independently re-derives "which org authenticates this request" from a payload field, and independently re-derives "which repository to act on" from another payload field, then never cross-checks them.

If a Shipit deployment is configured with multiple GitHub Apps (as the engine explicitly supports via `config/secrets.yml`'s multi-org `github:` block, documented in `docs/setup.md`) and *any one* of those configured organizations has a blank `webhook_secret` — a configuration explicitly shown as a valid/expected state in the engine's own example secrets files (`webhook_secret: # nil`) — then: [5](#0-4) [6](#0-5) 

1. An unauthenticated attacker crafts a webhook POST with `X-Github-Event: push`, `organization.login` (or `repository.owner.login`) set to the org lacking a secret.
2. `verify_signature` resolves `Shipit.github(organization: repository_owner)` to that org's app config, calls `verify_webhook_signature`, which returns `true` immediately because `webhook_secret` is blank — no signature check is performed at all. [7](#0-6) 
3. The request proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, invoking e.g. `PushHandler`. [8](#0-7) [9](#0-8) 
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(repository_name)`, where `repository_name` is `payload.dig('repository', 'full_name')` — a field the attacker fully controls and which need not match the org used in step 2 for signature bypass. [4](#0-3) [10](#0-9) 
5. The attacker sets `repository.full_name` to an entirely different, fully-secured organization's repository tracked by Shipit, and triggers `stack.sync_github(expected_head_sha: params.after)` for any matching non-archived stack/branch — an unauthenticated write into that stack's sync state for a repository whose own org's webhook secret was never checked. [9](#0-8) 

The same pattern applies to every other handler built on `Handler#repository_name`/`#stacks` (status, check_suite, deployable_status, merge_status, commit_status, pull_request family), since all inherit the same unauthenticated `repository.full_name` resolution once the outer signature gate is defeated via the unrelated org field. [11](#0-10) 

### Impact Explanation
This breaks the equality: `organization that authenticated == repository that is written`. An attacker who knows (or guesses/enumerates) that a multi-org Shipit installation has one org configured without a `webhook_secret` can forge push/status/check-suite/etc. webhooks that pass verification entirely unauthenticated, yet target and mutate the sync/CI/deploy-eligibility state of stacks belonging to a *different, properly-secured* organization's repositories. Depending on the stack's continuous-deployment configuration, forcing a bogus `sync_github` or manipulating commit statuses/CI signals can influence which commits are considered deployable, potentially leading to an unauthorized deploy trigger — this satisfies the "unauthorized deploy" Critical-impact category defined in scope.

### Likelihood Explanation
Requires the deployment to use the documented multi-GitHub-App configuration and for at least one configured org to have an unset `webhook_secret` — a state the engine's own example/dummy configs demonstrate as normal/supported (`webhook_secret: # nil`). No credentials, session, or repository write access are needed; the request is a plain unauthenticated HTTP POST to the public webhooks endpoint.

### Recommendation
Bind the org used for signature verification to the org actually acted upon:
- Require `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner` to match the `repository_owner` used in `verify_signature`, rejecting the request if they diverge.
- Do not allow `verify_webhook_signature` to silently return `true` for a blank `webhook_secret` when the engine is configured with more than one GitHub App; require every configured org to have a non-blank `webhook_secret`, or fail closed application-wide if any is missing while multiple orgs are configured.
- Alternatively, resolve the org strictly from `repository.full_name`'s owner (the field actually used to select the acted-upon repository) rather than from a separate `repository.owner.login`/`organization.login` field, so a single field drives both verification and action.

### Proof of Concept
Given a `config/secrets.yml` with two orgs, `secure-org` (has `webhook_secret`) and `weak-org` (no `webhook_secret`), and Shipit tracking a stack for `secure-org/app`:

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "organization": { "login": "weak-org" },
  "repository": { "full_name": "secure-org/app", "owner": {} },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
`repository_owner` resolves to `"weak-org"` (fallback), `verify_webhook_signature` short-circuits to `true` since `weak-org` has no secret, and `PushHandler` then acts on `secure-org/app`'s stacks via `Repository.from_github_repo_name("secure-org/app")`, all without ever validating a signature under `secure-org`'s actual `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
