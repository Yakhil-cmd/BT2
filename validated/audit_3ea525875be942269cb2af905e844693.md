## Title
Private Payment Duplicate-Detection Uses Partial Output Match Instead of Validating the Full Payload, Bypassing Spend-Proof and Input Validation - (File: `private_payment.js`)

### Summary
The DataEase bug validates only the top-level `sceneId`/token-resource binding, but never checks that the nested `tableId`/field identifiers in the request body actually belong to the authorized resource — letting an attacker swap in unrelated identifiers to read unauthorized data while the token still "passes" the one check that is performed.

`private_payment.js`'s `validateAndSavePrivatePaymentChain()` has the same shape of flaw: before running full payment validation (spend-proof verification, input/output consistency, asset rules), it runs a "duplicate" short-circuit that only checks whether **one** output entry inside the submitted payload happens to match **any** previously stored output row for `(unit, asset, message_index)`. If it matches, the entire payload is accepted as `ifOk()` without ever validating the rest of the payload (inputs, spend proofs, other outputs, totals).

### Finding Description
For divisible private assets, the duplicate check is: [1](#0-0) 

Key issue: for `objAsset.fixed_denominations === false` (arbitrary-amount/divisible assets), the SQL query has **no `output_index` filter** — the comment even says *"divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them"*. The subsequent `.some()` check declares the whole submitted chain a "duplicate" if **any single entry** in `payload.outputs` matches **any single previously-stored output row** by `(address, amount, blinding, denomination=1)`.

This is the same class of bug as the DataEase report: one identifier/field (a single output's public tuple) is validated to be "known/legit", but the code then treats the **entire surrounding object** (the full `payload` — its `inputs`, spend proofs, and all *other* `outputs`) as implicitly trusted and skips calling `assetModule.validateAndSavePrivatePaymentChain()`: [2](#0-1) 

Compare this to the actual validation path that is bypassed, which performs real cryptographic/DB binding of the whole chain (spend proofs, source-output linkage, sequence checks) in `indivisible_asset.js`/`divisible_asset.js`: [3](#0-2) [4](#0-3) 

Because the duplicate-detection SQL and the `.some()` match key on a single output tuple rather than the entire claimed payload (all inputs + all outputs for that exact `message_index`), an attacker who already knows one legitimate output for a given `(unit, asset, message_index)` — e.g., because they are a cosigner who legitimately received the "change" output, per the forwarding logic in `indivisible_asset.js`'s `arrCosignerChains`/`arrRecipientChains` — can construct a new `arrPrivateElements` chain for the *same* `(unit, asset, message_index)` that:
1. Includes that one already-known, publicly-matching output entry (satisfying the `.some()` predicate), and
2. Carries arbitrary/forged `inputs` (fake spend proofs) and arbitrary other `outputs` that were never checked against the real on-chain spend-proof table.

The function then calls `transaction_callbacks.ifOk()` — i.e., the caller (`network.js`'s `handleOnlinePrivatePayment`, `wallet.js`'s hub-side chain validation) treats the forged chain as **fully validated**, sets `assocValidatedByKey[key] = true`, emits acceptance events, and forwards the chain onward to other cosigners/output-address members as validated data: [5](#0-4) [6](#0-5) 

### Impact Explanation
Downstream consumers (wallets, hubs relaying on behalf of light clients, cosigner devices) rely on the `ifOk` verdict from `validateAndSavePrivatePaymentChain` to mean "this private payment chain's inputs/outputs/spend-proofs were cryptographically verified." Because the duplicate short-circuit can be satisfied without validating the actual claimed inputs and the rest of the outputs, a malicious counterparty in a private (divisible) asset transfer can get a forged chain accepted and propagated as validated among other wallet members / hub-relayed light clients, corrupting their view of the private chain's legitimacy (false acceptance) and enabling forwarding of unverified transaction data as if it were confirmed, undermining the integrity guarantee that a "validated" private payment actually has real, checked spend proofs.

### Likelihood Explanation
Reachable directly by any private-payment counterparty holding a legitimately-forwarded output for the target `(unit, asset, message_index)` — no special node/peer/hub privilege required, since `validateAndSavePrivatePaymentChain` is invoked from ordinary device-message/private-payment handling (`network.js` `handleOnlinePrivatePayment`, `wallet.js` `handlePrivatePaymentChains`) triggered by messages from a paired device/counterparty.

### Recommendation
Change the duplicate-detection query/logic for divisible assets to require a full match of the *entire* claimed payload (all outputs, inputs, and their linkage) against previously stored data for that exact `(unit, asset, message_index)`, or better, only treat the payload as a "duplicate" when the whole `payload` hashes identically to what was previously accepted (e.g., compare a canonical hash of the full `payload.inputs`/`payload.outputs` rather than matching a single output tuple with `.some()`), before skipping the call to `assetModule.validateAndSavePrivatePaymentChain()`.

### Proof of Concept
1. Attacker is a cosigner on a shared address and legitimately receives one hidden-output chain element for `(unit=U, asset=A, message_index=M)` with `output = {address: X, amount: N, blinding: B}` (from `arrCosignerChains` forwarding in `indivisible_asset.js`/`divisible_asset.js`).
2. Attacker crafts a new `arrPrivateElements` head element for the same `(U, A, M)` whose `payload.outputs` array includes an entry `{address: X, amount: N, blinding: B}` (matching the known real output) alongside other **forged** outputs, and whose `payload.inputs` reference **fabricated** spend proofs/inputs unrelated to the real transaction.
3. Attacker sends this chain via `private_payment` device message to a wallet/hub.
4. `validateAndSavePrivatePaymentChain()` in `private_payment.js` runs the duplicate-check SQL (no `output_index` filter for divisible assets), finds the stored row matching the one legitimate output, sets `bDuplicate = true`, and calls `ifOk()` — **without ever invoking `divisibleAsset.validateAndSavePrivatePaymentChain` to check the forged inputs/other outputs**.
5. The receiving wallet/hub treats the forged chain as validated and forwards it to other members of the output addresses as confirmed private-payment data.
