### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The GitHub App organization that authenticates a webhook (via its `webhook_secret`) is not the same entity that `StatusHandler` ultimately writes to. The handler resolves the target `Commit` purely by `sha`, globally, with no check that the commit's repository/organization matches the organization whose signature was verified. This breaks the equality `authenticated_organization(webhook) == organization_of(commit_written)`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the payload against based on the organization derived from the payload itself: [1](#0-0) [2](#0-1) 

This only proves that the payload was sent by *some* GitHub App/organization configured in `Shipit.github`, and that the signature matches the `repository.owner.login` (or `organization.login`) claimed inside that same payload. It does **not** constrain which `Commit`/repository the event is allowed to affect — that binding is supposed to be re-derived and enforced by the individual event handler.

Most handlers correctly scope their side effects to the repository named in the payload via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 
e.g. `PushHandler` and `CheckSuiteHandler` both filter through `stacks` (repository-scoped) before touching any `Commit`: [4](#0-3) [5](#0-4) 

However, `StatusHandler` never calls `stacks` / `repository_name` at all — it looks up commits by SHA across the entire `Commit` table, independent of repository or organization: [6](#0-5) 

Because Shipit is explicitly multi-tenant (multiple GitHub organizations/apps can be configured, each with its own `webhook_secret`, as shown in `config/secrets.development.shopify.yml`), an attacker who legitimately controls (or is a legitimate GitHub App/webhook sender for) Organization A's repository can send a correctly-signed `status` webhook naming a `sha` that also exists as a tracked `Commit` in Organization B's (a different, unrelated tenant's) repository — for example, because Org B's repository is a fork of, or shares history with, Org A's repository, so identical commit SHAs exist in both. `StatusHandler` will happily update that commit's status in Org B's stack, even though the webhook was authenticated only for Org A.

### Impact Explanation
Commit statuses reported through this path feed `CommitChecks`, which are used by Shipit to gate whether a commit is deployable/mergeable. An attacker who is legitimately entitled to send webhooks only for their own (unrelated) organization/repository can inject or forge a `success`/`pending`/`failure` status against a commit belonging to a different tenant's repository, as long as the SHA happens to coincide (trivially achievable for forks of a tracked upstream repository). This can be used to force a false "green" status on a commit in a repository the attacker does not control, potentially enabling an unauthorized deploy decision to be made on stale/forged CI status — a cross-repository write into another tenant's data that this webhook was never authorized to touch.

### Likelihood Explanation
Requires the attacker to control any GitHub App installation/webhook sender that is one of the configured `Shipit.github` organizations (a low bar in a multi-org Shipit deployment, since organizations are onboarded independently and many orgs' repos are forks of each other), and requires a shared commit SHA between their repository and the victim repository — a very common occurrence for forked repositories that haven't diverged on a given commit. No repository write access to the victim repo, no privileged Shipit account, and no signature-forgery are needed.

### Recommendation
`StatusHandler#process` should scope its `Commit` lookup to the repository derived from the authenticated payload, mirroring what `Handler#stacks` already does for other handlers, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Stack -> Repository` using `repository_name` before updating any commit status, rather than querying `Commit.where(sha: ...)` globally.

### Proof of Concept
1. Configure Shipit with two GitHub organizations/apps, `org-a` and `org-b`, each with its own `webhook_secret` (as supported by `config/secrets.yml`).
2. Shipit tracks a repository under `org-b` (the victim) that is a fork of / shares a commit `sha` with a repository under `org-a` (attacker-controlled org, e.g. attacker's own fork).
3. Attacker triggers (or crafts, since they control `org-a`'s repo/app) a `status` webhook event with `repository.owner.login = "org-a"`, `sha = <shared-sha>`, `state = "success"`.
4. `WebhooksController#verify_signature` validates the signature using `org-a`'s `webhook_secret` — this succeeds because the request is genuinely signed by `org-a`'s app.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this matches the commit belonging to `org-b`'s tracked repository too, and writes a forged `success` status onto it, even though the webhook was only authenticated for `org-a`.
