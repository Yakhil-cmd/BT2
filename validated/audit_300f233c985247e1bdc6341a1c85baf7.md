### Title
`pallet-asset-conversion::do_add_liquidity` mints LP tokens based on the requested transfer amount instead of the actually-credited balance - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`Pallet::do_add_liquidity` calls `T::Assets::transfer(asset, who, &pool_account, amount, Preserve)?` for both legs of the pool deposit and discards the `Result`'s `Ok` value (the *actual* amount credited to the pool account), then uses the originally computed `amount1`/`amount2` to derive `lp_token_amount`. [1](#0-0) 
This is the FRAME analog of the reported ERC20 fee-on-transfer issue in Surge's `Pool.sol`: the caller-specified amount is trusted for downstream accounting instead of the amount actually received by the receiving account.

### Finding Description
`fungibles::Mutate::transfer` (implemented for `pallet-assets` via `do_transfer`/`transfer_and_die`) explicitly documents that it "Returns the actual amount placed into `dest`... Exact semantics are determined by the flags `f`," and the return value can be less than the requested `amount` due to dust-burning behavior in `prep_debit`/`prep_credit` (visible via `burn_dust`/`TransferFlags`) when an account's remaining balance falls below `min_balance`. [2](#0-1) [3](#0-2) 

In `do_add_liquidity`, the pool computes `reserve1`/`reserve2` before the transfer, computes the intended `amount1`/`amount2` to move, executes the transfers with `?` (discarding the returned actual-credited amount), and then computes `lp_token_amount` purely from the *intended* `amount1`/`amount2` (via `mul_div(&amount1, &total_supply, &reserve1)` or `calc_lp_amount_for_zero_supply`) rather than from the pool account's balance delta actually observed. [4](#0-3) 

If the actual amount credited to `pool_account` is less than `amount1`/`amount2` (e.g., because dust is burned during the transfer, or because a custom `T::Assets` implementation applies a transfer-time deduction the same way an ERC20 fee-on-transfer token would), the pool mints LP tokens as if the full intended amount was deposited while the pool's real reserves increased by less. This creates an accounting mismatch: the LP-token/reserve ratio used for minting is inflated relative to the assets actually held, allowing a subsequent liquidity provider or remover to redeem more of the underlying assets than were actually contributed by the affected depositor — precisely the "user gets more minted tokens than they should" invariant violated in the original report.

Note: I could not fully verify inside this session whether the default/standard `pallet-assets` configuration used by `T::Assets` in `asset-conversion`'s reference runtimes can realistically produce actual < requested under normal (non-privileged) conditions purely from `prep_debit`/`prep_credit` dust logic without keep-alive or additional configuration (e.g., custom `Freezer`/`Extra` hooks). I was not able to retrieve the bodies of `prep_debit`/`prep_credit` before running out of tool calls, so the exact conditions under which `credit < debit` occurs in the shipped configuration remain unconfirmed.

### Impact Explanation
If a discrepancy between the requested and the actually-credited transfer amount can be produced by any permissionless action (e.g., an attacker deliberately triggering dust burn on their own account, or supplying an asset kind whose `T::Assets` transfer implementation under-credits the destination), the attacker can mint LP tokens that are not fully backed by the pool's actual reserves. This directly threatens the solvency of `pallet-asset-conversion` pools — other liquidity providers' redeemable share is diluted. This is a bounded, single-pallet accounting issue (not chain-halting or unbounded), consistent with a Medium severity classification, matching the original report's rating.

### Likelihood Explanation
Likelihood depends entirely on whether the configured `T::Assets`/`T::PoolAssets` implementation can produce `actual transferred < requested amount` under normal, permissionless operation. For the "vanilla" `pallet-assets` implementation this requires a code path where `prep_credit`'s dust-burn logic (or similar) reduces the destination credit below the debited amount without any admin/root involvement — this specific path was not confirmed in this session. This finding should be treated as **unconfirmed / requires further investigation** rather than proven exploitable, since the trust boundary (discarding `T::Assets::transfer`'s return value) is confirmed in code, but a concrete attacker-triggerable discrepancy path in the currently wired `T::Assets` implementation was not proven.

### Recommendation
Use the actual amount returned by `T::Assets::transfer` (the `Ok(actual)` value) — or compute the pool account's balance delta before/after the transfer — as the basis for `lp_token_amount` calculation in `do_add_liquidity`, instead of the nominal `amount1`/`amount2`:

```rust
let actual1 = T::Assets::transfer(asset1, who, &pool_account, amount1, Preserve)?;
let actual2 = T::Assets::transfer(asset2, who, &pool_account, amount2, Preserve)?;
// use actual1/actual2 (or post-transfer balance deltas) for lp_token_amount math
```

### Proof of Concept
No executable PoC was produced. Reasoning to this point:
- Confirmed by static code reading that `do_add_liquidity` discards the `Ok` value of `T::Assets::transfer` and instead uses the pre-transfer requested amounts for LP minting math. [5](#0-4) 
- Confirmed by documentation/signature that `fungibles::Mutate::transfer`/`pallet-assets::do_transfer` can legitimately return an amount different from what was requested. [2](#0-1) 
- Was unable, within the remaining tool budget, to locate and read `prep_debit`/`prep_credit` bodies to confirm a concrete, permissionless attacker-triggerable scenario producing `actual < requested` in the reference runtime configuration, or to write/run an integration test exercising this gap.
- No test was executed against any node or public network; this is a static-analysis-only finding pending confirmation of a concrete trigger path, and should be treated with the caveats above.

	/// Reduces the asset `id` balance of `source` by some `amount` and increases the balance of
	/// `dest` by (similar) amount.
	///
	/// Returns the actual amount placed into `dest`. Exact semantics are determined by the flags
	/// `f`.
	///
	/// Will fail if the amount transferred is so small that it cannot create the destination due
	/// to minimum balance requirements.
	pub fn do_transfer(
		id: T::AssetId,
		source: &T::AccountId,
		dest: &T::AccountId,
		amount: T::Balance,
		maybe_need_admin: Option<T::AccountId>,
		f: TransferFlags,
	) -> Result<T::Balance, DispatchError> {
		let (balance, died) =
			Self::transfer_and_die(id.clone(), source, dest, amount, maybe_need_admin, f)?;
		if let Some(Remove) = died {
			T::Freezer::died(id.clone(), source);
			T::Holder::died(id, source);
		}
		Ok(balance)
	}
