### Title
`StatusHandler` binds attacker-controlled `state` to a victim's `Commit` by SHA alone, with no `repository.full_name` check, flipping `Commit#deployable?` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `Commit.where(sha: params.sha)`, never checking the webhook payload's `repository.full_name` against the matched commit's `stack.github_repo_name`. A webhook genuinely signed for one GitHub organization/repository can therefore write a `Status` (with attacker-chosen `state`/`context`) onto a `Commit` belonging to an entirely different stack/repository, flipping that commit's `Commit#deployable?` truth value.

### Finding Description
The binding that should hold is:
`commit.stack.github_repo_name == payload.dig('repository', 'full_name')` for every `Commit` a `status` webhook is allowed to mutate.

Tracing the code:
- `Shipit::WebhooksController#create` dispatches the raw parsed JSON to every registered handler for the event with no per-handler repository scoping: [1](#0-0) .
- `verify_signature` only proves the payload was signed by the webhook secret belonging to `repository_owner` (taken straight from the payload itself), i.e. it authenticates *which organization* sent the webhook, not which repository's data the handler is allowed to touch: [2](#0-1) .
- The base `Handler` class does define `repository_name`/`stacks` helpers that scope work to `Repository.from_github_repo_name(repository_name)`, and every `PullRequest::*Handler` uses this pattern: [3](#0-2) .
- `StatusHandler`, however, never calls `repository_name`/`stacks`. It matches commits solely by SHA, globally, across all stacks/repositories, and immediately writes a status from the attacker-controlled `params`: [4](#0-3) .
- `Commit#create_status_from_github!` and `Status.replicate_from_github!` persist the status using the matched commit's own `stack_id` (not anything derived from the payload's repository), so the write lands on the victim's real stack: [5](#0-4) [6](#0-5) .
- `Commit#deployable?` trusts `success?` which is derived from `state`, delegated straight from `status`: [7](#0-6) .

**Exploit path**: In a multi-tenant Shipit install (one `/webhooks` endpoint, multiple GitHub orgs each with their own `webhook_secret` per `Shipit.github(organization:)`), the attacker owns an organization/repo genuinely configured in Shipit. Because Git commit SHAs are content-addressed, an attacker can fork or otherwise host a repository that shares a commit object (identical SHA) with the victim's tracked repository — e.g., forking the victim's public upstream so early/shared commits have byte-identical SHAs. The attacker then uses their own GitHub token to set an arbitrary commit status (`state: success`, any `context`) on that shared SHA in *their own* repo. GitHub genuinely signs and delivers this `status` webhook to Shipit's `/webhooks` endpoint using the attacker's own org's `webhook_secret`. `verify_signature` passes legitimately (correct org, correct secret) because it only authenticates the sender org, not the target commit's ownership. `StatusHandler.process` then finds the victim's `Commit` row purely by SHA match and writes the attacker's `state` into it via `commit.create_status_from_github!`, using the victim commit's real `stack_id`. This flips `Commit#deployable?` to `true` on the victim's stack without ever contacting the victim's repository, without `Stack#ignore_ci?`, and without any real GitHub check run.

Existing guards do not stop this: `verify_signature` validates only the sender's org signature, not repository identity of the target record; the `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`, with no `repository.full_name` requirement enforced against the resolved commit; `drop_unhandled_event` and `check_if_ping` are irrelevant; `force_github_authentication`/`User#authorized?`/`require_permission!` don't apply to unauthenticated webhook ingestion; model validations on `Repository`/`Stack` don't constrain cross-repository status writes since none is performed by identity — only by SHA.

### Impact Explanation
A `Status` record with attacker-chosen `state`/`context`/`description` is written onto a commit belonging to a stack/repository the attacker does not control, which can flip `Commit#deployable?` from `false` to `true`, directly enabling an unauthorized deploy of that commit on the victim's stack (`Stack#next_expected_commit_to_deploy` / `Stack#next_commit_to_deploy` consult `deployable?`). This is a cross-tenant authorization-truth bypass matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable against any commit whose SHA the attacker can reproduce/share (most easily any commit present in both a public upstream and its fork), and the blast radius spans every stack/repository configured in the same multi-tenant Shipit instance, since the SHA-based lookup has no tenant boundary.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment where the attacker legitimately controls at least one configured GitHub org/repo (a realistic precondition for any self-serve/multi-tenant Shipit install, and the scenario the question explicitly frames — "webhook their own webhook_secret signs"); (2) a shared commit SHA between attacker-controlled and victim repositories, trivially achieved via forking a public upstream repository, which is common in open-source CI setups. No Shipit secrets, sessions, or API tokens are needed — only the attacker's own legitimate GitHub webhook delivery. Cost is low (one API call to set a status via the attacker's own token, on their own repo) and fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the payload's own repository, mirroring the pattern already used by the `PullRequest::*` handlers: resolve `repository_name` from `payload.dig('repository', 'full_name')`, look up `stacks` via `Repository.from_github_repo_name`, and constrain `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalently assert `commit.stack.github_repo_name == repository_name` before calling `create_status_from_github!`), discarding matches whose stack's repository does not equal the payload's repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "StatusHandler must not flip deployable? for a commit whose stack repository differs from payload repository" do
          victim_commit = shipit_commits(:fifth) # has no successful status, deployable? == false
          refute_predicate victim_commit, :deployable?

          attacker_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'repository' => { 'full_name' => 'attacker-org/attacker-repo' }
          }

          # Binding under test:
          assert_not_equal victim_commit.stack.repository.full_name,
                            attacker_payload['repository']['full_name']

          StatusHandler.call(attacker_payload)

          victim_commit.reload
          # Proof of bypass if this flips to true purely via a cross-repo signed payload:
          assert_predicate victim_commit, :deployable?
        end
      end
    end
  end
end
```
This test demonstrates that `StatusHandler.call` with a payload whose `repository.full_name` differs from `commit.stack.repository.full_name` still mutates `commit.statuses` and flips `Commit#deployable?`, with no live GitHub interaction, confirming the missing binding.

      verified = github_app.verify_webhook_signature(
