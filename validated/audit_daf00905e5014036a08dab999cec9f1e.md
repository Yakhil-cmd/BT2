### Title
Cross-organization webhook signature confusion allows unauthenticated write to another org's repository state - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In multi-tenant configurations (`config/secrets.*.yml` with multiple GitHub orgs, e.g. `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects which org's `webhook_secret` to verify against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login` as a fallback). The actual write-side logic in `Handlers::Handler#repository_name` (used by `PushHandler`, `StatusHandler`, etc. to resolve the `Repository`/`Stack` to act on) independently reads `payload.dig('repository', 'full_name')`. These are two separate JSON fields inside the same payload that are never cross-validated against each other. [1](#0-0) [2](#0-1) 

### Finding Description
The equality that must hold for this trust boundary to be sound is:

`org whose webhook_secret authenticated the request == org that owns the repository/stack the handler subsequently mutates`

`verify_signature` resolves the `GithubApp` (and thus the `webhook_secret` used for HMAC verification) purely from `repository_owner`: [3](#0-2) , with `repository_owner` reading `params.dig('repository', 'owner', 'login')` or falling back to `params.dig('organization', 'login')`: [4](#0-3) .

`Shipit.github_app.rb#verify_webhook_signature` returns `true` unconditionally whenever the resolved org's `webhook_secret` is blank: [5](#0-4) . The multi-tenant setup documented in `docs/setup.md` explicitly allows per-org `webhook_secret` to be left empty, and the shipped dummy fixtures (`test/dummy/config/secrets_double_github_app.yml`) demonstrate exactly this: both `OrgOne` and `OrgTwo` have `webhook_secret: # nil`.

Once the controller decides the request is "verified" (trivially true because the selected org has no secret), it passes the *entire* attacker-controlled JSON body to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [6](#0-5) . The handler base class then resolves the target repository for writes from a *different* field of the same payload — `repository.full_name` — without any re-check that it belongs to the org that was used for signature routing: [2](#0-1) .

Because `repository.owner.login` (used to pick the signing secret) and `repository.full_name` (used to pick the target `Repository`/`Stack`) are independent, attacker-controlled strings in the same unsigned/unauthenticated JSON body, an attacker can set `repository.owner.login` (or `organization.login`) to the login of an org configured with a blank `webhook_secret`, while setting `repository.full_name` to `"other-org/some-tracked-repo"` belonging to a *different*, securely configured org. `verify_signature` will approve the request (no HMAC required for the blank-secret org), and `PushHandler`/`StatusHandler` will then act on the victim org's repository/stack — e.g. triggering `stack.sync_github(expected_head_sha: ...)` or forging a commit `status` via `commit.create_status_from_github!(params)` — for a repo the attacker never authenticated against.

This is the direct analog of the audited bug class: a field the trust decision is based on (`repository.owner.login`/`organization.login`, analogous to the mis-referenced struct field) diverges from the field actually acted upon (`repository.full_name`, analogous to the unconstrained `sqrtPriceLimitX96`), because the code never enforces that both fields describe the same entity.

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written." An unprivileged network attacker who knows (or guesses) that at least one configured GitHub org has no `webhook_secret` set — which the engine's own documentation and shipped fixtures show is an explicitly supported configuration — can inject forged webhook events (`push`, `status`, `check_suite`, `membership`) that get processed against any tracked repository/stack in the installation, regardless of which org it belongs to. This can trigger unwanted `GithubSyncJob` runs, forge commit CI statuses via `StatusHandler`, or create memberships/teams, all without ever presenting a valid signature for the target org. Depending on downstream deploy-gating logic that consults commit statuses, this can contribute to an unauthorized deploy pathway.

### Likelihood Explanation
Requires only that the Shipit instance is configured with the multi-org GitHub app schema and that at least one configured org has an empty `webhook_secret` — a state the project's own setup docs and dummy secrets fixtures present as normal/expected (webhook secret is described as "optional"). No credentials, tokens, or privileged access are needed; the attacker only needs to know one org's login string and reach the public `/webhooks` endpoint.

### Recommendation
When resolving the `repository_owner` used for signature verification, require it to be consistent with the repository actually processed by handlers, and require every configured org to have a non-empty `webhook_secret` (or globally require a secret) before webhook payloads are dispatched. `Handler#repository_name`/`stacks` should re-validate that the resolved repository's owner matches the org context under which the request was authenticated, rather than trusting an independently-controlled JSON field.

### Proof of Concept
Configuration (multi-org, as shown in `test/dummy/config/secrets_double_github_app.yml`):
```
github:
  OrgOne:
    webhook_secret: # nil
  OrgTwo:
    webhook_secret: <real-secret>
```
Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": { "login": "OrgOne" },
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "ref": "refs/heads/main",
  "after": "deadbeef..."
}
```
- `WebhooksController#repository_owner` resolves to `"OrgOne"`, so `Shipit.github(organization: "OrgOne")` is used and, since `OrgOne`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of any signature header (or lack thereof).
- `PushHandler` (via `Handler#repository_name`) reads `repository.full_name` = `"OrgTwo/victim-repo"`, looks up that `Repository`, and calls `stack.sync_github` on `OrgTwo`'s stack — an action never authorized by any secret belonging to `OrgTwo`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
