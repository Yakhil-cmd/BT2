### Title
Cross-organization webhook forgery — signing organization is not bound to the repository acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to use for HMAC verification based on an attacker-supplied field of the payload (`repository.owner.login`, falling back to `organization.login`), but every event handler that actually mutates state (`Repository`, `Stack`, `Commit`) looks up its target using a *different* attacker-supplied field of the same payload: `repository.full_name` [1](#0-0) . In a Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration [2](#0-1) ), this breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [3](#0-2) [4](#0-3) 

`Shipit.github(organization: repository_owner)` resolves a distinct `webhook_secret` per configured organization [5](#0-4) , and `verify_webhook_signature` only proves that *some* valid HMAC was produced with *that particular* organization's secret over the raw body [6](#0-5) .

Crucially, `repository.owner.login` (used to pick the secret) and `repository.full_name` (used later to select which `Repository`/`Stack` is mutated) are two independent, attacker-controlled JSON fields inside the same signed body — nothing forces them to refer to the same repository/organization. Every handler resolves its target purely from `full_name`: [1](#0-0) 
and `Repository.from_github_repo_name` just splits that string on `/` with no cross-check against the verified organization: [7](#0-6) 

Concretely, an attacker who possesses the legitimate `webhook_secret` for OrgA (e.g. because they are able to configure/observe webhooks for a repo they control under OrgA, which is installed on the same shared Shipit instance as OrgB) can craft a raw JSON body such as:
```json
{
  "repository": { "owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>"
}
```
and HMAC-sign it with OrgA's `webhook_secret`. `verify_signature` selects OrgA's app/secret (because `repository.owner.login == "OrgA"`), the signature checks out, and the request is accepted. The `PushHandler` (and other handlers) then act on `full_name = "OrgB/victim-repo"`: [8](#0-7) 
This is possible because `StatusHandler`, `PushHandler`, `MembershipHandler`, `CheckSuiteHandler` and the pull-request family of handlers all resolve their target repo strictly via `full_name`/`Repository.from_github_repo_name`, e.g.: [9](#0-8) 

The `StatusHandler` is the most severe instance: it applies a forged commit status to *any* existing commit matching `params.sha`, across all stacks, regardless of which organization actually owns that commit's repository: [10](#0-9) 
If the targeted stack has `continuous_deployment` enabled and relies on that status context as a required check, this forged status can be the trigger that starts an automatic deploy of a real commit in a repository the attacker does not control and for which they never possessed a valid signing secret.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose secret validated the webhook" and "the organization/repository the webhook is allowed to affect." In the accepted-impact taxonomy this reaches:
- Cross-repository writes: an attacker signing with OrgA's secret can create/mutate `Commit`/`Status`/`Stack` records that belong to OrgB.
- Potential unauthorized deploy: a forged `status` event can satisfy a required CI check on a victim stack with `continuous_deployment` enabled, causing Shipit to autonomously trigger a deploy of an existing commit without any legitimate signal from OrgB.

This qualifies as Critical under the rules ("cross-repository writes... or an unauthorized deploy").

### Likelihood Explanation
Requires only that the attacker legitimately possesses a `webhook_secret` for *any one* GitHub organization/app configured on the shared Shipit instance (the documented multi-org setup) — no privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repo is needed. Constructing the forged payload/HMAC is trivial once the secret is known; the only additional requirement for the deploy-trigger variant is that the victim stack has `continuous_deployment` enabled and the forged status context matches a required/blocking status, which is a fairly common configuration.

### Recommendation
Bind the verified organization to the resource actually acted upon: after `verify_signature` succeeds, derive `repository_owner` and pass it (or the resolved `GitHubApp`) explicitly into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }`, and have `Handler#stacks`/`#repository_name` assert that the owner segment of `payload.dig('repository','full_name')` matches `verified_organization` before performing any lookup, rejecting (422) the request otherwise.

### Proof of Concept
1. Configure Shipit for two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. Attacker knows `OrgA`'s `webhook_secret` (e.g. from a webhook they legitimately manage under OrgA).
3. Attacker builds body:
```json
{"sha":"<victim commit sha in OrgB>","state":"success","context":"required-ci","repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/victim-repo"}}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and sends `POST /github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully against OrgA's secret.
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (belonging to OrgB's stack) and calls `create_status_from_github!`, potentially satisfying a required check and triggering an unauthorized continuous deployment on OrgB's stack — despite the attacker never possessing OrgB's `webhook_secret`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
