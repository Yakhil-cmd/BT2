Cross-organization team-membership forgery via unscoped `github_id` lookup in `MembershipHandler#process` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only verifies that a webhook is signed with the secret belonging to `params.dig('organization', 'login')`, then dispatches to `MembershipHandler#process`, which looks up the target `Team` solely by `params.team.id` with no check that the team actually belongs to the organization that signed the request. Any organization configured in Shipit's multi-tenant `github:` config can therefore forge `membership` webhooks (signed with its own legitimate webhook secret) that add or remove members on a `Team` belonging to a completely unrelated organization, directly mutating `Shipit::Membership` rows that gate `User#authorized?` and thus `Shipit.github_teams` access.

### Finding Description
The binding that should hold is: **for every `Membership` mutation of a team `T` where `T.organization ∈ Shipit.github_teams`'s orgs, the webhook that triggered it must have been signed by GitHub on behalf of `T.organization`'s own installation** — i.e. `signing_org == T.organization`. Both branches of `MembershipHandler#process` violate this.

Trace:
1. `WebhooksController#create` parses the raw body and dispatches to handlers for the `X-Github-Event` header value [1](#0-0) .
2. `verify_signature` derives `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and validates the HMAC using `Shipit.github(organization: repository_owner)`'s own `webhook_secret` [2](#0-1) [3](#0-2) . `verify_webhook_signature` is a pure HMAC-SHA1 comparison against that organization's own secret [4](#0-3) . This proves only "this payload was signed by *some organization X configured in Shipit*" — it says nothing about whether the `team`/`member` referenced inside the payload actually belongs to organization X.
3. `MembershipHandler#process` then resolves the target team purely via `Team.find_or_create_by!(github_id: params.team.id)`, and mutates membership based on `params.action` [5](#0-4) . Nowhere is `params.organization.login` checked against the found team's `organization` attribute for an *existing* team (the `organization:` assignment inside the `find_or_create_by!` block only fires on creation, not on lookup of a pre-existing team) [6](#0-5) .
4. `Team#add_member` / `team.members.delete(member)` directly create/destroy `Shipit::Membership` rows [7](#0-6) , and these rows are exactly what `User#authorized?` consults to decide `Shipit.github_teams` membership: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) .

Exploit flow: an attacker who administers organization "Attacker-Org" (a legitimate, unrelated tenant configured in Shipit's multi-org `github:` secrets, per the documented multi-org setup [9](#0-8) ) knows their own org's `webhook_secret`. They send two POSTs to `/webhooks` with `X-Github-Event: membership`, `organization.login = "Attacker-Org"` (so `verify_signature` checks against their own known secret and passes), but `team.id` set to the numeric GitHub ID of the target's privileged team (already present in Shipit's DB from a prior legitimate sync). First payload: `action: "added"`, `member.login` = attacker-controlled user X → grants X membership on the privileged team. Second payload, before any `teams:fetch`/`refresh_members!` reconciliation: `action: "removed"`, `member.login` = victim Y already legitimately on that team → deletes Y's `Membership`. Both requests pass signature verification because the signature is validated against "Attacker-Org"'s own secret, not against the team's actual organization.

`drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of `action`, `team.id/name/slug/url`, `organization.login`, `member.login` — none of them cross-check organization vs. team ownership [10](#0-9) . `force_github_authentication`, `User#authorized?`, and `require_permission!` are irrelevant here since this is an unauthenticated webhook endpoint, not a session-based request.

### Impact Explanation
This is a direct authorization escalation into `Shipit.github_teams` (grant) combined with deauthorization/lockout of a legitimate user (revoke), executed purely through a webhook signed by an unrelated, unprivileged organization's own key. Impact matches the "High - escalation into `Shipit.github_teams` authorization" category (and arguably crosses into account takeover/denial of legitimate operator access, since revoking Y's membership can immediately deauthorize an active session-holder from privileged actions gated by `authorized?`/team checks). The attack is repeatable against any `Team.github_id` known or guessable by the attacker, and works across every tenant present in the multi-org Shipit config, so the blast radius spans all organizations sharing one Shipit instance.

### Likelihood Explanation
Preconditions: Shipit must be configured for multiple GitHub organizations (the documented multi-org `github:` config), the attacker must control one of those configured (but otherwise unrelated/unprivileged) organizations well enough to know its `webhook_secret`, and the attacker must know the target team's numeric `github_id` (these are typically discoverable via the GitHub API/UI for teams the attacker can view, or simply by observing prior webhook deliveries/Shipit UI). Attacker cost is low: two crafted HTTP POSTs with a valid HMAC computed from a secret they legitimately possess. No GitHub App private key, `secret_key_base`, or Shipit session is required, satisfying the stated attacker capability model. The race window ("before `teams:fetch`/`refresh_members!` reconciles") is real but not strictly required for the grant of X — periodic reconciliation would eventually revert unauthorized state, but the window between forged webhook and the next scheduled `teams:fetch` run is exploitable in practice.

### Recommendation
In `MembershipHandler#process` (and `find_or_create_team!`), verify that the resolved `Team#organization` equals `params.organization.login` before applying any membership mutation to a pre-existing team; reject (or safely no-op/log) the event otherwise. More generally, `verify_signature` should validate that the organization asserted inside a payload used for authorization-affecting mutations matches the organization whose secret validated it, for every handler that touches `Team`/`Membership` records — not only rely on secret-lookup-by-claimed-org.

### Proof of Concept

3. 4. POST membership webhook #1: `X-Github-Event: membership`, body `{action: "added", team: {id: 999, name:"Core", slug:"core", url:"..."}, organization: {login:"attacker-org"}, member: {login:"attacker_x"}}`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
