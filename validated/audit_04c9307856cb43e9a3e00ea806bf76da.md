### Title
Stack-scoped CCMenu token grants unauthenticated read access to *any* stack's deploy XML - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup used by every other API controller, replacing the tenant-scoped `stacks.from_param!(params[:stack_id])` with the unscoped `Stack.from_param!(params[:stack_id])`. As a result, a CCMenu token that is only supposed to authorize `read:stack` for the stack it was minted for can be replayed against `/stacks/:other_stack_id/ccmenu.xml?token=<t>` to read any other stack's build/deploy status.

### Finding Description
The broken binding is:
`current_api_client.stack_id == stack_id_of(record returned by #stack)`

In `Shipit::Api::BaseController` this binding is enforced everywhere via the `stacks` helper: [1](#0-0) 
`stacks` restricts the resolvable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` carries a `stack_id`, and `stack` calls `stacks.from_param!`. This is the mechanism by which a stack-scoped `ApiClient` (a supported feature: `belongs_to :stack, optional: true` on `Shipit::ApiClient`) is prevented from touching stacks other than the one it was issued for.

`CCMenuController`, however, defines its own `stack` method that bypasses this scope entirely: [2](#0-1) 
`Stack.from_param!(params[:stack_id])` looks the stack up in the global `Stack` table, ignoring `current_api_client.stack_id` completely.

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which checks the string `"read:stack"` against `permissions` and never touches `stack_id`: [3](#0-2) 

So any valid CCMenu token — including one deliberately scoped to a single stack via `ApiClient#stack_id` — passes `require_permission!` and then resolves `params[:stack_id]` against the *entire* `Stack` table instead of the token's authorized subset. The attacker's request is simply:
`GET /stacks/<victim_stack>/ccmenu.xml?token=<valid CCMenu token for stack A>`
and it returns HTTP 200 with the victim stack's deploy/rollback XML (`shipit/ccmenu/project` view built from `stack.deploys_and_rollbacks.last`), because `CCMenuController#stack` never checks that `<victim_stack>` belongs to the token's authorized set.

None of the existing guards catch this: `authenticate_api_client` only validates the token signature, `check_permissions!` only checks the permission string, and the one control that would have prevented cross-stack access (`stacks.from_param!`) is exactly the method this controller does not use.

### Impact Explanation
An attacker who obtains any single valid CCMenu token/URL (these are routinely embedded in public CI dashboards, wiki pages, or CCTray widgets, matching the "wiki page" context this question originated from) can enumerate and read the deploy/task status of every stack in the Shipit instance, not just the one the token was issued for. This is unauthenticated cross-tenant read of stack/deploy state, matching the High severity bucket ("unauthenticated read of stack state, task streams or deploy output"). The attack is trivially repeatable against arbitrary `stack_id` values and costs nothing beyond guessing/enumerating stack slugs.

### Likelihood Explanation
Preconditions: the attacker needs one valid CCMenu token (obtained via a legitimately shared/leaked CCMenu URL for any stack — these URLs are designed to be embedded in public status-monitoring tools) and knowledge of the target stack's `to_param` (repo owner/name/branch), which is generally public/guessable information in a Shipit deployment. No GitHub secrets, sessions, or special privileges are required once a single CCMenu URL is known. This makes the exploit low-cost and highly feasible in any deployment that uses per-stack scoped API clients or where CCMenu URLs are shared externally.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and rely on the base controller's scoped `stacks.from_param!(params[:stack_id])`, so CCMenu tokens are held to the same `current_api_client.stack_id` restriction as every other API endpoint.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's ccmenu.xml" do
  stack_a = Stack.create!(repository: Repository.new(owner: "foo", name: "a"), branch: 'main')
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "b"), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped CCMenu Client',
    stack: stack_a,
    permissions: %w[read:stack],
  )

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Binding under test: current_api_client.stack_id (stack_a.id) must equal
  # the id of the stack actually rendered (stack_b.id) -- it must NOT.
  assert_response :forbidden # or :not_found — must not be 200 with stack_b's data
end
```
Running this against current code shows `assert_response :ok` with `stack_b`'s XML payload, confirming the cross-stack leak.
