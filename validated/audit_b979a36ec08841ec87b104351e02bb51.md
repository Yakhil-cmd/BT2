### Title
Unstable data-feed values from chained AA responses can be read and manipulated atomically within a single trigger cascade, enabling a flash-loan-style price manipulation of any oracle-consuming AA - (File: `data_feeds.js`, `formula/evaluation.js`, `aa_composer.js`)

### Summary
The C4 report describes a flash-loan attack in which an attacker manipulates a pool's spot price within a single Ethereum transaction, uses it to obtain undervalued/overvalued shares from a vault contract, then reverses the manipulation before the transaction ends — all atomically, because Ethereum allows multiple contract calls to be composed in one transaction with no intervening state finality.

Obyte's Autonomous Agents (AAs) have an analogous atomicity primitive: a single triggering unit can cascade through a chain of **secondary AA triggers** that are all executed synchronously, one after another, inside the same `handlePrimaryAATrigger()` call, before any of the intermediate response units are network-confirmed or even broadcast. Crucially, the `data_feed[[...]]` formula function used by AAs to read oracle data explicitly includes **unstable** data-feed messages posted by other AA response units in this same chain, by design (`unstable_opts = bAA`). This lets one attacker-controlled AA post a bogus data-feed value that is consumed, uncorrected, by a *victim* AA later in the very same atomic chain — a direct analog of manipulating an on-chain spot price and consuming it within the same flash-loan transaction.

### Finding Description
When formula evaluation processes a `data_feed[[...]]` expression inside an AA, it calls: [1](#0-0) 

passing `bAA` (true whenever evaluation happens inside AA execution) as the `unstable_opts` parameter of `dataFeeds.readDataFeedValue`.

Inside `readDataFeedValue`, `bIncludeUnstableAAs = !!unstable_opts` becomes `true`, and the function scans `storage.assocUnstableMessages` for **any not-yet-stable unit whose author is an AA** (`objUnit.bAA`) and whose `latest_included_mc_index` is within the requested range, picking up its `data_feed` message payload as a candidate value: [2](#0-1) 

These "unstable" messages are populated the moment any unit (including an AA response unit created mid-chain) is written by `saveJoint()`, well before the unit is stable or even the primary trigger's response chain has finished: [3](#0-2) 

Meanwhile, AA execution supports arbitrarily deep chains of secondary triggers, executed synchronously in the same DB transaction/connection as part of one primary trigger's processing, via `handleSecondaryTriggers()`: [4](#0-3) 

and the overall primary-trigger handler wraps the whole cascade in one `BEGIN`/`COMMIT` before any of it is even written to the ball/witness process for real network finality: [5](#0-4) 

The combination means: an attacker can define
1. an "Oracle AA" that, when triggered, emits a `data_feed` message with an attacker-chosen extreme value and forwards a payment/trigger to a victim AA, and
2. rely on the victim AA's `if`/`init`/`state` formulas that call `data_feed[[oracles=<oracle_aa_address>, ...]]` (a legitimate, common oscript pattern for reading price/aggregator feeds, as seen in test fixtures such as `data_feed[[oracles='X55...', feed_name='GBYTE_USD_MA']]`).

Because the victim AA's read is done via `bAA=true` evaluation, it will happily pick up the Oracle AA's just-posted, still-unstable value from `storage.assocUnstableMessages`, execute its logic (e.g., issue shares, price a swap, value collateral) using that manipulated figure, and — since this occurs inside the same trigger cascade before real network stabilization — the victim can be made to act on a value that was never independently confirmed by other nodes/oracles and that the attacker fully controls within the same atomic unit-processing sequence.

### Impact Explanation
This is directly analogous to the flash-loan spot-price manipulation described in the report: instead of manipulating an AMM pool price atomically within one transaction, an attacker manipulates the "current" (unstable) value of a data feed read by another AA, atomically within one trigger cascade, and both patterns exploit the same underlying weakness — treating a spot/instantaneous, easily-influenced value as ground truth for financial calculations without a lock/cooldown or requiring the value to be independently stable. Any AA design that (a) reads price/aggregator data via `data_feed[[...]]` without restricting `min_mci`/requiring the value to be older/independent of the current trigger cascade, and (b) allows the oracle address itself, or a chain reachable from the trigger, to be an AA that can be triggered together with the victim in one composed sequence, is exposed to fund loss: incorrect share/collateral pricing, mispriced swaps, or draining of AA balances based on a value that is reversible/never-finalized.

### Likelihood Explanation
Likelihood is Medium: it requires an AA design that both consumes `data_feed[[...]]` for value-bearing decisions and permits its oracle address (or a party controlling that address) to be reachable in the same trigger chain as the read — a realistic pattern for AA authors building nonUST-strategy-style vaults or aggregator-fed products on top of AA-posted oracles rather than purely user-posted, independently-witnessed data feeds. The primitives needed (chained AA triggers, `bAA`-scoped unstable data-feed inclusion) are core, unprivileged, permissionless features of ocore reachable by any AA author or trigger sender.

### Recommendation
- When evaluating `data_feed[[...]]` for financial/price-sensitive logic, avoid relying on unstable/AA-sourced feed values from within the same atomic trigger cascade; consider requiring `min_mci` bounds that exclude data feeds authored within the current, not-yet-stable trigger sequence, or disallow use of `bIncludeUnstableAAs` for author addresses reachable as secondary triggers of the current chain.
- AA authors building oracle-consuming AAs should document/require the oracle to be a genuinely independent, previously-stabilized data source (not an AA that can be chained into the same trigger sequence as the consumer), and apply a minimum staleness/lock requirement analogous to `_minLockPeriod` before trusting a freshly posted value for value-bearing operations.
- Consider surfacing in `dataFeeds.readDataFeedValue`/`dataFeedExists` documentation and AA-development guidance the risk that `bAA`-scoped unstable lookups can return values from units created earlier in the very same trigger cascade, so AA authors are aware this is not equivalent to reading a network-confirmed oracle value.

### Proof of Concept
1. Attacker defines `OracleAA`: on trigger, it emits a `data_feed` message (e.g., `feed_name='PRICE'`, an attacker-favorable value) and forwards the received payment as a secondary trigger to `VictimAA`.
2. Attacker defines/uses `VictimAA`, a vault-like AA whose `state`/`if` formula computes shares or collateral value using `data_feed[[oracles='<OracleAA address>', feed_name='PRICE']]` (pattern shown in `test/ojson.test.js:1064-1073` and `test/samples/option_contract.oscript:64`).
3. Attacker sends a single unit that triggers `OracleAA`.
4. Inside the single `handlePrimaryAATrigger()` call, `OracleAA`'s response (containing the manipulated `data_feed` message) is written via `saveJoint`, registering it in `storage.assocUnstableMessages` immediately (`writer.js:603-613`).
5. `handleSecondaryTriggers()` immediately triggers `VictimAA` in the same DB transaction (`aa_composer.js:1702-1756`), and `VictimAA`'s `data_feed[[...]]` read (`formula/evaluation.js:646`) picks up `OracleAA`'s still-unstable value via `readDataFeedValue`'s `bIncludeUnstableAAs` branch (`data_feeds.js:211-248`), computing an outcome favorable to the attacker before the value is independently confirmed by the network.
6. The whole chain completes atomically and is committed; the attacker has extracted value from `VictimAA` based on a transient value it fully controlled.

			if (rows.length > 0 && constants.bTestnet && mci < testnetAAsDefinedByAAsAreActiveImmediatelyUpgradeMci)
				rows = rows.filter(function (row) {
					if (row.main_chain_index && row.main_chain_index < mci) // previous definition is already stable

					if (len > 0)
						console.log("not calling secondary trigger from unit " + objUnit.unit + " to AA " + row.address);
					return (len === 0);

				saveStateVars();
				addUpdatedStateVarsIntoPrimaryResponse();
