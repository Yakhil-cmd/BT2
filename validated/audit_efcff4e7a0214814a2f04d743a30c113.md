### Title
Webhook signature is verified against `repository.owner.login`, but every handler acts on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App config (and thus the webhook secret used to verify `X-Hub-Signature`) using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Every event handler, however, resolves the `Stack`/`Repository` to mutate using a completely different field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `Handler#stacks`. Signature verification therefore authenticates one identifier while every write operates on another, unrelated identifier taken from the same untrusted, attacker-controlled JSON body.

### Finding Description
`verify_signature` in [1](#0-0)  computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)` to obtain the `GitHubApp` (and its `webhook_secret`) used to validate the signature: [2](#0-1) .

`GitHubApp#verify_webhook_signature` explicitly bypasses verification when no secret is configured for that organization: `return true unless webhook_secret` in [3](#0-2) . `github.webhook_secret` is documented as optional in `docs/setup.md`, and multi-org configs (`Shipit.github_app_config`) allow per-organization entries, some of which may have no secret configured at all: [4](#0-3) .

Meanwhile, every webhook `Handler` locates the target `Stack`/`Repository` to write to using a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) .

Both `repository.owner.login` (used for auth) and `repository.full_name` (used for the write) are attacker-controlled fields inside the same unsigned-until-verified JSON body — nothing binds them together. An attacker who can obtain a validly-signed (or unsigned, if the org has no webhook secret) delivery for *any* organization configured in Shipit can set `repository.full_name` to `victim-org/victim-repo` while keeping `repository.owner.login` equal to their own (secret-less or attacker-known-secret) organization. `verify_signature` will authenticate against the attacker's own org config and pass, while the actual handler — e.g. `push` triggering `GithubSyncJob` (`app/jobs/shipit/github_sync_job.rb`) — will look up and mutate the victim repository's `Stack` via `Repository.from_github_repo_name(repository_name)`, appending fabricated commits, or the `membership`/`status`/`check_suite` handlers will write into the victim's data using the victim's `full_name`.

This exactly matches the class of bug in the external report: a security check is scoped to one field/entity (`AccessControlManager.botMethodsPaused()` gating almost every bot function but not `deleteActiveValidators`), while the actually-affected entity is different from what the check covers. Here, the "organization that authenticated" (`repository.owner.login`) is not the same as "the repository that is written" (`repository.full_name`).

### Impact Explanation
This breaks the binding `organization authenticated == repository written`, allowing an attacker who controls webhook delivery for any single configured GitHub organization (especially one with no `webhook_secret` set, which is an explicitly supported/documented configuration) to forge push/status/check_suite/membership events that are attributed to and mutate a completely different, victim organization's stack/repository records tracked by the same Shipit instance. This can lead to spoofed commits/statuses/check runs being recorded against a victim's stack and processed by the deploy pipeline (`GithubSyncJob`, `CacheDeploySpecJob`), i.e., cross-repository writes.

### Likelihood Explanation
Requires the Shipit instance to be configured with multiple GitHub organizations (the multi-org schema is a supported, documented configuration in `docs/setup.md`), and requires the attacker to control (or be able to trigger) genuine webhook deliveries for at least one of the configured organizations — e.g. one where they administer the GitHub App installation or where `webhook_secret` is left blank (explicitly optional per docs). Given webhook secrets are marked optional and multi-org support exists in the code, this is a realistically reachable misconfiguration-adjacent path rather than a purely theoretical one.

### Recommendation
Bind the field used for signature/organization verification to the field used for the actual write. Either verify the signature using the target repository owner exactly as resolved by `Handler#repository_name` (i.e., derive both from `full_name`), or re-validate inside each handler that the resolved `Stack`/`Repository`'s owner matches the same organization whose secret verified the signature, rejecting the payload otherwise.

### Proof of Concept
1. Shipit is configured with two GitHub orgs: `attacker-org` (no `webhook_secret` configured, or one the attacker knows) and `victim-org` (tracked stack `victim-org/victim-repo`, with its own secret).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` computes `repository_owner = "attacker-org"`, loads `attacker-org`'s `GitHubApp`, and since `webhook_secret` is nil for that org, `verify_webhook_signature` returns `true` unconditionally, regardless of `X-Hub-Signature` [3](#0-2) .
4. The `push` handler resolves the target using `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [6](#0-5) , enqueuing `GithubSyncJob` against the victim's real `Stack`, causing Shipit to fetch and append attacker-influenced commit data into the victim's deploy history.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
