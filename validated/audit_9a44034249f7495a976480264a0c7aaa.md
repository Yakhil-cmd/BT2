### Title
Byte-position diff truncation in `cap_diff_for_prompt` lets attacker-controlled padding push dangerous hunks/files out of the review prompt - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`cap_diff_for_prompt` truncates diff content by raw byte position (`content[:DIFF_PER_FILE_BYTES]`) and drops whole files once a running total exceeds `DIFF_TOTAL_BYTES`, with no awareness of where the actual `+` (added) lines or high-risk paths sit. An attacker who controls diff content (their own commit/PR, or an AI agent that was prompt-injected into writing the diff) can pad a file with large benign content before the dangerous hunk, or place several bulky files ahead of the dangerous one in the diff, so the truncation/omission boundary lands exactly before the exploit-relevant lines, silently removing them from what the review model ever sees.

### Finding Description
`cap_diff_for_prompt` in [1](#0-0)  caps each file's content to `DIFF_PER_FILE_BYTES` (80,000) and the running total to `DIFF_TOTAL_BYTES` (400,000), cutting content strictly by byte offset and appending a truncation marker, or replacing the whole file with an "omitted" placeholder once the total budget is exhausted. There is no logic that prioritizes hunks/lines containing `+` (new code) or high-risk path tokens within this function — unlike `_prioritize_diff_files` in [2](#0-1) , which only reorders whole files by risk score and only runs when the *file count* exceeds `MAX_DIFF_FILES` (30).

This creates two exploitable gaps:
1. **Intra-file**: an attacker fully controls the diff content of their own changed file (e.g., a large reformat/data-literal hunk placed before the actually dangerous hunk). Since `cap_diff_for_prompt`/`_cap_files_for_prompt` (identical logic in [3](#0-2) ) slices at a fixed byte offset regardless of hunk boundaries, padding >80,000 bytes before the dangerous hunk truncates it out of the prompt entirely.
2. **Inter-file**: when the file count is within `MAX_DIFF_FILES` (so `_prioritize_diff_files` never runs), file order going into `cap_diff_for_prompt` is whatever `parse_diff_into_files` produced (git's diff order, e.g. path order) — not risk-sorted. Padding earlier files to consume the shared 400,000-byte total budget causes the later, genuinely dangerous file to be replaced wholesale with `[omitted by security-guidance: total diff byte cap reached]`.

Both paths are reached from every LLM-review entrypoint that assembles a prompt from `diff_files`: `build_investigate_prompt` ( [4](#0-3) ) for the agentic commit reviewer, and the single-shot `analyze_security_concerns`/`agentic_review` paths in `llm.py` ( [5](#0-4) , [6](#0-5) ), all of which are driven by attacker-influenceable diff text (commit-review, push-sweep, Stop-hook flows in `security_reminder_hook.py`).

Existing defenses don't cover this: the self-refute prompt ( [7](#0-6) ) is designed to resist injected *safety claims inside visible diff text*, and `_prioritize_diff_files` mitigates *over-cap file-count* scenarios by risk-sorting whole files — but neither addresses byte-position truncation cutting off content the model never receives in the first place. If the dangerous lines are never in the prompt, there is nothing for stage 1 (investigate) to find, and stage 2 (self-refute) never runs on it.

### Impact Explanation
This breaks the stated invariant that "prompt assembly must not let untrusted repo content suppress review of dangerous changes." An attacker who can shape a diff (directly as a contributor, or indirectly by prompt-injecting an agent that writes the diff) can make the security reviewer silently skip the actual vulnerable code while the diff still appears fully processed (no error, review completes normally with e.g. `findings: []`), giving false assurance and allowing dangerous code to land unreviewed.

### Likelihood Explanation
Feasible and repeatable: it only requires crafting a diff with a large low-risk hunk/file preceding the real change, well within normal commit sizes for generated code, minified assets, large data literals, or verbose reformatting — none of which is unusual or requires any privilege beyond authoring a commit/PR that the plugin will review.

### Recommendation
Make truncation risk-aware instead of purely byte-positional:
- Within `cap_diff_for_prompt`/`_cap_files_for_prompt`, prioritize retaining hunks that contain `+` lines (and hunks matching `_SECURITY_RISK_PATH_TOKENS`-style content) when truncating a single file's content, rather than always keeping the first N bytes.
- Sort `diff_files` by the same risk heuristic used in `_prioritize_diff_files` before applying the total-byte cap, not only when the file count exceeds `MAX_DIFF_FILES`, so the highest-risk files are packed into the budget first regardless of count.
- When a file/hunk is truncated or omitted, surface a structured signal (not just inline text) so downstream metrics/telemetry can flag "possible evasion via padding" for manual follow-up.

### Proof of Concept
Unit test plan against `cap_diff_for_prompt`:
1. Construct `content = "+" + ("x" * 90000) + "\n+DANGEROUS: os.system(user_input)\n"` for a single file `evil.py` — over `DIFF_PER_FILE_BYTES` (80,000), with the dangerous `+` line placed after the cutoff.
2. Call `cap_diff_for_prompt([("evil.py", content)])` and assert the returned content does **not** contain `"DANGEROUS: os.system"` — demonstrating the dangerous added line is silently dropped rather than prioritized.
3. Construct multiple files `[("a.py", "x"*200000), ("b.py", "x"*200000), ("z_target.py", "+DANGEROUS: eval(user_input)\n")]` totaling >`DIFF_TOTAL_BYTES`, call `cap_diff_for_prompt`, and assert `z_target.py`'s returned content is the `"[omitted by security-guidance: total diff byte cap reached]"` placeholder — demonstrating the genuinely dangerous file is dropped wholesale due to file ordering rather than risk.
4. Expected (fixed) behavior: both assertions should instead show the dangerous `+` line/file is retained (or, at minimum, other lower-risk content is truncated first), proving truncation is risk-aware rather than position-based.

def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```

def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
```

def _cap_files_for_prompt(files):
    """Cap per-file and total content bytes before they're packed into the
    review prompt. Returns the capped (path, content) list. Sets module-level
    _last_review_truncated_bytes to the number of bytes dropped (0 if none) so
    the Stop hook can emit a `diff_truncated` metric. Truncation markers are
    written INSIDE the content so the reviewer knows the file is incomplete.
    """
    global _last_review_truncated_bytes
    _last_review_truncated_bytes = 0
    out = []
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            _last_review_truncated_bytes += len(content) - DIFF_PER_FILE_BYTES
            content = content[:DIFF_PER_FILE_BYTES] + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            _last_review_truncated_bytes += len(content)
            out.append((fp, "[omitted by security-guidance: total diff byte cap reached]"))
            continue
        if len(content) > room:
            _last_review_truncated_bytes += len(content) - room
            content = content[:room] + "\n... [truncated by security-guidance: total diff byte cap reached]"
        total += len(content)
        out.append((fp, content))
    return out
