### Title
Unchecked multiplication overflow in asset denomination cap calculation allows indivisible-asset supply inflation - (File: validation.js)

### Summary
`validateAssetDefinition()` in `validation.js` computes the declared total cap of a fixed-denomination asset by summing `count_coins * denomination` for each entry in `payload.denominations`, then compares that sum against `payload.cap`. Neither `count_coins` nor `denomination` is bounded to a safe numeric range before the multiplication — exactly the class of bug described in the external report: an unvalidated multiplicand bit-size/range leads to an arithmetic overflow that can be exploited to bypass a downstream invariant check (there, fee correctness; here, supply-cap correctness).

### Finding Description
In `validateAssetDefinition`, each denomination entry is checked only with: [1](#0-0) 
`isPositiveInteger(denomInfo.denomination)` and `isPositiveInteger(denomInfo.count_coins)` are the only numeric guards. `isPositiveInteger`/`isInteger` merely require `typeof value === 'number' && isFinite(value) && Math.floor(value) === value`, with no upper bound: [2](#0-1) 

The `denomination` value is only bounded against `constants.MAX_CAP` conditionally, gated by an upgrade-MCI check: [3](#0-2) . Crucially, `count_coins` is never bounded against `MAX_CAP` or any other limit anywhere in this function or in the equivalent AA asset-definition validator, which also only calls `isPositiveInteger` on `count_coins`: [4](#0-3) 

Because JavaScript numbers are IEEE-754 doubles, `denomInfo.count_coins * denomInfo.denomination` silently loses precision once the true product exceeds `Number.MAX_SAFE_INTEGER` (2^53), and the accumulated `total_cap_from_denominations` (a running sum of such products) can also silently round when it grows large. The final invariant check is a strict equality: [5](#0-4) 
This is directly analogous to the `MulDivGadget` bug: the gadget's `product` and `quotient` bit-widths were never validated, allowing a crafted `value`/`numerator` pair to overflow the field and defeat the "product must be bounded" assertion. Here, a crafted `count_coins`/`denomination` pair (each individually a legal "positive integer" per the check, but whose product exceeds 2^53) can defeat the "declared cap equals sum of denomination caps" assertion via floating-point rounding, letting `payload.cap` pass validation while not actually equaling the true (rational) sum of `count_coins_i * denomination_i`.

### Impact Explanation
An asset issuer (a completely unprivileged unit poster – anyone can define a new asset in a unit) controls both `count_coins` and `denomination` for each denomination tier of a fixed-denomination (indivisible) asset. By choosing values whose product and/or whose running sum crosses the IEEE-754 safe-integer boundary, the issuer can make `total_cap_from_denominations` (computed with floating-point semantics) equal an arbitrary `payload.cap` even though the true integer sum of per-denomination capacities differs. Because `count_coins` directly controls `max_issued_serial_number` limits used later when issuing coins of that denomination (see `indivisible_asset.js` issuance logic, which uses `count_coins` to bound how many coins of a denomination can ever be issued: `count_coins_to_issue = row.count_coins || Math.floor(...)`), a manipulated `count_coins` can let the issuer mint more total supply of the capped asset than the advertised `cap`, i.e. asset supply inflation, or create inconsistent per-node accounting of the asset's cap due to floating-point non-determinism across environments/engines. This falls squarely within "supply inflation" impact for asset issuance and is Medium/High severity depending on exploitability of a specific overflow combination.

### Likelihood Explanation
Likelihood is Medium: this requires an attacker to define a custom asset (trivial, requires no privilege beyond posting a unit) and to find a `count_coins`/`denomination` combination whose float arithmetic satisfies the equality check while producing a different actual/true cap than intended. Because both values are attacker-chosen with no upper bound besides `isPositiveInteger`, and both `MAX_CAP` (~9×10^15, comparable to `TOTAL_WHITEBYTES`) and `Number.MAX_SAFE_INTEGER` (~9×10^15) are extremely close in magnitude, an attacker has room to craft `count_coins` values large enough (while `denomination` is small, e.g. 1) to push `count_coins * denomination` or the running sum past the safe-integer boundary without tripping the `denomination > MAX_CAP` check (which only bounds `denomination`, not `count_coins`). Exact exploitability requires numeric experimentation to find a concrete overflow/rounding combination that satisfies the strict equality, but the code path itself is unambiguously reachable and unguarded.

### Recommendation
- Bound `count_coins` explicitly (e.g., `count_coins <= constants.MAX_CAP` and `count_coins * denomination <= constants.MAX_CAP`), and perform the multiplication/summation using a safe-integer-checked routine (e.g., reject if `count_coins > Number.MAX_SAFE_INTEGER / denomination`) instead of raw JS `*`/`+`.
- Apply the same bound unconditionally (not gated by `pemCurvesFixMci`) to both `denomination` and `count_coins`.
- Mirror the fix in `aa_validation.js`'s AA asset-definition validator (`validateDenominations`), which has the identical unbounded `count_coins`/`denomination` check.
- More generally, audit all places that multiply/sum attacker- or issuer-controlled integers before comparing to `MAX_CAP`/`TOTAL_WHITEBYTES` for the same overflow class.

### Proof of Concept
1. Post a unit defining a new fixed-denomination asset with `denominations`, e.g. two entries:
   - `{ denomination: 1, count_coins: 9007199254740993 }` (2^53+1, still passes `isPositiveInteger` since `Math.floor` of large floats equals themselves) 
   - a second small entry chosen so that the running floating-point sum in `total_cap_from_denominations` rounds to a specific representable value `X`.
2. Set `payload.cap = X` (the rounded floating-point sum) even though the true integer total of `count_coins_i * denomination_i` differs from `X`.
3. `validateAssetDefinition` accepts the unit because `total_cap_from_denominations !== payload.cap` check passes on floating-point values, even though the mathematically true cap differs.
4. Later, `indivisible_asset.js` issuance logic honors the (uncapped in effect) `count_coins` for that denomination tier, allowing the issuer to mint coins beyond the nominally advertised `cap`.

Note: exact numeric constants needed to trigger a passing equality after floating rounding were not empirically verified in this analysis (would require running the JS arithmetic); the vulnerability is the missing bound/validation itself, confirmed by direct code inspection of `validation.js` and `validation_utils.js`.
