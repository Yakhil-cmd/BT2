## Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` allows cross-fork replay of signer-capability offers - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`SignerCapabilityOfferProofChallengeV2`, the struct signed by an account owner to delegate `SignerCapability` to another address, omits the `chain_id` field that its sibling struct `RotationCapabilityOfferProofChallengeV2` explicitly includes for replay protection. This inconsistency lets a previously-published, legitimately-signed signer-capability-offer signature be replayed unmodified on a different chain that shares the same account address space and sequence numbers (e.g., a network fork), causing `signer_capability_offer.for` to be set on the forked chain without a fresh authorization from the account owner on that chain.

### Finding Description
The framework defines two "V2" challenge structs used for capability delegation: [1](#0-0) 

`RotationCapabilityOfferProofChallengeV2` carries a `chain_id: u8` field with an explicit comment stating it was added "which prevents replaying the challenge message." [2](#0-1) 

`SignerCapabilityOfferProofChallengeV2`, by contrast, has no `chain_id` (or any other network-binding) field: [3](#0-2) 

`offer_signer_capability` constructs this challenge purely from `sequence_number`, `source_address`, and `recipient_address`, then verifies the caller-supplied signature against it and writes the recipient into `signer_capability_offer.for`: [4](#0-3) 

Because the signed payload contains no chain-specific data, a signature produced for chain A validates identically on any other network (chain B) where:
- the same account address exists with the same current `sequence_number`, and
- the same `recipient_address` exists.

Both conditions hold trivially immediately after a chain fork (shared genesis/history), or on any long-lived test/replica network that shares the mainnet's account address space.

### Impact Explanation
An attacker who observes an already-broadcast `offer_signer_capability` transaction on one network (transaction contents, including `signer_capability_sig_bytes`, are public) can resubmit an equivalent transaction to a forked network. The unmodified signature will still pass `verify_signed_message`, causing the account's `signer_capability_offer.for` to be (re)bound to `recipient_address` on the fork without the account owner ever intending or authorizing that grant on that specific chain. Once granted, `recipient_address` can call `create_authorized_signer` to obtain a `signer` for the victim's account and act as it, which is a full account-capability compromise on the forked chain: [5](#0-4) 

This is a genuine domain-binding failure at the signature-verification boundary consistent with the "Replay, expiry, sequence, chain-id, or domain-binding failure" impact category.

### Likelihood Explanation
Exploitation requires no privileged access or leaked keys — only a previously published, legitimately signed offer transaction and a forked/replica network sharing address space and sequence-number state at the fork point. This is a realistic scenario for Aptos-based devnets/testnets/private forks that clone mainnet or testnet state, or for any hard fork that preserves account state. The window of validity is bounded by the recipient's `sequence_number` staying unchanged and the offer not being revoked/overwritten on the target chain, but no on-chain mechanism currently closes it, since unlike `RotationCapabilityOfferProofChallengeV2`, there is no `chain_id` to invalidate the replay.

### Recommendation
Add a `chain_id: u8` (and ideally reuse the same domain-separation pattern as `RotationCapabilityOfferProofChallengeV2`) to `SignerCapabilityOfferProofChallengeV2`, and populate/verify it in `offer_signer_capability` using `chain_id::get()`, mirroring the pattern already used for rotation capability offers. This closes the cross-network replay gap and makes the two "V2" proof-challenge structs consistent.

### Proof of Concept
1. On chain A (e.g., mainnet), account `S` calls `offer_signer_capability` with a signature over `SignerCapabilityOfferProofChallengeV2{ sequence_number, source_address = S, recipient_address = R }`. This transaction and its signature bytes are publicly visible.
2. Stand up (or use an existing) chain B that shares chain history/state with chain A up to a fork point, such that account `S` still has the same `sequence_number` and account `R` exists at the same address.
3. Submit a transaction to chain B calling `account::offer_signer_capability(S, signer_capability_sig_bytes, account_scheme, account_public_key_bytes, R)` using the identical bytes captured from chain A.
4. Observe that `verify_signed_message` accepts the signature on chain B (no `chain_id` mismatch is possible because none is encoded), and `signer_capability_offer.for` is set to `R` on chain B even though `S` never signed an offer intended for chain B.
5. `R` calls `create_authorized_signer(R_signer, S)` on chain B and obtains a `signer` for `S`'s account, demonstrating unauthorized capability grant via cross-chain replay.

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
