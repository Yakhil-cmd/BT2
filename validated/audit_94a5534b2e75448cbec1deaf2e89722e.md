### Title
Webhook signature check is bound to the wrong organization key, letting an unauthenticated request act on repositories it never authenticated for - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The engine authenticates incoming GitHub webhooks by looking up a per-organization `GitHubApp`/`webhook_secret` using a value taken from the payload itself, then lets every event handler resolve the actual `Repository`/`Stack` to mutate using a *different*, unrelated payload field. Nothing ties the two together, and if the organization used for the signature lookup has no `webhook_secret` configured (an explicitly supported, documented configuration), the signature check is skipped entirely — yet the handler still trusts the attacker-supplied repository field to decide what stack to write to.

### Finding Description
`WebhooksController#verify_signature` derives the organization to authenticate against directly from the untrusted payload: [1](#0-0) [2](#0-1) 

It calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, where `repository_owner` comes from `params.dig('repository', 'owner', 'login')` (fallback `organization.login`). This selects which `GitHubApp` config/secret to check against.

Inside `GitHubApp#verify_webhook_signature`, the check is a no-op when no `webhook_secret` is configured for that org: [3](#0-2) 
`return true unless webhook_secret` — this is intentional/documented, since `docs/setup.md` explicitly marks the webhook secret as "(optional)" and shows multi-org configs where each org has its own independent `webhook_secret`.

Meanwhile, every `Webhooks::Handlers::Handler` (and its `PullRequest::*` subclasses) resolves the target `Repository`/`Stack` using a completely separate field, `repository.full_name`, with no cross-check against the organization that was actually authenticated: [4](#0-3) 

So the binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository actually written to (repository.full_name)`

This equality is never enforced. If any configured GitHub organization in `config/secrets.yml` has no `webhook_secret` set (a supported configuration per `docs/setup.md`'s multi-org example, which shows `webhook_secret:` left blank per-org), `verify_signature` passes for a request naming that org as `repository.owner.login`, without validating `X-Hub-Signature` at all. The attacker then supplies an arbitrary `repository.full_name` value (e.g. a stack belonging to a *different*, fully-secured organization) and the handler will look it up via `Repository.from_github_repo_name` and act on it — because `full_name`, not `owner.login`, is what actually drives which `Stack`/`Commit`/`PullRequest` records get mutated.

### Impact Explanation
This breaks the authentication boundary between "which GitHub organization/app installation we just verified a signature for" and "which repository's Shipit state we are about to mutate." Concretely:
- A forged `status` webhook (`Handlers::StatusHandler`, resolved via the same `Handler#stacks`/`repository_name` mechanism) lets an attacker post an arbitrary CI `state` (e.g. `success`) for a commit on a stack belonging to an organization it was never authenticated against, which can unblock/allow deploys gated on green CI status.
- A forged `push` webhook (`Handlers::PushHandler`) can cause `stack.sync_github(expected_head_sha: ...)` to run against an arbitrary tracked stack, and `check_suite`/`membership` handlers similarly mutate state (`Team`, `Membership`, check-run refresh) for repositories/organizations outside the one that was actually authenticated.
- Net effect: cross-repository/cross-organization writes triggered by a request that never carried a valid signature for the repository it is mutating — meeting the "cross-repository writes" / unauthorized state-changing action bar.

This is a direct analog of the report's core bug class: a verification step (health-factor/liquidation check in the report; HMAC signature check here) is anchored to the wrong entity (the account calling `utilize()` vs. the account already liquidated; here, the org used to pick the secret vs. the repository actually written), so a request can "continue to operate" against a target it was never validated for.

### Likelihood Explanation
Requires only: (1) the Shipit deployment host multiple GitHub organizations via `config/secrets.yml`'s documented multi-org format, and (2) at least one of those configured organizations has no `webhook_secret` set — both are explicitly supported, documented configurations (`docs/setup.md`, "Webhook secret (optional)" and the multi-org example with blank `webhook_secret:` fields). No credentials, session, or API token are needed; `WebhooksController` is a public, unauthenticated endpoint by design (`skip_before_action :verify_authenticity_token`, no `authenticate_api_client`). The attacker only needs to know/guess the name of the org lacking a secret and the `full_name` of the target repository/stack they want to affect, both of which can be enumerated from Shipit's own public stack listing pages.

### Recommendation
Bind the signature verification and the state-mutation target to the same, single value: use `repository.full_name`'s owner segment (not a separate `repository.owner.login`/`organization.login` fallback) for both the `GitHubApp` lookup and the eventual repository resolution, and reject (or at minimum log/alert loudly) events where the two disagree. Independently, consider making `webhook_secret` mandatory when more than one organization is configured, or reject events for organizations with a blank secret when other organizations in the same install do have one configured, since a mixed trust configuration silently degrades the whole system's webhook authentication to "none."

### Proof of Concept
Conceptual (cannot be executed here, no filesystem/terminal access):
1. Configure Shipit per `docs/setup.md`'s multi-org example with two orgs: `OrgSecure` (has `webhook_secret`) and `OrgOpen` (no `webhook_secret`).
2. `OrgSecure` owns a tracked repository `OrgSecure/app` with an active Shipit stack.
3. POST to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` for `OrgSecure`, and a JSON body where:
   - `repository.owner.login = "OrgOpen"` (so `verify_signature` resolves `Shipit.github(organization: "OrgOpen")`, whose `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:77`)
   - `repository.full_name = "OrgSecure/app"`, `sha = <real commit sha>`, `state = "success"`
4. `Shipit::Webhooks::Handlers::StatusHandler` resolves the stack via `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and creates a passing status on `OrgSecure/app`'s commit — despite the request never being authenticated against `OrgSecure`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
