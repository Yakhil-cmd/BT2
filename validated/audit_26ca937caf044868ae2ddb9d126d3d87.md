### Title
Headers-commission distribution rounds each recipient's share independently, allowing supply inflation via crafted `earned_headers_commission_recipients` - ([File: headers_commission.js])

### Summary
The bug class from the referenced report — computing a proportional share by rounding each individual allocation instead of rounding once for the whole amount — is reproducible in ocore's headers-commission distribution logic. An unprivileged unit poster can split the `earned_headers_commission_recipients` list into many small percentage shares, each independently rounded with `Math.round()`, so that the sum of the rounded per-recipient amounts exceeds the actual `headers_commission` fee paid by the parent unit, creating bytes from nothing.

### Finding Description
`validateHeadersCommissionRecipients` only requires that recipient shares be positive integers summing exactly to 100 and does not bound the number of recipients or otherwise prevent fine-grained fractional splits: [1](#0-0) 

When a child unit later "wins" the headers commission of a parent unit, `calcHeadersCommissions` distributes the parent's full `headers_commission` (`full_amount`) among the recipients of the winning child by rounding **each recipient's amount independently**: [2](#0-1) [3](#0-2) 

Because `Math.round(full_amount * share / 100.0)` is applied per recipient rather than computing amounts for all-but-one recipient and assigning the remainder to the last one, the sum of the rounded amounts can differ from `full_amount`. Since each individual recipient's fractional part can independently round up (bias toward +0.5 each), an attacker who controls all recipient addresses (trivial — a single actor can author a multi-signed/multi-authored unit and freely name any number of `earned_headers_commission_recipients`, since they need not be co-authors) can choose the number of recipients and shares to maximize the number of amounts that round up simultaneously. The resulting `headers_commission_outputs` row for that main-chain-index sums these individually-rounded amounts: [4](#0-3) 

This is architecturally the same rounding-bias root cause as the Anchor staking bug: a proportional-share computation that rounds per-unit instead of rounding the aggregate once, letting the attacker choose the split to bias the total in their favor.

### Impact Explanation
`headers_commission_outputs.amount` becomes spendable base-currency (bytes) balance for the named addresses. If the sum of rounded per-recipient allocations for a payer unit exceeds the `headers_commission` actually charged (which is fixed by unit size and enforced elsewhere as a fee taken from the payer's balance), then more bytes become spendable in aggregate than were ever deducted from any payer — i.e., new bytes are minted out of thin air. Because the attacker controls both the winning child unit (choosing itself as the "best child" via crafting many candidate children, or simply being the sole winner) and the recipient list on that unit, they fully control the shares/rounding inputs and can repeat the technique across many main-chain indices to accumulate meaningful inflation over time.

### Likelihood Explanation
Reachable by any unprivileged unit poster: multi-authored units are a standard, permissionless feature, and `earned_headers_commission_recipients` is fully attacker-specified as long as shares are positive integers summing to 100 and addresses are sorted/unique — there is no restriction tying the list to actual authors or limiting its length. The main constraint is that the unit must legitimately win headers commission from at least one parent (an ordinary and unprivileged occurrence for any unit author), and the achievable inflation per event is bounded by the number of recipients and `full_amount` magnitude, so per-instance gains are small but repeatable, which is why this is rated Medium rather than Critical.

### Recommendation
Change the distribution algorithm to preserve conservation of the total amount, e.g.:
1. Sort recipients deterministically, round all but the last recipient's share normally, and assign the last recipient `full_amount - sum(already assigned)` so the total always equals `full_amount` exactly, or
2. Use a largest-remainder allocation method that guarantees the sum of allocated integer amounts equals `full_amount`.

### Proof of Concept
1. Attacker authors a multi-authored unit (or otherwise ensures the unit becomes the deterministic headers-commission "winner" per `getWinnerInfo`) and sets `earned_headers_commission_recipients` to N addresses it controls with integer shares summing to 100, chosen such that for the expected `full_amount` (the parent's `headers_commission`, deterministic from unit size), `full_amount * share_i / 100` has a fractional part ≥ 0.5 for as many recipients as possible.
   Example: `full_amount = 3`, recipients with shares `[17,17,17,17,16,16]` (sum=100):
   - `round(3*17/100) = round(0.51) = 1` for 4 recipients → 4
   - `round(3*16/100) = round(0.48) = 0` for 2 recipients → 0
   - Total distributed = 4 > `full_amount` = 3.
2. When `calcHeadersCommissions` processes this parent/child pairing, `headers_commission_contributions`/`headers_commission_outputs` will record 4 spendable bytes across the attacker's addresses even though only 3 bytes of `headers_commission` were actually paid by the parent unit, per the aggregation logic at: [2](#0-1) 
3. Repeating this pattern across many won parent units accumulates unbacked spendable byte balance for the attacker.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
