Cross-organization webhook forgery via mismatched `repository.owner.login` (used for signature verification) vs `repository.full_name` (used to resolve the target stack) - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a delivery against using `repository.owner.login` (or `organization.login`), while the handlers that actually act on the payload resolve the target `Repository`/`Stack` from an entirely different, unauthenticated field: `repository.full_name`. Nothing binds these two values together, so a payload can be legitimately signed for org A while acting on org B's repository.

### Finding Description
`verify_signature` picks the app config purely from the owner login embedded in the JSON body: [1](#0-0) [2](#0-1) 

`Shipit` supports multiple GitHub organizations, each with its own independent `webhook_secret`, as documented and configured via the `github: { org_a: {...}, org_b: {...} }` schema: [3](#0-2) 

Once the signature check passes, the event is dispatched to handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`), and every handler resolves the affected repository/stack from a **different** field of the same payload — `repository.full_name` — via the shared base class: [4](#0-3) 

Nothing anywhere validates that `repository.owner.login` (used to select the verifying secret) is consistent with the owner encoded in `repository.full_name` (used to select the acted-upon `Repository`/`Stack`). This breaks the trust binding: `organization authenticated == repository written`.

Concretely, `PushHandler` uses `stacks` (derived from `repository.full_name`) to sync arbitrary stacks: [5](#0-4) 

Other handlers in the same directory (`status_handler.rb`, `check_suite_handler.rb`, `membership_handler.rb`, `pull_request/*`) follow the identical pattern of trusting `repository.full_name`/embedded payload fields for the actual write, independent of which org's secret validated the request.

### Impact Explanation
On a multi-tenant Shipit instance (the documented multi-org `github:` config), any organization onboarded to that instance — an otherwise unprivileged tenant who only knows their **own** org's `webhook_secret` — can forge a webhook whose `repository.owner.login` names their own org (so `verify_signature` fetches and matches against a secret they know) but whose `repository.full_name` names a victim organization's repository. The signature will verify successfully even though the attacker has no relationship to, and no secret for, the victim org.

This lets the attacker: enqueue `GithubSyncJob`/`RefreshCheckRunsJob` against victim stacks, forge commit `Status` records that feed `Commit#deployable?` (gating the merge queue), and manipulate `Team`/`Membership` records — all against a repository the attacker never controlled the credentials for. Forged status events in particular can push an otherwise-unready commit through the merge queue of a victim repository, resulting in an unauthorized merge/deploy — satisfying the "unauthorized deploy, rollback, or merge" Critical/High impact bar.

### Likelihood Explanation
Requires only that the Shipit instance host more than one organization (the documented, supported multi-org configuration) and that the attacker be a legitimate but low-privilege tenant of that instance who knows their own org's `webhook_secret` (obtained legitimately when they set up their own GitHub App/webhook, not stolen). No GitHub App private key, `api_clients_secret`, session, or repository write access to the victim org is required — the `/webhooks` endpoint is unauthenticated apart from the per-org HMAC check, and the check itself is the thing being bypassed via the field mismatch.

### Recommendation
Bind the two fields together before dispatch: after `verify_signature` succeeds, re-derive `repository_owner` from `repository.full_name` (or `organization.login` used consistently) and require it to match the owner used to select the verifying secret; reject the request otherwise. Alternatively, key the webhook secret lookup by `repository.full_name`'s owner segment rather than the separate `repository.owner.login`/`organization.login` fields, so the same field authenticated is the field acted upon.

### Proof of Concept
Assume a shared Shipit instance configured with two orgs, `attacker-org` (secret known to the attacker) and `victim-org` (repo `victim-org/victim-repo` deployed as a Shipit stack):

```
BODY='{
  "ref": "refs/heads/main",
  "after": "deadbeefcafefeed",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}'
SIG=$(python3 -c "import hmac,hashlib,sys;print('sha1='+hmac.new(b'ATTACKER_ORG_SECRET', sys.argv[1].encode(), hashlib.sha1).hexdigest())" "$BODY")

curl -X POST https://shipit.example.com/webhooks \
  -H "X-Github-Event: push" \
  -H "X-Hub-Signature: $SIG" \
  -H "Content-Type: application/json" \
  -d "$BODY"
```

`verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and validates `SIG` against the attacker's own known secret — success — even though `PushHandler#stacks` (via `repository_name` = `repository.full_name`) resolves and syncs `victim-org/victim-repo`, a stack the attacker has no legitimate access to.
