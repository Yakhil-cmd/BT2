### Title
Unbounded regex execution in hookify rule matching enables ReDoS-based hook bypass - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._regex_match()` compiles `condition.pattern` from repo-local `.claude/hookify.*.local.md` rule files via `compile_regex()` (a plain `re.compile(pattern, re.IGNORECASE)`) and then calls `regex.search(text)` against attacker-influenced fields such as `Bash` `command` or `Write`/`Edit` `new_string` with no length cap, complexity check, or execution timeout. A maliciously crafted catastrophic-backtracking pattern combined with an adversarial matched string causes `re.search()` to hang indefinitely inside the hook subprocess.

### Finding Description
Rules are loaded from `.claude/hookify.*.local.md` files by `load_rules()`/`load_rule_file()` in `plugins/hookify/core/config_loader.py` (lines 198-275), parsing YAML-like frontmatter with `extract_frontmatter()` into `Condition` objects whose `pattern` field is taken verbatim from the file content (`Condition.from_dict`, lines 22-29). These files live in the repository/workspace and can be attacker-controlled if a contributor's rule file (or a generated/committed one) is checked out into a victim's workspace.

`pretooluse.py` (`plugins/hookify/hooks/pretooluse.py`, lines 35-70) reads the tool-use JSON from stdin, calls `load_rules(event=...)`, then `RuleEngine.evaluate_rules()` → `_rule_matches()` → `_check_condition()` (`rule_engine.py` lines 144-180). For `operator == 'regex_match'`, `_regex_match(pattern, field_value)` (lines 256-273) does:
```
regex = compile_regex(pattern)   # re.compile(pattern, re.IGNORECASE), lru_cache
return bool(regex.search(text))
```
`field_value` is extracted by `_extract_field()` (lines 182-254) directly from `tool_input` — e.g. `Bash`'s `command` or `Write`/`Edit`'s `new_string`/`content` — both of which are attacker-influenceable content (e.g. a file the agent is asked to write, or a command constructed from untrusted repository/PR data flowing through the session).

There is no regex complexity validation, no length truncation of `field_value` before matching, and no timeout/signal/thread-based cancellation around `regex.search()`. A pattern like `(a+)+$` or `(a|aa)+b` paired with a long non-matching string (e.g. `"a" * 40 + "!"`) triggers catastrophic backtracking, causing `re.search()` to hang the Python process running the PreToolUse hook.

Critically, this doesn't merely "fail closed safely" — `pretooluse.py` wraps the body in `try/except` with `finally: sys.exit(0)`, meaning errors are tolerated by allowing the operation, but a *hang* inside `evaluate_rules()` never reaches the `except`/`finally` at all; the hook process simply never returns, so Claude Code's calling harness must either wait indefinitely or time out and fall back to its own default behavior for a non-responsive hook (typically treated as allow, since the hook design in this file always favors availability of tool execution over blocking). This makes hookify's enforcement itself an availability target: an attacker who can plant one bad rule file gains the ability to hang or defeat all subsequent PreToolUse checks by using regular tool operations that touch fields evaluated by that pattern.

### Impact Explanation
Impact is scoped to availability / enforcement-bypass of the hookify guard layer: repeated invocation of tool calls whose `command`/`new_string`/`content` trip the vulnerable pattern causes the PreToolUse hook to hang, degrading or defeating hookify's PreToolUse blocking/warning behavior for the remainder of the session (or requiring the harness to time out and effectively allow the tool call, since no explicit deny was ever returned). This matches an availability-based bypass of a security control rather than direct code execution or secret disclosure, but it directly undermines the trust boundary hookify is meant to enforce.

### Likelihood Explanation
Requires two things attacker can plausibly control together in normal workflows: (1) contributing/checking out a `.claude/hookify.*.local.md` rule file containing a catastrophic-backtracking `regex_match` pattern (plausible via PR content, generated config, or a compromised/careless rule author), and (2) causing a subsequent tool call whose relevant field (e.g. `Bash` command, or file `new_string`/`content` written by the agent, potentially derived from repo/PR/issue text) contains a string shaped to trigger backtracking against that pattern. Both are realistic within "ordinary repository content" and don't require elevated privilege — this is a real, repeatable ReDoS with well-known trigger patterns (`(a+)+`, `(a|aa)+`, etc.), fully deterministic once preconditions are met.

### Recommendation
- Add a regex complexity/timeout guard around `regex.search()` in `_regex_match()` (e.g. run in a worker thread/process with a hard timeout via `signal.alarm`, `concurrent.futures` with `.result(timeout=...)`, or use the `regex` module's timeout support / `re2`-style linear-time engine).
- Truncate/limit the length of `field_value` before matching (e.g. cap at a few KB) to bound worst-case backtracking cost.
- Optionally validate/sanitize rule patterns at load time (static ReDoS pattern detection) and reject or warn on suspicious constructs before caching them via `compile_regex()`.
- Ensure a matching timeout is treated as a definitive `warn`/`block`-safe outcome (not silently defaulting to allow) so a slow pattern cannot be leveraged to disable enforcement.

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
