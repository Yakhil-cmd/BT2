### Title
Webhook signature is verified against the payload's `repository.owner.login`, but events are dispatched against the payload's `repository.full_name` — a mismatch lets a holder of one organization's webhook secret forge events for a different organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate the signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (with a fallback to `params.dig('organization', 'login')`). Once the signature check passes, `create` hands the entire raw JSON body — unmodified — to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Every handler (`Shipit::Webhooks::Handlers::Handler#stacks`) independently derives the target repository from a *different* field of the same payload: `payload.dig('repository', 'full_name')`. Nothing enforces that `repository.full_name`'s owner segment equals `repository.owner.login`. This is the same class of bug as the Ajna finding: a value used to authorize/validate an operation (`repository.owner.login`, akin to the intermediary LUP) is not the value that the operation actually acts on afterwards (`repository.full_name`, akin to the final LUP).

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
before_action :check_if_ping, :drop_unhandled_event, :verify_signature

def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The signature verification is HMAC-correct in itself — it validates that the raw body was signed by *some* organization's configured `webhook_secret`, and it correctly picks that organization's secret via `repository_owner`. The vulnerability is that `repository_owner` and the field the rest of the pipeline trusts are not the same binding:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside the same JSON body that the attacker fully composes before signing it with their own organization's legitimate webhook secret (obtained e.g. by installing/configuring the Shipit GitHub App on their own organization, a supported, unprivileged setup path). Nothing ties `repository.full_name`'s owner segment back to `repository.owner.login`. An attacker who controls a webhook secret for `attacker-org` can craft:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  ...
}
```
sign it with `attacker-org`'s secret, and `verify_signature` will pass (`repository_owner` == `attacker-org`, matching the secret used), while every downstream handler resolves the target `Stack` via `victim-org/victim-repo`.

This exactly mirrors the reported bug class: "an organization that authenticated versus the repository that is written" — the equality that should hold, `organization_that_signed == owner(repository_acted_upon)`, is broken because the two checks read from different, independently attacker-controlled JSON paths within one payload that is verified as a whole (HMAC covers the raw bytes, not field-level consistency).

### Impact Explanation
Handlers process events such as `push` (queues `GithubSyncJob` for the resolved stack), `status`/`check_suite` (updates commit statuses, potentially unblocking deploy gating for the victim stack), `pull_request`, `merge`, and `deployable_status`. Forging these for an arbitrary victim stack lets an attacker who only controls their own organization's webhook secret manipulate CI/status/merge state and trigger sync jobs on a stack they do not own, without any Shipit session, `ApiClient` token, or repository write access on the victim's side — a cross-repository write into state that should be scoped to the authenticating organization. This satisfies the "cross-repository writes" Critical-impact criterion, since actions intended to be authorized per-organization instead land on an arbitrary other organization's stack.

### Likelihood Explanation
Likelihood is high for any deployment that configures Shipit with more than one GitHub organization/App (each with its own `webhook_secret`), which is the documented multi-org support pattern (`Shipit.github(organization:)`). Any actor who legitimately controls one organization's webhook secret (e.g., by being an admin of their own org that has an app installation configured in this same Shipit instance) can exploit this with a single crafted HTTP POST to `/webhooks`, no auth token needed beyond the signature they can compute themselves.

### Recommendation
After signature verification, re-derive the repository/organization used for stack resolution from the *same* verified field used for signature selection (or vice versa), and reject the request if `repository.owner.login` (or `organization.login`) does not match the owner segment of `repository.full_name`. Concretely, in `WebhooksController#verify_signature` (or in `Handler#repository_name`), assert `repository_name.start_with?("#{repository_owner}/")` and `head(422)` otherwise, so the value trusted for authorization and the value acted upon are provably the same binding.

### Proof of Concept
1. Attacker operates `attacker-org`, which has a Shipit GitHub App installation with webhook secret `S`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "repository": {
    "owner": {"login": "attacker-org"},
    "full_name": "victim-org/victim-repo",
    "name": "victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates the signature successfully against `S`.
5. `create` dispatches `params` (containing `repository.full_name = "victim-org/victim-repo"`) to the push handler, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` / updates state for the victim stack — despite the request never being signed by `victim-org`'s secret.
