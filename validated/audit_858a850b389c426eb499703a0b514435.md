### Title
Webhook signature verification for one GitHub organization can be trivially bypassed and used to forge events for an unrelated repository — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and its `webhook_secret`) to verify a webhook against using `repository.owner.login` from the *unverified* request body, while the handlers that actually act on the event use a completely different field from the same body — `repository.full_name` — to decide which tracked `Stack`/`Repository` to mutate. Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured (a state explicitly shown as the default/expected value in the shipped config templates), an unauthenticated attacker can send a payload whose `repository.owner.login` matches a secret-less org, while `repository.full_name` points at a different, unrelated tracked repository, and have the handler act on that repository with no valid GitHub signature at all.

### Finding Description
`verify_signature` derives the organization used for verification purely from attacker-controlled JSON, before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank, *before even looking at the supplied signature header*: [3](#0-2) 

A `webhook_secret: nil` config is the documented/shipped default for this engine, not an unusual misconfiguration: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (trivially, for the secret-less org), `WebhooksController#create` dispatches the raw, still-unverified body to the registered handlers: [6](#0-5) 

Every handler resolves the target repository/stack from `payload.dig('repository', 'full_name')` — a field never checked against, or tied to, the `repository.owner.login` value used for signature-org selection: [7](#0-6) 

For example, `PushHandler` uses that repository to look up stacks and enqueue a sync with an attacker-supplied `after` SHA: [8](#0-7) 

This reproduces the report's underlying bug class exactly: a value used by the trust/verification step (`repository_owner`, i.e. "the organization that authenticated") is disjoint from the value the code subsequently acts on (`repository.full_name`, i.e. "the repository that is written"), and nothing enforces `equality` between the two — analogous to `Position.moveLiquidity` acting on `vars.lpbAmountFrom` (derived independently) instead of the tracked `fromPosition.lps` it was supposed to be bound to.

### Impact Explanation
Any unauthenticated network client can send a crafted POST to the webhook endpoint with:
- `X-Github-Event: push` (or `status`, `check_suite`, `pull_request`, etc.)
- no `X-Hub-Signature` header (or an arbitrary one — it is never inspected when `webhook_secret` is unset)
- `repository.owner.login` set to any org configured on the instance without a `webhook_secret`
- `repository.full_name` set to any *other* repository tracked by the instance (including ones belonging to orgs that *do* have a secret configured)

This lets the attacker enqueue `GithubSyncJob` for arbitrary stacks with an attacker-chosen `expected_head_sha`, forge `check_suite` refresh events, or (via `StatusHandler`) fabricate commit statuses used for deploy/merge gating on repositories the attacker has no access to — all without possessing any `webhook_secret`, `ApiClient` token, GitHub App key, or Shipit session. This crosses the "unauthorized deploy" / merge-status-manipulation boundary called out as in-scope Critical/High impact.

### Likelihood Explanation
High for any deployment following the project's own documented single-org or multi-org example configs (`webhook_secret` left blank), since no attacker secret is required — only knowledge of the target org's login name (often public) and the target repository's `full_name` (also public). This is a design flaw in the engine's own controller/model code, not a third-party gem defect or a documented-mounting issue.

### Recommendation
Bind the two identities together instead of trusting them independently:
- After selecting the `GitHubApp` via `repository_owner`, require that `payload.dig('repository','full_name')`'s owner matches `repository_owner` before any handler runs, or resolve the target `Repository`/`Stack` strictly through the same organization used for verification.
- Treat a missing/blank `webhook_secret` as "verification not possible" and reject (or clearly flag/quarantine) events for that organization rather than treating it as automatically verified, or require operators to configure a secret for any organization whose repositories are handled by push/state-changing webhook handlers.

### Proof of Concept
Assume an instance is configured (per the shipped example) with an org `orgone` that has `webhook_secret: nil`, and separately tracks a `Stack` for `victimorg/victim-repo` (owned by a different, secret-protected org).

```
POST /github/webhooks
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "orgone" },
    "full_name": "victimorg/victim-repo"
  },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```

`verify_signature` resolves `Shipit.github(organization: "orgone")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` without inspecting any signature header (`lib/shipit/github_app.rb:76-83`). `WebhooksController#create` then dispatches the parsed body to `PushHandler`, which resolves the stack from `repository.full_name = "victimorg/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and enqueues `GithubSyncJob` with the attacker-controlled `expected_head_sha` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — despite the request carrying no valid credentials for `victimorg`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
