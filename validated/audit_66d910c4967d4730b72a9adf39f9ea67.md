### Title
Cross-organization webhook confusion allows forging commit statuses and triggering syncs for repositories owned by a different GitHub organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a request against using an organization name taken from the same untrusted JSON body it is about to verify, while the handlers that act on the request use a different field (`repository.full_name`) from that same body to decide which `Stack`/`Repository` to mutate. On a multi-organization Shipit install, the two fields are never checked for consistency, so a party who legitimately controls the webhook secret for one onboarded organization can sign a payload that names an unrelated organization's repository, and Shipit will act on it as if GitHub had sent it for that other repository.

### Finding Description
`Shipit.github` supports a multi-tenant configuration where each organization has its own `webhook_secret` (`lib/shipit.rb:170-200`, `Shipit::TOP_LEVEL_GH_KEYS`). The webhook signature check picks which organization's secret to verify with directly from the incoming payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) — both attacker-supplied fields inside the very body being signed. `verify_signature` only proves that *some* organization's configured secret matches the raw body; it does not prove that the organization whose secret was used is the same organization that owns the repository the handlers subsequently operate on.

Once signature verification passes, `create` dispatches the parsed body to handlers such as `PushHandler` and `StatusHandler`, which resolve the target `Stack`/`Repository` from a *different* JSON field, `repository.full_name`: [3](#0-2) [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are two independent strings in the same attacker-crafted JSON body — GitHub itself would keep them consistent, but nothing in Shipit enforces that — an entity that owns/controls the webhook secret for *organization A* (e.g. because they legitimately onboarded their own public org/repo to this Shipit instance and therefore know or set that secret) can:
1. Build a payload with `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")`'s secret is used for verification) and `repository.full_name = "org-b/victim-repo"`.
2. Sign the raw body with org-A's known webhook secret.
3. Send it to `/webhooks`. `verify_signature` succeeds (org-A's secret matches), and the handler then resolves `Repository.from_github_repo_name("org-b/victim-repo")` and mutates that stack.

This is the same class of bug as the report: a field that is authenticated (`repository.owner.login`, used to select the verifying key) does not equal the field that is actually acted upon (`repository.full_name`), breaking the intended binding `verified-organization == acted-on-repository`.

### Impact Explanation
Depending on the event/handler exercised, this allows an attacker who only controls one organization's webhook secret on a shared Shipit instance to:
- Force `PushHandler` to invoke `stack.sync_github(expected_head_sha: ...)` on a victim's stack for an arbitrary branch/sha [4](#0-3) .
- Inject arbitrary CI/commit statuses via `StatusHandler#process` → `Commit#create_status_from_github!` for commits belonging to a victim's repository [5](#0-4) , which can be used to satisfy status-based deploy gating and lead to an unauthorized deploy.
- Affect pull-request driven review-stack lifecycle handlers (archive/unarchive/label capture) for a repository the attacker does not own [6](#0-5) .

This matches the "unauthorized deploy" / cross-repository-write class of impact called out in scope, since it lets a signature that is valid for repo/org A be used to drive state changes on repo/org B.

### Likelihood Explanation
This requires a Shipit deployment configured for multiple organizations (the `secrets.github` multi-key schema recognized by `Shipit.github_default_organization`/`github_app_config`) where more than one organization/tenant is onboarded with independent webhook secrets, and where at least one of those secrets is known to (or was itself set by) the attacker for their own organization's webhook. In that (documented, supported) multi-tenant configuration, no additional privileges beyond "controls one onboarded org's webhook config" are needed — this matches the "unprivileged attacker" bar since the attacker never obtains a Shipit session, `ApiClient` token, or the victim organization's own webhook secret.

### Recommendation
After signature verification succeeds, `WebhooksController#verify_signature`/`create` should re-validate that the organization whose secret was used to verify the signature (`repository_owner`) matches the owner of the repository actually referenced by the payload (`repository.full_name`'s owner segment, or `organization.login`), and reject the request otherwise. Alternatively, handlers should be passed the already-authenticated organization explicitly and refuse to act on any `repository.full_name` whose owner does not match it.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, e.g. `org-a` (attacker's own onboarded org, secret known to attacker) and `org-b` (victim org, unrelated secret).
2. Craft a JSON body for a `push` (or `status`) event:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature` using org-A's known webhook secret over this exact raw body, and send it to `POST /webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against org-A's secret [1](#0-0) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/victim-repo")` [7](#0-6)  and calls `stack.sync_github` on the victim's stack, even though the request was never signed by org-B's webhook secret.
