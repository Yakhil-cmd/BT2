### Title
Webhook signature verification key is selected from an unauthenticated payload field while the handled repository/team comes from that same untrusted payload, allowing forged GitHub events to escalate `Shipit.github_teams` authorization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* per-organization webhook secret to verify the request against based on a field read straight out of the unauthenticated request body (`repository.owner.login` / `organization.login`), then verifies the raw body against that secret. If any organization configured in `Shipit.github` is set up with `webhook_secret` left blank (an explicitly documented, supported configuration), `GitHubApp#verify_webhook_signature` short-circuits to `true` for any payload claiming to be from that organization. The handler that actually acts on the payload (`Webhooks::Handlers::Handler#stacks`/`#repository_name`, and `MembershipHandler`) uses other payload fields (`repository.full_name`, `team`/`member` objects) that are never re-checked against the organization that was used to select the verification key. This breaks the equality that should hold: `organization_used_to_verify_signature == organization/team the event is allowed to mutate`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
It derives `repository_owner` purely from the unauthenticated JSON body: [2](#0-1) 

That value is used to select the GitHub App config (and thus the HMAC secret) via `Shipit.github(organization: repository_owner)`. The actual verification is: [3](#0-2) 
`return true unless webhook_secret` means that for any organization configured with a blank/unset `webhook_secret` (documented as an optional field, e.g. `webhook_secret: # nil` in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`), signature verification is bypassed entirely regardless of what the attacker sends.

The event is then dispatched with the raw, unverified payload to handlers: [4](#0-3) 
Handlers resolve *what to act on* from a different payload field than the one used for the security decision: [5](#0-4) 
`PushHandler` triggers a git sync/deploy pipeline update on whatever stack matches `repository.full_name`: [6](#0-5) 
`StatusHandler` writes a commit status purely by `sha`, with no repository scoping check at all: [7](#0-6) 
The `membership` event handler creates `Team`/`Membership` records on the fly from payload data (confirmed by test behavior): [8](#0-7) 

`Shipit.github_teams` membership is exactly what gates application authorization: [9](#0-8) 

**The broken binding**: `organization authenticated (via verify_signature's repository_owner)` is supposed to equal `the organization/repository/team whose state the event mutates`, but nothing enforces that the `team`/`repository.full_name` fields inside a payload verified under organization X's (blank) secret actually belong to organization X. An attacker with no credentials can send a raw `membership` webhook claiming `organization.login` = an org configured with a blank `webhook_secret`, while the embedded `team`/`member` fields reference a team that satisfies `Shipit.github_teams` for a completely different, properly-secured organization, creating a `Membership` that grants the attacker's own GitHub login access to the tracked team.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization — explicitly listed as a High-severity impact for this engine. Once a forged `Membership` record exists for the attacker's login and a required team, the attacker's GitHub OAuth login (obtained through the normal, unprivileged OAuth login flow) will pass `current_user.authorized?`, granting them access to the Shipit UI/API to view stacks, task streams and deploy output, and potentially trigger deploys/tasks depending on further `ApiClient`/UI permissions. It can also be combined with `PushHandler`/`StatusHandler` forgery (repository/commit fields are never checked against the verifying organization either) to forge passing CI status on arbitrary tracked commits, undermining deploy gating.

### Likelihood Explanation
Requires only: (1) the (documented, supported) presence of at least one configured GitHub organization with an unset `webhook_secret` in a multi-org Shipit installation, and (2) knowledge of a target team slug/organization that participates in `Shipit.github_teams` — both discoverable from the public GitHub org/team structure. No credentials, tokens, or GitHub App keys are required, matching the "unprivileged attacker" scope. Likelihood is moderate: it depends on the specific documented multi-org configuration choice, not a misconfiguration outside the documented setup.

### Recommendation
Bind the verified organization to every field a handler acts on:
- After selecting the GitHub App config from `repository_owner`, re-verify that `repository_owner`/`organization.login` in the payload actually matches the organization that owns the `Repository`/`Team` being mutated (i.e., look up the `Repository`/`Team` record and compare its known owning organization, rather than trusting payload-declared owner fields blindly).
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in a multi-organization configuration; require explicit, non-blank secrets per organization, or reject requests for any organization lacking one.
- In `MembershipHandler`, `PushHandler`, and `StatusHandler`, cross-check that the team/repository/commit referenced belongs to the organization that was actually used to verify the signature before mutating state.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `Shipit.github`: `orgA` (real `webhook_secret`, contained in `Shipit.github_teams`) and `orgB` (no `webhook_secret` set, per the documented optional field).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, with body:
```json
{
  "action": "added",
  "organization": { "login": "orgB" },
  "team": { "id": 1, "name": "OrgA Team", "slug": "orga-team", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
3. `verify_signature` resolves `repository_owner` = `"orgB"`, fetches `orgB`'s (blank) `webhook_secret`, and `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb` line 77.
4. `MembershipHandler` processes the event and creates a `Membership` linking `attacker-github-login` to team `orga-team`, even though the request was never actually authenticated by `orgA` or `orgA`'s GitHub App.
5. Attacker logs in through the normal GitHub OAuth flow with `attacker-github-login`; `Authentication#force_github_authentication` finds them authorized because they're now a member of a team in `Shipit.github_teams`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
