### Title
Missing `SpokeUsage` row is silently treated as zero/absent, letting supply/borrow caps be bypassed after TTL archival - (File: contracts/controller/src/spoke_usage.rs)

### Summary
The Linux bug is a use-before-check: `ebu_nand_probe()` dereferences `res` before `platform_get_resource()`'s result is validated for `NULL`. The analog in XOXNO Lending is `SpokeUsageContext`, which consumes the result of `storage::get_spoke_usage(...)` (an `Option<SpokeUsageRaw>`) without checking presence: `apply_entry` unwraps a missing row to a zero default and `apply_exit` returns early on a missing row. Because `SpokeUsage` is the cumulative, protocol-wide accounting that spoke caps are enforced against, treating a missing row as "zero usage" silently discards all previously recorded usage.

### Finding Description
`SpokeUsageContext::apply_entry` loads the per-(spoke, hub_asset) usage row and, on absence, substitutes `SpokeUsageRaw::default()` before enforcing the cap:

```rust
// contracts/controller/src/spoke_usage.rs:111
let mut usage = self.load_usage_row(hub_asset).unwrap_or_default();
let next = enforce_spoke_cap(&self.env, side, &usage, delta_scaled, cap, index, decimals);
```

`apply_exit` takes the opposite shortcut: a missing row is a no-op rather than an invariant violation:

```rust
// contracts/controller/src/spoke_usage.rs:128-130
let Some(mut usage) = self.load_usage_row(hub_asset) else {
    return;
};
```

Both paths use the `Option` as if "absent" were a valid zero state — the exact shape of dereferencing a resource before checking it for `NULL`. The row lives in persistent storage (`storage::set_spoke_usage` → `set_shared`), so it is subject to Soroban archival: if the `(spoke_id, hub_asset)` row expires/archives (a dormant market sees no writes or TTL-extending reads), `load_usage_row` returns `None` even though accounts still hold nonzero supply/borrow positions in that spoke.

From that point:
- `apply_entry` recomputes caps against `usage = 0`, so the next `supply`/`borrow`/`multiply`/`flash_position` leg can deposit or borrow up to `supply_cap`/`borrow_cap` *again*, on top of the existing uncapped usage.
- `apply_exit` never writes the missing row back, so the under-count persists indefinitely; every subsequent entry continues to measure from the stale zero baseline.

The spoke cap check in `enforce_spoke_cap` (`next_scaled <= cap_scaled`) is the only thing bounding per-spoke exposure; once the baseline is silently zeroed, the bound becomes `cap` plus whatever usage existed at archival time.

### Impact Explanation
Protocol insolvency risk. Spoke `borrow_cap`/`supply_cap` are governance-set limits meant to bound a spoke's exposure per asset. After the usage row archives, any unprivileged address can call `borrow` (or `multiply`/`flash_position`) up to the full cap again, inflating spoke-level debt beyond the configured limit with no error. Repeated across dormant markets, the protocol can accumulate materially more risk than caps allow, and the permanently under-counted `supplied_scaled_ray`/`borrowed_scaled_ray` rows corrupt all later cap checks. This is not a fail-closed panic — it silently produces wrong accounting and succeeds.

### Likelihood Explanation
Medium-Low. It requires a `SpokeUsage` persistent entry to archive while positions still exist — i.e., a spoke/asset with real usage that goes long enough without any cap-relevant write or read to outlive its persistent TTL. That is realistic for deprecated or dormant spokes (`remove_spoke` explicitly leaves positions and usage in place without an empty-spoke check, `contracts/controller/src/config/spoke.rs:36-49`), which are precisely the rows most likely to lapse. Once lapsed, exploitation is permissionless through ordinary `supply`/`borrow` entrypoints; no privileges, leaks, or bad parameters are needed.

### Recommendation
Distinguish "absent" from "zero" the way the kernel fix distinguishes `NULL` from a valid resource: check before use. If a spoke has ever recorded usage for a hub asset, a missing row is an invariant violation, not a zero value. Concretely:
- In `apply_entry`, panic (e.g., `SpokeError`/`GenericError::InternalError`) when `load_usage_row` returns `None` and the market has nonzero totals, or recompute the row from authoritative position totals rather than defaulting to zero.
- In `apply_exit`, panic on `None` for a nonzero delta instead of returning, so an archived row cannot silently absorb a decrement and mask the divergence.
- Alternatively, derive cap checks from the market's `total_supply`/`total_debt` (which the pool tracks independently) rather than a separate persistent row that can archive out from under the accounting.

### Proof of Concept
1. Governance lists asset `A` on spoke `S` with `borrow_cap = 100_000`. Users borrow `80_000` total; `SpokeUsage(S, {hub, A}).borrowed_scaled_ray` reflects it.
2. The spoke goes dormant; the persistent `SpokeUsage` row archives while positions remain on the books.
3. Attacker (unprivileged) calls `controller.borrow(caller, account_id, payments)` for `100_000` of `A` on spoke `S`. `apply_entry` → `load_usage_row` → `None` → `unwrap_or_default()` → `enforce_spoke_cap` checks `delta ≤ 100_000` and passes.
4. Spoke `S` now carries `180_000` of `A` debt against a `100_000` cap, and the usage row is rewritten at only `100_000`, so the bypass repeats on every subsequent archival.
