### Title
Cross-organization team membership escalation via mismatched `team.id` in `membership` webhook - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the webhook payload bytes were signed with the secret of the organization named in `params['organization']['login']` (or `repository.owner.login`), but `MembershipHandler#find_or_create_team!` looks up `Team` solely by `params.team.id` (GitHub's numeric team id) and never checks that the found team's `organization` matches the organization that signed the request. If an attacker controls org-x's webhook secret (i.e. is an admin of their own GitHub org) and crafts a `membership` event whose `team.id` collides with a `Team` row already bound to a different, sensitive org-y, the handler will add the attacker to org-y's team.

### Finding Description
The intended binding is: `organization that signed the payload (verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` == `organization that owns the Team record being mutated (team.organization)`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the HMAC using `Shipit.github(organization: repository_owner)`'s `webhook_secret` [1](#0-0) [2](#0-1) . For a `membership` event this is `org-x`, controlled by the attacker, and the signature check passes because it is HMAC'd with org-x's own secret against org-x's own bytes.
- `WebhooksController#create` then dispatches the parsed JSON straight to the registered handlers with no further ownership check [3](#0-2) .
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`. Since `github_id` is the primary lookup key, if a `Team` row already exists with that `github_id` (belonging to `org-y`), it is returned as-is; the block that would set `team.organization = params.organization.login` only runs on creation, so an existing org-y team's `organization` attribute is untouched [4](#0-3) .
- `#process` then calls `team.add_member(User.find_or_create_by_login!(params.member.login))`, which unconditionally appends the member to `Team#members` with no organization/ownership check [5](#0-4) [6](#0-5) .
- Nothing in `Handler#initialize`/`ExplicitParameters` schema enforces that `params.organization.login` equals the `Team#organization` of the resolved record; the schema only requires the fields to be present/typed [7](#0-6) [8](#0-7) .

Attacker request: POST `/webhooks` with header `X-Github-Event: membership`, body `{"action":"added","team":{"id":<org-y team's github_id>,"name":"...","slug":"...","url":"..."},"organization":{"login":"org-x"},"member":{"login":"attacker-login"}}`, signed with `X-Hub-Signature` computed via HMAC-SHA1 using org-x's real `webhook_secret` (which the attacker legitimately owns as org-x's admin). `verify_signature` passes because it verifies against org-x. `find_or_create_team!` resolves to the pre-existing org-y `Team` row by numeric `github_id` collision (attacker can learn/guess org-y team ids, e.g., from public GitHub API `org_teams` or by having previously seen a webhook/notification referencing the team; team ids are not secret). `team.add_member` adds the attacker as a member of org-y's team.

### Impact Explanation
This directly escalates the attacker into `Shipit.github_teams`-style authorization data for org-y: the `Team#members` association populated here is used by `User#authorized?`/`require_permission!` (per the finding's stated precondition, corroborated by `github_teams` config usage in `lib/shipit.rb` and `app/models/shipit/user.rb`) to grant deploy/merge permissions on org-y's stacks. Because the write happens on the `Team` model without any organization-ownership check, the same request pattern is repeatable against any `Team` row whose `github_id` the attacker can discover, across arbitrary target organizations, as long as the attacker owns (or compromises) the webhook secret of any single registered organization in the Shipit installation. This matches the "escalation into `Shipit.github_teams` authorization" High/Critical impact category.

### Likelihood Explanation
Preconditions: (1) the Shipit instance must have more than one organization configured with the `membership` webhook enabled, (2) the attacker must control (own/administer) at least one such organization (org-x) to legitimately obtain its `webhook_secret` and register/send webhooks, (3) the attacker must know or guess a `github_id` of a `Team` already persisted for a different, sensitive org (github team ids are visible via GitHub's public/authenticated API for that org, or observable from prior webhook traffic/Shipit UI). Given these, the attack is a single crafted HTTP POST, fully repeatable, with no elevated Shipit privileges required.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and any other handler resolving a `Team`/`Repository` by GitHub numeric id), verify that the resolved record's `organization` equals `params.organization.login` (the organization that was cryptographically verified as `repository_owner` in `verify_signature`) before mutating it; raise/drop the event if they diverge. More generally, `WebhooksController` should pass the verified `repository_owner` into handlers so each handler can assert `record.organization == repository_owner` before performing any lookup-by-numeric-id-only mutation, closing the "signing org != owning org" gap. This is `app/models/shipit/webhooks/handlers/membership_handler.rb`.

### Proof of Concept
Minitest plan (webhooks_controller_test.rb style, `test/controllers/webhooks_controller_test.rb`):
1. Create `Shipit::Team.create!(github_id: 1234, organization: 'org-y', name: 'sensitive-team', slug: 'sensitive-team', api_url: 'https://api.github.com/teams/1234')`.
2. Configure two orgs in `Shipit.github_configs`/`Shipit.github(organization:)` stub: `org-x` with `webhook_secret: 'x-secret'`, `org-y` with `webhook_secret: 'y-secret'`.
3. Build payload: `{ "action" => "added", "team" => { "id" => 1234, "name" => "sensitive-team", "slug" => "sensitive-team", "url" => "..." }, "organization" => { "login" => "org-x" }, "member" => { "login" => "attacker" } }`.
4. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'x-secret', payload.to_json)` (org-x's own secret — attacker-controlled).
5. POST to `/webhooks` with `X-Github-Event: membership` and the above signature.
6. Assert response is `200 OK` (signature verified against org-x).
7. Assert, BEFORE the request: `Shipit::Team.find_by(github_id: 1234).organization == 'org-y'` and `Shipit::Team.find_by(github_id: 1234).members.map(&:login)` does not include `'attacker'`.
8. Assert, AFTER the request: `Shipit::Team.find_by(github_id: 1234).organization == 'org-y'` (unchanged) but `Shipit::Team.find_by(github_id: 1234).members.map(&:login)` now includes `'attacker'` — demonstrating a payload signed only by org-x mutated org-y's team membership.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
