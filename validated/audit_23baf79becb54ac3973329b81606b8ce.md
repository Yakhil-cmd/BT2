### Title
Unverified P2P `StakingInfo` Delivery Corrupts Reward Distribution and Proposer Selection — (File: `datasync/downloader/queue.go`)

---

### Summary

During fast sync, `StakingInfo` received from a remote peer is accepted and persisted to the local database with **zero content validation**. A malicious connected peer can inject fabricated staking amounts, reward addresses, and fund addresses. The corrupted data is then consumed by the reward module (`FinalizeState`) to distribute KAIA block rewards and by the valset module to build the weighted proposer list, causing unauthorized KAIA transfers to attacker-controlled addresses and invalid proposer selection.

---

### Finding Description

`queue.DeliverStakingInfos` in `datasync/downloader/queue.go` contains a deliberately empty `validate` function:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [1](#0-0) 

Every other data type has a cryptographic check against the block header:
- `DeliverBodies` checks `types.DeriveTransactionsRoot(...) != header.TxHash`
- `DeliverReceipts` checks `types.DeriveReceiptsRoot(...) != header.ReceiptHash` [2](#0-1) [3](#0-2) 

No equivalent `StakingInfoHash` field exists in the block header, and no alternative integrity check is performed. The accepted `StakingInfo` is written directly to the database in `commitFastSyncData`:

```go
if result.StakingInfo != nil {
    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
}
``` [4](#0-3) 

The same unverified write occurs in `commitPivotBlock`: [5](#0-4) 

The `SyncStakingInfo` recovery path (callable via `KaiaDownloaderSyncAPI`) performs only a `BlockNum` equality check before writing, with no content verification:

```go
if d.stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum {
    logger.Error(...)
    return
}
d.stakingModule.PutStakingInfoToDB(stakingInfo.BlockNum, staking.ToStakingInfo(stakingInfo))
``` [6](#0-5) 

---

### Impact Explanation

The persisted `StakingInfo` is consumed in two protected paths:

**1. KAIA reward distribution** — `RewardModule.FinalizeState` calls `GetDeferredReward` → `assignStakingRewards`, which reads `si.StakingAmounts`, `si.RewardAddrs`, `si.KIFAddr`, and `si.KEFAddr` to compute and credit KAIA balances via `state.AddBalance`: [7](#0-6) [8](#0-7) 

A fabricated `StakingInfo` with modified `RewardAddrs` or `KIFAddr`/`KEFAddr` redirects KAIA block rewards to attacker-controlled addresses every block for the entire staking interval.

**2. Proposer selection** — `calcBaseProposers` calls `generateProposerListWeighted`, which uses `StakingAmounts` to compute proposer frequency weights: [9](#0-8) [10](#0-9) 

Inflated `StakingAmounts` for a target validator give it a disproportionate share of proposer slots, enabling block-ordering manipulation.

---

### Likelihood Explanation

The attack is reachable by any peer the syncing node connects to during fast sync. The `handleStakingInfoMsg` handler in `node/cn/handler.go` delivers the peer's response directly to the downloader without any authentication of the content: [11](#0-10) 

The staking info fetch is scheduled automatically for every `StakingUpdateInterval`-th block during fast sync when `ProposerPolicy == WeightedRandom`: [12](#0-11) 

No special privilege is required beyond being a registered P2P peer. The TODO comment in the validate function confirms the missing check is a known gap, not an intentional design decision.

---

### Recommendation

1. **Add a cryptographic commitment**: Include a `StakingInfoHash` field in the block header (computed as the hash of the canonical `StakingInfo` JSON/RLP at that block) and verify it in `DeliverStakingInfos` analogously to how `TxHash` and `ReceiptHash` are verified.

2. **Alternatively, re-derive from state**: After fast sync completes, re-derive `StakingInfo` from the local state trie (via the AddressBook contract) rather than trusting peer-supplied data. This is the approach used for full-sync nodes.

3. **Harden `SyncStakingInfo`**: Verify the received `StakingInfo` content against the local canonical state at the corresponding block before writing to DB.

---

### Proof of Concept

1. Node A begins fast sync against a malicious peer B.
2. Node A schedules staking info fetches for blocks `[N, N+StakingInterval, ...]` via `queue.Schedule`.
3. Peer B responds to `RequestStakingInfo` with a `P2PStakingInfo` where:
   - `BlockNum = N` (passes the only check in `SyncStakingInfo`)
   - `RewardAddrs[i] = attacker_address` for all validators
   - `StakingAmounts[i] = 10^18` for attacker's validator
4. `queue.DeliverStakingInfos` calls `validate(...)` → returns `nil` unconditionally.
5. `commitFastSyncData` calls `PutStakingInfoToDB(N, fabricated_info)`.
6. For all blocks `[N+StakingInterval+1 ... N+2*StakingInterval]`, `RewardModule.FinalizeState` reads the fabricated `StakingInfo`, computes `assignStakingRewards` with `attacker_address` as the reward recipient, and calls `state.AddBalance(attacker_address, reward)` — minting KAIA block rewards to the attacker every block. 	}
