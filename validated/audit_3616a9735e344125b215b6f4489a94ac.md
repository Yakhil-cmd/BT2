### Title
Silent CL Staking Amount Drop in `consolidateNodes()` When Multiple CLNodeIds Share the Same RewardAddr — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidateNodes()` in `kaiax/staking/staking_info.go` uses a **last-write-wins** assignment when attaching a `CLStakingInfo` to a consolidated validator node. AddressBook explicitly allows multiple `NodeId`s to share one `RewardAddr` (the "consolidation" feature). CLRegistry is keyed per `NodeId`, not per `RewardAddr`. When two `NodeId`s that share a `RewardAddr` both have `CLStakingInfo` entries in CLRegistry, the first entry is silently overwritten and its `CLStakingAmount` is permanently dropped from every downstream reward calculation for that epoch.

---

### Finding Description

`consolidateNodes()` builds a `cmap[RewardAddr] → consolidatedNode` structure in two passes.

**Pass 1** — AddressBook entries:

```go
// kaiax/staking/staking_info.go  lines 131-148
for i, n := range si.NodeIds {
    r := si.RewardAddrs[i]
    nToR[n] = r          // NodeId → RewardAddr
    if cn, ok := cmap[r]; ok {
        cn.NodeIds = append(cn.NodeIds, n)
        cn.StakingAmount += si.StakingAmounts[i]
    } else {
        cmap[r] = &consolidatedNode{ ... }
    }
}
```

After this pass, `cmap[r1]` may contain `NodeIds = [n1, n3]` when both `n1` and `n3` share `RewardAddr r1`.

**Pass 2** — CLRegistry entries:

```go
// kaiax/staking/staking_info.go  lines 151-159
for _, clsi := range si.CLStakingInfos {
    if r, ok := nToR[clsi.CLNodeId]; ok {
        // One CLStakingInfo per validator is guaranteed by CLRegistry.
        cmap[r].CLStakingInfo = clsi   // ← plain overwrite, no guard
    }
}
```

The comment asserts "One CLStakingInfo per validator is guaranteed by CLRegistry." However, CLRegistry is keyed by `CLNodeId` (a `NodeId`), not by `RewardAddr`. It can guarantee at most one entry *per NodeId*. It cannot prevent two distinct `NodeId`s that share a `RewardAddr` from each having a CLRegistry entry. When both `n1` and `n3` appear in `CLStakingInfos`, the loop assigns `cmap[r1].CLStakingInfo = clsi_n1` and then immediately overwrites it with `cmap[r1].CLStakingInfo = clsi_n3`. `clsi_n1.CLStakingAmount` is permanently lost.

The test suite already documents this exact behavior:

```go
// kaiax/staking/staking_info_test.go  lines 258-267
// CL1 will be ignored when being consolidated since it has duplicate CL (not feasible in real)
{CLNodeId: n3, CLPoolAddr: clPool2, CLStakingAmount: clStakingAmount2},
// Result: only n3's CLStakingInfo survives; n1's clStakingAmount1 is dropped
```

The phrase "not feasible in real" is a design assumption, not an enforced invariant. The Go code contains no assertion, no deduplication check, and no error return.

---

### Impact Explanation

Every downstream consumer of `ConsolidatedNodes()` is affected:

1. **`assignStakingRewards()`** (`kaiax/reward/impl/getter.go` lines 488–533) — computes each validator's proportional staking reward using `cn.CLStakingInfo.CLStakingAmount`. With the first CL entry silently dropped, the dropped CL pool receives **zero staking reward** for the epoch even though it holds real staked KAIA. The remainder is redistributed to other stakers, constituting an incorrect KAIA transfer.

2. **`specWithProposerAndFunds[Flex]()`** (`kaiax/reward/impl/getter.go` lines 538–641) — calls `cn.Split(proposer)` which divides the proposer reward between the CN reward address and the CL pool address proportionally. With the first CL entry dropped, the split is computed against the wrong (or zero) CL amount, again misdirecting KAIA.

3. **`FinalizeState()`** (`kaiax/reward/impl/blockstate.go` lines 30–56) — calls `state.AddBalance(addr, amount)` for every entry in `spec.Rewards`. The dropped CL pool address never appears in `spec.Rewards`, so its balance is never incremented.

The corrupted value is `cn.CLStakingInfo` (nil or wrong pool/amount) for any consolidated node whose first-seen CLNodeId's entry was overwritten. The financial loss equals the staking reward share that should have been credited to the dropped CL pool address each block.

---

### Likelihood Explanation

The trigger requires:

1. A GC member registers two (or more) `NodeId`s in AddressBook with the **same `RewardAddr`** — this is explicitly supported and documented as the "consolidation" feature.
2. Both `NodeId`s have entries in CLRegistry — CLRegistry is keyed per `NodeId`, so this is structurally possible.

Condition 1 is a normal operational pattern (multiple staking contracts under one reward address). Condition 2 follows naturally if the operator deploys a CL pool for each of their node IDs. No majority-validator collusion is required; a single GC member with two consolidated node IDs suffices.

---

### Recommendation

Replace the silent overwrite with either:

**Option A — Reject duplicates (enforce the stated invariant explicitly):**
```go
if r, ok := nToR[clsi.CLNodeId]; ok {
    if cmap[r].CLStakingInfo != nil {
        logger.Error("duplicate CLStakingInfo for RewardAddr", "rewardAddr", r)
        return nil, staking.ErrCLRegistryResult
    }
    cmap[r].CLStakingInfo = clsi
}
```

**Option B — Accumulate amounts (handle the case correctly):**
```go
if r, ok := nToR[clsi.CLNodeId]; ok {
    if existing := cmap[r].CLStakingInfo; existing != nil {
        existing.CLStakingAmount += clsi.CLStakingAmount
        // CLPoolAddr: keep first or pick deterministically
    } else {
        cmap[r].CLStakingInfo = clsi
    }
}
```

Option A is safer because it surfaces the inconsistency rather than silently masking it, allowing operators to correct their CLRegistry registrations.

---

### Proof of Concept

The existing test case in `kaiax/staking/staking_info_test.go` already demonstrates the bug:

```
"4 nodes consolidated to 2 nodes and one node has two CLs"
  NodeIds:     [n1, n2, n3, n4]
  RewardAddrs: [r1, r2, r1, r2]   ← n1 and n3 share r1
  CLStakingInfos:
    {CLNodeId: n1, CLPoolAddr: clPool1, CLStakingAmount: clStakingAmount1}
    {CLNodeId: n3, CLPoolAddr: clPool2, CLStakingAmount: clStakingAmount2}

Expected (and actual) result:
  consolidatedNode for r1 = {NodeIds:[n1,n3], CLStakingInfo:{n3, clPool2, clStakingAmount2}}
  ← clPool1 / clStakingAmount1 silently dropped
```

`clPool1` would receive **zero** staking reward for every block in the epoch, despite holding `clStakingAmount1` KAIA in consensus liquidity.
```go
// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
```
