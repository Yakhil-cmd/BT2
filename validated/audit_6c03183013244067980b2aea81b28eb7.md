### Title
Repository-unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a webhook from one repository write a `Status` onto a commit belonging to another repository's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit purely by SHA, with no check that the commit's owning `Stack`/`Repository` matches the `repository.full_name` that authenticated the webhook. Because signature verification (`Shipit::WebhooksController#verify_signature`) only proves the request was really sent for *some* organization derived from the payload, it does not prove the payload's SHA belongs to that organization's repo, so a legitimately-signed webhook from Repository A can flip CI state on a commit that actually belongs to Repository B's stack whenever the SHAs coincide (e.g. shared git ancestry from a fork).

### Finding Description
The broken binding is: `commit.stack.repository.full_name == payload['repository']['full_name']` for every `Status` created by `StatusHandler#process`. This should always hold but does not.

`StatusHandler#process` is: [1](#0-0) 
which does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global lookup across every stack/repository in the install, with no repository filter, unlike the base `Handler` class which already provides a `stacks` helper scoped by `repository_name` from the payload: [2](#0-1) 
`StatusHandler` never calls this scoping helper.

`Shipit::WebhooksController#verify_signature` derives the GitHub App/secret to check purely from the payload's own `repository.owner.login`: [3](#0-2) 
So a genuinely-signed webhook (signed by GitHub for a repository the attacker controls, e.g. their own fork, once that repository/org is wired to Shipit's GitHub App) proves nothing about which SHAs the payload is allowed to touch — `params.sha` is fully attacker-controlled content inside an otherwise validly-signed envelope.

Exploit flow: attacker forks or otherwise controls a repository that shares commit history (identical SHAs) with the victim's tracked repository — a routine situation for forks sharing pre-fork history, or when an identical commit (same tree/parents/authorship/timestamps) is reproduced. The attacker pushes/labels/opens a PR in their own repo to trigger a genuine `status` event with `context: github-actions` and the shared SHA. GitHub signs and delivers this webhook using the real secret for the attacker's own org/repo. `verify_signature` passes because it only checks that the sender's org secret matches its own org — it never checks that the SHA in the payload belongs to that org's repos. `StatusHandler#process` then updates every `Commit` row across the database matching that SHA, including the one belonging to the victim's stack, via `Commit#create_status_from_github!` → `Status.replicate_from_github!` → `Commit#add_status`, which can flip `deployable_status`/`commit_status` and trigger `schedule_merges`/`ContinuousDeliveryJob` on the victim stack: [4](#0-3) [5](#0-4) 

Separately, and amplifying the impact when the victim is a review stack, `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` (and the analogous `ReopenedHandler#unarchive?`) has a Ruby operator-precedence issue where `review_stacks_enabled` is only ANDed with the `allow_all` branch, not with the `allow_with_label`/`prevent_with_label` branches: [6](#0-5) 
so a repository with `review_stacks_enabled: false` but `provisioning_behavior` set to `allow_with_label`/`prevent_with_label` can still have review stacks provisioned/unarchived. Note: this precedence logic lives in `opened_handler.rb`/`reopened_handler.rb`, not in `app/models/shipit/stack.rb` as the question's target list states — I could not locate any such precedence logic in `stack.rb`.

None of the existing guards (`verify_signature`, `ExplicitParameters` schema, model validations) check that the SHA in a `status` payload belongs to the repository that signed the webhook, so the divergence is real.

### Impact Explanation
An attacker who controls any repository onboarded to the same Shipit deployment (their own fork/repo, no special Shipit privilege needed) can, for any SHA that coincides between their repo and a victim's tracked stack, write an arbitrary `Status` (`state`, `context: github-actions`, `description`, `target_url`) onto the victim commit. This can flip a blocked/failing commit to `success`, unblocking deploys/merges (`schedule_merges`, `ContinuousDeliveryJob`) on a stack the attacker does not own — matching the "payload for one repository mutating another's stack/commit" Critical impact category. It is repeatable against any commit whose SHA the attacker can reproduce or share via git ancestry, and the write is not confined to a single tenant.

### Likelihood Explanation
Exploitation requires: (1) the attacker's own repository/org is already wired to Shipit's GitHub App/webhook (so a genuinely-signed webhook is deliverable at all — this is not something an attacker with zero relationship to Shipit can forge, since they hold no `webhook_secret`), and (2) a SHA collision with the victim's stack, realistically achievable only through shared git history (fork of the victim repo) rather than arbitrary attacker choice. This bounds the attack to victims whose repos are forkable/public and tracked alongside attacker-controlled repos in the same Shipit instance — a plausible but not universal precondition, hence not trivially "any internet user, any repo" but still a genuine repo-scoping defect in the engine's own code.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the stacks belonging to the webhook's own repository (using the existing `Handler#stacks` helper) instead of a bare `Commit.where(sha: params.sha)` across the whole database. Additionally fix the operator precedence in `OpenedHandler#provision?`/`ReopenedHandler#unarchive?` by explicitly parenthesizing `repository.review_stacks_enabled && (...)` around the entire behavior disjunction so `review_stacks_enabled: false` disables provisioning under every `provisioning_behavior`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for one repository must not create a Status on a commit belonging to another repository's stack" do
  victim_repo  = shipit_repositories(:shipit) # owns victim_stack
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(review_stacks_enabled: false) rescue nil # if applicable via repository

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'github-actions',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(attacker_payload).process
  end

  # Binding under test:
  # commit.stack.repository.full_name == payload['repository']['full_name']
  # Before fix: StatusHandler writes the Status anyway (assertion above fails),
  # proving `Commit.where(sha:)` is unscoped by repository.
end
```
