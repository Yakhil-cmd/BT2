### Title
Cross-organization webhook forgery via organization/repository binding mismatch in signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body, but the event handlers that actually mutate state (`Handler#repository_name`, `PushHandler`, `ReviewStackAdapter`, `CheckSuiteHandler`, etc.) resolve the target `Repository`/`Stack` using a *different* field from the same body: `repository.full_name`. Nothing binds these two fields together. In a multi-organization Shipit deployment, an attacker who legitimately controls one configured GitHub App (and therefore knows its `webhook_secret`) can sign a payload as their own organization while pointing `repository.full_name` at a repository belonging to a different, victim organization configured on the same Shipit instance.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
with
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

For multi-org configurations, `Shipit.github(organization:)` looks up the secret keyed by exactly this attacker-supplied string:
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  ...
end
``` [3](#0-2) 

So the HMAC secret used to "authenticate" the request is chosen purely by `repository.owner.login`, a value fully controlled by whoever is sending the JSON body. As long as the attacker signs with the secret belonging to *some* organization already configured on the shared `/webhooks` endpoint (documented as a single shared endpoint: `Webhook URL: <homepage>/webhooks`, docs/setup.md), the signature check passes — regardless of which repository the rest of the payload claims to touch.

Every handler that performs the actual mutation, however, keys off `repository.full_name`, not `repository.owner.login`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 
```ruby
def repository
  @repository ||= Shipit::Repository.from_github_repo_name(params.repository.full_name) ||
                  Shipit::NullRepository.new
end
``` [5](#0-4) 
```ruby
def repo_name
  params.repository["full_name"]
end
...
def stack_attributes
  {
    branch: params.pull_request.head.ref,
    environment:,
    ignore_ci: false,
    continuous_deployment: false
  }
end
``` [6](#0-5) 

Nothing in the request enforces `repository.owner.login == repository.full_name.split('/').first`. Equality broken: **organization that authenticated (`repository.owner.login`, secret lookup) ≠ repository that is written (`repository.full_name`, used to resolve the `Repository`/`Stack` mutated by the handler)**.

### Impact Explanation
Using a `pull_request` "opened" webhook signed with organization A's own secret (which the attacker legitimately possesses, e.g. as the admin of their own org's Shipit-connected GitHub App) but with `repository.full_name` set to `"VictimOrg/victim-repo"`, an attacker can:
- Make `Repository.from_github_repo_name` resolve to the real victim repository/Stack config.
- Have `ReviewStackAdapter#create!` build a brand-new review `Stack` whose `branch` is taken verbatim from the attacker-controlled `params.pull_request.head.ref`, tied to the victim organization's real repository, and immediately enqueue it for provisioning (`ReviewStackProvisioningQueue.add(stack)`).
- This results in Shipit checking out and deploying/provisioning an attacker-chosen branch of the victim's repository without any genuine webhook ever having been sent by the victim organization's own GitHub App — an unauthorized deploy/provisioning action crossing organizational trust boundaries, potentially executing whatever `shipit.yml` exists on that branch on the deploy host using the victim org's GitHub credentials.

Other handlers (`PushHandler`, `CheckSuiteHandler`) are similarly reachable to force spurious syncs/check-run refreshes against a victim org's stacks/commits using only an attacker-owned org's signing secret.

### Likelihood Explanation
This requires the Shipit instance to be configured with multiple GitHub organizations sharing the single `/webhooks` endpoint (an explicitly supported and documented configuration, see docs/setup.md "Using Multiple Github Applications"), and requires the attacker to be a legitimate operator/admin of at least one of those configured organizations — i.e., they possess a valid `webhook_secret` for their own org but have no privileges over the victim org. This is not a purely theoretical setup: Shipit is designed to support exactly this multi-tenant configuration, and the field mismatch (`owner.login` vs `full_name`) is unconditionally present in the routing logic for every non-membership event type.

### Recommendation
Bind the value used to select the verification secret to the same value used to resolve the affected repository/stack. Concretely, derive `repository_owner` from `repository.full_name.split('/').first` (or validate that `repository.owner.login` matches the owner segment of `repository.full_name`) before selecting the GitHub App used for `verify_webhook_signature`, and reject the webhook if they disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled, `webhook_secret: secretA`) and `VictimOrg` (attacker has no access), both installed on the same Shipit deployment (`config/secrets.yml` multi-org schema, docs/setup.md lines 182-209).
2. Attacker crafts a `pull_request` "opened" payload:
```json
{
  "action": "opened",
  "number": 999,
  "pull_request": { "head": { "ref": "attacker-branch" } },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "VictimOrg/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, raw_body)>` using `secretA`, which they legitimately know.
4. POST to `/webhooks` with header `X-Github-Event: pull_request`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully with `secretA` [1](#0-0) .
6. `OpenedHandler#process` resolves `Repository.from_github_repo_name("VictimOrg/victim-repo")` [7](#0-6)  and, if review stacks are enabled for that repository, provisions a new `Stack` with `branch: "attacker-branch"` against the real `VictimOrg/victim-repo` [8](#0-7) , despite the request never having been signed by `VictimOrg`'s own GitHub App.
