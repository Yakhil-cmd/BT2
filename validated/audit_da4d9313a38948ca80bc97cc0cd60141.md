## Confirmed vulnerable path

`Handler#repository_name` resolves the target stack/repository from `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the signature against based on a different field, `repository_owner` (`repository.owner.login`, falling back to `organization.login`) [2](#0-1) . `Shipit.github(organization:)` picks the secret purely from that organization string via `github_app_config` [3](#0-2) .

### Title
Webhook secret selection and target-repository resolution use different, independently attacker-controllable fields in a multi-org install - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In a multi-organization Shipit deployment (`secrets.github` keyed by organization, see `github_default_organization`/`github_organizations` [4](#0-3) ), the webhook signature is verified using the secret for the organization named in `repository.owner.login` / `organization.login`, but the handlers that act on the webhook (creating jobs, syncing commits, updating statuses) resolve the target `Stack`/`Repository` using the independent `repository.full_name` field [1](#0-0) , [5](#0-4) .

### Finding Description
The binding that must hold is: *organization whose secret authenticated the request* == *organization owning the repository being written to*. `verify_signature` computes `repository_owner` from the JSON body and uses it only to pick which per-org `webhook_secret` verifies `X-Hub-Signature` [6](#0-5) , start="59" end="61" />. Once verification passes, `Handler#stacks` and every concrete handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) look up the affected `Repository`/`Stack` from `repository.full_name`, a completely separate JSON field that is never compared against `repository_owner` [1](#0-0) .

Since the HMAC in `verify_webhook_signature` covers the full raw request body [7](#0-6) , this is not an integrity gap in the classic sense — but the *authorization* the signature is meant to convey ("this event genuinely originates from organization X, so it's fine to act on repositories under X") is never actually checked against which repository the payload claims to update. An entity that legitimately controls a Shipit-integrated GitHub App installation for organization A (and thus legitimately knows/holds org A's `webhook_secret`) can freely construct and correctly sign an arbitrary JSON body where `repository.owner.login`/`organization.login` = `"orgA"` (so `verify_signature` selects and successfully validates against the secret they hold) while `repository.full_name` = `"orgB/victim-repo"` (an unrelated organization's repository already registered in this Shipit instance). `Handler#repository_name` and every downstream handler will act on `orgB/victim-repo` using org A's validly-signed request.

Concretely, this lets such an attacker:
- Forge `push` events causing `GithubSyncJob` to sync arbitrary commits/branches into `orgB`'s stack, feeding attacker-chosen SHAs into the deploy pipeline [8](#0-7) , [9](#0-8) .
- Forge `status`/`check_suite` events to mark commits on `orgB`'s stack as green/passing, bypassing CI-gated deploy checks [10](#0-9) , [11](#0-10) .

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Forged/greenlit commit statuses can make Shipit believe unreviewed or malicious commits are deployable, and forged `push`/sync events can pull attacker-influenced commit metadata into another organization's stack — a cross-organization write achieved purely through the webhook endpoint, without needing `orgB`'s webhook secret, API tokens, or session.

### Likelihood Explanation
Requires: (1) the deployment uses the multi-organization `secrets.github` schema (documented, supported configuration), and (2) the attacker legitimately controls at least one configured organization/app installation (i.e., knows a valid per-org `webhook_secret`) while other organizations' repositories are also registered as Stacks in the same Shipit instance. This is a realistic shared/self-service Shipit deployment scenario and requires no privileged Shipit credentials — only knowledge of one's own, legitimately obtained webhook secret.

### Recommendation
After selecting the GitHub App config via `repository_owner` and verifying the signature, `WebhooksController`/`Handler` should additionally assert that `repository.full_name`'s owner segment (or `organization.login`) equals the `repository_owner` used to pick the verifying secret, rejecting the webhook (422) on mismatch. Alternatively, resolve the target `Repository` and confirm it belongs to the same organization whose secret verified the request before dispatching to any handler.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` containing `orgA: { webhook_secret: SECRET_A, ... }` and `orgB: { webhook_secret: SECRET_B, ... }`, with a `Stack` already registered for `orgB/victim-repo`.
2. As a party with legitimate knowledge of `SECRET_A` (e.g., an org admin of `orgA` who installed the Shipit GitHub App there), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(SECRET_A, body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `"orgA"`; `Shipit.github(organization: "orgA")` selects `SECRET_A`; `verify_webhook_signature` succeeds [6](#0-5) .
5. `PushHandler#stacks` resolves via `Handler#repository_name` = `"orgB/victim-repo"`, and `GithubSyncJob` is enqueued for `orgB`'s stack with the attacker-supplied `expected_head_sha`, despite the request never being authenticated for `orgB` [1](#0-0) , [5](#0-4) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
