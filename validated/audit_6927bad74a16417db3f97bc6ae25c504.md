### Title
AA can spend/issue non-transferable, definer-restricted assets without the `issued_by_definer_only` check when sending a real response unit (only the `bAir` dummy-unit path enforces it) - (File: aa_composer.js)

### Summary
This is a direct analog of the reported bug class: a state-changing operation is guarded by a validity check in one code path but the semantically equivalent path that performs the *same* action lacks that guard. In symio-core, `allocateForPartyB` enforces `notLiquidatedPartyB` while `transferAllocation`, which moves the same kind of funds, does not. In `ocore`, `aa_composer.js` has two parallel implementations of "AA sends payment messages and updates its balances": `sendDummyUnit()` (used for `bAir`/dry aggregated AA-to-AA calls) and the real `sendUnit()`/`completePaymentPayload()`/`issueAsset()` path (used for genuine response units). Only the dummy-unit path explicitly re-validates that an asset with `issued_by_definer_only` cannot have its balance driven negative (i.e. spent/issued) by a non-definer AA.

### Finding Description
`sendDummyUnit()` in `aa_composer.js` computes projected balances after applying an AA's outgoing payment messages, and if any non-base asset balance goes negative it explicitly checks the asset's issuance restriction before allowing the operation to proceed: [1](#0-0) 

This guard exists precisely because a negative asset balance for an AA means the AA is effectively issuing/spending more of a restricted asset than it legitimately holds, and for assets marked `issued_by_definer_only`, only the asset definer AA is allowed to do that (see the identical guard reused in the real issuance path, `issueAsset()`): [2](#0-1) 

However, the corresponding *real* unit-construction path, `sendUnit()` → `completePaymentPayload()`, which is used for all genuine (non-`bAir`) AA response units, does not perform this same negative-balance / `issued_by_definer_only` re-check before finalizing and saving the unit: [3](#0-2) 

The real path only calls `issueAsset()` when the payment payload explicitly needs an `issue` input to cover an outgoing amount for that specific payload (`target_amount - total_amount`), which is a narrower and structurally different check than the "did total projected balance across the whole response(s) for this asset go negative" check performed for the `bAir` path in `sendDummyUnit()`. This means the two entry points into essentially the same business rule ("an AA cannot spend/issue a definer-restricted asset it isn't authorized to issue") are not enforced identically. This is the same root cause pattern reported for `AccountFacet`: one legitimate way to reach the state-changing effect bypasses the guard that another, seemingly equivalent, way enforces.

### Impact Explanation
If an AA can be driven, via its own formula logic and outputs, into a state where it sends more of a definer-restricted asset than its tracked `aa_balances` entry allows (analogous to the `bOverflow`/negative-balance scenario handled explicitly in `sendDummyUnit`) through the real `sendUnit` path rather than the `bAir` chained-call path, the `issued_by_definer_only` restriction is not re-validated at unit-construction time. Any consensus-level check would then depend solely on `writer.js`/`validation.js` for the underlying payment message (`issued_by_definer_only` is enforced in `validation.js` case `"issue"` at the message level), but the AA-off-chain balance bookkeeping (`aa_balances` table) that ocore itself maintains as the AA's asset accounting can diverge from the on-chain constraint, since the `sendUnit` code path lacks the equivalent guard that exists in `sendDummyUnit`. This is a fund-integrity risk that could let AAs report/spend balances they should not control for restricted assets, corrupting `aa_balances` accounting used by other AAs and by wallets that trust this state.

### Likelihood Explanation
Medium likelihood: triggering this requires an AA definition whose formulas can cause a non-base asset balance to be spent beyond its `aa_balances` in the real (non-`bAir`) response path while that asset is `issued_by_definer_only` and the AA is not the definer. This requires careful crafting of an AA (or exploitation of an existing complex AA) but does not require any special network position, node compromise, or privileged actor — any unprivileged AA author/deployer can construct and trigger such an AA.

### Recommendation
Add the same negative-balance / `issued_by_definer_only` validation performed in `sendDummyUnit()` (lines 977-992) to the real `sendUnit()`/`completePaymentPayload()` path in `aa_composer.js`, ideally by factoring it into a single shared helper function called from both code paths, so that both real and dummy (`bAir`) unit construction enforce identical restrictions on definer-only assets before finalizing balances or issuing coins.

### Proof of Concept
Not independently executable within the scope of this review — this requires constructing an AA definition and a sequence of triggers that drive a non-base, `issued_by_definer_only` asset's `aa_balances` entry negative through the real (`bAir`-false) `sendUnit` path, and observing that the `objAsset.issued_by_definer_only && address !== objAsset.definer_address` guard present in `sendDummyUnit` (lines 989) is never evaluated for that path, unlike in `sendDummyUnit`. Confirming actual exploitability (i.e., that `completePaymentPayload`/`issueAsset` can indeed be driven to a negative-balance state without failing the underlying unit-level payment validation) would require running the AA test harness (`test/aa_composer.test.js`, `test/aa.test.js`) with a crafted asset+AA scenario, which was not performed here due to the read-only nature of this analysis.
