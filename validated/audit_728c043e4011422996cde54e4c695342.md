### Title
Label-controlled `PATH` environment variable overrides `Shipit.shell_paths` in `Command#unbundled_env`, allowing PR labelers to corrupt binary resolution for deploy commands - (File: lib/shipit/command.rb, app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` upcases attacker-controlled GitHub PR label names and merges them as environment variables into the task environment. Because `Command#unbundled_env` merges the caller-supplied `@env` hash *after* it sets `PATH` from `Shipit.shell_paths`, a PR label literally named `path` becomes `'PATH' => 'true'` in the final environment used for `PTY.spawn`, overriding Shipit's intended `PATH`.

### Finding Description
The broken binding: intended `Command#unbundled_env['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` for every deploy/task command, but with an attacker-labeled review-stack PR this becomes `Command#unbundled_env['PATH'] == 'true'`.

Code path:
1. An attacker (any GitHub user who can label their own PR against a repo with an active, non-archived review stack) applies a label named `path` (any case) to their PR.
2. `LabelCapturingHandler#capture_labels` at [1](#0-0)  stores label names verbatim into `pull_request.labels` on `labeled`, `unlabeled`, `opened`, or `reopened` events, guarded only by `stack.present? && !stack.archived?` — no relation to the label's identity.
3. `ReviewStack#env` at [2](#0-1)  builds `{ label_name.upcase => "true" }` for every label and merges it into the stack's environment hash, so `'path'` becomes `'PATH' => 'true'`.
4. `TaskCommands#env` at [3](#0-2)  merges `@stack.env` (containing the poisoned `PATH`) into the task's env, which is passed as `env:` into `Command.new`.
5. `Command#unbundled_env` at [4](#0-3)  computes `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` — the final `.merge(@env.stringify_keys)` means any `PATH` key inside `@env` (i.e., the attacker's label-derived value) wins over Shipit's constructed `PATH`.
6. `Command#start` passes this to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` at [5](#0-4) , so every subsequent shell command in the deploy (git, bundle, cap, etc.) runs with `PATH=true`.

No guard intercepts this: `LabelCapturingHandler`'s `ExplicitParameters` schema only validates types/presence of `labels[].name` as a `String`, not its content [6](#0-5) ; there is no reserved-key filtering (`EnvironmentVariables`, `Stack#env`, `Command` itself) that strips or protects `PATH`, `HOME`, `GEM_HOME`, etc. from label-derived or task-derived env before it reaches `Command#unbundled_env`.

### Impact Explanation
Any label named `path` (case-insensitive, since it's upcased) applied to a PR belonging to a review stack causes every command run for that review stack's deploys/tasks to execute with a broken `PATH` (`'true'`), breaking `git`, `bundle`, `cap`, etc. resolution via `Shipit.shell_paths`. This is a "command running that should not" scenario: the environment intended by the Shipit operator (`Shipit.shell_paths`) is silently replaced by attacker-supplied content, purely by naming a label on a PR the attacker controls, on a repository they may not even own (any contributor who can label PRs on the target repo — note GitHub requires "write" access to add labels in most cases, but that's a repo permission, not a Shipit permission). This affects the review stack for that PR only, not other stacks or repositories, and does not directly leak secrets or grant unauthorized deploys/merges on its own — it's a corruption of the deploy execution environment scoped to the PR's own review stack. It does not, by itself, demonstrate RCE: reaching arbitrary code execution requires an additional, independently-controlled condition (a relative-path executable resolvable ahead of intended binaries, which requires further conditions not established in code) — this remains speculative per the question's own admission ("depending on shell resolution", "in combination with any relative-path lookup").

### Likelihood Explanation
Preconditions: a review stack must exist and be active/not archived for the target repo, and the attacker must be able to add a label to a PR in that repo (this typically requires triage/write access on GitHub, not just PR authorship — GitHub does not allow arbitrary users to label PRs they don't have write access to, contradicting the audit's claim that "GitHub allows arbitrary label text" implies applying labels is available to any unprivileged submitter). Given labeling ability, the attack is trivial and repeatable for any review stack in scope.

### Recommendation
In `Command#unbundled_env`, protect reserved keys (at minimum `PATH`) by merging `@env` before setting `PATH`, or by explicitly re-asserting `PATH` after merging `@env`:
```ruby
def unbundled_env
  BASE_ENV.merge(@env.stringify_keys).merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}")
end
```
Additionally, `ReviewStack#env` should not allow PR labels to define arbitrary environment variable names verbatim — reserve/blocklist system variable names (`PATH`, `HOME`, `LD_PRELOAD`, `BUNDLE_*`, etc.) before merging label-derived keys into the stack env.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual, no live GitHub)
test "#env: a 'path' label overrides Shipit.shell_paths in Command#unbundled_env" do
  stack = shipit_review_stacks(:review_stack) # active, not archived
  stack.pull_request.update!(labels: ['path'])

  task = stack.tasks.build # or existing fixture task
  command = Shipit::Command.new('true', env: Shipit::TaskCommands.new(task).env, chdir: '.')

  expected_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  assert_equal 'true', command.unbundled_env['PATH']
  refute_equal expected_path, command.unbundled_env['PATH']
end
```
This confirms the binding `Command#unbundled_env['PATH'] == Shipit.shell_paths...` breaks once a `path` label is present, matching the code path traced above at [4](#0-3)  and [2](#0-1) .
