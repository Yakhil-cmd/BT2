### Title
`StatusHandler#process` writes GitHub statuses by bare SHA with no repository/stack scoping, letting a status delivered for one repository mutate a commit belonging to a different stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which is not scoped to the repository that authenticated the webhook, and calls `commit.create_status_from_github!(params)` on every match across every stack. Because the `commits` table only enforces uniqueness on `(sha, stack_id)` (not on `sha` alone), two different stacks/repositories can legitimately hold rows with the identical SHA, so a genuine, correctly-signed `status` webhook for repository A can also flip a commit's state in stack B's review/production stack.

### Finding Description
The broken binding: the code implicitly assumes `params.sha` uniquely identifies a commit for the repository that emitted the webhook, i.e. `Commit.where(sha: params.sha) == { the single commit belonging to repository_owner/repo }`. In fact `Commit.where(sha: params.sha)` can return **N commits across N different stacks**, because the schema-level uniqueness constraint is `add_index :commits, [:sha, :stack_id], unique: true` [1](#0-0)  — SHA alone is not unique. The fixtures themselves demonstrate two different stacks (`shipit_task_no_commits` and `check_deploy_spec`) sharing the exact same SHA `547578b362bf2b4df5903e1c7960929361c3435a` [2](#0-1) .

`StatusHandler#process` iterates every match with no repository filter: [3](#0-2) 

`Commit#create_status_from_github!` then unconditionally replicates the attacker-controlled `state`/`context` and re-evaluates deployability, scheduling merges or firing `deployable_status`/`commit_status` hooks: [4](#0-3) [5](#0-4) 

Upstream, `WebhooksController#verify_signature` only checks the HMAC signature against the GitHub App configuration keyed by `repository_owner` (the org/owner named in **the attacker's own payload**), it never checks that the resolved commit(s) belong to that repository: [6](#0-5) 

`GitHubApp#verify_webhook_signature` will accept **any** signature (or none) if no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [7](#0-6) .

Exploit flow: an attacker who controls any repository registered under an organization for which the Shipit GitHub App is installed (which is a precondition for `review_stacks_enabled true, allow_all` to auto-provision review stacks from external PRs at all) triggers or forges a `status` event with `sha` equal to a SHA that also exists in the victim stack (e.g. a shared ancestor commit, or the head SHA of a PR-based review-stack commit that was synced via `GithubSyncJob`), `context: security/scan`, `state: failure`. Because `StatusHandler#process` is unscoped, the status is also written onto the victim stack's commit, flips `deployable?`/`blocked?` via `add_status`, and can trigger `stack.schedule_merges` or block an in-flight deploy for a repository that never authenticated this specific status.

None of the existing guards catch this: `verify_signature` authenticates the webhook's claimed organization, not the specific commit/stack being mutated; the `ExplicitParameters` schema on `StatusHandler` only validates `sha`/`state`/`context` types, not repository ownership; there is no `stacks`/`repository` scope applied before `Commit.where(sha: ...)`.

### Impact Explanation
A payload delivered on behalf of one repository can mutate a commit/status/deployability state belonging to a different repository's stack — this is exactly the "payload for one repository mutating another's stack/commit" Critical class. Because review stacks with `allow_all` auto-provision and execute `shipit.yml`, a forced `success` status can trigger `stack.schedule_merges`/`ContinuousDeliveryJob` (unauthorized deploy) and a forced `failure` on `security/scan` can block deploys stack-wide (denial of legitimate deploys) for a victim that never received this webhook for its own repository. The blast radius is bounded by SHA collisions between the attacker's authenticated repository and the victim's stack, which is realistic for forks/mirrors of the same upstream history, shared vendored commits, or shared PR head SHAs synced into multiple stacks.

### Likelihood Explanation
Preconditions: the Shipit GitHub App must be installed on an organization/repo the attacker controls (or on an org without a configured `webhook_secret`, in which case `verify_webhook_signature` is a no-op), plus a SHA that collides between the attacker's repo and the victim's stack's commit history. Producing this collision reliably (e.g., via forks sharing the same ancestor commits, or via PR-based review stacks whose head SHA is later merged/detached and reused) requires some setup but no privileged Shipit credentials — the attacker never needs a Shipit session, API token, or the app's webhook secret for the victim organization.

### Recommendation
Scope `StatusHandler#process` (and any commit lookup by bare `sha`) to the repository that authenticated the request, e.g. resolve the `Repository`/`Stack` from the verified `repository_owner`/`repository.full_name` in the webhook payload and constrain `Commit.where(sha: params.sha, stack: { repository: repo })`, or add/enforce a stronger identity check before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "a status for one repository's SHA also mutates another stack's commit with the same SHA" do
  victim_stack = shipit_stacks(:shipit)          # review_stacks_enabled: true, allow_all
  victim_commit = shipit_commits(:some_shipit_commit)
  colliding_sha = victim_commit.sha

  attacker_stack = shipit_stacks(:cyclimse)      # unrelated repository/org
  attacker_commit = attacker_stack.commits.create!(
    sha: colliding_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus),
    authored_at: Time.now, committed_at: Time.now, message: "colliding sha"
  )

  before_state = victim_commit.reload.state
  refute_equal 'failure', before_state

  params = OpenStruct.new(sha: colliding_sha, state: 'failure', context: 'security/scan')
  Shipit::Webhooks::Handlers::StatusHandler.new.call(params.to_h)

  assert_equal 'failure', victim_commit.reload.state, "victim stack's commit state should NOT change from a status not scoped to its repository"
end
```
This test demonstrates the binding `Commit.where(sha:) == commits belonging to the requesting repository` is false: the write for the attacker's stack leaks into the victim stack's commit purely by SHA collision, with no repository check in `StatusHandler#process`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
