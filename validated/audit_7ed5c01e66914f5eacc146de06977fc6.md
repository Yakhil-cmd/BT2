### Title
Route-selected venue code can execute arbitrary token transfers under the caller’s authorization - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept attacker-influenced `swap` bytes and forward them to the configured aggregator after authorizing only the controller’s input transfer. [1](#0-0) 

The aggregator resolves each hop’s `pool` address from the payload’s unrestricted `assets` registry and invokes it through the selected venue adapter. [2](#0-1) 

Because the pool address is not allowlisted, a malicious contract can run during the swap and make an unrelated `token.transfer(victim, attacker, amount)` call that is attributed to the victim’s top-level `require_auth` tree. [3](#0-2) 

### Finding Description
The controller correctly limits its own router grant to one exact `token_in.transfer(controller, router, amount_in)` invocation, but that grant only constrains the router’s ability to move controller-held input; it does not constrain which contracts the router invokes afterward. [4](#0-3) 

A swap instruction obtains `pool`, `token_in`, and `token_out` directly from caller-provided registry indices. [5](#0-4) 

Every venue adapter ultimately invokes that route-selected pool address, such as Aquarius through `env.invoke_contract(pool, "swap", ...)`. [6](#0-5) 

The measured input/output checks validate the router’s balances, but they do not prevent the invoked contract from requesting authorization from the original account for an unrelated token transfer. [7](#0-6) 

A simulation therefore records the rogue transfer as a child of the victim’s controller authorization, and enforcement executes it when the victim signs the poisoned tree. [8](#0-7) 

### Impact Explanation
A malicious route can steal arbitrary tokens held in the victim’s wallet while still returning sufficient swap output for the controller operation to succeed. [9](#0-8) 

This crosses the intended authorization boundary: the user authorizes a lending strategy and its expected input movement, while route-selected code can add an unrelated child transfer to that same authorization tree. [10](#0-9) 

The test demonstrates loss of an unrelated wallet token without reducing the expected collateral output received by the strategy. [11](#0-10) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue, encode its address into `swap` bytes, and present the transaction or route to a victim through a wallet, quote flow, or crafted payload. [12](#0-11) 

Execution requires the victim to sign the authorization tree containing the extra token transfer, so the attack depends on insufficient wallet/simulation review rather than on privileged access. [13](#0-12) 

The affected entrypoint is directly reachable by an account owner or active delegate through `swap_collateral`, and the same forwarding pattern also serves `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [14](#0-13) 

### Recommendation
Bind route execution to an allowlist of audited venue contracts, or include a venue identity/implementation commitment in the signed strategy payload and reject any route that resolves a different address. [2](#0-1) 

At minimum, clients and transaction builders should simulate each strategy transaction, decode every signed authorization subtree, and reject any child invocation other than the expected token input transfer. [15](#0-14) 

The protocol-side fix should not rely on slippage checks or measured swap output, because those checks do not bound unrelated calls made by route-selected code. [16](#0-15) 

### Proof of Concept
The harness deploys `RogueHopPool`, whose `swap` function loads a victim, unrelated wallet token, attacker recipient, and amount, then calls `token.transfer(victim, attacker, amount)`. [3](#0-2) 

The malicious route supplies that pool address while declaring the normal USDC input and ETH output. [12](#0-11) 

Calling `swap_collateral(alice, account_id, usdc, 50_000_000_000, eth, route)` records a child authorization for `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [17](#0-16) [18](#0-17) 

When the same transaction is enforced with that child signed, Alice’s wallet token balance becomes zero and the attacker receives `WALLET_BALANCE`; without the child, the transfer is rejected and the strategy rolls back. [19](#0-18)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
