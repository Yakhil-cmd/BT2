### Title
Unbounded loop over all unstable units in `dataFeedExists`/`readDataFeedValue` allows AA data-feed lookups to be DoS'd by unstable-unit spam - (File: `data_feeds.js`)

### Summary
When an AA formula uses `data_feed` or `in_data_feed` and the caller allows unstable data feeds (`bAA` mode), `dataFeedExists` and `readDataFeedValue` iterate over the entire `storage.assocUnstableMessages` map — i.e. every currently-unstable unit in the DAG — instead of only the units authored by the relevant oracle addresses. This mirrors the reported bug class: a collection whose size is driven by ordinary, unprivileged unit posting is walked in full on a hot execution path (AA trigger/response evaluation), so growth of that collection degrades or can stall the operation for everyone.

### Finding Description
`dataFeedExists` in `data_feeds.js` does:
```
for (var unit in storage.assocUnstableMessages) {
    var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
    ...
    if (_.intersection(arrAddresses, objUnit.author_addresses).length === 0)
        continue;
    storage.assocUnstableMessages[unit].forEach(function (message) { ... });
}
``` [1](#0-0) 

and `readDataFeedValue` has the identical pattern:
```
for (var unit in storage.assocUnstableMessages) {
    var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
    ...
    storage.assocUnstableMessages[unit].forEach(function (message) { ... });
}
``` [2](#0-1) 

Both loops filter candidates *after* iterating (`objUnit.bAA`, mci range, `_.intersection(arrAddresses, objUnit.author_addresses)`), meaning the full outer `for...in` scan over `assocUnstableMessages` happens regardless of how irrelevant most entries are to the query. `assocUnstableMessages` is populated for every unit that has not yet reached stability — i.e., every unit currently posted to the network but not yet finalized — and is only pruned once units stabilize [3](#0-2) .

These functions are reachable from `oscript`/formula evaluation used by AAs: `formula/evaluation.js`'s `data_feed` and `in_data_feed` opcodes call `dataFeeds.readDataFeedValue` and `dataFeeds.dataFeedExists` respectively, passing `bAA` when evaluating for an AA trigger response. [4](#0-3) [5](#0-4) 
Because an AA's formulas can invoke `data_feed`/`in_data_feed` multiple times (e.g. inside loops bounded only by the formula's op/complexity budget), each invocation re-walks the full unstable-unit set, multiplying the cost of a single AA trigger by however many unstable units currently exist network-wide plus however many `data_feed` calls the formula makes.

Unlike the Sherlock report's `protectionInfos` (an array that a single buyer directly grows forever), here the attacker-controlled quantity is "number of currently-unstable units," which any unit poster increases simply by posting units faster than they stabilize (e.g., bursts of low-value units, or an AA that keeps re-triggering itself to keep its own response units unstable). While this collection eventually shrinks as units stabilize, an attacker can sustain a large unstable set by continuously posting, so the DoS is renewable rather than permanent, but it is unbounded on the poster's side and checked with no size cap anywhere in this code path.

### Impact Explanation
Any AA that relies on `data_feed`/`in_data_feed` with `bAA`-mode reads becomes progressively more expensive to evaluate as the number of unstable units in the DAG grows, because every such call rescans the full unstable set. Since AA trigger/response computation happens synchronously as part of unit processing (needed to determine validity, state changes, and fund movements), this can slow down or stall processing of triggers for any AA using data feeds, delaying premium/fee-like state updates and payouts analogous to the original report's "premium not accrued" and "protections not expired" harms — here manifesting as AA responses that time out, get delayed, or make nodes fall behind, risking divergence in whether/when a trigger's effects (fund transfers, state updates) are applied, and enabling a poster to grief specific AAs or slow the network's ability to process new units in a timely, consistent manner.

### Likelihood Explanation
Likelihood is bounded by the requirement to keep many units unstable simultaneously (which costs network bandwidth/fees to sustain) — this is somewhat more costly than the trivial `protectionInfos` spam in the original report, but still requires no special privilege: any unit poster can flood ordinary units, and any AA developer/trigger sender can design an AA that keeps re-triggering to inflate the unstable set feeding its own `data_feed` calls. No governance/authorization is needed, only unit fees, which is exactly the class of "unprivileged actor bloats an unbounded collection scanned on a hot path" that this report targets.

### Recommendation
Filter `storage.assocUnstableMessages` by oracle address before iterating (e.g., maintain an index of unstable units keyed by author address, or intersect `arrAddresses` against a precomputed address→unstable-unit map) instead of scanning every unstable unit and discarding non-matches inside the loop. Additionally, consider capping the number of unstable data-feed candidates considered per call, and reject/bounce AA execution if that cap is exceeded, to keep worst-case cost independent of global network congestion.

### Proof of Concept
1. Attacker (or a self-triggering AA) posts a sustained stream of units so that `storage.assocUnstableMessages` remains large (many hundreds/thousands of unstable units) — achievable since it only requires posting units faster than the network can stabilize them.
2. Any AA whose formula uses `in data feed`/`data_feed` with unstable reads (`bAA` path) is triggered.
3. `dataFeeds.dataFeedExists`/`readDataFeedValue` executes the `for (var unit in storage.assocUnstableMessages)` loop [1](#0-0) [2](#0-1) , iterating the entire inflated unstable set for every such formula call.
4. Repeat step 2 across many AA triggers (or a formula that calls `data_feed` multiple times), multiplying node-side compute cost and delaying/failing timely processing of legitimate AA triggers that depend on data feeds.
