### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login`, but the repository actually acted upon is resolved from the independent `repository.full_name` field — allowing cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but every webhook `Handler` resolves the `Stack`/`Repository` it actually mutates from a completely separate payload field, `repository.full_name`. Because these two fields are never cross-checked, an attacker who controls the webhook secret for *any* organization onboarded to the same Shipit instance can forge a payload whose `repository.owner.login` matches their own org (so the signature validates with their known secret) while `repository.full_name` names a target repository belonging to a different organization. This is the same class of bug as the reported issue: one field is used to gate/authorize the operation, while a materially different, unauthenticated field determines what the operation actually acts on.

### Finding Description
`verify_signature` computes the "authorizing organization" like this: [1](#0-0) [2](#0-1) 

The HMAC signature is verified against the secret configured for `repository_owner`: [3](#0-2) 

Once verification passes, `create` dispatches the *entire raw payload* to the registered handlers: [4](#0-3) 

Every handler resolves the target `Stack`/`Repository` independently, using `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

For example, `PushHandler` uses this `stacks` scope directly to trigger `GithubSyncJob` for every matching stack: [6](#0-5) 

The binding that should hold is:
`organization whose secret authenticated the request == owner of repository.full_name that the handler acts on`

Nothing in the controller or in `Handler#repository_name` enforces this equality. `repository.owner.login` and `repository.full_name` are two independent, attacker-supplied JSON fields inside the same signed body; the signature only proves "the sender knows secret S for organization O" — it says nothing about which repository the rest of the payload names. An attacker who legitimately controls (or has been issued webhook credentials for) one onboarded organization can craft a payload where `repository.owner.login`/`organization.login` = their own org (so `Shipit.github(organization: repository_owner)` picks a secret they know) while `repository.full_name` = `victim-org/victim-repo`, an entirely different onboarded stack.

### Impact Explanation
Because handlers key off `repository.full_name` alone, this allows an attacker who is authorized for one organization's webhook channel to forge GitHub events (`push`, `status`, `check_suite`, `deployable_status`, `pull_request`, `merge`, `membership`, etc.) that are attributed to and acted upon for a *different* organization's repository/stack, without ever knowing that victim organization's `webhook_secret`. This is a cross-repository write / authentication-bypass primitive: the signature check is supposed to prove the request is legitimately about the named repository, but it only proves legitimacy for the *signing* organization, decoupled from the repository name actually processed. Depending on which handler is invoked this can range from spurious `GithubSyncJob` triggers on an unrelated stack, to injecting statuses/events that feed into deploy-gating logic (`required_statuses`, `deployable?`) for a stack the attacker's organization does not own.

### Likelihood Explanation
Exploitation requires only that the attacker be authorized to send webhooks for *some* organization already onboarded to the same Shipit instance (a normal, unprivileged position relative to the *victim* repository/stack) and craft a JSON body with the `repository.owner.login` and `repository.full_name` fields set to different organizations. No GitHub App private key, `api_clients_secret`, session token, or victim-repo write access is required — only knowledge of one's own onboarded organization's `webhook_secret`, which is exactly the credential this endpoint is designed to accept from that organization.

### Recommendation
In `Handler#repository_name` (and in `WebhooksController#repository_owner`), require that the organization used for signature verification match the owner encoded in `repository.full_name` before any handler is allowed to act — i.e., derive both values from the same trusted field, or explicitly assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0` before dispatching to handlers.

### Proof of Concept
1. Attacker's organization `attacker-org` is legitimately onboarded to the Shipit instance with its own `webhook_secret` (known to the attacker).
2. Attacker builds a `push` (or `status`/`pull_request`) JSON payload with:
   - `repository.owner.login` = `"attacker-org"`
   - `repository.full_name` = `"victim-org/victim-repo"`
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC(webhook_secret_for_attacker_org, raw_body)`, per `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"` (`app/controllers/shipit/webhooks_controller.rb:59-62`), fetches `attacker-org`'s app, and the signature validates successfully.
5. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handler on the full payload (`app/controllers/shipit/webhooks_controller.rb:10-15`).
6. The handler resolves the target stack via `repository.full_name` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), acting on `victim-org`'s stack even though only `attacker-org`'s secret authenticated the request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
