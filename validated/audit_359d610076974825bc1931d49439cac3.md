### Title
Cross-tenant webhook forgery via divergent `repository.owner.login` (signature-selection) vs `repository.full_name` (handler-target) fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` in the request body [1](#0-0) . The actual mutation target used by `PushHandler`, `CheckSuiteHandler`, and the `PullRequest` handlers is derived from a *different* body field, `repository.full_name`, via `Handler#stacks`/`Handler#repository_name` [2](#0-1) . Nothing cross-checks that `repository.owner.login` and `repository.full_name` refer to the same repository, so an attacker can bind signature verification to one (secret-less) org while routing the handler's writes to a completely different, victim organization's repository/stack.

### Finding Description
The binding this code implicitly assumes is:
`organization used to select the GitHub App/secret in verify_signature (repository.owner.login)` == `organization/repository whose records get mutated by the handler (repository.full_name)`

Trace:
1. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) .
2. `GithubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank/unset: `return true unless webhook_secret` [4](#0-3) . `webhook_secret` is explicitly documented as optional in `docs/setup.md`, so a real multi-org Shipit deployment can have one org configured without a secret while others do.
3. `WebhooksController#create` then dispatches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` where `event` comes only from the `X-Github-Event` header [5](#0-4) .
4. Inside the handler base class, the target repository/stack is resolved from `payload.dig('repository', 'full_name')` — a *separate* string field from `repository.owner.login` [2](#0-1) , used by `PushHandler` and `CheckSuiteHandler` [6](#0-5) [7](#0-6) .

Because the attacker fully controls the raw JSON body, they can set `repository.owner.login` to an org with no configured `webhook_secret` (satisfying step 1/2 trivially) while setting `repository.full_name` to `victim-org/victim-repo` (satisfying step 4 against the real victim). No code compares these two fields. `StatusHandler` is even weaker: it never touches `repository` at all and looks up `Commit.where(sha: params.sha)` globally [8](#0-7) , so any known commit SHA across any tenant can have its CI status forged once *any* org's `repository_owner` bypass is available.

None of the existing guards prevent this: `drop_unhandled_event` only checks the event name is registered [9](#0-8) ; `verify_signature` never inspects `repository.full_name` or reconciles it with `repository_owner`; `ExplicitParameters` schemas in each handler only validate shape/types, not cross-tenant consistency (see `PushHandler`/`CheckSuiteHandler` `params` blocks).

### Impact Explanation
An attacker who knows (a) the login of any Shipit-configured GitHub org lacking a `webhook_secret`, and (b) the `owner/repo` full name (public) and, for status forgery, a commit SHA (public) of a victim repository, can:
- Trigger `GithubSyncJob`/`sync_github` on an arbitrary victim stack via a forged `push` event (`PushHandler`).
- Trigger `RefreshCheckRunsJob` against arbitrary victim commits via `check_suite`.
- Write forged CI statuses onto arbitrary victim commits via `status`, potentially unblocking merge/deploy gating logic that depends on commit status.
This is a cross-tenant authorization bypass: a payload for one (attacker-controlled, secret-less) tenant mutates another tenant's stack/commit records, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Requires at least one org in the Shipit deployment's `github:` config to have no `webhook_secret` set — an explicitly supported/optional configuration per `docs/setup.md`. Given that precondition, the attacker needs no Shipit session, API token, or GitHub secret: just the target's public `owner/repo` name and, for the status handler, a public commit SHA. The attack is a single unauthenticated `POST /webhooks` request and is fully repeatable against any repository/stack tracked by Shipit.

### Recommendation
Cross-validate `repository.owner.login` against `repository.full_name`'s owner segment (and, for `organization` events, against the resolved `repository_owner`) before dispatching to handlers, rejecting mismatches. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is absent in production configurations; require a secret to be configured for all orgs, or at minimum fail closed when config for an org is incomplete. `StatusHandler` should scope `Commit` lookup by the verified repository/organization rather than a global `sha` lookup.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "forged push event with secret-less owner but victim full_name syncs victim stack" do
  # Precondition: config org "secretless-org" has no webhook_secret (per fixtures)
  request.headers['X-Github-Event'] = 'push'
  body = JSON.parse(payload(:push_master))
  body['repository']['owner']['login'] = 'secretless-org'   # used by verify_signature
  body['repository']['full_name'] = @stack.repository.full_name # victim, used by handler
  expected_head_sha = body['after']

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: @stack.id, expected_head_sha:]) do
    post :create, body: body.to_json, as: :json
  end
  assert_response :ok
end
```
Assert on both sides of the binding: `Shipit.github(organization: 'secretless-org').verify_webhook_signature` returns `true` unconditionally (no real secret used), while `GithubSyncJob` is still enqueued for `@stack` (the victim), proving the org that "admitted" the request and the org whose stack was mutated diverge.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
