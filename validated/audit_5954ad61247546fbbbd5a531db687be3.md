This confirms the premise of the attack scenario is false. Multi-org GitHub App configuration in Shipit is **not auto-provisioned** by an attacker installing a GitHub App on their own org. It requires the Shipit **operator** to manually add an entry to `config/secrets.yml` (`github.<organization>.webhook_secret`, `app_id`, `installation_id`, `private_key`, etc.) for each organization, as shown in `docs/setup.md:182-209` and `config/secrets.development.shopify.yml`. `Shipit.github_app_config` at [1](#0-0)  only looks up organizations that the operator has pre-configured; an unconfigured org raises `GithubOrganizationUnknown` at [2](#0-1) . There is no code path in this engine where installing a GitHub App on an arbitrary org grants that org a `webhook_secret` entry known to Shipit — it must be explicitly configured by the operator ahead of time.

Given that, the attacker cannot "become" a verified organization named `attacker-org` unless the Shipit operator has already configured `attacker-org` as one of its trusted GitHub orgs (i.e., the operator's Shipit instance is multi-tenant and explicitly serves `attacker-org` as a legitimate customer/org). That is a materially different and much stronger precondition than "attacker installs GitHub App on their own org" (an unprivileged action) — it requires the *operator* to have configured `attacker-org` in `secrets.yml` with a real `webhook_secret`.

However, even granting that stronger precondition (multi-tenant Shipit with both `attacker-org` and `victim-org` configured — a realistic scenario, e.g. `test/dummy/config/secrets_double_github_app.yml`), the described exploit path is real: `verify_signature` at [3](#0-2)  selects the `GitHubApp` (and thus the HMAC secret) using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` at [4](#0-3) . But `Handler#repository_name`, used by `PushHandler#process` via `stacks`, reads a completely independent field, `payload.dig('repository', 'full_name')` at [5](#0-4) , which is then split into owner/name in `Repository.from_github_repo_name` at [6](#0-5) . Nothing in `WebhooksController#create` or `Handler#initialize` cross-checks that `repository.owner.login == repository.full_name.split('/').first`, so a payload can legitimately have these two fields disagree, and the signing organization (used only for signature verification) need not be the organization whose stack gets mutated.
