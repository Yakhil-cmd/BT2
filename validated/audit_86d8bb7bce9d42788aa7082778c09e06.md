### Title
`pull_request` webhook signature verified against `repository.owner.login`'s org while `ReopenedHandler` mutates the repo resolved from `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate an incoming webhook using `repository_owner`, which reads `params.dig('repository','owner','login')` [1](#0-0) . The `ReopenedHandler`, however, resolves the actual `Repository`/`ReviewStack` to mutate using `params.repository.full_name` [2](#0-1) . These two fields are never checked for consistency, so an attacker who controls both fields in a forged JSON payload can pick an org (`owner.login`) with no `webhook_secret` configured — or one they otherwise control — for signature purposes while pointing `full_name` at a different org/repo whose `ReviewStack` gets unarchived.

### Finding Description
The broken binding: the code implicitly assumes `params.repository.owner.login == owner_of(params.repository.full_name)`. This is never enforced.

Path:
1. `WebhooksController#create` parses the raw JSON body and dispatches `Shipit::Webhooks.for_event(event)` handlers [3](#0-2) .
2. Before that, `verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(...)`, using only `repository.owner.login` (or `organization.login`) to pick which per-org `webhook_secret` to check against [4](#0-3) .
3. `GitHubApp#verify_webhook_signature` returns `true` immediately `unless webhook_secret` is configured for that org [5](#0-4) , so if the attacker names an org with no configured secret in `repository.owner.login`, signature verification is trivially bypassed regardless of the actual signature header.
4. Once past `verify_signature`, `ReopenedHandler#process` calls `stack.unarchive!` when `respond_to_pull_request_reopened?` is true [6](#0-5) .
5. `stack`/`repository` are derived exclusively from `params.repository.full_name`, completely independent of the `owner.login` value used in step 2/3 [7](#0-6) .

Result: an attacker forges a `pull_request`/`reopened` payload with `repository.owner.login` = an org they control or that has no webhook secret configured, and `repository.full_name` = `"victim-org/victim-repo"`. The signature check passes (or is bypassed) against the wrong org, and the handler unarchives/recreates a `ReviewStack` belonging to the victim repository — a write to a repository/stack that never authenticated the request.

Regarding the "shared commit SHA with attacker repo" component of the question: I could not find any bare-SHA-based commit/status lookup inside `ReopenedHandler` or its `ReviewStackAdapter` dependency that would need a colliding SHA to trigger cross-tenant effects — the handler resolves the target stack purely via `repository.full_name` + pull request number, not by commit SHA. I was unable to fully inspect `ReviewStackAdapter`'s internals within the available context, so I cannot confirm or rule out a secondary SHA-collision amplification path there; this part of the claim remains unverified. The core owner/full_name divergence, however, is independently sufficient and confirmed in code to produce the cross-tenant mutation.

### Impact Explanation
This lets an unauthenticated internet attacker (no Shipit session, no API token, no webhook secret) unarchive/recreate a `ReviewStack` for an arbitrary victim repository's pull request, purely by crafting a JSON body and any acceptable-looking headers, as long as they can name an org with a missing/known webhook secret in the `owner.login` field. This is a cross-tenant state write — one repository's (attacker-chosen, low-value) organization identity is used to authenticate a mutation applied to a different repository's `ReviewStack` — matching the Critical category "a payload for one repository mutating another's stack." It is repeatable against any repository whose `full_name` the attacker knows, for every `pull_request`/`reopened` event.

### Likelihood Explanation
Preconditions: (a) at least one org configured in `Shipit.github_teams`/org config with no `webhook_secret` set (or one the attacker otherwise knows), which the attacker supplies as `repository.owner.login`; (b) `review_stacks_enabled` and a provisioning behavior on the victim repo that allows unarchiving (`provisioning_behavior_allow_all?` or label-based) [8](#0-7) ; (c) knowledge of the victim `repository.full_name` and a PR number/state satisfying the `ExplicitParameters` schema. All of these are plausible/discoverable, and the request itself is a single unauthenticated `POST /webhooks` call, making this cheap and repeatable.

### Recommendation
In `WebhooksController#verify_signature`, verify that the org used to select the webhook secret matches the org that owns the repository resolved from `repository.full_name` (or simply always derive the verifying org from `full_name`'s owner segment, not from the separate `owner.login` field). Additionally, each handler should assert `params.repository.full_name`'s owner matches the org whose secret was actually used to authenticate the request before mutating any record.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in `Shipit.github`: `"attacker-org"` with no `webhook_secret`, and `"victim-org"` with a configured `webhook_secret`.
2. Create `victim-org/victim-repo` as a `Shipit::Repository` with `review_stacks_enabled` and `provisioning_behavior_allow_all?` true, plus an existing open PR / `ReviewStack` marked archived.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, a body `{"action":"reopened","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"}, "pull_request": {...}, "sender": {...}}`, and an `X-Hub-Signature` computed with any arbitrary secret (or omitted, since `attacker-org` has no secret configured).
4. Assert: before request, `victim_repo.review_stacks.find_by(...).archived? == true`; after request, `head :ok` returned and `archived? == false` — i.e., the victim's stack was mutated by a request that never authenticated against `victim-org`'s secret.
5. Equality under test: `repository_owner (used for signature) == owner_of(repository.full_name) (used for mutation)` — assert this is false in the forged payload while the mutation still occurs, proving the invariant is violated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
