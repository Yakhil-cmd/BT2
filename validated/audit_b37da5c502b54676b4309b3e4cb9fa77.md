### Title
CCMenu URL grants an unscoped, global `read:stack` API token instead of one scoped to the requested stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` is meant to hand a user a token that authorizes read-only CCTray/CCMenu status polling for one specific stack. Instead, the `ApiClient` it mints (or reuses) is never bound to that stack, so the resulting token authorizes read access to **every** stack in the installation, and the CCMenu endpoint that consumes it doesn't even enforce the (missing) scope.

### Finding Description
`CCMenuUrlController#fetch` builds the token like this: [1](#0-0) 

`client` is resolved via:
```ruby
ApiClient.create_with(permissions: %w[read:stack])
         .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
```
Neither `create_with` nor the `find_or_create_by!` conditions include `stack:`, so the created (or reused) `ApiClient` record always has `stack_id = nil`, no matter which `stack_id` the user requested the URL for. `ApiClient` explicitly allows this: `belongs_to :stack, optional: true`. [2](#0-1) 

This `stack_id` is what the rest of the API uses to scope reads:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
``` [3](#0-2) 

Because `stack_id` is nil, `current_api_client.stack_id?` is false and `stacks` resolves to `Stack.all` — i.e. this token, which the UI presents and the user shares as a "single stack" CCMenu URL, is in fact a global `read:stack` credential usable via HTTP Basic Auth against any `Shipit::Api::BaseController`-derived endpoint (e.g. `Api::StacksController#index/#show`, `Api::CommitsController#index`, `Api::DeploysController#index`) for **any** stack, not just the one it was generated for.

The consuming controller compounds the same binding break independently: `Api::CCMenuController` overrides `stack` to bypass the scoping helper entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This never calls the `stacks` scoping method from `BaseController`, so even if the token's `stack_id` were correctly set, `Api::CCMenuController#show` would still accept an arbitrary `params[:stack_id]` and return that stack's build/deploy status, regardless of what stack the token is bound to. Also note `find_or_create_by!(creator:, name:)` means a single "CCMenu Client" record is reused across *every* stack a given user ever fetches a CCMenu URL for — one long-lived, unscoped, shareable token per user, for the lifetime of the app.

The binding broken: **the stack a token is presented (and named/labelled) as authorizing ≠ the stack(s) it actually touches** — it authorizes exactly one stack in the UI/URL, but touches all stacks via both (a) the never-set `stack_id` on the `ApiClient` record, and (b) `CCMenuController`'s bypass of stack-scoped lookup.

### Impact Explanation
Any token obtained through this legitimate, low-friction feature (intended only to expose a single stack's pass/fail status to a CI dashboard/CCTray tool, embedded as a plaintext query-string credential meant to be pasted into third-party monitoring software) becomes a durable, global read-access credential for the entire Shipit deployment estate: names, branches, deploy status, lock state, and deploy history of every stack, including stacks the requester may have no business viewing, and stacks created after the token was minted. Because the token is designed to be embedded in external, less-trusted systems (RSS-style dashboards), the practical exposure window and blast radius are large. This matches the "unauthorized/unauthenticated-scope read of stack state" impact class: the token holder gets authorization far beyond what the UI and naming imply.

### Likelihood Explanation
High. No special privilege is needed beyond the ordinary ability to view one stack and click "get CCMenu URL" (a completely standard, low-privilege workflow every Shipit user is expected to use for CI-status badges/dashboards). The bug is deterministic — every single such token is unscoped by construction — not a race condition or edge case.

### Recommendation
- Include `stack:` in both `create_with` and the `find_or_create_by!` lookup keys in `CCMenuUrlController#client`, so a distinct token is minted per (creator, stack) and its `stack_id` is actually persisted.
- Remove `Api::CCMenuController`'s private `stack` override and rely on `BaseController#stack`/`#stacks` so the `current_api_client.stack_id` scope is enforced consistently.
- Consider auditing/rotating existing `ApiClient` rows named `'CCMenu Client'` with `stack_id: nil`, since they are currently global tokens.

### Proof of Concept
1. As any authenticated Shipit user, request `GET /stacks/:stack_a/ccmenu_url` → response contains `ccmenu_url` with `?token=<T>`.
2. Inspect `ApiClient.last` (or observe server-side): `stack_id` is `nil`, `permissions == ["read:stack"]`.
3. Use `<T>` as HTTP Basic Auth password against `GET /api/stacks` or `GET /api/stacks/:stack_b/commits` for an unrelated stack `stack_b` the user was never granted a scoped token for → request succeeds (200) because `current_api_client.stack_id?` is `false`, so `stacks` resolves to `Stack.all`.
4. Alternatively, call `GET /api/stacks/:stack_b/ccmenu?token=<T>` directly — succeeds regardless of the token's (absent) scope because `Api::CCMenuController#stack` never consults `current_api_client.stack_id`.

  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    def client
