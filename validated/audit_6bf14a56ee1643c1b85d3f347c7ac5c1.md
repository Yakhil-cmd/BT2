## Finding: Unsafe live-array iteration in `foreach`/`map`/`filter`/`reduce` allows an AA's own array state to be mutated mid-iteration, corrupting element indices similarly to the xen-netback list-iteration UAF pattern

### Title
Iterating a live, unlocked array reference in oscript `foreach`/`map`/`filter`/`reduce` while the per-element callback can delete/splice from the *same* array corrupts iteration and AA accounting - ([File: formula/evaluation.js])

### Summary
The Linux CVE fixes a class of bug where a list is walked with an iterator that assumes elements are stable, while a nested code path is allowed to free/remove list members during the walk, corrupting the iterator. The oscript evaluator has a structurally analogous bug: `foreach`/`map`/`filter`/`reduce` snapshot only the array's *length* for a bounds check, then iterate the *same live array object* by index via `async.eachOfSeries`, while invoking a user-defined callback function that — because closures capture object references, not deep copies — can mutate (via `delete(...)`, which calls `Array.prototype.splice`) that very same array in place during the walk.

### Finding Description
In `formula/evaluation.js`, the `foreach`/`map`/`filter`/`reduce` opcode evaluates the target expression `res` and then iterates it directly: [1](#0-0) 

`arrElements` is a direct reference to `res.obj` (not a defensive copy) when the target is an array, and `async.eachOfSeries` walks it by index while invoking a caller function for each element.

The per-element callback can be a user-declared function that closes over the *same* outer local variable. `callFunction` copies scope variable names into the function's local scope by reference, not by deep clone, for object-typed locals: [2](#0-1) 

Because `func_locals[name] = locals[name]` assigns the same `wrappedObject` instance, a `delete(...)` statement executed *inside* that callback function operates on the identical underlying array that the outer `foreach`/`map`/`filter`/`reduce` is still iterating. The `delete` opcode performs an in-place `Array.prototype.splice` on that shared array: [3](#0-2) 

Splicing an element out of `arrElements` while `async.eachOfSeries` is mid-walk shifts every subsequent element left by one position. Since the iteration continues to read `arrElements[index]` for the next step, this causes:
- silent skipping of array elements that were never passed to the callback, and
- reprocessing of an element that shifted into an already-visited index,

exactly analogous to the kernel bug where continuing `list_for_each_entry`-style traversal after a concurrent removal reads stale/incorrect list state instead of the intended next entry.

### Impact Explanation
`foreach`/`map`/`filter`/`reduce` are reachable directly from any AA definition's oscript code, and thus indirectly from any unprivileged unit poster who triggers an AA (a permitted attack surface: "AA definitions and triggers, oscript/ojson evaluation"). If an AA author writes (intentionally or unwittingly) a pattern where a loop callback shares scope with, and deletes from, the array/object being iterated — e.g. a ledger-style AA that iterates an array of pending obligations/allocations, deducting balances or marking items processed as it goes, and calls `delete()` on that same array to "consume" an item — the item skipping/re-processing corruption can cause the AA to under- or over-account funds relative to its own bookkeeping (state vars / balances), i.e. AA fund loss or fund freezing for the address, without the AA's own logic ever detecting an inconsistency, since the evaluator itself silently proceeds. Because execution is fully deterministic (single-threaded JS, same nearley-parsed formula, same MCI-gated semantics on all full nodes), this does not itself split node consensus, but it is a genuine, exploitable state-corruption primitive inside the deterministic execution engine that governs AA fund custody.

### Likelihood Explanation
Any attacker who can post a trigger to an AA using this pattern (or who authors such an AA template that is then used by real depositors) can reliably reproduce the corruption — it requires no race condition or timing, only a `foreach`/`map`/`filter`/`reduce` whose callback function is declared in a scope containing the target array and calls `delete()` (or an equivalent in-place mutation) on it. This is fully deterministic and 100% reproducible via a single AA trigger/oscript formula.

### Recommendation
- In the `foreach`/`map`/`filter`/`reduce` handler (`formula/evaluation.js` around lines 2370-2465), snapshot `arrElements` with a shallow copy (`res.obj.slice()`) before starting `async.eachOfSeries`, so mutation of the original `wrappedObject` during callback execution cannot affect the ongoing iteration.
- Alternatively/also, mark the iterated object as `frozen` for the duration of the loop (similar to the existing `res.frozen` propagation to element values) and have the `delete`/assignment opcodes reject mutation of a frozen object, the same way they already reject mutation of variables explicitly frozen via `freeze()` (`formula/evaluation.js:2312-2313`).
- Add a regression test that declares a function sharing scope with the iterated array, calls `delete($arr, 0)` inside the callback, and asserts that `map`/`filter`/`reduce`/`foreach` still visits every original element exactly once with correct index/key/value.

### Proof of Concept
Conceptual oscript formula demonstrating the corruption (illustrative; exact syntax per `test/formula.test.js` conventions, e.g. `test/formula.test.js:5786-5800` for `map` usage):
```
$arr = [10, 20, 30, 40, 50];
$sum = 0;
$consume = ($x) => {
    $sum += $x;
    delete($arr, 0);   // mutates the SAME array object being iterated by map() below
    $x
};
$result = map($arr, 10, $consume);
$result   // expected [10,20,30,40,50]-derived array, but elements get skipped due to in-place splice during iteration
```
Because `$consume` is declared after `$arr` exists, `func.scopeVarNames` includes `arr`, and `callFunction` copies the same `wrappedObject` reference into the function's local scope (`formula/evaluation.js:3065-3081`). Each call to `delete($arr, 0)` shifts `arrElements` (identical to `$arr.obj`, `formula/evaluation.js:2371`) underneath the ongoing `async.eachOfSeries` loop (`formula/evaluation.js:2379-2381`), causing elements to be skipped from `$result`/`$sum` versus what the AA logic intends — the oscript-level analog of iterating a list while entries are concurrently freed out from under the iterator.

*Note: I was unable to execute this formula in a live test environment as part of this investigation; the analysis is based on static code tracing of `formula/evaluation.js` and `formula/validation.js`. A background Devin session with `test/formula.test.js` execution access would be needed to confirm the exact skip/duplicate behavior with a runnable reproduction.*
