### Title
Unauthenticated cross-repository/cross-organization CI status forgery enables unauthorized merges and deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* organization's webhook secret to check against based solely on `repository.owner.login` (or `organization.login`) taken from the untrusted request body, and — when that organization has no `webhook_secret` configured — skips signature verification entirely. Crucially, none of this verified/unverified "organization" identity is ever cross-checked against the data the event handlers actually act on. In particular, `Shipit::Webhooks::Handlers::StatusHandler` resolves target `Commit` records purely by `sha`, with **no repository or organization scoping at all**, unlike every other handler which resolves via `Repository.from_github_repo_name`. This breaks the intended trust binding: *the organization whose webhook was authenticated* ≠ *the repository/stack whose state is actually mutated*.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-49) computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (lines 59-62) is read directly from the JSON body: `params.dig('repository','owner','login') || params.dig('organization','login')`.

`lib/shipit/github_app.rb#verify_webhook_signature` (lines 76-83):
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
If the organization named in the (attacker-controlled) payload has no `webhook_secret` configured — an explicitly supported, documented configuration (`docs/setup.md`: "Webhook secret (optional)"; `config/secrets.development.shopify.yml` ships `webhook_secret: # nil`) — verification is bypassed unconditionally for any request claiming to originate from that organization.

Once past this gate, `WebhooksController#create` dispatches the raw payload to registered handlers (`app/models/shipit/webhooks/handlers/handler.rb`). Most handlers scope their effect through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (see `Handler#stacks`/`#repository_name`, and e.g. `PushHandler`, `PullRequest::OpenedHandler`, etc.). However, `app/models/shipit/webhooks/handlers/status_handler.rb`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
does **no repository/organization scoping whatsoever** — it matches `Commit` rows by `sha` across the entire database, i.e. across every stack and every organization configured in the Shipit instance.

`Commit#add_status` (`app/models/shipit/commit.rb` ~360-386) then fires `Hook.emit(:deployable_status, ...)` and, when the new status is `pending` or `success`, calls `stack.schedule_merges`. A commit's `deployable?` (`app/models/shipit/commit.rb:227-229`) is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, so injecting a `success` status can make a commit deployable, feeding into continuous delivery (`Stack#trigger_continuous_delivery`) and the merge queue (`schedule_merges`).

**Result:** an attacker who names, in a self-crafted POST to `/webhooks`, an organization that happens to have no `webhook_secret` configured can send a `status` event for an arbitrary `sha` that belongs to a *completely different* organization's stack, forging a "success" CI status for it — with zero credentials, tokens, or knowledge of any real secret.

### Impact Explanation
This is a genuine unprivileged-attacker exploit path: no Shipit session, no `ApiClient` token, no GitHub App private key, and — critically — no knowledge of any organization's real `webhook_secret` is required, only knowledge that some organization in a multi-org Shipit deployment left `webhook_secret` unset (a documented, supported configuration). The impact reaches the "Critical" tier explicitly listed in scope: it can produce an **unauthorized deploy/merge**, because forged `success` statuses satisfy `Commit#deployable?` and trigger `stack.schedule_merges` / continuous delivery for a stack whose organization was never authenticated by the request.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-organization Shipit deployment where at least one configured organization omits `webhook_secret` (explicitly presented as optional in `docs/setup.md` and in the shipped example `config/secrets.development.shopify.yml`). No rate limiting, IP allow-listing, or repository-ownership check gates the `/webhooks` endpoint beyond the per-organization signature check, and `StatusHandler` performs no additional authorization check tying the verified organization to the target commit's stack.

### Recommendation
- In `Shipit::Webhooks::Handlers::StatusHandler#process`, scope the `Commit` lookup by the repository resolved from the payload (as `Handler#stacks`/`repository_name` already does for other handlers), rather than matching bare `sha` globally.
- In `WebhooksController#verify_signature`, after determining the target repository/stack for the event, verify that the organization used for signature verification actually matches the owner of the repository/stack being mutated, rather than trusting the payload's `repository.owner.login` in isolation.
- Reconsider allowing `webhook_secret` to be entirely optional per-organization; at minimum, require it in any deployment configured with multiple organizations, since a single unsecured organization currently undermines the entire instance's webhook trust boundary.

### Proof of Concept
Preconditions: A Shipit instance configured with two organizations, e.g. `victim-org` (properly configured `webhook_secret`) and `unsecured-org` (no `webhook_secret`, per the documented optional setting).

1. Attacker identifies a commit `sha` belonging to a stack under `victim-org` (commit SHAs are public on GitHub).
2. Attacker POSTs directly to `https://<shipit-host>/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any arbitrary value), and body:
```json
{
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/forged",
  "organization": { "login": "unsecured-org" }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` → `"unsecured-org"` (no `repository` key present, falls back to `organization.login`), fetches `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit under `victim-org`'s stack (unscoped to `unsecured-org`), and calls `create_status_from_github!`, injecting a `success` status.
5. If this makes the commit `deployable?` (e.g., stack uses simple CI gating), `stack.schedule_merges`/continuous delivery may act on it, producing an unauthorized deploy/merge for `victim-org`'s stack triggered by an attacker with no relationship to `victim-org` and no valid credentials for either organization.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
