### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, allowing cross-organization/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization webhook secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but every webhook `Handler` subclass resolves the target `Repository`/`Stack` to mutate using the sibling field `repository.full_name`. These two fields live in the same attacker-influenced JSON body and are never checked for consistency, so a payload that is validly signed for one organization can be crafted to point its `full_name` at a repository belonging to a completely different organization/stack in the same Shipit instance.

### Finding Description
`verify_signature` derives the organization used for secret lookup and signature verification from the payload itself: [1](#0-0) [2](#0-1) 

Once the signature check passes, the raw params are dispatched unmodified to the registered handler for the event: [3](#0-2) 

All handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) inherit `Handler#stacks`/`#repository_name`, which resolve the target repository from a *different* payload field, `repository.full_name`, with no cross-check against the owner/organization field used for authentication: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

This is exactly the "organization that authenticated versus the repository that is written" binding: Shipit's multi-organization configuration (documented in `secrets.development.example.yml`, where distinct `webhook_secret`s are configured per GitHub organization) lets each organization admin legitimately know their own organization's `webhook_secret`. Nothing forces `repository.owner.login`/`organization.login` (checked side) to equal `repository.full_name`'s owner (written side).

### Impact Explanation
On a Shipit instance configured for multiple GitHub organizations, an attacker who is a legitimate GitHub App administrator for **their own** organization (and thus knows/controls that organization's `webhook_secret`, or can otherwise produce a validly-signed request through their own installation) can forge a `push`, `status`, or `check_suite` webhook body where `repository.owner.login` (or `organization.login`) names their own org (so the signature check passes using their own org's secret) while `repository.full_name` names a repository belonging to an unrelated organization/stack hosted on the same Shipit instance. Handlers will then act on that unrelated repository/stack: e.g. `PushHandler` triggers `stack.sync_github(expected_head_sha:)` on the victim stack, and `StatusHandler` writes a forged commit status (`commit.create_status_from_github!`) for any commit SHA, which can influence CI-gated deploy/merge decisions on a repository the attacker does not own. This is a cross-repository/cross-organization write achieved without the credentials that are supposed to gate access to that specific repository, matching the Critical "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Exploitability requires the target Shipit deployment to be configured with more than one GitHub organization/webhook secret (the multi-org config path is explicitly documented and supported), and requires the attacker to control a legitimate GitHub App installation (webhook secret) for at least one of those organizations — a bar clearly lower than compromising the target organization/repository or any Shipit account. No `ApiClient` token, session, or GitHub write access on the target repository is needed. Likelihood is Medium: it depends on multi-tenant configuration, but where present, exploitation is a straightforward crafted HTTP POST to `/webhooks`.

### Recommendation
Bind the authentication and authorization checks to the same payload identity: require `repository.full_name`'s owner (or `organization.login`) used for record lookup in `Handler#repository_name` to match the `repository_owner` value used in `WebhooksController#verify_signature`, and reject the webhook if they diverge. Alternatively, pass the verified organization into each `Handler` and have `stacks`/`repository_name` resolution scoped/filtered by that verified organization rather than trusting `repository.full_name` alone.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (secret `secretA`) and `OrgB` (secret `secretB`), per the multi-org config shown in `config/secrets.development.example.yml`.
2. As the legitimate GitHub App admin for `OrgB`, craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
3. Sign the raw body with `secretB` (known to the `OrgB` admin) and send it as `X-Hub-Signature` to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "OrgB"`, fetches `Shipit.github(organization: "OrgB")`, and the signature validates successfully.
5. `PushHandler#process` resolves `repository_name` from `repository.full_name` = `"OrgA/victim-repo"`, finds `OrgA`'s stacks via `Repository.from_github_repo_name`, and calls `stack.sync_github(expected_head_sha:)` on a stack the attacker does not control, demonstrating the cross-organization write.
