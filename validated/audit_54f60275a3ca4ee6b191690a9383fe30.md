### Title
Same Bitcoin L1 lockup output can be replayed across separate `register-for-bond` calls to double-count sats never re-locked — (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 path credits `sats-total` to a staker's bond based on a Bitcoin SPV proof (`verify-l1-lockups` → `validate-l1-lockup`), but the only replay protection (`seen-outpoints`) is a list local to the current call's `fold`, reset on every invocation. There is no persistent, contract-level map recording that a specific `(txid, output-index)` outpoint has already been credited to a bond. Once a staker's bond membership ends and is cleared (allowing `register-for-bond` to be called again, since `ERR_ALREADY_REGISTERED` only guards against *overlapping* active memberships), the same never-spent Bitcoin timelock output can be submitted again as proof for a new bond registration, crediting the same locked sats a second time without any additional BTC being locked.

### Finding Description
`verify-l1-lockups` [1](#0-0)  initializes `seen-outpoints: (list)` fresh on every call and folds `validate-l1-lockup` over the caller-supplied `outputs` list. The dedup check inside the fold, `(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)` [2](#0-1) , only prevents the *same* outpoint from being counted twice *within a single transaction's proof list*. It is never persisted to a data map, so nothing prevents the identical outpoint from being submitted again in a completely separate `register-for-bond` transaction.

`register-for-bond` computes `sats-total` from this proof and stores it directly into `protocol-bond-memberships` and `protocol-bonds-total-staked` [3](#0-2) , which back the staker's signing weight and reward share. The only "already registered" defense, `ERR_ALREADY_REGISTERED`, is scoped to prevent an *overlapping* active bond position for the same staker [4](#0-3) , not to prevent reuse of the underlying Bitcoin proof once that membership has ended (e.g., after the bond term completes and rolls off, or after `unstake`). Because the referenced Bitcoin output is a timelock script that is never proven "spent" by this contract — only its existence and script/amount/merkle validity are checked [5](#0-4)  — the exact same SPV proof (same `tx`, `header`, `output-index`, merkle path) remains valid indefinitely and can be resubmitted for a fresh bond registration.

This breaks the equality that "sats credited by an L1 proof" must equal "sats actually and currently locked on Bitcoin": the same locked BTC output can back multiple, non-overlapping bond credits over time, or even be presented by different transactions to inflate `protocol-bonds-total-staked` for different bond periods without any new BTC ever being locked.

### Impact Explanation
This lets a staker obtain signer weight / reward-share credit backed by BTC that was only locked once, by re-presenting the same L1 lockup proof after their original bond membership is cleared. This double-counts a Bitcoin commitment in the contract's stake accounting (`protocol-bonds-total-staked`, `get-total-shares-staked-for-cycle`) and inflates the staker's proportional reward share and voting/signing weight beyond what is actually collateralized by locked BTC — a Critical-class "double-counting a commitment or reward" per the scope rules.

### Likelihood Explanation
Exploitation requires only that the attacker's own bond membership eventually end (normal lifecycle: bond term completes, or after `unstake`), after which they resubmit the identical, already-public SPV proof for the same still-locked Bitcoin output in a new `register-for-bond` call. No cooperation from another party, admin, or additional Bitcoin transaction is needed — it is a standard, unprivileged account action reachable through the normal contract entry point.

### Recommendation
Persist a global (not per-call) map keyed by `(txid, output-index)` (or a canonical outpoint identifier) marking an L1 lockup output as "consumed" the first time it successfully backs a `register-for-bond` credit, and reject any future `register-for-bond`/`validate-l1-lockup` call that references the same outpoint, regardless of whether the staker's prior membership has since ended.

### Proof of Concept
1. Staker locks `S` sats in a Bitcoin P2WSH timelock script (per `construct-lockup-output-script`) with an unlock height far enough in the future to satisfy `get-bond-l1-unlock-height` for both bond N and a later bond N+6.
2. Staker calls `register-for-bond` for bond N with an SPV proof of this single output; `verify-l1-lockups`/`validate-l1-lockup` succeed, crediting `amount-sats: S` and updating `protocol-bonds-total-staked` for bond N's cycles.
3. Bond N's term ends and the staker's `protocol-bond-memberships` entry is cleared/rolled off (or unstaked) per normal lifecycle, satisfying the non-overlap check in `bond-overlaps-new-position?`.
4. Staker calls `register-for-bond` again — this time naming a different bond index (or later after some other bond cycle) — resubmitting the exact same `tx`/`header`/`output-index`/merkle-proof for the same still-locked, never-spent Bitcoin output. `validate-l1-lockup`'s `seen-outpoints` check does not fire (it is fresh per call), so the proof validates again and `sats-total = S` is credited a second time to a new bond position, with no new BTC ever locked.

Note: I was unable to locate `construct-lockup-output-script`'s exact definition body in the indexed context (only its call sites), so I cannot fully confirm whether the script encodes anything (e.g., bond-index) that might incidentally limit replay across different bonds. If it does bind the script to a specific bond index, this would narrow (but not eliminate) the issue to re-registration for the *same* bond after churn; if it does not, the issue applies across any bond. A Devin session with full repository access should inspect `construct-lockup-output-script`'s full body to confirm this detail before finalizing remediation scope.

(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
)
