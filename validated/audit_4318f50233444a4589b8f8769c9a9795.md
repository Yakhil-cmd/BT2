I found a clear analog. `Api::CCMenuController` bypasses the per-token stack scoping that `Api::BaseController` enforces everywhere else.### Title
Stack-scoped API token can read any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping by routing all `stack`/`stacks` lookups through `stacks.from_param!`, which restricts the visible `Stack` set to `current_api_client.stack_id` when the token is stack-scoped [1](#0-0) . `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing that restriction while still only checking the generic `read:stack` permission string [2](#0-1) .

### Finding Description
`ApiClient` records can be scoped to a single `stack_id`, and `Api::BaseController#stacks`/`#stack` enforce that scope for every other API endpoint (stacks, tasks, deploys, rollbacks, hooks, etc.) [1](#0-0) . `Api::CCMenuController`, however, defines its own `stack` method that queries `Stack.from_param!(params[:stack_id])` without going through the scoped `stacks` relation [3](#0-2) . The only authorization check it performs is `require_permission :read, :stack`, which merely checks that the string `"read:stack"` is present in `ApiClient#permissions` via `ApiClient#check_permissions!`, with no relation to which specific stack the client is bound to [4](#0-3) .

This breaks the intended binding: `current_api_client.stack_id == stack accessed`. A token that is supposed to authorize reads only for its assigned stack instead touches any stack in the Shipit instance when used against `/api/*/ccmenu`.

Notably, ordinary authenticated Shipit users can self-service mint such stack-scoped tokens with `read:stack` permission via `CCMenuUrlController#fetch`, which auto-creates (or reuses) a `read:stack`-only, stack-scoped `ApiClient` named "CCMenu Client" for `current_user` bound to whatever `stack` they are viewing [5](#0-4) . The test suite confirms that scoping is meant to be enforced elsewhere (`"an api client scoped to a stack will only see that one stack"`) [6](#0-5) , but no equivalent test exists for `CCMenuController`, and the code path clearly does not enforce it.

### Impact Explanation
This is a cross-stack unauthorized read: a token intentionally minted/limited to read one stack's build/deploy status can be used to read the deploy/rollback status (name, activity, last build status, last build label/time, web URL) of every other stack managed by the Shipit instance, including private/internal stacks the token holder should have no visibility into. This matches the explicitly in-scope High-severity class "unauthenticated read of stack state ... deploy output" analog — here the read is achieved with a token that is authenticated but not authorized for the target stack, i.e., the authorization boundary tied to the token ("a stack a token authorises versus a stack it touches") is broken.

### Likelihood Explanation
Any Shipit user (no special privilege beyond normal team membership) can generate a `read:stack`, single-stack-scoped CCMenu token for a stack they can view, then reuse that same token's `params[:token]` against `GET /api/:stack_id/ccmenu` with an arbitrary `stack_id`. No collusion, secrets, or elevated permissions are required — only a working, intentionally narrow-scoped token, and knowledge/guessing of another stack's identifier (stack ids/`owner/repo/env` triples are often enumerable/discoverable from the UI).

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController` (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `current_api_client.stack_id` restriction is honored the same way it is for every other API controller. Add a regression test mirroring the existing `stacks_controller_test.rb` scoping test to `ccmenu_controller_test.rb`, asserting a stack-scoped token receives a 404/403 when a different `stack_id` is requested.

### Proof of Concept
1. As a normal authenticated Shipit user with access to `stack-A`, visit the CCMenu URL feature (`CCMenuUrlController#fetch` for `stack-A`); this creates/returns an `ApiClient` named "CCMenu Client" scoped to `stack-A` with `permissions: ["read:stack"]` and returns a signed `token` [7](#0-6) .
2. Send `GET /api/<stack-B-id>/ccmenu?token=<token from step 1>` where `stack-B` is a different, unrelated stack the user's token was never scoped to.
3. `Api::BaseController#authenticate_api_client` (overridden in `CCMenuController`) accepts the token via `ApiClient.authenticate(params[:token])` [8](#0-7) ; `require_permission :read, :stack` passes because the token has `read:stack` in its permissions list, regardless of the bound `stack_id` [4](#0-3) .
4. `show` calls `stack` which resolves `Stack.from_param!(params[:stack_id])` against `stack-B` directly (no scoping check), returning `stack-B`'s deploy/rollback status in the response XML [9](#0-8) .
5. The response discloses `stack-B`'s name, activity, and last build status/label/time — data the token was never authorized to see.
