### Title
CCMenu API endpoint bypasses stack-scoped ApiClient authorization, allowing cross-stack state disclosure - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor inherited from `Shipit::Api::BaseController` with an unscoped lookup (`Stack.from_param!(params[:stack_id])`), instead of using the parent's `stacks.from_param!(params[:stack_id])`, which is the only place that enforces the binding between an `ApiClient`'s `stack_id` and the stack it is allowed to touch. This lets any `ApiClient` token that is scoped to one stack (via `belongs_to :stack`) read the CCMenu status of every other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the authorization-scoping helper: [1](#0-0) 

`stacks` is the enforcement point: if `current_api_client.stack_id?` is true (the client was created bound to a specific stack), the resolvable set of stacks is restricted to that single stack; `stack` (used by every other controller such as `StacksController`, `TasksController`, `DeploysController`, etc.) resolves through this scoped relation.

`CCMenuController`, however, redefines `stack` directly on the unscoped `Stack` model: [2](#0-1) 

Because Ruby method resolution uses the subclass's own `private def stack`, the parent's scoping via `stacks` is never invoked. The only gate left is `require_permission :read, :stack`, which only checks that the token has the generic `read:stack` permission string via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` never inspects which stack is being accessed — it only checks the `permissions` array. The `stack_id` binding is enforced exclusively in `BaseController#stacks`, which `CCMenuController` bypasses.

The equality broken is: `current_api_client.stack_id` (the stack the token authorizes) ≠ `params[:stack_id]` (the stack actually touched by `CCMenuController#show`, resolved via unscoped `Stack.from_param!`).

Confirmed reachability: the route is mounted at `GET /api/stacks/*stack_id/ccmenu` in `config/routes.rb`: [4](#0-3) 

And `ApiClient` supports being bound to a single stack: [5](#0-4) 

### Impact Explanation
A stack-scoped API token with only `read:stack` permission — intended by design to only see its own stack (this is exactly how `stacks` is meant to work in `BaseController`) — can instead be used against `GET /api/stacks/<any-other-repo>/<env>/ccmenu` to read that other stack's deploy/rollback status (last deploy id, running state, end time) via the `CCMenuController#show` action: [6](#0-5) 

This is an unauthorized read of stack state that crosses the authorization boundary the token was explicitly scoped to, which matches the High-impact category of "unauthenticated/unauthorized read of stack state."

### Likelihood Explanation
Low-to-moderate: it requires possession of a valid `ApiClient` token (basic-auth credential or the `token` param for CCMenu, per `authenticate_api_client` override in this controller) that has `read:stack` permission and is bound to a single stack — e.g., any token issued through the "CCMenu URL" self-service flow or through the admin `ApiClient` creation UI with a stack selected. No additional privilege escalation beyond holding such a legitimately-scoped-but-limited credential is required; the attacker only needs to substitute a different `stack_id` in the URL.

### Recommendation
Remove the private `stack` override in `CCMenuController` and rely on the inherited, properly-scoped `stack`/`stacks` methods from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`), so that stack-scoped API clients cannot resolve stacks outside their bound `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` bound to Stack A (`stack_id` set) with `permissions: ['read:stack']` — e.g. via the CCMenu URL flow for `owner/repoA/production`, obtaining its `authentication_token`.
2. Send `GET /api/stacks/owner/repoB/production/ccmenu?token=<tokenA>` (or via Basic Auth) where `repoB` is a stack the token was never scoped to.
3. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `BaseController#stacks`'s `Stack.where(id: current_api_client.stack_id)` restriction), returning Stack B's record and rendering its CCMenu XML status, disclosing deploy state of a stack the token was never authorized to see.
