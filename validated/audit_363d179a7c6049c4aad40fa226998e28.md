### Title
Stack-scoped API token authorization bypass in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the base controller's stack-lookup method with an unscoped lookup, breaking the binding between the stack an `ApiClient` token is authorised for (`ApiClient#stack_id`) and the stack the endpoint actually reads.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping for API clients that are bound to a single stack: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set, and `stack` performs `stacks.from_param!(params[:stack_id])` — i.e. the lookup is always filtered through the client's authorised stack scope.

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This calls `Stack.from_param!` directly on the unscoped model, not the client-scoped `stacks` relation. `ApiClient#check_permissions!` only validates that the `permissions` array contains `read:stack` — it never checks `stack_id` binding: [3](#0-2) [4](#0-3) 

The equality that should hold is: `stack authorised by token (current_api_client.stack_id) == stack touched by the request (params[:stack_id])`. Because `CCMenuController#stack` ignores `current_api_client.stack_id`, that equality is broken — any `read:stack`-permitted token, regardless of the `stack_id` it was scoped to, can fetch the CCMenu status of **any** stack in the installation simply by supplying a different `stack_id` in the URL (`GET /api/stacks/*stack_id/ccmenu`).

This directly matches the scoped comparison other API controllers implement correctly, e.g. `Api::StacksController#stack` uses the scoped `stacks.from_param!(params[:id])`: [5](#0-4) 

### Impact Explanation
An `ApiClient` created with `permissions: ["read:stack"]` and a specific `stack_id` (a supported, documented capability of the `ApiClient` model — `belongs_to :stack, optional: true`) is intended to only be able to read state for that one stack. Because of the CCMenu controller's unscoped lookup, that token can read the deploy/build status (`deploys_and_rollbacks.last`, deploy success/failure/running state, last build label) of every other stack managed by the Shipit instance, including stacks belonging to different repositories/teams the token holder should have no visibility into. This is an unauthorized read of stack state across a scope boundary that the token issuer explicitly set, matching the "unauthenticated/unauthorized read of stack state" class of High-severity issue.

### Likelihood Explanation
Any party in possession of a stack-scoped `read:stack` API token (e.g. a CI dashboard/CCMenu integration granted access to a single stack) can trivially exploit this by changing the `stack_id` path segment of the request — no additional privileges, secrets, or session are required beyond the token itself, which is exactly the credential this endpoint is meant to accept.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from the base controller instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores enforcement of `current_api_client.stack_id` scoping consistent with the rest of the API controllers.

### Proof of Concept
1. Create (or have an operator create) two stacks, `Stack A` (`repo-a/env`) and `Stack B` (`repo-b/env`).
2. Issue an `ApiClient` scoped to `Stack A` only: `permissions: ["read:stack"]`, `stack_id: <Stack A id>` (this is the supported scoping mechanism per `ApiClient#stack_id` / `Api::BaseController#stacks`).
3. Using that client's `authentication_token` as Basic Auth (per `Api::CCMenuController#authenticate_api_client`, also accepted via `params[:token]`), issue:
   ```
   GET /api/stacks/repo-b/env/ccmenu?token=<token-scoped-to-stack-A>
   ```
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, the request succeeds and returns Stack B's build/deploy status XML, even though the token was only authorised (via `stack_id`) for Stack A.
