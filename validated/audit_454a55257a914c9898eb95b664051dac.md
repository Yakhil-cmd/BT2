### Title
Cross-tenant `pull_request` webhook forgery via `repository.owner.login`/`repository.full_name` mismatch bypasses per-org webhook secret - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to validate against using `params.dig('repository','owner','login')` [1](#0-0) , but the pull_request handlers (e.g. `AssignedHandler`) resolve the `Repository`/`Stack` to mutate using a *different* field from the same JSON body, `repository.full_name` [2](#0-1) . Because these two attacker-supplied fields are never cross-validated, and because `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected org has no `webhook_secret` configured [3](#0-2) , an attacker can pick an org with no secret to pass signature verification, while pointing `repository.full_name` at a victim repository belonging to a completely different (properly-secured) organization.

### Finding Description
The broken binding, stated as an equality that the code should enforce but does not:

`params.dig('repository','owner','login')` (used to select the verifying `GitHubApp`/secret in `verify_signature`) **should equal** the owner encoded in `params.dig('repository','full_name')` (used by every handler, including `AssignedHandler`, to resolve the target `Repository`/`Stack`). The engine never checks this equality.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from `repository.owner.login` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(sig, raw_post)` [4](#0-3) .
2. `GitHubApp#verify_webhook_signature` returns `true` immediately when `@webhook_secret` is blank for that org's config [5](#0-4) . Multiple example/dummy configs in this repo ship with `webhook_secret: # nil` as an accepted valid state (single-org and multi-org schemas alike) [6](#0-5) [7](#0-6) , confirming this is a real, supported configuration state, not a hypothetical.
3. Once `verify_signature` passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers against the raw, unauthenticated JSON body [8](#0-7) .
4. `AssignedHandler#repository` and the base `Handler#stacks`/`repository_name` both resolve the target repository via `Repository.from_github_repo_name(params.repository.full_name)` [9](#0-8) [2](#0-1)  — a field independent from the one used to pick the verifying secret.
5. `AssignedHandler#process` then calls `pull_request.update(github_pull_request: params.pull_request)` for the `PullRequest` scoped to that resolved repository/stack whenever `action` is `assigned` or `unassigned` [10](#0-9) , which persists attacker-supplied title/state/labels/assignees and resolves `head` via `find_or_create_commit_from_github_by_sha!` [11](#0-10) .

Exploit: attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, body `{"action":"unassigned","number":<N>,"repository":{"owner":{"login":"org-without-secret"},"full_name":"victim-org/victim-repo"},"pull_request":{...},...}`. `repository_owner` resolves to `org-without-secret`, whose `GitHubApp` has no `webhook_secret`, so `verify_webhook_signature` returns `true` with no HMAC check at all. The handler then looks up and mutates the `PullRequest` belonging to `victim-org/victim-repo`'s stack — a repository/organization the attacker never authenticated against.

Existing guards do not stop this: `drop_unhandled_event` and `check_if_ping` only gate on event type; `ExplicitParameters` schema validation only checks types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; `Repository.from_github_repo_name` performs no ownership/authentication check, it is a pure lookup [12](#0-11) .

Regarding the `ignore_ci`/`Commit#deployable?` amplification claimed in the prompt: `Commit#deployable?` does short-circuit CI when `stack.ignore_ci?` is true [13](#0-12) , but `AssignedHandler` itself never triggers a deploy, rollback, or merge — it only calls `pull_request.update(...)`, which updates `PullRequest`/`Commit`/`PullRequestAssignment` records and their `after_update_commit` hooks (`emit_update_hooks` → `Hook.emit`) [14](#0-13) . There is no code path in `AssignedHandler` that calls `stack.trigger_deploy`, `Command`, or `PTY.spawn`. The `ignore_ci` condition affects whether a commit is later considered deployable through the normal UI/API deploy flow, but is not itself invoked by this handler.

### Impact Explanation
The demonstrated, code-supported impact is: an unauthenticated attacker can forge a `pull_request` webhook that authenticates against a no-secret organization's `GitHubApp` config but mutates the persisted `PullRequest` record (title, state, labels, assignees, linked commit) belonging to an entirely different repository/stack that the attacker did not authenticate against. This is a genuine "payload for one repository mutating another's stack/commit" primitive (matches the Critical impact category listed in the rules), but as traced, `AssignedHandler` writes a database record only — it does not itself execute a deploy/rollback/merge, run a `Command`, or spawn a process. The `ignore_ci`-based CI short-circuit does not change what `AssignedHandler` writes; it only affects a later, separate authorization decision (deploy eligibility) that this handler does not exercise.

### Likelihood Explanation
Preconditions: Shipit must have at least one organization configured with a blank `webhook_secret` (a supported, documented configuration state per `docs/setup.md` and the shipped example secrets files), and the attacker must know or guess that org's login plus the victim's `repository.full_name` and a valid PR `number` for the victim stack (these are typically public/guessable via GitHub). No GitHub secrets, session, or API token are needed — a single unauthenticated HTTP POST suffices, and it is fully repeatable against any repository/stack in the same Shipit instance.

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), enforce that the `owner` encoded in `repository.full_name` matches `repository.owner.login`/the organization used to select the verifying `GitHubApp`, rejecting the webhook (422) on mismatch. Additionally, do not treat a blank `webhook_secret` as "always verified" — either require `webhook_secret` to be present for every configured organization, or bind verification explicitly to the specific repository being targeted rather than to a caller-suppliable `owner.login` field.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb`, no live GitHub):
```ruby
test "pull_request payload with owner.login pointing to a no-secret org can mutate a different repository's PullRequest" do
  # Arrange: stub Shipit.github so 'no-secret-org' resolves to a GitHubApp with no webhook_secret
  no_secret_app = Shipit::GitHubApp.new('no-secret-org', {})
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(no_secret_app)

  victim_pr = shipit_pull_requests(:review_stack_review) # belongs to a real stack/repository, e.g. "shopify/shipit-engine"
  payload = payload_parsed(:pull_request_assigned)
  payload["action"] = "unassigned"
  payload["number"] = victim_pr.number
  payload["pull_request"]["number"] = victim_pr.number
  payload["repository"]["owner"]["login"] = "no-secret-org"        # selects the org with no secret -> verify_webhook_signature returns true
  payload["repository"]["full_name"] = victim_pr.stack.repository.full_name # points handler at victim repo/stack

  @request.headers['X-Github-Event'] = 'pull_request'
  # no X-Hub-Signature header sent at all

  assert_changes -> { victim_pr.reload.title }, to: payload["pull_request"]["title"] do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok
end
```
Both sides of the claimed binding (`repository.owner.login` used for auth vs. the owner implied by `repository.full_name` used for the DB write) diverge before the fix (`"no-secret-org" != "shopify"`) and the test shows the victim's `PullRequest` record changes despite the request never being verified against the victim org's secret. After adding the recommended equality check, the same request should return `422` and the assertion should fail to observe any change.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
