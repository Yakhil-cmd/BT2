### Title
Cross-repository commit-status forgery via unscoped SHA lookup in webhook status handler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Shipit verifies inbound GitHub webhooks by checking the `X-Hub-Signature` against the webhook secret configured for the **organization named in the payload** (`repository.owner.login`), but the `status` event handler then applies the status update to **every commit in the database that matches the SHA**, with no check that the commit actually belongs to a stack/repository owned by that organization. This breaks the trust binding "organization that authenticated versus the repository that is written."

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/secret to validate against purely from the payload's own `repository.owner.login` (or `organization.login`) field, then HMAC-verifies the raw body against that organization's `webhook_secret`: [1](#0-0) 

This only proves "a request signed by organization X's secret was sent," and correctly ties X to the `repository_owner` field of the same payload. It does **not** constrain which `Commit` records in Shipit's database that payload is allowed to mutate.

`StatusHandler#process`, however, looks up commits purely by SHA, globally, across all stacks/repositories tracked by the Shipit instance: [2](#0-1) 

Because Git commit objects are content-addressed, identical commits (e.g., produced by forking a public repository, or by cherry-picking/rebasing the same tree/parent/author/message onto another remote) share the exact same SHA1 across repositories. Any organization that has the Shipit GitHub App/webhook installed (Shipit is explicitly multi-organization — see `Shipit.github(organization: ...)` in `lib/shipit/github_app.rb` and the per-organization `webhook_secret` config) can:

1. Obtain/produce a commit whose SHA collides with a commit already tracked in a victim stack (trivial via forking a public victim repo, or independently authoring an identical commit).
2. Push a `status` update (pending/success/failure) to that commit through the GitHub API on their own, fully-owned repository.
3. GitHub delivers a webhook signed with the attacker-organization's own `webhook_secret` — which passes `verify_signature` legitimately, since it *is* correctly signed for that organization.
4. `StatusHandler#process` finds **every** `Commit` row with that SHA — including the one belonging to the victim's stack — and calls `commit.create_status_from_github!(params)` on it, injecting an attacker-chosen CI state (e.g., `success`) onto the victim's commit.

The equality that should hold but doesn't:
`organization authenticated by signature` == `repository/stack whose Commit rows are mutated`.
Instead the code only guarantees `organization authenticated by signature` == `repository named in payload`, while the actual write path (`Commit.where(sha:)`) is unscoped to any repository at all.

### Impact Explanation
Commit statuses recorded this way feed directly into Shipit's deploy-gating logic (`Stack#branch_status`, `Commit#deployable?`/CI state used for continuous deployment and manual deploy safety checks). An attacker who controls a second GitHub organization onboarded to the same Shipit instance can forge a `success` status on a victim stack's commit that never actually passed CI, causing an unauthorized/ungated deploy to be triggered (directly, or via continuous deployment picking up the now-"green" commit) — meeting the Critical bar of "unauthorized deploy" without ever holding a Shipit session, API token, or write access to the victim repository.

### Likelihood Explanation
Requires only that the attacker control (or be a collaborator on) any single GitHub organization/repository that is onboarded to the same Shipit deployment (a realistic multi-tenant scenario, since Shipit supports arbitrary numbers of organizations each with their own webhook secret) and the ability to fork/reproduce a commit SHA that also exists in the victim's stack — both achievable without any special privilege on the victim's side.

### Recommendation
In `StatusHandler#process` (and any other SHA-keyed webhook handler), scope the `Commit` lookup to the repository/stack that owns the webhook, e.g. by joining/filtering `Commit` through `Stack#repository` matched against `params.dig('repository', 'full_name')` (or the `repository_owner` already validated by signature), rather than a bare `Commit.where(sha: ...)` across the whole installation.

### Proof of Concept
1. Attacker's organization `evil-org` is a legitimate GitHub App installation on the shared Shipit instance (own `webhook_secret`).
2. Attacker forks (or reproduces) a commit from the victim's public repository so `evil-org/repo@<sha>` is identical to `victim-org/repo@<sha>`.
3. Attacker sets a `success` commit status on `evil-org/repo@<sha>` via the GitHub API.
4. GitHub sends a `status` webhook to Shipit, signed with `evil-org`'s `webhook_secret`; `verify_signature` passes.
5. `StatusHandler#process` executes `Commit.where(sha: <sha>).each { |c| c.create_status_from_github!(params) }`, which also matches and updates the victim stack's `Commit` row, marking it CI-green and eligible for deploy/continuous delivery.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
