### Title
Unauthenticated Null-Pointer Dereference in `handleOnlinePrivatePayment` via missing `payload` field - (File: network.js)

### Summary
`network.js`'s `handleOnlinePrivatePayment()` handles `private_payment` justsaying messages received directly from any peer or hub (originated by a private-payment counterparty). Before accessing `arrPrivateElements[0].payload.denomination`, the function only checks that `arrPrivateElements` is a non-empty array — it never verifies that `arrPrivateElements[0].payload` itself exists, similar in root cause to the CVE-2023-29996 NanoMQ bug where `subinfo_decode`/`unsubinfo_decode` dereferenced fields of an attacker-supplied structure without checking they were present, causing a null-pointer crash.

### Finding Description
```js
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
``` [1](#0-0) 

`arrPrivateElements` originates entirely from the wire message (`private_payment` justsaying, or `hub/message`-delivered content forwarded to the same handler via `wallet.js`), and its only validation prior to this line is `isNonemptyArray`. There is no check that `arrPrivateElements[0]` is a non-empty object, nor that `.payload` exists. An attacker (any connected peer, hub, or private-payment counterparty pairing device) can send:
```json
["private_payment", [ {"unit": "...", "message_index": 0} ]]
```
i.e., an object lacking the `payload` key entirely. Because `arrPrivateElements[0].payload` is `undefined`, the expression `arrPrivateElements[0].payload.denomination` throws a `TypeError: Cannot read properties of undefined (reading 'denomination')`.

This mirrors the CVE's bug class exactly: a decode/parse routine reads a nested field of attacker-controlled data without first checking that the parent object is present.

### Impact Explanation
An uncaught `TypeError` thrown synchronously inside a `ws`-message handler (`handleJustsaying`) is not caught by any try/catch in the call chain shown, and in Node.js an uncaught exception thrown outside of a promise/async context crashes the process (unless a global `uncaughtException` handler silently absorbs it — which would itself be a stability/DoS concern). Any full node, hub, or wallet that processes `private_payment` messages from any peer can be crashed remotely and repeatedly, without authentication, by any peer that connects to it — a network-wide denial of service that can prevent the target from confirming new units while it is down/restarting, satisfying the "network unable to confirm new units" impact bar.

### Likelihood Explanation
High. Any TCP/WS peer, hub, or paired device can send a malformed `private_payment` message with a single crafted element lacking the `payload` key; no authentication, funds, or special privileges are required, and the code path is reached unconditionally for any received private-payment message.

### Recommendation
In `handleOnlinePrivatePayment` (network.js), validate `arrPrivateElements[0]` and its `payload`/`output_index` fields (e.g., `ValidationUtils.isNonemptyObject(arrPrivateElements[0])` and `ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload)`) before dereferencing any nested property, returning `callbacks.ifError(...)` on failure — consistent with the defensive patterns already used elsewhere in this file and in `private_payment.js`/`indivisible_asset.js`.

### Proof of Concept
1. Connect a WebSocket client to a target ocore hub/full node as an ordinary peer (no special trust needed).
2. Send a justsaying message:
```json
["justsaying", { "subject": "private_payment", "body": [ { "unit": "SOME_44_CHAR_BASE64_UNIT_ID", "message_index": 0 } ] }]
```
(the single array element intentionally omits `payload`).
3. The node calls `handleOnlinePrivatePayment(ws, arrPrivateElements, ...)`, executes `arrPrivateElements[0].payload.denomination`, and throws a `TypeError`, crashing the node process (or, in wallet.js's private-payment handling paths that funnel into this same function via device pairing counterparties, crashing wallet processes). function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
