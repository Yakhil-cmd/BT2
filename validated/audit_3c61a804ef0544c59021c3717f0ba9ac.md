There's a `pallet-psm` (Peg Stability Module) — that's a strong candidate for a constant-sum, fixed-price swap analog. Let me inspect it.### Title
`pallet-psm` performs fixed 1:1 mint/redeem between externals with no price check, enabling risk-free arbitrage drainage of a healthy external's reserve using a de-pegged external - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm` (Peg Stability Module) implements the same bug class flagged in the external report: a fixed-rate, "zero-slippage" swap mechanism between assets that are merely *assumed* to always be worth $1, with no oracle or price-tolerance check of any kind. `mint`/`redeem` only do decimal scaling (`external_to_internal`/`internal_to_external`), never a price comparison, and debt/reserve accounting is tracked per `(internal_asset, external_asset)` pair rather than pooled by real economic value. If any one approved external asset de-pegs on the open market while another approved external on the *same* PSM instance stays near $1, an attacker can mint the internal stablecoin cheaply with the de-pegged asset and redeem it 1:1 against the outstanding debt of the healthy external, extracting real value from the PSM reserve at the healthy asset's expense.

### Finding Description
`mint()` converts `external_amount` to `internal_equivalent` purely via decimal scaling (`Self::external_to_internal`, no price term) and mints that amount of internal asset minus a flat fee: [1](#0-0) 

`redeem()` similarly burns internal asset and pays out external asset 1:1 (scaled only by decimals), and validates against `PsmDebt` (per external-asset pair), not against the PSM's aggregate solvency or any price signal: [2](#0-1) 

Debt is tracked with `PsmDebt<T>` keyed by `(internal_asset, external_asset)`: [3](#0-2) 

Conversion between internal/external is a pure decimal-scaling operation (`external_to_internal`/`internal_to_external`/`pow10`) — there is no price oracle, no `price_tolerance`, and no comparison to any external market price anywhere in the pallet: [4](#0-3) 

The pallet's own documentation acknowledges the arbitrage corridor is bounded only by the mint/redeem fees (0.5% each side ⇒ ~1% total), exactly mirroring the Frax report's finding that price swings are only bounded by fees/gas, with no mechanism limiting the magnitude of de-peg: [5](#0-4) 

**Attack path**: A single PSM instance can have multiple approved externals (e.g. `USDC` and `USDT`), each independently tracked in `PsmDebt` and `ExternalAssets`: [6](#0-5) 

1. Legitimate users have previously minted internal stablecoin against `external_B` (e.g. USDC), building up `PsmDebt[internal, external_B] = D > 0`, backed by `D` worth of USDC actually sitting in the PSM reserve account (`psm_account`).
2. `external_A` (e.g. USDT) de-pegs on the open market, trading at, say, $0.90.
3. Attacker buys/flash-loans a large amount of the now-cheap `external_A` and calls `mint(internal_asset, external_A, amount, max_fee)`. The pallet has no way to know `external_A` is worth less than $1 — it accepts 1:1 (minus 0.5% fee) purely by decimal scaling.
4. Attacker calls `redeem(internal_asset, internal_amount, external_B, max_fee)` up to `PsmDebt[internal, external_B]`. This burns internal asset and pays out `external_B` (USDC) 1:1 (minus 0.5% fee) from the shared reserve account, checked only against `PsmDebt` for that pair, not against real dollar value: [7](#0-6) 
5. Attacker now holds `external_B` (still worth ~$1) obtained by paying with de-pegged `external_A` (worth $0.90), net of ~1% combined fees — a risk-free profit for any de-peg exceeding ~1%, exactly the "buy the total reserve of the more expensive token" pattern described in the report. This can be repeated (subject to `max_debt`/`AssetCeilingWeight` ceilings, analogous to the `token_cap` in the report) until `PsmDebt[internal, external_B]` is drained, leaving the PSM holding a reserve skewed toward the de-pegged, devalued asset while the healthy asset's collateral has been extracted.

The pallet's `try-runtime` invariant only checks that each external's own reserve ≥ its own tracked debt, in nominal units — it never checks that the *aggregate* value backing the internal asset matches $1 per unit, so this drain is fully consistent with the pallet's own invariants: [8](#0-7) 

### Impact Explanation
This is a genuine fund-drainage vector reachable by any signed account with no privileged role (`mint`/`redeem` are plain signed extrinsics). If any approved external asset on a PSM instance de-pegs — a realistic, externally-driven event for third-party stablecoins like USDC/USDT that the pallet explicitly targets — an attacker can extract the healthy collateral backing other users' redemption rights, up to the outstanding debt/ceiling for that asset, with only ~1% in fees as friction. This directly undermines the "1:1 backing" guarantee the pallet advertises and can leave depositors of the healthy asset unable to redeem at par. This matches the report's classification as at least a **Medium**-severity, undefined-behavior/economic design flaw.

### Likelihood Explanation
Likelihood is **Medium**: it requires an external market condition (one approved external de-pegging) rather than an on-chain bug, and is bounded by `max_debt` / `AssetCeilingWeight` per PSM instance — similar constraints to the `token_cap` in the original report. It also requires PSM operators to onboard more than one external asset and for genuine prior debt to exist on the healthy asset. Given multiple real-world stablecoin de-peg events (e.g., USDC in March 2023), this is not a purely theoretical scenario for any runtime that instantiates `pallet-psm` with multiple externals.

### Recommendation
Do not treat `pallet-psm` mint/redeem as unconditionally safe for multi-asset PSM instances without an external price oracle or de-peg circuit breaker. Consider: (a) adding an oracle-based sanity check (or a permissionless, incentivized "de-peg reporter" that trips `CircuitBreakerLevel` automatically) before allowing mint/redeem at the fixed 1:1 rate; (b) segregating reserves so that redemption of `external_B` can only be paid from value actually contributed via `external_B` deposits denominated in real economic terms, not just nominal per-pair debt bookkeeping; (c) tightening `AssetCeilingWeight`/`max_debt` monitoring and alerting so operators can react quickly to de-peg events; (d) documenting explicitly (beyond the README's fee-corridor note) that multi-external PSM instances carry cross-collateral contagion risk equivalent to unlimited arbitrage once an external's market price diverges beyond the fee corridor.

### Proof of Concept
No PoC was executed. A minimal reproduction would extend `substrate/frame/psm/src/tests.rs` (mock at `substrate/frame/psm/src/mock.rs`) to: (1) create a PSM with `internal_asset` and two externals `A`, `B`; (2) have a legit user mint using `B` to build `PsmDebt[internal, B] > 0`; (3) have an attacker account `mint` internal asset using `A` (simulating that `A` is de-pegged, since the pallet has no price awareness this requires no special setup — just supplying `A` at nominal decimals); (4) have the attacker `redeem` against `B`, and assert the attacker's `B` balance increased while only having supplied `A`. This is a straightforward extension of the existing `mint`/`redeem` test helpers already in `substrate/frame/psm/src/tests.rs`; it was not run as part of this analysis — the finding is based on static code review of the mint/redeem/debt logic cited above, not on live execution.

		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}
