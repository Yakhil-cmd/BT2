### Title
Cross-repository commit-status forgery bypasses `required_statuses` allowlist - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, which has no `WHERE` clause tying the match to the repository that sent the webhook. Any repository that can legitimately deliver a signed `status` webhook to Shipit (e.g. an attacker's own repo/fork within an org already onboarded to Shipit) can write a `Status` row, with an attacker-chosen `context`, onto any other stack's commit that happens to share the same SHA.

### Finding Description
The broken binding is: `stack.required_statuses.include?(status.context) == true` is meant to imply `status.context` was produced by an integration authorized for R1 (the repository owning that stack). In reality the binding actually enforced is only: `Commit.sha == params.sha`, with no constraint that `params` originated from R1.

Path: `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event('status')` → `StatusHandler` [5](#0-4)  . `verify_signature` only checks that the payload's HMAC matches the webhook secret configured for `repository.owner.login` in the payload [6](#0-5)  — this authenticates "some org GitHub knows about", not "the specific repository that owns the target commit/stack". `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) , with zero join/filter on repository or stack. `create_status_from_github!` then persists the status using the matched commit's *own* `stack_id` [4](#0-3) , i.e. S1's stack, even though the webhook came from R2.

Attack flow:
1. Attacker owns/controls repository R2 (a fork or any repo in an org already onboarded to this Shipit instance, satisfying the enumerated "push to a fork"/"repository they own" capability).
2. Attacker arranges (or already has, via a shared git history/fork) a commit in R2 whose SHA is identical to a commit SHA already tracked by S1 (this is a normal git property for forked/shared history — SHAs are content+parent addressed and identical across repositories/forks).
3. Attacker sets a commit status on that SHA in R2 with `context: "ci/important"`, `state: "success"` — either via GitHub UI/API on their own repo, or GitHub's own delivery of a legitimately-signed `status` webhook.
4. Shipit's `StatusHandler` matches the SHA against `Commit.where(sha: ...)` and finds S1's commit record, then writes a `Status` row scoped to S1's stack with `context: "ci/important"`.
5. S1's `required_statuses` check (`ci.require` in `cached_deploy_spec`) is now satisfied by a status that was never produced by R1's actual CI, and `deployable?` becomes true.

Existing guards do not stop this: `verify_signature` validates org-level HMAC only, not repo/stack ownership of the SHA; `ExplicitParameters` schema for `StatusHandler` doesn't require or validate `repository` at all; there is no `Commit#stack` / `Repository` join filter in the query.

### Impact Explanation
This allows a payload authenticated for repository R2 to mutate state (a `Status` record, and downstream `deployable?`/`Commit#state`) belonging to a completely different stack/repository S1/R1, without R1's authorization. This directly enables an unauthorized deploy: once `required_statuses` is satisfied by the forged context, `Commit#deployable?` becomes true and continuous-deployment or manual "Deploy" actions on S1 can proceed as if genuine CI passed. This matches the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." The blast radius spans every stack/repository hosted by the same Shipit instance, since the `Commit.where(sha:)` scan is entirely global and not namespaced per tenant/org.

### Likelihood Explanation
Preconditions: the attacker needs (a) the ability to deliver a validly-signed `status` webhook from some repository already onboarded/known to this Shipit instance (owning a repo/fork in an onboarded org, which the rules explicitly grant as an unprivileged capability), and (b) a SHA collision between a commit tracked in the victim stack and a commit reachable in the attacker's own repository. SHA collisions are trivially achievable via forks/shared history (same content+parent hash across cloned/forked repositories), so this is not a cryptographic-collision requirement — it's an ordinary git property. No secrets, sessions, or maintainer roles are required. This is fully repeatable against any stack whose commits are also reachable (by SHA) from a repo the attacker controls.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository that sent the webhook, e.g. resolve `params.repository.full_name` (require it in the params schema) and filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { name:, owner: })`, so a status can only be recorded against commits belonging to stacks whose repository matches the webhook's authenticated origin.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook from an unrelated repository cannot satisfy another stack's required_statuses" do
          victim_stack = shipit_stacks(:shipit) # S1
          victim_stack.update!(cached_deploy_spec: DeploySpec.new('ci' => { 'require' => ['ci/important'] }))
          victim_commit = victim_stack.commits.create!(
            sha: 'deadbeef' * 5, # colliding sha, present only in S1's Commit table
            author: shipit_users(:walrus), committer: shipit_users(:walrus),
            authored_at: Time.now, committed_at: Time.now, message: 'victim commit'
          )

          refute_predicate victim_commit, :deployable?

          # Forged payload: legitimately signed for an unrelated repo R2 the attacker owns,
          # but referencing the victim's colliding sha and the exact required context.
          forged_params = ExplicitParameters::Params.new(
            sha: victim_commit.sha,
            state: 'success',
            context: 'ci/important'
          )

          StatusHandler.new(forged_params).process

          victim_commit.reload
          assert_predicate victim_commit, :deployable?, "forged cross-repo status must not satisfy required_statuses"
        end
      end
    end
  end
end
```
Both sides of the binding diverge: `status.context == 'ci/important'` is true, but "produced by an integration authorized for R1" is false, since the record was written purely off a global SHA match with no repository check — the test demonstrates `deployable?` flips to `true` despite that.
