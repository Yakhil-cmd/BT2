### Title
Stack-scoped ApiClient can create Stacks for arbitrary repositories, bypassing its `stack_id` binding - ([File: app/controllers/shipit/api/stacks_controller.rb])

### Summary
An `ApiClient` can be scoped to a single `Stack` via its `stack_id` foreign key [1](#0-0) , and `Api::BaseController#stacks` is supposed to enforce that binding by restricting the visible/actionable stack set to only that one stack when `stack_id` is present [2](#0-1) . However, `Api::StacksController#create` never consults this scoping helper — it builds a brand-new `Stack` directly from client-supplied `repo_owner`/`repo_name` params and saves it unconditionally [3](#0-2) [4](#0-3) . This is the same bug class as the reported `entireSystemColl` issue: a value meant to bound/limit an operation (`entireSystemColl` for TCR checks, `stack_id` for API-client authorization) is not maintained/enforced at one code path, letting the actual effect exceed what the binding permits.

### Finding Description
The equality that should hold is: `client.stack_id == stack.id` for every stack-mutating action reachable by a stack-scoped client. `update`, `destroy`, and `show` correctly enforce this because they resolve the target stack through `stack` → `stacks.from_param!`, which is filtered by `current_api_client.stack_id` [5](#0-4) [2](#0-1) . `create` is gated only by the coarse `write:stack` permission check [6](#0-5)  and never calls `stacks`/`stack`, so it is not bound to `current_api_client.stack_id` at all. The fixtures confirm this scoping model exists in practice (a client can be tied to one stack with limited permissions) [7](#0-6) , and the test suite documents the intended invariant — "an api client scoped to a stack will only see that one stack" [8](#0-7)  — but no test covers `create` for a stack-scoped client, meaning the missing check is not verified anywhere.

### Impact Explanation
An operator who provisions a narrowly-scoped `ApiClient` (bound to one `Stack`, granted `write:stack` so the client can update its own stack's `deploy_url`/`branch`/etc.) unintentionally also grants that client the ability to call `POST /stacks` with arbitrary `repo_owner`/`repo_name`/`environment`/`branch` values, registering a brand-new `Stack` for a repository it was never scoped to [9](#0-8) . This is a cross-repository write: the token's authorization boundary (one specific `stack_id`) is broken by an action that touches a different repository/stack entirely, directly matching the "stack a token authorises versus a stack it touches" binding called out in scope.

### Likelihood Explanation
Any deployment of Shipit that issues stack-scoped `write:stack` API tokens (a documented, intentional feature per the `ApiClient.stack` association and the `here_come_the_walrus`-style fixture pattern) is affected the moment such a token is used against `POST /stacks`; no additional privilege or race condition is required, only possession of that one scoped token.

### Recommendation
In `Api::StacksController#create`, when `current_api_client.stack_id?` is true, reject the request (403) or otherwise validate that the requested `repo_owner`/`repo_name`/`environment` resolves to the client's already-bound stack, mirroring the scoping already applied by `stacks`/`stack` in `show`/`update`/`destroy`.

### Proof of Concept
1. Provision `ApiClient` A with `stack_id = stack_foo.id` and permission `write:stack` (a legitimate, minimally-scoped token intended only to manage `stack_foo`).
2. Using A's Basic-Auth token, call `POST /stacks` with `repo_owner: "other-org", repo_name: "other-repo", environment: "production", branch: "main"`.
3. Observe `Api::StacksController#create` creates the new `Stack` successfully [3](#0-2)  — despite `current_api_client.stack_id` pointing only at `stack_foo`, proving the `write:stack`-scoped-to-one-stack binding is not enforced for `create`.
