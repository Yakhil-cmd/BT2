### Title
Webhook signature is verified against `repository.owner.login`, but event handlers act on the independent `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the HMAC against using `repository_owner`, a value read from the JSON body itself (`params.dig('repository','owner','login')`), while the event handlers that actually mutate state (e.g. `PushHandler`, `StatusHandler`) resolve the target repository/stack from a *different*, independently-controlled field of the same body: `repository.full_name`. Nothing binds these two fields together, so a valid signature computed with one organization's `webhook_secret` authorizes a payload that writes to a completely different organization's repository/stack. This mirrors the reported Solidity bug class: two logically-identical bindings (`the org that authenticates` vs `the repository that is written`) are backed by independent, unsynchronized values instead of one verified source of truth.

### Finding Description
`verify_signature` computes the signing key from a payload field, not from anything cryptographically bound to the rest of the payload's *content*: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`app_id`, `webhook_secret`, etc.) as documented for multi-org deployments: [3](#0-2) [4](#0-3) 

The HMAC (`verify_webhook_signature`) is computed over the *entire raw body* using the secret selected above: [5](#0-4) 

This proves only that *whoever holds the secret for `repository.owner.login`* produced the signature — it does not prove anything about the repository the handlers subsequently act on. Handlers derive the actual write target from a sibling field, `repository.full_name`, which is never cross-checked against `repository.owner.login`: [6](#0-5) [7](#0-6) 

Because an attacker who legitimately administers their own GitHub App installation for their own organization (org `A`, secret `S_A`) can freely construct the raw JSON body themselves (this is a synthetic HTTP POST directly to the webhook endpoint, not a real GitHub-relayed webhook), they can set `repository.owner.login = "A"` (so `Shipit.github(organization: "A")` resolves to their own known secret `S_A`) while setting `repository.full_name = "victim-org/victim-repo"` (so the handler's `stacks` lookup resolves an entirely different tenant's stack). They sign the whole crafted body with `S_A`, which passes `verify_signature` because the verification only checks that *the whole body* matches HMAC(`S_A`, body) — it never checks that `full_name`'s owner equals `owner.login`.

This exactly matches the required binding-break pattern: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Once the forged, validly-signed request passes `verify_signature`, `Shipit::Webhooks.for_event(event)` dispatches it to handlers keyed purely off `repository.full_name`, letting an attacker who controls only their own (unrelated, unprivileged) organization's webhook secret:
- Trigger `PushHandler` → `stack.sync_github(expected_head_sha:)` → `GithubSyncJob`, forcing arbitrary victim stacks to sync commits based on an attacker-chosen `after` SHA [8](#0-7) [9](#0-8) .
- Trigger `StatusHandler` → forge a `Commit#create_status_from_github!` state (e.g. mark a commit `success`) for `Commit.where(sha: params.sha)`, which is looked up globally, not scoped by repository [10](#0-9) . Since deploy readiness in Shipit is commonly gated on green CI status, this can be used to falsify the state used by deploy-blocking checks for a victim's stack.
- Trigger `MembershipHandler`/`CheckSuiteHandler` and other registered event types against stacks/data outside the attacker's own organization.

This crosses an organizational trust boundary that Shipit's multi-org GitHub App model is meant to enforce, enabling state corruption (forged commit statuses, forced syncs) in a victim's stack without requiring the victim's own `webhook_secret`, `ApiClient` token, or a Shipit session — satisfying the "unauthorized deploy/rollback" or cross-repository-write class of impact when combined with status/CI gating on deploy.

### Likelihood Explanation
Exploitability requires only that the attacker operates their own legitimately-installed GitHub App/org in a Shipit deployment configured for multiple organizations (a normal, documented configuration, see `docs/setup.md`), and can send arbitrary HTTP POSTs to the public `/webhooks` endpoint with a self-computed signature. No credentials belonging to the victim organization, no Shipit session, and no `ApiClient` token are required — only knowledge of a secret the attacker legitimately possesses for their own tenant. This is a fully unprivileged, remotely-triggerable condition.

### Recommendation
Bind the verified organization to the actual repository acted upon:
- After signature verification, re-derive `repository_owner` from `repository.full_name` (or explicitly compare `repository.full_name`'s owner segment to `repository.owner.login`/`organization.login`) and reject the request if they disagree.
- Alternatively, have handlers resolve the target `Stack`/`Repository` using the same identity (`repository_owner`) that was used to pick the signing secret, rather than trusting an independent `full_name` field pulled from the unauthenticated portion of request parsing logic.
- Scope `StatusHandler`'s `Commit.where(sha:)` lookup to the verified repository as well, to prevent cross-repository status forgery via SHA reuse.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs: `attacker-org` (attacker controls the GitHub App/installation and thus knows `webhook_secret_A`) and `victim-org` (has a stack tracked by Shipit).
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Attacker computes `sha1=HMAC(webhook_secret_A, body)` and sets it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), which succeeds since the attacker used their own known secret [1](#0-0) .
5. `create` dispatches to `PushHandler`, whose `repository_name` resolves to `"victim-org/victim-repo"` [11](#0-10) , causing `GithubSyncJob` to run against the victim's stack — despite the request never being signed by `victim-org`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  module Webhooks

      class PushHandler < Handler

          requires :ref
          requires :after

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
