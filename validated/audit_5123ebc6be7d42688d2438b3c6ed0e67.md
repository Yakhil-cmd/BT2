### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every handler routes on the *unchecked* `repository.full_name` field — allowing cross-organization stack sync/deploy triggering in multi-tenant Shipit installs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against based on `repository.owner.login` (or `organization.login`) read directly out of the untrusted JSON body. Once the signature check passes, the *entire* raw payload — including a separate, never-cross-checked `repository.full_name` field — is handed unmodified to every registered `Shipit::Webhooks::Handlers::Handler`, which uses `repository.full_name` (not `repository.owner.login`) to look up the `Repository`/`Stack` to act on. Because nothing enforces that `repository.full_name`'s owner segment matches `repository.owner.login`, a party who knows the webhook secret configured for one organization can sign a payload whose `owner.login` matches that organization (satisfying `verify_signature`) while setting `repository.full_name` to a *different* organization's repository, causing Shipit to sync/deploy stacks it has no authority over.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
picks the GitHub App config (and thus the `webhook_secret` used for HMAC verification, see `GitHubApp#verify_webhook_signature`) using: [2](#0-1) 

This is exactly the attacker-controlled field `params.dig('repository', 'owner', 'login')` inside the body whose integrity the signature is supposed to protect — but it's read out of the body *before* the signature is actually verified, purely to pick which secret to check against.

Once `verify_signature` passes, `create` dispatches the *raw, unmodified* parsed JSON to all registered handlers: [3](#0-2) 

Every handler (e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name`, via the base `Handler` class: [4](#0-3) [5](#0-4) 

Shipit explicitly documents and supports a multi-tenant deployment mode where a single Shipit instance serves multiple GitHub organizations, each with its own GitHub App and, critically, its own `webhook_secret`: [6](#0-5) [7](#0-6) 

In this documented configuration, `verify_signature` picks organization "A"'s secret if `repository.owner.login == "A"`, and organization "B"'s secret if `repository.owner.login == "B"`. The **binding that is broken** is:

`organization whose secret authenticated the request` ⟺ `repository/stack that the handler actually acts on`

Before the attack, these two are assumed to always coincide (a legitimate GitHub webhook always has `repository.owner.login` matching `repository.full_name`'s owner). After the attack, an actor holding organization A's webhook secret can craft a body where `repository.owner.login = "A"` (so `verify_signature` selects and successfully validates against A's secret) while `repository.full_name = "B/some-repo"` (so every handler resolves and acts on organization B's `Repository`/`Stack`, e.g. `PushHandler` calling `stack.sync_github(expected_head_sha: params.after)` → `GithubSyncJob`, or PR handlers archiving/unarchiving/provisioning review stacks under B).

### Impact Explanation
This is a cross-repository/cross-organization write: an actor with legitimate credentials (webhook secret) for only organization A's GitHub App can force Shipit to enqueue `GithubSyncJob` for stacks belonging to organization B, and via other handlers (`push_handler.rb`, PR handlers) trigger archive/unarchive/provisioning actions and, for stacks with continuous deployment enabled, downstream deploy activity — all without ever holding any credential for organization B. This crosses the "cross-repository writes / unauthorized deploy" bar because the org that authenticated the request is not the org whose repository state gets mutated.

### Likelihood Explanation
This requires the operator to run Shipit in the documented multi-organization mode (`docs/setup.md`, "Using Multiple Github Applications") and requires the attacker to know/control at least one configured org's `webhook_secret` — a scenario the engine itself anticipates as a legitimate, semi-trusted multi-tenant setup where different orgs' admins are not necessarily equally trusted with each other's repositories. Given a multi-org deployment, exploitation only requires crafting one raw HTTP POST with a body/signature pair computed offline; no other capability (session, ApiClient token, GitHub App private key) is needed.

### Recommendation
In `verify_signature`, after resolving `repository_owner` and validating the signature, also validate that the resolved organization matches the owner portion of every `repository.full_name` / `organization.login` referenced elsewhere in the same payload before dispatching to handlers — or better, derive the single GitHub App/secret to use strictly from `repository.full_name`'s owner (the same field handlers use), so the field that authorizes and the field that is acted upon are always the same value.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml`).
2. As a party who knows `OrgA`'s `webhook_secret` (e.g., its GitHub App admin), craft a `push` payload body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner == "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the signature validates successfully.
6. `PushHandler#process` runs against the full payload, resolving `stacks` via `Repository.from_github_repo_name("OrgB/target-repo")` and enqueuing `GithubSyncJob` for `OrgB`'s stack — despite the attacker never having any credential tied to `OrgB`.

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
