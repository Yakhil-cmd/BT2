### Title
Webhook HMAC verification is keyed on a payload field independent from the field used to locate the target repository, allowing cross-organization webhook forgery in multi-tenant deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate a webhook against using the attacker-supplied JSON field `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload (creating repositories/stacks, updating commit statuses, merging pull requests, etc.) resolve the target repository from a *different*, independently-controlled field of the same JSON body (`repository.full_name` / `repository.name`+`owner.name`). Because these two fields are not cryptographically bound to each other beyond being inside the same HMAC-signed blob, and a Shipit installation can be configured with a distinct `webhook_secret` per GitHub organization (`Shipit.github_organizations`, `github_app_config`), an actor who legitimately controls one onboarded organization (and therefore knows that organization's `webhook_secret`) can craft a signed payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` targets a completely different, victim organization's stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` looks up the app used for HMAC verification purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a per-organization config/secret when Shipit is set up in the multi-organization mode: [3](#0-2) 

The HMAC check itself only proves the body was signed by the secret associated with whatever organization `repository_owner` happened to name — it says nothing about the rest of the payload: [4](#0-3) 

The engine's own test suite demonstrates that `repository.full_name` is treated as an independent field from `repository.owner.login`, used solely by the event handlers to find/create the target `Repository`/`Stack`, decoupled from whatever value was used to select the verifying secret: [5](#0-4) 

**Binding broken:** `organization that authenticated` (`params.dig('repository','owner','login')`, used to pick the `webhook_secret`) `≠` `repository that is written` (`params['repository']['full_name']`, used by handlers to locate/create the `Repository`/`Stack` that is mutated). Nothing forces these two independently-read strings to refer to the same repository.

### Impact Explanation
In a Shipit deployment configured for multiple GitHub organizations (each with its own `github.<org>.webhook_secret`), any actor who is an admin of one onboarded organization (and thus can read/rotate that org's own GitHub App webhook secret) can forge a correctly-signed webhook whose `repository.owner.login` is their own org, but whose `repository.full_name`/commit/PR/status content references a victim organization's stack. Depending on the event type this can: create fake commits/statuses used to satisfy CI-gating and trigger unauthorized deploys, forge `pull_request`/`merge` events to push merge/close state on a repository they do not own, or fabricate `membership` events. This crosses the "unauthorized deploy/merge across repositories" boundary using credentials the attacker never should have for the victim repository — i.e. writes/actions on a repository the attacker does not control, satisfying the High/Critical impact bar (cross-repository writes / unauthorized deploy or merge) without needing the victim's `webhook_secret`, `GITHUB_TOKEN`, or a Shipit session.

### Likelihood Explanation
Requires only that the attacker be an authenticated owner/admin of *some* organization already onboarded onto the same multi-tenant Shipit instance — not a privileged Shipit account, API token, or the victim's secret. Multi-organization webhook configuration is a documented, supported configuration path (`docs/setup.md`, `lib/shipit.rb#github_organizations`), so this is a realistic deployment topology rather than a hypothetical one. The forgery itself is a simple HTTP POST with a manually computed HMAC using a secret the attacker legitimately possesses.

### Recommendation
Bind the field used to select the verification secret to the same field used to resolve the acted-upon repository (e.g., verify the signature using the secret associated with the organization contained in `repository.full_name`'s owner segment, and re-validate after parsing that the `organization.login`/`repository.owner.login` match `repository.full_name`'s owner). Alternatively, verify the payload against every currently configured organization secret and additionally assert that the resolved `Repository`'s owner matches the organization whose secret validated the request before handlers are invoked.

### Proof of Concept
1. Shipit instance is configured with two organizations, `attacker-org` and `victim-org`, each with its own `github.<org>.webhook_secret` (per `docs/setup.md` multi-org schema).
2. Attacker is an admin of `attacker-org`'s GitHub App installation and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a JSON body, e.g. for a `status` or `push` event:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully against the attacker's own known secret.
6. The event handler for `status`/`push` resolves the target `Repository`/`Stack` using `repository.full_name` = `"victim-org/victim-repo"`, applying the forged status/commit data to the victim's stack — enabling CI-gate bypass or spoofed deploy triggers on a repository the attacker does not control.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
