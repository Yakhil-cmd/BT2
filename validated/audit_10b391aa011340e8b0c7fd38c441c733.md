### Title
Webhook signature verified against a different organization than the repository the payload writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate `X-Hub-Signature` based on `repository_owner`, which falls back from `repository.owner.login` to `organization.login` in the raw, unauthenticated JSON body. The event handlers that subsequently act on the same body (e.g. `PushHandler`) look up the target `Stack`/`Repository` using an entirely different field, `repository.full_name`, without ever re-checking that this repository actually belongs to the organization whose secret was used to verify the signature.

### Finding Description
`verify_signature` computes: [1](#0-0) [2](#0-1) 

using `Shipit.github(organization: repository_owner)`, which resolves a webhook secret from `secrets.github[organization]` per [3](#0-2) . The signature check itself is a simple HMAC comparison of the *entire raw body* against that org's secret, per `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb`).

Once the signature passes, `WebhooksController#create` dispatches the same parsed body to handlers such as `PushHandler`: [4](#0-3) 

`PushHandler#process` and the base `Handler#stacks` resolve the affected `Stack` using `payload.dig('repository', 'full_name')`: [5](#0-4) [6](#0-5) 

The binding that should hold is: **organization whose secret verified the signature == organization that owns the repository the handler writes to**. But the verification step reads `repository.owner.login` (or `organization.login`) while the handler reads `repository.full_name` — two independent, attacker-controlled fields in the same unauthenticated JSON body, never cross-checked against each other. In a multi-tenant deployment (`Shipit.github_organizations` with multiple orgs, each with its own `webhook_secret`), an attacker who legitimately controls a webhook delivery for organization A (i.e., knows/can trigger a validly-signed payload for org A) can craft a body where `repository.owner.login`/`organization.login` = `"A"` (so the signature validates against A's secret) while `repository.full_name` = `"B/some-repo"` (a repository belonging to org B). The signature check passes using A's secret, yet `PushHandler` will act on `B/some-repo`'s stacks — e.g., calling `stack.sync_github(expected_head_sha: params.after)` for a repository the attacker does not control and was never authenticated for.

This is exactly analogous to the reported Solidity bug: two differently-scoped fields (`repository.owner.login` for auth, `repository.full_name` for the write target) are expected to agree but nothing enforces that agreement, similar to how `_hashLeaf` never validates the two packed fields are unambiguously bound together.

### Impact Explanation
This breaks a cross-repository trust boundary: a signature valid for one GitHub organization's webhook secret is treated as authorization to trigger sync/deploy-adjacent side effects on a stack belonging to a *different* organization/repository, provided that repository's owner/full_name fields can be forged in the payload body (only `X-Hub-Signature` is cryptographically bound; the JSON body's `repository` sub-object is not separately authenticated per field). This matches the "cross-repository writes" Critical impact bucket in scope, since `GithubSyncJob` triggered by `PushHandler` mutates commits/deploy-spec-cache state for a stack outside the authenticated tenant.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (multiple entries under `secrets.github` besides the top-level keys) where an attacker has the ability to produce a signature valid for at least one configured organization's `webhook_secret` (e.g., they operate a legitimate GitHub App/webhook installation for organization A, or otherwise can get a validly-signed delivery through GitHub for org A) and can control the JSON body's `repository.full_name`/`repository.owner.login` divergence within that single delivery. This is a realistic scenario for hosted/shared Shipit deployments serving many orgs, though it is contingent on the specific multi-org secrets configuration being used.

### Recommendation
After signature verification, re-derive the repository/organization to act on from the *same* field that was used for signature selection (or vice versa), and reject the request if `repository.full_name`'s owner segment does not match `repository_owner` used for `Shipit.github(organization:)`. Alternatively, verify the signature using a secret keyed strictly off `repository.full_name`'s owner, and use that identical value throughout `Handler#stacks`/`repository_name`.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orgA` (webhook_secret `SA`) and `orgB` (webhook_secret `SB`), each with tracked repositories.
2. Craft a push payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(SA, body)>` using `orgA`'s secret (attacker has legitimate access to trigger/know a valid orgA signature, e.g. via their own repo in orgA).
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"orgA"` (from `repository.owner.login`), validates successfully against `SA`.
5. `PushHandler#process` resolves `stacks` via `repository.full_name` = `"orgB/victim-repo"`, and calls `sync_github(expected_head_sha: ...)` on `orgB`'s stack — a cross-organization action never authenticated for `orgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
