Searching all call sites in the repo shows this function is only exercised by test code: property-based unit tests in [2](#0-1)  and a test helper for Jellyfish Merkle range-proof verification in [3](#0-2) , plus an unrelated example crate under `third_party/move/move-examples/diem-framework`.

None of these call sites sit on a production transaction-admission path (mempool, vm-validator, authenticator, REST/BCS input parsing). The actual production Merkle proof verification code in [4](#0-3)  reconstructs the root hash by folding sibling hashes using `iter_bits()` (producing bits from an already-trusted key), not `from_bit_iter` (consuming an arbitrary bit iterator to build a hash) — so there is no path where attacker-controlled proof/authenticator/API data is fed through `from_bit_iter` to corrupt a digest used for transaction-inclusion or expiry checks.

Additionally, exploiting the described guard would require constructing a custom `ExactSizeIterator` that violates its own contract (misreporting `len()`), which is not something achievable through untrusted transaction/proof/authenticator bytes deserialized via BCS/serde — those paths produce standard `Vec`/slice iterators whose `len()` is always accurate.

Since `from_bit_iter` has no production call site on the transaction-admission boundary (mempool, vm-validator, authenticator, or proof verification used for inclusion/expiry checks), this does not meet the boundary conditions or admission impact gate.

    pub fn from_bit_iter(
        iter: impl ExactSizeIterator<Item = bool>,
    ) -> Result<Self, HashValueParseError> {
        if iter.len() != Self::LENGTH_IN_BITS {
            return Err(HashValueParseError);
        }

        let mut buf = [0; Self::LENGTH];
        for (i, bit) in iter.enumerate() {
            if bit {
                buf[i / 8] |= 1 << (7 - i % 8);
            }
        }
        Ok(Self::new(buf))
    }
