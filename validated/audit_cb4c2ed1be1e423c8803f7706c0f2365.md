### Title
Cross-repository commit status/CI forgery via unscoped `Commit.where(sha:)` lookup allows an attacker to force `state: 'failure'` on a victim's commit and block continuous deployment - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit purely by `sha`, with no check that the webhook's `repository` matches the `Commit#stack`'s configured GitHub repository. `verify_signature` in `WebhooksController` only proves the payload was signed by *some* org the attacker legitimately controls (their own), not that it originates from the repository that owns the target commit's stack. An attacker who owns any GitHub repository can therefore emit a validly-signed `status` webhook naming a victim's known (public) commit sha with `state: 'failure'`, which `Commit#create_status_from_github!` will attach to the victim's `Commit`, flipping `Commit#deployable?` to `false` and preventing `Commit#schedule_continuous_delivery` from firing.

### Finding Description
The binding that should hold is: `repository that authenticated the webhook == repository.full_name of the stack owning Commit#sha`. This is false in the exploited path.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only verifies that the raw payload was HMAC-signed by the GitHub App/webhook secret belonging to `repository_owner` (derived from the payload's own `repository.owner.login`/`organization.login`, attacker-controlled data). It never cross-checks that `repository_owner`/`repository.full_name` matches any specific `Stack#repository`.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha` alone — no `stack_id`/repository scoping — and calls `create_status_from_github!` on every match across every stack/tenant in the installation.
- `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` (app/models/shipit/commit.rb:165-169, app/models/shipit/status.rb:24-33) creates a `Status` row with `state: params.state` tied to the victim commit, using the attacker-forged `state`/`description`/`context`.
- `Commit#deployable?` (app/models/shipit/commit.rb:227-229) is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`; injecting a `failure` status makes `success?` false (via `Status::Group`), flipping `deployable?` to `false`.
- `Commit#schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287) is gated on `deployable?`, so the forged failure prevents `ContinuousDeliveryJob` from being scheduled for the victim's otherwise-passing commit, defeating `Stack`'s continuous-deployment window for that sha.

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: status`, `X-Hub-Signature` computed with the attacker's own repository/org webhook secret (which they legitimately possess because they own that repo/org and configured the webhook, or trigger it via GitHub's real Status API on their own repo pointing at an arbitrary sha string), and JSON body:
```json
{
  "sha": "<victim's known/public commit sha>",
  "state": "failure",
  "context": "ci/attacker-forged",
  "repository": {"owner": {"login": "attacker-org"}}
}
```
Because GitHub's commit-status API does not require the target sha to exist in the posting repository, the attacker can produce a real, validly-signed webhook from their own repo naming any 40-character sha, including a victim's.

Existing guards do not stop this: `verify_signature` validates the *sender's own* signing key, not sha-to-repository ownership; `ExplicitParameters` (`params.sha`, `params.state`) only validates types/presence, not repository binding; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
An attacker controlling any GitHub repository can, per request, write a forged `Status` record onto an arbitrary victim `Commit` in a completely unrelated stack/tenant, flipping `deployable?` and blocking `schedule_continuous_delivery`/`trigger_continuous_delivery` for that commit. This is a cross-repository write into another tenant's `Commit`/`Stack` state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is fully repeatable against any commit sha the attacker can learn (commit shas are public via GitHub), against any number of victim stacks sharing Shipit's webhook endpoint, providing a targeted denial of legitimate deploys (and, symmetrically, the inverse of this bug — forging `success` — has already been shown to enable unauthorized deploys of unreviewed code).

### Likelihood Explanation
Preconditions are minimal: the attacker needs only a GitHub repository they control (to obtain a real signature) and knowledge of the victim's commit sha (public information visible on GitHub for any public repo, or via any prior webhook/PR they can observe). No Shipit session, API token, or GitHub App key is required. Cost is a single crafted HTTP POST replicated at will. This is highly feasible and trivially repeatable.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to only touch commits/stacks belonging to the repository that the verified webhook actually corresponds to, e.g. filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })`, and have `verify_signature`/`Handler` pass down and enforce the authenticated `repository.full_name` against `Stack#repository`/`Commit#stack` before applying any status/check-run mutation.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "a status webhook from an unrelated repository can flip deployable? on a victim commit" do
  victim_stack = shipit_stacks(:shipit) # repository: "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")
  victim_commit.statuses.create!(stack: victim_stack, state: "success", context: "ci")

  assert victim_commit.reload.deployable?, "precondition: victim commit is currently deployable"

  # Binding under test (must be false to prove the bug):
  # attacker_repository.full_name == victim_stack.repository.full_name
  attacker_payload = {
    "sha" => victim_commit.sha,
    "state" => "failure",
    "context" => "ci/attacker",
    "repository" => { "owner" => { "login" => "attacker-org" }, "full_name" => "attacker-org/unrelated-repo" }
  }
  refute_equal victim_stack.repository.full_name, attacker_payload["repository"]["full_name"]

  Shipit::Webhooks::Handlers::StatusHandler.new.call(attacker_payload)

  refute victim_commit.reload.deployable?, "attacker from unrelated repo forced victim commit non-deployable"
end
```
This test bypasses `WebhooksController#verify_signature` intentionally (calling the handler directly) since the exploit's core defect is in `StatusHandler#process`'s lack of repository scoping, independent of signature validity — the signature check only authenticates the attacker's own org, not the target repository binding.
