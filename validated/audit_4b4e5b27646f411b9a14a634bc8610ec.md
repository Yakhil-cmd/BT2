### Title
Cross-organization webhook forgery via unauthenticated `repository`/`sha` fields lets any configured GitHub App forge CI status and push events for stacks belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC secret) to validate a webhook against using unauthenticated JSON body fields (`repository.owner.login` / `organization.login`), not any value bound to the transport or endpoint identity. Once that check passes, the event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) act on a *different*, also-unauthenticated field (`repository.full_name`, or for `StatusHandler` just a bare `sha`) to decide which `Stack`/`Commit` to mutate. In a multi-organization Shipit deployment this breaks the binding "organization whose secret authenticated the request == repository being written."

### Finding Description
`Shipit.github` supports hosting multiple GitHub Apps/organizations behind one Shipit instance (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github_app_config`). Each org has its own `webhook_secret`, and the secret is optional per org (`docs/setup.md:71` "Webhook secret (optional)"; test fixtures configure `webhook_secret: # nil`).

In `WebhooksController#verify_signature`: [1](#0-0) 
the organization used to pick the verifying secret comes straight from the untrusted payload: [2](#0-1) 
and `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's secret is blank: [3](#0-2) 

After this check, `WebhooksController#create` dispatches to handlers using the same raw, attacker-controlled `params`: [4](#0-3) 

Handlers resolve the target `Stack`/`Commit` from a *different* unauthenticated field than the one used to select the verifying org:
- `Handler#stacks` resolves by `repository.full_name`, independent of `repository.owner.login`: [5](#0-4) 
- `StatusHandler#process` is even weaker: it looks up **any** commit anywhere in the whole install by bare `sha`, with no repository/org scoping at all, and directly records the attacker-supplied `state`/`context`/`target_url`: [6](#0-5) 
- `PushHandler#process` similarly triggers a sync using `repository.full_name`: [7](#0-6) 

Nothing anywhere cross-checks that the organization used to select/verify the HMAC secret (`repository.owner.login`) matches the organization that actually owns the `repository.full_name` (or, for `status` events, the commit's stack) that gets acted upon. The two fields are independent, attacker-supplied JSON keys in the same unauthenticated POST body.

### Impact Explanation
An attacker who can produce a valid signature for **any one** of the organizations configured in a multi-tenant Shipit instance (including trivially, any org whose optional `webhook_secret` was left blank, or any org whose GitHub App they otherwise install/control) can:
- Set `repository.owner.login` (or `organization.login`) to the org whose secret they hold to pass `verify_signature`.
- Set `repository.full_name` in the same payload to point at a completely different, victim organization's repository configured on the same Shipit instance, or, for the `status` event, simply supply a `sha` that matches any commit on any stack.

For the `status` event this enables directly writing arbitrary commit statuses (`state`, `context`, `description`, `target_url`) on commits belonging to victim stacks they have no access to. `Commit#deployable?` and `schedule_continuous_delivery` gate deploy eligibility purely on recorded status/CI state: [8](#0-7) [9](#0-8) . By forging a "success" status for a `ci.require`d context on a target commit, an attacker can satisfy CI gating and cause `ContinuousDeliveryJob` to deploy that commit on a stack they were never authorized to touch — an unauthorized deploy triggered purely by exploiting the webhook org/signature-selection mismatch. This matches the report's underlying bug class: a check (HMAC/org verification) performed on a value that is not the same value the subsequent effect (repository/commit mutation) is bound to.

I was not able to fully trace whether `ContinuousDeliveryJob` performs any additional revalidation against GitHub before actually deploying (e.g., re-fetching status from the real GitHub API) which could reduce/eliminate practical exploitability; this would need to be confirmed by a background agent with full test/runtime access, since the index does not show the complete `ContinuousDeliveryJob`/`stack.deployable?` chain.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with more than one GitHub organization (an explicitly documented, supported configuration), and (2) the attacker controlling or knowing the webhook secret for at least one of the configured orgs (trivial if any org has no `webhook_secret` set, which the docs mark optional). No repository write access, no `ApiClient` token, and no privileged Shipit account are required — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted body and matching (or absent) signature.

### Recommendation
- Verify webhook signatures against the secret of the organization that actually owns the acted-upon repository/commit, not a value taken from the same untrusted payload used to select the secret.
- In each handler, cross-check that `repository.owner.login`/`organization.login` used for signature selection matches the owner of `repository.full_name` (and, for `StatusHandler`, scope commit lookup by repository, not bare `sha`, across all stacks).
- Consider disallowing blank `webhook_secret` in multi-organization configurations, or requiring the same secret validate the specific org's own installation only.

### Proof of Concept
Given a Shipit instance configured with two orgs, `OrgA` (webhook secret unset/known) and `OrgB` (victim, `ci.require: ["ci/checks"]`):
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<valid HMAC for OrgA's secret (or omitted if OrgA has none)>

{
  "sha": "<sha of an undeployed commit belonging to an OrgB stack>",
  "state": "success",
  "context": "ci/checks",
  "repository": { "owner": { "login": "OrgA" } }
}
```
`verify_signature` resolves `Shipit.github(organization: "OrgA")` and passes; `StatusHandler#process` then looks up `Commit.where(sha: ...)` with no scoping to `OrgA`, matching the OrgB commit, and records the forged "success" status via `create_status_from_github!`, potentially unblocking `deployable?`/continuous delivery on the OrgB stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
