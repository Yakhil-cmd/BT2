### Title
Webhook signature is verified against the payload's `repository.owner.login`/`organization.login`, but event handlers act on the unrelated `repository.full_name` and even repo-unscoped commit `sha` lookups, letting an attacker who controls (or abuses a secret-less) one configured GitHub organization forge state for a completely different repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` picks *which* GitHub App/organization's `webhook_secret` to validate a payload against using an attacker-controlled field (`repository.owner.login`, falling back to `organization.login`), but never re-validates that this same field matches the repository the payload's handler actually mutates (`repository.full_name`). Several handlers derived from that `full_name` (or, worse, not scoped by repository at all) then write/trigger real state. This mirrors the reported bug class exactly: a value used to select/validate the trust boundary (`ERC20Method`/here "which org's secret verifies this request") is decoupled from the value the code actually acts on (`transfer_payload`/here `repository.full_name` and `sha`).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration solely from a payload field: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` short-circuits to `true` if the selected organization has no `webhook_secret` configured, which the setup docs explicitly describe as **optional**: [3](#0-2) 

Meanwhile, the actual event handlers resolve the target repository/commit from a *different, unrelated* field of the same JSON body - `repository.full_name` - with no check that it is consistent with `repository.owner.login`/`organization.login` used moments earlier to pick the verifying secret: [4](#0-3) [5](#0-4) 

`StatusHandler` is even more exposed: it doesn't scope by repository at all, matching commits **globally by SHA** across the entire Shipit install: [6](#0-5) 

So the "organization that authenticated" (whatever org's secret happened to validate, or trivially bypassed because that org left `webhook_secret` blank) is never bound to "the repository that is written" (`repository.full_name` used to look up `Stack`s, or the completely unscoped commit `sha` lookup in `StatusHandler`).

### Impact Explanation
An unauthenticated attacker who can satisfy `verify_signature` for **any one** configured organization (trivial if that org has no `webhook_secret` set, which the docs list as optional and which multi-org example configs in this repo show as commonly left blank) can submit a forged webhook whose `repository.full_name`/`sha` target an entirely different, unrelated Shipit-tracked repository:
- Via `push`, force `PushHandler` to invoke `stack.sync_github(expected_head_sha: ...)` on an arbitrary stack belonging to a different repository than the one that "authenticated" the request.
- Via `status`, forge a passing CI status for **any commit SHA tracked anywhere in the Shipit instance** (not scoped to any repository), directly undermining `ci.require` checks that gate deploy/merge safety, which can facilitate an unauthorized deploy.

This satisfies the "cross-repository writes" / "unauthorized deploy" impact criteria: the credential/authentication boundary (which org's secret validated the request) is never bound to the repository/commit actually mutated.

### Likelihood Explanation
Likelihood is high for any Shipit deployment that (a) supports multiple GitHub organizations (the shipped example configs `config/secrets.development.shopify.yml`/`docs/setup.md` show this pattern) and (b) leaves `webhook_secret` unset for at least one org, which is explicitly documented as optional. No privileged credentials, session, or `ApiClient` token are required - only a raw unauthenticated POST to `/webhooks` with a crafted body and matching `X-Github-Event`.

### Recommendation
After signature verification, re-validate that the organization/owner used to select the verifying secret (`repository_owner`) matches the owner encoded in `repository.full_name` (and any other repository identifiers used by handlers) before dispatching to handlers. Additionally, scope `StatusHandler`'s commit lookup by the request's verified repository rather than a global `sha` match, and require an explicit, non-blank `webhook_secret` per configured organization (reject/warn on blank secrets) rather than silently trusting unsigned payloads.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.yml`: `victim-org` (tracked stacks, has a webhook secret) and `attacker-org` (webhook_secret left blank, as shown optional in `docs/setup.md`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim-org's required-CI commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally - no valid signature needed.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which is not scoped to `attacker-org` at all, and marks the victim's commit status as `success`, satisfying `ci.require` for a stack the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
