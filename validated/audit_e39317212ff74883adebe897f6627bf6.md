### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Trust `repository.full_name` — Cross-Organization Forged Webhook Write - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects which GitHub organization's HMAC secret to verify a webhook against using one field of the unverified JSON body (`repository.owner.login`), but the actual target stack/repository that gets written to as a result of the event is resolved from a *different*, unrelated field of the same unverified body (`repository.full_name`). Because the two fields are never cross-checked, a party that legitimately controls the webhook secret for one Shipit-registered organization can forge a payload that authenticates as that organization while acting on a repository/stack belonging to a completely different organization.

### Finding Description
`WebhooksController#verify_signature` picks the verifying `GitHubApp`/secret purely from payload data: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the request body (`params.dig('repository', 'owner', 'login')`), which is attacker-controlled content transmitted alongside the signature — nothing in the signature computation binds the signature to *which* organization/secret was actually used to compute it beyond whichever secret `Shipit.github(organization: repository_owner)` happens to select.

`Shipit.github` resolves a distinct `webhook_secret` per organization in multi-tenant configurations: [3](#0-2) 

Once `verify_signature` passes, `create` dispatches the same raw payload to handlers: [4](#0-3) 

All default handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the base `Handler` used by pull-request handlers) determine the *actual* stack(s) to mutate using `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

The equality that should hold — "organization whose secret authenticated the request" == "organization/repository that gets written to" — is never enforced. Before the attack: the field used for signature selection (`owner.login`) and the field used for stack resolution (`full_name`) are implicitly assumed to describe the same repository. After the attack: an attacker crafts a payload where `repository.owner.login` names an organization whose `webhook_secret` the attacker can legitimately obtain a valid signature for (e.g., an org they administer that is also registered on this Shipit instance), while `repository.full_name` names a stack under a completely different, victim organization. `verify_signature` succeeds (secret for the attacker's own org matches), and `PushHandler`/`StatusHandler`/`CheckSuiteHandler` resolve and mutate the victim's stack via `Repository.from_github_repo_name(repository_name)`.

This is the direct analog of the reported bug class: a value used for a security decision (`setMaxTotalSupply`/signature-secret-selection) is decoupled from the value actually acted upon (`totalSupply`/`full_name`-based stack resolution), letting an attacker exploit the gap between the two.

### Impact Explanation
An attacker who controls (or can trigger deliveries for) any single organization onboarded to a multi-tenant Shipit instance can forge webhook events — e.g. `push` events driving `stack.sync_github(expected_head_sha: params.after)`, `status`/`check_suite` updates — against stacks belonging to unrelated organizations they do not administer. This is a cross-repository write: it lets an outsider (relative to the victim org) manipulate the recorded GitHub state (commit statuses, deployed refs, sync state) of stacks/repositories they have no legitimate relationship to, potentially unblocking or corrupting deploy gating for those stacks. This meets the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Requires the attacker to already have a Shipit-registered GitHub organization/webhook secret of their own (i.e., legitimately control at least one tenant on the instance), which is a real but non-Shipit-privileged position — they need no Shipit session, API token, or admin access to the engine itself. On multi-organization deployments (the `secrets.github` keyed-by-org configuration explicitly supported by `Shipit.github_app_config`), this is directly reachable by simply crafting a JSON body with mismatched `repository.owner.login` and `repository.full_name` values and computing the HMAC with the attacker's own known secret.

### Recommendation
Bind signature verification to the same repository identity that handlers use for authorization: verify the webhook using the secret associated with the resolved target repository/stack (via `repository.full_name` → `Repository.from_github_repo_name` → owning organization), or, if the org config must be selected first, cross-check that `repository.full_name`'s owner matches `repository_owner`/the organization whose secret validated the signature before dispatching to any handler.

### Proof of Concept
1. Attacker legitimately owns/administers GitHub organization `attacker-org`, which is registered on the target Shipit instance with a known/derivable `webhook_secret` (per multi-org `secrets.github` config).
2. Victim organization `victim-org` also has a stack (e.g. `victim-org/app`) registered on the same Shipit instance.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known webhook secret over this exact raw body.
5. POSTs to `/webhooks` with `X-Github-Event: push`. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature.
6. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/app")` (via `Handler#repository_name`, app/models/shipit/webhooks/handlers/handler.rb:36-38) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — a write triggered on a repository the attacker's authenticated organization does not own.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
