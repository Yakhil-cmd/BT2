### Title
CCMenu token minted without stack scoping grants cross-stack read access - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::CCMenuUrlController#fetch` mints an `ApiClient` with `read:stack` permission but never sets `stack_id` on it, and `Api::BaseController#stacks` only restricts an API client's visible stacks when `current_api_client.stack_id?` is true. Because the CCMenu client's `stack_id` is `nil`, `stacks` falls back to `Stack.all`, so the token returned for one stack's CCMenu URL is honored by `Api::CCMenuController` for every stack in the installation.

### Finding Description
The intended binding is: `token issued by CCMenuUrlController#fetch for stack S` == `set of stacks readable via that token` == `{S}`. In practice the second side equals `Stack.all`.

Path:
- `CCMenuUrlController#fetch` (`app/controllers/shipit/ccmenu_url_controller.rb:7-11`) requires only `current_user` via `ShipitController`/`Shipit::Authentication`, i.e. any logged-in Shipit user who can view the stack's settings page.
- `#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`. `ApiClient#stack` is `belongs_to :stack, optional: true` (`app/models/shipit/api_client.rb:8`), and it is never assigned here, so `stack_id` is `nil`.
- `#fetch` embeds `client.authentication_token` (a signed client id, `app/models/shipit/api_client.rb:34-36`) into the URL for `Api::CCMenuController#show`, keyed only by the visible path segment `stack_id: stack.to_param` - this path segment is not stored anywhere on the token.
- `Api::CCMenuController#show` (`app/controllers/shipit/api/ccmenu_controller.rb:22-31`) authenticates via `authenticate_api_client`/`ApiClient.authenticate(params[:token])`, requires `read:stack` (satisfied), then resolves `stack` via `stacks.from_param!(params[:stack_id])`.
- `Api::BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`): `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. Since the CCMenu client's `stack_id` is `nil`, `stack_id?` is false and the scope is `Stack.all` - any `stack_id` in the path is accepted, regardless of which stack the token was originally minted for.

Additionally, the client is looked up by `creator` + fixed `name: 'CCMenu Client'` with no stack disambiguation, so the same single client/token is reused (and is valid) across every stack the user later requests a CCMenu URL for - reinforcing that the token is not stack-scoped at any layer.

None of the API-layer guards prevent this: `require_permission :read, :stack` only checks the permission string, not the target stack; `authenticate_api_client` only verifies the token signature; there is no per-token stack check beyond the `stacks` scoping method, which is bypassed by the nil `stack_id`.

### Impact Explanation
Any logged-in user with UI access to even one non-sensitive stack can obtain a `ccmenu_url` for that stack, extract its `token` query parameter, and replay it against `Api::CCMenuController#show` for arbitrary other `stack_id` values, receiving each target stack's latest deploy/rollback id, status, and timestamp (`app/controllers/shipit/api/ccmenu_controller.rb:22-24`, `shipit/ccmenu/project` view). This is an unauthorized cross-tenant read of stack deploy state that the attacker's own permissions do not grant, matching the High-severity category "unauthenticated/unauthorized read of stack state." It is fully repeatable: the token does not expire and works for every stack in the Shipit installation, not just the one named in the original request path.

### Likelihood Explanation
Preconditions are minimal: the attacker needs a normal logged-in Shipit session with access to at least one stack's settings page (the README documents broad org-wide OAuth login as a common deployment). No secrets, admin role, or API client credentials are required - only a single authenticated HTTP GET to `/stacks/:owner/:repo/:env/cc_menu_url` and then reuse of the returned token against `/api/stacks/:other_owner/:other_repo/:other_env/cc_menu.xml`. This is trivial and fully feasible with tools already available to any low-privilege logged-in user.

### Recommendation
Set `stack_id: stack.id` when creating the `ApiClient` in `CCMenuUrlController#client`, and/or change `Api::BaseController#stacks` to always scope by `current_api_client.stack_id` when it is present versus absent by design intent (i.e., ensure CCMenu-purpose clients always have a non-nil `stack_id`), and disambiguate the `find_or_create_by!` lookup by stack so a distinct, stack-scoped client/token is minted per stack rather than one client reused/shared across all stacks a user visits.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (conceptual)
test "ccmenu token for stack A can read stack B's cc_menu.xml" do
  low_priv_user = shipit_users(:walrus) # only has UI access to stack_a
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # different, unrelated stack

  session[:user_id] = low_priv_user.id
  get :fetch, params: { stack_id: stack_a.to_param }
  ccmenu_url = JSON.parse(response.body)['ccmenu_url']
  token = URI(ccmenu_url).query.split('token=').last

  # Binding under test: token minted for stack_a should NOT be valid for stack_b
  get "/api/stacks/#{stack_b.repository.owner}/#{stack_b.repository.name}/#{stack_b.environment}/cc_menu.xml",
      params: { token: token }

  assert_response :success # demonstrates the divergence: expected :not_found/:forbidden
end
```
This demonstrates the equality `{stacks readable by token} == {stack_a}` fails; the actual set is `Stack.all` due to `ApiClient#stack_id` being `nil` and `Api::BaseController#stacks` falling back to `Stack.all`.
