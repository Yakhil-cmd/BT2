### Title
Webhook signature verification keys off an unsigned `params` lookup instead of the signed payload, allowing organization confusion / signature-check bypass - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a delivery against by reading `repository_owner`, which is derived from `params.dig('repository','owner','login')` / `params.dig('organization','login')` [1](#0-0) . This value is **not** the same object that is actually signature-checked. The signature check runs against `request.raw_post` [2](#0-1) , but `params` in Rails is `request.GET.merge(request.POST)` — a **shallow** merge where a query-string key is used whenever the POST body does not itself contain that same top-level key. Multi-org Shipit installations configure a distinct `webhook_secret` per organization (see `test/dummy/config/secrets_double_github_app.yml`, and `Shipit.github_app_config` / `Shipit.github`) [3](#0-2) . If any configured/onboardable organization has `webhook_secret: nil`, `verify_webhook_signature` unconditionally returns `true` [4](#0-3) .

### Finding Description
The trust binding that should hold is: **organization used to select the verification secret == organization whose payload is being verified**. The controller breaks this equality when the inbound event's JSON body lacks a top-level `repository` key (e.g. `membership`, or any event type where GitHub omits it, or simply a body crafted without it), because in that case `repository_owner` falls through to reading `organization.login` from `params`, and `params` can be influenced by attacker-supplied query-string parameters that were never covered by `X-Hub-Signature` (the HMAC is computed only over `request.raw_post`, i.e. the body) [5](#0-4) . An attacker can append `?organization[login]=<org-with-no-secret>` to the `/webhooks` URL while sending an arbitrary, unsigned body for a target organization/event. `verify_signature` then calls `Shipit.github(organization: 'org-with-no-secret')`, which looks up that organization's app config and instantiates a `GitHubApp` whose `webhook_secret` is `nil`, making `verify_webhook_signature` return `true` for free regardless of the actual signature header supplied [4](#0-3) . The `create` action then dispatches the (forged) payload to handlers such as `MembershipHandler`, which can add/remove `Membership` records and thereby manipulate `Shipit.github_teams` authorization state [6](#0-5) [7](#0-6) .

### Impact Explanation
This crosses the "GitHub identity/organization authenticated" vs. "organization whose payload is written" boundary named in the rules. Because handlers like `MembershipHandler` mutate `Membership`/`Team` state used by `User#authorized?` (`Shipit.github_teams`) [8](#0-7) , an unauthenticated attacker who can reach `/webhooks` and knows (or can guess) any configured organization slug with an unset `webhook_secret` can forge team-membership events, escalating into `Shipit.github_teams` authorization — matching the High-impact category explicitly listed ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (documented and tested — `secrets_double_github_app.yml`), (2) at least one configured organization with a blank `webhook_secret` (shown as a supported/valid configuration in the fixture, and the code path explicitly special-cases `webhook_secret` being blank rather than rejecting it) [9](#0-8) , and (3) an event payload lacking the `repository` key so the `organization` fallback is reached. No authentication, session, token, or repository access is required — only network reachability of the public `/webhooks` endpoint.

### Recommendation
Determine `repository_owner` exclusively from the parsed, already-signed `request.raw_post` body (not from Rails' merged `params`), and reject/short-circuit when query-string parameters attempt to supply `repository`/`organization` keys. Additionally, treat a missing/blank `webhook_secret` for a configured organization as "verification required and failing" rather than "verification skipped," or require every organization entry to explicitly opt out.

### Proof of Concept
1. Configure (or target) a multi-org Shipit instance where organization `OrgTwo` has `webhook_secret: nil` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Send: `POST /webhooks?organization[login]=OrgTwo` with header `X-Github-Event: membership` and a body such as `{"action":"added","team":{...},"organization":{"login":"OrgOne"},"member":{"login":"attacker"}}` and no valid `X-Hub-Signature` (or an arbitrary one).
3. `repository_owner` returns `"OrgTwo"` from the query string (body has no `repository` key, and the body's own `organization.login` collides with `organization` if also absent from body, or the attacker can simply omit `repository`/`organization` from the body entirely and let the query string supply it).
4. `Shipit.github(organization: 'OrgTwo')` builds a `GitHubApp` with `webhook_secret = nil`; `verify_webhook_signature` returns `true` unconditionally.
5. `MembershipHandler` processes the unsigned/forged body, adding `attacker` to a `Membership`, potentially satisfying `Shipit.github_teams` and unlocking authenticated-only actions (deploys, task triggers, etc.) once combined with normal GitHub OAuth login.

Note: I was unable to execute Rails locally to confirm the exact precedence/merge semantics of `ActionDispatch::Http::Parameters` (`GET.merge(POST)`) in this specific Rails version bundled in the repo, and could not find a test in this codebase that pins this behavior for the `WebhooksController`. This assumption underlies the exploit's reliance on query-string fallback and should be verified against the actual Rails version in the Gemfile.lock (out of scope per rules) before treating this as fully confirmed.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
