### Title
Webhook signature verification is keyed off an attacker-controlled `repository.owner.login`/`organization.login` field that is never bound to the `repository.full_name` the payload actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, a value read straight out of the unauthenticated JSON body [1](#0-0) . The signature is only checked against *that* organization's secret [2](#0-1) . However, the handlers that actually mutate state (`PushHandler`, `MembershipHandler`, etc.) resolve the target `Repository`/`Team` from a *different* payload field, `repository.full_name` or `organization.login`, with no cross-check that it matches the org whose secret was used for verification [3](#0-2) [4](#0-3) .

### Finding Description
In a multi-organization Shipit deployment (the documented `github: {org1: {...}, org2: {...}}` schema [5](#0-4) ), each organization has its own `webhook_secret`, looked up via `Shipit.github(organization: org)` [6](#0-5) . `verify_webhook_signature` explicitly treats a blank/`nil` secret as automatically verified: `return true unless webhook_secret` [7](#0-6) , and `webhook_secret` is documented as optional per-org [8](#0-7) .

The controller determines *which* org's secret to check against solely from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  — a field inside the very payload being verified, fully attacker-controlled since the request is unauthenticated at this point. This is the binding-break: **the organization whose secret authenticates the request ≠ the repository/organization the handler subsequently writes to**, because the two are read from independent JSON paths that an attacker can set inconsistently:
- Verification org: `repository.owner.login` / `organization.login`
- Handler-mutated target: `repository.full_name` (`PushHandler`/generic `Handler#repository_name`) or `organization.login` again in `MembershipHandler`, plus arbitrary `member.login`/`team.*` fields [9](#0-8) .

If any configured organization in `secrets.github` has `webhook_secret: nil` (explicitly supported/documented as optional), an attacker can craft a webhook whose `repository.owner.login`/`organization.login` names that no-secret org (satisfying `verify_signature`, since `verify_webhook_signature` short-circuits to `true`) while setting `repository.full_name` (or, for `membership` events, `organization.login`/`team`/`member`) to point at a *different*, protected organization's repository/team that Shipit actually tracks. Because `Handler#repository_name` and `MembershipHandler` never re-check that the resolved target belongs to the same org that was used for signature verification, the forged event is processed as if it were legitimately signed by the target org.

Concretely, for `membership` events this lets an unauthenticated attacker: create teams on the fly with `team.organization = params.organization.login` and add arbitrary GitHub logins as team members [10](#0-9) . Since `Shipit.github_teams` authorization (who may act as a member of an authorized team) is used to gate access to the whole application [11](#0-10) , an attacker who can add an arbitrary GitHub login into a team that matches `Shipit.github_teams` can grant *any* GitHub account (including their own) access to the deploy application — this is a direct authorization-escalation path into `Shipit.github_teams`.

### Impact Explanation
This reaches the High-severity bucket explicitly listed: "escalation into `Shipit.github_teams` authorization." By forging a `membership` webhook signed under a weak/no-secret organization's config while naming a target team/organization Shipit trusts, an unprivileged attacker can insert an arbitrary GitHub identity into an authorized team, bypassing the `force_github_authentication`/`authorized?` check and gaining access to stacks, deploy triggers, and stack settings.

### Likelihood Explanation
This requires a specific but documented and supported configuration: multiple GitHub orgs configured under `secrets.github`, with at least one of them having `webhook_secret` unset (which the docs/example config explicitly allow — `webhook_secret: # nil`). Given Shipit explicitly supports "multiple GitHub applications for different GitHub organizations" and marks `webhook_secret` "(optional)" per org, this misconfiguration is plausible in real deployments, especially internal/low-traffic orgs added without setting up a webhook secret. The root cause is a code-level design flaw (trust decision keyed on unauthenticated data, and no cross-check between the verifying org and the acted-upon org/repository) rather than a one-off admin mistake, since even a careful admin has no code-level mechanism to bind the two together.

### Recommendation
- Do not select the verification secret using unauthenticated payload fields; instead, ensure the resolved GitHub App/secret used for verification is the *same* one whose organization scope matches the repository/organization that handlers subsequently mutate (assert `repository.owner.login == verified_organization` and `organization.login == verified_organization` before dispatching to handlers).
- Remove or restrict the `return true unless webhook_secret` shortcut in `GitHubApp#verify_webhook_signature`, or make `webhook_secret` mandatory in multi-org configurations, since it turns "optional" into "unauthenticated by default."
- In `Shipit::Webhooks::Handlers::Handler` and `MembershipHandler`, explicitly bind the handler's `organization`/`repository.full_name` to the same trusted organization identity resolved by `WebhooksController#verify_signature`, rather than re-reading it independently from the payload.

### Proof of Concept
1. Configure Shipit with two orgs: `trusted_org` (has `webhook_secret` set, tracked stacks/teams) and `attacker_org` (added to `secrets.github` but with `webhook_secret: nil`, e.g. as a WIP integration).
2. Attacker sends a `membership` webhook to `/webhooks` with no valid `X-Hub-Signature` (or any junk value), and body:
```json
{
  "action": "added",
  "team": { "id": 123, "name": "Ops", "slug": "ops", "url": "https://api.github.com/teams/123" },
  "organization": { "login": "trusted_org" },
  "member": { "login": "attacker-handle" },
  "repository": { "owner": { "login": "attacker_org" }, "full_name": "attacker_org/whatever" }
}
```
3. `repository_owner` resolves to `attacker_org` (from `repository.owner.login`) [1](#0-0) ; `Shipit.github(organization: 'attacker_org')` has a blank `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally [7](#0-6) .
4. `MembershipHandler#process` runs using `params.organization.login == 'trusted_org'`, creating/reusing the `Team` scoped to `trusted_org` and adding `attacker-handle` as a member [12](#0-11) .
5. If that team is one of `Shipit.github_teams`, the attacker's GitHub login now passes `current_user.authorized?` and gains full access to `trusted_org`'s stacks.

Note: I could not fully verify from static inspection whether `current_user.authorized?` re-checks live GitHub team membership on every request versus trusting the locally-stored `Membership` record created by this handler; this affects how persistent the escalation is, and would need confirmation by inspecting `User#authorized?`/`Membership` in a live session, which is outside what this index could fully resolve.

```ruby
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
