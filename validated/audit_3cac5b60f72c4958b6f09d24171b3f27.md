### Title
Unbounded, sequentially-processed AA trigger backlog is executed while holding the global write lock, allowing an attacker to stall unit confirmation network-wide - ([File: writer.js])

### Summary
`writer.saveJoint()` acquires a single, global `"write"` mutex before doing anything else and does not release it until *all* AA trigger processing for the just-stabilized MCI(s) has finished. AA trigger execution (`aa_composer.handleAATriggers`) processes every pending trigger strictly sequentially (`async.eachSeries`) under its own mutex, and each trigger can recursively invoke secondary/chained AAs. Because this entire computation happens *inside* the global write lock, any unprivileged user can cheaply post units that trigger many/expensive AA calls to make the write lock be held for an extended period, during which no node can validate or save any other unit — exactly the "sequential processing blocks unrelated work" bug class described in the analog report, but here the blocked resource is the DAG's global unit-write path rather than a batcher.

### Finding Description
`saveJoint` takes the write lock up front: [1](#0-0) 

It only releases that lock at the very end of the function, and in between it `await`s AA trigger execution both for the MCI that stabilized as part of this call and for any further cascading stabilizations: [2](#0-1) [3](#0-2) [4](#0-3) 

`aa_composer.handleAATriggers()` itself is fully sequential: it takes a global `['aa_triggers']` mutex and then iterates every queued trigger one at a time with `async.eachSeries`, invoking `handlePrimaryAATrigger`/`handleTrigger` for each: [5](#0-4) 

Each trigger execution can itself fan out into secondary/chained AA calls, each requiring additional DB round-trips and oscript evaluation, further extending the time the write lock stays held: [6](#0-5) 

There is no bound on how many triggers can be queued for a single MCI (`aa_triggers` table has no cap), and `main_chain.js`'s `handleAATriggers()` (the MC-stability step that populates the queue) inserts one row per (unit, AA address) pair for every AA-addressed output in the newly-stable MCI: [7](#0-6) 

This is directly analogous to the reported issue: just as the rollup batcher immediately and sequentially processes each withdrawal, blocking all other batching work until it finishes, `ocore`'s writer sequentially and synchronously drains the entire AA-trigger backlog for a stabilized MCI while holding the single global write lock, blocking every other unit (from any user, anywhere on the network) from being validated/written until the backlog clears.

### Impact Explanation
Every call into `writer.saveJoint` — whether for units received from peers, from the wallet, or from AA composer bounces — must acquire the same `"write"` mutex. While that mutex is held processing a large/expensive trigger backlog, the node cannot commit any other unit. Because AA trigger execution and MC stabilization are deterministic and run identically on every full node upon reaching the same MCI, an attacker can cause this stall network-wide (every full node hits the same expensive trigger backlog at the same point), not just on one victim node. This matches the accepted impact category "a network unable to confirm new units" and can also cause "AA fund loss or freezing" for any AA whose response depends on completing another concurrent operation while units cannot be committed.

### Likelihood Explanation
The attack requires only unprivileged unit-posting capability: an attacker sends payments to one or more AA addresses (their own, or any AA with a cheap trigger acceptance path) such that many AA triggers become due in the same MCI, and/or crafts AAs with deep secondary-trigger chains to maximize per-trigger processing cost. Posting units and triggering AAs is a normal, low-cost, permissionless action, making the precondition easy to reach; only the amount of AA logic/chaining needed to make the stall material requires some engineering effort.

### Recommendation
- Decouple AA trigger execution from the global write lock: release the `"write"` mutex before running `aa_composer.handleAATriggers()`, using a separate mechanism (e.g., the existing `['aa_triggers']` mutex alone) to serialize trigger execution without blocking unrelated unit writes.
- Bound the amount of trigger work performed synchronously per stabilization step (e.g., cap the number of triggers/secondary calls processed before yielding), or process trigger backlogs asynchronously in the background.
- Document/enforce limits on AA trigger fan-out (max secondary AA chain depth/breadth per MCI) to bound worst-case processing time for a single stabilization event.

### Proof of Concept
1. Deploy (or reuse) AA definitions that call several secondary AAs in a chain (as exercised in `test/aa_composer.test.js`'s "chain of AAs" test), maximizing per-trigger execution cost. [8](#0-7) 
2. From an unprivileged wallet, submit a burst of low-value payment units to these AA addresses so that many triggers become due in the same MCI as it stabilizes.
3. When the MCI stabilizes, `main_chain.js` inserts one `aa_triggers` row per unit/address pair, and `writer.saveJoint` calls `aa_composer.handleAATriggers()` while still holding the global `"write"` mutex. [9](#0-8) 
4. Because `handleAATriggers` processes the backlog strictly sequentially (`async.eachSeries`) and each entry can spawn secondary triggers, the `"write"` lock remains held for the entire duration, during which no other unit (from any peer or local wallet) can be validated/saved on that node — and, since the same logic runs deterministically on every full node, the same stall occurs everywhere the MCI stabilizes.

	function handleAATriggers() {
		// a single unit can send to several AA addresses
		// a single unit can have multiple outputs to the same AA address, even in the same asset
		const mci_column = mci >= constants.pemCurvesFixMci ? 'aa_addresses.mci' : 'aa_definition_units.main_chain_index';
		conn.query(
			"SELECT DISTINCT address, definition, units.unit, units.level \n\
			FROM units \n\
			CROSS JOIN outputs USING(unit) \n\
			CROSS JOIN aa_addresses USING(address) \n\
			LEFT JOIN assets ON asset=assets.unit \n\
			CROSS JOIN units AS aa_definition_units ON aa_addresses.unit=aa_definition_units.unit \n\
			WHERE units.main_chain_index = ? AND units.sequence = 'good' AND (outputs.asset IS NULL OR is_private=0) \n\
				AND NOT EXISTS (SELECT 1 FROM unit_authors CROSS JOIN aa_addresses USING(address) WHERE unit_authors.unit=units.unit) \n\
				AND " + mci_column + "<=? \n\
			ORDER BY units.level, units.unit, address", // deterministic order
			[mci, mci],
			function (rows) {
				count_aa_triggers = rows.length;
				if (rows.length === 0)
					return finishMarkMcIndexStable();

					return "("+mci+", "+conn.escape(row.unit)+", "+conn.escape(row.address)+")";
				});
