## Finding: Uncaught exception / crash in `chash.js` on malformed c-hash strings reaching `isChashValid` without character-set pre-filtering

### Title
Unhandled exception (DoS) in `chash.isChashValid` via length-mismatched decode of an attacker-supplied address/chash string - (File: `chash.js`)

### Summary
`chash.isChashValid()` decodes an attacker-controlled string with `base32.decode()` (160-bit case) or `Buffer.from(str,'base64')` (288-bit case) and then unconditionally calls `separateIntoCleanDataAndChecksum(binChash)`, which `throw`s a plain `Error` if the resulting bit length is not exactly 160 or 288. That `throw` is **outside** the only `try/catch` in the function (which wraps just the decode call), so any caller that reaches `isChashValid` with a string whose decoded length differs from the expected size crashes with an uncaught exception instead of returning `false`.

### Finding Description [1](#0-0) 

```
function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48) throw Error(...);
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){ console.log(e); return false; }
	var binChash = buffer2bin(chash);
	var separated = separateIntoCleanDataAndChecksum(binChash);   // <-- can throw, NOT caught
	...
}
```

`separateIntoCleanDataAndChecksum` throws whenever `bin.length` (i.e. `decoded_buffer_length * 8`) is not 160 or 288: [2](#0-1) 

`Buffer.from(str, 'base64')` in Node.js silently skips characters that are not part of the base64 alphabet rather than throwing, so a 48-character string containing non-base64 characters decodes to fewer than 36 bytes. This produces a bit length that is neither 160 nor 288, hitting the uncaught `throw` path.

The generic wrapper `isValidChash(str, len)` only checks the string length, not its character set, before calling `isChashValid`: [3](#0-2) 

```
function isValidChash(str, len){ return (isStringOfLength(str, len) && chash.isChashValid(str)); }
function isValidAddressAnyCase(address){ return isValidChash(address, 32); }
function isValidAddress(address){ return (typeof address === "string" && /^[A-Z2-7]{32}$/.test(address) && isValidChash(address, 32)); }
```

Only `isValidAddress` (used for the primary 32-char/160-bit address check in `validation.js` at author-address validation, `arrAuthorAddresses.every(isValidAddress)`) applies a strict base32 charset regex before calling `isValidChash`, which prevents malformed base32 input in that specific call. However, `isValidAddressAnyCase` and any other caller that validates 288-bit chashes (48-character strings, decoded with the lenient `Buffer.from(..., 'base64')`) do **not** apply an equivalent charset restriction, so a crafted 48-character string that is mostly valid base64 but contains a few invalid characters can reach the unguarded `throw` in `separateIntoCleanDataAndChecksum`.

`isChashValid`/`isValidChash` is referenced widely across unit- and message-processing code (`validation.js`, `definition.js`, `aa_validation.js`, `wallet.js`, `network.js`, `light.js`, etc.), so a value that flows into one of these 288-bit chash checks without prior charset filtering (e.g., a definer/asset/attestor identifier, a definition-hash field, or a chash validated via `isValidAddressAnyCase`) can trigger the crash.

Any uncaught exception thrown during unit/joint processing on a full node is fatal: `network.js` installs a global `uncaughtException` handler that logs it and then **re-throws it to intentionally crash the process**: [4](#0-3) 

### Impact Explanation
An uncaught exception anywhere in the synchronous validation call chain of a broadcast unit causes the whole node process to crash (the codebase explicitly re-throws inside `uncaughtException` "to avoid ending up in an inconsistent state"). Any unprivileged peer/unit poster who can get a crafted string (of the right length, 48 characters for the 288-bit variant, or 32 characters bypassing the base32 charset gate for the any-case address check) into a 288-bit/`isValidAddressAnyCase`-style chash validation can crash any node that processes/validates that unit or message — a network-wide denial-of-service against nodes trying to confirm new units, matching the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Medium. Reaching `isValidAddress` itself (the most commonly used check, on author addresses in `validation.js`) is blocked by the preceding `/^[A-Z2-7]{32}$/` regex, so the most obvious path is not exploitable. However, other reachable code paths use `isValidChash`/`isChashValid` directly or via `isValidAddressAnyCase` for 288-bit hashes (definitions, attestor/definer identifiers, etc.) without an equivalent charset pre-filter, and `Buffer.from(str,'base64')`'s lenient handling of invalid characters is a well-known, easily-triggered Node.js behavior. Confirming exactly which caller passes fully unrestricted attacker input into the 288-bit or any-case path requires further code tracing that could not be completed within the available exploration.

### Recommendation
- In `chash.js`, wrap the entire body of `isChashValid` (not just the decode step) in the `try/catch`, and have `separateIntoCleanDataAndChecksum`/`mixChecksumIntoCleanData` return an error indicator instead of throwing on unexpected lengths, so malformed input safely resolves to `false`.
- Restrict `Buffer.from(encoded, 'base64')` decoding to strict base64 (validate the input against `/^[A-Za-z0-9+/]{48}$/` or use a strict-mode base64 decode) before calling it, mirroring the regex guard already used by `isValidAddress`.
- Apply the same charset validation to every caller of `isValidChash`/`isChashValid`, including `isValidAddressAnyCase`.

### Proof of Concept
1. Construct a 48-character string that is otherwise valid base64 alphabet but does not decode to exactly 36 bytes when Node silently drops invalid characters (e.g., include characters outside `[A-Za-z0-9+/=]` so `Buffer.from(str,'base64')` returns a buffer shorter than 36 bytes).
2. Get that string into any code path that calls `isValidChash(str, 48)` / `chash.isChashValid(str)` directly, or into a 32-character value validated via `isValidAddressAnyCase` (which skips the `[A-Z2-7]` charset regex) with characters outside that set that base32-decode without throwing but with a mismatched bit length.
3. `chash.isChashValid` decodes it, computes a `binChash` whose length is not 160/288, and calls `separateIntoCleanDataAndChecksum`, which throws an uncaught `Error("bad length=...")`.
4. This exception propagates out of the synchronous validation call chain and is caught by the global `process.on('uncaughtException', ...)` handler in `network.js`, which re-throws and crashes the node process — a remotely triggerable DoS from a single unprivileged unit/message.

*Note: full confirmation of the exact production call site that passes unfiltered 288-bit/any-case input from an unprivileged unit poster into `isChashValid` was not completed due to tool-call limits; this should be verified with a live Devin session tracing all callers of `isValidChash`, `isValidAddressAnyCase`, and `chash.isChashValid` for missing charset pre-validation.*
