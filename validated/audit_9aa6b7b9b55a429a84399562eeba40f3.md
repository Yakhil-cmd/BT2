Analyzing this against the CVE's use-after-free/out-of-sequence-freeing bug class, I found an analog in the pruned-content recovery path for spending outputs of locally stripped `final-bad` units.

### Title
Stale in-memory cached pruned-output data can be used after its TTL-based "free" (expiry), enabling inconsistent validation of inputs spending stripped final-bad outputs - (File: archiving.js)

### Summary
When a locally pruned (content-stripped) `final-bad` unit's output is referenced as an input by a newly posted unit, `validatePaymentInputsAndOutputs` in `validation.js` relies on an in-memory cache (`assocCachedPrunedJoints`) populated by `archiving.cachePrunedJoint()` to recover the output's `address`/`amount`/`denomination`/`asset`, since these columns were deleted from the DB during pruning. [1](#0-0) [2](#0-1) 

### Finding Description
The cache entry is time-bounded and unconditionally freed by a periodic sweep independent of whether any pending unit still needs it: [3](#0-2) 

The comment in `archiving.js` explicitly documents this is meant "for a while after pruning ... to recover from spends that raced the pruning locally," acknowledging the race is expected but bounding it only by a fixed 1-hour TTL rather than by actual completion of any dependent validation: [4](#0-3) 

An unprivileged unit poster can trigger this by submitting a payment whose input spends the output of a unit that is locally pruned and `final-bad`. If the cache entry has expired (freed) by the time this input is validated - e.g. because the joint was queued/retried, was received from a slow/rerequested peer path via `assocUnitsWaitingForPrunedContent`, or simply because more than the TTL window elapsed between pruning and (re)validation - `getCachedOutput()` returns `null`: [5](#0-4) 

In that case validation falls back to `ifNeedParentUnits` with `bRequestPrunedContent: true`, re-requesting content from peers and holding the joint in `assocUnitsWaitingForPrunedContent`/rocksdb rather than deterministically rejecting or accepting it: [1](#0-0) [6](#0-5) 

Because the recovered data now depends on which peer happens to respond and when, and on whether the local cache still happened to hold the data at validation time, two nodes validating the same input at different times (one before, one after the TTL-based free) can reach different validation outcomes for the same unit — one accepting the recovered `address`/`amount` from a stale cache hit, another re-deriving it later from a possibly different peer-supplied joint (`tryRecoverPrunedContentOfFinalBadUnit`) that is only checked for `allHashesAreValid`, not cross-checked against the original archived content: [7](#0-6) 

This is the "use-after-free"/out-of-order-resource-freeing analog: a resource (the full joint content backing the stripped output) is freed by TTL expiry independent of the consumers (pending validations) that still hold a logical reference to it, and consumers can end up using either the freed (missing) or a re-populated-from-untrusted-source version, leading to non-deterministic validation results across nodes/timing.

### Impact Explanation
If different nodes accept different `address`/`amount` values for the same spent output (or one accepts while another can't resolve it and stalls), this can cause node disagreement on unit validity for units spending final-bad-pruned outputs, which the rules classify as consensus-relevant impact (node disagreement on validity/stability).

### Likelihood Explanation
This requires a fairly narrow precondition: a final-bad unit that has been locally pruned (content stripped, i.e. old enough to be below `getMinRetrievableMci()`), and an unspent-looking output. Reaching this window and successfully racing the TTL from a single posted unit is complex, mirroring the CVSS AC:H characterization of the underlying CVE analog.

### Recommendation
Do not rely on a fixed TTL to free `assocCachedPrunedJoints` entries while dependent validations may still be pending; instead track and clear entries based on completion of any joints in `assocUnitsWaitingForPrunedContent` and re-validate any recovered content against `archived_joints`/original content hash before trusting `address`/`amount`, ensuring consistent, deterministic recovery regardless of timing.

### Proof of Concept
1. Locally prune a `final-bad` unit `U` past `min_retrievable_mci` so its `outputs.address` is stripped (per `storage.js` `updateMinRetrievableMciAfterStabilizingMci`, which calls `archiving.cachePrunedJoint(objJoint)`). [8](#0-7) 
2. Post a unit `V` whose input spends `U`'s stripped output before the 1-hour TTL expires — validation succeeds using the cached data path in `validation.js`.
3. Wait past `PRUNED_JOINT_CACHE_TTL_ms` (or trigger `purgeExpiredCachedPrunedJoints`) so the cache entry is freed, and resubmit an equivalent unit `V'` spending the same output on a different/lagging node that hasn't cached it — it instead falls into `ifNeedParentUnits`/`bRequestPrunedContent` and depends on peer-supplied recovery via `tryRecoverPrunedContentOfFinalBadUnit`, producing a different code path/outcome from step 2 for logically the same input data.

```javascript
// in-memory holdover of joints we just voided (stripped final-bad units), so that for a while after pruning
// we can still serve their full content to peers and recover from spends that raced the pruning locally
const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}
```

```javascript
// looks up a specific output within a cached pruned joint, in the same shape as the outputs table columns we lost to stripping
function getCachedOutput(unit, message_index, output_index){
	const objJoint = getCachedPrunedJoint(unit);
	if (!objJoint)
		return null;
	const message = objJoint.unit.messages && objJoint.unit.messages[message_index];
	if (!message || message.app !== 'payment' || !message.payload)
		return null;
	const output = message.payload.outputs && message.payload.outputs[output_index];
	if (!output)
		return null;
	return {
		address: output.address,
		amount: output.amount,
		denomination: message.payload.denomination || 1,
		asset: message.payload.asset || null
	};
}
```
