## Title
Webhook signature is authenticated against `repository.owner.login`/`organization.login`, but the repository whose stacks are written to is resolved from the independent `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-App deployments, Shipit binds webhook signature verification to one JSON field (`repository.owner.login` / `organization.login`) while every webhook handler resolves the target repository/stack from a *different*, independently-controlled JSON field (`repository.full_name`). This mirrors the report's root cause: two logically related values (which token authorizes the payload vs. which resource the payload actually mutates) are validated with divergent logic instead of one consistent check, letting the "unchecked" field drive privileged writes.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using the organization derived from the payload itself, not from any pre-established routing: [1](#0-0) [2](#0-1) 

Each `Shipit.github(organization: ...)` app carries its own `webhook_secret`, exactly as documented for multi-org setups: [3](#0-2) [4](#0-3) [5](#0-4) 

Once the signature check passes for organization X's secret, the raw parsed payload is dispatched to every registered handler, unmodified: [6](#0-5) 

But the handler base class — and every concrete handler (`PushHandler`, `OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`) — resolves which repository/stack to act on from `payload.dig('repository', 'full_name')`, a completely separate JSON key from the one used for signature routing: [7](#0-6) [8](#0-7) [9](#0-8) 

For `pull_request` events, `ReviewStackAdapter#create!` further takes the branch to provision straight from the attacker-controlled `pull_request.head.ref` and immediately queues it for provisioning: [10](#0-9) [11](#0-10) 

**The broken equality:** `organization authenticated by X-Hub-Signature == organization("repository.owner.login")` is treated as if it also implied `organization authenticated == organization owning "repository.full_name"`. Nothing in the controller or in `Handler#repository_name` cross-checks that the two fields refer to the same organization/repository. Any party who legitimately owns one configured GitHub App/org (and therefore knows that org's own `webhook_secret`, which they configured themselves) can POST directly to `/webhooks` with a forged JSON body where `repository.owner.login` = their own org (so the HMAC check passes with their own known secret) but `repository.full_name` = `"other-org/other-repo"` (so the handler acts on a completely different tenant's stacks).

### Impact Explanation
This breaks the cross-repository trust boundary the multi-org feature exists to enforce: one org's operator can drive `sync_github`, `archive!`, `unarchive!`, label-driven provision/deprovision, and — via `pull_request.opened`/`reopened` — creation and provisioning of a `ReviewStack` for an arbitrary branch on another organization's repository, all authenticated with credentials that were never issued for that repository. This matches the "cross-repository writes" / "unauthorized deploy" Critical impact class, since provisioning a review stack runs the target repository's `shipit.yml`-defined provisioning/deploy steps for an attacker-chosen branch.

### Likelihood Explanation
Requires only that the attacker be a legitimate administrator/operator of *any one* GitHub App/org configured on the shared Shipit instance in a multi-org configuration — they never need the victim org's `webhook_secret`, GitHub App private key, or any Shipit session/API token. Multi-org configuration is a documented, first-class Shipit feature, so this is a realistic deployment topology, not a theoretical one.

### Recommendation
After signature verification succeeds for organization X, require that `repository.full_name`'s owner (or `organization.login`) match X before any handler is invoked — i.e., verify the payload's authenticated organization and its acted-upon repository are the same entity, analogous to checking `msg.value` consistency in the referenced report. Reject the webhook (422) on mismatch instead of silently dispatching to handlers keyed off the unchecked field.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org example).
2. As the operator of `org-a` (who owns and knows `org-a`'s `webhook_secret`), craft a `pull_request` "opened" payload where `repository.owner.login = "org-a"` (or `organization.login = "org-a"`) but `repository.full_name = "org-b/victim-repo"`, and `pull_request.head.ref = "attacker-branch"`.
3. Compute `X-Hub-Signature` using `org-a`'s known `webhook_secret` over the raw body and POST to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and the signature validates successfully.
5. `OpenedHandler` resolves `Shipit::Repository.from_github_repo_name("org-b/victim-repo")` and calls `ReviewStackAdapter#create!`, provisioning a new stack on `org-b`'s repository for `attacker-branch` — despite the request never being authenticated against `org-b`'s app.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
