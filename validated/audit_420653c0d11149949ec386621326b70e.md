### Analysis

**Equality being tested:** `verify_blob_kzg_proof_batch(ok, [blob,blob], [C,C], [pi,pi], 2, s)` must equal `verify_blob_kzg_proof(ok0, blob,C,pi,s) && verify_blob_kzg_proof(ok1, blob,C,pi,s)`, i.e. `false && false` should stay `false`.

**Trace:** For `n == 2`, `verify_blob_kzg_proof_batch` recomputes `evaluation_challenges_fr[i]` and `ys_fr[i]` per index via `compute_challenge` and `evaluate_polynomial_in_evaluation_form` [1](#0-0) , then calls `verify_kzg_proof_batch`. There, `compute_r_powers_for_verify_kzg_proof_batch` hashes the domain string, `n`, and every commitment/z/y/proof byte (both copies) via `blst_sha256` + `hash_to_bls_field` to derive a single scalar `r`, then calls `compute_powers(r_powers_out, &r, n)` [2](#0-1) . `compute_powers` sets `r_powers[0] = 1`, `r_powers[1] = r` [3](#0-2) .

The aggregated pairing check is algebraically `e(\sum r^i Proof_i, X) == e(\sum r^i(C_i - y_i) + \sum r^i z_i Proof_i, G2)` [4](#0-3) , which is equivalent to `\sum_i r^i * e_i == 0` where `e_i` is the (nonzero, since the individual proof is invalid) discrepancy term for entry `i`. With duplicate identical invalid entries, `e_0 = e_1 = e ≠ 0`, so the combined sum is `e*(1+r)`. This vanishes only if `r = -1` in the BLS12-381 scalar field (order ≈ 2^255).

**Why this can't be exploited:** `r` is not attacker-chosen freely — it is the SHA-256-derived Fiat–Shamir output over the domain separator, `n`, and the full byte-serialization of both (identical) commitments/z/y/proofs [5](#0-4) . To make the batch accept, the attacker would need to find blob/commitment/proof bytes such that this hash output equals exactly `-1 mod r` — a preimage search over a ~253-bit space, which is computationally infeasible (not a deterministic bypass, not exploitable by simply duplicating an arbitrary invalid triple). This is the standard Schwartz–Zippel/Fiat–Shamir soundness argument underlying all KZG batch-verification schemes, not a defect specific to this implementation.

None of the existing guards (`bytes_to_bls_field`, `validate_kzg_g1` via `bytes_to_kzg_commitment`/`bytes_to_kzg_proof`, the `n==0`/`n==1` short-circuits) are what prevent this — the prevention comes from the negligible probability of `r = -1`, which holds regardless of duplication.

void compute_powers(fr_t *out, const fr_t *x, size_t n) {
    fr_t current_power = FR_ONE;
