### Title
Webhook signature verified against the payload's `repository.owner.login`, but the target stack is resolved from `repository.full_name` — cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate `X-Hub-Signature` based on a value read out of the *untrusted* JSON body (`repository.owner.login`, falling back to `organization.login`), while `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolves the actual repository/stack that gets acted upon from a *different* field in the same untrusted body (`repository.full_name`). These two fields are never checked for consistency, so the "organization that authenticated" the request and the "repository that is written to" can be made to diverge.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — both attacker-controlled JSON fields inside the raw POST body. This value is used only to pick *which* per-organization `webhook_secret` (`Shipit.github(organization: repository_owner)`) is used to compute the HMAC comparison, per `lib/shipit/github_app.rb`'s `verify_webhook_signature`: [3](#0-2) 

Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`): [4](#0-3) 

Once the signature check passes, the event is dispatched to handlers, e.g. `PushHandler`, which resolves the target `Repository`/`Stack` from a **different** payload field — `repository.full_name` — via the base `Handler` class: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used for signature/secret selection) and `repository.full_name` (used for target-stack resolution) are two independent, attacker-controlled strings inside the same signed body, an attacker who legitimately knows the `webhook_secret` for **their own** organization (Org A — e.g. because they administer Org A's GitHub App/webhook config, a normal, unprivileged capability relative to Shipit itself) can craft a payload where:
- `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")`'s `webhook_secret` is used for verification, which the attacker knows and can correctly HMAC-sign), and
- `repository.full_name = "org-b/some-target-repo"` (a repository/stack belonging to a completely different, unrelated organization the attacker has no access to).

`OpenSSL::HMAC.hexdigest` is computed over the exact raw POST body the attacker controls, using Org A's secret, so `verify_webhook_signature` returns `true`. The dispatch loop then calls `PushHandler.call(params)`, which looks up `Repository.from_github_repo_name("org-b/some-target-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` — a stack that belongs to Org B, an organization/webhook the attacker was never authenticated against.

This breaks the equality that should hold: `organization authenticated by signature == organization owning the repository/stack acted upon`. Before the attack, only Org B's own webhook (using Org B's secret) can trigger syncs/state changes on Org B's stacks. After the forged request, Org A's credentials are sufficient to drive Org B's stack state.

### Impact Explanation
`GithubSyncJob` (triggered via `stack.sync_github`) fetches commits from GitHub for the target repo, persists them (`stack.commits.create_from_github!`), can lock reverted commits, and triggers `CacheDeploySpecJob`, i.e., it mutates the deploy pipeline state of a stack the attacker does not own or have permission to touch, using only a webhook credential for a different, unrelated organization. Other handlers dispatched through the same `verify_signature` gate (`MembershipHandler`, `StatusHandler`, `check_suite`, `pull_request` handlers, `commit_status`) are equally reachable and similarly key their target objects off body fields (`sha`, `organization.login` for teams, etc.) independent from the field used to pick the verifying secret, so the same organization/repository mismatch generalizes to team membership changes and commit status creation on foreign repositories/stacks. This is a cross-organization write achieved without any credential belonging to the victim organization, matching the "cross-repository writes" high-impact criterion.

### Likelihood Explanation
Exploitability requires only that Shipit be configured for multiple independent GitHub organizations (the documented and supported multi-org config shown in `config/secrets.development.shopify.yml`) and that the attacker legitimately controls the webhook secret for at least one of those organizations (an ordinary, unprivileged administrative capability for their own org, not a Shipit credential). No Shipit session, `ApiClient` token, or GitHub App private key is needed — only knowledge of one org's `webhook_secret`, which the attacker is expected to know as the owner of that org's GitHub App/webhook config. This is a realistic multi-tenant deployment scenario for Shipit.

### Recommendation
Bind the verified organization to the acted-upon repository/stack: after (or as part of) signature verification, re-derive the organization that owns the target repository (e.g., from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and require it to match the organization whose secret validated the signature, rejecting the webhook (422) on mismatch. Alternatively, verify the signature using the secret associated with `repository.full_name`'s actual owning organization rather than the payload-supplied `repository.owner.login`/`organization.login`.

### Proof of Concept
1. Shipit is configured with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `secrets.yml` schema in `config/secrets.development.shopify.yml`).
2. Attacker administers `org-a`'s GitHub App and thus knows `org-a`'s `webhook_secret`. Attacker has no access to `org-b`.
3. Attacker builds a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "org-a" },
       "full_name": "org-b/target-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org-a_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, calls `Shipit.github(organization: "org-a").verify_webhook_signature(...)`, which succeeds because the attacker signed with the correct secret for `org-a`.
6. `PushHandler#process` runs, using `Handler#repository_name` = `"org-b/target-repo"`, looks up that `Repository`'s stacks, and calls `stack.sync_github(expected_head_sha: ...)`, mutating `org-b`'s stack state — despite the attacker never having been authenticated against `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
