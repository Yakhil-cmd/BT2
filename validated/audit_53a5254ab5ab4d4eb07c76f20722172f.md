### Title
`StatusHandler` writes commit statuses without scoping to the webhook's authenticated repository, allowing cross-repository CI-status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook delivery only at the *organization* granularity: it selects the `Shipit.github(organization: repository_owner)` app config and checks the HMAC signature against that org's `webhook_secret`. Every other handler that writes state (`PushHandler`, `PullRequest::*Handler`) additionally scopes its writes to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, i.e. the same repository that was authenticated. `StatusHandler`, however, ignores the `repository` field entirely and updates **any** `Commit` row in the whole Shipit database whose `sha` matches the payload, regardless of which stack/repository/organization that commit belongs to.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from the payload and picks the matching GitHub App config to check `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

This proves the request truly originated from GitHub for the identified *organization/repository*, and the base `Handler` class exposes a `stacks`/`repository_name` helper meant to scope subsequent database writes to that same repository: [3](#0-2) 

`PushHandler` correctly uses this scoping (`stacks.not_archived.where(branch:)...`): [4](#0-3) 

`StatusHandler`, by contrast, never calls `repository_name`/`stacks` at all — it looks up commits globally by `sha` across the entire installation: [5](#0-4) 

The binding that is broken is: **organization authenticated by `verify_signature` (via `repository_owner`) ≠ the repository/stack whose `Commit` row is actually mutated by `StatusHandler`**. Because SHA-1 commit hashes are content-addressed, the same commit SHA can legitimately exist under multiple repositories tracked by the same Shipit instance (forks, mirrors, subtree-shared history, or a commit cherry-picked/copied verbatim into another repo). Anyone able to trigger a legitimate, correctly-signed `status` webhook for *their own* repository/organization (e.g. a repo maintainer posting a commit status via the GitHub API on a repository they control, which is entirely unprivileged with respect to Shipit) can cause `Commit.where(sha: params.sha)` to match — and overwrite the status of — a commit belonging to a completely different stack/repository that they have no access to.

### Impact Explanation
`Commit#add_status` (triggered from `create_status_from_github!`) directly feeds `Status::Group`, `Commit#blocked?`, `Commit#deployable?`, and `stack.schedule_merges`: [6](#0-5) [7](#0-6) 

CI/CD gating (`blocking_statuses`, `required_statuses`, continuous deployment, and the merge queue) all key off of `Commit#status`/`Commit#deployable?`. Forging a `success` status on a commit belonging to a stack the attacker doesn't otherwise control can unblock continuous deployment or the merge queue for that unrelated repository, producing an **unauthorized deploy/merge** — matching the "High"/"Critical" impact criteria (escalation past a repository's own CI gating without any legitimate access to that repository). This is a genuine cross-tenant break of the trust boundary the signature check is meant to establish (organization/repository-level authentication), not merely a theoretical/best-practice gap.

### Likelihood Explanation
Exploitability depends on being able to produce two repositories tracked by the same Shipit instance that share at least one commit SHA (fork of a tracked repo, subtree-synced repo, or a repo whose history was copied/rebased from the target). In any Shipit deployment used for open-source or internal multi-team monorepo/fork workflows, this is a realistic and low-effort condition to engineer — an attacker only needs write access to any repository that shares history with the victim's tracked repository and the ability to post (or trigger CI to post) a commit status via the normal GitHub `status` webhook, both of which are actions available to an ordinary, unprivileged GitHub user/CI system with no access to the victim stack, Shipit session, or webhook secret of the victim organization.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries `Commit`/`Stack` by content rather than by the authenticated repository) to the repository identified in the webhook payload, mirroring `PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This requires the GitHub `status` payload's `repository.full_name` to be validated against the commit's own `stack.repository`, closing the cross-repository write.

### Proof of Concept
1. Shipit instance tracks `stack A` for repository `victim-org/app` (branch `main`), with `Commit#sha = X` present (e.g. a shared upstream commit).
2. Attacker forks `victim-org/app` into `attacker-org/app-fork` (or otherwise has write access to some *other* repository that shares commit `X`, e.g. via mirroring/subtree). The GitHub App used by this Shipit instance is also installed on `attacker-org` (a normal, unprivileged tenant onboarding scenario).
3. Attacker (or their own CI) POSTs a commit status for SHA `X` to GitHub against `attacker-org/app-fork` with `state: success`, `context: <required-status-context-of-victim-stack>`.
4. GitHub delivers a `status` webhook to Shipit, correctly signed with `attacker-org`'s own `webhook_secret`. `WebhooksController#verify_signature` passes because `repository_owner == "attacker-org"` and the signature matches.
5. `StatusHandler#process` runs `Commit.where(sha: "X")`, which matches the `Commit` row belonging to `stack A` under `victim-org/app`, and calls `commit.create_status_from_github!(params)`, marking that commit's required status as `success` in `victim-org`'s stack.
6. If `stack A` has continuous deployment enabled or the merge queue depends on that status/context, this forged success unblocks/triggers a deploy or merge on `victim-org/app` that the attacker had no authorization to influence.
