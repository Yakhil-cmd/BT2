## Title
Instant commission update retroactively re-prices already-earned but unredeemed epoch rewards - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

## Summary
This is the same "retroactively apply new rate to past accrual" bug class as the Super DCA `setMintRate()` issue: a privileged party (there, the DCA "manager"; here, the vote account's authorized withdrawer) can change a rate/commission that governs the split of already-accrued, but not-yet-settled rewards, without first "flushing" the prior interval at the old rate. In agave, when the `delay_commission_updates` feature (SIMD‑0249) is **not** active, `redeem_delegation_rewards()` reads the vote account's *current, live* commission value and applies it to the *entire* epoch's already-earned credits, instead of the commission that was in effect when those credits were earned.

## Finding Description
`redeem_delegation_rewards()` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` computes the commission to apply to a whole epoch's worth of already-earned stake credits at reward-redemption time (epoch boundary), not incrementally as credits are earned: [1](#0-0) 

When `delay_commission_updates` is `false`, the code falls straight to the `else` branch and reads `vote_state.commission()` / `vote_state.inflation_rewards_commission()` from the **live, current** vote account state — the exact value in effect at the moment the epoch-boundary reward redemption runs — rather than a value snapshotted from before the credits were earned.

The vote account's authorized withdrawer can change this commission at any point via a single signed transaction, `VoteInstruction::UpdateCommission`, whose only restriction (when the delay feature is off) is a first-half-of-epoch check for *increases*: [2](#0-1) [3](#0-2) 

This mirrors exactly the DCA `setMintRate()` root cause: `mintRate = newMintRate` overwrote the rate before `_updateRewardIndex()` flushed rewards for the elapsed interval at the old rate. Here, `set_commission()` overwrites the commission before the epoch's already-earned credits (`stake.credits_observed` .. `vote_state.credits`) are redeemed at the old commission — the withdrawer sets a low commission early in the epoch (satisfying the "first half" rule for increases, and decreases are unrestricted at any time), lets credits/points accrue at that displayed rate, then raises commission just before the epoch boundary (still legal, if still first half) or the vote-credit-weighted calculation simply uses whatever commission is live at redemption. The credits that were earned in the interval **before** the change are still split at the **new** rate, exactly like the DCA "past interval priced at new rate" bug.

Note that the codebase's own design comments confirm this was recognized as a real problem and was the reason `delay_commission_updates` (SIMD‑0249) was introduced — to force at least a full epoch of delay before a commission value affects reward redemption: [4](#0-3) [5](#0-4) 

The `if delay_commission_updates { … } else { vote_state.commission() … }` fallback path (lines 709–724 above) is the residual, non-delayed code path that still exists in the current codebase for when the feature is inactive.

## Impact Explanation
When `delay_commission_updates` is inactive, an authorized withdrawer can retroactively re-price already-earned inflation rewards for their own delegated stakers by changing commission shortly before the epoch boundary. This lets a validator operator (analogous to the "malicious manager" in the referenced report) reduce delegators' rewards or inflate their own commission on credits that were already earned under a previously-advertised (lower) rate — a stake/reward corruption of exactly the kind called out in the Validate section ("stake or reward corruption"). This is reachable purely by submitting a normal, signed `UpdateCommission` transaction from the vote account's authorized withdrawer — no leader, snapshot, or operator-only privilege is required beyond being the vote account's normal signing authority, which fits the "unprivileged transaction sender" criterion in the same sense the DCA "manager" role does.

## Likelihood Explanation
This is gated behind the `delay_commission_updates` feature flag being inactive. As a mainnet-track feature (SIMD-0249, already merged and expected to be broadly activated on production clusters), the exploitable window is limited to networks/test clusters/private forks where the feature has not yet been activated — the code path, however, is unconditionally present and reachable whenever that is the case, and the fallback branch is not dead code (it's exercised by `test_calculate_stake_vote_rewards_new_vote_account` with `delay_commission_updates: false`, confirming the behavior is intentionally supported for backward compatibility rather than removed): [6](#0-5) 

## Recommendation
Remove (or make permanently mandatory) the non-delayed commission path once `delay_commission_updates` is active on all supported clusters, so that `redeem_delegation_rewards()` can no longer fall back to reading the live `vote_state.commission()` for reward redemption. Until then, treat clusters/forks running without `delay_commission_updates` active as vulnerable to commission changes retroactively re-pricing already-accrued epoch rewards, consistent with the intent of SIMD-0249.

## Proof of Concept
1. Deploy/observe a cluster (or local test validator / private fork) where `delay_commission_updates` (SIMD-0249) has not been activated — confirmed via `deactivate_features(&mut genesis_config, &vec![delay_commission_updates::id()])`, mirroring the test setup at `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1984-1986`.
2. A validator's vote account authorized withdrawer sets a low commission (e.g. 1%) at the start of an epoch. Delegated stakers see the advertised low commission and their stake continues earning credits throughout the epoch.
3. Before the epoch boundary (still within the "first half" window permitted by `is_commission_update_allowed`, `programs/vote/src/vote_state/mod.rs:995-1009`), the withdrawer submits `VoteInstruction::UpdateCommission` raising commission to a high value (e.g. 90%), or on a `commission_rate_in_basis_points`-enabled vote-v4 account with `delay_commission_updates` off in the reward-calc feature snapshot, uses live values with no timing restriction at all via `UpdateCommissionBps` should its feature gate combination allow it.
4. At epoch-boundary reward redemption, `redeem_delegation_rewards()` (lines 703-724) reads `vote_state.commission()`/`inflation_rewards_commission()` from the **current** vote state (the just-raised 90%) and applies it to the **entire** epoch's earned credits, not just credits earned after the change.
5. Result: stakers who earned credits under the advertised 1% commission are paid out as if 90% commission applied for the whole epoch — an unsigned, unilateral misallocation of already-accrued rewards, analogous to the DCA PoC where 1000 seconds accrued at rate 10/sec were minted at rate 1000/sec instead.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}
