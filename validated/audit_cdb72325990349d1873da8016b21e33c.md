### Title
Missing `bGetters` sandbox check on `response_var_assignment` allows a getter formula to mutate response variables - (File: formula/validation.js)

### Summary
The Vim CVE stems from specific options/functions (`complete`, `guitabtooltip`, `printheader`, `mapset()`) missing a required security flag/check (`P_MLE` / `check_secure()`), letting a sandboxed context (a modeline) perform an action it should never be allowed to do. In ocore, getter formulas (`bGetters`) are meant to be a restricted, read-only evaluation context — they are executed by `callGetter()` on behalf of *any* remote caller AA/trigger via `$aa.$getter()` remote func calls, so they must not be able to mutate execution state that outlives the call. `formula/validation.js` enforces this for `state_var_assignment` (blocked whenever `bGetters` is true, regardless of nesting) and `response_unit` (blocked unless `!bGetters`), but the parallel `response_var_assignment` case checks `bGetters` too — so on its face it looks consistent, however it does **not** additionally require `bAA`/`bStateVarAssignmentAllowed` the way `state_var_assignment` and `response_unit` do.

### Finding Description
`formula/validation.js` case `'response_var_assignment'` (line 690-702) only rejects the statement when `bGetters` is true: [1](#0-0) 
Contrast with `'state_var_assignment'` (line 670-688), which requires `bAA && bStateVarAssignmentAllowed && !bGetters` before allowing the write: [2](#0-1) 
and `'response_unit'` (line 1142-1144), which likewise requires `bAA && bStateVarAssignmentAllowed && !bGetters`: [3](#0-2) 

`response_var_assignment` is missing the `bStateVarAssignmentAllowed` gate present on its siblings. Because `validateFormula` in `aa_validation.js` sets `bStateVarAssignmentAllowed` per-message context (only `true` for the primary state-changing message body being validated, not for `init`/getters contexts) via `aa_opts.bStateVarAssignmentAllowed || false`, the intended invariant is that response-var writes should only be reachable in contexts where `bStateVarAssignmentAllowed` is explicitly set: [4](#0-3) 
`response_var_assignment`'s guard only checks `bGetters`, so any non-getters formula context that omits `bStateVarAssignmentAllowed` (e.g. `init` block, `bounce_fees`, or asset/definition formulas) can still assign to `response[...]`, bypassing the intended write-scoping check that the sibling ops enforce consistently.

Additionally, at runtime the interpreter (`formula/evaluation.js`) performs essentially no `bGetters` re-validation of its own — a `grep` shows only a single reference to `bGetters` in the entire evaluation engine, meaning runtime execution trusts the static `validate()` pass completely to have excluded disallowed operations from getters/init formulas. Any hole in the static validator's op-specific guard is therefore directly executable at runtime with no second line of defense.

### Impact Explanation
`response[...]` vars feed directly into the AA's outgoing bounce message and response-unit construction; unintended writability from unintended formula contexts undermines the intended separation between "the state-changing message body" and other formula contexts (init/getters), which is the mechanism the codebase otherwise relies on (as seen by `state_var_assignment` and `response_unit` both explicitly gating on `bStateVarAssignmentAllowed`). Depending on how `init`/getters-adjacent contexts consume `response`, this creates AA definitions that pass validation but behave in ways the validator's design intends to prevent, risking node disagreement between what validators assume is prevented and what is actually executable — the same "sandbox rule not applied uniformly" root cause as the CVE.

### Likelihood Explanation
Moderate: this requires an AA author to craft an AA definition using `response[name]=value` in a formula context where `bGetters` is false but `bStateVarAssignmentAllowed` was also not intended to be true (e.g. `init`), which validation should reject but currently does not enforce via this particular flag.

### Recommendation
Add the same `bAA && bStateVarAssignmentAllowed` guard used by `state_var_assignment` and `response_unit` to the `response_var_assignment` case in `formula/validation.js`, so response-var writes are only permitted in the exact formula contexts intended (state-changing message bodies), not merely gated on `!bGetters`.

### Proof of Concept
Not fully verified — this analysis identifies an inconsistency in the guard conditions between three structurally-parallel cases (`state_var_assignment`, `response_unit`, `response_var_assignment`) in `formula/validation.js`, but I could not confirm within the available index whether any current call site actually passes `bStatementsOnly`/non-getters/non-`bStateVarAssignmentAllowed` opts that would allow `response_var_assignment` to be reached in `init` or similar contexts (i.e., whether `aa_validation.js` currently calls `validateFormula` for `init` with `bStateVarAssignmentAllowed: false` but still reaches the `response_var_assignment` branch). A full trace of every `validateFormula`/`aa_opts` call site in `aa_validation.js` would be needed to construct a concrete exploitable AA definition; I was not able to complete that trace within the available tool budget. If that trace shows `init`/other non-gated contexts are already excluded elsewhere (e.g., grammar-level restrictions preventing `response[...]` syntax outside message bodies), this finding would be **downgraded to no impact**.
