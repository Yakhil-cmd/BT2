### Title
`StatusHandler#process` writes CI status to any `Commit` matching a SHA without checking the reporting repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up `Commit` rows solely by `params.sha` and calls `commit.create_status_from_github!(params)` on every match, never verifying that the webhook's `repository.full_name` corresponds to the commit's own stack/repository. Since `Handler` exposes a `repository_name` helper (used by `PushHandler` and others) but `StatusHandler` never calls it, a status event delivered under one repository can mutate the CI state of a `Commit` belonging to a different repository/stack whenever the SHAs coincide.

### Finding Description
The broken binding is: `payload.dig('repository', 'full_name') == commit.stack.repository.full_name` must hold for the write to be legitimate, but `StatusHandler#process` never reads or checks `repository_name` at all: [1](#0-0)  compares only against `Commit.where(sha: params.sha)`.

`Handler` base class does provide a `repository_name`/`stacks` scoping helper that other handlers (e.g. `PushHandler`) use to restrict actions to the stacks belonging to the reporting repository: [2](#0-1)  and [3](#0-2) . `StatusHandler` skips this entirely and queries `Commit` globally by SHA, which is a cross-stack, cross-repository table.

`create_status_from_github!` then unconditionally writes a new `Status` row tied to that commit's actual stack: [4](#0-3) , and `add_status` recomputes `status`, fires `commit_status`/`deployable_status` hooks, and schedules merges/continuous delivery based on the new state: [5](#0-4) .

Signature verification (`WebhooksController#verify_signature`) only proves the payload was signed by the GitHub App/org named in `payload.dig('repository','owner','login')` — it authenticates *who sent the webhook*, not *which repository's commits may be affected*: [6](#0-5) . An attacker who controls their own GitHub org/app (registered in Shipit) can legitimately trigger a real, correctly-signed `status` webhook for their own repository. If that repository shares a commit SHA with a `Commit` row already present in some victim stack (trivially achievable by forking a public victim repo — forked commits keep identical SHAs — or by crafting an identical commit object), the shared-SHA lookup in `StatusHandler` will match and rewrite the victim's `Status`/CI state, with no repository-identity check anywhere in the path.

### Impact Explanation
This is a cross-repository/cross-tenant write: an attacker-controlled, correctly-authenticated webhook for repository A can flip the CI status of a `Commit` that actually belongs to stack/repository B. Consequences include: falsely marking a victim commit `success`, which can trigger `schedule_merges`/`ContinuousDeliveryJob` and downstream automatic deploys/merges (`Commit#schedule_continuous_delivery`, `Status#schedule_continuous_delivery`) [7](#0-6) [8](#0-7) , or firing `deployable_status`/`commit_status` hooks for the wrong repository. This matches the "payload for one repository mutating another's stack, commit ... or an unauthorized deploy" Critical category, and is repeatable against any victim commit whose SHA the attacker can reproduce (most easily via forking).

### Likelihood Explanation
Preconditions: the attacker needs a GitHub org/app already registered in Shipit (`Shipit.github(organization: ...)` must resolve to their credentials) so `verify_signature` passes for their own payload — this is a normal, low-cost setup for anyone with a Shipit-connected org, or exploitable if the victim's Shipit instance is multi-tenant across orgs. The SHA collision is achievable at negligible cost by forking a public victim repository, since forked commits retain identical SHAs. No victim secrets, sessions, or maintainer status are required, satisfying the "unprivileged attacker" constraint. The attack is repeatable per shared SHA and requires no timing tricks beyond triggering a status event on the forked SHA.

### Recommendation
In `StatusHandler#process`, restrict the `Commit` lookup to commits whose stack belongs to the reporting repository, mirroring the pattern used elsewhere in `Handler`:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.pluck(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the existing `repository_name`/`stacks` helper from `Handler`, so a status can only update commits belonging to stacks of the repository identified in the payload.

### Proof of Concept
Minitest plan (no live GitHub, uses `Handler.call` directly with a payload hash):
1. Create `victim_repo` (`full_name: 'victim/repo'`) with a `Stack` and a `Commit` with `sha: 'deadbeef...'`, state `pending`.
2. Create `attacker_repo` (`full_name: 'attacker/repo'`) with its own `Stack` but **no** commit with that SHA (simulating the attacker's fork having the shared-SHA commit only on GitHub, not yet imported into Shipit).
3. Build `payload = { 'sha' => victim_commit.sha, 'state' => 'success', 'context' => 'ci', 'repository' => { 'full_name' => 'attacker/repo' } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert the binding before: `payload.dig('repository','full_name') != victim_commit.stack.repository.full_name` (`'attacker/repo' != 'victim/repo'`).
6. Assert after the call: `victim_commit.reload.state == 'success'` — i.e., the victim commit's state changed despite the mismatched repository, proving the write crossed repository boundaries. A fixed implementation should leave `victim_commit.state` unchanged (`'pending'`/`'unknown'`) and instead create no `Status` row, since `attacker_repo`'s stacks do not include `victim_commit.stack`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
