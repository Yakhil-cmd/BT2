### Title
Webhook signature verification is bound to `repository.owner.login`, but every event handler dispatches on the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization whose webhook secret is used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`), but the handlers that act on the payload (`PushHandler`, pull-request handlers, etc.) resolve the target `Repository`/`Stack` from a *different* field, `repository.full_name`, which is never checked against the field used for signature verification. This is the same "checked one field, acted on another" class of bug as the ERC4626 report: `maxDeposit`/`maxMint` reflect state that `deposit`/`mint` don't actually honor. Here, the org that authenticates the request and the repository that is written to are two independent, unlinked fields of the same attacker-suppliable JSON body.

### Finding Description
`verify_signature` computes the org used to select the webhook secret purely from payload content: [1](#0-0) [2](#0-1) 

That resolved organization is used only to pick the `Shipit.github(organization:)` instance whose `verify_webhook_signature` validates the HMAC in `X-Hub-Signature`: [3](#0-2) 

Note also that `verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is configured for that organization - so any org onboarded to Shipit without a configured `webhook_secret` accepts any payload claiming to be from it.

Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, already-JSON-parsed payload to handlers: [4](#0-3) 

Every handler resolves the target repository/stack from `repository.full_name`, a completely separate JSON field from `repository.owner.login`: [5](#0-4) [6](#0-5) 

Nothing in the controller or in `Handler#stacks`/`Handler#repository_name` enforces that `repository.full_name` starts with the same organization login that was used to authenticate the request (`repository.owner.login`). For a legitimate GitHub-generated webhook these two fields are always consistent, but this engine never asserts that; it is purely convention, not verified. An attacker who controls their own GitHub organization (installs the Shipit-integrated GitHub App on their own org, a self-service action requiring no privileged access to the victim Shipit instance) knows that org's own `webhook_secret`, and can therefore produce a validly-signed webhook (`X-Hub-Signature` computed with their own secret) whose body sets:

- `repository.owner.login` = `attacker-org` (satisfies `verify_signature`)
- `repository.full_name` = `victim-org/victim-repo` (consumed by every handler to select the `Repository`/`Stack` to act on)

### Impact Explanation
This breaks the binding: `organization authenticated == repository written`. Concretely, for the `push` event, `PushHandler#process` looks up `stacks` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` and, for every non-archived stack on a matching branch, calls `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` for an attacker-chosen `stack_id`/`expected_head_sha` on a repository the attacker never authenticated for: [6](#0-5) [7](#0-6) 

The sync job itself fetches commits from GitHub using Shipit's own credentials for the victim repo (not attacker-controlled content), so this is not raw injection of malicious code, but it is an unauthorized ability to force resynchronization/commit-append and cache invalidation on a stack the attacker has no relationship to, and — where continuous deployment is enabled — this resync is the trigger that leads to an actual deploy being kicked off for the victim stack, i.e. an attacker-triggered deploy on infrastructure they don't own, satisfying the "unauthorized deploy" impact bar. The same pattern applies to the pull-request handlers (`OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`), which resolve `Repository.from_github_repo_name(params.repository.full_name)` independent of the org used for signature verification, allowing an attacker to trigger review-stack provisioning, archiving, or label-driven deploy/unblock actions against a victim's repository. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
Exploitation only requires the attacker to control a GitHub organization/repository that has installed the same Shipit-integrated GitHub App (or, for multi-org deployments, any org listed under `config/secrets.yml`'s `github` section) so they legitimately know that org's `webhook_secret`, and to send a crafted, correctly-signed webhook with a mismatched `repository.full_name`. This requires no Shipit session, no `ApiClient` token, and no access to the victim's GitHub credentials — only the ability to receive/send GitHub webhook traffic for one's own org, which is attacker-controlled infrastructure. The multi-org support explicitly documented in `docs/setup.md` (`Using Multiple Github Applications`) increases the realistic likelihood, since a single Shipit instance may track repositories across many organizations, each with independently known webhook secrets, while cross-checking between owner and full_name is never performed anywhere in the dispatch path.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after resolving `repository_owner` for signature verification, assert that it matches the organization/owner segment of `repository.full_name` before dispatching to handlers, rejecting (422) any payload where these two fields diverge. Additionally, treat a missing `webhook_secret` for a configured organization as a hard failure rather than an automatic pass in `GithubApp#verify_webhook_signature`.

### Proof of Concept
1. Attacker creates GitHub organization `attacker-org` and installs the same GitHub App that the target Shipit instance is configured to trust for `attacker-org` (a normal self-service GitHub App installation, requiring no access to the victim Shipit instance).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs this exact raw body with the HMAC-SHA1 `webhook_secret` known to them for `attacker-org` and sends it to `POST /webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and successfully verifies the signature since the attacker used the correct secret for that org.
5. `PushHandler#process` (dispatched with the full unverified payload) resolves the target via `Repository.from_github_repo_name('victim-org/victim-repo')`, unrelated to `attacker-org`, and enqueues `GithubSyncJob` for the victim's stack(s), forcing a resync (and, with continuous delivery enabled, an unauthorized deploy) on a repository the attacker never authenticated for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
