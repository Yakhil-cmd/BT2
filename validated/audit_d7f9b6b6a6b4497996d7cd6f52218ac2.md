Found the exact binding break. The webhook signature verification selects which GitHub App/organization's `webhook_secret` to check against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` — a field that is **not covered by the HMAC signature scope decision itself** (the signature only proves the payload came from *some* GitHub org holding that org's secret, but the org used to pick the secret is attacker-influenced input). More importantly, the actual repository that webhook handlers act on (`Handler#repository_name` → `payload.dig('repository', 'full_name')`) is a **separate field from the same payload**, never cross-checked against `repository_owner` or against which stack/org the verified secret belongs to.

### Title
Webhook signature verification authenticates the payload's declared organization but not the repository the handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` to validate the HMAC against using `repository_owner`, itself read straight from the unauthenticated JSON body (`repository.owner.login`, or `organization.login`). [1](#0-0) [2](#0-1) . Once the HMAC check passes for *that* org's configured secret, `create` hands the entire raw payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Every handler then determines the repository/stack to mutate from a *different* field of the same payload, `payload.dig('repository', 'full_name')` [4](#0-3) , which is never compared to `repository_owner`.

### Finding Description
This is the direct analog of the reported bug class: `mockRequestRandom()` emitted results and called `_handleRandom()` using attacker/owner-controlled inputs without re-validating them against the invariant enforced on the "real" path (`processedRequests`). Here, the webhook "real path" invariant is: *the signature must authenticate the same organization whose repository is being mutated*. That invariant is never enforced — `repository_owner` (used to select the secret) and `repository.full_name` (used to select the target `Stack`/`Repository`) are read independently from the same untrusted JSON body and are never required to be consistent.

Concretely:
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org has no `webhook_secret` configured: `return true unless webhook_secret` [5](#0-4) . Multiple documented/sample configs ship with `webhook_secret: # nil` for one or more configured organizations [6](#0-5) .
- If an attacker sets `repository.owner.login` (or `organization.login`) to an organization configured in `Shipit.github_organizations` that has **no** `webhook_secret`, `verify_signature` will select that org's `GitHubApp` and `verify_webhook_signature` returns `true` regardless of the actual `X-Hub-Signature` header value [7](#0-6) .
- The request then proceeds to `create`, and `payload.dig('repository', 'full_name')` — a completely independent field the attacker also controls — is used to resolve the target `Repository`/`Stack` via `Repository.from_github_repo_name(repository_name)` [4](#0-3) , which can point at *any* stack tracked by the Shipit instance, including ones belonging to organizations that *do* have a properly configured secret.

The binding broken is: `organization authenticated by signature == organization/repository actually written by handlers`. Before the fix this equality is never asserted; the code trusts two unrelated attacker-supplied fields from the same unauthenticated body to independently pick "which secret to check" and "which repository to mutate."

### Impact Explanation
This allows cross-repository/cross-stack writes: e.g., a `push` event forged with `repository.owner.login` set to an org lacking a secret but `repository.full_name` pointed at a fully-configured, unrelated tracked stack causes `PushHandler#process` to call `stack.sync_github(expected_head_sha: ...)` for that stack [8](#0-7) , or a forged `status`/`check_suite` event can flip commit statuses and unblock/trigger deploys for a stack the attacker has no legitimate signing credential for. This matches the report's "Critical" tier: cross-repository writes / unauthorized effect on deploy state, achieved purely by an unprivileged network attacker with no session, token, or GitHub write access — only knowledge that some configured org lacks a webhook secret (visible in this repo's own example configs).

### Likelihood Explanation
Requires only that the Shipit deployment has at least one configured GitHub organization without a `webhook_secret` (a documented/example configuration state, not a hardening requirement enforced by the code) and that the target stack's repository is tracked by the instance. No authentication token, session, or GitHub write access is needed — only the ability to send an unauthenticated HTTP POST to `/webhooks`.

### Recommendation
- Require every configured GitHub organization/app to have a non-blank `webhook_secret`; refuse to boot or reject webhooks for orgs with a blank secret instead of treating it as "always verified."
- After signature verification, explicitly assert that `repository.owner.login` (or `organization.login`) used to select the verifying secret matches the owner implied by `repository.full_name` used by the handler, rejecting the request (422) on mismatch.
- Consider passing the verified organization context explicitly into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization) }` so handlers can enforce the binding rather than re-deriving repository identity independently.

### Proof of Concept
1. Configure (or find deployed) `Shipit.github_organizations` containing an org, e.g. `someothergithuborg`, with `webhook_secret: nil` (as shown in `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml`).
2. Craft a POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or a garbage one), and JSON body:
```json
{
  "organization": { "login": "someothergithuborg" },
  "repository": { "owner": { "login": "someothergithuborg" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to be reachable>"
}
```
3. `verify_signature` resolves `github_app = Shipit.github(organization: "someothergithuborg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (invalid) signature header.
4. `create` calls `PushHandler.call(params)`, which resolves the target via `payload.dig('repository', 'full_name') == "victim-org/victim-repo"`, unrelated to the "verified" org, and triggers `stack.sync_github` on the victim's tracked stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
