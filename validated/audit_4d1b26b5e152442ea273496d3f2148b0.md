### Title
Status webhooks write `Status` rows for commits in unrelated stacks because `StatusHandler#process` never scopes by repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by SHA alone across the entire `Commit` table and calls `create_status_from_github!` on every match, without ever restricting to the stacks belonging to the reporting repository (`payload.dig('repository','full_name')`). By contrast, `CheckSuiteHandler#process` correctly scopes through `Handler#stacks`, which resolves stacks via `Repository.from_github_repo_name(repository_name)` before touching any commit. Any GitHub repository the attacker controls can therefore emit a legitimately-signed `status` event whose SHA happens to also exist in a victim's stack, and Shipit will attach that (attacker-controlled) status to the victim's commit.

### Finding Description
The binding that should hold is: **the set of commits a `status` webhook is allowed to mutate == `Repository.from_github_repo_name(payload.dig('repository','full_name')).stacks.commits`** (this is exactly what `Handler#stacks` computes at [1](#0-0) , and what `CheckSuiteHandler#process` uses at [2](#0-1) ).

`StatusHandler#process` never calls `stacks` and instead does: [3](#0-2) 
This queries `Commit.where(sha: params.sha)` unscoped by repository, i.e. across every stack/repository ever indexed by Shipit, and calls `commit.create_status_from_github!(params)` for each match, which writes to `Status` via `add_status`/`statuses.replicate_from_github!` at [4](#0-3)  and can trigger `Hook.emit`, deployability recalculation, and `stack.schedule_merges` at [5](#0-4) .

`verify_signature` in `WebhooksController` only proves that the payload was signed with the GitHub App secret for `repository_owner` (`params.dig('repository','owner','login')`) — it authenticates *that some repository under that owner sent this event*, not that the `sha`/repository named in the payload belongs to the reporting repository, and it does nothing to scope commit lookups to that repository: [6](#0-5) . So a legitimately-signed `status` event from the attacker's own repository (which the attacker fully controls, e.g. via `POST /repos/:owner/:repo/statuses/:sha` on GitHub) is accepted, and `StatusHandler` never checks that `sha` belongs to that repository's stacks — only that some commit with that SHA exists anywhere in Shipit's database. Since git SHA1s are content-derived, an attacker who mirrors/forks a victim's public commit (or otherwise causes a SHA collision, e.g. shared upstream history, cherry-picks, common base commits) into their own repo can reference that exact SHA in a real GitHub status event from their own repo, and Shipit will write attacker-controlled status data (`state`, `description`, `target_url`, `context`) onto the victim stack's commit, potentially flipping `deployable?`/`blocked?` and unblocking `schedule_merges` continuous delivery for the victim stack.

### Impact Explanation
This is a cross-tenant integrity violation: an attacker with control of an arbitrary repository can inject `Status` rows (attacker-chosen `state`, `context`, `target_url`, `description`) onto a victim's commit, which participates in deploy-gating logic (`deployable?`, `blocked?`, `schedule_merges`, continuous delivery). This can be used to force a victim stack's commit to appear "green" (success) and trigger an unauthorized deploy/continuous-delivery run, or to spam a victim's commit with fake failing statuses to block their releases. It matches the "Critical" category: a payload authenticated for one repository mutates another repository's stack/commit state. The attack is repeatable against any commit SHA the attacker can reproduce or that coincidentally overlaps (e.g. shared upstream commits, submodule commits, cherry-picks common in monorepo/fork ecosystems), and requires no privileges on the victim's Shipit stack or GitHub repo.

### Likelihood Explanation
Preconditions: attacker needs a repository whose owner/org has the Shipit GitHub App installed (so `verify_signature` succeeds for that owner) — this is typically true for any repo under an org already using Shipit, or any public repo depending on how the GitHub App is scoped. The attacker also needs a commit SHA that also exists in some victim stack's commit table; this is achievable for common scenarios (forked/upstream shared commits, vendored/cherry-picked commits, monorepo cross-references) though not for arbitrary chosen victim commits without a genuine SHA1 collision. Given SHA reuse across related repos is common in practice (shared git history, subtree/cherry-pick workflows), this is a realistic, low-cost, and repeatable attack once such an overlapping SHA exists.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler#process` does: resolve the reporting repository via `stacks` (i.e., `Repository.from_github_repo_name(repository_name)&.stacks`) and only look up/mutate commits belonging to those stacks, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, instead of querying the global `Commit` relation.

### Proof of Concept
Minitest plan (mirrors the described control/violation comparison):
1. Create two `Repository`/`Stack` fixtures: `stack_a` (owned by "attacker/repo") and `stack_b` (owned by "victim/repo").
2. Create a `Commit` on `stack_b` with a fixed `sha` (e.g. `"deadbeef" * 5`).
3. Build a `check_suite` webhook payload naming `attacker/repo` with `head_sha` equal to the victim commit's SHA and `head_branch` matching `stack_a`'s branch; call `CheckSuiteHandler.call(payload)` and assert the victim commit's `check_runs`/refresh job was **not** scheduled (control passes — scoped correctly).
4. Build a `status` webhook payload naming `attacker/repo` with `sha` equal to the same victim commit's SHA and an attacker-chosen `state`; call `StatusHandler.call(payload)`.
5. Assert `stack_b`'s commit now has a `Status` record created from the attacker's payload (`commit.statuses.reload.first.state == params.state`) — proving the violation: `StatusHandler` wrote to a commit in a stack whose repository (`victim/repo`) never authenticated the request (only `attacker/repo`'s signature was verified).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

        "unknown_organization=#{e.message}",

      ].join(' '))
    end
