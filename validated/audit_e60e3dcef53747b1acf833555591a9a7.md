### Title
Webhook Signature Verification Is Scoped to an Attacker-Controlled `repository.owner.login`/`organization.login` Field, Decoupled From the `repository.full_name` That Handlers Actually Act On - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to use for HMAC verification based on a field taken directly from the unauthenticated JSON body (`repository.owner.login` or `organization.login`), while the handlers that actually mutate state (create statuses, enqueue sync jobs, etc.) key off `repository.full_name` from that same, attacker-supplied body. These two fields are never cross-checked, and if any configured organization has no `webhook_secret` set, verification for that organization is a no-op — so an unprivileged, unauthenticated caller can post directly to the public `/webhooks` endpoint and have Shipit act as if a signed webhook arrived for a completely different, secret-protected organization's repository.

### Finding Description
`WebhooksController` picks the app used to verify the signature purely from JSON supplied in the request body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit's own documented multi-org setup explicitly shows `webhook_secret` left blank/`nil` as a normal, supported configuration state for one or more organizations: [4](#0-3) [5](#0-4) 

After `verify_signature` passes (either legitimately or via the no-secret bypass), `create` dispatches the entire raw JSON body to registered handlers: [6](#0-5) 

Those handlers (e.g. push, status, check_suite) look up the target `Stack`/`Repository` using `repository.full_name` — a field from the *same* unauthenticated JSON body, independent of the `repository.owner.login`/`organization.login` field used earlier to select the signing key. Nothing enforces that these two values refer to the same organization.

**The broken equality:** `organization whose webhook_secret authenticated the request` == `organization whose repository/stack data gets written`. An attacker who knows (or targets) an organization configured with `webhook_secret: nil` can set `repository.owner.login`/`organization.login` to that unprotected org (to pass/bypass `verify_signature`) while setting `repository.full_name` to point at an entirely different, real, secret-protected organization's stack. The forged payload is accepted and processed as if genuinely signed for that other organization's repository.

### Impact Explanation
This crosses the "unauthorized cross-repository write" bar: an external, completely unauthenticated attacker (no `ApiClient` token, no `api_clients_secret`, no GitHub App private key, no repository write access) can inject fabricated GitHub events — pushes, commit statuses, check runs — against any tracked stack, as long as the Shipit deployment has at least one organization configured without a `webhook_secret` (a state the project's own setup docs and fixtures treat as normal/supported). This can force spurious `GithubSyncJob`/`RefreshCheckRunsJob` runs, forge commit statuses that make otherwise-blocked commits appear `deployable?` (`Commit#deployable?`), and influence the merge queue (`ProcessMergeRequestsJob`) and continuous-deployment triggers — ultimately enabling an unauthorized deploy path for a repository the attacker never authenticated against. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
The precondition (at least one configured GitHub org/app with `webhook_secret` unset) is exactly what the shipped example/dummy configs and Shopify's own multi-org sample show as an accepted configuration, so it is plausible in real deployments (e.g. an org added for OAuth-only purposes, or one where the operator hasn't yet copied over the webhook secret). No credentials, session, or repository access are required by the attacker — only knowledge that such an organization exists in the target Shipit's config and the full_name of the victim stack's repository (both public information).

### Recommendation
- Verify the signature using the `webhook_secret` associated with the organization actually named in `repository.full_name` (or the repository record resolved from the DB), not a value taken unchecked from the same untrusted payload.
- Treat a missing/blank `webhook_secret` as "verification required but not configured" (reject/log) rather than "verification not required" — i.e., do not let `verify_webhook_signature` short-circuit to `true` when `webhook_secret` is blank.
- After signature verification, re-validate that the `repository.owner.login`/`organization.login` used to pick the app matches the owner implied by `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with two GitHub Apps configured: `OrgA` (no `webhook_secret` set) and `OrgB` (real `webhook_secret`, has a tracked stack `OrgB/victim-repo`).
2. POST directly to `/github/webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
No valid `X-Hub-Signature` for `OrgB` is required — `repository_owner` resolves to `OrgA`, whose `verify_webhook_signature` short-circuits to `true` because `OrgA` has no `webhook_secret`.
3. `WebhooksController#create` dispatches the payload to the push handler, which resolves the stack via `OrgB/victim-repo` and enqueues `GithubSyncJob` with the attacker-supplied SHA, exactly as if GitHub itself had sent a signed webhook for `OrgB`. [9](#0-8)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
