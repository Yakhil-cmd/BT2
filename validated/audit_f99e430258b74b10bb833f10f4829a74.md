### Title
`PATH` hijack of `bash script/release.sh` via fork-controlled `machine.environment` in `shipit.yml` - (File: `lib/shipit/command.rb`)

### Summary
`DeploySpec::FileSystem#load_config` reads `shipit.yml` from the checked-out working directory of the review-stack branch, which for a `ReviewStack` is the fork PR author's own branch content [1](#0-0) . `DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim, with no key filtering [2](#0-1) , and `TaskCommands#env` merges that hash into the environment passed to every `Command`, including deploy steps like `bash script/release.sh` [3](#0-2) . `Command#unbundled_env` builds a "safe" `PATH` and then overwrites it with any key present in `@env`, so an attacker-supplied `PATH` in `machine.environment` fully replaces the constructed `PATH` before `PTY.spawn` executes the shell.

### Finding Description
The broken binding: the code intends `PATH` used by `PTY.spawn` to always equal `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` (a host-controlled value), i.e. `unbundled_env['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` for every task run. In practice:

```ruby
def unbundled_env
  BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
end
``` [4](#0-3) 

The final `.merge(@env.stringify_keys)` means any key in `@env` — including `PATH` — overrides the safe value that was just constructed. `@env` is exactly the hash returned by `TaskCommands#env`, which merges `deploy_spec.machine_env` (fork-controlled) after the base variables and before `@task.env`:

```ruby
def env
  super
    .merge(@stack.env)
    .merge(...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)
end
``` [3](#0-2) 

`deploy_spec.machine_env` is `config('machine', 'environment') || {}`, read straight from the parsed YAML with no key allow-list [2](#0-1) . The config is loaded from the working directory checkout of the review-stack branch via `config_file_path` / `load_config`, i.e. the exact `shipit.yml` the PR author committed to their fork branch [1](#0-0) . Nothing in `EnvironmentVariables#permit` (only used for interpolation whitelisting of task variables, not `machine_env`) or elsewhere filters the `machine.environment` keys — the README even documents `machine.environment` as accepting arbitrary `key: val` pairs [5](#0-4) .

Exploit flow: an unprivileged user opens a PR from their fork whose branch's `shipit.yml` contains:
```yml
machine:
  environment:
    PATH: /tmp/evil:/usr/bin:/bin
deploy:
  override:
    - bash script/release.sh
```
When Shipit provisions/deploys the `ReviewStack` for that branch, `TaskCommands#env` merges this `PATH` into the command environment, `Command#unbundled_env` lets it override the safe `PATH`, and `PTY.spawn` runs `bash script/release.sh` with the attacker's `PATH` first. If the script (or bash itself, e.g. `sh`, `sed`, `cat`, or any bare command invoked inside `script/release.sh`) calls any unqualified binary name that the attacker has planted in `/tmp/evil`, that attacker binary executes on the Shipit deploy host with the privileges of the Shipit worker process.

### Impact Explanation
This is Remote Code Execution on the Shipit deploy host, matching the Critical "RCE via `Command`/`PTY.spawn`" category. Any repository owner or fork PR author with review stacks enabled for a repo can plant this in their own PR branch's `shipit.yml`, and it executes with the privileges of whatever principal runs the Shipit deploy worker (frequently possessing `GITHUB_TOKEN`s, deploy credentials, and access to other stacks' data on the same host) — so the blast radius extends beyond the single repository once code execution is achieved on the shared worker.

### Likelihood Explanation
Preconditions are minimal: review stacks must be enabled for the target repository, but no maintainer approval, secrets, or elevated GitHub role is required — an unprivileged fork PR author fully controls their own branch's `shipit.yml` (`machine.environment`) and any step content, including `bash script/release.sh`. This is a one-shot, repeatable technique (every deploy/task execution against the branch reruns the poisoned environment) and requires no interaction beyond opening/labeling a PR that Shipit ingests via its normal webhook flow.

### Recommendation
In `Command#unbundled_env`, exclude `PATH` (and other security-sensitive variables such as `LD_PRELOAD`, `BUNDLE_GEMFILE`, `RUBYOPT`) from being overridden by `@env`, or explicitly re-apply the safe `PATH` after merging `@env` so it cannot be shadowed:
```ruby
def unbundled_env
  BASE_ENV.merge(@env.stringify_keys).merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}")
end
```
Additionally, consider filtering `DeploySpec#machine_env` to reject reserved/dangerous key names so `shipit.yml` cannot set `PATH` at all.

### Proof of Concept
minitest (`test/unit/command_test.rb` style):
```ruby
test "#unbundled_env does not allow fork-controlled machine_env to override PATH" do
  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  command = Command.new('bash script/release.sh', env: { 'PATH' => '/tmp/evil' }, chdir: '.')

  # Binding under test: PATH used to spawn the subprocess must always equal the host-controlled safe_path,
  # regardless of attacker-supplied env.
  assert_equal safe_path, command.unbundled_env['PATH']
  refute_equal '/tmp/evil', command.unbundled_env['PATH']
end
```
Running this against current code fails: `command.unbundled_env['PATH']` equals `/tmp/evil`, proving the `PATH` hijack — the fork-controlled `machine.environment` entry silently overrides the intended safe `PATH` used by `PTY.spawn`.
