### Title
Session Fixation in GitHub OAuth Callback Allows Session/Account Takeover - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
The Rio report's root cause is that a value is trusted for the remainder of a lifecycle (a withdrawal claim) without re-binding it to the state that exists at the time it is actually consumed — the shares-owed snapshot never gets reconciled with the yield that accrues afterward. The structurally identical binding failure in Shipit is between the **session identifier** issued to a browser and the **GitHub identity** that gets attached to it during OAuth completion: `GithubAuthenticationController#callback` writes `session[:user_id]` into whatever session ID is currently present, without first rotating/resetting it, so a session ID fixed by an attacker before authentication remains valid and privileged after the victim authenticates through it.

### Finding Description
`GithubAuthenticationController#callback` handles the return leg of the GitHub OAuth flow: [1](#0-0) 

It never calls `reset_session` (or otherwise rotates the session ID) before assigning `session[:user_id] = sign_in_github(auth)`. Compare this to `logout`, which explicitly calls `reset_session`: [2](#0-1) 

`Authentication#find_current_user` subsequently trusts `session[:user_id]` alone to resolve `current_user`, with no secondary binding (e.g., to a token, device fingerprint, or IP) tying the session cookie to the identity that completed the OAuth handshake: [3](#0-2) 

Because the session ID itself is never rotated at the authentication boundary, the binding that should hold — *"the session ID an attacker can fix" ≠ "the session ID trusted after a GitHub identity is bound to it"* — collapses to equality. This is precisely the "GitHub identity versus the `User` bound to the session" binding class: whoever controls the session ID before OAuth completes controls it after, regardless of whose GitHub identity actually completed the flow.

### Impact Explanation
This directly matches the explicitly in-scope High-impact category "session fixation / forced OAuth completion." An unprivileged attacker who can fix a victim's session cookie (e.g., via a subdomain cookie-scoping issue, a response-splitting/cookie-injection vector, or simply sharing a link to a session ID obtained through a public/shared computer or proxy) and then induce the victim to complete the GitHub OAuth login (`/github/auth`) will find that the attacker's original session now resolves to the victim's authenticated `User` — granting the attacker full access to the victim's Shipit account, including whatever deploy/stack/team privileges that `User` holds, without ever knowing the victim's GitHub credentials.

### Likelihood Explanation
Exploitation only requires the attacker to fix a session ID in the victim's browser and get the victim to click through OAuth once — no repository write access, no `ApiClient` token, no `webhook_secret`, and no privileged account are needed. Since the engine's session cookie handling and `reset_session` are entirely within `app/controllers/**`, and the flaw is a straightforward omission (no session ID rotation on privilege elevation), this is a concrete, reachable, low-complexity path to unauthorized access.

### Recommendation
Call `reset_session` (or explicitly force session ID regeneration, e.g. `request.session_options[:renew] = true`) in `GithubAuthenticationController#callback` immediately before assigning `session[:user_id]`, re-establishing any values (like `omniauth.origin`) needed after the reset. This ensures the session ID trusted post-authentication is never one that could have been fixed by an attacker pre-authentication.

### Proof of Concept
1. Attacker obtains/sets a known session ID `S` in the victim's browser (e.g., via a fixation vector such as a shared/kiosk browser, a subdomain that can set cookies for the parent domain, or a crafted link if the app ever accepts session IDs from the URL/headers).
2. Attacker sends the victim a link to `Shipit::Engine`'s GitHub OAuth login path while session `S` is already active in the victim's browser.
3. Victim completes the GitHub OAuth flow; `GithubAuthenticationController#callback` runs `session[:user_id] = sign_in_github(auth)` on session `S` without rotating it: [4](#0-3) 
4. Attacker, still holding session `S`, is now recognized as the victim's `User` by `Authentication#find_current_user`, gaining the victim's authenticated access to Shipit stacks/deploys without any credential of their own.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
