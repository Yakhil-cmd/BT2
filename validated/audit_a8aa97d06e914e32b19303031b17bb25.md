### Title
CCMenu API endpoint bypasses `ApiClient` stack-scoping, letting a stack-scoped token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via its `stack` association, and `Shipit::Api::BaseController` enforces that scope by resolving the requested stack through a scoped relation. `Shipit::Api::CCMenuController` overrides that resolution method and looks the stack up globally, unscoped, breaking the binding between "the stack a token authorizes" and "the stack the endpoint actually touches."

### Finding Description
`Shipit::Api::BaseController` defines the intended scoping mechanism: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a stack, and `stack` resolves `params[:stack_id]` only within that restricted relation. This is confirmed as the enforcement mechanism by the `StacksController` test suite: "an api client scoped to a stack will only see that one stack" [2](#0-1) , and "index returns a list of stacks filtered by repo and api client" showing a stack-scoped client (`here_come_the_walrus`, scoped to stack `shipit`) gets zero results for a different repo's stack [3](#0-2) .

`CCMenuController`, however, overrides `stack` and drops the scoping entirely: [4](#0-3) 

Permission enforcement (`require_permission :read, :stack`) only checks that the token carries the string permission `"read:stack"` — it never checks which specific stack the token is bound to: [5](#0-4) 

So the only place that was supposed to bind "this token → this one stack" for `CCMenuController` is the `stack` method, and that binding is exactly what got overridden with an unscoped `Stack.from_param!(params[:stack_id])`. This is a structural equivalent of the Babylon `RefundTx` bug: the entity that should be authorized/credited (`feeGranter` / "the specific stack the token is scoped to") is not the one actually checked (`feePayer` / "whatever `stack_id` the request specifies"), because the code only checks a coarse-grained field (fee payer / raw permission string) and ignores the finer-grained authorization binding (fee granter / `stack_id` scope) that the system relies on elsewhere.

The existing test suite for `CCMenuController` never exercises this path with a stack-scoped client against a foreign stack — it always requests the same stack the token was created for [6](#0-5) , so the gap is untested and unnoticed by CI.

### Impact Explanation
This lets the holder of a legitimately-issued, narrowly-scoped `read:stack` `ApiClient` token (e.g. a CCMenu client meant to expose only one project's status, as created by `CCMenuUrlController`) read build/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of any other stack in the Shipit instance, including stacks belonging to different repositories/teams that the token was never meant to access. This matches the High-severity category "escalation into `Shipit.github_teams` authorization, unauthenticated [w.r.t. that stack] read of stack state" since the token grants no authority over the target stack yet the endpoint discloses its state.

### Likelihood Explanation
Any party in possession of a stack-scoped `read:stack` token (a routine, low-privilege credential intentionally minted to be narrow, e.g. shared with a third-party CI dashboard) can trivially exploit this by varying the `stack_id` request parameter — no additional privilege, session, or secret is required beyond the token they were already handed for a single, specific stack.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reintroduce the `stacks`-based scoping) so it resolves `params[:stack_id]` through the same `current_api_client`-scoped relation used by `BaseController`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and delete the now-redundant private `stack` method that calls `Stack.from_param!` directly.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id: <stack A's id>` with permission `read:stack` (the intended, minimal-privilege pattern used by `CCMenuUrlController`).
2. Using that client's `authentication_token`, call `GET /api/{owner}/{repo-for-stack-B}/ccmenu.xml?token=<token>` (or with Basic Auth) supplying `stack_id` for stack B, a stack the token was never scoped to.
3. `CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` with no scoping check, `require_permission :read, :stack` only checks the string permission is present, and the response renders stack B's build status — despite the token only being authorized for stack A.
