### Title
Arbiter contract offer accepts an `arbiter_address` equal to one of the contracting parties, allowing self-arbitration and unilateral theft of escrowed funds - (File: wallet.js, arbiter_contract.js)

### Summary
`ERC721SeaDrop` lets the deploying party self-appoint the "administrator" role, which is nominally meant to be a neutral operator (the marketplace), and then use that self-control to bypass the fee protection that the role was supposed to enforce. The analogous weakness in ocore's arbiter-contract escrow feature is that the `arbiter_address` — the role meant to be a neutral, disinterested third party who decides fund disputes — is never validated to be different from `my_address`/`peer_address` (the two contracting counterparties themselves). This allows one counterparty to name **itself** as arbiter, then unilaterally resolve any dispute in its own favor and drain the mutually-funded shared address, without the actual counterparty's cooperation.

### Finding Description
When an arbiter contract offer is created and sent (`createAndSend`, `arbiter_contract.js` lines 21-36) or received (`case 'arbiter_contract_offer'`, `wallet.js` lines 617-654), the only address validation performed is that `my_address`, `peer_address`, and `arbiter_address` are each syntactically valid addresses: [1](#0-0) 
There is no check anywhere in this handler, in `store` (`arbiter_contract.js` lines 91-116), or in `createAndSend` that `arbiter_address` differs from `my_address` or `peer_address`. [2](#0-1) [3](#0-2) 

The shared (escrow) address definition, built in `deriveSharedAddress`, encodes an `"or"` of four ways to unlock the funds. Two of these branches let either the offeror or the acceptor alone spend the funds, gated only by a data feed posted **by the `arbiter_address`** declaring that party the winner: [4](#0-3) 

If `arbiter_address` is set to `offeror_address` (or `acceptor_address`), the "neutral arbiter" data-feed condition collapses into a self-signed condition: the dishonest party can post the `"CONTRACT_" + hash = <own address>"` data feed themselves (since they *are* the address authorized to post it) and unilaterally satisfy the branch `["address", offeror_address] AND ["in data feed", [[arbiter_address], ...]]` where `arbiter_address == offeror_address`. This lets them claim the escrowed funds without any real dispute resolution and without the honest counterparty's second signature.

This mirrors the SeaDrop root cause precisely: a role intended to act as an independent check on one party (marketplace admin / arbiter) is not prevented from being controlled by that same party, defeating the entire trust model the role exists to enforce.

### Impact Explanation
An unprivileged wallet user (the "offeror" who creates and sends the arbiter contract offer, exactly the reachable "private-payment counterparty" role) can craft a contract offer where `arbiter_address` equals their own `my_address`. If the honest peer (an ordinary, unprivileged user) accepts the offer without independently verifying that the arbiter is a genuinely independent party — which the protocol does nothing to enforce or flag — they fund the resulting shared address believing a neutral arbiter can adjudicate a dispute. The self-appointed "arbiter" can then post a self-authored data feed naming themselves the winner and drain the shared address's funds via the `["in data feed", [[arbiter_address], "CONTRACT_"+hash, "=", ...]]` branch of the address definition, resulting in concrete unauthorized spending / fund loss for the honest counterparty in a private/escrow payment.

### Likelihood Explanation
The condition requires the honest peer to accept a contract offer without checking that the proposed arbiter is not one of the parties themselves. Since arbiter selection is presented as ordinary address input with no automated or protocol-level safeguard (no equality check against `my_address`/`peer_address`), any careless or socially-engineered acceptance directly leads to exploitation. This is analogous to the original report's own caveat that in practice a marketplace/wallet UI could filter out such contracts, but the protocol-level code itself performs no such check, so the vulnerability is real and only mitigated by discretionary application-layer diligence, matching the same "off-chain trust decision" caveat noted in the original SeaDrop report.

### Recommendation
- In `wallet.js` (`case 'arbiter_contract_offer'`) and `arbiter_contract.js` (`createAndSend`), reject any contract offer where `arbiter_address === my_address` or `arbiter_address === peer_address`.
- Consider requiring `arbiter_address` to belong to a registered/known arbstore (verified via `arbiters.getArbstoreInfo`) at offer-creation and offer-acceptance time, rather than trusting an arbitrary caller-supplied address.
- Surface a clear warning/refusal in the wallet UI when a proposed arbiter matches either contracting party's address.

### Proof of Concept
1. Attacker (Alice) is the "offeror" and wants to enter an arbiter-mediated deal with victim Bob (payee/payer of `contract.amount`).
2. Alice calls `createAndSend` with `objContract.arbiter_address = objContract.my_address` (her own address) — no validation in `createAndSend` (`arbiter_contract.js:21-36`) or in `store`/the `arbiter_contract_offer` handler (`wallet.js:617-654`) rejects this.
3. Bob's wallet receives and accepts the offer via `arbiter_contract_response`; nothing in that path (`wallet.js:865-940`) checks that arbiter ≠ either party either.
4. `deriveSharedAddress` (`arbiter_contract.js:454-575`) builds the shared address definition with the vulnerable branch `["and", [["address", offeror_address], ["in data feed", [[arbiter_address], "CONTRACT_"+hash, "=", offeror_address]]]]`, where `arbiter_address == offeror_address == Alice`.
5. Bob funds the shared address per the normal `pay` flow (`arbiter_contract.js:692-717`).
6. Alice, acting as her own "arbiter", posts a `data_feed` message from her own address setting `CONTRACT_<hash> = <her address>`.
7. Alice's `["address", offeror_address] AND ["in data feed", ...]` branch is now satisfied entirely by her own signature and her own self-posted data feed — she spends the full escrowed amount from the shared address without Bob's cooperation, and without any real dispute resolution having occurred.
