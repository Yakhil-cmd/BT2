### Title
Zero-amount order match still charges trading fee, allowing an attacker to repeatedly drain a resting order's fee balance - ([File: test/samples/order_book_exchange.oscript])

### Summary
The order-matching AA in `order_book_exchange.oscript` computes trade sizes from user-supplied signed order data and only rejects a match if the computed amounts *exceed* limits, never requiring them to be positive. An attacker can post a self-signed order with `sell_amount = 0`, which makes every guard condition trivially true (comparisons against zero always pass), match it against a victim's still-open resting order, and thereby trigger the fee-deduction state message with `$amount_left1 = $buy_amount1 = 0`. No actual value is exchanged, but the flat `$fee = 1000` is still deducted from the victim's `base` balance on every such call, and because the trade size is zero the victim's remaining order amount (`$amount_left2`) is never decremented and the order is never marked `executed`, so it stays available for repeated re-matching. This closely mirrors the reported `buy_state_rebalance` bug: an instruction whose data is not validated to actually produce an effect still charges a fee, and the slippage/soundness check (`from_usd_value` vs `to_usd_value` — here, `amount_left1` vs `sell_key` balances) trivially passes when both sides are zero, enabling unbounded repeated draining.

### Finding Description
In the "execute orders" branch of the AA: [1](#0-0) 
`$amount_left1` and `$amount_left2` default to the order's own declared `sell_amount` (`otherwise $order1.sell_amount`), which is part of the user's self-signed order data and is not required to be positive. All subsequent guards are one-sided inequality checks (`>`), which are satisfied vacuously when the left-hand value is `0`:
- `$amount_left1 > var[$sell_key1]` → `0 > x` is false, passes for any non-negative balance.
- `$buy_amount1 = round($amount_left1 * $order1.price)` → `0` when `$amount_left1 = 0`.
- `$buy_amount1 > $amount_left2` → `0 > x` false, passes.
- `$expected_buy_amount2 = round($buy_amount1 * $order2.price)` → `0`.
- `$expected_buy_amount2 > $amount_left1` → `0 > 0` false, passes.

Because there is no requirement that `$amount_left1 > 0` (or that any of the traded amounts be strictly positive), the "match" check returns `true` for a completely no-op trade, exactly analogous to how the Solana program's slippage check `mul_div(from_usd_value, ...) > to_usd_value` trivially holds when `from_usd_value` is `0`.

The state-update message then unconditionally applies a flat fee to both parties regardless of whether any real value was exchanged: [2](#0-1) 
`var[$sell_key1]`, `var[$sell_key2]`, `var[$buy_key1]`, `var[$buy_key2]` all change by `0`, but `var[$base_key1]` and `var[$base_key2]` are each reduced by `$fee = 1000`. Crucially, `$new_amount_left2 = $amount_left2 - $buy_amount1 = $amount_left2 - 0` leaves the victim's order fully intact and *not* marked as `executed`, so the same resting order (`$id2`) can be matched again and again.

`$id1` is derived from `trigger.data.order1.last_ball_unit`, which the attacker fully controls and can vary on every trigger unit, so the attacker can mint an unlimited stream of fresh, validly self-signed, zero-`sell_amount` orders and repeatedly re-trigger the AA against the same victim resting order, deducting `1000` from `var[$base_key2]` (the victim's fee balance) on each call until it is exhausted (further attempts bounce once negative, per the `if (var[$base_key1] < 0 OR var[$base_key2] < 0) bounce(...)` guard, so the drain is bounded by the victim's current fee balance but is otherwise fully repeatable at will).

### Impact Explanation
This is a direct AA fund-loss vulnerability: a counterparty who never intends a real trade can force fee charges against a passive order-book participant's stored `base` balance inside the AA, draining it entirely without the victim's consent and without providing any of the value (asset exchange) the fee is nominally paid for. This matches the "Accept only concrete ... AA fund loss" criterion — funds legitimately deposited by a user into the AA's internal balance ledger can be siphoned away by an unprivileged trigger sender.

### Likelihood Explanation
Trivial and cheap to execute: the attacker only needs to sign one order of their own (any two of their own addresses, or one attacker address plus a targeted victim's outstanding order id, which is discoverable from any prior order-posting unit/data message) with `sell_amount: 0`, and post a trigger unit referencing it plus the victim's `order2` package. This can be repeated unit after unit at minimal AA bounce-fee cost, with no need to control the victim's keys, browser, wallet, or any privileged role.

### Recommendation
Require strictly positive trade sizes before allowing a match to proceed and before charging any fee, e.g. add an explicit check such as `if ($amount_left1 <= 0 OR $buy_amount1 <= 0) return false;` in the matching condition, and only deduct `$fee` when a nonzero amount is actually transferred between the two balance keys. More generally, any AA/oscript logic that charges a fee tied to an operation's magnitude must validate that the computed magnitude is nonzero (or otherwise bound the check to strictly-positive comparisons) rather than relying on one-directional `>` checks that are vacuously satisfied at zero.

### Proof of Concept
1. Victim posts (or has previously posted via a signed `order2` package) a resting sell order for `sell_asset=A`, `buy_asset=B`, with `sell_amount = N > 0`, tracked under `var['amount_left_' || $id2] = N` (or default `N` from the order itself) and funded via `var[$sell_key2] >= N`.
2. Attacker crafts and signs an `order1` package for one of their own addresses with `sell_asset = B`, `buy_asset = A`, `sell_amount = 0`, `price` arbitrary, referencing a fresh `last_ball_unit` so `$id1` is new each time.
3. Attacker sends a trigger unit with `trigger.data = { order1: <signed order1>, order2: <victim's signed order2> }`.
4. The AA evaluates all guard conditions as `true` (since `$amount_left1 = 0` and `$buy_amount1 = 0` satisfy every `>` check vacuously), executes the state message: no asset balances move, but `var[$base_key2]` (victim) and `var[$base_key1]` (attacker) are each reduced by `1000`; `$new_amount_left2 = N - 0 = N`, so the victim's order remains fully open and unmarked as executed.
5. Attacker repeats steps 2–4 with new `order1` packages (new `last_ball_unit` ⇒ new `$id1`) against the same victim `order2`, each time deducting another `1000` from the victim's `var[$base_key2]` balance, until it reaches `0` (further attempts then bounce due to the negative-balance guard).
