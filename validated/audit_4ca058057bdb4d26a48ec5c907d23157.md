### Title
Fee-on-Transfer Token Accounting Mismatch Drains Counterpart Bridge Liquidity — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom`, then unconditionally emits `RequestValueTransfer` with the caller-supplied `_value`. For any registered fee-on-transfer ERC20 token, the bridge receives fewer tokens than `_value + _feeLimit`, yet the event records the full `_value`. Bridge operators on the counterpart chain observe the event and call `handleERC20Transfer(_value)`, releasing the full `_value` from the counterpart bridge's reserves — more than was ever deposited on the source side.

---

### Finding Description

In `requestERC20Transfer`:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit)); // (1)
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);     // (2)
}
```

Step (1) pulls `_value + _feeLimit` from the caller. For a fee-on-transfer token, the bridge actually receives `(_value + _feeLimit) × (1 − fee_rate)`.

Step (2) calls `_requestERC20Transfer`, which emits:

```solidity
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,        // ← original caller-supplied amount, not actual received amount
    requestNonce, fee, _extraData
);
```

The counterpart bridge's operators observe this event and call `handleERC20Transfer(..., _value, ...)`, which executes:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);   // releases full _value
```

The counterpart bridge releases `_value` tokens even though the source bridge only received `_value × (1 − fee_rate)` (after fee deduction). The deficit `_value × fee_rate` is extracted from the counterpart bridge's existing liquidity pool on every such transfer.

The same flaw exists in the `onERC20Received` (1-step) path: the token contract calls `onERC20Received(from, to, _value, _feeLimit, extraData)` with the original `_value`, and `_requestERC20Transfer` again emits that unchecked value.

---

### Impact Explanation

Each cross-chain transfer of a fee-on-transfer token causes the counterpart bridge to release `_value` tokens while the source bridge only holds `_value × (1 − fee_rate)`. The shortfall is permanently extracted from the counterpart bridge's liquidity. Repeated transfers drain the counterpart bridge's entire ERC20 reserve for that token, constituting an unauthorized transfer of bridged assets.

---

### Likelihood Explanation

Token registration is `onlyOwner`, so the precondition is that the bridge owner registers a fee-on-transfer ERC20 token. This is a realistic scenario: many production tokens (deflationary tokens, tokens with protocol fees) implement fee-on-transfer. Once such a token is registered — even inadvertently — any unprivileged user calling `requestERC20Transfer` triggers the accounting mismatch on every call. No further privilege is required after registration.

---

### Recommendation

In `requestERC20Transfer`, measure the actual balance increase and use that as the canonical transfer amount:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived == _value.add(_feeLimit), "fee-on-transfer token not supported");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Alternatively, compute `_value` from `actualReceived - _feeLimit` and pass that adjusted value to `_requestERC20Transfer`.

### Proof of Concept

1. Bridge owner registers a fee-on-transfer ERC20 token `T` (1% transfer fee) on both source and counterpart bridges.
2. Attacker calls `requestERC20Transfer(T, attacker, 1000e18, 0, "")` on the source bridge.
   - `safeTransferFrom` pulls 1000e18 from attacker; bridge receives 990e18 (1% fee deducted by token).
   - `RequestValueTransfer` event emits `valueOrTokenId = 1000e18`.
3. Counterpart bridge operators observe the event and call `handleERC20Transfer(..., 1000e18, ...)`.
   - `safeTransfer(attacker, 1000e18)` releases 1000e18 from counterpart bridge reserves.
4. Net result: source bridge holds 990e18; counterpart bridge paid out 1000e18. Deficit of 10e18 extracted per transfer.
5. After 100 such transfers, the counterpart bridge has lost 1000e18 tokens from its liquidity pool.

**Relevant code locations:** [1](#0-0)

`handleERC20Transfer` on the counterpart bridge releases exactly `_value` tokens (via `safeTransfer` or `mint`), with no cross-check against what the source bridge actually received. [4](#0-3) 

Token registration is `onlyOwner`, confirming the precondition is a semi-trusted owner action rather than a fully unprivileged one — but once registered, any user can exploit the mismatch.
