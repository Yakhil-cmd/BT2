### Title
`Api::CCMenuController` ignores stack-scoped `ApiClient` authorization, letting any valid CCMenu token read the deploy state of every stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping through its `stacks`/`stack` helpers, restricting a stack-scoped `ApiClient` to only the `Stack` referenced by `current_api_client.stack_id`. `Api::CCMenuController` overrides `stack` with an unscoped lookup, breaking that binding: `token authorizes stack A` ≠ `stack the endpoint actually returns`.

### Finding Description
`ApiClient#check_permissions!` only checks that the required `operation:scope` string (e.g. `read:stack`) is present in `permissions`; it never checks which stack the token is bound to: [1](#0-0) 

The only place that enforces the token's `stack_id` binding is `BaseController#stacks`/`#stack`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped: [2](#0-1) 

`Api::CCMenuController` re-defines `stack` to bypass this scoping entirely, resolving directly via `Stack.from_param!(params[:stack_id])` regardless of `current_api_client.stack_id`: [3](#0-2) 

`require_permission :read, :stack` only calls `check_permissions!(:read, :stack)`, which is satisfied by any client holding `read:stack`, and does not re-validate that the resolved `stack` matches `current_api_client.stack_id`. Since `CCMenuController#stack` never goes through the scoped `stacks` relation, a token created specifically for one stack (e.g. the "CCMenu Client" that `CCMenuUrlController` creates with `stack:` set and permission `read:stack`) can be replayed against `/api/stacks/:owner/:repo/:env/ccmenu` for **any other stack** simply by changing `stack_id` in the URL: [4](#0-3) 

This is the equality the report's bug class maps to: "a stack a token authorises" (`current_api_client.stack_id`) vs. "a stack it touches" (`Stack.from_param!(params[:stack_id])` in `CCMenuController#stack`) — before any fix these are unequal for any stack-scoped token, whereas `stacks.from_param!` in the base controller would keep them equal.

### Impact Explanation
Any holder of a legitimately-issued, narrowly-scoped `read:stack` `ApiClient` token (for example a CCMenu URL shared with a single team for one stack) can enumerate and read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state) of every other stack hosted on the same Shipit instance, including private/internal repositories the token owner has no access to. This is an authorization-scope escalation resulting in unauthorized read of stack state/deploy output across stacks the token was never granted access to, matching the "High" impact category (unauthenticated/unauthorized read of stack state or deploy output).

### Likelihood Explanation
High. Exploitation requires only a single valid, unprivileged `ApiClient` token that happens to have `read:stack` permission (the exact class of token `CCMenuUrlController` mints automatically for every user/stack pair) and knowledge/guessing of another stack's `owner/repo/environment` triple used in `stack_id` — no repository write access, GitHub App credentials, or privileged account is required.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the base controller's scoped resolution instead of an unscoped lookup, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that stack-scoped tokens can only resolve the `Stack` they were actually authorized for, restoring the `token.stack_id == resolved stack` invariant enforced everywhere else in `Api::BaseController`.

### Proof of Concept
1. As a legitimate user, visit `CCMenuUrlController#fetch` for `stack_A` (`GET /ccmenu/owner/repo-a/production`). This creates/returns an `ApiClient` named "CCMenu Client" scoped to `stack_A` with `permissions: ['read:stack']` and returns a URL containing `token=<T>`. [5](#0-4) 
2. Take token `T` and request a different stack's CCMenu endpoint: `GET /api/stacks/owner/repo-b/staging/ccmenu?token=<T>`.
3. `Api::BaseController#authenticate_api_client` (overridden in `CCMenuController`) accepts `T` via `ApiClient.authenticate(params[:token])`, succeeding because the token is valid regardless of target stack. [6](#0-5) 
4. `require_permission :read, :stack` passes because `T`'s permissions include `read:stack` (no stack comparison performed). [7](#0-6) 
5. `stack` resolves `repo-b/staging` directly via `Stack.from_param!`, ignoring that `T.stack_id` points to `stack_A`, and the controller renders `stack_B`'s deploy XML (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock reason) to the caller — data the token was never meant to expose. [8](#0-7)
