Confirmed: `Repository.from_github_repo_name` does a plain lookup keyed only on the `full_name` field, with no cross-check against the `repository.owner.login` value used for signature verification in `WebhooksController#verify_signature`.### Title
Webhook org-binding uses `repository.owner.login` for signature verification while handlers act on the independently-attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App config (and thus the HMAC secret) to validate a webhook using `params.dig('repository','owner','login')`, but every downstream handler (e.g. `LabeledHandler`) resolves the target `Shipit::Repository` from the separate, independently-settable `params['repository']['full_name']` field. Because these two values are never cross-validated, a payload verified against one org's (weakly/un-configured) secret can carry a `full_name` pointing at a completely different, victim repository.

### Finding Description
The claimed binding is: `org that verified the signature == org whose repository/label policy is executed`, i.e. `repository_owner (params.dig('repository','owner','login')) == owner(params['repository']['full_name'])`. In a legitimate GitHub payload this holds by construction, but nothing in the code enforces it, since it is JSON parsed from `request.raw_post` and both fields are independently attacker-controlled.

- `WebhooksController#verify_signature` ( [1](#0-0) ) picks the app config via `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository', 'owner', 'login')` [2](#0-1) .
- `Shipit.github` resolves per-org config in multi-org mode via `github_app_config(organization)`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank/unset [3](#0-2) .
- `LabeledHandler#repository` (and `Handler#repository_name`/`#stacks` in the base class) resolve the acted-upon repository from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, which is a plain `find_by(owner:, name:)` lookup with no relation to `repository.owner.login` [4](#0-3) [5](#0-4) [6](#0-5) .

Exploit flow: in a multi-org Shipit deployment, if any onboarded org ("attacker-org") has been configured with a blank `webhook_secret` (an easy/likely oversight since it is documented as optional, see `config/secrets.development.example.yml` and `docs/setup.md`), an attacker who knows/controls that org name sends a raw, unsigned `pull_request`/`labeled` POST to `/webhooks` with:
```json
{ "action": "labeled",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "pull_request": { "labels": [{"name": "<victim's provisioning_label_name>"}], ... } }
```
`verify_signature` looks up `attacker-org`'s config, finds `webhook_secret` blank, and returns `true` regardless of the (missing/garbage) `X-Hub-Signature` header. The controller then dispatches to `LabeledHandler`, which resolves `repository = Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and acts on the victim's `provisioning_behavior`/`provisioning_label_name` configuration - archiving/unarchiving/provisioning the victim's review stack.

Existing guards do not stop this: `drop_unhandled_event` and `ExplicitParameters` only validate JSON shape, not owner/full_name consistency; `verify_signature`'s `GithubOrganizationUnknown` rescue only fires if the *owner* org isn't configured at all - it does nothing to check that the *full_name*'s owner matches. Nowhere in the request path is `params.repository.owner.login` compared against the owner segment of `params.repository.full_name`.

### Impact Explanation
An attacker who controls (or is a member of) any org onboarded to a multi-tenant Shipit instance with a misconfigured (blank) `webhook_secret` can trigger label-driven review-stack provisioning/archival actions against **any other tenant's repository** by simply naming it in `full_name`, without ever possessing that victim's secret or credentials. This is a cross-repository/cross-tenant authorization bypass: the party that "authenticates" a webhook is not the party whose policy is executed. Depending on repository configuration, this can archive/unarchive or (re)provision review stacks - a real unauthorized action on another tenant's stack, matching the "payload for one repository mutating another's stack" Critical category.

### Likelihood Explanation
Requires: (1) a multi-org/multi-tenant Shipit deployment (`secrets.github` keyed by org), and (2) at least one onboarded org whose `webhook_secret` was left blank - a configuration state the docs and example secrets files explicitly show as valid/default (`webhook_secret: # nil`). Given that, exploitation is trivial and free for the attacker: a single unauthenticated HTTP POST with attacker-chosen JSON, no signature needed, repeatable against any victim repository already synced into Shipit. In a single-org deployment the same code path degrades to the existing (and already documented) "no secret = no verification" risk, not a cross-tenant issue. The finding is therefore conditional on a specific, plausible-but-not-universal misconfiguration, which affects confidence in a "by default" characterization but does not remove the underlying missing-binding bug.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, after signature verification succeeds, additionally verify that `params.dig('repository','owner','login')` matches the owner segment of `params.dig('repository','full_name')` (case-insensitively), and reject (422) on mismatch. Alternatively, always derive the org used for the App config lookup from `full_name`'s owner segment rather than the separate `owner.login` field, so a single field governs both which secret is used and which repository is acted on.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb`):
```ruby
test "cannot use attacker org's blank secret to act on a victim repository named in full_name" do
  # multi-org config: attacker-org has blank webhook_secret, victim-org has a real one
  Shipit.stubs(:github_default_organization).returns("attacker-org")
  Shipit.stubs(:github_app_config).with("attacker-org").returns({ webhook_secret: nil })

  victim_repo = shipit_repositories(:shipit) # owner: "victim-org", name: "shipit"
  configure_provisioning_behavior(repository: victim_repo, behavior: :allow_with_label, label: "deploy-me")

  payload = payload_parsed(:pull_request_labeled)
  payload["repository"]["owner"] = { "login" => "attacker-org" }
  payload["repository"]["full_name"] = victim_repo.github_repo_name
  payload["pull_request"]["labels"] = [{ "name" => "deploy-me" }]

  @request.headers['X-Github-Event'] = 'pull_request'
  # No/garbage X-Hub-Signature - attacker doesn't know victim-org's secret

  assert_no_difference -> { Shipit::ReviewStack.count } do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :unprocessable_entity # EXPECTED after fix; currently this passes verification and mutates victim's stack
end
```
Both sides of the equality to assert: `params.dig('repository','owner','login')` ("attacker-org") vs. owner segment of `params.dig('repository','full_name')` ("victim-org") - they diverge, and the current code performs no comparison between them before acting on the victim repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
