## Finding

### Title
Attacker-controlled `arbiter_address` in `arbiter_contract_offer` forces victim's wallet to send private contract/payment data to an attacker-chosen HTTP endpoint (SSRF/data-exfiltration) - (File: wallet.js, arbiter_contract.js, arbiters.js)

### Summary
A paired device (counterparty in an arbiter contract) fully controls the `arbiter_address` field of an `arbiter_contract_offer` message. This address is never checked against any whitelist of known/trusted arbiters — it only has to pass `ValidationUtils.isValidAddress`. When the victim later performs a normal wallet action (`openDispute`/`appeal`/`getAppealFee`), the wallet resolves this attacker-chosen address to a URL via the hub (`hub/get_arbstore_url`) and then issues an outbound HTTP request to that URL, sending contract details, addresses, contact info and (for private assets) the payment amount. Because the destination host is derived from data the remote peer fully controls, this is a direct analog of the reported "Client-side request forgery through dApp authentication" bug: an untrusted counterparty can redirect the victim wallet's authenticated/automatic HTTP requests to an arbitrary destination (e.g., an internal/local network service), causing SSRF and leakage of otherwise-private contract/payment data.

### Finding Description
In `wallet.js`, the `arbiter_contract_offer` device-message handler only validates that `body.arbiter_address` is a syntactically valid address: [1](#0-0) 

No check is performed to confirm the address corresponds to a real, previously-known, or user-approved arbiter. The value is stored via `arbiter_contract.store` and later used verbatim whenever the local (victim) party performs dispute-related actions:

- `openDispute()` resolves the arbstore URL for `objContract.arbiter_address` via the hub and then POSTs contract metadata, addresses, encrypted contract data, contact info, and — for private assets — the actual payment `amount`, to `<url>/api/dispute/new`. [2](#0-1) 

- `appeal()` and `getAppealFee()` follow the same pattern, resolving `hub/get_arbstore_url` (or `hub/get_arbstore_url_by_address`) for the attacker-supplied address and then issuing `httpRequest`/`http.request` to whatever host that resolves to. [3](#0-2) 

- The low-level `httpRequest` helper simply parses the resolved URL and performs a plain HTTP POST with no restriction on host/IP range (no blacklist of private/local network ranges, no host allow-list): [4](#0-3) 

- `arbiters.getInfo`/`getArbstoreInfo` similarly fetch arbitrary URLs for any `arbiter_address` supplied and only validate that the returned string is a non-empty string, not that it is safe/expected: [5](#0-4) 

The victim's own wallet action (disputing a contract, appealing a decision, or checking the appeal fee — all normal, expected user/wallet operations) is what triggers the outbound request, but the destination and thus the blast radius of that request is chosen entirely by the remote peer who proposed the contract, exactly mirroring the reported bug pattern where a wallet is tricked into making an HTTP request to an address supplied by an untrusted third party.

### Impact Explanation
An attacker who pairs with a victim's device (a normal, low-privilege interaction — pairing/chat is a supported feature) can propose an `arbiter_contract_offer` naming themselves (or an accomplice) as `arbiter_address`. If the attacker also controls (or can get the hub to return) an arbstore URL for that address — which is plausible since arbstore registration is itself address-keyed and not verified by the wallet — the victim's wallet will later send:
- Private contract terms, contact info, and pairing codes to an attacker-controlled endpoint.
- The private asset transfer `amount` in the dispute payload, defeating the privacy guarantee of private payments.
- An HTTP request whose destination the attacker fully controls, enabling SSRF against services on the victim's local network (development APIs, internal dashboards, etc.), matching the original report's "local server exposes a development HTTP API which allows an attacker to perform code execution" scenario.

This is a confidentiality breach for private-payment data and a SSRF vector reachable purely through the paired-device message-handling path, which is in scope per the rules (wallet and contract message handling; private payment chains).

### Likelihood Explanation
No special privileges are needed beyond pairing with the victim (a feature explicitly designed to accept unsolicited pairing/chat requests from third parties who obtain a pairing code, e.g., via a public link/QR shared by a "dApp" or service). The `arbiter_address` field is accepted with only a basic format check; there is no verification that it belongs to a known/trusted arbiter before storing the offer, and no confirmation step before dispute/appeal-triggered network requests are sent to whatever URL the hub resolves for that address. The attack requires the victim to take a normal action (open a dispute or appeal) on a contract they already agreed to, which is a realistic and expected user flow once a malicious contract has been accepted.

### Recommendation
- Before resolving and contacting an arbstore URL, require the wallet to explicitly display and let the user confirm the resolved arbstore URL/host prior to sending dispute/appeal data (mirroring the original short-term recommendation of surfacing `req.callback`/destination to the user).
- Maintain and check against a whitelist of trusted/known arbiter addresses (or a signed registry) rather than accepting any syntactically valid address supplied by a remote peer in `arbiter_contract_offer`.
- In `httpRequest`/`requestInfoFromArbStore`/`fetchUrl`-style helpers, resolve and reject destinations that fall within private/loopback/link-local IP ranges (SSRF hardening), consistent with the OWASP SSRF prevention guidance cited in the original report.

### Proof of Concept
1. Attacker pairs with victim's wallet device (via pairing code/link) and sends an `arbiter_contract_offer` message with `arbiter_address` set to an address the attacker controls and has registered as an arbstore on the hub, pointing to `http://127.0.0.1:<dev-api-port>` or another internal address.
2. Victim's wallet stores the offer after only validating address format: [1](#0-0) 
3. Victim accepts the (seemingly legitimate) contract and later disputes it via the normal UI flow, invoking `arbiter_contract.openDispute`.
4. The wallet resolves `arbiter_address` → URL via `hub/get_arbstore_url` and POSTs `contract_hash`, addresses, `encrypted_contract`, contact info, and (for private assets) the payment `amount` to that attacker-controlled URL: [6](#0-5) 
5. The attacker's server receives the forged request, exfiltrating private contract/payment data and/or reaching an internal service on the victim's network.

function appeal(hash, cb) {
	getByHash(hash, function(objContract){
		if (objContract.status !== "dispute_resolved")
			return cb("contract can't be appealed");
		var command = "hub/get_arbstore_url";
		var address = objContract.arbiter_address;
		if (objContract.arbstore_address) {
			command = "hub/get_arbstore_url_by_address";
			address = objContract.arbstore_address;
		}
		device.requestFromHub(command, address, async function(err, url){
			if (err)
				return cb("can't get arbstore url:", err);
			err = await fillArbstoreAddresses(objContract);
			if (err)
				return cb(err);
			device.getOrGeneratePermanentPairingInfo(function(pairingInfo){
				var my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;
				var data = JSON.stringify({
					contract_hash: hash,
					my_pairing_code: objContract.my_pairing_code,
					my_address: objContract.my_address,
					contract: {title: objContract.title, text: objContract.text, creation_date: objContract.creation_date, me_is_payer: objContract.me_is_payer, my_address: objContract.my_address, peer_address: objContract.peer_address, my_party_name: objContract.my_party_name, peer_party_name: objContract.peer_party_name, arbiter_address: objContract.arbiter_address, amount: objContract.amount, asset: objContract.asset},
				});
				httpRequest(url, "/api/appeal/new", data, function(err, resp) {

						return cb(err);

						cb(null, resp, objContract);

		});
	});

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

function getInfo(address, cb) {
	cb = cb || function() {};
	db.query("SELECT device_pub_key, real_name FROM wallet_arbiters WHERE arbiter_address=?", [address], function(rows){
		if (rows.length && rows[0].real_name) { // request again if no real name
			cb(null, rows[0]);
		} else {
			device.requestFromHub("hub/get_arbstore_url", address, function(err, url){
				if (err) {
					return cb(err);
				}
				if (!validationUtils.isNonemptyString(url))
					return cb("invalid url received from hub");
				requestInfoFromArbStore(url+'/api/arbiter/'+address, function(err, info){
					if (err) {
						return cb(err);
					}
					if (!validationUtils.isNonemptyObject(info))
						return cb("invalid arbiter info received from arbstore");
					db.query("REPLACE INTO wallet_arbiters (arbiter_address, device_pub_key, real_name) VALUES (?, ?, ?)", [address, info.device_pub_key, info.real_name], function() {cb(null, info);});
				});
			});
		}
	});
}

function requestInfoFromArbStore(url, cb){
	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;
		});
		resp.on('end', function(){
			try {
				cb(null, JSON.parse(data));
			} catch(ex) {
				cb(ex);
			}
		});
	}).on("error", cb);
}
