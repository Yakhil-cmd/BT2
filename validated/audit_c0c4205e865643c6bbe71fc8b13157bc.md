## Analysis Result

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independently-supplied `repository.full_name` (and even ignore repository scoping entirely), allowing any onboarded GitHub organization to write to other organizations' repositories - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The Livepeer bug is a case of an authorization decision computed from one field while a later action is driven by an independent, unchecked field taken from the same message. Shipit's webhook pipeline has the same structural flaw: `WebhooksController#verify_signature` picks *which organization's secret* to verify the HMAC against using `params.dig('repository', 'owner', 'login')`, but the actual event handlers resolve *which repository/stack to act on* using the separate `repository.full_name` field (or, in `StatusHandler`, no repository scoping at all). Nothing enforces that these two fields agree.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the payload itself: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once verified, `create` hands the *entire raw payload* to the handlers unmodified: [3](#0-2) 

`Shipit::Webhooks::Handlers::Handler` resolves the target repository from a **different** field, `repository.full_name`, with no cross-check against the `repository.owner.login` value that determined which organization's secret authenticated the request: [4](#0-3) 

`Repository.from_github_repo_name` simply splits `owner/name` out of that string and looks it up, with no relation to the organization whose key signed the request: [5](#0-4) 

Because `repository.owner.login` and `repository.full_name` are two unrelated keys in the same attacker-controlled JSON body (the endpoint accepts raw JSON, not GitHub-relayed webhooks with server-side enforced consistency), an organization that has its own legitimately configured `webhook_secret` in Shipit's multi-org configuration can craft a payload where `repository.owner.login` names its own org (so `verify_webhook_signature` succeeds using its own secret) while `repository.full_name` names a repository/stack belonging to a completely different, unrelated organization onboarded to the same Shipit instance. `PushHandler` and `CheckSuiteHandler` would then act on that victim stack (e.g. trigger `stack.sync_github`, `schedule_refresh_check_runs!`): [6](#0-5) [7](#0-6) 

`StatusHandler` is worse: it performs **no repository scoping at all**, matching purely by commit `sha` across the entire install: [8](#0-7) 

Any organization holding a valid `webhook_secret` for its own org can therefore forge a `status` event with a `sha` belonging to any commit tracked by *any* stack across *any* other organization on the same Shipit instance and call `commit.create_status_from_github!`, writing arbitrary CI/deploy status onto a foreign repository's commits.

This is the direct analog of the Livepeer finding's binding break: `organization that authenticated` (`repository.owner.login`, checked in `verify_signature`) ≠ `repository that is written` (`repository.full_name` / bare `sha`, used inside the handler), exactly the trust-binding class called out in the rules.

### Impact Explanation
This allows cross-repository/cross-organization writes: an attacker who legitimately controls one onboarded GitHub organization (and thus knows its own `webhook_secret`) can forge webhook deliveries that get verified using their own secret, yet cause writes/state changes (commit status creation, forced sync, check-run refresh) against stacks belonging to other organizations hosted on the same Shipit instance. This matches the "cross-repository writes" Critical-tier impact category defined in scope.

### Likelihood Explanation
Exploitation only requires: (1) the target Shipit instance is configured with multiple GitHub organizations (`docs/setup.md` documents this as a supported multi-org configuration), and (2) the attacker controls one of those organizations well enough to know/derive its `webhook_secret` (a normal, unprivileged capability for an org admin of their own org, not a Shipit credential or GitHub App private key). No Shipit session, API token, or GitHub App key is required — only crafting a raw HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses for their own org. This is a realistic, low-effort attack path for any multi-tenant Shipit deployment.

### Recommendation
Bind the two checks together: after verifying the signature, re-derive the acting organization from the *same* field used to select the secret (`repository.owner.login`), and require that the repository/stack resolved by `Handler#repository_name` (`repository.full_name`) has that exact owner. Reject the event (422) on mismatch. For `StatusHandler`, scope the `Commit` lookup by the repository/stack the verified organization owns, instead of matching bare `sha` globally.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (webhook_secret `S_A`, controlled by attacker) and `victim-org` (hosts a tracked stack), per the multi-org config in `docs/setup.md`.
2. Attacker crafts a JSON body for a `status` event:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<sha of a commit belonging to victim-org's tracked stack>",
  "state": "success"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` using their own known secret `S_A`.
4. POST to `/github/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and successfully verifies the signature with `S_A` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
6. `StatusHandler#process` matches on `sha` alone with no ownership check (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), creating a forged status on the victim organization's commit despite the request being authenticated only as `attacker-org`.
