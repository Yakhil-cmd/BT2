### Title
Stale account delegates regain authority after a position NFT round-trip - (File: contracts/controller/src/storage/account.rs)

### Summary
**Severity: Medium.** A delegate grant is scoped to the granting address rather than an ownership epoch. If an owner delegates a position manager, transfers the account NFT to another address, and later receives the same NFT back, the stale grant automatically becomes valid again without a new owner authorization.

### Finding Description
The controller resolves account ownership dynamically from the position NFT on every account load. [1](#0-0) 

`is_owner_or_delegate` authorizes a caller when it is an active position manager and appears in the stored delegate list for `account_id` and `owner`. [2](#0-1) 

The delegate lookup only checks `grant.granted_by == owner`; it does not bind the grant to the NFT transfer epoch, ownership version, or any other value that changes when ownership moves. [3](#0-2) 

A transfer to a new owner makes the old grant inactive only because `granted_by` no longer equals the current owner. When the NFT returns to the original owner, the same stored grant matches again. `remove_delegate` deletes a stale grant only if the current owner explicitly calls it for that delegate while the grant is stale; there is no automatic invalidation on NFT transfer. [4](#0-3) 

The reactivated delegate can then pass the authorization checks in `borrow` and `withdraw`. [5](#0-4) [6](#0-5) 

### Impact Explanation
A previously delegated position manager can drain restored collateral or take new debt against it after the NFT temporarily changes hands and returns. `withdraw` can send collateral to an arbitrary external recipient through `to`, while `borrow` can send borrowed assets to an arbitrary external recipient. [7](#0-6) [8](#0-7) 

This is theft of user funds: the regained authority was not freshly authorized by the current ownership period, and the delegate can direct proceeds to itself.

### Likelihood Explanation
Exploitation requires three conditions:

1. The victim previously called `add_delegate(account_id, delegate)` for an active position manager.
2. The victim transfers the position NFT to another address.
3. The NFT later returns to the victim, for example after a sale fails, an escrow/wrapper releases it, or the victim repurchases the same account.

The attacker cannot force the NFT round-trip, which limits likelihood, but no further victim signature is needed once the NFT returns.

### Recommendation
Bind delegate grants to an ownership epoch rather than only `granted_by`.

Maintain a per-account `ownership_epoch` incremented whenever controller-observed NFT ownership changes, or store the current NFT owner plus a monotonically increasing transfer epoch in `DelegateGrant`. Reject grants whose recorded epoch does not match the account's current epoch.

If observing every external NFT transfer is not practical, derive the epoch from NFT state that changes on transfer, or expose a controller-side invalidation that clears `ControllerKey::Delegates(account_id)` whenever the current owner differs from `DelegateGrant.granted_by`, including during `try_get_account`. The code must ensure that returning the NFT to the prior owner cannot reactivate the old list.

### Proof of Concept
1. Alice creates an account and supplies collateral:
   - `supply(caller=alice, account_id=0, spoke_id=S, assets=[(hub, USDC, amount)])`.
   - Alice receives `account_id=A` and position NFT `A`.
2. Governance has activated `manager=M`; Alice calls:
   - `add_delegate(caller=alice, account_id=A, delegate=M)`.
   - Storage now contains a grant with `granted_by=alice` and `delegates=[M]`.
3. Alice transfers NFT `A` to Bob. `account_owner(A)` resolves to Bob, so `get_delegates(A, bob)` filters out Alice's stale grant and `M` is denied.
4. Bob transfers NFT `A` back to Alice. The storage grant was never deleted, so `get_delegates(A, alice)` returns `[M]` again.
5. Without Alice re-authorizing it, `M` calls:
   - `withdraw(caller=M, account_id=A, withdrawals=[(hub, USDC, 0)], to=Some(M))`.
   - `require_owner_or_delegate` succeeds because `caller == M`, `M` remains an active manager, and the stale grant now matches the restored owner.
6. The pool pays Alice's collateral to `M`; alternatively, `M` calls `borrow(caller=M, account_id=A, borrows=[...], to=Some(M))` and extracts borrowed funds against Alice's collateral.

pub(crate) fn get_delegates(env: &Env, account_id: u64, owner: &Address) -> Vec<Address> {
    get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
        .filter(|grant| grant.granted_by == *owner)
        .map(|grant| grant.delegates)
        .unwrap_or_else(|| Vec::new(env))

    let Some(grant) = get_user::<DelegateGrant>(env, &key) else {
        return false;
    };

        env.storage().persistent().remove(&key);
        return false;
    }
