### No Vulnerability found for this question.

**Reasoning:** The claimed attack path hinges on `g1_lincomb_fast` "dropping" an infinity proof from the weighted sum while its `r^i` weight still applies elsewhere in the equation. But the filtering step in `src/common/lincomb.c` is purely a computational optimization that removes points where `blst_p1_is_inf(&p[i])` is true before calling `blst_p1s_mult_pippenger` [1](#0-0) . Mathematically, `[coeff]·O = O` for the point at infinity regardless of the scalar `coeff`, so removing a zero point from the sum before performing Pippenger's algorithm produces an identical result to including it — the filtering exists only because `blst`'s Pippenger implementation cannot safely process the point at infinity, not because it changes the value of the linear combination [2](#0-1) .

Because the filtered and unfiltered sums are always numerically equal for infinity inputs, there is no divergence in the aggregate value fed into `verify_cell_kzg_proof_batch`'s pairing check caused by this optimization. An attacker forcing a proof to decode to the identity element does not selectively "cancel" its own `r^i` weight while leaving a corresponding commitment/`y_i` correction term active elsewhere — both sides of the pairing equation are computed from the same aggregated lincomb logic, and substituting `O` for a proof simply zeroes that proof's contribution exactly as it would without filtering. To actually forge a valid batch verification, the attacker would need to find commitment/proof/evaluation values satisfying the pairing equation despite an invalid opening — which reduces to breaking the discrete-log/pairing assumption, not to exploiting the zero-filtering code path.

I was not able to fully retrieve and inspect the complete body of `verify_cell_kzg_proof_batch` (challenge computation, `r_powers`, and the final pairing check construction) due to tool/iteration limits, so I cannot independently confirm the exact structure of the aggregate equation beyond this mathematical argument about `g1_lincomb_fast`. However, based on the isolated behavior of `g1_lincomb_fast` and the general algebraic property that scalar multiples of the identity element are always the identity, there is no basis to conclude that the zero-point filtering introduces a soundness divergence. This matches the general pattern of prior, previously-dismissed reports about this exact filtering logic in c-kzg-4844.
