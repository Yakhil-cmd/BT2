### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, letting a secret for one GitHub organization authorize writes against a repository outside that organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook by reading `repository.owner.login` (falling back to `organization.login`) out of the *same untrusted JSON body* it is about to validate, then all event handlers (`PushHandler`, `PullRequest::*Handler`, `Handler#repository_name`) act on a *different* field of that body, `repository.full_name`, to look up the `Repository`/`Stack` to mutate. Because these two fields are independent, attacker-controlled strings inside one HMAC-signed JSON blob, an attacker who has learned the webhook secret configured for one organization ("OrgA") can forge a payload whose `repository.owner.login` is `"OrgA"` (so the signature check passes with OrgA's secret) but whose `repository.full_name` names a repository belonging to a completely different organization/stack, causing the push/pull_request handlers to sync commits or mutate stacks that were never authorized by that secret.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` looks up the app/secret to validate against using: [1](#0-0) [2](#0-1) 

`repository_owner` is computed purely from the still-unverified JSON body (`params.dig('repository', 'owner', 'login')`). `Shipit.github(organization: repository_owner)` then resolves a per-organization `webhook_secret` from `secrets.github`, and `verify_webhook_signature` HMACs the raw body against that secret: [3](#0-2) [4](#0-3) 

The `Shipit` engine explicitly supports multi-organization configuration with independent `webhook_secret` values per organization (confirmed by the multi-org fixture `test/dummy/config/secrets_double_github_app.yml` defining separate `OrgOne`/`OrgTwo` configs).

Once the HMAC check passes, the actual work is dispatched by event handlers that never re-check `repository.owner.login`. Instead they resolve the target repository from `repository.full_name`: [5](#0-4) [6](#0-5) [7](#0-6) 

`repository.owner.login` and `repository.full_name` are both plain, independently-settable JSON fields inside the same raw POST body. The HMAC signature only proves "this exact byte sequence was signed with organization X's secret" — it proves nothing about internal consistency between fields of that byte sequence. An attacker who already possesses (or brute forces/leaks) the webhook secret for one low-value/less-trusted organization can therefore forge a byte sequence where `repository.owner.login == "OrgA"` (satisfies signature lookup) while `repository.full_name == "OrgB/some-other-repo"` (drives the actual mutation), as long as a `Repository`/`Stack` exists in this Shipit instance matching that `full_name`. This is directly analogous to the reported bug class: the credential (webhook secret / vault "last claim" binding) is checked against one identifier, while the state-mutating logic operates on a different, unchecked identifier.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." A party holding a lower-trust organization's webhook secret can force `PushHandler` to call `stack.sync_github(expected_head_sha: ...)` for a stack whose repository belongs to a different, unrelated organization, or drive `PullRequest` handlers (`opened_handler`, `labeled_handler`, `closed_handler`, `reopened_handler`) to create/archive/unarchive review stacks for that unrelated repository. This can trigger unintended provisioning/deprovisioning, and unauthorized `sync_github` operations that update `last_deployed_commit`/reachable commit state used later for deploy authorization — effectively cross-repository writes performed under a credential never issued for that repository. This meets the "Critical - cross-repository writes" bar defined in the rules.

### Likelihood Explanation
The precondition is possession of a webhook secret for at least one organization configured on the instance — which is far weaker than requiring a GitHub App private key, an `ApiClient` token, or repository write access, and is realistic in a multi-tenant/multi-org Shipit deployment where different organizations may have different trust levels or where one org's secret leaks (e.g., via misconfigured hooks in GitHub project settings, logs, or a less-secured integration). No GitHub-side compromise, TLS interception, or privileged Shipit account is required — this is a pure logic flaw in how the identifier used for authentication diverges from the identifier used for authorization of the mutated resource.

### Recommendation
After signature verification succeeds, re-derive/validate that the same organization identifier used to select the webhook secret (`repository.owner.login`/`organization.login`) matches the owner portion of `repository.full_name` used by the handlers, and reject the event if they diverge. Alternatively, bind handler repository resolution to the already-authenticated organization instead of trusting `full_name` independently, or ensure a single canonical field is used both for secret selection and for driving mutations.

### Proof of Concept
1. Deploy a Shipit instance configured with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`) and Repository/Stack records for both `OrgA/repoA` and `OrgB/repoB`.
2. Attacker knows/leaks `webhook_secret` for `OrgA` only.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/repoB"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's `GitHubApp`, and `verify_webhook_signature` succeeds since the attacker signed with OrgA's real secret.
6. `PushHandler#process` is invoked; `stacks` resolves via `Repository.from_github_repo_name("OrgB/repoB")`, matching the unrelated `OrgB` stack, and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` — a write against a repository/organization never authenticated by the presented secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
