## Finding

### Title
Unbounded loop over an AA's unspent outputs during payment composition allows cheap dust flooding to DoS all future AA responses - ([File: aa_composer.js])

### Summary
`completePaymentPayload()` in `aa_composer.js` selects **all** unspent outputs owned by an AA address with an unbounded SQL query (no `LIMIT`) and then iterates over every returned row in JavaScript to accumulate enough value for an outgoing payment. Any unprivileged party can cheaply grow the number of unspent outputs owned by an AA by repeatedly sending it small payments that the AA silently "eats" (no matching `if` case, no response). Once the output set is large enough, every subsequent trigger that requires the AA to send a payment must query and loop through the entire, ever-growing set of dust outputs, which can push the AA past its available complexity/processing budget and prevent it from ever completing a response — mirroring the Sherlock report's "array flooded with cheap dust that an admin-driven loop must scan every time" DoS pattern.

### Finding Description
When an AA needs to build a payment message, it calls `readStableOutputs()`/`readUnstableOutputsSentByAAs()`, which run: [1](#0-0) 
Neither query has a `LIMIT`; they return every unspent output owned by the AA for the relevant asset. `iterateUnspentOutputs()` then walks the *entire* result set row by row to accumulate `total_amount`: [2](#0-1) 

The only anti-dust protection is a minimum output-size filter of `FULL_TRANSFER_INPUT_SIZE` bytes for bytes-asset outputs, explicitly documented as being there "to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond": [3](#0-2) 

This filter bounds the *size* of each dust output but not the *count*. Any unprivileged sender can post repeated payments to the AA address that don't match any `if` condition in `messages.cases`; the AA accepts the coins with no response ("eat the received coins and send no response, state changes are still performed"): [4](#0-3) 

Each such payment only needs to clear the bounce-fee floor check: [5](#0-4) 

so an attacker can cheaply create an unbounded number of small unspent outputs owned by the AA over time (bounded only by the network's per-unit fee, not by any per-output cost imposed by the AA). Every future trigger that causes the AA to send *any* payment (to the attacker, to legitimate users, or in response to a genuinely privileged/administrative action modeled in oscript, e.g. a payout/auction/exchange AA) must then scan and loop through this entire growing output set in `iterateUnspentOutputs`, since there is no secondary index/array of "reasonably-sized" outputs to prefer, analogous to the audited contract's `deposits[]` array being scanned in full by `netAtPrice()`/`depositAuction()`.

### Impact Explanation
As the number of dust outputs owned by the AA grows without bound, the cost (DB rows returned, JS loop iterations, and evaluation/processing time) of composing *any* outgoing payment from that AA grows linearly and unboundedly. This can push AA response composition past available time/complexity constraints, causing legitimate triggers (including privileged/administrative operations implemented in the AA's oscript, e.g. finalizing an auction, distributing funds, or processing a market order) to fail or never complete, effectively freezing the AA and its held funds for all users — matching the "AA fund loss or freezing" impact class.

### Likelihood Explanation
Any address can send a payment to an AA address; no special permission or private key belonging to the AA is required. The only cost is the network fee for issuing units plus a bounce-fee-covering amount, both of which are cheap and fully controlled by the attacker, and this can be repeated an arbitrary number of times, satisfying the "unprivileged unit poster / AA trigger sender" reachability requirement.

### Recommendation
- Cap the number of unspent outputs read per payment composition attempt with an explicit `LIMIT` and consolidate dust proactively (e.g. auto-merge many small outputs into one when a legitimate payment is sent to the AA), or
- Maintain and prefer a bounded, separately-tracked "large output" set to satisfy target amounts, falling back to (and paginating) the dust set only when necessary, similar to the Sherlock report's recommendation of tracking a separate array of non-zero/meaningful entries instead of scanning the full array unconditionally.
- Consider charging an increasing marginal cost (e.g., minimum-output-size floor that scales with the number of existing unspent outputs for that AA/asset) to make dust flooding economically infeasible.

### Proof of Concept
1. Deploy any AA whose `messages.cases` do not match a plain data-less/irrelevant payment (a common, realistic pattern for many financial AAs).
2. Repeatedly send unit payments to the AA address, each just above `FULL_TRANSFER_INPUT_SIZE` and above `bounce_fees.base`, with no matching trigger data — the AA accepts and "eats" them with no response (`no messages after filtering`), leaving each payment as a new unspent output owned by the AA.
3. Repeat thousands of times cheaply (paying only minimal network unit fees) to accumulate a very large number of unspent outputs for the AA's base asset.
4. Trigger the AA with a legitimate request requiring it to send a payment; observe that `readStableOutputs()`/`readUnstableOutputsSentByAAs()` (no `LIMIT`) plus `iterateUnspentOutputs()` must scan the entire dust set, with cost/time growing linearly with the number of attacker-created outputs, eventually preventing the AA from completing legitimate responses.
