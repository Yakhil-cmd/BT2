## Analysis

The Sherlock report describes a **griefing/callback-confusion vulnerability**: a privileged callback (`executeOperation`) is gated only by "caller must be the lending pool," but the contract never verifies that the *specific* flash loan being serviced was actually initiated by its own trusted flow (`executeFlashLoans`). Because any third party can ask the lending pool to call back into the victim contract, the "onlyLendingPool" check is trivially bypassed to drive state-changing logic that should only ever run as part of a self-initiated, single-purpose sequence.

The closest reachable analog in ocore is in the wallet-pairing / multisig-wallet-creation subsystem (`wallet.js` / `wallet_defined_by_keys.js`), which similarly gates sensitive, network-triggered state mutation with an overly coarse authorization check ("subject is whitelisted for non-correspondents") instead of verifying that the sender is actually a legitimate participant of the specific wallet-creation instance being referenced.

### Title
Unauthenticated device can inject itself into another user's multisig wallet's cosigner set and permanently block wallet finalization - (File: wallet_defined_by_keys.js)

### Summary
`my_xpubkey` and `wallet_fully_approved` are explicitly whitelisted to be processed **from correspondents ocore does not even know** (`arrSubjectsAllowedFromNoncorrespondents`), and their handlers persist database state (`extended_pubkeys` rows) referencing an attacker-chosen `wallet` id without ever validating that the sending device is one of the cosigners named in that wallet's `wallet_definition_template`.

### Finding Description
In [1](#0-0) , when a device message arrives from a completely unknown (non-paired) correspondent, only three subjects are permitted through: `pairing`, `my_xpubkey`, and `wallet_fully_approved`.

These are routed in [2](#0-1)  straight into:
- `walletDefinedByKeys.addDeviceXPubKey(body.wallet, from_address, body.my_xpubkey, callbacks.ifOk)`
- `walletDefinedByKeys.handleNotificationThatWalletFullyApproved(body.wallet, from_address, callbacks.ifOk)`

Both are documented as "called from network, without user interaction" in [3](#0-2) :

Neither function checks that `device_address` (== `from_address`, i.e. the actual sender authenticated only by its own self-generated device keypair) is one of the device addresses that the wallet's original creator (`handleOfferToCreateNewWallet`) listed as a cosigner in `body.wallet_definition_template` (validated only for the *legitimate* participants in [4](#0-3) ). Any party — including one that has never paired with the victim — can craft an arbitrary `wallet` id (the wallet's base64 identifier, which is broadcast/known to at least the intended cosigners during the offer/xpubkey-exchange phase and is not a secret bound to sender identity) and inject a bogus row into `extended_pubkeys` for that wallet.

This exactly mirrors the reported bug class: a state-mutating handler trusts "this message subject is allowed" (the wallet analog of "caller is `onlyLendingPool`") instead of verifying "this specific call is part of a flow I actually initiated with this specific counterparty" (the wallet analog of "this flash loan was started by my own `executeFlashLoans`").

### Impact Explanation
`checkAndFullyApproveWallet` in [5](#0-4)  only proceeds when every row for the wallet in `extended_pubkeys` has an `approval_date`:
```
if (rows.some(function(row){ return !row.approval_date; }))
    return onDone ? onDone() : null;
```
By inserting an extra `extended_pubkeys` row (via `addDeviceXPubKey`, which sets `approval_date` immediately, or via `handleNotificationThatWalletFullyApproved`, which inserts a row with no `approval_date`) for a wallet the attacker was never invited to, the attacker can permanently prevent `rows.some(!row.approval_date)` from ever becoming false for that wallet, freezing the legitimate multisig wallet-creation handshake for the real cosigners indefinitely (a form of fund/asset-custody freezing, since the shared address behind this wallet can never be marked ready). Separately, `readCosigners` in [6](#0-5)  throws an uncaught `Error` ("cosigner not found among correspondents") whenever it encounters an `extended_pubkeys` row for a device that is not a known correspondent — which is guaranteed here since the attacker was never paired — causing a node crash/DoS whenever the victim's wallet UI attempts to list cosigners for the affected wallet.

### Likelihood Explanation
The attack requires no privileges: the attacker only needs their own device keypair (self-generated, free) and the target `wallet` identifier, and can send the crafted `my_xpubkey`/`wallet_fully_approved` message directly, bypassing the normal pairing/correspondent trust model by design (`arrSubjectsAllowedFromNoncorrespondents`). Any node actively going through the multi-device wallet setup flow is exposed for the duration of that setup.

### Recommendation
`addDeviceXPubKey` and `handleNotificationThatWalletFullyApproved` should verify, before writing to `extended_pubkeys`, that `device_address` is actually part of the wallet's `definition_template` (i.e. present among `getDeviceAddresses(wallet_definition_template)` for the referenced `wallet`), analogous to the check already performed for the *offer* in `validateWalletDefinitionTemplate`. Reject/ignore the message if the sender is not an expected cosigner of that specific wallet.

### Proof of Concept
1. Attacker learns/observes a `wallet` base64 id that Alice used with cosigner Bob while creating a multisig wallet (e.g., visible on Bob's device before completion, or leaked).
2. Attacker (never paired with Alice) sends a device `justsaying`/message with `subject: "my_xpubkey"`, `body: {wallet: "<observed id>", my_xpubkey: "<attacker xpubkey>"}` directly to Alice's device address.
3. Because `my_xpubkey` is in `arrSubjectsAllowedFromNoncorrespondents`, Alice's node processes it via `handleMessageFromHub` → `addDeviceXPubKey`, inserting a row `(wallet, attacker_device_address, xpubkey, approval_date=now)`.
4. `checkAndFullyApproveWallet` now requires this new row's presence to always have `approval_date` (already true), but any later call to `readCosigners(wallet, ...)` throws, because `attacker_device_address` has no matching `correspondent_devices` entry — crashing the flow that lists/reports cosigners for that wallet.
5. Alternatively, attacker sends `subject: "wallet_fully_approved"` first (before Bob approves), inserting a row with no `approval_date`, permanently blocking `checkAndFullyApproveWallet` for the legitimate wallet since `rows.some(!row.approval_date)` will now always be true.
