## Finding

The bug-class in the Rancher report is: **a privileged update path lets an actor mutate an identity/principal-binding field, but doesn't validate that the actor legitimately owns the identity being bound — so the next event referencing that identity (login) gets silently rebound to the attacker.**

The closest reachable analog in `Camomtat/ocore--011` is in the **shared-address (multisig-wallet) device-message handler**, where a *paired device* can register the `device_address` binding for signing paths that belong to *other* co-signers, without any cryptographic proof that it actually controls those paths, and this binding is persisted "first-write-wins".

### Title
Unauthenticated co-signer `device_address` binding in shared-address setup allows a paired device to hijack signature routing for multisig wallets - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress()` accepts a `new_shared_address` device message from any paired correspondent and stores, for every signing path in the shared-address definition, both a member `address` **and** a `device_address` that tells the local wallet which device to contact when a signature at that path is needed. Only the `address` field is checked against the address hash/definition; the `device_address` field — i.e. which device (identity) is trusted to hold the corresponding private key — is accepted at face value for any member address that is not the receiver's own.

### Finding Description
`handleNewSharedAddress` validates that:
- `body.address` hashes to `body.definition` [1](#0-0) 
- each `signerInfo.address` is syntactically valid and matches the address literally present at that path in the definition [2](#0-1) 

It never validates that `signerInfo.device_address` (which device is authorized to answer signing requests for that member address) is authentic. `determineIfIncludesMeAndRewriteDeviceAddress` only rewrites the `device_address` field for the **receiver's own** addresses found in `my_addresses`; for every other member address in the definition (i.e. co-signers), the attacker-supplied `device_address` is kept unchanged: [3](#0-2) 

The record is then persisted via `addNewSharedAddress`, which uses `INSERT IGNORE` on both `shared_addresses` and `shared_address_signing_paths` (unique key on `(shared_address, signing_path)`): [4](#0-3) 

Because these are `INSERT ... IGNORE` statements, whichever `new_shared_address` message arrives **first** for a given `shared_address`/`signing_path` wins permanently; a later, legitimate message from the true coordinator carrying the correct `device_address` for a co-signer is silently dropped, since the row already exists.

### Impact Explanation
A paired device (an ordinary correspondent, the lowest-privilege relationship in ocore's wallet protocol) that learns or predicts the shared-address definition (e.g. because it is itself intended to be one of the co-signers, or because member addresses are commonly shared with correspondents for payment purposes) can pre-register a `new_shared_address` message naming a legitimate co-signer's `address` but pointing `device_address` at a device it controls (or an unreachable device). Once accepted:
- The victim's wallet will forever route "please sign at this path" requests for that co-signer to the wrong device.
- The real coordinator's subsequent, correct `new_shared_address` message is ignored (`INSERT IGNORE`), so the corruption cannot be self-healed by the legitimate party.
- The multisig shared address becomes unable to collect the required cosigner signature, freezing any funds sent to it, without the requirement of ever compromising a private key.

This is analogous to the Rancher CVE's core defect: an identity-binding field (`device_address`, playing the role of `principalIds`) that should be immutable/authenticated is instead trusted from an unprivileged input and silently rebinds control-plane routing for another party's identity, with lasting effect on subsequent operations (spending/signing) tied to that identity.

### Likelihood Explanation
Exploitation only requires an existing device pairing (a low bar; pairing secrets can be shared in the open or reused) and knowledge of the target shared-address definition, which is routinely exchanged among wallet co-signers/devices as part of normal shared-address setup flows (`create_new_shared_address`, `approve_new_shared_address`). Because `shared_addresses`/`shared_address_signing_paths` are keyed with `INSERT IGNORE`, a race to register first is sufficient — no additional cryptographic capability is needed.

### Recommendation
- Do not trust `device_address` values supplied by a third party for co-signer addresses that are not the local device; instead, require each co-signer's `device_address` binding to be attested by the co-signer's own message/signature (similar to the self-rewrite already done in `determineIfIncludesMeAndRewriteDeviceAddress`) or by the original address's on-chain definition owner.
- Reject or explicitly re-validate/update `shared_address_signing_paths` when a materially different `device_address` claim arrives for the same `(shared_address, signing_path)`, rather than silently ignoring it forever with `INSERT IGNORE`; at minimum, surface a conflict to the user instead of first-write-wins.

### Proof of Concept
1. Attacker device D_e is paired with victim device D_v (ordinary pairing).
2. Attacker learns/derives the definition of an intended shared address `S` involving victim's address `A_v` and co-signer's address `A_c` (e.g., because attacker is a would-be third member, or because addresses are shared publicly for payment).
3. Before the legitimate coordinator sends the real `new_shared_address` setup message, D_e sends the victim:
   ```
   {subject: "new_shared_address", body: {
     address: S,
     definition: [...],           // real, correct definition, hashes to S
     signers: {
       "r.0": {address: A_v, device_address: D_v},   // victim's own path (will be rewritten anyway)
       "r.1": {address: A_c, device_address: D_e}    // co-signer path, device_address forged to attacker's device
     }
   }}
   ```
4. `handleNewSharedAddress` passes all checks (hash matches, addresses match definition), `addNewSharedAddress` inserts the rows.
5. The real coordinator later sends the correct message with `"r.1": {address: A_c, device_address: D_c}` — it is ignored because the `(S, "r.1")` row already exists.
6. When the victim needs a signature from `A_c` to spend from `S`, the wallet contacts `D_e` instead of `D_c`, and the transaction can never be completed, freezing funds sent to `S`. [5](#0-4) [6](#0-5)

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
