### Title
Cross-repository commit status forgery via missing repository binding in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the incoming payload was signed with the webhook secret of *some* GitHub organization/app configured in `Shipit.github` — it derives that organization solely from `params.dig('repository', 'owner', 'login')` (or `organization.login`) inside the very payload the attacker controls, and never re-checks that field against any other part of the payload used downstream. `StatusHandler#process`, unlike every other handler in the engine, then acts on `Commit.where(sha: params.sha)` globally, with **no repository/stack scoping at all**. This breaks the equality "organization whose secret authenticated the request == repository that is written to": an attacker who legitimately controls a Shipit-registered GitHub organization/app (and therefore its `webhook_secret`) can forge a `status` event, sign it with their own secret, but populate `sha` with a commit SHA belonging to a completely different stack/organization, and Shipit will apply the forged CI status to that unrelated commit.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` verifies webhook signatures like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params['repository']['owner']['login']` (falling back to `params['organization']['login']`) — fields fully controlled by whoever sends the HTTP request, only constrained by the requirement that the raw body's HMAC matches `Shipit.github(organization: repository_owner).webhook_secret`: [3](#0-2) 

Once the signature check passes, the controller dispatches the whole payload to the relevant handler(s): [4](#0-3) 

Every other handler scopes its side effects through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, e.g. `PushHandler`, `CheckSuiteHandler`, and the pull-request handlers all call `stacks`/`repository` derived from `repository.full_name`: [5](#0-4) [6](#0-5) [7](#0-6) 

`StatusHandler`, however, does not scope to any repository/stack at all — it matches purely on commit SHA across the entire commits table: [8](#0-7) 

The verification step binds the request to "the organization named in `repository.owner.login`", but the code that actually writes state (`StatusHandler`) never checks that field, nor `repository.full_name`, at all — it only uses `sha`, which is a free-form string chosen by whoever crafts the payload. So the binding "organization that authenticated == repository/commit that is written" is completely absent for this handler: the signature only proves "some org's secret was used to sign this exact byte string," not "the sha in this payload belongs to a commit under that org's repositories."

`Commit#create_status_from_github!` writes the forged status directly into the `statuses` association, which feeds `Commit#status`, `Commit#deployable?`, and `Commit#schedule_continuous_delivery`: [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation
An attacker who runs their own GitHub organization with its own GitHub App/webhook installed into this Shipit instance (a legitimate, unprivileged multi-tenant setup as documented in `config/secrets.development.shopify.yml`/`docs/setup.md`, which explicitly supports multiple independent organizations each with their own `webhook_secret`) can forge a signed `status` webhook whose `sha` targets a commit that belongs to a *different* organization's stack that they have no access to. This lets them:
- Inject a fabricated `success` commit status onto a victim commit in another org's repository/stack.
- Because `Commit#deployable?` requires `success? && !blocked?`, and `schedule_continuous_delivery` triggers `ContinuousDeliveryJob` when `deployable? && stack.continuous_deployment? && stack.deployable?`, a forged "success" status can make an otherwise CI-failing/pending commit eligible for continuous deployment or unblock manual deploys gated on required statuses.
- This is an unauthorized deploy-gating bypass across repository/organization boundaries — the attacker never needed credentials for the victim organization, only their own (already-configured) webhook secret.

This satisfies the "unauthorized deploy" / cross-repository write class of impact described in scope, since the authenticated organization boundary (webhook_secret ownership) is not the same boundary enforced on the actual write target (arbitrary commit by SHA, with no repository check).

### Likelihood Explanation
Likelihood is Medium-High for any Shipit deployment that serves more than one GitHub organization (the multi-org config shown in `config/secrets.development.shopify.yml` is a first-class supported configuration). Any organization admin who can install a GitHub App/webhook pointed at this Shipit instance already possesses a valid `webhook_secret` for their own org and can trivially compute a valid `X-Hub-Signature` for any payload body they construct, including one with an unrelated `sha`. No GitHub credentials, Shipit session, or API token for the victim org are required — only knowledge of one's own configured webhook secret, which is explicitly not a privileged/administrative Shipit credential.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the repository derived from the payload (as every other handler does via `stacks`/`Repository.from_github_repo_name(payload.dig('repository','full_name'))`), and additionally verify that this derived repository's owner matches the `repository_owner` used to select the webhook secret in `WebhooksController#verify_signature`. More generally, `verify_signature` should assert that `repository.owner.login` and `repository.full_name`'s owner segment are consistent with each other before any handler is allowed to run, closing the gap between "who signed this request" and "what resource the request claims to modify."

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` layout).
2. Attacker controls `OrgA`'s GitHub App/webhook secret (legitimately, as its own org admin).
3. Attacker knows (or guesses) the `sha` of a commit belonging to a stack owned by `OrgB` (SHAs are often public/predictable, e.g. from public GitHub history).
4. Attacker crafts a `status` event payload:
```json
{
  "sha": "<OrgB-victim-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
5. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
6. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully.
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `OrgB` commit regardless of the `repository` field — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto a commit the attacker never had any legitimate relationship to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
