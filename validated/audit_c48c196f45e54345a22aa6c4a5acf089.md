### Title
Webhook signature verification is keyed by an attacker-controlled payload field, allowing cross-organization forgery of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using a field taken directly from the *unverified* request body, and `GithubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success. Combined, an unprivileged attacker can craft a webhook payload that is "verified" against one configured organization (in particular, one whose `webhook_secret` is blank) while all the actually-processed event data (`repository.full_name`, ref, sha, etc.) targets a completely different, properly-secured organization/repository.

### Finding Description
`verify_signature` computes the organization to check against via `repository_owner`, which is read straight out of the JSON body being verified: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp` config for whatever organization name the attacker put in the payload, and `verify_webhook_signature` immediately returns `true` if that organization has no `webhook_secret` configured: [3](#0-2) 

Shipit is designed to support multiple GitHub Apps/organizations simultaneously, each with its own (optional) `webhook_secret`, as shown in the dummy multi-org fixture where one org has a secret and another (`OrgTwo`) has none: [4](#0-3) 

Once `verify_signature` passes, `create` re-parses the same attacker-controlled raw body and dispatches it to the registered event handlers, which act on whatever `repository`/`organization` data is present in that body (e.g. resolving a `Stack`/`Repository` by `full_name` and enqueuing sync jobs): [5](#0-4) 

Because the field used to pick the verification secret (`repository.owner.login`, or `organization.login`) and the field the handlers actually act on (`repository.full_name`) are both attacker-supplied in a forged (non-GitHub) request, nothing enforces that they refer to the same repository. A genuine GitHub-origin payload always keeps these consistent, but an attacker forging the whole HTTP request is free to make them diverge.

This breaks the intended binding: **organization whose signature was verified == repository the engine subsequently writes/acts on**.

### Impact Explanation
An unprivileged attacker (no Shipit session, no `ApiClient` token, no `webhook_secret` knowledge) can:
- Bypass webhook authentication entirely for any repository, as long as the Shipit instance has at least one configured organization with no `webhook_secret` set (a supported, non-default-enforced configuration).
- Cause the engine to process forged `push`, `status`, `check_suite`, `pull_request`, or `membership` events for a *different, secured* organization's repository, e.g. triggering `GithubSyncJob` for an arbitrary `Stack`, injecting fabricated commit statuses, or manipulating `Team`/`Membership`/`User` records — all without ever proving knowledge of that organization's actual webhook secret.
- This constitutes an authentication bypass on the webhook ingestion path and can lead to unauthorized state changes (stack sync, statuses, review-stack/merge state) for repositories the attacker has no legitimate relationship with.

### Likelihood Explanation
Requires only that the Shipit deployment has multiple configured GitHub Apps/organizations and that at least one has no `webhook_secret` set — a configuration explicitly supported and exercised in the project's own multi-org test fixtures. No credentials, sessions, or tokens are needed; the attacker only needs the public `/webhooks` URL.

### Recommendation
- Verify the webhook signature using the organization actually associated with the `Stack`/`Repository` being modified (resolved server-side), not a value read from the unverified request body.
- Do not allow `verify_webhook_signature` to silently succeed for organizations without a configured secret when the payload could reference a different, secured organization; either require a secret for all configured GitHub Apps or bind verification strictly to a trusted per-repository lookup rather than payload content.
- After verification, re-validate that every organization/repository reference used later in the handler chain matches the organization whose secret validated the request.

### Proof of Concept
1. Configure Shipit with two GitHub Apps (as in `test/dummy/config/secrets_double_github_app.yml`): `OrgOne` (has `webhook_secret`) and `OrgTwo` (no `webhook_secret`).
2. Attacker sends, with no valid signature knowledge:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef

{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. `repository_owner` resolves to `"OrgTwo"`; `Shipit.github(organization: "OrgTwo").verify_webhook_signature` returns `true` because `OrgTwo` has no `webhook_secret`, regardless of the bogus `X-Hub-Signature`.
4. `create` re-parses the body and dispatches to the `push` handler using `repository.full_name = "OrgOne/victim-repo"`, causing Shipit to enqueue a sync/status update for a stack belonging to the properly-secured `OrgOne`, without ever validating `OrgOne`'s webhook secret.

**Uncertainty note:** I was unable to open `app/models/shipit/webhooks/handlers/push_handler.rb` and `app/models/shipit/repository.rb` directly in this session (tool errors on the final iteration) to confirm the exact downstream lookup/write logic beyond what is inferable from `test/controllers/webhooks_controller_test.rb` (which shows `full_name` alone drives `GithubSyncJob` enqueue/stack resolution) and the grep results showing these files reference `full_name`. A Devin session with full file access would be needed to confirm the precise downstream write path and whether any handler re-derives/cross-checks the organization before acting.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
