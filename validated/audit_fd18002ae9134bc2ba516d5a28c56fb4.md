### Title
Cross-organization write via webhook signature/routing field mismatch - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC secret) is used to authenticate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`), while every webhook `Handler` resolves the repository/stack to act on using a completely different field, `repository.full_name`. Because the HMAC signature only proves that *some* configured organization's secret was used to sign the raw body — not that the acting-repository field is consistent with the authenticating-organization field — a party who legitimately controls one configured GitHub organization's webhook secret can forge a payload that authenticates as their own org but drives handler logic against a stack belonging to a different organization/repository.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GithubApp` config (and its `webhook_secret`) using: [1](#0-0) 

That signature check only covers "is this payload's raw body signed with the secret belonging to whatever organization `repository.owner.login` claims to be." It does not bind the signature to `repository.full_name`, which is the field every downstream `Handler` actually uses to select the target `Repository`/`Stack`: [2](#0-1) 

For example `PushHandler` looks up stacks purely via `stacks` (derived from `repository.full_name`) and, for matching non-archived stacks on the pushed branch, calls `stack.sync_github(expected_head_sha: params.after)`: [3](#0-2) 

The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository actually acted upon (repository.full_name)`

Because these are two independent, attacker-influenceable JSON fields inside the same signed body, and the signature only certifies "signed by Org X's secret," not "every field is internally consistent with Org X," a caller who legitimately knows Org X's `webhook_secret` (e.g., they are the admin of the GitHub App they registered for Org X in Shipit's multi-org config) can post a payload where `repository.owner.login == "OrgX"` but `repository.full_name == "OrgY/some-repo"`. The signature check passes because it is computed over the raw body using OrgX's secret and OrgX's own login matches `repository_owner`; the handler then resolves and acts on OrgY's stack.

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated versus repository written," matching the explicitly named class of analog in the assignment rules. Depending on which handler fires, the practical impact ranges from:
- `PushHandler` triggering `stack.sync_github` on a stack that does not belong to the authenticating organization — refreshing/rewriting commit history state for a repository the caller does not control, and, if the target stack has continuous deployment enabled, this sync is the exact trigger that schedules the next deploy in `Shipit::Stack` (continuous-deploy scheduling lives in `app/models/shipit/stack.rb`, confirmed present via `continuous_deployment`/`schedule_next_deploy` methods there). That amounts to an unauthorized deploy of another organization's stack initiated by a party who only controls a different organization's webhook credential.
- Other handlers (`CheckSuiteHandler`, `MembershipHandler`, `PullRequest::*Handler`) similarly trust `repository.full_name`/`organization.login` payload fields without any re-validation that they match the org whose secret produced the valid signature, so team membership, PR/review-stack, and check-run state for a foreign org's stack can be manipulated the same way.

This satisfies the "cross-repository writes" / "unauthorized deploy" impact bar defined in scope.

### Likelihood Explanation
Exploitability requires the attacker to know a `webhook_secret` for at least one organization configured in Shipit's multi-org `github:` block — which is not a Shipit session, `ApiClient` token, or GitHub App private key, and is explicitly the credential an org owner configures themselves for their own installation. Any entity operating a legitimate, but lower-trust, organization onboarded into the same Shipit instance (a very common Shipit deployment pattern per `docs/setup.md`'s "Using Multiple GitHub Applications" section) can exploit this without needing access to any other organization's secrets, satisfying the "organization that authenticated versus the repository that is written" boundary crossing called out in the rules. The likelihood is therefore Medium-to-High in any multi-org deployment, and the vulnerability is deterministic (no race condition, no guessing beyond knowing a target repo's `full_name`, which is public GitHub information).

### Recommendation
After a signature is verified for organization `repository_owner`, re-validate that every repository/organization identifier used downstream (`repository.full_name`'s owner segment, or `organization.login` in org-scoped events) is actually owned by the same organization/App installation that produced the valid signature, rejecting the webhook (422) otherwise. Concretely, derive the owning org from `repository.full_name.split('/').first` and require it to equal `repository_owner`/`organization.login` before dispatching to any `Handler`.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `OrgX` (attacker-administered) and `OrgY` (victim, with a stack tracking `OrgY/private-repo`, continuous deployment enabled).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen or replayed sha>",
  "repository": { "owner": { "login": "OrgX" }, "full_name": "OrgY/private-repo" }
}
```
3. Attacker computes `sha1=HMAC(webhook_secret_OrgX, raw_body)` and sets it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgX")`, which succeeds because the signature was computed with `OrgX`'s own secret — verification passes. [4](#0-3) 
5. `PushHandler#process` resolves `stacks` via `repository_name = payload.dig('repository', 'full_name')` = `"OrgY/private-repo"` and calls `sync_github(expected_head_sha: ...)` on `OrgY`'s stack, potentially cascading into an unauthorized deploy if continuous deployment is enabled — despite the request only ever being authenticated as `OrgX`. [2](#0-1)
