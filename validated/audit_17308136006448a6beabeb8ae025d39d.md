## Title
Cross-tenant commit-status forgery bypasses deploy safety checks – webhook signature is verified against the sender's own GitHub organization while `StatusHandler` writes a `Status` to any commit matching the SHA, with no repository/stack scoping ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC against using `repository_owner`, a field taken straight from the untrusted payload (`repository.owner.login` or `organization.login`). Once the signature check passes, the `status` event is dispatched to `StatusHandler`, which looks up the target `Commit` **solely by SHA**, with no check that the commit belongs to a stack/repository owned by the organization whose secret was used to authenticate the request. The authenticated identity (the org whose webhook secret validated the signature) and the object actually written to (any commit anywhere in the Shipit instance sharing that SHA) are two different, uncorrelated bindings — mirroring the H-2 pattern where a value used for one purpose (`p` selects the market/deposit path) diverges from the value relied upon elsewhere (`principalToken(u, m)` mint) without a consistency check tying them together.

## Finding Description
- `WebhooksController#verify_signature` picks the app/secret with `Shipit.github(organization: repository_owner)` and `repository_owner` is derived from the JSON body itself (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`): [1](#0-0) [2](#0-1) 
- Shipit explicitly supports multiple independent GitHub App configurations, one per organization, each with its own `webhook_secret` (`docs/setup.md`, `lib/shipit.rb#github_app_config`), so a legitimate tenant/organization admin knows their own org's `webhook_secret` by design: [3](#0-2) 
- After signature verification succeeds, `WebhooksController#create` dispatches the parsed body to `Shipit::Webhooks.for_event(event)` handlers, with no further binding of the request to the authenticated organization: [4](#0-3) 
- `StatusHandler#process` looks up commits **only by `sha`**, across the entire instance, and calls `create_status_from_github!` on every match — it never calls the base `Handler#stacks`/`repository_name` scoping that other handlers use: [5](#0-4) 
- Contrast with the base `Handler` class, which most other handlers use to scope lookups to the repository named in the payload — `StatusHandler` bypasses this entirely: [6](#0-5) 
- The resulting `Status` record feeds directly into deploy-gating logic: `Commit#deployable?` requires `success?` and no blocking/required statuses missing, and creating a status schedules merges/continuous delivery: [7](#0-6) 

The binding that should hold is: *the organization whose secret validated the signature* == *the organization/stack that owns the commit being mutated*. Before the attack, this equality holds implicitly because GitHub only ever sends events for repositories that belong to the org where the App is installed. After the attack, an operator who legitimately installed the Shipit GitHub App on their own throwaway organization (knowing that org's `webhook_secret`) can compute a valid `X-Hub-Signature` for a forged `status` payload whose `sha` is copied from a public commit in a completely different, victim-owned stack. `StatusHandler` will happily attach a forged `success` status (or fail/error, causing DoS-adjacent denial of deploy, though the higher-impact direction is fabricating `success`) to that victim commit.

## Impact Explanation
This is an unauthorized-deploy-enabling vulnerability: `Commit#deployable?` and the merge/CD scheduling logic treat the forged `Status` as legitimate CI signal ( [8](#0-7) ). An attacker who only controls a separate, unrelated GitHub organization (with the Shipit App installed there, as documented for multi-tenant setups) can:
- fabricate a passing CI status for a victim stack's commit, satisfying `required_statuses`/`blocking_statuses` checks and enabling that commit to be deployed or merged via the merge queue, or
- fabricate a failing/error status to block a victim's legitimate deploy pipeline.

This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope, and the resulting effect (bypassing deploy-gating checks to enable an unauthorized deploy/merge) matches the defined High-impact category.

## Likelihood Explanation
Likelihood is moderate: the attacker needs (a) the Shipit instance configured with multi-organization GitHub App support (documented, supported feature) or knowledge of any org's `webhook_secret` that is registered with the instance, and (b) the target commit's SHA, which is public information on GitHub. No privileged Shipit session, `ApiClient` token, or the victim org's own secret is required — only a valid signature for *any* org known to the Shipit instance. This does not require guessing secrets or bypassing HMAC verification itself; it exploits the fact that a correctly-signed webhook for org A is trusted to mutate data belonging to org B because `StatusHandler` never re-checks repository ownership.

## Recommendation
Have `StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`) constrain the update to commits belonging to stacks whose repository matches `repository_owner`/`repository.full_name` from the same payload, rather than matching by SHA alone across the entire instance. Concretely, use `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })`-style scoping (leveraging `Handler#stacks`) instead of a global `Commit.where(sha: params.sha)`, and reject/ignore the event if the target commit's repository does not match the organization that authenticated the webhook.

## Proof of Concept
1. Set up (or already control) a second, unrelated GitHub organization/tenant `AttackerOrg` with the Shipit GitHub App installed, per the documented multi-org configuration — the attacker legitimately knows `AttackerOrg`'s `webhook_secret`.
2. Identify the SHA of a commit in the victim's tracked stack (public on GitHub), e.g. `sha = "abc123..."`.
3. Craft a `status` event payload:
   ```json
   {
     "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/throwaway" },
     "sha": "abc123...",
     "state": "success",
     "context": "ci/required-check",
     "description": "forged",
     "created_at": "2026-09-01T00:00:00Z"
   }
   ```
4. Compute `X-Hub-Signature: sha1=HMAC-SHA1(AttackerOrg_webhook_secret, raw_body)`.
5. POST to `/github/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner => "AttackerOrg"`, looks up `Shipit.github(organization: "AttackerOrg")`, and the signature validates successfully.
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (unrelated org/stack), and calls `commit.create_status_from_github!(params)`, attaching a forged `success` status that can satisfy `required_statuses`/`blocking_statuses` and enable deploy/merge of that commit.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
