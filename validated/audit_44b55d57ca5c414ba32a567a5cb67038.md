### Title
Unbounded recursive walk over `shared_address_signing_paths` in `readAllControlAddresses` can loop forever on a cyclic shared-address definition sent by a paired device - ([File: wallet_defined_by_addresses.js])

### Summary
`readAllControlAddresses` in `wallet_defined_by_addresses.js` recursively walks the `shared_address_signing_paths` table to collect every member ("control") address that ultimately controls a set of shared addresses, so that private-payment chains can be forwarded to all of them. The recursion assumes the member-address graph is acyclic (a DAG terminating at leaf key-addresses), exactly like the hickory-proto NSEC3 bug assumed the QNAME-to-SOA walk always terminates at an ancestor. Unlike the sibling functions in the codebase that solve the same problem (`readSharedAddressesDependingOnAddresses` in `balances.js`, `readAdditionalSigningAddresses` and `readWalletsByAddresses` in `wallet.js`), which explicitly compute `_.difference`/`NOT IN` against already-visited addresses before recursing, `readAllControlAddresses` performs no such de-duplication or visited-set check.

### Finding Description [1](#0-0) 

```
function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
```

Each recursive call re-queries `shared_address_signing_paths` for whatever addresses were just returned, with no accumulator of already-visited addresses and no depth cap. The loop's only termination condition is `rows.length === 0`, i.e. it assumes that walking "up" the member-address graph always eventually reaches leaf key addresses (a bare `address_definition`/no-signing-path record). If the local `shared_address_signing_paths` table ever contains a cycle — e.g. shared address `A` lists member address `B`, and `B` (recorded locally as a shared address too, via `handleNewSharedAddress`) lists member address `A` — the query for `A` returns `B`, the query for `B` returns `A`, and so on forever. This directly parallels the hickory-proto bug: a structural assumption ("the walk always converges on an ancestor/leaf") that a remote party can falsify by supplying crafted data, absent any explicit termination bound.

Contrast with the protected sibling implementations that solve an identical problem safely: [2](#0-1) [3](#0-2) 

Both of these compute `_.difference(newAddresses, alreadyKnownAddresses)` and stop recursing once no new addresses appear, which is exactly the missing safeguard in `readAllControlAddresses`.

`shared_address_signing_paths` rows are populated from data received from **paired devices** via `handleNewSharedAddress`/`createNewSharedAddress` (the wallet "shared address" and multi-device wallet protocol), so a correspondent device that a victim has paired with can construct or influence a shared-address definition whose member-address graph is cyclic (member addresses forming a loop through nested shared-address templates/definitions), causing this local table to contain the cyclic edges once the shared address is accepted.

### Impact Explanation
`readAllControlAddresses` is invoked whenever private-payment chains need to be forwarded to the members of a shared address that received a private payment: [4](#0-3) 

If the recursion never terminates, `forwardPrivateChainsToOtherMembersOfSharedAddresses` (and thus the whole private-payment forwarding/acceptance pipeline for shared/multi-sig addresses) never completes its callback. Because it runs under a mutex-protected private-payment handling path, this stalls processing of that private chain indefinitely and burns CPU/DB-query resources for every invocation, which is a resource-exhaustion / hang condition on the victim's node/wallet triggered purely by data a paired device supplied — directly analogous to the "attacker returns a response, node loops/exhausts resources" pattern in the reported advisory. It does not by itself cause fund loss, double-spend, or consensus disagreement, since it is a local/wallet-side helper, not part of unit/AA validation consensus rules.

### Likelihood Explanation
Reaching this requires only a device pairing relationship (a "paired device" per the allowed reach list) and the ability to define/propose a shared address whose signing-path graph is cyclic. This is plausible but not fully proven: I could not verify within the available index whether `handleNewSharedAddress`/definition validation elsewhere (e.g., `Definition.validateDefinition`, which does enforce `MAX_COMPLEXITY`/depth limits on the *definition* itself) would reject a shared-address definition that would produce a locally-stored cyclic `shared_address_signing_paths` edge set before `readAllControlAddresses` is ever invoked. I was not able to inspect `handleNewSharedAddress`'s body (it was not returned by search/read calls) to confirm whether it independently checks for cycles in the assembled `shared_address_signing_paths` rows it inserts. This is a meaningful gap: if `handleNewSharedAddress` already rejects self-referential/cyclic member graphs, the recursive query itself is unreachable with cyclic data and the bug is latent/defense-in-depth only.

### Recommendation
Add a visited-set (accumulator of already-seen addresses) to `readAllControlAddresses`, mirroring the pattern already used in `readSharedAddressesDependingOnAddresses` and `readAdditionalSigningAddresses`: before recursing, compute `_.difference(arrControlAddresses, arrAddresses already known)` and stop once the difference is empty, and independently verify (or add, if missing) that `handleNewSharedAddress` rejects shared-address definitions that would create a cycle in the member-address graph.

function readSharedAddressesDependingOnAddresses(arrMemberAddresses, handleSharedAddresses){
	var strAddressList = arrMemberAddresses.map(db.escape).join(', ');
	db.query("SELECT DISTINCT shared_address FROM shared_address_signing_paths WHERE address IN("+strAddressList+")", function(rows){
		var arrSharedAddresses = rows.map(function(row){ return row.shared_address; });
		if (arrSharedAddresses.length === 0)
			return handleSharedAddresses([]);
		var arrNewMemberAddresses = _.difference(arrSharedAddresses, arrMemberAddresses);
		if (arrNewMemberAddresses.length === 0)
			return handleSharedAddresses([]);
		readSharedAddressesDependingOnAddresses(arrNewMemberAddresses, function(arrNewSharedAddresses){
			handleSharedAddresses(arrNewMemberAddresses.concat(arrNewSharedAddresses));
		});
	});
}

				OR \n\
				EXISTS (SELECT 1 FROM shared_addresses WHERE shared_addresses.shared_address=shared_address_signing_paths.address) \n\

			) \n\
			AND ( \n\
				NOT EXISTS (SELECT 1 FROM addresses WHERE addresses.address=shared_address_signing_paths.address) \n\
				OR ( \n\
					SELECT definition IS NULL \n\
					FROM address_definition_changes CROSS JOIN units USING(unit) LEFT JOIN definitions USING(definition_chash) \n\
					WHERE address_definition_changes.address=shared_address_signing_paths.address AND is_stable=1 AND sequence='good' \n\
					ORDER BY level DESC LIMIT 1 \n\
				) = 1 \n\
			)";
	var arrParams = [arrFromAddresses];
	if (arrSigningAddresses.length > 0){
		sql += " AND address NOT IN(?)";
		arrParams.push(arrSigningAddresses);
	}
	if (arrSigningDeviceAddresses && arrSigningDeviceAddresses.length > 0){
		sql += " AND device_address IN(?)";
		arrParams.push(arrSigningDeviceAddresses);
	}
	db.query(
		sql, 
		arrParams,
		function(rows){
			var arrAdditionalAddresses = rows.map(function(row){ return row.address; });
			if (arrAdditionalAddresses.length === 0)
				return handleAdditionalSigningAddresses([]);

				handleAdditionalSigningAddresses(arrAdditionalAddresses.concat(arrMoreAddresses));

	);
