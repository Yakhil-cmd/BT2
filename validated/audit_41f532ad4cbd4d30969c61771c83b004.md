## Title
Unauthenticated `creator` identity field in `initialize_with_permission` allows permanent freezing of pool creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` records the pool's `pool_creator` identity from an `UncheckedAccount` that is never required to sign the transaction and is never constrained to equal the `payer` or any other verified identity. This mirrors the CVE-2025-55292 bug class in Meshtastic, where an identity attribute (the HAM-mode flag on a `NodeInfo`) is accepted and permanently trusted without cryptographic proof that the claimed identity actually authored it. Here, the `creator` field that becomes the pool's permanent `pool_creator` PDA-authority record is likewise accepted with no signature or ownership proof, letting a permissioned pool creator "impersonate"/assign an arbitrary, unauthenticated address as the pool's creator identity.

### Finding Description
In `InitializeWithPermission`, the `creator` account is declared as a plain `UncheckedAccount`, not a `Signer`, and carries no `constraint` tying it to `payer` or to any signed value: [1](#0-0) 

Only the `payer` is a `Signer`, and the permission PDA check is keyed off `payer`, not `creator`: [2](#0-1) 

The handler then commits this unauthenticated `creator.key()` directly as `pool_state.pool_creator`, an immutable, permanent field of `PoolState`: [3](#0-2) [4](#0-3) 

By contrast, the non-permissioned `Initialize` handler correctly requires `creator: Signer<'info>`, proving the codebase's own convention is that pool-creator identity must be cryptographically authenticated: [5](#0-4) 

Downstream, `pool_creator` is treated as an authoritative identity in both fee-collection instructions. `collect_creator_fee` requires the `creator` signer to match `pool_state.pool_creator` (a dead end if no one holds the key), while `collect_creator_fee_permissionless` unconditionally creates an ATA owned by whatever `pool_creator` value was recorded and transfers all accrued `creator_fees_token_0`/`creator_fees_token_1` there, with no verification that this address is ever spendable: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
A permission-holder invoking `initialize_with_permission` can set `creator` to any arbitrary pubkey with no known private key (e.g., an off-curve/unrenderable point, an address it does not control, or someone else's identity used without consent). Because `enable_creator_fee` is set to `true` for permissioned pools and creator fees accumulate on every swap, all creator fees are irrecoverably routed via `collect_creator_fee_permissionless` into an ATA whose authority nobody can sign for, while `collect_creator_fee` (which requires the recorded `creator` to sign) can never succeed either. This permanently and unilaterally freezes pool creator-fee funds, and, independently, forges the pool's recorded "creator" identity without any proof of authorization from that address, analogous to the unauthenticated identity/flag spoofing described in the reference report.

### Likelihood Explanation
Any actor holding a `Permission` PDA (a pool-creation permission grantee) can trigger this in a single `initialize_with_permission` transaction by simply supplying an unauthenticated pubkey for `creator`, with no additional signature, cross-check, or admin approval required at that step.

### Recommendation
Require `creator` in `InitializeWithPermission` to be a `Signer` (as already done in `Initialize`), or explicitly constrain it (`constraint = creator.key() == payer.key()` or an authenticated allow-list) so that `pool_creator` can never be set to an address that has not affirmatively authorized being recorded as the pool's creator.

### Proof of Concept
1. Obtain a `Permission` PDA for `payer` via `create_permission_pda` (admin-granted).
2. Call `initialize_with_permission` supplying `payer` as signer and an arbitrary unauthenticated pubkey (e.g., an address with no known keypair) as `creator`; the instruction succeeds because `creator` requires no signature (`programs/cp-swap/src/instructions/initialize_with_permission.rs:26-27`).
3. `pool_state.pool_creator` is permanently set to this address (`programs/cp-swap/src/states/pool.rs:134-152`).
4. As swaps accrue `creator_fees_token_0/1`, call `collect_creator_fee_permissionless`; funds are transferred into an ATA owned by the unspendable `creator` address (`programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs:91-123`), and `collect_creator_fee` can never succeed since no one can sign as that `creator` (`programs/cp-swap/src/instructions/collect_creator_fee.rs:10-13`), permanently freezing those funds.

```rust
pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;
```
