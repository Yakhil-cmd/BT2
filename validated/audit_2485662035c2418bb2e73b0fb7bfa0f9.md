## Analysis Result

I traced the external "owner's share not deducted" bug down to a single invariant class: **a validated/committed value (fee/approval hash) that gate a privileged action but that can be bypassed when an optional binding is absent or gated behind a feature flag**. I generated and evaluated four local candidates:

1. `multisig_account::validate_multisig_transaction` payload-mismatch gap (feature-gated stored-payload check).
2. `transaction_validation.move::prologue_common` sponsored-account-creation auth key substitution logic.
3. `TransactionAuthenticator::verify` fee-payer "sign over zero address OR real address" dual-acceptance.
4. `EncryptedPayload::as_encrypted_variant`/`try_into_decrypted` binding of decrypted plaintext to ciphertext commitment.

Candidate 1 is the strongest with a concrete, provable root cause in local code, so I report it.

### Title
Multisig transaction execution can run an unapproved payload when no payload hash was committed and the mismatch check is feature-gated — ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction`, the VM-invoked prologue for multisig execution, only verifies the caller-supplied `payload` against the on-chain `payload_hash` when `transaction.payload_hash.is_some()`. When the payload was created via `create_transaction` (which stores the raw payload on-chain, not a hash), the additional integrity check that the supplied `payload` argument equals the stored `transaction.payload` is wrapped in `features::abort_if_multisig_payload_mismatch_enabled()`. If that feature is disabled (or not yet enabled on a given network), an owner can call the multisig entry function with an arbitrary `payload` argument different from the approved, on-chain-stored payload, and the prologue will not reject it.

### Finding Description [1](#0-0) 

The prologue performs two independent checks depending on how the transaction was created:
- If `payload_hash` is set (hash-only creation path), it hashes the caller-supplied `payload` and compares to the stored hash — this path is always enforced.
- If the full `payload` was stored on-chain (`transaction.payload.is_some()`), the equality check between the caller-supplied `payload` and the stored payload is only performed `if (features::abort_if_multisig_payload_mismatch_enabled() && transaction.payload.is_some() && !payload.is_empty())`.

This means the binding between "what owners approved via votes" and "what code the VM will actually execute" depends on a feature flag rather than being an unconditional invariant. The owners' votes (`approve_transaction`) are recorded against a `sequence_number`, not against the payload content itself — the payload is fetched separately via `get_next_transaction_payload`, which prefers the caller-provided `provided_payload` argument whenever the stored transaction has no `payload_hash` requirement bound to it and the feature is off: [2](#0-1) 

So an owner with sufficient approvals for sequence number N can submit a completely different `payload` at execution time than the one that was originally proposed and voted on, and — unless `abort_if_multisig_payload_mismatch_enabled` is on — the VM prologue will accept it and execute the unapproved payload.

### Impact Explanation
This breaks the "approval set must bind to the executed action" admission invariant explicitly listed in the pivots ("Authenticator ... multisig, or approval validation accepting the wrong signing material or wrong approval set"). Votes are recorded per `sequence_number`, and the actual bytes executed are not cryptographically bound to those votes when the feature flag is off, allowing execution of a transaction the quorum never approved. This could let a single quorum-authorized executor swap in a different call (e.g., different recipient/amount/module) than what was voted on by the other owners, effectively defeating the entire multisig approval guarantee — a high-impact confused-execution primitive, gated purely by an on/off feature flag rather than an unconditional protocol rule.

### Likelihood Explanation
Likelihood depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active on a given deployment/genesis. If any network (testnet, devnet, or a chain that hasn't yet enabled this specific feature) has it disabled, the bypass is trivially reachable by any account that already qualifies as an owner and possesses (or colludes to obtain) enough approvals for the sequence number — no cryptographic material or replay tricks required, just calling the multisig entry function with a different `payload` argument.

### Recommendation
Make the stored-payload vs. supplied-payload equality check unconditional (remove the feature gate), or, better, always require that transactions created via `create_transaction` (i.e., where the payload is stored on-chain) execute the stored `transaction.payload` directly rather than trusting a caller-supplied `payload` argument at all. The commitment (hash or stored payload) that owners vote against must always be the actual bytes executed, independent of feature-flag state.

### Proof of Concept
1. Deploy/observe a network where `abort_if_multisig_payload_mismatch_enabled` feature is not yet enabled (default state pre-flag-activation).
2. Owner A calls `multisig_account::create_transaction(owner, multisig_account, payload_A)` — payload stored on-chain, no hash-only mode (`payload_hash` is `none`).
3. Owners vote and reach quorum via `approve_transaction` for that `sequence_number` (voting only references the sequence number, not payload bytes).
4. An owner who is the executor calls the multisig entry point supplying `payload_B` (any different call, e.g. differing amount/target) instead of `payload_A`.
5. `validate_multisig_transaction` skips the mismatch assertion (`abort_if_multisig_payload_mismatch_enabled()` is false), `transaction.payload_hash.is_none()` so the hash check is also skipped — the prologue passes and `payload_B` executes as if it had been approved by quorum.

**Uncertainty note:** I could not confirm from the indexed code the actual on-chain/genesis default value of `abort_if_multisig_payload_mismatch_enabled` for mainnet (only its definition in `features.move` and `aptos_features.rs` was found, not the specific initialization value at genesis or current mainnet feature-flag state). This determines whether the bypass is live on production Aptos or only a residual code path guarding an already-rolled-out fix. If the user needs the exact current activation status, a Devin session with access to the full repository/genesis config would be needed to confirm.
