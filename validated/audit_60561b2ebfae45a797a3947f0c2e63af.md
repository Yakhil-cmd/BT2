### Title
Unbounded growth of `storage.assocUnstableMessages`/data-feed & vote messages causes DoS on the hot stability-check path - ([File: main_chain.js])

### Summary
Any unprivileged unit poster can attach a `data_feed`, `definition`, `system_vote`, or `system_vote_count` message to a unit. Every such message is kept in the in-memory map `storage.assocUnstableMessages[unit]` until the unit becomes stable [1](#0-0) . This map has no size limit and can be inflated by anyone simply by posting many low-cost units (e.g. `data_feed` messages, which only cost the normal per-message fee) that remain unstable for a while (units near the tip of the DAG, or built to keep low witness confirmation). Several hot-path functions iterate over the *entire* `assocUnstableMessages` map on every stabilization attempt, not just over the units of the particular MCI being stabilized, e.g. `hasUnstableOpVoteCount()` [2](#0-1) , `getUnstableVotes()` [3](#0-2) , and the `get_system_var_votes` request handler [4](#0-3) . This mirrors the reported Sherlock issue where `ProtectionPool.activeProtectionIndexes` grows without bound from user-triggered actions and is fully iterated by `_assessState()`, causing a DoS on a critical, frequently-invoked function.

### Finding Description
`hasUnstableOpVoteCount()` is called from `determineIfStableInLaterUnitsAndUpdateStableMcFlag()`, which runs every time the code attempts to advance the stability point after a new unit is added [5](#0-4) . This function is on the critical path of consensus progression — it decides whether the OP list vote count could change and therefore whether extra per-MCI stability checks are needed. Its cost is `O(total unstable messages across the whole unstable region of the DAG)`, not bounded to a single MCI or a reasonable window.

An attacker (any address, no special privileges) can flood the network with a stream of cheap units that each carry a `data_feed` message (validated only for size/format, no rate limiting beyond normal fees, see `case "data_feed"` in validation.js) [6](#0-5) , or `system_vote`/`system_vote_count` messages, which are similarly open to any author once the v4 upgrade MCI is reached [7](#0-6) . As long as these units remain unstable (which can be prolonged by building them near witnesses/tips or simply by volume outpacing stabilization throughput), their messages accumulate in `assocUnstableMessages`, growing the map that `hasUnstableOpVoteCount()`, `getUnstableVotes()`, and `get_system_var_votes` must fully scan on every call. Because `hasUnstableOpVoteCount()` runs synchronously in Node's event loop on essentially every stabilization attempt, an attacker-inflated map directly increases the CPU time consumed by this hot loop for every node in the network, exactly analogous to the reported bug where an unbounded `activeProtectionIndexes` array is looped over inside `_assessState()`.

### Impact Explanation
Because `hasUnstableOpVoteCount()`/`determineIfStableInLaterUnitsAndUpdateStableMcFlag()` sit on the path that advances main-chain stability, a sufficiently large `assocUnstableMessages` map (grown by a single unprivileged attacker posting many cheap `data_feed`/`system_vote` units) increases the per-unit-addition processing cost for every full node in the network. Repeated abuse can slow down or stall stability advancement network-wide, i.e. the network becomes unable to confirm new units in a timely manner, which matches the "network unable to confirm new units" impact bucket. It does not directly cause fund loss, but it degrades availability of the whole DAG's finality process for all participants, not just the attacker.

### Likelihood Explanation
Likelihood is Medium: any address can post `data_feed`/`system_vote` messages cheaply and repeatedly, and there is no explicit bound on how many unstable units/messages of these types can exist concurrently in `assocUnstableMessages`. The main mitigating factor is that unstable units do eventually stabilize (bounding the backlog to some degree), and per-unit fees impose some cost on the attacker, but nothing in the validation logic caps the number of concurrently-unstable `data_feed`/`system_vote` messages system-wide.

### Recommendation
- Bound the cost of `hasUnstableOpVoteCount()`/`getUnstableVotes()` by tracking a running counter (e.g. increment/decrement a count of unresolved `system_vote_count`/`system_vote` messages as they are added/removed from `assocUnstableMessages`) instead of scanning the entire map on every call.
- Consider imposing a per-address or global rate limit / cap on the number of concurrently unstable `data_feed`, `system_vote`, and `system_vote_count` messages, similar to `MAX_DATA_FEEDS_PER_MESSAGE`, but scoped across units rather than within a single unit.
- Profile and batch the `get_system_var_votes` network handler similarly, since it is exposed to any connected peer and does an unbounded full scan of `assocUnstableMessages` on each request [4](#0-3) .

### Proof of Concept
1. An attacker generates and broadcasts a continuous stream of minimally-valued units, each containing one `data_feed` message (cheap, valid per validation rules) or a `system_vote`/`system_vote_count` message post v4 upgrade.
2. Because unit stabilization requires witness-level confirmations that lag behind unit posting rate, the attacker can keep a large number of such units unstable simultaneously, causing `storage.assocUnstableMessages` to accumulate many entries (bounded only by available bandwidth/fees, not by protocol logic).
3. Every subsequent call to `determineIfStableInLaterUnitsAndUpdateStableMcFlag()` → `hasUnstableOpVoteCount()` [2](#0-1)  now iterates the inflated map, increasing per-unit processing latency network-wide; likewise every `get_system_var_votes` request from any light client triggers a full scan [4](#0-3) .
4. As the attacker continues posting, the cost of these hot-path scans grows roughly linearly with the number of outstanding attacker-controlled unstable messages, degrading node responsiveness and stability-advancement throughput for the whole network.

function hasUnstableOpVoteCount() {
	for (let unit in storage.assocUnstableMessages) {
		for (let message of storage.assocUnstableMessages[unit]) {
			if (message.app === 'system_vote_count' && message.payload === 'op_list')
				return true;
		}
	}
	return false;

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}
