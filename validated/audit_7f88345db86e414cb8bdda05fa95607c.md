## Title
Cross-organization webhook forgery leads to unauthorized commit status injection and deploy triggering - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments, the webhook signature is verified against the GitHub App secret belonging to the organization named in `repository.owner.login`, but the event is then processed and dispatched to handlers using the *entire* raw payload, including `repository.full_name`, `sha`, etc., with no re-validation that those fields belong to the same organization that was authenticated. This breaks the binding: *organization whose secret authenticated the payload* == *repository/commit the payload is allowed to affect*.

### Finding Description
`WebhooksController#verify_signature` selects the signing secret purely from the org embedded in the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` looks up that specific organization's configured webhook secret in a multi-app setup: [3](#0-2) 

Once the signature check passes, the full raw JSON is handed to every registered handler for the event, unmodified: [4](#0-3) 

Handlers resolve which `Stack`/`Repository` to act on independently, using `repository.full_name` — a field that is never cross-checked against the `repository.owner.login` used for authentication: [5](#0-4) 

The `StatusHandler` is the most severe case: it doesn't even scope by repository at all, matching commits globally by `sha`: [6](#0-5) 

An attacker who legitimately controls their own GitHub organization/App (and therefore knows or can trigger requests signed with their own org's `webhook_secret`, configured in `config/secrets.yml` under the multi-org schema) can:
1. Send a `status` webhook whose raw body is signed with **their own org's** secret (satisfies `repository_owner` = their org).
2. Set `sha` inside that same payload to the SHA of a commit belonging to an entirely different, unrelated organization/repository also tracked by the same Shipit instance.

Because `StatusHandler` does `Commit.where(sha: params.sha)` with no ownership check, the forged status is applied to the victim organization's commit.

### Impact Explanation
Applying a forged `success` status to a commit triggers `Commit#add_status`, which can enable continuous deployment scheduling for the victim's stack: [7](#0-6) 

If the victim stack has `continuous_deployment: true`, injecting a fake successful CI status for a target commit results in an **unauthorized deploy** being scheduled for that stack — meeting the "Critical: unauthorized deploy" bar defined by the rules, achieved purely by an attacker who is only authorized within their own tenant/organization inside the same multi-tenant Shipit instance.

### Likelihood Explanation
This requires a Shipit deployment using the documented "Using Multiple Github Applications" multi-org configuration (explicitly supported and documented): [8](#0-7) 
An attacker only needs to be the legitimate operator/admin of one of the participating organizations (i.e., they know their own org's `webhook_secret`, which they configured themselves) — this is not a privileged Shipit credential, an `ApiClient` token, or repository write access to the victim's repo. The attack surface (forging arbitrary JSON body content while keeping a valid HMAC for their own org) is trivial to exploit once the config pattern is used.

### Recommendation
`WebhooksController#verify_signature` (or the handlers) should ensure the organization/owner used to select the verification secret is the *same* organization implied by every field acted upon by handlers (`repository.full_name`, `sha`'s owning stack, etc.). At minimum, `StatusHandler`, `PushHandler`, and other handlers should filter matches by the authenticated `repository_owner`/organization, not merely by `sha` or `full_name` taken from the unauthenticated part of the JSON body.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` and `VictimOrg`, each with its own GitHub App and `webhook_secret` (per the documented multi-org schema).
2. Attacker (owner of `AttackerOrg`) crafts a `status` event JSON body:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/fake",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
3. Attacker signs the raw body with `AttackerOrg`'s known `webhook_secret` and sends it to `/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `AttackerOrg`, verifies successfully against `AttackerOrg`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: "<victim_commit_sha>")`, finds the commit belonging to `VictimOrg`'s stack, and creates a `success` `Status` on it, potentially triggering `ContinuousDeliveryJob` for `VictimOrg`'s stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

  github:

      webhook_secret:
      private_key:
      oauth:
        id:
        secret:

    someothergithuborg:
