### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized merges - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` matches incoming GitHub `status` webhooks by raw commit SHA across the *entire* `commits` table, without scoping to the repository that signed the webhook. Because commit SHAs are shared across forks/mirrors of the same repository history, an attacker who owns any repository sharing commit ancestry with a victim's stack can emit a legitimate, correctly-signed `status` webhook from their own repo that creates a `success` `Status` row attached to the victim stack's commit, which feeds directly into `Commit#deployable?` and `MergeRequest#all_status_checks_passed?`, potentially causing an unauthorized merge.

### Finding Description
The broken binding: `Status` rows consulted by `MergeRequest#all_status_checks_passed?` for stack `S`'s head commit must have been created from a webhook whose `payload.dig('repository','full_name') == S.repository.full_name`; instead the actual code enforces only `Commit.sha == params.sha`, with no repository check at all.

`StatusHandler#process`: [1](#0-0) 
does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. This is a raw, unscoped query against the global `commits` table. Contrast this with the base `Handler` class, which provides a `stacks` helper explicitly scoped by `repository_name` derived from the webhook payload: [2](#0-1) 
`StatusHandler` never calls `stacks` — it is the only handler in this family that resolves target records purely by content-addressed SHA rather than by the repository identified in the payload.

Because `commits` has only a `(sha, stack_id)` unique index (not a global unique-on-sha constraint): [3](#0-2) 
the same SHA can legitimately exist as separate `Commit` rows under multiple different stacks — this happens naturally whenever a repository is forked/mirrored, since forks share git history and thus share SHAs for all commits prior to divergence (and any commit that is later merged back).

`create_status_from_github!` creates the `Status` scoped to `commit.stack_id` — i.e., the *matched* commit's own stack, not the stack that owns the repository which sent the webhook: [4](#0-3) 
This status creation runs inside `add_status`, which (on a state change to `success`/`pending`) calls `stack.schedule_merges`, enqueuing `ProcessMergeRequestsJob` for the *victim's* stack: [5](#0-4) 

`ProcessMergeRequestsJob` then revalidates and merges any pending `MergeRequest` whose head passes `all_status_checks_passed?`: [6](#0-5) 
`MergeRequest#all_status_checks_passed?` and `#need_revalidation?` read `head.statuses_and_check_runs` and `revalidated_at`: [7](#0-6) 
`Commit#deployable?` similarly relies purely on `status`/`success?`, derived from the same unscoped `statuses` association: [8](#0-7) 

Exploit flow: attacker forks or otherwise controls a repository that is also tracked as a Shipit stack and shares commit ancestry (a common base commit, or any commit later merged/rebased into both histories) with a victim's stack. Attacker triggers (or GitHub itself triggers, e.g. via CI on the attacker's own fork) a `status` webhook for that shared SHA with `state: success`. This webhook is correctly signed by GitHub using the attacker's own organization's legitimate webhook secret, so `verify_signature` passes: [9](#0-8) 
`StatusHandler` then attaches the forged success status to *every* `Commit` row sharing that SHA, including the row belonging to the victim's stack, causing `ProcessMergeRequestsJob` to run and potentially merge a `MergeRequest` on the victim's stack — right at the moment its `revalidate_merge_requests_after` timer causes `need_revalidation?` to become true and `refresh!`/`reject_unless_mergeable!`/`all_status_checks_passed?` to be (re)evaluated.

Existing guards do not stop this: `verify_signature` only authenticates that the payload came from *some* legitimate GitHub organization/app installation, not that the referenced commit belongs to that organization's repository. `drop_unhandled_event` and `ExplicitParameters` schema only validate shape, not repository ownership. No model validation ties `Status#stack_id` to the repository identified in the webhook payload.

### Impact Explanation
A `Status` record (and downstream merge/deploy eligibility signals) can be written for a stack that never authenticated the webhook that created it — this is exactly "a payload for one repository mutating another's stack/commit," and can culminate in an unauthorized merge of a victim's pull request, matching the Critical severity bucket. The attack is repeatable against any stack whose repository shares commit history (fork/mirror relationship) with a repository the attacker controls, and the attacker can time the forged status to line up with `revalidate_merge_requests_after` boundaries to force merges that would otherwise be rejected as stale/failing.

### Likelihood Explanation
Preconditions: (1) the victim stack's tracked repository must share at least one commit SHA with a repository the attacker owns or controls webhooks for (trivially achievable by forking the victim repo — shared ancestor commits retain identical SHAs), (2) the merge queue must be enabled on the victim stack with a `merge.revalidate_after` configured, and (3) a pending `MergeRequest` must exist whose `head` matches (or is later rebased/cherry-picked to) the colliding SHA. Cost to the attacker is low: forking a public repo and configuring/triggering a webhook or CI status on the fork requires no privileged Shipit access, no secrets, and no maintainer role — only ability to own a repository and emit its `status` events, which is explicitly in-scope per the threat model.

### Recommendation
Scope `StatusHandler#process` (and any commit-lookup based purely on SHA) to the repository identified in the webhook payload, mirroring the `stacks`/`repository_name` pattern used by other handlers — e.g., resolve target commits via `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before matching commits by SHA, rather than querying the global `Commit` table unscoped.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks/repositories, `victim_stack` (tracking `victim/repo`) and `attacker_stack` (tracking `attacker/repo`), each with a `Commit` row sharing the identical `sha` (simulating shared fork ancestry).
2. Create a pending `MergeRequest` on `victim_stack` whose `head` is the shared-SHA commit, with `merge.revalidate_after` configured and `revalidated_at` set so that, at test time, `need_revalidation?` is about to flip true.
3. Freeze time at the revalidation boundary (`travel_to(pr.revalidated_at + timeout + 1.second)`).
4. Post a `status` webhook payload with `repository.full_name = 'attacker/repo'` and the shared `sha`, `state: 'success'`, stubbing signature verification for the attacker's org only (no victim secrets used).
5. Assert: before the request, `Status.where(stack_id: victim_stack.id, commit_id: shared_commit.id).exists?` is `false`, and `merge_request.all_status_checks_passed?` is `false`/`merge_request.pending?` unmet.
6. After posting the webhook and running `ProcessMergeRequestsJob.perform_now(victim_stack)`, assert `Status.where(stack_id: victim_stack.id, commit_id: shared_commit.id, state: 'success').exists?` is `true` and `merge_request.reload.merged?` is `true` — proving a forged, attacker-repo-originated status caused a merge on `victim_stack` that no webhook signed by `victim/repo`'s organization ever authorized.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end

    def all_status_checks_passed?

    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    end
