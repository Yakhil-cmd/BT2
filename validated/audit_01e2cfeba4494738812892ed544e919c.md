### Title
Webhook signature verification is scoped to an attacker-chosen organization field that is never cross-checked against the repository/commit actually written by the event handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a payload against using `repository_owner`, a value read directly out of the *unverified* JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`). The actual state-changing work performed by the event `Handler` subclasses operates on a **different** field of the same body (`repository.full_name` for push, or nothing at all — a bare `sha` — for status). Nothing binds "the organization whose secret validated this signature" to "the repository/commit that gets written." An operator of any organization configured on the Shipit install (including one that simply left `webhook_secret` blank, which the docs explicitly treat as optional) can forge events that write to a completely unrelated, higher-value repository/stack.

### Finding Description [1](#0-0) 
`verify_signature` picks the `GitHubApp` instance (and therefore the secret used for HMAC verification) via `repository_owner`: [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when no secret is configured for that organization: [3](#0-2) 

Once "verified" (or trivially passed because the chosen org has no secret), the raw `params` are handed unmodified to the handlers: [4](#0-3) 

The base `Handler` resolves the target repository using a *different* JSON field, `repository.full_name`, which is never required to match the `repository.owner.login`/`organization.login` field used for signature-key selection: [5](#0-4) 

`PushHandler` uses that unscoped `full_name` lookup to sync arbitrary stacks: [6](#0-5) 

`StatusHandler` is worse: it doesn't even consult a repository field — it matches purely on `sha` across the entire `Commit` table, with zero scoping to any repository or organization: [7](#0-6) 

**The broken binding, as an equality:**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` ≠ `repository/commit actually mutated by the handler (repository.full_name for push, or nothing — global sha lookup — for status)`.

Before the attack: an operator with legitimate webhook-admin rights on Org A (a low-value/unprivileged org registered on the same multi-tenant Shipit instance, or any org whose `webhook_secret` was left blank) can only affect Org A's stacks.
After the attack: by setting `repository.owner.login`/`organization.login` = "OrgA" (to select a secret they control or that doesn't exist) while setting `repository.full_name` = "victim-org/victim-repo" (push) or simply reusing a known `sha` that belongs to a victim commit (status), they cause Shipit to write state (sync jobs, `Status` rows) against a stack/commit they have no relationship to.

### Impact Explanation
`Status` rows created via `StatusHandler` are read by `ci.require`/`ci.allow_failures` deploy gating logic (documented in `README.md`) to decide whether CI is green enough to permit a deploy or PR merge. Because the handler looks up the target commit purely by `sha` with no repository/organization scoping at all, and the org used to authorize the webhook payload is never checked against the repository actually referenced, an attacker who only controls webhook configuration for one low-trust org on the installation can forge a "success" status (with attacker-chosen `context`, `description`, `target_url`) onto a commit belonging to an entirely different, higher-value stack — causing Shipit to consider that stack's CI green and permitting an **unauthorized deploy**. `PushHandler` similarly lets such an attacker trigger sync/build activity against arbitrary stacks by forging `repository.full_name`. This falls under the explicitly in-scope "unauthorized deploy" / cross-repository-write impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to produce a payload that passes `verify_webhook_signature` for *some* configured organization — which the docs and fixtures show is explicitly optional (`webhook_secret: # nil`). In any multi-org Shipit deployment where at least one configured org has no webhook secret set (a documented, supported configuration), any unauthenticated internet requester can pick that org's name for `repository.owner.login`/`organization.login`, bypass verification unconditionally, and then supply arbitrary `full_name`/`sha` values targeting a different repository/commit. No Shipit session, `ApiClient` token, or GitHub App private key is required — only knowledge of an org name configured on the instance with a blank secret, or legitimate (but unprivileged relative to the victim repo) webhook-admin access to one org among many on a shared install.

### Recommendation
- In `Handler#repository_name` / each handler, cross-check that the `repository.full_name` owner (and for status events, the commit's actual repository) matches the organization whose secret validated the signature (`repository_owner` from `WebhooksController`); reject the event otherwise.
- For `StatusHandler`, scope the `Commit` lookup to commits belonging to the verified organization/repository instead of a global `sha` match.
- Consider making `webhook_secret` mandatory (or at minimum, refuse to trivially pass verification for organizations lacking one) rather than defaulting to `true` in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. On a Shipit instance configured with two GitHub orgs, `orgA` (attacker has webhook-admin rights, or `orgA.webhook_secret` is left unset/nil) and `orgB` (victim, hosts `orgB/prod-app` with `ci.require: ["ci/tests"]`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<known sha of a commit on orgB/prod-app pending deploy>",
  "state": "success",
  "context": "ci/tests",
  "organization": { "login": "orgA" },
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/throwaway-repo" }
}
```
signed (or unsigned, if `orgA` has no secret) such that `Shipit.github(organization: "orgA").verify_webhook_signature` returns `true`.
3. `WebhooksController#create` passes the raw `params` to `StatusHandler`, which executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — writing a forged `success` status onto the `orgB/prod-app` commit despite the signature only ever having been checked against `orgA`'s key.
4. Shipit's CI-gating logic on `orgB/prod-app` now sees `ci/tests` as green, enabling an unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
