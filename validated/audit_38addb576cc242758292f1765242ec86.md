### Analysis

CVE-2017-11590 is a NULL-pointer dereference in a hashing helper (`caseless_hash`) that is invoked on attacker-supplied data without adequate guard/exception handling, causing an unrecoverable crash on a single crafted input. The closest analog in this codebase is a hashing helper — `getUnitHashToSign` / `getSourceString` — that is invoked on unit data supplied by an unprivileged unit poster **without the exception handling that every other caller of the same function uses**.

`getSourceString` in [1](#0-0)  explicitly `throw`s a plain `Error` (not something recoverable) whenever it encounters a `null` value, an empty array/object, a non-finite number, an "undefined" field, or an embedded `\x00` byte in a string/key while walking an arbitrary nested object — i.e. it is designed to blow up on malformed input, similar in spirit to a crash-on-bad-input hashing routine.

`objectHash.getUnitHashToSign(objUnit)` calls this exact function on the full (naked) unit object, including the `messages` array and fields such as `earned_headers_commission_recipients`, `tps_fee`, `oversize_fee`, `burn_fee`, `max_aa_responses`: [2](#0-1) .

Every other place in the codebase that calls `getUnitHashToSign` / `getSignedPackageHashToSign` wraps the call in `try/catch` because the authors anticipated it can throw on attacker-controlled data:
- `signed_message.js`: [3](#0-2) 
- `validation.js` (`validateAuthorSignaturesWithoutReferences`): [4](#0-3) 

However, the primary, network-reachable call site inside `validateAuthors()`, which runs for every posted unit during normal consensus validation, has **no try/catch**: [5](#0-4) 

Compare this with `validate()`'s own unit-hash check a few lines earlier, which *is* guarded: [6](#0-5) 

Critically, for a normal serial unit (no `content_hash`), `getUnitHash` at line 133 computes the hash via `getStrippedUnit()`, which does **not** include `messages`, `earned_headers_commission_recipients`, `tps_fee`, `oversize_fee`, `burn_fee`, or `max_aa_responses`: [7](#0-6) . So the earlier, guarded hash computation never exercises `getSourceString`/`getJsonSourceString` over those fields. The first time those fields (together with the full message objects, not just their `payload` sub-object) are fed into `getSourceString` is inside the **unguarded** `getUnitHashToSign` call in `validateAuthors`.

This is a structural asymmetry: a hashing routine that is known (by the developers, evidenced by the try/catch used everywhere else) to throw on malformed/attacker-influenced data is invoked on the unprotected code path that runs for every unit received from the network/an unprivileged poster.

### Title
Unhandled exception in `getUnitHashToSign` during author validation causes unit-validation crash - (File: validation.js)

### Summary
`validateAuthors()` calls `objectHash.getUnitHashToSign(objUnit)` without a `try/catch`, unlike every other call site of the same hashing helper in the codebase. The underlying `getSourceString`/`getJsonSourceString` routines intentionally `throw` on malformed nested data (null values, empty containers, non-finite numbers, embedded NUL bytes) that is not guaranteed to be excluded by prior checks on message-level and unit-level fields.

### Finding Description
`getUnitHashToSign` builds a serialized "source string" from the full unit content (minus authentifiers) via `getSourceString`/`getJsonSourceString`, both of which throw plain `Error`s when they walk into a null value, empty array/object, or invalid number anywhere in the object graph [1](#0-0) . This function is called on attacker-controlled unit content at `validation.js:1142`, inside `validateAuthors`, which is invoked for every unit submitted for validation (posted units, AA triggers producing/consuming payment messages, etc.) [8](#0-7) .

Every sibling call site of `getUnitHashToSign`/`getSignedPackageHashToSign` is defensively wrapped in `try/catch` because the authors anticipated exceptions from crafted input [9](#0-8) [10](#0-9) . The `validateAuthors` call site is the exception (pun intended) — it has no guard.

For units with `content_hash` (nonserial/stripped units), the same object shape is already exercised earlier via a guarded `getNakedUnit`-based hash at line 133, so an exception would be caught earlier as `ifJointError`/`ifUnitError`. But for ordinary serial units, the earlier guarded hash check uses `getStrippedUnit()`, which strips out `messages`, `earned_headers_commission_recipients`, `tps_fee`, `oversize_fee`, `burn_fee`, and `max_aa_responses` [7](#0-6) . These fields (and the full message *objects*, not merely their `payload` sub-objects, which are separately hashed elsewhere) are first run through the throw-happy `getSourceString` at the unguarded call in `validateAuthors`.

### Impact Explanation
If any field that reaches `getUnitHashToSign` unguarded contains a value that trips one of `getSourceString`'s throw conditions (a `null`, an empty array/object, or a `\x00` byte in a nested string that survived prior format/type checks), the thrown `Error` propagates out of an asynchronous validation callback instead of being converted into a graceful `ifUnitError`/`ifJointError`. An uncaught exception thrown inside a Node.js callback chain like this crashes the running process. Since every full node runs this exact validation path on every unit it receives (from posted units, catchup, or AA trigger processing), a single crafted unit propagated to the network can crash every node that attempts to validate it — a network-wide denial of service that prevents new units from being confirmed, matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
Reaching this code path requires only posting an ordinary unit (or crafting an AA-trigger consequence) that passes the unit's structural/type checks earlier in `validate()` but still contains a disallowed value (e.g., `null`) in a field that is included in `getNakedUnit()`'s serialization but was not exercised by the earlier `getStrippedUnit()`-based hash for serial units. This is reachable by any unprivileged unit poster without special permissions, satisfying the reachability requirement. Exact confirmation of a concrete field/value combination that both (a) passes all prior explicit field validations and (b) still trips `getSourceString`'s throw conditions was not fully re-derived in this analysis due to the depth of per-message-app validation logic (validateMessages ordering relative to validateAuthors was not fully traced); this should be verified with an implementation review/PoC before treating this as fully confirmed.

### Recommendation
- Wrap the `objectHash.getUnitHashToSign(objUnit)` call in `validateAuthors()` (`validation.js:1142`) in a `try/catch`, mirroring the pattern already used in `signed_message.js` and `validateAuthorSignaturesWithoutReferences`, and return `callback("failed to calc unit hash to sign: " + e)` on failure instead of letting the exception propagate.
- More broadly, audit all `getSourceString`/`getJsonSourceString`/`objectHash.*` call sites reachable from network-supplied data to ensure every one is guarded, since these functions are documented (by their own throw statements) to reject malformed nested data by throwing rather than returning an error value.

### Proof of Concept
Conceptual (not independently reproduced against a running node in this session): craft and broadcast a unit whose `messages` array or top-level fee/commission fields include a value that is well-formed enough to pass the field-by-field checks in `validate()` prior to `validateAuthors()` (e.g., prior to reaching the per-message `app`-specific payload validators), but that contains a `null`, an empty nested array/object, or an embedded NUL byte in a string once serialized via `getNakedUnit()`. Submitting such a unit to the network would cause `validateAuthors()` on every receiving node to call the unguarded `getUnitHashToSign`, throw inside the async validation callback, and crash the node process — repeated for every node that processes the unit, since it is never wrapped in try/catch at that call site.

function getSourceString(obj) {
	var arrComponents = [];
	function extractComponents(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				if (variable.includes(STRING_JOIN_CHAR))
					throw Error("00 byte in string value in " + JSON.stringify(obj));
				arrComponents.push("s", variable);
				break;
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
				arrComponents.push("n", variable.toString());
				break;
			case "boolean":
				arrComponents.push("b", variable.toString());
				break;
			case "object":
				if (Array.isArray(variable)){
					if (variable.length === 0)
						throw Error("empty array in "+JSON.stringify(obj));
					arrComponents.push('[');
					for (var i=0; i<variable.length; i++)
						extractComponents(variable[i]);
					arrComponents.push(']');
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0)
						throw Error("empty object in "+JSON.stringify(obj));
					keys.forEach(function(key){
						if (typeof variable[key] === "undefined")
							throw Error("undefined at "+key+" of "+JSON.stringify(obj));
						if (key.includes(STRING_JOIN_CHAR))
							throw Error("00 byte in object key in " + JSON.stringify(obj));
						arrComponents.push(key);
						extractComponents(variable[key]);
					});
				}
				break;
			default:
				throw Error("getSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	extractComponents(obj);
	return arrComponents.join(STRING_JOIN_CHAR);
}
