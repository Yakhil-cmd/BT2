## Title
Webhook organization used for signature verification is not bound to the repository the payload mutates, allowing cross-org stack takeover via `check_suite` (and other handlers) - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify a webhook against using `payload.dig('repository','owner','login')`, while `Handler#stacks` resolves the target repository using `payload.dig('repository','full_name')`. These two payload fields are never checked for consistency, so an attacker who controls an org configured in Shipit with no `webhook_secret` set can name their own org for signature verification and an arbitrary victim `repository.full_name` for the mutation target.

### Finding Description
The broken binding: the question asks whether `Shipit.github(organization: verified_org).webhook_secret` being blank implies the org that "verified" the request equals the org that owns the mutated repository. It does not — `repository_owner` (verification key) and `repository_name` (mutation key) are read from two independent, attacker-controlled JSON fields with no cross-check.

- `WebhooksController#verify_signature` picks the app config by `repository_owner`: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org's config: [3](#0-2) 

- `Handler#stacks` (used by `CheckSuiteHandler#process`) resolves the repository from a *different* payload field, `repository.full_name`, with no relation to `repository_owner`: [4](#0-3) [5](#0-4) 

- `Repository.from_github_repo_name` does a straight `owner`/`name` lookup with no ownership assertion tying it back to the verified org: [6](#0-5) 

Exploit flow: attacker owns/controls a GitHub org ("attacker-org") that is a legitimately configured entry in Shipit's `github:` YAML (so `Shipit.github(organization: 'attacker-org')` resolves without raising `GithubOrganizationUnknown`) but has `webhook_secret` blank for that org (this is a documented supported configuration per `config/secrets.development.shopify.yml` and `docs/setup.md`'s multi-org example, and is even the default in `template.rb`'s generated secrets). The attacker POSTs directly to `/webhooks` with header `X-Github-Event: check_suite` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "check_suite": { "head_sha": "<victim commit sha>", "head_branch": "<victim branch>" }
}
```
`repository_owner` resolves to `"attacker-org"` → `verify_webhook_signature` returns `true` regardless of (or absent) `X-Hub-Signature` because that org's `webhook_secret` is blank. The request passes `before_action :verify_signature`. `CheckSuiteHandler#process` then calls `stacks`, which uses `repository_name` = `"victim-org/victim-repo"` from the payload's `full_name`, looks up the real victim `Repository`, and iterates its `Stack` records, calling `schedule_refresh_check_runs!` on victim commits matching the attacker-supplied `head_sha`/`head_branch`.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type is registered; `verify_signature` only checks the signature against the org named by `repository.owner.login`, not against the org implied by `repository.full_name`; there is no `ExplicitParameters` schema field validating that `repository.full_name`'s owner segment matches `repository.owner.login`; `CheckSuiteHandler`'s params schema only requires `check_suite.head_sha`/`head_branch`, not any repository/owner consistency.

### Impact Explanation
An attacker who controls one Shipit-configured GitHub org with a blank `webhook_secret` can trigger `schedule_refresh_check_runs!` (which enqueues `RefreshCheckRunsJob`, refreshing check-run state from GitHub and driving CI-gated actions in Shipit) against any other tenant's `Stack`/`Commit` records, purely by naming that other org's repository in the `full_name` field. This is a cross-repository/cross-tenant mutation of another organization's stack state without ever holding a valid signature for that repository's real webhook secret — an authentication-bypass-class issue matching the "Critical: payload for one repository mutating another's stack" category. It is fully repeatable against any repository name the attacker chooses to spoof, for every configured org that has a blank `webhook_secret`.

### Likelihood Explanation
Preconditions: the attacker must control (or have events emitted for) at least one GitHub organization that a Shipit operator has configured in the `github:` YAML with no `webhook_secret` set for that specific org entry — a configuration explicitly documented and shown as the default/example in this repo (`config/secrets.development.shopify.yml`, `docs/setup.md`, `template.rb`). No Shipit session, API token, or private key is needed; the attacker just crafts a raw HTTP POST to `/webhooks`. This is low-cost and trivially repeatable against arbitrary victim repositories tracked by the same Shipit instance.

### Recommendation
Bind webhook verification to the same repository the handler will act on: derive `repository_owner` for `verify_signature` from the same `repository.full_name` used later by `Handler#repository_name`/`stacks` (or vice versa), and reject the webhook if `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, consider treating a blank `webhook_secret` for a configured org as a hard misconfiguration warning rather than an automatic signature pass, or requiring an explicit opt-in flag to allow unsigned webhooks per org.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "check_suite payload naming attacker-org for verification but victim repo full_name mutates victim's stacks" do
  # attacker-org configured in Shipit with blank webhook_secret
  attacker_app = Shipit::GitHubApp.new('attacker-org', { webhook_secret: nil })
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(attacker_app)

  victim_stack = shipit_stacks(:shipit) # owned by victim-org/victim-repo per fixtures
  victim_commit = shipit_commits(:first)
  victim_stack.update!(branch: 'master')
  victim_commit.update!(sha: 'deadbeef')

  body = {
    action: 'requested',
    check_suite: { head_sha: 'deadbeef', head_branch: 'master' },
    repository: {
      owner: { login: 'attacker-org' },
      full_name: victim_stack.repository.github_repo_name # "victim-org/victim-repo"
    }
  }.to_json

  request.headers['X-Github-Event'] = 'check_suite'
  # no X-Hub-Signature header sent at all

  assert_enqueued_with(job: RefreshCheckRunsJob, args: [commit_id: victim_commit.id]) do
    post :create, body:, as: :json
    assert_response :ok # signature check passed despite attacker-controlled org
  end
end
```
Both sides of the binding diverge: `Shipit.github(organization: 'attacker-org')` (verified org) ≠ `Repository.from_github_repo_name('victim-org/victim-repo').owner` (mutated org), proving the exploit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
