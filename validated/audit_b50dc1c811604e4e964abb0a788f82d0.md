### Title
Uncaught exception on duplicate co-author address in nested `address` definition causes full-node crash - (File: definition.js)

### Summary
`validateDefinition()`'s handling of the `address` definition subtype (`case 'address':`) throws a raw, unguarded `Error` instead of returning it via the `cb` callback when it finds more than one author in the unit matching the referenced address/chash. Because this happens inside an async callback (`storage.readDefinitionByAddress`'s `ifDefinitionNotFound` handler), the thrown exception is not caught by the surrounding `try/catch` in the same function and propagates as an uncaught exception. [1](#0-0) 

### Finding Description
When an address definition contains a nested `["address", "OTHERADDR"]` element (an unprivileged, standard oscript construct any unit author or AA/attestation definition composer can use), `evaluate()` calls `storage.readDefinitionByAddress`. If the referenced address has never been defined before, the `ifDefinitionNotFound` branch looks for co-authors in the *same unit* whose `address` matches `other_address` and whose declared `definition`'s chash matches the not-yet-known chash: [2](#0-1) 

The `try/catch` in this block only guards the `.filter()` call (line 288–295) for hashing errors; the subsequent `if (arrDefiningAuthors.length > 1) throw Error("more than 1 address definition")` (line 298) is unprotected. If a unit's `authors` array contains two entries with the same `address` and same `definition` (which would both pass the `.filter()` predicate), this line throws synchronously inside an async I/O callback with no enclosing `try/catch` and no caller-side `.catch()` — this is a classic Node.js uncaught-exception crash vector. [3](#0-2) 

The unit passes through the normal `validate(objJoint, callbacks, external_conn)` entry point that every posted joint goes through, i.e., this is reachable by any unprivileged unit poster who crafts a unit with a nested address-definition referencing an address defined twice among the unit's own `authors`.

I was not able to fully confirm, within the available tool budget, whether an earlier validation step in `validation.js` (author list processing before `validateDefinition` is invoked) already rejects duplicate `author.address` entries in the `authors` array. If such a check exists and runs strictly before the definition-evaluation stage, this specific trigger path would be blocked. I found `authors.length`-related checks in `validation.js` but did not have the chance to read their exact logic to confirm duplicate-address rejection before the exception-throwing code is reached.

### Impact Explanation
If reachable, this is a node-crashing bug (`throw` outside protective error handling), matching the CVE-2026-46863 bug class of "unauthenticated attacker ... frequently repeatable crash (complete DoS)" — here specifically a DoS against every full node that validates the malicious unit (broadcast is unauthenticated and requires no special privilege), potentially halting the network's ability to confirm new units if repeated broadcast targets many/most nodes simultaneously.

### Likelihood Explanation
Medium-High if the duplicate-author precondition is reachable: crafting a unit with two co-authors sharing an address and definition is a purely client-side unit-composition task requiring no privileged keys beyond normal unit posting capability. This directly maps to the "unprivileged unit poster" threat actor allowed by the scan rules.

### Recommendation
Replace the `throw Error("more than 1 address definition")` at definition.js:298 with `return cb("more than 1 address definition")` (matching the error-handling convention used everywhere else in this function), and additionally add an explicit duplicate-author-address check earlier in unit validation (in `validation.js`, before definitions are evaluated) if one does not already exist, to reject units with duplicate `authors[i].address` entries outright.

### Proof of Concept
Conceptual (not verified end-to-end due to the unconfirmed precondition above):
1. Craft a unit with two entries in `authors`, both with `address = "AAAA...AAAA"` (a never-before-used address) and identical `definition` arrays, such that `objectHash.getChash160(author.definition)` equals `"AAAA...AAAA"`.
2. Have a definition elsewhere in the unit (e.g., a third author's or an AA definition) reference `["address", "AAAA...AAAA"]`.
3. Post the unit to the network; when `validateDefinition` reaches the `address` case for this reference and finds the address not yet defined in storage, it filters `objUnit.authors` and finds 2 matches, hitting the unguarded `throw Error(...)`, crashing the validating node process.

**Caveat**: I could not confirm within budget whether earlier author-array validation in `validation.js` already blocks step 1 (duplicate author addresses) before this code path is reached. If such a guard exists, this specific PoC would be prevented and the analog would not hold. I recommend a Devin session with full codebase access to trace the exact `authors` validation order in `validation.js` and confirm reachability before treating this as confirmed-exploitable.
