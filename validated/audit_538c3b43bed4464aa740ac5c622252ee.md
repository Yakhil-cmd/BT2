### Title
Malicious swap route can add an extra wallet-token transfer to the victim’s authorization tree - ([File: contracts/controller/src/strategies/swap_collateral.rs](contracts/controller/src/strategies/swap_collateral.rs))

### Summary
`swap_collateral` lets the account owner supply an arbitrary router payload, while route-selected pool code can invoke a token transfer from that same caller. [1](#0-0) [2](#0-1)   
When simulation records the malicious transfer beneath the caller’s `swap_collateral` authorization, signing that tree authorizes both the intended strategy and the unrelated wallet transfer. [3](#0-2) 

### Finding Description
`process_swap_collateral` authenticates `caller`, verifies that the caller owns or delegates the account, and forwards the caller-provided `swap` payload to `withdraw_and_swap_from_supply`. [1](#0-0)   
The controller protects only its own input token by authorizing one exact transfer to the configured router and later checking the controller’s measured spend. [4](#0-3)   
The router independently authenticates `sender`, pulls `total_in`, decodes the payload, and dispatches the route-selected `pool`, `token_in`, and `token_out` addresses without an allowlist. [5](#0-4) [2](#0-1)   
For example, the Soroswap adapter invokes `get_reserves` and `swap` on the payload-selected pool address. [6](#0-5)   
A malicious pool can therefore call `unrelated_token.transfer(victim, attacker, amount)` while still beneath the victim’s root authorization; the test demonstrates that simulation records this as a child of `swap_collateral` and that enforcement succeeds when that poisoned tree is signed. [7](#0-6) [8](#0-7) 

### Impact Explanation
The attacker can steal any unrelated token held by the victim’s wallet, not merely the collateral committed to the swap. [9](#0-8) [10](#0-9)   
The controller’s exact input-transfer authorization and router output checks do not bound this separate transfer because it targets the caller rather than the controller. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
Exploitation requires the victim to submit an attacker-crafted route and sign the expanded authorization tree returned by simulation, so this is not fully permissionless theft without user authorization. [13](#0-12) [8](#0-7)   
The route itself can name an attacker-controlled pool because the pool address is supplied by the payload and dispatched without a trusted-pool check. [2](#0-1) [14](#0-13)   
This warrants Medium severity: high-value wallet theft is possible, but successful exploitation depends on the victim signing a visibly poisoned authorization tree. [12](#0-11) 

### Recommendation
Prevent untrusted route contracts from executing under the caller’s authorization by restricting route pools to a governance-managed venue registry, or introduce a routing mode whose signed authorization tree cannot be extended with unrelated caller-token transfers. [2](#0-1) [14](#0-13)   
Until contract-level isolation exists, clients and wallets must decode every simulated authorization tree and reject any strategy that contains children beyond the expected input transfer. [12](#0-11) 

### Proof of Concept
1. The victim owns a funded lending account and holds an unrelated `WALLET_TOKEN`. [15](#0-14) 
2. The attacker deploys a route-compatible pool whose `swap` calls `WALLET_TOKEN.transfer(victim, attacker, amount)`. [16](#0-15) 
3. The attacker gives the victim a `swap_collateral(victim, account_id, usdc_asset, amount, eth_asset, malicious_route)` transaction whose route selects that pool. [17](#0-16) 
4. Simulation records the rogue wallet transfer as a child of the victim’s `swap_collateral` authorization. [18](#0-17) 
5. If the victim signs that returned tree, the transaction completes the collateral swap while transferring the victim’s entire unrelated wallet balance to the attacker. [19](#0-18)

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
```

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
