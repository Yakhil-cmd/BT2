Confirmed: `Handler#stacks` and `Handler#repository_name` derive the acted-upon repository purely from `payload.dig('repository', 'full_name')` — a field never cross-checked against `repository_owner` (the field used to *select which org's secret* verified the request).### Title
Webhook signature is verified against a GitHub org selected from an attacker-controlled payload field, but every handler resolves the target Stack from a *different* attacker-controlled payload field, allowing a valid signature from one configured organization to write to any other organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization deployments (`Shipit.github_organizations`, see `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` chooses which GitHub App's `webhook_secret` to validate against using `repository_owner`, which is read straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')` or the `organization.login` fallback). [1](#0-0) [2](#0-1)  Once the HMAC check passes, `WebhooksController#create` hands the *entire same JSON body* to every registered handler for the event. [3](#0-2)  All handlers (`Handler#stacks`/`Handler#repository_name`, used by `PushHandler`, the `PullRequest::*Handler`s, etc.) resolve the affected `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a completely independent field from the one used to pick the verification secret. [4](#0-3) 

### Finding Description
The binding that should hold is: **organization whose secret authenticated the request == organization owning the repository the handler mutates**. That binding is never enforced:

1. `repository_owner` (used only to pick `Shipit.github(organization: repository_owner)` / the HMAC secret) comes from `repository.owner.login` or `organization.login`. [2](#0-1) 
2. `Handler#repository_name` (used to find the `Stack`/`Repository` that gets written to) comes from `repository.full_name`. [5](#0-4) 
3. Nothing checks that `repository.full_name` actually starts with `repository.owner.login`, or that the resolved `Repository`'s owner matches `repository_owner`.

Because the whole raw JSON body is attacker-supplied (only the HMAC signature is proven, not any consistency between JSON fields), an attacker who knows/controls the `webhook_secret` for **any one** organization configured on the Shipit instance (e.g. because they administer that org's own GitHub App installation and set its webhook secret) can craft a payload where:
- `repository.owner.login` = the org they control (used to select the secret that validates the HMAC),
- `repository.full_name` = a repository belonging to a *different*, unrelated organization also hosted on the same Shipit instance,

sign the raw body with their own known secret, and POST it to `/webhooks`. `verify_signature` succeeds because it only checked the org derived from `repository.owner.login` against its own secret; `PushHandler`/`StatusHandler`/etc. then act on the `Stack` whose repository matches `repository.full_name`, i.e., the victim org's repository. [6](#0-5) 

The `PushHandler` triggers `stack.sync_github(expected_head_sha:)`, which asynchronously syncs commits from the *actual* GitHub repository using the app's own installation token (`Shipit.github(organization:).api`), so the direct payload isn't blindly trusted for commit content — but the attacker still controls *which stack* gets a forced resync and, via `StatusHandler`, can directly write arbitrary CI status entries (`Commit#create_status_from_github!`) against commits of a repository they don't own, since `StatusHandler` never re-derives/re-checks the owning org at all. [7](#0-6) 

This is the direct analog of the report's underlying pattern: a value used for one purpose (selecting/validating an authorization boundary) is trusted to also gate a materially different, more consequential action (which resource is written), while the two values are not provably the same and the code never re-derives the second from a source proven equal to the first.

### Impact Explanation
This falls under "High - unauthenticated read of stack state... " territory but arguably closer, in the worst handler (`StatusHandler`), to a cross-repository write of commit status data belonging to an org the attacker does not control — using only knowledge of a webhook secret that is scoped to a *different* organization. This crosses the organization boundary that `Shipit.github(organization:)` is meant to enforce per-tenant. Because the exploit only requires knowing one org's own legitimately-configured webhook secret (an artifact any org admin using this multi-tenant Shipit instance possesses) and not any credential belonging to the victim organization, it is an unauthorized cross-repository write and matches the "cross-repository writes" Critical category, or at minimum the High "escalation into authorization" category, depending on how much state the specific handler mutates.

### Likelihood Explanation
Requires: (a) the Shipit instance is configured for multiple GitHub organizations (an explicitly documented, supported configuration in `docs/setup.md`), and (b) the attacker legitimately controls the webhook secret of at least one of those organizations (which is normal for any org onboarded onto a shared/multi-tenant Shipit deployment). No GitHub App private key, no `ApiClient` token, and no `Shipit` session are needed — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a body signed by a secret the attacker legitimately possesses for their own org. This is a realistic misuse scenario in the documented multi-org feature, though it is not exploitable in the single-organization default configuration (where `repository_owner` selection is moot, since there is only one secret).

### Recommendation
After signature verification, re-derive the organization from the *same* trusted `repository.owner.login`/`organization.login` value used for verification, and require that every handler's target `Repository`/`Stack` actually belongs to that organization (e.g., compare `Repository#owner` against `repository_owner`, or scope `Handler#stacks` to `Repository.where(owner: repository_owner)`), rejecting/ignoring any webhook where the two disagree.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` and `OrgB` (as in `test/dummy/config/secrets_double_github_app.yml`), each with its own `webhook_secret`, both hosting stacks on the same Shipit instance.
2. As an admin of `OrgB` (attacker), you legitimately know `OrgB`'s `webhook_secret` (you configured the GitHub App yourself).
3. Craft a JSON body: `{"repository": {"owner": {"login": "OrgB"}, "full_name": "OrgA/victim-repo"}, "sha": "<known sha in OrgA's stack>", "state": "success", ...}`.
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgB_webhook_secret, raw_body)>`.
5. POST to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `"OrgB"`, loads `OrgB`'s `GitHubApp`, and the signature validates successfully (since it was computed with `OrgB`'s own secret over this exact body). [1](#0-0) 
7. `StatusHandler#process` runs unconditionally against `Commit.where(sha: params.sha)`, which resolves to a commit belonging to `OrgA`'s stack (via `repository.full_name`), and writes a forged CI status onto it — despite the request only ever being authenticated for `OrgB`. [8](#0-7)
