### Title
Webhook signature is verified against an attacker‑chosen organization, but the acted‑upon commit/repository is taken unchecked from the same payload — enabling cross‑organization forged CI status - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC against using a value taken directly from the *unverified* request body: `repository_owner` is `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), and that string is fed straight into `Shipit.github(organization: repository_owner)` before the signature has been checked. [1](#0-0) [2](#0-1) 

This means the *only* thing the signature proves is "this payload was signed with the webhook secret belonging to whatever organization login string appears in `repository.owner.login`" — an attacker who legitimately administers Organization A (and thus legitimately knows Organization A's `webhook_secret`, configured in this Shipit instance's `github` config, see `test/dummy/config/secrets_double_github_app.yml` for the documented multi-org configuration pattern) can put `repository.owner.login = "OrgA"` in the JSON body and sign the *entire raw body* with Organization A's secret. Signature verification passes. [3](#0-2) 

Once verified, `WebhooksController#create` dispatches the full, attacker-authored payload to the relevant `Shipit::Webhooks::Handlers` class. [4](#0-3) 

`StatusHandler#process`, however, does not re-derive or re-check "which organization does this commit/repository belong to" at all — it looks up commits **globally, by `sha` only**, with no scoping to the repository/organization that was actually used to authenticate the request: [5](#0-4) 

More generally, the base `Handler` class resolves the stacks/repository to act on from `payload.dig('repository', 'full_name')` — a field inside the same attacker-controlled JSON body, completely independent from the `repository.owner.login` field that was used to pick the verification secret: [6](#0-5) 

This is structurally the same bug class as the reported `calcStableBorrowBalance` issue: two related quantities that must move together (the field cryptographically authenticated, and the field the business logic actually acts on) are allowed to diverge, because the code trusts an attacker-supplied value to select the verification key and then trusts a *different* attacker-supplied value inside the same envelope for the privileged action. The broken equality is:

`organization used to select/verify webhook_secret (payload["repository"]["owner"]["login"])` ≠ `organization/repository actually mutated (payload["repository"]["full_name"], or — for `status` events — no organization check at all, just a global `sha` match)`

### Impact Explanation
Any party who is a legitimate GitHub organization admin able to configure their own GitHub App/webhook secret in this shared Shipit install (a normal, unprivileged position relative to *other* onboarded organizations) can:
- Forge a `status` webhook event, signed with their own org's secret, containing the `sha` of a real commit belonging to a different, victim organization's stack (commit SHAs are public information on GitHub) and `state: success`, `context` matching that stack's `ci.require` context. `StatusHandler` will create a passing `CommitStatus` on that victim commit with no ownership check, since lookup is purely `Commit.where(sha: params.sha)`.
- If the victim stack has `continuous_deployment: true` and depends on that CI context being green (a documented, common configuration, see `ci.require` in `README.md`), this forged status can unlock/trigger an automatic deploy that the victim organization never authorized — an **unauthorized deploy**, which is explicitly listed as a Critical impact for this program.
- The same organization‑vs‑repository mismatch also affects other handlers (`push`, `pull_request/*`) which resolve `Repository.from_github_repo_name`/`stacks` purely from the unverified `repository.full_name` field, letting a signed-but-mismatched payload trigger `GithubSyncJob`, PR-label-driven merge-queue actions, etc. against a repository/stack the attacker's org has no relationship to.

### Likelihood Explanation
Requires the attacker to control at least one legitimate GitHub App installation/webhook secret already configured on the target Shipit instance (i.e., be an onboarded-but-unprivileged organization relative to other tenants of the same install) — this is exactly the kind of "unprivileged attacker breaking a trust binding between two entities that should move together" the scan is looking for, and does **not** require a Shipit session, `ApiClient` token, `api_clients_secret`, GitHub App private key, or repository write access to the victim repo. Any multi-tenant Shipit deployment (multiple `github` orgs configured, as documented and tested in `secrets_double_github_app.yml`) is exposed; even a single-tenant install is exposed to the weaker "global sha lookup ignoring repository" variant of `StatusHandler`.

### Recommendation
- In `WebhooksController#verify_signature`, do not select the verification secret from an unverified payload field alone; after verifying, re-derive the acted-upon repository/organization strictly from the same trusted source used for verification, and reject the request if the `repository.full_name` referenced by the handler does not belong to the organization whose secret validated the signature.
- In `Shipit::Webhooks::Handlers::Handler` (and specifically `StatusHandler`), scope all lookups (`Commit.where(sha: ...)`, `Repository.from_github_repo_name`) to the repository/organization that was cryptographically verified for this request, not to whatever `repository.full_name` string appears in the JSON body.

### Proof of Concept
1. Shipit instance configured with two orgs, `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim, has a stack with `continuous_deployment: true` and `ci.require: ["ci/tests"]`).
2. Attacker crafts:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sha": "<public sha of OrgB's pending commit>",
  "state": "success",
  "context": "ci/tests"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#repository_owner` reads `"OrgA"`, `Shipit.github(organization: "OrgA")` returns the attacker's own legitimately-configured app, `verify_webhook_signature` succeeds. [1](#0-0) 
5. `StatusHandler#process` finds `Commit.where(sha: ...)` for OrgB's commit (no ownership check) and creates a passing status on it. [5](#0-4) 
6. If OrgB's stack was waiting on that CI context to go green for continuous deployment, this triggers an unauthorized deploy.
