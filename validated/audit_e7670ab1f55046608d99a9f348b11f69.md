### Title
Unbounded formula-string length allows Earley-parser CPU exhaustion via crafted AA definition/messages - (File: formula/common.js, formula/validation.js, aa_validation.js)

### Summary
`ocore`'s oscript/ojson formulas are parsed with the `nearley` library, which implements Earley parsing — the exact parser family called out in the xgrammar advisory as regressing to minutes-long processing on large-but-legal inputs. In `ocore`, any AA message payload, `init`, `if`, `getters`, `attestors`, or asset `cap`/`denominations` field that is recognized as a formula (`getFormula()` in `formula/common.js:82-93`, which merely checks for `{...}` wrapping) is handed unmodified to `nearley.Parser.feed()` in `formula/validation.js:249-266` and later `formula/evaluation.js:104-121`, with no upper bound on formula string length prior to parsing.

### Finding Description
The AA definition validator (`aa_validation.js`) recurses through the whole AA definition object (`validate()`, lines 598-710) and, for every string that `getFormula()` recognizes as a formula, calls `formulaValidator.validate()` (`aa_validation.js:535-573`), which immediately parses the string with `nearley.Parser.fromCompiled(grammar).feed(formula)` (`formula/validation.js:254-255`) before any complexity/op-count checks are applied — those checks (`MAX_COMPLEXITY`, `MAX_OPS` in `constants.js:67`) only run against the parsed AST *after* parsing succeeds. There is no explicit cap on the raw formula string length at this validation entry point (unlike the address-definition `'formula'` op which is capped at 10000 characters, `definition.js:599`).

The whole AA definition (and thus all its formulas combined) is only bounded indirectly by `constants.MAX_UNIT_LENGTH` (5,000,000 bytes, `constants.js:59`), since an AA definition is posted inside a unit. This still permits a single formula string, or the aggregate of many formula fields across many messages, on the order of megabytes — several orders of magnitude larger than the ~100KB-plus grammar that caused the referenced minutes-long parsing delay in xgrammar. Because the oscript grammar (`formula/grammars/oscript.ne` / `oscript.js`) contains numerous left-recursive rules for binary/associative constructs (`or_expr`, `and_expr`, `AS`, `MD`, chained comparisons, `expr_list`), a crafted formula consisting of long chains of these constructs (e.g., thousands of chained `+`/`or`/string-concat terms, analogous in spirit to the PoC's many enum options) can drive the Earley parser into its worst-case behavior, which for ambiguous/left-recursive grammars can scale super-linearly with input length.

Every node in the network that validates a newly posted unit containing an AA definition (or an AA trigger where the same nearley-based parsing/evaluation runs, `formula/evaluation.js:104-121`) must run this parse to determine unit validity, so the cost is imposed on all full nodes attempting to keep up with the DAG, not merely the poster.

### Impact Explanation
A single crafted but otherwise well-formed unit (AA definition or AA-triggering payment) can force every validating full node to spend a disproportionate amount of CPU time in the nearley/Earley parser before any of the existing complexity/op-count guards (`MAX_COMPLEXITY`, `MAX_OPS`) can reject it. If parsing time scales worse than linearly with formula length for adversarially chosen inputs, an attacker can repeatedly post such units (bounded only by the normal unit-posting fee/size economics, not by any formula-specific throttle) to degrade validation throughput network-wide, potentially slowing or stalling the node's ability to keep up with and stabilize new units — a network-unable-to-confirm-new-units condition, matching the class of impact called out for this advisory.

### Likelihood Explanation
Likelihood is moderate: constructing the crafted unit requires understanding of the oscript grammar's recursive rules and some experimentation to find the worst-case parsing pattern (similar to how the original xgrammar PoC needed a specific enum-heavy schema shape), but no special privileges are needed — any unprivileged unit poster can submit such a unit. The absence of any formula-length limit prior to parsing at the AA-definition/message-validation entry points (in contrast to the deliberate 10000-character cap that exists for the address-definition `'formula'` op) indicates this path was not hardened against the same class of parser-based DOS that other formula-parsing paths already anticipate.

### Recommendation
Add an explicit maximum length check on every formula string (and cumulatively across an AA definition/messages) before it is passed to `nearley.Parser.feed()`, both in `formula/validation.js` (`exports.validate`) and `formula/evaluation.js` (`exports.evaluate`), mirroring the existing `args.length > 10000` guard used for the `'formula'` op in `definition.js:599`. Additionally, benchmark/fuzz the oscript grammar's Earley parsing time against adversarial long inputs (deeply chained `or`/`and`/`+`/concat expressions) to determine a safe length bound, and consider bounding total formula-parsing work per validated unit independent of the eventual AST-based `MAX_OPS`/`MAX_COMPLEXITY` checks, since those only apply after the expensive parse has already completed.

### Proof of Concept
Construct an AA definition (or asset/message payload) containing a formula field of the form:
```
{1` + `1`.repeat(N)}   // e.g. "1+1+1+1+... " repeated tens of thousands of times, or
{"a" || "a" || "a" || ... }   // long chain of `concat` via ||
```
where `N` is chosen so the total AA-definition unit stays under `MAX_UNIT_LENGTH` (5,000,000 bytes) but the single formula string is on the order of hundreds of KB to a few MB — well beyond the 10000-character cap that exists for the analogous address-definition `'formula'` op but is absent here. Post this as a normal unit and measure `formula/validation.js`'s `nearley.Parser.feed()` time on a full node; a super-linear scaling in parse time relative to formula length would confirm the DOS analog to CVE-2025-58446. function getFormula(str, bOptionalBraces) {
	if (bOptionalBraces)
		throw Error("braces cannot be optional");
	if (typeof str !== 'string')
		return null;
	if (str[0] === '{' && str[str.length - 1] === '}')
		return str.slice(1, -1);
	else if (bOptionalBraces)
		return str;
	else
		return null;
}
