### Title
`StatusHandler#process` performs a global `Commit.where(sha:)` lookup, bypassing repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every other webhook handler (`PushHandler`, `PullRequest::*`) mutates state only through `Handler#stacks`, which scopes to `Repository.from_github_repo_name(repository_name)`. `StatusHandler#process` instead resolves target records via `Commit.where(sha: params.sha)` with no repository filter at all, so a signed webhook from repository A can mutate a `Commit`/status belonging to repository B if the two happen to reference the same 40-hex SHA.

### Finding Description
The binding that should hold for every handler is:
`handler_side_effect_targets == Repository.from_github_repo_name(payload['repository']['full_name']).stacks.<records>`

`Handler#stacks` and `Handler#repository_name` exist precisely to enforce this: [1](#0-0) 

`PushHandler#process` respects it — it only touches stacks returned by `stacks`: [2](#0-1) 

`StatusHandler#process` does not call `stacks` or `repository_name` at all; it looks up commits globally by SHA and mutates them: [3](#0-2) 

Signature verification in `WebhooksController` only proves the request came from GitHub for the organization named in `payload['repository']['owner']['login']`; it does not bind the payload to a specific repository's commits: [4](#0-3) 

Exploit flow: the GitHub Statuses API (`POST /repos/:owner/:repo/statuses/:sha`) lets any user with push access to their own repository set a status for an **arbitrary SHA string**, whether or not that commit actually exists in their repo. The attacker crafts a `sha` value equal to a real commit SHA already tracked by a Shipit `Stack` on a different tenant's repository (SHAs are content-addressed and can be discovered/guessed or copied from public commits/forks). GitHub signs and delivers this webhook using the attacker's own organization's legitimately configured secret — the attacker needs no Shipit secret. `verify_signature` passes because it only checks that the payload came from GitHub for the attacker's own org. `drop_unhandled_event` passes because `status` is a handled event. `StatusHandler.process` then runs `Commit.where(sha: <attacker-chosen sha>)`, finds the victim's commit record (belonging to a completely different repository/stack), and calls `commit.create_status_from_github!(params)`, mutating status data attacker does not own.

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) checks that the resolved `Commit` belongs to the repository named in the payload, since `StatusHandler` never consults `repository_name`/`stacks`.

### Impact Explanation
An attacker who owns any GitHub repository under an org with Shipit's app installed can forge commit-status writes against another tenant's `Commit` records purely by choosing a colliding/target SHA, without ever needing access to that tenant's repository, session, or API token. This is a cross-tenant write vector: status data (`state`, `description`, `target_url`, `context`) attached to another repository's commit is attacker-controlled. Since commit statuses are commonly consulted by Shipit's deploy-gating logic (e.g., CI status checks gating merges/deploys), this can influence deploy/merge decisions for stacks the attacker does not control — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Preconditions: attacker needs push/write access to any repository in an org where Shipit's GitHub App/webhook is installed (trivially satisfiable by creating their own public repo and installing/using an org they control, or exploiting a case where they already have a repo in a shared org). They must also know or guess a target SHA tracked by another tenant's stack — feasible for public commits, forks, or shared upstream branches, and only 40 hex chars but content-addressed and often discoverable (e.g., via public GitHub history, PR SHAs, or forks of the victim repo). Cost is low: one GitHub API call (`POST /repos/:owner/:repo/statuses/:sha`) using the attacker's own credentials — no Shipit secret required. Repeatable against any resolvable SHA.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve the target repository via `stacks`/`repository_name` first, then filter `Commit.where(sha: params.sha)` to commits belonging to stacks under that repository (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or add a `stack: { repository: ... }` join/scope) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (illustrative, not to be placed under out-of-scope test/ per rules but describing the assertion)
test "StatusHandler mutates a commit belonging to a stack absent from Handler#stacks for the payload's repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first) # belongs to victim_stack, sha: "aaaa...", NOT under attacker's repo

  payload = {
    'repository' => { 'full_name' => 'attacker/unrelated-repo' },
    'sha' => victim_commit.sha,
    'state' => 'success',
  }

  # Handler#stacks for this payload does not include victim_stack:
  handler = Shipit::Webhooks::Handlers::StatusHandler.new(payload)
  refute_includes handler.send(:stacks), victim_stack

  assert_difference -> { victim_commit.statuses.count }, 1 do
    handler.process
  end
  # StatusHandler mutated a commit outside its own Handler#stacks scope,
  # unlike PushHandler which only ever touches stacks returned by #stacks.
end
```
