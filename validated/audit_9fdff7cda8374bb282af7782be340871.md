### Title
Unvalidated P2P Staking Info Accepted During Fast Sync Corrupts Reward Distribution Database — (`datasync/downloader/queue.go`)

### Summary

During fast sync, `DeliverStakingInfos` in the downloader queue accepts peer-supplied `P2PStakingInfo` payloads through a deliberately stubbed-out validate function (`// TODO-Kaia-Snapsync update validation logic`). Unlike receipts — which are verified against `header.ReceiptHash` — staking info has no cryptographic commitment in the block header and no content check at delivery time. A malicious peer can respond to staking info requests with arbitrary `RewardAddrs`, `StakingAmounts`, `KEFAddr`, and `KIFAddr` values. These are written unconditionally to the persistent staking database via `PutStakingInfoToDB`, corrupting the reward-distribution and proposer-selection data used for all pre-Kaia-hardfork blocks.

### Impact Explanation

A malicious peer connected during fast sync can respond to `StakingInfoRequestMsg` with a crafted `P2PStakingInfo` payload containing:
- Attacker-controlled `RewardAddrs` → KAIA block rewards for the affected epoch are credited to attacker addresses in the node's local accounting
- Inflated `StakingAmounts` for attacker-controlled validators → biased weighted-random proposer selection
- Attacker-controlled `KEFAddr`/`KIFAddr` → treasury fund distributions redirected

The corrupted data is persisted to the staking database and cached, and is read back by `GetStakingInfo` for all pre-Kaia-hardfork blocks without re-deriving from state.

### Likelihood Explanation

- **Trigger**: Any peer connected during fast sync can deliver arbitrary staking info. No privileged access is required; any network participant can become a peer.
- **Precondition**: The victim node must be performing fast sync (a common bootstrap mode) and must be syncing pre-Kaia-hardfork blocks.
- **Detectability**: The corruption is silent — the only log line is `"Imported new staking information"` with no content validation.
- **Scope**: Limited to pre-Kaia-hardfork blocks (the `SyncStakingInfo` function explicitly rejects Kaia fork blocks). After Kaia hardfork, staking info is derived from the previous block's state, not the database.

### Recommendation

1. **Re-derive from state instead of trusting peers**: In `DeliverStakingInfos`, implement the `validate` function to re-derive the staking info from the canonical state at the requested block number and compare it against the peer-supplied data. This is the same approach used for receipts (compare against `header.ReceiptHash`).

2. **Remove the TODO stub**: Replace the `// TODO-Kaia-Snapsync update validation logic` no-op with an actual content check:

```go
validate := func(index int, header *types.Header) error {
    si := stakingInfoList[index]
    // Re-derive from canonical state and compare
    canonical, err := stakingModule.GetStakingInfo(header.Number.Uint64())
    if err != nil {
        return err
    }
    if !reflect.DeepEqual(staking.ToStakingInfo(si), canonical) {
        return errInvalidStakingInfo
    }
    return nil
}
```

3. **For `SyncStakingInfo`**: After receiving staking info from a peer, re-derive it from the local canonical state and compare before writing to the database.

### Proof of Concept

1. Attacker runs a Kaia node and connects to a victim node that is performing fast sync.
2. When the victim node sends a `StakingInfoRequestMsg` for block hashes corresponding to staking interval blocks, the attacker's node responds with a crafted `StakingInfoMsg` containing a `P2PStakingInfo` with:
   - `BlockNum` set to the correct block number (to pass the only check in `SyncStakingInfo`)
   - `CouncilRewardAddrs` replaced with attacker-controlled addresses
   - `CouncilStakingAmounts` inflated for attacker-controlled validators
3. The victim's `handleStakingInfoMsg` decodes the message and calls `DeliverStakingInfos`.
4. `queue.DeliverStakingInfos` calls `validate(index, header)` which returns `nil` unconditionally.
5. `commitFastSyncData` calls `PutStakingInfoToDB(si.BlockNum, staking.ToStakingInfo(si))`.
6. The corrupted staking info is now in the victim's database.
7. When the victim node later calls `GetStakingInfo(num)` for any block `num` whose source block is the corrupted entry, it reads the corrupted data from the database (cache/DB path, before falling back to state).
8. Reward distribution and proposer selection for those blocks use the attacker-controlled addresses and inflated weights.
