**Analysis:**

The `dlog_vec()`/`dlog_vec_batched()` functions in `crates/aptos-dkg/src/dlog/bsgs.rs` are discrete-log recovery primitives used only within the `aptos-dkg` crate's PVSS/chunked-ElGamal decryption logic [1](#0-0) , and are exercised in distributed key generation (DKG), which is a validator-internal protocol, not part of the transaction admission stack (mempool, vm-validator, authenticator parsing) [2](#0-1) .

There is no code path from an unprivileged REST/BCS transaction, its authenticator, WebAuthn signature, or multisig approval set into `dlog_vec`/`dlog_vec_batched`. Authenticator verification in `types/src/transaction/authenticator.rs` and VM validation in `aptos_vm.rs`/`keyless_validation.rs` rely on signature checks (Ed25519, MultiEd25519, WebAuthn, keyless/Groth16) [3](#0-2) [4](#0-3) , none of which invoke the BSGS dlog-recovery code. DKG transcript processing is handled as a `ValidatorTransaction` submitted only by validators, not by unprivileged transaction senders [5](#0-4) .

Additionally, the two functions are already covered by explicit equality tests (`test_dlog_vec_batched_matches_dlog_vec`, `test_dlog_vec_batched_rolling_with_batch_size_matches`) asserting byte-for-byte identical outputs across randomized `H_vec` inputs and multiple batch sizes [6](#0-5) , and both implementations perform the identical baby-step-table lookup logic, differing only in batching/normalization order — a purely algorithmic optimization with no divergent control flow that could produce different results for the same mathematical input.

Since the code is unreachable from any unprivileged transaction/authenticator/API entrypoint per the review's boundary conditions, this does not qualify as a transaction-admission vulnerability.
