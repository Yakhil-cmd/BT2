### Title
Arbitrary env-var injection into `PTY.spawn` via review-stack PR labels (`LD_PRELOAD`) - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` turns every GitHub label on the PR into an environment variable (`LABEL_NAME.upcase => "true"`) and merges it unconditionally into the stack's env, which `TaskCommands#env` (and therefore `DeployCommands#env`/`RollbackCommands#env`) merges before every `Command` is built. Because `Command#unbundled_env` passes that hash straight into `PTY.spawn` with no denylist, an attacker who can label their own PR (`LD_PRELOAD`) gets that variable injected into every spawned process (git, bundle, cap, ruby) for that review stack's deploys/rollbacks.

### Finding Description
The broken binding: the set of env keys reaching `PTY.spawn` for a task must equal `filter_task_envs/filter_deploy_envs/filter_rollback_envs(@task.env)` union the fixed machine/stack keys enumerated in `Stack#env`/`deploy_spec.machine_env` — but in practice it also includes `pull_request.labels.map(&:upcase)`, an attacker-controlled set with no filter at all.

Code path:
- `app/models/shipit/review_stack.rb:84-93` — `ReviewStack#env` does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })`, with no allowlist/denylist on label names. [1](#0-0) 
- `lib/shipit/task_commands.rb:33-48` — `TaskCommands#env` does `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)`. `@stack.env` (which includes the label-derived vars for a `ReviewStack`) is merged unconditionally, separate from and unrelated to the `@task.env` filtering path. [2](#0-1) 
- `lib/shipit/deploy_commands.rb:9-16` and `lib/shipit/rollback_commands.rb:9-13` — both simply `super.merge(...)`, inheriting the unfiltered `@stack.env` contribution from `TaskCommands#env`. [3](#0-2) 
- `lib/shipit/command.rb:103-105` and `92` — `unbundled_env` merges `@env.stringify_keys` (the fully-merged task env, including label-derived keys) directly into `BASE_ENV`, and `start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` with no key filtering whatsoever. [4](#0-3) [5](#0-4) 

The only existing filter, `filter_rollback_envs`/`EnvironmentVariables#permit` (via `deploy_spec.rollback_variables`), is applied solely to the explicit `env` param submitted at rollback-creation time (`app/controllers/shipit/api/rollbacks_controller.rb:18`, `app/controllers/shipit/rollbacks_controller.rb:30`) — i.e., to `@task.env`, not to `@stack.env`. It never sees or restricts the PR-label-derived keys because they enter through a completely different merge point. [6](#0-5) 

Attacker flow: attacker owns (or has label permission on) a GitHub repository connected to Shipit with review stacks enabled and `supports_rollback?` true. They open a PR, let CI/deploy succeed once (a real, successful deploy on the review stack, satisfying "reachable trigger_rollback" precondition), then add a label literally named `LD_PRELOAD` to that PR. GitHub sends a legitimate, correctly-signed `pull_request.labeled` webhook. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists `labels: ["LD_PRELOAD"]` onto the `PullRequest` record (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`). From then on, every `ReviewStack#env` call (deploy, rollback) includes `'LD_PRELOAD' => 'true'`. Since `"true"` is not a valid shared-object path, the attacker would instead need a label whose *upcased name equals* `LD_PRELOAD` and rely on this to demonstrate the binding break — but note the value is hardcoded to the string `"true"`, not attacker-supplied content, which materially limits exploitability (see Impact below).

Because GitHub label names cannot contain arbitrary binary-safe paths usable as `LD_PRELOAD` values (the value here is always the literal string `"true"`), the actual RCE requires that `"true"` resolve to a loadable `.so` at a predictable/writable path on the deploy host (e.g., `/true`, or a relative `true` resolved via `$PWD`/`RPATH` tricks) which is not guaranteed and is host-configuration dependent. This significantly weakens the "attacker fully controls the LD_PRELOAD value" premise embedded in the question.

### Impact Explanation
If a loadable shared object exists at a path equal to the literal string `"true"` reachable by the dynamic loader during command execution (not attacker-controlled, requires a specific host misconfiguration), every subsequent `git`/`bundle`/`cap`/`ruby` child process spawned for that review stack's deploys and rollbacks would preload it, executing attacker-influenced code in the process, which is RCE-class if achievable. Absent that misconfiguration, the attacker can still pollute the environment of every rollback/deploy for their own review stack with arbitrary uppercased label-name keys set to `"true"`, which is an environment-injection primitive scoped to the attacker's own stack (not other tenants' stacks, since `pull_request` and its labels belong to that PR/stack only).

### Likelihood Explanation
Requires: review stacks enabled on the repository, PR label management permission (self-serviceable if attacker owns the repo/fork wired to Shipit), a prior successful deploy on that review stack to reach `trigger_rollback`, and — critically for the RCE variant — a coincidental/loadable object at a path equal to the literal string `"true"` on the deploy host, which is not something the attacker controls via this endpoint. Without that last precondition, the "RCE" claim reduces to arbitrary (attacker-named) environment-variable injection with a fixed `"true"` value, not attacker-controlled shellcode/library paths.

### Recommendation
Sanitize/allowlist label-derived environment variable names in `ReviewStack#env` (e.g., reject names colliding with security-sensitive variables such as `LD_PRELOAD`, `LD_LIBRARY_PATH`, `BUNDLE_*`, `GIT_*`, `PATH`, `RUBYOPT`, etc.), or run label-to-env derivation through the same `EnvironmentVariables#permit`/allowlist mechanism (`deploy_variables`/`rollback_variables`) used for explicit rollback/deploy env params before merging into `TaskCommands#env`.

### Proof of Concept
minitest (`test/lib/shipit/rollback_commands_test.rb` or similar):
```ruby
test "#env does not let PR labels override security-sensitive env vars" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["LD_PRELOAD"]
  rollback = stack.trigger_continuous_delivery.build_rollback # or an equivalent successful-deploy + rollback setup

  env = Shipit::RollbackCommands.new(rollback).env

  # Binding under test: env keys reaching PTY.spawn must equal
  # filter_rollback_envs(@task.env) ∪ approved machine/task keys.
  # Currently this assertion PASSES, proving the label bypasses all filtering:
  assert_equal "true", env["LD_PRELOAD"]
  refute_includes stack.cached_deploy_spec.rollback_variables.map(&:name), "LD_PRELOAD"
end
```
This demonstrates `env['LD_PRELOAD']` is set via `@stack.env` even though `"LD_PRELOAD"` is absent from `rollback_variables`/`filter_rollback_envs`, i.e., it enters through `ReviewStack#env`, not `Rollback#env`. Note: this PoC proves the environment-injection primitive; it does **not** demonstrate arbitrary code execution, since the injected value is hardcoded to `"true"`, not an attacker-chosen library path.
