### Title
Webhook signature is verified against the organization named in `repository.owner.login`, while every event handler acts on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository','owner','login')` (or `organization.login`). But every webhook handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the target `Repository`/`Stack` using a *different* field of the same attacker-supplied payload: `params.dig('repository','full_name')`. In a multi-organization Shipit deployment, these two fields are never checked for consistency, so the identity that authenticates the request is not bound to the repository the request actually writes to.

### Finding Description
`verify_signature` picks the `GitHubApp` instance keyed by `repository_owner`: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` on that app instance is a no-op success when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations configured under `github:`, each with its own independent `webhook_secret` (confirmed by `test/dummy/config/secrets_double_github_app.yml`, where `OrgTwo` has `webhook_secret: # nil`) [4](#0-3) .

Meanwhile, every handler resolves the actual repository/stack acted upon from `repository.full_name`, a completely separate field of the same JSON body, never cross-checked against `repository.owner.login`: [5](#0-4) [6](#0-5) 
`Repository.from_github_repo_name` splits `full_name` on `/` and looks the row up purely by that string, with no relation to which organization's secret validated the request: [7](#0-6) 

**Equality broken:** the engine implicitly assumes
`organization authenticated (repository.owner.login → webhook_secret used)` == `repository written (repository.full_name → Stack acted upon)`
but nothing enforces this. An attacker who can satisfy signature verification for *any one* configured organization (e.g. one with no `webhook_secret` set, or whose secret has otherwise leaked/is weaker) can set `repository.owner.login` to that organization while setting `repository.full_name` to `victim-org/victim-repo`, and the request will be processed as a legitimate event for the victim's stack.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely, an attacker exploiting this can:
- Trigger `PushHandler#process` to force `stack.sync_github(expected_head_sha:)` on an arbitrary victim `Stack` [8](#0-7) , influencing which commit is considered "head" for deploy purposes.
- Trigger PR handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) to archive/unarchive review stacks or otherwise mutate merge-queue/review state for a victim repository, since these also resolve the acted-upon repository solely from `repository.full_name` [9](#0-8) .

This does not directly yield RCE/token exfiltration by itself, but it is an authentication-bypass-class issue: it lets a party who is not the victim organization's authenticated GitHub App produce state changes (unauthorized "deploy-adjacent" actions such as forced sync/archival) against the victim's stack, because the signature check is bound to the wrong field.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (explicitly documented/supported configuration), and (2) at least one configured organization with a weak/absent `webhook_secret` or leaked secret, distinct from the victim organization. Given the README/setup docs explicitly mark `webhook_secret` as "(optional)" [10](#0-9) , operators frequently omit it for at least one org, making this a realistic misconfiguration rather than a purely theoretical scenario.

### Recommendation
Bind the field used for signature-org selection to the field used for repository resolution: after verifying the signature for `repository_owner`, re-derive/require that `repository.full_name`'s owner segment matches `repository_owner` (or vice versa) before dispatching to handlers, rejecting the webhook otherwise.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs: `victim-org` (has `webhook_secret` set) and `attacker-org` (no `webhook_secret`, i.e., `webhook_secret: nil`).
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. POST to `/webhooks` with `X-Github-Event: push` and any/no `X-Hub-Signature` header (any signature is accepted because `attacker-org`'s `webhook_secret` is blank, per `verify_webhook_signature` returning `true` unconditionally in that case) [11](#0-10) .
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, succeeds trivially.
5. `PushHandler#process` resolves stacks via `repository.full_name = "victim-org/victim-repo"` and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [5](#0-4) [8](#0-7)  — without ever possessing `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
