### Title
Unprivileged Users Can Permanently Freeze a Vote Account by Front-Running Its Close/Withdraw with a `DepositDelegatorRewards` Deposit - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `DepositDelegatorRewards` instruction (SIMD-0123) lets *any* unprivileged account transfer lamports into *any* initialized V4 vote account, incrementing that vote account's `pending_delegator_rewards` counter with no restriction tying the depositor to the vote account or its authorities. `pending_delegator_rewards` is treated as a mandatory reserve in `withdraw()`: the authorized withdrawer can never bring the account below `rent_exempt_reserve + pending_delegator_rewards`, and cannot close the account at all while `pending_delegator_rewards > 0`. The only way `pending_delegator_rewards` is reduced is through `calculate_block_reward()` at epoch-reward distribution, which pays out block-revenue rewards proportional to a vote account's *currently delegated, active* stake — and returns `0` (no reduction at all) whenever the vote account has zero active stake in that epoch. Consequently, an attacker can permissionlessly deposit into any vote account that currently has (or will soon have) zero delegated stake, permanently blocking that account's ability to be closed and permanently locking its rent-exempt reserve plus the deposited dust, since there is no code path to ever redeem/zero `pending_delegator_rewards` for a vote account with no stake.

### Finding Description
`deposit_delegator_rewards()` only requires the source account to be a signer of the lamport transfer; it performs no check that the caller controls, is authorized on, or otherwise has any relationship to the target vote account: [1](#0-0) 
It then unconditionally increments the vote account's `pending_delegator_rewards`: [2](#0-1) 

`withdraw()` enforces that `pending_delegator_rewards` must be fully drained before a vote account can be closed (i.e., brought to a zero balance and deinitialized), and otherwise reserves `rent_exempt_reserve + pending_delegator_rewards` as a hard floor on the account's balance: [3](#0-2) 

The only mechanism that reduces `pending_delegator_rewards` is `calculate_block_reward()`, run during epoch-reward calculation. It looks up the vote account's *currently active delegated stake* for the rewarded epoch and pays out a reward proportional to it; if that total is `0`, the function returns `0` and `pending_delegator_rewards` is left completely untouched: [4](#0-3) 

There is no other instruction or code path that clears `pending_delegator_rewards` independent of active-stake-weighted block-reward redemption. Therefore, for any vote account with zero currently-delegated active stake — e.g., a newly created but not-yet-delegated vote account, or one whose validator has deactivated/withdrawn all delegated stake in preparation to retire and close it — depositing even 1 lamport via `DepositDelegatorRewards` sets `pending_delegator_rewards = 1` with no future epoch ever able to redeem it back to `0`, since `total_active_stake` for that vote account stays `0` forever (absent a fresh delegation, which the attacker does not control and the withdrawer may not want).

### Impact Explanation
This directly maps to the report's bug class: an unprivileged actor permissionlessly manipulates a state counter (`pending_delegator_rewards`, analogous to the report's `maxTotalSupply`) that a legitimate, otherwise-valid operation (`withdraw`/close, analogous to `deposit()`) checks against, and once manipulated the legitimate operation can never succeed again. Unlike the original medium-severity temporary DoS, this Agave analog produces a **permanently frozen account state**: the vote account's authorized withdrawer can never fully close the account nor recover the rent-exempt reserve (and the attacker's/dust lamports become permanently unspendable by anyone), satisfying the "permanently frozen accounts" impact bar. It is triggerable by any funded, unprivileged account against any vote account with zero active delegated stake, requiring no validator/operator role, and is fully reachable through the standard `DepositDelegatorRewards` and `Withdraw` vote-program instruction handlers.

### Likelihood Explanation
Likelihood is high once SIMD-0123/SIMD-0232/SIMD-0291 (`block_revenue_sharing`, `custom_commission_collector`, `commission_rate_in_basis_points`) are active, since:
- Newly created vote accounts naturally have zero delegated stake before their first delegation.
- Vote accounts being retired/closed typically deactivate and withdraw all stake first, leaving a window of zero active stake before the final `Withdraw`/close transaction.
- The attack costs only a trivial 1-lamport deposit and a single permissionless transaction; no signature or relationship to the target vote account or its withdrawer is required.

### Recommendation
Do not let `pending_delegator_rewards` permanently block account closure when there is no active stake to ever redeem it. Options include: (1) forbidding `DepositDelegatorRewards` deposits to vote accounts with zero currently-active delegated stake; (2) allowing the authorized withdrawer to sweep/burn or redirect `pending_delegator_rewards` directly (e.g., to the configured commission collector) when active stake is zero, so the reserve can reach zero independent of reward-distribution timing; or (3) excluding `pending_delegator_rewards` from the close-eligibility/minimum-balance check when the vote account has no active stake in the current epoch.

### Proof of Concept
1. Identify a vote account `V` with zero currently-delegated active stake (freshly created and undelegated, or fully deactivated in preparation for closure).
2. As any unprivileged, funded account `A`, submit `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` targeting `V` — this succeeds per `deposit_delegator_rewards()` since only `A` need sign, with no relationship to `V` required (`programs/vote/src/vote_state/mod.rs:946-988`).
3. `V.pending_delegator_rewards` becomes `1`.
4. At every subsequent epoch boundary, `calculate_block_reward()` looks up `V`'s active delegated stake, finds `0`, and returns `0`, leaving `pending_delegator_rewards` unchanged (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:206-212`).
5. `V`'s authorized withdrawer attempts `VoteInstruction::Withdraw` for the full balance to close the account; `withdraw()` rejects it with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0` (`programs/vote/src/vote_state/mod.rs:1087-1092`), and this will fail forever since `pending_delegator_rewards` can never be reduced absent a fresh delegation to `V`.
