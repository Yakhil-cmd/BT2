## Title
Division-by-zero panic (`unwrap()` on `checked_div`) in `calculate_stake_rewards` MigrationEpoch branch when `point_value.points == 0` but an individual stake's `tower_points != 0` - ([File: runtime/src/inflation_rewards/mod.rs])

### Summary
The MigrationEpoch reward-calculation branch of `calculate_stake_rewards` only guards the zero-divisor case for `point_value.points` when the stake's own `ag_points == 0`. If a stake's individually recalculated `tower_points != 0` while the (separately snapshotted) aggregate `point_value.points == 0`, the code performs `checked_div(point_value.points).unwrap()`, which panics on a `None` result. This mirrors the Y2K `previewEmissionsWithdraw` bug, where a denominator (`finalTVL`) could be left unset/zero for a code path that was not defended by the same guard used elsewhere.

### Finding Description
In `calculate_stake_rewards`, the `Tower` branch explicitly checks `point_value.points == 0` before dividing: [1](#0-0) 

But the `MigrationEpoch` branch only checks the zero-divisor condition combined with `ag_points == 0`: [2](#0-1) 

```rust
AlpenglowEpochType::MigrationEpoch { num_tower_slots, num_ag_slots, .. } => {
    if tower_points == 0 && ag_points == 0 {
        return skip_reward(SkippedReason::ZeroPoints);
    }
    if ag_points == 0 && point_value.points == 0 {
        return skip_reward(SkippedReason::ZeroPointValue);
    }
    ...
    let tower_points = tower_points
        .checked_mul(u128::from(point_value.rewards))
        .expect(...)
        .checked_div(point_value.points)   // <-- unguarded when ag_points != 0
        .unwrap()
        ...
}
```

If `tower_points != 0` and `ag_points != 0` while `point_value.points == 0`, neither guard triggers, and `checked_div(0)` returns `None`, causing `.unwrap()` to panic.

During normal, single-shot reward calculation (`calculate_reward_points_partitioned`), `point_value.points` is the sum of every delegation's own `tower_points`, so a nonzero individual `tower_points` implies a nonzero aggregate — this specific combination cannot arise there.

However, `point_value` used at redemption time is not always freshly summed. `recalculate_stake_rewards` reuses a **fixed** `point_value` taken from the `EpochRewards` sysvar snapshot (`total_points` computed once at the epoch boundary) while re-deriving each stake's `tower_points`/`ag_points` from the **current** `StakesCache` and vote-account state at recalculation time: [3](#0-2) 

Because partitioned reward distribution spans multiple blocks/slots, and this recalculation path re-derives points from live account state rather than the frozen aggregate, any drift between the snapshot-time aggregate and the current per-delegation contribution during that window (e.g., due to stake delegation/vote-state changes occurring between snapshot and distribution) can produce exactly the unguarded `tower_points != 0`, `point_value.points == 0` combination, hitting the unreachable-in-theory divide-by-zero `.unwrap()`.

### Impact Explanation
A panic inside epoch-boundary reward redemption is not an isolated per-transaction failure — it occurs inside mandatory bank processing that every validator must execute deterministically to advance the epoch. A panic here on all honest validators simultaneously (since they all process the same recalculation with the same inputs) results in a network-wide validator crash/halt, which is a consensus-critical availability failure, rather than a recoverable transaction error.

### Likelihood Explanation
The unguarded condition is narrow and depends on state divergence occurring specifically inside the partitioned-distribution recalculation window (`recalculate_stake_rewards`), which is a legitimate, reachable code path exercised every epoch under Alpenglow migration conditions with partitioned reward distribution. The severity (validator panic / consensus halt) combined with the missing symmetrical guard (present for the `Tower` branch, absent for `MigrationEpoch`) makes this a real latent defect, even though triggering the exact divergence requires a specific sequencing of stake/vote state changes during the distribution window.

### Recommendation
Add the same defensive guard used in the `Tower` branch to the `MigrationEpoch` branch: check `point_value.points == 0` unconditionally (not only when `ag_points == 0`) before performing the `checked_div`, and skip/return `None`/`skipped_reward()` in that case instead of relying on `.unwrap()`.

### Proof of Concept
Not directly demonstrable as a single-transaction PoC without reproducing the multi-slot partitioned-distribution recalculation window and inducing state drift between the epoch-boundary point snapshot and the later recalculation call; the code-level defect (missing guard compared to the sibling `Tower` branch) is shown above by direct comparison of the two branches in `runtime/src/inflation_rewards/mod.rs`.
