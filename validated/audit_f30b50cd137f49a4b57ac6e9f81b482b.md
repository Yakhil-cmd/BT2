### Title
Webhook secret selection uses `repository.owner.login`, but Statuses/PushHandler act on `repository.full_name` — cross-organization forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC signature against based on `params.dig('repository', 'owner', 'login')`, while the handlers that act on the payload (`Handler#stacks`, `PushHandler`, `StatusHandler`, pull-request handlers) select the target repository/stack using the independent `repository.full_name` field from the same body. These two fields are not cross-validated against each other.

### Finding Description
`verify_signature` computes `repository_owner` and uses it only to pick the app config for HMAC verification: [1](#0-0) [2](#0-1) 

The HMAC itself covers `request.raw_post` verified via `verify_webhook_signature`, keyed by `webhook_secret` of the app selected for `repository_owner`: [3](#0-2) 

However, once the signature check passes, the generic `Handler` base class (used by `PushHandler` and others) resolves the actual repository/stack to operate on from a *different* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

Shipit explicitly supports hosting multiple independent GitHub Apps/organizations on a single Shipit instance (`config/secrets.yml` keyed by organization), each with its own `webhook_secret`: [5](#0-4) 

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the target repository/stack) are two independent, attacker-controlled strings inside the same JSON body, an attacker who legitimately controls one organization's GitHub App (and therefore knows that organization's `webhook_secret`, as is expected for any organization admin who installed their own Shipit GitHub App) can craft a payload where:
- `repository.owner.login` = `attacker-org` (so `verify_signature` looks up and validates against `attacker-org`'s known secret — passes)
- `repository.full_name` = `victim-org/victim-repo` (so the handler acts on a stack/repository belonging to a completely different, unrelated organization hosted on the same Shipit instance)

This breaks exactly the "organization that authenticated vs. the repository that is written" binding: the signature proves control of `attacker-org`'s secret, but the write/action target is determined by an unrelated, unauthenticated-with-respect-to-that-org field.

### Impact Explanation
Depending on which webhook event/handler is invoked, this allows an attacker with no privileges on the victim organization/repository to:
- Force `PushHandler` to enqueue `GithubSyncJob` for the victim's stacks on arbitrary branches [6](#0-5) , forcing spurious re-syncs of a stack that isn't theirs.
- Forge commit statuses for the victim repository via the `status` event, since `StatusHandler` also resolves its target commit purely from repository/sha fields in the body rather than the org used for signature verification (statuses feed into CI-gating and can influence whether commits become deployable, and with continuous deployment enabled, can trigger real deploys).
- Trigger pull-request based review-stack provisioning/archiving actions (`opened_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`) against a victim's repository, since these also resolve repository via `params.repository.full_name` [7](#0-6) .

This can escalate to an unauthorized deploy (if a victim stack has `continuous_deployment` enabled and CI status is influenced by forged `status` events) or at minimum unauthorized state changes (stack archive/unarchive, spurious syncs) on a repository the attacker has no legitimate access to — satisfying the "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Requires a Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration) where the attacker legitimately administers one organization's GitHub App (and therefore its `webhook_secret`) but has no rights over the victim organization's repositories. Given this precondition — which is entirely plausible in shared/multi-tenant Shipit deployments used by platform teams hosting many orgs — the attack requires only crafting a JSON POST to `/webhooks` with a valid HMAC computed using the attacker's own known secret; no other credentials are needed.

### Recommendation
Bind the field used for authentication to the field used for the action: after selecting the GitHub App/secret via `repository_owner`, verify that the resolved repository's actual owner (as looked up/known to Shipit, e.g. from the `Repository`/`Stack` record or a re-derivation of owner from `repository.full_name`) matches `repository_owner` before dispatching to handlers. Concretely, in `WebhooksController#verify_signature`/`create`, assert that `repository_owner == params.dig('repository', 'full_name')&.split('/')&.first` (case-insensitively) and reject (422) on mismatch, or have `Handler#repository_name` cross-check against the same `repository.owner.login` used for signature verification instead of trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `attacker-org` (attacker's own GitHub App, attacker knows its `webhook_secret`) and `victim-org` (unrelated org, hosts a Shipit stack for `victim-org/victim-repo`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<any_sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over the raw body.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, looks up `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature using the attacker's own secret [1](#0-0) .
6. `PushHandler#process` resolves the target stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` [4](#0-3)  and enqueues `GithubSyncJob`/other side effects against the victim's stack, despite the attacker having no credentials for `victim-org`.

Note: I was unable to fully trace `StatusHandler`'s exact code within available search results (only confirmed its existence and that it references `continuous_deployment`-adjacent logic indirectly through `Commit`); confirming the precise depth of impact (e.g., whether forged `status` events can directly flip a commit to deployable and trigger an actual auto-deploy) would require reading `app/models/shipit/webhooks/handlers/status_handler.rb` and `app/models/shipit/commit.rb` in full, which the index did not surface in this session.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
