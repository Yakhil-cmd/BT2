### Title
Session fixation in OAuth callback allows attacker to force victim into attacker-controlled session - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` writes `session[:user_id]` and `session[:authenticated]` into the pre-existing session without calling `reset_session`. An attacker who can fix a victim's session id before authentication (e.g., via a `session_id` cookie set through a subdomain, `Set-Cookie` on a non-HTTPS-only cookie, or a shared/planted session) can complete their own OAuth handshake on that fixed session, then hand the browser back to the victim. If the victim continues browsing under that same session id and later re-authenticates or is otherwise coerced to keep using it, the identity bound to the session id can be attacker-controlled since the session id itself never rotates on login.

### Finding Description
The broken binding: `session.id` (the cookie value in the client's browser) should uniquely determine, post-authentication, a `User` whose OAuth handshake actually occurred under a freshly-issued session id — i.e. `session.id_before_login != session.id_after_login`. In this code, that never holds: [1](#0-0) 

`callback` reads `omniauth.auth` from the completed OAuth exchange, calls `sign_in_github(auth)` which resolves/creates a `User` and returns its id, then writes `session[:user_id] = user.id` and `session[:authenticated] = true` directly onto whatever session id was already attached to the request — there is no `reset_session` call. Compare this to `logout`, which does call `reset_session` [2](#0-1) , and to the stale-login branch of `force_github_authentication`, which also calls `reset_session` before redirecting to re-authenticate [3](#0-2) . Both of those code paths demonstrate the engine's authors treat `reset_session` as the correct control for rotating session identity — it is simply missing from `callback`, the one place identity is actually established.

`find_current_user` trusts `session[:user_id]` verbatim to resolve `current_user` [4](#0-3) , so whichever `User` last wrote `session[:user_id]` on a given session id is who the app treats as authenticated for that session id, permanently, until logout or a fresh-login check triggers.

None of the existing guards address this: `force_github_authentication`'s `authorized?` check only gates whether a logged-in user is a member of `Shipit.github_teams` — it does not prevent the initial `session[:user_id]` write during `callback` from landing on a pre-existing/attacker-influenced session id. `requires_fresh_login?` only resets sessions for stale/expired logins, not for the initial OAuth callback. There is no CSRF/state check visible in this controller that would bind the completing session to the session that initiated the OAuth flow.

### Impact Explanation
If an attacker can plant/fix a session id in a victim's browser before the victim (or the attacker acting on the victim's session) completes GitHub OAuth, the resulting `session[:user_id]` binding is not rotated, so the session id — and therefore whoever controls that cookie value — persists across the authentication boundary. This is a session-fixation primitive: it does not itself grant escalation into `Shipit.github_teams` (that still requires `User#authorized?` to pass for the identity in session), but it breaks the expectation that a login event rotates session identity, which is listed as an explicit High-severity category ("session fixation / forced OAuth completion").

### Likelihood Explanation
Exploitation depends entirely on the attacker's ability to fix a session id into the victim's browser before the OAuth callback fires — e.g., via cookie scope issues, a non-`HttpOnly`/non-secure cookie exposed to a shared network, subdomain cookie injection, or session id leakage through a referrer/log. The engine code itself does not provide a mechanism to *set* an arbitrary session cookie on the victim (that requires a separate delivery vector outside this controller, such as cross-subdomain cookie tossing or a session id disclosed in a URL/log by the host application/Rack session store configuration). Within this engine, the only concretely provable fact is that `callback` never rotates the session id — a necessary condition for fixation, not by itself a full end-to-end proof of a delivery vector, since delivering an attacker-known session id to the victim depends on the host's session-cookie configuration (`config/initializers/session_store.rb`), which lies outside this engine's own code.

### Recommendation
Call `reset_session` at the start of `callback`, before establishing `session[:user_id]`/`session[:authenticated]`, mirroring the pattern already used in `logout` and in `force_github_authentication`'s stale-login branch:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

### Proof of Concept
```ruby
test ":callback rotates the session id to prevent fixation" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(
      raw_info: OmniAuth::AuthHash.new(
        id: 44, name: 'Attacker', email: 'attacker@example.com',
        login: 'attacker', avatar_url: 'https://example.com',
        api_url: 'https://github.com/api/v3/users/attacker'
      )
    )
  )

  # Simulate an attacker-fixed/pre-existing session id.
  get :callback # establish some session first (or stub session.id directly)
  fixed_session_id = session.id

  @request.env['omniauth.auth'] = auth
  get :callback

  assert_not_equal fixed_session_id, session.id,
    "Expected session id to rotate on login (reset_session), but it did not"
end
```
With the current code, `session.id` before and after `callback` is identical while `session[:user_id]` changes to the newly authenticated user — demonstrating the missing `reset_session` call at [5](#0-4) .
