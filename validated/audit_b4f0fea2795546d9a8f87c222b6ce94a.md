## Analysis Result

This confirms the multi-org config model: `Shipit.github(organization:)` looks up a per-organization `webhook_secret` keyed purely by the organization name string supplied by the caller, with no cross-check against the repository actually being acted upon. [1](#0-0) 

### Title
Webhook signature verified against organization derived from `repository.owner.login`, but downstream handlers act on the unrelated `repository.full_name` field — allows cross-organization forgery of push/PR/status/check-suite events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the incoming HMAC signature against by reading `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [2](#0-1) [3](#0-2) 

In a multi-org Shipit deployment, `Shipit.github(organization:)` resolves a *separate* `webhook_secret` per organization key from `secrets.github`, and this is the only tenancy boundary between organizations sharing one Shipit instance. [1](#0-0) 

However, every downstream handler that decides *which Stack/repository actually gets acted upon* reads a **different** field of the same JSON body: `payload.dig('repository', 'full_name')`, via `Handler#repository_name` (used by `PushHandler`) or `params.repository.full_name` in the pull-request handlers. [4](#0-3) [5](#0-4) [6](#0-5) 

Nowhere in `verify_signature` or in any handler is `repository.owner.login` (the field used to pick the signing secret) checked to actually match the owner encoded inside `repository.full_name` (the field used to pick the target Stack/Repository). The binding that should hold is:

`organization whose secret authenticated the payload == owner of the repository that gets written to`

but the code only enforces "some organization's secret produced a valid HMAC over the raw body" — it never re-derives that same organization from `repository.full_name` and compares. An operator of a low-trust organization "OrgA" configured on the same Shipit instance (each org has its own independent GitHub App/webhook secret, as shown in the dual-org secrets template) knows OrgA's `webhook_secret` because they set up OrgA's GitHub App themselves. [7](#0-6)  That party can craft a POST to `/webhooks` where `repository.owner.login = "OrgA"` (so `verify_signature` picks OrgA's secret, which the attacker controls and can sign correctly) but `repository.full_name = "OrgB/high-trust-repo"` (a repository belonging to a different, higher-trust organization also hosted on the same Shipit instance). The signature check passes because it's validated against the attacker's own OrgA secret, and the handler then acts on OrgB's repository/stack because it only reads `full_name`.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written" and lets an attacker with only self-service control of a low-trust org's GitHub App secret forge `push` events (triggering `stack.sync_github` for any branch/SHA against a victim stack in another org) and pull-request/check_suite/status events, causing Shipit to perform actions (sync, archive/unarchive review stacks, apply status updates) against repositories the attacker never legitimately controls. Because deploy execution in Shipit is gated by the state of `Stack`/`Commit`/CI-status records that this webhook path mutates, an attacker can manipulate whether commits appear "green"/deployable, or force resynchronization pointing to attacker-chosen SHAs, on a victim organization's stack — an unauthorized-deploy-adjacent forgery reachable purely from outside, without any Shipit session, `ApiClient` token, or GitHub write access to the victim's repo.

### Likelihood Explanation
Exploitability requires only that the Shipit instance be configured with the documented multi-organization `secrets.github` schema (explicitly supported and documented, see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`) where the attacker legitimately administers at least one of the configured organizations/GitHub Apps and therefore knows its `webhook_secret`. No privileged Shipit account, session, or victim-repo access is needed — only network access to POST to the public `/webhooks` endpoint with a validly-signed-by-OrgA body whose `repository.full_name` field is forged to point at OrgB.

### Recommendation
After signature verification succeeds, re-derive the organization from the same `repository.full_name` (or `repository.owner.login`) field that handlers actually use to select the target `Stack`/`Repository`, and reject the webhook (422) if it does not match the organization whose secret validated the signature. Alternatively, always verify the payload against the specific organization owning the `full_name` repository rather than trusting a separately-read `owner.login`/`organization.login` field for secret selection.

### Proof of Concept
1. Shipit is deployed with a multi-org config: `secrets.github` contains `OrgA` (attacker's own org/app, secret known to attacker) and `OrgB` (victim org, hosts stack `OrgB/prod-app`).
2. Attacker builds a `push` webhook payload: `{"ref": "refs/heads/master", "after": "<attacker-chosen sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/prod-app"}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, gets OrgA's `GitHubApp`, and `verify_webhook_signature` succeeds since the attacker signed with OrgA's real secret. [8](#0-7) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` = `OrgB/prod-app`, and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — despite the request never being signed by OrgB. [9](#0-8) [10](#0-9)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
