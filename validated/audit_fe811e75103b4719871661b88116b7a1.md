This confirms the exact binding break the rules describe: "an organization that authenticated versus the repository that is written."

### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but every handler acts on the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook controller derives the GitHub App/organization used for HMAC verification from one payload field (`repository.owner.login`, falling back to `organization.login`), while every event handler that actually mutates state resolves the target `Repository`/`Stack` from a *different*, independently-controlled payload field: `repository.full_name`.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (or `organization.login`) and uses it to pick which GitHub App's `webhook_secret` to validate the request against: [1](#0-0) [2](#0-1) 

Once the signature check for that organization's app succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handler with the raw, attacker-supplied JSON body, unconstrained relative to the field used for verification. Every handler resolves its target repository via `Handler#repository_name`/`#stacks`, which reads `payload.dig('repository', 'full_name')` — a completely separate JSON field from `repository.owner.login`: [3](#0-2) 

`Repository.from_github_repo_name` then splits this `full_name` on `/` and looks up any repository/owner pair in the datastore, with no cross-check that it matches the organization whose secret validated the request: [4](#0-3) 

In a single-organization deployment this is harmless because the same GitHub App owns all repositories under that org, so `owner.login` and the owner half of `full_name` naturally coincide. But the engine explicitly documents and supports **multiple GitHub Apps for multiple organizations**, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml` and `docs/setup.md`'s "Using Multiple Github Applications" section): [5](#0-4) [6](#0-5) 

In that configuration, an attacker who can get *any one* configured GitHub App (org A) to relay a webhook whose body they control — e.g. via a repo they own inside org A, using a legitimate app installation event — can set `repository.owner.login = "A"` (so the signature validates against org A's real secret) while setting `repository.full_name = "B/some-repo"` for an entirely different organization B tracked by the same Shipit instance. The signature only proves "this came from a source holding org A's webhook secret / GitHub's relay for org A's installation"; it says nothing about which repository the payload claims to describe. Because handlers trust `full_name` unconditionally, this crosses a trust boundary: the organization that authenticated the request is not the repository the handler ends up writing to.

This exactly parallels the reported Malt bug class: a value (`active` / here, `repository.full_name`) is *acted upon* by downstream logic without being bound to the value that was actually validated (`activeTraders` membership / here, the webhook signature's organization).

### Impact Explanation
Handlers driven by `full_name` include the push handler, which enqueues `GithubSyncJob` to sync commits for any matching stack in the datastore: [7](#0-6) 

and `GithubSyncJob` fetches commits using `stack.github_api`, i.e. **org B's own installation token** (not org A's), so the confused-deputy angle is limited — the sync job still authenticates to GitHub using the target stack's real owner credentials. The practically exploitable consequence is state-confusion/spoofing: an actor who fully controls one configured organization's app/webhook relay can trigger sync, status, check-suite, membership, or pull-request handlers against a *stack belonging to a different tracked organization*, using forged `sha`/`state`/`ref`/`after` values that were never signed for that repository. This can, for example, inject fabricated commit `status` records or forge check-suite refreshes against another org's stack, since `status`/`check_suite` handlers key off `full_name` the same way.

### Likelihood Explanation
Exploitability strictly requires that the Shipit deployment be configured with multiple GitHub organizations/apps (a documented, supported configuration) and that the attacker controls, or can get arbitrary webhook deliveries relayed through, one of those configured apps (e.g., owning a repo in org A that is wired into the same Shipit instance). This is a real but narrower scenario than the general "unprivileged internet attacker" bar, so likelihood is moderate rather than trivial — it does not require compromising `webhook_secret` cryptographically, only using a legitimate, differently-scoped app relationship to smuggle a mismatched `full_name`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), bind the two fields together: after verifying the signature for `repository_owner`, assert that `payload.dig('repository', 'full_name')` (and `organization.login`, when present) is prefixed by/matches that same `repository_owner` before invoking any handler, rejecting the request with `422` otherwise.

### Proof of Concept
Conceptual PoC (would need a live multi-org Shipit deployment to fully execute):
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, both tracking repositories in Shipit (`docs/setup.md` multi-org config).
2. As a user controlling `OrgA`'s repository/app relay, submit (or relay) a `push` webhook whose body is:
   ```json
   { "ref": "refs/heads/master", "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" } }
   ```
   signed with `OrgA`'s `webhook_secret`.
3. `verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the signature successfully against the real `OrgA` secret [8](#0-7) .
4. `PushHandler#process` resolves `stacks` via `Handler#repository_name`, which reads `full_name = "OrgB/target-repo"` [3](#0-2) , and enqueues `GithubSyncJob` against `OrgB`'s stack — a repository never covered by the verified signature.
