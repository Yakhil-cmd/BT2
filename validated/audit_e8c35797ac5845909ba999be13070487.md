This confirms the vulnerability: `CCMenuUrlController#client` at [1](#0-0)  creates (or reuses) a single, unscoped `ApiClient` per user named `"CCMenu Client"` with `permissions: %w[read:stack]` and **no `stack_id`** set. Because `ApiClient#stack` is optional ( [2](#0-1) ) and `Api::BaseController#stacks` only restricts to a single stack `if current_api_client.stack_id?` ( [3](#0-2) ), this "CCMenu Client" token is authorized for **every** stack in the installation, not just the one the user requested a CCMenu URL for.

### Title
Unscoped CCMenu API token grants read access to all stacks regardless of requested stack - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints a signed `ApiClient` token intended to expose the CI status of one specific stack via a public, unauthenticated CCMenu XML feed. The token itself carries no stack binding, so once issued it authorizes reading *any* stack's deploy/build status, not just the one the user consented to share.

### Finding Description
When a user requests a CCMenu URL for a stack, `client` ( [1](#0-0) ) finds-or-creates a shared `ApiClient` named `'CCMenu Client'` per user, with `permissions: %w[read:stack]` and no `stack:` attribute set. The resulting `authentication_token` is a `SimpleMessageVerifier`-signed string that encodes only the `ApiClient` id ( [4](#0-3) ) — it does not encode which stack the user intended to expose.

`Api::CCMenuController` authenticates this token via `params[:token]` ( [5](#0-4) ) and then resolves the target stack with `Stack.from_param!(params[:stack_id])` ( [6](#0-5) ) — querying the global `Stack` relation directly, rather than the tenant-scoped `stacks` helper (`current_api_client.stack_id? ? Stack.where(id: ...) : Stack.all`) used elsewhere in `Api::BaseController` ( [7](#0-6) , contrast with `Api::StacksController#stack` at [8](#0-7) ). The permission check performed via `require_permission :read, :stack` ( [9](#0-8) ) only verifies the coarse `"read:stack"` string is in `ApiClient#permissions` ( [10](#0-9) ) — it never checks whether `current_api_client.stack_id` (if any) matches `params[:stack_id]`.

Because the "CCMenu Client" `ApiClient` record for a user has `stack_id: nil` (it was never assigned a stack), it is treated by `Stack.where(id: current_api_client.stack_id)` — but since `CCMenuController#stack` bypasses that scoping entirely, the `stack_id` on the `ApiClient` is irrelevant. This is exactly the "stack a token authorises versus a stack it touches" binding break: the URL a user shared publicly (often embedded in unauthenticated CI status badges/monitors) for stack A's status can be trivially modified (`stack_id` query/path param) to read stack B's, C's, or any other stack's status, deploy history, and lock reason, in an org the user may not even have visibility into.

### Impact Explanation
This is an unauthenticated read of stack state/task output for stacks outside the token's intended scope. The `CCMenuController#show` action exposes `stack.deploys_and_rollbacks.last` build status, lock state, and related metadata ( [11](#0-10) ) for arbitrary stacks to anyone possessing any single "CCMenu Client" token — tokens which are, by design, meant to be embedded in unauthenticated third-party CI-status tools. This matches the in-scope High-severity criterion: "unauthenticated read of stack state, task streams or deploy output" achieved via a credential/authorization boundary crossing (token scope vs. resource accessed).

### Likelihood Explanation
High. Any Shipit user with access to at least one stack can generate a CCMenu URL for it via the standard "Fetch CCMenu URL" feature, then simply change the `stack_id` in the resulting URL to any other stack slug in the installation to read its status — no privilege escalation, no session, no additional secrets required beyond the one CCMenu token they were legitimately given.

### Recommendation
Bind the CCMenu `ApiClient` to the specific stack it's created for (set `stack: @stack` instead of leaving it global/shared), and change `Api::CCMenuController#stack` to use the scoped `stacks.from_param!(params[:stack_id])` helper (as `Api::StacksController` does) rather than querying `Stack` directly, so the token's `stack_id` binding is actually enforced.

### Proof of Concept
1. User A owns/has read access to `stack-a` and visits the "Fetch CCMenu URL" action, receiving `https://shipit.example.com/api/stacks/stack-a/cc.xml?token=<here_come_the_walrus_style_token>`.
2. The `ApiClient` record backing this token has `permissions: ["read:stack"]` and `stack_id: nil` (created via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with no stack argument) — see [1](#0-0) .
3. An attacker who obtains this URL (e.g., from a public dashboard/monitoring tool where CCMenu URLs are commonly embedded) requests `https://shipit.example.com/api/stacks/some-other-private-stack/cc.xml?token=<same token>`.
4. `authenticate_api_client` succeeds because the token is valid regardless of stack ( [5](#0-4) ); `require_permission :read, :stack` succeeds because the client has the generic `read:stack` permission; `stack` resolves `some-other-private-stack` via unscoped `Stack.from_param!` ( [6](#0-5) ).
5. The attacker receives that stack's build/deploy status XML, despite the token never having been scoped or intended for that stack.
