No vulnerability found for this question.

The reported issue is specific to Solidity contracts that call `approve()` on an *externally supplied, arbitrary* ERC-20 token contract (e.g., `payoutToken.approve(address(optionTeller), rewards)` in the audited `OTLM.sol`), where some non-compliant tokens like USDT revert when changing a non-zero allowance without resetting to zero first.

Searching polkadot-sdk's production code for an analogous pattern turns up only the ERC-20 precompile in `pallet-assets-precompiles` [1](#0-0) , but this is structurally different: the precompile *is* the token itself (it implements ERC-20 `approve` semantics for `pallet-assets`, calling `pallet_assets::Pallet::do_approve_transfer`/`do_cancel_approval` on its own storage), not an external call out to a third-party, potentially non-compliant ERC-20 token. This code was already deliberately fixed in [2](#0-1)  to implement correct ERC-20 "set" semantics (cancel-then-approve when overwriting a non-zero allowance), which incidentally means it never re-enters an external contract's `approve` and therefore cannot trigger the USDT-style revert-on-non-zero-to-non-zero pattern described in the report.

I found no place in polkadot-sdk where a FRAME pallet, precompile, or XCM component calls `approve()` on an *externally supplied/arbitrary* ERC-20-like contract (analogous to `payoutToken.approve(...)` in the report) without first resetting the allowance to zero. Without a reachable code path where polkadot-sdk itself acts as the caller of an untrusted external token's `approve`, the invariant violated in the report (some tokens revert on non-zero→non-zero allowance changes) has no demonstrable Polkadot SDK analog.
