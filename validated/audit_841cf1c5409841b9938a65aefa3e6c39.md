### Title
Single-step, unrecoverable address definition change permits accidental permanent loss of address control - (File: [validation.js](https://github.com/byteball/ocore/blob/master/validation.js))

### Summary
The `address_definition_change` message app in ocore lets any address owner (or an AA-controlled/shared address participant, via a single-authored or multi-authored unit) replace the address's authentication rule (its `definition_chash`) in one irreversible step. Unlike a two-step "propose pendingOwner → claim" pattern recommended in the referenced report, ocore performs no verification that the poster actually knows/possesses a definition matching the new `definition_chash`, nor is there any grace period or rollback mechanism. Once the unit becomes stable, the address's old definition is permanently superseded — matching exactly the "single-step ownership transfer/renounce" risk described in the external report, but here applied to on-chain address control rather than a smart-contract `Ownable`.

### Finding Description
When validating an inline `address_definition_change` message, ocore only checks: [1](#0-0) 

- that the payload is a non-empty object with only `definition_chash`/`address` fields,
- that at most one definition change per address is included,
- and that `payload.definition_chash` is a syntactically valid address/hash (`isValidAddress`).

There is **no check that the sender can produce (now or ever) a definition whose hash equals `new_definition_chash`**. The new definition itself does not need to be revealed at the time of the change — only its hash. This is a deliberate design (definitions can be disclosed later, see `has definition change` / `seen definition change` ops), but it means a single mistake — a typo'd hash, an out-of-sync generated address, or reuse of a hash for a definition the user never actually recorded — permanently and unrecoverably changes the address's authentication rule.

The change is written and applied unconditionally once stable: [2](#0-1) 

From then on, any future unit from that address must supply a definition matching the new `definition_chash`, or it's rejected: [3](#0-2) 

If the actual definition matching the new hash cannot be produced (lost keys, wrong hash, or hash referencing a definition template that was never actually finalized correctly), the address becomes permanently unable to sign any future unit — there is no `pendingOwner`-style second step to reject/cancel an in-flight, not-yet-stable change, and once stable there is no revert path at all. Compare to `Ownable.transferOwnership()`/`renounceOwnership()` in the referenced report: this is the same "one transaction bricks control forever" risk, but the "owner" here is effectively the entire spending authority (private keys/oscript conditions) of the address, so the blast radius is broader — it can affect base-currency balances, private/indivisible/divisible asset holdings tied to the address, and (for shared/multisig addresses composed via `wallet_defined_by_addresses.js`) all cosigners simultaneously.

Additionally, before the definition change unit is even stable, the protocol still forbids sending anything from the address until the pending change resolves: [4](#0-3) 
This further compounds the irreversibility: the address is locked from further spending the moment the (possibly erroneous) change unit is posted, well before finality, with no cancellation mechanism.

### Impact Explanation
A user, wallet, or asset issuer that posts an `address_definition_change` with an incorrect or unusable `new_definition_chash` permanently loses the ability to authorize any further unit from that address — freezing all base-currency and asset balances held at that address. For shared/multisig addresses (`wallet_defined_by_addresses.js`), this also freezes the funds of every cosigner, not just the initiator. For an asset issuer address, this can permanently prevent further issuance, transfer-condition management, or attestor-list updates for the asset. This satisfies the "AA fund loss or freezing" / permanent lock impact class called out in scope.

### Likelihood Explanation
This does not require a malicious peer, node, or hub — it is entirely self-inflicted by the address owner (or by any single author of a multi-authored address performing this change) through ordinary use of a documented, unprivileged message app (`address_definition_change`) that any wallet or AA-composed transaction can include. Given the report's own precedent (real-world audits flagging identical single-step transfer/renounce patterns as Medium/High), and that ocore's implementation offers no confirmation, delay, or two-step opt-in safety net, the likelihood of accidental, permanent address bricking is realistic, especially for programmatically generated `definition_chash` values (e.g., in shared-address flows) where a mismatch between the locally computed template hash and the actually-disclosed definition can silently occur.

### Recommendation
- Introduce an optional two-phase definition change: a first unit that proposes the new `definition_chash` (with the actual `arrDefinition` preimage disclosed inline, not just the hash), and a required second confirming unit/signal (from the *new* definition) before the old definition is invalidated for spending.
- At minimum, require that the `address_definition_change` message optionally carry the actual new definition (or a commitment verified against a client-side "dry validate" of the definition) so wallets can warn/reject before broadcasting if the definition doesn't parse or self-hash consistently.
- Provide wallet-level tooling (in `wallet_defined_by_addresses.js`/`wallet_defined_by_keys.js`) that mandatorily dry-runs `Definition.validateDefinition` against the *actual* candidate definition before ever composing/broadcasting an `address_definition_change`, rather than relying solely on hash equality checks after the fact.
- Consider a governance/time-delay option analogous to the report's recommendation, especially for asset-issuer and shared/multisig addresses where the blast radius spans multiple cosigners.

### Proof of Concept
1. Alice controls address `A` with definition `D0 = ["sig", {pubkey: pk0}]`.
2. Alice (or her wallet software) composes an `address_definition_change` message with `payload.definition_chash = H` where `H` is intended to be `chash160(D1)` for a new definition `D1` she plans to use, but due to a bug/typo/desync in derivation (e.g., a wallet-template placeholder resolved incorrectly, as in `wallet_defined_by_addresses.js`'s template-based address derivation), `H` does not actually equal `chash160(D1)` for any definition Alice possesses.
3. The unit passes `validateInlinePayload`'s checks — `isNonemptyObject`, no unknown fields, `isValidAddress(H)` — because these only check syntactic hash validity, not correspondence to a real, known definition: [5](#0-4) 
4. The unit stabilizes; `address_definition_changes` and `unit_authors.definition_chash` are updated to `H`: [6](#0-5) 
5. Any subsequent unit from address `A` must supply `author.definition` such that `chash160(author.definition) === H`. Since Alice cannot produce such a definition, every future signing attempt fails at `validateDefinition()`: [7](#0-6) 
6. Address `A` and all its balances (base and any assets) are now permanently frozen, with no recovery path in-protocol.
