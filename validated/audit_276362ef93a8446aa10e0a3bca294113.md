### Title
Node.js binding truncates out-of-range `cell_index` (`u64::MAX`) via `double` conversion, causing acceptance where C/Rust reject - (`bindings/node.js/src/kzg.cxx`)

### Summary
The Node.js binding decodes each `cell_indices[i]` with `get_cell_index()`, which converts the JS `Number` to a C++ `double` and then `static_cast<uint64_t>`, silently truncating/undefined-behavior-mapping any value that does not fit in a JS-safe double (e.g. `2^64-1`) into some in-range or unpredictable `uint64_t` before it ever reaches `verify_cell_kzg_proof_batch`'s bounds check. A spec-compliant binding (Rust, Python, Go, Java, Zig) that decodes the exact `u64` value `18446744073709551615` will hit `cell_indices[i] >= CELLS_PER_EXT_BLOB` in `src/eip7594/eip7594.c` and return `C_KZG_BADARGS`, while the Node.js binding may pass a truncated in-range value into the same C bounds check, which then does not reject the input for that reason and proceeds to verification instead.

### Finding Description
The broken equality is: `cell_indices[i]` (decoded value passed into `verify_cell_kzg_proof_batch`) in the Node.js binding == `cell_indices[i]` decoded value in Rust/Go/Python/Java/Zig bindings, for identical wire-encoded input `18446744073709551615`.

- The C bounds check itself is correct and value-agnostic: `if (cell_indices[i] >= CELLS_PER_EXT_BLOB) return C_KZG_BADARGS;` [1](#0-0)  — for the literal `uint64_t` value `18446744073709551615`, this check reliably returns `C_KZG_BADARGS` in every binding that passes the value through unmodified (Python via `PyLong_AsUnsignedLongLong` [2](#0-1) , Java via `GetLongArrayElements`/`jlong` [3](#0-2) , Go/Zig/Rust which use native `uint64_t`/`u64` types).
- The Node.js binding is different: `get_cell_index()` requires the JS value to be `IsNumber()` and converts it via `val.As<Napi::Number>().DoubleValue()` then `static_cast<uint64_t>(number)`. [4](#0-3) 
- JavaScript's `Number` type is an IEEE-754 double, which cannot exactly represent `2^64-1`. If the JS caller (a node's JSON/wire decoder that surfaces `cell_indices` as JS `Number`) represents `18446744073709551615` as a `Number`, it necessarily rounds to the nearest representable double, e.g. `18446744073709551616` (2^64), and `static_cast<uint64_t>(1.8446744073709552e19)` is undefined behavior in C++ for out-of-range doubles (in practice on most platforms/compilers it saturates or wraps to an implementation-defined value, commonly `0` or `UINT64_MAX` depending on compiler/architecture) — the exact resulting `uint64_t` is not guaranteed to reproduce the attacker's original out-of-range wire value, and depending on toolchain it can land in-range (`< CELLS_PER_EXT_BLOB`), which would let this specific cell index pass the bounds check in `verify_cell_kzg_proof_batch` where a spec-compliant binding rejects the same wire-encoded sidecar with `C_KZG_BADARGS`.
- This is called directly from `VerifyCellKzgProofBatch`: `cell_indices[i] = get_cell_index(env, cell_indices_param[i]);` [5](#0-4)  before the call to `verify_cell_kzg_proof_batch(&out, commitments, cell_indices, cells, proofs, num_cells, kzg_settings)`. [6](#0-5) 
- No guard in `get_cell_index` validates that the number is an integer, non-negative, within `Number.isSafeInteger` range, or within `[0, CELLS_PER_EXT_BLOB)` before the cast — only `IsNumber()` is checked. [4](#0-3) 

### Impact Explanation
This is not a forged-proof/false-accept vulnerability in the pure C core — `src/eip7594/eip7594.c`'s bound check is deterministic and correct for any `uint64_t` value actually passed to it. The actual divergence, if it occurs, is caused entirely by the Node.js binding's lossy JS-`Number`-to-`uint64_t` conversion, which is a binding-layer bug, not a core-library bug. Whether this produces a verdict mismatch depends on: (a) how the calling JS code decodes the wire-format `cell_indices` field (many Ethereum consensus libraries decode SSZ `uint64` fields into `BigInt` rather than `Number` specifically to avoid this class of bug, in which case `IsNumber()` in `get_cell_index` would already reject a `BigInt` argument with a `TypeError`, preventing the divergence entirely), and (b) the specific `static_cast<uint64_t>` behavior of the compiler/platform for an out-of-range double, which is undefined behavior and not guaranteed to land in-range. Because the bug is contingent on binding-level integer type choice (a caller/binding-integration issue) rather than a deterministic, reproducible flaw in `verify_cell_kzg_proof_batch` itself, and because the exact resulting truncated value is UB-dependent (not a fixed, provable in-range value), this does not meet the bar for a Critical finding under the stated impact requirement of a proof/verdict that reliably diverges from a spec-compliant node on identical wire bytes.

### Likelihood Explanation
Exploitability requires that the JS caller pass `cell_indices` as JS `Number` (not `BigInt`) containing the exact wire value `2^64-1`, and requires a specific compiler/platform-dependent UB outcome from `static_cast<uint64_t>` of an out-of-range double to land in `[0, CELLS_PER_EXT_BLOB)`. This is not a guaranteed, deterministic, cross-platform effect, and the finding falls into the "wrong trusted setup file... client developer misusing the API... a compromised dependency, build" adjacent gray area, i.e., it is more a binding-integration hazard than a reproducible bug in this repo's public API surface guaranteed to cause consensus divergence.

### Recommendation
In `bindings/node.js/src/kzg.cxx`, `get_cell_index()` should reject non-safe-integer or negative `Number` inputs (e.g., via `Number.isSafeInteger` check or requiring `BigInt` for `cell_indices`) before casting, and/or explicitly bounds-check against `CELLS_PER_EXT_BLOB` in the binding layer with a thrown `TypeError` for any value that isn't an exact non-negative integer representable in the JS double, rather than relying on an unchecked C++ narrowing cast.

### Proof of Concept
Not conclusively reproducible as a guaranteed, deterministic verdict mismatch without pinning a specific Node.js/V8/compiler ABI, since the outcome of `static_cast<uint64_t>(1.8446744073709552e19)` is undefined behavior. A conditional test would be: call `verifyCellKzgProofBatch(commitments, [18446744073709551615], cells, proofs)` from JS with `cell_indices` passed as a `Number` and confirm whether the resulting native `cell_indices[0]` (loggable via a debug build) lands `< CELLS_PER_EXT_BLOB`; compare against Rust's `verify_cell_kzg_proof_batch` called with `cell_indices: vec![u64::MAX]`, which is expected to always return `Err`/`C_KZG_BADARGS` per [1](#0-0) .
