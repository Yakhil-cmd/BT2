### Title
Webhook signature verification authenticates the payload's `organization`/`repository.owner.login`, but event handlers act on the payload's `repository.full_name` — allowing a mis-scoped org to authorize writes to a repository it doesn't own - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which `Shipit.github(organization:)` config (and therefore which `webhook_secret`) to validate a delivery against, based solely on `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) — a field taken directly from the unauthenticated JSON body. [1](#0-0) [2](#0-1) 

Once that check passes, the full raw JSON is handed unmodified to every registered handler: [3](#0-2) 

Handlers such as `PushHandler`, `PullRequest::OpenedHandler`, and `PullRequest::ReviewStackAdapter` look up the actual `Repository`/`Stack` to mutate using a **different** field of the same payload — `repository.full_name` — with no re-check that this repository belongs to the org that was authenticated. [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
The binding that should hold is: **organization authenticated == organization that owns the repository written**. Shipit supports a multi-org GitHub App configuration where each org has its own (optional) `webhook_secret`: [7](#0-6) [8](#0-7) 

Crucially, `verify_webhook_signature` treats a missing secret as automatic success, not automatic failure:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [9](#0-8) 

An installation running multiple orgs where at least one org has no `webhook_secret` configured (explicitly documented as optional) lets anyone submit an unsigned/arbitrarily-signed webhook body claiming `repository.owner.login` = that secret-less org. Signature verification is skipped for the whole request, yet nothing then confirms that the actually-processed `repository.full_name` belongs to that same secret-less org. Handlers freely resolve stacks/repositories from `full_name`: [10](#0-9) [11](#0-10) 

This is the direct analog of the ride-sharing bug: `verify_signature` is the "check" (`on_ride`), performed against one attacker-controlled key (`repository.owner.login`), while the mutation (`choose_ride` / creating stacks, syncing commits, updating statuses) is driven by a second, independent attacker-controlled key (`repository.full_name`) that is never re-validated against the first.

### Impact Explanation
An attacker can forge webhook events (push, pull_request, status, check_suite, membership, etc.) that are accepted as authentic for a different organization than the one actually referenced by `repository.full_name`, as long as any org in the installation has no `webhook_secret` set. Depending on which handler is targeted this can:
- Trigger `stack.sync_github` on arbitrary tracked stacks via `PushHandler`.
- Auto-provision or archive/unarchive review stacks via `PullRequest::OpenedHandler`/`ReviewStackAdapter` for repositories outside the "authenticated" org.
- Create/alter commit statuses (via the `status`/`state` handler) for arbitrary commits, which feed directly into `Commit#deployable?` and `MergeRequest#all_status_checks_passed?`, potentially enabling spoofed CI success to unlock an otherwise-blocked deploy or merge queue entry.

This crosses the "unauthorized deploy/merge" impact bar defined for High/Critical findings, without requiring any Shipit session, `ApiClient` token, or GitHub App private key.

### Likelihood Explanation
Requires: (1) the target installation to use the documented multi-org GitHub App configuration, and (2) at least one configured org to have left `webhook_secret` unset (explicitly supported/optional per `docs/setup.md`). Given the config is officially "optional," and operators frequently leave secondary/staging orgs without a webhook secret, this is a realistic misconfiguration rather than a purely theoretical one. No credentials or prior access are needed by the attacker.

### Recommendation
After resolving the event's target repository/stack (`repository.full_name`), verify that its owning organization matches `repository_owner`/the org used to select the webhook secret, and reject the request if they differ. Additionally, treat a missing `webhook_secret` as "fail closed" (reject signature-less orgs) or require an explicit opt-in flag to allow unsigned webhooks, rather than defaulting to `true`.

### Proof of Concept
1. Configure Shipit with two orgs: `org-a` (no `webhook_secret`) and `org-b` (has a `webhook_secret`, and owns a tracked `Stack` for `org-b/victim-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
No valid `X-Hub-Signature` is required because `verify_webhook_signature` short-circuits to `true` for `org-a`.
3. `verify_signature` passes (`repository_owner` = `org-a`, secret-less), and `PushHandler#process` resolves and mutates the `org-b/victim-repo` stack based on `repository.full_name`, which was never checked against `org-a`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
