### Title
Unescaped Regex Metacharacters in `has_only()` Allow Bypass of AA Character-Whitelist Checks - ([File: formula/evaluation.js])

### Summary
The oscript function `has_only(str, charset)`, used by Autonomous Agents (AAs) to verify that a string contains only characters from an allowed set, builds a JavaScript `RegExp` character class directly from the attacker/trigger-influenced `charset` argument. It only escapes the `]` character and rejects a trailing backslash, but does not neutralize other regex metacharacters that have special meaning inside a character class — most notably a leading `^`, which negates the whole class. This mirrors the CVE-2018-16398 root cause: a security-relevant string comparison implemented via a naively-constructed regular expression can be subverted by injecting regex syntax instead of literal characters, silently inverting the intended policy.

### Finding Description
`has_only` is implemented in the evaluator as: [1](#0-0) 

The code:
1. Rejects `charset` values containing `\]` or ending in `\`.
2. Escapes literal `]` characters.
3. Otherwise inserts `charset` verbatim into `"^[" + sub + "]*$"` and tests it against `str`.

This means any other regex-significant character is passed through untouched. In a JS character class, a leading `^` means "match anything except the following characters." If a caller supplies a `charset` value that begins with `^`, the semantics of the whitelist flip to a blacklist without any error or warning — the exact same "regex mishandled → policy check reversed/bypassed" pattern described in the external report (where crafted input made a path-matching regex behave differently than the intended allow/deny policy).

`has_only` is a first-class oscript primitive documented for AAs to validate that trigger-supplied strings (e.g., codes, identifiers, referral tokens, memo fields) only contain expected characters before trusting them in further logic (fund releases, state transitions, whitelist enforcement). Both operands can originate from `trigger.data`, `state` variables written from prior triggers/oracles, or `params` — i.e., data reachable by an ordinary AA trigger sender: [2](#0-1) 

Grammar/parser confirm `has_only` accepts arbitrary expressions for both arguments, not just string literals: [3](#0-2) 

### Impact Explanation
If an AA's business logic uses `has_only()` as a validation gate — e.g., "only continue if the supplied code/parameter contains only digits/letters" before releasing funds, updating balances, or accepting an otherwise-restricted operation — an attacker who can influence the `charset` operand (directly, or indirectly via chained state built from earlier attacker-controlled triggers) can prepend `^` to invert the check, causing the AA to accept input it was designed to reject. Depending on the AA's logic this can lead to fund loss/incorrect payouts from the AA (a permitted "unauthorized spending"/"AA fund loss" outcome per the validation criteria), since the bypass happens deterministically and silently (no exception, no fatal error — `bMatches` is simply computed against inverted semantics).

### Likelihood Explanation
Exploitability depends on how a specific AA uses `has_only()`, so it is not a universal, unconditional break of every AA — but the function's entire purpose is character-set validation used as a business-logic gate, and both arguments are reachable from trigger/state data controllable by an ordinary AA trigger sender. Any AA that builds the allowed-charset argument even partially from attacker-influenced data (a realistic pattern for dynamic whitelists, e.g. combining a base charset with a state-configured suffix) is vulnerable to this bypass without any special privilege.

### Recommendation
In `formula/evaluation.js`, when constructing the character class for `has_only`, escape all regex-special characters in `sub` (`^ ] \ - ` and any other character class-significant symbols), not just `]`, before interpolating into the `RegExp`. Alternatively, avoid `RegExp` construction entirely and implement `has_only` via direct character-by-character membership testing (e.g., build a `Set` of allowed characters after literally decoding the intended charset) so that no character in `charset` can alter the matching semantics.

### Proof of Concept
Within an AA formula, if the allowed-charset value can include a leading `^` (e.g. constructed dynamically as `"^" || some_state_var` or otherwise influenced by trigger data):
```
has_only("secretbypass", "^0123456789")
```
This evaluates the regex `^[^0123456789]*$`, i.e. "string contains no digits," rather than the intended "string contains only digits." A string that should have failed a digits-only whitelist (`"secretbypass"`) now passes, because the class was negated by the unescaped leading `^`. Any AA gating a fund-releasing or state-changing branch on this call can be manipulated into taking the unintended branch.

**Note on certainty:** I could not find a concrete, shipped AA template in this repository that uses `has_only()` with an attacker-influenced `charset` argument, so the concrete "AA fund loss" impact is conditional on how a given AA author uses this primitive rather than an unconditional, always-exploitable break of ocore itself. The root-cause regex-escaping defect in `formula/evaluation.js` (lines 2037-2049) is confirmed and directly analogous to the CVE's "mishandled regular expression" bug class.
