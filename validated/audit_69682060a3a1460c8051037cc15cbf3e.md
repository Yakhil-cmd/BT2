### Title
Webhook signature verification is bound to `repository.owner.login`, not to `repository.full_name` that handlers act on, allowing cross-organization event forgery in multi-app deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is the Shipit analog of the Tigris `Lock.extendLock` bug: two code paths use different fields of the same untrusted payload to make security-relevant decisions, and the field that is authorized is not the field that is acted upon.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), which is itself taken straight out of the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` trivially returns `true` when the resolved app's `webhook_secret` is blank/`nil`: [3](#0-2) 

`webhook_secret` is explicitly documented and shipped as optional/`nil` per organization, including in multi-organization deployments (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`).

Once the request clears `verify_signature`, the actual event handler resolves the target `Repository`/`Stack` using an entirely different field — `repository.full_name` — with no relation back to the org that was "authenticated": [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` and looks it up independently of any organization context: [6](#0-5) 

The equality that should hold but does not is:
`organization whose signature was verified (repository.owner.login) == organization owning the repository whose Stack is mutated (repository.full_name)`

Before the attack: in a `Shipit.github_organizations` multi-app configuration, org `A` (attacker-influenced or with no webhook secret set) and org `B` (a fully trusted, secured org) each have their own `Stack`s. After the attack: an unprivileged, unauthenticated caller (no Shipit session, no `ApiClient` token, no GitHub App private key, no repository write access) POSTs to `/webhooks` with `repository.owner.login = "A"` (an org configured with `webhook_secret: nil`, as shown to be a supported, documented configuration) and `repository.full_name = "B/target-repo"`. `verify_signature` calls `Shipit.github(organization: "A")`, whose `verify_webhook_signature` returns `true` unconditionally because `A`'s secret is blank — no valid HMAC is required at all. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then runs the handler against `params`, and `Handler#stacks` resolves stacks for `B/target-repo` via `repository.full_name`, completely bypassing any check tied to org `A`.

### Impact Explanation
This is an authentication bypass: the signature check that is supposed to gate the ability to inject GitHub events is bound to a field (`repository.owner.login`) that is disjoint from the field the business logic actually trusts (`repository.full_name`). In a multi-org install where at least one configured org has no `webhook_secret` (a documented, supported default), an unauthenticated attacker can forge `push` events to trigger `GithubSyncJob`/`sync_github` on stacks belonging to a *different, secured* organization, and forge `status`/`check_suite` events to fabricate passing CI, potentially enabling unauthorized merges/deploys on repositories the attacker has no access to. This falls squarely under "authentication bypass" / "unauthorized deploy" impact.

### Likelihood Explanation
Requires only that the Shipit instance be configured with `Shipit.github_organizations` for multiple GitHub orgs and that at least one of them has no `webhook_secret` set — a state explicitly presented as valid/default in `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`. No credentials, session, or GitHub write access are needed; only knowledge that such an org name exists in the deployment's config (which may be guessable or discoverable via public GitHub App installation listings).

### Recommendation
Bind the verified identity to the field the handlers actually use to select the target repository: extract `repository_owner`/`organization` from `full_name` (or otherwise ensure `repository.owner.login`/`organization.login` and the owner segment of `repository.full_name` are cross-checked to be identical) before dispatching to `Shipit::Webhooks.for_event`. Additionally, do not allow `verify_webhook_signature` to short-circuit to `true` for organizations with a blank `webhook_secret` when other organizations in the same deployment have one configured — either require all configured orgs to set a secret, or reject payloads whose `repository.full_name` owner segment does not match the org resolved during signature verification.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `A` (`webhook_secret: nil`) and `B` (`webhook_secret: "real-secret"`), each with existing tracked `Stack`s (`A/repoA`, `B/repoB`), as supported by `docs/setup.md`'s "Using Multiple Github Applications" section.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "A" }, "full_name": "B/repoB" }
}
```
No `X-Hub-Signature` header, or any garbage value, is required.
3. In `verify_signature`, `repository_owner` resolves to `"A"`; `Shipit.github(organization: "A").verify_webhook_signature` returns `true` because `A.webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `Shipit::Webhooks.for_event('push')` runs `PushHandler`, whose `stacks` call resolves `Repository.from_github_repo_name("B/repoB")` — org `B`'s stack — and triggers `stack.sync_github(expected_head_sha: params.after)`, entirely bypassing any check tied to org `B`'s (correctly configured) secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
