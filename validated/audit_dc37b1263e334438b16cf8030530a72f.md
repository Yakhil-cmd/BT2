### Title
Rounding-based inflation of headers commission via attacker-controlled `earned_headers_commission_recipients` shares - (File: headers_commission.js)

### Summary
`SponsorPaymaster._postOp()` credits `balances[owner()]` with `ethCost` while the corresponding real ETH backing (`EntryPoint` deposit) is simultaneously drained to the bundler, so the sum of internally recorded balances no longer matches the real reserve, eventually causing insolvency for other depositors. The analogous root-cause class — an internal ledger crediting more value to accounts than is actually backed by the real, fixed source amount — exists in ocore's headers-commission distribution logic in `calcHeadersCommissions()` in `headers_commission.js`, where a unit's fixed `headers_commission` is split among `earned_headers_commission_recipients` using independent per-recipient rounding that can sum to more than the original amount, effectively minting extra spendable bytes.

### Finding Description
When a unit wins headers commission from a parent unit, the total payable amount is fixed: `full_amount = punits.headers_commission` (a value baked into the parent unit at creation time and never increased). This fixed amount is then split among the winning child unit's `earned_headers_commission_recipients`: [1](#0-0) 

Each recipient's share is rounded independently with `Math.round(full_amount * share / 100.0)` (both in the in-RAM path and in the SQL path): [2](#0-1) 

The resulting per-recipient amounts are inserted into `headers_commission_contributions` and subsequently aggregated into `headers_commission_outputs`, which become real, spendable base-asset outputs: [3](#0-2) 

The only validation constraint on `earned_headers_commission_recipients` is that the shares are positive integers, addresses are sorted/unique, and shares sum to exactly 100: [4](#0-3) 

There is no requirement that the recipients correspond 1:1 to unit authors — the code comment in `headers_commission.js` explicitly acknowledges recipients can be "another address" not among the authors, and nothing caps the number of recipients besides "positive integer share, sum to 100" (so up to 100 recipients with 1% shares are possible). Because each recipient's share of `full_amount` is rounded independently rather than the remainder being distributed exactly once, an attacker who fully controls both the number/shares of recipients and (indirectly) the exact byte size of their own unit (and thus `headers_commission`, which is deterministically derived from header size via `objectLength.getHeadersSize`) can choose values such that `full_amount * share_i / 100` lands just above `x.5` for many recipients simultaneously. Since `Math.round` always rounds `.5` up, the sum of all rounded per-recipient amounts can exceed `full_amount` by a significant margin (e.g., with 100 recipients each holding a 1% share and `full_amount = 150`, each `Math.round(1.5) = 2`, summing to 200 instead of 150 — a 33% inflation of that single commission payout, and the multiplier increases with more/careful recipient counts).

This directly parallels the reported bug class: an unprivileged actor causes an internal credited-balance total to diverge from (in this case exceed) the fixed real backing amount, and the excess is realized as genuine spendable base-asset (bytes) outputs once `headers_commission_outputs` is spent — i.e., new money created without a corresponding real payment, unlike the paymaster case where the mismatch instead causes insolvency for other accounts. Both stem from the same defect pattern: crediting derived/split amounts to multiple parties without enforcing that the sum equals the fixed source amount.

Note: the code's own internal consistency check (`_.isEqual(arrValuesRAM.sort(), arrValues.sort())`) only cross-validates the JS(RAM) computation against the SQL computation of the *same flawed rounding formula* — it does not validate that the sum of distributed amounts equals `full_amount`, so the bug is not self-detected by existing sanity checks.

### Impact Explanation
This is a supply-inflation bug reachable by any unprivileged unit poster: by crafting a multi-authored unit (or a unit whose `earned_headers_commission_recipients` names non-author addresses) with carefully chosen recipient counts/shares and by controlling the resulting unit's header size (hence `headers_commission`) via padding/parent selection, an attacker can cause `headers_commission_outputs` to be credited with more base-currency (bytes) than the network actually collected as headers commission from the payer unit. Those extra bytes are fully real, spendable, immediately-visible balances once the corresponding MC index stabilizes and the commission input becomes spendable — this constitutes unauthorized creation of new bytes, i.e., money supply inflation, without any compensating burn or payment.

### Likelihood Explanation
Likelihood is high for a determined attacker: all the necessary parameters (number of recipients, their shares, and to some extent the exact header size that determines `headers_commission`) are fully within the attacker's control when composing their own unit(s); no privileged role, hub cooperation, or network timing condition is required, only ordinary unit posting rights. The main engineering effort is precisely tuning header size/recipient shares to maximize the aggregate rounding-up effect, which is a deterministic, offline computation.

### Recommendation
Distribute the fixed `full_amount` exactly once across recipients rather than rounding each recipient's share independently — e.g., compute all-but-the-last recipient's share with `Math.round`/`Math.floor` and assign the last recipient the exact remainder (`full_amount - sum_of_previous`), guaranteeing the sum of distributed amounts always equals `full_amount`. Apply the same fix consistently to both the RAM computation path and the SQL computation path in `calcHeadersCommissions()` in `headers_commission.js`, and add an explicit assertion that the total distributed per `(child_unit, payer_unit)` equals `assocWonAmounts[child_unit][payer_unit]` before inserting into `headers_commission_contributions`.

### Proof of Concept
Conceptual (based on code inspection of `headers_commission.js:176-209` and `validation.js:1101-1126`; not executed against a live network):
1. Attacker crafts a unit `U` with sufficient content/padding so that `objectLength.getHeadersSize(U)` (and hence `U.headers_commission` once it becomes a parent that wins headers commission) equals `150` (or any value producing exact `.5` boundaries when divided by chosen shares).
2. Attacker sets `authors` with `earned_headers_commission_recipients` containing 100 entries, each `earned_headers_commission_share: 1`, with addresses sorted and summing to 100 — this passes `validateHeadersCommissionRecipients` in `validation.js:1101-1126`.
3. When `U` wins headers commission from a parent payer unit whose `headers_commission = 150`, `calcHeadersCommissions()` computes, for each of the 100 recipients, `Math.round(150 * 1 / 100) = Math.round(1.5) = 2`, inserting `100 * 2 = 200` total into `headers_commission_contributions`/`headers_commission_outputs` instead of the correct `150`.
4. The extra `50` bytes become real, spendable outputs across the 100 recipient addresses once matured, realizing unbacked supply inflation.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
