### Title
Webhook signature verification is bound to the payload's `repository.owner`/`organization` login, but every handler resolves and writes to a *different* repository/commit taken from unauthenticated payload fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC with by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body, then hands the *entire* parsed body to the event handlers. The handlers, however, resolve the actual repository/stack/commit to write to using a completely different field of that same untrusted body (`repository.full_name`, or in the `status` handler, no repository scoping at all - just the raw `sha`). Nothing ties "the organization whose secret validated this request" to "the repository/commit that gets written to." This is the same class of bug as the ETH-refund report: a value that is acted upon is never covered by the check that is supposed to authorize the action.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and asks for that organization's GitHub App config to verify the signature: [1](#0-0) [2](#0-1) 

Since Shipit supports multiple configured GitHub organizations, each with its own `webhook_secret`: [3](#0-2) 

...an actor who legitimately controls the webhook secret for organization `A` (e.g. because they administer the GitHub App installation on their own low-privilege org/repo) can independently POST a hand-crafted, correctly-signed request straight to the public `/webhooks` endpoint. Nothing forces `repository.owner.login`/`organization.login` (used only for signature selection) to match `repository.full_name` (used to pick the target) inside the same JSON body - both are attacker-controlled fields inside the payload that this same secret signs.

Once the signature passes, the base `Handler` resolves the target purely from `repository.full_name`: [4](#0-3) 

The `push` handler uses that resolution to enqueue a sync job against whatever stack matches `full_name`: [5](#0-4) 

`GithubSyncJob` then fetches commits and writes them to that stack's DB records: [6](#0-5) 

Even worse, `StatusHandler` performs no repository scoping whatsoever - it looks up commits **globally by SHA** across the entire Shipit installation and writes a CI status to whichever commit matches: [7](#0-6) 

That status feeds directly into deploy-gating logic: [8](#0-7) [9](#0-8) 

So the binding that should hold - `organization authenticated == organization owning the repository/commit written` - is never enforced. `Shipit.github(organization: repository_owner)` only picks the secret used to validate the bytes of the request; it has no relationship whatsoever to which stack/commit the handlers subsequently mutate.

### Impact Explanation
- **Cross-tenant writes (`push` event):** an attacker who controls a legitimate webhook secret for organization `A` can forge a payload with `repository.owner.login = A` (to pass signature verification) but `repository.full_name = "B/some-other-repo"`, causing `GithubSyncJob` to run against organization `B`'s stack and write `Commit` records to it, even though the attacker has no privilege for `B` at all.
- **Cross-tenant CI status injection (`status` event, more severe):** `StatusHandler` has zero repository scoping - it matches purely on commit `sha`. An attacker (again only needing a valid secret for their own low-privilege org) can inject a forged `success` status for a specific commit SHA belonging to a target's public repository. Because `Commit#deployable?` and `Commit#blocked?` rely on `Status` records, this can falsely mark a target commit as CI-passing/deployable, undermining `ci.require`/blocking-status protections that are meant to gate the merge queue and continuous delivery - i.e. an unauthorized-deploy enabler.

This satisfies the required impact bar (cross-repository writes / unauthorized deploy) via a genuine credential/authorization-boundary mismatch, not a hypothetical.

### Likelihood Explanation
Exploitation requires only possession of *any* organization's `webhook_secret` configured in the Shipit instance (a routine, legitimate credential an org owner/admin holds for their own tenant on a shared multi-org Shipit deployment) plus knowledge of the target's repository `full_name` (public information) or a target commit SHA (public for public repos, or leaked via CI/status logs). No GitHub-side access to the victim organization or repository is required, and `/webhooks` is an unauthenticated, internet-reachable endpoint. This is realistic in any multi-tenant Shipit installation serving more than one GitHub organization.

### Recommendation
Bind the verified identity to the write target instead of trusting independent fields of the same payload:
- After `verify_signature` succeeds, pass the verified `repository_owner`/organization down to the handler layer and require `Handler#repository_name`'s owner segment to equal the verified organization before resolving/mutating any stack.
- In `StatusHandler`, scope the `Commit` lookup by the resolved, verified repository/stack instead of a bare, cross-tenant `sha` match.
- Consider verifying signatures per-repository (using the specific `Stack`/`Repository`'s configured hook secret) rather than per-organization-from-payload, so the secret used for verification is tied to the exact resource being mutated.

### Proof of Concept
1. Configure two GitHub organizations in `secrets.yml`, `orgA` (attacker-administered) and `orgB` (victim), each with distinct `webhook_secret`s, both onboarded onto the same Shipit instance (as supported by `config/secrets.development.shopify.yml`).
2. Attacker crafts a `push` (or `status`) JSON body where `repository.owner.login` = `"orgA"` (so `WebhooksController#verify_signature` selects `orgA`'s secret) but `repository.full_name` = `"orgB/victim-repo"` (or, for `status`, sets `sha` to a known commit SHA of `orgB/victim-repo`).
3. Attacker computes `X-Hub-Signature` using `orgA`'s webhook secret (which they legitimately possess) over that crafted body, per `verify_webhook_signature`: [10](#0-9) .
4. POST this request to `/webhooks`. `verify_signature` passes (signed correctly with `orgA`'s secret). The dispatched handler (`PushHandler`/`StatusHandler`) resolves and mutates `orgB`'s stack/commit using the unrelated `full_name`/`sha` fields, as shown above - despite the request never having been authenticated as belonging to `orgB`.

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
