### Title
Webhook signature is verified against the organization derived from the payload while the effect is applied to whatever repository the same payload names - allowing cross-repository stack manipulation within an org from a single leaked org-level webhook secret ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check by extracting only `repository.owner.login` (or `organization.login`) from the JSON body and verifying the whole raw payload against that organization's `webhook_secret`. The `repository.full_name` field used later to select *which* `Stack`/`Repository` the event actually mutates is never itself bound to the verification decision beyond being part of the same organization. Because `Shipit.github(organization:)` configuration allows one `webhook_secret` per organization (see `config/secrets.development.example.yml`, which documents one secret governing every repo under `somegithuborg`), knowledge of that single org-wide secret is sufficient to forge a signed payload for **any** repository under that organization, even one the possessor is not authorized to administer within Shipit.

### Finding Description
`verify_signature` computes the expected signer purely from `repository_owner`: [1](#0-0) 
and `Shipit::GitHubApp#verify_webhook_signature` does a straight HMAC compare of the raw body against the per-organization `webhook_secret`: [2](#0-1) 

Downstream, every webhook `Handler` resolves the target `Stack` purely from `payload.dig('repository', 'full_name')`: [3](#0-2) 

The verified property is "this payload was signed with organization X's secret." The acted-upon property is "apply this event to repository `full_name`," which can be **any** repo in organization X. The engine's configuration model explicitly supports a single shared `webhook_secret` per organization for all its repositories: [4](#0-3) 

This is the same class of bug as the report: a verification step covers a coarser scope (the EigenLayer recipient/claim call vs. the Router's actual balance movement; here, "organization" vs. "specific repository") than the scope the subsequent state-changing logic actually operates on ("repository.full_name" chosen entirely by the unverified-at-that-granularity payload field).

### Impact Explanation
Any actor capable of producing (or replaying/tampering) a validly-signed payload for one repository in an organization - e.g., someone who has legitimate GitHub App webhook delivery access, or has otherwise obtained the organization's shared `webhook_secret` for one repo - can craft/deliver events for a *different* repository in the same org that they have no delivery rights to. Handlers such as the push handler enqueue `GithubSyncJob`, and other handlers create `Membership`/`Team` records, close pull requests, or mutate commit/CI status for that unrelated repository's stacks, none of which are gated by any per-repository check. This crosses the "repository write access" trust boundary the app relies on (each repo's Shipit stack is supposed to be updatable only by events genuinely originating from GitHub for that exact repo).

### Likelihood Explanation
Exploitation requires possession of the organization-level `webhook_secret`, which is a real but plausible failure mode given Shipit's own documented configuration pattern (one secret shared by every repo of an org) and the fact that GitHub App webhook secrets are often handled/rotated by less-trusted automation or shared across teams managing many repos. No repository write access, ApiClient token, or GitHub OAuth session is required - only the ability to send an HTTP POST to `/webhooks` with a correctly-signed body, which is exactly the class of "unprivileged" cross-boundary case in scope.

### Recommendation
Bind the verification granularity to the same identifier the handlers act on: verify the signature per-repository (store/validate a secret scoped to `repository.full_name`, not just `repository.owner.login`), or, at minimum, re-validate that the authenticated organization from the App installation context actually installed/authorizes the specific `repository.full_name` named in the payload before dispatching handlers, e.g. via a lookup against the App's installation repository list rather than trusting the payload's own `full_name` field.

### Proof of Concept
1. Organization `acme` is configured in Shipit with a single `webhook_secret` (per `config/secrets.development.example.yml` pattern) shared by `acme/service-a` and `acme/service-b`.
2. An actor with legitimate GitHub webhook delivery configuration for `acme/service-a` (or who otherwise obtains the org secret) computes `HMAC-SHA1(webhook_secret, body)` for a crafted `push` payload whose `repository.owner.login = "acme"` (for verification) but `repository.full_name = "acme/service-b"` (for the actual effect):
   ```ruby
   body = { repository: { owner: { login: "acme" }, full_name: "acme/service-b" }, ref: "refs/heads/master", after: "<any_sha>" }.to_json
   sig = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", webhook_secret, body)
   ```
3. `POST /webhooks` with header `X-Hub-Signature: sig` and `X-Github-Event: push` and this body.
4. `verify_signature` passes (org matches), and `PushHandler`/`Handler#stacks` resolves `Repository.from_github_repo_name("acme/service-b")`, dispatching sync/deploy-triggering jobs against `acme/service-b` even though the caller had no delivery rights on that repository.

Note: because this depends on the deployment actually sharing one `webhook_secret` across multiple repositories within an org (an explicitly documented supported configuration), full confirmation of exploitability in a specific deployment would require inspecting that deployment's `config/secrets.yml`, which is outside the indexed engine code available here.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
