### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table, with no scoping to the repository that sent the webhook, unlike every other handler (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) which resolve a `stacks`/`repository` scope from `payload['repository']['full_name']` before touching any record. Because `Status#state` includes `error`, and `Commit#blocking?` (delegated to `status`) directly drives `Commit#blocked?` for all later commits in a stack, an attacker who can get a signed "status" webhook accepted for any repository under the same GitHub organization can write an `error`/`failure` `Status` row onto a commit belonging to a completely unrelated stack, as long as that commit's `sha` matches.

### Finding Description
The broken binding is:
`commit.stack.repository == Repository.from_github_repo_name(payload.dig('repository','full_name'))` — this equality is asserted by `Webhooks::Handlers::Handler#stacks` for `PushHandler`/`CheckSuiteHandler`/PR handlers [1](#0-0)  but is **never checked** in `StatusHandler`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`StatusHandler` doesn't even declare/use `repository`/`stacks` in its `params` schema at all — it only requires `sha`, `state`, and optional fields, with no `repository` binding used to filter the query [3](#0-2) .

`Commit#sha` is not scoped to be globally unique nor tied uniquely to one repository/stack — the model is `belongs_to :stack` with no repository-level uniqueness constraint visible in the model [4](#0-3) . `create_status_from_github!` then unconditionally replicates the forged state into a `Status` row tied to `commit.stack_id` (the victim stack, not the attacker's) [5](#0-4) [6](#0-5) .

Once persisted, `Commit#blocking?` is delegated straight to `status.blocking?` [7](#0-6) , and every later, still-undeployed commit in that same victim stack checks it via:
```ruby
def blocked?
  return false if stack.blocking_statuses.empty?
  stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
end
``` [8](#0-7) 

**Why existing guards fail:** `WebhooksController#verify_signature` only validates that the request is signed by the correct *organization*'s app secret — `Shipit.github(organization: repository_owner)` — it does not validate that the specific `repository.full_name` in the payload matches any particular stack, nor does it constrain which repository within that org is allowed to reference which commit [9](#0-8) [10](#0-9) . That check authenticates "a repo in this org sent this," not "this repo owns this commit." The `ExplicitParameters` schema for `StatusHandler` has no `repository` requirement to even enforce format validation on the source repo, unlike `PushHandler`/`CheckSuiteHandler`, which do scope via `stacks`.

**Attacker exploit flow:** per the stated threat model, the attacker can "emit webhooks from a repository they own." If the attacker owns/controls a repository within the same GitHub organization as the victim's stack (e.g., a repo the org's GitHub App is installed against — a common org-wide installation), they can trigger a real, validly-signed `status` GitHub webhook event on their own repository whose `sha` collides with a commit already ingested into the victim's stack. Because many `Commit` shas originate from forkable/public history (git object hashes are content-addressed, so shared history/forks reproduce identical shas without needing an actual SHA-1 break), the attacker can set the GitHub Status API state to `error` on their own repo for a commit sha that is shared history with the victim repo. GitHub delivers a signed `status` webhook (signed with the org's shared app secret) that Shipit's `verify_signature` accepts, then `StatusHandler.process` matches `Commit.where(sha:)` against the victim's `Commit` row (found purely by sha) and writes an `error` `Status` onto it — corrupting the victim stack's blocking chain without ever naming the victim's repository in a way that's checked.

### Impact Explanation
An attacker-controlled repository's signed webhook can write a `Status` row (`state: 'error'`) onto a `Commit`/`Stack` it never authenticated ownership of, corrupting `blocking?`/`blocked?`/`deployable?` for the victim stack. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team": the write is unauthorized cross-repository state mutation of `Shipit::Commit`/`Shipit::Status` rows. It is repeatable against any stack whose commits share a sha reachable by the attacker (any commit in shared/forked history, or any commit the attacker can otherwise learn the sha of, since `StatusHandler` performs no repository-scoped lookup at all) — the blast radius spans every stack in the Shipit instance whose repository lives in the same GitHub organization as an attacker-controlled repo.

### Likelihood Explanation
Preconditions: (1) attacker controls a repository under the same GitHub organization/App installation as the victim's Shipit-tracked repository (consistent with the stated "emit webhooks from a repository they own" capability); (2) the victim stack has `blocking_statuses` configured (`stack.blocking_statuses.empty?` guard in `Commit#blocked?`); (3) attacker knows/reproduces a sha of an older commit in the victim's stack (trivial for forks/shared history, no actual collision required for the general case). No Shipit session, API token, or repo maintainer role is needed — only a legitimately signed webhook from any org repo, which `verify_signature` accepts because it checks organization identity, not repository identity.

### Recommendation
Scope `StatusHandler#process` (and any similar sha-based lookup) to the stacks belonging to the payload's own repository, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Require `repository.full_name` in `StatusHandler`'s `params` schema and use `Handler#stacks`/`Repository.from_github_repo_name` to constrain the commit lookup, exactly as `CheckSuiteHandler` already does with `stacks.where(branch:)` before touching commits.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook from unrelated repository mutates a victim stack's blocking chain" do
          victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
          victim_stack.update!(cached_deploy_spec: DeploySpec.new(
            'ci' => { 'blocking' => ['ci/important'] }
          ))

          older_commit = shipit_commits(:first)  # belongs to victim_stack
          newer_commit = shipit_commits(:second) # belongs to victim_stack, id > older_commit.id
          older_commit.statuses.destroy_all

          refute older_commit.reload.blocked?
          refute newer_commit.reload.blocked?

          # Forged payload claims to originate from an attacker-owned repository,
          # never naming victim_stack.repository.full_name
          payload = {
            'sha' => older_commit.sha,
            'state' => 'error',
            'context' => 'ci/important',
            'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'shopify' } }
          }

          StatusHandler.call(payload)

          # Equality claimed broken: commit.stack.repository != payload's repository,
          # yet the write still lands on victim_stack's commit.
          assert_equal 'error', older_commit.reload.status.state
          assert older_commit.blocking?
          assert newer_commit.reload.blocked?
        end
      end
    end
  end
end
```
This demonstrates the divergence without contacting live GitHub: `StatusHandler.call` is invoked directly with a forged payload whose `repository.full_name` never matches `victim_stack`'s repository, yet `Commit.where(sha:)` still finds and mutates the victim's commit/status rows.
