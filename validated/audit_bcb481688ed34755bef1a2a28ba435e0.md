### Title
Webhook signature validated against organization derived from the payload while the acted-upon repository comes from an independently-parsed field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login`, falling back to `organization.login` if the `repository` object lacks an `owner` sub-key. The webhook body handlers (e.g. `Shipit::Webhooks::Handlers::Handler#stacks`), however, independently parse `payload.dig('repository', 'full_name')` to determine which `Repository`/`Stack` to act on. These two payload reads are never cross-checked, so the "organization whose secret authenticated the request" and the "repository the handler writes to" are two different, uncorrelated bindings — the exact bug class described in the report (a value used for a check is not the same value that is actually consumed downstream).

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to pick the `github_app`/`webhook_secret` used for HMAC verification: [2](#0-1) 

Meanwhile, every default handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the target `Repository`/`Stack` via:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 
`Repository.from_github_repo_name` splits `owner/name` straight from that string with no relation back to `repository_owner`: [4](#0-3) 

Because Ruby's `Hash#dig` returns `nil` for missing keys rather than raising, an attacker can send a raw JSON body such as:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "victim-org/private-repo" },
  "organization": { "login": "attacker-org" }
}
```
`repository_owner` resolves to `"attacker-org"` (no `repository.owner.login` present, so it falls back to `organization.login`). If `attacker-org` is one of the organizations configured on this shared multi-tenant Shipit install and the attacker legitimately controls that org's GitHub App/webhook configuration (i.e., knows its `webhook_secret` — a lower-trust boundary than administering `victim-org`), the attacker can correctly compute `X-Hub-Signature` for the raw body using `attacker-org`'s secret. `verify_signature` passes. The `PushHandler` then reads `repository.full_name` = `"victim-org/private-repo"` and looks up and acts on `victim-org`'s stacks — an org the attacker's signing key was never authorized for.

This breaks the intended binding: `organization whose webhook_secret authenticated the request == organization whose repository is acted upon`. The two sides diverge because they are parsed from different, independently attacker-controlled JSON paths within the same signed body.

### Impact Explanation
`PushHandler#process` enqueues `stack.sync_github(expected_head_sha:)` for every matching stack of the forged repository, which schedules `GithubSyncJob`. This job fetches commits via `stack.github_api` (the victim org's own credentials, unaffected) and, more importantly, updates the deploy spec cache (`CacheDeploySpecJob`) and can drive continuous delivery scheduling logic tied to stack updates. `CheckSuiteHandler` and `StatusHandler` can likewise create/refresh commit statuses and check runs on the victim's commits, influencing `deployable?` checks that gate deploy approval in the UI/API. An attacker forging cross-organization webhook traffic can therefore manipulate a stack's perceived CI/status state and trigger unscheduled sync/deploy-spec cache activity for a repository/org they are not authorized to interact with, which can feed into an unauthorized deploy decision downstream (Shipit gates deploys on `Commit#deployable?`/CI status which these handlers mutate).

### Likelihood Explanation
Exploitation requires the attacker to control (or have legitimately configured) at least one organization's `webhook_secret` on a Shipit instance that hosts multiple organizations — a realistic operational scenario for shared/multi-tenant Shipit deployments where different teams manage their own GitHub App installations pointing at the same Shipit instance. No GitHub session, `ApiClient` token, or repository write access to the victim org is needed; only the ability to send a raw HTTP POST to the public `/webhooks` endpoint with a self-signed, self-crafted JSON body.

### Recommendation
After computing `repository_owner` for signature selection, re-derive the "acting" repository/organization strictly from the same authenticated value, or explicitly validate that `payload.dig('repository','full_name')`'s owner segment matches `repository_owner` before dispatching to handlers. Reject (422) whenever `repository.full_name`'s owner and `repository_owner` disagree, and stop falling back silently to `organization.login` when a `repository` object with a different owner is also present in the payload.

### Proof of Concept
1. Configure two organizations on one Shipit instance: `attacker-org` (secret known to attacker) and `victim-org` (contains stack `victim-org/private-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{"ref":"refs/heads/main","after":"deadbeef...","repository":{"full_name":"victim-org/private-repo"},"organization":{"login":"attacker-org"}}
```
3. Set `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"attacker-org"` (via `params.dig('organization','login')` since `repository.owner` is absent), validates successfully using `attacker-org`'s secret.
5. `PushHandler#process` reads `repository.full_name` = `"victim-org/private-repo"`, looks up `victim-org`'s stacks, and enqueues `GithubSyncJob` / triggers status updates for the victim's repository — actions the attacker's authenticated org was never entitled to perform. module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
