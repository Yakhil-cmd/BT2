## Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login`, but event processing acts on `repository.full_name` — cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (the documented "Using Multiple GitHub Applications" configuration), the field used to select the GitHub App/`webhook_secret` used to *authenticate* an inbound webhook is not the same field that later handlers use to decide *which repository/stack is written to*. An attacker who controls one configured organization's webhook secret can forge a payload that verifies under their own organization but performs writes against a different, victim organization's repository.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to pick the verifying GitHub App purely from attacker-suppliable JSON fields: [1](#0-0) 

That organization name is passed to `Shipit.github(organization:)`, which in a multi-org config looks up the matching app config (and its distinct `webhook_secret`) by that key: [2](#0-1) [3](#0-2) 

The HMAC signature is verified over the *entire raw request body* using that org's secret: [4](#0-3) 

Once verification passes, the same fully attacker-controlled JSON body is dispatched, unscoped, to every registered handler for the event: [5](#0-4) 

Handlers, however, identify the target repository/stack using a *different* field — `repository.full_name` — not `repository.owner.login`/`organization.login`: [6](#0-5) [7](#0-6) 

Because the entire JSON body is attacker-crafted (not independently re-fetched from GitHub), these two fields (`repository.owner.login` and `repository.full_name`) can be set independently within a single payload. Multi-org configuration is a first-class, documented deployment mode: [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `repository/stack actually written to by the handler (repository.full_name)`

Before the attack: for legitimate GitHub-originated payloads these two fields always describe the same repository, so the equality holds incidentally.
After the attack: an attacker who knows OrgA's `webhook_secret` submits a payload where `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) to pass signature verification, while `repository.full_name = "OrgB/victim-repo"` drives the handler's write. The equality is broken; verification and effect are decoupled.

### Impact Explanation
This allows cross-repository/cross-tenant writes without any credential for the victim organization: an attacker with only OrgA's webhook secret can forge:
- `push` events causing `PushHandler#process` to call `stack.sync_github` on OrgB's stacks, driving unauthorized deploy pipeline actions.
- `pull_request` `opened` events causing `ReviewStackAdapter#create!` to create/provision Stacks for OrgB's repositories.
This matches the "cross-repository writes" / "unauthorized deploy" impact bucket, since the write is bound to a repository the attacker never authenticated for.

### Likelihood Explanation
Requires only knowledge of one configured organization's `webhook_secret` — plausible for any tenant admin in a shared multi-org Shipit instance — and the ability to POST directly to the public, unauthenticated `/webhooks` endpoint (`config/routes.rb` mounts `resources :webhooks, only: :create` with no session/token requirement). No GitHub App private key, `ApiClient` token, or Shipit session is needed, satisfying the "unprivileged attacker" constraint relative to the victim organization.

### Recommendation
After verifying the signature, re-derive and pin the acted-upon repository/organization strictly to the same field/organization key used for verification (`repository_owner`), and reject the request if the handler-resolved repository's owner does not match the verified organization.

### Proof of Concept
1. Deploy Shipit with the multi-org config (`OrgA`, `OrgB` both configured, per `docs/setup.md`).
2. Attacker, who administers `OrgA`'s installed GitHub App, knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` JSON body: `{"ref": "refs/heads/main", "after": "<attacker sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
4. Attacker computes `sha1=` HMAC over this exact raw body using `OrgA`'s `webhook_secret` and sends it as `X-Hub-Signature`.
5. `verify_signature` looks up `Shipit.github(organization: "OrgA")`, verifies successfully.
6. `PushHandler#process` resolves stacks via `repository.full_name = "OrgB/victim-repo"` and calls `sync_github`, acting on OrgB's stack despite the attacker never possessing OrgB's credentials.

    # Backward compatibility

    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)

  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
