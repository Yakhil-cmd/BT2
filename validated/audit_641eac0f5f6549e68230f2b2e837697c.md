### Title
Stale block-scoped `index-cache` primed by one user's transaction is consumed by a later transaction in the same block, causing incorrect health/liquidation math for a different position - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
The external report's root cause is generic: a piece of "current state" is cached/retrieved once and then reused for a decision that must be consistent with a *different* context (a specific height) than the one that produced the cache. In `v0-4-market.clar`, the analogous shared, cross-caller state is `index-cache`, a **persistent contract-level map** keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . It is intentionally shared across every transaction in the same block for gas savings, and the docs explicitly describe it as invalidating only when the timestamp changes [2](#0-1) .

### Finding Description
`accrue-and-cache` is a cache-or-compute helper: on a cache miss it calls `vault-accrue` (which reflects the vault's *live* `total-borrowed`/`total-assets` at call time) and stores the result under the block-timestamp key; on a hit it simply returns whatever a prior, unrelated caller wrote [1](#0-0) . Every downstream computation that needs an index/lindex for that asset in that block — `borrow`, `liquidate` (`scale-debt-for-liquidation`, `remaining-debt-to-repay`), collateral accrual, and health checks — reads via `get-cached-indexes`, which is nothing more than `map-get? index-cache { timestamp: stacks-block-time, aid }` [3](#0-2) [4](#0-3) .

The one place the protocol clearly anticipated a divergence between the cached value and the vault's true post-mutation state is `socialize-debt-asset`, which explicitly re-primes the cache after `vault-socialize-debt` writes down `lindex` [5](#0-4) . This shows the team is aware the cache can go stale relative to on-chain vault mutations within a block, but the refresh is only applied to the specific liquidation path that triggers socialization — not universally enforced for every mutating vault call (deposit/redeem/borrow/repay) that happens between two transactions sharing the same `stacks-block-time`.

Because the cache is a *global* map (not scoped to `tx-sender` or per-call), any user, including an attacker, who is first to trigger `accrue-and-cache` for an asset in a given block determines the `{ index, lindex }` that every subsequent transaction for *any other user* touching that same asset in the same block will read — without re-deriving it from the vault's state at the time of the second transaction.

### Impact Explanation
If an attacker can front-run a victim's transaction in the same block (ordering is influenced by the miner/relayer/attacker's own priority) with an operation that mutates a vault's borrowed principal or asset totals in a way `vault-accrue` would otherwise reprice (e.g., a large `deposit`/`redeem` or a `borrow`/`repay` sized to shift `total-assets`/`total-borrowed` before the cache is set), and the cache read by the victim's later same-block transaction (e.g., `liquidate`, `borrow`, `collateral-add` capacity checks) does not reflect that mutation, the victim's collateral valuation (via `lindex` for ztokens) or debt valuation (via the borrow `index`) can be computed against stale numbers. This falls under the "shared index or cache primed by one caller and consumed by another" pattern explicitly called out as in-scope, and if exploitable it would manifest as either under-collateralization allowed to pass a health check (theft of protocol/lender funds), or a liquidator improperly capped/seizing an incorrect amount of collateral — both **Critical** impacts (fund theft / insolvency) or **High** (temporary freezing) depending on direction.

### Likelihood Explanation
Low-to-Medium confidence overall: I could not fully verify `vault-accrue`'s exact dependency on `total-borrowed`/`total-assets` (i.e., whether the interest `index`/`lindex` it returns depends only on elapsed time since last accrual, or also on the instantaneous principal/asset totals) because I ran out of tool budget before reading `v0-vault-stx.clar`'s `accrue` implementation. If `vault-accrue`'s index math is a pure function of elapsed time (standard interest-index design, unaffected by principal size), then same-block calls are supposed to be idempotent regardless of ordering, and this is intended, safe behavior with no victim impact — matching the protocol's own "Cache Invalidation... Eliminates stale data risks" claim [2](#0-1) . The exploitability of this analog therefore hinges entirely on whether any vault operation can alter the cached `index`/`lindex` outside of the deliberate liquidation-socialization refresh path, which I was not able to confirm from the available context.

### Recommendation
Verify whether any vault-mutating public function (`deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan` repayment) can change the `index`/`lindex` that `vault-accrue` would compute for the *same* `stacks-block-time`. If so, either (a) invalidate/refresh `index-cache` on every vault-state-mutating call within `market.clar` (as already done for `socialize-debt-asset`), or (b) scope the cache key to include a monotonically increasing per-block operation counter/nonce rather than only `stacks-block-time`, so a cached value can never be silently reused across two transactions where the underlying vault state diverged between them.

### Proof of Concept
Not constructed — this analog's exploitability could not be confirmed without reading `vault-accrue`'s implementation in `v0-vault-stx.clar` (or the other vault contracts), which was not completed due to tool-call exhaustion. A concrete PoC would require: (1) confirming `vault-accrue`'s index formula's dependency on `total-borrowed`/`total-assets`; (2) if dependent, crafting two same-block transactions (attacker mutates vault state, then victim's `borrow`/`liquidate`/`collateral-add` reads the stale cached index) and showing the victim's health/liquidation outcome differs from what it would be if the cache were freshly computed at the victim's transaction.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
