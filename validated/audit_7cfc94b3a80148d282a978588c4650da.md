### Title
Webhook authenticity check keyed off unverified payload field, defaulting to "verified" when an organization has no `webhook_secret` configured - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a field read directly out of the unverified, attacker-supplied JSON body. `GitHubApp#verify_webhook_signature` then trivially returns `true` whenever that selected app has no `webhook_secret` configured. This lets an attacker who knows (or guesses) the name of an organization configured without a `webhook_secret` submit a completely unsigned/forged webhook payload that Shipit will process as if it originated from GitHub.

### Finding Description
The webhook pipeline is:
```ruby
before_action :check_if_ping, :drop_unhandled_event, :verify_signature
...
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner`, which selects the App/secret used for verification, is taken straight from the request body before any signature check is done — i.e. the field that governs *which trust key is used* is itself unauthenticated attacker-controlled input.

`GitHubApp#verify_webhook_signature` is:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

If the App resolved for that organization has no `webhook_secret` set (`@webhook_secret = @config[:webhook_secret].presence`, so blank/nil is normalized to `nil`), verification unconditionally succeeds regardless of the actual `X-Hub-Signature` header or body content. The documentation and sample secrets file explicitly mark `webhook_secret` as optional and show it left `nil`: [3](#0-2) [4](#0-3) 

This breaks the trust binding: the organization used to authorize/verify the payload (`repository_owner`, chosen from unverified data) is not equal to the organization/repository the engine subsequently writes state for (creating commits, syncing branches, updating statuses, or creating `Team`/`User` records via the `membership` event handler, per `Webhooks.default_handlers`) — because the verification step itself can be neutralized by controlling which (secret-less) organization is targeted. [5](#0-4) 

### Impact Explanation
Once `verify_signature` passes, `create` dispatches the JSON body, unchanged, to every registered handler for the event type (`push`, `status`, `check_suite`, `membership`, etc.), which enqueue jobs like `GithubSyncJob`, create/modify `Commit`/`Status` records, and create/attach `Team`/`User` records: [6](#0-5) 
An attacker who can target an organization configured without a `webhook_secret` can therefore forge arbitrary webhook events (fake commit statuses, fake pushes that trigger `GithubSyncJob`, fake `membership` events) without possessing any GitHub credentials, session, or `ApiClient` token — an unauthenticated write path into Shipit's data model and job queue. Whether this reaches team-authorization escalation (`Shipit.github_teams` / `User#authorized?`) via the `membership` handler could not be fully confirmed because `Handlers::MembershipHandler`'s implementation was not retrievable within the indexed content; this should be verified directly in a full checkout.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: any organization/App entry in `secrets.yml` that omits `webhook_secret` (which the setup docs explicitly present as optional, and the sample multi-org secrets file shows as `nil`) is fully exposed. In single-organization deployments where the operator followed the "optional" guidance and skipped the secret, the exposure is unconditional — no signature at all is required, and the `repository_owner`/`organization` payload fields are freely attacker-chosen since there's nothing else to match against.

### Recommendation
- Do not allow webhook signature verification to succeed by default when no secret is configured; treat an unset `webhook_secret` as "reject all webhooks for this organization" rather than "accept all webhooks," or require operators to set a fallback/global mandatory secret.
- Resolve `repository_owner` only after the request has otherwise been confirmed to come from a known, secret-bearing organization, and refuse events for organizations with no configured secret rather than silently trusting them.
- Consider also supporting/enforcing `X-Hub-Signature-256` (sha256) as GitHub recommends, instead of relying solely on the deprecated sha1 signature.

### Proof of Concept
1. Configure Shipit (as the sample `config/secrets.development.shopify.yml` shows) with two organizations, one of which (`someothergithuborg`) has `webhook_secret: nil`. [7](#0-6) 
2. Send an unsigned `POST /webhooks` request with header `X-Github-Event: push` and a JSON body where `repository.owner.login == "someothergithuborg"` and `repository.full_name` set to any stack tracked under that org, along with a crafted `after` SHA.
3. `verify_signature` resolves `Shipit.github(organization: "someothergithuborg")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally — the request is processed and `GithubSyncJob` is enqueued from fully forged, unsigned data. [8](#0-7) [9](#0-8)
