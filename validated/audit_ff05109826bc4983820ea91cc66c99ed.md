### Title
`provision?` operator-precedence bug lets `review_stacks_enabled: false` be bypassed for `allow_with_label`/`prevent_with_label` repositories - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
The intended invariant `repository.review_stacks_enabled == true` gates all review-stack auto-provisioning behaviors, but in `OpenedHandler#provision?` Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to bind only to the `allow_all` branch. Any PR opener on a repository configured with `allow_with_label` or `prevent_with_label` can create a `Shipit::ReviewStack` purely by toggling labels on their own PR, even when review stacks are supposed to be disabled.

### Finding Description
Broken binding: intended `repository.review_stacks_enabled == true` should be a precondition for `provisioning_behavior_allow_with_label?` and `provisioning_behavior_prevent_with_label?` branches too, but the code only enforces `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?` as one AND-group; the other two disjuncts are independent of `review_stacks_enabled`: [1](#0-0) 

Due to Ruby precedence (`&&` binds tighter than `||`), this parses as:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```
instead of the evidently intended:
```
review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))
```

This is confirmed as unintended by comparing with the sibling handler `LabeledHandler#respond_to_label_change?`, which correctly ANDs `repository.review_stacks_enabled` across the whole disjunction of behaviors: [2](#0-1) 

`ReopenedHandler#unarchive?` has the identical bug pattern, but is out of scope for this question.

Attack: An attacker who owns a fork/branch opens a PR against a repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled: false` (the operator's intended "kill switch" for the whole review-stack feature). By adding (or omitting) the configured provisioning label on their own PR — an action fully within their control as PR author — they satisfy the second/third disjunct of `provision?` regardless of the disabled master switch. `OpenedHandler#process` then calls `ReviewStackAdapter#find_or_create!`, which creates a `Shipit::ReviewStack` and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) 

Existing guards do not stop this: `verify_signature`/webhook signature checks only authenticate that GitHub sent the payload for that repository — they say nothing about the intra-repository `review_stacks_enabled` flag, and the `ExplicitParameters` schema only validates payload shape, not business logic. No other check re-verifies `review_stacks_enabled` before `find_or_create!` in `OpenedHandler#process`. The existing test suite (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` lines 129-187) never exercises `allow_with_label`/`prevent_with_label` together with `review_stacks_enabled: false`, so the divergence is not caught.

### Impact Explanation
Once created, the `ReviewStack` is queued for provisioning, which downstream leads to `TaskCommands#perform` execution with `GITHUB_TOKEN`/`GIT_ASKPASS` populated in `Command#unbundled_env`, i.e., an unauthorized stack/deploy is created for a repository whose operator explicitly disabled review-stack auto-provisioning (`review_stacks_enabled: false`). This is a cross-configuration privilege escalation: a repository-level "off" switch is silently overridden whenever `allow_with_label`/`prevent_with_label` is also set, letting any PR author trigger deploy-time command execution on the host they don't otherwise control. Repeatable on every PR opened against any repository sharing that configuration.

### Likelihood Explanation
Requires a repository configured with `provisioning_behavior: allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` — a plausible transitional/misconfigured state (e.g., an operator disabling review stacks while leaving the behavior selector set). No secrets or elevated privileges are needed; the attacker only needs to open a PR and control its labels, which any GitHub user with a fork can do. Cost is trivial and fully repeatable.

### Recommendation
Add explicit parentheses/grouping in `provision?` (and the identical `unarchive?` in `ReopenedHandler`) so `review_stacks_enabled` gates the entire disjunction:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add a parameterized test using the existing `configure_provisioning_behavior` helper:
```ruby
[:allow_with_label, :prevent_with_label].each do |behavior|
  test "does not create stacks when review_stacks_enabled is false, even for #{behavior}" do
    repository = shipit_repositories(:shipit)
    configure_provisioning_behavior(
      repository:,
      provisioning_enabled: false, # master switch off
      behavior: behavior,
      label: "pull-requests-label"
    )
    payload = payload_parsed(:pull_request_opened)
    # set label state matching the "provisioning would occur" case for this behavior
    payload["pull_request"]["labels"] =
      behavior == :allow_with_label ? [{ "name" => "pull-requests-label" }] : []

    assert_no_difference -> { Shipit::Stack.count } do
      OpenedHandler.new(payload).process
    end
  end
end
```
With current code, `Shipit::Stack.count` changes (assertion fails), proving that `review_stacks_enabled: false` does not prevent stack creation for `allow_with_label`/`prevent_with_label`, contrary to the intended binding `repository.review_stacks_enabled == true` gating all provisioning behaviors.
