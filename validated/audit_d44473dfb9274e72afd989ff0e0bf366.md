## Title
`validateSignedMessage()` accepts signatures made with a **revoked/rotated address definition** in the non-network-aware (light) path - ([File: signed_message.js])

### Summary
`signed_message.js`'s `validateSignedMessage()` is used by AAs (via `is_valid_signed_package()` in `formula/evaluation.js`, which `require`s `signed_message.js`) to verify that an off-chain "signed message" (functionally analogous to a bearer credential/JWT presented to an AA) was actually authorized by the claimed address. When the message does **not** include a `last_ball_unit` (`bNetworkAware = false`), the function skips the on-chain lookup of the address's *current* definition and instead only checks that the caller-supplied definition hashes to the address: [1](#0-0) 

This mirrors the eZ Platform bug class: authentication succeeds by re-validating a *stale* credential (the original/definition-derived key) without checking whether the account's authorization state has since been revoked/disabled — here, "disabled" corresponds to an address that has executed an `address_definition_change` (key rotation, e.g. because the old key was compromised) via `validateInlinePayload`'s `address_definition_change` handling [2](#0-1) .

### Finding Description
`objectHash.getChash160(objAuthor.definition) === objAuthor.address` is true for the address's *original* (chash-defining) definition by construction — that's how ocore addresses are derived. It says nothing about whether that definition is still the *active* one. The network-aware branch correctly re-derives the state at `last_ball_mci` via `storage.readDefinitionByAddress`, which reflects the latest, stable `address_definition_change`: [3](#0-2) 

But the non-network-aware branch (no `last_ball_unit` supplied) bypasses this entirely:

An attacker who once held the private key(s) matching the address's *original* definition — even after the legitimate owner has issued an `address_definition_change` unit to rotate away from that (e.g., compromised) key — can still produce a fully valid `objSignedMessage` by supplying the old/original `definition` array and signing with the old key. Because `bNetworkAware` is false, `validateSignedMessage` never consults `storage.readDefinitionByAddress` to see that the address has since revoked that definition; it treats the "always chash-valid" original definition as sufficient proof of current authorization.

### Impact Explanation
`is_valid_signed_package` in oscript lets AAs accept externally signed messages as proof of an address's authorization (analogous to accepting a bearer token as proof of identity for a disabled/rotated account). If an AA (e.g., an escrow, oracle-relay, or exchange-style AA) uses this non-network-aware verification path to authorize a payout, order cancellation, or state change tied to "signature from address X," an attacker holding X's *revoked* key can still pass verification after the legitimate owner rotated keys specifically to lock the attacker out. This can lead to unauthorized AA actions / fund loss for the impacted address, exactly the "high-risk" scenario the advisory describes (disabled/revoked credential still authenticates).

### Likelihood Explanation
Exploitability requires: (1) an address previously defined with a definition later rotated via `address_definition_change`, and (2) an AA or application invoking `is_valid_signed_package`/`validateSignedMessage` without providing `last_ball_unit` (the documented "old" / non-network-aware calling convention retained for backward compatibility, per the "before the fix" comment in the code). Since rotating keys after suspected compromise is a realistic and commonly recommended defensive action, and the vulnerable code path is a first-class, still-supported branch of a function directly exposed to AA oscript evaluation, likelihood is non-trivial for AAs that use the simpler (non-last_ball_unit) form of `is_valid_signed_package`.

### Recommendation
- Require `last_ball_unit` (i.e., disallow/deprecate the non-network-aware branch) for any signed-message verification used to authorize state changes, so that the *current* on-chain definition (post any `address_definition_change`) is always what is checked.
- Alternatively, in the non-network-aware branch, additionally verify against the latest known/stable definition for the address (if any is retrievable) rather than only checking `chash160(definition) === address`, so a rotated-away-from definition is rejected.
- Audit/flag AA and oscript usages of `is_valid_signed_package` that omit `last_ball_unit` and require network-aware validation for anything security-sensitive.

### Proof of Concept
1. Address `A` is created with definition `D0 = ['sig', {pubkey: P0}]`; `chash160(D0) = A`.
2. Owner suspects `P0` is compromised and issues an `address_definition_change` unit changing `A`'s definition to `D1 = ['sig', {pubkey: P1}]`; this becomes stable.
3. Attacker (who has the compromised private key for `P0`) crafts `objSignedMessage = {signed_message: "...", authors: [{address: A, definition: D0, authentifiers: {r: sig_by_P0}}]}` with **no** `last_ball_unit` field.
4. `validateSignedMessage(conn, objSignedMessage, A, mci, cb)` is invoked (e.g., via `is_valid_signed_package` in an AA formula). Because `last_ball_unit` is absent, `bNetworkAware = false`, so the code only checks `chash160(D0) === A` (true) and validates the signature against `D0`/`P0` — both succeed, and `handleResult(null, ...)` reports success despite `A`'s active definition now being `D1`.
5. The AA/consumer treats this as a valid authorization from `A`, even though the owner explicitly revoked `P0`'s authority.
