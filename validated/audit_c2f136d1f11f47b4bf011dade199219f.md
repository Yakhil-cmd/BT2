## Title
AMM-style AA swap pattern in ocore computes trade output solely from live pool balances with no slippage/minimum-output check, enabling sandwich-attack value extraction - (File: `test/samples/uniswap_like_market_maker.oscript`)

## Summary
The C4 finding against `UniswapHelper.buyFlanAndBurn` describes the classic sandwich-attack pattern: a swap executes against whatever pool state exists at execution time, with no minimum-received check, so a bot that trades immediately before and after the victim's swap can extract value at the victim's expense. Ocore ships (and tests) a reference constant-product AMM autonomous-agent (AA) template, `uniswap_like_market_maker.oscript`, that implements exactly this unprotected pattern, and the Obyte trigger-processing model does not eliminate the ordering-manipulation risk that a sandwich attack relies on.

## Finding Description
The "exchange bytes to asset" and "exchange asset to bytes" cases in `test/samples/uniswap_like_market_maker.oscript` compute the amount a trader receives purely from the AA's current balances at the moment the trigger unit is executed: [1](#0-0) [2](#0-1) 

There is no user-supplied minimum-acceptable-output parameter and no oracle/TWAP-based sanity bound on the computed `$amount` — the formula is a bare constant-product calculation (`$p = $asset_balance * $bytes_balance`) evaluated against whatever `balance[$asset]`/`balance[base]` happen to be when the trigger is processed, mirroring the unguarded `getAmountsOut`-style call flagged in the original UniswapHelper report.

Crucially, unlike a naive assumption that Obyte's DAG has no attacker-controllable "block", trigger execution order is not something the trigger sender controls or can rely on being immune to manipulation. AA triggers are picked up and executed in a deterministic but externally-influenceable order based on stabilized MCI, unit level, and unit hash: [3](#0-2) [4](#0-3) 

Because this ordering is a function of when/how units are posted and which parents they choose (not a value the victim controls or that is hidden from other network participants before inclusion), a well-positioned actor who observes the victim's unstable swap-trigger unit can post one trigger that gets ordered immediately before it (shifting `balance[$asset]`/`balance[base]` unfavorably) and a second trigger ordered immediately after it (reversing the position and capturing the price impact) — the same "manipulate the pool, let the victim trade into it, then reverse" economics described for `buyFlanAndBurn`. Any AA author who copies this template (or a similar pool/AMM AA) inherits the same unmitigated exposure.

## Impact Explanation
A trigger sender interacting with a constant-product-style AMM AA built on this pattern can receive materially fewer output tokens/bytes than the fair market price implies, with the difference captured by the sandwiching party. This is a direct, quantifiable value-extraction loss borne by legitimate AA users on every swap where an attacker chooses to act, analogous in kind and severity to the original M-14 finding, and it recurs on every trade rather than being a one-off edge case.

## Likelihood Explanation
Likelihood is a function of pool liquidity and monitorability of pending trigger units; for any AMM AA deployed with meaningful liquidity, a bot that watches for incoming swap triggers and posts bracketing triggers has a straightforward, repeatable strategy, exactly as bots exploit AMM pools on other DAG/blockchain systems.

## Recommendation
- Extend the AMM AA template (and document the requirement for any AA implementing pooled swaps) to accept a caller-supplied minimum-acceptable-output (or maximum-acceptable-input) parameter in `trigger.data`, and `bounce()` the trigger if the computed `$amount` violates that bound.
- Optionally support a relative/percentage slippage bound benchmarked against a data-feed/oracle price (`data_feed[[...]]`) so callers can protect against cumulative price drift, following the same recommendation given in the original report.
- Update `test/samples/uniswap_like_market_maker.oscript` (and any documentation referencing it as a template) so it is not distributed as a "safe" reference pattern without slippage protection, since third-party AA authors are likely to copy it verbatim.

## Proof of Concept
1. AA author deploys an AMM AA based on `uniswap_like_market_maker.oscript`, funded with `$asset` and bytes.
2. Victim posts a trigger unit with `trigger.output[[asset=base]] > 1e5` to swap bytes for `$asset` (case at lines 102-123).
3. Before the victim's trigger unit's MCI stabilizes and is executed, an attacker posts their own trigger unit performing the same "bytes to asset" swap (or the reverse), engineered (via parent/timestamp selection) to be ordered by `level`/`unit` hash ahead of the victim's trigger, per the deterministic ordering in `aa_composer.js`/`main_chain.js` cited above — shifting `balance[$asset]` and `balance[base]` unfavorably for the victim.
4. The victim's trigger executes against this shifted balance, computing a worse `$amount` per lines 105-110/127-132 than the pre-attack market rate, since there is no minimum-output check to reject it.
5. The attacker immediately posts a reversing trigger, ordered after the victim's, capturing the price impact and profiting at the victim's expense — reproducing the sandwich economics of the original `buyFlanAndBurn` finding.
