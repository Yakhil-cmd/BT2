### Title
Stale cached `arbstore_device_address` permanently blocks appeal-verdict authorization after ArbStore migration - (File: arbiter_contract.js, wallet.js)

### Summary
The reported bug class is: an address used for an authorization check is captured once and cached, and if the real-world entity holding that role later migrates to a new address, the stale cached value causes the authorization check to reject legitimate future actions from that entity, freezing funds. The ocore arbiter-contract subsystem has the same pattern with the ArbStore's device address that gates acceptance of appeal-resolution updates.

### Finding Description
When an arbiter contract needs to talk to the arbiter's backend service ("ArbStore"), `fillArbstoreAddresses` resolves the ArbStore's on-chain address and device address once via the hub/HTTP and then permanently caches them in the local `wallet_arbiter_contracts` row: [1](#0-0) 

The guard `if (objContract.arbstore_device_address && objContract.arbstore_address) return cb();` means these values are fetched only the first time (e.g. during `openDispute`, `createSharedAddressAndPostUnit`, `appeal`, or `complete`) and are never refreshed afterward, even though `getArbstoreAddresses` performs a live hub/HTTP lookup that can return a different device address at any later call: [2](#0-1) 

This cached, potentially stale `arbstore_device_address` is later used directly as an authorization comparator in the P2P message handler for `arbiter_contract_update`, specifically the branch that authorizes the appeal verdict (`appeal_approved` / `appeal_declined`) coming from the ArbStore while the contract is `in_appeal`: [3](#0-2) 

If the arbiter re-registers or migrates their ArbStore to a new device address at the hub (an ordinary operational/maintenance event, analogous to `moveDao` updating the DAO's authoritative address), any peer or cosigner device that already cached the old `arbstore_device_address` for an existing contract will reject the incoming appeal-resolution update with `"not an owner"`, exactly like `Reserve.sol`'s `onlyGrantor()` modifier rejecting `grantFunds` after `moveDao` changed the DAO address without `Reserve.sol` being told.

### Impact Explanation
The local contract state machine gates fund settlement on this status: `complete()`, which performs the actual on-chain release of funds held in the shared (multisig) address for the contract, only proceeds when `objContract.status` is `"paid"` or `"in_dispute"`: [4](#0-3) 

Once a contract has progressed to `"dispute_resolved"` and then `"in_appeal"`, the only way to resume the workflow is through an authorized `arbiter_contract_update` (`appeal_approved`/`appeal_declined`) message from the ArbStore. Because that authorization check compares against the stale, never-refreshed `arbstore_device_address`, a legitimate appeal verdict sent from the ArbStore's new (migrated) device address is silently rejected, and the contract can never leave the `"in_appeal"` state through the normal flow. This leaves the funds locked in the shared address contract, unreachable by either counterparty through the wallet's intended completion path — an AA/contract fund-freezing condition analogous to the `grantFunds` revert in the original report.

### Likelihood Explanation
This requires the arbiter's ArbStore to change its registered device address (e.g., infrastructure migration, key rotation, provider change) while at least one contract is mid-appeal — a realistic, non-malicious operational event rather than an attack, matching the "Medium/non-critical, future-proofing" characterization of the original report. No malicious peer, node, or hub behavior is required; it is a normal state-desynchronization bug reachable purely by ordinary private-payment counterparties (contract offeror/acceptor) and the arbiter's own infrastructure change.

### Recommendation
Do not rely on the one-time cached `arbstore_device_address` value in `wallet_arbiter_contracts` for authorization once a dispute enters `in_appeal`. Instead:
- Re-resolve the ArbStore's current device address live (e.g. via `arbiters.getArbstoreInfo`/hub lookup) at the moment of validating an incoming `arbiter_contract_update` for the appeal verdict, rather than trusting the DB-cached copy; and/or
- Refresh `wallet_arbiter_contracts.arbstore_address` / `arbstore_device_address` (via `fillArbstoreAddresses`, removing the "already set" short-circuit) whenever a contract transitions into `in_dispute`/`in_appeal`, and add a TTL/expiry to the in-memory `arbStoreInfos` cache in `arbiters.js`, which currently never expires: [5](#0-4) 

### Proof of Concept
1. Party A and Party B create an arbiter contract with arbiter X and reach `paid` → dispute → `dispute_resolved` → `in_appeal`; during this flow both parties' wallets call `fillArbstoreAddresses` and persist arbiter X's current ArbStore device address `D1` in `wallet_arbiter_contracts.arbstore_device_address` (arbiter_contract.js:247-260).
2. Arbiter X's ArbStore operator migrates the ArbStore backend to a new device address `D2` (re-registers at the hub), without any of the previously-created contract records being updated.
3. The ArbStore (now speaking from `D2`) sends `arbiter_contract_update` with `field: "status", value: "appeal_approved"` for the pending contract.
4. In `wallet.js`, `from_address` (`D2`) does not equal `objContract.arbstore_device_address` (`D1`), so the check `from_address === objContract.arbstore_device_address && objContract.status === 'in_appeal'` fails and the handler returns `callbacks.ifError("not an owner")` (wallet.js:684-712).
5. The contract's local status never advances out of `in_appeal`, so `complete()`'s guard (`status !== "paid" && status !== "in_dispute"`) permanently blocks the on-chain release of the funds held in the shared address (arbiter_contract.js:719-722). [1](#0-0) [3](#0-2) [4](#0-3)

function fillArbstoreAddresses(objContract, cb) {
	if (!cb)
		return new Promise(resolve => fillArbstoreAddresses(objContract, resolve));
	if (objContract.arbstore_device_address && objContract.arbstore_address)
		return cb();
	getArbstoreAddresses(objContract.arbiter_address, function(err, result) {
		if (err)
			return cb(err);
		var { arbstore_address, arbstore_device_address } = result;
		objContract.arbstore_address = arbstore_address;
		objContract.arbstore_device_address = arbstore_device_address;
		db.query("UPDATE wallet_arbiter_contracts SET arbstore_address=?, arbstore_device_address=? WHERE hash=?", [arbstore_address, arbstore_device_address, objContract.hash], function () { cb(); });
	});
}
