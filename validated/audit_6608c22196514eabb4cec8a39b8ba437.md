### Title
Unbounded backdating of unit timestamps defeats the emergency OP-list vote-age safeguard - ([File: main_chain.js])

### Summary
The Verge incident exploited a flawed timestamp check that let an attacker present false block timestamps to the difficulty-retarget logic, letting them mine disproportionately fast. In `ocore`, unit timestamps are validated only for an *upper* bound (not too far in the future) and for non-decrease from parent units — there is no lower-bound / staleness check. This same class of bug lets a unit author backdate the `timestamp` of a `system_vote` unit almost arbitrarily, defeating the `EMERGENCY_COUNT_MIN_VOTE_AGE` safeguard that is meant to require votes to have genuinely aged before being counted in an emergency Order-Provider (OP) list change.

### Finding Description
Unit timestamp validation in `validation.js` only enforces:
- The timestamp must be a positive integer and not more than `conf.max_seconds_into_the_future_to_accept` (default 5s) ahead of the *validating node's own clock*. [1](#0-0) 
- The timestamp must not decrease relative to any parent unit. [2](#0-1) 

There is no check that the timestamp is not implausibly old relative to real elapsed time (no "median-time-past"-like rule as used to prevent this exact bug class elsewhere). Because an author fully controls which (their own) free/unstable parent units they reference, they can chain their own units with old, self-chosen timestamps and thereby set the timestamp field of a new unit to an old value while still satisfying "non-decreasing from parents".

This self-declared, mostly unconstrained `timestamp` field is trusted as a proxy for real elapsed time in the emergency OP-list governance mechanism:
- `getUnstableVotes(emergency_count_command_timestamp)` filters in only those unstable `system_vote` units whose age (`emergency_count_command_timestamp - timestamp`) is at least `constants.EMERGENCY_COUNT_MIN_VOTE_AGE`, where `timestamp` is each voting unit's own self-reported `timestamp`. [3](#0-2) 
- These unstable votes are merged into the OP-list vote tally that decides the new witness/order-provider set during an emergency change. [4](#0-3) 
- The emergency change itself is triggered from a `system_vote_count` message, passing the triggering unit's own `objUnit.timestamp` as `emergency_count_command_timestamp`. [5](#0-4) [6](#0-5) 

Because the vote-age check compares two attacker-influenceable fields (the vote unit's own `timestamp` and the trigger unit's own `timestamp`), and because unit timestamps have no lower/staleness bound, an attacker can craft `system_vote` units that appear to satisfy `EMERGENCY_COUNT_MIN_VOTE_AGE` instantly, even though they were authored moments before the emergency vote count executes — defeating the intended purpose of this age requirement (to prevent last-minute vote-stuffing when the emergency mechanism activates).

### Impact Explanation
The OP (Order Provider/witness) list determines which addresses anchor DAG stability/finality across the whole network. Bypassing the minimum-vote-age anti-rush safeguard for emergency OP-list changes allows an attacker (or a colluding set of voters with sufficient token balance behind the vote, per the existing `SYSTEM_VOTE_MIN_SHARE` design) to inject freshly minted, backdated votes at the moment the emergency mechanism activates rather than waiting for votes to genuinely age. This can accelerate/rig control over the OP list, directly implicating consensus safety (node disagreement on validity/stability of the DAG), which is one of the accepted Critical-class impacts.

### Likelihood Explanation
Reachable by any unpriviledged unit poster who is willing to author a `system_vote` (and, when the emergency window opens, a `system_vote_count`) message — no special privilege is required beyond holding/controlling voting balance for the OP subject, which is inherent to the governance design itself. The timestamp-backdating trick requires no cooperation from other nodes; it only depends on the attacker choosing old, self-authored parent units, which is fully under the attacker's control at unit-composition time. The primary constraining factor is the separate condition that gates *when* the emergency mechanism activates at all (main_chain.js's "too early to apply emergency OP list change yet" check based on the genuinely-stable MC timestamp), but once that activates, the vote-age filter itself is bypassable as described.

### Recommendation
Tie the vote "age" check to objective, network-agreed time rather than to attacker-controlled unit timestamps — e.g., use the unit's stabilization time / main_chain_index-derived timestamp of an already-stable ancestor, or otherwise bound how far in the past a unit's self-declared timestamp may be relative to its parents' real progression (a lower-bound "not too far in the past" check mirroring the existing "not too far in the future" check in `validation.js`). At minimum, `getUnstableVotes` and `applyEmergencyOpListChange` should not treat an unstable unit's self-reported `timestamp` as trustworthy proof of vote age for a security-critical governance gate.

### Proof of Concept
1. Attacker (with sufficient balance for `system_vote` weighting on `op_list`) creates a chain of self-authored free units, each referencing only their own previous unit as parent, deliberately keeping the `timestamp` field far in the past (this passes validation because the only checks are "not too far in future" and "not less than parent's timestamp" — both satisfiable within a self-controlled, artificially old chain).
2. Attacker posts a `system_vote` (`subject: "op_list"`) message in one of these units with the backdated `timestamp`.
3. When the emergency OP-list change window opens (network genuinely stuck per `applyEmergencyOpListChange`'s real-time-based gate), `countVotes` invokes `getUnstableVotes(emergency_count_command_timestamp)`, which computes `emergency_count_command_timestamp - timestamp >= EMERGENCY_COUNT_MIN_VOTE_AGE` using the attacker's backdated `timestamp`, and the vote is included in the tally as if it had aged normally — even though it was authored moments earlier in real wall-clock time.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}
