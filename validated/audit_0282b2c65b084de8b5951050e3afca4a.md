### Title
Any secondary AA bounce reverts and un-does responses of *all* independent AAs triggered by the same unit - (File: `aa_composer.js`)

### Summary
When a single unit sends outputs to multiple AA addresses, each recipient AA is handled as a "secondary trigger" of the same primary trigger chain [1](#0-0) . These secondary AAs are semantically independent contracts (e.g. unrelated pools/agents that simply happen to be paid by the same triggering unit), yet `handleSecondaryTriggers` processes them with `async.eachSeries` and, if **any single one** of them bounces, calls `revert()` for the *entire* trigger cascade instead of just isolating the one that failed [2](#0-1) . `revert()` rolls back the DB transaction to the initial savepoint and clears the whole KV batch, undoing the state changes and balance updates of every AA that had already succeeded in the same cascade, then bounces the primary trigger [3](#0-2) .

This mirrors the referenced Hubble finding: a loop over multiple, logically independent entities where one entity not being "ready" (here: bouncing) forces the whole batch to fail/revert instead of just excluding that one entity and letting the rest proceed.

### Finding Description
`handleTrigger()` computes `arrOutputAddresses` from the outputs of the response unit and, if any of them are AA addresses, calls `handleSecondaryTriggers(objUnit, arrOutputAddresses)` [4](#0-3) . For each such address a fresh, independent `handleTrigger` call is issued as a secondary trigger via `async.eachSeries`:

```js
async.eachSeries(
    rows,
    function (row, cb) {
        ...
        child_trigger_opts.onDone = function (objSecondaryUnit, bounce_message) {
            if (bounce_message)
                return cb(bounce_message);
            cb();
        };
        handleTrigger(child_trigger_opts);
    },
    function (err) {
        if (err) {
            if (bSecondary)
                return bounce(err);
            return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
        }
        ...
    }
);
``` [5](#0-4) 

`async.eachSeries` stops at the first error and passes it to the final callback, and that callback treats a bounce of *any single* secondary AA as fatal for the entire cascade: it calls `revert(err)`, which rolls back to `SAVEPOINT initial_balances`, clears the whole KV batch, and discards all `arrResponses` accumulated so far (including the ones from AAs that succeeded) [3](#0-2) . This means that if a trigger unit sends outputs to AA `X` (succeeds) and AA `Y` (bounces, e.g. because of a time/condition gate coded into `Y`), `X`'s successful execution and any funds/state it produced are also erased, purely because an unrelated AA `Y` was not ready.

### Impact Explanation
Since "a single unit can send to several AA addresses" is an explicitly supported, common pattern (see comment in `main_chain.js`) [6](#0-5) , any AA logic (or attacker-supplied trigger data forwarded by a router/composer AA) that fans out payments to multiple independent AAs is exposed to this coupling. A single AA among the targets that legitimately bounces under some internal condition (time gate, balance check, cap, etc.) forces the reversal of otherwise successful, unrelated AA state changes and fund movements in the same cascade. This can be used to:
- Grief/DoS legitimate multi-AA compositions (fund freezing/loss of intended state changes for unrelated AAs), and
- Force retriggering loops where the same primary trigger keeps bouncing entirely because one downstream AA never becomes "ready", even though the others would have succeeded — analogous to the referenced report's "AMM 1 won't be able to be updated until AMM 2 is ready".

### Likelihood Explanation
Reachable by any ordinary AA trigger sender or by AA authors who compose calls to several independent sibling AAs in the same response unit; no privileged access is required. The only precondition is that a unit ends up sending outputs to more than one AA address (a routine, documented pattern), and that at least one of the target AAs can bounce under conditions controllable or predictable by the trigger sender (e.g., a time-gated AA, a capped pool, or an intentionally crafted target AA).

### Recommendation
Do not treat a bounce of one secondary AA as fatal for sibling secondary AAs that are logically independent. Options:
- Track failures of individual secondary triggers and only bounce/roll back the branch that actually failed (per-AA savepoints), letting sibling AA responses commit independently, or
- Explicitly document/require that composed multi-AA sends are intentionally atomic, and provide AA authors a way to opt out (e.g., fire-and-forget outputs) so independent targets are not coupled by default.

### Proof of Concept
1. Deploy AA `A` (primary) whose response sends outputs both to AA `B` (which unconditionally succeeds) and to AA `C` (which bounces under some condition, e.g. `bounce('not ready yet')`).
2. Post a trigger unit to `A` with the condition met for `C` to bounce.
3. Observe that `handleSecondaryTriggers` runs `B`'s and `C`'s secondary triggers via `async.eachSeries`; `C` bounces, `async.eachSeries` short-circuits with that error, and `revert()` is invoked for the whole cascade [7](#0-6) .
4. Confirm that `B`'s state/balance changes (which would have succeeded) are rolled back (`ROLLBACK TO SAVEPOINT initial_balances`, `batch.clear()`) purely because `C` bounced, even though `B` and `C` are independent.
