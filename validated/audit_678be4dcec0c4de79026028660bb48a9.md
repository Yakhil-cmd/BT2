### Title
Emergency OP-list vote count derives the new witness list from node-local unstable-message state, causing nodes to disagree on the resulting OP list - (File: main_chain.js)

### Summary
The Perennial bug lets `Oracle.latest()`/`status()` compute a version from data that depends on the exact timing/order of provider-switch commits vs. requests, so different observers can end up with different (and invalid) "current" state. `ocore`'s emergency order-provider (OP) list re-election, `applyEmergencyOpListChange` → `countVotes(..., is_emergency=1, ...)` in `main_chain.js`, has an analogous root cause: the "current" authoritative value (`storage.systemVars.op_list`) is computed by mixing deterministic, DAG-committed data (stable `system_votes`) with node-local, non-committed, transient data (`storage.assocUnstableMessages`), gated only by a wall-clock-style age check rather than DAG stability. Because different honest full nodes can have different unstable messages in their local mempool/cache at the moment they process the same triggering unit, they can each independently compute a different OP list and write it into `system_vars`, from which `storage.getOpList(mci)` is read by consensus-critical code (witness/best-parent selection, stability determination, unit validation).

### Finding Description
`getOpList(mci)` reads `storage.systemVars.op_list`, an in-memory table of `{vote_count_mci, value}` entries maintained by `getSystemVar`: [1](#0-0) 

This table is consensus-critical: it feeds `validateWitnesses` for units at/after `v4UpgradeMci` (used to determine the OP set that must witness the unit and to check the witnessed level did not retreat), best-parent/parent selection in `parent_composer.js`, and MC stability determination via `readMcUnitWitnesses` in `paid_witnessing.js`: [2](#0-1) [3](#0-2) 

Normal (non-emergency) OP-list vote counting is triggered only once per MCI, after that MCI is fully stabilized, and only counts votes cast in already-stable units (`system_votes` table), which is deterministic and identical for every honest node that has stabilized the same MCI: [4](#0-3) 

However, the "emergency" path (used when the network appears to be stuck electing a new OP list) is triggered synchronously while a brand-new, still-unstable unit carrying a `system_vote_count` message is being written locally, *before* main-chain update/stabilization even runs: [5](#0-4) [6](#0-5) 

`countVotes` with `is_emergency=1` additionally pulls in votes from **unstable** units via `getUnstableVotes`, which iterates `storage.assocUnstableMessages` — a purely local, per-node cache of currently-known-but-not-yet-stable units — and includes any `system_vote` message whose containing unit is `sequence==='good'` and whose age (relative to the *local* `emergency_count_command_timestamp`) exceeds `constants.EMERGENCY_COUNT_MIN_VOTE_AGE`: [7](#0-6) 

These unstable votes are merged into a temporary `op_votes_tmp` table and the OP list is computed by summing voter balances and taking the top `COUNT_WITNESSES` addresses, which is then written into the canonical `storage.systemVars.op_list` used everywhere as "the" current OP list: [8](#0-7) 

The set of "unstable but good" units known to a node is not a DAG-committed, network-agreed quantity — it depends on propagation timing, connectivity, and each node's own view of the DAG at the instant it processes the triggering unit. Two honest, fully-synced nodes can legitimately have different `assocUnstableMessages` contents (e.g., one has already received/validated a fresh `system_vote` unit that hasn't yet reached the other, or has classified sequence differently pending further units), especially right at the edge of the `EMERGENCY_COUNT_MIN_VOTE_AGE` cutoff. Because the computation is age-based (using local receipt/processing time via `emergency_count_command_timestamp` compared against unit timestamps) rather than stability-based, it does not guarantee convergence the way normal vote counting (restricted to *stable* votes) does. This mirrors the Perennial bug's structural flaw: mixing "definitely-final" state with "not-yet-final, timing-dependent" state to compute the single canonical "current" value, without a check that guarantees the result is unambiguous/consistent for all observers.

### Impact Explanation
If two nodes compute different `ops` lists for the same `vote_count_mci` (`main_chain_index - 1` of the stuck point), each `REPLACE`s a divergent value into its local `system_vars`/`storage.systemVars.op_list`: [9](#0-8) [10](#0-9) 

From that point on, `storage.getOpList(mci)` returns different witness sets on different nodes for the same MCI range. Since this list directly gates unit validation (`validateWitnesses`/`checkWitnessedLevelDidNotRetreat`), best-parent selection, and MC-stability calculations, the nodes can disagree about which units are valid/serial and which MC units are stable — a consensus split (nodes disagreeing on validity/stability of the same units), which is one of the accepted high-impact outcomes for this class of bug (network unable to agree on/confirm new units consistently).

### Likelihood Explanation
This path only activates in the rare "stuck OP list election" emergency scenario (`EMERGENCY_OP_LIST_CHANGE_TIMEOUT` must have elapsed), so it is not attacker-triggerable on demand, and I could not fully verify the exact timing tolerances of `EMERGENCY_COUNT_MIN_VOTE_AGE`/`EMERGENCY_OP_LIST_CHANGE_TIMEOUT` from `constants.js` (grep confirmed their existence but I did not retrieve their numeric values within the remaining iterations, so I cannot state precisely how wide the race window is). Likelihood should be treated as low-to-medium: it requires the network to actually be stuck, but once triggered, ordinary propagation-timing differences between honest full nodes are sufficient to produce divergent unstable-vote sets — no malicious actor is strictly required, though a borderline-timed vote submission could reliably provoke the disagreement.

### Recommendation
Do not include unstable/unconfirmed votes in a computation whose result is asserted as globally canonical consensus state. Either:
1. Require the emergency vote count to only use votes from units that meet a DAG-stability-equivalent criterion at the time of computation across all nodes (e.g., require the vote-carrying unit's `latest_included_mc_index`/witnessed-level to already be included by the triggering unit, so all nodes that accept the same triggering unit are guaranteed to see the same set of prior votes), rather than an age-based wall-clock heuristic on locally-cached unstable messages; or
2. Snapshot/commit the exact set of counted vote units (e.g., as hashes or references) inside the `system_vote_count` unit itself, so all nodes replaying stabilization use the identical input set instead of each computing it from local mempool state.

### Proof of Concept
Not independently reproduced (no test harness run); the analysis is based on static code tracing of `main_chain.js` (`countVotes`, `getUnstableVotes`, `applyEmergencyOpListChange`), `writer.js` (call site before `updateMainChain`), `storage.js` (`getSystemVar`/`getOpList`), and `validation.js`/`paid_witnessing.js` (consumers of `getOpList`). Conceptually:
1. Network gets stuck electing a new OP list; `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` elapses.
2. Node A receives unit U1 (a fresh `system_vote` for `op_list`) and unit U2 (carrying `system_vote_count`) in that order, with U1 old enough by A's clock to pass `EMERGENCY_COUNT_MIN_VOTE_AGE` when A processes U2.
3. Node B receives U2 slightly before U1 propagates to it, or classifies U1's `sequence` differently pending more units; when B processes U2, U1 is either absent from `assocUnstableMessages` or fails the age/sequence check.
4. `countVotes(conn, mci, 'op_list', 1, ts)` on A includes U1's vote; on B it does not — the resulting `ops` (top `COUNT_WITNESSES` by voter balance) can differ between A and B whenever U1's vote changes the balance ranking near the cutoff.
5. Both nodes `REPLACE` this into `system_vars` at the same `vote_count_mci`, causing `storage.getOpList(mci)` to diverge across the network from that point forward.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");

		console.log(`too early to apply emergency OP list change yet`);

	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
