### Title
Cross-repository commit-status forgery via unscoped `StatusHandler` in webhook signature verification - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The report describes a gap between the value used to *select* an enforcement bound (`MAXIMUM_GAS_LIMIT`) and the value actually *applied* at execution time (`u64::MAX`), letting an unbounded value slip past the intended limit. The equivalent pattern exists in Shipit's webhook pipeline: the signature check binds trust to an **organization** derived from the payload, but the `status` event handler applies its effect to **any commit across any repository/stack**, without re-checking that the commit belongs to the organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the signature against using an attacker-influenced field from the payload: [1](#0-0) [2](#0-1) 

This only proves the request was legitimately signed *for that one organization's GitHub App*. Handlers are then expected to scope any effect to that same organization's repositories. Most handlers do this correctly through `Handler#stacks`, which resolves the affected stacks from `repository.full_name` in the payload: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` both use this repository-scoped `stacks` relation before acting: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does not use `stacks` at all — it queries `Commit` globally by SHA, with no repository/organization scoping whatsoever: [6](#0-5) 

The equality that should hold is:
`organization that signed the webhook == organization owning the Commit/Stack that gets its status updated`

For `push` and `check_suite` this equality is enforced via `stacks` (scoped by `Repository.from_github_repo_name`). For `status`, it is not — `Commit.where(sha: params.sha)` matches across **every stack Shipit tracks, regardless of which GitHub App/organization signed the request**. Any Shipit deployment that manages more than one GitHub organization/repository (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github_app_config`) is affected: a validly-signed `status` webhook from Organization A's GitHub App can create/update `CommitStatus` rows for commits belonging to Organization B's stacks, as long as the attacker knows (or can predict/collide) the target SHA.

### Impact Explanation
Commit statuses gate deployability in Shipit (blocking statuses / CI status checks). An attacker who can trigger a legitimately-signed `status` webhook for one onboarded organization (e.g., because they control CI integration or repo settings that emit commit statuses for a repo the operator has legitimately connected) can forge a passing/blocking status for a commit belonging to a **different** stack/organization, without ever needing that other organization's `webhook_secret`. This can be used to mark a commit as CI-green to unlock/allow a deploy that should have been blocked, i.e., an unauthorized deploy path — matching the report's "Critical" bar for authorization bypasses of the deploy pipeline.

### Likelihood Explanation
Likelihood is moderate: exploitation requires (a) the Shipit instance to track more than one GitHub organization/repository (an explicitly supported and documented setup) and (b) the attacker to know or guess the exact SHA of a commit tracked under a different organization's stack (SHAs of tracked commits are frequently visible via the Shipit UI itself, or via the target repository if it is public). No secret, session, or API token is required — only the ability to cause GitHub to send a validly-signed `status` event from an org already connected to the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the `Commit` lookup to `stacks.joins(:...)`/`Commit.where(sha: params.sha, stack: stacks)` (or equivalent), where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` as in `Handler#stacks`, so that a status update can only affect commits belonging to the repository named in the same signed payload/organization.

### Proof of Concept
1. Operator configures Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`, `lib/shipit.rb#github_app_config`), each tracking its own `Stack`/`Repository`.
2. `OrgB` has a `Commit` with `sha = X` belonging to a stack the attacker does not control.
3. Attacker, who only has legitimate access to trigger status events in `OrgA` (e.g., via a CI integration configured on an `OrgA` repository), causes GitHub to send a `status` webhook signed with `OrgA`'s `webhook_secret`, with `sha: X` and `state: "success"`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `OrgA`, validates the signature against `OrgA`'s secret — succeeds, because the payload genuinely came from `OrgA`'s GitHub App.
5. `StatusHandler#process` runs `Commit.where(sha: X)` with no organization/repository filter, finds `OrgB`'s commit, and calls `commit.create_status_from_github!(params)`, writing a forged status onto `OrgB`'s commit — even though the request was never signed by `OrgB`'s GitHub App/secret.

Note: I was not able to fully trace `Commit#create_status_from_github!` and the exact deploy-blocking logic (`Status`/`Status::Group`) in this session to confirm the precise mechanics by which a forged status unlocks a deploy; this should be verified directly in `app/models/shipit/commit.rb` and `app/models/shipit/status/group.rb` before remediation, but the missing repository-scoping in `StatusHandler` itself is confirmed against the sibling handlers' code shown above.
