### Title
Cross-repository forged CI status injection via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target `Commit` rows purely by matching the raw `sha` field of the incoming GitHub `status` payload against the entire `commits` table, without ever loading a `Shipit::Repository` or otherwise checking that `payload['repository']['full_name']` corresponds to the `Stack`/repository that actually owns the matched commit. Every other GitHub-repo-scoped handler (`PushHandler`, the `PullRequest::*` handlers) resolves `Shipit::Repository.from_github_repo_name` first and restricts mutation to that repository's stacks, but `StatusHandler` skips this entirely, letting a validly-signed `status` webhook from *any* repository mutate commit/status state belonging to a completely different, unrelated repository/stack.

### Finding Description
The claimed binding — `Repository.from_github_repo_name(payload.repository.full_name)` (authorization scope) `== Repository` that owns the `Commit` rows being mutated — is never established for the `status` event.

- `Shipit::Webhooks::Handlers::Handler#stacks` is the only place `Repository.from_github_repo_name` is invoked, and it is a private helper used by `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:13`) and all `PullRequest::*` handlers (e.g. `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`). [1](#0-0) 
- `StatusHandler#process` never calls `stacks` or `Repository.from_github_repo_name` at all; it looks up commits globally: [2](#0-1) 
- `WebhooksController#create` dispatches straight into `Handler.call -> new -> process` with no repository-ownership check of its own: [3](#0-2) 
- `verify_signature` only binds the HMAC check to the **organization** derived from `repository_owner` (`params.dig('repository','owner','login')`), never to the specific repository named in the payload: [4](#0-3) 

Because signature verification is organization-scoped (not repository-scoped) and `StatusHandler` performs a plain `Commit.where(sha: params.sha)` with no repository/stack filter, any repository that shares the same webhook-signing secret (i.e., any repository under a GitHub organization/App installation that Shipit tracks) can emit a `status` event whose `sha` value matches a commit that actually belongs to a *different* tracked stack/repository. Git commit SHAs are content-addressed and are preserved verbatim across forks/mirrors that share history, so an attacker who merely has push/admin rights on any repository within the same tracked organization (e.g. a personal scratch repo or a fork that shares ancestor commits with the real tracked repository) can call GitHub's "Create a commit status" API on a SHA that also exists as a `Shipit::Commit` row for an unrelated stack. GitHub signs and delivers that `status` webhook using the same organization-level secret, `verify_signature` accepts it, and `StatusHandler#process` attaches the forged status to the real commit row via `Commit#create_status_from_github!`.

`Status#after_create :enable_ci_on_stack` and `Commit#add_status` react to the newly created status by calling `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)`/`commit.schedule_continuous_delivery` for a `success`/`pending` state: [5](#0-4) [6](#0-5) 

None of the existing guards prevent this: `verify_signature` checks only the organization-level HMAC, `drop_unhandled_event`/`check_if_ping` are irrelevant, the `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`/etc. and never validates that the payload's repository owns that sha, and there is no model validation tying a `Status`/`Commit` to the webhook's originating repository.

### Impact Explanation
An attacker with push/admin access to any single repository within a GitHub organization tracked by Shipit (not necessarily the target stack's repository) can inject a forged `success`/`pending`/`failure` CI status onto a commit belonging to an entirely different stack they do not control. A forged `success` status can trigger `stack.schedule_merges` and continuous-delivery scheduling hooks on that unrelated stack/commit, potentially causing an unauthorized merge or deploy to proceed based on a status that never occurred for that repository. This is a cross-tenant integrity break where a payload nominally from repository A mutates state (`Status`, deploy scheduling) owned by repository/stack B, matching the "Critical" category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any commit SHA the attacker can reproduce/share and any organization Shipit tracks.

### Likelihood Explanation
Exploitation requires the attacker to be able to get a `status` webhook validly signed for a GitHub organization that Shipit tracks — i.e., have push/admin rights on some repository under that organization (their own repo, a fork with shared history, or a scratch repo they create), and know/produce a commit SHA that is shared with a commit already tracked in a different stack (trivial via `git push` of the same commit objects, since SHA1 is content-addressed and independent of the hosting repository). No Shipit secrets, sessions, or API tokens are required. The main precondition is having any foothold (even minimal, unprivileged, self-owned) inside an organization Shipit already tracks; this is consistent with the stated attacker model ("emit webhooks from a repository they own").

### Recommendation
In `app/models/shipit/webhooks/handlers/status_handler.rb`, scope the commit lookup to the repository named in the payload, mirroring `PushHandler`/`Handler#stacks`:
```ruby
def process
  stacks.joins(:commits).merge(Commit.where(sha: params.sha)).each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
or equivalently restrict to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring only commits belonging to the `Repository` resolved via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` can be mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status event does not touch commits outside the payload's repository" do
          victim_commit = shipit_commits(:first)              # belongs to stack/repo "shipit"
          other_repo_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'repository' => { 'full_name' => 'attacker/unrelated-repo' }
          }

          # Binding under test: Repository resolved for the payload's repo
          # must equal the Repository owning the mutated Commit.
          resolved_repo = Shipit::Repository.from_github_repo_name('attacker/unrelated-repo')
          owning_repo   = victim_commit.stack.repository
          assert_not_equal resolved_repo, owning_repo # attacker's repo != victim's repo

          assert_no_difference -> { victim_commit.statuses.count } do
            Shipit::Webhooks::Handlers::StatusHandler.call(other_repo_payload)
          end
        end

        test "Repository.from_github_repo_name is never consulted by StatusHandler" do
          Shipit::Repository.expects(:from_github_repo_name).never
          Shipit::Webhooks::Handlers::StatusHandler.call(
            'sha' => shipit_commits(:first).sha,
            'state' => 'success',
            'repository' => { 'full_name' => 'attacker/unrelated-repo' }
          )
        end
      end
    end
  end
end
```
The second test currently passes today (proving the dead-code claim), and the first test currently **fails** on this codebase (`assert_no_difference` is violated — the forged status is created), demonstrating the cross-repository mutation.
