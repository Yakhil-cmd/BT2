### Title
Cross-organization webhook signature confusion allows forged commit statuses to trigger unauthorized merges - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and its `webhook_secret`) to validate the HMAC signature using the payload's `repository.owner.login` field, while the event handlers that act on the payload (e.g. `StatusHandler`) never re-check that the org that authenticated the signature actually owns the resource being mutated. In a multi-organization Shipit deployment, an org that legitimately owns one GitHub App/webhook secret can forge a signature that is "valid" for its own org, while injecting a payload that mutates state belonging to a completely different, unrelated repository/stack — because `StatusHandler` looks up target `Commit`s by a global `sha` with no repository scoping at all.

### Finding Description
`verify_signature` derives the signing org strictly from the request payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This binds *only* the org identity used to pick the HMAC secret. Once verified, the raw JSON is dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) , and handlers independently decide what resource to act on. Most handlers (`Handler#stacks`) re-derive the repository from `payload.dig('repository', 'full_name')` [4](#0-3) , but nothing cross-checks that `full_name`'s owner segment matches the `repository.owner.login` that was used to select the webhook secret in the controller.

Critically, `StatusHandler` doesn't even use `stacks`/repository scoping — it looks up commits globally by SHA across the entire installation: [5](#0-4) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

An attacker who controls Organization A (which is legitimately configured in this same multi-tenant Shipit instance per `docs/setup.md`'s "Using Multiple Github Applications" section, and therefore knows Organization A's `webhook_secret`) can:
1. Craft a `status` event payload where `repository.owner.login = "OrgA"` (so `verify_signature` validates against Org A's secret, which the attacker legitimately knows) but `sha` is the SHA of a commit belonging to a completely different stack/repository owned by Organization B.
2. POST this to `/webhooks` with a valid `X-Hub-Signature` computed with Org A's secret.
3. `verify_signature` passes (Org A's secret matches), and `StatusHandler` then finds and updates the status of Org B's commit, since the SHA lookup is not scoped to any repository at all.

This breaks the binding: **organization that authenticated (Org A, via HMAC) ≠ repository/commit actually written (Org B's commit)**.

### Impact Explanation
Forged commit statuses feed directly into automatic merge-queue logic. `Commit#add_status` calls `stack.schedule_merges if new_status.pending? || new_status.success?` [6](#0-5) , and `MergeRequest.schedule_merges` iterates enabled stacks to process pending merge requests, ultimately calling `MergeRequest#merge!`, which invokes `stack.github_api.merge_pull_request(...)` [7](#0-6) . By forging a "success" status for an arbitrary commit belonging to another organization's stack, an unprivileged attacker (who only controls their own, unrelated GitHub org's webhook credentials) can cause Shipit to satisfy CI-status gating for a pull request they do not own and trigger an unauthorized merge on a repository they have no legitimate access to. This is a cross-repository write / unauthorized merge, matching the Critical severity bar (unauthorized merge across repositories the attacker's credentials should not reach).

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented and supported: `docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`), where the attacker legitimately controls one onboarded organization's webhook secret. This is a realistic, supported deployment topology, not a hypothetical misconfiguration, and requires no privileged Shipit session, API token, or GitHub App private key — only knowledge of one's own org's webhook secret, which the attacker legitimately possesses.

### Recommendation
`WebhooksController#verify_signature` (and/or each `Handler`) should cross-verify that the organization used to authenticate the signature matches the organization implied by `repository.full_name` (and by extension the resolved `Stack`/`Commit`'s actual repository) before dispatching to handlers. `StatusHandler` in particular must scope its `Commit` lookup by the verified repository/stack (via `stacks`), not by a bare, installation-wide `sha` match.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `OrgA` and `OrgB` (per multi-org docs), each with its own `Stack`/commits and distinct `webhook_secret`.
2. As the operator/owner of `OrgA` (attacker), take any commit SHA belonging to `OrgB`'s stack (SHAs are often knowable/public, e.g. from `OrgB`'s public repo).
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` for body:
```json
{
  "sha": "<OrgB's commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully.
5. `StatusHandler#process` executes `Commit.where(sha: ...)`, finds `OrgB`'s commit (no ownership check), and creates a success status on it, potentially triggering `stack.schedule_merges` and an unauthorized merge on `OrgB`'s repository.
