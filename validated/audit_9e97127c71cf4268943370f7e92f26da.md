### Title
Malicious FastSync Peer Can Corrupt Staking DB for Arbitrary Epoch via Unvalidated `P2PStakingInfo.BlockNum` — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

---

### Summary

During FastSync, the `queue.DeliverStakingInfos` validate closure is a deliberate no-op. The attacker-supplied `P2PStakingInfo.BlockNum` is never cross-checked against the header number of the `fetchResult` slot it is written into. `commitFastSyncData` and `commitPivotBlock` then call `PutStakingInfoToDB(result.StakingInfo.BlockNum, …)`, using the attacker-controlled field as the database key. A malicious peer can therefore write attacker-controlled validator node IDs and reward addresses under any pre-Kaia epoch boundary key in the staking DB.

---

### Finding Description

**Step 1 — No-op validate closure.**

`queue.DeliverStakingInfos` accepts a list of `P2PStakingInfo` objects from a peer and calls the generic `deliver` helper. The `validate` callback, which is the only place where the response item could be checked against the corresponding header, unconditionally returns `nil`: [1](#0-0) 

Compare this with `DeliverBodies` and `DeliverReceipts`, which both derive a Merkle root from the response data and compare it to the header's committed hash before accepting the item: [2](#0-1) [3](#0-2) 

**Step 2 — Attacker-controlled `BlockNum` stored verbatim.**

The `reconstruct` closure stores the raw peer-supplied `P2PStakingInfo` pointer directly into `result.StakingInfo`: [4](#0-3) 

**Step 3 — DB write uses attacker-supplied key.**

Both `commitFastSyncData` and `commitPivotBlock` call `PutStakingInfoToDB` with `result.StakingInfo.BlockNum` — the field that came from the peer — rather than `result.Header.Number.Uint64()`: [5](#0-4) [6](#0-5) 

**Step 4 — DB key is the epoch lookup key.**

`PutStakingInfoToDB` delegates directly to `WriteStakingInfo`, which stores the JSON blob under `"stakingInfo" || Uint64LE(num)`: [7](#0-6) [8](#0-7) 

**Step 5 — DB is the authoritative source for pre-Kaia staking info.**

`GetStakingInfo` consults the DB before falling back to state for all pre-Kaia blocks. A corrupted DB entry is returned directly without further validation: [9](#0-8) 

**Contrast with the recovery path**, which does validate `BlockNum`: [10](#0-9) 

---

### Impact Explanation

An attacker who is a connected P2P peer during a FastSync session targeting a pre-Kaia pivot can:

1. Respond to a staking-info request for epoch boundary `E_real` with a `P2PStakingInfo` whose `BlockNum` is set to a different epoch boundary `E_target`.
2. The victim node writes attacker-controlled `CouncilNodeAddrs`, `CouncilRewardAddrs`, and `CouncilStakingAmounts` under key `E_target` in the staking DB.
3. After FastSync completes, `GetStakingInfo` for any block whose `sourceNum` resolves to `E_target` returns the corrupted entry, directing block rewards to attacker-controlled addresses and potentially substituting attacker-controlled node IDs into the weighted-random validator selection.
4. The victim node also serves the corrupted DB entry to other peers via `handleStakingInfoRequestMsg`, propagating the corruption.

This satisfies the "unauthorized reward distribution" impact criterion for pre-Kaia epochs.

---

### Likelihood Explanation

- Any permissionless P2P peer can participate in FastSync as a data provider.
- The attack requires only that the victim is syncing to a pre-Kaia pivot block (or that the victim node will later serve staking info for pre-Kaia epochs to other syncing peers).
- No cryptographic break, key compromise, or validator-majority collusion is required.
- The `TODO-Kaia-Snapsync` comment confirms the missing validation is a known gap, not an intentional design choice.

---

### Recommendation

Replace the no-op validate closure in `queue.DeliverStakingInfos` with a check that `stakingInfoList[index].BlockNum == header.Number.Uint64()`. Alternatively, in `commitFastSyncData` and `commitPivotBlock`, use `result.Header.Number.Uint64()` as the DB key instead of `result.StakingInfo.BlockNum`, mirroring the pattern already used in the `SyncStakingInfo` recovery path.

---

### Proof of Concept

1. Set up a FastSync session where the victim node requests staking info for epoch boundary block `8000`.
2. The malicious peer responds with a `P2PStakingInfo{BlockNum: 4000, CouncilRewardAddrs: [attacker_addr], …}`.
3. `queue.DeliverStakingInfos` accepts it (validate returns nil).
4. `commitFastSyncData` calls `PutStakingInfoToDB(4000, …)`.
5. Call `ReadStakingInfo(db, 4000)` — it returns the attacker's reward address.
6. Call `GetStakingInfo(num)` for any `num` whose `sourceNum` is `4000` — it returns the corrupted entry, directing rewards to `attacker_addr`.
