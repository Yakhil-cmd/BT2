### Title
Griefing DoS via pre-funded (dust-transfer) target address permanently blocks `SystemInstruction::CreateAccount` / `CreateAccountWithSeed` — analog of pair-prefunding griefing - (File: programs/system/src/system_processor.rs)

### Summary
The System Program's account-creation path rejects creation whenever the destination account already holds a nonzero lamport balance [1](#0-0) . Because destination addresses used for `CreateAccount`/`CreateAccountWithSeed` (e.g., derived stake, vote, or nonce accounts) can be computed or observed ahead of the funding transaction landing, any unprivileged user can pre-fund the target address with a dust amount of lamports to make the legitimate creation transaction permanently fail with `SystemError::AccountAlreadyInUse`. This is the direct analog of the reported Blackhole issue, where an attacker pre-funds a deterministic liquidity-pair address to break a strict-zero-balance check and permanently block legitimate pool creation.

### Finding Description
`create_account` in `system_processor.rs` enforces that the "to" account must have zero lamports before it can be initialized: [2](#0-1) 

This check is shared by both `SystemInstruction::CreateAccount` and `SystemInstruction::CreateAccountWithSeed` (both route through the same `create_account` function, using `Address::create` to optionally derive a `base + seed + owner` address) [3](#0-2) .

For `CreateAccountWithSeed`, the target address is a deterministic function of `(base pubkey, seed string, owner)` and is computable by anyone who knows those three public inputs — analogous to how the Blackhole `pairFactory.getPair(nativeToken, fundingToken, stable)` address is deterministic and derivable from public token addresses. Once an attacker transfers even 1 lamport to that address (a simple `SystemInstruction::Transfer` to a pubkey with no privileged requirement), any subsequent `CreateAccount`/`CreateAccountWithSeed` targeting that same address will unconditionally fail the `to.get_lamports() > 0` check and return `SystemError::AccountAlreadyInUse` [1](#0-0) , exactly mirroring the reported `!ZV` (balance == 0) revert pattern in `depositNativeToken`.

Because the derived address is fixed by its inputs, the victim cannot simply "retry" with a different address without changing the seed/base/owner tuple that defines their intended account (e.g., an exchange's deterministic per-user deposit/stake-account derivation scheme, or any protocol convention that fixes `base`/`seed`). This makes the DoS effectively permanent for that specific intended address, not merely a one-off failed transaction.

Notably, Agave engineers appear to have recognized this exact class of problem: a new, feature-gated `SystemInstruction::CreateAccountAllowPrefund` instruction was added specifically to "create a new account without checking for 0 lamports... intended for use where account has already had rent paid in whole or in part before creation" [4](#0-3) , gated behind `feature_set.create_account_allow_prefund` [5](#0-4) . However, this is an opt-in instruction that must be explicitly used by client/CLI/program code; the default `CreateAccount` / `CreateAccountWithSeed` paths used throughout stake, vote, and nonce account creation flows (e.g., `cli/src/stake.rs` `CreateStakeAccount`) remain vulnerable to the prefund griefing pattern [6](#0-5) .

### Impact Explanation
An unprivileged attacker can permanently deny a specific, deterministically-derived address (stake/vote/nonce accounts created via `CreateAccountWithSeed`, which rely on public `base`/`seed`/`owner` conventions) from ever being initialized as intended, by transferring a trivial dust amount of lamports to it beforehand. This constitutes a low-cost, permanent griefing/DoS against a specific account address — matching the "permanently frozen accounts" impact category, since the address becomes forever unusable for its intended stake/vote/nonce purpose absent migrating to the newer, not-yet-universally-adopted `CreateAccountAllowPrefund` instruction.

### Likelihood Explanation
Likelihood is moderate-to-high in scenarios where `base`/`seed` conventions are public or predictable (common for exchange/custodian deterministic account derivation schemes, and any tooling using `create_account_with_seed`). The attack requires only a single, cheap `SystemInstruction::Transfer` of 1 lamport to the target address before the legitimate creation transaction lands — no elevated privileges, no validator/operator role, and minimal cost, consistent with the unprivileged-user constraint of this analysis.

### Recommendation
Consider making `CreateAccountAllowPrefund` semantics (ignore pre-existing lamports as long as data is empty and owner is System Program) the default behavior for `CreateAccount`/`CreateAccountWithSeed`, or provide an automatic account-address rescue path (e.g., transferring/burning attacker-deposited dust automatically as part of `create_account`) rather than requiring a separate opt-in instruction that most existing callers (CLI, stake-o-matic, exchange tooling) do not yet use.

### Proof of Concept
1. Compute a deterministic stake/nonce account address via `Pubkey::create_with_seed(base, seed, owner)` using publicly known `base`, `seed`, `owner` (as done in `Address::create`) [3](#0-2) .
2. Before the legitimate owner submits their `SystemInstruction::CreateAccountWithSeed` transaction, submit a `SystemInstruction::Transfer` of 1 lamport to that derived address.
3. When the legitimate `CreateAccount`/`CreateAccountWithSeed` transaction executes, `create_account` observes `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, permanently blocking initialization of that specific address [1](#0-0) , mirroring `test_create_already_in_use`'s "account that already has lamports" case in the existing test suite [7](#0-6) .

#[allow(clippy::too_many_arguments)]
fn create_account(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    to_address: &Address,
    lamports: u64,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(
                invoke_context,
                "Create Account: account {:?} already in use",
                to_address
            );
            return Err(SystemError::AccountAlreadyInUse.into());
        }

        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(
        from_account_index,
        to_account_index,
        lamports,
        invoke_context,
        instruction_context,
    )
}

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
