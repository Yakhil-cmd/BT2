## Analysis

The Discourse CVE describes a class of bug where **a dedup/identity check uses a non-canonical or incomplete identifier**, letting an attacker slip a distinct/malicious object past a check meant to recognize "this is the same thing I already have," causing the system to skip proper processing of the new object.

The closest reachable analog in ocore is in the **private-payment chain dedup logic** in `private_payment.js`, which is on the direct path of a private-payment counterparty processing an incoming private chain from another party (device message / P2P but application-level, reachable by any private-payment counterparty, not a network/hub attacker).

### Title
Loose "duplicate" match in private-payment chain validation lets an attacker bypass spend-proof, double-spend, and chain-integrity validation - (File: `private_payment.js`)

### Summary
`validateAndSavePrivatePaymentChain()` in `private_payment.js` short-circuits full chain validation whenever an already-stored output row happens to match *any* output entry in the incoming payload, rather than verifying that the specific chain being submitted is actually identical to a previously validated one.

### Finding Description
When a private-payment chain arrives, before invoking the real validator (`indivisibleAsset`/`divisibleAsset`'s `validateAndSavePrivatePaymentChain`, which checks spend proofs, graph inclusion, and amount conservation for the whole chain), the code performs a shortcut "already known" check: [1](#0-0) 

For divisible assets, the query has **no `output_index` filter** and the duplicate test iterates over *all* of `payload.outputs`, declaring a duplicate if *any* output in the incoming payload matches a stored row's `denomination/amount/address/blinding`:
```
else // divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them
    bDuplicate = (payload.outputs || []).some(output => { ... });
```
If `bDuplicate` is true, the function calls `transaction_callbacks.ifOk()` directly and **never calls `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)`** — i.e., the entire chain (spend proof check, `graph.determineIfIncludedOrEqual`/`determineIfIncluded` ancestry check, and amount validation performed inside `validatePayment`) is skipped: [2](#0-1) [3](#0-2) 

The identity check used for the "already validated" shortcut (matching a subset of *output* fields for the same `unit`/`message_index`) is not a canonical identifier of the whole chain (it doesn't tie to `output_index`, doesn't verify spend proofs, and doesn't verify the parent linkage that `buildPrivateElementsChain`/`validatePrivatePayment` normally enforce). This mirrors the Discourse flaw where a non-canonical identifier used for a "this already exists" check let a distinct object skip proper handling.

### Impact Explanation
An attacker who already knows one previously-revealed output (address+blinding+amount+denomination) for a given `unit`/`message_index` — which is disclosed to legitimate prior recipients/cosigners of that same payment message as part of normal private-payment flow — can submit a *different, unvalidated* `arrPrivateElements` chain (e.g., with a bogus/double-spent source input, wrong spend proof, or broken ancestry) that reuses that output value. Because the duplicate check only inspects the final output fields and not the full chain, the malicious chain is accepted via `ifOk()` without ever running spend-proof verification or double-spend/ancestry checks. This can let a counterparty in a private-asset payment be tricked into recording as valid a chain that does not correspond to a legitimately spent, non-double-spent input — i.e., private-asset double-spend / unauthorized crediting of private-asset balance in the recipient's local wallet state.

### Likelihood Explanation
Exploitation requires the attacker to know one output tuple `(address, blinding, amount, denomination)` for the exact `unit`/`message_index`, which is realistic in cosigned/multi-recipient private payments (change outputs and multiple recipients of the same payment message all learn each other's output fields as part of the normal chain-forwarding protocol), or when a chain is legitimately resent and reprocessed. No hub or node privilege is needed — this is triggered purely by a private-payment counterparty crafting and sending a chain via the existing private-payment message flow (`network.js`/`wallet.js` handlers that call into `private_payment.js`).

### Recommendation
Tie the "already known/duplicate" shortcut strictly to the specific `output_index` (and, for divisible assets, reintroduce an output_index-equivalent correlation) and to the specific chain being submitted — e.g., require that the entire submitted `arrPrivateElements` head element matches byte-for-byte (via a canonical hash of the relevant fields) an already fully-validated stored record, rather than matching loosely against any output row for the same `unit`/`message_index`. Alternatively, always run the full `validateAndSavePrivatePaymentChain` path and only use the stored-row comparison as an optimization once the chain is confirmed identical to one already fully validated.

### Proof of Concept
1. Two parties A (payer) and B (payee/cosigner) participate in a private payment where message `(unit=U, message_index=M)` has outputs `[out0 -> address_B, blinding_b, amount_b]` and `[out1(change) -> address_A, blinding_a, amount_a]`; B's wallet stores its own revealed `out0` row in `outputs` after successful validation.
2. Attacker (impersonating A or intercepting) crafts a new `arrPrivateElements` chain for the *same* `(U, M)` but with a forged/invalid parent (e.g., an already-spent or fabricated source output) — an attempt that would normally fail spend-proof/ancestry validation in `indivisible_asset.js`/`divisible_asset.js`.
3. Attacker ensures `payload.outputs` in the forged chain includes an output object with the exact same `address_B/blinding_b/amount_b/denomination` as B's previously stored `out0` (values B disclosed to A during the original chain forwarding).
4. B's node runs `validateAndSavePrivatePaymentChain`; the query at `private_payment.js:62-69` finds the stored row, the `.some()` match at line 92-98 succeeds against `out0`'s values, `bDuplicate` is `true`, and `transaction_callbacks.ifOk()` fires — the forged chain is accepted without ever running `assetModule.validateAndSavePrivatePaymentChain`, bypassing spend-proof and ancestry verification.
