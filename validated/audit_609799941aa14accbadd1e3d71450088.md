This is the strongest reachable analog in this engine: the webhook signature is verified against the sending organization's secret, but the `status` webhook handler applies the payload's `sha` globally across every stack/commit in the database, not scoped to the reporting repository.### Title
Cross-repository commit-status injection via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook only against the **organization** that owns the app installation, using `Shipit.github(organization: repository_owner)` [1](#0-0) . Once the signature is accepted, `StatusHandler#process` uses the attacker-controlled `sha` field from the payload to look up commits **across the entire application**, with no scoping to the repository/stack the signed webhook actually belongs to:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This is the same bug class as the reported NFT issue: a value in the payload (`sha`/`receiver_id`) is trusted and acted upon for an entity (a commit belonging to *any* stack / the wrong NFT owner) that is different from the entity the signature/authorization actually covers (the repository that sent the webhook / the correct owner).

### Finding Description
The equality that should hold is:

`repository whose organization-secret signed the webhook == repository/stack whose commit state gets mutated`

Before the attacker's action: a legitimate status webhook from `orgA/repoA`, signed with `orgA`'s app secret, only ever updates commits that belong to stacks tracking `orgA/repoA` (because in practice the sha reported by GitHub for that repo is a sha reachable in that repo's history).

After the attacker's action: `Commit.where(sha: params.sha)` matches **any** `Commit` record in the database with that sha, regardless of which stack/repository it belongs to [2](#0-1) . Git commit SHAs are stable and repository-independent — the same commit object (and therefore the same SHA) commonly exists in multiple repositories that share history, e.g. a public/OSS repository and any fork of it. An unprivileged attacker who:
1. Forks (or otherwise legitimately controls) a public repository that shares commit history with a Shipit-tracked victim stack, and
2. Has their own GitHub App/webhook installation on their own organization (which they fully control, so they can compute a valid signature for their own org's secret),

can send a `status` event whose `sha` matches a commit that also exists in the victim's Shipit-tracked stack. `verify_signature` will accept the request because the signature is valid for the attacker's own organization [1](#0-0) , but `StatusHandler` will apply the status to **every** commit row with that sha — including the one belonging to the victim's stack — via `commit.create_status_from_github!(params)` [3](#0-2) .

By contrast, the sibling handler `CheckSuiteHandler` correctly scopes lookups to stacks matching the reporting branch before touching commits: `stacks.where(branch: params.check_suite.head_branch)` then `stack.commits.where(sha: ...)` [4](#0-3) , confirming that `StatusHandler`'s lack of a stack/repository scope is the anomaly.

### Impact Explanation
`Commit#create_status_from_github!` creates a `CommitStatus` and triggers `add_status`, which re-evaluates the commit's aggregate `status` and, on success, calls `stack.schedule_merges` [5](#0-4) . Merge-queue eligibility and continuous-deployment eligibility (`MergeRequest#all_status_checks_passed?`, `Commit#deployable?`) are computed directly from these statuses [6](#0-5) [7](#0-6) . An attacker who injects a fabricated "success" status for a commit shared with the victim's stack can cause a pull request to be auto-merged by `ProcessMergeRequestsJob` [8](#0-7)  or trigger an unauthorized continuous deploy via `Commit#schedule_continuous_delivery` [9](#0-8) , bypassing required CI checks — an unauthorized merge/deploy, which is a Critical-tier impact per the stated rules.

### Likelihood Explanation
Exploitation requires only:
- An attacker-controlled GitHub organization with its own GitHub App/webhook (something anyone can create for a repo they own — no privileged access to the victim's Shipit instance, repository, or GitHub org is needed).
- A commit SHA shared between the attacker's repo and the victim's tracked repo, which naturally occurs for forks/mirrors of the same upstream project — a common and realistic scenario for open-source projects using Shipit.

No `ApiClient` token, session, or webhook secret of the victim organization is needed; the attacker only needs a valid signature for *their own* organization's webhook secret, which they control.

### Recommendation
Scope `StatusHandler#process` to the repository indicated by the (already-verified) organization/repository, not a bare global `sha` lookup — e.g. restrict to `stacks` belonging to the repository named in the payload's `repository.full_name`, mirroring the pattern used by `CheckSuiteHandler`:
```ruby
def process
  Repository.from_github_repo_name(params.repository.full_name)&.stacks&.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This ensures a status can only affect commits belonging to the repository that was actually authenticated by the webhook signature.

### Proof of Concept
1. Victim: organization `victim-org` runs Shipit tracking `victim-org/app` (public repo), with a commit `C` at SHA `abc123...` deployed/queued through the merge queue.
2. Attacker forks `victim-org/app` to `attacker-org/app-fork`, which necessarily contains the identical commit `C` at the same SHA `abc123...` (git history is content-addressed).
3. Attacker creates their own GitHub App / webhook pointed at the shared Shipit instance's `/webhooks` endpoint, installed on `attacker-org` (fully within attacker's control, so `attacker-org`'s webhook secret is known to the attacker).
4. Attacker sends a `status` event: `{"sha": "abc123...", "state": "success", "context": "ci/required-check", "repository": {"owner": {"login": "attacker-org"}}}`, signed with `attacker-org`'s secret.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which returns the commit row belonging to `victim-org`'s stack as well, and records the forged "success" status against it [2](#0-1) .
7. If that was the last required/missing status for `victim-org`'s pending merge request or continuous deploy, `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` proceeds to merge/deploy despite the victim's real CI never having reported success.

      yield

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
