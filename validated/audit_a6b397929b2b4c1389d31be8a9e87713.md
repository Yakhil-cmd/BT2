### Title
Stack-scoped `ApiClient` tokens bypass their stack authorization in `CCMenuController#show` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` records can be scoped to a single stack via `stack_id`, and `Api::BaseController` enforces that scope through its `stacks`/`stack` helpers. `Api::CCMenuController` however overrides authentication to accept a bare query-string token and then resolves the target stack with an **unscoped** `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!` inherited from `BaseController`. This breaks the binding "the stack a token authorises" ⇔ "the stack the request actually touches," letting a token issued for one stack read CI/deploy status of any other stack.

### Finding Description
`ApiClient` supports being restricted to a single stack (`belongs_to :stack, optional: true`), and permission scoping is enforced only against that association. [1](#0-0) 

`Api::BaseController` implements the intended binding: when a client is scoped to a stack, `stacks` is restricted to that stack, and `stack` resolves the requested id only within that restricted relation. [2](#0-1) 

`Api::CCMenuController` is designed for tokenized, unauthenticated-session polling (e.g., CI status badges): it authenticates via a raw `params[:token]` instead of HTTP Basic auth used elsewhere. [3](#0-2) 

Crucially, its `stack` method does **not** reuse the inherited, scope-aware `stack`/`stacks` helpers from `BaseController`. It calls `Stack.from_param!` directly on the unrestricted `Stack` model, ignoring `current_api_client.stack_id`: [4](#0-3) 

`CCMenuUrlController#fetch` is the normal issuance path for these tokens: it mints a dedicated, presumably stack-scoped, read-only `ApiClient` per stack for use in CI status URLs (confirmed by the accompanying test asserting an `ApiClient` is created and its `authentication_token` is embedded in the returned `ccmenu_url`). [5](#0-4) 

Because `show` uses `stack.deploys_and_rollbacks.last` from the unscoped lookup, the equality that should hold — `token.stack_id == params[:stack_id]` — is never checked; only `require_permission :read, :stack` is checked, which only validates the `read:stack` permission string, not which stack it applies to. [6](#0-5) 

### Impact Explanation
This directly matches the "stack a token authorises versus a stack it touches" binding called out as an in-scope analog. An attacker who obtains one stack's CCMenu token (these are embedded in plaintext CI badge/status URLs, meant to be low-privilege and widely distributed, e.g., pasted into READMEs or CI dashboards) can query `/api/stacks/<ANY_OTHER_STACK>/ccmenu?token=<TOKEN>` and receive that other stack's latest deploy/rollback status (id, timestamp, running state) — an unauthorized cross-stack read of stack/deploy state, which falls under the High-impact category ("unauthenticated read of stack state ... or deploy output" — here the read is authenticated-by-token but explicitly not scoped to that token's stack, i.e., broader than authorized).

### Likelihood Explanation
Exploitation requires only possession of a CCMenu token for **any one** stack the engine hosts (these tokens are intentionally low-friction — created without a browser session on plain GET and designed to be embedded in external CI tooling/URLs) plus knowledge/guessing of another stack's `owner/repo/env` path segment, which is not secret (stack ids are `owner/repo/environment` strings visible throughout the UI/API). No write access, no GitHub credentials, and no privileged account are needed — only a query-string change.

### Recommendation
In `Api::CCMenuController#stack`, mirror the `BaseController` scoping instead of querying `Stack` directly, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

so the `current_api_client.stack_id` restriction defined in `BaseController#stacks` is enforced for this controller as well, restoring the invariant that a token can only ever resolve the stack it was minted for.

### Proof of Concept
1. Obtain (or self-provision, as an authenticated Shipit user for stack A) a CCMenu URL via `GET /ccmenu/*stack_a_id`, handled by `CCMenuUrlController#fetch`, which returns a `ccmenu_url` containing an `ApiClient` token scoped to stack A. [7](#0-6) 
2. Send that same token against a different stack B: `GET /api/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu?token=<TOKEN_FOR_STACK_A>`.
3. `authenticate_api_client` successfully authenticates the token (it is valid, just scoped to stack A). [3](#0-2) 
4. `stack` resolves stack B directly via `Stack.from_param!`, bypassing the stack-A restriction, and `show` renders stack B's latest deploy/rollback status in the XML response — data the token holder was never authorized to see. [8](#0-7)
