### Title
`pox-5.clar` staking actions omit the `check-caller-allowed` consent gate present in pox-2/pox-3/pox-4, allowing an unauthorised contract to trigger STX locking/unlocking on a user's behalf - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
Every prior PoX contract (`pox.clar`, `pox-2.clar`, `pox-3.clar`, `pox-4.clar`) gates all stacking-state-mutating public functions with `(asserts! (check-caller-allowed) ...)`, which requires that `tx-sender == contract-caller` unless the user has explicitly opted in via `allow-contract-caller`. This prevents any intermediary/unrelated contract from silently invoking stacking operations "on behalf of" a signing principal. `pox-5.clar` drops this mechanism entirely: no `allowance-contract-callers` map, no `check-caller-allowed`/`allow-contract-caller`/`disallow-contract-caller` functions exist, and the core staking entry points (`stake`, `stake-update`, `unstake`, `register-for-bond`, `unstake-sbtc`, `update-bond-registration`, `register-signer`) never verify that `contract-caller` equals `tx-sender`.

### Finding Description
In `pox-4.clar`, `stack-stx`, `stack-increase`, `stack-extend`, `revoke-delegate-stx`, `delegate-stx`, `delegate-stack-stx`, and the aggregation functions all explicitly require: [1](#0-0) [2](#0-1) 

This mirrors the pattern in `pox-2.clar`/`pox-3.clar`/`pox.clar` as well: [3](#0-2) 

The purpose of this check is exactly analogous to the missing `requiresApprovedCaller` modifier in the `VirtualAccount.payableCall` bug: it is a consent gate ensuring that a stacking action tied to `tx-sender`'s locked STX can only be triggered directly by that principal, or by a contract the principal has explicitly whitelisted via `allow-contract-caller`. Without it, any other contract that the user happens to call into during the same transaction (even unknowingly, e.g. a DeFi vault, DEX router, or malicious "airdrop claim" contract) can forward a `contract-call?` into the staking contract, and because `tx-sender` is preserved across the call chain, the staking action executes as if the user had called it directly - despite the user never intending or approving that specific staking effect.

`pox-5.clar`'s public entry points that mutate locked-STX/lock schedule state - `stake`, `stake-update`, `unstake`, `register-for-bond`, `unstake-sbtc`, `update-bond-registration`, `register-signer` - use `tx-sender` for the staker identity but contain **no equivalent `check-caller-allowed`-style assertion**, and the contract defines no `allowance-contract-callers` map or `allow-contract-caller`/`disallow-contract-caller`/`check-caller-allowed` functions at all (absent from the constants/maps declarations and from every function body reviewed): [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

None of these gate on `contract-caller`. `announce-l1-early-exit` is the one function in the sections reviewed that *does* correctly restrict `contract-caller`: [8](#0-7) 
which underscores that the omission elsewhere is an inconsistency rather than an intentional design choice - the contract author clearly knew how to add this guard but forgot it on the primary `stake`/`stake-update`/`unstake`/`register-for-bond`/`unstake-sbtc`/`update-bond-registration` paths.

### Impact Explanation
This breaks the "a stacking action the staker/signer never authorised" invariant (High, per the rubric). Concretely:
- A malicious or compromised contract that a user interacts with for an unrelated purpose can silently call `stake` on the user's behalf, locking the user's STX into PoX-5 without their consent (temporary freezing of funds the user did not intend to lock, and forced participation with a signer chosen by the attacker's contract, not the user).
- Conversely, an unrelated contract-caller could invoke `unstake` for a user, unexpectedly ending the user's stacking commitment early and moving the unlock height earlier, defeating whatever commitment/reward assumptions the staker or protocol integrations relied on ("value unlocked early").
- `register-for-bond`/`update-bond-registration` could be triggered by a hostile contract to route a user's stake to an attacker-controlled `signer-manager`, letting that signer capture reward/signing weight the user never delegated.

### Likelihood Explanation
Likelihood is High: the only precondition is that the victim signs *any* transaction whose first hop is a contract that (deliberately or via supply-chain compromise) makes a nested `contract-call?` into `pox-5`'s `stake`/`unstake`/etc. Since `tx-sender` is preserved through the Clarity call chain, no signature forgery or special privilege is needed - this is exactly the attack class the `check-caller-allowed` mechanism was invented to stop in pox-2/3/4, and it requires no admin, miner, or victim key compromise.

### Recommendation
Introduce the same `allowance-contract-callers` map and `check-caller-allowed`/`allow-contract-caller`/`disallow-contract-caller` functions used in `pox-4.clar`, and add `(asserts! (check-caller-allowed) ERR_UNAUTHORIZED)` (or equivalent) at the top of `stake`, `stake-update`, `unstake`, `register-for-bond`, `unstake-sbtc`, `update-bond-registration`, and `register-signer` in `pox-5.clar`, mirroring the guard already correctly present in `announce-l1-early-exit`.

### Proof of Concept
1. Deploy a wrapper contract, e.g.:
```clarity
(define-public (innocuous-entry (signer-manager <signer-manager-trait>) (amount uint) (cycles uint) (start-ht uint))
  (contract-call? .pox-5 stake signer-manager amount cycles start-ht none))
```
2. Trick/induce a victim (who has never called `allow-contract-caller`, since no such function exists in pox-5) to sign a transaction calling `innocuous-entry`.
3. Because `tx-sender` remains the victim throughout the nested call, `pox-5.stake` executes using the victim's own STX balance and locks it under the attacker-chosen `signer-manager`, with no `check-caller-allowed`-style rejection - unlike the equivalent `pox-4.stack-stx` call, which would fail with `ERR_STACKING_PERMISSION_DENIED` unless the victim had previously called `allow-contract-caller` for `innocuous-entry`.

Note: I was unable to inspect the remainder of `pox-5.clar` (lines ~1450-3845, including `claim-rewards`/`withdraw-reserve`-style functions) due to tool-call budget limits, so it is possible (but based on the consistent absence of the map/functions in the declarations section, unlikely) that a caller-allowance mechanism is implemented elsewhere in the file for these functions specifically.
