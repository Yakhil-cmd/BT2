## Analysis

I confirmed the root cause chain sufficiently to state the finding, though I was not able to read `push_handler.rb` / `status_handler.rb` bodies directly (only confirmed the shared base class behavior) before the tool budget ran out.

### Title
Webhook signature is verified against the organization named in the payload, but handlers act on a different, unverified repository field — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using one payload field (`repository.owner.login`, falling back to `organization.login`), but the actual handlers that mutate Shipit state (sync commits, update statuses, close merge requests, etc.) key off a *different* payload field — `repository.full_name` — via `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties these two fields together, so the signature only proves "this payload was signed by organization X's webhook secret," not "this payload is actually about a repository owned by organization X."

### Finding Description
The controller resolves the GitHub App/secret to verify against like this: [1](#0-0) [2](#0-1) 

`verify_signature` looks up `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`, which is a straightforward HMAC compare against that organization's `webhook_secret`: [3](#0-2) 

Once verification passes, `create` dispatches the entire (attacker-controlled) JSON body to every registered handler for the event type, with no further binding to the organization that was just verified: [4](#0-3) 

Handlers, however, resolve the target `Stack`/`Repository` using a *different* field of the same payload — `repository.full_name` — not `repository.owner.login`: [5](#0-4) 

Because `repository.owner.login` (used for the signature/secret lookup) and `repository.full_name` (used for the actual DB lookup and mutation) are two independent, attacker-supplied strings within the same JSON body, an attacker who controls a webhook secret for *any* organization configured in Shipit (e.g., their own GitHub App installed against their own org, which is a legitimate, unprivileged setup step for any Shipit installation with multiple configured orgs) can craft a payload where:
- `repository.owner.login` = `"attacker-org"` (so the signature check passes using their own known secret), and
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler acts on a stack belonging to a completely different, victim organization).

This breaks the trust binding: **organization authenticated (`repository_owner`, used to pick and verify the signing secret) ≠ repository written (`repository.full_name`, used by handlers to look up and mutate the `Stack`)**.

### Impact Explanation
Depending on which event/handler is targeted, this allows an attacker who only controls one organization's webhook secret to:
- Forge `push` events for a victim stack, causing `GithubSyncJob` to be enqueued and potentially cause the sync logic to trust attacker-supplied SHAs/branch data for a repository they don't own.
- Forge `status`/`check_suite` events to mark a victim's commits as passing CI, bypassing branch-protection-equivalent gating and enabling an **unauthorized deploy** of a commit that hasn't actually passed CI on the real repository.
- Forge `pull_request` events (`closed`, `labeled`, etc.) affecting merge-queue/merge-request state for a victim stack, potentially triggering an **unauthorized merge**.

This lands squarely in the defined High/Critical impact categories: unauthorized deploy/merge, and escalation past intended per-organization isolation of webhook trust.

### Likelihood Explanation
Likelihood is High for any Shipit deployment configured with more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml` showing multiple orgs each with their own `webhook_secret`). Any attacker who is a legitimate/unprivileged member of *one* configured organization (able to see/derive that org's webhook secret, e.g. because they run their own GitHub App there) can immediately forge cross-organization events without needing any Shipit session, API token, or write access to the victim repository — satisfying the "unprivileged attacker" requirement.

### Recommendation
Bind the verified organization to the resource the handlers actually act on. Concretely:
1. Verify the signature using the *same* field the handlers use for lookup (`repository.full_name`'s owner segment), or
2. After signature verification, re-derive `repository_owner` strictly from `repository.full_name` (splitting on `/`) rather than from the separate `repository.owner.login`/`organization.login` fields, so the two can never diverge, or
3. Have `Handler#repository_name` cross-check that the resolved repository's owner matches the organization whose secret validated the signature, rejecting the event otherwise.

### Proof of Concept
1. Configure/attacker controls organization `attacker-org` in `Shipit.github` config (a legitimate GitHub App they installed on their own org, pointing at the same Shipit instance, with a webhook secret they know).
2. Victim Shipit instance also tracks a stack for `victim-org/victim-repo`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Signs the payload with `attacker-org`'s webhook secret (`X-Hub-Signature`).
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own secret.
6. `StatusHandler` (via `Handler#repository_name` → `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`) resolves the victim's `Stack` and records a forged passing CI status for the victim's commit, enabling that commit to become deployable/mergeable despite the attacker having no access to `victim-org`.

**Note on completeness:** I was unable to inspect the full bodies of `push_handler.rb` and `status_handler.rb` before running out of tool iterations; the analysis above relies on the confirmed shared `Handler#repository_name` base method that all handlers inherit, plus the controller's signature-verification logic. If any individual handler additionally re-validates the owner against the verified organization, that specific handler would not be exploitable — this would need to be confirmed by reading each handler file. The `WebhooksController` and `Handler` base class code cited above, however, is exact and does not perform such a cross-check.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
