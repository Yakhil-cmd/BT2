### Title
Deregistered Bridge Operator's Votes Persist and Operator Can Front-Run Removal to Execute Unauthorized Asset Transfers — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator` removes an operator from the `operators` mapping but does **not** revoke their outstanding votes in the `votes` mapping. Combined with the fact that `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` are gated only by `onlyOperators` (a point-in-time check), a compromised operator can front-run their own deregistration to drain bridge funds — a direct analog to the whitelist-removal race condition in the external report.

---

### Finding Description

`BridgeOperator.sol` manages a multi-operator voting system for bridge value transfers. The `deregisterOperator` function removes an operator from the `operators` mapping but explicitly leaves their existing votes intact:

```solidity
// Note that outstanding votes by the deregistered operator are not revoked.
// ...
// The Owner shall recognize this issue and expect that operator deregistration
// takes some time to be fully effective.
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    // operatorList cleanup only; votes[...][...].voted[_operator] is never cleared
    ...
}
``` [1](#0-0) 

The `_voteCommon` function counts votes without verifying that the original voter is still a registered operator at the time the threshold is reached:

```solidity
vote.voteCounts[_voteKey]++;
if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
    return true;
}
``` [2](#0-1) 

The default threshold for both `ValueTransfer` and `Configuration` vote types is **1**, set in the constructor:

```solidity
for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
    operatorThresholds[uint8(i)] = 1;
}
``` [3](#0-2) 

The handle functions (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`) are gated by `onlyOperators`, which is a point-in-time check against `operators[msg.sender]`:

```solidity
modifier onlyOperators() {
    require(operators[msg.sender], "msg.sender is not an operator");
    _;
}
``` [4](#0-3) 

`handleKLAYTransfer` and `handleERC20Transfer` both use `onlyOperators` and directly transfer assets: [5](#0-4) [6](#0-5)

### Impact Explanation

Two distinct attack paths exist:

**Path 1 — Front-running (threshold = 1, the default):**
A compromised operator A monitors the mempool. When the owner submits `deregisterOperator(A)`, A immediately submits `handleKLAYTransfer(...)` (or ERC20/ERC721 equivalent) with a higher gas price. A's transaction is mined first. Since `operators[A]` is still `true` at execution time, the `onlyOperators` check passes, `_voteValueTransfer` reaches threshold=1 immediately, and the bridge sends KLAY/tokens to an attacker-controlled address. The deregistration then mines and removes A — but the transfer has already executed.

**Path 2 — Stale vote persistence (threshold ≥ 2):**
Operator A votes on nonce N (legitimate at the time). The owner deregisters A. A's vote remains in `votes[ValueTransfer][N].voteCounts[voteKey]`. When operator B later votes on the same nonce N with the same parameters, the count reaches threshold and the transfer executes — with A's deregistered vote counting toward quorum. No front-running is required; A's vote is permanently stored and never cleared.

In both cases the corrupted value is the bridge's KLAY balance or ERC20/ERC721 token holdings, transferred to an attacker-controlled `_to` address.

---

### Likelihood Explanation

- The default threshold is 1, making Path 1 trivially exploitable by any single compromised operator.
- Kaia's mempool is public; pending transactions are observable before mining.
- The operator role is semi-trusted (not the owner), and the entire purpose of `deregisterOperator` is to revoke a bad actor — making the window of attack precisely the scenario the owner is trying to close.
- Path 2 requires no timing at all: any vote cast before deregistration persists indefinitely.

---

### Recommendation

1. **Revoke outstanding votes on deregistration**: In `deregisterOperator`, iterate over all open nonces and decrement `voteCounts` for any vote cast by the removed operator, or store a "deregistered-at" block and reject stale votes from operators deregistered before the vote was cast.

2. **Atomic pause-then-deregister**: Add a `pause` mechanism (analogous to the external report's recommendation) that the owner calls first to halt all `handle*` functions, then deregisters the operator, then unpauses. This eliminates the front-running window.

3. **Raise the default threshold**: Require threshold ≥ 2 for any production deployment so that a single compromised operator cannot unilaterally execute transfers.

---

### Proof of Concept

```
Setup:
  - Bridge deployed with operator A (owner), threshold = 1 (default)
  - Bridge holds 100 KLAY

Attack:
  1. Owner detects A is compromised; submits deregisterOperator(A) with gasPrice = P.
  2. A observes the pending tx in the mempool.
  3. A submits handleKLAYTransfer(
         requestTxHash = <any valid hash not yet handled>,
         from = <any>,
         to   = attacker_wallet,
         value = 100 KLAY,
         requestedNonce = <any open nonce>,
         requestedBlockNumber = <current>,
         extraData = ""
     ) with gasPrice = P + 1.
  4. A's handleKLAYTransfer mines first:
       - onlyOperators: operators[A] == true  ✓
       - _voteValueTransfer: voteCounts reaches 1 >= threshold(1)  ✓
       - 100 KLAY sent to attacker_wallet  ✓
  5. deregisterOperator(A) mines: operators[A] = false — too late.

Result: 100 KLAY drained from bridge before deregistration took effect.
```
