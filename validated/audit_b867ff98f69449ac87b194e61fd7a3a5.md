**Root cause chain:**

`getCurrentTps()` in `storage.js` computes the network's current transaction throughput by iterating over `storage.assocUnstableUnits` and summing `getCountUnitsPayingTpsFee(objUnitProps)` for every unit whose `main_chain_index` is null or beyond the stability shift.### Title
Conflicting/final-bad units keep inflating the in-memory TPS-fee statistics, letting the minimum acceptable fee grow unbounded and causing legitimate units to be rejected - (File: storage.js)

### Summary
`getCurrentTps()` / `getRecentTps()` in `storage.js` compute the network's throughput statistics by summing over every entry of the in-memory `assocUnstableUnits` map, but that map is not cleaned up when a unit becomes `final-bad` due to a conflicting/double-spend transaction. Only when a unit finally reaches its main-chain-index and is stabilized does `markMcIndexStable()` remove it from `assocUnstableUnits`. Until then, its resource footprint (`count_primary_aa_triggers` × `max_aa_responses` via `getCountUnitsPayingTpsFee()`) is fully counted toward the "current" and "recent" TPS, exactly analogous to the CKB advisory's core defect: transactions that are effectively rejected/voided are still counted in the pool statistics.

### Finding Description
- `checkSerialAddressUse()` in `validation.js` (around lines 1304-1343) and `checkForDoublespends()`/`checkInputDoubleSpend()` in `validation.js` (lines 1661-1705, 2258-2304) detect conflicting/double-spend units and mark them `temp-bad` or `final-bad` in `objValidationState.sequence`. [1](#0-0) 
- `writer.saveJoint()` stores the new unit's props (including its `sequence`) into `storage.assocUnstableUnits[objUnit.unit]` regardless of whether the unit is `good`, `temp-bad`, or `final-bad`. [2](#0-1) 
- Later, `main_chain.js`'s `markMcIndexStable()` → `propagateFinalBad()` sets the `sequence` field of these cached unit props to `'final-bad'` in place, but it never deletes them from `assocUnstableUnits`. Removal from that map happens only when the *stabilizing* mci is reached, in the `arrStabilizedUnits.forEach(...); delete storage.assocUnstableUnits[unit]` block, which can be many main-chain indices later (final-bad units may sit unstable for a long time waiting for their competitor "good" unit to stabilize). [3](#0-2) [4](#0-3) 
- `storage.getCurrentTps()` and `storage.getRecentTps()` iterate `assocUnstableUnits` unconditionally — they check only `timestamp`/`main_chain_index`, never `sequence` — and add `getCountUnitsPayingTpsFee(objUnitProps)` for every entry, including already-known conflicting/final-bad ones. [5](#0-4) [6](#0-5) 
- `getCurrentTpsFee()`/`getCurrentTpsFeeToPay()` derive the network's fee requirement directly from this inflated `getCurrentTps()` value, and `getMinAcceptableTpsFeeMultiplier()` derives from the equally inflated `getRecentTps()`. [7](#0-6) [8](#0-7) 
- `validateTpsFee()` in `validation.js` then rejects (with a *transient* error, i.e., the unit is discarded and must be resubmitted) any new unit whose paid `tps_fee` is below `min_acceptable_tps_fee = current_tps_fee * min_acceptable_tps_fee_multiplier * count_units`. [9](#0-8) 

Because a burst of conflicting/double-spend units (which an unprivileged unit poster can trivially create by broadcasting two units that spend the same output/address from divergent parents) stays counted in `assocUnstableUnits` for the entire time the fork remains unresolved, `getCurrentTps`/`getRecentTps` over-report network load. This raises the `min_acceptable_tps_fee` threshold for all subsequent unrelated units, causing the pool-wide fee-based admission control to reject legitimately-priced transactions — mirroring the CKB advisory where conflicting transactions removed from the pool were not subtracted from statistics, keeping the pool "full" and rejecting all transactions.

### Impact Explanation
This is a network-availability bug reachable by any unprivileged unit poster: by repeatedly creating cheap conflicting/double-spend units (author the same address, submit two different last-parent chains), an attacker inflates the perpetually-uncleaned `assocUnstableUnits` population used by the fee-estimation formulas. This drives up `getCurrentTpsFee`/`getMinAcceptableTpsFeeMultiplier`, causing `validateTpsFee` to soft-reject (transient error) otherwise valid, correctly-fee-paying units from unrelated addresses across the whole node/network until the conflicting chain resolves and stabilizes. This matches the "network unable to confirm new units" impact category accepted by the rules.

### Likelihood Explanation
Medium. Triggering it requires only posting ordinary conflicting/double-spend units (no privileged role, no malicious peer/node needed), which is inexpensive for an attacker to do repeatedly and keep the fork open, but the magnitude of the fee inflation depends on `constants.MAX_RESPONSES_PER_PRIMARY_TRIGGER`/`max_aa_responses` weighting and on how long the conflicting units remain unstable (`shift`, `tps_interval`, etc.), so the severity of DoS varies with how aggressively an attacker can keep units unstable.

### Recommendation
When a unit's `sequence` is updated to `'final-bad'` (in `propagateFinalBad()` / `handleNonserialUnits()` in `main_chain.js`) or otherwise permanently voided prior to reaching its own stabilization mci, either (a) exclude such units from `getCountUnitsPayingTpsFee` summation inside `getCurrentTps()`/`getRecentTps()` by checking `objUnitProps.sequence !== 'good'`, or (b) remove/flag them out of `assocUnstableUnits`-derived TPS statistics as soon as they are marked bad rather than waiting for the stabilization pass, so the fee-estimation logic accurately reflects only serial, chargeable units.

### Proof of Concept
1. Attacker composes and broadcasts unit `A` from address `X` spending output `O`.
2. Before `A` stabilizes, attacker composes and broadcasts a conflicting unit `B` from the same address `X`, spending the same output `O` from a different parent set. `validateAuthor`/`checkSerialAddressUse` marks one of them `temp-bad`/`final-bad`, but `writer.saveJoint` still inserts it into `storage.assocUnstableUnits`.
3. Attacker repeats steps 1–2 in a loop, keeping many conflicting/`final-bad` units alive in `assocUnstableUnits` while the fork remains unresolved (each conflict pair is cheap and requires only a valid signature).
4. Because `getCurrentTps()`/`getRecentTps()` count every entry in `assocUnstableUnits` (regardless of `sequence`) via `getCountUnitsPayingTpsFee`, the computed TPS and hence `min_acceptable_tps_fee` in `validateTpsFee()` rise proportionally to the number of injected conflicting units.
5. A legitimate user submits a normally-priced unit; `validateTpsFee` rejects it with a transient error because its `tps_fee` no longer clears the inflated `min_acceptable_tps_fee`, effectively denying service to the network until the attacker's forks resolve/stabilize.

	const since_mci = last_stable_mci + shift;

	for (let unit in assocUnstableUnits) {
