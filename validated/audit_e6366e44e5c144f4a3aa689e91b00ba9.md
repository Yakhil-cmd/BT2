### Title
Origin-conversion bypass via `AliasOriginRootUsingFilter<AssetHubKusama, KusamaGlobalConsensus>` lets any signed AssetHubKusama account impersonate arbitrary Kusama-network locations on Asset Hub Polkadot - ([File: system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs])

### Summary
`KusamaGlobalConsensus::contains` accepts *any* location under `(2, [GlobalConsensus(Kusama), ..])`, and it is used as the target-filter for `AliasOriginRootUsingFilter<bridging::to_kusama::AssetHubKusama, KusamaGlobalConsensus>` in `TrustedAliasers`. Because the only origin check performed is that the incoming XCM's origin equals the chain-level location `bridging::to_kusama::AssetHubKusama` — which is the *same* origin for every bridged message regardless of which account on AssetHubKusama sent it — any signed AssetHubKusama user can submit an `AliasOrigin` targeting an arbitrary Kusama-network account/location they do not control, then `Transact` as that aliased origin on Asset Hub Polkadot.

### Finding Description
`KusamaGlobalConsensus::contains` matches `(2, [GlobalConsensus(Kusama)])` or `(2, [GlobalConsensus(Kusama), ..])` with no further constraints on the target location: [1](#0-0) 

This is wired as the target-filter of `AliasOriginRootUsingFilter<bridging::to_kusama::AssetHubKusama, KusamaGlobalConsensus>` inside `TrustedAliasers`: [2](#0-1) 

`bridging::to_kusama::AssetHubKusama` is a fixed, chain-granularity `Location`, `(2, [GlobalConsensus(Kusama), Parachain(AssetHubKusama_id)])`: [3](#0-2) 

This exact location is what the inbound bridge processing establishes as the XCM origin for *every* message relayed from AssetHubKusama through BridgeHubKusama/BridgeHubPolkadot — it is derived from HRMP/`ExportMessage`/`UniversalOrigin`+`DescendOrigin(Parachain(...))` resolution at chain granularity, not per sending account. `pallet_xcm::send` on AssetHubKusama is permitted for any signed account (`SendXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalPalletOrSignedOriginToLocation>`, "Any local signed origin can send XCM messages"): [4](#0-3) 

and the raw `message` a user supplies to `pallet_xcm::send` is forwarded unmodified through the router/exporter; no per-account `DescendOrigin` is injected automatically into the exported program. Consequently, once the message reaches Asset Hub Polkadot with origin exactly `AssetHubKusama`, the `AliasOriginRootUsingFilter` origin check succeeds for *any* AssetHubKusama sender (there is no distinction between the actual invoking account and any other account on that chain), and the target-filter (`KusamaGlobalConsensus`) accepts *any* location under `GlobalConsensus(Kusama)` — including arbitrary `AccountId32` locations for accounts the attacker does not own, other Kusama system parachains, pallet instances, or even the bare Kusama relay-chain root location `(2, [GlobalConsensus(Kusama)])`. Once `AliasOrigin` succeeds, the effective XCM origin becomes the attacker-chosen victim location, and a subsequent `Transact` is dispatched through `XcmOriginToTransactDispatchOrigin`, producing a `RuntimeOrigin` derived from that victim location rather than from the attacker's own identity.

No other layer in `TrustedAliasers` restores the missing binding: `AliasChildLocation` only allows narrowing into sub-locations of the *current* origin (safe), and `AuthorizedAliasers<Runtime>` requires an explicit, victim-authorized alias registration (safe) — but `AliasOriginRootUsingFilter<AssetHubKusama, KusamaGlobalConsensus>` short-circuits both of these protections because it only checks the sender is "some account on AssetHubKusama" and the target is "somewhere in Kusama," with no cryptographic or structural link between the two.

### Impact Explanation
An unprivileged signed account on AssetHubKusama can force Asset Hub Polkadot to execute a `Transact` (or any other origin-sensitive instruction) as if it originated from an arbitrary Kusama-network account/location that the attacker does not control — e.g., another user's `AccountId32`, a Kusama system chain's sovereign, or even a location resolving to Kusama's relay-chain root. Depending on `XcmOriginToTransactDispatchOrigin`'s conversion for these Kusama-network junctions and the dispatched call, this can enable unauthorized asset moves, governance-adjacent actions, or other privileged operations attributed to an account/entity the attacker never controlled — a direct violation of the invariant that XCM origins must not be forgeable.

### Likelihood Explanation
Preconditions are minimal and fully within normal user capability: any signed account on AssetHubKusama can call `pallet_xcm::send` (no special privilege required), craft a raw `Xcm` program containing `AliasOrigin(victim_location)` followed by `Transact(call)`, and target Asset Hub Polkadot through the standard Kusama↔Polkadot bridge route. The exploit is fully repeatable and requires no relayer collusion, no privileged key, and no bug in the bridge messaging layer itself — it is a pure logic gap in the alias-target filter.

### Recommendation
Restrict the `AliasOriginRootUsingFilter` target filter so that the alias target must be structurally derivable from (a descendant of, or otherwise cryptographically bound to) the specific bridged origin, not merely "anything under `GlobalConsensus(Kusama)`." At minimum, tighten `KusamaGlobalConsensus` (and its Polkadot-side analogue `PolkadotOrEthereumGlobalConsensus`) so it cannot match arbitrary unrelated accounts — e.g., require the alias target to equal the sending chain's own location, or require an explicit `AuthorizedAliasers`-style opt-in from the target account rather than a blanket network-wide filter.

### Proof of Concept
xcm-emulator integration test (Kusama<->Polkadot bridge test suite, e.g. `integration-tests/emulated/tests/bridges/bridge-hub-polkadot`):
1. On `AssetHubKusama`, use an attacker-controlled signed account (not the victim) to call `pallet_xcm::send` with `dest = (2, GlobalConsensus(Polkadot), Parachain(AssetHubPolkadot_id))` and `message = Xcm(vec![UnpaidExecution/ WithdrawAsset/BuyExecution as needed, AliasOrigin(victim_location), Transact { origin_kind: SovereignAccount, call: <call whose dispatch effect is observable, e.g. remark_with_event or a balance-affecting call> }])`, where `victim_location = (2, [GlobalConsensus(Kusama), Parachain(AssetHubKusama_id), AccountId32{ id: victim_account }])`.
2. Relay the message through `BridgeHubKusama` -> `BridgeHubPolkadot` -> `AssetHubPolkadot` in the emulator.
3. Assert that the dispatched call's resolved `RuntimeOrigin` on Asset Hub Polkadot corresponds to `victim_location` (i.e., matches the account derived from `LocationToAccountId::convert_location(&victim_location)`), NOT the attacker's account.
4. Assert observable side effects occur under the victim's derived identity (e.g., an event emitted with the victim-derived `AccountId`, or a balance change on the victim-derived account) despite the victim never having signed or authorized anything.
