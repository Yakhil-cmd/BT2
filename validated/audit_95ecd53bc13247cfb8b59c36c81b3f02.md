### Title
Cross-organization webhook signature confusion in `WebhooksController#verify_signature` — organization authenticated ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')`, but the handler that actually mutates state (`PushHandler#process`) resolves the target repository from a *different* field, `payload.dig('repository', 'full_name')`. In a multi-organization deployment (`Shipit.github_organizations`), this creates the same "verify against snapshot A, act on snapshot B" class of bug as `_currentAccountedNativeRewards()`: the equality `organization_used_for_signature_check == organization_that_owns_the_written_repository` is never enforced.

### Finding Description
`WebhooksController#verify_signature` picks the app config via `repository_owner`: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . `Shipit.github(organization: repository_owner)` looks up per-organization config via `github_app_config`, which independently keys `webhook_secret` per organization [3](#0-2) . Crucially, `verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is unset: `return true unless webhook_secret` [4](#0-3) .

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs on the *raw parsed payload*, not scoped to the organization that was used for verification [5](#0-4) . `PushHandler` (and `Handler#repository_name`) resolve the target stack purely from `payload.dig('repository', 'full_name')` [6](#0-5) [7](#0-6) .

This means the field consumed to select the authentication secret (`repository.owner.login`) is not the same field bound to the state-changing action (`repository.full_name`). If an operator configures multiple GitHub organizations in `secrets.github` (as `github_organizations`/`github_app_config` explicitly supports) and any one of those organizations has no `webhook_secret` configured, an attacker can craft an unsigned/arbitrarily-signed webhook whose `repository.owner.login` matches the secret-less org (satisfying `repository_owner`) while `repository.full_name` names a *different*, protected organization's repository. Verification passes (secret is blank for the org used to select config), yet the handler acts on the unrelated organization's `Repository`/`Stack`, e.g. triggering `GithubSyncJob`/`sync_github` with an attacker-supplied `expected_head_sha` [8](#0-7)  for that other stack.

This directly parallels the Solidity finding: `_currentAccountedNativeRewards()` computes the reward window using `nativeRewardsLastPaid` (last known state) but the balance delta actually spans up to `block.timestamp`, letting freshly-arrived funds be over-credited to the wrong window. Here, the signature check is evaluated for organization X (per `repository_owner`), but the write happens against repository/organization Y (per `repository.full_name`) — the "verified" scope and the "acted-upon" scope silently diverge.

### Impact Explanation
This is only exploitable when the deployment configures **more than one** GitHub organization and at least one configured organization omits `webhook_secret` (or an attacker can otherwise get `repository_owner` to resolve to an org with no secret). Given that precondition, an attacker can push unauthenticated webhook events (`push`, `status`, `check_suite`, etc.) that are attributed to and acted upon a different organization's stacks, e.g. forcing `GithubSyncJob` re-sync with a crafted `expected_head_sha`, creating fabricated commit `Status`/`CheckRun` state, or triggering continuous-deployment logic (`ContinuousDeliveryJob`) for a protected stack — none of which require any `ApiClient` token, session, or repository write access. This maps to "unauthenticated read/mutation of stack state" territory, since normal operation requires per-org signature verification.

### Likelihood Explanation
Likelihood is conditioned on operator configuration (multi-org setup with a mixed/missing `webhook_secret`), which the code explicitly supports (`TOP_LEVEL_GH_KEYS`, `github_organizations`) rather than being an edge case; nothing in `WebhooksController` or `GithubApp` cross-checks that the resolved organization actually owns the acted-upon repository. This is a plausible, not merely theoretical, misconfiguration given the engine's own multi-tenant design.

### Recommendation
Bind the two lookups together: after selecting the GitHub App config via `repository_owner`, verify that `payload.dig('repository', 'full_name')`'s owner matches `repository_owner` (or, better, resolve `Repository`/`Stack` scoping strictly by the same organization used for signature verification) before dispatching to handlers. Additionally, do not silently treat a missing `webhook_secret` as "verification passed" for any organization in a multi-org configuration — require explicit opt-in for unsigned webhooks per organization, and log/reject cross-organization payload mismatches the same way `Hook`/native-reward-style code should track a consistent "last known" state instead of mixing snapshots.

### Proof of Concept
1. Configure `secrets.github` with two organizations: `orgA` (no `webhook_secret`) and `orgB` (has stacks and a configured `webhook_secret`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...attacker-controlled-sha",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/protected-repo"
  }
}
```
3. `verify_signature` computes `repository_owner = "orgA"`, loads `orgA`'s (secret-less) `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally (`return true unless webhook_secret`), regardless of any signature header sent.
4. `PushHandler#process` then resolves `stacks` from `repository.full_name = "orgB/protected-repo"`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `orgB`'s stack — a stack the attacker was never authenticated against.

Note: this proof of concept depends on the operator's specific multi-organization `secrets.github` configuration (at least one org without `webhook_secret`); I could not find code in `app/**`/`lib/shipit/**` that prevents this cross-organization mismatch, but I also could not confirm from the available index whether any deployment-level safeguard (e.g., required non-blank `webhook_secret` validation) exists outside the excluded paths (`docs/**`, `config/`), so this should be validated against the full `config/` and any secrets-schema validation before treating it as certain.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
