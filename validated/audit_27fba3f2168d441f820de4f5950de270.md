### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while target repository/stack is resolved from `repository.full_name` — cross-organization write - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which per-organization GitHub App secret to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`), but the handlers that actually mutate state (e.g. `PushHandler`, status/check_suite handlers) resolve the target `Repository`/`Stack` using `repository.full_name` via `Repository.from_github_repo_name`. These two fields both come from the same attacker-influenced JSON body but are never cross-checked against each other, breaking the intended binding: `organization authenticated == repository written`.

using `repository_owner`, computed as: [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key when Shipit is configured with the multi-org schema: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` dispatches the *same raw JSON payload* to handlers: [4](#0-3) 

Handlers determine the target repository/stacks using `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks up strictly by that owner/name pair, independent of whatever `repository.owner.login` said: [6](#0-5) 

Because `repository.owner.login` and the owner segment embedded in `repository.full_name` are two independent JSON fields inside the same payload, an attacker who controls a GitHub App/webhook installation on their own organization ("Org A", legitimately possessing Org A's `webhook_secret`) can construct a payload where:
- `repository.owner.login` = `"org-a"` (so `verify_signature` picks Org A's `GitHubApp` and the HMAC computed with Org A's `webhook_secret` validates), and
- `repository.full_name` = `"org-b/victim-repo"` (a different, victim organization's repository configured in the same Shipit instance).

The signature only proves the request was signed with *some* org's secret in this Shipit instance — it does not prove which org's data the payload legitimately describes, since `verify_signature` and the handlers key off different fields of the same untrusted body.

### Impact Explanation
This is a cross-repository/cross-organization write in a multi-tenant Shipit deployment (one instance serving multiple `github` orgs, as documented in `docs/setup.md` "Using Multiple Github Applications"). With a valid signature computed from an attacker-controlled org's `webhook_secret`, an attacker can:
- Forge `push` events (`PushHandler`) that enqueue `stack.sync_github(expected_head_sha:)` for a victim org's stack/branch, influencing which commit is considered "head" for deploy purposes.
- Forge `status`/`check_suite` events to inject fake CI statuses/check-runs on a victim's stack's commits, which downstream can gate or unblock deploys/merges.
- Forge `membership` events to add arbitrary GitHub logins into `Shipit.github_teams`-backed teams, potentially escalating authorization for the application (an unrelated attacker-controlled GitHub login could be granted membership in a team that Shipit treats as authorized).

This satisfies the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" impact tiers, achievable purely by owning a low-privilege GitHub App installation on an attacker-controlled org that happens to be configured (even independently) in the same multi-org Shipit instance — no access to the victim org's credentials, no Shipit session, and no `ApiClient` token is required.

### Likelihood Explanation
Exploitability is conditioned on the deployment using the documented multi-organization `github:` configuration schema (multiple orgs behind one Shipit instance), which is an explicitly supported and documented configuration, not a misconfiguration outside the engine's own code. Within that configuration, any org owner/admin who can install their own GitHub App/webhook (a low-privilege action over their own resources) can obtain a valid `webhook_secret` for their org and then freely forge the `repository.full_name` field to target any other org's repository tracked by the same Shipit instance. No social engineering, TLS interception, or privileged account is needed.

### Recommendation
In `WebhooksController#verify_signature`/`create`, derive the repository/stack lookup key from the same field used to select the verifying GitHub App (`repository.owner.login`/`organization.login`), or explicitly assert that the owner segment of `repository.full_name` matches `repository_owner` before dispatching to handlers. Equivalently, `Handler#repository_name` (and `Repository.from_github_repo_name`) should validate that the resolved repository's `owner` matches the organization whose secret validated the signature, rejecting the webhook (422) otherwise.

### Proof of Concept
1. Configure Shipit with the multi-org schema, with `org-a` (attacker-controlled) and `org-b` (victim) both having a Shipit-registered GitHub App/`webhook_secret`, and `org-b/victim-repo` tracked as a Shipit stack.
2. Attacker installs/owns the GitHub App webhook for `org-a` and thus knows `org-a`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
signed with `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook_secret, raw_body)>`.
4. `verify_signature` computes `repository_owner` = `"org-a"`, fetches Org A's `GitHubApp`, and the signature validates (since it was in fact computed with Org A's secret) — request passes.
5. `WebhooksController#create` dispatches the parsed payload to `PushHandler`, whose `repository_name` reads `payload.dig('repository','full_name')` = `"org-b/victim-repo"`, resolving to the victim's `Stack` and calling `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — a write against Org B's stack performed using Org A's credentials.
