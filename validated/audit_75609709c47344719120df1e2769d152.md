### Title
Unbounded artifact download in `downloadArtifact` allows disk/memory exhaustion via oversized or endlessly-streaming ZIP response - (File: pkg/cmd/run/download/http.go)

### Summary
`downloadArtifact` streams the HTTP response body for a workflow-run artifact directly to a temporary file using `io.Copy` with no maximum size, no `Content-Length` validation, and no read timeout/context deadline. A malicious or compromised artifact source can serve an arbitrarily large or endlessly-streaming body, causing `gh run download` to consume unbounded disk space (and correspondingly unbounded time/CPU) on the victim's machine.

### Finding Description
`downloadArtifact` issues a `GET` request for the artifact ZIP URL and copies the response body straight into a temp file without any bound: [1](#0-0) 

The `size` returned by `io.Copy` is only used afterward to construct the `zip.Reader`; there's no cap enforced during the copy, no check against a declared `Content-Length` header, and no context-based timeout on the request (`http.NewRequest` is created without a context, and the shared `httpClient` used elsewhere in this package is not configured with a global body-size limiter, as seen in `api/http_client.go`'s `NewHTTPClient`, which sets headers/auth/telemetry but no `io.LimitReader` or `MaxBytesReader` wrapping). This differs from other parts of the codebase (e.g., `pkg/cmd/skills/preview/preview.go`) which explicitly enforce a `maxTotalBytes` cap when reading remote content, showing that the project is aware of this class of risk elsewhere but does not apply it here.

The artifact URL itself comes from the GitHub Actions API (`shared.ListArtifacts`), and while the URL host is constrained by `safeurl.SafeURL`, nothing constrains the size or duration of the response body served from that host. An attacker who can get an oversized or slow/endless artifact published for a workflow run they control (e.g., a public repo where they can trigger workflow runs, or by tricking a victim into pointing `gh run download` at a hostile Actions runner endpoint) can cause the victim's `gh` process to write unbounded data to a temp file and/or block indefinitely reading the body.

### Impact Explanation
This is unbounded resource consumption (disk fill / memory or time exhaustion) triggered by a single attacker-published artifact, matching the "High - Unbounded resource consumption" impact class. Filling the victim's disk via a temp file (`os.CreateTemp("", "gh-artifact.*.zip")`) can affect other processes on the machine, and an endlessly-streaming body can hang the `gh` process indefinitely since there is no read deadline or context cancellation.

### Likelihood Explanation
Any GitHub user who can trigger a workflow run producing an artifact (e.g., in their own public repo, or a repo where they have write access such as a fork/PR context) controls the artifact bytes/size served by GitHub's artifact download URL, and a victim who runs `gh run download` against that run is directly exposed. The exploit requires no special privileges beyond normal artifact publication and no bypass of existing protections, since none of the existing safeurl/safepaths checks restrict body size or duration.

### Recommendation
- Enforce a maximum artifact size, e.g., wrap `resp.Body` with `io.LimitReader` (plus explicit check that copied bytes did not silently hit the cap) or use `http.MaxBytesReader`-style enforcement before writing to disk.
- Validate/compare against `resp.ContentLength` if present, and reject artifacts declaring an unreasonable size before starting the copy.
- Add a request timeout / context deadline (e.g., `http.NewRequestWithContext` with a bounded context, or `httpClient.Timeout`) to prevent slow-loris style endless streaming.
- Optionally surface download progress against the declared size, as the invariant in the question suggests.

### Proof of Concept
```go
func TestDownloadArtifact_UnboundedBody(t *testing.T) {
    // Simulate an attacker-controlled server that streams an effectively endless body.
    ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
        buf := make([]byte, 1024*1024) // 1MB chunk
        for {
            if _, err := w.Write(buf); err != nil {
                return
            }
            if f, ok := w.(http.Flusher); ok {
                f.Flush()
            }
        }
    }))
    defer ts.Close()

    url := safeurl.MustParse(ts.URL) // construct via package helper matching real usage
    destDir := safepaths.MustAbsolute(t.TempDir())

    done := make(chan error, 1)
    go func() {
        done <- downloadArtifact(http.DefaultClient, url, destDir)
    }()

    select {
    case err := <-done:
        t.Fatalf("expected download to hang or fail with a bounded error, got: %v", err)
    case <-time.After(5 * time.Second):
        // Confirms unbounded read: no size cap or timeout stopped the copy.
        t.Fatal("downloadArtifact did not terminate within bound; unbounded read confirmed")
    }
}
```
Expected (fixed) behavior: the download should terminate with a clear "artifact too large" or "download timed out" error well before disk/memory exhaustion, instead of copying indefinitely.
