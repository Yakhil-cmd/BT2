### Title
Creator fee collection permanently DoS'd if the pool creator's token account is frozen by the mint's freeze authority - (File: programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs, programs/cp-swap/src/instructions/collect_creator_fee.rs)

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` always route accrued creator fees to a single, deterministic recipient — the ATA owned by `pool_state.pool_creator` — via `transfer_from_pool_vault_to_user`. If the underlying SPL Token / Token-2022 mint has a freeze authority (the on-chain analog of an ERC20 "blacklist", used by many centralized stablecoins) and that authority freezes the creator's ATA, every future call to either instruction will revert, permanently locking the accrued `creator_fees_token_0`/`creator_fees_token_1` in the pool vaults since there is no alternate recipient or fallback path.

### Finding Description
Both instructions compute the pending creator fees, then unconditionally attempt a `TransferChecked` CPI to `creator_token_0` / `creator_token_1`, which are `init_if_needed` ATAs bound by seeds to `creator` (i.e., `pool_state.pool_creator`): [1](#0-0) 

The transfer and the state reset (`pool_state.creator_fees_token_0 = 0;`) happen in the same instruction, so a failed transfer reverts the whole transaction and the accrued fee counters are left unchanged: [2](#0-1) 

The same pattern exists in the creator-signed variant: [3](#0-2) 

The actual transfer is a standard `token_2022::transfer_checked` CPI with no handling for a frozen destination account: [4](#0-3) 

On Solana, both SPL Token and Token-2022 support per-account freezing via the mint's `freeze_authority` — this is the on-chain equivalent of the ERC20 blacklist mechanism described in the referenced report (e.g., stablecoin issuers freeze individual token accounts for compliance). Since `creator_token_0`/`creator_token_1` are always the same deterministic ATA (derived from `pool_creator` + mint), once that specific account is frozen there is no way to redirect the transfer to a different, unfrozen destination. Every subsequent call to `collect_creator_fee` or `collect_creator_fee_permissionless` will fail identically, regardless of caller.

### Impact Explanation
The accrued `creator_fees_token_0`/`creator_fees_token_1` become permanently unclaimable — funds stay in `token_0_vault`/`token_1_vault` indefinitely with no code path capable of releasing them to the creator (there's no admin override, no alternate recipient, no way to reset the freeze from within the protocol). This is a permanent freezing of user (pool creator) funds, meeting the Medium/High bar since it can lock an unbounded and growing amount of value over the life of the pool (fees keep accruing while collection is permanently blocked).

### Likelihood Explanation
Likelihood depends on the creator using a mint whose issuer actively exercises freeze authority against their specific ATA (e.g., regulatory/compliance blacklisting of a stablecoin like USDT/USDC-style tokens on Solana). This is not attacker-controlled in a single transaction, but it is a realistic and previously-exploited category of event for centralized-issuer tokens, and once it occurs there is no recovery path in this contract, unlike protocol/fund fee collection where an admin picks the `recipient_token_*_account` at call time and can supply a fresh, unfrozen account.

### Recommendation
Avoid hardcoding a single frozen-prone recipient for creator fees:
- Allow `collect_creator_fee`/`collect_creator_fee_permissionless` to accept a creator-specified (or admin-fallback) alternate recipient token account, rather than force-deriving the ATA from `pool_creator`.
- Alternatively, add an admin/governance recovery path to redirect stuck creator fees to a new address if the canonical ATA becomes frozen, similar to how `collect_fund_fee`/`collect_protocol_fee` let the caller supply arbitrary `recipient_token_*_account`s.

### Proof of Concept
1. Pool is created with `pool_creator = C`, using a Token-2022 (or SPL Token) mint `M` that has an active `freeze_authority` (e.g., a stablecoin-style token).
2. Swaps occur, accruing `creator_fees_token_0 > 0` in `pool_state`.
3. The freeze authority of `M` freezes `C`'s ATA for `M` (the exact account derived by `associated_token::mint = vault_0_mint, associated_token::authority = creator` in `collect_creator_fee`/`collect_creator_fee_permissionless`).
4. Any subsequent call to `collect_creator_fee` (by `C`) or `collect_creator_fee_permissionless` (by anyone) fails at the `TransferChecked` CPI in [5](#0-4) , reverting the transaction.
5. `pool_state.creator_fees_token_0` is never reset to 0 because the reset only happens after both transfers succeed, so the fee remains permanently stuck in `token_0_vault` with no alternate recipient path available.

```rust
pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;
```

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
