### Title
Webhook signature is verified against `repository.owner.login`, but the repository acted upon is selected from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The equality the engine should enforce is: `organization whose secret signed the payload == organization that owns the repository the handler writes to`. Instead, two different sub-fields of the same JSON body are used for each side of that check, and nothing ties them together.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate `X-Hub-Signature` using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [5](#0-4) . Every field inside the JSON body, including `repository.owner.login` and `repository.full_name`, is attacker-controlled plaintext — HMAC covers the raw bytes of the body but the controller trusts individual JSON keys within it to route the *verification* step before the signature is even checked.

Once verification passes, `Handler#stacks` (used by every default handler such as `PushHandler`, `StatusHandler`, etc.) resolves the target `Repository`/`Stack` from a *different* field: `payload.dig('repository', 'full_name')` [3](#0-2) , which is split into `owner`/`name` and looked up directly in `Repository.from_github_repo_name` with no re-check against the organization used earlier for signature verification [4](#0-3) .

Because `repository.owner.login` and `repository.full_name` are two independent keys inside the same JSON object, an attacker who legitimately controls a webhook delivery for an organization/app they own (e.g., their own GitHub org where they installed their own copy of the Shipit GitHub App, so they know that org's `webhook_secret`) can craft a payload where:
- `repository.owner.login` = their own organization (so `Shipit.github(organization: repository_owner)` picks their own app config and their own valid secret, letting `verify_webhook_signature` succeed), while
- `repository.full_name` = `"victim-org/victim-repo"` (an entirely different, unrelated repository tracked by the same Shipit instance).

Since `Handler#stacks` never re-derives or cross-checks the owner against `repository_owner`, the forged event is dispatched against the victim's `Stack`.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written." Depending on the event type, this allows an attacker who only controls a webhook secret for their own, unrelated GitHub org to inject fabricated events against another org's `Stack`:
- A forged `push` event triggers `GithubSyncJob` for the victim stack (`PushHandler` matches by `branch` only, scoped to whatever repository `Handler#stacks` resolved to) [6](#0-5) .
- A forged `status`/`check_suite` event can flip a commit's CI status to `success` via `StatusHandler`, bypassing `ci.require` checks that gate deploys/merges [7](#0-6) .

Combined with continuous deployment or a merge queue, this can lead to an unauthorized deploy/merge on a repository the attacker does not control, which meets the "unauthorized deploy/rollback/merge" High-impact bar in the rules.

### Likelihood Explanation
Requires the attacker to control a GitHub App installation (and its webhook secret) for at least one organization that this same Shipit instance is configured to trust — a realistic scenario for the documented "Using Multiple GitHub Applications" multi-tenant configuration [8](#0-7) . No repository write access or Shipit session is needed; only the ability to deliver a webhook to the public `/webhooks` endpoint with a valid signature for their own org.

### Recommendation
In `Handler#repository_name` (or in `WebhooksController`), require that the owner segment of `repository.full_name` matches `repository_owner`/`organization.login` used for signature verification, rejecting the event (or re-deriving the target repository strictly from the verified owner) if they diverge.

### Proof of Concept
1. Attacker installs their own GitHub App on `attacker-org`, configured in Shipit's multi-org `github:` secrets block, and knows `attacker-org`'s `webhook_secret`.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s known webhook secret and sets `X-Hub-Signature` accordingly.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `attacker-org`'s secret [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `repository.full_name` = `"victim-org/victim-repo"`, unrelated to `attacker-org`, and triggers `GithubSyncJob`/downstream deploy logic for the victim's stack [3](#0-2) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

  github:
    somegithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
