### Title
Future-dated Pyth timestamp permanently poisons the shared `last-update` freshness gate, DoS-ing price resolution for all users - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar` keeps a single, protocol-wide `last-update` map keyed only by `{type, ident}` (i.e. per price feed, shared by every user of every vault/egroup that reads that feed) and enforces monotonic freshness via `oracle-timestamp-fresh`. That function contains a logic flaw: if a submitted `publish-time` is greater than `stacks-block-time`, the staleness delta is forced to `u0`, so the update is *always* accepted as "fresh" no matter how far in the future its timestamp is. Any unprivileged caller can submit price-feed bytes through the public `price-feeds` parameter of `borrow`, `collateral-add`, `collateral-remove`, or `liquidate`, causing `last-update` to be ratcheted forward to that future timestamp. Every later, genuinely current price update for the same feed will then fail the `(>= ts prev)` monotonicity check and revert with `ERR-ORACLE-INVARIANT` until real-world time catches up to the injected value.

### Finding Description
- `resolve-pyth`/`resolve-dia` fetch a fresh price and its `publish-time` from external oracles, then `price-resolve` validates it via `oracle-timestamp-fresh` and, if valid, writes the new timestamp into the shared `last-update` map: [2](#0-1) 
- The freshness check is:
```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
``` [1](#0-0) 
  When `ts > stacks-block-time`, `delta` is hard-coded to `u0`, so the `<= max-staleness` test is trivially satisfied regardless of how far ahead `ts` is. There is no upper bound on how far in the future `ts` may be.
- `last-update` is declared as a single global map keyed by `{type, ident}` only — not per user, per block, or per transaction: [3](#0-2) 
- Because `price-resolve` writes `last-update` whenever `timestamp > last-update-time` (line 391-393), any caller who supplies a feed whose `publish-time` momentarily exceeds `stacks-block-time` (which can legitimately happen due to normal clock drift between the Pyth network and Stacks block timestamps, or via replay of a feed the attacker obtained slightly ahead of local block time) permanently raises the shared gate for that feed.
- Every subsequent transaction from *any other user* that needs to resolve that asset's price (via `price-resolve`/`price-multi-resolve`, used by `borrow`, `collateral-add`, `collateral-remove`, `liquidate`) must supply a feed with `ts >= prev`. Since real feed timestamps advance in step with wall-clock time, they cannot exceed the attacker's artificially inflated value until real time catches up — so `oracle-timestamp-fresh` returns `false` and every one of those calls reverts with `ERR-ORACLE-INVARIANT`.
- This is precisely the "shared cache primed by one caller and consumed by another" pattern: the attacker (unprivileged) primes `last-update`; the victim (any other unprivileged user, e.g. a liquidator trying to liquidate an unhealthy borrower, or a borrower trying to withdraw collateral) is blocked from using the shared oracle state they did not write.

### Impact Explanation
This lands on **High – temporary freezing of funds**. While the poisoned gate is active, no one can `borrow`, `collateral-add`, `collateral-remove`, or `liquidate` against the affected asset because price resolution for it always reverts. Most importantly, this can be used to **block liquidations** of unhealthy positions tied to that asset for the duration of the induced staleness window, protecting an underwater borrower at the expense of the protocol/lenders and any liquidator who is prevented from acting. Funds (collateral/debt operations) for every user of that asset are frozen until the wall-clock timestamp naturally advances past the attacker-injected value.

### Likelihood Explanation
The attack requires only a normal, permissionless call to a public entrypoint (`borrow`, `collateral-add`, `collateral-remove`, or `liquidate`) with a `price-feeds` argument containing a validly-signed Pyth update whose `publish-time` is ahead of the current `stacks-block-time`. Such feeds are not artificially forged — Pyth/Wormhole updates can legitimately be a few seconds ahead of a given Stacks block's timestamp due to normal network/clock skew, and an attacker only needs to capture and submit one such update at an opportune moment (e.g., right before attempting to protect their own or a colluding unhealthy position from liquidation). No special privileges, DAO control, or flashloan capital are required.

### Recommendation
Bound the future-timestamp allowance in `oracle-timestamp-fresh`: reject (or clamp) `ts` values that exceed `stacks-block-time` by more than a small explicit tolerance (e.g. a few seconds) instead of setting `delta` to `u0` unconditionally. This prevents an attacker from ratcheting `last-update` to an arbitrarily distant future value while still tolerating legitimate minor clock drift.

### Proof of Concept
1. Attacker monitors Pyth price update feeds for the target asset and obtains a validly signed update whose `publish-time` is `T_future`, slightly ahead of the current Stacks block's `stacks-block-time` (`T_block`).
2. Attacker calls any public function accepting `price-feeds` (e.g. `collateral-add`) supplying that feed. `resolve-pyth` returns `timestamp = T_future`; `oracle-timestamp-fresh(T_future, prev, max-staleness)` computes `delta = u0` (since `T_future > stacks-block-time`) and returns true regardless of `max-staleness`; `price-resolve` then executes `(map-set last-update key T_future)`.
3. In subsequent blocks, honest users (e.g. a liquidator calling `liquidate`, or a borrower calling `borrow`) submit genuinely current Pyth feeds with `publish-time = T_real`, where `T_real < T_future` (because real wall-clock time has not yet caught up to the attacker's injected future value).
4. `oracle-timestamp-fresh(T_real, T_future, max-staleness)` fails the `(>= ts prev)` check, so `price-resolve` returns `ERR-ORACLE-INVARIANT`, and the honest user's transaction reverts.
5. This repeats for every legitimate caller touching that asset's price until real time exceeds `T_future`, during which liquidations and other price-dependent operations for that asset are denied.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
