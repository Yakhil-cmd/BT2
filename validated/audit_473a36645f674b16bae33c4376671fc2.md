### Title
Arbiter-contract "share" logic leaks counterparty's device pairing secret (`peer_pairing_code`/`my_pairing_code`) to unrelated wallet cosigners - (File: arbiter_contract.js)

### Summary
`shareContractToCosigners()` and `shareUpdateToCosigners()` in `arbiter_contract.js` forward the entire `wallet_arbiter_contracts` row (obtained via `SELECT * ... WHERE hash=?` in `getByHash`) to every cosigner of `my_address`, including the `my_pairing_code` and `peer_pairing_code` fields. [1](#0-0) [2](#0-1)  These "pairing code" strings encode `device_pubkey@hub#pairing_secret`, i.e. a bearer credential that lets whoever possesses it pair with (become a trusted correspondent of) the device that generated it. [3](#0-2) [4](#0-3)  A cosigner is a device that merely shares signing authority over `my_address` in a shared multisig wallet — it has no legitimate need to know the opposing contract party's (`peer_pairing_code`) or my own (`my_pairing_code`) device-pairing credentials, which are analogous to the confidential `client_secret` unintentionally exposed to low-privilege OAuth token holders in the upstream authentik report.

### Finding Description
`getByHash()` performs an unrestricted `SELECT *` over `wallet_arbiter_contracts` and returns every column, including `my_pairing_code` and `peer_pairing_code`. [1](#0-0) 

These pairing codes are generated from the permanent device pairing secret (`device.getOrGeneratePermanentPairingInfo`), formatted as `pubkey@hub#pairing_secret`. [5](#0-4) [3](#0-2)  Anyone who obtains this string can call `sendPairingMessage`/`handlePairingMessage` to pair with the target device as a new correspondent, because the hub only checks that the secret exists and is unexpired — it performs no additional authorization. [6](#0-5) 

`shareContractToCosigners(hash)` fetches the full contract object (containing both pairing codes) and sends it verbatim to every device returned by `getAllMyCosigners`, i.e. every device that co-signs `my_address` in the local wallet: [7](#0-6) [8](#0-7) 

`shareUpdateToCosigners(hash, field)` similarly forwards individual field values — and `peer_pairing_code` is an explicitly allowed field for this function — directly disclosing the counterparty's pairing secret to cosigners on any update. [9](#0-8) [10](#0-9) 

Both functions are invoked automatically as part of normal contract flows (`respond()`, `createSharedAddressAndPostUnit()`), with no filtering of sensitive fields before transmission: [11](#0-10) [12](#0-11) 

This mirrors the reported bug class exactly: a nested/joined object (the full contract row, analogous to the nested `provider` object in the OAuth `access_tokens` response) contains a confidential credential (`client_secret`/`pairing_secret`) that is exposed to a party (cosigner / non-admin token holder) whose privilege level does not warrant access to it.

### Impact Explanation
A cosigner who receives the leaked `peer_pairing_code` can silently pair with the counterparty's device without their knowledge or consent, becoming a trusted correspondent. Once paired, the cosigner can impersonate a legitimate correspondent toward the peer device and initiate additional wallet/contract protocol messages (e.g., new arbiter/prosaic contract offers, signing offers, shared-address proposals) that the peer's software will process as coming from a known contact, enabling social-engineering-driven fund-loss scenarios (e.g., tricking the peer into signing a malicious multisig payment or shared address). This directly touches the "wallet and contract message handling" and "paired device" attack surface named in scope, and the ultimate risk is unauthorized fund movement mediated through the abused trust relationship, not merely a passive information leak.

### Likelihood Explanation
Every arbiter contract negotiated on a shared/multisig `my_address` automatically triggers `shareContractToCosigners`/`shareUpdateToCosigners`, so any cosigner of that address routinely and unavoidably receives the leaked pairing codes as part of normal application flow — no special timing or race condition is required, only participation as a cosigner on a wallet that is also used to negotiate an arbiter contract.

### Recommendation
Strip `my_pairing_code` and `peer_pairing_code` (and any other correspondent-only secrets) from the object before calling `shareContractToCosigners`/`shareUpdateToCosigners`, and add `peer_pairing_code`/`my_pairing_code` to a deny-list of fields never broadcast to cosigners in `setField`'s sharing path. Cosigners should only receive the fields they need to render/confirm the shared-address transaction (status, amount, asset, shared_address, party names), never device pairing credentials.

### Proof of Concept
1. Alice and Bob negotiate an arbiter contract; Alice's `my_address` is a 2-of-2 multisig wallet shared with cosigner device Carol.
2. Bob accepts the contract; `respond()` sets `my_pairing_code` (Bob's) and sends it to Alice via `arbiter_contract_response`, which Alice's `setField`/flow stores as `peer_pairing_code` on her side. [11](#0-10) 
3. When Alice's side proceeds (e.g., `createSharedAddressAndPostUnit` → `shareContractToCosigners`), the full contract row, including `peer_pairing_code` (Bob's pairing secret) and `my_pairing_code` (Alice's pairing secret), is sent to Carol via `arbiter_contract_shared`. [12](#0-11) [7](#0-6) 
4. Carol, who is only a signing cosigner on Alice's address and has no legitimate relationship with Bob, extracts `peer_pairing_code` from the received message and uses `sendPairingMessage` to pair with Bob's device directly, without Bob's or Alice's awareness. [13](#0-12) 
5. Carol is now a trusted correspondent of Bob and can send further device-protocol messages that Bob's device treats as coming from a known peer.

**Uncertainty note:** I was unable to fully trace how far an unsolicited pairing (step 4/5) can be leveraged into actually moving funds without additional user confirmation dialogs on the recipient's side (some flows like `handleOfferToCreateNewWallet` emit UI-confirmation events rather than acting fully autonomously). The severity therefore depends on how much of the subsequent exploitation chain requires user interaction versus being fully automatic; I could not verify this end-to-end within the available index. A full Devin session with repository access would be needed to confirm the exact automatic-vs-confirmed behavior of downstream device-message handlers.
