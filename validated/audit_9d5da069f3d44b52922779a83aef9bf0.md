### Title
Stack-scoped API tokens can read CI/deploy status of any other stack via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` enforces the binding "the stack(s) a token authorizes == the stack it may touch" via the `stacks`/`stack` helper methods, but `Api::CCMenuController` overrides `stack` in a way that breaks this binding, letting a token scoped to one stack read the CI status of an arbitrary other stack.

### Finding Description
`Api::BaseController` restricts a stack-scoped `ApiClient` to the stack it was created for: [1](#0-0) 

`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves the requested `params[:stack_id]` only from that restricted relation via `from_param!`. This is the mechanism that keeps a token bound to "its" stack (e.g. `here_come_the_walrus` fixture, scoped to the `shipit` stack) from touching other stacks — confirmed by the existing test asserting a stack-scoped client only sees its own stack via `StacksController#index`: [2](#0-1) 

`Api::CCMenuController`, however, defines its own private `stack` method that completely bypasses this scoping and resolves the stack straight from the global `Stack` relation: [3](#0-2) 

Authorization is enforced only via `require_permission :read, :stack`, which just checks that the token carries the string permission `read:stack` — it never checks which specific stack the permission applies to: [4](#0-3) 

So the binding that should hold — `current_api_client.stack_id == stack.id` for any client with a non-null `stack_id` — is enforced in every other API controller that inherits `stack`/`stacks` from `BaseController` (stacks, tasks, deploys, hooks, etc.), but is silently broken in `CCMenuController`, whose route accepts an arbitrary `stack_id` segment: [5](#0-4) 

### Impact Explanation
Any holder of a valid stack-scoped API token with `read:stack` permission (e.g. the auto-generated "CCMenu Client" created by `CCMenuUrlController#client`, or any manually scoped `ApiClient`) can authenticate and then supply a different `stack_id` in the URL to read that other stack's build/deploy status (name, activity, last build status/label/time, web URL, lock state) — data belonging to a repository/stack the token was never authorized to access. This is an unauthenticated-for-that-stack read of stack state that crosses a repository/stack authorization boundary the rest of the API enforces, matching the High-severity category of "unauthorized read of stack state."

### Likelihood Explanation
Likelihood is low-to-moderate: exploitation requires possession of any valid stack-scoped token (these are routinely created and distributed for CI dashboard integration via `CCMenuUrlController`, which embeds the token in a URL query string). Given such a token, the attack is a single unauthenticated (from the target stack's perspective) HTTP GET with a different `stack_id`, requiring no elevated privilege.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the inherited, scope-aware `stacks` method (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so stack-scoped tokens cannot address stacks outside their `stack_id` binding — consistent with every other controller under `Api::BaseController`.

### Proof of Concept
1. Create (or obtain) a stack-scoped `ApiClient` bound to Stack A with permission `read:stack` (e.g. via `CCMenuUrlController#fetch`, which creates such a client for the current stack: [6](#0-5) ).
2. Using that token's `authentication_token`, issue `GET /api/stacks/<Stack-B-owner>/<Stack-B-repo>/<Stack-B-env>/ccmenu?token=<token>` where Stack B is a different stack than the one the token is scoped to.
3. Observe that `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!` (bypassing the `stacks` scoping check), and the controller returns Stack B's build/deploy status XML, despite the token only being authorized (`stack_id`) for Stack A — confirmed by contrast with `StacksController#index`, which correctly restricts results to the token's own stack when scoped ( [2](#0-1) ).
