### Title
Unchecked `i128` overflow in index accrual permanently freezes a saturated market — (`File: contracts/pool/src/interest.rs`)

### Summary
The CVE class is "a public function fails to handle an internal error, producing a crash/DoS." The analog in XOXNO Lending: the fixed-point `mul` used by interest accrual converts `I256` intermediates back to `i128` and panics with `GenericError::MathOverflow` instead of clamping to the documented index cap. Once the ray-denominated total value (`scaled_amount * index`) can no longer fit in `i128`, every accrual panics. Because every stateful verb accrues first (`global_sync` in `contracts/pool/src/interest.rs:20`), the market freezes permanently: no `supply`, `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, or `update_indexes` can complete.

### Finding Description
`accrue_chunk` calls `accrue_step`, which internally computes `borrowed.mul(env, old_borrow_index)` / `new_total_debt` (see `common/src/rates/index.rs:80-81` in `calculate_supplier_rewards`). `Ray::mul` ultimately resolves through `mul_div_floor` → `to_i128`, which panics on any result that does not fit `i128` (`common/src/math/fp_core.rs:300-303`). `update_borrow_index` caps the *index* at `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:14-18`), but the panic occurs in the *value* computation `scaled * index`, before/independent of that cap. On a high-decimals token (e.g. 18 decimals), a whale-scale supplied amount near the cap combined with a steep interest curve pushes `supplied * index` past `i128::MAX` while `borrow_index` is still well under `MAX_BORROW_INDEX_RAY`. The repository's own test demonstrates this: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) shows `update_indexes` reverting with `MATH_OVERFLOW`, and confirms both `withdraw` and `repay` revert identically because every entrypoint accrues first.

### Impact Explanation
Permanent freezing of funds. All suppliers and borrowers in that `(hub, token)` market lose the ability to withdraw, repay, or be liquidated; liquidation-based bad-debt cleanup also cannot run because it accrues first. There is no recovery path within the pool's entrypoints — the panic is inside the shared accrual prelude.

### Likelihood Explanation
Reachable only in extreme parameter regimes: an 18-decimal token with caps lifted to near `i128` domain limits, sustained ~98% utilization on a steep curve, and accrual over many compound windows. An unprivileged attacker would need to supply/borrow whale-scale principal and the market must remain saturated for an extended period; it cannot be triggered in a single transaction. This is a Medium-severity, low-probability-but-high-impact freeze rather than an instant DoS.

### Recommendation
Use the saturating variant `mul_div_floor_saturating` (or an explicit clamp to a "max representable value" bound) in the value computations inside `accrue_step` / `calculate_supplier_rewards` and `update_supply_index` (`common/src/rates/index.rs:34`, `:80-81`), so that hitting the `i128` value ceiling behaves like the `MAX_BORROW_INDEX_RAY` cap — saturating instead of reverting. Alternatively, gate the borrow index by a value-space bound (`i128::MAX / scaled_total`) rather than a pure index bound, so the cap engages before the overflow.

### Proof of Concept
```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320
let principal = BILLION * 10i128.pow(18);            // 18-decimals token
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);  // ~98% utilization

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// errors::MATH_OVERFLOW from scaled_to_original inside accrual;
// borrow_index < MAX_BORROW_INDEX_RAY — the cap never engaged.

// Market is frozen: every verb accrues first and hits the same panic.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
