### Title
Unscoped `status` webhook (`Commit.where(sha:)`) writes CI state across every stack/repository sharing a SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository/stack scoping, then calls `create_status_from_github!` on every match. Any authenticated GitHub `status` webhook sender for an organization configured in Shipit (a repo owner, not a Shipit operator) can therefore write a fabricated CI status onto a commit belonging to a *different* repository/stack than the one that produced the event, as long as that commit's SHA also exists in Shipit's database.

### Finding Description
The broken binding: the code assumes `commit.stack.github_repo_name == payload['repository']['full_name']` for every `commit` returned by the query, but the code never checks this.

```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

The base `Handler` class already provides a repository-scoped helper, `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`), built from `payload.dig('repository', 'full_name')` [1](#0-0) , and other handlers such as `CheckSuiteHandler` use it to scope lookups. `StatusHandler` bypasses this entirely and queries `Commit` globally by `sha` [2](#0-1) .

`create_status_from_github!` mutates real CI state and cascades into deployability/merge scheduling for whichever stack the matched commit belongs to: it appends a `Status`, recomputes `status`, and can trigger `stack.schedule_merges` or `deployable_status`/`commit_status` hooks [3](#0-2) [4](#0-3) . `deployable?` directly depends on `success?`/`blocked?`, both derived from `status`/`statuses` [5](#0-4) .

Signature verification is per-organization, not per-repository: `WebhooksController#verify_signature` selects the GitHub App/secret using `repository_owner` (`params.dig('repository','owner','login')`) [6](#0-5) [7](#0-6) , and `GitHubApp#verify_webhook_signature` only checks the HMAC against that organization's shared `webhook_secret` [8](#0-7) . It performs no validation that the `sha` in the payload actually belongs to the `repository.full_name` in the same payload, and no validation restricts the query to the repository named in the payload at all — that check simply does not exist in `StatusHandler`. So even a legitimately signed, real GitHub `status` event for *repo A* (which the attacker can trigger by pushing a commit/build to a repository they control if it shares the same org/app configuration as Shipit, or by any repository whose commits get mirrored/duplicated across stacks with identical SHAs, e.g. forks, template repos, monorepo split mirrors) will be applied to *every* Shipit `Commit` row with that SHA, including ones tracked by an entirely unrelated stack/repository B.

Exploit flow:
1. Attacker controls or pushes a commit to a repository/fork whose SHA is known to also exist in another tracked stack's commit history (e.g. a shared upstream commit that got mirrored, cherry-picked, or fast-forwarded into two different Shipit-tracked repositories — a scenario the SHA-only lookup makes exploitable whenever this coincidence occurs).
2. Attacker (or GitHub, on the attacker's repo's behalf) emits a `status` webhook with `state: success` for that SHA, signed with that organization's normal webhook secret (which is legitimately obtainable for the attacker's own repo/org, not a Shipit secret).
3. `StatusHandler#process` matches `Commit.where(sha: params.sha)` across all stacks/repos and calls `create_status_from_github!` on each, forcing `success` status onto commits in the victim repository's stack.
4. Victim stack's commit becomes `deployable?` / unblocked and may trigger continuous deployment / merges it should never have received.

### Impact Explanation
This allows a payload legitimately produced for repository A to write CI/status records for repository B's stack — matching the "Critical: a payload for one repository mutating another's stack, commit" impact category. The blast radius is every Shipit-tracked stack whose commit table contains the same SHA as the attacker's own repository event, and it is fully repeatable per request (attacker can send unlimited crafted/duplicated `status` events).

### Likelihood Explanation
The precondition of two different repositories/stacks sharing a byte-identical commit SHA is not guaranteed for arbitrary attacker input (SHA-1 content-addresses the tree, so an attacker cannot pick a SHA unless the same commit content genuinely also exists in a victim's tracked repository — e.g. via forks, mirrors, shared submodules, or cherry-picked/rebased commits landing in multiple tracked repos). Given that precondition holds, the attack is trivial and repeatable: no secrets beyond the attacker's own repository's/organization's normal webhook signing are needed, and the attacker only needs to cause one real (or forged, if within the same signed org) `status` event with `state: success`.

### Recommendation
Scope `StatusHandler#process` by the reporting repository, matching the pattern already used elsewhere in the codebase (`Handler#stacks` / `Repository.from_github_repo_name`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, so a status can only affect commits belonging to the repository that produced the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook does not affect commits in unrelated repositories sharing the same SHA" do
  repo_a = shipit_repositories(:shipit)   # tracked stack A
  repo_b = create_repository(name: "other/unrelated-repo") # tracked stack B, different repo
  stack_b = create_stack(repository: repo_b)

  shared_sha = "a" * 40
  commit_a = create_commit(stack: shipit_stacks(:shipit), sha: shared_sha)
  commit_b = create_commit(stack: stack_b, sha: shared_sha)

  assert_not commit_b.reload.success?
  refute commit_b.deployable?

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => repo_a.full_name, "owner" => { "login" => repo_a.owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # BEFORE: commit_b.success? == false  /  AFTER (bug): commit_b.success? == true
  assert_not commit_b.reload.success?, "status for repo_a's payload must not mutate repo_b's commit"
end
```

This test would currently **fail** against the existing `StatusHandler#process` implementation, demonstrating the cross-repository write.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
