### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` flips `deployable?` on a default-state (`locked: false`) victim commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no repository/stack scoping, unlike every other webhook handler in the engine. Because `Commit#deployable?` is `!locked? && (...)` and commits default to `locked: false`, any attacker who legitimately controls a repository that shares a commit SHA with a victim's tracked repository (e.g., via a public fork) can send a validly-signed `status` webhook from their own repo and inject a forged `Status` row onto the victim's `Commit`, potentially flipping `deployable?` to `true`.

### Finding Description
The broken binding: `Commit.where(sha: params.sha)` is claimed to equal "commits belonging to the reporting repository," but it actually equals "every `Commit` row in the entire database with that SHA, across all stacks/repositories" [1](#0-0) . Every sibling handler (e.g. `PullRequest::OpenedHandler`, `LabeledHandler`) explicitly resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack-scoped record [2](#0-1) , but `StatusHandler` has no such scoping, and the base `Handler` class's `stacks`/`repository_name` helpers are simply unused here [3](#0-2) .

Exploit path:
1. Attacker controls (or forks) a public repository that is registered as a Shipit-tracked repo/stack under some organization `attacker-org` for which Shipit has a configured GitHub App / webhook secret (`Shipit.github(organization: repository_owner)`), so `verify_signature` in `WebhooksController` succeeds using the attacker's own legitimately-known signature [4](#0-3) .
2. That repository shares git history with the victim's tracked repository (fork relationship, mirrored/vendored history, or any scenario producing an identical commit SHA), so the same `sha` is tracked as a `Commit` row in both the attacker's stack and the victim's stack.
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org, and a payload naming that shared `sha`, `state: 'success'`, and a `context` matching a CI check the victim's stack requires.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, which matches and mutates the *victim's* `Commit` row too, since no `stack_id`/`repository` filter is applied [1](#0-0) .
5. `create_status_from_github!` calls `add_status` which recomputes `status` and can trigger `deployable_status` hooks and `stack.schedule_merges` [5](#0-4) .
6. `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [6](#0-5) . Fresh/tracked commits are not locked by any default workflow — `locked` is only ever set `true` via the explicit operator action `Commit#lock`/`lock_all` [7](#0-6) ; the test suite confirms `deployable?` is false only when explicitly locked and true otherwise once statuses are success [8](#0-7) . Therefore the `locked?` guard does not block this attack for the common case of an unlocked victim commit — the forged success status alone can satisfy `success? && !blocked?`.

Why existing guards fail: `verify_signature` correctly authenticates that the request came from the org that owns the *reporting* repository, but it says nothing about which `Commit` row the status may mutate — that authorization gap is entirely inside `StatusHandler`, which trusts `sha` as a global, tenant-agnostic key. `ExplicitParameters` only validates the shape of the payload, not authorization scope. No `stacks`/repository check gates the `Commit.where` lookup.

### Impact Explanation
A successful forged webhook writes a `Status` record onto a commit belonging to a repository/stack the attacker does not control, potentially flipping that commit's `deployable?`/`success?` state to `true`. Combined with `Commit#schedule_continuous_delivery` and `stack.schedule_merges` triggers inside `add_status`, this can enable an unauthorized deploy or merge decision for the victim stack — this is a cross-tenant record write and can lead to an unauthorized deploy, matching the Critical category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." The attack is repeatable against any commit SHA the attacker can also legitimately report through their own registered repository, and its blast radius spans every stack/repository that happens to track a shared commit history (forks, mirrors, monorepo splits).

### Likelihood Explanation
Preconditions: the attacker must already have a repository registered as a Shipit-tracked stack under an org configured in Shipit (so a valid webhook signature can be produced without secrets); the victim commit must be `locked: false` (the default); and the shared SHA condition must hold (fork of a public victim repo, or otherwise identical git object present in both repos' history). The SHA-collision-via-shared-history condition is not a cryptographic collision — it is the normal, guaranteed behavior of forked/shared git history, making this highly feasible in real-world open-source or monorepo-split setups. The attack costs one crafted, self-signed webhook POST and is fully repeatable.

### Recommendation
Scope `StatusHandler#process` to only the `Commit`s belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`, mirroring the pattern used by other handlers (`Repository.from_github_repo_name(...).stacks`), e.g. filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/commits_test.rb` and `test/controllers/webhooks_controller_test.rb`):

1. Binding check:
```ruby
test "commit is not locked by default" do
  commit = Commit.new(sha: "deadbeef", stack: shipit_stacks(:shipit))
  assert_equal false, commit.locked?
end
```

2. Exploit demonstration:
```ruby
test "status webhook from an unrelated repository flips deployable? on a victim commit sharing the same sha" do
  victim_commit = shipit_commits(:fifth) # tracked under `shipit_stacks(:shipit)`, unlocked, no successful status
  refute_predicate victim_commit, :deployable?
  assert_equal false, victim_commit.locked?

  # Attacker's own repo, registered under a different/attacker-controlled org, sends a validly signed
  # status webhook naming victim_commit.sha but with repository.full_name pointing to attacker's repo.
  request.headers['X-Github-Event'] = 'status'
  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/required-check',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  post :create, body: payload, as: :json

  victim_commit.reload
  assert_predicate victim_commit, :deployable? # forged write from an unrelated repo mutated the victim's stack state
end
```

Note: full confirmation that an attacker can obtain a validly-signed webhook for an org they do not administratively control (vs. one they self-register as a Shipit-tracked repo) depends on deployment-specific `Shipit.github_teams`/GitHub App installation configuration, which was not fully traceable in this index; the code-level authorization gap in `StatusHandler` (missing repository scoping) is confirmed directly in the source.
