## Analysis

The Polkadot SDK analog to the HAL-08 finding exists in `pallet-asset-rewards` (`substrate/frame/asset-rewards`). It implements a Synthetix-style JIT reward-per-token algorithm structurally identical to the `HaloStakeVault.sol` pattern in the report — including the same fixed-precision-multiplier division flaw, but the precision constant is even smaller (`4096` instead of `1e18`), making the bug easier to trigger. ### Title
Reward accrual permanently freezes for all stakers when `total_tokens_staked` exceeds `reward_rate_per_block * PRECISION_SCALING_FACTOR` due to integer-division truncation - (File: substrate/frame/asset-rewards/src/lib.rs)

### Summary
`pallet-asset-rewards::reward_per_token()` computes the incremental reward-per-token delta as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, using a fixed `PRECISION_SCALING_FACTOR` of `4096` (a `u16`). Any signed account can permissionlessly call the `stake` extrinsic to grow `total_tokens_staked` for a pool. Once `total_tokens_staked` exceeds `reward_rate_per_block * blocks_elapsed * 4096`, the checked integer division `ensure_div` yields exactly `0` (division truncation, not an error), so `reward_per_token_stored` stops increasing. Because this state is shared across all stakers in the pool, reward accrual silently and permanently halts for every participant, not just the account that inflated the stake — mirroring the root cause described in HAL-08 (fixed precision constant too small relative to real-world magnitudes causing `accPerShare` truncation to zero).

### Finding Description
`reward_per_token` in `substrate/frame/asset-rewards/src/lib.rs:787-810` is:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
```
`PRECISION_SCALING_FACTOR` is a pallet-wide constant fixed at `4096` [1](#0-0) , independent of the staked/reward asset decimals or magnitude, exactly the same design pattern the report criticizes (`ACC_PRECISION = 1e18` regardless of token decimals).

`ensure_div` here is a *checked* division — it only errors on division by zero, not on truncation. When the numerator (`reward_rate_per_block * blocks_elapsed * 4096`) is smaller than the denominator (`total_tokens_staked`), integer division silently returns `0`, so `reward_per_token_stored` stops advancing even though block time and configured reward rate continue to imply real rewards should accrue.

`total_tokens_staked` is fully attacker/user-controlled: any signed account can call `stake` (`pallet::call_index(1)`) with an arbitrary `amount` of the staking asset, which is added unconditionally to `pool_info.total_tokens_staked` [4](#0-3) . No privileged role is required — `stake` only requires `ensure_signed(origin)` and sufficient balance of the staked asset (which can be a low-decimal or low-value asset created via `pallet-assets` by anyone with deposit funds, or any existing asset). No admin/governance action is needed to trigger the freeze; it is purely a function of organic or attacker-driven stake growth relative to the admin-configured `reward_rate_per_block`.

Concretely, once `total_tokens_staked > reward_rate_per_block * blocks_elapsed_per_update * 4096`, the pool's reward-per-token value freezes permanently for every staker, since `reward_per_token_stored` is only ever updated through this same formula (`update_pool_and_staker_rewards` / `update_pool_rewards`), called on every `stake`, `unstake`, and `harvest_rewards` [5](#0-4) . Even if the staked amount is later withdrawn, all rewards for the period during which the division truncated are permanently lost — there's no retroactive accounting.

### Impact Explanation
This causes **irreversible freezing of rewards** for an entire pool: once the truncation condition is hit, `reward_per_token_stored` no longer increases regardless of how many reward-asset tokens the admin has deposited into the pool account via `deposit_reward_tokens`, and regardless of how long time passes. All existing and future stakers in that pool lose access to rewards they are otherwise entitled to, matching the BVSS `A:C` (availability: complete for reward accrual) characterization of the original HAL-08 finding. Because the trigger threshold is `total_tokens_staked > reward_rate_per_block * blocks_elapsed * 4096`, and `PRECISION_SCALING_FACTOR` is a small compile-time constant (not adaptive to asset decimals or reward-rate magnitude), the threshold can be reached with normal-scale staking amounts, especially for pools using low-decimal or low-valued staking assets, or pools with modest `reward_rate_per_block`.

### Likelihood Explanation
Likelihood is high for any pool where `reward_rate_per_block` is modest relative to the staking asset's typical unit magnitude, since `4096` is a very small scaling headroom (compare to `1e18` used by common Solidity patterns, which the original report already found insufficient for a legitimate use case). No privileged role, governance, or malicious node/collator is needed — a completely permissionless `stake` call by any ordinary signed account triggers it. This can happen unintentionally through organic pool growth, or be triggered opportunistically by a normal staker seeking to grief the pool or lock in a favorable share ratio before others can accrue rewards.

### Recommendation
Do not use a single fixed, compile-time `PRECISION_SCALING_FACTOR` for all pools. Either:
- Scale the precision factor based on the actual magnitudes/decimals of the staked and reward assets at pool-creation time (similar to the recommended HAL-08 fix of making the precision configurable/immutable per deployment), or
- Use a wider intermediate accumulator (e.g., perform the calculation in `U256`/`FixedU128` similar to `pallet-nomination-pools`'s `current_reward_counter`, which explicitly documents its accuracy bounds and uses `T::RewardCounter` fixed-point type rather than a fixed integer multiplier) so that truncation to zero only occurs at negligible reward magnitudes, and document/bound the minimum reward rate relative to expected stake sizes.

### Proof of Concept
Analytical PoC (arithmetic proof of the truncation condition, following the pallet's own checked-arithmetic code path):

- Pool created with `reward_rate_per_block = R` and `PRECISION_SCALING_FACTOR = 4096` (fixed).
- At any update epoch spanning `B` blocks, the pool's earned-per-token delta is:
  `delta = (R * B * 4096) / total_tokens_staked` (integer division, `ensure_div`, `lib.rs:808`).
- Choose `total_tokens_staked > R * B * 4096` (trivially achievable — e.g., `B = 1`, `R = 100`, staked asset threshold is `total_tokens_staked > 409_600` raw units, a small amount for any asset with more than a few decimals). Any signed account can reach this via one or more `stake` calls (`lib.rs:472-502`), which is a fully permissionless entry point requiring no privileged role.
- Then `delta = 0` exactly (integer division truncates, no error is raised since `ensure_div` only errors on divide-by-zero), so `reward_per_token_stored` in `update_pool_rewards` (`lib.rs:775-784`) does not increase for that epoch, and this repeats every epoch thereafter as long as the ratio condition holds — freezing rewards for the pool's stakers indefinitely, matching the described HAL-08 bug class.

This is a code-level arithmetic demonstration following the pallet's exact checked-arithmetic path (`ensure_mul`/`ensure_div`) at `substrate/frame/asset-rewards/src/lib.rs:803-809`; no test harness execution was run against a live network, and no privileged role, forged proof, or malicious authority was assumed — the entry point (`stake`) is a normal signed extrinsic available to any account.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
