### Title
Unrestricted `BridgeCommittee.initializeConfig` allows front-running to hijack the bridge's token/chain config, enabling vault fund theft - (File: `bridge/evm/contracts/BridgeCommittee.sol`)

### Summary
`BridgeCommittee.initializeConfig` is an `external` function with no access-control modifier and no `initializer` guard, mirroring the audited Holdefi `setHoldefiContract` pattern (an unrestricted setter for a critical dependency address that is wired up in a step separate from constructor/initializer). Anyone can call it first and permanently bind `BridgeCommittee.config` to an attacker-controlled contract before the legitimate deployer calls it with the real `BridgeConfig` address.

### Finding Description
`BridgeCommittee.sol` stores the trusted `BridgeConfig` reference in `config` and exposes: [1](#0-0) 

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

Unlike `initialize()` on the same contract (which uses OpenZeppelin's `initializer` modifier), `initializeConfig` has no modifier at all — no `onlyOwner`, no `initializer`, no committee-signature check. Its only guard is "not already set," identical in structure to the Holdefi bug: `holdefiContract` could be set by anyone via an unguarded `setHoldefiContract`, because the setter is decoupled from contract creation. [2](#0-1) 

The `config` value is later trusted implicitly and drives token addressing and chain support decisions in `SuiBridge`: [3](#0-2) [4](#0-3) 

Because `committee.config()` is used to resolve `tokenAddressOf(tokenID)`, `tokenSuiDecimalOf`, and `isChainSupported`/`isTokenSupported` inside `transferBridgedTokensWithSignatures` and `bridgeERC20`, whoever controls the deployed `config` contract controls which ERC20 token address the vault is instructed to pay out, and which chains/tokens are considered "supported." Deployment scripts and tests call `initializeConfig` as a step separate from `BridgeCommittee` deployment/`initialize()`: [5](#0-4) 

This split creates the same window as the Holdefi bug: between `BridgeCommittee` deployment (and its `initialize()` for committee members) and the deployer's transaction that calls `initializeConfig(realConfigAddress)`, any address can front-run with `initializeConfig(maliciousConfigAddress)`. Because of the `require(address(config) == address(0))` guard, the first caller wins permanently — the real deployer's later call reverts, and there is no recovery path since `BridgeCommittee` has no owner/admin capability to reset it.

### Impact Explanation
Once an attacker wins the race and binds `config` to a malicious `IBridgeConfig` implementation, they control:
- `tokenAddressOf(tokenID)` returned to `SuiBridge`, so `_transferTokensFromVault` will call `vault.transferERC20(attackerControlledTokenAddress, recipientAddress, amount)` — the attacker's implementation can be used to redirect calls to an arbitrary ERC20 (including the real wETH/USDT/WBTC held by the vault), or otherwise corrupt the withdrawal path.
- `isChainSupported` / `isTokenSupported`, effectively controlling deposit/withdrawal admission logic for the bridge.

Since `BridgeVault.transferERC20` and `transferETH` are gated by `onlyOwner` where the owner is expected to be `SuiBridge`, and `SuiBridge` itself trusts `committee.config()` unconditionally for token resolution, hijacking `config` is a governance-bypass primitive that can be chained into unauthorized token transfers out of the vault — a fund-theft / bridge governance bypass, matching the Critical "bridge governance or upgrade bypass that enables illegitimate mint or unlock" impact category.

### Likelihood Explanation
Exploitability depends entirely on deployment sequencing being non-atomic. `BridgeCommittee.initialize()` (committee member setup) and `initializeConfig()` (config binding) are two separate external calls, per the deploy script and test setup patterns observed in `bridge/evm/script/deploy_bridge.s.sol` and the various `*Test.t.sol` files that call `initializeConfig` as a distinct step. If these are deployed via two separate transactions (as the presence of a dedicated `initializeConfig` function combined with `initialize()` strongly implies), the window for front-running an unguarded state-setting call on a public mempool is realistic and directly analogous to the reported Holdefi pattern. I was not able to fully confirm the exact atomicity of the production deployment script from the available tool output (`deploy_bridge.s.sol` matches for `initializeConfig` were found but not read line-by-line for ordering/atomicity within a single transaction), so this should be verified before treating it as fully confirmed exploitable in production deployment — but the code-level absence of *any* access control on `initializeConfig` is a solid, reachable root-cause defect regardless of current deployment practice, and any future re-deployment, chain expansion, or config-rotation flow that calls this function separately is immediately vulnerable.

### Recommendation
- Add an `onlyOwner`/committee-authorization check to `initializeConfig`, or better, fold `config` assignment into `initialize()` (pass `_config` as a constructor/initializer parameter) so it can never be set outside contract creation — directly mirroring the recommended fix for the Holdefi bug (bind trusted addresses at creation time or gate the setter with `Ownable`).
- If a two-step deployment is required for chicken-and-egg dependency reasons, restrict `initializeConfig` to be callable only once by the deployer address recorded during `initialize()`, or require committee signatures via `verifyMessageAndSignatures`, consistent with how `updateBlocklistWithSignatures` and other privileged state changes are gated in this contract.

### Proof of Concept
1. Deployer publishes `BridgeCommittee` and calls `initialize(committee, stake, minStakeRequired)`.
2. Before the deployer's follow-up transaction calling `initializeConfig(realConfigAddress)` is mined, an attacker observes the pending transaction in the mempool and submits `initializeConfig(maliciousConfigAddress)` with higher gas, which gets mined first.
3. `require(address(config) == address(0))` passes (config still unset), so `config = IBridgeConfig(maliciousConfigAddress)` is set permanently; the deployer's later call reverts because `config` is no longer zero.
4. Deployer proceeds to deploy/initialize `SuiBridge` pointing at this `BridgeCommittee`, unaware `config` is malicious (or the bridge is deployed and this is discovered only after use).
5. Attacker's `maliciousConfigAddress` contract implements `tokenAddressOf`, `tokenSuiDecimalOf`, `isTokenSupported`, `isChainSupported`, `chainID` to return values that redirect `SuiBridge._transferTokensFromVault` into transferring the vault's real held ERC20 balances (e.g., wETH) to an attacker-chosen recipient once any valid committee-signed `transferBridgedTokensWithSignatures` message is processed, or to otherwise corrupt bridge accounting/limits enforcement.

        // transfer eth if token type is eth
