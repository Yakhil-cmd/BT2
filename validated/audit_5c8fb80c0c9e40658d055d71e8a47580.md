### Title
Webhook signature verification is keyed on `repository.owner.login`, while event processing is keyed on the independent, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) is used to validate `X-Hub-Signature` based on `params.dig('repository', 'owner', 'login')`, a field taken from the still-unauthenticated JSON body. `Handler#repository_name`, used by every event handler to locate the `Stack`/`Repository` to mutate, reads a *different* field of the same unauthenticated body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so an attacker who can produce a request that passes signature verification for *any* configured organization (in particular one whose app is configured with no `webhook_secret`, which the code explicitly special-cases) can set `full_name` to point at a stack belonging to a *different*, properly-secured organization.

### Finding Description [1](#0-0) 
`verify_signature` derives `repository_owner` and fetches the corresponding `GitHubApp`, then verifies the signature against that app's secret: [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` when no secret is configured for that organization: [3](#0-2) 

Multi-organization deployments are an officially documented configuration (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), and every example ships with `webhook_secret: # nil` as an accepted/likely value: [4](#0-3) 

Once `verify_signature` passes, `create` re-parses the same raw, attacker-controlled body and dispatches it to handlers unmodified: [5](#0-4) 

Handlers determine which repository/stack to act on using `full_name`, a completely separate key from the one used for organization/signature selection: [6](#0-5) 

Because the JSON body is parsed before (and independently of) verification, and verification is keyed off `repository.owner.login` while stack lookup is keyed off `repository.full_name`, the binding "organization that authenticated" ≠ "repository that is written" is never enforced by this engine's own code — there is no validation that `full_name`'s owner segment matches `repository.owner.login`/`organization.login`.

### Impact Explanation
This breaks the required binding "an organization that authenticated versus the repository that is written." If any organization in a Shipit multi-org deployment is configured with an empty/`nil` `webhook_secret` (a state the code explicitly documents and supports as a valid, permissive mode — e.g. for internal/low-risk orgs), an unauthenticated attacker can:
1. Send a POST to `/webhooks` with `repository.owner.login` = the org with no secret (so `verify_signature` passes unconditionally) and `organization.login` set the same way.
2. Set `repository.full_name` to `"<victim-org>/<victim-repo>"`, an actual tracked Stack belonging to a different, properly-secured organization.
3. Trigger `push`, `status`, or `check_suite` handlers against that victim stack — e.g. `PushHandler` enqueuing `GithubSyncJob` with an attacker-chosen `after` SHA, or `StatusHandler` forging a commit status — without ever proving knowledge of the victim org's real webhook secret or GitHub credentials.

This is a genuine authentication-bypass / cross-repository write: signature validation is bypassed by construction (unrelated org selection) and the write lands on an unrelated repository's state (commit sync, statuses, check runs), which can influence CI-gated deploy eligibility for the victim stack.

### Likelihood Explanation
Requires only: (a) a Shipit instance running in multi-organization webhook mode, and (b) at least one configured organization with no `webhook_secret` set (documented as a supported, and in the shipped example configs, default value). No repository write access, tokens, or GitHub credentials are needed — only network access to `POST /webhooks`. This matches the report's bug class of "a payload field acted on but never covered by the verified signature" (here, `full_name` is never actually checked against the org that was used to select/verify the signature).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the owner segment of `repository.full_name` (and/or `organization.login`) matches the `repository_owner` value that was used to select the `GitHubApp`/secret for signature verification, rejecting the request (422) on mismatch. Additionally, disallow the "no webhook secret configured" bypass (`return true unless webhook_secret`) for organizations that are used purely as a spoofing target, or require an explicit opt-in flag for unauthenticated orgs, and ensure that whichever organization is unauthenticated cannot be leveraged to act on stacks belonging to other organizations.

### Proof of Concept
Given a multi-org Shipit config where `OrgUnsecured` has `webhook_secret: nil` and `OrgVictim` has a real secret protecting stack `OrgVictim/app`:

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000

{
  "repository": {
    "owner": { "login": "OrgUnsecured" },
    "full_name": "OrgVictim/app"
  },
  "organization": { "login": "OrgUnsecured" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```

- `repository_owner` resolves to `"OrgUnsecured"` → `Shipit.github(organization: "OrgUnsecured")` has `webhook_secret == nil` → `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature`.
- `create` dispatches the same payload to `PushHandler`, which uses `payload.dig('repository', 'full_name')` = `"OrgVictim/app"` to resolve the real, protected stack and enqueues a `GithubSyncJob` for it — all without ever proving control of `OrgVictim`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
