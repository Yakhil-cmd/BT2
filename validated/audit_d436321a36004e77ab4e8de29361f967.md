### Title
CCMenu API endpoint bypasses ApiClient stack-scope restriction, allowing a token scoped to one stack to read another stack's status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces two independent checks for stack access: a permission check (`read:stack` etc.) via `require_permission`, and a scope check that restricts which `Stack` records an `ApiClient` may touch when it has a `stack_id` set, implemented in `stacks`/`stack`. `Shipit::Api::CCMenuController` overrides `stack` in a way that skips the scope check entirely, breaking the binding "the stack(s) a token authorizes" == "the stack the request actually touches."

### Finding Description
In the base controller, stack lookups are scoped to the API client's authorized stack: [1](#0-0) 

`ApiClient#stack_id` restricts the client to exactly one stack when set, as seen in the fixtures (`here_come_the_walrus` is scoped to `stack: shipit`): [2](#0-1) 

However, `CCMenuController` overrides `stack` to bypass the `stacks` scoping helper and looks up any stack directly from the request parameter: [3](#0-2) 

`require_permission :read, :stack` only checks that the client's `permissions` array contains `"read:stack"` via `ApiClient#check_permissions!`; it does not verify that the requested stack matches `current_api_client.stack_id`: [4](#0-3) 

Because `CCMenuController#stack` never calls the `stacks` (scoped) method, the stack-id restriction that every other stack-scoped API controller relies on (e.g. `TasksController`, `OutputsController`, both of which call `stack.tasks.find(...)` off of the scoped `stack`) is silently skipped for this one endpoint: [5](#0-4) [6](#0-5) 

The binding broken is: **stack a token authorizes (`current_api_client.stack_id`) vs. stack a request actually touches (`params[:stack_id]` resolved unscoped)**. Any client holding a valid `read:stack`-permission token that is scoped to Stack A can supply Stack B's id in the URL and receive Stack B's CCMenu status — before the fix this returns Stack A only; after (i.e., in the current/vulnerable code) it returns whichever stack is requested.

### Impact Explanation
An attacker (or a legitimately-issued, narrowly-scoped `ApiClient`, e.g. one created via `CCMenuUrlController` for a single stack as shown in `ccmenu_url_controller.rb`) can use their limited, stack-scoped token to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock status) of any other stack in the Shipit instance, not just the one the token creator intended: [7](#0-6) 

This matches the "High" impact tier: unauthenticated (out-of-scope) read of stack state via a token that should be confined to a single stack. It does not grant write/deploy access, but it does cross the authorization boundary the `stack_id` scoping mechanism is meant to enforce.

### Likelihood Explanation
Likelihood is high for any holder of a stack-scoped `ApiClient` token (these are routinely handed out per-stack for CI dashboard integration via `CCMenuUrlController`). No special privilege beyond possessing one legitimately-scoped token is required — the attacker only needs to change the `stack_id` path segment in the CCMenu URL to a different stack's identifier.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the same scoped lookup as the base controller (i.e., resolve through `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so a client's `stack_id` restriction is honored consistently across all API controllers.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id` = Stack A, with `read:stack` permission (as `CCMenuUrlController#client` does).
2. Send `GET /api/stacks/:owner/:repo_A/:env/ccmenu` with that token — succeeds, returns Stack A's status (expected).
3. Send `GET /api/stacks/:owner/:repo_B/:env/ccmenu` (a different, unrelated stack) using the same token.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than the scoped `stacks.from_param!`, the request succeeds and returns Stack B's build status, even though the token was only authorized for Stack A.
