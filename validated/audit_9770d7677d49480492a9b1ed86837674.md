### Title
Unbounded, unbatched full-network stake-delegation scan at epoch boundary can stall epoch processing - (File: `runtime/src/stakes.rs`, `runtime/src/bank.rs`)

### Summary
The BMX report describes `Voter::_processPendingRemovals()` iterating an attacker-inflatable list *without* a batch bound, unlike the batched `Voter::finalize()` design, letting cheap/refundable registrations blow up gas at epoch finalization. Agave has an analogous asymmetry: partitioned reward *distribution* is explicitly batched (`partitioned_rewards_stake_account_stores_per_block`, `MAX_PARTITIONED_REWARDS_PER_BLOCK`), but the reward *calculation*/stake-activation phase that runs once, synchronously, on the epoch-boundary bank is not batched — it walks the entire `stake_delegations` map for the whole cluster in one call.

### Finding Description
`Bank::process_new_epoch()` calls `compute_new_epoch_caches_and_rewards()`, which collects **every** stake delegation in the cluster into a `Vec` via `stakes.stake_delegations_vec()` [1](#0-0)  and then calls `Stakes::calculate_activated_stake()`, which does a `par_iter().fold()/reduce()` over the **entire** `stake_delegations` slice to build the new `StakeHistory` entry and refreshed `VoteAccounts`/`DelegatedStakes` [2](#0-1) . `refresh_vote_accounts()` similarly iterates the full delegation set unconditionally [3](#0-2) .

Unlike the partitioned-rewards *distribution* path, which is deliberately chunked across up to 10% of an epoch's slots via `get_reward_distribution_num_blocks()` and `partitioned_rewards_stake_account_stores_per_block()` specifically to bound per-block work [4](#0-3) , and unlike vote-account admission which is explicitly capped/filtered to `MAX_ALPENGLOW_VOTE_ACCOUNTS` with a minimum-balance floor via `clone_and_filter_for_vat()` to prevent cheap spam [5](#0-4) , there is **no analogous cap or batching** on the number of stake delegations processed by `calculate_activated_stake()`/`refresh_vote_accounts()` at the epoch boundary. This work must complete synchronously inside `process_new_epoch()` before the epoch-boundary bank can be considered processed [6](#0-5) .

Stake accounts are cheap to create (rent-exempt minimum only, fully refundable on withdrawal) and are not subject to the same VAT-style economic filter applied to vote accounts. An attacker can therefore create an arbitrarily large number of low-value delegated stake accounts across many transactions/blocks over time (each individually bounded by normal per-transaction compute limits, so no single instruction handler is DoS'd), and have them all be swept unconditionally into the single, unbatched `stake_delegations_vec()`/`calculate_activated_stake()` computation that runs once per epoch boundary.

### Impact Explanation
If the number of stake delegations grows large enough, the epoch-boundary computation (single synchronous call, run once per epoch on every validator) could take long enough to threaten the validator's ability to produce/replay the epoch-boundary block within its slot budget, unlike the reward-distribution phase which was deliberately partitioned to avoid exactly this class of problem. This is an "epoch-boundary halt"-class concern per the rules: a per-epoch cost that scales with attacker-controlled state size and is not amortized/batched the way the analogous reward-distribution logic is.

### Likelihood Explanation
Confidence is limited. The `calculate_activated_stake`/`refresh_vote_accounts` work is parallelized with a `ThreadPool` across cores rather than run in a single sequential loop, so its practical cost-per-account is much lower than a naive loop (unlike the Solidity `for` loop in the BMX bug that runs on a single EVM thread against a hard gas limit). There is no on-chain gas ceiling analog in this off-chain scan, so the realistic failure mode is degraded performance/slower epoch transitions rather than a hard revert/OOG failure as in the Solidity case. I could not confirm from the available index whether there is an existing global cap on stake-account count/delegation count (e.g., via minimum delegation amount `get_minimum_delegation`, found referenced in `runtime/src/stake_utils.rs` and `feature-set/src/lib.rs` but whose enforcement point I was not able to fully verify with the tools available) that already bounds this attack's practical scale. This uncertainty and the fact that this requires an extremely large number of accounts (a scale attack, not a cheap single-call trigger like the original bug) makes this a much weaker and less certain analog than the original report.

### Recommendation
- Verify/confirm whether `get_minimum_delegation` and rent-exemption requirements impose an effective economic floor that bounds the practical number of stake accounts an attacker can create cheaply.
- Consider whether `calculate_activated_stake()`/`refresh_vote_accounts()` should be chunked/incrementalized in the same spirit as the partitioned-rewards distribution path, or whether existing parallelism and account-count limits already provide sufficient bounding — this needs a deeper, code-verified investigation (e.g., benchmarking with a large synthetic delegation set) beyond what static code search can confirm here.
- Given the significant uncertainty about real-world exploitability (parallelized workload, unclear existing economic bound, no hard revert semantics), this should be treated as a lower-confidence, scale-dependent performance concern rather than a confirmed critical vulnerability.

### Proof of Concept
Not constructed — this analog requires empirically demonstrating that a sufficiently large stake-delegation count causes `process_new_epoch()`'s epoch-boundary computation to exceed the slot/epoch-transition time budget on real hardware, which cannot be verified through static code search alone.

    pub(crate) fn calculate_activated_stake(
        &self,
        next_epoch: Epoch,
        thread_pool: &ThreadPool,
        new_rate_activation_epoch: Option<Epoch>,
        stake_delegations: &[(&Pubkey, &StakeAccount)],
        use_fixed_point_stake_math: bool,
    ) -> (
        StakeHistory,
        VoteAccounts,
        DelegatedStakes,
        RewardEpochDelegatedStakes,
    ) {
        // Wrap up the prev epoch by adding new stake history entry for the
        // prev epoch.
        let (stake_history_entry, effective_delegated_stakes) = thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .fold(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(acc, mut delegated_stakes), (_stake_pubkey, stake_account)| {
                        let delegation = stake_account.delegation();
                        let activation_status = delegation_activation_status(
                            delegation,
                            self.epoch,
                            &self.stake_history,
                            new_rate_activation_epoch,
                            use_fixed_point_stake_math,
                        );
                        *delegated_stakes.entry(delegation.voter_pubkey).or_default() +=
                            activation_status.effective;
                        (acc + activation_status, delegated_stakes)
                    },
                )
                .reduce(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(activation_status_a, delegated_stakes_a),
                     (activation_status_b, delegated_stakes_b)| {
                        (
                            activation_status_a + activation_status_b,
                            merge_delegated_stakes(delegated_stakes_a, delegated_stakes_b),
                        )
                    },
                )
        });
        let mut stake_history = self.stake_history.clone();
        stake_history.add(self.epoch, stake_history_entry);
        // Refresh the stake distribution of vote accounts for the next epoch,
        // using new stake history.
        let (vote_accounts, delegated_stakes) = refresh_vote_accounts(
            thread_pool,
            next_epoch,
            &self.vote_accounts,
            stake_delegations,
            &stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        let reward_epoch_delegated_stakes = RewardEpochDelegatedStakes {
            epoch: self.epoch,
            delegated_stakes: effective_delegated_stakes,
        };
        (
            stake_history,
            vote_accounts,
            delegated_stakes,
            reward_epoch_delegated_stakes,
        )
    }

fn refresh_vote_accounts(
    thread_pool: &ThreadPool,
    epoch: Epoch,
    vote_accounts: &VoteAccounts,
    stake_delegations: &[(&Pubkey, &StakeAccount)],
    stake_history: &StakeHistory,
    new_rate_activation_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> (VoteAccounts, DelegatedStakes) {
    fn merge(mut stakes: DelegatedStakes, other: DelegatedStakes) -> DelegatedStakes {
        if stakes.len() < other.len() {
            return merge(other, stakes);
        }
        for (pubkey, stake) in other {
            *stakes.entry(pubkey).or_default() += stake;
        }
        stakes
    }
    let delegated_stakes = thread_pool.install(|| {
        stake_delegations
            .par_iter()
            .fold(
                DelegatedStakes::default,
                |mut delegated_stakes, (_stake_pubkey, stake_account)| {
                    let delegation = stake_account.delegation();
                    let stake = delegation_effective_stake(
                        delegation,
                        epoch,
                        stake_history,
                        new_rate_activation_epoch,
                        use_fixed_point_stake_math,
                    );
                    if stake != 0 {
                        *delegated_stakes.entry(delegation.voter_pubkey).or_default() += stake;
                    }
                    delegated_stakes
                },
            )
            .reduce(DelegatedStakes::default, merge)
    });
    let vote_accounts = vote_accounts
        .iter()
        .map(|(&vote_pubkey, vote_account)| {
            let delegated_stake = delegated_stakes
                .get(&vote_pubkey)
                .copied()
                .unwrap_or_default();
            (vote_pubkey, (delegated_stake, vote_account.clone()))
        })
        .collect();
    (vote_accounts, delegated_stakes)
}

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
