### Title
Multisig transaction execution payload is not required to match the owner-approved payload when `abort_if_multisig_payload_mismatch_enabled` is disabled - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction`, the function the VM invokes as the authoritative prologue/admission check for multisig transactions [1](#0-0) , only verifies that the payload being executed matches what owners approved in two gated code paths: (1) when the transaction was created with a payload *hash* (`payload_hash.is_some()`), or (2) when the transaction was created with a full payload **and** the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on [2](#0-1) . If the flag is off, an owner who obtains quorum approvals for one stored payload can execute a *different*, self-chosen payload under the multisig account's signer, because the mismatch check that is supposed to bind the executed payload to the approved one is entirely skipped.

### Finding Description
`validate_multisig_transaction` is documented as being "called by the VM as part of transaction prologue, which is invoked during mempool transaction validation and as the first step of transaction execution" [3](#0-2) . Its purpose is to serve as the admission boundary that ensures execution only proceeds if the exact payload agreed upon by the owners is the one being executed.

The prologue computes `num_approvals`/quorum for `sequence_number` from the votes recorded against the *stored* `MultisigTransaction` [4](#0-3) , then is supposed to bind the caller's actually-submitted `payload` bytes to that same approved transaction:

```
if (transaction.payload_hash.is_some()) {
    assert!(sha3_256(payload) == *payload_hash, ...);
};

if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    assert!(payload == *stored_payload, ...);
}
``` [2](#0-1) 

The `payload` argument passed into this function is not an arbitrary auxiliary value — it is derived directly from the caller's own submitted `SignedTransaction` executable (`bcs::to_bytes(&MultisigTransactionPayload::EntryFunction(entry_function.clone()))`), i.e., the code that will actually run, as constructed in `run_multisig_prologue` [5](#0-4)  and reused identically in `execute_multisig_transaction` to fetch `GET_NEXT_TRANSACTION_PAYLOAD` [6](#0-5) .

When a multisig transaction is created via `create_transaction` (full payload stored on chain, so `payload_hash` is `None`) [7](#0-6) , the *only* mechanism preventing the executor from substituting a different payload is the second, feature-flag-gated `assert!`. If `abort_if_multisig_payload_mismatch_enabled` is disabled, that assertion never runs, so:
- Approvals collected by owners for payload A (`transaction.payload`) are used to authorize execution.
- The executor submits a transaction whose own executable is payload B (any entry function/args of their choosing).
- `validate_multisig_transaction` never compares A and B — it passes.

This is structurally analogous to the external report's root cause: a value computed under one assumption (validator balance transitions attributable to one withdrawal event; here, owner approvals attributable to one specific approved payload) is reused for a different, unprivileged-party-controlled event (a deposit that manipulates the balance signal; here, a different payload substituted at execution time) because the binding/verification step that should tie the two together is conditionally skipped.

**Uncertainty:** I was not able to retrieve and fully inspect the body of `get_next_transaction_payload` (the function invoked via `GET_NEXT_TRANSACTION_PAYLOAD` in `execute_multisig_transaction`) before running out of tool iterations, so I cannot 100% confirm whether it independently re-derives/enforces the match when the flag is off, or whether it simply returns whichever of `provided_payload`/`stored_payload` is non-empty (which the parallel structure and comments strongly suggest). I also could not confirm the current default/rollout state of the `abort_if_multisig_payload_mismatch_enabled` feature flag on mainnet. These two points should be verified before treating this as a confirmed, currently-exploitable issue versus a defense-in-depth gap that may already be mitigated by `get_next_transaction_payload`'s own logic or by the flag being enabled everywhere.

### Impact Explanation
If the flag is disabled and `get_next_transaction_payload` does not independently enforce the match, an account owner (which is an "unprivileged" role relative to the multisig account's collective authority) can execute arbitrary entry functions as the multisig account signer using approvals that were never given for that specific action — an unauthorized transaction execution under the wrong approval/signer set, directly matching the "Authenticator/multisig approval validation accepting the wrong approval set" and "pre-validation mismatch causing an unapproved transaction to execute and commit" impact categories. Given multisig accounts commonly control significant treasury or governance authority, this would be High/Critical impact if confirmed exploitable.

### Likelihood Explanation
Likelihood is contingent entirely on unverified facts: (1) the default/current state of the `abort_if_multisig_payload_mismatch_enabled` feature flag, and (2) whether `get_next_transaction_payload` performs an independent, unconditional check. If the flag is enabled by default in current releases, or if `get_next_transaction_payload` always falls back to the stored payload when one exists (regardless of a non-matching `provided_payload`), this issue would not be exploitable in practice. Given the code explicitly guards the check behind a feature flag (implying it was rolled out gradually and may have been off in some historical or environment-specific deployment), and the surrounding code comments ("If the transaction payload is stored on chain and there is a provided payload, verify that the provided payload matches the stored payload") clearly indicate the intended invariant, this is presented as a plausible but not fully confirmed local root cause.

### Recommendation
- Verify the current/default value of `abort_if_multisig_payload_mismatch_enabled` across all deployed networks; if it can be off anywhere reachable, treat this as an active issue.
- Inspect `get_next_transaction_payload` to confirm whether it independently enforces payload matching or if it trusts the `provided_payload` argument by default when `transaction.payload` is stored on-chain.
- Regardless of the above, make the payload-match assertion in `validate_multisig_transaction` unconditional (not feature-flag gated) whenever `transaction.payload.is_some()`, so the prologue itself is the single source of truth and cannot silently authorize execution of an unapproved payload.

### Proof of Concept
Could not be fully constructed/verified within the available tool budget because the exact runtime behavior of `get_next_transaction_payload` (whether it also skips the mismatch check) was not confirmed. Conceptually: (1) owner A creates a multisig transaction via `create_transaction` with payload P1 (e.g., harmless transfer); (2) sufficient owners approve sequence number N for P1; (3) with `abort_if_multisig_payload_mismatch_enabled` disabled, the executing owner submits a `Multisig` `SignedTransaction` for sequence N whose embedded `EntryFunction` is P2 (e.g., a privileged/harmful call); (4) if `get_next_transaction_payload` returns/executes P2 instead of enforcing P1, `validate_multisig_transaction`'s missing match check allows P2 to execute under the multisig account's authority using approvals gathered only for P1.
