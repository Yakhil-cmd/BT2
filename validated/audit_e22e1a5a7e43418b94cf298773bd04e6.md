### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` updates every `Commit` record in the entire database that matches a given `sha`, regardless of which repository the verified webhook came from, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which correctly scope via `Repository.from_github_repo_name(payload.repository.full_name).stacks`. A single verified `status` webhook for a SHA shared across repositories (e.g., a colliding/duplicated commit, or a repo's commit that was forked/mirrored into another Shipit-tracked repo with the same history) writes a `Status` row to commits belonging to unrelated Stacks/repositories.

### Finding Description
The claimed binding is: `commits mutated by one verified status payload == commits belonging to the Stack of the payload's own repository`. Tracing the code shows this is false: `StatusHandler.process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0)  with no reference to `payload.dig('repository', 'full_name')` or `stacks` at all, whereas the base `Handler#stacks` helper exists precisely to scope queries to the repository that sent the webhook [4](#0-3) , and is used correctly by `PushHandler#process` [3](#0-2)  and `CheckSuiteHandler#process` (`stacks.where(branch: params.check_suite.head_branch)`).

`WebhooksController#verify_signature` only authenticates that the raw body's HMAC matches the `webhook_secret` configured for the organization named in `params.dig('repository','owner','login')` [5](#0-4) ; it never checks that the `Commit` rows the handler subsequently mutates actually belong to that same repository/organization. This is an org-level signature check, not a per-commit/per-repository authorization check, so it does not prevent `StatusHandler` from reaching across tenant boundaries once the org-level signature passes.

**Exploit flow**: An attacker who can get GitHub to deliver a genuinely-signed `status` webhook for *any* repository under an organization Shipit is configured for (e.g., they push to a branch/PR in a repo they control within that org, and CI posts a status) can craft the `sha` value to collide with a commit sha already tracked by an *unrelated* Stack in the same Shipit instance (git SHA-1 collisions of tracked history are plausible via cherry-picks, rebases, or reused initial commits across repos/forks). Since `StatusHandler` never filters by `payload.repository.full_name`, `commit.create_status_from_github!(params)` runs for every matching `Commit` row across all Stacks, writing an attacker-controlled `state`/`description`/`target_url` Status onto commits in Stacks the attacker's payload never authenticated against.

### Impact Explanation
This is a payload for one repository mutating another repository's `Commit`/`Status` records — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). A forged `success` status on an unrelated Stack's commit can unblock deploy gating logic that depends on `required_statuses`/`commit.state` (`Shipit::Commit#state`), potentially enabling an unauthorized deploy for a tenant the attacker never had signature-verified access to. The blast radius scales with however many Stacks/commits share the given `sha` in the shared database, and this is repeatable on every occurring sha collision without additional privileges.

### Likelihood Explanation
Exploitation requires: (1) the attacker's own repository to belong to an organization already configured in Shipit's `secrets.github` map (so `verify_signature` succeeds using that org's `webhook_secret`), and (2) a `sha` collision between a commit reachable by that org's CI and a commit tracked in a different Stack. Real SHA-1 collisions for arbitrary content are impractical to engineer directly, but identical commits across repositories/forks/mirrors (shared history, cherry-picked commits, or squash-merged upstream commits landing in multiple downstream forks each with their own Shipit Stack) are common in practice and require no cryptographic attack — just naturally shared commit objects. The attacker cost is a normal CI status push from a repo they legitimately control; no secrets, sessions, or elevated GitHub roles are needed.

### Recommendation
Scope `StatusHandler#process` to the payload's own repository, matching `PushHandler`/`CheckSuiteHandler`: replace `Commit.where(sha: params.sha)` with `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }` (or `Commit.where(sha: params.sha, stack: stacks)`), using the inherited `stacks` helper so only commits belonging to Stacks under the webhook's authenticated repository are updated.
