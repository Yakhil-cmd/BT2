The vulnerability exists in the comment/reference pagination loops reachable from `viewRun` (called by `NewCmdView`), not in `NewCmdView` itself.

### Title
Unbounded GraphQL pagination loop in issue comment/reference preloading allows resource-exhaustion DoS - (File: pkg/cmd/issue/view/http.go)

### Summary
`NewCmdView` in `pkg/cmd/issue/view/view.go` calls `viewRun`, which invokes `preloadIssueComments` and `preloadClosedByPullRequestsReferences` in `pkg/cmd/issue/view/http.go` whenever the initial GraphQL response indicates `hasNextPage: true`. Both functions loop `for {}` on the `pageInfo.hasNextPage`/`endCursor` fields returned by the server with no maximum page/iteration cap, so a malicious or compromised GraphQL endpoint can force `gh issue view` into unbounded requests and unbounded memory growth.

### Finding Description
`viewRun` ( [1](#0-0) ) calls `preloadIssueComments` and `preloadClosedByPullRequestsReferences` whenever the corresponding lookup field is requested and the issue's initial `PageInfo.HasNextPage` is true.

Both functions in `pkg/cmd/issue/view/http.go` implement cursor-based pagination with an unbounded loop: [2](#0-1) [3](#0-2) 

Each iteration:
1. Sends a GraphQL query using the `endCursor` returned by the *previous* server response.
2. Appends `comments.Nodes`/`ClosedByPullRequestsReferences.Nodes` to the in-memory `issue` object, unbounded.
3. Continues looping as long as the server-controlled `PageInfo.HasNextPage` is `true`.

There is no maximum iteration counter, no maximum node count, and no context/deadline applied to bound this loop — the only exit condition is a `false` `hasNextPage` value or a hard error from `gql.Query`. Since `hasNextPage`/`endCursor` are fields fully controlled by whatever GraphQL endpoint the victim's `gh` is configured against (e.g., a GitHub Enterprise Server host the victim points `gh --hostname` at, per the threat model's "controls responses from a host the victim points gh at"), a malicious host can respond indefinitely with `hasNextPage: true` and a fresh (or even repeating) `endCursor`, causing `gh issue view` to loop forever, issuing unbounded network requests and growing `issue.Comments.Nodes` / `issue.ClosedByPullRequestsReferences.Nodes` without bound — unbounded memory and CPU/network consumption on the victim's machine.

Unlike `pkg/cmd/api/api.go`'s pagination (bounded by `opts.Paginate` flag semantics and page-count driven by `Link` headers that terminate naturally when omitted) or the attestation/codespaces API clients that wrap retries with `backoff.WithMaxRetries(bo, 3)` (see `pkg/cmd/attestation/api/client.go:150-186`, `internal/codespaces/api/api.go:1299-1310`), these two GraphQL comment/reference pagination loops have no such cap.

### Impact Explanation
A single crafted server response sequence (from a malicious/compromised GitHub Enterprise host the victim has configured `gh` against) can force `gh issue view` to loop indefinitely, consuming unbounded memory (accumulating comment/reference nodes) and making unbounded outbound HTTP requests, hanging the CLI process. This matches "High - Unbounded resource consumption on the victim's machine from a single attacker-served response" since neither loop enforces any explicit retry/page counter as required by the stated invariant.

### Likelihood Explanation
Exploitability requires the victim to run `gh issue view` (with `--comments` or default field set including `comments`/`closedByPullRequestsReferences`) against a host under attacker control, or an issue with more than 100 comments/references hosted where the response pipeline can be manipulated (e.g. compromised/malicious enterprise server, or a proxy/MITM-adjacent scenario already accepted under "controls responses from a host the victim points gh at"). This is deterministic and trivially repeatable — the attacker only needs to keep returning `hasNextPage: true`.

### Recommendation
Add an explicit maximum page/iteration bound (and optionally a maximum accumulated node count) to both `preloadIssueComments` and `preloadClosedByPullRequestsReferences` loops in `pkg/cmd/issue/view/http.go`, e.g. capping at a fixed number of pages (matching GitHub's practical node limits) and returning an error or truncating gracefully if exceeded, consistent with the bounded-retry pattern already used elsewhere in the codebase (`backoff.WithMaxRetries`).

### Proof of Concept
Go test using `httpmock.Registry` registered against `gql.Query`'s GraphQL endpoint:
```go
func TestPreloadIssueComments_UnboundedPagination(t *testing.T) {
    reg := &httpmock.Registry{}
    defer reg.Verify(t)

    // Always respond with hasNextPage: true and a new cursor, simulating
    // an attacker-controlled/malicious GraphQL host.
    callCount := 0
    reg.Register(httpmock.GraphQL(`CommentsForIssue`), httpmock.GraphQLQuery(`
        {"data":{"node":{"__typename":"Issue","comments":{
            "nodes":[{"id":"c"}],
            "pageInfo":{"hasNextPage":true,"endCursor":"CURSOR"}
        }}}}`, func(_ string, _ map[string]interface{}) {
        callCount++
    }))

    client := &http.Client{Transport: reg}
    issue := &api.Issue{
        ID: "ISSUE_ID",
        Comments: api.Comments{
            PageInfo: api.PageInfo{HasNextPage: true, EndCursor: "start"},
        },
    }

    done := make(chan error, 1)
    go func() { done <- preloadIssueComments(client, someRepo, issue) }()

    select {
    case <-done:
        t.Fatalf("expected preloadIssueComments to hang/loop, but it returned after %d calls", callCount)
    case <-time.After(2 * time.Second):
        // Expected: the loop never terminates and callCount keeps growing unbounded.
        t.Logf("preloadIssueComments made %d requests before test timeout; no bound enforced", callCount)
    }
}
```
Expected assertion for a fix: the loop should terminate after a bounded number of requests (e.g. asserting `callCount <= N` for some fixed `N`), which currently fails.
