### Title
CCMenuController ignores an ApiClient's `stack_id` scope, letting a stack-scoped token read any other stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via `stack_id`, and every other API controller enforces that scope through `Api::BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` to bypass this scoping entirely, so a token that is only supposed to see one stack can be used to read the CCMenu (build/deploy) status of *any* stack in the installation.

### Finding Description
`Api::BaseController` defines the scoping contract that every other API resource controller relies on: [1](#0-0) 

`ApiClient#stack_id` is an optional column, and the engine explicitly supports and tests "stack-scoped" clients that should only ever see their own stack, e.g. `"an api client scoped to a stack will only see that one stack"`: [2](#0-1) 

`ApiClient` itself only checks permission *names* (`read:stack`, `write:stack`, …), never which stack the caller is bound to — the stack binding is enforced solely by the `stacks`/`stack` helper in `BaseController`: [3](#0-2) 

`Api::CCMenuController`, however, redefines `stack` to look the record up directly by URL parameter instead of going through the scoped `stacks` collection: [4](#0-3) 

Because `require_permission :read, :stack` only calls `ApiClient#check_permissions!`, and `stack` no longer filters by `current_api_client.stack_id`, any token carrying `read:stack` — including one deliberately created with a `stack_id` restriction — can fetch the CCMenu XML (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) for a stack it was never authorized for, simply by changing the `stack_id` route parameter.

This is the same class of bug as the reported Tempus finding: a value the authorization layer is supposed to bind together (token → authorized stack) is checked in one place (`BaseController#stack`) but a sibling code path (`CCMenuController#stack`) silently acts on a different, unchecked value (any `stack_id` in the request), breaking the equality `token.authorized_stack == stack_acted_on`.

### Impact Explanation
This crosses a real authorization boundary inside the engine's own code (no GitHub credentials, private keys, or webhook secrets involved). A token intentionally minted with a narrow `stack_id` scope — the mechanism the engine provides specifically so a client can be handed a token limited to one stack — instead grants read access to the state (build/deploy status, lock reason, web URL) of every other stack in the Shipit instance. This matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output" relative to the token's granted scope, since the token holder is unauthorized for any stack outside its `stack_id`.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` API token (a normal, low-privilege, shareable credential — CCMenu URLs are explicitly designed to be embedded in third-party CI dashboards) can trigger this by simply substituting a different `stack_id` in the `GET /api/stacks/:stack_id/ccmenu` URL. No elevated permission, write access, or secret material beyond the token itself is required, and the token is exactly the kind of narrowly-scoped credential the feature is meant to safely distribute.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so the `current_api_client.stack_id` restriction is enforced consistently across all API controllers.

### Proof of Concept
1. An operator issues an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to Stack A's id (the officially supported "scoped client" pattern, see `test/controllers/api/stacks_controller_test.rb:217-223`).
2. That token is embedded in a CCMenu URL and shared (this is exactly how `CCMenuUrlController` distributes tokens).
3. Instead of `GET /api/stacks/<A>/ccmenu?token=<token>`, the caller requests `GET /api/stacks/<B>/ccmenu?token=<token>` for an unrelated Stack B.
4. `authenticate_api_client` authenticates the token; `require_permission :read, :stack` passes because the token has `read:stack`; `stack` resolves to Stack B via `Stack.from_param!(params[:stack_id])`, bypassing the `stack_id` restriction that `BaseController#stacks` would have enforced.
5. The response renders Stack B's CCMenu project XML (build/lock/deploy status), which the token was never authorized to see.
