### Title
`OpenedHandler#provision?` bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` repositories - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` intends the binding `repository.review_stacks_enabled == true` to gate all provisioning behaviors, but Ruby operator precedence (`&&` binds tighter than `||`) only ANDs `review_stacks_enabled` with the `allow_all` branch. For repositories with `review_stacks_enabled == false` and `provisioning_behavior == 'allow_with_label'` (or `prevent_with_label`), an attacker-controlled label makes `provision?` return `true`, causing `ReviewStackAdapter#find_or_create!` to provision (and enqueue) a review stack that the operator explicitly disabled.

### Finding Description
The claimed/broken binding: `repository.review_stacks_enabled == true` should be required (`&&`) for every branch of `provisioning_behavior`, but in the code it is only associated with the first disjunct: [1](#0-0) 

Due to Ruby precedence, this parses as:
`(review_stacks_enabled && provisioning_behavior_allow_all?) || (provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`

So when `review_stacks_enabled == false` and `provisioning_behavior_allow_with_label? == true`, adding the provisioning label (`repository.provisioning_label_name`, checked via `pull_request_has_provisioning_label?` at [2](#0-1) ) makes the second disjunct true regardless of `review_stacks_enabled`. `respond_to_pull_request_opened?` then returns true and `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates a `ReviewStack` record, a `PullRequest` record, and enqueues `ReviewStackProvisioningQueue`, ultimately provisioning infrastructure ( [3](#0-2)  and [4](#0-3) ).

The attacker's exact action: open a PR against a repo where the operator set `review_stacks_enabled = false` and `provisioning_behavior = 'allow_with_label'`, and self-apply the label matching `repository.provisioning_label_name` (any PR author can label their own PR). No maintainer approval, session, or secret is required for this action — GitHub allows PR authors to label their own PRs in many configurations, and the webhook itself is verified by GitHub's own signature mechanism upstream of this handler (out of scope for this bug, but doesn't prevent the logic flaw once a legitimate webhook fires for an actual label/PR event).

For comparison, the sibling `LabeledHandler` correctly ANDs `review_stacks_enabled` across the entire behavior decision at the top-level `respond_to_label_change?` before delegating to `archive?`/`unarchive?`: [5](#0-4) , confirming that `OpenedHandler#provision?` diverges from the intended gating pattern used elsewhere in the codebase.

No other guard intercepts this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?` [6](#0-5) ; there is no repository-level check elsewhere in `process` or `ReviewStackAdapter` that re-validates `review_stacks_enabled` before creating the stack.

### Impact Explanation
An unprivileged PR author can force provisioning of a review stack (with associated infrastructure/task execution against the repository's review-stack scope) on a repository whose operator explicitly disabled review stacks (`review_stacks_enabled = false`). This is a cross-configuration authorization bypass: a security control (disabling review-stack provisioning) is silently ignored for two of the three `provisioning_behavior` settings. This can cause unwanted task/deploy-adjacent execution and resource creation for a repository, matching the "unauthorized deploy/task execution" Critical impact category since it results in the app taking an infrastructure-provisioning action for a repo the operator configured to prevent it. Repeatable on every PR the attacker opens/labels against any repository with this specific combination.

### Likelihood Explanation
Requires exact configuration: `review_stacks_enabled == false` AND `provisioning_behavior` in `{allow_with_label, prevent_with_label}`. Given this configuration, the attacker cost is trivial — open a PR and add/have a label present. No secrets, tokens, or elevated GitHub permissions are needed since labeling one's own PR is often permitted. Likelihood is moderate-to-high wherever this configuration combination exists, and it is fully repeatable.

### Recommendation
Fix operator precedence in `provision?` to bind `review_stacks_enabled` across the entire expression, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same audit to `ReopenedHandler`, which contains the identical pattern ( [7](#0-6) ).

### Proof of Concept
Minitest plan (Mocha), under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` pattern:
```ruby
test "provision? returns false and no ReviewStack is created when review_stacks_enabled is false, even with provisioning_behavior allow_with_label and matching label" do
  repository = stub(
    review_stacks_enabled: false,
    provisioning_behavior_allow_all?: false,
    provisioning_behavior_allow_with_label?: true,
    provisioning_behavior_prevent_with_label?: false,
    provisioning_label_name: "deploy-preview",
    review_stacks: Shipit::ReviewStack.none
  )
  Shipit::Repository.stubs(:from_github_repo_name).returns(repository)

  params = build_opened_params(action: "opened", labels: [{ "name" => "deploy-preview" }])
  handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params)

  Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.any_instance.expects(:find_or_create!).never

  handler.process
  # Assert equality: repository.review_stacks_enabled (false) must equal
  # the actual gating effect on provision? (currently true due to bug) -- this test should fail pre-fix.
end
```
This demonstrates that with `review_stacks_enabled: false`, `find_or_create!` is nonetheless invoked, proving the binding `review_stacks_enabled == true` is not enforced for the `allow_with_label`/`prevent_with_label` branches.
