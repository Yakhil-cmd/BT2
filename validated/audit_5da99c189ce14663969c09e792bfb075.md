### Title
Attacker-spoofable `StackStxOp.sender` via unbound `PreStxOp.output` lets attacker lock victim STX while diverting rewards to attacker's `reward_addr`/`signer_key` - (File: `stackslib/src/chainstate/burn/operations/stack_stx.rs`)

### Summary
`PreStxOp::parse_from_tx` sets `output` to whatever address appears in the first output of the burnchain transaction with no requirement that the transaction's Bitcoin input-signer controls that output address. `StackStxOp` inherits this attacker-chosen address as its `sender`, and the Clarity `stack-stx` call in `pox-4.clar` is then executed with `tx-sender` bound to this unauthenticated value, locking the named account's real STX balance while the reward slot and signer key are entirely attacker-controlled.

### Finding Description
The broken equality: **"STX locked == STX committed by its owner"** and **"reward slot/weight assigned == value actually locked by its true owner."**

Trace:
1. `PreStxOp::parse_from_tx` (`stackslib/src/chainstate/burn/operations/stack_stx.rs:74-144`) derives `output` purely from `outputs.get(0)` of the Bitcoin transaction — there is no check binding that output address to the transaction's own signer/input key. Any Bitcoin holder can create a `PreStxOp` naming an arbitrary victim Stacks address as `output`, funding it entirely from their own UTXOs, while output[1] (the "change") remains fully attacker-controlled.
2. `Burnchain::classify_transaction` (`stackslib/src/burnchains/burnchain.rs:929-963`) resolves `StackStxOp.sender` directly from `pre_stack_stx.output` — i.e., the attacker-chosen value — with `StackStxOp::get_sender_txid` (`stack_stx.rs:232-247`) only checking that the input spends vout=1 of the `PreStxOp` tx. Since the attacker created that `PreStxOp` tx, they trivially control and can spend its second output themselves; no victim key is ever required.
3. `StackStxOp::parse_from_tx` (`stack_stx.rs:270-350`) takes `reward_addr` and `signer_key` from data the attacker fully controls in the `StackStxOp` transaction, independent of `sender`.
4. `StacksChainState::process_stacking_ops` (`stackslib/src/chainstate/stacks/db/blocks.rs:4077-4130`) executes `tx.run_contract_call(&sender.clone().into(), ..., "stack-stx", &args, ...)` — i.e., the Clarity call is made *as* the spoofed `sender` principal, with no signature verification, because burnchain ops are not signed Stacks transactions.
5. Inside `pox-4.clar`'s `stack-stx` (`stackslib/src/chainstate/stacks/boot/pox-4.clar:571-621`), the checks performed are all against `tx-sender` (the spoofed victim): `is-none (get-stacker-info tx-sender)`, `is-none (get-check-delegation tx-sender)`, `(>= (stx-get-balance tx-sender) amount-ustx)`. Critically, `consume-signer-key-authorization` / `verify-signer-key-sig` (`pox-4.clar:735-788`) validates a signature/authorization over `{pox-addr, reward-cycle, topic, period, max-amount, auth-id}` — this payload contains **no stacker/tx-sender identity field**. The attacker can self-sign this authorization with their own `signer-key` for their own `reward_addr`, completely independent of whose STX balance ends up being locked.

Because none of the guards (`check-caller-allowed`, `verify-signer-key-sig`, balance check) bind the spoofed `tx-sender` cryptographically to the entity that actually authorized the transaction, the victim's real STX balance is locked under a PoX address and signer key chosen unilaterally by the attacker.

### Impact Explanation
The victim's STX becomes locked without consent (temporary/permanent freezing of the victim's principal for the stacking period), while the reward slot/weight and future BTC rewards accrue to the attacker's `reward_addr` and `signer_key`. This is theft of the yield on locked STX and freezing of the principal — matching the Critical category ("theft ... of locked STX ... rewards, ... freezing of staked STX"). This is repeatable against any victim account holding an unlocked STX balance sufficient for a valid `amount-ustx`, each cycle, as long as the victim's account isn't already stacking/delegating.

### Likelihood Explanation
Preconditions: the victim must have an unlocked STX balance and not already be stacking or delegating (both externally observable on-chain state, not privileged). The attacker needs only their own Bitcoin UTXOs (no fee-sponsorship or privileged role) and knowledge of the victim's Stacks address (public information). No node/relayer/miner collusion is required — this is achievable by any Bitcoin-transaction-crafting party observing chain state, matching the "unprivileged attacker" threat model. It is directly reproducible with the existing `#[cfg(test)]` constructors `PreStxOp::new` / `StackStxOp::new` already present in `stack_stx.rs:44-172`.

### Recommendation
Bind `PreStxOp.output` (and therefore `StackStxOp.sender`) to a value the burnchain-transaction signer actually controls — e.g., require that `output`'s hash160 matches a hash160 derivable from the transaction's own input signing key(s), or deprecate/remove the sender-spoofable burnchain stacking path in favor of exclusively signed Stacks-layer `stack-stx` transactions. Additionally, bind the `signer-key` authorization payload in `pox-4.clar` to the specific `stacker`/`tx-sender` principal so a self-signed authorization cannot be reused to lock an arbitrary third party's balance.

### Proof of Concept
Rust integration test plan (using existing scaffolding in `stack_stx.rs` and `burnchain.rs`):
1. Boot a local chainstate/sortition DB and fund `victim_addr` with an unlocked STX balance (e.g. via genesis allocation or a `TokenTransfer`).
2. Craft `pre_stx_tx`: a Bitcoin transaction funded solely from `attacker`'s UTXOs, with `Opcodes::PreStx`, output[0] = `victim_addr`'s corresponding Bitcoin-encoded address, output[1] = an address controlled by `attacker`. Feed through `PreStxOp::parse_from_tx` and assert `op.output == victim_addr`.
3. Craft `stack_stx_tx`: spends output[1] of `pre_stx_tx` (attacker-controlled, no victim key used), with `Opcodes::StackStx`, `reward_addr = attacker_pox_addr`, `signer_key = attacker_signer_pubkey`, self-signed `signer-sig` authorization matching `(reward_addr, cycle, "stack-stx", period, max_amount, auth_id)`. Run through `Burnchain::classify_transaction`; assert resulting `StackStxOp.sender == victim_addr` and `StackStxOp.reward_addr == attacker_pox_addr`.
4. Feed the op into `StacksChainState::process_stacking_ops`; assert the receipt shows `stacker: victim_addr` locked and no error.
5. Assert equality check both sides: BEFORE — `victim_addr` STX unlocked, no reward slot for `attacker_pox_addr`. AFTER — `victim_addr`'s `STXBalance` shows `amount_locked > 0` (owner-committed value diverges from actual authorizer), and the PoX reward-cycle reward set contains `attacker_pox_addr`/`attacker_signer_pubkey` credited with `victim_addr`'s locked amount — demonstrating both broken equalities.     pub fn parse_from_tx(
        block_height: u64,
        block_hash: &BurnchainHeaderHash,
        epoch_id: StacksEpochId,
        tx: &BurnchainTransaction,
        pox_sunset_ht: u64,
    ) -> Result<PreStxOp, op_error> {
        // can't be too careful...
        let num_inputs = tx.num_signers();
        let num_outputs = tx.num_recipients();

        if num_inputs == 0 {
            warn!(
                "Invalid tx: inputs: {}, outputs: {}",
                num_inputs, num_outputs,
            );
            return Err(op_error::InvalidInput);
        }

        if num_outputs == 0 {
            warn!(
                "Invalid tx: inputs: {}, outputs: {}",
                num_inputs, num_outputs,
            );
            return Err(op_error::InvalidInput);
        }

        if tx.opcode() != Opcodes::PreStx as u8 {
            warn!("Invalid tx: invalid opcode {}", tx.opcode());
            return Err(op_error::InvalidInput);
        };

        let outputs = tx.get_recipients();
        assert!(!outputs.is_empty());

        let output = outputs
            .get(0)
            .ok_or_else(|| {
                warn!("Invalid tx: first output not found");
                op_error::InvalidInput
            })?
            .as_ref()
            .ok_or_else(|| {
                warn!("Invalid tx: first output cannot be decoded");
                op_error::InvalidInput
            })?
            .address
            .clone()
            .try_into_stacks_address()
            .ok_or_else(|| {
                warn!("Invalid tx: first output must be representable as a StacksAddress");
                op_error::InvalidInput
            })?;

        // check if we've reached PoX disable
        if PoxConstants::has_pox_sunset(epoch_id) && block_height >= pox_sunset_ht {
            debug!(
                "PreStxOp broadcasted after sunset. Ignoring. txid={}",
                tx.txid()
            );
            return Err(op_error::InvalidInput);
        }

        Ok(PreStxOp {
            output,
            txid: tx.txid(),
            vtxindex: tx.vtxindex(),
            block_height,
            burn_header_hash: block_hash.clone(),
        })
    }

(define-public (stack-stx (amount-ustx uint)
                          (pox-addr (tuple (version (buff 1)) (hashbytes (buff 32))))
                          (start-burn-ht uint)
                          (lock-period uint)
                          (signer-sig (optional (buff 65)))
                          (signer-key (buff 33))
                          (max-amount uint)
                          (auth-id uint))
    ;; this stacker's first reward cycle is the _next_ reward cycle
    (let ((first-reward-cycle (+ u1 (current-pox-reward-cycle)))
          (specified-reward-cycle (+ u1 (burn-height-to-reward-cycle start-burn-ht))))
      ;; the start-burn-ht must result in the next reward cycle, do not allow stackers
      ;;  to "post-date" their `stack-stx` transaction
      (asserts! (is-eq first-reward-cycle specified-reward-cycle)
                (err ERR_INVALID_START_BURN_HEIGHT))

      ;; must be called directly by the tx-sender or by an allowed contract-caller
      (asserts! (check-caller-allowed)
                (err ERR_STACKING_PERMISSION_DENIED))

      ;; tx-sender principal must not be stacking
      (asserts! (is-none (get-stacker-info tx-sender))
        (err ERR_STACKING_ALREADY_STACKED))

      ;; tx-sender must not be delegating
      (asserts! (is-none (get-check-delegation tx-sender))
        (err ERR_STACKING_ALREADY_DELEGATED))

      ;; the Stacker must have sufficient unlocked funds
      (asserts! (>= (stx-get-balance tx-sender) amount-ustx)
        (err ERR_STACKING_INSUFFICIENT_FUNDS))

      ;; Validate ownership of the given signer key
      (try! (consume-signer-key-authorization pox-addr (- first-reward-cycle u1) "stack-stx" lock-period signer-sig signer-key amount-ustx max-amount auth-id))

      ;; ensure that stacking can be performed
      (try! (can-stack-stx pox-addr amount-ustx first-reward-cycle lock-period))

      ;; register the PoX address with the amount stacked
      (let ((reward-set-indexes (try! (add-pox-addr-to-reward-cycles pox-addr first-reward-cycle lock-period amount-ustx tx-sender signer-key))))
          ;; add stacker record
         (map-set stacking-state
           { stacker: tx-sender }
           { pox-addr: pox-addr,
             reward-set-indexes: reward-set-indexes,
             first-reward-cycle: first-reward-cycle,
             lock-period: lock-period,
             delegated-to: none })

          ;; return the lock-up information, so the node can actually carry out the lock.
          (ok { stacker: tx-sender, lock-amount: amount-ustx, signer-key: signer-key, unlock-burn-height: (reward-cycle-to-burn-height (+ first-reward-cycle lock-period)) }))))

                                         (topic (string-ascii 14))
                                         (period uint)
                                         (signer-sig-opt (optional (buff 65)))
                                         (signer-key (buff 33))
                                         (amount uint)
                                         (max-amount uint)
                                         (auth-id uint))
  (begin
    ;; Validate that amount is less than or equal to `max-amount`
    (asserts! (>= max-amount amount) (err ERR_SIGNER_AUTH_AMOUNT_TOO_HIGH))
    (asserts! (is-none (map-get? used-signer-key-authorizations { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))
              (err ERR_SIGNER_AUTH_USED))
    (match signer-sig-opt
      ;; `signer-sig` is present, verify the signature
      signer-sig (ok (asserts!
        (is-eq
          (unwrap! (secp256k1-recover?
            (get-signer-key-message-hash pox-addr reward-cycle topic period max-amount auth-id)
            signer-sig) (err ERR_INVALID_SIGNATURE_RECOVER))
          signer-key)

            { signer-key: signer-key, reward-cycle: reward-cycle, period: period, topic: topic, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount }))

;; This function does two things:
;;
;; - Verify that a signer key is authorized to be used
;; - Updates the `used-signer-key-authorizations` map to prevent reuse
;;
;; This "wrapper" method around `verify-signer-key-sig` allows that function to remain
;; read-only, so that it can be used by clients as a sanity check before submitting a transaction.
(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
  (begin
    ;; verify the authorization
    (try! (verify-signer-key-sig pox-addr reward-cycle topic period signer-sig-opt signer-key amount max-amount auth-id))
    ;; update the `used-signer-key-authorizations` map
    (asserts! (map-insert used-signer-key-authorizations
      { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount } true)
      (err ERR_SIGNER_AUTH_USED))
    (ok true)))
