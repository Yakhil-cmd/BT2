### Title
Asset display-name spoofing via unauthenticated registry `data` metadata (`asset_metadata.name`) - (File: wallet.js)

### Summary
Chrome's CVE-2023-5850 involves the Downloads UI displaying a spoofed/crafted domain name to trick users. The closest reachable analog in ocore is the asset-metadata mechanism that lets any address act as a "registry" and assign an arbitrary human-readable `name`/`suffix` to an asset, which is later displayed to wallet users as the trusted asset ticker with no linkage-strength guarantee to the real, well-known asset of the same or confusingly similar name.

### Finding Description
Any address can post a `data` message that is interpreted as asset metadata: `fetchAssetMetadata` in wallet.js reads the `data` payload from a unit and only verifies that `objJoint.unit.authors[0].address === registry_address` and that `payload.name` is a truthy value [1](#0-0) . There is no validation that this "registry" is an established/known registry, no uniqueness enforcement against the base name across registries beyond the `(name, registry_address)` composite unique key [2](#0-1) , and no homograph/confusable-character or length-collision defense on `name`/`suffix`. Consequently, an attacker can issue a brand-new asset and register a metadata unit naming it e.g. `"USDT"` or `"GBYTE"` (identical to, or visually confusable with, a well-known asset), which the wallet stores in `asset_metadata` and subsequently displays via `readAssetMetadata`, building the shown name as `name` or `name + '.' + suffix` [3](#0-2) . On the generic validation path for `data`/`asset` app messages, `validateInlinePayload` only requires the payload to be a non-empty object — no special-casing or stricter checks exist for asset-metadata-carrying `data` messages beyond the generic object-type check [4](#0-3) . The hub-side responder for `hub/get_asset_metadata` simply serves back whatever was stored, without any authenticity or reputation signal [5](#0-4) .

This mirrors the Chromium bug class: a crafted, attacker-controlled "name" is surfaced in a trust-sensitive UI surface (asset selection/send screens) without adequate assurance that it corresponds to the entity the user believes it does.

### Impact Explanation
A user relying on the wallet's displayed asset name (rather than the 44-character asset hash) to select or verify an asset before sending funds, accepting a payment, or interacting with an AA that expects a specific asset, can be deceived into transacting with a spoofed/lookalike asset instead of the intended legitimate one. This can result in unauthorized/misdirected spending of funds by the victim (paying value into a worthless spoofed asset believing it is the real one), a concrete "unauthorized spending" outcome as required by validation criteria. Because asset identity in ocore is fundamentally the unit hash, not the name, the underlying ledger operations remain internally consistent — the risk is entirely in the trust users place in the human-readable label surfaced from `asset_metadata`.

### Likelihood Explanation
The attack requires only posting a new asset definition and a `data` message from the same address acting as its own "registry" — both are standard, unprivileged operations available to any unit poster. No special permissions, hub cooperation, or network position is needed, which keeps likelihood moderate-to-high; the main constraint is convincing users to interact with the spoofed asset (typical for lookalike-token phishing).

### Recommendation
- Require the wallet UI to always display or prominently include the asset hash alongside any registry-provided `name`, and clearly indicate an untrusted/unverified registry.
- Maintain a curated allow-list or reputation mechanism for `registry_address` values that are permitted to set unqualified/short names, defaulting all others to mandatory, non-suppressible suffixing.
- Add homograph/confusable-character normalization checks when comparing or displaying names, and reject or flag names that are identical/confusable with names already claimed by higher-reputation registries.
- Consider validating `name` payload strings (charset restrictions, length caps, and confusable-script detection) at the point metadata is persisted in `fetchAssetMetadata`, rather than accepting the payload as-is.

### Proof of Concept
1. Attacker defines a new asset `A` via a standard `asset` message payload (any actor can do this, subject to normal `validateAssetDefinition` rules) [6](#0-5) .
2. From the same address (acting as `registry_address`), attacker posts a `data` message payload `{ asset: A, name: "USDT", decimals: 6 }`.
3. A victim's wallet calls `fetchAssetMetadata(A, ...)`, which fetches this unit, verifies only that `objJoint.unit.authors[0].address === registry_address` (true, since attacker controls both), and stores `name: "USDT"` into `asset_metadata` [7](#0-6) .
4. `readAssetMetadata`/wallet UI subsequently displays asset `A` as `"USDT"` (or `"USDT.<suffix>"`) [3](#0-2) , indistinguishable in the UI from the legitimate USDT-equivalent asset to an inattentive user, who may then send value intending to interact with the real asset.

Note: I was unable to locate the definition of `isUpdatableRegistry` or any registry allow-list/reputation constants within the indexed portion of the codebase before running out of search iterations, so I cannot confirm whether any registry-trust restrictions already partially mitigate this (e.g., limiting which addresses can suppress the suffix). This should be verified in a full checkout of the repository.
