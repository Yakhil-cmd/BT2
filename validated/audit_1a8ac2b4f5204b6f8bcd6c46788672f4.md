## Analysis

The reported bug class is: **a batched operation that iterates over multiple independent assets/outputs fails entirely (and irreversibly loses/blocks the non-problematic funds) because a single asset/output fails an external restriction check (blacklist)**.

The closest reachable analog in ocore is in the **Autonomous Agent (AA) response composer**, `aa_composer.js`, function `handleTrigger` → `sendUnit`. When an AA's oscript produces `messages` containing multiple `payment` messages (potentially to different assets/recipients), they are all merged and composed into a *single* response unit: [1](#0-0) 

Each payment message's asset is loaded and validated in `async.eachSeries` over `messages`; if any single message errors, the whole series callback receives that error: [2](#0-1) [3](#0-2) 

If `err` is non-null (e.g., the asset is `is_private` and can't be sent from an AA, or later fails `transfer_condition`/`is_transferrable`/`spender_attested`/`cosigned_by_definer` checks enforced in `validatePaymentInputsAndOutputs` in `validation.js`), the composer calls `bounce(err)`, discarding the *entire* response unit, not just the offending asset's message: [4](#0-3) 

### Title
AA response with multiple asset payments bounces entirely when only one asset's transfer condition fails, freezing all other legitimate outputs - (File: aa_composer.js)

### Summary
An Autonomous Agent that responds to a trigger with several `payment` messages for different assets (e.g., sending back a mix of bytes, asset A, and asset B to the triggering user or third parties) composes them into one response unit. Asset-level restrictions such as `transfer_condition`, `is_transferrable`, `spender_attested`, `cosigned_by_definer`, or `is_private` are evaluated for the whole response unit at validation/composition time. A restriction failure on **any single asset/output** causes the AA to reject (`bounce`) the **entire** response, not just the problematic message.

### Finding Description
`sendUnit()` in `aa_composer.js` iterates all response `messages` with `async.eachSeries`, loading each payment's asset via `storage.loadAssetWithListOfAttestedAuthors` and building the corresponding payload [5](#0-4) . If loading/validating any one asset fails (e.g. `objAsset.is_private` → `"sending private asset from AA"`), the overall `async.eachSeries` callback receives that error and the code calls `bounce(err)` [6](#0-5) , discarding the whole set of outputs across all assets/messages that the AA intended to send.

Even for messages that pass the composer's own quick checks, the resulting unit still undergoes full network validation, where each asset's `transfer_condition` (via `Definition.evaluateAssetCondition`) or transferability/attestation checks are enforced per-asset payload in `validatePaymentInputsAndOutputs` [7](#0-6) . Since all payment messages are merged into a single response unit for a trigger [8](#0-7) , a restrictive condition tied to a single asset (analogous to a "blacklist" — e.g., `transfer_condition` requiring attestation, or `spender_attested` rejecting a specific address) blocks delivery of the *entire* batch, including outputs of the base asset and any other unrelated, unrestricted assets that were destined for other legitimate addresses.

### Impact Explanation
This causes AA fund loss/freezing: legitimate payouts for unrelated assets/recipients that would have otherwise succeeded are blocked and the funds remain stuck in the AA's balance whenever the AA's response logic tries to combine a restricted-asset payment with other payments in the same trigger response. Since bounced state changes are rolled back, this can repeatedly recur on every subsequent trigger that hits the same code path, effectively locking those funds inside the AA with no way for the affected user (or others) to retrieve their share until the AA definition is changed (which is often impossible for immutable AAs).

### Likelihood Explanation
Any AA author combining a restricted/conditional asset (private, non-transferrable, `spender_attested`, or having a custom `transfer_condition`) with other asset payouts in the same response is exposed. This requires no special privilege — any user can define an AA (or trigger an existing composable AA template) that pays out multiple assets in one response, and any third party controlling/definer of one of those assets (or an attestor list) can effectively freeze all bundled payouts by failing the condition for one address.

### Recommendation
Consider validating/sending payment messages for different assets as decoupled response actions (or providing an oscript-level mechanism to detect and skip/(bounce only) the failing asset's message) rather than aggregating all payment messages of a trigger response into a single atomic unit whose success is all-or-nothing. At minimum, document this atomicity clearly so AA authors avoid combining restricted assets with unrelated payouts in a single trigger response, and/or add a composer-level check that surfaces which specific asset/message caused the bounce so AA logic can conditionally omit it.

### Proof of Concept
1. Deploy an AA whose response, for a given trigger, sends: (a) a base-asset payment to the trigger address, and (b) an asset-X payment (asset X defined with `spender_attested: true` or a `transfer_condition`) to the same or another address.
2. Trigger the AA from an address that is not on asset X's attested list (or whose transfer condition evaluates false).
3. Observe in `aa_composer.js`'s `sendUnit` / `validatePaymentInputsAndOutputs` that the entire response — including the base-asset payment that should have succeeded — is bounced, and the AA's balance for both assets remains unchanged and undeliverable, reproducing itself on every future identical trigger.

	// merges payment messages paying in the same asset into a single message,
	// and merges outputs paying in the same asset to the same address into a single output.
	// send-all outputs (amount === undefined) are left as they are and never merged with anything.
	// non-payment messages are left intact.
	function mergeMessagesAndOutputs(messages) {
		const arrMergedMessages = [];
		const assocMergedMessagesByAsset = Object.create(null);
		for (let message of messages) {
			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
