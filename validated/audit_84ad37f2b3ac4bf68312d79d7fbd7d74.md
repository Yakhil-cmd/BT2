### Title

Route-selected venue can piggyback on the caller’s signed authorization to steal unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary

A malicious pool address embedded in a strategy route can request an unrelated `token.transfer(victim, attacker, amount)` while executing below the caller-authorized controller invocation; if the victim signs the simulated authorization tree, that nested transfer executes even though the lending strategy itself remains solvent. [1](#0-0) 

### Finding Description

`swap_collateral` authenticates `caller`, verifies account ownership or delegation, and forwards the caller-supplied `swap` bytes into the strategy swap path. [2](#0-1)  `swap_tokens` invokes the configured router with `controller` as `sender` and authorizes only the controller’s exact input-token transfer, but it does not constrain which pool contract the route invokes. [3](#0-2)  The route payload selects the pool address, and the venue dispatcher invokes that address without an allowlist. [4](#0-3) [5](#0-4) 

Because the strategy’s root invocation already requires the account owner’s authorization, code reached through the route can request another `victim.require_auth()`-protected token transfer; Soroban simulation represents that request as a child of the victim’s controller authorization, and enforcement accepts it when the victim signs that tree. [6](#0-5) [7](#0-6)  The controller’s post-router checks only bound the controller-held input spend, require positive measured output, and apply final account-risk gates, so they do not detect a transfer from the caller’s unrelated wallet balance. [8](#0-7) 

### Impact Explanation

An attacker can cause the victim to authorize transfer of an unrelated token balance while receiving a valid-looking strategy output, resulting in theft of user funds outside the routed amount. [9](#0-8) [10](#0-9)  This bypasses the intended boundary that the strategy should spend only the position collateral or controller-authorized input: the malicious venue rides on the user’s signature rather than obtaining a token allowance from the victim. [11](#0-10) 

### Likelihood Explanation

Exploitation requires the victim to submit a route containing attacker-controlled venue code and to sign the expanded authorization tree produced by simulation. [12](#0-11)  The attacker needs no privileged role, existing allowance, or control of the victim’s lending account, and can make the venue return enough output for the route’s minimum-output and final-risk checks. [13](#0-12)  The resulting risk is high-impact but user-interaction-dependent because a wallet or client that rejects unexpected child invocations prevents execution. [14](#0-13) 

### Recommendation

Do not let route bytes select arbitrary executable venue contracts while a user authorization is active; bind each venue opcode to governance-approved pool contracts or another enforceable pool allowlist before invoking external code. [15](#0-14)  Until that boundary exists, clients should simulate every strategy transaction and reject any signed authorization tree containing calls other than the exact expected token pull, while the repository test fixture demonstrates the malicious-child shape to detect. [6](#0-5) 

### Proof of Concept

The harness deploys a route whose pool contract calls `wallet_token.transfer(victim, attacker, WALLET_BALANCE)` from inside its swap implementation. [16](#0-15)  The route is passed to `swap_collateral(caller=alice, account_id, current=USDC, amount=5_000 USDC, new=ETH, swap=route)`, and the router still returns a fair ETH output to the controller. [17](#0-16)  Recording simulation places `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` under Alice’s `swap_collateral` authorization, and signing that tree leaves Alice’s unrelated wallet token at zero and the attacker with `WALLET_BALANCE`. [18](#0-17)  With an honest root-only authorization tree the same call is rejected, confirming that the theft is enabled specifically by the poisoned authorization context rather than ordinary swap execution. [14](#0-13)

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };
