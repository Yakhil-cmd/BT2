### Title
Webhook organization used for signature verification is decoupled from the repository field used to route the event - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In the "Using Multiple GitHub Applications" configuration mode, Shipit selects the GitHub App / `webhook_secret` used to verify an incoming webhook's HMAC signature based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). However, every event handler resolves the actual `Stack`/`Repository` to mutate using a **different** field of the same untrusted JSON body: `payload.dig('repository', 'full_name')`. Because GitHub itself guarantees `repository.owner.login` and `repository.full_name` are consistent, this works safely for genuine GitHub deliveries. But nothing on the Shipit side enforces that these two fields agree, so a forged request only needs a valid signature for *some* configured organization while claiming an arbitrary `repository.full_name`.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` comes from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [5](#0-4) . `Shipit.github(organization:)` looks up the per-organization `webhook_secret` from the multi-org secrets config keyed by organization login [6](#0-5) .

After signature verification passes, `create` dispatches the same raw payload to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) . Every handler (`PushHandler`, `PullRequest::*Handler`, etc.) resolves the target repository/stack via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [3](#0-2) [4](#0-3) .

Equality that should hold but doesn't:
```
organization authenticated (repository.owner.login, used to pick webhook_secret)
   ==
organization implied by repository.full_name (used to pick the Stack/Repository acted on)
```

In the multi-GitHub-App setup documented in `docs/setup.md` ("Using Multiple Github Applications"), each organization has its own independent `webhook_secret`. Any org onboarded onto the Shipit instance (including one an attacker fully controls, e.g. their own GitHub org with their own app installed) has a legitimate, attacker-known `webhook_secret`. An attacker who knows their own org's secret can craft a POST to `/webhooks` where `repository.owner.login` (and `repository.full_name`'s owner segment) is set to their own controlled org so the HMAC verifies, while other payload content (e.g. `ref`, `after` sha, PR fields) can be set arbitrarily to whatever the handler needs — the binding that is actually enforced (organization signature) does not have to match the binding that determines *victim* impact, since `from_github_repo_name` is a simple string lookup with no ownership check tying it back to which GitHub App/secret validated the request.

Concretely, `PushHandler` only requires `ref` and `after`, and triggers `stack.sync_github(expected_head_sha:)` for any `Stack` whose `Repository#full_name` matches the string in the payload [8](#0-7) . If two different Shipit-tracked repositories happen to be routed under different GitHub Apps/orgs (a realistic scenario in the documented multi-app setup, e.g. forks, org renames, or shared Shipit instances serving multiple orgs), a webhook validly signed by org A's secret can carry `repository.full_name` for a repository actually configured under org B, and Shipit will process it as if it came from org B's GitHub App.

### Impact Explanation
This breaks the authentication boundary between "which organization's secret validated this request" and "which repository's stack gets acted on." Depending on the handler triggered, this can drive an unauthorized deploy pipeline event (`GithubSyncJob`/`sync_github` via `PushHandler`), archive/unarchive review stacks, or falsify commit `status`/`check_suite` state used by deploy gating — all attributed to a repository the attacker does not control the GitHub side of. This matches the "unauthorized deploy" / "cross-repository writes" impact class since a party who is only authenticated for org A can inject repository-state-changing events scoped to org B's tracked stacks.

### Likelihood Explanation
Requires the deployment to use the documented multi-GitHub-App configuration and requires the attacker to control (or have) a `webhook_secret` for at least one onboarded organization — this is a plausible unprivileged-attacker position if the Shipit instance serves multiple, mutually-untrusting GitHub orgs (a supported, documented configuration), since being able to sign a webhook for "your own" org is not privileged access to the Shipit application itself.

### Recommendation
When verifying the webhook signature, cross-check that the organization used to select the `webhook_secret` (`repository_owner`) matches the organization implied by `repository.full_name` (and any other repository-identifying fields used later by handlers) before dispatching to handlers, rejecting the request if they diverge.

### Proof of Concept
1. Configure Shipit with multiple GitHub Apps per `docs/setup.md`'s "Using Multiple Github Applications" section, onboarding `OrgA` (attacker-controlled) and `OrgVictim` (has a tracked `Stack`/`Repository` with `full_name = "OrgVictim/app"`).
2. Attacker computes a valid `X-Hub-Signature` using `OrgA`'s `webhook_secret` over a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgVictim/app" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
3. POST to `/webhooks` with `X-Github-Event: push` and the computed signature.
4. `verify_signature` selects `Shipit.github(organization: "OrgA")`, verifies successfully against `OrgA`'s secret.
5. `PushHandler` resolves `Repository.from_github_repo_name("OrgVictim/app")`, finds the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — an event scoped to `OrgVictim`'s repository is accepted on the strength of `OrgA`'s signature.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
