### Title
Single failing submodule permanently blocks publication of an otherwise valid, already-fetched commit - ([File: main.go])

### Summary
`configureWorktree` performs two sequential, independently-failing git operations against a single worktree — a full checkout of the main repository (`reset --hard`) and, if submodules are enabled, `submodule update --init[--recursive]` — and requires **both** to succeed before `SyncRepo` will flip the publish symlink. If the submodule step fails for any reason (unreachable/compromised/deleted submodule remote, auth mismatch, network partition, or a submodule pointer that references a URL the operator no longer controls), the entire sync is aborted even though the main repository content was already successfully checked out to disk in that worktree. This mirrors the reported pattern where multiple sub-operations (withdrawal requests) must *all* finalize before any of the result can be released, and the failure of just one blocks the whole set indefinitely.

### Finding Description
`configureWorktree` first hard-resets the worktree to the target commit: [1](#0-0) 

It then unconditionally attempts a submodule update as a second, separate step: [2](#0-1) 

If the `git submodule update` invocation fails, `configureWorktree` returns an error immediately, discarding the fact that the main repository checkout (the `reset --hard` step) already succeeded on disk in that worktree.

`SyncRepo` treats `configureWorktree` as an all-or-nothing gate before it will publish anything: the symlink flip and `afterPublish` hook only run after `configureWorktree` returns successfully, and any error from it short-circuits the whole sync attempt without ever calling `publishSymlink`: [3](#0-2) [4](#0-3) 

Because the sync loop retries `SyncRepo` from scratch every period, and by default `--max-failures` is unbounded (only `os.Exit(1)` when a configured limit is reached), a permanently-broken submodule causes an infinite retry loop that can never make progress: [5](#0-4) 

This is a direct structural analog to the reported bug: multiple sub-operations (there, N withdrawal requests via `manager.finalizeAndRedeemWithdrawRequest`; here, the main checkout + one or more submodule updates) are required to *all* succeed atomically before any result is released, and the codebase provides no mechanism to release/serve the successfully-completed portion (the main repo content) independently of the failing portion (a submodule).

### Impact Explanation
This falls into the accepted "persistent sync denial" category: as long as a submodule reference in the tracked ref is broken (e.g., a submodule repository is deleted, made private, rate-limited, or otherwise permanently unreachable — conditions an upstream committer with push access to the tracked repo/ref can trigger, intentionally or not, simply by adding/pointing a submodule at such a URL), `git-sync` can never advance past the last good commit, no matter how many valid, unrelated commits are pushed afterward to the main repository. Consumers relying on `--link` are frozen on stale data indefinitely, and there is no partial-publish fallback (e.g., disabling just the broken submodule) short of an operator manually reconfiguring `--submodules=off` or fixing the submodule URL out-of-band. This does not cause data loss (unlike the funds-stuck original), but it is a legitimate denial-of-service of the sync pipeline reachable purely from repository content an attacker (or any committer) controls.

### Likelihood Explanation
Moderate-to-high in any deployment that uses `--submodules=shallow|recursive` (the tool's non-default but documented feature) with submodules hosted outside the sync target's control or reliability guarantee. Any committer to the tracked repo can add a submodule pointing to a URL that later becomes unreachable, and once that commit is the tip of the tracked ref, sync is stuck until that specific ref/commit is superseded or the submodule config is fixed — no code path exists to "skip" or "finalize the good part."

### Recommendation
Decouple main-repo checkout success from submodule-update success where feasible: e.g., allow `configureWorktree`/`SyncRepo` to still publish the main-repo content (optionally flagging the sync as degraded/incomplete via metrics/logs) when only the submodule step fails, or provide a bounded retry/backoff + explicit alerting distinct from indefinite silent retries, rather than making a single submodule failure a hard, unconditional gate on all publication.

### Proof of Concept
1. Set up a repo with a submodule referencing `file://$SUBMODULE_PATH`.
2. Run `git-sync --repo=file://$REPO --root=$ROOT --link=link --submodules=recursive`.
3. After first successful sync, `rm -rf` (or otherwise make permanently unreachable) the submodule's remote path, then push a new, unrelated commit to the main `$REPO` that does not touch the submodule.
4. Observe: `configureWorktree` successfully runs `reset --hard` to the new main-repo commit but fails on `submodule update --init --recursive`; `SyncRepo` returns an error, `publishSymlink` is never called, and `$ROOT/link` stays pinned to the old commit forever, even though the new main-repo content is fully valid and was already checked out on disk in the (unpublished) worktree — reproducing the "one failed sub-operation blocks the finalized state of all others" pattern from the referenced report.
