### Title
Cross-organization webhook forgery via `repository_owner`/`organization.login` binding mismatch enables authorization escalation into `Shipit.github_teams` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify a payload against using `repository_owner`, which is read from the payload's `repository.owner.login` (falling back to `organization.login`). But once verification passes, `Shipit::Webhooks::Handlers::MembershipHandler` acts on a completely independent field, `params.organization.login`, to create/attach a `Team` record, and `params.team`/`params.member` to grant membership — with no check that this organization matches the org whose secret was actually used to verify the signature.

### Finding Description
In a multi-tenant Shipit deployment (explicitly documented in `docs/setup.md` "Using Multiple GitHub Applications" and exercised by `test/dummy/config/secrets_double_github_app.yml`), each onboarded GitHub organization has its own GitHub App with its **own webhook secret**, looked up via `Shipit.github(organization: repository_owner)` [1](#0-0) . The org admin who creates that GitHub App legitimately knows their own org's webhook secret (they configure it themselves on github.com per `docs/setup.md`).

The controller picks the verification key from the request body itself: [2](#0-1) [3](#0-2) 

The whole raw POST body is HMAC-signed and verified as one blob: [4](#0-3) 

Because the entire body is attacker-authored before signing, an attacker who owns/administers **their own onboarded organization** ("OrgTwo") can freely construct a JSON payload where `repository.owner.login` (or a top-level `organization.login`) is `"OrgTwo"` — satisfying `verify_signature`'s org-based secret lookup — while other fields inside the same payload reference an entirely different, victim organization/team. `MembershipHandler` trusts `params.organization.login` and `params.team` at face value with no cross-check against `repository_owner`/the verifying org: [5](#0-4) 

Authorization in this engine is not driven by live GitHub team membership but by locally-stored `Team`/`Membership` rows populated exclusively from these `membership` webhooks: [6](#0-5) 

Since `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, and `Shipit.github_teams` is configured by `github_id`/team identity rather than being scoped per-organization at check time, an attacker who can forge a `membership` "added" event naming a privileged team's `github_id`/`slug` and their own GitHub login as `member.login` can insert themselves into that `Team`'s `members` association purely by crafting a payload whose *signing organization* differs from the *acted-upon organization/team*.

### Impact Explanation
This breaks the equality "the organization that authenticated the payload == the organization the payload's actions are scoped to." Successful exploitation lets an attacker with legitimate access to only one onboarded, low-privilege GitHub organization grant themselves membership in a `Team` that is part of `Shipit.github_teams`, thereby escalating into full authorization on the shared Shipit instance — an explicit High-impact category ("escalation into `Shipit.github_teams` authorization"). From there, the attacker gains all privileges of an authorized Shipit user: viewing stacks, triggering deploys, etc., across organizations/repositories they were never meant to access.

### Likelihood Explanation
This requires: (1) a Shipit deployment configured for multiple GitHub organizations (an explicitly documented, supported configuration), and (2) the attacker administering one such onboarded organization's own GitHub App (hence knowing its webhook secret) while the target team's `github_id` is guessable or discoverable (team IDs/slugs are often public/enumerable via GitHub's API). No GitHub-side spoofing is needed—GitHub delivery isn't required at all, since the attacker can POST directly to `/webhooks` with a self-signed payload. This is a realistic, low-complexity attack once the multi-org precondition holds.

### Recommendation
Bind the organization used for the security decision to the organization actually acted upon:
- In `MembershipHandler`, verify `params.organization.login` matches the `repository_owner`/verifying organization already resolved by `WebhooksController#verify_signature` (e.g., pass the verified organization into the handler and reject mismatches).
- More generally, do not derive the HMAC-key-selecting field from unauthenticated payload content that can diverge from the payload fields actually consumed by the handlers; instead, verify against every organization configured, or ensure a single authoritative field is used both for key selection and downstream authorization decisions.

### Proof of Concept
1. Deploy Shipit with multiple GitHub Apps configured, e.g. `OrgOne` (target/victim) and `OrgTwo` (attacker-administered), as in `test/dummy/config/secrets_double_github_app.yml`.
2. As the admin of `OrgTwo`'s own GitHub App, the attacker knows `OrgTwo`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "action": "added",
  "organization": { "login": "OrgOne" },
  "team": { "id": 999, "name": "shopify/developers", "slug": "developers", "url": "https://github.com/x" },
  "member": { "login": "attacker-handle" },
  "repository": { "owner": { "login": "OrgTwo" } }
}
```
4. Attacker computes `sha1=HMAC(OrgTwo_webhook_secret, raw_body)` and sets `X-Hub-Signature` accordingly, `X-Github-Event: membership`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgTwo"` [3](#0-2) , loads OrgTwo's app, and the signature verifies successfully because the attacker signed it with the secret they legitimately know.
6. `MembershipHandler#process` runs, using `params.team`/`params.organization.login` = `"OrgOne"` to find-or-create the `Team` and add `attacker-handle` as a member [5](#0-4) , with no cross-check against the verifying org (`OrgTwo`).
7. If the targeted `Team` is part of `Shipit.github_teams`, `attacker-handle`'s Shipit `User` now passes `authorized?` [6](#0-5) , gaining full access to the shared Shipit instance including `OrgOne`'s stacks.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
