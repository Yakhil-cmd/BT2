### Title
Webhook signature is verified against the organization named in the payload, not the organization/repository the event is applied to — allows cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound webhook against using a field read out of the *same untrusted request body* it is about to verify, rather than the organization that is actually going to be mutated by the handler. Because different handlers key off a different payload field (`repository.full_name`) to decide which `Repository`/`Stack`/`Commit` to act on, an attacker who legitimately controls one Shipit-configured GitHub organization (and therefore knows/controls that organization's `webhook_secret`) can forge a webhook payload that authenticates as their own org while acting on a completely different, victim organization's repository.

### Finding Description
`verify_signature` derives the org used to look up the verification secret purely from the JSON body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` then just HMACs the *entire* raw body with the secret configured for that org: [3](#0-2) . Shipit explicitly supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret` [4](#0-3) .

Once the signature check passes, the actual event handlers do **not** re-derive the target from `repository_owner` — they use `repository.full_name` (`PushHandler`/`Handler#repository_name`) or, worse, a completely unscoped global lookup: [5](#0-4) [6](#0-5) 

`StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no repository/organization scoping at all — any commit anywhere in the Shipit instance with that SHA gets a status attached.

Because the signature only proves "this byte sequence was signed with org X's secret," and the handler dispatches based on a *different, attacker-controlled field* inside that same signed byte sequence, an attacker who is a legitimate admin of one configured org (org A, whose `webhook_secret` they know because they set it up in Shipit's config, or because they can reasonably obtain it as the org's App owner) can:

1. Build a JSON body with `repository.owner.login` = `"org-a"` (their own org, satisfying `verify_signature`) but `repository.full_name` = `"victim-org/victim-repo"` (or, for status events, simply omit any repository scoping and target an arbitrary `sha`).
2. Sign the whole raw body with `org-a`'s `webhook_secret` using `sha1=HMAC-SHA1(secret, body)`.
3. POST it to `/github/webhooks`. `verify_signature` succeeds because it validates against `org-a`'s secret. The dispatched handler then acts on `victim-org/victim-repo` or an arbitrary commit SHA belonging to any stack in the instance.

This breaks the binding: *organization authenticated by the webhook signature* == *organization/repository the handler writes to*.

### Impact Explanation
Depending on which handler is invoked, this permits:
- Forging `push` events to trigger `GithubSyncJob`/`stack.sync_github` for stacks belonging to a different organization than the one whose secret validated the request [7](#0-6) .
- Forging `status` events to write arbitrary commit statuses (e.g. marking CI as `success`) for **any commit in the entire Shipit installation**, regardless of which org the forger's signature belongs to, since `StatusHandler` performs no ownership check at all. This can satisfy blocking-status requirements for a merge/deploy on a repository the attacker has no access to, contributing to an unauthorized deploy/merge — matching the High-severity class in scope ("escalation into `Shipit.github_teams` authorization" / "unauthorized deploy").
- Cross-repository/cross-org effects analogous to `pull_request` handlers that resolve `repository` from the same attacker-controlled `full_name` field.

The severity is bounded by the fact that this requires the Shipit installation to be configured for multiple GitHub organizations (`docs/setup.md` "Using Multiple Github Applications") and for the attacker to hold a valid webhook secret for at least one of them — this is an unprivileged-attacker path within the multi-tenant boundary the engine itself defines (org isolation), so it is in-scope: it's not "requiring a Shipit session/API token/GitHub write access to the victim repo," only to the attacker's own, unrelated, low-trust org.

### Likelihood Explanation
Any Shipit deployment that onboards more than one GitHub organization (a documented, supported configuration) is exposed. The attack requires no interaction with the victim org's GitHub App, GITHUB_TOKEN, or Shipit session — only knowledge of one's own org's webhook secret and the ability to send an HTTP POST with a crafted JSON body and matching HMAC signature to the public webhook endpoint.

### Recommendation
Bind the field used to select the verification secret to the same field(s) used by the handlers to determine the acted-upon resource, and re-validate after dispatch:
- Have `verify_signature` (or a shared method) resolve the organization from `repository.full_name`'s owner segment (the same value handlers use), not a separate `repository.owner.login`/`organization.login` field.
- In each handler (especially `StatusHandler`), scope lookups (`Commit.where(sha: ...)`, etc.) to repositories belonging to the organization that was cryptographically verified, rejecting/ignoring records that belong to a different organization than the one whose secret validated the signature.
- Reject webhooks where the verified organization does not match the organization implied by every repository-identifying field present in the payload.

### Proof of Concept
1. Shipit is configured with two GitHub orgs in `secrets.yml`: `org-a` (attacker-administered, webhook secret `SECRET_A` known to the attacker) and `victim-org` (unrelated, has a stack tracking commits by SHA).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/some-repo"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=` `HMAC-SHA1(SECRET_A, body)`.
4. Attacker sets `X-Github-Event: status` and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `SECRET_A` [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` [6](#0-5)  and applies the forged `success` status to the victim's commit, with no relation to `org-a` checked anywhere in the flow.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
