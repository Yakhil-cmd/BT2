### Title
Unsafe `int64` Cast of `uint64` Staking Amounts Corrupts CN/CL Reward Split Ratio — (`kaiax/staking/staking_info.go`)

### Summary

`consolidatedNode.Split()` converts `uint64` staking amounts to `big.Int` via `big.NewInt(int64(...))`. The intermediate `int64` cast silently wraps any value ≥ 2^63 to a large negative number, producing a negative `big.Int` ratio denominator. Every downstream call that uses `Split()` to divide block rewards between a validator's CN staking address and its CL pool address will then compute a wrong `clAmount`, misdirecting KAIA reward distribution.

### Finding Description

In `kaiax/staking/staking_info.go`, `consolidatedNode.Split()` is the sole function that proportionally divides a reward amount between a validator's CNStaking address and its CLPool address (introduced in the Prague / KIP-226 hardfork):

```go
// kaiax/staking/staking_info.go  lines 169-187
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }

    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))              // ← unsafe cast
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount)) // ← unsafe cast
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount  = clAmount.Div(clAmount, totalAmount)
    cnAmount  := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
``` [1](#0-0) 

Both `c.StakingAmount` and `c.CLStakingInfo.CLStakingAmount` are declared as `uint64`: [2](#0-1) [3](#0-2) 

The staking amounts are stored in KAIA units (divided by `params.KAIA = 1e18` at ingestion time): [4](#0-3) [5](#0-4) 

`uint64` can hold up to 18,446,744,073 KAIA. `int64` can hold only up to 9,223,372,036 KAIA. Any staking amount ≥ 9,223,372,037 KAIA causes `int64(c.StakingAmount)` to wrap to a large negative value, making `cnAmountBig` or `clAmountBig` negative. The resulting `totalAmount` denominator is then wrong (small, zero, or negative), and the division produces a wildly incorrect `clAmount`.

`Split()` is called in four reward-distribution paths:

- `assignStakingRewards()` — splits per-staker block rewards between CN and CL pool
- `assignStakingRewardsFlex()` — same, under the Flex reward rule
- `specWithProposerAndFunds()` — splits the proposer's minting reward between CN and CL pool
- `specWithProposerAndFundsFlex()` — same, under the Flex reward rule [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation

When `c.StakingAmount` ≥ 2^63 KAIA, `cnAmountBig` becomes a large negative `big.Int`. The computed `clAmount` is then either near-zero (CL pool receives almost nothing) or exceeds `amount` (CL pool receives more than the total reward, making `cnAmount` negative, which `IncRecipient` would subtract from the CN address balance). Either outcome is an incorrect KAIA reward distribution: KAIA that should flow to the CL pool is silently redirected to the CN reward address, or vice versa, every block for every affected validator.

### Likelihood Explanation

The current total KAIA supply is approximately 5.4 billion KAIA. The overflow threshold is ~9.22 billion KAIA for a single consolidated validator (CN + CL combined). This is not reachable today. However:

1. The minting amount is a governance parameter that continuously inflates supply.
2. A single consolidated node aggregates multiple AddressBook entries sharing the same `RewardAddr` — their `StakingAmount` values are summed at line 138, so multiple staking contracts pointing to one reward address accelerate the approach to the threshold.
3. There is no upper-bound validation on staking amounts anywhere in the ingestion path.

The defect is latent and will become exploitable as supply grows, with no code change required by any party.

### Recommendation

Replace the unsafe `int64` intermediate cast with `new(big.Int).SetUint64()`, which correctly handles the full `uint64` range:

```go
// Before (unsafe):
cnAmountBig = big.NewInt(int64(c.StakingAmount))
clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))

// After (safe):
cnAmountBig = new(big.Int).SetUint64(c.StakingAmount)
clAmountBig = new(big.Int).SetUint64(c.CLStakingInfo.CLStakingAmount)
```

Apply the same fix to any other site that converts a `uint64` staking amount to `big.Int` via `big.NewInt(int64(...))`.

### Proof of Concept

1. A validator registers two staking contracts under the same `RewardAddr` in AddressBook, each holding 5,000,000,000 KAIA (10 billion KAIA combined, feasible after sufficient minting).
2. `consolidateNodes()` sums them: `cn.StakingAmount = 10_000_000_000` (uint64).
3. The validator also has a CL pool with `CLStakingAmount = 1_000_000` KAIA.
4. At block finalization, `Split(reward)` is called:
   - `int64(10_000_000_000)` = `10_000_000_000` — still fits in int64 here, but at `int64(9_223_372_037)` it wraps to `-9_223_372_036_854_775_807`.
   - With a wrapped negative `cnAmountBig`, `totalAmount` ≈ `−9.22e18 + 1_000_000` ≈ `−9.22e18`.
   - `clAmount = 1_000_000 * reward / (−9.22e18)` ≈ `0` (rounds to zero for any block reward).
   - `cnAmount = reward − 0 = reward` — CN address receives 100% of the reward.
5. The CL pool address receives 0 KAIA every block instead of its proportional share, permanently misdirecting KAIA rewards with no error or revert. [9](#0-8) [10](#0-9)

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}
