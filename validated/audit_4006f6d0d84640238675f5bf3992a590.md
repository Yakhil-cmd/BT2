## Finding: Valid, with one unverified gating point

### Title
`allow_missing_txn_authentication_key`'s derivable-AA branch is a global feature flag, not an account-scoped check, allowing accounts to be authenticated with stale/rotated-away authentication material - (File: `aptos-move/framework/aptos-framework/sources/transaction_validation.move`)

### Summary
`allow_missing_txn_authentication_key` decides whether a transaction may omit `txn_authentication_key` entirely: [1](#0-0) 

The two branches are asymmetric in scoping:
- The dispatchable-AA branch is *account-scoped*: `account_abstraction::using_dispatchable_authenticator(transaction_sender)` checks a resource stored **at the specific sender's address**.
- The derivable-AA branch is a **bare global feature flag** `features::is_derivable_account_abstraction_enabled()` with no reference to `transaction_sender` at all.

`prologue_common` uses this to decide whether to skip the `txn_authentication_key == account::get_authentication_key(sender_address)` binding check entirely: [2](#0-1) 

### Finding Description
Move-level authentication for a DerivableV1 abstract authenticator (`account_abstraction::authenticate`) only checks that the *sender's address* is derivable from the supplied `(function_info, abstract_public_key)` pair — it never inspects `AccountResource.authentication_key`: [3](#0-2) 

Because an Aptos account's address never changes after creation — `rotate_authentication_key`/`rotate_authentication_key_internal` only overwrite `Account.authentication_key`, never the address — [4](#0-3) 

any address that was originally derived from `(function_info, abstract_public_key)` remains permanently valid for that derivable-AA authentication path forever, **even after the account owner rotates `AccountResource.authentication_key` away to a standard Ed25519/SingleKey scheme**. The prologue's `allow_missing_txn_authentication_key` check does not re-verify that the account is still "currently" bound to derivable AA — it only checks the network-wide feature flag. So once `is_derivable_account_abstraction_enabled()` is on-chain, the binding between "what scheme currently authenticates this account" (`AccountResource.authentication_key`) and "what the prologue will accept without a key" (the global flag) is broken for any account that was ever derivable-AA-address-eligible.

This contradicts the documented intent in the code comment ("aa verifies authentication itself") which assumes AA verification for a *given* sender is equivalent to key-based verification for that *same* sender — that equivalence silently fails once the account has rotated to a different scheme, because nothing invalidates the old derivable capability.

### Impact Explanation
For an account that was created via (or is address-collidable with) a derivable-AA `(function_info, public_key)` pair, whoever holds the corresponding signing capability for that `authenticate` function can still produce a fully-admitted transaction for that account's current address — bypassing the authentication key that the account owner believes is now authoritative (`AccountResource.authentication_key` after rotation). This breaks the sender/signer binding guarantee that admission is expected to enforce: "the entity that can currently move this account's assets is whoever controls `authentication_key`." It resurrects an authentication path the owner believed was revoked by rotation.

### Likelihood Explanation
Exploitability strictly requires:
1. `is_derivable_account_abstraction_enabled()` is true (mainnet feature-flag dependent).
2. The target account's address is derivable from some `(function_info, public_key)` combination for which a registered derivable dispatch function exists, and the attacker holds the signing material for that `authenticate` function.

For an account that was genuinely created through derivable AA and later rotated away, condition 2 is trivially satisfied by the **original key material the account owner themselves used to create the account** — this is not a "leaked key" from someone else, it is the account's own historical AA key that the owner assumed was superseded by rotation. That nuance is important for triage: this is not a cross-account/unprivileged-attacker-with-nothing scenario in the strictest sense, but rather a broken revocation guarantee upon rotation.

### Recommendation
Scope the derivable-AA branch of `allow_missing_txn_authentication_key` to the sender, not just the global flag — e.g., require that the account's current `AccountResource.authentication_key` still corresponds to a derivable-AA authentication key (there currently is no such per-account state to check against, which is itself the gap), or invalidate/require re-binding of derivable-AA eligibility whenever `rotate_authentication_key*` changes the account away from a derivable scheme.

### Proof of Concept
Conceptual outline (could not fully execute a live PoC given tool-budget/index limits, see caveat below):
1. Create account A via derivable AA using `derive_account_address(function_info, pubkey)`, so `A.address` binds to `(function_info, pubkey)`.
2. Owner rotates `A`'s `AccountResource.authentication_key` to a plain Ed25519 key via `rotate_authentication_key`/`rotate_authentication_key_call` — address unchanged.
3. With `is_derivable_account_abstraction_enabled()` still true and the derivable dispatch function still registered, submit a transaction from sender `A` using `AccountAuthenticator::Abstract { auth_data: DerivableV1 { ..., abstract_public_key: pubkey } }` signed with the *original* AA key material.
4. `account_abstraction::authenticate` succeeds (address-derivation check passes; it never looks at `A`'s current `authentication_key`).
5. `transaction_data.authentication_proof().optional_auth_key()` yields the derivable-derived key (or, depending on code path, may still be treated via the "AA verifies itself" branch), and `prologue_common`'s `allow_missing_txn_authentication_key(A)` returns `true` purely due to the global flag — the transaction is admitted despite `A`'s authentication key no longer being the AA scheme.

### Caveat / what remains unverified
I ran out of tool iterations before confirming two adjacent details that affect exact severity:
- Whether `check_authenticator_features()` (called at the very start of `AptosVM::validate_transaction`, before `check_signature()`) further restricts which authenticator variants (e.g., bare `NoAccountAuthenticator` as *primary sender*, as opposed to a genuine `Abstract{DerivableV1}` authenticator) are permitted — this would matter for a stronger variant of this bug where an attacker with *no* key material at all (not even the original AA key) tries to submit `NoAccountAuthenticator` and rely solely on the global flag.
- The concrete implementation of `AccountAuthenticator::verify` and `AuthenticationProof::optional_auth_key` for the `NoAccountAuthenticator`/`AuthenticationProof::None` case, which I could not retrieve within the available searches.

The finding as scoped to the **DerivableV1 abstract-authenticator + post-rotation account** case is supported directly by the code cited above and is valid; the more severe "any account, any attacker, zero signature" variant implied by the literal PoC wording in the question is plausible but not fully confirmed against `check_authenticator_features`.

        account: signer,
        func_info: FunctionInfo,

        let master_signer_addr = signer::address_of(&account);
