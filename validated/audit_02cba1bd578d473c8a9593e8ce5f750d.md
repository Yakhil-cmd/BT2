### Title
Permanent device pairing secret disclosed in plaintext to arbstore server during arbiter dispute - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js`'s `openDispute()` transmits the user's **permanent** pairing secret (`my_pairing_code`/`peer_pairing_code`) as a plaintext field in the JSON body of an HTTP request to an external arbstore server, rather than as a one-time, dispute-scoped credential. This mirrors the CVE-2018-1192 bug class: a long-lived authentication credential (there, a UAA session ID; here, a permanent device-pairing secret) is exposed outside its trust boundary (audit logs there, an external HTTP endpoint/its logs here), enabling an attacker who obtains it to impersonate the victim device.

### Finding Description
The permanent pairing secret is generated once per wallet and cached indefinitely via `getOrGeneratePermanentPairingInfo()`: [1](#0-0) 

This secret alone is sufficient for anyone who possesses it to pair as a trusted correspondent of the device — `handlePairingMessage()` accepts any peer presenting a valid, non-expired `pairing_secret` and adds them as a confirmed correspondent: [2](#0-1) 

In `arbiter_contract.js`, `openDispute()` builds `my_pairing_code = device_pubkey@hub#pairing_secret` from this **permanent** pairing info and includes it — along with the peer's pairing code — as plaintext top-level fields (`my_pairing_code`, `peer_pairing_code`) in the JSON payload POSTed to the arbstore's `/api/dispute/new` endpoint. Only the contract title/text/party-name fields are wrapped via `device.createEncryptedPackage`; the pairing codes are not: [3](#0-2) 

Because this is the permanent pairing secret (not a fresh, dispute-scoped one-time secret via `startWaitingForPairing()`), any exposure of it — through arbstore-side request logging, a compromised/malicious arbstore, or interception — grants the holder the ability to indefinitely pair as a correspondent of the disputant's wallet, exactly analogous to how a leaked UAA session ID lets an attacker impersonate the session owner.

### Impact Explanation
An attacker who recovers the leaked permanent pairing secret (e.g., from arbstore server logs, a compromised arbstore backend, or a MITM before/after TLS termination at a proxy) can pair as a trusted correspondent of the victim's wallet without the victim's consent or knowledge. As a trusted paired correspondent, the attacker can subsequently send crafted device messages (e.g., fake `arbiter_contract_offer`, payment requests, or private-asset chain messages) that the victim's wallet treats as coming from a legitimate paired device, which can be leveraged toward fund loss (e.g., social-engineered payments, malicious contract offers) — the same "impersonation via credential leak" root cause as CVE-2018-1192.

### Likelihood Explanation
Any user who opens an arbiter dispute (a normal, unprivileged wallet action reachable by any private-payment counterparty in an arbiter-mediated contract) triggers this exposure automatically; no attacker action beyond having engaged in (or observing) the dispute flow or the arbstore's logs is required to obtain the secret.

### Recommendation
Do not reuse the permanent pairing secret for arbstore dispute contact. Generate a short-lived, dispute-scoped pairing secret via `startWaitingForPairing()` for each dispute submission, and encrypt `my_pairing_code`/`peer_pairing_code` within the existing `encrypted_contract` package rather than sending them as plaintext top-level JSON fields to the arbstore endpoint.

### Proof of Concept
1. User A and User B create and accept an arbiter contract via `createAndSend`/`respond`, each embedding their permanent pairing code (`device.getOrGeneratePermanentPairingInfo`).
2. User A calls `openDispute(hash, cb)`; the code builds `data.my_pairing_code`/`data.peer_pairing_code` in plaintext and POSTs it to the arbstore's `/api/dispute/new`. [4](#0-3) 
3. Anyone with read access to the arbstore's request logs/storage extracts `device_pubkey@hub#pairing_secret` for either party.
4. Using `sendPairingMessage`/pairing flow, the attacker presents that `pairing_secret` to the victim's hub; `handlePairingMessage` accepts it and adds the attacker as a confirmed correspondent device of the victim, since the permanent secret never expires and is not tied to a single use. [5](#0-4)
