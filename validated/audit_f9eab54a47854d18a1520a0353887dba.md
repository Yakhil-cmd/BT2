### Title
Cross-repository SHA collision lets a forged GitHub status webhook satisfy `MergeRequest#all_status_checks_passed?` and trigger an unauthorized `merge_request.merge!` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/merge_request.rb])

### Summary
`StatusHandler#process` attaches an incoming GitHub `status` webhook to *every* local `Commit` row whose `sha` matches the payload, with no check that the webhook's `repository.full_name` equals the repository owned by that commit's `Stack`. If an attacker can make GitHub sign a genuine `status` event for a SHA that also exists as the `head` of a victim `MergeRequest` (e.g., by reproducing the identical commit object in a repository they control), the forged status is persisted as a real `Shipit::Status` row on the victim's commit, which `MergeRequest#all_status_checks_passed?` and `ProcessMergeRequestsJob#perform` will happily consume to call `merge_request.merge!`.

### Finding Description
The broken binding is: `params.repository.full_name` (the repo that actually ran CI and emitted the webhook) MUST equal `merge_request.stack.repository.full_name` (the repo whose PR is about to be merged). This equality is never checked.

`StatusHandler#process` resolves target commits purely by SHA, globally: [1](#0-0) 
`Commit.where(sha: params.sha)` is not scoped to the repository named in the webhook payload at all — any commit row in any stack sharing that SHA gets `commit.create_status_from_github!(params)` called on it, which persists a real `Shipit::Status` record tied to that commit/stack.

`MergeRequest#all_status_checks_passed?` then evaluates readiness purely from locally stored statuses on `head`: [2](#0-1) 
`head.statuses_and_check_runs` is simply `statuses + check_runs` — i.e., every `Status`/`CheckRun` row ever attached to that `Commit` id, with no origin/repository filtering: [3](#0-2) 

`ProcessMergeRequestsJob#perform` refreshes the merge request, then merges as soon as `all_status_checks_passed?` returns true: [4](#0-3) 
Note that `merge_request.refresh!` calls `head.refresh_statuses!`, which only **adds** statuses fetched from the real GitHub API for the victim's own repo (via `find_or_create_by!` in `Status.replicate_from_github!`); it never deletes or invalidates the attacker-forged row already inserted by the webhook: [5](#0-4) [6](#0-5) 

So the forged status survives the refresh and remains part of the set fed into `StatusChecker` (a `Status::Group` subclass) for the required/ignored-context evaluation defined in the stack's deploy spec: [7](#0-6) 

If the attacker's forged status covers a `required_statuses` context (or simply reports `success` for a context the victim repo hasn't reported failure/pending on yet), `StatusChecker#success?` can return true even though the victim repo's own CI never passed for that commit, and `merge!` proceeds to call `stack.github_api.merge_pull_request` on the victim's PR: [8](#0-7) 

No existing guard catches this: `verify_signature` only authenticates that the payload was signed by *some* GitHub organization's registered webhook secret (`Shipit.github(organization: repository_owner)`), it does not bind the payload's `repository` field to the specific stack/repo being updated: [9](#0-8) 
and `StatusHandler`'s `params` schema does not even require/validate the `repository` field against the target commit's stack: [10](#0-9) 

### Impact Explanation
A successfully forged status causes `stack.github_api.merge_pull_request` to be invoked on a repository the attacker does not control, merging a pull request whose CI never actually passed on that repository. This is an unauthorized merge — Critical severity per the stated impact categories ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The attack is repeatable against any stack/repository as long as the SHA-collision precondition holds, and it crosses tenant boundaries: the attacker's own repo's CI result is trusted for a completely different repository's merge decision.

### Likelihood Explanation
The exploit requires: (1) a signed, valid `status` webhook reaching `WebhooksController#create` — feasible for the attacker only if they can get GitHub to sign such an event for an organization Shipit trusts (typically requires a repo under that same GitHub App/organization installation); (2) a victim `MergeRequest` in `pending` state whose `head` SHA the attacker can reproduce byte-for-byte in their own repository (git SHAs are content-addressed, so re-pushing an identical commit object — e.g., cherry-picking a public PR branch — reproduces the same SHA); (3) the forged status context aligning with the deploy spec's required/ignored status configuration. Given these preconditions (explicitly granted in the question), the attacker cost is low — a single webhook POST — and the technique is repeatable per matching precondition instance.

### Recommendation
In `StatusHandler#process`, scope the `Commit.where(sha: params.sha)` lookup to commits whose `stack.repository.full_name` matches `params.repository.full_name` (or `repository.owner.login`/`repository.name`) from the webhook payload, mirroring the repository binding already enforced elsewhere (e.g., `PushHandler`). Reject or ignore statuses whose payload repository does not match the target commit's own stack repository before calling `commit.create_status_from_github!`.

### Proof of Concept
Minitest plan (webhook + job integration test, no live GitHub):
1. Set up victim stack `stack_a` (repo `victim/repo`) with a `Commit` `head` having SHA `S`, and a `MergeRequest` in `merge_status: 'pending'` referencing that `head`, with deploy spec requiring status context `ci/travis`. Ensure `head.statuses` currently has no `success` status for `ci/travis` (unresolved/pending).
2. Set up attacker stack `stack_b` (repo `attacker/repo`), same GitHub organization (so `verify_signature` passes), with its own `Commit` sharing the identical SHA `S` (simulating the reproduced commit object).
3. Stub `GithubHook#verify_signature`/`verify_webhook_signature` to return true (as done in `WebhooksControllerTest`), then `POST /webhooks` with `X-Github-Event: status`, body `{ sha: S, state: 'success', context: 'ci/travis', repository: { full_name: 'attacker/repo', owner: { login: <org> } } }`.
4. Assert: `stack_a`'s `head.statuses.where(context: 'ci/travis', state: 'success')` now exists (`Commit.where(sha: S)` matched both commits — demonstrating `params.repository.full_name` ('attacker/repo') != `merge_request.stack.repository.full_name` ('victim/repo') yet the status was still attached).
5. Call `merge_request.reload.all_status_checks_passed?` and assert it returns `true`.
6. Stub `stack_a.github_api` and assert `ProcessMergeRequestsJob.new.perform(stack_a)` results in `merge_pull_request` being called (e.g., `stack_a.github_api.expects(:merge_pull_request)`), proving the merge fires off a status that never originated from `victim/repo`.

      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,

        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end

        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
