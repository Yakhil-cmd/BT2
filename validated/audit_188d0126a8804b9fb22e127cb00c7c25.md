### Title
Global (repository-unscoped) commit-status webhook write breaks the "authenticated repository ⇄ written commit" binding, enabling forged CI status and unauthorized deploys - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the GitHub App configured for the *owning organization/repository named in the payload*, but the `StatusHandler` that processes `status` events never re-checks that binding when performing its write: it looks up commits by raw SHA across the **entire** Shipit database, with no scoping to the repository/organization that was actually authenticated. This breaks the equality `organization/repository that authenticated == repository whose data gets written`.

### Finding Description
`WebhooksController` selects the GitHub App/secret used to verify the HMAC signature from fields taken directly from the (still-unverified) JSON body: [1](#0-0) [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event)` dispatches the same raw `params` hash to every registered handler, with no further validation that the "repository" the handler acts on matches the "repository" whose secret validated the signature: [3](#0-2) 

Every other handler in the codebase explicitly re-derives and scopes its writes to the repository named in the payload, e.g. `PushHandler` scopes to `stacks` derived from `repository.full_name`, and the base `Handler` class exists specifically to provide that scoping helper: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does not require a `repository` field at all in its parameter schema, and performs its write with a **global, unscoped** `Commit.where(sha: params.sha)` lookup, then writes attacker-supplied `state`, `description`, `target_url`, and `context` onto every matching `Commit` row it finds, regardless of which stack/repository that commit belongs to: [6](#0-5) 

Because the SHA lookup is global, a `status` event that is legitimately signable for one organization/repository (the one whose webhook secret authenticated the request) can still overwrite the CI status of a `Commit` row belonging to a **completely different** stack/repository tracked by the same Shipit instance — as long as that different stack happens to contain a `Commit` with the same SHA (e.g., shared history between a fork and its upstream, a commit cherry-picked/merged across repos, or any accidental/deliberate SHA collision across the repositories hosted on the same Shipit deployment). The equality that should hold — "the repository whose secret verified the signature" == "the repository whose commit gets its status mutated" — is not enforced anywhere in this path.

### Impact Explanation
Shipit's CI gating (`ci.require`) and continuous-deployment/merge-queue automation rely on `Commit` status rows created via this exact code path to decide whether a commit is `deployable?`. By forging a `status` webhook event that is validly signed for a repository/org the attacker controls (or for which they only need minimal legitimate status-reporting access, e.g. via a CI bot on one low-value repository), the attacker can inject a fabricated "success" status onto a `Commit` row that in fact belongs to an unrelated, higher-privilege stack on the same Shipit instance. This can satisfy the target stack's CI requirements and trigger an **unauthorized deploy** of a commit that was never actually reviewed or passed the target repository's real CI — a Critical-severity outcome (unauthorized deploy) under the program's impact classification.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a validly-signed `status` webhook (i.e., controlling or compromising a GitHub App/webhook secret for at least one organization/repository configured in the shared Shipit instance) and on a SHA collision existing between that repository and the victim stack (realistic for forks, mirrors, or repos sharing history). This is a real but narrower path than a full authentication bypass — it requires some existing standing (one onbo­arded, less-privileged org/repo) rather than none, and a matching SHA — but it does not require compromising `webhook_secret`, `api_clients_secret`, a Shipit session, or repository write access to the *victim* repository, satisfying the engine's own trust boundary rather than an external precondition explicitly excluded by scope.

### Recommendation
`StatusHandler` (and any other handler that mutates state) must scope its lookup to the repository actually authenticated for the request, not perform a global SHA lookup. Require the `repository.full_name` field in the handler's parameter schema, and constrain the query, e.g. `stacks.commits.where(sha: params.sha)` (using the `Handler#stacks`/`repository_name` helper already provided by the base class), so a commit status can only be written for the repository whose secret validated the webhook signature.

### Proof of Concept
1. Attacker has legitimate ability to fire a `status` webhook signed for `attacker-org/low-value-repo` (e.g., they operate a CI bot with `statuses:write` on that one tracked repository, or that org's `webhook_secret` is otherwise obtainable through normal, non-privileged means for that repo).
2. Attacker (or their CI bot) discovers/engineers a commit SHA `S` that also exists as a `Commit` row belonging to `victim-org/critical-repo`'s Shipit stack (e.g., a shared ancestor commit from when `critical-repo` was forked from, or merged with, `low-value-repo`).
3. Attacker POSTs (or has their CI system POST) a `status` event: `{"sha": "S", "state": "success", "context": "ci/required-check", ...}`, correctly HMAC-signed with `attacker-org`'s webhook secret.
4. `WebhooksController#verify_signature` resolves and validates the signature against `attacker-org`'s `GitHubApp` config — this succeeds because the payload is genuinely from that org.
5. `StatusHandler#process` executes `Commit.where(sha: 'S')`, which also matches the `Commit` row in `victim-org/critical-repo`'s stack, and calls `create_status_from_github!` on it, writing the forged `"success"` status.
6. If `victim-org/critical-repo`'s stack has `continuous_deployment: true` or is otherwise gated only by `ci.require` on that context, the forged status can now let the commit be deployed without ever having passed the victim repository's real CI.
