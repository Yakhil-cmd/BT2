### Title
API client scoped to one stack can read CI/build status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` enforces the `read:stack` permission bit but resolves the target `Stack` with an unscoped lookup, breaking the binding: *the stack a token authorizes* (`ApiClient#stack_id`) must equal *the stack the request touches* (`params[:stack_id]`).

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column, and this scoping is meant to be the sole per-resource authorization mechanism, since `check_permissions!` only checks a global permission string, not a specific resource: [1](#0-0) 

`Api::BaseController` implements this scoping via the `stacks`/`stack` helpers, which filter by `current_api_client.stack_id` before resolving `params[:stack_id]`: [2](#0-1) 

`CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving the stack directly from `Stack.from_param!(params[:stack_id])` with no reference to `current_api_client.stack_id`: [3](#0-2) 

Since `require_permission :read, :stack` (declared at the top of the controller) only verifies that the token carries the string `"read:stack"` in its `permissions` array — it never compares against the resolved stack — any token holding that generic permission, even one deliberately scoped by an admin to a single stack via `ApiClient#stack_id`, can supply an arbitrary `stack_id` in the URL and receive that other stack's latest deploy/rollback status. [4](#0-3) 

Every other API resource controller (e.g. `StacksController`, `LocksController`) relies on the `stacks`/`stack` helper from `BaseController`, so they correctly stay within the token's authorized scope; `CCMenuController` is the outlier that reimplements stack resolution and drops the scoping check.

### Impact Explanation
This breaks the intended trust boundary between a per-stack scoped `ApiClient` and stacks outside its scope, allowing unauthenticated read of another stack's build/deploy state (last deploy id, status, timestamp) through the CCMenu XML feed — an authorization escalation that lets a minimally-privileged, single-stack token enumerate and read the CI status of every stack in the Shipit instance.

### Likelihood Explanation
Any deployment that issues stack-scoped API tokens (a documented, expected use case for `ApiClient.stack_id`) is affected. Exploitation requires only knowledge of another stack's identifier (owner/repo/environment triple), which is often predictable or discoverable, and a single GET request to `/api/stacks/*stack_id/ccmenu`.

### Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks`/`stack` resolution from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so a stack-scoped token cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to Stack A: `stack_id = A.id`, `permissions = ["read:stack"]`.
2. Using that client's `authentication_token`, request:
   `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<tokenA>`
   where `repo-B/env-B` identifies Stack B, a stack the token was never scoped to.
3. `authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` passes (token has `read:stack`), and `stack` resolves Stack B directly via `Stack.from_param!`, returning Stack B's CI status in the XML response — despite the token being scoped only to Stack A.
