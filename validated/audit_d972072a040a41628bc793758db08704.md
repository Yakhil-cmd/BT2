### Title
Cross-organization webhook forgery via unbound signature-selection field vs. repository-acted-upon field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, the field used to select which GitHub App/webhook secret verifies a webhook's signature (`repository.owner.login`, or `organization.login`) is not the same field that downstream handlers use to determine which repository/stack to act on (`repository.full_name`). Because both fields live inside the same attacker-influenced JSON body, a party who legitimately controls one organization's webhook secret can craft a payload that verifies successfully against their own organization's secret while `repository.full_name` points at a stack belonging to a different, victim organization.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the `webhook_secret`) to check the signature against based on `repository_owner`, itself read straight out of the untrusted payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` supports a multi-tenant secrets schema where each GitHub organization has its own independent `webhook_secret`: [3](#0-2) 

Once signature verification passes, `create` dispatches the raw payload to event handlers, which look up the target stack/repository using a **different** field, `repository.full_name`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` simply splits `"owner/name"` and looks up any repository row by owner/name, with no cross-check that this owner matches the organization whose secret validated the signature: [5](#0-4) 

The binding that is broken is: **the organization whose secret authenticated the request ≠ the repository that is actually written to**. The HMAC signature only proves the raw bytes weren't altered by a third party — it says nothing about whether `repository.owner.login` and `repository.full_name` refer to the same organization. An org administrator who legitimately possesses a valid `webhook_secret` for their own organization ("OrgA") can set `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against OrgA's secret, which they control) while setting `repository.full_name = "OrgB/victim-repo"` (a repository belonging to a completely different, unrelated organization "OrgB" that is also registered in the same Shipit instance).

Concrete exploitable handlers that key purely off `full_name`/`sha` without any further authorization check against the actual owning organization's secret:
- `StatusHandler`, which writes a `Status` object directly from attacker-supplied fields (`state`, `description`, `target_url`, `context`, `created_at`) onto any `Commit` matching an attacker-chosen `sha`: [6](#0-5) 
- `PushHandler`, which triggers `GithubSyncJob`/`stack.sync_github` for any stack under the spoofed `full_name`'s repository/branch: [7](#0-6) 
- Pull-request handlers (`AssignedHandler`, `EditedHandler`, `LabeledHandler`, `ReopenedHandler`, etc.) that resolve `repository` purely from `params.repository.full_name`, independent of the org used to verify the signature: [8](#0-7) 

### Impact Explanation
This crosses the "cross-repository writes" boundary explicitly called out as Critical: an entity that only controls a webhook secret for its own organization/repo (a legitimate but limited GitHub App/webhook credential holder for Org A) can forge webhook events that mutate state (commit statuses, PR label/state tracking, triggering `GithubSyncJob` deploy pipelines) belonging to Org B's stacks/repositories, without ever knowing Org B's `webhook_secret`. Depending on which handler is reached, this can falsify CI status used to gate deploys (`StatusHandler`), or desynchronize/trigger sync jobs against another organization's stack (`PushHandler`), affecting deploy/rollback decision inputs for repositories the attacker does not own.

### Likelihood Explanation
Requires the Shipit instance to be configured with the multi-organization secrets schema (`secrets.github` keyed by organization, each with its own `webhook_secret`), and requires the attacker to legitimately hold a valid webhook secret for at least one organization configured on that instance (e.g., they are an admin of one org onboarded to a shared Shipit deployment that also serves other orgs). This is a realistic scenario for shared/multi-tenant Shipit deployments (which the `github_organizations`/`github_app_config` code explicitly supports) but not for single-organization deployments, since there `github_default_organization` short-circuits to a single shared config and the owner field bypass has no effect. Likelihood is therefore conditioned on multi-org configuration.

### Recommendation
Bind the organization used for signature verification to the same field(s) used for repository resolution, and re-validate that they agree before dispatching to handlers:
- In `WebhooksController#verify_signature`, additionally derive/require the acting repository owner from `repository.full_name`'s owner segment (not solely `repository.owner.login`/`organization.login`), and reject the request (422) if the two disagree.
- In `Handler#repository_name`/`stacks`, cross-check that the resolved `Repository#owner` matches the organization whose secret validated the current request (e.g., pass the verified organization through the pipeline and assert equality before acting).

### Proof of Concept
1. Shipit is configured multi-tenant with `secrets.github["orga"]` and `secrets.github["orgb"]`, each with a distinct `webhook_secret`. Org B has a repository (`orgb/victim-repo`) registered as a Shipit stack.
2. Attacker is a legitimate admin of Org A and knows/controls Org A's `webhook_secret` (e.g., they configured Org A's GitHub App webhook themselves).
3. Attacker crafts a `status` (or `push`) webhook payload:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature` using Org A's `webhook_secret` over this exact raw body and POSTs it to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orga")` (from `repository.owner.login`) and the signature verifies successfully because it was HMAC'd with Org A's own secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)...create_status_from_github!(params)`, writing an attacker-controlled status onto a commit belonging to `orgb/victim-repo`, a repository the attacker has no legitimate webhook credential for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
