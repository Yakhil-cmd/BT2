### Title
Missing lock on `dryRunPrimaryAATrigger` allows a race on the shared `assocUnstableUnits` cache leading to a crash on unit graph state — ([File: aa_composer.js])

### Summary
`aa_composer.js` exposes two independent code paths that mutate the same global, process-wide, in-memory unit-graph caches (`storage.assocUnstableUnits`, and friends) while composing/reverting Autonomous Agent (AA) response units: the real trigger-execution pipeline (`handleAATriggers`/`handlePrimaryAATrigger`), which is serialized behind `mutex.lock(['aa_triggers'], …)`, and the "dry run" pipeline (`dryRunPrimaryAATrigger`), which is invoked directly for every freshly-received, unprivileged unit that pays an AA and is **not** protected by that same lock. Both paths ultimately call `revertResponsesInCaches()`, which unconditionally dereferences a cache entry it assumes still exists. This is the closest structural analog in this codebase to the reported Chrome "Use after free in Network API" bug class: a reference to a shared, mutable in-memory object that can be concurrently invalidated/removed by another asynchronous flow before it is dereferenced.

### Finding Description
`dryRunPrimaryAATrigger` is triggered for every unit an unprivileged peer posts, as soon as it contains a payment output to a known AA address, whenever the node runs with `conf.bDryRunNewTriggers` enabled: [1](#0-0) 

It runs completely outside of the `'aa_triggers'` mutex that guards the real AA-execution pipeline: [2](#0-1) 

compared with the real pipeline, which explicitly serializes on `['aa_triggers']`: [3](#0-2) 

Both pipelines execute `handleTrigger`, which for bounces/dry-run completion calls `revertResponsesInCaches(arrResponses)`: [4](#0-3) 

`revertResponsesInCaches` reads and immediately dereferences an entry from the shared global cache `storage.assocUnstableUnits` without checking that it still exists: [5](#0-4) 

Because `dryRunPrimaryAATrigger` does not hold the `'aa_triggers'` lock that the "real" trigger/stabilization pipeline uses, it can run concurrently with `handlePrimaryAATrigger`/`handleAATriggers`, and both flows create/forget entries in the same `storage.assocUnstableUnits` map through `storage.forgetUnit`/`fixIsFreeAfterForgettingUnit`, and through the general write-failure recovery path in `writer.js`, which wipes memory caches on error: [6](#0-5) 

If the entry for the dry run's own newly-composed response unit is removed (forgotten/reset) by the concurrently-running, unrelated trigger-execution flow before `revertResponsesInCaches` runs, `storage.assocUnstableUnits[first_unit]` is `undefined`, and `objFirstUnit.parent_units` throws an uncaught `TypeError` deep inside nested asynchronous callbacks that are not wrapped in any try/catch in this call chain — crashing the full node process.

### Impact Explanation
This is reachable by any unprivileged party: simply sending bytes/an asset to an AA address in an ordinary unit is enough to make the receiving node run `dryRunPrimaryAATrigger` against attacker-influenced trigger/AA state (when `conf.bDryRunNewTriggers` is enabled). If an attacker can additionally cause real AA trigger execution to happen concurrently (e.g., by having other, unrelated AA-triggering units stabilize around the same time, or by causing an unrelated `saveJoint` failure that invokes `storage.resetMemory()`), the resulting crash of the node process constitutes a remote, unauthenticated denial of service. On many nodes simultaneously, this can degrade the network's ability to validate/confirm new units — one of the accepted high-impact outcomes for this exercise.

### Likelihood Explanation
Likelihood is moderate: the race depends on the timing of two independently-scheduled asynchronous flows (the unlocked dry run vs. the locked real pipeline) that both mutate `storage.assocUnstableUnits`, and on the node running with `conf.bDryRunNewTriggers` enabled. I was **not able to verify within the available tool budget** (a) whether `bDryRunNewTriggers` defaults to `true` for full nodes (would need `conf.js`, which I did not have time to inspect), or (b) the exact set of concurrent write/forget paths inside `handleTrigger`'s response-unit composition (`sendUnit`, `composer.js`) that would most reliably trigger the missing-entry condition. These would need follow-up verification before treating this as a fully proven, deterministically-reproducible exploit rather than a plausible race condition rooted in a concrete missing-lock + missing-null-check pair.

### Recommendation
- Protect `dryRunPrimaryAATrigger` with the same `mutex.lock(['aa_triggers'], …)` (or an equivalent shared lock) used by `handleAATriggers`, so dry-run and real AA-trigger execution never touch `storage.assocUnstableUnits`/related caches concurrently.
- Harden `revertResponsesInCaches` in `aa_composer.js` to check that `storage.assocUnstableUnits[first_unit]` exists before dereferencing `parent_units`, and handle the missing-entry case gracefully instead of crashing.
- Audit all other unlocked accessors of `storage.assocUnstableUnits`/`assocStableUnits`/`assocBestChildren` for similar unchecked-existence assumptions, given `storage.resetMemory()` can clear these caches asynchronously from an unrelated write-failure path.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to tool-time limits):
1. Run a full node with `conf.bDryRunNewTriggers = true`.
2. Attacker A posts unit `U1` with a payment output to AA address `X` (any ordinary AA that produces at least one response unit and can also fail/bounce after producing an initial response, e.g. a chained/secondary-AA scenario that hits `revert()`), causing the node to invoke `aa_composer.dryRunPrimaryAATrigger` for `U1` outside of the `'aa_triggers'` lock.
3. Concurrently (e.g., via other units the attacker also posts, that stabilize and trigger real AA execution, or via any unrelated `saveJoint` failure that calls `storage.resetMemory()`), force `handleAATriggers`/`writer.js`'s error path to run and forget/reset `storage.assocUnstableUnits` entries while step 2's dry run is still in-flight.
4. When the dry run's `handleTrigger` calls `revert()` → `revertResponsesInCaches(arrResponses)`, `storage.assocUnstableUnits[first_unit]` is missing, and `objFirstUnit.parent_units` throws, crashing the node process (`aa_composer.js:1900-1916`).

function revertResponsesInCaches(arrResponses) {
	// remove the rolled back units from caches and correct is_free of their parents if necessary
	console.log('will revert responses ' + JSON.stringify(arrResponses, null, '\t'));
	var arrResponseUnits = [];
	arrResponses.forEach(function (objAAResponse) {
		if (objAAResponse.response_unit)
			arrResponseUnits.push(objAAResponse.response_unit);
	});
	console.log('will revert response units ' + arrResponseUnits.join(', '));
	if (arrResponseUnits.length > 0) {
		var first_unit = arrResponseUnits[0];
		var objFirstUnit = storage.assocUnstableUnits[first_unit];
		var parent_units = objFirstUnit.parent_units;
		arrResponseUnits.forEach(storage.forgetUnit);
		storage.fixIsFreeAfterForgettingUnit(parent_units);
	}
}
