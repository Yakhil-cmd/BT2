### Title
Webhook signature is verified against the payload's `repository.owner.login`, but event handlers act on the (independently attacker-controlled) `repository.full_name` field — allowing forged GitHub events for any tracked repository ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check passes, the *same raw JSON body* is handed unmodified to `Shipit::Webhooks::Handlers::Handler`, whose `repository_name` method reads a **different** field — `payload.dig('repository', 'full_name')` — to decide which `Repository`/`Stack` the event applies to via `Repository.from_github_repo_name`. Because `owner.login` and `full_name` are two independent, attacker-supplied JSON fields inside the same POST body, an attacker who can produce a valid signature for *any one* configured GitHub organization can set `full_name` to point at a repository belonging to a completely different, unrelated organization, and have Shipit process the forged event (push/status/check_suite/membership/pull_request) against that other organization's stack.

### Finding Description
The webhook signature check is: [1](#0-0) 

`repository_owner` is read straight out of the untrusted JSON body: [2](#0-1) 

This value only selects which organization's `webhook_secret` (`Shipit.github(organization: repository_owner)`) is used to validate `X-Hub-Signature` via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Once `verified` is true, `create` dispatches the **entire raw `params`** to the registered handlers: [4](#0-3) 

But every handler resolves the target `Repository`/stacks using a *different* field of the same payload — `repository.full_name` — not `repository.owner.login`: [5](#0-4) 

`Repository.from_github_repo_name` performs a global, unscoped lookup across the entire Shipit install (all organizations), keyed purely on the owner/name parsed out of `full_name`: [6](#0-5) 

Concretely, `PushHandler` triggers `stack.sync_github` (arbitrary sha injection into a git ref) and `StatusHandler` creates a CI status object for any commit matching `params.sha` regardless of repository, using values taken entirely from the forged body: [7](#0-6) [8](#0-7) 

**The broken binding, stated as an equality that the code assumes but never enforces:**
`organization used to select/verify the webhook_secret (payload.repository.owner.login)` **should equal** `organization/repository the handler actually mutates (payload.repository.full_name)`.

Before the attack: for a legitimate GitHub-originated webhook, GitHub itself fills in both fields consistently for the real event repository, so they always match.

After the attack: an attacker who operates (or has compromised) any single organization/GitHub App instance registered in this Shipit deployment — and therefore legitimately possesses that organization's `webhook_secret` (it is handed to the org administrator during onboarding, per `docs/setup.md`) — can POST directly to `/webhooks` with a body whose `repository.owner.login` is their own org (so the signature check, scoped to that org's secret, passes) while `repository.full_name` names a repository belonging to any *other* organization tracked by the same Shipit instance. The lookup in `Handler#stacks` / `Repository.from_github_repo_name` is global and ignores which organization authenticated, so the forged event is applied to the victim stack.

### Impact Explanation
This crosses exactly the "organization that authenticated versus the repository that is written" boundary called out as in-scope. Concretely, with a signature valid only for the attacker's own organization, the attacker can:
- Forge `status` events (`StatusHandler`) to mark arbitrary commits on a *victim* repository's stack as CI-green, which is the gate Shipit's continuous-deployment / merge-queue logic uses to decide whether a stack auto-deploys or a PR auto-merges — i.e., this can produce an **unauthorized deploy** on a stack the attacker has no legitimate access to.
- Forge `push` events (`PushHandler`) to make Shipit believe a specific arbitrary SHA is now the head of a victim stack's branch, triggering `sync_github` against a commit the attacker chose.
- Forge `check_suite` / `membership` events against unrelated organizations' data.

This matches the High-impact category "escalation into unauthorized deploy" by breaking a trust boundary (webhook authenticity is per-organization, but the acted-upon repository identity is taken from an unauthenticated companion field in the same payload) — directly analogous to the referenced report's pattern of granting/approving permission for one identity while a different, uncoupled identity/action is actually exercised (`crocSwapAddress` approved as spender in principle but never actually approved for the `ASDUSDC` that gets swapped).

### Likelihood Explanation
Requires only that the attacker control or have knowledge of the `webhook_secret` for *any single* organization onboarded to this Shipit instance (a standard, documented credential for any customer/org admin per `docs/setup.md`, not a privileged Shipit account, `ApiClient` token, or GitHub App private key on the victim side). The rest — crafting the raw JSON body and computing an HMAC-SHA1 with a secret the attacker legitimately possesses — is trivial and requires no interception, no social engineering, and no access to the victim organization at all. This is realistic in any multi-tenant/multi-org Shipit deployment (the engine explicitly supports per-organization GitHub Apps/secrets via `Shipit.github(organization:)`).

### Recommendation
Bind the two fields together before dispatching to handlers: in `WebhooksController#verify_signature` (or in `Handler#initialize`), assert that the organization used to resolve the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` (and in `organization.login` for membership events), rejecting the request (422) on mismatch. Alternatively, scope `Repository.from_github_repo_name`/`Handler#stacks` lookups to the verified organization rather than performing a global lookup.

### Proof of Concept
1. Attacker administers organization `attacker-org`, which is registered in this Shipit instance with a known `webhook_secret` (`S`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<...>
```
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies the signature against `S` — passes, per [9](#0-8) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, finds the victim's stack (no relation to `attacker-org`), and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")`, per [7](#0-6)  and [6](#0-5) .
6. The same technique with `X-Github-Event: status` and a known victim commit SHA forges a green CI status on the victim's stack via `StatusHandler`, per [8](#0-7) , potentially triggering an unauthorized continuous deployment/merge on that stack.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
