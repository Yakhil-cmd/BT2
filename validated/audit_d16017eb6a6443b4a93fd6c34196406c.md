### Title
Weak/No Minimum-Entropy Requirement on "hash" Secret Authentifier Enables Bypass of Address Spending Conditions - (File: definition.js)

### Summary
Address (and asset) spending conditions in ocore can include a `["hash", {hash: "<sha256-base64>"}]` leaf, which is satisfied by supplying any authentifier string whose SHA-256 digest equals the stored hash [1](#0-0) . This "secret" factor is exposed to end users through the shared-address / wallet machinery (`wallet_defined_by_addresses.js` marks a `hash` leaf as a `'secret'` signer path, and `wallet.js`'s signer treats it as a user-supplied string) [2](#0-1) [3](#0-2) . Neither `validateDefinition` nor `validateAuthentifiers` enforce any minimum length or entropy on the secret preimage — only an upper bound (`MAX_AUTHENTIFIER_LENGTH`) is checked [4](#0-3)  and the "hash" clause itself only validates that `args.hash` is a syntactically valid base64 hash [5](#0-4) .

### Finding Description
This is directly analogous to the MLflow "weak password requirements" bypass: the "password" (the secret preimage checked via `hash`) can be arbitrarily short or low-entropy, and the protocol/wallet layer imposes no minimum-strength policy on it. The public on-chain artifact is not the secret itself but its SHA-256 hash, exposed in the address definition once revealed (definitions are published when the address is first used, e.g. in `author.definition`, or shared out-of-band during shared-address setup via `handleNewSharedAddress`) [6](#0-5) . Because SHA-256 is fast to compute and there is no length/complexity floor, any unprivileged party who can see the hash (a co-signer, or anyone the definition is disclosed to, or anyone who observes it once posted on-chain) can brute-force short/guessable secrets offline and forge the authentifier that `validateAuthentifiers`'s `hash` branch accepts [1](#0-0) .

Where the `hash` factor is combined with a `sig` factor in an `and`, the impact is bypass of one authentication factor (weakening what was designed as multi-factor/2FA protection: device signature + secret). Where a `hash` condition is used alone or in an `or` branch (definitions are fully attacker/user-composable oscript, so an `["or", [["hash", {...}]]]`-style single-factor "password wallet" is a legal, validator-accepted definition), guessing the secret is sufficient to fully satisfy `validateAuthentifiers` and spend the funds, exactly mirroring "authentication bypass via weak password."

### Impact Explanation
An attacker who correctly guesses/brute-forces a weak secret gains the ability to produce a valid authentifier satisfying that `hash` condition. If this is the sole or an `or`-branch condition protecting an address, the attacker can post a spending unit that `validateAuthor`/`Definition.validateAuthentifiers` will accept as validly authenticated, resulting in unauthorized spending of the funds controlled by that address [7](#0-6) . This is concrete unauthorized fund loss, matching the "unauthorized spending" impact bar.

### Likelihood Explanation
Likelihood depends entirely on how strong a secret end users/dApp authors choose for the `hash` leaf; ocore's core validation provides no floor, so any wallet UI, contract template, or AA-adjacent tool that lets a user pick a short PIN/passphrase for this factor is directly exploitable by brute force, with no special network position needed — any observer of the definition/hash can attempt it offline.

### Recommendation
Enforce a minimum length/entropy requirement for the authentifier value used to satisfy `hash` conditions (e.g., reject `hash` conditions unless the wallet-generated secret exceeds a fixed minimum entropy, or require the `hash` args to specify an explicit KDF with configurable work factor instead of a bare `sha256` of an arbitrary string), and document/enforce minimum-strength secrets in the shared-address/2FA wallet flows in `wallet_defined_by_addresses.js` and `wallet.js`.

### Proof of Concept
1. Create a shared address whose definition is `["hash", {hash: sha256("1234")}]` (or `["or", [["hash", {hash: sha256("1234")}], [... other branch ...]]]`), as permitted by `validateDefinition`'s `hash` case (only checks `args.hash` format) [5](#0-4) .
2. Fund the resulting address.
3. An attacker who observes the definition (revealed on first spend, or shared during `handleNewSharedAddress`) computes `sha256` over a small dictionary/brute-force space and finds `"1234"` matches the stored hash.
4. Attacker submits a unit with `authentifiers: {"r": "1234"}` (or the appropriate path); `validateAuthentifiers`'s `hash` case computes `crypto.createHash("sha256").update("1234","utf8").digest("base64")` and it matches, so the condition is satisfied and the spend is accepted [1](#0-0) .
