### Title
Webhook signature verified against `organization`/`repository.owner` while the handler acts on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC `webhook_secret`) to verify a webhook against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the HMAC passes, the entire raw JSON payload — including a completely independent `repository.full_name` field — is handed unchanged to the registered handler (e.g. `PushHandler`), which looks up the target `Stack` via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')`. The signature check and the repository-resolution-for-write use two different, independently attacker-influenceable fields of the same unsigned-at-the-field-level JSON body.

### Finding Description
`verify_signature` in [1](#0-0)  resolves which organization's `GitHubApp`/`webhook_secret` to validate against using: [2](#0-1) 

The HMAC itself, per `GitHubApp#verify_webhook_signature`, is computed over the entire raw request body using the secret configured for that one organization: [3](#0-2) 

This proves the body is unmodified and was sent by *someone who knows the secret for the organization identified by `repository.owner.login` (or `organization.login`)* — nothing more. It does not prove that `repository.full_name` (the field actually used downstream to select which `Stack`/repository gets written to) belongs to that same organization.

The handler base class then re-parses the same raw payload and derives the write target from a different key: [4](#0-3) 

`PushHandler#process`, for example, uses this `repository_name` to find stacks and call `stack.sync_github(expected_head_sha: params.after)`: [5](#0-4) 

Shipit is designed to serve multiple GitHub organizations, each configured with its own `webhook_secret` in `Shipit.github_configuration`/`secrets.yml` (confirmed by `Shipit.github(organization:)` being keyed on the org and by `GitHubApp#initialize` reading `config[:webhook_secret]` per-instance) — [6](#0-5) . An attacker who controls (or has push access to) any single repository belonging to an organization that is configured in this Shipit instance possesses that organization's GitHub-generated webhook deliveries and can therefore trigger arbitrary payloads signed with *that org's* secret. Because the JSON body is attacker-supplied content sent through their own repo's webhook (or replayed with modified JSON but same top-level `repository.owner.login`/HMAC — note the HMAC covers the raw body, so the attacker cannot simply edit `repository.full_name` in a genuine delivery without breaking the signature). The realistic exploitation window is when Shipit is configured with multiple orgs sharing overlapping trust boundaries, or when `organization.login` (used as fallback for signature selection per line 61) differs from the `repository.full_name`'s owner in the same payload — GitHub's `membership`/`organization` events, for instance, carry an `organization` key distinct from `repository`, and other event payloads can carry a `repository` block whose owner does not match the top-level `organization` block owner in edge cases (e.g. GitHub Apps installed across multiple orgs with cross-org forks, or enterprise setups). In such a case, the signature is validated against organization A's secret (via `organization.login`), while the handler resolves and mutates a `Stack` belonging to a repository under organization B purely from the unrelated `repository.full_name` field in the same trusted-looking JSON body.

This breaks the binding: **organization that authenticated (`repository.owner.login` / `organization.login`, used for HMAC secret selection) == repository that is written (`repository.full_name`, used for `Stack` lookup and mutation)**. These are two different reads of the same untrusted JSON body, and nothing enforces they refer to the same organization.

### Impact Explanation
If exploited, this allows a GitHub org that is validly configured/trusted by this Shipit instance to forge webhook events (via a real webhook delivery whose `organization`/`repository.owner` matches their org, or via an event type like `membership` that includes an `organization` block independent of `repository`) that get misattributed to a different org's repositories, causing unauthorized writes to `Stack` state (e.g. `sync_github` forcing head SHA updates, marking stacks out of sync, or triggering downstream deploy-eligibility state) for repositories the attacker's org does not own. This falls under "cross-repository writes" impact.

### Likelihood Explanation
Medium-to-low likelihood in a single-organization deployment (the common case, where `repository_owner` and `repository.full_name`'s owner are always the same because there is only one org configured), but present by design as soon as Shipit is configured for more than one GitHub organization/app — a documented, supported configuration (`Shipit.github(organization:)` explicitly takes an organization key, and `test/dummy/config/secrets_double_github_app.yml` demonstrates multi-org config exists in the test suite). No privileged Shipit credentials are required — only push/webhook-delivery capability on a repository belonging to any one configured organization.

### Recommendation
Cross-validate that `repository.owner.login` (or `organization.login`) used for signature verification is identical to the owner segment of `repository.full_name` before dispatching to handlers, or reject payloads where they diverge. Alternatively, derive the `Stack`/repository lookup key exclusively from the same field used for signature-organization resolution, rather than trusting a second, independently-controlled field of the same unsigned-per-field JSON body.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/orgs, `org-a` and `org-b`, each with its own `webhook_secret` (as supported by `Shipit.github(organization:)` and shown possible in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker has push access to `org-a/some-repo` and thus can trigger genuine webhook deliveries signed with `org-a`'s `webhook_secret`, or controls an event type (e.g. `membership`) whose payload legitimately contains an `organization` block (`org-a`) decoupled from any `repository` block.
3. Attacker crafts/triggers a `push` event delivery where the payload's `repository.full_name` is set/interpreted to reference `org-b/target-repo` while `repository.owner.login`/`organization.login` remains `org-a`.
4. `WebhooksController#verify_signature` computes `repository_owner` as `org-a`, fetches `org-a`'s `GitHubApp`, and the HMAC validates successfully (signed with `org-a`'s secret over the attacker-controlled body).
5. `PushHandler#process` resolves `repository_name` = `org-b/target-repo` via `Handler#repository_name`, looks up the `Stack` for `org-b/target-repo`, and calls `stack.sync_github(expected_head_sha: ...)`, mutating state for a repository outside `org-a`'s authenticated scope — [5](#0-4) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
