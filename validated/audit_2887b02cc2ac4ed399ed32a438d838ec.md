## Title
Stack-scoped ApiClient token authorizes CCMenu status for any stack, not just the one it was scoped to - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be created scoped to a single `stack` (`belongs_to :stack, optional: true`), and `Api::BaseController#stacks`/`#stack` are supposed to enforce that scope by restricting queries to `current_api_client.stack_id` when one is set. `Api::CCMenuController` overrides `#stack` to bypass this scoping entirely, breaking the binding "stack a token authorizes == stack the endpoint touches."

### Finding Description
`Api::BaseController` defines the intended authorization binding: an `ApiClient` scoped to a stack must only be able to operate on that stack. [1](#0-0) 

`Api::CCMenuController`, however, defines its own `#stack` method that queries `Stack.from_param!(params[:stack_id])` directly — it does not go through the `stacks` scoping helper that filters by `current_api_client.stack_id`: [2](#0-1) 

Compare this to `Api::StacksController#stack`, `Api::HooksController#stack_id`, which correctly call through `stacks.from_param!`: [3](#0-2) 

Since `CCMenuController#show` only calls `require_permission :read, :stack` (a permission-name check, not a stack-identity check) and then reads `stack.deploys_and_rollbacks`, a token that is scoped to stack A but carries the `read:stack` permission can be used to query the CI status (`deploys_and_rollbacks`, lock status, build state) of any other stack B in the deployment by simply passing `stack_id=B` in the URL: [4](#0-3) 

This mirrors the reported bug class: a binding meant to constrain what a credential (verified/authorized side) can touch is computed from one un-scoped code path while the authorization check only validates the permission label, not the actual entity identity — exactly analogous to `baseTokenId`/`_isForFounder` using different (unreduced) values than what should be checked.

### Impact Explanation
This is a scoped-token privilege escalation: a limited `ApiClient` (e.g., created for CI status badges via `CCMenuUrlController`, which explicitly issues tokens scoped to one stack with only `read:stack`) can read task/deploy status, lock reason, and build state for every stack in the Shipit instance, not just the one it was issued for. `CCMenuUrlController` is the normal mechanism that mints such scoped tokens: [5](#0-4) 

This qualifies as High severity per the rules ("unauthenticated read of stack state, task streams or deploy output" via escalation beyond the token's authorized stack scope) — the token holder gains unauthorized read access to other repositories'/stacks' state that they were never granted.

### Likelihood Explanation
High likelihood: any holder of a CCMenu URL/token (which are commonly embedded in CI dashboards, widely shared, and considered low-privilege/"read-only for one stack") can trivially enumerate or guess other `stack_id` params and query them — no additional credentials or privilege needed beyond possessing one legitimately-scoped token.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped `stacks` collection instead of the raw `Stack` model, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it inherits the same `current_api_client.stack_id`-based restriction enforced in `Api::BaseController#stacks`.

### Proof of Concept
1. Create a stack-scoped `ApiClient` for Stack A (as `CCMenuUrlController#client` does): `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack: stack_a, name: 'CCMenu Client')`.
2. Obtain its `authentication_token`.
3. Send `GET /api/stacks/:stack_a_id/ccmenu` — succeeds as expected.
4. Send `GET /api/stacks/:stack_b_id/ccmenu` using the same token, where `stack_b_id` is a different, non-authorized stack.
5. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (unscoped) rather than `stacks.from_param!`, the request succeeds and returns Stack B's build/deploy status, despite the token only being authorized for Stack A.

Note: I was unable to find or execute an actual test proving the exploit end-to-end (no existing test in `test/controllers/api/ccmenu_controller_test.rb` covers a stack-scoped client hitting a different stack's CCMenu endpoint), so this is based on static code-path analysis of `stack` in `CCMenuController` versus `BaseController#stacks`/`#stack`. Confirming this in a running instance would strengthen certainty, but the code path itself is unambiguous.
