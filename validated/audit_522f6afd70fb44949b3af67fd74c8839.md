### Title
Capped assets defined by a buggy AA are permanently frozen because `definer_address` and `cap` are immutable and cannot be transferred to a replacement AA - (File: `aa_validation.js`, `validation.js`, `aa_composer.js`)

### Summary
An AA can define an asset with a fixed `cap` and `issued_by_definer_only: true`. The `definer_address` of that asset is permanently bound to the AA's own address, and the `cap` can never be changed after the asset is defined. If the AA's issuance logic contains a bug that prevents it from ever reaching the code path that issues the capped asset, that asset's supply is permanently stuck at zero (or partially issued) forever, and — because AA definitions/addresses are immutable and asset ownership (`definer_address`) cannot be reassigned — there is no way to deploy a fixed replacement AA that can issue the *same* asset. This mirrors the reported AuctionHouse bug class: a stuck contract with an un-raisable cap and no mechanism to hand off "ownership" (here, definer rights) to a new contract instance.

### Finding Description
When an AA defines an asset via an `asset` message, the definition is validated once and stored immutably: [1](#0-0) [2](#0-1) 

The asset's `definer_address` is derived from the AA that posted the `asset` message and is fixed forever — there is no `app` message type or validation path that permits changing an asset's cap, `issued_by_definer_only` flag, or definer address after creation (only `asset_attestors` can be updated, and only by the original definer): [3](#0-2) 

Separately, AA definitions themselves are immutable — the AA's address is its own definition hash and cannot be changed: [4](#0-3) 

For issuance of a capped asset, `aa_composer.js`'s `issueAsset` enforces that only the definer address may issue, and that issuance can only happen once (per the "already issued" check): [5](#0-4) 

The core validation logic further enforces `if (objAsset.cap && !objAsset.issued_by_definer_only) return callback("if capped, must be issued by definer only");` and ties `issuer_address` strictly to `objAsset.definer_address`: [6](#0-5) [7](#0-6) 

Combining these facts: if the AA author writes buggy oscript logic such that the branch containing the `asset` issuance `payment` message can never be satisfied (e.g., an unreachable `if` condition, or a state-variable guard that can never become true), the capped asset's supply is permanently frozen at whatever partial state it reached (possibly zero). Since:
1. The AA's own bytecode/definition cannot be patched (AA address = definition hash, immutable), and
2. The asset's `definer_address` cannot be reassigned to a newly-deployed, fixed AA,

there is no way to "restart" issuance of that specific asset via a corrected AA, exactly analogous to the AuctionHouse being unable to transfer NFT ownership to a new, functioning AuctionHouse when `max_token` is set too low and can't be raised.

### Impact Explanation
Any value or logic that depends on that specific asset id (external DEX pools referencing the asset, users holding pre-issued partial supply, other AAs hardcoding the asset id, etc.) is permanently stuck: the intended full token supply can never be minted, and no migration path exists without creating an entirely new asset id, which breaks all existing integrations, liquidity, and holder expectations built around the original asset. This is a fund-freezing condition consistent with a Medium-severity finding: AA-issued capped assets can become irrecoverably deadlocked due to an unfixable, immutable definer_address/AA definition, with no path to reissue the same asset via a fixed AA instance.

### Likelihood Explanation
This requires the AA author to write oscript logic with a bug that makes the issuance branch unreachable (e.g., wrong `if` condition, incorrect state variable comparison, a data-feed condition that can never be satisfied) — a class of bug that has repeatedly occurred in real-world AA deployments. Given that AA definitions are immutable by design and there is no built-in recovery/reassignment mechanism for `definer_address` on capped assets, any such logic bug at deployment is permanent and unavoidable after the fact.

### Recommendation
Consider allowing capped, `issued_by_definer_only` assets to support a governed mechanism for the current definer to reassign `definer_address` to a new address (e.g., via a signed `asset_definer_change` message analogous to `asset_attestors` updates), so that if the defining AA is proven buggy/stuck, issuance rights can be migrated to a corrected AA while preserving the original asset id and any accumulated supply/holder state. Alternatively, document this immutability clearly so AA authors are warned to thoroughly test capped-asset issuance logic (e.g., via dry-runs) before binding a cap to an unchangeable AA address.

### Proof of Concept
1. Deploy an AA (`asset_aa`) that defines a capped asset (`cap: 1e6, issued_by_definer_only: true`) in one branch, and issues that asset from another branch guarded by a condition, e.g. `if: "{trigger.data.issue AND some_var_that_can_never_be_set}"`.
2. Because `some_var_that_can_never_be_set` is never actually set by any other code path (a logic bug), the issuance branch never fires — see the structurally identical pattern used correctly in [8](#0-7) , where issuance is gated behind a state-variable condition.
3. The asset's `cap` and `definer_address` (=`asset_aa`'s address) are now permanently fixed per [1](#0-0)  and [3](#0-2) .
4. Deploy a corrected AA (`asset_aa_v2`) with fixed logic. Attempt to have it issue the same asset — `validatePayment` rejects it because `issuer_address !== objAsset.definer_address` per [7](#0-6) , and there is no message type to reassign `definer_address`.
5. The asset supply remains permanently frozen at its current (possibly zero) issued amount, with no recovery path other than creating an entirely new asset id.
