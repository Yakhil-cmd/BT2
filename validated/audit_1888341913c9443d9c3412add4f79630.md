### Title
Stack-scoped API tokens can read any stack's CI/deploy status via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup method used by every other API controller, replacing the tenant-scoped lookup with an unscoped one. This breaks the binding `stack a token authorises == stack a token touches`: an `ApiClient` token that is scoped to a single stack (`ApiClient#stack_id`) can be used to read the CI/deploy status of **any** stack in the Shipit installation, not just the one it was issued for.

### Finding Description
`Shipit::Api::BaseController` establishes the tenant-isolation boundary for every API endpoint. It resolves the target stack through a helper that restricts the queryable set to the calling client's own stack when the client is scoped: [1](#0-0) 

That is: `stacks` returns `Stack.where(id: current_api_client.stack_id)` if the authenticated `ApiClient` has a `stack_id`, otherwise `Stack.all`; and `stack` is derived from that restricted collection via `stacks.from_param!(params[:stack_id])`.

`Api::CCMenuController`, however, does not use this helper. It defines its own `stack` method that bypasses the scoping entirely: [2](#0-1) 

It also authenticates via a `token` query parameter instead of the standard `BasicAuth` used by `BaseController#authenticate_api_client`, but still goes through `ApiClient.authenticate`, which only validates the token signature and does not perform any stack-scope check: [3](#0-2) [4](#0-3) 

The controller only enforces the coarse-grained permission `read:stack`: [5](#0-4) 

Because `require_permission :read, :stack` only checks that the `read:stack` string is present in `ApiClient#permissions` — it never checks `ApiClient#stack_id` — and because `stack` here calls `Stack.from_param!` directly (bypassing `stacks`), **any** `ApiClient` holding `read:stack` (even one deliberately scoped to a single stack via `stack_id`) can supply an arbitrary `stack_id` in the URL and receive that other stack's latest deploy/CI status: [6](#0-5) 

This is the exact bug-class analog described in the report: a value (`stack_id`) that must be checked against an authorization binding (the token's own `stack_id`) is instead consumed directly by a different code path that skips the check — analogous to how the flashloan amount used for the transfer diverges from the amount checked at repayment.

### Impact Explanation
This is a cross-stack unauthorized read of stack/deploy state: an actor holding any `read:stack`-permissioned `ApiClient` token — including one explicitly scoped to a single stack, which is the documented mechanism for restricting a token's visibility — can enumerate the deploy/CI status (`id`, `ended_at`, `running?`) of every stack in the installation by iterating `stack_id` values against this one endpoint. This matches the High-impact category "unauthenticated read of stack state, task streams or deploy output" in spirit — access is only nominally authenticated (any low-privilege `read:stack` token qualifies) while the intended per-stack authorization boundary is bypassed entirely.

### Likelihood Explanation
Any consumer that already holds a scoped, low-privilege `read:stack` API token (e.g., a per-project CCMenu/CI-badge integration token, which is the very use case `CCMenuUrlController` creates tokens for) can trivially trigger this by changing the `stack_id` route parameter. No additional privilege, secret, or session is required beyond a token that would normally only be trusted for one stack.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and reuse `BaseController#stack`/`#stacks` (or otherwise explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`) before rendering CI/deploy data, so that stack-scoped tokens cannot read other stacks' status.

### Proof of Concept
1. As an authorized user, generate a CCMenu URL/token for Stack A (`GET /stacks/:owner/:repo/:env/ccmenu_url`), or otherwise obtain any `ApiClient` token with only `read:stack` permission and `stack_id` set to Stack A.
2. Call `GET /api/stacks/:owner_b/:repo_b/:env_b/ccmenu.xml?token=<Stack-A-scoped-token>` for a different Stack B that the token was never authorized for.
3. Observe that `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!` (unscoped), and the response renders Stack B's latest deploy/CI status, despite the token only being intended to authorize reads for Stack A.
