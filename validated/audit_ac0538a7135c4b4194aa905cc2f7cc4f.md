### Title
`review_stacks_enabled` is not enforced for `allow_with_label`/`prevent_with_label` provisioning behaviors, allowing PR-driven stack creation and code execution when review stacks are disabled - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with `provisioning_behavior_allow_all?` using `&&`, but the two subsequent `||` clauses for `allow_with_label` and `prevent_with_label` never reference `review_stacks_enabled` at all, due to Ruby operator precedence (`&&` binds tighter than `||`). Consequently, a repository with `review_stacks_enabled == false` but `provisioning_behavior == "allow_with_label"` will still provision a `ReviewStack` for any pull request carrying the configured provisioning label. This lets an attacker who can only open a labeled PR against such a repository trigger stack creation and downstream provisioning/task execution driven by their own branch's `shipit.yml`.

### Finding Description
The binding that should hold is: `provision? == true` **only if** `repository.review_stacks_enabled == true`. The code at [1](#0-0)  is:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. When `review_stacks_enabled == false` and `provisioning_behavior_allow_with_label? == true`, the first clause is `false`, but the second clause `(allow_with_label? && has_label?)` evaluates independently and can be `true`, making `provision?` return `true` even though the repository owner disabled review stacks.

Call path: `process` at [2](#0-1)  calls `respond_to_pull_request_opened?` at [3](#0-2) , which calls the broken `provision?`. If true, `ReviewStackAdapter#find_or_create!` runs `create!` at [4](#0-3) , building a `ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled fork branch) and `environment: "pr#{params.number}"`, then enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` at [5](#0-4) . The queue worker calls `stack.provisioner.provision?` and `stack.provision`, which triggers `stack.provisioner.up` via the state machine transition at [6](#0-5) . The default `ProvisioningHandler::Base#provision?` returns `true` unconditionally at [7](#0-6) , so nothing blocks progression.

No other guard re-checks `review_stacks_enabled` in this path: `ReviewStackAdapter` at [8](#0-7)  only scopes to `repository.review_stacks` for lookup, it does not gate creation on `review_stacks_enabled`. `NullRepository` at [9](#0-8)  is irrelevant here since the repository record exists and is a real `Repository`.

The attacker's exact action: open a pull request (as any GitHub user with a fork) against the victim repository, with the repository owner's provisioning label attached to their own PR, while the owner has `provisioning_behavior_allow_with_label` set and `review_stacks_enabled` unset/false. GitHub emits a legitimate, correctly-signed `pull_request.opened` webhook (the attacker does not need to forge signatures — this is a real GitHub-originated event caused by their own PR).

### Impact Explanation
This causes a `ReviewStack` record to be created for a repository that explicitly opted out of review stacks, with `branch` set to the attacker's fork branch. Downstream, provisioning (`stack.provisioner.up`) and, if the repository's provisioning handler or subsequent deploy/task execution reads `DeploySpec::FileSystem`-parsed `shipit.yml` from that branch, arbitrary command steps could be executed via `Command`/`PTY.spawn` on the deploy host — this is the `Critical: RCE on the deploy host` category. The default `ProvisioningHandler::Base` is a noop, so actual command execution severity depends on the specific provisioning handler registered for the repository (e.g., a custom handler that checks out and runs the PR's `shipit.yml`); the finding itself is that the `review_stacks_enabled` gate is bypassable, which is the exact condition the repository owner used to prevent this from happening at all. This is repeatable against any repository configured with `allow_with_label`/`prevent_with_label` and `review_stacks_enabled = false`, and scales to every such repository/tenant in a multi-tenant Shipit instance.

### Likelihood Explanation
Preconditions: `repository.provisioning_behavior` is `allow_with_label` (or `prevent_with_label`) and `repository.review_stacks_enabled == false`. Attacker cost is trivial — open a PR from a fork and add/observe the provisioning label (for `allow_with_label`, attacker needs the label applied, which for `prevent_with_label` requires no label at all, an even lower bar). No secrets, tokens, or privileged roles are required; the webhook is a legitimate GitHub event. This is fully repeatable per PR/per repository matching the configuration.

### Recommendation
Fix the operator precedence in `provision?` by explicitly scoping `review_stacks_enabled` across all disjuncts, e.g.:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (existing test file), add:

```ruby
test "does not provision a review stack when review_stacks_enabled is false, even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit) # or a factory-built repository
  repository.update!(review_stacks_enabled: false, provisioning_behavior: "allow_with_label")

  params = build_opened_params(
    repository_full_name: repository.full_name,
    labels: [{ "name" => repository.provisioning_label_name }]
  )

  assert_no_difference -> { Shipit::Stack.count } do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process
  end
end
```

Before the fix: `Stack.count` increases by 1 and the created `ReviewStack.branch == params.pull_request.head.ref`, even though `repository.review_stacks_enabled == false` — demonstrating `provision? == true` when it should equal `false`. After applying the recommended fix, the assertion `assert_no_difference` passes because `provision?` correctly evaluates to `false`.
