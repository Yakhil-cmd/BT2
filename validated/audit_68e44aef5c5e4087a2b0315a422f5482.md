Found it — `Api::CCMenuController` overrides `stack`/`authenticate_api_client` in a way that breaks the "stack a token authorises" ↔ "stack it touches" binding that every other API controller enforces via `Api::BaseController#stacks`.

### Title
CCMenu API endpoint lets any stack-scoped ApiClient token read data from stacks it was never authorised for - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` scopes every resource lookup through `stacks`, which restricts an `ApiClient` to only the stack referenced by its `stack_id` column when that column is set [1](#0-0) . `Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely and resolve the stack straight from the global `Stack` table using only the URL parameter [2](#0-1) , exactly the "stack a token authorises versus a stack it touches" binding called out as in-scope. This mirrors the Ramses bug class: the code that is supposed to bind two related values (token's authorised stack vs. the stack acted upon) does the mapping incorrectly, silently widening scope instead of narrowing it.

### Finding Description
The intended invariant, enforced in `Api::BaseController`, is:
`current_api_client.stack_id == stack.id` (when the client is stack-scoped) [1](#0-0) 

`CCMenuController#stack` breaks this equality by never consulting `current_api_client.stack_id` at all:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

It also overrides `authenticate_api_client` to accept a `token` query parameter directly instead of Basic Auth [3](#0-2) , and only checks `require_permission :read, :stack` (a client-level permission check, not a stack-membership check) [4](#0-3) . `ApiClient#check_permissions!` only validates that the `"read:stack"` string is in the client's `permissions` array; it has no notion of which stack [5](#0-4) .

Legitimate, low-privilege stack-scoped tokens are routinely created and handed out for exactly this endpoint: `CCMenuUrlController` mints a `read:stack` `ApiClient` scoped to one stack and embeds its `authentication_token` in a URL [6](#0-5) . Those URLs/tokens are meant to be usable only for their one stack — but because `CCMenuController#stack` ignores `current_api_client.stack_id`, the same token can be replayed with a different `stack_id` in the URL and will render CI-status details (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for any stack in the installation.

### Impact Explanation
This is an unauthenticated-scope read: a token that was only ever authorised (and, per the UI, only ever handed out) for one stack can read build/deploy status metadata for every other stack in the Shipit instance, including private/internal stack names and last build status/labels. This matches the in-scope High impact category "unauthenticated read of stack state" (the requester never had a credential scoped to the target stack, only a token scoped elsewhere).

### Likelihood Explanation
Exploitation requires only possession of any valid stack-scoped `read:stack` token — no special privilege, no host misconfiguration, and no reliance on TLS interception, private keys, or session hijacking. Such tokens are widely distributed by design (CCMenu URLs are meant to be pasted into CI dashboard tools), making them the least-protected class of `ApiClient` credential in the system, so an attacker who obtains one CCMenu URL/token for any single stack can immediately pivot to read status for arbitrary stacks by changing the `stack_id` path segment.

### Recommendation
Make `Api::CCMenuController#stack` go through the same client-scoped lookup used everywhere else in the API (`stacks.from_param!(params[:stack_id])`, using the `stacks` scope from `Api::BaseController` that filters by `current_api_client.stack_id` when set), instead of querying the global `Stack` table directly.

### Proof of Concept
1. Create Stack A and Stack B. Obtain a `CCMenuUrlController#fetch` URL for Stack A (a stack-scoped, `read:stack`-only `ApiClient` token) [7](#0-6) .
2. Send `GET /api/<owner>/<stack-B-name>/<env>/ccmenu.xml?token=<Stack-A-token>`.
3. `authenticate_api_client` accepts the token via the query string [3](#0-2) , `require_permission :read, :stack` passes because the token does have that permission string [5](#0-4) , and `stack` resolves Stack B directly from `params[:stack_id]` without checking `current_api_client.stack_id` [2](#0-1) .
4. The response renders Stack B's CI/build data, even though the token was only ever issued for Stack A.
