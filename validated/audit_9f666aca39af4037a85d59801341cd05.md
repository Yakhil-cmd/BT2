### Title
`StatusHandler#process` writes commit statuses with no repository/stack scoping (branch filter, and repository filter, both absent) - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target rows purely via `Commit.where(sha: params.sha)`, never consulting `params.branches` and never calling the repository-scoped `stacks` helper that `PushHandler#process` uses (`stacks.not_archived.where(branch:)`). Because a commit `sha` is git content-derived and identical across any repositories that share history (e.g. a public repo and any fork of it), a status webhook genuinely delivered for an attacker-controlled repository can update the status of a `Commit` row belonging to a completely different stack/repository whose Shipit instance also recorded that same sha.

### Finding Description
Binding that should hold (mirroring `PushHandler`):
`stacks_touched == Repository.from_github_repo_name(payload['repository']['full_name']).stacks.where(branch: <branch from payload>)`

Actual code: [1](#0-0) 
`params.branches` is declared in the schema but never read in `process`, and `process` never calls `stacks` (defined in the base `Handler`) at all: [2](#0-1) 
Compare with `PushHandler#process`, which does bind stack selection to the reporting repository *and* to the branch named in the payload: [3](#0-2) 

`Commit` rows have a `stack_id` (belongs_to :stack) but `StatusHandler` never filters on it — it globally matches by `sha` across every stack in the installation and calls `commit.create_status_from_github!(params)` for each match: [4](#0-3) 

Attack path: an unprivileged attacker forks a public repository that is tracked by a victim Shipit stack (the fork initially shares identical commit SHAs with the upstream repo — this is standard git/GitHub behavior, not attacker-forged). The attacker installs/authorizes the Shipit GitHub App on their own fork (a legitimate, self-owned action) and uses the GitHub Status API (or Actions) to create a real status on a shared-ancestor commit SHA that also exists as a `Commit` row in the victim's stack. GitHub signs and delivers this event genuinely for the attacker's own repository — `verify_signature`/HMAC checks pass because the payload is real and correctly signed; nothing in the webhook pipeline re-derives or checks that `payload['repository']['full_name']` matches the stack that owns the sha-matched `Commit`. `StatusHandler#process` then updates the status of the victim's `Commit` row (any stack, any repository) purely because the sha matches, ignoring both `branches` and the reporting repository entirely.

None of the existing guards prevent this: `verify_signature` only authenticates that the byte-for-byte payload came from GitHub for the claimed (attacker's own) repository; `drop_unhandled_event` only filters on event type; the `ExplicitParameters` schema only validates shape/presence of `branches`, it does not enforce that it be consulted; there is no `Repository`/`Stack` lookup or `require_permission!` check in `StatusHandler#process` at all.

### Impact Explanation
A crafted (but genuinely GitHub-signed) status event from an attacker-owned repository can flip the CI status of a commit belonging to an unrelated, victim-owned Shipit stack (e.g., marking it `success`). `Commit#create_status_from_github!` → `add_status` triggers `stack.schedule_merges` and, via `Commit#schedule_continuous_delivery`, `ContinuousDeliveryJob` when the commit becomes `deployable?` — potentially causing an unauthorized deploy trigger for a repository the attacker never authenticated against. This is a cross-tenant write (one repository's webhook mutating another repository's stack/commit state) and matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy."

### Likelihood Explanation
Preconditions: the victim stack must have ingested a `Commit` whose `sha` is also reachable/creatable by the attacker in a repository they control (trivially true for any fork of a public repo tracked by Shipit, since fork history initially shares identical SHAs), and the Shipit GitHub App/webhook must be enabled for the attacker's own repo (a self-service, unprivileged action for public GitHub Apps). No Shipit secrets, sessions, or maintainer privileges are required — only ownership of a repository whose history overlaps with the target's. This is realistic and repeatable against any publicly forkable repository tracked by the target Shipit instance.

### Recommendation
Scope `StatusHandler#process` to the reporting repository (and ideally branch) the same way `PushHandler` does: resolve the owning `Stack`(s) via `stacks` (repository-scoped, as defined in `Handler#stacks`) before matching commits, i.e. restrict `Commit.where(sha: params.sha)` to `stacks.pluck(:id)` (`stack_id: stacks.select(:id)`), and optionally use `params.branches` to further narrow to matching branches, so a status event can only affect commits belonging to the stack(s) of the repository that actually reported it.

### Proof of Concept
```ruby
test "StatusHandler updates commits in unrelated stacks when sha collides across repos" do
  attacker_stack = shipit_stacks(:shipit)          # repository A, branch "attacker-branch"
  victim_stack   = shipit_stacks(:shipit2)         # unrelated repository B, branch "master"

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/test',
    'repository' => { 'full_name' => attacker_stack.repository.full_name }, # reporting repo != victim's
    'branches' => [{ 'name' => 'attacker-branch' }]                          # unrelated to victim's branch
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  assert_equal 'success', victim_commit.status.state
  # Binding check: repository/branch in payload does not match victim_stack,
  # yet the victim's commit status was still mutated -> scoping is absent.
end
```
This confirms the equality `stacks_touched == Repository.from_github_repo_name(payload['repository']['full_name']).stacks.where(branch:)` fails to hold: the actual write set is unconstrained by either the reporting repository or `params.branches`.
