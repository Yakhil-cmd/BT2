### Title
Cross-organization webhook signature confusion allows forging webhook events against any repository configured on a multi-org Shipit instance - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an incoming webhook signature against based on a field taken from the **attacker-controlled JSON body** (`repository.owner.login`, falling back to `organization.login`), while the code that actually decides *which repository/stack the event acts on* reads a **different field of the same body** (`repository.full_name`, consumed independently by `Shipit::Webhooks::Handlers::Handler#repository_name`). Nothing ties these two fields together, so a request whose body claims `repository.owner.login = "org-A"` but `repository.full_name = "org-B/victim-repo"` is verified using org-A's secret yet is dispatched to act on org-B's repository/stack. [1](#0-0) [2](#0-1) 

### Finding Description
Shipit explicitly supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret`, `oauth`, and `private_key` under `secrets.github`: [3](#0-2) 

`Shipit.github(organization:)` resolves the correct per-organization config, and `verify_webhook_signature` HMAC-validates the raw body against that organization's own `webhook_secret`: [4](#0-3) [5](#0-4) 

The controller determines *which organization's secret to use* purely from the JSON body itself, before the signature has even been checked:

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

Once signature verification passes, `create` dispatches the *entire, attacker-crafted* body to the event handlers: [7](#0-6) 

Every handler independently determines the target `Stack`/`Repository` from a *different* field of the same body — `repository.full_name` — with no cross-check against `repository.owner.login` used for signature selection: [2](#0-1) [8](#0-7) 

This breaks exactly the trust equality the scan targets: **organization that authenticated the request (via its own `webhook_secret`) ≠ repository whose Stack the handler writes to (`repository.full_name`)**.

Concretely, any party who legitimately administers *any one* GitHub organization configured on the same Shipit instance (and therefore knows/controls that org's `webhook_secret`, since they configured the GitHub App for it) can:
1. Craft an arbitrary JSON body with `repository.owner.login = "their-own-org"` and `repository.full_name = "victim-org/victim-repo"`.
2. Sign the raw body with their own org's known `webhook_secret`.
3. POST it to the shared `/webhooks` endpoint (`app/controllers/shipit/webhooks_controller.rb`).
4. `verify_signature` resolves `Shipit.github(organization: "their-own-org")` and validates successfully.
5. `PushHandler` (or `MembershipHandler`, `CheckSuiteHandler`, PR handlers) resolves the target stack from `repository.full_name` = the victim org's repository and acts on it — e.g. enqueuing `GithubSyncJob` for the victim's stack, or creating `Team`/`User` records via the `membership` event, entirely independent of the org whose secret authenticated the request. [9](#0-8) 

### Impact Explanation
This lets an attacker who only controls one tenant organization on a shared Shipit instance forge webhook events that mutate state belonging to a completely different organization/repository they have no access to — a cross-organization/cross-repository write triggered without ever authenticating as that organization. This matches the Critical "cross-repository writes" criterion: state changes (queued syncs, created teams/users, PR/check-run records) are performed against a repository whose organization never authorized the request.

### Likelihood Explanation
Requires only that the deployer runs Shipit in the documented multi-org configuration (`secrets.github` keyed by organization, as shown in `config/secrets.development.shopify.yml`) and that the attacker legitimately administers at least one of the configured organizations (a low bar — many self-serve Shipit deployments host multiple internal or partner orgs). No repository write access, GitHub App private key, or Shipit session is needed; the attacker only needs the `webhook_secret` of any one org they legitimately control.

### Recommendation
Bind signature verification to the same repository identity the handlers act on, and reject requests where the two are inconsistent. Concretely, `verify_signature` should resolve the target organization from `repository.full_name`'s owner (the same field used by `Handler#repository_name`) rather than a separate, independently-controlled field, or the handlers should re-verify that the repository resolved from `full_name` belongs to the organization whose secret validated the signature before performing any mutation.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml`).
2. As an administrator of `org-a` (attacker), build a push-event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<any sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "org-a")`, validates successfully against `org-a`'s secret (`app/controllers/shipit/webhooks_controller.rb` lines 24-30).
6. `PushHandler.process` resolves stacks via `Repository.from_github_repo_name("org-b/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb` lines 32-38) and enqueues `GithubSyncJob` for `org-b`'s stack — a mutation of `org-b`'s data authorized only by `org-a`'s credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
