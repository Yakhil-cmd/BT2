### Title
Cross-repository commit status write via unscoped SHA lookup in StatusHandler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the GitHub App configured for one specific organization, derived from the attacker-supplied `repository.owner.login` field of the JSON body [1](#0-0) . Once the HMAC check passes, the handler dispatch is fully generic: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [2](#0-1) . `StatusHandler`, unlike `PushHandler`, never re-validates that the commit it mutates actually belongs to the repository named in the payload that was authenticated.

### Finding Description
`PushHandler#process` correctly scopes its side effects to the repository claimed in the payload by resolving `stacks` through `Repository.from_github_repo_name(repository_name)`, where `repository_name` is `payload.dig('repository', 'full_name')` [3](#0-2) [4](#0-3) .

`StatusHandler#process`, by contrast, looks up commits purely by SHA across the entire instance and writes a status to every match, with no repository/stack scoping at all: [5](#0-4) 

The binding that should hold is: `organization/repository whose webhook secret authenticated the request == repository whose Commit records are mutated`. Because `StatusHandler` never consults `payload.dig('repository', 'full_name')`, a validly-signed `status` event for repository/organization A can create/overwrite a `Status` on any `Commit` row anywhere in the Shipit installation that happens to share the same `sha` — including commits belonging to Stacks tied to a completely different organization/repository, as long as that org also has a Shipit integration. Commit SHA collisions across repositories are routine in practice (forks, subtree/vendor imports, repository migrations/renames tracked as multiple `Repository`/`Stack` records, or shared initial/cherry‑picked commits), so this is a realistic condition, not a hash-collision attack.

### Impact Explanation
An attacker who legitimately controls commit-status webhook delivery for one tracked repository (e.g. is the CI/status reporter for repo A, and can therefore get GitHub to sign and deliver a `status` event with A's real webhook secret) can cause Shipit to write arbitrary commit status data (`state`, `description`, `target_url`, `context`) against commits belonging to an unrelated Stack/repository B, wherever those commits share a SHA. Commit statuses drive Shipit's deploy/merge safety gates (`deployable_status`, checks used before merge/deploy), so this is a cross-repository write that can corrupt or manipulate another stack's deploy-readiness signal — the kind of cross-repository write impact called out as in-scope Critical impact.

### Likelihood Explanation
Requires the attacker to already be a legitimate status-webhook source for at least one Shipit-tracked repository (e.g. has CI/commit-status write access there) and for a SHA collision to exist with a target Stack's history — a condition satisfied whenever repositories share git history (forks, migrations, subtree imports). This is more constrained than a fully unauthenticated attack, but crosses the credential/repository boundary the signature check is meant to enforce, since `StatusHandler` drops that scoping entirely while the sibling `PushHandler` preserves it.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: resolve the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` first, then restrict the `Commit` lookup to commits belonging to that repository/stack (e.g. `stacks.commits.where(sha: params.sha)`), rejecting or ignoring statuses for SHAs that don't belong to the authenticated repository.

### Proof of Concept
1. Attacker controls (or is the CI system for) repository `org-a/repo-a`, tracked by Shipit, and can trigger a genuine `status` webhook from GitHub for any commit SHA in that repo's history (commit statuses can be set for any SHA reachable in the repo via the Statuses API).
2. Shipit also tracks `org-b/repo-b` as a separate Stack, whose history shares a commit SHA with `org-a/repo-a` (e.g., `repo-b` was forked from/subtree-imported from `repo-a`, or is a renamed/duplicated import).
3. Attacker sets that shared SHA's commit status via GitHub's Statuses API on `org-a/repo-a` with a crafted `state`/`description`/`context`.
4. GitHub signs and delivers the webhook with `org-a`'s real `webhook_secret`; `WebhooksController#verify_signature` passes because it only checks the HMAC against `org-a`'s secret [6](#0-5) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository filter and calls `commit.create_status_from_github!(params)` on every matching commit, including the one belonging to `org-b/repo-b`'s Stack [5](#0-4) , writing attacker-controlled status data into a Stack the attacker has no relationship to.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
