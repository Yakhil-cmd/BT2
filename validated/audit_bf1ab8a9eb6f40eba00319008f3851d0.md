## Title
Cross-organization webhook impersonation via mismatched `repository.owner.login` (signature scope) and `repository.full_name` (target-selection field) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a webhook against using `repository.owner.login` from the JSON body, but the event handlers that actually act on the payload select the target `Stack`/`Repository` using a completely different field, `repository.full_name`. Nothing binds the two together, so a request signed with one organization's legitimate `webhook_secret` can carry a `full_name` pointing at a repository belonging to a *different* configured organization. This is the same class of bug described in the report: a mutating/authorizing check is performed against one piece of state (the org whose secret validated the HMAC) while the actual effect is applied against different, uncontrolled state (the repository named in the body), because the two are never cross-validated.

### Finding Description
Shipit supports multiple GitHub organizations in a single install, each with its own `webhook_secret`, resolved via `Shipit.github_app_config` / `Shipit.github`: [1](#0-0) 

The webhook signature check picks the secret to validate against solely from the payload's `repository.owner.login` (or `organization.login`): [2](#0-1) [3](#0-2) 

Once the HMAC passes, the raw parsed body is dispatched unmodified to handlers: [4](#0-3) 

Every handler determines *which* `Repository`/`Stack` to operate on using a separate field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

`Repository.from_github_repo_name` simply splits the attacker-controlled string on `/`: [6](#0-5) 

Because the entire `raw_post` — including both `repository.owner.login` and `repository.full_name` — is under the control of whoever computes the signature, an operator who legitimately controls one configured organization's `webhook_secret` (e.g. Org A, which they administer through their own GitHub App settings — not a Shipit credential) can:
1. Set `repository.owner.login = "org-a"` so `verify_signature` fetches and validates against Org A's own `webhook_secret` (which the attacker knows/controls).
2. Set `repository.full_name = "org-b/private-repo"`, an entirely different organization's repository also hosted on the same Shipit instance.

The HMAC will validate successfully (it's Org A's own secret over Org A's own crafted body), yet `PushHandler` (and other handlers) will resolve and act on Org B's `Stack`: [7](#0-6) 

This enqueues `GithubSyncJob` against Org B's stack, which appends commits into Org B's stack, transitions accessibility state, and schedules cache/deploy-spec recomputation — all effects meant to be gated by Org B's own webhook secret: [8](#0-7) 

The bound equality that should hold is: *organization whose secret authenticated the request == organization that owns the repository being written to*. `repository_owner` (used only for signature-key selection) and `repository_name`/`full_name` (used for the actual write target) are never compared, so this equality is not enforced anywhere in the controller or handler stack — mirroring the Raydium bug pattern where a value used for a check (cached/pre-cancel free-token amount) diverges from the value actually mutated (post-cancel orderbook), letting attacker-controlled state slip past a check that assumed the two stayed in sync.

### Impact Explanation
This allows cross-repository/cross-tenant writes in any multi-organization Shipit deployment: an entity that legitimately controls the webhook configuration of one onboarded GitHub organization (which requires no Shipit session, API token, or `webhook_secret` belonging to the victim org) can forge webhook deliveries that mutate stack state — appending commits, altering accessibility state, and triggering re-caching of deploy specs — for stacks belonging to a completely different, unrelated organization also hosted on the shared Shipit instance. This satisfies the "cross-repository writes" Critical bucket, since state belonging to Org B is written as a direct consequence of a request that was never authenticated by Org B's credentials.

### Likelihood Explanation
Exploitability only requires the attacker to be able to send an HTTP request to the public `/webhooks` endpoint with a body they fully control and a correctly computed HMAC using a `webhook_secret` they legitimately possess for their own organization's GitHub App/webhook configuration — no Shipit account, session, or privileged access is needed. The only prerequisite is that the Shipit instance hosts more than one GitHub organization (a documented, supported configuration per `lib/shipit.rb`'s `github_organizations`/`github_app_config`).

### Recommendation
In `WebhooksController#verify_signature` and/or `Shipit::Webhooks::Handlers::Handler`, enforce that the organization used to validate the webhook signature is the same organization that owns the repository named in `repository.full_name` (i.e., reject/short-circuit if `repository.full_name.split('/').first` does not match `repository_owner`), rather than allowing the two to be derived and used independently.

### Proof of Concept
1. Attacker administers Org A's GitHub App integration in a shared Shipit instance and knows Org A's configured `webhook_secret`.
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "org-b/private-repo",
    "owner": { "login": "org-a" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org_a_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully using Org A's own secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/private-repo")`, unrelated to Org A, and enqueues `GithubSyncJob` against Org B's stack — a write the attacker was never authorized to trigger.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
