### Title
Attacker-controlled swap routes inject arbitrary token transfers into the caller's authorization tree, draining the victim's wallet - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
CVE-2020-26287 is a content-injection bug: attacker-supplied mermaid markup executed attacker JavaScript inside a victim's authorized session. The analog in XOXNO Lending is route-code injection: the `swap` bytes supplied to controller strategies (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) are an attacker-controlled program. The swap aggregator dispatches each hop to whatever pool/venue address the payload names, with no allowlist of callable contracts. A malicious hop contract can call `token.transfer(victim, attacker, X)` inside the swap, and that transfer is recorded as a child of the *caller's* authorization entry — it executes if the caller signs the tree their wallet simulates. This is injection of executable code into a user-authorized context, the on-chain equivalent of the script-tag injection.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:34` authorizes exactly one `token_in.transfer(controller, router, amount_in)` and then invokes `router.execute_strategy` with caller-supplied `swap` bytes [1](#0-0) . The controller's checks are purely balance-delta based on its own address: it only rejects controller input growth/overspend and requires positive measured `token_out` output [2](#0-1) . Nothing in the controller bounds what the router or its hop venues do with the *caller's* authorization.

The aggregator README states the router "calls the pool and token addresses its payload names and keeps no allowlist of them" [3](#0-2) , and `dispatch_hop` invokes whichever venue contract the route specifies, measuring only the router's own balance deltas [4](#0-3) . The threat model confirms the exposure explicitly: "a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded... as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount." [5](#0-4) 

This is not theoretical: the harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` deploys a `RogueHopPool` whose `swap` function does `token.transfer(victim_wallet_token, attacker, amount)`, routes a `swap_collateral` through it, and shows simulation records the stolen transfer as a sub-invocation of the caller's `swap_collateral` auth entry; after signing, Alice's entire wallet balance (a token the protocol never listed) moves to the attacker while the swap itself pays a fair output and passes all controller gates [6](#0-5) .

### Impact Explanation
Theft of user funds. Any token in the victim's wallet — including assets the protocol never lists — can be transferred to the attacker inside a single otherwise-legitimate `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` call. The loss is unbounded by the routed amount, the payload `min_out`, or the account's final risk gates, which all pass because the swap itself is fair.

### Likelihood Explanation
Any unprivileged address can craft such a route and present it to a victim through a malicious or compromised frontend, a doctored quote API, or social engineering — the same delivery model as the CVE's injected note. The exploit depends on the victim signing an authorization tree containing the extra child invocation; standard wallet flows present/simulate trees opaquely enough that users routinely sign child invocations they did not intend (the CVE likewise required user interaction, UI:R). Because venue addresses are not allowlisted, there is no protocol-side mitigation. Documented in the threat model as a client responsibility, but the protocol design is what places arbitrary third-party code beneath user auth — Medium-High.

### Recommendation
- Enforce a venue/pool allowlist in the swap aggregator so route hops can only invoke governance-approved contract addresses (analogous to the CVE fix of disallowing `www.google-analytics.com` in the CSP).
- Have the controller pin the expected authorization shape: wrap the router call so the caller-facing entrypoint cannot silently attach unrelated child transfers — e.g., pull `token_in` to the controller before router invocation via `transfer_from` with allowance, so the caller's signature covers a single known transfer rather than an open-ended tree.
- Surface a canonical, minimal auth tree in the SDK so integrators can hard-reject any signature request containing extra sub-invocations.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC:

1. Attacker deploys `RogueHopPool` storing `(victim, wallet_token, attacker, amount)` [7](#0-6) .
2. Victim calls `controller.swap_collateral` with a `swap` payload whose hop pool is `RogueHopPool`. The router double pays a fair ETH output so all controller gates pass.
3. Inside the hop, `RogueHopPool::swap` executes `wallet_token.transfer(alice → attacker, WALLET_BALANCE)`. Recording-mode simulation shows this transfer nested under Alice's `swap_collateral` auth entry [8](#0-7) .
4. Alice signs the simulated tree; in enforcing mode the stolen transfer executes. Final state: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while Alice's ETH supply credit is the fair `25_000_000` — the protocol-visible swap was completely normal [9](#0-8) .

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
