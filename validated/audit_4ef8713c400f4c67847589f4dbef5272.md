### Title
Webhook organization used for signature verification is unauthenticated and decoupled from the repository actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against by reading `repository_owner` straight out of the **unverified** request body, and `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically valid. Because the organization used to authenticate the request and the repository/stack that the payload subsequently mutates are both taken from the same untrusted JSON body, an attacker can pick any organization configured on the instance that has no `webhook_secret` set, forge a webhook whose `repository.owner.login` names that unsecured org while `repository.full_name`/`ref`/`after`/`sha` target a stack belonging to a different, properly-secured organization, and have the request accepted as authentic.

### Finding Description
`verify_signature` derives the organization purely from payload content: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally passes when the selected org has no configured secret: [3](#0-2) 

Deployments frequently configure multiple GitHub organizations/apps on the same Shipit instance (see the multi-org secrets template), and a `webhook_secret` of `nil` is the documented/default value: [4](#0-3) 

The equality that should hold is: *organization that authenticated the webhook == organization owning the repository the payload mutates*. Before the attack, this holds because signatures are checked against the secret of the org that actually owns the target repository. After a forged request, the attacker supplies `repository.owner.login = "org-without-secret"` (satisfying `verify_signature` trivially via the `return true unless webhook_secret` branch) while `repository.full_name` / `ref` / `after` name a stack under a different, secured organization. `Hook#create` then dispatches the (now "verified") payload to handlers such as `PushHandler`, which acts on stacks matched purely by `branch`/repository derived from the payload, with no re-check that the payload's claimed owner matches the actual repository owner: [5](#0-4) 

The existing test suite confirms `repository.full_name`/`owner.login` are attacker-controllable body fields independent from any authentication step: [6](#0-5) 

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding. Webhook handlers beyond `push` include `status`/`commit_status`/`deployable_status`/`membership`, which write commit statuses, create teams/users, and can influence continuous-deployment gating (`ci.require`) that governs whether Shipit auto-deploys a commit. An attacker who only needs to know that *one* org on the shared Shipit instance lacks a `webhook_secret` (a common/default state, as shown in the shipped secrets templates) can forge signed-looking events for *any other* org's stacks, potentially forging passing CI/commit statuses that gate continuous deployment, leading to an unauthorized deploy.

### Likelihood Explanation
No privileged credentials, API tokens, or session are required — only network access to the public webhooks endpoint and knowledge that at least one configured GitHub organization on the instance has an empty `webhook_secret` (default value in the shipped config templates). Multi-org Shipit deployments are an explicitly supported and documented configuration, making this a realistic scenario rather than a theoretical edge case.

### Recommendation
- Never allow an unset `webhook_secret` to short-circuit signature verification; require an explicit, always-non-empty secret per organization, or reject the request if the target organization's secret is not configured.
- Do not select the "authenticating organization" from unverified payload content. Bind the webhook signature check to the actual `Repository`/`Stack` being targeted (looked up from a trusted mapping) rather than from `params.dig('repository','owner','login')` sent by the caller.
- After signature verification passes, re-validate that `repository.owner.login`/`repository.full_name` in the payload matches the organization whose secret produced a valid signature.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `secured-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, i.e. `nil`), as shown in `config/secrets.development.shopify.yml`.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "open-org" }, "full_name": "secured-org/target-repo" }
}
```
3. POST it to `/github/webhooks` with header `X-Github-Event: push` and any (or no) valid-looking `X-Hub-Signature`.
4. `repository_owner` resolves to `"open-org"`; `Shipit.github(organization: "open-org")` yields a `GitHubApp` with `webhook_secret` `nil`; `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-83`.
5. `PushHandler#process` runs against stacks matching `secured-org/target-repo`'s branch, triggering `stack.sync_github(expected_head_sha: params.after)` for a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
