Based on the investigation, there is a concrete analog: `unhandled_private_payments` provides unbounded, attacker-controlled storage growth from an unauthenticated/unprivileged private-payment counterparty, closely mirroring the IKEv2 "unbounded client transform storage" bug class (state accumulated per handshake without bound, from crafted repeated messages).

### Title
Unbounded storage growth from unvalidated private payment chains - (File: network.js)

### Summary
`network.js`'s `handleOnlinePrivatePayment` persists attacker-supplied `arrPrivateElements` chains into the `unhandled_private_payments` table before any real structural/cryptographic validation of the chain occurs, and cleanup is either non-existent (full nodes have no periodic cleanup for `linked` unresolved entries beyond a 1-day sweep only under specific conditions) or delayed for a full day, allowing a counterparty (paired device) to flood the table with large, never-resolving entries.

### Finding Description
When a paired device (a "private-payment counterparty", explicitly in scope) sends a `private_payment` message, it is routed to `handleOnlinePrivatePayment`: [1](#0-0) 

The only checks performed before storage are that `unit` is a valid base64 hash-length string, `message_index` is a non-negative integer, and `output_index` is valid — there is no validation of the actual chain content, length, or that it corresponds to a real, existing unit: [2](#0-1) 

For light clients with `arrPrivateElements.length > 1`, or whenever `joint_storage.checkIfNewUnit` reports the referenced unit is new/known-unverified, the full (attacker-controlled) `JSON.stringify(arrPrivateElements)` blob is inserted into `unhandled_private_payments`, keyed by `(unit, message_index, output_index)`: [3](#0-2) 

Because the primary key includes `unit`, an attacker can trivially generate arbitrarily many distinct, well-formed-looking but fake base64 unit hashes (`isValidBase64(unit, HASH_LENGTH)` only checks format, not that the unit exists or is ever going to be published) each paired with a large `arrPrivateElements` array (chain length and per-element payload size are not bounded anywhere in this code path), and repeatedly submit `private_payment` messages. Each submission creates a new, unique row that is never deduplicated against real chain content and is not immediately rejected.

Cleanup for these entries is weak:
- On light clients, cleanup for "linked" chains only fires opportunistically via `updateLinkProofsOfPrivateChain`, and stale entries with never-resolved units are deleted only inside `requestUnfinishedPastUnitsOfPrivateChains`'s callback, gated by a `-1 DAY` age condition — meaning at minimum a full day of accumulation is possible before any purge is attempted, and only if that code path is actually exercised for the specific unit. [4](#0-3) 
- On full nodes, `cleanBadSavedPrivatePayments` only deletes rows whose `unit` never showed up in `units` after 1 day, and only runs once, 300 seconds after `comeOnline()`: [5](#0-4) [6](#0-5) 

This means an attacker (any paired device / correspondent that can send `private_payment` messages, not requiring any special privilege) can sustain a flood of large JSON blobs into this table for up to a day at a time, with no rate limit, no per-peer/per-device cap, and no size cap on the chain content or number of chains, consuming unbounded disk/DB storage — directly analogous to the IKEv2 bug where crafted repeated messages caused unbounded per-flow state growth leading to resource exhaustion.

### Impact Explanation
This is a resource-exhaustion / denial-of-service vector: an unprivileged paired device (private-payment counterparty) can grow the `unhandled_private_payments` table without bound, exhausting node disk space and degrading DB performance, which can eventually prevent the node from confirming or processing units (a network unable to confirm new units) if disk fills or DB operations slow to a crawl. It does not directly cause double-spend, supply inflation, or fund loss, but it satisfies the "network unable to confirm new units" bar via storage/DoS.

### Likelihood Explanation
High likelihood: the only requirement is that the sender be a correspondent/paired device capable of sending `private_payment` messages (a normal wallet-to-wallet interaction, not requiring any special access), and the crafted chains need only pass superficial format checks (valid-looking base64 unit hash, non-negative indices) — no cryptographic validity or existence check is required prior to storage.

### Recommendation
- Impose a hard cap on the number of pending `unhandled_private_payments` rows per peer/device and reject inserts beyond that cap.
- Impose a maximum length/size on `arrPrivateElements` and the serialized JSON before insertion.
- Reduce the retention window for unresolved entries and run periodic cleanup unconditionally (not gated behind specific request/callback paths), independent of the 1-day full-day window.
- Consider requiring a lightweight proof (e.g., a plausible reference to a currently known dependency, or a stricter shape check) before persisting rather than immediately writing arbitrary attacker JSON to durable storage.

### Proof of Concept
1. As a paired device/correspondent of a victim wallet, repeatedly send `private_payment` (or `private_payment_chains` for light) messages where:
   - `unit` is a freshly-generated random 44-character base64 string (passes `isValidBase64(unit, HASH_LENGTH)` but does not correspond to any real unit),
   - `arrPrivateElements` contains a large, well-formed-looking chain (many elements, large `payload.inputs`/`payload.outputs`).
2. Each such message causes an `INSERT ... INTO unhandled_private_payments` with the full JSON blob, since `joint_storage.checkIfNewUnit` will treat the fabricated unit as new. [7](#0-6) 
3. Because the unit never actually appears in `units`, the row survives until the `-1 DAY` cleanup sweep runs and is triggered for that specific unit; repeating step 1 continuously outpaces cleanup, growing the table unbounded.

function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	if (!ValidationUtils.isValidBase64(unit, constants.HASH_LENGTH))
		return callbacks.ifError("invalid unit");
	if (!ValidationUtils.isNonnegativeInteger(message_index))
		return callbacks.ifError("invalid message_index");
	if (!(ValidationUtils.isNonnegativeInteger(output_index) || output_index === -1))
		return callbacks.ifError("invalid output_index");

	var savePrivatePayment = function(cb){
		// we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device.
		// in this case, we also receive the same (unit, message_index, output_index) twice - as cosigner and as recipient.  That's why IGNORE.
		db.query(
			"INSERT "+db.getIgnore()+" INTO unhandled_private_payments (unit, message_index, output_index, json, peer) VALUES (?,?,?,?,?)", 
			[unit, message_index, output_index, JSON.stringify(arrPrivateElements), bViaHub ? '' : ws.peer], // forget peer if received via hub
			function(){
				callbacks.ifQueued();
				if (cb)
					cb();
			}
		);
	};

function cleanBadSavedPrivatePayments(){
	if (conf.bLight || bCatchingUp)
		return;
	db.query(
		"SELECT DISTINCT unhandled_private_payments.unit FROM unhandled_private_payments LEFT JOIN units USING(unit) \n\
		WHERE units.unit IS NULL AND unhandled_private_payments.creation_date<"+db.addTime('-1 DAY'),
		function(rows){
			rows.forEach(function(row){
				breadcrumbs.add('deleting bad saved private payment '+row.unit);
				db.query("DELETE FROM unhandled_private_payments WHERE unit=?", [row.unit]);
			});
		}
	);

function requestUnfinishedPastUnitsOfPrivateChains(arrChains, onDone){
	mutex.lock(["private_chains"], function(unlock){
		function finish(){
			unlock();
			if (onDone)
				onDone();
		}
		privatePayment.findUnfinishedPastUnitsOfPrivateChains(arrChains, true, function(arrUnits){
			if (arrUnits.length === 0)
				return finish();
			breadcrumbs.add(arrUnits.length+" unfinished past units of private chains");
			requestHistoryFor(arrUnits, [], err => {
				if (err) {
					console.log(`error getting history for unfinished units of private payments`, err);
					return finish();
				}
				// get units that are still new or unstable after refreshing the history
				storage.filterNewOrUnstableUnits(arrUnits, async arrMissingUnits => {
					if (arrMissingUnits.length === 0) return finish();
					console.log(`will delete unhandled private payments whose units are not known after 1 day`, arrMissingUnits);
					await db.query(`DELETE FROM unhandled_private_payments WHERE unit IN(${arrMissingUnits.map(db.escape).join(', ')}) AND creation_date < ${db.addTime('-1 DAY')}`);
					finish();
				});
			});
		});
	});
}
