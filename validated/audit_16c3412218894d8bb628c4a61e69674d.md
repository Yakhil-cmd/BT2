### Title
Unallowlisted swap-route pool addresses can inject attacker contract calls into the caller’s authorization tree and steal unrelated wallet tokens - (contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The controller’s leveraged/swap strategies accept caller-supplied `StrategySwap` XDR and pass it to the configured router; the controller only authorizes one exact input-token transfer from itself to the router and later checks controller balance deltas and final account risk [1](#0-0) . The router decodes pool/token addresses from the payload and dispatches hops to those payload-named addresses without an allowlist [2](#0-1) [3](#0-2) . The project’s own threat model states that a route can put third-party code below the caller’s authorization, causing extra `token.transfer` children to be recorded under the caller’s auth entry and executed if the caller signs that tree [4](#0-3) .

### Finding Description
This is the Soroban analog of shell-metacharacter injection: the “special element” is not a filename but the route payload’s `assets`/`ops` registries, which let an unprivileged caller name arbitrary `pool`, `token_in`, and `token_out` addresses for each hop [5](#0-4) . `run` authenticates only `sender`, decodes the program, pulls `total_in` from `sender`, then executes the payload’s instruction stream [6](#0-5) [7](#0-6) . `dispatch_hop` selects an adapter by opcode and calls the payload-named pool; measured router balance deltas bound the routed input/output, not the set of contracts placed on the call stack [8](#0-7) .

For controller strategies, the dangerous surface is entrypoints such as `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral`, which route user-supplied swap bytes through `swap_tokens`/`swap_tokens_or_passthrough` [9](#0-8) . The controller’s grant is narrow for itself—one `transfer(controller, router, amount_in)` with no sub-invocations [10](#0-9) —but that does not constrain additional children the host may record under the user’s signature when route-nominated third-party code calls `token.transfer(victim, attacker, amount)`. The documented result is wallet loss beyond the routed amount when the victim signs the simulated poisoned authorization tree [4](#0-3) .

### Impact Explanation
A victim who signs a crafted strategy transaction can lose unrelated wallet tokens not listed by the protocol and not part of the swap, because a rogue “pool” contract embedded in the route can request a `transfer` from the victim under the same authorization tree [11](#0-10) . The controller’s measured-output and solvency checks still pass if the router pays fair output, so the theft is outside the routed amount and outside `min_out` [12](#0-11) [13](#0-12) . This is theft of user funds, though it requires the victim to sign the poisoned auth tree rather than being purely permissionless.

### Likelihood Explanation
Likelihood is bounded by user-assisted signing: an attacker must get a victim to sign a route whose simulation contains an extra child transfer, and honest clients are expected to reject non-empty children [14](#0-13) . The reachability is still real because swaps are user-facing, payload bytes are supplied off-chain, venue/pool addresses are not allowlisted, and the same exposure exists for direct `execute_strategy` users [15](#0-14) [4](#0-3) . I would rate it Medium: high impact on a signed victim, but dependent on wallet/client failure to detect an injected authorization child.

### Recommendation
Constrain route-reachable code at the router boundary instead of trusting payload-named pool/token addresses:
- Governance-allowlist concrete venue pool contracts and token addresses per venue type, and reject hops whose `pool`/token pair is not admitted.
- Prefer venue adapters that invoke fixed functions on pre-registered pool contracts rather than arbitrary `assets[idx]` addresses.
- Keep balance-delta settlement, but explicitly document that it does not bound authorization-tree children; require wallets/SDKs to refuse any auth tree beyond the single expected input transfer.
- Add a regression test that a payload-named rogue contract cannot be reached by production router adapters.

### Proof of Concept
1. Deploy a malicious contract exposing the function signature a venue adapter calls for a swap.
2. Craft `StrategyPayload` whose `assets` entries point `idx_a` at that malicious pool and choose listed `token_in`/`token_out`; encode an `ops` instruction that routes through it.
3. Get the victim to call `Controller::swap_collateral` or `Router::execute_strategy` with that payload and sign the simulated authorization tree.
4. During the hop, the router invokes the payload-named pool; inside that call the malicious contract invokes `token.transfer(victim, attacker, wallet_amount)`, which the host records as a child under the victim’s auth entry and executes if signed, while the router still returns acceptable measured output [16](#0-15) [4](#0-3) .

child. The direct `execute_strategy` path has the same exposure for every swap

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };
