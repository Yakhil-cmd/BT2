## Title
Missing WebAuthn Ceremony-Type Check in `PartialAuthenticatorAssertionResponse::verify` - ([File: types/src/transaction/webauthn.rs])

### Summary
`PartialAuthenticatorAssertionResponse::verify` deserializes `client_data_json` into a `CollectedClientData` struct that contains a `ty` field (the WebAuthn ceremony type, e.g. `webauthn.get` vs `webauthn.create`), but the verification logic never inspects or validates this field.

### Finding Description
The `verify` function only performs three checks:
1. Deserialize `client_data_json` into `CollectedClientData`.
2. Compare the `challenge` field against the SHA3-256 digest of the signing message (`verify_expected_challenge_from_message_matches_actual`).
3. Reconstruct `verification_data` (`authenticator_data || SHA-256(client_data_json)`) and cryptographically verify the signature against the provided public key. [1](#0-0) 

At no point is `collected_client_data.ty` compared against the expected ceremony type `webauthn.get` (`ClientDataType::Get`). The struct definition confirms `ty` exists as a field of `CollectedClientData` and is used by test helpers to construct valid assertions with `ClientDataType::Get`, but production `verify()` code path never reads it: [2](#0-1) 

Because the challenge is simply the SHA3-256 digest of the raw transaction's signing message, and the signature covers `authenticator_data || SHA256(client_data_json)`, an attacker who controls (or a compromised/malicious relaying party for) an authenticator's `create` ceremony output could produce a `client_data_json` with `"type":"webauthn.create"` yet the same `challenge` value, and the same authenticator_data/signature — this would still pass every check performed in `verify()`.

The comment above `verify()` explicitly documents intended WebAuthn §6.3.3 `authenticatorGetAssertion` semantics, implying the "get" ceremony is assumed, but the code doesn't enforce it: [3](#0-2) 

### Impact Explanation
This is a genuine gap relative to the WebAuthn specification (§7.2, step 11, requires verifying `clientDataJSON.type === "webauthn.get"`), and the code as reviewed does not implement it in `PartialAuthenticatorAssertionResponse::verify`. However, for this to be exploitable as a transaction-admission bypass, an attacker would need to obtain a signature over `authenticator_data || SHA256(client_data_json)` from the real private key holder's authenticator during a *different* ceremony (e.g., a registration/attestation flow) where the challenge happens to match a transaction's SHA3-256 digest. In practice:
- WebAuthn registration (`navigator.credentials.create`) does not produce an `AuthenticatorAssertionResponse` with a raw signature over attacker-chosen data in the same way `get` does — attestation signatures are typically over different data (attestationObject) and don't share the assertion signing algorithm output format required here.
- The exploit path described in the question requires the attacker to *already* get the legitimate signer to sign a create-ceremony challenge equal to a transaction's digest, which functions like a cross-ceremony confusion/replay attack, not a way to forge a new signature without any interaction from the real key holder.

This is a real correctness/spec-compliance defect (missing ceremony-type binding) but does not on its own allow an *unprivileged attacker with no interaction from the legitimate signer* to admit an arbitrary transaction — it still requires the legitimate signer's private key to produce a valid signature over the crafted verification_data during some ceremony. It does not create a novel admission path independent of key possession, and does not by itself break sender/signer/replay/domain guarantees for accounts that don't opt into WebAuthn signing.

### Likelihood Explanation
Low-to-moderate as a standalone admission-boundary bypass. It requires a scenario where the legitimate WebAuthn credential holder is tricked (via a malicious relying-party website or hijacked client) into performing a `create` ceremony whose `challenge` matches an attacker-selected transaction's SHA3-256 digest, and where the WebAuthn assertion structure/signature format for that ceremony coincidentally matches what `verify()` expects (raw ECDSA over `authenticator_data || SHA256(client_data_json)`). This is more of a cross-ceremony/type-confusion defense-in-depth gap than a directly-exploitable "unprivileged attacker submits crafted authenticator, no signer interaction needed" admission bypass.

### Recommendation
Add an explicit assertion in `PartialAuthenticatorAssertionResponse::verify` that `collected_client_data.ty == ClientDataType::Get`, returning an error otherwise, matching WebAuthn §7.2 step 11 and closing off any future cross-ceremony confusion risk regardless of how authenticator/relying-party implementations evolve.

### Proof of Concept
Construct a `CollectedClientData` with `ty: ClientDataType::Create` (or raw JSON `"type":"webauthn.create"`) but identical `challenge` (matching a target raw transaction's SHA3-256 digest), sign `authenticator_data || SHA256(client_data_json)` with the real private key (as would occur if the signer were tricked into a create-ceremony with this challenge), and call `PartialAuthenticatorAssertionResponse::verify(&raw_txn, &any_public_key)`. Based on the code at [4](#0-3) , verification would return `Ok(())` because `ty` is never checked — confirming the missing ceremony-type check, though actually obtaining such a signature from the legitimate key holder without their cooperation is a separate, non-trivial barrier not solved by this bug alone.

    /// In our adaptation of WebAuthn, the `challenge` provided to `authenticatorGetAssertion`
    /// is the SHA3-256 digest of the `RawTransaction`.
    ///
    /// This function should do the following:
    /// 1. Verify `actual_challenge` and expected challenge from message are equal
    /// 2. Construct `verification_data` as the binary concatenation of
    ///    authenticator_data and SHA-256(client_data_json)
    /// 3. Signature verification
    ///
    /// See WebAuthn §6.3.3 `authenticatorGetAssertion` for more info
    pub fn verify<T: Serialize + CryptoHash>(
        &self,
        message: &T,
        public_key: &AnyPublicKey,
    ) -> Result<()> {
        let collected_client_data: CollectedClientData =
            serde_json::from_slice(self.client_data_json.as_slice())?;
        let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())
            .map_err(|e| anyhow!("Failed to decode challenge bytes {:?}", e))?;

        // Check if expected challenge and actual challenge match. If there's no match, throw error
        verify_expected_challenge_from_message_matches_actual(message, challenge_bytes.as_slice())?;

        // Generates binary concatenation of authenticator_data and hash(client_data_json)
        let verification_data = generate_verification_data(
            self.authenticator_data.as_slice(),
            self.client_data_json.as_slice(),
        );

        // Note: We must call verify_arbitrary_msg instead of verify here. We do NOT want to
        // use verify because it BCS serializes and prefixes the message with a hash
        // via the signing_message function invocation
        match (&public_key, &self.signature) {
            (
                AnyPublicKey::Secp256r1Ecdsa { public_key },
                AssertionSignature::Secp256r1Ecdsa { signature },
            ) => signature.verify_arbitrary_msg(&verification_data, public_key),
            _ => Err(anyhow!(
                "WebAuthn verification failure, invalid key, signature pairing"
            )),
        }
    }
