### Title
Reentrancy in `requestERC20Transfer` / `_requestERC20Transfer` via ERC777-compatible token hooks allows double-spending of bridge reserves — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and its internal helper `_requestERC20Transfer` lack a `nonReentrant` modifier and increment `requestNonce` **after** all external token calls. If a registered ERC20 token supports transfer-flow hooks (ERC777-style `tokensToSend`/`tokensReceived`), an attacker can reenter the bridge through `onERC20Received` before `requestNonce++` executes, emitting two `RequestValueTransfer` events with **different** nonces from a single token deposit. The counterpart bridge handles both nonces independently, paying out double the bridged value and draining the bridge's locked reserves.

---

### Finding Description

`BridgeTransferKLAY` explicitly inherits `ReentrancyGuard` and marks both `handleKLAYTransfer` and `_requestKLAYTransfer` with `nonReentrant`. The comment in `BridgeFee._payKLAYFeeAndRefundChange` even states: *"Caller of this function must be nonReentrant."* [1](#0-0) [2](#0-1) [3](#0-2) 

`BridgeTransferERC20` inherits neither `ReentrancyGuard` nor applies `nonReentrant` to any of its entry points. The critical ordering in `_requestERC20Transfer` is:

1. External call: `_payERC20FeeAndRefundChange` → `IERC20.safeTransfer(feeReceiver, fee)` and `IERC20.safeTransfer(from, feeRefund)` — both external calls to token contract.
2. External call: `ERC20Burnable.burn(_value)` (mint/burn mode).
3. `emit RequestValueTransfer(..., requestNonce, ...)`.
4. **`requestNonce++`** — state update happens last. [4](#0-3) 

`requestERC20Transfer` (the public 2-step entry point) also calls `safeTransferFrom` before `_requestERC20Transfer`: [5](#0-4) 

`onERC20Received` is `public` with no access control and directly calls `_requestERC20Transfer(msg.sender, ...)`: [6](#0-5) 

The `_payERC20FeeAndRefundChange` function performs two `safeTransfer` calls (fee to `feeReceiver`, refund to `from`) with no reentrancy protection: [7](#0-6) 

---

### Impact Explanation

If a registered ERC20 token implements ERC777-style hooks (e.g., `tokensToSend` called on the sender before balances update, or `tokensReceived` called on the recipient after), the following occurs during `requestERC20Transfer`:

1. `safeTransferFrom(attacker, bridge, V+feeLimit)` triggers `tokensToSend` on the attacker's contract **before** the bridge receives tokens.
2. Attacker's hook calls `bridge.onERC20Received(attacker, to, V, feeLimit, data)`.
3. `_requestERC20Transfer` executes with `requestNonce = N`: pays fee from bridge's existing reserves, emits `RequestValueTransfer(nonce=N)`, increments `requestNonce` to `N+1`.
4. Control returns; `safeTransferFrom` completes — bridge now holds `V+feeLimit` new tokens.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
