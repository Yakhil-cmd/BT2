### Title
Cross-organization Team ID collision in `MembershipHandler` allows escalation into `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler` resolves the `Team` record to mutate solely by the GitHub-global `team.id` field taken from the webhook payload, and only sets `team.organization` when the record is first created. It never re-verifies that the organization which authenticated the current webhook (the org whose `webhook_secret` matched `X-Hub-Signature`) is the same organization that owns the `Team` row being updated. In a multi-organization Shipit deployment, this breaks the intended binding `organization_that_signed_the_webhook == organization_that_owns_the_authorization_team`.

### Finding Description
`WebhooksController#verify_signature` looks up which GitHub App/organization secret to verify against using an attacker-influenced field of the payload itself, then hands the fully-parsed JSON to the registered handlers: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` verifies the signature using whichever organization's `webhook_secret` was resolved by `repository_owner`/`organization.login`: [3](#0-2) 

For `membership` events, that means: whichever organization is named in `payload["organization"]["login"]` is the one whose secret must match — i.e., the webhook is only proven to come from *that* organization, nothing more.

`MembershipHandler` then resolves the `Team` to modify purely by the numeric, GitHub-global `team.id`, and only assigns `organization` on first creation — it is never checked against the authenticated organization on subsequent events: [4](#0-3) 

`Team#add_member` unconditionally appends the resolved `member` (fetched by login via the GitHub API) to the team: [5](#0-4) 

Team membership is exactly what governs application-wide authorization: [6](#0-5) [7](#0-6) 

**Binding broken:** `organization authenticated by the webhook signature == organization that legitimately owns/administers the `Team` record being mutated`. The signature only proves the request came from *some* configured organization (whichever `organization.login`/`repository.owner.login` names), but `find_or_create_team!` trusts the payload's numeric `team.id` to select *which* `Team` row (potentially belonging to a *different*, more privileged organization) gets its membership mutated.

### Impact Explanation
If a Shipit installation is configured with multiple GitHub organizations (as explicitly supported per `docs/setup.md`'s "Using Multiple Github Applications" section and `Shipit.github(organization:)`), and `Shipit.github_teams` is configured to restrict access to a team belonging to one trusted organization (Org A), while a second, lower-trust organization (Org B) is also onboarded (e.g., for a different set of repositories/stacks), an administrator of Org B can trigger a real, validly-signed `membership` webhook for a team they control in Org B, but set the JSON `team.id` field to the numeric GitHub team ID belonging to Org A's authorization team. Because `MembershipHandler#find_or_create_team!` finds the *existing* `Team` row purely by `github_id` and skips re-assigning `organization` for existing records, and because `Team#add_member` performs no organization cross-check, the handler adds an arbitrary GitHub login (`member.login`, also attacker-controlled in the payload) as a member of Org A's authorization team. That user (or the attacker themselves) then satisfies `User#authorized?` and gains full access to Shipit — i.e., escalation into `Shipit.github_teams` authorization, one of the explicitly in-scope High-impact outcomes.

### Likelihood Explanation
Exploitability requires: (1) a multi-organization Shipit configuration where at least one lower-trust organization is onboarded alongside the trusted authorization organization, and (2) the attacker to be able to trigger a real `membership` webhook event from that lower-trust org (i.e., be an owner/admin of a team in that org — a legitimate, non-Shipit-privileged capability) and (3) knowledge/guessability of the target team's numeric GitHub `id` (team IDs are sequential/global and often discoverable via the GitHub API or UI for teams the attacker can view). This is a realistic configuration for organizations that federate Shipit across a trusted "ops" GitHub org and other less-trusted engineering orgs.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the `Team#organization` of any *existing* record (case-insensitively) before mutating membership, and reject (or scope the lookup by both `github_id` and `organization`) rather than trusting the raw numeric `team.id` across organizations.

### Proof of Concept
1. Shipit is configured with two GitHub orgs: `trusted-org` (whose team `trusted-org/admins`, github team id `1000`, is set in `Shipit.github_teams`) and `attacker-org` (onboarded for unrelated stacks), each with its own `webhook_secret`.
2. Attacker is an owner of `attacker-org` and creates/controls a team there.
3. Attacker triggers (or crafts, since they control their org's GitHub App installation flow/team) a `membership` webhook, legitimately signed with `attacker-org`'s `webhook_secret`, with body:
```json
{
  "action": "added",
  "team": { "id": 1000, "name": "Admins", "slug": "admins", "url": "..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker" }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `attacker-org`'s real secret. [1](#0-0) 
5. `MembershipHandler#process` finds the pre-existing `Team` with `github_id: 1000` (created earlier from a legitimate `trusted-org` event) and calls `team.add_member(User.find_or_create_by_login!("attacker"))`. [8](#0-7) 
6. `attacker` is now a member of `trusted-org/admins`, and `User#authorized?` returns true, granting full Shipit access. [6](#0-5)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
