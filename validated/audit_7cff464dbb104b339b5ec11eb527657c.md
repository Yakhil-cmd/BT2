### Title
Webhook signature verification is keyed on `repository.owner.login`, but processing acts on the unrelated, unverified `repository.full_name` field - allowing forged commit-status/push events for any repository whose organization has no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body. Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the actual `Repository`/`Stack` to mutate using a completely different field of the same body: `repository.full_name`. Nothing ties these two fields together, and `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for the selected organization. This breaks the binding: `organization authenticated (repository.owner.login) == repository actually written (repository.full_name)`.

### Finding Description
`verify_signature` reads the verification org from the payload before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config from `secrets.github`, which is an explicitly supported/documented multi-org schema: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for the resolved org (documented as optional in the setup guide: "Webhook secret (optional)"): [5](#0-4) [6](#0-5) 

Once `verify_signature` passes, `WebhooksController#create` dispatches to handlers using the raw JSON body: [7](#0-6) 

Every handler ignores `repository.owner.login` entirely and instead resolves the target `Repository`/`Stack` from `repository.full_name`: [8](#0-7) [9](#0-8) 

For example, `StatusHandler` directly creates a `Status` on an existing `Commit` (matched purely by SHA, with no repository/org scoping check) using attacker-supplied `state`, `description`, `target_url`: [10](#0-9) 

`PushHandler` similarly resolves stacks via `repository.full_name` and schedules a resync using an attacker-chosen `after` SHA: [11](#0-10) 

The equality that should hold — "the organization whose signature verified the request == the organization that owns the repository being mutated" — is never checked. `repository_owner` (used only for key selection during verification) and `repository.full_name` (used for the actual write) are two independent, attacker-controlled fields in the same JSON body, and the code never cross-validates them.

### Impact Explanation
If any organization configured in `secrets.github` lacks a `webhook_secret` (explicitly documented as optional), `verify_webhook_signature` returns `true` for **any** payload claiming that `repository.owner.login`, regardless of the `X-Hub-Signature` header contents. An unauthenticated external attacker can then POST an arbitrary JSON body to `/webhooks` with:
- `repository.owner.login` = the name of the secret-less organization (used only to pass verification),
- `repository.full_name` = any other organization/repository actually tracked by the same Shipit instance (used for the real write).

This lets the attacker inject forged `commit_status` events (`StatusHandler`) for arbitrary commits of a repository they have no relationship to, or trigger `push`-driven resyncs (`PushHandler`) with attacker-chosen `after` SHAs. Forged commit statuses can flip CI/deployability gating used by `Shipit::CommitChecks`/`DeploySpec` safety checks, enabling an unauthorized deploy of a stack the attacker does not control — meeting the "unauthorized deploy" / cross-repository-write bar.

### Likelihood Explanation
Exploitability depends entirely on operational configuration (a secret-less org entry existing in a multi-org `secrets.github`), which the project's own setup docs explicitly present as an acceptable, optional configuration. No credentials, tokens, or GitHub access are required by the attacker — only knowledge (or discovery, since a 422 vs. processed response acts as an oracle) of an organization name configured without a `webhook_secret` on the target Shipit instance. This is a genuine unauthenticated boundary crossing, distinct from cases requiring possession of `webhook_secret`, `api_clients_secret`, or a GitHub App private key.

### Recommendation
- Verify the webhook HMAC using the config resolved from the organization/owner that is *also* asserted to own the repository the handler will mutate; do not allow `repository_owner` (verification key selection) and `repository.full_name` (write target) to diverge.
- Do not treat a blank/missing `webhook_secret` as "verification passed" — require an explicit opt-in (e.g., `Shipit.disable_webhook_signature_verification`) instead of silently defaulting to `true`.
- In each handler, re-derive/validate that the resolved `Repository#owner` matches the organization that was used to select the verification secret before mutating any commit/stack state.

### Proof of Concept
Preconditions: the target Shipit instance uses the multi-org `secrets.github` schema, and organization `secretless-org` is configured without a `webhook_secret`; a repository `victim-org/victim-repo` is tracked by the instance with commit `abcdef123...` present.

1. Attacker sends:
```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (any value)
Content-Type: application/json

{
  "repository": { "owner": { "login": "secretless-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "abcdef123...",
  "state": "success",
  "context": "ci/forged",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
2. `verify_signature` resolves `Shipit.github(organization: "secretless-org")`; because that org has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — the bogus `X-Hub-Signature` is never actually checked.
3. `StatusHandler#process` matches `Commit.where(sha: "abcdef123...")` in `victim-org/victim-repo` (found via `full_name`, unrelated to `secretless-org`) and creates a forged `success` status on that commit, potentially satisfying deploy-safety checks for a stack the attacker never had access to.   def github(organization: github_default_organization)
```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
```
