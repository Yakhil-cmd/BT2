### Title
Webhook signature verification is a no-op when `webhook_secret` is unset, allowing unauthenticated forgery of `membership` events to self-escalate into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects a `GitHubApp` by the attacker-controlled `repository`/`organization` field in the JSON body, then delegates the actual authenticity check to `GitHubApp#verify_webhook_signature`. That method treats a missing `webhook_secret` as automatic success, so any organization configured without a webhook secret (the documented default, e.g. `webhook_secret: # nil` in `config/secrets.development.example.yml` and `docs/setup.md`) makes the whole `/webhooks` endpoint unauthenticated. Combined with `MembershipHandler`, an unauthenticated caller can forge a `membership` event that adds an arbitrary existing `User` to a `Team` record matching the org/slug of a `Shipit.github_teams`-authorized team, bypassing the team-membership gate entirely.

### Finding Description
- `verify_signature` picks the `GitHubApp` instance via `repository_owner`, derived purely from the untrusted JSON payload: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

- The `webhook_secret: nil` value is a documented, supported configuration state (not an edge case), shown as the default in both the single-org and multi-org example configs: [4](#0-3) [5](#0-4) 

- When that condition holds for any configured organization, the request is processed with zero authentication. `MembershipHandler#process` then creates/finds a `Team` keyed by an attacker-chosen `github_id`, sets its `organization`/`login` from attacker-controlled fields, and adds an attacker-chosen `member` (an existing `User`, found purely by login) to that team: [6](#0-5) 

- Team membership is exactly what gates the entire application. `User#authorized?` checks membership against `Shipit.github_teams`: [7](#0-6) [8](#0-7) 

The equality broken: **organization/signature that "authenticated" the webhook request ≠ the `Team`/`User` binding that is actually written and later trusted for authorization.** GitHub's real webhook signature is meant to bind the entire payload (including `team`, `organization`, `member`) to a secret only GitHub and the operator know; when that secret is absent for one configured org, the binding collapses and the payload's team/member identity is accepted unauthenticated.

### Impact Explanation
An unauthenticated, credential-less caller can add themselves (or any known `User` row) to a `Team` matching a `Shipit.github_teams`-authorized org/slug, immediately satisfying `current_user.authorized?` and unlocking the entire Shipit UI/API for that user — deploys, rollbacks, merges, and stack management. This matches the "escalation into `Shipit.github_teams` authorization" High-impact category, and given deploy/rollback capability that follows, it functions as a path to unauthorized deploys as well.

### Likelihood Explanation
Requires only that at least one configured GitHub organization in `Shipit.secrets.github` has no `webhook_secret` set — the documented default in the setup guide and example configs — and that the target `User` login and target team `github_id`/`slug`/`organization` combination (which mirrors the real, authorized team) is knowable or guessable/observable from the Shipit UI (team lists, member lists are visible to any current member). No GitHub credentials, Shipit session, or API token are needed to hit `/webhooks`.

### Recommendation
- Require `webhook_secret` to be present and fail closed (reject with 422) rather than default-approve when it is blank.
- Scope `MembershipHandler` writes to organizations that are actually configured (verify `params.organization.login` matches the same org used for `Shipit.github` lookup) rather than trusting payload fields verbatim.
- Consider not allowing webhook-driven team/membership mutation to affect authorization-relevant teams without additional verification (e.g., re-syncing via the authenticated GitHub API instead of trusting the webhook body directly).

### Proof of Concept
1. Configure (or find deployed) Shipit with a multi-org `github:` config where at least one org key has `webhook_secret: nil` (per `docs/setup.md`/example configs).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999999, "name": "Fake", "slug": "<slug-of-authorized-team>", "url": "https://example.com" },
  "organization": { "login": "<org-with-nil-webhook-secret>" },
  "member": { "login": "<attacker-known-existing-user-login>" }
}
```
3. `verify_signature` resolves the `GitHubApp` for `<org-with-nil-webhook-secret>`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no `X-Hub-Signature` header needed.
4. `MembershipHandler#process` creates/finds the `Team` and calls `team.add_member(member)`, adding the target user to a team object; if the `github_id`/`slug`/`organization` match an existing authorized team, that user now passes `User#authorized?` and gains full access to Shipit.

Note: I could not verify within the index the exact `Team` model matching logic used by `Shipit.github_teams` (e.g., how `handle` is derived and matched to `oauth_teams` config) since `app/models/shipit/team.rb` was not returned by search; this detail should be confirmed before treating this as fully proven, but the authorization-check code path (`User#authorized?`) and the unauthenticated webhook write path are both directly confirmed above.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

          Team.find_or_create_by!(github_id: params.team.id) do |team|

          end
        end
```
