## Finding

### Title
Duplicate public keys in a `MultiKey` account allow a single key holder to satisfy a K-of-N threshold alone - ([File: types/src/transaction/authenticator.rs])

### Summary
`MultiKey`/`MultiKeyAuthenticator` verification checks admission by counting the number of *bitmap positions* with valid signatures against a threshold, rather than the number of *distinct* signing keys. Because nothing in `MultiKey::new` or `MultiKeyAuthenticator::verify`/`to_single_key_authenticators` rejects duplicate public keys in the key list, an account can be created with the same public key repeated at multiple indices. A holder of that one key can then produce a signature once and reuse it against two (or more) indices to satisfy a "K-of-N" threshold that was supposed to require K independent parties.

### Finding Description
`MultiKeyAuthenticator::verify` and `to_single_key_authenticators` only validate:
- number of signatures equals number of set bits in `signatures_bitmap`,
- `signatures.len() >= public_keys.signatures_required()`,
- each signature verifies against the public key at its own bitmap index, [1](#0-0) 

but never verifies that the underlying public keys referenced by distinct bitmap indices are actually distinct. `MultiKeyAuthenticator::new` similarly only guards against duplicate *indices*, not duplicate *keys*: [2](#0-1) 

The repo's own unit test demonstrates this directly: a `MultiKey` is constructed with `keys = [sender0_pub, sender1_pub, sender1_pub]` (index 1 and 2 are the *same* key) and threshold 2: [3](#0-2) 

The test then signs with `sender1`'s key twice (once claimed at index 1, once at index 2) using the identical signature value, and `signed_txn.verify_signature()` **succeeds**: [4](#0-3) 

This is checked in as passing, expected behavior (not a negative/"should fail" test), confirming the code path allows it. Because `AuthenticationKey::multi_key(multi_key)` derives the account address purely from the serialized key list (hash of the `MultiKey` bytes, including the threshold byte), an attacker who controls the account address generation (i.e., who creates the multi-key account in the first place, e.g., a "2-of-3 co-signer vault" whose other two nominal signers are attacker-controlled duplicates of one real key) can present what looks like a 2-of-3 or K-of-N account but is trivially satisfiable by one key holder alone.

### Impact Explanation
Any account configured as `MultiKey` with a repeated public key silently degrades its security threshold: a transaction that requires "2 signatures out of 3 keys" (intended to require cooperation of two distinct parties/devices) can be authorized by one party alone. Since transaction admission (`TransactionAuthenticator::verify` → `AccountAuthenticator::verify` → `MultiKeyAuthenticator::verify`) is exactly the boundary that is supposed to bind the authenticator to "the intended account set," this is a wrong-signer-set admission bypass: the VM/mempool will accept and execute transactions as validly authorized by the full "approval set" when in fact only a subset of distinct keys approved it.

### Likelihood Explanation
This requires the multi-key account to have been provisioned with duplicate keys in the first place (either through user/wallet error, or intentionally by a malicious co-signer who convinces others that a 2-of-3 vault is safe while secretly registering the same key twice under two of the three slots). It is not an unprivileged, remote, one-shot exploit against an arbitrary existing account with distinct keys — it requires control over (or a defect in) the key-list construction at account-authentication-key-derivation time. This limits likelihood to a specific misconfiguration/social-engineering scenario rather than a universal bypass, but there is no on-chain or client-side validation anywhere in the codebase found that would catch or reject such a duplicate-key `MultiKey` construction before or during admission.

### Recommendation
- In `MultiKey::new` (and/or `MultiKeyAuthenticator::new`), reject construction when the public-key list contains duplicate entries, so that "K-of-N" is enforced over N *distinct* signing identities.
- Additionally/alternatively, enforce distinctness in `to_single_key_authenticators`/`verify` at signature-checking time so that duplicate-key `MultiKey` accounts (if any already exist on-chain) cannot have their threshold satisfied by reusing one key's signature across multiple bitmap slots.
- Add negative test coverage asserting that signing with the same key at two indices of a "K-of-N" `MultiKey` fails to meet the threshold.

### Proof of Concept
The existing repository test `verify_multi_key_auth` is itself the PoC:
1. Construct `multi_key = MultiKey::new(vec![sender0_pub, sender1_pub, sender1_pub], 2)` (duplicate `sender1_pub` at indices 1 and 2). [5](#0-4) 
2. Sign the raw transaction once with `sender1`'s private key, producing `signature1`. [6](#0-5) 
3. Build `MultiKeyAuthenticator::new(multi_key, vec![(1, signature1.clone()), (2, signature1.clone())])` — i.e., claim the same signature satisfies both index 1 and index 2. [7](#0-6) 
4. Call `signed_txn.verify_signature()` — it returns `Ok(())`, meeting the "2-of-3" threshold using only one distinct key holder (`sender1`), never involving `sender0`. [8](#0-7) 

Note: I was not able to fully confirm within this session whether any higher-level guard (e.g., in `AuthenticationKey`/account-creation flow or wallet tooling) elsewhere in the broader Aptos stack rejects duplicate-key `MultiKey` construction before an authentication key is derived on-chain; the index/type-level code shown here does not. This uncertainty affects the practical likelihood but not the presence of the underlying signature-verification defect.

impl MultiKeyAuthenticator {
    pub fn new(public_keys: MultiKey, signatures: Vec<(u8, AnySignature)>) -> Result<Self> {
        ensure!(
            public_keys.len() < (u8::MAX as usize),
            "Too many public keys, {}, in MultiKeyAuthenticator.",
            public_keys.len(),
        );

        let mut signatures_bitmap = aptos_bitvec::BitVec::with_num_bits(public_keys.len() as u16);
        let mut any_signatures = vec![];

        for (idx, signature) in signatures {
            ensure!(
                (idx as usize) < public_keys.len(),
                "Signature index is out of public key range, {} < {}.",
                idx,
                public_keys.len(),
            );
            ensure!(
                !signatures_bitmap.is_set(idx as u16),
                "Duplicate signature index, {}.",
                idx
            );
            signatures_bitmap.set(idx as u16);
            any_signatures.push(signature);
        }

        Ok(MultiKeyAuthenticator {
            public_keys,
            signatures: any_signatures,
            signatures_bitmap,
        })
    }

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }
