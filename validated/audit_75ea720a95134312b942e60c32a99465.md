### Title
`handleERC20Transfer` and `handleERC721Transfer` do not validate `_tokenAddress` against the registered token list, allowing operators to transfer or mint arbitrary tokens — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge contract enforces a registered-token allowlist (`registeredTokens`) on the **request** (outbound) path but not on the **handle** (inbound) path. Any bridge operator — whose role has a default threshold of 1 — can call `handleERC20Transfer` or `handleERC721Transfer` with an arbitrary, unregistered `_tokenAddress`. In lock mode this drains any ERC-20 balance the bridge holds; in mint mode it mints tokens on any contract for which the bridge holds the minter role.

---

### Finding Description

`BridgeTokens` defines the `onlyRegisteredToken` modifier that gates access to the allowlist: [1](#0-0) 

The **request** functions correctly apply both `onlyRegisteredToken` and `onlyUnlockedToken`: [2](#0-1) [3](#0-2) 

The **handle** functions apply only `onlyOperators` — no token validation whatsoever: [4](#0-3) [5](#0-4) 

The `BridgeOperator` constructor sets the default threshold to **1**, meaning a single operator can unilaterally execute a handle call without any co-signer: [6](#0-5) 

The voting key used inside `_voteValueTransfer` is `keccak256(msg.data)`, which includes `_tokenAddress` as a parameter. This means operators must agree on the same `_tokenAddress` to reach threshold — but there is no check that the agreed-upon address is registered. [7](#0-6) 

---

### Impact Explanation

**Lock mode** (`modeMintBurn == false`): The handle function executes `IERC20(_tokenAddress).safeTransfer(_to, _value)`. An operator can pass any ERC-20 address for which the bridge holds a balance (e.g., tokens accidentally sent to the bridge, or a second registered token pair whose address is known). This results in an unauthorized transfer of bridged assets out of the bridge contract.

**Mint mode** (`modeMintBurn == true`): The handle function executes `ERC20Mintable(_tokenAddress).mint(_to, _value)`. If the bridge holds the minter role on any token contract (which is the standard setup for mint/burn bridges), an operator can mint an arbitrary amount of that token to any address, inflating supply without a corresponding cross-chain deposit.

Both cases match the allowed impact: **unauthorized transfer or mint of bridged assets**.

---

### Likelihood Explanation

- The default `operatorThresholds[ValueTransfer]` is **1**, so a single operator can execute this without any co-signer.
- Bridge operators are semi-trusted: they are registered by the owner but their keys can be compromised, or a buggy operator implementation can relay an incorrect `_tokenAddress`.
- The Go-layer bridge manager (`handleRequestValueTransferEvent`) does validate the counterpart token before calling `HandleERC20Transfer`, but this is off-chain logic. The on-chain contract provides no enforcement, so any operator can bypass the Go layer and call the Solidity function directly. [8](#0-7) 

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` (and optionally `onlyUnlockedToken(_tokenAddress)`) to both `handleERC20Transfer` and `handleERC721Transfer`, mirroring the validation already present on the request side:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // <-- add this
    onlyUnlockedToken(_tokenAddress)     // <-- add this
{
    ...
}
```

Apply the same change to `handleERC721Transfer`.

---

### Proof of Concept

```solidity
// Assume: bridge deployed in lock mode, operator threshold = 1 (default)
// Assume: tokenA is registered, tokenB is NOT registered but bridge holds 1000 tokenB
//         (e.g., accidentally sent or from a deregistered pair)

// Attacker is a registered operator (or has compromised one operator key)
bridge.handleERC20Transfer(
    bytes32(0),          // fake requestTxHash (not yet seen)
    attacker,            // _from (irrelevant)
    attacker,            // _to   (attacker receives)
    address(tokenB),     // _tokenAddress: UNREGISTERED token
    1000e18,             // _value
    999,                 // _requestedNonce (any unused nonce)
    1,                   // _requestedBlockNumber
    ""                   // _extraData
);
// Result: tokenB.balanceOf(attacker) increases by 1000e18
// No revert — onlyRegisteredToken is never checked
```

The nonce-based replay protection (`_lowerHandleNonceCheck`, `closedValueTransferVotes`) only prevents the same nonce from being handled twice; it does not prevent a fresh nonce from being used with an arbitrary token address. [9](#0-8)

        bytes32 _requestTxHash,

        uint64 _requestedNonce,
        uint64 _requestedBlockNumber,

        public
        onlyOperators

        if (!_voteValueTransfer(_requestedNonce)) {
            return;

            _extraData

        }
