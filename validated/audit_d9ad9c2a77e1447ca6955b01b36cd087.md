### Title
Webhook signature verification selects the wrong organization's secret from unauthenticated payload data, allowing cross-organization commit-status forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate an inbound webhook against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified** JSON body, before the HMAC signature has been checked. Every downstream `Handler` (e.g. `PushHandler`, the `status` handler) then independently re-reads `repository.full_name` from that same unverified body to decide which `Repository`/`Stack` to act on. Because these two payload fields are never cross-checked against each other, an attacker who knows the `webhook_secret` for *any one* organization configured on a shared Shipit instance can sign a forged event whose `repository.owner.login` matches that known-secret organization, while `repository.full_name` names a completely different, victim organization's repository. The signature check passes (it validates against the attacker's own org secret), yet the handler acts on the victim's repository/stack.

### Finding Description
- `verify_signature` derives the org used for HMAC validation purely from payload content: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization: repository_owner)` resolves to a specific per-organization webhook secret (raising `GithubOrganizationUnknown` if not configured), confirming the engine supports multiple, independently-configured organizations/GitHub Apps on one instance: [3](#0-2) [4](#0-3) 

- The verified field (`repository.owner.login`/`organization.login`) is never compared against the field the handlers actually use to select the target repository: `repository.full_name`. [5](#0-4) [6](#0-5) 

- The `status` webhook handler persists attacker-controlled fields (`state`, `description`, `context`, `target_url`) verbatim onto a `Commit`'s `Status`, with no independent GitHub API confirmation of the claimed status: [7](#0-6) 

This breaks the intended binding: **the organization whose secret authenticated the request must equal the organization owning the repository being written to**. Before the attack: `repository_owner` (used to pick the secret) == owner segment of `repository.full_name` (used to pick the target) for any legitimate GitHub-originated payload, because GitHub itself fills in both fields consistently. After a forged request: an attacker sets `repository.owner.login = "orgA"` (whose secret they know, e.g. because they administer Org A's GitHub App on this shared Shipit instance) but `repository.full_name = "orgB/victim-repo"`. `verify_signature` validates successfully against Org A's secret, and the handler then writes a `Status` (or triggers `sync_github`) against Org B's stack — an organization the attacker has no credentials for.

### Impact Explanation
This is a cross-organization forgery of GitHub state on a multi-tenant Shipit deployment: an attacker who is only authorized within one configured organization can inject fabricated commit statuses, pushes, or check-suite/PR events attributed to a different organization's repository. Since deploy gating relies on `ci.require`/`blocking_statuses` computed from stored `Status` records (`DeploySpec#required_statuses`, `#blocking_statuses`), injecting a forged "success" `Status` for a commit in a victim stack can satisfy CI requirements that were never actually met, enabling an unauthorized deploy — matching the required "unauthorized deploy" Critical/High impact criterion.

### Likelihood Explanation
Exploitability requires: (1) the Shipit deployment to host more than one organization/GitHub App config (a supported, documented capability via `Shipit.github(organization:)`), and (2) the attacker to know the webhook secret of at least one such organization (realistic if they administer that org's GitHub App, e.g. as a tenant/customer of a shared Shipit instance). Given that constraint, forging the cross-org payload is trivial (no cryptographic secret of the victim org is needed) — this is the same underlying bug class as the source report: a validated field (`repository_owner`/authentication scope) not covering the field actually acted upon (`repository.full_name`/target of the write).

### Recommendation
Compute the organization used for signature verification directly from `repository.full_name` (splitting owner/name) or from the resolved `Repository` record's stored `owner`, never trust `repository.owner.login`/`organization.login` as an independent field. Additionally, cross-check that `repository.owner.login` (when present) matches the owner segment of `repository.full_name` before accepting the payload, and reject on mismatch.

### Proof of Concept
1. Attacker administers Org A's GitHub App on a shared Shipit instance and knows Org A's `webhook_secret`.
2. Attacker crafts a `status` (or `push`) webhook JSON body with:
   - `repository.owner.login = "orgA"`
   - `repository.full_name = "orgB/victim-repo"`
3. Attacker computes `X-Hub-Signature` using Org A's known `webhook_secret` over the raw body, per `WebhooksController#verify_signature`: [1](#0-0) 
4. `verify_signature` resolves `repository_owner` → `"orgA"`, fetches Org A's app, validates the signature successfully.
5. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs; the handler resolves the target repo/stack via `payload.dig('repository', 'full_name')` → `"orgB/victim-repo"`, and creates/updates a `Status` on that victim stack's commit using the attacker-supplied `state`/`context`, as demonstrated by the existing test pattern: [7](#0-6) 
6. If `orgB/victim-repo`'s `shipit.yml` gates deploys on that `context` via `ci.require`, the forged "success" status can unblock an otherwise-blocked deploy of the victim's stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
