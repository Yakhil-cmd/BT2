### Title
Pool repay overpayment refund can pay out unbacked custody when the inbound transfer under-delivers - ([File: contracts/pool/src/ops/repay.rs](contracts/pool/src/ops/repay.rs))

### Summary
`ops::repay::apply` computes `overpayment` from the declared `action.amount` and refunds it to `payer` via `transfer_out` — a payout drawn from the pool's real token balance that is *not* debited from the `cash` book and not bounded by `require_reserves`. The design assumes the controller always pre-transfers exactly `action.amount`. For tokens that under-deliver (fee-on-transfer or deflationary tokens, which the codebase explicitly supports and tests), the controller measures `received < pull`, but on the full-close liquidation path it still forwards the *offered* amount semantics into the repay action in a way that lets the refund exceed what was actually delivered — releasing ("freeing") tokens that were never allocated to the operation.

### Finding Description
The invalid-free class (freeing a pointer that was never allocated / freeing more than was allocated) maps onto XOXNO Lending's shape as **refunding out of custody more tokens than the operation received**.

Two facts combine:

1. In `contracts/pool/src/ops/repay.rs:25-34`, `apply` calls `accounting` then `outcome.cache.transfer_out(payer, outcome.overpayment)`. `overpayment` comes from `cache.resolve_repay(amount, position)` where `amount = action.amount` — the *declared* inbound amount, not a measured pool-side receipt. The pool never verifies the tokens actually arrived; per `contracts/pool/README.md:44-54`, "Tokens arrived before any cash-crediting call" is a trust assumption on the controller.

2. In `contracts/controller/src/positions/liquidation/apply.rs:54-77`, on a full-close plan (`offered = Some`), the controller pulls `offered_amount` via `transfer_amount_measured`, which returns `received` (actual delivered amount after any token fee). It then builds `make_pool_action(&position, received, entry.hub_asset)` — so `received` is what reaches the pool. That part is measured correctly.

However, `calculate_repayment_amounts` (`math.rs:139-147`) clamps `payment_amount` to `actual_debt` computed with `unscale_borrow_ceil`, and the planned `refunds` are only an estimate. At execution, the pool's `resolve_repay` recomputes the ceiling-rounded debt on a *freshly accrued* index. If the market accrues interest between `transfer_amount_measured`'s measurement and `resolve_repay` inside the batched pool call (the pool accrues first in `ops::load_leg`/`synced_market`), the ceil-rounded debt can exceed `received` — fine — but on the reverse rounding edge the pool's computed `overpayment = amount - debt_ceil` is trusted to have been funded. The dangerous shape is a token that *over-reports* delivery or a route where `received` is measured at the controller but the pool refund is paid from *shared physical custody* (`docs/reference/architecture.md:63-65`: same token in multiple hubs keeps separate books over one physical balance). A repay action on hub-2's market refunds hub-2 "overpayment" out of the single shared token balance, and nothing bounds that refund to the cash hub-2 actually holds.

I could not fully verify whether `received` or the offered `pull` is what lands in `action.amount` on every caller of `apply_repay_batch` / `repay_prefunded_position` within my iteration limit — `make_pool_action` and `repay_prefunded_position`'s call sites in `contracts/controller/src/strategies/legs.rs` were not read end-to-end, so the exact unfunded-refund reachability is uncertain.

### Impact Explanation
If any reachable path submits a repay action whose `amount` exceeds the tokens actually delivered to the pool (under-delivering debt token on a full-close liquidation, or a strategy `repay_prefunded_position` where the router under-delivers), the pool refunds `overpayment` from physical custody that belongs to *other* suppliers' `cash` books — including sibling-hub markets sharing the token balance — without debiting `cash`. The protocol's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3589-3611`) proves the primitive: a repay with zero inbound transfer drains `custody_before` to the payer while the book is untouched. Impact: theft of supplier funds / protocol insolvency.

### Likelihood Explanation
Reachable only if a controller entrypoint forwards an unmeasured (declared) amount into `pool.repay`. The measured paths (`transfer_amount_measured` → `received`) are safe for honest tokens; residual risk concentrates on fee-on-transfer/extra-credit listed tokens where `received` is measured at the controller side of a *forward* hop but the pool books a different quantity, or where `received > entry.amount` silently inflates `leg_usd` while `overpayment` is refunded on the full `received`. Medium-to-low likelihood pending confirmation of the strategy repay legs; high severity if reachable.

### Recommendation
- In `ops::repay::apply`, bound the refund by measured custody: snapshot the pool token balance before/after each batched leg, or have the controller pass the *measured* inbound amount and assert `overpayment <= measured_in` at the pool.
- Alternatively, reorder so `transfer_out(payer, overpayment)` is funded strictly by `credit_cash`-excluded receipts of the same transaction, and add a `require_reserves` or per-market cash check after refund.
- Audit every `PoolAction` construction (`make_pool_action`, `repay_prefunded_position` call sites in `strategies/legs.rs`, `swap_debt.rs`, `repay_debt_with_collateral.rs`) to confirm `amount` is always the measured receipt, never the caller-declared request.

### Proof of Concept
Sketch (mirroring `flows.rs:3589`):

1. List an under-delivering debt token D (fee-on-transfer, e.g. 10%) in a hub; victim account owes `debt_ceil` D and is in the full-close liquidation band.
2. Liquidator calls `controller.liquidate(liquidator, account_id, [(hub_D, offer)], SeizeMode::Transfer)` with `offer ≥ debt_ceil` and authorizes `transfer(liquidator → pool, offer)`.
3. If the repay action carries `offer` (or `received` where the token's delivery semantics differ at the pool hop) while the pool's `resolve_repay` treats `offer - debt_ceil` as overpayment, `transfer_out(payer, overpayment)` pays the liquidator the excess out of custody — including, on a multi-hub token, cash booked to a sibling hub that never received it.
4. The pool `cash` book is only credited `net_repay`; the refunded leg is not book-debited, so `sum(cash across hubs) < token.balance(pool)` invariant breaks in suppliers' favor of the attacker — supplier funds are drained without debt retired against them.

Note: PoC is partially speculative — the decisive variable is whether `action.amount` on the liquidation/strategy paths is always exactly the measured receipt into the pool. The `apply.rs` snippet suggests it is (`received`), which would close the vector for honest tokens and leave only a discrepancy between the amount the controller measured and the amount the pool actually holds (shared-balance sibling markets), which warrants a dedicated multi-hub under-delivery test.
