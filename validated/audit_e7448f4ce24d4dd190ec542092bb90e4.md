### Title
Missing Git submodule protocol allowlist enables command execution via attacker-controlled `.gitmodules` - (File: main.go)

### Summary
`git-sync` runs `git submodule update --init [--recursive]` on every worktree checkout without ever configuring `protocol.allow` / `GIT_ALLOW_PROTOCOL` to restrict which transport helpers Git may invoke for submodule URLs. Because the `.gitmodules` file and its submodule URLs are part of the tracked, attacker-influenced repository content, a user who can push a commit to the synced ref controls the submodule URL/protocol that Git will use.

### Finding Description
`configureWorktree` unconditionally runs the submodule update step whenever `--submodules` is not `off`: [1](#0-0) 

This calls `git submodule update --init` (optionally `--recursive`, `--depth`) via `git.Run`, which shells out to the real `git` binary using the args built here. Git resolves submodule URLs strictly from the repo's own `.gitmodules` file — content that is fully controlled by whoever can push to the tracked branch/ref that git-sync is syncing.

I searched `main.go` for any protocol restriction (`protocol.allow`, `GIT_ALLOW_PROTOCOL`) that would sandbox which transport helpers Git can invoke for submodules (e.g., blocking `ext::`, `fd::`, or arbitrary helper protocols), and found none — the only matches for "protocol" in `main.go` are unrelated declarations/call sites, not actual config being set. The credential/SSH/cookie setup functions (`SetupGitSSH`, `SetupCookieFile`, `RefreshGitHubAppToken`) configure authentication but do not add any `protocol.*` git config to constrain submodule transport helpers: [2](#0-1) 

Modern Git (>= 2.38.1) disables the `ext::` transport helper and restricts `file://` for submodules by default (this was the fix for the well-known git submodule "ext" RCE, CVE-2022-39253), but that protection lives entirely in the vendored/host Git binary's compiled-in defaults, not in anything git-sync itself enforces. If git-sync is built against, or the container ships, an older/patched-differently Git, or if any `protocol.allow` override exists anywhere in the environment/global gitconfig that git-sync creates (`GIT_CONFIG_GLOBAL`) that doesn't explicitly deny `ext`/`file`, the attacker-controlled `.gitmodules` submodule URL is passed straight into Git's transport dispatch during `configureWorktree`.

### Impact Explanation
If a permissive/older Git is used or protocol defenses are otherwise bypassed, an attacker who can push a commit adding a submodule with an `ext::sh -c "..."`-style URL (or similar helper-based protocol) achieves arbitrary command execution in the git-sync sidecar container at sync time — a full compromise of the sync process, capable of writing/deleting files outside `--root`, exfiltrating credentials configured via `--credential`/`--askpass-url`, or corrupting the published symlink target. This satisfies the "code execution" and "credential disclosure" impact criteria in the validation rules.

### Likelihood Explanation
Requires `--submodules` to not be `off` (which is not the default off — the flag defaults to enabled per the README) and requires the ability to push a commit to the synced repo/ref (an "attacker-pushed commit" scenario explicitly in scope). It also depends on the underlying Git binary's own submodule protocol defenses being absent or misconfigured, since upstream Git 2.38.1+ already blocks the classic `ext::` vector by default. I was not able to verify, from the indexed files, whether git-sync pins a specific Git version in its container build or whether any `protocol.allow` config is set elsewhere (e.g., in `Dockerfile.in`, which was not part of these search results). This uncertainty limits confidence to "reachable but conditional" rather than "always exploitable."

### Recommendation
Explicitly set `protocol.allow=never` for `ext`, `fd`, and other risky helper protocols (or a strict global `protocol.allow` allowlist limited to `http`, `https`, `git`, `ssh`, `file` as needed) in the private gitconfig git-sync generates (the same `GIT_CONFIG_GLOBAL` file created before `SetupDefaultGitConfigs`), independent of the bundled Git version's compiled-in defaults, before ever invoking `git submodule update`.

### Proof of Concept
Conceptual PoC (cannot be executed in this read-only environment):
1. Attacker pushes a commit to the synced branch adding `.gitmodules` with:
   ```
   [submodule "evil"]
       path = evil
       url = ext::sh -c "touch$IFS/tmp/pwned"
   ```
2. git-sync's `SyncRepo` detects the new hash, creates a worktree, and calls `configureWorktree`, which runs `git submodule update --init` at [3](#0-2) .
3. If the runtime Git does not block the `ext` protocol (older Git or explicit override), the embedded command executes inside the git-sync container as the git-sync user.

func (git *repoSync) SetupGitSSH(setupKnownHosts bool, pathsToSSHSecrets []string, pathToSSHKnownHosts string) error {
	git.log.V(1).Info("setting up git SSH credentials")

	// If the user sets GIT_SSH_COMMAND we try to respect it.
	sshCmd := os.Getenv("GIT_SSH_COMMAND")
	if sshCmd == "" {
		sshCmd = "ssh"
	}

	// We can't pre-verify that key-files exist because we call this path
	// without knowing whether we actually need SSH or not, in which case the
	// files may not exist and that is OK.  But we can make SSH report more.
	switch {
	case git.log.V(9).Enabled():
		sshCmd += " -vvv"
	case git.log.V(7).Enabled():
		sshCmd += " -vv"
	case git.log.V(5).Enabled():
		sshCmd += " -v"
	}

	for _, p := range pathsToSSHSecrets {
		sshCmd += fmt.Sprintf(" -i %s", p)
	}

	if setupKnownHosts {
		sshCmd += fmt.Sprintf(" -o StrictHostKeyChecking=yes -o UserKnownHostsFile=%s", pathToSSHKnownHosts)
	} else {
		sshCmd += " -o StrictHostKeyChecking=no"
	}

	git.log.V(9).Info("setting $GIT_SSH_COMMAND", "value", sshCmd)
	if err := os.Setenv("GIT_SSH_COMMAND", sshCmd); err != nil {
		return fmt.Errorf("can't set $GIT_SSH_COMMAND: %w", err)
	}

	return nil
}
