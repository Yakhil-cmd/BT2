## Title
Merkle proof verification lacks leaf/internal-node domain separation, enabling second-preimage forgery of "included" values - (File: `merkle.js`)

### Summary
`merkle.js`'s `verifyMerkleProof` hashes the caller-supplied `element` exactly the same way internal nodes are hashed, with no leaf/branch domain separation. This is the classic Merkle second-preimage weakness (the same bug class reported and fixed in plasma-contracts PR #452). In ocore, this primitive is reachable by two unprivileged actors: (1) an address-definition author via the `'in merkle'` authentifier opcode, and (2) an AA/oscript author (or a trigger sender supplying the formula input) via the `is_valid_merkle_proof` function. Either can fabricate a "membership" proof for a value that was never an actual leaf of the referenced tree, as long as they know the concatenation of two sibling hashes anywhere inside the tree.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree purely with `hash(str) = sha256(str)`, applying the exact same hash function at the leaf level and at every internal level: [1](#0-0) 

`verifyMerkleProof` starts by computing `the_other_sibling = hash(element)` and then folds up the tree using the supplied `siblings`/`index`, comparing the final value to `proof.root`: [2](#0-1) 

The developers' own comment flags this exact gap and left it unaddressed: `// Node-as-Leaf issue might matter in some cases` [3](#0-2) .

Because `hash(A||B)` is used identically to derive both leaf-pair parents and higher branch nodes, an attacker who knows (or can derive) the pair of hashes `(H_left, H_right)` that combine to form some internal node `N` in the real tree can set `element = H_left + H_right`. Then `hash(element)` equals `N` exactly, and by supplying a proof whose `index`/`siblings` start one level *above* `N` (skipping the two levels below it), `verifyMerkleProof` will walk up from `N` to the same `root`. The check returns `true` even though `element` was never a genuine leaf — it is a forged "included value."

Two unprivileged, reachable call sites exist:

1. `'in merkle'` address-definition opcode. The value being "verified" (`args[2]`, i.e., `element`) is fixed at address-definition time by the address author, while the proof is supplied later as an authentifier at spend time and checked against a root that must equal a genuinely-posted oracle data feed: [4](#0-3) 
An attacker who authors such a definition can choose `element` to be the concatenation of two known internal hashes of the oracle's actual tree (feasible whenever the oracle's underlying data set/tree structure is knowable, e.g. published whitelists/price tables), then, at spend time, submit a forged, level-skipping proof so the `'in merkle'` check passes and `dataFeeds.dataFeedExists` succeeds against the legitimate root, satisfying a spending condition that was never actually met.

2. `is_valid_merkle_proof(element, proof)` oscript/AA formula function, where both `element` and `proof` can be trigger-controlled expressions: [5](#0-4) 
An AA that gates a payout on `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` against a trusted root (e.g. a whitelist/allocation root fixed in the AA's own state or definition) can be tricked by a malicious trigger sender who is not a genuine leaf: they submit a forged element/proof pair using the same second-preimage technique to make the check pass.

### Impact Explanation
Any protocol logic — address spending conditions or AA fund-release logic — that relies on `'in merkle'` or `is_valid_merkle_proof` to gate access/value based on "this value is a member of set X (rooted by hash R)" can be bypassed by a party who is not actually a member of X, provided they can derive an internal node's child-hash pair from the tree (which is often knowable when trees are built over public/derivable datasets such as whitelists, price feeds, or allocation lists). This directly enables unauthorized spending of funds guarded by such conditions and, for AAs, fund loss/drain to an attacker who was never an authorized member of the underlying merkle set.

### Likelihood Explanation
No privileged access is required. Both entry points (`'in merkle'` in an address definition, and `is_valid_merkle_proof` in an AA formula) are reachable by ordinary unit posters and AA trigger senders. The precondition is knowledge of two sibling hashes belonging to the target tree, which is realistic whenever the tree is constructed over a data set the attacker can observe or reconstruct (as is typical for oracle-published lists/whitelists used with `'in merkle'`, or AA-managed membership roots used with `is_valid_merkle_proof`). This mirrors exactly the scenario the referenced plasma-contracts report and fix (PR #452) addressed.

### Recommendation
Add domain separation between leaf and internal-node hashing, e.g. prefix leaf hashing with a distinct tag/byte (e.g. `hash(0x00 || leafData)`) and internal-node hashing with another (e.g. `hash(0x01 || left || right)`) in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`, so a forged concatenation of two child hashes can never collide with a legitimately-hashed leaf. Alternatively, encode and enforce the expected proof length/tree depth so that a supplied `element`/proof pair cannot silently "start" partway up the tree at an internal node.

### Proof of Concept
1. Build (or observe) a merkle tree over set `{L0, L1, L2, L3}` via `getMerkleRoot`, e.g. using ocore's own `merkle.js`, and note internal node `N01 = hash(hash(L0) + hash(L1))`.
2. Craft `element = hash(L0) + hash(L1)` (the raw string concatenation, not further hashed) and a proof with `index` pointing to `N01`'s position at that tree level and `siblings = [N23]` (the sibling needed to reach `root`), skipping the leaf level entirely.
3. Call `merkle.verifyMerkleProof(element, proof)` (as done at `formula/evaluation.js:1799` for `is_valid_merkle_proof`, or via `merkle.deserializeMerkleProof` + `verifyMerkleProof` at `definition.js:1014-1016` for `'in merkle'`) — it returns `true`, even though `element` (`hash(L0)+hash(L1)`) was never an actual leaf of `{L0, L1, L2, L3}`.
4. In a real deployment, use this forged pair as the `element` argument of an `'in merkle'` address-definition clause or as the `trigger.data.element`/`trigger.data.proof` inputs to an AA using `is_valid_merkle_proof`, to satisfy a spending/access condition that requires genuine membership, thereby releasing funds without legitimate authorization.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
