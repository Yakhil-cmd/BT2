Based on the analysis, the ocore engine's `spender_attested` asset mechanism contains an analogous freeze pattern: an asset issuer (a role reachable by any unprivileged asset creator or an AA acting as `definer`) can unilaterally revoke an address's attestation *after* that address has already legitimately received and is holding coins of the asset, permanently blocking that holder from ever moving/spending the funds they already hold — mirroring the "burn now, blocked later by an administrator" fund-freezing pattern in the report.

### Title
Asset definer can permanently freeze already-held `spender_attested` asset balances by revoking attestation after receipt - (File: validation.js, storage.js)

### Summary
For assets defined with `spender_attested: true`, the right to *spend* an already-owned, previously-received output is re-checked against the *current* (latest) attestor list at spend time rather than the list that was valid when the holder received the funds. The attestor list is a mutable state that only the asset's `definer_address` controls via the `asset_attestors` message, with no restriction preventing removal of addresses that already hold unspent balances. This lets the definer strand any holder's legitimately-acquired funds indefinitely, exactly like an administrator "pausing redeem" after the user has already committed to the transaction.

### Finding Description
When validating a payment that spends a `transfer`-type input of a `spender_attested` asset, `validatePaymentInputsAndOutputs` requires the current owner address to be in `objAsset.arrAttestedAddresses`: [1](#0-0) 

This attested-addresses list is computed dynamically by `storage.readAsset` / `loadAssetWithListOfAttestedAuthors`, which always looks up the *latest* `asset_attestors` unit as of `last_ball_mci` — not the list that was current when the holder originally acquired the output: [2](#0-1) [3](#0-2) 

The attestor list can be freely rewritten at any time solely by the asset's definer, with the only checks being that the caller is the definer and the new list is well-formed (sorted, valid addresses, size limit) — there is no restriction against removing addresses that currently hold unspent balances of the asset: [4](#0-3) [5](#0-4) 

The same "unknown fields"/authorization surface is validated identically for `asset_attestors` messages posted from an AA (autonomous agent), meaning an AA acting as an asset's definer can dynamically toggle attestation for addresses that already received AA-issued tokens: [6](#0-5) [7](#0-6) 

Consequently, the sequence:
1. Definer (unprivileged asset issuer or AA) issues `spender_attested` asset with attestor list `[A]`.
2. Address `A` legitimately receives an output of this asset (payment validated successfully because `A` was attested at that time).
3. Definer later posts a new `asset_attestors` unit removing `A` from the list (e.g., analogous to "pausing redemption").
4. Address `A` can never again spend/transfer/redeem that already-held output, because `validatePaymentInputsAndOutputs` re-checks attestation against the *current* list at every subsequent spend attempt, not the list at receipt time.

### Impact Explanation
This freezes funds a user already legitimately owns, with no way to recover them unless the definer voluntarily re-adds the address to the attestor list — mirroring the reported bug class where an administrator can permanently strand user assets after the user has already committed value to the system. If the same asset is used by an AA to represent redeemable claims (e.g., collateral receipts issued by a lending/DEX-style AA), the AA's controller could strand user claims indefinitely — a concrete case of AA fund freezing.

### Likelihood Explanation
Likelihood is moderate: it requires an asset explicitly designed with `spender_attested: true` (an opt-in feature), and a definer/AA willing to remove previously-attested holders. However, since attestor-list updates are unrestricted with respect to existing balances, this can happen either maliciously or accidentally (e.g., an attestor rotation that forgets to preserve existing holders), and it is entirely within the normal, unprivileged capabilities of any asset definer — no special network-level access is required.

### Recommendation
When validating a `transfer` input of a `spender_attested` asset, check attestation against the attestor list that was current when the source output was created (i.e., as of the `src_unit`'s last-ball MCI) rather than the current/latest list, so that a subsequent attestor-list change cannot retroactively invalidate already-owned, previously-valid outputs. Alternatively, document and enforce that attestor-list updates cannot remove addresses holding unspent balances, or provide a grace/exit mechanism allowing holders to move funds to an unrestricted state before an attestation revocation takes effect.

### Proof of Concept
1. Definer `D` issues asset `X` with `spender_attested: true`, `attestors: [A]` (validated per `validateAssetDefinition`/`checkAttestorList`) — see [8](#0-7) .
2. `D` sends a payment of asset `X` to address `A`. Validation succeeds because `A` is attested (`validatePayment` checks `arrAttestedAddresses.indexOf(issuer_address)` for issue, and output attestation for the destination): [9](#0-8) .
3. `D` posts an `asset_attestors` unit for asset `X` with a new list that excludes `A` (only requires `D` to be definer): [4](#0-3) .
4. `A` attempts to spend the previously received output of `X`. `validatePaymentInputsAndOutputs` looks up the current attestor list (now excluding `A`) via `storage.loadAssetWithListOfAttestedAuthors`, and rejects the spend with "owner address is not attested": [1](#0-0) .
5. `A`'s funds remain permanently stuck in that output as long as `D` chooses not to re-attest `A`, with no protocol-level remedy.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
