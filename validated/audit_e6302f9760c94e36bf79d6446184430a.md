### Title
Webhook Signature Binds to `repository.owner.login`, but Stack Lookup Binds to `repository.full_name` — Cross-Organization Forced Sync - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The reported bug pattern is a value-binding mismatch: `BountyV1.approveSubmission()` verified/refunded one value (the stake) while actually paying out a different, smaller value (stake minus fee) — the amount *acted on* was not the amount *covered by* the accounting the function claimed to guarantee. The same class of mismatch exists in Shipit's webhook trust chain: the organization used to *select and verify* the HMAC signature is not the same field used to *select the Stack/repository that gets acted upon*.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) using `repository_owner`, which reads `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

Once the signature check passes (i.e. the request was signed with *some* configured org's `webhook_secret`), the same raw JSON body is dispatched to the event handlers: [3](#0-2) 

Every handler resolves the target `Stack`/`Repository` not from `repository.owner.login` (the field that was actually authenticated), but from a completely independent field, `repository.full_name`: [4](#0-3) 

`PushHandler`, for example, uses this `stacks` helper to select the Stack it acts on and then queues a GitHub sync with an attacker-controlled `after` SHA: [5](#0-4) 

Nothing in `Handler`, `PushHandler`, `CheckSuiteHandler`, or the controller cross-checks that `repository.owner.login` (the value the signature was verified against) is a prefix of `repository.full_name` (the value used to pick the Stack that gets mutated). This is precisely the analog of the reported bug: the equality that should hold —
`organization authenticated (repository.owner.login used for HMAC/app selection) == organization whose repository is written (owner segment of repository.full_name used for Stack lookup)` — is never enforced.

### Impact Explanation
In a multi-org Shipit deployment (explicitly documented and supported, `docs/setup.md` "Using Multiple Github Applications"), each organization has its own independently configured `webhook_secret`. An org administrator who legitimately registered their own GitHub App with Shipit (and therefore knows their own org's `webhook_secret`, which they themselves generated when creating the App) can craft a raw HTTP POST directly to `/webhooks` with:
- `repository.owner.login` = their own org (so `Shipit.github(organization: ...)` selects their own valid `webhook_secret` and the HMAC check passes), and
- `repository.full_name` = `"victim-org/victim-repo"` (an entirely unrelated organization's repository that has a Stack configured in the same Shipit instance).

Because the signature only proves "this request was signed by *an* org configured in Shipit," not "this request concerns *that same* org's repository," `PushHandler` will call `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on the victim's Stack — a cross-repository/cross-organization action the attacker has no authorization to trigger. `CheckSuiteHandler` has the identical flaw. This satisfies the Critical impact bar: cross-repository writes / unauthorized action against a stack belonging to another tenant, triggered without any legitimate relationship to that repository.

### Likelihood Explanation
Requires only knowledge of one's own legitimately-issued `webhook_secret` for an org already onboarded to the shared Shipit instance — not the victim's secret, not repository write access to the victim repo, and not a Shipit session/API token. In any Shipit deployment shared across multiple GitHub organizations (a configuration the engine explicitly documents as supported), any onboarded org's administrator can reach every other tenant's stacks this way, making this a realistic and directly reachable multi-tenancy boundary break.

### Recommendation
In `Handler#repository_name` (and everywhere a handler resolves a `Stack`/`Repository` from the payload), require that the owner segment of `repository.full_name` equals `repository.owner.login`/`organization.login`, and additionally require that this value equals the organization whose `webhook_secret` was used to verify the signature in `WebhooksController#verify_signature`. Pass the verified organization down to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` and have `Handler` reject/ignore any payload whose `repository.full_name` owner does not match the verified organization.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md`), and a Stack for `org-b/victim-repo`.
2. As an administrator of `org-a` (who legitimately knows `org-a`'s `webhook_secret`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a-webhook-secret, body)>` and send it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and the signature validates successfully because it was genuinely signed with `org-a`'s secret.
5. `PushHandler#stacks` resolves the Stack via `Repository.from_github_repo_name("org-b/victim-repo")`, and `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` is invoked on `org-b`'s stack — a stack the attacker has no legitimate relationship with — confirming the cross-organization write.
