### Title
Unauthenticated cross-organization disclosure of stack merge/lock state via `MergeStatusController#check` - ([File: app/controllers/shipit/merge_status_controller.rb])

### Summary
`Shipit::MergeStatusController#check` is exempted from `force_github_authentication` via `skip_authentication only: %i[check show]`, and its private `stack` resolver builds a DB scope filtered only by attacker-supplied `referrer` URL (`owner`/`name` regex-parsed) with no ownership or session check. Unlike `show`, `check` never calls `current_user.logged_in?` before rendering `stack_status`, so any unauthenticated caller can read another organization's production stack `merge_status` (lock/queue state) by simply naming that org/repo in the `referrer` param.

### Finding Description
The broken binding: the code implicitly assumes `referrer_parser.repo_owner/repo_name (attacker-controlled string) == an organization the requester is authorized to view`. In reality nothing enforces that equality.

Path: `check` is listed in `skip_authentication only: %i[check show]` [1](#0-0) , which uses `skip_before_action(:force_github_authentication, ...)` [2](#0-1) , completely bypassing `force_github_authentication`'s login/authorization checks [3](#0-2) .

Inside `check`, `stack_status` calls `stack.merge_status(...)` [4](#0-3) , and `stack` (with no `params[:stack_id]`) resolves via a scope filtered only by `referrer_parser.repo_owner` / `repo_name`, ordered by lock/queue state, `.first` [5](#0-4) . `referrer_parser` merely regex-parses the client-supplied `referrer` param with no validation against any session, team membership, or repository permission [6](#0-5) [7](#0-6) .

Critically, `check` renders `stack_status` (via HTML plain text or JSON) unconditionally, with **no** `current_user.logged_in?` gate [8](#0-7)  — contrast with `show`, which does check `current_user.logged_in?` and renders `'logged_out'` otherwise [9](#0-8) . This asymmetry is the root cause: `show` at least gates the actual payload behind a login check even though skip_authentication applies to both, but `check` has no equivalent gate at all.

Attacker request: `GET /merge_status/check.json?referrer=https://github.com/<victim-org>/<victim-repo>/pull/1` with no session cookie, no API token. If a `Repository`/`Stack` row exists for `<victim-org>/<victim-repo>` with `environment: 'production'` (or matching `branch` param), the JSON response body discloses `stack_status` (e.g., `"pending"`, `"success"`, `"faulty"`, or blocked/locked states) reflecting real lock/queue state of that stack, with the HTML variant returning `503` plus the status string for non-success states.

None of the listed guards apply: `verify_signature`/webhook signature checks are irrelevant (this isn't a webhook route); `force_github_authentication` is explicitly skipped for this action; there's no `require_permission!` or `stacks` scope check on `stack`; model validations on `Repository`/`Stack` don't constrain *who* can query them, only what values are stored.

### Impact Explanation
An unauthenticated attacker can enumerate/probe organizations' production stack states (merge-queue depth proxy via ordering, lock state, pass/fail status) for any org that has a Shipit `Stack` configured, without any credential. This matches the in-scope "High - unauthenticated read of stack state" category. It is repeatable against arbitrary orgs/repos known to use the shared Shipit instance, and the leaked lock/queue signal could be used to time a competing merge into the queue (escalating toward the "hostile merge timing" scenario described). Blast radius spans all tenants (orgs/repos) hosted on the same Shipit instance, since the query is a simple parameter-driven DB lookup with no scoping to the requester's identity.

### Likelihood Explanation
Preconditions are minimal and realistic in a multi-tenant Shipit deployment: any `Stack`/`Repository` record must exist (which is the normal operating state for every onboarded repo), and the target stack must have `environment: 'production'` or the attacker must know/guess a `branch` name (production is the common default). No secrets, no GitHub permissions, no Shipit account are required — only knowledge of the target org/repo name, which is public information on GitHub. Attacker cost is a single unauthenticated HTTP GET, fully repeatable and scriptable for enumeration across many orgs.

### Recommendation
Require the caller to be authenticated and authorized for the resolved stack's repository before returning `stack_status` in `check`, mirroring (at minimum) the `current_user.logged_in?` gate already present in `show`, or better, verify `current_user.authorized?` / repository-level permission (`require_permission!` or equivalent) against the resolved `stack.repository` before rendering. Alternatively, restrict the `referrer`-based stack lookup to require a valid session tied to that repository's GitHub team/permission set rather than trusting an arbitrary client-supplied URL.

### Proof of Concept
```ruby
# test/controllers/shipit/merge_status_controller_test.rb
test "check discloses merge_status for a stack the requester has no session/permission for" do
  # Arrange: a victim org's production stack exists in fixtures, no session set (unauthenticated)
  victim_repo = shipit_repositories(:shipit) # owner/name from fixtures, e.g. "shipit-engine/shipit-engine"
  victim_stack = shipit_stacks(:shipit)      # environment: 'production'
  assert_nil session[:user_id]

  # Act: unauthenticated GET with referrer naming the victim org/repo, no auth headers/cookies
  get :check, params: {
    referrer: "https://github.com/#{victim_repo.owner}/#{victim_repo.name}/pull/1"
  }, format: :json

  # Assert: response reveals real stack_status rather than blank/403
  body = JSON.parse(response.body)
  assert_not_nil body['stack_status']
  assert_equal victim_stack.merge_status(backlog_leniency_factor: 1.0), body['stack_status']
  refute_equal response.status, 403
end
```
This demonstrates the binding `referrer owner/name (attacker-controlled) == authorized org` does not hold: the attacker supplies an arbitrary `referrer` and receives the real `merge_status` of a stack belonging to an organization for which no session, token, or team membership was presented.

    class ReferrerParser
      URL_PATTERN = %r{\Ahttps://github\.com/([^/]+)/([^/]+)/pull/(\d+)}

      attr_reader :repo_owner, :repo_name, :pull_request_number

      def initialize(referrer)
        unless (match_info = URL_PATTERN.match(referrer.to_s))
          raise ArgumentError, "Invalid referrer: #{referrer.inspect}"
        end

        @repo_owner = match_info[1].downcase
        @repo_name = match_info[2].downcase
        @pull_request_number = match_info[3].to_i
      end
    end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
