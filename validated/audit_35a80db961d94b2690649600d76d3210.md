**Rationale:** The reported GHSA-9wx7-jrvc-28mm advisory concerns the `starkbank-ecdsa` libraries' custom (non-standard) ECDSA verification implementation, which contained a modular-arithmetic bug allowing signature forgery for arbitrary messages against any public key. A search of this repository shows no dependency on `starkbank-ecdsa` in any ecosystem (PyPI/NuGet/npm/Maven) — no matches for `starkbank` anywhere in the codebase.

The codebase's ECDSA implementations in `sp-core` are built on the well-established, independently audited `k256` (RustCrypto) crate and `libsecp256k1`, not a custom-written verification algorithm.

The only closely related recent change I found is `pr_5841.prdoc` [1](#0-0)  which unifies `sp-core`'s ECDSA to `k256` and adds low-S signature normalization (BIP-62/EIP-2) checks across `MultiSignature::verify` [2](#0-1) , the `Verify` impl for `sp_core::ecdsa::Signature` [3](#0-2) , BEEFY's `ecdsa_crypto::BeefyAuthorityId::verify` [4](#0-3) , and `sp-application-crypto`'s `RuntimePublic::verify` [5](#0-4) . This addresses signature *malleability* (two valid signatures for the same message), which is a distinct and already-mitigated bug class — not the "forge a signature for any message against any public key without knowing the private key" defect that the starkbank advisory describes.

Since the affected library is not used, and the codebase relies on audited, standard elliptic-curve crypto crates rather than a custom-written verification routine susceptible to the same class of implementation flaw, there is no demonstrable analog in this repository. Per the reporting rules, dependency-only/non-existent-dependency findings and unsupported speculation are not reportable.
