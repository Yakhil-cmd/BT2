### Title
AA can be permanently DoS'd (funds frozen) via unbounded dust-output accumulation when composing an asset payout - ([File: aa_composer.js])

### Summary
The Sherlock finding describes a DoS where an attacker fills a payment queue with a huge number of tiny/blank entries that must all be iterated (and thus paid gas for) whenever the queue is processed, eventually exceeding the block gas limit and permanently blocking processing. The analogous mechanism in ocore is in `aa_composer.js`'s AA response-payment composer: when an AA needs to pay out a non-base asset, it selects *every* unspent output of that asset sent to it, with no per-call limit and no minimum-amount ("dust") filter, and the resulting payment message is explicitly exempted from the normal `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap in `validation.js` because it is an AA-authored message.

### Finding Description
When an AA composes a response that needs to pay `target_amount` of some asset, `completePaymentPayload()` calls `readStableOutputs()` and then `readUnstableOutputsSentByAAs()` to fetch unspent outputs of that asset belonging to the AA, and feeds them into `iterateUnspentOutputs()`, which keeps consuming rows (adding each as an input) until the accumulated `total_amount` reaches `target_amount`: [1](#0-0) 

Crucially, the SQL for stable/unstable outputs applies a dust-avoidance filter **only for the base asset** (`amount>=FULL_TRANSFER_INPUT_SIZE`); for any named asset there is no minimum-amount filter and no `LIMIT` clause at all: [2](#0-1) [3](#0-2) 

The comment in the code even acknowledges the dust-DoS class ("byte outputs less than 60 bytes ... are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond") but the mitigation was applied only to bytes, not to assets.

Normally, `validatePaymentInputsAndOutputs()` in `validation.js` caps a payment message to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) inputs — but this check is explicitly skipped for AA-generated messages: [4](#0-3) 

So an attacker can post many trigger units (or ordinary payments) that send a huge number of tiny amounts of a given asset to a target AA's address. Any time that AA subsequently needs to pay out that asset (e.g., as a response payment or change), `completePaymentPayload()` will attempt to accumulate enough of these dust outputs to reach the target amount, pulling in an unbounded number of inputs (since there's no `LIMIT` and no per-call cap for AA payments). This grows `payload.inputs` without bound, inflating the composed unit's size until it exceeds practical/protocol limits (`MAX_UNIT_LENGTH`, message size, oversize-fee blowup via `getOversizeFee`), causing the response-unit composition/validation to fail (`bounce`) every time the AA tries to pay in that asset.

### Impact Explanation
Because this queue-draining loop is a hard prerequisite for any payout of the affected asset by the AA, an attacker can permanently prevent the AA from ever successfully sending that asset to any user — every attempt keeps re-selecting the same (or growing) dust set and fails to fit into a valid unit, causing repeated bounces. This is a fund-freezing/DoS condition on the AA analogous to the Crab Netting queue-poisoning bug: unbounded attacker-controlled "blank/dust" entries that must be fully consumed before a legitimate operation (deposit/withdraw netting there, asset payout here) can complete. Depending on economics of the affected asset, this can freeze user or protocol funds held by the AA in that asset indefinitely.

### Likelihood Explanation
The attack is cheap and reachable by any unprivileged user: it only requires posting standard payment units sending very small amounts of an asset (down to 1 unit) to the target AA's address; there is no privileged role required. The only cost is base-byte transaction fees for creating the dust outputs, which is a normal, low, and repeatable cost for an attacker motivated to disable an AA that holds or manages a valuable non-base asset.

### Recommendation
Apply the same dust-avoidance/minimum-amount filtering used for base-asset outputs to non-base assets in `readStableOutputs`/`readUnstableOutputsSentByAAs` (e.g., ignore outputs below some fraction of the per-input storage/size cost), and/or impose an explicit cap on the number of asset inputs an AA-generated payment message may accumulate per composition (independent of the `MAX_INPUTS_PER_PAYMENT_MESSAGE` exemption), falling back to bouncing with a clear error rather than silently trying to include unlimited dust inputs. Alternatively, allow AA logic/state to skip over known-dust outputs (similar to the accepted Sherlock fix that let the owner fast-forward past bad queue entries).

### Proof of Concept
1. Attacker identifies an AA address that is expected to eventually pay out asset `X` (e.g., a token used for AA responses/change).
2. Attacker posts, e.g., 50,000 ordinary payment units, each sending a 1-unit output of asset `X` to the AA's address (well below any oversize/input-size threshold, since no dust filter applies to non-base assets in `aa_composer.js` lines 1140-1173).
3. A legitimate user triggers the AA to pay out `target_amount` of asset `X`.
4. `completePaymentPayload()`'s `iterateUnspentOutputs()` loop (`aa_composer.js` lines 1102-1138) starts consuming the attacker's dust outputs one by one since none are filtered out and there's no `LIMIT`/cap (the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check is bypassed for AAs per `validation.js` lines 2137-2138).
5. The resulting payment message grows to tens of thousands of inputs, causing the composed AA response unit to exceed size limits / trigger fatal errors during composition, so the AA bounces the trigger instead of successfully paying out asset `X`.
6. Every subsequent attempt to pay out asset `X` from the AA hits the same dust set (plus any newly received legitimate outputs), permanently preventing successful payout — freezing the AA's asset-`X` funds.
