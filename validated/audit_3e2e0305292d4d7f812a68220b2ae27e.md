### Title
Webhook signature verifies the sending GitHub organization, but event handlers route writes by an unverified `repository.full_name` / commit `sha` field, allowing cross-organization commit-status forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to HMAC-verify a webhook payload against using `repository_owner`, a field read directly from the untrusted JSON body. Once verification passes, the actual event handlers (e.g. `StatusHandler`, `PushHandler`, `CheckSuiteHandler`) resolve the affected `Repository`/`Stack`/`Commit` using a *different*, equally attacker-controlled field (`repository.full_name`, or in `StatusHandler`'s case, a bare commit `sha` with no repository scoping at all). Any party who legitimately owns a GitHub organization/App installation registered on the shared Shipit instance can therefore sign an arbitrary payload with their own organization's secret while pointing the payload's repository/commit fields at a completely different organization's stack.

### Finding Description
The binding that should hold is: **organization that authenticated == repository that is written**. This is broken as follows.

1. `WebhooksController#verify_signature` picks the GitHub App/secret to check the HMAC against using a value taken straight from the body: [1](#0-0) [2](#0-1) 

2. `verify_webhook_signature` HMACs the *entire* raw body against whichever organization's `webhook_secret` was selected in step 1: [3](#0-2) 

   This only proves "the sender knows organization A's `webhook_secret`" — it says nothing about which repository/stack the payload's content should be allowed to affect. Any admin who has legitimately installed the Shipit GitHub App for their own organization (organization A) knows or can obtain that organization's `webhook_secret`, and can therefore sign **any** JSON body of their choosing.

3. Handlers that process the verified payload determine which `Repository`/`Stack` to mutate using `payload.dig('repository', 'full_name')` — a field with no relationship to the organization whose secret validated the signature: [4](#0-3) 

4. `StatusHandler` is even weaker: it doesn't consult the repository at all, and matches commits **globally by SHA**: [5](#0-4) 

So an attacker who controls only organization A's webhook secret can forge a `status` event whose `sha` is a commit belonging to organization B's stack, with `state: success` and an arbitrary `context`, and Shipit will apply it to `Commit#create_status_from_github!` for that commit regardless of which organization actually owns it.

### Impact Explanation
Commit statuses drive Shipit's deployability/merge-gating logic (`ci.require`, `Stack#trigger_deploy`/`build_deploy`, which rely on `until_commit.deployable?`): [6](#0-5) 

By forging a passing status for a required CI context on an arbitrary commit in a stack the attacker does not own, the attacker can make that commit appear deployable/mergeable, enabling an **unauthorized deploy or merge** through Shipit's continuous-deployment/merge-queue pipeline — this crosses the Critical-impact bar (unauthorized deploy/merge across repositories) without ever holding an `ApiClient` token, a Shipit session, or write access to the victim repository.

### Likelihood Explanation
Requires only that the attacker legitimately control a GitHub organization/App installation already registered on the (multi-tenant) Shipit instance — a low bar compared to compromising `GITHUB_TOKEN`, `api_clients_secret`, or a privileged Shipit account. The attacker needs the target commit's SHA, which is typically public (GitHub commit URLs, PR pages, Shipit's own UI).

### Recommendation
Bind the field used to select the verifying webhook secret to the same field used by every handler to resolve the affected repository, and reject payloads where they diverge. Concretely, `WebhooksController` should re-derive `repository_owner` from `repository.full_name` (the same field `Handler#repository_name` uses) instead of `repository.owner.login`/`organization.login`, and `StatusHandler` should scope its `Commit` lookup by the repository resolved from the verified payload rather than matching by SHA alone.

### Proof of Concept
1. Attacker legitimately registers/owns organization `attacker-org` on the shared Shipit instance and knows its `webhook_secret` (obtained via normal GitHub App installation).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim-org/victim-repo commit sha>",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker computes `sha256=HMAC(attacker_org_webhook_secret, body)` and POSTs to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GithubApp`, and the HMAC validates successfully (attacker signed it with their own secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit globally — and calls `create_status_from_github!`, injecting a forged passing CI status onto a commit in a stack the attacker never had access to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
