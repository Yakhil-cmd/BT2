### Title
Cross-repository CI status forgery via global commit-sha lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub `status` webhook against the GitHub App/organization named inside the payload itself (`repository.owner.login`), but `StatusHandler#process` then applies the payload's `sha`/`state`/`context` to **any** `Commit` row in the entire Shipit database matching that SHA, with no check that the commit belongs to a stack whose repository/organization is the one that was actually authenticated.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against using `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')`), not out of any authenticated context: [1](#0-0) [2](#0-1) 

Because the org used for verification is chosen by the payload itself, anyone who owns/administers *any* GitHub organization onboarded to this Shipit instance (and thus knows that org's own `webhook_secret`) can self-sign an arbitrary payload — the signature only proves "the sender knows org X's secret and put org X's name in `repository.owner.login`", it says nothing about which commit the rest of the payload references.

`StatusHandler#process` then ignores repository scoping entirely and matches on the global `sha` field alone: [3](#0-2) 

Contrast this with `Handler#stacks`, which does scope by `repository.full_name` when other handlers use it: [4](#0-3) . `StatusHandler` deliberately bypasses that scoping and instead queries `Commit.where(sha: params.sha)` across all stacks/repositories.

`Commit#create_status_from_github!` then records the forged status and, on a state transition to `success`/`pending`, schedules merge processing: [5](#0-4)  This directly feeds `MergeRequest#reject_unless_mergeable!` / `any_status_checks_missing?` / `any_status_checks_failed?`, which gate automatic merges in the merge queue: [6](#0-5) , and `Commit#deployable?`, which gates continuous deployment: [7](#0-6) 

**The broken equality:** `authenticated_organization(payload.repository.owner.login)` ≠ `repository_that_owns(Commit matched by payload.sha)`. The webhook signature only proves the first; the handler acts on the second, with no code path tying them together.

### Impact Explanation
An attacker who administers one org configured in this Shipit instance's `Shipit.github` config (a routine, low-privilege scenario in a multi-tenant deployment, as shown by the `OrgOne`/`OrgTwo` test fixtures) can forge a required CI status (`success`) or clear a blocking status for a commit belonging to a completely different organization/stack that they have no access to. Since a forged `success` status can satisfy `MergeRequest#reject_unless_mergeable!`'s CI checks and `Commit#deployable?`, this can unblock an automatic merge (via `ProcessMergeRequestsJob`/merge queue) or an automatic continuous deployment for a stack/repository the attacker does not control — an unauthorized merge/deploy, which meets the Critical impact bar.

### Likelihood Explanation
The only precondition is knowing a target commit's SHA (visible on the public GitHub repo, PR page, or a public/semi-public Shipit stack page) and controlling any one GitHub org/app already configured on the shared Shipit instance — no access to the victim repository, no `ApiClient` token, and no session are required. This is realistic for any shared/multi-tenant Shipit deployment.

### Recommendation
Scope `StatusHandler#process` (and any other global `Commit`/`Status`/`CheckRun` lookups driven by webhook payload fields) to commits whose `stack.repository` matches `payload.dig('repository','full_name')`/the authenticated organization, mirroring the scoping already used via `Handler#stacks`. Additionally, derive the organization used for signature verification from a value that cannot be forged independently of the actual target repository (e.g. require and cross-check `repository.full_name` against a repository record whose organization matches the one used to verify the signature) rather than trusting `repository.owner.login` from the unauthenticated body.

### Proof of Concept
1. Shipit is configured with two organizations, `victim-org` and `attacker-org`, each with its own GitHub App/`webhook_secret` (as in `secrets_double_github_app.yml`).
2. Attacker administers `attacker-org` and knows its `webhook_secret`.
3. Attacker finds a commit SHA `deadbeef...` for a pending/blocked commit belonging to a stack under `victim-org` (visible via the public GitHub repo or Shipit UI).
4. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body `{"sha":"deadbeef...","state":"success","context":"required-ci","repository":{"owner":{"login":"attacker-org"}}}`, and `X-Hub-Signature` computed with `attacker-org`'s own `webhook_secret`.
5. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (since attacker knows that secret) — `head(422)` is never triggered. [1](#0-0) 
6. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, finds the victim's commit (in a stack under `victim-org`), and records a fabricated `success` status on it, potentially unblocking a merge or deploy for `victim-org`'s stack. [3](#0-2)

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(

        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
