The reported bug class is specific to the EVM/Solidity proxy-upgrade pattern: a `constructor` runs only once at deployment time in the *deployer's* context, so state it sets is never visible when later called through a proxy's `delegatecall`, which is why OpenZeppelin-style upgradeable contracts require an `initializer` function instead of a constructor.

I looked for a genuine FRAME/pallet-revive analog rather than forcing this EVM concept onto Substrate:

- Runtime upgrades in FRAME use explicit migration logic executed after `set_code`/`authorize_upgrade`, not constructor/proxy delegatecall semantics, so the underlying "constructor state lost in proxy context" invariant doesn't apply to pallet upgrades at all [1](#0-0) .
- `pallet-revive` does support Solidity contracts and even Solidity-style `delegatecall`, and its own test suite explicitly exercises the delegatecall/proxy pattern (`OriginIsRoot.sol`'s `delegateOriginIsRoot`), confirming that delegatecall context propagation (e.g., `originIsRoot`) is correctly implemented for proxy-style contracts [2](#0-1) [3](#0-2) .
- The constructor/initcode execution path in `pallet-revive` runs the constructor in the frame of the newly instantiated contract itself (via `push_frame`/`instantiate`), matching correct EVM constructor semantics, not the deployer's separate storage context [4](#0-3) .
- `set_code_hash`, which would be the closest analog to an "upgrade" operation for a deployed contract, is explicitly disabled for Solidity contracts precisely because Solidity's immutable/constructor model doesn't compose safely with upgrades, and re-enabling it is called out as requiring re-running the constructor in a dedicated follow-up design, not a silent bug [5](#0-4) .

If a user deploys their *own* Solidity contract on `pallet-revive` using a traditional constructor behind their own proxy, they would reproduce the same Solidity-level footgun described in the report — but that is a property of arbitrary user-supplied Solidity bytecode misusing the language's constructor semantics, not a defect in the Polkadot SDK's runtime, pallet-revive, or its dependencies. There is no FRAME pallet, XCM, bridge, or pallet-revive-internal code path where an "upgradeable contract constructor" pattern is used in production code and could plausibly lose state in the way described.
