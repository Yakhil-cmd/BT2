### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` but downstream handlers act on the unrelated `repository.full_name` field, allowing cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to validate an inbound webhook's HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). All event handlers, however, resolve the `Repository`/`Stack` to act on using a completely different, independently-controlled field of the same JSON body: `payload.dig('repository', 'full_name')`. Because HMAC verification only proves "this payload was signed with the secret belonging to organization X" and does not bind X to the `full_name` field used for the actual write, an attacker who legitimately controls a GitHub App/webhook secret for their own org can forge a payload claiming to be for a victim's repository.

### Finding Description
The signature check: [1](#0-0) [2](#0-1) 

selects the `GitHubApp` (and thus the `webhook_secret`) purely from `repository.owner.login` / `organization.login` in the JSON body, then verifies the raw payload's HMAC against that app's secret: [3](#0-2) 

Once `verified` is true, the controller dispatches the entire, attacker-controlled `params` blob to every registered handler for the event, unmodified: [4](#0-3) 

All the base handlers, though, resolve which `Repository`/`Stack` to mutate from `repository.full_name`, a sibling field independent from `repository.owner.login`: [5](#0-4) 

For example `PushHandler` triggers a GitHub sync (fetches and applies new commits) for whatever stacks match that `full_name`/branch: [6](#0-5) 

and the pull-request handlers archive/unarchive review stacks or create commit-status records keyed off `params.repository.full_name` as well: [7](#0-6) 

Nothing anywhere validates that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` — the field used to pick the signing secret. In a Shipit deployment configured with more than one GitHub App/organization (explicitly supported — see `Shipit.github(organization:)` indifferent-access lookup and the `secrets_double_github_app.yml` test fixture), an attacker who legitimately controls one configured organization's GitHub App (e.g., they installed their own GitHub App entry, or otherwise know/derive that org's `webhook_secret`) can send a POST to `/webhooks` with:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
signed with `attacker-org`'s own secret (`X-Hub-Signature: sha1=...`). `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the HMAC — because the attacker legitimately knows that secret. The request passes, and `PushHandler#process` (or the pull-request handlers, or `status`/`check_suite` handlers) then acts on `victim-org/victim-repo`, a stack the attacker has no access to.

Binding broken as an equality: the engine implicitly assumes
```
organization authenticated by signature (repository.owner.login) == organization of the repository actually written (repository.full_name owner)
```
but the code never enforces this equality — it verifies one field and writes based on an entirely separate field of the same unsigned-boundary JSON body.

### Impact Explanation
This crosses the "organization authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely this allows:
- Forged `push` events causing `GithubSyncJob`/`sync_github` to run against an arbitrary victim stack, using attacker-supplied `after` SHA, which can desynchronize commit history state or trigger continuous-delivery deploys of an attacker-chosen commit if that SHA happens to exist in the victim repo (`stack.trigger_continuous_delivery` reacting to newly-synced commits) — an unauthorized deploy pathway.
- Forged `pull_request` events (`opened`, `closed`, `reopened`, `labeled`/`unlabeled`) causing review stacks on the victim repository to be created, archived, or unarchived.
- Forged `status`/`check_suite` events writing fake CI status/check-run data onto the victim's commits, which can be leveraged to satisfy `ci.require` checks and unlock deploys of unreviewed code (cross-repository writes / unauthorized ship path).

This satisfies the required Critical/High impact bar (cross-repository writes / unauthorized deploy) once the multi-org configuration is in use, which the codebase explicitly supports and tests for.

### Likelihood Explanation
Requires the operator to run Shipit with more than one configured GitHub App/organization (documented and tested capability via `Shipit.github(organization:)` and `secrets_double_github_app.yml`), and requires the attacker to control (or know the webhook secret of) at least one of the configured organizations/apps — e.g., their own org onboarded onto the same Shipit instance. No access to the victim's repository, no Shipit session, and no `ApiClient` token is required; only knowledge of the victim's public `owner/name` string, which is always public. This is a realistic scenario for any Shipit instance shared across multiple orgs/teams, a supported and tested use case in this codebase.

### Recommendation
In `WebhooksController#verify_signature` / the base `Handler`, after signature verification, enforce that the resolved signing organization equals the owning organization of `repository.full_name` (or `organization.login`) before dispatching to handlers — e.g., reject the request if `repository_owner.casecmp?(params.dig('repository','full_name').to_s.split('/').first)` is false. Alternatively, derive the `Repository`/`Stack` lookup scope from the same field used to select the verifying app/secret, so the two can never diverge.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations in `secrets.yml` (as supported by `Shipit.github(organization:)` and demonstrated in `test/dummy/config/secrets_double_github_app.yml`): `attacker-org` (attacker's own, secret known to attacker) and `victim-org` (target).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "attacker-org"`, fetches that org's `GitHubApp`, and the signature check passes (`verify_webhook_signature` returns true) since the attacker signed with their own valid secret.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `Handler#repository_name` reads `payload.dig('repository', 'full_name') == "victim-org/victim-repo"`, and `stacks` resolves to the victim's actual stacks, triggering `sync_github(expected_head_sha: "deadbeef...")` on infrastructure the attacker never had access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
