### Title
IDOR: `CCMenuController` bypasses per-client stack scoping via `Stack.from_param!` instead of `stacks.from_param!` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController#stack` overrides `Api::BaseController#stack` and calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model instead of the scoped `stacks.from_param!(params[:stack_id])` that the base controller defines. Since `CCMenuController` also overrides `authenticate_api_client` to authenticate purely via `params[:token]` (bypassing Basic Auth), any valid `ApiClient` token — even one scoped to a single stack — can be used to read the CCMenu XML status of any other stack.

### Finding Description
The intended binding is: `current_api_client.stack_id == stack.id` for every stack-scoped API request, enforced in `Api::BaseController#stack` via `stacks.from_param!` where `stacks` is defined as: [1](#0-0) 
which restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`.

`CCMenuController`, however, defines its own private `stack` method that queries `Stack` (the full unscoped class), not `stacks`: [2](#0-1) 

It also overrides `authenticate_api_client` to accept `params[:token]` directly (rather than only HTTP Basic Auth as in the base class), and only calls `super` (which would return 401) if authentication fails: [3](#0-2) 

`ApiClient.authenticate` only validates the signed token and looks up the client by id — it performs no comparison to the requested `stack_id`: [4](#0-3) 

The only authorization check applied is `require_permission :read, :stack`, which calls `current_api_client.check_permissions!('read', 'stack')`. This only checks the `permissions` array (e.g., `read:stack`) — it never compares `current_api_client.stack_id` to the requested stack: [5](#0-4) [6](#0-5) 

The client token is legitimately minted per-stack by `CCMenuUrlController#fetch`, which creates an `ApiClient` scoped only to `read:stack` permission (not bound at token-verification time to a specific `stack_id` check downstream): [7](#0-6) 

**Exploit flow**: Attacker legitimately obtains a CCMenu URL for stack 1 (e.g., via `CCMenuUrlController#fetch`), getting a token for `ApiClient` A scoped to `stack_id: 1`. Attacker then sends `GET /api/stacks/2/cc.xml?token=<A's token>`. `authenticate_api_client` succeeds because the token is cryptographically valid. `require_permission!(:read, :stack)` passes because A has `read:stack` in its permissions list. `show` calls `stack`, which resolves via `Stack.from_param!(params[:stack_id])` — an unscoped lookup — and returns stack 2 regardless of A's `stack_id`. The rendered XML (`shipit/ccmenu/project`) exposes stack 2's deploy status to the attacker.

**Why guards fail**: `stacks` scoping exists in the base controller but is never invoked because `CCMenuController` shadows both `stack` and `authenticate_api_client`. `check_permissions!` validates only the operation/scope string, not the `stack_id` binding.

### Impact Explanation
An attacker with a valid `read:stack`-scoped token for any single stack can read deploy/build status (running state, last deploy id, end time, and stack activity) for any arbitrary stack in the same Shipit instance, without further authentication. This is a cross-tenant unauthenticated read of stack state, matching the "High - unauthenticated read of stack state" impact category. The attack is trivially repeatable against every stack id/param the attacker can guess or enumerate (stack `to_param` is `owner/name/environment`, often guessable), and requires no session or elevated privilege beyond a single legitimately-issued CCMenu token.

### Likelihood Explanation
Preconditions: attacker must be a legitimate Shipit user (or holder of a CCMenu URL) for at least one stack, which grants an `ApiClient` token via `CCMenuUrlController#fetch`. No secret material beyond that self-obtained token is needed. The attacker cost is trivial — one authenticated request to get the CCMenu URL for their own stack, then arbitrary GET requests substituting a different `stack_id` in the URL path. No GitHub credentials, webhook secrets, or operator privileges are needed. This is highly feasible and fully repeatable.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the scoped `stacks.from_param!(params[:stack_id])` (i.e., remove the override entirely and rely on `Api::BaseController#stack`), so lookups honor `current_api_client.stack_id`. Additionally, review whether `authenticate_api_client`'s token-in-query-param override is necessary, and if kept, ensure `current_api_client` is bound to `stacks` scoping downstream in the same way as the base controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (add to existing suite)
test "cannot read another stack's status with a token scoped to a different stack" do
  stack1 = shipit_stacks(:shipit)
  stack2 = create(:stack, environment: 'other-env')

  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped Client',
    stack_id: stack1.id,
    permissions: %w[read:stack]
  )

  get api_stack_ccmenu_url(stack_id: stack2.to_param), params: { token: client.authentication_token }

  # Binding under test: current_api_client.stack_id (stack1.id) == stack.id (stack2.id) -> should be false
  assert_response :not_found # or :forbidden, per fixed behavior
  assert_no_match(/#{stack2.repo_name}/, response.body)
end
```
Currently this request returns `200 OK` and renders stack 2's CCMenu XML, confirming the broken binding; after fixing `stack` to use `stacks.from_param!`, the same request should raise `ActiveRecord::RecordNotFound` (404) because stack 2 is outside the `stacks` scope for a client bound to stack 1.
