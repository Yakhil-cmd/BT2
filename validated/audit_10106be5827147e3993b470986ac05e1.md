### Title
Unvalidated P2P StakingInfo Delivery Corrupts Reward Address DB During FastSync/SnapSync — (`datasync/downloader/queue.go`)

### Summary

During FastSync/SnapSync, `queue.DeliverStakingInfos` accepts peer-supplied `P2PStakingInfo` payloads with a permanently no-op `validate` function (marked `TODO`). A malicious sync peer can inject arbitrary `CouncilRewardAddrs`, `KEFAddr`, and `KIFAddr` values that are persisted to the staking DB via `PutStakingInfoToDB`, corrupting the reward address set used for subsequent block reward distribution.

### Finding Description

**Step 1 — No-op validate in `queue.DeliverStakingInfos`:** [1](#0-0) 

The `validate` closure always returns `nil` with a `// TODO-Kaia-Snapsync update validation logic` comment. Compare this to `DeliverBodies` and `DeliverReceipts`, which both verify their payloads against the committed block header hash (`TxHash` and `ReceiptHash` respectively): [2](#0-1) [3](#0-2) 

No equivalent cryptographic anchor exists for staking info — there is no `StakingInfoHash` in the block header to validate against.

**Step 2 — Attacker-controlled fields in `P2PStakingInfo`:** [4](#0-3) 

All reward-sensitive fields (`CouncilRewardAddrs`, `KEFAddr`, `KIFAddr`, `CouncilStakingAmounts`) are freely settable by the delivering peer.

**Step 3 — Direct pass-through to `StakingInfo` via `ToStakingInfo`:** [5](#0-4) 

No field-level validation occurs here. The attacker-supplied addresses are mapped 1:1 into the `StakingInfo` struct that is then persisted.

**Step 4 — Staking info is only fetched for pre-Kaia-fork blocks at `stakingUpdateInterval` boundaries:** [6](#0-5) 

This means the attack window is pre-Kaia-fork epochs. A node syncing historical blocks in FastSync/SnapSync mode will have its staking DB entries for those epochs fully controlled by the malicious peer.

### Impact Explanation

The persisted `StakingInfo` entries (with attacker-controlled `CouncilRewardAddrs`, `KEFAddr`, `KIFAddr`) are subsequently read by the staking module for:
- Block reward distribution (council reward addresses, KEF/KIF treasury splits)
- Validator weight calculation (via `CouncilStakingAmounts`)

Any node that completes FastSync/SnapSync against a malicious peer will have corrupted reward address entries in its DB, causing block rewards to be distributed to attacker-controlled addresses for the affected epochs. This directly violates the invariant that only on-chain AddressBook state determines reward/treasury addresses.

### Likelihood Explanation

- The attacker only needs to be a connectable P2P peer — no privileged access required.
- The node must be in FastSync or SnapSync mode (common for new or resyncing nodes).
- The `TODO` comment confirms this is a known gap, not an intentional design choice.
- No existing guard in the delivery path checks the staking info content against any on-chain commitment.

### Recommendation

Implement a cryptographic anchor: either include a `StakingInfoHash` in the block header (committing to the staking info at that block), or re-derive staking info from the AddressBook contract state root after FastSync completes, discarding any peer-supplied values. At minimum, remove the no-op validate and replace it with a check that the delivered `P2PStakingInfo.BlockNum` matches the header number and that the node/staking address arrays are non-empty and consistent in length.

### Proof of Concept

1. Register a malicious sync peer that responds to `StakingInfoMsg` requests with a crafted `P2PStakingInfo` containing attacker-owned `CouncilRewardAddrs` and `KEFAddr`/`KIFAddr`.
2. Trigger FastSync on the victim node against this peer.
3. The call path `handleStakingInfoMsg` → `downloader.DeliverStakingInfos` → `queue.DeliverStakingInfos` → `deliver(validate=always-nil)` → `reconstruct` → `commitFastSyncData` → `PutStakingInfoToDB` persists the attacker addresses.
4. Assert that the DB entry for the synced staking update block contains the attacker-controlled addresses.
5. Observe that subsequent reward distribution reads the corrupted DB entry and sends rewards to attacker addresses. [7](#0-6)
