### Title
Cross-tenant Commit Status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` rows using only the `sha` supplied in the (correctly signature-verified) webhook payload, with no `stack_id`/`repository_id` predicate tying the lookup back to the repository whose organization signed the webhook. Any two Stacks (different repositories, different `webhook_secret`s) that happen to import a `Commit` with the same `sha` will both receive the `Status` created from a single organization's webhook.

### Finding Description
The broken binding is: `Status.stack_id == Stack(repository == webhook's verified organization's repository)`. In reality the code enforces only `Commit.sha == params.sha`, with no constraint on `Commit#stack_id` or `Commit#stack.repository`.

Path: `WebhooksController#create` verifies the HMAC signature against the org derived from `repository_owner` (`params.dig('repository','owner','login')`) via `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) , then dispatches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [2](#0-1) . This verification only proves the payload came from *an* org that owns *a* repository whose `webhook_secret` matches — it says nothing about which `Commit` rows should be affected.

`Handler` base class exposes a `stacks` helper that correctly scopes by `Repository.from_github_repo_name(repository_name)` [3](#0-2) , but `StatusHandler#process` does not use it at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

`create_status_from_github!` then writes the status using `commit.stack_id` (each matched commit's own stack, regardless of which repo sent the webhook) [5](#0-4) , and `Status.replicate_from_github!` persists it with that `stack_id` [6](#0-5) .

Attacker flow: attacker controls a repository/org A with a valid `webhook_secret` (self-service, e.g. installing the Shipit GitHub App on their own fork/org). They push/import a commit whose `sha` collides with a commit already present in victim Stack B (plausible via shared submodule commit, cherry-pick, or a monorepo fork sharing history — `sha` collisions across repos requiring identical git objects are attacker-achievable by copying/forking the exact blob history). Attacker POSTs a signed `status` webhook for org A with that `sha`. `StatusHandler` finds **all** `Commit` rows with that `sha` across all stacks, including the one in Stack B, and writes a `Status` on it with `stack_id` = victim Stack B's id, using `Status.replicate_from_github!` which further triggers `enable_ci_on_stack`, `schedule_continuous_delivery`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` if success/pending [7](#0-6) .

None of the existing guards prevent this: `verify_signature` only authenticates "some org with a repo owns this secret," not "this org owns this commit"; `drop_unhandled_event` is unrelated; the `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`/etc., not ownership [8](#0-7) ; and `Handler#stacks`/`repository_name` scoping exists but is simply not invoked by `StatusHandler#process`.

### Impact Explanation
An attacker who controls any repository onboarded to Shipit (or any org for which they can get a webhook accepted) can inject fabricated CI status (`success`/`failure`/`error`) onto commits belonging to an unrelated Stack/organization, provided a `sha` collision exists between the two repos' commit histories. Writing a `success` status on a victim's Stack can trigger `stack.schedule_merges` (auto-merge) and continuous delivery scheduling in the victim's Stack — i.e., a CI event scoped to org A can influence deploy/merge decisions in org B. This matches "a payload for one repository mutating another's stack, commit, task or team" — Critical impact. Blast radius spans every Stack in the installation that happens to share a `sha` with the attacker-controlled repository.

### Likelihood Explanation
Preconditions: the attacker needs their own repository legitimately onboarded/authorized in the Shipit instance (so their `webhook_secret` is valid and signature verification passes) — this is an unprivileged, self-service action for the attacker's own repo. The remaining precondition — a `sha` collision between the attacker's commit history and the victim Stack's commit history — is the limiting factor; it's plausible in shared-submodule/monorepo-fork/cherry-pick scenarios but not universal. Given that precondition, exploitation is trivial and repeatable per matching commit.

### Recommendation
Scope the lookup in `StatusHandler#process` to only commits belonging to stacks of the repository that sent (and was signature-verified for) the webhook, using the existing `stacks` helper, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern already used elsewhere in `Handler`.

### Proof of Concept
Minitest plan (bypassing the controller, calling `StatusHandler.call` directly as suggested):
```ruby
test "StatusHandler does not leak status across stacks with colliding sha" do
  stack_a = shipit_stacks(:shipit)          # org A's stack
  stack_b = shipit_stacks(:cyclimse)        # org B's stack (different repository)

  commit_a = stack_a.commits.create!(sha: "deadbeef", author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "a")
  commit_b = stack_b.commits.create!(sha: "deadbeef", author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "b")

  payload = {
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => stack_a.repository.owner } },
    'sha' => 'deadbeef', 'state' => 'success', 'context' => 'ci/travis'
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal 1, commit_a.reload.statuses.count, "status should be recorded for the sending repo's commit"
  assert_equal 0, commit_b.reload.statuses.count, "status must NOT leak into an unrelated stack (currently fails)"
end
```
With current code, `commit_b.statuses.count` will be `1`, proving the cross-stack leak; after applying the recommended fix it becomes `0`.

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end
      new_status
    end
