### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but the stack/repository that is actually acted on is selected from the independent `repository.full_name` field, letting a holder of one organization's `webhook_secret` forge events for a different organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`Shipit.github_organizations` / per-org `webhook_secret` config), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the HMAC against using `repository_owner`, which is read from the same untrusted JSON body it is verifying (`params.dig('repository', 'owner', 'login')`). The handlers that actually act on the payload (e.g. `PushHandler`) instead resolve the target `Stack`/`Repository` from a *different* field of that same body, `repository.full_name` (`Handler#repository_name`). Because HMAC-SHA1 only proves "this exact byte sequence was produced by someone who knows a particular secret" and not "the content is semantically consistent," an attacker who knows the `webhook_secret` for organization A (e.g. because they legitimately control that org's GitHub App/webhook) can send a raw POST body where `repository.owner.login = "A"` (so verification picks A's secret and succeeds) while `repository.full_name = "B/victim-repo"` (an entirely different org/repo tracked by the same Shipit instance). This breaks the intended binding: `organization authenticated == repository acted upon`.

### Finding Description
- `WebhooksController#verify_signature` picks the GitHub App config to validate against based on attacker-supplied payload content: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` performs a straightforward HMAC-SHA1 compare over the whole raw body against `@webhook_secret` for the org selected above; it says nothing about which repository the payload is allowed to reference: [3](#0-2) 

- The actual event handlers, however, determine which `Repository`/`Stack` to mutate using a **different** field of the same JSON body, `repository.full_name`, with no re-check against `repository_owner`/the verified organization: [4](#0-3) [5](#0-4) 

- Multi-org support with per-organization `webhook_secret` values is a first-class, documented feature (`Shipit.github(organization:)`, `github_app_config`), confirming this isn't a single-tenant deployment where the ambiguity is moot: [6](#0-5) 

Because the signature is computed over the full raw body and the attacker fully controls that body's content (only the secret is unknown to them, and they know org A's secret because they legitimately operate org A's app), they can set `repository.owner.login` to `"A"` (to pass verification) and `repository.full_name` to `"VictimOrg/victim-repo"` in the very same payload. `verify_signature` will succeed using org A's secret, and `PushHandler`/other handlers will then look up and act on `VictimOrg/victim-repo`'s `Stack` using `repository.full_name`, triggering `stack.sync_github(expected_head_sha: params.after)` (and analogous state changes in other handlers such as `status`, `check_suite`, `membership`) for a repository/organization the attacker has no legitimate relationship to.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. An attacker who legitimately controls org A's GitHub App webhook secret can inject forged sync/status/check-suite events against any other tracked repository/stack in the same Shipit instance, causing unauthorized state changes (forced re-sync to an attacker-chosen `expected_head_sha`, spoofed commit statuses/check runs) on a stack they do not own — a cross-repository write achieved without ever needing access to that other repository, satisfying the "cross-repository writes" impact bucket.

### Likelihood Explanation
Requires the deployment to use the multi-organization github secrets schema (`secrets.github` keyed by org, each with its own `webhook_secret`) and requires the attacker to hold a valid webhook secret for at least one configured organization (e.g., their own org's GitHub App, which they legitimately administer). This is a realistic scenario for any Shipit installation shared across multiple orgs/teams, which is exactly the use case the multi-org secrets format targets.

### Recommendation
After signature verification succeeds, re-derive/re-validate that `repository.full_name`'s owner segment matches the same `repository_owner` (org) that was used to select the verifying secret, and reject the webhook (422) if they differ. Alternatively, bind webhook secrets 1:1 to a specific repository/stack instead of to an organization-wide secret shared by all repos under that org's config, or pass/verify the organization context out-of-band (e.g., via URL path segment) rather than trusting it from the same unverified JSON body.

### Proof of Concept
1. Configure Shipit with two organizations under `secrets.github`: `OrgA` (webhook_secret `secretA`) and `OrgB` (webhook_secret `secretB`), each tracking their own stacks, e.g. `OrgA/repoA` and `OrgB/repoB`.
2. Attacker legitimately controls `OrgA`'s GitHub App and therefore knows `secretA`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/repoB"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(secretA, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` reads `repository_owner = "OrgA"`, calls `Shipit.github(organization: "OrgA")`, and `verify_webhook_signature` succeeds since the signature was computed with `secretA`.
6. `PushHandler#process` resolves `repository_name = "OrgB/repoB"` via `Handler#repository_name`, finds `OrgB`'s stack(s) on branch `main`, and calls `stack.sync_github(expected_head_sha: "<attacker_chosen_sha>")` — mutating `OrgB`'s stack state despite the attacker having no legitimate relationship to `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
