### Title
Membership webhook `team.id` lookup bypasses organization scoping, allowing escalation into `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` resolves a `Shipit::Team` record purely by the numeric `github_id` taken from the webhook payload, never validating that this `github_id` actually belongs to the organization that authenticated the request. Any organization that has its own valid GitHub App/webhook configuration in Shipit can forge a `membership` webhook whose `team.id` matches the `github_id` of a `Team` record that already exists in Shipit's DB for a *different, more privileged* organization (e.g., one of the teams configured in `Shipit.github_teams`), and add an arbitrary Shipit `User` to it — breaking the binding "the organization that authenticated the webhook" versus "the team whose membership is written."

### Finding Description
`WebhooksController#verify_signature` correctly selects the GitHub App/secret to check the signature against, based on `repository_owner` (or `organization.login`) found in the payload itself: [3](#0-2) 

This means a webhook is only proven to originate from *some* configured GitHub organization — the one named in its own `organization.login` field — not from any particular privileged organization. Shipit supports multiple independently configured GitHub organizations (see `config/secrets.development.shopify.yml`), each with its own `webhook_secret`. [4](#0-3) 

Once the signature check passes, `MembershipHandler#process` calls `find_or_create_team!`, which does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [5](#0-4) 

The `organization` assignment inside the block only takes effect when a *new* record is created. If a `Team` row with that `github_id` already exists (created earlier for a legitimate, possibly different, organization — e.g., through `Shipit.github_teams` bootstrapping via `Team.find_or_create_by_handle`), the lookup returns that existing record regardless of which organization is named in the current payload's `organization.login` field. [6](#0-5) [7](#0-6) 

The handler then does:
```ruby
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member) # when action == 'added'
``` [8](#0-7) 

`User.find_or_create_by_login!` will fetch/create a Shipit `User` for any GitHub login the attacker names — it is not restricted to members of the sending organization. [9](#0-8) 

This directly maps to the OrderNFT bug class: `decodeId()` trusted an ambiguous field (the `isBid` byte) without validating it maps unambiguously back to the originally-encoded `OrderKey`, letting an attacker craft a second token ID that decodes to the same order and bypasses the approval binding. Here, `find_or_create_team!` trusts an ambiguous/unscoped identifier (`github_id`) without checking it against the field that was actually verified by the signature (`organization.login`), letting an attacker's own (legitimately signed) organization graft membership writes onto an unrelated, already-existing, more-privileged `Team` record.

Authorization is decided by `User#authorized?`, which checks membership in any team listed in `Shipit.github_teams`: [10](#0-9) 

So an attacker who controls (or compromises) webhook delivery for *any* GitHub organization configured in this Shipit instance — even one unrelated to and less trusted than the organization whose team grants access — can add an arbitrary Shipit `User` to that privileged `Team`, if that team's `github_id` is already known/present in Shipit's database (which happens automatically once `Shipit.github_teams` is evaluated for the privileged org).

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization — explicitly listed as a High-severity impact category. It allows an attacker (who is not a member of, and has no access rights within, the privileged GitHub organization) to grant themselves (or any known Shipit user) team membership that satisfies `authorized?`, unlocking access to Shipit stacks, deploys, and GitHub-authenticated actions gated by that team.

### Likelihood Explanation
Exploitation requires: (1) the attacker to control webhook delivery for at least one organization that Shipit is configured to trust (i.e., they can produce a validly HMAC-signed `membership` event for *some* org — a reasonable bar in multi-tenant Shipit deployments, e.g. self-service or partner orgs), and (2) knowledge of the target privileged team's numeric `github_id`, which is not secret (team IDs are visible via GitHub's API/UI to team members, and could also have been observed in prior legitimate webhook deliveries or API responses). No repository write access, `ApiClient` token, or GitHub App private key is needed — only the ability to trigger/replay a `membership` webhook from an organization the attacker already administers.

### Recommendation
Scope the `Team` lookup by the authenticated organization in addition to `github_id` (e.g., `find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/ignore membership events whose `organization.login` does not match the `organization` already recorded on an existing `Team` with that `github_id`. This mirrors the OrderNFT fix's recommendation of validating decoded fields unambiguously before acting on them.

### Proof of Concept
1. Shipit is configured with two organizations: `privileged-org` (whose team `privileged-org/admins`, `github_id=999`, is listed in `Shipit.github_teams` and already persisted as a `Team` row, e.g. via prior `Shipit.github_teams` evaluation) and `attacker-org` (an org the attacker legitimately administers, with its own valid `webhook_secret` configured in Shipit).
2. Attacker discovers `github_id=999` for `privileged-org/admins` (e.g., via GitHub's team API while briefly having read access, or from cached data).
3. Attacker sends a `membership` webhook, correctly HMAC-signed with `attacker-org`'s `webhook_secret`, with body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-github-login" }
}
```
4. `WebhooksController#verify_signature` validates the signature using `attacker-org`'s secret and succeeds (payload's `organization.login` matches the signing org).
5. `MembershipHandler#find_or_create_team!` runs `Team.find_or_create_by!(github_id: 999)`, which returns the **existing** `privileged-org/admins` team row (created earlier for `privileged-org`), ignoring that the payload claims `organization: attacker-org`.
6. `User.find_or_create_by_login!('attacker-github-login')` creates/fetches the attacker's Shipit `User`, and `team.add_member(member)` adds them to `privileged-org/admins`.
7. The attacker's user now passes `User#authorized?` for `privileged-org`, gaining unauthorized access to Shipit functionality gated behind `Shipit.github_teams`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
