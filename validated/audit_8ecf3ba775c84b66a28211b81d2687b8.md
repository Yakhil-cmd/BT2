### Title
Cross-tenant Team hijack via unscoped `github_id` lookup in `membership` webhook - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook only against the webhook secret of the organization named in the payload itself (`repository_owner`/`organization.login`), but `MembershipHandler#find_or_create_team!` looks up the target `Team` solely by the global `github_id` field with no organization scoping. An attacker who controls a legitimate, Shipit-configured GitHub organization (and therefore knows that org's own `webhook_secret`) can forge a correctly-signed `membership` payload whose `team.id` matches a pre-existing victim `Team` row from a different organization, causing `team.add_member(member)` to add the attacker to that victim team and satisfy `User#authorized?`.

### Finding Description
The binding the system needs to hold is:
`organization_that_verified_the_signature == organization_that_owns_the_Team_row_matched_by_github_id`

In `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30), the app looks up `Shipit.github(organization: repository_owner)` where `repository_owner` falls back to `params.dig('organization', 'login')` (line 61) when no `repository` key is present — exactly the case for `membership` events. This means HMAC verification is scoped to whatever organization the attacker names in their own payload, using that organization's own `webhook_secret` — which the attacker, as owner of a Shipit-configured org, knows.

`MembershipHandler#find_or_create_team!` (app/models/shipit/webhooks/handlers/membership_handler.rb:38-43) then does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
```
This queries solely on `github_id`, a value taken verbatim from the JSON body — nothing ties it to `params.organization.login` for the *find* branch (organization is only set on *create*). Since the payload is a raw HTTP POST crafted by the attacker (not a real GitHub delivery), `team.id` can be set to any integer, including the `github_id` of a `Team` row already persisted for a victim organization (via `Shipit.github_teams`/`oauth.teams` provisioning, see `Team.find_or_create_by_handle` in app/models/shipit/team.rb:18-27).

`MembershipHandler#process` (lines 22-34) then calls `team.add_member(member)` where `member` is `User.find_or_create_by_login!(params.member.login)` — the attacker's own GitHub login. `Team#add_member` (app/models/shipit/team.rb:41-43) unconditionally appends the membership. Since `User#authorized?` (app/models/shipit/user.rb:80-82) checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, the attacker now satisfies authorization for the entire Shipit instance despite never being verified for the victim's organization.

Existing guards do not prevent this: `verify_signature` only proves the request was signed by *some* configured org's secret, not that the *content* (team id, organization) belongs to that org; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence, not cross-referencing `team.id` ownership against `organization.login`.

### Impact Explanation
A successful forged request grants the attacker `User#authorized?` == true instance-wide (High severity per the rubric: "escalation into `Shipit.github_teams` authorization"). Once authorized, the attacker can log in/act as an authorized Shipit user across the multi-tenant instance, which — depending on downstream `require_permission!`/authorization checks elsewhere in the app — may allow deploys, rollbacks, or other privileged actions against stacks belonging to *other* tenants, not just their own organization. The attack is repeatable (each POST is independent) and blast radius spans every `Team` whose `github_id` the attacker can correctly guess or enumerate, i.e., cross-tenant.

### Likelihood Explanation
Preconditions: Shipit must be run in the documented multi-organization mode (`config/secrets.yml` keyed per-org, see `docs/setup.md` "Using Multiple Github Applications"), the attacker must own/administer one of those configured orgs (and thus know its `webhook_secret`), and at least one victim `Team` (from `Shipit.github_teams`/`oauth.teams`) must already exist with a `github_id` the attacker can supply or guess. Attacker cost is low (a single signed HTTP POST); the main uncertainty is discovering the victim's real numeric `github_id`, which is not secret on GitHub (team ids are visible via the GitHub API for teams the attacker can query, or via other org-teams listings) and is not treated as a secret by Shipit. Given the intended threat model in this question (an org owner with their own installed GitHub app), the precondition is realistic for any Shipit deployment serving multiple GitHub organizations.

### Recommendation
Scope the `Team` lookup and validate cross-references by organization, e.g.:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
and additionally raise/reject if a `Team` with `github_id` already exists but its `organization` doesn't match `params.organization.login` (to catch a collision instead of silently reusing the wrong record). Also add a uniqueness/composite index on `(github_id, organization)` at the database level, and consider verifying `params.organization.login` against the same organization used for `verify_signature` before processing the handler.

    end
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],

      )
      head(422) unless verified

      Rails.logger.info([

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
