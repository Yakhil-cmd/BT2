### Title
Concurrent AA trigger dry-run vs. real execution corrupts shared in-memory unit caches - (File: aa_composer.js)

### Summary
`aa_composer.js` maintains process-wide, globally-shared associative maps in `storage.js` (`assocUnstableUnits`, `assocUnstableMessages`, `assocBestChildren`, `assocStableUnits`, `assocCachedUnits`, etc.) that are mutated by every AA trigger execution. When `conf.bDryRunNewTriggers` is enabled, `network.js` runs `aa_composer.dryRunPrimaryAATrigger()` for a freshly-posted unit's AA trigger *before* the unit is actually saved/committed, purely to "pre-flight" whether the real execution would crash. After the dry run finishes, it calls `revertResponsesInCaches(arrResponses)`, which walks the response units it created and calls `storage.forgetUnit()` on each, deleting them (and related bookkeeping) from the shared caches. Because both the dry run and any concurrently-in-flight real primary/secondary trigger executions for the same or related AA addresses operate on the *same* global caches across asynchronous DB round-trips (no mutex serializes dry-run vs. real trigger cache mutations on the same address), an attacker who posts a shaped AA-triggering unit can cause the dry-run's cleanup path to race with, and corrupt, cache state that a real, concurrently-processing trigger execution still depends on. This mirrors the EVerest CVE-2026-26070 pattern: one asynchronous flow (periodic/"real" update) mutates a shared map while an unrelated flow (an EV disconnect/"session finished"-style cleanup, here the dry-run revert) deletes/rewrites entries in the same map concurrently, corrupting the container.

### Finding Description
`revertResponsesInCaches()` unconditionally deletes cache entries for every response unit generated by a dry run: [1](#0-0) 

`storage.forgetUnit()` performs several sequential `delete`s across independent global maps (`assocKnownUnits`, `assocCachedUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`, `assocUnstableUnits`, `assocStableUnits`, `assocUnstableMessages`, `assocBestChildren`), and also mutates the *parent's* `assocBestChildren` array in place via `_.pull`: [2](#0-1) 

`dryRunPrimaryAATrigger()` is invoked directly from `network.js`'s `handleJoint` `ifOk` callback for every newly submitted unit that contains a primary AA trigger, prior to `writer.saveJoint()` actually persisting the unit — i.e., it runs on the hot path for any externally submitted unit: [3](#0-2) 

The dry-run trigger execution itself spans multiple asynchronous DB round trips (`db.takeConnectionFromPool`, `conn.query("BEGIN")`, `readLastStableMcUnit`, `handleTrigger`, which recursively performs further async `conn.query` calls for `aa_addresses`, `readAADefinition`, secondary triggers, etc.): [4](#0-3) 

Crucially, `handleTrigger()` (used by both the dry run and the real/committed execution path in `handlePrimaryAATrigger`) reads and writes the very same global caches (`storage.assocUnstableUnits`, `storage.assocStableUnits`, `storage.assocBestChildren`, `storage.assocUnstableMessages`) via `writer.saveJoint()`'s in-memory bookkeeping: [5](#0-4) 

Unlike the real trigger-processing pipeline, which is serialized behind `mutex.lock(arrAuthorAddresses, ...)` in `validation.js`: [6](#0-5) 

`dryRunPrimaryAATrigger()` takes **no such lock** on the AA address or on any global mutex key before mutating the shared caches (contrast with `handlePrimaryAATrigger`, which also has no explicit AA-address mutex and relies only on serialized MC processing). Because Node's event loop interleaves independent async chains at every `await`/callback boundary, a second unit that also triggers AA execution on the same address (or whose secondary-trigger chain touches units created transiently by the dry run) can have its callback fire in between the dry run's asynchronous steps. The dry run's final `revertResponsesInCaches()` → `storage.forgetUnit()` step can then delete unit-cache entries, and mutate `assocBestChildren` arrays via `_.pull`, that the interleaved real execution is concurrently relying on to compute best-parent/free-unit bookkeeping or to look up `storage.assocStableUnits[unit].count_aa_responses` (which `handleTrigger` throws on if missing: "handlePrimaryAATrigger: unit ... not found in cache"). The test suite's own assertions (`t.deepEqual(storage.assocUnstableUnits, old_cache.assocUnstableUnits)` etc. after every `dryRunPrimaryAATrigger` call in `test/aa_composer.test.js`) confirm that the developers consider full cache restoration a correctness invariant for the dry-run path — an invariant that a second, interleaved async flow touching the same caches can violate.

### Impact Explanation
If the shared unit-props/best-children/unstable-messages caches are corrupted (entries deleted or `assocBestChildren` arrays incorrectly pulled) while a real AA trigger chain or main-chain stabilization concurrently depends on them, the node can:
- crash via unhandled `throw Error(...)` (e.g. "handlePrimaryAATrigger: unit ... not found in cache", "no stable unit ...", "trying to forget stable unit ...") once the corrupted entry is looked up by the interleaved real flow — a node-wide denial of service/crash, analogous to the EVerest crash;
- silently diverge from other nodes on AA-execution/state-var bookkeeping if a response unit's presence in `assocBestChildren`/`assocUnstableMessages` is lost, potentially causing inconsistent `is_free` flags or missed data-feed/AA-response propagation, which is a form of node disagreement on unit state.

This satisfies the "node disagreement on validity/stability" and "network unable to confirm new units" acceptance bars from the validation rules, since a crash on the hot `handleJoint`/`saveJoint` path stalls processing of new units.

### Likelihood Explanation
Reachability requires `conf.bDryRunNewTriggers` to be enabled (an operator-configurable, not necessarily default-on, setting), which lowers likelihood somewhat, but the trigger condition itself — posting an AA-triggering unit while another AA-triggering unit for a related address is already mid-processing — is fully controllable by any unprivileged unit poster/AA trigger sender; no special privileges, malicious peers, or network-level manipulation are needed. The lack of any explicit mutex around `dryRunPrimaryAATrigger`'s cache mutations (unlike the mutex used in `validation.js`) makes the race structurally present whenever the feature is on. I could not fully trace every intermediate `await` point inside `handleTrigger`'s many nested `conn.query` continuations within the tool budget available, so the precise minimal repro (exact interleaving window) is not 100% confirmed — this should be validated with a live two-unit concurrent-trigger test.

### Recommendation
- Serialize `dryRunPrimaryAATrigger()` (and its `revertResponsesInCaches()` cleanup) behind the same mutex key(s) (author/AA address, or a dedicated `dry_run_aa` key) used by the real trigger-execution/validation path, so dry runs cannot interleave with real executions that touch overlapping units/addresses.
- Avoid mutating global shared caches (`storage.assocUnstableUnits`, `assocBestChildren`, `assocUnstableMessages`, `assocStableUnits`) during a dry run at all; instead operate on a private/shadow copy of the relevant cache slices for the duration of the dry run and discard it, rather than doing "mutate then revert."
- Add invariant checks (already partially present as `throw Error` guards) to fail loudly and safely rather than continue with a corrupted cache, and consider disabling `bDryRunNewTriggers` by default until the race is fixed.

### Proof of Concept
1. Enable `conf.bDryRunNewTriggers = true`.
2. Deploy an AA at address `A` with a secondary-trigger chain that performs at least one additional async DB round trip in `handleSecondaryTriggers` (e.g., calls into a second AA `B` via `aa_addresses` lookup), as in `aa_composer.js` `handleSecondaryTriggers`: [7](#0-6) 
3. From an unprivileged wallet, post unit `U1` that triggers AA `A` with `count_primary_aa_triggers` set (this is naturally set for any unit whose outputs pay an AA address). `network.js` will invoke `dryRunPrimaryAATrigger` for `U1` before saving it: [3](#0-2) 
4. While the dry run for `U1` is mid-flight (i.e., during its internal `conn.query` round trips for secondary AA `B`), post a second unit `U2` that also triggers AA `A` or `B` for real (this can be raced by timing two posts in quick succession, or by having `U1`'s own real `handlePrimaryAATrigger`, invoked later from `writer.saveJoint`/`handleAATriggers`, overlap with a third unit's trigger).
5. Observe that `dryRunPrimaryAATrigger`'s `revertResponsesInCaches` for `U1`'s dry run deletes cache entries via `storage.forgetUnit` ( [2](#0-1) ) that the concurrently-processing real trigger execution for `U2` still needs, causing a thrown error such as `"handlePrimaryAATrigger: unit ... not found in cache"` ( [8](#0-7) ) and crashing/stalling the node's unit-processing pipeline.
