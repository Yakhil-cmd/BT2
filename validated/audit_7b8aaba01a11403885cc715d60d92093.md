### Title
Permanent lock of bridged funds when Ethereum-side recipient cannot receive value - (File: `bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/BridgeVault.sol`, `crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary
This is a direct analog of the `FeeDistributor` bug: a single non-cooperative or incapable recipient blocks release of funds, and since the message is bound to that exact recipient with no built-in redirect/migration path, the funds become permanently stuck.

### Finding Description
`bridge::send_token`/`send_token_v2` burns/escrows the user's Sui asset unconditionally and commits an immutable `target_address` into the signed `BridgeMessage`/`BridgeRecord` [1](#0-0) . Once the committee signs this message, the only path to release the corresponding ETH/ERC20 is `SuiBridge.transferBridgedTokensWithSignatures`, which invokes `_transferTokensFromVault` → `vault.transferETH`/`transferERC20` **prior** to setting `isTransferProcessed[message.nonce] = true` [3](#0-2) . `BridgeVault.transferETH` performs a raw low-level `call{value: amount}("")` with `require(success, ...)` [4](#0-3) , and `transferERC20` uses `SafeERC20.safeTransfer` [5](#0-4) . If `recipientAddress` is (a) a contract with no payable `receive()`/`fallback()` or one that explicitly reverts, or (b) an address blacklisted by a token contract that supports blocklisting (e.g., USDC), every call to `transferBridgedTokensWithSignatures` for that nonce reverts. Because the transfer happens before the nonce is marked processed, there is no partial state to roll back to a different address — the message content (including `recipientAddress`) is fixed and already signed by the committee quorum, and there is no on-chain mechanism to re-target or refund the escrowed/burned Sui-side value to a different, working address.

### Impact Explanation
This matches the "permanent fund lock" High/Medium impact class explicitly listed in scope. Unlike the Ethereum `FeeDistributor` case (attacker griefs multiple stakeholders' fees at once via one bad receiver in a shared pool), here the burned/escrowed value belongs to the specific bridging user, but the amount already left circulation on the Sui side (burned via `treasury.burn`) and cannot ever be unlocked on Ethereum, nor can it be refunded on Sui, since `send_token_internal` has no reversal path once the coin is burned [6](#0-5) . This is a genuine, permanent, protocol-level fund lock reachable by an ordinary bridge user (no privileged actor needed), consistent with the bounty's allowed "permanent fund lock" category.

### Likelihood Explanation
Trivial to trigger: any user can call `send_token`/`send_token_v2` with `target_address` set to a contract they deploy with a reverting `receive()` (or fallback), or to a known-blacklisted USDC address, before or after the bridge signs the message. No committee/validator collusion or privileged role is required — this is squarely within the "ordinary bridge user" attacker model.

### Recommendation
Add an escape-hatch/migration mechanism analogous to what the original report recommends for `FeeDistributor`: e.g., allow marking a transfer as processed and diverting funds to a pull-based claim mapping (`recipient => balance`) when the push-transfer reverts, so users can later claim from a fixed, non-reverting address, or allow governance/committee-approved re-targeting of a stuck claim to a new address after a timeout, decoupling nonce consumption from successful value delivery.

### Proof of Concept
1. Attacker deploys `Reverter` contract on Ethereum with `receive() external payable { revert(); }`.
2. Attacker calls `bridge::send_token<SUI>(bridge, ETH_CHAIN_ID, address(Reverter), coin, ctx)` on Sui — this immediately burns the coin via `send_token_internal` and records a `BridgeRecord` [7](#0-6) .
3. Bridge committee signs the resulting `BridgeMessage` normally (this is routine, non-privileged/automatic infra behavior, not malicious quorum action).
4. Anyone submits `SuiBridge.transferBridgedTokensWithSignatures(signatures, message)` on Ethereum for the ETH token path — `vault.transferETH` reverts on `recipientAddress.call{value: amount}("")` because `Reverter` has no accepting receive, causing the entire transaction (including the nonce-processed flag) to revert [3](#0-2) .
5. Every future call with the same signed message reverts identically; the ETH remains locked in `BridgeVault` forever, and the burned Sui-side coin can never be recovered.

Note: I could not fully verify whether any off-chain relayer/orchestrator (e.g. `BridgeOrchestrator`) has retry logic that could work around this by somehow allowing a different signed message for the same deposit — from the code inspected, the message (including `target_address`) is derived once from the original `TokenDepositedEvent` and is not something a user can amend, so this appears to be a genuine dead end, but a full audit of `crates/sui-bridge` orchestrator/executor retry semantics would help confirm no undocumented recovery path exists.

public fun send_token<T>(
    bridge: &mut Bridge,
    target_chain: u8,
    target_address: vector<u8>,
    token: Coin<T>,
    ctx: &mut TxContext,
) {
    let inner = load_inner_mut(bridge);

    let bridge_seq_num = inner.get_current_seq_num_and_increment(message_types::token());
    let token_id = inner.treasury.token_id<T>();
    let token_amount = token.balance().value();
    assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
    assert!(token_amount > 0, ETokenValueIsZero);

    // create bridge message
    let message = message::create_token_bridge_message(
        inner.chain_id,
        bridge_seq_num,
        address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_id,
        token_amount,
    );

    inner.send_token_internal(target_chain, token, message);

    // emit event
    event::emit(TokenDepositedEvent {
        seq_num: bridge_seq_num,
        source_chain: inner.chain_id,
        sender_address: address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_type: token_id,
        amount: token_amount,
    });
}

fun send_token_internal<T>(
    inner: &mut BridgeInner,
    target_chain: u8,
    token: Coin<T>,
    message: BridgeMessage,
) {
    assert!(!inner.paused, EBridgeUnavailable);
    assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);

    // burn / escrow token, unsupported coins will fail in this step
    inner.treasury.burn(token);

    // Store pending bridge request
    inner
        .token_transfer_records
        .push_back(
            message.key(),
            BridgeRecord {
                message,
                verified_signatures: option::none(),
                claimed: false,
            },
        );
}

    function transferBridgedTokensWithSignatures(
        bytes[] memory signatures,
        BridgeUtils.Message memory message
    )
        external
        nonReentrant
        verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
        onlySupportedChain(message.chainID)
    {
        // verify that message has not been processed
        require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");

        IBridgeConfig config = committee.config();

        BridgeUtils.TokenTransferPayload memory tokenTransferPayload =
            BridgeUtils.decodeTokenTransferPayload(message.payload);

        // verify target chain ID is this chain ID
        require(
            tokenTransferPayload.targetChain == config.chainID(), "SuiBridge: Invalid target chain"
        );

        // convert amount to ERC20 token decimals
        uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
            IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
            config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
            tokenTransferPayload.amount
        );

        _transferTokensFromVault(
            message.chainID,
            tokenTransferPayload.tokenID,
            tokenTransferPayload.recipientAddress,
            erc20AdjustedAmount
        );

        // mark message as processed
        isTransferProcessed[message.nonce] = true;

        emit TokensClaimed(
            message.chainID,
            message.nonce,
            config.chainID(),
            tokenTransferPayload.tokenID,
            erc20AdjustedAmount,
            tokenTransferPayload.senderAddress,
            tokenTransferPayload.recipientAddress
        );
    }
