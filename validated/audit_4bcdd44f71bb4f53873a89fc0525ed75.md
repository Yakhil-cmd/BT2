### Title
Unauthenticated CPU-exhaustion DoS via crafted oscript formula strings evaluated by nearley Earley parser before any complexity limits apply - (File: formula/parse_ojson.js, formula/validation.js, formula/evaluation.js)

### Summary
The Zabbix CVE-2026-23930 root cause is that an unauthenticated request can trigger evaluation of an attacker-controlled expression whose parsing/evaluation cost is disproportionate to the request size, exhausting frontend CPU. ocore has an analogous pattern: every AA definition (`bounce_fees`/getters/state formulas) and any oscript/ojson formula embedded in a unit (AA definition, trigger `data`, or template) is parsed with the general-purpose `nearley` Earley parser in `formula/parse_ojson.js` (`parseOscriptGrammar`, called from `parseOjsonGrammar`/`parse`) [1](#0-0)  and again independently in `formula/validation.js`/`formula/evaluation.js` via `new nearley.Parser(nearley.Grammar.fromCompiled(grammar)); parser.feed(formula)` [2](#0-1) [3](#0-2) . Crucially, **parsing happens before any of the complexity/op-count/depth guards are applied** — `MAX_COMPLEXITY`, `MAX_OPS`, and the 100-level recursion-depth check only bound the AST-walking `evaluate()` function that runs *after* the nearley parse has already completed [4](#0-3)  and after `aa_validation.js`'s `validateFormula` calls into `formulaValidator.validate` [5](#0-4) .

### Finding Description
Earley parsing (the algorithm `nearley` implements) is only guaranteed sub-cubic time in the length of the input for the *worst case*, but grammars with local ambiguity (many overlapping derivations for the same substring) can produce a combinatorial blow-up in the number of parse states/edges tracked internally, well before hitting the O(n^3) bound, especially for short but deeply ambiguous inputs. The oscript grammar in `formula/grammars/oscript.js` contains many overlapping left-recursive/precedence rules for arithmetic, string concatenation, unary operators, and array/dictionary literals (e.g., `Exp`, `MD`, `AS`, `N`, `unary_expr` rules chained together) [6](#0-5) . Because `parser.feed(formula)` is invoked directly on attacker-supplied bytes with no pre-parse size or shape restriction other than the encompassing unit-size limit, and because the resulting `parser.results` set is only checked for length after the parse completes (`validateFormula` in `parse_ojson.js` throws only if `parserResults.length !== 1`, i.e. after the parse has already been paid for) [7](#0-6) , a single poster of an AA definition or a single AA-trigger sender can submit a formula string engineered to maximize Earley chart growth (e.g., long chains of ambiguous operators, deeply nested parentheses/arrays, or repeated concatenation operators) and force the node to spend disproportionate CPU parsing it — independent of and prior to the `MAX_COMPLEXITY`/`MAX_OPS` limits that only police the *evaluated* AST size, not the *parse* cost.

This mirrors the Zabbix root cause exactly: `testtriggerexpr`-style unauthenticated evaluation of a user-supplied expression grammar without bounding the cost of parsing itself, only the cost of the resulting expression tree.

### Impact Explanation
Because `evaluate` of unit content, AA-definition validation, and trigger processing occur inline during unit/AA-response validation on every full node (part of consensus-critical processing), a computationally expensive parse forces every node that validates the unit (or the AA that receives the trigger) to burn CPU on the same pathological input. If crafted formulas are embedded in widely-propagated units (AA definitions or AA triggers, which by design are processed by all full nodes tracking that AA), this can degrade the network's ability to validate and confirm new units in a timely manner — a network-wide availability impact, not merely a single node hiccup, satisfying the "network unable to confirm new units" bar.

### Likelihood Explanation
Any unprivileged user can post a unit defining an AA (`arrDefinition` validated by `validateAADefinition`/`validateFormula` in `aa_validation.js`) or send a payment/trigger with a `data` field containing an oscript formula processed by `aa_composer.js`'s `evaluateAA`/`replace` [8](#0-7) . No special privileges, keys, or node compromise are required — the formula string is fully attacker-controlled content of a normally-formed unit, so likelihood of exploitability (if the grammar indeed has an exploitable ambiguity) is high. However, I could not concretely construct or confirm a specific formula string producing worst-case exponential/polynomial blow-up within this session — that requires empirical benchmarking of `nearley` against the compiled `oscript`/`ojson` grammars in `formula/grammars/`, which I do not have tooling access to run here.

### Recommendation
- Impose a strict maximum length on any formula substring before calling `parser.feed()` in `formula/parse_ojson.js`, `formula/validation.js`, and `formula/evaluation.js`, independent of/tighter than the overall unit-size limit.
- Add a wall-clock or "parse step" budget around `nearley.Parser`/`parser.feed` calls, aborting and rejecting the unit if parsing exceeds a bounded time/step count.
- Audit `formula/grammars/oscript.js` and `formula/grammars/ojson.js` for locally ambiguous productions (rules producing multiple derivations for the same span) and refactor them to be unambiguous, since nearley's Earley chart cost is highly sensitive to grammar ambiguity.
- Consider caching rejection of previously-seen pathological formulas is not sufficient; the real fix is bounding parse cost independent of the eventual `MAX_COMPLEXITY`/`MAX_OPS` checks that currently only apply post-parse.

### Proof of Concept
Not concretely constructed. A conceptual PoC would be: post a unit defining an AA whose `getters`/message templates or a directly-triggered `data` field contains a short but maximally left/right-ambiguous formula string (e.g., long chains of un-parenthesized concatenation/arithmetic mixed with nested arrays/dictionaries near the maximum allowed string length) and measure `parseOscriptGrammar`/`formulaValidator.validate` CPU time before the `MAX_COMPLEXITY`/`MAX_OPS` rejection is reached. Confirming actual exponential (rather than merely polynomial-but-large) blow-up requires running `nearley`'s Earley parser against `formula/grammars/oscript.js` locally, which was not available in this analysis environment — this should be validated with a live Devin session before treating impact/likelihood as certain.

function validateFormula (formula, parserResults, context) {
	function searchNewlineRecursive (st) {
		if (_.isArray(st)) {
			for (var i = 0; i < st.length; i++) {
				searchNewlineRecursive(st[i])
			}
		} else if (st && _.isPlainObject(st)) {
			var keys = Object.keys(st)
			for (var i = 0; i < keys.length; i++) {
				searchNewlineRecursive(st[keys[i]])
			}
		} else if (_.isString(st) && st.includes('\n')) {
			throw new Error(`Error parsing formula starting at line ${context.line} col ${context.col}: newline is not allowed in string '${st}'`)
		}
	}

	if (!_.isArray(parserResults)) {
		throw new Error(`Error parsing formula starting at line ${context.line} col ${context.col}`)
	} else if (parserResults.length !== 1) {
		throw new Error(`Error parsing formula starting at line ${context.line} col ${context.col}: ambiguous parser result`)
	} else {
		searchNewlineRecursive(parserResults[0])
	}
}
