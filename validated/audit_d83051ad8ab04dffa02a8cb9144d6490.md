### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` match - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` applies an incoming GitHub `status` webhook payload to **every** `Commit` record in the entire database whose `sha` matches, without checking whether that commit belongs to the repository/stack that authored the webhook. Since `Commit#state`/`success?`/`failure?` (delegated to `Status`/`Commit`) directly feed `MergeRequest#any_status_checks_failed?` and `#any_status_checks_missing?` via `StatusChecker`, a status event that is legitimately signed for repository/stack B can flip the state of a same-sha commit belonging to stack A, letting `reject_unless_mergeable!` skip a rejection it should perform for A's queued merge request.

### Finding Description
The claimed binding is: `repository_that_authored(new_status) == repository_whose_merge_queue(consumes new_status)`.

Tracing the code shows this binding is **not enforced**: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never consults `params.name`/`params.repository` (the GitHub payload field identifying the source repo, present in the fixture at `test/fixtures/payloads/status_master.json:4`) nor scopes the query to a `stack`/`repository` derived from the payload. Every other handler family (e.g. `pull_request/*_handler.rb`) explicitly resolves a `repository`/`stack` before acting, but `StatusHandler` does not.

`Commit` rows are per-stack (`belongs_to :stack`, `by_sha`/`by_sha!` also query globally without stack scoping, `app/models/shipit/commit.rb:92-103`), so the same git `sha` can legitimately exist as separate `Commit` rows under different stacks — this occurs naturally when a stack's repository shares history with another Shipit-tracked repository (forks, mirrors, template repos) since git commit hashes are content-addressed and identical for shared history.

`Commit#state` and the boolean predicates (`success?`, `failure?`, etc., referenced in `test/models/commits_test.rb:671-712`) are computed from `statuses`/`check_runs` attached to that specific `Commit` row. `MergeRequest#any_status_checks_failed?`/`#any_status_checks_missing?` (`app/models/shipit/merge_request.rb:199-206`) build a `StatusChecker` from `head.statuses_and_check_runs`, so a `Status` row created on the wrong `Commit` row directly changes what these predicates report, and thus what `reject_unless_mergeable!` (`app/models/shipit/merge_request.rb:155-162`) decides.

Exploit flow: attacker controls/authors a repository (e.g., a fork sharing commit history with the victim stack's repository) that is also monitored by Shipit (its own stack or GitHub App installation). When GitHub legitimately delivers a correctly-signed `status` webhook for that attacker-controlled repository — for a commit sha that is shared with the victim's queued merge request head — `WebhooksController#verify_signature` passes normally (it is a genuinely signed event for the attacker's own repo/org), but `StatusHandler#process` then also applies that status to the victim's `Commit` row for the same sha in a completely different stack, because the query is unscoped by repository.

Existing guards do not stop this: `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only authenticates *which organization/app* sent the webhook, not *which Commit rows the payload is allowed to mutate*; `drop_unhandled_event` and `ExplicitParameters` (`params.sha`, `params.state`, etc.) validate the shape of the payload, not its scope; there is no `Repository`/`Stack` check inside `StatusHandler`.

### Impact Explanation
A status/CI result legitimately generated for one repository can mutate the `Commit`/`Status` state consumed by `MergeRequest#reject_unless_mergeable!` for a completely unrelated stack, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." Concretely, a rejected merge request with `rejection_reason == 'ci_failing'` can be kept alive (not re-rejected) by a same-sha status event that did not originate from the repository/stack owning that merge request, allowing an unauthorized/queued PR to reach `all_status_checks_passed?` and eventually be auto-merged by `ProcessMergeRequestsJob`. This is repeatable against any pair of Shipit-tracked stacks that share commit history (e.g., forks of the same upstream), since `Commit.where(sha:)` performs no per-repository scoping.

### Likelihood Explanation
Exploitation requires: (1) a Shipit-tracked victim stack with a queued/rejected merge request whose head sha is shared with a second Shipit-tracked repository the attacker can act on (fork lineage, mirrored repo, or duplicate history), and (2) the ability to trigger or forge a genuinely-signed `status` webhook for that second repository (e.g., via GitHub CI naturally posting to a fork the attacker owns, or an attacker-controlled repo already onboarded as a Shipit stack). No Shipit secrets are required because the webhook signature is valid for the attacker's own repository/organization — only the cross-tenant sha-matching logic is broken. The main precondition (two tracked repositories sharing commit history) is common in real-world fork-based/mirror deployments of Shipit, making this feasible without any secret compromise.

### Recommendation
Scope `StatusHandler#process` (and `Commit.by_sha`/`by_sha!`) to the repository/stack that actually authored the webhook: resolve the target `Stack`/`Repository` from `params.name` or `params.repository.full_name` (as done via `repository_owner` in the controller) and restrict `Commit.where(sha: params.sha, stack: stacks_for_repository)` before calling `create_status_from_github!`, rejecting/ignoring updates for commits owned by stacks whose repository does not match the payload's repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new)
test "status handler does not update commits belonging to a different repository/stack" do
  victim_stack = shipit_stacks(:shipit)                     # repo: shopify/shipit-engine
  attacker_stack = shipit_stacks(:cyclimse)                 # different repository, shares sha via fixture setup
  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  merge_request = victim_stack.merge_requests.create!(number: 99, head: victim_commit, ...)
  merge_request.head.statuses.create!(stack: victim_stack, state: 'failure', context: 'ci/circle')
  assert merge_request.reject_unless_mergeable!
  assert_equal 'ci_failing', merge_request.reload.rejection_reason

  # Forged/attacker-originated but genuinely-signed payload for attacker's own repo, same sha
  params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: 'success', context: 'ci/circle', description: nil,
    target_url: nil, created_at: Time.now.iso8601, branches: []
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.process(params)

  # BUG: victim commit/state changed by an event that did not belong to victim's repository
  assert_predicate victim_commit.reload, :success?
  refute merge_request.reject_unless_mergeable!  # should still reject 'ci_failing' but no longer does
end
```
This demonstrates that `Commit.where(sha: params.sha)` in `StatusHandler#process` updates `victim_commit` even though the forged/attacker status event was scoped to a different repository, flipping `MergeRequest#reject_unless_mergeable!` from rejecting to not rejecting.
