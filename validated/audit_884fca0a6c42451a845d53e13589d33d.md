The `ERC20Transactor` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and `pallet_revive`'s `impl_fungibles.rs` bridge arbitrary ERC20 contracts (deployed by any user via `pallet-revive`) into XCM's asset-transfer model, and both assume the ERC20 `transfer()` call moving `amount` results in exactly `amount` being credited — exactly the assumption the original report flags as unsafe for fee-on-transfer tokens.

### Title
XCM/Revive ERC20 asset transactor credits/burns nominal `amount` without verifying actual balance delta, unsafe for fee-on-transfer ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the target contract's `IERC20::transfer`, and on a `true` return simply mint an `AssetsInHolding` credit equal to the requested `amount` [1](#0-0) , without checking the actual balance change of the checking account or the beneficiary. `pallet_revive::impl_fungibles::Mutate::burn_from`/`mint_into` show the same pattern: on `is_success == true` they report `<Self as Inspect<_>>::balance(asset_id, who)` after the call, but the bookkeeping XCM/pallet-assets bridging code that turns Solidity ERC20 contracts into `fungibles::Inspect`/`Mutate` for XCM never asserts that the delta equals the requested amount [2](#0-1) .

### Finding Description
Any signed user can deploy an arbitrary Solidity contract via `pallet-revive` (`bare_instantiate`) and register/use it as an ERC20 for XCM transfers, as demonstrated in the runtime's own integration tests that deploy `MyToken`/`MyTokenFake`/`MyTokenExpensive` contracts and immediately transfer them through `PolkadotXcm::execute` withdraw/deposit-asset flows [3](#0-2) . This is the "enabled contract deploy/call" + "permitted XCM execute" entry point required by the scan.

`ERC20Transactor::withdraw_asset_with_surplus` withdraws `amount` from the user by calling `IERC20::transfer(checking_account, amount)` on the arbitrary contract, and on success it constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` [4](#0-3) . `deposit_asset_with_surplus` mirrors this on the deposit side, transferring from the checking account to the beneficiary and trusting the boolean return [5](#0-4) . In both cases the code only checks that the contract call did not revert and that the ABI-decoded return value is `true`; it never re-reads `balanceOf` before/after to confirm that exactly `amount` moved. This is precisely the check the external report says is missing for fee-on-transfer ERC20 tokens.

Because the deployed contract is fully attacker-controlled Solidity code, it can implement `transfer()` to (a) return `true` while moving less than `amount` (fee-on-transfer / deflationary logic), or (b) move more/less to a different account than expected. Since the XCM holding register is credited with the nominal `amount` regardless of the true balance movement, the XCM executor's internal accounting (holding register, `AssetsInHolding`, subsequent `DepositAsset`) can diverge from the real on-chain ERC20 balances. Symmetrically, `pallet_revive::impl_fungibles::Mutate::mint_into`/`burn_from` (used by `xcm_builder::FungiblesAdapter`) accept the ERC20's self-reported success and re-query `balance()` after the call rather than asserting the delta matches `amount` [6](#0-5) .

### Impact Explanation
If a fee-on-transfer (or otherwise non-standard) ERC20 is used as the XCM-transactable asset, the XCM holding register can be credited for more than the checking/beneficiary account actually received, or a withdraw can debit the user for `amount` while the checking account effectively received less. This breaks the 1:1 accounting invariant that the XCM executor depends on for `WithdrawAsset`/`DepositAsset` correctness, and can allow users of such tokens to receive assets they did not actually deposit, or other users interacting with the same checking account/pooled reserve to experience shortfalls, mirroring "Assets with transaction fees will result in losses for users."

However, this is scoped strictly to whichever ERC20 asset is configured/matched by `Matcher` for this transactor; it does not affect native `Balances`/`pallet-assets` since those are ledger-based (no fee-on-transfer possible) as confirmed by `pallet-assets`'s dust-sweep semantics, which only ever *increase* the transferred amount to zero out sub-ED remainders and never decrease it [7](#0-6) . I could not confirm from the index whether `ERC20Transactor`/this ERC20-fungibles bridge is actually wired into a live AssetHub XCM configuration as a general-purpose "any ERC20" transactor versus a fixed allow-list of vetted contracts; the tests instantiate arbitrary user-supplied bytecode, but I was unable to verify the production `Matcher`/asset registration policy (e.g., whether arbitrary ERC20 contract addresses are permissionlessly registrable as XCM-transactable assets on a real Parity-operated chain) within the available index. This materially affects severity and bounty eligibility and would need to be confirmed via the full runtime configuration, which is outside the indexed scope.

### Likelihood Explanation
Likelihood depends entirely on whether arbitrary/unvetted ERC20 contracts can be registered as XCM-transactable assets in a live deployment. If registration is permissionless (any deployed contract address becomes usable per `Matcher`), likelihood is high since deploying a fee-on-transfer token via `pallet-revive` requires no privileged role. If asset registration is gated (e.g. governance/sudo allow-list of specific vetted tokens), likelihood is low since this would require a privileged actor to onboard a malicious/misbehaving token, which is out of scope per the report's constraints (no privileged prerequisites allowed).

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, and in `pallet_revive::impl_fungibles::Mutate::{burn_from,mint_into}`, read the relevant account's `balanceOf` immediately before and after the `IERC20::transfer` call and use the observed delta (not the requested `amount`) to construct the `AssetsInHolding` credit / to determine `WithdrawConsequence`/return balance. Reject the operation (or credit only the actual delta) if it diverges from `amount`.
