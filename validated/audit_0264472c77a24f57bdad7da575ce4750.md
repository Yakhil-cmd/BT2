## Title
GitHub organization used to select the webhook secret is not bound to the repository actually acted upon, allowing cross-repository event injection when any configured org has no webhook secret - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate a request against using `repository_owner`, a value read straight out of the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). The push/status/check_suite handlers, however, act on the repository identified by other fields of that same body (e.g. `repository.full_name`), and `GithubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for the selected organization. This creates exactly the kind of "authenticated entity vs. entity acted upon" mismatch the Velodrome bug class describes: the org whose credential authenticates the request is not cryptographically bound to the repository/stack that ends up being mutated.

### Finding Description
`WebhooksController` has a single unauthenticated public endpoint (`POST /webhooks`, `config/routes.rb`) that dispatches on the raw JSON body: [1](#0-0) 

Signature verification picks the app config using a field that comes straight from the (unsigned-at-this-point) body: [2](#0-1) [3](#0-2) 

`repository_owner` is only used to pick *which* `GithubApp` instance (i.e. which `webhook_secret`) validates the request; it is not otherwise used to constrain which repository/stack the payload can affect. The handlers that actually process events resolve the target stack/repository from other fields in the same body (e.g. `repository.full_name`) — fields the attacker also fully controls.

Critically, `verify_webhook_signature` treats an unconfigured secret as automatically valid: [4](#0-3) 

The setup docs confirm `webhook_secret` is optional: [5](#0-4) 

Combining these: if *any* configured GitHub organization in `secrets.yml` (single or multi-org config, see `github_organizations`/`github_app_config`) has a blank/unset `webhook_secret`, an attacker can craft a POST to `/webhooks` with `repository.owner.login` (or `organization.login`) set to that unsecured org — making `verify_signature` pass unconditionally — while setting `repository.full_name` (and other payload fields consumed by the event handler) to reference a completely different, unrelated repository/stack that the attacker does not control and for which they have no legitimate webhook secret at all. [6](#0-5) 

This is the same class of bug as the report: `Bribe.setGauge` bound trust to "whoever calls first" rather than to the `Gauge` constructor's actual caller; here, signature verification is bound to "whichever org name appears in `repository.owner.login`" rather than to the repository the event handler will actually mutate.

### Impact Explanation
Successful exploitation lets an unauthenticated, unprivileged external attacker inject arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) against a victim stack/repository they do not own, as long as the Shipit instance has at least one configured GitHub org/app with no `webhook_secret` set. Depending on the handler this can:
- Force `GithubSyncJob` to sync/refresh a victim stack based on attacker-chosen `sha`/branch data (`push_handler.rb`).
- Inject fabricated commit `status`/`check_suite` results, potentially satisfying CI gating logic used by `MergeRequest`/deploy triggers for a victim repo (`status_handler.rb`, `check_suite_handler.rb`).
- Create/close fake `pull_request` webhook-driven review stacks or merge-queue actions.

This crosses a repository trust boundary without any credential for the targeted repository, matching the "cross-repository writes" / "unauthorized deploy" impact bar, since falsified CI status/check-suite events feed directly into whether Shipit considers a PR mergeable and can be auto-merged/deployed.

### Likelihood Explanation
Requires the operator to have configured at least one GitHub organization without a `webhook_secret` — which the documentation explicitly calls "optional" — a plausible real-world misconfiguration, especially in multi-org deployments (`test/dummy/config/secrets_double_github_app.yml` shows some orgs with `webhook_secret: # nil`). No authentication, GitHub App installation, or repository access is needed by the attacker; only knowledge of the unsecured org's login name, which is discoverable (Shipit UI/org settings pages are often public).

### Recommendation
- Reject webhook requests when the resolved app config has no `webhook_secret` configured, rather than treating a blank secret as automatically valid, or require all configured GitHub apps to have a secret.
- Cross-check that the organization used to select the signing secret (`repository.owner.login` / `organization.login`) matches the organization owning the repository actually referenced by the payload (`repository.full_name`) before dispatching to handlers.
- Consider deriving the target stack/repository strictly from a field that was itself covered by signature verification against the same org used to authenticate, rather than trusting two independently-attacker-controlled fields to agree.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `attacker-org` (no `webhook_secret`) and `victim-org` (has a repo/stack tracked by Shipit, e.g. `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`; because `attacker-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. `Shipit::Webhooks.for_event('push')` handler processes the payload using `repository.full_name`, enqueuing `GithubSyncJob` against `victim-org/victim-repo`'s stack — a repository the attacker never authenticated for.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
