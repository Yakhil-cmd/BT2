### Title
Webhook signature verification authenticates the payload's `repository.owner.login` but never binds it to `repository.full_name`, allowing cross-organization webhook forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a GitHub webhook against using the organization name embedded in the unverified JSON body, but the event handlers that subsequently mutate application state key off a *different* field of the same unverified body (`repository.full_name`). Because Shipit supports per-organization GitHub App configuration, each with its own `webhook_secret`, an attacker who legitimately controls one configured organization's webhook secret can forge a payload that verifies under their own org's key while claiming to describe a repository belonging to a completely different, unrelated organization tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` computes which `GitHubApp`/secret to use like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the still-unverified `params` (`params.dig('repository', 'owner', 'login')`), and is used only to pick which per-organization secret (`Shipit.github(organization: repository_owner)`) should verify the request via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Shipit explicitly supports configuring multiple independent GitHub Apps/organizations, each with its own `app_id`, `installation_id`, and `webhook_secret`: [4](#0-3) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire* raw JSON body — including all its fields — to the event handlers: [5](#0-4) 

Every handler resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name`, taken from that same unverified body: [6](#0-5) [7](#0-6) [8](#0-7) 

Nothing anywhere cross-checks that `repository.owner.login` (the field used to select the verifying secret) matches the owner implied by `repository.full_name` (the field used to select which Stack is actually written to). The HMAC only proves "this raw byte string was signed by whichever secret `repository_owner` pointed to" — it does not prove that the resource described inside that byte string (`repository.full_name`) actually belongs to that same organization.

This is exactly the reported bug class translated to this engine: a payload field (`repository.full_name`) is *acted upon* by the handlers but is never itself *covered by a verified binding* to the credential (webhook secret/organization) that authenticated the request. The binding that should hold — `verified_organization == written_repository_owner` — is never enforced.

### Impact Explanation
In a multi-organization Shipit deployment (the documented/supported configuration shape shown in `config/secrets.development.example.yml`), an attacker who is a legitimate administrator of Org A's GitHub App (and therefore knows Org A's `webhook_secret`) can:
1. Craft an arbitrary JSON webhook body with `repository.owner.login = "OrgA"` (so `repository_owner` resolves to the org whose secret they know) but `repository.full_name = "OrgB/target-repo"` (a repository belonging to a different, unrelated organization tracked by the same Shipit instance).
2. Sign the whole raw body with Org A's known `webhook_secret` and POST it to `/webhooks` with the appropriate `X-Github-Event` header.
3. `verify_signature` succeeds because it only checks the signature against Org A's secret.
4. The relevant handler (e.g. `PushHandler`, `StatusHandler`, or the `pull_request` handlers) then acts on `OrgB/target-repo`, e.g. triggering `stack.sync_github`, creating commit statuses, or creating/archiving review stacks for a stack the attacker has no legitimate authorization over.

This is a cross-repository/cross-organization write performed without holding the credential (webhook secret) for the organization actually being written to — it can trigger unauthorized syncs, statuses, or review-stack provisioning/deprovisioning cross-tenant, which can cascade into unauthorized deploys depending on how commit status / CI gating is used downstream. This satisfies the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
This requires the deployment to be configured for multiple GitHub organizations (an explicitly documented and supported configuration), and requires the attacker to legitimately control one of those configured organizations' GitHub App webhook secret while targeting another organization hosted on the same Shipit instance. This is a realistic scenario for any shared/multi-tenant Shipit installation, and requires no privileged Shipit account, `ApiClient` token, or repository write access on GitHub itself — only knowledge of one org's own webhook secret, which is by design available to that org's own administrators.

### Recommendation
Bind the field used for secret selection to the field used for resource resolution. Concretely, after choosing `github_app` via `repository_owner`, re-derive/validate that `params.dig('repository', 'full_name')` starts with `"#{repository_owner}/"` (or otherwise strictly matches the owner used for verification) before dispatching to handlers, and reject (422) any payload where they diverge. Alternatively, have handlers resolve the target `Repository`/`Stack` using the same owner value that was cryptographically verified rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Assume Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema), and `OrgB/target-repo` has an active Shipit `Stack`.
2. Attacker is a legitimate GitHub App admin for `OrgA` and thus knows `OrgA`'s `webhook_secret`.
3. Attacker builds a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/target-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. Attacker computes `sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and sends `POST /webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=...`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature with the attacker-known `OrgA` secret.
6. `PushHandler` resolves the target stack via `Repository.from_github_repo_name("OrgB/target-repo")` (per `app/models/shipit/webhooks/handlers/handler.rb`, lines 32-38) and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack — a write the attacker never had verified authority over.

Note: This analysis is based on static review of the controller/handler code and documented multi-org configuration support; I could not execute the flow end-to-end (no filesystem/terminal access), so runtime confirmation (e.g., exact downstream effects of `sync_github` in this exact repo revision) would need to be validated in a live/test environment.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
