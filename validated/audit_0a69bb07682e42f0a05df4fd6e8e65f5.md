### Title
Unauthenticated `X-Shipit-User` header lets any API-token holder impersonate an arbitrary Shipit `User` as the actor of deploys, rollbacks, locks and task triggers - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The `RewardsDistributor::triggerRoot` bug class is: a state-changing operation trusts a value that looks authoritative but is never actually re-verified against the real source of truth for that specific call, letting an unprivileged caller substitute their own value for the intended one. In `shipit-engine`, the API layer has the same shape of defect: `current_user` for all API actions (deploy, rollback, lock, task trigger/abort) is derived from a client-supplied `X-Shipit-User` HTTP header rather than from any authenticated identity, breaking the binding "GitHub identity that authenticated ⇔ `User` object attributed to the action."

### Finding Description
Shipit's session-based UI properly binds `current_user` to a GitHub OAuth login stored in `session[:user_id]`: [1](#0-0) 

But the API controllers (used by `ApiClient` bearer tokens) resolve `current_user` completely differently — by trusting an unauthenticated request header: [2](#0-1) 

`authenticate_api_client` only verifies the `ApiClient` bearer token (via `BasicAuth`/`ApiClient.authenticate`); it never associates that token with a specific `User`: [3](#0-2) 

`identify_user` then does a case-insensitive lookup of **any** login supplied in `X-Shipit-User` and returns that `User` record with no signature, no proof of GitHub identity, and no relationship check to the `ApiClient` making the request: [4](#0-3) 

This `current_user` is then used as the authoritative actor for privileged, audited actions:
- Triggering a deploy: `stack.trigger_deploy(commit, current_user, ...)` [5](#0-4) 
- Triggering a rollback / aborting an active task on someone's behalf: `active_task.abort!(aborted_by: current_user, ...)` and `deploy.trigger_rollback(current_user, ...)` [6](#0-5) 
- Triggering/aborting tasks: `stack.trigger_task(params[:task_name], current_user, ...)`, `task.abort!(aborted_by: current_user)` [7](#0-6) 
- Locking a stack: `stack.lock(params.reason, current_user)` [8](#0-7) 

The equality that should hold is: `User bound to the request == GitHub identity that was actually authenticated for this request`. Instead, the engine enforces only: `ApiClient token is valid`, and separately accepts `User := lookup(X-Shipit-User header)` with zero cryptographic or session binding between the two. Any caller holding a valid `ApiClient` token — even one issued for a low-trust integration limited to `deploy:stack` — can set `X-Shipit-User: <any-existing-login>` and have all resulting audit trails, lock authorship, and deploy/rollback authorship attributed to that arbitrary user, including admins or users with elevated GitHub team membership. Because `stack.lock`/`stack.unlock`/`trigger_deploy`/`trigger_rollback` are the actions that change deployability state (analogous to `root.value`/`root.lastUpdatedAt` in the report), an attacker with a merely `deploy:stack`-scoped token can spoof authorship of a deploy or lock/unlock action as a trusted human user, and can also unlock/relock stacks in the name of another user without ever authenticating as them.

### Impact Explanation
This crosses the credential/authentication boundary explicitly called out in scope: "GitHub identity versus the `User` bound to the session." An attacker possessing any valid `ApiClient` token (which does not require repository write access or a privileged GitHub account — API tokens are provisioned separately, e.g., via `CCMenuUrlController`, and can be scoped narrowly) can:
- Trigger unauthorized deploys/rollbacks/task runs while attributing them to another (potentially more trusted) `User`, undermining audit logs used for accountability and approval workflows.
- Lock/unlock stacks (bypassing the "who locked it" trust signal) enabling an unauthorized ship after impersonating the locking/unlocking user.

This matches the "unauthorized deploy, rollback" Critical-impact category, since the actual gating checks (`stack.locked?`, permission scope) are enforced against the `ApiClient`, but the recorded/human-facing responsibility and any downstream logic keyed off `current_user` identity is fully attacker-controlled.

### Likelihood Explanation
High. No special access is required beyond possessing a valid, even minimally-scoped `ApiClient` token — no GitHub session, no repository write access, no admin privileges. The `X-Shipit-User` header is a documented, ordinary HTTP header, not a signed or otherwise protected credential.

### Recommendation
Bind `current_user` for API requests to the `ApiClient`'s own `creator` (already tracked via `belongs_to :creator, class_name: 'User'`) rather than trusting a client-supplied header, or require a signed assertion (e.g., re-verify via GitHub token) before honoring `X-Shipit-User`. At minimum, restrict use of `X-Shipit-User` to the `UnlimitedApiClient`/internal trusted-service context and never accept it from externally-issued `ApiClient` tokens.

### Proof of Concept
1. Obtain any valid `ApiClient` bearer token scoped only to `deploy:stack` (e.g., via `CCMenuUrlController#fetch`, or any token issued to a low-trust integration): [9](#0-8) 
2. Send: `POST /api/stacks/:owner/:repo/:env/deploys` with header `X-Shipit-User: <victim-admin-login>` and `Authorization: Basic <base64(token)>`.
3. `identify_user` resolves `current_user` to the victim's `User` record purely from the header [4](#0-3) , and `DeploysController#create` records the deploy as triggered by the victim: [5](#0-4) 
4. Repeat with `LocksController#create`/`#destroy` to lock/unlock the stack "as" the victim, or with `TasksController#abort` to abort another user's running deploy while attributing the abort to a different `User`.

```ruby
      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
```
