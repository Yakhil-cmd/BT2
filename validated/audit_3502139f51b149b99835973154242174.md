### Title
Cross-organization CI status forgery via webhook signature/target-repository mismatch in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) is used to validate an inbound webhook's HMAC signature based on `repository.owner.login` (or `organization.login`) taken from the *same untrusted request body* it is about to validate. Once the signature check passes, every downstream `Webhooks::Handlers::Handler` subclass resolves the *actual target repository/stack* from a different field of that same body: `repository.full_name`. Because these two fields are never cross-checked against each other, a party that legitimately controls one onboarded GitHub organization's webhook secret can forge a signature that Shipit accepts as "verified for OrgA" while pointing the payload's `repository.full_name` at a stack belonging to a completely different onboarded organization (OrgB), whose commits/CI status/etc. get written by the handler.

### Finding Description
`Shipit.github(organization: repository_owner)` in `verify_signature` picks the `GitHubApp` config to validate the signature against, using:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple, independently-configured GitHub Apps (and independent `webhook_secret`s) for different organizations within a single Shipit instance — this is a documented feature (`docs/setup.md`, "Using Multiple Github Applications", and `test/dummy/config/secrets_double_github_app.yml` fixtures showing `OrgOne`/`OrgTwo` each with their own `webhook_secret`).

Once `verify_webhook_signature` succeeds using OrgA's own webhook secret (a secret the OrgA administrator legitimately possesses because they configured their own GitHub App), the request is dispatched to handlers:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`repository.owner.login` (used for signature-org selection) and `repository.full_name` (used to resolve the actual `Stack`/`Repository`/`Commit` that gets mutated) are independent fields in the same attacker-controlled JSON body — nothing binds them together. An attacker who administers OrgA's own GitHub App (and thus knows OrgA's `webhook_secret`, which they configured themselves) can:
1. Set `repository.owner.login` = `"OrgA"` so `verify_signature` selects OrgA's `GitHubApp` and correctly HMACs the raw body with the secret they know.
2. Set `repository.full_name` = `"OrgB/some-repo"` — a repository belonging to a different tenant organization (OrgB) hosted on the same shared Shipit instance, which the attacker does not control.

For the `status` event, `StatusHandler#process` writes directly into the database using unvalidated payload fields for whatever commit SHA matches, regardless of which organization actually owns it:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
This creates a `Status` row (`state`, `description`, `target_url`, `context`) on OrgB's commit that Shipit will treat as a real CI signal — even though it was never actually verified by OrgA's secret against OrgB's data, only against the attacker's own OrgA secret.

This breaks the binding: **"the organization whose secret authenticated the request" ≠ "the organization/repository whose data is written."** It is directly analogous to the reported `SwiftSource::unlockCompressedBatch` bug class, where a field trusted for one purpose (the action check verifying `COMPRESSED_UNLOCK`) was not actually bound to the data that got processed (the `msgHash`/payload offset used downstream), letting attacker-controlled data escape the intended verification scope.

### Impact Explanation
`Status` records directly influence whether a commit is `deployable?` (CI gating) and drive `enable_ci_on_stack`, `schedule_continuous_delivery`, and `ProcessMergeRequestsJob` (auto-merge queue processing) for the target stack. An attacker who is merely an administrator of their own onboarded GitHub organization (OrgA) — with no Shipit session, no `ApiClient` token, and no access to OrgB's actual `webhook_secret` — can forge passing/failing CI statuses on commits belonging to an unrelated organization (OrgB) sharing the same Shipit instance. This can be used to force a false "success" status that satisfies `required_statuses`/`merge_request_required_statuses`, enabling continuous-deployment auto-merges or unblocking manual deploys in Shipit for a repository the attacker does not control — an unauthorized deploy/merge condition, and this satisfies the High-impact bar ("escalation... unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires a Shipit instance configured with the documented multi-organization GitHub App setup (`github:` keyed by organization names, each with its own `webhook_secret`), which Shipit itself documents and ships test fixtures for as a first-class supported configuration. Any organization onboarded onto such a shared instance is, by design, a mutually-distrusting tenant from a security perspective (each org's own admins control their own GitHub App/webhook secret and can trigger inbound webhook POSTs at will, since GitHub webhook endpoints are public). No privileged Shipit account, GitHub App private key, or victim-org secret is required — only knowledge of the attacker's *own* org's webhook secret, which they inherently possess. This is a realistic, low-effort path once the documented multi-org feature is in use.

### Recommendation
Bind the field used for signature-secret selection to the field used for target-repository resolution: after selecting the `GitHubApp` via `repository_owner` and verifying the signature, re-derive the acted-upon repository strictly from `repository.owner.login` + `repository.name` (not an independently-supplied `repository.full_name`), or explicitly assert that `repository.full_name` starts with `"#{repository_owner}/"` before dispatching to handlers. Reject the webhook if the two disagree.

### Proof of Concept
Assume a Shipit instance configured with two onboarded orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org setup). Attacker administers `OrgA` and knows `OrgA`'s `webhook_secret`.

1. Craft a `status` event JSON body:
```json
{
  "sha": "<sha-of-a-commit-belonging-to-OrgB's-stack>",
  "state": "success",
  "context": "ci/travis",
  "description": "forged",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
2. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` — computable by the attacker since they own `OrgA`'s secret.
3. POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")`, HMAC matches, request is accepted.
5. `StatusHandler#process` looks up `Commit.where(sha: ...)` — matching the commit in `OrgB`'s stack — and creates a forged `Status` record on it, despite the signature never having been validated against `OrgB`'s actual secret.

Note: full end-to-end confirmation that a forged `success` status alone is sufficient to trigger an actual merge/deploy in `OrgB`'s stack depends on that stack's specific `shipit.yml` (`ci.require`, `continuous_deployment`) configuration, which was not directly inspected here; the write of the forged, unauthenticated-for-that-org `Status` row itself is confirmed directly from the cited code.
