### Title
Front-runnable signer-key authorization allows an attacker to consume another stacker's signature and brick their `stack-stx`/`stack-extend`/`stack-increase` call - (File: `stackslib/src/chainstate/stacks/boot/pox-4.clar`)

### Summary
`pox-4.clar`'s signer-key authorization scheme (`get-signer-key-message-hash`, `verify-signer-key-sig`, `consume-signer-key-authorization`) signs over `{pox-addr, reward-cycle, topic, period, auth-id, max-amount}` but never binds the signature to the calling `tx-sender` or to the exact `amount` being locked. Because the `(auth-id, signer-key, reward-cycle, topic, period, pox-addr, max-amount)` tuple is a single-use global key (enforced only via `map-insert` into `used-signer-key-authorizations`), any party who observes a broadcast `signer-sig` in the mempool can resubmit it under their own transaction and permanently consume the authorization before the intended stacker's transaction is mined — exactly analogous to the AutoRoller report's "create a colliding unique resource first to brick the legitimate caller" pattern (there: `SpaceFactory.create(adapter, maturity)`; here: `used-signer-key-authorizations` map-insert).

### Finding Description
The signer authorization message hash is computed as: [1](#0-0) 

It commits to `pox-addr`, `reward-cycle`, `topic`, `period`, `auth-id`, and `max-amount` — but not to `tx-sender` (the stacker who will actually lock STX) nor to the exact `amount` (only that `amount <= max-amount` is checked at call time, outside the signature): [2](#0-1) 

`consume-signer-key-authorization` then marks the tuple as globally used via `map-insert`, which fails (and reverts the whole transaction, including STX locking) if it is already present: [3](#0-2) 

This authorization gate is used, unmodified, in `stack-stx`, `stack-extend`, `stack-increase`, `inner-stack-aggregation-commit`, and `stack-aggregation-increase`: [4](#0-3) [5](#0-4) 

Because a signed `signer-sig` blob is transmitted in a plain, unencrypted transaction (visible in the mempool before it is confirmed), any observer can extract `(pox-addr, reward-cycle, topic, period, max-amount, auth-id, signer-key, signer-sig)` from the pending transaction and submit their own competing transaction to the same public function (e.g., `stack-stx`) using an amount of their own choosing (any value ≤ `max-amount`) and their own `tx-sender`. If this front-running transaction is mined first, `map-insert` on `used-signer-key-authorizations` succeeds for the attacker and the legitimate stacker's later transaction now fails permanently with `ERR_SIGNER_AUTH_USED`, because `auth-id` reuse is forbidden by design (`;; auth-id is a random uint to prevent authorization replays`).

The equality broken: the signer intended their delegated signing capacity/authorization to be consumed exactly once, by the specific stacker for whom the off-chain authorization was produced. Because `tx-sender`/stacker identity is not part of the signed payload, the contract cannot enforce "this specific stacker's stacking action was authorized by the signer" — an unrelated party can consume the authorization for a completely different stacking action (their own STX, their own pox-addr eligibility check bound to the same `pox-addr`), which is "a stacking action the staker/signer never authorised" per the impact rules, while permanently denying the legitimately-intended stacker the reward-cycle window they were relying on (their STX cannot be locked at all for that cycle since it requires a *new* signature/auth-id and the reward-cycle deadline for that authorization may have already passed) — a temporary freezing of the intended lock opportunity, directly mirroring the AutoRoller brick where a `maturity` collision permanently blocks the intended series creation.

### Impact Explanation
This matches the High-severity bucket: "temporary freezing of staked funds" / "an unsigned stacking action." A griefing attacker (who need not even be a stacker themselves, or who stakes a trivial amount) can:
1. Deny a legitimate stacker's `stack-stx`/`stack-extend`/`stack-increase` call for an entire reward cycle by consuming their `auth-id` first, forcing them to miss the reward-cycle window (since `stack-stx`'s `start-burn-ht` must equal the very next cycle — a missed window cannot simply be retried in the same cycle).
2. This is systematically repeatable against any signer/stacker pair whose signature is observed in the mempool, since nothing about the scheme prevents it (no nonce tied to sender, no commitment to sender in the signed payload).

The attack does not require the bond/pause admin, a miner, or another user's private key — it only requires observing a public mempool transaction and being faster to get included, which is a realistic capability for any well-resourced adversary (including via transaction-fee bidding), consistent with the AutoRoller report's threat model of "an adversary can brick [X] by pre-empting a uniquely-keyed resource."

### Likelihood Explanation
Likelihood is high in economic terms: any stacker/signer authorization broadcast to the network is visible pre-confirmation, and Stacks (like most blockchains) allows fee-based transaction reordering/front-running. Any party motivated to disrupt a specific stacker or pool operator (e.g. a competing pool, or a stacker excluded from a signer's preferred slot) can perform this at low cost — they only need to pay for one transaction with a valid but attacker-chosen `amount ≤ max-amount`, `pox-addr` equal to the target's, and their own account with sufficient balance to be a plausible participant. No cryptographic secret needs to be broken since the signature itself is copied verbatim.

### Recommendation
Bind the signature to the intended stacker: include `tx-sender` (or an explicit `stacker` principal argument that is checked against `tx-sender`) and, ideally, the exact `amount` (not just `max-amount`), inside `get-signer-key-message-hash`'s structured-data payload. This prevents a copied signature from being redeemed by any principal other than the one for whom the signer intended to authorize.

### Proof of Concept
1. Signer S signs an authorization off-chain for the exact tuple `(pox-addr=P, reward-cycle=R, topic="stack-stx", period=1, max-amount=M, auth-id=A)`, intending it for Stacker X's upcoming `stack-stx(amount-ustx=M, pox-addr=P, start-burn-ht=H, lock-period=1, signer-sig=SIG, signer-key=S, max-amount=M, auth-id=A)` call.
2. Stacker X broadcasts this transaction; it sits in the mempool momentarily before confirmation.
3. Attacker Y observes the mempool, extracts `(P, R, SIG, S, M, A)`, and submits their own `stack-stx(amount-ustx=1, pox-addr=P, start-burn-ht=H, lock-period=1, signer-sig=SIG, signer-key=S, max-amount=M, auth-id=A)` with a higher fee.
4. Attacker Y's transaction is mined first: `verify-signer-key-sig` passes (signature checks only pox-addr/reward-cycle/topic/period/auth-id/max-amount, none of which depend on `tx-sender`), and `consume-signer-key-authorization` succeeds, inserting the tuple into `used-signer-key-authorizations` under Y's transaction. Attacker Y's own (possibly tiny) STX gets locked under signer S's key/pox-addr.
5. Stacker X's original transaction (with the same `signer-sig`/`auth-id`) is mined next; `map-insert` at pox-4.clar lines 785-787 fails since the key already exists, and `stack-stx` reverts with `ERR_SIGNER_AUTH_USED`. Stacker X's intended STX is not locked for reward cycle R, and the specific authorization (auth-id A) can never be used again — they must obtain an entirely new signature/auth-id from S and wait for a future reward cycle to attempt again.                           (pox-addr (tuple (version (buff 1)) (hashbytes (buff 32))))
                          (start-burn-ht uint)
                          (lock-period uint)
                          (signer-sig (optional (buff 65)))

                          (max-amount uint)

    ;; this stacker's first reward cycle is the _next_ reward cycle

          (specified-reward-cycle (+ u1 (burn-height-to-reward-cycle start-burn-ht))))
      ;; the start-burn-ht must result in the next reward cycle, do not allow stackers

(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
  (begin
    ;; verify the authorization
    (try! (verify-signer-key-sig pox-addr reward-cycle topic period signer-sig-opt signer-key amount max-amount auth-id))
    ;; update the `used-signer-key-authorizations` map
    (asserts! (map-insert used-signer-key-authorizations
      { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount } true)
      (err ERR_SIGNER_AUTH_USED))
    (ok true)))

  (increase-by uint)
  (signer-sig (optional (buff 65)))
  (signer-key (buff 33))
  (max-amount uint)
  (auth-id uint))
   (let ((stacker-info (stx-account tx-sender))

         (amount-unlocked (get unlocked stacker-info))
         (unlock-height (get unlock-height stacker-info))
         (cur-cycle (current-pox-reward-cycle))
         (first-increased-cycle (+ cur-cycle u1))

                                          { stacker: tx-sender })
                                          (err ERR_STACK_INCREASE_NOT_LOCKED)))
         (cur-pox-addr (get pox-addr stacker-state))
         (cur-period (get lock-period stacker-state)))
      ;; tx-sender must be currently locked
      (asserts! (> amount-stacked u0)
                (err ERR_STACK_INCREASE_NOT_LOCKED))
