### Title
Unverified Third-Party Correspondent Injection via Multisig Wallet Offer — Pre-Trust Device Linkage - (File: wallet_defined_by_keys.js / device.js)

### Summary
When a device receives a `create_new_wallet` offer for a multisig wallet, the handler (`wallet_defined_by_keys.js`) passes an attacker-influenced `arrOtherCosigners` list to `device.addIndirectCorrespondents()` [1](#0-0) , which blindly `INSERT`s each claimed `{device_address, hub, pubkey, name}` tuple into `correspondent_devices` without verifying that `device_address` is actually derived from the supplied `pubkey` (unlike `addUnconfirmedCorrespondent`, which computes `device_address = objectHash.getDeviceAddress(device_pubkey)` before inserting) [2](#0-1) . This is structurally analogous to the 4gaBoards flaw: an untrusted party supplies an identity claim (there, an email; here, a device_address/pubkey/hub tuple) that gets silently linked into a trust table used for subsequent authenticated-looking interactions, without independent proof that the claimant actually controls that identity.

### Finding Description
`addIndirectCorrespondents(arrOtherCosigners, onDone)` iterates the cosigner list and does:
```
INSERT OR IGNORE INTO correspondent_devices (device_address, hub, name, pubkey, is_indirect) VALUES(?,?,?,?,1)
``` [1](#0-0) 
There is no check that `objectHash.getDeviceAddress(pubkey) === device_address`, in contrast to the vetted path used in `addUnconfirmedCorrespondent` [2](#0-1) . `arrOtherCosigners` originates from a `create_new_wallet` offer sent by a peer device during multisig-wallet setup (`wallet_defined_by_keys.js`, `createWallet`/offer handling, lines 233–258) [3](#0-2) ; the initiator of a shared/multisig wallet controls the contents of this array and can name arbitrary third-party device addresses, hubs, and pubkeys as "other cosigners" of the wallet being offered.

Once inserted, the `correspondent_devices` row becomes a recognized entity in tables that drive both correspondent-based UI trust and financial routing: `readCorrespondentsByDeviceAddresses`, `readAllControlAddresses` (`wallet_defined_by_addresses.js`, lines 545–561) [4](#0-3) , and private-chain forwarding logic that joins on `correspondent_devices` to determine where to forward private payment chains for a shared address, e.g. `forwardPrivateChainsToOtherMembersOfAddresses` (`wallet_defined_by_addresses.js`, lines 531–543) [5](#0-4)  and the equivalent in `wallet_defined_by_keys.js` lines 841–861 [6](#0-5) . These queries `JOIN correspondent_devices USING(device_address)` without checking `is_confirmed`, so a fabricated/injected row is functionally indistinguishable from a legitimately paired one for the purpose of routing private outputs (payload, amount, blinding, addresses) of a shared address the attacker is (or claims to be) a member of.

This mirrors the reported bug class: a lower-trust identity linkage (attacker-supplied claim of "this device_address belongs to this pubkey/hub") is persisted into a table consulted later as if it had been verified, letting the attacker (or an entity impersonating a victim's device_address) receive private financial data intended for a real cosigner, without ever proving control of the claimed device key.

### Impact Explanation
If exploited, a malicious wallet-creation offer could seed `correspondent_devices` with attacker-controlled `hub`/`pubkey` values bound to a `device_address` string chosen to collide with, or be substituted for, a legitimate cosigner. Subsequent `forwardPrivateChainsToOtherMembersOfAddresses`/`forwardPrivateChainsToDevices` calls would then route private payment chain data (outputs, addresses, blinding factors, spend proofs) for a shared address to the attacker's hub/device instead of (or in addition to) the intended cosigner, and could poison a victim's correspondent list to intercept or spoof further off-chain wallet coordination messages (`sign`, `new_shared_address`, xpubkey exchange) for that shared/multisig address — a private-payment-chain confidentiality/fund-coordination compromise reachable purely by sending a device message as an unprivileged wallet-creation counterparty.

### Likelihood Explanation
Reaching this path only requires being a counterparty in the ordinary multisig/shared-wallet creation flow (sending a `create_new_wallet` offer with a crafted `arrOtherCosigners` array), which is a normal, permissionless device-to-device operation available to anyone the victim pairs with to set up a shared wallet. No hub or node compromise is required — it is exploitable purely from the payload of a wallet-setup message.

### Recommendation
In `addIndirectCorrespondents` (device.js), verify `objectHash.getDeviceAddress(correspondent.pubkey) === correspondent.device_address` before inserting, mirroring the check implicit in `addUnconfirmedCorrespondent`. Additionally, ensure all trust-sensitive joins on `correspondent_devices` (private-chain forwarding, control-address resolution) explicitly filter on `is_confirmed=1` and/or require a real pairing handshake before a device is treated as an authenticated recipient for private financial data, rather than trusting `is_indirect=1` rows populated from a third party's claim.

### Proof of Concept
Conceptual outline (exact wire format would need confirmation against a running two-node ocore/hub setup, which is beyond static analysis):
1. Attacker device A pairs normally with victim device V (ordinary pairing).
2. A initiates a multisig wallet creation and sends V a `create_new_wallet` offer whose `arrOtherCosigners` list includes an entry `{device_address: <D_victim2 or arbitrary>, hub: "attacker-hub.example", pubkey: <attacker-controlled pubkey>, name: "..."}` for a device V has never paired with.
3. V's `wallet_defined_by_keys.js` offer handler calls `device.addIndirectCorrespondents(arrOtherCosigners, ...)`, which inserts the row into `correspondent_devices` with `is_indirect=1` and no pubkey/device_address consistency check [1](#0-0) .
4. If a shared address is later created naming that `device_address` as a member, V's `forwardPrivateChainsToOtherMembersOfAddresses`/`readAllControlAddresses` logic will treat the injected entry as a legitimate correspondent and route private-chain data to `attacker-hub.example` [7](#0-6) .

Note: I could not fully trace the exact caller of `addIndirectCorrespondents` inside `wallet_defined_by_keys.js` (the grep matched 13 references but the surrounding handler code for the incoming `create_new_wallet` offer was not retrieved in full within available iterations), so the precise validation (if any) performed on `arrOtherCosigners` before it reaches `addIndirectCorrespondents` should be double-checked in a live session before treating this as fully confirmed.

		);
	}, onDone);
}

		});
	});

function forwardPrivateChainsToOtherMembersOfAddresses(arrChains, arrAddresses, bForwarded, conn, onSaved){
	conn = conn || db;
	conn.query(
		"SELECT device_address FROM shared_address_signing_paths \n\
		JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?) AND device_address!=?", 
		[arrAddresses, device.getMyDeviceAddress()], 
		function(rows){
			console.log("shared address devices: "+rows.length);
			var arrDeviceAddresses = rows.map(function(row){ return row.device_address; });
			walletGeneral.forwardPrivateChainsToDevices(arrDeviceAddresses, arrChains, bForwarded, conn, onSaved);
		}
	);
}

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
