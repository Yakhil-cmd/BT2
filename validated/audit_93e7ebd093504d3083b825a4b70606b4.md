### Title
plugin-validator and validate-hook-schema.sh treat unknown hook event names and non-matching matcher patterns as warnings/passes instead of failures, producing false assurance that a protective hook is active - ([File: plugins/plugin-dev/agents/plugin-validator.md], [File: plugins/plugin-dev/skills/hook-development/scripts/validate-hook-schema.sh])

### Summary
The `plugin-validator` agent's hook-validation step and its underlying `validate-hook-schema.sh` utility only check that an event name/matcher key is a non-empty string; they never validate the event name against the enumerated valid list as a hard failure, and never check whether a `matcher` regex can ever match a real `tool_name`. A hooks.json with a typo'd event (`PreToolUS`) or a matcher that can never match any tool (e.g. `"matcher": "NoSuchTool"`) is reported as valid (exit 0, "✅ All checks passed" or only a warning), even though the hook will never fire at runtime.

### Finding Description
In `plugins/plugin-dev/skills/hook-development/scripts/validate-hook-schema.sh`, the event-name check at lines 41-56 iterates `VALID_EVENTS` and, if the event key from the plugin's hooks.json isn't in that list, only emits `echo "⚠️  Unknown event type: $event"` and unconditionally prints `"✅ Root structure valid"` right after — it never increments `error_count` or causes a non-zero exit for this case [1](#0-0) . The final exit logic at lines 150-159 only fails (`exit 1`) when `error_count` is non-zero, so a misspelled event name alone (with an otherwise well-formed hook object) results in "⚠️ Validation passed with N warning(s)" and `exit 0` [2](#0-1) .

For matchers, the script only checks `matcher` is present/non-empty (line 70-75) — there is no check that the matcher's regex intersects any real `tool_name` values (`Bash`, `Read`, `Write`, `Edit`, etc.) [3](#0-2) . A matcher like `"NeverMatchesXYZ"` passes this check trivially.

The `plugin-validator` agent's own guidance mirrors this weak semantics: step 7 tells the agent to check "Valid event names (PreToolUse, PostToolUse, Stop, etc.)" as a loose, example-based description rather than a strict enumerated allowlist, and to check only that "Each hook has `matcher` and `hooks` array" — no instruction to verify the matcher can actually match real tool names [4](#0-3) . Because the agent is an LLM-driven prompt (not a hard-coded validator), and its literal instruction is to use `validate-hook-schema.sh` — which itself does not hard-fail on this class of error — the agent has no path to producing anything but a pass/warning for a hooks.json with `PreToolUS` or an unmatchable matcher.

The result: an attacker (plugin author) ships a plugin whose "protective" block hook (e.g., an intended `PreToolUse` deny hook for `Bash`) has a typo'd event name or non-matching matcher. `plugin-validator` and `validate-hook-schema.sh` both report the plugin as valid/passing. A user who runs the validator before trusting/installing the plugin is told the hook is well-formed, but at runtime the hook dispatcher will never invoke it for the intended event/tool, so the "protection" silently never executes.

### Impact Explanation
This is a validation-tooling false-assurance bug: it does not itself execute unauthorized actions, but it defeats the security purpose of the validator by certifying a broken block/deny hook as "valid." A user relying on `plugin-validator`'s PASS verdict to decide whether a plugin's block hook is safe to trust would proceed as if a `PreToolUse` deny control is enforced, when in fact no hook will ever intercept the matching tool calls. This matches a "trust-boundary / control-bypass via false validation assurance" impact category — the security control (block hook) is inert while the validator asserts otherwise, directly undermining the guarantee the validator is documented and relied upon to provide.

### Likelihood Explanation
Highly feasible and repeatable: any plugin author (unprivileged, no special access needed) can commit a hooks.json with a misspelled event key or an intentionally non-matching matcher regex; this requires no exploitation of Claude Code internals, just crafting a plugin file. Running `validate-hook-schema.sh` against such a file, or asking the `plugin-validator` agent to check it, deterministically yields a pass (or pass-with-warning) rather than a hard failure, as shown directly in the script's control flow.

### Recommendation
1. In `validate-hook-schema.sh`, treat an unrecognized event key as a hard error (increment `error_count`, not just a warning) so the script exits non-zero.
2. Add a matcher-semantics check: for each `hooks.json` entry, verify the `matcher` (as a regex) matches at least one entry in a maintained list of valid Claude Code `tool_name` values (`Bash`, `Read`, `Write`, `Edit`, `Glob`, `Grep`, `Task`, `WebFetch`, etc., plus `*`/wildcard), and flag/error if it structurally cannot match any known tool name.
3. Update `plugin-validator.md` step 7 to explicitly instruct the agent to hard-fail (not warn) on unknown event names and to cross-check matcher patterns against the enumerated tool_name list, rather than describing the valid-events check with "etc." as an open-ended/loose set.
4. Ensure `Overall Assessment` in the validator's output format cannot be `PASS` when any hook's event name is unrecognized or its matcher provably never matches a real tool.

1. Create `fixtures/typo-event-hooks.json`:

```json
  ]

```
Run `validate-hook-schema.sh fixtures/typo-event-hooks.json`; current behavior: exits `0` with only "⚠️ Unknown event type: PreToolUS" and "✅ Root structure valid" — assert this should instead produce a non-zero exit and be counted as an error.

2. Create `fixtures/unmatchable-matcher-hooks.json`:
```json
{
  "PreToolUse": [
    { "matcher": "ToolThatDoesNotExist", "hooks": [{ "type": "command", "command": "${CLAUDE_PLUGIN_ROOT}/deny.sh" }] }
  ]
}
```
Run the validator; current behavior: passes with no error/warning about the matcher never matching any real `tool_name`. Assert the fixed validator flags this as an error/warning ("matcher does not match any known tool_name").

3. Add equivalent assertions to `plugin-validator` agent's expected behavior (e.g., via a scripted transcript test) confirming `### Overall Assessment` outputs `FAIL` (not `PASS`) for both fixtures, matching the invariant that validation tooling must not give false assurance that a block hook is active.

```shellscript
VALID_EVENTS=("PreToolUse" "PostToolUse" "UserPromptSubmit" "Stop" "SubagentStop" "SessionStart" "SessionEnd" "PreCompact" "Notification")

for event in $(jq -r 'keys[]' "$HOOKS_FILE"); do
  found=false
  for valid_event in "${VALID_EVENTS[@]}"; do
    if [ "$event" = "$valid_event" ]; then
      found=true
      break
    fi
  done

  if [ "$found" = false ]; then
    echo "⚠️  Unknown event type: $event"
  fi
done
echo "✅ Root structure valid"
```
