Based on my investigation, the closest structural analog to the reported "declared amount not validated against actual value" bug class is in the Snowbridge V2 outbound XCM-to-Ethereum message converter, where a user-supplied `value` field for a `Transact`/`CallContract` command is never checked against the ENA/PNA amount reserved for the recipient agent in the same XCM program.

### Title
Unvalidated `value` field in Snowbridge V2 `Transact`/`CallContract` XCM conversion allows a self-defined value with no relation to reserved assets - ([File: bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs])

### Summary
The Snowbridge V2 outbound converter builds a `Command::CallContract { target, calldata, gas, value }` command directly from the user-supplied `ContractCall::V1.value` field of an XCM `Transact` instruction, without ever validating that `value` is bounded by (or related to) the ENA/PNA amount that was reserved and deposited for the recipient/agent earlier in the same XCM program. An `XcmConverterError::CallContractValueInsufficient` variant is defined for exactly this purpose but is dead code — it is never constructed or returned anywhere in `convert.rs`.

### Finding Description
Any signed account can build and execute an arbitrary XCM program via `pallet_xcm::execute` (or send it cross-chain), reaching `XcmConverter::convert` in [1](#0-0) . This function parses `WithdrawAsset`/`ReserveAssetDeposited` for ENA/PNA, `AliasOrigin`, `DepositAsset`, and an optional `Transact` carrying a SCALE-encoded `ContractCall`: [2](#0-1) 

The `value` field decoded from the user-controlled `Transact.call` payload is pushed straight into `Command::CallContract` with no relation whatsoever to the `deposit_assets`/ENA amount that was reserved for the `recipient` earlier in the program (built in `extract_ethereum_native_assets` / `extract_polkadot_native_assets`, [3](#0-2) ). Notably, the enum already anticipates this check via the `CallContractValueInsufficient` variant: [4](#0-3) 

but no call site in the file constructs or returns it — i.e., the intended validation appears to have been designed but never wired in, structurally identical to the reported Solidity bug: a declared "amount"/"value" parameter that a caller fully controls and that is never validated against what was actually reserved/transferred for the operation.

An existing integration test explicitly documents this gap with an inline comment: [5](#0-4) 

The comment "`value should be less than the transfer amount, require validation on BH Exporter`" is a direct acknowledgement in the codebase that this check is expected but not enforced at the point I examined.

### Impact Explanation
If this `value` is used on the Ethereum Gateway side to instruct the recipient agent contract to release native ETH/value as part of executing `CallContract`, then a caller could declare a `value` larger than the assets actually reserved/deposited to that agent in the same message, potentially draining any residual ETH balance sitting in the agent contract (analogous to the "leftover ETH stolen" scenario in the source report). This would constitute unauthorized value transfer on the destination chain (Ethereum), a High/Critical class of issue (theft of funds) if confirmed end-to-end.

### Likelihood Explanation
Low-to-Medium confidence at this stage. The Polkadot-SDK repository only contains the *encoding*/outbound-queue side of this pathway; the actual `value` semantics and any offsetting checks are implemented in the Snowbridge Solidity Gateway contract on Ethereum, which is out of scope for this repository and which I could not inspect. It is possible the check exists on the Ethereum side (the test comment says "require validation on BH Exporter", suggesting the author intended enforcement in the `BridgeHubWestend`/Exporter pallet path, not necessarily in `convert.rs`), and I did not find where (or whether) that enforcement actually happens elsewhere in this Rust codebase (e.g., in `EthereumOutboundQueueV2`/`commitment` building prior to submission). The unused `CallContractValueInsufficient` variant is strong circumstantial evidence that a validation step was planned but is currently unreachable dead code, but I could not conclusively prove the missing check is exploitable without access to the Ethereum Gateway contract logic.

### Recommendation
Add an explicit check in `XcmConverter::convert` (or in the outbound-queue pallet before commitment) that `value <= total_reserved_amount_for_recipient` (the sum of `enas`/`pnas` amounts routed to the same `recipient`/agent in the message), returning `XcmConverterError::CallContractValueInsufficient` when violated, matching the intent already expressed by the existing (currently dead) error variant. If the check is genuinely enforced elsewhere (e.g. on the Ethereum Gateway contract), the unused Rust-side error variant and the misleading test comment should be removed/updated to avoid confusion and to document where the invariant is actually enforced.

### Proof of Concept

1. Constructing an XCM program with `WithdrawAsset`/`ReserveAssetDeposited` reserving a small ENA/PNA amount for a `recipient` agent, followed by `AliasOrigin`, `DepositAsset`, and a `Transact` carrying `ContractCall::V1 { value: <amount > reserved>, .. }`.
2. Running it through `XcmConverter::convert` (unit-testable in `bridges/snowbridge/primitives/outbound-queue`) to confirm it succeeds despite `value` exceeding reserved assets.

	fn extract_ethereum_native_assets(
		&mut self,
		enas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		for ena in enas.clone().into_inner().into_iter() {
			// Check the the deposit asset filter matches what was reserved.
			if !deposit_assets.matches(&ena) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// only fungible asset is allowed
			let (token, amount) = match ena {
				Asset { id: AssetId(inner_location), fun: Fungible(amount) } => {
					match inner_location.unpack() {
						(0, [AccountKey20 { network, key }]) if self.network_matches(network) => {
							Ok((H160(*key), amount))
						},
						// To allow ether
						(0, []) => Ok((H160([0; 20]), amount)),
						_ => Err(AssetResolutionFailed),
					}
				},
				_ => Err(AssetResolutionFailed),
			}?;

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			commands.push(Command::UnlockNativeToken { token, recipient, amount });
		}
		Ok(commands)
	}

	/// Extract polkadot native assets
	fn extract_polkadot_native_assets(
		&mut self,
		pnas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		ensure!(pnas.len() > 0, NoReserveAssets);
		for pna in pnas.clone().into_inner().into_iter() {
			if !deposit_assets.matches(&pna) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// Only fungible is allowed
			let Asset { id: AssetId(asset_id), fun: Fungible(amount) } = pna else {
				return Err(AssetResolutionFailed);
			};

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			// Ensure PNA already registered
			let token_id = TokenIdOf::convert_location(&asset_id).ok_or(InvalidAsset)?;
			let expected_asset_id = ConvertAssetId::maybe_convert(token_id).ok_or(InvalidAsset)?;
			ensure!(asset_id == expected_asset_id, InvalidAsset);

			commands.push(Command::MintForeignToken { token_id, recipient, amount });
		}
		Ok(commands)
	}
