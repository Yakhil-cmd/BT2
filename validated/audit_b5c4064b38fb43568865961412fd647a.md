### Title
Unbounded `count_coins` in fixed-denomination asset definitions allows floating-point precision-loss ("overflow-equivalent") in cap/issuance accounting - (File: validation.js, aa_validation.js, indivisible_asset.js)

### Summary
`ocore` (like the analog report's Solidity `Airdrop` contract) performs unchecked arithmetic accumulation on user-supplied numeric fields when validating fixed-denomination asset definitions and when issuing indivisible-asset coins. `denomInfo.count_coins` and `denomInfo.denomination` are validated only with `isPositiveInteger()`, which has no upper bound, and their product (`count_coins * denomination`) is used both to reconstruct/validate the asset `cap` and, at issuance time, to compute the actual number of tokens created. Because JavaScript numbers lose integer precision above `Number.MAX_SAFE_INTEGER` (2^53‑1), a single crafted denomination (or a small set of them) can produce a `count_coins * denomination` product that silently rounds, exactly mirroring the "overflow" bug class in the report (unchecked accumulation of unbounded per-item values into a value later trusted for consistency/supply guarantees).

### Finding Description
When an asset is defined with `fixed_denominations: true`, each `denomInfo` is checked only for positivity: [1](#0-0) 
`denomInfo.denomination` is bounded by `MAX_CAP` only under a version-gated condition, and `denomInfo.count_coins` has no upper bound at all — only `isPositiveInteger(denomInfo.count_coins)`: [2](#0-1) 
The same unbounded pattern exists in the AA-definition validator: [3](#0-2) 

The accumulator `total_cap_from_denominations` sums `denomInfo.count_coins * denomInfo.denomination` across up to `MAX_DENOMINATIONS_PER_ASSET_DEFINITION` entries and is later required to equal `payload.cap`: [4](#0-3) 

At issuance time, `indivisible_asset.js` computes the number of coins to mint for a denomination row directly as `count_coins * denomination`: [5](#0-4) 

Since `count_coins` is unbounded, an attacker acting as the asset definer can choose `denomination` and `count_coins` such that their product exceeds `Number.MAX_SAFE_INTEGER`. JavaScript will silently round the result to the nearest representable double instead of throwing or wrapping predictably — the JS-equivalent of the Solidity integer-overflow class described in the external report (unchecked arithmetic on attacker-controlled inputs feeding a value that downstream code treats as authoritative for supply/cap accounting).

### Impact Explanation
If the rounded product happens to equal a declared `cap` that passes `isPositiveInteger(payload.cap) && payload.cap <= constants.MAX_CAP`, the asset definition will validate as internally consistent even though the *true* mathematical total of `count_coins * denomination` across denominations differs from the value used for validation and possibly from the value ultimately reflected on-chain. Because indivisible-asset issuance for capped assets is gated to a single issuance per denomination row (`max_issued_serial_number=0`), the actual number of coins minted is determined by the (potentially precision-lossy) `count_coins * denomination` computed at issuance — this can create a discrepancy between the asset's declared cap and the real circulating supply, undermining the supply-integrity guarantee that asset holders and downstream wallets rely on (asset issuance and transfer conditions attack surface, reachable by any unprivileged asset issuer).

### Likelihood Explanation
This requires only the ability to define a new asset (or nested AA asset definition) with `fixed_denominations: true` — an operation available to any unprivileged unit poster / AA author, with no special permissions. No cooperation from other network participants is needed to trigger the validation path; only the specific numeric magnitudes needed to hit precision loss make this non-trivial to demonstrate as a full supply-inflation exploit, since I could not further confirm here (tool budget exhausted) the exact value of `constants.MAX_CAP` and whether an additional cap on `count_coins` exists in a code path I did not reach.

### Recommendation
- Add an explicit upper bound on `denomInfo.count_coins` (e.g., `count_coins <= constants.MAX_CAP`) in both `validation.js` (`validateAssetDefinition`) and `aa_validation.js` (`validateDenominations`), symmetric to the existing bound on `denomination`.
- Validate that `denomInfo.count_coins * denomInfo.denomination <= constants.MAX_CAP` explicitly, ideally using integer-safe arithmetic (e.g., check operands against `Number.MAX_SAFE_INTEGER / denomination` before multiplying) rather than relying on the product's magnitude implicitly.
- Reject any accumulated `total_cap_from_denominations` value (or per-row issuance amount) that is not an exact integer within `Number.MAX_SAFE_INTEGER` before comparing it to `payload.cap`.

### Proof of Concept
1. As an unprivileged user, post a unit (or AA that emits an `asset` message with `init` producing) a `fixed_denominations` asset definition containing a denomination row such as `{ denomination: 9007199254740992, count_coins: 3 }` (product exceeds `Number.MAX_SAFE_INTEGER`), alongside `cap` set to the JS-rounded value of that product.
2. The validators in `validation.js`/`aa_validation.js` accept `denomination` and `count_coins` individually (both pass `isPositiveInteger`), and the summed `total_cap_from_denominations === payload.cap` check passes despite floating-point rounding, since both sides are computed via the same lossy JS arithmetic.
3. At issuance (`indivisible_asset.js` `issueNextCoin`), `count_coins_to_issue * denomination` is computed again with the same precision loss, and coins are actually minted with an `issue_amount` inconsistent with the nominal, expected exact supply, since the asset's declared cap no longer exactly reflects true issuable total once precision-sensitive integers are involved.

*Uncertainty note:* I was unable to verify the exact numeric value of `constants.MAX_CAP` or `constants.MAX_DENOMINATIONS_PER_ASSET_DEFINITION` before the tool budget was exhausted, so the precise combination of `denomination`/`count_coins` needed to trigger a passing-but-inconsistent cap check could not be fully worked out to demonstrate concrete supply inflation beyond the mechanism described above.
