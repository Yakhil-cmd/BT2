### Title
Cross-organization stack takeover via GitHub webhook: signature verified against `repository.owner.login`'s app secret while every handler acts on the unrelated `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner` (derived from the payload's `repository.owner.login`, falling back to `organization.login`). However, none of the actual event handlers use that same field to decide which `Stack`/`Repository` to act on. They instead resolve the target purely from `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Because these two fields are never checked for consistency, a payload can be crafted where `repository.owner.login` names one (attacker-controlled) organization — whose secret the attacker can produce a valid signature with — while `repository.full_name` names a completely different organization/repository whose `Stack` gets acted upon.

### Finding Description
`Shipit::WebhooksController` mounts a single, global `/webhooks` endpoint for all configured GitHub organizations (`resources :webhooks, only: :create` in `config/routes.rb:14`). Signature verification is: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp`/webhook secret keyed by `repository_owner`, which is read only from `repository.owner.login` (or `organization.login`) — a field the attacker fully controls in the raw request they send to this public endpoint. In a multi-org Shipit deployment (see `test/dummy/config/secrets_double_github_app.yml`, showing distinct `webhook_secret`s per org), an attacker who legitimately administers/owns *one* onboarded organization (e.g. `OrgOne`) knows `OrgOne`'s `webhook_secret` (it is a value they configured when creating their own GitHub App/webhook). They can therefore sign an arbitrary raw POST body themselves and send it directly to `/webhooks`.

Once the signature check passes (because `repository.owner.login == "OrgOne"` correctly selected and matched OrgOne's secret), the request proceeds to `create`, which re-parses the body and dispatches to handlers: [3](#0-2) 

Every default handler (`PushHandler`, `PullRequest::OpenedHandler`, etc.) resolves the target repository/stack exclusively via `repository.full_name`, never via `repository.owner.login`: [4](#0-3) [5](#0-4) 

Nothing enforces `repository.full_name.start_with?(repository.owner.login)`. The attacker sets `repository.owner.login = "OrgOne"` (satisfies signature-org lookup) but `repository.full_name = "OrgTwo/victim-repo"` (an unrelated org/repo also configured on the same Shipit instance). The signature check authenticates "this request came from someone who knows OrgOne's secret," but the payload is acted upon as if it were an authentic event for `OrgTwo/victim-repo` — the binding `organization authenticated == repository written` is broken.

For the `push` event specifically, this lets the attacker drive `Stack#sync_github` for a stack they do not own/administer: [6](#0-5) 

`sync_github` schedules `GithubSyncJob` with an attacker-chosen `expected_head_sha`, which drives commit ingestion/CI-status resolution and can trigger the victim stack's continuous-delivery pipeline for that head, resulting in an unauthorized deploy on a repository the attacker has no legitimate relationship to.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written." An unprivileged external actor who only controls their own onboarded GitHub org/app (not a Shipit account, not GitHub write-access to the victim repo) can force Shipit to process crafted push/pull_request/status/check_suite events against a victim organization's stacks, enabling unauthorized deploy triggering, spoofed commit/CI status data, and provisioning/archival of another org's review stacks — satisfying the "unauthorized deploy" / cross-repository-write High/Critical impact bar.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator of at least one GitHub App/org that is also configured in the same multi-tenant Shipit instance (so they know that org's `webhook_secret`), and requires the victim org to be configured on the same instance — a realistic scenario for shared/self-hosted Shipit deployments serving multiple organizations, as explicitly supported by the engine's own multi-org config format.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler`, enforce that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` used to select the verifying secret, rejecting (422) any payload where they diverge, before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both onboarded with stacks.
2. As the administrator of `OrgOne`'s GitHub App, craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<sha attacker wants synced/deployed>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. Sign it with `OrgOne`'s `webhook_secret` using `sha1=HMAC-SHA1(secret, body)` and set header `X-Hub-Signature`.
4. `POST /webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner == "OrgOne"`, fetches OrgOne's app, and the signature validates.
6. `PushHandler#process` resolves `stacks` via `repository.full_name == "OrgTwo/victim-repo"` [7](#0-6)  and calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5)  on the victim org's stack, despite the request never having been authenticated for `OrgTwo`.
