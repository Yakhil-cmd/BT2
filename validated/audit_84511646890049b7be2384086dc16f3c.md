### Title
Asset definer can update the spender attestor list at any time, retroactively freezing previously-attested holders' existing coins - (File: `validation.js`, `storage.js`)

### Summary
For assets with `spender_attested=true`, the asset definer can post an `asset_attestors` message at any point to change the list of trusted attestors that determines whose payments are valid. Because payment validation always looks up the *current* (latest at `last_ball_mci`) attestor list rather than the list in effect when a holder's attestation was granted, the definer can unilaterally tighten the condition after coins have already been issued/transferred to attested holders, causing those holders' existing balances to become unspendable. This mirrors the reported Notional issue where the vault owner raises `minCollateralRatio` after positions are opened, retroactively pushing previously-healthy accounts into a bad/liquidatable state.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment of that asset requires the sender/issuer to be attested by one of the asset's current attestors, enforced in `validatePayment`: [1](#0-0) 

The attestor list itself is **not fixed at asset-definition time** — the definer can publish new `asset_attestors` messages that replace it, and only the identity of the definer is checked, with no restriction preventing tightening the list against addresses that already hold or are already attested: [2](#0-1) 

When resolving an asset for validation, `readAsset` always fetches the **latest** attestor list (by unit level/rowid) that is stable before `last_ball_mci`, discarding all prior lists: [3](#0-2) 

`filterAttestedAddresses` then checks whether an address is attested strictly against this current attestor list combined with the most recent `attestations` for the address: [4](#0-3) 

Because there is no snapshotting of "attestor list at the time coins were acquired," a holder who received attested-status coins under attestor set A can find those same coins permanently unspendable once the definer swaps to attestor set B (removing the attestor who vouched for the holder) — even though nothing about the holder's own address or attestation changed. This is analogous to the reported bug class: a privileged party (asset definer / vault owner) can change a validation threshold/condition after the fact, causing state that was valid to become invalid, with no timelock or grandfathering mechanism.

### Impact Explanation
Holders of a `spender_attested` asset can have their already-issued or already-transferred coins become permanently frozen (unspendable) as soon as the asset definer republishes a new attestor list that excludes the attestor who attested them, with no recourse and no on-chain warning beyond the new `asset_attestors` unit. This is a direct fund-freezing/loss-of-availability impact for unprivileged holders who interact with the asset in good faith, matching the "AA fund loss or freezing" acceptance criterion — the definer/asset-issuer role is one of the explicitly in-scope actors (asset issuance and transfer conditions).

### Likelihood Explanation
Any account that defines an asset with `spender_attested: true` (a standard, commonly used ocore feature, e.g. KYC/whitelisted tokens) can trigger this at will by posting a single `asset_attestors` message — no special permissions beyond being the asset's own definer are required, and the change takes effect for all subsequent payment validations of that asset as soon as it stabilizes. This does not require any protocol bug beyond the existing intended behavior of "latest list wins," making it straightforward to exercise, whether accidentally (definer rotates attestors for legitimate reasons) or maliciously (definer intentionally targets holders it wants to freeze).

### Recommendation
- Bind the attestor-list version used for validating a payment to the attestor list that was current when the spending output/attestation was created (i.e., snapshot per-output or require the attestation to be checked against the attestor list active at the attestation's own `main_chain_index`), rather than always re-resolving to the latest list at spend time.
- Alternatively, require attestor-list changes to only add attestors (never remove) for previously-attested addresses, or introduce a grace/timelock period before a new attestor list becomes enforceable, so existing holders have an opportunity to move funds before being locked out.

### Proof of Concept
1. Definer `D` issues asset `X` with `spender_attested: true` and initial `attestors: [A1]`.
2. `A1` attests address `H` (holder). `D`/anyone sends asset `X` coins to `H`; `H`'s payments validate fine since `H` is attested by `A1`, which is in the current attestor list, per `validatePayment`/`filterAttestedAddresses`.
3. `D` posts a new `asset_attestors` message for asset `X` with `attestors: [A2]` (removing `A1`). This is accepted solely because `D` is the definer, per `validateAttestorListUpdate`.
4. `H` attempts to spend the previously received coins. `readAsset` now resolves the latest attestor list to `[A2]`; `filterAttestedAddresses` finds no attestation of `H` by `A2`, so `arrAttestedAddresses` is empty and `validatePayment` rejects `H`'s payment ("none of the authors is attested").
5. `H`'s coins are now permanently unspendable unless `A2` re-attests `H`, which is entirely at the discretion of `D`/`A2`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});

		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
