### Title
Unfiltered PR-label injection into deploy/task process environment bypasses `EnvironmentVariables#permit` whitelist - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` merges every PR label name (uppercased) directly into the environment hash used by `TaskCommands#env`, which is passed unmodified to `PTY.spawn` in `Command#start`. Unlike the HTTP `env` param path (`DeploysController#deploy_params`, `Api::DeploysController` → `Stack#build_deploy` → `DeploySpec#filter_deploy_envs` → `EnvironmentVariables#permit`), the label-derived keys never pass through `EnvironmentVariables#permit`, so an unprivileged PR author can inject arbitrary environment variable *names* into the deploy host's process environment for that review stack.

### Finding Description
The intended invariant is that the set of environment-variable keys that can reach the spawned deploy process is bounded by `deploy_spec.deploy_variables` (`VariableDefinition#name`), enforced by `EnvironmentVariables#permit`:
`EnvironmentVariables.with(env).permit(deploy_variables) == env_reaching_PTY.spawn`.

For the HTTP path this holds: `Api::DeploysController`/`DeploysController` restrict params via `params.require(:deploy).permit(:until_commit_id, env: @stack.deploy_variables.map(&:name))` and `Stack#build_deploy` calls `filter_deploy_envs(env.to_h)` [1](#0-0) [2](#0-1) , which in turn calls `EnvironmentVariables.with(env).permit(deploy_variables)`, raising `NotPermitted` for any key not declared in `deploy.variables` [3](#0-2) [4](#0-3) .

For the PR-label path this invariant is broken. `LabelCapturingHandler` stores the raw GitHub label names on `PullRequest#labels` with no whitelist check whatsoever [5](#0-4) . `Shipit::ReviewStack#env` then merges every label, upcased, as a key with value `"true"`, directly into the value returned by `Stack#env`, completely bypassing `EnvironmentVariables#permit`: [6](#0-5) . `TaskCommands#env` merges `@stack.env` before `@task.env` (the only filtered source): [7](#0-6) . Because `@task.env` (last merge, wins on conflicts) is restricted to whitelisted deploy/rollback/task variables, any label whose name does *not* collide with a declared variable name passes through unfiltered. That merged hash is passed as `env:` into `Command.new`, stored in `@env`, and fed straight into `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` via `unbundled_env` [8](#0-7) [9](#0-8) .

Attacker flow: open a PR against a repository with `review_stacks_enabled` and a deploy spec declaring no (or unrelated) `deploy.variables` (the default is an empty array, `DeploySpec#deploy_variables`) [10](#0-9) . Add a label with the exact name of a security-sensitive environment variable (e.g. `BASH_ENV`), and commit a file literally named `true` (the fixed value all labels get) into the PR branch. When the review stack executes any deploy/task step through a shell that honors `BASH_ENV`, `chdir` is the checked-out PR working directory (attacker-controlled content), so the injected `BASH_ENV=true` resolves to the attacker's committed file relative to that directory and gets sourced, executing arbitrary attacker-authored shell commands as the deploy-host process — i.e. RCE. Existing guards fail here specifically because `NotPermitted`/`permit` is only wired into the HTTP `deploy`-param → `filter_deploy_envs`/`filter_rollback_envs` code path (confirmed by `test/controllers/deploys_controller_test.rb` and `Api::DeploysControllerTest`, which assert 422/`NotPermitted` for unknown env keys via HTTP) [11](#0-10) [12](#0-11) , while `ReviewStack#env`/label capture has no equivalent check — confirmed directly by the existing (non-adversarial) test asserting arbitrary label names flow unfiltered into `env` [13](#0-12)  and [14](#0-13) .

### Impact Explanation
An unprivileged PR author on any repository with review stacks enabled can inject arbitrary named environment variables (fixed value `"true"`) into the exact process environment used to run deploy/task shell steps for their own review stack, with the process's working directory being fully attacker-controlled PR content. This provides a practical RCE primitive (e.g., via `BASH_ENV`, `ENV`, `PYTHONSTARTUP`, `RUBYOPT`, or similar interpreter-startup env vars honored by whatever shell/tooling the deploy spec's steps invoke) on the shared Shipit deploy host, executing as the Shipit deploy user — which typically holds `GITHUB_TOKEN` and other deploy-time secrets accessible to the process, matching the Critical impact category (RCE on the deploy host, credential exfiltration). This is repeatable per pull request/label change and is scoped to the attacker's own review stack, but since the deploy host is shared infrastructure, code execution there threatens all tenants' secrets and running processes.

### Likelihood Explanation
Requires only: repository has `review_stacks_enabled` (a documented, common feature) and its deploy spec's `deploy.variables`/`rollback.variables` (or task variables) don't already whitelist the chosen env-var name (default is empty, so essentially always true out of the box). The attacker needs no Shipit credentials — only the ability to open a PR and add a label, both ordinary unauthenticated-relative-to-Shipit GitHub actions available to any contributor/fork author. Exploitation of the fixed `"true"` value into full RCE depends on the specific deploy steps' interpreter/shell honoring an env var whose value is a relative filename equal to `"true"` (e.g., `BASH_ENV`) — feasible for common deploy-step shells but somewhat environment-dependent; the underlying whitelist-bypass itself, however, is unconditionally reproducible.

### Recommendation
Route PR-label-derived environment variables through the same whitelist as HTTP-supplied env vars: in `Shipit::ReviewStack#env`, filter the label-derived hash through `EnvironmentVariables.with(...).permit(cached_deploy_spec.deploy_variables)` (or an explicit review-stack-specific variable whitelist) before merging, and drop/ignore (rather than silently pass) any label name not in that whitelist instead of raising in a codepath that can't reject a webhook. Alternatively, capture labels into a clearly separate namespace (e.g., prefixed `SHIPIT_LABEL_<NAME>`) rather than raw env var names so they can never collide with sensitive interpreter environment variables.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend)
test "#env does not allow labels to set arbitrary process environment variable names" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["BASH_ENV"]

  # Left side of the intended binding: what the HTTP whitelist would allow
  allowed = Shipit::EnvironmentVariables.with(stack.env).permit(stack.cached_deploy_spec.deploy_variables) rescue :not_permitted

  # Right side: what actually reaches TaskCommands/Command#env unfiltered
  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  unfiltered_env = Shipit::TaskCommands.new(task).env

  assert_equal :not_permitted, allowed # HTTP-equivalent whitelist rejects BASH_ENV
  assert_equal "true", unfiltered_env["BASH_ENV"] # yet the label path lets it through unfiltered
end
```
This demonstrates the equality `EnvironmentVariables.with(env).permit(deploy_variables) == unfiltered_label_env` fails: the HTTP-equivalent whitelist check raises/rejects `BASH_ENV`, while the label-derived `TaskCommands#env` (and therefore the env handed to `Command`/`PTY.spawn`) contains it unfiltered.
