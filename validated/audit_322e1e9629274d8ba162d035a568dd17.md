### Title
Cross-organization forged `pull_request` webhook via `repository.owner.login`/`repository.full_name` divergence bypasses signature check and mutates another org's `PullRequest` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to check using `repository_owner` (`params.dig('repository','owner','login')`), while the downstream handler resolves and mutates the actual `Repository`/`Stack` using `params.repository.full_name`. These two values are never required to reference the same organization, and if the organization named by `owner.login` has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` trivially returns `true`, letting an attacker forge a request that is "verified" against one org but writes to a stack belonging to a completely different org.

### Finding Description
The invariant that should hold is: `organization_that_verified_signature == organization_that_owns_the_mutated_repository`, i.e. `params.repository.owner.login == owner(Repository.from_github_repo_name(params.repository.full_name))`. Nothing in the code enforces this.

- `WebhooksController#verify_signature` picks the app config via `repository_owner`, which reads only `params.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) [2](#0-1) .
- `Shipit.github(organization:)` looks up that org's config and instantiates a `GitHubApp`; `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org has no `webhook_secret` configured [3](#0-2) , and returns `GithubOrganizationUnknown`→422 only when the org isn't configured at all, not when the org has no secret [4](#0-3) .
- Once verification passes, `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler` never re-checks `repository.owner.login`. It resolves the actual `Repository` purely from `params.repository.full_name` via `Repository.from_github_repo_name` [5](#0-4) , derives the `stack`/`review_stack` from that repository [6](#0-5) , and on `labeled_active_stack?` persists attacker-controlled label names onto that stack's `PullRequest` record [7](#0-6) [8](#0-7) .

Exploit flow:
1. Shipit is configured with at least two orgs, e.g. `victim-org` (has a `webhook_secret` and owns a real stack/repository `victim-org/victim-repo`) and `no-secret-org` (configured in `secrets.github` but with no `webhook_secret`, e.g. for a low-security/public integration).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request`, body `action: "labeled"`, `repository.owner.login: "no-secret-org"`, `repository.full_name: "victim-org/victim-repo"`, and arbitrary `X-Hub-Signature`.
3. `verify_signature` computes `repository_owner` = `"no-secret-org"`, fetches that org's `GitHubApp`, whose `verify_webhook_signature` immediately returns `true` because `webhook_secret` is blank — the attacker-supplied (or absent) signature is never checked.
4. `create` dispatches to `LabelCapturingHandler`, which resolves the repository/stack from `full_name` = `"victim-org/victim-repo"`, and persists attacker-chosen `labels` onto that real `PullRequest`, which later become environment variable keys via `ReviewStack#env`.

Existing guards do not stop this: `drop_unhandled_event` only checks the event is recognized, `verify_signature` never compares `repository.owner.login` against the repository actually resolved by the handler, and none of the `ExplicitParameters` schema, `Repository` validations, or `subset`/`url` validators require the two org references to match.

### Impact Explanation
An attacker who controls no secrets can inject arbitrary label state onto any stack registered in a Shipit instance, as long as the instance also configures at least one organization without a `webhook_secret` (a plausible configuration for low-trust/public-only integrations coexisting with private orgs on the same Shipit deployment). This is a cross-tenant record mutation: a payload nominally "from" one org's repo is used to mutate a `PullRequest`/`ReviewStack` belonging to a different org's stack, and those labels flow into `ReviewStack#env`, potentially influencing downstream `Command`/deploy environment construction. This matches "Critical - a payload for one repository mutating another's stack/commit/task" per the target's severity mapping.

### Likelihood Explanation
Requires a specific but realistic Shipit multi-org configuration where at least one configured GitHub org has no `webhook_secret` while other configured orgs own real, active review stacks. Given that configuration, exploitation costs nothing more than a single crafted HTTP POST with no valid GitHub signature, and is fully repeatable against any stack whose repository is registered in Shipit (attacker only needs to know/guess `owner/repo` full names). If no organization is configured without a secret, this path does not trigger, since every `verify_webhook_signature` call would require a correct HMAC.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler), require that the organization used to select the `webhook_secret` matches the organization that actually owns the resolved repository/stack — e.g., verify using the organization derived from `repository.full_name` rather than (or in addition to and cross-checked against) `repository.owner.login`. Additionally, treat a missing `webhook_secret` for a configured organization as a hard-fail (reject unsigned webhooks) rather than short-circuiting to `true` in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "labeled webhook naming a no-secret org but pointing full_name at a different org's repo mutates that repo's stack" do
  # Setup: secrets.github configured with:
  #   no-secret-org: { app_id:..., installation_id:..., private_key:... }  # no webhook_secret
  #   victim-org: { webhook_secret: "s3cr3t", ... }
  stack = create_review_stack(repository_full_name: "victim-org/victim-repo")
  pr = stack.pull_requests.create!(number: 42, ...)

  body = {
    action: "labeled",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "...", title: "x", state: "open",
      additions: 1, deletions: 1,
      head: { sha: "a" * 40, ref: "some-branch" },
      user: { login: "attacker" },
      assignees: [],
      labels: [{ name: "MALICIOUS_ENV_KEY" }]
    },
    repository: { owner: { login: "no-secret-org" }, full_name: "victim-org/victim-repo" },
    sender: { login: "attacker" }
  }.to_json

  post shipit.webhooks_path, params: body,
       headers: { "X-Github-Event" => "pull_request", "X-Hub-Signature" => "sha1=deadbeef", "Content-Type" => "application/json" }

  assert_response :ok
  pr.reload
  # Broken binding demonstrated: signature was verified against "no-secret-org",
  # but the record mutated belongs to "victim-org".
  assert_equal ["MALICIOUS_ENV_KEY"], pr.labels
end
```
This confirms `repository.owner.login` ("no-secret-org", the org that "verified" the request) differs from the org owning `stack`/`pr` ("victim-org"), yet the mutation still succeeds.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
