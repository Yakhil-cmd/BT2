This confirms the vulnerability: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [1](#0-0)  — a completely different JSON field than the one used to pick which signing secret to verify against, `params.dig('repository', 'owner', 'login')` [2](#0-1) .

### Title
Webhook signature verification is keyed on an attacker-controlled organization field decoupled from the repository whose stacks are acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The `WebhooksController` selects which GitHub App / webhook secret to verify a webhook against using `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated, unverified JSON body. The actual side-effecting code (`PushHandler`, `StatusHandler`, etc.) instead resolves the target `Repository`/`Stack` using a different field, `repository.full_name`. Because Shipit officially supports multiple GitHub App configurations keyed by organization name (documented in `docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`), an attacker can pick which organization's config (and therefore which secret/verification rule) is used, while independently controlling which repository is actually acted upon.

### Finding Description
`verify_signature` in `WebhooksController` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 

`repository_owner` is derived from the raw, attacker-supplied payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an unconfigured `webhook_secret` as automatically valid:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

Meanwhile, the actual handler that performs the write (e.g. triggering a `sync_github` on a stack) looks up the repository using an entirely separate field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

Because `repository.owner.login` (used for verification) and `repository.full_name` (used for the actual action) are two independent, attacker-controlled fields in the same unauthenticated JSON body, an unprivileged remote attacker who can POST to `/webhooks` can:
1. Set `repository.owner.login` (or `organization.login`) to any organization configured in Shipit's `github:` secrets that has `webhook_secret` unset/blank — this is explicitly a supported, documented configuration (`webhook_secret: # nil` appears as the default in every documented example: `config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`) — causing `verify_webhook_signature` to short-circuit and return `true` for any signature (or even without a signature header).
2. Independently set `repository.full_name` to the actual target organization/repository they want to affect.

This breaks the intended binding: *"the organization that authenticated the webhook" == "the repository that is written by the webhook handler"*. Verification authenticates org A; the mutation acts on repo B/org C.

### Impact Explanation
This qualifies as "cross-repository writes" from the impact list: an attacker with no credentials can forge push/status/check_suite/membership events for any repository/stack tracked by Shipit, as long as at least one configured GitHub organization in the multi-org setup lacks a `webhook_secret` (the documented default). Concretely, `PushHandler#process` calls `stack.sync_github(expected_head_sha: ...)` on stacks belonging to the attacker-chosen `repository.full_name` [6](#0-5) , and `StatusHandler#process` writes commit statuses for arbitrary SHAs (`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`) [7](#0-6) , which can influence CI-gated deploy checklists on repositories under a different, fully-verified organization.

### Likelihood Explanation
Requires no session, no API token, and no GitHub credentials — only an HTTP POST to the public `/webhooks` endpoint. Exploitability is conditioned on the deployment running Shipit's documented multi-organization GitHub App configuration where at least one org has no `webhook_secret` configured — a configuration explicitly shown as the default/example in the repo's own setup documentation and test fixtures, not an undocumented misuse.

### Recommendation
Bind webhook-signature verification and event processing to the same trusted field. Concretely: after verifying the signature for `repository_owner`, re-derive the acted-upon repository/organization strictly from `repository_owner` (or verify that `repository.full_name`'s owner segment equals the already-authenticated `repository_owner`) before dispatching to handlers, rejecting any mismatch. Additionally, do not treat a blank `webhook_secret` as "always verified" when multiple organizations are configured — require an explicit, non-blank secret per organization in multi-app deployments.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `weak-org` (no `webhook_secret`) and `target-org` (which owns the Shipit-tracked repository `target-org/target-repo`), as per the documented multi-org schema.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "weak-org" },
    "full_name": "target-org/target-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
No valid `X-Hub-Signature` is required (or any arbitrary value works).
3. `verify_signature` resolves `Shipit.github(organization: "weak-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [8](#0-7) .
4. `create` then dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("target-org/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the fully-verified `target-org`'s stacks [6](#0-5) , despite the request never being authenticated against `target-org`'s actual webhook secret.
