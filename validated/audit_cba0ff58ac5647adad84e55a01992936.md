### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the GitHub App/organization associated with the payload's `repository.owner.login` (or `organization.login`) and verifying the HMAC signature with that organization's `webhook_secret`. This proves only that *some organization Shipit knows about* sent the payload — it does not prove that the `sha` referenced inside a `status` event actually belongs to the repository that organization owns. `StatusHandler#process` never re-checks this: it resolves the target purely by commit SHA, globally, across every stack in the installation.

### Finding Description
`WebhooksController#verify_signature` computes the authenticating organization from the payload itself and verifies against that organization's secret: [1](#0-0) [2](#0-1) 

This establishes the binding: *organization authenticated == owner of `repository.full_name` in the payload*. Every other event handler re-derives the target scope from `repository.full_name` via `Handler#stacks`/`Handler#repository_name`, e.g. `PushHandler` and `CheckSuiteHandler` filter through `stacks` (which is `Repository.from_github_repo_name(repository_name)&.stacks`): [3](#0-2) [4](#0-3) 

`StatusHandler`, however, breaks this pattern — it does not call `stacks` or filter by repository at all; it looks up commits purely by SHA across the entire `Commit` table and writes a `Status` for whatever stack that commit belongs to: [5](#0-4) 

So the binding actually enforced at write-time is *organization authenticated == owner of the commit matched by raw SHA*, not *owner of the repository named in the payload*. Since git commit SHAs are content-addressed and identical across forks/mirrors that share history, an attacker who controls (or can get the Shipit GitHub App installed on) an unrelated, low-value organization/repo — sending a fully valid, correctly-signed `status` webhook for their own org — can supply a `sha` that also exists in a completely different, high-value stack (e.g. because that stack's repo was forked, mirrored, or otherwise shares commit history). Shipit will find the commit under the *other* stack and record the forged Status against it, even though the signature only ever proved authorization for the attacker's own organization.

### Impact Explanation
`Commit#status`/`Commit#deployable?` are used by `Commit#schedule_continuous_delivery` to gate continuous deployment: [6](#0-5) [7](#0-6) 

If the target stack has `ci.require` configured and continuous deployment enabled, an attacker who can only authenticate as an unrelated, unprivileged organization can inject a forged "success" status for a shared commit SHA into a victim stack's commit, satisfying `deployable?` and `stack.continuous_deployment?` and triggering `ContinuousDeliveryJob` — resulting in an unauthorized deploy of a stack the attacker was never authorized to interact with. This crosses the "unauthorized deploy" impact bar defined by the rules, and does so purely through a normal, correctly-signed webhook — no GitHub App private key, `webhook_secret`, `api_clients_secret`, or Shipit session is required for the attacker's own organization side.

### Likelihood Explanation
Requires (a) the attacker controlling an organization/repo where the Shipit-integrated GitHub App is installed (which may be a lower bar than compromising the victim organization, depending on installation model — e.g., a public GitHub App installable by any org), and (b) a commit SHA that is shared between the attacker's repo and the victim's stack (trivially achievable via forking the victim's public repository and pushing/mirroring the shared history into the attacker's own org). Given forking is a normal GitHub operation and status events are freely emitted by any repository owner, this is a plausible, low-effort path once the attacker has *any* org onboarded to Shipit — no privileged access to the victim stack, credentials, or session is needed.

### Recommendation
Scope `StatusHandler#process` (and any other SHA/branch-keyed handler) to the repository declared in the authenticated payload, mirroring the base `Handler#stacks` pattern used by `PushHandler`/`CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This restores the binding that the organization authenticated by `verify_signature` must equal the organization/repository whose commits are actually written.

### Proof of Concept
1. Attacker creates/controls GitHub org `attacker-org` with repo `attacker-org/victim-fork`, forked from the real target `victim-org/victim-repo`, sharing commit `abcdef123...` in history.
2. Attacker installs (or already has installed) the Shipit GitHub App on `attacker-org` (a normal, unprivileged action), obtaining a legitimate `webhook_secret` for `attacker-org`.
3. Attacker sends a `status` webhook to `/webhooks` with `repository.owner.login = attacker-org`, `sha = abcdef123...`, `state = success`, correctly HMAC-signed with `attacker-org`'s `webhook_secret`.
4. `WebhooksController#verify_signature` passes (`Shipit.github(organization: "attacker-org")` correctly verifies the signature) — [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the commit belonging to `victim-org`'s stack (because the SHA is shared), and calls `commit.create_status_from_github!(params)`, writing a "success" status onto the victim's commit — [5](#0-4) .
6. If `victim-org`'s stack has continuous deployment enabled, `Commit#schedule_continuous_delivery` fires and the forged status can trigger an unauthorized deploy — [7](#0-6) .
