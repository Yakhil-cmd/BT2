### Title
Same on-chain BTC lockup can be re-used across multiple `register-for-bond` calls to double-count sats/STX credit — (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 lockup path only de-duplicates Bitcoin outpoints *within a single call* via the fold accumulator's `seen-outpoints` list, not globally across calls, stakers, or bond periods.

### Finding Description
`verify-l1-lockups` seeds a fresh, per-call `seen-outpoints: (list)` and folds `validate-l1-lockup` over the submitted outputs, rejecting only duplicates *within that one list* with `ERR_DUPLICATE_LOCKUP_OUTPOINT`: [1](#0-0) [2](#0-1) 

There is no persistent map recording which `(txid, output-index)` outpoints have already been credited by a prior `register-for-bond` call. Each proof only checks: (a) the output script matches the staker's timelock script, (b) the unlock height/merkle proof are valid, and (c) the outpoint isn't repeated *inside the current outputs list*. Nothing prevents the *same* proof bytes (same `tx`, `output-index`, `header`, `leaf-hashes`) from being resubmitted in a brand-new transaction.

`register-for-bond` computes `sats-total` from this unauditable-for-reuse `verify-l1-lockups` result and then uses it to size the STX requirement, sats allowance, and bond membership record: [3](#0-2) [4](#0-3) 

Because sBTC credit derives from `sats-total` while STX-only requires `>= min-ustx-for-sats-amount(sats-total, ...)`, and the L1 path performs no STX/sBTC transfer for the sats amount itself (unlike the sBTC path, which calls `roll-sbtc`/`ft-transfer?`), the same Bitcoin lockup can be claimed as backing for one bond, then reused as backing for another bond membership (a different `bond-index`, or after the staker's first bond membership record is cleared/rolled over) — crediting the "amount-sats" of a single real BTC lock into two separate `protocol-bond-memberships` / `protocol-bonds-total-staked` totals.

This is the direct structural analog of the GitLab report's flaw: the "key" that identifies a unique resource (there: cache path; here: the BTC outpoint proving a lockup) is validated for uniqueness only within the scope of a single request, not globally, allowing the same underlying resource to be claimed more than once.

### Impact Explanation
Double-crediting a Bitcoin lockup means `protocol-bonds-total-staked` (and any downstream signer weight / reward-slot accounting keyed off `amount-sats`) reflects more locked BTC than actually exists on Bitcoin. This breaks the equality "sats credited by an L1 proof == sats actually locked on Bitcoin," inflating signing weight or reward eligibility beyond what is truly collateralized — a High/Critical double-counting-of-commitment class issue per the rules.

### Likelihood Explanation
Requires only an allowlisted staker (unprivileged account, no admin/miner/other-user key) calling `register-for-bond` twice with the same lockup proof against two different `bond-index` values (or once after a roll-over clears `protocol-bond-memberships`/`staker-info` for the first bond). No special timing beyond normal bond-registration windows is needed; the only gate is `protocol-bond-allowances` membership, which the attacker already satisfies as an allowlisted staker.

### Recommendation
Track consumed L1 outpoints in a persistent map (e.g., `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`) and assert non-membership before crediting sats in `validate-l1-lockup`, inserting the outpoint into that map on success so it cannot be replayed in any future `register-for-bond` call.

### Proof of Concept
1. Staker is allowlisted for `bond-index: 0` and `bond-index: 1` (via `protocol-bond-allowances`).
2. Staker performs a real BTC lockup of `sats-total` to their timelock script, producing a valid Merkle-proof lockup record `L`.
3. Staker calls `register-for-bond(bond-index: 0, ..., btc-lockup: (ok { outputs: [L], ... }))` — succeeds, `protocol-bond-memberships` and `protocol-bonds-total-staked[0]` are credited with `sats-total`.
4. Staker calls `register-for-bond(bond-index: 1, ..., btc-lockup: (ok { outputs: [L], ... }))` reusing the identical proof `L` — `verify-l1-lockups`/`validate-l1-lockup` re-validate the same on-chain lockup successfully (no cross-call outpoint tracking), crediting `protocol-bonds-total-staked[1]` with the same `sats-total` again, for a single real BTC lock now counted twice across bonds.
