### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit purely by SHA, with no repository/stack scoping, then writes the attacker-supplied status onto every matching `Commit` row across the entire database. Because GitHub SHAs are content-derived and identical across forks/shared history, a webhook validly signed for one repository (owned by the attacker) can write a `ci/test` status onto a commit belonging to a completely different, victim stack, and if that stack has `merge_queue_enabled: true`, a resulting green head triggers `stack.schedule_merges` and an unauthorized merge/deploy.

### Finding Description
The broken invariant, stated as an equality that should hold but doesn't:
`commit.stack.github_repo_name == payload.repository.full_name` for every `Commit` mutated by a `status` webhook — this is never checked.

Code path:
- `Shipit::WebhooksController#create` parses the JSON body and dispatches to handlers after `verify_signature`, which only checks the HMAC signature against `Shipit.github(organization: repository_owner)` — i.e., it authenticates the *organization*, not the specific repository named in the payload. [1](#0-0) 
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query has zero repository/stack filter — it matches any `Commit` row in the whole `commits` table sharing that SHA. [2](#0-1) 
- The uniqueness index on `commits` is `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming SHA is **not** globally unique — the same SHA can and does legitimately exist in multiple stacks (e.g., shared ancestor commits between an upstream repo and any fork tracked as a separate Shipit stack).
- `Commit#create_status_from_github!` → `add_status` writes the status, and if the resulting simple state becomes non-pending/success, calls `stack.schedule_merges if new_status.pending? || new_status.success?`, which drives the merge queue forward. [3](#0-2) 

Exploit flow: the attacker owns/controls a repository (fork or otherwise) whose organization has the Shipit GitHub App installed, so they can trigger a genuinely-signed `status` webhook (`context: ci/test`, `state: success`, `sha: <shared-ancestor-sha>`) for their own repo. That SHA also exists as a `Commit` row in a victim's stack (any fork relationship or shared history guarantees identical SHAs). `StatusHandler#process` finds and updates the victim's `Commit` row too, since the lookup ignores which repository authenticated the request. If the victim stack has `merge_queue_enabled: true` and this status makes the head commit "green" (satisfies required statuses), `schedule_merges` fires and `merge!` proceeds — an unauthorized merge/deploy decision driven entirely by a status the victim repository never sent.

Existing guards do not prevent this: `verify_signature` authenticates only the organization sending the webhook, not that the named `sha`/commit actually belongs to a stack tied to that organization's repository; there is no `ExplicitParameters` check tying `params.sha`'s resolved commit back to `params` repository info; no model validation restricts which stack a status attaches to beyond the SHA match itself.

### Impact Explanation
An attacker who controls any repository capable of emitting a validly-signed webhook (their own repo/fork within a Shipit-integrated org) can inject arbitrary CI status (`ci/test`, or any other context) onto a commit belonging to an unrelated victim stack, purely because the SHA coincides (which is trivial via forks/shared git history). Combined with `merge_queue_enabled: true`, this can force `Stack#schedule_merges`/`merge!` to proceed on the victim stack, resulting in an unauthorized merge, deploy, or block decision on code the victim did not authorize — this matches the Critical impact category "a payload for one repository mutating another's stack, commit, task, or team, or an unauthorized deploy, rollback or merge." [2](#0-1) [4](#0-3) 

### Likelihood Explanation
Preconditions: the attacker needs a repository within an org onboarded to Shipit's GitHub App (or one they can trigger a genuinely-signed status webhook from), and a victim stack with `merge_queue_enabled: true` whose commit history shares a SHA with the attacker's repo (trivially true for forks or shared-ancestor commits, and the attacker can also just push a commit and target its exact SHA if by chance it collides with a stack they already have visibility into via shared org history). The attack is repeatable per matching SHA and requires no privileged Shipit role, session, or API token — only the ability to emit a webhook for a repository the attacker legitimately controls.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and similarly `CheckRunHandler`/other SHA-keyed handlers) to the repository indicated in the webhook payload, e.g., resolve the stack(s) via `Repository` matched on `payload.repository.full_name`/`repository_owner`, and filter `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` instead of a bare SHA match across the whole table.

### Proof of Concept
```ruby
test "status webhook for shared SHA does not mutate a different repository's stack" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true, requires "ci/test"
  victim_stack.update!(merge_queue_enabled: true)
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  # Attacker's own repo/org sends a validly signed status webhook naming a *different* repository
  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/test",
    "repository" => { "full_name" => "attacker/other-repo", "owner" => { "login" => "attacker-org" } }
  }

  before_state = victim_commit.reload.status.state

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  after_state = victim_commit.reload.status.state

  # Binding under test: a status authenticated for attacker/other-repo must not affect victim_stack's commit
  assert_equal before_state, after_state,
    "status webhook scoped to a different repository must not mutate victim_stack's commit state"
  assert_not victim_stack.reload.updated_at > victim_commit.created_at, "merge queue must not have been advanced"
end
```

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
