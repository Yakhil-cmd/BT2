### Title
Cross-tenant commit status forgery — authenticating org differs from the repository whose commit gets written - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The signature check that authenticates a GitHub webhook is scoped to whichever organization the attacker names in the payload, while the `status` event handler that actually mutates data is scoped only by a global commit SHA, with no verification that the SHA belongs to a stack/repository owned by that same organization.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to validate the HMAC against using a field taken directly from the untrusted JSON body: [1](#0-0) [2](#0-1) 

That `repository_owner` value is used only to pick which secret must sign the request — it is never checked against the entity that the resulting handler will actually modify. Once the signature passes, `Shipit::Webhooks.for_event('status')` runs `StatusHandler`, whose `process` method looks up commits **globally by SHA**, with no relation back to `repository_owner` or any owning organization at all: [3](#0-2) 

Compare this with `Handler#stacks`/`repository_name`, which other handlers (e.g. `PushHandler`) use to scope to a specific `Repository`: [4](#0-3) . `StatusHandler` does not use this scoping at all — it operates on `Commit.where(sha: params.sha)` across the entire instance.

This breaks the trust binding: the organization whose secret authenticated the request ≠ the repository (and its commits/stacks) that the handler writes to. Any organization that is a legitimate, distinct tenant of this Shipit instance (i.e., knows/controls its own configured `webhook_secret` for its own GitHub App/organization entry, e.g. `Shipit::GithubHook` records shown in `test/fixtures/shipit/github_hooks.yml`) can sign a forged `status` payload with **its own** secret while setting `sha` to a commit belonging to a **completely different** organization's repository/stack.

### Impact Explanation
A tenant with no privileges on the victim's stack (no `ApiClient` token, no Shipit session, no GitHub write access to the victim repo) can inject arbitrary CI status entries (`state: success`, arbitrary `context`) for any commit tracked anywhere in the Shipit instance, using only the webhook secret associated with its own, unrelated organization. Because commit statuses feed `deployable_status`/CI-gating logic used to decide whether a commit is deployable, this can be used to make a victim commit appear green and deployable when it should not be, i.e. it can influence an unauthorized deploy decision on a stack the attacker does not own — matching the "unauthorized deploy" Critical impact category.

### Likelihood Explanation
This requires an attacker to control a distinct organization/tenant that is legitimately registered with the Shipit instance (its own webhook secret), but requires nothing further — no token, no repository write access to the victim, and no privileged Shipit account. In any multi-tenant deployment of this engine (which is the documented use case — multiple GitHub organizations/repositories registered against one Shipit instance), this is directly reachable by any onboarded, otherwise-unprivileged tenant.

### Recommendation
`StatusHandler#process` (and any other handler that does not use `Handler#stacks`) should scope its lookup to commits belonging to a repository that matches the authenticated `repository_owner`/organization from `verify_signature`, e.g. by joining through `Stack -> Repository` and filtering on `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, or otherwise reject the event if the payload's declared repository does not belong to the authenticating organization.

### Proof of Concept
1. Attacker's organization `attacker-org` is a legitimate tenant of the shared Shipit instance with `webhook_secret = S`, registered as `Shipit::GithubHook` (as in `test/fixtures/shipit/github_hooks.yml`).
2. Attacker crafts a `status` event JSON body: `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim-commit-sha>", "state": "success", "context": "ci/forged"}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, raw_body)` using their own known secret `S`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and verifies successfully because the signature was computed with the correct (attacker's own) secret — see `app/controllers/shipit/webhooks_controller.rb:24-30`.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — see `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` — writing a forged `success` status onto the victim's commit despite the request never having been authenticated by the victim organization's secret.
