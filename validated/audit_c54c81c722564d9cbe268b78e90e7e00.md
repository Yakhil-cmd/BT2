### Title
Webhook signature verification unconditionally trusts unsigned requests when an org has no `webhook_secret` configured - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` before ever inspecting `X-Hub-Signature` or `request.raw_post` whenever the organization's `webhook_secret` is blank. Combined with `docs/setup.md` explicitly documenting the webhook secret as *optional*, this lets anyone POST an arbitrary `membership` payload to `/webhooks` for such an org and have `Webhooks::Handlers::MembershipHandler#process` create/mutate `Team` and `Membership` records, potentially satisfying `User#authorized?` and granting access to `Shipit.github_teams`-gated resources.

### Finding Description
The claimed binding is: *signature-verified == HMAC(webhook_secret, raw_post) matches X-Hub-Signature*. The actual code breaks this equality: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret

  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'

  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

`return true unless webhook_secret` executes *before* `signature.split` and before `message` (i.e. `request.raw_post`) is ever hashed. If the configured `Shipit.github(organization:)` for the target org has no `webhook_secret` set, the function returns `true` for literally any header value — even `nil`, an empty string, or `sha256=garbage` — without ever computing an HMAC. This is not a "sha1-only, no-secret bypass" corner case as much as a complete short-circuit: the split/algorithm check is dead code in the no-secret path.

`app/controllers/shipit/webhooks_controller.rb#verify_signature` calls this method directly and only checks `head(422) unless verified`: [2](#0-1) 

No other guard exists: `check_if_ping` and `drop_unhandled_event` only gate on event type, not authenticity, and `verify_authenticity_token` is explicitly skipped: [3](#0-2) 

If verification passes, `create` parses the raw attacker body and dispatches it straight to handlers, e.g. `Handlers::MembershipHandler`: [4](#0-3) [5](#0-4) 

That handler unconditionally does `Team.find_or_create_by!(github_id: params.team.id)` and, on `action: 'added'`, `team.add_member(User.find_or_create_by_login!(params.member.login))`: [6](#0-5) 

`webhook_secret` is documented as optional and shipped as `nil` in example configs: [7](#0-6) [8](#0-7) 

so this is a realistic, not merely theoretical, deployment state.

**Escalation path**: `User#authorized?` gates Shipit login/access purely on team membership matching `Shipit.github_teams`: [9](#0-8) 

If the attacker knows (or guesses) the numeric GitHub team id of a team configured in `oauth.teams` for an org lacking `webhook_secret` (team ids/slugs are discoverable via the public GitHub API for orgs with public team pages, or by brute-forcing small integers), they can forge a `membership` `added` event naming that `team.id` and any GitHub login of their choosing as `member.login`. `find_or_create_by_login!` will call `Shipit.github.api.user(login)` to fetch public profile data for that login (no auth of the requester needed), create a local `User`, and add it to the `Team` — satisfying `authorized?` for that user without ever going through OAuth.

None of the listed guards intervene: `drop_unhandled_event` doesn't block `membership`, the `ExplicitParameters` schema on `MembershipHandler` only validates shape not origin, and `force_github_authentication`/`require_permission!` are controller-level concerns for the web UI, not for `/webhooks`.

### Impact Explanation
An attacker who identifies a Shipit-configured organization/app without a `webhook_secret` can, without any credentials, forge `membership` (and by the same bypass, `push`, `pull_request`, `status`, `check_suite`) webhook events for that org. For `membership` specifically, this allows fabricating `Team`/`Membership` rows, which — if that team is part of `Shipit.github_teams` — grants an attacker-chosen GitHub account authorization into the Shipit application (escalation into `Shipit.github_teams` authorization space, matching the High severity category). It is fully repeatable against any org/app entry lacking `webhook_secret` and requires only knowledge of a target team id.

### Likelihood Explanation
Preconditions: the target org's GitHub App config in `Shipit.github(organization:)` must have no `webhook_secret` set — explicitly supported and documented as optional. No Shipit session, API token, or GitHub secret is needed by the attacker; only an HTTP client and the target org's slug/team id. Team ids are often discoverable via public GitHub org team pages or the GitHub API. This is operator-misconfiguration-dependent but is a supported, documented configuration, not a hypothetical.

### Recommendation
Require `webhook_secret` to be present for all configured GitHub Apps/orgs (fail closed instead of `return true unless webhook_secret`), or explicitly reject webhook processing entirely when no secret is configured rather than treating it as "verified". Additionally, support/require `sha256=` (GitHub's current default) and always perform a constant-time compare rather than short-circuiting before any hashing.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "membership webhook is accepted and mutates Team/Membership when org has no webhook_secret" do
  # Arrange: an org whose GitHubApp has no webhook_secret configured
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(
    Shipit::GitHubApp.new('no-secret-org', { webhook_secret: nil })
  )

  @request.headers['X-Github-Event'] = 'membership'
  # No X-Hub-Signature header at all, and body arbitrary/attacker-controlled
  body = {
    action: 'added',
    team: { id: 999_999, name: 'Fake Team', slug: 'fake-team', url: 'http://example.com' },
    organization: { login: 'no-secret-org' },
    member: { login: 'attacker-login' }
  }.merge(repository: { owner: { login: 'no-secret-org' } }).to_json

  assert_difference -> { Shipit::Team.count }, 1 do
    post :create, body:, as: :json
    assert_response :ok
  end

  team = Shipit::Team.find_by(github_id: 999_999)
  assert team.present?
  assert team.members.exists?(login: 'attacker-login')
end
```
Binding checked before/after: expected `verify_signature == HMAC_SHA1(webhook_secret, raw_post) == provided_signature`; actual behavior observed is `verify_signature == true` regardless of `raw_post`/`X-Hub-Signature` whenever `webhook_secret` is nil, proven by the `Team`/`Membership` row being created purely from an unsigned, unauthenticated request.
