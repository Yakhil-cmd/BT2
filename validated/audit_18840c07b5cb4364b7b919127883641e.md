### Title
Cross-repository webhook forgery via `no-secret organization` verification bypass lets attacker inject labels into a victim's continuous-deployment ReviewStack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` config used to verify the HMAC signature by reading `repository.owner.login` from the attacker-controlled JSON body, while `LabelCapturingHandler#repository` (and every other `pull_request` handler) resolves the *actual target repository/stack* from a separate field of the same body, `repository.full_name`. These two fields are never checked for consistency, so an attacker can pick an organization that is configured in Shipit with no `webhook_secret` to satisfy `verify_webhook_signature`, while pointing `full_name` at an unrelated, secret-protected victim repository/stack.

### Finding Description
The broken binding: the code implicitly assumes
`params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`
i.e., that the organization used to authenticate the webhook is the same organization that owns the repository the handler will mutate. This is never enforced.

- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and passes it to `Shipit.github(organization: repository_owner)` to fetch a `GitHubApp` instance, then calls `verify_webhook_signature` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` immediately `unless webhook_secret`, i.e., if the selected org's config has no `webhook_secret` configured, no HMAC is checked at all [3](#0-2) .
- After the signature "check" passes, `WebhooksController#create` dispatches the entire raw body to handlers [4](#0-3) .
- `LabelCapturingHandler#repository` resolves the target repository using a *different* field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , and `review_stack`/`stack` locate the `ReviewStack` under that repository by `environment` (`pr#{number}`) [6](#0-5) .
- On `action == "opened"` with an existing stack, `capture_labels` persists `params.pull_request.labels.map(&:name)` onto the resolved stack's `PullRequest` record [7](#0-6) .

Exploit flow: the attacker crafts a `pull_request` `action=opened` JSON body where `repository.owner.login` = `"attacker-controlled-org"` (an org configured in Shipit's GitHub app config with a blank/absent `webhook_secret`) but `repository.full_name` = `"victim-org/victim-repo"` (the real, secret-protected victim repository that has a live PR / `ReviewStack` with `continuous_deployment: true`), and sets `pull_request.number`/`labels` to match an existing open PR's `pr#{number}` environment. `verify_signature` looks up the GitHub app config for `"attacker-controlled-org"`, finds no `webhook_secret`, and returns `true` unconditionally — no HMAC of any kind is checked, even though the payload's *actual* target (`full_name`) belongs to an org that does have a secret configured. `LabelCapturingHandler` then finds `victim-org/victim-repo`'s `ReviewStack` and overwrites its `PullRequest#labels`.

This bypasses the invariant "a webhook event only affects the repository/stack whose secret authenticated it" because the code authenticates against one attacker-chosen field (`repository.owner.login`) but acts on a different attacker-chosen field (`repository.full_name`); nothing ties them together, and there is no re-validation inside `LabelCapturingHandler` (or `ReviewStackAdapter`) that the authenticated organization matches the resolved repository's owner.

### Impact Explanation
This is a payload for one repository (the attacker's own, no-secret org) mutating another repository's stack — the class of impact explicitly called out as Critical in the rules ("a payload for one repository mutating another's stack, commit, task or team"). Concretely: `PullRequest#labels` for the victim's `ReviewStack` is overwritten with attacker-chosen names. `ReviewStack#env` merges these labels (uppercased) into the environment passed to deploy tasks, and because the target stack has `continuous_deployment` enabled, any newly green commit is auto-deployed via `ContinuousDeliveryJob` using that attacker-poisoned environment — giving the attacker partial control over environment variables injected into the victim's deploy command without ever authenticating against the victim organization's actual `webhook_secret`. The attack is repeatable against any stack whose owning organization the attacker can enumerate, provided some other configured org in the same Shipit instance has no `webhook_secret` set.

### Likelihood Explanation
Preconditions: (1) Shipit must have at least one configured GitHub organization with no `webhook_secret` (the "no-secret organization" precondition named in the question) — attacker needs no credentials for that org, just needs Shipit to be configured with it; (2) the victim stack must be a `ReviewStack` with an open PR and `continuous_deployment` enabled; (3) attacker must guess/know the victim PR number to hit the right `environment` (`pr#{number}`), which is easily discoverable since PRs are public. Attacker cost is a single unauthenticated `POST /webhooks` HTTP request with a crafted JSON body — no secrets, no session, no GitHub App credentials required. This is highly feasible and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature`, and/or in every `pull_request`/`push`/etc. handler, enforce that the organization used to select/verify the webhook signature is derived from — and matches — the same `repository.full_name`/`owner` used to resolve the target `Repository`/`Stack`. Concretely: derive `repository_owner` strictly from `repository.full_name.split('/').first` (never from a separate `owner.login` subtree), and reject the webhook if `repository.owner.login` (when present) disagrees with the owner segment of `full_name`. Additionally, do not treat a blank `webhook_secret` as "verification not required" for organizations serving real webhook traffic — require every configured organization handling incoming webhooks to have a `webhook_secret`, or fail closed rather than open when it's absent.

### Proof of Concept
Minitest plan (under `test/controllers/webhooks_controller_test.rb`, no live GitHub, following existing patterns in that file):

1. Configure two orgs in test config: `"no-secret-org"` with no `webhook_secret`, and `"victim-org"` with a real `webhook_secret`.
2. Create a `Shipit::Stack`/`Shipit::ReviewStack` fixture under `victim-org/victim-repo` with `environment: "pr42"`, `continuous_deployment: true`, and an associated `PullRequest` with `labels: []`.
3. Build a `pull_request` `action=opened` JSON payload where:
   - `repository.owner.login = "no-secret-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `pull_request.number = 42`, `number = 42`
   - `pull_request.labels = [{name: "MALICIOUS_ENV_KEY"}]`
   - no `X-Hub-Signature` header (or an arbitrary bogus one)
4. POST to `/webhooks` with `X-Github-Event: pull_request`.
5. Assert response is `200 OK` (not `422`), proving signature verification passed despite no valid HMAC for `victim-org`.
6. Assert the equality-check side: before the request, `victim_stack.pull_request.labels == []`; after the request, `victim_stack.reload.pull_request.labels == ["MALICIOUS_ENV_KEY"]` — demonstrating the payload authenticated under `no-secret-org`'s (non-)secret mutated `victim-org`'s stack, violating the stated invariant.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
