### Title
Forged `pull_request` `unlabeled` webhook lets any configured-org sender manipulate another org's review stack via decoupled `repository_owner`/`repository.full_name` fields - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC verifier using `repository_owner`, which falls back from `repository.owner.login` to `organization.login` when the former is absent [1](#0-0) . `UnlabeledHandler` and `ReviewStackAdapter`, however, resolve the target repository/stack purely from `params.repository.full_name`, which is a schema field completely independent of `organization.login` [2](#0-1) [3](#0-2) . A sender who controls (or whose org has no) `webhook_secret` for one tenant can therefore pass signature verification for their own org while the payload's `repository.full_name` names an entirely different tenant's repository, causing the handler to archive/unarchive that other tenant's review stack.

### Finding Description
The broken binding is: `organization_that_verified_signature == organization_that_owns_the_mutated_repository`. Trace:

1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [4](#0-3) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank — an explicitly supported/documented "optional" configuration [5](#0-4) .
3. `UnlabeledHandler`'s `params` schema only `requires :repository do requires :full_name, String end` — it never requires or cross-checks `repository.owner.login` against the org used for signature verification [2](#0-1) .
4. `repository` in the handler is resolved solely via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) , and `ReviewStackAdapter#stack`/`#repo_name` likewise derive everything from `params.repository["full_name"]` and `params.number` [7](#0-6) [3](#0-2) .

Exploit: attacker crafts a JSON body with `organization.login = "attacker-org"` (an org configured in this Shipit deployment's multi-org `github:` secrets block with no `webhook_secret`, per the documented "Using Multiple Github Applications" setup) and `repository = {"full_name": "victim-org/victim-repo"}` with no `owner` sub-object, plus a valid `pull_request`/`labels`/`sender` structure satisfying the handler's schema, `action: "unlabeled"`, and header `X-Github-Event: pull_request`. `repository_owner` resolves to `"attacker-org"`, `verify_signature` trivially passes (no secret to check), and `UnlabeledHandler#process` runs against `victim-org/victim-repo`'s review stack, calling `stack.archive!`/`stack.unarchive!` — writing state for a repository that never authenticated the request.

None of the existing guards stop this: `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema never requires `repository.owner.login`; there is no post-verification assertion tying `repository_owner` to `params.repository.full_name`'s owner.

### Impact Explanation
An attacker who only controls one under-secured (or no-`webhook_secret`) organization in a multi-tenant Shipit deployment can archive or unarchive review stacks belonging to any other organization/repository hosted on the same instance, purely by crafting the JSON body — no valid GitHub signature for the victim org is needed. This is a cross-tenant/cross-repository state-mutation bug matching the "Critical" impact category (one repo's payload writes another repo's records), since it deprovisions/reprovisions infrastructure (`stack.deprovision`, `Shipit::ReviewStackProvisioningQueue.add`) tied to the victim's PR review stack. It is repeatable against any repository whose `full_name` the attacker can guess/know, for as long as the attacker's own org lacks a properly random `webhook_secret` or the attacker has that secret.

### Likelihood Explanation
Requires the Shipit instance to be configured in the documented multi-organization mode (`secrets.github` keyed by org name) with at least one org (the attacker's) having no `webhook_secret` set, or the attacker knowing that org's secret. Given the docs explicitly present `webhook_secret` as "optional", this is a plausible real-world configuration. The attacker needs no Shipit session, API token, or GitHub App key — only the ability to POST to `/webhooks` and knowledge of a valid target `repository.full_name`. This makes the attack low-cost and repeatable.

### Recommendation
Do not let `repository_owner` (verifier selection) diverge from the org that actually owns `repository.full_name`. Options: (1) always require `repository.owner.login` in the schema for handlers that mutate state and use it — not `organization.login` — for verifier selection; (2) after verification, assert that the resolved `repository`'s owner matches `repository_owner`/the verified org before invoking handlers; (3) disallow/deprecate `webhook_secret`-less org configs, or require non-blank secrets in all multi-org deployments.

### Proof of Concept
Minitest ActionDispatch::IntegrationTest sketch:
```ruby
test "forged unlabeled webhook via organization fallback mutates unrelated repo's stack" do
  # configure two orgs: "attacker-org" (no webhook_secret) and "victim-org" (has a stack/review_stack)
  victim_stack = shipit_review_stacks(:some_victim_review_stack) # owned by victim-org/victim-repo

  body = {
    action: "unlabeled",
    number: victim_stack.pull_request... , # matches environment pr#
    pull_request: { ... state: "open", head: { sha: "...", ref: "..." }, user: { login: "attacker" },
                     assignees: [], labels: [] },
    repository: { full_name: "victim-org/victim-repo" }, # no owner.login
    organization: { login: "attacker-org" },
    sender: { login: "attacker" }
  }.to_json

  post "/webhooks", params: body, headers: {
    "X-Github-Event" => "pull_request",
    "X-Hub-Signature" => "sha1=deadbeef", # arbitrary, unverifiable secret is absent for attacker-org
    "Content-Type" => "application/json"
  }

  assert_response :ok
  # equality check that should have held but didn't:
  assert_not_equal "attacker-org", victim_stack.repository.owner
  victim_stack.reload
  assert victim_stack.archived? # or unarchived, depending on provisioning_behavior
end
```
This demonstrates `repository_owner` ("attacker-org", used to select the verifier) diverging from the actual repository owner ("victim-org", used by the handler), with the handler mutating the victim's stack despite the attacker never presenting victim-org's `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
