### Title
`in_data_feed` accepts unconfirmed data-feed values from units that have not passed the `sequence='good'` conflict check - ([File: data_feeds.js])

### Summary
The CVE describes Unbound trusting a primary hostname's DNS answer as valid (and treating it as the authoritative XFR source for a whole RPZ zone) even when that answer is DNSSEC-BOGUS, i.e. it skips a required validity check before granting trust. In ocore's `dataFeedExists()` (backing the oscript `in_data_feed` operator, reachable from any AA definition/trigger), the same class of bug exists: unstable data-feed messages are scanned and treated as authoritative feed values for AA logic without checking `objUnit.sequence === 'good'`, unlike the sibling function `readDataFeedValue()` which does perform that check.

### Finding Description
`in_data_feed` in `formula/evaluation.js` calls `dataFeeds.dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, mci, bAA, cb)` [1](#0-0) .

Inside `dataFeedExists`, when `bAA` is true, the function iterates `storage.assocUnstableMessages` for candidate units and applies only three filters — `objUnit.bAA`, `latest_included_mc_index` bounds, and author-address intersection — before treating any `data_feed` message found in that unit as a valid match: [2](#0-1) 

Notice it never checks `objUnit.sequence`. Compare this to `readDataFeedValue()`, the function used for the plain `data_feed[[...]]` getter, which explicitly filters out units whose `sequence` is not `'good'`: [3](#0-2) 

`sequence` marks whether a unit is the winner ('good') or loser ('final-bad'/'temp-bad') of a double-spend/non-serial conflict; a 'bad' unit's payload must not be treated as authoritative because it will never be applied to state (its data-feed message will never be indexed into the stable KV store `df\n...` keys once serialization resolves the conflict). By omitting this check, `dataFeedExists()`/`in_data_feed` accepts a losing, to-be-discarded unit's declared data-feed value as if it were confirmed — directly analogous to Unbound accepting a BOGUS (unvalidated/losing) DNS answer as if it were a trusted source.

### Impact Explanation
An oracle address (or any address referenced in an `in data feed` address-definition clause or an AA's `in_data_feed[[...]]` formula check) can be made to author two conflicting units in the same batch: one "good" unit with a legitimate/expected feed value, and one "bad" (losing, non-serial) unit carrying an attacker-favorable feed value for the same `feed_name`. While the conflicting unit is still unstable, `in_data_feed` will report `true`/match on the basis of the doomed unit's payload, even though this value will never be durably committed to the data-feed store. Any AA trigger, address-definition unlock condition (`in data feed`), or asset-transfer condition gated by `in_data_feed` evaluated during this unstable window can be spent/unlocked, releasing AA funds or unlocking payment conditions based on a value that has no lasting validity — leading to unauthorized fund release/loss from an AA or a payment output unlocked under a bogus, non-final condition. This satisfies "AA fund loss" / "unauthorized spending" impact criteria.

### Likelihood Explanation
This requires only that the address referenced as an oracle in `in_data_feed`/`in data feed` be controlled (or influenced) by the attacker, and that they post two conflicting units — an action any ordinary unit poster can perform (no privileged network/hub role needed), matching the required "unprivileged AA trigger sender / unit poster" reachability. The condition window is narrow (must be exploited while the conflicting units are unstable and before serialization resolves it), giving Medium likelihood, consistent with the CVE's own Medium/AC:H rating (attack requires timing/spoofing conditions).

### Recommendation
Add the same `objUnit.sequence !== 'good'` guard used in `readDataFeedValue()` to the `bAA` branch of `dataFeedExists()` in `data_feeds.js`, so that `in_data_feed` only considers unstable units whose sequence is confirmed 'good' before treating their data-feed payload as a match.

### Proof of Concept
1. Attacker controls address `ORACLE` referenced by an AA/definition as `in_data_feed[[oracles=ORACLE, feed_name='price', feed_value>100]]` (or an `in data feed` address-definition clause with the same predicate).
2. Attacker crafts two units from `ORACLE` that spend the same input (double-spend/non-serial), both containing `data_feed` messages with `feed_name='price'`: unit A (eventually 'good') with `price=50`, unit B (eventually 'final-bad') with `price=200`.
3. Attacker broadcasts both units so they are momentarily unstable in `storage.assocUnstableMessages`.
4. Attacker immediately triggers the AA (or posts the unit relying on the `in data feed` unlock condition) referencing `in_data_feed[[..., feed_value>100]]`. Because `dataFeedExists()` scans all unstable messages from `ORACLE` without checking `sequence`, it finds unit B's `price=200` and returns `true`, even though unit B is a losing/non-serial unit that will never be written into the stable data-feed KV store [4](#0-3) .
5. The AA/unlock condition executes as if `price>100` were confirmed truth, releasing funds/unlocking outputs that should not have been released once the conflict finally resolves in favor of unit A (`price=50`).
