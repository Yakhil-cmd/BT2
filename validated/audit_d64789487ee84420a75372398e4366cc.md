### Title
Unchecked-invariant subtraction in `get-rewards` can underflow and permanently brick `calculate-rewards`, freezing sBTC rewards - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s reward accounting relies on a Clarity subtraction, `(- current-balance total-staked-sbtc cur-reserve)`, whose safety depends entirely on an off-chain-maintained invariant (`current-balance >= total-staked-sbtc + cur-reserve`) that is never asserted anywhere in the contract. Clarity integers are checked at the VM level — exactly like Solidity ≥0.8 — so any drift that makes the accounted staked/reserve total exceed the real sBTC balance causes an unrecoverable abort, mirroring the `FullMath.sol` underflow pattern in the referenced report.

### Finding Description
`get-rewards` computes the pool of undistributed sBTC by subtracting the internally tracked `total-staked-sbtc` and `reserve-balance` from the live `sbtc-token` balance of the contract: [1](#0-0) 

`get-new-rewards` and `calculate-rewards` both depend transitively on this value: [2](#0-1) 

`calculate-rewards` is the *only* entry point in the contract that mints/apportions sBTC yield to bonds and stakers, and it is gated so it can be called by any principal (`sender` in the fuzz command harness is drawn from arbitrary accounts, not an admin) once per half-cycle: [3](#0-2) 

Like Solidity ≥0.8's checked arithmetic that turned the UniswapV3 `FullMath.sol` "phantom overflow" trick into a guaranteed revert whenever `sqrtRatioX96 < sqrtRatioAX96`, Clarity's built-in checked subtraction turns any bookkeeping drift between `total-staked-sbtc + reserve-balance` and the *actual* `sbtc-token` balance held by `pox-5` into a guaranteed abort of `get-rewards`. Because `calculate-rewards` is unconditionally called through this path, once the invariant is violated **every future call to `calculate-rewards` reverts**, permanently halting reward accrual/distribution for all bonds and all STX stakers — there is no admin recovery path (unlike `pause-rewards`, which only stops payouts intentionally; here the failure is silent and unrecoverable via normal contract flow, requiring a hard fork per the contract's own comments on `pause-rewards`): [4](#0-3) 

### Impact Explanation
If the underflow condition is ever reached, `calculate-rewards` reverts for every subsequent caller, permanently freezing distribution of the sBTC rewards accumulated in the contract to bond holders and STX stakers. This matches the "Critical — permanent freezing of staked STX or sBTC ... double-counting a commitment or reward" / "High — permanent freezing of reserve or fees" impact tiers: unlike the original report where only the depositor calling into a bad price range is frozen, here a single miscount freezes the reward pipeline for **every** participant in the protocol, since `calculate-rewards` is a shared, non-bypassable choke point.

### Likelihood Explanation
The invariant `current-balance >= total-staked-sbtc + cur-reserve` is not enforced by any `asserts!` in the visible reward-calculation code; the contract simply trusts that `total-staked-sbtc` (an internal counter incremented/decremented on stake/unstake) and `reserve-balance` (incremented every `calculate-rewards` call) always stay in lock-step with the real token balance reported by the external `sbtc-token` contract. I was not able to fully trace the unstake/withdraw code paths that decrement `total-staked-sbtc` within the tool budget available, so I cannot give a concrete, fully-proven call sequence that drives the two out of sync (e.g., a rounding mismatch between the sats amount proven via L1 merkle-lockup and the sBTC actually credited by the bridge, or a partial-unstake that removes more/less accounting than the token amount actually transferred out). This is the same class of "silent invariant, checked-math abort" bug as the reported finding, but confirming an unprivileged, concretely reachable trigger requires reviewing the full stake/unstake and L1-lockup-crediting logic, which was not completely available in this pass.

### Recommendation
- Add an explicit `asserts!` in `get-rewards`/`get-new-rewards` that fails gracefully (returns a typed error rather than aborting via arithmetic) when `current-balance < total-staked-sbtc + cur-reserve`, and audit every code path that mutates `total-staked-sbtc` or `reserve-balance` to guarantee they can never diverge from the real `sbtc-token` balance (including rounding on stake/unstake and any peg-in/peg-out amount deltas).
- Consider using `saturating`-style helpers (e.g., clamp to zero) instead of relying on the raw checked `-` so a transient mismatch degrades to "zero new rewards this cycle" rather than a hard, contract-wide, permanent revert.

### Proof of Concept
Not fully constructible from the code reviewed in this pass — the stake/unstake and L1-lockup crediting functions that mutate `total-staked-sbtc` were not located within the available search budget, so a concrete unprivileged trigger sequence could not be confirmed. The finding is reported based on the exact-match bug class (checked-arithmetic subtraction on an unenforced invariant, permanently bricking a shared reward-distribution entry point) found at [5](#0-4) .
