### Title
Wallet payments to AA addresses skip the bounce-fee safeguard outside `sendMultiPayment()`, risking permanent fund loss to an unresponsive AA - (File: composer.js / aa_addresses.js)

### Summary
The external report criticizes `Vault.sol` for calling raw `mint()` instead of `_safeMint()`, which would have verified that the receiving contract can actually accept and process the token, preventing silently-stuck/lost assets. `ocore` has an analogous "receiver-capability" safeguard for its own actor model: before a wallet sends bytes/assets to an address that turns out to be an Autonomous Agent (AA), `aa_addresses.checkAAOutputs()` is supposed to verify that the payment includes at least the AA's declared `bounce_fees`, because an AA that receives less than its bounce fee cannot construct a bounce response and the funds become permanently stuck in the AA's balance with no way to return them to the sender [1](#0-0) . This check is explicitly wired into `wallet.sendMultiPayment()` [2](#0-1) , but it is not universally enforced for every payment-composition code path that can target an AA address.

### Finding Description
`checkAAOutputs()` loads the AA definitions for all output addresses of a payment and, for any that are AAs, ensures the payment amount for each asset covers `bounce_fees` (defaulting to `constants.MIN_BYTES_BOUNCE_FEE` if unset) [3](#0-2) . If insufficient, it throws a `MissingBounceFeesErrorMessage`. This is the "safe guard" equivalent of `_safeMint()`: it verifies the receiver (the AA) is actually capable of handling the incoming message (specifically, capable of bouncing it back if it decides to reject it).

However, this guard is only invoked from `wallet.sendMultiPayment()`, gated behind the `opts.aa_addresses_checked` flag [2](#0-1) . Any other caller that composes and sends a payment unit directly (e.g. through `composer.js`'s lower-level joint composition functions, light wallet flows, or callers that build `arrPayments`/outputs without routing through `sendMultiPayment`) bypasses `checkAAOutputs()` entirely. Unlike the AA-to-AA transfer path in `aa_composer.js`, which is protected by its own internal `bounce_fees` accounting during `handleTrigger`/`bounce()` [4](#0-3) , a plain wallet-composed unit that sends fewer bytes than an AA's declared `bounce_fees.base` to an AA address will validate and stabilize successfully under `validation.js`'s generic payment/output rules (which only check address validity and balance conservation, not AA bounce-fee sufficiency) [5](#0-4) . Once stabilized, the AA is triggered, cannot generate a bounce (the trigger's `bounce_fees.base` is unmet), and per the bounce logic will simply return `finish(null)` without refunding — the funds are absorbed into the AA's balance with no path back to the sender [6](#0-5) .

This mirrors the sandclock bug class precisely: a value-transfer function (`mint()`/wallet payment composition) omits the safety check that a companion function already implements correctly (`_safeMint()`/`checkAAOutputs()`), and the omission is only caught if the caller happens to go through the "safe" path.

### Impact Explanation
Funds (bytes or assets) sent to an AA address without meeting its declared `bounce_fees` are irrecoverably absorbed into that AA's on-chain balance. Depending on the AA's logic, this can constitute a permanent, unintended loss of user funds — the AA has no way to identify or return an under-funded trigger since it never generated a response/bounce unit for it. This is a concrete "AA fund loss" scenario as required by the validation rubric, reachable by any unprivileged user composing a payment through a path that doesn't call `checkAAOutputs()`.

### Likelihood Explanation
Likelihood depends on how consistently every payment-composing code path (light wallet API consumers, third-party integrations building units via `composer.js` directly, CLI tools, textcoin flows, etc.) routes through `wallet.sendMultiPayment()`. Given that `checkAAOutputs` is called from exactly one place in the codebase, any alternate composition path is exposed. Since AA addresses are publicly known/discoverable and their `bounce_fees` are public in their definitions, an attacker or careless integrator could trivially trigger this by sending marginally-insufficient bytes to a real AA through a non-guarded path.

### Recommendation
Move the `checkAAOutputs()` safeguard down into the shared, low-level payment/joint composition routine in `composer.js` (analogous to always using `_safeMint()` instead of relying on each caller to opt in), so that every payment output destined for a known AA address is checked for bounce-fee sufficiency regardless of which higher-level API (`sendMultiPayment`, direct composer calls, light-wallet flows) initiated it. Alternatively, add a validation-time check (in `validation.js`) that flags/blocks non-AA-trigger units sending sub-bounce-fee amounts to AA addresses, providing a network-level backstop independent of client-side wallet logic.

### Proof of Concept
1. Identify a live AA address whose definition declares `bounce_fees: { base: 10000 }` (as used throughout the AA test suite, e.g. `secondary_aa` in `test/aa_composer.test.js`) [7](#0-6) .
2. Compose and broadcast a payment unit directly via `composer.js` (or any code path that does not call `wallet.sendMultiPayment` with `aa_addresses_checked` unset) sending, e.g., 5000 bytes to that AA address — below its 10000-byte bounce fee.
3. The unit passes `validatePaymentInputsAndOutputs` normally (balance conservation and valid address are the only base-asset checks) [8](#0-7)  and stabilizes.
4. When the AA is triggered, `bounce()` finds `trigger.outputs.base (5000) < bounce_fees.base (10000)` and calls `finish(null)` without any refund message [9](#0-8) , permanently crediting the 5000 bytes to the AA's balance with the sender unable to reclaim them.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
