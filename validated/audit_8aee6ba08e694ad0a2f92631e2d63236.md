### Title
Concurrent `RemoveGovAfter` / `AddGov` Race Corrupts `governanceDataBlockNums` DB Index, Causing Persistent Governance State Loss After Restart — (`kaiax/gov/headergov/impl/rewind.go`)

---

### Summary

`RemoveGovAfter` iterates `h.governances` without holding `h.mu`, then writes the DB index and reconstructs `h.history` under two separate, non-atomic lock acquisitions. A concurrent `HandleGov` (called from `PostInsertBlock`) can insert a new governance entry between those two steps, causing `RemoveGovAfter` to overwrite the DB index without the new entry while `h.history` is rebuilt with it. The resulting DB/in-memory divergence is permanent: after a node restart, `readGovDataFromDB` loads only what is in the DB index, so the governance entry is silently dropped, and `GetParamSet` returns stale parameter values for all subsequent blocks.

---

### Finding Description

**`RemoveGovAfter` — three distinct locking defects:**

**Defect 1 — unlocked map iteration (Go data race).** [1](#0-0) 
Line 43 ranges over `h.governances` with no lock held. `AddGov` writes to the same map under `h.mu.Lock()`. [2](#0-1) 
The Go runtime detects concurrent map read/write and panics; `-race` flags it as a data race.

**Defect 2 — per-element lock/unlock inside the iteration.** [3](#0-2) 
Each deletion acquires and immediately releases `h.mu`, leaving the map unprotected between iterations and between the loop and the subsequent DB write.

**Defect 3 — non-atomic DB write + history reconstruction.** [4](#0-3) 
After the loop, `WriteGovDataBlockNums` is called with the snapshot returned by `h.GovBlockNums()`, then `h.mu` is re-acquired to rebuild `h.history`. These are two separate critical sections with a gap between them.

**Concurrent `HandleGov` path:** [5](#0-4) 
`HandleGov` calls `AddGov` (updates `h.governances` + `h.history` under lock), then calls `GovBlockNums()` + `WriteGovDataBlockNums` outside the lock.

### Impact Explanation

**Exact interleaving that produces persistent corruption:**

| Step | Actor | Action |
|------|-------|--------|
| 1 | `RemoveGovAfter` | Deletion loop completes |
| 2 | `RemoveGovAfter` | `h.GovBlockNums()` snapshots keys — **no entry N** |
| 3 | `AddGov` (concurrent) | Adds entry N to `h.governances`; rebuilds `h.history` with N |
| 4 | `HandleGov` (concurrent) | `GovBlockNums()` sees N; `WriteGovDataBlockNums` writes DB **with N** |
| 5 | `RemoveGovAfter` | `WriteGovDataBlockNums` with stale snapshot — **overwrites DB, removing N** |
| 6 | `RemoveGovAfter` | `GovsToHistory(h.governances)` — `h.governances` has N → `h.history` includes N |

After step 6: in-memory `h.history` contains N; DB `governanceDataBlockNums` does not.

On restart, `readGovDataFromDB` reads only block numbers listed in `governanceDataBlockNums`: [6](#0-5) 
Entry N is absent from the index, so it is never loaded. `GetParamSet` then returns the pre-N parameter set for all blocks in N's epoch and beyond: [7](#0-6) 

Affected parameters include `governance.unitprice`, KIP-71 base-fee bounds, `reward.mintingamount`, `reward.ratio`, and others — directly corrupting fee pricing and reward distribution.

---

### Likelihood Explanation

`RewindDelete` is triggered by chain reorgs, which arrive via P2P. `PostInsertBlock` is called during canonical block insertion, also driven by P2P. Both paths share only `h.mu` (the headergov-internal mutex), not a blockchain-level serialization lock. The timing window (between `GovBlockNums()` snapshot and `WriteGovDataBlockNums` in `RemoveGovAfter`) is narrow but real on any multi-core node experiencing a reorg concurrent with block insertion — a normal operational condition on a live network.

---

### Recommendation

Replace the piecemeal locking in both `RemoveGovAfter` and `RemoveVotesAfter` with a single lock held for the entire operation (iteration + deletion + DB write + history rebuild). The pattern used by `AddGov` — acquire once, do all work, release — is the correct model:

```go
func (h *headerGovModule) RemoveGovAfter(blockNum uint64) {
    h.mu.Lock()
    dirty := false
    for blockNumIter := range h.governances {
        if blockNumIter > blockNum {
            dirty = true
            delete(h.governances, blockNumIter)
        }
    }
    if dirty {
        h.history = headergov.GovsToHistory(h.governances)
    }
    h.mu.Unlock()

    if dirty {
        WriteGovDataBlockNums(h.ChainKv, h.GovBlockNums())
    }
}
```

The DB write can remain outside the lock (it is already serialized by the DB layer), but the snapshot passed to it must be taken while the lock is held.

```go
// go test -race -run TestRemoveGovAfterRace ./kaiax/gov/headergov/impl/
func TestRemoveGovAfterRace(t *testing.T) {
    h := setupModule() // pre-populate h.governances with entry at block 1000

    var wg sync.WaitGroup
    wg.Add(2)

    go func() {
        defer wg.Done()
        h.RemoveGovAfter(500) // rewind: delete entries > 500
    }()

    go func() {
        defer wg.Done()
        // simulate PostInsertBlock processing a block with governance at 600
        gov, _ := headergov.NewGovData(...).ToGovBytes()
        h.HandleGov(600, gov)
    }()

    wg.Wait()

    // Verify DB and in-memory are consistent
    dbNums := ReadGovDataBlockNums(h.ChainKv)
    memNums := h.GovBlockNums()
    assert.Equal(t, []uint64(dbNums), memNums, "DB/memory mismatch")
}
```
