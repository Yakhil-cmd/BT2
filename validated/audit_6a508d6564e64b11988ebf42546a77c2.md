### Title
Bridge ERC721 Delivery Uses Unsafe `_mint`/`transferFrom` Without Receiver Check, Permanently Freezing Bridged NFTs — (File: `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`handleERC721Transfer` in `BridgeTransferERC721` delivers bridged ERC721 tokens to `_to` using either `mintWithTokenURI` (which internally calls `_mint`) or `transferFrom`. Neither path verifies that the recipient contract implements `IERC721Receiver`. If `_to` is a contract that does not implement `onERC721Received`, the NFT is permanently frozen in that contract with no recovery path, because the bridge nonce is already consumed and the transfer is marked as handled before the delivery call.

---

### Finding Description

In `handleERC721Transfer`, after the operator vote threshold is reached and the nonce is finalized, the function delivers the ERC721 token via one of two paths:

```solidity
// modeMintBurn = true
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");

// modeMintBurn = false
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

**Path 1 — `mintWithTokenURI`**: This calls `_mint(to, tokenId)` in `ERC721MetadataMintable`, which is the bare unsafe mint. It does not call `_safeMint` and does not invoke `_checkOnERC721Received`. [2](#0-1) 

**Path 2 — `transferFrom`**: This is the explicitly-discouraged unsafe transfer variant. The OpenZeppelin `ERC721.sol` in this repo documents it as "Usage of this method is discouraged, use `safeTransferFrom` whenever possible." [3](#0-2) 

The `_checkOnERC721Received` guard — which calls `onERC721Received` on the recipient and reverts if the magic value is not returned — is only invoked by `safeTransferFrom` and `_safeMint`, neither of which is used here. [4](#0-3) 

Critically, the nonce accounting and state updates happen **before** the delivery call:

```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

// delivery happens after — but nonce is already consumed
if (modeMintBurn) { ... mintWithTokenURI ... }
else { ... transferFrom ... }
``` [5](#0-4) 

Once the nonce is consumed and the `HandleValueTransfer` event is emitted, the bridge considers the transfer complete. There is no retry or recovery mechanism.

---

### Impact Explanation

A user who specifies a contract address as `_to` on the source chain (e.g., a multisig, a DeFi vault, or any contract that does not implement `IERC721Receiver`) will have their bridged NFT permanently frozen in that contract on the destination chain. The token is minted or transferred successfully at the ERC721 level (ownership record updated), but the receiving contract has no mechanism to interact with or recover the token. The bridge nonce is consumed and the transfer is marked handled, so there is no re-execution path. This constitutes permanent loss of bridged ERC721 assets.

---

### Likelihood Explanation

The `_to` address is fully user-controlled — it is specified in the original `requestERC721Transfer` call on the source chain and relayed verbatim by the bridge operator. Any user who bridges an NFT to a contract address (multisig wallet, DAO treasury, DeFi protocol, smart contract account) that does not implement `IERC721Receiver` will trigger this. Contract-to-contract NFT bridging is a common and expected use case.

---

### Recommendation

**For `modeMintBurn = true`**: Replace `mintWithTokenURI` (which calls `_mint`) with a `safeMintWithTokenURI` variant that calls `_safeMint` instead, or add an explicit `_checkOnERC721Received` call after minting.

**For `modeMintBurn = false`**: Replace `transferFrom` with `safeTransferFrom`:

```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

Additionally, consider moving the nonce finalization to after the delivery call, or implementing a pull-based recovery mechanism so that failed deliveries can be retried.

---

### Proof of Concept

1. Alice owns NFT token ID `42` on the parent chain.
2. Alice calls `requestERC721Transfer(tokenAddress, contractVault, 42, "")` where `contractVault` is a contract that does not implement `IERC721Receiver`.
3. The source-chain bridge burns/locks the NFT and emits `RequestValueTransfer`.
4. The bridge operator calls `handleERC721Transfer(..., contractVault, ..., 42, ...)` on the destination chain.
5. The nonce is consumed and `HandleValueTransfer` is emitted.
6. In `modeMintBurn = true`: `mintWithTokenURI(contractVault, 42, uri)` → `_mint(contractVault, 42)` succeeds silently. Token ID 42 is now owned by `contractVault`, which has no `onERC721Received` and no way to transfer it out.
7. In `modeMintBurn = false`: `transferFrom(bridge, contractVault, 42)` succeeds silently. Same outcome.
8. Alice's NFT is permanently frozen. The bridge nonce is consumed. No recovery is possible. [6](#0-5) [7](#0-6) [8](#0-7)

    function _checkOnERC721Received(address from, address to, uint256 tokenId, bytes memory _data)
        internal returns (bool)
    {
        if (!to.isContract()) {
            return true;
        }

        bytes4 retval = IERC721Receiver(to).onERC721Received(msg.sender, from, tokenId, _data);
        return (retval == _ERC721_RECEIVED);
    }
