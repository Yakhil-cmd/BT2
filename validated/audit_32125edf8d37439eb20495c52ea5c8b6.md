### Title
StatusHandler#process matches commits by sha with no per-repository scope, allowing a validly signed status webhook for one repository to write Status records (and trigger CI/CD side effects) on commits belonging to a different stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire `commits` table, with no scoping to the repository that the webhook signature actually authenticated. Every other comparable handler (`CheckSuiteHandler`) explicitly scopes the query through `stacks` (which is derived from `payload['repository']['full_name']`), but `StatusHandler` does not use `stacks` at all.

### Finding Description
The binding that should hold is: **the set of `Commit` rows a status webhook is allowed to mutate == the set of commits belonging to the repository that the webhook's signature authenticated** (i.e. `commit.stack.repository == params.repository`). Tracing the code shows this binding is broken.

- `Handler#stacks` resolves the repository from the payload and scopes to that repository's stacks: `Repository.from_github_repo_name(repository_name)&.stacks`, and `repository_name` reads `payload.dig('repository', 'full_name')`. [1](#0-0) 
- `CheckSuiteHandler` correctly uses this scope: `stacks.where(branch: params.check_suite.head_branch).each { |stack| stack.commits.where(sha: ...) }`. [2](#0-1) 
- `StatusHandler#process`, by contrast, never calls `stacks` and queries the global `Commit` table by exact sha equality only: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2) 
- `Commit.by_sha`/`by_sha!`'s ambiguity guard (`AmbiguousRevision`) is irrelevant to this path, confirming the premise: `StatusHandler` never calls `by_sha`, so no ambiguity check applies regardless of prefix length. [4](#0-3) 

`WebhooksController#verify_signature` only proves the payload came from the GitHub org named in `payload['repository']['owner']['login']` — it does not constrain which `Commit` rows the handler is permitted to touch. [5](#0-4) 

**Exploit flow:** Git commit SHA1s are content-addressed and repository-independent. If the same commit object exists in two different repositories tracked by Shipit as separate stacks (a routine occurrence for forks, mirrors, subtree-shared history, or repos that were renamed/migrated and re-added as a new `Repository`/`Stack`), a legitimate GitHub `status` event fired for repo A (which the attacker can trigger merely by pushing/creating a status on their own fork, or by any CI system tied to repo A) will be validly signed for repo A only. Because `StatusHandler` performs an unscoped, exact-sha match, it applies the status to **every** `Commit` row across **all stacks/repositories** that happen to share that sha — including a completely unrelated stack B that never received or authenticated this webhook.

Writing a `Status` is not inert: `Status#after_create` calls `enable_ci_on_stack` and schedules `schedule_continuous_delivery` on the commit's stack. [6](#0-5) [7](#0-6) 
So a forged/foreign "success" status on stack B's shared commit can flip that commit into a deployable state and kick off continuous delivery there, i.e. an unauthorized deploy trigger on a stack the attacker's webhook never authenticated against.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate that the JSON is well-formed and signed by *some* organization; none of them restrict `StatusHandler`'s DB query to that organization's stacks, unlike `CheckSuiteHandler`.

### Impact Explanation
A webhook payload authenticated for repository A results in a `Status` row being written (and continuous-delivery scheduling triggered) against a `Commit` belonging to stack B, a different repository/tenant, whenever the two share an identical full-length commit sha. This is a cross-repository write ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy") and matches the Critical impact category. It is repeatable against any pair of stacks that happen to share a commit sha (forks, mirrors, monorepo splits, renamed/re-added repositories), each repeat webhook re-applying the same cross-tenant effect.

### Likelihood Explanation
The precondition (identical full 40-character sha shared across two Shipit-tracked repositories) is not attacker-controlled in the general "random collision" sense, but is realistic and attacker-obtainable in common configurations: forking a tracked repository, mirroring, or migrating a repository to a new name/owner while the old `Repository`/`Stack` row still exists in Shipit produces commits with identical shas across distinct `Repository` records. An attacker who controls (or can trigger CI/status events on) one of the two repositories can then generate a genuinely signed status webhook for a sha that also exists in the victim stack, at no cost beyond owning/forking a repo that is itself onboarded to Shipit. No Shipit secrets are needed.

### Recommendation
Scope `StatusHandler#process` through `stacks` exactly like `CheckSuiteHandler`, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, so a status webhook can only mutate commits belonging to the repository that the signature actually authenticated.

### Proof of Concept
In a new/existing test under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or similar):
1. Create `repo_a`/`stack_a` and `repo_b`/`stack_b` as distinct `Repository`/`Stack` records.
2. Create `Commit` rows in both stacks with the identical full-length sha (`sha = 'a' * 40`).
3. Build a payload whose `repository.full_name` matches `repo_a` only, with `sha` set to the shared sha and `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert `stack_a`'s commit gained a `Status` (expected) **and** assert `stack_b`'s commit *also* gained a `Status` despite the payload never referencing `repo_b` — demonstrating the cross-repository write.
6. Contrast with `Commit.by_sha!(shared_sha[0..5])` on an ambiguous-but-full-match scenario to show `AmbiguousRevision` would have been raised if that guard were used, but `StatusHandler` bypasses it entirely and still performs the cross-stack write.

```ruby
    def self.by_sha(sha)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (too short)" if sha.to_s.size < 6

      commits = where('sha like ?', "#{sha}%").take(2)
      raise AmbiguousRevision, "Short SHA1 #{sha} is ambiguous (matches multiple commits)" if commits.size > 1

      commits.first
    end

    def self.by_sha!(sha)
      by_sha(sha) || raise(ActiveRecord::RecordNotFound, "Couldn't find commit with sha #{sha}")
    end
```
