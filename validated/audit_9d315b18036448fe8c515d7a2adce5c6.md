### Title
Potential Proportional Reward Manipulation via Consensus Liquidity Spot Imbalance - ([File: kaiax/staking/staking_info.go])

### Summary
The Kaia reward module calculates staking rewards for validators proportionally based on their "excess" staking amounts (amount over a threshold). Since the Prague hardfork, this calculation includes Consensus Liquidity (CL) staking. The distribution logic uses the spot values of `StakingAmount` (from `CNStaking`) and `CLStakingAmount` (from `CLRegistry`) to split rewards between the validator's reward address and the CL pool. An attacker (a validator or a large staker) can manipulate these spot proportions by timing their CL staking/unstaking or CN staking deposits right before a block is finalized, causing a mismatch in intended reward distribution, analogous to the slippage/spot manipulation described in the external report.

### Finding Description
In the `kaiax/reward` module, specifically within `assignStakingRewards` and `assignStakingRewardsFlex`, the protocol distributes rewards to stakers. Since the Prague hardfork, if a validator has Consensus Liquidity (CL) configured, the reward is split between the validator and the CL pool using the `consolidatedNode.Split` function.

The `Split` function [1](#0-0)  performs a proportional calculation:
```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    // ...
    cnAmountBig := big.NewInt(int64(c.StakingAmount))
    clAmountBig := big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)
    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```
This calculation relies on the spot `StakingAmount` and `CLStakingAmount` values captured at `SourceNum(num) = num - 1` [2](#0-1) . Because there is no slippage protection or minimum reward guarantee for either recipient, a validator can manipulate the ratio by depositing or withdrawing from the CL registry or CN staking contract in the block immediately preceding the reward distribution. 

Furthermore, the conversion from `uint64` to `int64` using `big.NewInt(int64(...))` [3](#0-2)  is dangerous. If a validator's staking amount (in KAIA or kei) exceeds the `int64` maximum value (approx 9.22e18), the value will overflow into a negative number, corrupting the reward distribution logic.

### Impact Explanation
1.  **Reward Manipulation**: A validator can manipulate the spot reserves (staking amounts) to receive a higher proportion of rewards in their preferred address (e.g., reward address vs. CL pool) than their average staking contribution would justify.
2.  **Arithmetic Corruption**: The `uint64` to `int64` conversion in `Split` can lead to negative reward calculations if staking amounts are extremely large (e.g., in a high-inflation or testnet scenario), breaking the `reward.Sign() > 0` invariant and potentially causing the `Sub` operation to result in unintended balance increases or panics [4](#0-3) .

### Likelihood Explanation
The likelihood is medium. While manipulating the total validator set staking is difficult, manipulating one's own CL vs CN ratio is trivial for a validator. The arithmetic overflow is low likelihood on mainnet due to current KAIA supply but higher on specialized service chains or testnets with modified parameters.

### Recommendation
1.  **Slippage/Bounds Check**: Implement a check to ensure the reward split ratio does not deviate significantly from a moving average or a user-defined expected ratio.
2.  **Safe Conversion**: Use `new(big.Int).SetUint64(...)` instead of `big.NewInt(int64(...))` to avoid potential overflow during the conversion from `uint64` to `big.Int`.
3.  **Snapshotting**: Use a longer delay or an average of staking amounts over multiple blocks to calculate distribution ratios, making front-running less effective.

### Proof of Concept
1.  Validator $V$ has $1,000,000$ KAIA in CN Staking and $1,000,000$ KAIA in CL.
2.  The expected reward split is 50/50.
3.  Right before the block where a large reward is distributed, $V$ unstakes a large portion of CL or increases CN staking significantly in the parent block.
4.  The `StakingInfo` captured at `num-1` now shows an imbalanced ratio (e.g., 90/10).
5.  The `Split` function [5](#0-4)  calculates `clAmount` using the manipulated spot values, sending 90% of the reward to the validator's direct address instead of the CL pool, bypassing the intended economic incentives of the Consensus Liquidity KIP.
