### Title
Unguarded Value-Transfer Request Burns User Tokens Permanently When `counterpartBridge` Is Unconfigured (mint-burn mode) — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain `Bridge` contract inherits `BridgeCounterPart`, which stores a `counterpartBridge` address that defaults to `address(0)`. None of the three request-transfer entry points (`_requestKLAYTransfer`, `_requestERC20Transfer`, `_requestERC721Transfer`) check whether `counterpartBridge` has been set before accepting and processing user assets. In **mint-burn mode** (`modeMintBurn = true`), ERC-20 tokens are **burned** and ERC-721 tokens are **burned** inside the request path before the `RequestValueTransfer` event is emitted. If the counterpart bridge is not configured (either in the Solidity contract or in the Go-level SubBridge relay), no corresponding mint ever occurs on the destination chain, and the user's assets are permanently destroyed.

---

### Finding Description

`Bridge.sol` inherits from `BridgeCounterPart`, which exposes:

```solidity
// BridgeCounterPart.sol
address public counterpartBridge;   // initialized to address(0)
``` [1](#0-0) 

The three request-transfer functions never read or validate this field:

**`_requestERC20Transfer`** (mint-burn path):
```solidity
if (modeMintBurn) {
    ERC20Burnable(_tokenAddress).burn(_value);   // tokens destroyed here
}
emit RequestValueTransfer(...);
requestNonce++;
``` [2](#0-1) 

**`_requestERC721Transfer`** (mint-burn path):
```solidity
if (modeMintBurn) {
    ERC721Burnable(_tokenAddress).burn(_tokenId);  // NFT destroyed here
}
emit RequestValueTransferEncoded(...);
requestNonce++;
``` [3](#0-2) 

**`_requestKLAYTransfer`** (lock path):
```solidity
require(isRunning, "stopped bridge");
require(msg.value > _feeLimit, "insufficient amount");
// no counterpartBridge check
emit RequestValueTransfer(...);
requestNonce++;
``` [4](#0-3) 

The Go-level relay (`sub_event_handler.go`) uses its own internal `BridgeInfo.counterpartAddress` — completely independent of the Solidity `counterpartBridge` field — to decide whether to process an event:

```go
handleBridgeAddr := cce.subbridge.bridgeManager.GetCounterPartBridgeAddr(addr)
if handleBridgeAddr == (common.Address{}) {
    return fmt.Errorf("there is no counter part bridge of the bridge(%v)", addr.String())
}
``` [5](#0-4) 

This means even if `counterpartBridge` is set in Solidity, the relay will silently drop the event if the Go-level pairing is absent. The Solidity contract provides no on-chain guard.

---

### Impact Explanation

| Asset type | Mode | Effect when counterpart absent |
|---|---|---|
| ERC-20 | `modeMintBurn = true` | Tokens **permanently burned**; no mint on destination |
| ERC-721 | `modeMintBurn = true` | NFT **permanently burned**; no mint on destination |
| KAIA | lock mode | KAIA **locked** in bridge contract; recoverable only if counterpart is later configured |

The corrupted value is the user's token balance: `_value` ERC-20 tokens or `_tokenId` ERC-721 NFT are destroyed on-chain with no corresponding credit anywhere. This is an unauthorized burn of user assets triggered by a valid user call.

---

### Likelihood Explanation

**Low-to-medium.** The scenario requires:
1. Bridge deployed with `modeMintBurn = true`.
2. At least one token registered via `registerToken()` (owner action).
3. `counterpartBridge` **not yet set** (or Go-level pairing absent) — a realistic partial-configuration window during deployment.
4. A user calls `requestERC20Transfer()` or `requestERC721Transfer()` during that window.

`isRunning` defaults to `true`, so no additional owner action is needed to open the attack surface. The window exists between token registration and full bridge configuration.

---

### Recommendation

Add a counterpart-bridge guard to all three request-transfer paths:

```solidity
// In BridgeTransferKLAY._requestKLAYTransfer
// In BridgeTransferERC20._requestERC20Transfer
// In BridgeTransferERC721._requestERC721Transfer
require(counterpartBridge != address(0), "counterpart bridge not configured");
```

This mirrors the fix applied in the referenced OmniX report: revert when the destination peer/counterpart is not configured, preventing asset destruction before the bridge is fully operational.

---

### Proof of Concept

1. Deploy `Bridge(true)` (mint-burn mode).
2. Owner calls `registerToken(tokenAddr, cpTokenAddr)` — token is now bridgeable.
3. Owner does **not** call `setCounterPartBridge(...)` (or Go-level `RegisterBridge` is absent).
4. User calls `requestERC20Transfer(tokenAddr, user, 100, 0, "")`.
5. Inside `_requestERC20Transfer`: `ERC20Burnable(tokenAddr).burn(100)` executes — 100 tokens destroyed.
6. `RequestValueTransfer` event emitted; Go relay finds no counterpart (`GetCounterPartBridgeAddr` returns zero) and drops the event.
7. User's 100 tokens are gone with no corresponding mint on any destination chain. [6](#0-5) [7](#0-6) [1](#0-0) [5](#0-4)

**File:** node/sc/sub_event_handler.go (L71-87)
```go
func (cce *ChildChainEventHandler) ProcessRequestEvent(ev IRequestValueTransferEvent) error {
	addr := ev.GetRaw().Address

	handleBridgeAddr := cce.subbridge.bridgeManager.GetCounterPartBridgeAddr(addr)
	if handleBridgeAddr == (common.Address{}) {
		return fmt.Errorf("there is no counter part bridge of the bridge(%v)", addr.String())
	}

	handleBridgeInfo, ok := cce.subbridge.bridgeManager.GetBridgeInfo(handleBridgeAddr)
	if !ok {
		return fmt.Errorf("there is no counter part bridge info(%v) of the bridge(%v)", handleBridgeAddr.String(), addr.String())
	}

	// TODO-Kaia need to manage the size limitation of pending event list.
	handleBridgeInfo.AddRequestValueTransferEvents([]IRequestValueTransferEvent{ev})
	return nil
}
