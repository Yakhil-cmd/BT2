Based on the investigation, I found a concrete analog. The key finding is in `private_payment.js`'s `validateAndSavePrivatePaymentChain` function, which performs a check-then-act sequence (duplicate check, then insert/spend) on a private payment chain **without any mutex serialization** — unlike the public unit validation path in `validation.js` (which locks on `arrAuthorAddresses`) or `writer.js`'s `saveJoint` (which acquires the `"write"` mutex). This mirrors the CVE-2017-10914 root cause: a race condition between a check and the corresponding resource release/consumption due to missing/insufficient locking, enabling a double-free-equivalent (double-spend) of the same private output.

### Title
Unsynchronized check-then-save race in private payment chain validation allows double-spend of a private output - (File: private_payment.js)

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain` opens its own DB connection and transaction, performs a "check if duplicate" `SELECT` against the `outputs` table, and then — if not a duplicate — calls into `indivisible_asset.js`/`divisible_asset.js` to validate and insert/spend the private chain, all without ever acquiring the `mutex` module's `"write"` lock (used by `writer.js:saveJoint`) or the per-address lock used by `validation.js:validate`. Two concurrent private-payment messages referencing the same source output can both pass the duplicate/spend check before either commits, resulting in the same private (hidden) output being spent twice.

### Finding Description
Normal unit processing goes through `validation.js:validate()` which takes `mutex.lock(arrAuthorAddresses, ...)` [1](#0-0) , and actual writes go through `writer.js:saveJoint()` which takes the global `"write"` mutex before touching `inputs`/`outputs` [2](#0-1) . This serializes public payment processing so double-spend checks and output/input inserts are atomic with respect to other unit saves.

Private payments received via device messages (recipient/cosigner/hub relay) instead flow through `private_payment.js:validateAndSavePrivatePaymentChain`, which takes its own connection from the pool and begins its own transaction, but never calls `mutex.lock` on `"write"`, `"handleJoint"`, or any per-address/per-asset lock [3](#0-2) . It runs a duplicate-check `SELECT` on `outputs` [4](#0-3)  and, if the row is not already a recorded duplicate, defers to `indivisibleAsset.validateAndSavePrivatePaymentChain` / `divisibleAsset.validateAndSavePrivatePaymentChain` [5](#0-4) .

Those functions validate the spend proof against the `spend_proofs` table and the source output's current state, then queue `INSERT`/`UPDATE` queries (including `UPDATE outputs SET is_spent=1 ...`) that are executed only after validation succeeds [6](#0-5) , [7](#0-6) . Because each incoming private-payment element opens its own independent BEGIN/COMMIT transaction and there is no mutex coordinating concurrent invocations for the same source output, two private-payment chains spending the same hidden output (e.g., sent to the same device twice by a malicious or buggy counterparty, or received simultaneously via hub and direct P2P) can both read the source output as unspent, both pass validation, and both commit an `INSERT`/`UPDATE` marking their own (different) destination outputs as the spend of that source — a race window analogous to the double-free race in XSA-218, where a resource is consumed twice because the check-then-release path lacks a lock that the rest of the system relies on.

### Impact Explanation
A successful race lets a private-payment counterparty (the asset issuer's counterparty or any device sending private payments) create two divergent private chains that both claim to spend the same hidden output. This is a double-spend of a private asset output — one node/wallet in the private chain accepts one branch as valid while another accepts the other, leading to loss of funds for whichever party ends up on the losing branch, or to inconsistent private balances between cosigners/recipients that no unique DB constraint (like the public `bySrcOutput` unique key enforced under the write lock) protects against here, since these private inserts use `INSERT IGNORE` [8](#0-7)  rather than being serialized by a lock.

### Likelihood Explanation
Triggering the race requires only sending (or relaying) two private-payment messages that reference the same source output within the same narrow window — well within reach of a private-payment counterparty or a malicious paired device, requiring no special network position, hub compromise, or protocol violation beyond normal device-message private payment delivery.

### Recommendation
Serialize `private_payment.js:validateAndSavePrivatePaymentChain` per source-output (or per asset/unit/message_index) using the same `mutex` module already used elsewhere (e.g., `mutex.lock(["private_write"])`, which validation.js already uses for a related purpose) so that the duplicate-check SELECT and the subsequent validate-and-save are atomic with respect to concurrent invocations for the same private chain element.

### Proof of Concept
1. Attacker (private-payment counterparty) crafts a private divisible/indivisible payment chain element referencing a real, currently-unspent hidden source output.
2. Attacker sends two structurally different but validly-signed spends of that same source output as two separate private-payment device messages, timed to arrive back-to-back at the victim node (or relayed via hub + direct connection simultaneously).
3. `network.js`/`wallet.js` dispatch both into `private_payment.js:validateAndSavePrivatePaymentChain` concurrently; each opens its own connection/transaction and runs the duplicate check at [9](#0-8)  before either has committed its `is_spent=1` update.
4. Both pass validation and both commit, leaving two different private outputs both marked as spending the same source output — a private double-spend that a wallet or AA relying on the private chain state cannot detect until the conflicting chains are compared out-of-band.
