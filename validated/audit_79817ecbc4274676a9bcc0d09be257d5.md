### Title
CCMenu API bypasses per-stack API client scoping, allowing cross-stack read of deploy/build state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` looks up the target stack with `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!` helper used by every other API controller. This breaks the equality that should hold for every request: `stack the ApiClient token is authorized for == stack the request actually touches`. A stack-scoped `ApiClient` (created with a `stack_id`) is meant to only ever see that one stack, but through this endpoint it can read the deploy/build status of any stack in the installation.

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . This scoping is enforced centrally in `Shipit::Api::BaseController`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every controller that inherits `BaseController#stack` (deploys, tasks, locks, etc.) is therefore automatically restricted to the API client's authorized stack when one is set. The fixture `here_come_the_walrus` demonstrates this real feature: a client scoped with `stack: shipit` and only `read:stack` permission [3](#0-2) , and `stacks_controller_test.rb` confirms such a client "will only see that one stack" through the scoped `stacks` relation [4](#0-3) .

`CCMenuController`, however, overrides `stack` and resolves it against the unscoped `Stack` relation, ignoring `current_api_client.stack_id` entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

The `require_permission :read, :stack` before-action only checks that the client's `permissions` array includes `read:stack` [6](#0-5)  — it never checks *which* stack the client is scoped to. So the "verified" binding (token → its one authorized `stack_id`) is checked at authentication time but never re-applied when the controller decides which `Stack` record to act on for the request — exactly the "field acted on but not covered by verification" pattern from the report, applied to authorization scope instead of a cryptographic signature.

### Impact Explanation
Any holder of a stack-scoped, `read:stack`-only `ApiClient` token (e.g., one issued for a single repository's CCTray/CI dashboard integration via `CCMenuUrlController`, which itself creates a `read:stack` client [7](#0-6) ) can supply an arbitrary `stack_id` to `GET /api/1/stacks/:stack_id/ccmenu.xml?token=...` and read the last deploy/rollback state, running status, build label, and web URL of *any* stack in the Shipit installation — not just the one the token was scoped and authorized for. This is a scope-escalated read of stack/deploy state across repositories the token holder was never granted access to, matching the "unauthenticated/unauthorized read of stack state ... or deploy output" class of issue since the token is authenticated but the resource-level authorization check is skipped.

### Likelihood Explanation
This requires only possession of any valid `read:stack` API token (these tokens are routinely embedded in query strings/URLs for CI dashboard polling, e.g. `CCMenuUrlController#fetch`, making them more likely to leak or be shared than Basic-Auth credentials) and knowledge or guessing of another stack's `stack_id`/param (stack slugs are visible throughout the UI/URLs). No privileged account, GitHub write access, or session is needed beyond the already-issued scoped token.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup from `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so the resolved stack is always intersected with `current_api_client.stack_id` when the client is scoped, consistent with every other API controller.

### Proof of Concept
1. Admin creates (or the app auto-creates via `CCMenuUrlController`) an `ApiClient` scoped to `stack_id = A` with permission `read:stack` only.
2. Attacker/integration holding this token calls:
   `GET /api/1/stacks/:owner/:repo_B/:env_B/ccmenu.xml?token=<token_scoped_to_A>`
3. `authenticate_api_client` in `CCMenuController` accepts the token (it's valid) [8](#0-7) .
4. `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack`, regardless of `stack_id` [6](#0-5) .
5. `stack` resolves stack B via unscoped `Stack.from_param!`, and `show` renders stack B's deploy status XML — even though the token was only ever authorized for stack A [9](#0-8) .
