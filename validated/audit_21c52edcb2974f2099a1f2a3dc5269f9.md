Confirmed: `PushHandler#repository_name` (and the base `Handler#stacks`) resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`, while `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate against using a *different* field — `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`).

### Title
Webhook signature verified against `repository.owner.login`-selected secret while handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate the request with based on `repository.owner.login` from the *attacker-supplied JSON body itself*, not from any transport-level or otherwise trusted identifier. [1](#0-0) 
The signature check only proves the payload was signed with the secret belonging to whatever organization `repository.owner.login` names — it does not bind that verification to the `repository.full_name` value that the actual event handlers use to look up the target `Stack`/`Repository`. [2](#0-1) [3](#0-2) 

### Finding Description
The binding that should hold is: `organization whose secret authenticated the payload == organization owning the repository the handler writes to`. In this engine that binding is broken because both fields (`repository.owner.login` used for secret selection, and `repository.full_name` used for repository resolution) live inside the same signed JSON body and are fully attacker-controlled prior to any verification. `Shipit.github(organization: repository_owner)` is looked up purely from body content, and `verify_webhook_signature` computes the HMAC over the entire raw body (so if the attacker correctly signs the body with the secret for the org named in `repository.owner.login`, the signature check passes for the whole body content), yet the actual `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. resolve the repository to act on via `payload.dig('repository', 'full_name')`, a completely independent field within the same body. An attacker who has legitimate access to any one organization's Shipit App installation (and therefore legitimately knows that organization's `webhook_secret`) can sign a payload where `repository.owner.login` names their own organization (so `verify_signature` succeeds using their own known secret) while `repository.full_name` names a stack belonging to a *different* organization/repository that Shipit also tracks.

### Impact Explanation
This breaks the "organization authenticated == repository written" equality required by the rules. Depending on which webhook event is spoofed, this can be leveraged to: enqueue `GithubSyncJob`/`sync_github` for a push event that is not a real push, forge `check_suite`/`status` updates that unblock the merge queue or a deploy safety check for a victim's stack, or fabricate `pull_request` webhook activity that the merge-queue handlers act on — effectively an unauthorized action on a stack outside the attacker's own organization, without ever needing that organization's webhook secret. This matches the "unauthorized deploy/rollback/merge" or cross-repository-write class of impact.

### Likelihood Explanation
Exploitability requires the attacker to control (or otherwise know) the `webhook_secret` for at least one organization configured on the same Shipit instance — a realistic scenario for any Shipit deployment serving multiple organizations/teams with per-org GitHub Apps, which is exactly the multi-tenant configuration `config/secrets.*.yml` and `docs/setup.md` describe (`github: { org_a: {...}, org_b: {...} }`). No repository write access, session, or `ApiClient` token is required — only knowledge of one org's webhook secret and the ability to send an HTTP POST to `/webhooks`.

### Recommendation
After `verify_signature` succeeds, re-derive the organization strictly from the *same* field the handlers use for repository resolution (`repository.full_name`'s owner segment), and reject the request if that owner does not match the organization whose secret validated the signature. Alternatively, verify the signature using the secret resolved from `repository.full_name`'s owner (not a separately-dug `organization`/`owner.login` field), so a single canonical field drives both trust decisions.

### Proof of Concept
1. Attacker legitimately controls org `attacker-org`, which has a Shipit App installed with a known `webhook_secret`.
2. Attacker crafts a `push` payload: `{"ref": "refs/heads/master", "after": "<malicious sha>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact payload and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: "attacker-org")` and validates the signature successfully, per [4](#0-3) 
5. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, per [3](#0-2) 
demonstrating a forged webhook event acted upon a repository outside the authenticated organization.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
