## Title
Asset definer can freeze existing holders' funds of a `spender_attested` asset by removing an attestor from the asset's attestor list - (File: `storage.js`, `validation.js`)

### Summary
For assets created with `spender_attested: true`, the current spendability of every payment message is gated on whether at least one author's address is "attested" — but "attested" is evaluated only against the *latest* attestor list of the asset, not against the attestor list that was active when the address originally acquired/held the tokens. Because the asset definer can freely replace the entire attestor list at any time via an `asset_attestors` message, removing (or swapping out) one attestor immediately and retroactively invalidates every attestation issued by that attestor. Legitimate holders who were correctly attested when they received the asset become permanently unable to transfer or spend their existing balance, with no fault of their own — the same "removing an entry from a whitelist freezes existing/backed value" root cause described in the reference report (removing a whitelisted USDC version stranded existing `asdUSDC` backed by that version).

### Finding Description
When a `spender_attested` asset payment is validated, `validatePayment()` requires that at least one author be counted as "attested": [1](#0-0) 

The set of "attested authors" is computed by `storage.loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses`, which restricts the join to attestor addresses in `objAsset.arrAttestorAddresses`: [2](#0-1) 

`objAsset.arrAttestorAddresses` itself is populated by `readAsset()`'s `addAttestorsIfNecessary`, which reads only the **single most recent** `asset_attestors` unit for the asset (`ORDER BY level DESC LIMIT 1`) — i.e. the attestor list is a full replacement, not an additive/cumulative whitelist: [3](#0-2) 

The attestor list can be replaced at will by the asset's definer via the `asset_attestors` app, whose validation only checks that the sender is the definer and that the new list is well-formed — there is no requirement to preserve previously-attested holders' eligibility: [4](#0-3) 

The historical `attestations` table (populated by `attestation` messages, see `writer.js`) permanently records which attestor vouched for which address, but that history becomes irrelevant the moment the attestor is dropped from the asset's current list, because `filterAttestedAddresses` only recognizes attestors that are in the *current* `arrAttestorAddresses` set: [5](#0-4) 

This exactly mirrors the reported bug class: a privileged party (the definer, analogous to the `asdUSDC` owner) unilaterally shrinks a "whitelist" (the attestor set, analogous to the whitelisted USDC versions) that existing token holders' spendability depends on, stranding value that was legitimately obtained under the old rules.

### Impact Explanation
Any holder of a `spender_attested` asset whose only qualifying attestation was issued by an attestor that the definer subsequently removes from the asset's attestor list is permanently unable to move or spend their existing balance of that asset (both `payment` transfers and further issuance by that holder are blocked by "none of the authors is attested" / "issuer is not attested" in `validatePayment`). This is a fund-freezing condition triggered entirely by an action of the asset definer that does not touch the affected holder's own address or definition — it silently invalidates value the holder already holds, with no recourse other than convincing a still-trusted attestor to re-attest them. For assets used to represent regulated/KYC'd value transfers (the intended use case of `spender_attested`), this can freeze arbitrary amounts of tokens held by unrelated, honest users.

### Likelihood Explanation
Any asset definer can trigger this unilaterally and at low cost by posting a single `asset_attestors` message that drops an attestor (e.g. to rotate attestors, respond to a compromised attestor key, or simply reduce the attestor set) — no protocol-level warning or grace period exists, and previously issued attestations from the removed attestor are dropped as a group as soon as the new list is stable. This requires only the routine, expected action of an asset definer (not an attacker exploiting a bug in the traditional sense), making the likelihood of accidental or careless triggering high in any deployment using `spender_attested` assets with more than one attestor.

### Recommendation
Consider one of the following:
- When validating "attested" status for spending, check the attestor list that was active at the time of the referenced attestation (or any attestor list that has ever included the attesting attestor), rather than only the current list, so that removing an attestor does not retroactively invalidate attestations already relied upon by holders.
- Alternatively, make attestor-list updates additive-only (attestors can be added but not removed), or require a time-locked/opt-in migration path so holders attested under the old list have an opportunity to be re-attested before losing spendability.
- At minimum, document this behavior prominently so integrators do not build stablecoin/KYC-style assets on `spender_attested` assuming attestations are permanent once granted.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and initial attestor list `[Attestor1, Attestor2]`.
2. `Attestor1` posts an `attestation` message attesting address `H`. `H` receives (and later validly transfers) units of asset `A`, each payment succeeding because `filterAttestedAddresses` finds `H` attested by `Attestor1`, who is in the current attestor list (`storage.js:1959-1974`).
3. `D` posts a new `asset_attestors` message for asset `A` with list `[Attestor2]` (removing `Attestor1`) — this passes `validateAttestorListUpdate` since `D` is the definer (`validation.js:2829-2848`).
4. Once this unit is stable, `readAsset`'s `addAttestorsIfNecessary` picks this newest unit as the asset's attestor list (`storage.js:1917-1946`), so `objAsset.arrAttestorAddresses = [Attestor2]`.
5. `H` attempts to spend/transfer their existing balance of asset `A`. `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses` no longer finds `H` attested (their attestation was from `Attestor1`, no longer in the list), so `objAsset.arrAttestedAddresses` is empty for `H`.
6. `validatePayment` rejects the transfer with `"none of the authors is attested"` (`validation.js:2118-2119`), permanently freezing `H`'s legitimately-acquired balance of asset `A` unless `Attestor2` (or a future attestor) re-attests `H`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
