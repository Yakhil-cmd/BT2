### Title
Native currency sent alongside a call to `pallet-revive` precompiles with `HAS_CONTRACT_INFO = false` (e.g. the `AssetConversion` swap precompile) is unconditionally transferred to the precompile's pseudo-account before dispatch and can become permanently unrecoverable - ([File: substrate/frame/revive/src/exec.rs])

### Summary
`pallet-revive` transfers `frame.value_transferred` into a called account **before** invoking a precompile's `call()` implementation, regardless of whether that specific precompile call actually uses/needs native currency. Several precompiles that implement asset-swap style operations (e.g. `substrate/frame/asset-conversion/precompiles/src/lib.rs`'s `AssetConversion::swap_exact_tokens_for_tokens`, `swap_tokens_for_exact_tokens`, `add_liquidity`, `remove_liquidity`, `create_pool`) never read or make use of `env.value_transferred()`. If a caller mistakenly (or is tricked into) sending non-zero `value` with such a call while swapping between two non-native assets, that value is deposited into the precompile's fixed pseudo-account with no code path that ever moves it back out, mirroring the Mover `ExecuteSwap` bug where `msg.value` sent alongside an ERC20-to-ERC20 swap becomes permanently stuck.

### Finding Description
In `pallet_revive::exec::Stack::run` (the exec.rs frame-execution driver), the balance transfer associated with a call is performed unconditionally for any non-delegate call: [1](#0-0) 

This happens *before* the precompile's `call()` is even invoked: [2](#0-1) 

The pre-compile framework distinguishes precompiles by `HAS_CONTRACT_INFO`. For precompiles like `AssetConversion` where `HAS_CONTRACT_INFO = false`, minting of the ED and consumer-increment only happens for `HAS_CONTRACT_INFO = true` precompiles: [3](#0-2) 

Yet the value transfer at line 1451-1463 is not gated on `HAS_CONTRACT_INFO` at all — it runs for every non-delegate frame, including calls into `HAS_CONTRACT_INFO = false` precompiles such as `AssetConversion`.

The `AssetConversion` precompile interface exposes `swapExactTokensForTokens`, `swapTokensForExactTokens`, `createPool`, `addLiquidity`, and `removeLiquidity` as regular (non-explicitly-payable, from a Solidity ABI standpoint there is no `payable` distinction enforced) functions: [4](#0-3) 

None of the handler functions ever call `env.value_transferred()`, nor check that it is zero, nor forward it anywhere: [5](#0-4) [6](#0-5) 

The underlying `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens` implementation only moves the ERC20-analog assets described by `path`/`AssetKind`, and never reads or refunds any incidental native value sent to the precompile's own account: [7](#0-6) 

Because `HAS_CONTRACT_INFO` is `false` for this precompile, it has no associated on-chain contract code, storage, or owner-controlled logic that could later reclaim value sent to its address — the account is a fixed, protocol-defined pseudo-account, not a user- or governance-controlled account. Once native value lands there via the unconditional transfer at exec.rs:1451-1463, there is no dispatchable path in the codebase that moves funds back out of that specific account for that specific caller.

This is the direct structural analog of the Sherlock finding: in the original bug, `ExecuteSwap.sol`'s `executeSwap` transferred `msg.value` into the contract implicitly whenever `_tokenFrom == ETH_TOKEN_ADDRESS`... but if a caller sent `msg.value` while `_tokenFrom != ETH_TOKEN_ADDRESS`, that ETH was never consumed by any code path and became stuck in the contract with no withdrawal mechanism. Here, `pallet-revive`'s frame execution machinery performs the analogous "any call may carry value" transfer irrespective of whether the specific target/method needs or uses it, and the `AssetConversion` precompile handlers implement the "does not check/consume the transferred value" half of the bug.

### Impact Explanation
Any signed account calling the `AssetConversion` precompile (a real, permissionless, non-privileged entry point reachable by any user through `pallet_revive::Pallet::call`/`bare_call`) with non-zero `value` while performing a swap or liquidity operation between two non-native `AssetKind`s will have that native currency amount irreversibly locked in the precompile's fixed pseudo-account. There is no owner, no governance-only rescue call, and no user-triggerable withdrawal for that specific value once it lands there via the unconditional pre-dispatch transfer. This is a direct, permanent loss of user funds triggered purely by normal, permitted usage (mistaken or malicious front-end/wallet behavior causing a nonzero `value` field on an unrelated call) — consistent with a High severity "funds get locked" class of bug.

### Likelihood Explanation
The precondition is simply that a caller (or a malicious/buggy dApp/wallet building the transaction on the caller's behalf) sets `value > 0` on a call to the `AssetConversion` precompile address while the swap path doesn't involve the native asset. Nothing in the Solidity ABI definition (`alloy::sol!` interface) or in the runtime marks these functions as explicitly non-payable in a way that is enforced by `pallet-revive`; the value transfer is performed by the calling framework regardless of the callee's semantics. This is realistically triggerable by ordinary usage mistakes (e.g., a front-end template that always attaches `value` to a "swap" call by habit, similar to how many payable Solidity swap routers work) and does not require any privileged actor.

### Recommendation
Add an explicit guard in `pallet_revive`'s precompile execution path (or, at minimum, in each affected precompile's `call()`) rejecting calls where `env.value_transferred()` is non-zero for `HAS_CONTRACT_INFO = false` precompiles that do not have a defined use for it (analogous to the report's recommendation to `require(msg.value == 0)` when the token path does not involve the native asset). Concretely: either (a) refuse to perform the frame's balance transfer for calls into precompiles that don't declare themselves as needing/accepting value, or (b) have each swap/liquidity handler in `substrate/frame/asset-conversion/precompiles/src/lib.rs` (and any other non-payable precompile) check `env.value_transferred()` is zero and revert otherwise.

### Proof of Concept
I was not able to execute a runtime integration test in this environment (no execution tooling available in this ask-only session), so this cannot be marked as an executed/verified PoC — only a code-path analysis. Deployment/reachability evidence gathered from source:
- The entry point is reachable by any signed account via `pallet_revive::Pallet::<Test>::bare_call(RuntimeOrigin::signed(caller), precompile_address(), value, ..., data, ...)`, as exercised (with `value = 0`) in the existing test suite: [8](#0-7)  and [9](#0-8) .
- The existing test suite never sets a non-zero `value` in these `bare_call` invocations, so the locked-fund scenario (call `swapExactTokensForTokensCall` with `path` = two non-native assets and `value > 0`) is not covered by any existing test, and I did not run a new integration test to confirm the exact balance outcome.
- The unconditional value-transfer-before-dispatch mechanism is confirmed by reading `substrate/frame/revive/src/exec.rs` lines 1451-1463 and 1465-1481, and the precompile's non-use of `value_transferred()` is confirmed by reading the full `substrate/frame/asset-conversion/precompiles/src/lib.rs`.

Because I could not run the reproduction and observe on-chain balances, treat the "permanently locked" conclusion as strongly supported by static code-path evidence but **not experimentally confirmed** — a background Devin session with access to `cargo test`/`cargo build` should add a test to `substrate/frame/asset-conversion/precompiles/src/tests.rs` that calls `swapExactTokensForTokensCall` with `value != 0` and a non-native `path`, then assert the native balance is stuck at the precompile's pseudo-account with no way to withdraw it, to make this fully demonstrable.

	fn swap_exact_tokens_for_tokens(
		call: &IAssetConversion::swapExactTokensForTokensCall,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		let path_len = Self::validated_path_len(&call.path)?;
		env.charge(
			<Runtime as pallet_asset_conversion::Config>::WeightInfo::swap_exact_tokens_for_tokens(
				path_len,
			),
		)?;
		let path: Vec<_> =
			call.path.iter().map(|e| Self::decode_asset_kind(e)).collect::<Result<_, _>>()?;

		let sender = Self::caller_account_id(env)?;
		let send_to = env.to_account_id(&H160(call.sendTo.0 .0));

		let amount_out = <pallet_asset_conversion::Pallet<Runtime> as Swap<
			<Runtime as frame_system::Config>::AccountId,
		>>::swap_exact_tokens_for_tokens(
			sender,
			path,
			Self::to_balance(call.amountIn)?,
			Some(Self::to_balance(call.amountOutMin)?),
			send_to,
			call.keepAlive,
		)?;

		Ok(IAssetConversion::swapExactTokensForTokensCall::abi_encode_returns(&Self::to_u256(
			amount_out,
		)?))
	}
