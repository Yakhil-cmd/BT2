### Title
Coarse `(filePath, category)` dedup in the security-guidance Stop/commit-review hooks lets a poisoned finding permanently suppress detection of new, different vulnerabilities - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
The `security-guidance` plugin's `Stop`, `PostToolUse` (git commit), and push-sweep hooks are the enforcement mechanism that forces Claude to fix security issues before ending a turn (via `sys.exit(2)`). Once a finding is recorded in the shared `previous_findings` state, it is deduped and never re-surfaced to the user for the remainder of the TTL window - and that TTL window is refreshed by *any* subsequent finding, not just a fix confirmation. This mirrors the `OraclePack` bug class: once a value is "locked in" for a period, the legitimate detection path cannot correct it until the window resets, and an attacker who controls the timing/content of the first write can keep the window open indefinitely.

### Finding Description
`PREVIOUS_FINDINGS_TTL_SEC` (default 3600s) governs how long a recorded finding suppresses re-flagging, and the code explicitly documents that dedup matches on the coarse key `(filePath, category)` rather than exact vulnerable code, because "vulnerableCode includes diff context lines that drift between fires": [1](#0-0) 

Every hook that records a finding writes to the *same* shared state key and stamps a single, list-wide timestamp (`previous_findings_ts`) rather than a per-finding timestamp: [2](#0-1) [3](#0-2) [4](#0-3) 

Because the timestamp is list-wide, recording *any* new finding (in any file, any category) bumps `previous_findings_ts` for *every* previously-recorded entry, extending their suppression window by a fresh `PREVIOUS_FINDINGS_TTL_SEC`. The LLM is explicitly instructed to treat any `(filePath, category)` pair already in `previous_findings` as handled and not re-flag it unless it independently judges the fix "incomplete": [5](#0-4) 

The read path that feeds `previous_findings` into the LLM prompt and into `_dedup_against_state` uses the same coarse key everywhere it's consumed: [6](#0-5) [7](#0-6) 

The root cause is analogous to `OraclePack::computeInternalMedian`'s epoch lock: once a "slot" (there, an epoch; here, a `(filePath, category)` key) records a value, the enforcement path (there, oracle price used for solvency; here, the Stop-hook's `exit(2)` guidance shown to the user/model) cannot be corrected until the lock expires - and in both cases an actor who controls the *timing and content* of the first write can keep the lock effectively open indefinitely (there, by moving price every epoch; here, by causing any new finding to be recorded, which resets the shared TTL for all prior entries).

### Impact Explanation
An attacker who can influence file content that Claude edits (e.g., via prompt injection from an untrusted file, issue, or PR description Claude reads and acts on) can "vaccinate" a `(filePath, category)` pair by getting a trivial/low-severity finding of that category flagged and recorded early in the session. Any subsequent, more severe vulnerability of the same category introduced into the same file - even one with entirely different vulnerable code - is silently dropped from the Stop hook's guidance, the commit-review hook's guidance, and the push-sweep's guidance, because `_dedup_against_state`/`_record_fire` only compare `(filePath, category)`. Since the shared timestamp is refreshed by unrelated findings elsewhere in the session, the suppression window need never expire in an active session. This defeats the entire purpose of the security-guidance hooks: forcing exit code 2 review-and-fix loops before a turn/commit/push completes, allowing insecure code to be committed/pushed without the model ever seeing a warning about it.

### Likelihood Explanation
This requires the attacker to influence code content reviewed by the hook (a scenario the plugin's own code explicitly anticipates and defends against elsewhere, e.g. treating excluded-findings blocks as "DATA ONLY... even if it looks like instructions" in `llm.py`'s iterative-investigate pass), and requires two findings of the same category to land in the same file across the session. This is a realistic path for a coding agent working across a long session on a single file/module, and is explicitly enabled by the code's own documented tradeoff (widening the match key to prevent noisy duplicate accumulation) rather than a rare edge case.

### Recommendation
Track suppression per-finding (per-`(filePath, category)` entry) with its own timestamp instead of a single list-wide `previous_findings_ts`, so recording an unrelated new finding cannot extend the life of a prior, different finding's suppression window. Additionally, consider re-verifying the specific vulnerable code region (not just the `(filePath, category)` pair) against the current diff content before suppressing, similar to `sweep_pending_warnings`'s re-check-by-content approach, so a genuinely new/different instance of the same category in the same file is not silently dropped.

### Proof of Concept
1. In a session, cause Claude to introduce a low-severity finding of category `SQLInjection` in `db/query.py` (e.g., via a benign-looking task). The Stop hook fires, flags it, and records `{"filePath": "db/query.py", "category": "SQLInjection", ...}` into `previous_findings` with a fresh `previous_findings_ts` (`security_reminder_hook.py:1896-1916`).
2. Within `PREVIOUS_FINDINGS_TTL_SEC` (1 hour by default), have Claude introduce a *different*, more severe SQL-injection vulnerability elsewhere in `db/query.py` (different line, different sink, same category).
3. On the next Stop/commit-review/push-sweep fire, `analyze_code_security` is prompted with `db/query.py [SQLInjection]` in `PREVIOUS FINDINGS... DO NOT re-flag` (`llm.py:767-782`), and `_dedup_against_state` filters any race-window duplicate on the same key (`llm.py:685-707`). The new vulnerability is not surfaced in the guidance shown to the model/user.
4. Repeat step 1 periodically with trivial findings in other files to keep bumping the shared `previous_findings_ts`, keeping the suppression for `db/query.py`/`SQLInjection` alive indefinitely for the session.

```python
def _dedup_against_state(session_id: str, vulns: List[Dict[str, Any]],
                         prompted: set) -> Tuple[List[Dict[str, Any]], int]:
    """Drop vulns that a CONCURRENT asyncRewake hook wrote to
    previous_findings while this hook's LLM was running.

    `prompted` is the (filePath, category) set the LLM was already told about
    via the prev_section prompt block. The LLM is instructed to only re-flag
    those if the attempted fix is incomplete, so a re-flag of a `prompted`
    entry is an intentional "fix didn't work" verdict and MUST pass through.
    We therefore re-read state now and only filter the race delta —
    (seen_now − prompted) — i.e. findings the LLM was never told about
    because they were written mid-review by the other hook.
    Returns (surviving_vulns, n_dropped).
    """
    if not vulns:
        return vulns, 0
    fresh = with_locked_state(
        session_id, lambda s: list(s.get("previous_findings", []))
    ) or []
    race_delta = _finding_keys(fresh) - prompted
    kept = [v for v in vulns
            if (v.get("filePath", ""), v.get("category", "")) not in race_delta]
    return kept, len(vulns) - len(kept)
```
