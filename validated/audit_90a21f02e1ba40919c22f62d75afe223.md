### Title
Webhook signature verification is selected and can be bypassed using unverified, attacker-supplied payload fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* `GitHubApp` (and therefore which `webhook_secret`) to validate an inbound webhook against by reading `repository_owner`/`organization.login` straight out of the still-unverified JSON body, and `GitHubApp#verify_webhook_signature` fails **open** (`return true unless webhook_secret`) whenever that selected org has no `webhook_secret` configured. The binding that should hold is: *organization whose secret authenticated the request == organization whose repository/webhook data is written into Shipit*. Because the org used for authentication is chosen from unauthenticated attacker data, and any org without a configured secret trivially "verifies" everything, this binding can be broken with a single unauthenticated HTTP request.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-49`: [1](#0-0) 
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```
`repository_owner` is computed from the request body **before** any signature check occurs: [2](#0-1) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This value directly selects which `GitHubApp` instance (and secret) is used to verify the *same* request's HMAC signature, via `Shipit.github(organization: repository_owner)` → `lib/shipit.rb#github_app_config`.

The verification itself fails open when a secret is absent: [3](#0-2) 
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

`webhook_secret` being unset per-organization is an explicitly supported, documented configuration state — it is shown as the literal default in the shipped multi-org example config: [4](#0-3) 
```yaml
github:
  somegithuborg:
    app_id:
    installation_id:
    webhook_secret: # nil
    private_key:
```

Consequently, an unauthenticated attacker who knows (or guesses) the login of *any one* configured GitHub organization that has no `webhook_secret` set can craft a JSON body whose `repository.owner.login` (or `organization.login`) equals that org's name, while the `repository.full_name` / other payload fields reference an *entirely different, arbitrary* repository/stack tracked under a different, secret-protected organization. `verify_signature` will select the no-secret org's `GitHubApp`, `verify_webhook_signature` returns `true` unconditionally, and the request proceeds to: [5](#0-4) 
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
so the fully-attacker-controlled `params` hash — including repository name, branch, SHA, membership/team data, statuses, etc. — is handed unauthenticated to every registered handler (`push`, `status`, `membership`, `check_suite`, `pull_request`, `merge`, `deployable_status`, ...), none of which re-validates the organization/repository binding against the org that actually "authenticated" the request.

### Impact Explanation
This breaks the trust binding "organization that authenticated the webhook == organization whose data/repository is acted upon." Concretely, an unauthenticated attacker can forge webhook events (e.g. `push`, `status`, `membership`, `check_suite`) attributed to arbitrary tracked stacks/repositories as long as at least one configured GitHub org lacks a `webhook_secret` — a state the project's own example configuration ships by default. This enables unauthenticated injection of Shipit-internal state used to drive deploy/merge decisions (e.g. `push` triggers `GithubSyncJob`, `status`/`check_suite` affect commit deployability, `membership` creates teams/users), i.e. an unauthorized influence over deploy eligibility without possessing any secret, GitHub credential, or session — matching the "unauthorized deploy" class of impact defined for this engine.

### Likelihood Explanation
Likelihood depends on operator configuration: it requires at least one configured GitHub organization/app with `webhook_secret` unset. This is not a hardening edge case — it is the literal example default shown in the repo's own multi-org secrets template and matches `docs/setup.md` sample. Any installation that follows the documented example config as-is, or that forgets to set a secret for a secondary/legacy org entry, is exposed. No credentials, tokens, or prior access are required — a single crafted POST to the public `/webhooks` endpoint suffices.

### Recommendation
- Do not use attacker-supplied payload fields to select the verification key before the signature has been verified. Require a stable, out-of-band identifier for the target org/app for signature key selection.
- Change `verify_webhook_signature` to fail **closed** (reject) when no `webhook_secret` is configured, rather than treating "no secret" as "trusted", or require `webhook_secret` presence at config-load time for every configured organization.
- After signature verification succeeds, re-validate that the payload's `repository.owner.login`/`organization.login` matches the organization whose secret was actually used to verify the signature before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with a multi-org GitHub config where at least one org (e.g. `orgwithoutsecret`) has `webhook_secret` left blank/nil (as shown in the shipped `config/secrets.development.shopify.yml` template), while another org (`secureorg`) tracks the target stack the attacker wants to affect.
2. Attacker sends, with no authentication and any (or no) `X-Hub-Signature` header:
```
POST /webhooks
X-Github-Event: push

{
  "repository": {
    "owner": { "login": "orgwithoutsecret" },
    "full_name": "secureorg/target-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `repository_owner` resolves to `"orgwithoutsecret"`; `Shipit.github(organization: "orgwithoutsecret")` returns a `GitHubApp` with `webhook_secret` = nil; `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature header.
4. `create` dispatches the forged payload — whose `repository.full_name` names the unrelated `secureorg/target-repo` — to all `push` handlers (e.g. enqueues `GithubSyncJob` for that stack), despite the request never having been authenticated by `secureorg`'s actual webhook secret.
