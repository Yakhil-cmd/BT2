### Title
Webhook authentication binds the payload's `repository.owner`, but event handlers act on the payload's `repository.full_name`, allowing any onboarded GitHub organization to trigger stack actions on another organization's repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the HMAC against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `organization.login`). Once the signature check passes, the entire attacker-controlled JSON body is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and every `Handler` subclass identifies the target repository via a *different* field: `payload.dig('repository', 'full_name')` (`Handler#repository_name`). Nothing ties `full_name`'s owner segment to `owner.login`, so the field that authenticates the sender (`repository.owner.login` / secret selection) is not the field that determines which repository/stack gets acted upon (`repository.full_name`).

### Finding Description
Shipit natively supports multi-organization deployments where each GitHub org has its own `webhook_secret`: [1](#0-0) 

The controller uses only the owner login to pick which org's secret verifies the signature: [2](#0-1) [3](#0-2) 

After verification, the raw parsed JSON (fully attacker-controlled aside from a valid HMAC) is dispatched to handlers unchanged: [4](#0-3) 

Every handler resolves the target repository from a sibling field of the same JSON object, `repository.full_name`, never cross-checked against `repository.owner.login`: [5](#0-4) 

`PushHandler` uses this unchecked field to select and resync stacks: [6](#0-5) 

Because a member org's `webhook_secret` only proves "this payload was signed by whoever holds org X's secret," not "this payload legitimately describes org X's repositories," an org that is a legitimate tenant of a shared Shipit instance can sign a payload with its own secret while setting `repository.full_name` to a different org's repository (`repository.owner.login`/`organization.login` is only used to pick the verification secret, and can be set to the attacker's own org so the HMAC check passes).

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." In a multi-tenant Shipit deployment it lets one onboarded org's signed webhook trigger `PushHandler#process` / `sync_github` (and analogous logic in other handlers keyed off `repository_name`) against a stack belonging to a completely different tenant, forcing an out-of-band resync (and, if `continuous_deployment` is enabled on the victim stack, an unintended deploy trigger) using attacker-chosen `ref`/`after` values, without the victim org's webhook ever being involved.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration via `secrets.github` per-org keys), and requires the attacker to control one legitimately onboarded organization's own webhook secret — which is normal for any tenant of a shared instance, not a privileged Shipit account. No repository write access, Shipit session, or GitHub App private key is needed.

### Recommendation
In `Handler#repository_name`, and in `WebhooksController#repository_owner`, derive the acting repository/org from the same, single trusted field, and explicitly verify that `repository.owner.login` (used to select the verification secret) matches the organization implied by `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing both `attacker-org` and `victim-org` entries (multi-tenant deployment), each with its own `webhook_secret`.
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s own `webhook_secret` and sends `X-Hub-Signature: sha1=<hmac>` plus `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s `GitHubApp`, and the HMAC verifies successfully.
5. `PushHandler#process` resolves the target via `payload.dig('repository','full_name')` = `victim-org/victim-repo`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — an action the victim organization never authorized.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
