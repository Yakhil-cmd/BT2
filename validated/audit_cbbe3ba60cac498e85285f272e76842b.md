### Title
Freezable SPL Token mints are accepted as pool assets, allowing a malicious pool creator to permanently freeze LP funds - (File: programs/cp-swap/src/utils/token.rs)

### Summary
`is_supported_mint` unconditionally accepts any mint owned by the legacy SPL Token program (and only whitelist-checks a limited extension set for Token-2022 mints), without ever verifying that the mint has no `freeze_authority` set. This lets a pool creator use a token whose freeze authority they control as one side of a pool, then freeze the pool's vault token account at will, permanently blocking `deposit`, `withdraw`, and `swap` for that pool - directly analogous to the referenced Ajna finding where a pausable/whenNotPaused external asset (CryptoKitties/CryptoFighter) could brick core pool operations and trap counterparties' funds.

### Finding Description
`is_supported_mint` is the sole gate used at pool-creation time to decide whether a mint is acceptable as pool collateral: [1](#0-0) 

For a legacy SPL Token mint (`owner == Token::id()`), the function returns `true` immediately with **no further checks**, in particular no check that `freeze_authority` is `None`: [2](#0-1) 

This check is invoked both in `initialize` and `initialize_with_permission`, the two permissionless pool-creation entry points, and if it fails to reject the mint the pool is created regardless of whether the mint carries a `freeze_authority`: [3](#0-2) [4](#0-3) 

Once the pool exists, every value-moving instruction (`deposit`, `withdraw`, `swap_base_input`, `swap_base_output`) moves tokens in/out of the pool's vault ATAs via `transfer_checked`: [5](#0-4) [6](#0-5) 

The SPL Token/Token-2022 program enforces at the protocol level that `transfer_checked` fails if either the source or destination token account is frozen. The mint's `freeze_authority` (a base `Mint` field, present on both legacy Token and Token-2022 mints, and never inspected by `is_supported_mint`) can issue a `FreezeAccount` instruction against *any* token account of that mint, including the pool's `token_0_vault`/`token_1_vault`, which are ordinary interface token accounts with no special freeze-exemption: [7](#0-6) 

If a pool creator mints a token with themselves as `freeze_authority`, pairs it with a legitimate asset (e.g. USDC) via `initialize`/`initialize_with_permission`, attracts liquidity providers, and then freezes the vault holding their token, every subsequent `deposit`, `withdraw`, and `swap` on that pool reverts because the corresponding `transfer_checked` call touches the frozen vault. Because `withdraw` (and `deposit`) move both `token_0` and `token_1` atomically in a single instruction, freezing just the malicious-token vault is sufficient to also lock the legitimate co-asset (e.g. USDC) that LPs deposited, since the whole withdraw transaction reverts if either transfer fails: [8](#0-7) 

This mirrors the referenced bug class: an asset with an externally-controlled "pause" capability (there: `whenNotPaused` on CryptoKitties/CryptoFighter `transfer`/`transferFrom`; here: SPL Token `freeze_authority` on the mint) is accepted by the pool's onboarding logic without excluding that capability, and once exercised it blocks the pool's core lifecycle operations (deposit/withdraw/swap here vs. borrow/repay/liquidate there), trapping counterparties' funds.

### Impact Explanation
LP funds (the legitimate co-asset, e.g. USDC/SOL) deposited into a pool paired with a freezable token can be **permanently frozen** by the malicious pool creator at will, since only the freeze authority (the attacker) can reverse the freeze and they have no incentive to. This is a concrete, permanent loss-of-access to user funds, satisfying the "permanent freezing of user or LP funds" impact criterion.

### Likelihood Explanation
The attack requires no privileged program access - only standard, permissionless actions: creating an SPL Token mint with a self-controlled `freeze_authority`, calling the permissionless `initialize`/`initialize_with_permission` instructions to create a pool with that mint, and later issuing a standard `FreezeAccount` instruction against the vault. All steps are attacker-chosen accounts/data within existing instructions, requiring no off-chain privileges, no validator collusion, and no non-default build features - making this readily reachable.

### Recommendation
In `is_supported_mint`, explicitly reject mints (both legacy Token and Token-2022) that have `freeze_authority.is_some()` (`COption::Some`), rather than trusting `owner == Token::id()` unconditionally. Alternatively, require pool creators to prove/attest the mint has no freeze authority, or restrict pool-eligible mints to those without freeze authority as part of the extension/attribute whitelist already applied to Token-2022 mints.

### Proof of Concept
1. Attacker creates SPL Token mint `M` via the legacy Token program with `freeze_authority = attacker`.
2. Attacker calls `initialize_with_permission` (or `initialize`) with `token_0_mint = M`, `token_1_mint = USDC`. `is_supported_mint(M, ...)` returns `true` at `programs/cp-swap/src/utils/token.rs:340-342` because `M.owner == Token::id()`, so pool creation succeeds.
3. Honest LP calls `deposit`, transferring real USDC and `M` into `token_0_vault`/`token_1_vault`.
4. Attacker (holding `freeze_authority`) issues a standard `FreezeAccount` instruction against `token_0_vault` (the `M` vault).
5. LP calls `withdraw` to redeem their USDC + `M`: the instruction calls `transfer_from_pool_vault_to_user` for `token_0_vault`, which invokes `transfer_checked` and fails because the source account is frozen (`programs/cp-swap/src/instructions/withdraw.rs:188-202`); the whole transaction reverts, so the LP's USDC also remains stuck in the pool alongside `M`, with no path to recovery since only the attacker can unfreeze.

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
