## Analog Found

### Title
Permit nonce can only be advanced by consuming a valid signature, giving the owner no way to cancel a pending `permit` before it is relayed - ([File: substrate/frame/assets/precompiles/src/permit.rs])

### Summary
`pallet_assets_precompiles`'s ERC-2612-style `permit` implementation stores a per-`(verifying_contract, owner)` nonce in `Nonces` and the *only* code path that mutates it is `Pallet::increment_nonce`, which is called exclusively from `Pallet::use_permit` after a signature has been successfully verified [1](#0-0) . There is no dispatchable, precompile selector, or admin/owner-triggered function that lets the `owner` (or any admin) bump their own nonce independently to invalidate an already-signed, not-yet-relayed permit. This mirrors exactly the bug class described in the report: the nonce is a signature-consumption counter with no owner-controlled "cancel" path.

### Finding Description
`use_permit` is the production entry point: it calls `do_verify_permit` (checks deadline, recovers the ECDSA signer, and compares it to `owner`) and, only on success, calls `Self::increment_nonce(verifying_contract, owner)` [2](#0-1) . `increment_nonce` is the sole mutator of the `Nonces` double map [3](#0-2) , and no other function in the module (public or pallet-private) writes to `Nonces`. The read-only `verify_permit`/`do_verify_permit` variants explicitly do *not* touch the nonce (documented in the module's own security notes and in `do_verify_permit`'s doc comment) [4](#0-3) [5](#0-4) .

This pallet is wired into production runtimes — it is referenced in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` and `substrate/bin/node/runtime/src/lib.rs`, and its behavior is exercised through the `pallet_revive` precompile machinery (this crate depends on `pallet_revive::precompiles::H160`, see the import at the top of `permit.rs` [6](#0-5) ), meaning `use_permit` is a real, EVM-reachable entry point for any caller holding a signature — exactly the "enabled contract call" entry the scan method requires.

Consequently, an `owner` who has signed a `permit(spender, value, deadline, v, r, s)` message and later wants to revoke it before a relayer submits it (e.g., they no longer trust the spender, or the transaction is stuck) has **no on-chain mechanism** to invalidate that specific nonce. Unlike `frame_system`'s account nonce (which is bumped by *any* normal signed extrinsic from that account, giving implicit cancellation as shown by `inc_account_nonce` in `pallet-meta-tx`'s test suite [7](#0-6) ), this permit nonce is a dedicated counter with a single writer gated behind successful signature verification — there is no "self-permit" or admin call that advances it independently.

### Impact Explanation
Medium. The owner cannot cancel a still-valid, signed permit once it exists off-chain. If circumstances change (compromised/mistaken spender, urgent need to revoke an approval before it is relayed), the owner has no recourse except waiting for the deadline to pass or hoping the relayer never submits it. This matches the original report's Medium severity: no direct loss of funds by itself, but it removes an owner's ability to defensively invalidate a pending authorization, which can matter in urgent situations (e.g., realizing the private key or the intended spender is compromised).

### Likelihood Explanation
Medium. Any owner who signs a `permit` message off-chain and later wants to revoke it before submission is in this situation; there's no attacker action required — it's a missing user-facing safety control reachable by every legitimate permit signer.

### Recommendation
Add an authenticated dispatchable/precompile function that lets the `owner` (`msg.sender` in the EVM-facing precompile call) directly invoke `Pallet::increment_nonce(verifying_contract, owner)` for their own address, so they can invalidate any outstanding signed-but-unconsumed permit without needing a matching signature.

### Proof of Concept
No signature check or on-chain invariant is bypassed here — this is a missing-feature/control finding, not a state-corruption exploit, so no PoC executing a broken guard is applicable. The evidence is structural: exhaustive grep over `substrate/frame/assets/precompiles/src/permit.rs` and its call sites (`permit_tests.rs`, `permit_precompile_tests.rs`, `lib.rs`, `benchmarking.rs`, `weights.rs`) shows `increment_nonce` is only ever invoked from `use_permit`, and no test (`use_permit_rejects_replay_of_consumed_permit` in `substrate/frame/assets/precompiles/src/permit_tests.rs` lines 540-600, confirmed via search) exercises an owner-initiated cancel path — none exists to test. I did not execute a live integration test since there is no code path to reproduce; the absence itself is the finding, consistent with the report's own recommendation ("implement a function that allows the owner ... to manually increment the nonce").

	/// Nonces for permit signatures.
	/// Mapping: (verifying_contract, owner_address) => nonce
	///
	/// Uses Blake2_128Concat for the first key to prevent storage collision attacks
	/// when the verifying_contract address could be influenced by an attacker.
	///
	/// Note: EIP-2612 specifies uint256 nonce. We store as U256 for compatibility.
	#[pallet::storage]
	pub type Nonces<T: Config> = StorageDoubleMap<
		_,
		Blake2_128Concat,
		H160, // verifying contract address (precompile address)
		Blake2_128Concat,
		H160, // owner ethereum address
		U256, // nonce (EIP-2612 uses uint256)
		ValueQuery,
	>;

	/// Error types for the permit pallet.
	#[pallet::error]
	pub enum Error<T> {
		/// The permit signature is invalid.
		InvalidSignature,
		/// The signer does not match the owner.
		SignerMismatch,
		/// The permit has expired (deadline passed).
		PermitExpired,
		/// The signature's `s` value is too high (malleability protection).
		SignatureSValueTooHigh,
		/// The signature's `v` value is invalid.
		InvalidVValue,
		/// Nonce overflow - account has used too many permits.
		NonceOverflow,
		/// The owner address is invalid (e.g., zero address).
		InvalidOwner,
		/// The spender address is invalid (e.g., zero address).
		InvalidSpender,
	}

	impl<T: Config> Pallet<T> {
		/// Get the current nonce for an owner on a specific verifying contract.
		pub fn nonce(verifying_contract: &H160, owner: &H160) -> U256 {
			Nonces::<T>::get(verifying_contract, owner)
		}

		/// Increment the nonce for an owner on a specific verifying contract.
		/// Returns the new nonce value, or an error if overflow would occur.
		pub fn increment_nonce(verifying_contract: &H160, owner: &H160) -> Result<U256, Error<T>> {
			Nonces::<T>::try_mutate(verifying_contract, owner, |nonce| {
				*nonce = nonce.checked_add(U256::one()).ok_or(Error::<T>::NonceOverflow)?;
				Ok(*nonce)
			})
		}

		pub fn use_permit(
			verifying_contract: &H160,
			name: &[u8],
			owner: &H160,
			spender: &H160,
			value: &[u8; 32],
			deadline: &[u8; 32],
			v: u8,
			r: &[u8; 32],
			s: &[u8; 32],
		) -> Result<(), Error<T>> {
			// Verify the permit first
			Self::do_verify_permit(
				verifying_contract,
				name,
				owner,
				spender,
				value,
				deadline,
				v,
				r,
				s,
			)?;

			// Consume the permit by incrementing the nonce
			// This prevents the same permit from being used again
			Self::increment_nonce(verifying_contract, owner)?;

			Ok(())
		}
