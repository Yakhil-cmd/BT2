### Title
Users cannot defend positions collateralized in a paused token, but liquidators can still seize it via `SeizeMode::Credit` - ([File: contracts/controller/src/positions/liquidation/mod.rs])

### Summary
In XOXNO Lending, adding collateral (`supply`) and repaying debt (`repay`) both require real token transfers into the pool, so a paused/frozen token (e.g. a classic Stellar asset with a frozen trustline or a token contract with paused transfers) blocks the borrower from improving their health factor. Liquidation, however, offers `SeizeMode::Credit`, which delivers the seized collateral as internal supply-share credit to a liquidator-owned account — no collateral token transfer ever occurs. The only token movement in the whole call is the debt repayment pulled from the liquidator, which is in a different token. A liquidator can therefore liquidate an account whose owner is physically unable to add collateral.

### Finding Description
The liquidation entrypoint `liquidate(liquidator, account_id, debt_payments, seize_mode)` seizes collateral pro rata across all supply positions. When `seize_mode = SeizeMode::Credit(0)` or `Credit(id)`, `resolve_seize_receiver` in `contracts/controller/src/positions/liquidation/mod.rs` resolves or creates a receiver account, and the seized RAY-scaled supply shares are credited to that account's position books instead of being withdrawn from the pool (`common/src/types/controller.rs` documents `Credit` as "moves supply shares, requiring no collateral cash"). The pool-side seize leg (`contracts/pool/src/ops/seize.rs`) explicitly "does not transfer tokens; the controller adjusts the position books".

By contrast, every defensive action available to the borrower moves real tokens:

- `supply` pulls the collateral token from the caller — reverts if that token's transfer is paused/frozen.
- `withdraw` pushes collateral out — also reverts, and is irrelevant to defense anyway.
- `repay` pulls the debt token — blocked only if the debt token is paused, and useless if the borrower holds no debt tokens.

So when the collateral token is the paused one, the borrower cannot supply more of it to raise their health factor, while a liquidator calling `liquidate` with `SeizeMode::Credit` succeeds because the collateral leg never touches the token contract. The documented pause model confirms no mitigation: "Global pause leaves withdrawal, repayment, liquidation, bad-debt cleanup and recapitalization callable" (`docs/reference/endpoints.md`), and seizure is only blocked per-asset by the `no_seize` flag, which is an admin action, not an automatic consequence of a broken token.

### Impact Explanation
A borrower whose entire collateral is in a paused/frozen token can be liquidated — losing the liquidation bonus (up to the HF-preserving cap on the bonus curve) — during a window in which the protocol gives them no reachable defense: supplying collateral reverts on the token transfer, and they may hold none of the debt asset to repay. This is a loss of user funds (the bonus portion of seized collateral) that the user was structurally prevented from avoiding.

### Likelihood Explanation
Low-to-moderate. It requires (a) the collateral token's transfer path to be halted (token pause, clawback-enabled authorization freeze, or trustline revocation on classic assets — plausible for Stellar assets with `AUTH_CLAWBACK`/`AUTH_REVOCABLE`), (b) the borrower holding insufficient debt tokens to repay, and (c) the account being liquidatable. The GMX sponsors themselves acknowledged the scenario as real but rare. Note the liquidator still needs the debt token unpaused, so the asymmetry exists only when collateral is paused and debt is not — but with multiple collateral/debt markets this asymmetry is easy to hit per-asset.

### Recommendation
Keep an admin/auto circuit breaker that halts liquidation (`no_seize` or a dedicated flag) for a market whose token transfers are verifiably failing, and ensure governance can set it quickly. Alternatively, when every collateral leg of an account resolves to a token whose transfers are failing, treat the account as non-liquidatable until transfers resume, or require `SeizeMode::Transfer` (which does touch the collateral token via the pool withdraw leg) so that a broken collateral token blocks liquidation symmetrically with defense.

### Proof of Concept
1. Alice supplies 10,000 USDC (collateral) and borrows ETH such that HF is near 1. USDC is her only collateral; she holds no ETH.
2. The USDC token contract's transfers are paused (or Alice's/pool's trustline is frozen via clawback authorization flags).
3. Price moves; `is_liquidatable(alice_id)` returns true.
4. Alice attempts `supply` of more USDC → reverts on the token `transfer`. She cannot `repay` (no ETH) and `withdraw` also reverts. No unprivileged path raises her HF.
5. Liquidator calls `liquidate(liquidator, alice_id, [(eth_hub_asset, amount)], SeizeMode::Credit(0))`. `resolve_seize_receiver` creates a fresh receiver account (`contracts/controller/src/positions/liquidation/mod.rs`), the pool pull of ETH succeeds (ETH not paused), and `apply` in `contracts/pool/src/ops/seize.rs` reclassifies Alice's supply shares as receiver shares/revenue without any USDC transfer.
6. Alice is liquidated despite every defense being unreachable; the liquidator received the collateral value plus bonus as shares, redeemable once USDC unpauses.
