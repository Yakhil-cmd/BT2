## Title
CCMenu API endpoint accepts any `stack_id` regardless of the authenticated `ApiClient`'s stack scope, breaking the "stack a token authorises = stack it touches" binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack lookups to the authenticated `ApiClient`'s `stack_id` when the client is stack-scoped, via the `stacks`/`stack` helper methods. [1](#0-0)  `Api::CCMenuController` overrides `stack` to bypass this scoping entirely, resolving the stack directly from the request parameter instead of from the authenticated client's authorized stack set. [2](#0-1) 

### Finding Description
`BaseController#stacks` restricts the queryable stacks to `Stack.where(id: current_api_client.stack_id)` when the client carries a `stack_id` (i.e., it is a stack-scoped token), otherwise `Stack.all`. [3](#0-2)  `BaseController#stack` then resolves the requested stack from that scoped relation: `stacks.from_param!(params[:stack_id])`. [4](#0-3)  This is the binding that "the stack a token authorises" (`current_api_client.stack_id`) must equal "the stack a request touches" (`params[:stack_id]`) whenever a client is stack-scoped.

`CCMenuController` declares `require_permission :read, :stack`, which only calls `current_api_client.check_permissions!(operation, scope)` — a check against the client's `permissions` array, unrelated to `stack_id` scoping. [5](#0-4) [6](#0-5)  The controller then overrides `stack` to bypass the `stacks` scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [7](#0-6) 

Because `Stack.from_param!` queries across *all* stacks rather than through `current_api_client`'s scoped relation, any `ApiClient` token carrying `read:stack` permission — even one deliberately created and scoped to a single stack via `stack_id` (the exact mechanism `BaseController` relies on for isolation) — can be used to fetch CCMenu deploy-status XML for any other stack by simply changing `params[:stack_id]` in the request. The equality the rest of the API enforces, `current_api_client.stack_id == requested stack`, is broken specifically in this controller.

### Impact Explanation
This meets the High-impact bar of "unauthenticated read of stack state" in the sense defined by the rules: a token that is authorized (scoped) for one stack can read state (deploy status: whether it's running, when it last completed) belonging to a stack it was never granted access to, an authorization-boundary violation between what the token's `stack_id` authorizes and what stack the request actually touches.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with `read:stack` permission can trigger this — no privileged account or additional secret is required beyond having one legitimate stack-scoped token (which is the normal, lower-trust type of token this application issues, e.g. via `CCMenuUrlController`, which explicitly creates `read:stack`-only clients). [8](#0-7)  The attack is a trivial parameter change on an otherwise-valid, unprivileged request.

### Recommendation
`CCMenuController#stack` should resolve through the inherited, client-scoped `stacks` relation instead of the unscoped `Stack` model, mirroring every other controller under `Api::BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to Stack A with permission `read:stack` (e.g. via the CCMenu URL flow for Stack A, which creates such a token). [8](#0-7) 
2. Call `GET /api/stacks/:stack_id_of_B/ccmenu.xml?token=<Stack-A-scoped-token>`, substituting Stack B's identifier in `params[:stack_id]`.
3. `authenticate_api_client` succeeds because the token is valid. [9](#0-8) 
4. `require_permission :read, :stack` succeeds because the token has `read:stack` in its permission list, irrespective of `stack_id`. [6](#0-5) 
5. `stack` resolves Stack B directly via `Stack.from_param!`, bypassing the `stacks` scope that would have restricted the token to Stack A only. [7](#0-6) 
6. The response renders Stack B's latest deploy/rollback status, disclosed to a client never authorized for Stack B. [10](#0-9)
