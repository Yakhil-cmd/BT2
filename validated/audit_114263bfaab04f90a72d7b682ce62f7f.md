### Title
Webhook signature verification silently no-ops when `webhook_secret` is unset, allowing unauthenticated forgery of `membership` events and escalation into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` delegates authenticity checking entirely to `GitHubApp#verify_webhook_signature`, which returns `true` unconditionally whenever no `webhook_secret` is configured for the resolved organization. `webhook_secret` is an explicitly documented, optional setting (shown as blank/`nil` in `config/secrets.development.example.yml` and `docs/setup.md`). In that supported configuration, the "verified" boolean produced by `verify_signature` is never actually bound to anything GitHub signed — every field in the JSON payload (`repository`, `organization`, `team`, `member`, `action`, `sha`, `state`, `ref`, `after`, etc.) is fully attacker controlled with zero cryptographic binding to a real GitHub delivery, exactly like the report's `onERC721Received` callback that is expected to enforce a check but is not actually wired up.

### Finding Description
The `create` action processes any inbound POST whose `verify_signature` before_action does not halt the request: [3](#0-2) 

`verify_signature` resolves the GitHub App for the (attacker-supplied) `repository_owner`/`organization.login` field and asks it to verify the `X-Hub-Signature` header against the raw body:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

When `webhook_secret` is blank — a state the project's own example secrets file and setup docs treat as valid ("webhook_secret: # nil") — `verified` is `true` for any request regardless of the `X-Hub-Signature` header content, meaning the "verified" binding (GitHub cryptographically signed this payload) never actually holds. The equality the engine relies on — `signature-verified organization == organization whose event handlers execute` — collapses to "always true," because the left side of that equality is vacuous.

Once past this gate, the `membership` event handler creates `Team`s on the fly and adds arbitrary logins as `Membership`s based purely on unauthenticated payload content, as shown by the existing test suite exercising this exact path: [4](#0-3) [5](#0-4) 

`Shipit.github_teams` (used by `Authentication#force_github_authentication` and `User#authorized?`) is derived from `oauth_teams`/`Team` membership: [6](#0-5) [7](#0-6) 

Because team membership is populated directly from forged `membership` webhook events with no verified provenance, an attacker can add an arbitrary GitHub login (including their own) to a `Team` that is listed in `Shipit.github_teams`, then complete the normal GitHub OAuth login flow (a step the engine allows for any GitHub account) and pass the `authorized?` check, gaining full access to the Shipit application (stacks, deploys, rollbacks, tasks).

### Impact Explanation
This breaks the binding "an organization/event that GitHub actually authenticated == the organization/event whose side effects execute," and its outcome — unauthenticated escalation into `Shipit.github_teams` authorization — is explicitly listed as a High-severity impact for this scope. In addition to the membership escalation, the same no-op verification lets an attacker forge `push` (triggering `GithubSyncJob`), `status`, and `check_suite` events that influence deploy readiness signals for any stack whose repository name the attacker knows.

### Likelihood Explanation
Likelihood is high wherever `webhook_secret` is left unset, which the shipped example configuration (`config/secrets.development.example.yml`) and setup documentation both present as a normal, supported option rather than a misconfiguration outside the documented setup. No GitHub App private key, `ApiClient` token, Shipit session, or repository write access is required — only knowledge of the target's public repository/organization name and the existence of a `Shipit.github_teams` entry, both of which are typically public information.

### Recommendation
Make `webhook_secret` mandatory (fail closed) rather than optional-with-bypass: reject webhook requests (`head 422`/500) when no `webhook_secret` is configured for the resolving organization instead of treating the absence of a secret as automatic verification success. At minimum, emit a hard startup/configuration error if any configured GitHub App lacks a `webhook_secret`, and stop trusting `membership`/`team` events to mutate `Shipit.github_teams`-backed authorization without corroborating the sender through the authenticated GitHub API.

### Proof of Concept
1. Deploy Shipit with a GitHub App configuration that omits `webhook_secret` (as shown in `config/secrets.development.example.yml`) — a documented supported configuration.
2. Without any credentials, POST to the webhooks endpoint with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <id-of-a-Shipit.github_teams-team>, "slug": "developers", "name": "Developers", "url": "http://example.com" },
  "organization": { "login": "<target-org>" },
  "member": { "login": "<attacker-github-login>" }
}
```
3. `verify_signature` calls `verify_webhook_signature` which returns `true` because `webhook_secret` is blank; the membership handler creates the `Membership`, exactly as exercised in `test/controllers/webhooks_controller_test.rb:142-149`.
4. The attacker completes GitHub OAuth login through `GithubAuthenticationController#callback`; `User#authorized?` now returns `true` because the attacker's `Team` membership matches `Shipit.github_teams`, granting full application access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
