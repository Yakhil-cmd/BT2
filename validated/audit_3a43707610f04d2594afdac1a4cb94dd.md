### Title
Uncaught exception in unstable data-feed candidate sorting crashes/DoS's nodes evaluating an AA - (File: `data_feeds.js`)

### Summary
The external report's root cause is a state-tracking edge case (`==` instead of `>=`, and an event-timestamp update rule with a gap) that lets two "in-flight randomness requests" exist simultaneously, letting an attacker pick the more favorable of two results. In `ocore`, the analogous state-tracking edge case exists in `readDataFeedValue()` in `data_feeds.js`, which resolves *unstable* AA data-feed candidates by sorting on `(latest_included_mc_index, level)` and **throws an unhandled `Error`** when two candidates tie on both fields instead of deterministically resolving the ambiguity, as is done for the `bIncludeAllUnstable` (non-AA) case.

### Finding Description
When an oscript/AA formula evaluates `data_feed[[...]]` (or `in_data_feed[[...]]`) while executing as an AA, `evaluation.js` calls `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, ...)` with `unstable_opts = bAA = true` [1](#0-0) . Inside `readDataFeedValue`, when `bIncludeUnstableAAs` is true, the function scans `storage.assocUnstableMessages` for still-unstable AA units authored by any of the referenced "oracle" addresses and collects all matching `data_feed` messages as `arrCandidates`, each tagged with `latest_included_mc_index` and `level` [2](#0-1) .

If more than one candidate is found, they are sorted to determine the "last" one:
```
arrCandidates.sort(function (a, b) {
    if (a.latest_included_mc_index < b.latest_included_mc_index) return -1;
    if (a.latest_included_mc_index > b.latest_included_mc_index) return 1;
    if (a.level < b.level) return -1;
    if (a.level > b.level) return 1;
    if (bIncludeAllUnstable) return 1; // still ambiguous, sort randomly (it's OK outside AAs)
    throw Error("can't sort candidates "+a+" and "+b);
});
``` [3](#0-2) 

For the AA case (`bIncludeAllUnstable === false`), a tie on both `latest_included_mc_index` and `level` results in a synchronous `throw`, executed inside an `Array.prototype.sort` comparator with no surrounding `try/catch` in `readDataFeedValue`, `evaluation.js`'s `getDataFeed`, or the higher-level `evaluateAA`/`handleTrigger` flow in `aa_composer.js` that drives AA trigger processing [4](#0-3) . Unlike other formula errors, which are captured via `setFatalError`/`fatal_error` and gracefully surfaced as a bounce, this throw escapes as a raw JS exception.

A tie on `(latest_included_mc_index, level)` is trivial to produce: any address referenced as an "oracle" in the AA definition (which, notably, can be an address the AA author or trigger flow itself controls) can author two sibling, non-conflicting units (using two distinct unspent outputs) that share identical parents, each carrying a `data_feed` message for the same `feed_name` with a matching value (or simply omit `feed_value`, matching everything via `value === null`). Both units end up with the same `level` (level = max(parent levels)+1, identical for units sharing parents) and the same `latest_included_mc_index` while still unstable, and get pushed into `arrCandidates` together.

### Impact Explanation
Any node/witness that evaluates the affected AA while these two colliding units are unstable will hit the uncaught `throw` during unstable-data-feed candidate sorting. Because this happens inside a raw synchronous call originating from AA trigger processing (`handleTrigger` → `evaluateAA`/state-update formula evaluation) with no enclosing try/catch, it propagates as an unhandled exception rather than a graceful bounce, disrupting AA execution for that trigger on every node that attempts it at that moment. This matches the "network unable to confirm new units" / "node disagreement on validity" impact class: nodes can crash or hang mid-validation of a unit that depends on this AA response, and different nodes may observe the ambiguous candidates in different orders/timings depending on when they see the colliding units, creating consensus risk around AA response determinism.

### Likelihood Explanation
The trigger condition only requires one address (which can be the AA author's own address, chosen as the "oracle" in their own AA definition) to post two sibling non-conflicting units with identical parents, each containing a matching `data_feed` message. This is fully achievable by an unprivileged AA author/oracle-designated address with ordinary wallet capability (splitting outputs to post two units built on the same parents), requiring no collusion with third parties and no privileged access.

### Recommendation
- Replace the `throw Error("can't sort candidates ...")` branch with a deterministic, side-effect-free tie-break (e.g., sort by `unit` hash lexicographically, mirroring the "OK outside AAs" branch) instead of throwing.
- Ensure any residual ambiguity is surfaced through the existing `setFatalError`/bounce mechanism rather than a raw exception, so AA evaluation degrades gracefully (bounce) instead of crashing/hanging the evaluating process.
- Add regression tests posting two unstable, sibling `data_feed` units from the same oracle address with identical `level`/`latest_included_mc_index` referenced by an AA's `data_feed[[...]]` condition, verifying the AA bounces cleanly instead of throwing.

### Proof of Concept
1. Define an AA whose `oracles` parameter includes address `O`, and whose formula reads `data_feed[[oracles='O', feed_name='x']]` (no `feed_value` filter, so `value === null` and any posted value is a candidate).
2. From address `O` (which the attacker/AA author controls, since it is merely the designated oracle address, not a privileged network role), construct two units `U1` and `U2` that:
   - share the exact same parent set (so both get the same DAG `level`), and
   - both contain a `data_feed` message with `feed_name: 'x'` (any values), and
   - consume two different unspent outputs of `O` so they are not conflicting/double-spends.
3. Broadcast both `U1` and `U2` so they remain unstable simultaneously.
4. Trigger the AA (or have any pending trigger get processed) while `U1`/`U2` are both unstable with identical `latest_included_mc_index` (a very likely occurrence since both were built on the same MC state).
5. `readDataFeedValue` collects both as `arrCandidates`, and `Array.prototype.sort`'s comparator throws `Error("can't sort candidates ...")` synchronously and uncaught, disrupting the AA trigger evaluation on any node processing it at that time instead of yielding a deterministic bounce/response.
