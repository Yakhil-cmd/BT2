### Title
Unbounded iteration over dust outputs of a custom asset lets an unprivileged unit poster freeze an AA's asset balance - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `completePaymentPayload()` builds an AA-generated payment by repeatedly querying unspent outputs of the paid asset and iterating them in `iterateUnspentOutputs()` until the target amount is reached. For the base asset, outputs smaller than `FULL_TRANSFER_INPUT_SIZE` are excluded from the query specifically to prevent a "dust attack" (per the code comment). For custom (non-base) assets, this filter is not applied, and the resulting number of consumed inputs is not bounded by `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` because `validatePaymentInputsAndOutputs()` in `validation.js` explicitly skips that check when `objValidationState.bAA` is true.

### Finding Description
In `aa_composer.js`, `readStableOutputs()` and `readUnstableOutputsSentByAAs()` build a SQL query to fetch unspent outputs owned by the AA address for the asset being paid: [1](#0-0) 
The dust filter `AND amount>=FULL_TRANSFER_INPUT_SIZE` is only inserted in the `asset ? ... : ...` ternary's `else` branch, i.e. only for the base asset. When `asset` is a custom asset, no minimum amount is enforced, and the query itself carries no `LIMIT`.

`iterateUnspentOutputs()` then loops over every row returned, unconditionally pushing each one into `payload.inputs` until the accumulated `total_amount` reaches `target_amount` (used, in particular, for send-all outputs where the target is "all remaining balance"): [2](#0-1) 

Normally `validatePaymentInputsAndOutputs()` rejects payments with more than `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) inputs: [3](#0-2) 
but this check is explicitly skipped `&& !objValidationState.bAA`, so units generated by an AA (as `completePaymentPayload` does) are not subject to this cap.

Any unprivileged party can post ordinary payment units sending an arbitrary number of tiny-amount outputs of a given asset to an AA address (an asset dust attack), since normal (non-AA) payments are only capped by `MAX_OUTPUTS_PER_PAYMENT_MESSAGE` (128) per message but an attacker can send many such units. Once the AA later needs to spend or "send-all" its balance in that asset — a common oscript pattern (see `test/samples/send_all.oscript`) — `completePaymentPayload` is forced to sweep in all of those dust outputs to reach the send-all target, producing an unboundedly large `payload.inputs` array and unit size.

### Impact Explanation
Because the number of inputs an AA-generated unit can carry for a custom asset is unbounded, an attacker can inflate it to the point that either:
- the resulting unit exceeds `constants.MAX_UNIT_LENGTH`, making it un-postable and permanently failing the AA's attempt to pay out or move its balance in that asset (the trigger bounces every time, since the query keeps returning all dust outputs and there is no mechanism to skip them), effectively freezing the AA's asset funds, or
- the node performing `handleTrigger` for that AA has to build/validate/hash a payload with thousands of inputs on every relevant trigger, causing severe processing slowdown for that specific AA's operations.

This matches the reported bug class (unbounded, attacker-controlled iteration inside a function whose success is required for correct operation of the module/contract, leading to inability to complete an operation, i.e. AA fund freezing), reachable purely by posting ordinary units from any address — no privileged, network, or node-level access is required.

### Likelihood Explanation
Likelihood is high for any AA that: (a) accepts and holds a custom (non-base) asset, and (b) implements a send-all/sweep pattern for that asset (a documented, encouraged idiom, e.g. `test/samples/send_all.oscript`). An attacker only needs to send many low-value outputs of the target asset to the AA's address before or between AA responses — a normal payment unit, requiring no special privilege.

### Recommendation
Apply the same dust-filtering (or a lower, asset-appropriate minimum output amount / a query `LIMIT`) to the custom-asset branch of `readStableOutputs()` and `readUnstableOutputsSentByAAs()` in `aa_composer.js` as is already applied to the base-asset branch, and/or enforce `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (or another explicit bound) on AA-generated payments regardless of `objValidationState.bAA`, so that the number of inputs an AA response can require is always bounded and cannot be inflated by third-party dust outputs.

### Proof of Concept
1. Deploy an AA that defines/holds a custom asset and implements a send-all payment pattern in that asset when triggered (analogous to `test/samples/send_all.oscript` but for `asset: <custom_asset>` instead of `'base'`). [4](#0-3) 
2. As an unprivileged party, repeatedly post ordinary payment units sending many (e.g. thousands of) tiny-amount outputs of that asset to the AA's address; these are accepted since ordinary payments of a custom asset have no per-output minimum amount check in `validatePaymentInputsAndOutputs()` and only the per-message output count is capped by `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`, so many messages/units can be used to accumulate dust. [5](#0-4) 
3. Trigger the AA so it attempts its send-all response in that asset. `completePaymentPayload()`'s `readStableOutputs`/`iterateUnspentOutputs` will attempt to sweep in all the dust outputs (no amount floor, no `LIMIT`, no `MAX_INPUTS_PER_PAYMENT_MESSAGE` enforcement for `bAA`), producing an oversized unit that cannot be validated/posted, causing the AA's response to bounce and its asset balance to become stuck. [6](#0-5)
