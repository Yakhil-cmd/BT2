### Title
Membership webhooks are authenticated against `repository.owner.login` but authorize teams for `organization.login`, allowing org impersonation when any configured org lacks a `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#repository_owner` selects the organization used for signature verification from `params.dig('repository','owner','login')`, while `MembershipHandler#process`/`#find_or_create_team!` trusts the independent `params.organization.login` field to create/tag a `Team`. These two fields are attacker-controlled and unrelated, so an attacker can pass verification against an organization with no `webhook_secret` while asserting authority over a completely different, secret-protected organization's team.

### Finding Description
The broken binding: `repository_owner (used for verify_webhook_signature) == params.organization.login (used to authorize the Team mutation)`. In practice these are two independent JSON fields read from the same attacker-supplied POST body, so the equality does not hold.

Code path:
- <cite repo="Jaredbentat/shipit-engine--014" path="app/controllers/shipit/webhooks_controller.rb" start="24,30" end="30" />
- [1](#0-0)  — `repository_owner` prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`.
- `verify_signature` calls `Shipit.github(organization: repository_owner)` and uses that org's `GitHubApp#verify_webhook_signature`. [2](#0-1)  — if `webhook_secret` is blank (unset in config, documented as optional), this returns `true` unconditionally regardless of the actual signature.
- `MembershipHandler#find_or_create_team!` uses `params.organization.login` (a completely separate top-level payload key) to set `team.organization`, with no cross-check against `repository_owner` or the org used for verification. [3](#0-2) 

Attack: attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and a body containing:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "org-with-no-secret"}},
  "organization": {"login": "org-with-secret"},
  "team": {"id": 1, "name": "n", "slug": "s", "url": "u"},
  "member": {"login": "attacker-or-victim"}
}
```
`repository_owner` resolves to `org-with-no-secret`, so `verify_signature` checks the signature against that org's (blank) secret and passes unconditionally. `MembershipHandler` then creates/finds a `Team` tagged `organization: 'org-with-secret'` and adds the specified member to it — with zero cryptographic proof that the request came from GitHub for `org-with-secret`.

This escalates to authorization impact because `Team#organization` is the primary key joined against `Shipit.github_teams`/webhook configuration and team membership drives access control elsewhere in the app (e.g., team-gated permissions, `github_hooks` association keyed on `organization`). No existing guard (`drop_unhandled_event`, `ExplicitParameters` schema, or the `rescue GithubOrganizationUnknown`) checks that the verified org equals `params.organization.login`.

### Impact Explanation
An attacker can forge a `membership` event that adds an arbitrary GitHub user (including themselves) to a `Team` scoped to any organization configured in the Shipit instance, as long as at least one other configured organization has no `webhook_secret`. Since Shipit `Team` records back `Shipit.github_teams` based authorization, this is an escalation into team-based authorization for a fully unrelated, secret-protected organization — matching the High/Critical category "escalation into `Shipit.github_teams` authorization" / effectively an authentication-bypass-equivalent forgery, repeatable per request against any org configured on the instance.

### Likelihood Explanation
Preconditions: multi-organization Shipit deployment where at least one configured org has no `webhook_secret` (explicitly documented as optional in setup docs, so realistic). Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body and a `X-Github-Event: membership` header — no secrets, sessions, or tokens required. This is trivially repeatable against any organization name, whether or not it is actually configured on the Shipit instance is irrelevant to the "org-with-secret" target, since only the `team.organization` string and downstream authorization logic care about that value.

### Recommendation
In `MembershipHandler` (and any other handler that reads a top-level `organization`/`repository` field independent of `WebhooksController#repository_owner`), require that the organization asserted in the payload matches the organization actually used for signature verification (i.e., pass `repository_owner` through to handlers and assert equality with `params.organization.login`/`params.repository.owner.login` before trusting it). More robustly, do not allow unauthenticated/`nil` `webhook_secret` organizations to verify events for other organizations — `verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank, or at minimum the controller should reject events whose `organization.login` differs from `repository_owner`.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb` style, not to be placed under excluded paths but described here):
1. Stub `Shipit.github_config` (or however `Shipit.github` resolves per-org config) with two orgs: `org-with-no-secret` (no `webhook_secret`) and `org-with-secret` (`webhook_secret: 's3cr3t'`).
2. POST to `/webhooks` with `X-Github-Event: membership`, no/garbage `X-Hub-Signature`, and body:
   `{"action":"added","repository":{"owner":{"login":"org-with-no-secret"}},"organization":{"login":"org-with-secret"},"team":{"id":1,"name":"Test","slug":"test","url":"http://x"},"member":{"login":"attacker"}}`.
3. Assert response status is `200`/`:ok` (verification passed via the unsecured org).
4. Assert a `Shipit::Team` row exists with `organization == 'org-with-secret'` and that `attacker` was added as a member — i.e., `team.organization == 'org-with-secret'` while verification only ever occurred against `org-with-no-secret`, proving `repository_owner (verified org) != params.organization.login (authorized org)`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
