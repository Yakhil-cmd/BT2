### Title
Stale cached spoke/asset risk configuration is used after a `governance::execute` invalidates it during the `flash_position` receiver callback — (File: contracts/controller/src/context.rs)

### Summary
`process_flash_position` builds a single `Context` that caches `SpokeAssetConfig` (LTV, liquidation threshold, caps, listing status) on first read and never re-reads it for the rest of the invocation. The receiver callback executes inside `with_flash_guard`, which blocks reentry into controller verbs (`supply`, `borrow`, `repay`, `liquidate`, etc.) — but it does not block a call into the separate `governance` contract. A ready governance operation can therefore be executed from inside the callback, mutating the same spoke/asset config storage the controller already snapshotted. Post-callback deposit processing and risk finalization then evaluate the position against freed/invalidated configuration, which is a direct analog of use-after-free (CVE-2026-0885: use of an object after its backing state is destroyed).

### Finding Description
- `Context::cached_spoke_asset` caches a `SpokeAssetConfig` on first access and returns the cached copy for the remainder of the transaction (`contracts/controller/src/context.rs:192-204`). `require_listed_active_config`, `require_spoke_asset`, spoke caps, and the health-factor path all consume this cache (`context.rs:207-243`).
- In `process_flash_position`, the collateral assets and refund assets are validated and thereby cached *before* the callback: `validate_collaterals` → `require_can_supply` (`strategies/flash_position.rs:103`, `:202`) and `validate_refund_assets` → `require_listed_active_config` (`flash_position.rs:104-111`, `:241`).
- The callback `invoke_receiver` runs untrusted receiver code (`flash_position.rs:131-141`, `:297-323`). The flash guard blocks every state-changing *controller* entrypoint (see `tests/test-harness/tests/meta/reentrancy_matrix.rs`), but `governance::execute` of a ready operation is an in-scope unprivileged path that writes controller/spoke storage directly — it does not traverse the guard.
- After the callback, `process_deposit` and `strategy_finalize` (`flash_position.rs:146-153`) compute deposit credits, LTV-weighted collateral, liquidation threshold, and health factor entirely from the same stale `Context`. `reset_spoke_context` (`context.rs:177-181`) is never invoked on this path.

The concrete shape: a governance op that (a) lowers the collateral asset's LTV/liquidation threshold, (b) delists the collateral from the spoke, or (c) lowers the spoke's borrow cap is executed inside the callback. The flash-position finalize still credits the deposit and passes the health check using the pre-change parameters, so a position is committed that violates the now-current risk limits — or that references a supply position in an asset the spoke no longer lists, which liquidation/withdraw logic (`require_spoke_asset` on a fresh context) will subsequently fail to process correctly.

### Impact Explanation
- Under (a)/(b), an attacker opens debt that is undercollateralized by the protocol's own current parameters and abandons the account, leaving bad debt that `clean_bad_debt` socializes onto suppliers — protocol insolvency / theft of user funds.
- Under (b), a supply position in a delisted asset can be permanently or temporarily unprocessable by flows that re-derive `require_spoke_asset`/`require_listed_active_config` on a fresh context, freezing funds.
- Severity: Medium — real loss path, but gated by the existence of a ready governance operation affecting the target asset.

### Likelihood Explanation
- The trigger requires a ready (timelock-matured) governance operation touching the debt or collateral asset's spoke config — not attacker-controlled timing, but explicitly an allowed reachable path per the engagement scope.
- Everything else is fully attacker-controlled: the receiver contract is `require_wasm_receiver`-validated only, the callback is arbitrary, and the stale cache is guaranteed because `cached_spoke_asset` retains the first-read value.
- No privileged key, leaked secret, or off-chain component is needed at execution time; `execute` of a ready op is callable by any address in typical Soroban governor designs (verify `contracts/governance` executor authorization to confirm permissionless execution).

### Recommendation
- After the receiver callback in `process_flash_position` (and symmetrically in `multiply`/`swap_debt`/`swap_collateral`/`repay_debt_with_collateral`/`flash_loan` where a post-callback risk decision is made), call `cache.reset_spoke_context()` and re-validate `require_listed_active_config` for every collateral and the debt asset before `process_deposit`/`strategy_finalize`, so finalization uses post-callback configuration.
- Alternatively, apply the flash guard to controller admin/config setters reachable via `governance::execute`, so config cannot change mid-invocation.
- Re-check `require_hub_active`/`is_flashloanable`-relevant params after the callback for the same reason (these are also cached at `context.rs:77-83`, `:94-102`).

### Proof of Concept
1. Governance schedules an operation reducing collateral asset `C`'s liquidation threshold (or delisting `C`); the op matures and sits ready.
2. Attacker deploys a receiver contract implementing `execute_flash_position`. Inside the callback it (a) receives the flash-minted debt, (b) calls `governance.execute(op_id)` — not blocked by `with_flash_guard` — so controller storage now reflects the new config, then (c) returns collateral token `C` to the controller.
3. Back in `process_flash_position`, `collect_collateral_deposits` measures the deposit, `process_deposit` credits `C` using the stale cached `SpokeAssetConfig`, and `strategy_finalize` computes the health factor against the pre-change LTV/threshold, so the position commits.
4. Subsequent liquidations/withdrawals on a fresh `Context` see the new config: the position is under-threshold (immediate bad debt accrual) or references an unlisted asset (`SpokeError::AssetNotInSpoke` on owner-gated unwinds).
5. Caveat not fully verified within scope: the exact authorization required by `governance::execute` and whether controller admin setters consult the flash guard; both should be confirmed in `contracts/governance` and the controller config entrypoints. If `execute` is permissionless and setters are unguarded, the chain holds as described.
