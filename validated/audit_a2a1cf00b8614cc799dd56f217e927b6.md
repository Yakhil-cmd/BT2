### Title
Missing Delimiter (`\n`) Validation for AA-Supplied `feed_name`/`feed_value` Enables Data-Feed Key Injection - ([File: data_feeds.js])

### Summary
`readDataFeedValueByParams()` in `data_feeds.js` builds raw key-value-store lookup keys by concatenating attacker-controllable strings with the `\n` delimiter, but — unlike the unit-level `data_feed` message validator — it never rejects `\n` inside `feed_name` or `feed_value`. This is the ocore analog of the WSO2 issue: a delimiter character that should terminate/bound a field is allowed to pass through unsanitized into a lower-level protocol (here, the KV-store key format), letting an untrusted value "split" the intended key boundary and read a different field/record than intended.

### Finding Description
Ocore's data-feed storage keys are delimited with `\n`, e.g. `'dfv\n'+address+'\n'+feed_name` and `'df\n'+address+'\n'+feed_name+'\n'+prefixed_value+'\n'+mci` [1](#0-0) . Because these are literal string prefixes fed straight into `kvstore.createReadStream`/`createKeyStream` range queries, any `\n` embedded in `feed_name` (or in a string `value`) changes how many "fields" the resulting key actually spans, letting the query prefix land on keys that belong to a different, legitimately-posted feed name/value pair than the one requested.

When an oracle posts a `data_feed` message directly in a unit, ocore is careful to reject `\n` in both feed names and values: [2](#0-1) 
The same check is duplicated in AA-definition validation for literal `data_feed` payloads: [3](#0-2) 

However, `readDataFeedValueByParams()` — the function backing the oscript `data_feed()` primitive used inside AA formulas — only validates that `feed_name` is a non-empty string and that `feed_value`/`ifnone` are scalars; it performs **no `\n` check at all**: [4](#0-3) 
These `params` (including `feed_name` and `feed_value`) are evaluated from the AA's formula/oscript expressions, which can reference `trigger.data` — fields fully controlled by whoever sends the triggering unit to the AA (an unprivileged unit poster). Nothing upstream in the oscript evaluator sanitizes `\n` out of these strings before they reach `data_feeds.js`; the `\n`-stripping guard in `getSourceString`/AA-payload validation only applies to literal payloads baked into the AA's own `data_feed` message, not to values passed at call time via `data_feed(...)` inside formula code.

This is structurally identical to CVE-2019-10797's root cause: header/record delimiter validation is enforced in one code path (the direct/"trusted" path) but omitted in another path that ends up writing/reading the same delimiter-based structure, allowing attacker input to escape its intended field.

### Impact Explanation
An AA that reads oracle data feeds via `data_feed(oracles=[...], feed_name=$attacker_controlled, ...)` (a very common pattern for price oracles/DEX AAs) can have its lookup redirected to an unintended stored key when the attacker crafts a trigger whose `feed_name`/`feed_value` contains embedded `\n` bytes. Because the resulting KV-store range boundaries no longer correspond to the field the AA author intended to query, the AA can be made to read a different oracle-posted value (e.g., matching on a longer/shorter feed name that shares a `\n`-delimited prefix), causing the AA to act on attacker-influenced or unintended data. Depending on the AA's logic, this can translate into mispriced trades, incorrect payouts, or fund loss/freezing in the AA — i.e., concrete AA fund loss.

### Likelihood Explanation
Any user can post a unit that triggers an AA with attacker-chosen `trigger.data`, and any AA that forwards `trigger.data` fields into `data_feed()`'s `feed_name`/`feed_value` parameters (a normal and encouraged pattern for configurable oracle queries) is reachable without special privilege. The bug requires only crafting a string containing `\n`, which is trivial to include in JSON/oscript string literals.

### Recommendation
In `readDataFeedValueByParams()` (and any other caller of `readDataFeedValue`/`dataFeedExists` that accepts externally-influenced strings), reject `feed_name` and string `feed_value`/`ifnone` values containing `\n`, mirroring the exact checks already used in `validation.js` (`case "data_feed"`) and `aa_validation.js`, before they are used to build KV-store keys.

### Proof of Concept
1. Deploy (or use) an AA whose oscript calls `data_feed(oracles=[Oracle], feed_name=trigger.data.name, feed_value=trigger.data.value, ifnone='none')`, a pattern used to let callers request arbitrary configured feeds.
2. Have the legitimate oracle regularly post two distinct feeds under address `Oracle`, e.g. `FOO` and `FOO_ALT`, whose serialized keys share a `\n`-delimited prefix (`df\nOracle\nFOO...` vs `df\nOracle\nFOO_ALT...`).
3. Trigger the AA with `trigger.data.name = "FOO\n<crafted-suffix>"` such that the constructed `key_prefix` in `readDataFeedByAddress` (`'df\n'+address+'\n'+feed_name+'\n'+prefixed_value`, see `data_feeds.js:305`) coincides with the stored key range for `FOO_ALT`'s value rather than `FOO`'s, because the intended delimiter boundary between `feed_name` and the value/mci fields is no longer where the code assumes it is.
4. Observe the AA reads/acts on the value from the unintended feed (`FOO_ALT`) instead of rejecting the malformed name, demonstrating the field-boundary "splitting" and resulting data confusion. [5](#0-4)
