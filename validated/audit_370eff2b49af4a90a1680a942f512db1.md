### Title
Webhook signature verification selects the secret from an attacker-controlled organization field that is never bound to the repository the event handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App secret to verify the HMAC against using `repository_owner`, a value read straight out of the JSON payload (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, every registered `Webhooks::Handlers::Handler` subclass determines *which stack/repository to act on* using a completely different payload field, `repository.full_name`, and never re-checks that this repository actually belongs to the organization whose secret was used to verify the request. This is the same "verify against stale/wrong reference, act on a different one" ordering flaw as the `unstake` finding: the equality `organization_whose_secret_verified_signature == owner_of_repository_being_written_to` is never enforced.

### Finding Description
`verify_signature` resolves the `GithubApp` (and thus the HMAC secret) purely from `repository_owner`: [1](#0-0) [2](#0-1) 

`repository_owner` is derived entirely from attacker-supplied JSON, with a fallback to a *different* top-level payload key (`organization.login`) when `repository` is absent or has a different owner than intended.

Once `verified` is true, `create` dispatches the parsed body, unmodified, to the handlers for that event: [3](#0-2) 

Every handler resolves the target `Stack`/`Repository` from a separate field of the same payload, `repository.full_name`, with no cross-check against the organization used to select the verification secret: [4](#0-3) 

`PushHandler`, for example, uses that repository lookup directly to sync arbitrary stacks: [5](#0-4) 

The `status` handler goes further: it persists attacker-controlled `state`, `description`, `target_url`, and `context` fields verbatim onto a `Commit#statuses` record, as confirmed by the existing test suite: [6](#0-5) 

Because the organization used to select the verifying secret (`repository_owner`) and the organization that owns the repository actually mutated (`repository.full_name`) are two independent, attacker-controlled fields inside the same signed JSON body, an attacker who controls (or has legitimately been granted, e.g. as an org admin) the webhook secret for **one** organization configured in this Shipit instance can forge a payload that is correctly signed with that secret while pointing `repository.full_name` (and `repository.owner.login`) at a **different** organization/repository also tracked by the same Shipit instance. The signature check only proves "this body was HMAC'd with org A's secret" — never "org A owns the repository this body claims to update."

### Impact Explanation
This breaks the equality `organization_that_authenticated == owner_of(repository_written)`, matching the "an organization that authenticated versus the repository that is written" binding called out in scope. Concretely, using the `status` event, an attacker who knows/administers one configured org's webhook secret can inject a forged `success` CI status onto an arbitrary commit belonging to a victim stack in a different organization tracked by the same Shipit instance. If that stack has continuous deployment or a merge queue enabled and is otherwise gated only on that status context, this can lead to an unauthorized deploy or merge of attacker-chosen commits — a Critical impact ("an unauthorized deploy, rollback, or merge"). Other handlers (`push`, `check_suite`, `pull_request/*`) are reachable the same way, causing cross-repository job scheduling and merge-queue state changes for stacks the attacker's credential was never meant to control.

### Likelihood Explanation
Exploitability requires only knowledge of one org's webhook secret already configured on the Shipit instance (a realistic scenario for any Shipit deployment serving multiple organizations/teams, each managing their own GitHub App/webhook secret) plus knowledge of a victim repository's `full_name` tracked by the same instance (public information). No GitHub write access, Shipit session, or `ApiClient` token is required — only the ability to POST to the public `/webhooks` endpoint with a validly-signed-for-org-A body. This is a single-request forgery, not requiring any race condition or timing window.

### Recommendation
Bind the two identities together before the payload is handed to handlers: after `verify_webhook_signature` succeeds, verify that `payload.dig('repository', 'full_name')`'s owner matches `repository_owner` (the same field/org used to select the secret), and reject the request otherwise. Alternatively, have `Handler#stacks` resolve repositories scoped to the verified organization rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Attacker administers (or otherwise knows the webhook secret of) `org-attacker`, a GitHub organization configured in this Shipit instance's `config.github` settings.
2. Attacker builds a `status` event payload:
   ```json
   {
     "sha": "<victim-stack-commit-sha>",
     "state": "success",
     "context": "ci/required-check",
     "target_url": "http://x",
     "repository": {"full_name": "victim-org/victim-repo", "owner": {"login": "org-attacker"}}
   }
   ```
   (`repository.owner.login` is set to `org-attacker` so `verify_signature` selects the secret the attacker knows, while `repository.full_name` points at the real victim repo tracked by Shipit under `victim-org`.)
3. Attacker computes `X-Hub-Signature` with `org-attacker`'s secret over the raw body and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'org-attacker')` and successfully verifies the HMAC [1](#0-0) .
5. `StatusHandler` (dispatched via `Shipit::Webhooks.for_event('status')`) looks up the commit/stack via `repository.full_name = "victim-org/victim-repo"` [4](#0-3)  and creates a `success` status on the victim commit, as demonstrated by the existing controller test pattern [6](#0-5) .
6. If `victim-org/victim-repo`'s stack has continuous deployment enabled and gates only on that status context, this forged status can trigger an unauthorized deploy of the referenced commit.
