### Title
Any authenticated `ApiClient` can impersonate an arbitrary Shipit `User` via `X-Shipit-User`, causing deploys, rollbacks and merges to execute as that spoofed identity - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The API layer authenticates requests against an `ApiClient` token that is scoped only to a `stack_id` and a list of coarse operation scopes (`read:stack`, `deploy:stack`, etc.), but the *acting user* attributed to the resulting privileged action (`Deploy`, `Rollback`, `Task`, `MergeRequest`) is taken from the client-supplied `X-Shipit-User` header with no cross-check against the token's owner.

### Finding Description
`authenticate_api_client` in `app/controllers/shipit/api/base_controller.rb` only verifies that the HTTP-basic token maps to a valid `ApiClient` via `ApiClient.authenticate(token)`: [1](#0-0) 

`ApiClient.authenticate` and `check_permissions!` only reason about the *token* and its coarse `permissions`/`stack_id`, never about a specific human identity: [2](#0-1) 

Separately, `current_user` is derived purely from an unauthenticated, attacker-controlled request header, looked up by `login` with no relation whatsoever to which `ApiClient`/token was presented: [3](#0-2) 

This spoofed `current_user` is then passed directly as the actor for privileged, side-effecting operations:
- Deploy creation: `stack.trigger_deploy(commit, current_user, env: params.env, force: params.force, allow_concurrency:)` [4](#0-3) 
- Merge request approval/merge trigger: `MergeRequest.request_merge!(stack, params[:id], current_user)` [5](#0-4) 

Critically, `User#github_api` uses that specific user's *own* stored GitHub OAuth token when one exists, falling back to the app-level client only if the user has none: [6](#0-5) 

The test suite documents this trust as intentional behavior but never verifies the header against the presenting `ApiClient`'s `creator`: [7](#0-6) 

**Binding broken:** `identity authenticated by the ApiClient token (the token's creator/scope)` should equal `identity attributed to and acting for the resulting Deploy/Rollback/MergeRequest`. Because `X-Shipit-User` is trusted unconditionally, `token-authenticated identity ≠ acting identity`: any caller holding a valid `ApiClient` token with `deploy:stack` permission on a given stack can set `X-Shipit-User` to the login of any other Shipit user (e.g. an org admin) and have the action recorded as, and in the merge case *executed with the GitHub credentials of*, that victim.

### Impact Explanation
This crosses the "unauthorized deploy, rollback, or merge" Critical bucket explicitly listed as in-scope impact: a possessor of any single scoped `ApiClient` token (e.g. one issued to a narrow CI integration with only `deploy:stack` on one stack) can forge the identity for that action to any registered `User`, and for `MergeRequestsController#update`, the merge is actually carried out via that spoofed user's real `github_access_token`, i.e. cross-repository / unauthorized merge action performed under someone else's GitHub authorization.

### Likelihood Explanation
Any party that already possesses a legitimately-issued `ApiClient` token (which is common - CI bots, deploy scripts, third-party integrations routinely hold these) can perform this with a single extra HTTP header on an otherwise normal, permitted API call; no additional secret, session, or GitHub credential is required to spoof the identity.

### Recommendation
`current_user` for API requests must be bound to the authenticated `ApiClient`'s `creator`, not to an unauthenticated request header, or the header must be cryptographically tied to the client credential (e.g. verified against `api_client.creator.login`) before being trusted for attribution/authorization purposes in `Deploy`, `Rollback`, `Task`, and `MergeRequest` flows.

### Proof of Concept
1. Obtain any valid `ApiClient` token scoped to `deploy:stack` for a target stack (e.g. from a CI pipeline environment).
2. `POST /api/stacks/:id/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: <victim-admin-login>`.
3. Observe (per `app/controllers/shipit/api/deploys_controller.rb`) that the resulting `Deploy.user` is the victim, and for `PATCH /api/stacks/:id/merge_requests/:id`, the merge is executed via `MergeRequest.request_merge!(stack, id, current_user)` using the victim's own `github_access_token` (`app/models/shipit/user.rb#github_api`), an unauthorized action performed under the victim's GitHub identity.
