### Title
Scoped API tokens can read CCMenu build status of any stack, bypassing the token's stack authorization - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the `stack` accessor inherited from `Api::BaseController` and looks up the stack directly by `params[:stack_id]` instead of going through the stack-scoped `stacks` collection. This breaks the invariant that a stack-scoped `ApiClient` token can only touch the stack it was authorized for.

### Finding Description
`Api::BaseController` enforces per-token stack scoping through two cooperating methods: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a single stack, and `stack` resolves `params[:stack_id]` only within that restricted set — this is the binding: `stack a token authorises == stack it touches`.

`Api::CCMenuController`, however, defines its own `stack` private method that ignores this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, not through `current_api_client`'s scoped `stacks` relation. The `require_permission :read, :stack` before_action only checks the token's permission list string via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` has no knowledge of `stack_id` — it only checks that `"read:stack"` is present in `permissions`. The stack_id restriction is enforced exclusively by the `stacks`/`stack` scoping in the base controller, which `CCMenuController` bypasses.

This particular token is generated for end users via `CCMenuUrlController#fetch`, which explicitly creates a per-stack `ApiClient` with only `read:stack` permission, intending it to be scoped to `stack`: [4](#0-3) 

However `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` does not set `stack_id` on the client at all — every user gets a single global "CCMenu Client" `ApiClient` with `read:stack` and no `stack_id` binding, so in the current implementation this specific path isn't scoped either. But the broader design intent — demonstrated by `Api::BaseController#stacks`/`#stack` — is that a stack-scoped `ApiClient` (`stack_id` set, as seen in the `here_come_the_walrus` fixture) must only be able to touch its own stack across all API controllers. `CCMenuController` is the one controller in `app/controllers/shipit/api/**` that opts out of this enforcement, so any token holder with `read:stack` permission (scoped or not) can pass an arbitrary `stack_id` to `Api::CCMenuController#show` and read deploy/build status for a stack outside their token's intended scope.

### Impact Explanation
This is an authorization-scope escalation: `equality(token's authorized stack, stack whose state is read)` fails. A caller holding a stack-scoped API token can enumerate `stack_id` values and read another stack's latest deploy state (`lastBuildStatus`, `lastBuildLabel`, lock state) via `Api::CCMenuController#show`, i.e., unauthorized read of stack state across repositories — matching the "escalation into authorization scope / unauthenticated-for-that-resource read of stack state" High-impact category.

### Likelihood Explanation
Any holder of a valid `ApiClient` token with `read:stack` permission (including one intentionally scoped to a single stack via `stack_id`) can trigger this simply by supplying a different `stack_id` in the request — no additional privilege or secret is required beyond a token that is already expected to be confined to one stack.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-respecting `stack`/`stacks` methods from `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`), so CCMenu lookups honor `current_api_client.stack_id`.

### Proof of Concept
1. Create a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (as in the `here_come_the_walrus` fixture pattern).
2. Using that token, call `GET /api/stacks/:stack_id/ccmenu.xml` with `stack_id` set to Stack B (a different stack the token was never scoped to).
3. Observe `Api::CCMenuController#stack` resolves Stack B directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction enforced everywhere else, and returns Stack B's deploy/build status in the XML response.
