### Title
Unauthenticated cross-repository commit status forgery via organization-based webhook signature bypass - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using the *organization* named in the incoming payload, while `StatusHandler#process` mutates commit status data by looking up commits **globally by SHA, with no repository or organization scoping at all**. This breaks the equality that should hold between "the organization whose secret authenticated this request" and "the repository/stack whose state is written," exactly the class of binding failure described in the report (values computed/verified in one context are silently assumed equal to values used in another).

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to check the signature against based on a value taken straight out of the unauthenticated payload: [1](#0-0) [2](#0-1) 

The actual signature check, `GitHubApp#verify_webhook_signature`, returns `true` unconditionally whenever that organization's `webhook_secret` is blank (documented as *optional* in `docs/setup.md`): [3](#0-2) 

So for any organization onboarded into the Shipit instance without a configured webhook secret, `verify_signature` passes for *any* payload, with no HMAC check whatsoever — the attacker only needs to claim `repository.owner.login` (or `organization.login`) as that no-secret org.

Once past `verify_signature`, the event is dispatched to handlers using only the event type, not the authenticated organization: [4](#0-3) 

Most handlers scope their side effects to the repository named in the payload via `Handler#stacks`/`#repository_name` (`payload.dig('repository', 'full_name')`), e.g. `PushHandler`: [5](#0-4) [6](#0-5) 

`StatusHandler`, however, does **not** scope by repository at all — it resolves target commits purely by SHA across the entire database: [7](#0-6) 

This is the broken binding, stated as an equality that the engine fails to enforce:
`organization_that_authenticated(payload.repository.owner.login)` **should equal** `repository_owner(of the commit whose status gets written)`, but `StatusHandler` never checks this — it only requires that the SHA happen to match a `Commit` row belonging to *any* stack in the installation, regardless of which organization's (possibly secret-less) webhook validated the request.

### Impact Explanation
An attacker with no Shipit account, no API token, and no GitHub write access to any tracked repository can:
1. Identify (or find) any organization configured in the Shipit instance that has no `webhook_secret` set (an explicitly optional field per `docs/setup.md`).
2. POST directly to `/webhooks` with `X-Github-Event: status` and a body such as `{"sha": "<known commit sha of an unrelated, higher-trust stack>", "state": "success", "repository": {"owner": {"login": "<org-without-secret>"}}}`.
3. Because that organization's secret is blank, `verify_webhook_signature` returns `true` with no signature required at all.
4. `StatusHandler` looks up `Commit.where(sha: params.sha)` across the whole database (not scoped to `<org-without-secret>`) and writes a forged `success`/`failure` status for a commit belonging to a completely different, unrelated repository/stack.

Since commit statuses in Shipit are the mechanism used to represent CI state for gating deploy eligibility and merge-queue safety checks, forging them for an arbitrary stack can bypass CI/status-based deploy safeguards for a repository the attacker has no relationship with — i.e., a cross-repository write that can contribute to an unauthorized deploy or merge decision on a stack the attacker never authenticated against.

### Likelihood Explanation
The prerequisite (at least one onboarded organization with no webhook secret configured) is explicitly presented as an optional/likely-skipped setting in the project's own setup documentation, making this a realistic multi-tenant misconfiguration rather than a hypothetical edge case. No credentials, tokens, or repository access of any kind are required from the attacker — only a plausible commit SHA belonging to the target stack, which is often publicly discoverable via GitHub itself.

### Recommendation
`StatusHandler` (and any other handler that does not currently do so) must scope its data lookups/writes to the repository/organization that the webhook was actually verified against, not merely to whatever data happens to match in the database. Additionally, treat an unset `webhook_secret` as a hard failure (or restrict such organizations to no-op/logging-only behavior) rather than an implicit "always trust" bypass, since it currently causes `verify_webhook_signature` to accept unsigned, fully attacker-controlled payloads.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<sha belonging to a commit on Stack X, a repo the attacker has no access to>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "<org-configured-without-webhook_secret>" } }
}
```
Because the target organization has no `webhook_secret`, `GitHubApp#verify_webhook_signature` returns `true` unconditionally (no `X-Hub-Signature` header is even required), and `StatusHandler#process` writes a forged `CommitStatus` for the named `sha`, regardless of which stack/organization actually owns that commit.

**Note on verification limits:** I traced the write path (`Commit.where(sha:).create_status_from_github!`) but did not fully trace, within this investigation, the exact downstream code that consumes `CommitStatus` to gate deploy/merge decisions (e.g. `Stack`/`Commit` "detailed status" logic). The authorization-boundary break itself (unscoped, potentially unauthenticated cross-repository write) is confirmed directly from the cited files; the precise blast radius on deploy/merge gating should be validated against `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb` status-checking logic in a follow-up session.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
