### Title
Unchecked list-length field drives out-of-bounds `Cursor::consume` in vote state view parsing - (File: vote/src/vote_state_view/field_frames.rs)

### Summary
`LockoutListFrame::read`, `LandedVotesListFrame::read`, `AuthorizedVotersListFrame::read`, and `EpochCreditsListFrame::read` all read an attacker/validator-controlled 8-byte length prefix from vote account data, convert it to `u8`, and then blindly call `cursor.consume(frame.total_item_size())` — the byte count computed from that length — without ever checking that `cursor` actually has that many bytes remaining. This mirrors the FNET IPv6 hop-by-hop extension header bug: a length field taken from untrusted input is used to skip/advance through a buffer with no validation against the buffer's real remaining size.

`total_item_size()` is `self.len() * self.item_size()` [2](#0-1) . The `len` byte comes directly from the vote account's raw bytes and is only checked to fit in a `u8` (0–255) — it is never checked against `cursor.remaining()`/the account data's actual length before `consume()` is called. `std::io::Cursor::consume` (a `BufRead` trait method) simply advances the internal position; it does not validate that the requested amount is available, so the cursor position can be pushed past the end of the underlying slice. The identical unchecked pattern repeats for `LandedVotesListFrame::read`, `AuthorizedVotersListFrame::read`, and `EpochCreditsListFrame::read` [3](#0-2) [4](#0-3) [5](#0-4) .

Once the cursor position is beyond the buffer end, any subsequent `ListView`/`read_item` access that computes item slices via `item_data.as_ptr()` and casts to a `#[repr(C)]` POD struct (`LockoutItem`, `AuthorizedVoterItem`, `EpochCreditsItem`) using raw unsafe pointer reads [6](#0-5)  can read past the slice bounds if the resulting offset/length arithmetic (`cursor.position()` + item math) is used to index into the original account-data slice without an explicit remaining-length check — exactly analogous to `_fnet_ip6_ext_header_handler_options` trusting an unchecked extension-header length to advance a packet cursor into unallocated/out-of-range memory.

### Impact Explanation
This code path parses vote-program account state (`VoteStateView`), which is exercised whenever a vote transaction or any instruction reading a vote account's state is processed on a validator (e.g., during vote processing in `programs/vote`, and RPC/bank paths that construct a `VoteStateView` from raw account bytes). Since the length field is taken straight from account data with no cross-check against the actual buffer size before consuming, a maliciously crafted vote account (which any transaction sender who owns/creates a "vote-owned" account can shape, subject to the vote program's own state layout invariants) could push the cursor position out of bounds. Depending on how downstream code uses the resulting (unbounded) offsets to slice the original buffer, this can manifest as an out-of-bounds read (panic/DoS) when validators process the malformed vote account, potentially causing a validator crash or divergent behavior between nodes that handle the malformed data differently — a transaction-triggered availability impact analogous to the CVE's DoS classification.

### Likelihood Explanation
Likelihood depends on whether every call site that ultimately slices the raw account-data buffer using cursor/frame-derived offsets independently re-validates against the buffer length (some code, like `LockoutListFrame`'s own bounds, is silently swallowed since `consume()` never errors). Given the number of duplicated `read()` implementations that all skip this check, and that `Cursor::consume` is documented not to panic or validate, this is a systemic pattern rather than an isolated slip, increasing the likelihood that at least one call path is reachable with attacker-influenced vote account bytes.

### Recommendation
In each `*Frame::read` implementation (`LockoutListFrame`, `LandedVotesListFrame`, `AuthorizedVotersListFrame`, `EpochCreditsListFrame`, and the `PriorVotersFrame`/`RootSlotFrame`/`BlsPubkeyCompressedFrame` variants that also call raw `consume`), validate that `cursor.get_ref().len() - cursor.position() as usize >= frame.total_item_size()` (or equivalent remaining-length check) before calling `cursor.consume(...)`, returning `VoteStateViewError::AccountDataTooSmall` otherwise — mirroring the fix pattern already used for the initial `read_u64`/`read_u8` fields.

### Proof of Concept
Conceptual PoC (cannot be executed here, but illustrates the mechanism):
1. Construct a vote account whose serialized state encodes a `votes` (or `authorized_voters`/`epoch_credits`) length prefix such that `len * item_size()` exceeds the remaining bytes in the account's data buffer, while the account data itself is truncated to just past the length field.
2. Have this data loaded via `VoteStateView` parsing (e.g., triggered by a vote instruction interacting with the vote account, or any RPC/bank code path that builds `VoteStateView` from the account's raw bytes).
3. Observe that `cursor.consume(...)` silently advances past the buffer end; if a later call computes an item slice (e.g., `AuthorizedVotersListFrame::get_authorized_voter` iterating via `ListView`) using that now out-of-range position/length, it reads out-of-bounds memory relative to the original slice, producing a panic (bounds-checked slicing) or, given the `unsafe` pointer casts in `read_item`, a genuine OOB memory read.

*Note: full confirmation of an actual OOB read (versus a bounds-checked panic) requires inspecting `list_view.rs`'s `ListView::into_iter()`/indexing implementation, which was not retrievable within the available search budget — I was unable to fully verify whether `ListView` independently re-clamps offsets against the real buffer length before dereferencing. This should be checked directly in `vote/src/vote_state_view/list_view.rs` to confirm whether the missing bounds check in `field_frames.rs` is fully mitigated downstream or is directly exploitable.*
