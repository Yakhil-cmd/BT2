### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `sha` equality, with no verification that the webhook's originating repository matches the repository/stack that owns the matched `Commit` record. Because git commit SHAs are content-addressed and are naturally shared across forks (and, per the threat model, can be made to collide), any repository able to deliver a `status` webhook can write a `CommitStatus` onto a commit that belongs to a completely different stack/repository it does not control.

### Finding Description
The broken binding is: `commit.repository == status_event.repository` is assumed true whenever `commit.sha == status_event.sha`, which is false. `StatusHandler` declares its params schema without any `repository`/`repository_name` field at all: [1](#0-0) 

and `process` performs the lookup and write purely on `sha`: [2](#0-1) 

Because the schema never captures the payload's `repository` object, there is structurally no way for `process` to scope the query to the stack/repository that actually triggered the event — the omission is in the handler's own contract, not just a missing runtime check. The `Webhooks.for_event('status')` dispatch table simply instantiates `Handlers::StatusHandler` and calls `process` for every delivered `status` event: [3](#0-2) 

Exploit flow: an attacker owns/controls a repository (their own fork, which shares commit ancestry — and therefore SHAs — with the upstream victim repository, or per the threat model can engineer a colliding SHA). They observe a victim commit SHA via Shipit's public/unauthenticated stack views, then cause (or directly trigger, e.g. via `POST /webhooks`) a `status` event referencing that SHA from a context they control. `StatusHandler#process` matches any `Commit` row across the entire Shipit installation with that SHA — regardless of which stack/repository it belongs to — and calls `commit.create_status_from_github!(params)`, writing a forged status onto the victim's commit/stack.

Existing guards do not prevent this: webhook signature verification (`GitHubApp#verify_webhook_signature`) only proves the payload was delivered through a valid GitHub App webhook channel — it authenticates *that GitHub sent it*, not *which repository's authority the payload should be scoped to*. `drop_unhandled_event` only filters unregistered event types, not payload content. The `ExplicitParameters` schema for `StatusHandler` never even models the `repository` field, so no downstream scoping is architecturally possible.

### Impact Explanation
A successful forged status write mutates `CommitStatus` state for a commit belonging to a stack/repository the attacker does not own or authenticate against — this is a payload for one repository mutating another's commit/stack state, directly matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). Since Shipit typically gates merges/deploys on required statuses, this can be used to mark a victim's commit as passing (or failing) checks it never actually satisfied, influencing deploy/merge decisions for a stack the attacker has no access to. The attack is repeatable against any commit SHA the attacker can discover or produce a match for, across arbitrary stacks/repositories tracked by the same Shipit instance.

### Likelihood Explanation
The attacker needs: (1) ability to observe or predict a victim commit SHA (feasible via Shipit's public commit/stack views, as referenced), and (2) a way to get a `status` webhook processed for that SHA — either by having a fork that legitimately shares that commit in its ancestry (very common, zero cost, no cryptography required) and installing/using the GitHub App on that fork, or by directly emulating a webhook body if signature enforcement can be satisfied under the stated threat model. The fork-sharing case in particular requires no exotic SHA-collision engineering at all — it is a routine consequence of git's content-addressed history — making this readily achievable with an unprivileged GitHub account.

### Recommendation
Extend `StatusHandler`'s params schema to require and capture the webhook payload's `repository` (owner/name), and scope the `Commit` lookup to commits whose owning stack's repository matches that identity (e.g., join through `Commit -> Stack -> Repository` and filter by `full_name`) before calling `create_status_from_github!`. Reject or ignore events where the repository does not match.

### Proof of Concept
Add to a webhooks/handlers test file (outside `test/**` exclusion applies to review only, actual test would live in the engine's test suite as normal): construct two `Commit` records with an identical `sha` but belonging to two different `Stack`/`Repository` combinations (`repo_a`, `repo_b`). Invoke `StatusHandler.new(payload_with_repository: repo_a_metadata, sha: shared_sha, state: 'success').process`. Assert that only the `Commit` under `repo_a` receives a new `CommitStatus`, and that the `Commit` under `repo_b` does not — the current code will incorrectly create statuses on both, proving the missing repository binding.
