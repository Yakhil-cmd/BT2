### Title
Membership webhook trust binding break: verified GitHub organization is not bound to the `Team` record mutated, allowing cross-organization escalation into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the secret of the GitHub *organization* named in the payload, but the `membership` event handler mutates a `Team` record looked up solely by an attacker-supplied numeric `team.id`, with no check that the team actually belongs to the organization whose signature was verified. This is the same class of bug as the GMX finding: one field (`organization.login`) is the basis of the trust decision, while a different, independently-controlled field (`team.id`) is what the privileged write actually acts on, and there is no mechanism binding the two.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to validate the HMAC signature against using `repository_owner`, which for events without a `repository` key falls back to `params.dig('organization', 'login')`: [1](#0-0) 

Once the signature is accepted for that organization, the raw parsed JSON body is dispatched unchanged to the registered handler for the event: [2](#0-1) 

For the `membership` event, `MembershipHandler#process` looks up (or creates) the `Team` purely by the attacker-controlled `team.id` field, and mutates its membership without ever checking that the found team's `organization` matches `params.organization.login` (the field the signature was actually verified against): [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` only sets `team.organization` inside the creation block, which does **not** run when a `Team` with that `github_id` already exists (e.g. a team already tracked by Shipit because it's used for `Shipit.github_teams` authorization). So if an attacker who administers *any* organization configured in Shipit's `github:` secrets (and therefore knows that organization's own `webhook_secret`) sends a signed `membership` payload with:
- `organization.login` = their own org (signature verifies successfully)
- `team.id` = the GitHub team ID of a *different* organization's privileged team (e.g. the team referenced by `github.oauth.teams`)
- `member.login` = their own account
- `action` = `'added'`

then `team.add_member(member)` runs against the *existing, unrelated* privileged `Team` record, adding the attacker as a member — completely bypassing the fact that their signature only proved control of their own, unrelated organization.

This breaks the equality: `organization authenticated by verify_signature == organization that owns the Team being written by MembershipHandler`. The GMX report is about a factor value that is used to gate a payout but which nothing lets a keeper set safely; here, the analogous "keeper action" is the webhook signature check, and the analogous "factor" is which `Team` object gets mutated — there is no mechanism binding the verified organization to the team record actually written.

### Impact Explanation
Successful exploitation lets an attacker who controls webhook-signing credentials for one organization onboarded to a shared Shipit instance add themselves (or anyone) to another organization's `Team`. If that `Team` is one of the entries in `Shipit.github_teams` (used by `Authentication#force_github_authentication` and `current_user.authorized?` to gate access to the entire application, including stack creation, deploys, and API client management), this is a direct escalation into Shipit's authorization boundary — explicitly listed as a valid High-impact outcome (escalation into `Shipit.github_teams` authorization). [4](#0-3) [5](#0-4) 

### Likelihood Explanation
Any tenant configured in Shipit's multi-organization `github:` secrets can compute a valid signature for their own organization at will (they control their own webhook secret / GitHub App configuration). The only additional requirement is guessing or discovering the numeric GitHub `team.id` of the target privileged team, which is not treated as a secret by GitHub and can often be obtained via the GitHub API or UI for teams the attacker can otherwise observe. No Shipit credential, `ApiClient` token, or GitHub App private key is required — only an unauthenticated POST to `/webhooks` with a payload signed using the attacker's own, legitimately-known secret.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally for all handlers that look up existing records by attacker-supplied IDs), verify that the found `Team#organization` matches `params.organization.login` before allowing any mutation, and reject/no-op if they differ instead of silently operating on a record belonging to a different, already-verified-for-a-different-organization team.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `attacker-org` (attacker administers this org and knows its `webhook_secret`) and `victim-org` (whose `victim-org/admins` team, with GitHub team id `1234`, is listed in `Shipit.github_teams`).
2. Attacker computes `sha1=` HMAC over the JSON body using `attacker-org`'s webhook secret:
```json
{
  "action": "added",
  "team": { "id": 1234, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/1234" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker" }
}
```
3. POST this to `/webhooks` with header `X-Github-Event: membership` and the computed `X-Hub-Signature`.
4. `verify_signature` validates successfully against `attacker-org`'s secret (`repository_owner` resolves to `attacker-org` via the `organization` fallback).
5. `MembershipHandler#process` calls `Team.find_or_create_by!(github_id: 1234)`, finds the pre-existing `victim-org/admins` team, and calls `team.add_member(User.find_or_create_by_login!('attacker'))`, granting the attacker's Shipit `User` membership in `victim-org/admins` — satisfying `Shipit.github_teams` authorization for the entire application despite never proving any relationship to `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

          team = find_or_create_team!
