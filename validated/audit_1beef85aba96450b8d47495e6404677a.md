### Title
Asset cap defined via a trigger-controlled formula can silently evaluate to `0`/falsy, flipping a capped asset into an uncapped one and allowing repeated re-issuance - (File: aa_composer.js)

### Summary
In AA-defined assets, the `cap` field of an `asset` message can be a formula (e.g. `"{trigger.data.cap otherwise ''}"`, see `test/samples/create_an_asset.oscript`). `aa_validation.js` only checks at static-validation time that the formula is syntactically valid, not what it evaluates to at trigger time. When the trigger sender supplies a value that makes the cap formula evaluate to `0` (or another falsy value), every place in the codebase that decides "is this asset capped?" uses a plain truthy check on `objAsset.cap`, so a `cap = 0` asset is silently treated as **uncapped**, exactly like the reported bug where a market parameter defaulting to `0` silently disables the loan's liquidation-eligibility check (`bidDefaultDuration[_bidId] == 0` ⇒ "cannot liquidate").

### Finding Description
When an AA issues an asset, the `cap` payload can be supplied as a formula string and is evaluated when the AA composes the `asset` message, based on inputs the trigger sender or AA state fully controls (e.g. `trigger.data.cap`). Validation of the AA definition (`aa_validation.js`, case `'asset'`, lines ~230-242) only ensures the formula parses; it never inspects the runtime value. [1](#0-0) 

Every consumer of `objAsset.cap` treats it with a bare truthy test rather than checking `"cap" in objAsset` or `cap !== null`:

- In `aa_composer.js`'s `issueAsset()`, the decision of whether the asset was "already issued once" (capped, single-issue) or can be freely re-issued (uncapped, multi-issue) hinges on `if (objAsset.cap) {...} else {...}`: [2](#0-1) 

- The same truthy pattern is repeated in `indivisible_asset.js` (`objAsset.cap ? "max_issued_serial_number=0" : "1"`) and `inputs.js` (`if (objAsset.cap){...} else {...}`), and in formula evaluation `asset[...]` accessor (`cb(convertValue(objAsset.cap || 0))`), meaning any code path that later reads `asset[$asset].cap` for logic decisions also loses the distinction between "no cap" and "cap of 0". [3](#0-2) [4](#0-3) 

If `cap` evaluates to `0` when the asset message is actually composed (a value that is not explicitly rejected the way a static-JSON `cap: 0` would be caught by `isPositiveInteger` in `validateAssetDefinition`/`aa_validation.js`, because the formula path is not validated for its result), the resulting on-chain asset object stored/consumed downstream has `cap === 0`, which is falsy. `issueAsset()` in `aa_composer.js` will then take the "uncapped" branch of `if (objAsset.cap) {...} else {...}` on every subsequent trigger, letting the AA (and effectively any attacker who can trigger this AA's issuance path) mint the asset an unbounded number of times, even though the AA author's intent (and possibly documented design, similar to the "cap" field's purpose of restricting the definer to a single fixed-supply issuance) was a hard, single, capped issuance.

This is structurally the same bug class as the reported Teller issue: a numeric configuration value that is meant to gate/restrict a critical action is allowed to take the value `0`, and `0` is reused elsewhere as the sentinel for "feature disabled/no restriction," so the restriction silently and permanently disappears without any explicit validation error.

### Impact Explanation
If an attacker can drive the cap formula to evaluate to `0` for an asset intended to be capped/fixed-supply (e.g. by controlling `trigger.data.cap` or another state value the formula reads), the asset silently becomes an unlimited-supply asset. Any user or AA holding balances or trading pairs denominated in that asset (which was advertised/expected to be scarce/capped) suffers dilution — this is a supply-inflation bug affecting all holders and counterparties of the asset, matching the "Medium" bar of AA fund loss via unintended supply inflation.

### Likelihood Explanation
Requires an AA author to define an asset's `cap` via a formula that is influenced by attacker/trigger-controlled data (a documented, supported pattern per `test/samples/create_an_asset.oscript` and `test/aa.test.js`'s `cap: "{trigger.output[[asset=base]]}"`). It is a realistic pattern for any AA offering configurable token creation, and no runtime check prevents `cap` from evaluating to `0` at the time the `asset` message is finally composed, unlike the static `cap: 0` case in `validateAssetDefinition`, which is explicitly rejected. Likelihood is moderate: it requires a specific AA design (dynamic cap) but no privileged access.

### Recommendation
Distinguish "uncapped" from "cap = 0" using a strict `("cap" in objAsset)` / `typeof objAsset.cap === 'number'` check (with an explicit runtime rejection of `cap === 0`) instead of the truthy checks in `aa_composer.js::issueAsset`, `indivisible_asset.js`, `inputs.js`, and `formula/evaluation.js`. Additionally, when an AA's `asset` message cap is defined by a formula, validate at message-composition time (`aa_composer.js`) that the evaluated cap is a strictly positive integer before creating the asset, bouncing the trigger otherwise (analogous to the static check already done for literal numeric caps in `validateAssetDefinition`/`aa_validation.js`).

### Proof of Concept
1. Deploy an AA whose `asset` message sets `cap: "{trigger.data.cap otherwise ''}"` and `issued_by_definer_only: true` (pattern taken from `test/samples/create_an_asset.oscript`).
2. Send a trigger with `data.cap = 0` (or any expression driving the formula result to `0`) to define the asset. `aa_validation.js`'s static check only validates that `cap` is a valid formula string, not its evaluated value, so the message passes validation.
3. The resulting `objAsset.cap` stored/returned is `0`.
4. On a subsequent issuance trigger, `aa_composer.js::issueAsset()` evaluates `if (objAsset.cap) {...} else {...}` and takes the "else" (uncapped) branch, issuing new units keyed by `max_serial_number+1` instead of refusing re-issuance as a capped asset would (`if (rows.length > 0) return cb2('already issued')`).
5. Repeated triggers keep issuing more of the "capped" asset, inflating supply beyond the intended fixed cap.
