### Title
Cross-repository stack mutation via unsigned `repository.full_name` in PR webhook handlers - ([File: app/models/shipit/repository.rb], [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret used for HMAC verification) using `repository_owner`, derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. However, the actual repository record acted upon by every `pull_request.*` handler is resolved later, independently, via `Repository.from_github_repo_name(params.repository.full_name)`. There is no check anywhere that the `owner` segment of `full_name` matches `repository_owner`. Both fields live in the same unsigned JSON body, so an attacker who legitimately controls one GitHub organization/app installed on Shipit can send a validly-signed webhook whose signature was checked against their own org's secret while `repository.full_name` names a victim's repository/owner.

### Finding Description
The intended binding is: `Repository.from_github_repo_name(params.repository.full_name).owner == repository_owner` (the value used to select the signing secret at `app/controllers/shipit/webhooks_controller.rb:25` [1](#0-0)  and `app/controllers/shipit/webhooks_controller.rb:59-62` [2](#0-1) ). This equality is never checked.

`verify_signature` only proves the request body was HMAC-signed by *some* configured GitHub App/org's secret - it says nothing about which repository's data inside that same body should be trusted. `Repository.from_github_repo_name` performs an exact, case-normalized lookup with no cross-check against the org that authenticated the request [3](#0-2) . Every PR handler (`ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, etc.) resolves `repository` purely from `params.repository.full_name` and then operates `review_stacks`/`stacks` scoped to that resolved `Repository`, e.g. `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb:49-53` [4](#0-3)  followed by `review_stack.archive!` at line 44 [5](#0-4) , which triggers `stack.deprovision` and `stack.archive!` inside `ReviewStackAdapter#archive!` [6](#0-5) . `OpenedHandler` similarly calls `find_or_create!`, creating a review stack under the victim repository [7](#0-6) .

Exploit flow: attacker controls `attacker-org`, which is configured as its own GitHub App in Shipit's multi-org config (`config/secrets.*.yml` "somegithuborg"/"someothergithuborg" pattern, confirmed supported at `docs/setup.md:182-209` [8](#0-7) ), and therefore knows its own `webhook_secret`. Attacker crafts a `pull_request` JSON payload where `repository.owner.login` (or top-level `organization.login`) is `attacker-org` (so `verify_signature` resolves and validates against the attacker's own secret via `Shipit.github(organization: repository_owner)` at `lib/shipit.rb:170-180` [9](#0-8) ), but sets `repository.full_name` to `"victim-owner/victim-repo"` and picks `number`/`pull_request.head.ref` to target/create a specific review-stack environment. Because the two fields are never cross-validated, the handler resolves the *victim's* `Repository` and mutates its `review_stacks`/`stacks` (archive, unarchive, or create-and-provision), even though the signature only proved the *attacker's* org's authenticity.

Existing guards do not stop this: `verify_signature` checks HMAC validity per-org but has no knowledge of `full_name`; `ExplicitParameters` schemas (`params do ... end` blocks) validate types/presence, not cross-field consistency; `Repository.from_github_repo_name`'s validations (`ascii_only`, lowercase regex) only constrain what values *can* be stored as a `Repository`, not which repository the handler is authorized to touch for a given signed org.

### Impact Explanation
Attack allows an authenticated-signature webhook from Organization A to archive, unarchive, or create/provision a review stack belonging to Organization B's repository - i.e., "a payload for one repository mutating another's stack" - matching the Critical severity bucket. Consequences include unauthorized deprovisioning of a live review-stack deployment, forced creation of a stack (queued for provisioning, which runs deploy commands) under an environment name chosen by the attacker, and repeated/arbitrary abuse against any repository configured in Shipit as long as review stacks are enabled for it. Blast radius spans all repositories hosted in a multi-tenant Shipit instance where more than one GitHub organization/app is configured, since the check that binds the signing identity to the acted-upon repository is entirely absent.

### Likelihood Explanation
Exploitability requires: (1) a multi-org Shipit deployment (the documented "Using Multiple GitHub Applications" configuration), (2) attacker legitimately controls at least one configured org/app (their own repos), (3) `review_stacks_enabled`/appropriate `provisioning_behavior` set on the victim repository (standard feature usage, not attacker-controlled but common), and (4) attacker must guess/know the victim's PR number or target environment to hit an existing stack, which is easily discoverable (PR numbers are public, sequential, and visible on GitHub). No secrets beyond the attacker's own webhook secret are needed, and the request is a plain unauthenticated POST to `/webhooks`. This is fully repeatable against any repository/PR-number combination.

### Recommendation
In `WebhooksController` or in a shared `Handler` base, after successful signature verification, cross-check that the `owner` portion of `params.repository.full_name` (or the resolved `Repository#owner`) equals the `repository_owner` used to select the signing `GitHubApp`, and reject (422) the request if they diverge. This should be enforced once centrally rather than per-handler.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` and/or `test/models/shipit/webhooks/handlers/pull_request/closed_handler_test.rb`):
1. Create `attacker_org` GitHub App config and `victim_repo` fixture (`Repository.create!(owner: 'victim-owner', name: 'victim-repo')`) with an existing `ReviewStack` for `pr7`.
2. Build a `pull_request` "closed" webhook payload with `repository.owner.login = 'attacker-org'`, `repository.full_name = 'victim-owner/victim-repo'`, `number = 7`, and a valid `X-Hub-Signature` computed with `attacker-org`'s webhook secret.
3. POST to `/webhooks` with the appropriate `X-Github-Event: pull_request` header.
4. Assert:
   - `repository_owner` (as computed by the controller) == `'attacker-org'`
   - `Repository.from_github_repo_name(payload['repository']['full_name']).owner` == `'victim-owner'`
   - These two are unequal, yet the request returns `:ok` and the victim's `ReviewStack` for `pr7` is archived (`stack.reload.archived?` is `true`), proving the mutation occurred despite the owner mismatch and without the victim's or Shipit operator's authorization.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
