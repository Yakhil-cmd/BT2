**Analysis**: The exploit hypothesis requires a "stale VM status cache" that permits re-admission of an authentication-failing transaction after mempool eviction and resubmission. This mechanism does not exist in the codebase.

Key facts that refute the premise:

1. `convert_prologue_error` in `errors.rs` maps the `EBAD_ACCOUNT_AUTHENTICATION_KEY` abort code deterministically to `StatusCode::INVALID_AUTH_KEY`, which is not a special-cased "retryable" status anywhere in the mapping logic. [1](#0-0) 

2. Every transaction resubmission through vm-validator triggers a fresh, independent VM prologue execution rather than consulting any cached status. `validate_and_add_transactions` calls `validator.read().validate_transaction(t.0.clone())` on each new submission batch, with no persistent cache keyed by transaction hash that could go "stale." [2](#0-1) 

3. In `core_mempool::mempool::reject_transaction`, only `SEQUENCE_NUMBER_TOO_NEW` is special-cased to keep the transaction in mempool (for later re-check as the account's sequence advances). Every other discard status, including auth failures, results in the transaction being rejected and removed — there is no code path that treats an auth failure as transiently retryable. [3](#0-2) 

4. The authentication key check itself is a deterministic function of the transaction's own signed authenticator and on-chain account state — it does not depend on submission history, so re-submitting the identical unauthenticated transaction will re-derive the identical `INVALID_AUTH_KEY` abort and identical `StatusCode::INVALID_AUTH_KEY` discard status every time, converging correctly between mempool and VM validation.

Since there is no caching mechanism in mempool or vm-validator that would let a stale/downgraded status persist across resubmission, and revalidation is always performed fresh against current on-chain state, the described "silent downgrade enabling re-admission" scenario is not supported by the code. No `expect_no_verification_errors`/`convert_prologue_error` behavior converts a genuine `MoveAbort` auth failure into an "invariant violation" or any status that would be treated more leniently on a later attempt — it consistently maps to `StatusCode::INVALID_AUTH_KEY`, a discard-only status. [4](#0-3)

        self.transactions

    }
