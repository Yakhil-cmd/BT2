The reported bug is a structural weakness specific to the Gnosis Safe + Zodiac Guard architecture: `HatsSignerGateBase` acts as an external Guard hooked via `checkTransaction`/`checkAfterExecution` around a Safe's `execTransaction`, and the vulnerability arises because a nested `delegatecall` inside that single guarded transaction can mutate the Safe's `owners` storage without the Guard's post-flight comparison catching it (it only diffs the `modules` set, not `owners`).

This class of bug — a pre/post invariant snapshot comparison around a transaction that omits comparing a critical piece of externally-mutable state, allowing a nested/delegate call to bypass a condition gate — does not have a structural analog in the FRAME pallets inspected:

- `pallet-proxy`'s `do_proxy` enforces its permission constraints via a real-time `origin.add_filter` closure that is evaluated for *every* nested dispatched call inside a `batch`/`as_derivative`/etc., not via a pre-vs-post state diff. This closure explicitly special-cases `add_proxy`/`remove_proxy`/`remove_proxies`/`kill_pure` to prevent privilege escalation through nested calls in real time, which is precisely the kind of check the Hats bug lacked. [1](#0-0) 
- `pallet-membership`'s `swap_member`/`remove_member`/`add_member` gate every membership mutation behind `T::SwapOrigin`/`T::RemoveOrigin`/`T::AddOrigin` checked synchronously at call time — there is no "condition" (analogous to "still wearing the hat") that is checked once and then can be invalidated by an intervening nested call before a separate post-flight check. [2](#0-1) 
- `pallet-multisig`'s signatory set is not pallet-stored state that could be swapped mid-flight; it's supplied fresh as call parameters (`other_signatories`) on every `as_multi`/`approve_as_multi` invocation, and storage is cleared before dispatch specifically to avoid reentrancy. [3](#0-2) 
- FRAME's `TransactionExtension` `prepare`/`post_dispatch_details` hooks are the closest conceptual parallel to Safe Guard's pre/post-flight checks, but they operate on transaction-extension-scoped state (weights, fees, nonces) computed and validated by the extension itself, not on externally-mutable pallet state that a nested call inside the same dispatch could silently alter to defeat a repeated invariant check. [4](#0-3) 

No FRAME pallet reachable via a signed extrinsic exhibits the same missing-invariant pattern (a permission list checked once, then bypassable via a nested/delegate call before a separate, incomplete post-flight comparison) that defines this Sherlock finding.
