### Title
Asset definer can rotate the `spender_attested` attestor list, freezing already-attested holders' funds - (File: validation.js / storage.js)

### Summary
For assets created with `spender_attested: true`, the definer address can at any time publish a new `asset_attestors` message that replaces the trusted attestor list used to decide whether a holder is allowed to spend the asset. Because the check re-evaluates attestation against only the *latest* attestor list at spend time (not the list in effect when the holder received the funds), a definer changing the attestor list can retroactively strip spend rights from users who legitimately received and held the asset while attested under the old list — precisely the "owner changes a critical pointer/config after users already hold funds" pattern from the `setLpToken` bug.

### Finding Description
When an asset is defined with `spender_attested: true`, a list of attestor addresses is stored per asset in the `asset_attestors` table [1](#0-0) . The asset definer is allowed to submit a follow-up `asset_attestors` message at any time to update this list; validation only enforces "one update per asset per unit" and delegates the actual content checks to `validateAttestorListUpdate`, with no restriction preventing the definer from replacing the list with a completely different set of attestors [2](#0-1) .

When resolving whether a spend is allowed, `readAsset`/`addAttestorsIfNecessary` always looks up only the *single most recent* `asset_attestors` unit for the asset and treats it as the current source of truth: `"...ORDER BY level DESC LIMIT 1"` [3](#0-2) . The set of "attested addresses" for a payment is then computed dynamically by joining current `attestations` rows against this latest attestor list via `filterAttestedAddresses`, not against whichever attestor list was active when the holder received their output [4](#0-3) .

Spend-time validation then hard-fails if the owner address isn't in `arrAttestedAddresses` computed from the current list: [5](#0-4) [6](#0-5) 
and the same check applies to private/indivisible payments [7](#0-6) .

So the sequence is:
1. Definer creates asset X with `spender_attested: true` and attestor list `[A]`.
2. Attestor `A` attests address `U` (a normal user). `U` receives asset X outputs, believing they can freely transact since they are attested.
3. Definer later posts a new `asset_attestors` message changing the trusted attestor list to `[B]` (a different attestor, possibly one that will never attest `U`, or simply an attestor that hasn't attested anyone yet).
4. From this point, `readAsset` picks up `[B]` as the "latest" list. `U`'s previous attestation by `A` is no longer counted for the current list, so `filterAttestedAddresses`/`arrAttestedAddresses` for `U` becomes empty.
5. `U`'s existing outputs of asset X become unspendable — validation rejects any payment where `U` is an input or output owner ("owner address is not attested" / "some output addresses are not attested" / "none of the authors is attested").

This mirrors the LP-token report exactly: a single privileged, unprivileged-reachable actor (the asset definer, who is simply the author of the original `asset` definition unit — not a protocol-privileged role) can post an ordinary follow-up unit that redirects the criterion used to gate withdrawals/transfers, after other users have already relied on the old criterion and hold funds.

### Impact Explanation
This is a fund-freezing bug for any `spender_attested` asset: legitimate holders can lose the ability to move (transfer, or in the case of issuers, issue) their asset holdings whenever the definer rotates the attestor list, even though the holders did nothing wrong and were properly attested at the time they acquired the funds. Because the check is asset-wide (used both for the base transfer-condition path and the private/indivisible payment path), the freeze affects every non-attested (under the new list) address currently holding the asset. This qualifies as AA/asset "fund freezing," matching the scoring rubric's "AA fund loss or freezing" impact bucket — funds are not stolen but become permanently or semi-permanently stuck until/unless the definer reintroduces the old attestor or the affected addresses obtain a new attestation from the currently-trusted attestor(s).

### Likelihood Explanation
Any asset definer using `spender_attested` assets can trigger this unintentionally (e.g., rotating a compromised or retiring attestor service) or intentionally (to grief a subset of holders) — it requires only a single ordinary `asset_attestors` unit, with no cool-down, no migration path, and no way for holders to "grandfather" a prior attestation. The mechanism is core to the `spender_attested` asset type, so any asset relying on it (a legitimate/commonly-recommended feature for KYC-gated assets) is exposed.

### Recommendation
- Evaluate attestation against the attestor list that was in effect at the time the holder's output was created (or at time of issuance), not merely the single latest list, so that already-received funds remain spendable under the terms that applied when they were received.
- Alternatively, require attestor-list changes to only add attestors (never remove), or implement a migration/grace window during which addresses attested under the previous list remain valid for spending down existing balances.
- At minimum, document/flag this behavior clearly so asset issuers understand that changing the attestor list can retroactively freeze existing holders' balances, and consider requiring an explicit governance/timelock or requiring the old attestor list to remain valid for some MCI window after replacement.

### Proof of Concept
1. Definer posts an `asset` definition unit with `spender_attested: true` and `attestors: [A]` (processed via `validateAssetDefinition`/`checkAttestorList`, stored via the `asset` message handling in `writer.js`) [8](#0-7) .
2. Attestor `A` posts an `attestation` message for holder address `U`, then `U` receives an issuance/transfer of asset X and is able to spend it because `filterAttestedAddresses` finds `U` attested against list `[A]`.
3. Definer posts a new `asset_attestors` message for asset X with `attestors: [B]` (accepted by `validateAttestorListUpdate`/`validateInlinePayload`'s `asset_attestors` case, limited only to "one update per asset per unit") [2](#0-1) ; stored via `writer.js`'s `asset_attestors` handling [9](#0-8) .
4. `readAsset` now resolves the "latest list of attestors" to `[B]` [10](#0-9) .
5. `U` attempts to send/spend the previously-received asset X output. `filterAttestedAddresses` returns no rows for `U` (since `U` was only attested by `A`, not `B`), so `arrAttestedAddresses` for `U` is empty, and `validatePaymentInputsAndOutputs` rejects the unit with `"owner address is not attested"` [5](#0-4) , permanently freezing `U`'s asset X balance until `B` attests `U` or the definer reverts the attestor list to include `A`.
