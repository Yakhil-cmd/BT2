### Title
Webhook signature is verified against an organization derived from the payload while handlers act on an independently-parsed repository, allowing cross-organization stack manipulation when the multi-org setup mixes configured and unconfigured `webhook_secret` values - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config to check the `X-Hub-Signature` against based on `repository_owner`, a value read directly out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). [1](#0-0)  The actual object acted upon by every event handler (`PushHandler`, `PullRequest::OpenedHandler`, etc.) is resolved independently from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks`. [2](#0-1)  Nothing binds the organization used for signature verification to the specific repository whose stacks get mutated, other than both fields sitting in the same JSON body.

### Finding Description
Shipit supports installing multiple GitHub Apps, one per organization, configured under `secrets.github` keyed by organization name [3](#0-2) . Each organization config carries its own `webhook_secret` [4](#0-3) , and crucially, `GitHubApp#verify_webhook_signature` explicitly bypasses signature checking when no secret is configured for that organization:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [5](#0-4) 

`verify_signature` picks the `GitHubApp` instance to check against using `Shipit.github(organization: repository_owner)`, where `repository_owner` comes straight from the attacker-controlled request body, not from any authenticated source [6](#0-5) , [7](#0-6) . If any organization in a multi-org deployment lacks a configured `webhook_secret` (the docs explicitly show `webhook_secret:` left blank as a valid config option) [8](#0-7) , an attacker can submit a raw unsigned POST to `/github/webhooks` claiming `repository.owner.login` (or `organization.login`) equal to that unsecured org, while setting `repository.full_name` in the same payload to point at a completely different, unrelated, properly-secured repository/stack tracked by the Shipit instance.

Because the verification step only checks the organization derived from the (attacker-supplied) owner field, and the handler logic that actually performs the mutation (`Repository.from_github_repo_name(repository_name)` → `stacks`) uses the independently-supplied `repository.full_name` field, the equality the code implicitly relies on - "the organization whose secret authenticated this request" == "the organization owning the repository being written to" - does not actually hold. This breaks the binding between "organization that authenticated" and "repository that is written."

### Impact Explanation
This crosses an authentication boundary between the organization used to authenticate (via `X-Hub-Signature` + configured secret) and the repository being mutated. Depending on the enabled handlers, an attacker can, without any credential or a valid signature for the target org, trigger:
- `PushHandler`: forces `stack.sync_github(expected_head_sha:)` for a targeted stack/branch [9](#0-8) , influencing which commit is considered deployable.
- `PullRequest::ClosedHandler`/`OpenedHandler`/`LabeledHandler`: archive, unarchive, or create Review Stacks for arbitrary tracked repositories [10](#0-9) , [11](#0-10) .

This maps to the "unauthorized deploy/rollback" and cross-repository-write class of impact defined in scope, since state mutation for a repository is achieved without ever satisfying that repository's/org's own webhook authentication.

### Likelihood Explanation
Exploitability is conditioned on the deployment running Shipit's multi-organization GitHub App mode (`secrets.github` keyed by org) with at least one organization left without a `webhook_secret` - a configuration explicitly supported and documented by the engine [12](#0-11) . Where that condition holds, no privileged credential is needed: the request is a plain, unauthenticated POST with a forged JSON body; `verify_signature`'s early-return-on-blank-secret path makes the bypass deterministic. This is a realistic, if configuration-dependent, misconfiguration-enabled bypass rather than a purely theoretical one, given the documented multi-org setup explicitly allows per-org blank secrets.

### Recommendation
Do not let the signature-verification organization and the acted-upon repository diverge:
- Cross-check that `repository_owner` (used to select the verifying org) matches the owner segment of `repository.full_name` used by the handler layer, rejecting mismatches.
- Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), or at minimum refuse to process events for organizations with no configured secret.
- Consider deriving the verifying organization strictly from the same `repository.full_name`/`organization.login` field that handlers use for repository resolution, rather than allowing a fallback chain that an attacker fully controls.

### Proof of Concept
Preconditions: Shipit deployed in multi-org mode with `secrets.github` containing e.g. `OrgUnsecured` (no `webhook_secret`) and `OrgTarget` (properly secured, owns a tracked repository/stack such as `OrgTarget/important-repo`).

1. Attacker sends, without any valid `X-Hub-Signature`:
```
POST /github/webhooks
X-Github-Event: push

{
  "repository": { "owner": { "login": "OrgUnsecured" }, "full_name": "OrgTarget/important-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
2. `verify_signature` computes `repository_owner == "OrgUnsecured"`, loads that org's `GitHubApp`, and `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank for `OrgUnsecured` [13](#0-12) .
3. Verification passes, `create` dispatches to `Webhooks.for_event('push')` → `PushHandler.call(params)` [14](#0-13) .
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgTarget/important-repo")` (from `repository.full_name`, never checked against `OrgUnsecured`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for the `master` branch of `OrgTarget`'s repository [9](#0-8) , [2](#0-1) .

This demonstrates mutation of `OrgTarget`'s stack state despite the attacker never having presented a signature valid for `OrgTarget`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",

      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
