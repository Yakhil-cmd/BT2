### Title
Byte-offset diff truncation in `cap_diff_for_prompt`/`build_investigate_prompt` silently drops attacker-positioned high-risk lines from security review - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_investigate_prompt` feeds the diff through `cap_diff_for_prompt`, which truncates each file's content at a fixed byte offset (`DIFF_PER_FILE_BYTES`, default 80,000) and the aggregate at `DIFF_TOTAL_BYTES` (default 400,000), keeping only the head and discarding the tail. Because the cut point is a pure byte offset with no awareness of diff semantics (`+`/`-`/context) or security-risk content, an attacker who controls where in a file's diff the dangerous change lands can push it past the cap and have it replaced by an inert truncation marker before the review model ever sees it.

### Finding Description
`cap_diff_for_prompt` (`plugins/security-guidance/hooks/review_api.py:31-64`) truncates per file with `content[:DIFF_PER_FILE_BYTES] + "\n... [truncated ...]"` and then per total budget the same way — always keeping the prefix and cutting the suffix, regardless of which lines are `+` (newly introduced, the only content the reviewer is instructed to flag per `AGENTIC_INVESTIGATE_SYSTEM`/diff instructions) versus unchanged context. `build_investigate_prompt` (`review_api.py:156-176`) calls this capping function directly and hands the resulting `diff_text` to the stage-1 investigate prompt with no other safeguard. The identical logic is duplicated in `plugins/security-guidance/hooks/llm.py` (`_cap_files_for_prompt`, lines 158-183) used by `agentic_review`'s stage-1 prompt build.

The only content-aware selection in the pipeline is `_prioritize_diff_files` (`plugins/security-guidance/hooks/gitutil.py:512-547`), which operates at file granularity (ranks whole files by path risk tokens and total added-line count) and only engages when the number of *files* exceeds `MAX_DIFF_FILES`. It does nothing to protect specific lines *within* a single file's diff from the per-file byte cap, and does not reorder or prioritize content inside a file's diff hunk.

Because the diff a session generates (via `get_git_diff`/`parse_diff_into_files`) reflects whatever content ends up in the working tree — including content written by Claude Code as a result of instructions embedded in ordinary repository content (README text, code comments, issue/PR text, or other prompt-injection vectors) — an attacker who can influence what gets written to a single file (e.g., causing a large amount of benign-looking scaffolding, generated boilerplate, or padding text to be added before a malicious change) can arrange for the dangerous `+` lines to fall past the 80,000-byte per-file offset. The capping function then silently drops them, replacing the tail with a generic truncation marker, and the stage-1 investigate model (and the stage-2 self-refute pass, which only re-examines what stage 1 already surfaced) never observes the dangerous lines at all.

This breaks the stated invariant — truncation is purely positional, not risk-aware, so it does not guarantee that high-risk/newly-added lines survive. No existing check (allowlist, approval prompt, workspace guard) mitigates this: the caps exist purely to bound LLM payload size, and there is no fallback (e.g., "if truncation occurred, escalate for human review" or "prioritize `+` lines within a file over context lines") in `cap_diff_for_prompt`/`build_investigate_prompt` or its `llm.py` twin.

### Impact Explanation
This is a security-control bypass on the security-guidance plugin's own commit/Stop-hook code review: an attacker able to influence written diff content can craft a single large file change such that the actually dangerous code is truncated out of what's sent to `build_investigate_prompt`/`agentic_review`. The reviewer then either reports no findings or misses the injected vulnerability, effectively silently disabling the review boundary the plugin exists to enforce — matching the "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries" impact category.

### Likelihood Explanation
The attack requires only the ability to get a large amount of content (padding) written before the dangerous change within one file's diff, and to keep the file under the 300-file pathological-diff bail and under the file count that triggers `_prioritize_diff_files` reordering (or to be the highest-priority file, since prioritization doesn't protect within-file position). An 80KB padding requirement per file is easily reachable with generated code, minified-looking blocks, or verbose comments that don't themselves trip the SKIP_FILE_SUFFIXES/SKIP_PATH_PATTERNS filters (e.g., `.py`/`.js` files, not `.min.js`/`.lock`). This is deterministic and repeatable — the byte-offset truncation always cuts the same way regardless of diff content, so the bypass is not probabilistic once the attacker knows the byte caps (which are also read from environment variables and documented in the code/comments, making them easy to target).

### Recommendation
Make truncation diff-aware and risk-aware instead of purely positional:
- Prioritize retaining all `+` (added) lines up to the byte budget before falling back to including context lines, rather than truncating strictly by original byte offset.
- If truncation would drop any `+` line, either raise the cap for that file, split it into multiple review calls, or explicitly flag in the review output/metrics that added lines were dropped so a human/downstream control can react instead of silently proceeding as if nothing was omitted.
- Consider scanning the to-be-dropped tail for `+`-line security-risk tokens (reusing `_SECURITY_RISK_PATH_TOKENS`-style heuricstics or simple sink keywords) and preferentially keep those chunks.

### Proof of Concept
Unit test in `plugins/security-guidance/hooks/review_api.py` test suite:
1. Construct a diff file `("app.py", content)` where `content` is `"+" + ("x"*79990) + "\n"` (padding, ~80KB) followed by `"+os.system(user_input)\n"` (the dangerous `+` line), so the dangerous line's byte offset exceeds `DIFF_PER_FILE_BYTES` (80000).
2. Call `cap_diff_for_prompt([("app.py", content)])` and assert that `"os.system(user_input)"` is **absent** from the returned capped content (demonstrating the drop) while the truncation marker `"[truncated by security-guidance: file exceeds per-file byte cap]"` is present.
3. Call `build_investigate_prompt(["app.py"], [("app.py", content)])` and assert the dangerous line/token is not present anywhere in the returned prompt string — confirming the stage-1 investigate model never receives it.
4. Repeat with a multi-file scenario where the total diff exceeds `DIFF_TOTAL_BYTES` and the dangerous file is ordered last, to confirm the same drop occurs at the total-budget cap (`"[omitted by security-guidance: total diff byte cap reached]"`).
Expected assertion for a fixed implementation: the dangerous `+` line's token must remain present in the capped/prompt output regardless of its byte offset within the file (until a reasonable overall size ceiling is truly exhausted of all `+` content), i.e., truncation should exhaust context/unchanged lines before ever dropping `+` lines.
