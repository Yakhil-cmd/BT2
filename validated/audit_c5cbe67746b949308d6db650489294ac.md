### Title
`GIT_ASKPASS` engine snippet path can be overridden by attacker-controlled `machine.environment` in `shipit.yml` - ([File: lib/shipit/task_commands.rb])

### Summary
`Commands#base_env` sets `GIT_ASKPASS` to the engine's own snippet path, but `TaskCommands#env` merges `deploy_spec.machine_env` (parsed directly from `shipit.yml` on the task/stack's checked-out branch) and `@task.env` *after* the base env, and `Hash#merge` lets the later hash's keys win. This allows a PR/branch-controlled `shipit.yml` to overwrite `GIT_ASKPASS` with an attacker path, and that overridden value flows unmodified into `Command#start`/`PTY.spawn` where `GITHUB_TOKEN` is also present in the environment.

### Finding Description
The claimed binding is: `base_env['GIT_ASKPASS'] == Shipit::Engine.root.join('lib','snippets','git-askpass').realpath.to_s` for every `Command` built via `Commands#git`.

`Commands#base_env` computes this value once and memoizes it: [1](#0-0) 

But the env that actually reaches a task's shell commands is not `base_env` directly — it is `TaskCommands#env`, which merges several additional sources **after** calling `super` (i.e., after `base_env`/`StackCommands#env` is folded in): [2](#0-1) 

Two of those later merges are attacker-influenceable:
- `deploy_spec.machine_env`, which reads directly from the `machine.environment` key of the parsed `shipit.yml` config with no filtering (unlike `deploy_variables`, which are passed through `EnvironmentVariables#permit` via `filter_deploy_envs`): [3](#0-2) 
- `@task.env`, a free-form hash on the task record.

Since Ruby's `Hash#merge` gives precedence to the argument's keys over the receiver's, a `shipit.yml` on the tracked/PR branch containing:
```yaml
machine:
  environment:
    GIT_ASKPASS: /tmp/attacker.sh
```
will overwrite the `GIT_ASKPASS` value set in `base_env` before the merged hash is ever handed to `Command.new`. `Command#initialize` stores this hash verbatim as `@env`, and `Command#start` builds the final spawn environment as `unbundled_env` where `@env` is merged last and thus wins: [4](#0-3) 

The `git_config`/`filter_deploy_envs` sanitization only guards `deploy_variables`/`rollback_variables`, not `machine.environment`; there is no key-name blocklist (e.g., for `GIT_ASKPASS`, `PATH`, `GITHUB_TOKEN`) applied to `machine_env` or `@task.env` anywhere in `DeploySpec` or `TaskCommands`. `filter_deploy_envs`/`EnvironmentVariables#permit` are not invoked on the path that builds `TaskCommands#env`, so this specific divergence is not caught by existing guards.

### Impact Explanation
If `Shipit.use_git_askpass?` is enabled (the documented production configuration) and any git operation performed with `TaskCommands#env`/`DeployCommands#env` runs while `GITHUB_TOKEN` is exported in the same process environment, the attacker's `GIT_ASKPASS` script is invoked by git to answer the username/password prompt and receives the full environment, including `GITHUB_TOKEN`. This is Critical: exfiltration of `GITHUB_TOKEN` and arbitrary code execution on the deploy host under the Shipit worker's privileges, repeatable for every deploy/task run against that stack once the malicious `shipit.yml` is merged/checked out.

### Likelihood Explanation
Exploitation requires: (1) the target Shipit installation runs with `Shipit.use_git_askpass? == true` (documented production default), and (2) the stack's checked-out branch/commit (e.g., a review stack tracking the attacker's PR branch, or any stack whose `shipit.yml` is sourced from a branch the attacker can push commits to) is used to build the `DeploySpec` consumed by `TaskCommands#env`. Given review stacks are an explicitly supported, PR-driven feature of this engine, an attacker who can open a PR/push a branch can satisfy this precondition with a normal, unprivileged PR — no session, API token, or secret is required.

### Recommendation
In `TaskCommands#env` (and any other place merging `deploy_spec.machine_env`/`@task.env`), re-apply the engine-controlled security-sensitive keys (`GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `PATH`, etc.) after the user/branch-controlled merges, or explicitly strip/blocklist these keys from `machine_env`/`@task.env` before merging (mirroring the `EnvironmentVariables#permit` approach already used for `deploy_variables`).

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (concept)
test "GIT_ASKPASS from shipit.yml machine.environment cannot override the engine snippet" do
  Shipit.stubs(:use_git_askpass?).returns(true)
  @deploy_spec.stubs(:machine_env).returns('GIT_ASKPASS' => '/tmp/attacker.sh')

  command = @commands.install_dependencies.first

  expected = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s
  assert_equal expected, command.env['GIT_ASKPASS']
  refute_equal '/tmp/attacker.sh', command.env['GIT_ASKPASS']
end
```
Run against current code: the assertion fails because `command.env['GIT_ASKPASS']` equals `/tmp/attacker.sh`, proving the binding is broken.
