### Title
Webhook signature verification is bound to a spoofable `organization`/`repository.owner.login` field while the actual mutated record is selected from an unverified `repository.full_name` field, allowing forged webhooks against any org with no (or an unknown) `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, itself derived from the payload fields `repository.owner.login` or `organization.login`. [1](#0-0) [2](#0-1)  The action that actually mutates state — `Handler#stacks`/`Handler#repository_name` — instead resolves the target `Repository`/`Stack` from a completely different payload field, `repository.full_name`, with no check that it is consistent with the organization used for signature verification. [3](#0-2)  Compounding this, `GitHubApp#verify_webhook_signature` unconditionally returns `true` (i.e. skips verification entirely) whenever that organization's `webhook_secret` is blank. [4](#0-3) 

### Finding Description
This is the same class of bug as the cited report: a value that gates/authorizes an action (`funding.discount` gating `getAmountOut()`) is disconnected from the value the action actually uses. Here, `Shipit.github(organization: repository_owner)` picks the secret used to authenticate the request based on `repository.owner.login`/`organization.login` in the JSON body, [1](#0-0)  but every event handler determines *which* repository/stack to act on using `payload.dig('repository', 'full_name')`, [5](#0-4)  a field that is never checked against the organization used for verification.

Shipit explicitly supports multi-organization configuration, each with its own, individually optional, `webhook_secret`: [6](#0-5)  the setup docs describe the webhook secret as optional. [7](#0-6)  `GitHubApp#verify_webhook_signature` treats an absent secret as "always verified":

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

Given any configured organization `orgA` that has no `webhook_secret` set, an unauthenticated attacker can POST to `/webhooks` with `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) to satisfy `verify_signature` unconditionally, while setting `repository.full_name` to any other organization/repository known to Shipit (e.g. `"orgB/critical-repo"`). The `organization` field bound by verification never equals the `repository` field the handler actually writes to — exactly the "organization authenticated vs. repository written" binding break called out in the rules.

The most severe consequence is via the `membership` event handler, whose behavior is exercised in `test/controllers/webhooks_controller_test.rb` (`":membership creates the mentioned team on the fly"`, `":membership creates the mentioned user on the fly"`, `":membership can append an user membership"`). [8](#0-7)  These handlers create `Team`/`User`/`Membership` records directly from webhook payload content. Because Shipit's authorization gate (`current_user.authorized?`, checked against `Shipit.github_teams`) is driven by these same `Membership`/`Team` records, [9](#0-8)  a forged `membership` webhook (passing verification because the target org has no secret configured) lets an attacker insert an arbitrary GitHub login into a team that `Shipit.github_teams` trusts, directly escalating that attacker-controlled login into deploy authorization — without ever needing a real GitHub OAuth login, App private key, `webhook_secret`, or existing session.

### Impact Explanation
This crosses the "High" bar explicitly listed in scope: escalation into `Shipit.github_teams` authorization via a forged webhook that bypasses signature verification because the organization used to pick the (missing) secret is decoupled from the repository/team data actually written. In deployments where every configured org does have a `webhook_secret` set, the same field confusion still lets a holder of one org's secret write/spoof events (push, status, check_suite) against any other configured organization's repositories/stacks, since `repository.full_name` is never cross-validated against the verified `repository_owner`.

### Likelihood Explanation
Likelihood is highest in the documented multi-organization configuration where `webhook_secret` is explicitly optional per the setup docs and example config; any org left without a secret (a supported, non-malicious operator choice) turns `/webhooks` into an unauthenticated write endpoint for that org's identity while still letting the attacker target other configured organizations' data via the unchecked `repository.full_name` field. No privileged credential, session, or token is required to reach this endpoint.

### Recommendation
Bind signature verification and the record-mutation target to the same field: after establishing which organization's key verified the signature, require that `repository.full_name`'s owner prefix (and/or `repository.owner.login`) exactly match the verified organization before dispatching to any `Shipit::Webhooks::Handlers::Handler`. Additionally, do not treat an absent `webhook_secret` as automatic verification success (`GitHubApp#verify_webhook_signature`) — instead reject/log webhooks for organizations with no configured secret, or require an explicit "no verification" opt-in per organization rather than allowing it as an implicit default.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, `orgA` (no `webhook_secret` set) and `orgB` (has a real repository/stack under Shipit management).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "orgA" },
  "team": { "id": 1, "name": "orgA-team", "slug": "orga-team", "url": "https://example.com" },
  "member": { "login": "attacker-login" }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and `verify_webhook_signature` returns `true` unconditionally because `orgA` has no `webhook_secret`. [4](#0-3) 
4. The `membership` handler creates/updates `Membership` for `attacker-login` under `orgA-team`, as demonstrated by the existing test coverage for this handler. [10](#0-9) 
5. If `orgA-team`'s slug/handle matches an entry configured in `Shipit.github_teams` (an operator-controlled but attacker-guessable/known value), `attacker-login`'s subsequent GitHub OAuth login is now `authorized?` per `app/controllers/concerns/shipit/authentication.rb`, without ever holding a real team membership on GitHub.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
