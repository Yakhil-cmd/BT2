### Title
Webhook signature verification is keyed on `repository.owner.login`, but every event handler dispatches on the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository_owner`, taken from the *same untrusted, unverified* JSON body it is about to validate. Once the HMAC passes, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` looks up the target `Repository`/`Stack` using a *different* field from that same body: `repository.full_name`. The signature only proves "this body was HMAC-signed by whoever holds `repository.owner.login`'s webhook secret" - it never proves that `repository.full_name` actually belongs to that owner.

### Finding Description
`verify_signature` computes the verification target before checking the signature: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) - fields fully controlled by the request body, not covered by any prior authentication. `Shipit.github(organization: repository_owner)` picks the `GithubApp` instance (and thus the `webhook_secret`) for that organization, and `verify_webhook_signature` HMACs the raw body against that org's secret: [3](#0-2) 

If verification succeeds, `create` dispatches the full, untouched `params` hash to every registered handler for the event: [4](#0-3) 

All handlers, however, resolve the target `Repository`/`Stack` from `repository.full_name`, not from `repository.owner.login`: [5](#0-4) 

The same pattern repeats in every pull-request handler (`opened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`, etc.), each of which independently does `Shipit::Repository.from_github_repo_name(params.repository.full_name)`.

Because each organization configured in `secrets.yml` gets its own, independently-known `webhook_secret` (an org admin necessarily knows their own org's secret, e.g. by registering their own GitHub App/webhook against their own repo), an attacker who controls org **A** (with a legitimate, correctly configured webhook secret for org A) can://
1. Sign an arbitrary JSON payload with org A's `webhook_secret`.
2. Set `repository.owner.login` (or `organization.login`) to `"orgA"` so `verify_signature` selects and validates against org A's secret.
3. Set `repository.full_name` to `"orgB/victim-repo"` - a repository belonging to a *different*, victim organization that also has a Stack configured in this Shipit instance.

`verify_signature` passes (the HMAC matches org A's secret and body), but the handler acts on `orgB/victim-repo`. This breaks the intended binding "organization that authenticated" == "repository that is written."

`PushHandler` is the highest-impact target reachable this way: [6](#0-5) 

It looks up stacks scoped to `repository.full_name` (via `Handler#stacks`) and calls `stack.sync_github(expected_head_sha: params.after)` for any matching branch - meaning an attacker who owns an unrelated GitHub org can trigger a `GithubSyncJob`/`CacheDeploySpecJob` sync cycle against a victim repository's stack, forging the `expected_head_sha` used to drive commit-fetch/eventual-consistency retry logic, and (via `PullRequest` handlers) can also forge `assigned`/`labeled`/`unlabeled`/`opened` pull-request state transitions (including Review Stack archive/unarchive and provisioning) against a victim org's repository, using only the attacker's own org's webhook secret.

### Impact Explanation
This crosses a repository-write / cross-organization boundary: an attacker who is authorized only for their own GitHub organization's webhook traffic can cause the engine to write state (sync commits, mutate `PullRequest`, archive/unarchive Review Stacks, trigger provisioning) attributed to a completely different, victim repository/stack that they have no legitimate relationship to. This matches the "High" bucket (unauthenticated influence over stack/task state via a spoofed identity boundary) and, depending on what a maliciously forged `push`/`pull_request` sync triggers (e.g. Continuous Deployment enabled on the victim stack, forged head SHA causing a deploy of an attacker-influenced commit set once the eventual-consistency GithubSyncJob resolves against the real GitHub API), could escalate toward unauthorized deploys.

### Likelihood Explanation
Likelihood is high for any Shipit instance configured with more than one GitHub organization in `secrets.yml`/`config/secrets.*.yml` (the documented multi-org configuration shown in `config/secrets.development.shopify.yml`). Any user who can register/own a GitHub App or webhook for *any* org configured in the instance (even a throwaway, low-trust org) obtains a valid `webhook_secret` and can craft an arbitrary payload naming a victim org's repository in `repository.full_name`. No repository write access, API token, or session is required - only knowledge of one's own org's webhook secret, which by design an org owner possesses.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, cross-check that the field used to select the verification secret (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` before dispatching to handlers, or better, verify against a secret bound at the `Repository`/`Stack` level (as already modeled by `Shipit::GithubHook`) rather than trusting an org name read out of the same unverified payload used for routing. Reject the webhook if the two identities diverge.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (attacker-controlled, e.g. a personal test org where the attacker configures their own GitHub App/webhook and thus knows `webhook_secret_A`) and `orgB` (victim org with an existing Stack for `orgB/victim-repo`).
2. Attacker computes `sig = HMAC-SHA1(webhook_secret_A, body)` where:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<sig>`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")`, verifies the HMAC successfully against `webhook_secret_A`.
5. `PushHandler#process` runs `Repository.from_github_repo_name("orgB/victim-repo").stacks...sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing `GithubSyncJob` to run against the victim's `orgB/victim-repo` stack - despite the request never being authenticated by anything belonging to `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
