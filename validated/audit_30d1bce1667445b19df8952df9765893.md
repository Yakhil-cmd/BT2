## Finding

### Title
CCMenu API endpoint ignores the stack scope bound to an ApiClient token, allowing a stack-restricted token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a `stack_id`) may only ever resolve `stack`/`stacks` to the single stack it was granted access to. `Api::CCMenuController` overrides both the authentication and the stack-resolution methods, and in doing so drops that scoping check entirely, letting any valid token read CI/build status for any stack in the installation, not just the one it authorizes.

### Finding Description
The base controller binds "the stack a token authorizes" to "the stack that gets touched" through `stacks`/`stack`: [1](#0-0) 

`current_api_client.stack_id?` narrows `Stack.where(id: ...)` to exactly the authorized stack when the token is scoped, and `stack` is derived from that scoped relation via `stacks.from_param!`.

`Api::CCMenuController`, however, defines its own `stack` method that resolves directly from `Stack.from_param!(params[:stack_id])`, bypassing `stacks` (and therefore the `current_api_client.stack_id` restriction) entirely, and its own `authenticate_api_client` that authenticates via `params[:token]` instead of HTTP Basic auth: [2](#0-1) 

The only authorization check performed is `require_permission :read, :stack`, i.e. `current_api_client.check_permissions!(:read, :stack)`, which only checks that the *permission bit* `read:stack` is present on the token — it never checks that the requested `stack_id` in the URL equals `current_api_client.stack_id`. This is the same class of defect as the audited `createStream`/Sablier bug: a value that should be bound to (and validated against) the authenticated principal's authorized scope (`current_api_client.stack_id`) is instead taken unchecked from attacker-controlled input (`params[:stack_id]`) and used to determine which resource is acted on.

Equality that should hold but is broken: `stack_id authorized by current_api_client` == `stack_id whose data is served`. Before the request, an ApiClient token exists with `stack_id = A` and permission `read:stack`. After the request, the CCMenu response actually reflects `stack_id = B` (any other stack in the installation), because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
Any holder of a valid `read:stack`-permissioned ApiClient token — even one deliberately created and scoped to a single, low-sensitivity stack — can query `/api/stacks/:owner/:repo/:env/ccmenu?token=...` for an arbitrary other stack and obtain that stack's build/deploy status, last build label, and web URL (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`). This is an unauthenticated-for-that-resource read of stack state that the token was never granted, matching the "unauthenticated read of stack state ... deploy output" High-impact category, since the scoping restriction (the very mechanism meant to keep multi-tenant API clients siloed to their own stack) is fully bypassed for this endpoint.

### Likelihood Explanation
This requires only possession of any valid ApiClient token with `read:stack` permission (which is routinely handed out to CI dashboards/build monitors, exactly the CCMenu use case) and knowledge/guessing of another stack's `owner/repo/environment` path, which is often predictable or discoverable via the stacks index. No privileged access, session, or additional secret is needed beyond a token that legitimately exists for an unrelated, narrowly-scoped purpose.

### Recommendation
Make `Api::CCMenuController#stack` go through the same scoped relation as the rest of the API (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so a stack-restricted `current_api_client.stack_id` is enforced identically to every other API controller. If query-string token auth must remain, still route stack resolution through `current_api_client`-scoped `stacks`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: A` with permission `read:stack` and generate its token (`api_client_token`).
2. As an unprivileged holder of that token, issue: `GET /api/stacks/<owner-B>/<repo-B>/<env-B>/ccmenu?token=<token>` where `owner-B/repo-B/env-B` is a *different* stack `B` than the one the token was scoped to.
3. Observe the response returns `B`'s CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), even though the token's `stack_id` only authorizes stack `A`. Compare with `Api::StacksController`/`Api::TasksController`, where the same token used against stack `B` correctly triggers `stacks.from_param!` returning `RecordNotFound` because `stacks` is filtered to `Stack.where(id: A)`.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
