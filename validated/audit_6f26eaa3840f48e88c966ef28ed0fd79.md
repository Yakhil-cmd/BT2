### Title
Unbounded synchronous recursion in address-definition authentifier evaluation causes call-stack-overflow crash of full nodes - (File: definition.js)

### Summary
`Definition.validateAuthentifiers()` in `definition.js` evaluates an address (or asset) spending-condition definition twice for every unit that is validated: first through `validateDefinition()`'s `evaluate()` (which enforces `MAX_COMPLEXITY`/`MAX_OPS` limits) and then through a second, separate `evaluate()` closure inside `validateAuthentifiers()` itself that performs the actual signature/authentifier check [1](#0-0) . Unlike the formula evaluators in `formula/validation.js` and `formula/evaluation.js`, which explicitly break up the JS call stack every 100 recursive calls with `setImmediate` to avoid "Maximum call stack size exceeded" [2](#0-1) [3](#0-2) , the `evaluate()` function used inside `validateAuthentifiers()` (and its counterpart in `validateDefinition()`) recurses purely through synchronous JS calls for boolean-composition ops such as `'or'`, `'and'`, and `'r of set'` [4](#0-3) , with no depth counter and no stack-yielding mechanism.

### Finding Description
Any ordinary unit poster can define (or change) the spending condition of their own address using deeply nested boolean composition ops (`and`/`or`/`r of set`/`weighted and`) up to the `MAX_COMPLEXITY` / `MAX_OPS` limit enforced in `validateDefinition()` [5](#0-4) . Because each `and`/`or` element is itself a nested 2-element array (`['and', [['and', [...]], ...]]`), an attacker can build a definition that satisfies the complexity/ops caps while maximizing nesting depth (e.g., a long chain of single-element `and`/`or` wrappers), each contributing 1 to `complexity`/`count_ops` but adding one full stack frame of recursion.

When the unit is later validated by any node — both the definition check (`validateDefinition`) and, more importantly, the actual authentifier evaluation (`validateAuthentifiers`'s `evaluate()`) — walk this AST recursively via direct function calls inside `async.eachSeries` iteratees, which for in-memory data execute synchronously rather than yielding the event loop [6](#0-5) . There is no per-call `setImmediate`/`process.nextTick` break as exists in the formula evaluators, so sufficiently deep nesting can throw an uncaught `RangeError: Maximum call stack size exceeded`.

This exception is not caught by any `try/catch` in the recursive `evaluate()` chain (only `definition template` and a couple of specific ops have local try/catch, and those don't wrap the recursive calls in `and`/`or`/`r of set`). It escapes to the top of the event loop and is handled only by the global `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws to crash the process: `throw err; // crash the process to avoid ending up in an inconsistent state` [7](#0-6) .

This is directly analogous to CVE-2021-2028: a moderately-privileged actor (here, merely an unprivileged unit author, not even requiring high privilege) sends crafted input through a normal protocol path (a unit/AA trigger) that the engine (InnoDB / ocore validator) processes, resulting in a crash/hang (complete denial of service) rather than data corruption or confidentiality loss.

### Impact Explanation
Every full node (and light-wallet-serving hub) that validates the malicious unit — via `validation.js`'s `validateAuthors` → `Definition.validateAuthentifiers` path, or via `wallet_defined_by_addresses.js`'s `validateAddressDefinition`, or via AA composer's message/definition validation — will crash with an uncaught `RangeError`, halting the entire node process network-wide. Because the crash is deterministic given the same crafted unit, an attacker can broadcast one poisoned unit to take down every node that processes it, i.e. "a network unable to confirm new units," matching the accepted-impact criteria.

### Likelihood Explanation
Easily exploitable: constructing a deeply nested `and`/`or` definition requires no special access, only a normal signed unit changing/setting an address definition (or an asset's `issue_condition`/`transfer_condition`) within the complexity/ops limits already permitted by the protocol. No privileged network position, hub cooperation, or timing race is needed — a single crafted unit reaching normal validation is enough.

### Recommendation
Add the same stack-guard used elsewhere in the codebase (e.g., a recursion counter with periodic `setImmediate`/`process.nextTick` yield, as done in `formula/validation.js` line 274-275 and `formula/evaluation.js` line 128-129) to the recursive `evaluate()` functions in both `validateDefinition()` and `validateAuthentifiers()` in `definition.js`. Alternatively/additionally, impose an explicit maximum AST nesting depth (mirroring `aa_validation.js`'s `MAX_DEPTH = 100` check) independent of the complexity/ops counters, since complexity/ops alone do not bound recursion depth when nesting is achieved via single-element `and`/`or` wrappers.

### Proof of Concept
Conceptually:
1. Construct an address definition of the form `['and', [['and', [['and', [ ... ['sig', {pubkey: ...}] ... ]]]]]]` nested N levels deep (N chosen just under the point where `MAX_COMPLEXITY`/`MAX_OPS` limits in `definition.js` would reject it, but deep enough to exceed V8's default call stack, e.g. several thousand levels using single-element `and` wrappers, each adding only 1 to complexity/count_ops).
2. Post a unit that sets this as the new definition for the attacker's own address (via `address_definition_change` message or as an author definition), or an asset with such an `issue_condition`.
3. When any full node processes and validates this unit (via `validation.js` → `validateAuthors` → `Definition.validateAuthentifiers`), the recursive `evaluate()` calls in `definition.js` recurse synchronously without yielding, exceeding V8's maximum call stack and throwing an uncaught `RangeError`.
4. The uncaught exception propagates to `process.on('uncaughtException', ...)` in `network.js`, which rethrows and crashes the node process.

Note: I was not able to retrieve the exact numeric values of `constants.MAX_COMPLEXITY` and `constants.MAX_OPS` from the index within the available iterations, so I cannot state with certainty whether the currently configured limits are numerically sufficient to reach V8's default stack limit in a single synchronous recursion chain; this would need to be confirmed by a Devin session with full file access to `constants.js` and by running an actual PoC against a test node.
