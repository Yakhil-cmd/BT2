### Title
`StackStxOp::check` fails to reject `num_cycles > POX_MAX_NUM_CYCLES`, only logs a warning - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`StackStxOp::check` contains an out-of-range validation branch for `num_cycles` that only calls `warn!()` and does not return `Err`, so a burnchain `StackStxOp` with `num_cycles` up to `u8::MAX` (255) passes validation and is forwarded to the `.pox-*` contract's `stack-stx` entry point.

### Finding Description
The equality that must hold is: **the number of reward cycles the staker's STX is locked for must equal a value `n` such that `0 < n <= POX_MAX_NUM_CYCLES`**, so that `unlock height = current cycle start + n * cycle length` is well-defined and reachable.

In `StackStxOp::parse_data` [1](#0-0)  `num_cycles` is read as a raw `u8` with no cap. In `StackStxOp::check`:

```rust
if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
    warn!(
        "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
        self.num_cycles, POX_MAX_NUM_CYCLES
    );
}
``` [2](#0-1) 

this branch logs a warning but falls through to `Ok(())` at the end of the function [3](#0-2) , unlike the `stacked_ustx == 0` check just above it which correctly returns `Err(op_error::StackStxMustBePositive)` [4](#0-3) . This is a clear inconsistency: the sibling check is fail-closed, this one is fail-open.

### Impact Explanation
If the pox-5 contract's `stack-stx` function does not independently re-validate `num-cycles <= 12` (`POX_MAX_NUM_CYCLES`) before computing the unlock burn height, an attacker (or even an honest miner submitting a malformed op) can drive `num_cycles = 255` through `StackStxOp::check` into the Clarity call. This is a Critical-class concern per the taxonomy (permanent freezing of staked STX) **if and only if** the downstream Clarity `stack-stx` function lacks its own bound check on `num-cycles`.

However, I was unable to verify within the available index whether `pox-5.clar`'s `stack-stx` function performs its own `<=` bound check on `num-cycles` — my searches for `num-cycles` inside `stackslib/src/chainstate/stacks/boot/pox-5.clar` returned no matches, which is inconsistent with the file containing 78 matches for `"num-cycles"` reported in an earlier grep against `.clar` files generally. This suggests the file is large enough that the indexer's coverage was incomplete for this specific query, and I could not confirm the exact validation logic (e.g., `check-pox-lock-period`) inside `pox-5.clar`'s `stack-stx`/`inner-stack-stx` handler.

### Likelihood Explanation
Preconditions: attacker needs a Bitcoin UTXO chain that produces a valid `PreStxOp`+`StackStxOp` pair with real `stacked_ustx` at their own address — no privileged role required. Constructing `num_cycles = 255` in the wire payload is trivial (single byte, no cap in `parse_data`). Feasibility of actual fund freezing depends entirely on whether the Clarity-side `stack-stx` implementation independently caps `num-cycles`, which is the standard defense-in-depth pattern in PoX contracts (all versions historically assert `(<= num-cycles MAX-POX-REWARD-CYCLES)` or similar).

### Recommendation
Fix `StackStxOp::check` to return an error instead of only warning:
```rust
if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
    warn!(
        "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
        self.num_cycles, POX_MAX_NUM_CYCLES
    );
    return Err(op_error::StackStxInvalidCycles); // or equivalent variant
}
```
This restores fail-closed behavior consistent with the `stacked_ustx == 0` branch immediately above it, and removes reliance on the Clarity contract as the sole enforcement point.

### Proof of Concept
Rust unit test in `stackslib/src/chainstate/burn/operations/stack_stx.rs`'s `tests` module:
```rust
#[test]
fn test_check_rejects_excessive_num_cycles() {
    let sender = StacksAddress::new(0, Hash160([0; 20])).unwrap();
    let reward_addr = PoxAddress::Standard(
        StacksAddress::new(C32_ADDRESS_VERSION_MAINNET_SINGLESIG, Hash160([1; 20])).unwrap(),
        None,
    );
    let op = StackStxOp::new(
        &sender,
        &reward_addr,
        1_000_000,
        255, // > POX_MAX_NUM_CYCLES
        None,
        None,
        None,
    );
    let result = op.check();
    assert!(result.is_err(), "check() must reject num_cycles > POX_MAX_NUM_CYCLES, got {:?}", result);
}
```
Currently this assertion fails because `check()` returns `Ok(())`. This confirms the equality break at the Rust validation layer independent of the Clarity contract behavior; a full end-to-end test would additionally need to drive this op through a booted chainstate and inspect `pox-5.clar`'s `stack-stx` call outcome, which I could not verify in this pass — I recommend a Devin session with full repo access to confirm whether `pox-5.clar` independently guards against `num-cycles > 12` before concluding definitively on exploitability at the funds-freezing level.
