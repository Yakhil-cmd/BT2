### Title
Stack-scoped API token bypasses its `stack_id` binding in the CCMenu API endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` accessor to look up `Stack.from_param!(params[:stack_id])` directly on the entire `Stack` table, instead of using the scoped `stacks` helper that every other API controller relies on to enforce an `ApiClient`'s `stack_id` restriction. This lets a token that was explicitly scoped to one stack read build/deploy status for any other stack in the installation.

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column [1](#0-0) . The intended enforcement of that scope lives in `Api::BaseController`: [2](#0-1) 

Here `stacks` restricts the visible `Stack` relation to `current_api_client.stack_id` when the client has one, and `stack` resolves `params[:stack_id]` only within that restricted relation. Tests confirm this is the expected binding: a client scoped via `stack_id` "will only see that one stack" [3](#0-2) .

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [4](#0-3) 

`Stack.from_param!` queries the full, unscoped `Stack` table [5](#0-4) , so the `current_api_client.stack_id` restriction that `stacks`/`stack` in `BaseController` implements is never applied here.

The authorization check that gates the `show` action, `require_permission :read, :stack` [6](#0-5) , only verifies that the string `"read:stack"` is present in `ApiClient#permissions` [7](#0-6) . It performs no comparison between the token's bound `stack_id` and the `stack_id` supplied in the request. So the binding that should hold — "the stack a token authorizes == the stack the action touches" — is broken specifically in this controller: `current_api_client.stack_id` (what the token was scoped to) diverges from `params[:stack_id]` (the stack whose data is rendered).

Additionally, `CCMenuController` supports an alternate authentication path via a query-string `token` param rather than Basic Auth [8](#0-7) , matching the `ccmenu_url` feature that mints a dedicated, narrowly-scoped (`read:stack`) client per stack for embedding in CI dashboards [9](#0-8) . This is precisely the scenario the `stack_id` scoping exists to contain: such a token is meant to be shared/embedded and restricted to one stack's status, yet by editing the `stack_id` in the URL, the holder can retrieve any other stack's latest deploy/build status.

### Impact Explanation
This is an unauthenticated-read escalation: a credential legitimately scoped to read the status of stack A can be used, unmodified except for the URL path segment, to read stack B's latest deploy/rollback status (deploy id, timestamp, running/success/failure state, stack name) via `app/views/shipit/ccmenu/project.xml.builder`. This matches the "unauthenticated read of stack state" High-impact category, since it authorizes cross-stack visibility that the token's `stack_id` binding was specifically meant to prevent, without requiring elevated permissions or additional secrets beyond the token itself.

### Likelihood Explanation
Likelihood is Medium-High for anyone already holding a scoped CCMenu-style token (a routine, low-privilege credential intentionally created for embedding into CI status widgets — see `CCMenuUrlController#client`). No webhook secret, GitHub App key, or admin access is needed; only the ability to substitute a different `stack_id` in an otherwise valid, already-possessed URL.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack.from_param!` directly, so a client's `stack_id` binding is enforced consistently across all API controllers, including this one.

### Proof of Concept
1. Create (or obtain, e.g. via `CCMenuUrlController#fetch`) an `ApiClient` scoped to `stack_id` of stack A with `permissions: ['read:stack']`, e.g. fixture `here_come_the_walrus` scoped to the `shipit` stack [10](#0-9) .
2. Confirm via the ordinary Stacks API that this token is restricted: `GET /api/stacks` returns only stack A [3](#0-2) .
3. Call `GET /ccmenu/*stack_id?token=<token>` (or the namespaced `/api/stacks/*stack_id/ccmenu` route) substituting `stack_id` for an unrelated stack B that the token was never granted access to.
4. Observe the request succeeds with `200 OK` and returns stack B's CI/deploy project XML, because `CCMenuController#stack` resolves `params[:stack_id]` against the entire `Stack` table rather than the client-scoped relation, and `require_permission :read, :stack` never checks that `stack.id == current_api_client.stack_id`.
