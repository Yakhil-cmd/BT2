### Title
Cross-tenant status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` GitHub webhook is authenticated per-organization (the HMAC signature is verified using the secret belonging to the org named in `repository.owner.login`), but the handler that processes the event mutates `Commit` rows selected **only by `sha`**, with no check that the matched commit belongs to the same `repository`/`stack` that owns the authenticating organization. This breaks the binding: `organization that authenticated == repository/stack that is written`.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, derived from the payload's `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

This only proves that the *sender knows the webhook secret for that organization* — it says nothing about which specific commit/stack the event is allowed to affect. Once verified, the raw payload is dispatched to handlers for the event type: [3](#0-2) 

For the `status` event, `StatusHandler#process` looks up commits **globally by `sha` alone**, with no scoping to the repository/organization that produced the signed payload: [4](#0-3) 

Compare this to `PushHandler` and `CheckSuiteHandler`, which correctly scope their effects through `stacks`, itself derived from `Repository.from_github_repo_name(repository_name)` (i.e., `payload.dig('repository','full_name')`): [5](#0-4) [6](#0-5) 

`StatusHandler` uniquely skips this scoping and instead does `Commit.where(sha: params.sha)`, matching any commit row across every tracked repository/stack in the Shipit instance, then calls `commit.create_status_from_github!(params)` for each match — writing the attacker-supplied `state`/`context`/`description`/`target_url` onto that commit's status list: [7](#0-6) 

Because `Commit#sha` is a content-addressed git hash and is not namespaced per repository in this lookup, and Shipit installations can be configured with multiple independent GitHub organizations each holding their own `webhook_secret`: [8](#0-7) 
an event correctly signed for organization A can still write a `Status` onto a `Commit` belonging to a stack tracked under organization B, as long as the `sha` value in the forged/received payload matches an existing commit row anywhere in the database. Since git commit hashes are deterministic over their content (tree, parents, author/committer, timestamps, message), an attacker who can push arbitrary commits to a repository under an org they legitimately control (and which is legitimately connected to Shipit) can reproduce the exact same SHA as a target commit in a *different*, unrelated org's repository (e.g., by replicating the same tree/parent/author/committer/timestamp/message), then trigger a real, properly-signed `status` webhook for their own commit. Shipit will apply that status to every `Commit` row sharing that SHA — including the victim stack's commit.

### Impact Explanation
`Commit#status` drives safety-critical decisions: `deployable?`, `blocked?`, and `schedule_continuous_delivery` (which enqueues `ContinuousDeliveryJob`) are computed from the aggregated status/check-run state: [9](#0-8) [10](#0-9) 

By forging a "success" status onto a target commit that they do not own, an attacker in an unrelated (but Shipit-registered) organization can mark a blocking CI check as passed for a victim stack, causing Shipit to consider the commit `deployable?` and trigger continuous delivery / merge queue progression (`stack.schedule_merges`) that the victim's own CI never approved: [11](#0-10) 
This is an unauthorized-deploy/merge-gating bypass across a repository/authentication boundary the attacker was never granted, matching the "unauthorized deploy, rollback or merge" Critical/High impact category.

### Likelihood Explanation
Exploitation requires: (1) the attacker to have legitimate push access to at least one repository under a GitHub org that is configured/onboarded with Shipit (so their own `status` webhooks are validly signed), and (2) the ability to produce a commit object with an identical SHA-1 to a target commit in a victim stack. Because git commit hashes are fully deterministic from their content fields (tree hash, parent hash(es), author, committer, timestamps, message) and commit metadata (including parent/tree hashes and commit messages) is often publicly visible on GitHub, replicating an existing commit's exact SHA in an attacker-controlled repository is realistic without needing a cryptographic SHA-1 collision — the attacker only needs to reconstruct the same object content, not find a collision between different content. This makes the attack feasible for a technically capable but otherwise unprivileged (with respect to the victim org) attacker.

### Recommendation
Scope `StatusHandler#process` to the repository the webhook was verified for, mirroring `PushHandler`/`CheckSuiteHandler`: restrict the `Commit` lookup to `stacks` derived from `Handler#repository_name` (`payload.dig('repository','full_name')`) rather than a bare, database-wide `Commit.where(sha: ...)`. Additionally, consider validating that `repository.owner.login`/`repository.full_name` are internally consistent with the organization used to select the webhook secret before dispatching to any handler.

### Proof of Concept
1. Shipit is configured with two independent GitHub App installations, one for `org-attacker` and one for `org-victim`, each with a distinct `webhook_secret` (per the documented multi-org configuration).
2. `org-victim/repo` has a tracked `Stack` with a pending commit `C` (sha `deadbeef...`) whose status is used to gate continuous delivery/merge.
3. Attacker, who has push access to `org-attacker/repo` (tracked as an unrelated stack in Shipit), constructs a commit with identical tree, parent, author, committer, and message as `C`, reproducing the same SHA `deadbeef...`, and pushes it to `org-attacker/repo`.
4. A CI system (or the attacker directly) posts a GitHub `status` event with `state: "success"` for sha `deadbeef...` against `org-attacker/repo`. GitHub signs this webhook with `org-attacker`'s legitimate `webhook_secret`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `org-attacker` and verifies successfully against `org-attacker`'s secret: [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, which matches commit `C` belonging to `org-victim`'s stack, and calls `commit.create_status_from_github!(params)`, applying the attacker-controlled "success" status to `C`: [4](#0-3) 
7. `org-victim`'s commit `C` is now marked as having a passing status it never actually received from `org-victim`'s own CI, potentially unblocking deploy/merge for a stack the attacker has no access to.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
