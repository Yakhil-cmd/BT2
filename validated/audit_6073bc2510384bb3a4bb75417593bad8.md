## Analysis

The Mantle DA bug class is: a value that is checked/gated by one rule is actually consumed by a different, weaker binding — i.e. a verification step exists on one representation of data while the code path that acts on it uses a different, unguarded representation of the same conceptual value.

I looked for an analog that breaks an unprivileged-attacker-reachable trust binding, per the rules. The strongest candidate is the single global GitHub OAuth callback (`GithubAuthenticationController#callback`) that resolves and binds a Shipit session (`session[:user_id]`) to a `Shipit::User` row using only the numeric `github_id` returned by whichever OmniAuth provider handled the request — with no scoping to which GitHub App/organization/domain performed the authentication.

`Shipit` explicitly supports multiple, independently configured GitHub Apps per organization, each with its own `domain` (defaulting to `github.com`, but overridable for GitHub Enterprise Server installs), its own `oauth.id`/`oauth.secret`, and its own webhook secret [1](#0-0) [2](#0-1) . `Shipit.github_organizations`/`Shipit.github_app_config` show this multi-org, multi-domain configuration is a first-class, documented feature [3](#0-2) , and the sample secrets file configures two separate orgs each with independent `oauth` credentials [4](#0-3) .

However, the single OAuth callback route mounted by the engine, `GET/POST /github/auth/github/callback`, does not carry or check which organization/domain the OmniAuth strategy authenticated against; it unconditionally calls `sign_in_github(auth)` [5](#0-4) . `sign_in_github` binds the session solely to whatever `User` row `User.find_or_create_from_github` returns:

```ruby
def sign_in_github(auth)
  user = User.find_or_create_from_github(auth.extra.raw_info)
  user.update(github_access_token: auth.credentials.token)
  user.id
end
``` [6](#0-5) 

`User.find_from_github` performs a lookup keyed **only** on the numeric `github_id`, with no domain/organization qualifier:

```ruby
def self.find_from_github(github_user)
  return unless github_user.id
  find_by(github_id: github_user.id)
end
``` [7](#0-6) 

This is the exact bug-class analog: the "verification" that occurred (a valid OAuth completion against *some* configured GitHub App/domain) is a different, narrower fact than what the code actually keys off when granting the session — a bare integer ID with no namespace/domain component. GitHub.com numeric user IDs are unique only within github.com's own ID space; GitHub Enterprise Server installs maintain their own independent, non-coordinated numeric ID sequence starting from 1. Any GHE install configured as a second `Shipit.github` organization therefore has user IDs that collide with pre-existing github.com (or another GHE instance's) IDs.

## Concrete break

- Binding that should hold: `identity authenticated by GitHub App/domain D` == `Shipit::User record scoped to domain D`.
- What the code actually enforces: `github_id integer` == `Shipit::User.github_id` (globally, across all configured domains).

An attacker who is an ordinary (unprivileged) user on a self-hosted GitHub Enterprise instance that an admin has configured as a secondary Shipit organization (a normal, documented multi-org deployment) can look up or brute force which low/attacker-controllable numeric ID on *their own* GHE instance matches the `github_id` of a legitimate `github.com`-authenticated user already known to Shipit (e.g. a repo owner/admin who is `github_id: 1` or any enumerable ID, discoverable via GitHub's public user API `GET /users/{id}`, or by registering new accounts on GHE to obtain a colliding ID such as `1`, `2`, `3`, ...). By completing OAuth against the GHE domain with an account whose ID collides, the callback creates a session (`session[:user_id] = sign_in_github(auth)`) that resolves to the *existing* `Shipit::User` row belonging to the victim on the other domain, because `find_by(github_id:)` has no domain filter. The victim's `github_access_token` field is then overwritten with the attacker's own GHE token, but the attacker now holds a session bound to the victim's `Shipit::User` id — with that account's `teams`/`authorized?` state (`Shipit.github_teams` membership) [8](#0-7)  and authorship identity for deploys, tasks and merges triggered under that user.

This is a session/identity fixation and authorization escalation: an attacker completes a legitimate, low-privilege OAuth handshake on one configured GitHub domain and is granted the Shipit session of an arbitrary pre-existing (or future) user from a different, unrelated GitHub domain whose numeric ID happens to collide — bypassing per-organization team authorization checks and impersonating another identity for triggering deploys/tasks.

## Uncertainty

I could not fully verify from the indexed files how the OmniAuth `provider` name / route is wired to a specific per-organization strategy in `lib/shipit/engine.rb` (the omniauth initializer file itself wasn't returned by search), so I cannot confirm with 100% certainty whether every organization uses the *same* callback path/strategy name or distinct ones per org. If each org gets a distinct OmniAuth provider name but they all funnel into the same `GithubAuthenticationController#callback` action (which routes.rb shows is a single, non-parameterized route), the collision described above still applies. A Devin session with full repo access should confirm `lib/shipit/engine.rb`'s OmniAuth builder configuration to remove any remaining doubt.

### Title
Cross-domain GitHub user ID collision allows session/account takeover in multi-organization Shipit deployments - (File: app/models/shipit/user.rb)

### Summary
`Shipit::User.find_from_github` binds a login session to a user record using only the raw numeric `github_id`, without scoping to the GitHub App/organization/domain that performed the OAuth authentication. Since Shipit natively supports configuring multiple GitHub orgs — including GitHub Enterprise Server installs with independently-issued, non-globally-unique numeric user IDs — an unprivileged user on one configured domain can authenticate with an ID that collides with an existing user on another configured domain and be logged in as that other, potentially privileged, user.

### Finding Description
`GithubAuthenticationController#callback` calls `sign_in_github(auth)` unconditionally for any successful OmniAuth completion [5](#0-4) , which resolves the `Shipit::User` via `User.find_or_create_from_github(auth.extra.raw_info)` [6](#0-5) . That method performs `find_by(github_id: github_user.id)` with no domain qualifier [7](#0-6) . `Shipit` is designed to support several independently configured GitHub organizations, each potentially pointing at a different `domain` (i.e. a self-hosted GitHub Enterprise instance) [1](#0-0) [2](#0-1) , as shown by the sample multi-org secrets file [4](#0-3)  and by `Shipit.github_app_config`/`github_organizations` [3](#0-2) . Because GitHub Enterprise Server installs maintain their own independent numeric ID sequences (not coordinated with github.com or other installs), the same `github_id` value legitimately refers to different real-world people across different domains. The `User` table has no column recording which domain/org a user's `github_id` belongs to, so the lookup conflates them.

### Impact Explanation
An attacker completing OAuth on one configured (secondary/Enterprise) domain can be signed into the `Shipit::User` account of a completely different person on another domain, inheriting that account's `teams`/`authorized?` status used to gate access to the entire application [8](#0-7) , and acting as that user's identity for deploys/tasks/merges. This meets the "escalation into `Shipit.github_teams` authorization" / session fixation impact bar, and depending on the victim's team membership can lead to an unauthorized deploy or rollback carried out under an impersonated identity.

### Likelihood Explanation
This requires the deployment to be configured with more than one GitHub organization/domain (a supported, documented configuration, not a misconfiguration), and requires the attacker to control or register an account on the secondary domain whose numeric ID collides with an existing victim account. Enumerating or engineering a colliding low ID on a freshly stood-up GitHub Enterprise instance is realistic (IDs start at 1 and are sequential), making this feasible for an unprivileged attacker without any credential, token, or repository access.

### Recommendation
Scope `User` lookups (and the `github_id` uniqueness constraint) by the authenticating organization/domain, e.g. store and match on a composite `(domain, github_id)` key instead of `github_id` alone, and have `sign_in_github` pass through which `GitHubApp`/domain handled the OmniAuth callback so `find_from_github` can filter on it.

### Proof of Concept
1. Admin configures Shipit with two organizations: `github.com` (default) and `enterprise-org` pointing to `domain: ghe.internal.example.com`, per the documented multi-org config format.
2. A legitimate user `alice` has `github_id: 12345` on `github.com` and is a member of a `Shipit.github_teams` team, granting her deploy access.
3. Attacker registers/controls an account on `ghe.internal.example.com` whose freshly-assigned numeric ID happens to be `12345` (feasible on a new/low-population GHE instance, or achievable by registering repeatedly until the desired ID is hit, or by asking an admin of that instance to create the millionth+1 user, etc.).
4. Attacker completes the OAuth flow against the `enterprise-org` provider at `/github/auth/github/callback`.
5. `sign_in_github` calls `User.find_or_create_from_github(auth.extra.raw_info)` with `github_id: 12345`; `find_by(github_id: 12345)` returns Alice's existing `Shipit::User` row (created originally via github.com auth).
6. `session[:user_id]` is set to Alice's user id; the attacker is now logged in as Alice, inheriting her team-based authorization and identity for subsequent deploys/tasks, while her `github_access_token` is silently overwritten with the attacker's own GHE token.
