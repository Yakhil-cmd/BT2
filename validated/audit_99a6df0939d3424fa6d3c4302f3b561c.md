### Title
Missing `return` after exception in private-payment hash handler causes double callback invocation and race condition - ([File: network.js])

### Summary
`CVE-2015-3146` is a state-validation bug class: libssh packet handlers (`SSH_MSG_NEWKEYS`, `SSH_MSG_KEXDH_REPLY`) kept processing a packet after an error path was taken, without validating that prior state had actually been set up, leading to use of stale/uninitialized state. The direct analog in ocore is in the private-payment processing code that handles queued `private_payment` messages from a private-payment counterparty: after an exception is caught, the handler fails to stop processing and continues into a second, conflicting code path, invoking the completion callback of the same iteration twice.

### Finding Description
In `network.js`, `handleSavedPrivatePayments()` processes private payment chains received from peers/counterparties and stored in `unhandled_private_payments`. Inside its `validateAndSave` closure: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws for a crafted `payload` (e.g. a value the hashing code rejects), the `catch` block calls `deleteHandledPrivateChain(..., cb)`, which will eventually invoke the `async.each` iteratee callback `cb()` once the DB delete completes. However, execution does **not** `return` after the catch block — it falls through and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` with `ifOk`/`ifError`/`ifWaitingForChain` handlers that **also** call `cb()` on completion (see lines 2486, 2495, 2501). This means the single `async.each` iteratee callback for this row is called twice.

This is structurally the same bug class as the CVE: an error/exit path is taken, but the surrounding state machine is not properly short-circuited, so a second, independent code path (that assumes the “good” state) is also executed against data (or callback machinery) that has already been handled/invalidated.

### Impact Explanation
`handleSavedPrivatePayments` is guarded by `mutex.lock(["saved_private"], ...)` and drives `async.each(rows, iteratee, finalCallback)`. In the `async` library, invoking an iteratee's callback more than once for the same item corrupts the internal completion counter, which can cause the `finalCallback` (which calls `unlock()` and emits `"new_my_transactions"`) to fire prematurely — while other rows in the same batch are still being validated/saved — or to fire multiple times. Because `"saved_private"` is the mutex that serializes private-payment writes (which insert `inputs`/`outputs`/`spend_proofs` rows for private asset chains), premature/duplicate unlocking allows a second `handleSavedPrivatePayments` invocation (or another related private-payment save) to start concurrently while the first batch's DB transaction/queries are still in flight, defeating the serialization the mutex is meant to guarantee. Concurrent, unserialized writes to private-payment chain state can result in duplicate acceptance of the same private chain, corrupted `is_spent`/`is_unique` bookkeeping in `inputs`/`outputs`, or inconsistent local state that can be leveraged by a malicious private-payment counterparty to get a private asset chain double-counted or re-spent from the victim's perspective — i.e., double-spend/inconsistency of a private payment chain rather than a mere crash.

Reachability: `handleSavedPrivatePayments` is invoked for private payments received from any peer via `private_payment` justsaying / `hub/message`, i.e. from an ordinary private-payment counterparty, requiring no special privilege — matching the allowed "private-payment counterparty" attack surface.

### Likelihood Explanation
Triggering the exception requires crafting `objHeadPrivateElement.payload` such that `objectHash.getBase64Hash(...)` throws (e.g., malformed/oversized numeric or malformed fields not otherwise rejected by earlier structural checks in `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`, which validate presence of fields but not full serializability/hash-computability). Because this path is only reached after the payment has already passed the coarse-grained shape checks in `handlePrivatePaymentChains` (`network.js`) and gets persisted to `unhandled_private_payments`, and then re-processed asynchronously by `handleSavedPrivatePayments`, an attacker acting as a private-payment counterparty controls the payload content well enough to attempt to trigger this exception. I was not able to fully confirm, within the available tool budget, the exact conditions under which `object_hash.getBase64Hash` throws for otherwise-structurally-valid payloads (the body of `getBase64Hash` in `object_hash.js` was located but not read in this session), so the precise trigger conditions for the exception remain unverified.

### Recommendation
Add an explicit `return` (or restructure with an `if/else`) after the `catch` block in `validateAndSave` in `network.js` so that `privatePayment.validateAndSavePrivatePaymentChain(...)` is never invoked when the hash computation already failed and `cb` was already scheduled via `deleteHandledPrivateChain`. More generally, audit all `try/catch` blocks in message/trigger/private-payment handlers that call an async completion callback inside the `catch` for missing `return` statements, to guarantee that only one control-flow path reaches the per-item completion callback, and that mutexes gating serialized state writes are only released once per batch.

### Proof of Concept
1. As a private-payment counterparty, send (directly or via hub) a `private_payment` message via `wallet.js`'s `handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment`, whose `arrPrivateElements[0].payload` passes the coarse `isNonemptyObject`/`isNonemptyArray` checks in `handlePrivatePaymentChains` (`wallet.js:955-972`) but is crafted so that `objectHash.getBase64Hash(payload, true)` throws when later re-processed (root cause and exact trigger value require further analysis of `object_hash.js`, not confirmed in this session).
2. The payment gets queued into `unhandled_private_payments` (light client path) or otherwise re-enters `handleSavedPrivatePayments`.
3. When `handleSavedPrivatePayments` processes this row, `getBase64Hash` throws; the `catch` block schedules `deleteHandledPrivateChain(..., cb)`, but code execution falls through and also calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, which independently calls `cb()` again on completion.
4. Observe (via instrumentation/logging of `async.each`'s internal counters, or by sending two concurrent batches of private payments and inspecting `inputs`/`outputs`/`spend_proofs` rows for the same private chain) that the `"saved_private"` mutex is released early/twice, allowing overlapping `handleSavedPrivatePayments` runs and resulting in duplicate/racy writes to private-chain spend state.
