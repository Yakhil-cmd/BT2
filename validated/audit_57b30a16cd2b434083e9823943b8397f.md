### Title
Cross-tenant webhook forgery via repository owner/full_name divergence in signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the per-organization `webhook_secret` using only `repository.owner.login` from the JSON body, but `PullRequest::OpenedHandler#repository` (and sibling handlers) independently resolves the target repository from `repository.full_name` in the same body. Because these two fields are never checked for consistency, a payload can pass signature verification against `attacker-org`'s secret while causing writes against `victim-org`'s tracked repository.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `org_whose_secret_verified_signature (params.dig('repository','owner','login'))` == `org_owning_mutated_repository (Repository.from_github_repo_name(params.repository.full_name).owner)`.

Trace:
- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads only `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), then calls `github_app.verify_webhook_signature(header_signature, raw_post)`. [2](#0-1) 
- `GitHubApp#verify_webhook_signature` just HMAC-verifies the raw body against the secret belonging to that named organization — it has no knowledge of, and does not inspect, `repository.full_name`. [3](#0-2) 
- Once verified, `WebhooksController#create` dispatches the entire raw `params` hash to the matching handlers (e.g. `Shipit::Webhooks.for_event('pull_request')` → `OpenedHandler`), with no re-derivation or re-validation of which organization the body "belongs to". [4](#0-3) 
- `OpenedHandler#repository` resolves the target row purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, and `OpenedHandler#process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` — this can create/mutate a `Stack`/`ReviewStack` belonging to whatever repository that `full_name` maps to, regardless of which org's secret verified the request. [5](#0-4) 

This precondition — multiple GitHub Apps/secrets per organization — is an explicitly supported, documented configuration (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`), confirming the attack surface is real for multi-tenant Shipit deployments. [6](#0-5) 

Attacker request: the attacker, who legitimately owns a repo under `attacker-org` (and thus knows/receives `attacker-org`'s `webhook_secret` when Shipit's admin installs the GitHub App on `attacker-org`), directly POSTs to `/webhooks` (not via GitHub's actual delivery pipeline) with:
- Header `X-Github-Event: pull_request`, `X-Hub-Signature` = valid HMAC-SHA1 of the raw body using `attacker-org`'s `webhook_secret`.
- Body JSON: `action: "opened"`, `repository.owner.login: "attacker-org"`, `repository.full_name: "victim-org/tracked-repo"`, plus a `pull_request` object satisfying `OpenedHandler`'s `ExplicitParameters` schema.

`verify_signature` computes `Shipit.github(organization: "attacker-org")` and validates the signature successfully (attacker knows this secret), then `OpenedHandler` resolves `repository.full_name` = `"victim-org/tracked-repo"` and calls `find_or_create!`, creating a `Shipit::ReviewStack`/`Stack` for `victim-org`'s repository — entirely outside the scope of what `attacker-org`'s webhook credentials should authorize.

Existing guards do not catch this: `drop_unhandled_event` only filters by event type, not org; `ExplicitParameters` schema only validates types/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`; there is no model validation tying `Repository#owner` to the webhook's authenticated org at request time.

### Impact Explanation
An attacker holding only their own low-privilege organization's webhook secret can cause `Shipit::Stack`/`ReviewStack` creation (and subsequent provisioning, which per `OpenedHandler#provision?`/`ReviewStackAdapter#find_or_create!` can trigger deploy tasks that shell out via `Command`/`PTY.spawn`) against an arbitrary tracked repository belonging to a different, victim organization. This is a cross-tenant authentication/provenance bypass matching "payload for one repository mutating another's stack" and potentially leading to unauthorized deploy/task execution against `victim-org`'s code — Critical severity. The attack is repeatable against any tracked repository whose `full_name` the attacker can guess/know, as long as any organization's webhook secret is available to the attacker.

### Likelihood Explanation
Requires: (1) the Shipit deployment configured with per-organization GitHub Apps/secrets (the documented multi-org schema), (2) attacker owns/administers a repository in at least one such configured organization (`attacker-org`), thus obtaining that org's `webhook_secret` through legitimate GitHub App installation, and (3) `victim-org/tracked-repo` exists as a tracked `Shipit::Repository` with review stacks provisioning enabled matching `OpenedHandler#provision?`. Given multi-org setups exist for exactly this purpose (onboarding multiple external orgs), and the attacker only needs one org's secret (their own), the cost is low and the request is fully scriptable/repeatable without hitting GitHub at all.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler's `repository` resolution), enforce that the organization derived from `repository.full_name` (or `repository.owner.login`) used to select the `webhook_secret` matches the organization owning the resolved `Shipit::Repository`/`full_name` before dispatching to handlers — e.g., reject the webhook if `params.dig('repository','full_name')&.split('/')&.first&.casecmp?(repository_owner)` is false.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, extending existing patterns like the double-github-app tests):
1. Configure `Shipit.stubs(:secrets)` with two orgs, `attacker-org` (webhook_secret `sekret_a`) and `victim-org` (webhook_secret `sekret_v`), using the `secrets_double_github_app.yml` fixture pattern.
2. Create `victim_repo = shipit_repositories(:shipit)` with `full_name: "victim-org/tracked-repo"`, `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
3. Build a `pull_request` `opened` payload with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/tracked-repo"`.
4. Compute `X-Hub-Signature` = `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'sekret_a', raw_body)`.
5. `post shipit_engine.webhooks_path, params: raw_body, headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }`.
6. Assert response is `200`/`:ok` (signature accepted), and `assert_difference -> { Shipit::Stack.where(repository: victim_repo).count }` around the POST, proving `attacker-org`'s secret created a stack for `victim-org`'s repository.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
