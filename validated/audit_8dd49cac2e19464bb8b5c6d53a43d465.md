### Title
Attacker-controlled post-commit/hook stdout can spoof `[branch sha]`+diffstat, causing the commit-review hook to `git show` and exfiltrate an unintended commit to the LLM sink - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`handle_commit_review_posttooluse` derives the SHA it reviews purely from text pattern-matching (`_COMMIT_SHA_RE` + `_COMMIT_DIFFSTAT_PATTERNS`) over the combined stdout/stderr of the `git commit` Bash invocation, without ever verifying that the extracted SHA is actually `HEAD` after the commit. A malicious hook script that runs as part of the same `git commit` invocation (e.g. a repo-tracked husky/pre-commit hook installed via `core.hooksPath`) and prints text after git's own summary line can spoof the "last match wins" heuristic, causing `git show -p <attacker-chosen-sha>` to run on a commit the attacker selects, whose diff is then forwarded to the remote LLM in `llm.py`.

### Finding Description
The commit-succeeded gate is: [1](#0-0) 
and the SHA used for `git show -p` is simply the last regex match in the combined output: [2](#0-1) 

The code's own comments acknowledge that hook frameworks (pre-commit/husky/lint-staged) can print decoy bracketed text that looks like `[branch sha]`, and defends against this only by (a) requiring a diffstat signal too, and (b) taking the *last* match, on the stated assumption that "the real commit line is always last in git's own output — the earlier matches are either decoys or superseded commits": [3](#0-2) 

This assumption only holds for hooks that run *before* git prints its summary line (pre-commit, commit-msg). It does not hold for `post-commit` hooks, which git invokes *after* the commit is created and after the "[branch sha] subject ... N files changed" summary is already written to the same stdout stream. A repo-tracked hook (e.g. installed via husky's `prepare` script setting `core.hooksPath` to a repo-tracked directory, or a checked-in `.pre-commit-config.yaml`/custom hook) that runs as `post-commit` can print a forged line such as `[main <attacker_sha>] fake\n 3 files changed\n create mode 100644 x` after the genuine line, and this forged line — not the real one — is what `_COMMIT_SHA_RE.findall(...)[-1]` returns.

The only remaining guard is that `git show -p <sha>` must succeed (`result.returncode == 0`), i.e. the SHA must resolve to a real object already present in the repo's object database: [4](#0-3) 
There is no check that the resolved SHA is `HEAD`, an ancestor of `HEAD`, or otherwise related to the commit that was just made — an attacker who controls repo content (and can therefore pre-plant a commit object anywhere in the repo's history/other branches/reflog) can point the forged line at any SHA of their choosing that exists in the local object store.

### Impact Explanation
This lets attacker-controlled repository content (a hook script, not the LLM-facing commit message) determine which local commit's diff is sent to the remote LLM defined in `llm.py`, instead of the diff of the commit the user/agent actually just made. Because `git show` only requires the object to exist locally (not to be reachable from the current branch), this could select and forward the diff of a different branch's tip, a stashed/rewritten commit, or another commit sitting in the local object database — i.e., content the user did not intend to send to a third-party model endpoint at that time. This is a trust-boundary bypass (hook output treated as trusted git metadata) and a scoped, real content-substitution/exfiltration bug, though its severity is bounded by the fact that (a) the target SHA must already exist as an object in the *same* repo (no cross-repo/arbitrary-content injection), and (b) the agent already has git access sufficient to read any such object directly.

### Likelihood Explanation
Exploitation requires: (1) attacker-controlled repo content that gets installed/executed as a git hook reachable from the agent's `git commit` invocation (e.g., husky config triggered by a `prepare`/`postinstall` script, or a tracked custom hooks directory the project points `core.hooksPath` at), and (2) that hook running with `post-commit` timing so its forged output lands after git's genuine summary line in the captured stdout/stderr. Both preconditions are plausible in realistic "malicious/compromised third-party repo" scenarios that agentic coding tools are commonly exposed to, and require no privilege escalation beyond ordinary repository content and a normal `npm install`/`git commit` workflow the agent would perform anyway.

### Recommendation
Do not trust free-text stdout/stderr to select the reviewed SHA. After a successful commit, resolve the actual commit via `git rev-parse HEAD` (or diff `HEAD@{1}..HEAD` / consult the reflog `commit:`/`commit (amend):` entry as already done in the reflog fallback path) and cross-check that this resolved value is a prefix match of the parsed `_COMMIT_SHA_RE` group before using it for `git show`, rather than trusting the last regex match unconditionally. Additionally, since git already invokes hooks with a controllable environment, consider disabling hook execution for the review-relevant `git` invocations (`git -c core.hooksPath=/dev/null` is not applicable to the user's own `git commit`, but the *parsing* step should not rely on hook-influenced output at all) — the safest fix is to stop parsing hook-tainted stdout entirely and always resolve the reviewed SHA via `git rev-parse HEAD`/reflog rather than string matching on Bash output.

### Proof of Concept
Unit/fuzz test plan for `security_reminder_hook.py`:
1. Construct a `tool_response.stdout` string simulating: genuine git output (`[main abc1234] real commit\n 1 file changed`) followed by attacker-appended text mimicking a `post-commit` hook: `[main deadbee] fake\n 5 files changed\n create mode 100644 secret.txt`, where `deadbee...` is a real, pre-existing SHA in the test repo's object store (e.g., an old commit on another branch containing a marker string) that is NOT `HEAD` after the real commit.
2. Invoke `handle_commit_review_posttooluse` with this crafted `tool_response` and assert that the SHA passed into `git show -p` equals `git rev-parse HEAD` at the time of the call, not `deadbee...`.
3. Assert failure of the current implementation: `_COMMIT_SHA_RE.findall(bash_output)[-1]` returns `deadbee...` instead of `abc1234...`, demonstrating the parser differential, and that `git show -p deadbee...` is executed and its diff forwarded toward `analyze_code_security`/`_call_claude`.
4. As an invariant/fuzz property: for any bash_output matching both `_COMMIT_SHA_RE` and `_COMMIT_DIFFSTAT_PATTERNS`, the SHA passed to `git show -p` must equal the actual `HEAD` (or a verified reflog-derived commit) produced by *this* `git commit` invocation; the test should fail on the current code and pass after adding the `HEAD`-verification recommended above.
