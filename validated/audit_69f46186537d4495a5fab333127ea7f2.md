### Title
Commit-status webhook forgery lets any onboarded GitHub organization inject CI status onto commits belonging to a stack it does not own - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit purely by SHA, with no scoping to the repository/organization whose webhook secret produced the signature. This breaks exactly the binding the Sherlock report describes: a value that is authenticated (the signing organization) diverges from the value that is acted upon (the repository/stack whose commit is written).

### Finding Description
The webhook signature check in `WebhooksController#verify_signature` selects the HMAC secret to validate against using `repository_owner`, i.e. `params.dig('repository','owner','login') || params.dig('organization','login')`: [1](#0-0) [2](#0-1) 

This only proves the payload was signed by *some* organization that has legitimately installed the Shipit GitHub App (a normal, unprivileged deployment scenario — any org onboarded onto the same Shipit instance, e.g. as shown by the multi-org config in `secrets_double_github_app.yml`, can independently sign requests with its own `webhook_secret`).

The generic `Handler` base class does correctly scope actions to the repository named in the payload via `stacks`/`repository_name`: [3](#0-2) 

However, `StatusHandler#process` bypasses this scoping entirely and looks up commits globally by SHA across every stack in the Shipit instance: [4](#0-3) 

The equality that should hold is: `organization that signed the payload == organization owning the repository/stack that the commit's status is applied to`. Instead, `StatusHandler` only checks `commit.sha == params.sha`, so any organization X that has validly installed the app (and therefore knows/controls its own `webhook_secret`) can send a signed `status` event naming an arbitrary SHA. If that SHA happens to exist in another org Y's stack (git SHAs of Y's commits are public on GitHub, so an attacker can simply read them off Y's public repository), the forged status is attached to Y's commit, not X's.

### Impact Explanation
Commit CI status directly governs `Commit#deployable?`, which gates whether a commit can be deployed: [5](#0-4) 

An attacker who controls any org installed on the shared Shipit instance can forge a `success` status for a commit belonging to a completely different, unrelated stack/repository, without ever authenticating to or holding any credential for that victim stack. This can enable an unauthorized deploy of a commit that never actually passed CI in its own repository (bypassing the `require_ci`/`ignore_ci` safety and CI-blocking checks), which matches the required "unauthorized deploy" impact class.

### Likelihood Explanation
The only prerequisite is that the attacker's own GitHub organization is one of the (potentially many) organizations onboarded to the shared Shipit instance — an ordinary, unprivileged condition documented by Shipit's own multi-org support (`secrets_double_github_app.yml`), not a privileged account or stolen secret. No `ApiClient` token, session, or victim's `webhook_secret` is required — only the attacker's own legitimately-issued secret for their own org, which they possess by design. Target commit SHAs are typically public (visible on the victim's GitHub repository page), making the cross-repo SHA collision trivial to exploit deliberately rather than requiring a hash collision.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload the same way the base `Handler#stacks` helper does, e.g. restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or otherwise verify `commit.stack.repository == repository` before applying the status), so status writes can only affect commits that belong to the same repository/organization that produced the verified signature.

### Proof of Concept
1. Onboard organization `Attacker/attacker-repo` onto the shared Shipit instance (normal, unprivileged setup already supported by the engine's multi-org config).
2. Identify a target commit SHA `abc123...` in `Victim/victim-repo`'s public GitHub history (or an existing `Commit` row already tracked by the target stack).
3. Using `Attacker`'s own legitimate `webhook_secret`, compute a valid `X-Hub-Signature` for a JSON body:
```json
{ "sha": "abc123...", "state": "success", "context": "ci/forged", "target_url": "http://attacker.example" }
```
4. POST to `/webhooks` with `X-Github-Event: status` and the forged, but validly-signed-for-`Attacker`, signature.
5. `WebhooksController#verify_signature` succeeds because it validates against `Attacker`'s secret (derived from the attacker-controlled `repository`/`organization` fields), which the request satisfies.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the commit belonging to `Victim/victim-repo`'s stack (unrelated to `Attacker`), and calls `create_status_from_github!`, writing a forged `success` status onto it — potentially unblocking a deploy of that commit in `Victim`'s stack. # frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
