### Title
Webhook signature verification is scoped to a forgeable "authenticating organization" while event handlers act on an unrelated "target repository" - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the `X-Hub-Signature` against using a value taken directly from the untrusted, attacker-supplied JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up per-organization config via `github_app_config`, and `GitHubApp#verify_webhook_signature` explicitly **skips verification entirely** when that organization has no `webhook_secret` configured: [3](#0-2) 

Crucially, once the request passes (or bypasses) this check, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire* attacker-controlled payload to handlers, which resolve the *actual target repository/stack/commit* from **different fields of the same payload** — fields never tied back to `repository_owner`:

- `PushHandler`/`Handler#stacks` resolves the target via `payload.dig('repository', 'full_name')`, independent of `repository.owner.login`: [4](#0-3) 
- `StatusHandler#process` resolves target commits via `Commit.where(sha: params.sha)` — with **no repository/organization scoping at all**: [5](#0-4) 
- `MembershipHandler#process` mutates `Team`/`User` membership using `params.organization.login`, again distinct from the `repository_owner` used for signing: [6](#0-5) 

This is the same trust-binding bug class as the MarinateV2 report: an operation is authorized against one identity (the whitelisted/authenticating party — here, `repository_owner`/organization used for signature selection), while the effect is applied to a different, unverified identity (the marinator receiving funds — here, the repository/commit/organization actually acted upon via `repository.full_name`, `sha`, or `organization.login`). The equality that should hold, `organization authenticated == repository/commit acted upon`, is never enforced.

### Impact Explanation
On a multi-organization Shipit deployment (`Shipit.github_organizations` / `github_app_config`), if **any one** configured organization omits `webhook_secret` (documented as optional in `docs/setup.md`), an unauthenticated attacker can:
1. Set `repository.owner.login` (or `organization.login`) to that unprotected organization to make `verify_signature` short-circuit to `true` via `return true unless webhook_secret`.
2. Set `repository.full_name` (push handler) or `sha` (status handler) to reference a **completely different, protected** stack/commit belonging to another organization.

This lets the attacker queue a `GithubSyncJob` with an attacker-chosen `expected_head_sha` for any tracked stack (via `PushHandler`), or inject arbitrary/forged commit statuses for **any commit SHA in the entire instance** (via `StatusHandler`, since it has no repository filter at all), potentially marking malicious commits as CI-green. Depending on how the host application gates deploys/merges on commit status, this can lead to an unauthorized deploy of attacker-controlled code — meeting the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Requires only that at least one organization configured in `secrets.github` (multi-org schema) has no `webhook_secret` set — an explicitly optional field per `docs/setup.md` — and requires no GitHub credentials, no Shipit session, and no API token; the attacker only needs to know one repository's `full_name`/one commit `sha` to target and POST directly to the public `/webhooks` endpoint.

### Recommendation
After signature verification, validate that the fields the handlers actually operate on (`repository.full_name`'s owner, or the resolved `Stack`/`Commit`'s owning repository) belong to the same organization/App installation that produced a *valid, non-bypassed* signature. Do not allow `verify_webhook_signature` to return `true` for organizations lacking a `webhook_secret`; instead require an explicit "signature not required" allow-list, and bind that decision to the same repository identifier the handlers use, not just `repository.owner.login`/`organization.login`.

### Proof of Concept
1. Configure Shipit in multi-org mode where org `attacker-org` has no `webhook_secret` set, while org `victim-org` (owning the tracked stack) has one.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-stack-latest-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
No `X-Hub-Signature` header (or an arbitrary one) is required because `verify_webhook_signature` returns `true` for `attacker-org`.
3. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, creating a forged "success" status on the victim commit despite the attacker never having presented any credential tied to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
