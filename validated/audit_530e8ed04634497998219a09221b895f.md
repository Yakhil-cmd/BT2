### Title
Uncaught exception / crash from malformed c-hash decoding in `chash.isChashValid` - (File: chash.js)

### Summary
The Alpine advisory describes a heap-based buffer overflow in `collectd`'s `parse_packet()`, where a crafted length field in attacker-controlled network data is not validated before being used to size/index a buffer, causing a crash (or worse). The ocore codebase has an analogous root cause in its c-hash (checksum-hash) decoder, `chash.js`, where an attacker-controlled "length" is derived from decoding an untrusted string and is not validated before being fed to length-sensitive downstream functions, which then `throw` on mismatch instead of failing gracefully.

### Finding Description
`isChashValid()` decides between 160-bit (address) and 288-bit (large-definition chash) decoding purely from the *string length* (32 or 48 chars), then decodes it into a `Buffer` and calls into helper functions that assume the resulting *bit length* is exactly 160 or 288: [1](#0-0) 

Only the decode step (`base32.decode` / `Buffer.from(..., 'base64')`) is wrapped in `try/catch`. The subsequent processing — `buffer2bin`, `separateIntoCleanDataAndChecksum`, `bin2buffer` — is not: [2](#0-1) 

`separateIntoCleanDataAndChecksum` explicitly `throw`s an `Error` if the *actual* bit length of the decoded buffer isn't exactly 160 or 288, i.e. it trusts the caller to have already guaranteed this invariant. But `Buffer.from(str, 'base64')` in Node.js is lenient: characters outside the base64 alphabet are silently skipped, so a 48-character string containing invalid base64 characters can decode to a buffer of a *different* byte length than 36 (288 bits). This directly parallels the CVE's root cause: an attacker-controlled length/size value derived from untrusted input is not validated before being trusted by downstream parsing logic, leading to an out-of-bounds/mismatched-length condition that the code does not defensively handle.

Callers rely on `isValidChash`/`isChashValid` to be safe boolean predicates: [3](#0-2) 

For 32-character values, `isValidAddress` additionally enforces a strict `^[A-Z2-7]{32}$` regex before calling `isValidChash`, which constrains base32 decoding to always succeed cleanly: [4](#0-3) 

However, `isValidChash`/`isChashValid` themselves provide no such character-set guard for the 48-character (chash288) case — that path only checks `encoded.length === 48` before calling `Buffer.from(encoded, 'base64')`. Any code path in ocore that validates a definition_chash or similar 48-character c-hash by calling `isValidChash(str, 288)`/`isChashValid` without first enforcing a base64-alphabet regex is exposed to this uncaught exception.

Note: due to tool/iteration limits I was not able to fully trace and cite the exact production call site(s) that invoke the 288-bit chash validation path with unsanitized attacker input (e.g., an `address_definition_change` message's `definition_chash` field, or an oscript `evaluate`/`address` verification path). This should be confirmed by grepping for all callers of `isValidChash`/`isChashValid` with an expected length of 48 before treating this as fully proven in a specific reachable path.

### Impact Explanation
If a 48-character c-hash value taken from attacker-controlled unit content (e.g. a definition_chash embedded in a posted unit, address-definition-change message, or an oscript definition reference) reaches `isChashValid` and contains characters outside the base64 alphabet, `separateIntoCleanDataAndChecksum` throws an uncaught `Error`. If this call occurs on a validation code path that isn't wrapped in try/catch at every layer, it will propagate as an unhandled exception during unit validation, crashing the node process that is validating the unit. Since this is triggered deterministically by the same crafted unit content on every node that validates it, an attacker could use a single posted unit to crash any/all full nodes that attempt to validate it — a "network unable to confirm new units" condition, which is one of the accepted impact categories.

### Likelihood Explanation
Likelihood depends on whether any reachable validation code path calls `isValidChash`/`isChashValid` on an unrestricted (non-regex-checked) 48-character string sourced from unit/message content without an upstream base64-alphabet check. The 32-character (address) path is protected by an explicit regex and is not exploitable this way. The overall bug-class match to the CVE (untrusted length used in parsing without a defensive check, leading to an unhandled fault) is strong and concrete within `chash.js` itself, but exploitability hinges on locating (or the existence of) an unguarded 288-bit chash validation call site, which I could not fully confirm within the available tool budget.

### Recommendation
- Wrap the whole body of `isChashValid` (not just the initial decode) in the try/catch, and treat any internal `Error` (e.g., "bad length=...") as `return false` rather than letting it propagate.
- Additionally enforce a strict base64-alphabet regex on 48-character inputs (analogous to the `^[A-Z2-7]{32}$` regex used for addresses) before calling `Buffer.from(encoded, 'base64')`, so length mismatches can never occur.
- Audit all call sites of `isValidChash`/`isChashValid` for the 288-bit case to ensure none of them can be reached with unvalidated, attacker-supplied strings without this hardening.

### Proof of Concept
1. Construct a 48-character string that satisfies `encoded.length === 48` but includes characters outside the base64 alphabet (e.g., replacing some characters with `!`, `~`, or Unicode characters), such that `Buffer.from(encoded, 'base64')` decodes to a buffer whose length in bits is not 288 (Node silently drops invalid characters, shortening the decoded output).
2. Pass this string to `chash.isChashValid(encoded)` (directly, or via any validation path — e.g., a definition_chash field in a posted unit/message — that calls `isValidChash(str, 288)` without a prior base64-charset check).
3. Execution reaches `separateIntoCleanDataAndChecksum(binChash)` in `chash.js` with `bin.length` not equal to 160 or 288, hitting the `throw Error("bad length="+len+...)` statement, which is outside of `isChashValid`'s try/catch block and propagates as an unhandled exception in the calling validation code.
