### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the handler dispatches on `repository.full_name` — allowing cross-organization/cross-repository writes in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App configuration, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against based on `repository_owner`, which is read from `payload.dig('repository', 'owner', 'login')` (falling back to `organization.login`). However, once the signature check passes, the actual event handler (e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a *different* payload field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name` and `Repository.from_github_repo_name`. Nothing ties the verified organization to the repository that is ultimately acted upon.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This selects the org-specific `webhook_secret` (configured per top-level org key in `secrets.github`) to validate the HMAC — this is the intended multi-app isolation mechanism documented for "Using Multiple Github Applications" [3](#0-2) .

But the actual side effect of the request — e.g. for `push` events — is computed by `PushHandler`, which pulls the repository to act on from a *separate* field of the same JSON body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

`Repository.from_github_repo_name` parses `owner/name` directly out of `full_name` with no relation to `repository_owner`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [6](#0-5) 

The binding that should hold is: `organization authenticated (repository_owner used to pick the webhook_secret) == owner of repository.full_name (the repository whose stacks get mutated)`. Nothing in `WebhooksController` or `Handler` enforces this equality — `repository.owner.login` and `repository.full_name`'s owner segment are read from independent, attacker-influenced JSON keys within the same signed payload, and the code never cross-checks them.

In a self-hosted, multi-org Shipit deployment (per `docs/setup.md`'s "Using Multiple Github Applications" section), each org owner legitimately possesses (or controls) their own GitHub App's `webhook_secret`. An organization admin/owner of Org A can therefore correctly compute a valid `X-Hub-Signature` for Org A's secret, while crafting the JSON body's `repository.full_name` to reference `OrgB/some-repo` — a repository/stack they do not own. Because the signature check only validates *that the bytes were signed with Org A's secret*, not that the repository referenced in the payload belongs to Org A, `verify_signature` passes, and `PushHandler` proceeds to call `stack.sync_github(expected_head_sha: ...)` on Org B's stack.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated == repository being written," directly enabling cross-repository writes: an attacker who legitimately controls one tenant's GitHub App configuration can force `GithubSyncJob`/`sync_github` against another tenant's `Stack`, syncing an arbitrary attacker-chosen `expected_head_sha` and branch state into that stack's git cache. If the target stack has `continuous_deployment` enabled, a forged sync of a malicious or unauthorized commit can feed directly into automatic deploy triggering, resulting in an unauthorized deploy on infrastructure the attacker does not control. This matches the Critical impact category "cross-repository writes, or an unauthorized deploy."

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with multiple GitHub Apps/organizations sharing one `/webhooks` endpoint (an explicitly documented supported configuration), and (2) the attacker to be an admin/owner of at least one onboarded organization (i.e., possess that org's `webhook_secret`). This is a narrower prerequisite than a fully unauthenticated attacker, but it is exactly the kind of "legitimate but limited" trust an org-scoped credential is supposed to be confined to — the vulnerability is that Shipit does not confine it, allowing lateral movement across tenants that the multi-org feature is meant to isolate.

### Recommendation
After computing `repository_owner` and verifying the signature, additionally assert that the repository/organization referenced by the event body used for dispatch (`payload.dig('repository', 'full_name')`'s owner, or `payload.dig('organization', 'login')`) matches the same `repository_owner` used to select the signing key. Reject the webhook (422) if they diverge. Alternatively, resolve the target `Stack`/`Repository` strictly by combining the owner used for signature verification with the repo name, rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org example) [7](#0-6) .
2. As the (legitimate) owner/admin of `org-a`, obtain `org-a`'s `webhook_secret`.
3. Craft a `push` event JSON body where `repository.owner.login = "org-a"` (so `repository_owner` resolves to `org-a`'s app for signature verification) but `repository.full_name = "org-b/target-repo"` and `ref`/`after` reference an attacker-chosen commit.
4. Compute `X-Hub-Signature` using `org-a`'s `webhook_secret` over the crafted raw body, per `verify_webhook_signature` [8](#0-7) .
5. POST to `/webhooks` with header `X-Github-Event: push` and the computed signature.
6. `verify_signature` passes (Org A's secret matches), and `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("org-b/target-repo")` and calls `stack.sync_github(expected_head_sha: <attacker sha>)` on `org-b`'s stack [5](#0-4) , despite the attacker having no relationship to `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
