### Title
Missing-field crash when an AA dereferences a content_hash-stripped unit via `unit[]` formula - (File: formula/evaluation.js)

### Summary
CVE-2021-37750 is a NULL-pointer dereference in MIT Kerberos's `do_tgs_req.c`, caused by code that assumes a `server` field is present in a FAST inner request body and dereferences it without checking, crashing the KDC when an attacker omits that field. The analogous bug class — unchecked assumption that an optional/absent field exists on an attacker-influenced object, leading to a crash — is reachable in ocore's oscript/formula evaluator when an Autonomous Agent formula reads an arbitrary past unit via the `unit[...]` operator.

### Finding Description
In `formula/evaluation.js`, the `case 'unit':` handler lets AA code fetch any past on-chain unit by hash and exposes it as a `wrappedObject` for further field access: [1](#0-0) 

After fetching the unit, the code unconditionally iterates `objUnit.messages` to strip `temp_data` payloads:
```
for (let m of objUnit.messages)
    if (m.app === "temp_data")
        delete m.payload.data;
```
This assumes `objUnit.messages` is always an array. However, `validation.js` explicitly allows units to be stored without a `messages` field when they are "nonserial" units that carry a `content_hash` instead of full message content — these units only need `unit, version, alt, timestamp, authors, witness_list_unit, witnesses, content_hash, parent_units, last_ball, last_ball_unit` and are accepted as valid, stable, "good"-sequence units: [2](#0-1) 

Because such content_hash-stripped units are legitimate, stable, `sequence='good'` units that can exist in the DAG (e.g., produced via catchup/hash-tree pruning or archived nonserial units), `storage.readJoint` can return an `objJoint.unit` object that has no `messages` property at all. When an AA's oscript calls `unit['<hash of such a unit>']`, the evaluator reaches the `for (let m of objUnit.messages)` line with `objUnit.messages === undefined`, and `for...of` on `undefined` throws a `TypeError` synchronously inside the `ifFound` callback of `storage.readJoint`.

This exception is not caught anywhere on this path (no try/catch wraps this iteration, unlike other risky operations in the same file which are explicitly wrapped in try/catch, e.g. `objectHash.getUnitHash`, `getBase64Hash`, etc.). An uncaught exception thrown asynchronously from a DB/cache callback in a full node is not caught by any surrounding `try` in the AA trigger-processing call chain (`handleTrigger` → `evaluateAA` → formula `evaluate`), and ultimately triggers Node's `uncaughtException` handler in `network.js`, which explicitly re-throws to crash the process: [3](#0-2) 

### Impact Explanation
Any address (including an unprivileged AA trigger sender) can construct an oscript/AA definition (or trigger an existing AA) that executes `unit[<hash>]` referencing a known nonserial/content_hash-stripped unit. Reaching this formula operator during AA response evaluation causes the node evaluating the trigger — which is every full node validating/computing AA responses on the network, not just the poster — to throw an uncaught `TypeError`. Because the process-level `uncaughtException` handler deliberately re-throws to crash the process ("crash the process to avoid ending up in an inconsistent state"), this results in a network-wide denial of service: every full node that processes this AA trigger unit crashes, halting confirmation of new units on affected nodes until manually restarted. This satisfies the "network unable to confirm new units" / "node disagreement" impact bar (nodes that crash cannot validate further units; nodes that haven't yet processed the trigger remain fine until they do, creating potential inconsistency and repeated crash loops on restart-and-reprocess).

### Likelihood Explanation
The trigger for the crash requires: (1) existence of at least one nonserial (content_hash-only) unit stored in the DB as `sequence='good'` and stable — which the protocol explicitly supports and validates as an allowed unit shape; and (2) an AA definition (which any unprivileged user can post, or an existing one an attacker can trigger) that references such a unit's hash via `unit[...]`. Both conditions are achievable by an ordinary, unprivileged AA author/trigger sender without any special node/hub/peer privileges, matching the allowed threat model (AA author/trigger sender). The main uncertainty is how frequently content_hash-stripped units exist/are known in practice (they arise from archiving/pruning of nonserial content), but their existence is a supported, intentional protocol feature, not an edge case requiring malicious peers.

### Recommendation
In `formula/evaluation.js`'s `unit[]` handler (`case 'unit':`, `ifFound` callback), guard the `messages` iteration:
```js
if (Array.isArray(objUnit.messages))
    for (let m of objUnit.messages)
        if (m.app === "temp_data")
            delete m.payload.data;
```
More generally, audit all formula/AA code paths that fetch and iterate `objUnit.messages` (and other unit fields not guaranteed to exist for nonserial/content_hash units) for missing-field guards, and wrap any remaining direct field dereferences of fetched historical units in defensive checks, consistent with how other risky operations in the same function are already wrapped in try/catch.

### Proof of Concept
1. Identify or produce a stable, `sequence='good'` nonserial unit `U` on the DAG that was validated via the "content_hash" branch of `validate()` in `validation.js` (i.e., stored with `content_hash` and without a `messages` array).
2. Post/trigger an AA whose oscript contains a message such as:
   ```
   { app: 'data', payload: { x: `{unit['<hash of U>'].unit}` } }
   ```
3. When any full node processes the AA trigger and evaluates this formula, `formula/evaluation.js` fetches `U` via `storage.readJoint`, reaches `for (let m of objUnit.messages)` with `objUnit.messages === undefined`, and throws an uncaught `TypeError`, which propagates to `network.js`'s `process.on('uncaughtException', ...)` handler and crashes the node process.
