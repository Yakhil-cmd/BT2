### Title
Webhook signature check binds the wrong entity, and `StatusHandler` writes cross-repository commit status data unscoped by `repository`/`organization` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using an attacker-supplied payload field (`repository.owner.login`/`organization.login`), and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that selected organization has no `webhook_secret` configured. Once past that gate, `StatusHandler#process` mutates commit status state by matching **only** on the payload's `sha`, with no check that the `sha` belongs to the same repository/organization that was used to satisfy the signature check. This breaks the equality "organization that authenticated the webhook == repository/stack whose data is written," allowing status data for any commit hosted on the shared Shipit instance to be forged by referencing an onboarded organization that has no webhook secret set.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App purely from attacker-controlled payload fields: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` returns `true` unconditionally when the resolved organization's `webhook_secret` is blank — a documented, optional configuration value: [3](#0-2) [4](#0-3) 

Config examples in this codebase show `webhook_secret` deliberately left `nil` by default: [5](#0-4) 

So any attacker who knows (or can guess/enumerate) the login of an organization onboarded to this Shipit instance that has no `webhook_secret` set can submit an entirely unsigned/arbitrarily-signed POST to `/webhooks` by simply setting `repository.owner.login` (or `organization.login`) to that org's name — bypassing signature verification with no secret knowledge at all.

Once past `verify_signature`, most handlers scope their effect to the payload's own `repository.full_name`: [6](#0-5) 

But `StatusHandler#process` ignores `repository` entirely and only matches on `sha` against every `Commit` in the entire multi-tenant Shipit database: [7](#0-6) 

Because git commit SHAs are public (visible via GitHub, CI logs, or the Shipit UI/API for any stack), an attacker can target a commit belonging to a completely different, victim organization/repository and inject a forged `state`/`context`/`target_url`/`description` as a legitimate-looking CommitStatus via `commit.create_status_from_github!(params)`.

### Impact Explanation
The binding broken is: **organization that authenticated the webhook (any onboarded org lacking a webhook secret) ≠ repository/stack whose commit status is written (any other org's commit, chosen solely by SHA)**. CommitStatus data drives Shipit's deploy-readiness/required-status-check gating for commits; injecting a forged "success" status on a victim stack's commit can make an otherwise-blocked commit appear deployable to a legitimate operator, leading to an unauthorized deploy of code that never actually passed its real checks. This matches the accepted Critical impact category "unauthorized deploy."

### Likelihood Explanation
Exploitation requires no privileged credentials, no `ApiClient` token, no session, and — for at least one onboarded organization with a blank `webhook_secret` (an explicitly supported/optional configuration in this engine) — no secret knowledge whatsoever. The only information needed is the name of such an organization and a target commit SHA, both of which are typically public. This is directly reachable by any unauthenticated network attacker who can reach the `/webhooks` endpoint.

### Recommendation
1. Never let a missing `webhook_secret` silently authorize a webhook: `verify_webhook_signature` should fail closed when no secret is configured for the resolved organization (or require a secret to be mandatory in the engine).
2. Do not let attacker-controlled payload fields (`repository.owner.login`/`organization.login`) alone select the trust boundary; corroborate the resolved organization against the actual repository the event claims to modify before dispatching.
3. Fix `StatusHandler#process` to scope commit lookups to the repository present in (and cryptographically bound to) the webhook payload, consistent with `Handler#stacks`/`repository_name`, rather than matching globally by `sha`.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `OrgA` (attacker's own, onboarded with `webhook_secret: nil`, per the documented optional setting) and `OrgB` (victim, with its own secret and stacks).
2. Attacker finds a real commit `sha` belonging to a `OrgB` stack (visible on GitHub or Shipit's UI).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, an arbitrary/absent `X-Hub-Signature`, and body:
```json
{
  "sha": "<OrgB victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/anything" }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the signature header — [8](#0-7) .
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against the victim's commit (no repository check) and writes the forged "success" status onto it — [7](#0-6) .

Note: I could not fully trace, within the available iterations, the exact downstream logic in `Status::Group`/`Stack`/`MergeRequest` that consumes `CommitStatus` to gate deploy/merge eligibility (files were located but not read in full), so the precise UI/API path from "forged status" to "operator clicks Deploy" is inferred from the model names and file structure rather than fully verified line-by-line.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
