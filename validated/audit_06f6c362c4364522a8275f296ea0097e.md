### Title
Unbounded in-memory buffering of `git` subprocess stdout/stderr enables memory-exhaustion DoS from attacker-controlled repo content - (File: pkg/cmd/cmd.go)

### Summary
The Trail of Bits finding describes a DoS where a low-level Solidity call is allowed to return unbounded data, causing the caller to pay unbounded gas/memory costs and never reach the state update that would prevent retries. The closest reachable analog in git-sync is `runWithStdin` in `pkg/cmd/cmd.go`, which captures the full stdout and stderr of every `git` subprocess into unbounded `bytes.Buffer` objects with no size cap, and this function backs essentially all `git` invocations driven by content that originates from the remote repository an attacker can push to.

### Finding Description
`runWithStdin` allocates `outbuf`/`errbuf` as `bytes.NewBuffer(nil)` and attaches them directly as `cmd.Stdout`/`cmd.Stderr` for every invocation of the `git` binary, with no limit on how much data is read into memory: [1](#0-0) 

This helper is the single choke point used by `repoSync.Run` / `repoSync.RunWithStdin`, which in turn drive dozens of git operations throughout `main.go` (`fetch`, `rev-parse`, `fsck`, `log`, `show`, worktree operations, etc.), all executed against the attacker-controllable remote repository content pointed to by `--repo`/`--ref`: [2](#0-1) 

Because these commands operate on refs, commit metadata, tags, and object content that come from the remote repository, an attacker who controls (or can push to) the synced repository can craft objects that cause `git` to emit very large stdout/stderr streams (e.g., pathological commit messages, tag annotations, verbose/error output triggered by malformed refs or objects, or fsck warnings enumerating many objects). Unlike the Solidity bug, there is no protocol-level cap analogous to fixing return data to 32 bytes — the buffers grow to whatever size `git` writes.

### Impact Explanation
If a git-sync sidecar processes a maliciously crafted repository, each sync attempt (`SyncRepo`, called in the main loop every `--period`) can be made to allocate large amounts of memory for command output that is otherwise only used for logging/error messages (`stdout`/`stderr` are trimmed and returned but not size-limited) as seen in the sync loop: [3](#0-2)  Repeated retries (git-sync retries on failure per `--max-failures`/`--period`) mean the buffering cost is paid on every attempt, similar to the Solidity report's concern that unsuccessful forwarding attempts are retried indefinitely, each incurring resource cost. This can degrade or crash the sidecar process (denial of service), and because `git-sync` typically runs as an unprivileged sidecar with a bounded memory limit in Kubernetes, an OOM here directly stops synchronization — a persistent sync denial.

### Likelihood Explanation
Reaching this requires only that the attacker be able to influence content in the repository git-sync is configured to sync (an attacker-pushed commit/ref/tag to a repo git-sync consumes) — no privileged operator, leaked key, or malicious node is required, consistent with the "attacker-pushed commit/ref" reachable-analog criteria. The likelihood of triggering large `git` output specifically (rather than just large objects, which `--depth`/`--filter` already mitigate for object transfer) is lower than the original report's trivial "return 10MB" call, since it depends on which git subcommands are invoked and how verbose their output can be made (e.g., `fsck` without `--verbose` is already used to limit this in `sanityCheckRepo`, see below), so likelihood is moderate rather than high.

### Recommendation
- Short term: Wrap `cmd.Stdout`/`cmd.Stderr` in a size-limited writer (e.g., `io.LimitReader`-backed buffer or a bounded ring buffer) in `runWithStdin` in `pkg/cmd/cmd.go`, truncating captured output past a fixed cap (e.g., 1–4 MB) before use in logs/errors.
- Long term: Audit every git subcommand invoked via `repoSync.Run`/`RunWithStdin` in `main.go` for flags that bound verbosity (as already partially done via `fsck --no-progress --connectivity-only`, see [4](#0-3) ), and document/enforce a policy that command output consumed by git-sync must never scale with attacker-controlled repository content.

### Proof of Concept
Not independently verifiable without running git-sync against a crafted repository (e.g., a repo with a tag/commit whose annotation/message is many megabytes, or a corrupt object designed to make `git fsck` emit large connectivity-warning output). The code path is confirmed statically: `runWithStdin` unconditionally buffers all stdout/stderr with no cap [5](#0-4) , and this path is invoked from `repoSync.SyncRepo`'s fetch/rev-parse sequence on every sync cycle against remote-controlled refs [6](#0-5) .
