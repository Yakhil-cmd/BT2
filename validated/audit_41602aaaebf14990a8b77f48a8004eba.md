### Title
Premature exposure of unstabilized data feed values via `light/get_data_feed` allows front-running of AA logic - (File: `network.js`, `data_feeds.js`)

### Summary
The BigBlueButton CVE exposed live/unstable state information about an in-progress event to anyone who merely knew a public identifier (the meeting ID), before the data was meant to be visible to that party. The closest reachable analog in ocore is the `light/get_data_feed` network request, which lets **any unprivileged peer** — not just parties to an AA that depends on the feed — read the value of a data feed **before it is stable**, by passing `unstable_opts: 'all_unstable'` all the way into `dataFeeds.readDataFeedValueByParams`.

### Finding Description
`network.js` handles the request: [1](#0-0) 
It calls `dataFeeds.readDataFeedValueByParams(params, params.max_mci || 1e15, 'all_unstable', ...)`, hard-coding `unstable_opts` to `'all_unstable'`, which is the mode that also inspects unconfirmed messages from units that are not yet AA-only: [2](#0-1) 
Because `bIncludeAllUnstable` is set, `readDataFeedValue` scans `storage.assocUnstableMessages` for **any** unstable unit (`!objUnit.bAA && !bIncludeAllUnstable` check is bypassed) whose author matches the requested oracle address, and returns its `data_feed` payload value — with no requirement that the caller be a party to the AA/trigger that consumes the feed, nor even that the message has reached finality.

This mirrors the BBB flaw structurally: a caller who knows only a public identifier (the oracle address + feed name, analogous to the meeting ID) can pull internal, not-yet-finalized state (analogous to the video stream's live timestamp/play-pause state) that should only become authoritative/visible once the underlying event is confirmed.

### Impact Explanation
An attacker (any light or full node peer, unprivileged) can observe an oracle's data-feed value the instant it is broadcast on the network but before it is included in the stable main chain, and before any AA that consumes it has actually processed it. Because AA trigger evaluation (`formula/evaluation.js` `getDataFeed`) is deterministic based on the same unstable data at MCI-resolution time, an attacker who queries `light/get_data_feed` with `all_unstable` gains an information/timing advantage over AA trigger senders who play fair and wait for stabilization: they can front-run trades, arbitrage, oracle-dependent AAs (e.g., price/oracle-consuming contracts), submitting triggers to spend or drain AA funds based on knowledge that isn't officially final and could later be reorganized (unstable units can still change sequence to `final-bad`/be reordered before stabilizing). This creates a fund-loss/unfair-advantage vector for any user or contract relying on the oracle feed being confidential/unrevealed until stabilization.

### Likelihood Explanation
Likelihood is high: `light/get_data_feed` is a normal, always-available light-client RPC command (no authentication, no relationship check to the oracle or any AA) reachable by any unprivileged peer connecting to a full node, exactly matching the class of "unauthenticated but ID-gated" data exposure in the original CVE.

### Recommendation
Restrict `light/get_data_feed` (and the underlying `readDataFeedValueByParams`/`readDataFeedValue` calls it triggers) from serving `unstable_opts:'all_unstable'` to arbitrary requesters. Either:
1. Only allow `'all_unstable'` mode for requests originating from local AA evaluation (internal calls), not external light/network requests, or
2. Require the requester to prove a legitimate relationship to the feed consumer (e.g., only return stabilized values, defaulting `unstable_opts` to `undefined`/false for the network-facing handler), matching the BBB fix pattern of "send the data only to users who are legitimately part of the transaction."

### Proof of Concept
1. Attacker connects as a light client to a full node.
2. Attacker sends `{"command":"light/get_data_feed","params":{"oracles":["ORACLE_ADDRESS"],"feed_name":"PRICE","max_mci":1e15}}`.
3. Server executes `dataFeeds.readDataFeedValueByParams(params, params.max_mci||1e15,'all_unstable', cb)` [3](#0-2) , which walks `storage.assocUnstableMessages` (unconfirmed units) and returns the freshest `data_feed` payload value even though it has not stabilized [4](#0-3) .
4. Attacker now knows the oracle's newest value ahead of AA stabilization and submits a trigger to an oracle-dependent AA to capture value before other, honest participants who wait for stabilization.
