This confirms Shipit supports multi-organization GitHub App configuration, where `Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization key in `secrets.github` [1](#0-0) . This is a valid analog to the report's fork-version binding mismatch: the field used to authenticate (verify) a webhook is not the field used to determine which resource is acted upon.

### Title
Webhook signature is verified against `repository.owner.login` while the repository acted upon is taken from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using the organization login taken from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`), but the handlers that actually act on the payload (creating stacks, syncing repos, archiving/unarchiving review stacks, etc.) resolve the target repository from a completely different, independently attacker-controlled field: `repository.full_name`.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`Shipit.github(organization:)` looks up a per-organization webhook secret from `secrets.github[organization]` when the app is configured for multiple organizations (`github_app_config`) [1](#0-0) .

Once the HMAC check passes, `WebhooksController#create` dispatches the *entire raw payload* to handlers [4](#0-3) . Every handler (`PushHandler`, `Handler#stacks`, all `PullRequest::*Handler`s) resolves the repository to operate on via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [5](#0-4) [6](#0-5) [7](#0-6) .

Because `repository.owner.login` and `repository.full_name` are two independent, unauthenticated JSON fields in the same request body, an attacker who controls (or has push/webhook access to) any organization/repository configured with its own GitHub App entry in Shipit's multi-org config can craft a payload where:
- `repository.owner.login` = the attacker's own organization (whose webhook secret the attacker legitimately knows, since GitHub signs webhooks for repos the attacker administers), used only to pass `verify_signature`.
- `repository.full_name` = a *different* organization/repository that Shipit also tracks, used by the handler to pick the actual `Stack`/`Repository` record to mutate.

This breaks the intended binding "the organization whose secret authenticated the request == the repository the request is permitted to act on." The signature only proves the sender knows *some* configured organization's secret, not that they are authorized for the repository the payload claims to mutate.

### Impact Explanation
This escalates into unauthorized cross-repository actions on stacks Shipit manages for organizations the attacker does not control: forcing `stack.sync_github` (push handler), archiving/unarchiving review stacks, or triggering label-driven provisioning/deprovisioning of review stacks for a victim organization's repository, purely by signing the crafted payload with a secret belonging to any other organization onboarded to the same Shipit instance. This matches the "authorized organization vs. repository actually written" analog class and can affect deploy/rollback-adjacent state (stack sync, review-stack provisioning) without the attacker ever having credentials for the victim org/repo.

### Likelihood Explanation
Medium-High in any Shipit deployment that onboards more than one GitHub organization with the multi-org `secrets.github` schema (explicitly supported by `github_app_config`/`github_organizations`) [8](#0-7) . Any tenant that can generate a genuinely GitHub-signed webhook for their own repository (e.g., by pushing to their own repo, opening a PR, etc., or simply computing the HMAC if they know their own `webhook_secret`) can mutate the `repository` JSON block to point at another tenant's `full_name` before it reaches Shipit's endpoint, since GitHub's HMAC only covers the delivered body but Shipit re-derives the secret from a body field disjoint from the field handlers trust for authorization scoping.

### Recommendation
Verify the signature using the same repository identity (`full_name`/repository record) that handlers subsequently use to select the target `Stack`/`Repository`, or explicitly validate that `repository.owner.login` used for secret lookup matches the owner segment of `repository.full_name` before dispatching to handlers. Alternatively, resolve the webhook secret from the `Repository` record already stored for the `full_name` in the payload rather than from attacker-suppliable owner fields.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` containing entries for `org-a` (attacker-controlled, webhook secret known/derivable by attacker) and `org-b` (victim, tracked repository `org-b/victim-repo` in Shipit).
2. Craft a `push` (or `pull_request`) webhook JSON body with:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/victim-repo"`
3. Compute `X-Hub-Signature` using `org-a`'s webhook secret over the raw body.
4. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "org-a")` and succeeds since the signature matches `org-a`'s secret [2](#0-1) .
5. `PushHandler#process` (or PR handlers) then resolves `Repository.from_github_repo_name("org-b/victim-repo")` via `Handler#repository_name` and acts on `org-b`'s stacks [5](#0-4) , triggering a sync/archive/unarchive on a repository the attacker never proved control over.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
