### Title
Uncaught exception (node crash) from unvalidated c-hash buffer length in address checksum verification - (File: `chash.js`)

### Summary
`chash.isChashValid()` decodes an attacker-supplied string with `base32.decode()`/`Buffer.from(..., 'base64')` and then feeds the resulting buffer into `buffer2bin()` → `separateIntoCleanDataAndChecksum()` without first re-validating that the decoded buffer actually has the expected bit-length (160 or 288 bits). `separateIntoCleanDataAndChecksum()` throws a plain `Error` ("bad length=...") whenever the buffer length is anything other than 160/288, and that call is made **outside** the `try/catch` that only wraps the decode step. This mirrors the Wireshark ULPDU bug class: a length value derived from untrusted input is trusted and used to drive further processing without being validated first, leading to an unhandled crash.

### Finding Description
`chash.isChashValid()` in `chash.js` decodes an encoded chash string with either `base32.decode()` (32-char inputs) or `Buffer.from(encoded, 'base64')` (48-char inputs) inside a `try { } catch(e) { return false; }` block: [1](#0-0) 

However, `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)` are called **after** that try/catch block, unprotected: [2](#0-1) 

`separateIntoCleanDataAndChecksum()` explicitly `throw`s when the bit-length of the decoded buffer is not exactly 160 or 288: [3](#0-2) 

Node's `Buffer.from(str, 'base64')` is lenient: it silently ignores characters that are not valid base64 and simply produces a shorter (or otherwise different-length) buffer instead of throwing, so a 48-character string containing invalid base64 characters passes the decode step without error but yields a buffer whose length is not the expected 36 bytes (288 bits). This unvalidated length then reaches `separateIntoCleanDataAndChecksum()`, which throws — and that throw is unguarded, propagating up through `isChashValid()`.

`isChashValid()` is reached through `ValidationUtils.isValidChash(str, len)`: [4](#0-3) 

`isValidAddress()` (used pervasively for payment/output/AA/address-definition addresses) pre-filters the input with a strict base32 regex (`/^[A-Z2-7]{32}$/`) before calling `isValidChash`, which protects the 32-char/base32 path: [5](#0-4) 

But `isValidAddressAnyCase()` calls `isValidChash(address, 32)` directly, **without** that regex pre-filter: [6](#0-5) 

Since `isChashValid` handles both the 32-char (base32→160-bit) and 48-char (base64→288-bit) code paths, and `isValidAddressAnyCase`/`isValidChash` do not restrict the caller to a fixed length, any code path that calls `isValidChash`/`isChashValid` with a 48-character attacker-controlled string bypasses the safe base32 regex gate and can trigger the uncaught `Error` deep inside `chash.js`.

### Impact Explanation
An uncaught exception thrown during unit/message validation (or any other synchronous call path that reaches `isChashValid` with unsanitized data) will propagate as an unhandled exception. In a Node.js process this either crashes the process outright (if not caught by a top-level handler) or aborts whatever operation was in progress in an inconsistent way. Because address/chash validation is invoked while processing units, definitions, and messages submitted by ordinary (unprivileged) unit posters, a specially crafted string can be used to force this code path and crash node processing — a network-wide denial-of-service condition analogous to the Wireshark dissector crash triggered by an unvalidated length field.

### Likelihood Explanation
The likelihood depends on whether any reachable validation call passes attacker-controlled 48-character strings into `isChashValid`/`isValidChash`/`isValidAddressAnyCase` without the protective regex used by `isValidAddress`. I found exactly one call site of `isValidAddressAnyCase` in `validation.js` (in addition to its two definitions/uses in `validation_utils.js`), but I was not able to retrieve its surrounding context before running out of tool calls, so I cannot confirm with certainty that the specific field validated there is fully attacker-controlled and unauthenticated at that point. This is the key uncertainty in this analog: the vulnerable low-level function (`chash.js`'s unguarded throw) is confirmed, but the exact unprivileged-reachable call site that feeds it a 48-character non-base64-clean string needs to be verified by reading `validation.js` around the `isValidAddressAnyCase` usage.

### Recommendation
- Wrap the entire body of `isChashValid()` (including `buffer2bin()` and `separateIntoCleanDataAndChecksum()`) in the existing `try/catch`, returning `false` on any exception, rather than only wrapping the decode step.
- Additionally, explicitly validate the decoded buffer length immediately after decoding (`chash.length === 20` for the 32-char/base32 case, `chash.length === 36` for the 48-char/base64 case) and return `false` early rather than relying on `separateIntoCleanDataAndChecksum` to throw.
- Audit all call sites of `isValidAddressAnyCase`/`isValidChash` (especially the one in `validation.js`) to confirm whether attacker-controlled data can reach it with a 48-character string, and apply the same strict character-set pre-filtering that `isValidAddress` uses if so.

### Proof of Concept
```js
const chash = require('./chash.js');

// 48-character string, valid length for isChashValid's "288-bit" branch,
// but containing characters that are NOT valid base64 (spaces are stripped/ignored
// by Buffer.from with 'base64' encoding), producing a decoded buffer whose
// bit-length is neither 160 nor 288.
const malformed = ' '.repeat(48); // 48 chars, decodes to a buffer far shorter than 36 bytes

try {
    chash.isChashValid(malformed);
    console.log('no crash');
} catch (e) {
    console.log('uncaught exception (crash):', e.message);
}
```
Running this reproduces an uncaught `Error("bad length=...")` thrown from `separateIntoCleanDataAndChecksum`, outside the `try/catch` in `isChashValid`, demonstrating the unguarded crash path described above.

function isChashValid(encoded){

	if (encoded_len !== 32 && encoded_len !== 48) // 160/5 = 32, 288/6 = 48

		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
