### Title
Stale address definition remains valid for signing after definition change is posted but not yet stable - (File: `validation.js`)

### Summary
Eclipse Mosquitto's CVE-2021-34434 is a case where revoking a client's permission (unsubscribing an ACL) does not retroactively invalidate the subscription state that was already granted, so the previously-authorized action keeps working until the client reconnects. The ocore analog is `address_definition_change`: an address owner can replace the definition (effectively "the permission/authentifier set") of an address, but the code explicitly allows units still bearing the *old* definition to be accepted as long as the new change unit has not yet become stable, i.e. the old authorization is not synchronously revoked.

### Finding Description
Address definitions in ocore serve the role of "who can spend/sign for this address" (equivalent to an ACL). Changing this set is done via the `address_definition_change` message, and the resulting new `definition_chash` only becomes authoritative for a unit once the change is `is_stable=1` and precedes `last_ball_mci` [1](#0-0) .

Because unit posting/validation happens before this stabilization boundary, `validateAuthor()`'s `handleDuplicateAddressDefinition()` explicitly tolerates a unit that reuses the **old** definition even though it hashes the same as what is *currently* stored (which can still be the old value if the change hasn't stabilized), deliberately deferring resolution to consensus instead of rejecting it outright: [2](#0-1) 

The surrounding code contains an explicit acknowledgment of this exact class of issue — a definition change ("revocation" of the old authorization) can be raced by a unit signed under the old, soon-to-be-revoked definition, because "the new definition will not be active yet": [3](#0-2) 

`validateDefinition()` in `definition.js` independently documents the same underlying hazard for nested/referenced addresses — that redefinition of an inner address must be re-evaluated every single time specifically because a definition change may not be visible/active yet at validation time, and that this can even alter complexity or reachability of authentifier paths: [4](#0-3) 

`checkSerialAddressUse()` picks `validateDefinition` vs. `checkNoPendingChangeOfDefinitionChash` based on `last_ball_mci` and confirms that non-stable, conflicting units are only demoted to `temp-bad`/`final-bad` after the fact, not prevented from being authored/broadcast with the stale definition in the first place: [5](#0-4) 

### Impact Explanation
If an address owner revokes a cosigner or authentifier path by posting `address_definition_change` (e.g., removing a compromised device/key from a shared or multi-sig address), a unit signed with the *old* definition can still be posted and validated as "good" during the window before the change unit stabilizes and passes `last_ball_mci`. This allows an attacker who possesses the old (supposedly revoked) signing material to spend funds from the address using authorization that the owner believed had already been withdrawn — a concrete unauthorized-spending / fund-loss scenario, directly analogous to Mosquitto honoring a subscription that should have been revoked.

### Likelihood Explanation
The race window is bounded by the time for the `address_definition_change` unit to become stable and cross `last_ball_mci`, which under normal DAG conditions is not instantaneous. An attacker who already holds the old signing keys (the realistic threat: a removed cosigner, a previously-shared shared_address key, or a device believed revoked) only needs to broadcast a conflicting unit signed with the old definition quickly after learning of (or anticipating) the revocation — no special network position or additional exploit primitive is required, matching the CVSS 5.3 / Medium profile of the original advisory (network-reachable, no privileges, low complexity).

### Recommendation
- When an `address_definition_change` for an address is detected as pending (posted but not yet stable), reject or hold as non-serial/pending any new unit from that address that is signed with the definition being replaced, rather than allowing it to compete purely through the standard doublespend/serial-resolution path.
- Track "definition change is pending" as an explicit blocking condition in `validateAuthor`/`checkSerialAddressUse`, closing the gap flagged by the existing TODO at `validation.js:1490-1491` where an attacker can "quickly send a new ball with the old definition."

### Proof of Concept
1. Address `A` is defined with a 2-of-2 multisig definition including keys `K1` and `K2` (held by owner and cosigner respectively).
2. Owner decides to revoke `K2` and posts `address_definition_change` changing `A`'s definition to a new one using only `K1` (or `K1`+`K3`).
3. Before this change unit becomes stable and crosses `last_ball_mci`, the holder of `K2` (now supposed to be revoked) crafts and broadcasts a spending unit from `A` signed with the old 2-of-2 definition (`K1`+`K2`, or if `K1` cooperated earlier/was compromised together, just using the old definition's authentifier paths).
4. Because `readDefinitionByAddress` for `last_ball_mci` still resolves to the old `definition_chash` (change not yet stable), and `handleDuplicateAddressDefinition` accepts a unit whose declared definition matches what's currently stored, the spending unit is validated as `good` and can be written by `writer.saveJoint`, moving funds under authorization the owner intended to have already withdrawn [6](#0-5) .
