### Title
Unsanitized PR-label-derived environment variables (e.g. `GIT_PROXY_COMMAND`) reach `git` subprocess env in `StackCommands#fetch`/`#git_clone` - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/stack_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the environment hash with `"true"` as the value and applies no allowlist, unlike task/deploy variables which go through `EnvironmentVariables#permit`. That unfiltered hash flows through `StackCommands#env` into every `git` invocation in `StackCommands#fetch`/`#fetch_commit`/`#git_clone`, and `Command#unbundled_env` merges it straight into the subprocess environment passed to `PTY.spawn` with no key filtering.

### Finding Description
The broken binding: `Command#env` passed to `PTY.spawn` should equal `EnvironmentVariables.with(source_env).permit(allowlist)`, but for `ReviewStack`-backed commands it instead equals `Stack#env.merge(pull_request.labels.map(&:upcase) => "true")` with **no** call to `EnvironmentVariables#permit` anywhere in the chain.

Trace:
- `ReviewStack#env` overrides `Stack#env` and merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the base env, with no key allowlist. [1](#0-0) 
- `pull_request.labels` is written verbatim from the webhook body by `LabelCapturingHandler#capture_labels`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` — no name filtering/allowlisting. [2](#0-1) 
- `StackCommands#env` merges `@stack.env` (i.e., the `ReviewStack#env` above) and passes it as `env:` to every `git` call in `#fetch`, `#fetch_commit`, and `#git_clone`. [3](#0-2) [4](#0-3) 
- `Command#unbundled_env` merges `@env.stringify_keys` directly into `BASE_ENV`/`PATH`, with no allowlist, right before `PTY.spawn`. [5](#0-4) [6](#0-5) 

By contrast, user-supplied deploy/task variables (via API params) are filtered through `EnvironmentVariables#permit`/`filter_task_envs`/`filter_deploy_envs` before being persisted as `@task.env` (`app/models/shipit/deploy_spec.rb:174-180`, `app/models/shipit/task_definition.rb:63-65`), and `EnvironmentVariables#permit` proves that pattern is the intended guard. `Stack#env`/`ReviewStack#env`, however, is merged directly into every command's env with no equivalent call, and no test or code confirms an allowlist is applied. [7](#0-6) [8](#0-7) 

Exploit flow: attacker (per the audit's defined threat model) labels their own PR against a repository configured with `provisioning_behavior: allow_all` using a label literally named `GIT_PROXY_COMMAND` (case-insensitive, since it is upcased), with the label's value effectively becoming the shell command git will execute for its transport (`.upcase` produces the key; the value is hardcoded `"true"`, so for `GIT_PROXY_COMMAND` specifically the payload string is fixed — but naming other git-honored variables like `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`, etc. as *label names* only injects the key with value `"true"`, which is a real constraint — see caveat below). GitHub sends a signed `labeled` webhook, `LabelCapturingHandler#capture_labels` persists the raw label name, and the next `PerformTaskJob`/deploy triggers `StackCommands#fetch`/`#git_clone`, spawning `git` with the attacker's env var present.

Existing guards checked and found insufficient/inapplicable to this path: `WebhooksController#verify_signature` validates the webhook HMAC signature via `Shipit.github(organization:).verify_webhook_signature`, which blocks *forged* webhooks but does not filter or sanitize the *content* of a genuine, correctly-signed `labeled` event — it never inspects label names. [9](#0-8) 
`EnvironmentVariables#permit` exists and is used for `deploy`/`task`/`rollback` variables, but is never invoked for `Stack#env`/`ReviewStack#env`, so it does not guard this path. [10](#0-9) 

**Caveat on exact severity of `GIT_PROXY_COMMAND`**: because `ReviewStack#env` always sets the label-derived value to the fixed string `"true"` (not an attacker-chosen command string), naming the label `GIT_PROXY_COMMAND` only sets `GIT_PROXY_COMMAND=true` in the subprocess env — this does not by itself achieve arbitrary command execution unless git treats `"true"` as an executable command name for `GIT_PROXY_COMMAND` (git would try to invoke a program literally named `true`, which exists on POSIX systems as a no-op binary, so this specific variable/value combination alone would not typically yield RCE beyond invoking `/usr/bin/true`, and only for `git://` protocol transports, not the `https`/`ssh` transports Shipit normally uses for GitHub). The broader/more exploitable vector is the unrestricted **key** injection (no allowlist on which environment variable names can be set from labels at all) which enables far more dangerous git-honored variables to be set to `"true"` (e.g., disabling checks) or, more importantly, demonstrates the systemic absence of any allowlist on `ReviewStack#env`, which is the actual root cause the question targets.

### Impact Explanation
Any environment variable name (uppercased) can be injected into every `git` subprocess spawned for a given `ReviewStack`'s `fetch`/`git_clone`/`checkout`/`clone` operations, with the value fixed to `"true"`. This affects only that stack's own git operations (the env is per-`Command` instance, scoped to `@stack`), so it is not a cross-tenant contamination by default, but it does demonstrate a real, unauthenticated content-injection path into a privileged subprocess's environment with zero allowlist enforcement — matching the "command running that should not" category described in scope, even though the specific `GIT_PROXY_COMMAND=true` payload does not itself achieve arbitrary code execution.

### Likelihood Explanation
Requires: (1) the target repository configured with `provisioning_behavior: allow_all` (or another behavior that provisions the stack without a maintainer gate) for Review Stacks; (2) the attacker's PR to receive a `labeled` webhook event genuinely signed by GitHub (the webhook signature check is a real, effective barrier against forged payloads); (3) on real GitHub, applying a label to a PR requires "triage" or higher repository permission — an anonymous outside contributor cannot normally label their own PR unless the repo maintainer has granted broader label permissions to non-collaborators, which is not GitHub's default. This external precondition (label-write access) is a genuine privilege boundary not present in Shipit's own code, and it substantially reduces real-world feasibility versus the "fully unprivileged" framing in the question.

### Recommendation
Apply the same `EnvironmentVariables#permit` allowlist mechanism (or an explicit denylist of `GIT_*`/known-dangerous variable names) to `Stack#env`/`ReviewStack#env` before merging into `StackCommands#env`/`Command#env`, so PR-label-derived keys cannot introduce arbitrary environment variable names into any `git` subprocess.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or new test file)
test "#env does not allow labels to set arbitrary git-sensitive env keys" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.update!(labels: ["git_proxy_command"])

  env = stack.env
  # Demonstrates the unrestricted key injection into the env hash
  # that later reaches Command#unbundled_env / PTY.spawn via
  # StackCommands#fetch / #git_clone with no allowlist applied.
  assert env.key?("GIT_PROXY_COMMAND"), "label name became an unfiltered env key"
end
```
Because the label value is hardcoded to `"true"` in `ReviewStack#env`, a stronger PoC to demonstrate actual command execution is not possible purely from label content; the test above proves the missing-allowlist binding (`stack.env.keys` ⊄ any permitted allowlist), which is the exact invariant the question asks to validate.
