### Title
Unfunded `recapitalize` refunds tokens the pool never received and leaves the cash book overstating custody - (File: contracts/pool/src/lib.rs)

### Summary
The upstream bug class is a missing cleanup/verification on a failed resource-registration path: `st7701` registered the panel, `mipi_dsi_attach()` failed, and the code never called `drm_panel_remove()`, permanently leaking the resource. The analog in XOXNO Lending is `LiquidityPool::recapitalize`: the pool registers a cash-book credit and pays a "refund of the excess" back to `payer` using only the internal book value, without ever measuring that `payer` actually transferred tokens in. When the transfer-in is absent or short (a failed/partial "attachment" of funds), the pool still performs the credit and refund instead of reverting the registration, permanently draining real custody and leaving the cash book overstated.

### Finding Description
`recapitalize` is documented in `contracts/pool/src/lib.rs:182-194` as: "Credits cash up to the market's backing shortfall (`guards::backing_shortfall`) and transfers the excess back to `payer`. The controller transfers `amount` in before this call." The credit decision and the refund are computed from the cash book alone; unlike the flash path (`lib.rs:33-36`, which explicitly "checks the token balance after payout, after the callback and after repayment"), recapitalize performs no balance-delta measurement of what it received.

The crate's own test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408-3483`) demonstrates the concrete end state: a `recapitalize` call where the payer delivered nothing transfers the pool's entire real token custody to `payer` as "excess," while the cash book still reports the suppliers' deposits. Subsequent withdrawals pass `require_reserves`/`PoolInsolvent` guards because those guards read the book, then fail inside the SAC transfer (`BalanceError = 10`) — the book claims funds that no longer exist.

From the unprivileged side, the in-scope `controller::recapitalize` entrypoint lets any address act as `payer`. The controller trusting the pool's refund amount (rather than the pool measuring actual receipt) means: (a) any pre-existing book-vs-custody divergence is amplified — the refund is sized against a shortfall the book understates; (b) each call compounds the divergence because a partially-funded call still credits up to the book's shortfall figure. The "registered but never attached" resource is the cash credit itself: it persists in state exactly like the orphaned `drm_panel`.

### Impact Explanation
Protocol insolvency and permanent freezing of user funds. Once real custody is paid out while the cash book still counts it, every liquidity guard (`InsufficientLiquidity`, `PoolInsolvent`, utilization caps) evaluates against phantom cash. Suppliers' and repayers' withdrawals/liquidation payouts pass all pool-side checks and then revert inside the token transfer, permanently freezing the residual deposits of honest suppliers — the test proves the book stays overstated after the failed exit (`flows.rs:3478-3482`).

### Likelihood Explanation
Reachable by a single unprivileged address through the controller's `recapitalize` entrypoint whenever the book/custody ratio permits an "excess" refund, and self-reinforcing: each short-funded call worsens the very divergence it exploits. Unlike typical leak analogs, this needs no admin key, no upgrade, and no oracle manipulation — it depends only on the pool trusting an unverified inbound transfer, which is exactly the missing-cleanup shape of the source bug.

### Recommendation
Apply measured-receipt settlement to `recapitalize` in `contracts/pool/src/ops/recapitalize.rs`: snapshot `token.balance(pool)` before crediting, re-read after the controller-side transfer leg settles (or accept the pulled amount via `transfer_from` inside the pool), and compute both the credit and the refund from the measured delta rather than `amount`. Alternatively, revert the whole call (the "remove the panel" equivalent) whenever the received delta is less than the applied credit, so a failed attach of funds leaves no registered credit behind.

### Proof of Concept
The in-repo regression test already serves as the PoC (`contracts/pool/tests/flows.rs:3408-3483`):

```rust
// contracts/pool/tests/flows.rs
token_admin.mint(&t.pool, &deposit);            // real custody: supplier deposit
t.client().supply(&t.sup(0, deposit));          // book cash == custody

// recapitalize called with custody-sized amount but NO inbound transfer
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);          // "excess" refund drained custody
assert!(t.state_snapshot().cash >= deposit);    // book still claims the funds

// supplier exit passes all pool guards, then dies inside the SAC transfer
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
// outcome is SAC BalanceError(10), not InsufficientLiquidity / PoolInsolvent
```

On mainnet this sequence runs through `controller::recapitalize(hub_asset, amount)` with the caller as `payer`: any call where the pool's shortfall calculation under-credits relative to the delivered delta produces a refund paid out of other suppliers' custody.
