### Title
Bridge Handle Functions Commit No Failure State, Enabling Permanent Asset Lock on Permanently-Failing Transfers — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`, `node/sc/vt_recovery.go`)

---

### Summary

The Kaia service-chain bridge's `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` functions perform all state updates (nonce recording, request-hash marking, event emission) **before** the actual asset transfer. If the asset transfer reverts, the entire transaction reverts atomically, leaving zero on-chain record that execution was ever attempted. The off-chain Value Transfer Recovery (`valueTransferRecovery`) uses `handleNoncesToBlockNums[nonce] > 0` as its sole "already handled" signal. Because a failed attempt leaves that mapping at `0`, the VTR treats the request as perpetually pending and retries it indefinitely. When the failure is permanent (e.g., a KLAY recipient contract that always rejects native value), the source-chain assets are burned or locked forever with no recovery path.

---

### Finding Description

**Contract-level ordering flaw**

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` executes in this order:

1. `_lowerHandleNonceCheck` — guard
2. `_voteValueTransfer` — sets `closedValueTransferVotes[nonce] = true`
3. `_setHandledRequestTxHash` — sets `handledRequestTx[txHash] = true`
4. `handleNoncesToBlockNums[nonce] = _requestedBlockNumber`
5. `_updateHandleNonce` — may advance `lowerHandleNonce`
6. `emit HandleValueTransfer`
7. `(bool ok,) = _to.call.value(_value)("")`
8. `require(ok, "handleKLAYTransfer: transfer failed")`

If step 8 fails, the EVM reverts the entire transaction, undoing steps 2–6. The same pattern exists in `handleERC20Transfer` (steps 1–6 then `mint`/`safeTransfer`) and `handleERC721Transfer` (steps 1–6 then `mintWithTokenURI`/`transferFrom`).

**Off-chain recovery cannot detect the failure**

`isHandledEvent` in `vt_recovery.go` is the only guard the VTR uses to skip already-processed requests:

```go
func isHandledEvent(to *BridgeInfo, ev IRequestValueTransferEvent) bool {
    blk, err := to.bridge.HandleNoncesToBlockNums(nil, ev.GetRequestNonce())
    if err == nil && blk > 0 {
        return true
    }
    return false
}
```

After a reverted handle transaction, `handleNoncesToBlockNums[nonce]` is `0`, so `isHandledEvent` returns `false`. The VTR's `retrievePendingEventsFrom` adds the event back to the pending list, and `recoverPendingEvents` re-queues it via `AddRequestValueTransferEvents`. `processingPendingRequestEvents` then calls `handleRequestValueTransferEvent` again, which submits another on-chain handle transaction — which reverts again.

**No expiry, no failure tombstone**

There is no timestamp, block-number deadline, or explicit "failed" flag stored for a request nonce. A request that can never succeed (e.g., KLAY sent to a contract whose fallback always reverts) will be retried on every VTR interval forever.

---

### Impact Explanation

**Permanent loss of bridged assets (primary)**

In ERC20/ERC721 mint-burn mode, the source-chain burn (`ERC20Burnable.burn` / `ERC721Burnable.burn`) executes inside `_requestERC20Transfer` / `_requestERC721Transfer` at request time. If the corresponding destination-chain mint permanently fails (e.g., the token contract is paused, upgraded, or the minter role is revoked), the tokens are burned on the source chain and never minted on the destination chain — a permanent, irrecoverable loss of bridged ERC20/ERC721 assets.

For KLAY in lock-unlock mode, the KLAY is locked in the source bridge at request time. If `_to.call.value(_value)("")` permanently fails on the destination bridge (recipient is a contract without a payable fallback), the KLAY is locked in the source bridge forever with no refund path.

**Operator gas drain (secondary)**

The VTR retries the failing request on every recovery interval, consuming operator gas indefinitely. This is analogous to the M-03 Scenario 1 gas-drain attack.

**Indistinguishable error state**

Because `closedValueTransferVotes[nonce]` is also reverted on failure, operators can re-vote on the same nonce. The contract cannot distinguish "vote pending" from "vote succeeded but transfer failed" — the same ambiguity identified in M-03.

---

### Likelihood Explanation

- **KLAY permanent failure**: Any KLAY transfer to a contract address without a `payable` fallback (common in Kaia/Ethereum). The user may not know the recipient is a contract, or the recipient may be upgraded after the request is submitted.
- **ERC20/ERC721 permanent failure**: Token contract paused, minter role revoked, or token contract upgraded to reject minting — all realistic operational events.
- **No attacker privilege required**: Any user can submit a `RequestValueTransfer` to a recipient that will permanently reject the handle. The VTR is triggered automatically by the bridge operator node.

---

### Recommendation

1. **Store a failure tombstone before the asset transfer.** Record `handleNoncesToBlockNums[nonce]` and `handledRequestTx[txHash]` in a separate, non-reverting step (e.g., using a try/catch pattern in Solidity ≥0.6, or restructuring so the state write is in a sub-call that cannot be reverted by the outer transfer failure). Alternatively, record a `failedHandleNonces` mapping that the VTR checks.

2. **Add an expiry / max-retry mechanism.** The VTR should track how many times a nonce has been retried and stop after a configurable limit, emitting a `HandleFailed` event so operators can take manual action.

3. **Separate voting from execution.** Commit `closedValueTransferVotes[nonce] = true` in a way that survives a transfer revert, so that re-voting is blocked and the state unambiguously reflects "execution was attempted."

4. **Provide a refund path.** Add an owner/operator function to mark a nonce as permanently failed and trigger a refund on the source chain (or unlock the locked assets).

---

### Proof of Concept

**Scenario — Permanent KLAY lock**

```solidity
// Deployed on the parent chain
contract KLAYRejector {
    // No payable fallback — rejects all KLAY transfers
    function doSomething() external {}
}
```

1. User on child chain calls `requestKLAYTransfer(address(KLAYRejector), value, "")`. KLAY is locked in the child bridge. `RequestValueTransfer` event is emitted with `requestNonce = N`.
2. Operator's `handleRequestValueTransferEvent` calls `bridge.HandleKLAYTransfer(...)` on the parent bridge.
3. Inside `handleKLAYTransfer`: steps 2–6 execute (state written), then `_to.call.value(_value)("")` returns `ok = false`, `require` reverts the transaction. All state writes are undone.
4. `handleNoncesToBlockNums[N]` = 0. `handledRequestTx[txHash]` = false.
5. VTR's `isHandledEvent` returns `false` for nonce N. VTR re-queues the event.
6. Steps 2–5 repeat on every VTR interval. The KLAY in the child bridge is permanently locked. The operator pays gas on every retry.
