### Title
`provision?` operator-precedence bug lets `prevent_with_label` PRs bypass `review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses `&&`/`||` without parentheses so that `repository.review_stacks_enabled` is only ANDed with `provisioning_behavior_allow_all?`, never with the `allow_with_label?` or `prevent_with_label?` branches. Consequently, when `review_stacks_enabled == false` and `provisioning_behavior == 'prevent_with_label'`, an attacker opening an unlabeled PR from their own fork still causes a `Shipit::ReviewStack` to be created with `branch` set to their fork's ref.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled` (an operator-configured `false`) should equal the value actually consulted by `provision?` for every provisioning-behavior branch. It does not, because Ruby's `&&` binds tighter than `||`:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

This parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. The last two disjuncts never reference `review_stacks_enabled`, so toggling it off has no effect once `provisioning_behavior` is `allow_with_label` or `prevent_with_label`.

Path: `PullRequest::OpenedHandler#process` calls `respond_to_pull_request_opened?`, which is `params.action == "opened" && provision?` [2](#0-1) . When `provision?` wrongly returns `true`, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` runs, and `create!` builds the stack from `stack_attributes`, setting `branch: params.pull_request.head.ref` directly from attacker-controlled payload data [3](#0-2) .

The attacker's request: open a PR (`action: "opened"`) against a repository where `provisioning_behavior` is `prevent_with_label`, `review_stacks_enabled` is `false`, and the PR carries no provisioning label. This is a normal `pull_request.opened` webhook that GitHub sends for any fork PR — no privileged action is required from the attacker beyond opening the PR (webhook signature verification is orthogonal; it authenticates that GitHub sent the event, not that the PR content itself is safe).

Existing guards (`verify_signature`, `ExplicitParameters` schema, model validations) do not check this logical relationship — they validate payload shape and webhook authenticity, not the intended-vs-actual `provision?` semantics. The `ReopenedHandler#unarchive?` method has the identical unparenthesized bug [4](#0-3) , compounding the issue on PR reopen events too. Notably, `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the whole condition [5](#0-4) , showing the intended pattern that `OpenedHandler`/`ReopenedHandler` fail to follow.

### Impact Explanation
A stack is created and queued for provisioning (`Shipit::ReviewStackProvisioningQueue.add(stack)`) for a repository whose operator explicitly disabled review stacks (`review_stacks_enabled = false`). Per the project's own documentation, provisioning subsequently runs deploy-spec-defined commands against the deploy host using the attacker-controlled branch/ref content from their fork. This is unauthorized stack creation and downstream unauthorized command execution against the repository owner's deploy host — matching the Critical category ("a payload for one repository mutating another's [state]" / "unauthorized deploy... via a record written for a repository that did not authenticate it"). The attack is repeatable against any repository configured with `provisioning_behavior: prevent_with_label` regardless of `review_stacks_enabled`, i.e., across all tenants using that behavior setting.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior == 'prevent_with_label'` (a supported, documented, non-default configuration) with `review_stacks_enabled == false`. No secrets, tokens, or team membership are needed — the attacker only needs to open a PR against the tracked repository (a normal, unprivileged GitHub action for public repos or forks) with no provisioning label attached (the default state of any new PR). This is trivially reproducible and requires no race condition or timing dependency, making it highly feasible wherever this configuration combination exists.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every disjunct, in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?`:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not create stacks when review_stacks_enabled is false even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,       # repository.review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []  # no provisioning label

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
  # Current buggy behavior: this assertion FAILS because a stack IS created
  # with stack.branch == payload["pull_request"]["head"]["ref"], proving
  # review_stacks_enabled(false) was never consulted for the prevent_with_label branch.
end
```
