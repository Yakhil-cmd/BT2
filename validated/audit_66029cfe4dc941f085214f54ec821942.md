### Title
Webhook signature is verified against an organization selected from an unauthenticated field, while handlers act on a different, independently-controlled repository field in the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to verify the request against using `repository_owner`, computed from the raw, unauthenticated JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`) [1](#0-0) [2](#0-1) . But every event handler independently determines *which repository/stack to mutate* from a separate field of the same attacker-supplied JSON, `repository.full_name` [3](#0-2) , or in the case of `StatusHandler`, simply the `sha` with no repository scoping at all [4](#0-3) . These two fields are never checked for consistency, and in a multi-org deployment (`Shipit.github(organization:)`, `github_app_config`) each organization can have its own, independently configured `webhook_secret`, including none at all [5](#0-4) [6](#0-5) .

### Finding Description
`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` config for whatever organization string appears in the payload, then `verify_webhook_signature` is called on that config's secret [1](#0-0) . Critically, `verify_webhook_signature` treats a missing/blank `webhook_secret` as automatically valid: `return true unless webhook_secret` [7](#0-6) . The sample multi-org secrets template explicitly shows `webhook_secret:` left blank/nil as a supported configuration per organization [6](#0-5) .

Because the JSON body is fully attacker-controlled (there is no cryptographic binding tying `repository.owner.login`/`organization.login` to `repository.full_name` within an unverified request), an attacker can craft a single payload where:
- `repository.owner.login` (or `organization.login`) = an organization configured in `secrets.yml` with a blank/nil `webhook_secret` (the "authenticated" side, trivially passes verification), while
- `repository.full_name` = a completely different, properly-secured organization/repository (the "written" side that handlers actually act on).

`verify_signature` only checks the signature against the *first* org string; it never re-derives or cross-checks `repository.full_name` against that org. Once `head(422) unless verified` passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire* raw payload — including the mismatched `repository.full_name` — to handlers [8](#0-7) .

Handlers resolve the target `Stack`/`Repository` purely from `repository.full_name`:
- `PushHandler` resolves `stacks` via `Repository.from_github_repo_name(repository_name)` (where `repository_name = payload.dig('repository','full_name')`) and calls `stack.sync_github` [3](#0-2) [9](#0-8) .
- `StatusHandler` is even weaker: it does not check `repository` at all — it matches purely on commit `sha` across the entire `Commit` table (`Commit.where(sha: params.sha)`) and forges a CI status via `create_status_from_github!` [4](#0-3) .

This breaks exactly the trust binding the prompt calls out: *"an organization that authenticated versus the repository that is written."* An org whose `webhook_secret` is nil/blank (or unknown/unauthorized to the attacker) satisfies `verify_signature`, but the handler writes state for an entirely different, properly-secured repository's commits/stacks.

### Impact Explanation
`Status` records feed directly into deploy gating: `Commit#create_status_from_github!` → `add_status` fires `deployable_status` and can trigger `stack.schedule_merges` when the new status is `success`/`pending` [10](#0-9) , and creating a `Status` also runs `after_create :enable_ci_on_stack` and `schedule_continuous_delivery` [11](#0-10) . `README.md` documents that `ci.require` gates deploys on named status contexts [12](#0-11) . An attacker who only needs to know/guess one organization slug configured with a blank `webhook_secret` (a documented, supported configuration state) can forge a `success` CI status for any commit SHA hosted under a *different, fully-secured* organization, potentially satisfying `ci.require` gates and triggering continuous-delivery merge/deploy scheduling for a repository the attacker has no access to — an unauthorized-deploy-adjacent impact. `PushHandler` similarly lets the attacker force a `GithubSyncJob`/`sync_github` on an arbitrary stack belonging to the mismatched target organization.

### Likelihood Explanation
Exploitability requires only (a) knowledge that at least one configured GitHub organization in `secrets.yml` has no `webhook_secret` set — a state the project's own sample secrets file treats as normal/supported — and (b) an unauthenticated POST to `/webhooks` with a forged JSON body; no GitHub credentials, session, or API token are required. The mismatch between the field used for signature-org selection and the field used for target-repository resolution is a straightforward code-level oversight, not requiring any race condition or complex chaining.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner`/organization strictly from the same fields the dispatched handlers will use to select the target repository (i.e., verify that `repository.full_name`'s owner matches the organization whose secret authenticated the request), and reject the request if they differ. Additionally, do not treat a missing/blank `webhook_secret` as automatically valid in `GithubApp#verify_webhook_signature`; require an explicit "insecure mode" opt-in per organization instead of silently accepting unsigned webhooks.

### Proof of Concept
1. Deploy Shipit with two orgs configured, e.g. `orgA` (`webhook_secret:` blank/nil) and `orgB` (`webhook_secret: <strong-secret>`, hosting a real, sensitive stack) — mirroring the documented multi-org secrets layout [6](#0-5) .
2. Send an unauthenticated POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, and a body such as:
```json
{
  "sha": "<sha-of-a-commit-in-orgB/private-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" } },
  "organization": { "login": "orgA" }
}
```
3. `verify_signature` resolves `repository_owner` = `"orgA"`, calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [7](#0-6) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a forged `success` status for the targeted commit belonging to `orgB`'s repository, with no re-check that `orgA` has any relationship to that commit/repo [4](#0-3) , potentially satisfying `ci.require` and triggering `schedule_continuous_delivery`/merge scheduling for `orgB`'s stack.

**Note on verification limits:** I could not execute this against a live multi-org Shipit instance to confirm end-to-end deploy triggering (e.g. that `ci.require` actually gates a real deploy in this exact code path) — this is based on static analysis of `add_status`, `Status#enable_ci_on_stack`/`schedule_continuous_delivery`, and the documented `ci.require` behavior in `README.md`. A background Devin session with a runnable environment could confirm the full chain to an actual deploy trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
```
