## Title
Cross-Organization Webhook Spoofing via Unbound `repository.owner.login` vs `repository.full_name` — Forged CI Status / Push Events on Any Tracked Stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The DeFi analog is a value used to *authorize* an action (`guaranteedValue`) diverging from the value that actually *limits* the action (`poolAmount`), letting an unprivileged actor exploit the mismatch. In Shipit's webhook ingestion pipeline, the field used to **select the signing/verification key** (`repository.owner.login`, read from the unverified JSON body) is never bound to the field that handlers subsequently use to **select the target repository/stack** (`repository.full_name`). When Shipit is configured with multiple GitHub Apps (per-org `github:` config, as documented in `docs/setup.md`), and any one org has no `webhook_secret` configured (an explicitly supported, documented state — "Webhook secret (optional)"), an external, unauthenticated attacker can forge webhook payloads that pass signature verification under that org's identity while carrying `repository.full_name` pointing at a completely different, secured organization's tracked stack.

### Finding Description
`WebhooksController#verify_signature` derives the app/secret to verify against from attacker-controlled JSON, before the signature has been checked: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success — a documented, supported configuration (`webhook_secret: # nil` appears in `config/secrets.development.example.yml` and per-org sections): [3](#0-2) 

Once the signature check passes (trivially, for an org without a secret), `WebhooksController#create` dispatches the *entire, unverified payload* to event handlers: [4](#0-3) 

Handlers resolve the target `Stack`/`Repository`/`Commit` using a **different** field, `repository.full_name`, which was never involved in the signature-selection step: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization whose secret verified the request == organization that owns the repository the handlers act on`

but the engine only enforces:
`organization named in repository.owner.login (used to pick the key) == organization named in repository.owner.login (nothing else)`

while `repository.full_name` (used everywhere downstream to select the actual `Stack`/`Commit`/`Repository`) is completely independent and unchecked. An attacker who knows (or who is a legitimate collaborator on) any org configured with `webhook_secret: nil` can set `repository.owner.login` to that org (satisfying/bypassing verification) while setting `repository.full_name` to `victim-org/victim-repo` for a *different*, secured stack tracked by Shipit. Downstream handlers (`push`, `status`, `check_suite`, `pull_request`, etc.) then process the forged event as if it legitimately originated from the victim organization's GitHub App/webhook, e.g. creating a `Status` record for an arbitrary commit SHA in the victim's tracked repo, or forcing a `GithubSyncJob`/`RefreshCheckRunsJob` against the victim stack.

### Impact Explanation
This crosses a repository/organization trust boundary without any credential belonging to the victim org: it is an unauthenticated, unauthorized write into another organization's Shipit-tracked state (fabricated CI `Status`/check-run data, forced syncs, PR-driven state transitions such as `review_stack.archive!`/`stack.unarchive!`). Because Shipit's merge queue and deploy gating rely on `Status`/check-run state (`MergeRequest::StatusChecker`, `all_status_checks_passed?`), a forged "success" status on an arbitrary commit can unblock or trigger an unauthorized deploy/merge for a stack the attacker has no legitimate access to — matching the "unauthorized deploy" / cross-repository-write impact tier.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, and (2) at least one configured organization with no `webhook_secret` set — both are explicitly documented, supported configurations, not misconfigurations outside the engine's design (`config/secrets.development.example.yml`, `docs/setup.md`). No session, API token, or GitHub credential for the victim organization is required — only knowledge that such a no-secret org exists in the deployment (discoverable via the public `/webhooks` 422 error which echoes back whether an org is "unknown", or by trial payloads). This is a realistic configuration for smaller/simpler Shipit installs that don't bother setting a webhook secret for one org.

### Recommendation
Bind the verification key to the *actual* repository being acted upon, not to an independently-controlled field: verify the signature using the secret for the organization derived from `repository.full_name` (the same field handlers use to resolve `Stack`), or verify against the specific `Stack`'s configured organization once the repository is resolved, before dispatching to handlers. Additionally, do not allow signature verification to trivially succeed when `webhook_secret` is unset if `repository.owner.login` and `repository.full_name`'s owner differ, and consider making `webhook_secret` mandatory for any App used in a multi-org configuration.

### Proof of Concept
Given a Shipit deployment configured with two orgs, `NoSecretOrg` (no `webhook_secret`) and `Shopify` (tracked stack `Shopify/shipit-engine`, has webhook_secret):

```
POST /webhooks
X-Github-Event: status
(no valid X-Hub-Signature needed)

{
  "sha": "<any-commit-sha-in-Shopify/shipit-engine>",
  "state": "success",
  "target_url": "https://ci.example.com/forged",
  "context": "ci/travis",
  "repository": { "owner": { "login": "NoSecretOrg" }, "full_name": "Shopify/shipit-engine" }
}
```

`verify_signature` calls `Shipit.github(organization: "NoSecretOrg")`, whose `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-77`. `Shipit::Webhooks.for_event('status')`'s handler then resolves the target commit/stack via `repository.full_name = "Shopify/shipit-engine"` and records a forged `success` status for a commit in a stack that belongs to a different, secured organization — with no credential belonging to `Shopify` ever presented.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
