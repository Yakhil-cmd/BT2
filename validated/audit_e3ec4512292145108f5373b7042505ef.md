### Title
Webhook authentication bypass via optional `webhook_secret` combined with unvalidated organization/repository binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` configuration to use for HMAC verification based on an attacker-supplied field in the unauthenticated request body (`repository.owner.login` / `organization.login`), and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that selected app has no `webhook_secret` configured. Because the field used to select the verifying app (`repository_owner`) and the field used by every downstream handler to decide which `Stack`/`Repository` to act on (`repository.full_name`) are never cross-checked against each other, an attacker can forge a webhook that is "verified" against any organization lacking a secret while acting on any repository tracked by Shipit.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` derives the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an app with no configured `webhook_secret` as automatically "verified": [3](#0-2) 

This is a real, reachable configuration: the shipped setup guide documents `webhook_secret` as optional, and the reference secrets template even ships with it explicitly nil for each org: [4](#0-3) [5](#0-4) 

Every downstream handler independently re-derives the target `Repository`/`Stack` from the same unauthenticated payload, without any reference to which organization actually "authenticated" the request: [6](#0-5) 

Equality that should hold but is broken: `organization authenticated (repository.owner.login used to pick the GitHubApp/secret) == organization owning the repository actually written (repository.full_name used by handlers to resolve Stack)`. Because (a) verification can be trivially satisfied for any org whose config omits `webhook_secret`, and (b) `repository.full_name` is a completely independent, unauthenticated field, an attacker who knows of (or controls) one org entry with a blank secret can send a payload where `repository.owner.login` equals that unsecured org while `repository.full_name` names a `Stack` belonging to a different, "secured" organization. `verify_signature` passes (secret is blank ⇒ `true`), and the handler for that event then acts on the targeted stack as if it were a legitimate GitHub-originated event.

### Impact Explanation
Handlers triggered this way include:
- `push` → enqueues `GithubSyncJob`, syncing arbitrary commits into a stack's history.
- `status` → creates a `Status` for any commit, which `MergeRequest#all_status_checks_passed?`/`StatusChecker` rely on to gate auto-merge and continuous deployment.
- `pull_request` labeled/closed/opened → provisions or archives review stacks.
- `membership` → creates arbitrary `User`/`Team` records from attacker-chosen logins.

Forging green CI status via the `status` handler on a stack with `continuous_deployment` enabled can directly cause an unauthorized deploy, and forging statuses on a pending `MergeRequest` can cause an unauthorized merge — matching the Critical "unauthorized deploy, rollback or merge" impact bar.

### Likelihood Explanation
No session, `ApiClient` token, `webhook_secret`, or repository write access is required — only knowledge that at least one organization entry in `Shipit.github` configuration lacks a `webhook_secret` (a state explicitly presented as supported/optional by the project's own setup docs and reference config). Given that omission, the exploit is a single unauthenticated HTTP POST to `/webhooks` with a crafted JSON body.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization and fail closed (reject the request) instead of returning `true` when it is blank.
- Bind repository resolution to the same trust boundary used for signature verification: after selecting the `GitHubApp` by `repository_owner`, verify that the resolved `Repository`/`Stack` actually belongs to that same organization before any handler acts on it.

### Proof of Concept
1. Identify (or configure) one Shipit-tracked GitHub organization, `unsecured-org`, whose `config/secrets.yml` entry under `github:` has no `webhook_secret` (as shown possible in `docs/setup.md` and `config/secrets.development.shopify.yml`).
2. Send, without any valid `X-Hub-Signature` header:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "created_at": "2026-09-01T00:00:00Z"
}
```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request passes with `head(:ok)`.
4. `StatusHandler` processes the payload against `victim-org/victim-repo`'s commit, recording a forged successful status that `MergeRequest#all_status_checks_passed?` / continuous deployment logic will treat as legitimate CI signal for a repository entirely unrelated to `unsecured-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
