### Title
Unbounded `from_main_chain_index`/`to_main_chain_index` range in headers_commission/witnessing inputs enables expensive per-unit aggregation - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs` accepts `headers_commission` and `witnessing` inputs whose `from_main_chain_index`/`to_main_chain_index` fields define an MCI range that is bounded only by "not overlapping with previous spends" and "not exceeding `last_ball_mci`", with no cap on the *width* of the range. This range is then fed into `mc_outputs.calcEarnings`, which runs a `SUM(amount) ... WHERE main_chain_index BETWEEN ? AND ?` query whose cost scales with the size of the range/number of matching rows, analogous to the naive, unbounded disposition-range handling described in CVE-2026-66276.

### Finding Description
In `validation.js`, the `headers_commission`/`witnessing` input branch validates the range fields: [1](#0-0) 
The only lower-bound restriction on `from_main_chain_index` is that it must not be smaller than `next_spendable_mc_index` (i.e., ranges of a single address must not overlap with previously-claimed ranges) — there is no restriction preventing an author from claiming, in a single input, the *entire* unspent history in one call: [2](#0-1) 

The range is then passed straight into `calcEarnings`/`calcWitnessEarnings`, which execute a full-range `SUM` aggregation query over the `headers_commission_outputs`/`witnessing_outputs` tables for the given address and MCI bounds: [3](#0-2) [4](#0-3) 

Because `from_main_chain_index` can start at 0 (an address that has never spent its commissions before) and `to_main_chain_index` can be as large as `last_ball_mci - 1` (headers commission) or `last_ball_mci - 1 - COUNT_MC_BALLS_FOR_PAID_WITNESSING` (witnessing) — i.e., effectively the entire chain history up to the current tip — any address that has accumulated commission outputs over a long period (a witness, or any unit author who has ever earned headers commission and simply never spent it) can submit a single payment message whose input spans the full range of MCIs. This forces every validating node that processes the unit to run a wide range-scan aggregation over that address's accumulated output rows during unit validation, which happens synchronously inside the mutex-protected validation path shown in the `validate()` pipeline: [5](#0-4) 

This mirrors the CVE-2026-66276 bug class: the attacker (an authenticated unit author) supplies range bounds that are individually within legal limits but whose *width* is unconstrained, and the naive range-based aggregation performs work proportional to that width/row-count rather than being capped, causing excessive CPU work per validated unit.

### Impact Explanation
An authenticated author (any address that has ever earned headers commission, or any current/former witness for witnessing commissions) can force expensive full-range SUM aggregations on every full node that validates the unit. Because validation runs under an author-address mutex lock and inside a DB transaction (`validation.js` lines 357-378 area) while the node processes the unit, repeatedly triggering wide-range aggregations (by posting many units, each re-claiming/extending ranges as new commissions accrue, or by multiple long-dormant addresses coordinating) degrades validation throughput network-wide — a node unable to keep up with a stream of such units cannot confirm new units promptly, which is the "network unable to confirm new units" DoS class explicitly listed as acceptable impact.

### Likelihood Explanation
Likelihood is constrained: to make the range large, the address must have genuinely accumulated a large historical span of unspent headers_commission or witnessing outputs (e.g., an old, rarely-spending witness or unit author). This is a realistic scenario for long-lived witness addresses that batch their reward collection, and it does not require any large amount of funds or special privilege beyond authoring one payment unit with the corresponding input — well within reach of any registered witness or prolific author. The attack is repeatable indefinitely as chain height grows, each time potentially widening the exploitable range.

### Recommendation
Cap the width of `to_main_chain_index - from_main_chain_index` for headers_commission/witnessing inputs to a reasonable maximum (or require multiple smaller claims), and/or ensure the underlying SQL aggregation is served by an index on `(address, main_chain_index)` with a bound on scanned row count, rejecting inputs whose range width or matching row count exceeds a sane anti-spam threshold — consistent with the `MAX_PARENTS_PER_UNIT`-style anti-spam caps already used elsewhere in `validation.js`.

### Proof of Concept
1. Use (or simulate) an address that has authored many units over a long period without ever spending its `headers_commission` outputs, so that `headers_commission_outputs` contains many rows for that address spanning MCI 0 through a very high MCI close to the current `last_ball_mci`.
2. Construct a payment message with a `headers_commission` input:
   `{ type: "headers_commission", from_main_chain_index: 0, to_main_chain_index: last_ball_mci - 1 }`
   for that address, satisfying `validation.js` lines 2544-2586 (non-overlap and upper-bound checks pass trivially since the address never spent before and `to_main_chain_index` is within the allowed max).
3. Post the unit. Every validating node executing `calcEarnings` (`mc_outputs.js` lines 116-132) will run a `SUM(amount) WHERE main_chain_index BETWEEN 0 AND last_ball_mci-1 AND address=?` aggregation scanning the address's entire historical output set during synchronous unit validation.
4. Repeat with multiple such addresses/units to amplify aggregate validation latency across the network.

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
