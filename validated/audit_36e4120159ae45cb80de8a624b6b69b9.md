### Title
Webhook signature is verified against `repository.owner.login` while the acted-upon repository is taken from the unverified `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) [2](#0-1) . However, the event handlers that actually decide which `Repository`/`Stack` the webhook acts on resolve the repository from a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `Handler#stacks` [3](#0-2) . Nothing ties these two fields together, so the organization whose secret verified the payload is never checked against the repository that is actually written to.

### Finding Description
Shipit supports a documented "Using Multiple Github Applications" configuration where each GitHub organization has its own `app_id`/`webhook_secret` (see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`) [4](#0-3) [5](#0-4) . `Shipit.github(organization:)` looks up the per-organization app config by that organization name [6](#0-5) .

In `WebhooksController#verify_signature`, the organization used to pick the verifying `GitHubApp` (and thus its `webhook_secret`) is `repository_owner`, which is read straight from the attacker-controlled JSON payload (`repository.owner.login`, falling back to `organization.login`): [1](#0-0) [2](#0-1) 

Once the signature is accepted, the payload is dispatched to the appropriate `Handlers::*` class, and every handler resolves the target `Repository`/`Stack` via `Handler#repository_name`, which reads a *separate* JSON field, `repository.full_name`: [3](#0-2) 

`PushHandler#process` uses this to call `stack.sync_github` on every matching stack [7](#0-6) ; `StatusHandler#process` uses it (indirectly, via `Commit.where(sha:)`, which is scoped by stack membership through the commits table) to call `commit.create_status_from_github!` [8](#0-7) ; `CheckSuiteHandler#process` schedules check-run refreshes on the resolved stack's commits [9](#0-8) .

The binding that should hold is:
`organization_that_signed(repository_owner) == owner(repository_full_name)`

but this equality is never enforced. GitHub itself always produces consistent `repository.owner.login` and `repository.full_name` values in genuine webhooks, so this divergence is invisible in normal operation — but an attacker forging a raw POST to `/webhooks` is free to set these two fields independently. An attacker who knows (or controls) the `webhook_secret` for *any one* configured organization — e.g., their own organization, onto which they can install/administer the Shipit GitHub App and thus legitimately possess that organization's `webhook_secret` — can craft a payload where `repository.owner.login` = their own org (so the signature validates against their own known secret) while `repository.full_name` = `"victim-org/victim-repo"`, a stack belonging to a completely different, unrelated organization configured in the same Shipit instance. `verify_signature` passes because it only checked the signature against the attacker's own org's secret; the handler then blindly acts on `victim-org/victim-repo`.

### Impact Explanation
This breaks the intended trust boundary between "the organization that authenticated this webhook" and "the repository the webhook payload is written against," which is precisely the ownership/binding mismatch pattern in the source report (pool a reward is accrued for vs. pool that is actually listed/legitimate). Concretely, with a forged `status` event an attacker can inject arbitrary commit statuses (`Commit#create_status_from_github!`) for commits in a victim stack they have no access to — commit statuses gate `deployable_status`/merge and safety checks used before a deploy is allowed to proceed, so this can be used to force a false-green status enabling an **unauthorized deploy** on a stack the attacker has no legitimate access to. A forged `push` event can also make Shipit believe a victim branch's HEAD moved (`stack.sync_github`), and a forged `check_suite` event can force refreshing of check runs on victim commits. All of this crosses an organizational boundary that the per-org webhook secret was specifically designed to enforce.

### Likelihood Explanation
This requires the attacker to control the `webhook_secret` for at least one organization onboarded onto the same Shipit deployment (a normal, low-privilege scenario for anyone administering their own org's GitHub App integration in a multi-tenant Shipit install), plus knowledge of a victim stack's repository full name (which is generally public information, e.g. `owner/repo` on GitHub). No repository write access, API token, or session to Shipit itself is required — only the ability to send an arbitrary signed HTTP POST to the shared `/webhooks` endpoint, which is exactly the class of "unprivileged attacker breaks a deployment-trust binding" scenario this scan targets.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`Handler#stacks`), enforce that the organization used to verify the webhook signature matches the owner of `repository.full_name` (and/or `organization.login`) before dispatching to handlers — e.g., reject the webhook if `repository_owner.casecmp?(payload.dig('repository', 'full_name').to_s.split('/').first)` is false. More robustly, resolve the target `Repository` first, verify the signature using that repository's own configured organization's `webhook_secret`, and only then invoke handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (attacker controls/knows its `webhook_secret`) and `victim-org` (hosts a real stack, e.g. `victim-org/victim-repo`), per the documented multi-org `secrets.yml` format.
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against the attacker's own secret [1](#0-0) .
5. `StatusHandler#process` is invoked and creates a fabricated success status on the victim's commit, unrelated to `attacker-org` [8](#0-7) .

    if github_default_organization.nil?
      config = secrets.github

      config = github_app_config(organization)

  end
