Based on my research, I found a legitimate analog to the Hydra `HeadID` replay issue in ocore's generic off-chain signed-message primitive used by Autonomous Agents (`is_valid_signed_package`).

### Title
Off-chain `signed_message` hash omits any binding to the verifying AA/channel instance, enabling cross-instance signature replay - (File: `object_hash.js`, `signed_message.js`, `formula/evaluation.js`)

### Summary
`is_valid_signed_package()` lets an AA accept an off-chain, counter-signed statement (`signed_message`) as proof of authorization without requiring an on-chain unit from the signer. The hash that is actually signed, produced by `getSignedPackageHashToSign()`, commits only to the `signed_message` payload, `authors`, `last_ball_unit`, `timestamp` and `version` — it never commits to the address/identity of the *verifying* AA or to any unique instance/channel id. Exactly like Hydra's snapshot signature that omitted `cid` (Head ID), a valid signed package produced for one AA instance can be replayed verbatim against any other AA instance that (a) trusts the same signer address and (b) expects a message of the same shape, because the multisig/signature check only binds signer + content, never the destination contract instance.

### Finding Description
`getSignedPackageHashToSign` in [1](#0-0)  builds the hash-to-sign purely from the cloned `signedPackage` object (with authentifiers stripped): `signed_message`, `authors`, optional `last_ball_unit`/`timestamp`/`version`. There is no field for the address of the AA that will consume the package, nor any session/channel identifier.

`signed_message.validateSignedMessage()` in [2](#0-1)  validates the authors, definitions and signature over that same hash, and is invoked from the oscript evaluator's `is_valid_signed_package` opcode in [3](#0-2) . The only identity check performed is that the `evaluated_address` (the address passed by the calling AA as the *expected signer*) matches one of the `authors` — there is no check that the package was created "for" this particular AA. This mirrors the Hydra bug exactly: verification checks who signed and what was signed, but not for which instance/context it was signed.

This is a deliberate general-purpose primitive (comparable to Hydra's multisig-based snapshot signing before v0.13.0), so the platform relies entirely on AA authors to embed their own uniqueness data (e.g., their own address, a nonce, or a channel id) inside `signed_message`. Nothing in the core validation path enforces or even encourages that binding, and no `nonce`/anti-replay field exists anywhere in the signed-message schema (`hasFieldsExcept(objSignedMessage, ["signed_message", "authors", "last_ball_unit", "timestamp", "version"])`, [4](#0-3) ).

### Impact Explanation
Any AA pattern that uses `is_valid_signed_package` to authorize state transitions from an off-chain-signed statement from a trusted counterparty/oracle address (e.g., payment-channel-style balance attestations, price attestations reused as authorization, or multi-instance contracts sharing the same signer set) is exposed to cross-instance replay: a package signed for AA instance A (or for an earlier "epoch"/deployment with the same participants) can be resubmitted as a trigger to AA instance B, causing the same authorization decision to be accepted twice in a context it was never intended for. Depending on the AA's logic this can cause fund loss/drain from AA reserves, incorrect balance/state updates, or denial of finalization for legitimate later states — the same class of harm described in the CVE (incorrect value distribution / DoS on finalization), scoped here to AA fund loss or freezing.

### Likelihood Explanation
Reachable by any unprivileged AA trigger sender who is one of the counterparties: no special privileges are needed beyond being a party who legitimately received/holds a previously signed package (or colludes with one), and then posts it as `trigger.data` to a different but structurally similar AA instance that reuses the same signer address(es). Because the platform itself doesn't require any instance-binding field, correctness depends entirely on individual AA authors remembering to embed one — a common and easy-to-miss omission, exactly as it was for Hydra's original implementation before v0.13.0.

### Recommendation
Extend `getSignedPackageHashToSign` (or `is_valid_signed_package`) to optionally/mandatorily bind the signature to the verifying AA's own address (and ideally a monotonically increasing sequence/nonce or explicit channel id), and reject packages lacking such binding when used inside AA formulas. At minimum, document prominently and provide oscript helpers so AA authors are forced to include their own address plus a nonce in every `signed_message` they intend to validate with `is_valid_signed_package`, preventing cross-instance/cross-AA replay of otherwise validly-signed packages.

### Proof of Concept
1. Two AAs, `AA_X` and `AA_Y`, are deployed with identical logic that accepts a `signed_message` such as `{ debit: 100, counterparty: 'ADDR' }` signed by trusted address `S`, via `is_valid_signed_package(trigger.data.pkg, 'S')`, and on success pays out funds to the trigger sender.
2. `S` signs a package once (per `signMessage()` in [5](#0-4) ) for interaction with `AA_X`.
3. Attacker captures this valid `signed_message` (e.g., as the legitimate counterparty of `AA_X`) and re-submits the identical `trigger.data.pkg` to `AA_Y`.
4. `AA_Y`'s call to `is_valid_signed_package` succeeds because `getSignedPackageHashToSign`/`validateSignedMessage` only check that `S` signed this exact content — they never check that the content was meant for `AA_Y` — causing `AA_Y` to pay out funds a second time for the same underlying authorization.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
