### Title
Cross-repository/cross-stack Status forgery via unscoped sha lookup in `StatusHandler` bypasses `require_ci` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no binding to the repository that authenticated the webhook, then writes a GitHub status directly onto every matching `Commit` row regardless of which stack/repository it belongs to. Because a git commit's SHA-1 is a hash of its content and ancestry — not of the repository it lives in — an attacker who forks/mirrors a repo (or who owns a stack tracking the same upstream repo) shares real, identical SHAs with commits that belong to stacks they do not own, letting them flip `Commit#deployable?` from `false` to `true` on someone else's commit and clear the `require_ci` check in `Api::DeploysController#create`.

### Finding Description
Binding claimed by the design (and violated): `stack_that_authenticated_the_webhook.repository == commit.stack.repository` for every `Commit` mutated by a given webhook payload. In reality: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, cross-tenant lookup with **no** `stack_id`/repository filter. `create_status_from_github!` then appends a real `Status` row to that commit using attacker-controlled `state`/`description`/`context`/`target_url`: [2](#0-1) 

`Commit#deployable?` is computed purely from the commit's own `statuses`/`status` aggregation: [3](#0-2) 

`Api::DeploysController#create` resolves the commit within the *authorized* stack via `stack.commits.by_sha(params.sha)`, then trusts `commit.deployable?` to gate `require_ci`: [4](#0-3) 

`WebhooksController#verify_signature` only proves the payload came from GitHub for *some* `repository_owner`/org that Shipit has an App configured for — it never checks that the `sha` in the payload actually belongs to that same repository's Shipit commits: [5](#0-4) 

Exploit flow: attacker forks (or otherwise controls a repository sharing history with) the victim repository tracked by a Shipit stack. Because git SHAs are content-derived, unmodified ancestor commits in the fork have byte-identical SHAs to commits already ingested into the victim stack's `commits` table. Attacker triggers (or has GitHub trigger, e.g. via the Statuses API on their own repo) a `status` webhook with `state: 'success'` and that shared `sha`. The webhook signature validates because it is a genuine GitHub webhook for the attacker's own repository/org. `StatusHandler` then finds *every* `Commit` row with that sha — including the victim stack's row — and writes a passing status to it, flipping `deployable?` to `true` without any status ever having come from the victim's own repository. A subsequent authenticated call to `Api::DeploysController#create` for the victim stack with `require_ci: true` now passes the check.

None of the existing guards catch this: `verify_signature` authenticates the sender's org, not the sha-to-repository binding; `ExplicitParameters` only validates payload shape; `require_permission!`/`stacks` scope authorize the *deploy* endpoint but never re-validate where the commit's statuses originated; and `Commit#deployable?`/`blocked?` never check `status.stack_id` or provenance of individual `Status` rows against the commit's own repository.

### Impact Explanation
A user with no access to the victim stack can cause a real `Status` record to be written against a commit belonging to that stack and use it to bypass the `require_ci` safety check on `Api::DeploysController#create`, enabling an unauthorized deploy to proceed as if CI had passed — this is the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" category (Critical). The attack is repeatable against any commit whose SHA the attacker can reproduce via forking/shared history, and generalizes to any multi-stack Shipit instance where multiple stacks track the same or forked upstream repository.

### Likelihood Explanation
Preconditions: attacker needs a repository (fork or otherwise) sharing SHA history with the victim's tracked repository, and the ability to have GitHub deliver a genuine `status` webhook for that repo to the shared Shipit host (a public/multi-tenant GitHub App configuration where any org can install the app is the realistic case; a single-tenant, single-secret setup where the attacker's org isn't configured would block `verify_signature`). No SHA-1 cryptographic collision is required — this relies on git's well-known property that forked/cherry-picked commits retain identical SHAs. Cost is low (fork + push/trigger a status), and the attack is repeatable against any commit whose SHA is shared or known publicly.

### Recommendation
Scope the `StatusHandler` (and the analogous `CheckRunHandler`/other sha-keyed handlers) lookup by the repository that authenticated the webhook, not by `sha` alone, e.g. `Commit.joins(:stack).merge(Stack.for_repository(payload_repository)).where(sha: params.sha)`, so a status can only be attached to commits belonging to stacks tracking that exact repository (owner/name), not merely to any row sharing the same content-derived SHA.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, referencing existing fixtures/factories):
1. Create `stack_a` for repository `"victim/repo"` and `stack_b` for a different repository `"attacker/fork"`.
2. Create `commit = shipit_commits(:...)` (or `stack_a.commits.create!(sha: 'deadbeef...', ...)`) belonging to `stack_a`, with no statuses (so `commit.deployable?` is currently `false`, e.g., because `success?` is false).
3. Assert precondition: `assert_equal false, commit.deployable?`.
4. Build a `status` webhook payload where `payload['repository']['full_name'] == 'attacker/fork'` (a repo unrelated to `stack_a`) but `sha == commit.sha`, `state == 'success'`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(...).call(payload)` (or invoke `process` directly with the parsed params), bypassing only the HTTP-layer signature check to isolate the handler logic (as existing handler tests do).
6. Reload `commit` and assert `commit.reload.deployable?` is now `true`, and assert `commit.statuses.last.stack_id == stack_a.id` while the payload only ever named `attacker/fork` — proving no status ever legitimately originated from `stack_a`'s own repository.
7. Optionally extend to `Api::DeploysController#create` with `params: { require_ci: true }` on `stack_a` to show `param_error!(:require_ci, ...)` is no longer raised.
