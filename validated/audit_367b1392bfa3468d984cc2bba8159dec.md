### Title
Webhook signature verified against a different organization's secret than the repository actually written to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check the signature against using `repository_owner`, which is read from the JSON body itself (`repository.owner.login`), while every event handler determines *which repository/stack to mutate* using a different field of the same body, `repository.full_name` [1](#0-0) [2](#0-1) [3](#0-2) . In a multi-organization Shipit deployment (the config format explicitly supports multiple GitHub orgs, each with its own `webhook_secret`) [4](#0-3) , nothing ties `repository.owner.login` to `repository.full_name`'s owner segment, so a payload signed with organization A's secret can freely declare a `repository.full_name` belonging to organization B.

### Finding Description
The signature check does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

This only proves the raw body was HMAC-signed by *some* organization's configured `webhook_secret` — specifically whichever organization's login appears in `repository.owner.login`. It does not prove that the repository/commit/stack subsequently acted upon actually belongs to that organization.

Every handler that follows resolves the target repository independently, from `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [3](#0-2) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does an independent `owner`/`name` lookup, with no cross-check against `repository.owner.login`: [6](#0-5) 

`PushHandler` uses this to trigger a git sync (fetches new commits and can trigger deploy pipelines) for whatever stack is resolved from `full_name`: [7](#0-6) 

`StatusHandler` writes a `CommitStatus` for any commit matching `sha` globally (no repository scoping at all beyond the sha lookup) which can flip a commit's CI status and unblock/allow deploys: [8](#0-7) 

`CheckSuiteHandler` similarly schedules check-run refreshes keyed only off branch/sha within stacks resolved from `full_name`: [9](#0-8) 

The pull-request handlers (`ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`) also resolve the repository purely from `params.repository.full_name` and then archive/unarchive review stacks accordingly: [10](#0-9) [11](#0-10) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by signature (repository.owner.login)` **=** `organization implied by repository.full_name that handlers act on`.

Before the attack: for a legitimate GitHub-originated webhook, GitHub itself guarantees `repository.owner.login` and the owner segment of `repository.full_name` always refer to the same repository, so this binding holds implicitly and was never enforced in code.

After the attack: an operator/admin of organization A (who legitimately possesses org A's `webhook_secret`, e.g. from the App they registered for their own org in this shared multi-org Shipit instance) can compute a valid HMAC-SHA1 over a hand-crafted JSON body where `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")` picks org A's secret and `verify_webhook_signature` succeeds) but `repository.full_name = "org-b/victim-repo"` (or any repository/commit sha tracked by the shared Shipit instance). `verify_signature` passes, and the handler layer performs writes against org B's stack/commits/review stacks using data attributed solely to full_name/sha, with no verification that org B ever authorized or signed anything.

### Impact Explanation
This is a cross-organization/cross-repository write: an actor who is only trusted for organization A can forge webhook events that trigger `stack.sync_github` (potentially kicking off automatic deploy pipelines depending on stack configuration), inject fabricated commit statuses via `StatusHandler` (which can gate whether Shipit considers a commit deployable/mergeable), or archive/unarchive review stacks and manipulate PR-driven state for a completely different organization's repository. This matches the "cross-repository writes" / "unauthorized deploy" Critical impact criteria, since the write is not bound to the credential (webhook secret) that authenticated the request.

### Likelihood Explanation
Requires that the Shipit instance is configured for multiple GitHub organizations (documented/supported configuration, see `config/secrets.development.shopify.yml`) and that the attacker legitimately controls one such organization's GitHub App/webhook secret — a realistic scenario for shared/multi-tenant Shipit deployments where different teams/orgs are onboarded to the same instance. No GitHub App private key, `api_clients_secret`, or Shipit session is needed; only the attacker's own organization's webhook secret, which they are meant to have.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select the verifying secret is the same organization implied by every repository/stack the handler subsequently touches — e.g., require `repository.full_name.split('/').first == repository_owner` (case-insensitively) before dispatching to handlers, and reject (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with distinct `webhook_secret`s, both tracking repositories in Shipit (per `docs/setup.md`/`config/secrets.*.yml` multi-org format).
2. As an admin of `org-a`, compute `sha1=HMAC(org_a_webhook_secret, body)` for body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-already-known-to-Shipit>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and verifies successfully against `org-a`'s own secret [1](#0-0) .
5. `PushHandler` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on org B's stack [12](#0-11) , even though org B never signed or sent this request.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
