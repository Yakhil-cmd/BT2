### Title
Stale `Account.owner` lets a transferred position's previous owner keep spending authority (borrow/withdraw) while the new NFT owner is locked out - (File: contracts/controller/src/account.rs)

### Summary
The controller authenticates account spending authority against the `owner` field stored inside the `Account` struct (`account.owner`), which is written once at account creation and never updated. Separately, `require_account_owner` authenticates against the live NFT owner via `storage::account_owner`. After a `position-nft::transfer`, the stored `Account.owner` still names the previous holder, so the previous holder — or any delegate they granted — retains full borrow/withdraw authority over the account, while the new NFT owner fails both owner checks. This is the direct analog of CVE-2025-9312's missing-authentication class: the enforcement point validates a stale credential instead of the authoritative one.

### Finding Description
`load_or_create_account` and the position flows authenticate via `require_owner_or_delegate(env, account_id, caller, &account.owner)` (contracts/controller/src/account.rs:130-140), which returns early when `caller == owner` — comparing against `account.owner` loaded by `storage::get_account` (line 98). That `owner` is set only in `create_account` (lines 64-70) at mint time; no code path rewrites it (no `account.owner =` assignment exists in the crate). In contrast, `require_account_owner` (lines 143-148) correctly reads `storage::account_owner(env, account_id)`, which resolves the NFT `owner_of` — proving the codebase itself treats NFT ownership as the source of truth.

The delegate list is also keyed by the stored owner: `is_owner_or_delegate` checks `storage::get_delegates(env, account_id, owner).contains(caller)` (line 126), so delegates granted by the old owner remain active after transfer.

Consequences after `positionNft.transfer(victim → buyer)`:

- The **old owner** (or their previously granted delegate) can still call `controller::borrow` / `withdraw` on `account_id`, because `caller == account.owner` still holds, draining the account's collateral/debt capacity — theft of the position's value from the new owner.
- The **new owner** cannot call `borrow`, `withdraw`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, `add_delegate`, `remove_delegate`, or `renew_account` — every path requires either equality with the stale `account.owner` or live-NFT-owner delegation keyed to the old owner — freezing the legitimate owner's control of the account.

The stale owner can combine this with a sale: list/transfer the NFT, receive payment, then borrow against or withdraw the collateral, leaving the buyer holding an emptied or over-leveraged account.

### Impact Explanation
Theft of user funds (ex-owner drains collateral/borrows to max LTV after selling the position) and freezing of the legitimate owner's funds (new NFT owner cannot act on the account at all). A single unprivileged address reaches this via `position-nft::transfer` followed by `controller::borrow`/`withdraw` on the same `account_id`.

### Likelihood Explanation
Deterministic on every position NFT transfer or sale. The auth check unconditionally passes for the stale stored owner and unconditionally fails for the live NFT owner; no timing, price, or configuration dependency. The protocol even acknowledges the divergence elsewhere (`require_account_owner` reading the NFT), but the spending paths use the stale field.

### Recommendation
Make `require_owner_or_delegate` resolve the owner from `storage::account_owner(env, account_id)` (the live NFT owner) instead of `account.owner`, or resynchronize `account.owner` on every `get_account` load. Delegate grants should be keyed to the current NFT owner, and grants from prior owners must not remain usable — mirroring the documented intent that "delegate grants from the previous owner go inactive."

### Proof of Concept
1. Alice supplies collateral to `account_id` = N (account owner Alice; `Account.owner = Alice`).
2. Alice calls `positionNft.transfer(Alice, Bob, N)` — the NFT owner becomes Bob.
3. Alice (or a delegate she added before the sale) calls `controller::borrow(caller=Alice, account_id=N, …)`. `require_owner_or_delegate` compares `caller` to `account.owner` (still Alice) and passes; funds are drawn against the account Bob now owns.
4. Bob calls `controller::withdraw(caller=Bob, account_id=N, …)`; `caller == account.owner` fails (owner is Alice), and Bob has no delegate grant under key `Alice`, so it reverts `NotAuthorized` — Bob cannot move his own position.

Supporting code: `contracts/controller/src/account.rs:64-70` (owner set once), `account.rs:98-110` and `130-140` (spending paths gate on stored owner), `account.rs:143-148` (live NFT owner used only for non-spending paths), `contracts/position-nft/src/contract.rs` (transfer/approve are caller-auth and do not notify the controller).
