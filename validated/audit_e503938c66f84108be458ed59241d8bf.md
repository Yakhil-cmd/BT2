### Title
`review_stacks_enabled` killswitch bypassed by operator-precedence bug in `provision?`/`unarchive?` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` combine `repository.review_stacks_enabled` with the provisioning-behavior checks using unparenthesized `&&`/`||`, so `review_stacks_enabled` only gates the `allow_all` branch. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, a repository can still auto-provision/unarchive a Review Stack even though `review_stacks_enabled` is `false`. `LabeledHandler#respond_to_label_change?` shows the correct pattern (parenthesized), confirming the other two are a real regression, not intended behavior.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == false` ⇒ `provision?/unarchive? == false` for every `provisioning_behavior`.

`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Because `&&` binds tighter than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. `review_stacks_enabled` is therefore never consulted for the `allow_with_label` and `prevent_with_label` branches. [1](#0-0) 

The identical pattern exists in `ReopenedHandler#unarchive?`: [2](#0-1) 

By contrast, `LabeledHandler#respond_to_label_change?` correctly parenthesizes the boolean so `review_stacks_enabled` gates both branches: [3](#0-2) 

Reachable path: `Shipit::WebhooksController#create` dispatches any `pull_request` payload whose signature passes `GitHubApp#verify_webhook_signature` (which returns `true` unconditionally when the org has no configured `webhook_secret`) to the registered handlers, including `OpenedHandler`/`ReopenedHandler`. [4](#0-3) [5](#0-4) 

Note: an attacker does not even need to forge the signature — per the rules, an unprivileged attacker "who can open a pull request... label their own PR" against the target repo triggers a genuinely-signed GitHub webhook that reaches the same buggy `provision?`/`unarchive?` logic, so the vulnerability is exploitable regardless of `webhook_secret` configuration.

`LabelCapturingHandler` compounds this: `reopened_active_stack?`/`opened_active_stack?` only check `stack.present? && !stack.archived?` — they never check `repository.review_stacks_enabled` — so once a stack exists (via the precedence bug or otherwise), attacker-chosen label names are persisted onto `PullRequest#labels` and surface as uppercase keys in `ReviewStack#env` (fixed value `"true"`). [6](#0-5) [7](#0-6) 

The RCE framing in the question is overstated: `ReviewStack#env` only ever injects the literal string `"true"` for attacker-chosen keys, and `Command#interpolate_environment_variables`/`EnvironmentVariables` escape shell metacharacters in values (demonstrated by the existing test asserting `$(echo pwnd)` is not executed), so this specific label→env path alone is not command injection. [8](#0-7) [9](#0-8) 

### Impact Explanation
The demonstrable, in-scope impact is that the `review_stacks_enabled` killswitch — the control an operator uses to disable all dynamic Review Stack provisioning for a repository — can be silently bypassed for repositories configured with `allow_with_label` or `prevent_with_label`. This causes an unauthorized provisioning/unarchiving (and subsequent `stack.provisioner.up` invocation and deploy-queue enqueue) of a Review Stack for a repository whose operator explicitly disabled the feature, matching the "unauthorized deploy" impact category. It is repeatable against every repository using those two provisioning behaviors with `review_stacks_enabled: false`.

### Likelihood Explanation
No secrets are required for the core bug: an attacker only needs the ability to open or label a pull request against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior` other than `allow_all` (a legitimate, unprivileged capability per the rules). If the target org additionally has no `webhook_secret` configured, the attacker can also directly forge the entire webhook body without any real GitHub interaction, widening the blast radius to arbitrary repositories under that org. This is highly feasible and repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire boolean expression in both handlers:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`, and add regression tests combining `review_stacks_enabled: false` with each non-`allow_all` behavior (mirroring the pattern already used to test `LabeledHandler`).

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does NOT provision a stack when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Expected (correct) behavior: no stack created — `review_stacks_enabled == false ⇒ provision? == false`.
Actual (current) behavior: the assertion fails because `Shipit::Stack.count` increases by 1, proving `provision?` returns `true` despite `review_stacks_enabled == false`, confirming the broken binding. An analogous test against `ReopenedHandler#unarchive?` (using `create_archived_stack` + `provisioning_enabled: false, behavior: :prevent_with_label`, no label) demonstrates the same bypass for unarchiving.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
