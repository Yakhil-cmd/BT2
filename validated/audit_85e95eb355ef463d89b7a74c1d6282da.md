Based on my investigation, I found a genuine gap: the `EncryptedPayload::verify()` AEAD-binding check (which cryptographically ties an encrypted transaction's ciphertext to the specific `(sender, auth_key)` pairs that are allowed to trigger decryption) is only invoked in two places — the REST API's `validate_signed_transaction_payload` in `api/src/transactions.rs` and the consensus quorum-store batch check `verify_batch_kind_transactions` in `consensus/consensus-types/src/common.rs`. It is **not** invoked in `AptosVM::validate_transaction` (the vm-validator path used by mempool for admission) nor in `CoreMempool`'s `add_txn`/`insert`.

### Title
Encrypted-transaction admission (vm-validator / mempool) skips `EncryptedPayload::verify` sender/auth-key binding check - ([File: aptos-move/aptos-vm/src/aptos_vm.rs])

### Summary
`AptosVM::validate_transaction` (the `VMValidator` impl used by mempool/vm-validator to admit transactions) only checks that encrypted transactions are feature-gated and that `check_signature()` passes, then proceeds to the Move prologue. It never calls `EncryptedPayload::verify(sender, signer_auth_keys)`, the associated-data AEAD check that the API layer (`api/src/transactions.rs:1376-1393`) and the consensus batch validator (`consensus/consensus-types/src/common.rs:156-164`) both perform.

### Finding Description
`EncryptedPayload::verify` binds the ciphertext to `PayloadAssociatedData::new(sender, signer_auth_keys)` [1](#0-0) . This is a distinct check from the raw ed25519/etc. transaction signature verified by `TransactionAuthenticator::verify` / `SignedTransaction::check_signature` [2](#0-1) , since the signature only proves the sender authorized the *ciphertext blob*, not that the ciphertext's AEAD associated data matches the claimed sender/auth-key set used by the threshold-decryption committee.

`AptosVM::validate_transaction` — the entry point vm-validator uses for mempool admission — performs feature gating and `check_signature()` only, then runs the Move prologue; it never calls `EncryptedPayload::verify` [3](#0-2) . By contrast, the REST API explicitly performs this exact check before accepting a transaction for submission [4](#0-3) , and the consensus quorum-store batch verifier performs the same check again before treating a batch as `BatchKind::Encrypted` [5](#0-4) .

Mempool's own admission path (`CoreMempool::add_txn` → `TransactionStore::insert`) performs no encrypted-payload-specific validation at all, relying entirely on whatever called it (client submission via the API, or a validator-to-validator broadcast) to have already validated the payload [6](#0-5) .

### Impact Explanation
Because `EncryptedPayload::verify` is enforced only at the REST submission edge and again at batch-formation time in consensus, but is absent from the vm-validator/mempool admission path itself, any transaction-injection surface that calls `AptosVM::validate_transaction` directly (vm-validator tests, alternate submission RPCs, or any future/alternate client path that constructs and hands a `SignedTransaction` to mempool without going through `TransactionsApi::validate_signed_transaction_payload`) will admit an `EncryptedPayload::Encrypted` transaction whose ciphertext associated data does not match its claimed sender/auth-keys. Since the redundant checks in the API and consensus batch-builder currently mask this from being exploitable by a normal client through the standard `/transactions` endpoint, this is best characterized as a missing defense-in-depth invariant at the actual admission/validation boundary (`AptosVM::validate_transaction`) rather than a confirmed end-to-end bypass — I could not fully trace whether any other production code path reaches mempool/vm-validator without first going through `api/src/transactions.rs`'s validation.

### Likelihood Explanation
Low-to-Medium. The primary client-facing path (`POST /transactions`) does perform the check, so exploitation requires a route into mempool/vm-validator admission that bypasses `TransactionsApi::validate_signed_transaction_payload`. I was not able to conclusively identify such a route within the available indexed code (time/tool budget exhausted), so this should be treated as an architectural gap needing confirmation rather than a proven bypass.

### Recommendation
Move the `EncryptedPayload::verify(sender, signer_auth_keys)` check into `AptosVM::validate_transaction` (and/or the Move prologue itself, similar to other structural checks like chain-id/sequence-number), so that the encrypted-payload sender/auth-key binding invariant is enforced at the actual VM/mempool admission boundary rather than being duplicated only at the API and consensus-batch layers. This removes the possibility of any current or future submission path skipping the check.

### Proof of Concept
Could not be fully constructed/verified within the available exploration (would require confirming a concrete code path that calls `mempool::add_txn` or `AptosVM::validate_transaction` with an attacker-controlled `EncryptedPayload::Encrypted` transaction without first passing through `api/src/transactions.rs::validate_signed_transaction_payload`). Recommend a Devin session with repo access to trace all callers of `CoreMempool::add_txn` / `VMValidator::validate_transaction` to determine whether such a bypass exists in practice (e.g., via JSON-RPC, gRPC transaction submission, or internal test/tooling harnesses that construct transactions directly).
