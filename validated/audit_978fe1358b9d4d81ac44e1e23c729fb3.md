### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while the actual mutation targets `repository.full_name` - unauthenticated cross-repository webhook forgery when any configured GitHub App has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GithubApp` (and therefore which secret) is used to validate the inbound webhook based on an attacker-controlled JSON field (`repository.owner.login`, falling back to `organization.login`), while the handler that actually mutates state (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target `Repository`/`Stack` from a *different* attacker-controlled field, `repository.full_name`. Because Shipit supports multiple GitHub App configurations keyed by organization, and `GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the selected organization, an attacker can pick an organization with no secret to authenticate the request, then point `repository.full_name` at a completely different, secret-protected organization/stack to make the handler act on it.

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is derived purely from the untrusted JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a per-organization `GithubApp` instance, whose `verify_webhook_signature` short-circuits to `true` when that organization has no `webhook_secret` configured: [3](#0-2) 

This is a real, supported configuration state - Shipit ships an example with two organizations where one has a secret and the other explicitly has none (`webhook_secret: # nil`): [4](#0-3) 

Once `verify_signature` passes (i.e. `repository_owner` resolved to the secret-less org), the request body is dispatched to handlers, which resolve the repository/stack to act on using a *different* field, `repository.full_name`, with no cross-check against `repository_owner`: [5](#0-4) [6](#0-5) 

For example, the push handler enqueues a sync job for whatever stack matches that repository name/branch: [7](#0-6) 

And the status handler writes a `Status` for any commit matching an attacker-supplied `sha`, regardless of which org authenticated the request: [8](#0-7) 

**Binding broken (equality that must hold but doesn't):**
`organization used to select/verify the webhook secret (repository_owner from repository.owner.login/organization.login)` == `organization/repository whose data is mutated (repository.full_name used by Handler#repository_name)`

Before the attacker's request: both fields normally originate from the same real GitHub delivery, so they naturally match.
After the attacker's forged request: `repository.owner.login` is set to an org with no configured `webhook_secret` (bypassing the HMAC check entirely), while `repository.full_name` is set to `<victim-org>/<victim-repo>`. The controller only checks the former; the handler only uses the latter. No code path re-validates that the two agree.

### Impact Explanation
This is an authentication-bypass of the webhook trust boundary that Shipit explicitly relies on to accept GitHub events as authoritative (`verify_signature` is the only gate before dispatching to handlers, per `before_action :check_if_ping, :drop_unhandled_event, :verify_signature`). An unauthenticated external attacker who only needs to know that *some* configured GitHub organization on the instance has no `webhook_secret` (multi-org/multi-app setups are a documented, supported configuration) can:
- Forge `push` events to trigger `GithubSyncJob`/`sync_github` for arbitrary victim stacks not belonging to the org that "authenticated" the request - a cross-repository/cross-organization write.
- Forge `status` events to create fabricated commit statuses on arbitrary commits (`StatusHandler`), which can influence deploy-gating/merge logic elsewhere in Shipit.
- Forge `check_suite` or `membership` events similarly, since all handlers key off payload fields independent of `repository_owner`.

This matches the Critical bucket "cross-repository writes" / "unauthorized deploy" classes named in scope, since the write is performed on a repository/organization that never actually authenticated the request.

### Likelihood Explanation
Requires no credentials, sessions, or tokens - only a POST to the public `Shipit::WebhooksController#create` endpoint with a crafted JSON body and mismatched `X-Hub-Signature`/no valid signature for the target org. The only precondition is that the Shipit deployment configures more than one GitHub organization/app and at least one of them has no `webhook_secret` set (a state explicitly demonstrated in the codebase's own multi-app fixture). This is a realistic and even encouraged setup for installations onboarding new orgs incrementally.

### Recommendation
Bind signature verification and repository resolution to the same trusted field. Concretely: after verifying the signature for `repository_owner`, re-derive the target repository/organization strictly from data already validated as belonging to that same organization (e.g., reject the payload if `repository.full_name`'s owner segment does not case-insensitively match `repository_owner`), or verify signatures against all configured secrets rather than a payload-chosen one keyed by an attacker-controlled organization field. Additionally, `GithubApp#verify_webhook_signature` returning `true` when `webhook_secret` is blank should be reconsidered/removed as a default, or such organizations should be prevented from being selectable via untrusted payload data.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgOne` (has `webhook_secret`) and `OrgTwo` (no `webhook_secret`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   (any value/omitted)

{
  "ref": "refs/heads/main",
  "after": "attacker-controlled-sha",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
3. `verify_signature` computes `repository_owner = "OrgTwo"`, loads `OrgTwo`'s `GithubApp`, calls `verify_webhook_signature`, which returns `true` unconditionally because `OrgTwo.webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `create` dispatches to `PushHandler`, which resolves the target stack via `payload.dig('repository','full_name')` = `"OrgOne/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), and enqueues `sync_github` for that stack - despite the request never being signed with `OrgOne`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
