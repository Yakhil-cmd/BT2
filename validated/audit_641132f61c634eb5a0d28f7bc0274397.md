### Title
Webhook signature verified against attacker-chosen organization while the acted-upon repository/stack is taken from a separate unverified payload field — cross-tenant status/sync injection - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify the incoming signature against using `repository_owner`, a value read straight out of the unverified JSON body (`payload.dig('repository','owner','login')` or `payload.dig('organization','login')`). Once the signature check passes, `create` dispatches the very same raw payload to handlers that instead key off `payload.dig('repository','full_name')` to find the `Repository`/`Stack` to mutate. Because the field that selects "whose secret proves authenticity" and the field that selects "which repository/stack is written to" are independent and both attacker-supplied, a party that legitimately owns a webhook secret for **one** configured GitHub organization (in a multi-org `secrets.github` deployment) can forge a signature for a payload whose `repository.full_name` points at a stack belonging to a **different** organization/repository tracked by the same Shipit instance. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Shipit.github(organization:)` looks up per-organization GitHub App config (including a distinct `webhook_secret` per org) when `secrets.github` uses the multi-org schema documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml`: [4](#0-3) 

`verify_signature` fetches this org-scoped app using `repository_owner`, which is read directly from the JSON body before any authenticity check has happened: [5](#0-4) 

The HMAC verification itself (`GitHubApp#verify_webhook_signature`) only proves that *someone in possession of the secret for the claimed `repository_owner`* produced this exact `raw_post`; it says nothing about the trustworthiness of any other field inside that same, self-authored body: [6](#0-5) 

Once `head(422)` is not triggered, `create` re-parses the body and dispatches it to the registered handler for the event, passing the full untouched payload: [7](#0-6) 

Handlers resolve the target `Stack`/`Repository` using `payload.dig('repository', 'full_name')`, a field that is never cross-checked against `repository_owner`/the organization whose secret validated the request: [3](#0-2) [8](#0-7) 

`StatusHandler` is even weaker: it scopes purely by commit `sha` with no repository check at all before invoking `create_status_from_github!`: [9](#0-8) 

That call flows into `Commit#add_status`, which can flip a commit's CI/deploy-gating state and unconditionally trigger `stack.schedule_merges` (enqueuing `ProcessMergeRequestsJob`, which can execute a real GitHub merge) whenever the new state is `pending` or `success`: [10](#0-9) [11](#0-10) 

`PushHandler` similarly enqueues `GithubSyncJob` for any stack matching the attacker-chosen `full_name`/branch, causing Shipit to re-fetch and ingest commits for a repository the attacker's own signing key had no relationship to: [12](#0-11) [13](#0-12) 

**Binding broken:** *organization that authenticated the request* (`repository_owner` → the `webhook_secret` used in `verify_signature`) `≠` *repository/stack that is actually written* (`payload.dig('repository','full_name')` used by every `Handler`). Before the attacker's request: both fields, if honest, refer to the same GitHub org. After the attacker's crafted request: `repository_owner` = attacker's own org (whose secret they legitimately hold to run their own GitHub App/webhook), `repository.full_name` = a victim stack under a different org tracked by the same Shipit instance — and the signature still verifies because it was computed with the attacker's own secret over their own chosen body.

### Impact Explanation
This breaks cross-tenant isolation on a Shipit instance configured with multiple GitHub organizations (the documented, supported `secrets.github.<org>` schema). An attacker who administers their own org's GitHub App webhook can:
- Inject fabricated CI `status` events for arbitrary commits of *another* organization's stacks, flipping deploy-gating state and force-triggering `ProcessMergeRequestsJob`, which can merge a pull request on GitHub the attacker doesn't own (`Stack#schedule_merges` → `ProcessMergeRequestsJob#perform` → `merge_request.merge!`).
- Force `GithubSyncJob` execution for arbitrary victim repositories, causing unwanted commit ingestion.
This constitutes cross-repository writes / an unauthorized merge triggered from outside the actual repository's trust boundary, meeting the Critical bar.

### Likelihood Explanation
Requires the attacker to be a legitimate holder of a `webhook_secret` for *any one* organization configured on the shared Shipit instance (a normal, expected credential for a Shipit customer/org admin setting up their own GitHub App) — not the victim's secret, not an `ApiClient` token, and no privileged Shipit account. Any customer of a shared, multi-org Shipit deployment can attempt this against any other tenant's stacks by simply changing `repository.full_name`/`repository.owner.login` fields in a hand-crafted webhook body.

### Recommendation
After `verify_signature` succeeds, bind the verified organization to the repository being acted on: reject (or ignore) any event whose `payload.dig('repository','owner','login')` does not match the `repository_owner`/organization key whose secret validated the signature, before dispatching to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Handlers' `repository_name`/`stacks` resolution should be scoped to only repositories belonging to the authenticated organization.

### Proof of Concept
1. Shipit instance configured with `secrets.github` in multi-org form, containing `OrgA` (attacker-administered, attacker knows its `webhook_secret`) and `OrgB` (victim, unrelated to attacker), both with stacks tracked by this Shipit instance.
2. Attacker builds a JSON body:
```json
{
  "sha": "<victim-commit-sha-in-OrgB-stack>",
  "state": "success",
  "context": "ci/attacker",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` using their own legitimately-held `OrgA` secret.
4. POST to the webhooks endpoint with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), verifies successfully against `OrgA`'s secret.
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matches the victim commit in `OrgB`'s stack regardless of the verified org — and calls `create_status_from_github!`, flipping the commit to `success` and triggering `stack.schedule_merges`, potentially merging a victim pull request the attacker has no access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
