### Title
StatusHandler mutates Commit statuses across repositories without checking payload repository or branches - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone (`Commit.where(sha: params.sha)`) and never restricts the query to the repository or branch named in the webhook payload, unlike `PushHandler` which scopes via `stacks` (built from `Repository.from_github_repo_name(repository_name)`). Because GitHub signature verification only proves the webhook came from *some* repository/org the attacker controls, not that the sha belongs to that repository, an attacker who owns any repository (e.g. a public fork) can forge a `status` event for a sha that also exists in a victim's tracked stack (forks of public repos routinely share identical commit shas) and mutate the victim's `Status` records.

### Finding Description
The intended binding is: `payload['repository']['full_name'] == commit.stack.repository.full_name` (and, per the question, `payload branches ⊇ commit's stack branch`). Neither is ever checked.

- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally, across all stacks/repositories, keyed only by `sha`. `params.branches` (accepted at lines 15-17) is parsed but never read.

- `Handler` (app/models/shipit/webhooks/handlers/handler.rb:32-38) exposes a `stacks` helper that scopes by `Repository.from_github_repo_name(repository_name)`, and `PushHandler` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) correctly uses `stacks.not_archived.where(branch:)` before touching any records — i.e., push events are scoped to the repository that authenticated the webhook. `StatusHandler` does not call `stacks` at all, so it inherits none of that scoping.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only confirms the payload is signed by `Shipit.github(organization: repository_owner)` — i.e., that the attacker legitimately controls the repository/org named in *their own* payload. It does not, and cannot, prove that a given `sha` in the payload actually belongs to that repository.

Exploit flow: attacker owns (or forks) a public GitHub repository that is also tracked by a victim's Shipit stack (e.g. an open-source project). Because forks preserve commit shas verbatim, a commit sha visible in the attacker's fork is identical to the sha of the corresponding commit in the victim's tracked repository/stack. The attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org, `sha: <shared sha>`, `state: success`, and `branches: []` (or any branch, including one that doesn't exist in the victim's repo). `StatusHandler#process` finds the victim's `Commit` row purely by `sha` match and calls `commit.create_status_from_github!(params)`, creating a forged status (e.g., `success`) on the victim's commit regardless of repository or branch.

`Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) then runs `add_status`, which can trigger `stack.schedule_merges` on success (app/models/shipit/commit.rb:383) and feeds into `deployable?`/`blocked?` checks (app/models/shipit/commit.rb:227-237) used by continuous delivery (`schedule_continuous_delivery`, lines 281-287). A forged "success" status can therefore make a victim's commit appear CI-passing and eligible for continuous deployment/merge, independent of the actual CI state on the victim's repository.

Existing guards do not prevent this: `verify_signature` only authenticates the attacker's own repository/org, `drop_unhandled_event`/`check_if_ping` are irrelevant, and there is no `ExplicitParameters` or model-level check tying `params.sha`/`params.branches` to `repository_name`/`stack.branch`.

### Impact Explanation
An attacker who controls any GitHub repository (no Shipit privileges, no victim credentials) can write forged CI `Status` rows onto commits in a victim's Shipit-tracked stack whenever the sha coincides (trivially true for forks/mirrors of the same upstream history, or any repository sharing commit history with the victim's repo). Because `create_status_from_github!` participates in `deployable?`/`schedule_merges`/`schedule_continuous_delivery`, this can enable an unauthorized deploy or auto-merge for the victim's stack based on a fabricated status. This is cross-repository mutation of another tenant's `Commit`/`Status` records driven entirely by an unauthenticated (with respect to the victim) payload — matching the Critical category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy."

### Likelihood Explanation
Preconditions: the attacker needs (a) their own GitHub repository/org capable of emitting a validly-signed webhook (trivial — any GitHub user can create a repo and a Shipit GitHub App/webhook installation on it, or simply craft the request if they can obtain a signature via their own installation), and (b) a sha that also exists as a `Commit` in a victim's Shipit-tracked stack. Sha collision across repositories is not a hash-collision requirement — it is the normal, expected behavior of Git forks/mirrors, which share identical commit objects/shas with their upstream. This makes the attack cheap, repeatable against any number of forked/mirrored repositories, and requires no victim secrets.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: resolve `stacks` from the webhook's `repository_name`, restrict the `Commit` lookup to `stacks` (e.g. `Commit.where(sha: params.sha, stack: stacks)` or joining through `stack.repository`), and additionally honor `params.branches` by only updating commits whose owning stack's `branch` is included in the payload's branch list (mirroring the "untracked branch" test intent). Reject/ignore statuses whose payload repository does not match the commit's actual repository.

### Proof of Concept
minitest plan (test/models/shipit/webhooks/handlers_test.rb or a new test file):
1. Create `stack_a` for `repository_full_name: "victim/repo"` with `branch: "main"`, and a `Commit` `commit_v` with `sha: "deadbeef"` belonging to `stack_a`.
2. Create `stack_b` for a different repository `attacker/fork` (irrelevant to lookup since StatusHandler ignores it).
3. Build a status payload: `{ 'sha' => 'deadbeef', 'state' => 'success', 'branches' => [], 'repository' => { 'full_name' => 'attacker/fork' } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit_v.reload.statuses.count == 1` and `commit_v.status.state == 'success'`, proving the status was written to `victim/repo`'s commit even though the payload's `repository.full_name` is `attacker/fork` and `branches` is empty — i.e. `payload['repository']['full_name'] ("attacker/fork") != commit_v.stack.repository.full_name ("victim/repo")` yet the mutation still occurred, confirming the binding is broken.     def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
