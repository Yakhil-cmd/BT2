### Title
Uncapped RAY value overflow during interest accrual permanently freezes a market - ([File: contracts/pool/src/interest.rs](contracts/pool/src/interest.rs))

### Summary

The permissionless `update_indexes` path can drive a sufficiently large, highly utilized market into an `i128` RAY-value overflow before the configured borrow-index ceiling is reached, permanently preventing subsequent accrual-dependent operations. [1](#0-0) [2](#0-1) 

### Finding Description

`markets::update_indexes` only requires caller authorization and forwards the selected hub assets to the pool, so any address can trigger accrual for its own account. [3](#0-2)  The pool accrues interest through `global_sync`, which splits elapsed time into bounded chunks and invokes `accrue_chunk` for each interval. [4](#0-3)  Each accrual step evaluates the market's scaled borrow and supply totals before committing the updated borrow and supply indexes. [5](#0-4) 

Scaled totals are converted back to asset value through `scaled_to_original` when utilization is calculated. [6](#0-5)  Although admitted token inputs and both indexes are bounded independently, the protocol documentation explicitly states that accrued market totals can exceed the RAY/`i128` domain before either bound prevents growth. [7](#0-6)  The regression test demonstrates that a billion-token, 18-decimal market at approximately 98% utilization reaches this overflow while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [8](#0-7) 

### Impact Explanation

Once the market crosses the RAY-value limit, every mutation that performs accrual first panics with `MATH_OVERFLOW`, including withdrawals and repayments. [2](#0-1)  Because the failing transaction cannot commit a newer accrual timestamp or a capped index, later calls encounter the same elapsed interval and overflow again rather than recovering. [4](#0-3) 

Supplier funds, borrower collateral, liquidation proceeds, and unclaimed protocol revenue in the affected market therefore become unavailable through the normal controller paths. [9](#0-8)  This constitutes permanent freezing of user funds and can leave economically significant debt impossible to repay or liquidate. [2](#0-1) 

### Likelihood Explanation

An unprivileged caller can supply a market, provide collateral in another listed market, borrow at high utilization, and later invoke `update_indexes` as time accrues. [10](#0-9) [11](#0-10)  The same state can also arise organically from ordinary deposits and borrowing, after which any caller can expose the failure through `update_indexes`. [3](#0-2) 

Likelihood depends on configured caps and a market reaching extreme scale and sustained utilization; the issue is not instant for ordinary-sized markets. [7](#0-6)  Nevertheless, the code admits token amounts near the conversion bound and does not enforce a corresponding accrued-value ceiling, making the condition reachable under valid market configuration. [12](#0-11) 

### Recommendation

Before interest accrual, derive the post-accrual scaled totals using widened arithmetic or an explicit market-value ceiling and revert with a recoverable bounded-index state rather than trapping in `scaled_to_original`. [6](#0-5) [5](#0-4)  Alternatively, clamp or stop borrow-index growth early enough that `borrowed_scaled * borrow_index` and `supplied_scaled * supply_index` remain below the supported RAY-value domain, while still permitting withdrawals and repayments. [7](#0-6) 

### Proof of Concept

1. Configure a high-decimal market with an interest model whose steep segment produces sustained growth, and configure a separate collateral market. [13](#0-12) 
2. From one unprivileged address, supply approximately one billion whole units of the debt asset and enough collateral in the second market. [14](#0-13) 
3. Borrow approximately 98% of the supplied debt asset. [15](#0-14) 
4. Advance time and repeatedly call the permissionless `update_indexes(caller, [debt_asset])`. [1](#0-0) [16](#0-15) 
5. Observe `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`. [17](#0-16) 
6. Attempt `withdraw` or `repay`; both fail with the same overflow because they accrue before mutating the market. [18](#0-17)

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
```

```rust
        ops::run_batch(&env, entries, ops::supply::apply)

    /// Batch-borrows assets and transfers them to `receiver`: accrues
    /// interest, mints scaled debt, debits cash, and enforces max
    /// utilization after each mint. Restricted to the owner; returns one
    /// [`PoolPositionMutation`] per entry.
    #[only_owner]
    fn borrow(

        receiver: Address,
        entries: Vec<PoolBorrowEntry>,

        ops::run_batch(&env, entries, |env, entry| {
            ops::borrow::apply(env, &receiver, entry)
        })
```
