### Title
Sybil-splitting a single staker's locked STX across many `signer_key`s inflates signing weight beyond the locked-value bound in `pox_5_make_signer_set`'s leftover round - (File: `stackslib/src/chainstate/nakamoto/signer_set.rs`)

### Summary
`NakamotoSigners::pox_5_make_signer_set` allocates a base weight of `floor(stacked_amt / threshold)` per distinct `signer_key`, then hands out any leftover reward slots one-per-distinct-key in descending-remainder order [1](#0-0) . Because the leftover bonus is capped at exactly `+1` per distinct key regardless of that key's stacked amount, an attacker who fragments one locked-STX position across `k` distinct `signer_key`s (each below `threshold`, each still crossing `SIGNER_SET_MIN_USTX` to enter the pox-5 linked list) can compete for up to `k` leftover slots instead of the single `+1` a lone key could ever win, producing total weight for that one staker strictly greater than `ceil(locked_amount / threshold)`.

### Finding Description
The invariant this question asks about is: *for one principal's total locked `amount_ustx`, total signing weight granted should not exceed `ceil(amount_ustx / threshold)` (the single-key bound already covered by the existing `+1` rounding tolerance), regardless of how many `signer_key`s that principal's stake is spread across.*

Tracing `pox_5_make_signer_set`:
- Entries are aggregated per `signer_key` (not per staking principal) in the `signer_set: HashMap<[u8;33], u128>` [2](#0-1) .
- `threshold = max(1, total_ustx_locked.div_ceil(reward_slots))` is a network-wide value [3](#0-2) .
- Each key's base weight is `stacked_amt / threshold` (integer floor); `assigned = sum(weight)` is guaranteed `<= reward_slots` [4](#0-3) .
- `leftover = reward_slots - assigned` slots are then awarded **one per distinct key**, sorted by `remainder` descending, ties broken by `signing_key` [5](#0-4) .

Because the leftover bonus is a flat `+1` keyed by `signing_key` rather than by staking principal, a single principal's locked value has no aggregate cap on how many `+1` bonuses it can collect — that cap is per-key, not per-principal. `pox-5` (and `pox_5_stake_entries`/`StakeEntryIteratorPox5`) build the signer set purely from `signer_key`s registered via `register-for-bond`/`stake` on distinct `signer-manager-trait` contracts; there is no cross-key deduplication by staker identity anywhere in this path [6](#0-5) . The code's own comment acknowledges this leftover-per-key design exists specifically to avoid dropping signers when many distinct keys each floor to zero base weight [7](#0-6) , but that same mechanism is what an attacker abuses: it does not, and structurally cannot, distinguish "many distinct genuine stakers" from "one staker's Sybil-split stake."

**Exploit shape:** Attacker deploys `k` distinct `signer-manager-trait` contracts (each an unprivileged, self-owned contract) and locks their total STX `V` split into `k` fragments `v_1..v_k`, each satisfying `SIGNER_SET_MIN_USTX <= v_i < threshold`, so each fragment's base weight floors to 0 and its `remainder == v_i` (maximal remainder). In a reward cycle where the leftover pool is large relative to the number of genuinely competing high-remainder stakers (the "degenerate," thinly-spread-stake regime the code comment itself describes), the attacker's `k` fragments can rank among the top-`leftover` remainders and each win a `+1` bonus — for total weight `k`, versus at most `1` had the attacker kept `V` as a single key (`weight = floor(V/threshold) + at most 1`). This is exactly the divergence the question's proposed property test (`pox_5_make_signer_set_props`, split-vs-unsplit comparison) is designed to catch, and property (b') as currently written in the test file only checks the **network-wide** total-weight bound (`total_weight <= reward_slots`), not a per-principal bound tying an individual staker's total granted weight to their own locked amount [8](#0-7) .

No existing guard in this file (`verify-not-prepare-phase`, `check-pox-lock-period`, `verify-signer-key-grant`, etc., which live in `pox-5.clar` and are out of the direct Rust apportionment logic) constrains the *number* of distinct signer keys one staking principal can register, nor does `pox_5_make_signer_set` deduplicate by staker identity — only by `signer_key`.

### Impact Explanation
The attacker gains extra `.signers` weight/reward-slot allocation disproportionate to the STX they actually locked. This falls under the "High" impact category explicitly listed in scope: *"signing weight or reward slots exceeding locked value."* It is not, by itself, a theft, unbacked mint, or freezing of funds (the Critical bucket) — no STX/sBTC balance accounting (`STXBalance`, `protocol-bond-memberships`, sBTC allowance) is altered by this apportionment step; only `.signers`' `weight` tuples and the derived `WaterfallCycleSet` are affected. The practical downstream risk is disproportionate influence over Nakamoto block/signature thresholds and the sBTC-waterfall aggregate-key computation for that cycle, which is repeatable every reward cycle in which the attacker maintains the split and the leftover pool is large enough to favor their fragments.

### Likelihood Explanation
Preconditions are non-trivial: (1) the network-wide `threshold` and leftover-pool size must fall into the "many low-remainder competitors" regime for the attacker's fragments to actually outrank other stakers' remainders for available leftover slots; (2) each fragment must independently clear `SIGNER_SET_MIN_USTX` to enter the pox-5 linked list (exact constant value not confirmed within available context — this bounds the minimum capital/number of fragments feasible); (3) the attacker must deploy and manage `k` separate `signer-manager-trait` contracts, an unprivileged but non-zero operational cost. Exploitability is highest in low-participation or early-network cycles where stake is thin relative to `reward_slots`; it is largely self-defeating once total locked stake densely saturates `reward_slots` via floor weights, since then `leftover` shrinks toward the number of truly distinct competitive stakers.

### Recommendation
Cap the total leftover bonus (and ideally total granted weight) per staking **principal**, not per `signer_key`: aggregate `RawPox5Entry`s by the underlying staker/principal (or by the STX lock commitment they originate from) before running the largest-remainder leftover round, or bound each principal's total weight to `ceil(principal_total_ustx / threshold)` after apportionment and reclaim any excess leftover slots for reallocation to other competitors.

### Proof of Concept
Extend `pox_5_make_signer_set_props` in `stackslib/src/chainstate/nakamoto/tests/signer_set.rs`:
1. Generate a `total_ustx: u128` and a split count `k: u8 (>1)`, plus `k` distinct random `signer_key`s and a partition of `total_ustx` into `k` positive fragments each below `threshold` computed from a fixed background entry set.
2. Run `pox_5_make_signer_set` once with a single `RawPox5Entry{signer_key: SK, amount_ustx: total_ustx}` mixed into the same background entries; record `weight_single = sum of weight for SK`.
3. Run `pox_5_make_signer_set` again with the `k` fragment entries (same background entries, same aggregate `total_ustx_locked`); record `weight_split = sum of weight for the k fragment signer_keys`.
4. Assert `weight_split <= weight_single` (i.e., `weight_split <= ceil(total_ustx/threshold)`); construct at least one concrete background-entry fixture (many small nonzero-remainder competitors saturating the leftover pool) under which this assertion fails, demonstrating `weight_split > weight_single`.

        // Allocate `reward_slots` weight across signers in proportion to stake using the
        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
        }
