## Title
Vault `initialize()` has no access control and can be front-run before the DAO's atomic init proposal executes - (`mainnet/contracts/vault/v0-vault-usdh.clar`, similarly `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Every vault's `initialize` function is `define-public` and guarded only by a one-time boolean flag, exactly like Velodrome's `Bribe.setGauge`. Any unprivileged address can call it directly before the DAO's single atomic init proposal (which is supposed to call `initialize` as one step among many) executes, permanently consuming the one-shot flag and causing the whole proposal transaction to revert.

### Finding Description
`initialize()` sets `initialized` to `true` and performs the minimum-liquidity seed deposit, with no `check-dao-auth` or owner check at all: [1](#0-0) 

Compare this to `set-authorized-contract` and `set-flashloan-permissions` in the very same file, which do call `check-dao-auth`: [2](#0-1) 

The intended flow is a single DAO proposal (`v0-init.clar`) that atomically sets caps, calls `initialize` on all six vaults, and then authorizes the market contract in the same `execute` transaction: [3](#0-2) 

Because Clarity `try!` aborts the entire transaction on the first error, if `initialize` has already been flipped to `true` by an attacker's earlier, independent call, the proposal's own `(try! (contract-call? .v0-vault-usdh initialize))` step returns `ERR-ALREADY-INITIALIZED` and the *entire* `execute` transaction - including cap-setting and market authorization for every vault, and egroup creation - rolls back. This mirrors the report's root cause precisely: a permissionless, one-time setter (`Bribe.setGauge` / here `initialize`) that is meant to be called only as part of an atomic sequence (`Gauge` constructor / here the DAO's `v0-init` proposal) can be griefed by any third party calling it first.

### Impact Explanation
- **Attacker**: any unprivileged address, who simply calls `.v0-vault-usdh initialize` (or any of the six vaults) before the DAO's init proposal is executed.
- **Victim**: the DAO/protocol and all intended depositors/borrowers - the shared state is the `initialized` data-var and the fact that the whole market bring-up is bundled into one non-repeatable proposal transaction.
- **Outcome without attacker**: the DAO proposal executes once, atomically initializing all vaults, setting caps, and authorizing the market - the market opens for lending/borrowing as designed.
- **Outcome with attacker**: the proposal transaction reverts entirely at the first vault whose `initialized` flag was already flipped, and none of the caps/authorizations/egroups configured in that same transaction take effect. The DAO must draft, vote on, and pass a new proposal (potentially requiring a redeployed proposal script since the original hardcodes an unconditional `initialize` call that will always fail against the already-initialized vault), delaying market launch.

This is a temporary freezing of protocol funds/operation: tokens already staged for the minimum-liquidity seeding (minted/transferred to the executor/proposal context ahead of execution, per the test helper flow) sit unusable, and the market cannot be authorized or opened until the DAO repeats governance, mirroring the "temporary system-breaking impact" that made the analogous Velodrome finding Medium severity.

### Likelihood Explanation
Any DAO governance action that has a voting/queuing delay between contract deployment and proposal execution creates a window in which this call is exploitable, since `initialize()` requires no privilege and the underlying seed amount (`MINIMUM-LIQUIDITY`, 1000 base units per vault) is a negligible cost for an attacker to grief the transaction.

### Recommendation
Add a `check-dao-auth` (or equivalent restricted-caller check, e.g. only `.dao-executor` or the deploying proposal contract) to `initialize`, matching the pattern already used by `set-authorized-contract` and `set-flashloan-permissions` in the same contracts, so it cannot be triggered by an arbitrary caller ahead of the DAO's atomic bring-up proposal.

### Proof of Concept
1. Vault contracts (e.g. `v0-vault-usdh.clar`) are deployed to mainnet.
2. Before the DAO's `v0-init` proposal is voted through and executed, an attacker calls `(contract-call? .v0-vault-usdh initialize)` directly, supplying the negligible `MINIMUM-LIQUIDITY` amount themselves; `initialized` becomes `true`.
3. When the DAO's proposal is later executed, its own `(try! (contract-call? .v0-vault-usdh initialize))` step returns `ERR-ALREADY-INITIALIZED`, and the entire `execute` function - covering caps, market authorization, and egroup setup for all vaults - reverts, per [3](#0-2) .
4. The DAO must draft and pass a new corrected proposal before the market can open, freezing protocol launch/funds in the interim.
