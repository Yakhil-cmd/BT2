### Title
Webhook signature is verified against the wrong organization field, allowing cross-organization forged GitHub events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a payload's HMAC using `repository.owner.login` (or `organization.login`), but the actual repository/stack that gets mutated by the downstream handler is resolved from a completely different, unrelated field: `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Since the HMAC only proves the request was signed by *whoever's* secret matches the org named in the payload — and that org name is attacker-controlled input, not independently verified against `full_name` — an attacker who administers any single GitHub organization onboarded into the same multi-org Shipit instance (a supported configuration per `docs/setup.md`) can self-sign a forged webhook whose `repository.full_name` field points at a stack belonging to a different organization they do not control.

### Finding Description
`WebhooksController#verify_signature` computes the signing organization purely from attacker-supplied payload content: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that org's `webhook_secret`: [3](#0-2) 

If the request validates, the raw params are dispatched unmodified to whichever handler matches the event, e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`: [4](#0-3) 

Every handler resolves the target stack(s) from an entirely different payload field — `repository.full_name` — with no cross-check against `repository.owner.login`/`organization.login` used for signature selection: [5](#0-4) 

Shipit explicitly supports hosting multiple GitHub organizations/Apps on one instance, each with its own `webhook_secret`: [6](#0-5) 

**Binding broken:** `organization that authenticated (repository.owner.login used to pick the verifying secret) != repository that is written (repository.full_name used by the handler to locate the Stack)`. The signature only proves "this payload was signed by the holder of `<repository.owner.login>`'s secret" — not "the events inside this payload legitimately concern `<repository.full_name>`."

### Impact Explanation
An attacker who administers `attacker-org` (with a GitHub App installed and thus knows `attacker-org`'s `webhook_secret`, a legitimate, unprivileged capability any org admin has) can:
1. Craft a JSON body with `repository.owner.login` (or `organization.login`) = `attacker-org` and `repository.full_name` = `victim-org/victim-repo` (a stack tracked by Shipit but owned by an org the attacker does not administer).
2. Self-compute the HMAC-SHA1 using `attacker-org`'s own webhook secret and send it as `X-Hub-Signature`.
3. `verify_signature` passes because it only checks the signature against `attacker-org`, which the attacker legitimately controls.
4. The dispatched handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) then acts on `victim-org/victim-repo`'s stacks using `Repository.from_github_repo_name(repository_name)`.

Concretely reachable effects on a repo/stack the attacker does not own:
- `PushHandler#process` forces `stack.sync_github(expected_head_sha: ...)` on victim stacks with an attacker-chosen `after` SHA/branch, causing unscheduled resync activity.
- `StatusHandler#process` lets the attacker inject arbitrary commit statuses (`create_status_from_github!`) for any commit SHA already known to Shipit, which is used to gate continuous-deployment/merge-queue eligibility — directly enabling an unauthorized/forced deploy or merge condition on a stack outside the attacker's authorization scope.
- `MembershipHandler`/`CheckSuiteHandler` similarly act using cross-org data without any binding check.

This satisfies the "unauthorized deploy" / cross-repository-writes class of impact since Shipit trusts webhook payload content for a repository that was never actually verified as belonging to the signing organization.

### Likelihood Explanation
This requires the target Shipit instance to be configured for multiple GitHub organizations (an explicitly documented and supported setup) and requires the attacker to control at least one onboarded org (e.g., their own company/org that legitimately uses the same Shipit instance for other repos). No privileged Shipit account, API token, or GitHub write access to the victim repository is needed — only knowledge of one's own org's webhook secret, which any org admin holds. This is a realistic multi-tenant scenario for shared Shipit deployments.

### Recommendation
In `Shipit::Webhooks::Handlers::Handler`, cross-validate that the resolved `repository.owner.login`/`organization.login` (the field used to select the verifying secret in `WebhooksController#repository_owner`) matches the owner portion of `repository.full_name` before resolving stacks, or better: pass the authenticated organization into `Handler.call` and reject/ignore any repository lookup whose owner does not match the org that was actually used to verify the signature.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two orgs: `attacker-org` (attacker-administered, webhook secret known to attacker) and `victim-org` (hosting a tracked stack `victim-org/victim-repo`).
2. POST to `/webhooks` with headers `X-Github-Event: status` and:
```json
{
  "sha": "<victim commit sha tracked by shipit>",
  "state": "success",
  "context": "ci/attacker-forced",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org's webhook_secret, raw_body)>`.
4. `WebhooksController#verify_signature` succeeds (verifies against `attacker-org`'s secret, which matches).
5. `StatusHandler#process` looks up `Commit.where(sha: ...)` independent of `repository.full_name`/owner, and creates a forged successful status on `victim-org`'s commit, potentially unlocking continuous deployment/merge-queue progression the attacker has no authorization over.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
