### Title
`Shipit::Webhooks::Handlers::StatusHandler#process` writes GitHub Status updates to commits in ANY stack sharing a SHA, without checking that the webhook's authenticated repository owns that commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no scoping to the repository that the webhook payload names and that `verify_signature` authenticated. Unlike `PushHandler` and the `pull_request/*` handlers, it never calls `Handler#stacks`, so any repository that can get a validly-signed `status` webhook delivered (i.e. its own repo, using its own installation's secret) can write a Status onto a commit belonging to a completely different tenant's stack, as long as the SHAs collide.

### Finding Description
The binding that must hold is: `repository named in payload.dig('repository','full_name') == repository owning the Commit row that gets create_status_from_github! called on it`. This binding is broken.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and verifies the HMAC signature against that organization's configured secret. This proves only that the payload was signed by *some* org/app the attacker legitimately controls (their own repo A's installation) - it says nothing about which `Commit` rows in the Shipit DB the payload is allowed to touch.
- `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, invoking `StatusHandler.call(params)` → `Handler#initialize` parses the payload into `params` (sha, state, etc.) via `ExplicitParameters`, but the schema (app/models/shipit/webhooks/handlers/status_handler.rb:7-18) does not require/validate `repository`.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. This queries across the entire `commits` table, all stacks, all repositories — it never calls `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-34), which is the mechanism (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers (e.g. `PushHandler`) use to scope mutations to the repository that was cryptographically verified.
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) unconditionally writes into `statuses` for that commit/stack, triggering `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` — i.e. it can flip a foreign stack's commit into a "success"/deployable state.

Exploit: Attacker owns repo A (`attacker/repoA`), pushes an empty-tree (or otherwise SHA-colliding/copied) commit whose SHA also exists as a `Commit` row in victim `Stack` for `victim/repoB` (e.g. a cherry-picked/vendored commit shared across repos). Attacker's own CI (or any webhook sender they control for repo A) POSTs a `status` event, correctly signed for org A, with that SHA and `state: success`. `verify_signature` passes (it's a legitimate signature for repo A). `StatusHandler#process` then finds *all* `Commit` rows with that SHA — including the one under `victim/repoB` — and writes a Status onto it, potentially marking it deployable and triggering `stack.schedule_merges` for a repository the attacker never authenticated against.

Existing guards do not close this: `verify_signature` only authenticates the org that signed the request, not the set of commits the handler is permitted to mutate; `drop_unhandled_event` and `ExplicitParameters` only validate shape of parameters, not repository ownership; there is no model validation on `Status`/`Commit` tying the written status to the payload's `repository.full_name`.

### Impact Explanation
A payload authenticated for repository A causes a Status write on a Commit belonging to Stack of repository B — this is exactly the "payload for one repository mutating another's stack/commit" Critical category. It can flip `deployable?`/`blocked?` computation for the victim commit and trigger `stack.schedule_merges`, potentially enabling continuous deployment or merge-queue behavior on a tenant's stack that the attacker doesn't own. This is repeatable against any commit SHA that happens to be shared across repositories (common with cherry-picks, monorepo forks, vendored subtree merges, or empty/trivial commits with identical trees), and requires no privilege beyond owning a repo whose webhooks point at the shared Shipit instance.

### Likelihood Explanation
Preconditions: a Shipit deployment hosting multiple tenants/repositories where an attacker controls at least one onboarded repository (or its webhook delivery), and a SHA collision exists between the attacker's commit and a victim's commit row (achievable deliberately via git commit-hash crafting - amount of entropy in a git SHA does allow this to be engineered in adversarial scenarios such as identical empty trees/messages/timestamps, or naturally via shared history). Attacker cost is low: create/push a commit in their own repo, let a signed `status` webhook fire (or forge one via their own CI integration) for that SHA. Fully repeatable per matching SHA.

### Recommendation
In `StatusHandler#process`, scope the lookup to commits belonging to the verified repository's stacks, e.g. replace `Commit.where(sha: params.sha)` with `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the inherited `Handler#stacks`/`repository_name` binding the same way `PushHandler` does, so a Status is only ever written for commits under the repository that signed the webhook.

       }

  assert_response :ok
  # BROKEN BINDING: repository named in payload ('attacker/repoA') != repository owning victim_commit ('victim/repoB')

end
