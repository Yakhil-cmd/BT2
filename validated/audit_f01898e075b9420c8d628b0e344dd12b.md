### Title
CCMenu API leaks deploy state of stacks outside a token's authorized scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` may only see the single `Stack` it is bound to, by routing every stack lookup through the scoped `stacks`/`stack` helpers. `Shipit::Api::CCMenuController` (and its URL-minting cousin) override `stack` to bypass that scoping, so any authenticated `ApiClient` — even one restricted to one stack — can read the deploy state of any other stack by supplying a different `stack_id` in the request. This mirrors the FeiPool bug class: a value that gates access (`ApiClient#stack_id`) is checked for permission *type* but never re-verified against the *object* actually acted upon, letting an authenticated-but-limited actor act outside its authorized boundary.

### Finding Description
`Shipit::Api::BaseController` defines the authoritative scoping contract for API access: [1](#0-0) 

Here, `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a stack (`ApiClient#stack_id` is a real, nullable `belongs_to :stack` association: [2](#0-1) ). Every controller that relies on the inherited `stack`/`stacks` methods therefore enforces the invariant `current_api_client.stack_id == accessed_stack.id` (when the client is scoped).

`CCMenuController` breaks that invariant. It defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id`: [3](#0-2) 

The `require_permission :read, :stack` before_action only checks that the client's `permissions` array contains `read:stack` — it never checks *which* stack the permission applies to: [4](#0-3) [5](#0-4) 

So a client whose `stack_id` is set to Stack A — deliberately provisioned to see only Stack A — can hit the CCMenu endpoint with an arbitrary `params[:stack_id]` for Stack B and receive Stack B's `#show` response (latest deploy/rollback id, running state, timestamps): [6](#0-5) 

That existing scoped-client behavior is exercised elsewhere in the suite (confirming scoped `ApiClient` records are a real, supported configuration, not a theoretical one): [7](#0-6) 

### Impact Explanation
This crosses the "stack a token authorizes versus a stack it touches" trust boundary: a credential deliberately restricted to one stack's data can be replayed to read another stack's deploy/build state without further authorization. This is an unauthorized read of stack state / deploy output by a scoped credential, matching the High-impact category for unauthorized read of stack state or deploy output beyond the token's authorized scope.

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token — which by design is meant to be handed to lower-trust consumers (e.g., embedding a CCMenu URL in a CI dashboard) — can trivially exploit this by changing the `stack_id` path/query parameter on a single unauthenticated-looking GET request. No privilege escalation, signature forgery, or timing race is required; it's a direct scoping omission in one controller.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (and the analogous one in `Shipit::CCMenuUrlController` if it is reachable via API-client auth) and let it inherit `BaseController#stack`, which resolves through the scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) so `current_api_client.stack_id` is always honored.

### Proof of Concept
1. Provision (or observe an existing) `ApiClient` scoped to Stack A: `ApiClient.create!(creator: user, name: 'A-only', stack: stack_a, permissions: ['read:stack'])`, matching the pattern shown in [8](#0-7) .
2. Using that client's `authentication_token` as HTTP Basic auth, request `GET /api/stacks/<stack_b_id>/ccmenu.xml` where `stack_b` is unrelated to the client.
3. `authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` succeeds (client has `read:stack`), and `stack` resolves to Stack B via `Stack.from_param!(params[:stack_id])` — bypassing the `stacks` scope — returning Stack B's latest deploy/rollback status and id in the XML response, despite the token being authorized only for Stack A.
