### Title
Webhook signature verification is bound to the payload's organization, but event handlers act on a different, unauthenticated `repository` field - allowing forged CI status/merge-triggering payloads across repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using only `params.dig('repository','owner','login')` (or `organization.login`), and then hands the **entire raw JSON body** to the event handler untouched. The handlers that consume that body (`StatusHandler`, `PushHandler`, `CheckSuiteHandler`) never re-check that the `repository`/`sha` values they act on actually belong to the organization whose secret produced the signature. This breaks the equality "organization whose secret authenticated the request == repository/commit the request is allowed to mutate."

### Finding Description
The signature check only binds the HMAC to an *organization*: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the app config (and thus `webhook_secret`) for that one org in a multi-org deployment (a documented, supported configuration in `docs/setup.md` "Using Multiple Github Applications"), and `verify_webhook_signature` computes an HMAC over the raw body using that org's secret: [3](#0-2) 

Once the signature is accepted, the raw, attacker-controlled JSON (not a sanitized/re-derived object) is dispatched unchanged to the handler: [4](#0-3) 

Crucially, `StatusHandler` resolves the target purely by `sha`, with **no repository/organization scoping at all**: [5](#0-4) 

and `PushHandler`/`CheckSuiteHandler` resolve their target stacks via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — a field independent from the `repository.owner.login` used for signature selection: [6](#0-5) [7](#0-6) [8](#0-7) 

Because `repository.owner.login` (used only to select the HMAC key) and `repository.full_name`/`sha` (used to pick the actual DB row to mutate) are two independent, attacker-supplied fields inside the same signed body, an operator of any organization onboarded to a shared Shipit instance (with its own legitimate, distinct `webhook_secret`) can produce a validly-signed payload whose `repository.owner.login` matches their own org (so the signature check passes) while its `repository.full_name`/`sha` point at a victim organization's stack/commit. The handler then acts on the victim's data with no further check that it was actually authorized by the victim's organization's key.

Concretely, `StatusHandler#process` creates a forged `Status` for any known commit `sha` anywhere in the Shipit instance: [9](#0-8) 

`Commit#create_status_from_github!` → `Commit#add_status` then reacts to the forged status by scheduling merges when the new status is `pending` or `success`: [10](#0-9) 

`ProcessMergeRequestsJob` merges any pending PR whose head commit statuses pass `all_status_checks_passed?`: [11](#0-10) [12](#0-11) 

So a forged `success` status is sufficient to satisfy `all_status_checks_passed?` and cause `merge!` to call `stack.github_api.merge_pull_request(...)` — an unauthorized merge/deploy of the victim's repository using Shipit's own GitHub App credentials.

### Impact Explanation
This is an unauthorized-deploy vector: an attacker who controls one organization onboarded to a multi-org Shipit instance (with their own legitimate `webhook_secret`, obtained lawfully when configuring their own GitHub App/webhook) can forge signed webhook payloads that impersonate CI results for a **different** organization's commits, causing Shipit to merge/deploy code that never actually passed CI, or to falsely mark commits as failing/blocking legitimate deploys. This matches the "unauthorized deploy, rollback or merge" High-impact category, and is the direct structural analog of the reported bug class: a verification step (webhook HMAC/org identity) that does not cover the field the downstream logic actually trusts (repository/commit identity), exactly as the original report describes a stake certificate check that is bypassed while the join request is still processed as if it had been validated.

### Likelihood Explanation
Exploitability requires the attacker to control at least one organization/app entry configured on the same shared multi-org Shipit deployment (a supported, documented configuration) — this is a plausible "unprivileged attacker" relative to any *other* tenant's repositories on that instance, since Shipit does not otherwise isolate the trust domains beyond this signature check. No knowledge of the victim's secret, GitHub token, or Shipit session is required; only knowledge of a target commit `sha` (public on GitHub) or a target `repository.full_name`. This is a design gap in a first-class documented feature (multiple GitHub Apps / organizations), not a hypothetical misconfiguration.

### Recommendation
Bind the verified organization to every field the handlers subsequently trust:
- After signature verification, re-derive `repository_owner` and pass it (or the resolved `GitHubApp`/org) into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization:) }`.
- In `Handler#stacks`/`repository_name`, require that `Repository.from_github_repo_name(repository_name)` belongs to `verified_organization`, rejecting/ignoring mismatches.
- In `StatusHandler`, additionally scope `Commit.where(sha: params.sha)` by the repository/organization derived from the verified webhook, not merely by `sha` globally.

### Proof of Concept
1. Configure a Shipit instance with two organizations in `github:` per `docs/setup.md` "Using Multiple Github Applications" (e.g. `AttackerOrg` and `VictimOrg`), each with a distinct `webhook_secret`, both onboarded and known to the attacker's own org's `webhook_secret` (which the attacker owns legitimately for `AttackerOrg`).
2. Attacker observes a public commit `sha` on `VictimOrg/victim-repo` tracked by the Shipit instance.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and validates successfully, since the signature was computed with `AttackerOrg`'s own secret.
6. `StatusHandler#process` matches `Commit.where(sha: "<victim-commit-sha>")` (no org check) and creates a `success` Status; `add_status` triggers `stack.schedule_merges`, and `ProcessMergeRequestsJob` can subsequently merge/deploy the victim's pending PR whose CI never actually passed.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
