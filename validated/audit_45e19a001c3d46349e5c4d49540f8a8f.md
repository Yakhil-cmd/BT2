### Title
Membership webhook signature verified against `repository.owner.login` but `Team.organization` set from unchecked `organization.login` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and its `webhook_secret`) used to validate the HMAC signature via `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` first, falling back to `params.dig('organization', 'login')` only if `repository` is absent. `Webhooks::Handlers::MembershipHandler#find_or_create_team!` independently reads `params.organization.login` (a different JSON path) to set `team.organization` when creating a new `Team`. Because these two fields are never cross-checked, a payload can be signed/verified as belonging to one organization while creating a `Team` record attributed to a different organization.

### Finding Description
The broken binding, stated explicitly: the question assumes
`organization_used_for_signature (repository_owner = params.dig('repository','owner','login'))` == `organization_trusted_for_team_creation (params.organization.login)`.

Code path:
- `WebhooksController#verify_signature` at [1](#0-0)  calls `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that organization's own `webhook_secret`.
- `repository_owner` is defined as: [2](#0-1)  — it prefers `repository.owner.login`, only falling back to `organization.login` when `repository` key is absent.
- `MembershipHandler#find_or_create_team!` reads a *different* field, `params.organization.login`, to populate `team.organization` on create: [3](#0-2) . It never reads or validates against `repository_owner`/`repository.owner.login`.
- `Shipit.github(organization:)` in a multi-tenant configuration resolves a per-organization `GitHubApp` with its own independently configured `webhook_secret`: [4](#0-3) , and `verify_webhook_signature` HMACs the raw, unparsed body against that org's secret only: [5](#0-4) .

Root cause: the HMAC signature authenticates the raw bytes of the JSON body as having come through a channel provisioned with a specific org's secret, but it says nothing about which *field* inside that body should be trusted for which purpose. The controller picks the verifying org from `repository.owner.login` while the handler picks the "owning" org from `organization.login`. Real GitHub `membership` webhook payloads never include a `repository` object, so in production these two paths only diverge if an attacker deliberately injects a `repository` key that GitHub itself would not send.

Exploit flow: an attacker who legitimately owns a tenant org `attacker-org` on this multi-org Shipit installation (and therefore knows/controls a valid `webhook_secret` for `attacker-org`, since GitHub App webhook secrets are set by whoever configures the GitHub App/webhook — here the attacker as owner of their own org) crafts a `membership` event body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "x", "slug": "x", "url": "https://example.com"},
  "organization": {"login": "real-org"},
  "member": {"login": "attacker-controlled-login"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
signed with `attacker-org`'s own secret. `verify_signature` computes `repository_owner == "attacker-org"`, loads `attacker-org`'s `GitHubApp`, and the signature check passes (it is attacker's own legitimately-provisioned secret). `MembershipHandler#process` then runs `find_or_create_team!`, which sets `team.organization = params.organization.login == "real-org"`, creating a new `Team` row claiming membership in `real-org` — despite `real-org`'s own webhook secret never having authenticated anything. The handler then calls `team.add_member(member)`, attaching an attacker-chosen `User` (looked up/created by login via `User.find_or_create_by_login!`) to that spoofed `real-org` team.

Existing guards do not prevent this: `ExplicitParameters` in `MembershipHandler` only validates presence/type of `organization.login`, `team.*`, `member.login` — it does not cross-reference `repository.owner.login`; `drop_unhandled_event` only checks the event has a handler; `force_github_authentication`/`User#authorized?` are unrelated to webhook ingestion.

### Impact Explanation
This lets an attacker who controls only their own tenant org (`attacker-org`) on a multi-org Shipit install create/mutate `Team` records falsely attributed to another org (`real-org`) that never authenticated the request, and add an attacker-controlled GitHub login as a member of that team. If `real-org/<slug>` matches an entry in the operator's `oauth.teams` configuration (i.e. is one of `Shipit.github_teams`), this membership record directly feeds `User#authorized?` at [6](#0-5) , which grants Shipit-wide authorization based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`. This is a cross-tenant record-mutation (a payload verified for one org mutating another org's `Team`) and, when the fabricated team maps to a real authorization-relevant team, an authentication/authorization bypass — matching the Critical "payload for one repository mutating another repository's ... team" and the High "escalation into `Shipit.github_teams` authorization" categories.

### Likelihood Explanation
Requires the target Shipit instance to be configured for multiple GitHub organizations (`docs/setup.md` "Using Multiple GitHub Applications") and the attacker to be one of the already-onboarded tenant orgs with their own valid webhook secret — this is a real precondition set by the operator, not something arbitrary internet attackers can self-provision, but it is entirely plausible in a SaaS-style multi-tenant deployment where any onboarded customer org is otherwise untrusted relative to other tenants. Given that precondition, the attack is a single crafted HTTP POST to `/webhooks` with a valid signature computed from the attacker's own secret — trivial and fully repeatable against any `Team`/organization name the attacker chooses to type into `organization.login`.

### Recommendation
In `MembershipHandler` (and any other handler that reads an org/owner field independently of `WebhooksController#repository_owner`), require that `params.organization.login` (or `repository.owner.login` if present) equals the org selected during signature verification, and reject the payload otherwise — e.g. pass the verified `repository_owner` into the handler and assert equality before trusting `params.organization.login` for `team.organization`. More robustly, `repository_owner` should not silently prefer an attacker-suppliable `repository` object over `organization.login` for event types that shouldn't carry a `repository` key at all (e.g. validate expected top-level keys per `event`).

### Proof of Concept
```ruby
test ":membership from one org's secret cannot create a Team attributed to another org" do
  # Configure two orgs with distinct GitHubApp instances/secrets (as in multi-org tests)
  attacker_org = 'attacker-org'
  real_org = 'real-org'

  payload = {
    action: 'added',
    team: { id: 4242, name: 'Spoofed', slug: 'spoofed', url: 'https://example.com' },
    organization: { login: real_org },
    member: { login: 'mallory' },
    repository: { owner: { login: attacker_org } }
  }.to_json

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)}"

  # Signature verification uses repository.owner.login == attacker-org, and succeeds with attacker's own secret
  assert_difference -> { Shipit::Team.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  team = Shipit::Team.order(:id).last
  # BROKEN BINDING: team.organization ends up as real_org despite real_org never verifying anything
  assert_equal real_org, team.organization
  assert_not_equal attacker_org, team.organization
end
```
This demonstrates the divergence: signature verification is bound to `attacker-org` (which authenticated the request) while the resulting `Team.organization` is bound to `real-org` (which did not), with no code path enforcing that these two values match.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
