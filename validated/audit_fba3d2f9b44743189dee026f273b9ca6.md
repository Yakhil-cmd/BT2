### Title
Asset definer's `asset_attestors` update can permanently freeze already-held units of a `spender_attested` asset - (File: `validation.js`, `storage.js`)

### Summary
For assets defined with `spender_attested: true`, the asset definer can update the attestor list at any time via an `asset_attestors` message. `readAsset()` in `storage.js` always looks up the *most recent* attestor-list-defining unit and uses only that current set of attestor addresses to decide whether an address is "attested." Every subsequent payment from that asset re-checks `owner_address` against this always-current attestor set. There is no mechanism to preserve spendability for holders who received/hold coins while attested under a *previous* attestor list. If the definer swaps or narrows the attestor list, holders who are no longer attested under the new list have their existing, validly-held balances permanently frozen — mirroring the reported bug where `unregisterSingularity()` deletes registry state (`activeSingularities`) without checking for currently-locked positions, stranding user funds that depended on that state.

There is no historical/point-in-time attestor snapshot tied to when a holder actually received the funds; the check is always against whatever attestor list is currently in force. Consequently, exactly like `unregisterSingularity()` deleting `activeSingularities[]` while `totalDeposited` (locked positions) is nonzero, the definer's `asset_attestors` update mutates the shared registry state (`objAsset.arrAttestorAddresses`) that existing balances depend on, with no check that all current holders remain attested under the new list.

### Impact Explanation
Any holder of a `spender_attested` asset whose attestation was issued by an attestor that gets removed (or who was simply never attested by a newly added/sole attestor) becomes permanently unable to spend, transfer, or (for non-transferrable assets) even return their tokens to the definer, because every payment path requires the current owner address to be in `arrAttestedAddresses`. This is a fund-freezing bug: legitimately acquired, previously-spendable balances become unspendable through no fault or action of the holder, purely as a side effect of a privileged administrative message (`asset_attestors`) that the protocol allows the definer to send freely.

### Likelihood Explanation
The attestor list can be changed unilaterally and at will by the asset definer via a normal, single-authored `asset_attestors` message that passes validation as long as the list is well-formed (`validation.js:2033-2042`, `2829-2848`). No cooldown, no snapshotting of prior holders, and no check for existing balances is required. Any asset issuer using `spender_attested` (a documented, supported asset feature) can trigger this — intentionally (to exclude certain holders) or unintentionally (rotating attestor infrastructure) — making this readily reachable.

### Recommendation
Either (a) snapshot the attestor list that was in force when each holder's balance was created/attested and permanently grandfather those addresses for that specific balance, or (b) require the `asset_attestors` update to only add attestors (never remove) and require any removed attestor's previously-attested addresses to be automatically counted as attested under the new list (union of historical valid attestations) rather than requiring attestation under only the latest list. At minimum, the definer-only attestor update should not immediately invalidate the spendability of previously attested outstanding balances.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true`, `attestors: [Attestor1]`.
2. Attestor1 attests holder address `H`; `H` receives a payment in asset `A` (valid, spendable at the time — `arrAttestedAddresses` includes `H`).
3. Definer sends an `asset_attestors` message for asset `A` setting `attestors: [Attestor2]` (validated successfully per `validateAttestorListUpdate`, since only definer signature and list format are checked).
4. `H` attempts to spend/transfer their previously received balance. `storage.readAsset()` now resolves `arrAttestorAddresses = [Attestor2]`; `filterAttestedAddresses` finds no attestation of `H` by `Attestor2`.
5. `validatePaymentInputsAndOutputs` rejects the payment with `"owner address is not attested"` (`validation.js:2506-2507`), permanently freezing `H`'s previously valid balance with no path to spend it (short of somehow obtaining attestation from `Attestor2`, which is outside `H`'s control).

	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");

		return callback("attestor update must be a non-empty object");

			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
