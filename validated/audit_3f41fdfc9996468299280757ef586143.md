## Analysis

I found a concrete analog matching the rule's explicit binding class: "an organization that authenticated versus the repository that is written."

### Title
Webhook signature verification selects the GitHub App/secret using an attacker-controlled `repository.owner.login` field that is decoupled from the `repository.full_name` used by handlers to write data - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which configured GitHub organization's `webhook_secret` to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body, *before* the signature has been validated. The actual data-mutating handlers (`PushHandler`, `PullRequest::*Handler`, `MembershipHandler`, etc.) instead resolve the target `Repository`/`Stack`/`Team` using a *different* field of the same body, `repository.full_name`. Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank, an attacker only needs one configured organization with no `webhook_secret` set to defeat verification entirely, while still causing the handlers to act on a `repository.full_name` belonging to a different, secured stack/organization.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-30) does: [1](#0-0) 
selecting the org via `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` from the raw, unauthenticated JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` loads the config for that org via `github_app_config`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for it: [3](#0-2) 

Multi-org deployments are explicitly supported (`test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml` both show multiple orgs, each with an independently configurable/omittable `webhook_secret`): [4](#0-3) 

After `verify_signature` passes (because the attacker named the org with no secret), `WebhooksController#create` dispatches the full raw payload to handlers: [5](#0-4) 

Handlers, however, resolve the repository to act on from a *different* JSON field, `repository.full_name`, via `Handler#stacks`/`Repository.from_github_repo_name`: [6](#0-5) [7](#0-6) 

For example `PushHandler` triggers a `GithubSyncJob`-driving `sync_github` for any stack matching the branch on whatever repo `full_name` names: [8](#0-7) 
and `MembershipHandler` creates/modifies `Team`/`User` membership using `organization.login` and `member.login`, independent of the field checked for signature purposes: [9](#0-8) 

Nothing in the controller or in `Handler` enforces that `repository.owner.login` (the field the signature check is scoped to) equals the owning organization of `repository.full_name` (the field the handlers act on). The equality broken is:
`organization whose secret authenticated the request` ≠ `organization/repository the handler actually mutates`.

### Impact Explanation
If the host application configures the multi-organization GitHub App schema (`Shipit.github(organization:)`, as documented and exercised in `test/dummy/config/secrets_double_github_app.yml`) and any one configured organization is left with no `webhook_secret` (a state the sample config `config/secrets.development.shopify.yml` explicitly shows as valid/expected, `webhook_secret: # nil`), an unauthenticated network attacker can post a forged webhook naming that unsecured org as `repository.owner.login`/`organization.login` while pointing `repository.full_name` (and other identifying fields) at a stack tracked under a different, properly secured organization. This lets the attacker forge `push` (triggering sync/deploy-adjacent jobs against a real stack's branch), `pull_request` (archiving/unarchiving/provisioning review stacks), and `membership` (adding arbitrary GitHub users to `Shipit.github_teams`-backing `Team`s, which gate authorization elsewhere in the app) events for repositories they do not control. This crosses the rule's accepted impact of "escalation into `Shipit.github_teams` authorization" and "unauthorized... deploy" trigger paths, without any session, `ApiClient` token, or webhook secret.

### Likelihood Explanation
Requires only that the deployment uses the multi-organization GitHub config schema with at least one organization lacking a `webhook_secret` - a configuration explicitly modeled and shipped as an example (`config/secrets.development.shopify.yml`) and exercised in the test fixtures (`test/dummy/config/secrets_double_github_app.yml`). No credentials, GitHub App key, or prior access are needed; the request is a single unauthenticated `POST` to `/webhooks` with a crafted `X-Github-Event` header and JSON body.

### Recommendation
Bind the "organization used for signature verification" to the same identity as the "repository the handlers write to": derive both from `repository.full_name` (splitting on `/` for the owner) rather than from the separate `repository.owner.login`/`organization.login` fields, and reject the request if an organization has no `webhook_secret` configured (treat blank secret as "verification not possible" -> reject, not "always verified").

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `secured-org` (has `webhook_secret` set, owns tracked stack `secured-org/prod-app`) and `attacker-controlled-org` (left with `webhook_secret: nil`, as shown valid in `config/secrets.development.shopify.yml`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-controlled-org" },
    "full_name": "secured-org/prod-app"
  }
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `verify_signature` calls `Shipit.github(organization: "attacker-controlled-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` (`lib/shipit/github_app.rb:76-83`), bypassing verification entirely.
4. `PushHandler#process` resolves stacks via `repository.full_name = "secured-org/prod-app"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "deadbeef")` on the real, secured stack — action taken on a repository whose organization never authenticated the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
