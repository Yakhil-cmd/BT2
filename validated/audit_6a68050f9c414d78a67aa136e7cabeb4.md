### Title
Cross-tenant team escalation via decoupled signature-verification identity and business-logic identity in `WebhooksController#verify_signature` / `MembershipHandler#process` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to verify the signature based on `repository_owner`, which prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`. `MembershipHandler#process` and `find_or_create_team!`, however, use `params.organization.login` and `params.team.id` (a global `github_id`), never checking that the organization that authenticated the request is the same organization that owns the mutated `Team`. An attacker who controls a legitimate Shipit-configured org (Org-Evil) can forge a `membership` payload with a fabricated `repository.owner.login = "Org-Evil"` (satisfying signature verification) while setting `organization.login = "Org-Victim"` and `team.id` to a real Org-Victim team's `github_id`.

### Finding Description
The broken binding: the organization whose `webhook_secret` verified the request bytes (`repository_owner` in `WebhooksController#verify_signature`, [1](#0-0) ) is assumed to equal the organization that owns the `Team` record being mutated (`params.organization.login` used only on initial creation in `find_or_create_team!`, [2](#0-1) ). These are in fact two independently attacker-influenced fields of the same JSON body, with no cross-check enforced anywhere in the pipeline.

Code path:
1. `verify_signature` computes `repository_owner` by preferring `repository.owner.login`, falling back to `organization.login`, and calls `Shipit.github(organization: repository_owner)` to fetch the app/secret used in `verify_webhook_signature` [3](#0-2) .
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`. If a `Team` with that `github_id` already exists (a real Org-Victim team), the block (which would set `team.organization = params.organization.login`) never runs — the existing record is returned unchanged and unchecked against the org that signed the request [4](#0-3) .
3. `team.add_member(User.find_or_create_by_login!(params.member.login))` then unconditionally appends the attacker's own GitHub user (`params.member.login`, fully attacker-controlled) to that Org-Victim `Team`'s `memberships` [5](#0-4) .

Attacker's exact request: a `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed over the raw body using Org-Evil's own `webhook_secret` (which the attacker legitimately possesses because they administer Org-Evil), and a JSON body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "Org-Evil"}},
  "organization": {"login": "Org-Victim"},
  "team": {"id": <Org-Victim team's real github_id>, "name": "...", "slug": "...", "url": "..."},
  "member": {"login": "<attacker-github-login>"}
}
```
Since `repository.owner.login` is present and equals `Org-Evil`, `verify_signature` fetches Org-Evil's app/secret, verifies successfully (attacker signed with their own secret), and the request proceeds. `find_or_create_team!` then finds the pre-existing Org-Victim `Team` by `github_id` and returns it as-is; `team.add_member` adds the attacker.

Why existing guards fail: `drop_unhandled_event` only filters by event type, not organization; the `ExplicitParameters` schema on `MembershipHandler` only validates shape/types of `team`, `organization`, `member`, not that they're mutually consistent or consistent with the signing organization [6](#0-5) ; `verify_webhook_signature` only checks HMAC correctness against whatever `webhook_secret` was selected by `repository_owner`, and has no idea which organization the *body* claims to be about [7](#0-6) . Nothing in the controller or handler ever asserts `repository_owner == params.organization.login` or `team.organization == repository_owner`.

### Impact Explanation
A successful forgery lets an attacker, using only their own Shipit-registered organization's webhook secret, add themselves (or any GitHub login they choose to name in `member.login`, causing `User.find_or_create_by_login!` to create/target that user) as a member of a `Team` belonging to a completely different, victim organization. Per `User#authorized?`, authorization checks membership against `Shipit.github_teams` [8](#0-7) , so if the targeted `Team` is one of the configured `Shipit.github_teams`, this directly grants the attacker Shipit-side authorization associated with the victim org — an escalation into `Shipit.github_teams` authorization scope. This is repeatable against any `Team` `github_id` the attacker can enumerate/guess and can be replayed for multiple victim teams from the same Org-Evil webhook secret, so the blast radius spans every tenant whose team `github_id`s become known to the attacker.

### Likelihood Explanation
Preconditions: the attacker must operate at least one org onboarded to Shipit with a configured `webhook_secret` (a realistic bar — the same "attacker owns Org-Evil" scenario as described), and must know or guess the numeric `github_id` of the target Org-Victim `Team` (team IDs can leak via various public GitHub surfaces, e.g., PR "requested team reviewers" payloads, org-team API responses if teams are visible, or prior legitimate interaction). No Shipit secrets, sessions, or privileged roles are required — the attacker only ever uses their own webhook secret. The attack is a single crafted HTTP POST, fully repeatable, with no rate limiting relevant to the bypass.

### Recommendation
In `WebhooksController#verify_signature`, do not let `repository.owner.login` silently override `organization.login` for events (like `membership`) that are organization-scoped; instead derive `repository_owner` consistently per event type, or verify that both fields (when present) agree. Additionally, `MembershipHandler#find_or_create_team!` must not trust `params.team.id` alone: it should verify that the found (or newly created) `Team#organization` equals `params.organization.login`, and that `params.organization.login` matches the organization whose `webhook_secret` verified the request (i.e., pass/compare `repository_owner` into the handler and raise/reject on mismatch rather than silently mutating or returning a foreign-org `Team`).

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), no live GitHub calls:
```ruby
test ":membership from a foreign org cannot add members to another org's team" do
  victim_team = shipit_teams(:shopify_developers) # pre-existing team, e.g. organization: "shopify", github_id: 999
  evil_org_login = "org-evil"

  Shipit.stubs(:github).with(organization: evil_org_login).returns(
    stub(verify_webhook_signature: true)
  )

  body = {
    action: "added",
    repository: { owner: { login: evil_org_login } },  # used for signature app selection
    organization: { login: "org-victim" },              # organization business logic believes it's operating on
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    member: { login: "attacker-login" }
  }.to_json

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = 'sha1=<computed-with-org-evil-secret>'

  assert_no_difference -> { Team.count } do
    post :create, body:, as: :json
  end

  attacker = Shipit::User.find_by(login: "attacker-login")
  # BROKEN BINDING: repository_owner ("org-evil", the org that authenticated the request)
  # must equal victim_team.organization ("org-victim", the org owning the mutated Team)
  # for this membership row to be legitimate. It does not.
  assert Shipit::Membership.exists?(team: victim_team, user: attacker),
    "attacker was added to a team belonging to an org whose webhook_secret never signed this request"
end
```
This demonstrates a `Membership` row is created linking the attacker's user to Org-Victim's team despite Org-Evil's secret being the only one used for signature verification, proving the binding does not hold.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'

          end
        end

          end
        end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
