### Title
Attached NEAR deposit is permanently absorbed by the contract when `rlp_execute` returns early due to an in-flight transaction guard - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is `#[payable]`, meaning any caller can attach a NEAR deposit to the call. As soon as the FunctionCall action executes, the NEAR protocol credits the attached deposit into the wallet contract's account balance unconditionally, before any contract logic runs. The very first statement inside `rlp_execute` checks `self.has_in_flight_tx` and, if true, returns `PromiseOrValue::Value(...)` immediately without ever constructing an `ExecutionContext`/`CallerDeposit`, without creating any refund promise, and without emitting any transfer back to the caller.

### Finding Description
`rlp_execute` is entered with: [1](#0-0) 

If `has_in_flight_tx` is `true` (i.e., there is already a pending cross-contract call awaiting a callback from a previous `rlp_execute`), the function returns the failure `ExecuteResponse` value directly — this is a plain value return, not a `Promise`. No `Promise` is created, so no refund transfer to the predecessor is ever scheduled.

Contrast this with the only path that *does* track a refundable deposit, `inner_rlp_execute`, which builds an `ExecutionContext` from `env::attached_deposit()` and wraps it in a `CallerDeposit`: [2](#0-1) [3](#0-2) 

`CallerDeposit` is only later consumed and refunded in `rlp_execute_callback` when the downstream cross-contract call fails: [4](#0-3) 

Because the `has_in_flight_tx` check happens *before* `inner_rlp_execute`/`CallerDeposit::new` is ever invoked, any deposit attached to a call that hits this early-return branch is never tracked, never refunded, and never spent on the user's intended action. Per the NEAR Economics API, the attached deposit is deposited into the account's balance immediately when the call is made, regardless of what the contract does afterward, so the deposit is not "reverted" — it is simply absorbed into the wallet contract's own balance with no accounting trail and no path back to the sender: [5](#0-4) 

This is structurally identical to the reported Alchemix bug class: a payable entry point with an early-return guard clause that bypasses the deposit-handling/refund logic entirely, causing user funds sent to interact with the contract to be permanently stuck in the contract's balance instead of being used or returned.

### Impact Explanation
Any unprivileged relayer or user account that calls `rlp_execute` on an eth-implicit account while a previous transaction from that same account is still in flight (e.g., resubmitting because the first call appeared "stuck", or two relayers racing to submit the same signed Ethereum transaction) will have its attached NEAR deposit permanently absorbed into the wallet contract's balance. This is a permanent loss of user funds with no recovery path, matching the "Permanent freezing of funds" impact category, since the deposit never becomes part of any refund or action-execution accounting once the `has_in_flight_tx` short-circuit fires.

### Likelihood Explanation
Likelihood is low-to-medium: it requires (a) the caller to attach a nonzero deposit to `rlp_execute` (relevant for the `EOABaseTokenTransfer`/`ERC20Transfer` relayer-fee flows and any external caller who calls this method directly, as demonstrated by `test_caller_refunds`), and (b) a second call landing while a prior transaction for the same eth-implicit account is still in flight (i.e., pending its callback). Since only one in-flight transaction is allowed per wallet by design, a relayer resending a transaction that appears delayed, or two relayers racing, is a plausible occurrence — directly analogous to the "user resubmits `claim()` after it appears stuck" scenario in the original report.

### Recommendation
When `has_in_flight_tx` is `true`, do not silently swallow `env::attached_deposit()`. Either:
- Reject the call by panicking (so the whole receipt fails and the NEAR protocol's standard deposit-refund mechanism at the receipt level returns the deposit to the predecessor), or
- Explicitly check `env::attached_deposit() > NearToken::from_yoctonear(0)` and schedule a refund `Promise` back to `env::predecessor_account_id()` before returning the early `ExecuteResponse` value.

### Proof of Concept
Conceptual reproduction, mirroring the original report's structure:
1. Deploy `WalletContract` for an eth-implicit account and grant a relayer key to call `rlp_execute`.
2. Relayer submits a valid RLP transaction to `rlp_execute` with a positive `attached_deposit`; this sets `has_in_flight_tx = true` and returns a `Promise` awaiting a callback.
3. Before that callback resolves, the relayer (or another party) submits a second `rlp_execute` call, also attaching a positive deposit, for the same wallet account.
4. Because `has_in_flight_tx` is still `true`, the second call hits the early-return branch at [6](#0-5) , returning `success: false` as a plain value with no promise and no refund.
5. The wallet contract's account balance permanently increases by the second call's attached deposit, with no corresponding action performed and no refund issued to the caller — verifiable by comparing `view_account().balance` of the caller before/after, analogous to the "ETH balance after second compound" check in the original PoC.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
