### Title
Webhook signature verification binds the *organization owner login* but every event handler acts on the unchecked *repository full_name* field, allowing cross-organization stack forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (or falls back to `params.dig('organization', 'login')`). Once the signature check passes, every `Handler` subclass (push, status, check_suite, pull_request, membership) determines *which Stack/Repository to act on* using a completely different, unchecked field: `payload.dig('repository', 'full_name')` in `Handler#repository_name`. Because the raw JSON body is attacker-controlled up to producing a valid HMAC for the org whose secret they know, the `owner.login` used for authentication and the `full_name` used for authorization are never cross-validated against each other.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and verifies the HMAC signature against **that** organization's `webhook_secret`. If the attacker controls (or is a legitimate, lower-privileged member of) an organization "orgA" that has its own GitHub App/webhook secret configured in Shipit (multi-org support is explicit in `config/secrets.development.shopify.yml`), they can compute a valid `X-Hub-Signature` for any JSON body they want, because they know `orgA`'s secret.

After signature verification succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers on the raw parsed JSON. Every handler inherits `repository_name` from the base `Handler` class: [3](#0-2) 

`repository_name` is used to resolve `Repository.from_github_repo_name(repository_name)` and thereby the target `Stack`(s) that `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers act on: [4](#0-3) 

Nothing ties `payload['repository']['full_name']` back to `payload['repository']['owner']['login']` (the value used to select the verifying secret). An attacker who controls `orgA`'s webhook secret can craft a body where `repository.owner.login == "orgA"` (so the correct secret is selected and the signature check passes) while `repository.full_name == "orgB/some-repo"` (any repository/stack tracked by Shipit, belonging to a completely different organization). The signature only proves the sender knows `orgA`'s secret; it proves nothing about which repository the payload's business fields describe.

### Impact Explanation
This breaks the equality that should hold: `organization that authenticated == repository that is written`. With a valid signature for one org, an attacker can:
- Force `PushHandler` to call `stack.sync_github(expected_head_sha: params.after)` for an arbitrary Stack belonging to another organization, driving Shipit to sync/deploy state based on attacker-chosen `ref`/`after` SHA values [4](#0-3) .
- Force `StatusHandler` to write fabricated commit statuses against commits of a repository outside the authenticating org [5](#0-4) .
- Trigger `PullRequest` handlers (open/close/label/etc.) that create, archive, or unarchive `ReviewStack`s for a target org's repository, keyed only off `params.repository["full_name"]` [6](#0-5) .

Depending on downstream stack configuration (`continuous_deployment`, `ignore_ci`), a forged `push`/`status` sequence can influence whether Shipit considers a commit deployable and can drive an unauthorized deploy/rollback trigger for a repository/organization the attacker does not control — a cross-repository/cross-organization write crossing an authentication boundary, matching the "unauthorized deploy" impact criteria.

### Likelihood Explanation
Exploitation requires the attacker to already possess a valid webhook secret for *some* organization configured in the multi-tenant Shipit instance (e.g., their own org's GitHub App, which they legitimately administer) — this is a normal, low-privilege capability in multi-org Shipit deployments, not a privileged Shipit account or `ApiClient` token. No repository write access to the *target* org, no `GITHUB_TOKEN`, and no Shipit session are needed. The only extra work is crafting a POST with mismatched `repository.owner.login` vs `repository.full_name` fields and a correctly computed HMAC, which is trivial once the secret is known.

### Recommendation
Cross-validate the organization used to select the verifying secret against the organization embedded in `repository.full_name` (and any other repository-identifying fields consumed by handlers) before dispatching to handlers. Concretely, in `WebhooksController#verify_signature`/`create`, derive the target repository strictly from the same trust root as the verified organization — e.g., reject the payload if `params.dig('repository','full_name')&.split('/')&.first != repository_owner` — or scope `Handler#repository_name`/`stacks` lookups to repositories confirmed to belong to the organization whose secret validated the signature.

### Proof of Concept
1. Shipit is configured with two orgs, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret` (as supported by `config/secrets.development.shopify.yml`). Attacker administers `orgA`'s GitHub App and knows `orgA`'s `webhook_secret`. `orgB` has a Stack tracking `orgB/target-repo`.
2. Attacker builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(orgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")` [3](#0-2)  and invokes `stack.sync_github(expected_head_sha: ...)` on `orgB`'s stack — an org whose secret the attacker never knew [4](#0-3) .
