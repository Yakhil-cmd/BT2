### Title
Unbounded `account_ids` in `changes` RPC allows RocksDB prefix-scan amplification and RPC node resource exhaustion - ([File: chain/jsonrpc/src/api/changes.rs], [chain/jsonrpc-primitives/src/types/changes.rs], [chain/chain/src/store/mod.rs])

### Summary
`RpcStateChangesInBlockByTypeRequest::parse` deserializes `StateChangesRequestView::AccountChanges { account_ids }` (and the other `*_ids`-bearing variants) directly via `serde_json`/`Params::parse` with no cap on the size of the `account_ids` vector [1](#0-0) [2](#0-1) . Each entry is later fed one-by-one into `ChainStore::get_state_changes`, which performs a separate RocksDB prefix/exact scan per account id [3](#0-2) , so an attacker-controlled list size directly and linearly (or worse, given sharded fan-out) drives CPU/IO work on the serving node(s).

### Finding Description
`Params::parse` only performs generic serde deserialization of the JSON body into `StateChangesRequestView`; there is no length/size validation applied to the `account_ids: Vec<AccountId>` field before the request is dispatched to the view client [1](#0-0) . The only per-item cost that bounds this somewhat is that each `AccountId` string itself is validated/bounded in length by `AccountId`'s own parsing rules, but the *count* of ids in the array is unconstrained.

Downstream, `state_changes_request_is_empty` and `extract_target_shards` in `chain/jsonrpc/src/lib.rs` iterate the full `account_ids` list to compute target shards and to decide whether to scatter the request across shard-tracking peers [4](#0-3) . For each shard group, `filter_request_to_shard_group` again iterates the full list [5](#0-4) . Ultimately, `ChainStore::get_state_changes` loops over every `account_id` and performs one `KeyForStateChanges::from_trie_key(...).find_exact_iter(&store)` RocksDB scan per id for `AccountChanges`, and analogous prefix scans for `AllAccessKeyChanges`, `ContractCodeChanges`, and `DataChanges` [6](#0-5) . There is no cap on `account_ids.len()` anywhere in this call chain, so a request with e.g. 1,000,000 distinct (but syntactically valid) `AccountId` strings will cause the node to perform 1,000,000 sequential RocksDB lookups/scans for a single JSON-RPC call, and (per the sharded-routing logic) potentially fan this out to multiple peer nodes that track different shards.

I was unable to find any framework-level HTTP body size limit (e.g. axum `DefaultBodyLimit`/`RequestBodyLimitLayer`) configured in `chain/jsonrpc/src/lib.rs` that would cap the overall JSON payload size, nor any explicit `account_ids.len()` check anywhere in `chain/jsonrpc-primitives` for this request type — a grep across `chain/jsonrpc-primitives/src/types/*` for length/limit checks found such checks in other request types (e.g. `receipts.rs`, `view_state.rs`) but not in `changes.rs`.

### Impact Explanation
This matches the "node panic or unbounded resource use" bounty class for RPC/validator nodes. A single unauthenticated public-RPC call can force the serving node (and potentially other shard-tracking peers it forwards to) to perform an attacker-scaled number of RocksDB scans, causing sustained CPU/IO consumption and possibly OOM if results are buffered before being serialized back, effectively enabling a low-cost denial-of-service against public RPC infrastructure. It does not affect consensus, funds, or validator staking directly — the scope is limited to RPC/view-client node resource exhaustion.

### Likelihood Explanation
The attacker needs only public RPC access (no funded account, no valid transaction, no special privileges) — just the ability to send an HTTP/JSON-RPC POST with a `changes` method call containing a large `account_ids` array of syntactically valid `AccountId` strings. This is trivially and repeatably reproducible, and can be automated to generate sustained load with minimal attacker resources (the JSON payload cost of generating ids is far cheaper than the server-side RocksDB scan cost per id), making it highly likely to be practically exploitable against any RPC node exposing this endpoint without additional infrastructure-level protections (e.g. a reverse-proxy body-size limit or rate limiter) that are external to this code path.

### Recommendation
Add an explicit upper bound (e.g. a small constant such as a few hundred) on the number of `account_ids` (and `keys`, in `SingleAccessKeyChanges`) accepted in `StateChangesRequestView`/`RpcStateChangesInBlockByTypeRequest::parse`, returning a proper `RpcParseError`/`RpcStateChangesError` when exceeded. Additionally, consider enforcing an overall JSON body size limit at the axum router level (`DefaultBodyLimit`) as defense in depth, and consider adding a per-request cost/time budget or query timeout in `ChainStore::get_state_changes` to bound worst-case scan cost regardless of input validation gaps.

### Proof of Concept
Integration test plan (to be added under `chain/jsonrpc-primitives` or `test-loop-tests`):
1. Start an RPC node with a small chain state (few known accounts) via the existing test-loop harness (pattern from `test-loop-tests/src/tests/view_requests.rs`).
2. Send a `changes` RPC request with `StateChangesRequestView::AccountChanges { account_ids }` where `account_ids` contains N distinct valid-format `AccountId` strings (not necessarily existing accounts), varying N across {100, 10_000, 1_000_000}.
3. Measure wall-clock time and CPU for handling each request via `RpcRequest::parse` → `ChainStore::get_state_changes`.
4. Expected (failing) result absent a fix: response time/CPU scales linearly (or worse) with N and no error is returned for arbitrarily large N, demonstrating unbounded resource consumption; assert instead that requests with `account_ids.len()` above a defined threshold are rejected with a bounded, cheap-to-compute `RpcStateChangesError`/`RpcParseError` and that response latency remains bounded regardless of N.

/// Filters a `StateChangesRequestView` to only the accounts belonging to the
/// given shard group, returning a new sub-request for just those accounts.
fn filter_request_to_shard_group(
    request: &StateChangesRequestView,
    shard_group: &[ShardId],
    shard_layout: &ShardLayout,
) -> StateChangesRequestView {
    let shard_set: HashSet<&ShardId> = shard_group.iter().collect();
    let filter_accounts = |account_ids: &[AccountId]| -> Vec<AccountId> {
        account_ids
            .iter()
            .filter(|id| shard_set.contains(&shard_layout.account_id_to_shard_id(id)))
            .cloned()
            .collect()
    };

/// Returns `true` if the request references no accounts or keys, i.e.
/// `extract_target_shards` would return an empty set for any shard layout.
fn state_changes_request_is_empty(request: &StateChangesRequestView) -> bool {
    match request {
        StateChangesRequestView::AccountChanges { account_ids }
        | StateChangesRequestView::AllAccessKeyChanges { account_ids }
        | StateChangesRequestView::ContractCodeChanges { account_ids }
        | StateChangesRequestView::DataChanges { account_ids, .. } => account_ids.is_empty(),
        StateChangesRequestView::SingleAccessKeyChanges { keys } => keys.is_empty(),
    }
}

/// Extracts the set of target shards from a `StateChangesRequestView`.
/// Returns the unique shards the request's accounts/keys belong to. Returns
/// an empty set if the request has no accounts or keys.
fn extract_target_shards(
    request: &StateChangesRequestView,
    shard_layout: &ShardLayout,
) -> HashSet<ShardId> {
    let account_ids: &[AccountId] = match request {
        StateChangesRequestView::AccountChanges { account_ids } => account_ids,
        StateChangesRequestView::SingleAccessKeyChanges { keys } => {
            return keys
                .iter()
                .map(|k| shard_layout.account_id_to_shard_id(&k.account_id))
                .collect();
        }
        StateChangesRequestView::AllAccessKeyChanges { account_ids } => account_ids,
        StateChangesRequestView::ContractCodeChanges { account_ids } => account_ids,
        StateChangesRequestView::DataChanges { account_ids, .. } => account_ids,
    };
    account_ids.iter().map(|id| shard_layout.account_id_to_shard_id(id)).collect()
}
