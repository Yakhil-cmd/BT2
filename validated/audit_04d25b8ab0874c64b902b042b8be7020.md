## Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits by SHA alone, with no repository/stack scoping, unlike sibling handlers such as `PushHandler` and `CheckSuiteHandler` which both scope through `Handler#stacks` (which is derived from `repository.full_name` in the payload). This lets a `status` webhook that is validly signed for *any* onboarded GitHub organization write a status (e.g. `context: ci/test`, `state: success`) onto a commit record belonging to a completely unrelated stack/repository, as long as the SHA values collide (identical git objects, e.g. via fork of a public repo).

### Finding Description
The broken binding: the code assumes `commit.stack == repository_that_authenticated_the_event`, but nothing enforces it.

- `WebhooksController#verify_signature` only checks the webhook signature against `Shipit.github(organization: repository_owner)` — it validates that the request came from *some* configured GitHub organization/app installation, not that the specific `repository_name` in the payload is the one that legitimately owns the target commit. [1](#0-0) 
- `Handler#stacks` is available precisely to scope processing to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks`. [2](#0-1) 
- `PushHandler#process` and `CheckSuiteHandler#process` both correctly go through `stacks` before touching any `Commit` record. [3](#0-2) [4](#0-3) 
- `StatusHandler#process`, in contrast, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across every repository/stack in the Shipit instance. [5](#0-4) 
- `create_status_from_github!` -> `add_status` -> `statuses.replicate_from_github!(stack_id, github_status)` then writes a `Status` row tied to `commit.stack_id` (the *victim's* stack), not the attacker's. [6](#0-5) [7](#0-6) 

Exploit flow: an attacker onboarded on any organization that Shipit trusts (i.e., any org for which a `github_app`/webhook secret is configured — a normal, unprivileged tenant in a multi-org Shipit deployment) forks or otherwise obtains a repository containing the exact same commit object (same SHA1) as a commit that exists in the victim's tracked stack (trivial if the victim repo is public — forks share git object storage, so SHAs are identical). The attacker's own CI (or a direct crafted webhook, since they own that repository/org and its webhook configuration) emits a `status` event with `context: ci/test`, `state: success` for that shared SHA. This event passes `verify_signature` because it is properly signed for the attacker's own organization. `StatusHandler#process` then finds and updates the status for *every* commit row across the database sharing that SHA — including the victim's — silently rewriting the victim commit's status group and thus its `deployable?`/merge eligibility if `ci/test` is a required context there.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate that some legitimate GitHub org sent a well-formed status payload; none of them check that the payload's `repository.full_name` corresponds to the stack owning the target `Commit`, and `StatusHandler` is the only status-related handler that omits this check.

### Impact Explanation
A payload authenticated for one repository/organization is used to write a `Status` record onto another repository's commit and stack (`commit.stack_id` of the victim), potentially flipping `ci/test` to `success` and unblocking deploy/merge for attacker-controlled code the victim never actually tested — this is a cross-tenant integrity violation matching "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge" (Critical). It is repeatable against any commit whose SHA the attacker can reproduce and works across arbitrarily many victim stacks sharing that SHA.

### Likelihood Explanation
Preconditions: the attacker needs (a) a Shipit-recognized GitHub organization/app installation under their control (common in shared/multi-tenant Shipit deployments), and (b) a commit whose SHA1 matches one already present in the victim's tracked history — trivially achieved by forking a public repository, since git objects (and thus SHAs) are identical across forks. No Shipit session, API token, or secret is required beyond what the attacker's own onboarded org already legitimately has. This makes the attack cheap and repeatable.

### Recommendation
Scope `StatusHandler#process` through `stacks` (using the payload's `repository.full_name`) before touching commits, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, mirroring `PushHandler`/`CheckSuiteHandler`, so a status is only ever applied to commits belonging to the repository that authenticated the webhook.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create `stack_victim` with `repository` `victim/repo` and `ci.require` including `ci/test`; create `commit_victim` under it with `sha = "deadbeef..."`.
2. Create `stack_attacker` with `repository` `attacker/repo`; create `commit_attacker` under it with the **same** `sha = "deadbeef..."`.
3. Assert baseline: `commit_victim.state` (or its status group) does not include a successful `ci/test`, and `commit_victim.deployable?` is `false` (or whatever the pre-status baseline is) — this is the "before" side of the equality `commit.stack == repository_that_authenticated_event`.
4. Build a status webhook payload: `{ sha: "deadbeef...", state: "success", context: "ci/test", repository: { full_name: "attacker/repo", owner: { login: "attacker" } } }`.
5. Stub `Shipit.github(organization: "attacker").verify_webhook_signature` to return `true` (simulating attacker's own valid org signature).
6. POST to `/webhooks` with `X-Github-Event: status` and the payload.
7. Assert `commit_victim.reload.statuses.where(context: "ci/test", state: "success").exists?` is now `true`, and `commit_victim.deployable?` (or merge eligibility) has changed to `true`, even though the payload's `repository.full_name` was `attacker/repo`, not `victim/repo` — proving the equality is broken.
