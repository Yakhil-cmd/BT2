### Title
Cross-organization commit-status forgery via webhook signature scoped to payload org while `StatusHandler` writes unscoped by repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The engine binds webhook authenticity to the *organization named in the payload* (used to pick which `webhook_secret` verifies the HMAC), but `StatusHandler` writes commit statuses by matching a raw `sha` across the entire database with no check that the sha belongs to a stack under the organization that actually signed the request. An attacker who legitimately administers one onboarded GitHub organization can forge a `status` webhook, signed with their own organization's `webhook_secret`, that targets a commit belonging to a completely different organization's stack.

### Finding Description
`WebhooksController#verify_signature` selects the app/secret to check the HMAC against using the organization derived from the payload itself: [1](#0-0) [2](#0-1) 

This means the signature only proves "this payload was HMAC-signed with `repository_owner`'s webhook_secret" — it proves nothing about which repository/stack the payload's `sha` actually belongs to.

`StatusHandler#process` then applies the status update purely by matching `sha` globally, with no scoping to the repository/organization that produced a valid signature: [3](#0-2) 

Contrast this with the base `Handler` class, which does expose a `repository_name`/`stacks` helper scoped by `payload.dig('repository', 'full_name')` and is used by `PushHandler`, but is never consulted by `StatusHandler`: [4](#0-3) [5](#0-4) 

Shipit explicitly supports multiple GitHub organizations behind one instance, each with its own `webhook_secret`, configured by whoever administers that org's GitHub App installation: [6](#0-5) [7](#0-6) 

The broken binding, stated as an equality that should hold but doesn't:
`organization-that-authenticated (repository_owner used to pick webhook_secret and verify HMAC)` == `organization-owning-the-repository/stack that gets written (StatusHandler's target commit)`.

Before the attack: only GitHub, holding Org A's real `webhook_secret`, can produce Org A-signed payloads; those payloads are only ever expected to describe Org A's repositories.
After the attack: the org administrator of Org A (who legitimately knows Org A's own `webhook_secret` because they configured it) crafts a raw JSON body with `repository.owner.login: "orgA"` (satisfies `verify_signature`) but `sha` equal to a commit belonging to Org B's stack (a completely different, unrelated organization onboarded to the same Shipit instance). `StatusHandler` finds and updates that commit's status regardless of which organization it belongs to.

### Impact Explanation
Commit statuses (e.g. CI "success"/"failure") are used by Shipit as deploy-readiness signals for a stack. Forging a "success" status on an unreviewed/malicious commit belonging to Org B's stack — from an attacker who only has legitimate access to Org A — can satisfy required-status gating and enable an **unauthorized deploy** of that commit through Shipit's normal deploy flow, without the attacker ever holding credentials, tokens, or write access on Org B's repository or Shipit account. This matches the Critical-impact bucket of "unauthorized deploy" via a broken deployment-trust binding (authenticated organization vs. the repository actually written to).

### Likelihood Explanation
Requires only that the Shipit instance hosts more than one organization (a documented, supported configuration) and that the attacker legitimately administers one of them (an "unprivileged" attacker relative to the victim organization). The attacker needs to know a target commit `sha` in the victim stack, which is often discoverable from public repository history, PR links, or prior webhook traffic. No GitHub App private key, `ApiClient` token, or Shipit session is required — only the attacker's own organization's `webhook_secret`, which they configured themselves.

### Recommendation
`StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`) must resolve the target commit only within the set of stacks belonging to the repository named in the payload (`payload.dig('repository', 'full_name')`), and that repository's owner must match `repository_owner` used for signature verification, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
This re-establishes the invariant that the signing organization and the repository/stack being written to are the same entity.

### Proof of Concept
1. Attacker is legitimate owner/admin of `orgA`, onboarded to a shared Shipit instance, and knows `orgA`'s `webhook_secret` (they configured it during GitHub App setup).
2. Attacker crafts:
```json
{
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgA/attacker-repo"},
  "sha": "<known commit sha belonging to orgB's tracked stack>",
  "state": "success",
  "context": "ci/tests"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` and POSTs to the engine's webhook endpoint with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "orgA"`, fetches `orgA`'s app/secret, and the signature verifies successfully. [1](#0-0) 
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — finding the commit belonging to `orgB`'s stack — and applies the forged "success" status, with no verification that `orgB` matches the signing organization. [3](#0-2)
