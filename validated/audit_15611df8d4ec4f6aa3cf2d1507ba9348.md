### Title
Webhook signature-verification organization does not bind to the payload's `repository.full_name` used for dispatch, allowing cross-repository webhook spoofing on multi-organization Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC `webhook_secret`) to validate a webhook against using `repository_owner`, which is read straight out of the untrusted JSON payload (`params.dig('repository', 'owner', 'login')`). The actual event handlers, however, resolve which `Repository`/`Stack` to act on using a *different* payload field, `repository.full_name`, which is never cross-checked against `repository_owner`. In a multi-organization Shipit installation (a documented, supported configuration), this breaks the binding "organization whose secret authenticated the request" == "repository the request is allowed to act on."

### Finding Description
`verify_signature` in `WebhooksController` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up the app/secret configured for that org name in `secrets.yml` (multiple orgs are explicitly supported, see `docs/setup.md` "Using Multiple Github Applications") [2](#0-1) . The HMAC is verified with `OpenSSL::HMAC` / `SecureCompare.secure_compare` against that org's `webhook_secret` [3](#0-2) .

Once the signature passes, `WebhooksController#create` dispatches the raw parsed JSON to the registered handler for the event, with no further tie to `repository_owner`:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Every handler resolves its target repository/stack from `repository.full_name`, not from `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` uses exactly this `stacks` scope to trigger a GitHub sync for any matching, non-archived stack:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

The Pull Request handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `label_capturing_handler.rb`) all independently resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` for their `repository`/`review_stack`, again completely decoupled from `repository_owner` [7](#0-6) [8](#0-7) .

There is nothing in the controller, the `Handler` base class, or `Repository.from_github_repo_name` that requires `full_name`'s owner segment to equal `repository_owner`. Since both fields come from the same attacker-controlled JSON body, a caller who legitimately owns/administers one GitHub organization configured in Shipit (and thus knows/controls that organization's `webhook_secret`) can compute a valid `X-Hub-Signature` over a payload whose `repository.owner.login` is their own org (so `verify_signature` picks their own, known secret and passes) while setting `repository.full_name` to `"other-org/other-repo"` — a stack belonging to a different, unrelated organization also configured in the same Shipit instance.

### Impact Explanation
This breaks the trust binding "organization that authenticated the webhook" vs. "repository the webhook payload acts on." A push-webhook forger who controls only their own organization's webhook secret can:
- Force `PushHandler` to call `stack.sync_github(expected_head_sha: ...)` on stacks belonging to a completely different organization/repository configured in the same multi-org Shipit deployment, forging arbitrary `after` (head) SHAs for those foreign stacks.
- Depending on stack configuration (e.g. `continuous_deployment`), this sync can lead to unauthorized/forced deploy activity being scheduled for a repository the attacker does not own.
- Similarly spoof `pull_request` events (`opened`, `closed`, `labeled`, `unlabeled`) against foreign repositories' review stacks (archiving/unarchiving/provisioning review stacks that don't belong to the attacker's org).

This matches the required impact class of "an unauthorized deploy/rollback" and "cross-repository writes," achieved purely by an attacker who legitimately controls one organization's webhook secret within a shared Shipit instance — no `ApiClient` token, session, or GitHub App private key for the *victim* org is required.

### Likelihood Explanation
Requires:
1. Shipit configured with multiple GitHub organizations sharing one instance (a documented, supported feature, not an undocumented misuse).
2. Attacker controls (or is a member/admin of) one of those organizations, and thus can either configure/know that org's `webhook_secret`, or observe legitimate webhook deliveries for their own org to derive/replay a validly signed request for that org.
3. Attacker crafts a payload where `repository.owner.login`/`organization.login` matches their own org (to pick the right secret) but `repository.full_name` points at the victim org/repo.

Given multi-org support is a first-class, documented capability of Shipit, this is a realistic configuration, and the exploit requires no privileged credentials belonging to the victim organization — only knowledge of the victim's `owner/repo` name (public information) and control over one's own organization's app.

### Recommendation
Bind the two payload fields together before dispatch: after `verify_signature` succeeds, validate that `repository.full_name`'s owner segment (or `repository.owner.login`) matches the `repository_owner` value that was used to select and verify the signing organization, and reject the webhook (422) otherwise. Do this centrally in `WebhooksController` (or `Handler`) rather than per-handler, since every handler independently re-derives the target repository from `full_name`.

### Proof of Concept
Given a Shipit instance configured for two organizations, `attacker-org` (attacker-controlled, webhook secret known to attacker) and `victim-org` (unrelated, has a Shipit stack `victim-org/victim-repo` with `continuous_deployment` enabled):

1. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over the raw JSON body (per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` algorithm) [3](#0-2) .
3. POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature against it [9](#0-8) .
5. `create` dispatches to `PushHandler`, which resolves stacks via `repository.full_name = "victim-org/victim-repo"` [5](#0-4) , and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [6](#0-5)  — despite the request never having been signed by, or originating from, `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
