### Title
Webhook signature verification is bound to `repository.owner.login`, not to the `repository.full_name` the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App configuration (and therefore the webhook secret used to validate `X-Hub-Signature`) using `repository_owner`, which is read from the same untrusted JSON body as `params.dig('repository','owner','login')`. Every downstream webhook handler, however, resolves which `Stack`/`Repository` to mutate using a *different* field of that same body: `payload.dig('repository', 'full_name')`. Because these two fields are never required to refer to the same repository/organization, an attacker who controls (or knows the un-set secret of) any organization configured in Shipit can pick that organization's `owner.login` to pass signature verification while pointing `repository.full_name` at a completely different, "protected" repository whose stacks actually get acted upon.

### Finding Description
`WebhooksController#verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it to fetch the App config to verify with:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially passes when the selected organization has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Shipit natively supports multiple GitHub App/organization configs, and it is a documented/tested configuration that one organization can have `webhook_secret: # nil` while another has a real secret (`test/dummy/config/secrets_double_github_app.yml`, `OrgTwo`). [4](#0-3) 

Once `verify_signature` passes, `Handler#stacks`/`#repository_name` (used by every event handler, e.g. push → `GithubSyncJob`, status handlers, pull-request handlers) resolves the target repository from a **different** field of the very same attacker-supplied JSON body:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

The equality that should hold but does not is:
`organization used to select the webhook secret that authenticates the request (repository.owner.login)` == `repository whose stacks/commits are mutated (repository.full_name)`.

An attacker only needs to control (or be aware that Shipit configured with no secret for) any one organization entry to forge webhooks that act on stacks belonging to an unrelated, properly-secured organization/repository, because the two fields are read from unauthenticated, attacker-controlled JSON with no cross-check.

### Impact Explanation
Handlers driven by this forged payload can, without any credential for the target repository/org: enqueue `GithubSyncJob` for the real stack (push event) or create `CommitStatus` records for the target commit (status event), potentially satisfying `ci.require` checks and triggering Shipit's continuous-deployment auto-deploy for a real, unrelated repository/stack. This crosses the "unauthorized deploy" bar in the rules (writing to a repository's Shipit state that was not authenticated for that repository) and is a cross-repository write.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub App/organization (a supported, documented configuration) and that at least one configured organization lacks a `webhook_secret` (also a documented, valid configuration state, as shown by the `OrgTwo` fixture) or that the attacker otherwise controls one org's secret. The `WebhooksController` endpoint is unauthenticated by design (it's the GitHub webhook receiver), so no session, `ApiClient` token, or GitHub App private key is needed — only network access to POST to `/webhooks`.

### Recommendation
Verify the webhook signature using the same field that handlers use to select the target repository (`repository.full_name`, resolved to its owning organization via the local `Repository`/`Stack` records), rather than trusting the unauthenticated `repository.owner.login` field from the payload body to pick the verification secret.

### Proof of Concept
1. Configure Shipit with two organizations: `SecureOrg` (has `webhook_secret` set, hosts the real target stack `SecureOrg/app`) and `OpenOrg` (no `webhook_secret`, i.e., `nil`) — a supported multi-org configuration.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "SecureOrg/app" },
  "after": "<attacker-chosen sha reachable on SecureOrg/app>"
}
```
No valid `X-Hub-Signature` is required, since `verify_signature` looks up `Shipit.github(organization: "OpenOrg")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally.
3. `Handlers` resolve the target stack via `repository.full_name` = `SecureOrg/app`, enqueuing `GithubSyncJob`/creating a `CommitStatus` for the secured repository, despite the request never having been authenticated for `SecureOrg`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
