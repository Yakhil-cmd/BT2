### Title
`StatusHandler` writes commit statuses by bare SHA with no repository scoping, letting one authenticated repository forge `release/gate` status for another stack's commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and applies the incoming GitHub status to every matching commit, with no filter on the `repository` field from the payload, unlike every other handler in the same namespace (`PullRequest::OpenedHandler`, `ClosedHandler`, etc.) which explicitly scope lookups through `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. Combined with `Commit#deployable?`'s `stack.ignore_ci?` short-circuit and the blocking-status logic keyed on `context`, a `status` webhook that is validly signed for one GitHub organization/repository can mutate status/deployability state for a commit belonging to a completely different stack, provided the two share a SHA (e.g. a public fork sharing upstream history).

### Finding Description
The broken invariant stated by the question is: `status_webhook.repository.full_name == commit.stack.repository.full_name` should hold for any commit whose status is mutated by that webhook. In `StatusHandler`, this equality is never checked: [1](#0-0) 

The `params` schema does not even declare a `repository` field, and `process` iterates `Commit.where(sha: params.sha)` — a bare SHA lookup across the entire `commits` table, spanning all stacks/repositories — and calls `commit.create_status_from_github!(params)` on each match. Compare this to the sibling handlers under `app/models/shipit/webhooks/handlers/pull_request/*_handler.rb`, all of which resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack-scoped record, and the base `Handler#stacks` helper which does the same: [2](#0-1) [3](#0-2) 

`create_status_from_github!` writes to `statuses.replicate_from_github!(stack_id, github_status)` using `commit.stack_id` — the *found* commit's own stack, not anything derived from the attacker's payload: [4](#0-3) 

Signature verification in `WebhooksController#verify_signature` is scoped only to the *organization* that owns the payload's `repository.owner.login`, via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`: [5](#0-4) [6](#0-5) 

This proves an authentic GitHub-signed `status` event only proves the event came from *some* repository/org that GitHub validated for the app installation — it proves nothing about which SHA the status applies to being unique to that repository. Because git SHAs are content/history-addressed, a public fork of the victim's repository shares identical commit SHAs for the shared history. An attacker who owns a fork (or any repository where the app/webhook is installed, per the threat model in this audit) can call the GitHub Statuses API on their own repo/commit with `context: release/gate`, `state: success`. GitHub delivers a webhook signed with that org's real webhook secret — which passes `verify_signature` — but the JSON body's `sha` matches a commit that also exists (by content) in the victim's stack's `commits` table. `StatusHandler#process` then finds *both* commits (attacker's and victim's) via the unscoped SHA lookup and writes a `success` status attributed to the victim stack's `stack_id`.

Once written, `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is:
```
!locked? && (stack.ignore_ci? || (success? && !blocked?))
```
On a stack with `ignore_ci: true`, deployability is already independent of any status content — but the forged `release/gate` status still affects `blocked?` (`app/models/shipit/commit.rb:231-237`), which checks `stack.blocking_statuses...any?(&:blocking?)` over intervening commits, and affects `stack.schedule_merges` triggering in `add_status` (`app/models/shipit/commit.rb:379-384`) whenever `previous_status.simple_state != new_status.simple_state`. If `release/gate` is configured as a required/blocking context for the victim stack, injecting a fabricated `success` (or `failure`) unblocks or blocks merges/continuous-delivery evaluation for a commit the attacker never actually pushed to the victim's tracked repository, and does so without ever authenticating against the victim's organization or repository.

No existing guard catches this: `verify_signature` only authenticates the org that sent the request, not the repository referenced in `sha`-keyed writes; `ExplicitParameters` schema in `StatusHandler` never requires `repository`, so there's nothing to validate against; `drop_unhandled_event` and `check_if_ping` are irrelevant; there is no `stacks`/`Repository.from_github_repo_name` scoping call anywhere in `StatusHandler`.

### Impact Explanation
An attacker who authenticates a webhook for a repository/organization they control can write `Status` rows attributed to `stack_id`s belonging to unrelated victim stacks whenever a SHA collision exists (most reliably via public forks sharing upstream commit history). This is a cross-tenant write: "a payload for one repository mutating another's stack, commit ... task" — matching the Critical impact category for unauthorized deploy/merge/rollback triggering, since forged `release/gate` `success`/`failure` states can flip `blocked?` and trigger `stack.schedule_merges` for a victim stack whose repository never sent this event. The blast radius is limited to stacks/commits that share a SHA with a repository the attacker can send authenticated webhooks from — realistically any public-repo victim stack, since forks preserve SHAs for shared history.

### Likelihood Explanation
Preconditions: (1) the attacker must be able to produce a validly-signed `status` webhook — achievable by owning/forking a repository where the GitHub App/webhook integration is installed and calling GitHub's real Statuses API, which GitHub then relays as a properly signed webhook; (2) a SHA collision must exist between the attacker-controlled repo and the victim stack's commit history, trivially satisfied by forking a public victim repository; (3) the victim stack must have `release/gate` (or whatever `context`) configured as a required/blocking status for the attack to have practical effect on merges/blocking, though the underlying scoping bug exists regardless of `ignore_ci`. This requires no Shipit credentials, no `api_clients_secret`, and no privileged GitHub role — only the ability to fork a public repo and hit the GitHub Statuses API, which is low-cost and repeatable against any victim stack tracking a public repository.

### Recommendation
Scope `StatusHandler#process` to only the repository that authenticated the webhook: require `repository.full_name` in the params schema (mirroring the other handlers), resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit.where(sha: params.sha)` lookup to `commits.joins(stack: :repository).where(repositories: { id: repository.id })` (or equivalent) before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (add to `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "a status for a SHA shared with another repository does not affect a foreign stack" do
  victim_stack = create_stack(ignore_ci: true)
  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared")

  attacker_repo_payload = payload_parsed(:status)
  attacker_repo_payload["sha"] = shared_sha
  attacker_repo_payload["context"] = "release/gate"
  attacker_repo_payload["state"] = "success"
  attacker_repo_payload["repository"]["full_name"] = "attacker/unrelated-repo"

  before_status = victim_commit.reload.status.state

  StatusHandler.new(attacker_repo_payload).process

  after_status = victim_commit.reload.status.state
  assert_equal before_status, after_status,
    "status webhook authenticated for attacker/unrelated-repo must not mutate victim_stack's commit status"
end
```
Assert on both sides of the binding: `attacker_repo_payload["repository"]["full_name"] != victim_stack.repository.full_name` before processing, and `victim_commit.statuses.count` / `victim_commit.status.state` unchanged after processing, to prove the write was rejected/ignored rather than applied cross-repository. As implemented today, this test is expected to fail (the status is applied to `victim_commit` despite the mismatched `repository.full_name`), demonstrating the missing scoping guard.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
