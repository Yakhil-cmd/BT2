### Title
Attacker-controlled ref/object failures drive `git-sync` past `--max-failures` and terminate the sidecar, causing persistent sync denial - (File: main.go)

### Summary
`git-sync`'s main sync loop treats every `SyncRepo` error identically and, once a configurable failure threshold is reached, calls `os.Exit(1)`, killing the entire process. Any condition an attacker who controls the remote ref/branch history can trigger repeatedly (deleted ref, corrupted/unreachable objects that fail `git fsck`, force-pushed history that breaks fast-forward assumptions, etc.) drives `failCount` upward on every poll cycle. Because there is no differentiation between transient and terminal errors, and no backoff/degraded mode, a remote-side attacker can reliably force the sidecar to self-terminate, producing a persistent liveness/sync denial that requires external orchestrator intervention (pod restart) to recover — the git-sync analog of the `StaleOracle` liveness DoS in the reported Solidity bug.

### Finding Description
The main sync loop in `main.go` unconditionally increments a shared `failCount` on **any** error returned by `git.SyncRepo`, and exits the whole process once that counter reaches `--max-failures` (or `--init-max-failures` before the first successful sync): [1](#0-0) 

`SyncRepo` can fail for reasons entirely controlled by the upstream repository owner or anyone with push/ref-manipulation ability on the tracked remote — e.g. `fetch` failing because the ref was deleted or renamed, `rev-parse FETCH_HEAD^{}` failing, or `sanityCheckWorktree`/`sanityCheckRepo`'s `git fsck --connectivity-only` failing after a fetch of corrupted or dangling objects: [2](#0-1) [3](#0-2) [4](#0-3) 

The `getMaxFailures` closure shows there is a hard ceiling on tolerated errors — once exceeded, the process aborts entirely rather than continuing to retry indefinitely or entering a degraded/serve-last-good-state mode: [5](#0-4) 

This mirrors the reported `StaleOracle` pattern: a single unconditional gate (there, a tick-deviation check; here, a failure counter) blocks/kills the operation regardless of the *type* of failure, and the triggering condition (ref state / object graph) is attacker-influenceable via ordinary pushes to the tracked repository — no privileged access to git-sync's host is required. The existing e2e test confirms an unrecoverable exit is a designed outcome for bad-ref conditions in one-time mode, and the same code path applies to the continuous loop via `os.Exit(1)`: [6](#0-5) 

### Impact Explanation
When `--max-failures` is exceeded, `os.Exit(1)` terminates the entire `git-sync` process (not just the current sync attempt). In the typical Kubernetes sidecar deployment, this crashes the container; depending on restart policy this either causes a `CrashLoopBackOff` (repeated restarts, repeated failures if the malicious state persists) or, if the surrounding orchestration does not restart it, a permanent stop of synchronization, meaning the consuming application container silently serves stale content indefinitely (the symlink stays pointed at the last good worktree, but is never updated again) or the pod is marked not-ready via the liveness endpoint: [7](#0-6) 

This is a persistent sync denial reachable purely from actions on the remote repository (an attacker who can push/force-push/delete refs on the tracked repo, e.g. a compromised or malicious upstream, or a member with branch-delete permission), satisfying the "persistent sync denial" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high in deployments where `git-sync` tracks a branch/ref that is not fully trusted or where write access to the upstream is broader than the operators of the sidecar assume (e.g., CI-writable branches, third-party mirrors, or shared repos). Triggering requires only ordinary git operations against the remote (deleting/renaming the tracked ref, or pushing history that leaves dangling/unreachable/corrupt objects reachable via the fetched ref) — no exploitation of git-sync internals, credentials, or the host filesystem is needed. The default `--max-failures` is finite (bounded retries before exit), so sustained failure conditions are guaranteed to eventually trigger the abort path.

### Recommendation
- Distinguish terminal/config errors (e.g., malformed `--ref` flag at startup) from transient, remote-controlled errors (fetch failures, fsck failures, missing ref) and do not count the latter toward a process-terminating threshold; instead log/alert and keep retrying indefinitely with backoff.
- Avoid `os.Exit(1)` from within the steady-state sync loop for remote-triggerable conditions; prefer marking the pod not-ready (already exposed via the liveness endpoint) while continuing to retry in the background, so an orchestrator can react without losing the last-known-good published symlink.
- If a hard-exit is still desired for operational reasons, gate it behind a distinct, explicitly-remote-attributable failure class and make the threshold/behavior configurable independently from generic errors, and document that `--max-failures` should be set with awareness that it is influenceable by anyone who can affect the tracked ref/objects.

### Proof of Concept
1. Point `git-sync` at a repository/ref you can push to, with a small `--max-failures` (or default) and `--period` short enough to exhaust the counter quickly:
   `git-sync --repo=file://$REPO --ref=main --root=$ROOT --link=current --period=200ms --max-failures=3`
2. After the first successful sync, delete/rename the tracked ref on the remote (`git -C $REPO branch -D main` or force-push unrelated history that leaves the previous tip unreachable, then run `git -C $REPO gc --prune=now` to actually corrupt/remove objects the local mirror still references at the next `fsck`).
3. Observe `git.fetch` (main.go:1885) or the subsequent `git fsck --connectivity-only` sanity checks (main.go:1483, main.go:1530) fail on each poll; `failCount` increments each cycle (main.go:1057).
4. After `failCount >= maxFailures`, the process logs "too many failures, aborting" and calls `os.Exit(1)` (main.go:1059-1061), terminating the sidecar. Confirm via `assert_fail` pattern already used in `e2e::bad_ref_non_zero_exit` (test_e2e.sh:491-500) that this is a genuine full-process exit rather than a recoverable retry, and note that in continuous (non `--one-time`) mode this exit is permanent until the orchestrator restarts the container, during which the published symlink/content is never refreshed again.
