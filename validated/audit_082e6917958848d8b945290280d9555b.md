### Title
Signature verification scopes trust to a GitHub organization, not a repository — combined with unscoped `Commit.where(sha:)` lookup this lets any repo within that org's boundary write another repo's commit status - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository filter, so a validly-signed `status` webhook for one repository can write a `CommitStatus` onto a `Commit` belonging to a different `Stack`/repository if they happen to share a SHA. Signature verification (`Shipit::WebhooksController#verify_signature`) authenticates only that the payload was signed with the webhook secret configured for the GitHub organization named in `repository.owner.login`, not that it was signed for the specific repository whose stacks are being mutated, so the invariant "a status for `ci/e2e` only affects the repository that authenticated it" is not enforced by any code in this engine.

### Finding Description
The broken binding: the code should guarantee `commit.stack.repository == payload.repository`, but `StatusHandler#process` only enforces `commit.sha == payload.sha`.

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This scans every `Commit` row across every `Stack`/repository in the installation and applies the incoming `state`/`context`/`description` to all matches, then `add_status` recomputes `Status::Group` and, if the simple state changed, calls `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`, i.e. it can flip `blocked?`/`deployable?` for a stack that never received the webhook itself. [2](#0-1) [3](#0-2) 

`blocked?` is derived purely from status rows on commits in the range, without any repository check:
```ruby
def blocked?
  return false if stack.blocking_statuses.empty?
  stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
end
``` [4](#0-3) 

The only gate in front of this is `Shipit::WebhooksController#verify_signature`, which resolves trust at the **organization** level from the payload itself, not per repository:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) [6](#0-5) 

`GitHubApp#verify_webhook_signature` uses one `webhook_secret` per organization config entry (`Shipit.github_app_config(organization)`/`Shipit.github(organization:)`), and notably auto-passes if no secret is configured for that org:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [7](#0-6) [8](#0-7) 

So the strongest guarantee this engine provides is: "the sender knew the webhook secret configured for organization X (or none is configured for X)". It provides **no** guarantee that the payload's `repository.full_name` matches the repository tracked by the `Stack` owning the `Commit` being mutated. Any repository under an org with no `webhook_secret` configured for it, or any repository under an org whose secret has leaked/is reused, can produce a validly "signed" (or trivially unsigned, if unconfigured) webhook naming an arbitrary `sha` and `context`. If that SHA collides with a commit tracked by a different stack (e.g., shared history from a fork, cherry-pick, or a monorepo split into multiple `Stack`s each with their own `blocking_statuses`), `StatusHandler` writes the forged status onto that unrelated stack's commit and `blocked?`/`deployable?`/`schedule_merges` react to it — without any check that the forged payload's `repository` matches that stack's `repository`.

None of the listed guards close this gap: `verify_signature` checks organization-level HMAC only, not the specific repo; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `StatusHandler.params` validates shape (`sha`, `state`, `context`, etc.) but has no repository field to constrain the query; `force_github_authentication`/`User#authorized?`/`require_permission!` are UI/API-session concerns not applied to `/webhooks`; and no model validation on `Commit` or `Stack` ties `create_status_from_github!` to the requesting repository.

### Impact Explanation
A validly-authenticated webhook for repository A can write `CommitStatus` rows against commits that belong to a `Stack` tracking a different repository B, provided a SHA collision exists between the two repos' commit histories (realistic for forks, mirrors, or shared upstream history). Because `Stack#blocked?`/`deployable?` are computed purely from status rows on commits in the undeployed range, this can force-block or force-unblock deploys and trigger `stack.schedule_merges`/`ContinuousDeliveryJob` for a stack that repository B's own CI never reported on — matching the "payload for one repository mutating another's stack/commit" Critical impact category. The blast radius is bounded by SHA collisions actually existing across the tracked repositories in a given Shipit deployment; it is not a universal "any repo can hit any repo" primitive, but rather a scoping failure that becomes exploitable whenever two tracked stacks share commit history (forks, mirrors, split monorepos) — a common real-world Shipit topology.

### Likelihood Explanation
Preconditions: (1) the attacker must be able to get a `status` webhook accepted by `verify_signature` — this requires either controlling a repo in an org that has no `webhook_secret` configured (auto-pass) or knowing/leaking that org's webhook secret; (2) a target stack must have `blocking_statuses` configured and share a commit SHA with the repo the attacker authenticated as. Given rule constraints (attacker holds no secrets), the practical path is limited to the "no webhook_secret configured for an org" case or a genuine SHA collision across independently-owned repos, both of which are configuration-dependent rather than universally exploitable. This is a real scoping bug in the engine's authorization model (org-level trust, not repo-level), but its exploitability in a specific deployment depends on that deployment's `secrets.github` configuration and whether tracked stacks share commit history.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other webhook handlers) to the specific repository named in the payload: join `Commit` to `Stack`/`Repository` and filter `where(sha: params.sha, stacks: { repository: repo_from_payload })` instead of a bare `Commit.where(sha:)`. Additionally, require a `webhook_secret` to be configured for every organization used in production (fail closed instead of `return true unless webhook_secret`), and consider validating `payload.repository.full_name` against each matched commit's `stack.repository.full_name` before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/shipit/status_handler_test.rb` or similar, no live GitHub):
1. Create two stacks, `stack_a` (repository `attacker/repo`) and `stack_b` (repository `victim/repo`), with `stack_b.blocking_statuses = ['ci/e2e']`.
2. Create a `Commit` on `stack_a` and a `Commit` on `stack_b` with the **same** `sha` value (simulating a SHA collision/shared history), both newer than `stack_b.last_deployed_commit`.
3. Assert baseline: `stack_b.commits.find_by(sha: shared_sha).blocked? == false` (no status yet).
4. Build a `status` webhook payload with `repository.owner.login` = attacker org (configured with no `webhook_secret`, or a known test secret), `sha: shared_sha`, `context: 'ci/e2e'`, `state: 'failure'`.
5. POST to `/webhooks` with a valid `X-Hub-Signature` for the attacker org (or none, if `verify_webhook_signature` auto-passes for that org) and assert response is `200`.
6. Reload `stack_b`'s commit and assert `commit.blocked? == true` even though the payload's `repository` was `attacker/repo`, not `victim/repo` — proving `commit.stack.repository == payload.repository` was never checked, breaking the stated invariant.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
