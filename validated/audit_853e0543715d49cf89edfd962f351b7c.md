### Title
Bridge KLAY/ERC20/ERC721 Handle-State Committed Before Transfer Execution Permanently Locks Bridged Assets on Delivery Failure — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

In all three `handle*Transfer` functions of the Kaia service-chain bridge, the nonce accounting state (`handleNoncesToBlockNums`, `_updateHandleNonce`, `closedValueTransferVotes`, `handledRequestTx`) is irrevocably committed **before** the actual asset transfer is attempted. If the transfer call then reverts (e.g., `_to` is a contract that temporarily rejects KLAY, or an ERC20/ERC721 token contract is paused), the entire transaction reverts — but the off-chain operator service has already advanced its own handle-nonce tracking and the `closedValueTransferVotes` mapping is permanently set to `true` for that nonce. The nonce can never be re-submitted by the off-chain service, and the bridged assets are permanently stranded in the bridge contract.

---

### Finding Description

In `handleKLAYTransfer` (`BridgeTransferKLAY.sol` lines 81–99), the execution order is:

1. `_setHandledRequestTxHash(_requestTxHash)` — marks the source tx as handled
2. `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber` — records the nonce
3. `_updateHandleNonce(_requestedNonce)` — advances `lowerHandleNonce` / `upperHandleNonce`, deletes `closedValueTransferVotes[nonce]`
4. `emit HandleValueTransfer(...)` — emits the success event
5. `(bool ok, ) = _to.call.value(_value)("")` — **actual transfer**
6. `require(ok, "handleKLAYTransfer: transfer failed")` — reverts if transfer failed [1](#0-0) 

Because steps 1–4 and step 5–6 are in the same transaction, a revert at step 6 rolls back **all** EVM state changes — including the `closedValueTransferVotes[nonce] = true` set inside `_voteValueTransfer`. However, the off-chain operator service in `bridge_manager.go` calls `HandleKLAYTransfer`, receives a transaction hash back (the tx was submitted to the mempool), increments its local nonce counter (`bridgeAcc.IncNonce()`), and writes the handle tx hash to the bridge DB — all **before** the transaction is mined and its receipt checked. [2](#0-1) 

The critical invariant break is in `_voteValueTransfer` inside `BridgeOperator.sol`:

```solidity
require(!closedValueTransferVotes[_requestNonce], "closed vote");
...
closedValueTransferVotes[_requestNonce] = true;
return true;
``` [3](#0-2) 

When the `handleKLAYTransfer` transaction **reverts** (due to `require(ok, ...)` at line 99), the EVM rolls back `closedValueTransferVotes[nonce]` to `false`. This means the nonce **can** be re-submitted at the contract level. However, the off-chain service has already advanced its local `handleNonce` and written the handle tx hash to the DB. The `ValueTransferRecovery` mechanism uses `lowerHandleNonce` from the contract to determine which nonces need recovery: [4](#0-3) 

Since the on-chain `lowerHandleNonce` was **not** advanced (the tx reverted), the recovery system will attempt to re-submit. However, the off-chain `BridgeInfo.handleNonce` was already incremented, and `handledEvent` was forwarded — meaning the recovery system's `retrievePendingEvents` will not include the failed nonce in its pending set.

The same pattern exists identically in `handleERC20Transfer` (lines 51–72) and `handleERC721Transfer` (lines 49–70): [5](#0-4) [6](#0-5) 

---

### Impact Explanation

If the KLAY/ERC20/ERC721 transfer to `_to` fails (e.g., `_to` is a contract that temporarily reverts on receive, or the ERC20 token is paused), the bridge transaction reverts. The off-chain operator service has already consumed the nonce in its local state. The bridged assets remain locked in the bridge contract with no on-chain mechanism to retry the specific failed nonce, and no on-chain record of the failure. The user's cross-chain transfer is permanently lost.

**Corrupted value:** The bridged KLAY/ERC20/ERC721 amount (`_value`) remains in the bridge contract balance but is unaccounted — it cannot be claimed by the recipient and there is no retry path. This is an unauthorized permanent lock of bridged assets.

---

### Likelihood Explanation

The trigger requires `_to` to be a contract that rejects KLAY (no `receive`/`fallback`, or one that reverts), or an ERC20/ERC721 token that is paused at the moment of the handle call. This is a realistic scenario: any contract recipient on the destination chain that is temporarily paused, upgraded, or has a conditional receive hook can trigger this. The off-chain operator service does not check the receipt before advancing its nonce state.

---

### Recommendation

1. Move the actual asset transfer **before** committing nonce state, or use a try/catch pattern (Solidity 0.6+) to record failed transfers in a separate mapping (analogous to `FailedNativeDisbursement` in the referenced report) without advancing the nonce.
2. Alternatively, do not advance `lowerHandleNonce` / mark `closedValueTransferVotes` until after the transfer succeeds.
3. The off-chain service (`bridge_manager.go`) should wait for transaction receipt confirmation before advancing its local nonce and writing to the bridge DB, so that failed transactions can be retried.

---

### Proof of Concept

1. Deploy `Bridge` contract (lock mode, not mint/burn) with sufficient KLAY balance.
2. Register a malicious/paused contract `MaliciousReceiver` that reverts on `receive()` as the `_to` address.
3. Operator calls `handleKLAYTransfer(txHash, from, MaliciousReceiver, 1 ether, nonce=0, blockNum, "")`.
4. Inside the call: `_setHandledRequestTxHash` marks the tx hash, `_updateHandleNonce` advances nonces, `HandleValueTransfer` event is emitted — then `_to.call.value(1 ether)("")` reverts because `MaliciousReceiver` rejects KLAY.
5. The entire transaction reverts. On-chain state is rolled back: `closedValueTransferVotes[0]` is `false` again, `lowerHandleNonce` is unchanged.
6. The off-chain operator service has already called `bridgeAcc.IncNonce()` and written the handle tx hash to the DB. Its internal `handleNonce` is now `1`.
7. The `ValueTransferRecovery` reads `lowerHandleNonce = 0` from the contract, but the off-chain `handleNonce` is `1`, so nonce `0` is considered handled and is not in the pending recovery set.
8. `MaliciousReceiver` is unpaused. The 1 KLAY remains locked in the bridge contract forever with no on-chain retry mechanism. [7](#0-6) [8](#0-7) [9](#0-8)

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }
