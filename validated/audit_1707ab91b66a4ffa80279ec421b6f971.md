### Title
Truncated integer exponentiation in `calc-liq-factor-exp` causes incorrect graduated liquidation factor, allowing over-seizure of a borrower's collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` is Zest's analog to the reported `FixedPointMathLib.rpow`-only-integer-exponent bug: it only correctly evaluates the curve exponent for the fixed cases `exp == BPS` (exponent = 1) and implicitly `exp` corresponding to 0.5, and for any other fractional/non-power-of-BPS `curve-exponent` value it truncates via integer division (`/ exp BPS`), producing a mathematically wrong graduated liquidation factor. Because this factor directly drives how much penalty is applied and how much collateral is seized from a borrower's position, a liquidator can exploit the truncation to seize more of a borrower's collateral than the intended graduated-liquidation curve allows.

### Finding Description
The liquidation-factor exponentiation helper is: [1](#0-0) 

```
;; Apply curve exponent for graduated liquidation
;; liq-factor = liq-factor^alpha
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
```

`exp` is the `curve-exponent` parameter (expressed in BPS units, i.e. `BPS` = 1.0) used to scale the linear liquidation factor into a curved one (`liq-factor = liq-factor^alpha`). This is exactly the bug class from the external report: Clarity's built-in `pow` (like `FixedPointMathLib.rpow`) only accepts integer exponents. The code attempts to work around this by:
- Special-casing `exp == BPS` (alpha = 1, exact).
- For `exp > BPS`, truncating `exp / BPS` to an integer via integer division, discarding the fractional part of alpha entirely, then computing `factor^floor(alpha)`.
- For `exp < BPS`, hard-coding the calculation as if alpha were always exactly 0.5 (`sqrti(factor*BPS)`), regardless of the actual configured value (e.g., alpha = 0.3 or 0.8 all collapse to the same sqrt behavior).

This is used in the graduated liquidation pipeline: [2](#0-1) 

`calc-liq-factor-exp` feeds `liq-pct-scaled`, which in turn determines `liq-penalty` (via `calc-liq-factor-bound`) and `max-debt-usd`/collateral seized (via `calc-liq-debt-repay` and `calc-liq-collateral-repay`) for every partial/graduated liquidation of every borrower on the market.

### Impact Explanation
The victim is the borrower being liquidated; the attacker is the liquidator calling `liquidate`. The shared state is the borrower's collateral/debt position and the DAO-configured `curve-exponent` for the egroup. Because the exponent computation silently truncates for any `curve-exponent` that is not exactly `BPS` (1.0) or implicitly assumed 0.5, the resulting `liq-pct-scaled` and derived `liq-penalty`/`max-debt-usd` diverge from the value the DAO intended when calibrating the graduated liquidation curve for the egroup's risk parameters. For `exp > BPS` truncation discards the fractional part of alpha (e.g., alpha = 1.5 truncates `exp/BPS` to `1`, effectively computing `factor^1` scaled incorrectly by the extra `pow BPS (.. - 1)` denominator term), and for any `exp < BPS` other than the one value actually representing 0.5, the code silently substitutes a different exponent than configured. The practical result is a `liq-penalty`/`liq-pct-scaled` that can exceed the value the curve was designed to bound at a given LTV, causing collateral to be seized from the borrower beyond the intended graduated bound — a direct financial harm to the borrower (temporary/permanent freezing or loss of collateral beyond what governance parameters intended), realized at liquidation time without the borrower's consent or any error/revert to signal the miscalculation.

### Likelihood Explanation
Any egroup configured with a `curve-exponent` other than exactly `BPS` (1.0) triggers this miscalculation on every liquidation call against positions in that group; graduated/curved liquidation penalties are the documented intended mechanism (per the comment "Apply curve exponent for graduated liquidation"), so this is not an edge case but the normal operating path whenever the DAO sets a non-unity curve exponent, making it highly likely to be triggered in production once such an egroup is active.

### Recommendation
Replace the truncating integer-only exponentiation with a proper fixed-point power function capable of handling fractional exponents precisely (e.g., an `exp`/`ln`-based fixed-point power, or restrict `curve-exponent` to a small enumerated set of exactly-supported values with explicit validation at set-time, rejecting any other value instead of silently substituting an incorrect approximation).

### Proof of Concept
1. DAO configures an egroup with `curve-exponent = 12000` (i.e., alpha = 1.2, intending a modest sub-quadratic curve).
2. `calc-liq-factor-exp` computes `(/ exp BPS)` = `12000 / 10000` = `1` (integer division truncates 1.2 to 1), so it computes `factor^1 / BPS^0` = `factor`, effectively treating alpha as `1.0` instead of `1.2`.
3. For a borrower at an LTV where the correctly curved `liq-pct-scaled` (with true alpha = 1.2) would be lower than the linear factor, the truncated computation instead returns the full linear factor unmodified.
4. `calc-liquidation-params` then computes a higher `liq-penalty` and `max-debt-usd` than intended by the curve, via [3](#0-2) , letting the liquidator seize more collateral from the borrower than the DAO's graduated-liquidation design permits, without any revert or bounds check catching the discrepancy.

```text
;; Graduated liquidation parameter calculation
;; Combines the 4-step liquidation factor calculation into a single helper
;; Returns: { liq-pct-scaled: uint, liq-penalty: uint, max-debt-usd: uint }
(define-private (calc-liquidation-params
  (current-ltv uint)
  (ltv-liq-partial uint)
  (ltv-liq-full uint)
  (liq-penalty-min uint)
  (liq-penalty-max uint)
  (curve-exponent uint)
  (total-debt-usd uint))
  
  (let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
        (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
        (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
        (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
    {
      liq-pct-scaled: liq-pct-scaled,
      liq-penalty: liq-penalty,
      max-debt-usd: max-debt-usd
    }))
```
