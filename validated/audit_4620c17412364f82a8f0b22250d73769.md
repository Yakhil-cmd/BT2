### Title
Missing complexity charge for the oracle-address list in `data_feed()`/`in_data_feed()` formulas allows disproportionately cheap, unbounded KV-store scans - (File: `formula/validation.js`)

### Summary
The `data_feed()` and `in_data_feed()` oscript functions accept an `oracles` parameter that can list an arbitrary number of colon-separated addresses. Every listed address is looked up individually against the key-value store when the formula is evaluated. Unlike the analogous `in data feed` address-definition condition, the static complexity accounting for these formula functions does **not** charge per additional oracle address, so an AA author can make the per-evaluation cost scale with the number of addresses in the list while paying the complexity/fee cost of a single-oracle lookup.

### Finding Description
When an address definition uses `in data feed`, the validator explicitly charges one complexity point per additional oracle address: [1](#0-0) 

The equivalent formula-language validators for AA definitions do the opposite - they compute `addresses = value.split(':')` from the `oracles` parameter but explicitly leave the corresponding complexity increment commented out in both `validateDataFeed` (used by `data_feed()`) and `validateDataFeedExists` (used by `in_data_feed()`): [2](#0-1) [3](#0-2) 

At evaluation time, both functions turn the `oracles` string back into an address array and hand it to `data_feeds.js`, which iterates the array with `async.eachSeries`, performing one KV-store stream read (`dataFeedByAddressExists`/`readDataFeedByAddress`) per address: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Any user can post an AA definition (an unprivileged action) whose response formula includes `data_feed()`/`in_data_feed()` with a long `oracles` list. Because the complexity metric governs how much an AA formula "costs" (and is used to bound formula processing), omitting the per-address charge means the attacker's formula reports the same complexity as a single-oracle lookup while actually performing N sequential KV scans on every trigger. AA trigger processing is serialized through the `aa_triggers` mutex (`handleAATriggers` in `aa_composer.js`), so any unprivileged party can send a trivial payment to trigger such an AA repeatedly and force the node to perform many uncharged KV-store scans in the critical, serialized trigger-processing path.

### Impact Explanation
This mirrors the reported bug class: an attacker-controlled, effectively unbounded loop (the oracle address list) is reachable through a normal, unprivileged action (defining an AA and triggering it with ordinary payments), and the cost-accounting mechanism meant to price/limit this loop does not apply to it. Because AA trigger handling is serialized (mutex `aa_triggers`), repeated cheap triggers of such an AA can slow down or stall processing of the trigger queue for all AAs, degrading the node's ability to keep up with confirming/processing units in a timely manner - a resource-exhaustion/DoS effect on validity/processing throughput rather than a simple local revert.

### Likelihood Explanation
Likelihood is limited by practical bounds: the overall AA definition (and hence the `oracles` string) is still constrained by general unit/message size limits, so the address list cannot be truly unbounded, only large relative to what its charged complexity would suggest. The bug requires no privileged access - just posting an AA definition and sending it ordinary trigger payments - which is available to any unit poster.

### Recommendation
Charge complexity (or another cost metric) proportional to the number of addresses in the `oracles` list for both `data_feed()` and `in_data_feed()`, consistent with the `in data feed` address-definition condition in `definition.js`, i.e. re-enable and correct the commented-out `complexity += addresses.length` lines in `formula/validation.js`, and/or cap the number of oracle addresses allowed in these formula functions.

### Proof of Concept
1. Post an AA definition whose response messages compute a condition using `in_data_feed({oracles: "ADDR1:ADDR2:...:ADDRn", feed_name: "x", feed_value: "y"})` (or `data_feed(...)`) with a large `n` (bounded only by overall unit size limits, e.g. hundreds of addresses).
2. Because `validateDataFeedExists`/`validateDataFeed` do not add per-address complexity (lines commented out in `formula/validation.js`), this AA formula validates with the same complexity cost as one using a single oracle.
3. Send a trivial payment unit to this AA to trigger it. Trigger processing invokes `dataFeeds.dataFeedExists`/`readDataFeedValue`, which run `async.eachSeries` over all `n` addresses performing a KV-store stream read per address, inside the serialized `aa_triggers` mutex section of `aa_composer.js`.
4. Repeating cheap triggers amplifies the number of uncharged KV scans performed by the node in the serialized trigger-processing critical path, degrading trigger-processing throughput disproportionately to the fee/complexity paid.
