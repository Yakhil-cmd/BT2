### Title
Webhook signature verification uses an unauthenticated `repository.owner.login`/`organization.login` field to select the HMAC secret, letting an attacker forge cross-organization/cross-repository webhook events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to validate the request against by reading `repository_owner`, a value taken directly from the unauthenticated JSON body, before the HMAC signature has been checked. The signature only proves the body was signed by *some* configured organization's secret — it never proves that the `repository.full_name` acted on by the downstream handlers belongs to that same organization. This mirrors the report's bug class: a value used to select the trust/authorization context (which side/secret to check) is not itself covered by the mechanism meant to protect it.

### Finding Description
`before_action :verify_signature` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params.dig('repository','owner','login')` (attacker-controlled raw body) and used to select `Shipit.github(organization: repository_owner)`, i.e. which webhook secret is used to verify `X-Hub-Signature` for the *entire* raw body: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured (`return true unless webhook_secret`). Shipit explicitly supports (and documents) a multi-organization secrets schema where each org can have its own, optionally empty, `webhook_secret`: [4](#0-3) 

Once `verify_signature` passes, `create` dispatches the body to handlers, which resolve the target `Stack`/`Repository` from an entirely different, still-unauthenticated field — `repository.full_name` — with no cross-check that this repository's owner matches the `repository_owner` that was used to select/verify the signature: [5](#0-4) [6](#0-5) 

This is the equality that the report's bug class requires be broken and proven: **the organization whose secret authenticates the request ≠ the repository/stack whose state the handler mutates.** Concretely, if Shipit is configured for two organizations, where `OrgA` has no `webhook_secret` (or an attacker-known one) and `OrgB` is the organization actually owning stacks tracked in Shipit, an attacker can:
1. Craft a raw JSON body whose `repository.owner.login`/`organization.login` = `OrgA` (so `Shipit.github(organization: 'OrgA')` is selected and its (empty) secret trivially "verifies").
2. Set `repository.full_name` inside the very same body to `OrgB/some-tracked-repo` and any event type handled by Shipit (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.).
3. POST it to `/github/webhooks` (or the mounted path) with no valid credentials for `OrgB` at all.

The handler layer performs the actual state mutation (queue `GithubSyncJob`, create commit statuses, create/modify `Team`/`User` records via `membership`, drive `pull_request` merge-queue behavior) purely off `repository.full_name`, which was never covered by the signature check tied to `OrgA`.

### Impact Explanation
This breaks the authentication boundary the webhook signature is supposed to enforce: an attacker with no credentials for the target organization can inject fabricated GitHub events (pushes, commit statuses, pull_request events, membership/team changes) against real tracked stacks. Depending on which handler is triggered, consequences reach:
- Forged `status`/`check_suite` events can flip commit statuses used as deploy gates (`ci.require`), enabling an unauthorized deploy of a commit that never actually passed CI.
- Forged `membership` events create/attach `User`/`Team` records that feed into `Shipit.github_teams` authorization checks (`User#authorized?`), a High-severity escalation path per the accepted-impact criteria.
- Forged `push` events can trigger `GithubSyncJob`, causing Shipit's view of a stack's commit history to be resynchronized based on attacker-asserted data mapped through `sha`.

This is analogous in class (not certainty of full RCE) to the McDex bug: a value that determines *who bears responsibility* (here, which org's cryptographic secret is checked) is not the same value that determines *what state is changed* (which repository/stack), and the binding between them is never enforced, so the "loss" (state mutation) lands on the wrong, unauthenticated side.

### Likelihood Explanation
The webhook endpoint is unauthenticated by design (it must accept traffic from GitHub) and fully attacker-reachable from the public internet. Exploitation requires the multi-organization secrets configuration where at least one configured organization has no `webhook_secret` set — this is a documented, supported configuration (`webhook_secret: # nil` appears in the shipped example/dummy config and setup docs), not a misconfiguration outside the engine's own supported feature set. No repository write access, session, or `ApiClient` token is required — only knowledge of one org name that Shipit is configured for without a secret, or a leaked/guessed secret for any one of the configured organizations.

### Recommendation
After determining `repository_owner`/`organization_login` and verifying the signature against that organization's secret, cross-check that the `repository.full_name` (or `organization.login` for org-scoped events like `membership`) referenced by the payload actually belongs to that same verified organization before dispatching to handlers. Reject the webhook (422) on mismatch. Additionally, consider disallowing organizations configured with an empty/absent `webhook_secret` from being used to satisfy verification when other organizations in the same install are configured with real secrets, or require `webhook_secret` to always be present per-organization at boot instead of only per-org optionally.

### Proof of Concept
1. Configure Shipit with `secrets.yml`'s multi-org schema (as in `test/dummy/config/secrets_double_github_app.yml`), with `OrgA.webhook_secret` empty and `OrgB` (a real org with tracked stacks) having a real secret unknown to the attacker.
2. Attacker crafts:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "OrgB/tracked-repo", "owner": { "login": "OrgA" } }
}
```
3. POST to the webhooks endpoint with `X-Github-Event: push` and no `X-Hub-Signature` (or any arbitrary value) — `verify_signature` resolves `Shipit.github(organization: 'OrgA')`, whose `verify_webhook_signature` short-circuits `true` because `webhook_secret` is blank.
4. `Shipit::Webhooks.for_event('push')` runs `PushHandler`, which calls `Repository.from_github_repo_name('OrgB/tracked-repo')` and enqueues `GithubSyncJob` for that stack — a stack in an organization the attacker never authenticated against. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
