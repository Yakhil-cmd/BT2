### Title
Asset `denomination` values permitted by consensus validation exceed the 32-bit `INT` capacity of the `asset_denominations.denomination` column - (File: `validation.js`, `initial-db/byteball-sqlite.sql`, `initial-db/byteball-mysql.sql`)

### Summary
`validateAssetDefinition()` in `validation.js` allows an asset issuer to define denominations as large as `constants.MAX_CAP` (9×10¹⁵), but the persistent schema stores `denomination` as a 32-bit `INT` column (max ≈2.147×10⁹), the same class of "value accepted by application logic but too large for its storage/serialization datatype" bug described in the referenced report for `tick_spacing: u8`.

### Finding Description
When an unprivileged unit poster defines a new asset (`app: "asset"` message, divisible/non-fixed-denomination asset with an explicit `denominations` array), `validateAssetDefinition` checks each `denomInfo.denomination` with: [1](#0-0) 
only requiring it to be a positive integer not exceeding `constants.MAX_CAP`, which is defined as: [2](#0-1) 
i.e. up to 9×10¹⁵ — far beyond the 32-bit signed integer range (±2.147×10⁹).

The value is nonetheless persisted into a fixed-width `INT` column: [3](#0-2) 

The same column type is used identically across all initial-db schema variants (SQLite, SQLite-light, MySQL, MyRocks), all of which declare `denomination INT NOT NULL` in `asset_denominations`. SQLite's dynamic typing does not enforce the 32-bit boundary (values are stored losslessly regardless of declared affinity), whereas a MySQL/MyRocks-backed full node enforces the strict `INT` range and will either reject the insert or silently clamp/overflow the value on `INSERT`, depending on SQL mode. This mirrors the audited Seawater bug exactly: a value legitimately accepted by the higher-level validation/business logic cannot fit into the fixed-width datatype used to persist it.

### Impact Explanation
Because the bound enforced by consensus-level validation (`MAX_CAP` = 9×10¹⁵) is much larger than what an `INT` column can hold, a single posted unit defining an asset with `denominations: [{ denomination: <value greater than 2^31-1 and up to 9e15> }]` would be judged valid by `validation.js` logic uniformly on every node, yet would be stored inconsistently depending on the underlying storage engine (SQLite full/light nodes vs. MySQL/MyRocks-backed hubs). This causes a **node disagreement on validity/storage of an asset definition** — MySQL-backed nodes may throance an error (rejecting the unit as bad) or silently truncate the denomination (corrupting subsequent divisible-asset issuance/transfer amount checks that depend on `denomination` matching exactly), while SQLite-backed nodes accept and store the full value. This can partition the network on whether the defining unit (and any dependent issuance/transfer units referencing that denomination) is good/bad, undermining consensus on unit validity — one of the explicitly accepted high/medium impact categories (node disagreement on validity or stability).

### Likelihood Explanation
Likelihood is non-negligible: any address can post an `asset` definition message as a normal, unprivileged unit; no special permission (definer-only fee tiers, arbiter, or AA context) is required to trigger it. The only requirement is choosing a denomination value above 2,147,483,647 and at or below 9×10¹⁵, which is fully permitted by `validateAssetDefinition`'s explicit `MAX_CAP` bound. This is analogous in class and root cause (validated numeric range far exceeding storage datatype capacity) to the audited Seawater `tick_spacing: u8` finding rated Medium severity.

### Recommendation
Either (a) widen the `denomination` column in all `asset_denominations` schema files (`byteball-sqlite.sql`, `byteball-sqlite-light.sql`, `byteball-mysql.sql`, `byteball-myrocks.sql`) to `BIGINT` to match `MAX_CAP`'s true range (consistent with how `amount`/`cap` columns already use `BIGINT`), or (b) tighten the validation bound in `validateAssetDefinition` (and the AA-definition counterpart in `aa_validation.js`) so that `denomInfo.denomination` cannot exceed the actual 32-bit `INT` storage limit, ensuring the application-level bound and the physical storage datatype limit are consistent across all supported database backends.

### Proof of Concept
1. An attacker (or any unprivileged unit poster) composes and posts a valid, single-authored unit containing an `asset` message with `fixed_denominations: false` (or `true`) and `denominations: [{ denomination: 5000000000 }]` (5×10⁹, which is `> 2^31-1` but `<= constants.MAX_CAP`).
2. `validateAssetDefinition` (`validation.js:2725-2792`) accepts this value: it passes `isPositiveInteger(denomInfo.denomination)` and the `denomInfo.denomination > constants.MAX_CAP` check is false, so no error is raised.
3. On unit stabilization, the writer inserts the row into `asset_denominations` with this denomination value.
4. On a SQLite-backed node the value is stored verbatim (dynamic typing ignores the `INT` affinity's practical 32-bit limit). On a MySQL/MyRocks-backed node, the `INT NOT NULL` column enforces the 32-bit signed range; the insert either fails (making the node treat the unit as bad/unprocessable) or the value is silently truncated (per SQL mode), producing a persisted denomination that differs from what other nodes calculated as valid — a divergence in how the asset (and everything issued/transferred against it) is recognized across the network.
