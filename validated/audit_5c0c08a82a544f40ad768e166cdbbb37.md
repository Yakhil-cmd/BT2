### Title
Stack-scoped API client can read the CCMenu status of any stack, not just the stack it is authorized for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` supports being scoped to a single stack via its `stack_id` column [1](#0-0) . Every other API controller that resolves a stack from `params[:stack_id]` does so through the scoped `stacks` helper, which restricts the visible stacks to the ones the authenticated client is bound to [2](#0-1) . `Api::CCMenuController` overrides this helper and instead resolves the stack directly from the global `Stack` relation, discarding the scoping entirely [3](#0-2) .

### Finding Description
This is the same class of bug as the reported Zaros issue: a value that is supposed to be constrained by one binding (credit deposits vs. net USD issuance) is instead computed/consumed against the wrong reference, inverting the intended authorization outcome. Here the broken equality is "a stack a token authorizes" vs. "a stack it touches".

- `Api::BaseController#stack` (the method every other API controller relies on) is: `@stack ||= stacks.from_param!(params[:stack_id])`, where `stacks` is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . This is the enforcement point that binds a stack-scoped `ApiClient` to only the one stack it was issued for.
- `Api::HooksController` correctly goes through this scoped `stack`/`stacks` chain (via `stack_id` -> `stack.id`) [4](#0-3) .
- `Api::CCMenuController` instead redefines `stack` as `@stack ||= Stack.from_param!(params[:stack_id])`, bypassing `stacks` and therefore the `current_api_client.stack_id` restriction entirely [5](#0-4) .
- The controller still authenticates via `ApiClient.authenticate(params[:token])` (or Basic auth) and only checks the coarse permission `read:stack` with `require_permission :read, :stack` [6](#0-5) [7](#0-6) . `check_permissions!` only checks the permission string, not which stack it applies to [8](#0-7) .

As a result, any valid `ApiClient` credential with `read:stack` permission — even one deliberately scoped to a single stack (`stack_id` set) — can pass an arbitrary `stack_id` in the CCMenu request and receive that other stack's deploy/lock/activity status, which `HooksController` and `StacksController` correctly prevent through the same `stacks` scoping mechanism.

### Impact Explanation
This is an authorization-scope bypass: it lets a low-privilege, stack-restricted credential obtain unauthorized read access to another stack's state (deploy status, lock reason/author, activity, last build label) through `Api::CCMenuController#show`, which renders `shipit/ccmenu/project` for the target stack [9](#0-8) . This matches the "unauthenticated/unauthorized read of stack state" High-impact class called out in scope, since the trust boundary broken is exactly "a stack a token authorizes versus a stack it touches."

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token/credentials with `read:stack` permission (a normal, low-privilege API client, not an admin credential) — no repository write access or GitHub session is needed. Any deployment that issues per-stack scoped API clients (e.g., for CI integrations limited to a single stack) is exposed as soon as that client can reach the CCMenu endpoint with a different `stack_id`.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited scoped resolution (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` unscoped, so the `current_api_client.stack_id` restriction is honored the same way it is in `HooksController` and `StacksController`.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to Stack A (`stack_id = A.id`, `permissions: ["read:stack"]`).
2. Authenticate as that client (Basic auth or `?token=`) and request `GET /api/stacks/:B_stack_id/ccmenu.xml` where `B` is a different stack the client is not scoped to.
3. Observe that `Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` against all stacks (bypassing the `stacks` scope check performed in `Api::BaseController#stack`), returning Stack B's status instead of a 404/403 [5](#0-4) .
