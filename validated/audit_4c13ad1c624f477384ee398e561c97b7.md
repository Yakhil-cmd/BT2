## Analysis

The external report's bug class — trusting an ERC20/fungible-token `transfer` call's success without checking its returned boolean, so a "soft failure" (`false`/`(ok false)`) is silently treated as success — has a direct Clarity analog in `pox-5.clar`'s sBTC accounting.

### Root cause

Every sBTC movement in `pox-5.clar` follows this pattern: mutate internal state (`total-sbtc-staked`, `reserve-balance`, `protocol-bond-memberships`) *before* the transfer, then call the external `sbtc-token` contract wrapped only in `try!`:

- `unstake-sbtc`: decrements `total-sbtc-staked` and the staker's bond membership amount, then does [1](#0-0) 
- `roll-sbtc`: mutates `total-sbtc-staked` before/around the transfer [2](#0-1) 
- `transfer-from-reserve`: decrements `reserve-balance` before the transfer [3](#0-2) 
- `transfer-stranded-rewards`: identical pattern with no state guard at all [4](#0-3) 

In every case, `try!` only inspects the outer `response` for `(err ...)` — it discards the inner `bool` from `(ok bool)` without asserting it is `true`. If `sbtc-token`'s SIP-010 `transfer` implementation ever returns `(ok false)` on failure (a legal Clarity/SIP-010 return path, exactly analogous to an ERC20 token returning `false` instead of reverting), `try!` unwraps it as success and pox-5 proceeds as if the sBTC had moved, even though it never left custody (or never reached the recipient).

### Why this is in scope and non-speculative

This is pox-5's *own* handling of the sbtc-token call result that is the flaw — the rules explicitly permit citing sbtc-token usage where pox-5's own use of it is defective. The defect is structural in pox-5.clar itself: nowhere does it `asserts!` on the boolean returned by `transfer`; it only relies on `try!`'s error-path short-circuit.

### Impact

- In `unstake-sbtc`, the staker's tracked stake (`total-sbtc-staked`, bond membership `amount-sats`) is already reduced by the time the transfer executes; a soft-failed transfer leaves the sBTC custodied in pox-5 with no accounting record entitling the staker to reclaim it — a **permanent freeze of staked sBTC**.
- In `transfer-from-reserve` / `transfer-stranded-rewards`, `reserve-balance` is drained (or in the "stranded" case, no accounting exists at all) while the sBTC remains stuck in the contract, unreachable by the intended recipient — a **permanent freeze of reserve funds**.

### Title
Unchecked boolean return of sbtc-token `transfer` calls in `pox-5.clar` desynchronizes sBTC accounting from actual custody — (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar`'s sBTC-moving functions (`unstake-sbtc`, `roll-sbtc`, `transfer-from-reserve`, `transfer-stranded-rewards`) wrap the external `sbtc-token transfer` call only in `try!`, which unwraps `(ok bool)` without checking the inner boolean. A `transfer` that soft-fails with `(ok false)` instead of erroring is treated identically to a successful transfer, while pox-5 has already committed to the corresponding state decrement.

### Finding Description
`try!` in Clarity only short-circuits on `(err ...)`; for `(ok x)` it simply evaluates to `x`, discarding it if unused. Every sBTC-transfer call site in `pox-5.clar` discards this boolean ( [5](#0-4) , [6](#0-5) , [7](#0-6) , [8](#0-7) ). All of these functions perform state mutation (decrementing `total-sbtc-staked`, `reserve-balance`, or membership `amount-sats`) around the transfer, assuming that reaching the post-`try!` code means the transfer moved the funds. There is no `asserts!` re-checking the returned `bool`.

### Impact Explanation
If the `sbtc-token` contract's `transfer` ever returns `(ok false)` on a failure path (legal per SIP-010's `(response bool uint)` signature, mirroring the EURS-style ERC20 issue in the source report), pox-5's ledger (`total-sbtc-staked`, `reserve-balance`, bond membership amounts) permanently diverges from actual custodied sBTC. Stakers' or the reserve's sBTC becomes permanently frozen in the pox-5 contract with no state path to reclaim it, since the accounting that would authorize a future withdrawal has already been zeroed/decremented.

### Likelihood Explanation
This requires the deployed `sbtc-token` contract to exercise a soft-failure return path rather than erroring, which is outside the direct control of pox-5, but pox-5's design provides no defense-in-depth against it — a single non-strict `transfer` implementation (or future upgrade of the sBTC token) is sufficient to trigger the freeze across all four call sites.

### Recommendation
After every `(try! (contract-call? sbtc-token transfer ...))` in `pox-5.clar`, explicitly `asserts!` that the unwrapped boolean is `true` (e.g. `(asserts! (try! (contract-call? ...)) ERR_SBTC_TRANSFER_FAILED)`), so a soft `false` result aborts the transaction and rolls back the preceding state mutation instead of being silently accepted.

### Proof of Concept
1. Assume `sbtc-token`'s `transfer` returns `(ok false)` when, e.g., the sender's balance check fails internally without calling Clarity's native `ft-transfer?` error path.
2. Staker calls `unstake-sbtc`; pox-5 decrements `total-sbtc-staked` and the staker's `amount-sats` in `protocol-bond-memberships`, then calls `sbtc-token transfer` which returns `(ok false)`.
3. `try!` unwraps to `false` but the surrounding `try!` on the outer `as-contract?` block only checks for `err`, so execution continues; `(ok result)` is returned to the caller as success.
4. The staker's actual sBTC never left the pox-5 contract, but their tracked stake is already reduced — the sBTC is now unaccounted for and cannot be re-claimed through any pox-5 entry point.
