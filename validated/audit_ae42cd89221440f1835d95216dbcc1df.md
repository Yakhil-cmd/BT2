### Title
`review_stacks_enabled: false` does not prevent stack creation under `prevent_with_label` behavior due to `&&`/`||` precedence bug - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with the three provisioning-behavior predicates using `&&`/`||` without parentheses, so Ruby operator precedence makes `review_stacks_enabled` only gate the `allow_all?` branch. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, review stacks are created even if `review_stacks_enabled` is `false`.

### Finding Description
The binding the code should enforce is: `repository.review_stacks_enabled == false` implies `provision? == false` for all values of `provisioning_behavior`. The actual code is: [1](#0-0) 

Due to Ruby's operator precedence (`&&` binds tighter than `||`), this evaluates as:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)
```
`review_stacks_enabled` is only ANDed into the first disjunct. If an operator sets `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label` (intending to fully disable review stacks while keeping the label-based config in place, or simply misconfiguring in this order), any external, unprivileged PR author who opens a pull request without the provisioning label satisfies `(prevent_with_label? && !has_label) == true`, making `provision?` return `true` regardless of `review_stacks_enabled`.

`process` then calls `ReviewStackAdapter#find_or_create!`, which creates a real `Stack` record from attacker-controlled PR data (`params.pull_request.head.ref` as `branch`, `pr#{params.number}` as environment) and enqueues it in `Shipit::ReviewStackProvisioningQueue`, per [2](#0-1) .

None of the existing guards prevent this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?` [3](#0-2) ; there is no separate top-level check requiring `review_stacks_enabled` before evaluating behavior. The same precedence bug is also present identically in `ReopenedHandler#unarchive?` [4](#0-3) . Note that `LabeledHandler` and `UnlabeledHandler` correctly `&&` the `review_stacks_enabled` check with parenthesized behavior checks at the top level [5](#0-4) , showing the intended pattern that `OpenedHandler`/`ReopenedHandler` fail to follow.

### Impact Explanation
Any unprivileged GitHub user who can open a pull request against the affected repository can trigger creation of a `Stack` record and enqueue it for provisioning, even though the repository owner explicitly set `review_stacks_enabled: false` to disable this exact feature. Since review stack provisioning ultimately runs deploy-time commands/tasks against the created stack, this is an unauthorized task/stack creation on infrastructure the operator believed to be fully disabled, matching "a record written for a repository that did not authenticate it" / unauthorized task execution reachable by an outside contributor. The impact is scoped to repositories misconfigured this exact way (review stacks disabled + `allow_with_label` or `prevent_with_label` behavior set) and is repeatable per PR/repository matching that configuration.

### Likelihood Explanation
Requires only that a repository has `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible state, e.g., an operator previously used review stacks and then disabled the feature without resetting behavior, or set behavior before toggling the enable flag). No secrets, tokens, or privileged roles are needed by the attacker — only the ability to open a PR (or send a crafted `pull_request` "opened" webhook if signature verification is otherwise satisfied by the legitimate GitHub delivery). This is low-cost and repeatable.

### Recommendation
Add explicit parentheses/short-circuit so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
test "does not create stacks when review_stacks_enabled is false even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
This currently fails because `provision?` returns `true` despite `review_stacks_enabled == false`.
