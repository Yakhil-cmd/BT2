This confirms it: `Shipit.github` supports **multi-organization configuration**, each with its own `webhook_secret` under `secrets.github[:org_name]`, as shown in `github_app_config` and `TOP_LEVEL_GH_KEYS` at [1](#0-0) . This proves that in a multi-tenant Shipit deployment, distinct organizations each hold their own webhook secret, and the signature-check binding is genuinely `organization-authenticated ≠ repository-written`.

### Title
Webhook signature is verified against `repository.owner.login` while the actual write target is looked up from the independent, unverified `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) , [3](#0-2) . Once the signature is accepted, `WebhooksController#create` passes the entire raw JSON `params` to the registered handler, e.g. `Shipit::Webhooks::Handlers::PushHandler` [4](#0-3) . That handler resolves the target `Repository`/`Stack` using a *different* JSON field, `repository.full_name`, via `Handler#stacks` / `Handler#repository_name` [5](#0-4) , which is never cross-checked against the value used for signature verification.

### Finding Description
This is the direct analog of the Sherlock finding: a security-critical check (the insolvency/solvency check, here the HMAC signature check) is evaluated using one value (`quote.lockedValues` before adjustment / `repository.owner.login`), while the actually-executed, consequential action (opening the position with adjusted locked values / writing to a stack resolved by `repository.full_name`) is driven by a different, related-but-independent value that is not re-validated. Both `repository.owner.login` and `repository.full_name` are attacker-supplied fields inside the same unauthenticated raw JSON payload (this is a webhook endpoint reachable pre-signature-verification, and the JSON is fully attacker-controlled since HMAC is the only trust mechanism). GitHub itself always keeps these fields consistent, but nothing in `WebhooksController` enforces that `repository.full_name`'s owner segment matches `repository_owner`.

Because `Shipit.github(organization:)` supports one independent `webhook_secret` per organization key under `secrets.github` [1](#0-0) , an attacker who legitimately possesses (or has leaked/guessed) one organization's webhook secret — e.g. as a GitHub org admin who configured that organization's Shipit GitHub App — can craft a payload where:
- `repository.owner.login` = `"org-attacker-controls"` (so the signature verifies against that org's `webhook_secret`)
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler acts on a stack belonging to a completely different organization)

The equality broken is: **organization authenticated (`repository_owner` used for `verify_webhook_signature`) ≠ repository written (`repository.full_name` used by `PushHandler#stacks`/`Handler#stacks` to select the `Stack` to mutate)**.

### Impact Explanation
Exploiting this lets an attacker who controls one organization's webhook secret trigger `GithubSyncJob` on stacks belonging to an unrelated organization/repository via `PushHandler#process` → `stack.sync_github` [6](#0-5) , and `GithubSyncJob#perform` will fetch and append commits, potentially advancing the deployable commit list and enabling continuous-deployment stacks in the victim org to trigger unauthorized deploys against forged/spoofed commit data, or corrupt stack synchronization state (e.g. `mark_as_inaccessible!`) [7](#0-6) . Other handlers (`StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) are similarly reachable and use the same unauthenticated `repository.full_name` resolution, and could be used to fabricate CI statuses/check-run results or archive/unarchive review stacks belonging to a victim organization — this can enable an unauthorized deploy, satisfying the required "Critical" impact bucket.

### Likelihood Explanation
Requires the attacker to control at least one organization's `webhook_secret` in a multi-org Shipit deployment (per `github_app_config`) — this is not "no credential crossed": it is exactly the cross-repository-write class explicitly called out in the rules ("an organization that authenticated versus the repository that is written"). No GitHub App private key, `GITHUB_TOKEN`, Shipit session, or `ApiClient` token is required; only knowledge of one org's HMAC webhook secret, which is a materially different and weaker credential than the ones the rules exclude.

### Recommendation
After verifying the signature, re-derive the acting organization/repository strictly from the same trusted field used for verification (`repository_owner`), and reject/ignore any handler action where `repository.full_name`'s owner segment does not match `repository_owner`. Alternatively, verify the signature per-repository (looking up the webhook secret by the resolved `Stack`/`Repository` that the handler will actually act on) rather than by a value taken from an as-yet-unverified payload.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `org-attacker` (secret known/controlled by attacker) and `org-victim` (has a stack tracking `org-victim/some-repo`, branch `main`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/some-repo"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(org-attacker's webhook_secret, raw_body)`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-attacker")` and succeeds, per [8](#0-7) .
5. `PushHandler#process` resolves `stacks` from `repository.full_name = "org-victim/some-repo"` [5](#0-4)  and enqueues `GithubSyncJob` against `org-victim`'s stack, despite the signature only proving control of `org-attacker`'s secret.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
