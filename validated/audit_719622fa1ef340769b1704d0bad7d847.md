### Title
Attested Assets Can Be Permanently Frozen When Owner Rotates Address Definition - ([File: validation.js])

### Summary
The Vault report's bug class is: a whitelist-style check (`onlyWhitelistTransfer`) is enforced symmetrically on both `from` and `to` sides of a transfer, and re-evaluated at *spend time* rather than at *receipt time*. If the holder is later removed from the whitelist, they can no longer move funds out at all — permanent lock. Ocore's `spender_attested` asset mechanism reproduces the same root cause: attestation status is re-checked on the **input (spending) side** at validation time, using the *current* attestation state, which is invalidated whenever the address performs the ordinary, unprivileged `address_definition_change` operation.

### Finding Description
For assets defined with `spender_attested: true`, every payment message is validated by requiring that the *owner address of each spent output* currently appears in `objAsset.arrAttestedAddresses`: [1](#0-0) 
and, for private fixed-denomination coins: [2](#0-1) 

`arrAttestedAddresses` is computed by `storage.filterAttestedAddresses()`, which only counts an attestation as valid if it was posted **after** the address's most recent `address_definition_change`: [3](#0-2) 

`address_definition_change` is a standard, unprivileged message any address owner can post at any time (e.g., to rotate keys or switch to a different signing definition) — it is processed the same way as any other application message: [4](#0-3) 

Because the spend-time check (`validatePayment` → `validatePaymentInputsAndOutputs`) re-derives attestation status from scratch using the address's *current* definition-change history rather than the attestation status that was valid when the coins were received, an address that:
1. received `spender_attested` coins while properly attested, and
2. later posts an `address_definition_change` (e.g., normal key rotation) without being re-attested afterward by the trusted attestor,

permanently loses the ability to satisfy `objAsset.arrAttestedAddresses.indexOf(owner_address) !== -1` for those already-held coins. This exactly mirrors the Vault flaw: a check meant to gate *new* transfers/attestations is instead applied to *existing, already-acquired* balances, and it blocks the funds from moving in any direction — the user cannot pay a third party, cannot destroy/return to the definer, and (for divisible assets) cannot even take back change to themselves, since the output-side check in the same function also requires all output addresses (including self-change) to be attested: [5](#0-4) 

Unlike the Vault's `requestWithdraw()`, which could in principle route funds to a designated address(this) exemption, ocore has no analogous escape hatch: there is no way to "unstick" already-spender_attested coins once the owning address's post-receipt definition change invalidates its attestation, short of convincing the (possibly unavailable, unresponsive, or since-revoked) attestor to re-attest the same address after the definition change.

### Impact Explanation
Any holder of a `spender_attested` asset who performs a completely ordinary, self-serving wallet operation (rotating their address's signing definition) can inadvertently and permanently freeze their entire balance of that asset with no recovery path other than re-cooperation from the attestor. This is a fund-freezing vulnerability with Medium impact, matching the severity classification of the referenced report, because it results in genuine unauthorized-by-design loss of access to funds that were legitimately acquired and are otherwise fully owned by the address.

### Likelihood Explanation
Likelihood is realistic because `address_definition_change` is a routine, frequently used wallet feature (key rotation, switching to multisig, recovery flows) with no warning that it will strip attestation eligibility for previously received `spender_attested` assets. A user does not need any special privilege or interaction with a malicious party — a single normal transaction (definition change) by the asset holder themselves triggers the freeze on their next attempt to spend.

### Recommendation
Decouple attestation eligibility for *already-owned* outputs from the address's current definition-change history. Options:
- When checking `objAsset.spender_attested` for spending inputs (validation.js lines ~2432 and ~2506), verify attestation as of the time the output was created (or at minimum, do not invalidate attestation retroactively due to a *subsequent* definition change of the owning address), or
- If the definition-change invalidation is an intentional anti-theft safeguard, provide a re-attestation grace mechanism, or exempt spends where the input and output owner addresses are identical (self-consolidation), analogous to excluding `address(this)`/self-transfers from the Vault's whitelist check.

### Proof of Concept
1. Attestor `A` defines an asset with `spender_attested: true` and lists `A` as trusted attestor.
2. Address `U` receives some of this asset, then attestor `A` posts an `attestation` message certifying `U` (recorded in `attestations` table, tied to `main_chain_index = M1`).
3. `U`, as part of routine key management, posts an `address_definition_change` message at `main_chain_index = M2 > M1` (e.g., switching to a new key or multisig definition) — a completely unprivileged, self-authored action.
4. `U` now attempts to spend the previously received asset (e.g., to pay a merchant, or simply to move it back to themselves).
5. `validatePayment` calls `storage.loadAssetWithListOfAttestedAuthors`, which calls `filterAttestedAddresses`; because the attestation's `main_chain_index (M1)` is not `> M2` (the latest definition-change mci), `U` is filtered out of `arrAttestedAddresses`.
6. `validatePaymentInputsAndOutputs` then rejects the payment with `"owner address is not attested"` for every subsequent spend attempt by `U`, regardless of destination — the asset is permanently frozen unless attestor `A` re-attests `U` after `M2`, which `U` cannot compel and which is outside `U`'s control.

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
