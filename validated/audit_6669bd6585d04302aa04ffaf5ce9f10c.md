### Title
Cross-organization Team hijack via unscoped `github_id` lookup in `find_or_create_team!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Shipit::Team` solely by the global `github_id` field taken from the webhook payload, with no scoping to the organization that the payload/signature actually authenticated. Because `verify_signature` only proves that the request was signed with the secret belonging to the organization named in the *same* payload (`repository_owner`), an attacker who legitimately controls a low-trust organization can submit a `membership` webhook whose `organization.login` is their own org (satisfying signature verification) but whose `team.id` collides with an existing, privileged `Team` record that actually belongs to a different organization, causing that unrelated team's membership to be mutated.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`Team.find_or_create_by!(github_id: params.team.id)` should only ever return/create a `Team` where `team.organization == params.organization.login` (the organization whose secret verified the request). Instead the lookup is: [1](#0-0) 

which queries by `github_id` alone, with `organization` only assigned in the create-block used *if a new record is created*. If a `Team` row with that `github_id` already exists (created earlier by a legitimate `membership` event from the victim org), `find_or_create_by!` returns that existing, already-privileged row unchanged — regardless of which organization the current, verified request belongs to.

`verify_signature` in `Shipit::WebhooksController` derives the signing organization strictly from the payload itself: [2](#0-1)  and [3](#0-2) 

This only guarantees that the request was signed by the org named in `organization.login`/`repository.owner.login` in that same payload — it says nothing about `team.id`. Nothing downstream re-validates that `team.id` actually belongs to that organization on GitHub's side; Shipit trusts the payload's numeric `team.id` at face value in `Team#github_team=`: [4](#0-3) 

Exploit flow:
1. Attacker legitimately administers a low-trust org `evil-org` added to Shipit, and knows `evil-org`'s `webhook_secret`.
2. A privileged `Team` (e.g., `github_id: 12345`, `organization: "victim-org"`) already exists in Shipit's DB (created from a real webhook from `victim-org`).
3. Attacker POSTs to `/webhooks` a `membership` event: `organization.login: "evil-org"`, `team: {id: 12345, ...}`, `member.login: <attacker-controlled login>`, `action: "added"`, signed with `evil-org`'s known secret.
4. `verify_signature` computes `repository_owner = "evil-org"`, fetches `evil-org`'s `GitHubApp` config, and verifies successfully — the signature is valid for the org actually named in the payload.
5. `find_or_create_team!` looks up `Team` by `github_id: 12345` only, ignoring `organization.login`, and returns the pre-existing `victim-org` `Team`.
6. `team.add_member(member)` inserts a `Membership` linking the attacker-controlled user to `victim-org`'s privileged `Team`.

No existing guard catches this: `verify_signature` validates the wrong binding (payload-org ↔ secret) rather than the one that matters (payload-team ↔ payload-org ↔ existing-Team-row); `find_or_create_by!` has no compound scope; there is no model validation tying `github_id` to `organization` at write time for existing records.

### Impact Explanation
A successful request adds an arbitrary attacker-supplied GitHub login as a `Membership` of a `Shipit::Team` belonging to a completely different, higher-trust organization than the one that authenticated the request. If that team maps into `Shipit.github_teams` or otherwise grants deploy/merge authorization, this is a direct escalation path: an attacker who is unprivileged with respect to `victim-org` gains team membership recognized by Shipit for that org. This is repeatable against any organization whose privileged team's `github_id` the attacker can learn or guess, and is cross-tenant by construction — one organization's authenticated request mutates another organization's authorization-relevant record. This matches "Critical: payload for one repository/organization mutating another's team" and potentially "High: escalation into `Shipit.github_teams` authorization" depending on downstream use of `Team`.

### Likelihood Explanation
Preconditions: attacker must legitimately control at least one low-trust organization already configured in Shipit (feasible — Shipit is often self-service, e.g. adding one's own repo/org), and must know/guess the numeric GitHub `team.id` of a privileged team in the target org (team IDs are not secret and are discoverable via GitHub's API/UI for any team the attacker can see, or via team activity in public repos). No Shipit session, API token, or victim org secret is required. The attack is a single crafted HTTP POST, fully repeatable, and does not depend on race conditions or timing.

### Recommendation
Scope the team lookup/creation to the authenticated organization, not just `github_id`, e.g.:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
Additionally, enforce a uniqueness/model-level validation on `(github_id, organization)` (or reject/raise if a `github_id` already exists under a different organization) so that a payload cannot silently rebind an existing team to another org's webhook flow. Consider also validating `organization.login`/`repository_owner` consistency against the resolved `Team#organization` before allowing membership mutations.

### Proof of Concept
Minitest plan (no live GitHub):
```ruby
test "membership webhook cannot mutate a Team belonging to a different organization" do
  # Fixture: two orgs configured in Shipit's github config, each with distinct webhook_secret
  # victim-org already has a Team with github_id: 12345, organization: 'victim-org'
  victim_team = shipit_teams(:victim_privileged_team) # github_id: 12345, organization: 'victim-org'

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'Owners', slug: 'owners', url: 'https://api.github.com/teams/12345' },
    organization: { login: 'evil-org' },
    member: { login: 'attacker-login' }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', evil_org_webhook_secret, payload)

  post :create, body: payload, params: {},
       headers: { 'X-Hub-Signature' => signature, 'X-Github-Event' => 'membership', 'Content-Type' => 'application/json' }

  assert_response :ok

  # BROKEN BINDING CHECK:
  # LHS: organization that verified the signature
  authenticated_org = 'evil-org'
  # RHS: organization owning the Team that actually got mutated
  mutated_org = victim_team.reload.organization

  refute_equal authenticated_org, mutated_org, "expected orgs to differ, demonstrating the cross-org write"
  # This currently passes today (bug present): the membership was written despite the mismatch
  assert victim_team.members.exists?(login: 'attacker-login'),
    "attacker was added to victim-org's privileged team despite authenticating only as evil-org"
end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
