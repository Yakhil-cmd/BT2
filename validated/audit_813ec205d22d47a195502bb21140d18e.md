### Title
Contract-acceptance signature scope confusion allows forging peer acceptance of altered prosaic/arbiter contract terms - (File: wallet.js)

### Summary
Both `prosaic_contract_response` and `arbiter_contract_response` handlers in `wallet.js` accept a peer's `signed_message` as proof that the peer authorized/accepted a full contract offer, but the verification only checks that the signed string equals `objContract.title`, not the contract's full content (`title + text + creation_date`, i.e. `objContract.hash`) that the contract offer/acceptance is actually keyed by.

### Finding Description
This is the same bug class as CVE-2017-17847 (Enigmail): a cryptographic signature that legitimately covers only a narrow scope (an "attachment"/sub-field) is treated by the receiving logic as if it covers the entire enclosing object ("the whole message"). In ocore:

- A prosaic/arbiter contract is uniquely identified and immutably bound by `prosaic_contract.getHash()`, computed over `contract.title + contract.text + contract.creation_date`: [1](#0-0) 

- When a peer accepts a contract, they produce a `signed_message` (via `signed_message.js`'s `signMessage`) and send it back in a `prosaic_contract_response` / `arbiter_contract_response` device message.

- On receipt, `wallet.js` validates the signed package cryptographically with `signed_message.validateSignedMessage`, then performs the *business-logic binding check* — but that check only compares the signed string to `objContract.title`, not to the full contract hash/content: [2](#0-1) [3](#0-2) 

Because `validateSignedMessage` only proves that the address holder signed exactly the string in `signed_message.signed_message` [4](#0-3) , and the binding check at line 569/933 only pins that string to `objContract.title`, the signature never actually covers `objContract.text` or `objContract.creation_date`. Any signature the peer ever produced whose `signed_message` payload happens to equal the contract's `title` string (e.g. from signing an earlier/different contract offer that reused the same title, or from any other flow that lets the peer sign an attacker-chosen title string) will be accepted as valid acceptance of the *current* contract, including a locally-modified `text`/`creation_date`/terms, since those fields are never part of what was verified as signed.

This mirrors the Enigmail flaw precisely: the UI/consumer conflates "signature over this sub-string" with "signature over the entire container document" — here the container is the full contract (title+text+date), the sub-string is just the title.

### Impact Explanation
An application (or a malicious local peer / MITM at the storage layer, since `title` is attacker/peer-supplied text and not cryptographically bound to `text`) can present a `prosaic_contract_offer`/`arbiter_contract_offer` with an innocuous title but altered legal/financial `text` (e.g., changed payment terms, arbiter fee splits, or obligations) and later replay/craft a `signed_message` covering only that same `title` string to make the local wallet believe the counterparty explicitly accepted the *entire* contract terms, when in fact those additional terms were never signed. Since arbiter/prosaic contracts drive real fund transfers (shared address definitions, dispute resolution, `CHARGE_AMOUNT` deposits), this can result in disputes being resolved or funds moved under contract text the counterparty never actually authorized — a concrete unauthorized-obligation / potential fund-loss scenario for the accepting party who relies on this "accepted" signature as legal/technical proof.

### Likelihood Explanation
Exploitation requires an attacker who controls the contract offer content (title/text) presented locally, or who can capture/replay a peer's prior signed acceptance string that matches a chosen title — a plausible scenario given `title` is free-form user text under attacker's control at contract-creation time and is never bound to `text` by the signature check. This is reachable from an unprivileged counterparty in a private wallet-to-wallet "asset issuer/private-payment counterparty" style flow (arbiter/prosaic contracts are exactly the AA-like paired-party feature reachable by an unprivileged trigger sender/counterparty), matching the in-scope actor set.

### Recommendation
Change the binding check in both `prosaic_contract_response` and `arbiter_contract_response` handlers to compare the signed message against the full contract hash (`prosaic_contract.getHash(objContract)` / the arbiter contract equivalent) instead of `objContract.title` alone, and reject responses whose `signed_message` does not equal the canonical hash covering `title + text + creation_date` (and any other contract-defining fields, e.g. cosigners/amount for arbiter contracts).

### Proof of Concept
1. Party B receives a `prosaic_contract_offer` with `title = "Deal #1"`, `text = "A pays B 100 GB"`.
2. B accepts, producing `signed_message.signed_message = "Deal #1"` signed by B's key, sent as `prosaic_contract_response`.
3. Attacker (or A itself, or anyone able to modify local storage/replay) creates a new contract row with the same `title = "Deal #1"` but `text = "A pays B 100000 GB and forfeits arbitration rights"`.
4. On `prosaic_contract_response`, `wallet.js` line 569 only checks `objSignedMessage.signed_message != objContract.title`, which still passes because the title is unchanged — the altered `text` is accepted as agreed by B even though B's signature never covered it. [5](#0-4)
