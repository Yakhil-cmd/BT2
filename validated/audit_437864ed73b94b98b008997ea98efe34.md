### Title
Header-splitting regex mis-parses file paths containing " b/", desyncing reported `file_path` from the actual git-diffed path - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`extract_file_paths_from_diff` and `parse_diff_into_files` both parse the `diff --git a/<old> b/<new>` header with `re.match(r'^a/(.+?) b/(.+)$', lines[0])`, which splits at the *first* literal occurrence of `" b/"` due to the lazy `(.+?)` quantifier. If a tracked path contains a directory component ending in a space followed by `b/` (e.g. `foo b/bar.py`), the regex splits inside the real path instead of at the true `a/`↔`b/` boundary, producing a `file_path` string that does not match the path git actually diffed.

### Finding Description
Both functions build `file_path` from `header_match.group(2) or header_match.group(1) or ''`, and since `group(2)` is `(.+)` it is always non-empty on a match, so `file_path` is effectively always `group(2)` [1](#0-0) [2](#0-1) .

An attacker who controls file naming in a cloned repo (e.g. a directory literally named `"foo b"` containing a file `bar.py`, giving path `foo b/bar.py`) causes the diff header line to be `a/foo b/bar.py b/foo b/bar.py`. The lazy `(.+?)` finds the *first* `" b/"` substring — which occurs right after `"foo"`, inside the real path — rather than at the actual `a/...`↔`b/...` separator. This yields `group(1) = "foo"` and `group(2) = "bar.py b/foo b/bar.py"`, a garbled string that is neither the real old path nor the real new path. `_is_reviewable_source` operates on this corrupted string using `os.path.splitext` and basename checks [3](#0-2) ; because the corrupted string still ends with the true extension (`.py`/`.sh`/etc.) in the common non-rename case, it still evaluates as "reviewable" by extension, but the string itself no longer identifies the actual file that was modified. The diff *content* portion of `parse_diff_into_files` is extracted independently by scanning for `@@` hunk markers [4](#0-3) , so the hunk body stays correct while the label attached to it is wrong — a binding break between the reported identifier and the actual diffed content/path.

This is a real parser-invariant violation (state desync between the string used for identification/filtering/reporting and git's own name-only truth), reachable purely from attacker-controlled file names in a cloned repository, with no privilege beyond being able to name files before Claude Code diffs them.

### Impact Explanation
The mis-split degrades to path *misattribution*, not a full filtering bypass in the common case, because `group(2)` retains the tail of the line, which (absent a rename) still carries the correct trailing extension. However:
- It can still cause **misleading path reporting** to the LLM/security-reminder review output, undermining review trust and any per-path logic (e.g., the review's own `_LOW_PRIORITY_PATH_TOKENS`/`_SECURITY_RISK_PATH_TOKENS` heuristics in `_prioritize_diff_files`, which match substrings/prefixes of `file_path`) — a garbled path could dodge or falsely trigger security-risk-token weighting.
- In a **rename** scenario (`diff --git a/old_name b/new/path/with a b/hack.py`), the old and new sides can differ, and the lazy-first-match could bind `group(2)` to a hybrid string that matches neither the real old nor new path, meaning downstream consumers keying off `file_path` (dedup/allow-list/reviewed-tracking, if any exist) could be confused about which file was actually touched.
- I could not fully verify, within available context, whether `file_path` from these functions is used anywhere in `security_reminder_hook.py` for a security-gating decision (e.g., skip-once tracking, allow-listing) that would let a dangerous file evade review outright — the grep results were truncated before analysis completed. Without confirming a gating dependency on the exact string, the demonstrated impact is bounded to path misattribution/reporting corruption rather than a confirmed full bypass of `_is_reviewable_source` filtering.

### Likelihood Explanation
Precondition is simply that the attacker can create a directory or file whose repo-relative path contains a literal `" b/"` substring (e.g., a directory ending in a trailing space before a subdirectory named `b`), which is legal on Linux/macOS filesystems and via git. This requires no special privilege, only being able to add such paths to a repository that will later be cloned and diffed by Claude Code's security-guidance hook. It is fully reproducible with a crafted local repo and deterministic given the regex's lazy-quantifier semantics.

### Recommendation
Replace the ad hoc regex split with git's own unambiguous parsing:
- Use `git diff --name-only -z` / `--raw -z` (as `_git_name_only` already does elsewhere) to get NUL-delimited, unambiguous paths instead of parsing the human-readable `diff --git a/... b/...` header text.
- If the header must be parsed, anchor on the `---`/`+++` lines (which are prefixed and NUL/quote-safe with `core.quotePath=false`) rather than the free-text `diff --git` line, or handle git's own quoting of paths containing tricky characters (`core.quotePath` output) instead of a greedy/lazy regex heuristic.
- At minimum, assert `group(1)` and the tail of `group(2)` are internally consistent (e.g., cross-check against the `--- a/...` / `+++ b/...` lines that follow) before trusting the derived `file_path`.

### Proof of Concept
```python
import re

HEADER_RE = re.compile(r'^a/(.+?) b/(.+)$')

def current_parse(line):
    m = HEADER_RE.match(line)
    return (m.group(1), m.group(2)) if m else None

# Simulated diff header for a real path "foo b/bar.py" (dir "foo b", file "bar.py")
line = "diff --git a/foo b/bar.py b/foo b/bar.py"
after_prefix = line[len("diff --git "):]
result = current_parse(after_prefix)
print(result)
# Actual real path (per `git diff --name-only`) would be: "foo b/bar.py"
# Current parser yields group(1)="foo", group(2)="bar.py b/foo b/bar.py"
assert result[1] != "foo b/bar.py", "parser mis-split the header"
```

Integration-test plan:
1. Create a temp git repo, `mkdir "foo b" && printf 'x=1\n' > "foo b/bar.py"`, `git add -A && git commit`.
2. Modify `foo b/bar.py`, run `git diff --no-color` and capture real output; independently run `git diff --name-only -z` to get ground truth (`foo b/bar.py`).
3. Feed the same diff text into `extract_file_paths_from_diff` / `parse_diff_into_files`.
4. Assert the returned `file_path` equals git's `--name-only` ground truth — this assertion currently fails, demonstrating the desync.
