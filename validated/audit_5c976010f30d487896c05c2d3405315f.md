### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets a status webhook for one repository write/flip status on another stack's identically-shaed commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no repository or stack scoping, and calls `commit.create_status_from_github!` on every match. Combined with `Commit#schedule_continuous_delivery`, a `success` status on a `continuous_deployment`-enabled stack's commit can trigger an automatic ship via `ContinuousDeliveryJob`, so a status event that is properly authenticated for repository A can flip deployability for a completely unrelated stack B if the two happen to share a commit SHA (e.g., a fork of a public repo).

### Finding Description
The broken binding: the code implicitly assumes `status.repository == commit.stack.repository`, but the only join key used is `sha`, i.e. `Commit.where(sha: params.sha)` [1](#0-0)  — there is no `stack_id`/`repository` filter tying the incoming webhook's originating repository to the commit(s) it is allowed to mutate.

`WebhooksController#verify_signature` authenticates the webhook only against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-supplied JSON payload (`params.dig('repository','owner','login')`) [2](#0-1) . It authenticates that *some* known GitHub organization/app produced this payload; it never checks that the `sha` inside the payload actually belongs to that organization's repository. `Commit` also has no application-level or DB-level constraint preventing the same `sha` from existing under two different `stack_id`s (the only unique index found is `stack_id + sha`, not `sha` alone) [3](#0-2) .

Exploit flow:
1. Attacker forks the victim's public GitHub repository (or any repo that shares history) into their own GitHub account/org, which is a legitimate, real GitHub org that Shipit is configured to trust (`Shipit.github(organization: ...)` resolves to a real `GitHubApp` with a real `webhook_secret`).
2. Because the fork shares the exact same commit content, the forked commit has an identical `sha` to a commit already tracked by the victim's Shipit stack.
3. Attacker sets up (or already has) a real CI/status integration on their own fork that posts a `status` webhook with `context: codecov/project`, `state: success` for that shared `sha`. This webhook is genuinely and correctly signed by GitHub for the attacker's own repo/org — no secret needs to be stolen.
4. Shipit's `verify_signature` passes (real signature, real org).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim's commit row (same sha, different `stack_id`), and calls `commit.create_status_from_github!(params)` on it — writing a `success` status into the *victim's* stack context [4](#0-3) .
6. If the victim stack requires `codecov/project` and has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` fires once `deployable?` && `stack.continuous_deployment?` && `stack.deployable?` are all true, enqueuing `ContinuousDeliveryJob` to auto-ship [5](#0-4)  and `app/models/shipit/commit.rb" start="227" end="229" />.

Existing guards do not stop this: `verify_signature` checks org-level HMAC only, not sha-to-repo ownership; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema in `StatusHandler` validates shape (`sha`, `state`, `context`, etc.) but not repository identity; there is no `require_permission!`/`stacks` scope check anywhere in the webhook path since it is intentionally unauthenticated (webhooks come from GitHub, not a Shipit session).

### Impact Explanation
A payload correctly authenticated for repository/organization A mutates commit status state belonging to stack/repository B, and — where B has `continuous_deployment` enabled and requires the spoofed context — can trigger an unauthorized deploy of attacker-influenced or arbitrary commits via `ContinuousDeliveryJob`, or conversely block a legitimate deploy by never allowing the required status to appear genuinely (denial of shipping is out of scope per rules, but the ship-triggering direction is in scope). This is a cross-tenant write: one repository's authenticated webhook affects another stack's state, matching the "payload for one repository mutating another's stack, commit... or an unauthorized deploy" Critical category. Blast radius is limited to stacks/commits that share an identical SHA with a repository the attacker controls — realistically forks of public repos, or repos with shared history/mirrors — but is repeatable for every such SHA the attacker can produce.

### Likelihood Explanation
Preconditions: the victim stack must have `continuous_deployment` enabled and require the `codecov/project` context (or whatever context is spoofed) for deployability; the victim's repository must be public (or otherwise forkable) so the attacker can create a commit with an identical SHA; Shipit must be configured to accept webhooks from an organization the attacker controls (any org they can install a status-emitting integration on). Attacker cost is low: fork, no modification needed, and either use an existing CI/status app or send the status manually if they operate an app installed on their own org. This is fully repeatable against any stack tracking a SHA that also exists in an attacker-controlled repo, without needing any Shipit secret, session, or API token.

### Recommendation
Scope `StatusHandler#process` (and the underlying `Commit` status/check-run write paths) to the repository that authenticated the webhook: resolve the target stack(s) via `Repository`/`repository_owner`+`repository_name` from the verified payload, then constrain `Commit.where(sha: params.sha, stack: { repository: repo })` (via a join on `stacks.repository_id`) instead of a bare `sha` lookup, so a status can only affect commits belonging to the same repository that produced the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "a status for one repository must not flip status/deployability for another stack's identical sha" do
  repo_a = shipit_stacks(:shipit)               # victim stack, continuous_deployment: true, requires codecov/project
  repo_b = create_stack_for_different_repository # attacker-controlled repo config

  shared_sha = "a" * 40
  victim_commit = repo_a.commits.create!(sha: shared_sha, message: "same content")
  attacker_commit = repo_b.commits.create!(sha: shared_sha, message: "same content")

  before_deployable = victim_commit.deployable?   # expect: false (missing codecov/project)

  params = ExplicitParameters payload built with:
    { sha: shared_sha, state: "success", context: "codecov/project",
      repository: { full_name: repo_b.github_repo_name, owner: { login: repo_b.organization } } }

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [repo_a]) do
    Shipit::Webhooks::Handlers::StatusHandler.new(params).call
  end

  after_deployable = victim_commit.reload.deployable?
  # Binding under test: status authenticated for repo_b's org must equal repo_b's commit state only.
  assert_not_equal before_deployable, after_deployable  # demonstrates repo_a mutated by repo_b's webhook
  assert_equal "success", victim_commit.statuses.last.state
end
```
This demonstrates that a status payload signed/authenticated only for repository/org B ends up mutating stack A's commit status and enqueuing an auto-deploy for stack A, confirming the cross-repository write.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
