### Title
Session Fixation in GitHub OAuth Callback Allows Attacker to Hijack an Authenticated User Session - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` binds a freshly-verified GitHub identity to the *existing* Rails session without first invalidating/regenerating that session, breaking the binding "GitHub identity that authenticated" versus "the `User` object the session belongs to." An attacker who plants a session on a victim's browser before the victim completes the GitHub OAuth handshake ends up sharing the victim's authenticated session afterward.

### Finding Description
The OAuth callback stores the resulting user id directly into the current session without regenerating the session identifier: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

Compare this to `logout`, which explicitly calls `reset_session`: [2](#0-1) 

No equivalent `reset_session` (or session-id regeneration) is performed on the *login* path. `current_user` throughout the engine is resolved purely from `session[:user_id]`: [3](#0-2) 

```ruby
def current_user
  @current_user ||= find_current_user || AnonymousUser.new
end

def find_current_user
  session[:user_id].present? && User.find_by(id: session[:user_id])
end
```

The binding equality that should hold is:
`session_id (before OAuth) == session_id (after OAuth)` must never be true across a privilege boundary (anonymous → authenticated). Because `callback` never rotates the session identifier, the pre-authentication session — one an attacker may have caused the victim's browser to hold — becomes a fully authenticated session for whatever GitHub identity happens to complete the OAuth flow on it. This is the same class of "authenticated principal not bound to the credential/verification event" problem as the debt-repayment mismatch in the referenced report: a value (here, session identity) is trusted after a verification step (OAuth) without re-establishing the binding at the moment of verification.

### Impact Explanation
If an attacker can force a known session cookie into a victim's browser (e.g., cookie scope shared across a parent/sibling domain used for other purposes, or any mechanism that lets the attacker write a cookie for the Shipit host prior to login), and later the victim performs the legitimate GitHub OAuth login, the attacker's held session becomes indistinguishable from the victim's authenticated session. This matches the explicitly in-scope High-impact category "session fixation / forced OAuth completion," and could be escalated further: with the victim's session, the attacker inherits the victim's `Shipit.github_teams` authorization, and can perform any UI action available to that user (create `ApiClient` tokens, trigger deploys/rollbacks, approve merges), which crosses into the Critical "unauthorized deploy, rollback or merge" category.

### Likelihood Explanation
Exploitability depends on the attacker's ability to seed a session cookie in the victim's browser before OAuth completion — a well-known, practical technique whenever an application fails to rotate session state after authentication (classic OWASP session fixation). No `ApiClient` token, `webhook_secret`, GitHub App private key, or repository write access is needed; the attacker only needs to get the victim to visit a URL/response under the attacker's control that sets the shared session cookie for the Shipit host, then have the victim log in normally. This is a code-level defect independent of deployment configuration.

### Recommendation
Call `reset_session` (or otherwise regenerate the session identifier, e.g. `request.session_options[:renew] = true`) inside `GithubAuthenticationController#callback` immediately before assigning `session[:user_id]`, mirroring the existing `logout` action. This ensures a new, attacker-unknown session ID is issued at the moment a `User` is bound to the session, eliminating the fixation window.

### Proof of Concept
1. Attacker obtains/creates an unauthenticated session with the Shipit host and notes the session cookie value (or forces this cookie onto the victim's browser via any cookie-setting primitive the deployment exposes, e.g., a shared parent-domain cookie).
2. Attacker sends the victim a link to Shipit's login flow while the victim's browser still holds the attacker-known session cookie.
3. Victim completes the GitHub OAuth handshake; `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on the *same* session record without rotating it.
4. Attacker, using the previously known session cookie value, now sends requests to Shipit and is treated as the victim by `Authentication#current_user` / `find_current_user`, since both browsers reference the same `session[:user_id]`.
