### Title
Bridge ERC721 Delivery Uses `transferFrom`/`_mint` Without `onERC721Received` Check, Permanently Locking Bridged NFTs in Non-Receiver Contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`handleERC721Transfer()` in `BridgeTransferERC721.sol` delivers bridged ERC721 tokens to `_to` using either bare `transferFrom()` (lock/unlock mode) or `mintWithTokenURI()` → `_mint()` (mint/burn mode). Neither path calls `onERC721Received()` on the recipient contract. If `_to` is a contract that cannot handle ERC721 tokens, the bridged NFT is permanently locked there. Because the source-chain NFT was already burned or escrowed and the bridge handle-nonce is consumed, recovery is impossible.

---

### Finding Description

In `handleERC721Transfer()`:

**Lock/unlock mode** (line 69):
```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```
`transferFrom` performs no `onERC721Received` callback. The ERC-721 standard explicitly reserves `safeTransferFrom` for this safety check. [1](#0-0) 

**Mint/burn mode** (line 67):
```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
```
`mintWithTokenURI` calls `_mint()`, which only sets `_tokenOwner[tokenId] = to` and emits `Transfer`. It never invokes `onERC721Received`. [2](#0-1) [3](#0-2) 

The library's own `_checkOnERC721Received` correctly validates the selector (`retval == _ERC721_RECEIVED`), but it is never called from either delivery path. [4](#0-3) 

The `_to` address in `handleERC721Transfer` is supplied by bridge operators and originates from the user's original cross-chain request. There is no on-chain guard preventing `_to` from being a contract that lacks ERC-721 receiver support. [5](#0-4) 

---

### Impact Explanation

When `_to` is a contract that does not implement `onERC721Received` (or implements it but returns a wrong selector):

- **Lock/unlock mode**: `transferFrom` succeeds; the NFT is now owned by the non-receiver contract and is irrecoverable.
- **Mint/burn mode**: `mintWithTokenURI` succeeds; the freshly minted NFT is owned by the non-receiver contract and is irrecoverable.

In both cases the source-chain NFT has already been burned or locked in the source bridge, and the handle nonce (`handleNoncesToBlockNums[_requestedNonce]`) is consumed and marked handled. There is no replay or recovery path. The bridged asset is permanently lost.

---

### Likelihood Explanation

A user can specify any address as `_to` in a cross-chain transfer request. Specifying a multisig wallet, a DAO treasury, a DeFi protocol contract, or any other contract that does not implement `IERC721Receiver` is a realistic and common mistake. No privileged action is required beyond the normal user-initiated bridge deposit. The bridge operators faithfully relay whatever `_to` was recorded in the source-chain event.

---

### Recommendation

1. **Lock/unlock mode**: Replace `transferFrom` with `safeTransferFrom`:
   ```solidity
   IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
   ```

2. **Mint/burn mode**: After `mintWithTokenURI`, call `onERC721Received` on `_to` if it is a contract and verify the return value equals `IERC721Receiver.onERC721Received.selector` (`0x150b7a02`). Alternatively, use a `safeMint` variant that performs this check internally.

---

### Proof of Concept

1. Alice owns NFT token ID 42 on the child chain and calls `requestERC721Transfer(nftAddr, contractAddr, 42, "")` where `contractAddr` is a deployed contract that does **not** implement `onERC721Received` (e.g., a plain multisig or a DeFi vault).
2. The source-chain bridge emits `RequestValueTransferEncoded`; in mint/burn mode the NFT is burned immediately.
3. Bridge operators observe the event and call `handleERC721Transfer(txHash, alice, contractAddr, nftAddr, 42, nonce, blockNum, uri, "")` on the destination bridge.
4. **Mint/burn mode**: `mintWithTokenURI(contractAddr, 42, uri)` → `_mint(contractAddr, 42)` succeeds. NFT 42 is now owned by `contractAddr`. No `onERC721Received` is called. `contractAddr` has no way to transfer or use the NFT.
5. **Lock/unlock mode**: `transferFrom(bridge, contractAddr, 42)` succeeds. Same outcome.
6. `handleNoncesToBlockNums[nonce]` is set and the nonce advances. The handle is marked complete. Alice's NFT is permanently lost with no recourse. [1](#0-0) [3](#0-2)

    function _mint(address to, uint256 tokenId) internal {
        require(to != address(0), "ERC721: mint to the zero address");
        require(!_exists(tokenId), "ERC721: token already minted");

        _tokenOwner[tokenId] = to;
        _ownedTokensCount[to].increment();

        emit Transfer(address(0), to, tokenId);
    }

    function _checkOnERC721Received(address from, address to, uint256 tokenId, bytes memory _data)
        internal returns (bool)
    {
        if (!to.isContract()) {
            return true;
        }

        bytes4 retval = IERC721Receiver(to).onERC721Received(msg.sender, from, tokenId, _data);
        return (retval == _ERC721_RECEIVED);
    }
