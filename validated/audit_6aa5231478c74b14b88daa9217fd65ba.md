### Title
Unauthenticated device message with an unrecognized recipient ephemeral pubkey triggers a delayed, uncaught exception that crashes the node process - (File: device.js)

### Summary
`device.decryptPackage()` schedules an unconditional `throw Error(...)` inside a `setTimeout` callback whenever an incoming encrypted device message's `dh.recipient_ephemeral_pubkey` does not match any of the node's known keys (current temp key, previous temp key, or permanent key). Because the throw happens asynchronously inside `setTimeout`, it escapes every surrounding `try/catch` in `device.js`/`network.js` and becomes an uncaught exception. `network.js` installs a global `process.on('uncaughtException', ...)` handler that explicitly re-throws to crash the whole process. Any party able to route a `hub/deliver`/`hub/message` packet to a node (which only requires knowing the target's public device address, a value routinely shared for pairing) can trigger this and take the node offline.

### Finding Description
`device.js` `decryptPackage()`: [1](#0-0) 

When `objEncryptedPackage.dh.recipient_ephemeral_pubkey` is not `objMyTempDeviceKey.pub_b64`, not `objMyPrevTempDeviceKey.pub_b64`, and not `objMyPermanentDeviceKey.pub_b64`, the function does: [2](#0-1) 
```
else{
    console.log("message encrypted to unknown key");
    setTimeout(function(){
        throw Error("message encrypted to unknown key, device "+my_device_address+", len="+objEncryptedPackage.encrypted_message.length+". The error might be caused by restoring from an old backup or using the same keys on another device.");
    }, 100);
    return null;
}
```

This is invoked from the `hub/message` justsaying handler: [3](#0-2) 
```
try {
    var json = decryptPackage(objDeviceMessage.encrypted_package);
}
catch(e){
    return respondWithError("failed to decrypt: " + e);
}
```
The surrounding `try/catch` only covers the synchronous call to `decryptPackage`. Since the actual `throw` is deferred by `setTimeout(..., 100)`, it executes on a later turn of the event loop, completely outside this (or any) `try/catch` block, and therefore becomes an uncaught exception.

`network.js` installs a process-wide handler that always re-throws to crash the process: [4](#0-3) 

The delivery path that reaches `decryptPackage` does not require the sender to be a known correspondent. On the hub side, `hub/deliver` only checks that required fields are present, that `to` is a syntactically valid device address, and that the message is self-consistently signed by the attacker's own (freshly generated) keypair — it does not require the recipient to know the sender: [5](#0-4) 
It then simply checks that the target device address is registered on the hub and relays the message: [6](#0-5) 

Once relayed, the recipient's own client validates the outer signature/hash (both attacker-controlled and self-consistent, so they pass) and then calls `decryptPackage` on the attacker-supplied `encrypted_package`: [7](#0-6) 

An attacker only needs:
1. The target's device address (`to`), which is routinely exposed/shared for pairing purposes and is not a secret authenticator.
2. Their own valid keypair to self-sign the outer envelope.
3. An arbitrary/garbage value for `dh.recipient_ephemeral_pubkey` (any base64 blob that doesn't happen to equal the target's current keys).

No correct decryption key, correspondence relationship, or prior pairing is required to reach the vulnerable branch — the check for "unknown key" happens before any correspondent-whitelist check.

### Impact Explanation
This causes a full crash of the ocore node process (wallet/AA node/hub), not merely a caught error. Per `network.js`'s `uncaughtException` handler, the exception is deliberately re-thrown to terminate the process ("crash the process to avoid ending up in an inconsistent state"). For any node running this code (wallets, witnesses, hubs, AA-hosting nodes), an unauthenticated remote party can force repeated crashes/restarts, denying availability of that node's services — a "network unable to confirm new units" condition if witnesses/hubs are targeted, and a wallet/device-message DoS more broadly. This aligns with the CVE-2018-19626 bug class (malformed/attacker-controlled input causing a crash of the processing engine), reachable here through unauthenticated device-message handling rather than a network dissector.

### Likelihood Explanation
High. The only prerequisite is knowledge of the target's device address, which is inherently exposed (it's shared out-of-band for pairing, appears in pairing links/QR codes, and is derivable from the target's permanent pubkey via `objectHash.getDeviceAddress`). No cryptographic secret of the victim is needed, no correspondent relationship is required, and the message need not decrypt successfully — it is intentionally malformed to hit the "unknown key" branch. The exploit is a single crafted `hub/deliver` request.

### Recommendation
- Do not `throw` inside the `setTimeout` callback in `decryptPackage`; instead emit a `nonfatal_error` event (the code already has a commented-out `eventBus.emit('nonfatal_error', ...)` alternative) or log/report without crashing the process.
- If the delayed throw is intended purely as a debug/breadcrumb mechanism, gate it behind a debug flag and never let it terminate a production process from unauthenticated network input.
- Alternatively/additionally, verify that the sender is a known correspondent (or otherwise rate-limit/deprioritize) before processing `encrypted_package` from unrecognized senders, so that unauthenticated peers cannot reach `decryptPackage`'s failure branches at all.

### Proof of Concept
1. Attacker generates a fresh secp256k1 keypair and derives `pubkey`/`sender_ephemeral_pubkey`.
2. Attacker builds:
```
objEncryptedPackage = {
  encrypted_message: <any base64>,
  iv: <any 16-byte base64>,
  authtag: <any base64>,
  dh: {
    sender_ephemeral_pubkey: <attacker ephemeral pubkey b64>,
    recipient_ephemeral_pubkey: <arbitrary base64 blob not equal to victim's known keys>
  }
};
objDeviceMessage = {
  encrypted_package: objEncryptedPackage,
  to: "<victim device address>",
  pubkey: <attacker permanent pubkey b64>
};
objDeviceMessage.signature = ecdsaSig.sign(objectHash.getDeviceMessageHashToSign(objDeviceMessage), attacker_priv_key);
```
3. Attacker connects to the victim's hub and sends `hub/deliver` with `objDeviceMessage` (per `network.js:3508-3567`, this only requires valid self-signature and a registered `to` address).
4. Hub relays a `hub/message` justsaying to the victim node (if online) or stores it for later delivery.
5. Victim's `device.js handleJustsaying('hub/message', ...)` verifies the (self-consistent, attacker-signed) outer envelope, then calls `decryptPackage`, which detects `recipient_ephemeral_pubkey` matches none of its keys and schedules the `setTimeout` `throw`.
6. ~100ms later, the throw fires uncaught; `network.js`'s `process.on('uncaughtException', ...)` handler re-throws, crashing the victim's node process. [1](#0-0) [8](#0-7) [4](#0-3)
