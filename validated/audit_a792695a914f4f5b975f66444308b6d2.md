### Title
Webhook signature verification org derived from `repository.owner.login` diverges from the org whose repository is mutated via `repository.full_name`, enabling cross-tenant stack forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App (and thus the `webhook_secret` used to verify the payload) based on `params.dig('repository','owner','login')`, but downstream handlers like `LabeledHandler` resolve the actual repository/stack to mutate from `params.repository.full_name` via `Repository.from_github_repo_name`. Because both values come from the same unauthenticated JSON body and are never checked against each other, an attacker can set `repository.owner.login` to an organization configured with no `webhook_secret` (verification short-circuits to `true`) while setting `repository.full_name` to a victim org/repo that Shipit actually tracks under a different, secret-protected org.

### Finding Description
The broken binding: `verifying_org (params.repository.owner.login)` == `mutated_repo_org (params.repository.full_name.split('/').first)` is assumed but never enforced.

Path:
1. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner)`, at [3](#0-2) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank, at [4](#0-3) , and `@webhook_secret = @config[:webhook_secret].presence` at [5](#0-4) . `docs/setup.md` documents the webhook secret as "optional" and the multi-app config fixture in the repo (`test/dummy/config/secrets_double_github_app.yml`) even ships two orgs both with `webhook_secret: # nil`, confirming this is a real, supported configuration shape.
3. Once verification passes, `create` dispatches to handlers with the raw parsed `params`, at [6](#0-5) .
4. `LabeledHandler#repository` resolves the repository from `params.repository.full_name` — a completely different field than the one used for org selection — via `Shipit::Repository.from_github_repo_name`, at [7](#0-6) , and `from_github_repo_name` simply splits that string on `/` to look up any repository by owner/name with no relation to the verifying org, at [1](#0-0) .
5. `#handle` then calls `stack.archive!`/`stack.unarchive!` on the resolved stack, at [8](#0-7) , which the `ReviewStackAdapter` executes unconditionally against the found stack, at [9](#0-8) .

Attacker request: `POST /webhooks`, header `X-Github-Event: pull_request`, body `action: "labeled"`, `repository.owner.login: "NoSecretOrg"`, `repository.full_name: "VictimOrg/victim-repo"`, `pull_request.state: "open"`, plus required fields per the `LabeledHandler` schema. No signature needed since `NoSecretOrg`'s app has no secret. `verify_signature` verifies against `NoSecretOrg`'s (secret-less) app and passes; `LabeledHandler` then resolves and mutates `VictimOrg/victim-repo`'s `ReviewStack`, running its `archive!`/`unarchive!` (which triggers deprovisioning/provisioning, i.e., running `shipit.yml` steps).

Existing guards don't prevent this: `drop_unhandled_event` only checks event type, not org binding, at [10](#0-9) . `GithubOrganizationUnknown` is only raised if `NoSecretOrg` isn't configured at all — but it is configured (that's the precondition), so no exception fires. `ExplicitParameters`/`LabeledHandler.params` schema validates types/presence but never cross-checks `repository.owner.login` against `repository.full_name`'s owner segment. `Repository` model validations constrain `owner`/`name` character sets but do not tie a repository to a specific verifying GitHub App/org at webhook-processing time. `force_github_authentication`, `User#authorized?`, `require_permission!`, and `stacks` scoping are session/API-token concerns not exercised in the unauthenticated webhook path.

### Impact Explanation
An unprivileged attacker who controls no more than a public GitHub org/app with no webhook secret can archive or unarchive (re-provision) another organization's `ReviewStack` for any repository Shipit tracks, without ever authenticating against that victim org's `webhook_secret`. Re-provisioning triggers execution of `shipit.yml`-defined provisioning steps for the victim stack — a write and a command execution against a repository/tenant that never authenticated the request. This is repeatable against any repository/stack whose owner org is known and is cross-tenant by construction, matching the "Critical: a payload for one repository mutating another's stack" category.

### Likelihood Explanation
Requires: (a) the Shipit deployment configures at least two GitHub orgs (a documented, supported pattern per `docs/setup.md`'s "Using Multiple Github Applications"), and (b) at least one configured org has no `webhook_secret` (documented as optional, and the shipped test fixture demonstrates this exact double-org, no-secret configuration). Given those, the attacker needs zero credentials — no session, no API token, no GitHub App keys — just the ability to send an arbitrary HTTP POST to `/webhooks` and knowledge of the victim's `owner/repo` name (public information). This is trivially repeatable against any tracked repository.

### Recommendation
Cross-validate that the org used for signature verification matches the org actually referenced by the payload's `repository.full_name` (and `organization.login` fallback) before dispatching to handlers — e.g., reject the webhook if `repository.owner.login` (or `organization.login`) does not equal the owner segment of `repository.full_name`. Additionally/alternatively, require a non-blank `webhook_secret` for every configured GitHub App (fail closed instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`), removing the ability for any org to accept unsigned payloads.

### Proof of Concept
Minitest integration test under `test/controllers/webhooks_controller_test.rb` style, using a two-org config (`OrgOne` secret-less, `VictimOrg` with a real `webhook_secret`, mirroring `test/dummy/config/secrets_double_github_app.yml`):
1. Seed `shipit_repositories` fixture for `VictimOrg/victim-repo` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`, and an existing non-archived `ReviewStack`.
2. Build a `pull_request`/`labeled` payload with `repository.owner.login = "OrgOne"` and `repository.full_name = "VictimOrg/victim-repo"`, omitting/using an arbitrary `X-Hub-Signature` (no stubbing of `GithubHook` for `VictimOrg`, since the request must not know `VictimOrg`'s secret).
3. `post :create, body: payload.to_json, as: :json`, asserting `assert_response :ok` (not `:unprocessable_entity`).
4. Assert `stack.reload.archived?` (or `provision_status`) changed as a result, proving the victim stack was mutated without ever satisfying `VictimOrg`'s `webhook_secret` check — i.e., assert `verifying_org ("OrgOne") != mutated_repo_owner ("VictimOrg")` while the request still succeeded and produced a write.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
