### Title
Round Number (`*big.Int`) Silently Truncated to `uint8` in VRank Module Corrupts Validator Scoring at Round ≥ 256 — (`File: kaiax/vrank/impl/handler.go`)

---

### Summary

The VRank module in `kaiax/vrank/impl/handler.go` casts `view.Round` (a `*big.Int` that can be arbitrarily large) to `uint8` in six separate call sites without any bounds check. When consensus reaches round ≥ 256, the truncated value wraps to `round % 256`, causing three distinct misbehaviours that corrupt VRank scoring and, downstream, the permissionless validator state-transition (promotion/demotion of `ValActive` nodes and their reward eligibility).

---

### Finding Description

`bft.View.Round` is typed `*big.Int`. In `HandleIstanbulPreprepare`, `HandleVRankPreprepare`, `recoverVRankPreprepareSender`, and `BroadcastVRankPreprepare` the round is narrowed to `uint8` with a bare Go conversion:

```go
// handler.go line 53
v.collector.AddPrepreparedTime(vrank.ViewKey{N: blockNum, R: uint8(view.Round.Uint64())}, ...)

// handler.go line 84
v.markSeenPreprepare(vrank.ViewKey{N: block.NumberU64(), R: uint8(view.Round.Uint64())}, block.Hash())

// handler.go line 92
sigHash := v.vrankCandidateSigHash(block.NumberU64(), uint8(view.Round.Uint64()), block.Hash())

// handler.go line 106
v.BroadcastVRankCandidate(&vrank.VRankCandidate{
    Round: uint8(view.Round.Uint64()), ...
})

// handler.go line 219
sigHash := v.vrankPreprepareSigHash(msg.Block.NumberU64(), uint8(msg.View.Round.Uint64()), ...)

// handler.go line 278
sigHash := v.vrankPreprepareSigHash(block.NumberU64(), uint8(vrankPreprepare.View.Round.Uint64()), ...)
```

`VRankCandidate.Round` is declared `uint8` in the types package, so once the value is truncated it propagates through the entire message pipeline. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

### Impact Explanation

Three concrete broken invariants when `round ≥ 256`:

**1. `markSeenPreprepare` key collision — VRankPreprepare for round 256 silently dropped**

`seenPreprepare` is keyed by `ViewKey{N, R uint8}`. Round 256 maps to `R=0`. If round 0 was already processed for the same block number (with a different block hash, as is normal after a round change), `markSeenPreprepare` returns `conflictingView=true` and the legitimate round-256 VRankPreprepare is discarded with a warning log. Candidates never broadcast `VRankCandidate` for that round. [7](#0-6) 

**2. `isStaleVRankCandidate` false-positive — all VRankCandidates for round 256 dropped**

`prepreparedView.Round` is stored as the full `uint64` (256). `VRankCandidate.Round` is `uint8` (0 after truncation). The staleness check is:

```go
return msg.BlockNumber == prepreparedSeqNum && uint64(msg.Round) < prepreparedRound
// uint64(0) < 256  →  true  →  stale!
```

Every VRankCandidate for round 256 is discarded as stale by every committee member. [8](#0-7) 

**3. `AddPrepreparedTime` key collision — timing data for round 256 overwrites round 0**

The collector stores preprepared timestamps under `ViewKey{N, R: uint8(round)}`. Round 256 and round 0 share the same key, so the timestamp recorded for round 256 silently overwrites the one for round 0 (or vice versa), corrupting the latency measurement used for VRank scoring. [1](#0-0) 

**Downstream protected-state impact:**

VRank scores drive the permissionless validator lifecycle (`CandTesting → ValActive → ValExiting`). `ValActive` is the only state eligible for block rewards (`IsRewardEligible`). Corrupted scores at round 256 cause the module to record zero candidate responses for that round, biasing promotion/demotion decisions. A validator that should be promoted to `ValActive` may be held back, or one that should be demoted may remain active, directly affecting which addresses receive KAIA block rewards via `FinalizeState → state.AddBalance`. [9](#0-8) [10](#0-9) 

---

### Likelihood Explanation

Istanbul BFT round numbers are unbounded `*big.Int`. Under adversarial conditions (e.g., a Byzantine proposer repeatedly broadcasting invalid blocks), honest nodes increment the round counter without limit. Round 256 is reachable without any privileged operation — it requires only that 256 consecutive rounds fail to reach quorum, which an attacker controlling a minority of validators can sustain. The permissionless fork is the target deployment context, where the validator set is open and adversarial participants are expected.

---

### Recommendation

1. Add an explicit bounds check before every `uint8(view.Round.Uint64())` cast. If `view.Round.Uint64() > math.MaxUint8`, either return an error or clamp and log.
2. Widen `ViewKey.R` and `VRankCandidate.Round` to `uint64` to match the type of `bft.View.Round`.
3. Update `isStaleVRankCandidate` to compare `uint64(msg.Round)` against `prepreparedRound` only after ensuring both are in the same numeric domain.
4. Add a unit test that exercises round = 256 through the full `HandleIstanbulPreprepare → HandleVRankPreprepare → HandleVRankCandidate` pipeline.

---

### Proof of Concept

```
Setup: permissionless fork active, block N in consensus.

1. Rounds 0–255 all fail (Byzantine proposer or network partition).
   Each round's VRankPreprepare is processed normally; seenPreprepare[{N, R:0..255}] is populated.

2. Round 256 begins. Honest proposer P256 broadcasts IstanbulPreprepare(block=B256, round=256).
   HandleIstanbulPreprepare stores:
     prepreparedView = {Sequence: N, Round: 256}   // full uint64
     ViewKey{N, R: uint8(256)} = ViewKey{N, R: 0}  // TRUNCATED

3. P256 broadcasts VRankPreprepare(block=B256, view.Round=256).
   HandleVRankPreprepare on each candidate:
     markSeenPreprepare(ViewKey{N, R:0}, hash(B256))
     → seenPreprepare[{N,R:0}] already holds hash(B0) from round 0
     → hash(B256) ≠ hash(B0) → conflictingView=true → return nil
   No VRankCandidate is ever broadcast for round 256.

4. Even if a VRankCandidate with Round=uint8(256)=0 somehow arrives:
     isStaleVRankCandidate: uint64(0) < 256 → true → dropped.

5. EvaluateCandidates for block N, round 256: zero candidates recorded.
   VRank scores for all validators are zero for this round.
   Promotion/demotion decisions use corrupted scores.
   Validators that should reach ValActive (and receive KAIA rewards) are incorrectly held back.
```
