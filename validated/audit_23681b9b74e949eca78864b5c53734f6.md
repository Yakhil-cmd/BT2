### Title
`Api::CCMenuController#stack` bypasses per-client stack scoping via unscoped `Stack.from_param!` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the base `stack` helper to call `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!(params[:stack_id])` used everywhere else, so any authenticated `ApiClient` — including one whose `stack_id` restricts it to a single stack — can read `ccmenu.xml` for an arbitrary, unrelated stack. This occurs regardless of whether authentication happens through `params[:token]` or through the Basic‑Auth `super` fallback, because the override is unconditional.

### Finding Description
Intended binding: `stack touched ∈ (current_api_client.stack_id? ? {current_api_client.stack_id} : Stack.all)`, which is exactly what `BaseController#stacks`/`#stack` implement: [1](#0-0) .

`Api::CCMenuController` redefines `stack` to skip that scoping entirely: [2](#0-1) . This override applies no matter how `@current_api_client` was populated — via the controller's own `params[:token]` check or via the inherited Basic-Auth `super` path: [3](#0-2) .

`check_permissions!` (invoked by `require_permission :read, :stack`) only checks the permission string `"read:stack"` is present in `permissions`; it never compares `current_api_client.stack_id` to the requested `:stack_id`: [4](#0-3) . The only place that ties a client's permission to *its own* stack is the `stacks` scoping in `BaseController`, which `CCMenuController` deliberately bypasses.

Attacker request: obtain (via any legitimate means available to a client scoped to stack A — e.g., its own valid API token or Basic-Auth credentials) an `ApiClient` with `stack_id = A` and `permissions` including `read:stack`. Send `GET /stacks/B/ccmenu.xml` with that client's Basic-Auth credentials and no `params[:token]`. `authenticate_api_client` fails the token branch, falls to `super`, which authenticates the client via `BasicAuth.authenticate`. `require_permission!(:read, :stack)` passes because the client has `read:stack` in its permission list. `stack` then resolves stack B via unscoped `Stack.from_param!`, and `show` renders stack B's latest deploy/rollback data.

Existing guards don't catch this: `require_permission!` checks only the operation:scope string, not the stack binding; `stacks` scoping exists but is overridden/unused in this controller; there's no other stack-id equality check in the request path.

### Impact Explanation
An `ApiClient` credential scoped to one stack (stack A) can read CI/CD status (`ccmenu.xml`: latest deploy/rollback id, status, end time) for any other stack (stack B) in the same Shipit instance, purely by targeting a different `:stack_id` in the URL. This is a cross-tenant/cross-stack authorization bypass — an authenticated but unauthorized-for-that-stack read of deploy state — matching the High-severity category "escalation into authorization... unauthenticated/unauthorized read of stack state... deploy output." It is fully repeatable against any stack ID and requires only credentials for any one client with `read:stack` permission scoped elsewhere.

### Likelihood Explanation
Preconditions: attacker needs a valid `ApiClient` token or Basic-Auth credential (issued by an operator for some stack A) with `read:stack` permission — this is not GitHub-secret or Shipit-secret dependent knowledge beyond the credential itself, and once such a credential exists (e.g., issued to a CI system or low-privilege integration), the attacker can pivot to any other stack. No GitHub interaction, signature, or session is needed. Feasibility is high and the request is a single unauthenticated-relative-to-target-stack `GET`.

### Recommendation
In `Api::CCMenuController`, remove the local `stack` override (or reimplement it using the inherited scoped lookup):
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it reuses `BaseController#stacks`, restoring the `current_api_client.stack_id` scoping regardless of which authentication branch (`token` param or Basic-Auth `super`) populated `@current_api_client`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a client scoped to stack A cannot read stack B's ccmenu via basic auth" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocoaship) # different stack fixture

  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack_id: stack_a.id,
    permissions: ['read:stack']
  )

  authorization = ActionController::HttpAuthentication::Basic.encode_credentials(client.authentication_token, '')
  get shipit.api_stack_ccmenu_path(stack_b), headers: { 'Authorization' => authorization }

  # Binding under test: stack touched must be ∈ {stack_a.id}, not stack_b.id
  assert_response :not_found # or :forbidden — MUST NOT be :success
  # Current (buggy) behavior: assert_response :success and body contains stack_b's project name,
  # proving the cross-stack read.
end
```
