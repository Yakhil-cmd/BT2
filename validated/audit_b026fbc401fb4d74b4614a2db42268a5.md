### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire database and writes a GitHub status onto whatever `Commit` row matches, without checking that the commit belongs to the repository/organization that the webhook's signature was actually verified against. An attacker who controls (or knows the secret of) any GitHub org registered with Shipit can forge a `status` webhook naming a victim commit's sha and force a status onto that victim's stack.

### Finding Description
The broken binding: `payload.repository.owner.login == commit.stack.repository.owner` must hold before writing a status onto `commit`; in this code it does not.

- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves the GitHub App config purely from `repository_owner` in the untrusted payload (`params.dig('repository','owner','login')`), then calls `github_app.verify_webhook_signature`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is configured for that organization: `return true unless webhook_secret`. [2](#0-1) 
  So any organization Shipit knows about but that has no `webhook_secret` configured (or whose secret the attacker knows) lets an attacker post arbitrary, signature-"verified" payloads while claiming to be that org.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no scoping by repository/stack at all, unlike the base `Handler` class which provides a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)` — a helper `StatusHandler` never uses. [3](#0-2) [4](#0-3) 
- `Commit#create_status_from_github!` writes the status using the commit's own real `stack_id` (`statuses.replicate_from_github!(stack_id, github_status)`), i.e. the victim stack's ID, regardless of which org/repo the attacker claimed in the payload. [5](#0-4) 

Exploit flow: attacker owns/knows the credentials for `attacker-org` (no `webhook_secret` set, or secret leaked/known), sends `POST /webhooks` with header `X-Github-Event: status` and body `{"repository":{"owner":{"login":"attacker-org"},"full_name":"attacker-org/decoy"},"sha":"<victim-sha>","state":"success"}`. `verify_signature` passes trivially for `attacker-org`. `StatusHandler#process` finds the `Commit` row for `<victim-sha>` (which belongs to `victim-org`'s stack) and calls `create_status_from_github!`, writing a forged `success`/`failure` status onto that commit under the victim's stack. This can flip `Commit#state`/`deployable_status`, potentially unblocking a merge (`ProcessMergeRequestsJob` is enqueued on state transition, as shown in `test/models/commits_test.rb:763-777`) or a deploy gate that checks CI status.

No existing guard prevents this: `verify_signature` only authenticates the claimed organization, not the specific repository/commit being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape (`sha`, `state`, etc.), not ownership; there is no `Repository`/`Stack` scoping check in `StatusHandler` at all.

### Impact Explanation
A successfully forged webhook writes a `Status` row (and can flip `Commit#state`) on a commit belonging to a different, unrelated stack/repository than the one the webhook was authenticated for. This is a cross-tenant write directly enabling unauthorized deploy/merge gating decisions on victim stacks — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any commit sha the attacker can learn (shas are often visible in PRs, CI logs, or the Shipit UI itself) and against any number of victim stacks sharing the same Shipit instance, as long as the attacker can get any org accepted by `verify_signature`.

### Likelihood Explanation
Preconditions: the attacker needs the webhook to pass `verify_signature` for *some* organization known to Shipit's GitHub App config — either because that org has no `webhook_secret` configured, or because the attacker knows/leaked that secret (per the scenario's stated precondition, this is granted). No Shipit session, API token, or team membership is required. The attacker also needs the victim's commit sha, which is commonly discoverable (PR pages, CI, Shipit stack UI). Given the precondition is satisfied, the attack is a single unauthenticated `POST /webhooks` request, trivially repeatable.

### Recommendation
Scope `StatusHandler#process` (and ideally all handlers) to only mutate commits belonging to the repository named in the verified payload, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks` helper from `Handler`, which resolves `Repository.from_github_repo_name(repository_name)` from the same verified payload. This enforces `payload.repository.full_name == commit.stack.repository.full_name` before any write.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` pattern):
```ruby
test ":status webhook must not mutate a commit belonging to a different repository" do
  request.headers['X-Github-Event'] = 'status'

  victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit), repo e.g. "shopify/shipit-engine"
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulates attacker-org verified independently

  attacker_payload = {
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => 'attacker-org/decoy' },
    'sha' => victim_commit.sha,
    'state' => 'success'
  }.to_json

  assert_no_difference 'victim_commit.statuses.count' do
    post :create, body: attacker_payload, as: :json
  end
end
```
Assertion: before the request, `victim_commit.stack.repository.full_name` ("victim-org/...") != payload `repository.full_name` ("attacker-org/decoy"); the test asserts `victim_commit.statuses.count` is unchanged after the forged request — currently this assertion fails (a status IS written), demonstrating the vulnerability; after applying the fix scoping by `stacks`, the assertion passes.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
