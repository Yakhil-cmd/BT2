### Title
Cross-repository `sha`-only lookup in `StatusHandler#process` lets any Shipit-onboarded org trigger `ContinuousDeliveryJob` for another org's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target `Commit` records purely by `Commit.where(sha: params.sha)`, with no scoping to the webhook's own `repository.full_name` or organization. Because signature verification (`WebhooksController#verify_signature`) authenticates only that *some* Shipit-registered GitHub organization sent the payload — not that the `sha`/`repository` inside the payload belongs to that organization — a legitimate webhook from an attacker's own (Shipit-onboarded, but otherwise unrelated) repository can drive `Status` creation, and therefore `Commit#schedule_continuous_delivery`, for any other tenant's `Commit` rows sharing the same `sha` string.

### Finding Description
The binding the question assumes should hold is:

`ContinuousDeliveryJob enqueues authorized by victim org's own CI` == `ContinuousDeliveryJob enqueues an attacker can cause by POSTing status webhooks signed for their own unrelated repo`

Tracing the path:

1. `WebhooksController#verify_signature` looks up the GitHub App/secret **by organization login taken from the payload itself** (`repository_owner`, i.e. `params.dig('repository','owner','login')`), via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`. [1](#0-0) [2](#0-1) 
This only proves "some org configured on this Shipit instance genuinely sent this webhook" — it never ties the `sha`/`repository.full_name` inside the JSON body to the commit or stack that will actually be mutated. Any org with its own legitimate GitHub App/webhook secret registered on the same multi-tenant Shipit instance can produce a validly-signed `status` event for its own repository.

2. `StatusHandler#process` then does a **global, unscoped** lookup: [3](#0-2) 
`Commit.where(sha: params.sha)` matches every `Commit` row in the entire database with that sha, across all stacks/organizations, and calls `commit.create_status_from_github!(params)` on each. There is no check that `commit.stack.repository` (or its org) matches `repository_owner`/`repository.full_name` from the payload.

3. `Commit#create_status_from_github!` → `add_status` → creates a `Status`, and `Status` fires `after_commit :schedule_continuous_delivery` on create: [4](#0-3) 
which calls `Commit#schedule_continuous_delivery`: [5](#0-4) 
If the victim stack has `continuous_deployment?` true, the target commit is `deployable?` (CI green after the forged status, or `stack.ignore_ci?`), and `stack.deployable?`, this unconditionally enqueues `ContinuousDeliveryJob.perform_later(stack)`.

4. Root cause: `sha` values are content-addressed Git hashes, not tied to any specific repository. An attacker with knowledge of a victim's public/ancestor commit content (author, committer, tree, parents, message, timestamps) — e.g., by forking a public repo or reproducing an old commit's exact metadata — can create/push an identical-SHA commit inside their own, separately-onboarded repository, and drive GitHub to emit a real `status` event for it. The webhook is fully legitimate for the attacker's org/repo; the flaw is that `StatusHandler` doesn't check whose repository the payload actually describes before applying the status to whatever `Commit` rows happen to share that sha.

Existing guards do not prevent this: `verify_signature` checks org-level authenticity, not sha/repository binding; there is no `ExplicitParameters` constraint tying `sha` to `repository`; `Commit#deployable?`/`stack.deployable?`/`continuous_deployment?` are legitimate victim-side gating conditions, but once the forged `Status` row is created with `state: 'success'`, those conditions are satisfied exactly as intended for real CI, indistinguishably.

### Impact Explanation
Each accepted forged `status` webhook that matches an existing victim `Commit.sha` creates a `Status` row on the victim's stack and can independently trigger `ContinuousDeliveryJob.perform_later(stack)` for the victim stack — an unauthorized deploy trigger for a repository/organization that never sent that status. Repeating this against successive ancestor commits (one sha match per POST) lets the attacker "walk" the victim's undeployed commit range toward `HEAD`, each POST from the attacker's own timing, producing a sequence of unauthorized `ContinuousDeliveryJob` enqueues driven entirely by the attacker. This is a payload for one repository (attacker's) mutating another repository's stack/commit records and triggering deploys — matching the Critical category ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy").

### Likelihood Explanation
Preconditions: (a) the Shipit instance is multi-tenant, hosting stacks for more than one GitHub organization, each with its own registered GitHub App/webhook secret (a documented, common Shipit deployment shape); (b) the victim stack has `continuous_deployment?` enabled and `last_deployed_commit` behind `HEAD`; (c) the attacker can produce commits with identical `sha` to victim ancestor commits in their own repository — feasible via forking a public repo (fork commits share sha with upstream) or precisely reconstructing commit metadata, both achievable by an unprivileged GitHub user with no Shipit credentials. Attacker cost is low: create/own a repo already onboarded to the shared Shipit instance, push/report a status on a commit sha that coincides with a victim ancestor commit, repeat per commit. This is repeatable per targeted stack/commit.

### Recommendation
In `StatusHandler#process` (and equivalently in `CheckSuiteHandler`/push handlers using bare sha lookups), scope the `Commit` lookup by the webhook's own repository, not by `sha` alone — e.g. join through `stack.repository` and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: matching_repository.id })`, deriving the repository from `params.dig('repository','full_name')`/owner+name rather than trusting an unscoped global sha match. Reject or ignore statuses whose payload repository does not match the commit's own stack repository.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from an unrelated org's repo enqueues ContinuousDeliveryJob for a victim stack sharing the sha" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment? true, last_deployed_commit behind HEAD
  ancestor_commits = [shipit_commits(:first), shipit_commits(:second), shipit_commits(:third)]

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulates a validly-signed webhook from the ATTACKER's own onboarded org

  assert_enqueued_jobs(ancestor_commits.size, only: ContinuousDeliveryJob) do
    ancestor_commits.each do |commit|
      body = {
        'sha' => commit.sha,                 # sha collides with victim's own Commit row
        'state' => 'success',
        'context' => 'attacker/ci',
        'repository' => { 'full_name' => 'attacker-org/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
      }.to_json
      post :create, body:, as: :json
    end
  end
  # Binding check: victim org authorized 0 of these CI results, attacker caused 3.
end
```
Note: the underlying assumption that the attacker can obtain a commit with identical `sha` to a tracked victim ancestor commit (via fork or content reconstruction) is outside this engine's code and should be validated/documented separately; the engine-level bug demonstrated here is the unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` that removes repository/tenant isolation once that sha collision exists.
