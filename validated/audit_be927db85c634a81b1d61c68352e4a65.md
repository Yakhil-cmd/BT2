## Analysis

The reported bug class — a griefer pre-funding a not-yet-fully-initialized contract to permanently break a "this is the very first/only deposit" invariant check — has a direct structural analog in Obyte's Autonomous Agent (AA) balance model, demonstrated by ocore's own reference AA implementation.

In ocore, an AA's `balance[asset]` is not scoped to the current trigger: it is the cumulative total of every output ever sent to that address, aggregated by `insertAADefinitions` regardless of who sent it or when [1](#0-0) , and read at formula-evaluation time straight from the `aa_balances` table [2](#0-1) . Any user can send bytes or an arbitrary asset to any valid address at any time, whether or not an AA is even defined there yet, since payments only require a syntactically valid output address [3](#0-2) ; when the AA is later defined/activated, all pre-existing outputs to its (deterministic, `chash160`-derived) address are folded into its opening `aa_balances` row.

ocore's bundled `uniswap_like_market_maker.oscript` sample AA relies on exactly the anti-pattern the Sherlock report warns about: it uses `balance == 0` as a proxy for "this is the genuine, first deposit" to decide how many pool shares to mint [4](#0-3) .

### Title
Donation-before-first-deposit permanently corrupts the "initial deposit" invariant in the market-maker AA pattern, causing legitimate depositors to receive zero pool shares - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The "invest in MM" branch of the reference market-maker AA decides whether a deposit is the pool's genesis deposit purely by checking `$asset_balance == 0 OR $bytes_balance == 0`, where `$asset_balance`/`$bytes_balance` are the AA's `balance[]` values *minus* the current trigger's outputs [5](#0-4) . Because `balance[]` accumulates every output ever received by the AA's address (see the balance-aggregation query in `insertAADefinitions`) [1](#0-0) , any unprivileged user can send a trivial, unsolicited amount of the paired asset to the AA's address before the intended first investor's deposit unit is posted. This is the same pattern as donating fCash to the wfCash contract's predictable address before deployment to defeat its "exactly one balance" check.

### Finding Description
1. When the market-maker AA's share-asset is defined (`define share asset` case), the pool has zero liquidity and zero outstanding shares (`var['mm_asset_outstanding']` is unset/0) [6](#0-5) .
2. Before the intended first liquidity provider's deposit unit stabilizes/executes, an attacker posts a payment sending a small amount of `$asset` (and/or bytes) directly to the AA's address. Since the AA's address is a deterministic `chash160` of its known definition, and outputs to any address are unconditionally valid, this donation is accepted and immediately reflected in the AA's persisted `aa_balances` row [7](#0-6) .
3. When the genuine first investor later triggers the "invest in MM" case, `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` is now **non-zero** (polluted by the donation), so the `// initial deposit` branch (which would normally mint `$issue_amount = balance[base]`, i.e., 100% ownership, to the first depositor) is skipped forever [8](#0-7) .
4. Execution falls into the "not initial deposit" ratio-based branch, which computes `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`. Since `var['mm_asset_outstanding']` is still `0` (no shares were ever minted, because the initial-deposit branch never fired), `$issue_amount` evaluates to `0` regardless of how much the real investor deposits [9](#0-8) .
5. The real investor's base/asset payment is nonetheless absorbed into the AA's balance (the `payment` message sends them `0` shares) [10](#0-9) , and there is no code path that ever resets or corrects this state — the pool is permanently bricked with respect to fair share issuance.

### Impact Explanation
This is a concrete, permanent AA fund loss: any unprivileged user who front-runs the pool's genesis deposit with a dust donation causes every subsequent (legitimate) depositor's funds to be absorbed by the AA while they receive zero pool-share tokens in return. There is no recovery path in the oscript logic; the corrupted `mm_asset_outstanding == 0` combined with `$asset_balance != 0` state persists for the life of the AA. This matches the "AA fund loss or freezing" impact category.

### Likelihood Explanation
The attack requires only a single, cheap payment (dust amount of the paired asset, or an even smaller quantity of bytes) sent to a publicly known, deterministic AA address before the pool's first real investment is confirmed — no privileged access, no timing precision beyond ordinary front-running of an as-yet-unfunded contract, and no cost beyond a bounce/dust-sized transfer. Any AA author who copies this documented, ocore-provided reference pattern for detecting "first deposit" via a bare balance-equals-zero check is exposed.

### Recommendation
Do not infer "first/only deposit" state from `balance[asset] == 0`. Track initialization explicitly via a dedicated state variable (e.g., `var['initialized']` set exactly once, or `var['mm_asset_outstanding'] === undefined`) that cannot be manipulated by unsolicited transfers, and require that the genesis deposit case validate that the total value contributed by the trigger equals the *entire* current balance (rejecting/refunding stray pre-existing balances rather than silently treating any nonzero incoming balance as a normal deposit).

### Proof of Concept
1. Attacker learns/derives the market-maker AA's address (its definition, and therefore `chash160`, is public/predictable once the "asset" app response for `$asset` returns and the AA's overall definition template is known) before any real liquidity is added.
2. Attacker sends `1` unit of `$asset` directly to the AA's address (a normal payment, valid regardless of AA/trigger semantics) [3](#0-2) .
3. This output becomes part of `aa_balances[address][$asset]` once observed/aggregated [1](#0-0) .
4. Victim posts the intended first "invest in MM" deposit with real bytes and `$asset` amounts.
5. `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` evaluates to `1` (nonzero) due to the attacker's earlier donation, so the genesis branch at line 38 is skipped, `var['mm_asset_outstanding']` remains `0`, and `$issue_amount` computed at line 47 is `0` — the victim's deposit is absorbed with zero shares returned [11](#0-10) .
