### Title
Cross-organization webhook forgery via mismatch between the org used for `X-Hub-Signature` verification and the `repository.full_name` field used by webhook handlers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a delivery with by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, unverified JSON body [1](#0-0) , [2](#0-1) . Once the HMAC is judged valid for that organization, the *entire* raw payload — including a completely independent `repository.full_name` field — is handed unmodified to every registered webhook handler [3](#0-2) . Every handler resolves the repository/stack to act on via `payload.dig('repository', 'full_name')` [4](#0-3) , and nothing cross-checks that `full_name`'s owner segment matches the `repository.owner.login` (or `organization.login`) that was used to select the signing secret.

### Finding Description
Shipit supports hosting multiple GitHub organizations from one instance, each with its own `webhook_secret` configured under `secrets.github.<org>` [5](#0-4) . The binding the security model depends on is:

`organization whose secret authenticated the HMAC == organization owning the repository the payload writes to`

In `verify_signature`, the org used to look up the verifying `GitHubApp`/secret is taken from the payload itself, before the signature has been checked:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

Once `verified` is true, `WebhooksController#create` dispatches the raw, attacker-supplied `params` to the handlers [3](#0-2) . Every handler (base `Handler`, `PushHandler`, `StatusHandler`, all `PullRequest::*Handler`s) resolves the target repository/stack purely from `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) [7](#0-6) [8](#0-7) 

`repository.owner.login` (used for signature routing) and `repository.full_name` (used for authorization/lookup) are two independent JSON fields in the same body — nothing forces `full_name.split('/').first == owner.login`. `Repository.from_github_repo_name` looks the repo up globally by `owner/name`, with no relation to which org's secret verified the request [9](#0-8) .

**Before the attacker's request:** owner of organization "orgA" (configured in this Shipit instance, whether by legitimate multi-tenant setup or an attacker who registers/administers their own small org+app against the same shared Shipit instance) knows `orgA`'s `webhook_secret`. They have no access to `victim-org`'s secret, and no write access to `victim-org`'s repositories on GitHub.

**After the attacker's request:** they POST to `/webhooks` a raw body where `repository.owner.login` = `"orgA"` and `repository.full_name` = `"victim-org/victim-repo"`, signed with orgA's own known secret via `X-Hub-Signature`. `verify_signature` picks orgA's `GitHubApp`, the HMAC checks out (attacker knows the secret), and the handlers then act on `victim-org/victim-repo`'s stacks using data the attacker fully controls.

This breaks the equality: **organization that authenticated (orgA) != repository being written (victim-org/victim-repo)**.

### Impact Explanation
Depending on event type this yields cross-repository writes into stacks the attacker does not own or control, without any GitHub-side permission on that repository:
- `push` → `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` for the victim stack with an attacker-chosen `after` SHA [10](#0-9) .
- `pull_request` (`opened`/`closed`/`labeled`/`reopened`) → attacker can `find_or_create!`, `archive!`, `unarchive!` review stacks belonging to the victim repository [11](#0-10) , [12](#0-11) .
- `status` → `StatusHandler` writes a commit status onto any `Commit` matching `params.sha` (not even scoped by repository) via `commit.create_status_from_github!` [13](#0-12) , which can be used to forge green CI/status checks that Shipit's deploy-gating logic relies on to decide deployability — leading toward an unauthorized deploy.

This satisfies the "cross-repository writes" / "unauthorized deploy" High/Critical impact bar defined in scope.

### Likelihood Explanation
Exploitability requires the attacker to control (or know the `webhook_secret` of) at least one organization that is configured in the same Shipit instance as the victim — i.e., a multi-tenant/multi-org Shipit deployment (explicitly supported per `Shipit.github_organizations`/`github_app_config` [5](#0-4) ). No GitHub credentials, Shipit session, or `ApiClient` token for the victim repository are required — only the ability to sign an arbitrary HTTP body with a secret the attacker legitimately possesses for their own org, then POST it directly to the shared `/webhooks` endpoint. This is a real, low-effort exploit path in any deployment using the documented multi-org `secrets.yml` schema.

### Recommendation
After signature verification succeeds, re-derive the organization strictly from the verified `repository.full_name` (or `repository.owner.login`) and confirm it matches the organization whose secret validated the signature (i.e., require `repository.full_name.split('/').first == repository_owner` before dispatching to handlers, or better, resolve the target `Repository`/`Stack` and confirm its `owner` equals `repository_owner` used for verification). Handlers should reject events whose declared repository does not belong to the organization that authenticated the request.

### Proof of Concept
1. Configure/host two orgs in one Shipit instance per the documented multi-org schema, `orgA` (attacker-controlled, webhook secret `secretA` known to attacker) and `victim-org` (has stacks in this Shipit instance, secret unknown to attacker).
2. Attacker builds JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")` (from `repository.owner.login`), verifies successfully against `secretA` [1](#0-0) .
5. `PushHandler#process` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stacks [10](#0-9)  — a write to a repository the attacker never authenticated for.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
