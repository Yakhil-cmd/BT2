## Root cause

`Shipit::Api::BaseController` scopes every stack lookup to the authenticated `ApiClient`'s assigned stack when one is set: [1](#0-0) 

`stacks` returns `Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true, and every other API controller (`StacksController`, `DeploysController`, `TasksController`, `HooksController`, `CommitsController`, `LocksController`, …) resolves the target stack through this scoped `stack`/`stacks` helper, so a client token minted for stack A cannot touch stack B.

`Shipit::Api::CCMenuController` overrides `stack` and bypasses that scoping entirely: [2](#0-1) 

It resolves the stack via `Stack.from_param!(params[:stack_id])` — an unscoped, engine-wide lookup — instead of `stacks.from_param!(params[:stack_id])`. The only check performed is `require_permission :read, :stack`, which only verifies that `'read:stack'` is present in the token's `permissions` list; it never verifies that the `stack_id` in the request matches the stack the token was scoped to via `ApiClient#stack_id`: [3](#0-2) [4](#0-3) 

## The broken binding

Equality that should hold but doesn't: `stack_touched_by_request == stack_authorized_for(current_api_client)`.

- Before the request: an `ApiClient` is created scoped to a single stack (e.g. fixture `here_come_the_walrus`, `stack: shipit`, `permissions: ['read:stack']`) — see [5](#0-4) . Its token authorizes reads on that one stack only, as proven by the sibling controller test `"an api client scoped to a stack will only see that one stack"` [6](#0-5) .
- After the request: `GET /api/{other_stack}/ccmenu?token=<token>` reaches `CCMenuController#show`, which calls the unscoped `stack` method and returns deploy/status data for **any** `stack_id` supplied in the URL, not just the one the token is bound to.

Because the `authenticate_api_client` override in this controller accepts the token via a plain query-string parameter (`ApiClient.authenticate(params[:token])`) rather than HTTP Basic auth, this is trivially reachable by anyone who obtains a stack-scoped CCMenu token (these URLs are explicitly designed to be embedded/shared, see `CCMenuUrlController`), and lets them read deploy status, last build state, and CI failure/lock state of stacks they were never authorized for.

## Impact

This crosses the boundary listed as High severity: "unauthenticated read of stack state, task streams or deploy output" — a token scoped to stack A can read the CI/deploy state (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state) of any other stack B in the installation, including private/internal stacks the token holder has no business seeing.

## Recommendation

`CCMenuController#stack` should resolve through the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) exactly like every other `Api::BaseController` subclass, so the `stack_id` scope baked into the `ApiClient` is actually enforced.

## Caveat

I could not fully verify `Stack.from_param!`'s exact implementation (its body wasn't returned by search, likely truncated by index size limits), but its usage pattern everywhere else in the codebase (`stacks.from_param!` vs. bare `Stack.from_param!`) is consistent and the fixture/test evidence above confirms the scoping contract that `CCMenuController` violates. If you need the exact `from_param!`/`from_param` method bodies, a full Devin session with repo access would be needed to inspect `app/models/shipit/stack.rb` in full.
