### Title
Webhook signature is verified against a different organization than the repository the payload's handlers act on, allowing cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to check the HMAC signature against using `repository_owner`, which is read straight out of the **unverified** JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Once the signature check passes, `create` dispatches the same raw, unverified body to event handlers, which instead resolve the target `Repository`/`Stack` using a *different* field of the same body: `payload.dig('repository', 'full_name')`. Because Shipit supports configuring multiple GitHub organizations, each with its own `webhook_secret` [1](#0-0) , an attacker who legitimately owns one configured organization can forge a payload whose `repository.owner.login` matches their own org (so the signature validates against their own secret) while `repository.full_name` points at a stack belonging to a completely different, victim organization.

### Finding Description
`verify_signature` picks the app/secret using the attacker-controlled `repository_owner` value taken from the JSON body before any cryptographic check is performed: [2](#0-1) [3](#0-2) 

The signature is verified over the entire raw body using that org's secret via `GithubApp#verify_webhook_signature`: [4](#0-3) 

Once verification passes, `create` forwards the parsed body unchanged to the registered handlers: [5](#0-4) 

But every handler resolves the acted-upon repository/stack from a **different field** of the same body — `repository.full_name` — with no cross-check against the organization used for signature verification: [6](#0-5) 

This pattern repeats across handlers, e.g. `PushHandler#process`, which triggers `stack.sync_github` for any not-archived stack matching the branch of the (attacker-chosen) repository: [7](#0-6) 

and pull-request handlers that archive/deprovision or unarchive review stacks based on `params.repository.full_name`, independent of which org's secret signed the request: [8](#0-7) [9](#0-8) 

This is exactly the trust-binding break described by the rules: the organization whose secret authenticated the request (`repository.owner.login`) is not equal to the repository whose stacks are written to (`repository.full_name`). Both fields live in the same attacker-supplied JSON, and only one of them is cryptographically bound to a verified secret.

### Impact Explanation
An attacker who controls (or is granted) their own GitHub organization configured in Shipit's multi-org `github:` config can send a validly-signed webhook (using their own legitimate `webhook_secret`) whose `repository.full_name` names an arbitrary victim repository/stack tracked by a different organization. Handlers such as `PushHandler` will enqueue `stack.sync_github(expected_head_sha: ...)` for the victim's stack, and pull-request handlers will archive/deprovision or unarchive the victim's review stacks — all cross-organization writes performed without ever presenting a valid secret for the victim's organization. This matches the "cross-repository writes" / "unauthorized... rollback" impact class.

### Likelihood Explanation
Exploitability requires the attacker to control at least one organization that is configured in the Shipit instance's `github:` section (a normal, low-privilege prerequisite for any Shipit installation servicing multiple orgs — e.g. a self-service internal deploy platform onboarding many teams' orgs), and knowledge of a victim repository's `full_name` tracked by another onboarded org, which is public information. No repository write access, `ApiClient` token, or session is required — only a webhook secret the attacker legitimately possesses for their own org. This is realistic wherever Shipit is configured with `github: { org_a: {...}, org_b: {...} }` as documented.

### Recommendation
After verifying the webhook signature, re-derive the trusted organization from the verification step and require that `repository.owner.login` (used for signature selection) match the organization owning the `Repository` resolved via `repository.full_name` before any handler acts on it. Alternatively, pass the verified organization explicitly into `Handler#stacks`/`#repository_name` resolution and scope the `Repository.from_github_repo_name` lookup to that organization, rejecting the event if the two disagree.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as supported by `config/secrets.yml`).
2. As the attacker (who legitimately owns `attacker-org` and its webhook secret), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Compute `X-Hub-Signature` using `attacker-org`'s webhook secret over the raw body and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `attacker-org` (from the same body), fetches `attacker-org`'s `GithubApp`, and successfully verifies the signature.
5. `create` dispatches the body to `PushHandler`, which resolves stacks via `payload.dig('repository', 'full_name')` = `victim-org/victim-repo`, and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on the victim's stack — a cross-organization write triggered without ever presenting `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
