### Title
Webhook signature authenticates the `repository.owner.login` organization while event handlers act on the independent, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The `ERC20TokenEmitter` bug is a case where a value the contract's math depends on (`timeSinceStart`) is never bounded/validated against what's actually verified before being trusted. The same trust-binding gap exists in `Shipit::WebhooksController`: the field used to select which secret verifies the HMAC signature (`repository.owner.login`) is a *different* JSON field from the one every event handler later trusts to pick the `Stack`/`Repository` to mutate (`repository.full_name`). Nothing ties these two fields together, so in a multi-organization Shipit deployment, a payload can be "authenticated" as belonging to one (weakly-configured) organization while acting on a completely different, fully-secured organization's repository.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the payload itself, not from anything cryptographically bound to the request: [1](#0-0) [2](#0-1) 

`repository_owner` is resolved from `params.dig('repository', 'owner', 'login')` and is used to select which `GitHubApp` (and thus which `webhook_secret`) validates the signature via `Shipit.github(organization: repository_owner)`.

Meanwhile, every default event handler (push, status, pull_request, check_suite, membership) determines the actual `Repository`/`Stack` to act on from a **separate** payload field, `repository.full_name`, with no cross-check against `repository.owner.login`: [3](#0-2) [4](#0-3) 

For multi-org configurations, `Shipit.github_app_config(organization)` looks up an independent config (including its own `webhook_secret`) per organization: [5](#0-4) [6](#0-5) 

And `GitHubApp#verify_webhook_signature` explicitly no-ops when that organization's `webhook_secret` is blank: [7](#0-6) 

Since `webhook_secret` is documented as optional per organization ("If you've set a webhook secret during the App creation, you should copy it here"), it is plausible for an operator running a multi-org Shipit instance to have one organization configured without a secret (e.g. a legacy/staging org) while other organizations are fully secured.

**The broken binding (equality that should hold but doesn't):**
`organization used to select/verify webhook_secret` (`repository.owner.login`) **≠** `organization/repository whose Stack is mutated by the handler` (`repository.full_name`).

**Attack sequence:**
1. Attacker crafts a JSON payload where `repository.owner.login = "weak-org"` (an organization configured in `secrets.github` with no `webhook_secret`), but `repository.full_name = "victim-org/victim-repo"` (a tracked, fully-secured stack).
2. `verify_signature` calls `Shipit.github(organization: "weak-org")`, gets a `GitHubApp` whose `webhook_secret` is blank, and `verify_webhook_signature` returns `true` unconditionally — no valid HMAC is required at all.
3. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs, and the handler (e.g. `PushHandler`) resolves `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — i.e. `victim-org/victim-repo`.
4. The forged, unsigned event is fully processed against the victim stack.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose credential authorized this request" and "the repository being written to," matching the Critical bucket for unauthorized deploy/cross-repository writes:
- A forged `push` event causes `GithubSyncJob` to sync commits for the victim stack; if `continuous_deployment` is enabled on that stack, this leads to an **unauthorized deploy**.
- A forged `status` event can flip commit statuses used by `required_statuses`/CI gating, bypassing deploy-safety checks for the victim stack.
- A forged `membership`/`pull_request` event can manipulate team membership or review-stack state cross-organization.

This requires no credentials belonging to the victim organization at all — only knowledge that some organization configured in the same Shipit instance lacks a `webhook_secret`.

### Likelihood Explanation
Requires a specific but plausible operational condition: a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` set (explicitly supported/optional per `docs/setup.md`). This is a realistic misconfiguration in enterprise/multi-org Shipit setups (e.g. an org added for testing before a secret was provisioned), and the mismatch between `repository.owner.login` and `repository.full_name` is unconditional — no other precondition is needed once the weak org exists.

### Recommendation
Bind signature verification to the same repository identity the handlers act on: derive the verifying organization from `repository.full_name`'s owner segment (or require `repository.owner.login == repository.full_name.split('/').first`) before dispatching to handlers, and reject/require a non-blank `webhook_secret` for every configured organization instead of silently trusting unsigned payloads when one is absent.

### Proof of Concept
Given a Shipit instance configured with organizations `weak-org` (no `webhook_secret`) and `victim-org` (secured), POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "weak-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No `X-Hub-Signature` header is required to pass validation, since `Shipit.github(organization: "weak-org").verify_webhook_signature` short-circuits to `true` [8](#0-7) 
, while `PushHandler` targets stacks under `victim-org/victim-repo` [9](#0-8) 
, triggering a sync/deploy for a stack the attacker was never authorized to affect.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
