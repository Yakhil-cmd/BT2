### Title
`r of set` / `weighted and` / `and` definitions do not enforce that set members are distinct signers, allowing one keyholder to satisfy an M-of-N spending condition alone - ([File: definition.js])

### Summary
`QVBaseStrategy.reviewRecipients()` lets one manager cast unlimited "reviews", defeating an `M`-of-`N` threshold that is meant to require independent approvals from distinct reviewers. The analogous weakness exists in Obyte's address-definition ("oscript") threshold primitives `r of set` and `weighted and`, which are evaluated purely by counting satisfied branches/paths without ever checking that those branches correspond to distinct signers/keys.

### Finding Description
Address spending conditions are boolean expressions validated by `validateDefinition()`/`evaluate()` in `definition.js`. For `r of set`, the code only checks structural constraints (`required` is a positive int, `set` is an array of length ≥2, `required <= set.length`) and never checks whether the elements of `set` are distinct signers: [1](#0-0) 

At signature-verification time, `validateAuthentifiers()`'s `r of set` handler simply counts how many child branches evaluate to true and compares against `required`, with no deduplication by underlying pubkey/address: [2](#0-1) 

The same "count satisfied branches, no uniqueness check" pattern applies to `and`/`or` and `weighted and`: [3](#0-2) [4](#0-3) 

Because each `set` element is just an independent boolean sub-expression (e.g. `["sig", {pubkey: X}]`) evaluated at a distinct path (`r.0`, `r.1`, ...), nothing stops the same `pubkey` (or the same `["address", A]` sub-branch) from being placed in two or more slots of the `set`. A single private-key holder can then produce a valid signature for every slot that references their own key (the signature payload, `unit_hash_to_sign`/`getSignedPackageHashToSign`, is identical for the whole unit, so the same signature bytes satisfy every `sig` node using that pubkey), letting them alone reach `required` even though the definition superficially looks like an N-of-M multisig requiring independent cooperators.

This is directly exploitable in the shared/multisig address flow: `wallet_defined_by_keys.js`'s `createMultisigWallet()` builds exactly this kind of `r of set` template from a list of device addresses: [5](#0-4) 

and `handleNewSharedAddress()` in `wallet_defined_by_addresses.js`, which processes a peer-proposed shared-address `definition`, validates that every signing path has a corresponding `signers` entry and every entry's address matches the definition — but never verifies that the *set of underlying addresses/pubkeys referenced across the whole definition are pairwise distinct*: [6](#0-5) 

A malicious co-signer proposing a "2-of-3 shared address" can therefore craft a definition where two of the three `set` slots reference their own pubkey/address (disguised behind different paths or a nested `and`/`address` wrapper) and only one slot references the honest counterparty's key. The honest party sees a definition whose per-path signer list looks legitimate (address matches), approves it believing genuine 2-of-3 cooperation is required, but the malicious proposer can single-handedly satisfy the `required` threshold and spend/control the shared funds without ever needing the honest co-signer's signature.

### Impact Explanation
This breaks the fundamental security guarantee of `r of set` / `weighted and` multisig-style address definitions: instead of requiring cooperation of `required` distinct parties, one party can unilaterally satisfy the threshold if their key occupies multiple slots. In a shared-address / escrow / arbiter-contract context, this results in unauthorized spending of jointly-held funds by a single party who crafted (or was allowed to craft) the shared definition — a concrete loss-of-funds impact for the deceived counterparty.

### Likelihood Explanation
Any unprivileged user can define an address (or propose a "new_shared_address" definition to a peer) with attacker-chosen oscript, so reaching this path requires no special privilege — only that a counterparty accept a maliciously-constructed multisig definition without independently auditing every leaf `sig`/`address` node in the `set` for duplicate underlying keys. This is realistic in wallet/shared-address UX flows where cosigners are expected to trust the aggregated `signers` map rather than manually re-deriving key-uniqueness across the whole boolean tree.

### Recommendation
When validating `r of set` and `weighted and` (and ideally `and`/`or`) during `validateDefinition()`, collect the set of underlying `sig` pubkeys / `address` references reachable from each set element and reject the definition if the same pubkey or address appears in more than one element of the same `set`/`or`/`and` group used to satisfy a threshold count. Additionally, `handleNewSharedAddress()` should validate that no two signing paths in `assocDefinitionAddresses` map to the same signer address for a given `r of set`/`weighted and` node, so that peers cannot be tricked into approving a multisig definition where one party controls more than the intended number of slots.

### Proof of Concept
1. Attacker chooses a pubkey `P` (their own) and honest counterparty's pubkey `Q`.
2. Attacker constructs `arrDefinition = ["r of set", {required: 2, set: [["sig",{pubkey:P}], ["sig",{pubkey:P}], ["sig",{pubkey:Q}]]}]` (or hides the duplication behind two different nested `["address", innerAddr]` wrappers that both resolve to attacker-controlled keys).
3. Attacker computes `address = objectHash.getChash160(arrDefinition)` and sends a `new_shared_address` message with a `signers` map that superficially assigns paths `r.0`→attacker, `r.1`→attacker (labeled differently, e.g. via a second address they control), `r.2`→honest party.
4. Honest party's `handleNewSharedAddress()` only checks `assocDefinitionAddresses[signing_path] === signerInfo.address` per path and that every def path has a signer — it never checks that at least 2 *distinct* real-world parties are required, so it accepts and funds the shared address.
5. Attacker signs `r.0` and `r.1` themselves with `P`, satisfying `required:2` in `evaluate()` at `definition.js:692-711` without ever needing `Q`'s cooperation, and spends the funds.
