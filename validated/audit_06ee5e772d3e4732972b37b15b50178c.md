### Title
Webhook signature verification is keyed to a different repository field than the one the handlers act on, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the request against using `repository.owner.login` (falling back to `organization.login`) taken directly from the unauthenticated JSON body. Every webhook `Handler` then determines the repository/stacks that are actually mutated using a **different** field of the same payload: `repository.full_name`. Because these two lookups are not cryptographically bound together, an attacker can pick an organization whose config has no `webhook_secret` configured to trivially pass verification, while pointing `repository.full_name` at a different, real, secured organization's repository, causing forged events to be applied to that repository's stacks.

### Finding Description
`verify_signature` picks the GitHub App config to validate against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the attacker-supplied, not-yet-verified JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`).

`GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

This is not a hypothetical corner case — the documented/example multi-org configuration explicitly ships with `webhook_secret: # nil` per organization: [4](#0-3) 

Once "verified", every concrete webhook `Handler` derives the actual repository/stacks to mutate from a *different* payload field, `repository.full_name`, not from `repository.owner.login`/`organization.login` used for signature routing: [5](#0-4) 

Because `repository_owner` (used to select and validate the HMAC) and `repository_name`/`repository.full_name` (used to select the target stacks) are two independent, attacker-controlled fields inside the same unauthenticated JSON body, an attacker can craft a payload where:
- `repository.owner.login` (or `organization.login`) = an organization configured with no `webhook_secret` (verification trivially passes), and
- `repository.full_name` = `"<victim-org>/<victim-repo>"`, a different, properly secured organization's repository that has real Shipit stacks.

The signature check never validates that the org used to authenticate the request is the same org that owns the repository being acted upon — an equality of the form `authenticated_org == repository.full_name.split('/').first` is never enforced.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding. With a forged, unauthenticated event the attacker can drive any handler against a victim's real stacks without ever knowing the victim organization's `webhook_secret`:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for arbitrary shas on the victim's branches. [6](#0-5) 
- `StatusHandler` creates a forged CI status (e.g. `state: success`) on an arbitrary commit sha of the victim repository. [7](#0-6) 
- Combined with `Stack#continuous_deployment?` / `ContinuousDeliveryJob`, a forged successful CI status can enable an unauthorized/continuous deploy of attacker-influenced commits, since the job only checks `stack.continuous_deployment?`/schedule/occupancy, not the authenticity of the underlying CI signal. [8](#0-7) 
- `MembershipHandler`/`PullRequest` handlers can create arbitrary teams/users or archive review stacks tied to the victim repository.

This qualifies as a High-impact finding: "unauthenticated read/write of stack state ... via [a boundary]" and can escalate to an "unauthorized deploy" per the rules — attacker-controlled forged webhook events reach and mutate a victim organization's stacks despite never possessing that organization's credentials.

### Likelihood Explanation
The endpoint is a public, unauthenticated controller (`skip_before_action :verify_authenticity_token`), reachable by anyone who can send an HTTP POST. The only requirement is that the Shipit deployment is configured with more than one GitHub organization and at least one of them has no `webhook_secret` set — which is the exact configuration shown in this engine's own example/test config (`test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.example.yml`). No GitHub credential, Shipit session, ApiClient token, or webhook secret of the targeted (victim) organization is required — only knowledge that a second, low-security org exists in the same Shipit instance.

### Recommendation
Bind the value used to select/verify the webhook signature to the value used to identify the repository/stacks the handler will mutate — e.g., derive both from the same field, and additionally verify (post-authentication) that `repository.full_name`'s owner matches the organization whose secret validated the request. Do not allow an org with an empty `webhook_secret` to authenticate events referencing a different organization's repository. Consider also refusing to route webhooks for organizations with no `webhook_secret` configured, or forcing all configured orgs in a multi-org deployment to require a secret.

### Proof of Concept
Given a Shipit instance configured with two orgs (as in `test/dummy/config/secrets_double_github_app.yml`), where `OrgUnsecured` has `webhook_secret: nil` and `OrgVictim` has a real repository/stack with a real `webhook_secret`:

```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # ignored because OrgUnsecured has no webhook_secret

{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci",
  "repository": {
    "owner": { "login": "OrgUnsecured" },
    "full_name": "OrgVictim/victim-repo"
  }
}
```

`repository_owner` resolves to `OrgUnsecured` → `Shipit.github(organization: "OrgUnsecured").verify_webhook_signature` returns `true` unconditionally (no secret configured) → request passes `verify_signature` → `StatusHandler#process` looks up `Commit.where(sha: params.sha)` on `OrgVictim/victim-repo`'s stacks (via `repository_name` = `repository.full_name`) and creates a forged successful status, without the attacker ever knowing `OrgVictim`'s `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
