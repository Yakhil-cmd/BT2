### Title
Stack-scoped API token can read CCMenu deploy status of any stack, bypassing its stack authorization - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper to bypass the stack-scoping enforced by `BaseController`, allowing an `ApiClient` token that is authorized for a single stack to read the CI/CD status (CCMenu XML) of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the trust binding between a token and the stacks it may touch: `stacks` restricts the visible set to the client's assigned `stack_id` when one is set, and the generic `stack` helper resolves the requested `:stack_id` param only within that restricted `stacks` relation. [1](#0-0) 

`CCMenuController`, however, defines its own `stack` method that resolves the `:stack_id` param directly against `Stack.from_param!`, completely bypassing the `stacks` scoping method that enforces `current_api_client.stack_id`: [2](#0-1) 

The controller only checks that the token holds the `read:stack` permission via `require_permission :read, :stack`, using `ApiClient#check_permissions!`, which validates the operation/scope pair but has no knowledge of which specific stack ID the client is bound to: [3](#0-2) 

The test fixtures confirm that `ApiClient` records can be scoped to a specific stack (`stack: shipit`), and that this scoping is meant to be enforced elsewhere (e.g. `StacksController#index`): [4](#0-3) [5](#0-4) 

This is exactly the binding-break class described: "a stack a token authorises versus a stack it touches." The token is only authorized (by its `stack_id` column) to act on one stack, but `CCMenuController#show` lets it touch (read) the status of any stack by supplying a different `stack_id` request parameter, because the resolution path (`Stack.from_param!`) never consults `current_api_client.stack_id`.

### Impact Explanation
This is an authorization-scope escalation: a token deliberately restricted to a single stack (for example, issued to an external CI badge/monitoring integration for one project) can be used to enumerate and read the deploy/build status, last deploy id, and running state of every other stack managed by the Shipit instance. This matches the in-scope High-impact category of "escalation into unauthenticated/unauthorized read of stack state, task streams or deploy output" — here achieved by escalating a validly-authenticated but stack-scoped token beyond its authorized stack.

### Likelihood Explanation
Likelihood is high for any deployment that issues per-stack scoped `ApiClient` tokens (a documented, intended feature) to third parties, e.g. exposing a CCMenu/CI status badge to an external system, since no privileged access or social engineering is needed — only knowledge of another stack's `to_param` (repo/env/branch identifier), which is often guessable/public information (stack names mirror repository names/environments).

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` collection (as `BaseController#stack` does) instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and remove the private override entirely so the base implementation (which is stack-scope aware) is used.

### Proof of Concept
1. Create/observe an `ApiClient` scoped to stack "shipit" with only `read:stack` permission (matches fixture `here_come_the_walrus`) — this token is meant to see only the "shipit" stack, as enforced and tested for `StacksController#index`.
2. Authenticate to the CCMenu API endpoint using that token's `authentication_token`, but pass a `stack_id` parameter for a *different* stack (e.g. `soc` or any other environment) that the token is not scoped to:
   `GET /api/{other_stack_id}/cc.xml` with `Authorization: Basic base64(token)`
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`, the lookup succeeds for the unauthorized stack, and `show` renders that stack's latest deploy/rollback status (id, `ended_at`, `running?`) in the XML response — an unauthorized cross-stack information disclosure that the base controller's `stacks`/`stack` scoping was specifically designed to prevent.
