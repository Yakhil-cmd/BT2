## Analysis

The Aloe bug class is: a liquidation flow that must transfer an asset to a specific (attacker-controlled) recipient reverts entirely if that transfer is blocked (e.g., a blacklisted/incompatible recipient), so the whole liquidation — including debt cleanup — never completes, creating bad debt.

The closest reachable analog in `ocore` is in the **Autonomous Agent (AA) response engine**. When an AA sends a `payment` message as part of its response, `aa_composer.js`'s `sendUnit()` builds the response unit and hands it to `validateAndSaveUnit()`, which runs the full unit validator (`validation.js`). If validation fails for *any* message in the unit — including because a payment output address fails an asset's `spender_attested` requirement or its `transfer_condition`/`issue_condition` formula — the AA does not selectively skip that payment; it calls `bounce(err)`, which discards **all** state changes performed by the trigger (via `revert()`/`ROLLBACK TO SAVEPOINT`) and returns only the leftover base-asset fee to the trigger address.

Concretely:
- `validatePaymentInputsAndOutputs` requires every output address of a `spender_attested` asset to be attested (`storage.filterAttestedAddresses`), and separately evaluates a custom `transfer_condition`/`issue_condition` formula against the recipient; either failing causes `callback("some output addresses are not attested")` or `callback("transfer or issue condition not satisfied")`. [1](#0-0) 
- In the AA composer, this validation failure propagates up through `validateAndSaveUnit`, immediately triggering `bounce(err)`. [2](#0-1) 
- `bounce()` unconditionally erases the response and any state updates the AA made in this trigger (balances, `stateVars`), refunding only the leftover base bytes to the trigger's address — it cannot selectively drop just the one problematic payment message. [3](#0-2) 
- On non-primary/secondary paths, `revert()` rolls back to the savepoint and clears `stateVars` and cached responses before bouncing. [4](#0-3) 

So any AA-based protocol on Obyte that pays out a restricted asset (an asset with `spender_attested: true`, or a `transfer_condition`/`issue_condition` formula) to a trigger-supplied or state-recorded address is exposed to the same DOS pattern as the Aloe finding: an address that permanently fails the attestation/condition check (e.g., an attestor revokes/never grants attestation, or a `transfer_condition` formula that is unsatisfiable for that address) makes every AA response that tries to pay that asset to that address bounce forever, wiping the AA's accompanying state changes (e.g., debt/position closure bookkeeping) each time. Unlike a plain payment (which just fails for the one sender), this is *worse* in the AA context because a single failing payment message aborts the entire multi-message state transition, not just the transfer.

### Title
AA responses that pay a `spender_attested`/`transfer_condition`-restricted asset can be permanently bounced, wiping accompanying state changes (DOS on AA fund/position finalization) - (File: aa_composer.js)

### Summary
An Autonomous Agent that sends a payment of a restricted asset (`spender_attested: true`, or an asset with a `transfer_condition`/`issue_condition` formula) to an address controlled by, or associated with, the trigger sender bounces the *entire* response — including all state variable updates — whenever that address fails the attestation/condition check at validation time.

### Finding Description
`aa_composer.js`'s `sendUnit()` composes the AA's response unit and passes it to full unit validation (`validateAndSaveUnit`). Validation of a `payment` message for a non-`fixed_denominations`, non-`is_private` asset checks `objAsset.spender_attested` (every output address must be attested) and evaluates `objAsset.transfer_condition`/`issue_condition` against the recipient via `Definition.evaluateAssetCondition`. [1](#0-0) 
Any failure here surfaces as a validation error back in the AA composer, which calls `bounce(err)`: [2](#0-1) 
`bounce()` discards the whole computed state update (`objStateUpdate = null`), restores original balances/state (in `bAir` mode) and, outside `bAir`, relies on `revert()` to `ROLLBACK TO SAVEPOINT initial_balances` and clear `stateVars`/cached responses before re-entering bounce to refund only the leftover base bytes. [3](#0-2) [4](#0-3) 
There is no mechanism in the AA engine to skip or retry only the failing payment message while keeping the rest of the state transition — a single unsatisfiable recipient condition aborts the entire trigger's effect.

### Impact Explanation
Any AA (e.g., a lending/vault/DEX-style AA) that must pay out a restricted asset to record-holder addresses (trigger address, or an address stored in AA state from an earlier deposit/borrow trigger) can be permanently blocked from finalizing that operation if the recipient's attestation is revoked/never granted, or if the asset's `transfer_condition` formula evaluates to false for that address (e.g., it references a data feed, `attested`, or other externally-controlled condition). Because the bounce discards all of the AA's accompanying bookkeeping (debt clearance, position removal, balance updates) together with the failed payment, the position/state can become permanently stuck — mirroring the "liquidation can't complete, creating bad debt" impact from the Aloe report, but scoped to any AA logic gated on paying out a conditioned asset.

### Likelihood Explanation
Reaching this path requires only posting the AA-defining `asset` message with `spender_attested: true` (or a `transfer_condition`), plus normal user interaction: send/deposit funds via a trigger from an address, then have that address's attestation revoked or never attested (attestors are third parties named in the asset, not the AA), or design a `transfer_condition` formula whose evaluation can go permanently false for a specific address (e.g. depends on a data feed value that changes). No privileged network/node/peer access is needed — everything is reachable by unprivileged unit/trigger authors and attestors, matching the "AA definitions and triggers" / "asset issuance and transfer conditions" reachable surface.

### Recommendation
When an AA's outgoing `payment` message targets a restricted asset and the recipient fails `spender_attested`/`transfer_condition` checks, consider treating that specific message as droppable (similar to how zero-amount or `fixed_denominations` outputs are already filtered out before finalizing the unit) rather than unconditionally bouncing the whole trigger, or expose the check result to AA formula logic (e.g., via a getter) so AA authors can branch around dead-end payouts instead of losing all state progress. At minimum, document this hard dependency clearly so AA authors avoid conditioning critical state transitions (debt/position closure) on successful delivery of restricted assets to externally-controlled addresses.

### Proof of Concept
1. Define asset `A` with `spender_attested: true` and `attestors: [attestor_addr]` (or with a `transfer_condition` formula referencing `attested`/a data feed).
2. Deploy a lending-style AA whose "close position" response message includes `{app:'payment', payload:{asset:'A', outputs:[{address:'{trigger.address}', amount:...}]}}` together with state-variable updates that clear the user's debt/collateral record.
3. Have `attestor_addr` attest the borrower's address, let the borrower open a position (deposit collateral, borrow, etc.).
4. Before the borrower triggers "close position", have the attestor revoke/stop renewing the attestation (or otherwise make `transfer_condition` false for that address).
5. Borrower (or a liquidator) sends the closing trigger. `validatePaymentInputsAndOutputs` rejects the output address as unattested/condition-unsatisfied, `validateAndSaveUnit` returns an error, and `aa_composer.js` calls `bounce()`, discarding the debt-clearing state update — the position remains open/stuck indefinitely, an ongoing DOS on that user's position with no recovery path through the AA logic.
