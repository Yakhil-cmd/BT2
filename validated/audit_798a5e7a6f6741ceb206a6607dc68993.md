### Title
Permanent market freeze from RAY value overflow before the borrow-index cap engages — (File: common/src/rates/index.rs)

### Summary
The kernel bug is a lock-ordering deadlock: a function holds a lock while waiting for work that itself needs the lock, blocking forever. The analog in XOXNO Lending is an ordering deadlock in the accrual math: the protocol caps the borrow index at `MAX_BORROW_INDEX_RAY` specifically so index growth cannot freeze a market, but `calculate_supplier_rewards` computes `borrowed * new_borrow_index` — the unscaled debt value — *after* the cap and *inside* the accrual that every monetary entrypoint must run first. At a whale-scale market, that multiplication overflows `i128` (panics with `MATH_OVERFLOW`) before the index cap can engage, so `global_sync` can never complete and every verb on that market reverts permanently: no repay, no withdraw, no liquidation, no bad-debt cleanup.

### Finding Description
Every controller and pool verb accrues the market before mutating it: `interest::global_sync` chunks elapsed time and calls `accrue_step` per chunk. [1](#0-0) 

Inside each chunk, `calculate_supplier_rewards` computes `old_total_debt = borrowed.mul(old_borrow_index)` and `new_total_debt = borrowed.mul(new_borrow_index)` via `Ray::mul`, which panics on `i128` overflow. [2](#0-1) 

The borrow index itself is capped at `MAX_BORROW_INDEX_RAY` (~170x), which is the protocol's intended defense against runaway index growth. [3](#0-2)  But the cap clamps the *index*, not the *value*. For a market whose scaled `borrowed` is roughly `i128::MAX / 170` — a billion whole tokens at 18 decimals is `~1e36` raw ray — the debt value overflows at an index well below the cap. The panic is raised inside the accrual that `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `update_indexes` all run first, so it can never be skipped: the market is deadlocked — accrual cannot complete because accrual itself overflows.

The checked-in characterization test demonstrates exactly this: at 98% utilization on the XLM rate curve, `update_indexes` reverts with `MATH_OVERFLOW` after a few years, `borrow_index` remains below `MAX_BORROW_INDEX_RAY` (the cap never engaged), and both `withdraw` and `repay` revert with the same error. [4](#0-3) 

### Impact Explanation
Permanent freezing of user funds. Once the scaled debt value crosses the overflow boundary, no participant — supplier, borrower, or liquidator — can move tokens in that market ever again: suppliers cannot withdraw, borrowers cannot repay, and the bad-debt path (`clean_bad_debt`, `recapitalize`) also accrues first. All tokens held by the pool book for that (hub, asset) are bricked. This is the direct analog of the CVE's "blocks forever" outcome.

### Likelihood Explanation
The trigger requires a very large market — scaled debt on the order of `i128::MAX/170`, reachable for a high-supply 18-decimal asset (a ~1 billion whole-token book at 98% utilization, as the test constructs) with caps set large enough to admit it. Caps are validated by `require_cap_within_asset_domain`, which permits large caps, so this does not require a misconfiguration rejected by validation, though it does require an admin-listed market with generous caps and sustained near-max utilization over an extended period. The condition is irreversible once crossed — there is no recovery path, which is why the checked-in test asserts the freeze rather than a cap clamp. Likelihood is low in the near term but the outcome is total and unrecoverable, consistent with Medium.

### Recommendation
Clamp or saturate the debt-value computation rather than panicking on the post-cap value. Concretely, in `calculate_supplier_rewards` (`common/src/rates/index.rs:73-89`), use a saturating multiplication for `new_total_debt`/`old_total_debt` (or compute `accrued_interest` via a saturating `mul_div`), so that once `borrowed * MAX_BORROW_INDEX_RAY` exceeds `i128`, accrual still commits the capped index and `mark_accrued` advances `last_timestamp`, keeping the market operable. Alternatively, engage an earlier effective cap: derive the maximum safe index per market as `i128::MAX / borrowed.raw()` and clamp `new_borrow_index` to `min(MAX_BORROW_INDEX_RAY, that bound)` inside `update_borrow_index`, so the cap engages before the value multiplication can overflow.

### Proof of Concept
The repository already contains the executable proof — `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`):

1. Build a market with an 18-decimal asset on the XLM rate curve with caps lifted to admit the position; any unprivileged supplier/borrower pair performs: `supply(BOB, BIG18, 1e9 * 1e18)` and `borrow(ALICE, BIG18, 0.98e9 * 1e18)` via the public `supply`/`borrow` entrypoints.
2. Advance ledger time (public `update_indexes` keeper calls accrue it in chunks).
3. After the index grows past ~170x scale factor for that book, `update_indexes` reverts `MATH_OVERFLOW` with `borrow_index < MAX_BORROW_INDEX_RAY` — the cap never engages.
4. Subsequent `withdraw(BOB, 1)` and `repay(ALICE, ...)` revert `MATH_OVERFLOW`; every other accrual-first verb behaves identically. The market and all funds in it are permanently frozen.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```
