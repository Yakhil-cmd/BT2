### Title
Webhook Signature Verification Authenticates the Wrong Organization Relative to the Repository the Payload Acts On - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `params.dig('organization', 'login')`) — an untrusted, attacker-controlled field inside the request body. Every event handler, however, resolves the actual `Repository`/`Stack` to act on using a *different* field from the same body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a valid signature computed with one organization's secret can carry a payload whose `repository.full_name` names a repository belonging to a completely different organization/stack tracked by the same Shipit instance.

### Finding Description
Shipit officially supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` (`docs/setup.md`, commented multi-org example in `config/secrets.development.example.yml`). For each incoming webhook:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`verify_webhook_signature` only checks that the raw body's HMAC matches the secret configured for whatever organization name is embedded in the body itself:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

Every webhook handler (`PushHandler`, `PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, etc.) resolves the target `Repository`/`Stack` from the payload's `repository.full_name`, completely independent of `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

```ruby
def repository
  @repository ||=
    Shipit::Repository.from_github_repo_name(params.repository.full_name) ||
    Shipit::NullRepository.new
end
``` [4](#0-3) 

`Repository.from_github_repo_name` looks up a repository purely by the `owner/name` string parsed from that field, with no cross-check against the value used to select the signing secret:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [5](#0-4) 

**The binding that should hold but doesn't:**
`organization_authenticated_by(repository_owner) == organization_owning(repository.full_name)`

Because the entire raw HTTP body is what gets HMAC'd, and `repository.owner.login` (used for authentication) and `repository.full_name` (used for action) are two separate, independently attacker-writable JSON keys in that same body, anyone who knows the `webhook_secret` for **any one** organization configured on the Shipit instance can forge a payload that:
- sets `repository.owner.login` (or `organization.login`) to their own org, so `verify_signature` fetches and validates against their own known secret, and
- sets `repository.full_name` to `victim-org/victim-repo`, an entirely unrelated repository/organization tracked by the same Shipit instance.

The signature check passes (it's mathematically valid for the org whose secret was used), yet the handler acts on the victim repository.

### Impact Explanation
This breaks a repository-write trust boundary explicitly called out as Critical impact: **cross-repository writes**. With a forged webhook signed by an org they legitimately administer, an attacker can, against a victim repository they have no access to:
- Trigger `Repository#sync_github` on arbitrary branches (`PushHandler#process` → `stack.sync_github`) [6](#0-5) 
- Archive/unarchive/create Review Stacks for the victim's PRs (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`), causing provisioning/deprovisioning actions against infrastructure tied to a repository they don't control [7](#0-6) 

This directly matches the rule's Critical bucket ("cross-repository writes … or an unauthorized deploy, rollback or merge"), since `sync_github` and review-stack lifecycle actions on the victim stack are unauthorized, cross-organization mutations triggered purely by knowledge of an unrelated org's webhook secret.

### Likelihood Explanation
This is exploitable by any party who administers even one GitHub organization hosted on a shared, multi-org Shipit deployment (a configuration explicitly documented and supported), since such an admin necessarily knows/sets their own org's `webhook_secret` when configuring the GitHub App. No privileged Shipit session, `ApiClient` token, or GitHub App private key is required — only knowledge of one org's webhook secret and the ability to POST an arbitrary JSON body with a valid `X-Hub-Signature` to the public `/webhooks` endpoint. On a single-organization Shipit deployment this specific analog is not reachable (there is only one secret and it maps 1:1 to the only tracked repositories), but the moment the documented multi-org configuration is used, the boundary is broken as described.

### Recommendation
After computing `github_app` from `repository_owner` and verifying the signature, additionally verify that the resolved target repository (`payload.dig('repository', 'full_name')`) actually belongs to that same authenticated organization (e.g., assert that `repository.full_name.split('/').first.casecmp?(repository_owner)` or equivalent, matching the pattern of adding a third `notBlacklisted`-style check in the original report) before dispatching to any handler. Reject the webhook (422) if the owner embedded in `repository.full_name` does not match the organization whose secret validated the signature.

### Proof of Concept
1. Shipit is configured (as documented) for two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret`.
2. Attacker administers `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a-secret, raw_body)>` and sets `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully because the signature matches `org-a`'s secret over the exact raw body. [8](#0-7) 
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim stack, which the attacker never had access to. [6](#0-5)
