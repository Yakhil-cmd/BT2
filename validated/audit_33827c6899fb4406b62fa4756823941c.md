### Title
`Api::CCMenuController#stack` ignores the ApiClient's `stack_id` scope, letting a stack-scoped token read any stack's CCTray/deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces a binding between an `ApiClient` token and the stacks it may act on: when a client is `stack_id`-scoped, `stacks` is restricted to that single stack and `stack` is resolved through it. `Api::CCMenuController` overrides `stack` and resolves it directly from `Stack.from_param!(params[:stack_id])`, bypassing that scoping entirely, so a token authorized for stack A can be used to read stack B.

### Finding Description
`BaseController` defines the trust boundary "stack a token authorizes == stack it touches": [1](#0-0) 
`current_api_client.stack_id?` restricts `stacks` to the single authorized stack, and `stack` is looked up only within that scoped relation, so `stacks.from_param!` raises `ActiveRecord::RecordNotFound` for any other stack.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping and query `Stack` directly: [2](#0-1) 
Permission enforcement here only checks that the token carries the `read:stack` permission string via `require_permission :read, :stack` (`ApiClient#check_permissions!`) — it never checks that `params[:stack_id]` matches `current_api_client.stack_id`: [3](#0-2) 

An `ApiClient` can legitimately be created scoped to one stack (`belongs_to :stack, optional: true`), which is the documented mechanism for limiting a token's reach to a single stack: [4](#0-3) 

Before/after the payload difference:
- Before (intended binding): token.stack_id == A ⇒ `stack` for any request with this token resolves only to A (enforced in `BaseController#stack`/`#stacks`).
- After (in CCMenuController): token.stack_id == A, but `GET /api/stacks/B/ccmenu.xml` (or the analogous route with `stack_id: B`) still resolves `stack` to B because `Stack.from_param!(params[:stack_id])` ignores `current_api_client.stack_id`, breaking the equality that the rest of the API enforces.

### Impact Explanation
This is an unauthenticated-relative-to-scope escalation: a caller holding only a stack-A-scoped `read:stack` token can read stack B's CCTray XML, which exposes stack activity, last build status/label, last build time, and web URL for a stack it was never authorized to see: [5](#0-4) 
This matches the in-scope High-severity class "unauthenticated read of stack state, task streams or deploy output" because it grants cross-stack read access outside of the token's authorized scope, defeating the per-stack `ApiClient` isolation model that the rest of the API (`BaseController#stack`) relies on.

### Likelihood Explanation
Any legitimate holder of a stack-scoped, `read:stack`-permissioned API token (a normal, intended, low-privilege credential — e.g., issued via the CCMenu URL flow or the admin API-clients UI with a specific stack assigned) can trivially exploit this by substituting a different `stack_id` in the URL. No additional privilege, secret, or session is required beyond the token itself, which the scoping feature is specifically meant to constrain.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` collection from `BaseController`, i.e., use `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction applies uniformly across all API controllers.

### Proof of Concept
1. As an admin, create (or have `CCMenuUrlController` create) an `ApiClient` with `stack_id` set to Stack A and `permissions: ["read:stack"]`.
2. Using that client's `authentication_token`, issue: `GET /api/1/stacks/OWNER_B/NAME_B/ccmenu.xml` with `Authorization: Basic base64(token)`, where `OWNER_B/NAME_B` is Stack B (an entirely different, unauthorized stack).
3. Observe `200 OK` with Stack B's CCTray XML (`name`, `activity`, `lastBuildStatus`, etc.) returned, even though the token was only ever authorized for Stack A — confirmed by the fact that `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than the scoped `stacks.from_param!` used everywhere else in `Api::BaseController`.
