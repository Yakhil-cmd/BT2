### Title
Unbounded coin-selection loop in AA payment composition can cause AA response failure / fund freezing - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) responds to a trigger by sending a payment in a custom asset, `aa_composer.js`'s `completePaymentPayload` collects unspent outputs belonging to the AA and adds them one-by-one as inputs until the target amount is reached. For custom (non-base) assets there is no dust-amount filter and no cap on the number of inputs collected, unlike other coin-selection code paths in the codebase that explicitly enforce `constants.MAX_MESSAGES_PER_UNIT`/`MAX_INPUTS_PER_PAYMENT_MESSAGE`. This mirrors the reported class of bug: an unbounded loop whose iteration count is controlled by an attacker, which can make legitimate reward/response processing fail once resource limits are hit.

### Finding Description
`iterateUnspentOutputs` loops over every row returned by `readStableOutputs`/`readUnstableOutputsSentByAAs` and pushes each one into `payload.inputs` without any limit check: [1](#0-0) 

`readStableOutputs` only filters out dust for the base asset (`asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE`); for a custom asset, `amount` is unconstrained, so an attacker can create an unlimited number of dust outputs of that asset addressed to the AA: [2](#0-1) 

The same lack of a minimum applies to `readUnstableOutputsSentByAAs`: [3](#0-2) 

By contrast, the analogous coin-selection routine for indivisible assets explicitly caps the number of collected inputs against `constants.MAX_MESSAGES_PER_UNIT`: [4](#0-3) 

No equivalent cap exists in `completePaymentPayload`/`iterateUnspentOutputs`, so if the AA's balance in a custom asset is composed of a very large number of tiny outputs (attacker-controlled, since anyone can pay an asset to a public AA address), the loop can accumulate far more inputs than a single payment message or unit can legally contain.

### Impact Explanation
If the number of accumulated inputs required to cover the AA's outgoing payment amount exceeds the unit/message size or input-count limits enforced elsewhere in the codebase (e.g. `constants.MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, oversize-fee/size ceilings), the AA-composed response unit will fail post-composition/unit validation. Because AA execution is atomic (all state changes and balance updates are rolled back if the resulting unit cannot be composed/validated), this causes the AA's response to bounce or error out. Funds that were meant to be paid out by the AA become effectively stuck/inaccessible via that code path — the AA can receive the dust-poisoned asset but is unable to reliably compose a valid payment to spend it, directly matching the reported "inability to claim reward"/fund-freezing impact class.

### Likelihood Explanation
Any address (an unprivileged unit poster / asset counterparty) can send an arbitrary number of tiny-amount payments of a custom asset to a known AA address at negligible cost (since there's no minimum-amount dust filter for non-base assets). This does not require any AA cooperation or special privilege — only enough issuance capacity of a custom asset (which the attacker can create themselves) and enough fee-bytes to post many small payment units.

### Recommendation
- Apply a minimum-amount / dust filter to custom-asset outputs symmetrical to the existing base-asset filter in `readStableOutputs`/`readUnstableOutputsSentByAAs`.
- Cap the number of inputs collected in `iterateUnspentOutputs` against `constants.MAX_MESSAGES_PER_UNIT` / `MAX_INPUTS_PER_PAYMENT_MESSAGE`, mirroring the check already present in `indivisible_asset.js`.
- When the cap would be exceeded, allow the AA to compose a partial payment (batching) rather than bouncing the whole response, similar to the "claim rewards in several batches" mitigation recommended in the original report.

### Proof of Concept
1. Attacker issues a custom asset `X` with itself as the sole holder.
2. Attacker sends thousands of minimal-amount (e.g. 1-unit) `X` outputs to a target AA address `A` in many small units over time (cheap, since there's no dust filter for non-base assets).
3. Attacker triggers `A` in a way that causes it (per its oscript logic) to pay out `X` tokens to some recipient.
4. During response composition, `completePaymentPayload`/`iterateUnspentOutputs` iterates through all of the attacker's dust outputs trying to reach the target amount, producing far more inputs than the unit/message limits allow.
5. Unit composition/validation fails, the AA response bounces, and the AA cannot successfully send its `X` balance — funds remain stuck in the AA for that asset until the situation is otherwise resolved (e.g., manual cleanup, which is not exposed to normal users).
