### Title
Stale creator-fee ledger allows double collection via Token-2022 CPI reentrancy (checks-effects-interactions violation) - ([File: programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs])

### Summary
`collect_creator_fee_permissionless` (and its sibling `collect_creator_fee`) read `creator_fees_token_0`/`creator_fees_token_1` into local variables, perform two outbound token transfers using those cached values, and only zero out the ledger fields in `pool_state` *after* both transfers complete. This is the same root-cause pattern as the ERC20Pods `_removeAllPods` bug: a stale/cached balance is used to drive one or more external calls before the authoritative state is updated, so a callback triggered during the external call can observe and act on the not-yet-zeroed state.

### Finding Description
In `collect_creator_fee_permissionless`, the accounting update happens after both CPI transfers: [1](#0-0) 

The same ordering (compute → transfer → transfer → zero) exists in `collect_creator_fee`: [2](#0-1) 

This differs from the correct checks-effects-interactions pattern used elsewhere in the program, e.g. `collect_protocol_fee` and `collect_fund_fee`, which subtract from the ledger *before* issuing the transfers: [3](#0-2) 

The transfers are issued via `transfer_from_pool_vault_to_user`, which performs a `token_2022::transfer_checked` CPI into whichever token program owns the vault mint: [4](#0-3) 

On Solana, an SPL Token-2022 mint can carry a `TransferHook` extension, which causes `transfer_checked` to synchronously invoke an attacker-controlled hook program mid-transfer, before returning to the calling instruction. If such a hook program is invoked during the first (`token_0`) transfer inside `collect_creator_fee_permissionless`, it could attempt to re-enter the same instruction (this instruction is explicitly permissionless — any `payer` can call it, per the doc comment and account struct) while `creator_fees_token_0`/`creator_fees_token_1` are still un-zeroed in `pool_state`, potentially draining the vault a second time before the first invocation's zeroing write lands.

**Important caveat on exploitability:** I was not able to fully confirm within the available tool budget whether the program's mint-acceptance logic (`is_supported_mint` in `programs/cp-swap/src/utils/token.rs`, enforced at pool `initialize`/`initialize_with_permission` time) would actually reject mints carrying the `TransferHook` extension. The allow-list I found only explicitly permits `TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, and `ScaledUiAmount` extensions: [5](#0-4) 
If `TransferHook` is not in this allow-list, pools cannot be initialized with such mints (`is_supported_mint` would return `false` for a hook-bearing mint and, if enforced as a hard constraint at initialize time, block pool creation entirely) — in which case the reentrancy vector for existing pools would not be reachable through this path, and this analog would reduce to a defense-in-depth / code-quality issue (CEI ordering) rather than an exploitable one. I could not verify, in the remaining iterations, exactly how/whether `is_supported_mint`'s boolean result is enforced as a hard constraint in `initialize.rs`/`initialize_with_permission.rs` for *both* vault mints on *every* pool, nor whether any legacy/already-initialized pool could be created with a hook-bearing mint through another path.

### Impact Explanation
If reachable (i.e., if a pool can exist where `vault_0_mint` or `vault_1_mint` is a Token-2022 mint with an attacker-controlled `TransferHook`), an attacker who is also the `pool_creator` (or who can get creator fees routed to themselves) could re-enter `collect_creator_fee`/`collect_creator_fee_permissionless` during the hook callback and drain more from `token_0_vault`/`token_1_vault` than the recorded `creator_fees_token_0`/`creator_fees_token_1` actually entitle them to — a direct theft of pool/LP funds and an insolvent fee ledger, matching the "concrete theft ... or insolvent pool or fee-ledger accounting" acceptance criteria.

### Likelihood Explanation
Likelihood is **uncertain** and hinges entirely on whether `TransferHook`-extension mints are permitted by the pool's mint validation at `initialize`. I could not conclusively verify this within the tool budget. If such mints are rejected at pool creation (which the partial evidence I found suggests is likely, since `TransferHook` is absent from the allow-list in `is_supported_mint`), likelihood is low/none for existing/newly created pools. If there is any gap — e.g., a mint whose extensions pass `is_supported_mint` at creation time but later has a `TransferHook` extension added, or another instruction path that doesn't call `is_supported_mint` — likelihood would be high given the instruction is explicitly permissionless.

### Recommendation
Regardless of the mint-allow-list question, apply the same fix pattern as the referenced ERC20Pods remediation: zero out `creator_fees_token_0`/`creator_fees_token_1` (effects) in `pool_state` *before* issuing the `transfer_from_pool_vault_to_user` CPIs (interactions), matching the ordering already used in `collect_protocol_fee`/`collect_fund_fee`. This closes the CEI gap defensively even if the current mint allow-list happens to exclude `TransferHook` mints today, protecting against future changes to the supported-mint list or Token-2022 extension set.

### Proof of Concept
Conceptual (unverified end-to-end due to inability to confirm mint-acceptance gate):
1. Attacker creates (or becomes) the `pool_creator` of a pool where `vault_0_mint` is a Token-2022 mint carrying a `TransferHook` extension pointing to an attacker-controlled hook program — contingent on this being possible past `is_supported_mint`.
2. Creator fees accrue (`pool_state.creator_fees_token_0 > 0`).
3. Attacker (or anyone, since the call is permissionless) calls `collect_creator_fee_permissionless`.
4. Inside `transfer_from_pool_vault_to_user` for `token_0`, the Token-2022 program invokes the attacker's transfer-hook program before returning.
5. The hook program re-invokes `collect_creator_fee_permissionless` (or `collect_creator_fee`) again; `pool_state.creator_fees_token_0`/`creator_fees_token_1` are still non-zero (not yet reset by the outer call, which hasn't reached line 125-126 yet), so the transfers execute again.
6. The outer call's frame eventually also zeroes the fields, but the vault has already been drained twice for one accrual. [6](#0-5)

pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
