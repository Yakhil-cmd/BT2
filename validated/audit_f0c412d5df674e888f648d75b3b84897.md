### Title
Readiness/health endpoint reports "ready" even during persistent post-initial-sync failures - (File: main.go)

### Summary

### Finding Description
`git-sync` exposes an HTTP health/readiness endpoint whose `/` handler is documented to return a 5xx status until the first sync completes, and a 200 status "thereafter" [1](#0-0) . This is backed by a package-level boolean `repoReady`, guarded by `readyLock`, with `getRepoReady()`/`setRepoReady()` accessors [2](#0-1) .

`setRepoReady()` is called once inside `SyncRepo` after a successful publish [3](#0-2) , and again unconditionally in the main sync loop whenever `git.SyncRepo` returns without error [4](#0-3) . Critically, there is no corresponding "un-ready" transition: when `git.SyncRepo` returns an error, the code only increments `failCount`, records an error metric, and (if `failCount >= maxFailures`) exits the process — it never calls a `setRepoNotReady()`-equivalent [5](#0-4) .

This is directly analogous to the reported `TokenggAVAX`/`ERC4626Upgradeable` bug class: two logically-paired accessors (`maxWithdraw`/`maxRedeem` vs. `maxDeposit`/`maxMint`, and here `SyncRepo` success vs. failure paths for `repoReady`) are supposed to consistently reflect the same underlying "is the resource actually usable" state, but only one direction of the state transition is implemented. As in the original report, the resulting stale/incorrect status is returned to an external consumer (there, `maxDeposit`; here, the Kubernetes readiness/liveness HTTP probe at `--http-bind`).

### Impact Explanation
Once the initial sync succeeds, `repoReady` is permanently `true` for the remaining lifetime of the process, regardless of how many subsequent sync attempts fail. If `--max-failures` is configured to retry indefinitely (a negative value, which the manual explicitly documents as supported) [6](#0-5) , the process never exits on repeated failures, yet the `/` endpoint continues to return HTTP 200 the entire time [1](#0-0) . A Kubernetes readiness/liveness probe consuming this endpoint will keep routing traffic to / keeping alive a sidecar whose synced content is stale or whose upstream connectivity/auth is broken, i.e., persistent sync denial masked as healthy. This mirrors the "component that relies on the function to return a correct value" malfunctioning, as called out in the original finding.

### Likelihood Explanation
Reachable purely through normal, unprivileged operation: any transient or persistent network/auth failure to the upstream remote (attacker-controlled or otherwise) after the first successful sync triggers this path, with no special flags required beyond `--http-bind` being enabled to expose the probe endpoint (a documented, common Kubernetes sidecar configuration) [7](#0-6) . Using `--max-failures=-1` (documented, supported) makes the window during which the endpoint lies about health unbounded [6](#0-5) .

### Recommendation
Add a corresponding "not ready" transition on the failure path of the sync loop (mirroring how `maxWithdraw`/`maxRedeem` were made pause-aware while `maxDeposit`/`maxMint` were not): e.g., call a `setRepoNotReady()` once `failCount` exceeds a threshold (or immediately on failure, depending on desired probe semantics), so the `/` endpoint's 200/5xx status accurately reflects current sync health rather than only the historical "synced at least once" fact.

### Proof of Concept
1. Start `git-sync` with `--http-bind=:PORT --max-failures=-1 --period=<short>` against a reachable repo; wait for the first successful sync (`/` returns 200, matching documented behavior) [8](#0-7) .
2. Make the remote repository unreachable (e.g., revoke network access, rotate/break credentials, or point DNS away) so every subsequent `git.SyncRepo` call in the loop returns an error [5](#0-4) .
3. Because `--max-failures=-1`, the process never exits and `failCount` grows unboundedly, but `repoReady` was already set to `true` from step 1 and is never reset [9](#0-8) .
4. Repeatedly `curl http://localhost:PORT/` — it continues returning HTTP 200 indefinitely, even though the underlying data is stale and no further syncs are succeeding, contradicting the documented contract that the endpoint reflects sync health.

// repoReady indicates that the repo has been synced.
var readyLock sync.Mutex
var repoReady = false

func getRepoReady() bool {
	readyLock.Lock()
	defer readyLock.Unlock()
	return repoReady
}

func setRepoReady() {
	readyLock.Lock()
	defer readyLock.Unlock()
	repoReady = true
}
