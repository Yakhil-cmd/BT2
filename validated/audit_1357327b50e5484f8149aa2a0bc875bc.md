### Title
Webhook signature is verified against the organization derived from an unsigned payload field while the acted-upon repository is derived from a different unsigned payload field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). But the handlers that actually act on the payload (`Handler#stacks`) resolve the target `Repository`/`Stack` using an entirely separate field, `payload.dig('repository', 'full_name')`. Because both fields live in the same unsigned JSON body and only one of them gates which secret is used to verify the signature, an attacker who possesses (or controls) the webhook secret for organization A can forge a payload whose `repository.owner.login` is `"orgA"` (so the signature check passes using orgA's secret) while `repository.full_name` points at `"orgB/some-repo"` (so the actual side effects target orgB's stack).

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

`Shipit.github(organization:)` looks up the app config (and thus the `webhook_secret` used for HMAC verification) keyed by this organization name, supporting multiple GitHub Apps/orgs per deployment: [2](#0-1) [3](#0-2) 

Once the signature check passes, `create` dispatches the raw, attacker-controlled `params` to event handlers:
```ruby
def create

  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

``` [4](#0-3) 

Handlers (e.g. `PushHandler`) resolve the target stacks via `Handler#stacks`, which is keyed off `repository.full_name`, a field completely independent from `repository.owner.login` used for signature-key selection:
```ruby
def stacks

end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` splits `owner/name` straight from the (attacker-supplied) `full_name` string with no cross-check against `repository.owner.login`: [7](#0-6) 

**Binding broken:** the organization that authenticated the request (`repository_owner` used to pick the `webhook_secret`) ≠ the repository whose stack is actually written to (`repository.full_name` used by `Handler#stacks`). Before the attack, in a correctly-formed GitHub webhook these two fields always agree (GitHub always sends `owner.login` and `full_name` consistent with the actual firing repo). After the attacker's forged request, `repository.owner.login` is set to an org whose secret the attacker controls, while `repository.full_name` is set to a different org/repo whose stack the attacker wants to affect — the equality no longer holds, yet the code never checks it.

### Impact Explanation
This qualifies as escalation into unauthorized cross-repository/cross-organization state changes via forged webhook events, once a Shipit deployment is multi-tenant (multiple GitHub orgs configured, which the engine explicitly documents and supports via `Shipit.github_app_config`). An attacker holding a legitimate `webhook_secret` for their own organization's GitHub App installation can forge:
- `push` events to trigger `GithubSyncJob` against another organization's stack [6](#0-5) 
- `status`/`check_suite` events to inject forged commit statuses onto commits belonging to another organization's repository, which `Stack#deployable?`-style gating logic elsewhere relies on to decide whether a commit is safe to deploy.

This crosses the "cross-repository writes" / "unauthorized deploy" bar described in the impact criteria, since it lets an attacker who is only trusted for organization A inject state for organization B's repositories that Shipit tracks.

### Likelihood Explanation
Requires the attacker to already have a legitimate webhook secret for at least one organization configured on the Shipit instance (a realistic scenario for any Shipit deployment serving multiple GitHub organizations, since each org admin who can configure the app for their own org possesses their own `webhook_secret`). Given that, forging the cross-org payload is trivial — it is just crafting two independent JSON fields (`repository.owner.login` and `repository.full_name`) to diverge, and computing a normal valid HMAC over the raw body with the known secret.

### Recommendation
After signature verification succeeds, verify that the organization derived from `repository.full_name` (or `organization.login`) matches the organization (`repository_owner`) whose secret was used to authenticate the request, and reject the webhook (422) if they diverge. Alternatively, always resolve the verification key and the acted-upon repository from the same single field.

### Proof of Concept
1. Deploy Shipit with two GitHub Apps configured, one for `orgA` and one for `orgB`, each with their own `webhook_secret` (per `docs/setup.md`'s multi-app configuration section) [3](#0-2) .
2. Attacker has legitimate access to `orgA`'s webhook secret (e.g., is an admin of orgA's GitHub App installation).
3. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using orgA's `webhook_secret` over the raw body and sends the request.
5. `verify_signature` computes `repository_owner = "orgA"`, loads orgA's `GitHubApp`, and the signature verifies successfully [8](#0-7) .
6. `create` dispatches to `PushHandler`, which resolves `repository_name = "orgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` against orgB's stack [5](#0-4) [6](#0-5)  — despite the request only ever being authenticated as belonging to orgA.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
