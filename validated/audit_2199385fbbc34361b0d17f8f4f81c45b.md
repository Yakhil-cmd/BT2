### Title
Uncaught length-mismatch exception in `chash.isChashValid` via `isValidAddressAnyCase` on crafted address string - (File: `chash.js`, `validation_utils.js`)

### Summary
CVE-2017-9746 is a buffer-overflow/crash in binutils' `objdump.c` caused by insufficient bounds checking when parsing a crafted binary's instruction bytes, letting attacker-controlled input drive an out-of-bounds/size-mismatch condition that crashes the tool. The closest reachable analog in `ocore` is `chash.js`'s `isChashValid` function, which decodes an attacker-supplied "c-hash" (address) string and only bounds-checks the *decoded* buffer length inside a `try/catch` for the decode step itself, but performs a second, unguarded length check afterward that throws a raw `Error` when the decoded byte length doesn't match one of the two expected sizes (160/288 bits) [1](#0-0) .

### Finding Description
`isChashValid` first decodes the encoded string with `base32.decode` or `Buffer.from(_, 'base64')` inside a `try/catch`, returning `false` on a decode exception [2](#0-1) . It then calls `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)` **outside** any exception handling [3](#0-2) . `separateIntoCleanDataAndChecksum` unconditionally `throw`s `Error("bad length=...")` if the decoded bit-length isn't exactly 160 or 288 [4](#0-3) .

The normal, safe entry point `isValidAddress` first enforces a strict regex `/^[A-Z2-7]{32}$/` before calling `isValidChash`/`isChashValid`, which guarantees the base32 decode always yields exactly 20 bytes (160 bits), so the unguarded throw path is never hit [5](#0-4) . However, `isValidAddressAnyCase` only checks `isStringOfLength(str, 32)` before calling `isChashValid`, without restricting the character set to the base32 alphabet [6](#0-5) . If the underlying `thirty-two` base32 decoder treats any 32-character string permissively (e.g., silently dropping/ignoring characters outside `A-Z2-7` rather than throwing), the resulting buffer can have a length other than 20 bytes, which will make `separateIntoCleanDataAndChecksum` throw an uncaught `Error` inside `isChashValid`.

### Impact Explanation
If this uncaught exception is not wrapped by an outer `try/catch` at the point where `isValidAddressAnyCase` (or `isValidChash`) is invoked during unit/message validation, it becomes an unhandled exception in the validating process — the same class of "crafted input causes a crash" impact described in the CVE, just realized as a JS uncaught-exception crash instead of a native buffer overflow. A crash of the validating node process during handling of a maliciously crafted unit posted by an unprivileged party would deny that node's ability to validate/process new units (a node-availability/DoS impact), qualifying under the "network unable to confirm new units" criterion.

### Likelihood Explanation
This is **uncertain** and I was not able to fully verify two key facts before running out of investigation budget:
1. Whether `thirty-two`'s `base32.decode` actually returns a non-20-byte buffer for a 32-character string containing characters outside `A-Z2-7` (rather than throwing, which would be caught).
2. The exact call site(s) of `isValidAddressAnyCase` in `validation.js` and whether that call is wrapped in an outer `try/catch` that would absorb the exception before it propagates to a place that crashes the process.

Without confirming both points, I cannot assert this is a proven, exploitable node-crash vector with the same confidence as the other citations. I flag this explicitly rather than asserting certainty.

### Recommendation
Regardless of the above uncertainty, defensively hardening `chash.isChashValid` is cheap and correct: move the `buffer2bin`/`separateIntoCleanDataAndChecksum` calls into the existing `try/catch` block (or add a length pre-check on the decoded buffer) so any malformed decoded length returns `false` instead of throwing. This removes the uncaught-exception surface regardless of how `isValidAddressAnyCase` is used today or in the future.

### Proof of Concept
Not confirmed end-to-end due to inability to verify the `thirty-two` library's exact decode behavior for out-of-alphabet characters and the call-site exception handling in `validation.js` within the remaining investigation budget. Conceptually: craft a unit whose author/definition address field is a 32-character string that is accepted by `isStringOfLength(str,32)` but contains characters outside `[A-Z2-7]`, and route it to a validation path that calls `isValidAddressAnyCase` rather than `isValidAddress`; if `base32.decode` returns a buffer whose length isn't 20 bytes, `isChashValid` throws uncaught.
