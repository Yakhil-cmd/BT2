### Title
Cross-Repository Webhook Trust Escape: GitHub Organization Signature Binding Does Not Restrict Which Commits/Stacks a Webhook Event Can Mutate - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The Sherlock report's root cause is a mismatch between the field used to establish a trust boundary (the timestamp used for batch creation) and the field used to act on that trust (the timestamp used for claim eligibility), letting an actor's write bypass the scope the boundary was meant to enforce. The same class of bug exists in `shipit-engine`'s webhook trust model: `WebhooksController#verify_signature` establishes an authenticity/scope boundary keyed on the payload's `repository.owner.login` (resolving to one GitHub organization's `webhook_secret`), but `Webhooks::Handlers::StatusHandler#process` acts on the payload's `sha` field alone, with **no scoping at all** to the repository/organization whose signature was verified.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload and uses it to select which organization's `webhook_secret` verifies the HMAC signature: [1](#0-0) [2](#0-1) 

This authenticates *that the sender knows organization X's webhook secret*, and nothing more — it does not, and cannot, bind the verification to which repository record inside Shipit will actually be mutated by the handler.

`Webhooks::Handlers::Handler` (the common base class) does scope lookups by `payload.dig('repository', 'full_name')` via `stacks`: [3](#0-2) 

But `StatusHandler#process` — invoked for every `status` webhook event — does **not** use `stacks`/`repository_name` at all. It looks up commits globally by SHA across the entire Shipit instance and writes a GitHub status onto them: [4](#0-3) 

`Commit.create_status_from_github!` then mutates commit state and triggers deploy-safety recalculation (`add_status` → `deployable?`/`schedule_continuous_delivery`): [5](#0-4) [6](#0-5) [7](#0-6) 

**The broken equality:** the trust boundary enforced is `organization_that_signed(payload) == webhook_secret_owner`, but the write boundary actually exercised is `commit_written == any Commit row in the DB whose sha matches params.sha`, with **no requirement** that `commit.stack.repository.owner == organization_that_signed(payload)`. Any tenant/organization onboarded into a shared Shipit instance (each org configured via `Shipit.github(organization:)` with its own `webhook_secret`) can sign a `status` event payload with its own valid secret while setting `sha` to a commit that belongs to a *different* organization's stack — the signature check passes (it only proves knowledge of org A's secret) and the handler writes state onto org B's commit, entirely outside `repository_owner`'s scope.

### Impact Explanation
A commit's status directly gates `Commit#deployable?` and `schedule_continuous_delivery`, which drives whether continuous deployment auto-ships a commit. By forging a `state: "success"` status webhook (signed with an organization's own legitimately-known `webhook_secret`) targeting a SHA that exists in another organization's/stack's commit history, an attacker can flip that foreign commit into a deployable state and trigger an unauthorized deploy through Shipit's continuous-delivery pipeline — a cross-tenant, cross-repository write and unauthorized-ship outcome, matching the "Impact" bar (unauthorized deploy / cross-repository writes).

### Likelihood Explanation
Requires the attacker to be an onboarded, low-privilege tenant of the same Shipit instance (owning/administering at least one GitHub organization integrated with Shipit and therefore knowing that organization's own `webhook_secret` — not requiring any Shipit session, API token, or access to a foreign org). It further requires the attacker to know or predict a SHA that exists in the target stack's `commits` table (e.g., via public repo history, a shared/forked commit, or observing Shipit's public commit listing endpoints). This is plausible in shared/multi-tenant Shipit deployments where the webhook signature check is organization-scoped but no engine-level authorization ties the acted-upon commit/stack back to that same organization.

### Recommendation
In `StatusHandler#process` (and any other handler that doesn't use the base `Handler#stacks` scoping), restrict the commit lookup to commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`. More generally, every webhook handler must verify that the commit/stack/repository it writes to belongs to the same repository whose name was used to select the verifying `webhook_secret`, closing the gap between "who signed" and "what gets written."

### Proof of Concept
1. Shipit instance hosts two independent GitHub organizations, `org-a` and `org-b`, each configured with its own `webhook_secret` via `Shipit.github(organization:)`.
2. Attacker administers `org-a` (a legitimate, low-privilege tenant) and therefore knows `org-a`'s `webhook_secret`.
3. Attacker discovers/obtains a commit SHA `S` that belongs to a stack under `org-b` (e.g., from `org-b`'s public repository history or Shipit's own commit listing UI).
4. Attacker POSTs to `/webhooks` a `status` event: `{"repository": {"owner": {"login": "org-a"}, "full_name": "org-a/some-repo"}, "sha": "S", "state": "success", "context": "ci/build"}`, signing it with `org-a`'s `webhook_secret` via `X-Hub-Signature`.
5. `WebhooksController#verify_signature` resolves `repository_owner == "org-a"` and verifies successfully against `org-a`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: "S")` — unscoped — finds the commit under `org-b`'s stack and calls `create_status_from_github!`, marking it `"success"`.
7. If `org-b`'s stack has continuous deployment enabled and that commit was previously blocked only by CI status, `Commit#deployable?` now returns true and `schedule_continuous_delivery` queues an unauthorized deploy of `org-b`'s commit, entirely triggered by an `org-a` tenant.
