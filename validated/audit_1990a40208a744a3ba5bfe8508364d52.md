### Title
CCMenu API endpoint bypasses per-`ApiClient` stack scoping, allowing a token authorized for one stack to read the deploy/lock state of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Just as `Reserve.sol` validated the reserve invariant against the wrong quantity (`scaledTotalSupply()` instead of `totalSupply()`), `Shipit::Api::CCMenuController` validates stack access against the wrong scope: it checks only that the presented `ApiClient` token has the `read:stack` permission, but then resolves the target `Stack` from `params[:stack_id]` against *all* stacks instead of the set of stacks the token is actually authorized for. The binding that should hold — "stack a token authorizes == stack it touches" — is broken.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The generic `Shipit::Api::BaseController` correctly enforces this scope when resolving `stack`/`stacks`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

However, `CCMenuController` overrides `stack` and resolves it directly against `Stack` (unscoped), completely bypassing the `current_api_client.stack_id?` restriction:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!` [4](#0-3)  — it never checks *which* stack the token is scoped to. Authentication itself is also token-only, accepted from the query string:

```ruby
def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [5](#0-4) 

Because `#show` calls `stack` (the overridden, unscoped version) rather than the base controller's scoped `stack`, any valid `ApiClient` token with `read:stack` permission — even one explicitly created and distributed for a single stack (e.g., via `CCMenuUrlController`, which mints a `read:stack` token tied to one stack's CCMenu URL) — can be replayed against `/api/stacks/:stack_id/ccmenu.xml?token=...` for a *different* `stack_id` and successfully read that other stack's deploy status, lock status, and last-build information.

### Impact Explanation
This breaks the intended binding "stack a token authorizes vs. stack it touches," matching the High-severity class defined for this engine: unauthenticated/under-authorized read of stack state. A token meant to be scoped to a single stack's public CCMenu feed can be used to enumerate and read the build/deploy/lock status of every stack in the Shipit instance, which is stack-state disclosure across authorization boundaries.

### Likelihood Explanation
Likelihood is high given the intended usage pattern: `CCMenuUrlController#client` creates (or reuses) an `ApiClient` with only `read:stack` permission and hands its `authentication_token` out embedded in a CCMenu URL [6](#0-5) . These tokens are designed to be shared/distributed for continuous-integration monitors (CCTray/CCMenu clients), i.e., lower-trust consumers, but by design they carry no stack-restriction enforcement in this controller. Any holder of one such token for one stack can trivially change the `stack_id` route parameter to reach any other stack.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped resolution from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that a token's `stack_id` restriction (`current_api_client.stack_id?`) is enforced the same way it is for the rest of the API.

### Proof of Concept
1. As an admin, create (or let `CCMenuUrlController` create) an `ApiClient` scoped to Stack A with permission `read:stack`, and obtain its `authentication_token` (e.g., via the generated CCMenu URL `GET /api/stacks/stack-a/ccmenu.xml?token=<TOKEN_A>`).
2. Note Stack A's token is meant to only reveal Stack A's status.
3. Send `GET /api/stacks/stack-b/ccmenu.xml?token=<TOKEN_A>` (any other existing stack's identifier).
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` without checking `current_api_client.stack_id?`, the request succeeds (`require_permission :read, :stack` only checks the permission string, not the stack binding), returning Stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and lock state — data the token was never authorized to access.
