### Title
Fork-controlled `machine.environment` in `shipit.yml` reaches `Command#unbundled_env`/`PTY.spawn` unfiltered on `allow_all` review stacks - (File: app/models/shipit/deploy_spec.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
On a repository with `provisioning_behavior=allow_all`, an unprivileged fork PR causes Shipit to check out and execute the PR's own commit, and any `machine.environment` keys defined in that commit's `shipit.yml` are merged into the task/deploy `env` hash with no whitelist, unlike `deploy.variables`/`rollback.variables`/task `variables` which are always passed through `EnvironmentVariables#permit`. That raw env hash is passed into `Command.new(..., env:)` and ultimately merged unfiltered into `unbundled_env` before `PTY.spawn`.

### Finding Description
The broken binding is: for machine env, the code should enforce `env_reaching_PTY.spawn == permit(machine_env, whitelist)` the same way it does for deploy/rollback/task variables (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs` all call `EnvironmentVariables.with(env).permit(...)`, see [1](#0-0) ). Instead, `machine_env` is read straight from `config('machine', 'environment')` with no permit step, [2](#0-1) , and it is merged directly into the command environment in `TaskCommands#env`: `.merge(deploy_spec.machine_env).merge(@task.env)` [3](#0-2) .

`Command#unbundled_env` then merges this attacker-influenced `@env` on top of `BASE_ENV` (itself derived from `Bundler.unbundled_env`/`Bundler.clean_env`) with no key filtering at all: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [4](#0-3) , and this is exactly the hash handed to `PTY.spawn` in `Command#start`: `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [5](#0-4) .

Reachability for an unprivileged fork PR: `provision?` in `OpenedHandler` allows stack creation with no maintainer approval whenever `repository.provisioning_behavior_allow_all?` is true — no label check is even consulted in that branch: `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...)` [6](#0-5) . The created `ReviewStack` is provisioned and deployed, running commands built by `TaskCommands`/`DeployCommands` against the PR's own checked-out commit (`DeploySpec::FileSystem.new(@task.working_directory, @stack)`, `app/models/shipit/deploy_spec/file_system.rb`), meaning the attacker's own `shipit.yml` in the fork PR branch supplies `machine.environment`.

Separately, `ReviewStack#env` also merges raw PR label names into the env hash unfiltered (`labels[label_name.upcase] = "true"`) [7](#0-6) , which lets an attacker set the *key* `RUBYOPT` (with a fixed value of `"true"`) merely by naming a label on their own PR — real code injection via label alone is not possible since the value is hardcoded to `"true"`, but it does confirm the same unfiltered merge pattern (`EnvironmentVariables#permit` is never invoked for `stack.env`).

Existing guards do not stop this: `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb`) exists and is used for deploy/rollback/task variables, but `machine_env` and `stack.env` (labels) never pass through it.

### Impact Explanation
An unprivileged fork PR author can set `RUBYOPT="-r/tmp/evil.rb"` (or similar) via `shipit.yml`'s `machine.environment` on a review-stack-enabled repository configured with `provisioning_behavior=allow_all` (also reachable, with slightly more friction, on `allow_with_label` since the attacker can add their own label to their own PR). This value flows unfiltered into `PTY.spawn`'s env for every subsequent `ruby`/`rake`/`bundle`-based step run during dependency installation/deploy/rollback of that review stack, causing arbitrary Ruby code execution on the Shipit deploy host — Critical RCE per the stated impact category. Blast radius is scoped to the repositories that have review stacks enabled with `allow_all` (or `allow_with_label` when self-labeling is possible), but any Ruby/Bundler invocation on the deploy host during that stack's task execution is compromised, and the deploy host is shared infrastructure, so this could affect subsequent tasks/stacks executed on the same host/user context depending on deployment isolation.

### Likelihood Explanation
Preconditions: the target `Repository` must have `review_stacks_enabled = true` and `provisioning_behavior = allow_all` (a documented, first-recommended configuration in `docs/review_stacks.md`). No Shipit credentials, sessions, or GitHub App secrets are required — only the ability to open a pull request against the tracked repository (which for `allow_all` review stacks is by design intended to include external contributors). The attacker only needs to add a `shipit.yml` (or `.shipit/shipit.yml`) to their PR branch with a `machine: environment: RUBYOPT: ...` entry. This is a single PR open action, fully repeatable against any `allow_all` repository the attacker can send a PR to.

### Recommendation
Route `machine_env` (and `stack.env`'s label-derived entries) through the same `EnvironmentVariables#permit` whitelist mechanism used for `deploy_variables`/`rollback_variables`/task `variables`, or maintain a fixed deny-list of dangerous interpreter-hijacking variables (`RUBYOPT`, `RUBYLIB`, `BUNDLE_GEMFILE`, `GEM_PATH`, `LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, etc.) that can never be set from repo-controlled `shipit.yml` or PR labels, applied uniformly in `Command#unbundled_env` regardless of source. At minimum, `Command#unbundled_env` should strip such variables from `@env` before merging into the environment passed to `PTY.spawn`, since it is the final choke point for every code path (`TaskCommands`, `DeployCommands`, `RollbackCommands`, `StackCommands`) that reaches process execution.

### Proof of Concept
Minitest plan (no live GitHub required):
1. In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`-style setup, configure a repository with `review_stacks_enabled: true`, `provisioning_behavior: :allow_all`.
2. Stub `DeploySpec::FileSystem#load_config` (as done in `test/models/deploy_spec_test.rb`) to return:
   ```ruby
   { 'machine' => { 'environment' => { 'RUBYOPT' => '-r/tmp/evil.rb' } } }
   ```
3. Build a `TaskCommands` (or `DeployCommands`) for a task/deploy on that stack and assert:
   ```ruby
   assert_equal '-r/tmp/evil.rb', commands.env['RUBYOPT']
   ```
4. Construct a `Shipit::Command.new('true', env: { 'RUBYOPT' => '-r/tmp/evil.rb' }, chdir: '.')` and assert:
   ```ruby
   assert_equal '-r/tmp/evil.rb', command.unbundled_env['RUBYOPT']
   ```
5. Both assertions passing (no `NotPermitted` raised, no filtering applied) demonstrates the equality `env_reaching_PTY.spawn == permit(machine_env, whitelist)` is violated — the whitelist step never runs for `machine_env`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil

      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
