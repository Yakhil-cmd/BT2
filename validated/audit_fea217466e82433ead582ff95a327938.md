### Title
Partially-initialized unit left in `storage.assocUnstableUnits`/`assocBestChildren` if `saveJoint` fails after the unit is linked into the in-memory unstable-unit graph but before DB commit - ([File: writer.js])

### Summary
`writer.js`'s `saveJoint()` mirrors the kernel `slram` bug class: it links a new entry into a global, process-wide in-memory structure (`storage.assocUnstableUnits`, `storage.assocBestChildren`) *before* all of the dependent state-building operations (`updateBestParent`, `updateLevel`, `updateWitnessedLevel`, `main_chain.updateMainChain`, `storage.insertAADefinitions`) have completed successfully. If any of those later operations fails (`err` truthy in `async.series(arrOps, ...)`), the code path calls `storage.resetMemory(conn)` as the only recovery step, rather than performing a symmetric, immediate unwind of the specific partially-initialized entry as the kernel patch does for `slram_mtdlist`.

### Finding Description
In `writer.js`, `saveJoint()` inserts the new unit's props object directly into the shared caches before its fields (`level`, `witnessed_level`, `best_parent_unit`, MC-related fields) are finalized: [1](#0-0) 

It then queues asynchronous operations (`updateBestParent`, `updateLevel`, `updateWitnessedLevel`, `main_chain.updateMainChain`, and conditionally `storage.insertAADefinitions`) that mutate this same object and the shared graph further: [2](#0-1) 

Only after this async pipeline resolves does the code check for `err` and, if present, roll back the SQL transaction and reset in-memory state: [3](#0-2) 

The recovery path is `storage.resetMemory()`, which entirely tears down and reloads `assocUnstableUnits`/`assocBestChildren`/`assocStableUnits` from the (rolled-back) DB: [4](#0-3) 

This differs qualitatively from the kernel fix's approach (targeted unwind of the single failed list entry on each failure path) — here the whole global unstable-unit cache is nuked and rebuilt from disk whenever any single unit's `saveJoint()` fails partway. The risk window is the (possibly asynchronous, since `updateMainChain`/`insertAADefinitions` do I/O) interval between the object being placed in `assocUnstableUnits`/`assocBestChildren` (line 597/601) and the eventual `resetMemory()` call. During that window:
- The unit is present in `assocUnstableUnits` with incomplete fields (e.g. `level: null`, `witnessed_level` not yet computed, `best_parent_unit` possibly stale) and is also pushed into its parent's `assocBestChildren` array (line 598-602), before `updateBestParent`/`updateLevel`/`updateWitnessedLevel` run.
- Because Node.js is single-threaded and no other unit-writing operation runs concurrently under the `["write"]` mutex, ordinary code paths cannot observe this partial state mid-flight. However, `mutex.lock(["write"])` only serializes writers; other read paths across the codebase that consult `storage.assocUnstableUnits`/`assocBestChildren` without taking the write mutex (e.g. `main_chain.js`, `graph.js`, AA execution code reading the cache for stability/graph traversal) could, in principle, read the half-built object if invoked synchronously from an event handler triggered inside the same call stack (for instance from `eventBus` emissions or from `preCommitCallback`, which executes arbitrary code before `arrOps` fully finishes and while the just-added unit's `level`/`witnessed_level` are still `null`).
- If `insertAADefinitions` (invoked mid-`arrOps`) throws or rejects partway through inserting multiple AA definitions from one unit, only some of the AAs from `arrAADefinitionPayloads` may be registered in `aa_addresses`/caches while the triggering unit itself is already sitting in `assocUnstableUnits`, and `resetMemory()` (a full DB-driven cache rebuild after rollback) is relied upon rather than an explicit unwind, so any code that captured a reference to the stale, partially-populated `objNewUnitProps` object (e.g. via `assocBestChildren[parent]` array, which is only cleared by wiping the whole array, not by targeted removal) could still operate on it.

Whether this actually leads to a corrupted-consensus-visible outcome (as opposed to just a rebuilt cache masking the transient inconsistency) is uncertain from static reading alone: `resetMemory()` does eventually restore consistency once it completes, and I could not find, within the scope of this analysis, a concrete synchronous reader of `assocUnstableUnits`/`assocBestChildren` that executes strictly between the object's insertion (line 597) and the `resetMemory()` call (line 712) with a failing `arrOps` operation. This gap is a limitation of this analysis, not a claim that no such path exists.

### Impact Explanation
If a reachable synchronous reader does exist (e.g., through `preCommitCallback` or nested `eventBus` handlers invoked from within `arrOps`), it could observe a unit with `level: null`/`witnessed_level: null`/incomplete `best_parent_unit`, potentially causing incorrect stability/MC computations, a thrown exception mid-flight (crashing the node process, since many of these code paths use `throw Error(...)` liberally on invariant violations), or divergent state between nodes if the crash/inconsistency is not deterministic across all validators — mapping to "node disagreement on validity or stability" or a DoS-like crash of the write path for legitimately-formed but resource-exhausting/edge-case units (e.g., a unit defining many new AAs via `insertAADefinitions`, or one with a pathological main-chain update).

### Likelihood Explanation
Low-to-Medium confidence. The `["write"]` mutex protects against concurrent `saveJoint()` calls, and I could not confirm a concrete external trigger (unprivileged unit poster or AA trigger) that reliably makes `updateBestParent`/`updateLevel`/`updateWitnessedLevel`/`updateMainChain`/`insertAADefinitions` fail with `err` for a legitimately-validated unit under normal conditions — most of these functions appear to `throw` on invariant violations rather than return a soft `err`, which would crash the process outright rather than triggering the `resetMemory()` recovery path. Triggering the exact `err`-returning branch (as opposed to a `throw`) from attacker-controlled input needs further verification.

### Recommendation
Do not link `objNewUnitProps` into `storage.assocUnstableUnits`/`assocBestChildren` until `arrOps` (in particular `insertAADefinitions`, `updateBestParent`, `updateLevel`, `updateWitnessedLevel`, `updateMainChain`) have all completed successfully; alternatively, add a synchronous unwind step that removes the specific unit's entry from `assocUnstableUnits` and pulls it back out of the parent's `assocBestChildren` immediately when `err` is set, mirroring the kernel's per-entry unwind, rather than deferring to a full `resetMemory()` rebuild. Audit all code paths (including `preCommitCallback` implementations and any `eventBus` listeners invoked synchronously during `arrOps`) to ensure none of them read `assocUnstableUnits`/`assocBestChildren` for the in-flight unit before its fields are fully populated.

### Proof of Concept
Not constructed — I was unable to confirm, from static analysis alone within the available tool budget, a concrete synchronous read of the partially-initialized `objNewUnitProps` from a reachable code path during the vulnerable window, nor a guaranteed way to make `arrOps` return a soft `err` (as opposed to `throw`) for a validly-formed but adversarial unit/AA definition. A Devin session with runtime/debugging access would be needed to instrument `writer.js` and attempt to trigger `insertAADefinitions` or `updateMainChain` failure mid-`arrOps` for a unit that defines many AAs or has adversarial MC/witness structure, and to check whether any reader observes the half-built cache entry before `resetMemory()` restores consistency.

function resetUnstableUnits(conn, onDone){
	Object.keys(assocBestChildren).forEach(function(unit){
		delete assocBestChildren[unit];
	});
	Object.keys(assocUnstableUnits).forEach(function(unit){
		delete assocUnstableUnits[unit];
	});
	initUnstableUnits(conn, onDone);
}

function resetStableUnits(conn, onDone){
	console.log('resetStableUnits');
	Object.keys(assocStableUnits).forEach(function(unit){
		delete assocStableUnits[unit];
	});
	Object.keys(assocStableUnitsByMci).forEach(function(mci){
		delete assocStableUnitsByMci[mci];
	});
	initStableUnits(conn, onDone);
}

function resetMemory(conn, onDone){
	if (!onDone)
		return new Promise(resolve => resetMemory(conn, resolve));
	resetUnstableUnits(conn, function(){
		resetStableUnits(conn, function(){
			min_retrievable_mci = null;
			initializeMinRetrievableMci(conn, onDone);
		});
	});
}
