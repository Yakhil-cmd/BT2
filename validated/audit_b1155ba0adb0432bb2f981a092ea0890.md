This confirms a severe finding. Note `StatusHandler` doesn't even use `repository.full_name` — it looks up `Commit.where(sha: params.sha)` globally, across **all** stacks/repositories in the Shipit instance, regardless of which organization's webhook secret validated the payload. This makes the cross-org write even more direct than the `PushHandler` case, since `StatusHandler#process` requires no repository field to match at all, and a successful status can flip `continuous_deployment?` stacks to deploy via `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob`.### Title
Multi-organization webhook signature check binds the wrong field, allowing cross-organization forged GitHub events (spoofed status/push updates on stacks the attacker's org does not own) - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate an inbound webhook's HMAC against, based on `repository_owner` — a field read from the *unverified* JSON payload itself before the signature is checked. The actual work done by the event handlers, however, is routed using *different* fields of the same payload (`repository.full_name` in `PushHandler`, or nothing at all — a global `sha` lookup — in `StatusHandler`). This is the same class of bug as the reported Float128 issue: the value used to decide "how much trust/verification to apply" is not the same value that is ultimately acted upon.

### Finding Description
In a Shipit deployment configured for multiple GitHub organizations (documented in `README.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), each organization has its own, distinct `webhook_secret`: [1](#0-0) 

`WebhooksController#verify_signature` picks the app/secret to verify against using `repository_owner`, itself derived from the attacker-controlled JSON body: [2](#0-1) 

If the requester administers (or has been granted GitHub App access to) at least one organization on the Shipit instance — e.g. `attacker-org` — they legitimately know that organization's `webhook_secret` (they configured or received it when installing the App). Nothing then stops them from crafting an arbitrary event body where:
- `repository.owner.login` = `"attacker-org"` (so `verify_signature` looks up and validates against the attacker's own known secret — the check passes, using an HMAC the attacker can correctly compute).
- `repository.full_name` = `"victim-org/victim-repo"` (a different org's repository Shipit also tracks).

`Webhooks.for_event` then dispatches the *entire, self-signed* payload to the registered handler with no further re-validation that `repository.full_name`'s owner matches the org whose secret validated the signature: [3](#0-2) [4](#0-3) 

For `push` events, `PushHandler`/`Handler#stacks` resolves the target stacks purely from `repository.full_name`, independent of the organization that was used for signature verification: [5](#0-4) [6](#0-5) 

For `status` events, the binding is even weaker: `StatusHandler` ignores the repository entirely and matches by commit SHA globally across the whole instance: [7](#0-6) 

That status write feeds directly into deploy-gating logic — `Commit#deployable?` and `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob`, which can trigger an actual deploy on a stack with `continuous_deployment: true`: [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
This crosses the "unauthorized deploy / cross-repository writes" bar: an attacker who is a legitimate low-privilege GitHub App installer for their own organization (`attacker-org`) can forge fully self-signed webhook payloads that write commit statuses, or trigger `sync_github`, on stacks belonging to a completely different, victim organization also configured on the same Shipit instance. A crafted `success` status on the right commit context can unlock `continuous_deployment` and cause an unauthorized deploy of the victim's stack, or a forged `push`/status can corrupt commit history/CI state used by merge-queue and deploy-gating decisions for a repository the attacker has no access to.

### Likelihood Explanation
Requires only that the Shipit instance is running in the documented multi-organization GitHub App mode and that the attacker controls (is an admin of, or has been granted webhook configuration for) at least one of the configured organizations — no `ApiClient` token, `api_clients_secret`, session, or GitHub App private key is needed, since the attacker signs the payload themselves with a secret they legitimately possess for their own org. The single-organization (default) configuration is not affected, because `Shipit.github` ignores the `organization:` argument entirely when `github_default_organization` is nil, so only one shared secret exists in that mode.

### Recommendation
Bind the verification decision to the same value that is ultimately acted upon:
- After choosing the GitHub App config for signature verification, re-derive `repository.full_name`'s owner and require it to match the `repository_owner`/organization whose secret validated the request; reject (422) on mismatch.
- In `Webhooks::Handlers::Handler` and each concrete handler (`PushHandler`, `StatusHandler`, membership/pull_request handlers), scope repository/commit lookups to the verified organization rather than trusting `repository.full_name`/`sha` alone. For `StatusHandler` specifically, scope `Commit.where(sha:)` to commits belonging to stacks under the verified organization.
- Alternatively, pass the verified organization down into `Webhooks.for_event(...).each { |handler| handler.call(params, verified_organization:) }` and have handlers assert consistency before mutating any state.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. As the operator of `attacker-org`, compute `sha1=HMAC(webhook_secret_attacker, raw_body)` for a `status` event payload where:
   ```json
   {
     "sha": "<sha of a commit on victim-org/victim-repo tracked by Shipit>",
     "state": "success",
     "context": "ci/travis",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
   }
   ```
3. POST to `/github/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully (the attacker signed with their own known secret).
5. `Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which runs `Commit.where(sha: params.sha)` — matching the commit on `victim-org/victim-repo` regardless of the fact the signature was only proven for `attacker-org` — and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto the victim's commit and potentially triggering `ContinuousDeliveryJob` for that stack.
