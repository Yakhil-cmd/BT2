### Title
Webhook signature is validated against an organization derived from an attacker-controlled field that is not the field used to select the repository/stack acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`) taken directly from the unauthenticated request body. Once verification passes, every `Webhooks::Handlers::Handler` subclass resolves the target repository/stack using a *different* field of the same payload: `repository.full_name`. Because the entire raw body — including both fields — is attacker-supplied before any signature check occurs, an attacker who legitimately controls one organization's webhook secret (i.e., who owns/administers an org that has installed the Shipit GitHub App) can forge a payload where `repository.owner.login`/`organization.login` names their own org (so the signature check passes using their real secret) while `repository.full_name` names a repository belonging to a *different* organization/stack tracked by the same Shipit instance.

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the signature == organization owning the repository the handlers act on`

Verification path: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) *before* the signature has been checked, and is used only to pick which `Shipit.github(organization: ...)` app/secret computes the expected HMAC over the full raw body. The HMAC itself is computed over `request.raw_post` — the whole body, which the attacker fully controls.

Action path (after verification succeeds), for every handler: [3](#0-2) 

`repository_name` — used to look up `Repository.from_github_repo_name(repository_name)` and thus the `Stack`s that are mutated — comes from `payload.dig('repository','full_name')`, a *different* JSON field than the one used to pick the verifying secret.

Because nothing ties `repository.owner.login` to `repository.full_name`'s owner segment, an attacker who is an authorized administrator of Organization A (and therefore knows/controls A's registered `webhook_secret` in this Shipit deployment) can:
1. Build a payload with `repository.owner.login = "A"` (or `organization.login = "A"`) and `repository.full_name = "B/some-repo"` (owned by Organization B, tracked by the same Shipit instance).
2. Sign the raw body with A's real webhook secret (`X-Hub-Signature`).
3. `verify_signature` resolves `Shipit.github(organization: "A")`, computes the HMAC with A's secret over the attacker's full body, and it matches — verification passes.
4. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers that key off `repository.full_name`, i.e., Organization B's repository/stack:
   - `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for B's stacks. [4](#0-3) 
   - `StatusHandler` writes fabricated commit statuses via `commit.create_status_from_github!(params)` for B's commits. [5](#0-4) 
   - Similarly `CheckSuiteHandler`, `MembershipHandler`, and the `PullRequest::*` handlers act on org-B-owned data resolved from `repository.full_name`. [6](#0-5) 

This is the exact class of bug described in the report: a value used to authorize/derive a boundary (here, the signing organization) is fetched at one point (pre-verification, from the payload itself) while a *different* value from the same untrusted payload is used to decide what gets mutated — and nothing forces them to be consistent.

### Impact Explanation
This crosses an organizational trust boundary the engine is supposed to enforce: webhook events for Organization B's repositories are only supposed to be accepted if they are validated by Organization B's secret. Using this mismatch, an attacker with legitimate control over Organization A's GitHub App/webhook secret in a multi-organization Shipit deployment can inject forged `push`, `status`, `check_suite`, `membership`, or `pull_request` events against stacks/repositories belonging to Organization B, causing:
- Forged commit statuses (`StatusHandler`) that can satisfy required-status checks and unblock/trigger deploys on B's stacks.
- Forced `GithubSyncJob`s / spurious `sync_github` calls on B's stacks (`PushHandler`).
- Fabricated `check_suite` refreshes, membership/team changes, or pull-request state transitions for B.

This is a cross-organization write into stack/commit state that the attacker has no legitimate authorization over, matching the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization (each with its own App/webhook secret) — a supported and documented configuration (`Shipit.github(organization:)`, `GithubOrganizationUnknown` handling in `verify_signature`). The attacker only needs to be a legitimate, authenticated administrator/owner of any one of those organizations (i.e., someone who can see/rotate that org's own webhook secret) — no privileged Shipit account, GITHUB_TOKEN, or TLS interception is required. The rest is pure payload crafting against the public `/webhooks` endpoint.

### Recommendation
Bind the field used to select the verifying secret to the same field used by handlers to resolve the target repository/stack — verify that `repository.owner.login`/`organization.login` matches the owner segment parsed out of `repository.full_name` before dispatching to handlers, or derive both values from a single canonical field. Alternatively, after selecting the app by `repository_owner`, re-check that the resolved `Repository`/`Stack` actually belongs to that same verified organization before invoking any handler.

### Proof of Concept
1. Shipit is configured for two organizations, `org-a` and `org-b`, each with their own GitHub App/webhook secret (`Shipit.github(organization: "org-a")` vs `"org-b"`), both tracking stacks in the same Shipit instance.
2. Attacker administers `org-a` and knows its webhook secret `secret_a` (legitimately, as configured for their own org's Shipit integration).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha-in-org-b-repo>",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(secret_a, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` reads `repository_owner = "org-a"`, loads `Shipit.github(organization: "org-a")`, verifies the HMAC with `secret_a` — succeeds. [7](#0-6) 
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` for the given SHA — which belongs to `org-b/victim-repo` — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto Organization B's commit despite the request only ever being authenticated for Organization A. [5](#0-4)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
