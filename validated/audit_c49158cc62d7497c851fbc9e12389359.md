### Title
Cross-tenant commit-status forgery via unscoped `StatusHandler` lookup breaking the organization/repository binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against based on `repository.owner.login` (or `organization.login`), i.e. it authenticates "which configured GitHub organization sent this". However, `Shipit::Webhooks::Handlers::StatusHandler#process` never checks which repository/organization the status belongs to — it looks up `Commit.where(sha: params.sha)` globally across the entire `commits` table. On a multi-tenant Shipit instance (the documented "Using Multiple Github Applications" setup), this breaks the invariant that "the organization whose secret authenticated the webhook" equals "the repository the handler is allowed to mutate."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` picks the verification secret dynamically per request: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the still-unauthenticated request body, and is used only to choose which `GitHubApp`/secret to check the signature against: [3](#0-2) 

This is the intended multi-organization design (`config/secrets.development.shopify.yml`, `docs/setup.md` "Using Multiple Github Applications" section) — each org onboarded to the shared Shipit instance has its own `webhook_secret`, and anyone administering that org's GitHub App legitimately knows/controls that secret.

Once the signature check passes (proving only that *some* configured org's secret signed the raw body), `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`: [4](#0-3) 

`StatusHandler#process` never reads `repository.full_name` or ties the update to `repository_owner` at all — it queries `Commit.where(sha: params.sha)` globally, then calls `commit.create_status_from_github!(params)`, which persists a new `Status` on whatever `Commit` records anywhere in the database share that `sha`: [5](#0-4) 

That status feeds directly into deploy-gating logic: [6](#0-5) [7](#0-6) 

So the equality that should hold is:

`organization whose secret authenticated the request == organization/repository whose commit is mutated`

An attacker who legitimately administers **their own** org's GitHub App on a shared multi-tenant Shipit deployment (and therefore knows their own org's real `webhook_secret`) can sign a forged `status` (or `push`/`check_suite`/`pull_request`) payload with their own secret while targeting a commit `sha` that belongs to a **different tenant's** stack. `verify_signature` only checks "was this signed by a secret I know for the org named in the body" — it never checks that the org matches the actual `Commit`/`Stack`/`Repository` being modified, and `StatusHandler` doesn't scope by repository at all.

Other handlers exhibit a weaker version of the same break: `PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers derive the target `Repository`/`Stack` from `repository.full_name`, a field that is never cross-checked against `repository.owner.login`/`organization.login` (the field actually used to pick the verification secret): [8](#0-7) [9](#0-8) [10](#0-9) 

This is the same class of bug as the report's hardcoded-index issue: a value used for one purpose (authorization/scope selection) is silently decoupled from the value that actually governs the effect of the operation, so upgrading the trust model (single org → multiple orgs sharing one instance) opens an unintended cross-boundary write.

### Impact Explanation
This allows an attacker who administers one tenant organization on a shared Shipit instance to forge GitHub status events for **any other tenant's tracked commits** by only knowing their own org's webhook secret. A forged "success" status on a required CI context can:
- Mark a victim's blocked/pending commit as `deployable?` (bypassing CI gating), enabling an unauthorized deploy trigger via continuous delivery (`schedule_continuous_delivery`) or a manual deploy that relies on `required_statuses`.
- Constitutes an unauthorized cross-repository write into another tenant's data (`Status` rows tied to another tenant's `Commit`/`Stack`), satisfying the "cross-repository writes" / "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Requires the attacker to control (as an org admin) at least one GitHub organization that is configured as a tenant on the same shared Shipit instance — an unprivileged position relative to any *other* tenant's repositories, and explicitly supported/documented multi-tenant configuration (`docs/setup.md`, `config/secrets.development.shopify.yml`). No Shipit session, API token, or victim's webhook secret is required. Attacker also needs a target commit `sha`, which is generally discoverable from GitHub (commits, PRs, compare views) even without repo write access.

### Recommendation
- Scope `StatusHandler` (and any handler that mutates records) by the repository/organization actually resolved from the payload, not just by `sha`, e.g. restrict `Commit.where(sha: ...)` to commits whose `stack.repository.full_name`/`owner` matches the organization that produced a valid signature.
- Enforce that the org used to select the webhook secret (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` before processing any handler, rejecting mismatches.
- Consider binding webhook processing to the specific `Repository`/`Stack` resolved during signature verification, rather than re-deriving it independently inside each handler.

### Proof of Concept
1. Deploy Shipit with multi-org config (as in `docs/setup.md` "Using Multiple Github Applications"), onboarding `attacker-org` (attacker is admin, knows `webhook_secret_A`) and `victim-org` (unrelated tenant, has a stack tracking commit `sha=deadbeef...`).
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "deadbeef...",           // victim-org's tracked commit
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://evil.example/",
  "created_at": "2026-09-02T00:00:00Z",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_A, raw_body)` using their own known `webhook_secret_A`, sets `X-Github-Event: status`, and POSTs directly to `https://shipit.example.com/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — matches victim-org's commit — and calls `create_status_from_github!`, injecting a forged `success` status onto a commit the attacker has no access to, which can unblock `deployable?`/trigger continuous delivery for `victim-org`'s stack.
