### Title
Unbounded RAY share-and-index multiplication permanently freezes a lending market - (File: common/src/rates/simulate.rs)

### Summary
The pool computes aggregate debt and supply values by multiplying stored RAY-scaled shares by their respective indexes, and panics when the result cannot fit in `i128`. [1](#0-0) [2](#0-1) 

Once either product crosses the representable range, accrual reverts before `last_timestamp` is advanced, while every pool mutation synchronizes the market before changing state. [3](#0-2) [4](#0-3) 

### Finding Description
`Controller::update_indexes(caller, assets)` is callable by any authenticated caller and forwards the requested `Vec<HubAssetKey>` to the pool. [5](#0-4) [6](#0-5) 

The pool’s `update_indexes` implementation invokes `ops::market::accrue`, which reaches `global_sync` and then `accrue_step`. [7](#0-6) [8](#0-7) 

`accrue_step` first calculates `borrowed * borrow_index` and `supplied * supply_index`, then later recalculates debt at the newly grown borrow index. [9](#0-8) [10](#0-9) 

These operations delegate to `Ray::mul`, which calls `mul_div_half_up`; when the exact result exceeds `i128`, conversion returns `None` and the panicking wrapper raises `MathOverflow`. [11](#0-10) [12](#0-11) 

The borrow-index ceiling does not prevent this condition because the ceiling is applied to the index itself, not to `borrowed * index` or `supplied * index`. [13](#0-12) [1](#0-0) 

Because `global_sync` marks the market accrued only after all chunks complete, a revert leaves both the oversized state and stale timestamp intact, so every subsequent synchronized operation encounters the same overflow. [3](#0-2) 

### Impact Explanation
This permanently freezes the affected `(hub_id, asset)` market: repayments, withdrawals, liquidations, bad-debt cleanup, revenue claims, recapitalization, and further index updates all need the same accrual path and therefore revert before they can repair the state. [4](#0-3) [14](#0-13) 

The repository’s regression test demonstrates that a sufficiently large market at sustained high utilization reaches the RAY-value ceiling before the index cap, after which both withdrawal and repayment fail with `MathOverflow`. [15](#0-14) 

### Likelihood Explanation
Triggering the state requires an exceptionally large pool book and enough index growth that an aggregate value exceeds `i128`; the reproduced fixture uses a one-billion-unit 18-decimal supply and 98% borrowed principal. [16](#0-15) 

Once such a market state exists, any unprivileged authenticated caller can cross the boundary by submitting `update_indexes(caller, [HubAssetKey { hub_id, asset }])`; no privileged call, oracle manipulation, contract upgrade, or leaked key is required. [5](#0-4) [6](#0-5) 

### Recommendation
Bound admitted aggregate scaled supply and debt so their values remain representable at the protocol’s maximum relevant index, rather than only bounding token input amounts and indexes independently. [17](#0-16) [13](#0-12) 

At accrual time, evaluate index growth with non-panicking multiplication and clamp the next index to the largest value for which both `borrowed * index / RAY` and `supplied * index / RAY` fit in `i128`, before calculating rewards or utilization. [18](#0-17) [2](#0-1) 

### Proof of Concept
1. Establish or identify a market whose stored scaled debt is large enough that `borrowed * borrow_index / RAY` will exceed `i128::MAX` after sustained accrual; the checked-in fixture uses one billion units of an 18-decimal asset with 98% borrowed. [16](#0-15) 

2. Let ledger time advance until the stored borrow index is large enough for the next value calculation to overflow. [19](#0-18) 

3. Submit:

```text
controller.update_indexes(
    caller = attacker,
    assets = [HubAssetKey { hub_id, asset }]
)
```

The call is permissionless and reaches the pool accrual path. [5](#0-4) [6](#0-5) 

4. `accrue_step` reverts while calculating the book’s RAY value, leaving `last_timestamp` unchanged and making the same failure deterministic on every later synchronized operation. [1](#0-0) [3](#0-2) 

5. Subsequent `withdraw`, `repay`, liquidation, and cleanup calls cannot pass accrual; the existing test confirms withdrawal and repayment both return `MathOverflow`. [20](#0-19)

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
