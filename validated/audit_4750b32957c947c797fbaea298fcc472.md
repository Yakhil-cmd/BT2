This confirms the finding. The binding claimed (`organization whose webhook_secret verified the body == organization owning the Team mutated`) is indeed broken, in the removal direction, by the same root cause as the `added` case.

The webhook signature is verified against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly from attacker-controlled payload fields (`repository.owner.login` or `organization.login`) <cite repo="hirayap/shipit-engine--013" path="app/controllers/shipit/webhooks_controller.rb" start="24,59" end="30,62" />. This only proves the request was signed by *some* org's registered secret — the org named in the payload — but that org can be entirely different from the org that actually owns the `Team` referenced by `team.id`.

`MembershipHandler#process` never cross-checks this: it looks up the team purely by `github_id` via `Team.find_or_create_by!(github_id: params.team.id)`, ignoring `params.organization.login` except when creating a brand-new record <cite repo="hirayap/shipit-engine--013" path="app/models/shipit/webhooks/handlers/membership_handler.rb" start="38,42" end="43" />. So if a `Team` with `github_id == X` already exists (owned by `org_a`), a webhook signed by `org_b`'s secret, claiming `organization.login == "org_b"` and `team.id == X`, will still resolve to `org_a`'s team.

For `action == 'removed'`, the handler runs `team.members.delete(member)` [1](#0-0) , which deletes the `Membership` row joining `org_a`'s team and the named user — regardless of whether that user was ever actually removed from the real GitHub team. `member` is resolved via `User.find_or_create_by_login!(params.member.login)`, so any existing Shipit user's login can be targeted [2](#0-1) . Since `User#authorized?` is computed live from `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [3](#0-2) , removing the `Membership` immediately flips `authorized?` to `false` for that victim if `org_a`'s team was their only authorizing team.

The only precondition is that a `Team` row for the victim's team already exists with a known `github_id` (an attacker can learn/guess GitHub team IDs, which are not secret, or simply target teams they can observe), and that the attacker controls a `GithubHook::Organization` registration (their own org, `org_b`) with a valid `webhook_secret` for `Shipit::WebhooksController` to accept the signature. No Shipit session, API token, or GitHub App credentials from `org_a` are needed.

### Title
Cross-organization membership webhook can de-authorize an arbitrary user via `team.id` collision - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` resolves the target `Team` solely by `params.team.id` (GitHub team numeric ID) without verifying that the organization which signed the webhook (`repository_owner`/`organization.login`, checked in `WebhooksController#verify_signature`) actually owns that team. An attacker who controls any registered GitHub organization's webhook secret can send a `membership`/`removed` event referencing another organization's team ID and a victim's login, causing `team.members.delete(member)` to strip that victim's `Membership`, immediately revoking `User#authorized?`.

### Finding Description
Broken binding: `organization_that_signed_the_payload (org_b, verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` should equal `organization_owning_the_mutated_Team (org_a, Team#organization for the row matched by github_id)` — but it does not.

Code path:
1. `WebhooksController#verify_signature` picks the signing org from attacker-supplied payload fields: `params.dig('repository','owner','login') || params.dig('organization','login')` [4](#0-3) , then verifies the HMAC using that org's own `webhook_secret`. This only proves "some org (attacker's own org_b) signed this", not that org_b owns the team referenced inside the payload.
2. `MembershipHandler#process` calls `find_or_create_team!`, which is `Team.find_or_create_by!(github_id: params.team.id) { ... }` [5](#0-4) . The `organization:` block only runs on record creation; when a `Team` with that `github_id` already exists (belonging to org_a), it's returned unchanged — the attacker-supplied `params.organization.login` ("org_b") is silently ignored.
3. For `action == 'removed'`, `team.members.delete(member)` deletes the `Membership` join row between `org_a`'s team and the resolved `member` [1](#0-0) .
4. `member` is found/created purely by login: `User.find_or_create_by_login!(params.member.login)` [2](#0-1)  — any existing victim's login works.
5. `User#authorized?` is derived live from current `Membership` rows against `Shipit.github_teams` [3](#0-2) , so deleting the membership immediately de-authorizes the victim.

Attacker's exact request: register/own an org `org_b` with a `GithubHook::Organization` webhook secret in Shipit (a normal, legitimate onboarding step for any org an attacker administers), then send a signed (with org_b's secret) POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "removed",
  "team": { "id": <org_a_team.github_id>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "org_b" },
  "member": { "login": "<victim_login>" }
}
```
No org_a secret, GitHub App key, or victim credentials are required.

Existing guards that fail to catch this: `verify_signature` only authenticates *a* sender org, not team ownership; the `ExplicitParameters` schema in `MembershipHandler` validates shape/types only, not cross-references; `Team.find_or_create_by!` has no `organization:` predicate in its lookup, only in the creation block.

### Impact Explanation
An attacker who owns any GitHub organization with a webhook registered in this Shipit instance can forcibly revoke `Membership` (and therefore `authorized?`) for any Shipit user by referencing another org's `Team.github_id`. This is a cross-tenant authorization-integrity violation: it corrupts authorization state for a party (the victim, and the victim's org) that never authenticated the request. It matches "escalation into `Shipit.github_teams` authorization" in reverse — de-authorization rather than authorization, but the same broken binding — and is repeatable against arbitrary users/teams for as long as the attacker can guess or observe target `Team.github_id` values (which are simply GitHub's public team IDs, discoverable via GitHub's API/UI in many cases). It does not require repository-level pairing (unlike stack/commit mutation), since `Team` records are keyed purely by `github_id`, not scoped to the requesting org, and the write is a real, persisted deletion in the primary tenant's `Membership` table, not just a display bug.

### Likelihood Explanation
Preconditions: (1) a `Team` record for `org_a`'s team must already exist in Shipit (created previously by a legitimate membership event or via `Team.find_or_create_by_handle`), (2) the attacker needs their own GitHub org onboarded to this Shipit instance with a valid webhook secret (a normal/cheap step, since Shipit supports multi-org hooking by design), and (3) the attacker must know the target `Team`'s numeric GitHub `github_id`, which is not treated as secret by GitHub. Given these, the attack is a single unauthenticated-adjacent HTTP POST, fully scriptable, and repeatable at will against any known team ID / victim login combination.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and analogously for the `added` path), require that the resolved `Team#organization` matches `params.organization.login` before allowing any mutation; reject (raise/drop) the event if an existing `Team` with that `github_id` belongs to a different organization than the one whose secret verified the webhook. Alternatively, scope the `find_or_create_by!` lookup to `(github_id:, organization: params.organization.login)` so cross-org collisions on `github_id` cannot resolve to another org's `Team`.

### Proof of Concept
```ruby
test "cross-org membership 'removed' webhook cannot de-authorize a victim from another org's team" do
  org_a_team = shipit_teams(:shopify_developers) # organization: 'shopify'
  victim = shipit_users(:walrus)
  Membership.find_or_create_by!(user: victim, team: org_a_team)
  assert victim.reload.authorized?

  # Attacker owns org_b, with its own webhook secret registered.
  GithubHook::Organization.create!(organization: 'org_b', event: 'membership', secret: 'org_b_secret')

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'removed',
    team: { id: org_a_team.github_id, name: org_a_team.name, slug: org_a_team.slug, url: org_a_team.api_url },
    organization: { login: 'org_b' }, # signs with org_b's secret, NOT org_a's
    member: { login: victim.login }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'org_b_secret', payload)
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Membership.where(user: victim, team: org_a_team).count } do
    post :create, body: payload, as: :json
  end
  assert victim.reload.authorized?, "victim should remain authorized; org_b must not be able to mutate org_a's team membership"
end
```
Before the fix, this test fails: the `Membership` is deleted and `victim.authorized?` becomes `false`, despite the request being signed only by `org_b`, an organization with no relationship to `org_a`'s team.
