## Title
Webhook signature verification binds to `repository.owner.login`, but every event handler binds to `repository.full_name` — an attacker owning one configured GitHub App organization can forge cross-organization webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which per-organization `webhook_secret` to validate an inbound `X-Hub-Signature` against using `repository_owner`, itself read straight from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`). Every webhook handler, however, resolves the `Repository`/`Stack` to actually act on using a *different* attacker-controlled field of that same body: `repository.full_name`. Nothing ties these two fields together, so a valid HMAC computed with organization A's webhook secret authorizes a payload whose `repository.full_name` names a repository belonging to organization B.

### Finding Description
In `verify_signature`:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a per-organization GitHub App config (`github_app_config(organization)`), each with its own independently configured `webhook_secret`, and raises `GithubOrganizationUnknown` (→ 422) only if that organization isn't configured in Shipit at all: [2](#0-1) 

`verify_webhook_signature` only proves that the raw request body was HMAC-signed with the secret belonging to whatever organization `repository_owner` claims — it makes no statement about any other field in that body: [3](#0-2) 

But once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, attacker-controlled JSON to handlers that never re-derive or check `repository.owner.login` again. Instead they resolve the target repository from `repository.full_name`: [4](#0-3) [5](#0-4) 

For example, `PushHandler` looks up stacks purely by `repository_name` (`full_name`) and triggers a sync using attacker-supplied `after` (head sha): [6](#0-5) 

The same disconnect exists for pull-request handlers, which archive/unarchive review stacks and mutate `PullRequest` records purely off `params.repository.full_name`: [7](#0-6) [8](#0-7) 

This is structurally the same bug class as the Fedimint report: an unauthenticated (from Shipit's perspective — no session/token needed) endpoint resolves *which resource to act on* from a field the caller freely chooses, while the field that was actually checked (`repository.owner.login`, used to pick the signing secret) is a different, independent field the caller also freely chooses. There is no cryptographic binding between "the organization whose secret authenticated this request" and "the repository the handler will mutate."

### Impact Explanation
This breaks the equality: *organization that authenticated == repository that is written*, which does not hold. Any org administrator who legitimately installs Shipit's GitHub App on their own organization ("Org A") learns Org A's `webhook_secret`. They can then POST directly to `/webhooks` with a body whose `repository.owner.login` is `"Org A"` (so `verify_signature` selects and validates against Org A's own secret, which they can correctly sign) but whose `repository.full_name` is set to any other repository configured in the same Shipit instance (e.g., `"Org B/victim-repo"`). Depending on the event chosen, this permits:
- Forcing `GithubSyncJob` on Org B's stack with an attacker-chosen `expected_head_sha` (`push` event via `PushHandler`).
- Archiving/unarchiving Org B's review stacks and forging pull-request state (`pull_request` events).
- Injecting/forging commit statuses and check-runs (other handlers keyed the same way).

This is a cross-organization/cross-repository write achieved without any GitHub credentials, Shipit session, or `ApiClient` token for the victim organization — it only requires a legitimate GitHub App installation for *some* organization already onboarded to the same Shipit instance. This matches the report's "Critical: cross-repository writes" impact bucket.

### Likelihood Explanation
Exploitability requires only:
1. A multi-tenant Shipit deployment with more than one organization configured (each with its own GitHub App / webhook secret) — an explicitly supported configuration (`github_app_config`).
2. Attacker control of one such organization's GitHub App installation (attainable by any org owner who legitimately onboards their own org to a shared Shipit instance).
3. A direct HTTP POST to the shared `/webhooks` endpoint with a hand-crafted JSON body and a correctly computed `X-Hub-Signature` using their own secret.

No interaction with the actual GitHub webhook delivery pipeline is required, since Shipit's controller performs no validation that the request actually originated from GitHub for that repository — it only checks the HMAC against a secret chosen by an attacker-controlled field.

### Recommendation
After signature verification, cross-check that `repository.owner.login` (or `organization.login`) used to select the webhook secret matches the owner segment implied by `repository.full_name` before dispatching to any handler, rejecting the payload (422/400) on mismatch. Alternatively, derive the repository/stack scoping exclusively from the same organization value that authenticated the request, rather than from an independently attacker-controlled `full_name` field.

### Proof of Concept
1. Configure Shipit with two organizations, each with distinct GitHub Apps/webhook secrets: `OrgA` (attacker-controlled) and `OrgB` (victim, hosting stack `OrgB/victim-repo`).
2. Attacker, as an admin of `OrgA`, knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac using OrgA's webhook_secret over the raw body>` and POSTs it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, validates successfully against `OrgA`'s secret.
6. `PushHandler#process` resolves stacks via `repository.full_name == "OrgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — despite the request never being signed with anything belonging to `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
