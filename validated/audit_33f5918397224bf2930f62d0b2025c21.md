## Finding confirmed

**The broken binding:** `repository_owner` used to select the HMAC-verifying `GitHubApp` should equal the owner of the repository the handler actually mutates. Concretely, the code requires:

`Shipit.github(organization: params.dig('repository','owner','login')).webhook_secret` (used in `verify_signature`) ⟺ `Shipit::Repository.from_github_repo_name(params.repository.full_name).owner` (used in the handler to locate the `Stack`).

These are two independent reads of attacker-controlled JSON with no cross-check, so the equality can be broken trivially.

### Trace

- `Shipit::WebhooksController#verify_signature` selects the app/secret purely from `repository_owner`, i.e. `params.dig('repository', 'owner', 'login')`: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` trivially returns `true` when that org has no configured `webhook_secret`: [3](#0-2) 
- Multi-org config is officially supported, and each org can independently have `webhook_secret: nil` (documented, and mirrored in fixtures such as `test/dummy/config/secrets_double_github_app.yml`). [4](#0-3) 
- The handler never consults `repository_owner`/the verified org again — it resolves the target repo strictly from `params.repository.full_name`: [5](#0-4)  via `Repository.from_github_repo_name`, which parses `"owner/name"` out of the string and does a DB lookup with no relation to `repository.owner.login`: [6](#0-5) 
- `capture_labels` then persists attacker-supplied label names onto the resolved victim stack's `PullRequest`: [7](#0-6) 
- Those labels are turned into uppercased env vars for the `ReviewStack`, which then flow into deploy/task env building (`TaskCommands#env`, `DeployCommands#env`) and eventually into commands executed for the stack: [8](#0-7) [9](#0-8) 

### Exploit

1. Attacker controls (or is designated as owner of) a GitHub org that is configured in Shipit's multi-org `github:` secrets block with `webhook_secret: nil`/absent (a legitimate, documented configuration pattern for orgs without webhook secrets set yet, e.g. during onboarding). Call it `no-secret-org`.
2. Attacker forges a `pull_request` webhook: `X-Github-Event: pull_request`, `action: "unlabeled"`, `repository.owner.login = "no-secret-org"`, but `repository.full_name = "victim-org/victim-repo"` (a real repository already registered in Shipit with an active `merge_queue_enabled: true` `ReviewStack`).
3. `verify_signature` looks up `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid signature is even required.
4. `LabelCapturingHandler#process` resolves `repository` via `victim-org/victim-repo`'s `full_name`, finds the victim `Stack`/`PullRequest`, and overwrites its `labels` with attacker-chosen values.
5. Because `ReviewStack#env` uppercases each label into a `"true"`-valued env var, and merge-queue continuous delivery reads `Stack#env`/`ReviewStack#env` during deploy/merge task execution, the attacker injects env vars into a repo/stack they never authenticated against.

Existing guards do not catch this: `drop_unhandled_event` only checks the event type exists, the `ExplicitParameters` schema only validates the shape/types of fields (not their cross-consistency), and there is no comparison anywhere between the verified organization and the resolved repository's owner.

### Title
Webhook signature verification org (`repository.owner.login`) is decoupled from the repository actually mutated (`repository.full_name`), allowing cross-org label injection via `LabelCapturingHandler` on merge-queue-enabled stacks - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks the HMAC secret to verify with based solely on `repository.owner.login`, while `LabelCapturingHandler` (and all sibling `pull_request` handlers) resolve the target `Stack` solely from `repository.full_name`. In a multi-org Shipit deployment where at least one configured org has no `webhook_secret`, an attacker can pick that org as `repository.owner.login` (making signature verification a no-op) while pointing `repository.full_name` at a victim org's real, registered, merge-queue-enabled review stack, causing the forged event to mutate that victim stack's `PullRequest#labels` unauthenticated.

### Finding Description
See trace above. Root cause: the two params (`repository.owner.login` for auth, `repository.full_name` for the mutated record) are never cross-validated. `verify_webhook_signature` short-circuits `true` when the selected org's `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`), a state that is officially supported/documented for multi-org configs. The attacker forges a `pull_request`/`action=unlabeled` payload naming the no-secret org as owner and a real victim `owner/repo` as `full_name`; `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) resolves purely off the string, ignoring which org authenticated the request.

### Impact Explanation
Attacker-controlled `PullRequest#labels` are written for a repository/stack they never authenticated against — a payload for one (no-secret) org mutating another org's stack, matching the Critical "payload for one repository mutating another's stack" category. Because `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) turns each label into an uppercased `"true"` environment variable consumed by `TaskCommands#env`/`DeployCommands#env` and ultimately by spawned deploy/merge/rollback commands, this is an env-injection primitive into another tenant's deploy pipeline. On a `merge_queue_enabled: true` stack, this can influence merge-queue behavior gates that key off env vars, amplifying to unauthorized deploy/merge activity. This is repeatable against any victim repository whose `owner/name` the attacker can guess or observe, as long as any configured org in the multi-org secrets file lacks a `webhook_secret`.

### Likelihood Explanation
Requires: (a) a multi-org Shipit deployment, (b) at least one configured org with `webhook_secret` unset — an explicitly supported/documented configuration, not a misconfiguration unique to one operator, (c) knowledge of a victim `owner/repo` name (public information). No GitHub secrets, session, or API token needed at all — purely an unauthenticated `POST /webhooks`. Attacker cost is a single crafted HTTP request, fully repeatable/scriptable against any pull-request-related handler (`opened`, `labeled`, `unlabeled`, `reopened`, `closed`, `assigned`, `edited` — all use the same `repository.full_name`-only resolution).

### Recommendation
After successfully verifying the webhook signature for `repository_owner`, assert that the resolved `Repository`/`Stack`'s owner equals `repository_owner` (or, better, resolve which org/app to use for verification from the already-loaded `Repository` record's stored owner rather than from untrusted payload fields) before invoking any handler. Reject the event (422) on mismatch.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` patterns):
```ruby
test "cross-org owner/full_name split lets a no-secret org mutate a victim's merge-queue stack" do
  victim_stack = shipit_stacks(:review_stack) # merge_queue_enabled: true, repository owner e.g. "shopify"
  no_secret_org = "no-secret-org"

  Shipit.stubs(:github_app_config).with(no_secret_org).returns(webhook_secret: nil, app_id: 1, installation_id: 1, private_key: nil)
  # (or configure via secrets fixture with webhook_secret: nil for no_secret_org)

  payload = {
    action: "unlabeled",
    number: victim_stack.pull_request.number,
    pull_request: {
      id: 1, number: victim_stack.pull_request.number, url: "http://x", title: "t", state: "open",
      additions: 1, deletions: 1,
      head: { sha: "a" * 40, ref: "feature" },
      user: { login: "attacker" },
      assignees: [],
      labels: [{ name: "MALICIOUS_ENV_FLAG" }]
    },
    repository: { owner: { login: no_secret_org }, full_name: victim_stack.repository.github_repo_name },
    sender: { login: "attacker" }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  # no X-Hub-Signature needed since no_secret_org has no webhook_secret

  assert_changes -> { victim_stack.pull_request.reload.labels }, to: ["MALICIOUS_ENV_FLAG"] do

  end
  assert_response :ok
  assert_equal "true", victim_stack.reload.env["MALICIOUS_ENV_FLAG"]
end
```
Assert on both sides of the equality: before the fix, `repository_owner == "no-secret-org"` while the mutated stack's actual `repository.owner == "shopify"` (mismatch, exploit succeeds); after the recommended fix, the request is rejected with 422 because the resolved repository owner does not match the org that authenticated the request.
