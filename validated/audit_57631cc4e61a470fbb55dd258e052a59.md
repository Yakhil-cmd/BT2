### Title
Recovery pallet's reentrancy filter in `control_inherited_account` only checks the outer call, allowing an inheritor to slash higher-priority recovery attempts via a `Utility::batch` wrapper - ([File: substrate/frame/recovery/src/lib.rs])

### Summary
`pallet_recovery::control_inherited_account` lets the `inheritor` of a recovered account dispatch an arbitrary `RuntimeCall` as the recovered ("lost") account, while installing a call filter meant to prevent that call from being (or containing) another `pallet_recovery` call — specifically to stop an inheritor from calling `slash_attempt` or `set_friend_groups` to sabotage a higher-priority, still-pending recovery attempt from a competing friend group.

### Finding Description
`control_inherited_account` builds a `Signed(recovered)` origin and adds a filter that rejects the call if it *is* a `pallet_recovery::Call` subtype: [1](#0-0) 

The filter closure is `|c| c.is_sub_type().is_none()`, i.e., it only inspects whether the *outer* call passed to `dispatch` is itself a `Call::Recovery(..)` variant. It does not account for wrapper pallets such as `pallet_utility` that internally re-dispatch inner calls using the *same, filter-carrying* origin (`call.dispatch(origin.clone())` inside `Utility::batch`/`batch_all`/`force_batch`), which independently re-evaluate the filter for each inner call via `RuntimeCall::dispatch`'s `filter_call` check: [2](#0-1) [3](#0-2) 

The included regression tests explicitly document the intended invariant and an attempted bypass:
- `inheritor_can_slash_higher_priority_attempts_and_remove_friend_groups` shows the filter correctly blocks a *direct* `slash_attempt`/`set_friend_groups` call. [4](#0-3) 
- `inheritor_cannot_bypass_filter_via_utility_batch` wraps the same `slash_attempt` call inside `pallet_utility::Call::batch` and dispatches it through `control_inherited_account`, asserting no bypass occurs. [5](#0-4) 

Because `OriginTrait::filter_call`/`add_filter` re-checks the composed filter stack on every nested `dispatch` call (as used generically by `construct_runtime!`), whether the wrapped `slash_attempt` actually executes depends on whether `Utility::batch`'s inner `call.dispatch(origin.clone())` call preserves and re-applies the added reentrancy filter to the inner call. I was not able to execute the test suite in this environment to confirm the observed runtime behavior (pass/fail) of `inheritor_cannot_bypass_filter_via_utility_batch`, so I cannot confirm with certainty whether this specific pathway currently produces a bypass in this snapshot of the code, or whether the standard FRAME filter-composition mechanism already prevents it (which is the documented, expected behavior of `add_filter`/`dispatch`).

### Impact Explanation
If the filter bypass is real, a malicious inheritor of a *lower-priority* friend group could invoke `slash_attempt`/`set_friend_groups` as the recovered account through an allowed wrapper call (e.g., `Utility::batch`, `dispatch_as`, or other multi-call pallets), burning another initiator's security deposit and/or destroying friend-group configuration, undermining the guarantee documented at lines 559-561 that "the controller is not allowed to dispatch calls of the recovery pallet." This would let a lower-priority claimant griefing/destroy a higher-priority recovery attempt, effectively stealing account inheritance rights — a Critical/High impact if confirmed.

### Likelihood Explanation
Low-to-moderate, contingent on unverified code behavior. The attacker only needs: (1) to be configured as `inheritor` for some friend group of the victim (a legitimate, non-privileged actor recorded on-chain via `finish_attempt`), and (2) to submit one additional signed extrinsic (`control_inherited_account` wrapping a `Utility::batch` call). No governance, root, or validator privileges are required. However, this hinges entirely on whether FRAME's generic filter composition (`add_filter`/`filter_call`, re-checked at every `Dispatchable::dispatch`) actually fails to re-apply to nested calls dispatched by `pallet_utility`, which is the well-established, tested mechanism that the recovery pallet's own comment ("This includes bypassing... filter") and `pallet_utility`'s documentation reference as behaving correctly for non-root origins. I could not confirm a concrete deviation from that mechanism in this analysis.

### Recommendation
- Verify empirically (unit test execution) whether `inheritor_cannot_bypass_filter_via_utility_batch` passes or fails against the current `Utility::batch`/`OriginTrait::add_filter` implementation.
- If a bypass is confirmed, harden `control_inherited_account`'s filter to recursively inspect wrapped/nested calls (e.g., reject any call whose type is `pallet_utility`, `pallet_multisig`, `pallet_proxy`, or other call-forwarding pallets, in addition to `pallet_recovery` itself), rather than relying solely on `is_sub_type()` of the outer call.
- Add an explicit `IsSubType`-based recursive filter or a dedicated `CallFilter` trait bound that walks nested `RuntimeCall` variants before dispatch.

### Proof of Concept
Not independently executed; relying on the existing repository test `inheritor_cannot_bypass_filter_via_utility_batch` in [6](#0-5)  as the closest available integration reproduction. I was unable to run `cargo test -p pallet-recovery` in this session (no terminal/execution access) to observe pass/fail status, so **this finding is unverified** and should be treated as a hypothesis requiring test execution before being reported as a confirmed vulnerability.

				return Err(BadOrigin.into());

			let calls_len = calls.len();
			ensure!(calls_len <= Self::batched_calls_limit() as usize, Error::<T>::TooManyCalls);

			// Track the actual weight of each of the batch calls.
			let mut weight = Weight::zero();
			for (index, call) in calls.into_iter().enumerate() {

fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});
