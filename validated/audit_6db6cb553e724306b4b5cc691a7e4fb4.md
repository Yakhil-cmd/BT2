### Title
Path Traversal via Unsanitized Release Asset Filename in `gh release download` - ([File: pkg/cmd/release/download/download.go])

### Summary
`gh release download` writes downloaded release assets to disk using the asset's `name` field taken directly from the GitHub API response, without stripping directory-traversal sequences. The same file builds a *different*, sanitized code path for source-archive downloads (using `filepath.Base()`), showing the developers are aware of the risk for one code path but omitted the same protection for the asset-name path.

### Finding Description
In `downloadRun`, each release asset name returned by the API is used verbatim as the destination file name: [1](#0-0) 

That name flows into `destinationWriter.Copy`, which builds the destination path with a plain `filepath.Join(w.dir, name)`: [2](#0-1) [3](#0-2) 

`filepath.Join` calls `path.Clean` on the joined string but does **not** confine the result to `w.dir`; a name containing `../` sequences (e.g. `../../../.ssh/authorized_keys`) can walk the resulting path outside the intended download directory, letting the file be written anywhere the running user has permission to write.

By contrast, the archive-download branch of the very same function explicitly guards against this by taking only the base name of the server-supplied filename: [4](#0-3) 

The asset `name` originates from the GitHub Releases API and is attacker-published content in the sense required here: any user (or automation) who is allowed to attach assets to a release in a repository (including public repos where the release itself is the “attacker-controlled” artifact a victim is enticed to download from) controls this string. A victim who runs `gh release download <tag>` against such a repository will have `gh` write the file to a path chosen by the value of `name`, not confined to `--dir`/`.`.

### Impact Explanation
If an attacker can get a victim to run `gh release download` (or the equivalent without `--pattern`/`--archive` filtering by matching filenames) against a repository containing a release with a maliciously-named asset, the CLI can be made to write attacker-controlled bytes to an attacker-chosen path outside the destination directory — e.g. overwriting `~/.ssh/authorized_keys`, shell rc files, or other configuration files reachable by the invoking user, potentially leading to code execution or persistence. This matches the “file write outside the intended path” acceptance criterion.

### Likelihood Explanation
Exploitability depends on whether the GitHub Releases API/UI permits an asset `name` value containing path-separator or `..` sequences to reach this code unmodified. GitHub's release-asset upload flow is known to normalize/sanitize file names in many cases, so this could not be independently confirmed to bypass server-side validation from the available codebase context alone (no server-side test, docs, or evidence in-repo of what characters are rejected). The finding is nonetheless a defense-in-depth gap: the code demonstrates the authors already treat server-supplied filenames as untrusted (the `filepath.Base()` call in the archive branch) but failed to apply the same sanitization to the asset-name branch, so the risk is real regardless of current server-side restrictions, and could be reintroduced or exploited via any host (e.g., GitHub Enterprise Server or a compromised/misconfigured instance) with looser validation.

### Recommendation
Sanitize `a.Name` the same way the archive branch sanitizes its filename — apply `filepath.Base()` (and/or explicitly reject names containing `..` or path separators) before it is used in `destinationWriter.Check`/`Copy`/`makePath`, so a malicious or unexpected asset name can never resolve outside `opts.Destination`.

### Proof of Concept
1. Attacker creates/edits a release on a repository and uploads (or otherwise causes the API to return) an asset with `name` = `../../../../tmp/pwned`.
2. Victim runs: `gh release download <tag> -R attacker/repo`
3. In `downloadRun`, `toDownload` includes the asset with `Name = "../../../../tmp/pwned"`; `downloadAsset` calls `dest.Copy("../../../../tmp/pwned", resp.Body)`.
4. `makePath` computes `filepath.Join(".", "../../../../tmp/pwned")`, which resolves outside the intended `Destination` directory, and `os.OpenFile` writes attacker-controlled content to `/tmp/pwned` instead of the victim's chosen download directory.
