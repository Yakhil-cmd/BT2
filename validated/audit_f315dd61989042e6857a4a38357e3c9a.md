### Title
DoS via Reverting Recipient Permanently Locks Bridged KAIA and Corrupts `lowerHandleNonce` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge updates critical nonce-tracking state and then makes an unchecked external call to the recipient address. If that call reverts, the entire transaction is rolled back — including the nonce bookkeeping — leaving the bridge permanently unable to advance `lowerHandleNonce` past the stuck request, locking the user's KAIA in the source bridge with no recovery path.

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` executes the following sequence:

1. `_setHandledRequestTxHash(_requestTxHash)` — marks the source tx hash as handled  
2. `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber` — records the block  
3. `_updateHandleNonce(_requestedNonce)` — attempts to advance `lowerHandleNonce`  
4. `emit HandleValueTransfer(...)` — emits the settlement event  
5. `(bool ok, ) = _to.call.value(_value)("")` — pushes KAIA to the recipient  
6. `require(ok, "handleKLAYTransfer: transfer failed")` — **reverts everything above if the call fails** [1](#0-0) 

Because Solidity reverts all state changes on `require` failure, steps 1–4 are atomically undone. `handleNoncesToBlockNums[N]` is never durably set to a non-zero value, so the inner loop inside `_updateHandleNonce` — which advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` — can never move past nonce N:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) 

`recoveryBlockNumber` is also frozen at the block of nonce N−1, so the off-chain `valueTransferRecovery` module perpetually re-scans from that block and re-submits the same failing handle transaction. [3](#0-2) 

The same pattern exists in `handleERC20Transfer` (token contract paused / insufficient balance) and `handleERC721Transfer`: [4](#0-3) 

### Impact Explanation

- **Bridged-asset lock**: KAIA deposited on the source chain is irrecoverable — the source bridge has no refund mechanism once `RequestValueTransfer` is emitted and `requestNonce` is incremented.  
- **Persistent bridge-state corruption**: `lowerHandleNonce` is permanently stuck at nonce N; `recoveryBlockNumber` never advances. The off-chain recovery daemon enters an infinite retry loop, wasting operator gas and masking genuine pending transfers.  
- **No admin escape hatch**: The bridge contract exposes no function to skip or override a stuck nonce. The only mitigation available to the owner is `setRunningStatus(false)`, which halts the entire bridge for all users.

### Likelihood Explanation

Any user who requests a KLAY transfer to a contract address whose fallback function reverts (deliberately or accidentally) triggers this condition. The attacker pays only the source-chain gas for `requestKLAYTransfer`; the cost of the infinite retry loop falls entirely on the bridge operator. A single such request is sufficient to permanently freeze `lowerHandleNonce`.

### Recommendation

Adopt a **pull-payment** pattern: instead of pushing KAIA to `_to` inside `handleKLAYTransfer`, record the claimable amount in a mapping and let the recipient withdraw it separately. This decouples nonce advancement from the external call, so a reverting recipient cannot block bridge progress. Alternatively, wrap the external call in a `try/catch`-equivalent (low-level call without `require`) and emit a `TransferFailed` event, allowing the operator to mark the nonce as permanently skipped and advance `lowerHandleNonce` regardless.

### Proof of Concept

```
1. Attacker deploys RevertingWallet on the destination chain:
       fallback() external payable { revert(); }

2. On the source chain, attacker calls:
       sourceBridge.requestKLAYTransfer{value: 1 ether}(
           RevertingWallet, 1 ether, ""
       );
   → emits RequestValueTransfer(nonce=N), increments requestNonce.
   → 1 KAIA is now held in the source bridge with no refund path.

3. Bridge operator calls on the destination chain:
       destBridge.handleKLAYTransfer(
           txHash, attacker, RevertingWallet, 1 ether, N, blockNum, ""
       );
   → Steps 1–4 execute (state written).
   → _to.call.value(1 ether)("") → RevertingWallet.fallback() reverts.
   → require(ok) fires → entire tx reverts.
   → handleNoncesToBlockNums[N] = 0 (reverted).
   → lowerHandleNonce stays at N.

4. Every subsequent retry produces the same revert.
   lowerHandleNonce is permanently stuck at N.
   recoveryBlockNumber is frozen at block(N-1).
   The off-chain recovery loop re-submits the failing tx indefinitely.
   The attacker's 1 KAIA is permanently locked in the source bridge.
``` [5](#0-4) [6](#0-5)
