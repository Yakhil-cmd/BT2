### Title
Webhook signature verification is keyed to an attacker-controlled organization field that is disconnected from the team/stack actually mutated, allowing forged `membership`/`push`/`status` events to escalate into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate a webhook against using a value taken directly from the *unverified* request body. `GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as "always valid." Because the field used to select the verifying organization (`repository_owner`) is independent from the team/repository data that the registered event handlers actually act on (e.g., `team`/`member` for `membership` events), an attacker can pick *any* configured organization that has no `webhook_secret` set to trivially pass signature verification, then supply arbitrary `team`/`member` data to mutate `Team`/`Membership` records for a completely different, "secured" organization — the exact "organization that authenticated versus the repository/entity that is written" binding break called out in scope.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON body before the signature has been checked: [1](#0-0) [2](#0-1) 

It then fetches the GitHub App config for that attacker-supplied organization name and verifies against *that org's* secret: [3](#0-2) 

`verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank — a state explicitly supported by the documented configuration format (`webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

Once `head(422)` is not triggered, `create` dispatches the full, attacker-controlled `params` to the registered handlers for the event type, with no re-check that the data being acted upon belongs to the organization that was used to authenticate the request: [6](#0-5) [7](#0-6) 

For the `membership` event, the handler creates/updates `Team` and `Membership` records purely from `team`/`member`/`action` fields in the body — fields that have no relationship whatsoever to the `organization.login` value that was used to select the signing secret: [8](#0-7) 

`Shipit.github_teams` membership is precisely what gates application-wide authorization: [9](#0-8) 

**The broken binding, as an equality that should hold but doesn't:**
`organization_used_to_verify_signature(params['organization']['login'] or params['repository']['owner']['login'])` == `organization/team actually mutated by the handler (params['team'], params['member'])`

Before the attacker's request: only a real GitHub webhook delivery, signed with the correct org's `webhook_secret`, can create/modify `Team`/`Membership` rows for that org's teams.

After the attacker's request: any unauthenticated actor who knows (a) the name of *any* organization configured in the Shipit instance without a `webhook_secret` (multi-org deployments commonly have this, and it's a documented default/example value), and (b) the numeric `team.id` of a team listed in `Shipit.github_teams` for a *different*, secured organization, can add an arbitrary GitHub login as a member of that team, since `verify_signature` only checks the secret belonging to the (attacker-chosen) `repository_owner`/`organization.login`, not the organization actually owning the mutated team.

### Impact Explanation
This lets an unauthenticated attacker escalate into `Shipit.github_teams` authorization by forging a `membership` webhook — explicitly listed as a High-impact category. Once a login is added as a member of an authorized team, and that login later authenticates via GitHub OAuth, `User#authorized?` will grant it access to the Shipit UI/stacks gated by team membership. The same organization-selection gap also applies to `push`/`status` handlers, letting the same unauthenticated primitive forge commit sync/status events against stacks belonging to a different, secured organization.

### Likelihood Explanation
Exploitability depends only on the deployment having at least one configured GitHub organization with a blank `webhook_secret` (a state directly shown as an accepted/example configuration in the repo's own docs and secrets template) while other configured organizations are secured. No credentials, tokens, or sessions are required — only knowledge of an org name and a target team id (discoverable via the public Shipit UI which lists team names, or by observing legitimate webhook payload shapes).

### Recommendation
Do not let a value taken from the unauthenticated request body determine which secret is used to authenticate that same request. Bind the verifying organization to the fixed configuration entry (single global secret, or a secret resolved from server-side stack/repo registration rather than payload-declared `organization`/`repository.owner`), and additionally validate — inside each handler — that any organization/team/repository identifiers acted upon match the organization that was cryptographically verified for the request. Treat a blank/unset `webhook_secret` as "reject all webhooks" rather than "accept all webhooks."

### Proof of Concept
1. Configure (or target a deployment that configures) two GitHub orgs in `secrets.yml`: `org-unsecured` (no `webhook_secret`) and `org-secured` (has a `webhook_secret`), both per the documented multi-org config format.
2. Identify (via the Shipit UI, which is publicly viewable for team-gated deployments before authorization) the numeric `team.id` for a team under `org-secured` that is included in `Shipit.github_teams`.
3. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "org-unsecured" },
  "team": { "id": <secured_team_id>, "name": "...", "slug": "...", "url": "..." },
  "member": { "login": "attacker-github-login" }
}
```
No valid `X-Hub-Signature` header is required, since `verify_webhook_signature` short-circuits to `true` for `org-unsecured`'s blank secret.
4. `Shipit::Webhooks::Handlers::MembershipHandler` creates a `Membership` record linking `attacker-github-login` to the team belonging to `org-secured`, as demonstrated by the existing test behavior for the `membership` event.
5. When `attacker-github-login` subsequently logs in via GitHub OAuth, `User#authorized?` reports `true`, granting access gated by `Shipit.github_teams`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```markdown
## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
```
