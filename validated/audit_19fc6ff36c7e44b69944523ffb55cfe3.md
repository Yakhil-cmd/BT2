### Title
Deterministic `level`/`unit`-hash ordering of same-MCI AA triggers enables hash-grinding front-running of order-sensitive AAs - (File: `main_chain.js`, `aa_composer.js`)

### Summary
The reported EosNow attack used many Sybil-controlled transactions to manipulate the *order* in which a quiz/bet contract's transactions were processed, letting the attacker control the outcome ("transaction squeeze"). In `ocore`, when several units trigger the same Autonomous Agent (AA) within the same main-chain index (MCI), the order of execution is fully deterministic and derived from unit-level metadata that an ordinary unit poster can freely influence: `level` and the raw base64 `unit` hash string. An attacker who wants to win a race condition inside an order-sensitive AA (e.g. "first to fill the pool", "first to cross a threshold", limited-fund payout games such as the bundled `51_attack_game.oscript`) can grind the content of their own not-yet-broadcast unit (extra no-op data fields, alternate valid parent-unit sets, etc.) to obtain a unit hash/level that sorts ahead of a competitor's already-visible (but still unstable) unit, then broadcast only the winning variant — mirroring the "manipulate multiple wallets/transactions, only publish the favorable one" congestion technique from the external report.

### Finding Description
When an MCI is stabilized, `main_chain.js` selects all units whose outputs trigger AAs and inserts them into the `aa_triggers` queue with an explicitly "deterministic order" comment: [1](#0-0) 

The queue is then drained in exactly that same deterministic order, `level`, then unit hash string, then address: [2](#0-1) 

Both `level` (`ORDER BY ... level ...`) and the unit id itself (`ORDER BY ... aa_triggers.unit ...`, a base64-encoded hash of the unit's content) are attributes that the unit's own author fully controls before broadcasting:
- `level` is derived from the chosen `parent_units` (an author can often choose among several valid free/compatible parent sets returned by `pickParentUnitsAndLastBall`), see the parent-selection logic in `parent_composer.js`: [3](#0-2) 
- The unit hash is computed over the full "naked" unit content (messages, parents, timestamp, etc.) via `objectHash.getUnitHash`/`getNakedUnit`: [4](#0-3) 

Because a unit author can add or vary content that has no effect on the AA's economic logic (e.g., an additional harmless key inside the `data` message consumed via `trigger.data`, or picking amongst multiple equally valid parent sets), they can compute many candidate unit hashes offline (without broadcasting any of them) and only submit the variant whose `(level, unit)` tuple sorts most favorably relative to a competitor's unit that is already visible, but not yet stable, in the DAG. This is the on-chain analogue of the reported "manipulate the transaction/pick which of many crafted transactions actually lands" congestion attack — instead of controlling block-producer scheduling, the attacker controls the deterministic tie-breaker used by every full node to decide `handleAATriggers` execution order for units in the same MCI.

Order-sensitive AA logic is a documented and expected pattern in this codebase — the bundled `51_attack_game.oscript` sample explicitly implements "first team to cross 51% wins" semantics, decided purely by processing order within a state variable check: [5](#0-4) 

Any AA of this shape (limited-fund payout, "first past the post" threshold, a giveaway pool that runs out, etc.) is affected: whichever trigger unit is processed first, per the deterministic `level`/`unit` sort, wins, and this sort key is attacker-grindable.

### Impact Explanation
An attacker can systematically win races in any deployed order-sensitive AA against honest, unprivileged co-participants by grinding unit content to force their trigger to be ordered ahead of a competing, already-visible unstable unit. This results in concrete fund loss/misallocation to honest bettors/contributors (they pay into the AA and lose the race unfairly), i.e. unauthorized diversion of AA funds to the attacker instead of the legitimate, honestly-first participant. This matches the "AA fund loss" impact category: honest counterparties lose their stake to an adversary who wins the payout race by construction rather than by legitimate first-arrival.

### Likelihood Explanation
Any address can post a payment to an AA (fully permissionless, no privileged role required). Grinding unit content (adding a harmless unused field, or selecting among multiple valid parent sets returned by `pickParentUnitsUnderWitnessedLevel`) is cheap and can be done off-chain, without broadcasting failed attempts, so there is no visible "noise" or cost beyond normal unit composition/signing. The attacker only needs to observe a competitor's unstable but already-broadcast unit (which is public on the network) before finalizing and broadcasting their own competing unit. This requires order-sensitive AA logic to exist (a design choice by the AA author, as in the bundled `51_attack_game.oscript` example), so likelihood is Medium rather than High/Critical — it depends on specific application logic, but the deterministic and attacker-influenceable sort key is a core-protocol property, not an isolated one-off contract bug.

### Recommendation
- Avoid using attacker-controllable identifiers (`level`, raw `unit` hash) as the sole implicit ordering/fairness mechanism for cross-trigger races in AAs; if execution order must be a fairness-relevant quantity, document/derive it from something the poster cannot cheaply grind offline (e.g., something bound to values only known after MCI stabilization, or explicit commit-reveal patterns implemented at the AA level).
- Consider providing documentation/tooling warnings (and could be enforced by `aa_validation.js`) for AA templates that base payout branching purely on `number_of_responses`/processing order without a commit-reveal or randomness-from-post-hoc-seed pattern, since the underlying trigger ordering is not adversarially robust.
- At minimum, clearly document in the oscript/AA developer guidance (and via `dryRunPrimaryAATrigger` tooling) that trigger execution order within the same MCI is influenceable by the triggering unit's author, so AA authors do not unknowingly build "first come first served" pools that assume unbiased ordering.

### Proof of Concept
1. AA `X` is deployed implementing a "first N contributors get reward" or "first to cross threshold" pattern, similar in spirit to `test/samples/51_attack_game.oscript`'s 51%-threshold check.
2. Honest user `H` broadcasts a payment+trigger unit `U_H` to AA `X`. `U_H` is visible on the network (unstable, not yet included in an MCI).
3. Attacker `A`, before `U_H`'s MCI stabilizes, composes many candidate variants of their own competing trigger unit `U_A` (varying inconsequential fields such as an unused key in the `data` message payload, or choosing among multiple valid free-parent sets from `pickParentUnitsUnderWitnessedLevel`), computing `objectHash.getUnitHash` locally for each variant without broadcasting.
4. `A` selects the `U_A` variant whose `(level, unit)` tuple sorts before `U_H`'s in the ordering used by `main_chain.js`'s AA-trigger query (`ORDER BY units.level, units.unit, address`) and `aa_composer.js`'s dequeue query (`ORDER BY aa_triggers.mci, level, aa_triggers.unit, address`), and broadcasts only that variant, ensuring both land in the same MCI.
5. When the MCI stabilizes, `handleAATriggers` executes `U_A`'s trigger before `U_H`'s, letting `A` win the race/limited payout that `H` would otherwise have won on a first-come basis. [1](#0-0) [2](#0-1)
