### Title
Liquidation aborts via `unwrap-panic` on disabled-collateral price resolution, allowing an insolvent position to become permanently unliquidatable - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate` calls `process-collateral-asset`, which for disabled collateral resolves the oracle price with `unwrap-panic (price-resolve oracle-data)` instead of a recoverable `try!`/`asserts!` path [1](#0-0) . `price-resolve` itself can legitimately fail (oracle call error, confidence-check failure, staleness/invariant failure) via `try!`/`asserts!` returning `err` [2](#0-1) . When that happens inside `process-collateral-asset`, the `unwrap-panic` aborts the entire transaction with no error code instead of returning a handled error, even though the codebase reserves a dedicated error `u400020 ERR-DISABLED-COLLATERAL-PRICE-FAILED` for exactly this situation [3](#0-2) , which is never actually surfaced/used in `liquidate`.

### Finding Description
`liquidate(borrower, collateral-ft, debt-ft, ...)` is a permissionless action that any liquidator (an unprivileged principal) calls against another user's position (the borrower, a different unprivileged principal), reading the shared oracle/collateral state [4](#0-3) . Within it, `process-collateral-asset` is invoked to price the collateral asset being seized. If that collateral is *disabled* (not part of the enabled bitmap used to build `assets`), the code falls into the "not found" branch and calls `unwrap-panic (price-resolve oracle-data)` directly, bypassing any graceful failure path [1](#0-0) .

`price-resolve` can fail for reasons entirely outside the liquidator's or borrower's control, such as:
- the underlying Pyth/DIA oracle call failing (`try! (call-pyth ...)` / `try! (call-dia ...)`) [5](#0-4) 
- the confidence-interval check failing (`check-confidence`) [6](#0-5) 
- the staleness/monotonic-timestamp invariant failing (`oracle-timestamp-fresh`/`oracle-price-legal`) [7](#0-6) 

Any of these conditions causes `price-resolve` to return an `err`, which `unwrap-panic` turns into an unconditional runtime abort of the whole `liquidate` call - for every liquidator, on every attempt, until the oracle condition clears. This exactly mirrors the H-02 pattern: a value that is only needed to complete a state transition that benefits a third party (there: event log for winners' withdraw path; here: the collateral price needed to complete seizure of an insolvent borrower's disabled collateral) is fetched via a call that can revert for reasons unrelated to the caller, blocking that third-party-benefiting action entirely.

The existence of the dedicated `u400020 ERR-DISABLED-COLLATERAL-PRICE-FAILED` error code in the documented error table [3](#0-2)  confirms the protocol's own design intent was to handle this failure gracefully (return a typed error so it can be caught/retried, or so the liquidator can choose a different collateral asset), but the implementation instead uses `unwrap-panic`, which provides no such recoverable path.

### Impact Explanation
If a borrower holds any *disabled* collateral asset whose oracle feed is temporarily failing (oracle outage, stale publish time exceeding `max-staleness`, or a confidence-ratio breach that is transiently wide), then **any liquidator attempting to liquidate that specific insolvent position via that collateral will have their transaction abort**, regardless of how underwater the position is. This is a stranger-affecting freeze: the borrower's insolvent debt cannot be repaid/seized by liquidators through that collateral path while the oracle condition persists, exposing all other suppliers of the affected debt asset pool to continued bad-debt accrual and socialized loss risk once the position becomes irrecoverable — this lands on the in-scope "temporary freezing of funds" (liquidation seizure of the borrower's collateral is frozen) and, in the worst case where the position's LTV keeps worsening while unliquidatable, contributes to protocol insolvency.

### Likelihood Explanation
Disabled collateral existing on a borrower's position is a normal, expected state (an asset can be disabled by governance while still held by users), and oracle feed hiccups (staleness beyond `max-staleness`, confidence-ratio spikes during volatility, or the external Pyth/DIA call reverting) are realistic, recurring conditions rather than contrived edge cases — the same class of event (sequencer/oracle unavailability) that triggered the original H-02 finding. No attacker action or privileged compromise is required; the bug is purely in how `liquidate` handles a foreseeable oracle failure for the disabled-collateral branch.

### Recommendation
Replace `unwrap-panic (price-resolve oracle-data)` in `process-collateral-asset` with a proper `unwrap!`/`try!` that returns the dedicated `ERR-DISABLED-COLLATERAL-PRICE-FAILED` (u400020) error, allowing callers (and off-chain retry logic, or a fallback liquidation path using a different collateral asset) to handle the failure instead of the whole liquidation transaction aborting unrecoverably.

### Proof of Concept
1. Governance disables collateral asset `X` (still held by borrower `B`) via the assets registry, so `X` is excluded from `get-enabled-bitmap`/`get-assets`.
2. `B`'s position becomes unhealthy (`current-ltv >= ltv-liq-partial`).
3. The oracle feed backing `X` becomes temporarily stale/fails confidence check (e.g., Pyth publish time exceeds `max-staleness`, or `check-confidence` fails during volatility) — `price-resolve` now returns `err`.
4. A liquidator calls `liquidate(B, X, debtToken, ...)`; execution reaches `process-collateral-asset`, hits the `unwrap-panic (price-resolve oracle-data)` at line 814, and the entire transaction aborts with a raw runtime panic (no error code) [1](#0-0) .
5. Every liquidator attempting to seize `X` from `B` fails identically until the oracle condition clears, during which `B`'s bad debt can continue to grow, harming the debt-asset pool's suppliers.

                (borrower principal)
                (collateral-ft <ft-trait>)
                (debt-ft <ft-trait>)
                (debt-amount uint)

                (collateral-receiver (optional principal))

  (let (
    (feeds-check (try! (write-feeds price-feeds)))
    (liquidator contract-caller)
    (position (try! (get-liquidation-position borrower)))
    (pos-full (try! (get-full-position borrower)))
    (mask (get mask position))
    (group (try! (get-egroup mask)))

    (coll-address (contract-of collateral-ft))
    (debt-address (contract-of debt-ft))

    (debt-asset (try! (get-asset debt-address)))

    (debt-aid (get id debt-asset))

    ;; accrue FIRST - populates cache for zToken price resolution
    (u-debt (accrue-user-debts (get debt pos-full)))
    (u-coll (accrue-user-collateral (get collateral pos-full)))

    ;; NOW safe to resolve prices (cache is populated)
    (assets (get-assets mask))
    (notional-valued-assets (get-notional-evaluation { position: position, assets: assets }))
    (total-collateral-usd (get collateral notional-valued-assets))
    (total-debt-usd (get debt notional-valued-assets))

    ;; LTC thresholds, liq params, health

    (liq-penalty-max (buff-to-uint-be (get LIQ-PENALTY-MAX group)))
    (curve-exponent (buff-to-uint-be (get LIQ-CURVE-EXP group)))

    ;; LTV = (debt x 10,000) / collateral

                       (mul-div-down total-debt-usd BPS total-collateral-usd)))
