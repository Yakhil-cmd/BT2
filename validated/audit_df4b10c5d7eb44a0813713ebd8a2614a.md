### Title
Cross-tenant `Status` forgery via unscoped SHA lookup in status webhook handler - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The GitHub `status` webhook handler resolves target commits by `sha` alone, with no check that the commit's repository matches the repository that originated the webhook. Any party who can get GitHub to emit a validly-signed `status` event referencing a SHA that also exists as a `Commit` row in an unrelated stack can mutate that unrelated stack's commit status.

### Finding Description
The expected binding is: `commit.stack.repository.full_name == payload.repository.full_name` must hold before a `Status` is written for that `commit`. The actual code enforces no such equality.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This queries `Commit` globally across every stack/repository in the Shipit installation, keyed only on `sha`, and calls `create_status_from_github!` on every match — regardless of which repository sent the webhook. `create_status_from_github!` unconditionally creates a `Status` record scoped to that commit's own `stack_id` [2](#0-1) , which in turn triggers `enable_ci_on_stack`, `schedule_continuous_delivery`, and `Hook.emit(:deployable_status, ...)` / merge-scheduling side effects via `add_status` [3](#0-2) . None of these downstream effects re-validate the repository.

Upstream, `WebhooksController#verify_signature` authenticates the webhook using `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` [4](#0-3) . This authenticates that the payload was genuinely signed by the GitHub App/organization webhook secret associated with the `repository.owner.login` in the payload — i.e., it proves "this event really came from GitHub for organization/repo A," but it does **not** prove any relationship between repo A and the specific `Commit` row(s) in stack B that happen to share the same `sha`. `verify_signature` and `drop_unhandled_event` guard against forged signatures and unrecognized events, but they do nothing to scope the `status` event's *effect* to the repository it was actually signed for.

Exploit flow:
1. Attacker observes a public SHA that is deployable-track in victim stack B (public PR, commit link, or CI badge).
2. Attacker creates repo A (any GitHub account/org that already has a `webhook_secret`-configured GitHub App entry in Shipit, or any repo covered by an existing organization already onboarded to Shipit), and cherry-picks the commit so the exact `sha` exists in A.
3. Attacker connects any CI provider (or calls the GitHub Statuses API directly on their own repo) to post a status against that SHA in A.
4. GitHub emits a real, correctly-signed `status` webhook for repository A to Shipit's `POST /webhooks`.
5. `verify_signature` passes (it's a legitimate signature for A's organization).
6. `StatusHandler#process` matches `Commit.where(sha: <shared sha>)`, which returns the row belonging to stack B (and any other stack sharing that SHA), and creates/mutates a `Status` on B's commit — with no reference to repo A anywhere in the write.

### Impact Explanation
An attacker with no access to and no relationship with victim stack B can inject arbitrary CI status states (`success`, `failure`, `error`, `pending`, description, `target_url`, `context`) onto a specific commit in B's stack. Because `Status` feeds directly into `Commit#status`/`deployable_status`, this can flip a commit from non-deployable to "green," triggering `stack.schedule_merges` and continuous-deployment auto-deploy logic for stacks with `continuous_deployment: true` [5](#0-4) . This is a payload for one repository mutating another repository's stack/commit state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
The only precondition is that the attacker controls (or can get onboarded onto) any repository whose organization already has a `webhook_secret` configured in Shipit — this is the same precondition needed to get any legitimately signed webhook to Shipit at all, and is independent of whether that organization/repo has anything to do with victim stack B. The attacker needs zero credentials for B, no session, no API token, and no knowledge of B's secrets — only a public SHA and any onboarded repo to replicate it into. Cost is low (a cherry-pick, a CI hookup) and the attack is fully repeatable against any commit whose SHA is guessable/known.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the repository named in the webhook payload (`params.repository.full_name`), joining through `Stack#repository`, instead of a bare `Commit.where(sha: params.sha)`. E.g. resolve stacks via `Stack.joins(:repository).where(repositories: { owner: ..., name: ... })` and only then look up `Commit` within those stacks by `sha`, mirroring the repository-scoping already done for `push`/`check_suite` handlers.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (illustrative)
test "status webhook for repo A must not mutate a commit's status in unrelated stack B" do
  stack_b = shipit_stacks(:shipit) # repository owner/repo-b
  shared_sha = 'deadbeefcafefeed'
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:walrus))

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => stack_b.branch }],
    'repository' => { 'full_name' => 'attacker/repo-a', 'owner' => { 'login' => 'attacker' } }
  }

  # Simulate a genuinely-signed webhook for repo A being processed by the engine's handler
  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  commit_b.reload
  assert_equal 'success', commit_b.state, "commit in stack B was mutated by a status event signed for repo A"
end
```
Both sides of the binding before the bug: `commit_b.stack.repository.full_name` = `"owner/repo-b"` vs `payload['repository']['full_name']` = `"attacker/repo-a"` — they differ, yet `StatusHandler#process`'s unscoped `Commit.where(sha: ...)` still writes the `Status`, proving the divergence.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
