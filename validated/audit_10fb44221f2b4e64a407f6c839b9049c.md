### Title
Signed packages verified via `is_valid_signed_package`/`validateSignedMessage` lack chain/domain binding, enabling cross-network and cross-AA signature replay - (File: object_hash.js, signed_message.js, formula/evaluation.js)

### Summary
Obyte's oscript exposes `is_valid_signed_package()`, which lets any AA trigger sender submit an arbitrary `signed_package` object that is checked against a signer address via `signed_message.validateSignedMessage()`. The hash that is actually signed/verified, `getSignedPackageHashToSign()`, is computed purely from the message content and author list, with no mandatory binding to the network (livenet vs testnet vs devnet), to the specific AA address that consumes it, or to any single-use nonce enforced by the protocol. This is the same root cause described in the external report: signatures are validated off a raw content hash instead of a domain-separated hash, so a signature legitimately produced in one context can be replayed in a different context that shares the same verification code path.

### Finding Description
`getSignedPackageHashToSign()` clones the signed package, strips only the `authentifiers`, and hashes whatever remains: [1](#0-0) 

The `version` field, which is the only thing that differs between livenet (`'4.0'`), testnet (`'4.0t'`) and devnet (`'4.0dev'`) builds, is optional in a signed package schema: [2](#0-1) 

When `version` is omitted (a perfectly valid, in-schema package), the hash to sign no longer depends on network at all, since `getSourceString` is used identically regardless of which network the validating node runs: [3](#0-2) 

`validateSignedMessage()` further does not require `last_ball_unit` (network-awareness) — when it is absent, the function skips all MCI/last-ball freshness checks and only requires the author's `definition` to hash to the claimed address: [4](#0-3) 

Crucially, this same signed package is what oscript's `is_valid_signed_package` op accepts directly from `trigger.data`, i.e. content fully controlled by whoever posts the triggering unit to any AA: [5](#0-4) [6](#0-5) 

Because nothing in the protocol binds the signature to (a) a specific network/chain, (b) a specific AA address that is meant to consume it, or (c) a single use, a signature that an off-chain signer produced to authorize one action (e.g. "release 100 units to X for order #11") is cryptographically indistinguishable from a valid authorization on any other AA (on the same or a different network) that checks `is_valid_signed_package` against the same signer address and expects the same `signed_message` shape. Any protection against replay (nonces, order IDs already consumed, network binding) is entirely left to the AA author's oscript logic; ocore itself provides no mandatory domain separator in the signature scheme, unlike the recommended EIP‑712 style fix in the report (chain ID + verifying-contract binding baked into the hash itself).

### Impact Explanation
If an AA is written to release funds/assets upon presentation of a validly signed package (a common "off-chain authorization" / "voucher" pattern, e.g., signed price attestations, signed payout approvals, or signed claim tickets), an attacker who obtains one such signature (from its legitimate one-time use, from a public testnet deployment of the same AA template, or from another AA sharing the signer address) can resubmit it as `trigger.data.signed_package` to trigger unauthorized fund release again. Because the protocol-level hash offers no chain/AA/nonce binding, this can lead to AA fund loss (double-spending of an authorization that was meant to be honored once) purely through a maliciously crafted, but perfectly protocol-valid, triggering unit — reachable by any unprivileged AA trigger sender.

### Likelihood Explanation
Exploitability depends on an AA actually using `is_valid_signed_package`/signed messages as an authorization gate without adding its own nonce/one-time-use tracking and network binding in the signed message content — which is a documented and encouraged oscript pattern (see the `is_valid_signed_package` test fixtures), making misuse plausible. The attack itself requires no special privilege: any address can submit the replayed `signed_package` as `trigger.data` to any AA that performs this check, and ocore's own signature-hash construction provides no defense-in-depth against it.

### Recommendation
Bind the hash produced by `getSignedPackageHashToSign()` to an explicit domain: mandatory network/`alt` field, and encourage/require an AA-specific binding (e.g., always require `last_ball_unit`/network-aware packages, or add a mandatory field identifying the intended verifying AA address) so a signature cannot validate identically across networks or across unrelated AAs, mirroring the EIP-712 style domain separator recommended in the original report.

### Proof of Concept
1. Off-chain signer creates `signed_message = {order: 11, action: "release", amount: 1000}` and signs it with `signMessage()` using `bNetworkAware=false`, producing `signed_package` with `authors[0].definition` and no `last_ball_unit`. [7](#0-6) 
2. AA `X` on livenet is written with `if (is_valid_signed_package(trigger.data.signed_package, 'SIGNER_ADDR')) { send 1000 units to trigger.address; }` and no additional replay-protection state var.
3. The legitimate consumer posts this package once to AA `X` and receives the payout.
4. Because the hash never bound to AA `X`'s address, network, or a single-use nonce, the same `signed_package` bytes remain a valid authentifier for `SIGNER_ADDR` forever, on any network build (testnet/livenet/devnet) and for any other AA `Y` that checks the same signer address with the same message shape.
5. The attacker resubmits the identical `trigger.data.signed_package` to AA `X` from a different triggering unit/address, or to a clone AA `Y`; `is_valid_signed_package` returns `true` again via `validateSignedMessage`, and funds are released a second time without the signer's fresh consent. [8](#0-7)
