### Title
Race between stale-worktree cleanup and in-flight exechook execution can cause the hook to run against a deleted worktree path - ([File: pkg/hook/hook.go])

### Finding Description
`HookRunner.Run` only tracks a hash string across the producer/consumer channel; it does not hold any reference or lock on the worktree that hash corresponds to: [1](#0-0) 

The hash is written by `hookData.send`, a single-slot, last-write-wins channel with no back-pressure: if the hook is slow or fails and sleeps `--exechook-backoff`, the sync loop can call `Send()` again several times, each time overwriting `hookData.hash` and coalescing the channel event: [2](#0-1) 

When the retry loop wakes up, it re-reads `r.data.get()` to get "the latest value" and calls `Exechook.Do`, which computes the worktree path fresh, purely from the hash, with no existence check: [3](#0-2) [4](#0-3) 

Meanwhile, the main sync loop runs independently and asynchronously of the hook goroutine. After each publish it starts a staleness timer on the previous worktree via `touch()` and, on a later iteration, calls `cleanup()` → `removeStaleWorktrees()` → `git worktree prune` to reclaim any worktree that is no longer the "current" one: [5](#0-4) [6](#0-5) 

Because `hook.Do()` re-derives the worktree path from a bare hash string with no lock/hold against `cleanup()`, there is a genuine TOCTOU window: if the sync loop advances past the hash that `HookRunner` just fetched via `get()` (publishing a newer hash) before or while `Do()` actually executes the command, that worktree becomes non-current and is a candidate for removal by the next `cleanup()` pass, even though the hook goroutine is about to (or currently does) execute a command whose working directory is that now-removed path. An attacker who controls the repo content/ref cadence (per the threat model, they can push commits/branches at will) can:
1. Craft repo content that makes the exechook command fail deterministically on the first hash (forcing entry into the retry/backoff path).
2. Push additional commits during the `--exechook-backoff` sleep so several more syncs complete, each superseding the prior worktree.
3. Rely on the independent, uncoordinated `cleanup()` calls in the main sync loop to prune the earlier (now non-current) worktree(s).
4. Cause the eventual retry of `Do()` to race against `cleanup()` for whichever worktree is current at the moment `get()` executes but becomes stale before/while the command actually runs.

### Impact Explanation
This is a real code-path issue (no coordination between `HookRunner`/`Exechook` and `repoSync.cleanup()`/`removeStaleWorktrees()`), reachable purely from attacker-controlled repo content and push timing under the documented, supported `--exechook-command` / `--exechook-backoff` / `--stale-worktree-timeout` flags. The consumer-facing outcome matches "hook operating on a deleted path": the exec hook's working directory can disappear out from under it, causing the command to fail (non-existent cwd) or, in racier timings, operate against a partially-pruned/inconsistent tree. This is a validation/availability-class bug (repeated hook failures, wedged retry loop, or wrong-tree action), not remote code execution or a --root escape.

### Likelihood Explanation
Requires only the documented `--exechook-command` feature (and optionally a short `--stale-worktree-timeout`, whose default is 0, i.e., no extra retention) plus normal attacker capability to push multiple commits in quick succession while the hook is sleeping in its backoff. No non-default or unsupported flags are required beyond features already documented in `README.md`. The race window is proportional to `--exechook-backoff` and sync `--period`, both attacker-influenceable indirectly by controlling how fast they can force retries; the more failures/pushes an attacker triggers, the more reliably the window can be hit, making this a plausible, repeatable condition rather than a purely theoretical one.

### Recommendation
Have `HookRunner`/`Exechook` acquire a reference (e.g., an open file-descriptor-based pin, or a shared refcount incremented by `Send`/decremented after `Do` returns) on the worktree directory for the hash being processed, and have `removeStaleWorktrees` skip any worktree with an outstanding hook reference, not just the "current" one. Alternatively, verify the worktree still exists (and re-fetch the current worktree for the hash) immediately before invoking the command in `Exechook.Do`, and treat a missing worktree as a distinguishable, retryable error rather than letting the exec command fail against a nonexistent cwd.

### Proof of Concept
Integration-test sketch:
1. Configure `git-sync` with `--exechook-command` pointing to a script that (a) fails on the first invocation for a specific commit content, and (b) on later invocations records `pwd` and `GITSYNC_HASH` to a log file.
2. Start git-sync with a short `--period` (e.g. 100ms) and default `--stale-worktree-timeout` (0) and a `--exechook-backoff` of a few hundred ms.
3. Push commit A that trips the failing condition, then rapidly push commits B, C, D within the backoff window so that several publish/cleanup cycles complete before the hook's retry fires.
4. Assert that the recorder script's logged `pwd`/`GITSYNC_HASH` at retry time corresponds to a worktree directory that still exists on disk at the moment of invocation; under the race, this assertion can fail (directory removed) or the exec call itself errors with "no such file or directory" for the working directory, demonstrating the hook executing against (or attempting to execute against) a reclaimed worktree path — instead of the expected "exactly one invocation per published hash against a live worktree."

func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}

// Do runs exechook.command, implements Hook.Do.
func (h *Exechook) Do(ctx context.Context, hash string) error {
	ctx, cancel := context.WithTimeout(ctx, h.timeout)
	defer cancel()

	worktreePath := h.getWorktree(hash)

	env := os.Environ()
	env = append(env, envKV("GITSYNC_HASH", hash))

	h.log.V(0).Info("running exechook", "hash", hash, "command", h.command, "timeout", h.timeout)
	stdout, stderr, err := h.cmdrunner.Run(ctx, worktreePath, env, h.command, h.args...)
	if err == nil {
		h.log.V(1).Info("exechook succeeded", "hash", hash, "stdout", stdout, "stderr", stderr)
	}
	return err
}

// cleanup removes old worktrees and runs git's garbage collection.  The
// specified worktree is preserved.
func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

	// Let git know we don't need those old commits any more.
	git.log.V(3).Info("pruning worktrees")
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}
