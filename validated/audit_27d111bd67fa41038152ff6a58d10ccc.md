## Analysis Summary

The ToB finding is Solidity-specific (`TickLogic.sol`) and has no direct code presence in `polkadot-sdk`. However, the same *bug class* — truncating fixed-point division compounding an accrual accumulator, exploitable by an unprivileged user triggering many small state-updates instead of one large one — has a demonstrable analog in `pallet-asset-rewards`.

### Title
Reward-per-token accumulator truncation lets a staker grief other stakers' accrued rewards via repeated small stake/unstake calls - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes a running `reward_per_token_stored` accumulator every time `stake`, `unstake`, or `harvest_rewards` is called for a pool [1](#0-0) . The accumulator update performs `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` using integer (rounding-down) division via `ensure_mul`/`ensure_div` [2](#0-1) . This is functionally identical to the reported `tick.yieldFactor += accrualsFor(...).div(...)` pattern: each call truncates a fraction of a raw balance unit, and because any signed staker can force this recomputation as often as they like by splitting a single stake/unstake into many small ones, the total truncation loss compounds far beyond what a single, larger operation would incur over the same block range.

### Finding Description
- `stake` and `unstake` are ordinary signed extrinsics, callable permissionlessly by any holder of the staked asset once a pool exists [3](#0-2) [4](#0-3) . Pool *creation* is permissioned, but staking/unstaking against an existing pool is not.
- Both call `update_pool_and_staker_rewards`, which calls `reward_per_token` and then persists `reward_per_token_stored` and `last_update_block` [5](#0-4) .
- `reward_per_token` computes the accumulator increment as `reward_rate_per_block.ensure_mul(rewardable_blocks_elapsed)?.ensure_mul(PRECISION_SCALING_FACTOR)?.ensure_div(pool_info.total_tokens_staked)?`, where `PRECISION_SCALING_FACTOR = 4096` [6](#0-5) [7](#0-6) . `ensure_div` truncates toward zero (no rounding-up correction), so each invocation can lose up to `(PRECISION_SCALING_FACTOR-1)/PRECISION_SCALING_FACTOR` of a "scaled" unit.
- Because `last_update_block` advances to the current block on every call, an attacker can force this division to execute once per block (or once per extrinsic) instead of once over the whole reward period, by repeatedly staking and unstaking a minimal, non-zero amount. Each extra call is an independent truncation event, so the cumulative lost precision grows with the number of forced updates — directly mirroring the report's "borrow 100,000 USDC one hundred times" pattern.
- The lost fraction is not credited to any staker; it simply never enters `reward_per_token_stored`, so `derive_rewards` (which multiplies by `reward_per_token` and divides by `PRECISION_SCALING_FACTOR` again [8](#0-7) ) under-pays every staker in the pool relative to `reward_rate_per_block * elapsed_blocks`.

### Impact Explanation
This reduces the rewards actually claimable by legitimate stakers below what the configured `reward_rate_per_block` promises, with the shortfall instead staying in the pool's reward account until the admin reclaims it via `cleanup_pool` (which requires the pool to have no stakers left) [9](#0-8) . Unlike the original report, the attacker does not personally capture the diverted value — the effect is a griefing/precision-loss issue that skews reward accounting away from the documented `reward_rate_per_block` rate, not a direct fund-theft primitive. Actual per-call loss is bounded (well under one raw balance unit per truncation, scaled by `PRECISION_SCALING_FACTOR`), and repeated staking/unstaking costs the attacker transaction fees and (for non-zero amounts) freeze/unfreeze operations each time.

### Likelihood Explanation
Low-to-Medium. Any account holding a small amount of the staked asset can trigger this without any privileged role, matching the "no privileged prerequisite" requirement. However, the economic incentive for an attacker is weak (no direct personal gain, pure griefing, and each call costs fees), and the per-call loss is small and bounded by `PRECISION_SCALING_FACTOR = 4096`, unlike a token with very low decimals (e.g. USDC's 6 decimals) exercised at large scale in the original report.

### Recommendation
- Increase `PRECISION_SCALING_FACTOR` or otherwise increase the internal precision of `reward_per_token_stored` (e.g. use a wider fixed-point type) to shrink per-call truncation.
- Consider rounding the `ensure_div` in `reward_per_token` using a rounding mode that minimizes systemic bias (e.g. round-to-nearest or round-up with residual tracking), consistent with `sp_arithmetic`'s `Rounding`/`multiply_by_rational_with_rounding` utilities already used elsewhere in the runtime [10](#0-9) .
- Add a property/fuzz test asserting that total rewards accrued over a fixed `(rate, duration)` are identical regardless of how many `stake`/`unstake` calls are interleaved during that duration, similar to the recommendation in the original report.

### Proof of Concept
No executable reproduction was run in this environment (no code-execution/terminal access available here). The reasoning above is derived purely from static code inspection of `substrate/frame/asset-rewards/src/lib.rs`. A concrete reproduction would be a Rust integration test added to `substrate/frame/asset-rewards/src/tests.rs` that:
1. Creates a pool with a fixed `reward_rate_per_block` and stakes an initial amount from a "victim" account.
2. In scenario A, advances N blocks and calls `harvest_rewards` once.
3. In scenario B, advances the same N blocks but has a second account call `stake(1)`/`unstake(1)` every block to force `reward_per_token` recomputation each time.
4. Asserts the victim's claimable rewards in scenario B are strictly less than in scenario A, demonstrating the truncation-compounding effect.

This test has not been implemented or executed; it is presented as the minimal reproduction path a background engineer could run to confirm the finding.

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}

		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.

			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

/// Returns `a * b / c` (wrapping to 128 bits) or `None` in the case of
/// overflow.
pub const fn multiply_by_rational_with_rounding(
	a: u128,
	b: u128,
	c: u128,
	r: Rounding,
) -> Option<u128> {
	use double128::Double128;
	if c == 0 {
		return None;
	}
	let (result, remainder) = Double128::product_of(a, b).div(c);
	let mut result: u128 = match result.try_into_u128() {
		Ok(v) => v,
		Err(_) => return None,
	};
	if match r {
		Rounding::Up => remainder > 0,
		// cannot be `(c + 1) / 2` since `c` might be `max_value` and overflow.
		Rounding::NearestPrefUp => remainder >= c / 2 + c % 2,
		Rounding::NearestPrefDown => remainder > c / 2,
		Rounding::Down => false,
	} {
		result = match result.checked_add(1) {
			Some(v) => v,
			None => return None,
		};
	}
	Some(result)
}
