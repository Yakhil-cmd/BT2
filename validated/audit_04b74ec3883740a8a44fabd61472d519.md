## Analog Found

The Allo `_fundPool()` bug's root cause is: an arbitrary, attacker-supplied external token contract's `transfer()` call is trusted by its **return value alone** for security-critical accounting, with no verification that a real balance change occurred. The Polkadot SDK analog of this exact anti-pattern exists in `ERC20Transactor`, the XCM `TransactAsset` implementation wired into Asset Hub's XCM executor to let arbitrary `pallet-revive` contracts (deployable by any signed account) act as XCM-transferable "assets."

### Title
Arbitrary pallet-revive contract's `transfer()` return value is trusted without balance verification in `ERC20Transactor`, allowing fabrication of XCM asset holding-register credits - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` treat any `pallet-revive` contract address matched by `ERC20Matcher` as a valid XCM fungible asset. To move value, they issue a `bare_call` invoking the contract's own `IERC20::transfer` function and trust the ABI-decoded boolean return value to determine whether `amount` was actually moved. There is no check of the checking account's or sender's real token balance before/after the call.

### Finding Description
`withdraw_asset_with_surplus` calls into the user-controlled contract at `asset_id` with a `transfer(checking_account, amount)` message and, if the decoded return is `true`, unconditionally credits an `Erc20Credit(amount)` into the XCM holding register: [1](#0-0) 

`deposit_asset_with_surplus` mirrors this on the way out, calling `transfer(beneficiary, amount)` from the checking account and trusting the returned boolean: [2](#0-1) 

The code explicitly documents that it does **not** enforce runtime-level balance constraints, deferring entirely to the attacker-deployed contract: [3](#0-2) 

This is wired into production Asset Hub Westend XCM configuration as one of the trusted `AssetTransactors`: [4](#0-3) 

Contract upload/instantiation on `pallet-revive` is permissionlessly available to any signed account: [5](#0-4) 

This is the same violated invariant as the Allo report: "no checks exist ... to ensure the fee/amount is actually collected, instead of only relying on the successful return of `_transferAmountFrom`." Here, instead of a fee being silently skipped, an attacker's own malicious contract can report success for an arbitrary `amount` without moving any real balance, letting the XCM executor's holding register (`AssetsInHolding`) believe `amount` units of value exist/moved when none actually did.

### Impact Explanation
Any XCM program (executed via the permissionless `pallet_xcm::execute`/`transfer_assets*` extrinsics) that references an attacker-deployed malicious "ERC20" contract as the asset can fabricate arbitrary holding-register credits for that asset with no real backing, because:
1. `withdraw_asset_with_surplus` accepts any `amount` the attacker specifies in the XCM `Asset` value and credits exactly that amount into holding as long as the malicious contract's `transfer` call returns `true` — the contract fully controls this outcome and is not required to actually debit any balance.
2. `deposit_asset_with_surplus` similarly trusts the contract when moving value out of the checking account.

Since the token identity here is the attacker's own deployed contract, this by itself only lets the attacker lie about their own worthless token's movement inside a single XCM program. The severity is bounded by whatever else in the runtime is willing to treat this fabricated holding-register credit as real value (e.g., any downstream XCM instruction, precompile, or pallet that consumes the `AssetsInHolding` register contents, such as fee payment via `BuyExecution`, or transfers to third-party beneficiaries where the illusion of a genuine `Transfer` event could mislead off-chain observers/bridges). I could not confirm, within the scope reachable here, that this fabricated credit is accepted as *reserve-backed* by any other chain (cross-chain `TrustedReserves` filters are `ForeignAssets`-registration-based, not raw-contract-address based), so I cannot substantiate cross-chain unbacked issuance. The demonstrable, in-scope issue is the accounting-integrity break within the local XCM executor's holding register/checking-account flow, rated Medium given the uncertain downstream exploitability beyond self-dealing with the attacker's own asset.

### Likelihood Explanation
High likelihood of triggering the flawed check itself: any signed account can deploy a malicious ERC20-like contract on `pallet-revive` and immediately invoke `pallet_xcm::execute` with a `WithdrawAsset`/`DepositAsset` program referencing it — no privileged role, governance, or third-party cooperation is required to reach `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus`. What remains unproven is a concrete downstream sink that converts the fabricated credit into loss for a third party.

### Recommendation
Do not rely solely on the boolean return value of an externally-controlled contract's `transfer` call for XCM asset accounting. Before crediting/debiting the holding register, read the checking account's (and/or sender's/beneficiary's) actual `balanceOf` before and after the call and use the observed delta — not the attacker-controlled `amount` parameter or return value — to determine how much was actually moved, mirroring the Allo report's own recommended mitigation of comparing balances before/after instead of trusting the transfer's return status.

### Proof of Concept
Not executed against a live/test network; no test harness run was performed. The finding is derived from static analysis of the reachable, permissionless code path:
- Contract deployment: `pallet_revive::Config::UploadOrigin`/`InstantiateOrigin = EnsureSigned<Self::AccountId>` [5](#0-4) .
- Asset transactor reachable via XCM executor config `AssetTransactors` including `ERC20Transactor` [4](#0-3) .
- Trust-without-verification in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` [6](#0-5) , [7](#0-6) .

A concrete integration-test PoC would require: (1) deploying a PVM/EVM contract on `pallet-revive` implementing `IERC20::transfer` that always returns `true` without adjusting any storage balance, (2) registering its address so `ERC20Matcher` resolves it as an `AssetId`, and (3) calling `pallet_xcm::execute` with `WithdrawAsset`/`DepositAsset` for that asset and asserting the holding register/checking-account state versus the contract's actual (unchanged) `balanceOf`. This was not run; I am not claiming test execution or results beyond the static code-path analysis above.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
