### Title
Race condition between `shrinkCache()`'s premature mutex release and concurrent DAG/stability writers causes cache corruption ([File: storage.js])

### Summary
The Linux CVE is a use-after-free caused by a race between resizing a shared ring buffer and a parallel reader/opener that is not correctly serialized. The `ocore` analog is `storage.shrinkCache()`, which acquires the global `"write"` mutex but releases it (`unlock()`) *before* the asynchronous `db.query()` callbacks that actually mutate the shared in-memory DAG caches (`assocKnownUnits`, `assocCachedUnits`, `assocBestChildren`, `assocStableUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`) have completed. This breaks the mutual-exclusion guarantee the rest of the codebase relies on for these structures, letting a concurrent writer/validator run its own critical section while `shrinkCache`'s deletions are still in flight — the same "protective lock released too early relative to the operation it is meant to protect" bug class as the kernel race.

### Finding Description
`shrinkCache()` in [1](#0-0)  is invoked periodically (`setInterval(shrinkCache, 300*1000)`, [2](#0-1) ) and whenever the caches (`assocCachedUnits`, `assocKnownUnits`, `assocStableUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`) grow past `MAX_ITEMS_IN_CACHE`. It:

1. Acquires the global `"write"` mutex: `const unlock = await mutex.lock("write");` [3](#0-2) 
2. Fires off a series of asynchronous `db.query()` calls in a `for` loop, each of which deletes cache entries in its callback: [4](#0-3) 
3. Calls `unlock()` immediately after starting the loop, **without waiting** for any of the `db.query` callbacks to finish: [5](#0-4) 

Because `unlock()` is called synchronously right after the loop (not inside a completion callback / `Promise.all`), the `"write"` lock is released while an unbounded number of pending `db.query` callbacks are still queued to delete entries from `assocKnownUnits`, `assocCachedUnits`, `assocBestChildren`, `assocStableUnits`, `assocCachedUnitAuthors`, and `assocCachedUnitWitnesses`.

Every other subsystem that mutates the DAG state treats the `"write"` lock as sufficient protection for these same maps: `writer.saveJoint()` takes it via `await mutex.lock(["write"])` [6](#0-5)  before writing new entries into `storage.assocStableUnits` / `storage.assocStableUnitsByMci` [7](#0-6) , and `joint_storage.purgeUncoveredNonserialJoints()` also takes `["write"]` before calling `storage.forgetUnit()` / `storage.fixIsFreeAfterForgettingUnit()` which iterate and delete from `assocUnstableUnits` [8](#0-7) , [9](#0-8) .

Because `shrinkCache` releases the lock early, a second `"write"`-locked operation can begin and run concurrently with `shrinkCache`'s still-pending `db.query` deletion callbacks. Node's single-threaded event loop interleaves these callbacks with the newly-unlocked writer's callbacks, so:
- A unit that is freshly (re)written into `assocCachedUnits`/`assocBestChildren` by the concurrent writer can be deleted moments later by `shrinkCache`'s stale, already-computed `arrUnits` list (captured before the lock was released), silently reverting the in-memory cache to a stale/missing state even though the DB and the rest of the in-memory state have already moved forward.
- Code such as `fixIsFreeAfterForgettingUnit` in `joint_storage.purgeUncoveredNonserialJoints`, which reads `storage.assocUnstableUnits[row.unit].parent_units` and iterates `assocUnstableUnits` to compute `is_free` flags [10](#0-9) , can now execute concurrently with `shrinkCache`'s in-flight deletes touching overlapping unit sets, since the `"write"` lock is no longer providing exclusivity for the whole shrink operation.

This mirrors the CVE's root cause: a lock intended to serialize a "resize"-style bulk cache operation against concurrent readers/writers is dropped before the operation is actually complete, allowing the two to race on the same shared structure.

### Impact Explanation
`assocUnstableUnits`, `assocBestChildren`, and `assocStableUnitsByMci` are the exact in-memory structures used by `main_chain.js` (`updateLatestIncludedMcIndex`, `advanceMcStability`, `determineIfStableInLaterUnits`) to compute main-chain stability [11](#0-10) , and by `writer.js` to decide `is_free`/`is_stable` flags when saving new units. If these caches are corrupted or entries vanish mid-computation due to the race, a node can compute stability/free-unit status differently from its peers, i.e., **node disagreement on validity or stability of units**, which is one of the explicitly accepted impacts. In the worst case a `TypeError` (dereferencing a `null`/`undefined` cache entry that was concurrently deleted, e.g. `storage.assocUnstableUnits[row.unit].parent_units` in `joint_storage.js` line 271) crashes the write path, stalling that node's ability to confirm new units.

### Likelihood Explanation
`shrinkCache` runs automatically every 5 minutes and additionally whenever cache sizes exceed `MAX_ITEMS_IN_CACHE`, a threshold that any unprivileged unit poster can drive up simply by posting many units to the network, increasing both the frequency of `shrinkCache` invocations and the size (hence duration) of its pending, unprotected `db.query` batch — directly widening the race window. Because `"write"` is the most heavily used lock in the codebase (taken by `saveJoint`, `purgeUncoveredNonserialJoints`, `advanceMcStability`, etc.), the probability that some other write-locked operation starts immediately after `shrinkCache`'s premature `unlock()` (while its deletes are still queued) is high under normal, adversarially-amplified network load.

### Recommendation
Do not call `unlock()` until every `db.query` issued inside `shrinkCache`'s loop has completed — e.g., collect the queries with `async.eachSeries`/`Promise.all` over the chunk loop and only call `unlock()` in the final completion callback, or wrap the deletions in a single query using `db.query(..., callback)` chained sequentially before calling `unlock()`. This restores the exclusivity guarantee that other `"write"`-locked consumers of `assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`, `assocCachedUnits`, `assocCachedUnitAuthors`, and `assocCachedUnitWitnesses` depend on.

### Proof of Concept
1. An attacker (or heavy legitimate usage) posts a large number of units so that `assocCachedUnits`/`assocKnownUnits` exceed `MAX_ITEMS_IN_CACHE`, guaranteeing `shrinkCache()` will proceed past its early-return check on its next 5-minute tick [12](#0-11) .
2. `shrinkCache()` acquires `"write"`, computes `arrUnits` (a snapshot of unit ids to prune), and issues its `db.query` chunk-delete loop, then calls `unlock()` immediately without waiting for the loop's callbacks [13](#0-12) .
3. Immediately after `unlock()`, the attacker's continued unit-posting traffic causes `writer.saveJoint()` or `joint_storage.purgeUncoveredNonserialJoints()` to acquire the now-free `"write"` lock and mutate `assocUnstableUnits`/`assocBestChildren`/`assocStableUnits` for units overlapping the set captured in step 2.
4. When `shrinkCache`'s pending `db.query` callbacks finally fire, they delete cache entries for those same units, undoing/corrupting the state the concurrent writer just established, or (if the unit was concurrently forgotten) causing a `null`-dereference in `joint_storage.fixIsFreeAfterForgettingUnit`/related code paths that assume the cache entry still exists.
5. Result: divergent in-memory DAG/stability state between nodes hitting this race at different times, or a crash on the write path — both are within the accepted impact set (node disagreement on stability / inability to confirm new units).

function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;

			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;

		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
