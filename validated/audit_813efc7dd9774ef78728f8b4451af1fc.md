### Title
`ProxyType::NonTransfer` falsely declares itself a superset of `ProxyType::Auction`, letting a `NonTransfer` proxy self-escalate to `Registrar::swap` - ([File: polkadot/runtime/rococo/src/lib.rs])

### Summary
On the Rococo (and structurally, Westend) relay-chain runtime, `ProxyType::is_superset` claims `NonTransfer` is a superset of every other `ProxyType`, including `Auction`. But `ProxyType::Auction`'s call filter admits the *entire* `Registrar` pallet (including `swap`), while `NonTransfer`'s own filter explicitly and deliberately excludes `Registrar::swap`. Because `pallet_proxy::do_proxy` authorizes `add_proxy`/`remove_proxy` purely through `is_superset` (not `filter`), a delegate holding only a `NonTransfer` proxy can grant an `Auction` proxy for the real account and then use that `Auction` proxy to invoke `Registrar::swap` — a call its own `NonTransfer` grant was specifically designed to deny.

### Finding Description
`pallet_proxy`'s privilege-escalation guard only checks `is_superset`, not `filter`, when a proxy call tries to add/remove another proxy: [1](#0-0) 

For Rococo, `is_superset` is defined so that `NonTransfer` is unconditionally a superset of *every* other `ProxyType`: [2](#0-1) 

Yet `NonTransfer`'s own `filter` explicitly omits `Registrar::swap` while admitting all other `Registrar` register/deregister/reserve calls: [3](#0-2) 

And `ProxyType::Auction`'s filter admits the entire `Registrar` pallet unrestricted (i.e., including `swap`): [4](#0-3) 

So `NonTransfer.filter()` denies `Registrar::swap`, but `Auction.filter()` admits it, while `NonTransfer.is_superset(Auction)` returns `true`. This is exactly the same class of bug that was already identified and fixed for Asset Hub Westend's `NonTransfer`/`Governance` pair in PR #12769, with a regression test added specifically to guard against this lattice violation: [5](#0-4) [6](#0-5) 

That fix and its regression test exist only in `asset-hub-westend`; searching the repository shows no equivalent `is_superset`/`filter` consistency test for `polkadot/runtime/rococo` or `polkadot/runtime/westend`, and their `is_superset` implementations still use the unconditional `(ProxyType::NonTransfer, _) => true` pattern: [7](#0-6) [8](#0-7) 

Westend has the analogous pattern: `NonTransfer` filter excludes `Registrar::swap` (comment "Specifically omitting Registrar `swap`") while `ProxyType::Auction` admits full, unfiltered `Registrar(..)`.

I was not able to fully retrieve and verify the exact body/origin requirements of `Registrar::swap` in `polkadot/runtime/common/src/paras_registrar/mod.rs` before running out of tool iterations, so the precise on-chain effect of `swap` (e.g., whether it swaps parachain lease/lifecycle state between two `ParaId`s under the manager's signed origin) is not confirmed from source in this session — a background agent/Devin session would need to read that file in full to confirm the exact state mutation and its practical impact.

### Impact Explanation
This is a genuine control-flow/authorization gap in the `InstanceFilter` lattice, not a filter denial bypass at dispatch time (dispatch-time `filter` still correctly denies `Registrar::swap` for direct calls under `NonTransfer`). The impact is that a `NonTransfer` delegate can add itself (or a colluding third account) as an `Auction` proxy for the real account, and then dispatch calls through that `Auction` proxy that `NonTransfer` was never meant to authorize — specifically `Registrar::swap`, which manipulates parachain registration/lease state. Depending on `swap`'s exact semantics (unconfirmed above), this could let an account that was only ever entrusted with non-transfer, non-privileged operations manipulate parachain slot/lease assignment for the delegator's account — a authorization boundary violation matching the CWE-266 (incorrect privilege assignment) pattern in the reported Keycloak advisory, where a narrower permission (`manage-clients`/`NonTransfer`) was wrongly treated as equivalent to a broader one (`manage-permissions`/`Auction`).

### Likelihood Explanation
The `NonTransfer` proxy type is a commonly delegated, low-trust proxy type intended for exactly this kind of non-transfer administrative delegation, so the precondition (a user having granted a `NonTransfer` proxy to some account) is realistic and requires no privileged role, governance action, or stolen keys — only a normal `add_proxy(NonTransfer)` extrinsic by any account holder. The escalation itself requires only two ordinary signed extrinsics (`add_proxy(Auction)` via the `NonTransfer` proxy, then `Registrar::swap` via the newly created `Auction` proxy), both dispatchable by the same untrusted delegate.

### Recommendation
Apply the same fix used for Asset Hub Westend (PR #12769/#12771) to the relay-chain runtimes: either remove `Auction` (and any other type whose filter is a strict superset of `NonTransfer`'s filter for some call) from the unconditional `(ProxyType::NonTransfer, _) => true` rule in `polkadot/runtime/rococo/src/lib.rs` and `polkadot/runtime/westend/src/lib.rs`, or extend `NonTransfer`'s filter to also admit `Registrar::swap`. Add a lattice-consistency regression test (mirroring `proxy_type_superset_relation_matches_call_filters`) to `polkadot/runtime/rococo` and `polkadot/runtime/westend` test suites to prevent recurrence.

### Proof of Concept
A full runtime integration reproduction was not executed in this session (no terminal/build access available in ask-only mode). The logical PoC path, backed by the cited source lines, is:
1. Account `A` grants account `B` a `ProxyType::NonTransfer` proxy via `Proxy::add_proxy`.
2. `B` calls `Proxy::proxy(real: A, proxy_type: NonTransfer, call: Proxy::add_proxy(delegate: B_or_C, proxy_type: Auction))`. This passes `pallet_proxy`'s guard because `NonTransfer.is_superset(Auction) == true` [2](#0-1) , even though `NonTransfer.filter()` denies `Registrar::swap`.
3. The now-`Auction` proxy calls `Proxy::proxy(real: A, proxy_type: Auction, call: Registrar::swap { .. })`, which `Auction.filter()` admits [4](#0-3) .
4. `Registrar::swap` executes with `A`'s parachain registration state, a call `A`'s original `NonTransfer` grant was designed to exclude.

This finding should be treated as **unconfirmed/needs verification** pending: (a) reading the full `Registrar::swap` implementation to confirm its exact origin checks and mutation effects, and (b) an actual integration test run (e.g., adapting `asset-hub-westend`'s `tests.rs` pattern to `polkadot/runtime/rococo`) to empirically demonstrate the escalation, since I was unable to execute or read that file's body before the session's tool budget was exhausted.

/// `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `ProxyType::is_superset`, so a
/// proxy type that *declares* itself a superset of another must also *admit* every call that other
/// type admits. Otherwise the "smaller" type is reachable as an escalation: the declared superset
/// can grant itself the subset proxy and thereby gain permissions its own filter denies.
///
/// This checks that property across the whole lattice rather than a single pair, so the class of
/// bug cannot silently reappear on another edge.
#[test]
fn proxy_type_superset_relation_matches_call_filters() {
	use frame_support::traits::InstanceFilter;

	let calls = representative_proxy_calls();

	for superset in all_proxy_types() {
		for subset in all_proxy_types() {
			if !superset.is_superset(&subset) {
				continue;
			}

			for call in calls.iter() {
				if subset.filter(call) {
					assert!(
						superset.filter(call),
						"lattice violated: {superset:?} declares itself a superset of {subset:?}, \
						 but rejects {call:?} which {subset:?} admits",
					);
				}
			}
		}
	}
}
