The root cause is confirmed: `Team` lookup is keyed solely by `github_id`, with no organization-scoping check against the org that signed the webhook.

### Title
Cross-organization team membership forgery via unscoped `github_id` lookup - (`app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` resolves the target `Team` via `Team.find_or_create_by!(github_id: params.team.id)`, which is looked up purely by the GitHub team numeric ID and never validated against the organization that actually authenticated the webhook. Because `WebhooksController#repository_owner` falls back to the attacker-controlled `organization.login` field of the payload for signature verification, an attacker who owns any GitHub organization (and thus its own genuine `webhook_secret`) can sign a `membership` event referencing a victim org's real `team.id`, causing Shipit to delete (or add) a `Membership` for a team it doesn't own.

### Finding Description
The binding that must hold is: `organization_that_signed(request) == organization_that_owns(team_referenced_by_payload)`. Tracing the code:

- `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . A GitHub `membership` webhook payload has no `repository` key, so `repository_owner` resolves to `params['organization']['login']` — a field fully controlled by the attacker's own payload.
- `Shipit.github(organization: repository_owner)` is used to fetch the webhook secret and verify `X-Hub-Signature` [3](#0-2) . Since `repository_owner` is the attacker's own org, this passes with the attacker's own genuine secret.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... team.organization = params.organization.login ... }` [4](#0-3) . The `organization` block only runs on *creation*; if a `Team` row with that `github_id` already exists (the real victim team, previously created legitimately), it is fetched by ID alone, with no check that its `organization` matches `params.organization.login` or the signing org.
- `process` then does `member = User.find_or_create_by_login!(params.member.login)` (resolves the real "legit-operator" user by login) and, for `action == 'removed'`, `team.members.delete(member)` [5](#0-4)  — deleting the real `Membership` row for the real team, despite the request never having been authenticated by that team's actual organization.

Attacker request: POST `/webhooks` with header `X-Github-Event: membership`, body `{"action":"removed","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"legit-operator"}}`, signed with `X-Hub-Signature` computed using the attacker's own org's `webhook_secret` (which they legitimately possess since it's their own GitHub org/App installation).

None of the existing guards catch this: `verify_signature` only proves the request was signed by *some* org's secret, not the org owning the referenced team; `ExplicitParameters` schema only validates types/presence, not cross-field ownership; `drop_unhandled_event` is irrelevant since `membership` is a handled event.

### Impact Explanation
A completely unrelated, attacker-owned GitHub organization's webhook can delete (or forge-add) `Membership` rows for teams belonging to any other organization onboarded to this Shipit instance, as long as the attacker can guess/observe the target team's numeric `github_id` (sequential/enumerable, or discoverable via public GitHub team APIs/URLs). This directly revokes (or grants) `Shipit.github_teams` authorization for arbitrary users, per `User#authorized?` [1](#0-0) , without any legitimate action occurring on GitHub. This is repeatable against any team/org pair known to the attacker and matches the "escalation into/out of `Shipit.github_teams` authorization" High-severity category (arguably Critical-adjacent since it is an authentication-bypass of the org-binding guarantee the signature check is meant to provide).

### Likelihood Explanation
Preconditions: attacker must control a GitHub organization (trivial to create, free) with a valid `webhook_secret` configured in Shipit (`GithubApp`/`GithubHook::Organization` record must exist for that org — this depends on host configuration allowing arbitrary orgs to register hooks/apps against this Shipit instance). Attacker must also know or guess the victim team's numeric `github_id`. Cost is low: one HTTP POST, no privileged session, no victim secrets. Feasibility depends on whether the deployment permits any org's webhook to reach this Shipit instance's `/webhooks` endpoint (which appears to be the case, since `verify_signature` looks up the org dynamically from the payload rather than restricting to a fixed allow-list).

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally in `Team` lookups from webhooks), scope the lookup by both `github_id` AND `organization` (derived from the verified signing organization, not from attacker-controlled payload fields), rejecting/ignoring the event if an existing `Team` with that `github_id` belongs to a different organization than the one that signed the request.

### Proof of Concept
```ruby
test ":membership webhook from unrelated org cannot alter another org's team membership" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'
  membership = Membership.create!(team: victim_team, user: shipit_users(:walrus))
  Shipit.github_teams = [victim_team]
  operator = membership.user
  assert operator.authorized?

  # Attacker owns 'attacker-org' with its own genuine webhook secret
  payload = {
    action: 'removed',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: operator.login }
  }.to_json

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = attacker_org_signature_for(payload)

  assert_difference -> { Membership.count }, -1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  refute operator.reload.authorized?
end
```
