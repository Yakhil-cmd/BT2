### Title
Cross-repository commit status forgery via unscoped `StatusHandler` breaks organization-authentication-to-repository-write binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's `/webhooks` endpoint verifies an incoming GitHub webhook's HMAC signature against the secret configured for the *organization* named in the payload's `repository.owner.login` / `organization.login` field [1](#0-0) , but the `status` event handler that then mutates state never re-checks that the commit it writes to actually belongs to that same, authenticated repository/organization. This breaks the binding: *organization that authenticated the webhook == repository whose data is written*, analogous to the reported pool contract sending an attacker-crafted notification that is trusted purely because of its sender rather than its content.

### Finding Description
`WebhooksController#verify_signature` looks up the GitHub App/secret using only `repository_owner`, derived from the payload itself: [2](#0-1) . It uses that organization's `webhook_secret` to validate the HMAC over the raw payload [3](#0-2) . This only proves the payload was signed by *some* organization the attacker controls (their own org/app installation on the same Shipit instance) — it does not restrict what that payload is allowed to claim about `repository.full_name` or which commit `sha` it references.

Most handlers correctly re-derive the target scope from the payload via `Handler#stacks`, which looks up `Repository.from_github_repo_name(repository_name)` before touching any stack/commit [4](#0-3) . `PushHandler` and `CheckSuiteHandler` use this scoped `stacks` relation [5](#0-4) [6](#0-5) .

`StatusHandler`, however, bypasses this scoping entirely:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

It queries `Commit` globally by `sha` with no join/filter on `repository_name`/`repository.full_name` from the payload, even though `Commit` is scoped to a `Stack`/`Repository` in the schema. Any organization whose webhook signature verifies (i.e., any org onboarded to the shared Shipit instance) can forge a `status` webhook naming an arbitrary `sha` that happens to belong to a *different* repository's commit, and have `create_status_from_github!` write a fabricated status (e.g. `state: "success"`, matching a `ci.require`d `context`) onto that unrelated commit.

### Impact Explanation
Commit statuses gate automated deploys and merges: `deploy_spec`'s `ci.require`/`blocking_statuses` configuration is checked against a commit's statuses [8](#0-7)  before Shipit allows continuous delivery or the merge queue to proceed (see `merge_request.rb`/`stack.rb` usages of statuses). By forging a successful status for a required CI context on a commit in a repository/stack the attacker does not control, an attacker on any onboarded organization can cause an **unauthorized deploy or unauthorized merge** to be triggered on a completely different repository — crossing the "Critical: unauthorized deploy, rollback or merge" bar defined in scope.

### Likelihood Explanation
Requires only that the attacker control (or have push/admin access to) *some* GitHub organization/App installation that is legitimately onboarded onto the same shared Shipit instance (the README documents multi-organization support), so they can obtain a validly-signed webhook. No access to the victim repository, no `ApiClient` token, and no privileged Shipit account is needed — only knowledge/guessing of a target commit SHA (often public, e.g. visible via GitHub's public commit history or CI logs) and the required status `context` name from the target's `shipit.yml`.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the payload, mirroring `Handler#stacks`, e.g. resolve `Repository.from_github_repo_name(repository_name)` first and restrict `Commit.where(sha: params.sha, stack: { repository: repo })` (or join through `stacks.commits`) before creating the status, so a webhook authenticated for organization/repo A can never write status data attributed to a commit belonging to repository B.

### Proof of Concept
1. Attacker's org `evil-org` has its own GitHub App installed and registered in Shipit with its own `webhook_secret` (legitimate multi-org onboarding).
2. Attacker learns/guesses the SHA of a commit belonging to `victim-org/victim-repo`, a stack requiring CI context `ci/tests` before deploy (`ci.require: [ci/tests]`).
3. Attacker sends a `status` webhook, signed with `evil-org`'s own valid `webhook_secret`, with body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": {"full_name": "evil-org/evil-repo", "owner": {"login": "evil-org"}}
}
```
4. `WebhooksController#verify_signature` succeeds (signed correctly for `evil-org`) [3](#0-2) .
5. `StatusHandler#process` finds the commit by `sha` globally and creates a "success" status on it, regardless of the payload's `repository` field [7](#0-6) .
6. `victim-org/victim-repo`'s required `ci/tests` status now shows green, allowing an unauthorized deploy or merge to proceed on the victim's stack.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",

        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

    end
