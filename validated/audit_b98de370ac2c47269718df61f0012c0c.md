### Title
Unfiltered `Shipit.env` secrets leak into PR-visible review-check output via `Command::NotFound`/`Denied` messages - ([File: lib/shipit/command.rb], [File: app/models/shipit/ephemeral_commit_checks.rb])

### Summary
`EphemeralCommitChecks#run` builds review-check commands with the *entire, unfiltered* `Shipit.env` hash as `env:`, unlike deploy/rollback commands which pass env through `DeploySpec#filter_deploy_envs`/`filter_rollback_envs`. Because `Command#start` constructs its `Errno::ENOENT`/`Errno::EACCES` error message from `interpolated_arguments` (post environment-variable interpolation), a PR author who controls `shipit.yml`'s `review.checks` list can reference any `$ENV_VAR_NAME` that exists in `Shipit.env`, causing the interpolated (and therefore secret-bearing) string to appear verbatim in the exception message, which `EphemeralCommitChecks#capture` writes directly to attacker-visible check output.

### Finding Description
The claimed binding is: `content of exception messages surfaced in task output` == `content free of environment-variable values interpolated into the command line`. This binding is broken.

Path:
1. `EphemeralCommitChecks#run` reads `deploy_spec.review_checks` from the fork's own `shipit.yml` (attacker-controlled, since `DeploySpec::FileSystem` loads it from the checked-out PR commit) and builds each command with `Command.new(c, env: Shipit.env, chdir:)` — the raw, un-permitted `Shipit.env`: [1](#0-0) 
2. `Shipit.env` is `{'SHIPIT'=>'1'}.merge(secrets.env || {})`, i.e. the operator-configured global env, potentially containing deploy-time secrets: [2](#0-1) 
3. Contrast: deploy/rollback commands filter env through an explicit variable whitelist (`filter_deploy_envs`/`filter_rollback_envs`) before it ever reaches `Command`, but review checks do not apply any such filter: [3](#0-2) [4](#0-3) 
4. `Command#interpolate_environment_variables`/`interpolated_arguments` substitutes `$VAR` references in the attacker-supplied command string with the literal (Shellwords-escaped) value from `env`: [5](#0-4) [6](#0-5) [7](#0-6) 
5. `Command#start` rescues `Errno::ENOENT`/`Errno::EACCES` and builds the exception message directly from `interpolated_arguments`, i.e. from the secret-substituted string, not from the original unexpanded command text: [8](#0-7) 
6. `EphemeralCommitChecks#capture` rescues `Command::Error` and writes `e.message` verbatim into the check output, which is stored/exposed as check output visible to the PR author: [9](#0-8) 

Exploit: attacker submits a PR modifying their fork's `shipit.yml` to add a `review.checks` entry consisting solely of `$SOME_GUESSED_SECRET_ENV_NAME` (a single token). Since `Command.new` stores this whole string as one argument (no attacker-controlled whitespace splitting occurs before interpolation for a scalar YAML string), `interpolated_arguments.first` becomes `Shellwords.escape(secret_value)` after interpolation. If that value is not a valid executable path (near-certain for typical secret strings), `PTY.spawn` raises `Errno::ENOENT`, `Command#start` raises `NotFound` with message `"#{Shellwords.split(interpolated_arguments.first).first}: command not found"` — `Shellwords.split` correctly un-escapes the single escaped token back to the literal secret value, which then appears whole in the message. `EphemeralCommitChecks#capture` writes this message into check output, ending up in the commit's review-check status/output surfaced to the PR author.

None of the listed guards intercept this: `verify_signature`/webhook checks only gate that a PR event is genuine, not what `shipit.yml` inside it contains; `DeploySpec`'s `deploy_variables`/`rollback_variables` permit-lists are simply never invoked for `review_checks`; `EnvironmentVariables#permit` exists but `build_commands` for review checks never calls it — it passes `Shipit.env` straight into `Command.new`.

### Impact Explanation
An unprivileged PR author (no Shipit session, no API token) can trigger review checks on their own fork/PR and, by referencing arbitrary/guessed environment variable names in a `review.checks` command, cause the literal value of any variable configured in `Shipit.env` (`secrets.env`, operator-configured, potentially deploy tokens, API keys, database credentials, etc.) to be echoed into the check output attached to their own PR's commit. This is a direct credential-exfiltration path from the deploy host to an untrusted party, matching the "Critical – exfiltration of deploy-time secrets" category. The blast radius is scoped to whatever variables are set in the shared `Shipit.env` (global, not per-stack scoped, unlike deploy variables), so a single compromised value can affect every stack that relies on it.

### Likelihood Explanation
Preconditions: the target Shipit instance must run `EphemeralCommitChecks`/review checks against externally-triggered PR commits with a `shipit.yml` that includes a `review.checks` entry (feature must be enabled and used by the operator), and `Shipit.env`/`secrets.env` must actually contain secret-like values. Attacker cost is low — a public PR with a modified `shipit.yml` and knowledge/guessing of an env-var name is sufficient; the attacker does not need to know the value, only its name, since the interpolation+error path leaks the value. This is fully repeatable and requires no privileged Shipit role.

### Recommendation
Filter/whitelist the environment passed to review-check (and dependency-step) commands the same way deploy/rollback commands are filtered (e.g., via an explicit `review`/`checks` variable whitelist and `EnvironmentVariables#permit`), and/or redact interpolated values from `NotFound`/`Denied`/exception messages in `Command#start` (build the error message from the original, un-interpolated argument rather than `interpolated_arguments`).

### Proof of Concept
```ruby
# test/unit/command_test.rb (conceptual, no live GitHub required)
test "NotFound leaks interpolated environment variable secret" do
  secret = 'super-secret-token-value'
  command = Command.new('$LEAKED_SECRET', env: { 'LEAKED_SECRET' => secret }, chdir: '.')
  error = assert_raises(Command::NotFound) { command.start }
  assert_includes error.message, secret
end

# test/models/commit_checks_test.rb (conceptual)
test "#run writes unfiltered Shipit.env secret into review check output on command failure" do
  Shipit.stubs(:env).returns('SHIPIT' => '1', 'LEAKED_SECRET' => 'super-secret-token-value')
  StackCommands.any_instance.expects(:with_temporary_working_directory).yields(Pathname.new(Dir.tmpdir))
  DeploySpec::FileSystem.any_instance.expects(:dependencies_steps).returns([])
  DeploySpec::FileSystem.any_instance.expects(:review_checks).returns(['$LEAKED_SECRET'])

  @checks.run

  assert_equal 'failed', @checks.status
  assert_includes @checks.output, 'super-secret-token-value'
end
```
Both assertions show the secret value (right-hand side of the claimed binding) appearing in attacker-visible output/exception message, proving the binding is false.
