### Title
Webhook signature verification is keyed by `repository.owner.login`, but `PushHandler` resolves the mutated `Stack` via `repository.full_name` — allowing the signing org to diverge from the mutated org's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` looks up the HMAC secret using `repository_owner`, which reads only `payload['repository']['owner']['login']`, while `Handler#stacks` (used by `PushHandler#process`) resolves the target `Repository`/`Stack` using the independent field `payload['repository']['full_name']`. Because these two fields are never cross-checked for consistency, an attacker who owns any org configured in Shipit's multi-org setup can sign a payload with their own secret while pointing `full_name` at an unrelated victim repository, causing `sync_github` to run against the victim's `Stack` rows.

### Finding Description
The broken binding the code is supposed to enforce is:
`organization_whose_secret_verified_signature == organization_owning_the_repository_whose_Stack_is_mutated`

In practice:
- `repository_owner` is computed solely from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and used only to select which HMAC secret to check against: [1](#0-0) [2](#0-1) 
- The `full_name` field of the same JSON body is never compared to `owner.login`; once `verify_signature` passes, the raw, attacker-supplied `params` object is handed unmodified to every registered handler: [3](#0-2) 
- `PushHandler#process` finds stacks by branch, scoped through `Handler#stacks`, which resolves the `Repository` using `payload.dig('repository', 'full_name')` — an entirely separate JSON field from the one used for signature verification: [4](#0-3) [5](#0-4) 

Root cause: nothing enforces that the org segment of `repository.full_name` matches `repository.owner.login`. An attacker who owns `attacker/attacker-repo` in a Shipit deployment configured with multi-org webhook secrets (`Shipit.github(organization: ...)`) can send:

```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker" }
  }
}
```
signed with `attacker`'s own webhook secret (which they legitimately possess as the owner of that GitHub org/repo). `Shipit.github(organization: 'attacker')` verifies the signature successfully because the secret matches the org the attacker actually owns. `repository_owner` never appears again after signature verification, so the divergent `full_name` flows straight into `PushHandler#stacks`, which loads the real `victim-org/victim-repo` `Repository` and calls `sync_github(expected_head_sha: params.after)` on its `Stack` rows — with an attacker-controlled `after` SHA.

None of the existing guards intercept this: `verify_signature` only checks the HMAC against the secret it picked using `owner.login`, it does not re-validate `full_name`; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema for `PushHandler` only requires `ref` and `after`, not that `repository.full_name`'s owner matches `repository.owner.login`; there is no `Repository` or `Stack` validation performed here that ties them back to the signing organization.

### Impact Explanation
A successful request causes `Stack#sync_github` to run for a `Stack` belonging to a repository (`victim-org/victim-repo`) the attacker does not own and never authenticated for, using an attacker-supplied `after` SHA — i.e., a payload from one repository/org mutating another repository's `Stack`/commit state without that org's webhook secret ever being checked against the actual target. This matches the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any repository/organization configured in the Shipit instance as long as the attacker controls at least one org with a valid webhook secret registered in the same multi-org Shipit deployment; blast radius scales with the number of tenants sharing one Shipit host.

### Likelihood Explanation
Preconditions: Shipit must be running in the "multi-org" mode implied by `Shipit.github(organization: repository_owner)` (i.e., per-organization webhook secrets), and the attacker must legitimately own/administer at least one org/repo onboarded to that same Shipit instance (satisfied by the stated attacker capability of owning `attacker/attacker-repo`). No Shipit session, API token, or victim secret is required — only the attacker's own legitimately-issued webhook secret for their own org. Given that, forging the request is trivial: craft an HTTP POST with a mismatched `full_name`/`owner.login`, sign with the attacker's own secret, and send it to `/webhooks`. This is fully repeatable and requires no timing or race conditions.

### Recommendation
Enforce provenance by deriving the signing organization and the mutation target from the same trusted field, or by validating that they match. Concretely: compute `repository_owner` as the owner segment parsed out of `repository.full_name` itself (not the independent `owner.login` field), or explicitly assert `payload.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first` in `verify_signature` and reject (422) on mismatch before dispatching to handlers.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "signature verified for attacker org does not authorize mutating victim stack" do
  attacker_repo = shipit_repositories(:shipit) # any Repository the fixture owns, standing in for attacker's own repo
  victim_stack = stacks(:shipit) # belongs to a different repository, e.g. 'victim-org/victim-repo'
  victim_repo = victim_stack.repository

  # Sanity check the binding under test:
  refute_equal 'attacker', victim_repo.owner, "victim repo must not be owned by attacker"

  fake_github_app = mock
  fake_github_app.stubs(:verify_webhook_signature).returns(true)
  Shipit.stubs(:github).with(organization: 'attacker').returns(fake_github_app)

  payload = {
    ref: "refs/heads/#{victim_stack.branch}",
    after: 'deadbeef',
    repository: {
      full_name: "#{victim_repo.owner}/#{victim_repo.name}", # points at victim
      owner: { login: 'attacker' } # signed with attacker's own secret
    }
  }.to_json

  Shipit::Stack.any_instance.expects(:sync_github).never

  post :create, body: payload, params: { as: :json },
       headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => 'sha1=whatever' }

  # Today this assertion FAILS: PushHandler#stacks resolves victim_repo via
  # payload['repository']['full_name'] regardless of the 'attacker' owner.login
  # used only for HMAC secret lookup, so sync_github IS invoked on victim_stack.
end
```
This demonstrates that `repository_owner` (`owner.login`) and the org actually mutated (`full_name`) are independent fields with no cross-validation, breaking webhook provenance: [2](#0-1) [4](#0-3)
