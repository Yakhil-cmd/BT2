### Title
`Api::CCMenuController#stack` bypasses the ApiClient's stack scope, letting a single-stack token read any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` supports being scoped to a single stack via its `belongs_to :stack, optional: true` / `stack_id` column, and `Api::BaseController#stacks` enforces that scope for every other API endpoint. `Api::CCMenuController` overrides the `stack` lookup to bypass this scoping entirely, so a token that is only supposed to authorize `read:stack` on one stack can be used to read the CCMenu status of *any* stack in the installation.

### Finding Description
Every other controller under `app/controllers/shipit/api/` resolves the target stack through the instance method `stacks`, which restricts the query to the client's own stack when the client is scoped:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`require_permission!` only checks that the client has the named permission string (`read:stack`, etc.) in its `permissions` array — it never checks *which* stack the permission applies to:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [2](#0-1) 

So the *only* place the per-stack restriction (`ApiClient#stack_id`) is actually enforced is inside `stacks`/`stack` in `BaseController`. `Api::CCMenuController` redefines `stack` to skip that scoping and query all stacks directly:
```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
``` [3](#0-2) 

The invariant that should hold is: `stack the token authorises == stack the token can touch`. Before an attacker's request: a client with `stack_id = A` and `permissions = ['read:stack']` can only read stack A through the scoped `stacks` relation used by every other endpoint. After a request to `GET /api/stacks/:owner/:name/:env/ccmenu?token=<A's token>` with `stack_id` pointing at stack B, `CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` (an unscoped class-level lookup), so the equality is broken: the token authorized for A now touches B.

### Impact Explanation
This is a High-severity authorization bypass matching the required "escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state" category: it grants unauthorized read of stack state to a party holding a token that was deliberately scoped to a single stack (e.g. issued to a third-party integration or CI system for one specific stack). The disclosed data (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state, etc., rendered via `shipit/ccmenu/project`) reveals deploy status and identifying details for stacks the token holder was never authorized to see, across the whole Shipit installation.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` records (the `stack_id` column and the scoping code in `BaseController#stacks` exist specifically to support this use case) and exposes the CCMenu endpoint, which is an unauthenticated-adjacent, token-only, read-only integration point commonly embedded in third-party CI dashboards. No special privilege beyond possessing a valid (but narrowly scoped) `ApiClient` token/basic-auth credential for the CCMenu feature is required to enumerate other stacks.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation instead of the raw `Stack` class method, mirroring `BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
More generally, audit all controllers that override `stack`/`stacks` in the `Api` namespace to ensure none of them use an unscoped `Stack.from_param!`/`Stack.find` that circumvents `ApiClient#stack_id` scoping, and consider moving the scope check into `require_permission!`/`check_permissions!` itself so scoping cannot be silently dropped by a subclass.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to Stack A only, with `permissions: ['read:stack']` and `stack_id: A.id` (the model supports this via `belongs_to :stack, optional: true`) [4](#0-3) .
2. Confirm the token cannot see Stack B through a normally-scoped endpoint, e.g. `GET /api/stacks` — it only returns Stack A, as covered by the existing test `"an api client scoped to a stack will only see that one stack"` [5](#0-4) .
3. Using the same token/basic-auth credentials, request `GET /api/stacks/:B_owner/:B_name/:B_env/ccmenu` (routed to `Api::CCMenuController#show`).
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the request succeeds and returns Stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, etc.), even though the token was never authorized for Stack B.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack

      end
