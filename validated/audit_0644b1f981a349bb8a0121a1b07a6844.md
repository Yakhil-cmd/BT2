## Title
Webhook signature authenticates the sending organization but never binds it to the repository the payload mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC against using `repository_owner`, a value taken straight from the JSON payload (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, the entire raw payload — including `repository.full_name`, which is used by every event handler to look up the `Repository`/`Stack` to mutate — is trusted with no further validation that the repository actually belongs to the authenticated organization.

### Finding Description
In a multi-tenant Shipit deployment (as evidenced by `test/dummy/config/secrets_double_github_app.yml`, which configures independent `webhook_secret`s per organization, e.g. `OrgOne`/`OrgTwo`), the webhook signature check is org-scoped: [1](#0-0) 

`repository_owner` is derived purely from attacker-controlled JSON fields: [2](#0-1) 

`Shipit.github(organization:)` resolves the `GitHubApp`/secret for that specific org and nothing else: [3](#0-2) 

Crucially, once `verify_signature` succeeds, `params` (the full parsed payload) is dispatched unmodified to every handler: [4](#0-3) 

Handlers resolve the target `Repository`/`Stack` using `repository.full_name`, a completely separate field from the one used to select the signing secret: [5](#0-4) [6](#0-5) 

Nothing checks that `repository.owner.login` (used to select and verify against organization A's secret) matches the owner segment of `repository.full_name` (used to determine which repository/stack the event mutates). An organization admin who legitimately controls a webhook secret for their own tenant (organization A) can therefore submit a request whose `X-Hub-Signature` is valid for organization A, but whose JSON body sets `repository.full_name` to `"orgB/some-repo"` — a repository belonging to an entirely different tenant, organization B, configured in the same Shipit installation. Handlers such as `PushHandler`, `StatusHandler`, and the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) will then act on organization B's stacks: enqueuing `GithubSyncJob` to resync a branch, writing commit `Status` rows, or provisioning/archiving Review Stacks — for a repository the caller never authenticated for.

This mirrors the root cause of the referenced ZETA report exactly: an authorization check is performed on one field (organization identity, via a sentinel-secret lookup), while the *action actually taken* is keyed off a different, unchecked field (`repository.full_name`) from the same signed envelope. The signature guarantees "this body was sent by a holder of organization A's secret," but the code silently generalizes that to "and everything inside this body, including which repository/organization it claims to target, can be trusted," which is not implied.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written." A tenant organization boundary is a real security boundary in a multi-org Shipit install — one customer's webhook credentials should never allow writing to another customer's stack state. Concretely this permits:
- Forcing `GithubSyncJob` resyncs and fabricated commit `Status` records against another organization's stack (`StatusHandler`, `PushHandler`), corrupting CI/deploy gating decisions.
- Creating, labeling, archiving/unarchiving Review Stacks for another organization's repository (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`), which can influence provisioning/deprovisioning and, depending on the host app's `ProvisioningHandler`, trigger infrastructure changes.

This is a cross-repository/cross-tenant write achieved without ever needing organization B's own credentials — qualifying as "cross-repository writes" under the stated Critical impact category.

### Likelihood Explanation
Requires: (1) a Shipit installation configured for more than one GitHub organization (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml` and the `github_organizations`/`github_app_config` machinery in `lib/shipit.rb`), and (2) the attacker to be a legitimate holder of *their own* organization's webhook secret (not a stolen one). No access to the victim organization's repository, secret, or Shipit session/API token is required, satisfying the "unprivileged attacker" constraint. The payload fields involved (`repository.owner.login` vs `repository.full_name`) are both attacker-supplied and mutually inconsistent by design of the exploit, and no code path anywhere cross-checks them.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after it, before dispatch), derive the organization used to look up the repository/stack from the same value that was authenticated (`repository_owner`), and reject (or ignore) events whose `repository.full_name` owner segment does not match `repository_owner`/`organization.login`. Equivalently, `Handler#repository_name`/`Handler#stacks` should be scoped by the authenticated organization rather than trusting the raw `repository.full_name` field independently.

### Proof of Concept
1. Configure Shipit with two tenants, `OrgOne` (attacker-controlled) and `OrgTwo` (victim), each with its own `webhook_secret`, per `test/dummy/config/secrets_double_github_app.yml`.
2. As an OrgOne admin, compute a valid `X-Hub-Signature` for OrgOne's `webhook_secret` over a crafted JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
3. POST this body with header `X-Github-Event: push` and the correctly-computed `X-Hub-Signature` to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"OrgOne"`, verifies successfully against OrgOne's secret.
5. `PushHandler#stacks` looks up `Repository.from_github_repo_name("OrgTwo/victim-repo")` and enqueues `GithubSyncJob` for OrgTwo's stack, even though the request was never authenticated by OrgTwo.
