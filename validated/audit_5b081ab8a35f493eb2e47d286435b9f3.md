## Analog Found

### Title
Refunds to a non-existent `beneficiary_id` on `DeleteAccountAction` are irrecoverably burned instead of returned - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
The reported vulnerability is about a "recipient" value (an NFT royalty/fee address) that is only checked for the *trivially valid* case (non-zero payout amount) but never checked for whether the recipient itself is a valid/usable destination, causing funds to be irrecoverably burned at `address(0)`. The nearcore analog is `DeleteAccountAction::beneficiary_id`: it is validated only for syntactic correctness (valid `AccountId` string), never for whether the account actually exists. If it doesn't exist, the balance-refund receipt to it fails and the entire remaining account balance is burned.

### Finding Description
When an account is deleted via `Action::DeleteAccount(DeleteAccountAction { beneficiary_id })`, the runtime unconditionally creates a refund receipt carrying the deleted account's full balance to `beneficiary_id`: [1](#0-0) 

The only pre-execution validation applied to `beneficiary_id` is a syntax check via `AccountId::validate`, not an existence check: [2](#0-1) [3](#0-2) 

This is documented explicitly in the spec — the only validation error for `beneficiary_id` is `InvalidAccountId` for malformed IDs, with no existence requirement: [4](#0-3) 

The resulting balance-refund receipt is a system-generated refund receipt (`predecessor_id == "system"`). When it is later applied to the receiver, `apply_action` computes `is_refund` and deliberately disables implicit-account creation for refunds: [5](#0-4) 

If `beneficiary_id` does not correspond to an existing account (and is not eligible for implicit creation, which refunds never are), the transfer action fails with `AccountDoesNotExist`, matching the documented and tested behavior for transfers to non-existent accounts: [6](#0-5) 

Per the runtime's own refund spec, a failed refund is burned, not returned to anyone: [7](#0-6) 

This is implemented directly in `apply_action_receipt`: for refund receipts (`predecessor_id().is_system()`), if the result is an error, the deposit is added to `stats.balance.other_burnt_amount` rather than returned anywhere: [8](#0-7) 

### Impact Explanation
Concretely: a user (or a contract acting on the user's behalf via `promise_batch_action_delete_account`) submits a `DeleteAccountAction` naming a `beneficiary_id` that is syntactically valid but does not exist on-chain (e.g., a typo, a not-yet-created sub-account, or an account that was itself deleted between transaction construction and execution). The account's *entire remaining NEAR balance* is transferred into a refund receipt that fails and is burned — a real, permanent loss of token value with no path to recovery, mirroring the "ETH sent to address 0 is burned" root cause in the reported bug (a recipient that "looks valid" but is unusable, silently swallowing funds instead of falling back to a safe default such as returning to the predecessor/signer).

### Likelihood Explanation
This is reachable from an ordinary, unprivileged user transaction or from any contract that calls `promise_batch_action_delete_account`/`promise_batch_action_delete_account` on wasm — no validator or node-privilege is required: [9](#0-8) 
The only guard is the account-id syntax check; supplying a non-existent (but syntactically valid) `beneficiary_id` is trivial and can also happen accidentally (race between transaction construction and a beneficiary account being deleted before the delete-account receipt executes), making this both attacker-triggerable and accident-prone.

### Recommendation
Before creating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or is treated as implicit-account-eligible), or change the refund/transfer path so that a failed refund to a non-existent beneficiary falls back to the receipt's predecessor/signer instead of being burned — analogous to the "treat as if no recipient was returned so other priorities take over" recommendation from the referenced report.

### Proof of Concept
1. Create account `victim.near` with balance `B`.
2. Submit `SignedTransaction` from `victim.near` with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "doesnotexist.near" })` (a syntactically valid, but never-created, account).
3. `action_delete_account` pushes `Receipt::new_balance_refund("doesnotexist.near", B)`. [1](#0-0) 
4. When that refund receipt executes, `check_account_existence` rejects it because `implicit_account_creation_eligible` is `false` for refunds, yielding `ActionErrorKind::AccountDoesNotExist`. [5](#0-4) 
5. Because `receipt.predecessor_id().is_system()` and `result.result.is_err()`, the full amount `B` is added to `stats.balance.other_burnt_amount` — permanently burned. [8](#0-7)

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
