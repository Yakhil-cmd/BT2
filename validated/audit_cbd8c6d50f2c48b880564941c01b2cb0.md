### Title
Webhook signature is verified against the organization named in the payload, but handlers act on repository/commit fields from the same untrusted payload with no cross-check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a request against by reading `repository_owner` straight out of the *unverified* JSON body [1](#0-0) . Once the signature check passes for that organization, the raw, attacker-supplied `params` are handed unmodified to the event handlers [2](#0-1) , which independently pick the target `Stack`/`Commit` from other fields in the same body (`repository.full_name`, `sha`) with no verification that those fields belong to the organization whose key actually signed the request. This breaks the binding "organization that authenticated == repository/commit that is written."

### Finding Description
`verify_signature` computes:
```
repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
``` [3](#0-2) 

This only proves the request was signed with *some organization's* `webhook_secret` - the one named by `repository_owner`. Shipit explicitly supports multiple, independently configured GitHub Apps/organizations, each with its own `webhook_secret` [4](#0-3) . Any tenant organization onboarded this way legitimately possesses its own `webhook_secret` and can produce a validly-signed request.

After verification, `create` dispatches the same raw body to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [2](#0-1) . The handlers never re-check that the repository/commit they act on belongs to the organization that produced the valid signature:

- `PushHandler` resolves the target stacks purely from `payload.dig('repository', 'full_name')` via `Handler#stacks`/`Handler#repository_name` [5](#0-4)  and then calls `stack.sync_github(expected_head_sha: params.after)` [6](#0-5) .
- `StatusHandler` is worse: it does a **global** lookup with no repository scoping at all - `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [7](#0-6) . Any commit sha anywhere in the Shipit instance can have a status attached by whoever's signature happened to pass, regardless of which organization/repository actually owns that commit.

Since `repository_owner`, `repository.full_name`, and `sha` all come from the same attacker-controlled JSON body, nothing stops Org A (a legitimate tenant that knows its own `webhook_secret`) from signing a request as itself while filling `repository.full_name`/`sha` with values belonging to Org B's stack.

### Impact Explanation
A tenant organization that is legitimately onboarded to a multi-organization Shipit instance (each org has its own `webhook_secret`, per `docs/setup.md`) can forge webhook events that are correctly signed for itself but target another tenant's repository or commits. Via `StatusHandler`, this allows injecting a fabricated `success` commit status onto any commit anywhere in the instance [7](#0-6) , which can satisfy deploy-safety "required status" gates that Shipit uses to decide whether a commit is deployable - resulting in an unauthorized deploy of another organization's stack. Via `PushHandler`, an attacker can force sync/refresh cycles against arbitrary stacks it doesn't own [6](#0-5) . This crosses a repository/tenant boundary that the signature check was supposed to enforce, matching the accepted "unauthorized deploy" impact class.

### Likelihood Explanation
Requires being one of the (possibly many) legitimately configured GitHub organizations/GitHub Apps on a multi-tenant Shipit deployment - a scenario the engine explicitly documents and supports [4](#0-3) . No repository write access, session, or `ApiClient` token to the *victim* organization is required; only knowledge of the attacker's own already-provisioned `webhook_secret`, which is not privileged with respect to other tenants.

### Recommendation
After `verify_signature` passes, bind the verified organization identity to the rest of request processing: re-derive/require that every repository or organization reference used by a handler (`repository.full_name`, `organization.login`, and any commit lookup in `StatusHandler`) belongs to the same `repository_owner`/organization that produced the valid signature, rejecting the event otherwise. In particular, scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup by the verified repository/stack rather than performing a global sha lookup.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `github.webhook_secret` (per `docs/setup.md` multi-app config).
2. Org A is a legitimate tenant and therefore knows its own `webhook_secret_a`.
3. Org A crafts a `status` webhook payload:
   ```json
   {
     "sha": "<sha of a commit belonging to org-b's stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
   }
   ```
4. Org A signs the raw body with `webhook_secret_a` and sends `POST /webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
5. `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, fetches `Shipit.github(organization: "org-a")`, and successfully verifies the signature [3](#0-2) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the matching commit under org-b's stack, and calls `create_status_from_github!`, recording a forged "success" status on org-b's commit [7](#0-6) , potentially unblocking a deploy gate that depends on that status.

Note: I was unable to fully verify, within available tool budget, whether the deploy-safety pipeline strictly gates deploys on this specific `Status` record (vs. `check_suite`/checks only) - confirming the exact deploy-blocking logic (`Stack#deployable?` or similar) would require reading `app/models/shipit/stack.rb` and `app/models/shipit/commit.rb`, which I could not complete before the iteration limit.
