### Title
Weak, delimiter-less contract hash allows field-boundary collision in arbiter escrow contracts - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js`'s `getHashSrc()` computes the identifying hash of a peer-to-peer arbiter escrow contract by concatenating its title, text, dates, names, arbiter/party addresses, amount and asset. For contracts whose `creation_date` is not yet past `exports.NEW_HASH_DATE` ('2026-11-01') — i.e. essentially **all contracts created today, since today's date (2026-09-15) is before that cutoff** — the fields are joined with an **empty separator (`""`)** instead of the dedicated `exports.DELIMITER = "[|#|]"` used in the new scheme: [1](#0-0) 

### Finding Description
`getHash()` hashes the output of `getHashSrc()`: [2](#0-1) 

Because the legacy branch joins `[title, text, creation_date, payer_name, arbiter_address, payee_name, amount, asset]` with no separator at all, the concatenation is ambiguous: content can be shifted across adjacent free-text fields (`title`/`text`, `text`/`creation_date`, `payer_name` boundaries, etc.) so that two semantically different contracts (different title/text split, or a party name that "borrows" characters from the neighboring field) produce byte-identical source strings and therefore identical SHA-256 hashes. This is the same bug class as the CRLF-injection issue in the report: unsanitized, delimiter-free construction of a security-relevant string lets an attacker who controls one or more of the joined fields (`title`, `text`, `my_party_name`/`peer_party_name`) manipulate field boundaries to forge collisions, exactly as CRLF characters let an attacker manipulate HTTP header boundaries.

`title`, `text`, and the party names are supplied by the contract offeror — an unprivileged wallet user, i.e. exactly the "unprivileged AA/asset/contract counterparty" class in scope — and are never validated to exclude characters that would make the join reversible/unambiguous (unlike `getSourceString()` in `string_utils.js`, which explicitly guards against this exact hazard by rejecting `STRING_JOIN_CHAR` in any component precisely because naive joins are collision-prone): [3](#0-2) 

This contrasts with the "new" hash branch, which already fixes the flaw by using `exports.DELIMITER`, confirming the developers recognized the join-without-delimiter pattern as broken — but the fix is gated behind a future date, leaving the vulnerable code path live for all contracts created before 2026-11-01.

### Impact Explanation
`contract.hash` is the sole identifier used to correlate the two negotiating peers, the arbiter, and the arbstore across the entire lifecycle of the escrow:
- It is embedded as `contract_text_hash` in the on-chain `data` message when the shared address is funded/signed, and verified against the stored contract on receipt: [4](#0-3) 
- It is used to build the data-feed keys `"CONTRACT_" + contract.hash` and `"CONTRACT_DONE_" + contract.hash` that gate the disputed/undisputed release branches of the shared address's oscript definition: [5](#0-4) [6](#0-5) 
- It is sent to the arbstore as `contract_hash` together with a separately-encrypted copy of the contract text for dispute resolution: [7](#0-6) 

Because the hash can collide across different `(title, text, party_name)` combinations, a malicious counterparty (payer or payee) can present one version of the contract text to the honest peer/arbiter for signing/escrow purposes while later asserting or reconstructing a different, colliding version whose `contract.hash` is identical. Since dispute resolution, on-chain verification of the `data` message, and the in-data-feed authorization checks for fund release all key off this collidable hash rather than the full contract content, this enables a counterparty to create ambiguity about which contract terms actually apply to a signed/funded shared address — directly affecting the correctness of AA/oscript fund-release conditions tied to `CONTRACT_<hash>` and `CONTRACT_DONE_<hash>` data feeds, and undermining the arbiter's ability to unambiguously resolve which party is entitled to the escrowed funds. This can translate into unauthorized release of escrowed payment funds or a stalemate where honest nodes/peers disagree on the correct contract terms bound to a given shared address.

### Likelihood Explanation
The vulnerable path is not a corner case — it is the **default/active** code path today, since `exports.NEW_HASH_DATE` is set to a future date (`2026-11-01`) and any contract created before then falls into the delimiter-less legacy branch. Any wallet user who can initiate or accept an arbiter contract (an unprivileged action, `createAndSend`) fully controls the `title`, `text`, and party-name fields that are joined without a separator, making collision construction straightforward and requiring no special privileges, node, or hub compromise.

### Recommendation
Retire the delimiter-less legacy hashing branch immediately (or bring the cutover date `NEW_HASH_DATE` to the present) so that all contracts use the safe `exports.DELIMITER`-joined (or `getSourceString`/`getJsonSourceString`-style, length-prefixed/00-byte-guarded) source string. If backward compatibility with old, already-created contracts must be preserved, at minimum validate that `title`, `text`, and party-name fields cannot contain characters/byte sequences that make the join ambiguous, and prefer a canonical, unambiguous encoding (e.g., length-prefixing each field, as `getSourceString` does) for any newly created contract hash.

### Proof of Concept
1. Two contracts with `creation_date` before `'2026-11-01'` (true for any contract created today):
   - Contract A: `title="Payment for services"`, `text="A"`, same `creation_date`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, `asset`.
   - Contract B: `title="Payment for services"` with the trailing `"A"` moved from `text` to `title` (i.e., `title="Payment for servicesA"`, `text=""`), all other fields identical.
2. `getHashSrc()` for both, using the pre-cutoff branch `[title, text, creation_date, payer_name, arbiter_address, payee_name, amount, asset].join("")`, produces the exact same concatenated string, hence identical `sha256` hash from `getHash()`.
3. Contract A is negotiated/signed with the counterparty and funded on-chain (its `contract_text_hash` and `CONTRACT_<hash>`/`CONTRACT_DONE_<hash>` data-feed keys are derived from this shared hash). The attacker can later present Contract B (different textual terms) referencing the identical hash to the arbiter/arbstore or to justify a differing on-chain data-feed claim, since nothing besides this collidable hash binds the specific contract content to the escrow's release conditions.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
