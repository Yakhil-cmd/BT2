### Title
Pool creator fee collection permanently DoS'd if the creator's fixed associated token account becomes frozen/blacklisted - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` always transfer accrued creator fees to a token account whose address is deterministically fixed to `associated_token::authority = creator`. Unlike `withdraw`, which lets the caller supply an arbitrary destination token account, there is no way to redirect the payout to a different account. If that specific associated token account becomes unable to receive tokens (e.g. a Token-2022 mint with a freeze authority freezes it, or a `DefaultAccountState = Frozen` extension), every future call to either instruction reverts permanently, freezing the creator's accrued fees in the vault indefinitely.

### Finding Description
Both instructions load `pool_state.creator_fees_token_0/1` and unconditionally attempt `transfer_from_pool_vault_to_user` into `creator_token_0`/`creator_token_1`: [1](#0-0) [2](#0-1) 

The same fixed-ATA pattern applies to the permissionless variant, where the recipient's ATA address is derived from `pool_state.pool_creator` and cannot be substituted by the caller: [3](#0-2) [4](#0-3) 

Because the underlying transfer uses `token_2022::transfer_checked`, a frozen destination account causes the CPI (and thus the whole instruction) to revert: [5](#0-4) 

`pool_state.creator_fees_token_0`/`creator_fees_token_1` are only zeroed out after a successful transfer, so as long as the transfer keeps failing, the fees remain accrued but unclaimable.

By contrast, `withdraw` lets the LP designate any token account of matching mint they control (no `associated_token::authority` constraint tying it to a single deterministic address), so an LP who gets their default ATA frozen can still supply an alternate account: [6](#0-5) 

This program supports arbitrary Token-2022 mints for pool tokens without restricting risky mint extensions (no allow-list of extensions is enforced before pool creation), so a pool can legitimately be created on a mint whose freeze authority (or a malicious/compromised authority) can freeze the creator's specific ATA, or that mint could even be configured with `DefaultAccountState = Frozen`, permanently blocking payouts to the creator's canonical ATA.

### Impact Explanation
Once the creator's associated token account for `vault_0_mint`/`vault_1_mint` is frozen, `collect_creator_fee` and `collect_creator_fee_permissionless` become permanently uncallable for that pool: every attempt reverts on the `transfer_checked` CPI to the frozen account, and there is no fallback destination. The creator fees sitting in `pool_state.creator_fees_token_0/1` remain locked inside the pool's vault indefinitely — a permanent freezing of the pool creator's funds, one of the explicitly in-scope actors (pool creator).

### Likelihood Explanation
This requires only that the creator's associated token account become frozen, which is realistic for tokens with a freeze authority (common on Token-2022 mints, e.g. stablecoin-style tokens) or a `DefaultAccountState = Frozen` extension. Since the pool program does not restrict which Token-2022 extensions are permitted on pool mints, this is directly reachable by any pool created with such a mint, without any privileged action beyond the normal token-freezing capability of the mint's freeze authority.

### Recommendation
Avoid hard-coding the payout destination to a single deterministic ATA. Either (a) allow the caller to supply any token account owned by `pool_creator` (similar to `withdraw`'s `token_0_account`/`token_1_account`, validated only by mint and ownership) instead of constraining via `associated_token::authority`, or (b) implement a pull-based claim/accounting mechanism so that a temporarily blocked recipient does not permanently lock the accrued fees, and consider restricting supported Token-2022 mint extensions to exclude freeze-capable/default-frozen configurations for pool tokens.

### Proof of Concept
1. Create a pool via `initialize`/`initialize_with_permission` using a Token-2022 mint (`vault_0_mint`) that has a freeze authority (or `DefaultAccountState = Frozen`).
2. Perform swaps so that `pool_state.creator_fees_token_0` accrues via the normal fee split.
3. The mint's freeze authority freezes the `pool_creator`'s canonical associated token account for `vault_0_mint` (the same account address that `collect_creator_fee`/`collect_creator_fee_permissionless` are constrained to use via `associated_token::authority = creator`).
4. Call `collect_creator_fee` (or `collect_creator_fee_permissionless`): the `transfer_from_pool_vault_to_user` CPI to the frozen `creator_token_0` account fails, reverting the whole instruction.
5. Because the accounts struct hard-codes the destination ATA and offers no alternate-account parameter, every subsequent call fails identically — the accrued `creator_fees_token_0` remains stuck in `token_0_vault` with no way for the creator to ever claim it.

pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
