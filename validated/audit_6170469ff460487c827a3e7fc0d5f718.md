### Title
Cross-organization CI status forgery leads to unauthorized deploy - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate a delivery against using a field taken directly from the still-unverified request body (`repository.owner.login` / `organization.login`), then treats the whole payload as trusted once that single organization's HMAC matches. [1](#0-0)  Downstream, `Shipit::Webhooks::Handlers::StatusHandler#process` uses `params.sha` to look up commits with **no repository or organization scoping whatsoever**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1)  The organization whose secret authenticated the request is never checked against the stack/repository that the commit status is written to.

### Finding Description
The binding that should hold is: `organization whose webhook_secret validated the signature == organization/repository whose commit state is mutated`. That binding is broken here:

- Signature verification: `Shipit.github(organization: repository_owner)` picks the `GithubApp`/`webhook_secret` purely from `params.dig('repository','owner','login')` (or `organization.login`), both attacker-supplied fields inside the very payload being verified. [3](#0-2) [4](#0-3) 
- The `verify_webhook_signature` implementation performs a straightforward HMAC-SHA1 check of the whole raw body against that org's `webhook_secret`. [5](#0-4) 
- If an attacker legitimately administers/owns **any one** organization that is configured in this multi-tenant Shipit instance (`config/secrets.yml` supports multiple `github:` orgs each with its own `webhook_secret`), [6](#0-5)  they know that org's `webhook_secret` (they provisioned the GitHub App / secret for their own org). They can therefore craft an arbitrary raw JSON body, correctly HMAC-sign it with their own org's secret, set `X-Github-Event: status`, and set `sha` to any commit SHA and `state`/`context` to any value they like.
- `StatusHandler#process` never checks `repository_name`, `repository`, or any org/tenant scoping before writing the forged status — it queries `Commit.where(sha: params.sha)` across the **entire** Shipit installation and calls `create_status_from_github!` on every match. [2](#0-1)  This is unlike other handlers (e.g. `PushHandler`, pull-request handlers) which correctly resolve `repository_name`/`repository` from `payload.dig('repository','full_name')` before scoping any writes. [7](#0-6) [8](#0-7) 
- `Commit#create_status_from_github!` records the forged status, and `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, where `success?` is driven by `Status::Group`/`Status::Common#success?` checking `state == 'success'` for the (attacker-chosen) `context`. [9](#0-8) [10](#0-9)  Because `context` is attacker-controlled (`accepts :context, String`), [11](#0-10)  the attacker can match the exact `required_statuses`/`blocking_statuses` context names of a victim stack, causing `Status::Group#select_significant_status`/`required_statuses` checks to see a satisfied requirement. [12](#0-11) 
- Whenever a commit's status transitions to success, `Commit#add_status` triggers `stack.schedule_merges` and, on commit creation/update, `schedule_continuous_delivery` checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob`. [13](#0-12) [14](#0-13) 

Net effect: an attacker who legitimately controls webhook secrets for Organization A can forge a `status` event that fabricates a passing CI check on an arbitrary commit belonging to an unrelated Organization B's stack, bypassing that stack's actual CI requirements and enabling deploy/merge-queue eligibility on a repository they have no privileges over.

### Impact Explanation
This breaks the "unauthorized deploy" boundary explicitly called out as Critical impact. An attacker with only their own tenant's webhook secret (no `ApiClient` token, no GitHub write access to the victim repo, no Shipit session) can flip an arbitrary victim commit's CI/status state to "success" for whatever `context` the victim stack requires, which is consumed by `deployable?`, `schedule_continuous_delivery`, and merge-queue revalidation (`schedule_merges`) — enabling continuous deployment or merge-queue merges of commits that never actually passed real CI, i.e. an unauthorized deploy/merge across organizational/tenant boundaries.

### Likelihood Explanation
Requires only that the target Shipit deployment configures more than one GitHub organization (a documented, supported setup, per `config/secrets.development.shopify.yml`) and that the attacker is a legitimate administrator/webhook-secret-holder for one of those organizations. No credentials belonging to the victim organization are needed, and no interaction from the victim is required — the attacker directly POSTs to `/webhooks` with a correctly-signed, forged body. This is a straightforward, deterministic attack path once multi-tenancy is in use.

### Recommendation
- In `StatusHandler` (and any other handler that resolves records purely by cross-tenant-unscoped fields like `sha`), scope the lookup by the repository/organization that the verified signature actually authenticated for, e.g. restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository` belongs to the authenticated `repository_owner`/organization.
- In `WebhooksController#verify_signature`, after determining which org's secret validated the signature, re-validate that `repository.full_name`'s owner matches that same organization before dispatching to handlers, and reject (422) on mismatch.
- Consider signing/verifying per-repository rather than per-organization-derived-from-payload fields, or cryptographically binding the `repository` fields used by handlers to the value used for secret selection.

### Proof of Concept
1. Deploy Shipit configured with two GitHub organizations, `orgA` (attacker-administered, webhook secret known to attacker) and `orgB` (victim, has a stack `orgB/app` requiring CI context `ci/tests`).
2. Attacker crafts a JSON body:
```json
{
  "sha": "<victim-commit-sha-in-orgB-app>",
  "state": "success",
  "context": "ci/tests",
  "target_url": "https://example.com",
  "created_at": "2026-09-01T00:00:00Z"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` (they know `orgA`'s secret) and sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<computed>
<raw_body>
```
4. `verify_signature` selects `Shipit.github(organization: repository_owner)` — since the body has no `repository`/`organization` object, `repository_owner` is `nil`, but if attacker includes `"organization": {"login": "orgA"}` in the body (allowed since `repository_owner` falls back to it), verification succeeds using `orgA`'s secret.
5. `StatusHandler#process` finds the victim commit by `sha` (global lookup, no org scoping) and calls `create_status_from_github!`, marking it `success` for context `ci/tests`.
6. If `orgB/app`'s stack has `continuous_deployment: true`, `schedule_continuous_delivery` now sees `deployable?` true and enqueues `ContinuousDeliveryJob`, deploying a commit that never passed real CI — an unauthorized deploy triggered entirely from an unrelated tenant's credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      end
