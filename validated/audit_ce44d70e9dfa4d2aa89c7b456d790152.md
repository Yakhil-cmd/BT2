### Title
AA-received spender_attested asset can become permanently stuck when bounce-refund to an unattested trigger address fails - (File: `aa_composer.js`)

### Summary
This is an analog of the Halborn finding: a payment to a party that is forbidden from receiving a given token (blacklisted USDC/USDT holder) makes the closing/refund transfer permanently revert, trapping the funds. In `ocore`, the equivalent restriction mechanism is the `spender_attested` asset flag: a payment (including one issued by an Autonomous Agent, "AA") is only valid if every output address is on the asset's current attestor-approved list, checked in `validatePaymentInputsAndOutputs` via `storage.filterAttestedAddresses`. [1](#0-0) 

### Finding Description
When an AA receives a payment in a `spender_attested` asset as a trigger, and its response logic (or its automatic bounce mechanism) fails and must refund the received asset back to `trigger.address`, `aa_composer.js`'s `bounce()` builds a payment message sending the asset back to `trigger.address` with no attestation check at all: [2](#0-1) 

That refund message is passed to `sendUnit()`, which eventually calls `validateAndSaveUnit`. If `trigger.address` is not (or no longer) on the asset's attestor list, `validatePaymentInputsAndOutputs` rejects the unit with `"some output addresses are not attested"`. [3](#0-2) 

On that validation failure, `sendUnit` calls `bounce(err)` again to retry the refund: [4](#0-3) 

But `bounce()` guards against infinite recursion with the `bBouncing` flag — the *second* time it is invoked it silently gives up and calls `finish(null)`, sending no response unit at all: [5](#0-4) 

Meanwhile, the AA's balance was already credited with the full asset amount from the trigger in `updateInitialAABalances`, unconditionally, before any response is attempted: [6](#0-5) 

Because `finish(null)` is reached with no response unit and no state-variable update, the credited balance is never spent back out, and normal AA logic has no code path that revisits an abandoned bounce. The asset amount is permanently locked in the AA's `aa_balances` entry with no way for the trigger's own funds to be returned or for the AA's business logic to route them elsewhere, since the AA logic that would normally send them out is precisely what already failed the attestation check.

### Impact Explanation
Any AA (i.e., any address supporting a `spender_attested` asset, e.g., a controlled/regulated asset a project intentionally issues with an attestor whitelist) that accepts that asset as a trigger payment and must send an equal or partial amount back to the sender (refund, order cancellation, unmatched escrow return, auction/bid refund, etc., implemented via the AA's own payment message or via the automatic bounce fallback) will have those funds permanently frozen if the trigger address is or becomes unattested by the time of the response. This is a fund-freezing bug reachable by any ordinary trigger sender — no privileged access required — and it can be exploited or triggered accidentally by any legitimate holder of the asset who is (or later becomes) de-attested, exactly mirroring the reported "blacklisted bidder locks the auction contract" bug class.

### Likelihood Explanation
`spender_attested` assets are a first-class, publicly documented ocore feature (fields validated in `aa_validation.js` and `validation.js`, persisted in `assets`/`asset_attestors` tables) intended for compliance-style tokens where an attestor can add/remove approved holders at will. Any AA design that accepts arbitrary users' payments in such an asset and needs to bounce/refund them (a common pattern for exchanges, auctions, escrows, and vaults implemented as AAs) is exposed. The trigger only needs to be a normal payment from an address that is not on the attestor list — no cooperation from witnesses, miners, or protocol operators is needed, and the condition can arise naturally (attestor revokes an address after the trigger unit is already broadcast but before the AA response is computed).

### Recommendation
- In `bounce()`, before constructing refund payment messages for non-base assets, check whether `trigger.address` is currently attested for that asset (via `storage.filterAttestedAddresses` / `loadAssetWithListOfAttestedAuthors`), analogous to the check already performed in `divisible_asset.js`/`indivisible_asset.js` composer code.
- If the trigger address is not attested, avoid crediting/holding the asset balance indefinitely: either reject/ignore the trigger before crediting balances in `updateInitialAABalances` for `spender_attested` assets whose sender is unattested, or expose the stuck balance to AA-authored recovery logic (e.g., allow the state formula to detect and reroute it) rather than silently discarding the response.
- More generally, apply the same fix pattern the referenced report used for `AuctionUpgradeable`: disallow `spender_attested` assets as inputs to bounce/refund flows unless the AA logic explicitly re-validates attestation for the destination before attempting the transfer, so a failed attestation check cannot result in an unrecoverable "silent eat" of funds.

### Proof of Concept
1. Attestor(s) define an asset `A` with `spender_attested: true` and an initial attestor list that includes address `U`. [7](#0-6) 
2. An AA is deployed that, upon receiving asset `A`, performs some logic that can fail (bounce), or explicitly forwards/refunds the received amount back to `trigger.address` in asset `A` (e.g., an escrow/auction-style AA).
3. Attestor removes `U` from the attestor list via an `asset_attestors` update message (a normal, permissionless-to-the-attestor operation already supported by the protocol) — analogous to USDC/USDT blacklisting a wallet. [8](#0-7) 
4. `U` sends a trigger unit paying asset `A` to the AA. `updateInitialAABalances` credits the AA's balance for asset `A` with the full amount immediately. [9](#0-8) 
5. The AA's response logic attempts to send asset `A` back to `U` (either explicitly, or through the automatic `bounce()` fallback after some other failure). `validatePaymentInputsAndOutputs` rejects the unit because `U` is no longer attested. [3](#0-2) 
6. `sendUnit` calls `bounce(err)` a second time; the `bBouncing` guard makes it call `finish(null)` with no response. [10](#0-9) 
7. Result: the AA's `aa_balances` row for asset `A` retains the received amount forever, with no response unit, no state update, and no code path in the AA that can subsequently release it back to `U` or anyone else — the funds are permanently stuck, mirroring the blacklisted-USDC-bidder scenario in the original report.
