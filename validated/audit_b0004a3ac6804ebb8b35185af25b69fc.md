### Title
Reward-partition count cap overrides the per-block store budget, letting excess stake accounts inflate per-block reward-store work unboundedly - (File: `runtime/src/bank/partitioned_epoch_rewards/mod.rs`)

### Summary
`get_reward_distribution_num_blocks` computes the ideal number of reward-distribution blocks as `total_stake_accounts / partitioned_rewards_stake_account_stores_per_block()`, but then clamps that value down to at most `slots_per_epoch / 10`. Once `total_stake_accounts` exceeds `10 * slots_per_epoch * stake_account_stores_per_block` scale, the clamp — not the store budget — decides `num_partitions`, so the actual average (and, via hash-based bucketing, worst-case) number of stake accounts stored per block grows linearly with attacker-created account count instead of staying capped at the configured per-block budget.

### Finding Description
`get_reward_distribution_num_blocks` ( [1](#0-0) ) computes:
```
num_chunks = total_stake_accounts.div_ceil(stake_account_stores_per_block)
num_chunks.clamp(1, slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH)
```
The upper clamp bound (`slots_per_epoch / 10`) is unrelated to `total_stake_accounts`; it only depends on epoch length. When `total_stake_accounts` is large enough that the ideal `num_chunks` exceeds `slots_per_epoch / 10`, the returned `num_partitions` is truncated to that fixed epoch-derived ceiling, regardless of how many stake accounts must actually be distributed.

The resulting `num_partitions` is used to bucket all stake rewards via `hash_rewards_into_partitions`, which assigns each stake account's `stake_pubkey` to one of `num_partitions` buckets by hashing ( [2](#0-1) ). This is essentially uniform random bucketing, not an enforcement of `stake_account_stores_per_block` accounts per bucket. Each block then processes exactly one such bucket in `distribute_epoch_rewards_in_partition` ( [3](#0-2) ), with no additional per-block cap on how many accounts a bucket may contain.

The existing unit test `test_get_reward_distribution_num_blocks_cap` already demonstrates the mechanism: with `stake_account_stores_per_block = 10` and a 32-slot epoch (cap = 3 blocks), `4 * stake_account_stores_per_block` (40) and `5 * stake_account_stores_per_block` (50) accounts both still report only 3 blocks ( [4](#0-3) ) — i.e. average per-block work of ~13.3 and ~16.7 respectively, already 33%–67% above the configured budget of 10. This ratio is unbounded: as `total_stake_accounts → ∞` with `num_partitions` fixed at `slots_per_epoch/10`, average per-block store count grows linearly with `total_stake_accounts`.

An unprivileged attacker can drive `total_stake_accounts` up by creating many stake accounts, each delegated (directly or via CPI) to a vote account they control, funded at least at rent-exemption plus the enforced minimum delegation ( [5](#0-4) , 1 SOL once `stake_raise_minimum_delegation_to_1_sol`/BPF stake program v5 is active). Each such delegation, if it earns ≥1 lamport of reward for the epoch, contributes one entry to `rewards.num_rewards()` used by `get_reward_distribution_num_blocks` ( [6](#0-5) ). No signer/authority/rent/overflow guard limits how many such stake accounts a single attacker may create and delegate.

### Impact Explanation
Once `total_stake_accounts` crosses the epoch-length-derived threshold (`(slots_per_epoch/10) * stake_account_stores_per_block`, e.g. on mainnet-like schedules with `MAX_PARTITIONED_REWARDS_PER_BLOCK = 4096` and `slots_per_epoch = 432000`, this is `43200 * 4096 ≈ 176.9M` stake accounts), each reward-distribution block must store proportionally more stake accounts than the configured per-block budget, growing without further bound as the attacker adds more stake accounts. This directly violates the "bounded epoch-boundary work" design invariant documented at `MAX_PARTITIONED_REWARDS_PER_BLOCK` ( [7](#0-6) ), which states the budget "affects consensus." Concretely this could increase block-production time at every reward-distribution block for the entire distribution window of that epoch, a precursor DoS/consensus-timing risk rather than a direct fund-theft bug, matching the "scoped impact" described in the question (no minting, but potential to stall block production/consensus at epoch boundaries).

### Likelihood Explanation
The mechanism is real and unconditional (no feature flag guards this clamp logic), and is reachable purely through normal, permissionless system/stake instructions (create stake account, delegate stake). However, exploitation requires driving `total_stake_accounts` past a very large threshold (tens to hundreds of millions of stake accounts, each requiring at least the 1 SOL minimum delegation plus rent-exempt reserve). This makes practical exploitation extremely capital-intensive (tens/hundreds of millions of SOL) under the current 1 SOL minimum-delegation feature, though the underlying design flaw scales with `slots_per_epoch` and `stake_account_stores_per_block`, both of which are configurable per-cluster values (e.g. lower minimum delegation, shorter effective per-bank budget from slot-time scaling in `apply_partitioned_epoch_rewards_config_for_active_features`, [8](#0-7) ) and could lower the practical threshold on some cluster configurations.

### Recommendation
Decouple the per-block store budget from the epoch-fraction cap: instead of capping `num_partitions` at `slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH` outright, either (a) keep `num_partitions` sized to guarantee each partition holds at most `stake_account_stores_per_block` accounts and instead reject/throttle epoch-boundary progression (or split calculation across more than one epoch-equivalent budget) when `total_stake_accounts` would require more partitions than fit in the epoch-fraction limit, or (b) enforce a genuine secondary per-block slice limit within `distribute_epoch_rewards_in_partition` so a single partition's excess accounts spill into subsequent blocks rather than being processed all at once, preserving the invariant that no single block processes more than `partitioned_rewards_stake_account_stores_per_block()` stake accounts regardless of `total_stake_accounts`.

### Proof of Concept
Extend the existing `test_get_reward_distribution_num_blocks_cap` in `runtime/src/bank/partitioned_epoch_rewards/mod.rs` ( [9](#0-8) ) into an invariant test:

```rust
#[test]
fn test_reward_distribution_num_blocks_unbounded_per_block_work() {
    // Same setup as test_get_reward_distribution_num_blocks_cap:
    // stake_account_stores_per_block = 10, slots_per_epoch = 32 => max_blocks = 3
    let stake_account_stores_per_block = 10u64;
    let max_blocks = 3u64; // slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH

    for multiplier in [10u64, 100, 1_000, 10_000] {
        let num_stakes = multiplier * stake_account_stores_per_block;
        let stake_rewards = (0..num_stakes)
            .map(|_| Some(PartitionedStakeReward::new_random()))
            .collect::<PartitionedStakeRewards>();

        let num_blocks = bank.get_reward_distribution_num_blocks(&stake_rewards);
        assert_eq!(num_blocks, max_blocks); // clamp always hits the ceiling

        let avg_per_block = num_stakes / num_blocks;
        // INVARIANT (expected to FAIL as multiplier grows):
        // per-block store count should never exceed the configured budget.
        assert!(
            avg_per_block <= stake_account_stores_per_block,
            "average per-block stake-account stores ({avg_per_block}) exceeds configured \
             budget ({stake_account_stores_per_block}) for {num_stakes} total stake accounts"
        );
    }
}
```
Expected result: the assertion fails once `multiplier > max_blocks` (i.e. `num_stakes > max_blocks * stake_account_stores_per_block`), demonstrating that per-block reward-store work is unbounded in `total_stake_accounts`, not capped at `partitioned_rewards_stake_account_stores_per_block()` as the design intends.

```rust
    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
```

```rust
pub(in crate::bank::partitioned_epoch_rewards) fn hash_rewards_into_partitions(
    stake_rewards: &PartitionedStakeRewards,
    parent_blockhash: &Hash,
    num_partitions: usize,
) -> Vec<Vec<usize>> {
    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

    for (i, reward) in stake_rewards.enumerated_rewards_iter() {
        // clone here so the hasher's state is reused on each call to `hash_address_to_partition`.
        // This prevents us from re-hashing the seed each time.
        // The clone is explicit (as opposed to an implicit copy) so it is clear this is intended.
        let partition_index = hasher
            .clone()
            .hash_address_to_partition(&reward.stake_pubkey);
        indices[partition_index].push(i);
    }
    indices
}
```
