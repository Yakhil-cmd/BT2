### Title
Webhook signature verification is bound to a different payload field than the one used to select the target repository — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound webhook from the attacker-controlled JSON body field `repository.owner.login` (or `organization.login`), while the code that actually acts on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target `Repository`/`Stack` from a *different* field, `repository.full_name`. Both fields live in the same unverified JSON body and are read independently before/around the signature check, so nothing forces them to refer to the same repository/organization.

### Finding Description
`verify_signature` picks the GitHub App/webhook secret to check the signature against using only the claimed owner: [1](#0-0) [2](#0-1) 

`Shipit.github_app_config` resolves this claimed organization case-insensitively against the configured per-organization secrets: [3](#0-2) 

Once the signature check "passes", `create` dispatches the *raw, unmodified* JSON body to every registered handler for the event: [4](#0-3) 

But every handler determines which `Repository`/`Stack` to mutate from a **different** field of the same payload, `repository.full_name`, not from `repository.owner.login`/`organization.login` that was used for signature verification: [5](#0-4) 

This is structurally the same class of bug as `directionMask`: one field of an untrusted input is the one that gets "authenticated" (here: `repository.owner.login` picks the secret used to verify the HMAC), while a *different* field of that same input is the one that actually gets acted upon (here: `repository.full_name` picks the `Repository`/`Stack` the handler mutates). Nothing ties the two together.

**The binding that should hold:** `organization_whose_secret_verified_the_HMAC == owner(repository_that_handlers_act_on)`.

**Before the attack (legitimate GitHub delivery):** GitHub always populates `repository.owner.login` and `repository.full_name` consistently for the repository the event actually originated from, and only GitHub (or someone holding that installation's real webhook secret) can produce a matching signature, so the equality always holds naturally.

**After the attack:** an operator of a Shipit instance configured for multiple GitHub organizations (per `config/secrets.development.example.yml`'s multi-org schema) legitimately owns/administers "OrgA" and therefore legitimately knows OrgA's `webhook_secret` (it is their own GitHub App's webhook secret, not a Shipit application secret they had to steal). They craft an arbitrary JSON body where:
- `repository.owner.login` (or `organization.login`) = `"orga"` — selects OrgA's secret for verification.
- `repository.full_name` = `"victim-org/some-repo"` — the repository actually processed by the handler.

They compute a valid `X-Hub-Signature` over this crafted raw body using OrgA's known secret and POST it to `/webhooks`. `verify_signature` uses `repository_owner == "orga"`, fetches OrgA's `webhook_secret`, and the HMAC matches — verification succeeds. `create` then hands the same payload to handlers, which read `full_name = "victim-org/some-repo"` and mutate the victim stack, completely unrelated to OrgA.

### Impact Explanation
Depending on the event type, this lets an attacker who only controls one (any) organization configured on a shared/multi-tenant Shipit instance forge webhook events against **any other organization's stacks**:
- `push` events enqueue `GithubSyncJob` for the victim stack, re-syncing/refreshing its deploy spec and commit list based on attacker-supplied SHAs.
- `status`/`check_suite` events let the attacker inject a fabricated commit `Status`/check-run result for a victim commit, which feeds directly into `Commit#deployable?` — used by `Stack#build_deploy` to gate/allow deploys. Forging a passing status on a commit that never actually passed CI can enable an unauthorized deploy of that commit.
- `membership`/`pull_request`/etc. events likewise operate on whatever `full_name` claims, independent of which org's secret was used to authenticate.

This crosses the "cross-repository writes" / "unauthorized deploy" bar (Critical) described in the rules, because the write target (`repository.full_name`) is never bound to the identity that was cryptographically verified (`repository.owner.login`).

### Likelihood Explanation
This is only reachable on Shipit deployments using the **multi-organization** GitHub configuration schema (`secrets.github` keyed by organization, as documented in `config/secrets.development.example.yml`), where more than one organization's webhook secret is configured on the same Shipit instance. In that (documented, supported) configuration, any org owner who is allowed to install a GitHub App pointing at the shared Shipit instance automatically knows their own org's `webhook_secret` — no privileged Shipit access, no victim secrets, and no GitHub App private key are required. The `head(422)`/`GithubOrganizationUnknown` rescue only rejects organizations *unknown* to Shipit; a *known but unrelated* organization is accepted.

### Recommendation
After a webhook signature is verified for organization `X`, require that the repository actually referenced in the payload (`repository.full_name`) belongs to that same organization `X` before dispatching to handlers, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) and return unless verified
  head(422) and return unless payload_repository_owner_matches?(repository_owner)
  ...
end
```
and have `Handler#repository_name`/`#stacks` cross-check that the owner segment of `repository.full_name` equals the verified `repository_owner`, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `victim-org`, each with its own `webhook_secret` (multi-org schema).
2. As an attacker who legitimately controls `orga` (and therefore knows `orga`'s `webhook_secret` from their own GitHub App settings), craft a JSON body:
```json
{
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "victim-org/some-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success",
  ...
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orga_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner => "orga"`, verifies successfully using `orga`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `create` dispatches the payload to the `status` handler, which resolves the stack via `repository_name = "victim-org/some-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and records a forged `success` status against the victim commit — with no relationship to `orga` at all.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
