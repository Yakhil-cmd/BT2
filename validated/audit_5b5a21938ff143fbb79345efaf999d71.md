### Title
`Stack#inaccessible?` never checks `repository.review_stacks_enabled`, letting `CacheDeploySpecJob` cache/run specs for a `ReviewStack` on a repo with review stacks disabled - (`File: app/jobs/shipit/cache_deploy_spec_job.rb`)

### Summary
`CacheDeploySpecJob#perform` gates only on `stack.inaccessible?`, which is implemented purely as `inaccessible_since?` [1](#0-0)  — it has no relationship whatsoever to `repository.review_stacks_enabled`. Combined with an operator-precedence bug in `OpenedHandler#provision?` [2](#0-1) , an unprivileged PR author can get a `ReviewStack` provisioned on a repository that has `review_stacks_enabled: false`, and its deploy spec will still be cached and later executed.

### Finding Description
Binding to check: `stack.inaccessible?`'s truth value == `repository.review_stacks_enabled`. This is false: `inaccessible?` is defined as `inaccessible_since?` [1](#0-0) , and `inaccessible_since` is only ever set by `mark_as_inaccessible!`, called from `GithubSyncJob` when a GitHub sync fails to find/access the repo — it is completely decoupled from `review_stacks_enabled`. So the two sides never track each other; a `ReviewStack` on a `review_stacks_enabled: false` repository is `inaccessible? == false` by default (fresh sync succeeded), so `CacheDeploySpecJob#perform` proceeds past the guard [3](#0-2) .

The precondition ("bug-created ReviewStack" on a `review_stacks_enabled: false` repo) is itself real, due to an independent bug in `OpenedHandler#provision?`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [2](#0-1) 

Ruby's `&&` binds tighter than `||`, so this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.

The `review_stacks_enabled` check is scoped only to the first disjunct. If a repository has `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` (or `prevent_with_label`), `provision?` still returns `true` for a PR that carries (or lacks) the provisioning label, regardless of `review_stacks_enabled`. This calls `ReviewStackAdapter#find_or_create!`, provisioning a `ReviewStack` on a repository whose owner explicitly disabled review stacks.

Once that `ReviewStack` exists, `sync_github` / provisioning flows enqueue `CacheDeploySpecJob` for it. `CacheDeploySpecJob#perform` checks out the head commit via `Commands.for(stack)` and writes `stack.update!(cached_deploy_spec: ...)` with no re-check of `review_stacks_enabled` [3](#0-2) . A cached spec is a precursor to task execution reaching `Command#start`/`PTY.spawn` for deploys, rollbacks, and CI-triggered tasks on that stack.

### Impact Explanation
An attacker who can open a pull request (or apply a label to their own PR, if they are the PR author) on a repository configured with `provisioning_behavior: allow_with_label` or `prevent_with_label` and `review_stacks_enabled: false` can force Shipit to provision a `ReviewStack`, checkout their branch, cache the deploy spec (parsed from files in their own PR branch, `.shipit/*.yml`), and proceed toward task execution — none of which the repository owner authorized once `review_stacks_enabled` was turned off. This is an unauthorized-deploy/provisioning path against a repository configuration explicitly meant to prevent it, matching the "unauthorized deploy" Critical category. It is repeatable against any repository owned by the attacker (or any repo the attacker can PR into) that has this specific provisioning_behavior + review_stacks_enabled combination.

### Likelihood Explanation
Requires a repository configured with `provisioning_behavior_allow_with_label?` or `provisioning_behavior_prevent_with_label?` while `review_stacks_enabled: false` — a plausible but non-default combination (an operator disabling review stacks without also resetting `provisioning_behavior` back to a neutral state, or intentionally trying to restrict via label while believing `review_stacks_enabled: false` fully disables the feature). No secrets or privileges are needed by the attacker: opening a PR and/or adding a label to their own PR is sufficient. This is a genuine logic bug reachable purely through public GitHub actions on a repo already connected to Shipit.

### Recommendation
1. Fix `provision?` to parenthesize correctly so `review_stacks_enabled` gates all provisioning behaviors:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
2. Defense in depth: have `Stack#inaccessible?` (or a new guard) for `ReviewStack` also return `true`/block when `repository.review_stacks_enabled` is `false`, and have `CacheDeploySpecJob#perform` check this before caching/checkout.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb (style)
test "provision? ignores review_stacks_enabled for label-based behaviors" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: 'allow_with_label', provisioning_label_name: 'ship-it')
  # simulate opened PR with the label
  handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(pull_request_payload_with_label('ship-it'))
  assert handler.send(:provision?) # BUG: true even though review_stacks_enabled == false
end

# test/jobs/shipit/cache_deploy_spec_job_test.rb (style)
test "CacheDeploySpecJob caches spec for ReviewStack even when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false)
  stack = shipit_review_stacks(:shipit) # existing ReviewStack under repository
  assert_equal false, repository.review_stacks_enabled
  assert_equal false, stack.inaccessible? # binding: inaccessible? does NOT track review_stacks_enabled

  Shipit::Commands.any_instance.stubs(:with_temporary_working_directory).yields(Dir.mktmpdir)
  Shipit::CacheDeploySpecJob.new.perform(stack)

  assert stack.reload.cached_deploy_spec.present? # spec cached despite review_stacks_enabled == false
end
```
