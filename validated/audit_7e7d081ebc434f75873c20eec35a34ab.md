## Finding

### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, allowing a stack-scoped token to read any stack's status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via the `stack_id` column, and `Api::BaseController` enforces that scope by filtering the queryable stack set through `stacks`/`stack` before looking up `params[:stack_id]`. `Api::CCMenuController` overrides `#stack` and resolves the requested stack directly against the global `Stack` relation, never checking it against the authenticated client's `stack_id`, breaking the "stack a token authorizes" vs. "stack it touches" equality that the rest of the API relies on.

### Finding Description
`Api::BaseController` establishes the intended trust boundary: [1](#0-0) 

`stacks` is restricted to `current_api_client.stack_id` when the client is scoped, and `stack` is derived only from within that restricted relation, i.e. the invariant `requested_stack ∈ {stacks authorized by token}` is always checked. This invariant is exercised and expected by the test suite (e.g. "an api client scoped to a stack will only see that one stack").

`Api::CCMenuController`, however, overrides `stack` and bypasses `stacks` entirely: [2](#0-1) 

`require_permission :read, :stack` only checks that the client's `permissions` array contains `read:stack` — it never checks that the requested `stack_id` matches the client's own `stack_id`: [3](#0-2) 

Because `CCMenuController#authenticate_api_client` also accepts standard Basic-Auth tokens (via `super`) in addition to the `?token=` query parameter, any credential holding a valid `ApiClient` with `read:stack` — including one deliberately scoped to a single stack via `stack_id` — can call `GET /api/:stack_id/cc.xml` with an arbitrary `stack_id` and receive that other stack's deploy status, because `stack` resolves against `Stack.from_param!` on the unrestricted `Stack` relation instead of the client-scoped `stacks` relation used everywhere else in the API namespace. [4](#0-3) 

### Impact Explanation
This breaks the "stack a token authorises" vs. "stack it touches" binding: an `ApiClient` scoped to stack A (i.e., its owner intentionally limited it to that one stack, e.g. via `stack_id` set out-of-band or through code that supports stack-scoped tokens) can be used to read the deploy/build status (name, last build status, last build label, last build time, web URL) of any other stack B in the installation, purely by changing the `stack_id` path parameter. This is an authorization-scope escalation yielding unauthenticated-for-that-stack read of stack state, matching the High-impact category "escalation ... or unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Any holder of a valid `ApiClient` credential with `read:stack` permission can trigger this with a single unauthenticated-for-target-stack GET request; no additional privilege, secret, or social engineering is required beyond possessing one legitimate, narrowly-scoped API token. The stack-scoping mechanism (`ApiClient#stack_id`) is a first-class, tested feature of the engine, so any consumer relying on it for isolation (e.g., handing a CCMenu URL/token to a less-trusted party for one stack) is directly affected.

### Recommendation
Have `Api::CCMenuController#stack` reuse the inherited, scope-respecting `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so stack-scoped `ApiClient` tokens cannot be used to read other stacks' CI/deploy status.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to `stack_a.id` (stack-scoped token), e.g. as tested in `test/controllers/api/stacks_controller_test.rb` for `here_come_the_walrus`.
2. Authenticate to `GET /api/:stack_id/cc.xml` using that client's Basic-Auth credentials (falls through `CCMenuController#authenticate_api_client`'s `super` path) but supply `stack_id = stack_b.to_param` for a different, unrelated stack.
3. Observe that `BaseController#authenticate_api_client` succeeds (valid credentials) and `require_permission :read, :stack` passes (client has `read:stack`), then `CCMenuController#stack` returns `stack_b` via `Stack.from_param!(params[:stack_id])`, rendering `stack_b`'s deploy status even though the client's `stack_id` is `stack_a.id`. [5](#0-4)
