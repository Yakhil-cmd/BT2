### Title
Missing WebAuthn ceremony `type` validation in `PartialAuthenticatorAssertionResponse::verify` - (File: `types/src/transaction/webauthn.rs`)

### Summary
`PartialAuthenticatorAssertionResponse::verify()` deserializes attacker-supplied `client_data_json` into a `CollectedClientData` and validates only the `challenge` and the cryptographic signature over `authenticator_data || SHA-256(client_data_json)`. It never asserts that `collected_client_data.ty` equals the expected assertion ceremony type (`"webauthn.get"`), which is a mandatory step in the WebAuthn verification procedure (§7.2, step 11).

### Finding Description
`verify()` performs the following steps, in order, on the caller-controlled `client_data_json` bytes:
1. `serde_json::from_slice` into `CollectedClientData` [1](#0-0) 
2. Extracts `challenge` and compares it against the SHA3-256 digest of the signing message of the `RawTransaction` [2](#0-1) 
3. Builds `verification_data = authenticator_data || SHA-256(client_data_json)` and checks the signature against the account's bound public key [3](#0-2) 

At no point does the code inspect `collected_client_data.ty`. This is confirmed directly by the repo's own test suite: `verify_real_partial_authenticator_assertion_response_from_spc` constructs a `CollectedClientData` with `"type": "payment.get"` (not `"webauthn.get"`) and asserts `verify()` returns `Ok(())` [4](#0-3) . This proves the `ty` field is entirely unchecked in the production `verify()` path — any string value in that field is accepted as long as `challenge` and the signature validate.

### Impact Explanation
Per the WebAuthn spec, the `type` check exists specifically to prevent cross-ceremony signature confusion (e.g., preventing a registration-ceremony signature/response from being replayed as an authentication assertion, or vice versa). Its absence here means Aptos's WebAuthn authenticator does not enforce operation-type binding: any JSON payload with the right `challenge` and a valid signature over `authenticator_data || SHA-256(client_data_json)` is accepted regardless of what ceremony it claims to be.

However, actual exploitability is constrained by cryptography, not by this check: the attacker still needs a signature produced by the account's real private key over the exact `verification_data` bytes. Since Aptos-bound WebAuthn accounts are keyed off `AnyPublicKey::Secp256r1Ecdsa` and the only ceremony that normally produces a raw assertion signature with that key is `authenticatorGetAssertion` (registration/`create` ceremonies typically don't sign arbitrary challenges with the credential private key in this way), there is no demonstrated path here for an unprivileged attacker — lacking the private key — to forge admission of a transaction under the wrong sender. The missing check is a genuine deviation from the WebAuthn spec's verification steps and a latent invariant violation, but this repo intentionally accepts non-`"webauthn.get"` types already (the SPC `"payment.get"` test is treated as expected behavior, not a bug), and no code path was found where an attacker without possession of the appropriate private key can leverage the missing `type` check to gain admission for a transaction they aren't authorized to sign.

### Likelihood Explanation
Low, as a standalone unprivileged-attacker path to unauthorized transaction admission: exploitation still requires possession of a valid secp256r1 signature over `authenticator_data || SHA-256(client_data_json)` bound to the target account's public key, which an unprivileged attacker without the private key cannot produce for an arbitrary `challenge`. The finding is real as a spec-compliance/defense-in-depth gap, but does not by itself satisfy the "unprivileged input gets a transaction admitted under the wrong sender/signer" bar without an additional key-leakage or cross-ceremony-signing primitive that was not found in this codebase.

### Recommendation
Add an explicit check in `PartialAuthenticatorAssertionResponse::verify()` that `collected_client_data.ty` matches the expected ceremony type (`ClientDataType::Get`, and any explicitly supported extensions like the SPC `payment.get` variant), returning an error otherwise, to fully align with WebAuthn §7.2 step 11 and remove reliance on cryptographic-key possession as the sole mitigating factor.

### Proof of Concept
The existing test `verify_real_partial_authenticator_assertion_response_from_spc` is direct evidence: it builds `client_data_json` with `"type": "payment.get"` and a matching `challenge`/signature, and asserts `paar.verify(&raw_txn, &any_public_key)` is `Ok(())` [5](#0-4) , proving `ty` is not validated. A minimal additional test could reuse this fixture but set `ty` to an arbitrary/unexpected string and assert the same success, confirming no type gate exists in `verify()`.
