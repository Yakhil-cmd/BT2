### Title
Webhook signature verification is keyed on `repository.owner.login`, but event processing acts on the unrelated `repository.full_name` field, allowing cross-organization event forgery when any configured GitHub App has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to verify a webhook against using `repository.owner.login` (or `organization.login`) taken from the request body, but every event `Handler` (push, status, check_suite, pull_request, etc.) identifies the `Repository`/`Stack` to mutate using the independent `repository.full_name` field from the same body. Neither field is checked against the other, so verification and the acted-upon resource are bound to two different, attacker-controllable pieces of the same unauthenticated JSON payload.

### Finding Description
`verify_signature` picks the GitHub App config to verify against based on the organization name in the payload: [1](#0-0) [2](#0-1) 

The verification itself is skipped entirely if that organization has no `webhook_secret` configured: [3](#0-2) 

Shipit's own setup docs describe the webhook secret as optional: [4](#0-3) 

Once a webhook is accepted, every handler resolves the target `Repository`/`Stack` using `repository.full_name`, a completely separate field never covered by the signature-selection logic: [5](#0-4) [6](#0-5) 

Concrete handlers act on that resolved repository/stack without any relation to the organization whose secret validated the request: `PushHandler` triggers `stack.sync_github`, `StatusHandler` creates commit statuses that can drive continuous deployment, and `CheckSuiteHandler` schedules check-run refresh: [7](#0-6) [8](#0-7) [9](#0-8) 

The equality that should hold but does not is:
`organization authenticated via repository.owner.login (secret lookup)` == `organization/repository actually written via repository.full_name (handler target)`.

Before the attack: an operator has configured Shipit for two GitHub organizations in `secrets.yml` (`config/secrets.development.shopify.yml` shows this multi-org shape), one of which — e.g. a low-value staging org — is left with `webhook_secret: nil` as the docs allow. [10](#0-9) 

After the attack: an unauthenticated internet client (no GitHub App access, no Shipit account, no API token) posts directly to `/webhooks` with `X-Github-Event: status` (or `push`/`check_suite`), setting `repository.owner.login` to the unsecured org (bypassing signature checks per `github_app.rb:76-78`) while setting `repository.full_name` to a repository/stack that belongs to the fully-secured organization. `verify_signature` passes because `webhook_secret` is blank for that org, and `StatusHandler`/`PushHandler` then act on the victim stack identified purely by `full_name`.

### Impact Explanation
This lets an unprivileged, unauthenticated attacker forge GitHub commit statuses (`StatusHandler`) for arbitrary commits on stacks belonging to organizations they have no relationship with, which can flip required-status checks to "success" and trigger Shipit's continuous-deployment machinery, producing an unauthorized deploy. It can also forge `push` events causing `sync_github` to run against a victim stack, and forge `check_suite` events to trigger check-run refresh cycles. This crosses the "unauthorized deploy" and "cross-repository writes" impact bar because the write target (`repository.full_name`) is never validated against the credential that authorized the request (`repository.owner.login`'s secret).

### Likelihood Explanation
Requires only that at least one configured GitHub App/organization in the Shipit instance has no `webhook_secret` set — an explicitly documented, "optional" configuration choice — while other organizations on the same instance are secured. Given multi-tenant/multi-org Shipit deployments are a supported and documented configuration shape, and no cross-check exists anywhere in the handler pipeline tying the verified organization to the acted-upon repository, this is straightforward to exploit with a single crafted HTTP POST once the misconfigured org is identified (organization names are often public).

### Recommendation
In `WebhooksController#verify_signature`, after determining `repository_owner` and verifying the signature, additionally assert that the resolved repository owner matches the owner embedded in `repository.full_name` (and vice-versa in `Handler#repository_name`), rejecting mismatches. Independently, treat a missing `webhook_secret` as a hard misconfiguration error rather than an implicit bypass (`lib/shipit/github_app.rb:76-78` should not `return true`), and update `docs/setup.md` to make the webhook secret mandatory.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `victim-org` (has `webhook_secret`) and `staging-org` (no `webhook_secret`), each with an installed GitHub App, per `config/secrets.development.shopify.yml`.
2. As an outside, unauthenticated attacker, send:
```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<commit sha belonging to a stack under victim-org>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "staging-org" }, "full_name": "victim-org/victim-repo" }
}
```
No `X-Hub-Signature` header is required for this request.
3. `verify_signature` resolves `repository_owner` to `staging-org`, whose `webhook_secret` is `nil`; `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-78`).
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)`, forging a "success" status on `victim-org/victim-repo`'s commit even though the request was never validated by `victim-org`'s secret — potentially satisfying a required status check and triggering continuous deployment for that stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
