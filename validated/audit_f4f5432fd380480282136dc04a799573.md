### Title
`spender_attested` asset restriction permanently blocks a holder's own funds once its attestation is revoked, even for returning/burning tokens to the definer - (File: validation.js)

### Summary
For assets defined with `spender_attested: true`, `ocore` requires that both the spending address (input owner) and every output address of a transfer/issue be present in the currently attested-address list, exactly like the reported ERC20 pattern where a restriction is applied unconditionally to a spender regardless of the *purpose* of the action. Unlike the `auto_destroy` exception which explicitly special-cases sending back to the definer, no equivalent carve-out exists for the attestation check, so a holder who loses attestation can never move the asset again — not even to return/burn it to the definer.

### Finding Description
`validatePaymentInputsAndOutputs` in `validation.js` enforces, for every `transfer` input of a `spender_attested` asset, that the owner address of the spent output is currently in `objAsset.arrAttestedAddresses`: [1](#0-0) 

This check is unconditional — it runs before any special-casing similar to the `auto_destroy` exception right above it that explicitly allows sending to the definer address: [2](#0-1) 

The same unconditional owner-attestation check is duplicated for the private/fixed-denomination code path: [3](#0-2) 

Additionally, at the end of `validatePaymentInputsAndOutputs`, *every* output address of the transfer (including a change/return output back to the definer) must also be attested, with no exception: [4](#0-3) 

The attestor list itself can only be modified by the asset's definer: [5](#0-4) 

So once the definer removes an address from the attestor list (or simply never attests it, e.g., it received the asset via a change output before being un-attested), that address's outstanding balance of the asset becomes permanently unspendable by that holder — it cannot even be sent back to the definer to "revoke" its exposure, because the output-side attestation check (`arrOutputAddresses` must all be attested) and input-side owner-attestation check apply uniformly with no analogous carve-out to the `auto_destroy`-to-definer exception.

### Impact Explanation
This is a fund-freezing condition: an ordinary asset holder (an unprivileged unit poster performing a payment message referencing a `spender_attested` asset) can have funds permanently locked once attestation is withdrawn or was never granted, with no protocol-level mechanism (unlike `auto_destroy`) to unwind or return the position. This falls in the accepted "AA fund loss or freezing" impact category, since AAs or wallets holding such assets can become unable to ever dispose of the balance.

### Likelihood Explanation
This is triggered purely by ordinary use of a `spender_attested` asset combined with a definer-controlled attestor-list update (`asset_attestors` message) — no privileged node/hub/network role is required to reach the vulnerable code path; the "attacker" role here is simply the asset definer withdrawing attestation, or the natural consequence of an attestor list never covering a change/return address.

### Recommendation
Add an explicit carve-out in the attestation checks (mirroring the existing `auto_destroy` → definer exception) that allows a currently-unattested owner to send the entire balance of a `spender_attested` asset back to the asset's `definer_address` (and correspondingly permit the definer_address as an output even when not itself in the attestor list), so that holders always retain the ability to "revoke"/return their position even if their attestation is withdrawn.

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and attestor list `[Attestor1]`.
2. `Attestor1` attests address `X`; `X` receives a payment of asset `A`.
3. Definer posts `asset_attestors` update removing `X`'s attestation path (e.g., `Attestor1` stops attesting `X`, or the attestor list is changed) — validated via `validateAttestorListUpdate`, [5](#0-4) .
4. `X` now attempts to send its asset-`A` balance anywhere, including back to the definer address to exit the position.
5. `validatePaymentInputsAndOutputs` rejects the input with `"owner address is not attested"` at [6](#0-5) , and even if that check were bypassed, the output-side check at [7](#0-6)  would also reject the definer's output address if it isn't itself attested.
6. `X`'s balance of asset `A` is now permanently frozen with no way to move or return it.
