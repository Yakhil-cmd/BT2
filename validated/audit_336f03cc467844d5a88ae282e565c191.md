### Title
Unbounded/Unreasonable `bounce_fees` in AA Definitions Enables Fund Confiscation from Unprivileged Triggerers - (File: aa_validation.js, aa_composer.js)

### Summary
AA (Autonomous Agent) definitions include an optional `bounce_fees` object specifying, per asset, how much of the payment attached to a trigger unit the AA is entitled to keep if the trigger bounces (fails). The only validation applied to this value is an upper bound of `constants.MAX_CAP` (the entire token supply cap) and a lower bound of `constants.MIN_BYTES_BOUNCE_FEE` for the base asset. There is no economically sane cap relative to typical transaction sizes, so an AA author can set `bounce_fees` to an arbitrarily large value and design AA logic that reliably bounces triggers, causing any unprivileged user who sends a payment-triggering unit to that AA to lose their entire attached amount to the AA (and ultimately to its owner/definer), rather than the small, reasonable "gas"-like fee the mechanism was designed for.

### Finding Description
`validateAADefinition` in `aa_validation.js` validates the `bounce_fees` map: [3](#0-2) 
The only numeric constraint is `fee > constants.MAX_CAP` (rejected) and, for the base asset, a floor of `constants.MIN_BYTES_BOUNCE_FEE`. `MAX_CAP` represents the total token supply, so in practice this check imposes essentially no real limit for a normal AA use case — an author can set `bounce_fees.base` to millions or billions of bytes.

At execution time, `handleTrigger` in `aa_composer.js` reads this value (defaulting to `constants.MIN_BYTES_BOUNCE_FEE` if absent): [4](#0-3) 
and enforces that the trigger's attached amount for each asset covers the configured `bounce_fees`, otherwise it bounces immediately: [5](#0-4) 
When the AA logic bounces (either because of insufficient bounce-fee coverage or because some other condition in the AA's `bounce()`/evaluation path triggers a failure), the bounce logic keeps `bounce_fees[asset]` and only refunds `amount - fee` (or nothing at all if `fee >= amount`): [1](#0-0) 

Because there is no meaningful upper bound tied to the actual cost of the AA's operations, a malicious AA author can:
1. Set `bounce_fees.base` to an arbitrarily large amount (bounded only by `MAX_CAP`).
2. Publish the AA with a superficially legitimate-looking `messages`/`init` script that appears to perform a useful service (e.g., a swap, lottery, or vault) but is designed (via formula logic) to bounce under conditions that are not obvious to the average user, or simply always bounce for certain input patterns.
3. Any unprivileged user who sends a trigger unit with an attached payment to interact with this AA loses the payment (up to the full `bounce_fees` amount) if the trigger bounces, since the fee is deducted entirely from the trigger sender's own funds without ever reaching the intended AA outputs.

This differs from the normal, expected use of `bounce_fees`, which is meant to cover the AA's own storage/processing cost (default is `MIN_BYTES_BOUNCE_FEE`), not to serve as an economic trap for interacting users.

### Impact Explanation
This allows an AA author (an unprivileged, arbitrary poster of an AA definition unit — anyone can publish an AA) to cause unauthorized loss of funds from any user who sends a trigger to that AA and whose trigger is bounced, up to the entire attached payment. This is a concrete "AA fund loss" scenario for the triggering party: their bytes/asset payment intended for the AA's business logic is instead absorbed by the bounce-fee mechanism and stays in the AA's balance under the definer's control, without the trigger sender receiving any of the intended response. Because `bounce_fees` is a self-declared parameter with no meaningful cap, this is exploitable at scale against any user who is not aware of (or does not carefully audit) the exact bounce_fees value and the AA's bounce conditions.

### Likelihood Explanation
Likelihood is high for any AA that a user interacts with without carefully verifying `bounce_fees` and the exact bounce conditions of the `messages`/`init` formula — which for typical end-users is effectively invisible, since bounce conditions can depend on complex oscript logic. Since defining and publishing an AA is a fully public, unprivileged action (any unit poster can register one), and users are commonly directed to interact with third-party AAs (e.g., DeFi/exchange AAs), the attack surface is broad and requires no special access.

### Recommendation
Introduce an economically meaningful upper bound for `bounce_fees` values independent of `constants.MAX_CAP`, e.g., cap them to a small multiple of the unit's actual storage/processing cost (similar in spirit to `MIN_BYTES_BOUNCE_FEE`), or require that `bounce_fees` be provably related to unit size rather than an arbitrary attacker-chosen constant. Additionally, consider warning/UX-level surfacing of `bounce_fees` amounts relative to typical trigger payment sizes so wallets can flag suspiciously large bounce fees before a user sends a trigger.

### Proof of Concept
1. Attacker publishes an AA definition unit with:
```
["autonomous agent", {
  bounce_fees: { base: 999999999999999 }, // near MAX_CAP, passes validation since it's <= MAX_CAP
  messages: [ { app: "payment", if: "{ trigger.data.x != 42 }", payload: { asset: "base", outputs: [{address:"{trigger.address}", amount:"{trigger.output[[asset=base]]-1000}"}] } } ]
}]
```
Validation passes per `aa_validation.js` lines 748-760, since `999999999999999 <= constants.MAX_CAP`.
2. A user, unaware of the exact bounce logic, sends a trigger unit with `trigger.data.x` unset (or any value != 42) and attaches, say, 100,000 bytes hoping to receive the AA's payment response.
3. Because the `if` condition on the payment message is false for the default trigger.data, the AA falls through to "no messages", causing `handleTrigger`'s bounce path (`aa_composer.js` lines 909-945) to keep up to `bounce_fees.base` bytes (here, essentially unlimited, capped only by what the user attached) rather than refunding it, since `fee > amount` results in no bounce-back message and the funds remain with the AA.
4. The user's entire attached payment is absorbed by the AA/definer with no service rendered and no recourse, illustrating unauthorized fund loss enabled by the unbounded (`MAX_CAP`-only) validation of `bounce_fees`.
