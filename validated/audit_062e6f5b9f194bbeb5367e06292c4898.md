### Title
Headers-Commission Split Can Redirect a Co-Author's Share to an Attacker-Controlled Address - (File: validation.js)

### Summary
`validateHeadersCommissionRecipients()` only checks that the `earned_headers_commission_recipients` list contains syntactically valid addresses that sum to 100%; it never checks that the listed addresses are actually among `objUnit.authors`. Any unprivileged user who composes/co-signs a multi-authored unit can therefore route 100% of the unit's future headers-commission earnings to an address he alone controls, cutting out the other legitimate co-author(s) who jointly earned that reward, exactly analogous to the reported "Level-5 self-referral" pattern where a fee that is supposed to be split among multiple parties is instead diverted entirely to the attacker.

### Finding Description
When a unit has more than one author, the protocol requires `earned_headers_commission_recipients` to declare how the headers commission earned by that unit (when it wins parent-selection) is later split: [1](#0-0) 

The only checks performed are: non-empty array, positive integer shares, valid checksum address, sorted-by-address, and sum of shares == 100. There is no cross-check against `objUnit.authors` (the actual co-signers of the unit) anywhere in this function or in `validateAuthors()`: [2](#0-1) 

The unchecked recipient list is persisted verbatim in `writer.js`: [3](#0-2) 

and is later used, without re-validating membership in `unit_authors`, to actually pay out the headers commission to whichever address was listed: [4](#0-3) 

Because share distribution is keyed purely off the `earned_headers_commission_recipients` table rather than off `unit_authors`, the composer of a jointly-authored unit (e.g. the party who builds the final joint and asks the co-signer(s) to add their signature) can set the list to `[{address: <attacker_address>, earned_headers_commission_share: 100}]` while the unit is still nominally co-authored by another address that expected a share. Nothing in unit validation, in signature verification, or in the commission-payout code enforces that the recipients equal (or even intersect) the set of authors, so the co-author has no on-chain guarantee that they will receive any of the commission their signature helped earn.

### Impact Explanation
This directly diverts protocol reward funds (headers commission) that are supposed to be shared with the entitled co-author(s) of a unit to an address chosen unilaterally by whoever composed the recipients list, resulting in unauthorized redirection/theft of funds from the rightful commission earner — the same "commission bypass/self-redirection" bug class as the reported issue, just expressed through ocore's native commission-sharing primitive instead of an external referral contract.

### Likelihood Explanation
Any wallet or user composing multi-authored units controls the `earned_headers_commission_recipients` field when building the joint (see `composer.js`), and validation never ties it back to the authors, so this is trivially reachable by any unprivileged unit poster/composer without any special privilege — it only requires convincing/expecting another party to co-sign a unit whose composer controls the recipients list.

### Recommendation
In `validateHeadersCommissionRecipients()` (validation.js), require that every `recipient.address` in `earned_headers_commission_recipients` be one of `objUnit.authors[].address`, in addition to the existing checks (or otherwise require author consensus/attestation before deviating from the current default of splitting proportionally/equally among authors).

### Proof of Concept
1. Address A and address B agree to jointly author (co-sign) a payment unit, each expecting 50% of any future headers commission the unit earns.
2. A composes the joint via `composeJoint()`/`composer.js`, setting `params.earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 100}]` (A's own address) instead of the agreed 50/50 split.
3. A signs with their key and asks B to co-sign; B, trusting the arrangement, adds their signature without independently verifying the recipients list (or the wallet UI does not surface it).
4. The unit passes `validateHeadersCommissionRecipients()` because the list is non-empty, sums to 100, and contains a valid address — it never checks that A is (or is not) the sole beneficiary versus B being excluded.
5. Once the unit becomes stable and wins headers commission from a later best child, `calcHeadersCommissions()` pays out 100% of the commission to A only, per `objUnit.assocEarnedHeadersCommissionRecipients`, leaving B with nothing despite having co-authored (and thus earned) the reward.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
