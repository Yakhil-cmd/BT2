### Title
Arbiter-locked shared-address funds can be frozen indefinitely with no time-lock fallback - (File: arbiter_contract.js)

### Summary
The `deriveSharedAddress` function builds an `["or", ...]` address definition for arbiter contracts where funds held in the shared address can only be released by (a) both parties' mutual signature, or (b) an `in data feed` condition keyed on the arbiter address publishing `"CONTRACT_" + contract.hash`. If the counterparty refuses to cosign and the arbiter never posts a resolution (whether due to unavailability, refusal, going offline, or being compromised), the funds in the shared address are permanently locked with no time-based escape hatch, mirroring the reported `Perpetual` bug where a privileged party can hold funds hostage indefinitely because no timelock exists to force resolution.

### Finding Description
`deriveSharedAddress` (in `arbiter_contract.js`) constructs the definition for the payment-holding shared address as an OR of five conditions: mutual signing (`arrDefinition[1][0]`), a "self-release" branch for each party gated on an `in data feed` published by the *other* party (private-asset case, `arrDefinition[1][1]`/`[1][2]`), and two branches gated on the *arbiter* publishing a `CONTRACT_<hash>` data feed naming the winner (`arrDefinition[1][3]`/`[1][4]`), as shown at [1](#0-0) . The arbiter is expected to resolve the dispute via `openDispute`/`complete` off-chain workflow using `data_feed` messages containing `"CONTRACT_" + hash` (see `parseWinnerFromUnit` reading that key) [2](#0-1) . None of the OR branches include a timestamp- or MCI-bounded fallback (e.g., "after N days, either party may reclaim their share unilaterally"). Unlike the `Perpetual` contract's `beginGlobalSettlement`/`endGlobalSettlement` pair, where an admin enters an unlimited "emergency" hold with no forced exit, this arbiter-contract definition permanently conditions spending on the arbiter's voluntary action, with the counterparty's cooperation as the only alternative.

### Impact Explanation
If the arbiter becomes unresponsive, malicious, loses their private key, or simply refuses to rule (and the counterparty also refuses to cosign a mutual release), the funds locked in the shared address defined by `deriveSharedAddress` become permanently unspendable — a full and indefinite freeze of user funds analogous to the reported "emergency mode indefinitely" issue, since there is no code path or oscript condition that allows escaping the lock after any elapsed time.

### Likelihood Explanation
This is reachable by any two ordinary wallet users who set up an arbiter contract (a core feature exposed to any unprivileged user via `wallet.js`/`arbiter_contract.js`), and requires only that the arbiter (a third party chosen at contract creation, not a network administrator) withholds action — no privileged network role or malicious node/hub behavior is required, satisfying the "AA/asset/private-payment counterparty" reachability the scan is limited to. Arbiters going silent, disputing indefinitely, or being unreachable is a realistic real-world failure mode with no special exploit needed.

### Recommendation
Add a time-locked branch to the shared-address definition (similar in spirit to the External Report's suggested fix): e.g., after a fixed timeout (tracked via `ttl`/`creation_date`, both of which already exist in the `wallet_arbiter_contracts` schema at [3](#0-2) ), allow either party to reclaim their agreed share unilaterally (e.g., via a `["and", [["address", party], ["not before", timestamp]]]`-style clause), so an unresponsive or malicious arbiter cannot freeze funds forever.

### Proof of Concept
1. Two users (offeror and acceptor) create an arbiter contract and fund the shared address per `deriveSharedAddress`, whose definition is exactly the OR of mutual-signature / arbiter-data-feed branches shown above.
2. The paying party sends the agreed amount to the shared address, moving the contract to `"paid"` status.
3. A dispute arises; `openDispute` is called, moving status to `"in_dispute"` [4](#0-3) .
4. The arbiter never publishes a `CONTRACT_<hash>` `data_feed` message (goes offline, refuses, or is compromised), and the counterparty never cosigns a mutual release.
5. Because the `arrDefinition` OR branches only accept mutual signatures or an arbiter-signed data feed, no unit can ever satisfy the shared address's spending conditions — the funds are frozen in the DAG forever, with no timelock-based branch to break the deadlock.

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
