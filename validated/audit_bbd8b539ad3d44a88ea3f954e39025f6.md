### Title
Cross-organization forged commit status via webhook signature/action scope mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on an untrusted payload field (`repository.owner.login`, falling back to `organization.login`), while the `status` webhook handler that then *writes* application state (`StatusHandler#process`) does not check that field at all — it looks up the target `Commit` purely by `sha` across the entire Shipit instance, with no repository/organization scoping. This breaks the equality "organization that authenticated == repository/commit that is written."

### Finding Description
`WebhooksController#verify_signature` picks the verifying `github_app`/secret using a field read straight out of the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

The HMAC signature is verified over the raw request body using the secret configured for whichever organization `repository_owner` claims to be, via `Shipit.github(organization: repository_owner)` and `GithubApp#verify_webhook_signature`: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` dispatches the parsed body to the registered handler for the event, unconditionally: [4](#0-3) 

Most handlers (e.g. `PushHandler`) at least re-scope the action to a `Repository` derived from `repository.full_name` in the same payload via `Handler#stacks`/`#repository_name`: [5](#0-4) [6](#0-5) 

But `StatusHandler`, which handles GitHub's `status` event and writes commit CI-status rows used for deploy gating, does **not** go through this repository scoping at all — it finds target commits by `sha` alone, globally, across every stack/organization tracked by the Shipit instance: [7](#0-6) 

So the identity that was cryptographically authenticated (the organization whose `webhook_secret` matched, selected via `repository.owner.login`/`organization.login`) is never checked against the identity of the object actually mutated (`Commit` matched only by `sha`, which can belong to a completely different repository/organization configured on the same Shipit instance). An attacker who is a legitimate admin of, or otherwise has access to, the webhook secret for **any one** GitHub organization/repository connected to a given Shipit deployment can forge a `status` webhook, correctly sign it with that org's secret, but populate `sha`/`state`/`context`/`description` to target a commit sha belonging to a **different** tracked repository/organization. `verify_signature` will accept it (secret matches the org named in the payload), and `StatusHandler#process` will happily create/attach that forged status to the unrelated commit via `Commit#create_status_from_github!`.

### Impact Explanation
Commit statuses are used by Shipit as CI-gating signals (`ci.require`/`ci.hide` configuration referenced in `deploy_spec.rb`/`stack.rb`) to decide whether a commit is deployable. A forged "success" status on a commit in a repository/org the attacker doesn't otherwise control can satisfy required-check gating and enable that commit to be deployed/merged through Shipit's normal flow, i.e., an unauthorized deploy — one of the explicitly in-scope Critical impacts. This is a genuine authentication/authorization binding failure: the HMAC check authenticates "an organization," not "the specific repository/commit the payload claims to describe," yet the write path trusts the payload's commit reference unconditionally.

### Likelihood Explanation
Exploitation requires the attacker to already know a valid `webhook_secret` for at least one organization configured on the target Shipit instance — this is available to anyone with admin access to that org's GitHub webhook settings (a much lower bar than access to the Shipit instance itself, a `GITHUB_TOKEN`, or any Shipit credential). Given that bar, forging the `status` payload and computing a valid HMAC is trivial, and the vulnerable code path (`Commit.where(sha: params.sha)`, unscoped by repo) is unconditional for every incoming `status` event.

### Recommendation
`StatusHandler#process` (and any other handler that doesn't already scope through `Handler#stacks`) must additionally verify that the commit(s) matched by `sha` belong to a `Stack`/`Repository` whose `full_name`/`owner` matches the `repository`/`organization` field of the same payload that was used to select the verifying secret in `WebhooksController#verify_signature`. More generally, `verify_signature` should bind the authenticated organization to the specific repository object acted upon by the handler, not merely to secret selection.

### Proof of Concept
1. Shipit instance tracks stacks for two independent GitHub orgs, `org-a` and `org-b`, each with its own `webhook_secret` configured under `Shipit.github(organization:)`.
2. Attacker is an admin of a repository under `org-a` and thus knows/controls `org-a`'s `webhook_secret` (visible/settable in that repo's/org's GitHub webhook settings).
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<commit sha belonging to a stack under org-b>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "org-a" } }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` derives `repository_owner = "org-a"`, fetches `Shipit.github(organization: "org-a")`, and the HMAC matches → request accepted.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matches the `org-b` commit regardless of the `org-a` scoping used for verification — and calls `commit.create_status_from_github!(params)`, writing a forged "success" status for a commit in `org-b`'s repository that the attacker has no legitimate access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
