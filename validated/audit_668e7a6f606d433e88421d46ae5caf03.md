### Title
Webhook signature verification is scoped to the wrong organization, allowing cross-repository status/commit injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to check the `X-Hub-Signature` against using `repository_owner`, taken from the same untrusted JSON body it is about to verify. [1](#0-0)  The handlers that actually act on the payload (e.g. `Shipit::Webhooks::Handlers::StatusHandler`, `Handler#stacks`) never re-check that the record they mutate belongs to the same organization/repository whose secret produced a valid signature — they instead trust independent fields of the same payload (`sha`, `repository.full_name`). [2](#0-1) [3](#0-2)  This breaks the equality that should hold: `organization whose secret authenticated the signature == organization owning the repository/commit the handler mutates`.

### Finding Description
Shipit explicitly supports hosting multiple, mutually untrusted GitHub organizations from a single instance, each with its own `webhook_secret` configured under a top-level org key in `config/secrets.yml`. [4](#0-3) 

When a webhook is delivered, `verify_signature` resolves the app/secret to verify against solely from the request body:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

This only proves the request was signed with the secret belonging to `repository_owner` — it does not constrain what any other field of the same JSON body may contain. Handlers then act on unrelated fields with global scope:

- `StatusHandler` looks up commits by `sha` alone, with no scoping to the organization that produced a valid signature:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
`Commit.sha` is not guaranteed unique per organization, and nothing ties the `sha` being reported to the `repository`/`organization` field that was used for signature verification.

- The base `Handler#stacks`/`#repository_name` (used by `PushHandler`, `pull_request` handlers, etc.) resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`, a field independent of `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Consequently, an attacker who administers their own GitHub organization/App configured in the same Shipit instance (a supported, unprivileged setup) knows their own org's `webhook_secret`. They can craft a webhook whose `repository.owner.login` (or `organization.login`) matches their own org — so `verify_signature` succeeds — while every other field of the payload (`sha`, `repository.full_name`, `ref`, `state`, `context`) references a victim organization's repository/commit. The signature check offers no cryptographic binding between "who signed this" and "what repository/commit this payload describes."

### Impact Explanation
Via the `status` event, this allows an attacker to inject arbitrary CI statuses (e.g. `state: "success"`, matching `context`) against any commit `sha` known to the attacker in a victim stack they do not control. `Commit#deployable?` and `Commit#schedule_continuous_delivery` use exactly this status data to decide whether a commit is deployable and to trigger continuous delivery:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
...
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [6](#0-5) 
For a victim stack with `continuous_deployment: true`, forging a passing status for a pending commit can trigger an unauthorized automatic deploy — matching the "unauthorized deploy" Critical-impact criterion. Even without continuous deployment, it corrupts the CI/status gating (`required_statuses`, `blocking_statuses`) that human operators rely on before manually deploying, again enabling an unauthorized deploy decision. This crosses the required credential/organization boundary: the attacker only ever authenticates as an org they legitimately administer, yet writes state belonging to another organization's stack.

### Likelihood Explanation
This requires only that the target Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker administers or controls one of those organizations' GitHub Apps (an "unprivileged attacker" relative to the victim organization — they hold no credentials, tokens, or access to the victim's resources). No `ApiClient` token, session, or GitHub write access to the victim repository is required — only knowledge of the attacker's own webhook secret, which they legitimately possess.

### Recommendation
Bind the verified signature's organization to every entity the handler subsequently mutates:
- Reject events where `repository.owner.login` / `organization.login` do not match the `Repository`'s known GitHub organization for the resolved `Stack`.
- In `StatusHandler`, scope the `Commit` lookup to commits whose `stack.repository.owner` equals the organization that authenticated the signature, not by `sha` alone.
- More generally, pass the authenticated organization from `verify_signature` into the handler and have `Handler#stacks`/`#repository_name` cross-check it against the resolved repository's actual owner before performing any writes.

### Proof of Concept
1. Operate a Shipit instance configured with two GitHub organizations, `attacker-org` (attacker-administered) and `victim-org` (target), per the multi-org `secrets.yml` layout. [4](#0-3) 
2. Attacker knows `attacker-org`'s `webhook_secret` (they configured it when creating their own GitHub App).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org-webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#repository_owner` returns `"attacker-org"`, `Shipit.github(organization: "attacker-org")` verifies successfully. [7](#0-6) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit — and calls `create_status_from_github!`, injecting a forged "success" status onto a commit in `victim-org`'s stack, independent of the organization that signed the request. [2](#0-1) 

Note: I was not able to fully trace `ContinuousDeliveryJob`/deploy-trigger internals within index limits to confirm every downstream side effect end-to-end; the analysis above is grounded directly in `Commit#deployable?`/`#schedule_continuous_delivery` and the handler/controller code cited. For complete verification of the downstream deploy path, a Devin session with full repository access would be needed.
