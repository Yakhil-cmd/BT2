### Title
Missing `--` separator in `git.(*Client).CheckoutBranch` allows attacker-controlled branch names to be parsed as git-checkout options - ([File: git/client.go])

### Summary
`CheckoutBranch` builds its argv as `[]string{"checkout", branch}` with no `--` end-of-options separator, unlike other functions in the same file (`ShowRefs`, `WorktreeRemove`, `IsIgnored`, `RemoteURL`) that consistently use `--` before untrusted path/ref arguments. A branch name beginning with `-` reaching this function is parsed by `git checkout` as an option rather than a ref name, enabling argument injection into `git checkout`.

### Finding Description
`(c *Client) CheckoutBranch` at [1](#0-0)  passes `branch` as a bare positional argument to `git checkout` with no `--` separator. This function is reached from `pkg/cmd/issue/develop/develop.go`'s `checkoutBranch()` at [2](#0-1) , where `checkoutBranch` (the ref name) originates from `api.CreateLinkedBranch`'s GraphQL mutation response field `mutation.CreateLinkedBranch.LinkedBranch.Ref.Name` [3](#0-2) , or from `api.ListLinkedBranches`'s `node.Ref.Name` field [4](#0-3) . Both values come directly from a GraphQL response with no validation that the name doesn't start with `-`.

By contrast, `CheckoutNewBranch` (`checkout -b <branch> --track <track>`) and `DeleteLocalBranch` (`branch -D <branch>`) are safe in this respect because the untrusted value is consumed as the direct value of an explicit flag (`-b`, `-D`), which git's option parser treats as a literal value regardless of a leading `-`, not as a new option token [5](#0-4) .

For `CheckoutBranch`, however, the branch name is the sole bare token after `checkout`, so `git` will parse it as an option if it starts with `-` (e.g., `--orphan`, `-b`, `--conflict=...`, `--pathspec-from-file=<file>` on newer git). No sanitization exists on the branch-name path (`ghrepo`/`ghinstance` host checks do not apply to ref-name content), and no `--` is inserted, unlike the safer patterns used elsewhere in the same file.

### Impact Explanation
This is best classified as an argument-injection / unexpected-behavior issue rather than direct remote code execution: git's `checkout` subcommand does not expose an option that trivially yields command execution or credential exfiltration by itself. Concretely demonstrable impacts are limited to denial of local operation (fatal errors from malformed option combinations), unexpected repository state changes (e.g., `--orphan` creating an orphan branch, `-f`/`--force` discarding local changes), or, on git versions supporting `--pathspec-from-file=<path>` / `--pathspec-file-nul`, reading an arbitrary local file's contents into a pathspec (information disclosure limited to whether patterns match, not a full file read/exfil channel). No sequence in this codebase was found where `CheckoutBranch`'s injected option can escalate to RCE or token disclosure, so the concrete verified impact is scoped to unexpected/incorrect checkout behavior and potential local file-content probing on newer git, not full compromise.

### Likelihood Explanation
Requires the attacker to control the GraphQL response for `createLinkedBranch`/`linkedBranches` (i.e., attacker controls, or has compromised, the GitHub Enterprise/host the victim points `gh` at), and the victim to run `gh issue develop <issue> --checkout` against that host with a local branch of the same name already existing (to hit the `HasLocalBranch` → `CheckoutBranch` branch instead of `CheckoutNewBranch`). This is a narrower precondition than plain PR-branch-name attacker control, since the primary listed call path (`developRunCreate`) largely relies on a malicious/compromised server response rather than an ordinary untrusted fork/PR branch name.

### Recommendation
Add the `--` end-of-options separator in `CheckoutBranch`: `args := []string{"checkout", "--", branch}` is incorrect for `checkout` since `--` there separates branches from pathspecs, not options from branches, in old git; the safe universal fix is to reject/validate branch names beginning with `-` before use (mirroring how other client.go functions already guard untrusted refs with `--`), or use `git checkout <branch> --` only after validating the name doesn't start with `-`. Apply consistent validation of ref/branch names returned from GraphQL (`Ref.Name`) before they are used to build any git argv.

func ListLinkedBranches(client *Client, repo ghrepo.Interface, issueNumber int) ([]LinkedBranch, error) {
	var query struct {
		Repository struct {
			Issue struct {
				LinkedBranches struct {
					Nodes []struct {
						Ref struct {
							Name       string
							Repository struct {
								Url string
							}
						}
					}
				} `graphql:"linkedBranches(first: 30)"`
			} `graphql:"issue(number: $number)"`
		} `graphql:"repository(owner: $owner, name: $name)"`
	}

	variables := map[string]interface{}{
		"number": githubv4.Int(issueNumber),
		"owner":  githubv4.String(repo.RepoOwner()),
		"name":   githubv4.String(repo.RepoName()),
	}

	if err := client.Query(repo.RepoHost(), "ListLinkedBranches", &query, variables); err != nil {
		return []LinkedBranch{}, err
	}

	var branchNames []LinkedBranch

	for _, node := range query.Repository.Issue.LinkedBranches.Nodes {
		branch := LinkedBranch{
			BranchName: node.Ref.Name,
			URL:        fmt.Sprintf("%s/tree/%s", node.Ref.Repository.Url, node.Ref.Name),
		}
		branchNames = append(branchNames, branch)
	}

	return branchNames, nil
}
