### Title
Cross-org webhook confusion: `repository.owner.login` used for signature verification diverges from `repository.full_name` used to select the Stack to mutate - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`WebhooksController#verify_signature` derives the org whose `webhook_secret` must match the HMAC solely from `payload['repository']['owner']['login']` [1](#0-0) , while `Handler#stacks`/`#repository_name` resolves the target `Repository`/`Stack` solely from `payload['repository']['full_name']` [2](#0-1) . These two fields are never cross-checked for consistency, so a payload can be legitimately signed under one org's secret while it targets a completely different org's repository/stack.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`org_that_signed_the_payload (params.dig('repository','owner','login'))` == `org_whose_stack_is_mutated (params.dig('repository','full_name').split('/').first)`

Trace:
1. `WebhooksController#create` parses the raw JSON body and, before dispatching to handlers, runs `verify_signature`, which computes `repository_owner` from `params.dig('repository','owner','login')` (or `organization.login`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [3](#0-2) . This only proves the request was signed with *that org's* secret - it says nothing about which repository the payload's other fields describe.
2. `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [4](#0-3) .
3. `Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` [2](#0-1) , and `Repository.from_github_repo_name` simply splits that string on `/` and does a DB lookup with no relation to `repository.owner.login` [5](#0-4) .

Because nothing enforces `repository.full_name.split('/').first == repository.owner.login`, an attacker who owns `org-attacker` (and thus legitimately possesses `org-attacker`'s real `webhook_secret`) can craft:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/other-repo"
  }
}
```
and sign it with `org-attacker`'s secret. `verify_signature` passes (it only checks the org-attacker secret against the org-attacker login field). `PushHandler#stacks` then resolves `org-victim/other-repo`'s real `Stack`(s) on branch `master` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on each non-archived one, writing an attacker-chosen SHA as the expected head for a repository the attacker never authenticated against and does not own.

None of the listed guards prevent this: `verify_signature` checks only the org-attacker's own secret against the org-attacker login it itself reads from the payload; `drop_unhandled_event`/`check_if_ping` are unrelated; the `ExplicitParameters` schema for `PushHandler` only requires `ref` and `after` and does not constrain `repository.owner.login` vs `repository.full_name` [6](#0-5) ; `Repository` model validations only constrain `owner`/`name` format of *stored* repositories, not incoming payload consistency [7](#0-6) .

### Impact Explanation
This is a cross-repository/cross-tenant write: a payload authenticated for `org-attacker` mutates the `Stack` belonging to `org-victim`, forcing `Stack#sync_github` to treat an attacker-chosen SHA as the expected head commit for `org-victim/other-repo` on the `master` branch. Since `sync_github` drives what commit becomes the stack's head (and subsequently deployable), this is a repository-boundary violation matching the "payload for one repository mutating another's stack" Critical category. It is repeatable against any Shipit-tracked repository/branch as long as the attacker knows (or guesses) its `owner/name` and it is not archived; the attacker needs no privilege on `org-victim` at all, only ownership of some org already registered with Shipit (`org-attacker`) with its own valid `webhook_secret`.

### Likelihood Explanation
Preconditions are modest and plausible in any multi-org Shipit deployment: the attacker must control at least one GitHub org/app registered in Shipit (so they legitimately hold that org's `webhook_secret`), and the victim repository must have a non-archived `Stack` tracking a known branch. No Shipit session, API token, or GitHub write access to the victim repo is required - only the ability to POST an arbitrary JSON body with a valid `X-Hub-Signature` computed from the attacker's own secret. This is fully within the unprivileged attacker model described (an internet user who can send `POST /webhooks` and who owns/administers `org-attacker`).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the org used to select the verifying secret matches the org embedded in `repository.full_name`, e.g. reject the request if `params.dig('repository','owner','login')&.downcase != params.dig('repository','full_name').to_s.split('/').first&.downcase`. Alternatively, derive both the verifying org and the target repository from a single trusted field (`full_name`) rather than two independently attacker-controlled JSON fields.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub - stub `Shipit.github`):
```ruby
test "push webhook signed by org-attacker cannot mutate org-victim's stack" do
  victim_stack = shipit_stacks(:shipit) # repository owner "org-victim", name "other-repo", branch "master", not archived
  attacker_secret = "attacker-org-secret"
  Shipit.stubs(:github).with(organization: "org-attacker").returns(
    stub(verify_webhook_signature: true) # simulates attacker's real, valid secret
  )

  payload = {
    ref: "refs/heads/master",
    after: "deadbeefattackersha",
    repository: {
      owner: { login: "org-attacker" },
      full_name: "org-victim/other-repo"
    }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, payload)

  Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: "deadbeefattackersha")

  post :create, body: payload,
       headers: { "X-Github-Event" => "push", "X-Hub-Signature" => signature }

  assert_response :ok
end
```
Assertion on both sides of the binding: `params.dig('repository','owner','login')` ("org-attacker", used to select the verifying secret) must be shown to differ from `params.dig('repository','full_name').split('/').first` ("org-victim", used to select the mutated Stack), and the test proves `sync_github` still runs with the attacker's `after` value despite that mismatch - demonstrating the equality the system should enforce is currently unchecked.
