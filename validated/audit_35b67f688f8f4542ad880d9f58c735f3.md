### Title
Stack-scoped API token bypasses its `stack_id` restriction in `CCMenuController#stack` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a non-nil `stack_id`) can only resolve `stack`/`stacks` to the single `Stack` it was scoped to, via `stacks` filtering by `current_api_client.stack_id`. `CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely skipping that scoping filter, so any stack-scoped token can read CI/deploy status for any stack in the installation, not just the one it was authorized for.

### Finding Description
`Shipit::Api::BaseController` defines the intended trust boundary between an `ApiClient`'s authorized stack and the stacks it may touch: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Permission checks (`require_permission`) only verify that the client's `permissions` array contains the operation/scope string (e.g. `read:stack`) via `ApiClient#check_permissions!`; they never verify which stack ID is being accessed: [2](#0-1) 

The actual "which stack can this token see" enforcement lives entirely in `BaseController#stacks`/`#stack`. `Shipit::Api::CCMenuController`, however, overrides `stack` to bypass that scoping entirely: [3](#0-2) 

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
```

This is the exact binding break described by the rules: "a stack a token authorises versus a stack it touches." A token minted for stack A (via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator:, stack: A)` as used by `CCMenuUrlController`) is authorized only for stack A, but `CCMenuController#show` will happily resolve and render any stack B simply because the attacker changes the `stack_id` route param — the code path never consults `current_api_client.stack_id`. [4](#0-3) 

### Impact Explanation
Any holder of a legitimately-issued, narrowly-scoped `read:stack` CCMenu token (e.g. handed out to a CI dashboard/status-monitor integration for one specific stack) can enumerate and read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity) for every stack in the Shipit installation, including stacks belonging to other repositories/teams they were never granted access to. This matches the in-scope High-severity impact: "unauthenticated read of stack state, task streams, or deploy output" via escalation of a scoped credential beyond its intended authorization boundary.

### Likelihood Explanation
High. Exploitation requires only a single valid `read:stack`-scoped `ApiClient` token that a user or integration was legitimately given for one stack (these tokens are handed to third parties routinely, e.g. via `CCMenuUrlController#fetch`, embedded in CI dashboards, CCMenu/CCTray clients, etc.). No signature forgery, GitHub credentials, or additional privileges are needed — just changing the `stack_id` URL parameter on an authenticated GET request.

### Recommendation
Make `CCMenuController#stack` use the scoped `stacks` helper from `BaseController` instead of calling `Stack.from_param!` directly, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

so that a stack-scoped `ApiClient` cannot resolve any `stack_id` other than the one it is bound to.

### Proof of Concept
1. As an authorized user, create (or have Shipit auto-create via `CCMenuUrlController#fetch`) a `read:stack`-scoped `ApiClient` bound to `stack: shipit` (`stack_id` set), e.g. fixture `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml` (`stack: shipit`, `permissions: ['read:stack']`).
2. Grab its `authentication_token`.
3. Issue: `GET /api/stacks/<other_owner>/<other_repo>/<other_environment>/cc.xml?token=<here_come_the_walrus_token>`
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (not the client-scoped `stacks.from_param!`), the request succeeds and returns build/deploy status for `<other_owner>/<other_repo>/<other_environment>`, a stack the token was never authorized to see — confirmed by contrast with `BaseController#stacks`, which every other API controller (e.g. `Api::StacksController`, `Api::DeploysController`) relies on to correctly restrict scoped tokens to their bound stack.
