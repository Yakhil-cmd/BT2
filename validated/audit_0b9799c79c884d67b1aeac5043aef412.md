### Title
Router/Node crash from unhandled `throw Error()` in private-asset transfer validation when `src_coin` context is inapplicable/missing - (File: validation.js)

### Summary
The MongoDB advisory describes a crash that occurs when a generic argument (`lsid`) is supplied in a context where it is not applicable, and the server does not gracefully reject it but instead crashes. `ocore`'s unit validator has an analogous pattern in `validatePaymentInputsAndOutputs()`: for `"transfer"` payment inputs belonging to private, fixed-denomination assets, the code assumes a specific piece of pre-populated validation context (`objValidationState.src_coin`) is always present and well-formed, and if it is not, it does not return a normal validation error through the callback — it synchronously `throw`s an `Error`, which is not caught anywhere in this branch of the async control flow.

### Finding Description
In `validation.js`, when validating a `"transfer"` input for an asset that is both `is_private` and `fixed_denominations`, validation deliberately bypasses the normal database lookup of the source output (because private-chain validation happens entirely off the normal database record) and instead relies on `objValidationState.src_coin` being prepopulated by the caller: [1](#0-0) 

If `objValidationState.src_coin` is missing, or if it is present but missing `src_output`, `denomination`, or `amount`, the code does not call `cb(errorMessage)` (the normal, safely-handled validation-failure path used everywhere else in this function) — it instead does a synchronous `throw Error(...)`. Every other malformed-input check surrounding this exact block (e.g. `hasFieldsExcept`, `isStringOfLength`, `isNonnegativeInteger` checks a few lines above) correctly returns a soft error via `cb(...)`, showing that this is an aberration: a generically-expected internal invariant is instead enforced with a hard `throw`, exactly like MongoDB's improper handling of a field that is not applicable to the given code path.

This validation runs inside `validatePaymentInputsAndOutputs`, itself invoked from `validateMessage` → `validateMessages`, which is called from the main `validate()` unit-validation entry point that is reachable by any unprivileged unit poster, and specifically by any private-payment counterparty processing a private-asset payment chain sent to them by another party (the exact scenario `is_private && fixed_denominations` targets, per the comment "for private fixed denominations assets, we can't look up src output in the database because we validate the entire chain before saving anything... we prepopulate objValidationState with denomination and src_output").

The codebase's own `network.js` acknowledges the general risk that validation can crash and takes explicit measures around it (rather than treating it as impossible): [2](#0-1) 

That comment ("clear host only if validation completed with any result, otherwise it crashed and we keep it for a while to avoid DoS from the same peer") shows the maintainers are aware that unhandled exceptions inside `validation.js` can propagate out of the `validate()` call and crash the node process (or at minimum leave it in an inconsistent locked state), which is functionally the same failure mode as the MongoDB router crash: an argument/context that is inapplicable for the given input combination is not rejected gracefully but instead triggers an unhandled fatal exception.

### Impact Explanation
An unhandled `throw` deep inside unit validation, triggered by unexpected/missing internal state for a specific asset+input-type combination, can crash the node process handling that unit (or corrupt in-flight validation state / leave locks unreleased), which maps to "a network unable to confirm new units" if triggered broadly, or at minimum a targeted denial-of-service against any single peer/wallet that attempts to validate the crafted private-asset chain — satisfying the "node disagreement on validity or stability" / crash class the rules require.

### Likelihood Explanation
The trigger conditions are asset-attribute–gated (`is_private && fixed_denominations`) and depend on `objValidationState.src_coin` prepopulation logic that lives in `indivisible_asset.js` (only one reference found), which I was not able to fully trace within the available tool budget to construct a concrete, minimal malicious private-chain unit that reaches `validatePaymentInputsAndOutputs` with `src_coin` unset/malformed. This limits confidence in exact exploitability versus purely being a defensive/unreachable assertion.

### Recommendation
Replace all `throw Error(...)` calls inside `validatePaymentInputsAndOutputs`'s private/fixed-denomination transfer branch (`"no src_coin"`, `"no src_output"`, `"no denomination in src coin"`, `"no src coin amount"`, and the sibling `"more than 1 src output"` / `"spending a stable temp-bad output"` throws in the same function) with normal `cb(errorMessage)` / `callback(errorMessage)` invocations, consistent with every other validation failure in this function, so that malformed or unexpected private-chain input data results in a graceful unit-rejection instead of an unhandled process-level exception.

### Proof of Concept
Not fully constructed — would require crafting a private, fixed-denomination asset transfer chain (via `indivisible_asset.js`'s chain-composition/validation flow) such that the wallet validating an incoming private payment reaches the `"transfer"` case in `validatePaymentInputsAndOutputs` for that asset without `objValidationState.src_coin` being populated (e.g., by desynchronizing the transfer input from the chain object the receiving wallet used to build its `src_coin` map). I could not fully verify this specific reachability within the tool-call budget available; this should be treated as a plausible but not fully confirmed analog, and the exact crafting of the malicious private-chain payload needs verification directly in `indivisible_asset.js`.
