### Title
AA payment batches can be permanently frozen by a `spender_attested` asset when one output address is unattested - ([File: aa_composer.js])

### Summary
The reported Sherlock issue is about `CrabNetting.sol` looping through a FIFO queue of withdrawers and calling `usdc.transfer()` to each; if one recipient is USDC-blacklisted, that single `transfer()` reverts and the whole `netAtPrice`/`withdrawAuction` loop reverts, jamming the withdrawal queue for every user behind the blacklisted one. The oscript/AA analog in `ocore` is the interaction between AA response-payment composition in `aa_composer.js` and the `spender_attested` asset-transfer validation rule enforced in `validation.js`. An asset definer can act as a "blacklist" authority via the attestor list, and — unlike a normal single-recipient payment — an AA that batches multiple outputs of the same `spender_attested` asset into one payment message has no way to skip only the denied address: the entire message (and hence the whole trigger response) is rejected/bounced when even one output address is unattested, freezing funds intended for all other (unaffected) recipients in that batch, indefinitely, until the definer re-attests the frozen address.

### Finding Description
When an AA (autonomous agent) composes its response payment, it builds one payment message per asset containing all the outputs computed by the oscript for that trigger: [1](#0-0) 
For non-fixed-denomination assets it calls `loadAssetWithListOfAttestedAuthors` to fetch the asset's attestation settings, but this pass performs no per-output attestation filtering of the AA's own outputs — it only checks whether the AA (sender) is attested via `arrAttestedAuthors`, then completes the payload and queues the message: [2](#0-1) 

The actual enforcement of "every output address must be attested" happens later, at unit validation time (`validateAndSaveUnit`), which calls `validatePaymentInputsAndOutputs`. There, for a `spender_attested` asset, **all** output addresses collected across the message must pass `storage.filterAttestedAddresses`, or the entire payment (and therefore the whole unit) is rejected: [3](#0-2) 

Back in `aa_composer.js`, if `validateAndSaveUnit` fails for any reason (including "some output addresses are not attested"), the AA response is bounced as a whole: [4](#0-3) 

Because the entire payment message — potentially containing outputs to many legitimate, still-attested recipients — is bounced together with the one denied output, an AA whose oscript logic distributes a `spender_attested` asset to a set of addresses in a single message (e.g., dividend/airdrop/reward-distribution style logic, analogous to Crab's withdrawal queue that sends to multiple withdrawers per call) cannot make partial progress: as long as the batch includes even one address whose attestation has been revoked by the asset definer, every attempt to run that distribution logic bounces, and the AA's balance of that asset (and the bytes needed to cover bounce fees) is stuck. Unlike a plain user-to-user payment (where the sender chooses recipients and can simply drop the bad one before broadcasting), the AA's oscript-computed output set is deterministic state, so the AA keeps regenerating the same doomed message on every trigger until the state/queue itself is changed — the AA has no built-in mechanism (analogous to the report's proposed `cancelBlacklistedWithdraws`) to detect and skip a denied recipient before composing/sending.

### Impact Explanation
This is a fund-freezing condition reachable purely by an ordinary, in-scope actor: an asset definer maintains authority to revoke `spender_attested` status from any address at any time via the `asset_attestors`/attestor-list update message (a normal application message any address controlling the asset's attestor list can post). Once a previously-attested address that participates in an AA's queued/batched distribution logic for that asset is de-attested, all subsequent AA responses that would pay out that asset to the group containing the de-attested address bounce entirely. This blocks legitimate, unrelated recipients in the same batch from ever receiving their share, and can permanently strand the AA's asset balance (an AA fund-freezing outcome), matching the "Medium" severity class of the source report (contract functionality broken / funds stuck for non-blacklisted parties) rather than any p2p/network/light-client issue.

### Likelihood Explanation
The precondition (existence of a `spender_attested` asset whose AA-controlled distribution batches multiple outputs together, and an attestor later revoking one recipient) is entirely within normal, documented asset/AA functionality — no malicious peer, hub, or protocol-level attacker is required, only the standard attestor-revocation right that `spender_attested` assets already grant to their definer/attestors. Any AA author building pooled payout/distribution/vesting logic on top of a `spender_attested` asset is exposed to this by design, and the freezing is triggered by ordinary application messages (asset definition, attestor updates, and AA triggers), all reachable by unprivileged posters.

### Recommendation
Provide oscript/AA-level primitives (or built-in AA-composer support) to let an AA determine, before composing a payment, whether a given output address is currently attested for a `spender_attested` asset (e.g., an `is_attested(address, asset)` bound function), so an AA can skip or defer payouts to de-attested addresses instead of bundling them with unaffected recipients in one all-or-nothing message. Alternatively, consider allowing partial output filtering at validation time for AA response messages composed of independent per-recipient outputs, similar to the report's suggested "cancel/skip the blacklisted entry, keep processing the rest" pattern, so one denied recipient cannot block payouts to everyone else in the same batch.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true`, `is_transferrable: true`, and publishes an initial attestor list including attestor `T`.
2. Attestor `T` attests addresses `U1`, `U2`, `U3` (all users of an AA `D` that periodically distributes asset `A` it holds to a list of stakeholder addresses stored in AA state, sending one payment message with outputs to `U1`, `U2`, `U3` in a single trigger response — analogous to Crab's per-call multi-withdrawer payout).
3. AA `D` successfully distributes asset `A` to `U1`, `U2`, `U3` in one response unit while all three are attested (validated via `validatePaymentInputsAndOutputs` → `filterAttestedAddresses` at [5](#0-4)  passing because `arrAttestedOutputAddresses.length === arrOutputAddresses.length`).
4. Attestor `T` (or the definer) posts an `asset_attestors` update that stops attesting `U2` (revocation is a normal application message, no special privilege beyond being the current attestor).
5. On the AA's next trigger that attempts to distribute asset `A` again to `U1, U2, U3` (oscript-driven output set unchanged), `aa_composer.js` composes the same three-output payment message per [2](#0-1) , but `validateAndSaveUnit` now fails at [6](#0-5)  ("some output addresses are not attested") because `U2` is no longer attested.
6. The trigger bounces entirely per [4](#0-3) , meaning `U1` and `U3` (still attested, uninvolved in the revocation) also receive nothing, and this repeats on every subsequent trigger attempt as long as `U2` remains part of the batch and de-attested — freezing the AA's asset balance meant for all three users.
