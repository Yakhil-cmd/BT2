### Title
Webhook authentication is keyed to `repository.owner.login` while event dispatch is keyed to `repository.full_name`, letting an unauthenticated attacker forge events against any stack by impersonating a differently-configured organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify the HMAC signature against using `repository.owner.login` taken from the attacker-supplied JSON body. `Handler#repository_name`, used by every event handler (push, status, check_suite, membership, etc.) to decide which `Stack`/`Repository` the event actually acts on, uses a *different* field of the same body: `repository.full_name`. These two fields are never cross-checked against each other, so the "identity that is authenticated" and the "repository that is written to" are decoupled — the same binding-break pattern as the referenced report, where the address checked (`who`) was not bound to the token actually moved.

### Finding Description
`verify_signature` computes the authenticating organization purely from the payload: [1](#0-0) [2](#0-1) 

It then fetches that organization's GitHub App config and verifies the signature with `github_app.verify_webhook_signature`, which explicitly returns `true` — bypassing HMAC verification entirely — whenever that organization has no `webhook_secret` configured: [3](#0-2) 

A blank `webhook_secret` per-organization is a documented, first-class configuration in this engine's multi-org setup files, not an operator misconfiguration outside scope: [4](#0-3) 

Once signature verification passes (trivially, for the no-secret org), `create` re-parses the same raw body and dispatches it to handlers: [5](#0-4) 

Every handler determines the target repository/stack from an entirely different payload field, `repository.full_name`, with no relation to `repository.owner.login` used above: [6](#0-5) [7](#0-6) 

Because nothing ties `repository.full_name` to `repository.owner.login`, an unauthenticated attacker can:
1. Set `repository.owner.login` to an organization configured in `Shipit.github` with no `webhook_secret` (authentication for the request trivially passes per `verify_webhook_signature`'s `return true unless webhook_secret`).
2. Set `repository.full_name` (and any other repository fields the handler reads) to `"victim-org/victim-repo"`, a different, properly-secret-protected organization's repository.
3. The handler acts on the victim stack (e.g. `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)`, `StatusHandler`/`CheckSuiteHandler` fabricate CI state) without ever having the victim org's `webhook_secret`.

### Impact Explanation
This crosses a repository/organization authentication boundary: an attacker with zero credentials for `victim-org` can inject forged GitHub events (push refs, commit statuses, check-suite results, team membership changes) into stacks belonging to `victim-org`, purely by exploiting the fact that a co-tenant org in the same Shipit installation has no webhook secret configured. Forged `status`/`check_suite` events can fabricate passing CI on arbitrary SHAs, which Shipit's deploy-gating logic (`ci.require`) consults before allowing a deploy — enabling an unauthorized deploy path, and constituting a cross-repository/cross-organization write into stack state that the attacker was never authorized to touch.

### Likelihood Explanation
Any Shipit installation configured for multiple GitHub organizations (a supported, documented setup shipped with example config files in this engine) where at least one organization's `webhook_secret` is left unset is exploitable by any unauthenticated internet client with a single crafted HTTP POST — no session, API token, or GitHub credentials of any kind are required.

### Recommendation
Bind authentication and dispatch to the same value: derive the organization used for both HMAC verification and repository lookup from a single, consistently-sourced identifier (e.g., always resolve via `repository.full_name`'s owner segment, or vice versa), and reject the request if `repository.owner.login` and the owner segment of `repository.full_name` disagree. Additionally, consider refusing to treat a missing `webhook_secret` as "verification passed" and instead require an explicit `insecure_webhooks: true` opt-in per organization.

### Proof of Concept
1. Configure Shipit with two orgs: `org-a` (`webhook_secret: nil`) and `org-b` (`webhook_secret: "s3cr3t"`, has stack `org-b/app`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/app"
  }
}
```
No `X-Hub-Signature` header, or an arbitrary one, is required.
3. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s app config, and `verify_webhook_signature` returns `true` immediately because `org-a.webhook_secret` is blank.
4. `PushHandler#process` resolves `repository_name` = `"org-b/app"` via `Handler#repository_name`, finds `org-b`'s stack, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` — a forged event injected into `org-b`'s stack without ever presenting `org-b`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
