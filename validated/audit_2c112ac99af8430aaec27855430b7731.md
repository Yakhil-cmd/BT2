### Title
Webhook organization/repository binding confusion allows unauthenticated event forgery against any Shipit-managed repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to validate a webhook against using an attacker-controlled field inside the unverified JSON body (`repository.owner.login`), while the handlers that actually mutate application state (sync commits, post statuses, process pull requests) resolve the target `Stack`/`Repository` from a *different*, never-cross-checked field (`repository.full_name`). If any organization configured in the Shipit instance has no `webhook_secret` set — which the project's own setup docs describe as optional — signature verification is skipped entirely for payloads claiming to originate from that organization, letting a fully unauthenticated attacker forge webhook events that write into any *other* organization's repository/stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GithubApp` instance (and therefore the secret used for HMAC verification) based on `repository_owner`, which is read straight out of the untrusted JSON payload: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever that organization has no configured secret: [3](#0-2) 

The project's own setup documentation explicitly marks `webhook_secret` as optional, so an organization with no secret configured is a supported, documented deployment state, not a misconfiguration: [4](#0-3) 
and the sample multi-org secrets file shows exactly this pattern (`webhook_secret: # nil`) alongside other organizations that do have secrets: [5](#0-4) 

Once the controller decides the payload is "verified" (or verification is skipped because the claimed org has no secret), it dispatches the *entire raw payload* — including the real `repository.full_name` — to the event handlers: [6](#0-5) 

Every handler resolves the actual `Stack`/`Repository` to mutate from `payload.dig('repository', 'full_name')`, which is completely independent of the `repository.owner.login` field used earlier to select the verification secret: [7](#0-6) 

For example, `PushHandler` uses this repository resolution to trigger a GitHub sync job for the matching stacks: [8](#0-7) 

**The broken binding (as an equality):**
`organization whose secret validated the webhook signature` should equal `organization owning the repository that the handler actually mutates`. In this engine, the first value is derived from `repository.owner.login` (attacker-controlled, and trivially satisfiable with no secret at all if that org has none configured), while the second value is derived from `repository.full_name` (also attacker-controlled, and never checked against the first). Nothing enforces that these two fields refer to the same repository/organization.

### Impact Explanation
An attacker with no Shipit session, no API token, and no GitHub credentials can send a POST to `/webhooks` with a body such as:
```json
{
  "repository": { "owner": { "login": "org-without-secret" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
with header `X-Github-Event: push` and no valid `X-Hub-Signature` at all (or any arbitrary value), as long as `org-without-secret` is one of the organizations configured in `Shipit.github` without a `webhook_secret`. Because `verify_signature` looks up the app for `org-without-secret` and `verify_webhook_signature` returns `true` unconditionally for orgs without a secret, the request is accepted and dispatched to `PushHandler`, which resolves stacks for `victim-org/victim-repo` — an organization/repository that never authenticated this request at all — and forces `stack.sync_github(expected_head_sha: ...)`. The same confusion applies to `status`, `check_suite`, `membership`, and `pull_request` handlers, enabling spoofed commit statuses, fake check-run results, and forged pull-request/merge events against a target repository the attacker never authenticated against, potentially influencing deploy eligibility and stack state for repositories entirely unrelated to the (unsecured) organization the attacker abused.

### Likelihood Explanation
Exploitability depends only on a documented, officially-supported configuration state (an org with no `webhook_secret`) existing anywhere in the Shipit deployment's `Shipit.github` config; no compromise of credentials, sessions, or tokens is required. Any operator following the setup docs literally ("Webhook secret (optional)") and configuring more than one organization, only one of which has a secret, is exposed. Likelihood is therefore Medium: it requires no attacker privilege at all but does require this specific (documented) multi-org configuration shape to be present.

### Recommendation
Do not select the verification secret from an unauthenticated field of the payload being verified. Instead, verify webhook signatures against every organization's configured secret (or the secret tied to the repository actually referenced by `repository.full_name`) and require a match; if a candidate organization has no secret configured, do not treat that as an automatic pass when other organizations in the same instance do have secrets. Additionally, cross-check `repository.owner.login` against `repository.full_name` before dispatching to handlers, and consider rejecting all unsigned webhooks whenever any organization in the installation defines a `webhook_secret`, to avoid the "weakest configured org" bypassing protection for all others.

### Proof of Concept
1. Configure a Shipit instance with two organizations under `Shipit.github`: `victim-org` (has `webhook_secret` set) and `attacker-org` (no `webhook_secret`, per the documented-optional setting) — see `app/controllers/shipit/webhooks_controller.rb` lines 24-30 and `lib/shipit/github_app.rb` lines 76-83.
2. Attacker (no session, no token) sends:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `verify_webhook_signature` returns `true` because `attacker-org` has no secret (`app/controllers/shipit/webhooks_controller.rb` lines 24-30; `lib/shipit/github_app.rb` lines 76-83).
4. `create` dispatches the payload to `PushHandler`, which resolves `victim-org/victim-repo`'s stacks via `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb` lines 32-38) and calls `stack.sync_github(expected_head_sha: "deadbeef...")` (`app/models/shipit/webhooks/handlers/push_handler.rb` lines 12-17) — mutating state for a repository the attacker never authenticated a webhook for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
