### Title
Webhook signature verification is keyed to an unvalidated `repository.owner.login`, letting any configured GitHub organization forge commit statuses on another organization's commits - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
The `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature against purely from an attacker-controlled field inside the *same* unauthenticated JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

This satisfies the equality "the signature is valid for organization X's secret" ⇒ "the request came from GitHub for organization X's installation". It does **not** establish "the data acted upon by the downstream handler belongs to organization X." In a multi-organization Shipit deployment (`Shipit.github(organization:)` supports per-organization `webhook_secret`s, see `lib/shipit.rb#github` and `docs/setup.md` "Using Multiple Github Applications"), each configured organization owns its own independent secret. [3](#0-2) 

`Shipit::Webhooks::Handlers::StatusHandler`, invoked after signature verification succeeds, never re-derives or checks the organization/repository at all. It looks up the target `Commit` purely by SHA, globally, across every stack/repository registered in the whole Shipit instance: [4](#0-3) 

and `Commit#create_status_from_github!` unconditionally writes the attacker-supplied `state`/`description`/`context` as a new status on that commit: [5](#0-4) 

Thus, the binding actually enforced is `{signature valid} = {sender knows OrgX's webhook_secret}`, while the binding required for safety is `{signature valid for OrgX} = {commit written belongs to a repository owned by OrgX}`. Because `StatusHandler` never consults `repository.full_name`/owner at all, the org-scoped signature check provides no isolation between tenants once a matching SHA exists in any other org's stack. Since git commit SHAs are deterministic content hashes, an attacker who forks/mirrors a target repository into an organization they control (and which is configured with its own GitHub App/webhook secret in Shipit) will have identical commit SHAs for shared history, and can craft a `status` webhook payload directly against Shipit's `/webhooks` endpoint, signing it with their own org's known secret.

### Impact Explanation
A forged, HMAC-valid `status` event lets an unprivileged-relative-to-the-victim attacker inject a fabricated `success` status onto a commit belonging to a stack owned by a different, unrelated GitHub organization configured on the same Shipit instance. `Commit#deployable?` and `Commit#blocked?`/`Status::Group` gate whether a commit is eligible for deploy based on stored statuses: [6](#0-5) [7](#0-6) 

and `Commit#schedule_continuous_delivery` triggers `ContinuousDeliveryJob` when a commit becomes `deployable?` under continuous deployment: [8](#0-7) 

An attacker who forges a passing CI status for a commit that real CI has not (yet) passed, or that is blocked, can therefore cause an **unauthorized deploy** of that commit on the victim organization's stack — this matches the explicitly in-scope Critical impact "an unauthorized deploy."

### Likelihood Explanation
Exploitation requires: (1) the target Shipit instance to be configured with more than one GitHub organization (documented, supported multi-tenant configuration), (2) the attacker to control (or be a member with access to) one of those other configured organizations' webhook secret, and (3) a SHA collision with the victim commit, achievable trivially by forking/mirroring the victim's public repository so the shared history has identical commit hashes. All three conditions are realistic in a shared/hosted Shipit deployment serving multiple orgs, and require no privileged Shipit account, GitHub token, or webhook secret belonging to the victim organization — only the attacker's own, already-authorized org credentials. This is a boundary-crossing exploit strictly through the engine's own webhook-handling code, not a misconfiguration or missing deployment step.

### Recommendation
Bind the authenticated organization to the data acted upon:
- Include the resolved `repository_owner`/organization used for signature verification when resolving handler targets, and reject/ignore any handler action (in particular `StatusHandler`, and any other handler that resolves records without checking `repository.full_name`) whose payload's repository does not belong to the authenticated organization.
- In `Shipit::Webhooks::Handlers::Handler`, expose the verified organization and require subclasses (especially `StatusHandler`) to scope commit/stack lookups by `Repository.from_github_repo_name` and assert the `Repository#owner` matches the organization whose secret validated the request, instead of matching on `sha` alone.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (victim, has a registered stack/repository `OrgA/app`) and `OrgB` (attacker-controlled, e.g. a legitimate customer or business unit sharing the same Shipit instance), per `docs/setup.md` "Using Multiple Github Applications".
2. Attacker forks `OrgA/app` into `OrgB/app-fork`; the forked commit `SHA` is identical, since git history/content hashes are unchanged by forking.
3. Attacker computes `sha1=HMAC-SHA1(OrgB_webhook_secret, body)` for a crafted body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgB" } }
}
```
4. Attacker `POST`s this to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgB")` and validates successfully (the attacker legitimately knows `OrgB`'s secret). [1](#0-0) 
6. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against the victim's `OrgA/app` commit (no org/repo check) and calls `create_status_from_github!`, writing a forged `success` status onto a commit in a stack the attacker never had access to. [4](#0-3)

    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)

    @github[organization] ||= GitHubApp.new(organization, config)
  end
