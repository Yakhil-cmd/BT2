### Title
Operator-precedence bug in `provision?` bypasses `repository.review_stacks_enabled` gate - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`PullRequest::OpenedHandler#provision?` combines `review_stacks_enabled` and the three provisioning-behavior predicates with mixed `&&`/`||` without parentheses, so Ruby's `&&`-before-`||` precedence only applies `review_stacks_enabled` to the `allow_all?` branch. When `provisioning_behavior` is `allow_with_label` (or `prevent_with_label`), the operator-set `review_stacks_enabled == false` gate is never consulted, and a review stack is created anyway.

### Finding Description
The binding claimed by the operator is: `repository.review_stacks_enabled` (an explicit opt-in flag set by a Shipit operator/maintainer, defaulting to disabling all PR-driven review-stack creation) should equal the boolean actually gating `ReviewStackAdapter#create!`. Tracing the code: [1](#0-0) 

`respond_to_pull_request_opened?` calls `provision?`, which is written as:
```
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
Because `&&` binds tighter than `||`, this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So when `review_stacks_enabled == false` and `provisioning_behavior == :allow_with_label`, the second disjunct alone (`allow_with_label? && has_label?`) can make `provision?` return `true`, entirely independent of `review_stacks_enabled`.

`pull_request_has_provisioning_label?` matches purely on the `labels[].name` string sent in the webhook payload: [2](#0-1) 

Any PR author on the tracked repo (or anyone able to add that specific label to their own PR — labels are repo-scoped, and the label is chosen by the operator, e.g. `deploy-review`) triggers a genuine GitHub `pull_request.opened` (or the same predicate is reused by `LabeledHandler`) webhook carrying that label. This webhook is legitimately signed by GitHub because it reflects a real event on a real, tracked repository — `verify_webhook_signature` therefore does not block this path since no forgery is required.

When `provision?` returns `true`, `process` unconditionally calls: [3](#0-2) 
which invokes `ReviewStackAdapter#find_or_create!` → `create!`, creating a `Shipit::ReviewStack` and pushing it into `ReviewStackProvisioningQueue`: [4](#0-3) 

Nothing downstream re-checks `review_stacks_enabled` before this queue add/provisioning — the flag is only consulted inside the buggy `provision?` expression.

### Impact Explanation
An attacker who can open a pull request and apply a single (operator-named) label on a tracked repository can force Shipit to create and provision a `Shipit::ReviewStack` for that repository even though the repository owner explicitly disabled review stacks (`review_stacks_enabled == false`). This is a record written and a provisioning/deploy pipeline started for a repository against its owner's explicit configuration, matching "unauthorized deploy" impact. It is repeatable per PR/label combination and only affects repositories configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) while `review_stacks_enabled` is false — it does not cross into other repositories' stacks, but it defeats the intended operator-level kill switch for review-stack provisioning on the affected repository.

### Likelihood Explanation
Preconditions: the repository must have `review_stacks_enabled == false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (an operator misconfiguration/edge-case, since the two settings appear semantically contradictory but nothing in the model prevents this combination — no validation ties them together in `app/models/shipit/repository.rb`). Attacker cost is trivial: open a PR and add the named label, both ordinary unprivileged GitHub actions on their own PR. No secrets, sessions, or elevated GitHub permissions are needed.

### Recommendation
Parenthesize the boolean expression in `provision?` so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to any other handler reusing this exact expression (e.g. `LabeledHandler`, `ReopenedHandler`, `UnlabeledHandler`) if they replicate the pattern.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style (minitest):
```ruby
test "does not provision a review stack when review_stacks_enabled is false, even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: "allow_with_label",
    provisioning_label_name: "deploy-review"
  )

  payload = pull_request_opened_payload(repository: repository, labels: [{ name: "deploy-review" }])

  assert_no_difference "Shipit::Stack.count" do
    handle_webhook_delivery("pull_request", payload)
  end
end
```
Before the fix: `Shipit::Stack.count` (via `ReviewStack`) increases despite `review_stacks_enabled == false`, demonstrating `provision?` returns `true` through the `allow_with_label?` disjunct regardless of the leading `review_stacks_enabled &&` term. After applying the parenthesization fix, the assertion holds.
