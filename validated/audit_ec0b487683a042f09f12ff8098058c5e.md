### Title
Cross-organization commit status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to check against using only `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body, and authorizes the whole request based on that org matching. But `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that organization when it acts on the payload: it looks up commits purely by `sha`, with no scoping to the repository/stack that org actually owns. The organization that authenticated the request and the stack whose state gets mutated are two different things, and nothing binds them together.

### Finding Description
The webhook signature check picks the GitHub App configuration (and thus the HMAC secret) to validate against dynamically from the payload: [1](#0-0) 

`repository_owner` is derived straight from the request body: [2](#0-1) 

Shipit explicitly supports multiple independent GitHub organizations configured under one installation, each with its own (optional) `webhook_secret`: [3](#0-2) 

`verify_webhook_signature` even treats a missing secret for an organization as automatically valid: [4](#0-3) 

Once the request passes verification for *whatever organization the attacker names in the payload*, `StatusHandler#process` performs the actual write with no repository/organization scoping at all — it matches commits globally by `sha`: [5](#0-4) 

Contrast this with `PushHandler`, which correctly scopes to `stacks` resolved from `repository.full_name`: [6](#0-5) 

`StatusHandler` has no equivalent check. The binding that should hold — "the organization whose secret authenticated this webhook == the organization whose stack is being mutated" — is never enforced, because the handler doesn't use `repository.full_name`/`repository.owner.login` at all when finding target commits.

A forged status is not inert: `Commit#create_status_from_github!` → `add_status` can immediately trigger merge-queue processing and continuous deployment: [7](#0-6) 

### Impact Explanation
Any organization configured in a multi-org Shipit instance (including one whose own webhook secret the attacker legitimately controls, or one with no secret configured at all, which the docs treat as optional) can be used to sign/send a `status` webhook that injects a fabricated `success`/`failure` CI status for **any commit SHA in any other organization's stacks**, as long as that SHA is already known to Shipit (e.g., a public commit that was already synced). Because `add_status` calls `stack.schedule_merges` on success/pending transitions and can enqueue `ContinuousDeliveryJob` for continuously-deployed stacks, this can produce an unauthorized merge or an unauthorized deploy on a stack the attacker does not own or have any legitimate relationship with — crossing the "organization authenticated vs. repository/stack written" trust boundary described in scope.

### Likelihood Explanation
The only prerequisite is that the attacker's own organization (or any org without a configured webhook secret) is one of the organizations Shipit is configured to serve, and that a target commit SHA is already known/synced in another org's stack — both plausible in any shared/multi-tenant Shipit deployment. No access to the victim organization's secret, GitHub token, or Shipit session is required.

### Recommendation
`StatusHandler` (and any other handler that doesn't already scope through `stacks`/`repository_name`) must verify that the commit(s) it mutates belong to a stack whose repository's organization matches the organization that was used to authenticate the webhook signature, e.g. filter `Commit.where(sha: params.sha)` through `stacks` (built from `repository.full_name`) the same way `PushHandler` does, and reject/ignore commits that fall outside that repository's stacks.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (attacker knows/owns its `webhook_secret`, or it has none configured) and `victim-org` (has a stack tracking commits with known public SHAs, e.g. from an open-source repo already synced by Shipit).
2. Find a commit SHA `X` that already exists in `victim-org`'s stack inside Shipit (visible via the Shipit UI/API or GitHub itself).
3. POST to `/webhooks` with header `X-Github-Event: status`, a valid signature computed with `attacker-org`'s webhook secret (or no secret if unset), and body:
```json
{
  "sha": "X",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and passes verification. `StatusHandler#process` finds the commit with SHA `X` (belonging to `victim-org`'s stack) via `Commit.where(sha: params.sha)` and creates a `success` status for it, potentially triggering `stack.schedule_merges` / continuous deployment for `victim-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
