### Title
NULL/undefined dereference on unchecked private-payment input elements causes node crash - (File: divisible_asset.js)

### Summary
`validateDivisiblePrivatePayment()` in `divisible_asset.js` validates only that `payload.inputs` is a non-empty array, but never checks that each element of that array is itself a non-empty object before dereferencing `.type`/`.address` on it, unlike the indivisible-asset validator which does perform this check.

### Finding Description
In `divisible_asset.js`, `validateDivisiblePrivatePayment` does: [1](#0-0) 
Only `ValidationUtils.isNonemptyArray(payload.inputs)` is checked — no per-element validation. The payload then flows into `validateSpendProofs`, which iterates `payload.inputs` and immediately dereferences `input.type`: [2](#0-1) 
If an attacker crafts `input` as JSON `null` inside the `inputs` array (e.g. `payload.inputs = [null]`), the expression `input.type === "issue"` on line 101 throws an uncaught `TypeError: Cannot read properties of null (reading 'type')` synchronously inside the `async.eachSeries` iterator, which is not wrapped in try/catch.

Crucially, this payload is never sanitized by the general per-message check in `validation.js` (`m.payload.inputs.every(i => isNonemptyObject(i) ...)`), because that check only fires when `m.payload` is present on the public unit, i.e. for `payload_location: "inline"` messages: [3](#0-2) 
Private-asset payments use `payload_location: "none"` (no `payload` field on the public unit — only `payload_hash`), so this defensive array-element check is bypassed entirely for private payment chains. The only remaining gate before reaching the vulnerable dereference is `initPrivatePaymentValidationState`, which merely verifies the payload's hash matches the previously committed `payload_hash`: [4](#0-3) 
Since the attacker (payer) chooses the payload before computing its own hash, they fully control the malformed `inputs` array and can make the hash match trivially.

By contrast, `indivisible_asset.js`'s `validatePrivatePayment` explicitly checks the single input element is a non-empty object before use: [5](#0-4) 
This confirms the omission in the divisible-asset path is a genuine, asymmetric gap analogous to MuPDF's missing null check before a pixmap-mask paint operation — both are "missing validation of an internal field before dereference," reachable directly by attacker-controlled input.

### Impact Explanation
A malicious private-payment counterparty (the payer in a divisible private-asset transfer) can send a crafted private payment chain via the wallet/chat channel to the payee's node/wallet. When the payee's node calls `validateDivisiblePrivatePayment` to validate and store the incoming private payment, the uncaught `TypeError` propagates out of the `async.eachSeries` iterator. Depending on the surrounding call context this results in either an unhandled exception crashing the receiving node process, or at minimum makes the node permanently unable to process/accept the (and possibly subsequent) private payment, denying the victim from receiving/confirming that private-asset payment — directly impacting their ability to receive/confirm funds.

### Likelihood Explanation
Likelihood is high for any party that regularly receives divisible private-asset payments (a normal wallet feature): the trigger requires no special privileges, no witness collusion, and no timing race — just crafting a JSON `null` (or otherwise non-object) element inside `payload.inputs` in a private payment package sent to a counterparty. The attacker fully controls the payload prior to hash computation, so the existing hash-integrity check offers no protection.

### Recommendation
In `divisible_asset.js`, before iterating `payload.inputs` in `validateDivisiblePrivatePayment`/`validateSpendProofs`, validate that every element is `ValidationUtils.isNonemptyObject(input)` (mirroring the check already present in `indivisible_asset.js` line 83) and reject the payment via `callbacks.ifError` otherwise, prior to accessing `input.type`, `input.address`, `input.unit`, etc.

### Proof of Concept
1. Attacker (payer) constructs a divisible private-asset payment payload where `payload.inputs = [null]` (or any non-object value with `.type` unresolvable causing a throw) along with valid `outputs`.
2. Attacker computes `payload_hash` over this exact payload and publishes a unit on the public ledger with `app: "payment"`, `payload_location: "none"`, `payload_hash` matching, referencing the asset.
3. Attacker sends the crafted private element (containing the malicious `payload.inputs`) to the payee via the standard private-payment/chat delivery mechanism.
4. Payee's node calls `validateAndSaveDivisiblePrivatePayment` → `validateDivisiblePrivatePayment` → `validateSpendProofs`, which executes `input.type === "issue"` on `input === null`, throwing an uncaught `TypeError` that is not caught anywhere in the call chain, crashing/hanging the payee's private-payment validation logic.
