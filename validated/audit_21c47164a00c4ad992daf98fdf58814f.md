### Title
Membership webhook handler trusts unsigned payload data to grant `Shipit.github_teams` authorization when `webhook_secret` is unset - ([File: lib/shipit/github_app.rb])

### Summary
`GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the target organization [1](#0-0) . Because `WebhooksController#verify_signature` relies solely on this method to gate `/webhooks` [2](#0-1) , any unauthenticated caller can post a forged `membership` event for such an organization. The `membership` handler then creates/updates local `Team`, `User`, and `Membership` records straight from the unverified payload, as shown by the controller tests that build teams and users purely from POST body content [3](#0-2) . If that team's `organization`/`slug` matches an entry configured in `Shipit.github_teams`, the attacker-chosen login gains `User#authorized?` once it logs in via GitHub OAuth [4](#0-3) .

### Finding Description
This is the same bug class as the report: a security-relevant transfer/write path (`buy()`'s `tNft.transferFrom`) skips the safety check that the rest of the system relies on (`safeTransferFrom`'s receiver-support check), because the check is conditionally bypassable.

Here, the analogous binding is: *"the organization that cryptographically authenticated the webhook delivery" must equal "the organization whose Team/Membership state is mutated by the payload."* `verify_webhook_signature` breaks this binding whenever `webhook_secret` is blank for the resolved organization:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [1](#0-0) 

`webhook_secret` is a supported, first-class optional configuration value (`@webhook_secret = @config[:webhook_secret].presence`) [5](#0-4)  — it is not a misconfiguration outside the engine's own code paths, it's an explicit branch the engine implements.

`WebhooksController` picks which `GithubApp` (and thus which secret) to check against using organization data taken from the *same, unverified* body, and then, regardless of verification outcome semantics, dispatches to handlers as soon as `verified` is truthy:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
  ...
``` [6](#0-5) 

Downstream, the `membership` handler creates a `Team` on the fly and appends arbitrary members purely from payload fields (`team.organization/slug`, `member.login`), as demonstrated by: [7](#0-6) 

`Team#add_member` performs no additional verification against real GitHub org/team membership beyond what the (bypassable) webhook delivered [8](#0-7) .

Finally, `User#authorized?` trusts local `Membership` rows to decide access:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [4](#0-3) 

So when an org has no `webhook_secret` set, an attacker with no credentials at all can forge a `membership` webhook naming any GitHub login as newly added to a team matching a configured `Shipit.github_teams` handle. That login only needs to complete a normal (unprivileged) GitHub OAuth login afterward to be treated as `authorized?`.

### Impact Explanation
This is a privilege escalation into `Shipit.github_teams` authorization — explicitly one of the listed High-impact categories. An attacker who is not a real member of any authorized GitHub team can grant themselves (or any other GitHub account) access to the Shipit UI/API, which in turn exposes stack state, deploy triggers, and other authorization-gated actions.

### Likelihood Explanation
Requires: (a) at least one configured GitHub organization/app in `Shipit.github` with `webhook_secret` unset — a supported configuration shown in the engine's own example secrets templates (`webhook_secret: # nil`) [9](#0-8) , and (b) the attacker knowing or guessing the organization/team handle configured in `Shipit.github_teams`. No `ApiClient` token, session, or webhook secret is needed to reach `/webhooks`; the only requirement is the app-level config choice already exercised in the codebase's own fixtures.

### Recommendation
- Make `verify_webhook_signature` fail closed (return `false`/reject) when `webhook_secret` is not configured, rather than returning `true`.
- Alternatively, require a configured `webhook_secret` for any organization whose teams are referenced by `Shipit.github_teams`, and refuse to process `membership` events for organizations lacking one.
- Re-validate `membership` payload data (e.g., confirm the claimed member is actually part of the GitHub org/team via an authenticated API call) before mutating local `Team`/`Membership` records.

### Proof of Concept
1. Configure (or target a deployment that configures) a GitHub organization in `Shipit.github` with `webhook_secret` left blank, matching the documented pattern in `secrets_double_github_app.yml`.
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and a JSON body:
   ```json
   {
     "action": "added",
     "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999"},
     "member": {"login": "attacker-controlled-login"},
     "organization": {"login": "target-org"}
   }
   ```
   (matching the shape used in `membership_params`/tests referenced above).
3. Because no `webhook_secret` is set for `target-org`, `verify_webhook_signature` returns `true` unconditionally, and `WebhooksController#create` dispatches to `Handlers::MembershipHandler`, creating a `Team` for `deployers` and a `Membership` linking `attacker-controlled-login`'s `User` record to it — exactly as exercised by the existing controller tests [7](#0-6) .
4. If `deployers` matches an entry in `Shipit.github_teams`, once the GitHub account `attacker-controlled-login` completes normal OAuth login, `User#authorized?` returns `true` and it is granted application access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
