Based on my investigation, I found a concrete binding-break in the webhook authentication flow — the organization that authenticates the request is never bound to the repository the resulting handler acts on.

### Title
Webhook Organization-Secret Verification Is Not Bound to the Repository Acted Upon, Allowing Cross-Repository Status/Sync Forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` selects which GitHub App/organization's `webhook_secret` to verify a request against using a field taken from the same request body (`repository.owner.login` / `organization.login`), then hands the *entire* attacker-influenced-in-content-but-legitimately-signed body to event handlers that key off a different field (`repository.full_name`, `sha`, etc.) to decide which Stack/Repository/Commit to mutate. Because Shipit supports multiple orgs configured with independent secrets, anyone who legitimately owns one configured org/app (and thus knows that org's `webhook_secret`) can craft a payload that authenticates as their own org while pointing its content (`repository.full_name`, commit `sha`, status `state`) at a different, victim-owned stack.

### Finding Description
`verify_signature` computes `repository_owner` from the JSON body and uses it to fetch the corresponding `github_app`, then checks the signature against that org's secret: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` only asserts that *some* valid payload was signed with the resolved organization's secret — it says nothing about which repository the payload's content refers to: [3](#0-2) 

Once verification passes, `create` dispatches the fully attacker-controlled JSON body to registered handlers: [4](#0-3) 

Handlers, however, key their side effects off other fields in that same body — e.g. the `status` handler locates and mutates a `Commit`'s CI status using the `sha`/`repository` fields, independent of which org's secret was used to verify the request, as confirmed by the test asserting a `Status` record is created directly from payload content merged with `repository_params`: [5](#0-4) 

Because the config format explicitly supports multiple independently-secreted orgs (`OrgOne`, `OrgTwo`, ...): [6](#0-5) [7](#0-6) 

...an attacker who legitimately controls one configured org (and thus knows *that* org's `webhook_secret`) can sign an arbitrary JSON body with it. The binding broken is: **organization authenticated (`repository_owner` used to pick the verifying secret) ≠ repository/commit the handler actually writes to (`repository.full_name` / `sha` inside the same attacker-chosen body)**. Nothing in `verify_signature` or the dispatched handler cross-checks that the repository named in the payload actually belongs to the organization whose secret verified it.

### Impact Explanation
An attacker who owns a small, legitimately Shipit-integrated org/repo (their own `webhook_secret`, no privileged access to the victim's repo, no `ApiClient` token, no GitHub App private key) can forge a `status` event naming an arbitrary victim commit `sha`/`repository.full_name` and inject a fabricated `success` state for a CI context. Shipit's merge-queue/deploy gating (`ci.require`) trusts `commit.statuses` populated this way, so this can enable an **unauthorized deploy or merge** on a repository the attacker has no access to — matching the Critical impact bar (unauthorized deploy/rollback/merge). The same organization/repository disjunction also lets an attacker trigger `GithubSyncJob`-style push processing for a victim stack, expanding blast radius beyond status forgery.

### Likelihood Explanation
Likelihood is High for anyone who administers one of the multiple GitHub orgs/apps Shipit is configured to serve (a normal, expected deployment topology per `test/dummy/config/secrets_double_github_app.yml`), since they hold a valid `webhook_secret` for their own org and only need to alter unrelated fields (`repository.full_name`, `sha`) in a self-signed POST to `/webhooks`. No session, `ApiClient` token, or GitHub write access to the victim repo is required — only knowledge of the target commit `sha` and repo full name, both public GitHub information.

### Recommendation
After verifying the HMAC signature, cross-validate that the `repository.full_name` (and any repo/commit identifiers acted on by handlers) actually belongs to the resolved `repository_owner`/organization before dispatching to handlers, e.g. by rejecting payloads where `repository.owner.login` does not match the org name embedded in `repository.full_name`, or by re-deriving the org strictly from `repository.full_name` for authorization purposes rather than trusting a separate payload field for secret selection.

### Proof of Concept
1. Configure Shipit (as in `test/dummy/config/secrets_double_github_app.yml`) with two orgs, `OrgOne` (attacker-controlled, known secret) and `OrgTwo` (victim, has an existing tracked Stack/Commit).
2. Attacker builds a `status` webhook JSON body with `organization.login`/`repository.owner.login` = `OrgOne` (so `repository_owner` resolves to `OrgOne`'s secret) but `repository.full_name`/`sha` referencing a real commit in `OrgTwo`'s tracked repository, and `state` = `success` for a context listed in that stack's `ci.require`.
3. Attacker computes `X-Hub-Signature` using `OrgOne`'s known `webhook_secret` over the raw body and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` succeeds (secret matches `OrgOne`), and the `status` handler creates/updates a `Status` on the victim's commit as shown in the test flow at `test/controllers/webhooks_controller_test.rb:42-59`, potentially satisfying merge/deploy CI gating for a commit the attacker never had access to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
