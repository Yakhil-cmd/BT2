### Title
Bad-debt wipeout clamps `supply_index` to `SUPPLY_INDEX_FLOOR_RAW` instead of zeroing shares, resurrecting wiped suppliers into phantom claims that drain the next depositor — (File: contracts/pool/src/interest.rs)

### Summary
When bad debt at or above total supplied value is socialized, `apply_bad_debt_to_supply_index` caps the write-down at total supplied value but then floors the resulting index at `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000) instead of zeroing or burning the affected supply shares. Every scaled supply position retains a small positive claim. The first honest deposit after the wipeout credits real cash into a market whose stranded phantom shares can immediately withdraw it in full, stealing the fresh deposit. The in-repo test `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` demonstrates exactly this sequence end-to-end. The bug class (memory corruption → attacker-controlled state surviving an overwrite that should have destroyed it) maps here as index corruption: state that should have been destroyed by the wipeout survives and pays out real tokens.

### Finding Description
`contracts/pool/src/interest.rs:73-89`:

```rust
let capped = bad_debt.min(total_supplied_value);
let remaining = total_supplied_value.checked_sub(cache.env(), capped);
let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
let new_supply_index = cache.supply_index().mul_floor(cache.env(), reduction_factor);
cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

When `bad_debt >= total_supplied_value`, `remaining = 0`, `reduction_factor = 0`, `new_supply_index = 0`, but the `.max(SUPPLY_INDEX_FLOOR_RAW)` resurrects the index to `RAY/1000`. All existing scaled supply shares — which economically should be worth zero — still unscale to a positive amount via `unscale_supply_floor` (`contracts/pool/src/cache/scale.rs:60-67`). Neither the shares nor the `supplied` total are reduced, so `supplied × supply_index` now exceeds pool cash.

Reachability is permissionless:

- `controller::liquidate` (`contracts/controller/src/lib.rs:144-158`) → `pool_seize_positions_call` → `contracts/pool/src/ops/seize.rs:24-28`, which calls `apply_bad_debt_to_supply_index` for each `Borrow` seize entry and `absorb_supply_as_revenue` for `Deposit` entries. Note the Deposit branch *reclassifies* the seized account's own shares as revenue but does not touch other suppliers' stranded shares.
- `controller::clean_bad_debt` (`contracts/controller/src/lib.rs:163-165`) → `execute_bad_debt_cleanup` (`contracts/controller/src/positions/liquidation/bad_debt.rs:14-60`), permissionless when residual collateral is at or below the dust cap; reaches the same `seize::apply` borrow path.

After the wipeout, `withdraw` → `resolve_withdrawal` (`contracts/pool/src/cache/scale.rs:97-105`) pays `pos_scaled × supply_index` gross against `require_reserves`, which only checks current cash — so any fresh `supply` deposit becomes withdrawable by a stranded holder.

### Impact Explanation
Theft of user funds / protocol insolvency: a wiped-out supplier (or any holder of stranded scaled shares, including shares acquired cheaply after the wipeout) can withdraw real tokens equal to `stranded_claim` as soon as the market holds any cash. The in-repo tests prove the stranded holder drains exactly the next depositor's principal, leaving `cash < fresh_scaled_claim` — i.e., the honest supplier's deposit is unrecoverable (`contracts/pool/tests/interest.rs:372-427`, `430-494`). Since the stranded claim persists indefinitely, every subsequent depositor into that market is exposed until the phantom shares are burned.

### Likelihood Explanation
Triggering requires a full socialization event where bad debt ≥ total supplied value, i.e., a wipeout liquidation or `clean_bad_debt` on an account whose debt meets the dust-threshold cleanup criteria. Small or young markets, extreme price moves, or thin-liquidity assets make `bad_debt >= total_supplied_value` reachable; a self-liquidation is explicitly permitted (`liquidate` doc, `lib.rs:137`), so an attacker can manufacture an insolvent account with their own collateral, force the wipeout, keep the stranded shares (their own supply is seized into revenue only for that account — other accounts' shares on the same market remain stranded), wait for or induce a fresh deposit, and withdraw. No privileged role is needed at any step.

### Recommendation
Do not floor the post-socialization index above zero while shares remain. Either:
- when `capped == total_supplied_value`, burn/write down all supply positions (e.g., set `supply_index` such that claims are zero and mark the market for recapitalization), or
- on a full wipeout, scale down `supplied` shares proportionally to the remaining claim value so `supplied × supply_index ≤ cash` holds invariant.

At minimum, `recapitalize` or the next `supply` should reconcile `supplied × supply_index` against actual cash before crediting new shares, so stranded claims cannot attach to fresh liquidity.

### Proof of Concept
Already encoded as unit tests in the repo (`contracts/pool/tests/interest.rs`):

```rust
// test_raw_cache_floor_clamp_strands_claim_without_supply_guard (lines 372-428)
// 1. Old supplier holds old_scaled = 1000 * RAY shares; supply_index = RAY.
apply_bad_debt_to_supply_index(&mut cache, Ray::from(5_000 * RAY)); // wipeout
assert_eq!(cache.supply_index().raw(), SUPPLY_INDEX_FLOOR_RAW);     // index resurrected to RAY/1000
let stranded = cache.unscale_supply_floor(old_scaled);
assert!(stranded > 0);                                             // phantom claim survives

// 2. Honest user deposits fresh_cash = stranded.
cache.mint_supply(cache.calculate_scaled_supply(fresh_cash));
cache.credit_cash(fresh_cash);

// 3. Stranded holder withdraws i128::MAX.
let (burn, gross) = cache.resolve_withdrawal(i128::MAX, old_scaled);
cache.require_reserves(gross);   // passes: cash covers gross
cache.burn_supply(burn);
cache.debit_cash(gross);
assert_eq!(gross, fresh_cash);   // drains exactly the fresh deposit
assert!(cache.cash() < cache.unscale_supply_floor(fresh_scaled)); // depositor's claim unbacked
```

End-to-end: `controller.clean_bad_debt(caller, victim_account)` (or `liquidate` with `SeizeMode::Credit`) on a market where the victim's ceil-unscaled debt ≥ total supplied value triggers `seize::apply` → `apply_bad_debt_to_supply_index`; the attacker then calls `supply` from a second account is unnecessary — the attacker simply waits for any victim `supply`, then calls `withdraw(account_with_stranded_shares, i128::MAX)` to take the deposit.

One caveat: the tests I found exercise the pool cache directly; I did not fully trace whether any controller-level guard (e.g., spoke usage accounting or a global supply-index sanity check) blocks the stranded withdrawal, so the exploit path should be confirmed at the entrypoint level.
