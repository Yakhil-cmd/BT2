### Title
Cross-organization webhook signature confusion allows unauthorized Stack sync/writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App config (and thus the HMAC secret) used to validate the webhook based on `repository_owner`, which is read straight out of the unauthenticated JSON body. Downstream, `Handler#stacks` resolves the target `Repository`/`Stack` from a *different* field of the same unauthenticated body: `repository.full_name`. Because the field that authenticates the request (`repository.owner.login`) is never cryptographically bound to the field that is acted upon (`repository.full_name`), an attacker who controls a legitimate GitHub App installation on their own organization can forge a payload whose `owner.login` points to their own org (so the signature validates against a secret they know) while `full_name` points to a victim organization's repository whose stacks then get processed.

### Finding Description
`Shipit::WebhooksController#verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to pick which `GitHubApp` (and therefore which `webhook_secret`) is used to verify the HMAC:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 

Once verified, the raw parsed body is dispatched unchanged to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
end
``` [3](#0-2) 

`Handlers::Handler` (the base class for `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target repository/stacks using a *different* JSON key, `repository.full_name`, with no cross-check against `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process` then acts on every non-archived stack matching the branch, triggering a GitHub sync against the resolved repository:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The equality that should hold is:
`organization whose secret authenticated the request == organization that owns the repository whose stacks are acted upon`

Before the attack: `repository.owner.login == "attacker-org"` and `repository.full_name == "attacker-org/some-repo"` — both fields agree, so the binding holds trivially for legitimate traffic.

After the attacker's crafted request: `repository.owner.login == "attacker-org"` (used only to select `attacker-org`'s known `webhook_secret` for HMAC verification) while `repository.full_name == "victim-org/victim-repo"` (used by `Handler#stacks` to locate and act on the actual `Stack`). The signature check in `verify_webhook_signature`/`SecureCompare.secure_compare` at `lib/shipit/github_app.rb:76-83` [6](#0-5)  passes because it is validated against `attacker-org`'s secret — a secret the attacker legitimately possesses from their own GitHub App installation — but the payload content acted upon belongs to `victim-org`.

This is the direct structural analog of the reported `calc_spot_price_fixed` bug: two conceptually distinct "coins" (here: the org whose credential is checked vs. the org whose repository is mutated) are supposed to be the same value but the code lets them diverge because it reads them from two different fields of the same untrusted input without binding them together.

### Impact Explanation
Any GitHub organization onboarded to this Shipit instance (i.e., any org for which the operator configured a `webhook_secret`/App) can forge a webhook that is "signed" with its own known secret but whose `repository.full_name` names a stack belonging to a different, unrelated organization also configured on the same instance. Since `PushHandler` calls `stack.sync_github(expected_head_sha: ...)` for every matching stack, and `StatusHandler`/`CheckSuiteHandler` similarly key off `repository.full_name`, this allows a low-privilege attacker (one who only controls their own onboarded org's webhook secret, not a Shipit session, `ApiClient` token, or GitHub write access to the victim repo) to trigger unauthorized syncs, status changes, and check-run refreshes against another organization's stacks — a cross-repository write/unauthorized deploy-input path, matching the "organization that authenticated versus the repository that is written" boundary called out in scope.

### Likelihood Explanation
Exploitability requires only that the Shipit instance host multiple GitHub organizations (a documented, supported multi-org configuration — see `secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml` showing multiple orgs configured under `github:`) [7](#0-6)  and that the attacker controls one of those orgs' webhook delivery (which they legitimately do, as the owner of that org's GitHub App/installation). No secrets, sessions, or write access to the victim repo are needed — only crafting a raw HTTP POST with a mismatched `repository.owner.login` / `repository.full_name` and a valid HMAC for the attacker's own org.

### Recommendation
Bind the field used for repository/stack resolution to the same organization that was cryptographically verified: after `verify_signature` succeeds, assert that `payload.dig('repository', 'full_name')`'s owner segment matches the verified `repository_owner`, and reject (422) the request otherwise. Alternatively, derive the verifying organization strictly from `repository.full_name`'s owner segment (the same field handlers use) rather than from `repository.owner.login`, so verification and resolution are always sourced from one authoritative field.

### Proof of Concept
1. Operator configures Shipit with two orgs: `attacker-org` (attacker knows its `webhook_secret`) and `victim-org` (hosts a real `Stack` for `victim-org/victim-repo`).
2. Attacker computes `sha1=HMAC(attacker-org secret, raw_body)` for a crafted push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully because the signature was computed with `attacker-org`'s known secret. [2](#0-1) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `victim-org`'s stack, even though the request was never signed by `victim-org`. [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
