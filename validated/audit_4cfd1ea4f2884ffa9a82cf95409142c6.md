### Title
Unfiltered PR-label-derived env vars (e.g. `BUNDLE_GEMFILE`) reach `tasks.<name>.steps`, `deploy` and `install_dependencies` command execution - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment with no key allowlist, and `TaskCommands#env`/`StackCommands#env` merge `@stack.env` directly into the environment passed to `Command.new`/`Command#unbundled_env`/`PTY.spawn` without ever routing it through `EnvironmentVariables#permit`. An unprivileged fork PR author can therefore set an environment-variable key of their choosing (value fixed to `"true"`) for every step Shipit executes on a review stack, including `tasks.<name>.steps`, `deploy` steps, and `install_dependencies` (bundler invocation).

### Finding Description
The broken binding: for review stacks, `env["ANY_LABEL_NAME".upcase]` should equal `nil` unless that key is present in an explicit allowlist (as it is for `deploy_variables`/`rollback_variables`/task `variables` via `EnvironmentVariables#permit`). In fact:

- `ReviewStack#env` [1](#0-0)  merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into `super` with zero filtering.
- `PullRequest#github_pull_request=` sets `self.labels = github_pull_request.labels.map(&:name)` directly from GitHub API/webhook data [2](#0-1) , and `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the webhook body with no allowlist [3](#0-2) .
- `StackCommands#env` merges `@stack.env` unfiltered [4](#0-3) , and `TaskCommands#env` (parent of `DeployCommands#env`) does the same, merging `@stack.env` before task/deploy-specific keys and `@task.env` (the latter *is* filtered by `EnvironmentVariables.permit`) [5](#0-4) .
- This merged hash is what `perform`/`install_dependencies` pass as `env:` to `Command.new` [6](#0-5) , which in `Command#unbundled_env` does `BASE_ENV.merge(...).merge(@env.stringify_keys)`, overriding the sanitized `BASE_ENV` (which strips `BUNDLE_GEMFILE` etc. via `Bundler.unbundled_env`) with the attacker-controlled key before `PTY.spawn` [7](#0-6) [8](#0-7) .

Exploit flow: an attacker opens a fork PR against a repository with `provisioning_behavior=allow_all` and `review_stacks_enabled`, and adds a label named `bundle_gemfile` (any case) to their own PR. `LabeledHandler`/`LabelCapturingHandler` persist this label on the `PullRequest` record with no validation of the name. When any task/deploy/install-dependencies step runs for that review stack, `ReviewStack#env` injects `BUNDLE_GEMFILE=true` into the environment reaching `Command#unbundled_env` and `PTY.spawn`. Because bundler resolves `BUNDLE_GEMFILE` relative to the working directory when it is not an absolute path, and the attacker also controls the fork's tree (including a file literally named `true`), any subsequent bundler invocation (during `install_dependencies`'s bundler steps, or any `bundle exec`/`bundle install` command referenced in `tasks.<name>.steps`) will load and evaluate that attacker-authored file as a Gemfile — Ruby code in a Gemfile executes at load time.

Existing guards do not catch this: `EnvironmentVariables#permit` is applied only to `@task.env`/deploy/rollback `env` supplied through the human/API-triggered `env` params (`Stack#trigger_task`, `Stack#build_deploy`, `RollbacksController`), not to `@stack.env`, which is merged separately and unconditionally in `TaskCommands#env`/`StackCommands#env`. There is no per-key allowlist on `ReviewStack#env`'s label-derived hash at all, and no validation on `PullRequest#labels`/label names.

### Impact Explanation
The attacker gains the ability to force any environment variable key (fixed value `"true"`) into the process environment of every command Shipit runs for their own review stack — including deploy, custom task, and dependency-install steps. Combined with the attacker's own control of the checked-out fork content (a normal capability of review apps), setting `BUNDLE_GEMFILE`/similar bundler/tool-hijacking variables lets the attacker's Gemfile (or other tool config resolved via env var) execute arbitrary Ruby/code on the Shipit deploy host during a step that invokes `bundle`. This is Remote Code Execution on the deploy host, matching the Critical impact category (`Command`/`PTY.spawn`). The blast radius is scoped to the attacking repository's own review stack/host resources (shared deploy host, git cache, bundler cache directories), but is repeatable on every task/deploy run for that stack, and is achievable by any repository configured with `allow_all` provisioning for review stacks — a configuration the maintainers control, not the attacker.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and `provisioning_behavior` set to `allow_all` (or `allow_with_label`/`prevent_with_label` with the label condition met) so a fork PR gets a review stack; then the attacker must be able to open a PR and add a label to it — labels can typically be added by anyone with triage-level access or via automation depending on repo settings, and PR labels are entirely attacker-influenced in many workflows (self-labeling, bot-labeling, or CI auto-labels reflecting PR title/branch). Attacker cost is minimal: open a PR, add one label, wait for a task/deploy to run. This is fully repeatable and requires no privileged credentials, matching the described "Fast validation" test.

### Recommendation
Restrict `ReviewStack#env`'s label-derived keys to an explicit allowlist (e.g. a configurable prefix such as `LABEL_` or a `shipit.yml`-declared list of permitted label-derived variable names), and route `@stack.env` through `EnvironmentVariables.permit` with a defined variable-definition list before merging it into `TaskCommands#env`/`StackCommands#env`, exactly as is already done for `@task.env` via `EnvironmentVariables.permit`. At minimum, block reserved/dangerous names (`BUNDLE_*`, `RUBYOPT`, `LD_PRELOAD`, `PATH`, etc.) from being set via PR labels.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_bundle_gemfile_test.rb
require "test_helper"

class TaskCommandsBundleGemfileTest < ActiveSupport::TestCase
  test "PR label cannot inject BUNDLE_GEMFILE into tasks.<name>.steps env" do
    stack = shipit_stacks(:review_stack) # a Shipit::ReviewStack fixture
    stack.pull_request.update!(labels: ["bundle_gemfile"]) # attacker-controlled label name

    task = shipit_tasks(:shipit_restart)
    task.stack = stack

    env = Shipit::TaskCommands.new(task).env

    # Invariant under test: no fork-controllable key such as BUNDLE_GEMFILE should reach the
    # spawned process env for tasks.<name>.steps.
    refute env.key?("BUNDLE_GEMFILE"), "BUNDLE_GEMFILE was injected via a PR label: #{env['BUNDLE_GEMFILE'].inspect}"
  end
end
```
Running this against the current code fails: `env["BUNDLE_GEMFILE"]` equals `"true"`, demonstrating that `Command#unbundled_env` (`BASE_ENV.merge(...).merge(@env.stringify_keys)`) will pass an attacker-set `BUNDLE_GEMFILE` to `PTY.spawn` for `tasks.<name>.steps`, `deploy_steps`, and `install_dependencies`.
