### Title
Unauthenticated `StackStxOp` sender forgery via `PreStxOp` output0 lets an attacker lock a victim's STX and steal PoX rewards - (File: `stackslib/src/chainstate/burn/operations/stack_stx.rs`, `stackslib/src/burnchains/burnchain.rs`)

### Summary
`StackStxOp::sender` is not derived from any Stacks-layer signature; it is copied verbatim from the `PreStxOp`'s first Bitcoin output address, which is fully attacker-controlled and requires no private key ownership to encode a victim's hash160. Combined with `StackStxOp::reward_addr` being taken from the attacker's own `StackStx` transaction output, an attacker can craft a `PreStxOp`/`StackStxOp` pair that locks a victim's unlocked STX balance while directing the PoX reward payout to the attacker's own address.

### Finding Description
The broken equality: **STX locked (attributed to `sender`) == STX committed and authorized by the party who signs the Bitcoin operation.** After this exploit, the left side is the victim's balance while the right side is the attacker's Bitcoin key — the equality is broken.

Code path:
1. `PreStxOp::parse_from_tx` decodes `output` (the future `sender`) purely from the first output's Bitcoin address, converted with `try_into_stacks_address()` — no signature or private-key proof is required, only knowledge of the victim's public hash160 (which is public, being derivable from the victim's Stacks address): [1](#0-0) 
2. `Burnchain::classify_transaction` for `Opcodes::StackStx` looks up the referenced `PreStxOp` and passes `&pre_stack_stx.output` as `sender` directly into `StackStxOp::from_tx`, with no check that the entity broadcasting the `StackStx` transaction is the same Stacks-key holder as `sender`: [2](#0-1) 
3. `StackStxOp::parse_from_tx` sets `sender: sender.clone()` (the forged victim address) and `reward_addr` from the **StackStx transaction's own first output**, which the attacker fully controls since they craft that transaction: [3](#0-2) 
4. `StackStxOp::get_sender_txid` only validates that the input spends vout=1 of the referenced PreStx tx — it never checks that the same Bitcoin key/entity that produced vout=0's encoded address also signs the spending input: [4](#0-3) 
5. `StacksChainState::process_stacking_ops` executes the `stack-stx` contract call with `sender.clone().into()` as the literal `tx-sender`, with no additional authentication layer: [5](#0-4) 
6. In `pox-4.clar`'s `stack-stx`, the only check on the "victim's" ability to have funds locked is a balance check on `tx-sender`, with no signature verification tying `tx-sender` to the Bitcoin key that authored the burn operation: [6](#0-5) 

The `signer-key`/`signer-sig` mechanism validated by `consume-signer-key-authorization` authenticates only the *signer* role (who is allowed to represent a PoX address in the signer set) — it is not bound to and does not authenticate `tx-sender`. An attacker fully controls `signer_key` too, since it's parsed from their own crafted OP_RETURN payload: [7](#0-6) .

Attacker's exact call sequence: broadcast `PreStxOp` with output0 = victim's hash160/address, output1 = attacker's own Bitcoin key (so they can later spend it); then broadcast `StackStxOp` spending vout=1 of that `PreStxOp`, with data encoding `stacked_ustx` = victim's full unlocked balance and output0 = attacker's own reward `PoxAddress`. No signature from the victim's Stacks key or Bitcoin key is ever produced or checked.

### Impact Explanation
The victim's unlocked STX (up to their entire balance) is locked without their consent (permanent freezing of the victim's funds for the lock period), and the PoX reward for that stacked amount is paid to the attacker's `reward_addr` (theft of rewards). This is repeatable against any victim address with sufficient unlocked balance, each time the attacker is able to produce a fresh `PreStxOp`/`StackStxOp` pair (bounded only by Bitcoin transaction fees the attacker pays and burn-block cadence). This matches the Critical category: "theft ... of locked STX or sBTC rewards, permanent freezing of staked STX."

### Likelihood Explanation
Preconditions: PoX-4 active reward cycle, victim not already stacking or delegating (`is-none (get-stacker-info tx-sender)` / `is-none (get-check-delegation tx-sender)`), victim has enough unlocked balance to cover `amount-ustx`. Attacker cost is only the Bitcoin fees for two low-value transactions and knowledge of the victim's public Stacks address (public knowledge). No privileged role, no victim cooperation, and no cryptographic proof of Stacks-key ownership is required anywhere in the path — this is trivially and repeatably exploitable against any sufficiently-funded, non-stacking address.

### Recommendation
Require the `StackStxOp`/`PreStxOp` `sender` to be cryptographically tied to the Bitcoin key that authored the operation (or require a Stacks-layer signature from the claimed `sender`/stacker binding the burn operation to their consent), rather than deriving `tx-sender` solely from an arbitrary Bitcoin output address that anyone can encode with a third party's hash160. At minimum, `pox-4.clar`'s `stack-stx` entry point invoked from burn ops should require an explicit stacker-authorized signature analogous to the existing `signer-sig`/`consume-signer-key-authorization` mechanism, but scoped to authenticate `tx-sender` itself, not merely the signer role.

### Proof of Concept
Rust test plan (in `stackslib/src/chainstate/burn/operations/test/mod.rs` or a chainstate-boot integration test similar to `stackslib/src/burnchains/tests/db.rs:489-525`):
1. Boot a test chainstate through PoX-4 activation; fund a `victim` Stacks address with unlocked STX (e.g., 500,000,000 uSTX) and derive `victim`'s hash160/Bitcoin-style address deterministically from their known Stacks address bytes.
2. Craft `PreStxOp` with `output = victim` (using only public victim hash160 bytes, no victim key material) and a second output funded/controlled by `attacker`'s Bitcoin key.
3. Craft `StackStxOp` spending vout=1 of that PreStx tx, signed only by `attacker`'s Bitcoin key, encoding `stacked_ustx = 500_000_000`, `num_cycles = 1`, and output0 = `attacker`'s `PoxAddress`.
4. Run both through `Burnchain::classify_transaction` → `StacksChainState::process_stacking_ops`.
5. Assert `op.sender == victim` and `op.reward_addr == attacker_pox_addr` (as in the existing test at `stackslib/src/burnchains/tests/db.rs:517-524`), then assert post-processing that the victim's STX balance shows a lock (`stx-account victim` reflects `locked = 500_000_000`) while the reward-cycle's PoX address entries for `attacker_pox_addr` show the committed 500,000,000 uSTX — with no transaction anywhere signed by `victim`.
6. The equality check: before, `locked_STX(victim) == 0` and `committed_to(attacker_reward_addr) == 0`; after, `locked_STX(victim) == 500_000_000` while `committed_to(attacker_reward_addr) == 500_000_000`, proving the divergence between the party whose STX is locked and the party who authorized/benefits from the operation.

            magic  op         uSTX to lock (u128)     cycles (u8)     signer key (optional)   max_amount (optional u128)  auth_id (optional u32)

        if data.len() < 17 {
            // too short
            warn!(
                "StacksStxOp payload is malformed ({} bytes, expected {} or more)",
                data.len(),
                17
            );
            return None;
        }

        let num_cycles = *data.get(16)?;

        let mut max_amount: Option<u128> = None;
        let mut auth_id: Option<u32> = None;

            signer_key = Some(StacksPublicKeyBuffer::from(data.get(17..50)?));

                return None;

            let Some(id) = parse_u32_from_be(data.get(66..70)?) else {
                return None;

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
