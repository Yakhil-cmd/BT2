### Title
`StatusHandler#process` writes GitHub status updates to every `Commit` row sharing a SHA, regardless of repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)` with no check that the commit's owning `Stack`/repository matches the repository that authenticated the incoming webhook. Any attacker who can trigger a genuine, correctly-signed `status` webhook for a commit SHA that is shared between their own repository and a victim's tracked stack (e.g. via a fork, shared history, or a monorepo/submodule relationship) can overwrite the `ci/build` (or any) status on the victim's commit, altering `deployable?`/merge eligibility for a repository they never authenticated for.

### Finding Description
The broken binding is: for every `commit` returned by `Commit.where(sha: params.sha)`, the invariant `commit.stack.repository == payload.repository` must hold before `commit.create_status_from_github!(params)` is called. This is never checked.

- `StatusHandler#process` iterates `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/stack filter [1](#0-0) .
- `Commit#create_status_from_github!` unconditionally appends the incoming status to `statuses` and recomputes `status`, which feeds `deployable?`, `blocked?`, and triggers `Hook.emit(:deployable_status, ...)` / `stack.schedule_merges` [2](#0-1) [3](#0-2) [4](#0-3) .
- The controller's only gate, `verify_signature`, resolves the `GitHubApp` (and thus the HMAC secret) using `repository_owner` taken from the payload's `repository.owner.login`/`organization.login`, then verifies the raw body signature against that org's secret [5](#0-4) . This proves the payload was genuinely emitted by GitHub for *some* repository belonging to that org/app configuration — it does **not** prove, and never checks, that the `sha` in the payload belongs to that same repository's commit history as recorded in Shipit, nor does it constrain `StatusHandler` to that repository.
- `Commit#sha` has no uniqueness constraint scoped to `stack`/repository; multiple `Stack`s (different repositories, forks, or shared history) can contain `Commit` rows with an identical `sha`.

Attack flow: attacker pushes/owns a repository whose commit history shares a SHA with a commit already ingested into a victim's Shipit stack (fork of the victim's repo, shared submodule, or any scenario producing an identical git commit object). Attacker sets a commit status (`context: ci/build`, `state: failure`) on that SHA in their own repository via the GitHub API (or by pushing a build that reports it). GitHub delivers a legitimately-signed `status` webhook to `POST /webhooks` for the attacker's own repository/org. `verify_signature` passes because the signature is valid for that org. `StatusHandler#process` then finds *every* `Commit` row with that SHA — including the victim's — and calls `create_status_from_github!`, rewriting the victim's `ci/build` status to `failure`, which (if `ci/build` is in the victim stack's `ci.require`) flips `deployable?` to `false` and can block/unblock merges depending on `blocking_statuses`.

No existing guard prevents this: `verify_signature` only authenticates "an org", not "this specific repository's commit"; the `ExplicitParameters` schema for `StatusHandler` validates types only, not repository scope; there is no model validation tying `Commit#sha` uniqueness or write permission to the stack that owns it.

### Impact Explanation
An attacker can force a required CI context to `failure` (or `success`) on a commit belonging to a repository/stack they never authenticated for, directly manipulating `Shipit::Commit#deployable?` and merge-queue behavior (`stack.schedule_merges`, `Hook.emit(:deployable_status, ...)`) for that victim stack. This is a cross-tenant write: a payload authenticated for repository A mutates state belonging to repository B, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable for any SHA collision the attacker can produce and blast radius covers any stack containing a `Commit` row with the colliding SHA.

### Likelihood Explanation
The attacker needs: (1) a repository under their control whose webhook events flow into the same Shipit instance (or any org configured in `Shipit.github_teams`/`GitHubApp` with a webhook secret they can trigger genuine deliveries against), and (2) a commit SHA that also exists in the victim's stack's `commits` table — achievable via forks, shared monorepo history, cherry-picked/rebased-but-identical commits, or submodule sharing, all of which are common in real engineering setups. No Shipit secrets, sessions, or API tokens are required; only the ability to produce a real GitHub `status` event for a SHA they can influence. This makes the attack moderately feasible in shared-history environments and trivially repeatable.

### Recommendation
Scope `StatusHandler#process` (and the analogous `CheckRunHandler`/other SHA-keyed handlers) to only update commits belonging to the stack(s) whose repository matches the webhook's authenticated repository (`params.dig('repository', 'full_name')`), e.g. filter via `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })` instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (no live GitHub required):
1. Create two `Repository`/`Stack` pairs: `victim_stack` (repository `victim/repo`) and `attacker_stack` (repository `attacker/repo`), both with `ci.require` including `"ci/build"`.
2. Create a `Commit` with `sha: "deadbeef..."` under `victim_stack`, and record `victim_commit.deployable?` (expect `true` after a passing `ci/build` success status is seeded) and `victim_commit.status.simple_state`.
3. Create a second `Commit` with the **same** `sha: "deadbeef..."` under `attacker_stack` (simulating shared history).
4. Build a `status` webhook payload: `{ sha: "deadbeef...", state: "failure", context: "ci/build", repository: { full_name: "attacker/repo", owner: { login: "attacker" } } }`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)` (or `process` directly), bypassing only the HTTP-layer signature check (which is orthogonal — it validates org identity, not repo/commit scope).
6. Assert: `attacker_commit.reload.status.state == "failure"` (expected/legitimate) AND `victim_commit.reload.status.state == "failure"` / `victim_commit.deployable? == false` (the bug: victim's commit was mutated by a payload authenticated only for `attacker/repo`).
7. Equality check before/after: before, `victim_commit.status.state == "success"` and `victim_commit.deployable? == true`; after processing the attacker-repo payload, both flip — proving the cross-repository write.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
