### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while the write target is bound to a different, unverified field — breaking the "organization that authenticated == repository that is written" invariant - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, a value read straight out of the untrusted, attacker-supplied JSON body [1](#0-0) . Once the signature check passes, the actual event handlers resolve the write target using a *different* field from that same untrusted body — `repository.full_name` — or, in the case of `StatusHandler`, no repository scoping at all. Nothing ties the value used to select/verify the signing organization to the value used to decide which stack/commit gets mutated. This is structurally the same class of bug as the reported `_capFeeAmount` issue: two values that are supposed to be consistent (the authorized amount/organization vs. the amount/repository actually acted upon) are computed independently, and the code implicitly assumes they match when nothing enforces it.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
with
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is fully attacker-controlled: it is read from the raw, unauthenticated POST body before the signature is even validated. It only proves that *some* configured organization's HMAC secret matches the raw payload — it says nothing about the rest of the JSON structure.

After the before_action passes, `create` dispatches the same untrusted body to handlers:
```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [3](#0-2) 

Handlers derive their target repository from `repository.full_name`, not from `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Worse, `StatusHandler` doesn't even use `stacks`/repository scoping — it looks up commits globally by SHA across the entire Shipit instance:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

`CheckSuiteHandler` and `PushHandler` do scope via `stacks` (i.e., `repository.full_name`) [6](#0-5) [7](#0-6) , but that scoping field is still never cross-checked against `repository_owner`/`organization.login`, the field actually used for authentication.

Shipit explicitly supports multiple independently-configured GitHub Apps/organizations sharing one Shipit instance, each with its own `webhook_secret` [8](#0-7) . In that documented, in-scope configuration, an entity that is fully authorized only for "OrgOne" (and thus legitimately knows OrgOne's `webhook_secret`) can:
1. Craft a JSON body with `repository.owner.login = "OrgOne"` (or `organization.login = "OrgOne"`) so `repository_owner` resolves to the app/secret they know, and
2. Set `repository.full_name = "OrgTwo/victim-repo"` (or, for `status` events, just set `sha` to a commit belonging to any stack Shipit tracks — no repository field needed at all).
3. Sign the raw body with OrgOne's HMAC secret and POST it to `/webhooks`.

`verify_webhook_signature` only checks the HMAC against OrgOne's secret and the raw bytes, which is self-consistent and passes [9](#0-8) . The handler then acts on OrgTwo's (or any) repository/commit using the crafted fields, even though the signer was never authenticated for that organization/repository.

### Impact Explanation
This breaks the equality `organization that authenticated == repository that is written`, one of the binding categories explicitly in scope. Concrete unauthorized-write paths enabled:
- `StatusHandler` lets a signer for *any* configured org inject a fabricated commit status (`state`, `description`, `context`, `target_url`) for *any* commit SHA tracked anywhere in the Shipit instance, since lookup is global (`Commit.where(sha: params.sha)`), with zero repository/organization scoping. Commit statuses feed into deploy-safety/CI-gating decisions (`Commit#deployable?`/statuses), so this enables an entity with legitimate signing rights for one low-trust organization to fabricate a passing CI status for a commit in a completely unrelated, higher-trust repository, potentially enabling an unauthorized deploy of unreviewed/untested code.
- `PushHandler`/`CheckSuiteHandler` let the same signer trigger `stack.sync_github`/`schedule_refresh_check_runs!` for stacks belonging to organizations they were never authenticated for, by supplying an arbitrary `repository.full_name` while signing with their own org's secret.

This matches the "unauthorized deploy" / "cross-repository writes" impact tier.

### Likelihood Explanation
Requires only capabilities the engine's own documented multi-tenant configuration grants to a legitimately onboarded (but lower-privileged, unrelated-repo) organization: knowledge of that organization's own `webhook_secret`, which they are expected to have as the owner/administrator of their own GitHub App installation. No GitHub session, `ApiClient` token, `api_clients_secret`, repository write access to the victim repo, or any Shipit account is needed — only a raw HTTP POST to the public `/webhooks` endpoint with a body they fully control. The vulnerability is a straightforward mismatch between two independently-parsed fields in the same request, not a theoretical edge case.

### Recommendation
Bind the field used for signature/organization selection to the same field used for locating the write target: e.g., require that the resolved GitHub App organization for `repository_owner` matches the owner segment of `repository.full_name` (and, ideally, look up `Repository`/`Commit` scoped to that verified organization) before dispatching to handlers. `StatusHandler` in particular must scope its `Commit` lookup by the verified repository instead of a global SHA search.

### Proof of Concept
Given a Shipit instance configured per `docs/setup.md`'s multi-organization example with `OrgOne` and `OrgTwo` each having distinct `webhook_secret`s, an entity that only knows `OrgOne`'s webhook secret can forge a `status` event body:
```json
{
  "sha": "<victim-org-two-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "description": "forged by OrgOne signer",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "OrgOne" } }
}
```
Sign the raw JSON body with `HMAC-SHA1(OrgOne_webhook_secret, body)`, set `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: status`, and POST to the webhooks endpoint. `verify_signature` resolves `Shipit.github(organization: "OrgOne")` and validates successfully [10](#0-9) ; `StatusHandler#process` then updates the status of `<victim-org-two-commit-sha>` regardless of which organization it actually belongs to [5](#0-4) .

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
