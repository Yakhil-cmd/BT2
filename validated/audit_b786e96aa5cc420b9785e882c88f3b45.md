### Title
CCMenu API endpoint bypasses ApiClient stack scoping, letting a single-stack read-only token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
This confirms the same class of flaw as the Nouns Builder report: a binding created at issuance time (an ApiClient token's authorized scope) is not enforced at usage time, letting a narrowly-scoped credential act beyond the object it was granted for. In Nouns Builder, votes were moved directly between addresses instead of between the delegates the accounting model expected. Here, `Shipit::Api::CCMenuController` loads the target `Stack` directly from request params instead of through the scoped `stacks` accessor that every other API controller uses, so the equality "stack authorized by the token == stack acted upon" is broken.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting accessor: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the `ApiClient` is scoped to a single stack, and `stack` resolves the requested `params[:stack_id]`/`params[:id]` only within that scoped set (see also `Shipit::Api::StacksController#stack`, which correctly reuses `stacks.from_param!`): [2](#0-1) 

`CCMenuController`, however, overrides `stack` to bypass this scoping entirely, loading any stack in the system directly by id/slug regardless of the authenticating `ApiClient`'s `stack_id`: [3](#0-2) 

The controller still calls `require_permission :read, :stack`, but `ApiClient#check_permissions!` only checks that `"read:stack"` is present in the token's `permissions` array - it never compares `stack_id`: [4](#0-3) 

Tokens intended to be scoped to exactly one stack are minted by `CCMenuUrlController`, which explicitly creates a single-stack, read-only `ApiClient` and embeds its `authentication_token` in a URL meant to be shared with external CI dashboards/widgets: [5](#0-4) 

Because `CCMenuController#stack` ignores `current_api_client.stack_id`, any holder of one such CCMenu URL/token - which is deliberately low-privilege and designed to be embedded/shared outside the trust boundary of the full Shipit UI - can substitute any other `stack_id`/`stack_slug` in the URL and read that other stack's latest deploy/rollback status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, activity, etc.) through the same token.

### Impact Explanation
This is an authorization-scope escalation: a token explicitly authorized only for "read:stack" on **stack A** is usable to read state of **any stack** in the Shipit instance, including stacks belonging to different repositories/teams the token holder was never granted access to. This matches the specified High-impact category "escalation into `Shipit.github_teams` authorization... or unauthenticated read of stack state, task streams or deploy output" from the perspective of the CCMenu token holder, since possession of one narrowly-scoped, shareable token becomes equivalent to possession of a global read:stack token. It does not, by itself, allow writes, deploys, or credential exfiltration - the token still can only read the CCMenu XML view (build status), so the impact is bounded to unauthorized read access rather than RCE or unauthorized deploy.

### Likelihood Explanation
Likelihood is moderate-to-high in any Shipit deployment where CCMenu integration is used: these tokens are specifically designed to be embedded in third-party CI dashboard tools and shared outside of the primary authenticated UI, increasing the chance of exposure/leakage of one token. Once any single CCMenu token is obtained, exploitation requires nothing more than changing the `stack_id` request parameter - no additional secrets, signatures, or GitHub credentials are needed.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` accessor (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`. Add a regression test asserting that a CCMenu token scoped to stack A returns 404/403 when `stack_id` is swapped for stack B.

### Proof of Concept
1. As an authenticated Shipit user, open the CCMenu URL for **Stack A** via `CCMenuUrlController#fetch`, which creates an `ApiClient` scoped to Stack A with `permissions: %w[read:stack]` and returns a URL like `.../api/stacks/:stack_a_id/ccmenu.xml?token=<TOKEN_A>`.
2. As an unprivileged attacker in possession only of `TOKEN_A` (e.g. scraped from an embedded CI dashboard), send a request to the same endpoint but substitute Stack B's id/slug: `.../api/stacks/:stack_b_id/ccmenu.xml?token=<TOKEN_A>`.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `current_api_client.stack_id` scoping enforced everywhere else), the request succeeds and returns Stack B's `lastBuildStatus`/`lastBuildLabel`/`webUrl`, even though `TOKEN_A` was never authorized for Stack B.

Note: I could not locate the CCMenu XML view template (`app/views/shipit/ccmenu/project.xml.erb`) in the indexed content to confirm the exact fields rendered; this may be due to index size limits excluding view files (which are also out-of-scope per the engine rules, but the controller logic itself, which is in scope, is sufficient to demonstrate the scoping bypass).

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
