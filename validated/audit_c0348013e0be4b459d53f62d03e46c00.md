### Title
Webhook signature verification uses `repository.owner.login`/`organization.login` while every handler acts on the unrelated `repository.full_name` field, letting one authenticated GitHub organization forge writes against another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's webhook secret to validate a payload against using `repository.owner.login` (falling back to `organization.login`). Every `Webhooks::Handlers::Handler` subclass, however, resolves the `Stack`/`Repository` to mutate using a completely different, independently attacker-controlled field: `repository.full_name`. The two fields are never cross-checked, so the organization whose secret authenticates a request is not bound to the organization/repository the request actually writes to.

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` keyed by org, as documented in `docs/setup.md`), `Shipit.github(organization: X)` returns the `GitHubApp` (and webhook secret) registered for organization `X` [1](#0-0) .

`WebhooksController#verify_signature` picks `X` from the payload itself, not from any authenticated channel: [2](#0-1) [3](#0-2) 

Once the signature check passes, `create` dispatches the raw JSON `params` unmodified to every registered handler for the event: [4](#0-3) 

Every handler, however, resolves which `Repository`/`Stack` to act on using `repository.full_name`, a different key of the same payload: [5](#0-4) [6](#0-5) 

The lookup itself only trusts the caller-supplied string, splitting it on `/` with no validation that it matches the organization used for authentication: [7](#0-6) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the actual write target) are two independent JSON fields inside the same payload, an attacker can set them to different organizations. The HMAC signature covers the raw body, but `/webhooks` is a public, unauthenticated HTTP endpoint reachable by anyone on the internet (not restricted to GitHub's IPs), so an attacker who legitimately owns/administers their own GitHub App+org configured in the same multi-tenant Shipit instance (`AttackerOrg`, with a webhook secret they know because they created that App) can:

1. Craft a JSON body with `repository.owner.login = "AttackerOrg"` and `repository.full_name = "VictimOrg/victim-repo"` (a real Stack belonging to a different, unrelated tenant of the same Shipit instance).
2. Compute a valid `X-Hub-Signature` using `AttackerOrg`'s own webhook secret.
3. POST it directly to `/webhooks`.

`verify_signature` fetches and validates against `AttackerOrg`'s secret (since `repository_owner == "AttackerOrg"`) and succeeds. The handler that runs afterward, however, resolves the target `Repository`/`Stack` via `repository.full_name == "VictimOrg/victim-repo"`, completely bypassing the fact that `VictimOrg` never authenticated this request.

This breaks exactly the invariant: `organization that authenticated the webhook == organization/repository actually written to`, matching the analog binding class this scan is validating.

### Impact Explanation
Depending on which handler fires, this allows an attacker who only controls their own org's GitHub App/webhook secret to make Shipit perform state-changing actions against a completely unrelated tenant's stack, e.g.:
- `PushHandler` forces `GithubSyncJob`/`stack.sync_github` on the victim's stack with an attacker-chosen `expected_head_sha`.
- `PullRequest::*Handler`s (`ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `AssignedHandler`, `EditedHandler`) directly `archive!`/`unarchive!` the victim's review stacks and overwrite stored `github_pull_request`/label data in Shipit's own database using attacker-supplied JSON, with no relation to the org that was actually authenticated.

This is a cross-tenant/cross-repository write achieved without any credential belonging to the victim organization — matching the Critical "cross-repository writes" impact bucket.

### Likelihood Explanation
Requires only that the attacker legitimately controls one organization/App already configured on the same shared multi-tenant Shipit instance (a realistic, low-privilege scenario for any SaaS-style shared Shipit deployment) and can freely POST to the public `/webhooks` endpoint. No Shipit session, `ApiClient` token, TLS interception, or victim credentials are needed.

### Recommendation
Bind the signature-verification organization to the same field used for repository/stack resolution: derive both from `repository.full_name`'s owner segment (or otherwise validate that `repository.owner.login`/`organization.login` matches the owner portion of `repository.full_name`) before dispatching to handlers, and reject the request if they diverge.

### Proof of Concept
1. In a multi-org Shipit deployment, register `AttackerOrg` (attacker-owned GitHub App, secret known to attacker) and confirm `VictimOrg/victim-repo` is a real Stack on the same instance.
2. Build a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(body, AttackerOrg_webhook_secret)>`.
4. `POST /webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `verify_signature` succeeds (validated against `AttackerOrg`'s secret) per `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`; `PushHandler#process` then resolves and syncs the `VictimOrg/victim-repo` stack per `app/models/shipit/webhooks/handlers/handler.rb:30-38` and `push_handler.rb:12-17`, despite `VictimOrg` never having authenticated the request.
