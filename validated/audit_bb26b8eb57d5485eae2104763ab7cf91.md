### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the stack acted upon is selected by the independent `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the `Shipit::GitHubApp` (and thus the webhook secret) to validate a signature with by reading `repository.owner.login` (or `organization.login`) out of the **unverified** JSON body, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature` [3](#0-2) . Once the signature check passes, `Handler#stacks` resolves the actual `Stack`/`Repository` that gets acted on using a completely different field, `repository.full_name` [1](#0-0) . Nothing enforces that `full_name`'s owner matches `owner.login`.

### Finding Description
Shipit supports hosting multiple GitHub organizations, each with its own app config/`webhook_secret`, keyed by organization name in `secrets.github` [4](#0-3) ; the app config, including `webhook_secret`, is per-organization [5](#0-4) . Any org configured with `webhook_secret: nil` causes `verify_webhook_signature` to unconditionally return `true`, skipping verification entirely for that org [6](#0-5) , and the setup docs explicitly show that as a normal, supported configuration [7](#0-6) .

An attacker who controls (or is a legitimate collaborator of) *any one* organization onboarded to this Shipit instance — call it `AttackerOrg` — can send a `push` event whose top-level `repository.owner.login` is `AttackerOrg` (so the controller loads `AttackerOrg`'s webhook secret, which the attacker knows or which is `nil`) while setting `repository.full_name` to `VictimOrg/victim-repo`, a repository belonging to an unrelated organization also hosted by this Shipit instance. The signature check in `WebhooksController#verify_signature` passes because it only checks the payload's HMAC against `AttackerOrg`'s secret [3](#0-2) . Processing then proceeds through `PushHandler#process`, which uses `Handler#stacks`, itself derived from `payload.dig('repository', 'full_name')` = `VictimOrg/victim-repo` [8](#0-7) [1](#0-0) . This enqueues `GithubSyncJob` for the victim's real `Stack`, which then fetches commits and appends them using `Shipit.github(organization: repository.owner)` derived from the *actual* victim repository record — meaning `stack.sync_github` will proceed against the real victim repo/org using the app's legitimate GitHub credentials for that org [9](#0-8) [10](#0-9) .

This is the direct analog of the [M-05] bug class: the report's `interest`/`loan.loanAmount` transfer executed on data never covered by the check that was supposed to gate it (`lastAccumulatedTimestamp`). Here, the signature check covers `X-Hub-Signature` over the raw body, but the *decision of whose secret to check against* is taken from a payload field (`repository.owner.login`) that is disjoint from the field actually used to select and mutate state (`repository.full_name`). The binding broken is: `organization authenticated (repository.owner.login) == repository written (repository.full_name)` — and nothing in the engine enforces that equality.

### Impact Explanation
This crosses a genuine authentication boundary between tenants of a single multi-org Shipit deployment: a user who is only authorized (or webhook-trusted) for `AttackerOrg` can forge sync events for `VictimOrg`'s stacks without ever knowing `VictimOrg`'s webhook secret. While `push`/sync itself "only" causes `Stack#sync_github` to run (fetching commits via the app's GitHub credentials and appending `Commit` records), other webhook-driven handlers (e.g. `status`, `check_suite`, `membership`, `pull_request`) key off the same unauthenticated cross-check pattern (`Handler#repository_name`) and can affect commit statuses, merge-queue state, and team/user membership for a stack the attacker does not otherwise control — an unauthorized write into another organization's Shipit state, satisfying the "cross-repository writes" / "unauthorized deploy pipeline manipulation" bar.

### Likelihood Explanation
Requires the deployment to be configured for multiple GitHub organizations (a documented, supported configuration in `docs/setup.md`) and requires the attacker to control (or know the webhook secret of, or have it be `nil` for) at least one of the onboarded organizations — a low bar for an "unprivileged" outsider onboarding their own org to a shared Shipit instance, which is a realistic SaaS/shared-instance scenario this engine explicitly supports.

### Recommendation
After verifying the HMAC signature, re-derive `repository_owner` from the same trusted source used for verification and require that `payload.dig('repository', 'full_name')`'s owner component matches it (or, simpler, always use the verified `repository_owner` — not a fresh read of `full_name` — to resolve the `Repository`/`Stack` in `Handler#stacks`). Reject the webhook if the two disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` (attacker-controlled, `webhook_secret: nil` or known) and `VictimOrg` (hosting a real stack for `VictimOrg/victim-repo`), per `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, or a real victim commit sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and validates against `AttackerOrg`'s secret (or passes unconditionally if that org has no secret) — request succeeds.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victimorg/victim-repo")`, matching the real victim stack, and enqueues `GithubSyncJob` for it, causing Shipit to fetch/append commits for the victim repository triggered entirely by an actor who only controls `AttackerOrg`.
