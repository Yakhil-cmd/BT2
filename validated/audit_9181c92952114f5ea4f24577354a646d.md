Based on my research, I found a genuine local admission-boundary flaw in the multisig transaction execution path: the on-chain payload binding check can be entirely skipped depending on how the multisig transaction was proposed and a feature flag, meaning owner approvals for one action can be silently redirected to execute a different action.

### Title
Multisig payload binding is skipped for full-payload proposals when `abort_if_multisig_payload_mismatch` is disabled, allowing execution of an unapproved payload - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`validate_multisig_transaction`, invoked by the VM prologue for every `MultisigTransaction` [1](#0-0) , is supposed to guarantee that the payload an executing owner submits with their transaction is the same payload that other owners approved. The Move implementation only enforces this binding in two disjoint paths, and one of them is feature-gated and conditioned on the payload not being empty, leaving a gap for transactions created via `create_transaction` (full payload stored on-chain).

### Finding Description
`multisig_account::validate_multisig_transaction` [2](#0-1)  performs quorum counting against a `sequence_number` slot, then attempts to bind the *content* being executed to what was approved:

```
if (transaction.payload_hash.is_some()) {
    assert!(sha3_256(payload) == *payload_hash, ...);
};

if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    assert!(payload == *stored_payload, ...);
}
```

A `MultisigTransaction` created via `create_transaction` (as opposed to `create_transaction_with_hash`) stores the full payload and has `payload_hash = None` [3](#0-2) . For such a transaction:
- The first `assert` (hash comparison) is skipped entirely because `payload_hash.is_some()` is `false`.
- The second `assert` (direct payload comparison against `transaction.payload`) only fires when the `abort_if_multisig_payload_mismatch_enabled` feature is turned on *and* the caller-provided `payload` is non-empty.

If that feature is not enabled on a given network/epoch, there is **no check at all** binding the `payload` an executing owner passes at execution time to the `payload` that was actually approved by the multisig owners at creation/vote time. The quorum check only verifies that *some* transaction exists at the resolved `sequence_number` with enough approvals — it never verifies *which* transaction content those approvals were cast for when the full-payload flow is used.

Separately, `run_multisig_prologue`/`execute_multisig_transaction` compute `provided_payload` from the *current* transaction's own `TransactionExecutableRef` (the entry function/script the executor is submitting right now) [4](#0-3)  — this is what actually gets executed as the multisig account, not a reconstruction from the stored `MultisigTransaction.payload`. This confirms the design intent that the stored payload is the *sole* authorization artifact for full-payload proposals, and its comparison is the only thing standing between "approved action" and "executed action."

### Impact Explanation
This is an unauthorized-state-transition / wrong-approval-set admission bug matching the required impact class: "Authenticator, WebAuthn, multisig, or approval validation accepting the wrong signing material or wrong approval set" and "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit." An owner (or colluding minority of owners meeting the k-of-n threshold) who obtained approvals for a benign action (e.g. "transfer 1 APT to owner A") can, at execution time, submit an entirely different entry function/script (e.g. draining funds, rotating keys, adding a malicious owner) as the multisig account's transaction, and it will execute successfully because nothing checks that the executed payload matches what was voted on. This breaks the fundamental multisig security guarantee (execution requires approval *of that specific action*) and results in the multisig account performing state transitions its owners never approved — a critical authorization bypass at the transaction admission boundary.

### Likelihood Explanation
Likelihood depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active on the target network/epoch. The existence of a dedicated feature flag specifically for enforcing this comparison strongly suggests this check was historically absent and is being rolled out gradually; any deployment, testnet, devnet, or subnet where the flag has not yet been activated is exposed. I was not able to confirm within available tool calls whether this flag defaults to on or off on mainnet at HEAD of this repo snapshot, which is a limitation of this analysis — this should be verified against the live on-chain `Features` bitmap and `feature_flags.rs` release configuration before treating this as exploitable in production.

### Recommendation
Make the payload-vs-stored-payload comparison for full-payload multisig transactions unconditional (not gated behind `abort_if_multisig_payload_mismatch_enabled`), or require `transaction.payload_hash` to always be set (i.e., deprecate/require hashing for `create_transaction` as well) so that `validate_multisig_transaction` always cryptographically binds the executed payload to what owners approved, regardless of feature-flag state.

### Proof of Concept
1. Owner A creates a multisig account requiring 1 signature (`num_signatures_required = 1`) or obtains enough colluding owners to hit the threshold.
2. Owner A calls `create_transaction(owner, multisig_account, payload_A)` where `payload_A` is a benign, publicly reviewed entry function call (full payload stored on-chain, `payload_hash = None`).
3. Other owners approve based on reviewing `payload_A`, reaching quorum.
4. On a network where `abort_if_multisig_payload_mismatch_enabled` is disabled, Owner A submits a `MultisigTransaction` execution with a *different*, malicious `executable` (e.g., `payload_B` draining the account) instead of `payload_A`.
5. `validate_multisig_transaction` skips the hash check (`payload_hash` is `None`) and skips the direct comparison (feature disabled), so quorum is confirmed purely by `sequence_number` and vote count.
6. `execute_multisig_transaction` executes `payload_B` (the actually-submitted executable) as the multisig account signer — an action that was never approved by the other owners.

pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };

    session
        .execute_function_bypass_visibility(
            &MULTISIG_ACCOUNT_MODULE,
            VALIDATE_MULTISIG_TRANSACTION,
            vec![],
            serialize_values(&vec![
                MoveValue::Signer(txn_data.sender),
                MoveValue::Address(multisig_address),
                MoveValue::vector_u8(provided_payload),
            ]),
            &mut UnmeteredGasMeter,
            traversal_context,
            module_storage,
        )
        .map(|_return_vals| ())
        .map_err(expect_no_verification_errors)
        .or_else(|err| convert_prologue_error(err, log_context))
}

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }
