Confirmed: `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb`) matches commits solely by `Commit.where(sha: params.sha)` with no repository/stack scoping, then invokes `commit.create_status_from_github!(params)` on every match. Since `Commit belongs_to :stack` and any two independently-provisioned stacks (from unrelated GitHub repositories, e.g. a fork sharing base-commit SHAs, or a monorepo split across multiple Shipit stacks) can each hold a `Commit` row with an identical `sha`, a single signed webhook triggers writes across every stack that happens to share that SHA — not just the repository that authenticated the webhook.

### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets one repository's status webhook mutate CI state on unrelated stacks/repositories - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no filter on `stack_id`/`repository`, so a legitimately signed status webhook from one GitHub repository can write a `Status` row onto `Commit` records belonging to a completely different stack that happens to share the same commit SHA (e.g., a fork of a victim repository, or shared history across multiple stacks). This breaks the implicit invariant that a status for context `ci/smoke` should only affect the repository whose webhook secret authenticated the event.

### Finding Description
The broken binding: the code assumes `sha ⟺ repository`, i.e. `Commit.where(sha: params.sha)` is treated as equivalent to "commits belonging to the repository that authenticated this webhook," but SHA is not unique per repository — `Commit` rows are keyed by `(stack_id, sha)`, not by `sha` alone.

Path: `Shipit::WebhooksController#create` parses the raw payload, `verify_signature` validates the HMAC using `Shipit.github(organization: repository_owner)` [1](#0-0) , then dispatches to `Shipit::Webhooks.for_event(event)` handlers, including `StatusHandler` [2](#0-1) . `StatusHandler#process` does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This query has no `stack_id`, `repository`, or `github_repo_name` filter — it matches every `Commit` in the entire Shipit instance sharing that SHA, across every stack/repository. `create_status_from_github!` then calls `add_status`, which evaluates `deployable?`/`blocked?` and, on a state transition, calls `stack.schedule_merges` and, via `after_create`/status changes, can trigger `ContinuousDeliveryJob` / `trigger_continuous_delivery` on the victim stack [4](#0-3) [5](#0-4) .

The attacker's request: any repository the attacker legitimately controls that is connected to Shipit (their own fork/CI) sends a real, GitHub-signed `status` event with `context: ci/smoke`, `sha` equal to a commit that also exists (with the identical SHA) in a victim stack's `commits` table (plausible for forks, cherry-picks, or shared monorepo history), and `state: success` (or `failure`). Because `verify_signature` only checks that the payload was signed by the org that owns the *sending* repository — it never checks that the resolved `Commit` rows actually belong to that org/repository — the write reaches the victim stack's commit unimpeded.

Existing guards do not catch this: `verify_signature` authenticates the source org/repo but is not consulted again when resolving which `Commit` rows to update [6](#0-5) ; the `ExplicitParameters` schema only validates presence/type of `sha`, `state`, `context`, not repository ownership [7](#0-6) ; and `Commit` model validations don't enforce SHA uniqueness across stacks.

### Impact Explanation
A status/CI-state write intended for the attacker's own repository lands on an unrelated victim stack's commit. If the victim stack is a production environment requiring `ci/smoke`, this can flip a commit from blocked/pending to `deployable?`, causing `stack.schedule_merges` and continuous delivery to trigger a deploy of attacker-uncontrolled but now falsely-"passing" code, or conversely force a false `failure`/blocking status to halt a legitimate victim deploy. This is a cross-tenant write — "a payload for one repository mutating another's stack, commit" — matching the Critical category (unauthorized deploy/rollback triggered from a payload that did not authenticate for that repository).

### Likelihood Explanation
Preconditions: the victim stack must contain a `Commit` row with a SHA identical to one the attacker can produce a signed webhook for. This is realistic for forked repositories (shared base history yields identical SHAs) or organizations running multiple Shipit stacks over overlapping/shared git history (e.g., monorepo split into several stacks, or a shared library repo). The attacker only needs to control one legitimately Shipit-connected repository (their own fork, or any repo they can push CI signals from) — no Shipit credentials, session, or `webhook_secret` for the victim's org are required. This is fully repeatable per shared SHA and requires no privileged role.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the analogous `check_run`/CI handlers) by the reporting repository, e.g. join through `stack` and filter by `github_repo_name`/`repository.full_name` matching the payload's `repository.full_name`, instead of matching on bare `sha` across all stacks: `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repo_owner: owner, repo_name: name })`.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, hypothetical — not present today):
1. Create `stack_a` for repo `attacker/repo` and `stack_b` for repo `victim/repo`, with `stack_b.environment = 'production'` and deploy spec `ci.require = ['ci/smoke']`.
2. Create `Commit` rows with the identical `sha = "deadbeef..."` under both `stack_a` and `stack_b` (simulating shared history/fork).
3. Assert baseline: `stack_b`'s commit is not `deployable?` (missing `ci/smoke`) — i.e., `refute commit_b.deployable?`.
4. Build `params` for `StatusHandler` with `sha: "deadbeef...", context: "ci/smoke", state: "success"` (as would be signed by `attacker/repo`'s webhook secret) and call `StatusHandler.new(params).process` (or `.call`).
5. Reload `commit_b`; assert the equality that should NOT hold but does: `commit_b.statuses.exists?(context: "ci/smoke", state: "success")` is `true`, and `commit_b.deployable?` is now `true` — despite the webhook never having been signed by/for `victim/repo`.
6. Assert this demonstrates the broken binding: `sha` uniquely identifying a repository's commit is false; the fix should scope the query so step 5's assertions fail (no status written to `commit_b`).
