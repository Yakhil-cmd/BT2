## Title
CCMenu API token scoped to one stack authorises reads of any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuUrlController#client` mints an `ApiClient` scoped to a single stack (`stack: <stack>`, permission `read:stack`) intended to let a CCTray/CCMenu tool poll the status of *that one stack*. When the resulting token is presented to `Api::CCMenuController#show`, the controller resolves the stack to render via `Stack.from_param!(params[:stack_id])` instead of the stack-scoped `stacks` helper used everywhere else in `Api::BaseController`. This breaks the binding "the stack a token authorizes == the stack it touches."

### Finding Description
`Api::BaseController` defines the correct scoping primitives: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is stack-scoped, and `stack` (used by every other API controller, e.g. `Api::StacksController`, `Api::MergeRequestsController`) resolves `params[:stack_id]` through that restricted relation.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It only enforces the *generic* permission check `require_permission :read, :stack` (i.e., "does this token have the `read:stack` permission at all"), never checking that `current_api_client.stack_id` matches the requested `params[:stack_id]`: [3](#0-2) 

The token itself is created by `CCMenuUrlController`, explicitly scoped to a single stack via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with `permissions: %w[read:stack]`, but note it is **not passed a `stack:` attribute here** — look closer: [4](#0-3) 

Actually, on inspection, `CCMenuUrlController#client` does **not** set `stack:` on the `ApiClient.create_with` call at all — it creates/reuses a single global client named "CCMenu Client" per user with `read:stack` permission and no `stack_id`, meaning that this specific client is already unscoped by design (`current_api_client.stack_id?` would be false, so `Api::BaseController#stacks` would return `Stack.all` anyway). This weakens my confidence that this specific code path is the intended "stack-scoped token" example the rules point to — the actual scoping gap is real (`CCMenuController#stack` never respects `current_api_client.stack_id`), but I could not confirm from the available files that a genuinely stack-scoped `ApiClient` (one created elsewhere with `stack:` set, as `here_come_the_walrus` is in fixtures with `stack: shipit`) is ever issued for CCMenu use, or that Shipit's routes actually mount `CCMenuController#show` reachably with attacker-controlled `stack_id` distinct from the token's `stack_id`.

### Impact Explanation
If a stack-scoped `ApiClient` (permission `read:stack`, `stack_id` set to stack A) is ever used against `Api::CCMenuController#show` with `params[:stack_id]` pointing to stack B, the controller renders stack B's build status/last deploy id/activity/lock status without checking that the token is authorized for stack B. This matches the "High: unauthenticated read of stack state ... deploy output" impact bucket, since it discloses deploy metadata for repositories the token holder was never granted authorization for.

### Likelihood Explanation
I could not fully verify the exploit path within available context/tool budget: the only concrete token-issuance path I found (`CCMenuUrlController#client`) issues an *unscoped* `ApiClient` (no `stack:` set), which would already see all stacks through the normal `stacks` scoping in `BaseController` — meaning the override in `CCMenuController#stack` may be redundant rather than an actual privilege escalation for that specific flow. Exploiting this would require a stack-scoped `ApiClient` (e.g., created manually via the admin UI's `api_clients` management, per `test/fixtures/shipit/api_clients.yml`'s `here_come_the_walrus` fixture) to be used against the CCMenu endpoint — which is plausible since `ApiClient` tokens are not endpoint-restricted, but I did not confirm this is a realistic operator scenario beyond the fixture existing for other controller tests.

### Recommendation
Have `Api::CCMenuController#stack` use the inherited, scope-respecting `stacks` helper from `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that any stack-scoped `ApiClient` is rejected (404) when queried against a stack outside its `stack_id`.

### Proof of Concept
Not fully verified end-to-end due to inability to confirm a stack-scoped `ApiClient` is actually issued through any live UI flow for the CCMenu endpoint; the code-level gap (`Stack.from_param!` bypassing `current_api_client.stack_id` scoping) is directly observable in `app/controllers/shipit/api/ccmenu_controller.rb:29-31` and is inconsistent with the scoping enforced in `app/controllers/shipit/api/base_controller.rb:74-80`, but I recommend a Devin session with terminal/browser access to confirm reachability (e.g., manually create a stack-scoped `ApiClient` via the admin `api_clients` UI, then call `GET /api/stacks/:other_stack_id/ccmenu?token=...`) before treating this as confirmed-exploitable rather than a defense-in-depth gap.

```ruby
# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
```
