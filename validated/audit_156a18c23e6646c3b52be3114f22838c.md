This is a valid multi-tenant analog. `Shipit.github(organization:)` supports multiple GitHub App configs keyed by organization name under `secrets.github` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` [2](#0-1) . But the handlers that actually act on the payload (finding the `Repository`/`Stack` to write to) use a *different field of the same JSON body*, `payload.dig('repository', 'full_name')` [3](#0-2) , and `Shipit::Repository.from_github_repo_name` derives owner/name purely by splitting that `full_name` string [4](#0-3) .

### Title
Webhook signature verification key is selected by `repository.owner.login`/`organization.login` but writes are routed by `repository.full_name`, allowing a valid tenant to forge cross-organization webhook events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` verifies the HMAC signature using the webhook secret belonging to the organization named in `repository.owner.login`/`organization.login`, while the handlers that perform writes (creating statuses, syncing stacks, archiving/unarchiving review stacks, deleting review stacks, etc.) resolve the target `Repository`/`Stack` from the independent `repository.full_name` field. Because both fields are attacker-controlled JSON fields inside a payload that the attacker legitimately signs with their own organization's webhook secret, an attacker who controls (and has legitimately registered) one organization's GitHub App/webhook secret in the same Shipit instance can craft a payload whose `owner.login` matches their own org (so the signature check against their own secret succeeds) but whose `repository.full_name` names a repository/stack belonging to a different organization, causing Shipit to execute writes against that other organization's stack.

### Finding Description
`Shipit.github(organization:)` looks up per-organization GitHub App configuration (`app_id`, `webhook_secret`, `private_key`, etc.) from `secrets.github`, keyed by organization name [1](#0-0) . `WebhooksController#verify_signature` picks which of these per-org secrets to validate the raw request body against based solely on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [5](#0-4) . Once `verified` is true, `create` dispatches the entire raw payload to every handler registered for the `X-Github-Event` header, unconditionally: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .

Handlers never re-check `repository.owner.login` against the field they use to select the target: `Handler#repository_name` reads `payload.dig('repository', 'full_name')` directly [3](#0-2) , and pull-request handlers do the same via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [7](#0-6) . `Repository.from_github_repo_name` simply splits that string on `/` to get `owner`/`name` and looks up the DB record — it performs no cross-check against the org whose secret validated the signature [4](#0-3) .

Binding that should hold but doesn't: `verified-signing-org(payload.repository.owner.login) == target-org(payload.repository.full_name.split('/').first)`. Before the attack, both fields naturally agree for legitimate GitHub-generated webhooks. An attacker who is a legitimate GitHub App owner for `org-a` in the same Shipit instance can send a POST to `/github_authentication/../webhooks` (or wherever `WebhooksController` is mounted) with a body they sign with `org-a`'s `webhook_secret`, setting `repository.owner.login = "org-a"` (so `verify_signature` picks `org-a`'s secret and passes) while setting `repository.full_name = "org-b/victim-repo"`. This is exactly analogous to H-02's pattern where the entity that authenticated/authorized an operation (the organization whose signature validated) differs from the entity actually operated on (the repository written to).

### Impact Explanation
Depending on the event type sent, this can lead to unauthorized cross-organization writes: e.g. `push` events trigger `stack.sync_github(expected_head_sha: params.after)` on stacks under a foreign organization's repository [8](#0-7) , `status` events create/update commit statuses that can gate deploys, and `pull_request` labeled/unlabeled/opened/closed events can archive, unarchive, or provision review stacks belonging to `org-b` [9](#0-8) . Since Shipit deploy/rollback pipelines rely on commit status and stack sync state to gate ships, forged status/push events for a foreign org's stack can be used to manipulate deploy gating or trigger unwanted syncs/rollback-relevant state changes, meeting the "cross-repository writes" / "unauthorized deploy" criteria.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (the `secrets.github` keyed-by-org schema in `lib/shipit.rb` lines 183-200), and requires the attacker to control a legitimate GitHub App/webhook secret for at least one of those organizations. This is a realistic deployment mode explicitly supported by the engine (`github_app_config`, `github_organizations`) [10](#0-9) , but it is not the common single-org Shipit setup, so exploitability depends on the specific multi-tenant deployment.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, re-derive `repository_owner` from the same field the handlers use for repository resolution (`repository.full_name`'s owner segment), and reject (422) if it doesn't match the organization whose secret validated the signature. Alternatively, have `Handler#stacks`/`Repository.from_github_repo_name` accept and enforce the verified organization explicitly, rather than trusting `full_name` unchecked.

### Proof of Concept
Conceptual (multi-org Shipit instance with `org-a` and `org-b` configured under `secrets.github`):
```
POST /webhooks  (mounted WebhooksController)
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(org-a.webhook_secret, body)>

{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
`verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and successfully verifies the signature (attacker legitimately owns `org-a`'s webhook secret) [11](#0-10) . `PushHandler#process` then resolves stacks via `Handler#stacks` → `Repository.from_github_repo_name("org-b/victim-repo")` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack [8](#0-7) , an operation the attacker was never authorized to trigger for `org-b`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

    github_config[github_organization]
  end

      verified = github_app.verify_webhook_signature(
