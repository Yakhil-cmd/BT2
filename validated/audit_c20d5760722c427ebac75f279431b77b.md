### Title
Cross-repository forged GitHub status accepted by `StatusHandler#process` due to missing repository scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone across the entire `Commit` table, with no constraint tying the lookup to the repository that authenticated the webhook. Unlike `PushHandler` and `CheckSuiteHandler`, which scope through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`), `StatusHandler` never reads or validates `payload['repository']` at all, so a validly-signed webhook from an attacker-owned repository can write a `Status` onto a commit belonging to a completely different repository/stack, as long as the SHA matches (trivially achieved via forking, since git commit SHAs are content-addressed and preserved across forks).

### Finding Description
The broken binding is: `Status.stack_id` (and the commit it is attached to) should equal `Stack(repository == payload['repository']['full_name'])`, but instead `StatusHandler#process` does: [1](#0-0) 

There is no `requires :repository` in its `params` schema and no use of the `stacks` helper that every other handler relies on for scoping: [2](#0-1) 

Compare with `PushHandler#process`, which correctly resolves the repository from the payload before touching any stack: [3](#0-2)  and `CheckSuiteHandler#process`, which does the same: [4](#0-3) .

`WebhooksController#verify_signature` only proves that the payload was genuinely emitted by GitHub for the *organization* named in `params.dig('repository','owner','login')`, using a webhook secret configured per organization/installation, not per specific repository-to-commit binding: [5](#0-4) . Nothing after signature verification checks that the SHA in the `status` payload actually belongs to the repository that signed the webhook.

Exploit flow: the attacker forks the victim's public repository (or otherwise legitimately owns a GitHub repository onboarded to the same Shipit instance/organization, which the threat model explicitly allows: "push to a fork... emit webhooks from a repository they own"). Because git objects are content-addressed, commits shared with the upstream victim history keep identical SHAs in the fork. The attacker POSTs a `status` event to `/webhooks` with `X-Github-Event: status`, a valid signature for their own org/repo, `sha` = the victim's mid-queue commit SHA, and `state: success`. `StatusHandler#process` finds the victim's `Commit` purely by SHA and calls `commit.create_status_from_github!(params)`, creating a `Status` row whose `stack_id` is taken from the victim commit's own stack (`Commit#create_status_from_github!` / `add_status`, whose hooks reference `commit.stack`): [6](#0-5) .

This forged success status changes `Commit#deployable?`/`UndeployedCommit#deployable?`, which feeds `Stack#next_expected_commit_to_deploy`: [7](#0-6)  and `Stack#next_commit_to_deploy` used directly by `trigger_continuous_delivery`: [8](#0-7) . With `maximum_commits_per_deploy` set and a real failing commit ahead of it in the queue, the newly-"passing" middle commit becomes the selected deploy target, and `UndeployedCommit#expected_to_be_deployed?` also flips for the UI: [9](#0-8) .

None of the existing guards catch this: `verify_signature` authenticates the org, not the SHA-to-repo relationship; `ExplicitParameters` schema for `StatusHandler` doesn't even declare `repository` as required so it can't be checked; there is no `require_permission!`/`stacks` scoping call in this handler at all.

### Impact Explanation
An attacker who owns any repository onboarded to (or sharing an organization/webhook-secret configuration with) the Shipit instance can write arbitrary `Status` records — including forged `success` — onto commits belonging to a victim repository's stack that they do not control, purely by matching a SHA (trivial via forking public repos). This directly changes which commit `ContinuousDeliveryJob`/`Stack#trigger_continuous_delivery` deploys next and what the "expected to deploy" UI indicator shows, constituting an unauthorized manipulation of another repository's deploy ordering — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and enabling attacker-chosen unauthorized deploys. This is repeatable against any repository whose commit history the attacker can replicate SHAs for (i.e., any fork of a public repo), and is not confined to a single tenant.

### Likelihood Explanation
Preconditions: `maximum_commits_per_deploy` set on the victim stack, multiple undeployed commits queued with a genuinely failing commit ahead of the target, and the attacker must possess a validly signed webhook from some repository (achievable simply by owning/forking a repository already permitted to emit webhooks to the Shipit host per the threat model). No Shipit secrets, sessions, or API tokens are required — cost is essentially free (fork + `git push` + one crafted HTTP POST), and it is fully repeatable/automatable across targets.

### Recommendation
Scope `StatusHandler#process` to the repository indicated in the payload the same way `PushHandler`/`CheckSuiteHandler` do: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name`, restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent join), and reject/ignore statuses for commits that do not belong to a stack of the authenticated repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `victim_stack` backed by `Repository(full_name: "victim/repo")` with `maximum_commits_per_deploy: 1`.
2. Create three undeployed commits on `victim_stack`: `commit_a` (oldest, failing status), `commit_b` (middle, no status), `commit_c` (newest, no status) — same SHA value reused for `commit_b` on a second `Repository(full_name: "attacker/fork")`'s stack to simulate the forked-history SHA collision.
3. Assert baseline: `assert_nil victim_stack.next_expected_commit_to_deploy` and `refute commit_b.deployable?`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call({'sha' => commit_b.sha, 'state' => 'success', 'repository' => {'full_name' => 'attacker/fork'}})` (simulating a validly-signed webhook from the attacker's own repo).
5. Assert the binding is broken: `assert_equal commit_b, victim_stack.reload.next_expected_commit_to_deploy` even though the status-producing repository (`attacker/fork`) is not `victim_stack.repository.full_name` — i.e. assert `commit_b.statuses.last.stack_id == victim_stack.id` while `payload['repository']['full_name'] != victim_stack.repository.full_name`.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else

      end
