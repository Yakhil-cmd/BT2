### Title
Cross-organization `pull_request.edited` webhook forgery via `repository_owner` / `repository.full_name` divergence - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` picks the HMAC-verifying `GitHubApp` using `repository_owner`, which falls back to `params.dig('organization', 'login')` whenever the top-level `repository.owner.login` is absent. `EditedHandler`, however, resolves the target repository from `params.repository.full_name`, a field the schema requires but which is independent of `repository_owner`. Because these two lookups are decoupled, an attacker can pick an organization with a lenient/unset `webhook_secret` to pass signature verification while pointing `repository.full_name` at an entirely different organization's repository, causing `Shipit::PullRequest#update` to mutate a record it never authenticated.

### Finding Description
The broken invariant is: `organization_that_verified(request) == organization_that_owns(repository.full_name)`.

- `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . If the top-level `repository` object omits `owner`, this silently falls back to an attacker-supplied `organization.login`.
- `verify_signature` uses that value to select the `GitHubApp` instance: `Shipit.github(organization: repository_owner)` and then calls `verify_webhook_signature` [2](#0-1) . `GitHubApp#verify_webhook_signature` explicitly returns `true` (skips HMAC check entirely) if no `webhook_secret` is configured for that org: `return true unless webhook_secret` [3](#0-2) .
- `EditedHandler`'s schema requires `repository.full_name` but not `repository.owner.login` [4](#0-3) , and the handler resolves the target repository purely from that field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) , then updates the matching `PullRequest` via `pull_request.update(github_pull_request: params.pull_request)` [6](#0-5) .

Exploit request: a JSON body with `action: "edited"`, `organization: {login: "attacker-or-unsecured-org"}`, no `repository.owner`, and `repository: {full_name: "victim-org/victim-repo"}`, plus the required `pull_request`/`sender` sub-objects. If "attacker-or-unsecured-org" is a configured Shipit GitHub org whose `webhook_secret` is unset (a real, documented possibility in multi-org configs, per `GitHubApp#initialize` reading `@config[:webhook_secret].presence` [7](#0-6) ), `verify_signature` accepts the request unconditionally regardless of the `X-Hub-Signature` header's validity. The engine then dispatches to `EditedHandler`, which updates the `PullRequest` belonging to `victim-org/victim-repo`, writing `title`, `state`, `additions`, `deletions`, `user`, `assignees`, `labels`, and `head` commit from the attacker payload [8](#0-7) .

This bypasses the intended guarantee because the verifier selector (`repository_owner`) and the data-consumption key (`repository.full_name`) are two independently attacker-controlled fields that are never cross-checked anywhere in the request path — no code in `WebhooksController` or `EditedHandler` asserts that the verifying organization matches the repository owner encoded in `repository.full_name`.

### Impact Explanation
An attacker who can identify (or, in a self-service/multi-tenant Shipit deployment, register) one organization with no `webhook_secret` configured can forge webhooks that mutate `PullRequest` records — including which commit (`head.sha`), user, assignees, and labels are attached — for any *other* organization's repository tracked by Shipit, without ever possessing that organization's `webhook_secret`. This is a cross-tenant state-manipulation vulnerability: one repository's forged payload mutates another repository's persisted state, matching the Critical impact category (payload for one repository mutating another's stack/commit/task/team-adjacent record).

### Likelihood Explanation
Exploitability requires a specific but realistic precondition: the Shipit deployment must be running in multi-organization mode (`github_default_organization` present) with at least one configured organization lacking a `webhook_secret`. Given that, the attack requires no credentials, no session, and no valid signature — only a single unauthenticated `POST /webhooks` with a crafted JSON body and an `X-Github-Event: pull_request` header. The request is trivially repeatable against any repository/PR combination known to the attacker (repo full name and PR number), making it cheap and scriptable.

### Recommendation
Bind the value used for signature verification to the same field the handler will consume as the tenant identifier, and refuse to fall back to `organization.login` when `repository` is present but incomplete. Concretely: derive `repository_owner` strictly from `params.dig('repository', 'full_name')`'s owner segment (or require `repository.owner.login` to be present whenever `repository` exists), and reject the request (422) if `repository` is present without `owner`. Additionally, do not treat an absent `webhook_secret` as automatic verification success in multi-org configurations — require every configured GitHub org to declare a real secret, or explicitly opt into "no verification" per org.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "forged pull_request edited event via organization fallback mutates a different org's PullRequest" do
  # Setup: two orgs configured, "leaky-org" with NO webhook_secret, "victim-org" WITH a webhook_secret.
  victim_repo = shipit_repositories(:some_repo_owned_by_victim_org) # full_name: "victim-org/repo"
  victim_stack = victim_repo.stacks.first
  victim_pr = Shipit::PullRequest.create!(stack: victim_stack, number: 42, user: shipit_users(:walrus))

  body = {
    action: 'edited',
    number: 42,
    organization: { login: 'leaky-org' },          # no webhook_secret -> verify_webhook_signature returns true
    repository: { full_name: 'victim-org/repo' },    # no `owner` key -> repository_owner falls back to organization.login
    pull_request: {
      id: 999, number: 42, url: 'https://api.github.com/pr/42',
      title: 'forged title', state: 'open', additions: 1, deletions: 1,
      head: { sha: 'deadbeef', ref: 'evil' },
      user: { login: 'attacker' }, assignees: [], labels: []
    },
    sender: { login: 'attacker' }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=totally-invalid-signature'

  post :create, body:, as: :json
  assert_response :ok

  victim_pr.reload
  # BEFORE == title unchanged, org that "verified" ("leaky-org") != org that owns the mutated record ("victim-org")
  assert_equal 'forged title', victim_pr.title
end
```
This demonstrates that a request "verified" under `leaky-org`'s (secret-less) `GitHubApp` mutates a `PullRequest` record belonging to `victim-org`, confirming the invariant `verifying_org == owning_org` is violated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
