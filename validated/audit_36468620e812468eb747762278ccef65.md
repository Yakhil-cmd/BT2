### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` — ([File: app/models/shipit/commit.rb])

### Summary
`StatusHandler#process` resolves commits purely by SHA, with no check that the payload's `repository` matches the commit's owning stack/repository. Any GitHub repository whose webhooks are routed to the same Shipit instance (e.g. any repo under the same GitHub organization/App installation) can post a `status` event for a commit SHA that also exists in a different stack's history, causing `Commit#create_status_from_github!` to write an attacker-chosen `context`/`state` pair scoped to the victim stack.

### Finding Description
The broken binding: `Status.context/state written for stack_id=A` should equal `the context/state approved by repo A's own CI for that commit`, but the code allows `Status.context/state written for stack_id=A` = `context/state supplied in a webhook payload whose repository field is B`.

Trace:
- `Shipit::WebhooksController#create` dispatches the parsed JSON straight to handlers after `verify_signature`. [1](#0-0) 
- `verify_signature` only checks that the HMAC signature is valid for the GitHub App/organization named by `repository_owner` (derived from the payload's own `repository.owner.login`). It never compares the payload's `repository.full_name` to any stack's configured repository. [2](#0-1) [3](#0-2) 
- `StatusHandler#process` looks up commits by SHA alone, with zero repository/stack filtering, and calls `create_status_from_github!` on every matching row across every stack in the install: [4](#0-3) 
- `Commit#create_status_from_github!` writes the status keyed by `stack_id` taken from the matched `Commit` row (i.e. the victim stack), using whatever `context`/`state` came in the attacker's payload: [5](#0-4) 

Root cause: SHA is treated as a globally unique, self-authenticating identifier tying a status update to "the" owning repository, but nothing in this engine enforces that a given SHA can only be authenticated by the specific repository configured on the stack that recorded it. Because git commit objects (and thus SHAs) can legitimately be shared across multiple repositories under the same GitHub owner/App installation (forks, shared history, cherry-picks, subtree merges), an attacker who controls **any** repository whose webhooks reach this Shipit instance can name that shared SHA and any `context` string (e.g. `ci/required`, learned from stack A's public `shipit.yml` or CI badge) in a real, validly-signed `status` webhook for their own repo B. `verify_signature` will accept it because it only authenticates "this came from GitHub for owner X," not "this SHA belongs to repo B."

Once accepted, `Commit.where(sha:)` matches the pre-existing `Commit` row belonging to stack A (created when Shipit fetched A's real history), and `statuses.replicate_from_github!(stack_id, ...)` persists a `Status` row scoped to `stack_id = A` with the attacker-supplied `context`/`state`. This directly feeds `Commit#blocked?` / `Stack#deployable?` via `stack.blocking_statuses` / `required_statuses`, allowing the attacker to forge a passing `ci/required` status for stack A without ever having CI access to repo A.

Existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) validate webhook authenticity and payload shape, but none of them validate that the payload's `repository` corresponds to the stack that owns the matched commit — the divergence the question describes is real and unmitigated.

### Impact Explanation
An attacker can cause a `Status` record to be written for stack A (a repository they do not control and have no permission over) purely by controlling the payload of a webhook for repository B. This satisfies the explicitly listed Critical category: "a payload for one repository mutating another's stack, commit, task or team." Because `Commit#blocked?` and `Commit#deployable?` consume these `Status` rows directly, this is a forged-CI-signal authentication bypass that can unblock an otherwise CI-gated deploy on stack A — an unauthorized-deploy-enabling condition. The blast radius covers every stack sharing the Shipit instance/App installation with the attacker-reachable repository, i.e., any multi-repo/multi-tenant Shipit deployment where more than one repo's webhooks are verified under the same GitHub App/organization secret.

### Likelihood Explanation
Preconditions: (1) attacker needs push/webhook-triggering capability on some repository B whose webhooks are routed to the target Shipit instance (commonly true in org-wide GitHub App installations, or if the attacker is a legitimate low-privilege contributor on any repo tracked by the same Shipit install); (2) a SHA that is present in both repo B's actual git history and stack A's `commits` table — realistic via forks, shared upstream commits, or subtree/cherry-pick scenarios, not a cryptographic hash collision; (3) knowledge of the required `context` string, which the prompt notes is discoverable from A's public `shipit.yml` or CI badge. No Shipit session, API token, or GitHub App secret is needed. This is repeatable per commit/context pair and requires only a single crafted, legitimately-signed webhook per attempt.

### Recommendation
In `Shipit::Webhooks::Handlers::StatusHandler#process` (and similarly `CheckRunHandler`/related handlers), scope the `Commit` lookup by the payload's repository, not just SHA — e.g., resolve `stack`/`repository` from `params.repository.full_name` first, then constrain `Commit.where(sha: params.sha, stack: stack)` (or verify `commit.github_repo_name == params.repository.full_name`) before calling `create_status_from_github!`. Reject/ignore the event if the repository does not match the stack that owns the commit row.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create `stack_a` with `repository` `org/repo-a` and configure `required_statuses`/`blocking_statuses` (via stubbed `Stack#required_statuses`) to include `'ci/required'`.
2. Create a `Commit` row belonging to `stack_a` with `sha: 'deadbeef...'` and no existing statuses — assert `commit.blocked?` is `true` (or that `stack_a.deployable?` is `false`) because the required context has no passing status.
3. Build a `status` webhook payload with `repository.full_name = 'org/repo-b'`, `sha: 'deadbeef...'`, `context: 'ci/required'`, `state: 'success'` — i.e., a payload naming a different repository than `stack_a`'s.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)` (or `.process`) directly, bypassing only signature verification (already covered/trusted per rules), to simulate a validly-signed webhook for repo B.
5. Reload `commit`, assert a `Shipit::Status` row now exists with `stack_id == stack_a.id`, `context == 'ci/required'`, `state == 'success'`.
6. Assert `commit.blocked?` is now `false` / `stack_a.deployable?` reflects the forged success — demonstrating that repo B's payload mutated stack A's CI-gating state, with the equality `Status(stack_id: A).context/state` now equal to attacker-supplied values from a payload declaring `repository: org/repo-b`, not `org/repo-a`.
