### Title
Forged `PreStxOp.output` lets an attacker declare an arbitrary victim `sender` for `TransferStxOp`, enabling unauthorized STX transfer - (File: stackslib/src/chainstate/burn/operations/transfer_stx.rs)

### Summary
`TransferStxOp::check` only validates that `transfered_ustx != 0` and `sender != recipient`; it performs no cryptographic check that the `sender` StacksAddress is actually controlled by whoever crafted the burnchain operation. Since `sender` is populated from the previously-recorded `PreStxOp.output` field — itself just an arbitrary Bitcoin output address parsed from a transaction the attacker fully controls — an attacker can declare any victim address as `output`, then legitimately spend the PreStxOp's second output (which the attacker, not the victim, funds and signs) to submit a `TransferStxOp` that moves the victim's STX to themselves.

### Finding Description
The broken equality: **the STX debited from account X == an operation X actually authorized**. Here, `sender = pre_stx.output` is set purely from parsing bytes of a Bitcoin transaction output that the attacker constructs (`TransferStxOp::parse_from_tx`, `stackslib/src/chainstate/burn/operations/transfer_stx.rs:166-194`), with no signature or proof that the address holder authorized anything: [1](#0-0) 

`get_sender_txid` only enforces that the `TransferStxOp`'s first input spends `vout=1` of *some* prior transaction — it never checks that the entity spending `vout=1` is the same entity who wrote the `output` (declared "sender") into `vout=0` of the original `PreStxOp`: [2](#0-1) 

`check()` performs no ownership/authorization validation at all beyond non-zero amount and sender != recipient: [3](#0-2) 

**Root cause**: `vout=0` (the declared "output"/sender) and `vout=1` (the UTXO that must be spent to authorize the follow-up op) are two independent outputs of the same Bitcoin transaction. Proving control of `vout=1`'s spending key proves nothing about who is entitled to declare `vout=0`'s address as `sender`. The attacker fully constructs the `PreStxOp` transaction (funds it, signs its input, chooses both outputs), so they can set `vout=0` to the victim's `StacksAddress` bytes while directing `vout=1` back to an address they control, then trivially spend `vout=1` themselves in the follow-up `TransferStxOp`.

**Attacker's exact call sequence**:
1. Attacker crafts and broadcasts a `PreStxOp` Bitcoin transaction: `vout=0` address = victim's `StacksAddress`, `vout=1` = attacker-controlled address, inputs signed with attacker's own Bitcoin key.
2. Attacker crafts a `TransferStxOp` Bitcoin transaction spending `vout=1` of the above tx, with `recipient` = attacker's `StacksAddress`, `transfered_ustx` = victim's full unlocked balance.
3. `TransferStxOp::parse_from_tx` resolves `sender = pre_stx.output` (victim), `recipient` = attacker.
4. `TransferStxOp::check` passes trivially (amount nonzero, sender != recipient).
5. `Chainstate::process_transfer_ops` invokes `run_stx_transfer`, debiting the victim's account and crediting the attacker.

No existing guard in this file (or in the reachable path from `PreStxOp`/`TransferStxOp` parsing) verifies that the declared `output` in the `PreStxOp` corresponds to the private key that funds/signs either the `PreStxOp` or the subsequent `TransferStxOp`.

### Impact Explanation
This allows any unprivileged attacker who can broadcast two ordinary Bitcoin transactions to steal the full unlocked STX balance of any victim StacksAddress, with no signature or consent from the victim required. This is a **Critical** theft of victim's locked/unlocked STX, is fully repeatable against any address holding a balance, and requires no privileged role — only the ability to submit burnchain operations from the attacker's own Bitcoin UTXOs.

### Likelihood Explanation
Preconditions are minimal: the victim must hold >= `transfered_ustx` unlocked STX at a known `StacksAddress` (trivially discoverable on-chain), and the attacker needs only ordinary Bitcoin transaction-crafting capability (their own UTXOs, own keys, standard OP_RETURN payload construction) — no interaction with pox-5, no signer role, no miner role. This is feasible for any attacker and repeatable against every address with a nonzero balance, making likelihood high assuming the trace above is accurate.

### Recommendation
Bind the `sender` field cryptographically to whoever actually authorizes the operation: e.g., derive `sender` from the address that signs/funds the `PreStxOp`'s own inputs (i.e., the input signer's translated `StacksAddress`), not from an arbitrary declared output (`vout=0`). Alternatively, require that `vout=0`'s address matches the address derived from the `PreStxOp`'s input-signing key, rejecting any `PreStxOp`/`TransferStxOp` pair where they diverge.

### Proof of Concept
Rust integration test plan (in `stackslib`/`stacks-node` burnchain-ops integration tests):
1. Set up two Bitcoin-funded regtest keys: `attacker_btc_key`, and record `victim_stacks_addr` (an address with a known STX balance, e.g., pre-funded via genesis or a prior legitimate transfer, controlled by a *different*, unrelated key that the attacker never touches).
2. Have the attacker submit a `PreStxOp` Bitcoin tx: `vout[0].address` encodes `victim_stacks_addr`, `vout[1].address` = attacker-controlled address, inputs signed only by `attacker_btc_key`.
3. Have the attacker submit a `TransferStxOp` Bitcoin tx spending `vout=1` of the above tx, `recipient` = `attacker_stacks_addr`, `transfered_ustx` = victim's full balance, signed only by `attacker_btc_key`.
4. Mine both into the burnchain, process through `Chainstate::process_transfer_ops`.
5. Assert: `get_stx_balance(victim_stacks_addr)` decreased by `transfered_ustx` and `get_stx_balance(attacker_stacks_addr)` increased by exactly `transfered_ustx`, despite no Stacks transaction signed by `victim_stacks_addr`'s key and no Bitcoin input ever signed by any key belonging to the victim.

*Note: I was unable to directly inspect `pre_stx.rs`'s `output` derivation or `burnchains/burnchain.rs`'s lookup of `sender` from `PreStxOp` (tool budget exhausted before those reads completed); this finding relies on the confirmed contents of `transfer_stx.rs` plus the well-established/public structure of the `PreStxOp`→`TransferStxOp` UTXO-chaining mechanism in stacks-core. Confirming the exact `sender`-resolution code in `burnchain.rs` is recommended before treating this as fully verified.*

impl TransferStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.transfered_ustx == 0 {
            warn!("Invalid TransferStxOp, must have positive ustx");
            return Err(op_error::TransferStxMustBePositive);
        }
        if self.sender == self.recipient {
            warn!("Invalid TransferStxOp, sender is recipient");
            return Err(op_error::TransferStxSelfSend);
        }
        Ok(())
    }
}
