### Title
Webhook signature verifies the org that signed the payload, but handlers trust unrelated repository/commit fields inside the same payload — cross-repository status forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) inside the very payload it is about to verify. Once the HMAC check passes for that organization's secret, the entire raw JSON body is treated as trusted and dispatched to handlers. However, those handlers do not re-derive their target from the same field used for verification: `StatusHandler` looks up commits by a bare `sha` with no repository scoping at all, and `Handler#repository_name` (used by push/pull-request handlers) reads a separate field, `payload.dig('repository', 'full_name')`. Nothing ties `repository.owner.login` (the identity that authenticated the request) to `repository.full_name` / the matched `sha` (the resource that gets acted on).

### Finding Description
The binding that should hold is:
`organization whose secret produced a valid HMAC == organization owning the repository/commit the handler mutates`

But the verification path and the action path use independently attacker-influenced fields within the same JSON body:
- Verification: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [5](#0-4) .
- Action: `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across every stack/repository tracked by this Shipit instance, keyed only by commit SHA [6](#0-5) .

Any GitHub organization/app that is onboarded into this multi-tenant Shipit instance (i.e., has its own `webhook_secret` configured, which it controls since it is the one that sets up the webhook in its own GitHub settings) can send a `status` event whose `repository.owner.login` matches its own org (so the HMAC check passes using its own secret) but whose `sha` matches a real commit belonging to a completely different, unrelated stack tracked by the same Shipit instance (SHAs are public and easy to observe for any repo Shipit deploys). Because `StatusHandler` never checks that the commit's actual repository matches the verified `repository_owner`/`repository.full_name`, the attacker's org can forge a `success` (or any) CI status on that foreign commit.

### Impact Explanation
Forged commit statuses feed directly into deploy gating: `ci.require` in `shipit.yml` blocks deploys/continuous delivery unless required contexts report success on the commit. By injecting a fabricated "success" status for an arbitrary context on someone else's commit, an attacker who only controls a different, unrelated GitHub organization onboarded to the same Shipit instance can satisfy another team's CI gate and trigger an unauthorized deploy of a real commit that never actually passed CI — matching the in-scope Critical impact of "an unauthorized deploy" via a broken authentication-to-resource binding.

### Likelihood Explanation
Exploitability requires only that the attacker control (own) some GitHub organization already configured as a Shipit tenant — not the target organization, not a Shipit account, not the target's webhook secret, and no `ApiClient` token. Multi-tenant Shipit deployments onboarding many orgs (e.g., an internal platform serving many teams) make this a realistic and low-effort vector: craft one JSON body, sign it with your own org's known secret, send it to the shared webhooks endpoint.

### Recommendation
Scope every mutating handler to the repository that produced a valid signature rather than trusting payload-embedded identifiers independently. Concretely: pass the verified `repository_owner` (or the whole verified repository identity) from the controller into `Shipit::Webhooks.for_event(event)` handlers, and have `StatusHandler`/`Handler#stacks`/`Handler#repository_name` restrict lookups to stacks/commits belonging to that verified owner, rejecting the event if `repository.full_name`'s owner segment does not match `repository_owner`.

### Proof of Concept
1. Attacker owns/administers GitHub organization `attacker-org`, which is a legitimate tenant of the shared Shipit instance with its own `webhook_secret` (`S_attacker`), configured per `lib/shipit/github_app.rb`.
2. Attacker observes that `victim-org/victim-repo` is deployed via the same Shipit instance and knows a pending commit SHA `abc123` for it (SHAs are visible on GitHub).
3. Attacker POSTs to `/webhooks` with:
   ```json
   {
     "sha": "abc123",
     "state": "success",
     "context": "ci/required-check",
     "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"}
   }
   ```
   and header `X-Hub-Signature: sha1=<HMAC(S_attacker, body)>`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC matches `S_attacker` — verification succeeds [7](#0-6) .
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, finds the victim's commit (unscoped to any repository), and records a forged `success` status on it [6](#0-5) .
6. If `victim-org/victim-repo`'s `shipit.yml` requires `ci/required-check`, continuous delivery (or a human clicking deploy relying on the green check) can now ship `abc123` despite it never actually passing CI in `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
