## Title
Missing validation that `amount_at_least ≤ amount_at_most` (and `at_least ≤ at_most`) in address/asset spending-condition filters permanently freezes funds - (File: `definition.js`)

## Summary
`definition.js`'s `getFilterError()` and the `sum` operator validator check `amount_at_least`, `amount_at_most`, `at_least` and `at_most` individually for being positive integers, but never verify that the "at least" bound is not greater than the "at most" bound. An address (or asset issue/transfer condition) definer can therefore commit a definition containing an internally-contradictory numeric range, which the evaluator will always resolve to `false`, permanently disabling that spending/authentication branch — exactly the same missing floor/ceiling ordering check described in the source report for the leverage-ratio parameters.

## Finding Description
`getFilterError()` in `definition.js` validates the `amount_at_least`/`amount_at_most` fields of a filter used by `has`, `has one`, `seen`, and `has equal` conditions: [1](#0-0) 

It checks each bound individually for being a positive integer but performs no check that `amount_at_least <= amount_at_most`. The same pattern exists for the `sum` operator's `at_least`/`at_most` fields: [2](#0-1) 

Only the mutual exclusivity with `equals` is checked; ordering between `at_least` and `at_most` is never validated. This omission propagates directly into `validateDefinition()` (definition creation/validation path, reachable by any address/asset definer posting a `definition`, `address_definition_change`, or asset `issue_condition`/`transfer_condition` message) and into evaluation at authentication time:

For inputs/outputs filters (`has`/`has one`/`seen`), the runtime evaluator applies both bounds independently: [3](#0-2) [4](#0-3) 

For the `sum` operator: [5](#0-4) 

If `amount_at_least > amount_at_most` (or `at_least > at_most` for `sum`), no possible amount/sum can simultaneously satisfy `amount >= amount_at_least` and `amount <= amount_at_most`, so the branch is unconditionally `false` for every unit ever posted, forever — since a definition's validity is bound to its content-hash address and cannot be altered afterward. This is the exact analog of the Carapace `ProtectionPool` bug: no check that "floor" (`at_least`) is not greater than "ceiling" (`at_most`), which can permanently disable a required operation.

## Impact Explanation
If the contradictory filter guards a required branch of an address's spending definition (e.g., an `and` clause, or the only viable branch of an `or` in a multi-signature/shared address, or a `sum` condition gating an `issue_condition`/`transfer_condition` of an asset), that branch becomes permanently unsatisfiable. Because Obyte address definitions are immutable once their chash is committed on-chain (an address's validity is tied to `chash160(definition)`), this can permanently freeze funds sent to that address for every co-signer/beneficiary who is not the sole author of the mistake, or permanently block the ability to issue/transfer a shared asset if such a filter guards `issue_condition`/`transfer_condition`. This matches the "AA fund loss or freezing" / permanent inability to move funds impact category.

## Likelihood Explanation
Likelihood is limited to definer error (nobody profits from deliberately bricking their own or a shared address), but no protocol-level guard exists to catch it — same characterization as the original report ("owner can set invalid floor/ceiling by mistake"). Any unprivileged unit poster defining an address, or an asset issuer defining `issue_condition`/`transfer_condition`, can trigger this by mis-ordering `amount_at_least`/`amount_at_most` or `at_least`/`at_most`, and the validation layer will accept it silently.

## Recommendation
In `getFilterError()`, add a check that when both `amount_at_least` and `amount_at_most` are present, `amount_at_least <= amount_at_most`. Similarly, in the `sum` operator validation, add a check that when both `at_least` and `at_most` are present, `at_least <= at_most`. Reject such definitions during `validateDefinition()`/`validateAssetDefinition()` so they can never be committed on-chain.

## Proof of Concept
1. Author constructs an address definition such as:
```
["sum", { "filter": { "what": "output", "asset": "base" }, "at_least": 1000, "at_most": 500 }]
```
2. `validateDefinition()` (`definition.js:565-592`) accepts this because it only checks each bound's type individually — no ordering check exists.
3. The address is created (its chash is derived from this definition) and funds are sent to it, e.g. in a multi-authored/shared-address scenario.
4. Any attempt to satisfy this branch at spend time evaluates via `definition.js:1155-1177`: for any real `sum`, either `sum < 1000` (fails the `at_least` check) or `sum >= 1000 > 500` (fails the `at_most` check) — the condition can never return `true`.
5. If this branch is required (sole branch, or an `and` term) for spending, the funds controlled by that address definition are permanently unspendable.
