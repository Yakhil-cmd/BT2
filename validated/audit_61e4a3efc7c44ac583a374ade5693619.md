### Title
Cross-tenant `membership` webhook forgery escalates into `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary

### Finding Description
In a multi-organization Shipit deployment (the documented "Using Multiple Github Applications" setup, `docs/setup.md`), each configured GitHub organization gets its own independent GitHub App and `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which secret to use for HMAC verification based entirely on attacker-supplied payload fields (`repository.owner.login` or `organization.login`), not on any independently-verified source of the request: [2](#0-1) [3](#0-2) 

So a party who legitimately administers Org B's own GitHub App (and thus knows Org B's real `webhook_secret`) can compute a genuinely valid `X-Hub-Signature` for a POST to `/webhooks`, while filling every other field of the JSON body — including the `team` and `organization` referenced by the `membership` handler — with values belonging to an unrelated, higher-trust Org A tracked by the same Shipit instance.

`MembershipHandler#process` then trusts those payload fields to locate and mutate team membership: [4](#0-3) 

`find_or_create_team!` looks the team up **only by `github_id`** (`Team.find_or_create_by!(github_id: params.team.id)`); the `organization.login` from the payload is only used inside the create block, so if a team with that `github_id` already exists (e.g. Org A's real, previously-synced authorization team), it is simply returned — the mismatched `organization.login` supplied by the forging party is silently ignored. `team.add_member(member)` then unconditionally appends the attacker-controlled `member.login` (resolved to a real `User` via `User.find_or_create_by_login!`) to that team: [5](#0-4) 

If that team is one of `Shipit.github_teams` (the configured OAuth-team access restriction), the newly-added membership directly satisfies `User#authorized?`: [6](#0-5) [7](#0-6) 

The broken binding is exactly: **the organization whose webhook secret authenticated the request ≠ the organization/team the handler is permitted to write to.** Signature verification only proves "this came from someone who knows Org B's secret"; it proves nothing about the `team`/`organization`/`member` fields the handler subsequently trusts and mutates.

### Impact Explanation
An operator of any one of the (potentially many, lower-trust) organizations configured on a shared multi-tenant Shipit instance can escalate into `Shipit.github_teams` authorization for an arbitrary GitHub login, without ever being a real member of the target team on GitHub. This directly matches the in-scope High-severity impact "escalation into `Shipit.github_teams` authorization," and from there can be leveraged to unlock stack access, deploy/rollback controls, and other UI/actions gated by team membership.

### Likelihood Explanation
This requires only that the Shipit instance runs the documented multi-organization configuration (an explicitly supported, non-exotic setup) and that the attacker administers the GitHub App for one of the configured (lower-trust) organizations, giving them their own genuine `webhook_secret` — no access to any other organization's secrets, no `ApiClient` token, and no privileged Shipit account is needed. The `team.github_id` of the target authorization team is not a secret (discoverable via the public/organization GitHub API), making the forged payload straightforward to construct.

### Recommendation
In `MembershipHandler`, verify that `params.organization.login` matches the organization actually used to authenticate the webhook (the `repository_owner`/organization resolved and used by `WebhooksController#verify_signature`), and reject/ignore membership events whose `organization.login` doesn't match the `Team#organization` already on record before calling `team.add_member`/`team.members.delete`. More generally, `WebhooksController` should pass the organization it used for signature verification down to handlers (instead of letting handlers re-derive trust from the same untrusted payload), so no handler can act on data belonging to an organization other than the one whose secret actually signed the request.

### Proof of Concept
1. Shipit is configured for multi-org mode with Org A (`secrets.github.OrgA`, has an authorization team `Shipit.github_teams` synced with `github_id: 123`) and Org B (`secrets.github.OrgB`, attacker administers this App and knows `webhook_secret_B`).
2. Attacker computes `sig = HMAC-SHA1(webhook_secret_B, body)` for:
```json
{
  "action": "added",
  "team": { "id": 123, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-login" },
  "repository": { "owner": { "login": "OrgB" } }
}
```
3. POST to `/webhooks` with `X-Github-Event: membership` and `X-Hub-Signature: sha1=<sig>`.
4. `verify_signature` resolves `repository_owner = "OrgB"`, fetches Org B's real secret, and the signature validates.
5. `MembershipHandler#process` finds Org A's real team by `github_id: 123` and calls `team.add_member(User.find_or_create_by_login!("attacker-login"))`, adding the attacker to Org A's authorization team in Shipit's database.
6. Attacker signs in via OAuth as `attacker-login`; `User#authorized?` now returns `true` because their team membership intersects `Shipit.github_teams`.
