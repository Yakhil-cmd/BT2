### Title
Unbounded in-memory scan of `assocUnstableMessages` during AA data-feed formula evaluation causes a network-wide DoS - (File: data_feeds.js)

### Summary
`dataFeedExists()` and `readDataFeedValue()` in `data_feeds.js` iterate synchronously over the entire global `storage.assocUnstableMessages` map whenever an AA formula uses `data_feed` / `in data feed` with unstable/AA data. This map grows with every unstable unit carrying a `data_feed`, `definition`, `system_vote`, or `system_vote_count` message network-wide, and is walked in full, in-process, for every AA trigger evaluation that reads unstable data feeds — mirroring the reported `ClearingHouse#updatePositions` pattern of iterating an unbounded, attacker-growable array on every user-triggered call.

### Finding Description
`dataFeedExists(arrAddresses, feed_name, ..., bAA, handleResult)` and `readDataFeedValue(arrAddresses, feed_name, ..., unstable_opts, ...)` contain a `for (var unit in storage.assocUnstableMessages) { ... storage.assocUnstableMessages[unit].forEach(...) }` loop that runs whenever `bAA`/`bIncludeUnstableAAs` is set: [1](#0-0) [2](#0-1) 

`storage.assocUnstableMessages` is a process-global object populated in `writer.js` every time *any* unit (posted by *any* unprivileged unit poster) contains a `data_feed`, `definition`, `system_vote`, or `system_vote_count` message, and it is only cleaned up once that unit's MCI stabilizes: [3](#0-2) [4](#0-3) 

This map is also scanned in full by `storage.getUnconfirmedAADefinition` and `storage.getUnconfirmedAADefinitionsPostedByAAs`, which are invoked from `insertAADefinitions` (executed on every AA-defined-AA definition and on secondary AA triggers): [5](#0-4) 

The formula evaluator (`formula/evaluation.js`) calls `dataFeedExists`/`readDataFeedValue` for the `in data feed` and `data_feed` oscript operators, which are ordinary, unprivileged constructs usable in any AA definition and reachable by any AA trigger sender simply by sending a payment to that AA: [6](#0-5) 

Because Obyte/ocore uses a single write-mutex/single-process model where unit validation, writing, and AA-trigger execution are serialized (`mutex.lock(['write'|'aa_triggers'], ...)`), a long synchronous JS loop inside this critical section blocks all subsequent unit validation and stabilization for the duration of the scan: [7](#0-6) 

An attacker who is only an ordinary unit poster / AA trigger sender can inflate `assocUnstableMessages` cheaply and unboundedly by:
1. Posting many low-value units, each carrying a `data_feed` message (a normal, permissionless message type), and delaying/preventing their stabilization (e.g., by keeping the DAG wide/shallow, or simply flooding faster than MC advances), keeping thousands of entries "unstable" and resident in the map.
2. Then triggering any AA (their own or a third-party AA) that uses `in data feed`/`data_feed` against unstable data, forcing the node to walk the entire inflated map synchronously on every single such trigger.

This is directly analogous to the reported bug class: an attacker-controllable, unbounded collection is iterated in full on every normal user action, with no cap on the collection's size or on the number of entries scanned per call.

### Impact Explanation
Every subsequent AA trigger that queries unstable/AA data feeds — and every `insertAADefinitions` call for AA-defined AAs / secondary triggers — must scan the entire `assocUnstableMessages` map. As this map is inflated by spam units, the per-call cost grows linearly with the number of outstanding unstable messages network-wide, not with anything under the caller's control. Because this scan runs inside the mutex-protected write/AA-trigger path, a sufficiently large map can cause processing of a single trigger (and therefore MC stabilization and subsequent unit acceptance) to take excessively long, degrading throughput for the whole node and, since all full nodes must perform the identical work to stay in consensus, for the network as a whole — i.e., a node becomes unable to confirm new units in a timely manner. This matches the "network unable to confirm new units" acceptance criterion for a Medium/High severity DoS.

### Likelihood Explanation
- `data_feed` messages and AA triggers referencing `in data feed`/`data_feed` are ordinary, permissionless features usable by any address; no special privilege is required.
- Keeping many units "unstable" for an extended period is achievable by any well-resourced spammer by continuously posting units (Obyte units require proof-of-work-free but fee-bearing payloads, so the cost is bounded by transaction fees, not a hard technical barrier).
- The vulnerable code paths (`dataFeedExists`, `readDataFeedValue`, `getUnconfirmedAADefinition(s)`) are exercised on the hot path of ordinary AA usage, so the DoS is triggered by normal usage patterns once the map is inflated, without needing further attacker interaction.
- Likelihood is Medium: it requires sustained spending to keep the unstable set large, and the network already has some economic disincentives (fees) for spam, but no explicit cap exists on `assocUnstableMessages` size or on the amount of unstable data scanned per formula evaluation.

### Recommendation
- Cap the number of unstable messages considered per `data_feed`/`in data feed` evaluation (e.g., limit by max_mci/min_mci range check before iterating, or index `assocUnstableMessages` by feed-relevant keys instead of scanning the whole map).
- Maintain a secondary index (e.g., `address -> feed_name -> [unstable message refs]`) so lookups are O(matches) instead of O(all unstable messages network-wide).
- Consider bounding the total size of `assocUnstableMessages`/the set of outstanding unstable data-feed-bearing units that can be produced within a given time window, or charge additional formula-evaluation "op count"/complexity cost proportional to the number of unstable messages scanned so that this cost is reflected in the AA's complexity/op budget (`MAX_COMPLEXITY`/`MAX_OPS`) rather than being unbounded.

### Proof of Concept
1. An attacker repeatedly posts units, each containing one `data_feed` message from an address they control, without waiting for stabilization, so `storage.assocUnstableMessages` accumulates a large number of entries (bounded only by network fee costs, not by any protocol-level cap).
2. The attacker (or anyone) then sends a trigger to any AA whose oscript uses `in data feed [oracle] "feed_name" ...` referencing unstable data (or any AA-defined-AA scenario triggering `insertAADefinitions`/`getUnconfirmedAADefinitionsPostedByAAs`).
3. `dataFeedExists`/`readDataFeedValue` (or `getUnconfirmedAADefinition[sPostedByAAs]`) executes `for (var unit in storage.assocUnstableMessages)` over the full, attacker-inflated map inside the AA-trigger/write mutex, as shown at [1](#0-0)  and [5](#0-4) , delaying the processing of that trigger and, transitively, subsequent unit validation/stabilization handled under the same lock.

function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (objUnit.sequence !== 'good')
			continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition')
				continue;
			var payload = message.payload;
			if (payload.address === address)
				return payload.definition;
		}
	}
	return null;
}

// arrAddresses is an array of AA addresses whose definitions are posted by other AAs
function getUnconfirmedAADefinitionsPostedByAAs(arrAddresses) {
	var payloads = [];
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit]; // just stabilized
		if (!objUnit)
			throw Error("unstable unit " + unit + " not in assoc");
		if (!objUnit.bAA)
			continue;
		assocUnstableMessages[unit].forEach(function (message) {
			if (message.app !== 'definition')
				return;
			var payload = message.payload;
			if (arrAddresses.indexOf(payload.address) >= 0)
			payloads.push(payload);
		});
	}
	return payloads;
}
