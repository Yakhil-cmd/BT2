### Title
Webhook signature is verified against a secret selected from unverified payload fields, decoupling the authenticated organization from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization whose `webhook_secret` will be used to validate the `X-Hub-Signature` HMAC by reading `repository.owner.login` (or `organization.login`) straight out of the **same untrusted JSON body** that is later processed by the event handlers. Nothing ties the organization used to select the verification secret to the repository object that the handlers subsequently act on, breaking the equality that should hold: `organization authenticated == organization owning the repository written`.

### Finding Description
`verify_signature` resolves the signing key like this: [1](#0-0) 

and the organization used to look up the app config comes from the payload itself: [2](#0-1) 

`Shipit.github(organization: ...)` maps that attacker-controlled string to one of the configured `github` app entries (each with its own `webhook_secret`) via `github_app_config`: [3](#0-2) 

This is the exact analog of the `isProposalOpen()` misuse pattern: a helper (`verify_signature`/`isProposalOpen`) that is correct for its stated purpose (validate *a* signature for *the organization named in the request*) is being relied upon by the caller as if it verified something stronger (that the request's actual repository/org identity is trustworthy). Once the request passes `verify_signature`, `create` blindly re-parses the body and dispatches it to handlers keyed only on `event`, with no additional cross-check that `repository.owner.login` used for the HMAC lookup matches the `repository.full_name`/`repository.owner` the handler will act on: [4](#0-3) 

In a multi-organization Shipit deployment (the documented multi-tenant config schema), each organization has its own `webhook_secret`: [5](#0-4) 

An attacker who legitimately controls (or has compromised) one onboarded GitHub organization/app knows that organization's `webhook_secret` (it is configured by that organization's own GitHub App settings and is not a Shipit-wide secret). They can therefore forge a signature that is valid for `repository.owner.login = "attacker-org"` while putting a completely different `repository.full_name`/commit/status/PR payload for a **victim repository tracked by a different stack** in the same body. `verify_signature` selects and validates against the attacker's own known secret, passes, and the handler (e.g. `push`, `status`, `merge_status`, `commit_status`) then acts on whatever repository/commit identifiers are embedded in the body, not on the organization that was actually authenticated.

### Impact Explanation
This breaks a deployment-trust binding equivalent to "an organization that authenticated versus the repository that is written." Depending on which webhook handler is targeted, this can be used to inject forged CI/commit statuses, forged `merge_status`/`pull_request` events, or forged `push` events for stacks belonging to a different, victim organization than the one whose secret was actually used to authenticate the request — i.e., cross-repository/cross-organization writes into Shipit's data model and potentially into deploy/merge decision-making (unauthorized ship/merge), which maps to the Critical impact category ("cross-repository writes" / "unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability requires the attacker to control (or have compromised) at least one legitimate GitHub App/organization already configured in Shipit's multi-org `secrets.yml` — a scenario the multi-tenant config schema explicitly supports and documents. No Shipit session, `ApiClient` token, or private key is needed; only knowledge of one org's own `webhook_secret`, which that org's own admins possess by design. This is a plausible, unprivileged-relative-to-other-tenants attack path in any multi-organization Shipit deployment.

### Recommendation
After signature verification succeeds, explicitly re-validate that the organization/owner used to select the verifying secret matches the `repository.owner.login`/`organization.login` actually referenced by the event body being processed (and that the resolved `Stack`/`Repository` record's owner matches). Do not trust `repository_owner` derived from the payload as sufficient identity proof merely because *some* configured secret validated the HMAC over that payload — bind the verified organization identity to the specific repository the handler will mutate, analogous to introducing an explicit `isProposalEnded()`-style check instead of reusing `isProposalOpen()` for a different guarantee.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` and `OrgB`, each with distinct `github.webhook_secret` values (per `docs/setup.md` multi-org schema).
2. As an operator/compromised credential holder of `OrgA`, craft a webhook body with `X-Github-Event: push` (or `status`) where `repository.owner.login = "OrgA"` (so `repository_owner` resolves to `OrgA`'s app/secret) but `repository.full_name` / `sha` / branch fields identify a stack that is actually tracked under `OrgB`'s repository.
3. Sign the raw body with `OrgA`'s known `webhook_secret` and send it to `POST /github_webhooks` (or the engine's webhook route) with header `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")`, validates successfully against `OrgA`'s secret, and `create` dispatches the handler which acts on the `OrgB` repository data embedded in the body (e.g., triggers `GithubSyncJob`, updates a commit's `Status`, etc.) — mutating state for a stack the attacker does not control.

Note: I was not able to fully inspect `app/models/shipit/webhooks/handlers/push_handler.rb` (and sibling handlers) within the remaining tool budget to confirm the exact lookup key used to resolve the target `Stack`/`Repository` record (e.g., whether it's purely `full_name`-based with no additional owner cross-check). The root-cause binding break in `WebhooksController#verify_signature`/`#repository_owner` is confirmed directly from the code, but full confirmation of downstream handler behavior would benefit from a deeper read of `app/models/shipit/webhooks/handlers/*.rb` in a follow-up session.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
