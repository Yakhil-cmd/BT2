## Title
`StatusHandler#process` matches status webhooks by SHA alone, with zero repository binding to `payload['repository']` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits via `Commit.where(sha: params.sha)` and writes a GitHub status to every matching commit across the entire installation, regardless of which repository the webhook's `X-Hub-Signature` was verified for. The inherited `stacks`/`repository_name` helpers that would scope the lookup to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` are defined on the base `Handler` class but are never called anywhere in `StatusHandler#process`'s execution path.

### Finding Description
The claimed binding is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` — i.e., a status update should only ever be applied to commits belonging to the repository that the webhook was actually signed for.

Tracing the code:
- `app/models/shipit/webhooks/handlers/handler.rb` defines `stacks` (line 32-34) and `repository_name` (line 36-38), which use `Repository.from_github_repo_name(repository_name)` to scope to the signed repository — but these are `private` and only invoked by handlers that explicitly call `stacks` (e.g. the `pull_request/*` handlers).
- `app/models/shipit/webhooks/handlers/status_handler.rb` line 20-24: `process` calls only `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. Neither `stacks`, `repository_name`, nor `payload.dig('repository', 'full_name')` is referenced.
- `params.sha` is fully attacker-controlled input from the webhook JSON body (`ExplicitParameters` schema only requires `sha`/`state` be strings; no repository-consistency check, see `app/models/shipit/webhooks/handlers/status_handler.rb` lines 7-18).
- `Commit#sha` is not globally unique per repository — `Commit.by_sha`/`where(sha:...)` operate over the whole `commits` table across all stacks/repositories (`app/models/shipit/commit.rb` line 92-99, no scoping by stack in `process`'s query).

So if two different repositories mounted on the same Shipit instance happen to share a commit SHA (e.g., a fork of a repo, a cherry-picked/rebased commit, or a repo created by copying history), an attacker who controls a webhook-emitting repository (attacker's own fork/repo, signed with attacker's own legitimate secret for *their* repository) can send a `status` event with `sha` equal to a commit that also exists in a *victim* stack. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb` line 24-30) only checks that the payload was signed by the GitHub App/secret configured for `repository_owner` (from the payload's own `repository.owner.login`) — it authenticates *that the sender owns some registered repo*, not that the `sha`/status content is scoped to that repo. Once signature verification passes for the attacker's own repo, `StatusHandler.call` runs uncontrolled and writes/overwrites a `Status` on any commit row matching that SHA, in any stack, including one belonging to a different tenant repository.

This confirms via code inspection (matching the requested unit-test proof) that `Repository.from_github_repo_name` and `payload.dig('repository', 'full_name')` are never invoked in `StatusHandler#process`'s call graph — `stacks`/`repository_name` are dead for this handler. A Mocha `Shipit::Repository.expects(:from_github_repo_name).never` around `StatusHandler.call(payload)` would pass, proving zero repository-scope enforcement, not merely thin test coverage.

### Impact Explanation
An attacker who legitimately owns/administers *one* Shipit-registered repository can push a `status` webhook (signed with their own valid webhook secret for their own repo) carrying an arbitrary `sha`. If that SHA collides with a commit belonging to a different repository's stack (which is plausible for forks/duplicated histories, and guaranteed to be forgeable once any such collision exists), the handler mutates `Status`/`Commit` state for that unrelated victim stack via `create_status_from_github!` → `add_status`, which can flip `deployable?`/`blocked?` and trigger `stack.schedule_merges` or `ContinuousDeliveryJob` (`app/models/shipit/commit.rb` lines 281-287, 379-384). This is a cross-tenant write: a payload authenticated for repository A mutates repository B's commit/stack state, potentially unblocking or triggering an unauthorized deploy path. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: attacker must control at least one repository already registered with Shipit (so a valid webhook secret/App installation exists for *some* org/repo), and a SHA collision must exist between that repo's commit and a victim stack's commit. SHA collisions are not guaranteed by default (git SHAs are content-addressed), so this is not trivially exploitable against arbitrary unrelated repositories out-of-the-box; it primarily manifests when repositories share history (e.g., forks, mirrors, monorepo splits) or, more strongly, wherever `commits` from multiple repos overlap in a Shipit instance. Given the strict "attacker is unprivileged, no secrets" framing, actually forging an unrelated repository's SHA to collide requires either shared git history or engineering a collision — a real but non-trivial precondition, reducing (but not eliminating) practical likelihood.

### Recommendation
Scope `StatusHandler#process` to the repository the webhook was verified for, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the already-defined `stacks`/`repository_name` helpers from `Handler`, so status updates can never cross repository boundaries.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (illustrative)
test "#process never enforces repository scope via Repository.from_github_repo_name" do
  payload = {
    'sha' => 'a' * 40,
    'state' => 'success',
    'repository' => { 'full_name' => 'shipit-engine/shipit-engine' },
  }
  Shipit::Repository.expects(:from_github_repo_name).never
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end
```
This proves `Repository.from_github_repo_name` (and thus `payload.dig('repository', 'full_name')`) is never consulted by `StatusHandler.call`, confirming the repository-scope binding is absent in code, matching the equality-violation claim: `commit.stack.repository.full_name == payload.dig('repository','full_name')` is never checked.
