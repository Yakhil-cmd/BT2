### Title
`ReviewStackProvisioningQueue.add` enqueues and later provisions a `ReviewStack` created via the `OpenedHandler#provision?` operator-precedence bug, bypassing `repository.review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/review_stack_provisioning_queue.rb])

### Summary
`OpenedHandler#provision?` uses `A && B || C || D`, so `repository.review_stacks_enabled` only gates the `allow_all` branch and does not gate `allow_with_label`/`prevent_with_label`, letting a PR author create+enqueue a `ReviewStack` for a repository with review stacks disabled. `Shipit::ReviewStackProvisioningQueue#work`/`#provision` then processes any queued stack matching `awaiting_provision: true` and calls `stack.provisioner.provision?`/`stack.provision` with no re-check of `repository.review_stacks_enabled` at all, so the disabled flag is never enforced anywhere in the provisioning pipeline.

### Finding Description
Binding claimed: `repository.review_stacks_enabled` at provisioning-queue processing time == the enabled state an authorized user approved when the stack was queued (i.e., queue processing should only ever provision stacks for repos where this was, and still is, `true`).

Root cause 1 - creation-time bypass: in `respond_to_pull_request_opened?`/`provision?` [1](#0-0) 
`repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (...)` — Ruby's `&&` binds tighter than `||`, so this evaluates as `(enabled && allow_all) || (allow_with_label && has_label) || (prevent_with_label && !has_label)`. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, `review_stacks_enabled` is never consulted. A PR opened against a repo with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, carrying the configured provisioning label, makes `provision?` return `true`.

This leads into `ReviewStackAdapter#create!`, which creates the `ReviewStack` and immediately calls `Shipit::ReviewStackProvisioningQueue.add(stack)`: [2](#0-1) 

Root cause 2 - processing-time bypass: `ReviewStackProvisioningQueue` [3](#0-2) 
`self.add` just calls `stack.enqueue_for_provisioning`; `queued_stacks` selects any `ReviewStack` with `provision_status: deprovisioned` and `awaiting_provision: true`, independent of the owning repository's flags; `work`/`provision` checks only `stack.provisioner.provision?` (a per-stack resource guard, unrelated to `review_stacks_enabled`) before calling `stack.provision`. No code path in this file, or in `Stack#provisioner`/`Stack#provision`, re-reads `repository.review_stacks_enabled` before executing the actual provisioning/deploy commands. This is invoked periodically via `lib/tasks/cron.rake` calling `ReviewStackProvisioningQueue.work` (out of scope path but shows the trigger exists).

Existing guards that were checked and do not help: `LabeledHandler`/`UnlabeledHandler` correctly gate on `repository.review_stacks_enabled` as a top-level `&&` term in `respond_to_label_change?`, so they are not vulnerable to this specific precedence issue — only `OpenedHandler#provision?` has the flattened `||` chain. `ProvisioningHandler::Base#provision?` is unrelated (a stack-level resource guard), and no controller-level authorization or `ExplicitParameters` validation constrains `provisioning_behavior`/labels.

### Impact Explanation
An attacker who can get a label matching `repository.provisioning_label_name` applied to a pull request opened against a target repository whose maintainer explicitly disabled review stacks (`review_stacks_enabled: false`, `provisioning_behavior: allow_with_label` or `prevent_with_label`) causes Shipit to create and enqueue a `ReviewStack`, which the cron-driven `ReviewStackProvisioningQueue.work` will later provision — running the repository's real provisioning/deploy pipeline (`stack.provision`) against attacker-influenced branch/PR content. This is an unauthorized deploy/provisioning execution for a repository that opted out of review stacks, matching the Critical "unauthorized deploy" category. It is repeatable for any repository configured this way and does not require any Shipit credential.

### Likelihood Explanation
Requires a target repository configured with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible/documented configuration, not `allow_all`). It also requires the attacker's PR to carry (or lack, for `prevent_with_label`) the configured provisioning label — labeling capability on someone else's PR is normally restricted by GitHub permissions, which somewhat limits real-world reach, but is granted to the attacker model in this exercise. Given that configuration, the Shipit-side bug fires deterministically on every matching `opened` webhook with no additional obstacles (no signature/auth issue on the Shipit side; the flaw is purely the boolean-precedence logic).

### Recommendation
Fix `OpenedHandler#provision?` to properly parenthesize so `repository.review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Additionally, as defense in depth, have `ReviewStackProvisioningQueue#provision` (or `queued_stacks`) re-check `stack.repository.review_stacks_enabled` before calling `stack.provision`, so a stack enqueued while enabled but later disabled cannot be provisioned, and vice versa.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb (conceptual, place under test/)
test "provision? bypasses review_stacks_enabled=false when provisioning_behavior is allow_with_label" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: "allow_with_label", provisioning_label_name: "deploy-preview")
  params = build_opened_params(repository: repository, labels: [{ name: "deploy-preview" }])

  assert_difference -> { Shipit::ReviewStack.count }, 1 do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process
  end

  stack = Shipit::ReviewStack.last
  assert stack.awaiting_provision?
  assert_equal false, stack.repository.review_stacks_enabled

  # Binding check: queue includes a stack whose repository has review_stacks_enabled == false
  assert_includes Shipit::ReviewStackProvisioningQueue.queued_stacks, stack

  # #work calls stack.provision without checking review_stacks_enabled
  stub_any_instance(Shipit::ProvisioningHandler::Base, :provision?, true) do
    assert_called stack, :provision do
      Shipit::ReviewStackProvisioningQueue.new.work
    end
  end
end
```

# frozen_string_literal: true

module Shipit
  class ReviewStackProvisioningQueue
    def self.work
      new.work
    end

    def self.add(stack)
      stack.enqueue_for_provisioning
    end

    def self.queued_stacks
      new.queued_stacks
    end

    def work
      queued_stacks.find_each(&method(:provision))
    end

    def queued_stacks
      @queued_stacks ||= Shipit::ReviewStack
                         .with_provision_status(:deprovisioned)
                         .where(awaiting_provision: true)
    end

    private

    def provision(stack)
      if stack.provisioner.provision?
        stack.provision
      else
        Rails.logger.info(
          "Putting review ReviewStack<#{stack.id}> back into the provisioning queue - #provision? was falsey."
        )
      end
    end
  end
