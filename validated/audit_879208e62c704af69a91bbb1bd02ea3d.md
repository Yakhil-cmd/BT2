The CVE describes an XZ/LZMA decompression bomb causing unbounded output during decompression. This codebase does not use the `xz`/`lzma` crate for any production decompression path — the relevant compressed-blob handling (`sp-maybe-compressed-blob`) uses `zstd` exclusively, and critically, unlike the reported XZ issue, decompression here is already bounded by an explicit bomb-limit check: `read_from_decoder` truncates the reader to `bomb_limit + 1` bytes and returns `Error::PossibleBomb` if the output exceeds the limit [1](#0-0) , with limits enforced at both the code-blob call site (`CODE_BLOB_BOMB_LIMIT = 50MB`) [2](#0-1)  and the PoV decompression call site in the PVF execute worker (`POV_BOMB_LIMIT`) [3](#0-2) , and again when constructing the runtime blob [4](#0-3) .

There is no reachable attacker-controlled entry point (extrinsic, XCM, contract call) that feeds untrusted input into an unbounded decompression routine analogous to the XZ bomb scenario; the two decompression consumers found (runtime code blobs and PoV block data) are already guarded by explicit output-size caps that reject the exact "endless output" pattern the CVE describes. This also falls under the excluded category of oversized-input/resource-exhaustion claims per the reporting rules, and no xz/lzma dependency-only usage exists to even form a dependency-based analog.

```rust
fn read_from_decoder(
	decoder: impl Read,
	blob_len: usize,
	bomb_limit: usize,
) -> Result<Vec<u8>, Error> {
	let mut decoder = decoder.take((bomb_limit + 1) as u64);

	let mut buf = Vec::with_capacity(blob_len);
	decoder.read_to_end(&mut buf).map_err(|_| Error::Invalid)?;

	if buf.len() <= bomb_limit {
		Ok(buf)
	} else {
		Err(Error::PossibleBomb)
	}
```
