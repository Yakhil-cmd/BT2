The Sherlock report describes a `mulDiv`/`convertToAssets` rounding‑down issue where per‑user share calculations lose precision individually. The closest reachable analog in `ocore` is not a Solidity vault, but the on‑chain commission distribution logic that splits payload/headers commissions among multiple recipients using independent `Math.round()` calls — a pattern where per‑recipient rounding can make the sum of distributed amounts diverge from the exact total that was actually collected as a fee, i.e., real byte-supply inflation/deflation baked into consensus-critical tables.

### Title
Independent per-recipient rounding in witnessing/headers commission distribution can inflate total paid amount beyond collected fee - (File: paid_witnessing.js, headers_commission.js)

### Summary
`paid_witnessing.js` and `headers_commission.js` split a single fixed fee amount (`payload_commission` / `headers_commission`) among several recipient addresses by rounding each recipient's share **independently**, instead of first computing exact shares and then correcting the rounding remainder so the sum stays fixed. Because each share is rounded separately, the sum of the rounded shares does not necessarily equal the original fee amount.

### Finding Description
In `paid_witnessing.js`, `buildPaidWitnessesForMainChainIndex` computes each witness's share of a unit's `payload_commission` as: [1](#0-0) 
and the equivalent SQL path does the same with `ROUND(1.0*payload_commission/count_paid_witnesses)`: [2](#0-1) 

Because `Math.round()`/`ROUND()` is applied to the *same* quotient independently for each of the `count_paid_witnesses` recipients, the total credited to `witnessing_outputs` is `count_paid_witnesses * round(payload_commission / count_paid_witnesses)`, which is not guaranteed to equal `payload_commission`. For example, `payload_commission = 11`, `count_paid_witnesses = 3` → `11/3 = 3.667` → `round = 4` → total distributed `= 12`, one byte more than was actually collected as commission.

The same pattern exists in `headers_commission.js`, where each recipient's share of `full_amount` is computed independently via `Math.round(full_amount * share / 100.0)`: [3](#0-2) [4](#0-3) 

These rows are inserted directly into `headers_commission_outputs`/`witnessing_outputs`, which back real spendable bytes: they are later summed via `mc_outputs.calcEarnings`'s `SUM(amount)` and accepted as valid `headers_commission`/`witnessing` input amounts during unit validation: [5](#0-4) [6](#0-5) 

There is no step anywhere that reconciles the sum of the rounded per-recipient shares back to the exact fee amount that was actually collected from the paying unit (`payload_commission`/`headers_commission` fields validated to balance inputs/outputs at unit-acceptance time): [7](#0-6) 

### Impact Explanation
Because every full node computes this distribution deterministically from the same on-chain data, all nodes agree on the (slightly wrong) total, so this is not a consensus-disagreement bug. However, it is a genuine, deterministic byte-supply drift: whenever independent rounding causes the sum of shares to exceed the original commission, additional bytes are created out of nothing and become spendable by the commission recipients — a small, continuous supply inflation. Conversely, when rounding drifts the other way, small amounts of value are permanently lost (dust), which by itself is lower severity, but the inflationary direction is a genuine violation of "total spendable bytes must equal collected commissions."

### Likelihood Explanation
This occurs automatically for any headers-commission or witnessing-commission distribution whose `full_amount`/`payload_commission` is not evenly divisible by the number of recipients or by the recipients' percentage shares — a very common, naturally occurring condition (any prime-count divisor, any percentage split not aligned to the amount) — so it is a high-likelihood, continuously triggered condition rather than a rare edge case. No malicious actor is even required; ordinary multi-recipient/multi-witness situations trigger it.

### Recommendation
Instead of rounding each recipient's share independently, compute exact (possibly fractional) shares, round them using a scheme that preserves the total (e.g., largest-remainder method / cumulative rounding: track running rounding error and adjust the last recipient's amount so the sum exactly equals `full_amount`/`payload_commission`), or explicitly assign the rounding remainder (positive or negative) to a single deterministic recipient (e.g., the first or last by address) so the total distributed always equals the exact input amount.

### Proof of Concept
1. Construct (or observe naturally occurring) a unit whose `payload_commission = 11` is paid to `count_paid_witnesses = 3` witnesses (any MC unit where exactly 3 of the 12 witnesses authored descendant units within the window qualifies).
2. `updatePaidWitnesses` → `buildPaidWitnessesForMainChainIndex` computes each witness's `amount = Math.round(11/3) = Math.round(3.667) = 4` [1](#0-0) .
3. Three rows of `amount = 4` are inserted into `witnessing_outputs` for `main_chain_index`, totaling `12`, one byte more than the `payload_commission = 11` actually paid by the unit's author as a fee.
4. Each witness can later spend their `4`-byte output via a `witnessing` input, validated by `mc_outputs.calcEarnings` summing `witnessing_outputs.amount` [5](#0-4)  and accepted in `validation.js` as legitimate `total_input` [6](#0-5) , so the extra byte becomes real spendable supply not backed by any corresponding fee payment.
