This confirms the vulnerability path: `PushHandler` (and `Handler#stacks`/`#repository_name`) resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` [1](#0-0) , while `WebhooksController#verify_signature` selects which GitHub App/secret to authenticate the request with by computing `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and using `Shipit.github(organization: repository_owner)` [2](#0-1) . For the `membership` event specifically, `MembershipHandler` authorizes/writes a `Team` scoped to `params.organization.login`, an entirely different field from `repository_owner` used for signature selection [3](#0-2) .

### Title
Cross-organization team/repository confusion via webhook signature/content field mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC secret) used to authenticate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`) [4](#0-3) . However, the handlers that act on the payload use a *different* field to decide what is written: `PushHandler`/`Handler#stacks` uses `repository.full_name` [1](#0-0) , and `MembershipHandler` uses `organization.login` to create/find a `Team` and add a member to it [5](#0-4) . Because the HMAC covers the raw JSON body (`request.raw_post`) but the *only* thing checked is "does this body's signature match the secret configured for the org named in `repository_owner`", nothing ties the value used for authentication to the value used for authorization/action in a multi-org (or attacker-known-secret) setup. This is the same class of bug as the reported issue: a value/binding that is trusted implicitly but never actually cross-checked against the field it's supposed to protect.

### Finding Description
Shipit supports mounting multiple independent GitHub Apps, one per organization, each with its own `webhook_secret` configured under `github.<org>.webhook_secret` in `secrets.yml` [6](#0-5) . Each participating organization's administrators typically create and configure their own GitHub App (and therefore know their own `webhook_secret`), then hand the values to the Shipit operator to add to the multi-org config.

`verify_signature` picks the app/secret via:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

and validates the HMAC only against that selected app's secret. It does not check that every organization-identifying field embedded elsewhere in the same payload is consistent with `repository_owner`. For the `membership` event, `MembershipHandler#find_or_create_team!` trusts `params.organization.login` (a sibling field, independent of `repository.owner.login`) to scope the `Team` record that is created/looked up and to which the specified `member` is added [7](#0-6) .

An org administrator who legitimately controls Org A's own GitHub App (and thus knows Org A's `webhook_secret`) can therefore forge a `membership` event: set `repository.owner.login` = `"orgA"` (so `verify_signature` selects Org A's app and the HMAC — computed with the attacker's own known secret — validates), while setting `organization.login` = `"orgB"` (the victim organization) and `member.login` to an attacker-controlled Shipit user. `MembershipHandler` will create/find `Team` scoped to `orgB` and add the attacker's user to it, without ever verifying the membership against GitHub itself.

### Impact Explanation
`User#authorized?` checks whether the current user belongs to any team in `Shipit.github_teams` [8](#0-7) , and `Authentication#force_github_authentication` gates all engine access on this check [9](#0-8) . By forging a `membership` "added" event scoped to a victim org/team combination that is part of `Shipit.github_teams`, an attacker who only controls a co-tenant organization's own GitHub App secret can grant themselves (or any Shipit `User`) membership in a team they are not actually a GitHub member of, bypassing the `Shipit.github_teams` authorization boundary and gaining access to stacks, deploys and secrets belonging to organizations they do not control — matching the High-severity "escalation into `Shipit.github_teams` authorization" criterion.

### Likelihood Explanation
This requires the attacker to be an admin of at least one organization onboarded into Shipit's multi-org GitHub App config (a legitimate but low-trust position in this specific deployment model), and requires Shipit to be running with the documented multi-org configuration, `membership` webhooks enabled, and `Shipit.github_teams` restrictions in place. This is a realistic scenario for Shipit installations serving multiple semi-trusted organizations, since the "Using Multiple GitHub Applications" model is explicitly documented and supported [6](#0-5) .

### Recommendation
In `MembershipHandler` (and any other handler that reads an organization/repository-identifying field), require that the field used for authorization/write matches the field used to select the verifying GitHub App (`repository_owner`), e.g. assert `params.organization.login == repository_owner` (or pass `repository_owner` down from the controller into the handler and cross-check it) before creating/mutating `Team` records. More generally, bind every organization-identifying field consumed by a handler to the single organization identity that was cryptographically verified for that request.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with its own GitHub App/`webhook_secret` (multi-org setup per `docs/setup.md`).
2. As an admin of `orgA` (attacker), compute a valid `sha1=` HMAC of a crafted JSON body over `orgA`'s known `webhook_secret`:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Victim Team", "slug": "victim-team", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "orgB"},
  "member": {"login": "attacker-shipit-user"},
  "repository": {"owner": {"login": "orgA"}}
}
```
3. POST this body with header `X-Github-Event: membership` and the computed `X-Hub-Signature` to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s app, and the signature validates successfully (per `app/controllers/shipit/webhooks_controller.rb` lines 24-49).
5. `MembershipHandler#process` runs, creating/finding a `Team` with `organization: "orgB"` and adding `attacker-shipit-user` to it (per `app/models/shipit/webhooks/handlers/membership_handler.rb` lines 22-43).
6. If `orgB/victim-team` is part of `Shipit.github_teams`, `attacker-shipit-user` now passes `User#authorized?` and gains access to `orgB`'s stacks.

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|

            team.organization = params.organization.login
          end
