### Title
Webhook `status` events are applied to commits by SHA alone, letting any authenticated GitHub organization forge CI status for another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on the request body's own `repository.owner.login`/`organization.login` field, then hands the *entire* JSON body to the matching event handler. `StatusHandler`, however, applies the status update by matching `Commit.where(sha: params.sha)` globally, without ever checking that the commit's stack/repository belongs to the same organization that produced a valid signature. This breaks the intended binding: "organization that authenticated" == "repository that is written."

### Finding Description
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own GitHub App and `webhook_secret`: [1](#0-0) 

Signature verification picks the app/secret to verify against using an attacker-controlled field of the *same* unverified payload: [2](#0-1) [3](#0-2) 

Once the signature check passes (using whichever organization's secret matches `repository_owner`), the raw params are dispatched unchanged to the handler for the event type: [4](#0-3) 

`StatusHandler#process` looks up the target `Commit` purely by `sha`, across the entire `commits` table, with no scoping to the repository/organization that was actually authenticated: [5](#0-4) 

The equality that should hold but doesn't:
`organization whose webhook_secret verified the HMAC` == `organization owning the repository/commit that gets mutated`.

Because `Commit` records are global (not namespaced by the signing organization) and `StatusHandler` never cross-checks `payload['repository']['full_name']`/owner against the commit's actual stack/repository, an attacker who is a legitimate GitHub App admin for **any one** organization configured on the shared Shipit instance (call it Org A) can:
1. Learn a target commit `sha` belonging to a stack in Org B (also hosted on the same Shipit instance) — commit shas are visible on GitHub, in PR pages, CI logs, etc.
2. Send a `status` webhook payload with that `sha`, `state: "success"`, and any `context`, signed with **Org A's** `webhook_secret` (fully within the attacker's control since they administer Org A's GitHub App/webhook settings).
3. `verify_signature` validates the HMAC successfully against Org A's secret (since `repository_owner` in the payload can independently be set to `"orgA"` while `sha` still targets a commit belonging to Org B).
4. `StatusHandler` finds the Org B `Commit` purely by `sha` and calls `commit.create_status_from_github!(params)`, injecting a forged, attacker-chosen CI status onto it.

### Impact Explanation
Commit status is a security-relevant signal consumed by `MergeRequest#any_status_checks_missing?`/`any_status_checks_failed?`/`all_status_checks_passed?` (via `StatusChecker`) and by `Stack#branch_status`, which gate whether a pull request can be auto-merged by the merge queue and whether a commit is eligible for deploy: [6](#0-5) [7](#0-6) 

By forging a passing status for an arbitrary commit in Org B's repository, an attacker who has no GitHub write access, Shipit `ApiClient` token, or webhook secret for Org B can make a blocked commit appear CI-green, enabling the merge queue to merge a pull request or a deploy to proceed that should have been blocked — an unauthorized merge/deploy across organizational trust boundaries, meeting the Critical bar (unauthorized deploy/merge).

### Likelihood Explanation
This requires the Shipit instance to host more than one GitHub organization (an explicitly documented and supported configuration) and requires the attacker to control/administer the GitHub App webhook settings for at least one of the hosted organizations, plus knowledge of a target commit SHA in another hosted organization (obtainable from public GitHub activity). No repository write access, GitHub App private key, or `Shipit` API token for the victim organization is needed. This is a realistic scenario for shared/multi-tenant Shipit deployments.

### Recommendation
In `StatusHandler` (and any other handler that resolves records purely from payload identifiers), scope lookups to the repository the verified webhook's organization owns — e.g., join `Commit` through `stack.repository` and require `repository.full_name`/`owner` to match the organization whose secret verified the signature, rejecting the event otherwise. More generally, `WebhooksController#verify_signature` should re-derive and pin the authenticated organization for the remainder of request processing, and every handler should assert that `payload['repository']['owner']['login']` (or equivalent) matches that pinned organization before mutating any record.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `github.webhook_secret` (per documented multi-org config).
2. As the administrator of `orgA`'s GitHub App, note `orgA`'s `webhook_secret`.
3. Identify a commit `sha` belonging to a stack under `orgB` (e.g., from GitHub's public commit history or a PR page).
4. Build a `status` event JSON body: `{"sha": "<orgB commit sha>", "state": "success", "context": "ci/required", "repository": {"owner": {"login": "orgA"}, "full_name": "orgA/some-repo"}}`.
5. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` and POST to `/webhooks` with header `X-Github-Event: status`.
6. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")` and validates successfully.
7. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the `orgB` commit, and calls `create_status_from_github!`, writing the forged `success` status onto `orgB`'s commit even though the attacker never authenticated to or had credentials for `orgB`.
