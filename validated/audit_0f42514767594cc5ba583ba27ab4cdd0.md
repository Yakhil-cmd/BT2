### Title
Cross-repository Commit status write via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository/stack scoping, while `Handler#stacks`/`#repository_name` (which would derive the correct scope from `payload['repository']['full_name']`) exist but are never called by this handler. Any webhook delivering a `status` event for a repository whose signature the attacker can legitimately produce (because they own/administer that repository and installed the app there) can write a `Status` for **any** commit in the database that happens to share the same `sha`, regardless of which repository that commit actually belongs to.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`Handler#stacks` (i.e. `Repository.from_github_repo_name(payload['repository']['full_name'])&.stacks`) == the actual set of `Commit` rows that `StatusHandler#process` mutates.

Code path:
- `WebhooksController#create` parses the JSON body and dispatches `Shipit::Webhooks.for_event('status')` → `Handlers::StatusHandler` [1](#0-0) [2](#0-1) .
- `Handler.call` → `new(payload).process`, and the base `Handler` class defines `#stacks`/`#repository_name` helpers that scope operations to the repository named in the payload, but nothing forces subclasses to use them [3](#0-2) .
- `StatusHandler#params` never requires or reads `payload['repository']` at all — only `sha`, `state`, and a few optional fields [4](#0-3) .
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across the entire `commits` table [5](#0-4) .
- `Commit belongs_to :stack` and `has_many :statuses` [6](#0-5) , so any commit matched by `sha`, in any stack/repository, gets a new `Status` row created and stack-level side effects triggered (`Hook.emit`, `stack.schedule_merges`, `ProcessMergeRequestsJob`) via `add_status` [7](#0-6) .

Compare with the sibling `CheckSuiteHandler`, which correctly scopes via `stacks.where(branch: ...)` before touching commits [8](#0-7) , confirming the pattern `StatusHandler` should have followed but doesn't.

Existing guards do not close this gap:
- `verify_signature` in `WebhooksController` only checks the webhook's HMAC using the GitHub App secret for the `repository_owner` inferred from the payload/organization — it authenticates that *some* legitimate GitHub delivery for that owner's app occurred, it says nothing about which `sha`/commit the payload targets [9](#0-8) .
- `drop_unhandled_event` only filters unregistered event types, not payload content.
- The `ExplicitParameters` schema for `StatusHandler` doesn't declare or validate `repository` at all, so there is no schema-level enforcement tying the sha to a repository.

**Attacker's exact request:** attacker controls (or has app access to) their own GitHub repository "attacker/own-repo" with the Shipit GitHub App installed and configured, so GitHub will legitimately sign and deliver `status` webhooks to the Shipit `/webhooks` endpoint for events on that repo (no secrets need to be stolen — the signature is produced by GitHub itself using the app secret associated with the attacker's own installation/org). The attacker crafts (or triggers via CI on their own repo, or via direct code if their own org's status API allows arbitrary status posts) a `status` payload with `sha` set to a commit SHA known to belong to a **different** target repository (commit SHAs are not secrets — they are publicly visible in commit history, PRs, CI logs, etc., for public repos, and even for private repos may leak via CI logs, PR references, etc.). The `repository.full_name` field is irrelevant to processing since `StatusHandler` never reads it.

### Impact Explanation
A successful request causes `Commit#create_status_from_github!` to run against a commit that belongs to a repository/stack the attacker never authenticated against, writing a new `Status` row, potentially flipping the commit's deployability state, triggering `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` / `ProcessMergeRequestsJob` [7](#0-6) . This can mark an arbitrary target commit as `success`/`failure`, potentially triggering an automatic merge or unblocking a deploy for a stack the attacker has no relationship with — a payload for one repository mutating another's stack/commit state, matching the "Critical" impact category defined in the rules. It is repeatable against any target repository/commit for which the attacker can learn (or, per the question's stricter framing, collide) a SHA.

### Likelihood Explanation
The attacker needs: (1) the ability to have GitHub deliver a legitimately signed `status` webhook — achievable by installing/using the Shipit GitHub App on their own repository, something any unprivileged GitHub user with a repo can do if the org allows the app, or by controlling any repository already integrated with the target Shipit instance; and (2) knowledge of a target commit `sha`. Knowledge of a SHA is often trivial (public repos, PR links, CI logs) — no cryptographic collision is required in the common case, weakening the "sha collision" framing in the question but not the underlying bug, since the bug is really "no repository scoping at all," not "SHA collision resistance." No Shipit session, API token, or secret material is required.

### Recommendation
Scope `StatusHandler#process` to the repository indicated by the payload, mirroring `CheckSuiteHandler`: require `repository.full_name` in the `params` schema, then restrict the commit lookup via `stacks.joins(:commits).where(commits: { sha: params.sha })` (or `stacks.flat_map(&:commits).select { sha match }`) instead of a bare `Commit.where(sha:)`, so a status payload can only mutate commits belonging to stacks under the repository that was authenticated for that webhook delivery.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — not present in repo today):
```ruby
test "StatusHandler must not write a status for a commit outside the payload's own repository" do
  attacker_repo_stack = shipit_stacks(:attacker_repo_stack) # belongs to repository "attacker/own-repo"
  victim_commit = shipit_commits(:victim_repo_commit)       # belongs to a different repository/stack

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/own-repo' }
  }

  # Binding under test, both sides evaluated BEFORE calling the handler:
  # LHS: Handler#stacks for this payload (scoped to attacker's repo)
  scoped_stacks = Shipit::Repository.from_github_repo_name('attacker/own-repo')&.stacks || Shipit::Stack.none
  assert_not_includes scoped_stacks, victim_commit.stack   # LHS excludes victim's stack

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Running this against current code fails the `assert_no_difference` — `victim_commit.statuses.count` increases by 1 even though `victim_commit.stack` is not in `scoped_stacks`, proving `Handler#stacks` is never consulted and the equality is broken.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
