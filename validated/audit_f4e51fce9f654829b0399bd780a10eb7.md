### Title
Use-after-free-style race on shared unit caches via unlocked `storage.resetMemory()` triggered by unprivileged `light/dry_run_aa` requests - ([File: network.js])

### Summary
Every `light/dry_run_aa` network request from an unprivileged light client causes the full node to run an unlocked, fire-and-forget `storage.resetMemory()` call whenever `constants.COUNT_WITNESSES === 1`. This function synchronously deletes every entry of the shared in-memory caches `assocUnstableUnits`, `assocBestChildren`, `assocStableUnits`, `assocStableUnitsByMci` and then asynchronously repopulates them from the DB — all without acquiring the `"write"` mutex that every other consumer of these caches (validation, the writer, `shrinkCache`) relies on for exclusivity. [1](#0-0) 

### Finding Description
The handler for `light/dry_run_aa` runs a dry-run AA trigger and then, if the network has a single witness, calls:
```js
db.executeInTransaction(function (conn, onDone) {
    storage.resetMemory(conn, onDone);
});
```
This call is not awaited and is not protected by any mutex. [2](#0-1) 

`storage.resetMemory` synchronously wipes the caches and asynchronously rebuilds them:
```js
function resetUnstableUnits(conn, onDone){
	Object.keys(assocBestChildren).forEach(unit => delete assocBestChildren[unit]);
	Object.keys(assocUnstableUnits).forEach(unit => delete assocUnstableUnits[unit]);
	initUnstableUnits(conn, onDone);
}
function resetStableUnits(conn, onDone){
	Object.keys(assocStableUnits).forEach(unit => delete assocStableUnits[unit]);
	Object.keys(assocStableUnitsByMci).forEach(mci => delete assocStableUnitsByMci[mci]);
	initStableUnits(conn, onDone);
}
``` [3](#0-2) 

Every other writer of these same caches takes the `"write"` mutex before mutating them, e.g. `shrinkCache()`:
```js
const unlock = await mutex.lock("write");
...
delete assocKnownUnits[row.unit]; delete assocCachedUnits[row.unit]; ...
unlock();
``` [4](#0-3) 

and `initCaches()` itself takes the same lock before the very first population of the caches: [5](#0-4) 

Meanwhile, unit validation and stabilization (`validateParents`, `determineIfStableInLaterUnitsAndUpdateStableMcFlag`, `writer.saveJoint`) read and mutate `assocUnstableUnits[unit].parent_units`, `assocBestChildren[parent_unit]`, etc. while holding only the per-author mutex from `validation.validate` — not the `"write"` lock that guards `resetMemory`: [6](#0-5) 

`readUnitProps` explicitly assumes `assocUnstableUnits[unit]` is always present for non-stable units and throws if it is missing:
```js
if (!assocUnstableUnits[unit])
    throw Error("no unstable props of "+unit);
``` [7](#0-6) 

Because `resetMemory` is fired from an unauthenticated/unprivileged network handler concurrently with normal validation/writer flow, another in-flight code path (a unit poster's validation, an AA trigger being applied, or `forgetUnit`/`fixIsFreeAfterForgettingUnit` cleanup) can observe the caches in a torn state: entries momentarily deleted before `initUnstableUnits`/`initStableUnits` repopulate them, or repopulated with a different generation of objects than the ones already captured by reference in in-flight closures (e.g. `objFirstUnit = storage.assocUnstableUnits[first_unit]` in `revertResponsesInCaches`, or `assocBestChildren[best_parent_unit]` arrays holding stale row references) [8](#0-7) [9](#0-8) 

This is the same bug class as CVE-2022-1145: a user-reachable action (profile destruction in Chrome / a light-client dry-run request in ocore) frees/destroys a shared in-memory object graph while another asynchronous operation still holds and dereferences stale references into that same graph, without any synchronization guaranteeing exclusivity.

### Impact Explanation
Concurrent access to a cache in the middle of being wiped and rebuilt can:
- Throw uncaught `Error("no unstable props of "+unit)` / `Error("trying to forget stable unit "+unit)` in the middle of unit validation or AA-trigger processing, crashing the node process (denial of service, "network unable to confirm new units").
- Cause `fixIsFreeAfterForgettingUnit`/`forgetUnit` to operate on a half-rebuilt `assocUnstableUnits`/`assocBestChildren` set, corrupting `is_free` bookkeeping used by unit composition and stability determination, which can lead to nodes disagreeing on which units are free/stable — a "node disagreement on validity or stability" condition.
- If two `resetMemory` calls or a `resetMemory` and a `writer.saveJoint`/stabilization pass interleave, `assocStableUnitsByMci` / `assocStableUnits` can end up inconsistent with the DB state that the caches are supposed to mirror, since nothing re-validates consistency after an unlocked rebuild (contrast with the locked, single-consumer `shrinkCache`).

This satisfies the "Validate" bar: node disagreement on validity/stability or a node crash preventing confirmation of new units.

### Likelihood Explanation
Reaching this path requires only sending a `light/dry_run_aa` request naming any existing AA address, which is available to any (light) peer with no authentication, and requires `constants.COUNT_WITNESSES === 1` (private/testnet-style single-witness deployments, which are a supported and documented configuration in ocore). An attacker can trivially spam this request while normal unit posting/AA trigger activity is ongoing to maximize the race window, making the race easy to trigger repeatedly, though the specific window in which a crash/corruption occurs still depends on timing.

### Recommendation
- Wrap the `storage.resetMemory()` call inside `network.js`'s `light/dry_run_aa` handler with `mutex.lock("write")` (matching how `shrinkCache`, `initCaches`, and other writers of `assocUnstableUnits`/`assocStableUnits` synchronize).
- Await the `resetMemory` operation (currently fire-and-forget) so overlapping requests cannot race each other, and consider skipping the reset entirely for the dry-run path (the dry run itself already rolls back its transaction and calls `revertResponsesInCaches`), since a global cache-wide reset for a stateless dry run is disproportionate and unnecessary.
- Audit `resetUnstableUnits`/`resetStableUnits` to make the delete+rebuild atomic with respect to `"write"`-lock holders, or perform the swap by building new objects off to the side and atomically re-assigning the module-level references once fully populated, instead of `delete`-ing keys in place.

### Proof of Concept
1. Run an ocore-based full node configured with `constants.COUNT_WITNESSES === 1` (e.g., a private/testnet deployment).
2. From a light client (or any peer able to open a websocket to the node), continuously send:
```json
["request", {"command": "light/dry_run_aa", "params": {"address": "<existing AA address>", "trigger": {"outputs": {"base": 10000}, "address": "<any address>"}}}]
```
3. Concurrently, have another peer post ordinary units / AA triggers that get validated and stabilized by the same node (normal traffic).
4. Because each `dry_run_aa` response triggers an unlocked `storage.resetMemory()`, repeating step 2 rapidly increases the probability of it interleaving with the write-mutex-protected validation/writer code in step 3, ultimately producing a thrown `"no unstable props of "+unit"` (or similar) error from `readUnitProps`/`forgetUnit`, crashing the node or leaving its caches — and therefore its view of unit stability — inconsistent with peers that did not experience the race.
