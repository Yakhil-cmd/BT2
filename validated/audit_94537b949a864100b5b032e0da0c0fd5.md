### Title
Webhook signature verification is bound to `repository.owner.login`, not to `repository.full_name` acted on by handlers — allows cross-organization webhook forgery in multi-org installs - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the payload against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . However, every event `Handler` (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolves the target `Stack`/`Repository` using a *different* field of the same payload: `payload.dig('repository', 'full_name')` [3](#0-2) . The signature check never verifies that these two fields agree.

### Finding Description
Shipit supports per-organization GitHub App configuration, each with its own optional `webhook_secret` (`docs/setup.md` explicitly documents the webhook secret as "optional", and `test/dummy/config/secrets_double_github_app.yml` shows two orgs, one of which is configured with `webhook_secret: # nil`). In `GitHubApp#verify_webhook_signature`, if no secret is configured for the resolved organization, the check short-circuits and returns `true` unconditionally, without inspecting the signature header at all: [4](#0-3) .

The organization used to pick this (possibly secret-less) `GitHubApp` instance is taken from the attacker-controlled JSON body itself, via `repository_owner` — `params.dig('repository', 'owner', 'login')` [2](#0-1) . Once `verify_signature` passes, `WebhooksController#create` parses the same raw JSON and dispatches it unmodified to the registered handlers for the event [5](#0-4) .

Every handler's `stacks`/`repository_name` lookup is driven by `payload.dig('repository', 'full_name')` [3](#0-2) , which is resolved into an owner/name pair independently via `Repository.from_github_repo_name` [6](#0-5) .

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the acted-upon repository/stack) are two independent, attacker-supplied JSON fields in the same unsigned-at-this-point request body, an attacker can set them to different organizations. If any organization configured in `Shipit.github` has no `webhook_secret` set, the attacker can claim that organization in `repository.owner.login` (bypassing signature verification entirely, since `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header value) while pointing `repository.full_name` at a real, tracked repository belonging to a *different*, properly-secured organization.

This breaks the trust binding: **organization authenticated (via `repository.owner.login`) ≠ repository actually written to/acted upon (via `repository.full_name`)**.

### Impact Explanation
With this decoupling, an unauthenticated attacker can drive any registered webhook handler against a real tracked `Stack`:
- `PushHandler` will call `stack.sync_github(expected_head_sha: params.after)` for the victim repo/branch using an attacker-chosen SHA [7](#0-6) , forcing Shipit's model of the branch head/commit list to sync with attacker-supplied data.
- `StatusHandler`/`CheckSuiteHandler` (also keyed off the same `full_name`-derived `stacks`/`Repository` lookup in `Handler`) can be used to record CI status or check-run results against arbitrary commits of the victim stack, as demonstrated for legitimate signed requests in `test/controllers/webhooks_controller_test.rb` (`:state create a Status for the specific commit`).

Since Shipit deploy pipelines gate merges/deploys on commit status/check-run state, an attacker able to inject fabricated "success" statuses for arbitrary SHAs of a legitimately tracked repository — without ever holding that repository's webhook secret — can manipulate the CI gating data Shipit relies on for deploy decisions. This qualifies as unauthorized manipulation of deploy-gating state through a forged, effectively-unauthenticated webhook, which the engine explicitly guards through the org-scoped `verify_webhook_signature` check.

### Likelihood Explanation
Exploitability depends on the deployment running with at least one configured GitHub organization/App whose `webhook_secret` is left unset — a state the engine's own documentation and test fixtures (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`) explicitly present as a supported, optional configuration for multi-org installs. Given that, no credentials, tokens, or valid signatures are required at all — a bare unauthenticated HTTP POST to `/webhooks` with a crafted body is sufficient.

### Recommendation
Bind the organization used for signature verification to the same repository field the handlers act upon. Concretely, `WebhooksController#repository_owner` should be derived from `repository.full_name`'s owner segment (or the two must be validated as equal) rather than trusting `repository.owner.login`/`organization.login` independently. Additionally, consider requiring `webhook_secret` to be present for every configured organization (reject boot/verification when absent) instead of silently returning `true`, closing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Given a Shipit install configured with two GitHub orgs, `secured-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, i.e. `nil`), where `secured-org/victim-repo` is a tracked Shipit stack:

```
POST /webhooks
X-Github-Event: push
(no X-Hub-Signature header required)

{
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secured-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```

1. `verify_signature` resolves `repository_owner` = `"open-org"` and fetches `Shipit.github(organization: "open-org")`.
2. `GitHubApp#verify_webhook_signature` returns `true` immediately because `open-org` has no `webhook_secret` configured — the request passes verification with no valid signature.
3. `create` parses the body and dispatches to `PushHandler`, whose `repository_name` reads `payload.dig('repository', 'full_name')` = `"secured-org/victim-repo"`.
4. `Repository.from_github_repo_name("secured-org/victim-repo")` resolves the real, secured stack, and `stack.sync_github(expected_head_sha: "deadbeef...")` is invoked — despite the request never being signed with `secured-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
