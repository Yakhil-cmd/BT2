### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while all event handlers act on the independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC using the organization derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), but every downstream `Shipit::Webhooks::Handlers::Handler` resolves the repository/stack to mutate using the separate, unchecked field `payload.dig('repository','full_name')`. These two JSON fields are never cross-validated against each other.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is used solely to pick which `Shipit.github(organization: ...)` app/secret verifies the raw body's HMAC signature via `github_app.verify_webhook_signature`, defined in: [3](#0-2) 

Once verification succeeds, `WebhooksController#create` dispatches the entire, attacker-fully-controlled JSON body to handlers unchanged: [4](#0-3) 

Every handler resolves the target `Stack`/`Repository` from a *different* field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

`PushHandler` uses this to directly trigger a git sync on any stack matching that repository/branch: [6](#0-5) 

Pull-request handlers (`OpenedHandler`, `ClosedHandler`, etc.) likewise resolve `repository` purely from `params.repository.full_name`, independent of the field used for signature verification: [7](#0-6) [8](#0-7) 

**Binding that is broken (as an equality):**
`organization authenticated by verify_signature (repository.owner.login)` == `repository written by the handler (repository.full_name)`

Because Shipit supports multi-tenant GitHub App configuration (`config/secrets.*.yml` keyed by organization, e.g. `somegithuborg` / `someothergithuborg`), an operator/attacker who legitimately controls one configured organization ("attacker-org", with its own valid `webhook_secret` known to them) can:
1. Craft an arbitrary JSON payload where `repository.owner.login = "attacker-org"` (so `verify_signature` picks and successfully validates against attacker-org's own secret, which the attacker legitimately possesses/can compute) — while
2. Setting `repository.full_name = "victim-org/victim-repo"` (a repository/stack tracked by Shipit under a completely different, unrelated organization).

`verify_signature` only checks the HMAC against `repository.owner.login`'s secret; it never confirms that `repository.full_name` starts with that same owner. The dispatched handlers then act on the victim repository resolved via `full_name`, e.g. `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, and PR handlers can create/archive review stacks or manipulate merge-queue state for the victim repository — all triggered by a payload only cryptographically bound to the attacker's own organization, not to the victim's.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding described in the reference bug class: cryptographic authentication is scoped to one entity (attacker-org) while the write/side-effect target is scoped to a different entity (victim-org's stack) with no cross-check. This allows cross-repository state manipulation (forced sync, review-stack creation/archival, merge-queue state changes) on repositories the caller does not control, which the rules classify under cross-repository writes / unauthorized deploy-adjacent actions reachable purely from an unprivileged actor's own legitimately-configured organization credentials — no `ApiClient` token, GitHub App private key, or repository write access on the *victim* repo is required.

### Likelihood Explanation
Likelihood is High in any Shipit deployment using the documented multi-tenant GitHub configuration (multiple orgs, each with distinct `webhook_secret`, as shown in `config/secrets.development.shopify.yml` and the multi-org example in `config/secrets.development.example.yml`). Any organization admin who is permitted to install/operate their own GitHub App entry in Shipit's config can trivially forge this decoupling, since they know their own `webhook_secret` and can freely author arbitrary JSON bodies to `/webhooks`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that `repository.full_name`'s owner segment matches `repository.owner.login` (or `organization.login`) before dispatching to handlers — i.e., enforce the equality `repository.owner.login == repository.full_name.split('/').first` prior to acting on any handler-resolved repository, rejecting mismatched payloads with a 422.

### Proof of Concept
1. Configure Shipit with two orgs in `config/secrets.yml`: `attacker-org` (secret known/controlled by the attacker, who legitimately administers this org's GitHub App) and `victim-org` (tracks a real Shipit `Stack`, e.g. `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using attacker-org's own `webhook_secret` (`lib/shipit/github_app.rb#verify_webhook_signature`, `app/controllers/shipit/webhooks_controller.rb#verify_signature`).
4. `verify_signature` resolves `repository_owner = "attacker-org"`, verifies successfully against attacker-org's secret, and `head(422)` is never called.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb`), finds the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: params.after)` on a stack the attacker never legitimately controls — using only the attacker's own organization's signing secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
