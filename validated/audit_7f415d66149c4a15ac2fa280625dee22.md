I found a concrete analog to the Deepbook "trade proof bypass" bug class in `private_payment.js`'s duplicate-detection shortcut, which — just like `settle_balance_manager` skipping `trade_proof` validation when `balances_out == balances_in` — skips the entire spend-proof / double-spend / chain-linkage validation path whenever a loosely-matching "duplicate" condition is met.

### Title
Private Payment Duplicate-Output Shortcut Bypasses Spend-Proof and Chain Validation - (File: private_payment.js)

### Summary
`validateAndSavePrivatePaymentChain` in `private_payment.js` contains a "duplicate" detection shortcut intended to make re-delivery of an already-validated private payment idempotent. For divisible (non-fixed-denomination) private assets, the shortcut matches on *any* output in the incoming payload against *any* previously stored output for that `(unit, asset, message_index)`, rather than requiring the entire submitted private-payment chain to be identical to what was already validated. If a match is found, the function immediately calls `transaction_callbacks.ifOk()` and returns — completely skipping `divisibleAsset.validateAndSavePrivatePaymentChain`, which is what performs spend-proof verification, source-output inclusion checks, and payment balance validation (`validation.validatePayment`).

### Finding Description
The vulnerable logic is in `private_payment.js`: [1](#0-0) 

For divisible assets, `bDuplicate` is computed as:
```
bDuplicate = (payload.outputs || []).some(output => {
    return ValidationUtils.isNonemptyObject(output)
        && stored.denomination === 1
        && stored.amount === output.amount
        && stored.address === output.address
        && stored.blinding === output.blinding;
});
```
This iterates over **all** outputs in the attacker-supplied `payload.outputs` array and returns true if **any one of them** matches a single already-stored, previously-validated output row for the same `(unit, asset, message_index)`. It does not verify that the rest of the submitted payload/chain (inputs, other outputs, spend proofs, or the referenced previous chain elements `arrPrivateElements[1..]`) is identical to what was originally validated and saved.

This is structurally the same bug class as the reported `vault::settle_balance_manager` issue: a proof/validation routine (`assetModule.validateAndSavePrivatePaymentChain`, which is the private-payment analog of `deposit_with_proof`) is invoked *conditionally*, gated on an equality check that can be satisfied without the full data actually being validated. Just as an attacker could craft a `trade_proof` that's never verified because `balances_out == balances_in`, here an attacker can craft a private-payment chain that reuses one legitimate, previously-seen output (address+blinding+amount, which are not secret — they're transmitted directly to the recipient/cosigner in the private chain, cf. `network.js` `handleOnlinePrivatePayment` and `wallet.js` `handlePrivatePaymentChains`) to trigger the "duplicate" shortcut while attaching arbitrary/unvalidated inputs, other outputs, or a different (possibly broken/forked) chain of prior elements.

Since `assetModule.validateAndSavePrivatePaymentChain` (which performs `parsePrivatePaymentChain` → `validatePrivatePayment` → `validateSpendProof` / `validateSourceOutput` / `validation.validatePayment`) is never invoked when `bDuplicate` is true, none of these checks — spend-proof correctness ( [2](#0-1) ), chain-link inclusion, or input/output balance (`validation.validatePaymentInputsAndOutputs`) — occur for the "duplicate" submission, and the code proceeds straight to `ifOk()`.

### Impact Explanation
An unprivileged private-payment counterparty (anyone who legitimately received one private output belonging to a given `(unit, asset, message_index)` and thus knows its address/amount/blinding) can craft a new private-chain submission that piggybacks on that known output to satisfy the `bDuplicate` check, while pairing it with unvalidated inputs/other outputs. Because the underlying `validateAndSave` call is skipped, this can let an attacker record/accept a private payment element whose spend-proof was never checked and whose reference to prior chain elements was never confirmed to be genuine — a path toward double-spending a private (potentially stable) output or accepting an invalid/forged private-payment chain, since `ifOk()` triggers acceptance (`callbacks.ifAccepted`, event emission, forwarding to other wallet members) as if full validation had succeeded.

### Likelihood Explanation
Reaching this code path only requires being a normal recipient/cosigner in an existing private-payment chain (or otherwise learning one output's plaintext address/amount/blinding, which private chains routinely disclose to their designated recipients) and then submitting a follow-up/malformed chain via the standard `private_payment` device-message or network path (`network.js:handleOnlinePrivatePayment`, `wallet.js:handlePrivatePaymentChains`). No special privileges, node compromise, or protocol-level access are needed — this matches the "asset issuer / private-payment counterparty" threat model.

### Recommendation
The duplicate check must verify that the *entire* incoming payload (all inputs and all outputs, matched positionally, plus the full private-element chain) is byte-for-byte identical to what was previously validated and stored — not merely that some single output value matches some stored output row. Safer approaches: (1) hash the full incoming `arrPrivateElements` (or `payload`) and compare against a stored hash of the previously accepted submission for that `(unit, message_index)`; or (2) require full match against `payload.outputs[i]` for every index `i`, and also re-verify (or at minimum re-derive and compare) the chain of prior elements, not skip it outright. Do not let matching "the same output ended up in the DB" — which any counterparty can trivially reconstruct — substitute for full re-validation of a differently-shaped submission.

### Proof of Concept
1. Alice sends Bob a divisible private-asset payment; Bob receives the private chain and learns his own output's `{address, amount, blinding}` for `(unit, asset, message_index)`. This output gets validated and stored via `assetModule.validateAndSavePrivatePaymentChain` the first time.
2. An attacker (could be Bob himself, or anyone Bob shares the output with) crafts a new `arrPrivateElements` head element for the same `(unit, message_index)`, with `payload.outputs` containing Bob's already-stored output (same amount/address/blinding) as one of several outputs, but with a *different*/forged `inputs[0]` (e.g., pointing to a different, unvalidated or non-existent source unit) or a modified prior-chain element.
3. Submit this via `handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`.
4. In `private_payment.js`, the SQL lookup finds the stored row matching Bob's known output; `bDuplicate` evaluates true because `payload.outputs.some(...)` finds that one matching output, regardless of the forged input/other outputs.
5. `transaction_callbacks.ifOk()` fires immediately, bypassing `divisibleAsset.validateAndSavePrivatePaymentChain` (spend-proof check, source-output inclusion check, and `validation.validatePayment` balance check) entirely, and the submission is accepted as valid.
