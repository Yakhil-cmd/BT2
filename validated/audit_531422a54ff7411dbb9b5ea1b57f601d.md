### Title
Attacker-controlled routeXdr injects arbitrary contract calls beneath the caller's authorization, draining arbitrary tokens from the signer's wallet - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The Pagekit bug class — attacker-supplied data reaching a code-execution sink — maps onto the swap router's packed route program. `execute_strategy(sender, total_in, swap_xdr)` decodes `swap_xdr` into an address registry and instruction stream; every hop's `pool`, `token_in`, and `token_out` addresses come from that registry with no allowlist, and each venue adapter calls `env.invoke_contract` on the attacker-chosen `pool`. Rogue code on that call stack can invoke `token.transfer(victim, attacker, amount)` on any token; the Soroban host records it as a child of the caller's `require_auth` entry, and it executes if the caller signs the simulated authorization tree — which is the standard signing flow. The protocol's own test harness proves the theft end-to-end.

### Finding Description
`Program::decode` validates only byte layout, index bounds, modes, and opcodes; it never validates the `pool` address itself (program.rs). `dispatch_hop` then calls a venue adapter that performs `env.invoke_contract(&ctx.hop.pool, "swap", ...)` — e.g. Sushi's adapter invokes `token0`, `token1`, `get_oracle_hints`, and `swap` on the payload-chosen pool [1](#0-0) . The only call-site auth is `sender.require_auth()` at the top of `run` [2](#0-1) .

Because venue calls are not wrapped in invoker-contract auth on the router's side for the pool invocation itself, any `require_auth`-protected call the rogue pool makes on the *victim* attaches as a sub-invocation of the victim's auth entry. The harness test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows `token.transfer(alice, attacker, WALLET_BALANCE)` recorded beneath Alice's `swap_collateral` root and Alice's wallet emptied; the companion test shows the same theft succeeding in enforced mode once she signs the tree simulation returned [3](#0-2) [4](#0-3) . The threat model acknowledges the router "keeps no allowlist" of pools/tokens and that "the loss is then the caller's wallet" [5](#0-4) .

Both reachable paths are in scope: direct `execute_strategy` (one input-transfer child is honest; anything else is injected) and controller strategies (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) where the same rogue-hop mechanism applies to the caller's auth tree.

### Impact Explanation
Theft of user funds. A malicious route executes arbitrary token transfers of *any* asset the victim holds — not just the routed `token_in` — under the victim's own authorization. Neither the payload `min_out`, the router's measured balance deltas, nor the controller's `RouterOverspend`/`NoSwapOutput` checks bound the theft, because the stolen transfer never touches router or controller balances [6](#0-5) .

### Likelihood Explanation
Exploitation requires a victim to sign an authorization tree containing the rogue transfer. That is exactly what the normal flow produces: the quote server returns `routeXdr`, `simulateTransaction` records the auth tree, and the wallet signs it. A compromised/malicious quote or phishing route therefore suffices; the victim's only defense is decoding `routeXdr` and auditing every auth child client-side — a mitigation the threat model itself assigns to clients rather than the contract [7](#0-6) . This is user-interaction-dependent, matching the source advisory's `UI:R` profile — Medium.

### Recommendation
Enforce an on-chain allowlist (or hash-pinned venue registry) for `pool` addresses per venue opcode at `Program::decode` or hop dispatch time, so a route cannot name arbitrary contracts. Short of that, wrap each venue pool call so that sub-invocations requesting the *sender's* auth are structurally impossible (e.g., document and enforce that only the router's own invoker-contract auth may appear below a hop), and reject `token_in`/`token_out` registry entries that differ from the program header's declared pair where the semantics allow.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a complete PoC: `RogueHopPool.swap` calls `token::Client::transfer(victim, attacker, WALLET_BALANCE)` when reached as a hop pool; the test at lines 194–227 shows simulation recording the theft under Alice's `swap_collateral` auth root, and lines 229–269 show the enforced-mode execution succeeding when Alice signs that tree — her full wallet balance of an unlisted token moves to the attacker while the swap still returns fair output and passes all router/controller checks.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

That bound covers the controller's own grant only. The router calls the pool

recorded by an honest simulation as a child of the caller's authorization

entry, and a direct router swap gives exactly one input transfer. A client must

child. The direct `execute_strategy` path has the same exposure for every swap
