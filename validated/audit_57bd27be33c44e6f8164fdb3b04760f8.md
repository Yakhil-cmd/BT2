### Title
Webhook organization-authentication is decoupled from the repository actually acted on, allowing signature-check bypass for events targeting a different repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The Anycall bug reduces to: the entity that pays/authenticates the call ("_flag" on source) is not actually enforced against the effect the call has (fee is never supplied), so a call that should require payment silently proceeds unauthenticated. The same class of bug exists in `WebhooksController`: the *organization used to select and verify the webhook signature* is read from the **unverified** payload and is never required to match the *repository the event will actually act on*. Combined with the fact that signature verification is a no-op whenever an org has no `webhook_secret` configured, an attacker can make the "verified" org be one with no secret while the payload's `repository.full_name` targets a completely different, secret-protected repository/stack.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the secret) to verify against using a field taken straight from the raw, not-yet-verified JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository','owner','login')` — fully attacker-controlled, and it is used *before* any signature check occurs to decide **which** app/secret authenticates the request.

The verification itself is a no-op when that org has no configured secret: [3](#0-2) 

`return true unless webhook_secret` — this is also the documented default for a newly configured org (`webhook_secret: # nil`) in the setup docs and example secrets files.

Separately, the actual event handlers resolve **which repository/stack to act on** from a different key in the *same* payload, with no cross-check against the organization that was used for authentication: [4](#0-3) [5](#0-4) 

So the binding that should hold — `organization authenticated == owner(repository acted on)` — is never enforced. Concretely: `repository.owner.login` (used to pick the verifying `GitHubApp`) and `repository.full_name` (used to pick the `Stack` that gets acted on) are two independent, attacker-supplied fields inside one HTTP body. Nothing forces them to refer to the same organization. If the Shipit instance is configured with multiple GitHub orgs (a documented, supported configuration — see `config/secrets.development.shopify.yml`) and even one of them has no `webhook_secret` set, an attacker can:
1. Set `repository.owner.login` to that unprotected org, so `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header sent.
2. Set `repository.full_name` to any other, secret-protected repository already registered as a `Stack` in this Shipit instance.
3. The `create` action then dispatches the event to the appropriate handler using the *same* forged payload, which resolves the `Stack` via `repository.full_name` and acts on it (e.g. `PushHandler` calls `stack.sync_github`, driving `GithubSyncJob`), even though the request was never authenticated for that repository's org.

### Impact Explanation
This is an authentication-bypass on the webhook trust boundary: an unprivileged, unauthenticated network attacker can make Shipit process forged, unsigned GitHub events for any repository already tracked as a `Stack`, as long as any other org on the instance has no webhook secret configured (the documented default). Downstream this reaches `GithubSyncJob` and other status/PR handlers that feed commit "deployable" state and merge/queue behavior, meaning forged events can influence which commits get treated as deployable or queued, i.e. can be leveraged toward unauthorized deploy/merge actions without ever presenting a valid webhook secret for the targeted repository's organization. This satisfies the Critical/High bar of "unauthorized deploy" / authentication bypass.

### Likelihood Explanation
Likelihood is high wherever a Shipit deployment tracks more than one GitHub organization (a first-class, documented configuration) and any one of them omits `webhook_secret` (the shipped example configs default this field to blank/nil). No credentials, session, or repository write access are required — only knowledge of another tracked repository's `full_name`, which is visible in the Shipit UI itself.

### Recommendation
Bind the two fields together before trusting either: derive the organization used for signature verification and the organization implied by `repository.full_name` from the same value, and reject the request if they differ, or simply verify the signature using the secret that corresponds to the repository actually being resolved by the handler (not a caller-chosen `repository.owner.login`). Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for multi-org configurations; require every configured org's secret to be present or fail closed.

### Proof of Concept
Given a Shipit instance configured with two orgs, e.g.:
```yaml
github:
  open-org:      # no webhook_secret configured (blank/nil)
    app_id: 1
    installation_id: 1
  secure-org:    # webhook_secret: "s3cr3t"
    app_id: 2
    installation_id: 2
```
and a tracked `Stack` for `secure-org/production-repo`, an attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-invalid

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to exist>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/production-repo"
  }
}
```
`verify_signature` calls `Shipit.github(organization: 'open-org')` and `verify_webhook_signature` returns `true` unconditionally (no `webhook_secret` for `open-org`), so the before_action passes despite the bogus signature header. `create` then dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('secure-org/production-repo')` and calls `stack.sync_github(expected_head_sha:)` for `secure-org`'s protected stack — all without ever presenting `secure-org`'s real webhook secret.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
