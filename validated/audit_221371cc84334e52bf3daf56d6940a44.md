### Title
Webhook secret is selected using an unverified `repository.owner.login`/`organization.login` field that differs from the `repository.full_name` field trusted to select the Stack to sync - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the HMAC against based on `repository_owner`, derived from the *unverified* JSON body (`repository.owner.login` or `organization.login`). Once the signature check passes, the `create` action hands the very same raw JSON body to `Shipit::Webhooks::Handlers::PushHandler`, which instead resolves the target `Repository`/`Stack` using a *different* field of that same body: `repository.full_name`. Because GitHub itself always keeps these two fields consistent, this divergence is invisible in normal operation, but nothing in the code enforces that `repository.owner.login` and the owner segment of `repository.full_name` refer to the same organization.

### Finding Description
`verify_signature` computes: [1](#0-0) 
using `repository_owner`: [2](#0-1) 

This value selects which per-organization `github_app`/`webhook_secret` (in a multi-org `config/secrets.yml` setup, see `docs/setup.md` "Using Multiple Github Applications") is used to HMAC-verify the raw body via `verify_webhook_signature`: [3](#0-2) 

After signature verification succeeds, the same raw JSON is dispatched to handlers: [4](#0-3) 

`Handler#stacks`/`#repository_name` resolves the target repository using a *different* JSON key, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

`PushHandler#process` then triggers a sync against whatever `Stack` belongs to that resolved repository: [7](#0-6) 

The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository whose stack is acted upon**. Because the controller uses `repository.owner.login`/`organization.login` for authentication while the handler uses the independent `repository.full_name` string for authorization/target-selection, an attacker who controls a legitimate GitHub App installation on organization `A` (and therefore legitimately knows `A`'s `webhook_secret` — e.g., a Shipit admin of organization A, or anyone able to trigger/replay a webhook delivery from A) can craft a raw POST body where:
- `organization.login` / `repository.owner.login` = `A` (so the signature is validated against `A`'s known secret), and
- `repository.full_name` = `"victim-org/victim-repo"` (an unrelated organization/repo also configured on the same Shipit instance)

The HMAC only proves "the body was signed with A's secret" — it does not prove that the body's claims about the target repository are limited to `A`'s own repositories. `verify_signature` never checks that `repository.full_name`'s owner segment equals `repository_owner`.

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated == repository written," matching the class of finding requested (payload field acted on vs. field actually covered/matched by the verified credential). With a forged `push` event, the attacker triggers `stack.sync_github(expected_head_sha: params.after)` for a stack belonging to a *different* organization, causing `GithubSyncJob` to fetch and ingest commits up to an attacker-chosen `expected_head_sha` into the victim stack's commit history, which is used later to build deploy candidates. Depending on which handler is reached (`push`, `status`, `check_suite`, `pull_request`, `membership`), this could also let a webhook signed by org A's secret create Teams/Memberships, mutate commit status/check state, or drive PR-based provisioning for a stack that belongs to a repository under org B — i.e., a cross-organization/cross-repository state mutation that the per-org webhook secret was specifically meant to prevent. This is only meaningfully exploitable in the documented multi-organization configuration (`docs/setup.md`, "Using Multiple Github Applications"), where more than one org's webhook secret is configured on the same Shipit instance.

### Likelihood Explanation
Requires: (1) Shipit configured with more than one GitHub organization (each with independently known/derivable webhook secrets), and (2) the attacker controls or can obtain the webhook secret for at least one of those organizations (e.g., is an admin of one of the participating orgs, which is a materially lower bar than compromising the target/victim org). Single-org deployments (the common case, single top-level `github:` key) are not affected because there's only one secret to select from, though the code path is still logically unsound. Given the specific multi-tenant precondition, likelihood is Medium.

### Recommendation
After signature verification, re-derive `repository_owner`/the app used to look up secrets strictly from a value that is cross-checked against `repository.full_name`'s owner segment (or vice-versa), and reject the webhook (422) if they disagree. More robustly, verify the signature against every configured organization's secret that is consistent with the resolved repository (looked up via `repository.full_name`) rather than trusting an attacker-controlled field to pick which secret to check.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config) — the attacker legitimately administers `attacker-org`'s GitHub App and therefore knows its `webhook_secret`.
2. Attacker crafts a raw JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "organization": { "login": "attacker-org" },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s `webhook_secret` over the exact raw body, and sends `POST /webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"` (from `repository.owner.login`), loads `Shipit.github(organization: 'attacker-org')`, and the signature validates successfully.
5. `create` dispatches the payload to `PushHandler`, which resolves the target repo via `repository.full_name` → `"victim-org/victim-repo"`, finds that `Stack`, and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')`, mutating the victim org's stack state despite the request never having been authenticated by anything belonging to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
