### Title
Route-selected pool can execute arbitrary token transfers under the caller’s signed authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
Controller strategy routes can name arbitrary venue contract addresses. During `swap_collateral`, `repay_debt_with_collateral`, `swap_debt`, or `multiply`, the configured router invokes those addresses without checking that they are trusted pools. A malicious route contract can therefore perform a token `transfer` from the strategy caller to an attacker while inside the caller’s authorization context. Soroban records that transfer as a child of the caller’s authorization tree; if the caller signs the simulated tree, the transfer executes.

The controller’s exact-input authorization, balance-delta checks, positive-output check, and final risk checks do not bound this side effect because the stolen asset need not be part of the swap.

### Finding Description
`Controller::swap_tokens` calls only the configured router and correctly grants it one exact `token_in.transfer(controller, router, amount_in)` invocation. It then measures input spending and output receipt.

The loss occurs below that boundary. `execute::run` decodes caller-supplied route bytes and constructs each `SwapHop` directly from the payload’s `assets` registry. `idx_a` becomes `hop.pool`; there is no venue/pool allowlist or validation that the address is an instance of the selected DEX. `dispatch_hop` invokes the selected adapter, and adapters call `hop.pool` directly. For example, the Aquarius adapter invokes `pool.get_tokens` and then `pool.swap`, while the Soroswap adapter invokes `get_reserves` and `swap`.

Consequently, an attacker can supply a route whose `pool` is a malicious contract implementing the expected entrypoints. During that call, the malicious contract can call an unrelated token’s `transfer(victim, attacker, amount)`. Because this occurs below the victim’s top-level authorization for the controller strategy, simulation records the transfer as a child authorization. If the victim signs the resulting authorization tree, the token transfer succeeds even though the controller itself never authorized that asset movement.

The included regression test demonstrates the complete primitive through `swap_collateral`: `RogueHopPool::swap` calls `token.transfer(alice, attacker, WALLET_BALANCE)`, simulation places that transfer under Alice’s `swap_collateral` authorization, and enforcement succeeds only when Alice signs the poisoned tree. With an honest tree, the host rejects it.

### Impact Explanation
An unprivileged attacker can craft a valid-looking strategy route that steals arbitrary tokens from the caller’s wallet, including assets unrelated to the lending markets and assets never supplied to the protocol. The routed swap can still return sufficient output and leave the account solvent, so the controller’s measured output and final risk gates do not detect the theft.

This is theft of user funds. The amount is bounded by the token balances and signed child authorizations rather than by the strategy input amount.

### Likelihood Explanation
Exploitation requires the victim to submit a malicious route and sign the authorization tree produced by simulation. This is plausible when route bytes are opaque XDR generated off-chain: a wallet or integration that does not decode the route and inspect every child authorization can present the transaction as a normal strategy operation.

No privileged role, leaked key, compromised router, or invalid market configuration is required. The malicious venue address is supplied by the route payload itself.

### Recommendation
Restrict route execution to governance-approved or otherwise verified venue contracts for each `SwapVenue`. The router should maintain a pool allowlist/registry or validate pool identity against trusted factory/registry contracts before invoking `hop.pool`.

As defense in depth, reject route payloads containing unregistered venue addresses and expose a route-decoding/auth-tree inspection API so clients can reject any child authorization other than the expected input-token pull. Clients should refuse signatures whose authorization tree contains unrelated token transfers.

### Proof of Concept
1. Alice owns a funded lending account and also holds `WALLET_TOKEN`, which need not be listed by the protocol.
2. The attacker deploys `RogueHopPool` with a `swap` function that calls:
   `WALLET_TOKEN.transfer(alice, attacker, WALLET_BALANCE)`.
3. The attacker creates a `StrategyPayload` for `swap_collateral` from listed `USDC` to listed `ETH`, using the malicious contract as the Aquarius/Soroswap `pool` address and setting a fair `min_out`.
4. Alice submits `controller.swap_collateral(alice, account_id, usdc_key, amount, eth_key, route)`.
5. The controller authorizes only `USDC.transfer(controller, router, amount)` and calls the configured router.
6. The router decodes the payload, invokes the attacker-controlled pool, and the pool attempts `WALLET_TOKEN.transfer(alice, attacker, WALLET_BALANCE)`.
7. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization.
8. If Alice signs the poisoned tree, the malicious pool receives authorization and moves `WALLET_TOKEN` to the attacker. The swap can still return valid `ETH` output and pass controller checks.

The behavior is pinned by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, where `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` records the unauthorized-wallet-transfer child and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows that signing that child drains the wallet.
