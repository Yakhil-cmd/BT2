### Title
Webhook Signature Verification Trusts a Different Payload Field Than the One Used to Select the Repository/Stack Acted On - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments (`config/secrets.yml` with several `github.<org>` blocks), the webhook controller picks the HMAC secret to verify a request against the `repository.owner.login` field of the JSON body, while the event handlers later locate the `Repository`/`Stack` to mutate using the completely independent `repository.full_name` field of the *same, attacker-authored* body. This breaks the equality "organization whose secret authenticated the request" == "repository that is written to," letting an attacker who legitimately controls one organization's webhook secret forge events for a different organization's repository on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to fetch the verification secret from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` then looks up the per-organization `webhook_secret` from `secrets.github.<org>` and `GitHubApp#verify_webhook_signature` HMACs the raw body with that secret: [3](#0-2) [4](#0-3) 

Once the signature check passes, `params = JSON.parse(request.raw_post)` is dispatched unmodified to the registered handler(s): [5](#0-4) 

Every handler, however, resolves the target `Repository`/`Stack` from a *different* JSON field — `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

For example `PushHandler#process` uses `stacks` (built from `repository_name`) to trigger a git sync for arbitrary branches/stacks: [7](#0-6) 

Because the entire raw body is authored by the requester before it is signed, and the HMAC only proves "this body was produced by whoever holds the secret for the organization named in `repository.owner.login`," nothing ties `repository.full_name` to that same organization. An attacker who legitimately administers a GitHub App/organization configured in this Shipit instance (Organization A) knows Organization A's real `webhook_secret`. They can craft a JSON body where `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against Org A's secret) but `repository.full_name = "OrgB/victim-repo"` (a different organization's repository also tracked by the same Shipit instance), sign it with Org A's secret, and POST it to `/webhooks`. The signature check succeeds, and the handler acts on `OrgB/victim-repo` — a repository the attacker does not own — because handler-side repository resolution never re-checks it against the verified organization.

### Impact Explanation
This is a cross-repository/cross-organization write vulnerability. Depending on the event type dispatched, the attacker can:
- Force `PushHandler` to enqueue `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`, effectively driving that stack's git history state from outside the victim org.
- Forge `StatusHandler` events to inject fabricated commit statuses on a victim's commits (`commit.create_status_from_github!`), which can be used to make otherwise-blocked commits appear deployable, enabling an unauthorized deploy.
- Forge `check_suite`/`membership` events against organizations the attacker does not control.

This crosses a repository/authorization boundary the signature mechanism is explicitly designed to enforce, matching the "Critical: cross-repository writes / unauthorized deploy" category.

### Likelihood Explanation
Exploitation requires the attacker to legitimately control one organization's webhook secret within a multi-organization Shipit deployment (i.e., they administer their own GitHub App/org that is one of several orgs configured on a shared Shipit instance) — a realistic setup for shared/SaaS-style Shipit installations serving multiple GitHub organizations. No access to the victim organization, its repository, or Shipit session credentials is needed, satisfying the "unprivileged attacker" bar relative to the victim.

### Recommendation
After signature verification succeeds for organization `O`, re-validate that `repository.full_name`'s owner matches `O` (or, more robustly, iterate/derive the repository strictly from the same `repository.owner.login`/`organization.login` field that was used to select the verification secret) before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. `secrets.github.orga.webhook_secret = "secretA"` and `secrets.github.orgb.webhook_secret = "secretB"`, each with a `Repository`/`Stack` tracked (`orga/repoA`, `orgb/repoB`).
2. As the (legitimate) administrator of `orga`'s GitHub App, craft a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/repoB" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` using Org A's known `secretA`.
4. `POST /webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `WebhooksController#verify_signature` resolves `repository_owner => "orga"`, fetches `secretA`, and the signature validates.
6. `PushHandler#process` resolves `repository_name => "orgb/repoB"` and enqueues `GithubSyncJob` for Org B's stack — a stack the attacker (an Org A admin only) has no legitimate access to — confirming the cross-organization write.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
