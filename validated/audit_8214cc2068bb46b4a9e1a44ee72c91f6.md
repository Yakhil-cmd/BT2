### Title
Webhook Signature Verified Against `repository.owner.login`, But Handlers Act On Unverified `repository.full_name` — Cross-Organization Stack Manipulation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate against using one payload field (`repository.owner.login` / `organization.login`), while every webhook `Handler` subclass resolves the actual `Stack`/`Repository` to mutate using a *different* payload field (`repository.full_name`). Both fields live in the same attacker-authored JSON body. In a multi-organization Shipit deployment, an attacker who legitimately controls one onboarded organization can craft a webhook whose `repository.owner.login` matches their own org (so it verifies against their own known secret) while `repository.full_name` points at a Stack belonging to an entirely different organization, causing the handler to act on a repository the attacker never authenticated for.

### Finding Description
The signature check is: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` picks a per-organization `webhook_secret` from config when Shipit is set up for multiple GitHub organizations, as documented and supported: [2](#0-1)  and [3](#0-2) .

Once the signature is deemed valid for whatever organization `repository_owner` claims, the request is dispatched to handlers: [4](#0-3) 

Every handler resolves its target `Stack` via a completely different field: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

For example `PushHandler` uses this to trigger a sync against arbitrary matching stacks: [6](#0-5) .

Nothing ties `repository_owner` (used to choose the secret) to `repository.full_name` (used to choose the acted-upon repository). GitHub itself always keeps these two fields consistent on genuine deliveries, but here the attacker is the author of the raw JSON body being signed — the invariant "the organization whose secret validated this signature owns the repository the handler will mutate" is never checked, exactly analogous to the reported LPMath issue where a derived value was used without re-validating it against the invariant that produced it.

### Impact Explanation
This breaks the binding: *organization authenticated (`repository_owner` → secret used to verify) ≠ repository actually written (`repository.full_name` → `Stack` mutated by the handler)*.

Concretely, an attacker who legitimately operates one organization onboarded to a shared/multi-tenant Shipit instance (a supported, documented configuration) can:
- Forge a `status` webhook with `repository.owner.login` = their own org but `repository.full_name` = a victim organization's tracked repository, injecting a fabricated "success" CI status onto an arbitrary commit of a repo they don't control.
- This can flip `Commit#deployable?` for that commit, bypassing `require_ci` safety checks and unblocking deploys, or feed a continuous-deployment pipeline into shipping an attacker-chosen commit — an **unauthorized deploy**, one of the explicitly listed Critical impacts.
- Other handlers (`push`, `check_suite`, `pull_request`) using the same `Handler#stacks`/`repository_name` mechanism are equally reachable, allowing cross-repository state mutation (sync triggers, check-run refreshes, merge-queue manipulation) against stacks outside the attacker's own organization.

### Likelihood Explanation
Exploitability requires only that Shipit be configured with more than one GitHub organization (a normal, documented multi-tenant setup) and that the attacker controls (or has legitimately been granted) one such organization with a known `webhook_secret` — no privileged Shipit account, `ApiClient` token, or GitHub App private key for the *victim* org is needed. The attacker only needs to POST directly to `/webhooks` with a self-crafted payload and a correctly computed HMAC using their own org's secret; GitHub delivery infrastructure is not required. This is a straightforward, repeatable HTTP-level forgery.

### Recommendation
In `WebhooksController#verify_signature`, after establishing which organization's secret verified the signature, cross-check that this organization is consistent with the repository the handler will act on (e.g., require `repository.full_name.split('/').first.casecmp?(repository_owner)`, or resolve the `Repository`/`Stack` before dispatch and assert its owning organization matches `repository_owner`). Reject the request (422) if the two disagree, mirroring the report's recommendation to re-validate the invariant after using a derived value rather than trusting it implicitly.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `attacker-org` and `victim-org`, each with its own `github.webhook_secret` (per `config/secrets.development.example.yml` multi-org schema).
2. Attacker (who administers `attacker-org` and therefore knows `attacker-org`'s `webhook_secret`) builds a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/build",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s secret, and the signature validates successfully (per `app/controllers/shipit/webhooks_controller.rb#L24-49`).
5. `Shipit::Webhooks.for_event('status')` dispatches to the status handler, which resolves the target repository via `payload.dig('repository','full_name') == "victim-org/victim-repo"` (per `app/models/shipit/webhooks/handlers/handler.rb#L30-38`), and writes a forged commit status onto `victim-org/victim-repo`'s commit despite the attacker never authenticating for `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
    end

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
