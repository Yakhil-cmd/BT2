This confirms the contrast: `CheckSuiteHandler.process` correctly scopes writes through `stacks.where(branch: ...)` (i.e. `Repository.from_github_repo_name(repository_name).stacks`, from `Handler#stacks`) before touching any commit, but `StatusHandler.process` does not use `stacks`/`repository_name` at all — it queries `Commit.where(sha: params.sha)` globally, across every stack/repository tracked by the Shipit instance.

### Title
Cross-repository commit-status writes via unscoped `StatusHandler` webhook processing - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check based on `repository.owner.login` in the payload [1](#0-0) , then dispatches to `Shipit::Webhooks::Handlers::StatusHandler`. Unlike every other repository-scoped handler (e.g. `CheckSuiteHandler`, the `PullRequest::*` handlers), `StatusHandler#process` never consults `repository_name`/`stacks` — it looks up commits purely `Commit.where(sha: params.sha)` and writes a status to every matching row, regardless of which repository/stack owns it. [2](#0-1) 

### Finding Description
The binding that should hold is: `organization verified by X-Hub-Signature (payload.repository.owner.login)` == `repository/stack whose Commit rows are mutated`. `Handler` provides `stacks`/`repository_name` helpers precisely to enforce this equality [3](#0-2) , and `CheckSuiteHandler` uses them correctly (`stacks.where(branch: ...)` before touching commits) [4](#0-3) .

`StatusHandler`, however, breaks this binding: it only validates `sha`/`state` shape via `ExplicitParameters`, and its `process` method writes to any `Commit` in the database whose `sha` matches — with no `repository`/`stacks` filter at all [5](#0-4) . The webhook signature verification only proves that the request came from *an* organization whose secret was known and matched the payload's declared owner — it says nothing about which repository's commits should be touched. Because `Commit.sha` is not globally unique across stacks (identical commits — e.g. via forks, shared history, or an attacker cherry-picking/pushing a victim's commit into their own controlled repository, which Shipit will then sync via `GithubSyncJob` into a `Commit` row for the attacker's own stack) an attacker who controls any repository configured in the same Shipit instance can trigger a validly-signed `status` webhook (via GitHub's real status API on their own repo, using a sha that also exists as a `Commit` row belonging to a victim stack) and thereby write a commit status (`success`/`failure`/etc, `context`, `target_url`, `description`) onto the victim stack's commit.

### Impact Explanation
Commit status directly feeds `Commit#blocking?` / `deployable?` and `ci.require` gating logic used by continuous deployment (`Commit#deployable?`, `blocked?`) [6](#0-5) . A forged `success` status injected cross-repository can satisfy a victim stack's required CI contexts and unblock/trigger an unauthorized deploy via continuous delivery, or conversely a forged `failure`/`error` status can block a victim's legitimate deploys (denial of a deploy gate) — this is a cross-repository write into another stack's authorization state, matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
This requires: (1) a multi-repository/multi-org Shipit deployment (documented and directly supported, see `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.example.yml` multi-org schema) [7](#0-6) , (2) attacker control of at least one repository/stack tracked by that Shipit instance (already an unprivileged-but-onboarded participant, not requiring any Shipit credentials), and (3) a commit-sha collision between the attacker's repository and the victim's, which is straightforward to engineer by pushing/cherry-picking the victim's exact commit (same tree/parents/author/committer timestamps yields identical SHA) into a repository the attacker controls, causing Shipit's own sync job to create the colliding `Commit` row. No `ApiClient` token, webhook secret, or GitHub App key is needed by the attacker.

### Recommendation
Scope `StatusHandler#process` (and any other handler operating on `Commit.where(sha: ...)`) through `stacks`/`repository_name`, mirroring `CheckSuiteHandler`, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, so a status update can only ever be applied to commits belonging to the repository asserted (and cryptographically bound via signature) in the same webhook payload.

### Proof of Concept
1. Attacker owns `attacker/repo`, installed on the same Shipit instance (multi-org config) as victim's `victim/repo` (stack tracked by Shipit).
2. Attacker pushes/cherry-picks victim's exact commit `abc123...` into `attacker/repo`; Shipit's `GithubSyncJob` (triggered by the attacker's own legitimate, properly-signed `push` webhook) creates a `Commit` row for `abc123` scoped to the attacker's stack.
3. Attacker calls GitHub's real Statuses API on `attacker/repo` for sha `abc123` with `state: success`, `context: <victim's required CI context>`. GitHub delivers a `status` webhook, correctly signed with the attacker's own org's `webhook_secret`.
4. `WebhooksController#verify_signature` passes (attacker's own valid signature for attacker's own org) [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123')` — this returns **both** the attacker's commit row and the victim's commit row (same sha) — and calls `create_status_from_github!` on both, injecting the forged `success` status onto the victim's commit/stack [2](#0-1) .
6. If `victim/repo`'s stack has continuous delivery enabled and requires that CI context, the forged status can trigger/unblock an unauthorized deploy.
