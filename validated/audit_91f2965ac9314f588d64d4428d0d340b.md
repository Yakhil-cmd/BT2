### Title
Cross-organization webhook forgery via mismatched signing-key field and repository-target field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC verification key using `repository_owner`, which reads `params.dig('repository','owner','login')` from the attacker-controlled JSON body, while `Handler#repository_name` (used by `PushHandler#process` to resolve the target `Stack`) reads a different field, `payload.dig('repository','full_name')`. Because both fields are attacker-supplied and independent, an attacker who owns `attacker-org` (and therefore knows its real `webhook_secret`) can sign a payload whose `owner.login` is `attacker-org` but whose `full_name` is `victim-org/victim-repo`, passing signature verification while mutating a stack that belongs to `victim-org`.

### Finding Description
Broken binding: the organization whose `webhook_secret` verified the raw bytes (`repository_owner` = `params.dig('repository','owner','login')`) must equal the organization owning the repository/stack that the handler acts on (`repository_name` = `payload.dig('repository','full_name')`'s owner segment). This does not hold.

Code path:
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (line 61) and uses it to fetch `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against `request.raw_post` using that org's `webhook_secret` (`GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`).
- On success, `create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the same raw body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, e.g. `PushHandler`.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves target stacks via `stacks`, which calls `Repository.from_github_repo_name(repository_name)` where `repository_name` is `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), reading `payload.dig('repository', 'full_name')` — a completely different JSON field from the one used for signature-key selection.
- Nothing ties these two fields together: no code checks that `full_name`'s owner segment matches `owner.login`. An attacker who owns `attacker-org` and knows its real webhook secret can post a body where `repository.owner.login = "attacker-org"` (used only to pick the verification key) and `repository.full_name = "victim-org/victim-repo"` (used to pick the target stack), signed correctly for `attacker-org`.
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on `victim-org`'s real stack for `master`, an attacker-chosen SHA that must exist as a real commit on GitHub (since `sync_github` fetches/validates against GitHub), but the trigger itself is fully forged.
- Existing guards do not stop this: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` schema for `PushHandler` only requires `ref`/`after` are present syntactically, not that they're consistent with the signing organization; `verify_signature`'s `rescue Shipit::GithubOrganizationUnknown` only handles unknown orgs, not mismatched orgs.

### Impact Explanation
An attacker who controls only their own GitHub organization/webhook can force an authenticated-looking sync trigger (`stack.sync_github`) on any other tenant's `Stack` whose `branch` matches, without possessing that tenant's `webhook_secret`, GitHub App credentials, or any Shipit session/API token. This is a cross-repository/cross-tenant authentication bypass: the party who cryptographically "authenticated" the request (`attacker-org`) is not the party whose resource is mutated (`victim-org`). Repeatable against any known victim `full_name`/branch combination for every push-type event handler that relies on `Handler#repository_name` for target resolution (PushHandler and any others sharing this pattern), matching the Critical category ("a payload for one repository mutating another's stack").

### Likelihood Explanation
Preconditions: multi-tenant Shipit deployment where `Shipit.github(organization:)` is configured per-organization with distinct `webhook_secret`s, and the attacker owns/controls at least one such configured organization (a low bar — any onboarded org/team). Attacker cost is trivial: compute an HMAC-SHA1 over an arbitrary JSON body using their own known secret and POST it to `/webhooks` with `X-Github-Event: push`. No interaction with GitHub's real webhook delivery is required since the body and signature are attacker-crafted directly against the Shipit endpoint. Fully repeatable and scriptable against any victim repository name known to the attacker.

### Recommendation
Bind signature-key selection and target resolution to the same field. Either: (1) verify the signature against the organization derived from `repository.full_name` (the same field `Handler#repository_name` uses) instead of `repository.owner.login`, or (2) after successful verification, additionally assert that `repository.full_name`'s owner segment equals `repository_owner` before dispatching to handlers, rejecting (422) on mismatch.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (conceptual, no live GitHub):
1. Configure two orgs in `Shipit.github` test config: `attacker-org` with `webhook_secret: "attacker-secret"`, and `victim-org` with `webhook_secret: "victim-secret"`.
2. Create a real `Stack` for `victim-org/victim-repo` on branch `master`, `stack.sha = "old_sha"`.
3. Build body: `{"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"ref":"refs/heads/master","after":"new_sha"}`.
4. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', "attacker-secret", body)`.
5. POST to `/webhooks` with `X-Github-Event: push` and that signature header.
6. Assert response is `:ok` (verification passed using `attacker-org`'s secret) — `repository_owner == "attacker-org"` on the verification side.
7. Assert `stack.reload.sha` (or that `sync_github` was invoked with `expected_head_sha: "new_sha"`) changed for the `victim-org/victim-repo` stack — `repository_name.split('/').first == "victim-org"` on the mutation side — demonstrating the two sides of the equality diverge while the request still succeeds.
