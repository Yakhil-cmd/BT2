This report describes a classic Solidity gas-exhaustion-via-unbounded-loop pattern (iterating over pool tokens in `getPriceInEth`). This exact bug class is explicitly excluded by the scan methodology, which instructs to reject "unbounded-loop or memory/storage-growth scenarios, oversized-input/flooding/generic resource-exhaustion claims and gas-only optimization" findings.

Additionally, Polkadot SDK's FRAME architecture does not have an EVM-style block gas limit failure mode analogous to this report. Instead, FRAME uses a weight-metering system where dispatchables must declare/benchmark their worst-case weight, and pallets that iterate over user-influenced collections use linear-component benchmarks with explicit bounds (e.g., `pallet_asset_conversion`'s `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` benchmarked over path length bounded by `T::MaxSwapPathLength`), and the benchmarking framework's own documentation flags unbounded loops as a red flag requiring "sane boundaries" enforcement at design time rather than as a runtime attack surface.
