### Title
Webhook signature verified against `repository.owner.login` while handlers act on the unrelated, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks *which* org's HMAC secret to validate a webhook against using one field of the attacker-supplied JSON body (`repository.owner.login`, or `organization.login` as fallback), but every `Handlers::Handler` subclass resolves the `Stack`/`Repository` to actually mutate using a completely different field of that same unverified body (`repository.full_name`). Nothing forces these two fields to agree, so a valid signature for organization A authorizes writes against a repository belonging to organization B.

### Finding Description
`verify_signature` computes the signing organization purely from the payload, before any cryptographic check has taken place: [1](#0-0) [2](#0-1) 

It fetches `Shipit.github(organization: repository_owner)` and checks the request's `X-Hub-Signature` against that organization's `webhook_secret` via `verify_webhook_signature`. This only proves the request was signed by *some* org that is configured in Shipit and whose secret matches `repository.owner.login`/`organization.login` — it says nothing about which repository the rest of the payload will be applied to.

Every handler, however, resolves the target `Stack` from an entirely different field of the same JSON body: [3](#0-2) 

`repository_name` comes from `payload.dig('repository', 'full_name')`, and `stacks` looks up `Repository.from_github_repo_name(repository_name)`. `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack: [4](#0-3) 

The binding that should hold is: `organization that authenticated the signature (repository.owner.login) == organization that owns the repository being written to (owner portion of repository.full_name)`. Nothing in the controller or in `Handler` enforces this equality — an attacker who is an admin/owner of *any* single GitHub organization configured on this Shipit instance (and therefore legitimately knows that org's `webhook_secret`, which every org-admin necessarily has access to when wiring up the GitHub App) can:

1. Craft a raw JSON body where `repository.owner.login` (or `organization.login`) is set to their own org, `attacker-org`.
2. Sign the raw body with `attacker-org`'s `webhook_secret` using GitHub's standard `sha1=` HMAC scheme — this passes `verify_signature` because `Shipit.github(organization: 'attacker-org')` resolves to the secret the attacker already knows.
3. Set `repository.full_name` (and other fields such as `ref`, `after`, PR fields, `sha`/`state` for the `status` event, etc.) to point at `victim-org/victim-repo`, a repository tracked by a completely unrelated Shipit-managed org.
4. POST this to `/github/webhooks` (or wherever `WebhooksController` is mounted).

Since `repository_name` is taken from `full_name`, not from the signature-checked `repository_owner`, the request is routed to `victim-org/victim-repo`'s `Stack` and processed as if GitHub itself had sent it for that repository.

### Impact Explanation
This crosses a cross-repository write boundary without any credential for the victim repository: an attacker with legitimate access to only one Shipit-tracked organization's webhook secret can inject fabricated GitHub events for any other organization's repositories tracked by the same Shipit instance. Depending on which event/handler is targeted this enables, among others:
- Forged `push` events causing `Stack#sync_github` to run against arbitrary victim stacks with an attacker-chosen `after` SHA [4](#0-3) .
- Forged `pull_request`, `status`, `check_suite`, and `membership` events processed by the corresponding handlers, which mutate `MergeRequest`, `Commit`/`CommitStatus`, and `Team`/`Membership` records for the victim repository, since they all resolve their target via the same unverified `repository.full_name` (or team data) rather than the signature-checked organization.

Forged commit-status/check-suite events in particular can flip a victim commit's deployability state, which is the gate the UI/API relies on before allowing a deploy — i.e., this can be used to help push an unauthorized deploy on a repository the attacker does not control and for which they hold no GitHub credentials, satisfying the "unauthorized deploy" impact bar in scope.

### Likelihood Explanation
The precondition is that the attacker administers (or has been granted webhook configuration for) at least one GitHub organization that is configured in this Shipit instance's `Shipit.github` settings — a low bar in any multi-tenant/self-serve Shipit deployment where several unrelated orgs are onboarded, and explicitly the scenario `secrets.*.yml` supports (`somegithuborg`, `someothergithuborg`, ...) [5](#0-4) . No GitHub App private key, `ApiClient` token, or Shipit session is required — only knowledge of one org's own `webhook_secret`, which is not one of the excluded-by-rule credentials (those are `webhook_secret`/`api_clients_secret` *of the target*, not of an org the attacker legitimately administers).

### Recommendation
In `WebhooksController#verify_signature`, after verifying the HMAC, cross-check that the field used to select the signing secret (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` (and any other org-identifying field the handler will later use) before dispatching to handlers. Equivalently, have `Handlers::Handler#repository_name` re-derive the repository owner exclusively from the same value that was cryptographically verified, rejecting payloads where they diverge.

### Proof of Concept
1. Attacker is an owner of GitHub org `attacker-org`, which is configured in this Shipit instance with a known `webhook_secret` (`S`).
2. Attacker crafts:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC(S, raw_body)` and sends:
```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<computed>
<raw_body>
```
4. `verify_signature` resolves `repository_owner` = `"attacker-org"` from `repository.owner.login`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature with the attacker's own known secret — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
5. `PushHandler` (invoked via `Shipit::Webhooks.for_event('push')`) resolves the target repository via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` — see `app/models/shipit/webhooks/handlers/handler.rb:30-38` — and runs `stack.sync_github(expected_head_sha: "deadbeef...")` on every matching stack for `victim-org/victim-repo`, even though the attacker has no credentials for `victim-org` at all.
