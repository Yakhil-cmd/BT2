### Title
Membership webhook trusts `params.team.id`/`params.organization.login` without binding to the signing organization, allowing cross-org team hijack - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only authenticates the raw request bytes against the webhook secret associated with `repository_owner` (attacker-controlled `repository.owner.login`/`organization.login` fallback), and does not bind that verified organization to the semantic content of nested `team`/`organization`/`member` objects. `MembershipHandler#find_or_create_team!` then looks up or mutates a `Team` solely by the attacker-supplied `team.id` (`github_id`), with no check that the requesting/signing organization actually owns that team, letting an attacker who controls a legitimately-registered GitHub organization add an arbitrary user to another organization's `Team` record.

### Finding Description
The broken binding: `verify_signature`'s org == `params.dig('team')/params.dig('organization')`'s claimed org should be equal, but nothing enforces `Shipit.github(organization: repository_owner)`'s secret owner == `params.organization.login` == the organization of the `Team` located by `params.team.id`.

Path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-49) derives the signing key from `repository_owner`, which reads `params.dig('repository','owner','login') || params.dig('organization','login')` — both attacker-controlled JSON fields [1](#0-0) [2](#0-1) .
- Once the byte signature validates against whatever secret corresponds to the attacker's own organization, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, whose `ExplicitParameters` schema only enforces types/presence (`String`, `Integer`), not cross-field consistency [3](#0-2) .
- `find_or_create_team!` resolves the `Team` purely by `github_id: params.team.id`, and if a `Team` already exists with that `github_id` (e.g., belonging to a victim organization), it is returned as-is — the `organization` field is only set inside the `find_or_create_by!` block, which does not run for an existing record [4](#0-3) .
- `process` then calls `team.add_member(member)` where `member` is `User.find_or_create_by_login!(params.member.login)`, an attacker-chosen login [5](#0-4) .
- The `teams` table has no uniqueness constraint on `github_id` alone (only a composite unique index on `organization, slug`) [6](#0-5) , so nothing at the DB layer prevents this cross-organization github_id collision from resolving to the wrong `Team` row.
- `Team.members`/`Membership` has no organization scoping check either [7](#0-6) .

Attacker's exact request: attacker owns/administers a real (even trivial) GitHub organization `attacker-org` with a Shipit webhook configured, giving them the legitimate `X-Hub-Signature` for that secret. They send `X-Github-Event: membership` with body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "attacker-org"}},
  "organization": {"login": "attacker-org"},
  "team": {"id": <victim_team_github_id>, "name": "x", "slug": "x", "url": "https://example.com"},
  "member": {"login": "attacker-controlled-login"}
}
```
signed with `attacker-org`'s known webhook secret. `verify_signature` passes because it only checks the byte signature against `attacker-org`'s secret — it never checks that `victim_team_github_id` belongs to `attacker-org`. `MembershipHandler#process` then adds the attacker-controlled user as a member of the victim's `Team` row.

Why existing guards fail: `drop_unhandled_event` only checks event routing exists; `verify_signature` authenticates provenance of the request bytes for whichever org is named in the payload, not the semantic ownership of nested IDs; `ExplicitParameters` only validates types/presence; no model validation ties `Team#organization` to the requesting org on lookup.

### Impact Explanation
If the victim `Team` is one of the teams listed in `Shipit.github_teams` (the teams whose membership gates access via `User#authorized?` [8](#0-7)  and `force_github_authentication` [9](#0-8) ), an attacker can add an arbitrary GitHub login as a member of that authorization-gating team, granting that account authenticated access to the entire Shipit instance (stacks, deploys, tasks) without ever being a real member of the victim org. This matches the listed High-severity category: "escalation into `Shipit.github_teams` authorization." It is repeatable against any `Team.github_id` the attacker can learn or guess, and is not limited to one repository — it affects the shared, cross-tenant `teams`/`memberships` tables.

### Likelihood Explanation
Preconditions: the attacker needs (a) control of a legitimate GitHub organization with a Shipit webhook configured (achievable by any GitHub user — creating an org and installing a webhook requires no special privilege over the target Shipit instance or victim org), and (b) knowledge of the victim `Team`'s `github_id` (GitHub team IDs are numeric and can be discovered via GitHub's public API for teams visible to org members, or through reconnaissance/prior interaction with Shipit if the team was ever exposed e.g., in UI/API responses). No Shipit secrets, sessions, or API tokens are required — only the attacker's own webhook secret, which they legitimately possess. This is a repeatable, low-cost attack once the target `github_id` is known.

### Recommendation
In `find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that `params.organization.login` matches `repository_owner`/the organization whose secret validated the signature before performing any team membership mutation. Consider passing the verified `repository_owner` into the handler explicitly rather than trusting a duplicate, attacker-controlled `organization.login` field in the body.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership cannot hijack a team belonging to a different organization" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1
  attacker_org = 'cyclimse' # attacker's own org, whose webhook secret they legitimately know

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate valid signature for attacker_org

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    repository: { owner: { login: attacker_org } },
    organization: { login: attacker_org },
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'https://example.com' },
    member: { login: 'attacker-controlled-login' }
  }.to_json

  assert_no_difference -> { victim_team.members.count } do
    post :create, body:, as: :json
  end
  # FAILS on current code: attacker-controlled-login is added to shopify_developers
  # even though the request was signed for `cyclimse`, not `shopify`.
end
```
This demonstrates that `MembershipHandler#find_or_create_team!` resolves an existing `Team` purely by `github_id`, independent of which organization's signature validated the request, confirming the broken binding between signer identity and mutated record ownership.
