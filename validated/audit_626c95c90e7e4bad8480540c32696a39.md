### Title
Stale per-block index cache lets zToken collateral be over-valued after a same-block `socialize-debt` write-down - ([File: local-testing/contracts/market/market.clar])

### Summary
`market.clar` caches vault `index`/`lindex` values per `(timestamp, aid)` for the duration of a block to save cross-contract calls. Liquidation-triggered `socialize-debt` writes down a vault's `lindex` directly in the vault contract without invalidating or refreshing this cache. Any other transaction later in the same block that prices zToken collateral for a different user reads the stale, pre-socialization (too high) `lindex` from the cache, over-valuing that user's collateral and allowing them to pass health checks (and borrow) against collateral that is actually worth less. The resulting under-collateralized debt is ultimately absorbed by the debt-asset vault's other suppliers.

### Finding Description
The market maintains a shared, block-scoped cache:
```
(define-map index-cache { timestamp: uint, aid: uint } { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)               ;; cache HIT: stale value reused
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [1](#0-0) 

This cache is primed the first time any user's transaction in a block touches a given asset (`collateral-add`, `borrow`, `repay`, `liquidate`), via `accrue-user-collateral`/`accrue-user-debts`, which resolve zToken collateral through the underlying vault's `index`/`lindex`: [2](#0-1) [3](#0-2) 

Separately, when a liquidation leaves bad debt, `liquidate` calls into the vault's `socialize-debt`, which directly mutates the vault's `lindex` data-var (writing it down proportionally to the loss) without ever going through or refreshing the market's `index-cache`:
```
(var-set lindex new-lindex)
(var-set principal-scaled ...)
(var-set total-borrowed ...)
(var-set assets ...)
``` [4](#0-3) 

The liquidation path that triggers this write-down is: [5](#0-4) 

Because `stacks-block-time` is constant for every transaction within the same block, once the market has cached `{index, lindex}` for an asset in that block (e.g., primed by an earlier borrow/collateral-add), any subsequent transaction (from a different user) in that same block that needs the price of that vault's zToken hits the cache and receives the pre-socialization `lindex`, even if a liquidation with `socialize-debt` has already reduced the vault's real `lindex` earlier in the same block. There is no cache invalidation tied to `socialize-debt`.

### Impact Explanation
An attacker (or any ordinary user, even unintentionally) who supplies the affected zToken as collateral and borrows later in the same block as a `socialize-debt` event will have their collateral valued using the stale, higher `lindex`, i.e. their zToken is worth more on paper than the vault's real exchange rate now supports. This lets them pass the health check and borrow more than their collateral truly backs. Because the true collateral value is lower, the position is effectively already under-collateralized at origination; any subsequent shortfall becomes new bad debt that must eventually be socialized again — this time onto the honest suppliers of the debt-asset vault, who bear a loss they would not have borne had the correct, up-to-date `lindex` been used. This is a shared-cache-primed-by-one-caller-consumed-by-another/ordering-dependence issue between two distinct principals (the borrower exploiting the stale cache, and the vault's other suppliers who absorb the resulting bad debt), landing in the "temporary freezing of funds" / socialized-loss impact category tied to the vault suppliers' capital.

### Likelihood Explanation
This requires (a) a liquidation that produces bad debt and triggers `socialize-debt` for a given vault, and (b) a second transaction in the same block that prices zToken collateral of that same vault for borrowing/health-check purposes. On a fast/high-throughput chain, multiple transactions landing in the same block (same `stacks-block-time`) is common, and an attacker can deliberately submit a borrow transaction to land in the same block right after observing a liquidation candidate, making this practically triggerable rather than purely theoretical.

### Recommendation
Invalidate or refresh the market's `index-cache` entry for an asset whenever `socialize-debt` is invoked against that asset's vault within the same transaction/block, or have `socialize-debt` return the updated `{index, lindex}` and have the market immediately `map-set` the cache with the fresh values before continuing. Alternatively, remove reliance on the timestamp-only cache key for zToken valuation and force a fresh `vault-accrue` call whenever a `socialize-debt` event has occurred in the current block.

### Proof of Concept
1. User A supplies zUSDC as collateral and holds an open position.
2. In the same block, a liquidation on some other borrower triggers `vault-usdc socialize-debt`, reducing `lindex` for the USDC vault from `L_old` to `L_new < L_old`. The market's `index-cache` for `(timestamp, USDC)` still holds `L_old` from an earlier accrual in that block (or has not yet been invalidated).
3. Later in the same block, User A calls `borrow`, which calls `accrue-user-collateral` → `accrue-and-cache(USDC)`. Because the cache key `(stacks-block-time, USDC)` was already set (or gets set by an accrual step that doesn't reflect the vault's post-socialization state), User A's zUSDC collateral is valued using `L_old` instead of `L_new`.
4. `is-healthy` / `is-healthy-with-mask` pass based on the inflated collateral value, and User A borrows an amount that is not actually backed once the correct `L_new` is used.
5. The gap becomes bad debt in the borrowed asset's vault, which will later need to be socialized onto that vault's other suppliers via [5](#0-4) , causing them a loss they would not have incurred under correct pricing.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
