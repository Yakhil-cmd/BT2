### Title
Silent `PostInsertBlock` Error Swallowing in Proposer Path Causes Persistent Validator-Set / Governance State Inconsistency — (`work/worker.go`)

---

### Summary

In `work/worker.go`, the `handleFinalizedBlock` function silently discards every error returned by `module.PostInsertBlock`. Because the block has already been committed to the database before this loop runs, a failure inside any execution module leaves the canonical chain and the module's persistent state permanently out of sync. The identical loop in `blockchain/blockchain.go` (`insertChain`) correctly propagates the error and aborts insertion. The asymmetry means the bug is exclusive to the locally-mined-block path.

---

### Finding Description

**Vulnerable site — `work/worker.go` lines 553–558:**

```go
// Invoke ExecutionModules after executing a block
for _, module := range self.executionModules {
    if err := module.PostInsertBlock(block); err != nil {
        logger.Error("Failed to call PostInsertBlock", "err", err)
        // error is dropped; loop continues
    }
}
``` [1](#0-0) 

**Correct handling in the sync path — `blockchain/blockchain.go` lines 2210–2214:**

```go
for _, module := range bc.executionModules {
    if err := module.PostInsertBlock(block); err != nil {
        return i, events, coalescedLogs, err   // error propagated
    }
}
``` [2](#0-1) 

By the time the loop in `handleFinalizedBlock` executes, `WriteBlockWithState` has already committed the block to the database:

```go
writeResult, err := self.chain.WriteBlockWithState(block, work.receipts, work.state)
``` [3](#0-2) 

Any subsequent `PostInsertBlock` failure is therefore unrecoverable: the block is canonical, but the module's persistent state was never updated.

**Affected modules and their protected state:**

| Module | `PostInsertBlock` action | Failure mode |
|---|---|---|
| `ValsetModule` | Writes updated validator council to DB; in permissionless mode, caches `TransitionResult` from state | `Chain.StateAt(header.Root)` fails (missing trie node / pruned state); `getTransitionResult` fails reading system contract |
| `headerGovModule` | Persists governance vote and governance-data block numbers to DB | `ToVoteData` / `ToGovData` parse error; DB write error |
| `StakingModule` | Persists staking info for the new block | `GetStakingInfo` DB/state error |
| `GaslessModule` | Updates in-memory allowed-token set from state | `Chain.StateAt` fails | [4](#0-3) [5](#0-4) [6](#0-5) 

The `ValsetModule.postInsertBlockPermissionless` path is the most reachable failure point: it calls `v.Chain.StateAt(header.Root)` on the just-committed block's root. If the state is unavailable (e.g., archive pruning, transient I/O error), it returns an error that is silently dropped. [7](#0-6) 

---

### Impact Explanation

**Validator-set corruption (consensus divergence):** After a silent failure in `ValsetModule.PostInsertBlock`, the proposer node's council DB is not updated. All subsequent calls to `GetCouncil`, `GetQualifiedValidators`, and `GetCommittee` return the stale pre-block council. The node then selects committee members and a proposer for the next block from the wrong set. Blocks produced with an incorrect committee are rejected by honest peers, causing the proposer to diverge from the canonical chain.

**Governance-parameter corruption:** A silent failure in `headerGovModule.PostInsertBlock` means a ratified governance vote (e.g., a `unitPrice` or `minimumStake` change) is never recorded in the in-memory `groupedVotes` map or the DB. The node applies stale parameters for all subsequent blocks, diverging from the network's view of the parameter set.

**Reward-distribution corruption:** A silent failure in `StakingModule.PostInsertBlock` leaves staking info un-persisted. `RewardModule.FinalizeState` reads staking info to compute per-validator rewards; stale info causes incorrect KAIA minting and distribution.

All three impacts fall within the allowed scope: consensus divergence on honest nodes, and incorrect reward distribution affecting KAIA balances.

---

### Likelihood Explanation

The trigger is any transient or persistent error inside a `PostInsertBlock` implementation on the proposer node. The most reachable path is `ValsetModule.postInsertBlockPermissionless` calling `Chain.StateAt(header.Root)` immediately after the block is written. Under aggressive state pruning, a race between the pruner and this call can return `"missing trie node"`. This is a known operational condition on archive-less nodes and does not require attacker action. The bug is latent on every proposer node running with state pruning enabled after the Permissionless fork.

---

### Recommendation

Mirror the error-handling pattern used in `blockchain/blockchain.go`. If a `PostInsertBlock` call fails in `handleFinalizedBlock`, the node must not silently continue. Options:

1. **Propagate and halt block announcement** — return the error from `handleFinalizedBlock` and prevent `PostChainEvents` from firing, forcing the node to re-sync the block through `insertChain` (which handles errors correctly).
2. **Retry with backoff** — retry the failed module call before giving up, then halt if retries are exhausted.
3. **Panic / `logger.Crit`** — treat a `PostInsertBlock` failure as a fatal node error, consistent with how other state-corruption conditions are handled elsewhere in the codebase.

```go
// Proposed fix in work/worker.go
for _, module := range self.executionModules {
    if err := module.PostInsertBlock(block); err != nil {
        logger.Crit("PostInsertBlock failed; node state is inconsistent", "module", module, "err", err)
    }
}
```

### Proof of Concept

1. Run a Kaia node with state pruning enabled, past the Permissionless fork block.
2. Configure the node as a proposer (validator).
3. Inject a transient I/O error on the state DB (e.g., via `LD_PRELOAD` fault injection or by temporarily making the state directory read-only) timed to coincide with the `Chain.StateAt` call inside `ValsetModule.postInsertBlockPermissionless`.
4. Observe that `handleFinalizedBlock` logs `"Failed to call PostInsertBlock"` but continues normally.
5. Inspect the council DB: the council entry for the mined block is absent.
6. Observe that the node's next block proposal uses the stale council, producing a block whose `IstanbulExtra.Validators` field does not match the state-derived qualified set, causing peer rejection and consensus divergence.

func (v *ValsetModule) postInsertBlockPermissionless(block *types.Block) error {
	header := block.Header()
	nextNum := header.Number.Uint64() + 1
	parentStatedb, err := v.Chain.StateAt(header.Root)
	if err != nil {
		return err
	}
	_, err = v.getTransitionResult(nextNum, parentStatedb) // to cache the transition result
	return err
}
```

func (h *headerGovModule) PostInsertBlock(b *types.Block) error {
	if len(b.Header().Vote) > 0 {
		var vb headergov.VoteBytes = b.Header().Vote
		vote, err := vb.ToVoteData()
		if err != nil {
			logger.Error("ToVoteData error", "vote", vb, "err", err)
			return err
		}
		err = h.HandleVote(b.NumberU64(), vote)
		if err != nil {
			logger.Error("HandleVote error", "vote", vb, "err", err)
			return err
		}
	}

	if len(b.Header().Governance) > 0 {
		var gb headergov.GovBytes = b.Header().Governance
		gov, err := gb.ToGovData()
		if err != nil {
			logger.Error("DeserializeHeaderGov error", "governance", gb, "err", err)
			return err
		}
		err = h.HandleGov(b.NumberU64(), gov)
		if err != nil {
			logger.Error("HandleGov error", "governance", gb, "err", err)
			return err
		}
	}

	return nil
