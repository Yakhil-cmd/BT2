Based on the investigation, there is no valid Polkadot SDK analog for this finding.

**Why the report doesn't map to FRAME:**

The underlying bug class in the report is Solidity-specific: `_callData` is raw bytes consumed via low-level ABI encoding (fixed 4-byte selector + 32-byte-aligned parameters), so an incorrect byte length can cause the ABI decoder to read past the intended fields or silently pad/truncate data, corrupting downstream logic. That failure mode is a consequence of ABI's positional/offset-based encoding scheme, which has no length self-description.

FRAME/Substrate does not use this encoding model. All `RuntimeCall`s are SCALE-encoded, and SCALE decoding is type-driven and self-describing — each field decodes according to its own type layout, not a fixed byte offset. Every relevant place in the codebase that accepts caller-supplied encoded/boxed calls or callback data enforces exact-consumption and/or length-witness checks rather than trusting an unchecked length:

- `pallet-collective`'s `propose`/`execute` explicitly checks `proposal.encoded_size() <= length_bound` and validates it again from storage in `validate_and_get_proposal`, rejecting mismatched lengths with `WrongProposalLength`. [1](#0-0) [2](#0-1) 

- `pallet-whitelist`'s `dispatch_whitelisted_call` requires a length witness and calls `decode_all`-style logic that fails with `UndecodableCall`/`UnavailablePreImage` if the encoded bytes don't exactly match a valid call (proven by `test_whitelist_call_and_execute_decode_consumes_all`, which shows extra trailing bytes are rejected rather than silently accepted). [3](#0-2) 

- Extrinsic decoding itself (`UncheckedExtrinsic`) enforces that the declared length prefix matches the actual consumed bytes, returning `"Invalid length prefix"` on mismatch.
