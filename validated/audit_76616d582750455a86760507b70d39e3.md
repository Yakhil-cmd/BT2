### Title
Stack-scoped API tokens can read the CCMenu status of any stack, not just the one they authorize - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the shared `stack` lookup helper with an unscoped variant, breaking the invariant that a stack-restricted `ApiClient` may only touch the single stack recorded in its `stack_id`.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through two cooperating methods: `stacks`, which returns `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped (`current_api_client.stack_id?`), and `stack`, which resolves the requested record only from that restricted relation via `stacks.from_param!(params[:stack_id])` [1](#0-0) . This is the binding the rest of the API relies on: **stack a token authorizes == stack a token can touch**.

`Api::CCMenuController` breaks that binding. It defines its own `stack` method that queries the entire `Stack` table unconditionally: `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping relation [2](#0-1) . The controller's only authorization gate is `require_permission :read, :stack` [3](#0-2) , which resolves to `ApiClient#check_permissions!`, a check that only inspects the `permissions` array for the literal string `read:stack` and never compares `stack_id` to the requested resource [4](#0-3) .

The controller additionally supports authenticating via a plain query-string `token` param (`authenticate_api_client` override), matching how the CCMenu URL is normally distributed/shared (e.g. pasted into CI dashboard tools) [5](#0-4) . Such tokens are routinely created scoped to one stack, e.g. by `CCMenuUrlController#client`, which creates an `ApiClient` with `permissions: %w[read:stack]` for a single stack context [6](#0-5) , and the intent of that scoping is precisely what `stacks`/`stack` on `BaseController` is meant to enforce for other endpoints (stacks#show, tasks, deploys, etc.), but `CCMenuController` silently opts out of it.

### Impact Explanation
Before the attacker's request: an `ApiClient` token is minted scoped to `Stack A` only (`stack_id = A.id`), with permission `read:stack`. Under the intended binding enforced elsewhere in the API, `stacks.from_param!(...)` for this client would raise `RecordNotFound`/404 for any `stack_id` other than `A`.

After the attacker's request: because `CCMenuController#stack` ignores `current_api_client.stack_id` entirely, the same token can be replayed against `GET /api/stacks/:any_other_stack/ccmenu` (or `GET /api/stacks/:any_other_stack/ccmenu?token=...`) for any `stack_id` in the installation, and the server renders that other stack's latest deploy/rollback state (build status, label, timestamp) in the CCMenu XML.

This is an unauthenticated-for-that-resource read of stack state: the token is valid, but its authorization was scoped to one stack, and the controller lets it read deploy status for stacks it was never granted. This matches the High-severity category of "unauthenticated read of stack state ... deploy output" via a broken authorization scoping boundary.

### Likelihood Explanation
Likelihood is high for any deployment where scoped CCMenu tokens exist. `CCMenuUrlController` is a first-class, unprivileged (session-only) feature that mints exactly this kind of stack-scoped token for CI dashboard integrations [7](#0-6) , so the vulnerable code path is reachable through normal, documented product usage rather than a contrived setup. Any holder of one such token (which is often embedded in external dashboard tool configs, not treated as highly sensitive) can enumerate other stacks' `stack_id` values (derivable from repository/branch/environment naming) and read their deploy status.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scoped `stacks` relation instead of querying `Stack` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that stack-scoped `ApiClient` tokens are restricted to their authorized stack exactly like every other API controller.

### Proof of Concept
1. As an authenticated user, visit a stack and trigger `CCMenuUrlController#fetch` for `Stack A` (e.g., via the settings page "CCMenu URL" link). This creates an `ApiClient` with `stack_id = A.id`, `permissions = ["read:stack"]`, and returns a URL containing `?token=<A-scoped-token>`.
2. Send `GET /api/stacks/<Stack B owner>/<Stack B repo>/<Stack B branch>/ccmenu?token=<A-scoped-token>` for a different `Stack B` that the token was never granted.
3. Observe a `200 OK` XML response containing `Stack B`'s real `lastBuildStatus`, `lastBuildLabel`, and `lastBuildTime`, because `CCMenuController#stack` resolved `params[:stack_id]` against the unscoped `Stack` table rather than the `stacks` relation filtered by `current_api_client.stack_id`.

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client

    end

    end
  end
