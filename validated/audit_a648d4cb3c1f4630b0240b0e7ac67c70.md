## Title
CCMenuController scopes CI-status reads by raw `stack_id` param instead of the token-authorized stack set, allowing a stack-scoped CCMenu token to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` establishes a binding: **the set of stacks a token authorizes == the set of stacks the controller action can touch**, enforced via the `stacks`/`stack` helpers (`stacks` filters by `current_api_client.stack_id` when the token is scoped to one stack, `stack` resolves `params[:stack_id]` only within that filtered scope) [1](#0-0) . `Api::CCMenuController` overrides `stack` to bypass this scope entirely, breaking the binding.

### Finding Description
`Api::CCMenuController#stack` is redefined to call `Stack.from_param!(params[:stack_id])` directly, instead of using the inherited `stacks.from_param!(...)` which is filtered to `current_api_client.stack_id` when the client is stack-scoped [2](#0-1) . Compare with `BaseController#stack`, which correctly resolves against the scoped `stacks` relation [1](#0-0) .

`CCMenuController` also overrides `authenticate_api_client` to accept the token as a URL query parameter (`params[:token]`) rather than HTTP Basic auth, which is how these tokens are normally distributed for CCMenu/CI-status-badge integrations [3](#0-2) . Such tokens are minted per-stack by `CCMenuUrlController#client`, which creates an `ApiClient` with only `read:stack` permission scoped to a specific stack via the URL's `stack_id`, and the resulting token is embedded directly in a URL meant to be pasted into third-party CI dashboard tools [4](#0-3) . `ApiClient#check_permissions!` only checks that `"read:stack"` is present in `permissions`; it performs no per-instance stack-id check [5](#0-4) , so the confinement to a single stack is expected to come entirely from the `stacks`/`stack` scoping helper in `BaseController`, which `CCMenuController` does not use.

**Binding broken (equality that should hold but doesn't):**
`{stacks authorized by the presented token}` == `{stacks reachable via CCMenuController#show}`

Before the PR/behavior: a CCMenu token minted for Stack A (`stack_id = A`) is intended to only ever resolve Stack A, because `stacks` filters by `current_api_client.stack_id`.
After: `CCMenuController#stack` ignores that filter and resolves whatever `params[:stack_id]` says, so the same Stack-A token can fetch CI status for Stack B, C, ... any stack in the instance, merely by changing the `stack_id` path segment.

This directly parallels the audited bug class: a value trusted for one narrower scope (WETH always being `tokens[2]`, i.e., an unchecked structural assumption) is substituted for the correct per-instance value that should have been derived from the authorized/verified source (analogous here: assuming any presented `read:stack` token authorizes the requested `stack_id`, instead of checking it against the token's own bound `stack_id`).

### Impact Explanation
This is an authorization escalation into stack-scoped data: a leaked or shared CCMenu URL for a low-sensitivity stack becomes a general "read status of every stack" token, exposing task/deploy history and build status of stacks the token holder was never intended to see. This maps to the "High - unauthenticated/under-authorized read of stack state" category, since it lets a legitimately-scoped, weak (`read:stack` only, URL-embedded) credential read state of other stacks.

### Likelihood Explanation
High likelihood: CCMenu URLs are explicitly designed to be pasted into third-party tools (CCMenu clients, dashboards) and passed via `token` query parameter rather than Basic Auth, i.e., they are treated as "low sensitivity, easily shared" credentials [4](#0-3) . Any holder of one such URL/token can trivially change the `stack_id` path segment of the request to enumerate and read any other stack's CI status - no additional privilege, secret, or session is required beyond possessing one legitimate scoped token.

### Recommendation
In `Api::CCMenuController`, remove the private `stack` override and rely on the inherited `BaseController#stack` (i.e., `stacks.from_param!(params[:stack_id])`), so the stack-scoping enforced for stack-scoped `ApiClient`s is applied consistently here as it is in every other API controller (e.g., `Api::TasksController`, `Api::StacksController`).

### Proof of Concept
1. Operator visits Stack A's page and uses "CCMenu URL" feature; `CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` with `permissions: ['read:stack']` and `stack_id: A`, returning a URL like `.../api/stacks/A/ccmenu.xml?token=<T>` [4](#0-3) .
2. Anyone who obtains `<T>` (e.g., pasted into a shared CI dashboard config) sends `GET /api/stacks/B/ccmenu.xml?token=<T>` for an arbitrary Stack B.
3. `authenticate_api_client` successfully authenticates via `ApiClient.authenticate(params[:token])` [6](#0-5) ; `require_permission :read, :stack` passes since the client has `read:stack` [7](#0-6) .
4. `stack` resolves `Stack.from_param!(params[:stack_id])` = Stack B directly, bypassing the intended `stack_id == A` scoping [8](#0-7) , and `#show` renders Stack B's latest deploy/rollback status to the caller [9](#0-8) .

      render(json: { ccmenu_url: uri.to_s })
