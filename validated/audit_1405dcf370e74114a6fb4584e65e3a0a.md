### Title
Webhook signature verification is bound to the attacker-controlled `repository.owner.login` field while dispatched handlers act on a different, unverified `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-tenant Shipit deployment (multiple GitHub organizations configured under `secrets.github`, each with its own `webhook_secret`), the HMAC signature check picks *which* organization's secret to verify against using an unauthenticated field of the same JSON body it is trying to authenticate, while the actual repository/stack that gets mutated is selected from a different field of that same body. This breaks the intended binding "organization whose secret authenticated the request == repository that gets written to."

### Finding Description
`WebhooksController#verify_signature` derives the organization used to look up the GitHub App / webhook secret directly from the unverified request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, read from the raw, not-yet-authenticated JSON payload, and used to call `Shipit.github(organization: repository_owner)`, which resolves a per-organization config (including `webhook_secret`) via `github_app_config`: [3](#0-2) 

Once `verify_webhook_signature` passes (checked against whichever org's secret was picked based on the attacker-supplied `repository.owner.login`), `create` dispatches the **same** payload to event handlers: [4](#0-3) 

Those handlers, however, resolve the target `Repository`/`Stack` from a **different** field in the payload — `repository.full_name` — not `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because the whole raw body (`request.raw_post`) is what's HMAC'd, an attacker cannot simply change `full_name` after computing a valid signature for a legitimate payload — that would invalidate the digest. So this alone does not produce a forgeable cross-repo write; the signature does cover the entire body including `full_name`.

The exploitable gap instead is `verify_webhook_signature`'s early-return: `return true unless webhook_secret` in `lib/shipit/github_app.rb` (`verify_webhook_signature`, lines 76-83, seen earlier). If **any** organization entry in a multi-org `secrets.github` config is present but has `webhook_secret` unset/blank (a state explicitly shown as a supported/example configuration in `config/secrets.development.shopify.yml` and `config/secrets.development.example.yml`, both listing `webhook_secret: # nil`), then signature verification for requests naming that organization in `repository.owner.login` is **unconditionally bypassed**. Since the organization used to select this bypassable config is attacker-controlled (`repository.owner.login` from the unauthenticated body) while the repository actually written to (`repository.full_name`) can be a completely different, real, tracked repository under a different org's Stack, an attacker can craft a request where:
- `repository.owner.login` = an org configured with a blank `webhook_secret` (signature check trivially passes, `head(422)` is never issued because `head(422) unless verified` doesn't halt execution — it doesn't `return`, so processing continues to `create`... actually `before_action` callbacks in Rails do halt the chain when `head` is rendered, but only if the response is committed; regardless the bypass means `verified` is `true`)
- `repository.full_name` = the victim's real repository name tracked by a different Stack

This lets an unauthenticated actor inject arbitrary events (push shas, pull_request opened/closed/labeled, membership add/remove, commit statuses) for a Stack whose organization uses a properly configured, secret-protected webhook, as long as *some other* org's config in the same Shipit instance has no webhook secret set.

### Impact Explanation
This breaks the "organization that authenticated" vs. "repository that is written" binding described in the audit rules. Concretely reachable, unprivileged writes include:
- Forcing `PushHandler` to call `stack.sync_github(expected_head_sha:)` with an attacker-chosen SHA for a real, victim-owned Stack, corrupting deploy state / triggering syncs against arbitrary shas.
- Forcing `ReviewStackAdapter`/PR handlers to archive, unarchive, or mutate review stacks and pull request records for repositories the attacker does not control.
- Injecting fabricated commit statuses (`status` event) affecting deploy gating for a tracked commit.

None of this requires a Shipit session, an `ApiClient` token, or GitHub write access to the victim repository — only knowledge that the host's multi-tenant configuration has one org without a `webhook_secret`, a configuration pattern the project's own example/dev secrets files show as valid.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: this only manifests when a Shipit instance is set up with the multi-organization `secrets.github` schema and at least one configured organization has a blank/absent `webhook_secret` (shown as an accepted configuration shape in the shipped example secrets files). Single-org / single-GitHub-App deployments (the more common setup, `github_default_organization` nil) are not affected because there is only one secret to choose from. This is a real but configuration-dependent gap, not a universal unauthenticated bypass.

### Recommendation
- Do not allow `verify_webhook_signature` to trivially return `true` when `webhook_secret` is blank in a multi-organization configuration; require every configured organization to have a non-blank secret, or reject the request instead of treating "no secret configured" as "always valid."
- Ensure that if `head(422)` is issued in `verify_signature`, the before_action chain halts (`return` after `head(422)`) so a failed verification cannot fall through to `create`.
- Bind the organization used for secret lookup to the same field trusted for repository resolution, or independently validate that `repository.owner.login` is consistent with `repository.full_name`'s owner segment before dispatching handlers.

### Proof of Concept
Preconditions: Shipit deployed with multi-org `secrets.github` (e.g., `orgA` and `orgB`), where `orgB.webhook_secret` is unset (as in the shipped `config/secrets.development.shopify.yml` template), and `orgA` has a real Stack tracking `orgA/victim-repo` protected by a strong `webhook_secret`.

1. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/victim-repo" }
}
```
2. POST to `/github/webhooks` with `X-Github-Event: push` and any `X-Hub-Signature` header, e.g. `sha1=deadbeef` (arbitrary — since `orgB` has no secret).
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgB")`, resolves `orgB`'s config, `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the supplied signature [1](#0-0) .
4. `create` proceeds and dispatches to `PushHandler`, which resolves the target via `payload.dig('repository','full_name')` = `"orgA/victim-repo"` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the real, secret-protected `orgA` Stack [6](#0-5) , despite the attacker never possessing `orgA`'s `webhook_secret`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
