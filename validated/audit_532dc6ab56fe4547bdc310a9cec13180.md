Based on my research, ocore does implement an on-chain governance/voting mechanism for system parameters (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) that exhibits the same "no snapshot" root cause as the FrankenDAO finding: vote weight is computed from the voter's *current* balance at tally time rather than a balance fixed at the moment the vote was cast.

### Title
Vote weight in `countVotes` is computed from the voter's current balance instead of a balance snapshot, allowing consensus-parameter votes to be manipulated with transient/borrowed balance - (File: main_chain.js)

### Summary
`main_chain.js`'s `countVotes()` tallies votes for system parameters (witness/OP list, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) by summing each voter address's *current* unspent, stable, good balance at the moment the tally runs, then attributing that balance to whichever `system_vote` records exist for that address, regardless of when the vote was cast or what balance the address held at that time.

### Finding Description
`saveSystemVote()` records a `system_vote` only with `address`, `subject`, `value` and `timestamp` — no balance snapshot is taken at vote time: [1](#0-0) 

When votes are tallied, `countVotes()` builds `voter_balances` from a live query of the `outputs` table representing each address's balance *right now* (at the current stabilization point), not the balance the address had when it cast its vote: [2](#0-1) 

This balance is then joined against all recorded votes (which can be up to several years old, extendable by the "expand the timeframe" loop) to compute the winning value: [3](#0-2) , [4](#0-3) , [5](#0-4) 

Because balance is read at counting time rather than snapshotted at voting time, a party can cast a `system_vote` from an address while holding little or no real long-term stake, then later — right before a `countVotes` invocation is triggered (via a `system_vote_count` message, processed once per stabilized MCI: [6](#0-5) , [7](#0-6)  ) — move a large balance into that same address (or into any other address that has a stale but still-valid vote on record). The full current balance is then attributed to that old vote as if it had been backing that position all along. This lets short-term/borrowed capital dominate the tally for consensus-critical parameters such as the number of order/witness providers (`op_list`) or TPS fee parameters, without the actual long-term economic stake the voting model is meant to represent.

### Impact Explanation
`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` are core consensus/economic parameters of the network. Manipulating their outcome via transient balance shifting can let an attacker install malicious or colluding order providers, or set fee/TPS parameters that disrupt network confirmation economics or enable fee-based DoS/inflation, i.e., "a network unable to confirm new units" or systemic fund-loss/fee-manipulation at the protocol level. This is a High-severity governance-integrity issue analogous to the original "no snapshot of votes" finding.

### Likelihood Explanation
Any unit poster who is an unprivileged holder of bytes can send `system_vote` messages, and votes remain valid for a rolling window that can extend to multiple years if turnout is thin (`SYSTEM_VOTE_MIN_SHARE` check loop). An attacker only needs enough capital to briefly move through one or more previously-voted addresses just before/at the mci where `countVotes` fires (which happens as part of ordinary MC stabilization once a `system_vote_count` payload has been seen), making this practically reachable without special privileges — though I was not able to fully verify from the indexed code exactly which callers are permitted to submit `system_vote_count` (validation.js references were only partially inspected within available context), so the exact triggering conditions/rate limits should be confirmed against the full `validation.js` and `composer.js` handling of `system_vote`/`system_vote_count` messages.

### Recommendation
Snapshot each voter's balance (or a suitable stake measure) at the moment the `system_vote` is cast, and store that snapshot value alongside the vote (in `system_votes`/`numerical_votes`/`op_votes`), rather than re-reading current balance during `countVotes()`. Alternatively, weight/require votes to be re-affirmed based on balance held continuously since the vote, or use balance measured at a fixed reference MCI/timestamp shared by all votes in a given tally, consistent with the pattern already used elsewhere in ocore for stable, deterministic state evaluation.

### Proof of Concept
1. Address A casts `system_vote` for `op_list=X` at time T1 while holding balance B1 (recorded with timestamp T1 only, no balance snapshot) — see `saveSystemVote` at `main_chain.js:1619-1628`.
2. A's balance is later spent/moved elsewhere; A's on-chain vote record for `op_list=X` remains valid as long as T1 is inside the rolling vote window (`since_timestamp` logic, `main_chain.js:1807-1821`).
3. Shortly before a `countVotes` run is triggered by a `system_vote_count` message reaching stability (`main_chain.js:1575-1578`, `1657-1665`), the attacker moves a large real-time balance into address A (or any other address with a stale vote on record).
4. `countVotes` computes `voter_balances` from A's live `outputs` balance (`main_chain.js:1753-1777`) and attributes the entire current balance to the old vote for `X`, potentially swinging `op_list`/`threshold_size`/TPS-fee parameter selection (`main_chain.js:1850-1899`) without that balance having genuinely backed the position throughout the vote period.
