### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` with no repository scoping, unlike `CheckSuiteHandler#process` which correctly restricts writes to `stacks` derived from the webhook's own `repository.full_name`. Because git commit SHAs are frequently shared across repositories (forks, shared history, cherry-picks, or CI checkouts of a common base), any GitHub org with the Shipit GitHub App installed can send a legitimately-signed `status` webhook for a commit SHA that also exists in a completely unrelated stack's history, injecting a fabricated CI status onto that foreign stack's commit.

### Finding Description
The binding that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` (the commit being mutated belongs to the repository that authenticated the webhook). `CheckSuiteHandler#process` enforces this by only iterating `stacks` from `Handler#stacks`, which is `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [1](#0-0) , then filters by `branch` and searches `stack.commits.where(sha: ...)` — strictly repository-scoped [2](#0-1) .

`StatusHandler#process`, however, queries `Commit.where(sha: params.sha)` globally across the entire `commits` table, with no reference to `payload['repository']` at all [3](#0-2) . `Commit#create_status_from_github!` then writes the status onto whichever stack that commit happens to belong to, via `statuses.replicate_from_github!(stack_id, github_status)` using the commit's own `stack_id` [4](#0-3) .

`WebhooksController#verify_signature` only proves the payload was signed by the GitHub App installation belonging to `repository_owner` (i.e., the attacker's own org/repo) — it does not prove that the SHA inside the payload actually belongs to that repository [5](#0-4) . Thus an attacker who owns/forks a repository with the Shipit App installed, and whose repository shares a commit SHA with a victim stack (e.g. a fork sharing base history, or a shared base branch checked out by CI in multiple repos), can send a `status` event naming their own repository but the victim's shared SHA. The signature check passes because it's genuinely signed by GitHub for the attacker's own repo/event; `StatusHandler` then finds and mutates the victim's `Commit` regardless of which repository the webhook was actually for.

No other guard closes this gap: `ExplicitParameters` only validates the shape of `sha`/`state`/etc, not repository ownership; there is no `stacks`/`Repository.from_github_repo_name` scoping in `StatusHandler` unlike its sibling handler.

### Impact Explanation
This lets a payload authenticated for repository A mutate a `Status` (and therefore deployability/CI state) on a commit belonging to repository B's stack — a direct cross-tenant write matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." A forged success status can flip `Commit#deployable?`/`blocked?` evaluation and enable `stack.schedule_merges` on the victim stack (`Commit#add_status`) [6](#0-5) , potentially causing an unauthorized deploy or merge on the victim's stack without their CI ever having run. This is repeatable against any stack whose commits' SHAs collide with SHAs reachable by the attacker's own repository/org.

### Likelihood Explanation
Preconditions: attacker needs a repository (their own, or a fork) with the Shipit GitHub App installed so they can trigger a genuinely-signed `status` webhook; then they need a commit SHA that is shared with a target stack's history — realistic via forking a victim's public repo (shared base commits) or via common upstream dependencies/shared branches. No Shipit credentials, session, or maintainer role are needed — only ability to trigger GitHub status events for a repo they control. Feasibility is moderate-to-high for forked or mirrored repositories, and the attack is fully repeatable per-SHA.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler#process` does: restrict the commit lookup to commits belonging to `stacks` (derived from `Handler#stacks`/`repository_name`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack: stacks)`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
test "StatusHandler mutates foreign stack's commit while CheckSuiteHandler does not" do
  victim_stack = shipit_stacks(:shipit)
  attacker_repo_full_name = "attacker/unrelated-repo"
  shared_sha = victim_stack.commits.first.sha

  # CheckSuiteHandler: repository-scoped, no effect on foreign stack
  check_suite_payload = {
    'repository' => { 'full_name' => attacker_repo_full_name },
    'check_suite' => { 'head_sha' => shared_sha, 'head_branch' => victim_stack.branch }
  }
  assert_no_enqueued_jobs(only: RefreshCheckRunsJob) do
    Shipit::Webhooks::Handlers::CheckSuiteHandler.new(check_suite_payload).process
  end

  # StatusHandler: globally scoped by sha, mutates victim stack's commit
  status_payload = {
    'repository' => { 'full_name' => attacker_repo_full_name },
    'sha' => shared_sha,
    'state' => 'success'
  }
  assert_difference -> { victim_stack.commits.first.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new(status_payload).process
  end
end
```
This demonstrates the divergence: identical attacker-controlled payload shape (foreign `repository.full_name`, victim's shared `sha`) is rejected by `CheckSuiteHandler` (no effect, since `stacks` resolves against `attacker/unrelated-repo`) but succeeds against `StatusHandler`, writing a `Status` onto the victim stack's commit.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
