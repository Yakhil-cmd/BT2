### Title
Bridged ERC721 NFTs Permanently Locked When `_to` Is a Non-ERC721-Receiver Contract — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

### Summary

`handleERC721Transfer` in `BridgeTransferERC721` delivers bridged ERC721 tokens to an arbitrary `_to` address using either `mintWithTokenURI` (which internally calls the unsafe `_mint`) or `transferFrom` (not `safeTransferFrom`). Neither path checks whether `_to` is a contract that implements `IERC721Receiver`. If `_to` is such a contract, the NFT is permanently locked and the bridge handle nonce is consumed, making the loss irreversible.

### Finding Description

In `handleERC721Transfer`, after the handle nonce is updated and the `HandleValueTransfer` event is emitted, the token delivery is performed via two unsafe paths:

**Path 1 — `modeMintBurn = true`:** [1](#0-0) 

This calls `ERC721MetadataMintable.mintWithTokenURI`, which internally calls the bare `_mint`: [2](#0-1) 

`_mint` only sets `_tokenOwner[tokenId] = to` and emits `Transfer`; it never calls `_checkOnERC721Received`: [3](#0-2) 

**Path 2 — `modeMintBurn = false`:** [4](#0-3) 

`transferFrom` also does not invoke `_checkOnERC721Received`, unlike `safeTransferFrom`: [5](#0-4) 

The receiver check that would catch non-ERC721-receiver contracts only exists in `safeTransferFrom`: [6](#0-5) 

The nonce update and event emission happen **before** the token delivery: [7](#0-6) 

Because the nonce is consumed and the `HandleValueTransfer` event is emitted before the unsafe mint/transfer, the bridge considers the transfer complete. There is no recovery path.

### Impact Explanation

A bridged ERC721 NFT is permanently locked inside a contract that does not implement `onERC721Received`. The bridge handle nonce for that request is consumed and cannot be replayed. The asset is irretrievably lost from the user's perspective. This is a direct asset-loss impact on bridged ERC721 tokens.

### Likelihood Explanation

The `_to` address is supplied by the user on the source chain via `requestERC721Transfer` or `onERC721Received`: [8](#0-7) 

A user may legitimately specify a multisig wallet, DAO treasury, or any other contract as the recipient. If that contract does not implement `IERC721Receiver`, the NFT is locked. No attacker action is required; ordinary user error is sufficient. Bridge operators faithfully relay the `_to` from the source-chain event: [9](#0-8) 

### Recommendation

1. Replace `mintWithTokenURI` (which calls `_mint`) with a safe-mint variant that calls `_safeMint`, or add a `_checkOnERC721Received` call after minting.
2. Replace `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` with `IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId)`.

Both `safeTransferFrom` and `_safeMint` are already available in the inherited OpenZeppelin library: [10](#0-9) 

### Proof of Concept

1. User on the source chain calls `requestERC721Transfer(tokenAddress, contractRecipient, tokenId, extraData)` where `contractRecipient` is a deployed contract that does **not** implement `IERC721Receiver` (e.g., a plain multisig or DAO contract).
2. Bridge operators observe the `RequestValueTransferEncoded` event and call `handleERC721Transfer(..., _to=contractRecipient, ...)` on the destination bridge.
3. The bridge updates `handleNoncesToBlockNums[_requestedNonce]`, calls `_updateHandleNonce`, and emits `HandleValueTransfer` — the nonce is consumed.
4. In `modeMintBurn` mode: `mintWithTokenURI(contractRecipient, tokenId, uri)` → `_mint(contractRecipient, tokenId)` succeeds silently. The NFT is now owned by `contractRecipient` but `contractRecipient` has no way to transfer it out (no `onERC721Received`, no internal ERC721 logic).
5. In non-mintBurn mode: `transferFrom(bridge, contractRecipient, tokenId)` succeeds silently with the same result.
6. The NFT is permanently locked. The bridge nonce cannot be replayed. The asset is lost.
