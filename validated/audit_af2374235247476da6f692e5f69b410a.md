### Title
Stack-scoped API tokens bypass their stack authorization on the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` token which is scoped to a single stack (`ApiClient#stack_id` set) can only ever resolve `stack` to that one `Stack` record. `Shipit::Api::CCMenuController` overrides this accessor and resolves the target `Stack` directly from the unauthenticated `params[:stack_id]` route parameter, completely bypassing the scoping check. A `read:stack` token that was authorized for Stack A can therefore be replayed against `/api/stacks/<STACK_B>/ccmenu.xml` to read Stack B's deploy state.

### Finding Description
`ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The generic API base controller enforces this binding for every subclass by resolving the target stack through a query filtered on `current_api_client.stack_id`: [2](#0-1) 

This is exactly the binding the test suite validates for the ordinary stacks API: "an api client scoped to a stack will only see that one stack" [3](#0-2) , using a fixture `ApiClient` that is explicitly scoped to a single stack with only `read:stack` permission [4](#0-3) .

`Api::CCMenuController`, however, redefines `stack` to resolve directly from the request parameter, independent of the authenticated client's `stack_id`: [5](#0-4) 

The only authorization check applied on this endpoint is `require_permission :read, :stack`, which merely checks that the token's permission list contains the string `read:stack` — it never compares the requested stack to the client's `stack_id`: [6](#0-5) 

This breaks the equality the rest of the API enforces: `token.stack_id == requested_stack.id`. On `CCMenuController`, the right-hand side of that equality is attacker-controlled via `params[:stack_id]` while the left-hand side (the permission gate) is never checked against it.

### Impact Explanation
Any holder of a valid, narrowly-scoped `read:stack` token for one stack — the exact shape of token the codebase supports and tests (a single-stack, read-only `ApiClient`) — can use it to read the deploy/build state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, running/locked state via `Api::CCMenuController#show` and the `shipit/ccmenu/project` view) of *any* other stack in the installation, not just the one it was authorized for. This is an unauthorized read of stack/deploy state across a trust boundary the rest of the API otherwise enforces, matching the "unauthenticated read of stack state, task streams or deploy output" class of High-severity issue (here, "unauthenticated" with respect to the target stack, since the token carries no authorization for it).

### Likelihood Explanation
High. Exploitation is a single HTTP GET with a substituted `stack_id` path parameter and requires no interaction beyond possessing any valid `read:stack` token — no write/deploy/lock permission or session is needed, and CCMenu-style tokens are the class of credential this feature exists to hand out for lightweight, embeddable status polling.

### Recommendation
Remove `CCMenuController`'s private `stack` override and let it inherit `BaseController#stack` (which resolves through the `stacks` scope filtered by `current_api_client.stack_id`), so a stack-scoped token can never resolve a stack other than the one it was issued for. If a global stack lookup is intentionally desired for unscoped tokens, explicitly re-check `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
1. An administrator issues (via console, or any future/other integration path that sets `ApiClient#stack_id`) a token `T` with `permissions: ['read:stack']` and `stack_id` = Stack A's id — the same shape as the `here_come_the_walrus` fixture used by the test suite.
2. Attacker who obtains `T` (e.g., from an embedded CCMenu status URL) issues:
   `GET /api/stacks/<STACK_B_PARAM>/ccmenu.xml` with `Authorization: Basic base64(T)` (or `?token=T`).
3. `authenticate_api_client` succeeds because `T` is a valid token. `require_permission :read, :stack` succeeds because `T.permissions` includes `read:stack`.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (app/controllers/shipit/api/ccmenu_controller.rb:29-31), ignoring `T.stack_id`, and returns Stack B.
5. The response renders Stack B's latest deploy/build status — data the token was never authorized to read.

Note: I was unable to find an in-repo UI flow that currently provisions a stack-scoped (`stack_id` set) `ApiClient` (the UI `ApiClientsController#create_params` only permits `:name` and `permissions`, and `CCMenuUrlController#client` creates an unscoped client) — this scoping model is presently exercised only in the model/API test suite and fixtures. This does not remove the vulnerability (the enforcement code path and the bypass both exist and are actively tested elsewhere in the engine), but it does mean the most direct exploit requires a stack-scoped token to first exist via some provisioning mechanism (e.g., admin console, a future API, or direct DB creation) rather than through a currently-wired UI control; this uncertainty could not be fully resolved with the available index.
