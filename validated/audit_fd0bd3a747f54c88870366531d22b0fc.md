### Title
Incorrect free/teardown logic when reverting AA response units can throw on already-forgotten cache entries and crash the node - ([File: aa_composer.js])

### Summary
Ghostscript's CVE-2018-16541 crashed the interpreter because a pagedevice replacement freed an object while other code still expected it to exist, and the incorrect free-then-reuse ordering triggered a fatal error. Obyte's `ocore` has a structurally analogous bug in the AA (autonomous agent) unit "teardown" path: `revertResponsesInCaches()` in `aa_composer.js` unconditionally "frees" (forgets) every accumulated response unit from the in-memory unit caches, but the underlying `forgetUnit()` in `storage.js` assumes the object it is about to delete is still present and dereferences it unconditionally, with no existence check.

### Finding Description
When an AA trigger's execution chain has to be rolled back — e.g. `dryRunPrimaryAATrigger()` (aa_composer.js:272-306) or the `revert()` helper inside `handleTrigger()` (aa_composer.js:1759-1783) — the code calls `revertResponsesInCaches(arrResponses)`: [1](#0-0) 

This function collects every `response_unit` recorded so far in `arrResponses` and calls `storage.forgetUnit` on each one, then calls `storage.fixIsFreeAfterForgettingUnit()` using only the parent_units of the *first* unit in the list:
```
var first_unit = arrResponseUnits[0];
var objFirstUnit = storage.assocUnstableUnits[first_unit];
var parent_units = objFirstUnit.parent_units;
arrResponseUnits.forEach(storage.forgetUnit);
storage.fixIsFreeAfterForgettingUnit(parent_units);
```
`forgetUnit()` itself performs the actual "free" of the cached unit object with no defensive check that the entry still exists: [2](#0-1) 
```
function forgetUnit(unit){
	console.log('forgetting unit '+unit);
	if (!conf.bLight){
		console.log('parents', assocUnstableUnits[unit].parent_units);   // <-- unchecked dereference
		assocUnstableUnits[unit].parent_units.forEach(...)
```
If `assocUnstableUnits[unit]` is already `undefined` when `forgetUnit` runs — e.g. because the same response unit was already freed earlier in the same revert pass, or because a secondary-AA chain produced a duplicate/overlapping `response_unit` entry in `arrResponses` before the bounce/rollback path collected them — the very first line of the "free" logic (`assocUnstableUnits[unit].parent_units`) throws a synchronous `TypeError: Cannot read properties of undefined`. This mirrors the Ghostscript bug class exactly: an object gets torn down/replaced without validating that the free target is still live, and the incorrect free ordering (as opposed to a check-then-free) becomes a crash primitive when triggered by attacker-controlled input (in this case, an AA trigger author or a chain of AAs that produces a revert with more than one already-processed response unit).

This code path is reachable by any unprivileged unit poster/AA-trigger sender: sending a payment/data message to a chain of AAs where a later AA in the chain bounces (forcing `revert()`/`revertResponsesInCaches()` to run over an `arrResponses` array that already contains entries) is entirely attacker-controlled and requires no special privilege — it is the standard code path for any bounced multi-hop AA chain and for `dryRunPrimaryAATrigger`, which network.js also invokes synchronously for every incoming AA-triggering unit when `conf.bDryRunNewTriggers` is set (network.js:1271-1281).

### Impact Explanation
An uncaught synchronous `TypeError` thrown deep inside `handleJoint`/`dryRunPrimaryAATrigger`'s callback chain is not caught by any `try/catch` in this flow, so it propagates to the process's `uncaughtException` handler. Depending on how that handler is configured, this can terminate or otherwise destabilize the full node process while it holds the `write` mutex/DB transaction, i.e. denial of service against the node's ability to process/validate new units — matching the "network unable to confirm new units" impact class allowed by the rules. Because this reachable from posting ordinary triggering units to a legitimately deployed multi-AA chain, no privileged access is required.

### Likelihood Explanation
The precondition (duplicate/overlapping response unit already forgotten in cache when `revertResponsesInCaches` is invoked a second time on overlapping unit sets, or same unit appearing twice in `arrResponses`) requires a specific but constructible AA definition/trigger sequence (chains of AAs bouncing after a partial response has already been produced and reverted once). It is not a trivial one-line trigger, but it is fully reachable using standard, publicly-documented AA authoring primitives (bounce_fees, secondary triggers, chained payments) — no protocol-level privilege or malicious peer/hub cooperation is needed, satisfying the scope rules (AA author/trigger sender only).

### Recommendation
Harden `forgetUnit()` to defensively check for existence before dereferencing:
```js
function forgetUnit(unit){
    var o = assocUnstableUnits[unit];
    if (!o) return; // already forgotten, nothing to do
    ...
}
```
Additionally, `revertResponsesInCaches()` should de-duplicate `arrResponseUnits` before iterating, and should not assume the first unit's `parent_units` represents all reverted units' parents; each removed unit's own parent set should be tracked and passed to `fixIsFreeAfterForgettingUnit`.

### Proof of Concept
1. Deploy AA chain `Primary -> Secondary` where `Secondary` bounces under a specific condition after `Primary` has already produced (and recorded in `arrResponses`) a non-bounced response unit.
2. Trigger the chain such that the revert path in `handleTrigger`'s `revert()` (aa_composer.js:1759) is invoked, which calls `revertResponsesInCaches(arrResponses)`.
3. Craft a scenario (e.g. via `dryRunPrimaryAATrigger` being invoked twice concurrently or a secondary trigger loop that appends the same `response_unit` reference twice into `arrResponses` before the batch write/rollback) so that `forgetUnit` is called on a unit whose `assocUnstableUnits[unit]` entry has already been deleted by a prior `forgetUnit` call within the same revert pass.
4. Observe the uncaught `TypeError: Cannot read properties of undefined (reading 'parent_units')` thrown from `storage.js:2212`, crashing/destabilizing the node process.

Note: I was not able to fully trace, within the available indexed code, every exact call sequence that produces overlapping/duplicate entries in `arrResponses` across nested secondary triggers and repeated `revertResponsesInCaches` calls (some of the async control flow in `aa_composer.js` around `handleSecondaryTriggers`/`bounce`/`revert` spans code not fully returned by search). A Devin session with full repository access should trace `bounce()`, `revert()`, and `handleSecondaryTriggers()` end-to-end to confirm the exact duplicate/overlap condition and validate the PoC concretely before treating this as fully proven.
