Confirmed: default `credential.helper` is set to `cache --timeout 3600` [1](#0-0) , an in-memory cache, so the injection mechanics I outlined against the git-credential protocol via `credential approve` do apply, and the vulnerable sink is `StoreCredentials`.

### Title
Unvalidated GitHub App token value spliced into git-credential input enables credential-store line injection - ([File: main.go])

### Summary
`RefreshGitHubAppToken` takes the `token` field from a JSON response returned by the (network-reachable, non-pinned) GitHub App installation-token endpoint and, without any validation of its content or structure, passes it straight into `StoreCredentials`, which builds a multi-line `url=...\nusername=...\npassword=...\n` blob via `fmt.Sprintf` and feeds it as raw stdin to `git credential approve` [2](#0-1) [3](#0-2) . This mirrors the reported bug class: a value obtained from an external/untrusted response is used directly in a security-sensitive protocol operation without validating its length/structure (specifically the absence of embedded `\n` / extra `key=value` attribute lines), enabling injection into the git-credential attribute stream.

### Finding Description
`git credential approve` (and the `store`/`cache` helpers behind it) parse stdin as a sequence of `key=value` lines terminated by a blank line/EOF; whichever `url=`/`username=`/`password=` line appears last for a given key wins for that credential record. `StoreCredentials` builds this input with an unescaped `fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)` [4](#0-3) . The `password` value in the GitHub App path comes from `tokenResponse.Token`, decoded straight from JSON with no validation of length, character set, or the absence of `\n`/`\r` bytes [5](#0-4) . Because JSON strings can carry literal newline characters (as the escape sequence `\n`), a token value such as `"abc\nurl=https://attacker.example/\nusername=x\npassword=y\n"` decodes to a Go string containing real newlines, which are then written verbatim into the credential-approve stdin stream, allowing the attacker-controlled response to inject additional/overriding `url=`, `username=`, or `password=` attributes into the credential record actually stored by git.

This is directly analogous to the reported issue: in both cases, a value obtained from a remote endpoint (`authentication["message"]` there, `tokenResponse.Token` here) is consumed by a security-critical operation (signing there, credential-store population here) without first validating its structure/length, allowing an attacker who controls that endpoint's response to smuggle additional structured content past the trust boundary.

`RefreshGitHubAppToken` is invoked on every `refreshCreds` cycle whenever GitHub App auth flags are configured [6](#0-5) , so this occurs on essentially every sync when GitHub App auth is enabled, and `--github-base-url` is user/operator configurable, expanding the reachable attack surface to any endpoint that flag can be pointed at (e.g. malformed/compromised proxy, or a compromised upstream GitHub-app-token issuing endpoint).

### Impact Explanation
Because the injected attribute lines can override `url=`, the attacker (who already controls the response and therefore the token contents) can force git's in-memory credential cache to associate arbitrary attacker-chosen `username=`/`password=` pairs with an arbitrary URL of their choosing, rather than the intended `git.repo` URL. This can corrupt the credential cache for other configured URLs (e.g. those set via `--credential` for submodules), causing:
- Persistent sync denial for other remotes, if their legitimate cached credentials are overwritten by garbage, causing subsequent authenticated fetches to fail.
- Confused-deputy style credential misuse: git-sync could later authenticate to a different (possibly attacker-chosen) URL using attacker-supplied username/password, which is undesirable if that URL is reachable and treated as trusted (e.g. an internal submodule host), since it substitutes the intended credential material.

This does not directly exfiltrate the operator's real password/token (the attacker already supplies the malicious value), but it does allow attacker-controlled data to overwrite trust-boundary state (the credential cache) beyond the URL that was supposed to receive it, satisfying the "persistent sync denial" / wrong-content-publication impact category.

### Likelihood Explanation
Exploitation requires control (or MITM/compromise) of the GitHub App installation-token response, or the ability to redirect `--github-base-url` to an attacker-controlled endpoint. This is a real but narrower trust boundary than a fully "malicious operator" scenario, since it targets the *response content* from an endpoint git-sync itself calls as part of normal operation — squarely within the "credential/token handling" analog class called out as in-scope. Likelihood is low-to-moderate: it requires the response value to reach git-sync unvalidated, which is exactly what happens today.

### Recommendation
- **Short term**: Validate `tokenResponse.Token` (and any other value later interpolated into credential-approve input) rejects/strips embedded `\n`/`\r` characters and enforces a reasonable length/charset before calling `StoreCredentials`. Apply the same validation to `username`/`password` obtained from `CallAskPassURL` for defense in depth.
- **Long term**: Stop building the `git credential approve` payload with `fmt.Sprintf` string concatenation; use a small structured writer that percent/line-encodes each attribute value (or rejects values containing control characters) so that no value can introduce additional attribute lines, regardless of its source.

### Proof of Concept
1. Configure git-sync with `--github-app-*` flags pointing `--github-base-url` at an attacker-controlled/MITM'd HTTPS endpoint (or compromise the real endpoint's response).
2. Have that endpoint return, for the `POST /app/installations/{id}/access_tokens` call, a JSON body such as:
   ```json
   {"token": "realtoken\nurl=https://internal-submodule.example/\nusername=evil\npassword=evil-controlled\n", "expires_at": "2999-01-01T00:00:00Z"}
   ```
3. `RefreshGitHubAppToken` decodes this into `tokenResponse.Token` unchanged and calls `StoreCredentials(ctx, git.repo, "-", tokenResponse.Token)` [7](#0-6) .
4. `StoreCredentials` writes `url=<git.repo>\nusername=-\npassword=realtoken\nurl=https://internal-submodule.example/\nusername=evil\npassword=evil-controlled\n\n` to `git credential approve` [8](#0-7) .
5. Git's credential-cache helper parses the trailing `url=`/`username=`/`password=` lines as overriding attributes for the single record being approved (last-value-wins per git's credential protocol), storing attacker-chosen credentials under `https://internal-submodule.example/` instead of, or in addition to, the intended repo URL — corrupting the cache used for subsequent fetches/submodule operations.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
