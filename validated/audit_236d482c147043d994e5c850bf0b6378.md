### Title
Attacker can inflate an uncapped asset's balance at a target AA to permanently DoS/freeze that AA's handling of the asset via `MAX_BALANCE` overflow check - (File: aa_composer.js)

### Summary
`LiquidStakingManager._autoStakeWithSyndicate` griefing (fixed contribution + attacker-controlled small stake pushed over a hard cap → revert) has an analog in ocore's AA balance accounting. Any unprivileged user can repeatedly self-issue an uncapped, `issued_by_definer_only:false` asset and pay it into an Autonomous Agent's address until the AA's tracked balance for that asset approaches `MAX_BALANCE`. Once close to the ceiling, a legitimate user's payment of the same asset to the AA (as part of a normal trigger) tips the sum over `MAX_BALANCE`, causing `handleTrigger` to bounce with `"balance overflow"`.

### Finding Description
`updateInitialAABalances` adds the coins received in a trigger to the AA's persisted `aa_balances` row and flags overflow if the result exceeds `MAX_BALANCE`: [1](#0-0) [2](#0-1) 

`MAX_BALANCE` is defined as a fixed, hard ceiling on a per-(address, asset) basis: [3](#0-2) 

Unlike the base "bytes" asset, whose global money supply is capped well below `MAX_BALANCE` (`TOTAL_WHITEBYTES`), a custom asset defined with `issued_by_definer_only: false` can be self-issued by *any* address, with each issuer maintaining an independent `serial_number` sequence, effectively allowing unbounded repeated issuance: [4](#0-3) [5](#0-4) 

Each issuance can be up to `constants.MAX_CAP`, and nothing stops a single address from issuing the asset many times over many units (validation only forbids re-using the same serial number per issuer, but a new serial number is granted every time by incrementing `max_serial_number`): [6](#0-5) [7](#0-6) 

By repeatedly issuing and paying this asset to a target AA's address, an attacker can drive `aa_balances[address][asset]` arbitrarily high — up to and beyond `MAX_BALANCE`. Once the balance is already at/near the ceiling, the AA becomes permanently unable to accept any further inflow of that asset: any trigger (from the legitimate DApp user) that includes an output of that asset to the AA will make `trigger_opts.assocBalances[address][asset] > MAX_BALANCE` true, and the trigger will bounce with `"balance overflow"` after the `pemCurvesFixMci` upgrade point: [8](#0-7) 

This is structurally the same bug class as the Syndicate/LiquidStakingManager finding: a fixed/expected contribution combined with an attacker-controlled, cheaply repeatable contribution that is summed against a hard, shared cap, causing the legitimate operation to permanently revert (DoS). In ocore's case the "shared pool" is the AA's own `aa_balances` row for that asset, which persists on-chain forever (there is no way to reduce a balance except by the AA itself spending it), so the griefing is durable rather than a one-shot front-run.

### Impact Explanation
Once an AA's balance for a given asset is pinned near `MAX_BALANCE`, every trigger sending that asset to the AA bounces, effectively freezing that part of the AA's functionality (e.g., a DEX/AA that accepts a specific asset for trading, staking, or accounting purposes can be permanently disabled for that asset). This is a fund-freezing/denial-of-service condition reachable by an ordinary, unprivileged unit poster who only needs the ability to define and self-issue an uncapped asset (`issued_by_definer_only: false`) and send it to the target AA — no special privileges required.

### Likelihood Explanation
Feasibility depends on how many issuances are needed to reach `MAX_BALANCE` (`2^63 - 1 - MAX_MESSAGES_PER_UNIT * MAX_CAP`), which is extremely large. The attacker fully controls the asset's supply cap situation (self-issued, uncapped asset), so there is no external limit like total byte supply constraining them — they can issue `MAX_CAP` per issuance across arbitrarily many units/messages over time. This makes reaching the threshold a matter of sustained but unprivileged effort (issuing many units), not requiring any race condition or front-running precision, unlike the original 1-block front-run scenario. I was not able to fully verify the exact numeric value of `constants.MAX_CAP` from the index (grep found matches in `constants.js` but content wasn't retrievable in this session), so I cannot give a precise number of transactions required; this should be verified in a live session.

### Recommendation
- Consider capping the *rate or total* of self-issuance for uncapped, non-definer-restricted assets, or track/limit `aa_balances` growth from external inputs independent of `MAX_BALANCE`.
- Alternatively, decouple the "balance overflow" precision safeguard from asset-specific caps by using arbitrary-precision arithmetic (e.g., `Decimal`) for `aa_balances`, removing the need for a hard `MAX_BALANCE` ceiling that attacker-controlled uncapped assets can approach.
- At minimum, document that AA authors accepting uncapped, non-definer-issued assets are exposed to this griefing vector, and recommend AA definitions restrict accepted assets to `issued_by_definer_only: true` or capped assets.

### Proof of Concept
1. Attacker defines an asset `is_private:false, is_transferrable:true, fixed_denominations:false, issued_by_definer_only:false, cosigned_by_definer:false` (no `cap`), matching the shape validated in `validateAssetDefinition` [9](#0-8) .
2. Attacker repeatedly composes payment units that include an `"issue"` input for this asset (self-issued, up to `MAX_CAP` per input, per the checks in `validation.js` lines 2315-2353) with an output paying the issued amount directly to the target AA's address.
3. Each such unit is a normal, single-author "transfer/issue" payment; there is no rate limiting on how often an address can issue a self-issued asset, so the attacker can perform this thousands of times over an extended period.
4. Once `aa_balances[victim_AA][attacker_asset]` accumulates to just below `MAX_BALANCE`, any legitimate user's trigger to the same AA that includes an output of the same asset (even a tiny amount) causes `updateInitialAABalances` to compute a sum `> MAX_BALANCE`, setting `bOverflow = true` and bouncing the trigger with `"balance overflow"` [8](#0-7) , permanently denying that AA's use of the asset.
