### Title
Unhandled exception in `objectLength.getHeadersSize()` during unit validation crashes the node - ([File: validation.js])

### Summary
`validation.js`'s `validate()` computes the header commission size via `objectLength.getHeadersSize(objUnit)` at [1](#0-0)  without wrapping the call in a `try/catch`, unlike the structurally identical `getTotalPayloadSize()` check immediately below it, which *is* guarded by `try { ... } catch (e) { return callbacks.ifJointError(...) }` [2](#0-1) . `getHeadersSize()` recurses through the unit's header fields (including `authors[].definition` and `earned_headers_commission_recipients`, which are not yet type/structure-validated at this point in the pipeline) via `getLength()` in `object_length.js`, and that function throws a plain `Error` for any non-finite number, undefined field value, or unrecognized JS type [3](#0-2) .

### Finding Description
This is the closest reachable analog to CVE-2021-25829: instead of a native binary-stream parser crashing on malformed length/field data, ocore's JSON-based unit parser has an object-size calculation routine that throws on malformed numeric data, and that throw is not caught where it is reachable from a single externally posted unit.

Root cause chain:
1. A remote/unprivileged peer posts a `unit` whose header contains `earned_headers_commission_recipients` (an allowed top-level unit field per the field whitelist at [4](#0-3) ) with an `earned_headers_commission_share` value that is a syntactically valid JSON number literal with an extreme exponent, e.g. `1e400`. `JSON.parse()` legally parses this token but the resulting JS value is `Infinity`.
2. At this point in `validate()`, `earned_headers_commission_recipients` has *not yet* been structurally validated — `validateHeadersCommissionRecipients()` only runs later inside the `async.series` pipeline (after `getHeadersSize` is invoked), and `objUnit.authors[].definition` (an arbitrary attacker-controlled nested structure) has not been validated by `validateAuthors()`/`Definition.validateDefinition()` either, since those run even later in the same `async.series` chain [5](#0-4) .
3. `objectLength.getHeadersSize(objUnit)` is called synchronously and unguarded at [6](#0-5) , which builds `objHeader` (a clone of the unit minus a few fields) and calls `getLength(objHeader, bWithKeys)`.
4. `getLength()`'s recursive walker throws `Error("invalid number: " + value)` as soon as it encounters the `Infinity` value [7](#0-6) .
5. Because the call site has no `try/catch`, this exception propagates synchronously out of `validate()` — through the `mutex.lock` callback in `network.js`'s `handleJoint()`, which likewise has no surrounding `try/catch` for the `validation.validate(...)` call [8](#0-7) .
6. ocore installs a global `process.on('uncaughtException', ...)` handler that deliberately re-throws to terminate the process: `throw err; // crash the process to avoid ending up in an inconsistent state` [9](#0-8) .

The result: one maliciously crafted, syntactically valid unit posted by any unprivileged peer crashes the receiving full node.

### Impact Explanation
This matches the "Accept" criteria for a network unable to confirm new units: a crash of the hub/full node process halts all validation, relaying, and stabilization until manually restarted, and if propagated (broadcast) to multiple full nodes simultaneously, it is a fleet-wide denial of service triggered by a single unit — directly analogous to the ONLYOFFICE binary-stream DoS (CVE-2021-25829), which likewise used malformed structured data to force a crash via unhandled parsing exceptions.

### Likelihood Explanation
High reachability: no privileged position (peer, hub, or operator role) is required — this is exploitable by any address able to compose and post/broadcast a unit. The triggering value (`1e400` or similarly large exponent literal) is a completely valid JSON number token, so it passes JSON parsing and the WebSocket message framing without issue; it is only ocore's own domain-specific `isFinite()` check deep in `getLength()` that rejects it, and by then the exception is unguarded.

### Recommendation
- Wrap the `objectLength.getHeadersSize(objUnit)` call in `validation.js` (and its duplicate call two lines later in the error-message branch) in the same `try/catch` pattern already used for `getTotalPayloadSize()`, converting the thrown error into `callbacks.ifJointError(...)`.
- More generally, validate `earned_headers_commission_recipients` and reject non-finite/absurd numeric values *before* any size-length computation is performed on the raw unit, and ensure `objectLength.getLength()`/`getHeadersSize()` are never invoked on unvalidated, attacker-controlled substructures (e.g., `authors[].definition`) prior to their own structural validation.
- Consider hardening `network.js`'s `handleJoint`/`validation.validate` call sites with a top-level `try/catch` so a single malformed unit cannot crash the whole node even if a future helper function introduces a similar unguarded throw.

### Proof of Concept
1. Craft (or directly construct, bypassing the wallet composer) a unit JSON where:
   - `messages` is a valid non-empty array satisfying the earlier structural checks (so execution reaches line 257), and
   - `earned_headers_commission_recipients` = `[{"address": "<any base32 address>", "earned_headers_commission_share": 1e400}]`.
2. Broadcast this unit as a normal joint to a full node (e.g., via `network.js` WS `joint` message, or `POST /post_unit`-style API depending on version).
3. On the target node, `validation.validate()` reaches `objectLength.getHeadersSize(objUnit)` (`validation.js:257`), which internally calls `getLength()` (`object_length.js`) and throws `Error("invalid number: Infinity")` while walking `earned_headers_commission_recipients`.
4. This exception is not caught anywhere in the synchronous call stack and bubbles up to Node's `uncaughtException` handler in `network.js:4530-4543`, which re-throws, terminating the process.

*Note: I was unable to fully execute this PoC in a live environment (no code execution tools available in this session); the analysis is based on static tracing of the exact call chain and confirmed absence of try/catch guards and confirmed absence of prior validation of the relevant fields at the point of the vulnerable call. A Devin session with repository/runtime access would be needed to empirically confirm the crash with a live node instance.*
