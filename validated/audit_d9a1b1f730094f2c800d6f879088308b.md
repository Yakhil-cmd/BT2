### Title
Blind SSRF via attacker-controlled `arbiter_address`/arbstore URL in arbiter contract handling - (File: arbiters.js / arbiter_contract.js)

### Summary
The oxAuth bug (CVE-2022-36663) is a blind SSRF where an attacker-supplied URL parameter (`request_uri`) causes the server to make an outbound HTTP request to an attacker-chosen host with no destination validation. The analogous pattern in this repo is the arbiter-contract subsystem: a paired device (potentially the attacker, posing as an "arbiter") can cause a victim wallet to resolve an `arbiter_address` to a URL via the hub and then issue automatic outbound HTTP(S) requests to that URL, with no scheme/host allow-listing or SSRF protection.

### Finding Description
When a wallet receives an `arbiter_contract_offer` device message (built and sent in [1](#0-0) ), the message contains an attacker-controlled `arbiter_address`, which is persisted via `store()` [2](#0-1) . Later, whenever the wallet resolves arbiter/arbstore information for that contract (e.g. `getInfo`, `getArbstoreInfo`, `appeal`, `getAppealFee`), it queries the hub for a URL tied to the attacker-chosen `arbiter_address`: [3](#0-2) [4](#0-3) 

and then performs a raw, unvalidated outbound HTTP GET/POST to whatever URL string was returned: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

The only checks performed on the URL are `isNonemptyString(url)` [9](#0-8)  — there is no restriction on protocol, host, or destination (no block of `localhost`, private/link-local ranges such as `169.254.169.254`, non-HTTP(S) schemes, etc.). Because any device can register itself as an "arbiter" and set its own arbstore URL on the hub (the hub is untrusted infrastructure from the wallet's security-model perspective, and any peer can act as the counterparty proposing a contract naming a colluding/self arbiter address), a remote peer effectively controls a URL that the victim wallet will automatically fetch and parse as JSON once the victim interacts with the offered contract (viewing arbiter info, filing an appeal, or checking appeal fees). This is a direct parallel to the oxAuth `request_uri` SSRF: attacker-supplied data (indirectly, an address that maps to an attacker-controlled URL) drives an unauthenticated outbound HTTP fetch performed by the victim node.

The related `uri.js` `fetchUrl` path (triggered by `byteball:data?app=definition&definition=https://...`) is a similar unrestricted `https.get` [10](#0-9)  but requires local user interaction opening a crafted URI, so it is a weaker/less directly remote-reachable analog compared to the device-message-driven arbiter flow.

### Impact Explanation
This enables blind SSRF from the wallet process: an attacker (any paired device that proposes an arbiter contract naming a self-controlled or colluding "arbiter" address) can direct victim wallets to issue authenticated-looking HTTP requests to internal network addresses, cloud metadata endpoints, or other otherwise-unreachable services, and can use response timing/errors as an oracle for internal network reconnaissance. Because `requestInfoFromArbStore`/`httpRequest` parse the response body as JSON and feed selected fields (`device_pub_key`, `real_name`, `address`, `cut`) back into wallet database records and UI, a malicious response can also inject attacker-controlled data into the wallet's arbiter records used to compute payout addresses/cuts for arbitration outcomes — a data-integrity concern beyond pure SSRF. This falls under "wallet and contract message handling" impact.

### Likelihood Explanation
Likelihood is moderate: requires the victim to be a counterparty who accepts (or merely inspects) a contract offer that references an attacker-supplied `arbiter_address`, and requires the attacker to control what the hub returns for `hub/get_arbstore_url` for that address (achievable by the attacker registering their own arbiter listing via the hub, a routine, unprivileged action). No cryptographic or blockchain-level trust is being bypassed — this is purely off-chain device-message and hub-lookup plumbing with no destination validation, so exploitation only requires normal contract-negotiation flow, not any special node/hub compromise.

### Recommendation
- Validate arbstore URLs before making outbound requests: enforce `https:` scheme, disallow `localhost`, loopback, link-local (169.254.0.0/16), private RFC1918 ranges, and other non-routable addresses, similar to `isValidWsUrl` used elsewhere in `network.js` [11](#0-10) .
- Consider pinning/allow-listing known arbstore hosts rather than trusting hub-supplied URLs verbatim per arbitrary `arbiter_address`.
- Apply the same URL validation to `uri.js`'s `fetchUrl` definition-fetch path.

### Proof of Concept
1. Attacker device sends the victim an `arbiter_contract_offer` (via `device.sendMessageToDevice`, handled by wallet.js) naming `arbiter_address` = an address the attacker controls.
2. Attacker registers, via the shared hub, an `arbstore_url` for that address pointing to an internal/SSRF target (e.g. `http://169.254.169.254/latest/meta-data/` or an internal admin panel).
3. Victim wallet, when displaying/accepting the contract or checking appeal status, calls `arbiters.getInfo`/`getArbstoreInfo` or `arbiter_contract.appeal`/`getAppealFee`, which resolves the URL via `hub/get_arbstore_url` and issues an outbound HTTP request via `requestInfoFromArbStore`/`httpRequest` to the attacker-chosen target, with the response parsed and partially persisted — completing the blind SSRF.

Note: I could not directly confirm the exact wallet.js handler that dispatches the `arbiter_contract_offer` justsaying/message to `arbiter_contract.store()` (the search matched wallet.js but I was not able to retrieve those specific lines within available iterations), so the precise inbound dispatch code path should be verified directly in `wallet.js` if further confirmation is needed.

```javascript
function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
```

```javascript
function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}
```

```javascript
function fetchUrl(url, cb) {
	var https = require('https');
	var bDone = false;
	function returnError(err) {
		console.log(err);
		if (bDone)
			return;
		bDone = true;
		cb(err);
	}
	try {
		https.get(url, function (resp) {
			if (resp.statusCode !== 200)
				return returnError("non-200 response while trying to fetch " + url);
			var data = '';

			// A chunk of data has been recieved.
			resp.on('data', function(chunk) {
				data += chunk;
			});

			// aborted before the whole response has been received
			resp.on('aborted', function () {
				returnError("connection aborted while trying to fetch " + url);
			});

			// The whole response has been received
			resp.on('end', function () {
				if (bDone)
					return;
				bDone = true;
				cb(null, data);
			});
		}).on("error", function(err) {
			returnError("non-200 response while trying to fetch " + url + ": " + err.message);
		});
	}
	catch(err) {
		returnError(err.message);
	}
}
```

```javascript
function isValidWsUrl(url) {
	try {
		const { protocol, hash, username, password } = new URL(url);
		if (hash)
			return false;
		if (url.includes('#')) // empty trailing hash
			return false;
		if (username || password) // no legitimate peer url needs credentials
			return false;
		if (!['wss:', 'ws:'].includes(protocol))
			return false;
		if (conf.WS_PROTOCOL === 'wss://' && protocol !== 'wss:')
			return false;
		return true;
	}
	catch {
		return false;
	}
}
```
