### Title
Webhook signature verification authenticates `repository.owner.login`, but the handler pipeline resolves the target stack from the independent, unauthenticated `repository.full_name` field, allowing cross-tenant stack forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/repository.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks the `GitHubApp` (and its `webhook_secret`) to validate against using `params.dig('repository','owner','login')`, but every downstream handler (`ReopenedHandler`, `LabelCapturingHandler`, etc.) resolves the actual target repository/stack via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a completely separate, attacker-controlled JSON field. Nothing enforces that `repository.owner.login` and the owner segment of `repository.full_name` match, so an attacker can authenticate the request as their own (secret-less or attacker-controlled) org while pointing the payload at a victim's repository.

### Finding Description
The invariant the code should enforce is: `authenticated_owner == target_repository.owner`, i.e. `params.repository.owner.login == params.repository.full_name.split('/').first`. This is never checked.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to select the `GitHubApp` config: `Shipit.github(organization: repository_owner)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that organization, and even when a secret exists, only accepts the legacy `sha1=` prefix: `return true unless webhook_secret` / `return false unless algorithm == 'sha1'` [3](#0-2) .
- Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw, attacker-supplied JSON to handlers [4](#0-3) .
- `ReopenedHandler#repository` and `LabelCapturingHandler#repository` both resolve the target repository from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [5](#0-4) [6](#0-5) , which simply splits `owner/name` from the string and does a DB lookup with no cross-check against `repository.owner.login` [7](#0-6) .

Exploit flow: the attacker owns/controls an org whose Shipit config has no `webhook_secret` (or knows that secret). They send `POST /webhooks` with `X-Github-Event: pull_request`, `repository.owner.login = "attacker-org"`, but `repository.full_name = "victim-org/victim-repo"`, `action = "reopened"`, and forged `pull_request.labels`. `verify_signature` looks up `attacker-org`'s (secret-less) `GitHubApp`, trivially returns `verified = true`, and the request proceeds. `ReopenedHandler` and `LabelCapturingHandler` then resolve `victim-org/victim-repo` from the body and mutate the victim's `PullRequest`/`ReviewStack` — a payload authenticated for one repository mutates another's stack. Existing guards (`drop_unhandled_event`, `ExplicitParameters` schema, model validations on `Repository#owner`/`#name` format) only validate structure, not the owner/full_name consistency, so none of them block this.

### Impact Explanation
An attacker who controls only their own GitHub org/repo (no victim privileges, no secrets) can inject forged `pull_request` events that are attributed to and processed against an arbitrary victim repository's review stack, as long as they know or can guess the victim's `owner/name` string (public information). For a `continuous_deployment`-enabled victim stack, `LabelCapturingHandler` persists attacker-chosen label names onto the victim `PullRequest`, which `ReviewStack#env` turns into uppercased environment variables injected into deploy commands, and `ReopenedHandler` can unarchive/reactivate a stack. Combined with the stack's continuous delivery pipeline auto-shipping green commits, this constitutes an unauthorized mutation of another tenant's stack state — matching the Critical category "a payload for one repository mutating another's stack" and potentially enabling unauthorized deploy behavior through attacker-controlled environment variables.

### Likelihood Explanation
Preconditions: attacker needs (a) an org in Shipit's multi-org config with no `webhook_secret` set, or a secret they know (e.g., their own org, which they fully control), and (b) knowledge of the victim's `owner/name` public repo path. Both are attacker-cheap: they need no victim credentials, no GitHub App key, no session. The request is a single unauthenticated `POST /webhooks` and is fully repeatable against any victim repository whose name is known, making this a low-cost, highly repeatable cross-tenant forgery.

### Recommendation
In `Shipit::WebhooksController#verify_signature` (or earlier in the pipeline), enforce that the organization used to select the `webhook_secret`/`GitHubApp` matches the owner embedded in `params.repository.full_name` before dispatching to handlers; reject the request (422) on mismatch. Additionally, require `webhook_secret` to be mandatory for all configured organizations (remove the `return true unless webhook_secret` bypass) and support/require `X-Hub-Signature-256` (sha256) rather than only legacy sha1.

### Proof of Concept
minitest plan (under `test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Configure two orgs in test secrets: `attacker-org` with no `webhook_secret`, and `victim-org` with a `webhook_secret` set.
2. Create `victim-org/victim-repo` with `continuous_deployment: true`-eligible `Shipit::ReviewStack`/`Shipit::Stack` and an existing `PullRequest` fixture.
3. POST `/webhooks` with header `X-Github-Event: pull_request`, no or garbage `X-Hub-Signature`, and body: `{"action":"reopened","number":1,"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"pull_request":{...,"labels":[{"name":"malicious_env"}]},"sender":{"login":"attacker"}}`.
4. Assert response is `200`/`:ok` (not `422`), proving signature check passed via the secret-less `attacker-org` path.
5. Assert `victim_repo.review_stacks.find_by(environment: "pr1").pull_request.labels` now includes `"malicious_env"` — proving the victim stack (authenticated by nobody's real secret) was mutated by a request that never proved knowledge of `victim-org`'s `webhook_secret`.
6. Equality check: before, `repository.owner.login ("attacker-org") != full_name.owner ("victim-org")` yet the request succeeded — the binding `authenticated_owner == target_repository.owner` is violated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
