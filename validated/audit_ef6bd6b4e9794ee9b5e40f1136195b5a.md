### Title
Webhook signature verification authenticates the wrong organization, allowing cross-organization Status/PR/push forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check *based on a field read from the same untrusted payload it is verifying*, and never confirms that the org whose secret validated the signature actually owns the repository the payload claims to act on. In a multi-organization Shipit deployment, this breaks the binding "organization that authenticated == repository that is written": a party holding a valid webhook secret for Org A can forge a payload whose `repository.full_name` points at a stack belonging to Org B, and Shipit will process it as legitimate.

### Finding Description
`verify_signature` picks the GitHub App/secret to verify against using `repository_owner`, which is read straight out of the JSON body being verified: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a *per-organization* config/secret (this is the documented multi-org setup, e.g. `somegithuborg` / `someothergithuborg`): [3](#0-2) [4](#0-3) 

Once the HMAC check passes against the secret picked from `repository.owner.login` (or the `organization.login` fallback), the whole raw payload is handed to the event handlers, which instead key everything off `repository.full_name`: [5](#0-4) 

`repository.owner.login` and `repository.full_name` are two independent, attacker-controlled fields inside the same JSON body. Nothing ties the org whose secret validated the signature to the org that `repository.full_name` actually belongs to. Because the HMAC only proves "this body was signed with Org A's secret," not "Org A's data is confined to Org A's repos," anyone who legitimately possesses Org A's `webhook_secret` (e.g., an admin of Org A's own GitHub App settings, or anyone who leaked/holds that one org's secret in a shared Shipit instance) can put `repository.owner.login: "OrgA"` (to pass signature selection) while setting `repository.full_name: "OrgB/some-tracked-repo"` (to control which Shipit stack is acted upon).

The most damaging handler reachable this way is `StatusHandler`, which builds a `Status` record directly from attacker-supplied fields with no independent GitHub API confirmation: [6](#0-5) [7](#0-6) 

`Status` creation triggers `schedule_continuous_delivery` and feeds `StatusChecker`/`MergeRequest#reject_unless_mergeable!`, which gate automatic deploys and the merge queue: [8](#0-7) [9](#0-8) [10](#0-9) 

`PushHandler` similarly resolves stacks purely from `repository.full_name` and enqueues sync/deploy scheduling for that stack, with no cross-check against the org that authenticated the request: [11](#0-10) 

### Impact Explanation
An attacker who is a legitimate webhook secret holder for one organization configured on a shared, multi-org Shipit instance can forge fabricated commit `Status` events (arbitrary `state`, `context`, `description`) for commits belonging to a completely different organization's stack. This can satisfy `ci.require`/`merge.require` checks, unblock `reject_unless_mergeable!`, and trigger the merge queue or continuous-delivery path — resulting in an **unauthorized deploy or merge** on a repository the attacker was never authenticated against. This matches the Critical impact category ("an unauthorized deploy, rollback or merge") because the org that authenticated the signature is not the org whose repository state gets mutated.

### Likelihood Explanation
Requires the target Shipit instance to run the multi-organization GitHub config (explicitly documented as a supported setup) and requires the attacker to hold a valid `webhook_secret` for *any one* of the configured organizations — not the target org. Given that webhook secrets are typically set/known by org admins of the GitHub App and are not scoped to prevent cross-use inside Shipit, this is plausible in any deployment onboarding multiple orgs, matching the report's "unprivileged/wrong-scope attacker breaking a trust binding" class.

### Recommendation
After successfully verifying the signature against Org A's secret, `WebhooksController` (or the handler base class) must also verify that `repository.owner.login`/`organization.login` used to select the verification secret matches the actual owner of `repository.full_name` used for stack resolution, rejecting payloads where these disagree. Equivalently, resolve the target `Stack`/`Repository` first, derive the authenticating organization strictly from that repository's known owner (not from attacker-supplied fields), and verify the signature against that organization's secret only.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub config containing `orgA` (attacker-controlled webhook secret) and `orgB` (victim org, tracked stack `orgB/prod-repo`).
2. Attacker computes `sha1=HMAC(orgA_webhook_secret, body)` over a crafted `status` event body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/circle",
  "repository": { "full_name": "orgB/prod-repo", "owner": { "login": "orgA" } }
}
```
3. POST to `/webhooks` with header `X-Hub-Signature: sha1=<computed>` and `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` resolves commits by `sha` (global, not org-scoped) and calls `commit.create_status_from_github!(params)` with attacker-chosen `state`/`context`, injecting a fabricated "success" CI status for `orgB`'s commit despite the attacker never holding `orgB`'s webhook credentials.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
```

```ruby
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
```
