Webhook signature verified against attacker-controlled organization while payload's `repository.full_name` is used to select the write target - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, derived from the payload field `repository.owner.login` (or `organization.login`) [3](#0-2) [2](#0-1) . Once the signature passes, the event handlers resolve the actual `Repository`/`Stack` to act on using a *different* payload field, `repository.full_name` [4](#0-3) , via `Repository.from_github_repo_name` which splits it into `owner/name` and does a plain DB lookup with no cross-check against `repository.owner.login` [5](#0-4) . Nothing enforces that the organization whose secret validated the signature is the same organization/repository the handler subsequently writes to.

### Finding Description
This is directly analogous to the reported bug class: a field that is *used* to decide behavior (`repository.full_name`, driving DB writes and stack selection) is never *covered* by the field that is actually verified/bound (`repository.owner.login`, which only selects which secret validates the raw byte-signature). The signature covers the raw request bytes, but the *authorization decision* ("which org's secret must this event pass under, to be trusted for which repo") is made from an unrelated, independently-attacker-controlled subfield of the same unsigned-until-verified JSON body.

In a multi-org Shipit deployment (a documented, supported configuration, `docs/setup.md`, where each GitHub org has its own `webhook_secret`), an attacker who is a legitimate GitHub App/webhook administrator of their *own* organization ("Org A") — an unprivileged actor with respect to any other org managed by the same Shipit instance — knows Org A's `webhook_secret`. They can freely craft any JSON body and self-sign it with Org A's secret, then set `repository.owner.login` to `"org-a"` (so `verify_signature` selects and matches against Org A's secret) while setting `repository.full_name` to `"victim-org/victim-repo"` (so the handler resolves and writes to the victim's `Stack`/`Repository`/`Commit` records) [2](#0-1) [6](#0-5) .

This lets the attacker drive any registered `Webhooks` handler (`status`, `push`, `check_suite`, `pull_request/*`, `membership`) against a victim organization's stack despite never having any credential, repository access, or trust relationship with that organization. For example, the `status` handler creates a `CommitStatus` row for an arbitrary `sha`/`state`/`context` tied to whatever commit the attacker names in the victim repo (confirmed by `test/controllers/webhooks_controller_test.rb:42-59`, which shows a status webhook creating `commit.statuses` directly from payload fields) [7](#0-6) . Since Shipit stacks commonly gate deploy readiness on required commit statuses/checks, forging a passing status on a victim commit can flip that commit into a deployable state and enable an unauthorized deploy.

### Impact Explanation
Falsifying commit status/check state for a victim organization's stack, or otherwise mutating victim `Stack`/`Repository` state, via a signature that was only ever validated against the attacker's own (unrelated) organization's secret, is a cross-repository/cross-organization write that can be leveraged into an unauthorized deploy — matching the Critical impact bucket ("cross-repository writes" / "an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the Shipit instance to be configured in multi-org mode (a first-class, documented feature) and requires the attacker to control (or be an admin of) at least one org registered on that same Shipit instance — a realistic scenario for shared/hosted Shipit deployments serving multiple orgs/teams. No access to the victim org, no `ApiClient` token, and no privileged Shipit account are required.

### Recommendation
In `WebhooksController#verify_signature`, after selecting `github_app` by `repository_owner`, re-validate that the same owner is consistent with every repository-owner-bearing field actually used by the handlers (in particular `repository.full_name`'s owner segment) before dispatching to `Shipit::Webhooks.for_event(event)`. Alternatively, bind the resolved `Repository`/`Stack` lookup in `Handler#stacks` to the same organization identity that was used to select and validate the webhook secret, rejecting events where they diverge.

### Proof of Concept
1. Attacker is the GitHub org admin for `org-a`, which is registered in the target Shipit instance's multi-org `github:` config with `webhook_secret: SECRET_A` (a secret only `org-a`'s admin should know, per docs/setup.md multi-org example).
2. Attacker crafts a `status` (or `push`/`pull_request`) webhook JSON payload where:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `sha`, `state = "success"`, `context`, `target_url` set to values matching a real commit on `victim-org/victim-repo`'s tracked stack.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(SECRET_A, raw_body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully against `SECRET_A` [8](#0-7) [9](#0-8) .
5. The `status` handler resolves `Repository.from_github_repo_name("victim-org/victim-repo")` from the `full_name` field and writes a forged `CommitStatus` onto the victim's commit [4](#0-3) [5](#0-4) , despite the signature never having been checked against any secret belonging to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
