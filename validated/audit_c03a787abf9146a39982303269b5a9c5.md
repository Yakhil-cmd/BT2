## Analog Found

### Title
Unhandled Exception (Missing Default Parameter) in `isTooBigObj()` Crashes AA Formula Evaluation on `json_parse` - (File: formula/evaluation.js / string_utils.js)

### Summary
The reported Newtonsoft.Json CWE-755 issue is about improper handling of exceptional conditions when processing deeply nested/oversized JSON, leading to unhandled exceptions and DoS. Ocore has an analogous "improper handling of exceptional condition" bug in the `json_parse()` oscript function: the size-guard helper `isTooBigObj()` is called without its required options argument, so it throws an uncaught `TypeError` instead of gracefully rejecting oversized/nested JSON.

### Finding Description
`isTooBigObj` is declared with a destructured second parameter that has no fallback default object: [1](#0-0) 

If called with only one argument, destructuring `undefined` throws `TypeError: Cannot destructure property 'depthLimit' of 'undefined' as it is undefined`, before any of the internal `depthLimit`/`nodesLimit`/`lengthLimit` defaults can apply.

This is exactly how it is invoked from the `json_parse` opcode handler in the oscript/AA formula evaluator, right after a successful `JSON.parse`: [2](#0-1) 

The `try/catch` in this block only wraps `JSON.parse(res)`; it does not wrap the subsequent `isTooBigObj(json)` call. Any AA trigger sender can supply a `data` payload whose `json_parse('...')` argument decodes to an object (e.g. `{"a":1}`), reaching `isTooBigObj(json)` with a single argument and triggering the uncaught `TypeError`, which propagates synchronously out of the `evaluate()` continuation used throughout `formula/evaluation.js`.

This mirrors the external report's root cause pattern: a code path meant to *reject* oversized/nested untrusted input instead throws an unhandled exception because of an implementation defect in the guard itself, rather than failing safely.

### Impact Explanation
`json_parse` is a documented oscript function usable in any AA formula (getters, triggers, state updates). Because the guard throws instead of returning a controlled `setFatalError`, evaluation of the AA response for that trigger can abort with an uncaught exception instead of a normal formula-level failure. Since AA response evaluation must be deterministic across all full nodes that compose/validate the AA response, an uncaught exception at this point risks either crashing the node process handling AA triggers or producing inconsistent behavior between the node that composed the response (which may or may not catch the error at some outer layer) and nodes that later validate it — this falls into the "node disagreement on validity" / "network unable to confirm new units" impact classes.

### Likelihood Explanation
The trigger is trivial: any unprivileged user can post a payment to an AA whose formula contains `json_parse(trigger.data.x)` (or any AA author can define such a getter/trigger-processing formula), and any external party can post a trigger unit with a `data` field that, once parsed, is a JSON object. No special privileges, race conditions, or large payloads are required — a minimal object like `{"a":1}` suffices to hit the `typeof json === 'object'` branch and invoke the broken guard.

### Recommendation
Give the second parameter of `isTooBigObj` a default empty object (e.g. `function isTooBigObj(obj, { depthLimit = 100, nodesLimit = 10000, lengthLimit = 1000000 } = {})`), or always pass an explicit options object at every call site in `formula/evaluation.js`. Additionally, wrap the `isTooBigObj` call (and the rest of the `json_parse` post-processing) in the same `try/catch` that already guards `JSON.parse`, so any unexpected exception degrades to `cb(false)`/`setFatalError` rather than propagating uncaught.

### Proof of Concept
1. Define/use an AA whose formula evaluates `json_parse('{"a":1}')` on attacker-controlled trigger data, e.g. `json_parse(trigger.data.x)`.
2. Send a trigger unit to the AA with `data: { x: '{"a":1}' }`.
3. During formula evaluation, `formula/evaluation.js` reaches the `json_parse` case, successfully parses the string into an object, and calls `isTooBigObj(json)` with only one argument. [3](#0-2) 
4. `string_utils.js`'s `isTooBigObj` attempts to destructure its missing second argument and throws `TypeError`, which is not caught by the surrounding `try/catch` (that only wraps `JSON.parse`), propagating out of the evaluation pipeline.
