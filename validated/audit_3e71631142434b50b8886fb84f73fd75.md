### Title
Floating-point precision loss (integer-overflow analog) in asset denomination cap validation allows a fake "cap" to be accepted for a fixed-denominations asset - ([File: validation.js])

### Summary
`validateAssetDefinition()` accumulates `total_cap_from_denominations` by multiplying two attacker-controlled integers, `denomInfo.count_coins` and `denomInfo.denomination`, without ever bounding `count_coins` and while `denomination` is only bounded to `MAX_CAP` (9e15). Because JavaScript numbers are IEEE-754 doubles with 53 bits of integer precision (`Number.MAX_SAFE_INTEGER = 9007199254740991`), this multiplication/accumulation can silently lose precision once the true product exceeds `2^53-1`, exactly the "unchecked size multiplication" root cause class described in CVE-2016-5139 (`opj_tcd_init_tile` multiplying tile dimensions without overflow checks). Here the attacker is any unprivileged asset issuer (or AA issuing a nested asset), not a malicious peer/hub, so it is in-scope.

### Finding Description
In `validateAssetDefinition`, for a `fixed_denominations` asset: [1](#0-0) 
```
for (var i=0; i<payload.denominations.length; i++){
    var denomInfo = payload.denominations[i];
    ...

    if (denomInfo.denomination > constants.MAX_CAP && (...))

``` [2](#0-1) 

* `denomInfo.denomination` is bounded to `constants.MAX_CAP = 9e15` [3](#0-2) .
* `denomInfo.count_coins` is validated only with `isPositiveInteger`, i.e. it is a positive integer with **no upper bound whatsoever** — unlike `cap` itself, which is explicitly capped: `if ("cap" in payload && !(isPositiveInteger(payload.cap) && payload.cap <= constants.MAX_CAP))` [4](#0-3) .
* The product `denomInfo.count_coins * denomInfo.denomination` and the running sum `total_cap_from_denominations` are plain JS numbers, so once the true mathematical value exceeds `Number.MAX_SAFE_INTEGER` (≈9.007e15), the stored result silently rounds to the nearest representable double — the JS/double analog of a C integer overflow, since there is no explicit finiteness/precision check anywhere in this loop (contrast with other places in the codebase that do check, e.g. `isFiniteDecimal` calls in `formula/evaluation.js`).
* The final consistency check is a strict equality: `if (total_cap_from_denominations && payload.cap !== total_cap_from_denominations) return callback("cap doesn't match sum of denominations");` [5](#0-4) . Because the accumulated sum is the rounded/imprecise floating value rather than the true sum of `count_coins × denomination` across all denomination buckets, an attacker can pick `payload.cap` equal to the rounded double so the check passes even though the true combinatorial maximum issuable supply for the declared denominations is different from (and can exceed) the nominal `cap` that downstream consumers (wallets, exchanges, AAs) treat as the enforced supply ceiling for the asset.
* This validation path is reached from an ordinary `asset` message posted by any unprivileged unit author (`validatePayment` → `validateAssetDefinition`) [6](#0-5) , and similarly from AA-authored nested asset definitions via `aa_validation.js`'s `asset` case, which performs the same style of `cap` bound-checking without an equivalent guard on the interplay with denomination `count_coins` products [7](#0-6) .

### Impact Explanation
`cap` is the invariant the rest of the protocol and all downstream tooling rely on as the hard ceiling on total token supply for a fixed-denomination, capped asset. A precision-loss induced mismatch between the declared `cap` and the real maximum obtainable supply from the declared denominations breaks that invariant at definition time. Nodes will accept an asset definition whose `cap` field does not actually correspond to the sum of `count_coins * denomination`, i.e. a state where the protocol-level "supply cannot exceed cap" guarantee is violated by construction — a supply-inflation-class bug, not merely cosmetic, since asset consumers (exchanges, AAs, wallets) make trust and accounting decisions based on `cap`.

### Likelihood Explanation
Any unprivileged account can author an `asset` message (or have an AA define a nested asset) with `fixed_denominations: true` and craft a `denominations` array with values near `MAX_CAP` and an oversized `count_coins`, then compute the resulting JS double sum offline and supply it as `cap`. No special privileges, timing, or race conditions are required — this is a straightforward, deterministic validation-logic flaw reachable by a single posted unit.

### Recommendation
Perform the denomination cap-sum arithmetic using an overflow-safe integer type (e.g. BigInt or the existing `Decimal` library already used elsewhere in the codebase for financial-precision math, as seen in `formula/evaluation.js`), reject any `count_coins`/`denomination` product or running sum that exceeds `constants.MAX_CAP`/`Number.MAX_SAFE_INTEGER`, and add an explicit upper bound on `denomInfo.count_coins` (analogous to the existing `payload.cap <= constants.MAX_CAP` check) rather than relying solely on `isPositiveInteger`.

### Proof of Concept
1. Craft an `asset` message with `fixed_denominations: true` and `denominations`: e.g. `[{ denomination: 9007199254740992, count_coins: 2 }]` (or any combination whose true product exceeds `Number.MAX_SAFE_INTEGER`).
2. Compute `total = denomination * count_coins` in Node.js (observe the returned double is a rounded approximation of the true mathematical product due to IEEE-754 precision limits).
3. Set `payload.cap` to that rounded double value.
4. Submit the unit; `validateAssetDefinition` accepts it because `payload.cap === total_cap_from_denominations` holds under floating-point rounding, even though the actual maximum coin supply implied by `count_coins`/`denomination` differs from the declared `cap`.

Note: I could not fully trace every downstream consumer of `objAsset.cap` for fixed-denomination assets (e.g., exact wallet/exchange trust logic) within the indexed portion of the repository; a full Devin session with complete file access would be needed to enumerate all places that rely on `cap` as a hard supply invariant to precisely quantify exploitability magnitude.
