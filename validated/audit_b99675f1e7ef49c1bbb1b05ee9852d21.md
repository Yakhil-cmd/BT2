### Title
CCMenuController never scopes `stack` lookup to `current_api_client.stack_id`, and CCMenuUrlController mints a global (unscoped) `read:stack` client — (File: `app/controllers/shipit/api/ccmenu_controller.rb`, `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
`CCMenuController` overrides `BaseController#stack` with a version that looks up `Stack.from_param!(params[:stack_id])` directly, discarding the `current_api_client.stack_id` scoping that `BaseController#stacks`/`#stack` normally enforce. Independently, `CCMenuUrlController#client` creates the `ApiClient` used for the CC.xml URL without ever setting `stack:`, so the resulting token authenticates as a client with global `read:stack` permission. Either defect alone is sufficient for a token legitimately issued for one stack to read `cc.xml` for any other stack.

### Finding Description
The binding that should hold is:
`current_api_client.stack_id == stack.id` (or `current_api_client.stack_id.nil?` only for clients intentionally granted global access) must be true before `CCMenuController#show` renders `cc.xml` for `params[:stack_id]`.

In `BaseController`, this binding is enforced generically: [1](#0-0) 
`stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` calls `stacks.from_param!(...)` on top of that restricted relation.

`CCMenuController`, however, overrides `stack` and bypasses this scoping entirely: [2](#0-1) 
`def stack; @stack ||= Stack.from_param!(params[:stack_id]); end` performs a global lookup independent of `current_api_client.stack_id`. The only guard left is `require_permission :read, :stack`, which merely checks that the string `read:stack` is present in `current_api_client.permissions` — it never compares `current_api_client.stack_id` to the requested stack: [3](#0-2) [4](#0-3) 

Compounding this, `CCMenuUrlController#fetch` (reached via `GET /ccmenu/*stack_id`, session-authenticated) creates the token-bearing `ApiClient` without ever assigning it a `stack`: [5](#0-4) 
`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — the lookup/creation keys are only `creator` and `name`; `stack` is never part of the `find_or_create_by!` criteria nor assigned afterward. The `ApiClient` model confirms `stack` is optional: [6](#0-5) 
Fixtures confirm the model supports scoping a client to a `stack:` (`here_come_the_walrus` does), which shows this is a real, intentional feature that `CCMenuUrlController` fails to use, and that `CCMenuController` fails to enforce even when it is used.

`ApiClient.message_verifier`/`authenticate` (`Shipit::SimpleMessageVerifier` over `Shipit.api_clients_secret`) only signs/verifies the numeric primary key: [7](#0-6) [8](#0-7) 
This confirms sibling `ApiClient` rows do differ only by an incrementing id in the signed payload, but that fact is irrelevant to the exploit: no brute force of ids is needed, because the attacker's own legitimately-issued, correctly-signed token already carries no `stack_id` binding that `CCMenuController` checks.

Attacker flow (no privileges beyond owning/maintaining stack A, which any authenticated Shipit user can do for their own stack):
1. Attacker is logged in and calls `GET /ccmenu/*stack_id` (`stack_id` = their own stack A) → `CCMenuUrlController#fetch` returns a `ccmenu_url` containing `token=<sig>` for a client with `permissions: ['read:stack']` and no `stack_id`.
2. Attacker replays that exact token against `GET /api/stacks/*stack_id/ccmenu?token=<sig>` with `stack_id` = stack B (any other stack, owned by a different repository/team).
3. `CCMenuController#authenticate_api_client` verifies the token and finds the `ApiClient` (valid signature, valid id) — succeeds regardless of stack.
4. `require_permission :read, :stack` passes because permission is `read:stack` (no per-stack check).
5. `stack` resolves `Stack.from_param!(params[:stack_id])` for stack B directly, with no comparison to the client's `stack_id`.
6. `show` renders `cc.xml` for stack B, exposing that stack's `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` to the attacker — cross-tenant unauthenticated read of stack state.

No existing guard intercepts this: `require_permission!` only checks the permission string set, not scope; `stacks`/`from_param!` scoping is bypassed by the controller-specific override; `ApiClient.authenticate` only validates the HMAC signature and row existence, not stack ownership.

### Impact Explanation
An attacker with legitimate access to one stack can read build/deploy state (`activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of any other stack in the same Shipit instance, using only a token they already legitimately hold — a single request, no brute force, fully repeatable against every stack id in the system. This is an unauthenticated (cross-scope) read of stack state, matching the High severity category ("unauthenticated read of stack state ... across tenants"). The blast radius is every stack managed by the same Shipit deployment.

### Likelihood Explanation
Preconditions are trivial: the attacker only needs to be a normal Shipit user who owns or is permitted to fetch the CCMenu URL for at least one stack (a self-service, unprivileged action reachable via the stack settings page). No secrets (`api_clients_secret`, `secret_key_base`, GitHub tokens) are needed. The attack is a single, deterministic HTTP GET replaying an already-issued token against a different `stack_id` — cost is negligible and fully repeatable.

### Recommendation
- In `CCMenuController`, remove the `stack` override or reimplement it to reuse `BaseController`'s `stacks` scoping (`stacks.from_param!(params[:stack_id])`) so a stack-scoped `ApiClient` cannot read any stack other than the one it's bound to.
- In `CCMenuUrlController#client`, pass `stack:` into the `find_or_create_by!`/`create_with` criteria so the CCMenu client is created (and looked up) per-stack, e.g. `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`.
- Add an explicit check in `CCMenuController#show`/`stack` that `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`.

### Proof of Concept
minitest plan (extends `test/controllers/api/ccmenu_controller_test.rb`):

```ruby
test "a token scoped to one stack must not authenticate a different stack's cc.xml" do
  other_stack = shipit_stacks(:shipit_canaries) # stack != @stack

  # legitimately obtained, stack-scoped client (mirrors here_come_the_walrus fixture / CCMenuUrlController intent)
  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'CCMenu Client',
    stack: @stack,
    permissions: %w[read:stack]
  )

  # binding under test, BEFORE the request
  assert_equal @stack.id, scoped_client.stack_id
  refute_equal other_stack.id, scoped_client.stack_id

  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

  # binding under test, AFTER the request: must be rejected, but currently succeeds
  assert_response :not_found # or :forbidden — desired behavior
  # current (buggy) behavior: assert_response :ok, and body contains other_stack.to_param
end
```

This test currently fails (returns `:ok` with `other_stack`'s data) because `CCMenuController#stack` never checks `current_api_client.stack_id`, proving the scope check is entirely absent, independent of whether `CCMenuUrlController` is fixed to set `stack:` on client creation.

module Shipit
  class SimpleMessageVerifier < ActiveSupport::MessageVerifier
    def initialize(secret, **options)
      options[:serializer] ||= ToS
      super(secret, **options)
    end

    private

    def encode(data)
      data.to_s
    end

    def decode(data)
      data
    end

    module ToS
      def self.dump(object)
        object.to_s
      end

      def self.load(payload)
        payload
      end
    end
  end
