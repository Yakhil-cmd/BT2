### Title
`StatusHandler#process` has no repository-scoping equality that `Commit#refresh_statuses!` structurally guarantees - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Commit#refresh_statuses!` always fetches statuses using `stack.github_api.statuses(github_repo_name, sha, ...)`, i.e. it is structurally bound to `commit.stack`'s own `github_repo_name` and cannot cross tenants. `StatusHandler#process`, which is invoked from the unauthenticated `POST /webhooks` endpoint for GitHub `status` events, instead does a global `Commit.where(sha: params.sha)` lookup with no equivalent binding to `payload['repository']['full_name']`, allowing any commit sharing that sha in any stack/tenant to be updated.

### Finding Description
The binding that should hold, mirroring `refresh_statuses!`, is: `commit.stack.github_repo_name == params.repository.full_name` for every commit mutated by the handler.

- `Commit#refresh_statuses!` (`app/models/shipit/commit.rb:156-163`) calls `stack.github_api.statuses(github_repo_name, sha, per_page: 100)`, where `github_repo_name` delegates to `commit.stack`'s own repository name. Every status pulled is attributed to the commit's own stack's repo — the API call itself enforces the equality, so cross-tenant contamination is structurally impossible.
` [1](#0-0) `

- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This is a **global** lookup by `sha` across the entire `commits` table, spanning every stack/tenant. There is no comparison against `payload['repository']['full_name']` or `commit.stack.github_repo_name` anywhere in this method.
` [2](#0-1) `

Contrast with the sibling `PushHandler`, which *does* scope through the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name).stacks`) before acting:
` [3](#0-2) `
` [4](#0-3) `
`StatusHandler` never calls `stacks` or `repository_name` — it bypasses the only scoping mechanism the base `Handler` class provides.

Existing guards do not close this gap: `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the webhook came from the GitHub org/repo identified by `repository_owner` in the payload — it authenticates *who sent the webhook*, not *which commits the payload is allowed to affect*. Since sha values are git content hashes, any repository sharing history with a tracked repo (e.g., a public fork the attacker controls, or simply a coincidentally/attacker-crafted matching sha for a short/ambiguous case) can trigger a webhook that is validly signed for the attacker's own repo/org but whose `sha` collides with a commit belonging to a different stack.

### Impact Explanation
An attacker who owns a repository (and thus its own valid webhook secret) can send a `status` event whose `sha` matches a commit tracked under a completely different stack/tenant. `StatusHandler#process` will locate that commit via the global `Commit.where(sha: ...)` scan and call `create_status_from_github!`, writing a forged CI status (`state`, `context`, `description`, `target_url`) onto that foreign commit. Since commit status transitions can trigger deploy-relevant behavior (continuous deployment triggers, merge-queue unblocking, `deployable?`/`blocked?` checks), this is a payload for one repository mutating another stack's commit/CI state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any commit sha the attacker can produce a webhook for.

### Likelihood Explanation
Preconditions: the attacker needs a GitHub repository they control (to receive a validly signed webhook) and a target commit sha tracked in another Shipit stack that they can also cause to exist/collide in their own repo's history (e.g., via forking a public upstream repo that Shipit also tracks, which is a very low-cost, common scenario). No Shipit credentials, session, or API token are required — signature verification is scoped to the attacker's own org, not the target stack's repo.

### Recommendation
In `StatusHandler#process`, scope the lookup to the commits belonging to stacks whose `github_repo_name` matches `payload['repository']['full_name']`, mirroring the binding `refresh_statuses!` enforces structurally, e.g. `stacks.commits.where(sha: params.sha)` (using the base `Handler#stacks` helper) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/commits_test.rb (differential control)
test "refresh_statuses! only ever calls github_api.statuses with commit.stack's own github_repo_name" do
  Shipit.github.api.expects(:statuses)
    .with(@stack.github_repo_name, @commit.sha, per_page: 100)
    .returns([])
  @commit.refresh_statuses!
end

# test/models/shipit/webhooks/handlers/status_handler_test.rb (contrast)
test "StatusHandler#process has no equivalent repository binding and mutates a commit in a different stack" do
  victim_commit = shipit_commits(:first) # belongs to stack A, github_repo_name = "shopify/shipit"
  other_stack   = shipit_stacks(:cyclimse) # a different tenant/repo

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'forged',
    'repository' => { 'full_name' => other_stack.github_repo_name }, # attacker's own repo
    'branches' => [{ 'name' => other_stack.branch }]
  }

  assert_not_equal victim_commit.stack.github_repo_name, payload['repository']['full_name']

  assert_difference '-> { victim_commit.statuses.count }', 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # proves victim_commit (belonging to a different repo than payload['repository']['full_name'])
  # was mutated -- no equality check exists in StatusHandler#process
end
```
