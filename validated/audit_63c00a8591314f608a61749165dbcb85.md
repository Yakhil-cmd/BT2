### Title
Unhandled Crypto Exception on Malformed Encrypted Device Package Crashes the Node - ([File: device.js])

### Summary
`device.js`'s `decryptPackage()` parses attacker/peer-controlled fields (`iv`, `authtag`, `encrypted_message`, `dh.*`) from an incoming device message and feeds them directly into Node's crypto primitives without a surrounding `try/catch` around the setup calls, while the process-wide handler in `network.js` deliberately re-throws any uncaught exception to kill the whole node. This mirrors the CVE-2019-13113 bug class: a crafted, structurally-invalid payload reaches a low-level parser that assumes well-formed input, triggering a hard crash (there, an `assert()`; here, a synchronous `throw` from Node's crypto bindings) instead of a graceful validation failure.

### Finding Description
`decryptPackage()` builds the decipher directly from base64-decoded fields supplied in the encrypted package object: [1](#0-0) 

Unlike the `decipher.final()` call a few lines below, which is wrapped in `try { ... } catch(e) { ... }`: [2](#0-1) 

the calls `crypto.createDecipheriv('aes-128-gcm', shared_secret, iv)` and `decipher.setAuthTag(authtag)` are **not** guarded by any `try/catch`. Node's `createDecipheriv` synchronously throws (e.g. `RangeError: Invalid IV length`) if the `iv` field decodes to a buffer whose length isn't the 12 bytes required for AES-128-GCM, and `setAuthTag` similarly throws on a malformed tag length. Since `objEncryptedPackage.iv` and `.authtag` are only checked for `typeof === 'string'` before being base64-decoded (no length validation): [3](#0-2) 

a peer/paired device can send an `iv` or `authtag` string that decodes to the wrong byte length, causing an uncaught synchronous exception inside `decryptPackage()`.

Any exception that escapes to the top level is intentionally fatal for the whole process: [4](#0-3) 

This handler explicitly re-throws ("crash the process to avoid ending up in an inconsistent state"), meaning any unguarded parser exception anywhere in message handling brings down the entire node — not just the connection/peer that sent the bad data.

### Impact Explanation
A single malformed encrypted device/hub message (reachable via the wallet/device message-handling paths that call `decryptPackage`, e.g. via `wallet.js`) can crash the node's process entirely, per the deliberate crash-on-uncaughtException policy in `network.js`. This is a denial-of-service against a node: the network becomes unable to process new messages/units until it is manually restarted, directly matching the "network unable to confirm new units" criterion for impact, and is analogous to the exiv2 crash-via-malformed-input class in the source CVE.

### Likelihood Explanation
Likelihood is high for any actor who can send a device-encrypted package to a target node (e.g., a paired device, hub-relayed correspondent, or textcoin/private-payment flow that invokes `decryptPackage`). The attacker only needs to supply `iv`/`authtag` fields of an incorrect decoded byte length; no cryptographic material or valid key needs to be guessed because the crash occurs during decipher setup, before any authentication check succeeds.

### Recommendation
Wrap the `crypto.createDecipheriv(...)` / `decipher.setAuthTag(...)` calls in `decryptPackage()` in a `try/catch` (as already done for `decipher.final()`), and additionally validate that `iv` decodes to exactly 12 bytes and `authtag` decodes to exactly 16 bytes before use, returning `null`/logging on failure instead of throwing. More generally, review other unguarded crypto/parsing calls invoked from attacker-reachable message paths, since the global `uncaughtException` handler converts any such oversight into a full-node crash.

### Proof of Concept
1. Establish a paired-device/hub relationship (or intercept the encrypted-package flow) so that a crafted JSON object reaches `decryptPackage()`.
2. Send an `objEncryptedPackage` with valid-looking `dh.sender_ephemeral_pubkey`/`dh.recipient_ephemeral_pubkey` (matching one of the node's known keys) but an `iv` field that base64-decodes to fewer or more than 12 bytes (e.g., `iv: Buffer.alloc(4).toString('base64')`).
3. `crypto.createDecipheriv('aes-128-gcm', shared_secret, iv)` throws `RangeError: Invalid IV length` synchronously, uncaught by `decryptPackage()`.
4. The exception propagates to `process.on('uncaughtException', ...)` in `network.js`, which re-throws it, terminating the node process.

Note: I could not fully trace, within the available tool budget, every call site of `decryptPackage()` in `network.js`/`wallet.js` to confirm the absolute absence of any outer `try/catch` around the entire message-handling chain; this should be verified by a Devin session with full file access before treating this as conclusively exploitable end-to-end.
