### Title
Webhook signature verification is bound to the payload's `repository.owner.login`/`organization.login`, but event processing is bound to unrelated fields (`repository.full_name` or bare `sha`) — allowing cross-organization/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body. [1](#0-0) [2](#0-1)  Once "verified", the actual event handlers select the target `Stack`/`Commit` using a completely different, independently-controlled field of the same payload — `repository.full_name` in most handlers, or just `sha` in `StatusHandler`, with no cross-check against the field used for signature/org selection. [3](#0-2) [4](#0-3)  This breaks the intended binding "organization authenticated == repository being written," analogous to the `ChainlinkOracle` report's pattern of trusting a field that is not covered by the actual verification.

### Finding Description
`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever no `webhook_secret` is configured for the organization being checked:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [5](#0-4) 

`webhook_secret` is documented as optional per configured GitHub App/organization, and Shipit explicitly supports multiple independent GitHub organizations, each with its own app config (`app_id`, `installation_id`, `webhook_secret`, etc.), selected dynamically via `Shipit.github(organization:)`. [6](#0-5) 

`WebhooksController#verify_signature` picks the organization used for verification straight from the attacker-supplied JSON body, before any signature has been validated:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

Meanwhile, the field that actually determines *which stack/commit is mutated* is unrelated:
- The base `Handler` class (used by `PushHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the target repository from `repository.full_name`, not `repository.owner.login`. [3](#0-2) 
- `StatusHandler` doesn't scope by repository/organization at all — it matches purely on `sha` across the entire `Commit` table and writes an attacker-controlled `state`/`context`/`description`/`target_url` as a real status:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

Because `repository.owner.login`/`organization.login` (verification side) and `repository.full_name`/`sha` (mutation side) are both attacker-controlled fields inside the same unauthenticated raw JSON body, nothing forces them to agree. An attacker who can produce a valid signature for **any one** configured organization (e.g., one whose operator left `webhook_secret` blank, which the setup docs list as optional) can set `repository.owner.login` to that organization to pass `verify_signature`, while setting `repository.full_name` (or `sha`) to target a stack/commit belonging to a completely different organization/repository that they have no relationship to and whose secret they do not know.

This is exactly the "organization authenticated vs. repository written" binding called out as in-scope: `left(payload) = repository.owner.login used for HMAC/org selection`, `right(payload) = repository.full_name / sha used for the actual write`, and the two are never required to be equal.

### Impact Explanation
An attacker exploiting this can forge GitHub webhook events for stacks/commits they do not control, as long as one org in the Shipit deployment has a blank/optional `webhook_secret` (a documented, supported configuration) or as long as the attacker otherwise knows any single org's secret. The most severe consequence is forging a `status` event: `StatusHandler` writes an arbitrary `state`/`context` status onto any `Commit` row matching a known `sha`, with no repository scoping whatsoever. [4](#0-3)  Since deploy eligibility and merge automation depend on configured "required" CI statuses (`required_statuses`, `merge_request_required_statuses` in `DeploySpec`), [8](#0-7) [9](#0-8)  an attacker can forge a passing status for a required context on a victim commit, potentially causing an unauthorized automatic merge or continuous deployment of an unreviewed/malicious commit — matching the "unauthorized deploy, rollback or merge" Critical impact bucket.

### Likelihood Explanation
Exploitation requires no privileged Shipit account, `ApiClient` token, `webhook_secret`, or GitHub App key for the *victim* organization — only the ability to submit an HTTP POST to `/webhooks` with a crafted JSON body and a signature valid for *any* configured organization (including one with a blank/optional secret, a supported and documented configuration). This is reachable by a fully unauthenticated network attacker, satisfying the "unprivileged-attacker" scope.

### Recommendation
1. Bind webhook signature verification to the same field(s) used for subsequent authorization/mutation. Specifically, after selecting `github_app` by `repository_owner`, re-derive/require that `repository.full_name`'s owner segment (and any `sha`/commit lookups) matches the organization that was cryptographically authenticated, rejecting the request otherwise.
2. In `StatusHandler`, scope `Commit.where(sha: ...)` to commits belonging to the authenticated organization/repository (e.g., join through `Repository`/`Stack` filtered by the verified organization), rather than matching bare `sha` globally.
3. Consider making `webhook_secret` mandatory (reject configs with no secret) so `verify_webhook_signature` can never trivially return `true`.

### Proof of Concept
1. Deploy configuration with two GitHub orgs: `victim-org` (real secret, hosts sensitive stack with `ci.require: ["ci/build"]`) and `attacker-org` (installed by the attacker, `webhook_secret` left blank per the documented optional setting).
2. Attacker learns the `sha` of a commit on `victim-org`'s stack (visible via the public Shipit UI/API or GitHub).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/build",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the signature header supplied. [5](#0-4) [1](#0-0) 
5. `StatusHandler.process` runs unconstrained by organization and creates a "success" status for `ci/build` on the victim's commit. [4](#0-3) 
6. If `victim-org`'s stack has continuous deployment/merge enabled with `ci/build` as a required status, this forged status can unblock an automatic deploy/merge of that commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
