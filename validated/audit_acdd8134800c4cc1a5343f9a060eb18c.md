The base `Handler` class provides a `stacks` helper method scoped to the webhook's own repository (`Repository.from_github_repo_name(repository_name)&.stacks`), used by other handlers, but `StatusHandler#process` does not use it — it queries `Commit.where(sha: params.sha)` globally, across all stacks/repositories.

### Title
Cross-repository status forgery: `StatusHandler#process` writes required-context statuses to any commit sharing a SHA, regardless of authenticated repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits via `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` with no filter on the repository/stack that the webhook actually authenticated for. Any attacker who owns a legitimate repository connected to the same Shipit instance can send a signed `status` webhook for a SHA shared with a victim's stack, causing the write to apply to the victim commit too, potentially flipping `deployable?`/merge eligibility if `review/approved` (or any required context) is set to `success`.

### Finding Description
The broken binding: `commit.stack_id` (the stack whose repository authenticated the webhook via `verify_signature`/`repository_owner`) should equal the `stack_id` of every `Commit` record that `StatusHandler` mutates, but it does not — `Commit.where(sha:)` matches across all stacks in the database.

Code path:
- `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) verifies the HMAC signature using `Shipit.github(organization: repository_owner)` — this authenticates that the request came from *a* legitimate GitHub organization/app installation tied to the payload's `repository.owner.login`, not that it is authorized to act on any specific stack. [1](#0-0) 
- Dispatch calls `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and `Handler.call` instantiates the handler and calls `process`. [2](#0-1) 
- The base `Handler` class defines a `stacks` helper explicitly scoped to the webhook's own repository (`Repository.from_github_repo_name(repository_name)&.stacks`), intended to constrain handlers to the authenticated repository. [3](#0-2) 
- `StatusHandler#process` ignores this scoping entirely and instead does a global `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [4](#0-3) 
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, using the *matched commit's* own `stack_id` (correctly scoped per-record), but the matching itself is unscoped, so any commit row anywhere with the same `sha` gets a new `Status` row attributed to its own stack. [5](#0-4) [6](#0-5) 
- `Commit#status` recomputes from `Status::Group.compact(self, statuses_and_check_runs)`, and `Commit#deployable?` depends on `success?` derived from that status group, so a newly written `success` status for a required context can flip `deployable?` for the victim stack's commit. [7](#0-6) [8](#0-7) 

Exploit flow: the attacker registers/owns a repository already connected to the target Shipit instance (a precondition many multi-tenant Shipit deployments allow — any repo added as a stack). They engineer or coincidentally obtain a commit whose SHA matches a commit already present in a victim's stack (git SHA collisions across repos happen naturally when commits/trees are byte-identical, e.g., cherry-picks, copied history, or shared subtree/vendoring workflows — no cryptographic break is required, just identical git object content). The attacker then triggers (or directly POSTs) a `status` event from their own repository with `context: review/approved`, `state: success`, `sha: <shared sha>`. The signature check passes because it is validated against the attacker's own organization/app secret for their own repository — it says nothing about which stacks the event may mutate. `StatusHandler` then writes the `success` status onto every `Commit` row with that SHA, including the victim's, updating the victim's required-context status group and its `deployable?`/merge-eligibility.

Existing guards fail here because: `verify_signature` authenticates *origin org*, not *target stack*; `drop_unhandled_event`/`check_if_ping` are unrelated; the `ExplicitParameters` schema only validates payload shape, not repository scoping; and no model validation ties a `Status` write to the repository that emitted the event — the only scoping (`stack_id`) is derived from whichever `Commit` row happens to match the raw SHA.

### Impact Explanation
An attacker's webhook (from their own authenticated repository) writes a `Status` record scoped to a victim's stack, mutating the victim commit's status group and `deployable?`. If `review/approved` (or any `ci.require`d context) is set to `success` this way, it can enable deploy/merge eligibility for a commit the victim never actually approved — a payload for one repository mutating another's commit/stack. This matches "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The technique is repeatable against any repository pair that shares/produces an identical commit SHA and generalizes to any status context, not just `review/approved` — including CI contexts that gate `ignore_ci?`/`blocked?` and thus continuous delivery (`schedule_continuous_delivery`). [9](#0-8) 

### Likelihood Explanation
Preconditions: (1) attacker must control/own at least one repository already wired into the same Shipit instance as a stack (a legitimate, low-privilege action in many Shipit deployments where any team can add its own repo); (2) attacker's commit SHA must collide with a SHA present in the victim's stack — feasible via identical commit content (same tree, message, author/committer timestamps, parents), which is a realistic occurrence in mirrored/forked/subtree-shared repositories, not a cryptographic SHA-1 collision. Attacker cost is a single signed webhook POST from their own authenticated origin. The vulnerability is fully repeatable — every additional shared SHA is another opportunity, and the write goes through unconditionally on each request since `create_status_from_github!` uses `find_or_create_by!` with no uniqueness precondition beyond the state/timestamp tuple.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks under the webhook's authenticated repository, mirroring the base `Handler#stacks` helper, e.g. filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalent join through `Repository.from_github_repo_name(repository_name)`) before calling `create_status_from_github!`, so a status event can only ever affect commits that belong to the repository that authenticated it.

### Proof of Concept
minitest plan (e.g. `test/models/webhooks/status_handler_test.rb`):
1. Create two `Repository`/`Stack` records: `attacker_repo`/`attacker_stack` and `victim_repo`/`victim_stack`, with `victim_stack.ci.require` (or equivalent config) including `review/approved`.
2. Create `victim_commit = Commit.create!(stack: victim_stack, sha: "deadbeef" * 5)` and assert `victim_commit.deployable?` is `false` (no `review/approved` success status yet — left side of the binding).
3. Create `attacker_commit = Commit.create!(stack: attacker_stack, sha: victim_commit.sha)` (same SHA, different stack) to simulate the shared-SHA precondition.
4. Build a payload: `{ "sha" => victim_commit.sha, "state" => "success", "context" => "review/approved", "repository" => { "full_name" => attacker_repo.github_repo_name, "owner" => { "login" => attacker_repo.owner } } }` and call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, which is orthogonal to this bug — it only authenticates the attacker's own repo).
5. Reload `victim_commit`; assert `victim_commit.status.state == "success"` and `victim_commit.deployable? == true` — proving the equality `commit.stack_id == authenticated_repository.stacks.ids` was violated: a status meant for `attacker_stack` mutated `victim_stack`'s commit.
6. Assert that after applying the recommended fix (scoping by `stacks` from `repository_name`), `victim_commit.reload.deployable?` remains `false` and no `Status` row is created for `victim_commit`.
