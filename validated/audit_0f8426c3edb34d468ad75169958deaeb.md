### Title
Unbounded decompression of attacker-controlled archives leads to disk/CPU exhaustion (decompression bomb) - ([File: internal/zip/zip.go])

### Summary
Several `gh` commands download and decompress archives originating from remote, attacker-influenceable content (workflow run artifacts, release assets, extension releases) without any limit on the compressed download size or the decompressed output size. A malicious or compromised repository/extension owner can publish a "zip bomb" style artifact that `gh` will fully download and fully extract to disk, exhausting the invoking user's disk space and/or CPU — a direct client-side analog of the "abusive client / missing resource limits" bug class described in the report (there it was server-side DoS from unbounded request processing; here it is client-side DoS from unbounded response processing).

### Finding Description
The core extraction routine copies every zip entry to disk with no size cap: [1](#0-0) 

This is called from multiple commands that stream a remote HTTP response body into a file and then fully decompress it, with no limit on either the downloaded size or the expanded size:

- `gh run download` streams an artifact response directly into a temp file and then extracts it via `ghzip.ExtractZip`: [2](#0-1) 

- `gh release download --archive zip|tar.gz` and asset downloads write the full response body to disk via `io.Copy` with no byte limit: [3](#0-2) 

- `gh extension install` downloads a release asset (a zip on Windows) directly to disk and later unzips it, with no size limit: [4](#0-3) 

- The Copilot CLI installer (`gh copilot`) downloads a release archive to a temp file and fully extracts it (zip or tar.gz), again with no size bound at either the download or extraction stage: [5](#0-4) [6](#0-5) 

A codebase-wide search confirms there is no `io.LimitReader`, `MaxBytes`, or similar guard anywhere in these download/extraction paths, meaning a small compressed payload can expand to an arbitrarily large size on disk (classic "zip/gzip bomb"), and there is no cap on the number of bytes read from the HTTP response before writing to disk either.

### Impact Explanation
Any of these code paths can be reached by content that is not controlled by the `gh` user:
- A CI workflow artifact uploaded by anyone with write access to a repository (or via a compromised Actions workflow) can be a decompression bomb consumed via `gh run download`.
- A GitHub Release asset (or archive) published by a repository owner/maintainer — including a public repository the victim does not control — can be a decompression bomb consumed via `gh release download`.
- A malicious `gh` extension repository can serve a decompression bomb consumed via `gh extension install`.

Since none of these flows enforce a maximum downloaded or extracted size, a victim running a normal `gh` command against attacker-supplied content can have their disk filled and/or CPU consumed, resulting in local resource exhaustion (denial of service) on the machine running `gh`. This mirrors the reported bug class (missing throttling/limits allowing a party to cause disproportionate resource consumption) but manifests on the CLI client rather than the in3 server.

### Likelihood Explanation
Likelihood is meaningful but not "trivial-drive-by": the victim must voluntarily run `gh run download`, `gh release download`, or `gh extension install` against a repository/release/extension that is under attacker control (or compromised). This is a normal, common workflow for `gh` users (e.g., downloading CI artifacts or third-party extensions), so the attacker only needs to get the victim to target their repo/release — no additional social engineering technique beyond a plausible artifact/release name is required.

### Recommendation
- Wrap the HTTP response body in `io.LimitReader` (or track bytes written) before copying to the temp/destination file in `internal/zip/zip.go`, `pkg/cmd/run/download/http.go`, `pkg/cmd/release/download/download.go`, `pkg/cmd/extension/http.go`, and `pkg/cmd/copilot/copilot.go`, aborting with an error once a configurable maximum compressed size is exceeded.
- Track cumulative decompressed bytes written per archive during extraction (`extractZipFile` in `internal/zip/zip.go`, and the tar/gzip extraction loop in `pkg/cmd/copilot/copilot.go`) and abort if a maximum uncompressed size threshold is exceeded, to defend against zip/gzip bombs regardless of the compressed size on the wire.
- Consider also bounding the number of entries extracted, to mitigate bombs composed of many small files.

### Proof of Concept
1. Craft a highly-compressible zip file (e.g., a single file consisting of gigabytes of `0x00` bytes, compressing to a few KB) and publish it as:
   - a GitHub Actions workflow artifact in an attacker-controlled repository, or
   - a GitHub Release asset / archive.
2. Have the victim run `gh run download <run-id>` or `gh release download <tag> --archive zip` against that repository.
3. Observe that `downloadArtifact` (`pkg/cmd/run/download/http.go:41-63`) or `destinationWriter.Copy` (`pkg/cmd/release/download/download.go:452`) writes the entire response body to disk, and `ghzip.ExtractZip`/`extractZipFile` (`internal/zip/zip.go:60-72`) then decompresses every entry via unbounded `io.Copy`, filling the victim's disk with no size check at any stage.

// Copy writes the data from r into a file specified by name.
func (w destinationWriter) Copy(name string, r io.Reader) (copyErr error) {
	fp := w.makePath(name)
	if fp == "-" {
		if w.allowEscapes {
			_, copyErr = io.Copy(w.stdout, r)
			return
		}
		copyErr = iostreams.CopyGuardedContent(w.stdout, r, w.isTTY)
		if binErr, ok := errors.AsType[iostreams.BinaryTerminalError](copyErr); ok {
			copyErr = fmt.Errorf("%w; use `--output` to save it to a file, or pass --allow-escape-sequences to output it anyway", binErr)
		} else if errors.Is(copyErr, iostreams.ErrEscapeSequence) {
			copyErr = errors.New("the asset contains terminal escape sequences; use `--output` to save it to a file, or pass --allow-escape-sequences to output it anyway")
		}
		return
	}
	if copyErr = w.check(fp); copyErr != nil {
		return
	}

	if dir := filepath.Dir(fp); dir != "." {
		if copyErr = os.MkdirAll(dir, 0755); copyErr != nil {
			return
		}
	}

	var f *os.File
	if f, copyErr = os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644); copyErr != nil {
		return
	}

	defer func() {
		if err := f.Close(); copyErr == nil && err != nil {
			copyErr = err
		}
	}()

	_, copyErr = io.Copy(f, r)
	return

// extractTarGz reads a TAR.GZ archive from r and extracts its contents into destDir.
// It returns an error if the archive cannot be read,
// or if any file or directory within the archive cannot be created or written.
func extractTarGz(r io.Reader, destDir string) error {
	gzr, err := gzip.NewReader(r)
	if err != nil {
		return fmt.Errorf("failed to create gzip reader: %w", err)
	}
	defer gzr.Close()

	absDestDirPath, err := safepaths.ParseAbsolute(destDir)
	if err != nil {
		return err
	}

	tr := tar.NewReader(gzr)
	for {
		header, err := tr.Next()
		if err == io.EOF {
			break
		}
		if err != nil {
			return fmt.Errorf("failed to read tar: %w", err)
		}

		absFilePath, err := absDestDirPath.Join(header.Name)
		if err != nil {
			return err
		}
		target := absFilePath.String()

		if header.Typeflag == tar.TypeReg {
			if err := os.MkdirAll(filepath.Dir(target), 0755); err != nil {
				return fmt.Errorf("failed to create parent directory: %w", err)
			}
			if err := extractFile(target, os.FileMode(header.Mode)&0777, tr); err != nil {
				return err
			}
		}
	}
	return nil
}
