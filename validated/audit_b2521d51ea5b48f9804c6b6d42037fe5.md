This is a strong analog to the fee-collector bug class: a value used to authenticate/authorize a request (`repository.owner.login`) is a different field from the value used to determine what gets written (`membership.organization.login` or `repository.full_name`), and both come from the same unauthenticated JSON body an attacker fully controls.

### Title
Webhook signature verification is keyed on an attacker-controlled `repository.owner.login` field that is disjoint from the `organization`/`repository` fields actually acted upon, allowing forged `membership` and repo events to bypass signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login')` [1](#0-0) , falling back to `params.dig('organization', 'login')` [2](#0-1) . This lookup happens before the body is trusted at all — the entire JSON payload is attacker-supplied over HTTP, and only the `X-Hub-Signature` header is meant to prove authenticity. The organization selected here binds to a `GitHubApp` config whose `verify_webhook_signature` **short-circuits to `true` whenever no `webhook_secret` is configured** for that org: `return true unless webhook_secret` [3](#0-2) . The webhook secret is explicitly documented as optional per organization [4](#0-3) .

Once `verify_signature` passes, `create` re-parses the same raw body and dispatches it to event handlers using entirely different fields of that payload: `MembershipHandler` trusts `params.organization.login` to create/attach a `Team` [5](#0-4) , and generic repo-scoped handlers (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) resolve the acted-upon `Stack`/`Repository` via `payload.dig('repository', 'full_name')` [6](#0-5) . Nothing enforces that `repository.owner.login` (used to pick the signing secret) is consistent with `organization.login` or `repository.full_name` (used to decide what gets mutated).

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization/repository the handler writes to`

Because both sides are read from the same attacker-controlled JSON body, and the field used for verification (`repository.owner.login`) is independent of the field used for the write (`organization.login` / `repository.full_name`), an attacker can decouple them:

1. Set `repository.owner.login` to any organization configured in this Shipit instance with no `webhook_secret` set (a documented, supported, and common configuration — see `config/secrets.development.shopify.yml` and `docs/setup.md`, both showing `webhook_secret: # nil`) [7](#0-6) .
2. `verify_signature` calls `Shipit.github(organization: repository_owner)` [8](#0-7) , which resolves that org's `GitHubApp`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank [3](#0-2) . No valid `X-Hub-Signature` is required at all.
3. In the same payload, set `organization.login` (for a `membership` event) or `repository.full_name` (for `push`/`status`/`pull_request` events) to a **different**, protected organization/repository that the attacker wants to affect.
4. `WebhooksController#create` dispatches the parsed body to the matching handler, which trusts those latter fields to decide what `Team`/`Membership`/`Stack` to mutate [9](#0-8) .

This lets an unauthenticated network attacker forge webhook events for any organization/repository configured in Shipit, as long as at least one other organization in the same instance has no webhook secret set.

### Impact Explanation
The most severe reachable outcome is via `Handlers::MembershipHandler`, which is used to synchronize `Team`/`Membership` records that back `User#authorized?` and thus `Shipit.github_teams` authorization checks [10](#0-9) . Forging a `membership` `added` event lets an attacker add an arbitrary GitHub login (including their own, if it can resolve via `User.find_or_create_by_login!`) to a `Team` whose `organization`/`slug` matches a team Shipit trusts for `github_teams` authorization [11](#0-10) . This is exactly the "escalation into `Shipit.github_teams` authorization" impact called out in scope. Secondary impact via `push`/`status` events lets an attacker inject forged commit statuses or trigger `GithubSyncJob` against arbitrary stacks/repos configured in the instance.

### Likelihood Explanation
This requires only that the Shipit instance configures more than one GitHub organization (a documented, supported feature — `docs/setup.md` "Using Multiple Github Applications") and that at least one configured organization has no `webhook_secret` (also explicitly documented as optional, and shown as the default/example value `# nil` in the shipped config templates). No credentials, session, or prior access are needed — this is a pure unauthenticated HTTP POST to `/webhooks`.

### Recommendation
Do not select the verification secret from any field of the untrusted payload body independent of what will be acted upon. Concretely:
- Verify the signature using a single, deployment-wide secret validation path, or ensure the same authenticated `organization` value is used consistently for both signature verification and the object being mutated (i.e., re-derive/validate `organization.login`/`repository.full_name` against the org whose secret actually verified, and reject if they diverge).
- Consider making `webhook_secret` mandatory (fail closed) rather than allowing verification to trivially pass when unset, at least when multiple organizations are configured.

### Proof of Concept
Given a Shipit instance configured with two GitHub orgs, `SecureOrg` (has `webhook_secret` set) and `OpenOrg` (no `webhook_secret`, per the documented optional config), an attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and no valid signature:
```json
{
  "action": "added",
  "team": { "id": 48, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "organization": { "login": "SecureOrg" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "OpenOrg" } }
}
```
`verify_signature` resolves `Shipit.github(organization: "OpenOrg")` from `repository.owner.login`, which has no `webhook_secret`, so verification passes unconditionally [12](#0-11) . `MembershipHandler#process` then uses `params.organization.login` ("SecureOrg") to find/create the `Team` and adds the attacker's user as a member [13](#0-12) , without ever validating a signature scoped to `SecureOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
