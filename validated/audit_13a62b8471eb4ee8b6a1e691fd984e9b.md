Confirmed: `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) calls `Stack.from_param!(params[:stack_id])` directly, bypassing the tenant-scoping helper `BaseController#stacks`/`#stack` (`app/controllers/shipit/api/base_controller.rb:74-80`) that every other API controller relies on to restrict a stack-scoped `ApiClient` to `Stack.where(id: current_api_client.stack_id)`.

### Title
Stack-scoped ApiClient token grants CCMenu read access to any stack, not just the stack it was issued for - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The equality broken is: `stack a token authorises == stack it touches`. A `Shipit::ApiClient` created by `CCMenuUrlController` is bound to one stack in the URL but `CCMenuController` never checks that binding when serving the request.

### Finding Description
`CCMenuUrlController#fetch` mints (or reuses) a `read:stack`-only `ApiClient` scoped to `current_user` and embeds its long-lived, unencrypted-except-for-signature `authentication_token` in a URL built for one specific stack: [1](#0-0) . This kind of CCTray/CCMenu URL is designed to be pasted into third-party CI dashboard widgets/monitors, which is a normal, expected leak vector for this exact type of token.

The token authenticates against `Api::CCMenuController`, which extends `Api::BaseController` and its `require_permission :read, :stack` check [2](#0-1) . `require_permission!` only calls `ApiClient#check_permissions!`, which checks the permission string list, not which stack the client is bound to [3](#0-2) . Stack scoping is enforced only by the `stacks`/`stack` helpers in `BaseController`: [4](#0-3) . Every other API resource controller relies on this scoped `stack` method inherited from `BaseController` to resolve `params[:stack_id]`. `CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table, ignoring `current_api_client.stack_id` entirely: [5](#0-4) .

Before vs. after: before the request, `ApiClient#stack_id` is fixed to the stack for which the URL was generated (e.g. stack A). After swapping `params[:stack_id]` to stack B in the request URL while keeping the same `token`, `CCMenuController#stack` resolves stack B directly via `Stack.from_param!`, and `show` renders stack B's latest deploy/build status via that unscoped `stack`: [6](#0-5) . The stack the token was issued/authorised for and the stack actually touched by the request diverge.

### Impact Explanation
This matches the High-severity class "unauthenticated/unauthorized read of stack state, task streams or deploy output" carved out in the rules: the leaked CCMenu token (an expected leak scenario, since these URLs are meant to be embedded in external CI status tools) grants read access — build/deploy status, last build label/time, running state — to every stack in the Shipit instance, not just the one it was created for, undermining the entire purpose of per-stack `ApiClient` scoping.

### Likelihood Explanation
Likelihood is meaningfully high for a "stack-scoped, read-only" token: CCMenu/CCTray URLs are explicitly built to be pasted into third-party build-status widgets/browser extensions/status boards, which is the normal, sanctioned way this feature leaks a bit of visibility. Once such a URL (with its token) is observed by anyone, only editing the `stack_id` path segment is required — no cryptography is broken, since the vulnerability is a missing authorization check, not a signature forgery.

### Recommendation
Make `Api::CCMenuController#stack` use the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) inherited from `BaseController`, exactly like other API controllers, so the resolved stack is intersected with `current_api_client.stack_id` when the client is stack-scoped.

### Proof of Concept
1. As a legitimate Shipit user with access to Stack A, visit the CCMenu URL page for Stack A; `CCMenuUrlController#fetch` returns a URL of the form `.../api/stacks/<A>/ccmenu?token=<T>`.
2. Take token `<T>` (now bound to an `ApiClient` with `stack_id = A`) and issue `GET /api/stacks/<B>/ccmenu?token=<T>` for an unrelated Stack B that this user/client should not be able to read.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!`, the request succeeds and returns Stack B's build/deploy status in the CCTray XML response, even though the `ApiClient` backing `<T>` is scoped to Stack A only. [7](#0-6)
