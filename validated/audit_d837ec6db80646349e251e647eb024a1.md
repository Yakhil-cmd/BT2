### Title
Webhook secret selection uses `repository.owner.login`/`organization.login` while message processing trusts `repository.full_name` — cross-organization signature/authorization binding is broken (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects **which** organization's `webhook_secret` to validate a GitHub webhook against using the payload field `repository.owner.login` (or `organization.login`), but the handlers that actually act on the webhook (enqueue syncs, deploys, membership changes, etc.) key off a **different** field, `repository.full_name`. Nothing in the code enforces that these two fields refer to the same organization. Anyone who holds a valid webhook secret for *any* organization configured in this Shipit instance can therefore forge a signed payload whose `repository.full_name` points at a repository belonging to a *different* organization, and Shipit will process it as authentic.

### Finding Description
`Shipit.github(organization: repository_owner)` is used to pick the `GitHubApp` (and its `webhook_secret`) that will validate the request: [1](#0-0) 

`repository_owner` is derived purely from the JSON payload: [2](#0-1) 

The HMAC check itself only proves that "whoever knows the secret associated with the claimed `organization`" produced the body — it says nothing about which repository the body's contents refer to: [3](#0-2) 

Lookup of the secret is done by literal, case-insensitive string match against `secrets.github` keys, i.e. purely on the attacker-supplied `repository_owner` string: [4](#0-3) 

Once the signature passes, every webhook handler (push, status, membership, pull_request, etc.) determines the target repository/stack from a **different** field in the same payload, `repository.full_name`, with no cross-check against the organization that was used to select the secret: [5](#0-4) 

Because the HMAC covers the raw request body and not a canonical "organization claim," anyone who legitimately knows one organization's webhook secret (e.g., because they administer that org's GitHub App/webhook integration into this shared Shipit instance) can freely construct the JSON body themselves — including setting `repository.owner.login` to their own organization (to select their own secret in `verify_signature`) while setting `repository.full_name` to `OtherOrg/some-repo` (to make handlers act on a repository/stack that belongs to a completely different, unrelated organization).

This is exactly the audited bug class: a validation check binds trust to one field (`_firstInt`/`repository.owner.login`) while a *different* field (`_thirdInt.._eighthInt`/`repository.full_name`) is the one actually acted upon, with the mismatch never being checked.

### Impact Explanation
If this Shipit deployment is configured with multiple `secrets.github` organizations (as supported by `Shipit.github_organizations`/`github_app_config`), an actor who is only trusted for one organization's webhook secret can craft signed webhook payloads that cause Shipit to perform actions (queueing `GithubSyncJob`, creating commit statuses, altering `PullRequest`/`Team`/`Membership` records, unarchiving/provisioning review stacks, etc.) against stacks/repositories owned by a different organization they have no legitimate access to. This is a cross-repository/cross-organization write achieved purely by exploiting the authorization-selection logic, matching the Critical "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitability requires the attacker to already hold a legitimate webhook secret for *some* organization configured in the multi-tenant instance (i.e., they are a legitimate integrator for that org, not for the victim org). This is a real, plausible operator of a multi-organization Shipit deployment (e.g., a company running several GitHub orgs, or a shared instance serving several teams), and the vulnerable code path (`repository_owner` selection vs. `repository_name`/`full_name` consumption) is hit on every single webhook delivery, so likelihood is moderate-to-high wherever multi-organization webhook configuration is used.

### Recommendation
In `WebhooksController#verify_signature`/`repository_owner`, after selecting and validating the signature for a claimed organization, re-derive and enforce that `repository.full_name`'s owner segment (and/or `organization.login`) matches the organization whose secret was used to validate the signature, rejecting (422) any mismatch before dispatching to `Shipit::Webhooks.for_event(event)` handlers.

### Proof of Concept
1. Configure `secrets.github` with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (multi-org mode, per `lib/shipit.rb#github_app_config`).
2. As an attacker who legitimately knows `orgA`'s `webhook_secret` (e.g. they administer `orgA`'s GitHub App integration), craft a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
     ...
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac(orgA_webhook_secret, body)>` and POST it to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")`, validates successfully against `orgA`'s secret.
5. The dispatched handler (e.g. push handler) resolves the target via `payload.dig('repository','full_name') == "orgB/victim-repo"` and acts on stacks belonging to `orgB`, even though the request was only ever authenticated for `orgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
