### Title
Stack-scoped API tokens can read CI/build status of any stack via CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The `Api::CCMenuController#stack` method resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, bypassing the stack-scoping enforcement that every other API controller relies on through `Api::BaseController#stacks`/`#stack`. This breaks the binding "the stack a token authorises == the stack it touches": an `ApiClient` created with a `stack_id` (i.e. explicitly restricted to a single stack) and only the `read:stack` permission can still fetch the CCMenu XML status (build/deploy status, lock status) of any other stack in the installation by simply supplying a different `stack_id` in the request.

### Finding Description
`ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true` [1](#0-0)  and `Api::BaseController` enforces this scope everywhere by intersecting the requested stack with the client's own stack:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving directly against the global `Stack` relation instead of the scoped `stacks` helper:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

The controller only enforces the permission class (`require_permission :read, :stack`) [4](#0-3) , which is checked against `ApiClient#check_permissions!` and only validates that the `"read:stack"` string is present in the client's `permissions` array — it never validates that the specific `stack` being accessed matches `current_api_client.stack_id`: [5](#0-4) .

Before the fix an attacker's PR: any legitimate but narrowly-scoped ApiClient (e.g. one issued to a single team/stack with `read:stack` permission, as in the `here_come_the_walrus` fixture [6](#0-5) ) is authorized only for its own `stack_id`. After: by calling `GET /api/stacks/:stack_id/ccmenu.xml` with an arbitrary `stack_id` and its own token, the client receives that other stack's `lastBuildStatus`, `lastBuildLabel`, activity and lock state — data outside the scope its token was authorised for.

### Impact Explanation
This is a cross-stack authorization bypass: a token authorised (bound) to one stack is able to touch (read state of) any stack, unlike every other endpoint in the API (`Api::StacksController`, etc.) which correctly narrows access through `stacks.from_param!`. This matches the High-impact bucket of "unauthorized read of stack state" — an authenticated-but-scoped API client escalates beyond its authorized stack to read status/lock information of stacks it should have no visibility into.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (a documented/expected usage pattern, exercised by the `here_come_the_walrus` fixture) since the only requirement is possessing any valid scoped token with `read:stack` and knowing/guessing another stack's `to_param` (owner/repo/environment), which is not secret.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` helper from `Api::BaseController` (i.e. remove the override, or implement it as `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create an `ApiClient` with `stack_id` set to Stack A and permission `read:stack` only (mirrors fixture `here_come_the_walrus`).
2. Using that client's `authentication_token`, request `GET /api/stacks/:owner/:repo/:env/ccmenu.xml` (or via the `token` query param path used by `Api::CCMenuController#authenticate_api_client`) with `stack_id` pointing to Stack B, a stack the client is not scoped to.
3. Observe the response returns Stack B's `lastBuildStatus`/`lastBuildLabel`/lock status, proving the token's authorized-stack boundary (Stack A) was not enforced against the stack actually touched (Stack B).
