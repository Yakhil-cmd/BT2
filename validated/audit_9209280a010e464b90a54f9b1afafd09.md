### Title
Missing authorization check on cosigner identity for local "sign" requests allows any paired device to request signing of arbitrary transactions from a victim's address - (File: wallet.js)

### Summary
The Pagekit CVE is a classic IDOR: an authenticated but unprivileged actor can reference another user's object (a role) by ID and mutate it because the handler never verifies that the caller is actually entitled to act on that object. The closest reachable analog in `ocore` is the `"sign"` message handler in `handleMessageFromHub`, which lets any paired correspondent device reference a *local* address by name/signing-path and get a signing prompt fired for it, without verifying that the sender is actually a legitimate co-signer of that address. The equivalent check exists only for the *remote*-forwarding branch, not for the *local* branch, and a comment shows the ownership check was deliberately removed.

### Finding Description
In `wallet.js`, the `"sign"` case parses `body.address` / `body.signing_path` / `body.unsigned_unit` from an arbitrary paired device and calls `findAddress()` to resolve the object: [1](#0-0) 

When `findAddress` resolves the address to a key that lives on the local device (`ifLocal`), the handler proceeds straight to firing the `signing_request` UI event for the caller-supplied unit — with only a stale, explicitly commented-out ownership check: [2](#0-1) 

Compare this with the `ifRemote` branch a few lines below, which *does* enforce that the sender is actually listed as a cosigner of the target address before honoring the request: [3](#0-2) 

No such check exists on the `ifLocal` path. `findAddress` itself only determines *where* a signing key physically lives (via `my_addresses`, `shared_address_signing_paths`, `peer_addresses`), not *who* is allowed to request a signature over it: [4](#0-3) 

Consequently, the object being referenced (the victim's own address + signing path) is treated as a valid target for a signing request from *any* correspondent device, not just addresses/co-signers the sender is actually associated with — the same "reference an object by ID with no ownership check" pattern behind the Pagekit IDOR, here reachable via an unprivileged paired-device message rather than a privileged web session.

### Impact Explanation
Because the sender-authorization check was intentionally stripped from the local-signing path (per the inline comment "the commented check would make multilateral signing impossible"), any device that is merely paired with the victim (correspondent, not necessarily a cosigner) can submit a `"sign"` request naming the victim's own wallet address and an attacker-crafted `unsigned_unit` (e.g., payment outputs to an attacker address). This causes the victim node to validate the joint and fire a `signing_request` event that can trigger automatic or semi-automatic signing flows in headless/automated wallet integrations that don't perform additional origin checks beyond what `handleMessageFromHub` already does — leading to unauthorized spend attempts from the victim's funds if the UI/automation layer trusts the fact that a signing_request event fired as sufficient confirmation.

### Likelihood Explanation
Any node that pairs with another device (a normal, common operation in this wallet protocol) exposes this surface — the attacker only needs to be a paired correspondent, not a cosigner of the target address, matching the "unprivileged... paired device" reachability constraint. The missing check is explicit and intentional in the code (comment left in place), indicating this is a known gap rather than a theoretical one.

### Recommendation
Re-introduce (and generalize, rather than fully remove) the ownership/cosigner check on the `ifLocal` branch of the `"sign"` handler: before emitting `signing_request`, verify that `from_address` is a legitimate co-signer/device for `body.address`/`body.signing_path` (e.g., present in `wallet_signing_paths`/`shared_address_signing_paths` for that address), falling back to allowing single-owner addresses only when the requester is the sole owner. At minimum, ensure downstream UI/automation cannot silently approve signing requests whose origin device is not verified as an authorized party for the referenced address.

### Proof of Concept
1. Pair a rogue device D with victim wallet V (standard, low-privilege pairing).
2. From D, send `{"subject":"sign","body":{"address": V_ADDRESS, "signing_path":"r", "unsigned_unit": {...attacker-chosen payment to attacker address...}}}` to V's hub inbox.
3. `handleMessageFromHub` → `case "sign"` → `findAddress(V_ADDRESS, "r", ...)` resolves `ifLocal` (V_ADDRESS is a local wallet address).
4. No check verifies D is entitled to request this signature; `signing_request` fires with attacker-controlled unit content, exercising the reachable code path with zero object-ownership verification, mirroring the Pagekit IDOR bug class.
