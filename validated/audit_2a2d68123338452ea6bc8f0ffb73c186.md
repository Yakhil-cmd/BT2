### Title
Session fixation on GitHub OAuth callback lets an attacker force a victim's session to become authenticated as the victim under an attacker-known session ID - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` writes `session[:user_id]` (and `session[:authenticated]`) directly into whatever session is currently attached to the request, without ever calling `reset_session`. This is the same "check bound to the wrong side of a state transition" bug class as the external report: in the report, `withdrawLPToken()` trusted `expirations[_LPToken]` state that could be set through a completely different, unguarded function (`depositAndLock()`), breaking the intended binding between "token is blocked" and "token cannot be withdrawn." Here, the intended binding is "session ID == freshly-issued, post-authentication session," but that binding is never enforced: the pre-authentication session ID (which an attacker can plant in a victim's browser) is preserved across the login transition and simply promoted to an authenticated session.

### Finding Description
The OAuth completion flow is: [1](#0-0) 

`callback` never invalidates or rotates the session before assigning `session[:user_id] = sign_in_github(auth)`. Compare this to `logout`, which does call `reset_session`: [2](#0-1) 

`force_github_authentication` (the gate that decides whether a request is treated as logged in) only checks whether `session[:user_id]` is present and resolves to a `User`: [3](#0-2) 

The binding being broken, expressed as the equality the code should (but does not) enforce:
`session_id_before_oauth_completion == session_id_after_oauth_completion` must be **false** (i.e., the session cookie must be rotated on privilege change) — but the code lets it remain **true**, exactly as `withdrawLPToken()`'s `expirations[_LPToken] == 0` check could be satisfied through `depositAndLock()`'s unrelated code path instead of being independently enforced at the point that matters.

Because Rails/Rack session cookies are typically scoped by domain and can be set by any response from the same origin (or a related subdomain, or a login page an attacker can visit and then plant on the victim), a classic session-fixation flow applies:
1. Attacker visits Shipit and obtains a valid but unauthenticated session ID/cookie (or engineers one to be shared, e.g. via a subdomain-scoped cookie if the deployment sets `domain: :all` or similar, or simply captures the pre-auth `_session_id` cookie value from a controlled network position or via any mechanism that lets them fix a cookie in the victim's browser).
2. Attacker gets the victim to use that exact session (fixation vector — e.g., a crafted link, or any application behavior that reflects/sets a session cookie value chosen by the attacker).
3. Victim completes the real GitHub OAuth login flow. `callback` writes `session[:user_id] = <victim's id>` into the *same* session record/cookie the attacker fixed, without rotating it.
4. Attacker, already holding that same session ID, is now treated as the victim by `force_github_authentication`/`current_user`, gaining the victim's authenticated Shipit identity (deploy/merge/rollback/lock permissions per `Shipit.github_teams`).

### Impact Explanation
This falls squarely under the explicitly allowed High-impact category "session fixation / forced OAuth completion." A successful fixation grants the attacker a fully authenticated `current_user` session for the victim, which is used throughout the app (e.g., `Authentication#current_user`) to authorize deploys, rollbacks, locks, and merge-queue actions gated by `Shipit.github_teams` membership — i.e., escalation into `Shipit.github_teams` authorization using the victim's identity, without the attacker ever needing the victim's GitHub credentials, a Shipit API token, or `webhook_secret`.

### Likelihood Explanation
Likelihood is High for any application relying on the default Rails cookie/session-store behavior without extra hardening: no code path in this engine rotates the session ID at authentication time, and the only place `reset_session` is invoked is `logout`. Any generic fixation vector (cookie planting via a shared/parent domain, response splitting, or a link that sets a session cookie before redirecting into the OAuth flow) is sufficient — no repository access, GitHub App keys, or Shipit tokens are required, matching the "unprivileged attacker" constraint.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` before assigning `session[:user_id]`/`session[:authenticated]`, so a brand-new session ID is issued at the moment of authentication (mirroring what `logout` already does). This closes the loophole the same way the report recommends adding the missing check directly to the function that performs the sensitive action (`withdrawLPToken`) rather than relying on state set through an unrelated path (`depositAndLock`).

### Proof of Concept
1. Attacker obtains/fixes a Shipit session ID in the victim's browser (e.g. via any cookie-setting vector reachable pre-authentication, since `callback` performs no rotation).
2. Attacker separately holds/observes that same session ID value.
3. Victim clicks "Log in with GitHub" using the fixed session, completes GitHub OAuth; `GithubAuthenticationController#callback` runs:
   ```ruby
   session[:user_id] = sign_in_github(auth)   # writes into the pre-existing, attacker-known session
   session[:authenticated] = true
   ```
   No `reset_session` occurs.
4. Attacker replays the same session cookie against Shipit; `Authentication#find_current_user` resolves `session[:user_id]` to the victim's `User` record, and `force_github_authentication` treats the attacker's request as the victim, granting the victim's authorized actions (deploy/rollback/lock/merge-queue per `Shipit.github_teams`).

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
