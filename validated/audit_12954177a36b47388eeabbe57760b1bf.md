### Title
Uncaught exception when sorting unstable data-feed candidates with equal level/MCI causes AA trigger processing to abort - ([File: data_feeds.js])

### Summary
`readDataFeedValue()` in [1](#0-0)  lets an AA (via the `data_feed[[...]]` oscript operator) read a data-feed value from *unstable* (not-yet-finalized) units authored by the oracle address(es), which is the ocore analog of an on-chain price oracle read used by a DeFi contract — the exact bug class exploited in the Rodeo Finance incident (price/data manipulation via a value read before it is finalized).

### Finding Description
When an AA formula executes `data_feed[[oracles=..., ...]]`, the evaluator passes `bAA` (a truthy flag) as the `unstable_opts` argument to `dataFeeds.readDataFeedValue`, enabling the "include unstable AAs' data feeds" branch [2](#0-1) . Inside that branch, all currently-unstable data-feed messages from the oracle address(es) are collected into `arrCandidates` and, if more than one candidate exists with `ifseveral !== 'abort'`, they are sorted by `latest_included_mc_index` and then `level` [3](#0-2) :

```
if (a.level < b.level) return -1;
if (a.level > b.level) return 1;
if (bIncludeAllUnstable) return 1;
throw Error("can't sort candidates "+a+" and "+b);
```

The code assumes two different unstable data-feed-posting units from the same oracle address can never share both the same `latest_included_mc_index` and the same `level`. This assumption is not sound: `level` in ocore is derived from parent units (typically `max(parent levels) + 1`), so two sibling units built on the exact same parents can have identical `level` values while both being unstable and posted by the same author address. If an oracle address (which can be any address referenced in an AA's `oracles` parameter, including `this_address`/attacker-controlled addresses in self-referential AA patterns) posts two different `data_feed` messages in two sibling units with identical parents before either is included on the MC, the comparator throws an uncaught `Error`. This exception occurs synchronously inside `Array.prototype.sort`'s comparator, invoked from within `readDataFeedValue`, which is called from the AA formula evaluator during AA trigger processing (`aa_composer.js` handling stabilized triggers) — a path with no surrounding `try/catch` for this specific failure mode based on the code reviewed. An uncaught exception in this code path aborts trigger/unit processing.

### Impact Explanation
This meets the "node disagreement on validity or stability, or a network unable to confirm new units" bar: if the thrown error is not caught up the call stack, it will crash the process handling AA trigger execution or unit validation for any node that attempts to evaluate this formula while the ambiguous unstable state exists, effectively halting that node's ability to stabilize/execute AA triggers referencing the affected data feed until the DAG advances past the ambiguity. Because AA definitions are public and permissionless, and posting two sibling units from one address is trivial and cheap, this is remotely triggerable by any single actor who controls (or is) an oracle address used by any live AA on the network.

### Likelihood Explanation
Likelihood is High for any AA design that treats the trigger's own author address (or another attacker-influenced address) as a data-feed oracle for immediate/unstable reads, and Medium for arbitrary AAs whose fixed oracle address could still be coerced/compromised into emitting two conflicting near-simultaneous data feed values. Creating two sibling units with identical parents from the same author is a normal, low-cost DAG operation requiring no special privilege — only that the attacker's address matches the `oracles` list checked by `readDataFeedValue`, which the rules classify as a reachable "data feed" actor.

### Recommendation
- Replace the `throw Error("can't sort candidates ...")` with a deterministic, total-order tiebreaker (e.g., compare `unit` hash lexicographically) instead of assuming the ambiguous case is impossible.
- Wrap AA-triggered data-feed evaluation in defensive error handling so that any unexpected internal error degrades to a formula evaluation failure (bounce) rather than an uncaught process-level exception.
- Audit all call sites of `readDataFeedValue`/`dataFeedExists` to ensure `bIncludeAllUnstable`/`ifseveral='abort'` semantics fully cover every case where multiple unstable candidates can exist with equal MCI and level.

### Proof of Concept
1. Deploy an AA whose logic includes `data_feed[[oracles=<address>, feed_name='X', ifseveral='last']]` and is triggered/evaluated while `X` is still unstable (e.g., default `unstable_opts` behavior for AA-context reads).
2. From `<address>`, compose two sibling units (same parent set, hence same `level`, same `latest_included_mc_index`) — Unit A posting `data_feed` message `{X: 1}` and Unit B posting `{X: 2}` — and broadcast both before either is included on the main chain.
3. Trigger the AA (or wait for a pending trigger) so that `readDataFeedValue` is invoked with `unstable_opts` truthy while both Unit A and Unit B remain unstable.
4. `arrCandidates` will contain two entries with identical `latest_included_mc_index` and `level`; the sort comparator throws `"can't sort candidates ..."`, which is not caught by any surrounding handler in the reviewed formula-evaluation/AA-trigger path, aborting processing of that trigger/unit on any node that reaches this code (verification of the exact top-level catch behavior in `aa_composer.js`/`main_chain.js` trigger execution could not be fully confirmed from the excerpts reviewed and should be validated in a live/test environment).
