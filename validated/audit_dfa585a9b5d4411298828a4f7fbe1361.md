### Title
Cross-repository status injection via unscoped `Commit.where(sha: ...)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by SHA with no repository/stack scoping, and applies the incoming GitHub `status` payload (`context`, `state`) to every matching `Commit` record across the entire Shipit instance. Because git commit SHAs are content-addressed and identical across forks/shared history, a webhook that is legitimately signed for one repository can flip the status of a commit belonging to an unrelated stack, and if that victim stack has `continuous_deployment` enabled, this can drive `ContinuousDeliveryJob` to ship (or block) that commit.

### Finding Description
The broken binding is: `commit.stack.github_repo_name == params.dig('repository', 'full_name')` (the status must only apply to commits belonging to the repository that authenticated the webhook) — this is never checked.

Code path:
- `Shipit::WebhooksController#create` dispatches the parsed payload to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` succeeds [1](#0-0) .
- `verify_signature` resolves the signing secret via `Shipit.github(organization: repository_owner)` — i.e., at the **organization/GitHub App level**, not per-repository — and only checks the HMAC signature, never that the `sha` belongs to the repo that sent the event [2](#0-1) .
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no filter on `stack_id`/`repository`** [3](#0-2) .
- `create_status_from_github!` writes the status and re-evaluates `status`/`deployable?` for that commit's own stack [4](#0-3) .
- If the affected commit's stack has continuous deployment enabled, `schedule_continuous_delivery` (invoked on create, but re-evaluation also happens through `add_status` → `stack.schedule_merges`) enqueues `ContinuousDeliveryJob` once `deployable?` and `stack.continuous_deployment?` are true [5](#0-4) , and `deployable?` depends on `success?`/`blocked?` which are derived from exactly the status rows this handler writes [6](#0-5) .

Exploit flow: an attacker who legitimately controls a repository/fork whose owner matches an organization configured in Shipit (so `verify_signature` succeeds using that org's webhook secret) sets a `status` (context `review/approved`, state `success`) via the GitHub API on a commit SHA that is **shared history** with a victim stack (e.g., a common ancestor commit that exists identically, byte-for-byte, in both the attacker's repo and the victim's repository/stack, which is normal for forks or repos with shared lineage). GitHub delivers a validly-signed webhook. `StatusHandler` matches this SHA against `Commit` rows across **all** stacks, including the victim's, and writes the `review/approved`/`success` status onto the victim's commit row regardless of which repository actually owns it. If the victim stack requires `review/approved` and has continuous deployment enabled, this can make an unshipped commit `deployable?` and trigger `ContinuousDeliveryJob`, or conversely inject a failing/blocking status to block deploys.

None of the existing guards prevent this: `verify_signature` only proves the payload came from *some* repository under a known organization/App, not that it's for the specific repository owning the target commit; `ExplicitParameters` schema on `StatusHandler` only type-checks fields, it does not enforce repository ownership; there is no `Repository`/`Stack` scoping anywhere in `Commit.where(sha: params.sha)`.

### Impact Explanation
A payload sent for one (attacker-controlled) repository can mutate commit/status state for a stack belonging to a different repository/tenant — this matches the "Critical: a payload for one repository mutating another's stack/commit" category. Concretely, an attacker can force or block a deploy of a specific commit in a victim's continuous-deployment-enabled stack by forging a `review/approved`/`success` (or a blocking-status) event for a SHA the victim also has in its commit history. This is repeatable against any repository that shares commit SHAs with a Shipit-tracked stack (forks, repos seeded from the same upstream, mirrored repos) and requires no session, API token, or Shipit secret from the attacker beyond ordinary GitHub write access to their own repository.

### Likelihood Explanation
Preconditions: (1) Shipit must have a configured GitHub App/organization matching the attacker's repository owner (so `verify_signature` passes) — this is the same organization/owner as the victim's stack in the common cross-repo-in-same-org case, or any organization where the attacker's repo happens to share commit SHAs with a victim repo elsewhere; (2) the victim stack must have `continuous_deployment` enabled and use `review/approved` (or another attacker-forgeable context) as a required/blocking status; (3) the specific SHA must exist as an actual `Commit` row in the victim stack (i.e., already imported by Shipit, e.g., shared history, common ancestor, or cherry-picked/identical commit). Attacker cost is low — a single legitimate GitHub API call to set a commit status on their own repository. It is fully repeatable for any SHA that overlaps between the attacker's repo and a victim stack.

### Recommendation
Scope `StatusHandler#process` (and the analogous `CheckRunHandler`, if present) to only affect commits whose `stack.github_repo_name` matches `params.dig('repository', 'full_name')` from the webhook payload, e.g., `Commit.joins(:stack).merge(Stack.where(...)).where(sha: params.sha)` filtered by repository, rejecting or ignoring matches for stacks belonging to a different repository than the one that sent and authenticated the webhook.

### Proof of Concept
Minitest plan (no live GitHub required):
1. Create two `Stack` records for two different `Repository` values (`owner/victim-repo`, `attacker/attacker-repo`), each with an associated `Commit` row sharing the identical `sha` (simulating shared git history/fork).
2. Configure the victim stack with `continuous_deployment: true` and a deploy spec requiring `review/approved` as a required/blocking status context.
3. Build a `status` webhook payload: `{ sha: <shared_sha>, context: 'review/approved', state: 'success', repository: { full_name: 'attacker/attacker-repo', owner: { login: 'attacker' } } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(...).process` (or POST to `/webhooks` with a validly computed signature for the attacker org) directly, bypassing only signature computation.
5. Assert on both sides of the binding:
   - Before: `victim_commit.status.state != 'success'` and `victim_commit.deployable?` is `false` (or unchanged from baseline).
   - After: `victim_commit.reload.status.state == 'success'` for the `review/approved` context and `victim_commit.deployable?` becomes `true` — demonstrating that a payload authenticated for `attacker/attacker-repo` mutated the state of `owner/victim-repo`'s commit, and that `ContinuousDeliveryJob` was enqueued via `schedule_continuous_delivery`/`add_status`'s `stack.schedule_merges` for the victim stack as a result.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
