Confirmed: creator fees accumulate from swaps via `CreatorFeeOn` logic in `programs/cp-swap/src/states/pool.rs` and are tracked in `pool_state.creator_fees_token_0` / `creator_fees_token_1`, which represent real accrued LP-swap-fee revenue owed to the pool creator, sitting physically in `token_0_vault` / `token_1_vault`.

### Title
Permanent freezing of pool-creator fees when the creator's fixed ATA is frozen/blacklisted - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs], [File: programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs])

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` are the only fee-collection instructions whose recipient token accounts are *hardcoded* to a deterministic address (an Associated Token Account owned by `creator`), rather than an arbitrary caller-supplied account. If that specific ATA ever becomes frozen (a standard SPL Token / Token-2022 account state, settable by any mint's freeze authority — the on-chain analog of a USDC-style blacklist), both instructions revert every time they are invoked, permanently locking the creator's accrued swap fees in the pool vaults with no recovery path, exactly mirroring the root cause in the referenced Nouns DAO `Stream.cancel()` report (a hardcoded transfer to a potentially-frozen party blocks the whole instruction).

### Finding Description
`collect_creator_fee` transfers `creator_fees_token_0`/`creator_fees_token_1` to `creator_token_0`/`creator_token_1`, which are constrained via `associated_token::authority = creator` — i.e., the address is deterministically derived and cannot be substituted: [1](#0-0) 

The transfer is executed via `transfer_from_pool_vault_to_user`, which performs `token_2022::transfer_checked` — this CPI fails if the destination token account is frozen: [2](#0-1) [3](#0-2) 

Because the fee-ledger fields are only zeroed *after* both transfers succeed, a failure in the transfer leaves `pool_state.creator_fees_token_0`/`creator_fees_token_1` unchanged and the funds inaccessible on every subsequent retry: [4](#0-3) 

`collect_creator_fee_permissionless` has the identical structure and the identical hardcoded, non-substitutable ATA constraint (`associated_token::authority = creator`), so the same freeze condition blocks it as well, even though "anyone" can call it: [5](#0-4) [6](#0-5) 

By contrast, `collect_protocol_fee` and `collect_fund_fee` accept a caller-supplied `recipient_token_0_account`/`recipient_token_1_account` with no ownership/ATA constraint, so the admin/fund owner can always redirect fees to a different, unfrozen token account they control — these are not vulnerable: [7](#0-6) 

This is precisely the pattern flagged in the report: a token transfer to a *hardcoded* address can be blocked by that party's account being frozen, and because that transfer is bundled in the same instruction/state-transition as the accounting update, the whole operation — and thus the funds — become permanently stuck.

### Impact Explanation
The creator's accrued swap-fee revenue (a real, growing balance sitting physically in `token_0_vault`/`token_1_vault`) becomes permanently unclaimable once the creator's ATA is frozen, since:
- The recipient address is fixed by the ATA derivation and cannot be changed by the creator or anyone else.
- Every future call to either collection instruction will revert at the `transfer_checked` step.
- There is no alternate withdrawal path in the program for these specific ledger balances (unlike `collect_protocol_fee`/`collect_fund_fee`, which allow redirecting to any account).

This matches the Validate criteria for "permanent freezing of user funds," since the pool creator's legitimately earned funds become permanently locked in the pool's vaults.

### Likelihood Explanation
Freezing an SPL Token / Token-2022 account is a standard base-layer capability (freeze authority), not a non-default/experimental feature, so any mint deployed with an active freeze authority (common for regulated/stablecoin-style tokens) can trigger this condition on the creator's ATA at any time after pool creation — independent of any single malicious transaction, exactly as in the original report where blacklisting happened through unrelated activity. Because `collect_creator_fee_permissionless` is explicitly callable by anyone, an attacker cannot force the freeze themselves, but the design gives the creator (and the protocol) no way to work around a freeze once it happens, unlike the admin-fee paths.

### Recommendation
Track creator fee entitlement per token-account failure independently of a single atomic double-transfer, and/or allow the creator (or an authorized fallback) to specify an alternate destination token account for fee collection, mirroring how `collect_protocol_fee`/`collect_fund_fee` accept caller-supplied recipient accounts instead of a hardcoded ATA. At minimum, decouple the two token transfers so that a revert on one (e.g., a frozen `creator_token_1`) does not block collection of the other, and update `pool_state.creator_fees_token_0`/`creator_fees_token_1` incrementally per successful transfer rather than only after both succeed.

### Proof of Concept
1. Create a pool where `vault_1_mint` is a Token-2022 (or legacy SPL Token) mint whose freeze authority is retained (this is a normal, supported mint configuration — no unsupported extensions are required, since freeze authority is a base mint field, not an `ExtensionType` gated by `is_supported_mint` in `programs/cp-swap/src/utils/token.rs`).
2. Perform swaps so that `pool_state.creator_fees_token_1` accrues a nonzero balance (fee accounting logic in `programs/cp-swap/src/states/pool.rs`).
3. The mint's freeze authority freezes the creator's associated token account for `vault_1_mint` (the address is deterministic: `associated_token::mint = vault_1_mint, associated_token::authority = creator`).
4. Call `collect_creator_fee` or `collect_creator_fee_permissionless`. The `transfer_from_pool_vault_to_user` call for `token_1` invokes `token_2022::transfer_checked` to the frozen `creator_token_1` account, which fails, reverting the entire instruction.
5. `pool_state.creator_fees_token_1` remains nonzero forever; every subsequent call to either instruction fails identically, since the destination address cannot be changed — the accrued fees are permanently locked in `token_1_vault`.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;
```

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
