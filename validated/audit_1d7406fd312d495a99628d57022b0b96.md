### Title
Cross-tenant Team membership mutation via `MembershipHandler` — webhook signed by one org's secret can add/remove members from another org's `Team` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the request was signed with *some* organization's `webhook_secret` (the one derived from `repository_owner`, i.e. `params.dig('organization','login')`), but `MembershipHandler#process` never re-checks that the `team.id` in the payload actually belongs to that same organization before mutating `Shipit::Team` membership. Because `Team.find_or_create_by!(github_id: params.team.id)` looks the team up purely by GitHub's global numeric team id, an attacker who legitimately controls an org (and thus its own signed `webhook_secret`) can send a `membership` webhook naming a *different* org's existing `Team.github_id`, and the handler will add/remove a member on that target org's team.

### Finding Description
The broken binding is:
`repository_owner (org whose webhook_secret verified request signature) == params.team.id's owning Team#organization (the row mutated)`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  — for a `membership` event there is no `repository` key, so this is entirely attacker-supplied `organization.login`.
2. It then does `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`, which succeeds because the attacker legitimately owns org A and signed the payload with org A's real secret [2](#0-1) .
3. `MembershipHandler#process` then runs `find_or_create_team!`, which resolves the `Team` purely by `params.team.id` (GitHub's global numeric team id) via `Team.find_or_create_by!(github_id: params.team.id)`; the `organization` attribute is only set inside the `do |team| ... end` block, i.e. **only when the record is newly created** [3](#0-2) . If a `Team` row with that `github_id` already exists (belonging to org B), the existing row — and its `organization` — is left untouched, and `team.add_member(member)` / `team.members.delete(member)` operate directly on org B's team [4](#0-3) .
4. Nowhere in this call chain is `params.organization.login` (the org that was cryptographically verified) compared against the `organization` column of the `Team` being mutated. The signature only proves "signed by org A's secret"; it never proves "this write targets org A's team."

Attacker request: attacker controls org A (with its own webhook_secret under the "Using Multiple GitHub Applications" pattern), obtains the numeric GitHub team id of a target team belonging to org B (team ids are sequential/public via GitHub's team APIs for many contexts), and POSTs to `/webhooks` with `X-Github-Event: membership`, `organization.login = "org-a"`, `team.id = <org-B-team-github-id>`, `member.login = "attacker-controlled-or-arbitrary-user"`, `action = "added"`, signed with org A's real `webhook_secret`.

Existing guards do not stop this: `verify_signature` validates the HMAC against org A's secret only, `drop_unhandled_event` doesn't apply since `membership` is handled, and the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not organizational ownership [5](#0-4) .

### Impact Explanation
This lets an attacker mutate `Shipit::Team`/`Shipit::Membership` rows belonging to an organization they do not control, using only a webhook secret for their own unrelated org. Since `Shipit.github_teams` and `User#authorized?`-style checks are used for authorization gating (per `lib/shipit.rb#github_teams`) [6](#0-5) , an attacker who can get an arbitrary GitHub-login user added to a privileged team's `Membership` could escalate that user's authorization within Shipit — a cross-tenant authorization write. This matches "escalation into `Shipit.github_teams` authorization" (High) and, depending on how team membership feeds into deploy/merge authorization checks downstream, could rise to unauthorized deploy/merge (Critical) in deployments that gate actions on team membership.

### Likelihood Explanation
Requires the "Using Multiple GitHub Applications" multi-tenant configuration (each org has its own `webhook_secret`), which is a documented supported pattern, and requires the attacker to control at least one onboarded org (or have access to any org's legitimate `webhook_secret`) plus knowledge of the target team's numeric `github_id`. Team ids are GitHub-global sequential integers that are often discoverable through public GitHub API endpoints or prior interaction, making them guessable/enumerable at low cost. The attack is fully repeatable — any org with its own webhook_secret can target any other tenant's existing `Team` row, and can be replayed for `removed` as well as `added` events.

### Recommendation
In `MembershipHandler` (and any other handler that resolves records purely by GitHub numeric id from payload), verify that the `organization` on the resolved/found `Team` matches `params.organization.login`/`repository_owner` that was used for signature verification, and raise/reject when it does not. Additionally, `find_or_create_by!` should not silently skip updating/checking `organization` for pre-existing rows — the lookup key should include organization scoping (e.g., `find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`) so mismatched writes fail instead of mutating the wrong tenant's row.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/membership_handler_test.rb` or similar):
```ruby
test "membership webhook signed by org A cannot mutate org B's team" do
  org_a_secret = "secret-a"
  org_b_secret = "secret-b"
  # stub Shipit.github(organization: "org-a") -> GitHubApp with webhook_secret org_a_secret
  # stub Shipit.github(organization: "org-b") -> GitHubApp with webhook_secret org_b_secret

  team_b = Shipit::Team.create!(github_id: 4242, organization: "org-b", name: "Owners", slug: "owners", api_url: "https://api.github.com/teams/4242")

  payload = {
    action: "added",
    team: { id: 4242, name: "Owners", slug: "owners", url: team_b.api_url },
    organization: { login: "org-a" }, # attacker's own org
    member: { login: "victim-or-attacker-user" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_secret, payload)

  post "/webhooks", params: payload, headers: {
    "X-Github-Event" => "membership",
    "X-Hub-Signature" => signature,
    "Content-Type" => "application/json"
  }

  assert_response :ok
  # Assertion on both sides of the binding:
  assert_equal "org-b", team_b.reload.organization        # team's actual owning org, unchanged
  assert team_b.members.exists?(login: "victim-or-attacker-user") # yet membership was written
  # This demonstrates repository_owner ("org-a", signature-verified) != team_b.organization ("org-b", row mutated)
end
```
This proves a payload signed with org A's `webhook_secret` produced a write on org B's `Team`/`Membership` records, without any live GitHub calls, confirming the cross-tenant authorization write.
