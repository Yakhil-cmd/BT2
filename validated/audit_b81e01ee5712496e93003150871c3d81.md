### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` for `prevent_with_label` repositories - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses `&&`/`||` without parentheses around the `review_stacks_enabled` guard, so it only gates the `allow_all` branch. The `prevent_with_label` branch `(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` is evaluated independently of `review_stacks_enabled`, so a repository with review stacks disabled but configured as `prevent_with_label` will still provision a stack for any PR opened without the provisioning label — which is the default state of every newly opened PR.

### Finding Description
The intended binding is: `review_stacks_enabled == true` AND (one of the three behavior conditions) must hold before provisioning. The actual code in `respond_to_pull_request_opened?`/`provision?`: [1](#0-0) 

parses in Ruby as:
```
(review_stacks_enabled && allow_all?) ||
(allow_with_label? && has_label?) ||
(prevent_with_label? && !has_label?)
```
because `&&` has higher precedence than `||`. The last disjunct is completely unguarded by `review_stacks_enabled`.

Path: any GitHub user who owns/controls a repository connected to Shipit (or can send a forged/legitimate webhook payload — no Shipit auth is required to hit `POST /webhooks`, only GitHub's HMAC signature which the repository owner's own PR event will satisfy) opens a pull request with no labels (`labels: []`, the default). `Repository#provisioning_behavior_prevent_with_label?` is `true` and `pull_request_has_provisioning_label?` is `false`, so `provision?` returns `true` regardless of `repository.review_stacks_enabled`. `process` then calls `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` (`scope.create!(stack_attributes)`) and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`, i.e. a real record write and provisioning-queue side effect for a repository whose operator explicitly disabled review stacks.

No existing guard prevents this: `respond_to_pull_request_opened?` only checks `params.action == 'opened'` and `provision?` itself; there is no separate `review_stacks_enabled` check elsewhere in `process`, and `NullRepository#review_stacks_enabled` returning `false` doesn't help here since a real, persisted `prevent_with_label` `Repository` is used.

### Impact Explanation
Any repository owner who has `review_stacks_enabled: false` but a stale/misconfigured `provisioning_behavior: prevent_with_label` setting will have a `ReviewStack` (and downstream provisioning/task execution via `ReviewStackProvisioningQueue`) created for every unlabeled PR opened against that repo — with zero attacker effort (labels default to empty). This is an unauthorized-record-write / unauthorized-provisioning issue scoped to that specific repository's configuration, matching "a record written for a repository that did not authenticate/intend it" and downstream stack task execution.

### Likelihood Explanation
Requires a repository configured with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false` — a specific, plausible misconfiguration/legacy-setting combination. Given that precondition, exploitation costs the attacker nothing beyond opening a normal PR with no labels, and is fully repeatable for every PR opened on the affected repository.

### Recommendation
Add explicit parentheses to enforce the intended precedence, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` pattern):
1. Create a `Shipit::Repository` with `provisioning_behavior: 'prevent_with_label'` and `review_stacks_enabled: false`.
2. Build `params` for an `opened` action PR event with `pull_request.labels: []` (no provisioning label).
3. Assert binding before fix: `repository.review_stacks_enabled == false` (left) vs. `OpenedHandler.new(params).send(:provision?) == true` (right) — mismatch demonstrates the bug.
4. Call `OpenedHandler.new(params).process` and assert a `Shipit::ReviewStack` was created (`Shipit::ReviewStack.exists?(environment: "pr#{params.number}")`) despite `review_stacks_enabled` being `false`.
5. After applying the parenthesization fix, re-run and assert no `ReviewStack` is created.
