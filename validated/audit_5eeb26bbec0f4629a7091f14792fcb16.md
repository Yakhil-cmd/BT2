### Title
Cross-repository CI status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature check in `WebhooksController#verify_signature` binds trust only to the *organization* that owns the repository named in the payload, but `StatusHandler#process` writes a commit status by looking up commits **globally by `sha` alone**, with no check that the `Commit` record actually belongs to the repository/stack the signature was verified for. This breaks the binding "organization authenticated == repository/stack written to."

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config to verify the `X-Hub-Signature` against using only `repository_owner`, derived from the payload's own `repository.owner.login` (or `organization.login`): [1](#0-0) [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`: [3](#0-2) 

`StatusHandler#process` does **not** use `repository.full_name`/`repository_name` (the field that the base `Handler` class exposes via `Repository.from_github_repo_name`) to scope which commits it may update. Instead it queries `Commit.where(sha: params.sha)` across the *entire* database and calls `create_status_from_github!` on every match: [4](#0-3) 

Compare this with `PushHandler`, which correctly scopes to stacks belonging to the repository named in the payload via `Handler#stacks`/`Repository.from_github_repo_name(repository_name)`: [5](#0-4) [6](#0-5) 

Because git commit SHAs are content-derived (SHA-1 of tree/parents/author/committer/message), an attacker who controls a real GitHub repository/organization tracked by this Shipit instance can craft a commit whose SHA collides with a commit that already exists in a Shipit `Commit` record belonging to a *different*, unrelated repository/stack (e.g. by replaying the exact same tree, parent, author and commit dates — all of which are visible in the target repo's public commit metadata). The attacker then sets a commit status (e.g. via GitHub's Statuses API) on that SHA in their own repo. GitHub signs and delivers the resulting `status` webhook using the legitimate secret configured for the attacker's own organization — which correctly passes `verify_webhook_signature` because the *signature* only ever attests "this payload really came from organization X for repository X," never "this `sha` belongs to repository X."

`Shipit::Commit` records have no repository/stack uniqueness constraint on `sha` beyond `belongs_to :stack` (there's no scoping to the owning stack enforced in `StatusHandler`): [7](#0-6) 

`required_statuses`/`blocking_statuses` (used to gate deploys) are delegated straight from `stack`, and `Commit#deployable?`/CI-gating logic elsewhere relies on the `statuses` association populated by this same unchecked write path: [8](#0-7) 

### Impact Explanation
An attacker who is authenticated only as an organization/repository owner for *one* GitHub org tracked by this Shipit instance can forge a "success" (or arbitrary) CI status on a `Commit` record belonging to a completely different stack/organization/repository that they have no access to. Since CI status is used to gate `deployable?`/continuous delivery, this can unblock or trigger an unauthorized deploy on a repository the attacker never had write access to — matching the "unauthorized deploy" Critical-impact category. It also constitutes an authorization boundary break equivalent to "cross-repository writes," since the write (a `Status` record) lands on a `Commit` tied to a stack/repository outside the attacker's authenticated organization.

### Likelihood Explanation
Medium: the attack requires the attacker to (a) already control a repository/organization onboarded to the target Shipit instance (so their webhook signature is valid), and (b) be able to produce a commit whose SHA-1 collides with a specific target commit — feasible when full commit metadata (tree, parents, author/committer name+email+timestamps, message) of the target commit is public/known, which is often the case for public repositories or forks/mirrors sharing history. This is more involved than a trivial forgery but does not require any secret, session, or GitHub App private key — only ordinary write access to one onboarded repository.

### Recommendation
Scope `StatusHandler#process` (and any other handler using bare identifiers like `sha`) to the repository/stack identified by the webhook payload, mirroring `Handler#stacks`/`Repository.from_github_repo_name(repository_name)`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the organization whose signature was verified is the same one whose commits/stacks can be mutated by the event.

### Proof of Concept
1. Attacker owns/administers `org-attacker/repo-a`, which is onboarded to the target Shipit instance (so `Shipit.github(organization: 'org-attacker')` has a valid webhook secret and GitHub signs events for it).
2. Attacker identifies a target `Commit` in a different stack, e.g. `org-victim/repo-b`, and its public commit metadata (tree hash, parents, author/committer info, message, timestamps) via GitHub's API/UI.
3. Attacker crafts a commit object in `repo-a` with identical tree/parents/author/committer/message/timestamps such that `git hash-object` produces the exact same SHA-1 as the victim commit, and pushes/creates it in `repo-a`.
4. Attacker calls `POST /repos/org-attacker/repo-a/statuses/{sha}` (GitHub Statuses API) setting `state: success`.
5. GitHub sends a `status` webhook with `repository.owner.login = "org-attacker"` and `sha = <colliding sha>`, signed with `org-attacker`'s webhook secret.
6. `WebhooksController#verify_signature` verifies successfully against `org-attacker`'s secret.
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the victim's `Commit` record in `org-victim/repo-b`'s stack, and calls `create_status_from_github!`, forging a "success" status on a commit the attacker never had access to — potentially unblocking a deploy gated on that status.
