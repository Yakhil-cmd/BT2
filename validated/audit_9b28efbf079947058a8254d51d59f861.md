### Title
Cross-organization Team hijack via `membership` webhook — `organization.login` trusted independently of the org whose secret verified the request - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check against using `repository_owner`, which prefers `params.dig('repository','owner','login')` and only falls back to `params.dig('organization','login')` if no `repository` key is present. [1](#0-0) [2](#0-1)  `MembershipHandler#find_or_create_team!` independently reads `params.organization.login` to set `Team#organization`, with no cross-check that this value matches the organization whose secret was used for verification. [3](#0-2)  Because the attacker fully controls the raw JSON body and computes the HMAC with their own org's known `webhook_secret`, they can inject a fabricated `repository.owner.login` field pointing at their own org (to pass signature verification) while setting a different `organization.login` value to write a `Team`/`Membership` record scoped to a victim organization.

### Finding Description
The intended (and required) binding is: `organization_used_for_signature_verification == params.organization.login used to create/label the Team`, i.e. `repository_owner == params.organization.login`. Before tracing the code, this equality is assumed to hold because a real `membership` webhook payload from GitHub has no `repository` key, so both values are read from the same `organization.login` field. However, the controller does not enforce this equality directly — it is only true if the attacker doesn't inject a `repository` key.

`WebhooksController#create` does `JSON.parse(request.raw_post)` on the raw attacker-controlled body [4](#0-3) , and `verify_signature` picks the GitHub App/org config via `repository_owner`, preferring `repository.owner.login` over `organization.login`: [2](#0-1) 

Since the attacker constructs the entire raw body themselves (and signs it with the `webhook_secret` of an organization X they legitimately control/configured in Shipit's multi-org `secrets.github` config, per `Shipit.github_app_config`) [5](#0-4) , they can add an arbitrary `repository.owner.login: "X"` field (not naturally present in a real `membership` payload) so `verify_signature` selects org X's `webhook_secret` and passes, while simultaneously setting `organization.login: "Y"` in the same JSON body. `MembershipHandler#find_or_create_team!` then trusts `params.organization.login` verbatim to set `team.organization`, and `params.team.id` to find/create the `Team` row, with no comparison to `repository_owner`/org X: [6](#0-5) 

The `ExplicitParameters` schema on `MembershipHandler` only validates types/presence of `team.id`, `team.name`, `team.slug`, `team.url`, `organization.login`, `member.login` — it does not require the absence of a `repository` key or any cross-field consistency check [7](#0-6) . No other guard (`drop_unhandled_event`, `User#authorized?`, model validations) checks that the `Team#organization` being written matches the organization that authenticated the request.

Attacker request: POST `/webhooks` with header `X-Github-Event: membership`, body:
```json
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name": "...", "slug": "...", "url": "..."},
  "organization": {"login": "victim-org"},
  "repository": {"owner": {"login": "attacker-org"}},
  "member": {"login": "attacker-github-login"}
}
```
signed with `X-Hub-Signature` computed via HMAC-SHA1 using `attacker-org`'s `webhook_secret`.

### Impact Explanation
`find_or_create_team!` creates/updates a `Team` row with `organization: "victim-org"` and the attacker's chosen `github_id`, then `team.add_member(member)` inserts a `Membership` linking the attacker's own GitHub login to that team. [6](#0-5)  If `Shipit.github_teams` includes a team from `victim-org` (an OAuth-authorizing team), and the attacker's crafted `team.id` collides with that team's `github_id`, `User#authorized?` (driven by `Membership` rows) will subsequently treat the attacker as authorized for `victim-org`'s Shipit stacks/deploys, without ever being vetted by `victim-org`. This matches the High severity category: escalation into `Shipit.github_teams` authorization using a foreign organization's own configured secret, spanning across tenants in a multi-org Shipit deployment.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations via the multi-org `secrets.github` schema (`github_app_config`), (2) the attacker legitimately controls at least one configured organization (`X`) and therefore knows/derives its `webhook_secret` (e.g., they registered their own org's GitHub App integration with Shipit), and (3) the attacker knows or guesses the victim team's `github_id` (guessable/enumerable via GitHub's public team API for orgs whose teams are visible, or via prior legitimate membership webhooks observed). Given these preconditions — realistic for any Shipit deployment supporting multiple tenant organizations — the attack is a single unauthenticated HTTP POST, fully repeatable and scriptable against arbitrary victim organizations/teams.

### Recommendation
In `WebhooksController#verify_signature`/`repository_owner`, do not allow `membership`/`organization`-scoped events to be verified using a `repository.owner.login` value that differs from `organization.login` in the same payload — for organization-level events, verification should be tied strictly to `params.dig('organization','login')`, and for repository events strictly to `params.dig('repository','owner','login')`, never falling back cross-type. Additionally, `MembershipHandler#find_or_create_team!` should assert `params.organization.login == repository_owner` (or receive the verified organization from the controller context) before creating/updating a `Team`, rejecting the webhook otherwise.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/membership_handler_test.rb`):
1. Configure `secrets.github` with two orgs, `attacker-org` (webhook_secret `"attacker_secret"`) and `shopify` (webhook_secret `"shopify_secret"`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Build payload: `{"action"=>"added","team"=>{"id"=>shipit_teams(:shopify_developers).github_id,"name"=>"Developers","slug"=>"developers","url"=>"..."},"organization"=>{"login"=>"shopify"},"repository"=>{"owner"=>{"login"=>"attacker-org"}},"member"=>{"login"=>"attacker"}}`.
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker_secret", payload.to_json)`.
4. POST to `/webhooks` with `X-Github-Event: membership` and the above signature/body.
5. Assert response is `200`/`204` (accepted) — establishing `repository_owner == "attacker-org"` (verified against `attacker_secret`) while `params.organization.login == "shopify"` (the value written to `Team#organization`).
6. Assert `Membership.exists?(team: shipit_teams(:shopify_developers), user: Shipit::User.find_by(login: "attacker"))` is `true`, and that `User.find_by(login: "attacker").authorized?` becomes `true` if `shopify_developers` is in `Shipit.github_teams`, demonstrating the equality `repository_owner == params.organization.login` was broken and exploited.

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
