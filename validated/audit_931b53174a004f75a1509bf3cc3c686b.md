### Title
Merkle leaf and internal-node hashing use the same unkeyed function without domain separation, enabling "node-as-leaf" forgery of `in merkle` authentifier proofs - (File: merkle.js)

### Summary
`merkle.js` computes both leaf hashes and internal-node hashes with the identical function `hash(str) = sha256(str)`, with no prefix/tag to distinguish a leaf hash from an internal node hash. Internal nodes are computed as `hash(left + right)` [1](#0-0)  while leaves are computed as `hash(element)` [2](#0-1) . Because the same hash function and no domain tag is used for both, a value equal to the raw concatenation of two sibling hashes `H_L + H_R` hashes to exactly the same digest as the real parent node `hash(H_L + H_R)`. This is the same root cause as the reported Sherlock issue (`keccak256` reused for a 64-byte leaf and for 32+32-byte sibling concatenation in `FootiumPrizeDistributor.sol`), just implemented with `sha256`/string concatenation instead of `keccak256`/`abi.encode`. The code even contains a developer comment flagging this exact class of bug: `// Node-as-Leaf issue might matter in some cases` at `verifyMerkleProof` [3](#0-2) .

### Finding Description
`verifyMerkleProof(element, proof)` walks the sibling path starting from `hash(element)` and repeatedly applies the same `hash(a+b)` combiner used to build internal nodes [2](#0-1) . Since leaf-hashing and node-hashing are indistinguishable, any two adjacent, already-public tree hashes `H_L, H_R` (siblings revealed by any legitimate proof, or by `getMerkleRoot`/`getMerkleProof` outputs that get published) can be concatenated into a synthetic "element" string `H_L + H_R`. Hashing that string reproduces the real parent node's hash exactly, so a proof that starts one level above that parent (using the real sibling path from there to the root) will pass `verifyMerkleProof` even though `H_L + H_R` was never one of the original leaves.

This primitive is consumed directly by the `in merkle` authentifier, used when validating address definitions:
```
case 'in merkle':
    ...
    var proof = merkle.deserializeMerkleProof(serialized_proof);
    if (!merkle.verifyMerkleProof(element, proof)){
        fatal_error = "bad merkle proof at path "+path;
        return cb2(false);
    }
    dataFeeds.dataFeedExists(arrAddresses, feed_name, '=', proof.root, min_mci, objValidationState.last_ball_mci, false, cb2);
``` [4](#0-3) 

Here `element` is the fixed value baked into the address definition, but `serialized_proof` (siblings, index, and implicitly the resulting `proof.root`) is fully supplied by whoever is trying to satisfy the authentifier when spending from/using that address (`assocAuthentifiers[path]`). An attacker who does not hold the real inclusion proof for `element` can instead search for two already-public sibling hashes `H_L, H_R` in *any* Merkle tree ever committed by the oracle (via a data feed) such that `H_L + H_R === element` (or, working the other direction, pick which oracle-posted root to target and locate a real internal node pair whose concatenation happens to already equal the fixed `element`), then submit a "proof" consisting of the real sibling path from that internal node up to the root. `verifyMerkleProof` will accept it, and `dataFeeds.dataFeedExists` will confirm `proof.root` was genuinely posted by the oracle - satisfying the authentifier without the attacker ever having a legitimate inclusion proof of `element`.

The same unkeyed leaf/node hashing is reused by the `is_valid_merkle_proof` oscript/AA function [5](#0-4) , which evaluates attacker/trigger-supplied `element` and `proof` and is available to any AA trigger sender; any AA that trusts a root value (e.g., stored in a state variable, or checked against a data feed) as a whitelist/allowlist commitment and calls `is_valid_merkle_proof` inherits the same node-as-leaf forgery weakness.

### Impact Explanation
`in merkle` is a first-class authentifier operator usable inside address definitions to gate signing/spending conditions on Merkle-tree membership proven against an oracle-posted data feed root. If a definition author relies on `in merkle` (alone or combined with other conditions) to authorize spending, an attacker able to construct a colliding node-as-leaf proof from any previously-published tree/root by the referenced oracle(s) can satisfy the authentifier without ever legitimately proving the required condition, resulting in unauthorized use of the address's spending authority (fund loss). The same weakness undermines any AA that uses `is_valid_merkle_proof` to gate fund release against a whitelist/root, potentially causing AA fund loss to an unauthorized trigger sender.

### Likelihood Explanation
Exploitation requires the attacker to find or influence a pair of sibling hashes in a tree committed by the trusted oracle such that their concatenation equals the definition's fixed `element` (for `in merkle`) or is useful for the specific AA logic (for `is_valid_merkle_proof`). This is opportunistic rather than universally exploitable on every deployment, but it is a structural flaw acknowledged in the code itself ("Node-as-Leaf issue might matter in some cases"), and any deployment where the oracle publishes multiple/growing Merkle trees over time, or where tree internal nodes are otherwise observable (e.g., via other legitimately-shared proofs), materially raises the chance that a matching collision exists.

### Recommendation
Add domain separation between leaf and internal-node hashing in `merkle.js`, e.g. prefix leaves with a distinct tag/byte (`hash("leaf:" + element)`) and internal nodes with a different tag/byte (`hash("node:" + left + right)`), and version the proof format so `verifyMerkleProof`, `getMerkleRoot`, and `getMerkleProof` all incorporate this domain separation consistently. Existing callers (`in merkle` authentifier, `is_valid_merkle_proof` oscript function) require no further change once the primitive itself is fixed.

### Proof of Concept
1. Oracle publishes a Merkle root `R` for some unrelated tree `T` and, in the normal course of proof exchanges, reveals two sibling hashes `H_L` and `H_R` at some internal level of `T` (e.g., by providing any valid proof for a leaf under that subtree, which necessarily discloses the sibling path including `H_L`/`H_R`).
2. An address definition contains `['in merkle', [[oracle_address], 'feed_name', ELEMENT, 0]]` where `ELEMENT` happens to equal the byte-concatenation `H_L + H_R` (the attacker can search across all oracle-published trees/roots for such a match, or, if they control the definition, choose `ELEMENT` to match a pair they expect to eventually appear).
3. To satisfy the authentifier, the attacker builds `serialized_proof` using the real sibling path from the parent of `H_L`/`H_R` up to `R` (skipping the leaf level entirely) and index equal to that parent's position, per `merkle.serializeMerkleProof` format [6](#0-5) .
4. `merkle.verifyMerkleProof(ELEMENT, proof)` computes `hash(ELEMENT) = hash(H_L + H_R)`, which equals the real parent node hash, then continues up the (real) sibling path and lands on `R`, matching `proof.root` [2](#0-1) .
5. `dataFeeds.dataFeedExists(...)` confirms `R` was indeed posted by the oracle, and `definition.js` accepts the authentifier as valid even though `ELEMENT` was never an actual leaf that the oracle intended to commit to [4](#0-3) .

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function serializeMerkleProof(proof){
	var serialized_proof = proof.index;
	if (proof.siblings.length > 0)
		serialized_proof += "-"+proof.siblings.join("-");
	serialized_proof += "-"+proof.root;
	return serialized_proof;
}

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}
