## Title
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` bypass `review_stacks_enabled` via operator‑precedence bug, allowing unauthorized stack provisioning - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`OpenedHandler#provision?` and the structurally identical `ReopenedHandler#unarchive?` combine `repository.review_stacks_enabled` with the three provisioning-behavior branches using Ruby's default `&&`/`||` precedence, so `review_stacks_enabled` only gates the `allow_all` branch and is silently ignored for `allow_with_label`/`prevent_with_label`. An attacker who controls a PR's label on a repository configured with `review_stacks_enabled: false, provisioning_behavior: allow_with_label` can still trigger stack creation/unarchival and `Shipit::ReviewStackProvisioningQueue.add` → `enqueue_for_provisioning` on every open/reopen cycle.

### Finding Description
The intended binding is: `provision-or-unarchive-triggered == repository.review_stacks_enabled AND <behavior-specific rule>`, i.e. `review_stacks_enabled` must gate every branch. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`. `review_stacks_enabled` is parenthesized only with the first disjunct, so when `review_stacks_enabled == false`, `provisioning_behavior == allow_with_label`, and the PR carries the configured label, the second disjunct evaluates to `true` and `provision?` returns `true` despite review stacks being disabled for the repository. The identical pattern exists in: [2](#0-1) 

By contrast, `LabeledHandler`/`UnlabeledHandler` correctly AND `review_stacks_enabled` across the *entire* condition at the top level (`params.action == "labeled" && pull_request_state == "open" && repository.review_stacks_enabled && (archive? || unarchive?)`), confirming that `review_stacks_enabled` is meant to be a global gate, not one scoped to `allow_all` only.

Exploit flow: attacker opens a PR against a repository where the operator set `review_stacks_enabled=false` but left `provisioning_behavior=allow_with_label` configured (e.g., disabled review stacks temporarily, or a stale/misconfigured setting) and adds the configured label to their own PR (label creation on one's own PR requires no special privilege beyond opening the PR in many setups, or is otherwise attacker-controlled webhook content). `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!` → `create!` → `Shipit::ReviewStackProvisioningQueue.add(stack)` → `stack.enqueue_for_provisioning` → `update!(awaiting_provision: true)`, at `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:72-85` and `app/models/shipit/review_stack.rb:103-107`. Closing/reopening the PR repeats the cycle through `ReopenedHandler#process` → `ReviewStackAdapter#unarchive!` → `Shipit::ReviewStackProvisioningQueue.add(stack)` again, each time re-flagging `awaiting_provision`. Once the background `ReviewStackProvisioningQueue.work`/provisioner runs, the stack proceeds through provisioning and executes `shipit.yml` steps against the attacker's branch content.

No other guard intercepts this: `respond_to_pull_request_opened?`/`respond_to_pull_request_reopened?` call `provision?`/`unarchive?` directly with no additional outer `review_stacks_enabled` check, unlike the labeled/unlabeled handlers.

### Impact Explanation
This allows an unprivileged PR author to force stack creation, re-provisioning, and re-execution of `shipit.yml` steps for a repository whose operator explicitly disabled review-stack provisioning, using only PR open/reopen/label actions. This is a real authorization bypass on the `review_stacks_enabled` flag intended to gate the entire feature, matching Critical impact category: a command runs (deploy pipeline execution against attacker-controlled branch) that should not, for a repository state (`review_stacks_enabled=false`) that did not authorize it. It is repeatable indefinitely by reopening the same PR, and applies to any repository misconfigured this way (any repo with `review_stacks_enabled=false` + `allow_with_label`/`prevent_with_label`).

### Likelihood Explanation
Requires the specific repository configuration `review_stacks_enabled=false` with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible state, e.g., an operator disabling the feature without also reverting `provisioning_behavior`). Given that configuration, the attacker cost is minimal: open a PR, add/remove the configured label, and open/close/reopen. No secrets or elevated privileges are required.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all branches: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && label_present?) || (prevent_with_label? && !label_present?))` in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (and analogously for `reopened_handler_test.rb`):
```ruby
test "does not provision when review_stacks_enabled is false even with allow_with_label and label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: `repository.review_stacks_enabled == false` while `OpenedHandler.new(payload).send(:provision?) == true` before the fix (divergence), and `== false` after applying the parenthesization fix (equality restored).
