### Title
Unqualified `--ref` in `repoSync.fetch` lets an attacker-pushed tag shadow a same-named branch, causing FETCH_HEAD to resolve to unauthorized content - (File: main.go)

### Summary
`repoSync.fetch` builds the fetch argv as `fetch <repo> <ref> --verbose --no-progress --prune --no-auto-gc [...]` using the raw, unqualified `--ref` string the operator supplied, rather than a fully-qualified refspec like `refs/heads/<ref>`. Git's own remote-side ref disambiguation for an unqualified name checks `refs/tags/<name>` before `refs/heads/<name>`, so if a repo has both, `git fetch <repo> <name>` will fetch the tag object, not the branch tip.

### Finding Description
In `main.go`, `repoSync.fetch` at [1](#0-0)  constructs the fetch command directly from `git.ref`:
```
args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
```
`SyncRepo` calls `git.fetch(ctx, git.ref)` and then resolves the fetched object via `rev-parse FETCH_HEAD^{}` [2](#0-1) . Neither call qualifies the refname with `refs/heads/` or `refs/tags/`, so resolution of the ambiguous name is delegated entirely to git's default ref-disambiguation rules on the remote/negotiation side, which prefer `refs/tags/<name>` over `refs/heads/<name>` for an otherwise-identical short name. If a repo maintainer names a branch `main` and an attacker with push access creates a tag also named `main` pointing at different, attacker-chosen content, the `git fetch <repo> main` invocation in `fetch()` can resolve to the tag object instead of the branch tip that the operator intended when they configured `--ref main`. The subsequent `SyncRepo` logic treats whatever `FETCH_HEAD^{}` resolves to as authoritative and publishes it via the symlink, with no check that the fetched object actually came from `refs/heads/<ref>` as opposed to `refs/tags/<ref>` or any other ref matching the short name.

The test suite (`test_git.sh`) documents and exercises unqualified fetches of branches, tags, and annotated tags individually [3](#0-2) [4](#0-3) , but none of the tests exercise the case where a branch and a tag share the exact same name in the same repository, so this ambiguity is not covered or guarded against.

### Impact Explanation
If exploited, an attacker with push access to the source repository (which the threat model explicitly grants: "can push commits/branches/tags to the synced repo") can cause git-sync to publish the content of an attacker-created tag instead of the operator-designated branch tip, silently substituting unreviewed/unauthorized content into the workload that consumes the synced volume. This matches "unauthorized content published to consumers (supply-chain code substitution)."

### Likelihood Explanation
This requires attacker push access to create a ref (a tag) with the exact same short name as the branch specified in `--ref`. That precondition is explicitly stated as the granted attacker capability in this question ("push a tag whose name is identical to the branch"), so under that threat model the exploit is straightforward and fully repeatable: it does not depend on any git-sync flag, only on the general behavior of `git fetch <repo> <shortname>`. No `--one-time` specific behavior changes the mechanics — the ambiguity exists on every periodic fetch cycle, and `--one-time` just means the attacker only needs to win the race once (before the process exits) to have the wrong content published and consumed.

### Recommendation
Have `repoSync.fetch` (and the object resolution in `SyncRepo`) use a fully qualified, explicit refspec rather than relying on git's default short-name disambiguation. Specifically:
- Attempt fetch with an explicit `refs/heads/<ref>:refs/remotes/... ` (or `+refs/heads/<ref>`) refspec first when the operator's intent is a branch, and fall back progressively to `refs/tags/<ref>` and then a bare hash, rather than passing the ambiguous short name straight to `git fetch`.
- Alternatively, resolve the ref type up-front (e.g., via `git ls-remote --heads`/`--tags` against the same short name) and pick the intended ref deterministically, then use the corresponding fully-qualified refspec for the actual fetch, so tag/branch collisions cannot silently override the operator's ref selection.

### Proof of Concept
Local git-server repro (extending `test_git.sh` style tests):
```bash
mkdir upstream && pushd upstream
git init -b main
echo legit > file
git add file && git commit -qam "legit commit"
LEGIT_SHA="$(git rev-parse HEAD)"

# attacker creates a tag named identically to the branch, pointing elsewhere
git checkout --detach
echo malicious > file
git commit -qam "malicious commit"
MAL_SHA="$(git rev-parse HEAD)"
git tag main "$MAL_SHA"   # tag "main" now shadows branch "main"
git checkout main
popd

mkdir clone && cd clone
git init -b clone_branch
git fetch "file://$WORKDIR/upstream" main
# Expected (if invariant holds): FETCH_HEAD == $LEGIT_SHA (the branch tip)
# Actual: FETCH_HEAD resolves to $MAL_SHA (the tag), demonstrating tag-over-branch precedence.
git rev-parse FETCH_HEAD^{}
```
Run git-sync with `--ref=main --one-time` against `upstream`, then compare `readlink <link>`'s underlying commit hash to `$LEGIT_SHA`; it will match `$MAL_SHA` instead, confirming unauthorized content is published.
