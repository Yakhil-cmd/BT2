### Title
Session fixation on GitHub OAuth callback allows an attacker to hijack a victim's authenticated session - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` binds a freshly-authenticated GitHub identity to the *existing* session by writing `session[:user_id]` and `session[:authenticated]` without first calling `reset_session`. Because the session id itself is never rotated at the moment authentication succeeds, whoever controls that pre-existing session id (the attacker) becomes bound to the victim's `User` once the victim completes the OAuth dance on it — the exact "GitHub identity vs. `User` bound to the session" trust binding named in the ruleset, and directly analogous to the reported bug class: a check-then-write is completed on an identifier (here, the session id) that was never re-validated/re-generated for the party actually completing the privileged action.

### Finding Description
Authentication is centered on `session[:user_id]`, which `Shipit::Authentication#find_current_user` trusts unconditionally: [1](#0-0) 

The OAuth callback that establishes this trust does the following: [2](#0-1) 

Note it never calls `reset_session`. Compare this to `logout`, which explicitly does: [3](#0-2) 

The equality that should hold is: `session_id at authentication time == session_id trusted afterwards, and only for the party who actually authenticated`. Before the pull/patch, an attacker can:
1. Visit the Shipit instance unauthenticated, obtaining a session cookie/id `S` (e.g. `session[:user_id]` unset).
2. Fixate `S` onto a victim (classic session-fixation delivery: shared browser/kiosk, a subdomain-set cookie if `domain` is broadly scoped, or any mechanism that lets the attacker plant a known session identifier in the victim's browser — this is the standard precondition for any session-fixation bug and does not require an `ApiClient` token, webhook secret, GitHub App key, or repository write access).
3. Lure the victim to complete GitHub OAuth login using session `S` (e.g. by sending them the `github_authentication_path(origin: ...)` link).
4. `callback` writes `session[:user_id] = <victim's User id>` into session `S` without rotating it.
5. The attacker, still holding session `S`, is now authenticated as the victim in `current_user`, gated only by `current_user.authorized?` (team membership), inheriting whatever Shipit privileges (and thus GitHub-App-mediated deploy/rollback/merge capability) the victim has.

This is the shipit-engine analog of the ENS-name front-running bug: both are "verify-then-bind" flows where the identifier that gets bound (an ENS/DAO name vs. a session id) is never re-derived/re-validated at the moment of binding, letting a party other than the intended actor complete the operation first/instead.

### Impact Explanation
A successful fixation grants the attacker a session indistinguishable from the victim's, i.e., authentication bypass: `current_user` resolves to the victim's `User` record for the rest of that session's lifetime. Since `current_user` gates deploy triggering (`DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)`), lock/unlock, and merge-request actions in the web UI, this converts to an unauthorized deploy/rollback/merge performed as the victim — matching the "authentication bypass" / "unauthorized deploy, rollback or merge" Critical/High impact categories.

### Likelihood Explanation
Exploitation requires the attacker to be able to plant a session identifier into the victim's browser before the victim completes GitHub OAuth — a standard session-fixation precondition, not requiring any Shipit session, ApiClient token, webhook secret, or GitHub App key of the attacker's own. The vulnerable code path (`callback`) is hit by every login, and the missing `reset_session` is unconditional, so likelihood is bounded only by the attacker's ability to deliver/fixate a session id to the victim (e.g., session cookie not scoped strictly, or environments where session ids can be set via other means), which is a common and well-understood attack setup.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` before assigning `session[:user_id]` and `session[:authenticated]`, so a new session identifier is issued at the moment of authentication (mirroring what `logout` already does). This severs any session id an attacker may have fixated prior to the victim's login.

### Proof of Concept
1. Attacker (unauthenticated) opens the Shipit host, capturing session id `S` from the response `Set-Cookie` header.
2. Attacker fixates `S` in the victim's browser (any session-fixation delivery vector for the deployment's cookie scope).
3. Attacker sends the victim a link to `/github/auth/github?origin=...`.
4. Victim completes the GitHub OAuth flow; `GithubAuthenticationController#callback` runs `session[:user_id] = sign_in_github(auth)` on session `S` without regenerating it: [4](#0-3) 
5. Attacker replays session `S`; `find_current_user` resolves to the victim's `User`: [5](#0-4) 
6. Attacker now acts as the victim across the Shipit UI (subject only to `current_user.authorized?` team-membership gating, which the victim already satisfies), including triggering deploys/rollbacks/merges as that user.

      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint

      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
