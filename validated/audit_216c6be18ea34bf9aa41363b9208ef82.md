### Title
Market permanently freezes once accrued book value overflows the RAY/i128 value ceiling — every verb accrues first and panics in `scaled_to_original` - ([File: common/src/rates/scaling.rs](common/src/rates/scaling.rs))

### Summary
The MySQL CVE is a remotely triggerable, repeatable crash that takes the whole service down. The strongest analog in XOXNO Lending is the accrual-time RAY value overflow: an unprivileged user can build a very large, high-utilization market whose debt value (scaled shares × borrow index) eventually exceeds the representable RAY domain. From that point on, `accrue_step` → `scaled_to_original` panics with `MathOverflow` on every invocation. Because `global_sync` runs at the head of every mutating entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `update_indexes`), the market freezes permanently: suppliers cannot exit, borrowers cannot repay, liquidators cannot act, and bad debt cannot be socialized.

### Finding Description
Index accrual converts scaled borrow/supply shares to original token value via `scaled_to_original`, which is `scaled.mul(env, index)` — a checked multiplication that panics on overflow (common/src/rates/scaling.rs:14-16; the panic surfaces as `GenericError::MathOverflow`). `accrue_step` calls this conversion to compute utilization each chunk, and `global_sync` runs `accrue_chunk` at the top of every state-changing pool call, chunked by `MAX_COMPOUND_DELTA_MS` (contracts/pool/src/interest.rs:20-53). The borrow index is capped at `MAX_BORROW_INDEX_RAY = 10^36` (docs/reference/invariants.md INV-IDX-01), but the i128/RAY value ceiling on `borrowed × index` is reached *before* the index cap on a sufficiently large book at sustained high utilization on a steep rate curve. The repository's own harness proves this: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361) shows `try_update_indexes_for` failing with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and then both `try_withdraw_raw` and `try_repay` failing with the same error because "every verb accrues first". Nothing bounds `supplied`/`borrowed` scaled totals against future index growth at entry time; supply/borrow caps are literal asset-unit caps converted to shares at the *current* index (ADR-0015), so a cap sized for today's index does not prevent tomorrow's accrued value from crossing the ceiling.

### Impact Explanation
Permanent freezing of funds and protocol insolvency. Once the accrued `borrowed × borrow_index` (or `supplied × supply_index`) crosses i128 capacity, all entrypoints that touch the market revert in `global_sync` before any business logic runs. Supplier principal and accrued yield are locked forever; the bad debt on the book cannot be liquidated, cleaned, or recapitalized (`recapitalize` also accrues). This is a repeatable crash of the contract's core function, directly analogous to the CVE's complete availability loss — but with permanent rather than temporary effect, since `last_timestamp` is never reset and the overflowing state cannot be unwound by any unprivileged or privileged path short of an upgrade.

### Likelihood Explanation
Medium. The trigger needs three conditions: (1) a market whose governance-set caps admit a book whose scaled value, times plausible index growth over the market's lifetime, approaches ~1.7e38 raw; on high-decimal assets (e.g., 18 decimals) this is a large but plausible whale book when caps are generous or effectively lifted; (2) sustained high utilization so the steep segment of the rate curve compounds the index (the harness reaches the cliff at ~98% utilization within tens of years on the XLM curve, faster on steeper curves); (3) time — accrual is monotone, so no user action can reverse the approach once shares exist. All trigger actions (`supply`, `borrow`, `update_indexes`) are unprivileged. The main mitigating factor is that reaching the cliff requires governance caps to admit the overlarge book, which the threat model partially acknowledges ("caps must account for plausible index growth") — but the contract enforces no such relationship, and the failure mode is silent until the first panic.

### Recommendation
Track and bound the accrued *value* domain, not just the index domain:
- In `accrue_step`/`accrue_chunk`, saturate rather than panic: when `scaled × index` would overflow, clamp the index at the last representable value (treat it as an effective `MAX_BORROW_INDEX_RAY`) so accrual becomes a no-op instead of a trap, preserving exits and repayment.
- At `supply`/`borrow` admission, reject new exposure when `scaled_total × MAX_BORROW_INDEX_RAY` exceeds the safe RAY domain, deriving the cap from the worst-case index rather than the current one.
- Document and enforce the per-market "value ceiling" alongside `MAX_BORROW_INDEX_RAY` in `validation::require_cap_within_asset_domain` so governance-set caps cannot admit a book that will freeze mid-life.

### Proof of Concept
Unprivileged path (assuming caps admit the book, as the harness does with lifted caps):

```text
1. Attacker/supplier: controller.supply(hub, "BIG18", 1e9 * 1e18)        // whale supply
2. Borrower:          controller.supply(hub, "COL",  collateral)
                      controller.borrow(hub, "BIG18", ~98% of the book)  // steep-curve utilization
3. Time passes (no action needed); optionally keeper calls
                      controller.update_indexes(["BIG18"])               // permissionless
4. When borrowed * borrow_index exceeds i128 RAY capacity:
   - pool::interest::global_sync -> accrue_chunk -> accrue_step
     -> scaled_to_original(borrowed, borrow_index)                       // common/src/rates/scaling.rs:14
     -> Ray::mul panics -> GenericError::MathOverflow
5. From then on, every call that touches the market reverts before any
   business logic:
   - update_indexes -> MathOverflow
   - withdraw(supplier) -> MathOverflow    // verified: try_withdraw_raw fails
   - repay(borrower) -> MathOverflow       // verified: try_repay fails
   - liquidate / clean_bad_debt / recapitalize -> MathOverflow (all accrue first)
```

Reference implementation of the freeze: tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361 asserts `borrow_index < MAX_BORROW_INDEX_RAY` at the failure point (the index cap never engages) and confirms both withdrawal and repayment revert with `MATH_OVERFLOW` after the cliff, i.e., the market is permanently frozen.
