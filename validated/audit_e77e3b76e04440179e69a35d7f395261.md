Cross-organization webhook forgery due to signature/target binding mismatch in `WebhooksController` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` [1](#0-0) , resolved via `Shipit.github(organization:)`/`github_app_config` [2](#0-1) . All organizations share the same `WebhooksController#create` endpoint. The controller selects which organization's secret to verify the HMAC signature against using a field taken directly from the untrusted, attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`), but the handlers that actually act on the payload identify the target repository/stack using a *different, unchecked* field of that same body (`repository.full_name`). Because the two fields are never cross-validated, a party who only knows the webhook secret for Org A can forge a signed request that is verified as "from Org A" but whose `repository.full_name` points at a repository belonging to Org B, causing Shipit to act on Org B's stack.

### Finding Description
`WebhooksController#verify_signature` picks the signing organization purely from the payload: [3](#0-2) [4](#0-3) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — a value inside the raw POST body that the requester fully controls before signing it. The signature is a valid HMAC over the exact body sent, so as long as the requester knows the `webhook_secret` configured for the organization named in `repository.owner.login`, the check passes regardless of what other fields the body contains.

Once signature verification succeeds, `Shipit::Webhooks.for_event(event)` handlers are invoked with the same raw params [5](#0-4) . The base `Handler` resolves the target `Repository`/`Stack` from a *different* field of the payload, `repository.full_name`, with no relation to `repository.owner.login`: [6](#0-5) 

`PushHandler#process`, for example, uses this `stacks` scope directly to trigger a GitHub sync: [7](#0-6) 

The binding that should hold is:
`organization_whose_secret_signed_the_request == owner_of_the_repository_the_handler_acts_on`

Before the fix would apply, nothing enforces `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`. An attacker who is a legitimate collaborator/admin able to see or set the webhook secret for their own org ("Org A", e.g. `test/dummy/config/secrets_double_github_app.yml` shows two independently-configured orgs, `OrgOne`/`OrgTwo`, each with a distinct `webhook_secret`) [8](#0-7)  can:
1. Build a JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"`.
2. Sign it with Org A's known `webhook_secret` (`X-Hub-Signature`).
3. POST it to the shared webhooks endpoint.

`verify_signature` resolves `Shipit.github(organization: "OrgA")` and the signature check succeeds. `PushHandler` then resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` for Org B's stacks — a repository the attacker never authenticated against.

### Impact Explanation
This breaks the trust boundary between tenants of a multi-org Shipit deployment: possession of one organization's webhook secret becomes sufficient to force GitHub sync / status / check-suite processing against another organization's stacks, driving them toward an unauthorized deploy path (`sync_github` with an attacker-chosen `expected_head_sha`, and `StatusHandler`/`CheckSuiteHandler` similarly act on attacker-supplied `sha`/state data tied only to `repository.full_name`, not to the signing org). This is a cross-tenant/cross-repository write triggered without possessing the victim organization's credentials, matching the "Critical: cross-repository writes / unauthorized deploy" category.

### Likelihood Explanation
Exploitability requires only knowledge of one organization's configured webhook secret (something a repository admin/maintainer inside that org — not a Shipit operator — plausibly has access to, since GitHub webhook secrets are typically visible/settable by repo/org admins in GitHub's webhook settings UI), plus the ability to POST to the public `/webhooks` endpoint. No Shipit session, `ApiClient` token, or GitHub App private key is needed, and the flaw is purely a same-payload field confusion in engine code, so this is realistically reachable in any multi-organization Shipit deployment.

### Recommendation
Cross-validate the field used for signature/organization selection against the field used to resolve the target repository before dispatching to handlers — e.g., require `repository.full_name`'s owner segment to match the resolved `repository_owner`/organization whose secret verified the signature (or route webhooks per-organization instead of relying on payload-derived identifiers), rejecting requests where they diverge.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`):

1. Attacker (an admin of an `OrgA`-hosted repo with a Shipit webhook, hence in possession of `OrgA`'s `webhook_secret`) crafts:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)`.
3. POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` (per `repository_owner`) and the HMAC check passes.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Org B's stack, even though the request was never authenticated by Org B.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      head(422) unless verified

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
