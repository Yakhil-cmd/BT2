### Title
Credential Disclosure to Attacker-Controlled Submodule URLs via Host-Scoped `credential.helper` Cache - (File: main.go)

### Summary
The external report flags "use of arbitrary token addresses" — untrusted, caller/content-supplied addresses being fed directly into privileged operations without validation. The closest reachable analog in `git-sync` is that submodule URLs, which are **untrusted content pulled from the synced repository itself** (`.gitmodules`, controllable by anyone with push/PR access to the synced repo, or a MITM on an unauthenticated transport), are passed directly to `git submodule update --init --recursive` while git-sync's global credential cache is not scoped to a specific path, only to protocol+host.

### Finding Description
`git-sync` configures a global, non-path-scoped credential cache: [1](#0-0) 

Credentials (from `--username`/`$GITSYNC_PASSWORD`, `--credential`, or `--askpass-url`) are stored via `git credential approve`-style calls keyed to a URL: [2](#0-1) 

Separately, `configureWorktree` unconditionally runs `git submodule update --init [--recursive]` after checking out the fetched commit, with the submodule URLs coming entirely from the repository's own `.gitmodules` file (i.e., from the untrusted, remote-controlled tree being synced), not from any git-sync flag: [3](#0-2) 

Because `git`'s default credential matching (`credential.helper`) is scoped by protocol and host — not by path — unless `credential.useHttpPath` is explicitly enabled, any credential git-sync has cached for the primary `--repo` host (or a `--credential`-registered host) will automatically be offered by git to **any other path on that same host**, including a submodule URL an attacker embeds in `.gitmodules` after gaining push/PR access to the synced repository, or via `submodule.<name>.update = ...`/nested submodules (as exercised in `e2e::submodule_sync_default`) that can point to arbitrary paths. Nowhere in `SetupDefaultGitConfigs` or the credential-storage code path is `credential.useHttpPath` set to `true` to restrict credential exposure per-path.

### Impact Explanation
An attacker who can add or modify a `.gitmodules` entry in the synced repository (e.g., via a merged PR, a compromised branch, or a MITM'd unauthenticated fetch) can point a submodule at another repository/path under the same host as the legitimate `--repo`. When git-sync runs the automatic `git submodule update --init --recursive`, git will present the cached username/password (or askpass-url-derived token) for that host to the attacker's endpoint, disclosing the credential to an attacker-controlled resource. This is a credential-disclosure vulnerability, matching "credential or token disclosure" in the accepted-impact list.

### Likelihood Explanation
Requires: (1) `--submodules` not set to `off` (default is `recursive`), (2) credential-based auth in use (`--username`/`--password-file`, `--credential`, or `--askpass-url`), and (3) an attacker able to influence the synced repository's `.gitmodules` content (push access, PR merge, or unauthenticated transport MITM) with a submodule URL sharing the host of the credentialed endpoint. This is a realistic scenario for CI/CD or GitOps deployments where `git-sync` pulls from repos that accept external contributions, and is a well-documented git credential-leak class (the same mechanism behind several public git/GitHub-Actions credential-leak advisories). It does not require a malicious operator or leaked key — it is exploitable purely through attacker-controlled repository content, matching the scope of this scan.

### Recommendation
- Explicitly set `credential.useHttpPath=true` (or otherwise scope credentials to exact repo paths) whenever git-sync stores credentials, so cached credentials are not replayed to sibling paths on the same host.
- Consider disabling submodule credential inheritance by default, or requiring an explicit allow-list of submodule hosts/paths (mirroring the report's "add whitelisting" recommendation), especially when `--submodules=recursive` is combined with credential-based auth.
- Document this risk clearly for users combining `--credential`/`--username`+password auth with `--submodules=recursive` on repositories that accept untrusted contributions.

### Proof of Concept
1. Configure `git-sync` against `--repo=https://git.example.com/org/trusted-repo` with `--username=svc --password-file=/creds/pass` (or `--credential` for that host), and default `--submodules=recursive`.
2. An attacker with push/PR access to `trusted-repo` adds `.gitmodules` referencing `https://git.example.com/attacker/evil-repo` (same host, different path) and commits it.
3. On next sync, `git-sync` fetches the new commit, then `configureWorktree` runs `git submodule update --init --recursive` (`main.go:1733-1747`).
4. Because `credential.helper=cache` is host-scoped (no `credential.useHttpPath`), git offers the previously stored `svc`/password credential to `https://git.example.com/attacker/evil-repo`, which the attacker's git server can log, disclosing the credential. [1](#0-0) [3](#0-2) [2](#0-1) 

**Note on confidence:** I was unable to view the full body of `StoreCredentials`/`CallAskPassURL`'s exact `git credential approve` invocation and confirm whether `credential.useHttpPath` is set anywhere else in the codebase (search iterations were exhausted before I could inspect that function in full). This should be verified before treating the finding as fully confirmed rather than a strong analog based on the visible `SetupDefaultGitConfigs` code and standard git credential-helper semantics.
