### Title
`provision?` operator precedence bug allows attacker to bypass `review_stacks_enabled: false` via a self-applied PR label - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` (and the identical pattern in `ReopenedHandler#unarchive?`) uses `&&`/`||` without parentheses grouping the `review_stacks_enabled` check across all three provisioning-behavior branches. Because `&&` binds tighter than `||` in Ruby, `review_stacks_enabled` is only ANDed into the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches evaluate independently of it. This lets any pull-request author label their own PR to force `provision?` to return `true` even when the repository has `review_stacks_enabled: false`.

### Finding Description
The broken binding: the code intends `provision? == review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`, but the actual implementation is: [1](#0-0) 
which Ruby parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The `review_stacks_enabled` flag is not applied to the last two disjuncts.

Attack path: an admin previously enables review stacks with `provisioning_behavior: allow_with_label` and a `provisioning_label_name` (e.g. `"shipit"`), then later sets `review_stacks_enabled: false` intending to fully pause automatic stack provisioning for that repository (the UI and docs present this flag as the master switch: [2](#0-1) ). Because the repo still has `provisioning_behavior_allow_with_label?` true and a configured `provisioning_label_name`, any unprivileged GitHub user with fork access can open a PR and add that label — `pull_request_has_provisioning_label?` becomes true via `pull_request_label_names.include?(repository.provisioning_label_name)` [3](#0-2)  — causing `provision?` to return `true` and a review stack to be created via `ReviewStackAdapter#find_or_create!` despite the disabled flag.

Existing guards do not catch this: webhook signature verification and `ExplicitParameters` schema validation only confirm the webhook came from GitHub for that repo/PR, they do not enforce authorization semantics of `review_stacks_enabled`; that enforcement is expected to happen in `provision?` itself, and it is exactly this method that is broken.

### Impact Explanation
Any GitHub user who can open a pull request against the tracked repository (including from a fork, which requires no special privilege) can force Shipit to create/provision a review stack even though the repository owner explicitly disabled review-stack provisioning. This results in unauthorized stack creation and (depending on host-app `ProvisioningHandler`) execution of infrastructure provisioning code (`up`) for that repository — an unauthorized resource-creation action the repository owner explicitly turned off. The blast radius is scoped to repositories where an operator has this specific combination of settings (`review_stacks_enabled: false` + `provisioning_behavior: allow_with_label` or `prevent_with_label` + a set `provisioning_label_name`); it does not cross tenant/repository boundaries by itself, but it is a genuine, repeatable authorization bypass matching "unauthorized deploy" class impact for that repository's review-stack lifecycle.

### Likelihood Explanation
Requires the specific repository misconfiguration described above (review stacks previously enabled with `allow_with_label`/`prevent_with_label` and then disabled), which is a plausible real-world admin action ("temporarily pause review stacks" without resetting provisioning_behavior). No secrets are needed; the label name is visible in the repository settings UI to anyone with view access, or guessable (default patterns like `"shipit"`). Cost to the attacker is one PR + one label action, fully repeatable on every PR while the misconfiguration persists.

### Recommendation
Fix the operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` (and equivalent logic in `LabeledHandler`/`UnlabeledHandler` if affected) by explicitly parenthesizing `review_stacks_enabled` across all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false, regardless of label match (allow_with_label)" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `provision?` returns `true` and a stack is created purely from the label match, with `repository.review_stacks_enabled == false` and no other authorization signal — demonstrating the equality `provision? == review_stacks_enabled && behavior_check` does not hold in the current implementation.
