### Title
`DenyReserveTransferToRelayChain` in `asset-hub-kusama`'s `Barrier` only scans top-level instructions, allowing a nested `SetAppendix`/`SetErrorHandler` sub-program to perform a reserve transfer of KSM to the Relay Chain - ([File: system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs])

### Summary
`Barrier` on Asset Hub Kusama wraps `DenyReserveTransferToRelayChain` directly (not `DenyRecursively<DenyReserveTransferToRelayChain>`), while other chains in the same codebase (e.g. `bridge-hub-polkadot`, `bulletin-polkadot`) explicitly wrap the same deny-filter with `DenyRecursively` to close exactly this gap. Because `should_execute` is invoked once against the top-level instruction list before `XcmExecutor::execute` runs, and `SetAppendix`/`SetErrorHandler` instructions carry an *opaque* nested `Xcm<Call>` program that is executed later by the executor without a second barrier check, a user can hide `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` targeting `Parent` inside the appendix/error-handler and have it execute anyway.

### Finding Description
`Barrier` is defined as [1](#0-0)  — note the top filter is plain `DenyReserveTransferToRelayChain`, unlike `bridge-hub-polkadot`'s barrier which uses `DenyRecursively<DenyReserveTransferToRelayChain>` [2](#0-1)  and `bulletin-polkadot`'s barrier which does the same [3](#0-2) .

`DenyReserveTransferToRelayChain::should_execute` (from `xcm-builder`, an external dependency not vendored in this repo) is invoked exactly once, on the outer/top-level instruction slice, before `XcmExecutor::execute` runs the program. It iterates the top-level instructions (so simple reordering of top-level instructions does *not* bypass it), but it has no visibility into instructions nested inside `SetAppendix(Xcm<Call>)` or `SetErrorHandler(Xcm<Call>)`, because those inner programs are opaque data fields of the outer instruction and are executed by the `XcmExecutor` *after* the initial barrier check, without re-invoking `Barrier::should_execute`. `DenyRecursively` exists specifically to walk into these nested sub-programs; chains that omit it (Asset Hub Kusama among them) do not get that protection.

Exploit flow for an unprivileged signed user via `PolkadotXcm::execute` on Asset Hub Kusama:
1. `WithdrawAsset(their_own_KSM)` — pulls the caller's own KSM into the holding register (a normal, allowed operation).
2. `SetAppendix(Xcm(vec![DepositReserveAsset { assets: All, dest: Parent, xcm: Xcm(vec![]) }]))` — this instruction type does not match any pattern in `DenyReserveTransferToRelayChain`, so the top-level check passes.
3. Program ends; the executor then runs the appendix, which executes `DepositReserveAsset` targeting `Parent`, sending the assets back to the Relay Chain as a reserve transfer — the exact operation the filter is meant to deny — without any additional barrier check.

The `AllowTopLevelPaidExecutionFrom<Everything>`/`TakeWeightCredit` checks in the `Allow` tuple only gate execution admission (fee/weight), not the content of nested sub-programs, so they do not stop this.

### Impact Explanation
An unprivileged user can route their own KSM back to the Relay Chain via a reserve transfer that the runtime explicitly intends to forbid on Asset Hub Kusama, bypassing the intended asset-routing/accounting invariant enforced by `DenyReserveTransferToRelayChain`. This breaks the "filters/barriers must not be bypassable" invariant for this specific denied pattern, though the assets remain the attacker's own (no theft of others' funds) — the concrete scoped impact is an unauthorized reserve-transfer path to the relay chain that circumvents the intended routing policy.

### Likelihood Explanation
Feasible and repeatable by any signed account with KSM and access to `pallet_xcm::execute`, requiring no special privileges, proxy authorization, or governance action — only constructing an XCM program with `SetAppendix`/`SetErrorHandler` wrapping the denied instruction. No preconditions beyond holding some KSM to withdraw and normal execution weight/fee.

### Recommendation
Wrap the deny filter used in `asset-hub-kusama`'s (and other affected chains') `Barrier` with `DenyRecursively`, i.e. change `DenyReserveTransferToRelayChain` to `DenyRecursively<DenyReserveTransferToRelayChain>` in the `DenyThenTry<...>` tuple, matching the pattern already applied in `bridge-hub-polkadot` and `bulletin-polkadot`.

### Proof of Concept
xcm-emulator/integration test plan (extending the existing `reserve_transfer_ksm_from_asset_hub_to_relay_fails` test at `integration-tests/emulated/tests/assets/asset-hub-kusama/src/tests/reserve_transfer.rs:561-597`):
```rust
#[test]
fn reserve_transfer_ksm_from_asset_hub_to_relay_via_appendix_bypasses_deny() {
    let signed_origin = <AssetHubKusama as Chain>::RuntimeOrigin::signed(AssetHubKusamaSender::get());
    let amount_to_send: Balance = ASSET_HUB_KUSAMA_ED * 1000;
    let assets: Assets = (Here, amount_to_send).into();

    // Build: WithdrawAsset(assets) ; SetAppendix(DepositReserveAsset{dest: Parent, ..})
    let message: Xcm<()> = Xcm(vec![
        WithdrawAsset(assets.clone()),
        SetAppendix(Xcm(vec![DepositReserveAsset {
            assets: AllCounted(1).into(),
            dest: Parent.into(),
            xcm: Xcm(vec![]),
        }])),
    ]);

    AssetHubKusama::execute_with(|| {
        let result = <AssetHubKusama as AssetHubKusamaPallet>::PolkadotXcm::execute(
            signed_origin,
            bx!(xcm::VersionedXcm::from(message)),
            Weight::from_parts(10_000_000_000, 1_000_000),
        );
        // Expected (fixed) behavior: denied, same as the direct-instruction test.
        assert_err!(result, /* Filtered / Barrier error */);
        // Currently (bug): result succeeds and Relay Chain sovereign/receiver
        // balance increases, proving the reserve transfer executed despite the deny filter.
    });
}
```
Assertions: (1) on a patched runtime with `DenyRecursively<DenyReserveTransferToRelayChain>`, the call is rejected with the same `Filtered`/`Barrier` error as the direct top-level case; (2) on the current runtime, the call succeeds and KSM is observed leaving Asset Hub's sovereign account and arriving at the Relay Chain, demonstrating the bypass.
