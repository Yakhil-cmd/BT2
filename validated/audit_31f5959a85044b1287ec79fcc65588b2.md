### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` policies, letting an unprivileged PR author auto-provision a review stack and trigger a deploy task that leaks secrets via `TaskCommands#env` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` intends to require `repository.review_stacks_enabled` as a master switch for all three provisioning-behavior modes, but Ruby's `&&`/`||` precedence only applies that guard to the `allow_all?` branch. If a repository is configured with `provisioning_behavior_allow_with_label?` or `provisioning_behavior_prevent_with_label?` while `review_stacks_enabled` is `false`, an unprivileged PR author can still satisfy the label condition and get `provision?` to return `true`, causing a `ReviewStack` to be created and provisioned from their own (potentially malicious) `shipit.yml`. The task that later runs against that stack builds its execution environment via `TaskCommands#env`, which merges `deploy_spec.machine_env` sourced from that attacker-controlled `shipit.yml`, exposing `@stack.env`/deploy-time secrets (including `GITHUB_TOKEN`) to attacker-authored shell steps.

### Finding Description
The intended binding is: `provision? == (review_stacks_enabled && policy_satisfied?)` — i.e., no stack should ever be auto-created when `review_stacks_enabled` is `false`, regardless of behavior mode.

The actual code in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`: [1](#0-0) 
is parsed by Ruby as:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```
Because `&&` has higher precedence than `||`, `review_stacks_enabled` only gates the `allow_all?` disjunct. If an operator sets `review_stacks_enabled = false` but leaves `provisioning_behavior` at `allow_with_label` (with a label configured) or `prevent_with_label`, `provision?` still evaluates `true` whenever the label condition on the second/third disjunct is met — with no dependency on `review_stacks_enabled` at all.

Exploit flow:
1. Attacker (unprivileged, per threat model can open a PR and label their own PR) opens a pull request against the target repository.
2. If behavior is `prevent_with_label`, simply not adding the provisioning label satisfies `!has_label?`, making `provision?` true even with `review_stacks_enabled == false`. If behavior is `allow_with_label`, attacker adds the known label to their own PR.
3. `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!`, which creates a `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` from the attacker's PR and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [2](#0-1) 
4. Once the stack is provisioned/deployed, `TaskCommands#perform` builds each step's `Command` with `env:` computed by `TaskCommands#env`, which merges `@stack.env`, `deploy_spec.machine_env`, and `@task.env`: [3](#0-2) 
`deploy_spec` is loaded from the checked-out working directory of that same attacker-supplied branch/commit (`DeploySpec::FileSystem.new(@task.working_directory, @stack)`), so the attacker's `shipit.yml` steps run with this merged environment, including `Shipit.github` deploy credentials/`GITHUB_TOKEN` if configured for the stack. [4](#0-3) 

Why guards fail: `respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?`, and there is no separate, unconditional check of `repository.review_stacks_enabled` before calling `provision?`. [5](#0-4) 
None of `verify_signature`, `ExplicitParameters` schema, or model validations touch this authorization logic; they validate payload shape/signature, not the provisioning policy semantics, so they don't catch the precedence error.

### Impact Explanation
An attacker who does not administer the repository can force creation of a `ReviewStack` and get a deploy/provisioning task executed against it, purely by opening (and optionally labeling) their own pull request — even though the repository owner has explicitly disabled review stacks (`review_stacks_enabled = false`). Because the executed `shipit.yml` is sourced from the attacker's own branch, any step they define runs with the merged environment from `TaskCommands#env`, which can include `GITHUB_TOKEN`/deploy secrets configured on `Shipit.github` for that stack. This matches the Critical category: exfiltration of `GITHUB_TOKEN`/deploy-time secrets, and an unauthorized deploy/provisioning action on a repository whose owner opted out of the feature.

### Likelihood Explanation
This requires a specific but plausible repository misconfiguration: `review_stacks_enabled == false` combined with `provisioning_behavior` left at `allow_with_label` or `prevent_with_label` (e.g., an operator toggling the master switch off without resetting the behavior mode, or the two settings being managed independently in the UI). Given that combination, attacker cost is trivial — open a PR, optionally add/omit a label they control on their own PR — and it is repeatable against any repository sharing this configuration state, at zero cost to the attacker.

### Recommendation
Fix the boolean grouping in `provision?` so `review_stacks_enabled` gates all three modes, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Audit `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler` for the same pattern and apply the same fix if present.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (existing suite already has a `configure_provisioning_behavior` helper):
```ruby
test "does not create stacks when review_stacks_enabled is false, regardless of behavior/label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no label -> !has_label? true -> should NOT provision

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Given the current code, this assertion fails (a stack IS created), demonstrating `review_stacks_enabled == false` does not equal actual non-provisioning behavior for `prevent_with_label`/`allow_with_label` modes — confirming the broken binding `provision? != (review_stacks_enabled && policy_satisfied?)`.
