### Title
Cross-organization webhook forgery via organization/repository binding mismatch in `WebhooksController#verify_signature` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a payload against based on `repository_owner`, a value read from the *unauthenticated* JSON body (`repository.owner.login` or `organization.login`). Once the HMAC check passes, the entire raw payload — including an independent `repository.full_name` field — is handed unchanged to the event handlers. Nothing ties the organization whose secret validated the signature to the repository that the handlers actually act on. In a multi-organization Shipit deployment (`docs/setup.md`, "Using Multiple Github Applications"), a party who legitimately controls a webhook secret for one configured organization can sign an arbitrary payload claiming `repository.full_name` belongs to a completely different, unrelated tracked organization/repository.

### Finding Description
`verify_signature` derives the verifying organization purely from attacker-controlled JSON, then verifies the raw body against that organization's secret: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the `GitHubApp` (and its `webhook_secret`) purely by that string: [3](#0-2) 

Once `verify_webhook_signature` returns true, `create` dispatches the full raw JSON to handlers unmodified: [4](#0-3) 

Handlers resolve the target `Repository`/`Stack` from a **different** field of the same payload — `repository.full_name` — with no cross-check against `repository_owner`, the field that was used for signature selection: [5](#0-4) [6](#0-5) 

Because HMAC-SHA1 validates the byte content of the request body against whichever secret was selected — and the secret selection and the acted-upon repository are read from two independent, equally attacker-controlled JSON keys (`repository.owner.login` vs `repository.full_name`) — a party who knows/controls organization A's `webhook_secret` (e.g., because they administer a GitHub App installed on organization A, one of the multiple organizations configured under `secrets.github`) can craft and correctly sign a payload where:
- `repository.owner.login` = `"OrgA"` (used to pick OrgA's secret for verification), and
- `repository.full_name` = `"OrgB/some-tracked-repo"` (used by the handler to select the actual `Repository`/`Stack` to act on).

The binding that should hold — *the organization whose secret authenticated the request == the repository the handlers write/act upon* — is broken. This lets a webhook holder for one tracked org forge push/status/pull_request events for stacks belonging to a different tracked org on the same Shipit instance.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly listed as in-scope. Depending on the forged event type, an attacker with a valid `webhook_secret` for *any one* configured organization could:
- Forge `status` events to post fabricated CI states for arbitrary commit SHAs on a victim organization's repository (`app/models/shipit/webhooks/handlers/status_handler.rb`), which — combined with `continuous_deployment`/CI-gated deploy logic — can enable an **unauthorized deploy** of an attacker-chosen commit.
- Forge `push` events to trigger `GithubSyncJob` for a victim stack, or `pull_request` events to create/update review stacks belonging to a repository the attacker does not control.

This satisfies the "unauthorized deploy" high/critical impact criterion.

### Likelihood Explanation
Exploitability requires the attacker to already possess a valid `webhook_secret` for at least one organization configured in the same Shipit instance's multi-org `secrets.github` block — this is a real precondition (not "no credential boundary crossed") but is a materially weaker requirement than compromising the target organization's own secret, GITHUB_TOKEN, or a Shipit session/API token. Any GitHub App admin/webhook operator for organization A gains the ability to forge events for organization B purely due to the engine's binding gap, which is exactly the kind of trust-crossing this scan looks for. Likelihood is elevated further by the fact this is a documented, supported configuration (`docs/setup.md`, "Using Multiple Github Applications").

### Recommendation
After verifying the signature, re-derive the repository/stack strictly from the verified organization context (e.g., require that `repository.full_name`'s owner segment matches the `repository_owner` used to select the webhook secret, or resolve `Repository` scoped by the authenticated organization) and reject the event otherwise.

### Proof of Concept
1. Deploy Shipit configured with multiple GitHub organizations, e.g. `OrgA` and `OrgB`, each with distinct `webhook_secret`s, both with tracked stacks (`docs/setup.md` "Using Multiple Github Applications" section).
2. As the operator/administrator of `OrgA`'s installed GitHub App (who knows `OrgA`'s `webhook_secret`), construct a JSON payload:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "branches": [{"name": "master"}]
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac(webhook_secret_OrgA, payload)>` and POST it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` computes `repository_owner = "OrgA"`, fetches OrgA's `GitHubApp`, and the HMAC validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. The status handler resolves the target repository/commit using `repository.full_name = "OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), applying a forged "success" CI status to a commit under an organization the attacker never authenticated as.

Note: I could not fully inspect `app/models/shipit/webhooks/handlers/status_handler.rb`'s complete body within the available tool budget (only confirmed its existence and the shared `repository_name`/`stacks` resolution in the base `Handler` class it presumably relies on) — its exact downstream effect on deploy gating should be independently confirmed by the assignee before treating the deploy-trigger chain as fully proven, though the core organization/repository binding break at the controller/handler level is confirmed with exact line citations above.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
