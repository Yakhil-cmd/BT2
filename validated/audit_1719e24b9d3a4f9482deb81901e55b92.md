### Title
Cross-repository Status write via unscoped `sha` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) solely by `Commit.where(sha: params.sha)`, with no filter on the stack's repository, while `WebhooksController#verify_signature` only proves that *some* trusted GitHub App produced the payload — in the common single-app configuration it does not bind the signature to the specific `repository.owner.login`/`repository.full_name` claimed in the JSON body. Together this lets a webhook that is genuinely signed for one repository write a `Status` row onto a `Commit` belonging to an entirely different stack/repository whenever the `sha` values collide (e.g., via a fork sharing history with the victim repo, or a commit that is legitimately present in two different Shipit-tracked stacks).

### Finding Description
The binding claimed by the question is:
`Status.state written == state reported by the CI that owns the repository of the Commit row it's attached to`, i.e. `status.commit.stack.github_repo_name == payload.repository.full_name` for every `Status` created.

Tracing the code:
- `WebhooksController#verify_signature` computes `repository_owner` from the attacker-supplied JSON body itself (`params.dig('repository','owner','login')`), and looks up the GitHub App config with `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
- In `Shipit.github`, when `github_default_organization` is `nil` — i.e. the standard single-GitHub-App configuration documented in `docs/setup.md` and used by `test/dummy/config/secrets.yml` — the `organization:` argument passed in is **ignored** and the single global `secrets.github` config (and its single `webhook_secret`) is used regardless of what `repository_owner` claims to be. [3](#0-2) 
- `GitHubApp#verify_webhook_signature` only checks the HMAC against the raw body using that single secret; it never checks that the `sha`/`repository` fields inside the signed payload actually correspond to the stack that is about to be mutated. [4](#0-3) 
- `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no `stack_id`, no repository check at all. [5](#0-4) 
- `Commit#create_status_from_github!` unconditionally appends the status to that commit's `statuses` association and recomputes `status` (used by `blocking?`/`blocked?`). [6](#0-5) [7](#0-6) 

Attack flow: an attacker who legitimately controls one Shipit-integrated repository (so any Github App/CI webhook they trigger is genuinely and correctly signed with the instance's shared `webhook_secret`) sends/crafts a `status` webhook whose `sha` matches a commit that also exists in a *different*, victim stack (e.g. because the victim's stack tracks a public repo the attacker forked, preserving identical commit SHAs, or because the same commit was merged into two Shipit-tracked repositories). Because `StatusHandler` selects by `sha` alone across the whole `commits` table, the write lands on the victim's `Commit` row even though the attacker's repository — not the victim's — is what produced the signed event. `verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema (`sha`, `state`, etc.) never check that `params.dig('repository','full_name')` equals `commit.stack.github_repo_name`, so none of the existing guards catch this divergence.

### Impact Explanation
This is a genuine cross-repository write: a payload legitimately signed for repository A ends up mutating a `Status` row (and therefore `Commit#state`/`blocking?`/`blocked?`) belonging to stack/repository B, which never authenticated that event. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any victim stack whose tracked commit history shares a SHA with a repository the attacker controls, and — because the whole Shipit instance frequently shares one GitHub App/secret (the documented default, single-org setup) — is not confined to a single tenant.

### Likelihood Explanation
Preconditions: Shipit configured with a single GitHub App/secret (the documented default), the attacker owns or administers at least one repository integrated with that Shipit instance (so their commit-status webhooks are genuinely signed), and a colliding SHA exists between attacker-controlled history and the victim's tracked commit (trivially achievable by forking a public victim repository, since forks preserve identical commit hashes for shared history). Attacker cost is a single crafted/triggered status webhook, fully repeatable and scriptable.

### Recommendation
In `StatusHandler#process` (and analogous handlers, e.g. `CheckRunHandler`), scope the `Commit` lookup by the reporting repository, not just `sha`: join through `stack` and require `stack.github_repo_name` (or repo id) to equal `params.dig('repository','full_name')`/`repository.id` from the payload before applying the status. Additionally, in single-app configuration mode, `verify_signature` should not silently ignore mismatches between the claimed `repository.owner.login` and the org actually authorized for that repository/stack — validate that the resolved stack's owner matches the payload's claimed owner.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new/extended)
test "process does not write a status to a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = Shipit::Stack.create!(repo_owner: 'attacker', repo_name: 'attacker-repo', environment: 'production')

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')
  attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/attacker-repo', 'owner' => { 'login' => 'attacker' } }
  }

  # Binding under test: status.commit.stack.github_repo_name must equal payload's repository.full_name
  assert_equal victim_stack.github_repo_name, victim_commit.stack.github_repo_name

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  victim_commit.reload
  # Vulnerability: victim commit gets the attacker-repo's status despite provenance mismatch
  assert_not_equal 'attacker/attacker-repo', victim_commit.stack.github_repo_name
  assert victim_commit.statuses.exists?(state: 'failure', context: 'ci/attacker'),
    "Status for a different repository's payload was written to victim commit"
end
```
This demonstrates the provenance mismatch (`victim_commit.stack.github_repo_name != payload['repository']['full_name']`) directly on the `Status` row, without invoking any live GitHub call, per the required binding equality.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
