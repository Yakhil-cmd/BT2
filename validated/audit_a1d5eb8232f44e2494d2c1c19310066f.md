### Title
Webhook signature is verified against the org named in `repository.owner.login`, but event handlers act on the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (`secrets.github` keyed by multiple orgs), `WebhooksController#verify_signature` selects which GitHub App config/secret to verify the HMAC signature against using the attacker-controlled `repository.owner.login` (or `organization.login`) field of the *unauthenticated* JSON body, while the downstream event handlers resolve the target `Stack`/`Repository` using a *different*, equally attacker-controlled field: `repository.full_name`. Because these two fields are never checked for consistency, a party who legitimately controls one configured organization in the same Shipit instance can forge a webhook payload that passes signature verification (using their own org's secret) but names a victim organization's repository in `full_name`, causing Shipit to act as if GitHub sent an event for that victim repository.

### Finding Description
`verify_signature` computes the organization used to pick the webhook secret before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a *distinct secret per organization key* in `secrets.github`: [3](#0-2) 

So the secret used for HMAC verification is chosen by `repository.owner.login`. Once the signature check passes, the raw JSON `params` are dispatched to handlers, e.g. `PushHandler`, which locate the target repository/stack using an entirely separate field, `repository.full_name`: [4](#0-3) [5](#0-4) 

The same pattern repeats in every pull-request handler (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`, `edited_handler.rb`), all of which resolve `Repository.from_github_repo_name(params.repository.full_name)` independent of whichever org's secret validated the signature.

This is the same root cause as the referenced Sherlock finding: a value used to establish trust (`sherlockCore` address / here, the org whose secret is used to authenticate the message) is not the same value that is subsequently acted upon (`pullReward`'s implicit trust in `msg.sender` / here, `repository.full_name` used to select the stack). The binding that should hold — "the organization whose secret validated this signature" == "the organization whose repository is being modified" — is never enforced.

### Impact Explanation
In a Shipit instance configured with multiple GitHub organizations (as documented and supported in `secrets.github`, e.g. `config/secrets.development.example.yml`), any org that has a legitimate GitHub App/webhook secret registered in the same instance can forge events for repositories belonging to a completely different configured org. This can:
- Trigger fake `push` events that enqueue `GithubSyncJob` for a victim's stack with an attacker-chosen `after` SHA, feeding attacker-influenced commit metadata into the victim's deploy history via `stack.commits.create_from_github!`.
- Trigger `pull_request` `opened`/`labeled`/`closed` events causing `ReviewStackAdapter` to provision/archive review-stack deployments for a victim repository, or `PullRequest` records to be manipulated cross-tenant.

This breaks the equality "authenticating organization == acted-upon repository owner", enabling cross-repository/cross-tenant writes to stack/deployment state without possessing the victim's webhook secret — matching the High-impact criteria for escalation across authorization boundaries.

### Likelihood Explanation
Exploitability requires the attacker to be an onboarded organization/customer within the same multi-tenant Shipit deployment (i.e., they know their own org's `webhook_secret`), which is a real deployment pattern explicitly supported by `Shipit.github_organizations`/`github_app_config`. No GitHub App private key, `api_clients_secret`, or session is required — only the ability to send an HTTP POST to `/webhooks` with a self-signed HMAC using their own configured secret and a spoofed `repository.full_name`/`owner.login` mismatch. Likelihood is moderate: it depends on the operator running a multi-org configuration, but where present, exploitation is straightforward and requires no privileged access.

### Recommendation
After computing `repository_owner` for secret selection, re-verify that it matches the owner embedded in the same `repository.full_name`/`organization.login` field that handlers will subsequently use, and reject the webhook if they diverge. More robust: derive the org used purely from `repository.full_name`'s owner segment (single source of truth) rather than a separate `repository.owner.login`/`organization.login` field, so the same value both selects the secret and is used to resolve the target repository/stack.

### Proof of Concept
1. Deploy Shipit with `secrets.github` configured for two orgs, `attacker-org` (with known `webhook_secret_a`) and `victim-org` (with `webhook_secret_v`, unknown to the attacker), each with stacks/repositories registered.
2. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `webhook_secret_a` (known to attacker) over the raw body.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s config, and successfully verifies the signature against `webhook_secret_a`. `PushHandler#process` then looks up the stack via `repository.full_name` = `"victim-org/victim-repo"` and enqueues `GithubSyncJob` for the victim's stack, despite the request never having been signed with `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
