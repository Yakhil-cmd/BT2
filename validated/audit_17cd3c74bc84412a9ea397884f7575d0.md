### Title
`StackStxOp::check()` fails to reject `num_cycles` outside `(0, POX_MAX_NUM_CYCLES]`, allowing out-of-range lock periods to reach PoX lockup math - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`StackStxOp::check()` validates that `num_cycles` is in the range `(0, POX_MAX_NUM_CYCLES]`, but the branch that detects a violation only logs a `warn!` and falls through to `Ok(())` instead of returning an error. This lets a burnchain-op-crafting attacker submit a `StackStxOp` with an unbounded `num_cycles` (a full `u8`, up to 255) that passes validation and is accepted into the PoX lockup path.

### Finding Description
The broken equality is: **validated num_cycles == num_cycles actually used to compute unlock_burn_height**, which the code claims to enforce via the range check but does not. [1](#0-0) 

Concretely:
```rust
pub fn check(&self) -> Result<(), op_error> {
    if self.stacked_ustx == 0 {
        warn!("Invalid StackStxOp, must have positive ustx");
        return Err(op_error::StackStxMustBePositive);
    }

    if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
        warn!(
            "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
            self.num_cycles, POX_MAX_NUM_CYCLES
        );
        // <-- no `return Err(...)` here
    }
    ...
    Ok(())
}
```
Unlike the `stacked_ustx == 0` branch immediately above it (which correctly returns `Err(op_error::StackStxMustBePositive)`), the `num_cycles` branch has no `return` statement — it warns and falls through, ultimately returning `Ok(())` from the function regardless of `num_cycles`'s value.

The wire-format parser (`StackStxOp::parse_data`) reads `num_cycles` as a raw `u8` from the burnchain OP_RETURN payload with no bounds enforcement of its own [2](#0-1) , so `check()` is the only gate meant to bound this value before it reaches downstream reward-cycle/unlock-height computation in `pox-locking` (`pox_5.rs`) and `pox-5.clar`.

An attacker fully controls the wire payload of their own `StackStxOp` (this is literally "craft burnchain stacking ops from their own Bitcoin inputs" — an explicitly permitted unprivileged capability), so they can set `num_cycles` to any value up to 255, far exceeding `POX_MAX_NUM_CYCLES`.

### Impact Explanation
If `num_cycles` reaches the unlock-height computation unclamped, the resulting `unlock_burn_height` could be computed far beyond what `POX_MAX_NUM_CYCLES` cycles would produce, freezing the attacker's own staked STX for an excessively long, possibly effectively permanent, duration relative to intended protocol limits. This only affects the sender's own funds (the STX being locked belongs to the address derived from the op's first Bitcoin input), so it is a self-harm/permanent-freezing-of-own-funds scenario, not third-party theft.

### Likelihood Explanation
I was not able to fully trace, within the available search budget, whether `pox-locking/src/pox_5.rs` (the Rust code that turns a validated `StackStxOp` into a Clarity-level lockup) independently re-validates and clamps `num_cycles` before computing `unlock_burn_height`, nor whether `pox-5.clar`'s `stack-stx` entry point (used for contract-call-based stacking, not burnchain ops) enforces this separately from the burnchain-op path. I could not complete this trace before running out of tool iterations. This matters because in the Stacks architecture, burnchain-sourced stacking ops (`StackStxOp`) are processed through a distinct Rust code path (`pox_5.rs`'s handler) rather than through the full `pox-5.clar` public `stack-stx` function with its own Clarity-level asserts — so if that Rust-side handler has no separate bound on `num_cycles`, the `check()` bug is directly exploitable end-to-end.

### Recommendation
Add `return Err(op_error::StackStxInvalidCycles);` (or the appropriate existing error variant) inside the `if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES` block in `StackStxOp::check()`, matching the pattern already used for the `stacked_ustx == 0` check immediately above it.

### Proof of Concept
```rust
// stackslib/src/chainstate/burn/operations/stack_stx.rs (test module)
#[test]
fn test_check_rejects_num_cycles_out_of_range() {
    let sender = StacksAddress::new(0, Hash160([0; 20])).unwrap();
    let reward_addr = PoxAddress::Standard(
        StacksAddress::new(C32_ADDRESS_VERSION_MAINNET_SINGLESIG, Hash160([0x01; 20])).unwrap(),
        None,
    );
    let op = StackStxOp::new(
        &sender,
        &reward_addr,
        1_000_000,
        POX_MAX_NUM_CYCLES + 1, // out of range
        None,
        None,
        None,
    );
    let result = op.check();
    assert!(result.is_err(), "expected Err for num_cycles > POX_MAX_NUM_CYCLES, got {:?}", result);
}
```
Today this assertion fails because `check()` returns `Ok(())`. Given the incomplete trace into `pox-locking/src/pox_5.rs`, a full end-to-end PoC (verifying `unlock_burn_height` computed from this unbounded `num_cycles`) should additionally be run against the burnchain-op-to-PoX-lock pipeline (`pox_5.rs`'s `pox_lock_v5`/lockup handler) to confirm no independent clamp exists there before treating this as fully exploitable.
