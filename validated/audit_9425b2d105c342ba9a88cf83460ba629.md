## Title
Cross-Organization Commit-Status Forgery via Webhook Signature/Payload-Field Mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against using one payload field (`repository.owner.login` / `organization.login`), while the handlers that act on the payload (in particular `StatusHandler`) use a completely different, unscoped field (`sha`) to decide what to mutate. In a multi-organization Shipit deployment (explicitly supported via `config/secrets.*.yml` with one `webhook_secret` per GitHub org), this breaks the binding "organization whose secret authenticated the request == repository/record the request is allowed to write to."

### Finding Description
`WebhooksController#verify_signature` resolves which `Shipit.github_app`/`webhook_secret` to use for HMAC verification purely from attacker-controlled payload data: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config (`app_id`, `webhook_secret`, etc.), as shown by the multi-org secrets schema: [3](#0-2) 

Once the signature check passes, the raw JSON body is dispatched to handlers keyed only by `X-Github-Event`, with no re-check that the record being mutated actually belongs to the organization whose secret validated the request: [4](#0-3) 

Crucially, `StatusHandler#process` looks up commits **globally by `sha`**, with no scoping to the repository/organization that produced the signature: [5](#0-4) 

Contrast this with `Handler#stacks`, which scopes lookups by `repository.full_name` (still a different, independently-attacker-supplied field from the one used for signature routing, but at least scoped) : [6](#0-5) 

So the equality that should hold — `organization used to select/verify webhook_secret == organization that owns the resource being written` — is never enforced. The signature only proves "this payload was HMAC-signed with secret(payload.repository.owner.login)"; it proves nothing about whether `sha` (for `status` events) or `repository.full_name` (for `push`/`check_suite` events) actually belongs to that same organization.

### Impact Explanation
In a Shipit instance configured for multiple GitHub organizations (the documented multi-tenant setup), an attacker who administers **any one** of the configured organizations (and can therefore register a real webhook / know that organization's `webhook_secret`) can:
1. Send a `status` event whose `repository.owner.login` is set to their own org (so `verify_webhook_signature` succeeds against their own known secret), while `sha` is set to the SHA of a commit belonging to a **different tenant's** repository.
2. `StatusHandler` will locate `Commit.where(sha: params.sha)` across the entire Shipit instance and call `commit.create_status_from_github!(params)`, injecting an arbitrary CI status (e.g., `state: 'success'`) for that foreign commit.

Since deploy gating (`required_statuses`/`hidden_statuses` in `DeploySpec`) and merge-queue/continuous-delivery logic in `Stack`/`MergeRequest` rely on stored `Status` records to decide whether a commit is safe to deploy or merge, forging a passing status on another tenant's commit can push it past CI gating, potentially triggering an unauthorized deploy or merge of a commit whose CI never actually passed. This matches the "unauthorized deploy, rollback, or merge" impact bar. It does not grant RCE or credential exfiltration directly, but is a genuine authorization-boundary break enabled purely by the mismatch between the field used for authentication and the field used for the write.

### Likelihood Explanation
The attack requires the target Shipit instance to be configured with more than one GitHub organization (a supported, documented configuration, not a misconfiguration) and requires the attacker to control at least one of those organizations (able to register a webhook there, e.g., because it's their own personal org/repo pointed at the shared Shipit instance, or because they compromised one tenant's webhook secret only). No `ApiClient` token, GitHub App private key, or Shipit session is needed — only knowledge of one legitimate (lower-privilege) org's webhook secret, which they can obtain trivially if it's their own org. This is a realistic path for shared/multi-tenant Shipit deployments, which the codebase explicitly supports and documents.

### Recommendation
After verifying the HMAC signature, re-validate that every payload field actually used to identify the target resource (`sha` for status events, `repository.full_name`/`owner.login` for push/check_suite events) is consistent with the organization whose secret validated the signature — e.g., scope `Commit` lookups in `StatusHandler` through `Stack`/`Repository` records belonging to the verified organization, rather than a global `Commit.where(sha:)`, and reject events where `repository.owner.login` used for verification doesn't match the `repository.full_name`'s owner used for the actual write.

### Proof of Concept
1. Configure (or find) a multi-org Shipit instance with orgs `attacker-org` and `victim-org`, each with its own `webhook_secret`.
2. As an admin of `attacker-org`, compute a valid `X-Hub-Signature` over a JSON body of:
```json
{
  "sha": "<victim-org/victim-repo commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"}
}
```
using `attacker-org`'s known `webhook_secret`.
3. POST to `/github/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and succeeds.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the victim commit regardless of organization — and creates a `success` status on it via `commit.create_status_from_github!`, satisfying `victim-org`'s required CI checks for deploy/merge gating. [7](#0-6) [8](#0-7)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
