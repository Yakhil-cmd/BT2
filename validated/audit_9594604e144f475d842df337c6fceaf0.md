### Title
CCMenu API token is never scoped to the requesting stack, granting instance-wide `read:stack` access - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token intended to grant read-only CI status for a single stack, but the token is created without ever binding it to that stack, and the lookup logic silently reuses the very same token for every stack a user requests it for. The resulting token therefore authorizes `read:stack` on **all** stacks in the Shipit instance, not just the one whose CCMenu URL was generated, breaking the binding "stack a token authorises == stack it touches."

### Finding Description
`CCMenuUrlController#fetch` builds a per-stack "CCMenu URL" containing an `ApiClient` authentication token intended for embedding in external, unauthenticated CI status widgets (CCTray-style dashboards): [1](#0-0) 

The client is looked up/created via:
```ruby
ApiClient.create_with(permissions: %w[read:stack])
         .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
```
Note that `stack:` is never passed to `create_with`, so the `ApiClient#stack_id` column, which is defined precisely to scope a token to one stack, is left `nil`: [2](#0-1) 

`find_or_create_by!` matches only on `creator` and `name`, ignoring which stack the request was for. This means the very first time a user fetches a CCMenu URL for any stack, a single global `ApiClient` (with `stack_id = nil`) is created and cached for that user; every subsequent call, regardless of `stack_id` param, returns the same unscoped token embedded in the new URL.

The permission check performed by the API layer only validates the generic permission string, never the specific stack: [3](#0-2) 

And the stack-scoping mechanism that is supposed to restrict a token to `current_api_client.stack_id` explicitly falls back to `Stack.all` when `stack_id` is blank: [4](#0-3) 

`CCMenuController` itself doesn't even use this scoped `stacks` helper — it resolves the target stack directly via `Stack.from_param!(params[:stack_id])`, independent of the authenticated client's intended scope: [5](#0-4) 

Because the token's `stack_id` is nil, it is also unscoped when used against the general API surface (e.g. `api/stacks`, `api/tasks`, `api/commits`) which uses the shared `stacks`/`stack` helpers in `BaseController`, since those helpers treat "no stack_id" as "all stacks."

Binding broken: `stack a token authorises` (the single stack whose CCMenu URL a team member requested) `== stack it touches` (before the bug) vs., after minting, the token touches **every** stack in the instance.

### Impact Explanation
CCMenu URLs are designed to be embedded in external, non-authenticated systems (build-status widgets, wikis, dashboards) specifically because they are meant to reveal only one stack's non-sensitive CI status. Because the token backing that URL is actually a global `read:stack` credential, leakage of a single CCMenu URL (an expected, low-sensitivity artifact) grants the holder unauthenticated read access to every stack's state via the JSON API — stack details, deploy/task metadata, and potentially task output/commit info depending on what `read:stack`-gated endpoints expose. This matches the High-impact bullet: "unauthenticated read of stack state, task streams, or deploy output," achieved by an attacker who never needed a full Shipit session or elevated privileges — just one previously-shared CCMenu link.

### Likelihood Explanation
Any team member with basic Shipit access can trigger this by simply visiting the CCMenu-URL feature for any stack (`CCMenuUrlController#fetch`), which is a completely ordinary, expected user action documented as a feature (embedding build status badges). No special privilege or attack technique is needed to produce the over-scoped token; the design flaw guarantees every generated token is global.

### Recommendation
- Persist `stack:` on the created `ApiClient` in `CCMenuUrlController#client`, e.g. `ApiClient.create_with(stack:, permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`, ensuring the `find_or_create_by!` lookup also keys on `stack` so each stack gets its own distinct, scoped token.
- Make `Api::CCMenuController#stack` use the inherited scoped `stacks.from_param!` (as `BaseController` does) instead of calling `Stack.from_param!` directly, so an already-issued token cannot be replayed against an unintended stack.
- Consider hardening `BaseController#stacks`/`ApiClient#check_permissions!` to require an explicit `stack_id` for any `ApiClient` used outside the admin/unlimited context, rather than defaulting to `Stack.all` when `stack_id` is blank.

### Proof of Concept
1. As an authorized Shipit user, visit stack A's page and trigger the CCMenu URL feature: `GET /*stack_a_id/ccmenu_url` (or the equivalent UI action calling `CCMenuUrlController#fetch`). Note the returned `token` query parameter.
2. Reuse that same `token` against a different, unrelated stack B that this URL was never generated for: `GET /api/*stack_b_id/ccmenu.xml?token=<token>`.
3. Observe the response returns stack B's CI/build status successfully (HTTP 200), because the token's `stack_id` is `nil` and both `Api::CCMenuController#stack` (direct `Stack.from_param!`) and the default `BaseController#stacks` scoping (`Stack.all` when `stack_id` is blank) allow it — demonstrating the token authorizes far more than the single stack it was generated for.
