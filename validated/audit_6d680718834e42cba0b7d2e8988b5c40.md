### Title
Webhook signature scoped by attacker-controlled `repository.owner.login` while stack actions are dispatched by a different `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Analogous to the `token_vesting.move` bug — where the address checked (`receiver`) and the address actually credited (`tx.sender`) are two different fields taken from the same request — Shipit's `WebhooksController` verifies the HMAC signature using the GitHub App/secret selected by `repository.owner.login` (or the fallback `organization.login`), but the handlers that actually mutate state (create/sync stacks, archive/unarchive review stacks, refresh check runs, etc.) key off a *different* field of the very same payload: `repository.full_name`.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/secret to validate the request against using: [1](#0-0) [2](#0-1) 

using `repository_owner = params.dig('repository', 'owner', 'login')`. Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw JSON straight to handlers such as `PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers, all of which resolve the target `Stack`/`Repository` through `Handler#repository_name` / `#stacks`: [3](#0-2) 

which reads `payload.dig('repository', 'full_name')` — a field within the same `repository` hash but semantically independent of `owner.login`.

In a Shipit deployment configured for multiple GitHub organizations (`Shipit.github(organization:)` per-org secrets, as documented in `docs/setup.md`), a customer who legitimately owns/administers one onboarded GitHub organization (and therefore genuinely knows that organization's `webhook_secret`) can craft a raw webhook body where `repository.owner.login` is set to their own org (so the correct app/secret is selected and the HMAC validates) while `repository.full_name` is set to `"other-org/other-repo"` — a repository belonging to a different, unrelated organization also onboarded onto the same Shipit instance. Because the signature check only decides *which secret to use*, not *which repository the payload is allowed to reference*, the handler will act on the victim repository's `Stack` using a signature that was never issued by (and does not correspond to) that repository's owner.

### Impact Explanation
This breaks the binding: `organization that authenticated == repository that is written`. An attacker who controls one legitimate organization's webhook secret can forge `push`/`check_suite`/`pull_request` events for a stack belonging to a different organization, causing Shipit to run `stack.sync_github(expected_head_sha: ...)`, archive/unarchive review stacks, or refresh check runs for that unrelated stack — a cross-repository write/deploy trigger performed without any credential tied to the victim's repository. This matches the "cross-repository writes / unauthorized deploy" Critical impact category, since `sync_github` can pull new commits and (depending on continuous deployment settings) advance the deploy pipeline for a repository the attacker never had access to.

### Likelihood Explanation
Requires the attacker to legitimately operate one onboarded GitHub organization/app on the same multi-tenant Shipit instance (a realistic scenario for any Shipit deployment serving several orgs) and requires no privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repository — only knowledge of their own organization's webhook secret, which they possess by design. The webhook endpoint is unauthenticated apart from this HMAC check, so this is directly reachable by any unprivileged external actor who administers one onboarded org.

### Recommendation
After signature verification, re-derive the repository owner from the same `repository.full_name`/`repository.owner.login` pair and assert `repository_owner` used for secret selection matches the owner segment of `repository.full_name` before dispatching to handlers. Alternatively, verify that the resolved `Stack`/`Repository`'s configured GitHub organization matches the organization whose secret validated the signature, rejecting the webhook (422) on mismatch.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.yml`: `attacker-org` (secret known to the attacker, who administers that org's installed GitHub App) and `victim-org` (unrelated, tracked stack `victim-org/victim-repo`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s webhook secret and sets `X-Hub-Signature` accordingly.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and the HMAC validates successfully.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers `stack.sync_github(expected_head_sha: ...)` for the victim's stack, despite the request never having been signed by anything associated with `victim-org`.
