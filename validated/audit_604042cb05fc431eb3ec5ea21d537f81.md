### Title
Cross-tenant CI-state forgery via unscoped `sha`-only lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` writes GitHub commit statuses to every `Commit` record in the database matching a given `sha`, without checking that the `sha` belongs to the repository named in the webhook payload. An attacker who owns any repository legitimately onboarded to the same Shipit installation can produce a commit whose SHA-1 collides (by exact copy) with a public commit belonging to a victim's stack, then trigger a real, validly-signed `status` webhook for their own repository referencing that SHA, causing the victim's `Commit` to receive an attacker-controlled `Status` row.

### Finding Description
The broken binding is: **the webhook's `repository.full_name` MUST equal `commit.stack.repository.full_name` for the `commit` being updated**, but `StatusHandler#process` never checks this — it is: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` [3](#0-2) .

Path: `WebhooksController#create` parses the JSON payload and dispatches to handlers for the `status` event [4](#0-3) . `verify_signature` only validates the HMAC using the shared `webhook_secret` configured for the GitHub App/organization derived from `repository_owner` in the payload [5](#0-4)  and `GitHubApp#verify_webhook_signature` [6](#0-5) . This signature check proves the request came from GitHub for *some* repository owned by that organization/app installation — it does **not** bind the payload's `sha` to the payload's `repository`, nor to any specific stack.

The `Handler` base class exposes a `stacks` helper explicitly designed to scope lookups to `Repository.from_github_repo_name(repository_name)` [1](#0-0) , and `CheckSuiteHandler` correctly uses it: `stacks.where(branch: params.check_suite.head_branch)` [2](#0-1) . `StatusHandler` is the outlier — it ignores `stacks`/`repository_name` entirely and matches purely on `sha` [7](#0-6) .

Exploit flow: attacker owns repository B, onboarded normally to the same Shipit instance/GitHub App (legitimate but unprivileged). Attacker crafts a commit in B with tree/parents/author/committer/timestamps identical to a target public commit in victim stack A, producing an identical SHA-1 (achievable for e.g. cherry-picked/rebased-without-changes commits, or reproducible commit metadata). Attacker pushes this commit to B and creates a `status` on it via the GitHub API for repo B (or GitHub sends the resulting webhook automatically) — this is a completely legitimate GitHub-signed `status` event scoped to repo B. When Shipit receives it, `verify_signature` passes (real signature, real repo B, real webhook_secret for the org), but `StatusHandler#process` matches `Commit.where(sha: ...)` against **all stacks**, including stack A, and writes a `Status` row to the victim's commit via `commit.create_status_from_github!(params)` [8](#0-7) .

`Status` creation is not benign metadata: it triggers `enable_ci_on_stack` and `schedule_continuous_delivery` after commit [9](#0-8) , meaning a forged `success` status can unblock the victim's continuous-delivery/merge pipeline for a commit the attacker does not own or control.

### Impact Explanation
An attacker with no relationship to the victim stack can write arbitrary CI status rows (`success`, `failure`, `error`, `pending`, with attacker-chosen `description`/`target_url`/`context`) onto any commit in the system merely by knowing its SHA and reproducing it in a repository they control. This can force `success` statuses that unblock continuous delivery/merges (`schedule_continuous_delivery`) or inject `failure` states to block a competitor's deploys — a payload for one repository mutating another's stack/commit state, matching the Critical category of cross-tenant impact.

### Likelihood Explanation
Preconditions: attacker needs (a) their own repository legitimately onboarded to the same Shipit instance/GitHub App/org (a normal, low-privilege, self-service onboarding step in most Shipit deployments), and (b) the ability to produce a commit with an identical SHA-1 to a target victim commit, which is trivial for direct copies/no-op rebases/cherry-picks of public commits (same tree, parent, author, committer, timestamps, message). No Shipit or GitHub secrets are required — GitHub itself signs the webhook. This is repeatable against any commit whose SHA the attacker can learn (all public GitHub commits) and any number of times.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the webhook's own repository using the existing `stacks` helper, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, so a status event only updates commits belonging to stacks whose `Repository` matches `repository_name` from the payload — mirroring the pattern already used in `CheckSuiteHandler`.

### Proof of Concept
Minitest plan (ActionController::TestCase style, consistent with existing `test/controllers/webhooks_controller_test.rb`):
```ruby
test ":status from repository B must not update a commit belonging to stack A" do
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature is legitimately valid for repo B
  stack_a = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first) # belongs to stack_a's repository
  # attacker's own onboarded stack/repository B, unrelated to stack_a
  repo_b_full_name = "attacker/repo-b"

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker-ci',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => repo_b_full_name, 'owner' => { 'login' => 'attacker' } }
  }.to_json

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body:, as: :json
  end
end
```
Binding to assert: `payload['repository']['full_name']` (`"attacker/repo-b"`) must NOT equal `victim_commit.stack.repository.full_name` (`stack_a.repository.full_name`), yet current `StatusHandler#process` writes a `Status` anyway because it never reads `payload['repository']` — the test's `assert_no_difference` will currently **fail** on the unpatched code, demonstrating the cross-tenant write.
