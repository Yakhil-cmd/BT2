### Title
Webhook signature verification is keyed on `repository.owner.login`, but handlers act on `repository.full_name`, allowing cross-organization stack manipulation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to authenticate the incoming GitHub webhook with, using `repository_owner`, a value taken straight from the untrusted JSON payload (`params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`). Once the signature check passes, the raw `params` are dispatched unchanged to event handlers (e.g. `PushHandler`), which resolve the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, via `Handler#repository_name`. These two fields are never cross-checked against each other.

### Finding Description
This is the direct analog of the report's root cause: a value is verified/predicted on one basis, but the actual state-changing action is executed against a different, uncontrolled value. Concretely:

- Authentication binding: `Shipit.github(organization: repository_owner)` in `verify_signature` [1](#0-0)  looks up the per-organization `webhook_secret` via `github_app_config(organization)` [2](#0-1) , confirming that a single Shipit instance can host multiple organizations, each with its own independent webhook secret.
- Execution binding: `Handler#repository_name` (used to resolve the `Repository`/`Stack` that actual mutating actions target) reads `payload.dig('repository', 'full_name')` [3](#0-2) , and `PushHandler#process` uses that resolution to call `stack.sync_github(expected_head_sha: params.after)` [4](#0-3) .

Nothing enforces that `repository.owner.login` (used to select the verifying secret) equals the owner portion of `repository.full_name` (used to select the acted-upon repository). An attacker who legitimately controls a GitHub App installation/webhook for Organization A on this Shipit instance can compute a valid HMAC signature over a payload where `repository.owner.login = "OrgA"` (so `verify_webhook_signature` succeeds against OrgA's secret) while `repository.full_name = "OrgB/victim-repo"` (a different, unrelated org/repo also configured on the same instance). This breaks the binding: *the organization that authenticated ≠ the repository that is written*.

### Impact Explanation
Because the payload is passed through untouched to handlers, an attacker authenticated only as Organization A can force `GithubSyncJob` to run against Organization B's `Stack`, triggering `stack.sync_github` [5](#0-4) , which fetches new commits and, on stacks with continuous deployment enabled, can lead to unauthorized deploy activity on a stack the attacker was never authorized to touch — satisfying the "unauthorized deploy" high-impact criterion. It also allows spoofed `status`, `check_suite`, `membership`, and `pull_request` events to be attributed to and acted on repositories/stacks outside the attacker's own organization, since every handler that inherits `Handler#repository_name` shares this same flaw.

### Likelihood Explanation
Exploitation requires that the target Shipit deployment be configured in the multi-organization mode (`secrets.github` keyed by org name, each with its own GitHub App/`webhook_secret`), and that the attacker legitimately controls at least one such configured organization (able to compute a valid signature for it). This is a realistic scenario for any shared/multi-tenant Shipit instance serving several organizations, which the codebase explicitly supports (`github_organizations`, `github_app_config`) [6](#0-5) .

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), cross-validate that the organization used to select/verify the webhook secret matches the owner segment of `repository.full_name` (and any other repository-identifying field used later, e.g. `organization.login` for membership events) before dispatching to handlers, rejecting the request with `422` on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with its own `webhook_secret` under `secrets.github` [7](#0-6) .
2. As the legitimate owner of `orga`'s GitHub App/webhook, craft a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<existing sha on orgb/victim-repo>",
     "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature` using `orga`'s `webhook_secret` (`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, payload)`), matching `verify_webhook_signature` [8](#0-7) .
4. POST to `/github/webhooks` (or configured route) with `X-Github-Event: push`. `verify_signature` resolves and validates against `orga`'s secret and succeeds [1](#0-0) .
5. `PushHandler` resolves `stacks` from `repository.full_name = "orgb/victim-repo"` [3](#0-2)  and enqueues `GithubSyncJob` against `orgb`'s stack, even though the request was only authenticated for `orga`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
