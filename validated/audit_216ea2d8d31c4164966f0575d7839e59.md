### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the acted-upon repository is resolved from a different, unverified field (`repository.full_name`) — cross-organization stack sync - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository.owner.login` (falling back to `organization.login`), but the handler that actually decides which `Stack`/`Repository` gets mutated resolves it from an entirely different field, `repository.full_name`. When the resolved organization has no `webhook_secret` configured, verification is skipped outright, letting an unauthenticated caller supply an arbitrary `full_name` that a handler like `PushHandler` uses to trigger `stack.sync_github` on any repository/stack known to the instance.

### Finding Description
`verify_signature` computes the organization used for signature checking purely from payload fields, never from the field that downstream handlers use to select the target repository: [1](#0-0) [2](#0-1) 

`Shipit::GithubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, every webhook `Handler` (base class) resolves the actually-affected repository/stacks from a *different* payload key, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used for signing: [4](#0-3) 

`PushHandler#process` uses those unauthenticated-by-signature stacks to trigger a GitHub sync directly: [5](#0-4) 

`Repository.from_github_repo_name` looks up any repository record by owner/name pulled straight out of `full_name`: [6](#0-5) 

This is the trust-binding break called out in the rules: "an organization that authenticated versus the repository that is written." The equality that should hold is:
`organization used to verify the HMAC == owner of the repository the handler mutates`
but the code enforces:
`organization used to verify the HMAC == payload["repository"]["owner"]["login"]` while
`repository/stack mutated == Repository.from_github_repo_name(payload["repository"]["full_name"])`
Nothing forces these two payload substrings to agree, and if the first organization happens to have no `webhook_secret` set (a common state for orgs that haven't configured one, or one an attacker can probe for via repeated attempts / knowledge of a low-value org), signature verification is bypassed entirely, and the `full_name` field — controlling which unrelated stack gets acted on — is free for the attacker to set.

### Impact Explanation
An unprivileged caller with no GitHub webhook secret, API token, or repository write access can invoke `stack.sync_github(expected_head_sha:)` on any stack managed by the Shipit instance, by crafting a `push` payload whose `repository.owner.login`/`organization.login` names an organization with no configured `webhook_secret` while `repository.full_name` names the victim organization/repository whose stack should actually be protected. This is a cross-repository, unauthenticated write into another tenant's stack state (forcing sync against an attacker-chosen SHA), which the report's mitigation rules classify as "cross-repository writes" — a Critical-tier outcome.

### Likelihood Explanation
Exploitability depends on at least one organization configured in this Shipit instance having a blank `webhook_secret` (line 77 of `github_app.rb` makes verification a no-op in that case) — this is plausible in multi-tenant deployments where not every onboarded GitHub organization has a secret configured, and the webhooks endpoint is unauthenticated by design (it's meant to be called by GitHub, protected only by the HMAC). No session, API token, or GitHub write access is required — only knowledge of one weakly-configured organization name recognized by the instance.

### Recommendation
Bind repository resolution to the same organization that was cryptographically verified: after `verify_signature` succeeds, ensure the organization derived for HMAC verification matches the owner segment of `repository.full_name` used by `Handler#repository_name`/`Repository.from_github_repo_name`, and reject the payload otherwise. Additionally, do not treat a missing `webhook_secret` as an implicit pass; require an explicit "unsigned webhooks allowed" configuration flag instead of defaulting to `true`.

### Proof of Concept
1. Configure (or identify) an organization `org-no-secret` in `Shipit.github_apps`/`Shipit.github` config with no `webhook_secret` set.
2. POST to `/github/webhooks` with `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-no-secret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-no-secret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb` line 77) regardless of the `X-Hub-Signature` header supplied.
4. `PushHandler` is invoked; `Handler#repository_name` reads `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, resolves the real victim `Stack`, and calls `stack.sync_github(expected_head_sha: "deadbeef")` — a state-changing action on a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
