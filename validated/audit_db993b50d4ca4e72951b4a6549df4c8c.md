### Title
Webhook signature is verified against an organization derived from `repository.owner.login`/`organization.login`, but handlers act on a repository looked up from the independent, unvalidated `repository.full_name` field — allowing a member of any Shipit-configured GitHub organization to forge deploy-gating events for a completely different organization's repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . Once the signature check passes, every registered handler (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) is executed against the raw, attacker-controlled JSON body [3](#0-2) . Handlers such as `PushHandler` resolve the target `Repository`/`Stack` from a *separate* field, `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name` [4](#0-3) [5](#0-4) . Nothing enforces that `repository.owner.login` (used to pick the trusted signing secret) matches the owner segment embedded in `repository.full_name` (used to pick the repository actually written to). `StatusHandler` is even more permissive: it doesn't scope by repository at all, updating `Commit.where(sha: params.sha)` globally across the entire Shipit instance [6](#0-5) .

### Finding Description
This is the same class of bug as the report: an untrusted, attacker-suppliable field is used to select trusted authorization context, while a different, unvalidated field determines the object actually mutated — breaking an implicit equality the code relies on (`authenticated_organization == organization_of_repository_written`).

- The binding assumed by the code: *the organization whose secret validated the signature* must equal *the organization owning the repository the handlers mutate*.
- What is actually checked: only the first (`repository_owner`, from `repository.owner.login`/`organization.login`) is cryptographically verified [7](#0-6) .
- What is actually used to select the mutated object: `repository.full_name`, read independently and never cross-checked against `repository.owner.login` [8](#0-7) .

Any entity that legitimately administers one GitHub App configured under `Shipit.github(organization: ...)` (i.e., knows that org's `webhook_secret`, as documented for multi-org setups) can sign a payload where `repository.owner.login` = their own org (so the signature check passes against their known secret) while `repository.full_name` = `"victim-org/victim-repo"` (so the handler operates on a completely different organization's `Repository`/`Stack`). No `ApiClient` token, GitHub App private key, or `Shipit` session is required — only the ability to POST to the public `/webhooks` endpoint with a validly-signed body for one's own org.

The most damaging concrete handler is `StatusHandler`, which performs no repository scoping whatsoever: it updates `Commit.where(sha: params.sha)` for the given SHA across the whole install [6](#0-5) . This directly feeds `Commit#create_status_from_github!` → `add_status`, which recomputes `Commit#status`/`deployable?` and triggers `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` [9](#0-8) [10](#0-9) . Since `deployable?` gates `schedule_continuous_delivery`, forging a "success" status for any commit whose SHA is guessable/known (SHAs are not secret) can make a victim stack believe CI passed and trigger continuous deployment/merge scheduling it should not have [11](#0-10) .

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" bar: an attacker who is a legitimate operator of one Shipit-configured GitHub organization can forge commit-status/webhook events that get attributed and applied to a victim organization's commits and stacks, altering deployability state (`Status`) and triggering continuous-delivery scheduling (`schedule_continuous_delivery`) for repositories they have no authorization over [12](#0-11) . `PushHandler`-driven `sync_github` calls can also be forced on arbitrary victim stacks by mismatching `repository.owner.login` vs `repository.full_name` in the same way [13](#0-12) .

### Likelihood Explanation
Requires only knowledge of one legitimately-configured org's `webhook_secret` (available to that org's own GitHub App owner in a multi-tenant Shipit deployment, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section) plus a target commit SHA, which is not secret information. No privileged Shipit account, `ApiClient` token, or GitHub App private key is needed. This is a moderate-effort, high-value cross-tenant abuse path in any deployment configuring more than one GitHub organization.

### Recommendation
Enforce that the field used for signature verification and the field used for repository resolution are the same, verified value: derive both `repository_owner` (for secret selection) and the repository/stack lookup from a single, consistently-parsed identifier (e.g., split `repository.full_name` and require `full_name.split('/').first == repository.owner.login`, rejecting mismatches with 422). Additionally, scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to stacks whose repository matches the verified webhook organization, rather than searching all commits in the installation.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `attacker-org` (attacker administers its GitHub App and knows its `webhook_secret`) and `victim-org` (unrelated).
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<known victim commit sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker signs this body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` and `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"` from `repository.owner.login`, fetches `Shipit.github(organization: 'attacker-org')`, and the signature verifies successfully [1](#0-0) .
5. `StatusHandler.call(params)` runs unmoored from any repository check, matching `Commit.where(sha: params.sha)` — the victim's commit — and calls `commit.create_status_from_github!(params)`, marking it successful and potentially triggering `stack.schedule_merges` / continuous delivery on `victim-org`'s stack [6](#0-5) [14](#0-13) .

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
