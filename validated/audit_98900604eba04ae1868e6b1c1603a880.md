### Title
Tokens transferred directly to the pool are permanently locked — no entrypoint recovers a balance above booked cash - (File: contracts/pool/src/lib.rs)

### Summary
The bug class: a contract holds a token balance that no rescue/withdrawal path can reach, so excess tokens are trapped. In the original report, `rescueERC20` refused the stream's own `token()`, so excess funding was only recoverable through `cancel()`. In XOXNO Lending, the pool's token balance is deliberately decoupled from its `cash` accounting book, and no pool or controller entrypoint can transfer out a balance that exceeds booked cash. Any tokens sent directly to the pool address (e.g., an accidental `transfer` instead of going through `supply`, or a third-party donation) become part of the physical balance without crediting `cash`, and there is no unprivileged — or even privileged — sweep/rescue path to release them.

### Finding Description
The pool is a custodial contract: it holds the actual token balances for every `(hub, token)` market, while `cash` is only an accounting number in `Cache` (`contracts/pool/src/cache/cash.rs:24-41`). `transfer_out` moves tokens out, but only downstream of a bookkeeping debit on owner-only entrypoints (`withdraw`, `borrow`, `claim_revenue`, `flash_loan`, `recapitalize` refund) — and every mutator is gated by `#[only_owner]`, where the owner is the controller (`contracts/pool/src/lib.rs:33`, `contracts/pool/src/lib.rs:94-96`, `contracts/pool/src/lib.rs:150-210`).

A direct `token.transfer(user → pool, X)` increases the pool's physical balance but never calls `credit_cash`, so `cash` stays unchanged. The docs confirm this is intentional: "direct donations do not automatically increase booked cash" (`docs/reference/architecture.md:57-59`). The consequence: since every outbound transfer is backed by a `debit_cash`/`require_reserves` check (`contracts/pool/src/cache/cash.rs:15-21`, `32-41`), the donated `X` can never leave the pool through normal operations — `withdraw`/`borrow` can only pay out up to `cash`.

The only entrypoint that even interacts with the surplus is `recapitalize`: it credits `min(amount, backing_shortfall)` to cash and refunds the rest to `payer` (`contracts/pool/src/ops/recapitalize.rs:26-67`). But it is `#[only_owner]` (controller-only) and requires the controller to transfer `amount` in first — it never returns pre-existing unbooked balance to the original sender; at best it socializes the donation into supplier backing, and when there is no bad-debt shortfall `backing_shortfall` is zero so nothing is applied. Unlike the Nouns `Stream` report (where `cancel()` at least returned excess to the payer), no controller entrypoint (`supply`, `repay`, `recapitalize`, `clean_bad_debt`, `claim_revenue`) sends unbooked pool balance back to the donor. There is no `sweep`/`rescue` on the pool or controller at all (contrast `sweep_balance` on the swap-aggregator, which does recover stray tokens but is out of scope and owner-only anyway).

### Impact Explanation
Permanent freezing of funds: any token amount a user sends directly to the pool contract address is irrecoverable by that user through any reachable entrypoint, forever, unless the token contract itself is upgraded. The tokens effectively become protocol-owned surplus that can only be absorbed into `cash` via `recapitalize` during a shortfall — benefiting suppliers, not the sender. On Soroban there is no fallback, no `selfdestruct`, and no generic rescue; the pool exposes only owner-gated mutators (`contracts/pool/src/lib.rs:33`).

### Likelihood Explanation
Moderate. The trigger requires only a direct token `transfer` to the pool address — an explicitly allowed unprivileged action per the threat model ("direct token transfers to the pool or controller"). Users accustomed to contracts that measure inbound deltas (the pool itself credits "the tokens actually received" in `supply`/`repay`, so front-running-style misdirected transfers feel plausible) can easily paste the pool address instead of invoking `controller::supply`. The docs even warn "do not transfer tokens to the router beforehand" for the aggregator, indicating this failure mode is realistic across the system.

### Recommendation
Add a recovery path for unbooked balance, e.g. an owner-gated `rescue(hub_asset, to, amount)` on the pool that can transfer at most `physical_balance − cash` (sum over all hubs sharing that token's physical balance), or a controller-level `recapitalize`-style call that credits an externally donated amount and optionally mints supply shares or refunds the donor. At minimum, emit/document the donation explicitly and consider making `recapitalize` able to sweep an existing surplus up to the shortfall without requiring a fresh transfer in.

### Proof of Concept
```text
1. User calls token::transfer(user -> pool_address, 1_000e7) on a listed asset.
2. Pool state: token balance += 1_000e7, but market `cash` is unchanged
   (credit_cash is only invoked inside owner-only ops).
3. User attempts recovery:
   - controller::withdraw — burns their supply shares; cannot exceed booked cash
     and requires their own position. Donation not reachable.
   - controller::recapitalize — controller transfers `amount` from the payer in;
     pool credits only min(amount, backing_shortfall) and refunds the rest to
     `payer`. It never touches the pre-existing unbooked 1_000e7, and with no
     bad-debt shortfall it applies 0.
   - pool::claim_revenue — pays only min(cash, revenue); donation excluded.
4. Result: token::balance(pool) > sum(booked cash across hubs) permanently;
   the 1_000e7 has no reachable exit. Only a future recapitalize during a
   shortfall can absorb it — as a gift to suppliers, not to the sender.
```
Relevant code: `contracts/pool/src/lib.rs:33` (all mutators owner-only), `contracts/pool/src/cache/cash.rs:46-53` (outbound transfer only via booked paths), `contracts/pool/src/ops/recapitalize.rs:44-67` (refund bounded by fresh `amount`, not surplus), `docs/reference/architecture.md:57-59` (donations not booked).
