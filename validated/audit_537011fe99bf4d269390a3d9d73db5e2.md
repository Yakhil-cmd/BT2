### Title
CCMenu token scoped to one stack can read build status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the inherited stack-scoping helper with an unscoped lookup, breaking the binding between the stack an `ApiClient` token is authorized for and the stack whose data is actually served.

### Finding Description
`Api::BaseController` enforces per-token stack scoping via: [1](#0-0) 
`stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped, and `stack` (used by `DeploysController`, `TasksController`, `RollbacksController`, etc.) resolves `params[:stack_id]` only within that restricted set.

`Api::CCMenuController`, however, redefines `stack` to bypass this scope entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, never consulting `current_api_client.stack_id`. The permission check registered via `require_permission :read, :stack` only validates that the token's `permissions` array contains `"read:stack"`: [3](#0-2) 
It never compares the token's `stack_id` to the stack being requested.

This is the exact analog of the Frax bug class: the constant/binding that is supposed to enforce "token's authorized stack == stack acted on" is implemented differently in this one controller (bypassing the scope check present everywhere else), so the authorization intent (`current_api_client.stack_id == stack.id`) is silently violated for CCMenu requests, in the same way `dirtyLiquidationFee` silently diverged from the intended 90% due to reusing a similarly-named but differently-scaled constant.

This is compounded by `CCMenuUrlController`, which generates these tokens without ever persisting a `stack_id` on the `ApiClient` record at all: [4](#0-3) 
`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` never sets `stack`, so even the intended one-stack scoping is not established by the normal token-issuing flow — but even if a stack-scoped `ApiClient` existed (e.g., created through the admin UI with `stack_id` set and `read:stack` permission), `CCMenuController#stack`'s bypass would still let it read any other stack.

### Impact Explanation
A `read:stack`-scoped API token/URL, intended for one stack's CI badge/status, can be replayed with a different `stack_id` in the request to read another stack's build status, last build label/time, activity, and web URL for any stack in the installation. This matches the "High" impact category defined by the rules: "unauthenticated read of stack state, task streams or deploy output" achieved by an attacker with only a low-privilege, single-stack scoped credential.

### Likelihood Explanation
High. Any user who requests a CCMenu URL for one stack via `CCMenuUrlController#fetch` obtains a valid `ApiClient` token; because `Api::CCMenuController#stack` never checks the token's `stack_id`, simply changing the `stack_id` path/query parameter is a trivial, no-additional-privilege attack.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it to reuse `stacks.from_param!(params[:stack_id])` from `BaseController`) so the same stack-scoping guarantee applied to every other API controller also applies here. Additionally, have `CCMenuUrlController#client` persist `stack:` on the created `ApiClient` so tokens are genuinely bound to a single stack.

### Proof of Concept
1. User A (with access to `stack-alpha`) visits the CCMenu URL feature for `stack-alpha`, obtaining `GET /api/stack-alpha/ccmenu?token=<TOKEN>`.
2. Attacker (holding `<TOKEN>`, or any other `read:stack`-permission token) requests `GET /api/stack-beta/ccmenu?token=<TOKEN>` for an unrelated `stack-beta` they have no access to.
3. `authenticate_api_client` verifies `<TOKEN>` successfully (valid signature, valid permission `read:stack`), and `Api::CCMenuController#stack` resolves `stack-beta` directly via `Stack.from_param!`, ignoring that the token was never authorized for `stack-beta`.
4. The response renders `stack-beta`'s build name, last build status/label/time, and web URL — data the token holder is not authorized to view.
