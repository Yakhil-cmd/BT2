### Title
Permanent market freeze via i128 value overflow in accrual before the borrow-index cap engages — (File: common/src/rates/simulate.rs)

### Summary
The buffer-overflow class maps onto this codebase as fixed-point magnitude overflow: the accrual step values the whole scaled debt book as `borrowed_shares * borrow_index / RAY` in `i128` and panics with `MathOverflow` when the RAY-scaled debt value exceeds `i128::MAX`. Because every pool verb accrues first (`synced_market` → `global_sync` → `accrue_step`) and the borrow index is monotone non-decreasing, once a market's debt value crosses the `i128` ceiling the panic is permanent and unrecoverable — the market can never repay, withdraw, or liquidate again. The `MAX_BORROW_INDEX_RAY` cap exists to bound index growth but does not save this path, because the overflow is in the *value* product (`shares × index`), not the index itself, and triggers at index values far below the cap whenever the book is large enough.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60-61` computes utilization via `scaled_to_original(env, borrowed, borrow_index)`, which is `Ray::mul` → `mul_div_half_up` → panic on `MathOverflow` when the quotient does not fit `i128` (`common/src/rates/scaling.rs:14-16`, `common/src/math/fp_core.rs:108-118`). The same multiplication also runs inside `calculate_supplier_rewards` for `borrowed × new_borrow_index`. `global_sync` (`contracts/pool/src/interest.rs:20-33`) runs this on every mutating pool call, so a single overflowing multiplication bricks the market's entire entry surface: `supply`, `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, `recapitalize`, `update_indexes` — all accrue first and all revert.

The repository's own harness proves the cliff is reachable and permanent: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` supplies `1e9` units of an 18-decimal asset, borrows at 98% utilization on the XLM rate curve, advances time, and observes `try_update_indexes` fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — i.e., the value ceiling is hit *before* the index cap. The test then asserts both `withdraw` and `repay` revert with the same error, and explicitly comments "The market is frozen: exits and repayments accrue first and hit the same panic. The index cap never engages."

The attacker path is unprivileged: `controller::supply` of a large position on a high-decimals market followed by `controller::borrow` to ~98% utilization creates the state; thereafter ordinary time passage (anyone calling the permissionless `update_indexes`, or any victim's own transaction) advances the index into the overflow region. Nothing can reverse it: `borrow_index` has no downward writer (`contracts/pool/README.md` notes `update_borrow_index` is its sole writer and it is monotone), and `supply_index` write-downs via `apply_bad_debt_to_supply_index` cannot run because bad-debt ops accrue first too.

### Impact Explanation
Permanent freezing of all funds in the affected (hub, asset) book: every supplier's deposit and every borrower's collateral claim on that market becomes unreachable, since there is no path that skips accrual. Liquidations also fail, so surviving debt is uncollectable — a permanent freeze plus de-facto insolvency for that market, within the accepted impact classes.

### Likelihood Explanation
Requires a very large nominal supply (the harness uses 10^9 tokens at 18 decimals, i.e., a whale-scale or low-unit-price asset) at sustained ~98% utilization on a steep rate curve so the index grows ~170× before cap intervention. That is significant capital and time, but entirely unprivileged and requires no oracle manipulation or governance action; on a meme/low-priced high-decimals listing the nominal scale is realistic. Medium likelihood, High impact.

### Recommendation
Break the `accrue_step` dependency on the full-value product: clamp the borrow index *before* valuing the book so `update_borrow_index`'s `MAX_BORROW_INDEX_RAY` cap actually engages first, or value the book with the saturating `mul_div_floor_saturating` (already used for caps in `calculate_scaled_cap`) and cap utilization at 1 RAY when saturation occurs — an over-saturated utilization only selects the max rate, which is the correct behavior at that scale anyway. Alternatively, bound mintable scaled shares (`MAX_SHARES`-style guard at supply/borrow entrypoints) so `shares × MAX_BORROW_INDEX_RAY / RAY` can never exceed `i128::MAX`, making the value ceiling unreachable by construction.

### Proof of Concept
Reproduced by the existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

```rust
t.supply_raw(BOB, "BIG18", BILLION * 10i128.pow(18));   // 1e9 tokens, 18 decimals
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);      // 98% utilization
loop { t.advance_time(YEAR_SECS); try_update_indexes(&["BIG18"]) } // -> MATH_OVERFLOW
// borrow_index still < MAX_BORROW_INDEX_RAY, yet:
try_withdraw_raw(BOB, "BIG18", 1) -> MATH_OVERFLOW      // frozen
try_repay(ALICE, "BIG18", 1.0)  -> MATH_OVERFLOW        // frozen
```

Root cause: `scaled_to_original` (`common/src/rates/simulate.rs:60`) panics inside `accrue_step`, which `global_sync` (`contracts/pool/src/interest.rs:28`) invokes before every market operation; since the panic occurs while merely *reading* the debt value, no state transition (including the index cap or any repayment) can ever execute afterward.
