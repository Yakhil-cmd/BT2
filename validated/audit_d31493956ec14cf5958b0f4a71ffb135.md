## Analysis

The reported bug class — a mandatory external token call embedded in a shared operation, whose revert (due to a pause/freeze on that token) blocks the operation for everyone relying on it — has a direct analog in the `liquidate()` flow of the Zest market contracts.

### Title
Liquidation of an undercollateralized position can be permanently blocked if the collateral token freezes/pauses transfers to the receiver - (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`liquidate()` unconditionally forwards the seized collateral to the liquidator (or a specified `collateral-receiver`) via `market-vault.collateral-remove`, which calls `send-tokens`, which itself performs a hard `try!`-wrapped `contract-call? asset transfer ...` to the arbitrary collateral `<ft-trait>` contract. If that underlying/collateral asset (e.g. a bridged token such as `sbtc-token`, which is DAO-approved and used as production collateral, or any other future collateral asset with issuer-level pause/blacklist controls) reverts the transfer to the target account, the entire `liquidate()` transaction reverts atomically — including the debt write-down and bad-debt socialization logic that were supposed to execute in the same call.

### Finding Description
The call chain is:
- `liquidate()` (`v0-4-market.clar`) → `contract-call? .v0-market-vault collateral-remove borrower coll-final collateral-ft coll-aid actual-receiver` [1](#0-0) 
- `collateral-remove()` (`v0-market-vault.clar`) → `(try! (send-tokens ft amount recipient))` [2](#0-1) 
- `send-tokens()` performs `(try! (contract-call? asset transfer amount tx-sender account none))` against the externally supplied collateral token contract [3](#0-2) 

Because `try!` is used at every layer, any revert from the external collateral token's `transfer` (e.g. because the borrower's/receiver's address is frozen, or the token contract itself is globally paused by its own governance/bridge signers — a real capability of bridged assets like sBTC) causes the *entire* `liquidate()` call to abort. Crucially, this also reverts the debt reduction (`debt-remove-scaled`) and the bad-debt socialization path (`socialize-debt-asset`) that are computed and executed later in the same transaction [4](#0-3) , so none of that state advances either.

This is structurally identical to the reported RED-mint issue: a mandatory external call to a token that can independently pause/freeze, embedded inside a function relied upon by parties other than the token's own operator, blocking a critical shared operation for as long as the pause/freeze persists.

### Impact Explanation
While the token is frozen/paused for that specific liquidation flow, an unhealthy position (LTV above `ltv-liq-partial`) cannot be liquidated by anyone — not the liquidator (caller), and not any other liquidator, since the `send-tokens` call target is intrinsic to the collateral asset, not something the liquidator controls. This leaves the borrower's bad debt exposure to the shared lending pool unresolved and growing (interest continues to accrue via `accrue()`), which is a real harm to the *lenders/suppliers* of that debt asset (an unprivileged principal separate from both borrower and liquidator) — this is a "position made unevaluable by a third party" and a form of loss socialized onto all suppliers of the debt vault. This lands on **temporary freezing of funds** (lender liquidity effectively locked/at risk behind an unliquidatable bad position), with potential escalation to protocol insolvency if the freeze/pause persists while debt keeps accruing.

### Likelihood Explanation
Low, matching the original report's own assessment for the RED analog: this requires the specific collateral token in question to have (and actually trigger) a pause/freeze/blacklist mechanism on the receiving address, which is expected to be rare and outside Zest's control, but is a real, documented capability for bridged assets like sBTC.

### Recommendation
Do not let a failed collateral transfer block the debt write-down/bad-debt-socialization state changes in `liquidate()`. Split the liquidation into (1) an atomic accounting step that removes debt and marks/escrows the collateral for the receiver, and (2) a separate, retryable/pull-based claim step for the actual token transfer (or wrap the `send-tokens` call in `match`/`unwrap!` with graceful fallback instead of `try!`, deferring the transfer to a claimable balance if it fails), so that a paused/frozen collateral token cannot block debt reduction and bad-debt socialization for the shared pool.

### Proof of Concept
1. Borrower opens a position using a collateral asset whose token contract (external to Zest, e.g. a bridged asset like `sbtc-token`) supports pausing/freezing transfers to specific principals or globally.
2. Borrower's position becomes unhealthy (LTV ≥ `ltv-liq-partial`).
3. The collateral token issuer pauses/freezes transfers (for the liquidator's/receiver's address, or globally) for any reason unrelated to Zest.
4. Any liquidator calls `liquidate()`; `vault-system-repay` and debt calculations succeed, but `collateral-remove` → `send-tokens` → `contract-call? asset transfer ...` reverts [5](#0-4) .
5. The whole `liquidate()` transaction reverts, so `debt-remove-scaled` and `socialize-debt-asset` never execute [6](#0-5) .
6. The position remains unhealthy and unliquidatable for the duration of the pause, while interest continues to accrue against the debt-asset vault's lenders.

(define-private (receive-tokens (asset <ft-trait>) (amount uint) (account principal))
  (contract-call? asset transfer amount account current-contract none))

(define-private (send-tokens (asset <ft-trait>) (amount uint) (account principal))
  (let ((asset-contract (contract-of asset)))
    (if (is-eq asset-contract ZEST-STX-WRAPPER-CONTRACT)
      (as-contract? ((with-stx amount))
          (try! (contract-call? asset transfer amount tx-sender account none)))
      (as-contract? ((with-ft asset-contract "*" amount))
          (try! (contract-call? asset transfer amount tx-sender account none))))))

(define-public (collateral-remove (account principal) (amount uint) (ft <ft-trait>) (asset-id uint) (recipient principal))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-collateral user-id asset-id amount)))
        (updated-mask (if (is-eq remaining u0)
                        (mask-update mask asset-id true false) ;; collateral, remove
                        mask))
        (updated-entry (merge entry (refresh updated-mask))))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-remove states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (insert updated-entry)
    (try! (send-tokens ft amount recipient))
