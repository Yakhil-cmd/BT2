### Title
Webhook signature verification is scoped to `repository.owner.login` while review-stack repository resolution is scoped to `repository.full_name` — mismatched, attacker-controlled JSON fields with no equality check allow cross-org `Stack` creation - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App config (and therefore the secret used to validate the signature) using `params.dig('repository','owner','login')`, but `OpenedHandler#repository` resolves the actual `Shipit::Repository` used for provisioning purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`. These are two independent, fully attacker-controlled JSON fields, and nothing in the request path checks that they refer to the same organization. If any GitHub App/org configured in this Shipit instance lacks a `webhook_secret` (a documented "optional" setting), an attacker can set `repository.owner.login` to that secretless org while pointing `repository.full_name` at a victim repository belonging to a different, properly-secured org, causing `ReviewStackAdapter#find_or_create!` to create a brand-new deploy-capable `Stack` for the victim repository from a fabricated pull request.

### Finding Description
Binding claimed broken: `repository_owner (used to select the GitHubApp/secret for verify_signature) == owner(repository.full_name) (used by OpenedHandler#repository to resolve the Stack's target Repository)`. This binding does not hold anywhere in the code.

- `verify_signature` in [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository','owner','login')` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that org's config has no `webhook_secret`: `return true unless webhook_secret` [3](#0-2) . This is a documented, legitimate configuration option ("Webhook secret (optional)").
- `OpenedHandler#repository` resolves the repository independently via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) , and `from_github_repo_name` simply splits `full_name` on `/` and looks up by `owner`/`name` — with no relation whatsoever to `repository.owner.login` used for signature selection [5](#0-4) .
- If `provision?` returns true for the resolved repository, `ReviewStackAdapter#find_or_create!` creates a new `Stack`/`ReviewStack` and enqueues it for provisioning, populated entirely from attacker JSON (`pull_request.head.sha`, `pull_request.head.ref`, `sender.login`) [6](#0-5) .

Exploit flow: attacker crafts a JSON body with `X-Github-Event: pull_request`, `action: opened`, `repository.owner.login = "attacker-org"` (an org configured in the Shipit instance's `secrets.github` with no `webhook_secret`, e.g. matching the `OrgTwo` pattern shown in `test/dummy/config/secrets_double_github_app.yml`), and `repository.full_name = "victim-org/victim-repo"` (a real tracked repository with `review_stacks_enabled` and `provisioning_behavior_allow_all?` true). `verify_signature` looks up `attacker-org`'s `GitHubApp`, finds no secret, and accepts the request regardless of the (missing/arbitrary) `X-Hub-Signature` header. `OpenedHandler` then resolves `victim-org/victim-repo` from `full_name` and provisions a new `Stack` for it, with fake `head.sha`, fake `ref`, and a fake/attacker-chosen `sender.login` used to auto-create a `Shipit::User`.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` only validates shapes/types, not cross-field consistency; `Repository` validations only constrain `owner`/`name` character sets, not which org "authenticated" the payload; there is no code anywhere that compares the org used in `verify_signature` to the org embedded in `full_name`.

### Impact Explanation
A JSON payload that is "authenticated" only against one (potentially unrelated, secretless) GitHub organization's webhook config can create and enqueue-for-provisioning a `Shipit::Stack` for a different, victim repository/organization, entirely from unauthenticated data. This matches the Critical category "a payload for one repository mutating another's stack." The created `ReviewStack` subsequently proceeds through normal provisioning/deploy machinery (`Shipit::ReviewStackProvisioningQueue.add(stack)`), so this is not merely a database row but a trigger for real CI/deploy actions on the victim repository. This is repeatable against any tracked repository configured with `review_stacks_enabled` + `allow_all` (or satisfying the label-based provisioning conditions), as long as any org in the multi-org Shipit configuration lacks a `webhook_secret`.

### Likelihood Explanation
Requires: (a) a multi-org Shipit deployment where at least one configured GitHub App/org has no `webhook_secret` set (an explicitly supported, "optional" configuration per `docs/setup.md`), or a single-org deployment with no secret set at all (in which case `repository_owner` matching is irrelevant and any payload is accepted); (b) a victim repository already tracked by Shipit with `review_stacks_enabled` and `provisioning_behavior_allow_all?` (or matching label-based provisioning). No GitHub session, API token, or secret is needed — cost is a single crafted HTTP POST to `/webhooks`, fully within the stated unprivileged attacker capability. This is highly feasible and cheaply repeatable per target repository.

### Recommendation
In `WebhooksController#verify_signature` (or in the handler base class), after resolving `repository_owner` for signature verification, also verify that it matches the owner segment of `params.dig('repository','full_name')` before proceeding; reject (422) any payload where they diverge. Additionally, consider treating a missing `webhook_secret` for any configured org as a hard misconfiguration warning/error rather than a silent bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style):
```ruby
test "cross-org payload creates a Stack for a repository whose owner never authenticated the webhook" do
  victim_repo = shipit_repositories(:shipit) # owner: "shopify", tracked repo
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  # Simulate a second, secretless org config for "attacker-org"
  Shipit.stubs(:github).with(organization: "attacker-org")
        .returns(Shipit::GitHubApp.new("attacker-org", { webhook_secret: nil }))

  payload = JSON.parse(payload(:pull_request_opened))
  payload["repository"]["owner"]["login"] = "attacker-org"
  payload["repository"]["full_name"] = victim_repo.github_repo_name
  payload["pull_request"]["head"]["sha"] = "f" * 40
  payload["pull_request"]["user"]["login"] = "totally-fake-user"

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = "sha1=deadbeef" # arbitrary/invalid signature

  assert_difference -> { victim_repo.stacks.count }, 1 do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok

  # Binding check: repository_owner used for verification != owner encoded in full_name
  assert_not_equal "attacker-org", victim_repo.owner
end
```
Assert both sides of the binding explicitly: `repository_owner` (`"attacker-org"`) used by `verify_signature` must equal `victim_repo.owner` (`"shopify"`) used by `OpenedHandler#repository`; the test demonstrates they differ yet a `Stack` is still created for `victim_repo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
