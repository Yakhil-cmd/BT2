### Title
Bridge Operator Can Supply Arbitrary `_value` in `handleKLAYTransfer` / `handleERC20Transfer` With No On-Chain Verification Against the Original Request — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge contracts accept `_value` (and `_to`) as free caller-supplied parameters in `handleKLAYTransfer` and `handleERC20Transfer`. The contract never verifies these parameters against the original `RequestValueTransfer` event on the counterpart chain. With the default operator threshold of 1, a single operator can call either function with an inflated `_value` and an attacker-controlled `_to`, draining the bridge's entire KAIA or ERC20 balance in one transaction.

---

### Finding Description

When a user initiates a cross-chain transfer, the source bridge emits a `RequestValueTransfer` event recording the exact amount. The off-chain operator is expected to relay this event to the destination bridge by calling `handleKLAYTransfer`. However, the destination bridge contract performs no on-chain check that the relayed `_value` matches the original event.

`handleKLAYTransfer` in `BridgeTransferKLAY.sol`:

```solidity
function handleKLAYTransfer(
    bytes32 _requestTxHash,
    address _from,
    address payable _to,
    uint256 _value,          // ← free parameter, never verified
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    nonReentrant
{
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    _setHandledRequestTxHash(_requestTxHash);
    handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
    _updateHandleNonce(_requestedNonce);
    // ...
    (bool ok, ) = _to.call.value(_value)("");   // ← sends _value KAIA
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [1](#0-0) 

The contract enforces:
- `_requestedNonce >= lowerHandleNonce` (replay protection)
- `closedValueTransferVotes[_requestedNonce] == false` (vote not already closed)
- `operators[msg.sender]` (caller is an operator)
- Vote threshold reached, using `keccak256(msg.data)` as the vote key [2](#0-1) 

It does **not** enforce that `_value` equals the amount recorded in the original `RequestValueTransfer` event. The `_requestTxHash` is stored to prevent the same hash from being processed twice, but it is never used to look up and compare the original event's value. The mapping `handleNoncesToBlockNums` stores only the block number, not the amount. [3](#0-2) 

The identical pattern exists in `handleERC20Transfer` (mint-burn mode: `ERC20Mintable(_tokenAddress).mint(_to, _value)`): [4](#0-3) 

The default operator threshold is **1**, set in the `BridgeOperator` constructor: [5](#0-4) 

The off-chain Go relay (`BridgeInfo.handleRequestValueTransferEvent`) reads the event and passes `valueOrTokenId` directly from the event log into the handle call — there is no independent on-chain record to cross-check against: [6](#0-5) 

---

### Impact Explanation

A single operator (the default configuration) can call `handleKLAYTransfer` with:
- `_value` = entire bridge KAIA balance (e.g., from `chargeWithoutEvent` liquidity)
- `_to` = attacker-controlled address
- Any fresh `_requestTxHash` not previously stored
- Any unhandled `_requestedNonce`

This results in an **unauthorized transfer of all KAIA held in the bridge contract** to an arbitrary address. In ERC20 mint-burn mode, the operator can mint an unbounded token amount to any address, inflating supply without any corresponding locked collateral on the source chain.

The corrupted value is: `_to.balance` increases by `_value` (attacker-chosen), while the bridge's KAIA balance is drained — the correct invariant `bridge_payout == original_request_amount` is broken.

---

### Likelihood Explanation

The operator role is a semi-trusted off-chain actor (the "backend" analog). The default threshold is 1, meaning a single operator key is sufficient. The operator key is managed entirely off-chain with no on-chain attestation of its actions. Any compromise of the operator key — or a malicious operator — directly enables this drain. The `valueTransferRecovery` module in `node/sc/vt_recovery.go` provides no protection because it only checks whether a nonce was handled, not whether the correct amount was transferred. [7](#0-6) 

---

### Recommendation

Store the original requested amount on-chain when `RequestValueTransfer` is emitted (e.g., `mapping(uint64 => uint256) public requestedValues`) and require `_value == requestedValues[_requestedNonce]` inside `handleKLAYTransfer` and `handleERC20Transfer`. Alternatively, require operators to commit to a hash of `(nonce, value, to)` in a first phase and verify it in the execution phase, so no single operator can unilaterally alter the transfer parameters.

---

### Proof of Concept

1. Bridge is deployed with `modeMintBurn = false`. Owner calls `chargeWithoutEvent{value: 1000 ether}()` to fund liquidity.
2. User calls `requestKLAYTransfer(userDest, 1 ether, "")` with `msg.value = 1.4 ether` (fee = 0.4). Bridge emits `RequestValueTransfer(KLAY, user, userDest, addr(0), 1 ether, nonce=0, ...)`.
3. Operator (threshold=1) calls:
   ```solidity
   bridge.handleKLAYTransfer(
       bytes32(uint256(0xdeadbeef)),  // fresh unused hash
       user,
       attacker,                      // attacker address, not userDest
       1000 ether,                    // entire bridge balance, not 1 ether
       0,                             // nonce=0 (matches the request)
       blockNum,
       ""
   );
   ```
4. `_lowerHandleNonceCheck(0)` passes (0 >= 0). `_voteValueTransfer(0)` passes (threshold=1, vote key = keccak256(calldata), count reaches 1). `_setHandledRequestTxHash` stores the fake hash. `_to.call.value(1000 ether)("")` sends 1000 KAIA to attacker.
5. Result: attacker receives 1000 KAIA; `userDest` receives nothing; bridge is drained. The original request for 1 KAIA is now marked as handled (`closedValueTransferVotes[0] = true`), so the legitimate user can never recover their funds. [8](#0-7) [9](#0-8)

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
