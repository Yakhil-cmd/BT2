### Title
`handleERC721Transfer` Uses `transferFrom` Instead of `safeTransferFrom`, Permanently Locking Bridged ERC721 Tokens in Unprepared Contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

In `BridgeTransferERC721.handleERC721Transfer`, when operating in lock/unlock mode (`modeMintBurn = false`), the bridge delivers the ERC721 token to the user-specified `_to` address using `IERC721.transferFrom` instead of `safeTransferFrom`. If `_to` is a contract that does not implement `onERC721Received`, the token is silently transferred into that contract and permanently locked there. Because the source-chain request nonce has already been consumed and the `HandleValueTransfer` event emitted, the bridge considers the transfer complete with no recovery path.

---

### Finding Description

`handleERC721Transfer` in `BridgeTransferERC721.sol` (line 69) executes:

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```

The `_to` address is taken directly from the cross-chain request originally submitted by the user via `requestERC721Transfer` or `onERC721Received`. A user can freely set `_to` to any address, including a contract that does not implement `IERC721Receiver`. The `IERC721` interface used by the bridge (`contracts/libs/openzeppelin-contracts-v2/contracts/token/ERC721/IERC721.sol`) already declares `safeTransferFrom`, so the safe variant is available but unused.

The `transferFrom` call succeeds without reverting even when `_to` is an unprepared contract, because `transferFrom` performs no receiver check. The token ownership is updated in the ERC721 contract, the `HandleValueTransfer` event is emitted, and `_updateHandleNonce` advances the nonce — all before the transfer. There is no rollback mechanism.

---

### Impact Explanation

- **Asset loss**: The bridged ERC721 token is permanently locked inside the unprepared destination contract. It cannot be recovered because the ERC721 contract records the contract as the new owner, but the contract has no way to call `transferFrom` or `safeTransferFrom` to move it out.
- **Source-chain finality**: On the source chain, the token was either locked in the source bridge (lock mode) or burned (burn mode). Either way, the source-chain asset is gone.
- **No recovery**: The bridge nonce is already advanced (`_updateHandleNonce`) and the request tx hash is marked handled (`_setHandledRequestTxHash`). The bridge will not re-process the same request.

This constitutes an **unauthorized permanent loss of a bridged asset** — the user's ERC721 token is destroyed from their perspective with no recourse.

---

### Likelihood Explanation

- Any user can trigger this by specifying a contract address as `_to` in `requestERC721Transfer` or `onERC721Received`. No special privilege is required.
- Many common contract patterns (multisigs, DAOs, vaults, proxy contracts without ERC721 receiver hooks) do not implement `onERC721Received`.
- The bridge operators faithfully relay the user-supplied `_to` to `handleERC721Transfer` with no validation.
- This is a one-step user action with no preconditions beyond having an ERC721 token approved to the bridge.

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in the lock/unlock branch of `handleERC721Transfer`:

```diff
- IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
+ IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

`safeTransferFrom` is already declared in the `IERC721` interface used by the bridge ( [1](#0-0) ) and will revert if `_to` is a contract that does not implement `onERC721Received`, preventing the token from being locked. This causes the entire `handleERC721Transfer` transaction to revert, preserving the token in the bridge until the user corrects the destination address.

---

### Proof of Concept

1. Alice owns ERC721 token ID `42` on the parent chain.
2. Alice calls `requestERC721Transfer(nftAddr, victimContractAddr, 42, "0x")` on the parent bridge, where `victimContractAddr` is a deployed contract without `onERC721Received`. [2](#0-1) 
3. The bridge operators observe the `RequestValueTransferEncoded` event and call `handleERC721Transfer(..., victimContractAddr, ...)` on the child bridge. [3](#0-2) 
4. Inside `handleERC721Transfer`, the nonce is updated and `HandleValueTransfer` is emitted **before** the token transfer. [4](#0-3) 
5. `IERC721(_tokenAddress).transferFrom(address(this), victimContractAddr, 42)` executes successfully — no receiver check is performed. [5](#0-4) 
6. Token ID `42` is now owned by `victimContractAddr`, which has no way to move it. The source-chain token is locked/burned. Alice's ERC721 is permanently lost.
