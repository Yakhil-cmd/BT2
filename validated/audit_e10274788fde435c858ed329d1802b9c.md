## Analog Finding

### Title
`Shipit::Api::CCMenuController` bypasses ApiClient stack-scoping, letting a token authorized for one stack read the deploy status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The external report's root cause is a value that is acted upon (`mintFee` consumed) without being validated against the value that was actually authorised (`msg.value`). The analogous binding in Shipit is: `ApiClient#stack_id` (the stack a token is authorised to touch) must equal the `stack` a controller action actually operates on. `Shipit::Api::CCMenuController` breaks this equality by re-implementing its own unscoped `stack` lookup instead of reusing the scoped one from `BaseController`.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping via: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set, and `stack` (used by every other API controller such as `StacksController`, `TasksController`, `DeploysController`) resolves `params[:stack_id]` only within that scoped relation. This is exactly the mechanism that lets an org issue a narrowly-scoped `ApiClient` (`belongs_to :stack, optional: true`) — for example the `here_come_the_walrus` fixture, scoped to a single stack with only `read:stack` — and be confident that token cannot see other stacks: [2](#0-1) [3](#0-2) 

This scoping guarantee is explicitly tested for `StacksController`: [4](#0-3) 

However, `CCMenuController` overrides `stack` and drops the scoping entirely: [5](#0-4) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model instead of `stacks.from_param!(...)`. The only authorization check that remains is `require_permission :read, :stack`, which only verifies the token's `permissions` array contains `read:stack` — it never checks `current_api_client.stack_id` against the requested `stack_id`: [6](#0-5) [7](#0-6) 

So any authenticated `ApiClient` with `read:stack` permission — even one deliberately restricted at creation to a single `stack_id` to limit its blast radius if leaked (the entire purpose of the scoping feature) — can supply an arbitrary `stack_id` in the CCMenu request and receive that other stack's latest deploy/rollback status and name, breaking the equality `token.stack_id == stack_touched`.

### Impact Explanation
This is an authorization-scope escalation: possession of a token intentionally restricted to one stack yields unauthenticated-for-that-scope read access to any stack's deploy state (`stack.deploys_and_rollbacks.last`, stack name, activity/build status) across the whole Shipit instance. This matches the "High" impact category of unauthorized read of stack state / deploy output beyond what the credential authorizes.

### Likelihood Explanation
Exploitation only requires a single valid, narrowly-scoped `ApiClient` token with `read:stack` permission (a routine, low-privilege artifact — e.g. the CCMenu integration flow itself creates and hands out such tokens via `CCMenuUrlController`) and knowledge/guessing of another stack's `to_param`/slug. No signature secret, session, or admin privilege is required beyond having one legitimately scoped API token.

### Recommendation
Remove the private `stack` override in `Shipit::Api::CCMenuController` and rely on the inherited, scope-aware `stack`/`stacks` methods from `BaseController` (or explicitly call `stacks.from_param!(params[:stack_id])`), so that stack-scoped tokens cannot query stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` restricted to Stack A with `permissions: ['read:stack']` and `stack_id: <A.id>` (this is the normal outcome of visiting the CCMenu URL feature for Stack A, or an admin-issued scoped token as in the `here_come_the_walrus` fixture).
2. Using that token/`authentication_token`, call `GET /api/stacks/:B_stack_id/ccmenu.xml` where `B` is a different stack the token was never granted access to.
3. Because `CCMenuController#stack` calls `Stack.from_param!` directly instead of the scoped `stacks.from_param!`, the request succeeds (permission check only verifies `read:stack` is in the permission list, not the stack id), returning Stack B's `deploys_and_rollbacks.last` build status/name in the XML response — data that should have been inaccessible to a token scoped to Stack A only.
