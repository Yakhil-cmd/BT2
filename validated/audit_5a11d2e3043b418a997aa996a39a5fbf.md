Found the binding break: `WebhooksController#verify_signature` selects which GitHub App config (and thus which HMAC secret) to verify against based on `repository_owner`, which is read from the attacker-controlled payload itself (`repository.owner.login`, falling back to `organization.login`), while the handler that actually creates/writes data (`PushHandler`, via `Handler#repository_name`) uses a *different* payload field — `repository.full_name` — to resolve the target `Repository`/`Stack`. These two fields are not required to agree.

### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while write path keys off `repository.full_name`, allowing cross-organization signature confusion - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret with `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`, both of which are attacker-supplied fields inside the same JSON body being verified. The actual repository that is mutated by handlers (e.g. `PushHandler` via `Handler#repository_name`/`#stacks`) is resolved from `payload.dig('repository','full_name')`, a sibling field in the same payload that is never cross-checked against `repository_owner`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` in `config/secrets*.yml`. When a webhook arrives, `verify_signature` picks the org-specific `github_app`/secret using `repository_owner`, which is the `login` under `repository.owner` in the JSON body (or `organization.login` as fallback). Because the HMAC signature (`X-Hub-Signature`) is computed over the **entire raw body**, and every field including `repository.owner.login` is part of that body, an attacker who owns/controls a legitimate GitHub App installation for **their own** organization (`org-A`, with a real, valid `webhook_secret`) can craft a payload where:
- `repository.owner.login` = `org-A` (so the app looks up `org-A`'s webhook secret to verify),
- `repository.full_name` = `org-B/victim-repo` (a different organization/repository actually tracked by Shipit).

The signature will validate correctly (it's signed with `org-A`'s real secret over the whole crafted body), and `verify_signature` passes. Then `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers (e.g. `PushHandler`) which resolve the target purely via `repository.full_name`, i.e., `org-B/victim-repo`, and operate on stacks belonging to that repository — a repository not owned by the authenticating organization at all. [4](#0-3) [5](#0-4) [6](#0-5) 

This breaks the intended binding: `organization authenticated (repository.owner.login) == repository written (repository.full_name)`. The signature check authenticates "this payload was sent by someone who knows org-A's webhook secret," but the write path trusts a different, unverified-against-that-identity field (`repository.full_name`) to decide *which* repository's stacks get processed.

### Impact Explanation
`PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for every non-archived stack matching the (attacker-chosen) branch on the spoofed target repository. Depending on which webhook events are wired up (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc. — see `Hook::EVENTS`/`Shipit::Webhooks.handlers`), this allows an attacker who only controls one legitimate, low-privilege GitHub App installation to inject fabricated GitHub state (commit statuses, check-suite results, membership/team changes, pull request metadata) into stacks belonging to a completely different organization/repository that they have no GitHub access to. This can influence CI-status-gated deploy safety checks or membership/team records for a repository the attacker does not own, i.e., an authentication-bypass-adjacent cross-repository write driven by a spoofable identity field. [2](#0-1) 

### Likelihood Explanation
Exploitation requires the attacker to control (or have installed) at least one GitHub App/organization already configured in Shipit's `github:` secrets with a known-to-them `webhook_secret" — i.e., they must already be an onboarded/trusted organization in this Shipit instance. Given that constraint, forging the cross-repository payload is trivial (a single crafted HTTP POST with a valid HMAC computed from their own secret). Multi-tenant Shipit deployments (multiple orgs configured, as shown in `config/secrets.development.shopify.yml`) are the realistic precondition. [7](#0-6) 

### Recommendation
After verifying the signature for `repository_owner`, additionally assert that `repository.full_name`'s owner segment matches the authenticated `repository_owner` (and likewise for `organization.login` events) before dispatching to handlers, e.g. reject the webhook if `params.dig('repository','full_name')&.split('/')&.first != repository_owner`.

### Proof of Concept
1. Attacker has a legitimate GitHub App installed for `org-A`, with `webhook_secret_A` configured in Shipit.
2. Attacker builds a `push` JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_A, body)>` and POSTs to `/webhooks`.
4. `verify_signature` computes `repository_owner = "org-A"`, loads `Shipit.github(organization: "org-A")`, verifies the signature successfully. [1](#0-0) 
5. `create` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("org-B/victim-repo")` and runs `sync_github` on its stacks, entirely unrelated to `org-A`. [5](#0-4) [3](#0-2)
