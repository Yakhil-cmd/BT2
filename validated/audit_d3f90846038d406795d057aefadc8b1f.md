### Title
Trigger unit timestamp is attacker-controlled below the true current time, letting an AA trigger sender bypass time-based freshness/maturity checks that rely on `trigger.timestamp` (analog to un-validated price staleness) - ([File: validation.js], [File: formula/evaluation.js])

### Summary
Obyte AAs commonly use the `timestamp` value of the triggering unit as a proxy for "now" in oscript formulas (e.g. maturity/freshness gates such as `if (timestamp < X) bounce(...)` as seen in `test/samples/futures_contract.oscript`). The only protocol-level constraints on a unit's `timestamp` field are an upper bound (`ifTransientError("timestamp is too far into the future")`) and a monotonicity constraint versus parent units. There is no lower bound tying the timestamp to the real wall-clock time it was actually broadcast/included, so an unprivileged unit author can post a trigger whose `timestamp` is set arbitrarily far in the past (down to the parent's timestamp), and this passes consensus validation.

### Finding Description
Unit timestamp validation only checks:
1. It's a positive integer, and
2. It is not more than `max_seconds_into_the_future_to_accept` (default 5s) ahead of the validating node's local clock: [1](#0-0) 

2. It does not decrease relative to any parent unit's timestamp: [2](#0-1) 

There is no check that the timestamp be *close to* the real current time from below — an author can freely choose any value between the parent's timestamp and "now + 5s". This value later flows into `objValidationState.last_ball_timestamp`/unit timestamp and is exposed to oscript formulas evaluated for AA triggers (e.g. the `timestamp` keyword and `data_feed[[...]]` freshness gating used together in `test/samples/futures_contract.oscript`, where formulas explicitly rely on `timestamp` to decide whether a maturity/exchange-rate condition has been reached): [3](#0-2) 

This mirrors the RAACNFT staleness bug pattern: the report's root cause was that a caller-supplied value used for economic decisions (price) had no freshness check against the true state. Here, the analogous caller-supplied value is the AA trigger's `timestamp`, used by AA authors as their only proxy for "current time" to gate stale-price/maturity logic, and it is not anchored to real elapsed time from below.

### Impact Explanation
An unprivileged trigger sender can craft a unit with an artificially old `timestamp` (as low as permitted by the parent-monotonicity rule) while still getting the unit accepted by validators/witnesses, since there is no floor check against actual wall-clock time. Any AA that gates fund-moving logic on `timestamp` thresholds (maturity dates, "wait for the price to be refreshed", deprecation/expiry windows, or time-locked releases) can be manipulated by an attacker choosing a timestamp that falsely represents "not yet matured" or "still fresh," letting them trigger AA logic paths at times the AA author intended to block, or hold back logic paths (bounce loops) intended to fire. Depending on the AA's design this can cause fund loss/freezing or unintended payouts, satisfying the "AA fund loss or freezing" impact criterion.

### Likelihood Explanation
Likelihood is moderate: exploitation requires an AA that uses `timestamp` (or the combination `timestamp` + `data_feed`) for maturity/staleness gating without cross-checking against the unit's MCI-derived last-ball timestamp or an independent oracle-provided freshness signal — a common enough pattern shown directly in the shipped sample contract (`futures_contract.oscript`). No special privilege is needed: any address can author a unit/trigger and choose its own timestamp within the permitted bounds.

### Recommendation
Add a lower-bound sanity check on unit timestamps relative to real time (not just an upper bound), or require AAs/oscript evaluation to expose a trusted, tamper-resistant time source (e.g., last-ball MCI-derived median timestamp) rather than the raw self-declared unit timestamp, so time-gated economic logic in AAs cannot be manipulated by the trigger author's chosen timestamp value. At minimum, document this clearly for AA authors and encourage using `last_ball_timestamp`/MCI-based time instead of raw `timestamp` for maturity checks in AA templates and examples.

### Proof of Concept
1. Attacker submits a payment/AA-trigger unit whose `timestamp` field is set to a value only slightly greater than its chosen parent's timestamp (satisfying `objUnit.timestamp >= objParentUnitProps.timestamp` at `validation.js:693-694`), while real wall-clock time has advanced much further — the unit still passes `validation.js:280-287` because that check only bounds the timestamp from above (`current_ts + 5s`), never from below.
2. This unit becomes a valid AA trigger; when the target AA evaluates formulas containing `timestamp` (as in `test/samples/futures_contract.oscript:59-90`, e.g. `if (timestamp < 1556668800) bounce('wait for maturity date')`), the attacker's artificially old timestamp lets them either avoid or force branches keyed to maturity/freshness, despite real time having already passed the threshold.
3. No confirmation from the exact production AA templates in this environment beyond the sample was verified due to index truncation; the fundamental gap (no lower-bound timestamp validation tied to real time) is confirmed directly in `validation.js`.
