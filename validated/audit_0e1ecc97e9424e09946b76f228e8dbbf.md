### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while the target `Stack`/`Repository` is resolved from the unauthenticated `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) from the *unverified* JSON body, but the handlers that actually act on the payload (push, pull_request, status, etc.) resolve the target `Repository`/`Stack` using a *different* field of the same unverified body — `repository.full_name`. Because both fields come from the same attacker-controlled payload and are never cross-checked, a webhook correctly signed by Organization A's webhook secret can carry a `repository.full_name` pointing at Organization B's repository, causing Shipit to act on Organization B's stack.

### Finding Description
`Shipit.github(organization:)` supports multiple independent GitHub App configurations keyed by organization name (`lib/shipit.rb:170-200`, `Shipit::TOP_LEVEL_GH_KEYS`, `github_app_config`), each with its own `webhook_secret`. Fixtures such as `test/dummy/config/secrets_double_github_app.yml` show this "double github app" multi-tenant configuration is an intended, supported deployment shape. [1](#0-0) 

`verify_signature` picks the app/secret used to validate `X-Hub-Signature` purely from: [2](#0-1) 

i.e. `params.dig('repository', 'owner', 'login')`, itself taken from the raw JSON body before any authentication has occurred.

Once the signature check passes (using Org A's `webhook_secret`), `create` dispatches the same raw params to the registered handler: [3](#0-2) 

Handlers resolve which `Repository`/`Stack` to mutate from a *different* field of the same body, `repository.full_name`, with no re-validation that it belongs to the organization that produced a valid signature: [4](#0-3) [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` simply splits `owner/name` out of that string and looks it up with no relation to `repository.owner.login`: [7](#0-6) 

**Binding broken (equality that must hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login)` ⚉ `repository/stack actually written by the handler (repository.full_name)`

Before the attack: for legitimate GitHub-originated webhooks, `repository.owner.login` and the owner segment of `repository.full_name` always refer to the same repository, so the two fields are implicitly consistent and the missing cross-check is invisible.

After the attack: an operator who legitimately controls Organization A (and thus knows Org A's `webhook_secret`, configured for their own Shipit GitHub App installation) can send a request to `/webhooks` with `X-Hub-Signature` computed over a JSON body where `repository.owner.login = "OrgA"` (so `verify_signature` loads and validates against Org A's secret) but `repository.full_name = "OrgB/some-repo"` (a repository/stack belonging to a different, unrelated tenant of the same Shipit instance). The signature check succeeds, and the event handler acts on Org B's `Stack`, e.g.:
- `push` event → `GithubSyncJob` enqueued for Org B's stack, using an attacker-chosen `after` SHA (`PushHandler#process`), influencing what Shipit considers "known"/deployable commits for that stack;
- `pull_request opened/closed/reopened/labeled/unlabeled` events → creation, archival, or unarchival of Org B's `ReviewStack` (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`), which can trigger provisioning/deprovisioning workflows and task execution against Org B's infrastructure;
- `status`/`check_suite` events → forged commit statuses / check-run refreshes recorded against Org B's commits, which can influence CI gating and thus which commits Shipit considers deployable.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. It allows a customer/tenant of a shared, multi-org Shipit instance to forge webhook events attributed to a different tenant's repository despite passing signature verification, causing unauthorized state changes (sync, review-stack provisioning/deprovisioning, forged CI status) on stacks they do not own. Depending on `shipit.yml` `ci.require`/`review` configuration for the victim stack, this can influence whether a commit is treated as deployable or trigger provisioning task execution (`ReviewStackProvisioningQueue`), which can lead to task/step execution against the victim's stack. This maps to the "unauthorized deploy/rollback" / "escalation across tenants" class of High-severity impact.

### Likelihood Explanation
The attacker only needs to be a legitimate operator of one organization/tenant configured on a shared Shipit instance (i.e., they already know their own org's `webhook_secret`, which they set up themselves when installing their own GitHub App) — no privileged Shipit account, `ApiClient` token, or leaked secret belonging to another tenant is required. Crafting the raw JSON payload and computing an HMAC-SHA1 signature over it is trivial; the request can be sent directly to the public `/webhooks` endpoint. The precondition is a multi-organization Shipit deployment (explicitly supported and documented, e.g. `secrets_double_github_app.yml`), so likelihood is moderate-to-high in any installation serving more than one GitHub organization/tenant.

### Recommendation
After signature verification, require that the resolved `repository_owner` (used to select the verifying GitHub App/secret) matches the owner segment of `repository.full_name` (or `organization.login` for org-scoped events) before dispatching to handlers; reject the webhook with 422 on mismatch. More generally, handlers should receive/validate the already-authenticated organization context rather than re-reading unauthenticated fields from the JSON body to select the write target.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App/`webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`); create a `Stack`/`Repository` for `OrgB/victim-repo`.
2. As the operator of `OrgA` (who knows `OrgA`'s `webhook_secret` because they configured it), build a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)`.
4. `POST /webhooks` with header `X-Github-Event: push`, the above signature, and the body.
5. `WebhooksController#verify_signature` resolves `repository_owner = "OrgA"`, loads `OrgA`'s `GitHubApp`, and the signature validates successfully.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues a `GithubSyncJob`/updates state for `OrgB`'s stack — despite the request never being authenticated by `OrgB`'s GitHub App or webhook secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
