## Title
AA financial-logic that relies on live `balance[asset]` for share/price math is manipulable through atomic chained secondary triggers — ([File: formula/evaluation.js], [File: aa_composer.js])

### Summary
The Spartan Protocol exploit stems from computing LP-share issuance/redemption from the pool's *instantaneous* token balance (`balanceOf`) rather than from an internally tracked reserve, and from being able to chain `addLiquidity`/donate/`removeLiquidity` atomically inside one flash-loaned transaction. ocore's Autonomous Agent (AA) engine has the same structural ingredients: the `balance[asset]` oscript operator returns the AA's *live*, mutable balance (not an independently-tracked reserve), and a single top-level trigger unit can atomically chain multiple secondary AA invocations — including re-invoking the *same* AA more than once — all committed (or rolled back) together in one database transaction. ocore's own reference AMM sample encodes LP math directly from `balance[]`, reproducing the exact anti-pattern that caused the Spartan loss.

### Finding Description
The `balance` oscript operator reads the AA's currently tracked balance directly out of `objValidationState.assocBalances` / the `aa_balances` table, which is mutated incrementally on every trigger and every payment sent by the AA: [1](#0-0) 

This balance is updated in place both when a trigger's incoming coins are first "added" to the AA (`updateInitialAABalances`) and again after the AA sends its own payments (`updateFinalAABalances`): [2](#0-1) [3](#0-2) 

Critically, ocore supports **synchronous, atomic chains of AA invocations** stemming from one primary trigger unit: whenever an AA's response sends a payment to another AA address, that AA is immediately triggered as a "secondary trigger", all within the same open DB transaction, and this can recurse arbitrarily (subject to `MAX_RESPONSES_PER_PRIMARY_TRIGGER`), including the **same AA being called more than once** in the chain, as explicitly handled at commit time: [4](#0-3) [5](#0-4) 

If any step later in the chain bounces, the entire top-level transaction rolls back atomically via `revert()`/rollback of the surrounding SQL transaction and batch — but if every step succeeds, all state/balance changes across every hop of the chain, including multiple sequential invocations of the same pool AA, are committed together. This gives an attacker the same capability the Spartan exploit relied on a flash loan for: performing "deposit → donate → withdraw" (or an equivalent sequence) against a pool AA fully atomically, with each step's `balance[asset]` read reflecting all state mutations made by the earlier steps in the same chain, and with no atomicity boundary that isolates one logical "operation" from another the way a real reserve variable would.

ocore's own shipped AMM reference implementation encodes LP issuance/redemption and swap pricing directly from live `balance[$asset]` / `balance[base]` (rather than an isolated, protected reserve state variable), exactly mirroring Spartan's flawed design: [6](#0-5) [7](#0-6) 

Any AA author who copies this documented, tested pattern (or the analogous cross-AA `balance[$destination_aa][base]` read in `fundraising_proxy.oscript`) inherits the same class of bug: a value computed as "my share of currently-held balance" can be inflated by any party who can insert an intermediate atomic step (a plain "donate" payment, or a chained secondary-trigger payment) between the mint and the burn steps of the same atomic call chain. [8](#0-7) 

### Impact Explanation
If exploited against a deployed pool/vault AA built on this pattern (which ocore itself documents and tests as the canonical AMM design), an attacker could mint LP/share tokens against an inflated `balance[]` reading produced by their own atomic chain of payments, then redeem those shares for more of the pool's real assets than they contributed — directly draining funds from other liquidity providers/AA balance holders. This is a concrete AA fund-loss scenario reachable by any ordinary unit poster/AA trigger sender, matching the "AA fund loss" impact category.

### Likelihood Explanation
Exploitability requires only standard, unprivileged capabilities available to any AA author or trigger sender: posting payment units, defining/chaining AAs, and using `balance[asset]`/`balance[base]` — all of which are core, sanctioned oscript features, and the vulnerable pattern is literally distributed as ocore's own tested sample AMM. No consensus-breaking bug in the engine itself is required; the risk arises from a genuine, reachable, and officially-endorsed combination of features (`balance[]` + atomic secondary-trigger chaining), making it moderate-to-high likelihood wherever such AAs are deployed as-is.

### Recommendation
- Do not use ocore's `balance[asset]`/`balance[base]` operator as the sole source of truth for pro-rata share/price math in AMM-like or vault-like AAs; instead maintain a dedicated, explicitly updated state variable (a "reserve") that is only mutated by the AA's own recognized deposit/withdraw code paths, and reconcile it against `balance[]` defensively (e.g., reject/ignore unexpected surplus rather than incorporate it into share math).
- Update the shipped reference implementations (`test/samples/uniswap_like_market_maker.oscript`, `test/samples/fundraising_proxy.oscript`) to use tracked reserve state vars instead of live `balance[]`, since these samples are likely copied as templates by real AA authors.
- Consider documenting explicitly (in AA-authoring guidance) the atomicity/chaining semantics of secondary triggers and the risk of using instantaneous `balance[]` reads for financial calculations, given that a single top-level trigger can atomically re-invoke the same AA multiple times.

### Proof of Concept
Conceptual chain, analogous to the Spartan flow, exploiting the combination of `balance[]`-based math and atomic secondary-trigger chaining against an AA implementing the `uniswap_like_market_maker.oscript` pattern:
1. Attacker posts a unit whose primary trigger goes to an "orchestrator" AA (or directly issues carefully sequenced units if secondary-trigger chaining to the pool suffices).
2. Orchestrator's response #1 sends a payment to the pool AA structured to match the "invest" case, minting `mm_asset` shares based on `balance[$asset]`/`balance[base]` computed *before* this step.
3. Orchestrator's response #2 (chained secondary trigger back to the pool, or a subsequent unit within the same processing window) sends a plain "donate" payment that the pool logic interprets favorably (e.g., matches the "exchange" case or is simply added to `balance[]`), inflating `balance[$asset]`/`balance[base]` without minting further shares to a legitimate depositor.
4. Orchestrator's response #3 immediately divests using the `mm_asset` shares minted in step 2, whose payout formula (`round($investor_share * balance[$asset])`) now reflects the inflated balance from step 3, letting the attacker extract more value than deposited — all committed atomically in a single top-level trigger's DB transaction per `aa_composer.js`'s `handleSecondaryTriggers`/commit logic. [9](#0-8)
