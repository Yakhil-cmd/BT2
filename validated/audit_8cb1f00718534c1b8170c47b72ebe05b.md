### Title
CCMenu API endpoint ignores `ApiClient#stack_id` scoping, letting a stack-scoped token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` re-implements `stack` lookup by calling `Stack.from_param!(params[:stack_id])` directly instead of using the scoped `stacks` helper from `Shipit::Api::BaseController`. This breaks the equality that should hold for every API endpoint: `stack a token authorizes == stack a token touches`. A token bound to `ApiClient.stack_id` (a stack-scoped credential) is authorized for `read:stack` on **its own stack only**, but the CCMenu controller lets it read CI/deploy status for **any stack** by supplying a different `stack_id` param.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping generically: [1](#0-0) 

`current_api_client.stack_id?` restricts the visible/queryable stacks to the one the token was created for, and every controller that inherits `stack`/`stacks` unmodified (e.g. `Shipit::Api::StacksController`) is subject to this restriction: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving the requested `stack_id` against the full `Stack` table instead of the `stacks` scope: [3](#0-2) 

The controller's authorization check only validates the coarse-grained permission string via `require_permission :read, :stack`, which resolves to `ApiClient#check_permissions!`: [4](#0-3) 

This method never inspects `stack_id`; it only checks that `"read:stack"` is present in `permissions`. The per-stack restriction is enforced *only* via the `stacks` scoping method in `BaseController`, which `CCMenuController` deliberately does not call. The `ApiClient` model itself confirms `stack_id` is a real, intended per-record scope (`belongs_to :stack, optional: true`): [5](#0-4) 

and the fixture/test suite for `StacksController` demonstrates this scoping is an explicit security guarantee ("an api client scoped to a stack will only see that one stack"): [6](#0-5) 

Because `CCMenuController` has its own `authenticate_api_client` that authenticates any valid token by query-string parameter (rather than only the app's own CCMenu client), any stack-scoped `ApiClient` token (e.g. one with `permissions: ['read:stack']` and `stack_id` set, matching fixture `here_come_the_walrus`) can be replayed against `/api/<any-stack>/ccmenu.xml` with an arbitrary `stack_id`, disclosing deploy/rollback status of stacks the token was never authorized for: [7](#0-6) [8](#0-7) 

### Impact Explanation
This matches the "High" bucket defined by the rules: **unauthenticated/unauthorized read of stack state or task/deploy output**. A credential minted to be readable-only for one stack (deliberately scoped via `stack_id`, e.g. via the CCMenu URL feature or any other stack-scoped API client a user was issued) can be used to enumerate deploy/rollback state of every other stack in the installation, defeating the per-stack confidentiality boundary that `ApiClient.stack_id` is meant to enforce.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` API token (which is routinely handed out per-stack, e.g., via the CCMenu integration flow in `CCMenuUrlController`, or via manually created scoped `ApiClient`s) can exploit this with a single unauthenticated-boundary-crossing HTTP GET, requiring no special privileges beyond possessing one legitimate scoped token and knowledge/guessing of another stack's identifier. No signature forgery or additional secrets are needed — this is a straightforward authorization-scope bug, trivially reachable by anyone with any valid stack-scoped token.

### Recommendation
Have `CCMenuController#stack` reuse the scoped lookup from `BaseController` instead of hitting `Stack` directly, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This restores the equality that `stacks` (and therefore `stack`) is always filtered by `current_api_client.stack_id` when present, consistently with every other endpoint in `Shipit::Api::BaseController`.

### Proof of Concept
1. Using the `here_come_the_walrus` fixture pattern, create/have a stack-scoped `ApiClient` with `stack_id` set to Stack A and `permissions: ['read:stack']` (see `test/fixtures/shipit/api_clients.yml` lines 12-17 for the exact shape of such a token).
2. Compute its `authentication_token` (as shown in `test/models/api_client_test.rb`).
3. Send `GET /api/<Stack B id or name>/ccmenu.xml?token=<token>` where Stack B is a stack the client was never scoped to.
4. Because `CCMenuController#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) resolves `params[:stack_id]` against the entire `Stack` table rather than `stacks` (which would filter by `current_api_client.stack_id`), the request succeeds and returns Stack B's latest deploy/rollback status — data the token was never authorized to read.
