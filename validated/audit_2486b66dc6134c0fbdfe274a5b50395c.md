### Title
Asymmetric validation in `SyncRepo` allows publishing an unverified new worktree via the atomic symlink - ([File: main.go])

### Summary
The Hyperdrive report describes a class of bug where a function validates one output value (`baseProceeds`) but leaves a second, causally-linked output (`withdrawalShares`) completely unchecked, letting an attacker manipulate the unchecked value between "check" and "use." The analogous condition in `git-sync--012` is in `repoSync.SyncRepo`: the integrity check (`sanityCheckWorktree`) is only ever applied to the *reused* current worktree path, never to the *newly created* worktree that is about to be published via the atomic `--link` symlink.

### Finding Description
`SyncRepo` [1](#0-0)  computes `remoteHash` from `FETCH_HEAD^{}` and compares it to the locally recorded `currentHash`. The sanity check is only invoked in the branch where the hash is unchanged, to validate the pre-existing worktree: [2](#0-1) 

When the hash *has* changed (the normal "there is new content" path), `createWorktree` builds a brand-new worktree with `--no-checkout` [3](#0-2) , `configureWorktree` performs the actual checkout/sparse-checkout/submodule setup, and then the code immediately calls `syncHooks.beforePublish` and `git.publishSymlink(newWorktree)`: [4](#0-3) 

There is no call to `sanityCheckWorktree` (which validates that the directory isn't empty, that `HEAD` matches the expected hash, and runs `git fsck --connectivity-only`) on `newWorktree` before it is atomically exposed to consumers through `publishSymlink` [5](#0-4) . In other words, the "slippage check" (integrity/consistency validation) exists for one code path (re-use of an already-published worktree) but is missing for the other, more security-sensitive path (publishing brand-new content fetched from a remote, possibly attacker-influenced, repository) — mirroring the pattern in the Hyperdrive report where one output is protected and the other is not.

### Impact Explanation
Since `configureWorktree` performs the real checkout (including submodule handling, per the many `submodule`-related code paths in `main.go`) and can partially fail or leave the worktree inconsistent without necessarily returning a fatal error for every failure mode, and because no post-checkout consistency check exists for the "changed" branch, git-sync can publish a worktree via the `--link` symlink that is empty, partially checked out, or inconsistent with the recorded hash. This directly matches the accepted impact category "publishing wrong or partial content" through the tool's core atomic-publish contract, which downstream consumers rely on as their sole correctness guarantee [6](#0-5) .

### Likelihood Explanation
This path is reachable on every normal sync where the remote ref changes — i.e., any attacker who can push a commit/ref to the tracked repository (the standard, unprivileged threat model for git-sync) exercises exactly this code path each time. No special flags are required; it is the default `SyncRepo` behavior whenever `changed == true`. The likelihood of the missing-check condition being *hit* is high; the likelihood of it being *exploitable* into concrete corruption depends on ancillary failure modes in `configureWorktree`/checkout (e.g., truncated checkout, submodule fetch partial failure) that are not fully instrumented from the available index — this residual uncertainty should be validated against the full `configureWorktree` implementation, which the current index did not return in full.

### Recommendation
Call `git.sanityCheckWorktree(ctx, newWorktree)` unconditionally after `configureWorktree` and before `beforePublish`/`publishSymlink` in the `changed` branch of `SyncRepo`, so that both the reused-worktree and newly-created-worktree paths receive the same integrity validation before being exposed through the atomic symlink contract.

### Proof of Concept
Conceptual PoC (not runnable without the full `configureWorktree` source, which the index did not surface):
1. Point `--repo`/`--ref` at an attacker-controlled or attacker-influenced remote (e.g., a repo with a submodule that fails mid-checkout, or induce a filesystem race during `createWorktree`/`configureWorktree`).
2. Trigger a sync where `remoteHash != currentHash` so the `changed` branch executes.
3. Cause `configureWorktree` to leave `newWorktree` partially checked out without returning a hard error.
4. Observe that `SyncRepo` proceeds directly to `publishSymlink(newWorktree)` without ever invoking `sanityCheckWorktree` on it, exposing the incomplete/incorrect content to consumers reading through `--link`.

Given the incomplete visibility into `configureWorktree`'s exact failure semantics, a Devin session with full repository access would be needed to construct and run a concrete, executable end-to-end PoC (e.g., adapting an `e2e::*` test in `test_e2e.sh`) confirming that partial content can pass through unchecked.

// publishSymlink atomically sets link to point at the specified target.  If the
// link existed, this returns the previous target.
func (git *repoSync) publishSymlink(worktree worktree) error {
	targetPath := worktree.Path()
	linkDir, linkFile := git.link.Split()

	// Make sure the link directory exists.
	if err := os.MkdirAll(linkDir.String(), defaultDirMode); err != nil {
		return fmt.Errorf("error making symlink dir: %w", err)
	}

	// linkDir is absolute, so we need to change it to a relative path.  This is
	// so it can be volume-mounted at another path and the symlink still works.
	targetRelative, err := filepath.Rel(linkDir.String(), targetPath.String())
	if err != nil {
		return fmt.Errorf("error converting to relative path: %w", err)
	}

	const tmplink = "tmp-link"
	git.log.V(2).Info("creating tmp symlink", "dir", linkDir, "link", tmplink, "target", targetRelative)
	if err := os.Symlink(targetRelative, filepath.Join(linkDir.String(), tmplink)); err != nil {
		return fmt.Errorf("error creating symlink: %w", err)
	}

	git.log.V(2).Info("renaming symlink", "root", linkDir, "oldName", tmplink, "newName", linkFile)
	if err := os.Rename(filepath.Join(linkDir.String(), tmplink), git.link.String()); err != nil {
		return fmt.Errorf("error replacing symlink: %w", err)
	}

	return nil
}

// createWorktree creates a new worktree and checks out the given hash.  This
// returns the path to the new worktree.
func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}

One of the things in that directory is a symlink (see the `--link` flag) to the

exact target of that symlink is an implementation detail, but the leaf
component of the target (i.e. `basename "$(readlink <link>)"`) is the git hash
