### Title
Unvalidated swap routes can execute arbitrary contract code under the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller treats a caller-provided swap route as opaque `Bytes` and forwards it to the configured router after authorizing only the expected input-token transfer. However, the route can direct the router through an arbitrary venue/pool contract. Code invoked through that route can make additional `require_auth` calls against the caller; transaction simulation records those calls as child invocations of the caller’s swap authorization. If the caller signs the resulting authorization tree, the routed contract can transfer unrelated wallet assets to an attacker.

This is analogous to the NocoDB issue: a validation boundary checks the expected outer operation but does not constrain the executable target. Here, the checked operation is the controller’s exact input transfer; the unchecked route-selected contract executes below the caller’s authorization.

### Finding Description
`swap_collateral` accepts attacker-controlled `swap: Bytes` and passes it to `swap_tokens`. `swap_tokens` authorizes one exact transfer of `token_in` from the controller to the router, invokes `router.execute_strategy(controller, amount_in, swap)`, and then validates only balance deltas and positive output.

The relevant flow is:

- `contracts/controller/src/lib.rs:283-302`: `swap_collateral` accepts the route bytes.
- `contracts/controller/src/strategies/swap.rs:29-38`: controller snapshots balances, authorizes the exact input transfer, and invokes the configured router with opaque `swap`.
- `interfaces/swap-aggregator/src/lib.rs:20`: `execute_strategy` receives the caller-controlled serialized route.
- `contracts/swap-aggregator/src/execute/mod.rs:153-165`: decoded swap hops can name the pool/contract to dispatch.
- `docs/explanation/threat-model.md:154-164`: documents that unallowlisted route venues can place third-party code below the caller’s authorization and induce additional caller-token transfers.
- `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:39-46`: demonstrates a router calling a route-selected `hop_pool`.
- `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-70`: demonstrates the rogue pool transferring a victim’s unrelated wallet token.
- `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-226`: demonstrates simulation recording the theft under the caller’s `swap_collateral` authorization.
- `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:258-268`: demonstrates that signing the recorded tree authorizes the theft.

The controller’s post-router checks cannot detect this theft because the stolen token need not be the strategy input or output. The route can still return a valid output, satisfy `received > 0`, and leave the account solvent.

### Impact Explanation
An attacker can steal arbitrary tokens from a user’s wallet, beyond the collateral amount being routed.

The malicious venue can call `token.transfer(victim, attacker, amount)` on any token where `victim.require_auth()` succeeds. Simulation records that token transfer as a child invocation under the victim’s `swap_collateral` authorization. If the victim signs the poisoned authorization tree, the unrelated wallet-token transfer succeeds while the apparent swap still completes normally.

This is theft of user funds and is not limited to the routed amount, swap output, or assets deposited in the lending protocol.

### Likelihood Explanation
An unprivileged attacker only needs to convince a victim to submit a transaction containing a crafted route. No privileged role, leaked key, oracle manipulation, contract upgrade, or protocol parameter change is required.

The attack depends on the victim signing the authorization tree produced by simulation. This is realistic because Soroban transaction flows commonly present the outer invocation while relying on clients to inspect nested authorization entries. The repository’s own threat model explicitly identifies this exposure and states that clients must reject routes whose authorization tree contains unexpected child calls.

Likelihood is therefore moderate: exploitation requires malicious-route delivery and insufficient client-side authorization-tree inspection, but no on-chain privilege is needed.

### Recommendation
Constrain route execution so strategy calls cannot place arbitrary contracts beneath the caller’s authorization.

The router should restrict hop `pool` addresses to governance-approved venue contracts, or otherwise prevent route-selected contracts from invoking token calls authorized by the original `sender`. If arbitrary venues must remain supported, the protocol boundary should be changed so the router cannot rely on the caller’s root authorization during venue execution.

Clients should additionally:

1. Decode route payloads before signing.
2. Simulate the complete controller call.
3. Reject any authorization tree containing children other than the expected strategy input transfer.
4. Surface nested token transfers and their token, recipient, and amount to the signer.

Regression coverage should assert that a route-selected contract cannot add a caller-token transfer beneath `swap_collateral`, `repay_debt_with_collateral`, `swap_debt`, `multiply`, or `flash_position`.

### Proof of Concept
The repository already contains a focused reproduction in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

The test constructs a route whose `hop_pool` is an attacker-deployed `RogueHopPool`. During `swap_collateral`, the router calls that pool; the pool calls:

```rust
token::Client::new(&env, &wallet_token)
    .transfer(&victim, &attacker, &amount);
```

Simulation records the transfer as a child of the victim’s `swap_collateral` authorization, and enforcing auth accepts it when the victim signs that child. The test then verifies:

```rust
assert_eq!(s.wallet(&s.alice), 0);
assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
```

The swapped `ETH` output is still delivered and deposited, demonstrating that the protocol’s output and solvency checks do not prevent the unrelated wallet-token theft.
