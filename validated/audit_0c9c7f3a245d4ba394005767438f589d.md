### Title
Unbounded per-output double-spend conflict list causes unbounded validation cost in `checkForDoublespends` - (File: `validation.js`)

### Summary
`checkForDoublespends` in `validation.js` iterates over every conflicting record returned by a doublespend-lookup SQL query, and for each one performs a graph traversal (`graph.determineIfIncludedOrEqual`) to determine ancestry. Nothing in the code bounds the number of conflicting spends that can accumulate against a single output before it stabilizes, so an attacker fully controls the size of this list and, by extension, the CPU cost every validating node must pay whenever a competing unit spending the same output is validated.

### Finding Description
When a unit is validated, `validatePaymentInputsAndOutputs` (in `validation.js`, around lines 2258-2305) builds a doublespend query for every input (`checkInputDoubleSpend`) and calls `checkForDoublespends`: [1](#0-0) 
`checkForDoublespends` then runs `async.eachSeries` over **all** rows returned by that query, and for every non-light node calls `graph.determineIfIncludedOrEqual`, a DAG ancestry-walk, for each conflicting record: [2](#0-1) 

There is no limit anywhere in this path on how many prior conflicting (`is_unique=NULL`) spends of the same source output can exist simultaneously. An unprivileged unit poster can:
1. Post a first unit that spends an output.
2. Before that unit stabilizes, repeatedly author many further sibling units, each spending the *same* source output from the same address (classic doublespend), each producing a new row in `inputs` with `is_unique=NULL` and each internally re-triggering the same `checkForDoublespends`/`acceptDoublespends` logic (lines 2274-2296), which appends more entries to `objValidationState.arrDoubleSpendInputs` and re-uses the same unbounded query pattern each time a new doublespend arrives.
3. Every subsequent legitimate/competing unit that touches this output (or any of the growing set of conflicting units) forces every full node in the network to run the O(N) graph-ancestry loop where N is the number of accumulated conflicting spends, since `checkForDoublespends` is invoked again on each new unit.

This is directly analogous to the reported `FCNProduct.sol` bug: a loop whose iteration count is proportional to attacker-controlled state (there: queue length; here: count of conflicting doublespend inputs for one output), with no upper bound, callable by anyone who is a normal DAG participant (not a privileged/hub/witness role).

### Impact Explanation
Because `checkForDoublespends` is on the mandatory validation path for every payment unit (`validatePaymentInputsAndOutputs` → `validatePayload`/`validateInlinePayload` → `validate`), unbounded growth of the conflict list directly increases the CPU/DB cost of validating units that touch the contested output. Different full nodes may process the accumulating doublespend chain at different speeds (depending on hardware, current mutex/queue load, DB backend), which can cause:
- Nodes falling behind in validating/writing units in the affected DAG region, delaying main-chain advancement and stability determination for units depending on it.
- In degenerate cases (very large attacker-built doublespend fan-out), a node could stall long enough on this single validation call that timely stabilization of the region is disrupted, since MC advancement requires witnessed/stable ancestors to be fully validated first.

This maps to the "node disagreement on validity or stability" / "network unable to confirm new units" impact classes required by the validation rules, because the attack vector is a normal unprivileged double-spend (an already-tolerated but rate-unlimited pattern) whose cost scales with an attacker-chosen, unbounded fan-out.

### Likelihood Explanation
Likelihood is Medium: doublespending is an intrinsic, permitted (if ultimately penalized) DAG operation — any address holder can author many sibling units spending the same output before the first one stabilizes, at the cost of proportional bytes/fees for each additional unit. The barrier to building a large N is economic (unit posting cost), not structural, since the codebase places no explicit cap on the number of simultaneous conflicting spends of one output that get processed by `checkForDoublespends`.

### Recommendation
- Add an explicit upper bound on the number of conflicting doublespend records that `checkForDoublespends` will process/query (e.g., `LIMIT` clause plus a hard validation failure if the true count exceeds the cap), similar to the `MAX_PARENTS_PER_UNIT`, `MAX_MESSAGES_PER_UNIT`, and other existing anti-spam caps used elsewhere in `validation.js` (e.g. `constants.MAX_MESSAGES_PER_UNIT`, `objUnit.parent_units.length > constants.MAX_PARENTS_PER_UNIT` in `validateParentsExistAndOrdered`): [3](#0-2) 
- Alternatively, short-circuit `checkForDoublespends`'s per-record `graph.determineIfIncludedOrEqual` calls with cheaper pre-filters (e.g., skip conflicting records whose `main_chain_index` already places them outside the plausible ancestry range) before falling back to the expensive graph walk, and cap the batch size passed into `async.eachSeries`.
- Consider rate-limiting/penalizing repeated doublespend attempts from the same address within a short DAG window, independent of the validation-cost fix, to reduce economic incentive for building large conflict sets.

### Proof of Concept
1. Attacker controls address `A` with a spendable output `O`.
2. Attacker composes and posts unit `U1` spending `O` to address `X`.
3. Before `U1` stabilizes, attacker composes and posts `U2..UN`, each also spending `O` (classic doublespend), fanned out as siblings in the DAG (not descendants of each other), each unit paying only minimal fees.
4. Each `Ui` insertion runs `validatePaymentInputsAndOutputs` → `checkInputDoubleSpend` → `checkForDoublespends`, and every additional `Ui` grows the set of `is_unique=NULL` rows in `inputs` tied to `O`.
5. Once `N` is large, any further legitimate unit referencing `O`'s conflict set (or any node re-validating this DAG region, e.g. during a resync or reorg check) must execute `graph.determineIfIncludedOrEqual` `N` times inside `checkForDoublespends`, with cost scaling linearly (or worse, given repeated graph walks) in `N`, with no cap in place.

Note: I was not able to fully trace every downstream re-validation trigger (e.g., exact behavior during `advanceMcStability`/`markMcIndexStable` re-processing of the conflicting units) within the available tool budget; a full reproduction would require running the local test harness (e.g. `test/validation*.js`) to measure actual wall-clock validation time as `N` grows, which a Devin session with code execution access could verify directly.

	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);

					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);

	);
}
