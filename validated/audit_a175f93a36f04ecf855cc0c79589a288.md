### Title
`StatusHandler#process` applies GitHub `status` events to any commit matching `sha` without verifying the payload's `repository.full_name` against the commit's own `stack.github_repo_name`, letting a `status` webhook for one repository flip `Commit#deployable?` for a same-SHA commit tracked under a different, victim-owned repository/stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` (`Commit.where(sha: params.sha)`) and writes the attacker-supplied `state` onto every matching commit, regardless of which repository the webhook's payload claims to describe. Because git SHA1s are content-addressed and identical across forks that share history, an attacker who owns any GitHub repository/organization configured in Shipit (and thus its `webhook_secret`) can fork a victim's repository, then send a signed `status` webhook whose `repository.full_name` is their own fork but whose `sha` matches a commit already tracked in the victim's `Stack`, forcing `Commit#deployable?` to become true for the victim's commit.

### Finding Description
The trust binding the question describes should be:
`status.stack.github_repo_name == payload['repository']['full_name']` — a `state` transition should only be trusted for a commit if it was reported against that commit's own tracked repository.

Tracing the code shows this binding is never enforced:

- `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` do resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, but `StatusHandler` **never calls `stacks` or `repository_name`**: [1](#0-0) 
- `StatusHandler#process` looks up commits **globally by `sha` only** and unconditionally applies the payload's `state`: [2](#0-1) 
- `Commit#create_status_from_github!` simply persists a `Status` record from whatever is passed in, with no repository check: [3](#0-2) 
- `Commit#deployable?` reads that status directly through `status`/`success?`: [4](#0-3) , and `status` is derived from `statuses_and_check_runs`, i.e. exactly the rows `create_status_from_github!` writes: [5](#0-4) 

**Exploit path:** Webhook signature verification (`WebhooksController#verify_signature`) is scoped **per repository owner**, not globally: `Shipit.github(organization: repository_owner)` selects the GitHub App/`webhook_secret` config for whatever organization owns `params.dig('repository','owner','login')` in the *attacker's own payload*: [6](#0-5) . This means an attacker who controls (or has installed the Shipit-integrated GitHub App on) their own organization/repository can produce a validly-signed webhook for events "about" that org — that is the intended design (self-service GitHub App installs). The signature check validates *who sent the event*, not *which repository's commits it is allowed to mutate*.

Because `StatusHandler` never cross-checks `payload['repository']['full_name']` against the `stack.github_repo_name` of the commits it mutates, a validly-signed webhook from the attacker's own repository can write a `state` onto a `Commit` row belonging to an entirely different, victim-owned `Stack` — as long as the `sha` values coincide. SHA1 git commit hashes are content-addressed (tree + parents + author/committer + message), so any public fork of the victim's repository trivially reproduces identical commit SHAs for the shared history. The attacker:

1. Forks/clones the victim's public repository (shared commit history ⇒ identical SHAs).
2. Configures/owns a GitHub organization or repo for which Shipit already holds a `webhook_secret` (their own installation), giving them a legitimately-signable webhook channel.
3. POSTs `/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` for their own org's secret, and a JSON body: `sha` = the shared/victim commit SHA, `state: "success"`, `repository.full_name` = the attacker's own fork.
4. `verify_signature` passes (it only checks the attacker's own secret against the attacker's own claimed `repository_owner`).
5. `StatusHandler#process` finds the victim's `Commit` row by `sha` (ignoring `repository.full_name`) and writes a `success` status onto it.
6. `Commit#deployable?` on the victim's stack flips to `true` (if `!locked?` and no other `blocked?`/`stack.blocking_statuses` condition holds), with no contact ever made to the victim's repository, `Stack#ignore_ci?`, or any real GitHub check API.

None of the listed guards prevent this: `verify_signature` authenticates the *sender's own organization*, not the *target repository of the mutation*; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` requires `sha`/`state`/`repository` shape but performs no cross-record authorization; `force_github_authentication`, `User#authorized?`, `require_permission!`, and the `stacks` scope are UI/API-session concerns not invoked on this webhook path; model validations on `Repository`/`Stack` don't constrain which `Commit` rows a `Status` write may target.

### Impact Explanation
An attacker with only their own GitHub repository/organization webhook credentials can write arbitrary `state`/`description`/`target_url`/`context` `Status` records onto any `Commit` row in the entire Shipit instance that happens to share a SHA with a commit they control — including commits belonging to a repository they never had any access to. This directly flips `Commit#deployable?` to `true`, which feeds `Stack#next_commit_to_deploy`, `Stack#trigger_continuous_delivery`, and manual/API deploy checks, enabling an unauthorized deploy of a victim's stack. This is a "payload for one repository mutating another's stack/commit" scenario explicitly called out as Critical, and it is repeatable against arbitrary repositories/stacks tracked by the same Shipit instance as long as SHA collisions (via forking public history) can be produced.

### Likelihood Explanation
Preconditions: the victim's repository/commit must already be present as a `Stack`/`Commit` in the same Shipit instance (typical for any organization using Shipit for CI/CD across multiple repos), and the attacker needs *some* org/repo already configured in Shipit with an associated `webhook_secret` — plausible in any Shipit deployment supporting self-service GitHub App installs, personal forks, or multiple orgs. Producing colliding SHAs is trivial for public repositories (fork ⇒ identical git objects); no cryptographic collision is required. Attacker cost is a single crafted HTTP POST with a correctly-computed HMAC using their own known secret — fully repeatable and scriptable.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the resolved `Repository`/`Stack` for the payload, mirroring the base `Handler#stacks`/`repository_name` helpers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `payload['repository']['full_name'] == commit.stack.github_repo_name` before any status mutation, closing the cross-tenant write.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook for a foreign repository must not flip deployable? on a victim commit with the same sha" do
          victim_commit = shipit_commits(:fifth) # tracked, currently not deployable (no success status)
          refute_predicate victim_commit, :deployable?

          attacker_payload = {
            "sha" => victim_commit.sha,
            "state" => "success",
            "repository" => { "full_name" => "attacker-org/attacker-fork" } # != victim_commit.stack.repository.full_name
          }

          refute_equal victim_commit.stack.github_repo_name,
                       attacker_payload["repository"]["full_name"] # binding stated explicitly, unequal before

          StatusHandler.call(attacker_payload)

          victim_commit.reload
          # FAILS on current code: attacker payload flips deployable? for a repo they never controlled
          refute_predicate victim_commit, :deployable?
        end
      end
    end
  end
end
```
This test constructs a `status` payload whose `repository.full_name` is deliberately different from `victim_commit.stack.repository.full_name`, calls `StatusHandler.call` directly (bypassing controller signature verification per the Mocha-stub pattern already used in `test/controllers/webhooks_controller_test.rb`), and asserts `deployable?` is unaffected. On the current codebase the final assertion fails, proving the cross-repository mutation.
