## Analysis

The bug is real and the code confirms it. Here is the exact trace:

**The overwrite in `consolidateNodes()`:**

```go
for _, clsi := range si.CLStakingInfos {
    if r, ok := nToR[clsi.CLNodeId]; ok {
        // One CLStakingInfo per validator is guaranteed by CLRegistry.
        cmap[r].CLStakingInfo = clsi   // ← unconditional assignment, no accumulation
    }
}
```

The comment "One CLStakingInfo per validator is guaranteed by CLRegistry" means one entry **per NodeId** — not per RewardAddr group. Two distinct NodeIds N1 and N3 can each independently register in CLRegistry, and both can share RewardAddr R1 in AddressBook. The code has no guard against this.

The test suite at line 243–271 explicitly exercises this exact scenario and labels it `"not feasible in real"` — but that is a developer assumption, not an enforced invariant anywhere in the codebase. [1](#0-0)

### Title
CLStakingInfo Silent Overwrite in `consolidateNodes` Causes CL Pool Reward Loss for Multi-NodeId Validators — (`kaiax/staking/staking_info.go`)

### Summary
When two NodeIds sharing the same RewardAddr both register in CLRegistry, `consolidateNodes` silently overwrites the first `CLStakingInfo` with the second. The surviving entry carries only the second pool's amount, causing the first pool to receive zero reward and the consolidated node's total staking power to be understated.

### Finding Description
`consolidateNodes` builds a `cmap[RewardAddr]` entry by accumulating CNStaking amounts from all NodeIds sharing a RewardAddr. For CLStakingInfos it does a plain assignment:

```go
cmap[r].CLStakingInfo = clsi
``` [2](#0-1) 

If N1 and N3 both map to R1 and both appear in `CLStakingInfos`, the loop processes N1 first (sets `CLStakingInfo = {pool1, A_cl1}`), then N3 (sets `CLStakingInfo = {pool2, A_cl2}`), discarding pool1 entirely. The `consolidatedNode` for R1 ends up with `StakingAmount = A1+A3` but `CLStakingInfo.CLStakingAmount = A_cl2` only.

`Split()` then computes the CL share as:

```go
clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))  // A_cl2 only
totalAmount = cnAmountBig + clAmountBig                           // A1+A3+A_cl2
``` [3](#0-2) 

And `assignStakingRewards` uses the same understated total to compute the group's reward share:

```go
cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount  // A_cl2, not A_cl1+A_cl2
``` [4](#0-3) 

Then distributes it:

```go
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount  // pool2 only; pool1 gets nothing
``` [5](#0-4) 

### Impact Explanation
- **pool1** receives zero CL reward every block — its entire `A_cl1` contribution is silently dropped.
- The R1 group's total staking power is understated by `A_cl1`, so it earns less total reward than it should; the deficit is redistributed to other validators.
- This is a durable, per-block reward misdistribution affecting KAIA token flows, meeting the "unauthorized reward distribution" impact gate.

### Likelihood Explanation
The scenario requires a validator operating multiple NodeIds under one RewardAddr (an explicitly supported and documented configuration) where each NodeId independently registers in CLRegistry. Both operations are individually valid and permissionless. The CLRegistry enforces uniqueness per NodeId, not per RewardAddr group, so no on-chain guard prevents this state from arising.

### Recommendation
Replace the unconditional assignment with accumulation. The `consolidatedNode` should hold a slice of `CLStakingInfo` entries (or sum their amounts into a single synthetic entry), and `Split()` should use the combined CL amount:

```go
if existing := cmap[r].CLStakingInfo; existing != nil {
    existing.CLStakingAmount += clsi.CLStakingAmount
    // optionally track multiple CLPoolAddrs for per-pool distribution
} else {
    cmap[r].CLStakingInfo = clsi
}
```

`Split()` and `assignStakingRewards` must then distribute to each pool proportionally.

### Proof of Concept
```
NodeIds          = [N1, N3]
StakingContracts = [S1, S3]
RewardAddrs      = [R1, R1]
StakingAmounts   = [A1=5M, A3=5M]
CLStakingInfos   = [{N1, pool1, A_cl1=3M}, {N3, pool2, A_cl2=2M}]
```

After `consolidateNodes()`:
- `ConsolidatedNodes()[0].CLStakingInfo` = `{N3, pool2, 2M}` (pool1 lost)

In `assignStakingRewards`:
- `cnTotalStakingAmount` = 5M+5M+2M = 12M (should be 15M)
- R1 group gets reward proportional to 12M, not 15M
- `Split()` sends `2M/12M` of that reward to pool2, `0` to pool1

Assert: `ConsolidatedNodes()[0].CLStakingInfo.CLPoolAddr == pool2` ✓ (pool1 silently dropped)
Assert: pool1 allocation = 0 ✓ [6](#0-5)
