## Title
Duplicate members in `r of set` address definitions allow a single signer to satisfy a multi-signature threshold intended to require multiple distinct co-signers - ([File: definition.js])

### Summary
The reported bug class is a loop that sums/counts entries of an attacker-influenceable array without deduplication, so a repeated entry is counted once per occurrence instead of once per distinct value, corrupting a threshold calculation. In `ocore`, the address-definition operator `r of set` performs exactly this kind of unguarded counting over a `set` array of member sub-definitions, and nothing in `validateDefinition` rejects a `set` that lists the same `["sig", {pubkey}]` / `["address", X]` member more than once. When authentifiers are later checked, each position in the `set` is authenticated independently by signing path (`r.0`, `r.1`, …), but a signature over the shared `unit_hash_to_sign` is valid regardless of which path it is attached to. As a consequence, one physical signer whose key/address occupies two or more slots of the `set` can supply the same signature at multiple paths and satisfy a `required` count that the other co-owners of the address believed corresponded to that many *distinct* signers.

### Finding Description
`validateDefinition` in `definition.js` validates the `r of set` operator by checking only structural properties of the `set` array (length ≥ 2, `required` ≤ `set.length`), never checking for duplicate elements: [1](#0-0) 

Contrast this with `checkAttestorList`, used for asset attestor lists, which explicitly rejects duplicates by enforcing a strict sort order (`arrAttestors[i] <= prev` is rejected): [2](#0-1) 

No equivalent anti-duplication check exists for `r of set` members (or for `weighted and` members, which has the same structure).

At authentication time, `validateAuthentifiers`'s `r of set` handler iterates over `args.set` and evaluates each element at a distinct path (`path+'.'+index`), incrementing `count` for every element that authenticates successfully — exactly like the reported `collateral` loop that adds an asset's balance once per array entry instead of once per distinct asset: [3](#0-2) 

The leaf `sig` evaluation (and analogous `hash`) verifies a signature against `objValidationState.unit_hash_to_sign`, which is the same value for every signing path within one unit/authentifier package. If the `set` contains the same `["sig", {pubkey}]` (or `["address", innerAddr]` pointing to the same inner `sig`) twice, the *same* signature bytes are a valid authentifier at both corresponding paths (`r.0` and `r.1`, say), so the signer only needs to duplicate the entry in `assocAuthentifiers` to be counted twice by the `count >= args.required` check.

This exact pattern (one signature reused for multiple author entries via duplicated addresses) is explicitly tested for the *authors-array* case (`signed_message.js` sorts/dedupes authors, and `formula.test.js` has a dedicated regression test "is_valid_signed_package with duplicate addresses" asserting the check returns `false`), showing this project is aware that duplicate address entries can be replayed to satisfy count-based checks: [4](#0-3) [5](#0-4) 

However, the equivalent protection is missing for the `set` member list inside `r of set`/`weighted and` definitions used for real on-chain shared/multisig addresses (as built interactively via `wallet_defined_by_addresses.js`, which itself walks `r of set`/`weighted and` structures without deduplicating members): [6](#0-5) 

### Impact Explanation
A shared/multisig address is a security agreement among co-signers who each contribute independent keys expecting that `required` (e.g., "2 of 3") distinct parties must approve any spend. If the definition author (any of the co-signers proposing/crafting the definition, or a device compromised during collaborative address setup) inserts the same member twice into the `set`, that single signer alone can satisfy `required` using one key and a duplicated authentifier entry, bypassing the multi-party control the other legitimate co-signers believe is enforced. This is a concrete unauthorized-spending/fund-loss vector: honest co-signers deposit funds into what they believe is an N-of-M address, but the definition author can unilaterally spend once the definition is accepted, because the on-chain validation of `r of set` never rejects duplicate members and the authentifier count treats repeated members as independent signers.

### Likelihood Explanation
The `set` array is fully attacker/party-controlled content of an address definition — any unprivileged user can construct such a definition when proposing a shared address, and nothing in `validateDefinition` (structural validation, run by every full node/witness on every unit referencing this address) rejects duplicate `set` entries. The exploit requires only: (1) crafting a definition with a repeated member, (2) getting other parties to accept/fund the resulting address (a normal shared-address workflow), and (3) submitting one signature duplicated across the corresponding authentifier paths. No race condition, no privileged role, and no network-level trust is required — this is purely a validation gap in `definition.js`, reachable by any ordinary unit/address author.

### Recommendation
In `validateDefinition`'s `r of set` (and `weighted and`) handling in `definition.js`, reject `set` arrays containing duplicate/equivalent member sub-definitions (e.g., by comparing the hash of each serialized member, similar to how `checkAttestorList` enforces strict ordering/uniqueness for attestor lists). At minimum, disallow structurally identical leaves (`sig` with the same `pubkey`, `address` pointing to the same inner address, `hash` with the same hash) from appearing more than once within the same `set`.

### Proof of Concept
1. Alice and Bob agree to create a 2-of-3 shared address using `r of set`, e.g.
   `["r of set", {required: 2, set: [["sig",{pubkey:A}], ["sig",{pubkey:B}], ["sig",{pubkey:A}]]}]`
   where the third `set` element is a duplicate of the first (Alice's key placed twice). `validateDefinition` accepts this definition without error because it only checks `set.length >= 2` and `required <= set.length` (`definition.js:147-159`).
2. Bob and other observers, inspecting the definition informally, may not notice the duplicate slot and believe 2 distinct co-signers are required.
3. Alice signs the unit hash once with key `A`, then submits the identical signature value under authentifier paths `r.0` and `r.2` (the two positions occupied by her duplicated key).
4. `validateAuthentifiers`'s `r of set` handler (`definition.js:692-711`) evaluates each `set` element independently; both `r.0` and `r.2` verify successfully against the same signature and the same `unit_hash_to_sign`, giving `count = 2 >= required (2)`.
5. The unit is accepted as validly authorized by "2 of 3," even though only Alice's single key participated — she has unilaterally spent funds that Bob believed required his cooperation.

// Returns a map of signing_path -> address for every ["address", ...] leaf in the definition
function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}
