### Title
`StatusHandler#process` updates commit statuses globally by SHA, letting a status genuinely signed for Attacker's repository flip `blocked?`/`deployable?` for Victim's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike every sibling handler (`PushHandler`, `CheckSuiteHandler`) which first narrows to `stacks` derived from `payload.dig('repository', 'full_name')`. Because two different Shipit-tracked repositories can legitimately share identical git SHAs (shared history via fork/common ancestor), a status webhook that is validly signed for Attacker's own repository will still update `Commit` rows belonging to Victim's stack whenever the SHA collides, letting Attacker un-block a commit that `Commit#blocked?` relies on for Victim's continuous delivery decision.

### Finding Description
The binding the system is supposed to enforce is: `commit.statuses` mutated by webhook X == a status that GitHub genuinely reported for **that commit's owning repository** (`commit.stack.github_repo_name`). In code, `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-38` only proves the payload was sent by GitHub for `repository_owner` = `payload.dig('repository','owner','login')` — i.e. it authenticates *which repository the payload claims to be about*, not that the referenced SHA is unique to that repository.

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global, cross-repository/cross-stack lookup on the `commits` table. Compare to `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-16`), both of which scope through `stacks` (built from the verified `repository_name`) before touching any `Commit`. `StatusHandler` defines no such scoping and never calls `stacks` at all.

`Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) trusts that any status attached to a commit row in `stack.commits` was reported for that stack's repository:
```ruby
stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
```
Since `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!` (`app/models/shipit/commit.rb:165-169`, `366-386`) mutates whichever `Commit` record matched by SHA regardless of which repository the webhook was "about," Attacker can:
1. Register/own a repository in Shipit that shares git history with Victim's repository (fork, or any repo that shares an ancestor commit — the shared commits have identical, real SHAs).
2. Identify a SHA that exists both in Attacker's repo and in Victim's stack's undeployed commit range, where that Victim commit is currently reporting a `blocking_statuses` context (e.g. `ci/danger`) that keeps a later commit `blocked?`.
3. Send (or have GitHub send, by pushing/updating status on their own repo) a `status` webhook naming Attacker's repository with that SHA and a non-blocking `state`.
4. `verify_signature` succeeds (it is a real, GitHub-signed event for Attacker's own org/repo).
5. `StatusHandler#process` finds the `Commit` row(s) with that SHA — including the one belonging to Victim's stack — and rewrites its status via `create_status_from_github!`.
6. `Commit#blocked?` re-evaluates to `false` for the later Victim commit, `deployable?` flips to `true`, and `schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) enqueues `ContinuousDeliveryJob`.

None of the listed guards catch this: `verify_signature` authenticates the *sender's own repository*, not SHA ownership; `drop_unhandled_event`/`ExplicitParameters` only validate the payload shape; there is no `Repository`/`Stack` scoping check anywhere in `StatusHandler`.

### Impact Explanation
A payload that is only ever validated against Attacker's own repository/org mutates a `Commit` and, transitively, a `Stack`'s deployability that belongs to a different tenant (Victim). This directly matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" and can result in "an unauthorized deploy" by enabling `ContinuousDeliveryJob` to run when it should have been blocked. The attack is repeatable against any Victim stack for which Attacker can find/produce a SHA collision (trivial for forks, since the entire pre-fork history is byte-identical and thus SHA-identical), and generalizes across tenants: any two onboarded repositories sharing history are cross-exploitable this way.

### Likelihood Explanation
Preconditions: Victim stack has `blocking_statuses` configured and an undeployed range containing a commit whose status is currently blocking; Attacker owns/controls a Shipit-registered repository that shares at least one commit SHA with Victim's history (a public fork is the simplest and extremely common case). No Shipit session, API token, or GitHub secret is required — Attacker only needs to control the status of a commit in their own repository (trivially done via their own CI or a direct GitHub API/webhook re-delivery for their own repo). This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the requesting repository/stack, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
so a status is only ever applied to commits belonging to the stack(s) whose repository the (signature-verified) payload actually names.

### Proof of Concept
Minitest plan (e.g. `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `victim_stack` with `Repository` `full_name: "victim/repo"` and `blocking_statuses: ['ci/danger']`; create `attacker_stack` with `Repository` `full_name: "attacker/repo"`.
2. Create a shared SHA `sha = "c" * 40` and insert two `Commit` rows with that SHA — one on `victim_stack` (`blocking_commit`), one on `attacker_stack`.
3. Build the undeployed chain on `victim_stack`: `last_deployed_commit` → `blocking_commit` (gets a status with context `ci/danger`, state `failure`, so `blocking_commit.blocking?` is true) → `later_commit` (has passing status).
4. Assert baseline: `later_commit.blocked?` == `true`, `later_commit.deployable?` == `false` (binding LHS: commit state in Victim's range == statuses reported for `victim/repo`).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call('repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } }, 'sha' => sha, 'state' => 'success', 'context' => 'ci/danger')` — i.e. a payload that only ever names `attacker/repo`.
6. Assert: `blocking_commit.reload.blocking?` == `false` even though no status was ever reported for `victim/repo` (binding RHS now diverges from LHS — violated).

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
