### Title
Cross-Repository Commit Status Forgery via Organization/Repository Binding Mismatch in Webhook Processing - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`) [1](#0-0) [2](#0-1) , but the handler that actually mutates state (`StatusHandler`) resolves which `Commit` record to write to purely by `sha`, with no scoping to the organization or repository that authenticated the request [3](#0-2) . In a multi-organization Shipit deployment (`secrets.github` keyed by organization, each with its own `webhook_secret`, as documented and exercised in `test/dummy/config/secrets_double_github_app.yml`) [4](#0-3) , an actor who legitimately controls the GitHub App/webhook secret for their own onboarded organization ("OrgA") can forge a `status` webhook whose `repository.owner.login` is `OrgA` (so it authenticates against OrgA's secret) while embedding an arbitrary commit `sha` that actually belongs to a completely unrelated stack/repository ("OrgB"). Because `StatusHandler#process` does `Commit.where(sha: params.sha)` with no repository filter, the forged status is written onto OrgB's commit.

### Finding Description
The binding that should hold is: **the organization whose secret authenticated the webhook == the repository/stack the webhook is allowed to write to**. This binding is broken because:

1. Signature verification only proves the payload was signed with the secret of whatever organization is named in `repository.owner.login`/`organization.login` — a JSON field fully controlled by the sender (it just has to be consistent with whichever secret they use to sign): [5](#0-4) 
2. `Handler#repository_name`/`Handler#stacks` (used by handlers like `PushHandler`) at least scope to `payload.dig('repository', 'full_name')` [6](#0-5) , but `StatusHandler` bypasses this entirely and looks up commits globally: [3](#0-2) 
3. Consequently, nothing ties the authenticated organization to the repository that owns the commit being updated. Anyone who owns a valid webhook secret for *any* organization configured in the multi-org `secrets.github` map can create/overwrite a `Status` (state, description, target_url, context) on any commit SHA in the entire Shipit database, regardless of which stack/repository that commit belongs to.

This is the direct code analog to the reported issue: a "setter" (`create_status_from_github!` driven by an unauthenticated-for-that-repo payload) lacks a bounds check — here the missing bound is "the target commit must belong to a repository owned by the organization that signed the request" instead of "percentage ≤ 100%."

### Impact Explanation
Commit statuses gate both deploy safety and the merge queue: `DeploySpec#required_statuses`/`blocking_statuses` and merge-queue validation rely on `Status` records associated with a commit [7](#0-6) . A forged "success" status injected onto a victim commit in another organization's stack can cause that commit to be treated as CI-green, letting it pass through the merge queue or `required_statuses` checks it never actually satisfied — an unauthorized deploy or merge. This matches the report's "Critical — unauthorized deploy, rollback or merge" impact bucket.

### Likelihood Explanation
Low-to-moderate: it requires the attacker to be a legitimate (but otherwise unprivileged w.r.t. the victim organization) tenant of a multi-org Shipit install — i.e., they administer their own GitHub App/organization entry in Shipit's `secrets.github`, and thus legitimately know their own `webhook_secret`. No access to the victim's repository, GitHub App, or Shipit session is required; they only need to know or guess a target commit SHA (trivial for public repos). This aligns with the report's likelihood framing of a plausible-but-narrow misconfiguration/trust scenario, but here it's exploitable by design rather than requiring owner error.

### Recommendation
Scope every webhook write to the organization/repository that was actually authenticated, not to attacker-supplied identifiers reused for routing convenience:
- In `StatusHandler#process`, restrict the `Commit` lookup to commits whose `stack.repository.full_name` matches `payload.dig('repository', 'full_name')`, and additionally verify that repository's owner matches the organization used in `verify_signature`.
- More generally, in `WebhooksController`, after verifying the signature, assert that `repository_owner` (the value used to pick the signing secret) equals the owner embedded in `repository.full_name` for every event that carries a `repository` object, rejecting the request otherwise.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing at least `OrgA` (attacker-controlled, secret `SECRET_A`) and `OrgB` (victim, secret `SECRET_B`), per the multi-org schema in `lib/shipit.rb#github_app_config` and `docs/setup.md`.
2. Victim stack under `OrgB/victim-repo` has a real commit with SHA `abc123` currently lacking a passing CI status (or with a `pending`/`failed` status) required by `deploy_spec.required_statuses`.
3. Attacker crafts a `status` webhook body:
   ```json
   {
     "sha": "abc123",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-owned-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(SECRET_A, body)` — a signature they can legitimately produce because they own OrgA's app.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully [1](#0-0) .
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which executes `Commit.where(sha: 'abc123').each { |commit| commit.create_status_from_github!(params) }` [3](#0-2)  — writing a forged "success" status onto `OrgB`'s commit despite the request only ever having been authenticated for `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
