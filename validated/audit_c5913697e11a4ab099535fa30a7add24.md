### Title
SecretarySalaryPaymaster reuses FellowshipSalaryInteriorLocation, causing both salary instances to share one AssetHub sovereign account and bypass independent budget isolation - ([File: system-parachains/collectives/collectives-polkadot/src/secretary/mod.rs])

### Summary
`SecretarySalaryPaymaster` (a `PayOverXcm` instance backing `pallet_salary::Config<SecretarySalaryInstance>`) is configured with `crate::fellowship::FellowshipSalaryInteriorLocation` as its interior location rather than its own `PalletInstance(<SecretarySalary as PalletInfoAccess>::index())`. Both `SecretarySalaryPaymaster` and `FellowshipSalaryPaymaster` therefore resolve, via `AliasesIntoAccountId32`/`LocationToAccountId` on AssetHub, to the exact same sovereign-derived AccountId keyed off `PalletInstance(FELLOWSHIP_SALARY_PALLET_INDEX)` (index 64), even though the runtime independently tracks separate `SecretarySalaryBudget` and `FellowshipSalaryBudget` values.

### Finding Description
`FellowshipSalaryInteriorLocation` is defined once in `system-parachains/collectives/collectives-polkadot/src/fellowship/mod.rs:286-288` as `PalletInstance(<crate::FellowshipSalary as PalletInfoAccess>::index() as u8)`, and used both by `FellowshipSalaryPaymaster` (`fellowship/mod.rs:295-304`) and, erroneously, by `SecretarySalaryPaymaster` (`secretary/mod.rs:95-104`). [1](#0-0) [2](#0-1) 

Both `pallet_salary::Config<FellowshipSalaryInstance>` and `pallet_salary::Config<SecretarySalaryInstance>` independently define their own `Budget` (`FellowshipSalaryBudget` and `SecretarySalaryBudget` respectively), meant to be enforced per-instance by `pallet_salary`'s internal accounting (each instance tracks its own `Status`/`Claimant` storage and enforces `Budget` against `TotalRegistrations`/period totals within its own instance). [3](#0-2) [4](#0-3) 

However, that per-instance budget check only limits how much each instance is willing to *register/promise* to pay; the actual payment execution goes through `PayOverXcm::pay`, which builds a withdraw-and-teleport/reserve-transfer XCM from the sovereign account derived from the paymaster's `InteriorLocation`. Because `SecretarySalaryPaymaster` uses `FellowshipSalaryInteriorLocation`, its XCM withdraws from the identical AssetHub sovereign account that `FellowshipSalaryPaymaster` withdraws from — confirmed explicitly by the existing test comment: "SecretarySalary uses FellowshipSalaryPaymaster, so the pay_from account is derived from the fellowship salary pallet's interior location (pallet index 64)." [5](#0-4) 

Exploit/reachable path: a Secretary Collective member (rank ≥1, an unprivileged signed account added via governance but who then acts unilaterally) calls `pallet_salary::Pallet::<Runtime, SecretarySalaryInstance>::register` and then `payout` — both are ordinary signed extrinsics gated only by `Members` (i.e., being an existing collective member, not requiring any special privilege beyond that membership, and not requiring proxy/root/governance approval per payout). This is confirmed reachable since `Members = pallet_ranked_collective::Pallet<Runtime, SecretaryCollectiveInstance>` at `secretary/mod.rs:121`, and analogous `induct`/`register`/`payout`/`payout_other` weight functions exist for `SecretarySalaryInstance` confirming these extrinsics are live and benchmarked. [6](#0-5) 

No barrier, filter, or fee-waiver check in `xcm_config.rs` distinguishes between the two pay-from origins, since `WaivedLocations` treats `FellowshipSalaryLocation` and `SecretarySalaryLocation` as separate `Equals<>` matches on outbound-fee waiving only — it does not detect or prevent the underlying interior-location aliasing that makes their sovereign accounts identical. [7](#0-6) 

### Impact Explanation
Whoever funds AssetHub's sovereign account for `PalletInstance(64)` (the Fellowship Salary pallet index) intending it to cover only `FellowshipSalaryBudget`, will find that Secretary Collective members can drain that same account via `SecretarySalaryPaymaster`, since both paymasters share the same pay-from sovereign account. This breaks the invariant that each salary instance draws only from its own configured/funded interior location: the combined amount withdrawable by both `FellowshipSalary` and `SecretarySalary` claimants in a period can exceed what was earmarked as `FellowshipSalaryBudget` alone (up to `FellowshipSalaryBudget + SecretarySalaryBudget`, limited only by whatever balance actually sits in the shared account), and conversely Fellows can find their intended salary funds have been consumed by Secretary members, or vice versa — a cross-collective budget/fund misappropriation.

### Likelihood Explanation
High feasibility and fully reachable with no privileged action required beyond ordinary collective membership (which is a normal, expected state for both collectives to have active members). No governance action, no proxy bypass, and no origin-forgery is needed — it is a static runtime misconfiguration that manifests every single salary period as soon as both collectives have registered claimants and the shared AssetHub account holds funds.

### Recommendation
Define a dedicated `SecretarySalaryInteriorLocation` parameter in `secretary/mod.rs` analogous to `FellowshipSalaryInteriorLocation`, e.g. `pub SecretarySalaryInteriorLocation: InteriorLocation = PalletInstance(<crate::SecretarySalary as PalletInfoAccess>::index() as u8).into();`, and use it as the first type parameter of `SecretarySalaryPaymaster` instead of `crate::fellowship::FellowshipSalaryInteriorLocation`. This matches the existing pattern already used correctly for `AmbassadorSalaryLocation`/`AmbassadorSalaryPaymaster`. [8](#0-7) 

### Proof of Concept
xcm-emulator integration test (extending the existing `pay_salary_secretary`/`pay_salary_fellowship` tests in `integration-tests/emulated/tests/collectives/collectives-polkadot/src/tests/collectives_salary.rs`):
1. On `AssetHubPolkadot`, compute `pay_from` as `LocationToAccountId::convert_location(&(Parent, Parachain(CollectivesPolkadot::para_id()), PalletInstance(FELLOWSHIP_SALARY_PALLET_ID)).into())`.
2. Mint into `pay_from` exactly `FellowshipSalaryBudget` worth of the configured asset (no extra buffer).
3. On `CollectivesPolkadot`, as a Fellow, call `FellowshipSalary::induct`/`register`/`payout` claiming the full `FellowshipSalaryBudget` for one member, and assert successful XCM dispatch and successful `Assets::Transferred` on AssetHub, fully draining `pay_from`.
4. In the same salary period, as a Secretary Collective member, call `SecretarySalary::induct`/`register`/`payout` for a nonzero `SecretarySalaryBudget` amount.
5. Assert that the second `payout` either fails (`InsufficientBalance`/XCM failure) due to `pay_from` being already drained, or, if funded separately, assert total withdrawn from `pay_from` across both instances exceeds `FellowshipSalaryBudget` alone — proving the shared-account budget bypass. Expected correct behavior (post-fix) is that `SecretarySalary` draws from a distinct sovereign account so both payouts succeed independently up to their own budgets.
