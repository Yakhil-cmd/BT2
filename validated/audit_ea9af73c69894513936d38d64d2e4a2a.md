### Title
Cross-repository/cross-organization Commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target `Commit` rows purely by SHA (`Commit.where(sha: params.sha)`) with no filtering by `repository_name`/`repository_owner`, unlike other handlers (e.g. `push_handler.rb`) which scope through `Handler#stacks` (which is derived from `repository_name`). A validly-signed webhook for one repository/organization can therefore mutate `Commit` rows belonging to a completely different repository, stack, or organization whenever the SHA matches, including via shared git history between a fork and its upstream.

### Finding Description
Binding claimed vs. actual: `verify_signature` binds `github_app_for(repository_owner(payload))` to the payload's *own declared* `repository.owner.login` [1](#0-0) [2](#0-1) . This means the exact cross-organization signature-substitution described in the prompt (org A's secret verifying a payload whose declared owner is org B) is not possible: the app looked up to verify the signature is selected from the payload's own `repository.owner.login`/`organization.login`, so verification is self-consistent with the declared owner, not with some unrelated org.

However, a real divergence exists one layer down. `StatusHandler#process` never consults `repository_name`/`stacks` at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Contrast this with the base `Handler#stacks`/`repository_name` helpers that other handlers use to scope work to the repository named in the payload [4](#0-3) . Because `Commit.sha` is not guaranteed unique per repository (git SHAs are content-addressed and identical commits — e.g. shared history between a fork and its upstream, or identical trees/messages/timestamps — collide across repositories), any organization/repository that can legitimately deliver a real, correctly-signed GitHub `status` event for a SHA it owns will cause Shipit to update **every** `Commit` row in the database sharing that SHA, regardless of which `Repository`/`Stack`/organization it belongs to.

Attacker flow: attacker administers (or is a collaborator/CI integration on) a repository under org A with a legitimate Shipit GitHub App installation. Org A's repo shares history with victim org B's repo (fork relationship, or by construction attacker crafts an identical commit — same tree, parent, author, message, timestamps — which is feasible without a full SHA-1 collision when history is shared or reproduced). Attacker triggers a `status` event on their own org A commit (e.g., via the GitHub Statuses API on their own repo, or by having their own CI post a status) — GitHub signs and delivers this with org A's real `webhook_secret`. `verify_signature` succeeds legitimately for org A. `StatusHandler#process` then updates `Commit` rows for that SHA across all stacks, including org B's, via `create_status_from_github!`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) validate the payload shape and the signing organization's authenticity, but do not validate that the mutated `Commit` actually belongs to the repository/organization named in (or authenticated by) the webhook payload.

### Impact Explanation
A forged/legitimately-owned status update from an attacker-controlled repository can flip the recorded GitHub status (`state`, `context`, `target_url`, `description`) of a commit belonging to an unrelated stack/organization. If a victim stack's merge/deploy gating relies on commit status checks (`Shipit::CommitChecks`, PR mergeability), this enables an attacker to force a matching commit into a "green"/passing state it never actually validated in the victim's CI pipeline, which can facilitate an unauthorized merge or deploy decision on the victim's stack — matching the "payload for one repository mutating another's stack/commit" Critical category. The blast radius is any tenant/organization sharing a SHA with the attacker's repository, and the technique is repeatable per matching SHA.

### Likelihood Explanation
Requires: (1) the attacker controls or can trigger status webhooks for a repository with its own legitimate Shipit GitHub App installation (an unprivileged action for their own repo/fork), and (2) a Commit SHA shared with the victim's stack (trivially true for forks with common history, or constructible without secrets for crafted-but-identical commits). No Shipit secrets, sessions, or API tokens are needed — only the attacker's own, legitimately signed webhook traffic. This is feasible and repeatable, though bounded by needing SHA overlap with the victim (fork-based overlap is common and requires no cryptographic collision).

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring other handlers: resolve `stacks`/`Repository.from_github_repo_name(repository_name)` first, and restrict the `Commit.where(sha: ...)` lookup to commits belonging to stacks under that repository (e.g., `commit.stack.repository == repository_from_payload`) before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status event scoped to org A repo must not mutate commits belonging to org B's stack" do
  org_a_repo = shipit_repositories(:orgA_repo) # owner: "orgA"
  org_b_stack = shipit_stacks(:orgB_stack)     # repository owner: "orgB"
  shared_sha = "a" * 40

  # Commit exists under both repos' stacks with the same sha (fork/shared history)
  org_a_commit = org_a_repo.stacks.first.commits.create!(sha: shared_sha, ...)
  org_b_commit = org_b_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => org_a_repo.full_name, "owner" => { "login" => "orgA" } },
  }

  # Signature verified with orgA's own real webhook_secret (legitimate delivery for org A)
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal "success", org_a_commit.reload.state   # expected mutation
  assert_not_equal "success", org_b_commit.reload.state # BUG: currently also mutated
end
```
Assert the equality both sides: `repository_owning(mutated_commit.stack) == payload["repository"]["owner"]["login"]` must hold for every mutated `Commit`; the current implementation violates this for `org_b_commit`.
