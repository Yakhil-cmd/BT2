### Title
Webhook signature scope is selected from the unverified `repository.owner.login`/`organization.login` field, allowing a `status` event signed with one organization's `webhook_secret` to write commit statuses onto any stack instance-wide - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify an inbound webhook against using `repository_owner`, a value read directly out of the still‑unverified JSON body. Once the signature is accepted, the actual event processing (`StatusHandler`) does not re‑check that the signing organization has any relationship with the data being mutated: `Commit.where(sha: params.sha)` is a completely global, cross-repository/cross-stack lookup. This breaks the equality that should hold: `organization whose secret authenticated the request == organization/repository whose data is mutated`.

### Finding Description
The webhook signature verification flow is: [1](#0-0) [2](#0-1) 

`repository_owner` is taken straight from the attacker-controlled request body (`params.dig('repository','owner','login')` or `organization.login`) *before* any signature check happens. `Shipit.github(organization: repository_owner)` then picks the `webhook_secret` configured for that organization (multi-tenant configuration of several orgs, each with their own `webhook_secret`, is a documented, supported setup — see `config/secrets.development.shopify.yml`).

Because the HMAC is only checked against whatever `webhook_secret` corresponds to the attacker-supplied `repository_owner` field, an attacker who is a legitimate/authorized user of *one* organization onboarded to this Shipit instance (and therefore knows/controls that organization's `webhook_secret`, e.g. as an org admin who configured the GitHub App) can compute a valid signature for a payload of **any content**, as long as `repository.owner.login` (or `organization.login`) equals their own organization. Nothing forces the rest of the payload (the data actually consumed by the event handler) to belong to that same organization/repository.

The `status` event handler amplifies this into a cross-tenant write: [3](#0-2) 

`StatusHandler#process` looks up `Commit.where(sha: params.sha)` with **no repository or stack scoping at all** — unlike other handlers (`PushHandler`, `CheckSuiteHandler`) which resolve `stacks` via `Repository.from_github_repo_name(...)` in the shared base class: [4](#0-3) 

So the attacker can craft a JSON body where `repository.owner.login` is their own org (to pass signature verification with a secret they know) while `sha` is the SHA of a commit belonging to an entirely unrelated stack/repository/organization hosted on the same Shipit instance. `create_status_from_github!` then persists an attacker-chosen `state`/`context`/`description` onto that victim commit: [5](#0-4) [6](#0-5) 

The equality broken is: **organization that authenticated the webhook (`repository_owner` used to pick the HMAC secret) ≠ repository/stack whose commit status is written (`sha` looked up with zero scoping in `StatusHandler`)**.

### Impact Explanation
CI status directly gates automated behavior in Shipit: `Status#enable_ci_on_stack`/`schedule_continuous_delivery` and the "required/blocking" status logic determine whether a commit is `deployable?` and whether continuous delivery triggers a deploy: [7](#0-6) 

By forging a `success` status for a required CI context on a victim stack's pending commit (whose SHA the attacker can learn from a public repo, PR, or the Shipit UI), an attacker who controls a completely unrelated organization's webhook secret can flip a victim commit into a deployable state and, on stacks with `continuous_deployment: true`, trigger an **unauthorized deploy** of that victim stack. This satisfies the "unauthorized deploy" high/critical impact criterion without needing any Shipit session, `ApiClient` token, or the victim organization's own webhook secret.

### Likelihood Explanation
Any legitimate operator of one organization configured on a shared/multi-tenant Shipit installation (a supported configuration, per `config/secrets.development.shopify.yml`) already knows or can retrieve their own org's `webhook_secret`, and can freely craft raw HTTP POSTs to `/webhooks` (this endpoint has `skip_before_action :verify_authenticity_token` and is unauthenticated aside from the HMAC check). No repository write access, GitHub App private key, or victim credentials are required — only knowledge of a target commit's SHA and required CI context, both of which are commonly public.

### Recommendation
Bind the verified signature to the data being processed:
- After verifying the signature for `repository_owner`, re-derive and cross-check that `repository_owner` equals the owner embedded in `params['repository']['full_name']` (or reject payloads with inconsistent owner fields) before dispatching to handlers.
- Scope `StatusHandler#process` (and any other handler reading global tables) to the repository/stack derived from `payload['repository']['full_name']`, mirroring `Handler#stacks`, instead of querying `Commit` unscoped by `sha` alone.

### Proof of Concept
1. Attacker is an admin of `attacker-org`, one of several organizations configured in this shared Shipit instance, and knows `attacker-org`'s `webhook_secret` (`Shipit.github(organization: 'attacker-org')`).
2. Attacker identifies a victim stack's pending commit SHA `deadbeef` belonging to `victim-org/victim-repo`, which requires CI context `ci/circleci` to be `success` before deploy.
3. Attacker builds payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/circleci"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker_org_webhook_secret, payload)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner == "attacker-org"`, fetches `attacker-org`'s secret, and the signature verifies successfully (per `verify_webhook_signature` in `lib/shipit/github_app.rb`).
6. `StatusHandler#process` executes `Commit.where(sha: "deadbeef")`, finds the victim's commit (no ownership check), and calls `create_status_from_github!`, writing a `success` status for `ci/circleci` onto the victim stack's commit — potentially unlocking or triggering an unauthorized deploy on `victim-org/victim-repo`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
