## Title
Webhook tenant identity used for signature verification (`repository.owner.login`) is not bound to the tenant identity used for the write (`repository.full_name`), letting one org's signed webhook mutate another org's `PullRequest#labels` - (File: `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret using `params.dig('repository','owner','login')`, while `LabelCapturingHandler#repository` (and every other handler built on `Handler#stacks`/`#repository_name`) resolves the target `Repository` from the sibling field `params.repository.full_name`. Because these are two independent, attacker-controlled fields inside the same JSON body, a legitimate multi-tenant Shipit customer who knows their own `webhook_secret` can sign a payload whose `repository.owner.login` is their own org but whose `repository.full_name` points at a different tenant's repository, causing `capture_labels` to `update!` that other tenant's `PullRequest#labels`.

### Finding Description
The binding the code implicitly assumes is:

`repository_owner_authenticated_by_signature (params.dig('repository','owner','login'))` == `owner segment of repository.full_name used by the handler`

This is never asserted anywhere.

- `WebhooksController#verify_signature` picks the GitHub App/secret with `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository', 'owner', 'login')`, and verifies the HMAC over the raw body with that org's `webhook_secret`. [1](#0-0) [2](#0-1) 
- Shipit natively supports multiple GitHub App configurations (one per organization), each with its own `webhook_secret`, selected purely by the `organization` key. [3](#0-2) 
- `LabelCapturingHandler#repository` (and `Handler#stacks`/`#repository_name` used by other handlers) resolves the actual `Repository` row from `params.repository.full_name`, a completely separate JSON field from `repository.owner.login`, with no cross-check against `repository_owner`. [4](#0-3) [5](#0-4) 
- `Repository.from_github_repo_name` only downcases and splits the string; it doesn't confirm any relationship to the request's authenticated org. [6](#0-5) 
- `capture_labels` then writes directly into the resolved stack's `PullRequest`, using attacker-supplied label names, with the environment/PR chosen by attacker-controlled `params.number`/`params.pull_request`. [7](#0-6) [8](#0-7) [9](#0-8) 

**Exploit flow (multi-org Shipit deployment, e.g. `test/dummy/config/secrets_double_github_app.yml`-style config):**
1. Attacker controls org `OrgOne`, which is legitimately configured in Shipit with its own `webhook_secret`, so the attacker knows it (they set it when installing the GitHub App). `OrgTwo` is a victim tenant with its own repository/stacks in the same Shipit instance.
2. Attacker crafts a raw JSON body for a `pull_request` event: `repository.owner.login = "OrgOne"`, but `repository.full_name = "OrgTwo/victim-repo"`. `number` is set to a PR number that matches an existing `ReviewStack` (`environment = "pr#{number}"`) for `OrgTwo/victim-repo` (PR numbers/branches are typically observable on a public repo).
3. Attacker computes `sha1=HMAC(webhook_secret_of_OrgOne, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: pull_request` and that signature.
4. `verify_signature` calls `Shipit.github(organization: "OrgOne")`, uses OrgOne's real secret, and the signature matches — the request is accepted.
5. `LabelCapturingHandler` runs, resolves `Repository.from_github_repo_name("OrgTwo/victim-repo")` → the real `OrgTwo` `Repository`, finds the matching `ReviewStack`/`PullRequest`, and calls `pull_request.update!(labels: attacker_supplied_labels)`.
6. Because label state drives `provisioning_behavior_allow_with_label?`/`prevent_with_label?` used by sibling handlers (e.g. `UnlabeledHandler`) to archive/unarchive/(de)provision review stacks, this cross-tenant label write can cascade into unauthorized deprovisioning/archival actions on `OrgTwo`'s stack. [10](#0-9) 

None of the existing guards prevent this: `verify_signature` only authenticates that the sender knows *some* org's secret matching the top-level `owner.login`, it never validates that this org matches the org embedded in `full_name`; the `ExplicitParameters` schema only requires `full_name` to be a `String` with no relationship constraint to `owner.login`; `Repository` model validations only constrain format/casing of `owner`/`name`, not tenancy binding to the request.

### Impact Explanation
An attacker who is a legitimate tenant admin for one org (holding only their own `webhook_secret`) can cause writes (`PullRequest#labels`) to a `Repository`/`Stack` belonging to an entirely different, unrelated tenant, without ever possessing that tenant's secret. This is a cross-tenant write via a payload targeting one repository mutating another repository's stack — matching the "Critical" bucket ("a payload for one repository mutating another's stack, commit, task or team"). Since label changes drive automated `provisioning_behavior` archive/unarchive/deprovision actions on review stacks, this can also cause unauthorized stack state changes on the victim tenant. The attack is repeatable against any repository/tenant configured in the same multi-org Shipit instance, for any PR number the attacker can guess or observe, and requires no privileges beyond running a legitimate (but malicious) org's own webhook.

### Likelihood Explanation
This requires Shipit to be configured for multiple GitHub organizations (the documented "Using Multiple Github Applications" mode) — each with independently configured `webhook_secret`s. In that mode, the attacker needs only to be the legitimate operator of one of the configured orgs (any customer/tenant of a multi-tenant Shipit instance), know their own secret (which they configured), and know/guess a target PR number for the victim repository (often publicly observable). No GitHub session, Shipit session, or victim secrets are required — cost is a single crafted HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses.

### Recommendation
Bind the two identities: after resolving `Repository.from_github_repo_name(params.repository.full_name)` (or before selecting the webhook_secret), assert that the resolved repository's `owner` equals the `repository_owner` used in `verify_signature` (i.e., `params.dig('repository','owner','login')` downcased). Reject/`head(422)` the request if they diverge. This check should live centrally in `WebhooksController`/`Handler` base class so all handlers (not just `LabelCapturingHandler`) are protected.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb`, using a two-org secrets fixture like `test/dummy/config/secrets_double_github_app.yml`):

```ruby
test "a payload signed for OrgOne but full_name pointing at OrgTwo's repo mutates OrgTwo's pull request" do
  # Setup: OrgOne and OrgTwo are both configured orgs with distinct webhook_secret values
  org_one_secret = "org-one-secret"
  org_two_secret = "org-two-secret"
  Shipit.stubs(:github_app_config).with('orgone').returns(webhook_secret: org_one_secret)
  Shipit.stubs(:github_app_config).with('orgtwo').returns(webhook_secret: org_two_secret)

  victim_repo   = shipit_repositories(:shipit) # owner: "orgtwo" (fixture adjusted)
  victim_stack  = create_review_stack_for(victim_repo, number: 42) # environment "pr42"

  payload = payload_parsed(:pull_request_labeled)
  payload["repository"]["owner"]["login"] = "OrgOne"          # authenticates as OrgOne
  payload["repository"]["full_name"]      = "OrgTwo/#{victim_repo.name}" # but targets OrgTwo's repo
  payload["number"] = 42
  payload["pull_request"]["labels"] = [{ "name" => "attacker-label" }]

  body = payload.to_json
  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', org_one_secret, body)}"

  request.headers['X-Github-Event']   = 'pull_request'
  request.headers['X-Hub-Signature']  = signature

  # binding under test: repository_owner_authenticated_by_signature == owner used by handler
  assert_equal "orgone", payload.dig("repository", "owner", "login").downcase
  assert_equal "orgtwo", Shipit::Repository.from_github_repo_name(payload["repository"]["full_name"]).owner

  assert_no_changes -> { victim_stack.pull_request.reload.labels } do
    post :create, body: body, as: :json
  end
  # Without the fix, this assertion fails: victim_stack.pull_request.labels becomes ["attacker-label"]
end
```

This demonstrates the signature passes (`assert_response :ok`) while `victim_stack`'s `PullRequest#labels`, belonging to `OrgTwo`, changes as a result of a request authenticated only for `OrgOne`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
