### Title
Reflog fallback's fixed 5-entry / 120s scan window lets a decoy-commit flood cause a quiet malicious commit to permanently escape commit-review - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`handle_commit_review_posttooluse`'s reflog-based fallback (used when `git commit` stdout is suppressed, e.g. via `-q`/pipe/redirect) relies on `_git_reflog_recent_commits` in `gitutil.py`, which only scans the **last 5** HEAD reflog entries. If an attacker issues a quiet `git commit` and then quickly performs ≥4 additional decoy commits (e.g. `git commit --allow-empty`) before the asynchronous PostToolUse hook actually executes the reflog scan, the quiet commit's reflog entry is pushed outside the scanned window and is never returned as a "fresh" SHA, so it is never diffed/reviewed, while the benign decoy commits are.

### Finding Description
`handle_commit_review_posttooluse` determines `commit_succeeded` from the visible `[branch sha]`/diffstat lines in Bash stdout [1](#0-0) . When stdout is suppressed (`-q`, pipe, redirect) this check fails, and the hook falls back to `_git_reflog_recent_commits(_root)` [2](#0-1) .

`_git_reflog_recent_commits` hard-codes `max_n=5` and only examines `git log -g -n 5` (the last 5 reflog entries), returning as "fresh" only commit-type entries within that window (age-gated except index 0) [3](#0-2) . Later in the handler, `shas = _reflog_shas` and *all* SHAs returned by the scan are reviewed via `git show -p <sha>` for each entry [4](#0-3) [5](#0-4) .

Because `PostToolUse` hooks run as `asyncRewake` (fired in the background while Claude/the agent continues), there is a real window between the quiet commit's Bash tool call returning and this Python hook actually invoking the reflog scan. If, within that window, ≥4 additional commits are made (pushing the quiet commit's reflog entry to position 5 or later), `_git_reflog_recent_commits` simply never sees or counts that entry — it falls entirely outside both the "fresh" and "stale" buckets (`skip_21_sub=4`, "no commit-action entries — genuine fail"). The quiet, attacker-authored commit is thus never diffed or reviewed, while decoy commits (which are themselves visible in stdout, or caught by the reflog scan for their own PostToolUse invocation) get reviewed normally. This violates the intended review-target binding invariant documented in the function's own comments, which only account for a *single* racing extra commit ("HEAD raced ahead... both commits appear in the scan and both get reviewed — correct"), not an arbitrarily sized decoy flood that exceeds `max_n`.

Existing protections do not stop this: the SHA-dedup (`_load_reviewed_shas`/`_already`) only prevents double-review, not under-review; the age gate (120s) is irrelevant here since the bypass is purely about entry-count truncation, not staleness. I was unable to verify from the code I inspected whether a separate `push-sweep` handler (which appears to use `_git_rev_list_range` over the full push range rather than the reflog) would independently catch the missed commit on a later `git push` — I found references to `PUSH_SWEEP_ENABLED`/`_detect_prev_upstream` but did not fully trace that code path before running out of investigation budget, so it is uncertain whether push-sweep provides a full backstop for this bypass or only for commits still within `_REVIEWED_SHAS_CAP`/reflog range at push time.

### Impact Explanation
An attacker (or prompt-injected agent) with only ordinary repository/command execution capability (no admin, no leaked keys) can make a security-relevant quiet commit invisible to Claude Code's automated security-guidance commit review, while decoy commits absorb the review budget and pass. This is a genuine gate/enforcement bypass on the commit-review security control (LLM vulnerability scan + exit-code-2 model rewake), matching a "hook/security control bypass" class of impact: the model is never made aware of and never asked to remediate a malicious commit that the plugin exists specifically to catch.

### Likelihood Explanation
Preconditions: `ENABLE_COMMIT_REVIEW` on (default), attacker/agent controls the sequence and timing of `git commit` invocations in the working repo, quiet commit uses `-q`/pipe/redirect to suppress stdout, and at least 4 further commits land in the same repo before the asynchronous hook's reflog read executes. Because PostToolUse fires asynchronously and LLM-review latency (seconds) is nontrivial, an automated or scripted decoy-commit burst (`git commit --allow-empty -m d1` × N in quick succession) is easily fast enough to exceed the fixed 5-entry window before the hook consumes it. This is fully repeatable and does not require any race against the exact instant of hook execution — only "enough" decoys within the 120s/5-entry budget, which an attacker fully controls.

### Recommendation
Make the reflog scan window scale with actual commit volume rather than a fixed entry count: e.g., scan reflog entries strictly by time (`max_age_s`) without an entry-count cap, or dynamically increase `max_n` until entries fall outside `max_age_s`, so a burst of decoy commits cannot evict an in-window commit purely by count. Alternatively, track a per-repo "last known HEAD" checkpoint at PostToolUse dispatch time (before hand-off to asyncRewake) and always include `commit_prev_head..new_head` (a full rev-list, not a fixed reflog slice) when computing `_fresh`, similar to how push-sweep computes its range via `_git_rev_list_range`.

### Proof of Concept
Integration test (extending `_git_reflog_recent_commits` / `handle_commit_review_posttooluse` test suite):
1. Init a temp git repo.
2. Perform a quiet commit `git commit -q -m "malicious" <file>` (stdout captured/suppressed so `commit_succeeded` fast-path fails).
3. Immediately perform 5 additional `git commit --allow-empty -m "decoyN"` commits (N=1..5) before invoking the hook logic, simulating decoys landing during async hook latency.
4. Call `_git_reflog_recent_commits(repo_root)` directly and assert the malicious commit's SHA is **absent** from the returned `fresh` list (demonstrating the truncation).
5. Invoke `handle_commit_review_posttooluse` (or its core logic) for the quiet commit's Bash tool_response and assert that the malicious commit's SHA never appears in the set of SHAs passed to `git show -p` / `analyze_code_security`, while decoy SHAs (or at least the position-0 decoy) are reviewed — asserting the review-target binding invariant is violated (malicious commit unreviewed, benign decoy reviewed).

```python
def _git_reflog_recent_commits(repo_root, max_age_s=120, max_n=5):
    """Return (fresh_commit_shas, stale_count) from the HEAD reflog.

    Scans the last `max_n` reflog entries and returns the SHAs whose action is
    `commit*` AND whose commit timestamp is within `max_age_s` of now,
    newest-first. `stale_count` is the number of commit-action entries that
    were too old (so the caller can distinguish "no commit happened" from
    "commit happened earlier than the window").

    Used by commit-review when stdout-based `[branch sha]` detection fails
    (output piped/redirected/-q, or a chained command after `git commit`
    pushed the success line off — `git commit && git push` makes HEAD@{0}
    `update by push`, not `commit:`). The HEAD@{0}-only check
    keeps the not-yet-visible-HEAD skip rare; analysis showed the
    residual is dominated by these chained-command and noop-guard cases.

    Safety vs. blindly reading HEAD:
      - cross-repo (`cd ../other && git commit`): repo_root's own reflog has
        no fresh commit, so this returns ([], 0).
      - commit actually failed (pre-commit reject, nothing-staged): reflog's
        recent entries are the prior checkout/commit/reset → ([], 0) or only
        stale entries.
      - HEAD raced ahead (a second commit landed before this async hook ran):
        both commits appear in the scan and both get reviewed — correct.
      - prior Bash call's commit within the window: would be returned here,
        but the call site deduplicates against `.git/sg-reviewed-shas` so a
        SHA is reviewed at most once. This is also the non-overlap invariant
        with push-sweep.
    """
    if not repo_root:
        return [], 0
    try:
        # %gs (the reflog subject) is `commit: <commit-msg first line>` and can
        # contain `|`; put it LAST so split("|", 2) leaves it intact. %H is
        # hex and %ct is integer, so the first two fields are delimiter-safe.
        r = subprocess.run(
            [*GIT_CMD, "log", "-g", "-n", str(max_n),
             "--format=%H|%ct|%gs", "HEAD"],
            cwd=repo_root, capture_output=True, text=True, timeout=5,
        )
    except (subprocess.TimeoutExpired, FileNotFoundError, OSError):
        return [], 0
    if r.returncode != 0:
        return [], 0
    import time as _time
    now = int(_time.time())
    fresh, stale = [], 0
    for idx, line in enumerate(r.stdout.splitlines()):
        parts = line.split("|", 2)
        if len(parts) != 3:
            continue
        sha, ct, subject = parts
        # `commit: msg`, `commit (amend): msg`, `commit (initial): msg`,
        # `commit (merge): msg` — all create a reviewable commit object.
        if not subject.startswith("commit"):
            continue
        try:
            age = now - int(ct)
        except ValueError:
            continue
        # HEAD@{0} (idx==0) is exempt from the age gate. The gate exists to
        # bound the WIDENED HEAD@{1..max_n-1} scan from picking up commits
        # made by *prior* Bash calls; HEAD@{0} is by definition the most
        # recent reflog entry and was previously accepted unconditionally
        # (_git_reflog_head_if_just_committed previously had no age check).
        # Applying max_age_s to idx==0 made the not-yet-visible-HEAD skip
        # noticeably more frequent on chained
        # `git commit && <slow command>` where %ct is >120s old by the
        # time the async PostToolUse hook fires.
        if idx == 0 or age <= max_age_s:
            fresh.append(sha)
        else:
            stale += 1
    return fresh, stale
```
