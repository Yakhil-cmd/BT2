### Title
Direct token transfers to the controller are permanently uncredited and unrecoverable - ([File: contracts/controller/src/payments.rs])

### Summary
An unprivileged user can transfer any token directly to the controller contract address, but the controller has no entrypoint that sweeps, credits, or returns pre-existing token balances. The controller’s refund helper explicitly preserves balances that existed before an operation and refunds only the positive delta received during that operation. As a result, tokens sent directly to the controller are permanently locked. [1](#0-0) 

### Finding Description
The controller’s public interface exposes lending operations such as `supply`, `repay`, liquidation, flash-loan strategies, and `recapitalize`, but no generic token-recovery or withdrawal function for arbitrary controller-held balances. [2](#0-1) 

Normal payment flows either measure a new transfer into an intended recipient or move funds through the pool; they do not account for tokens already sitting at the controller. `transfer_amount_measured` measures only the recipient’s balance change caused by the explicit transfer being performed. [3](#0-2) 

The controller’s only generic refund logic snapshots the pre-operation controller balance, computes the new delta, and transfers out only that new positive amount. A prior donation is therefore deliberately excluded from every later refund path. [1](#0-0) 

### Impact Explanation
Any user who authorizes a token `transfer` with the controller as `to` loses access to those funds permanently. The controller can hold the token balance, but no public controller operation can attach it to an account, market cash book, or refund recipient. This is a permanent freezing of user funds, matching the bug class of assets being receivable by a contract without a corresponding withdrawal path. [1](#0-0) 

### Likelihood Explanation
The path is permissionless and requires only an ordinary token transfer authorized by the sender. No privileged role, malformed parameter, oracle manipulation, or contract vulnerability in a third party is required. The impact is limited to funds sent directly to the controller outside the intended payment flows, so it does not endanger all protocol deposits, but any amount sent this way is unrecoverable. [4](#0-3) 

### Recommendation
Add an explicit recovery mechanism for controller-held tokens, such as an owner-gated sweep of the excess over balances reserved for in-flight operations, or prevent the controller address from being used as a token recipient in integrations. If recovery is added, it must preserve measured in-flight deltas and must not expose funds temporarily held during strategy execution. [1](#0-0) 

### Proof of Concept
1. Let `controller` be the deployed controller address and `token` be any standard token contract.
2. An unprivileged sender calls `token.transfer(sender, controller, amount)` with `amount > 0`.
3. The token balance now belongs to the controller contract.
4. Calling controller operations cannot recover it: `refund_controller_balance_delta` snapshots the controller’s already-increased balance and refunds only subsequent positive deltas, while the public ABI contains no token-sweep endpoint.
5. The transferred amount remains at the controller indefinitely. [1](#0-0) [2](#0-1)

/// Refunds only the controller balance increase since `balance_before`,
/// preserving the pre-existing balance; no-op for a nonpositive delta.
pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }

pub fn transfer_amount_measured(
    env: &Env,
    asset: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
    non_positive_error: GenericError,
) -> i128 {
    assert_with_error!(env, amount > 0, non_positive_error);
    let tok = token::Client::new(env, asset);
    let pre = tok.balance(to);
    tok.transfer(from, to, &amount);
    let post = tok.balance(to);
    post.checked_sub(pre)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::AmountMustBePositive))
