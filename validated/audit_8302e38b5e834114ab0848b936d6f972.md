### Title
Webhook signature verification selects the GitHub App/secret from an attacker-controlled `repository.owner`/`organization.login` field that is decoupled from the organization actually acted upon by the event handlers, enabling forged `membership` events to grant escalation into `Shipit.github_teams` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and thus which `webhook_secret`) to verify the HMAC signature against based on `repository_owner`, a value read straight out of the untrusted JSON body. Every handler downstream, however, reads its *own* organization/repository identifier from the same body (e.g. `MembershipHandler` uses `params.organization.login`, `PushHandler`/`StatusHandler` use `repository.full_name`/commit `sha`). Nothing ties the organization whose secret validated the signature to the organization/repository that the handler subsequently mutates. In a multi-org Shipit deployment (the officially documented "Using Multiple Github Applications" mode), an attacker who legitimately controls one configured organization's webhook secret can forge events that are "signed" with their own org's secret but whose body claims to belong to a completely different organization/repository, causing state-changing writes against that other tenant.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

**Binding broken:** `organization authenticated (via webhook_secret lookup keyed on payload `repository_owner`)` != `organization/team actually written (via payload `organization.login`/`team.slug` in the handler)`. The HMAC only proves "the sender knows *some* configured org's secret," not "the sender is authorized to act as the org named elsewhere in the same body."

### Impact Explanation
An attacker who is a legitimate administrator of Organization A configured in a multi-org Shipit instance (and therefore knows/controls Organization A's own `webhook_secret`, which is not a privileged Shipit credential — it's their own org's GitHub App secret) can:
1. Sign a `membership` event payload with Organization A's secret (`repository.owner.login` / `organization.login` at the top used only for `verify_signature` set to `"A"`).
2. Set the `membership`-handler-relevant `organization.login`, `team.slug`, `team.id`, and `member.login` fields to target Organization B's team that is listed in `Shipit.github_teams` (the privileged team gating admin functionality), with `member.login` equal to a GitHub identity the attacker controls (or has already logged into Shipit via OAuth, creating a matching `User` row).
3. `MembershipHandler#process` creates/finds that `Team` and calls `team.add_member(member)`, granting the attacker's `User` membership in Organization B's authorization team without ever having been a real GitHub team member.
4. The attacker can now pass `Shipit::Authentication`'s "member of `Shipit.github_teams`" check and access privileged, org-B-scoped functionality (e.g. `ApiClientsController`), which is explicitly listed as a High-severity impact: "escalation into `Shipit.github_teams` authorization."

The same signature-selection flaw also allows cross-tenant `push`/`status`/`check_suite` forgery (e.g., triggering `GithubSyncJob` or writing `Commit` statuses for another org's stacks), but the `membership` handler path is the most directly severe since it grants durable authorization state.

### Likelihood Explanation
This requires only that the Shipit instance be configured for multiple GitHub organizations (an explicitly documented, supported configuration) and that the attacker be an ordinary administrator/owner of one of those organizations — not a privileged Shipit user, not in possession of any Shipit session, `ApiClient` token, or the target organization's secret. Crafting and sending the forged JSON body with a valid `X-Hub-Signature` computed from their own known secret is trivial and requires no special access to the target organization or to Shipit internals.

### Recommendation
Do not select the verification secret (nor any downstream authorization decision) from unauthenticated payload fields. After verifying the signature with a given organization's secret, cross-check that every organization/repository identifier consumed by the dispatched handler (`repository.full_name`'s owner, `organization.login` in `membership` events, etc.) matches the organization whose secret validated the signature, and reject the event (422) on mismatch. Alternatively, bind webhook delivery to an unambiguous, GitHub-provided value (e.g. verify against every configured org's secret and only accept the org for which verification succeeds AND for which the payload's actual acted-upon organization equals that org).

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (attacker-controlled, secret `sA` known to attacker) and `OrgB` (victim, with a Shipit-privileged team `OrgB/admins` in `oauth.teams`).
2. Attacker builds a `membership` event body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(sA, body)` using OrgA's own secret and POSTs to `/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` computes `repository_owner = "OrgA"`, fetches OrgA's `GitHubApp`, and successfully verifies the signature against OrgA's secret (see `app/controllers/shipit/webhooks_controller.rb` lines 24-49).
5. `create` dispatches the full payload to `MembershipHandler`, which creates/finds `Team(organization: "OrgB", slug: "admins")` and adds a `User` with login `attacker-controlled-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb` lines 22-43; `app/models/shipit/team.rb` lines 41-43).
6. If the attacker previously authenticated to Shipit via GitHub OAuth as `attacker-controlled-login`, their `current_user` now satisfies the "member of `Shipit.github_teams`" check for `OrgB`, granting access to functionality gated for `OrgB` administrators despite never having been a legitimate `OrgB/admins` GitHub team member.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
