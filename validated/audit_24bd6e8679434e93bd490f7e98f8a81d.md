### Title
Missing length/format validation of attacker-controlled ephemeral public key before native ECDH parsing - ([File: device.js])

### Summary
`device.js`'s `decryptPackage()` accepts `objEncryptedPackage.dh.sender_ephemeral_pubkey` from an untrusted peer (a paired device, or any device that can reach `hub/deliver`) with only a `typeof === 'string'` check, then feeds the raw base64-decoded bytes directly into the native `secp256k1` `ecdh()` binding via `deriveSharedSecret()`, without validating that the buffer is a well-formed compressed/uncompressed EC point of the expected length (33/65 bytes) beforehand.

### Finding Description
`decryptPackage()` validates only the *type* of the DH fields, not their length or content: [1](#0-0) 

It then calls: [2](#0-1) 

`peer_b64_pubkey` (`sender_ephemeral_pubkey`) comes straight from the JSON payload of a device message delivered through the hub (`hub/deliver`), i.e. fully attacker-controlled data from any peer that knows (or guesses) a recipient's temp/permanent public key — this is the "paired device" / device-message attack surface explicitly in scope. The resulting `Buffer` is passed as the raw public-key argument into the `secp256k1` native `ecdh()` binding (`require('secp256k1')`, imported as `ecdsa` in `device.js`), which parses the buffer as an EC point. Unlike the sibling code path for `hub/temp_pubkey`, which validates the pubkey length before use via `isValidPubKey`/`isStringOfLength(..., constants.PUBKEY_LENGTH)`: [3](#0-2) 

...`decryptPackage()`'s `sender_ephemeral_pubkey` has no equivalent length/format check. Depending on which secp256k1 binding/version is resolved at install time (native bindings vs. pure-JS `elliptic`/`noble` fallback), passing a buffer of unexpected length or malformed point encoding into the native point-parsing routine is the same class of bug as the reported CVE: a length-derived index/loop miscalculation while parsing a compact binary structure (compare to `read_2004_section_revhistory` reading past the allocated buffer based on an unvalidated internal length/count field). Here, the "internal length field" is effectively the buffer's own (attacker-controlled) length being fed into a fixed-format point-parsing routine without a prior bounds/format check in application code.

### Impact Explanation
If the resolved `secp256k1` binding does not itself perform strict length/format validation before reading X/Y coordinate bytes (some native bindings assume the caller has validated length and can read/act on out-of-bounds memory or crash on malformed input), an attacker who can deliver an `encrypted_package` to a device (any paired correspondent, or anyone able to route a device message through `hub/deliver`) can trigger memory-safety issues in the recipient's wallet process — ranging from denial of service (crash of the wallet/hub) to, in the worst case for native heap-overflow-class bugs, memory corruption. This is a client-side (wallet/device) impact rather than a direct funds-loss/consensus bug, but it fits the requested class of "wallet and contract message handling" reachable by an unprivileged paired device / message sender.

### Likelihood Explanation
Likelihood is high for a crash/DoS: the code path is reached automatically whenever a `decryptPackage` call happens on any inbound device message, which is normal correspondent traffic and requires no special privileges beyond being a paired device (or one whose device address is targeted via the hub). Whether it escalates beyond a JS-level thrown exception (which is already handled with try/catch further down in the JSON-parsing stage, but *not* around `deriveSharedSecret`/`ecdh` itself) into actual heap corruption depends on the specific secp256k1 backend in use, which could not be fully confirmed from the available index (native vs. pure-JS build details were not resolved).

### Recommendation
- Validate `dh.sender_ephemeral_pubkey` and `dh.recipient_ephemeral_pubkey` length/format (e.g., using the existing `isValidPubKey`/`constants.PUBKEY_LENGTH` check already used for `hub/temp_pubkey`) in `decryptPackage()` before calling `deriveSharedSecret()`.
- Wrap the `ecdsa.ecdh(...)` call in `deriveSharedSecret()` in a try/catch so any parsing failure in the native/JS binding fails safely instead of propagating an unhandled exception or, in the worst case, undefined native behavior.
- Confirm which `secp256k1` implementation/version is actually bundled and audit its point-parsing bounds checks for buffers of arbitrary length.

### Proof of Concept
1. Pair with (or otherwise become a known correspondent of) a target device, or intercept the `hub/deliver` flow to a target `device_address`.
2. Send a device message whose `encrypted_package.dh.sender_ephemeral_pubkey` is a base64 string decoding to a buffer of anomalous length (e.g., 0, 1, or 200 bytes) instead of the expected 33/65-byte compressed/uncompressed point, while `recipient_ephemeral_pubkey` is set to match the victim's known temp or permanent public key so `decryptPackage()` selects a private key and proceeds to call `deriveSharedSecret()`.
3. Observe that no length/format validation occurs before the malformed buffer reaches `ecdsa.ecdh()`, and monitor the recipient process for a crash or abnormal behavior in the native secp256k1 binding.

*(Note: full confirmation that this results specifically in a heap-based overflow — as opposed to a safely-thrown JS exception — depends on internal details of the `secp256k1` native binding used at runtime, which could not be directly inspected within the indexed codebase.)*
