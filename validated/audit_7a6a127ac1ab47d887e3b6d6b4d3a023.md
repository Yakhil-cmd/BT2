### Title
Cross-tenant webhook forgery via organization-selectable signature verification bypassing per-repository authentication - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook-secret to validate a payload against using `repository_owner`, which falls back to attacker-controlled `organization.login` when `repository.owner.login` is omitted. Because `LabelCapturingHandler` (and other `pull_request` handlers) only require `repository.full_name` and never re-check that it belongs to the organization used for signature verification, an attacker who knows the name of any configured organization whose `webhook_secret` is empty-string (`''`) can name a *different* organization's repository in `repository.full_name` and have the mutation processed unauthenticated.

### Finding Description
The broken binding is: **organization used to select the webhook secret for signature verification == organization that actually owns the mutated `repository.full_name`**. This is never enforced.

- `WebhooksController#repository_owner` reads `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and is passed straight into `Shipit.github(organization: repository_owner)` in `verify_signature` [2](#0-1) .
- `GitHubApp#initialize` converts `webhook_secret: ''` into `nil` via `.presence` [3](#0-2) , and `verify_webhook_signature` auto-passes (`return true unless webhook_secret`) whenever the secret is `nil` [4](#0-3) .
- `LabelCapturingHandler`'s schema requires only `repository.full_name`, not `repository.owner.login` [5](#0-4) , and resolves the target `Repository` purely from `params.repository.full_name` with no cross-check against the organization used for signature verification [6](#0-5) , then writes labels via `pull_request.update!` [7](#0-6) .

Exploit flow (requires multi-org config, per `Shipit.github_app_config` / `github_default_organization` in `lib/shipit.rb:170-200`): if org `A` is configured with `webhook_secret: ''` and org `B` owns a real tracked repository/stack with a real secret, the attacker POSTs to `/webhooks` with `X-Github-Event: pull_request`, `organization: {login: "A"}`, no `repository.owner`, and `repository.full_name: "B/real-repo"`. `repository_owner` resolves to `"A"`; `Shipit.github(organization: "A")` loads org A's config with `webhook_secret` nil (post-`.presence`); `verify_webhook_signature` returns `true` for any signature; the handler then mutates B's stack/pull request using the payload's `repository.full_name`, entirely bypassing B's real webhook secret.

Existing guards do not stop this: `drop_unhandled_event` only filters unregistered event types; `GithubOrganizationUnknown` only rejects *unknown* org names, not this cross-org substitution; and the `ExplicitParameters` schema for the handler never requires or validates `repository.owner.login` against the verifying organization.

### Impact Explanation
An unauthenticated attacker can forge `pull_request` (and by the same mechanism, `push`/`status`/other) webhooks that mutate a *different* organization's tracked repository/stack — writing pull-request labels, archiving/unarchiving review stacks, or triggering provisioning actions — for any repository already tracked in Shipit, so long as any one configured organization in the deployment has an empty-string `webhook_secret`. This is a cross-tenant authentication bypass matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
This requires two preconditions that narrow real-world likelihood: (1) the deployment must use the **multi-org** `github:` config schema (top-level keys are organization names) — in the common single-org schema, `Shipit.github_default_organization` is `nil` and `Shipit#github` ignores the `organization:` argument entirely, using the single global config regardless of what `repository_owner` resolves to, so the bypass has no effect [8](#0-7) ; and (2) at least one configured org must have `webhook_secret` set to the empty string `''` rather than left unset/`nil` or a real value — a specific misconfiguration, though the docs' multi-org example shows secrets simply left blank per-org [9](#0-8) . Given both, the attacker only needs the public name of the misconfigured org and the `full_name` of the target repo — both are typically public GitHub information — making this trivially repeatable per request.

### Recommendation
- In `WebhooksController#verify_signature`, verify the signature using the organization that actually owns `repository.full_name`/`repository.owner.login` from the payload, not an attacker-suppliable fallback to `organization.login` when `repository` is present but its owner is omitted.
- Treat `webhook_secret: ''` as a hard misconfiguration error at boot (raise if `secrets.github[...][:webhook_secret]` is present but blank) rather than silently treating it as "no secret configured."
- Cross-check, inside handlers or centrally, that the repository resolved from `repository.full_name` belongs to the same organization that was used to verify the signature.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test, multi-org fixture)
test "org with empty-string webhook_secret allows forging payload naming another org's repo" do
  # Config: OrgA webhook_secret: '' ; OrgB webhook_secret: 'realsecret' (target org owning tracked repo)
  Shipit.stubs(:github_default_organization).returns('orga')
  Shipit.stubs(:github_app_config).with('orga').returns({ webhook_secret: '' })

  payload = {
    action: 'labeled',
    number: 2,
    pull_request: { /* ... required fields ... */ },
    organization: { login: 'orga' },       # attacker-chosen org, no repository.owner given
    repository: { full_name: 'orgb/real-repo' }, # actual target, different org
    sender: { login: 'attacker' }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # arbitrary/invalid signature

  post :create, body: payload, as: :json

  assert_response :ok # bypasses 422, proving auto-verify true via GitHubApp#verify_webhook_signature
end
```
Assertions: before the fix, `Shipit.github(organization: 'orga').verify_webhook_signature(anything, anything)` returns `true` (because `''.presence` → `nil`), and the request succeeds (`:ok`) despite naming `orgb`'s repository with an arbitrary signature — demonstrating the equality "verifying org == owning org of mutated repository" does not hold.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
