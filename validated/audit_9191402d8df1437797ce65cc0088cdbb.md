Confirmed: Shipit supports multi-tenant GitHub App configuration where each organization has its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml`), and `Shipit.github(organization:)` selects the app/secret keyed by organization name [1](#0-0) . This confirms the exploit path below is real: signature verification is scoped per-organization, but the field used to select *which* organization's secret to check is not the same field later used to select *which repository's stacks* get mutated.

### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while handlers act on the unverified `repository.full_name` field, allowing cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's HMAC secret to validate the request against using `repository_owner`, derived from `params.dig('repository','owner','login')` with fallback to `params.dig('organization','login')` [2](#0-1) . Once the signature check passes, every registered handler for the event is invoked with the *entire* raw JSON body [3](#0-2) . All the concrete handlers (`PushHandler`, `PullRequest::*Handler`, etc.) determine the target repository/stacks using a *different* field, `payload.dig('repository','full_name')` [4](#0-3) , or `params.repository.full_name` in each pull-request handler [5](#0-4) .

Because the HMAC only proves "this org's registered secret produced this exact byte string," and Shipit supports one webhook secret per organization (`Shipit.github(organization:)` resolves per-org config, confirmed by the multi-org fixture) [6](#0-5) [7](#0-6) , an attacker who controls (or has push/webhook access to) their **own** GitHub App-installed organization "AttackerOrg" can craft an arbitrary raw payload — signing it correctly with AttackerOrg's webhook secret — where:
- `repository.owner.login` = `"AttackerOrg"` (so verification picks AttackerOrg's secret and passes), and
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler logic operates against the victim's stacks).

This breaks the equality the engine implicitly relies on: `organization that authenticated == repository that is written`. The `increaseRedemptionFee`/`provideRedemptionProof` bug class is directly analogous — one code path checks/authorizes based on one derived value, while a different, unguarded code path acts on a related-but-distinct value from the same untrusted payload, and nothing binds them together.

### Finding Description
- Verification: `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` — this only proves the raw body was HMAC-signed by *some* org's secret, chosen by the attacker-controlled `repository.owner.login` field [8](#0-7) .
- Action: handlers parse `params` from the same raw body and resolve the acted-upon repository via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [4](#0-3) .
- Nothing in the codebase enforces that `repository.owner.login` (used for auth) is consistent with `repository.full_name` (used for action) — they are simply two independent fields inside one JSON body that only needs to satisfy the org-level secret used for the field the attacker also controls.
- Under GitHub's real webhook delivery this invariant naturally holds because GitHub sets both fields, and only GitHub knows each installation's real secret. The vulnerability requires the attacker to legitimately possess a valid signature for *a* body under *some* org's secret — i.e., they must control an org where Shipit's GitHub App is installed with a known/derivable webhook secret, or exploit any org whose secret is `nil`/blank, in which case `verify_webhook_signature` returns `true` unconditionally [9](#0-8) .

### Impact Explanation
If the attacker's own org has no `webhook_secret` configured (returns `true` always) or the attacker otherwise obtains a valid signature for their own org, they can submit a `push` event whose `repository.full_name` points at any *other* tracked repository/stack, causing `PushHandler#process` to call `stack.sync_github(expected_head_sha: params.after)` [10](#0-9)  against the victim's stack — forcing sync to an attacker-chosen `after` SHA. Similarly, `pull_request` handlers can create/label/archive/unarchive review stacks belonging to a different repository [11](#0-10) . This is a cross-repository write triggered without any credential belonging to the victim organization, matching the Critical-tier "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Exploitability depends entirely on the attacker being able to produce a validly-signed body for *some* organization known to Shipit — either an org with `webhook_secret: nil` (blank secret bypasses verification entirely, as shown in the `secrets_double_github_app.yml` fixture where both orgs have `webhook_secret: # nil`) [12](#0-11) [13](#0-12) , or an org where the attacker controls the GitHub App installation and thus the delivered secret. Deployments using per-organization GitHub Apps without a configured `webhook_secret` for every org are directly exposed; deployments that always set a strong `webhook_secret` per org are not exploitable this way since the attacker would need that specific org's secret to forge the outer signature, though the field-mismatch design flaw remains latent.

### Recommendation
Bind the field used for authentication to the field used for action: after signature verification succeeds, re-derive `repository_owner` from the *same* `repository.full_name` used by handlers (e.g., parse the owner out of `full_name` and require it match `repository.owner.login`/`organization.login`), or better, have `verify_signature` reject the request if `repository.owner.login` and the owner segment of `repository.full_name` diverge. Additionally, do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in any production-configured organization — treat a missing secret as a hard misconfiguration error rather than an auto-pass.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `AttackerOrg` (webhook secret known to/controlled by attacker, or blank) and `victim-org` (has a tracked stack, e.g. `victim-org/victim-repo` on branch `master`).
2. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "AttackerOrg" }
  }
}
```
3. Sign the raw body with `AttackerOrg`'s webhook secret (known/blank) to compute `X-Hub-Signature`.
4. POST to `/webhooks` (`Shipit::WebhooksController#create`) with header `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and the signature check passes [8](#0-7) ; `PushHandler` then resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [10](#0-9) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
