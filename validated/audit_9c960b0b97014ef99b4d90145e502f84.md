### Title
Attacker-controlled PR label named `path` overrides `PATH` in the deploy shell environment, breaking binary resolution / enabling command hijack - (File: app/models/shipit/review_stack.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every PR label, upcased, with the literal value `"true"` into the stack's environment hash with no key filtering. That hash flows unfiltered through `TaskCommands#env` and `StackCommands#env` into `Command#unbundled_env`, where it is merged *last* and therefore wins over the `PATH` value Shipit computes from `Shipit.shell_paths`. A PR label named `path` (case-insensitive) from an untrusted fork thus overwrites `PATH` to `"true"` in the exact hash handed to `PTY.spawn`.

### Finding Description
The broken binding is: `Command#unbundled_env`'s `'PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` should equal the `PATH` key present in the hash ultimately passed to `PTY.spawn`. This binding is broken because `unbundled_env` is computed as `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [1](#0-0) , so any `PATH` key present in `@env` unconditionally overrides the computed value, and that merged hash is passed straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [2](#0-1) .

`@env` is populated from `Command.new(..., env:)`, which is `TaskCommands#env`, which calls `.merge(@stack.env)` [3](#0-2) . For a `ReviewStack`, `#env` is overridden to merge in the PR's labels, upcased, each mapped to the string `"true"`, with no allow-list or reserved-key check:
```ruby
def env
  return super unless pull_request.present?
  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
``` [4](#0-3) 

The labels themselves are persisted verbatim from the GitHub webhook payload by `LabelCapturingHandler#capture_labels`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [5](#0-4) . Nothing in the `ExplicitParameters` schema restricts label names to a safe set (`requires :labels, Array do requires :name, String end`) [6](#0-5) .

Attacker-controlled input: any GitHub user who can open a PR against a repository configured with `Shipit.review_stacks?` and add/rename a label to `path` (or `Path`, `PATH`, etc. — case-folded via `.upcase`). GitHub webhooks for `pull_request` `labeled`/`opened`/`reopened` events are processed by this handler regardless of whether the PR is from a fork, as long as the base repository has review stacks enabled and a `PullRequest`/`stack_id` record exists (created on `opened_active_stack?`). This does not require write access to the base repo, only the ability to open a PR and apply a label they control on their own PR (label creation/application on one's own fork-originated PR against a public repo accepting PRs is standard unprivileged GitHub behavior).

Exploit flow: attacker opens a PR (or already has one open) against a review-stack-enabled repo, adds a label named `path`, which becomes `PullRequest#labels` including `"path"`. Any subsequent task/deploy run for that stack calls `TaskCommands#env`/`StackCommands#env` → `ReviewStack#env`, producing `{'PATH' => 'true', ...}` merged over the base stack env. When `Command#unbundled_env` runs, `@env.stringify_keys` includes `'PATH' => 'true'`, which overrides the `Shipit.shell_paths`-derived `PATH`, and this corrupted hash is what `PTY.spawn` receives.

None of the existing guards intercept this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the payload came from GitHub, not that label names are safe. `drop_unhandled_event` and the `ExplicitParameters` schema validate presence/type (`String`) of `labels[].name`, not content. There is no `EnvironmentVariables#permit`/allow-list applied to `ReviewStack#env`'s label-derived keys (that permit/filter mechanism, per `filter_envs`/`Task#env`, is only used for explicit user-triggered task env params via the API/UI, not for PR labels flowing through `ReviewStack#env`). `Stack` model validations (`environment` format, `branch` presence) do not touch the `env` method's runtime hash construction.

### Impact Explanation
Every command run for the affected review stack's deploy (git fetch/clone, bundle install, deploy steps) executes with `PATH=true` instead of the intended `Shipit.shell_paths`-derived value, since `Command#unbundled_env`'s merge order lets attacker-controlled data override the safety-critical `PATH`. Binary resolution for `git`, `bundle`, and any command that isn't given as an absolute path fails to resolve as Shipit intends — at minimum breaking deploys for that stack. Combined with `Shipit.shell_paths` typically being narrowed to a curated/trusted directory list (a defense meant to constrain what binaries get invoked), this override means the intended safe-`PATH` control is nullified; if any attacker-influenced additional `PATH`-like value can later be substituted (out of scope to prove further here), the divergence is the same class of "environment corruption on the deploy host for that stack's repository." This is scoped per-repository/per-review-stack (the attacker only affects the environment for tasks running against that stack), but it is repeatable on every deploy/task run as long as the label persists, and requires no elevated privilege — matching the RCE-adjacent process environment corruption category for that stack's repository.

### Likelihood Explanation
Preconditions are modest and attacker-achievable: `Shipit.review_stacks?` must be enabled for the base repository (an operator/config choice, common for repos wanting per-PR environments), and a `PullRequest`/review stack record must exist (auto-created on PR `opened` against such a repo). The attacker needs only the ability to open a PR and apply a label — both permitted to any GitHub user who can fork-and-PR a public repo accepting contributions, no Shipit credentials required. The label name `path` is trivial to add. This is fully repeatable per stack and does not depend on timing races beyond a deploy/task being triggered afterward (which stack maintainers do routinely).

### Recommendation
In `Shipit::ReviewStack#env`, filter or reject label names that collide with reserved/sensitive environment variable names (at minimum `PATH`, and ideally restrict to a safe prefix or allow-list, e.g. only accept labels matching `\A[a-z0-9_]+\z` and reject/deny-list known-dangerous names like `PATH`, `LD_PRELOAD`, `BUNDLE_*`, `RUBYOPT`, etc.). Additionally, in `Command#unbundled_env`, compute `PATH` last (or explicitly re-assert the safe `PATH` after merging `@env`) so that caller-supplied environment can never override the shell's binary search path:
```ruby
def unbundled_env
  BASE_ENV.merge(@env.stringify_keys).merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}")
end
```
This defends in depth even if a future feature reintroduces label/env-derived overrides.

### Proof of Concept
```ruby
# test/lib/shipit/command_test.rb (or task_commands_test.rb)
test "#env PATH cannot be overridden by attacker-controlled env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["path"]  # attacker-controlled GitHub label
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["PATH"]  # demonstrates ReviewStack#env pollution

  command = Shipit::Command.new("echo hi", chdir: Dir.tmpdir, env: env)
  resolved_path = command.unbundled_env["PATH"]

  expected_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
  # BROKEN BINDING: resolved_path == expected_path should hold but does not
  assert_equal "true", resolved_path
  refute_equal expected_path, resolved_path
end
```
This demonstrates that the equality `Command#unbundled_env`'s intended `PATH` == the `PATH` actually reaching `PTY.spawn` does not hold once a PR label named `path` is present, confirming the vulnerability end-to-end from `ReviewStack#env` through `TaskCommands#env` to `Command#unbundled_env`.
