Based on my investigation, I found a concrete analog in `Shipit::WebhooksController`. This maps to the report's core bug pattern — a value that determines *authorization/trust* is derived from a different payload field than the value that determines *what gets written* — creating a binding mismatch that an attacker can exploit.

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, letting anyone holding one configured org's `webhook_secret` write to another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC signature against using `repository_owner`, a value taken from `params.dig('repository', 'owner', 'login')` (with a fallback to `organization.login`) [1](#0-0) . It uses that org's `webhook_secret` to check the signature [2](#0-1) . However, every webhook handler (`PushHandler`, `MembershipHandler`, pull-request handlers, etc.) determines *which repository/stacks to act on* using a completely different field: `payload.dig('repository', 'full_name')`, resolved through `Repository.from_github_repo_name` [3](#0-2) . Nothing enforces that the owner encoded in `full_name` matches `repository.owner.login`/`organization.login` used for signature verification.

### Finding Description
Shipit supports multi-tenant configuration where distinct GitHub organizations each get their own `app_id`/`webhook_secret` [4](#0-3) . `Shipit.github(organization: repository_owner)` looks up the `GitHubApp` instance (and thus the `webhook_secret`) for whatever organization name is present in the *current request's own JSON payload* [5](#0-4) [6](#0-5) .

Because the attacker fully controls the raw JSON body being signed, they can set `repository.owner.login` to an organization whose `webhook_secret` they know (e.g., their own onboarded organization on the same Shipit instance) while independently setting `repository.full_name` to `"<victim-org>/<victim-repo>"`. `verify_signature` only checks that the HMAC is valid for the secret belonging to `repository.owner.login` — it never cross-checks that this owner matches the owner encoded in `repository.full_name`, which is the value handlers actually use to resolve the target `Repository`/`Stack` [3](#0-2) . This breaks the equality that should hold: `organization that authenticated the request == organization owning the repository being written to`.

Concretely:
- `PushHandler#process` looks up stacks for `repository.full_name` and calls `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) , so the forged event can drive a sync against the victim org's stack using an attacker-chosen `after` SHA.
- `MembershipHandler`/team-related webhook flows (per `test/controllers/webhooks_controller_test.rb` fixtures) create/modify `Team`/`Membership` records from the payload's `team`/`organization`/`member` fields, using the same signature-verification indirection [8](#0-7) , which can escalate into `Shipit.github_teams` authorization if forged for an org whose teams gate access.

### Impact Explanation
An entity that only controls credentials for one configured (low-trust) organization can forge a signed webhook that Shipit accepts as authentic for a *different* organization's repository, since the signature check and the "which repository do I act on" logic key off two independent, unlinked fields in the same attacker-crafted payload. This can trigger unauthorized syncs into another organization's `Stack` (cross-repository writes) or manipulate `Team`/`Membership` records tied to `Shipit.github_teams`, escalating authorization for stacks the attacker should have no access to. This matches the High/Critical impact categories: cross-repository writes and escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
This requires the deployment to run Shipit's documented multi-organization mode with more than one configured GitHub App/`webhook_secret`, and requires the attacker to legitimately possess (or leak) one org's `webhook_secret` — a normal, low-privilege situation for an org admin onboarded to a shared Shipit instance, not for the specific victim org. No repository write access, session, or `ApiClient` token is needed; it is purely a payload-crafting attack against the public `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, additionally assert that the organization used to select the verifying secret (`repository_owner`) matches the owner portion of `repository.full_name` (and any `organization.login` present) before dispatching to handlers. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` (attacker-controlled, secret known) and `OrgB` (victim) as in `docs/setup.md` [4](#0-3) .
2. Craft a `push` event body: `{"ref":"refs/heads/main","after":"<attacker-sha>","repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/victim-repo"}}`.
3. Sign it with `OrgA`'s `webhook_secret` per `Hook::DeliverySigner`/HMAC-SHA1 scheme and set `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner => "OrgA"`, verifies successfully against `OrgA`'s secret [2](#0-1) .
5. `PushHandler#process` resolves stacks via `repository.full_name => "OrgB/victim-repo"` [3](#0-2)  and triggers `stack.sync_github` for OrgB's stack, even though the request was never authenticated as coming from OrgB.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
