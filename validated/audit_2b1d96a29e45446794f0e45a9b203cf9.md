### Title
Unfiltered PR-label injection into task/deploy process environment allows overriding reserved variables like `GEM_HOME` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack environment hash with no allowlist, and this hash is merged unconditionally into the environment used to spawn every deploy/task command via `TaskCommands#env` → `Command#unbundled_env` → `PTY.spawn`. Unlike deploy-time variables submitted through the controller, which are filtered by `DeploySpec#filter_deploy_envs`/`EnvironmentVariables#permit`, label-derived keys are never checked against any allowlist or reserved-key blocklist.

### Finding Description
The broken binding: the invariant claims `env_reaching_PTY.spawn ∩ fork_controllable_keys == ∅` for reserved keys such as `GEM_HOME`. In practice `env_reaching_PTY.spawn ⊇ {label_name.upcase => "true" for each PR label}`.

Path:
1. An unprivileged fork PR author (or any GitHub user labeling their own PR) adds a label, e.g. `gem_home`. `LabelCapturingHandler#capture_labels` persists `pull_request.update!(labels: params.pull_request.labels.map(&:name))` straight from the webhook body with no name restriction. [1](#0-0) 
2. `ReviewStack#env` turns every label into an uppercased key mapped to the literal string `"true"` and merges it into the stack env with no allowlist. [2](#0-1) 
3. `TaskCommands#env` (parent of `DeployCommands#env`) merges `@stack.env` directly into the hash used to build every `Command.new(command_line, env:, chdir:)` for `install_dependencies` and `perform` (the actual deploy steps), with no call to `filter_deploy_envs`/`EnvironmentVariables#permit` anywhere in this chain. [3](#0-2) [4](#0-3) 
4. `Command#unbundled_env` merges `@env.stringify_keys` last, on top of `BASE_ENV` (derived from `Bundler.unbundled_env`), so any fork-controlled key — including `GEM_HOME`, `BUNDLE_GEMFILE`, or even `PATH` — overrides the host-sanitized base environment. [5](#0-4) 
5. `Command#start` spawns the process with this merged env via `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, where `chdir` is the checked-out fork working directory — content fully controlled by the attacker. [6](#0-5) 

Existing guards fail to prevent this because `EnvironmentVariables#permit` (used by `DeploySpec#filter_deploy_envs`/`#filter_rollback_envs`) is only applied to `Deploy#env`, which is populated from controller params filtered by `deploy_params` in `DeploysController` — a completely separate path from the label-derived stack env. [7](#0-6) [8](#0-7) 
No such filtering exists on the label-injected path — this is confirmed by tests that treat this as intended feature behavior for feature-flag-style labels, without any reserved-key exclusion. [9](#0-8) [10](#0-9) 

**Important caveat**: the injected value is hard-coded to the literal string `"true"` (`labels[label_name.upcase] = "true"`), not an attacker-chosen arbitrary string. So an attacker cannot set `GEM_HOME=/attacker/arbitrary/path` directly — only `GEM_HOME=true`. Turning this into "gem resolution redirected to an attacker-populated gem tree" for RCE requires the attacker to additionally place a directory literally named `true` inside their own fork checkout (which they fully control as the PR author) so that the relative path `true` resolves to attacker content when bundler/rubygems consult `GEM_HOME` during `bundle install`/`bundle exec` in the deploy steps. This is a plausible but more constrained exploitation chain than "arbitrary path injection."

### Impact Explanation
Any fork PR author whose repository has review-stacks enabled (any `provisioning_behavior`, including `prevent_with_label`, since capturing happens regardless of behavior as long as the stack is active/not archived) can inject arbitrary-named environment variables (fixed value `"true"`) into every command spawned for that review stack's deploys and tasks, including `bundle install` and deploy scripts. This can override sensitive process environment such as `GEM_HOME`, `BUNDLE_GEMFILE`, `RUBYOPT`, or `PATH`, on the Shipit deploy host, within the scope of that stack's working directory (which is the attacker's own fork checkout). Combined with attacker-controlled repository content at that relative path, this can escalate to code execution during dependency installation/deploy step execution — matching the Critical/RCE-on-deploy-host category via `Command`/`PTY.spawn`. Blast radius is limited to the review stack tied to that PR/fork (not other tenants' stacks), since `env` is scoped to `pull_request.labels` on that specific stack.

### Likelihood Explanation
Preconditions: review stacks must be enabled for the target repository (any provisioning behavior, since label capture is independent of `provisioning_behavior`), and the attacker must be able to open/label a PR on their own fork against that repository (a normal, low-privilege GitHub interaction) — no Shipit credentials required. Attacker cost is trivial (add a label to their own PR). The value is fixed to `"true"`, so full arbitrary-path redirection requires an additional layer (attacker also controls the repo checkout content, so populating a literal `true` directory in their fork is feasible). This is repeatable on every deploy/task run for the affected review stack.

### Recommendation
In `ReviewStack#env`, do not merge raw uppercased label names as environment keys without an allowlist. Either: (a) route label-derived env through `EnvironmentVariables#permit` against a declared allowlist (e.g., `deploy_variables`/a dedicated `review.labels` allowlist in `shipit.yml`), or (b) exclude reserved/sensitized key names (`GEM_HOME`, `BUNDLE_*`, `PATH`, `RUBYOPT`, `GIT_*`, etc.) from ever being settable via labels, or (c) namespace label-derived variables (e.g., prefix with `SHIPIT_LABEL_`) so they can never collide with process-critical environment variable names.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (add)
test "#env does not allow labels to override reserved environment keys like GEM_HOME" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["gem_home"]

  # Binding under test: env reaching Command#start must not contain fork-controlled GEM_HOME
  assert_not_equal "true", stack.env["GEM_HOME"]
end

# test/lib/shipit/deploy_commands_test.rb (add)
test "deploy.variables step env does not inherit fork-controllable GEM_HOME from PR labels" do
  stack = shipit_stacks(:review_stack)
  deploy = stack.trigger_continuous_delivery
  stack.pull_request.labels = ["gem_home"]

  env = Shipit::DeployCommands.new(deploy).env
  command = Shipit::DeployCommands.new(deploy).perform.first

  # both sides of the equality: attacker-controlled label vs env reaching PTY.spawn
  assert_equal "true", env["GEM_HOME"]                      # demonstrates injection succeeds
  assert_equal "true", command.unbundled_env["GEM_HOME"]    # demonstrates it reaches the spawned process
end
```
These reproduce the exact reachable path (`ReviewStack#env` → `TaskCommands#env`/`DeployCommands#env` → `Command#unbundled_env` → would-be `PTY.spawn` argument) with no live GitHub calls required, using existing fixtures (`shipit_stacks(:review_stack)`).

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
