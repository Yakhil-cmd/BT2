### Title
Unsigned/optional GitHub webhook secret allows unauthenticated forgery of `status`, `push`, `membership` and `pull_request` events, enabling unauthorized merges and stack manipulation - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` delegates HMAC verification entirely to `GitHubApp#verify_webhook_signature`, which short-circuits to `true` whenever no `webhook_secret` is configured for the organization resolved from the payload. Since `webhook_secret` is documented and shipped as an *optional*, commonly-nil setting, any deployment that leaves it blank for an organization accepts **completely unauthenticated** webhook payloads, letting anyone who can reach `/webhooks` spoof GitHub events and mutate protected state — including commit statuses that gate automatic merges.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` runs `verify_signature` before dispatching any event: [1](#0-0) 

It resolves the `GitHubApp` instance for whatever organization the request payload claims (`repository.owner.login` / `organization.login`) and calls `verify_webhook_signature`: [2](#0-1) 

The verification method in `lib/shipit/github_app.rb` is: [3](#0-2) 

`return true unless webhook_secret` means: if the organization's `webhook_secret` config value is blank/nil, **every** request is treated as verified, regardless of the `X-Hub-Signature` header content. The setup documentation and generator templates present `webhook_secret` as optional and default it to nil: [4](#0-3) [5](#0-4) [6](#0-5) 

Once past `verify_signature`, `WebhooksController#create` blindly dispatches to all registered handlers for the claimed event: [7](#0-6) 

Handlers resolve the target `Stack`/`Repository` purely from attacker-controlled JSON fields such as `repository.full_name`: [8](#0-7) 

Concretely exploitable handlers include:
- `StatusHandler`, which creates a `Status` record for any commit whose `sha` is supplied, with an attacker-chosen `state`/`context`/`description`: [9](#0-8) 
- `PushHandler`, which triggers a `GithubSyncJob` for any matched stack/branch: [10](#0-9) 
- Membership handling in the controller test fixtures shows `membership` events create/delete `Team`/`User`/`Membership` records from payload data: [11](#0-10) 
- Pull-request handlers archive/unarchive review stacks and merge-adjacent state based on `label`, `opened`, `closed`, `reopened` events: [12](#0-11) 

The binding that is broken is: **"organization the signature is verified against" vs. "the repository/stack the handler actually writes to."** Even setting aside cross-org spoofing, the more direct break is: **"presence of a valid GitHub webhook signature" vs. "whether verification is actually enforced."** Because verification is a no-op when `webhook_secret` is unset, an unprivileged, unauthenticated network attacker can inject fabricated commit statuses. Those statuses feed directly into `MergeRequest::StatusChecker` (subclass of `Status::Group`, used by `all_status_checks_passed?`, `any_status_checks_failed?`, `any_status_checks_missing?`): [13](#0-12) [14](#0-13) 

If a stack's merge queue is enabled and required CI status checks are satisfied only by forged `success` statuses injected via the unauthenticated webhook path, `reject_unless_mergeable!` will not reject the merge, and `merge!` proceeds to call `stack.github_api.merge_pull_request`, i.e., an **unauthorized merge is executed using the app's own GitHub credentials** even though CI never actually passed.

### Impact Explanation
This crosses the Critical bar of "an unauthorized deploy, rollback or merge": forged `status` webhook events (requiring zero credentials when `webhook_secret` is unset) can satisfy required CI checks and unblock Shipit's automatic merge-queue processing, causing the app to merge a pull request via its own privileged GitHub App token without any real CI success. It also allows unauthenticated writes across `Team`, `User`, `Membership`, `Commit::Status`, and stack archival state, and can spuriously trigger `GithubSyncJob` for arbitrary tracked repositories.

### Likelihood Explanation
Likelihood is high wherever a Shipit operator does not set a per-organization `webhook_secret` — which every shipped configuration template (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `template.rb`, `docs/setup.md`) explicitly marks as optional/commented-as-nil, and the setup guide frames it as merely a good idea ("Webhook secret (optional): Fill it with some randomly generated string"). No credentials, session, or prior access are required — only network reachability of the public `/webhooks` endpoint, which is mounted specifically to receive unauthenticated GitHub-originated traffic.

### Recommendation
Do not silently accept unsigned requests. Require `webhook_secret` to be present for every configured organization at boot (fail fast / raise a configuration error), or, if it is intentionally allowed to be unset, refuse to process any webhook for that organization (reject with 4xx) rather than treating it as automatically verified. At minimum, log loudly and disable state-mutating handlers (status, push, membership, pull_request) whenever verification is not cryptographically enforced.

### Proof of Concept
1. Deploy Shipit with an organization configured without `webhook_secret` (the shipped default/example configs leave it blank).
2. As an anonymous attacker, `POST /webhooks` with headers `X-Github-Event: status` and `X-Hub-Signature: sha1=deadbeef` (arbitrary/invalid) and a JSON body:
```json
{
  "sha": "<sha of the commit blocking merge on the target stack>",
  "state": "success",
  "context": "<required-status-context>",
  "repository": {"full_name": "org/repo", "owner": {"login": "org"}}
}
```
3. `verify_webhook_signature` returns `true` because `webhook_secret` is blank for `org`, so the invalid signature is never checked.
4. `StatusHandler#process` creates a `Commit::Status` with `state: "success"` for the given commit.
5. If this was the last required/missing status for a pending `MergeRequest`, `ProcessMergeRequestsJob`/merge-queue logic sees `any_status_checks_missing?`/`any_status_checks_failed?` as false and proceeds to `merge!`, causing Shipit to merge the PR via the GitHub App's credentials without genuine CI success.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
