## Title
Cross-Stack Authorization Bypass in `CCMenuController#stack` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Every other API controller resolves the requested `Stack` through `BaseController#stacks`, which restricts the lookup to the stack an `ApiClient` token is scoped to. `Api::CCMenuController` overrides that resolution with its own private `stack` method that queries `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` relation, completely ignoring the token's `stack_id` binding. A token that was only supposed to authorize reads of one stack can be used to read the CI/build status of any stack in the installation.

### Finding Description
`Api::BaseController` establishes the trust binding between an `ApiClient` and the stacks it may act on: [1](#0-0) 

`current_api_client.stack_id?` is populated when the client was created with `stack:` set (e.g. via `ApiClientsController`), scoping it to a single repository/environment. All the resource controllers that inherit from `BaseController` (`StacksController`, `HooksController`, `TasksController`, `DeploysController`, …) call `stacks.from_param!(...)`, so a stack-scoped client can never resolve a `Stack` outside its own `stack_id`.

`Api::CCMenuController` breaks that binding by redefining `stack` to bypass the scoped `stacks` relation entirely: [2](#0-1) 

It only checks the coarse-grained permission string via `require_permission :read, :stack`, which is satisfied by any client that has `read:stack` in its `permissions` array, regardless of which stack that permission was scoped to: [3](#0-2) 

Because `stack` resolves `params[:stack_id]` against `Stack.from_param!` (unscoped), a request supplying an arbitrary `stack_id` for a *different* stack than the one bound to the authenticating token is served successfully — breaking the binding `token.stack_id == stack accessed`.

### Impact Explanation
An `ApiClient` that was deliberately scoped to a single stack (`stack_id` set, `permissions: [read:stack]` only) can be reused against `Api::CCMenuController#show` with any other stack's `stack_id` and receive that stack's build/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc.). This is an unauthorized cross-repository read of stack state/deploy output that the token was never granted, matching the "unauthenticated/unauthorized read of stack state" impact category for tokens that are supposed to be repository-scoped.

### Likelihood Explanation
Exploitation only requires possession of any valid stack-scoped `ApiClient` token with `read:stack` permission (such tokens are routinely created and embedded in CI status badge URLs, e.g. by `CCMenuUrlController`) and knowledge/guessing of another stack's `owner/repo/environment` triple, which is often public information (GitHub org/repo names). No privilege escalation, session, or GitHub credentials are required beyond the token itself.

### Recommendation
Make `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` instead of querying `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the same `current_api_client.stack_id` binding enforced by every other API controller.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_a` with `permissions: ['read:stack']` (as done by `ApiClientsController` or `CCMenuUrlController`).
2. Using that client's Basic-Auth token (or `?token=` query param, both supported by `CCMenuController#authenticate_api_client`), send:
   `GET /api/stacks/:owner/:repo_of_stack_b/:environment/ccmenu?token=<stack_a_token>`
3. The response returns `stack_b`'s CCMenu XML (`lastBuildStatus`, `activity`, `webUrl`, etc.) even though the token is only authorized for `stack_a`, as demonstrated by contrast with `Api::StacksController`, whose `stack` method correctly raises `ActiveRecord::RecordNotFound` for out-of-scope stacks: [4](#0-3)
