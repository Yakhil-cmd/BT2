### Title
Webhook signature is verified against the wrong GitHub App configuration, allowing cross-organization repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read straight out of the *unverified* JSON body. The event handlers that actually act on the payload, however, locate the target `Repository`/`Stack` using a *different* field from that same unverified body: `repository.full_name`. Because these two fields are never checked against each other, the organization whose secret authenticated the request is not bound to the repository that is ultimately written to.

### Finding Description
`verify_signature` computes the organization to authenticate against purely from attacker-controlled JSON, before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the app config for that organization out of `secrets.github`, in a Shipit deployment supporting multiple GitHub organizations (a documented feature): [3](#0-2) 

Each organization can be configured with its own, independently optional `webhook_secret` — the setup docs explicitly call it optional: [4](#0-3) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank/unset: [5](#0-4) 

Once `verify_signature` passes (either legitimately, for an org whose secret the attacker knows, or trivially, for any org configured without a `webhook_secret`), the *entire raw body* — including the `repository.full_name` field, not the `repository.owner.login`/`organization.login` field used for authentication — is dispatched unchanged to the event handlers: [6](#0-5) 

Every handler resolves its target `Repository` via `params.repository.full_name` (or `payload.dig('repository', 'full_name')`), with no re-check that this repository belongs to the organization that was used to authenticate the request: [7](#0-6) [8](#0-7) [9](#0-8) 

This is the exact bug-class analog of the dPrime report: an action-relevant field (`mintAndDelay`'s recipient/threshold in the report; here, `repository.full_name`, i.e. "the repository that is written") is never covered by the check that is supposed to bind trust ("organization that authenticated"). The binding `organization_used_for_signature == organization_owning(full_name)` is assumed but never enforced.

### Impact Explanation
An attacker who can get any one organization onboarded onto a multi-org Shipit instance without a `webhook_secret` configured for it (an explicitly supported/optional configuration per the docs), or who otherwise knows/controls the webhook secret for *any single* organization served by the instance, can forge a POST to `/webhooks` whose `repository.owner.login`/`organization.login` names that low-trust organization (so signature verification passes or is skipped) while `repository.full_name` names an arbitrary repository belonging to *any other, unrelated organization* configured on the same Shipit instance. This lets the attacker drive `PushHandler` (triggering `stack.sync_github`), the `pull_request` handlers (archiving/unarchiving review stacks, mutating captured labels, updating stored PR state) and other handlers against a victim organization's stacks, without ever presenting a valid signature for that victim organization — a cross-repository write across a trust boundary the engine is supposed to enforce (matches the "cross-repository writes" / "unauthorized deploy, rollback" Critical/High impact category).

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` (documented as optional) or whose secret is otherwise known/weak to the attacker — a realistic operational misconfiguration rather than a hypothetical one, since the feature and the optional-secret behavior are both intentionally supported by the code and documentation. No privileged Shipit session, `ApiClient` token, or GitHub write access is needed; only the ability to POST to the public `/webhooks` endpoint.

### Recommendation
After (or as part of) signature verification, require that the `repository.owner.login` (the organization used to select/verify the webhook secret) matches the owner segment of `repository.full_name` before dispatching to handlers, and reject mismatched payloads. Do not treat a per-organization `webhook_secret` as optional for organizations sharing a Shipit instance with others, or fail closed when it is absent instead of returning `true`.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `victim-org` (has a real `webhook_secret`) and `attacker-org` (deployed without a `webhook_secret`, e.g. left blank per the documented optional setting).
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` for `victim-org`, and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and invokes `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — a write triggered without ever authenticating against `victim-org`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
