I have sufficient evidence to write up the finding.### Title
Unbounded `in data feed` / `in_data_feed` existence check enables per-unit validation DoS via oracle-controlled data feed history - ([File: data_feeds.js])

### Summary
The `in data feed` address/asset spending condition [1](#0-0)  and the `in_data_feed` AA formula function [2](#0-1)  both call `dataFeeds.dataFeedExists` → `dataFeedByAddressExists` with a caller-controlled, un-bounded-by-default `min_mci` (`args[4] || 0` in the definition path, `min_mci = 0` by default in the formula path). For any relation other than `=` (`>`, `>=`, `<`, `<=`, `!=`), `dataFeedByAddressExists` streams the LevelDB/RocksDB key range ordered by **value**, not by MCI, and only filters by `[min_mci, max_mci]` inside the per-record callback [3](#0-2) . Because the key ordering is value-first, the scan cannot terminate early based on MCI proximity — it must walk every historical record matching the value comparison for that oracle/feed pair until a record within the MCI window is found or the whole range is exhausted, exactly analogous to the reported `TargetEpoch=0` issue where "the longer the chain is around, the more work responding to a query like this will take."

### Finding Description
This condition is directly reachable by an unprivileged party in two ways:
1. As a spending/authentication condition on any address or private asset definition (`in data feed`), validated in `definition.js` and evaluated at `evaluate('in data feed', ...)` [1](#0-0) , which is exercised whenever a unit signed/authorized by that definition is posted and validated by every full node.
2. As an AA formula construct (`in_data_feed[[...]]`), evaluated by `formula/evaluation.js` [4](#0-3) , reachable by anyone who triggers an AA that uses this construct.

An attacker acting as the "oracle" address referenced in the condition can post a large number of `data_feed` messages under one `feed_name` over a long time span with values chosen so that the target relation (e.g. `>` a very low threshold) matches nearly the entire history. When a unit (or AA trigger) later evaluates `in data feed`/`in_data_feed` against that oracle+feed with `min_mci` at or near the top of the range (or simply not satisfiable), `dataFeedByAddressExists` must stream through the entire (attacker-inflated) set of matching value-keys, checking the MCI of every record, before it can conclude "not found" [5](#0-4) . Multiple oracle addresses can be listed in `arrAddresses`, and `dataFeedExists`/`readDataFeedValue` iterates them serially with `async.eachSeries`, multiplying the cost [6](#0-5) .

Crucially, the static complexity/op-count limits enforced during validation (`constants.MAX_COMPLEXITY`, `constants.MAX_OPS` in `definition.js`'s `evaluate` [7](#0-6) , and the analogous formula validation in `formula/validation.js` [8](#0-7) ) only count the number of `in data feed`/`in_data_feed` op occurrences (plus a small per-oracle-address increment), not the actual size of the historical KV range that must be scanned at evaluation time. The fee paid for the unit does not scale with this cost, so a single cheap unit or AA trigger can force every validating full node to perform an expensive, unbounded key-stream scan.

### Impact Explanation
This is not a single-server RPC DoS as in the report — it is a **validation-time DoS reachable by any unprivileged unit poster or AA trigger sender**, meaning the computational cost is imposed on every full node in the network that validates the unit, not just an optional public API consumer. Repeated posting of such units/AA triggers can significantly degrade the ability of full nodes to process and validate new units in a timely manner, which maps to "a network unable to confirm new units" in a degraded/delayed sense. It qualifies as Medium risk because it is a computational-amplification/DoS vector rather than direct fund loss, but it is broader in blast radius than the original report (affects consensus-critical validation on all nodes, not one RPC endpoint).

### Likelihood Explanation
The attack requires only:
- Control of an "oracle" address (trivial — any address can be an oracle; no special permission needed).
- Ability to post many `data_feed` unit messages over time (normal network usage, cheap).
- Ability to post a single unit whose spending condition includes `in data feed`, or an AA that uses `in_data_feed` — both standard, publicly documented oscript/AA features.

No special privileges, timing, or race conditions are required; the attacker fully controls both the data-feed history shape and the query that triggers the scan.

### Recommendation
- Bound the amount of work `dataFeedByAddressExists` can do per call, e.g. by adding a `limit` to the underlying `kvstore` stream and treating results beyond the limit as "not found/inconclusive → reject", or by re-keying data feed entries so they can be range-scanned by MCI directly for non-equality relations.
- Charge complexity/ops proportional to actual stream iterations (e.g., increment `count_ops`/complexity based on `count_before_found`/`count` returned from `dataFeedByAddressExists`, similar to how other constructs scale cost with argument counts, e.g. `arrAddresses.length` in `definition.js` line 418).
- Consider requiring `min_mci` to be mandatory (not defaulting to `0`) and/or enforcing a maximum lookback window (`max_mci - min_mci`) for `in data feed`/`in_data_feed` conditions, analogous to bounding `TargetEpoch` in the original report.

### Proof of Concept
1. Attacker controls oracle address `O`.
2. Over an extended period, `O` posts thousands of `data_feed` units with `feed_name = "F"` and values alternating just above/below a threshold `T`, all with `sequence='good'`.
3. Attacker posts a unit whose address definition (or an AA it triggers) contains:
   `['in data feed', [['O'], 'F', '>', T]]` (definition.js) or `in_data_feed[[oracles="O", feed_name="F", feed_value>T]]` (AA formula), with no `min_mci` (defaults to 0) so the "not found" path is likely, forcing a full scan.
4. Every node validating that unit executes `dataFeedByAddressExists` [9](#0-8) , which streams through the full set of `O`/`F` value-keys built up in step 2 before returning a result, consuming disproportionate CPU/I/O relative to the fee paid for the single triggering unit.

	if (relation === '!='){
		// comparison only makes sense within the same type, otherwise 'abc' != 123 but we don't want to say that they are not equal, because they are incomparable
		return dataFeedByAddressExists(address, feed_name, '>', value, min_mci, max_mci, function(bFound){
			if (bFound)
				return handleResult(true);
			dataFeedByAddressExists(address, feed_name, '<', value, min_mci, max_mci, handleResult);
		});
	}
	var prefixed_value;
	var type;
	if (typeof value === 'string'){
		var bLimitedPrecision = (max_mci < constants.aa2UpgradeMci);
		var float = string_utils.toNumber(value, bLimitedPrecision);
		if (float !== null){
			prefixed_value = 'n\n'+string_utils.encodeDoubleInLexicograpicOrder(float);
			type = 'n';
		}
		else{
			prefixed_value = 's\n'+value;
			type = 's';
		}
	}
	else{
		prefixed_value = 'n\n'+string_utils.encodeDoubleInLexicograpicOrder(value);
		type= 'n';
	}
	var strMinMci = string_utils.encodeMci(min_mci);
	var strMaxMci = string_utils.encodeMci(max_mci);
	var key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value;
	var bFound = false;
	var options = {};
	switch (relation){
		case '=':
			options.gte = key_prefix+'\n'+strMaxMci;
			options.lte = key_prefix+'\n'+strMinMci;
			options.limit = 1;
			break;
		case '>=':
			options.gte = key_prefix;
			options.lt = 'df\n'+address+'\n'+feed_name+'\n'+type+'\r';  // \r is next after \n
			break;
		case '>':
			options.gt = key_prefix+'\nffffffff';
			options.lt = 'df\n'+address+'\n'+feed_name+'\n'+type+'\r';  // \r is next after \n
			break;
		case '<=':
			options.lte = key_prefix+'\nffffffff';
			options.gt = 'df\n'+address+'\n'+feed_name+'\n'+type+'\n';
			break;
		case '<':
			options.lt = key_prefix;
			options.gt = 'df\n'+address+'\n'+feed_name+'\n'+type+'\n';
			break;
	}
	var count = 0;
	var count_before_found = 0;
	var handleData;
	if (relation === '=')
		handleData = function(data){
			count++;
			count_before_found++;
			bFound = true;
		};
	else
		handleData = function(data){
			count++;
			if (bFound)
				return;
			count_before_found++;
			var mci = string_utils.getMciFromDataFeedKey(data);
			if (mci >= min_mci && mci <= max_mci){
				bFound = true;
				console.log('destroying stream prematurely');
				stream.destroy();
				onEnd();
			}
		};
	var bOnEndCalled = false;
	function onEnd(){
		if (bOnEndCalled)
			throw Error("second call of onEnd");
		bOnEndCalled = true;
		console.log('data feed by '+address+' '+feed_name+relation+value+': '+bFound+', '+count_before_found+' / '+count+' records inspected');
		handleResult(bFound);
	}
	var stream = kvstore.createKeyStream(options);
	stream.on('data', handleData)
	.on('end', onEnd)
	.on('error', function(error){
		throw Error('error from data stream: '+error);
	});
}
