### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, letting an attacker who controls one configured GitHub organization's webhook secret forge events for a completely different repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the inbound HMAC signature against using an attacker-controlled JSON field (`repository.owner.login` or `organization.login`), then hands the *entire raw, attacker-supplied payload* to event handlers. Those handlers, however, resolve the repository/stack to act on using a **different** field from the same payload: `repository.full_name` (`Handler#repository_name`), or, in the case of `StatusHandler`, no repository scoping at all. Because the field used to pick the verifying secret is not the same field used to determine what gets written, an attacker who legitimately controls one org's webhook secret in a multi-tenant Shipit deployment can forge a validly-signed webhook whose "owner" field points to their own org (so signature verification passes) while its "repository" / "sha" fields target another org's stack or commit.

### Finding Description
`WebhooksController#verify_signature` computes the verifying app/secret from an unauthenticated payload field: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` just checks the HMAC of the raw body against whichever org's secret was selected above: [3](#0-2) 

After the signature check passes, `WebhooksController#create` hands the *same untouched raw payload* to all handlers registered for the event: [4](#0-3) 

But `Handler#stacks`/`#repository_name`, used by `PushHandler` and `CheckSuiteHandler`, resolve the target repository from a *different* JSON field, `repository.full_name`, with no cross-check against the `repository.owner.login`/`organization.login` value used for signature selection: [5](#0-4) [6](#0-5) [7](#0-6) 

`StatusHandler` is worse: it does not scope by repository at all - it matches any `Commit` in the entire Shipit database by raw `sha`: [8](#0-7) 

This breaks the trust binding the engine relies on: **the organization whose secret authenticated the request must equal the repository the request is allowed to affect**. Since `Shipit.github(organization:)` supports multiple independently-configured organizations, each with its own `webhook_secret`, as documented in `config/secrets.development.example.yml` and `docs/setup.md`, a party who legitimately administers (and thus knows the webhook secret of) *one* configured organization is, with respect to *other* organizations hosted on the same Shipit instance, an unprivileged attacker. That attacker can:
1. Craft an arbitrary JSON payload with `repository.owner.login` (or `organization.login`) set to their own org, and `repository.full_name`/`sha` set to point at a victim stack/commit belonging to a different configured org.
2. Sign the raw body with their own known `webhook_secret`.
3. POST it to the shared `/webhooks` endpoint; `verify_signature` looks up and validates against their own org's secret and passes.
4. The handler then acts on the victim's repository/commit data embedded in the same payload, e.g. triggering `stack.sync_github` for an arbitrary `expected_head_sha` (`PushHandler`), scheduling check-run refresh for an arbitrary stack/branch (`CheckSuiteHandler`), or - most severely - injecting a forged CI status onto any commit in the entire install matched purely by `sha` (`StatusHandler`) with no ownership check whatsoever.

### Impact Explanation
A forged `status` event via `StatusHandler#process` creates a `Status` record on a victim commit via `Commit#create_status_from_github!`, which recomputes `Commit#status` and, on a state transition to `success`, calls `stack.schedule_merges` and fires `deployable_status`/`commit_status` hooks: [9](#0-8) 

Since `Commit#deployable?` depends on `success?` (derived from these forged statuses) and gates continuous deployment/merges (`Commit#schedule_continuous_delivery`, `deployable?`): [10](#0-9) [11](#0-10) 

an attacker who only controls one tenant's org secret can push a fabricated "success" CI status onto a victim's stack's commit, unblocking that commit for merge/continuous-deployment consideration in the victim's org - an unauthorized-deploy-adjacent, cross-repository write that meets the "unauthorized deploy/rollback" and "cross-repository writes" impact bar.

### Likelihood Explanation
This requires a multi-tenant Shipit deployment where more than one GitHub organization is configured (a documented, supported configuration per `config/secrets.development.example.yml`/`docs/setup.md`), and requires the attacker to know only their own org's webhook secret - something any legitimate admin of one tenant already has. No `ApiClient` token, GitHub App private key, TLS interception, or Shipit session is needed; the webhook endpoint is unauthenticated aside from the (misapplied) HMAC check. Likelihood is moderate: it is gated on multi-org configuration but requires no privilege beyond controlling one's own tenant.

### Recommendation
After signature verification succeeds for organization `O`, the handler layer must re-validate that `repository.full_name`'s owner (and, where used, the `sha`'s owning stack) actually belongs to organization `O` before acting - i.e., bind the field trusted for authentication to the field trusted for the write. At minimum, `StatusHandler` should scope its `Commit.where(sha:)` lookup to commits belonging to stacks under the verified organization, and `Handler#repository_name` should be cross-checked against the organization used in `verify_signature`.

### Proof of Concept
1. Configure Shipit for two orgs, `attacker-org` (attacker is the legitimate GitHub App admin, knows its `webhook_secret`) and `victim-org` (unrelated, tracked stack `victim-org/victim-repo` with commit `deadbeef...`).
2. Attacker crafts body:
```json
{
  "action": "success",
  "sha": "deadbeef000000000000000000000000000000",
  "state": "success",
  "context": "ci",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker_webhook_secret, body)>`.
4. Attacker sends `POST /webhooks` with `X-Github-Event: status` and the above signature.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully (attacker's own secret matches). [1](#0-0) 
6. `StatusHandler#process` runs unscoped `Commit.where(sha: "deadbeef...")`, finds the victim's commit, and creates a forged `success` status, potentially unblocking merges/deploys on `victim-org`'s stack. [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
