## Finding: Multisig transaction execution payload is not verified against the on-chain approved payload unless a feature flag is enabled

### Title
Multisig executor can substitute an unapproved execution payload when `abort_if_multisig_payload_mismatch_enabled` is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the function the VM calls during transaction admission (mempool prologue and first step of execution) for multisig-account transactions, only checks that the `payload` argument supplied by the executor matches the on-chain approved payload when both `features::abort_if_multisig_payload_mismatch_enabled()` is true and the supplied `payload` is non-empty. [1](#0-0)  If a `MultisigTransaction` was created with the full payload stored on-chain via `create_transaction` (as opposed to `create_transaction_with_hash`), owners vote to approve that specific stored `payload`. [2](#0-1) 

### Finding Description
`validate_multisig_transaction` performs two distinct payload-integrity checks:

1. Hash-based transactions (`payload_hash.is_some()`): the executor-supplied `payload` is always required to hash to the stored `payload_hash` — this check is unconditional. [3](#0-2) 
2. Full-payload transactions (`transaction.payload.is_some()`, created via `create_transaction`): the executor-supplied `payload` is only compared against the stored `payload` if the feature `abort_if_multisig_payload_mismatch_enabled` is turned on **and** the supplied `payload` is non-empty. [1](#0-0) 

Everything else that admission enforces — owner membership, quorum (`num_approvals >= num_signatures_required`), and the timelock — validates that *a* transaction at the given sequence number was approved, but does not itself bind the approval to the exact bytes that will be dispatched for execution when this feature is off. [4](#0-3)  The gate's very existence (a dedicated feature flag named `abort_if_multisig_payload_mismatch_enabled`) indicates that prior to/without this flag, the execution-time payload argument was not being checked against the payload that owners actually voted on.

This directly parallels the BeefyAdapter bug-class: an unvalidated/attacker-controlled input (`_beefyBooster` there, the execution-time `payload` argument here) is trusted at the point where privileged action is taken, because the validating code assumes — without checking (or checks only conditionally) — that it matches the entity/data that was actually authorized.

### Impact Explanation
If this feature flag is not enabled on a given network/at a given point in time, any owner with sufficient standing to invoke the executing entry function for a full-payload `MultisigTransaction` could supply a `payload` different from the one that was actually voted on by the required quorum of owners, and admission would not reject it. This would let a transaction that should fail admission (wrong/unapproved payload) execute and commit under the multisig account's authority — i.e., unauthorized execution of code that was never approved by the required signer set, which is exactly the class of "approval-set confusion" impact called out in the Admission Impact Gate.

### Likelihood Explanation
Likelihood depends entirely on the current on-chain/default state of the `abort_if_multisig_payload_mismatch_enabled` feature flag, which I was not able to confirm within the scope of this investigation (I found only the flag's definition sites in `features.move`/`aptos_features.rs` and its three call sites, but not its default/rollout status). [5](#0-4)  I also was not able to fully trace, within the remaining iterations, whether the VM's actual dispatch of the target function uses this same `payload` argument or independently re-reads the stored payload from chain state for execution — that distinction determines whether the check is a hard security boundary or a redundant sanity check. Given the explicit gating and comment describing it as protecting against payload substitution, it is very likely the former, but this should be verified directly against `aptos-move/aptos-vm/src/aptos_vm.rs`'s multisig dispatch path before treating this as conclusively exploitable.

### Recommendation
- Confirm whether `abort_if_multisig_payload_mismatch_enabled` is enabled by default / already rolled out network-wide; if not, prioritize enabling it, since it is the only guard preventing payload substitution for full-payload multisig transactions.
- Consider removing the feature gate entirely (making the payload-match check unconditional, analogous to the hash-based path) once backward-compatibility concerns are resolved, so admission always binds the executed payload to the approved one regardless of feature-flag state.
- Independently verify in `aptos-move/aptos-vm/src/aptos_vm.rs` that the same `payload` bytes validated in `validate_multisig_transaction` are the ones actually dispatched for execution, to close the gap between what was analyzed here and full end-to-end proof.

### Proof of Concept
1. Owner A creates a multisig transaction with `create_transaction(owner, multisig_account, payload_A)`, storing `payload_A` fully on-chain (not a hash). [2](#0-1) 
2. The required quorum of owners calls `approve_transaction` to vote yes, believing they are approving `payload_A`. [6](#0-5) 
3. On a network/period where `abort_if_multisig_payload_mismatch_enabled` is disabled, an executing owner submits the transaction with `payload_B` (a different, unapproved payload) instead of `payload_A`.
4. `validate_multisig_transaction` checks owner membership, quorum, and timelock (all satisfied, since they are payload-independent), then skips the stored-payload-equality check entirely because the feature is off. [1](#0-0) 
5. If the VM subsequently dispatches based on `payload_B` (unconfirmed — see Likelihood Explanation), `payload_B` executes under the multisig account's authority despite never having received the required approvals.

**Caveat:** This finding is reported with the confidence level supportable by the code I was able to inspect in the available iterations. The critical unresolved question — whether the VM execution path actually uses the unchecked `payload` argument for dispatch, and the current default state of the gating feature flag — should be verified before treating this as a confirmed, exploitable vulnerability.
