### Title
Unauthenticated multisig-wallet state injection via whitelisted `my_xpubkey` / `wallet_fully_approved` device messages - (File: device.js / wallet.js / wallet_defined_by_keys.js)

### Summary
`NetAlertX` allowed unauthenticated requests to reach sensitive `util.php` functions because the code failed to enforce that the caller had a trusted session. In `ocore`, the analogous trust boundary is the hub-relayed "device message" channel: a message is normally only processed if the sender is a known, paired `correspondent_devices` entry. However, `device.js` explicitly whitelists the subjects `"pairing"`, `"my_xpubkey"`, and `"wallet_fully_approved"` to be dispatched **even when the sender is not a known correspondent at all**, and the corresponding handlers in `wallet_defined_by_keys.js` never verify that the sending device is an actual, intended cosigner of the target multisig wallet before mutating wallet state.

### Finding Description
In `device.js`, `handleJustsaying` processes `hub/message`: [1](#0-0) 
Any device that is cryptographically valid (i.e., possesses *some* keypair — trivial to generate, no pairing/approval required) but is **not** a known correspondent of the victim can still have its message dispatched for the subjects `pairing`, `my_xpubkey`, and `wallet_fully_approved`.

`my_xpubkey` is routed to `walletDefinedByKeys.addDeviceXPubKey`: [2](#0-1) [3](#0-2) 
This function performs `INSERT IGNORE INTO extended_pubkeys (wallet, device_address)` followed by `UPDATE ... SET extended_pubkey=?, approval_date=NOW()`, **without any check that `device_address` (derived solely from the attacker's own self-chosen keypair) is one of the devices actually listed in the wallet's `wallet_signing_paths` / definition template**. The only gating that exists for legitimate cosigner membership (`validateWalletDefinitionTemplate`, called from `handleOfferToCreateNewWallet`) is bypassed entirely for this code path.

Likewise `wallet_fully_approved` is routed to `handleNotificationThatWalletFullyApproved`, which also blindly inserts/updates a row for the caller-controlled `device_address` and then calls `checkAndFinalizeWallet`: [4](#0-3) [5](#0-4) 

`checkAndFullyApproveWallet`/`checkAndFinalizeWallet` use a **row-existence query joined against `extended_pubkeys`** (`SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallet=?`) to decide readiness. Because an attacker can inject an arbitrary extra row keyed by `(wallet, attacker_device_address)` into `extended_pubkeys` for **any wallet hash it can obtain** (the wallet id is `sha256(xPubKey)`, transmitted in cleartext-adjacent chat/contract flows such as `arbiter_contract.js`'s pairing codes and prosaic/arbiter contract text markers), it corrupts the bookkeeping table that is the sole source of truth for "who is a legitimate cosigner of this shared wallet" — used later by `readCosigners` (`wallet_defined_by_keys.js:395-413`), which even `throw`s an unguarded `Error` when it finds a device that "should" be a correspondent but isn't, since it never anticipated foreign, unauthenticated rows being present.

This mirrors the root cause of CVE-2025-32440: a sensitive state-mutating function reachable through a message path that was intended to require prior authentication/relationship establishment, but which an explicit allow-list bypasses for specific message subjects, and the downstream handler performs no additional authorization check to compensate.

### Impact Explanation
An attacker who is not paired with, or known to, the victim can:
- Corrupt the `extended_pubkeys` table for any multisig wallet-in-progress they can identify the wallet-hash of, interfering with the legitimate multi-party wallet approval/finalization protocol (denial of the wallet-creation flow for real cosigners, or triggering an unhandled `throw Error` in `readCosigners` when a real cosigner tries to enumerate cosigners of a wallet the attacker polluted — a code path with no `try/catch`, capable of crashing the wallet process).
- This is a genuine authentication-boundary bypass matching the CVE's bug class (sensitive multi-party wallet functions reachable without any prior authenticated relationship), but the concrete on-chain consequence (unauthorized spend / stable-output double-spend / supply inflation) is **not established** by this code path alone — actually spending funds still requires the real cosigners to independently approve/sign, which the polluted row does not bypass. I was not able to fully trace whether the injected/attacker-approved row can ever cause `checkAndFullyApproveWallet`/`checkAndFinalizeWallet` to fire prematurely for a *legitimate* wallet before all real cosigners are ready (the join semantics appeared to only add an already-approved extra row rather than remove the requirement for real members), so the most severe consequences (fund loss) remain unproven with the available evidence.

### Likelihood Explanation
Reachable by any party who can establish a hub-relayed device message and knows/guesses a target wallet-id — no pairing or prior trust relationship is required for these three subjects. Likelihood of triggering the code path is high; likelihood of achieving a *concretely quantified* financial-impact outcome (vs. state corruption / crash) is unproven from the code reviewed.

### Recommendation
For `my_xpubkey` and `wallet_fully_approved`, before touching `extended_pubkeys`, verify that `device_address` is actually listed in `wallet_signing_paths` (or the wallet's stored `definition_template`) for the given `wallet` id, mirroring the check already performed in `handleOfferToCreateNewWallet`/`validateWalletDefinitionTemplate`. Also wrap `readCosigners`'s invariant check in error handling instead of `throw`, so that unexpected foreign rows fail safely rather than crashing the process.

### Proof of Concept
Not fully constructable from the indexed code alone — the exploit requires driving `device.sendMessageToHub`/`handleJustsaying` with a crafted `hub/message` whose decrypted `json.subject` is `"my_xpubkey"` or `"wallet_fully_approved"` and a guessed/leaked `wallet` id, from a device address that has never paired with the victim. I could not verify from available files whether this concretely escalates to fund loss (vs. state corruption/DoS), so I flag this analog with **medium confidence** rather than presenting it as a fully proven critical fund-loss vulnerability.

function checkAndFinalizeWallet(wallet, onDone){
	db.query("SELECT member_ready_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0){ // wallet not created yet or already deleted
		//	throw Error("no wallet in checkAndFinalizeWallet");
			console.log("no wallet in checkAndFinalizeWallet");
			return onDone ? onDone() : null;
		}
		if (rows.some(function(row){ return !row.member_ready_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET ready_date="+db.getNow()+" WHERE wallet=? AND ready_date IS NULL", [wallet], function(){
			if (onDone)
				onDone();
			eventBus.emit('wallet_completed', wallet);
		});
	});
}

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()], 
						function(rows){
							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet
							rows.forEach(function(row){
								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});
}
