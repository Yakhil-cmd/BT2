## Analysis Result

### Title
Unbounded per-address conflicting-unit scan enables a DAG-wide DoS analogous to Nomad's `improperUpdate()` queue scan - (File: `validation.js`)

### Summary
The Nomad bug lets an unprivileged actor grow an on-chain queue that `improperUpdate()` must linearly scan (`queue.contains`), making every future validity check cost O(n) and letting the attacker degrade availability cheaply. Ocore has a structurally identical pattern in `validateAuthor()`'s `findConflictingUnits()`: any unprivileged unit poster can create many mutually-conflicting ("nonserial") pending units from a single address, and every one of those units must be scanned and graph-walked on each subsequent validation touching that address, before the DAG stabilizes them.

### Finding Description
`findConflictingUnits()` in [1](#0-0)  queries all unstable (and recently-stable) units authored by the same address as the unit under validation, then iterates over every returned row with `async.eachSeries`, calling `graph.determineIfIncludedOrEqual()` for each one to decide whether it's a real competitor. `determineIfIncludedOrEqual`/`determineIfIncluded` themselves perform a possibly multi-hop DAG traversal (`goUp` loops, DB queries per level) as seen in [2](#0-1) .

This is directly analogous to Nomad's `contains()`/`improperUpdate()`: a single unprivileged party (any address owner) can post an unbounded number of pending, mutually conflicting units from that address (each individually valid enough to enter the DAG as `sequence='temp-bad'`/non-serial units) and there is no cap found in `validation.js` on how many unstable competing units per address can accumulate before stabilization. Each new unit authored by (or referencing) that address then re-triggers `findConflictingUnits()` and a `graph.determineIfIncludedOrEqual()` call per accumulated competitor, so the validation cost for that address grows linearly (compounded by graph-walk cost) with the number of conflicting units the attacker has queued.

Because `validate()` serializes work per author address via `mutex.lock(arrAuthorAddresses, ...)` ( [3](#0-2) ) and `mutex.js`'s FIFO queuing ( [4](#0-3) ), a slow validation for one address's history also delays queued validations that share that address lock, compounding the effect on units related to the victim address.

The identical shape appears in `checkForDoublespends()` ( [5](#0-4) ) which likewise `async.eachSeries` over all conflicting input rows and calls `graph.determineIfIncludedOrEqual` for each — an attacker spending the same output/asset serial number from many conflicting nonserial units similarly inflates the scan for every future validation involving that output/serial number, and `findStableConflictingUnits()` in `main_chain.js` does the same during stabilization ( [6](#0-5) ).

### Impact Explanation
By repeatedly posting units from (or paying into/spending from) a single address that all conflict with each other (double-spending the same author address, or spending/issuing the same output/asset serial repeatedly), an attacker inflates the number of DAG competitors that must be graph-walked on every future validation touching that address/output. Because these per-unit checks run under the per-author `mutex` lock, this can materially slow down confirmation of legitimate units competing for the same address/lock, degrading the node's — and potentially the network's — ability to validate and confirm new units in a timely manner, mirroring the "network unable to confirm new units" impact category from the source report.

### Likelihood Explanation
Any unprivileged party can trigger this: posting many nonserial units from one address (or with conflicting inputs) requires only enough bytes/fees to pay for unit issuance, no special permission is needed, and the accumulation of unstable conflicting units is entirely attacker-controlled until MC stabilization catches up. The cost to Ocore for each subsequent unit-validation event however grows with the size of the attacker-built conflict set, similar to Nomad's queue-growth attack, and there is no explicit cap in `findConflictingUnits()`/`checkForDoublespends()` limiting the number of unstable conflicting competitors per address that can accumulate before stabilization bounds it.

### Recommendation
Introduce an explicit, cheap-to-check cap on the number of unstable, conflicting ("temp-bad"/nonserial) units permitted per address (or per output/serial-number key) before further conflicting units from that address are rejected outright, similar in spirit to Nomad's fix of removing the linear queue scan. Alternatively, replace the O(n) `async.eachSeries` + graph-walk pattern with an indexed/pre-computed structure (e.g., persisting the minimal set of currently-live competitors per address) so that adding a new conflicting unit does not require re-walking all previously known competitors on every subsequent validation.

### Proof of Concept
1. Attacker controls address `A`.
2. Attacker crafts and posts many valid-but-mutually-conflicting units authored by `A` in parallel forks (each spends/reuses the same prior output or otherwise conflicts), so they all enter the DAG as pending, non-finalized ("temp-bad"/nonserial) units — `findConflictingUnits()` accepts such units as long as they aren't yet excluded (`sequence!='final-bad'`), see [7](#0-6) .
3. Each new legitimate unit authored by, or spending from, address `A` now triggers `findConflictingUnits()`/`checkForDoublespends()`, which must `async.eachSeries` over all N accumulated conflicting rows and call `graph.determineIfIncludedOrEqual()` (a DAG traversal) for each, per [8](#0-7) .
4. As N grows, validation time for units touching `A` grows correspondingly, and because validation for address `A` is serialized via `mutex.lock(arrAuthorAddresses, ...)` ( [3](#0-2) ), other units queued behind that lock are delayed as well, degrading confirmation throughput for that address's activity — the DAG-native analog of Nomad's queue-growth DoS.

		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
