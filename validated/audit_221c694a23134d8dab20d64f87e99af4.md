## Title
Numeric governance parameters (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) can be changed at the very next MCI by any single vote-count triggering unit, with no timelock and no cooldown - unlike the equivalent `op_list` mechanism - ([File: main_chain.js])

### Summary
Ocore has a decentralized "system vote" mechanism that lets token holders vote on protocol-wide parameters, and any unprivileged unit author can post a `system_vote_count` message to trigger tallying of the currently cast votes. For the `op_list` subject, the protocol explicitly protects against instant/abusive recomputation with a mandatory cooldown (`EMERGENCY_OP_LIST_CHANGE_TIMEOUT`). No equivalent cooldown exists for the numeric subjects (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`), so any user can force these fee-governing parameters to change, and the new value takes effect starting at the very next MCI with zero advance warning — the exact "instant governance parameter change" pattern flagged in the external report.

### Finding Description
`system_vote_count` is validated as an ordinary message any non-AA unit author may include, with the only restrictions being one-per-unit and a known subject name: [1](#0-0) 

When the containing unit stabilizes, `countVotes()` is invoked for the requested subject and immediately recomputes and stores the new value: [2](#0-1) [3](#0-2) 

The new value is recorded with `vote_count_mci = mci`, and per the schema comment this value "applies since the next mci" — i.e., it is live essentially immediately, not after any grace period: [4](#0-3) 

By contrast, the protocol authors clearly recognized that instant application of a similarly-triggerable change (the `op_list`/witness change) is dangerous, and specifically added a cooldown before an emergency recount can be applied: [5](#0-4) 

No analogous delay exists for the numeric subjects’ ordinary (non-emergency) `system_vote_count` path — `countVotes` for `threshold_size`/`base_tps_fee`/`tps_interval`/`tps_fee_multiplier` is called unconditionally as soon as the triggering unit is stable, with no minimum time since the last count.

These parameters have direct, nonlinear effects on required fees:
- `threshold_size` controls the oversize fee via an exponential formula: `Math.ceil(size * (exp(size / threshold_size - 1) - 1))` [6](#0-5) 
- `base_tps_fee`, `tps_interval`, `tps_fee_multiplier` control the TPS fee similarly, and insufficient `tps_fee` causes hard validation failure (not merely a warning) for the balance-derived check: [7](#0-6) 

Because the median-of-votes value can jump sharply (e.g. `threshold_size` dropping suddenly makes previously "free" unit sizes suddenly incur an exponentially growing oversize fee, or `base_tps_fee`/`tps_fee_multiplier` spiking makes previously-adequate `tps_fee` insufficient), any unit whose `last_ball_mci` lands on or after the new `vote_count_mci` is validated against the new, unannounced parameter. Ordinary users, AAs relying on stable fee assumptions (e.g. payment-channel or bounce-fee AAs sized to a known bounce fee), and wallets that pre-compute fees have no window to adapt.

### Impact Explanation
- Legitimate units composed under the old parameters can fail hard validation (`"tps_fee ... less than required"`, `"oversize_fee mismatch"`) once a triggered vote count changes the effective parameter at the next MCI, causing broadcast/inclusion failures and wasted composition/broadcast effort for ordinary users.
- AAs and oscript logic that hard-code assumptions about `bounce_fees`/oversize thresholds (see `bounce_fees` usage in AA responses) can start bouncing or failing unexpectedly when the oversize/tps fee schedule jumps, freezing expected fund flows.
- Because the change is deterministic on `last_ball_mci` and takes effect at the very next MCI, there is no window (days, as the original report recommends) for wallets/AA authors to adjust, unlike the intentionally-delayed `op_list` emergency path.

This matches "AA fund loss/freezing" and "node disagreement" adjacent categories: nodes agree on validity by protocol rules, but the sudden parameter shift produces unexpected unit rejections/AA bounces for actors who had no way to anticipate the change.

### Likelihood Explanation
Any address that has previously cast a `system_vote` (even a small stake, as long as votes exist for the subject) is eligible to be counted; any unprivileged unit author (holder or not) can pay `SYSTEM_VOTE_COUNT_FEE` and post `system_vote_count` at any time to force a recount, with no rate limiting comparable to `EMERGENCY_OP_LIST_CHANGE_TIMEOUT`. Given normal operation of the network (votes naturally accumulate over time as per `initial_votes.js` and ongoing `system_vote` messages), triggering a recount that shifts a numeric parameter is straightforward and requires no special privilege — it is directly reachable by a single unprivileged unit poster.

### Recommendation
Introduce a mandatory activation delay (analogous to `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` for `op_list`) before a newly-counted numeric system var (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) becomes effective — e.g., set `vote_count_mci` (or a new `effective_mci`) several thousand MCIs (multi-day equivalent) in the future rather than the immediately-following MCI, and/or enforce a minimum interval between successive `system_vote_count` calls for the same subject to prevent rapid oscillation and give users/wallets/AAs advance notice to adapt.

### Proof of Concept
1. Wait until at least one address has cast a `system_vote` for, say, `threshold_size` with a value far below the current effective value (this can happen naturally over time as votes accumulate; validation only requires `payload.value >= 1000`, see `validation.js:1884-1890`).
2. Any unprivileged address posts a `system_vote_count` unit for subject `threshold_size` (paying `SYSTEM_VOTE_COUNT_FEE`); validation only checks the subject name and one-per-unit, `validation.js:1913-1923`.
3. Once this unit stabilizes, `countVotes()` recomputes the balance-weighted median and stores it with `vote_count_mci = mci`, `main_chain.js:1878-1912`.
4. Starting at MCI `vote_count_mci + 1`, `storage.getOversizeFee()` uses the new, much lower `threshold_size`, causing units of previously-acceptable size to suddenly owe a large oversize fee they did not budget for (`storage.js:1147-1165`), producing `"oversize_fee mismatch"` rejections (`validation.js:768-776`) for units whose authors had no warning of the change.

function getOversizeFee(objUnitOrSize, mci, bAA) {
	let size;
	if (typeof objUnitOrSize === "number")
		size = objUnitOrSize; // must be already without temp data fee
	else if (typeof objUnitOrSize === "object") {
		if (!objUnitOrSize.headers_commission || !objUnitOrSize.payload_commission)
			throw Error("no headers or payload commission in unit");
		// AA-generated units pay the oversize fee based on the unit size excluding its payment messages to avoid swelling the fee while spending dust outputs
		const payload_commission = (bAA && mci >= constants.pemCurvesFixMci)
			? objectLength.getTotalPayloadSize({ ...objUnitOrSize, messages: objUnitOrSize.messages.filter(message => message.app !== 'payment') })
			: objUnitOrSize.payload_commission;
		size = objUnitOrSize.headers_commission + payload_commission - objectLength.getPaidTempDataFee(objUnitOrSize);
	}
	else
		throw Error("unrecognized 1st arg in getOversizeFee");
	const threshold_size = getSystemVar('threshold_size', mci);
	if (size <= threshold_size)
		return 0;
	return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
