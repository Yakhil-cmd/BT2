When the top-level `/api/hooks` route is hit, `params[:stack_id]` is never present, so `stack_id` evaluates to `nil` and `hooks` becomes `Hook.where(stack_id: nil)` — i.e., the **global** hooks collection (`Hook.scoped_to`/`global` semantics defined in `app/models/shipit/hook.rb:93`), regardless of which stack the authenticated `ApiClient` is authorized for.

Authorization for this controller is only `require_permission :read, :hook` / `:write, :hook` (`app/controllers/shipit/api/hooks_controller.rb:6-7`), which is checked via `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`). ### Title
Stack-scoped ApiClient tokens can create/manage global webhooks via unscoped `/api/hooks` route - (File: app/controllers/shipit/api/hooks_controller.rb)

### Summary
`Api::HooksController` computes its authorization scope (`stack_id`) from an *optional* route parameter instead of unconditionally deriving it from the authenticated `ApiClient`'s bound stack. Because `config/routes.rb` mounts `resources :hooks` both nested under a stack and again at the top level with no `stack_id` segment, a token that is only supposed to operate within its assigned stack can hit the top-level route and manage the global (`stack_id: nil`) `Hook` collection instead.

### Finding Description
`Shipit::ApiClient` supports being scoped to a single `stack_id` (`app/models/shipit/api_client.rb`), and `Api::BaseController#stacks`/`#stack` enforce that scope for every resource reached through `stack.<association>` (`app/controllers/shipit/api/base_controller.rb:74-80`). `HooksController` is the exception: it computes its own `hooks` collection directly against `Hook`, gated only by `stack_id` derived from `params[:stack_id]` (`app/controllers/shipit/api/hooks_controller.rb:46-52`). The route table exposes two entry points to this controller — `/api/stacks/*stack_id/hooks` (scoped) and `/api/hooks` (unscoped, `config/routes.rb:46`). Calling the latter means `params[:stack_id]` is absent, `stack_id` returns `nil`, and `hooks` resolves to `Hook.where(stack_id: nil)`, the global hooks used for events across all stacks (`app/models/shipit/hook.rb:93,95`). The permission check on this controller, `require_permission :read, :hook` / `:write, :hook`, only verifies the client carries that permission string (`ApiClient#check_permissions!`, `app/models/shipit/api_client.rb:38-45`); it performs no comparison between the client's authorized `stack_id` and the stack (or lack thereof) actually being written to. This breaks the equality "stack a token authorizes == stack a token touches."

### Impact Explanation
An `ApiClient` created with `write:hook` permission and a `stack_id` binding intended to limit it to one stack's webhooks can instead create, update, or delete global hooks that fire for every stack in the installation. Global hooks can point `delivery_url` at an attacker-controlled server and receive event payloads for all stacks' deploys/rollbacks/tasks/commit statuses — a cross-stack (cross-repository) write and a channel for exfiltrating operational data beyond the scope the token was provisioned for.

### Likelihood Explanation
Requires possession of a legitimately-issued `ApiClient` token with `write:hook`/`read:hook` permission (any stack-scoped token with hook permissions, not necessarily privileged). No other precondition beyond calling a documented, already-mounted route (`/api/hooks`) that is reachable exactly like the nested one.

### Recommendation
Make `HooksController#stack_id`/`#hooks` unconditionally derive the scope from `current_api_client.stack_id` (falling back to `nil` only for unscoped clients), or remove the top-level `resources :hooks` route and require all `Api::HooksController` access to go through the stack-nested path, ensuring hooks queries and mutations are always scoped consistently with the client's authorization.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ['write:hook']` and `stack_id` set to stack A.
2. Authenticate as that client and `POST /api/hooks` (top-level route, no `stack_id` in path) with a `delivery_url`, `events`, and `content_type`.
3. Observe the created `Hook` has `stack_id: nil` (verifiable via `GET /api/hooks` or `Hook.global`), meaning it now receives events for stack B, C, etc., despite the client only being authorized for stack A.
