### Title
Unauthenticated cross-repository commit-status forgery via `StatusHandler` failing to scope commits by the signature-verified repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` binds signature validity to the GitHub organization named in the payload (`repository.owner.login`), using that org's `webhook_secret` to HMAC-verify the raw request body. [1](#0-0)  This only proves the request came from a GitHub App installation for *that* organization/repository — it says nothing about which `Commit` rows the handler is allowed to mutate. `StatusHandler#process`, however, looks up commits solely by `sha` across the entire `Commit` table, with no scoping to the repository that produced the signed payload:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

By contrast, other handlers correctly scope lookups to `Repository.from_github_repo_name(repository_name)`-derived stacks via the base `Handler#stacks` helper. [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
This is the same bug class as the M-26 report: a field that is acted upon (`sha`, used to find and mutate a `Commit`) is never bound to the identity that was actually verified by the signature check (the organization/repository in `params['repository']`). The equality that should hold is:

`organization whose webhook_secret authenticated this request == repository whose commits are mutated`

`WebhooksController#verify_signature` establishes the left side (`repository_owner` from the payload picks `Shipit.github(organization: repository_owner)`, whose secret must validate the HMAC over the full raw body). [6](#0-5)  But `StatusHandler` never checks the right side: it doesn't call `stacks` or filter by `repository_name` at all — it globally matches `Commit.where(sha: params.sha)`. [2](#0-1) 

In a Shipit deployment tracking multiple organizations/repositories (explicitly documented and supported via per-organization `webhook_secret` config), [7](#0-6)  an attacker who controls (or has push/App-webhook access to) *any one* tracked repository — e.g., their own low-privilege project — can:

1. Discover a target commit `sha` in a *different* tracked repository/stack (SHAs are public git identifiers, visible on GitHub).
2. Send a legitimately-signed `status` webhook from their own repository/org (signed with their own org's valid `webhook_secret`, which passes `verify_signature` since the signature check only validates "some registered org's secret matches", not "this org owns the target commit").
3. Set `sha` to the target commit's SHA and `state` to `"success"` (or `"failure"`), with arbitrary `context`, `description`, `target_url`.
4. `StatusHandler#process` finds `Commit.where(sha: target_sha)` — which will match the row in the *victim* stack — and calls `commit.create_status_from_github!(params)`, forging a CI status/check on a commit the attacker never had signature-verified authority over. [8](#0-7) 

### Impact Explanation
Forged commit statuses directly influence deploy gating: `Commit#deployable?` requires `success?` (derived from `statuses`/`status`) unless CI is ignored, and blocking/required statuses gate deploys via `stack.blocking_statuses`/`stack.required_statuses`. [9](#0-8)  A forged `"success"` status on a target repository's malicious or otherwise CI-failing commit can make it `deployable?`, and `schedule_continuous_delivery` will even auto-trigger a deploy via `ContinuousDeliveryJob` if continuous deployment is enabled for that stack. [10](#0-9)  This is a cross-repository write (forged deployment-status state on a repository the attacker's authenticated identity does not own) that can lead to an unauthorized deploy — matching the report's High/Critical impact bar ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Likelihood is High for any Shipit instance tracking more than one organization/repository (a documented, supported configuration) where an attacker controls at least one low-trust repository among those tracked. No GITHUB_TOKEN, session, or ApiClient token is needed — only the ability to trigger a genuine GitHub webhook event (e.g., a `status` API call or push-triggered status) from a repository under the attacker's control, which is normal, unprivileged GitHub usage on their own repo. The target commit `sha` is public information.

### Recommendation
Scope `StatusHandler#process` (and any other handler mutating cross-cutting records purely by content-derived keys like `sha`) to the repository verified by the signature check, mirroring `Handler#stacks`:

```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

or equivalently restrict to `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, ensuring the mutated `Commit` belongs to a `Stack`/`Repository` matching `payload.dig('repository', 'full_name')` — the same repository whose organization's `webhook_secret` was used in `verify_signature`.

### Proof of Concept
1. Configure Shipit with two tracked GitHub organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per the documented multi-org config).
2. Attacker creates/owns a repo in `attacker-org` tracked as a Shipit stack, and obtains a valid webhook delivery for a `status` event from GitHub (any commit push triggers one), which is HMAC-signed with `attacker-org`'s `webhook_secret`.
3. Attacker crafts (or replays with modification, since GitHub webhook signatures cover only what GitHub computed server-side — attacker instead directly emulates GitHub's own outbound webhook by controlling a repo where they can push arbitrary commit statuses via the GitHub API, which GitHub then delivers, HMAC-signed by GitHub using `attacker-org`'s secret) a `status` payload where:
   - `repository.owner.login = "attacker-org"` (so `verify_signature` picks and passes with `attacker-org`'s secret)
   - `sha = "<victim commit sha>"`
   - `state = "success"`
4. POST to `/github/webhooks` passes `verify_signature` (valid signature for `attacker-org`). [6](#0-5) 
5. `StatusHandler#process` runs `Commit.where(sha: "<victim commit sha>")`, finds the victim's commit (belonging to `victim-org`'s stack), and calls `create_status_from_github!`, recording a forged `"success"` status on it. [2](#0-1) 
6. If `victim-org`'s stack has continuous deployment enabled or a human triggers a deploy relying on CI status, the forged status makes the commit `deployable?`, resulting in an unauthorized deploy of a commit that never passed real CI in that repository.

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
