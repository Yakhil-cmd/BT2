### Title
Missing existence check on `assocUnstableUnits[unit]` in `forgetUnit()` allows an unprivileged unit poster to crash node validation/purging paths - (File: storage.js)

### Summary
The CVE bug class is: a lookup that can transiently fail due to a race (a concurrently-expiring/removed object) is used without checking the result, and the object is later dereferenced, causing a use-after-free/crash. The closest reachable analog in ocore is `storage.forgetUnit()`, which unconditionally dereferences `assocUnstableUnits[unit].parent_units` without checking that the cache entry still exists, even though several independent, unsynchronized code paths compete to call `forgetUnit()`/read `assocUnstableUnits[unit]` for the same unit.

### Finding Description
`forgetUnit()` directly indexes the in-memory cache and dereferences `.parent_units` with no null check: [1](#0-0) 

This cache entry is deleted by the same function on every call (`delete assocUnstableUnits[unit]`), so `forgetUnit()` is explicitly not idempotent: [2](#0-1) 

`forgetUnit()` is invoked from multiple independent flows that walk the DAG and race against each other for the same unit:
- `purgeUncoveredNonserialJoints()` iterates units matching a SQL condition (`is_free=1` or no children) and, per row, reads `storage.assocUnstableUnits[row.unit].parent_units` directly before calling `forgetUnit(row.unit)` — with no check that the entry exists: [3](#0-2) 
- `archiveJointAndDescendants()` performs the identical unchecked pattern while walking an entire descendant subtree computed by a separate recursive DB query (`addChildren`): [4](#0-3) 

Both of these operations recompute their unit lists from the database (via `is_free=1`, "no children" subqueries, or a parent→child join) rather than from the in-memory cache, and both are wrapped only in the `["write"]` mutex or DB transaction, not in a shared "cache mutation" lock keyed by unit. `archiveJointAndDescendants` can be triggered by attacker-controlled DAG data (e.g., voiding of a final-bad/uncovered branch caused by a posted double-spend unit), and `purgeUncoveredNonserialJoints` runs periodically/independently over any final-bad or uncovered unit. If a unit's descendant subtree overlaps between the two purge passes (a realistic scenario when a poster submits a chain of units that becomes final-bad/uncovered because of a conflicting double-spend), the second pass to reach that unit will find `assocUnstableUnits[unit]` already `undefined` (deleted by the first pass's `forgetUnit`), and `assocUnstableUnits[unit].parent_units` throws a `TypeError: Cannot read properties of undefined`. Because these code paths run inside `async.eachSeries`/`db.executeInTransaction` continuations without a wrapping try/catch, the exception is unhandled and crashes the Node.js process — this is functionally the same "unchecked failure of a lookup that can be concurrently invalidated" root cause as `get_client_locked()` returning NULL after a raced client expiry in the NFSD CVE, except here the outcome is process termination rather than memory UAF (JS has no raw pointers), but the reachable, attacker-triggerable state corruption is analogous.

### Impact Explanation
A crash inside a purge/archive path that is entered as a result of processing an attacker-supplied (double-spend / final-bad) unit stops the affected full node's write/validation mutex holder, halting all further unit validation and main-chain/stability advancement on that node until manual restart — i.e., "a network unable to confirm new units" on affected nodes, and if triggered non-deterministically across a subset of nodes (depending on their local purge timing), it produces node disagreement about processed state after restart/replay. This is a Medium/borderline-High severity denial-of-service condition reachable purely by an unprivileged unit poster crafting a double-spend or final-bad branch of the DAG; it does not on its own enable unauthorized spending or double-spend finalization.

### Likelihood Explanation
The race requires both `purgeUncoveredNonserialJoints()` (interval/triggered) and `archiveJointAndDescendants()` (triggered by voiding of final-bad/uncovered units, which itself can be induced by a posted double-spend) to independently reach the same unit's `forgetUnit()` without a shared per-unit lock. Both derive their unit lists from separate DB queries computed at different times, so the two in-memory caches can legitimately diverge from what the DB currently reports mid-operation. This is plausible but requires specific timing (both purge/archive operations running close together on the same final-bad subtree), making it a real but not trivially-always-reproducible condition — consistent with a "race condition" class bug rather than a deterministic one.

### Recommendation
Add an existence check at the top of `forgetUnit()` and treat a missing cache entry as already-forgotten (no-op) rather than dereferencing it:
```js
function forgetUnit(unit){
    if (!assocUnstableUnits[unit]) {
        console.log('unit ' + unit + ' already forgotten');
        return;
    }
    ...
}
```
Additionally, guard the two call sites (`joint_storage.js` purge loop and `storage.js` `archiveJointAndDescendants`) with a check on `assocUnstableUnits[unit]` before reading `.parent_units`, and serialize unit-cache mutations (purge/archive/forget) under a single dedicated mutex key so that concurrent purge/archive passes cannot race on the same unit.

### Proof of Concept
Not independently reproducible from static analysis alone; the exact interleaving requires two asynchronous purge/archive tasks to be scheduled against the same final-bad subtree within the same short window. Concretely:
1. Post a valid unit `A`, then post a conflicting double-spend `B` that causes some downstream chain to be marked `final-bad`/uncovered.
2. Trigger conditions so that both `joint_storage.purgeUncoveredNonserialJointsUnderLock()` (interval-driven) and a `storage.archiveJointAndDescendants()` call (triggered elsewhere, e.g. by `light.js`'s voiding logic) select overlapping units from that final-bad branch in the same time window.
3. Whichever call reaches `forgetUnit(unit)` second will crash on `assocUnstableUnits[unit].parent_units` being `undefined`.

Given the uncertainty in exactly reproducing the timing window from static review, this should be validated dynamically in a Devin session with a debugger/log-injected delay between the two purge paths to force the interleaving.
