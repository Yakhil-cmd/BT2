### Title
Authenticated CPU-DoS via Cheap Repeated AA Triggers Invoking Expensive RSA `is_valid_sig`/`vrf_verify` Ops - ([File: formula/evaluation.js])

### Summary
Any unprivileged trigger sender can post units that pay only the minimal, size-based bounce fee while forcing every full node in the network to perform expensive RSA-based PEM signature/VRF verification during AA execution. The static complexity/op-count budget treats `is_valid_sig` and `vrf_verify` as flat, cheap operations (`complexity+=1`), completely decoupled from their real CPU cost, so an attacker can repeatedly trigger the same AA at negligible fee cost while every node redoes disproportionately expensive cryptographic work — the same "cheap authenticated request causes expensive server-side crypto operation, repeated to exhaust CPU" pattern as CVE-2026-32588's repeated `ALTER ROLE` password hashing.

### Finding Description
`formula/validation.js` charges a fixed `complexity+=1` / a small fixed `count_ops` for `is_valid_sig` and `vrf_verify`, regardless of the actual computational cost of verifying the signature: [1](#0-0) 

At execution time, `formula/evaluation.js` performs the real work: it parses/validates the caller-supplied PEM public key and calls `signature.verifyMessageWithPemPubKey`, which does full RSA signature/VRF verification — an operation that is orders of magnitude more CPU-expensive than the vast majority of other oscript ops (arithmetic, string ops, etc.) that are also billed at `complexity+=1`: [2](#0-1) 

Because the complexity/op-count budget (`MAX_COMPLEXITY`, `MAX_OPS`) is a syntactic proxy for cost and not a true CPU-cost model, an AA definition containing one or more `is_valid_sig`/`vrf_verify` calls with large RSA keys stays well within budget while consuming much more CPU than "normal" complexity-1 formulas: [3](#0-2) 

An AA trigger is authorized (accepted for execution by every full node) as long as it pays the AA's `bounce_fees`, which defaults to `MIN_BYTES_BOUNCE_FEE` — a small, fixed, byte-size-based amount unrelated to the actual CPU cost the AA's formula will incur: [4](#0-3) [5](#0-4) 

Any address (an "unprivileged" party — anyone able to send a payment) can act as the trigger sender for a pre-deployed AA. Because triggering costs only the (cheap) bounce fee in bytes and is otherwise unauthenticated/unprivileged beyond normal unit posting, an attacker can spam many trigger units in quick succession, each individually within the `MAX_COMPLEXITY`/`MAX_OPS` budget but each forcing every full node that must reach consensus on AA state to perform one or more expensive RSA/VRF verifications. This is directly analogous to the CVE's authenticated-but-unprivileged repeated `ALTER ROLE` calls that force the server to repeatedly run expensive password hashing, inflating query/validation latency for the whole cluster.

### Impact Explanation
Repeated cheap triggers force disproportionate, attacker-amplified CPU consumption on every full node validating/executing AA state transitions (all nodes must execute the same AA formula to agree on the resulting `state` and `payment` messages). Sustained spam can materially raise validation/AA-execution latency network-wide, delaying stabilization of the DAG and confirmation of unrelated units — i.e., "a network unable to confirm new units in a timely manner," which is explicitly an accepted impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: deploying the AA definition is a one-time, permissionless action; triggering it repeatedly requires only paying the AA's minimal bounce fee per trigger, which is far cheaper than the CPU work it forces every node to perform. No special privilege, hub/relay compromise, or protocol-level access is needed — only the ability to post ordinary payment units, which is available to any user of the network.

### Recommendation
- Weight `complexity`/`count_ops` for `is_valid_sig` and `vrf_verify` (and similar PEM/RSA-based ops) proportionally to key size/algorithm cost rather than a flat `+=1`, so the existing `MAX_COMPLEXITY`/`MAX_OPS` caps meaningfully bound real CPU cost.
- Consider a per-AA or per-address rate limit / increasing marginal fee for repeated triggers that exercise expensive cryptographic primitives, independent of raw byte size.
- Audit other primitives billed at flat complexity (e.g., `sha256`, `chash160`, `number_from_seed`, `is_valid_merkle_proof`) for similar cost/complexity mismatches, since `MAX_SIGNED_PACKAGES_PER_AA_EVAL` only limits count per single AA evaluation, not the trigger rate across many separate units.

### Proof of Concept
1. Deploy an AA definition whose triggered formula includes a call like `vrf_verify(trigger.data.seed, trigger.data.proof, trigger.data.pem_key)` or `is_valid_sig(...)`, using a maximally-sized RSA PEM key (allowed up to the length checks in `formula/evaluation.js`).
2. From any wallet address (unprivileged trigger sender), send a stream of payment units to the AA, each carrying just enough `base` output to cover `bounce_fees.base` (default `MIN_BYTES_BOUNCE_FEE`) and a `data` message with the seed/proof/key.
3. Each trigger unit is accepted for AA execution at minimal fee cost while forcing every full node to run full RSA/VRF verification during `handleTrigger`/`evaluateAA`.
4. Repeat the trigger stream at a rate the byte-fee economics allow; observe AA-execution and unit-validation latency rising disproportionately to the fees paid, across all validating nodes.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}
