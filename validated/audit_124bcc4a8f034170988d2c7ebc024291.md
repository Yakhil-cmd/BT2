### Title
Signature verification is keyed on `repository.owner.login`, but the target stack is resolved from the unrelated `repository.full_name` field, letting an attacker use a no-secret organization to forge webhooks against any other stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) using `params.dig('repository', 'owner', 'login')`, while `Handlers::Handler#stacks`/`#repository_name` resolves the *actual mutated* repository/stack using the independent `params.dig('repository', 'full_name')` field of the very same attacker-supplied JSON body. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected organization's config has no `webhook_secret`, an attacker can pick any Shipit-configured organization with a blank secret for `owner.login` to pass verification, while setting `full_name` to a completely different victim repository/stack (e.g. one with a production environment) whose config *does* have a secret.

### Finding Description
The invariant that should hold is:
`org(auth) == org(affected)`, where `org(auth) = params.dig('repository','owner','login')` (used to pick the `GitHubApp`/secret for HMAC verification) and `org(affected) = Repository.from_github_repo_name(params.dig('repository','full_name')).owner` (the repository/stack that is actually mutated).

Tracing the code:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and does `Shipit.github(organization: repository_owner)` [1](#0-0)  and [2](#0-1) .
- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when `webhook_secret` is blank, before any HMAC comparison happens: [3](#0-2) .
- Once `verify_signature` passes, `WebhooksController#create` dispatches the *same raw JSON body* to `PushHandler.call(params)` [4](#0-3) .
- `Handlers::Handler#stacks` resolves the target using `repository_name`, computed independently from `payload.dig('repository', 'full_name')` — a different, unchecked field of the same payload: [5](#0-4) .
- `PushHandler#process` then iterates every non-archived stack on the matching branch of that resolved repository and calls `stack.sync_github(expected_head_sha: params.after)`: [6](#0-5) .

Nothing in this path cross-validates that `repository.owner.login` (used to choose the secret) matches the owner encoded in `repository.full_name` (used to pick the mutated stack). GitHub's real webhooks always keep these fields internally consistent, but Shipit's controller/handler code does not enforce that consistency itself, so a forged unauthenticated request is free to decouple them.

Exploit flow: attacker sends an unauthenticated `POST /webhooks` with header `X-Github-Event: push`, body containing `repository.owner.login = "no-secret-org"` (any organization configured in Shipit with `webhook_secret` blank/absent) and `repository.full_name = "victim-org/victim-repo"` (a real repository with a stack configured for a production environment), plus `ref` and `after` matching a real branch/stack. `verify_signature` resolves the GitHubApp for `"no-secret-org"`, finds `webhook_secret` blank, and returns `true` regardless of the `X-Hub-Signature` header supplied. `PushHandler` then resolves stacks via `full_name = "victim-org/victim-repo"` and invokes `sync_github` against the production stack.

No other guard intercepts this: `drop_unhandled_event` only checks the event type is registered [7](#0-6) ; there is no `ExplicitParameters` validation of `repository.owner.login` vs `full_name` consistency; `PushHandler`'s param schema only requires `ref` and `after` [8](#0-7) .

### Impact Explanation
The attacker causes `PushHandler` to run `sync_github(expected_head_sha:)` against an arbitrary Shipit-registered stack (including one on a production environment) using a webhook whose HMAC was validated against a completely unrelated organization's (blank) secret. This is exactly the "payload for one repository mutating another's stack, commit, task or team" scenario: the forged request is authenticated by `no-secret-org`'s (non-)secret yet mutates `victim-org/victim-repo`'s stack state (commit sync), which can subsequently drive continuous delivery on that stack. This is repeatable against any repository/stack registered in Shipit, as long as at least one configured organization in the Shipit deployment has a blank `webhook_secret`, and does not require any credentials, session, or API token from the attacker.

### Likelihood Explanation
Preconditions: Shipit must have at least one organization configured without a `webhook_secret` (the "no-secret organization" condition), and a victim stack/repository must exist for a different organization that the attacker wants to target. Both conditions are plausible operational misconfigurations (e.g., an internal/test org onboarded before secrets were rotated in). Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body; no GitHub account, Shipit session, or secret material is required. The attack is fully repeatable against arbitrary stacks by simply changing `full_name`, `ref`, and `after` in the forged body.

### Recommendation
Cross-validate that the organization used to resolve/verify the webhook secret in `WebhooksController#verify_signature` matches the actual owner of the repository resolved by the handler (`payload.dig('repository', 'full_name')`) before dispatching to any handler — i.e., derive `repository_owner` from the same `full_name` value used for stack resolution, or explicitly assert `full_name.split('/').first == owner.login` and reject on mismatch. Additionally, treat a blank/absent `webhook_secret` for an organization as a hard misconfiguration (reject signature verification, or log/alert) rather than silently returning `true` in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb` (or a new test), add a minitest case for the "no-secret organization" scenario:
1. Configure `Shipit.github_configs` (or the equivalent test fixture) with two organizations: `"no-secret-org"` (no `webhook_secret` key) and `"victim-org"` (with a real `webhook_secret`).
2. Create a `Shipit::Stack` for `victim-org/victim-repo` with `environment: "production"` and a known `branch`.
3. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or an arbitrary bogus one), and a JSON body: `{"repository": {"owner": {"login": "no-secret-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/<branch>", "after": "<some_sha>"}`.
4. Assert the response is `200 OK` (not `422`), proving signature verification passed via the no-secret org.
5. Assert that `Shipit::Stack#sync_github` (or `GithubSyncJob`) was invoked/enqueued for the `victim-org/victim-repo` stack (e.g., via mocking `Stack#sync_github` and asserting it was called with `expected_head_sha: "<some_sha>"`), demonstrating that a payload "authenticated" only by `no-secret-org`'s blank secret mutated `victim-org`'s production stack — violating the claimed invariant that a push event only affects the repository/stack whose secret authenticated it.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
