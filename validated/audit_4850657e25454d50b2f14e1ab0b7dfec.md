## Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read the status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` resolution method used by the base API controller and resolves the target stack directly from the request parameter instead of going through the `ApiClient`-scoped collection. This breaks the trust binding "the stack an `ApiClient` token is authorised to read" == "the stack the request actually reads," mirroring the reported smart-contract bug class where two values meant to be kept consistent (here: the token's authorized scope vs. the resource actually served) diverge.

### Finding Description
`Shipit::ApiClient` can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The intended enforcement of this scope lives in `Shipit::Api::BaseController`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every controller that inherits `stack` from `BaseController` (e.g. `CommitsController`) is therefore constrained: if the authenticated `ApiClient` has a `stack_id`, only that stack is resolvable, regardless of `params[:stack_id]`.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely:

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack

  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
``` [3](#0-2) 

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks that `"read:stack"` is in the client's `permissions` array — it never checks `stack_id`:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [4](#0-3) 

So the equality that should hold — `current_api_client.stack_id == stack.id` (or `stack_id nil` meaning "any stack") — is broken specifically for this controller: the permission check validates the operation/scope pair, but the resource-selection method (`stack`) resolves an arbitrary `Stack` straight from user-supplied `params[:stack_id]`, exactly as `withdrawnStakingEarnings`/`vaultEndedStakingEarnings` diverged in the referenced report by using two different sources of truth for the same accounting value.

### Impact Explanation
An `ApiClient` created with `stack_id` set (e.g. a token intentionally issued to a CI system with `read:stack` permission restricted to one stack, as supported by the admin UI in `Shipit::ApiClientsController`/`app/views/shipit/api_clients/show.html.erb`) can be used to fetch `GET /api/1/stacks/:stack_id/ccmenu.xml?token=...` for *any other stack ID* in the installation, not just the one it was scoped to. This discloses deploy/rollback state, timestamps, and running status (`latest_deploy.running?`, `ended_at`, etc.) for stacks the token holder was never granted access to — an unauthorized cross-stack read of stack state/deploy output, matching the "High — unauthenticated (here: out-of-scope) read of stack state, task streams or deploy output" impact bucket via escalation beyond the token's authorized scope.

### Likelihood Explanation
High. Any environment that issues stack-scoped `ApiClient` tokens with `read:stack` (a supported, documented configuration) is affected. No special conditions are needed beyond knowing another stack's `to_param` (slug), which is not secret information within a Shipit instance.

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` collection from `BaseController` instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the invariant that a stack-scoped `ApiClient` can only ever resolve to its authorized stack, consistent with every other controller under `app/controllers/shipit/api/`.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (supported via the `ApiClientsController` UI/API).
2. Holder of that token issues:
   `GET /api/1/stacks/<other-stack-B>/ccmenu.xml?token=<token-for-A>`
3. `authenticate_api_client` succeeds (valid token) [5](#0-4) , `require_permission :read, :stack` succeeds because the client has `read:stack` permission [4](#0-3) , and `stack` resolves stack B directly from params, bypassing the `stack_id == A` restriction [6](#0-5) .
4. Response renders stack B's deploy/rollback status, which the token was never authorized to see.
