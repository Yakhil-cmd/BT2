### Title
Payload-named route addresses let attacker code run under the victim's authorization and drain the caller's wallet - ([File: contracts/swap-aggregator/src/venues/mod.rs])

### Summary
The Flowise bug class is "a sanitization/allowlist check that validates the *command* but lets attacker-controlled *arguments* smuggle in arbitrary code execution." The direct analog in XOXNO Lending is the swap router: it fixes the set of allowed *venue adapters* (the "safe commands"), but the hop `pool` and `token` addresses come straight from the caller-supplied `StrategyPayload` with no allowlist (the "arguments"). A route instruction naming an attacker-deployed contract puts arbitrary Wasm on the call stack *below the user's signed authorization*, and that code can invoke `token.transfer(victim, attacker, amount)` on any token the victim holds — the Soroban host records it as a child of the victim's root auth entry, so signing the simulated tree executes the theft.

### Finding Description
`dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs:23-40` dispatches to a venue adapter chosen by `hop.venue`, but `hop.pool`, `hop.token_in`, and `hop.token_out` are payload-supplied addresses from the decoded `StrategyPayload`. The venue adapter then `invoke_contract`s whatever `pool` address the route names. The threat model itself documents the consequence: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md:154-165`).

This is reachable through every unprivileged controller strategy entrypoint that accepts a route: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `flash_position` (which internally swaps through `swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55`). The controller's protections — `authorize_transfer_as_current` (one exact input-transfer grant), `RouterOverspend`, `NoSwapOutput`, and final health-factor checks — bound only the *routed* funds. They are exactly analogous to Flowise's `validateCommandInjection`/`validateArgsForLocalFileAccess`: they constrain the declared channel while the attacker-controlled argument (the pool address) escapes it entirely.

### Impact Explanation
Theft of user funds beyond the transaction's declared scope. If the victim signs the simulation-produced authorization tree without decoding it (which honest clients do — simulation output is typically signed as-is), the rogue pool's `token.transfer(victim, attacker, wallet_balance)` executes for *any* token in the victim's wallet, including tokens the protocol never listed. The theft is unbounded by `total_in`, by `min_out`, and by the account's risk checks — all of which still pass because the swap itself can be made to settle honestly.

### Likelihood Explanation
The attack requires the victim to sign a crafted route. The adversary is an unprivileged address: it deploys a `RogueHopPool`-style contract, embeds it as `hop.pool` in a route returned through a malicious or compromised quote path, and offers the victim a fair-looking swap. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the mechanism end-to-end on the real controller path: in recording mode the stolen transfer is attached under Alice's `swap_collateral` entry and her unlisted `wallet_token` balance moves to the attacker (lines 194-227), and in enforcing mode the poisoned signed tree executes the drain while the honest tree correctly refuses (lines 229-269). Likelihood is bounded by the signing requirement, so Medium severity.

### Recommendation
Treat payload-named pool addresses as untrusted code, not just untrusted parameters:
- Maintain an on-chain allowlist of venue pool contracts (set by governance) and reject hops naming non-registered pools, or at minimum pin per-venue pool registry entries the adapter resolves rather than executing arbitrary addresses.
- Alternatively/additionally, sandbox each hop so venue code cannot request additional user auth — e.g., run route hops under a sub-context where only the router's own `authorize_as_current_contract` entries exist; note that today the caller's auth entry legitimately remains active for the whole call.
- Document at the controller boundary that the signed auth tree must be inspected, and have the SDK expose the expected child-invocation set (exactly one `token_in.transfer(sender, router, total_in)` for `execute_strategy`, plus the input transfer for controller routes) so clients can reject poisoned trees automatically.

### Proof of Concept
The repository already contains a working PoC: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Attacker deploys `RogueHopPool` (`lines 51-72`) whose `swap()` executes `token::Client::new(&env, &wallet_token).transfer(&victim, &attacker, &amount)`.
2. Attacker builds a `RoutedSwap` route naming that contract as `hop_pool` with a fair `min_out` (`route_through_pool_stealing`, `lines 111-125`).
3. Victim calls `controller.swap_collateral(caller, account_id, usdc, amount, eth, route)`. The controller authorizes its exact input transfer and calls the router, which `invoke_contract`s the rogue pool (`UnlistedPoolRouter::execute_strategy`, `lines 38-47` — mirroring the real `dispatch_hop` shape).
4. Simulation records the rogue transfer as a child of the victim's auth entry (`lines 195-226`): `recorded == [(alice, swap_collateral_root{children:[wallet_token.transfer(alice→attacker, WALLET_BALANCE)]})]`, and `assert_eq!(wallet(alice), 0)` / `wallet(attacker) == WALLET_BALANCE`.
5. `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (`lines 229-269`) confirms enforcing mode executes the drain iff the victim signs the tree simulation returned — the realistic signing path.

Note: this exposure is explicitly acknowledged in `docs/explanation/threat-model.md:154-165` as a client-side signing hazard rather than a router-side invariant, so it may be argued a documented design choice; the code itself, however, performs no validation that would bound the damage to the routed amount, which is the same structural gap as the Flowise advisory.
