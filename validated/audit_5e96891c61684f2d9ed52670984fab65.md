### Title
Unbounded-size formula parse-tree cache enables per-process memory-exhaustion DoS via AA definitions/oscript formulas - (File: formula/common.js)

### Summary
The oscript formula parser used to validate and evaluate every AA formula (state scripts, `init` fields, payment/data conditions, address-definition expressions, etc.) is memoized in a global, process-wide cache. The cache is bounded only by **number of entries** (100), not by the size of each cached parse tree or of the source formula string. An attacker who authors an AA (or an address definition containing an oscript expression) can craft up to 100 extremely large/complex formulas whose parsed ASTs are each disproportionately large, get stored forever (until evicted by the 100-entry FIFO) in every node's memory, and are never bounded by an actual byte/size limit — unlike the deliberate size guards (`MAX_AA_STRING_LENGTH`, `isTooBigObj`) that exist for *values* produced during evaluation but not for the cached grammar/parse output itself.

### Finding Description
`formula/common.js` defines the shared formula cache: [1](#0-0) 

Both `formula/evaluation.js` and `formula/validation.js` use this cache identically: they key the cache by the raw formula string and store the full parsed nearley grammar result (`parser.results`), evicting only when the *count* of cached formulas exceeds `cacheLimit` (100): [2](#0-1) [3](#0-2) 

This cache is populated for every unique formula string that is validated or evaluated — including formulas embedded in AA definitions (`init`, `messages[].payload.init`, `state` code, oscript conditions in address/asset definitions), all of which are attacker-controlled content posted by any unprivileged AA author. Every full node that processes a unit referencing/triggering such an AA (or validates a definition containing the formula) will independently parse and cache the formula in this same process-global map.

Unlike the value-size protections found elsewhere in the evaluator (e.g., `isTooBigObj`, `MAX_AA_STRING_LENGTH` checks on strings/objects during *evaluation*, see `formula/evaluation.js:2801-2805`), there is no limit on:
- the raw length of the input `formula` string used as the cache key, or
- the size/depth of the parsed AST (`parser.results`) that gets memoized.

The eviction logic only pops the oldest formula when `formulasInCache.length > cacheLimit`, meaning it can hold up to 100 arbitrarily large parsed formulas simultaneously — this is structurally identical to the SvgSprite bug class: a size-unbounded artifact derived from attacker-controlled input is cached indefinitely per process, and can be grown without limit by the attacker, risking OOM/process kill.

### Impact Explanation
Because the formula cache is populated by parsing *any* oscript formula seen in AA definitions and address/asset definitions (data reachable by an ordinary AA-definition author or address-definition author — not requiring any special/admin privilege), a malicious author can:
1. Deploy up to 100 AAs (or definitions) each containing an extremely long, deeply nested, or combinatorially large oscript expression (parenthesized expressions, deeply chained ternaries/concats, etc., subject only to unit/message size limits, not formula-complexity limits at the grammar level).
2. Trigger evaluation/validation of these formulas across the network so that every full node parses and caches each large AST.
3. Because the cache is retained by every process (main full nodes, hubs, and any node re-validating/re-evaluating triggers), this can inflate the per-process resident memory disproportionately to input size (nearley parse trees can be significantly larger than the source text), risking process termination (OOM killer) — a network-wide DoS on nodes attempting to validate/confirm new units referencing these AAs, potentially stalling confirmation of new units broadly if enough nodes are affected simultaneously.

This matches the required impact bar: "a network unable to confirm new units" if enough full nodes crash or become unresponsive while re-parsing/holding these caches repeatedly (the cache is also process-lifetime scoped and refills after crash-restart, and it is refreshed on every re-validation, e.g., resent triggers, catch-up, or re-evaluation during estimation).

### Likelihood Explanation
Medium. Creating an AA and having a trigger (or another AA) invoke it is fully within reach of a normal unprivileged actor — no special permissions, mining power, or hub role are required. The formula content itself is only bounded by the general unit/payload size limits (thousands of bytes per message), not a dedicated "formula complexity" cap enforced before parsing/caching, so an attacker can pack a formula near the message-size ceiling with maximally recursive/nested syntax to inflate the parsed AST relative to the raw byte count. However, the actual per-formula amplification factor and whether 100 such formulas are sufficient to cause practical OOM was not independently measured in this review, so severity should be validated with a memory-profiling PoC before treating this as fully proven at High severity.

### Recommendation
- Add a size/complexity guard on formulas *before* they are cached (e.g., bound formula string length, and/or estimate parsed-AST node count/depth) and reject or refuse to cache the memoized results for oversized formulas, so they are always reparsed without persisting a large tree in the shared cache.
- Alternatively/also, size-bound the cache by aggregate serialized size of cached ASTs (similar to `isTooBigObj`), not simply entry count, so 100 huge parse trees can't accumulate.
- Ensure per-address/per-formula caching doesn't allow one attacker to force retention of 100 maximal-size entries indefinitely by rotating formulas across AAs.

### Proof of Concept
Not independently constructed/run in this review (no execution environment available). Conceptual PoC: deploy N (~100) AAs whose `state`/`init` oscript contains large deeply-nested boolean/arithmetic expressions at/near the unit payload size limit (e.g., deeply chained `concat()`/ternary/`in`/array-literal expressions to maximize nearley parse-tree branching relative to source length); trigger each AA once so every full node parses and caches its formula via `formula/evaluation.js:104-121`; then measure RSS growth of a validating node process versus the sum of raw formula byte sizes to demonstrate disproportionate memory retention driven by the size-unbounded cache.
