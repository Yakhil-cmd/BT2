### Title
Membership-webhook trust binding lets an attacker forge team membership using an unsigned/unrelated organization's webhook secret, escalating into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` derives *which* HMAC secret to check the request against from a field inside the unauthenticated request body itself (`repository.owner.login` or `organization.login`), rather than from a fixed, pre-established trust anchor. The `MembershipHandler` that is subsequently invoked also trusts fields taken from that same unauthenticated body (`params.organization.login`, `params.team`, `params.member.login`) to create `Team`/`Membership` records that directly control `User#authorized?`, which gates access to the entire Shipit application via `Shipit.github_teams`. Because the “organization whose secret was used to authenticate the request” and “the organization/team whose membership is actually written” are both selected from attacker-controlled JSON, and because GitHub Apps in this engine can be configured with `webhook_secret: nil` (explicitly documented as optional in `docs/setup.md`), the signing/verification step can become a no-op for any deployment (or any additionally configured organization) that leaves the secret blank — letting an unprivileged network attacker forge a `membership` webhook and grant an arbitrary existing `User` login access to a `Shipit.github_teams`-restricted instance.

### Finding Description
`Shipit::WebhooksController#verify_signature` computes the organization to authenticate against straight from the payload: [1](#0-0) [2](#0-1) 

It then fetches a `GitHubApp` instance for that organization and calls `verify_webhook_signature`: [3](#0-2) 

Note line 77: `return true unless webhook_secret`. Per the setup docs, `webhook_secret` is explicitly “optional”: [4](#0-3) [5](#0-4) 

If an operator (or a second/third organization added later, since Shipit supports multi-organization config via `github_app_config`) does not configure `webhook_secret`, `verify_webhook_signature` unconditionally returns `true` for any request claiming that organization — no HMAC is actually checked. Once past `verify_signature`, `WebhooksController#create` dispatches the raw, still-unauthenticated-in-content JSON body straight to handlers: [6](#0-5) 

The `membership` event is routed to `MembershipHandler`, which trusts `params.organization.login`, `params.team`, and `params.member.login` completely to find-or-create a `Team` and add/remove a `Membership`: [7](#0-6) 

Team membership is exactly what gates access to the whole application: `User#authorized?` checks whether the user belongs to any team in `Shipit.github_teams`, and `Shipit.github_teams` itself is built from `Team` records (the same model the forged webhook writes to): [8](#0-7) [9](#0-8) [10](#0-9) 

This reproduces the BondNFT-style bug class: a value that gates a security decision (“is this webhook signature valid, and for what scope”) is computed from — and can diverge from — the exact same untrusted field(s) that the subsequent business logic (`MembershipHandler#process`) uses to perform a privileged write (creating `Membership` rows that unlock authorization). The equality the engine implicitly relies on is:

`organization whose secret authenticated the HTTP request == organization/team whose Membership record is mutated by the handler`

but nothing enforces this equality when `webhook_secret` is unset for that organization (a documented, supported configuration), or when a second organization is configured without a secret while `Shipit.github_teams` still references teams under a different, secret-protected organization — the signature check for the payload's claimed org is a no-op while the write still lands on `Team`/`Membership` records that back global authorization.

### Impact Explanation
This crosses the authentication boundary explicitly called out as High: “escalation into `Shipit.github_teams` authorization.” An attacker who is not a Shipit session holder, not an `ApiClient`, and does not know `webhook_secret` can:
1. POST to `/webhooks` with `X-Github-Event: membership` and a body naming an organization that has no `webhook_secret` configured.
2. `verify_signature` passes trivially (`return true unless webhook_secret`).
3. `MembershipHandler#process` creates/loads a `Team` and calls `team.add_member(User.find_or_create_by_login!(params.member.login))`, adding any existing (or newly created) Shipit `User` to a team in `Shipit.github_teams`.
4. That user (or the attacker, if they control a `User` record via prior GitHub OAuth login) is now `authorized?` and gains full access to the Shipit instance — stacks, deploy triggers, task execution, etc.

This is a genuine authentication/authorization bypass into the exact mechanism (`Shipit.github_teams`) the rules call out as High severity, achieved purely by exploiting the disconnect between which organization's (possibly absent) secret authenticated the request and which team/membership record the handler actually mutates.

### Likelihood Explanation
Likelihood is contingent on operator configuration: this is fully exploitable whenever `webhook_secret` is left blank for the organization used in the forged event (a state the project's own documentation and example config present as normal/optional), or whenever a multi-org Shipit deployment configures an additional organization without a webhook secret while sharing `Shipit.github_teams`. No GitHub App private key, session, or `ApiClient` token is required — only network access to `/webhooks` and knowledge of an existing/creatable `User` login and a team handle in `Shipit.github_teams`.

### Recommendation
- Do not allow `webhook_secret` to be silently treated as "no verification required." Require a webhook secret before accepting security-relevant events (at minimum `membership`), or fail closed instead of `return true unless webhook_secret`.
- Bind the “authenticating organization” at the `GithubHook`/config level and cross-check it strictly against `params.organization.login` / `params.team.organization` inside `MembershipHandler`, rejecting mismatches instead of trusting the payload's own claim end-to-end.
- Ensure `Team#find_or_create_by_handle`/`MembershipHandler` cannot mutate `Membership` for any organization other than the one whose signature was actually cryptographically verified with a configured, non-blank secret.

### Proof of Concept
Given a Shipit deployment where organization `evilorg` is configured in `Shipit.github` (single-org or multi-org schema) with `webhook_secret: nil` (a supported/documented configuration), while `Shipit.github_teams` includes a team `evilorg/admins`:

```
POST /webhooks HTTP/1.1
X-Github-Event: membership

{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "evilorg" },
  "member": { "login": "attacker-controlled-existing-user" },
  "repository": { "owner": { "login": "evilorg" } }
}
```

`verify_signature` resolves `repository_owner` = `"evilorg"`, fetches its `GitHubApp` config, calls `verify_webhook_signature(nil, body)`, which returns `true` immediately because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`). `MembershipHandler#process` then creates the `Team` and adds `attacker-controlled-existing-user` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-33`), which flips `User#authorized?` to `true` via `Shipit.github_teams` (`app/models/shipit/user.rb:80-82`, `lib/shipit.rb:256-258`), granting full application access without ever presenting a valid GitHub webhook signature.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else

          end
        end

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|

          end
        end
```
