## Analysis

This confirms the vulnerability. `Shipit.github(organization:)` at [1](#0-0)  looks up per-organization config via `github_app_config(organization)`, and each org's `GitHubApp` independently decides whether to enforce signature verification: `verify_webhook_signature` at [2](#0-1)  **returns `true` unconditionally when `webhook_secret` is blank for that org**. The `organization` used to select which org's `GitHubApp`/secret applies is taken directly from the *unverified* JSON body in `WebhooksController#repository_owner`, before the signature has been validated: [3](#0-2) .

### The broken binding

`organization_whose_secret_is_checked == organization_claimed_in_unverified_payload_body`

should be

`organization_whose_secret_is_checked == organization_that_actually_signed_the_request`

Because the org name is read from `params.dig('repository','owner','login')` (or `organization.login`) of the *raw, unauthenticated* body before `verify_signature` runs, and because `verify_webhook_signature` trivially passes (`return true unless webhook_secret`) for any org configured in the multi-org `secrets.github` map that has a blank/unset `webhook_secret` (which the setup docs/examples explicitly show as a supported, common state — e.g. `webhook_secret: # nil` in `config/secrets.development.example.yml` lines 11 and 18-33), any external caller can forge a webhook for a *different, fully-configured* organization simply by claiming `repository.owner.login` (or `organization.login`) equal to the name of an org in the install that lacks a webhook secret. The signature check then no-ops, and the forged payload's actual `repository.full_name`/data is processed by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` at [4](#0-3) , exactly matching the "organization that authenticated versus the repository that is written" analog class.

### Impact

Handlers driven by unauthenticated webhook payloads include, e.g., `push` triggering `GithubSyncJob` and `status`/`check_suite` mutating commit statuses used for merge/deploy gating (seen in `test/controllers/webhooks_controller_test.rb`). Forging these for a stack under a properly-secured org (by impersonating a sibling org without a secret) can flip commit statuses, trigger syncs, or manipulate merge-queue state — potentially enabling an unauthorized merge/deploy decision, which meets the "High" bar (escalation affecting stack state) in the rules.

### Caveat / uncertainty

This requires a specific deployment configuration: multiple GitHub orgs configured under `secrets.github` (the multi-org schema, keyed by org name — see `github_default_organization`/`github_app_config` at [5](#0-4) ) where **at least one** configured org has no `webhook_secret` set. I could not verify from the index whether the host application's setup docs treat "some orgs with secret, some without" as a supported/expected combination versus every org being required to set a secret — this is an operational/deployment nuance that a background agent or the docs (`docs/setup.md`, out of scope for citation here) would need to confirm. If every org in a given installation is required to set `webhook_secret`, this exact bypass path doesn't apply, though the root design flaw (organization selection from unverified payload before signature check) still stands as a control-order weakness.

### Title
Webhook organization selection uses unverified payload before signature check, enabling cross-organization webhook forgery — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub organization's webhook secret to validate against using `repository_owner`, a value read from the unverified/unauthenticated JSON body. Combined with `GitHubApp#verify_webhook_signature` short-circuiting to `true` when that org's `webhook_secret` is blank, an attacker can forge a webhook whose *claimed* organization has no secret configured while its payload content (repository, commit sha, statuses, etc.) targets a different, secret-protected stack.

### Finding Description
- `repository_owner` is derived from `params.dig('repository','owner','login') || params.dig('organization','login')`, i.e., directly from the untrusted raw body [6](#0-5) .
- This value selects the `GitHubApp` instance/secret used for verification via `Shipit.github(organization: repository_owner)` [7](#0-6) , which internally resolves through `github_app_config(organization)` [8](#0-7) .
- `verify_webhook_signature` unconditionally returns `true` when the selected org's `webhook_secret` is blank [2](#0-1) .
- The controller never cross-checks that the org named in the payload actually matches the `repository.full_name` used by downstream handlers, nor that the org has a mandatory secret — the equality `organization used for signature ≠ organization actually authoring the request` is never enforced.

### Impact Explanation
An attacker with no credentials can submit a crafted POST to `/github/webhooks` claiming to be from an org without a configured `webhook_secret`, while embedding payload data (repository name, commit SHA, CI status, push refs) belonging to any other stack tracked by the instance. Because verification passes trivially, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` processes the forged data as authentic, letting the attacker manipulate commit statuses, trigger syncs, or otherwise affect stack/merge state without possessing any GitHub credentials or Shipit session.

### Likelihood Explanation
Requires: (1) a multi-org `secrets.github` configuration, and (2) at least one configured org left without a `webhook_secret`. The engine's own example/doc configs demonstrate this as a normal, supported configuration shape, making the precondition plausible in real deployments rather than purely theoretical.

### Recommendation
Do not select the verification org from the unauthenticated payload. Either (a) require `webhook_secret` for every organization when the multi-org schema is used and refuse startup/refuse requests otherwise, or (b) verify the signature against *every* configured org's secret and only proceed if a match is found for an org whose secret is actually configured, rejecting requests where the claimed org has no secret. Additionally, cross-validate that the org derived from the payload matches the org owning the `repository.full_name` referenced by the same payload before dispatching handlers.

### Proof of Concept
1. Configure `secrets.github` with two orgs: `orgA` (has `webhook_secret: secretA`) and `orgB` (no `webhook_secret`, i.e., `nil`).
2. Send `POST /github/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature`, and body:
```json
{
  "repository": {"full_name": "orgA/private-repo", "owner": {"login": "orgB"}},
  "sha": "<targeted commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `repository_owner` resolves to `"orgB"`; `Shipit.github(organization: "orgB")` returns a `GitHubApp` with `webhook_secret` nil; `verify_webhook_signature` returns `true` regardless of the (absent/invalid) signature.
4. The status handler processes the payload as authentic, updating the commit status for `orgA/private-repo` despite the request never being signed by `orgA`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
