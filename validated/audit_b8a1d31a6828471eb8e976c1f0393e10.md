### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup forces `ContinuousDeliveryJob` on victim's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone across the entire `commits` table with no scoping to the repository/organization that authenticated the webhook, unlike `PushHandler`, which restricts to `stacks` derived from `payload.dig('repository', 'full_name')`. Because commit SHAs are shared across forks of the same upstream history, an attacker who owns any GitHub repository wired into Shipit (with a valid `webhook_secret` for their own org) can post a `status` webhook referencing a SHA that also exists as a `Commit` row belonging to a victim's stack, causing that victim stack's commit to receive a new `Status`, which enqueues `ContinuousDeliveryJob` for the victim's stack via `Commit#schedule_continuous_delivery`.

### Finding Description
The claimed binding is: `stack enqueued for ContinuousDeliveryJob == stack whose organization's webhook_secret verified the request`.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository','owner','login')`). This only proves the payload was signed by *some* organization's secret — the attacker's own, since they control that org. [1](#0-0) [2](#0-1) 
- `WebhooksController#create` dispatches the parsed body to `Shipit::Webhooks.for_event(event)` handlers without any further repository/stack binding. [3](#0-2) 
- The base `Handler` class defines a `stacks` helper that *does* correctly scope lookups to the repository that sent the payload: `Repository.from_github_repo_name(repository_name)&.stacks`, using `payload.dig('repository', 'full_name')`. `PushHandler` uses this helper. [4](#0-3) [5](#0-4) 
- `StatusHandler#process`, however, ignores this scoping entirely and queries `Commit.where(sha: params.sha)` globally, then calls `commit.create_status_from_github!(params)` on every match regardless of which stack/repository owns that commit. [6](#0-5) 
- `Status` has `after_commit :schedule_continuous_delivery, on: :create`, which calls `commit.schedule_continuous_delivery`. [7](#0-6) 
- `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` for `commit.stack` — the stack that owns the matched `Commit` row, not the stack of the repository that produced the signature. [8](#0-7) 

Root cause: `StatusHandler` performs a global, cross-tenant SHA lookup instead of scoping to `stacks` (the repository that authenticated the request), so the equality the question asks about does not hold — the stack that gets a `ContinuousDeliveryJob` enqueued is whichever stack happens to contain a `Commit` with a matching `sha`, not necessarily the stack belonging to the organization whose `webhook_secret` verified the request.

Attacker's exact request: own any GitHub repository connected to Shipit (satisfies "unprivileged" — any GitHub user with a repo and Shipit App installed on it, or any org where they can push commits), then `POST /webhooks` with header `X-Github-Event: status`, a body signed with their own org's genuine webhook secret, and `sha` set to a commit SHA that is already recorded as a `Commit` for a victim's stack (trivially achievable when both repos share git history via fork lineage — pre-fork commits have byte-identical, and therefore identical SHA, content) and `state: success` (or whatever satisfies the victim's `required_statuses`).

Existing guards do not prevent this: `verify_signature` only authenticates *an* organization, not the organization owning the target commit/stack; `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha, String; requires :state, String`) impose no repository binding; there is no `Repository` full_name check in `StatusHandler` at all, unlike `PushHandler`.

### Impact Explanation
An attacker who authenticates only as their own GitHub organization can write a `Status` record onto, and enqueue `ContinuousDeliveryJob` for, a stack belonging to a completely different, victim organization/tenant, as long as a shared-history commit SHA collision exists. If the victim stack has `continuous_deployment` enabled and the forged status is the last required status, this can trigger `Stack#trigger_continuous_delivery` → an actual deploy of the victim's stack via `Task`/`Command` execution, i.e., a payload from one repository mutating another's commit/stack/task and causing an unauthorized deploy — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." This is repeatable against any stack in the installation whose tracked commits share history (forks, subtree merges, cherry-picks) with an attacker-controlled repository.

### Likelihood Explanation
Preconditions: the attacker needs a Shipit-integrated GitHub repository/org of their own (to obtain a legitimate signature), and a SHA collision with a commit already ingested into a victim stack's `commits` table. Forcing an exact SHA-1 collision from scratch is infeasible, but sharing pre-fork/common-ancestor commits between a victim's tracked upstream repo and an attacker-controlled fork is common and requires no privileged access — this is a realistic, low-cost path for open-source or internally-forked projects tracked by Shipit. No Shipit session, API token, or secret is needed beyond the attacker's own legitimately obtained webhook secret for their own repo.

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to stacks of the repository that authenticated the webhook, mirroring `PushHandler`'s use of the `stacks` helper, e.g. filter via `Commit.where(sha: params.sha, stack: stacks)` (or join through `Repository.from_github_repo_name(repository_name)`) instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook from repo A must not schedule CD for a commit owned by repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # belongs to repository "shopify/shipit-engine"
  attacker_repo_full_name = "attacker/unrelated-repo"

  # Victim already has a tracked commit with this sha (e.g. shared fork history)
  shared_sha = shipit_commits(:first).sha
  victim_commit = shipit_commits(:first)
  assert_equal victim_stack, victim_commit.stack

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } }
  }

  # Binding under test: stack enqueued == stack of org that authenticated (attacker's), NOT victim_stack
  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload) # should be scoped to attacker's stacks (none), so no enqueue
  end

  # Current (buggy) behavior demonstrates the violation:
  assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_stack]) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
This demonstrates that `StatusHandler.call` with a payload whose `repository.full_name` does not correspond to `victim_stack` still enqueues `ContinuousDeliveryJob` for `victim_stack`, violating the claimed binding.
