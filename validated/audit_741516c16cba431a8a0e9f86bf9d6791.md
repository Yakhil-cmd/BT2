### Title
Webhook signature verification is keyed off an attacker-controlled `repository.owner.login` field, decoupled from the `repository.full_name` the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using `repository_owner`, a field read straight out of the still-unverified JSON body [7](#0-6) . The actual data written by the event (which `Stack`/`Repository`/`PullRequest` records get updated) is determined later, independently, from `repository.full_name` inside each handler [8](#0-7) . Because these two fields are never cross-checked, the equality "organization whose secret authenticated this request" == "organization that owns the repository actually mutated" is not enforced.

### Finding Description
In a multi-organization Shipit deployment (`Shipit.github(organization:)` is looked up per-organization via `github_app_config`) [9](#0-8) , each org can have its own, independently-optional `webhook_secret` [10](#0-9) . `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's `webhook_secret` is not configured: `return true unless webhook_secret` [4](#0-3) .

`WebhooksController#verify_signature` picks *which* org's secret to check against using `repository_owner`, itself taken from the unauthenticated payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . Once the signature step passes (or is skipped because that org has no secret), `WebhooksController#create` dispatches the *entire* raw payload to the registered handlers [11](#0-10) . Every handler then resolves the target `Stack`/`Repository` from `repository.full_name`, a completely separate field of the same payload [2](#0-1) , e.g. `PushHandler#process` finds and syncs stacks by that repository [3](#0-2) .

Nothing validates that `repository.owner.login` (used to pick/skip the signature secret) matches the owner segment of `repository.full_name` (used to pick the stack that gets synced/updated). An attacker who knows of any configured organization lacking a `webhook_secret` (e.g., a low-priority/personal org onboarded to the same Shipit instance) can set `repository.owner.login` to that unsecured org while setting `repository.full_name` to any other, secured organization's repository tracked by Shipit — bypassing signature verification entirely for that target repository's webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`).

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated versus repository written." A successful bypass lets an unauthenticated attacker inject arbitrary GitHub webhook events for a repository/stack they don't control signature for. Depending on handler, this can:
- Force `GithubSyncJob` to fetch/append fabricated commit history via `PushHandler` for a foreign stack, feeding attacker-influenced SHAs into deploy pipelines [3](#0-2) .
- Manipulate `PullRequest` records (`ClosedHandler`, `LabeledHandler`, etc.) to archive/unarchive review stacks or alter merge/label state used by the merge queue for a repository the attacker does not control [12](#0-11) .

This can enable unauthorized state changes leading toward unauthorized deploys/merges without ever holding write access to the targeted repository, matching the Critical/High impact classes (unauthorized deploy/rollback/merge path).

### Likelihood Explanation
This requires: (1) the Shipit instance to be configured for multiple GitHub organizations, and (2) at least one of those configured organizations to have no `webhook_secret` set. Both are supported, documented configuration patterns (`secrets.github` keyed by organization, `webhook_secret` optional per org) rather than engine misuse. An attacker only needs to discover/guess the name of one such lightly-configured organization and knowledge of the target repository's `full_name` — no credentials, tokens, or repository access are required.

### Recommendation
Cross-validate that the organization used to select/verify the webhook signature matches the owner of `repository.full_name` (and any other repository references) before dispatching to handlers; reject the request otherwise. Consider making `webhook_secret` mandatory for every configured organization (fail closed rather than `return true` when absent), and derive the organization strictly from a value that cannot diverge from the resource actually being mutated.

### Proof of Concept
1. Shipit is configured with two GitHub organizations in `secrets.github`: `victim-org` (has `webhook_secret` set) and `test-org` (no `webhook_secret` configured).
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: push` and JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "test-org" }
  }
}
```
3. `verify_signature` computes `repository_owner` = `"test-org"`, loads `Shipit.github(organization: "test-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent/garbage) `X-Hub-Signature` header [4](#0-3) .
4. `create` proceeds and `PushHandler` resolves stacks via `repository.full_name` = `"victim-org/victim-repo"`, enqueuing `GithubSyncJob`/updating stacks belonging to `victim-org`, entirely bypassing the signature protection configured for `victim-org`.
