This confirms the vulnerability path clearly. The `WebhooksController` selects which GitHub App/organization's `webhook_secret` verifies the HMAC signature based on `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) , while every event handler independently resolves the target `Repository`/`Stack` from a completely separate field in the same untrusted JSON body — `payload.dig('repository', 'full_name')` [3](#0-2) . Multi-organization Shipit deployments configure one `webhook_secret` per organization [4](#0-3) , and `Shipit.github` picks the app purely from that owner-login field [5](#0-4) . Nothing cross-validates that the org used for verification matches the org embedded in `repository.full_name`. The `StatusHandler` writes a `Status` straight from attacker-controlled fields into `Commit#create_status_from_github!`, which drives continuous deployment/merge scheduling [6](#0-5) [7](#0-6) .

### Title
Webhook signature verified against `repository.owner.login`, but every handler acts on the unbound `repository.full_name` — cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The equality that must hold is: `organization used to select webhook_secret (repository.owner.login)` == `organization of the repository the handlers act on (repository.full_name)`. `WebhooksController#verify_signature` only checks the former; every `Shipit::Webhooks::Handlers::Handler` subclass derives its target `Stack`/`Repository` from the latter, independently, from the same unverified JSON body.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON body (`params.dig('repository','owner','login')` or `organization.login`) and uses it to pick the `GitHubApp` instance whose `webhook_secret` verifies the `X-Hub-Signature` HMAC [8](#0-7) . In a multi-org Shipit deployment (`config/secrets.yml` keyed by GitHub org, as documented) each org has its own `webhook_secret` [4](#0-3) ; `Shipit.github(organization:)` looks the app up purely by that string, case-insensitively, with no further binding [5](#0-4) .

After the signature check passes, `WebhooksController#create` dispatches the full parsed `params` hash to the registered handlers for the event type [9](#0-8) . Every handler resolves its target repository/stack via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a field entirely distinct from `repository.owner.login` used for signature-org selection [3](#0-2) . Nothing requires `repository.full_name`'s owner segment to equal `repository.owner.login`.

Someone who legitimately controls (or has installed the Shipit GitHub App for) any one organization onboarded to this Shipit instance knows/can obtain a valid HMAC over an arbitrary raw body using that organization's `webhook_secret` (e.g., by triggering real events, or, if that org's `webhook_secret` is blank/unset, `verify_webhook_signature` returns `true` unconditionally regardless of secret [10](#0-9) ). They can therefore submit a crafted body where `repository.owner.login` = their own (or any unset-secret) organization, satisfying `verify_signature`, but `repository.full_name` = `"victim-org/victim-repo"`, so the handler acts on a completely different organization's stacks.

### Impact Explanation
`StatusHandler` uses `params.sha`/`params.state`/etc. — taken straight from the forged body — to create a `Status` on any `Commit` matching that SHA across all stacks tracking that repo name, via `Commit#create_status_from_github!` [11](#0-10) . Creating a `success` status triggers `schedule_continuous_delivery` [7](#0-6) , which feeds continuous deployment and the merge queue. This lets an attacker who only controls a foreign/mis-scoped org's webhook credentials forge a fake "CI passed" signal for a victim repository's commit, causing an unauthorized deploy/merge of a commit that never actually passed CI — matching the Critical "unauthorized deploy" impact bucket. `PullRequestHandler`s (`OpenedHandler`, `LabeledHandler`, etc.) are similarly reachable and act on `params.repository.full_name`-resolved stacks, enabling forged provisioning/archival of review stacks belonging to unrelated repositories.

### Likelihood Explanation
Exploitability depends on the deployment using the multi-org config schema with more than one `webhook_secret` (or any org left with a blank `webhook_secret`, which is the documented default placeholder value, e.g. `webhook_secret: # nil` in every example config) [12](#0-11) . Given a blank secret returns `true` unconditionally in `verify_webhook_signature` [13](#0-12) , any deployment where even one configured organization lacks a `webhook_secret` allows unauthenticated forgery of events against every other onboarded organization's repositories, requiring no credentials at all beyond network access to `/webhooks`.

### Recommendation
After signature verification, require that the organization derived from `repository.full_name` (or `organization.login`) matches the `repository_owner` used to select and validate the signing secret, rejecting the request (422) on mismatch. Additionally, do not treat a missing/blank `webhook_secret` as "verification succeeds"; require an explicit opt-in (e.g., a distinct flag) to run in unsigned mode, and warn loudly when any configured organization has no secret configured in a multi-org setup.

### Proof of Concept
1. Deploy Shipit configured with two organizations: `orgA` (attacker-controlled or with `webhook_secret` unset) and `orgB` (victim, hosts the real `orgB/app` repo/stack).
2. Attacker computes `sha1=` HMAC over a crafted JSON body using `orgA`'s `webhook_secret` (or, if `orgA` has no secret configured, skips this — any signature is accepted).
3. Craft body: `event: status`, `repository: {"owner": {"login": "orgA"}, "full_name": "orgB/app"}`, `sha: <victim commit sha>`, `state: "success"`.
4. POST to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
5. `verify_signature` resolves `Shipit.github(organization: "orgA")` and validates against `orgA`'s secret — passes.
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (which belongs to `orgB/app`'s stack) and creates a `success` `Status`, triggering `schedule_continuous_delivery` and potentially an unauthorized deploy/merge for `orgB`'s repository, without ever possessing `orgB`'s credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
