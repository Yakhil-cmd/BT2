### Title
Missing Input-Size Limits on AA-Composed Payment Inputs Enables Unbounded Growth of Autonomous Agent Response Units - (File: aa_composer.js, validation.js)

### Summary
`validatePaymentInputsAndOutputs` explicitly exempts AA-generated units from the anti-spam array-length checks that apply to ordinary user payments, and the corresponding unit-size cap is exempted for AAs as well. An unprivileged unit poster who can pay tiny amounts to an AA address can inflate the number of unspent outputs (UTXOs) an AA must consume when it later needs to pay out (e.g. a `send_all`/balance-based payment), with no corresponding cap enforced either at composition time in `aa_composer.js` or at validation time in `validation.js`.

### Finding Description
For ordinary (non-AA) payments, `validatePaymentInputsAndOutputs` enforces: [1](#0-0) 
```
if (payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA)
    return callback("too many inputs");
if (payload.outputs.length > constants.MAX_OUTPUTS_PER_PAYMENT_MESSAGE && !storage.isGenesisUnit(objUnit.unit))
    return callback("too many outputs");
```
The `!objValidationState.bAA` condition means the input-count limit is deliberately skipped for AA-generated response units. Likewise, the overall unit-size cap is skipped for AAs: [2](#0-1) 
```
if (objUnit.headers_commission + objUnit.payload_commission > constants.MAX_UNIT_LENGTH && !bGenesis && !bAA)
    return callbacks.ifUnitError("unit too large");
```

When an AA needs to pay from its own balance (e.g. a `send_all`/change output that must cover accumulated storage size, or a payout that must sum to a target amount), `aa_composer.js`'s `completePaymentPayload`/`iterateUnspentOutputs` walks through the AA's spendable outputs and keeps `payload.inputs.push(input)` for every row returned by `readStableOutputs`/`readUnstableOutputsSentByAAs` until the target amount is reached: [3](#0-2) 
```
function iterateUnspentOutputs(rows) {
    for (var i = 0; i < rows.length; i++){
        var row = rows[i];
        var input = { unit: row.unit, message_index: row.message_index, output_index: row.output_index };
        arrUsedOutputIds.push(row.output_id);
        arrConsumedOutputs.push({asset: asset || 'base', amount: row.amount});
        payload.inputs.push(input);
        total_amount += row.amount;
        ...
    }
}
```
Unlike wallet-composed payments, which are bounded through `inputs.pickDivisibleCoinsForAmount` (whose SQL query is explicitly `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2`, see [4](#0-3) ), no equivalent LIMIT was found in the AA payment-composition path for `readStableOutputs`/`readUnstableOutputsSentByAAs` queries feeding `iterateUnspentOutputs`. Because both the composer-side selection and the validator-side check are unbounded/exempted for AAs, any unprivileged party can send many small (dust) payments to an AA address, inflating the number of outputs that AA owns. Any later AA-triggered payout (including a bounce/fee refund or a `send_all` output covering storage size, see [5](#0-4) ) can then be forced to enumerate an arbitrarily large set of these UTXOs as inputs, producing a response unit that is enormous and/or takes excessive time/DB round trips to build, without validation ever rejecting it for being "too large" or having "too many inputs" (since both checks are skipped for `bAA`).

### Impact Explanation
This can cause AA fund freezing: since the input-count/unit-size caps are skipped for AAs, a poisoned AA (whose balance is fragmented into a very large number of dust outputs by any external unit poster) can be driven to generate response units that fail to propagate/validate downstream (oversized payload, timeouts, or resource exhaustion during composition), preventing the AA from ever completing a payout that spends/consolidates its balance. This is a concrete "AA fund loss or freezing" outcome, not merely a resource/DoS nuisance, because the underlying anti-spam limits (`MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_UNIT_LENGTH`) were designed specifically to bound payment size but are intentionally bypassed for AA units with no substitute bound in the composer.

### Likelihood Explanation
Likelihood is moderate-to-high: any unprivileged actor can post many low-value payment units to a target AA address using ordinary payment messages (no special privilege, no AA-definition control needed), which is the minimal capability described in scope (unprivileged unit poster). No cooperation from witnesses, hubs, or other AAs is required; only patience/fees to create many dust UTXOs, and eventually triggering (or waiting for) an AA payout that must consolidate its balance.

### Recommendation
- Cap the number of inputs actually selected by `iterateUnspentOutputs`/`completePaymentPayload` in `aa_composer.js` to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (mirroring the `LIMIT` used in `inputs.pickDivisibleCoinsForAmount`), splitting large consolidations across multiple secondary AA responses if necessary.
- Reconsider or bound the `!objValidationState.bAA` exemptions in `validation.js` (input-count and unit-size checks) so AA-generated payments cannot silently grow without limit; if AAs must be allowed larger units, define an explicit, separately-enforced maximum rather than no limit at all.
- Consider adding protection against dust-output flooding of AA addresses (e.g., minimum payment size to AA addresses, or output consolidation/aggregation logic bounded by a fixed batch size per AA response).

### Proof of Concept
1. Deploy or identify a target AA that, on trigger, issues a `send_all` output back to the sender or otherwise pays out of its full balance (a common oscript pattern, see `test/samples/send_all.oscript`).
2. As an unprivileged unit poster, send a large number (e.g., tens of thousands) of minimal-value payment units to the AA's address over time; each individual payment unit is fully valid and inexpensive to post.
3. Once the AA's spendable-output set is large, trigger the AA in a way that requires it to sweep its balance (e.g., call the `send_all` message path).
4. Observe that `aa_composer.js`'s `iterateUnspentOutputs` iterates all matching outputs to build `payload.inputs` with no `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap, and that `validatePaymentInputsAndOutputs` in `validation.js` does not reject the resulting oversized/many-input unit because `objValidationState.bAA` is true — resulting in an unusually large response unit that is expensive or impossible to finalize, freezing the AA's ability to pay out.
