### Title
Sensitive private-payment data (blinding factors, amounts, addresses) and decrypted device-message plaintext are written to debug logs - ([File: indivisible_asset.js], [File: device.js])

### Summary
`ocore` contains multiple `console.log` calls that dump the full content of privacy-sensitive protocol data structures — blinding factors, amounts, addresses of private-asset outputs, and even fully decrypted device-to-device message plaintext — into application debug logs. This mirrors the Slack Morphism advisory's bug class (CWE-1258/CWE-200/CWE-212): sensitive material that is meant to stay confidential leaks through debug/log output rather than through the protocol itself, and any downstream log aggregation, crash reporter, or shared log file exposes it to whoever can read the logs.

### Finding Description
In `validatePrivatePayment` (indivisible assets), the code logs the entire spend-proof source object — including `blinding`, `amount`, and `address` — for every private-payment input received from a peer or paired device: [1](#0-0) 

This data is exactly the information that the private-payment protocol is designed to hide (see the "hidden" outputs in `payload.outputs` that are stripped of `address`/`blinding` before being shared, and the `output_hash` commitment scheme used everywhere else in `validation.js`, e.g. [2](#0-1) ). Once this data is written in cleartext to `console.log`, the confidentiality guarantee of the private/indivisible asset is undermined for anyone with access to node logs (which are commonly shipped to third-party log aggregators, crash reporting tools, or left on disk with looser permissions than the DB).

A second, broader instance is in `device.js`'s `decryptPackage`, which decrypts every incoming encrypted device message (used for wallet pairing, signing requests, private-payment chains, chat, etc.) and then logs the fully decrypted plaintext: [3](#0-2) 

Any message that a paired device or hub relay routes to this node — including `private_payments` bodies containing blinding factors/amounts (see `handlePrivatePaymentChains` in `wallet.js` at [4](#0-3) ) and `sign` requests containing `private_payloads` with output addresses/blindings ( [5](#0-4) ) — will have its full plaintext dumped to the log by this single `console.log` line, regardless of message type.

Similar leakage occurs elsewhere:
- `validateAndSavePrivatePaymentChain` logs the entire private-element chain: [6](#0-5) 
- `forwardPrivateChainsToOtherMembersOfOutputAddresses` logs the private chains: [7](#0-6) 
- `composeIndivisibleAssetPaymentJoint`'s `retrieveMessages` callback logs the composed messages, which for private assets include `spend_proofs`: [8](#0-7) 

### Impact Explanation
The private/indivisible-asset design relies on keeping `address`, `amount`, and `blinding` hidden from anyone except legitimate chain participants — that's the entire point of `output_hash` commitments and the staged reveal in `validatePrivatePayment`/`initPrivatePaymentValidationState`. Any unprivileged remote party (an AA counterparty, a paired device, or anyone who can get a private-payment chain accepted or forwarded to a victim node) can trigger these log lines by simply sending a private payment or a device-encrypted message. If the resulting debug log is later exposed (shared support logs, centralized logging infrastructure, crash dumps, or a misconfigured log file permission), an attacker gains the blinding factor and amount tied to a specific address — enough to de-anonymize a private transaction and, combined with the address, to potentially trace/spend-link outputs that the private-asset protocol was specifically designed to conceal. This is a confidentiality breach of exactly the kind CVE-2022-31162 addresses, scoped here to on-chain privacy guarantees rather than OAuth tokens.

### Likelihood Explanation
These log lines execute automatically on the normal message-processing path (`decryptPackage` runs on every decrypted device message; `validatePrivatePayment`/`validateAndSavePrivatePaymentChain` run on every private payment chain a node receives or is asked to forward). No special privilege or attacker capability beyond normal protocol participation (pairing a device, sending a private payment) is required to cause the sensitive data to be written to logs — the attacker doesn't even need to read the log himself if operators forward logs elsewhere, but likelihood of *this specific analog being exploitable* depends on whether logs are exposed outside the node operator's trust boundary, which is common in production deployments (log shipping, crash reporting, shared hosting).

### Recommendation
- Remove or gate all `console.log` calls that print full private-payment payloads, spend-proof components (`blinding`, `amount`, `address`), or decrypted device-message plaintext behind a `conf.bLightDebug`/verbose-only flag defaulting to off, similar to how the Slack Morphism fix removed sensitive fields from the `Debug` implementation.
- For `device.js`'s `decryptPackage`, drop the `console.log("decrypted: "+decrypted_message)` line entirely, or hash/truncate the field before logging.
- For `indivisible_asset.js` lines 125-133 and 243/272, log only non-sensitive identifiers (unit, message_index, output_index) rather than the full object containing `address`/`blinding`/`amount`.
- Audit `divisible_asset.js`, `wallet.js`, `private_payment.js`, `network.js` for the same pattern (`JSON.stringify` of chain/payload objects) and apply the same redaction.

### Proof of Concept
1. Attacker pairs a device with the victim wallet (or is already a private-payment counterparty).
2. Attacker sends a `private_payments` device message (or forwards a private asset payment) to the victim, per `handlePrivatePaymentChains` (`wallet.js:955`).
3. On the victim node, `device.js`'s `decryptPackage` decrypts the message and executes `console.log("decrypted: "+decrypted_message)`, writing the full JSON — including private outputs with `address`/`blinding`/`amount` — to stdout/log file.
4. Validation proceeds into `indivisible_asset.js`'s `validatePrivatePayment`, which additionally logs the spend-proof object with `address`, `amount`, and `blinding` in cleartext (`indivisible_asset.js:125`).
5. Anyone with read access to the victim's log output (log aggregation service, support-shared logs, crash reports) now has the private/blinded transaction details that the protocol otherwise keeps confidential.
