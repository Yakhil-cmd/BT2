### Title
Arbitrary account STX theft via unauthenticated `sender` field derived from attacker-controlled `PreStxOp.output` - (File: stackslib/src/chainstate/burn/operations/transfer_stx.rs)

### Summary
`TransferStxOp::check` only rejects `sender == recipient`; it performs no check that the `sender` address is actually authorized by the entity broadcasting the burnchain operation. The `sender` field is never derived from a Stacks-level signature — it is copied verbatim from `PreStxOp.output`, a field that the attacker fully controls when constructing their own `PreStxOp` Bitcoin transaction. This lets an attacker designate *any* Stacks address (including a victim's, who never signed anything) as the `sender` of a `TransferStxOp`, and `process_transfer_ops` will debit that address's real STX balance.

### Finding Description
The broken equality: **STX debited by the applied `TransferStxOp`** should equal **STX owned by the party who cryptographically authorized the burnchain input/operation**. Instead it only equals **whatever `StacksAddress` the attacker wrote into `PreStxOp.output`**.

Trace:
- `PreStxOp.output` is parsed straight from the first Bitcoin output address of the attacker's own `PreStxOp` transaction, with zero linkage to any Stacks signature or to the address that signed the transaction's Bitcoin input: [1](#0-0) 
- `Burnchain::classify_transaction` resolves `sender` for the follow-on `TransferStxOp` purely from `pre_stx.output`: [2](#0-1) 
- `TransferStxOp::parse_from_tx` accepts this `sender` unconditionally and only extracts `recipient`/`amount` from the wire data: [3](#0-2) 
- `TransferStxOp::check` (the only validation gate) checks `transfered_ustx != 0` and `sender != recipient`; it never checks that `sender`'s Stacks key authorized the transfer, nor that `sender` corresponds to whoever actually signed/funded the Bitcoin inputs of the `PreStxOp`/`TransferStxOp` pair: [4](#0-3) 
- The sortition-processing check dispatch calls exactly this `check()` for `TransferStx`, with no additional authorization step, and explicitly notes `PreStx` requires *no* `check()` at all: [5](#0-4) 

Exploit flow: attacker broadcasts `PreStxOp` with `output = victim_stacks_address` (any address of the attacker's choosing, entirely unrelated to who signs the PreStx input), funded by the attacker's own Bitcoin UTXO. They then broadcast a `TransferStxOp` spending `vout=1` of that `PreStxOp` txid, with `recipient = attacker_address`. `classify_transaction` looks up `sender = pre_stx.output = victim`, `TransferStxOp::check` passes because `sender != recipient`, and `process_transfer_ops`/`run_stx_transfer` in `stackslib/src/chainstate/stacks/db/blocks.rs` executes `run_stx_transfer(victim, attacker, amount)`, debiting the victim's real STX balance without any Stacks-level signature or proof that the attacker controls the victim's key.

Existing guards fail because: `check()` in transfer_stx.rs only guards against self-send, never against unauthenticated sender designation; and `PreStxOp` itself has no `check()` validating that its `output` corresponds to the signer of its own input.

### Impact Explanation
Any account's unlocked STX balance can be stolen by an attacker who never possesses that account's private key — pure theft of STX from an arbitrary victim address, matching the Critical impact category ("theft ... of locked STX" — here, unlocked/general STX, but the mechanism generalizes: the same `pre_stx.output`-as-sender pattern is reused by `StackStxOp`/`DelegateStxOp` for locking operations, meaning the same broken authorization could also let an attacker lock/stake a victim's STX under attacker-controlled `signer_key`/`reward_addr`). Repeatable per PreStx/TransferStx pair; the attacker only pays Bitcoin transaction fees, so it is cheap and can be repeated against any address with a positive STX balance.

### Likelihood Explanation
Preconditions: attacker needs only their own Bitcoin funds to pay for the two chained Bitcoin transactions (`PreStxOp` + `TransferStxOp` spending its `vout=1`); no PoX cycle phase, membership, or protocol-bond state gates this path since it happens entirely in burnchain-op processing, independent of pox-5 contract logic. Attacker cost is a Bitcoin fee only, and the attack is fully repeatable against any STX-holding address as long as balance > 0.

### Recommendation
Bind `PreStxOp.output` (and hence the derived `sender`) to a cryptographic proof of ownership — e.g., require that the address be verifiably derived from the public key that signed the `PreStxOp`'s own funding input (so `output` must equal the p2pkh/p2wpkh address of the signer of input 0), rather than trusting an arbitrary output script chosen by the broadcaster. At minimum, `TransferStxOp::check` (and the analogous checks for `StackStxOp`/`DelegateStxOp`/`VoteForAggregateKeyOp`) must validate that `sender` is provably controlled by whoever authorized the underlying Bitcoin transactions, not merely take `pre_stx.output` at face value.

### Proof of Concept
Rust integration test (extending the pattern already used in `stacks-node/src/tests/epoch_21.rs` around lines 933-997):
1. Generate `victim_sk`/`victim_addr` and fund `victim_addr` with STX via genesis/faucet; assert `get_balance(victim_addr) == V > 0`.
2. Generate `attacker_sk` with its own Bitcoin UTXO (not derived from `victim_sk`).
3. Submit `PreStxOp { output: victim_addr, .. }` signed/funded solely with `attacker`'s Bitcoin key (`BurnchainOpSigner::new(attacker_sk)`), i.e., the input(0) signer is `attacker`, not `victim`.
4. Submit `TransferStxOp { sender: victim_addr, recipient: attacker_stx_addr, transfered_ustx: V, .. }` spending `vout=1` of the PreStxOp txid, again signed only by `attacker`'s Bitcoin key.
5. Mine blocks until processed.
6. Assert broken equality is exploited: `get_balance(victim_addr) == 0` (was `V`) and `get_balance(attacker_stx_addr) == V`, despite `victim_sk` never signing anything (neither Bitcoin nor Stacks). Compare against the expected-safe equality `sender_of_debited_balance == controller_of_signed_input`, which fails.

impl TransferStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.transfered_ustx == 0 {
            warn!("Invalid TransferStxOp, must have positive ustx");
            return Err(op_error::TransferStxMustBePositive);
        }
        if self.sender == self.recipient {
            warn!("Invalid TransferStxOp, sender is recipient");
            return Err(op_error::TransferStxSelfSend);
        }
        Ok(())
    }
