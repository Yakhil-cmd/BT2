### Title
Global cross-tenant Status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)`, with no filter tying the payload's `repository` to `commit.stack.repository`. Any validly-signed `status` webhook whose `sha` collides with a `Commit` row belonging to an unrelated stack writes a forged `Status` onto that unrelated stack, regardless of which repository actually originated the event.

### Finding Description
The broken binding is: `payload['repository']['full_name'] == commit.stack.repository.full_name` for every `Commit` mutated by the handler. This equality is never checked anywhere on the write path.

`StatusHandler#process` does: [1](#0-0) 
It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` against the entire `commits` table, unscoped by repository. Compare this to the base `Handler` class, which defines exactly the scoping primitive that would be needed but is unused here: [2](#0-1) 
`stacks` resolves `Repository.from_github_repo_name(repository_name)` before acting, but `StatusHandler` never calls `stacks` or `repository_name` at all — it only declares a params schema that doesn't even require `repository` fields: [3](#0-2) 

Upstream, `WebhooksController#verify_signature` only authenticates that the payload came from *an* organization known to Shipit — it selects the `GitHubApp`/secret using `repository_owner` from the payload itself and does not bind the payload's declared repository to any specific stack: [4](#0-3) [5](#0-4) 

Root cause: HMAC verification only proves "this request came from GitHub for organization X" (or, in a legitimately signed request, simply "this request has a valid signature for the org whose secret was used"); it proves nothing about which specific repository/stack the event should apply to. `StatusHandler` then trusts a global SHA lookup with no secondary check, so the org-level authentication is silently laundered into a database-wide write.

Two concrete ways to trigger the collision, both compatible with an unprivileged attacker:
1. As stated in the question: the attacker crafts a `status` payload claiming `repository.full_name: 'attacker/own-repo'` for a `sha` that already exists as a `Commit` row on victim Stack V, and gets it validly signed because they control (or are a legitimate low-privileged member of) an org/app installation registered in Shipit's multi-org config (`Shipit.github_app_config`, illustrated by `test/dummy/config/secrets_double_github_app.yml`), where the webhook secret used for signature verification is not repository-specific.
2. Even without any secret knowledge at all: the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904` (or any byte-for-byte reproducible commit object with matching author/committer/tree/parents/timestamps) is deterministic across all git repositories. An attacker who owns any Shipit-tracked repository can push a commit reproducing a target sha and then legitimately set a GitHub commit status on their own repo (fully within their own privileges); GitHub delivers a correctly-signed `status` webhook for that event. `StatusHandler` will match it against *every* `Commit` row across the installation sharing that sha, including rows belonging to entirely unrelated stacks/orgs, without the attacker ever forging `repository.full_name` or touching a secret.

No existing guard catches this: `verify_signature` only checks the HMAC against an org-level secret, `drop_unhandled_event`/`check_if_ping` are unrelated, `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`) does not include or validate `repository` at all, and `Commit`/`Status` models have no uniqueness or ownership constraint tying a sha to a single repository (git shas are content hashes, not globally unique per-repo identifiers by design).

### Impact Explanation
A successful request creates a `Status` row (`Shipit::Status`) on an arbitrary victim `Commit`/`Stack`, forging CI state (`success`/`failure`/etc.) for a repository the attacker does not own and never authenticated against. Because `Status#after_create` calls `enable_ci_on_stack` and `Commit#deployable?`/merge-queue logic depend on status state, this can unblock deploys or the merge queue (`ProcessMergeRequestsJob` is enqueued on transitions per `test/models/commits_test.rb:763-777`) on the victim stack, i.e. it can cause an unauthorized deploy/merge decision on a repository that never signed off on that CI result. This is repeatable against any stack in the same Shipit installation whose `Commit.sha` the attacker can predict or reproduce, and it crosses organizational boundaries whenever a single Shipit instance hosts multiple orgs/repos (as explicitly supported per `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`). This matches "a payload for one repository mutating another's stack/commit" — Critical.

### Likelihood Explanation
Preconditions: Shipit must have a `Commit` row for the target sha (normal for any stack under CI), and the attacker needs either (a) an org/app registration in Shipit whose webhook secret they can get GitHub to sign a crafted-looking payload with, or (b) the ability to reproduce an identical git commit object (trivial for the empty-tree sha, feasible for any public commit whose author/committer/timestamp/tree/parents are known). No Shipit session, API token, or maintainer role is required. The attack costs nothing beyond controlling one Shipit-tracked repo/org and is fully repeatable per request.

### Recommendation
In `StatusHandler#process` (and any other handler doing sha/global lookups), scope the query to the repository declared (and authenticated) in the event, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or add a join/verify step ensuring `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`, mirroring the `Handler#stacks`/`repository_name` pattern already used elsewhere. Also require `repository` in the `StatusHandler` params schema so a missing/mismatched repository is rejected at parse time rather than silently ignored.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
```ruby
test ":status webhook only applies to commits in the matching repository" do
  request.headers['X-Github-Event'] = 'status'
  victim_commit = shipit_commits(:cyclimse_first) # belongs to a different fixture stack than :shipit
  refute_equal victim_commit.stack.repository.full_name, 'attacker/own-repo'

  body = {
    sha: victim_commit.sha,
    state: 'success',
    context: 'ci/travis',
    repository: { full_name: 'attacker/own-repo', owner: { login: 'shopify' } } # signed via same org secret
  }.to_json

  assert_no_difference 'victim_commit.statuses.count' do
    post :create, body:, as: :json
  end
end
```
Assert both sides of the binding explicitly: `payload['repository']['full_name']` (`'attacker/own-repo'`) must equal `victim_commit.stack.repository.full_name` (the real fixture repo) for the write to be legitimate; currently the test would fail (`Status` gets created) because `StatusHandler#process` never checks this equality — confirming the vulnerability.
