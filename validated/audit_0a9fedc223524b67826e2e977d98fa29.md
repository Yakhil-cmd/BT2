### Title
Cross-organization webhook signature confusion allows unauthorized writes to another tenant's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify the request against based on an **attacker-controlled payload field** (`repository.owner.login` / `organization.login`), while the downstream event handlers act on a **different field of the same payload** (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. In a multi-organization Shipit deployment, this breaks the intended binding "organization whose secret authenticated the request == repository/organization being written to."

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `secrets.github` in multi-tenant mode: [3](#0-2) 

The signature itself is only checked against `request.raw_post` using whichever organization's secret was selected by `repository_owner` — nothing ties the *verified organization* to the fields the handlers subsequently trust: [4](#0-3) 

Handlers, however, resolve the target `Stack`/`Repository` from a **separate** field of the same JSON body, `repository.full_name`, not from `repository.owner.login`: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` and `repository.full_name` are two independent, attacker-supplied strings inside the same unsigned-until-verified JSON body, an attacker who legitimately administers a GitHub App/organization onboarded to the same Shipit instance (and therefore knows that org's `webhook_secret`, which they configured themselves) can craft a payload where:
- `repository.owner.login` = their own organization ("orgA") → so `verify_signature` picks orgA's `webhook_secret` and the HMAC matches.
- `repository.full_name` = `"orgB/some-repo"` → a different tenant's repository tracked by the same Shipit instance.

The signature check passes (it's valid for orgA's secret and the exact raw body), yet the handler that actually mutates state (e.g. `PushHandler`) resolves and acts on orgB's `Stack` via `Repository.from_github_repo_name(params.repository.full_name)`.

### Impact Explanation
This breaks the trust binding: *organization that authenticated (orgA, via signature) ≠ repository that is written (orgB, via `full_name`)*. Concretely, for `push` events this lets the attacker enqueue `GithubSyncJob` for an arbitrary victim stack with an attacker-chosen `expected_head_sha`: [7](#0-6) 
which triggers commit ingestion and, on stacks with continuous deployment enabled, downstream automatic deploy scheduling — an unauthorized cross-tenant write/deploy trigger without ever needing orgB's own webhook secret, GITHUB_TOKEN, or repository write access. The same class of confusion applies to other handlers keyed by `repository.full_name` (pull-request labeled/unlabeled/reopened/closed handlers that archive/unarchive review stacks), letting an attacker who controls one tenant's GitHub App config manipulate a different tenant's review-stack lifecycle.

### Likelihood Explanation
Exploitability requires only that the Shipit instance is configured for multiple GitHub organizations (the `secrets.github` multi-org schema handled in `Shipit.github_app_config`) and that the attacker legitimately administers a GitHub App/organization onboarded there — a low bar relative to the required capabilities in scope (no `ApiClient` token, no `GITHUB_TOKEN`, no privileged Shipit account, no repository write access to the victim's repository, and no interception is needed). The attacker only needs a valid webhook secret they themselves control and the ability to POST an arbitrary JSON body to `/webhooks`.

### Recommendation
Bind the verified organization to the actual repository being acted upon: after signature verification, re-derive the acting organization strictly from `repository.full_name`'s owner segment (or the org used by the specific event handler) and reject the request if it doesn't match the organization whose secret validated the signature. Alternatively, verify the signature independently per-repository/per-installation using the installation context (e.g., include/require the GitHub App installation id in the verification path) rather than trusting a payload field that handlers don't subsequently rely on.

### Proof of Concept
1. Configure Shipit multi-org: onboard `orgA` (attacker-controlled) and `orgB` (victim) as separate GitHub Apps, each with its own `webhook_secret` in `secrets.github`.
2. Attacker computes `sha1=HMAC(orgA_webhook_secret, body)` for a crafted push payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository.owner.login`), which succeeds because the signature matches orgA's secret.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on orgB's stack — a write the attacker was never authorized to trigger.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
