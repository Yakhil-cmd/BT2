This confirms `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [1](#0-0) , so membership in a `Shipit.github_teams` team grants authorization. The vulnerability is confirmed.

### Title
Cross-organization `Team` hijack via `github_id` collision in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that the webhook payload's `organization.login`/`repository.owner.login` matches the org whose `webhook_secret` produced the HMAC signature; it never binds that authenticated organization to the specific `Team` row being mutated downstream. `MembershipHandler#find_or_create_team!` looks up teams solely by the GitHub-global `team.id` (`github_id`), so an attacker who legitimately owns a GitHub App installation on their own organization can forge a `membership` webhook, correctly signed with their own secret, whose `team.id` collides with a victim `Team#github_id` already stored in Shipit's database, and thereby add an attacker-controlled `User` to that victim team.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:

`authenticating_org(payload.organization.login) == Team.find_by(github_id: payload.team.id).organization`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) , then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [3](#0-2) . This only verifies the payload was signed with the secret belonging to `repository_owner` — it says nothing about which `Team` record the payload is entitled to touch.
2. `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler` [4](#0-3) .
3. `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [5](#0-4) . The `organization:` assignment inside the block only executes on **creation**. `github_id` is a GitHub-global integer, not scoped per organization, and the `teams` table has no unique constraint on `github_id` alone (only a unique index on `[organization, slug]`) [6](#0-5) .
4. If the attacker sends `team.id` equal to an existing victim `Team#github_id`, `find_or_create_by!` finds the pre-existing row (owned by the victim org) and skips the block entirely — `team.organization` is left untouched, still the victim's org.
5. `MembershipHandler#process` then calls `team.add_member(member)` for `action == 'added'`, where `member` is `User.find_or_create_by_login!(params.member.login)` — fully attacker-controlled [7](#0-6) . `Team#add_member` appends the member to `members` (backed by `Membership`) with no re-check of the authenticating organization [8](#0-7) .

Attacker's exact request: a `membership` webhook, `action: added`, `organization: { login: "attacker-org" }`, signed with the attacker's own valid `webhook_secret` for `attacker-org` (which they legitimately control), `team: { id: <victim_team.github_id>, name, slug, url }`, `member: { login: "attacker-controlled-login" }`. `verify_signature` passes because the signature matches `attacker-org`'s secret. `find_or_create_team!` resolves to the victim's existing `Team` row by `github_id`, and the attacker's user is added as a `Membership` on it.

Existing guards fail because: `verify_signature` validates payload authenticity per-organization but is never re-checked against the specific resource (`Team`) being mutated; the `ExplicitParameters` schema only validates types/presence, not cross-org identity; `drop_unhandled_event` and `check_if_ping` are irrelevant to this path.

### Impact Explanation
A successful exploit adds an attacker-controlled `Shipit::User` as a `Membership` on a victim's `Team` row. If that victim team is one of the entries returned by `Shipit.github_teams` (the configured authorization teams, see `lib/shipit.rb` `github_teams` and `app/models/shipit/user.rb#authorized?`) [9](#0-8) [1](#0-0) , the attacker's user gains `authorized?` status and everything gated behind it. This is repeatable against any `Team#github_id` the attacker can guess or discover (GitHub team IDs are visible via the public GitHub API for any team the attacker can query), and does not require any privileged Shipit credentials — only a self-owned GitHub App installation. This matches the "High - escalation into `Shipit.github_teams` authorization" impact category.

### Likelihood Explanation
Preconditions: the attacker needs their own GitHub organization with a GitHub App installation configured in Shipit (a normal, unprivileged setup step available to anyone who can install a GitHub App on an org they own), and needs to learn or guess a victim `Team#github_id` (a small integer, discoverable via GitHub's public team API or brute-forced since Shipit's `find_or_create_by!` is idempotent and returns success either way — no error signals whether the ID collided or created a new row, though the resulting `Membership.count` diff would differ, requiring some blind interaction). This is realistic and repeatable at attacker's chosen pace.

### Recommendation
Scope the `Team` lookup in `MembershipHandler#find_or_create_team!` to the authenticated organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, or explicitly verify `team.organization == params.organization.login` before calling `add_member`/`members.delete`, raising/dropping the event on mismatch.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
```ruby
test ":membership does not add member to a team owned by a different organization" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X
  attacker_org = 'attacker-org'
  Shipit.stubs(:github).with(organization: attacker_org).returns(stub(verify_webhook_signature: true))

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker-controlled-user' },
    repository: { owner: { login: attacker_org } }
  }.to_json

  assert_no_difference -> { victim_team.reload.members.count } do
    post :create, body: payload, as: :json
  end
end
```
Assert both sides of the binding: before the request, `victim_team.organization == 'shopify'` and `victim_team.members` excludes the attacker user; after the request, if the vulnerability exists, `victim_team.members` includes the attacker user despite the request having authenticated as `attacker-org`, violating `authenticating_org == Team.organization`.
