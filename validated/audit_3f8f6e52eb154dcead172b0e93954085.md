### Title
Cross-organization webhook forgery via mismatched signature-selection field vs. acted-upon repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), while every downstream `Webhooks::Handlers::Handler` resolves the actual `Stack`/`Repository` to mutate using a *different* payload field, `payload.dig('repository','full_name')`. Because `/webhooks` is a plain unauthenticated `ActionController::Base` endpoint whose only trust gate is the HMAC check, and the HMAC-covered JSON body is entirely attacker-supplied, nothing enforces that `repository.owner.login` (used to pick the secret) is the same organization referenced by `repository.full_name` (used to write data). An org whose administrator legitimately knows their own `webhook_secret` (they chose it when creating their GitHub App, per `docs/setup.md`) can sign a payload whose `repository.owner.login` is their own org but whose `repository.full_name` names a repository belonging to a different, unrelated org hosted on the same Shipit instance.

### Finding Description [1](#0-0) 
`verify_signature` computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)` to fetch the matching `GithubApp`, then verifies the signature against that app's `webhook_secret`: [2](#0-1) 

Every event handler, however, independently derives the entity to act on from a *different* field of the same JSON body: [3](#0-2) 

For example `OpenedHandler` looks up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to decide which repository/review-stack to provision: [4](#0-3) 

`verify_signature` never checks that `repository.owner.login`/`organization.login` (the value used to pick the secret) matches the owner encoded in `repository.full_name` (the value used to identify what gets written). Legitimate GitHub-generated webhooks never diverge on these two fields because GitHub itself derives both from the actual event's repository, so this gap is invisible in normal operation. It only becomes exploitable because `Shipit` explicitly supports multiple independent GitHub Apps/organizations sharing one Shipit instance (`docs/setup.md`, "Using Multiple GitHub Applications"), each with its own `webhook_secret` chosen by that org's own administrator at GitHub App creation time. Any onboarded organization's administrator therefore legitimately possesses a valid `webhook_secret` for *their own* org, but that secret is trusted to authorize writes to *any* repository named in `repository.full_name`, including repositories owned by a completely different onboarded organization.

The binding that should hold but does not:
`organization authenticated via webhook_secret(repository.owner.login) == organization implied by repository.full_name acted upon by the handler`

Before the attack: Org A's secret only ever appears on genuine GitHub deliveries where `owner.login` and `full_name`'s owner are the same org (A).
After the attacker's crafted POST: `owner.login = "org-a"` (secret known to attacker) while `full_name = "org-b/target-repo"` (a repository Shipit hosts for an unrelated tenant B). Verification passes using org-a's secret, but the `full_name` field routed to the handler now selects org B's `Repository`/`Stack`.

### Impact Explanation
Depending on the `X-Github-Event` chosen, this crosses the tenant/repository trust boundary in several concrete ways once signature verification is bypassed for org B's data:
- `push` events enqueue `GithubSyncJob` for org B's stack, and `status`/`check_suite` events fabricate commit statuses / trigger `RefreshCheckRunsJob` for org B commits — false CI/status data that can unblock deploys or the merge queue for a stack the attacker does not own.
- `pull_request` events (`opened`, `labeled`, `reopened`, etc.) create/archive/deprovision Review Stacks belonging to org B's repository (`review_stack_adapter.rb`), an unauthorized write into org B's infrastructure.
- `membership` events create/delete `Team`/`Membership` records — since `Shipit.github_teams` gates `User#authorized?`, forging membership data can be used to attempt to manipulate team membership, touching the `Shipit.github_teams` authorization surface.

This satisfies the required "cross-repository writes" / "unauthorized deploy" Critical-High impact bucket: an entity authenticated as Org A is able to cause writes against Org B's stacks/repositories/teams with no legitimate authorization from Org B.

### Likelihood Explanation
Requires: (1) the Shipit deployment to host more than one GitHub organization (an explicitly documented, supported configuration), and (2) the attacker to be an administrator (or someone in possession of the `webhook_secret`) of at least one of the onboarded, lower-trust organizations. This is a realistic scenario for any Shipit instance that lets multiple independent teams/orgs self-onboard (common in a platform-team setup), since each org's own admin necessarily knows their own `webhook_secret` by design. No GitHub App private key, session, or `ApiClient` token is needed — only the ability to send an arbitrary HTTP POST to `/webhooks` and knowledge of one tenant's `webhook_secret`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), cross-check that the organization used to select the `webhook_secret` (`repository_owner`) matches the owner segment parsed out of `repository.full_name` (and any other organization-identifying field used later, e.g. for `membership` events); reject the webhook (422) if they diverge. More robustly, resolve the target `Repository`/`Stack` strictly by the same organization identity that was authenticated, rather than trusting a second, independently-attacker-controlled field from the same payload.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s "Using Multiple Github Applications" section: `org-a` (attacker's own org, webhook secret `S_A` known to attacker) and `org-b` (victim org, unrelated repository `org-b/target-repo`).
2. Attacker crafts a `push` (or `pull_request`) JSON body with:
   ```json
   {
     "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/target-repo"},
     ...event-specific fields referencing org-b/target-repo commit/PR data...
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` using the secret they legitimately know for `org-a`.
4. POST to `/webhooks` with `X-Github-Event: push` and the above signature.
5. `verify_signature` resolves `Shipit.github(organization: "org-a")`, verifies successfully against `S_A` — [5](#0-4)  — and the request proceeds.
6. `Shipit::Webhooks.for_event('push')` handlers use `payload.dig('repository','full_name')` = `"org-b/target-repo"` to locate and act on `org-b`'s `Stack`, e.g. enqueuing `GithubSyncJob` for that stack — [3](#0-2)  — despite the request only having been authenticated as `org-a`.
