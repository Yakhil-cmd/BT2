## Title
Cross-repository status injection via unscoped `Commit.where(sha:)` allows unauthorized merge of victim PR - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `sha` alone with no repository/stack scoping, unlike every sibling handler (`PushHandler`, `CheckSuiteHandler`) which first resolve `stacks` from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`. Because commit SHAs are content-addressed and identical across forks/mirrors of the same tree, an attacker who legitimately controls a different, unrelated repository (with its own valid, correctly-signed webhook) can cause a `Status` row to be attached to a `Commit` belonging to a victim's stack whenever that commit's SHA happens to match — and since PR head SHAs are public, an attacker can trivially reproduce the identical commit object (fork the victim repo, or push the exact same tree/parents/authoring metadata) so its SHA collides with the victim's queued `MergeRequest#head`.

## Finding Description
The broken binding: the question assumes `identity(webhook) == identity(stack that owns the commit with that sha)`. In this codebase that binding is **never enforced** for the `status` event.

`StatusHandler#process`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This queries `Commit` globally by `sha` across **all stacks/repositories**, with no filter on `payload.dig('repository', 'full_name')`. Compare to `PushHandler` and `CheckSuiteHandler`, which both resolve `stacks` (scoped to the repository named in the payload) before touching any commit: [2](#0-1) [3](#0-2) [4](#0-3) 

`verify_signature` only proves the payload was signed by `Shipit.github(organization: repository_owner)` for the organization named in the *attacker's own* payload — it authenticates "this webhook really came from GitHub for org X," not "this status applies to a commit belonging to org X's stacks": [5](#0-4) 

Once `Commit.where(sha:)` matches the victim's commit row (owned by `victim_stack`), `create_status_from_github!` → `add_status` writes a `Status` and, on transition to `pending`/`success`, calls `stack.schedule_merges`: [6](#0-5) [7](#0-6) 

This enqueues `ProcessMergeRequestsJob`, which calls `merge_request.reject_unless_mergeable!` and, if `all_status_checks_passed?`, `merge_request.merge!`: [8](#0-7) 

`all_status_checks_passed?`/`any_status_checks_failed?` read `head.statuses_and_check_runs`, which now includes the attacker-injected `success` status for the required context: [9](#0-8) [10](#0-9) 

`merge!` then calls `stack.github_api.merge_pull_request` for the victim's PR: [11](#0-10) 

**Attacker's exact request**: a `status` webhook, correctly signed by GitHub for a repository/org the attacker legitimately controls (or any org configured in Shipit), whose `sha` field equals the SHA of the victim stack's queued `MergeRequest#head` commit, `state: "success"`, `context` matching `stack.cached_deploy_spec.merge_request_required_statuses`. Achieving SHA equality requires only that the attacker reproduce (fork/replay) the exact same git commit object as the victim's PR head — trivial since GitHub commit SHAs are public and content-addressed, and forks of the same repository naturally share identical commit objects/SHAs for unmodified commits.

Existing guards fail here specifically: `verify_signature` validates only the *authenticity of the sender*, not that the sender is authorized to speak for the *stack owning the target commit*; `drop_unhandled_event` and `ExplicitParameters` schema (`requires :sha, :state`) don't add any ownership scoping; there is no `stacks`/`Repository.from_github_repo_name` lookup at all in `StatusHandler`, unlike its siblings.

## Impact Explanation
An attacker who controls any repository with a legitimately signed webhook path into this Shipit instance can inject a fabricated `success` status onto an arbitrary commit belonging to a **different tenant's stack**, as long as that commit's SHA is known/reproducible. Combined with `merge_queue_enabled?`/`ProcessMergeRequestsJob`, this results in `Shipit::MergeRequest#merge!` firing `stack.github_api.merge_pull_request` for the victim's PR without its CI ever having passed — an unauthorized merge driven by a payload that mutates a different repository's stack/commit state than the one that authenticated the webhook. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge." It is repeatable against any stack/repository configured in the same Shipit instance, for any commit SHA the attacker can reproduce, and requires no privileged Shipit role, GitHub team membership, or Shipit secret.

## Likelihood Explanation
Preconditions: `merge_queue_enabled?` on the victim stack, a queued `MergeRequest` with a known head SHA (public via GitHub PR metadata), and a required-status context configured in `merge_request_required_statuses` (also discoverable, e.g. via public `.shipit.yml`/branch protection or trial-and-error). Attacker cost is low: they need any repository in the same Shipit deployment (or any GitHub org Shipit is configured against) capable of emitting a real, correctly-signed `status` webhook — e.g., their own fork or an unrelated onboarded repo — and they need to get a commit with the colliding SHA to exist (trivial via forking, since forks preserve identical commit objects/SHAs). No Shipit credentials, GitHub App private key, or webhook secret of the victim's org are needed. The exploit is deterministic and repeatable per target commit.

## Recommendation
Scope `StatusHandler#process` (and any other commit-touching handler) to the repository named in the webhook payload, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks` helper (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) so a status can only ever be attached to a commit belonging to the stack whose repository actually emitted the webhook.

## Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create two stacks: `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/repo`), each with a `Commit` sharing the **same `sha`** (`"deadbeef..." `), simulating a forked/replayed commit.
2. On `victim_stack`, create a `MergeRequest` in `pending` with `head` = the shared-sha commit, `mergeable: true`, no statuses for the required context (`ci/circle`), and stub `victim_stack.cached_deploy_spec.merge_request_required_statuses` to `['ci/circle']`.
3. Stub `victim_stack.github_api.merge_pull_request` and `pull_requests`/`delete_branch` (mocha `.expects`) — assert they are called exactly once.
4. Build a webhook payload `{ "sha" => shared_sha, "state" => "success", "context" => "ci/circle", "repository" => { "full_name" => "attacker/repo", "owner" => { "login" => "attacker" } } }` and invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, since the finding is about the handler's missing repo scoping, not signature bypass).
5. Assert: `victim_stack's commit.statuses.count` increased by 1 even though the webhook's `repository.full_name` was `attacker/repo`, not `victim/repo` — i.e. `commit.stack_id == victim_stack.id` while `payload['repository']['full_name'] != victim_stack.repository.full_name` (the broken equality).
6. Run `ProcessMergeRequestsJob.new.perform(victim_stack)` and assert `merge_request.reload.merged?` is true and `github_api.merge_pull_request` was invoked — demonstrating the unauthorized merge driven entirely by the attacker-controlled webhook.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
