### Title
Creator fees permanently locked when the creator's associated token account becomes frozen/unusable, with no alternative recipient or recovery path - (File: programs/cp-swap/src/instructions/collect_creator_fee.rs, programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs)

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` are the only two instructions that can move accumulated `creator_fees_token_0` / `creator_fees_token_1` out of the pool vaults, and both instructions hard-code the destination to a single deterministic associated-token account (ATA) derived from the pool creator's key. If that specific ATA ever becomes unable to receive tokens (e.g. it is frozen by the mint's freeze authority, similar in effect to a blacklisted address in the referenced bridge bug), the fee transfer will always fail, and there is no mechanism to redirect the payout to a different account or otherwise recover the accrued fees — mirroring the "no way to recover funds" bug class in the reported `AvailBridge.receiveERC20` issue.

### Finding Description
Both fee-claiming instructions constrain the destination accounts to a single PDA-style ATA tied to `creator`: [1](#0-0) 

and the permissionless variant is identical in structure: [2](#0-1) 

The transfer call uses `token_0_program`/`token_1_program` (which may be Token-2022) to move the accumulated fee balances to these fixed accounts, and only zeroes out the pool's fee ledger after a successful transfer: [3](#0-2) 

Pool initialization performs no check that would reject mints with a freeze authority — `is_supported_mint` only inspects a whitelist of Token-2022 *extensions* (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`); a mint's base `freeze_authority` field (present in both classic SPL Token and Token-2022 mints) is never examined: [4](#0-3) 

Because Solana transactions are atomic, if `transfer_checked` fails (e.g., because the creator's ATA has been frozen by the mint's freeze authority), the whole instruction reverts and `creator_fees_token_0`/`creator_fees_token_1` are never cleared — so the accrued fees stay parked in the pool vault, but neither `collect_creator_fee` nor `collect_creator_fee_permissionless` provides any way to specify an alternate destination token account or otherwise route the funds elsewhere. Since the ATA address is deterministically derived from `creator` (and, for Token-2022 mints, is subject to the mint's freeze authority which the pool has no control over), the creator has no on-chain path to ever unfreeze or bypass that specific account, permanently locking the fees.

### Impact Explanation
Creator fees generated by every swap through the pool (tracked via `creator_fees_token_0`/`creator_fees_token_1` in `PoolState`) can become permanently unrecoverable if the creator's designated ATA is frozen (or otherwise rendered permanently unable to receive tokens) by the mint's freeze authority — a condition entirely outside the AMM program's control since mint freeze authority is set by whoever creates the token mint. This is a permanent freezing of legitimate creator funds with no admin or user-driven recovery instruction, matching the "no way to recover funds" impact category of the reported bug class.

### Likelihood Explanation
Likelihood is moderate: it requires a token mint (used as `token_0_mint`/`token_1_mint` of the pool) that retains a freeze authority, and requires that authority to freeze the creator's specific ATA (or the ATA to otherwise become permanently unusable, e.g., due to `Token2022` extensions rejecting the transfer). Since `is_supported_mint` does not reject mints with a freeze authority, pools backed by such tokens can be created without restriction, and any subsequent freeze of the creator's ATA permanently blocks fee collection through both available entry points.

### Recommendation
Add a mechanism to recover creator fees when the primary ATA cannot receive tokens — for example, allow the pool creator (via a privileged/administrative path or a governance-approved override) to specify an alternate destination token account for fee collection, or reject mints whose base `freeze_authority` is set (not just extension-based checks) during `initialize`/`initialize_with_permission` so that freezable mints cannot be paired with pools that rely on a single fixed fee-recipient account.

### Proof of Concept
1. Create a pool via `initialize` using a `token_0_mint` (classic SPL Token or Token-2022) that has a non-null `freeze_authority` — this passes `is_supported_mint` because freeze authority is not checked.
2. Perform swaps so that `creator_fees_token_0` accumulates in `PoolState` (via `swap_base_input`/`swap_base_output`).
3. The mint's freeze authority freezes the creator's associated token account for `token_0_mint` (the exact account address used as `creator_token_0` in `CollectCreatorFee`/`CollectCreatorFeePermissionless`).
4. Any subsequent call to `collect_creator_fee` or `collect_creator_fee_permissionless` invokes `transfer_from_pool_vault_to_user`, which fails at the `token_2022::transfer_checked` CPI because the destination account is frozen; the whole instruction reverts and `creator_fees_token_0` is never cleared.
5. Because both instructions always target this same fixed ATA with no alternate-recipient parameter, the creator has no path in the program to collect these fees ever again — the funds remain permanently locked in `token_0_vault`.

pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;

    Ok(())
}

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
