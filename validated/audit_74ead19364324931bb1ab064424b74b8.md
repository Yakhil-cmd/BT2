### Title
Cross-repository status forgery via unscoped SHA lookup enables unauthorized ship/block on production stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves commits with `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike `PushHandler#process`, which restricts writes to `stacks.not_archived.where(branch:)` [1](#0-0) . Because the `status` webhook signature is only verified against the *sender's* organization/repository (`Shipit.github(organization: repository_owner)`), an attacker who controls a repository with the Shipit GitHub App installed can emit a validly-signed `status` webhook whose `sha` happens to also exist as a `Commit` row belonging to an unrelated victim stack, flipping that victim commit's status.

### Finding Description
The broken binding the code should enforce is: `Commit#stack.github_repo_name == payload['repository']['full_name']` (the commit being mutated belongs to the same repository that authenticated the webhook). In `StatusHandler#process`:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
this equality is never checked — the lookup is a bare SHA match across the entire `commits` table, spanning every stack/repository tracked by the Shipit instance.

`WebhooksController#verify_signature` only proves that the payload was signed by the GitHub App belonging to `repository_owner` taken from the payload's own `repository.owner.login`/`organization.login` field [3](#0-2) . It proves authenticity of "this event came from GitHub for this owner/org," not that the `sha` in the body actually belongs to that repository. Since git commit SHAs are content-addressed (function of tree, parents, author/committer, timestamps, message) and not scoped to a specific remote, an attacker who forks a public victim repository (or otherwise reproduces an existing commit object byte-for-byte) obtains a repository containing a commit with the identical SHA already tracked by Shipit against the victim's stack. The attacker then triggers (or directly POSTs) a `status` event on their own repository for that SHA with `context: ci/coverage`, `state: success`. `verify_signature` accepts it because it's genuinely signed for the attacker's own org/repo. `StatusHandler#process` then finds the victim's `Commit` row (matching by bare SHA) and calls `commit.create_status_from_github!(params)`, which calls `add_status`, updates `status`/`deployable?` via `Status::Group.compact`, and can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` [4](#0-3) . If the affected stack is configured as the production environment requiring `ci/coverage`, this directly flips `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [5](#0-4) , forcing a ship (via continuous deployment) or clearing a block for attacker-controlled/unrelated code — none of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema on `StatusHandler` check repository identity against the commit being mutated.

### Impact Explanation
A cross-tenant write: a webhook authenticated for repository A mutates a `Commit`/`Status` record belonging to repository/stack B, which the attacker never authenticated against. On a production-environment stack this can force `deployable?` to flip to `true` (unblocking/triggering continuous deployment of code the operator did not intend to ship) or, symmetrically, forge a `failure`/`error` state to block a legitimate deploy — Critical, matching "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy". The attack is repeatable against any repository/stack whose commits happen to share (or can be engineered to share) a SHA with a repo the attacker controls, and is not limited to one victim.

### Likelihood Explanation
Preconditions: (1) the attacker must have a repository with the Shipit GitHub App/webhook installed (something any GitHub user can do on their own repo/org, since Shipit's model treats each org's app installation independently), and (2) the victim's commit must already exist in Shipit's `commits` table with a SHA the attacker can reproduce — trivially achievable by forking a public repository and pushing the exact same commit object (same tree/parents/message/timestamps yields an identical SHA), which is a well-known git property, not a hash collision. No Shipit secrets, sessions, or GitHub App private keys are required by the attacker; they only need control of a repo webhook they legitimately own. This is a low-cost, deterministic, and repeatable attack.

### Recommendation
Scope `StatusHandler#process` (and any other handler doing bare cross-repo lookups) to the repository that authenticated the webhook, e.g. join through `stack` and filter by `github_repo_name`/`repository_owner` matching `params.dig('repository','full_name')`, mirroring the pattern already used in `PushHandler#process` (`stacks.where(...)`). Reject or ignore statuses whose payload repository does not match the commit's stack repository before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create `stack_a` (attacker-controlled repo, e.g. `attacker/repo`) and `stack_b` (production environment, e.g. `victim/repo`, `environment: "production"`, requiring `ci/coverage`).
2. Create a `Commit` on `stack_b` with `sha: "deadbeef..."` (simulating a commit that also exists verbatim in `stack_a`'s repo).
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha: "deadbeef..."`, `context: "ci/coverage"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload_params, stacks: Stack.where(...))`/`.call` (bypassing signature verification, as done in other handler unit tests) and assert:
   - Before: `commit_b.reload.status.success?` is `false` (or `deployable?` is `false`).
   - After processing: `commit_b.reload.status.success?` is `true` and `commit_b.deployable?` is `true`, despite the webhook payload's `repository.full_name` never equaling `stack_b.github_repo_name`.
5. Assert this equality (`payload['repository']['full_name'] == commit_b.stack.github_repo_name`) is `false` both before and after, proving the mutation occurred without repository authentication — demonstrating the missing scoping check.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
