### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup in status webhook handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to using only the commit's `sha`, without any check that the webhook's `repository` matches the commit's own stack/repository. [1](#0-0)  Because `sha` is only unique per `(sha, stack_id)` pair and not globally, an attacker who controls any repository/organization tracked by Shipit can send a legitimately GitHub-signed `status` event whose `sha` collides with a commit that also exists in a victim's stack (e.g. via a fork sharing git history, or by reproducing the exact tree/parent/author/committer metadata of a public victim commit), and have Shipit write an attacker-controlled `context`/`state`/`description`/`target_url` Status row against the victim's stack.

### Finding Description
The broken binding the code should enforce is:
`webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` a status webhook is allowed to mutate.

What is actually enforced is only:
`commit.sha == params.sha`

with no join or comparison against `params['repository']` at all.

`WebhooksController#verify_signature` only checks that the payload was signed by the GitHub App configured for `repository_owner` derived from the *payload itself* — i.e., the attacker's own organization/repo, which the attacker legitimately owns and for which GitHub will produce a valid signature on a real event. [2](#0-1)  This guard authenticates *which organization sent the webhook*, not *which stack the sha belongs to*. It does nothing to prevent a payload naming the attacker's own repository from targeting a completely different stack's commit.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This query is unscoped by stack/repository. The schema explicitly supports the same `sha` existing under multiple `stack_id`s — the unique index is `(sha, stack_id)`, not `sha` alone [3](#0-2)  — which is the normal, expected case for forks or shared upstream history.

`Commit#create_status_from_github!` then persists the status using the found commit's *own* `stack_id`, verbatim from attacker-controlled fields:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [4](#0-3) 

```ruby
def replicate_from_github!(stack_id, github_status)
  find_or_create_by!(
    stack_id:,
    state: github_status.state,
    description: github_status.description,
    target_url: github_status.target_url,
    context: github_status.context,
    created_at: github_status.created_at
  )
end
``` [5](#0-4) 

Since `stack_id` here comes from the matched `Commit` row (belonging to the victim's stack, not the attacker's), and `state`/`description`/`target_url`/`context` come directly from the attacker's webhook params, the attacker fully controls the content of a Status row written against the victim's stack. This Status feeds directly into `Commit#status`, which drives `Status::Group.compact`:
```ruby
def status
  @status ||= Status::Group.compact(self, statuses_and_check_runs)
end
``` [6](#0-5) 

`Status::Group` compares the visible statuses' `context` against `commit.required_statuses` (delegated to `stack.required_statuses`, sourced from `deploy_spec.cache`), so an attacker naming a `context` equal to one of the victim's required statuses with `state: 'success'` can satisfy a required check that was never actually run by the victim's CI, or conversely inject a `failure` to block the victim's deploy. [7](#0-6) [8](#0-7) 

None of the existing guards prevent this: `verify_signature` only authenticates the sending organization named in the payload (the attacker's own, legitimately), `drop_unhandled_event` only checks the event type is handled, and the `StatusHandler` `ExplicitParameters` schema only validates types/presence of `sha`, `state`, `context`, etc. — none tie the payload's `repository` to the matched `Commit`'s stack.

### Impact Explanation
An attacker who owns or controls any GitHub repository tracked by Shipit (their own fork, or any repo whose commit metadata they can reproduce to collide a sha) can write arbitrary `Status` rows — with attacker-chosen `context`, `state`, `description`, `target_url` — against a completely unrelated victim stack's commit, as long as a `Commit` row with the same `sha` exists in the victim's stack. This can spoof a passing CI check that satisfies `required_statuses`, enabling an unauthorized/unearned deploy or auto-merge decision for the victim's stack, or inject a `failure` state to block the victim's legitimate deploys — a payload for one repository mutating another's stack/commit state, matching the Critical impact category. The attack is repeatable against any stack/commit for which the attacker can find or engineer a colliding sha, and is not limited to a single victim.

### Likelihood Explanation
Preconditions: the attacker needs (a) some Shipit-tracked repository/organization under their control capable of emitting a real, GitHub-signed `status` webhook, and (b) a commit sha that also exists in the victim's tracked stack. Condition (b) is trivially satisfied for forked public repositories (shared history), and even for non-forked cases a Git commit's sha is fully determined by its tree/parent/author/committer/message content — all of which are visible via the victim's public GitHub repo/API — so an attacker can construct an object with an identical sha in a repository they control. This requires no Shipit secrets, no privileged role, and no session — only ordinary GitHub repository ownership, matching the "unprivileged attacker" threat model in scope.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and the analogous `check_suite`/other handlers) by the webhook's own repository, e.g. resolve the `Stack`(s) matching `params.dig('repository','full_name')` first, then find commits by `sha` within `commit.statuses` etc. `stack_id: stack.id, sha: params.sha`, ensuring a status payload can only ever mutate commits belonging to the stack(s) associated with the repository that actually emitted the webhook.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from an unrelated repository forges a Status on a colliding-sha commit belonging to a different stack" do
  victim_stack  = shipit_stacks(:shipit)                     # victim tenant
  victim_commit = shipit_commits(:first)                     # belongs to victim_stack, has some sha X

  # Simulate an attacker-controlled repository producing a commit with the SAME sha X
  # (e.g. via fork of victim's public repo, or reproduced git object), tracked under
  # a different stack that the attacker legitimately owns/controls.
  attacker_repo_payload = JSON.parse(payload(:status_master)).merge(
    'sha' => victim_commit.sha,
    'context' => 'ci/circleci',       # matches one of victim_stack.required_statuses
    'state' => 'success',
    'description' => 'forged-by-attacker',
    'target_url' => 'https://attacker.example.com/fake-ci'
  ).merge(
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  ).to_json

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature is genuinely valid for attacker-org

  assert_difference -> { victim_commit.reload.statuses.count }, 1 do
    post :create, body: attacker_repo_payload, as: :json
  end

  status = victim_commit.statuses.last
  # Equality that should NOT hold but does:
  assert_equal 'attacker-org'.downcase, JSON.parse(attacker_repo_payload)['repository']['owner']['login']
  refute_equal victim_stack.repository.owner, 'attacker-org' # confirms cross-tenant mismatch
  assert_equal victim_stack.id, status.stack_id               # yet Status was written under victim's stack_id
  assert_equal 'success', status.state
  assert_equal 'ci/circleci', status.context
  assert_equal 'https://attacker.example.com/fake-ci', status.target_url
end
```
