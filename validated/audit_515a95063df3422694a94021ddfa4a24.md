### Title
Membership webhook trust confusion allows cross-organization Team-membership injection into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using an **unauthenticated, attacker-controlled field of the same request body** (`repository.owner.login`, falling back to `organization.login`), and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that selected organization has no `webhook_secret` configured — a state explicitly documented as optional (`docs/setup.md`, `config/secrets.development.shopify.yml`). Once "verified", `MembershipHandler#process` writes to a `Team` selected only by `github_id`, with no re-check that the team actually belongs to the organization that was used to authenticate the request. This breaks the equality: *organization whose credential authenticated the webhook* ≠ *organization/team actually mutated*, letting an unauthenticated caller add an arbitrary GitHub login to a `Team` that is enrolled in `Shipit.github_teams` (the access-control gate).

### Finding Description
`verify_signature` picks the verification target purely from body content that has not yet been verified: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` is a no-op when the resolved org/app has no configured secret: [3](#0-2) 

Multi-organization configuration with per-org optional `webhook_secret` (including `nil`) is a documented, supported deployment shape, not a misconfiguration: [4](#0-3) [5](#0-4) 

`MembershipHandler#process` then resolves the `Team` to mutate solely by `github_id` taken from the payload, with no verification that this team's `organization` matches the organization used to authenticate the request: [6](#0-5) 

`Team` records (and the users added to them) directly back `Shipit.github_teams` authorization used by `current_user.authorized?`: [7](#0-6) [8](#0-7) 

**Attack path:** In a Shipit deployment configured for multiple GitHub organizations (as shown in `config/secrets.development.shopify.yml`), suppose org `unsecured-org` has `webhook_secret: nil` (a documented, optional setting) while org `shopify` is the org whose `Team` (github_id known or discoverable, e.g. `1` in fixtures) gates access via `Shipit.github_teams`. An unauthenticated attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and a body where:
- `organization.login = "unsecured-org"` (used by `verify_signature`/`repository_owner` to pick the GitHub App to check against — which has no secret, so `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header sent, or if absent),
- `team = { id: <shopify's real team github_id>, name, slug, url }` (the actual authoritative team),
- `action = "added"`, `member.login = "attacker-controlled-login"`.

`MembershipHandler#find_or_create_team!` looks the team up **only by `github_id`**, finds the existing, already-created `shopify` Team, and `team.add_member(member)` adds the attacker-chosen GitHub login to it — with zero cryptographic binding checked against `shopify`'s own secret.

### Impact Explanation
This crosses "escalation into `Shipit.github_teams` authorization," an explicitly listed High-severity impact. Once a controlled GitHub login is a member of an authorizing team, any user who can authenticate to Shipit under that login via GitHub OAuth (`GithubAuthenticationController#callback` → `User.find_or_create_from_github`) passes `current_user.authorized?` and gains full access to the Shipit UI/API for all stacks, including triggering deploys/rollbacks/tasks — an unauthorized deploy path.

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (`skip_before_action :verify_authenticity_token`) and requires no session, token, or repository access — only network reachability to the public webhook URL. The only precondition is that the Shipit deployment has at least one configured organization without a `webhook_secret`, which the codebase's own example configs (`config/secrets.development.shopify.yml`) and docs (`docs/setup.md:30`, marking the secret "optional") present as a normal, supported setup, not a documented-against misconfiguration. Given that, exploitation requires no privileged credential of any kind, matching the "unprivileged attacker" scope of this scan.

### Recommendation
- Do not use attacker-supplied payload fields to select the verification key; verification must be bound to a fixed, pre-registered credential (e.g. via URL/path scoping per app installation, or verifying against every configured secret and only proceeding with the org whose secret actually matches).
- Make `webhook_secret` mandatory (reject requests / refuse to boot) rather than silently returning `true` when absent.
- In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and reject/no-op if an existing team's `organization` does not match the organization that was cryptographically verified for this request.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json
(no X-Hub-Signature, or any junk value)

{
  "action": "added",
  "organization": { "login": "unsecured-org" },
  "team": { "id": 1, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "member": { "login": "attacker-controlled-login" }
}
```
Because `unsecured-org` is configured in Shipit with `webhook_secret: nil`, `verify_webhook_signature` short-circuits to `true` (`lib/shipit/github_app.rb:76-77`), and `MembershipHandler` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`) locates the real `shopify/developers` team purely by `github_id: 1` and adds `attacker-controlled-login` as a member, without any check that `unsecured-org` matches `shopify`.

*Note:* I was unable to fully inspect `Shipit.github`'s multi-org resolution logic in `lib/shipit.rb` (file read failed in the final iteration), so the exact behavior when only a single global `github:` config (no per-org keys) is present is not fully confirmed; the finding as described applies specifically to the documented multi-organization configuration mode.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
