## Analysis

The bug class here (a `try/catch`-style validation check that authenticates against the wrong scope, letting an attacker-controlled value slip through unverified) maps to a real binding mismatch in `Shipit::WebhooksController`.

`verify_signature` selects the `GitHubApp`/secret used to check the HMAC based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . That signature check happens in a `before_action` on the raw, unparsed JSON before any handler runs [2](#0-1) . However, once the signature is accepted, `create` re-parses the same JSON and dispatches it to handlers unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .

Every handler determines *which repository/stack to act on* from a **different** field: `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `Repository.from_github_repo_name` [4](#0-3) [5](#0-4) . `Shipit.github(organization:)` config is looked up per lower-cased organization key in the app's own multi-tenant Github config, and each configured organization can have its own independent `webhook_secret` [6](#0-5) .

Because the field used to pick the verifying secret (`repository.owner.login` / `organization.login`) is never cross-checked against the field used to pick the acted-upon repository (`repository.full_name`), an attacker who legitimately controls (or is an authorized sender for) organization **A** — and therefore knows/can trigger a validly-signed webhook delivery under A's `webhook_secret` — can craft a payload where `repository.owner.login` = `A` (so the signature verifies against A's secret) while `repository.full_name` = `B/some-repo`, a completely different, victim organization/repository that Shipit also manages. `PushHandler`, and the various `pull_request` handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) all resolve the target `Repository`/`Stack` purely from `repository.full_name` [7](#0-6) [8](#0-7) , with no re-validation that `full_name`'s owner matches the organization whose secret produced the signature.

This is the exact binding class called out in the rules: **"an organization that authenticated versus the repository that is written."** The equality that should hold and is broken is:

```
owner(repository.full_name used by handlers) == organization used to select webhook_secret for signature verification
```

### Impact
This lets a sender who is a legitimate, authenticated webhook source for organization A forge events (pushes triggering `sync_github`/deploy pipeline recompute, PR opened/closed/labeled events triggering review-stack provisioning, archiving, or unarchiving) against any other organization/repository configured in the same Shipit instance, without ever possessing that victim organization's `webhook_secret`. Depending on which handler is hit, this can trigger unauthorized `GithubSyncJob` runs, review-stack archive/unarchive/provisioning actions, or pull request merge-status changes — a cross-repository write performed under the guise of a differently-owned, validly-signed webhook.

### Caveat
This requires the Shipit instance to be configured with **multiple GitHub organizations** each with independent per-organization `webhook_secret`s (the `github_app_config(organization)` multi-tenant path in `lib/shipit.rb`) [9](#0-8) ; in the single-org legacy config schema (`github_default_organization.nil?`), only one webhook secret exists for the whole app, and this specific cross-org confusion collapses (though the mismatch between the header-derived "owner" and the handler's "full_name" persists structurally). I could not fully verify, given index limits, what production deployments typically configure (single-org vs. multi-org secrets), nor could I find a test that exercises `repository.owner.login` differing from `repository.full_name`'s owner — the closest test only checks unknown-organization handling [10](#0-9) . A Devin session with full repo/test access would be needed to confirm whether multi-org secret configurations are a supported/documented deployment mode in this engine before treating this as a fully proven exploit.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
