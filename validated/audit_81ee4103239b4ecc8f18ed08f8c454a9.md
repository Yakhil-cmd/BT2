### Title
Webhook signature verification is bypassed when the attacker-controlled `repository.owner.login`/`organization.login` field selects an organization whose `webhook_secret` is unset - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub organization's HMAC secret to check the request against by reading `repository_owner`, a field taken directly from the unauthenticated JSON body, before any signature has been validated. The secret lookup then delegates to `GithubApp#verify_webhook_signature`, which unconditionally returns `true` whenever the selected organization has no `webhook_secret` configured. An attacker who has no credentials at all can therefore pick an organization (one that Shipit has configured without a `webhook_secret`) and submit an arbitrary, unsigned webhook payload naming any repository/team/branch they like; the app treats it as a verified GitHub event and dispatches it to the corresponding handler.

### Finding Description
The controller extracts the organization used for authentication purely from payload data: [1](#0-0) 

That value feeds directly into signature verification, which happens after the attacker-controlled field has already been used to choose the trust anchor: [2](#0-1) 

Crucially, `verify_webhook_signature` is a no-op whenever the selected organization config has no secret set: [3](#0-2) 

This breaks exactly the trust binding the analog targets: the *organization that gets authenticated* (chosen by an unauthenticated, attacker-supplied `repository.owner.login`/`organization.login` field, analogous to the unvalidated `appchain_id` in the original report) is not equal to the *organization/repository whose data actually gets written* by the handler that subsequently runs. If any configured GitHub organization in `Rails.application.credentials.github` omits `webhook_secret`, the signature check degenerates to always-true for payloads claiming that organization, and the request is processed as if it were a legitimately signed GitHub event.

Once verification is bypassed, the dispatched handler acts on further unauthenticated fields with no additional authorization check. Most notably, `MembershipHandler` will create arbitrary teams/users and add a member to any team purely from payload data: [4](#0-3) 

Team membership in Shipit governs authorization: `Shipit.github_teams` maps configured OAuth team names to `Team` records used to grant application access. An attacker-controlled `membership` event can add an attacker's own GitHub login to one of those teams, escalating into `Shipit.github_teams` authorization directly — one of the explicitly listed High-impact outcomes.

Other handlers are similarly reachable without any valid signature, e.g. `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` for any branch matching an existing stack: [5](#0-4) 

### Impact Explanation
If any configured organization entry lacks `webhook_secret` (a supported, non-error configuration per `verify_webhook_signature`'s `return true unless webhook_secret` fallback), a completely unauthenticated attacker can forge GitHub webhook events for that organization. The most severe consequence is escalation into `Shipit.github_teams` authorization via `MembershipHandler#process` adding an arbitrary GitHub login to a privileged team, which is an explicitly in-scope High-impact outcome. It can also spoof `push`/`status`/`check_suite` events, influencing deploy readiness signals (commit statuses, check runs) that gate merges/deploys.

### Likelihood Explanation
Exploitability is entirely conditional on deployment configuration: it requires at least one organization entry in `secrets.github` with no `webhook_secret` set. Given `webhook_secret` is optional per the code path (`return true unless webhook_secret`), this is a plausible and easy-to-miss misconfiguration, but it is not guaranteed to exist in every deployment — the engine's own code permits and silently accepts it rather than requiring a secret for every organization.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization at boot (fail fast instead of silently allowing `verify_webhook_signature` to always return `true`).
- Do not let payload-sourced fields (`repository.owner.login`, `organization.login`) select the verification key before the signature itself has been validated; instead, verify the signature against every registered secret (or a single well-known one) independent of unauthenticated request content, mirroring the report's fix of validating the untrusted field *before* it is trusted for a privileged action.
- Add an authorization check in `MembershipHandler`/team-mutating handlers that doesn't rely solely on the outer signature gate.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (has `webhook_secret`) and `orgB` (no `webhook_secret` set) — a supported configuration under `GitHubApp#verify_webhook_signature`.
2. Send an unsigned POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Deployers", "slug": "deployers", "url": "https://example.com"},
  "organization": {"login": "orgB"},
  "member": {"login": "attacker-github-login"}
}
```
3. `repository_owner`/`organization.login` resolves to `orgB`; `verify_webhook_signature` short-circuits to `true` because `orgB` has no `webhook_secret`.
4. `MembershipHandler#process` runs unauthenticated, creating/finding team `Deployers` and adding `attacker-github-login` as a member — escalating the attacker into whatever authorization that team grants via `Shipit.github_teams`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
