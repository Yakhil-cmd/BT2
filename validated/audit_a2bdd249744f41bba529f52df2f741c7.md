### Title
Attacker self-shields from liquidation by adding an Aquarius LP collateral leg then draining the pool below `min_pool_value_wad` — (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The CVE class is "an unauthenticated actor causes repeated failures that starve legitimate work — a denial of service." In XOXNO Lending the equivalent is not a connection error but an *oracle* error an unprivileged account can manufacture on demand: `aquarius::read` returns `OracleError::InsufficientAquariusLiquidity` whenever the Aquarius pool's fair value falls below the configured `lp.min_pool_value_wad` [1](#0-0) . Since the controller fetches prices strictly — `fetch_prices` panics with `OracleNotConfigured` on any missing/unusable feed [2](#0-1)  — any valuation-dependent entrypoint (`liquidate`, `clean_bad_debt`, `withdraw`, `borrow`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `update_account_threshold`) reverts for every account holding that LP token as a supply leg. An attacker who is also an LP in the referenced Aquarius pool can withdraw their liquidity to force `pool_value_wad < min_pool_value_wad`, producing a self-inflicted, persistent price outage on exactly the collateral that shields their own underwater account. The threat model acknowledges this shape: "For an Aquarius LP leg, liquidity providers can cause that outage by withdrawing pool value below `min_pool_value_wad`. The same leg blocks bad-debt cleanup and force-socialization" .

### Finding Description
1. `supply` requires no price read (per threat model: "Supply needs no price"), so an attacker calls `controller.supply(attacker, 0, spoke_id, [(hub_asset(AQUA_LP), dust)])`, minting a new account with a tiny LP collateral leg. Position-limit checks pass because it is a new slot under `max_supply_positions` [3](#0-2) .
2. The attacker adds a normal-valued collateral leg (e.g. USDC) and calls `borrow` to take maximum debt against it.
3. When the position drifts toward HF < 1 (interest accrual or market movement), the attacker withdraws their own liquidity from the underlying Aquarius pool. This is an unprivileged action on an external venue ("own trades on Aquarius/Soroswap" is in scope).
4. `fair_lp_price_wad`/`fair_stable_lp_price_wad` still computes a *positive* share price — the LP token is not worthless, just thin — but `pool_value_wad < lp.min_pool_value_wad` makes `read` fail with `InsufficientAquariusLiquidity` [4](#0-3) . The observation never reaches the engine, so `prices()` returns no feed for that asset and `fetch_prices` panics [5](#0-4) .
5. Every liquidation attempt reverts while building the `Context` — the planner cannot value the supply book containing the LP leg — so the attacker's account cannot be liquidated, `clean_bad_debt` cannot socialize it, and `recapitalize` cannot price the write-down. The attacker keeps the borrowed funds; when residual collateral < debt, the shortfall becomes protocol bad debt.

This mirrors the CVE: repeated/replicable low-cost errors (here, a persistent pricing error the attacker toggles by depositing/withdrawing their own LP) starving the protocol's liquidation clients.

### Impact Explanation
Protocol insolvency / theft of user funds: the attacker extracts borrowed value and permanently blocks the two mechanisms (liquidation, bad-debt socialization) that would recover it, because both fail-closed on the unusable feed. The freeze is not transient fail-closed unavailability of a third-party oracle — it is a targeted, attacker-toggled outage keyed to a specific collateral leg on their own position, which also immunizes that leg from seizure while other legs remain unseizable (liquidation plans value the whole book). Loss equals borrowed value minus forfeited collateral; repeatable per LP market and per account.

### Likelihood Explanation
Requires only: (a) an Aquarius LP token listed as collateral whose configured `min_pool_value_wad` is within reach of the attacker's own LP share, and (b) enough capital to be a meaningful LP in that pool while holding a borrow. Mainnet `configs/mainnet/markets.json` configures multiple Aquarius LP sources with `min_pool_value_wad` thresholds, so the precondition exists in the intended deployment. Small or attacker-dominated pools make the drain cheap; the attacker can even re-deposit after insolvency is locked in to unfreeze unrelated users — but their own bad debt is already socialized. Medium-High likelihood; severity High only where an LP market's liquidity is genuinely thin.

### Recommendation
- Do not fail the entire valuation context on `InsufficientAquariusLiquidity`; treat the LP leg as zero-valued (or skip it) inside the risk/liquidation path so the rest of the book remains liquidatable and `clean_bad_debt` can still write down the account.
- Alternatively, cache the last good LP observation with a bounded staleness window for valuation while still rejecting it for new borrows.
- Keep the `min_pool_value_wad` floor for *attestation* of new collateral listings, but decouple runtime liquidation from a metric (pool TVL) an LP can unilaterally lower.
- Governance-side: prefer listing LP tokens only from pools with deep, distributed liquidity so no single LP can cross the floor.

//    => prices() omits feed => fetch_prices panics OracleNotConfigured

Key code support: `aquarius::read` floor check and `InsufficientAquariusLiquidity` [1](#0-0) ; strict fail-closed price fetch [2](#0-1) ; dust deposits of `1` unit are accepted with no floor [6](#0-5) ; documented threat-model row DoS.1 confirms both legs of the mechanism .

Caveat: this is borderline against the "reject fail-closed DoS" rule — it is reported because the impact is not mere unavailability but unblockable liquidation leading to insolvency, and because the outage is attacker-manufactured rather than third-party oracle honesty. If the auditor classifies fail-closed pricing behavior as an accepted design decision, this finding reduces to the documented threat-model row.

/// Checks position limits only when adding a new hub-asset slot.
/// Deduplicates new assets and excludes positions already held by the account.
pub(crate) fn validate_bulk_position_limits(
    env: &Env,
    account: &Account,
    position_type: AccountPositionType,
    aggregated: &AggregatedPayments,
) {
    let limits = storage::get_position_limits(env);

    let (current_count, max_allowed) = match position_type {
        AccountPositionType::Deposit => {
            (account.supply_positions.len(), limits.max_supply_positions)
        }
        AccountPositionType::Borrow => {
            (account.borrow_positions.len(), limits.max_borrow_positions)
        }
    };

    let mut seen: Map<HubAssetKey, bool> = Map::new(env);
    let mut new_positions_count: u32 = 0;
    for (hub_asset, _) in aggregated.iter() {
        if seen.contains_key(hub_asset.clone()) {
            continue;
        }
        seen.set(hub_asset.clone(), true);

        let already_present = match position_type {
            AccountPositionType::Deposit => account.supply_positions.contains_key(hub_asset),
            AccountPositionType::Borrow => account.borrow_positions.contains_key(hub_asset),
        };
        if !already_present {
            new_positions_count += 1;
        }
    }

    // Existing positions remain usable after governance lowers the position limit.
    if new_positions_count == 0 {
        return;
    }

    let total_positions = current_count
        .checked_add(new_positions_count)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        total_positions <= max_allowed,
        CollateralError::PositionLimitExceeded
    );

fn poc_single_actor_spams_unbounded_dust_accounts() {
    let mut t = LendingTest::new().with_market(usdc_preset()).build();

    let attacker = t.get_or_create_user("attacker");
    let usdc = t.resolve_market("USDC");

    const N: u64 = 64;
    usdc.token_admin.mint(&attacker, &(N as i128));
    let asset = usdc.asset.clone();

    let ctrl = t.ctrl_client();
    let mut created: u64 = 0;
    let mut last_id: u64 = 0;
    for _ in 0..N {
        let dust = vec![&t.env, (hub_asset(asset.clone()), 1i128)];
        let id = ctrl.supply(&attacker, &0u64, &1u32, &dust);
        assert!(id > 0, "1-unit deposit must be accepted (no dust floor)");

        assert!(id > last_id, "each supply(id=0) must mint a new account id");
        assert!(
            ctrl.account_exists(&id),
            "spammed account persists in storage"
        );
        last_id = id;
        created += 1;
    }

    assert_eq!(
        created, N,
        "one actor created {N} distinct accounts with dust deposits"
    );
