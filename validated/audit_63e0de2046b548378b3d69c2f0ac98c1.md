### Title
Unbounded scaled-balance multiplication can permanently freeze a lending market - (File: common/src/rates/simulate.rs)

### Summary

An unprivileged borrower can create enough scaled debt that the ordinary interest-accrual calculation overflows `i128` before the configured borrow-index ceiling is reached. [1](#0-0)  Every subsequent pool operation synchronizes the market before acting, so the same overflow blocks repayment, withdrawal, liquidation and further index updates. [2](#0-1) [3](#0-2) 

### Finding Description

The pool stores supply and debt as RAY-scaled share amounts and converts them back to value by multiplying by the current index through `scaled_to_original`. [4](#0-3)  `accrue_step` performs this multiplication for both borrowed and supplied totals before calculating utilization, the borrow rate and the next index. [5](#0-4) 

Although `update_borrow_index` caps the newly calculated index at `MAX_BORROW_INDEX_RAY`, the multiplication that revalues existing scaled debt can overflow first when `borrowed` is sufficiently large. [6](#0-5) [7](#0-6)  `global_sync` runs `accrue_step` for every elapsed compounding chunk, while `synced_market` is called by the mutation legs. [8](#0-7) [9](#0-8) 

An attacker can create the state using the permissionless controller path: `supply(caller, account_id, spoke_id, [(debt_asset, principal)])`, then `borrow(caller, account_id, [(debt_asset, debt)], to)`. [10](#0-9)  After the market index grows enough that `borrowed * borrow_index` exceeds `i128::MAX`, a permissionless `update_indexes` call reaches `accrue_step` and traps. [11](#0-10) [12](#0-11) 

The repository already contains a regression demonstrating this cliff with a large 18-decimal market at sustained high utilization: `update_indexes` returns `MATH_OVERFLOW`, the stored index remains below `MAX_BORROW_INDEX_RAY`, and both `withdraw` and `repay` subsequently fail. [13](#0-12) 

### Impact Explanation

The affected market cannot process repayments, withdrawals, borrows, liquidations, bad-debt cleanup or index updates because those paths must first load a synchronized market and rerun the overflowing calculation. [2](#0-1) [14](#0-13)  Since ledger time cannot be moved backwards and the stored scaled balances remain unchanged, the arithmetic error repeats indefinitely and can permanently freeze all supplier and borrower funds in that market. [15](#0-14) [16](#0-15) 

### Likelihood Explanation

The attack requires a market whose configured supply cap, borrow cap, available liquidity and rate model permit enough scaled debt to exceed `i128::MAX` when multiplied by the current index. [17](#0-16) [18](#0-17)  This is economically expensive but does not require privileged calls during the attack, leaked keys, oracle manipulation or a malicious token. [10](#0-9)  Low-decimal assets are especially exposed because each native unit occupies a much larger RAY-scaled range, while the existing test demonstrates that an 18-decimal market can also cross the boundary at a large enough balance and index. [19](#0-18) [20](#0-19) 

### Recommendation

Prevent scaled totals from entering a state whose value at `MAX_BORROW_INDEX_RAY` or `MAX_SUPPLY_INDEX_RAY` cannot fit in `i128`, and enforce those bounds when minting supply or debt shares. [21](#0-20) [7](#0-6)  Use widened `I256` multiplication or explicit preflight checks for `borrowed * borrow_index` and `supplied * supply_index`, and clamp the index before the revaluation can trap. [22](#0-21) [23](#0-22)  Add market-creation and borrow-time invariants that bound `borrowed` and `supplied` by `i128::MAX / MAX_*_INDEX_RAY` rather than relying only on asset-unit caps. [24](#0-23) [25](#0-24) 

### Proof of Concept

```text
1. Attacker calls:
   controller.supply(
       attacker,
       0,
       spoke_id,
       [(vulnerable_market, very_large_principal)]
   )

2. Attacker supplies sufficient collateral in another market and calls:
   controller.borrow(
       attacker,
       account_id,
       [(vulnerable_market, debt_close_to_available_liquidity)],
       Some(attacker)
   )

3. Ledger time advances normally while utilization remains high.

4. Anyone calls:
   controller.update_indexes([vulnerable_market])

5. The controller invokes the owner-only pool update, which loads the market and
   calls global_sync.

6. accrue_step evaluates:
   scaled_to_original(borrowed, borrow_index)

   When borrowed * borrow_index exceeds i128::MAX, the call panics with
   MATH_OVERFLOW before the index cap can be applied.

7. Subsequent controller.withdraw, controller.repay, controller.liquidate and
   controller.update_indexes calls all load the same market, rerun accrual and
   hit the same overflow, leaving the market's funds inaccessible.
```

The existing regression test constructs this sequence with a billion-token 18-decimal market and 98% utilization, observes `MATH_OVERFLOW` from `update_indexes`, verifies that the borrow index is still below `MAX_BORROW_INDEX_RAY`, and confirms that both withdrawal and repayment fail. [13](#0-12)

    borrowed: Ray,

    supply_index: Ray,

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Rescales `a` from `from_decimals` to `to_decimals`. Upscaling multiplies by the exact
/// power-of-ten factor. Downscaling returns `round_down(a, factor)`, where `factor` is `None`
/// when the power of ten overflows `i128`; every `|a|` is then below that power. Returns `a`
/// unchanged when the decimal counts are equal. Panics with `GenericError::MathOverflow` if the
/// upscaling factor or the upscaled value overflows `i128`.
fn rescale(
    env: &Env,
    a: i128,
    from_decimals: u32,
    to_decimals: u32,
    round_down: impl Fn(i128, Option<i128>) -> i128,
) -> i128 {
    if from_decimals == to_decimals {
        return a;
    }
    let factor = 10i128.checked_pow(to_decimals.abs_diff(from_decimals));

    if to_decimals > from_decimals {
        factor
            .and_then(|factor| a.checked_mul(factor))
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
    } else {
        round_down(a, factor)
    }
}
