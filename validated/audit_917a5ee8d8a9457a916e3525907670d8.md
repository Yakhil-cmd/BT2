### Title
Bridge `handle*Transfer` Functions Bypass `isRunning` and Lock Guards, Allowing Asset Drains During Emergency Stop — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

### Summary

The Kaia service-chain bridge contracts expose an exact structural analog to the reported Move gateway bug: the **request** (deposit) path enforces both the `isRunning` running-status flag and the per-asset lock flags (`isLockedKLAY` / `lockedTokens`), while the **handle** (withdrawal/payout) path enforces neither. A bridge operator can therefore drain KLAY, ERC-20, or ERC-721 assets from a bridge vault even after the owner has triggered an emergency stop or asset lock.

### Finding Description

`BridgeTransfer.sol` declares two state guards:

- `isRunning` (bool, default `true`) — toggled by the owner via `setRunningStatus` / `start` to halt all bridge activity.
- `isLockedKLAY` (bool in `BridgeTransferKLAY`) and `lockedTokens` (mapping in `BridgeTokens`) — toggled by the owner to freeze specific asset flows.

**Request (deposit) functions enforce both guards:**

`_requestKLAYTransfer` carries the `unlockedKLAY` modifier and `require(isRunning, "stopped bridge")`: [1](#0-0) 

`_requestERC20Transfer` carries `onlyUnlockedToken` and `require(isRunning, "stopped bridge")`: [2](#0-1) 

`_requestERC721Transfer` carries `onlyUnlockedToken` and `require(isRunning, "stopped bridge")`: [3](#0-2) 

**Handle (withdrawal/payout) functions enforce neither guard:**

`handleKLAYTransfer` — only `onlyOperators` + `nonReentrant`; no `isRunning` check, no `unlockedKLAY` check: [4](#0-3) 

`handleERC20Transfer` — only `onlyOperators`; no `isRunning` check, no `onlyUnlockedToken` check: [5](#0-4) 

`handleERC721Transfer` — only `onlyOperators`; no `isRunning` check, no `onlyUnlockedToken` check: [6](#0-5) 

The `isRunning` flag is the bridge's sole emergency-stop mechanism: [7](#0-6) 

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` or `lockKLAY()` / `lockToken()` to halt the bridge during an incident, the handle functions remain fully callable by any registered operator. Concretely:

- `handleKLAYTransfer` will still execute `_to.call.value(_value)("")` and transfer KLAY out of the vault.
- `handleERC20Transfer` will still execute `IERC20.safeTransfer` or `ERC20Mintable.mint`, moving or minting tokens.
- `handleERC721Transfer` will still execute `IERC721.transferFrom` or `ERC721MetadataMintable.mintWithTokenURI`.

This is an **unauthorized transfer of KAIA and bridged assets** from system-managed bridge vaults during a state that the owner explicitly intended to be frozen. The corrupted value is the vault balance: assets leave (or are minted) when the contract's own invariant (`isRunning == false` ⇒ no asset movement) is violated.

### Likelihood Explanation

Operators are semi-trusted: they are registered by the owner but are independent parties (often automated relayer processes). A compromised relayer key, a malicious operator, or even an honest operator whose off-chain software continues processing queued events after the owner stops the bridge can trigger this path. The owner's only recourse is a second transaction to remove each operator — a race condition that leaves a window for asset loss. The trigger requires only a valid `onlyOperators` caller and a matching nonce, both of which are normal operational conditions.

### Recommendation

Add `isRunning` and the relevant lock checks to all three handle functions. The minimal fix mirrors the pattern already used on the request side:

```solidity
// BridgeTransferKLAY.sol — handleKLAYTransfer
function handleKLAYTransfer(...) public onlyOperators nonReentrant unlockedKLAY {
    require(isRunning, "stopped bridge");
    ...
}

// BridgeTransferERC20.sol — handleERC20Transfer
function handleERC20Transfer(...) public onlyOperators onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    ...
}

// BridgeTransferERC721.sol — handleERC721Transfer
function handleERC721Transfer(...) public onlyOperators onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    ...
}
```

Alternatively, extract a shared `whenRunning` modifier in `BridgeTransfer` and apply it uniformly to both request and handle paths.

### Proof of Concept

1. Owner deploys bridge with KLAY balance and registers Operator.
2. An incident occurs; owner calls `bridge.setRunningStatus(false)` and `bridge.lockKLAY()`.
3. `bridge.requestKLAYTransfer(...)` now reverts with `"stopped bridge"` / `"locked"` — new deposits are blocked.
4. Operator calls `bridge.handleKLAYTransfer(txHash, from, attacker, 10 ether, nonce, blockNum, "")`.
5. The call succeeds: `handleKLAYTransfer` has no `isRunning` or `unlockedKLAY` guard, so `_to.call.value(10 ether)("")` executes and 10 KLAY leaves the vault.
6. Repeat for any remaining valid nonces; the bridge is drained while the owner believes it is fully stopped.
