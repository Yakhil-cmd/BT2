### Title
Permanent freezing of L1-locked BTC when `verify-block-header` returns false for an out-of-window burn height - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 lockup path validates a staker's Bitcoin timelock proof through `validate-l1-lockup`, which calls `verify-block-header`. That function is a thin wrapper over `get-burn-block-info? header-hash`, a Clarity primitive that only returns `Some` for burn heights within a bounded lookback window from the current tip; for any height outside that window it deterministically returns `none`, which `verify-block-header` maps to `false`, forcing `ERR_INVALID_BTC_HEADER`.

### Finding Description
`verify-block-header` is defined as: [1](#0-0) 

and it is the sole gate used in `validate-l1-lockup` to accept a staker's proof of an on-chain BTC timelock output: [2](#0-1) 

This is invoked from the fold over the staker-supplied lockup list in `verify-l1-lockups`, which is in turn the only path `register-for-bond` uses to accept BTC-side collateral proofs (as opposed to sBTC deposits): [3](#0-2) 

`get-burn-block-info? header-hash <height>` is a VM primitive backed by `special_get_block_info`/burn-block lookups in the Clarity database layer, which only stores/serves a bounded lookback window of burn-block headers relative to the current chain tip (analogous to `get-block-info?`'s windowed behavior documented in `clarity/src/vm/functions/database.rs`, lines 917-936). Once a Bitcoin lockup's `height` falls outside that window (e.g., the staker constructed the BTC timelock, waited, and only later submitted the merkle proof — or simply submitted late for any reason), `get-burn-block-info?` returns `none` for every future call at that height. `verify-block-header` then unconditionally returns `false`, and `register-for-bond` reverts with `ERR_INVALID_BTC_HEADER` for that lockup output forever — there is no fallback height-independent verification path, no way to re-anchor the proof to a more recent/available height, and no admin/guardian override analogous to `resetBreaker` in the source report.

This directly mirrors the reported bug class: an oracle-like data source (`get-burn-block-info?`, standing in for the Chainlink price feed) that is guaranteed to eventually return "no data" for old inputs, causing the dependent function (`fetchEthPrice`/`verify-block-header`) to fail and the surrounding transaction (`redeemCollateral`/`register-for-bond`) to permanently revert, with no recovery path for the affected user.

### Impact Explanation
The staker has already irreversibly locked real BTC into a P2WSH Bitcoin-script timelock (constructed via `construct-lockup-output-script`) that only they (via `staker-unlock-bytes`, gated by the CLTV `unlock-burn-height`) or the bond's early-unlock key can spend. If the on-chain proof of that lockup cannot be submitted to `register-for-bond` before the burn-height window used in the proof falls outside Clarity's `get-burn-block-info?` lookback, the staker can never register their locked BTC for the bond they intended to join — their PoX-5 bond membership, staking rewards, and signer participation from that BTC are permanently unobtainable, while the BTC itself remains locked on Bitcoin under the timelock script until `unlock-burn-height`/CLTV expiry. This is a temporary-to-permanent freezing of a staker's committed collateral value with no way to unlock or resubmit a valid proof, which is a High/Critical impact under the freezing-of-staked-funds category.

### Likelihood Explanation
Likelihood is moderate-to-low but realistic: any delay between mining the Bitcoin lockup transaction/block and successfully submitting `register-for-bond` on Stacks (e.g., due to congestion, mempool issues, incorrect merkle-proof construction requiring a resubmission, or simply waiting to gather multiple lockup outputs into one call as the function supports up to 10 outputs of possibly different heights) can push the earliest lockup height outside the lookback window while the transaction is still being retried. No malicious actor is required — the staker's own honest but delayed submission triggers the freeze, similar to the guardian-response-window issue described in the source finding.

### Recommendation
Do not rely solely on `get-burn-block-info?` at the raw Bitcoin `height` supplied in the untrusted lockup struct. Options: (1) allow the staker to include a full SPV commitment (Bitcoin header + confirmations) with a monotonically increasing set of anchor headers so verification doesn't require querying an aging burn height directly; (2) cache/checkpoint verified burn-block header hashes at the time of first observation via a data map so later calls do not depend on Clarity's real-time lookback window; or (3) add a maximum age check with an explicit, well-documented registration deadline tied to the lockup height plus the lookback window, and surface this constraint to callers so they cannot construct a lockup that is unregisterable before submission.

### Proof of Concept
1. Bondholder sends BTC to the P2WSH lockup address at Bitcoin/burn height `H`, matching `construct-lockup-output-script` for their principal and desired `unlock-burn-height`.
2. Bondholder waits (for any legitimate operational reason — batching multiple outpoints, congestion, retrying a bad merkle proof) until the current Stacks burn-chain tip has advanced far enough that `get-burn-block-info? header-hash H` no longer returns `Some` (i.e., past Clarity's fixed burn-block lookback window).
3. Bondholder calls `register-for-bond` with a `btc-lockup` `ok` response containing this outpoint at height `H`.
4. `verify-l1-lockups` → `validate-l1-lockup` calls `(verify-block-header (get header lockup) (get height lockup))`, which internally resolves to `(get-burn-block-info? header-hash H)` → `none` → function returns `false`.
5. `(asserts! (verify-block-header ...) ERR_INVALID_BTC_HEADER)` fails, and the transaction reverts with `ERR_INVALID_BTC_HEADER` unconditionally — there is no other successful path for this outpoint at height `H`, ever, while the BTC remains locked under the on-chain timelock script.
