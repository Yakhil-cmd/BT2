### Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login` while every event handler dispatches on the untethered `repository.full_name` field, letting an attacker who controls a webhook secret for *any* configured organization forge events against a stack belonging to a *different* organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate a delivery with by reading the organization login out of the JSON payload itself (`repository.owner.login`, falling back to `organization.login`), then HMAC-verifies the raw body with that organization's configured `webhook_secret`. Once verification passes, the entire raw payload (unchanged) is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and every handler resolves the target `Repository`/`Stack` from a *different* field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`. Because Shipit supports multi-organization GitHub App configuration (`Shipit.github_app_config`, `TOP_LEVEL_GH_KEYS`), nothing ties `repository.owner.login` (the field used to select the verifying secret) to `repository.full_name` (the field the handler actually acts on).

### Finding Description
`Shipit.github(organization:)` looks up a per-organization secret from `secrets.github[organization]` [1](#0-0) . `WebhooksController#verify_signature` derives that `organization` argument directly from attacker-supplied JSON, not from any authenticated context:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`verify_webhook_signature` only proves that *some* payload with this exact byte content was HMAC-signed with organization `X`'s secret [3](#0-2) . It does not prove any relationship between `repository.owner.login` and any other field inside that same payload — HMAC verification only guarantees payload integrity relative to the secret used, it says nothing about whether the *content* of the payload is self-consistent.

Every handler, however, resolves its target using a completely different key:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process`, for example, then walks `stacks.not_archived.where(branch:)` and calls `stack.sync_github(expected_head_sha: params.after)` [5](#0-4) , i.e. it triggers a GitHub sync (which pulls commits/statuses and can advance what Shipit considers deployable) for whatever repository is named in `full_name`, entirely independent of which organization's secret validated the request.

The equality broken is exactly: `organization that authenticated` (`repository.owner.login`, used to pick the HMAC secret) `≠` `repository that is written` (`repository.full_name`, used by `Handler#stacks` to select the `Repository`/`Stack` acted upon). Nothing in `WebhooksController` or `Handler` cross-checks that `repository.full_name`'s owner segment matches `repository_owner`.

### Impact Explanation
This is a cross-tenant confusion inside the trust boundary that the per-organization webhook secret is supposed to enforce. In a multi-org Shipit deployment (the schema explicitly supported by `github_app_config`/`TOP_LEVEL_GH_KEYS`), an actor who legitimately administers the GitHub App/webhook configuration for Organization A (and therefore knows or controls Org A's `webhook_secret`) can sign an arbitrary JSON body with that secret while setting `repository.owner.login` to `"OrgA"` and `repository.full_name` to `"OrgB/target-repo"`. The signature check passes (it only validates against Org A's secret), yet the handler dispatches against Org B's stack. Depending on handler this can force spurious `GithubSyncJob` runs, forged `commit_status`/`check_suite` events feeding into `deployable?` checks, or membership/team side effects (`MembershipHandler` creates `Team`/`User` records) for a repository/organization the attacker has no legitimate relationship with. This does not on its own hand the attacker `GITHUB_TOKEN` or trigger an unauthorized deploy outright, but it lets an unprivileged-with-respect-to-OrgB attacker inject state (fake CI status, fake sync triggers) into another tenant's stack, which is a precursor to influencing `ci.require`/`deployable?` gating used to authorize deploys.

### Likelihood Explanation
Requires the target Shipit instance to be configured with more than one GitHub organization (multi-tenant `secrets.github` schema) and requires the attacker to control (or know) the webhook secret for at least one configured organization — a bar far lower than repository write access on the *victim* organization/repo, which the rules explicitly exclude as out-of-scope. The actual crafting of the payload is trivial (any HTTP client capable of computing an HMAC-SHA1 with a known key). The main residual constraint is that the attacker's controlled organization must itself be onboarded into the same Shipit instance as the victim organization; this is inherent to the documented multi-org design, not an unsupported deployment.

### Recommendation
Cross-validate that the organization used to select the webhook secret matches the owner encoded in every payload field the handler will act on (e.g., require `repository.full_name.split('/').first.casecmp?(repository_owner)` before dispatch, or resolve the target `Repository` using `repository_owner` rather than trusting `full_name` alone). Alternatively, bind webhook secrets to the specific `Repository`/`Stack` record rather than to a organization string parsed from the same untrusted body being verified.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orga` (secret `S_A`) and `orgb` (secret `S_B`), each with a stack tracking `orga/repo1` and `orgb/repo2` respectively.
2. As an actor who controls `orga`'s webhook secret `S_A` (e.g., an org owner who set up Shipit integration for `orga`), craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/repo2" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(S_A, raw_body)`.
4. POST to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` → `"orga"`, fetches `orga`'s `GitHubApp`, and the signature verifies successfully because it was in fact computed with `S_A`.
6. `PushHandler#process` resolves `repository_name` → `"orgb/repo2"`, looks up `orgb`'s stack via `Repository.from_github_repo_name`, and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` — a sync action on Organization B's stack triggered by an actor who only ever proved control over Organization A's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
