### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while all downstream handlers key off the unrelated `repository.full_name` field, letting a valid webhook sender for one organization forge events for another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, and only checks that the raw body's signature matches that org's secret. Every event handler, however, resolves the target `Stack`/`Repository` using a completely different, independently attacker-controlled field: `repository.full_name` [1](#0-0) . Because nothing binds `repository.full_name` to `repository.owner.login`, an attacker who legitimately controls a GitHub App installation on *any* configured organization (and thus knows/can trigger that organization's `webhook_secret`) can send a signed payload whose `owner.login` matches their own org (so signature verification passes) while `full_name` points at a stack belonging to a completely different, victim organization.

### Finding Description
In `WebhooksController#verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This only proves the raw HMAC body signature matches the secret configured for whichever organization `repository.owner.login` claims to be — it never validates that any other field in that same signed body (in particular `repository.full_name`) actually belongs to that organization.

Downstream, every handler resolves which `Stack`/`Repository` record to act on using `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

`Repository.from_github_repo_name` simply splits this string on `/` and looks up any repository by owner/name [3](#0-2) .

Shipit explicitly supports multiple GitHub App installations, one per organization, each with its own `webhook_secret` [4](#0-3) . This is precisely the "organization authenticated vs. repository written" binding called out in the analog rules: the signature check binds trust to `repository.owner.login`, but the code that actually mutates state (stack sync jobs, CI status writes, membership/team writes, PR label/review-stack handling) is keyed on the unrelated `repository.full_name` value from the same untrusted payload.

Concretely, since the JSON body is fully attacker-controlled up to producing a valid signature for their own org, an attacker who has (legitimately) installed/administers the Shipit GitHub App on `OrgEvil` (and thus can compute a valid `X-Hub-Signature` using `OrgEvil`'s `webhook_secret`) can send:
```json
{
  "repository": {
    "owner": { "login": "OrgEvil" },
    "full_name": "OrgVictim/secret-repo"
  },
  ...
}
```
`verify_signature` picks `Shipit.github(organization: "OrgEvil")` and successfully verifies the signature against the attacker's own known secret, but every handler that follows operates on the `OrgVictim/secret-repo` stack.

### Impact Explanation
This crosses the organization/repository trust boundary explicitly listed as in-scope: "an organization that authenticated versus the repository that is written." Concrete abuses enabled by this once a stack for `OrgVictim/secret-repo` exists in the Shipit instance:
- `status` webhooks let an attacker mark an arbitrary existing commit sha of a victim stack with a forged CI `state`/`description`/`context` [5](#0-4) , which can flip a commit's CI status to "success," a status many `shipit.yml` `ci.require` configurations gate deploy eligibility on — enabling an unauthorized deploy of code that never actually passed CI for that org.
- `push` webhooks force a `GithubSyncJob` to run for the victim's stack on attacker-chosen timing (via `PushHandler#process` filtering on branch only) [6](#0-5) .
- `check_suite` and `membership` handlers similarly act on data resolved via the same `repository.full_name`/`organization.login` fields, letting an attacker manipulate teams/CI check state tied to a victim organization's stacks.

This matches the required Critical/High impact bar (cross-organization writes leading to unauthorized deploy) because the actual gate that is supposed to isolate one organization's webhook traffic from another's data is bypassed by controlling only the free-text `full_name`/`owner.login` fields inside a body that the attacker can sign with their own legitimately-obtained secret.

### Likelihood Explanation
Requires only that the target Shipit instance is configured with multiple GitHub App installations (documented, common multi-tenant deployment pattern) and that the attacker legitimately controls/administers the GitHub App installation for at least one of those organizations (i.e., knows or can trigger use of that org's `webhook_secret`) — this does not require access to the victim org, a Shipit account, or any API token, only knowledge of one's own org's webhook secret, satisfying the "unprivileged attacker" bar relative to the victim organization/repository.

### Recommendation
Verify that `repository.full_name`'s owner segment matches the `repository.owner.login` (or `organization.login`) value used to select the signing organization before dispatching to handlers, e.g. reject/422 the request in `WebhooksController#verify_signature` if `repository.full_name.split('/').first.casecmp(repository_owner) != 0`, or better, have `Handler#repository_name` derive the repository strictly from the already-verified organization context rather than re-reading an independent field out of the unauthenticated-relative-to-owner JSON body.

### Proof of Concept
1. Configure Shipit with two GitHub App orgs per `docs/setup.md`, e.g. `OrgEvil` and `OrgVictim`, each with a distinct `webhook_secret` [4](#0-3) .
2. As the administrator/owner of the `OrgEvil` GitHub App installation, obtain/know `OrgEvil`'s `webhook_secret`.
3. Craft a `status` (or `push`) event JSON body where `repository.owner.login = "OrgEvil"` but `repository.full_name = "OrgVictim/secret-repo"` and `sha` is a real commit sha of an existing `OrgVictim` stack.
4. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgEvil_webhook_secret, raw_body)` and POST it to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgEvil")` and verifies successfully against the attacker-known secret [7](#0-6) .
6. `StatusHandler`/`Handler#stacks` resolves the target stack via `payload.dig('repository','full_name')` = `"OrgVictim/secret-repo"` [1](#0-0)  and writes a forged CI status on `OrgVictim`'s commit, despite the signature only ever having been checked against `OrgEvil`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      Rails.logger.warn([

      ].join(' '))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
