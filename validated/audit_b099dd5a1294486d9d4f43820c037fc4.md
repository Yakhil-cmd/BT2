## Title
Webhook signature check keyed on unverified `repository.owner.login` while event handlers act on the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using a field pulled from the **unauthenticated** JSON body, then dispatches the same unauthenticated body to event handlers that trust a *different* field from that body to decide which repository/stack to mutate. This mirrors the reported analog class: a value the code "acts on" is not actually covered by the verification that is supposed to gate it.

## Finding Description
`verify_signature` computes `repository_owner` straight from `request.raw_post` before any signature check occurs: [1](#0-0) [2](#0-1) 

That `repository_owner` value is used only to look up which per-organization `GitHubApp` config (and therefore which `webhook_secret`) to verify the `X-Hub-Signature` against: [1](#0-0) 

Critically, `verify_webhook_signature` treats a **blank** `webhook_secret` as automatically verified: [3](#0-2) 

In the documented multi-org configuration, each organization has its own independent `webhook_secret` (which can be left blank for some orgs): [4](#0-3) 

Once `verify_signature` passes (using whatever secret matched the attacker-controlled `repository.owner.login` field), the controller re-parses the very same raw, unauthenticated body and dispatches it to event handlers, e.g. `PushHandler`: [5](#0-4) 

Those handlers resolve the target repository/stack from `repository.full_name` in the same payload, a field that was never covered by the signature check (the check only keyed off `repository.owner.login`, used solely to select the verifying secret): [6](#0-5) 

This is the trust binding break described by the report's bug class: the field the engine authenticates against (`repository.owner.login`, used to pick a per-org secret) is not the same field the engine subsequently acts on when writing state (`repository.full_name`, used to resolve which stack/repository is synced or has commits/statuses recorded).

## Impact Explanation
If a Shipit instance is configured with multiple GitHub organizations (as documented) and any one of them has no `webhook_secret` set (explicitly supported/blank per the setup docs), an attacker can craft a webhook payload where `repository.owner.login` names the org with no secret (satisfying `verify_webhook_signature`'s early `return true unless webhook_secret`) while `repository.full_name` names a stack belonging to a *different, secret-protected* organization. The push/status/check_suite handlers would then process unauthenticated, attacker-supplied commit/status data against that other organization's stack — e.g. fabricating commit statuses, injecting fake commits into `Stack#commits`, or influencing `GithubSyncJob`/`RefreshCheckRunsJob` enqueue decisions for a repository the attacker does not control. This is a cross-repository write achieved without ever presenting a valid signature for the org being written to.

## Likelihood Explanation
Requires: (1) the host application to configure Shipit for more than one GitHub organization (explicitly documented and supported), and (2) at least one configured organization with a blank `webhook_secret` (also explicitly documented as an accepted configuration, e.g. `secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`). Under that (documented, non-exotic) configuration, the attack requires only sending a single crafted HTTP POST to the public webhooks endpoint with mismatched owner/full_name fields — no credentials, no session, no repository access needed. Likelihood is Medium: contingent on the multi-org + blank-secret configuration, which is a supported but not universal deployment shape.

## Recommendation
- Verify the webhook signature using the secret associated with the organization that owns the repository actually referenced by `repository.full_name` (the value the handlers act on), not a separately-derived `repository.owner.login`.
- Stop treating a blank `webhook_secret` as an automatic pass in `GitHubApp#verify_webhook_signature`; instead, require an explicit `Shipit.disable_webhook_signature_validation`-style opt-out, or refuse to route/act on payloads for orgs without a configured secret.
- After signature verification, re-derive the repository/organization strictly from the same field that was authenticated, and reject events where `repository.owner.login` and the owner segment of `repository.full_name` disagree.

## Proof of Concept
1. Configure Shipit (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs: `SecureOrg` (has `webhook_secret` set) and `OpenOrg` (has `webhook_secret` left blank), each with a stack.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "SecureOrg/protected-repo" },
  "after": "<attacker-chosen-sha>",
  ...
}
```
3. `verify_signature` calls `Shipit.github(organization: "OpenOrg")`, whose `verify_webhook_signature` returns `true` unconditionally because `OpenOrg`'s `webhook_secret` is blank — no valid `X-Hub-Signature` needed.
4. `Shipit::Webhooks.for_event('push')` handlers run against `params`, resolving the stack via `repository.full_name` = `"SecureOrg/protected-repo"`, causing `GithubSyncJob`/commit ingestion to run against `SecureOrg`'s stack despite `SecureOrg`'s secret never being validated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
