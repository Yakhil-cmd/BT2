### Title
NULL/undefined pointer dereference in private-payment justsaying handler causes node crash - (File: network.js)

### Summary
`network.js`'s `handleOnlinePrivatePayment()` reads `arrPrivateElements[0].payload.denomination` before validating that `payload` exists on the head chain element. A peer or paired device can send a malformed `private_payment` message whose head element omits the `payload` field, causing a synchronous `TypeError` ("Cannot read properties of undefined") that is not caught anywhere in the call chain, crashing the receiving node process — the same class of bug as CVE-2021-32275 (a function dereferencing an unchecked/absent field on attacker-controlled input, causing a crash/DoS).

### Finding Description
`handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` only checks that `arrPrivateElements` is a non-empty array: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	...
```

There is no check that `arrPrivateElements[0].payload` is a defined object before `.denomination` is accessed. If an attacker (any connected peer, or a paired device sending a wallet-level private-payment chain) sends a `private_payment`/`private_payments` justsaying whose first chain element has no `payload` key (or `payload: null`), this line throws a synchronous, uncaught `TypeError`.

This function is reached from the network justsaying dispatcher for the `private_payment` message type (and the analogous wallet-level `handlePrivatePaymentChains` path in `wallet.js`, which does perform stronger validation — but the raw network entry point in `network.js` calling `handleOnlinePrivatePayment` directly does not enforce that `payload` exists before this line is reached), making it reachable pre-validation from any unprivileged private-payment counterparty. Compare this to the properly-guarded `validateAndSavePrivatePaymentChain` in `private_payment.js`, which explicitly checks `if (!headElement.payload) return callbacks.ifError("no payload in head element");` before touching `payload` fields — confirming that the missing check in `network.js` is the anomaly, not the intended validation gate: [2](#0-1) 

Because the dereference happens synchronously at the very top of `handleOnlinePrivatePayment`, before any `try/catch` boundary or the deeper chain-validation logic in `private_payment.js`/`indivisible_asset.js`/`divisible_asset.js` is reached, the exception propagates up through the message-handling call stack for this justsaying. If this occurs outside of a guarding `try/catch` in the outer WebSocket message dispatcher, it results in an unhandled exception that terminates the Node.js process (classic NULL/undefined-pointer-dereference-style DoS, analogous to `CosPrim::computeSigOutput()` dereferencing an unchecked pointer in the CVE).

### Impact Explanation
A successful trigger crashes the full node process handling the connection (full nodes process `private_payment` justsayings from any connected peer, and hubs/wallets process them from paired devices). Because full nodes exchange `private_payment` messages as part of normal p2p private-asset routing, a single malformed message from an unprivileged private-payment counterparty can remotely crash a target node's process, taking it offline and preventing it from validating/relaying/confirming new units until restarted — a network-availability (DoS) impact consistent with the "network unable to confirm new units" acceptance criterion when the crash hits witness/relay nodes.

### Likelihood Explanation
Likelihood is high for any counterparty that can open a private-asset exchange with the target (paired wallet device sending a private payment, or any peer forwarding a `private_payment` justsaying it received). No signature, PoW, or spend validation is required before the vulnerable line executes — only that `arrPrivateElements` be a non-empty array, which is trivial to satisfy with `[{}]` or `[{unit: "..."}]`.

### Recommendation
Add an explicit guard in `handleOnlinePrivatePayment` (and any other direct callers) validating that `arrPrivateElements[0].payload` is a non-empty object before accessing `.denomination`/`.outputs`/etc., mirroring the check already present in `private_payment.js`'s `validateAndSavePrivatePaymentChain`:
```js
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("no payload in head private element");
```
Additionally, ensure the top-level WebSocket message dispatcher wraps message-type handlers in `try/catch` so that any single malformed/unvalidated message cannot crash the whole process, rather than relying solely on per-field validation.

### Proof of Concept
1. Establish a paired-device or peer connection capable of sending a `private_payment` justsaying to a target ocore node (light wallet or full node with private-asset support).
2. Send:
```json
{"chains": [[{"unit": "SOME_VALID_LOOKING_UNIT_HASH", "message_index": 0}]]}
```
i.e., a chain whose head element has no `payload` field (or `"payload": null`).
3. The receiving node's dispatch reaches `network.js`'s `handleOnlinePrivatePayment`, which executes `arrPrivateElements[0].payload.denomination`, throwing `TypeError: Cannot read properties of undefined (reading 'denomination')`.
4. If uncaught up the stack, the node process crashes, denying service to that node.

**Note on verification limits:** I was unable to fully trace the exact WebSocket dispatch call site that invokes `handleOnlinePrivatePayment` (to confirm the absence/presence of a wrapping `try/catch` at that specific call layer) due to tool/search truncation in the final iteration. The core defect — the missing `payload` existence check before dereferencing `.denomination` in `network.js:2382`, contrasted with the correct guard present in `private_payment.js:27-28` — is confirmed directly from source, but whether every code path leading to this call is unconditionally unguarded by a `try/catch` should be double-checked in a full review/session before treating this as a certain crash-on-every-topology finding.
