### Title
Signature verification org (`repository.owner.login`) diverges from mutated repository org (`repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC against using `repository_owner`, which reads only `params.dig('repository','owner','login')` [1](#0-0) . The actual handler that mutates state, `LabelCapturingHandler`, resolves the target repository/stack independently via `params.repository.full_name` [2](#0-1) . Nothing in the controller or handler enforces that `repository.full_name`'s owner segment matches `repository.owner.login`, so an attacker who controls (or who owns a no-secret) organization can authenticate a forged webhook with their own org's secret while pointing `full_name` at an unrelated victim org's repository.

### Finding Description
The broken binding, stated as an equality that the code should enforce but does not:

`params.dig('repository','owner','login')` (used to pick the HMAC secret in `verify_signature`) **must equal** the owner segment of `params.repository.full_name` (used by `LabelCapturingHandler#repository` via `Repository.from_github_repo_name`).

Trace:
1. `WebhooksController#create` runs `before_action :verify_signature`, which calls `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(signature, raw_post)` [3](#0-2) . `repository_owner` is exactly `params.dig('repository','owner','login')` [1](#0-0) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is configured for that organization [4](#0-3) . So if the attacker names an organization in `repository.owner.login` that has no `webhook_secret` configured in Shipit (a "no-secret org"), the request passes verification with **zero** knowledge of any secret.
3. After passing this gate, `create` dispatches to handlers with the full raw `params`, unmodified — `repository.owner.login` is never consulted again [5](#0-4) .
4. `LabelCapturingHandler#repository` resolves the target repo via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, splitting `owner/name` straight out of `full_name` [2](#0-1) , `app/models/shipit/repository.rb" lines 53-56`. This is a **completely separate field** from the one used for signature verification, and it can legitimately belong to a different org, e.g. `full_name = "victim-org/prod-app"` while `repository.owner.login = "attacker-org"`.
5. For `action=labeled` on a resolved active (non-archived) stack, `capture_labels?`/`labeled_active_stack?` is true, and `capture_labels` persists `params.pull_request.labels.map(&:name)` onto `stack.pull_request` [6](#0-5) , [7](#0-6) .
6. `ReviewStack#env` merges those label names, uppercased, with value `"true"`, into the stack's environment used for deploy/task commands: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` [8](#0-7) . This env is merged into `TaskCommands#env`/`DeployCommands#env`, which ultimately reaches the shell environment for deploy/rollback commands [9](#0-8) .

If the target stack's `deploy.yml`/Capistrano recipes branch on env flags (a common review-stack pattern, e.g. `if ENV['SKIP_TESTS']`, `if ENV['FORCE_DEPLOY']`), an attacker with no relationship to the victim org can inject arbitrary uppercase env flags into that org's **production-environment** stack purely by forging a webhook that "authenticates" against their own (secret-less) org.

Why existing guards fail:
- `verify_signature` only checks the HMAC against the org named in `repository.owner.login`; it never cross-checks that this org owns the repository named in `repository.full_name`.
- `drop_unhandled_event` only checks event/handler existence, not repository consistency.
- `ExplicitParameters` schema in `LabelCapturingHandler` requires `repository.full_name` to be a `String`, with no constraint tying it to `repository.owner.login` [10](#0-9) .
- `Repository.from_github_repo_name` performs a plain DB lookup by owner/name parsed from `full_name`, with no relation back to any authenticated org [11](#0-10) .
- No model validation, `force_github_authentication`, or `User#authorized?` applies here — this is an unauthenticated webhook path entirely.

### Impact Explanation
An attacker who owns/controls any GitHub organization with no `webhook_secret` configured in the Shipit deployment (or knows a secret for an org they don't own the target repo in) can write attacker-chosen "labels" onto a victim's `ReviewStack#pull_request`, and those labels become uppercase environment variables merged into every subsequent deploy/rollback/task run against that stack, including a **production**-environment stack. This is a genuine "payload for one repository mutating another's stack" case matching the Critical category (unauthorized deploy/rollback behavior alteration via injected env flags), because the write is authenticated only against the attacker's own org while it mutates a repository/stack the attacker's org does not own. It is repeatable against any repository whose review-stack PR the attacker can discover (`full_name`, PR number, active stack), and is bounded only by which repos have active, non-archived review stacks known to the attacker.

### Likelihood Explanation
Preconditions: (1) Shipit is configured with at least one organization that has no `webhook_secret` set (or the attacker otherwise can produce a valid signature for some org config), (2) the victim's repository is registered in Shipit with an active `ReviewStack` (a PR-linked review stack, not archived), (3) the attacker knows/guesses the victim `owner/repo` full name and an open PR number — both are public GitHub information. Attacker cost is a single crafted HTTP POST with a fabricated JSON body; no GitHub or Shipit credentials, sessions, or team membership required. This is fully repeatable and requires no live GitHub interaction to reproduce in tests, satisfying the "unauthenticated" attacker model in the rules.

### Recommendation
In `WebhooksController#verify_signature` (or in a shared preprocessing step before dispatching to handlers), cross-validate that the owner segment of `params.dig('repository','full_name')` matches `params.dig('repository','owner','login')` (or `organization.login`) before verifying/accepting the payload, rejecting (422) on mismatch. Additionally, harden `GitHubApp#verify_webhook_signature` so that a missing `webhook_secret` for an organization does not implicitly authenticate arbitrary payloads (return `false`/require explicit opt-in for "no secret configured" organizations), removing the "no-secret org" bypass entirely.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub, following existing test patterns in that file):

```ruby
test "pull_request labeled webhook authenticated by no-secret org A mutates production stack owned by org B" do
  # Arrange: victim production review stack under org "victim-org"
  victim_repo = shipit_repositories(:shipit) # owner: e.g. "victim-org" in fixtures
  victim_stack = shipit_stacks(:review_stack) # production environment, active, has pull_request
  victim_stack.update!(environment: "production")
  before_labels = victim_stack.pull_request.labels.dup

  # Attacker org "attacker-org" has no webhook_secret configured (Shipit.github(organization: 'attacker-org') has no secret)
  payload = JSON.parse(payload(:pull_request_labeled)) # base fixture
  payload["action"] = "labeled"
  payload["repository"]["owner"]["login"] = "attacker-org"          # signature verification org
  payload["repository"]["full_name"] = victim_repo.full_name        # actual mutated repo, different org
  payload["number"] = victim_stack.pull_request.number
  payload["pull_request"]["number"] = victim_stack.pull_request.number
  payload["pull_request"]["labels"] = [{ "name" => "force_deploy" }]

  @request.headers["X-Github-Event"] = "pull_request"
  # no valid signature needed because attacker-org has no webhook_secret -> verify_webhook_signature returns true

  post :create, body: payload.to_json, as: :json
  assert_response :ok

  victim_stack.reload
  # Binding check: owner used for auth ("attacker-org") != owner of mutated repo (victim_repo.owner)
  assert_not_equal "attacker-org", victim_repo.owner
  # Impact: attacker-authenticated request mutated victim org's PRODUCTION stack labels/env
  assert_includes victim_stack.pull_request.reload.labels, "force_deploy"
  assert_equal "true", victim_stack.env["FORCE_DEPLOY"]
  refute_equal before_labels, victim_stack.pull_request.labels
end
```

This test asserts both sides of the equality (`repository.owner.login` used for signature verification vs. the owner embedded in `repository.full_name` used by the handler) diverge, and demonstrates the resulting unauthorized write into the victim's production `ReviewStack` env/labels.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
