### Title
Missing `return` after exception in `handleSavedPrivatePayments` causes double invocation of `async.each` callback and double `unlock()`, freezing private‑payment processing - (File: network.js)

### Summary
In `handleSavedPrivatePayments()` the inner `validateAndSave` closure computes `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` inside a `try/catch`, but the `catch` block does not `return` after handling the error. This mirrors the OpenSSL PKCS#12 bug class: a malformed/untrusted structure is passed to a hashing/decoding routine that can fail, and the failure path is not properly short‑circuited, leaving the code to continue operating on the object as if the failure did not happen — leading to a fault condition (in this case a double completion signal / mutex desynchronization instead of a NULL deref, but the same "unchecked continuation after failure on attacker data" root cause).

### Finding Description
`handleSavedPrivatePayments` iterates over rows from `unhandled_private_payments` (populated from private-payment chains sent by a payment counterparty/hub, i.e., attacker-reachable JSON stored via `arrPrivateElements = JSON.parse(row.json)`): [1](#0-0) 

```
async.each( // handle different chains in parallel
    rows,
    function(row, cb){
        var arrPrivateElements = JSON.parse(row.json);
        ...
        var validateAndSave = function(){
            var objHeadPrivateElement = arrPrivateElements[0];
            try {
                var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
            }
            catch (e) {
                console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
                if (ws)
                    sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
                deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
            }
            var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
            privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
```

`objHeadPrivateElement.payload` is attacker-controlled — the JSON is stored from `handlePrivatePaymentChains` in `wallet.js`, whose shape check only verifies presence of a few fields via `isNonemptyObject`/`isNonemptyString`/`isNonemptyArray` and does not restrict value types or depth: [2](#0-1) 

so a payload can still contain values that `getSourceString`/`getJsonSourceString` (used internally by `objectHash.getBase64Hash`) reject, e.g. unsupported types, `NaN`, or structures that throw during string_utils serialization: [3](#0-2) 

When such a value causes `getBase64Hash` to throw, the `catch` block runs `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` which deletes the row and invokes `cb()` once: [4](#0-3) 

But because there is no `return` statement in the `catch` block, execution falls through to the line below, computing `key` with `json_payload_hash === undefined`, and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`. That call's `ifOk`/`ifError` callbacks each also invoke `deleteHandledPrivateChain(...)`, calling `cb()` a **second time** for the same `async.each` iteration: [5](#0-4) 

Calling the `async` callback twice for one iteration item is undefined/dangerous behavior in the `async` library and, combined with the surrounding `mutex.lock(["saved_private"], function(unlock){...})` wrapper, can result in the final completion handler `function(){ unlock(); ... }` running twice, or firing prematurely/being followed by a stray second completion. This can double-release/desync the `"saved_private"` mutex key.

### Impact Explanation
`mutex` keys guard sequential processing of the wallet's private-payment queue. Any node/wallet operator receiving private payments (a normal, unprivileged use case for AA/asset transfer counterparties) is affected as soon as an untrusted counterparty sends a malformed private-payment chain whose payload cannot be hashed. Because the same `"saved_private"` lock also gates `handleSavedPrivatePayments`, an unlock desynchronization can leave the queue permanently locked (subsequent `mutex.lock(["saved_private"], ...)` calls never fire) or cause overlapping executions that corrupt in-flight state (`assocNewUnits`, duplicate DB deletes, duplicate `eventBus.emit(key, ...)` calls consumed by `handlePrivatePaymentChains`'s `eventBus.once(key, ...)` in `wallet.js`). The practical effect is that a node/wallet becomes unable to reliably confirm/process further private payments — a network/wallet DoS condition analogous to the crash-on-malformed-input class described in the report, without requiring any privileged access, malicious peer/hub role, or protocol-level attack; a normal payment counterparty triggers it simply by sending a payload with an unhashable field.

### Likelihood Explanation
Reaching this code only requires acting as a normal private-payment sender (asset issuer/transfer counterparty) whose payload is accepted by the loose validation in `handlePrivatePaymentChains` (`isNonemptyObject`/`isNonemptyString`/`isNonemptyArray` checks do not constrain all value types reachable by `getJsonSourceString`). No p2p/hub compromise or elevated privilege is needed — it is purely a matter of crafting a payload whose values are of a type unsupported by the source-string serializer used inside `getBase64Hash`.

### Recommendation
Add a `return` (or otherwise short-circuit) immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `network.js`'s `handleSavedPrivatePayments`, so that when hash computation fails, the function does not fall through to also invoke `privatePayment.validateAndSavePrivatePaymentChain`. Additionally, validate/normalize the private-payload structure before it is persisted to `unhandled_private_payments` (in `handlePrivatePaymentChains`) so that only JSON-hashable payloads (no `undefined`, functions, or other non-serializable values) are ever queued.

### Proof of Concept
Conceptual PoC (cannot be executed without the full runtime, but demonstrates the code path):
1. A wallet peer sends a `private_payment_chain` (via `handlePrivatePaymentChains` in `wallet.js`) whose head element's `payload` passes the loose structural checks (`isNonemptyObject`, `isNonemptyString` on `asset`, `isNonemptyArray` on `inputs`/`outputs`) but contains a value type that `getJsonSourceString`/`getSourceString` cannot serialize (e.g., a numeric field set to `NaN`, or an extra nested object causing the serializer's internal assertions to throw).
2. This chain is stored in `unhandled_private_payments` and later picked up by `handleSavedPrivatePayments`.
3. `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws; the `catch` block deletes the row and calls `cb()`.
4. Execution falls through (no `return`) and calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError` handler calls `deleteHandledPrivateChain(...)` again, invoking `cb()` a second time for the same `async.each` item — corrupting the `mutex.lock(["saved_private"], ...)` lifecycle for that batch and stalling subsequent private-payment processing on the node.

function getBase64Hash(obj, bJsonBased) {
	var sourceString = bJsonBased ? getJsonSourceString(obj) : getSourceString(obj)
	return crypto.createHash("sha256").update(sourceString, "utf8").digest("base64");
}
