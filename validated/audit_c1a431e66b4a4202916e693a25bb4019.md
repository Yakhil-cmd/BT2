### Title
Unauthenticated `reject_new_shared_address` device message lets any paired peer delete another user's pending shared-address setup - ([File: wallet.js])

### Summary
The `reject_new_shared_address` device-message handler deletes all pending-shared-address state for a given `address_definition_template_chash` with no check that the sending device (`from_address`) is actually one of the participants in that specific pending shared-address creation. This mirrors the reported ArcadeDB pattern: an operation that mutates/destroys shared state is exposed to any caller without verifying the caller's authorization/ownership over the target object.

### Finding Description
In `wallet.js`, the `reject_new_shared_address` case only validates that `body.address_definition_template_chash` looks like a valid address/hash, then immediately calls `walletDefinedByAddresses.deletePendingSharedAddress(body.address_definition_template_chash)`: [1](#0-0) 

`deletePendingSharedAddress` performs an unconditional delete keyed only by `definition_template_chash`, with no `device_address`/`from_address` filter at all: [2](#0-1) 

Compare this to `deleteWallet` (used for the analogous `cancel_new_wallet` message), which explicitly checks that the rejecting device is a genuine, not-yet-approved member of the wallet before deleting anything: [3](#0-2) 

No equivalent membership/authorization check exists for `reject_new_shared_address`. Since `address_definition_template_chash` is a public, guessable/observable hash (it is sent in the `create_new_shared_address` offer to all intended members, and is derived deterministically from the definition template via `objectHash.getChash160`), any device that is a correspondent of the victim (or that can otherwise reach the message handler) can send a forged `reject_new_shared_address` message with any `address_definition_template_chash` value and delete the corresponding rows from `pending_shared_addresses` and `pending_shared_address_signing_paths` — including for a shared-address creation process the attacker is not a party to.

### Impact Explanation
This is analogous to the reported bug class ("unauthorized deletion of state without authorization check"), scoped to wallet/contract message handling reachable by a paired device. The impact is a griefing/denial-of-service against multisig ("shared address") wallet setup: a malicious paired correspondent can silently cancel in-flight shared-address (multi-party wallet) creation between two other honest cosigners by replaying or guessing/observing the `address_definition_template_chash` and sending a spoofed rejection, causing the victims' pending multisig setup to be wiped without their consent. It does not directly cause double-spend or fund loss on already-created addresses (those are separate, immutable `shared_addresses` rows), but it undermines availability/integrity of the wallet-provisioning protocol and can be used to repeatedly block legitimate users from establishing shared addresses.

### Likelihood Explanation
Likelihood is moderate: the attacker must be a correspondent device able to send messages to the target device (this is explicitly in-scope per the "wallet and contract message handling" reachable-by-paired-device category), and must know or guess the `address_definition_template_chash` for the specific pending shared address it wants to sabotage. Since this hash is broadcast to all intended member devices as part of the normal `create_new_shared_address` protocol, and since chats/hub messages between correspondents can be intercepted or replayed by any of the intended-but-uninvolved correspondents, this is straightforward to exploit for a device already paired with the victim.

### Recommendation
Add an ownership/authorization check in `reject_new_shared_address` (mirroring `deleteWallet`'s check) before deleting pending state: verify that `from_address` corresponds to a `device_address` row in `pending_shared_address_signing_paths` for the given `address_definition_template_chash`, and that this device has not already approved (`approval_date IS NULL`), before performing the delete. This should be implemented inside `deletePendingSharedAddress` (or a new wrapper) in `wallet_defined_by_addresses.js`, analogous to the existing check in `wallet_defined_by_keys.js`'s `deleteWallet`.

### Proof of Concept
1. Device A and Device B are correspondents and begin creating a shared (multisig) address; Device A sends `create_new_shared_address` offer, and the resulting `address_definition_template_chash` becomes known to both A and B (and is derivable from the definition template).
2. A malicious correspondent C (paired with A, but not a party to this particular shared-address negotiation) sends A the message:
```json
{ "subject": "reject_new_shared_address", "body": { "address_definition_template_chash": "<hash known/observed from A's traffic>" } }
```
3. `wallet.js`'s handler validates only that the chash string looks like a valid address, then calls `deletePendingSharedAddress`, which deletes the `pending_shared_addresses` and `pending_shared_address_signing_paths` rows for that hash — silently destroying the in-progress multisig setup between A and B, even though C was never a participant.
