### Title
CCMenuController#stack bypasses ApiClient stack scoping, letting a token permitted for one stack read the CI status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
This mirrors the reported bug class: a value is checked with the wrong side of a comparison/scope, so a request that "should" be capped by an authorization boundary passes through un-clamped. Here, an `ApiClient` scoped to a single `stack_id` (analogous to the buyer's `msg.value` cap) is only checked for the *permission name* (`read:stack`) but the *stack the token actually touches* is resolved from unscoped `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks` collection used everywhere else in the API.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scoped resolution of "which stacks can this token see": [1](#0-0) 

Every other API controller (`DeploysController`, `StacksController`, `TasksController`, etc.) resolves the target stack through this `stacks`/`stack` helper, so a token created with a `stack_id` (i.e. `here_come_the_walrus` in the fixtures) is confined to `Stack.where(id: current_api_client.stack_id)`.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It still declares `require_permission :read, :stack`, which only calls `current_api_client.check_permissions!('read', 'stack')` — a check against the *permission list*, not against which stack the client is authorized to see: [3](#0-2) 

The binding that should hold is: `stack_id authorized for the token == stack_id the token can query`. Before the request: a token scoped to stack A has permission `read:stack` and `stack_id = A`. After the request: by supplying an arbitrary `params[:stack_id] = B`, the same token — through `CCMenuController#show` → `stack` → `Stack.from_param!(params[:stack_id])` — resolves and reads stack B's `deploys_and_rollbacks`, `branch`, `environment`, and deploy status entirely unscoped by `current_api_client.stack_id`. The permission check passes because it only inspects the permissions array, never the `stack_id` restriction that `BaseController#stacks` enforces for every other endpoint.

### Impact Explanation
This is an unauthenticated-scope escalation: any holder of a stack-scoped `read:stack` API token (e.g. distributed for a specific project's CCMenu/CI-status widget via `CCMenuUrlController`, which explicitly creates limited `read:stack` tokens: [4](#0-3) ) can read deploy/task status, branch, and environment metadata of every stack in the installation, not just the one the token was minted for. This is an unauthorized read of stack/task state across repositories the token holder has no legitimate access to, matching the "High" bucket ("unauthenticated read of stack state, task streams or deploy output" / escalation past the intended authorization scope).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires possession of a legitimately-issued, stack-scoped `read:stack` API token (these are handed out somewhat freely for CI status badges via `CCMenuUrlController`), plus knowledge/guessing of another stack's `id`/param. No signature, session, or GitHub credentials are required beyond the token itself — this matches the "requires a mistake"-style low-likelihood-but-high-impact profile of the referenced bug class, since the vulnerable code path is reachable by design (this endpoint is meant to be used with narrowly-scoped tokens) but the scoping check was simply omitted.

### Recommendation
In `Shipit::Api::CCMenuController`, resolve the stack through the inherited scoped `stacks` collection (i.e. `stacks.from_param!(params[:stack_id])`) instead of unscoped `Stack.from_param!`, so a stack-restricted `ApiClient` cannot escape its `stack_id` binding. Alternatively, add an explicit check that `params[:stack_id]` matches `current_api_client.stack_id` when the client is stack-scoped.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (as `CCMenuUrlController#client` does).
2. Using that token's basic-auth credentials, request `GET /api/stacks/:stack_id_of_B/ccmenu` where `B` is a different, unrelated stack.
3. `authenticate_api_client` succeeds (valid token) and `require_permission :read, :stack` succeeds (`permissions` includes `read:stack`).
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` — unscoped — resolving stack B instead of raising `ActiveRecord::RecordNotFound`/403.
5. The response renders `shipit/ccmenu/project` with stack B's real deploy/rollback status, disclosing information about a stack the token was never authorized to access.
