### Title
Signature Threshold Bypass via Duplicate Keys in `r of set` / `weighted and` Address Definitions - (File: definition.js)

### Summary
`definition.js`'s `validateDefinition()` never checks that the members of an `r of set` or `weighted and` set are distinct (different pubkeys/addresses/sub-definitions). Because `validateAuthentifiers()` verifies each set-member independently against the *same* `unit_hash_to_sign`, a definition that lists the same signing key at two or more set slots can be satisfied by a single signer supplying the identical signature at each of those paths. This is the exact same root cause as GHSA-8m7c-8m39-rv4x: a threshold ("R of N") is met by counting the same cryptographic key/signature more than once instead of requiring N distinct keys.

### Finding Description
`validateDefinition()`'s handling of `r of set` only checks cardinality, not uniqueness of the set elements: [1](#0-0) 

The same absence of a uniqueness check exists for `weighted and`: [2](#0-1) 

At verification time, `validateAuthentifiers()`'s `r of set` branch simply evaluates every listed set member against `assocAuthentifiers[path]` and counts how many pass, with no check that the underlying keys are distinct: [3](#0-2) 

For a leaf `sig` op, verification is: `ecdsaSig.verify(objValidationState.unit_hash_to_sign, signature, args.pubkey)` — since `unit_hash_to_sign` is identical for the whole unit, the same signer providing the same pubkey at two different set paths (`r.0`, `r.1`, ...) can supply the *same* signature value at both paths and both will verify successfully: [4](#0-3) 

This is directly reachable by an ordinary unit poster: any address's spending definition is chosen by whoever creates that address (`chash160` of the definition array), so nothing stops a party from constructing, e.g., `["r of set", {required: 2, set: [["sig",{pubkey:A}], ["sig",{pubkey:A}]]}]`, which *looks* like a 2-signature requirement but is satisfiable by a single key `A`.

The practical attack surface is shared/multisig wallets built via `wallet_defined_by_keys.js`. `createMultisigWallet()` builds the `set` array directly from the caller-supplied `arrDeviceAddresses`, one `sig` slot per device address, with no de-duplication: [5](#0-4) 

If a malicious participant in a shared-wallet negotiation supplies (or manipulates the wallet-definition template so that) the same device address/pubkey occupies two or more of the `set` slots, the resulting definition superficially reads as "N of M distinct co-signers" (e.g. "2 of 3") while in reality only one real private key is needed to satisfy two of the required slots, reducing the effective multisig threshold — a direct multisig signature-threshold bypass identical in nature to the `tough` advisory (accepting a role/definition as satisfying a threshold when the "distinct" signatures actually trace back to fewer unique keys than the threshold implies).

### Impact Explanation
An address that is nominally protected by an `r of set`/`weighted and` multisig (e.g., a 2-of-3 or 3-of-5 shared-custody wallet, escrow, or governance address) can be fully controlled and drained by fewer real key-holders than the threshold advertises, because duplicate key slots let one holder's signature count multiple times toward the required threshold. This is concrete unauthorized spending / fund loss for any multi-party address whose definition contains (accidentally or maliciously) duplicated `sig`/`address` set members, undermining the core security guarantee that N distinct parties must cooperate.

### Likelihood Explanation
Exploitation requires no special privilege — any unit poster can define such an address, and any participant proposing a shared wallet's `arrWalletDefinitionTemplate`/`arrDeviceAddresses` set can insert a duplicate slot. Because neither `validateDefinition()` nor the wallet-creation helper de-duplicates set members, the malformed-but-"valid" definition passes all protocol checks and is accepted by every node, making the flaw silently exploitable whenever counterparties don't manually audit every raw pubkey/address in the definition JSON.

### Recommendation
In `validateDefinition()` (definition.js), for `r of set` and `weighted and` (and ideally `and`/`or` too, for defense-in-depth), reject definitions whose `set` array contains structurally identical sub-expressions or, at minimum, duplicate `sig` pubkeys / `address` targets among the members that could be independently satisfied by the same private key. Additionally, `wallet_defined_by_keys.js`'s `createMultisigWallet()` should reject/de-duplicate `arrDeviceAddresses` before building the `r of set` template.

### Proof of Concept
1. Attacker generates one keypair with pubkey `A`.
2. Attacker defines address `X` with definition:
   `["r of set", {"required": 2, "set": [["sig",{"pubkey":"A"}], ["sig",{"pubkey":"A"}]]}]`
   — this passes `validateDefinition()` since only set length/required bounds are checked, not uniqueness.
3. Funds are sent to address `X` by a victim who is told (or assumes from a "2 of N" template) that two independent keys are required.
4. To spend, the attacker signs `unit_hash_to_sign` once with key `A`, producing signature `S`, and submits `authentifiers = {"r.0": S, "r.1": S}`.
5. `validateAuthentifiers()`'s `r of set` handler independently verifies `r.0` and `r.1`, both succeed (`ecdsaSig.verify` passes twice for the same `pubkey`/signature/hash), `count` reaches `2 >= required`, and the unit is accepted — bypassing the intended 2-distinct-key threshold with a single key.
