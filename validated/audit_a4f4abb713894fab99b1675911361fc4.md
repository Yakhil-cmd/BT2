### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but the acted-upon record is selected only by `sha`/`repository.full_name` with no cross-check to that org — allowing a valid signer from one configured GitHub org to write commit statuses (and trigger continuous delivery) for stacks belonging to a different repository/org - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` or the fallback `params.dig('organization', 'login')`. Once the signature passes, the same raw payload is handed to `Shipit::Webhooks::Handlers::StatusHandler`, whose `process` method resolves the target records purely by `Commit.where(sha: params.sha)` — with no scoping to the repository/org that was actually authenticated. This is the same class of bug as the Gearbox report: the entity that is cryptographically verified (the organization owning the webhook secret) is not the same entity that is ultimately acted upon (the commit/stack, which may belong to any repository in the datastore).

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) fetches the GitHub App config for `repository_owner` and verifies the raw HMAC signature against that org's `webhook_secret`: [1](#0-0) 

This binds trust to "the sender knows Org X's `webhook_secret`" — nothing more. Shipit explicitly supports multiple GitHub organizations, each configured with its own `webhook_secret`/`oauth` block: [2](#0-1) 
and `Shipit.github(organization:)`/`github_app_config` resolve a distinct app per org: [3](#0-2) 

After signature verification succeeds, `create` dispatches the parsed JSON body to all handlers for the event: [4](#0-3) 

`StatusHandler#process`, however, does not scope its target lookup to the repository that was authenticated at all — it queries every `Commit` in the entire datastore by `sha`: [5](#0-4) 

Compare this to `PushHandler`, `PullRequest::*Handler` and the base `Handler#stacks`, which all scope through `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`: [6](#0-5) 

The binding that breaks is:
`organization authenticated by verify_signature (Org X, via its webhook_secret)` ≠ `stack/repository actually written by StatusHandler (any org's commit whose sha happens to match)`.

Before the attacker acts: a commit's `Status` rows can only be created by GitHub itself sending a signed `status` event scoped to that commit's own repository.
After the attacker's request: any principal who legitimately administers a webhook for *any* org configured in this Shipit instance (i.e., knows that org's `webhook_secret`, which is normal, unprivileged/self-service knowledge for that org's own integration) can send a `status` event whose `sha` matches a commit that lives under a *completely different* org/stack. Because `StatusHandler` never re-checks that the target commit's repository matches the authenticated `repository_owner`, the forged status is accepted and written.

### Impact Explanation
`Commit#create_status_from_github!` → `Commit#add_status` emits `commit_status`/`deployable_status` hooks and — critically — calls `stack.schedule_merges` when the new status is `pending` or `success`: [7](#0-6) 
`Status#schedule_continuous_delivery` similarly reacts to newly created rows on `after_commit`. In a stack configured with `continuous_deployment: true`, driving a commit's aggregated status to `success` is sufficient to enqueue `ContinuousDeliveryJob`, i.e. trigger an unauthorized deploy, as shown by the existing test that documents this exact effect for legitimate same-repo status updates: [8](#0-7) 

Because `StatusHandler` performs a global `Commit.where(sha:)` lookup rather than one scoped to the authenticated repository, an attacker who controls one org's webhook integration in a multi-org Shipit deployment can forge CI success/failure state for a commit belonging to an unrelated org's stack, potentially forcing an unauthorized deploy or blocking a legitimate one — matching the report's "Critical: unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitation requires only knowledge of a `webhook_secret` for *some* org configured in the Shipit instance — a credential an org admin legitimately possesses for their own integration, not a Shipit-privileged secret, session, or `ApiClient` token. The attacker needs the target commit's `sha`, which is public information for any GitHub commit. This fits squarely in the "unprivileged attacker" scope defined by the rules (an org that authenticated versus the repository actually written), and requires no additional foothold beyond controlling one legitimate but low-trust webhook endpoint.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already do so) to the repository resolved from the signed payload's `repository.full_name`/`owner.login`, and verify that this matches `Commit#stack#repository` before applying the update — mirroring the pattern already used by `Handler#stacks` / `PushHandler`. More generally, ensure every handler cross-checks that the entity authenticated during signature verification (the org owning `webhook_secret`) is the same entity whose data is mutated, instead of trusting the payload's `sha`/id fields independently of that authentication.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `webhook_secret` (multi-org config as in `config/secrets.development.example.yml`).
2. As the administrator of `org-a`'s GitHub App/webhook (an unprivileged actor with respect to `org-b`'s stacks), craft a `status` event payload:
   ```json
   {
     "sha": "<sha of a commit belonging to org-b's tracked repository>",
     "state": "success",
     "context": "ci/travis",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
   }
   ```
3. Sign the raw body with `org-a`'s `webhook_secret` and POST it to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `org-a`, fetches `org-a`'s app/secret, and the signature validates successfully.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches the commit under `org-b`'s stack (no repository check), creating a `Status` record and, if the commit becomes `success` on a stack with `continuous_deployment: true`, enqueuing `ContinuousDeliveryJob` — an unauthorized deploy triggered by an actor with no relationship to `org-b`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
