### Title
Signature verification is keyed to attacker-controlled `repository.owner.login` while the handler mutates the repo/stack chosen by an independent `repository.full_name` field, letting an attacker forge `pull_request` payloads for a victim repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate a webhook against using `params.dig('repository', 'owner', 'login')` [1](#0-0) , while `LabelCapturingHandler` (via `ReviewStackAdapter`) resolves the repository/stack that actually gets mutated using the independent `params.repository.full_name` field [2](#0-1) [3](#0-2) . Because both fields are attacker-controlled JSON in a single unauthenticated `POST /webhooks` request, an attacker who owns/administers *any* organization configured in this Shipit instance (particularly one with `webhook_secret` unset, which is the documented default in every example config) can pass signature verification for that org while forging a `pull_request` payload whose `repository.full_name` targets a completely different, victim repository.

### Finding Description
The intended invariant is: `repository_owner used to select the verifying secret == repository whose stack/records are mutated`. In this codebase that binding does not hold.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [4](#0-3) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank for that organization, and otherwise only accepts the legacy `sha1` HMAC over `X-Hub-Signature` [5](#0-4) . Multi-org setups documented and shipped in this repo (`test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml`) explicitly default `webhook_secret` to nil per organization.
- The handler that actually processes the event (`LabelCapturingHandler`) never re-checks `repository_owner`; it derives the target `Repository` solely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [2](#0-1) , and finds the stack by `environment: "pr#{params.number}"` scoped to that repository via `ReviewStackAdapter#stack` [6](#0-5) [7](#0-6) .

Exploit flow: attacker crafts a raw JSON body with `repository.owner.login = "attacker-org"` (an org configured on this Shipit instance with no `webhook_secret`, or one whose secret the attacker knows because they administer it) but `repository.full_name = "victim-org/victim-repo"`, `action = "reopened"`, an existing victim PR `number`, and an arbitrary `labels` array. They send `POST /webhooks` with `X-Github-Event: pull_request` and any `X-Hub-Signature: sha1=...` header. `verify_signature` looks up the GitHub App config for `"attacker-org"`, finds no secret, and returns `true` regardless of the signature value [8](#0-7) . `Webhooks.for_event('pull_request')` then dispatches to `LabelCapturingHandler`, which resolves `repository` from `params.repository.full_name` (the victim repo), finds the victim's active `ReviewStack` for `pr<number>` since `reopened_active_stack?` only checks `stack.present? && !stack.archived?` [9](#0-8) , and calls `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [10](#0-9) . Those forged label names are persisted on the victim's `PullRequest` and later surface as uppercased environment variables via `ReviewStack#env`, which merges `pull_request.labels.map(&:upcase) => "true"` into the deploy environment [11](#0-10) .

No existing guard closes this gap: `drop_unhandled_event` only checks event type presence [12](#0-11) ; `verify_signature` never compares `repository_owner` against `repository.full_name`'s owner segment; and the handler's `ExplicitParameters` schema validates types/presence of fields but not cross-consistency between `repository.owner.login` and `repository.full_name` [13](#0-12) .

### Impact Explanation
An attacker who has (or can obtain) valid webhook credentials for *any* org configured on the shared Shipit instance — including a secretless org, which is the shipped default — can write attacker-controlled `PullRequest.labels` onto any other tenant's `ReviewStack`, regardless of which org/repo actually owns that PR. Since labels become uppercased environment variables merged into the stack's deploy/provisioning environment (`ReviewStack#env`), this is a cross-repository record mutation that can influence downstream deploy behavior driven by env vars (e.g., feature-flag-like labels consumed by provisioning scripts). This matches the "Critical — payload for one repository mutating another's stack" category. It is repeatable against any victim repo/PR number known to the attacker (PR numbers are public/discoverable), for every `pull_request` sub-event handled by `LabelCapturingHandler` (opened/labeled/unlabeled/reopened).

### Likelihood Explanation
Preconditions: the Shipit instance must be configured with multiple GitHub organizations (`Shipit.github(organization:)` multi-org mode) and the attacker's org must have no configured `webhook_secret`, or the attacker must otherwise know a valid secret for some org on the instance. Both example configs shipped in this repo default `webhook_secret` to nil, making the secretless-org precondition a realistic, low-cost, common misconfiguration rather than a theoretical edge case. No Shipit session, API token, or GitHub App private key is required — only knowledge of the victim's `full_name` and an existing PR number, both public information. The attack is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
Bind the verified organization to the repository actually acted upon: after verifying the signature for `repository_owner`, require that `params.repository.full_name`'s owner segment equals `repository_owner` before dispatching to any handler, and reject (422) on mismatch. Additionally, treat a missing/blank `webhook_secret` as a hard misconfiguration error (fail closed) rather than an implicit bypass in `GitHubApp#verify_webhook_signature`, and require `X-Hub-Signature-256` (SHA-256) support in addition to/instead of the legacy `sha1`-only check.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure `Shipit.stubs(:secrets)` (or use `secrets_double_github_app.yml` fixture) with two orgs: `"AttackerOrg"` (`webhook_secret: nil`) and `"victim-org"` (repository actually stored in DB as `owner: "victim-org", name: "victim-repo"`).
2. Create `victim_repository = shipit_repositories(:...)` with `owner: "victim-org"`, and an active `Shipit::ReviewStack` with `environment: "pr42"` plus an associated `Shipit::PullRequest` with `labels: []`.
3. Build payload: `{ "action" => "reopened", "number" => 42, "pull_request" => { ..., "labels" => [{"name" => "FORGED_LABEL"}] }, "repository" => { "full_name" => "victim-org/victim-repo", "owner" => { "login" => "AttackerOrg" } }, "sender" => { "login" => "attacker" } }`.
4. `@request.headers['X-Github-Event'] = 'pull_request'; @request.headers['X-Hub-Signature'] = 'sha1=deadbeef'` (arbitrary, unverified since `AttackerOrg` has no secret).
5. `post :create, body: payload.to_json, as: :json`.
6. Assert `response.status == 200` (verification passed despite bogus signature) and `victim_repository.review_stacks.find_by(environment: "pr42").pull_request.reload.labels == ["FORGED_LABEL"]` — proving a payload authenticated under `AttackerOrg`'s (non-)secret mutated `victim-org`'s `PullRequest` record, i.e. `repository_owner (AttackerOrg) != repository.full_name owner (victim-org)` yet the write succeeded.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
