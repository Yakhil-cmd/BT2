### Title
Webhook signature verification is bound to `organization.login`'s GitHub App config, not to `repository.full_name`'s owner, enabling cross-repository forgery when any configured org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and thus which webhook secret) to verify a request against using `repository_owner`, which falls back to the top-level `organization.login` field if `repository.owner.login` is absent. The handlers invoked in `#create`, however, resolve the target repository/stacks purely from `payload.dig('repository', 'full_name')`, with no re-check that this repository actually belongs to the organization used for verification. If any configured GitHub App organization has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` unconditionally returns `true`, letting an attacker "authenticate" via that blank-secret org while naming an arbitrary victim repository in `repository.full_name`.

### Finding Description
The broken binding, stated as an equality that the code should enforce but does not:

`org_used_for_verification (params.dig('repository','owner','login') || params.dig('organization','login'))` **must equal** `owner_of(params.dig('repository','full_name'))` used by the handlers.

Code path:
- `repository_owner` in [1](#0-0)  picks the first present value between `repository.owner.login` and the fallback `organization.login`. An attacker fully controls the JSON body of `POST /webhooks`, so they can omit `repository.owner` and only supply `organization.login`.
- `verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `Shipit.github` looks up the per-org config via `github_app_config(organization)`, raising `GithubOrganizationUnknown` only if that org key is entirely missing from `Shipit.github_config` [3](#0-2) . If the fallback org's key *does* exist (attacker picks a real, configured org), no exception is raised.
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that org's `webhook_secret` is blank: `return true unless webhook_secret` [4](#0-3) .
- `#create` then dispatches `payload` to handlers registered for the event without any further authorization check [5](#0-4) .
- Every handler in `app/models/shipit/webhooks/handlers/**` inherits from `Handler`, whose `stacks` method resolves the target purely from `repository_name`, i.e. `payload.dig('repository', 'full_name')` [6](#0-5) . Nothing in this class, or in the individual handlers, cross-checks that `repository.full_name`'s owner matches `organization.login`/`repository.owner.login` used during `verify_signature`.

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event` set to a handled event (e.g. `push`, `pull_request`), body containing no `repository.owner`, `organization.login` set to `victimless-org` (a real org configured in `Shipit.github_config` with a blank `webhook_secret`), and `repository.full_name` set to `some-other-org/target-repo`. `verify_signature` resolves the GitHubApp for `victimless-org`, finds no secret, and returns `true` regardless of the (missing/forged) `X-Hub-Signature` header. `#create` then runs the handler against `target-repo`'s stacks, which belong to a completely different, unrelated organization.

Existing guards do not stop this: `drop_unhandled_event` only filters by event type, not payload contents; `GithubOrganizationUnknown` is only raised for orgs absent from config, not for the binding mismatch; there is no `ExplicitParameters` schema-level or model-level check tying the verifying org to the acted-upon repository.

### Impact Explanation
An attacker who can trigger a request signed against (or exempted from) one organization's app config can cause Shipit to execute state-changing webhook handlers (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) against a completely different, uninvolved organization's repository and stacks. This is a forged-webhook authentication bypass and cross-repository/cross-tenant mutation — matching the Critical category ("payload for one repository mutating another's stack/commit/task", "authentication bypass (forged webhook ... accepted)"). The attack is repeatable against any repository whose full name is known, for any event Shipit handles, as long as one configured org in the deployment has a blank webhook secret.

### Likelihood Explanation
This requires a specific Shipit operator misconfiguration: a multi-org GitHub App deployment (`github_default_organization` non-nil) where at least one configured organization's entry has no `webhook_secret` set. If that precondition holds, exploitation is trivial and free for any unauthenticated internet user — no GitHub credentials, no session, and no signature computation are needed, since the secret-less org's verification always returns `true`. If every configured org has a properly-set `webhook_secret` (the expected/documented setup), this specific fallback path is not exploitable, though the underlying design defect (verification org ≠ payload's acted-upon repo owner) still exists structurally.

### Recommendation
Verify the webhook signature using the GitHub App config for the organization that actually owns `repository.full_name` (or `repository.owner.login`) — never trust the `organization.login` fallback for secret selection, and do not fall back to it when `repository` is present. Additionally, have `Handler`/`stacks` (or the controller) cross-check that the resolved repository's owner matches the organization whose secret verified the request, and reject webhooks where a `webhook_secret` is blank for a configured org (treat blank secret as a hard misconfiguration error rather than silently accepting unsigned payloads) in `lib/shipit/github_app.rb#verify_webhook_signature`.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:
1. Configure `Shipit.github_config` (or stub `Shipit.github`) with two orgs: `org-a` (no `webhook_secret`) and `org-b` (with a repo `org-b/victim-repo`).
2. `POST /webhooks` with header `X-Github-Event: push`, and JSON body: `{"organization": {"login": "org-a"}, "repository": {"full_name": "org-b/victim-repo"}, ...push payload fields...}` and no `X-Hub-Signature` header (or a bogus one).
3. Assert the response is not `422` (verification passed) — asserting `org_used_for_verification == "org-a"`.
4. Assert that `PushHandler`/relevant handler was invoked with `repository_name == "org-b/victim-repo"` (e.g., stub/mock `Shipit::Webhooks.for_event` or assert a stack belonging to `org-b/victim-repo` receives an update) — asserting `owner_of(repository.full_name) == "org-b"`.
5. Assert `"org-a" != "org-b"`, demonstrating the binding is violated and the victim org's repository was mutated using the attacker-chosen unrelated org's (secret-less) verification path.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
