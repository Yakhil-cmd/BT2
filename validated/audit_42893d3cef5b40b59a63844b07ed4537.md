## Title
Missing timestamp/expiry enforcement in `is_valid_signed_package`/`validateSignedMessage` allows replay of stale signed packages in AAs - (File: formula/evaluation.js, signed_message.js)

### Summary
The reported CVE-2023-40178 shows that `@node-saml/node-saml`'s `validatePostRequestAsync()` verified the cryptographic signature and issuer of a SAML LogoutRequest but never checked the current time against the message's own validity window (`NotOnOrAfter`), letting an attacker replay an already-signed, already-expired request forever. ocore has a directly analogous primitive: `is_valid_signed_package()` (exposed to oscript/AA code) and its underlying `validateSignedMessage()` verify only the cryptographic signature, address definition, and that `last_ball_unit` is a stable ball — they never enforce any freshness/expiry semantics on the signed content itself.

### Finding Description
`validateSignedMessage()` accepts a `timestamp` field as part of the signed-message schema, but that field is only used for the `hasFieldsExcept` allow-list check — it is never read, compared to `Date.now()`, or compared to the referenced `last_ball_timestamp` anywhere in the function body. [1](#0-0) [2](#0-1) 

The whole validation path only checks: field shape, author address/definition consistency, and (if network-aware) that `last_ball_unit` resolves to an existing, stable ball whose `main_chain_index`/`timestamp` are read but only used to build `objValidationState` for definition evaluation, not for any expiry comparison. [3](#0-2) 

`is_valid_signed_package`, the oscript builtin that AA authors call to validate one of these signed packages inside AA triggers, wraps `validateSignedMessage` and additionally only checks version compatibility and that `last_ball_unit` is a stable unit not newer than the current evaluation `mci`. No expiration/staleness of the signed content is enforced at this layer either. [4](#0-3) 

Because the primitive itself performs no expiry check, the burden falls entirely on the AA author to invent their own anti-replay/expiry scheme. This is exactly the same root cause as the SAML flaw: the framework validates authenticity but delegates temporal validity to a layer that may forget to implement it. ocore's own shipped reference AA sample demonstrates this failure mode in practice: `test/samples/order_book_exchange.oscript` accepts two signed orders (`trigger.data.order1`/`order2`), validates them with `is_valid_signed_package`, but has a bare `// to do check expiry` comment where an expiry check should be — i.e., no expiry check is implemented for the signed orders used to execute a trade. [5](#0-4) 

### Impact Explanation
Any address can pre-sign a package (e.g., an order with a favorable price, or any other signed authorization consumed by an AA via `is_valid_signed_package`) and hold onto it indefinitely. Because neither `validateSignedMessage` nor `is_valid_signed_package` enforce any time-based expiry, that signed package remains "valid" forever as long as its signature and (optional) `last_ball_unit` stability checks pass — the only thing an AA can rely on is an application-level check that the AA author must remember to add. When such a check is omitted (as in ocore's own reference `order_book_exchange.oscript` sample), a counterparty can replay an old, stale signed order/authorization after market conditions or other application state has changed, causing the AA to execute against outdated terms. This directly leads to AA fund loss for the counterparty who signed the stale order and expected it to become void, i.e., unauthorized spending/loss of AA-held funds triggered by a single posted trigger unit from an unprivileged AA trigger sender.

### Likelihood Explanation
Likelihood is high for any AA built on top of `is_valid_signed_package` that does not itself implement expiry tracking, since the underlying platform primitive provides no protection and gives no warning that one is needed. ocore ships its own example (`order_book_exchange.oscript`) exhibiting exactly this gap, indicating this is a natural, easy-to-make mistake for AA developers using the officially documented pattern, not merely a theoretical edge case. Exploitation requires no privileged access — only crafting/replaying a previously obtained signed package and sending a trigger unit to the AA.

### Recommendation
Add first-class temporal validity to the signed-package primitives:
- In `validateSignedMessage` (signed_message.js), validate the `timestamp` field against the referenced `last_ball_timestamp`/current time when present, and expose it to callers.
- In `is_valid_signed_package` (formula/evaluation.js), support (and document) an explicit expiry mechanism — e.g., require/verify a `valid_till`/`not_after` value inside `signed_message` and reject packages whose `last_ball` timestamp or trigger timestamp exceeds it — so that AA authors are not solely responsible for re-implementing replay protection.
- Update reference samples such as `order_book_exchange.oscript` to implement the expiry check rather than leave a TODO, since it is used as guidance for real AA development.

### Proof of Concept
1. Party A signs an order package (`signed_message` containing `sell_asset`, `buy_asset`, `price`, etc.) intended to be valid only briefly, as in `order_book_exchange.oscript`. [6](#0-5) 
2. Party B holds onto the signed package well past when Party A intended it to expire (no expiry field is enforced anywhere in the validation chain).
3. Party B submits a trigger unit to the AA with `trigger.data.order1 = <A's stale signed package>` and a matching `order2`.
4. The AA calls `is_valid_signed_package(trigger.data.order1, $order1.address)`, which only checks signature validity and last-ball stability via `validateSignedMessage`, with no timestamp/expiry check performed at any layer. [7](#0-6) 
5. The stale order executes at outdated terms, causing Party A's AA balance to be spent under conditions Party A no longer consents to — a concrete AA fund loss triggered by an unprivileged trigger sender.
