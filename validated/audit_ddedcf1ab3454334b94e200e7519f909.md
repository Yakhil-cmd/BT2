Based on my research, I found a structurally similar reward-accumulation pattern in `substrate/frame/asset-rewards`, but I was unable to confirm the exact numeric value of the `PRECISION_SCALING_FACTOR` constant before running out of tool budget — this is critical to proving the rounding-to-zero condition is practically reachable, so I flag that explicitly below rather than asserting certainty.

### Title
`reward_per_token` accumulator in pallet-asset-rewards can round down to zero, permanently losing staker yield - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards::reward_per_token` computes a per-block reward delta as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` and adds it to the persistently-stored, monotonically-accumulating `reward_per_token_stored`. Just like the Canto Coordinator's `secRewardsPerShare += (blockDelta * 1e18) / marketSupply`, if `total_tokens_staked` is large relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR`, the delta truncates to zero via integer division, and since `last_update_block` still advances, that reward interval is permanently lost rather than deferred. [1](#0-0) 

### Finding Description
`reward_per_token` is called from `update_pool_and_staker_rewards`, which any signed staker triggers via the permissionless `stake`/`unstake`/`harvest_rewards` extrinsics: [2](#0-1) [3](#0-2) 

The reward delta is computed and added into the stored, ever-increasing `reward_per_token_stored`:
```
reward_per_token_stored += reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked
``` [4](#0-3) 

Because integer division truncates, whenever `reward_rate_per_block.saturating_mul(blocks_elapsed).saturating_mul(PRECISION_SCALING_FACTOR) < total_tokens_staked`, the delta added to `reward_per_token_stored` is `0`, even though `last_update_block` is advanced to the current block on every call: [5](#0-4) 

This is precisely the root-cause pattern from the report: the accumulator update is a fire-and-forget, monotonically-advancing calculation (`last_update_block` moves forward regardless), so a zero-delta interval is not "deferred until enough accrues" — it is permanently forfeited. This differs materially from `pallet-nomination-pools`, which instead *recomputes* `current_reward_counter` from the full historical balance delta each time (not an incremental per-block accretion), so a temporarily-zero `FixedU128` counter does not erase already-accrued value — confirmed by its explicit accuracy-notes and the `zero_reward_claim_does_not_update_reward_counter` test showing rewards are preserved rather than lost: [6](#0-5) [7](#0-6) 

The `total_tokens_staked` denominator that any unprivileged staker interacts with is directly attacker-influenceable: an attacker can stake a large amount of the pool's staked asset (an ordinary, non-privileged action gated only by holding/acquiring the staked asset), inflating `total_tokens_staked` for the whole pool. If this pushes `reward_rate_per_block * 1 (block) * PRECISION_SCALING_FACTOR` below `total_tokens_staked`, every subsequent single-block reward update for the *entire pool* (not just the attacker) truncates to zero, silently zeroing out yield for all other honest stakers as well, since `reward_per_token_stored` is shared pool state.

### Impact Explanation
Loss is limited to yield/rewards, not principal — stakers' underlying staked assets remain safe and can be unstaked. This mirrors the original finding's accepted Medium severity rationale ("the loss is limited to yield"). Because the loss compounds silently across every block where the delta truncates, and affects all pool participants (not just the staker who inflated `total_tokens_staked`), the aggregate yield loss for a popular pool with many/large stakers could be substantial over time.

### Likelihood Explanation
Reaching the zero-delta condition requires no privileged role — `stake` is callable by `ensure_signed(origin)`, and pool admins (a `CreatePoolOrigin`-gated but potentially permissionless-in-future role per the pallet's own doc comments) set `reward_rate_per_block`, not the attacker. Whether this is *practically* triggerable depends on the concrete value of `PRECISION_SCALING_FACTOR` relative to realistic `reward_rate_per_block` and `total_tokens_staked` magnitudes for a given `T::Balance` type (e.g., 18-decimal assets) — **I was not able to retrieve the exact numeric definition of `PRECISION_SCALING_FACTOR` within my tool budget**, so I cannot state with certainty whether the constant is large enough (analogous to the recommended `1e27` fix in the original report) to make this practically unreachable, or too small (analogous to the vulnerable `1e18`) to make it easily triggerable with realistic pool parameters. This is the single missing piece needed to fully confirm exploitability.

### Recommendation
- Confirm/increase `PRECISION_SCALING_FACTOR` to a magnitude that, combined with `T::Balance`'s max realistic supply and minimum realistic `reward_rate_per_block`, cannot round to zero for any single-block update (analogous to using `1e27`-scale precision instead of `1e18`).
- Alternatively, switch `reward_per_token`/`derive_rewards` to a higher-precision fixed-point type (e.g. `FixedU128`/`U256` intermediate, as `pallet-nomination-pools` does with `T::RewardCounter: FixedPointNumber`) rather than raw integer division scaled by a constant.
- Consider accumulating a remainder/dust carry-over across updates instead of discarding the truncated fractional part outright.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

	#[test]
	fn zero_reward_claim_does_not_update_reward_counter() {
		// create a pool that has a quarter of the current polkadot issuance
		ExtBuilder::default()
			.ed(DOT)
			.min_bond(POLKADOT_TOTAL_ISSUANCE_GENESIS / 4)
			.build_and_execute(|| {
				assert_eq!(
					pool_events_since_last_call(),
					vec![
						Event::Created { depositor: 10, pool_id: 1 },
						Event::Bonded {
							member: 10,
							pool_id: 1,
							bonded: 2500000000000000000,
							joined: true,
						},
						Event::MetadataUpdated { pool_id: 1, caller: 900 },
					]
				);

				// and have a tiny fish join the pool as well..
				Currency::set_balance(&20, 20 * DOT);
				assert_ok!(Pools::join(RuntimeOrigin::signed(20), 10 * DOT, 1));

				// earn some small rewards
				deposit_rewards(DOT / 1000);

				// if 20 claims now, their reward counter should stay the same, so that they have a
				// chance of claiming this if they let it accumulate. Also see
				// `if_small_member_waits_long_enough_they_will_earn_rewards`
				assert_ok!(Pools::claim_payout(RuntimeOrigin::signed(10)));
				assert_ok!(Pools::claim_payout(RuntimeOrigin::signed(20)));
				assert_eq!(
					pool_events_since_last_call(),
					vec![
						Event::Bonded {
							member: 20,
							pool_id: 1,
							bonded: 100000000000,
							joined: true
						},
						Event::PaidOut { member: 10, pool_id: 1, payout: 9999997 }
					]
				);

				let current_reward_counter = default_pool_reward_counter();
				// has been updated, because they actually claimed something.
				assert_eq!(
					PoolMembers::<T>::get(10).unwrap().last_recorded_reward_counter,
					current_reward_counter
				);
				// has not be updated, even though the claim transaction went through okay.
				assert_eq!(
					PoolMembers::<T>::get(20).unwrap().last_recorded_reward_counter,
					Default::default()
				);
			});
