### Title
Uncaught exception in `definition template` authentifier evaluation crashes the validating node - (File: definition.js)

### Summary
`definition.js`'s `validateAuthentifiers()` (the function that verifies unit signatures/authentifiers against an address definition during ordinary unit validation) contains an unguarded `throw` inside an asynchronous `db.query` callback for the `definition template` operator. Any address owner can put a `['definition template', [unit, params]]` clause in their address definition, and any unit author signing with that address (or any peer merely validating a unit authored by such an address) can cause every validating node to hit an uncaught exception, crashing the Node.js process — a direct analog to the Dovecot NTLM parser crash (CVE-2020-12673), where malformed/attacker-influenced input reaching an unguarded code path causes the target service to crash.

### Finding Description
`validateAuthentifiers()` in `definition.js` evaluates an address's definition tree to verify authentifiers for a posted unit. The `'definition template'` case looks up the referenced template unit: [1](#0-0) 
The equivalent case inside `validateDefinition()` (used for definition *validation*, not authentifier *checking*) has proper error handling via `try { … } catch (e) { … return cb(e.toString()) }`: [2](#0-1) 
However, `validateAuthentifiers()`'s copy of this logic — the one exercised at actual unit-signature-verification time, on every unit spent from such an address — has no such guard: if `rows.length !== 1` (the template unit not found, not yet stable, or matching more than one row), it directly does `throw Error("not 1 template")` inside the `conn.query` callback. Because the throw happens inside an asynchronous database callback, it is not caught by any surrounding `try/catch` in the call stack; it becomes an uncaught exception that (absent a global handler that gracefully continues) terminates the Node.js process for every node performing this validation.

An unprivileged user can create an address whose definition includes a `definition template` op referencing a unit that:
- does not exist,
- exists but is not (yet) app=`definition_template`,
- is not yet stable, or
- is not on the main chain below `last_ball_mci` at validation time,

any of which makes `rows.length !== 1` true. Since address definitions are chosen and hashed by their owner (`objectHash.getChash160(definition)` determines the address), and definitions become active any time an author signs a unit from that address, this path is reachable purely by posting units — no privileged role, hub, or node compromise is required.

This mirrors the CVE-2020-12673 bug class: a specially crafted/attacker-controlled input reaching a parsing/validation code path without adequate defensive checks causes the receiving service to crash (there, an out-of-bounds read in C; here, an uncaught JS exception thrown from inside an async callback).

### Impact Explanation
Because `validateAuthentifiers()` is invoked by every full node (and light-wallet-serving hub) when validating any unit spent from the crafted address, a single posted unit referencing an unresolved/duplicate "definition template" can crash every node in the network that attempts to validate it (the same deterministic code path executes on all nodes independently). This satisfies the "node unable to confirm new units" / network-availability bar: nodes crash, restart, and re-crash on the same unit until the code is fixed or the poisoning unit is filtered out, potentially halting confirmation of new units network-wide (equivalent in kind to a service-crashing DoS, as with the Dovecot auth service crash referenced in the CVE).

### Likelihood Explanation
High. No special privileges are needed: any wallet user can construct an address definition containing `['definition template', [some_unit, {...}]]` where `some_unit` is deliberately chosen/left unresolved (e.g., referencing a unit that will never become app=`definition_template`, or that is not yet stable). The attacker then simply posts/spends from that address. This requires only standard unit-posting capability, matching the "unprivileged unit poster" reachability constraint.

### Recommendation
Wrap the `conn.query` callback logic for the `'definition template'` case in `validateAuthentifiers()` in a `try/catch` (mirroring the safer pattern already used in `validateDefinition()`), and replace the unconditional `throw Error("not 1 template")` with a graceful `cb2(false)` (treat as authentifier failure) instead of throwing. Additionally, audit all other unguarded `throw` statements inside asynchronous `conn.query`/`db.query` callbacks throughout `definition.js` (e.g., `signed_message.js`, other callers of `validateAuthentifiers`) for the same uncaught-exception-in-async-callback pattern, since these are silent process-crash vectors reachable from validation of ordinary, attacker-crafted units.

### Proof of Concept
1. Attacker creates address `A` with definition `['definition template', ['UNIT_X', {p:1}]]` combined validly with a `sig` branch elsewhere so the definition passes `validateDefinition()`'s complexity/signature checks (`UNIT_X` can be any base64-looking 44-char string that is not (yet) a stable `definition_template` unit — this is legal at definition-creation time since `validateDefinition()`'s `definition template` case only rejects it at evaluation time, when actually used as part of authentifier checking, if `rows.length !== 1`, but returns an error there via `cb`, not a throw — so the address itself can be created and become the author's address).
2. Attacker posts a payment unit spending from address `A`, requiring the `definition template` authentifier branch to be evaluated by `validateAuthentifiers()` (i.e., the corresponding signing path is used/reachable per `pathIncludesOneOfAuthentifiers`).
3. When any full node validates this unit, `validateAuthentifiers()`'s `'definition template'` handler runs the `conn.query` for `UNIT_X`; because `UNIT_X` is not a stable `definition_template` unit at `last_ball_mci`, `rows.length !== 1`.
4. The unguarded `throw Error("not 1 template")` executes inside the async DB callback, producing an uncaught exception that crashes the validating Node.js process.
5. Every peer/hub that receives and attempts to validate this unit crashes identically, since the code path is deterministic — the network becomes unable to confirm units referencing this crafted address until the offending unit or code is patched.
