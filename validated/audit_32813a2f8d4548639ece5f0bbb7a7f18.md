### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler` lets any repository forge a required-context `success` Status onto another stack's commit, defeating the `require_ci` deploy gate - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely `Commit.where(sha: params.sha)` with no repository/stack scoping, then calls `commit.create_status_from_github!(params)` for every match. Because Git commit SHAs are content-addressed and identical across fork networks (an unmodified commit keeps the same SHA in every fork), an attacker who owns any repository sharing history with the victim's repo can push a real, validly-signed `status` webhook that gets applied to the victim's `Commit` row, forging a `success` status for a `required_statuses` context and flipping `Commit#deployable?` to `true`.

### Finding Description
The broken binding is:
`Status(context, state) satisfying required_statuses.include?(context) && state == "success"` **should equal** `a status produced by the CI system the owner of that specific repository/stack configured for that context`.

In reality: [1](#0-0) 
`Commit.where(sha: params.sha)` is global across the entire application - it is not filtered by `repository`, `stack_id`, or any tenant boundary. Any commit row in any stack whose `sha` matches the payload's `sha` gets `create_status_from_github!` invoked on it: [2](#0-1) 
which calls `Status.replicate_from_github!(stack_id, github_status)`, persisting a `Status` scoped to *that commit's* `stack_id` (the victim's stack), using only the fields from the incoming payload (`state`, `context`, `description`, `target_url`): [3](#0-2) 

`WebhooksController#verify_signature` validates the HMAC signature against the GitHub App/organization named in the payload's own `repository.owner.login`: [4](#0-3) 
This only proves the webhook really came from GitHub for *some* repository where the shared Shipit GitHub App is installed - it says nothing about which `stack`/`Commit` the SHA inside the payload should be associated with. There is no check that `repository.full_name` in the payload matches `commit.stack.repository.full_name`.

`Commit#deployable?` then trusts the resulting `Status::Group`: [5](#0-4) 
and `required?`/inclusion in `Status::Group` is purely `context`-string matching, oblivious to which repository actually produced the status: [6](#0-5) [7](#0-6) 

**Exploit flow:**
1. Attacker forks (or otherwise obtains a repo sharing commit history with) the victim's repository, so at least one unmerged/ancestor commit SHA is identical between attacker's repo and a commit already tracked by the victim's `Stack`.
2. Attacker installs/has the shared Shipit GitHub App on their own repo (an action over their own property, requiring no victim secret) and, using their own GitHub token, sets a commit status (`state: success`, `context: <victim's required context string>`) on that shared SHA via the GitHub Statuses API.
3. GitHub delivers a genuinely-signed `status` webhook to Shipit's `/webhooks` endpoint. `verify_signature` passes because the signature is valid for the (attacker's) `repository.owner.login`.
4. `StatusHandler#process` finds the victim's `Commit` row purely by matching `sha`, with zero regard for which repository sent the event, and writes a `Status` under the victim's `stack_id` with the forged `success` state and matching `context`.
5. `Commit#deployable?` and the `Status::Group` required-context check now report the commit as CI-passed for the victim's stack.
6. If an `Api::DeploysController#create` request is later made with `require_ci: true` (which calls `param_error!(:require_ci, ...) unless commit.deployable?`), the forged status satisfies the check and the deploy proceeds, bypassing the CI gate the victim's stack owner configured.

None of the existing guards prevent this: `verify_signature` authenticates the webhook's *origin org*, not the *target stack*; `ExplicitParameters` on `StatusHandler` only validates payload shape (`sha`, `state`, `context`, etc.), not repository identity; there is no `drop_unhandled_event` rejection for status events; and `Commit`/`Status` model validations never assert `commit.stack.repository == payload.repository`.

### Impact Explanation
A cross-tenant write: a webhook that genuinely originates from repository A (attacker-controlled) mutates `Status` records belonging to stack/commit of repository B (victim), directly matching the "payload for one repository mutating another's stack/commit" Critical category. Combined with a valid `ApiClient` scoped to the victim's stack (a separate precondition, as the question itself notes), this defeats the `require_ci` safety gate and can produce an unauthorized deploy of a commit that never actually passed the victim's CI. Repeatable against any stack/repo pair that shares a commit SHA (trivial via forking public repos), and is not limited to a single victim - it works for any repository reachable through the shared GitHub App installation.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository that shares at least one commit SHA with the victim's tracked history (achievable via a public fork, common in Git workflows), (b) the shared Shipit GitHub App/webhook endpoint installed for their own repo/org (something they control), and (c) - to reach actual deploy impact - a valid `ApiClient` token scoped to the victim's stack, which is a privilege outside the baseline "unprivileged attacker" model defined in this audit. Absent that token, the practical impact is limited to corrupting the victim's commit-status/CI display state (still a real cross-tenant write) rather than a full unauthorized deploy. The forgery step itself (steps 1-5) requires no secrets and is fully repeatable at will.

### Recommendation
Scope the `StatusHandler` (and `refresh_statuses!`/`CheckRunsHandler` equivalents) lookup by repository, not merely `sha`. Since a `Commit` doesn't store repository directly, join through `stack.repository` (e.g., `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner: ..., repository_name: ... })` using `params.dig('repository', 'owner', 'login')` / `params.dig('repository', 'name')` from the webhook payload) before calling `create_status_from_github!`, so a status is only ever applied to commits whose stack's configured repository matches the webhook's originating repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
test "a status webhook from an unrelated repository forges a required status on another stack's identical-SHA commit" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  victim_stack.update!(
    ignore_ci: false,
    lock_reason: nil
  )
  DeploySpec.any_instance.stubs(:required_statuses).returns(['ci/required'])

  # Attacker's payload references a *different* repository, but the same sha
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/required',
    'repository' => { 'full_name' => 'attacker/unrelated-fork', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  victim_commit.reload
  assert victim_commit.deployable?, "victim commit should NOT become deployable from a forged cross-repo status"
end
```
Both sides of the binding diverge: the `Status` satisfying `required_statuses` was produced by `attacker/unrelated-fork`'s CI, not by `shopify/shipit-engine`'s configured CI, yet `commit.deployable?` returns `true`, proving the gate is bypassed. `test/` proof requires no live GitHub call - it directly invokes `StatusHandler#call`, mirroring how `WebhooksController#create` dispatches parsed payloads after signature verification.
