Found the exploitable binding mismatch: the `WebhooksController` verifies the HMAC signature against an app/secret selected by `repository.owner.login` (or `organization.login`) from the JSON body, but every event `Handler` (e.g. `PushHandler`, `PullRequest::*Handler`) independently resolves the target `Repository`/`Stack` from `repository.full_name` in that same, single, attacker-controlled JSON body. Nothing binds "the organization whose secret validated this signature" to "the repository full_name that the handler actually acts on" — they are two different fields read from the same payload, verified with one org's key but consumed for a different org's repository.

### Title
Webhook signature verification authorizes by `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature with, based on `repository.owner.login` (falling back to `organization.login`) taken from the untrusted JSON body itself. [1](#0-0) 
Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same parsed body to handlers, which locate the `Repository`/`Stack` to act on via `payload.dig('repository', 'full_name')`, a completely separate field of the same body, never itself covered by any per-organization binding. [2](#0-1) [3](#0-2) 

### Finding Description
An operator running Shipit with more than one configured GitHub organization (`config/secrets.*.yml` supports multiple `github.<org>` blocks, each with its own `app_id`/`webhook_secret`/`private_key`) creates exactly this trust binding: "the organization that authenticated this request" should equal "the repository this request is permitted to mutate." [4](#0-3) 
Nothing enforces that equality. `repository_owner` (used only for signature verification) and `repository.full_name` (used only for locating the target `Stack`) are two independent, attacker-suppliable fields of the same raw JSON POST body: [5](#0-4) 
An attacker who is a legitimate, unprivileged member/collaborator of **OrgTwo** (weak or leaked `webhook_secret`, or an org they fully control) can craft a webhook whose `repository.owner.login` / `organization.login` is `OrgTwo` — so the signature is verified using `OrgTwo`'s secret — while `repository.full_name` is set to a stack belonging to `OrgOne` (e.g. `OrgOne/critical-repo`). `PushHandler.process`, and the various `PullRequest::*Handler` classes, resolve the acted-upon `Stack` purely from `repository.full_name` via `Repository.from_github_repo_name`, with no check that this repository belongs to the organization that produced a valid signature. [6](#0-5) [7](#0-6) 

This breaks the equality: `organization that authenticated == repository that is written`. Before the attacker's request: only genuine GitHub webhooks signed with `OrgOne`'s secret can drive `OrgOne`'s stacks. After: any party controlling (or with signature material for) `OrgTwo` can forge a `push`/`pull_request` event that is accepted as validly signed and yet drives sync, provisioning, or archival actions on `OrgOne`'s stacks, because verification and dispatch key off different, uncorrelated fields of the same untrusted body.

### Impact Explanation
This crosses a cross-repository trust boundary: a party who only controls credentials/secret material for one configured organization can trigger `GithubSyncJob`/`sync_github`, `ReviewStackAdapter#find_or_create!`/`archive!`/`unarchive!` (deprovision/reprovision of infrastructure), and other webhook-driven actions against stacks owned by an unrelated organization on the same Shipit instance. This matches the "cross-repository writes" high/critical impact category, since state-changing operations (build sync triggers, review-stack archival/deprovisioning/re-provisioning) are performed on a repository the signing organization does not own.

### Likelihood Explanation
Requires the deployment to configure more than one GitHub organization (explicitly supported and documented, e.g. `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), and requires the attacker to already have or obtain valid signing material for at least one of the configured orgs (e.g. their own org's `webhook_secret`, which they legitimately possess since they administer that org's GitHub App). No `ApiClient` token, session, or GitHub write access to the victim repository is needed — only knowledge of the victim's `repository.full_name` string, which is public information.

### Recommendation
Bind the two fields cryptographically instead of trusting both independently from the same payload: after selecting the GitHub App via `repository_owner` and verifying the signature, re-derive/validate that the `repository.full_name`/`repository.owner.login` used by the handler for repository lookup is the *same* organization whose secret validated the request (e.g., pass the authenticated organization into `Handler.call` and have `stacks`/`repository` lookups filter by it, rejecting mismatches), rather than letting `Handler#stacks` resolve repositories purely from unauthenticated payload data.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who controls `OrgTwo`'s GitHub App webhook secret, build a `push` event JSON body where `organization.login` / `repository.owner.login` = `OrgTwo` (so `Shipit.github(organization: 'OrgTwo')` is selected) but `repository.full_name` = `OrgOne/critical-repo`.
3. Sign the raw body with `OrgTwo`'s `webhook_secret` and send `X-Hub-Signature`, `X-Github-Event: push` to `/github/webhooks`.
4. `verify_signature` succeeds (signature matches `OrgTwo`'s secret for `repository_owner == 'OrgTwo'`). [8](#0-7) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('OrgOne/critical-repo')` and triggers `sync_github` on `OrgOne`'s stack, despite the request only being validly signed for `OrgTwo`. [9](#0-8) [10](#0-9)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
