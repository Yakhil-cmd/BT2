### Title
Cross-tenant webhook forgery via repository_owner/repository.full_name divergence enables scheduling check-run refreshes on another organization's commit - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` from the attacker-supplied JSON body, while `Handler#stacks` resolves the target repository/stack using `repository.full_name` from the same body. Because both fields are read from the same attacker-controlled raw POST body and never cross-validated against each other, an operator of one legitimately onboarded org (who knows their own `webhook_secret`) can sign a payload that verifies against their own org while pointing `repository.full_name` at a repository owned by a completely different, non-consenting org.

### Finding Description
The broken binding, stated explicitly: `repository_owner` (used to pick the `GitHubApp`/`webhook_secret` for signature verification) is assumed to equal the owning organization of `repository.full_name` (used to resolve the target `Repository`/`Stack`), i.e. `params.dig('repository','owner','login') == repository.full_name.split('/').first`. GitHub itself always keeps this true for real deliveries, but Shipit's `POST /webhooks` endpoint accepts arbitrary requests from anyone, not just from GitHub, and both values are read independently from the same attacker-controlled JSON:

- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(signature, request.raw_post)`, where `repository_owner` is `params.dig('repository','owner','login')`. [1](#0-0) [2](#0-1) 

- `verify_webhook_signature` is a pure HMAC check over the raw body using whatever `webhook_secret` was configured for the org named by `repository_owner`; it does not inspect any other field of the payload. [3](#0-2) 

- `Handler#stacks` (base class used by `CheckSuiteHandler`) resolves the target repository using a *different* field, `payload.dig('repository', 'full_name')`, via `Repository.from_github_repo_name`. [4](#0-3) [5](#0-4) 

- `CheckSuiteHandler#process` then iterates `stacks` (scoped to whatever `Repository` `full_name` resolved to) and calls `Commit#schedule_refresh_check_runs!` on any matching commit — no further ownership check is performed. [6](#0-5) 

**Exploit flow**: Attacker legitimately owns/administers `org-a`, which has been onboarded into this Shipit instance with its own `webhook_secret` (per the multi-org config pattern shown in `config/secrets.development.example.yml`). The attacker crafts a raw JSON body:
```json
{
  "check_suite": {"head_sha": "<victim-commit-sha>", "head_branch": "<victim-branch>"},
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/private-repo"}
}
```
computes `sha1=HMAC(org-a's webhook_secret, raw_body)` (known to them because they configured that secret themselves), sets header `X-Github-Event: check_suite`, and POSTs to `/webhooks`. `verify_signature` looks up `org-a`'s app via `repository_owner` ("org-a"), verifies successfully, and passes control to `CheckSuiteHandler`, which resolves the target repo from `full_name` ("org-b/private-repo") — a repository `org-b` never authorized `org-a` to touch — and calls `schedule_refresh_check_runs!` on `org-b`'s commit.

Existing guards do not catch this: `drop_unhandled_event` only checks the event name is registered; the `ExplicitParameters` schema for `CheckSuiteHandler` only validates `head_sha`/`head_branch` types/presence, not repository identity; `verify_signature`'s only role is proving the *bytes* weren't tampered with relative to a secret chosen from the same untrusted payload — it never asserts that the secret owner matches the object being mutated. There is no code anywhere in the request path that compares `repository.owner.login` to `repository.full_name`'s owner segment.

### Impact Explanation
Any org configured as a tenant on a shared Shipit instance can trigger `Commit#schedule_refresh_check_runs!` (and by the same mechanism, any other webhook-driven side effect keyed off `repository.full_name` in other handlers such as the `pull_request/*` handlers, `status`, `push`, etc., which all inherit `Handler#stacks`/`repository_name`) against a stack/commit belonging to a different tenant that never authorized or interacted with the attacker's org. This is a payload for one repository/organization mutating another tenant's stack/commit state — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. The attack is repeatable against any repository name known to the attacker (repository names are commonly public/guessable) and is not limited to `check_suite` — the same divergence exists in the shared `Handler` base class used by many other webhook handlers, widening blast radius across the whole webhook surface for any multi-tenant Shipit deployment.

### Likelihood Explanation
Preconditions: the Shipit instance must be configured for multiple GitHub organizations (documented, supported pattern in `config/secrets.development.example.yml`), and the attacker must control (as a legitimate admin) at least one onboarded org with a known `webhook_secret` — which is the normal, expected state for any tenant in such a deployment, not a privileged secret. No GitHub interaction is required at all; the attacker sends a direct HTTP POST to the public `/webhooks` endpoint with a self-computed HMAC. Cost is trivial (one HTTP request, standard HMAC computation), fully repeatable, and requires no race conditions or timing tricks.

### Recommendation
Cross-validate that `repository.owner.login` (the identity used to select the verifying `webhook_secret`) matches the owner segment of `repository.full_name` (the identity used to resolve the target `Repository`) before dispatching to any handler — e.g., in `WebhooksController#create` or `Handler#initialize`, reject the request (422) if `payload.dig('repository','owner','login')` does not case-insensitively equal `payload.dig('repository','full_name').split('/').first`. Additionally/alternatively, resolve the target `Repository` first and verify the signature using the secret belonging to that repository's own `owner` column rather than trusting the attacker-suppliable `repository.owner.login` field independently.

### Proof of Concept
Minitest plan (functional/controller test, no live GitHub, WebMock-free per prompt):
```ruby
test "check_suite webhook signed by org-a cannot schedule refresh on org-b's commit" do
  # Setup: org-a and org-b are separate tenants with distinct webhook_secret configs
  Shipit.stubs(:github).with(organization: 'org-a').returns(github_app_for('org-a', secret: 'org-a-secret'))
  Shipit.stubs(:github).with(organization: 'org-b').returns(github_app_for('org-b', secret: 'org-b-secret'))

  victim_repo = create_repository(owner: 'org-b', name: 'private-repo')
  victim_stack = create_stack(repository: victim_repo, branch: 'main')
  victim_commit = create_commit(stack: victim_stack, sha: 'deadbeef')

  body = {
    'check_suite' => { 'head_sha' => victim_commit.sha, 'head_branch' => 'main' },
    'repository' => { 'owner' => { 'login' => 'org-a' }, 'full_name' => 'org-b/private-repo' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'org-a-secret', body)

  @request.headers['X-Github-Event'] = 'check_suite'
  @request.headers['X-Hub-Signature'] = signature

  # Assertion: binding equality 'org-a' == owner-of(repository.full_name) == 'org-b' is FALSE,
  # yet the handler still acts on org-b's commit.
  Commit.any_instance.expects(:schedule_refresh_check_runs!).never # after fix, should be `.never`
  # Before fix, this would instead be:
  # victim_commit.expects(:schedule_refresh_check_runs!) -- demonstrates the bug fires

  post :create, body: body, as: :json
  assert_response :ok
end
```
Both sides of the equality to assert explicitly in the test: `repository_owner` resolved by the controller (`'org-a'`) vs. `Repository.from_github_repo_name('org-b/private-repo').owner` (`'org-b'`) — showing they diverge, and that `schedule_refresh_check_runs!` is nonetheless invoked on `victim_commit`, which belongs to `org-b`, not `org-a`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

    end
