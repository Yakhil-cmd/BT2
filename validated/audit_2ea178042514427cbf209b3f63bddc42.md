## Title
Scoped ApiClient bypasses stack authorization in CCMenu API endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method used by `Shipit::Api::BaseController` in a way that discards the stack-scoping enforced for `ApiClient` tokens, allowing a client token authorized for one stack to read the CI status of any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the authenticated client's authorized stack when the `ApiClient` is stack-scoped: [1](#0-0) 

That is, `stacks` resolves to `Stack.where(id: current_api_client.stack_id)` only when `current_api_client.stack_id?` is true, and `stack` is derived from that scoped relation via `stacks.from_param!(params[:stack_id])`. This is the binding: `token.stack_id == stack.id` for any stack-scoped client.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

Instead of calling `stacks.from_param!(params[:stack_id])`, it calls `Stack.from_param!(params[:stack_id])` directly against the full `Stack` relation, ignoring `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the token *has* the `read:stack` permission string — it never checks that the requested stack matches the token's `stack_id`: [3](#0-2) [4](#0-3) 

So an `ApiClient` created with `stack_id` set to stack A (e.g. via `CCMenuUrlController#client`, which creates a `read:stack`-only token, or any stack-scoped client created through the `api_clients` admin UI) can be replayed against `/api/:stack_id/ccmenu.xml` for stack B, and `CCMenuController#stack` will happily resolve and render stack B's data — breaking the `token.stack_id == stack.id` equality that every other API controller (deploys, tasks, hooks, etc.) enforces through the inherited `stack`/`stacks` methods.

### Impact Explanation
This allows unauthorized cross-stack read access: a token meant to be scoped to a single stack (e.g. the `here_come_the_walrus` fixture pattern, or a CCMenu link token) can be used to read another stack's build/deploy state (`activity`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status) via the CCMenu XML endpoint, regardless of the `stack_id` binding on the `ApiClient` record. This matches the "unauthenticated read of stack state" class of impact for tokens that were never granted visibility into that stack.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` API token (which is routinely distributed for CI status widgets via `CCMenuUrlController`) can trivially trigger this by changing the `stack_id` path segment on the CCMenu endpoint — no additional privilege or secret is required beyond a token that is normally exposed for narrow, single-stack use.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to reuse the inherited, scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `token.stack_id == stack.id` binding is enforced consistently with the rest of the API surface.

### Proof of Concept
1. Create (or have created via `CCMenuUrlController#fetch`) an `ApiClient` scoped to `stack_id: A` with permission `read:stack`.
2. Call `GET /api/B/ccmenu.xml?token=<token for A>` where `B` is a different stack.
3. Observe the request succeeds (`200 OK`) and returns stack `B`'s build/activity data, even though the token's `stack_id` is `A`, because `CCMenuController#stack` resolves via `Stack.from_param!` rather than the scoped `stacks.from_param!` used elsewhere: [5](#0-4)
