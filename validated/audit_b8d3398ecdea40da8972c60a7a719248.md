### Title
Webhook signature verification only proves *an* organization signed the payload, not that it owns the data being written — allows cross-organization commit-status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) straight out of the **unverified** JSON body, then only asserts that the payload matches *that* organization's secret [1](#0-0) . It never verifies that the organization whose secret validated the signature is the same organization that owns the entity the handler subsequently mutates. `Webhooks::Handlers::StatusHandler#process` then updates `Commit` rows purely by matching `sha`, with no repository/organization scoping at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .

### Finding Description
Shipit is designed to support multiple GitHub organizations behind one instance, each with its own `github.<org>.webhook_secret` [3](#0-2) . Any org onboarded onto that shared instance legitimately knows its own webhook secret (it configured it when creating its GitHub App/webhook). The binding that should hold is:

`organization whose secret verified the signature == organization that owns the repository/commit being mutated`

But `verify_signature` derives the verifying organization from the attacker-controlled payload field `repository.owner.login`/`organization.login` [4](#0-3) , while `StatusHandler` (unlike other handlers that call `Handler#repository_name`/`Repository.from_github_repo_name` to scope by repo, e.g. `Handler#stacks` [5](#0-4) ) performs **no** repository check whatsoever — it looks up `Commit` globally by `sha` across every stack/organization tracked by the instance.

This is the same class of bug as the reported Uniswap issue: a value used for authorization/verification purposes (pool-wide liquidity / here, "organization X's signature is valid") is implicitly assumed to scope the entity being acted on (a single position / here, a specific org's commits), when in fact the acted-upon entity (the pool's aggregate state / here, `Commit.where(sha:)`) is not actually restricted to that scope.

Concretely: an attacker who legitimately administers **Org A** (onboarded to the same Shipit instance, e.g. self-service GitHub App install) knows Org A's `webhook_secret`. They send a `status` webhook to `/webhooks` with:
- `repository.owner.login: "OrgA"` (so `verify_signature` picks Org A's secret and the HMAC computed with Org A's secret validates),
- `sha`: the SHA of a real commit belonging to **Org B**'s stack (guessable/observable since commit SHAs and stack pages are often visible),
- `state: "success"`, arbitrary `context`.

`verify_signature` passes because the signature genuinely matches Org A's secret. `StatusHandler#process` then finds the `Commit` row for that `sha` regardless of which org it belongs to and calls `create_status_from_github!`, forging a CI status for Org B's commit.

### Impact Explanation
Forged commit statuses feed directly into deploy eligibility logic: `Commit#add_status` fires `deployable_status` hooks and calls `stack.schedule_merges` when the new status is `pending`/`success` [6](#0-5) , and enqueues `ProcessMergeRequestsJob` on success transitions. On stacks that gate continuous deployment/merge-queue progression on CI status, an attacker controlling any single onboarded organization can inject a fabricated "success" status for another organization's commit and trigger an unauthorized deploy/merge of that commit — matching the Critical "unauthorized deploy" impact bucket, without ever needing Org B's credentials, a Shipit session, or an `ApiClient` token.

### Likelihood Explanation
The prerequisite is only that the attacker administers one organization already onboarded to the shared Shipit instance (self-service GitHub App per org is a documented deployment pattern), which is a much lower bar than compromising the victim organization. Guessing/observing a target commit SHA on a public or known repository is straightforward.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already do so), resolve the target `Stack`/`Repository` from `payload['repository']['full_name']` (as `Handler#stacks` already does) and scope the `Commit` lookup to that repository's stacks, then cross-check that this repository's owner matches the organization whose secret verified the signature in `WebhooksController#verify_signature`, rejecting the payload if they diverge.

### Proof of Concept
1. Attacker administers `OrgA`, onboarded onto the shared Shipit instance with its own `webhook_secret_A`.
2. Attacker observes/guesses SHA `deadbeef...` of a commit tracked under `OrgB/some-repo`'s stack.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
```json
{ "sha": "deadbeef...", "state": "success", "context": "ci/fake",
  "repository": { "owner": { "login": "OrgA" } } }
```
signed with `sha1=HMAC(webhook_secret_A, body)`.
4. `verify_signature` computes `Shipit.github(organization: "OrgA")` and validates successfully against `webhook_secret_A` [7](#0-6) .
5. `StatusHandler#process` finds the `Commit` with `sha == "deadbeef..."` (belonging to `OrgB`) and records a forged "success" status on it [2](#0-1) , potentially unlocking merges/deploys for `OrgB`'s stack.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
