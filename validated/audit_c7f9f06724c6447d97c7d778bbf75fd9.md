### Title
Hash-lock authentifier accepts arbitrarily short/low-entropy secrets, enabling offline brute-force forgery of spending authorization - (File: definition.js)

### Summary
Analogous to the note-mark JWT issue (no minimum length/entropy enforced on a secret used to authenticate/authorize an action, whose public commitment can be brute-forced offline), ocore's `hash`-type authentifier only validates that the *committed* value is a well-formed 32-byte SHA256 digest, but never enforces any minimum length or entropy on the underlying secret preimage that satisfies it. Because the SHA256 commitment is published on-chain as part of an address/asset definition (visible to anyone), a low-entropy secret can be recovered offline and replayed to satisfy the authentifier and spend funds, exactly mirroring the "commit weak secret → brute-force → forge authentication" pattern in the report.

### Finding Description
`validateDefinition`'s `hash` case only checks the shape of the committed hash, not the strength of the secret that will later be revealed to satisfy it: [1](#0-0) 

At spend time, `validateAuthentifiers`'s `hash` case accepts any nonempty string whose SHA256 equals the committed hash — there is no minimum length, complexity, or entropy check on `assocAuthentifiers[path]` itself: [2](#0-1) 

The only length constraint applied anywhere in the authentifier pipeline is an *upper* bound (`MAX_AUTHENTIFIER_LENGTH`), never a lower one: [3](#0-2) 

On the wallet side, when a shared/multisig address path is defined as `secret` (hash-locked leaf), the client simply passes whatever string the user supplies as the raw preimage/authentifier with no strength validation: [4](#0-3) [5](#0-4) 

Because address definitions (and thus the `["hash", {hash: "..."}]` commitment) are disclosed publicly the first time the address is used — either in the unit itself (`author.definition`) or via `handleNewSharedAddress` broadcast to co-signers — the SHA256 digest of the secret becomes public data an attacker can attack offline, just like a leaked JWT reveals the signature that can be attacked to recover a weak `JWT_SECRET`.

### Impact Explanation
An address (or AA/asset spending condition) that uses a `hash` authentifier with a short/low-entropy secret (e.g., a PIN, short passphrase, or a weakly-generated token used for HTLC-style conditional payments between two parties) can have its preimage recovered by any third party who observes the public commitment on the DAG. The attacker can then submit a unit supplying the recovered preimage as the authentifier for that path and satisfy the spending condition — allowing unauthorized spending of the funds locked behind that condition (concrete fund theft), independent of any real signature key. This is a full "authentication bypass via secret recovery," structurally identical to the JWT forgery described in the report, but the impact class here is direct financial loss rather than session hijack.

### Likelihood Explanation
Reachable by any unprivileged address owner, AA author, or private-payment counterparty who chooses to construct a `hash`-locked spending condition (a documented, first-class oscript primitive) with an insufficiently random secret. Because ocore performs zero minimum-entropy or minimum-length validation on the secret/preimage anywhere in the definition-evaluation or authentifier-validation code paths, exploitation requires only patience for offline brute force after the commitment is published — no privileged access, no malicious peer/hub involvement, and no network-level attack is needed.

### Recommendation
- Enforce a minimum entropy/length requirement on the preimage accepted by `hash`-type authentifiers at spend time (`definition.js` `validateAuthentifiers`, case `'hash'`), e.g., reject preimages below a safe byte length (analogous to RFC 7518's 32-byte minimum for HMAC).
- Optionally add a corresponding warning/validation in `validateDefinition`'s `hash` case and in wallet UI/API (`wallet.js` `ifSecret`, `wallet_defined_by_addresses.js` shared-address handling) to actively discourage or reject low-entropy secrets when they are generated/entered by users, rather than only validating the hash's byte length.
- Document that `hash` conditions require cryptographically strong, randomly generated secrets, since the commitment becomes public once the address is used.

### Proof of Concept
1. Address owner defines an address (or AA/asset transfer condition) containing `["hash", {"hash": sha256("1234").toString('base64')}]` as one branch of an `and`/`or` spending condition.
2. The definition is published on first use (included in `author.definition` of a unit, or shared via `handleNewSharedAddress`), exposing the base64 SHA256 digest publicly (`definition.js:265`, `wallet_defined_by_addresses.js:389`).
3. An attacker brute-forces short candidate strings offline: `sha256(candidate) == committed_hash`, recovering `"1234"` in negligible time.
4. Attacker crafts a new unit spending from the address, supplying `assocAuthentifiers[path] = "1234"`; `validateAuthentifiers` (`definition.js:756-772`) computes `sha256("1234")`, matches the committed hash, and accepts it as valid — authorizing the spend without any legitimate signature.
