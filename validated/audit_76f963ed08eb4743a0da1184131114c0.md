### Title
Malformed PoX-4 reward-set entries are silently rewarded to the burn address instead of being rejected, permanently burning a stacker's earned reward slot - (File: stackslib/src/chainstate/nakamoto/signer_set.rs)

### Summary
`RawRewardSetEntry::from_pox_4_tuple` treats an unparseable `pox-addr` tuple pulled from the PoX-4 contract's `reward-cycle-pox-address-list` map as if the stacker had explicitly asked to burn their reward, rather than treating it as "no recipient" and excluding/re-routing the entry. This mirrors the Foundation Markets finding: a recipient-selection function silently substitutes `address(0)`-equivalent (the chain's burn address) for a party that is otherwise entitled to a payout, resulting in leaked/burned value.

### Finding Description
When the node reconstructs the PoX-4 reward set from chain state, each entry's PoX address is parsed with: [1](#0-0) 

```
let reward_address = PoxAddress::try_from_pox_tuple(is_mainnet, &pox_addr_tuple)
    .unwrap_or_else(|| {
        warn!("Invalid PoX address supplied, replacing with burn address"; ...);
        PoxAddress::standard_burn_address(is_mainnet)
    });
```

If `try_from_pox_tuple` cannot parse the stored `pox-addr` tuple (e.g., due to a malformed/edge-case version byte or hashbytes length combination that the Clarity-side validation in `pox-4.clar` does not reject for every code path, or a downstream data-corruption edge case), the code does not drop the entry or fail the reward-set computation. Instead it silently substitutes `PoxAddress::standard_burn_address(is_mainnet)` as the recipient for the *stacker's earned reward slot*, while the `total-ustx`/`amount_stacked` for that slot is retained unchanged in `RawRewardSetEntry`.

This is exactly the bug class in the external report: a function responsible for resolving a payout recipient (`royaltyInfo`/`getFeeRecipients` in the Foundation case, `get-reward-set-pox-address` → `from_pox_4_tuple` here) can resolve to "no valid recipient," and instead of falling back to "treat as if no recipient was specified" (i.e., exclude the entry from the paid reward set, or refuse to advance/finalize the cycle), the code forwards the burn address as a valid payout target. The reward amount itself (`total-ustx`) is *not* zeroed out or treated as "no reward" — only the address defaults to burn — so the STX/BTC value nominally due to that reward slot is sent to the burn output and permanently lost instead of being retried, re-routed, or excluded.

### Impact Explanation
This breaks the equality "value stacked and earning rewards == value the stacker/signer group actually receives." A reward-set entry that is legitimately due a Bitcoin-side (or Stacks-side) payout gets that payout diverted to a `PoxAddress::standard_burn_address`, i.e., the value is permanently burned rather than being credited to the actual stacker/signer. This is a permanent-freezing/loss-of-reward condition for whichever stacker's PoX address triggers the fallback, with no way to recover the burned funds — matching the High-impact category "temporary/permanent freezing of ... fees" / "reward slots ... exceeding locked value" framing in that a reward slot that should be paid to a real principal is instead unconditionally forfeited.

### Likelihood Explanation
Likelihood is Low-to-Medium and is the main uncertainty here: normally `pox-4.clar`'s own `stack-stx`/`stack-aggregation-commit` entry points validate the `pox-addr` tuple shape before it is written into `reward-cycle-pox-address-list`, so under ordinary conditions `try_from_pox_tuple` should not fail for entries the contract itself accepted. I was not able to fully verify (within the available index) whether there exists a Clarity-side code path that stores a `pox-addr` tuple whose `version`/`hashbytes` combination is accepted by the contract's tuple-shape typechecking but is rejected by `PoxAddress::try_from_pox_tuple` on the Rust side (e.g., an unrecognized version byte value that is valid `(buff 1)` at the Clarity type level but has no corresponding `PoxAddressType` match). If such a mismatch between the Clarity-level and Rust-level validation exists, this fallback is directly reachable by an ordinary stacker choosing an edge-case version byte, making it an unprivileged-account path that forfeits their own (or, if the entry mixes contributions, potentially another delegator's) locked reward.

### Recommendation
Do not substitute the burn address for an unparseable reward-set entry. Instead:
1. Treat a failed `PoxAddress::try_from_pox_tuple` as "no recipient" for that slot — exclude the entry from `rewarded_addresses`/`RawRewardSetEntry` collection entirely (as the external report recommends: let other priorities/paths take over) rather than defaulting the address while keeping the `amount_stacked`.
2. Alternatively, hard-fail reward-set computation for that cycle so the corrupt/invalid entry is surfaced and cannot silently result in burned rewards, since `pox_5_compute_and_update_signers`/`pox_5_stake_entries` and related callers already `Err`-propagate other malformed-input cases (e.g., `ChainstateError::Expects`).
3. Add cross-validation so that the Clarity-side PoX-address version/hashbytes constraints in `pox-4.clar`/`pox-5.clar` are provably a superset of what `PoxAddress::try_from_pox_tuple` accepts, closing any gap that could make this fallback reachable from an unprivileged stacking transaction.

### Proof of Concept
Concrete exploitation could not be fully confirmed with the tools available in this pass — I could not verify from the indexed contract source whether `pox-4.clar`'s Clarity-level tuple typechecking on `version`/`hashbytes` fully excludes every value that `PoxAddress::try_from_pox_tuple` (in `stackslib/src/chainstate/stacks/address.rs`) rejects. Conceptually, the PoC would be:
1. Call `stack-stx`/`stack-aggregation-commit` on `pox-4.clar` with a `pox-addr` tuple whose `version` byte is a value accepted by the contract's `(buff 1)` typecheck but not mapped to any `PoxAddressType` variant recognized by `try_from_pox_tuple`.
2. Let the reward cycle proceed; when the node computes the reward set via `RawRewardSetEntry::from_pox_4_tuple` [2](#0-1) , the parse fails and the entry's recipient becomes `PoxAddress::standard_burn_address(is_mainnet)`, while `total_ustx`/`amount_stacked` for that slot is preserved.
3. When the reward slot is paid out on the Bitcoin side, the BTC reward for that slot is sent to the burn output, permanently lost to the staker who locked STX for that slot.

Due to the uncertainty on step 1's reachability, this should be validated against the full `pox-4.clar` version-byte validation logic (not fully available in the indexed context) before treating it as a confirmed, exploitable finding rather than a defensive-coding gap.

```rust
impl RawRewardSetEntry {
    pub fn from_pox_4_tuple(is_mainnet: bool, tuple: TupleData) -> Result<Self, ChainstateError> {
        let mut tuple_data = tuple.data_map;

        let pox_addr_tuple = tuple_data.remove("pox-addr").ok_or_else(|| {
            ChainstateError::Expects(
                "no `pox-addr` in return value from (get-reward-set-pox-address)".into(),
            )
        })?;

        let reward_address = PoxAddress::try_from_pox_tuple(is_mainnet, &pox_addr_tuple)
            .unwrap_or_else(|| {
                warn!("Invalid PoX address supplied, replacing with burn address"; "pox_addr_tuple" => %pox_addr_tuple);
                PoxAddress::standard_burn_address(is_mainnet)
            });
```
