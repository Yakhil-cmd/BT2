### Title
Webhook signature verification is bound to `repository.owner.login`, not to the `repository.full_name` the handler actually writes to, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON payload. The event handlers that subsequently act on the payload (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target `Repository`/`Commit` using a *different* payload field, `repository.full_name`. Because these two fields are never cross-checked against each other, a valid HMAC computed with organization A's `webhook_secret` can be replayed with a payload whose `repository.full_name` points at organization B's repository, letting the request act on a repository never authenticated by the signature that validated it. This mirrors the VaultTracker.sol bug class: a value used for the “authorization” step (`exchangeRate`/here, `repository_owner`) diverges from the value later acted upon (`maturityRate`/here, `repository.full_name`), because the code never re-checks that they match.

### Finding Description
- `WebhooksController#verify_signature` picks the GitHub App config by organization and verifies the raw body's HMAC against the corresponding `webhook_secret`: [1](#0-0) 
- `repository_owner` is derived purely from the JSON body: [2](#0-1) 
- `Shipit.github(organization: repository_owner)` looks up a distinct GitHub App/secret per organization, as configured in multi-org deployments: [3](#0-2) 
- The actual signature check only depends on `webhook_secret` for that organization and the raw body bytes: [4](#0-3) 
- After the signature check passes, `WebhooksController#create` dispatches the *entire* parsed payload to handlers, without re-validating that any field used by those handlers is consistent with `repository_owner`: [5](#0-4) 
- Handlers resolve the target repository via a completely separate field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) 
- `PushHandler` uses that repository/stack resolution to trigger a GitHub sync job on the target stack: [7](#0-6) 
- `StatusHandler` writes commit statuses (used to gate deploys, e.g. CI checks) keyed only by `sha`, with no repository/organization check at all: [8](#0-7) 

Binding that should hold but is broken: `organization_that_signed_the_webhook == organization_owning_the_repository_that_is_acted_on`. Before a malicious request: only GitHub, holding org A's `webhook_secret`, can produce a valid `X-Hub-Signature` for a payload whose `repository.owner.login` is org A. After the flaw is exploited: anyone who knows (or controls delivery of) org A's `webhook_secret`/HMAC (e.g., a webhook configured for an org A repo they control, or a leaked/shared secret in a multi-tenant Shipit instance) can sign a payload where `repository.owner.login` = "orgA" (to pass `verify_signature`) but `repository.full_name` = "orgB/other-repo" (used by the handler), causing Shipit to act on org B's stack/commits using authorization derived only from org A.

### Impact Explanation
`StatusHandler#process` writes a `Commit::Status` record for any commit whose `sha` matches, with no ownership check tying the commit to the organization that authenticated the request: [8](#0-7) 
Because deploy safety gating in Shipit is driven by required/blocking commit statuses (`ci.require`/`ci.blocking` in `shipit.yml`, evaluated via `DeploySpec`), an attacker who can forge a `status` event for an arbitrary commit sha (once they hold *any* configured org's `webhook_secret`) can inject a passing CI status for a commit belonging to a stack they do not administer, potentially unblocking an unauthorized deploy. `PushHandler` similarly lets the forged request trigger `sync_github` on any stack whose repository matches the attacker-chosen `repository.full_name`, regardless of which organization's secret validated the request. This satisfies the "unauthorized deploy" / cross-repository-write impact bar, but requires the multi-organization webhook configuration (`config/secrets.*.yml` with multiple github orgs) to actually have more than one distinct `webhook_secret` in play — in a single-org deployment the org-keyed lookup collapses to the one secret and the practical blast radius is limited to acting outside the intended repository namespace with the same trust level the operator already granted that secret.

### Likelihood Explanation
Exploitation requires the attacker to already be in possession of, or able to trigger delivery signed with, one configured organization's `webhook_secret` — e.g., they administer a GitHub App/organization that a shared/multi-tenant Shipit instance also trusts, or the secret has been reused/leaked across orgs. This is a real deployment pattern documented in this codebase (`config/secrets.development.shopify.yml` shows the multi-org config shape), so the precondition is plausible for multi-tenant Shipit installs, but does not apply to the common single-org install. Likelihood is Medium: it depends on a specific but supported and documented configuration (multiple GitHub orgs sharing one Shipit instance), not a default hardening gap that is universally present.

### Recommendation
After `verify_signature` succeeds for organization O, re-derive and enforce that every payload field consumed downstream to select the target repository (`repository.full_name`, and by extension `repository.owner.login` used in `Handler#repository_name`) actually belongs to organization O, rejecting the request (422) otherwise. Concretely, in `app/controllers/shipit/webhooks_controller.rb`, compare `params.dig('repository', 'full_name')&.split('/')&.first` against `repository_owner` and abort if they differ; alternatively, thread the verified `repository_owner` into `Shipit::Webhooks::Handlers::Handler` and have `repository_name`/`stacks` refuse to resolve a `Repository` whose `owner` does not match the organization that produced a valid signature.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml`).
2. Attacker legitimately controls a GitHub App/webhook delivery for `orgA` (e.g., owns a test repo under `orgA` that is wired into the same Shipit instance), so they can compute a valid `X-Hub-Signature` using `orgA`'s `webhook_secret` for any body they choose.
3. Craft a `status` event JSON body where `repository.owner.login = "orgA"` (so `WebhooksController#repository_owner` resolves to `orgA` and `verify_webhook_signature` succeeds using `orgA`'s secret) but the `sha`/`state`/`context` fields target a commit sha that actually belongs to a stack under `orgB`.
4. POST to `/webhooks` with `X-Github-Event: status` and the crafted body/signature.
5. `verify_signature` passes (org A's secret matches), and `StatusHandler#process` writes a `Commit::Status` for the given `sha` with no check that the commit's repository belongs to `orgA`: [8](#0-7) 
This forges a CI status for a commit in a different organization's repository using credentials scoped to `orgA` only, demonstrating the broken binding between the authenticating organization and the repository actually written to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
