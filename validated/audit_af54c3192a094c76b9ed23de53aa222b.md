### Title
Operator-precedence bug in `provision?` lets PRs bypass `review_stacks_enabled`, and `ReviewStackProvisioningQueue` never re-checks it before provisioning - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/review_stack_provisioning_queue.rb])

### Summary
`OpenedHandler#provision?` mis-groups `&&`/`||` so that `repository.review_stacks_enabled` only gates the `allow_all` behavior, not `allow_with_label`/`prevent_with_label`. Once a stack is created this way, `Shipit::ReviewStackProvisioningQueue.add`/`#work` never re-checks `review_stacks_enabled` before invoking the stack's `ProvisioningHandler`, so the entire provisioning pipeline runs for a repository that opted out.

### Finding Description
The claimed binding is `repository.review_stacks_enabled == true` must hold at PR-open time for provisioning to occur, and it must still hold when the queue actually provisions the stack.

`provision?` is written as:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is only ANDed into the first disjunct. If `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, the method can return `true` even when `review_stacks_enabled == false`. In the `prevent_with_label` case with no label configured/present, this is true for essentially every opened PR - so an attacker who simply opens a PR against such a misconfigured (but review-stacks-disabled) repository triggers `ReviewStackAdapter#create!`, which calls `Shipit::ReviewStackProvisioningQueue.add(stack)` immediately: [2](#0-1) .

Downstream, `ReviewStackProvisioningQueue#work`/`#provision` only checks `stack.provisioner.provision?` (an optional, host-defined guard that defaults to `true` in `ProvisioningHandler::Base`) - it performs no check of `repository.review_stacks_enabled` at all: [3](#0-2) [4](#0-3) . So there is no second gate at provisioning time; whatever provisioning logic the host app registers (`up`, potentially shelling out via `Command`) executes for a repository whose administrator explicitly disabled review stacks.

Note: the file named in the question header, `app/jobs/shipit/continuous_delivery_job.rb`, is unrelated to this flow - it only gates `continuous_deployment?`/`occupied?`/schedule checks for existing stacks' CD and contains no review-stack provisioning logic: [5](#0-4) . The real, reachable bug lives in `opened_handler.rb` and `review_stack_provisioning_queue.rb` as traced above.

### Impact Explanation
A repository owner who has explicitly disabled review stacks (`review_stacks_enabled: false`) but left `provisioning_behavior` at `prevent_with_label` (or `allow_with_label` combined with a label an attacker can apply to their own PR) still gets a `Shipit::ReviewStack` record created, enqueued via `awaiting_provision: true`, and - once the queue worker runs - fully provisioned through whatever `ProvisioningHandler` the host app registered for that repository, with no re-verification of the disabled flag. This is a record/resource created and a provisioning workflow (potentially including shell commands via a custom handler's `up`) executed for a repository that opted out, repeatable on every PR against any repository with this configuration.

### Likelihood Explanation
Requires no special privileges: opening a PR is available to any GitHub user able to open PRs against/into the target repo (or via a webhook payload asserting to be from that repo, subject to normal webhook handling). It requires the target repository to be configured with `review_stacks_enabled: false` and `provisioning_behavior` of `allow_with_label` or `prevent_with_label` - a configuration combination the settings UI explicitly allows (the "review_stacks_enabled" checkbox and "provisioning_behavior" select are independent fields) [6](#0-5) . No secrets, tokens, or elevated roles are needed.

### Recommendation
Parenthesize `provision?` so `review_stacks_enabled` is ANDed across the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to the equivalent expressions in `labeled_handler.rb`/`reopened_handler.rb`/`unlabeled_handler.rb`. Additionally, add a defensive re-check of `stack.repository.review_stacks_enabled` inside `ReviewStackProvisioningQueue#provision` before invoking the handler, so a stack created under a since-fixed/changed config is never provisioned.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not enqueue provisioning when review_stacks_enabled is false but behavior is prevent_with_label" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: :prevent_with_label, provisioning_label_name: "provision")
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no provisioning label -> !has_label? == true

  assert_equal false, repository.review_stacks_enabled
  Shipit::ReviewStackProvisioningQueue.expects(:add).never
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Expected (buggy) result: the test fails because `ReviewStackProvisioningQueue.add` IS called and a stack IS created, demonstrating `provision?` returns `true` despite `review_stacks_enabled == false`.
