## Analysis Summary

The reported Chakra bug class is: an action-authorization check that should be scoped to a specific, unprocessed identifier is missing/bypassed, letting an unprivileged caller act outside the boundary the system intends (`txId` status not checked → replay across the "only this tx" boundary). The closest reachable analog in this engine's own code is the rule-listed binding: **"a stack a token authorizes vs. a stack it touches."**

`Shipit::Api::BaseController` correctly scopes stack access to the `ApiClient`'s bound stack: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true, and `stack` (used by every other API controller) resolves through that scoped relation. [1](#0-0) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass that scoping entirely, resolving directly against the full `Stack` table by the `stack_id` param, and only checks the caller has the generic `read:stack` permission (not that the token is bound to *this* stack): [2](#0-1) 

Stack-scoped tokens are a documented, first-class concept: `CCMenuUrlController` mints exactly this kind of token — an `ApiClient` limited to `read:stack` — and hands the resulting authenticated CCMenu URL (with `token` embedded in the query string) to any logged-in user for a single stack, intending that URL/token to only ever reveal that one stack's deploy status: [3](#0-2) 

Because `Api::CCMenuController#stack` never consults `current_api_client.stack_id`, any holder of a stack-scoped CCMenu token (or any other `read:stack`-scoped `ApiClient` token) can substitute an arbitrary `stack_id` in the URL and read another stack's deploy/task status — data the token issuer never intended to expose to that holder. This breaks the equality `token.authorized_stack_id == stack.id` that `BaseController#stacks` otherwise enforces everywhere else in the API.

### Title
Stack-scoped CCMenu API tokens bypass stack authorization scoping, allowing unauthorized read of any stack's deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the `stack` resolver used by all other API controllers, replacing the token-scoped lookup (`Stack.where(id: current_api_client.stack_id)`) with an unscoped `Stack.from_param!(params[:stack_id])`. This defeats the per-stack authorization binding that `ApiClient#stack_id` is designed to enforce.

### Finding Description
`ApiClient` records can optionally be bound to a single `stack` (`belongs_to :stack, optional: true`), and `BaseController#stacks`/`#stack` enforce that binding for every controller that inherits the default resolver: [1](#0-0) 
`CCMenuUrlController` explicitly creates such a scoped token (`permissions: %w[read:stack]`, implicitly bound via the generated URL to one `stack_id`) so that a CCMenu client (e.g., a CI dashboard) fetching `api_stack_ccmenu_url` only ever has access to that one stack: [4](#0-3) 
`Api::CCMenuController` however defines its own `stack` method that ignores `current_api_client.stack_id` and fetches any stack by the `stack_id` request parameter: [5](#0-4) 
`require_permission :read, :stack` only checks that `'read:stack'` is in `ApiClient#permissions` (a flat permission string, not tied to which stack), via `ApiClient#check_permissions!`: [6](#0-5) 
Combined, a `read:stack`-scoped token issued/intended for stack A is accepted by `Api::CCMenuController#show` for any stack B simply by changing the `stack_id` URL segment — the binding `token.stack_id == requested_stack.id` is never verified. `Stack.from_param!` raises on unknown params but performs no ownership check either.

### Impact Explanation
This yields **unauthenticated (from the target stack's perspective) read of stack state** — deploy status, last deploy id, timestamp, and running state — for any stack in the Shipit instance, using only a token that was authorized for a single, unrelated stack. This matches the "High" impact bucket defined by the rules ("unauthenticated read of stack state, task streams or deploy output"), since the holder of a narrowly-scoped token gains read access across the entire stack namespace, escalating beyond what the token issuer authorized.

### Likelihood Explanation
Likelihood is high for any deployment that uses the CCMenu integration (a documented, built-in feature — settings page exposes "CCMenu URL"). Any party who legitimately possesses one stack's CCMenu URL/token (e.g., a CI dashboard widget, a shared monitoring page, or a user who once had access to a stack that was later locked down) can enumerate `stack_id` values and read every other stack's build/deploy status without further authentication, permission grants, or the app owner's knowledge.

### Recommendation
In `Api::CCMenuController`, remove the custom `stack` override and instead reuse the scoped resolver from `BaseController` (i.e., resolve via `stacks.from_param!(params[:stack_id])`, consistent with `Api::CommitsController`, `Api::StacksController`, etc.), so that a stack-bound `ApiClient` can only ever resolve the stack it was issued for.

### Proof of Concept
1. As a legitimate stack owner, visit "Settings" for `stack-a` and copy the generated CCMenu URL, e.g. `GET /api/stacks/:stack-a-id/ccmenu.xml?token=<token-scoped-to-stack-a>` (minted by `CCMenuUrlController#fetch`) — this issues an `ApiClient` with `stack_id = stack-a.id` and `permissions = ['read:stack']`. [7](#0-6) 
2. Replace the `stack_id` in the URL with any other stack's id (`stack-b`), keeping the same `token`: `GET /api/stacks/:stack-b-id/ccmenu.xml?token=<token-scoped-to-stack-a>`.
3. `Api::BaseController#authenticate_api_client` authenticates the token to the original `ApiClient` bound to `stack-a`; `require_permission :read, :stack` passes because the token has `read:stack` in its flat `permissions` list. [8](#0-7) 
4. `Api::CCMenuController#show` calls `stack`, which resolves `stack-b` directly via `Stack.from_param!(params[:stack_id])` — bypassing the `current_api_client.stack_id` check entirely — and renders `stack-b`'s deploy/build status in the XML response, disclosing information the token was never authorized to see. [9](#0-8)

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
```

```ruby
require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
```
