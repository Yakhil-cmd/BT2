### Title
ANSI/OSC/control-sequence passthrough via `formatRawComment` allows terminal escape injection - (File: pkg/cmd/pr/shared/comments.go)

### Summary
`formatRawComment` writes `comment.Content()` (a PR/issue comment or review body originating from the GitHub API) directly into the output buffer with `fmt.Fprintln`, with no stripping of ANSI/OSC/C0/C1 control sequences. This output is surfaced via `gh pr view --comments --raw` / `gh issue view --comments --raw` through `RawCommentList`, meaning any GitHub user who can leave a comment or review on a PR/issue can inject terminal escape sequences that execute when the victim views them.

### Finding Description
`RawCommentList` iterates over sorted comments/reviews and calls `formatRawComment(comment)` for each, appending the result to a `strings.Builder` that is ultimately printed to the terminal (consumed by `pkg/cmd/pr/view/view.go` and `pkg/cmd/issue/view/view.go`). [1](#0-0) 

Inside `formatRawComment`, the comment body is written verbatim: [2](#0-1) 

`comment.Content()` is backed by the `Body`/comment text fields returned from the GitHub GraphQL/REST API (`api/queries_comments.go`, `api/queries_pr_review.go`), which is fully attacker-controlled — any unprivileged GitHub user can author a PR comment, issue comment, or review body containing raw bytes, including ANSI CSI sequences, OSC sequences (e.g. `ESC ] 52 ; c ; <base64> BEL` for clipboard write, or `OSC 8` for hyperlink spoofing), and C1 control bytes.

A repo-wide search found no sanitization utility (`StripANSI`, `RemoveHyperlinks`, control-character filtering) applied to comment content before it reaches the raw output path; the only ANSI-stripping reference in the codebase is unrelated (`pkg/cmd/skills/list/list.go`). The rich/colorized path (`formatComment`) does route content through `markdown.Render`, which may perform some sanitization/escaping as part of markdown rendering, but the `--raw` path (`formatRawComment`) bypasses markdown rendering entirely and writes the content unmodified.

### Impact Explanation
This enables terminal escape sequence injection when a victim runs `gh pr view <PR> --comments --raw` (or the issue equivalent) on an attacker-authored/commented PR or issue. Depending on the victim's terminal emulator, this can achieve: OSC 52 clipboard exfiltration/poisoning, OSC 7/8 spoofing of prompt/hyperlink text, cursor manipulation to hide or rewrite prior terminal content (prompt spoofing), or in vulnerable terminal emulators, more severe effects. This maps to "Terminal output/prompt spoofing leading to credential capture or unintended destructive confirmation" (High) per the stated impact class, since a spoofed prompt or hidden output could trick a victim into approving a destructive action or pasting a credential.

### Likelihood Explanation
Fully attacker-reachable with no privileges: any GitHub user can open a PR/issue or leave a comment/review on a public repo the victim inspects with `gh`. The only precondition is that the victim runs the `--raw` view path (a normal, documented usage pattern for scripting/parsing) against attacker content. This is reliably repeatable — the escape bytes pass straight through `fmt.Fprintln` with no filtering.

### Recommendation
Sanitize `comment.Content()` (and other raw-printed fields such as author login, association, hidden reason) before writing to the raw output buffer in `formatRawComment` — strip/escape ANSI CSI/OSC/DCS sequences and C0/C1 control bytes (excluding benign `\n`/`\t`) prior to `fmt.Fprintln(&b, comment.Content())`. Apply the same sanitization to any other command paths that print raw remote-supplied text to the terminal (check output, release notes, etc.).

### Proof of Concept
Go unit test (add to `pkg/cmd/pr/shared/comments_test.go`):
```go
func TestFormatRawComment_StripsEscapeSequences(t *testing.T) {
	malicious := "hello\x1b]52;c;ZXZpbCBjbGlwYm9hcmQ=\x07world\x1b[2J"
	c := &fakeComment{content: malicious, author: "attacker"}
	out := formatRawComment(c)
	if strings.Contains(out, "\x1b") {
		t.Fatalf("expected no raw escape bytes in output, got: %q", out)
	}
}
```
Expected (current) result: test fails because `\x1b]52;...` and `\x1b[2J` bytes are present unmodified in `out`, confirming the escape sequence passthrough. After remediation, the assertion should pass.
