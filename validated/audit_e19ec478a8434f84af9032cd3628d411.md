### Title
Webhook signature verification keys on `repository.owner.login` while every event handler routes on the independent `repository.full_name` field, allowing a valid signature from one GitHub organization to authorize actions against a Stack in a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit.github(organization:)` supports a multi-tenant configuration where each GitHub organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to validate the HMAC against using `repository_owner`, itself read straight out of the unauthenticated JSON body via `params.dig('repository', 'owner', 'login')` [2](#0-1) . Every downstream handler, however, resolves the target `Repository`/`Stack` from a *different* field in that same body: `repository.full_name`, via `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . Because the signature check and the target-resolution logic each trust a different, independently attacker-supplied JSON key, they can be made to disagree.

### Finding Description
`verify_signature` derives the organization to authenticate against from the payload itself, before the signature has been validated: [5](#0-4) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This selects a `GitHubApp` instance (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)` [6](#0-5) , and only after computing the HMAC over the raw body is the request accepted or rejected.

Once accepted, `create` dispatches to handlers such as `PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers. None of them re-check `repository.owner.login`; they all resolve the acted-upon repository from `repository.full_name`: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/targeting) are two independent, attacker-controlled keys in the same JSON body - nothing enforces that `full_name` starts with `owner.login`, or vice versa. This breaks the intended binding: `organization authenticated == organization of repository written`.

An attacker who legitimately controls (or has push access to) one GitHub organization/repository already configured in Shipit knows or can trigger a validly-signed webhook body for that organization (its `X-Hub-Signature` is computed from `Shipit.github(organization: "own-org").webhook_secret`). By crafting the JSON body so `repository.owner.login` (and/or `organization.login`) is `"own-org"` (so signature verification picks and passes with the attacker's own known/derivable secret) while `repository.full_name` is set to `"victim-org/victim-repo"`, the request passes `verify_signature` yet is processed as if it targeted the victim's stack.

### Impact Explanation
This lets an attacker forge events against a Stack belonging to an organization/repository they do not control, once they possess a validly-signed envelope for their own organization. Concretely:
- `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for the victim stack's branch [7](#0-6) , letting the attacker force a re-sync toward an attacker-chosen SHA.
- `CheckSuiteHandler` schedules a refresh of check runs for an arbitrary victim commit [8](#0-7) , and the `status`/`check_suite` webhook types (which drive `StatusChecker` and thus `merge!`/CI-required-checks gating used by `MergeRequest#reject_unless_mergeable!`) can be manipulated to make Shipit believe CI passed on a commit it did not actually pass on [9](#0-8) .
- Combined with the merge queue / continuous-deployment flow, forging CI statuses for a victim repository can lead to an unauthorized merge or deploy, matching the Critical-impact category of "unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitability depends on multi-tenant configuration (multiple organizations each with their own `webhook_secret` under `secrets.github`) — this is an explicitly supported configuration in `lib/shipit.rb` (`github_app_config`, `github_organizations`) [10](#0-9) . Any party who has legitimate webhook delivery rights for one connected organization (e.g., a maintainer of a smaller/less-trusted org onboarded to the same Shipit instance) can attempt to cross into another organization's stacks purely by mismatching `repository.owner.login` vs `repository.full_name` in the JSON body, without needing that victim organization's `webhook_secret`, GitHub App private key, or any Shipit session/API token.

### Recommendation
Bind signature verification and repository resolution to the same authenticated value:
- After successfully verifying the signature for `repository_owner`, additionally assert that `params.dig('repository', 'full_name')` (or `organization.login`, if that field is what handlers use) belongs to that same organization before dispatching to handlers, e.g. reject with 422 if `repository_owner` does not case-insensitively match the owner segment of `repository.full_name`.
- Alternatively, look up the organization based on the resolved `Repository` record (via `full_name`) rather than the raw, pre-verification `repository.owner.login`, so a single authoritative field drives both authentication and authorization.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing two organizations, `attacker-org` (attacker has legitimate push/webhook access) and `victim-org` (has a Stack, e.g. tracking `victim-org/app` on branch `master`), each with distinct `webhook_secret`s.
2. Attacker crafts (or captures from their own repo's real push event and edits) a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
     "owner": { "login": "attacker-org" },
     "full_name": "victim-org/app"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully [6](#0-5) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/app")` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack [7](#0-6) , despite the attacker never having demonstrated any control over, or knowledge of the secret for, `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    end
