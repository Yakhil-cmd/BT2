### Title
CCMenu API token bypasses stack scoping, allowing a stack-scoped `ApiClient` to read any stack's build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The analog of the ParaSpace bug — a value used to make an authorization decision diverging from the value actually acted upon — occurs in `Shipit::Api::CCMenuController`. An `ApiClient` token can be scoped to a single stack via `stack_id`, and the base API scoping mechanism (`stacks`) is designed to enforce `token authorises stack == stack acted upon`. `CCMenuController` however overrides `stack` to bypass that scoping entirely, so the stack a token is authorized for and the stack it actually touches can differ.

### Finding Description
`ApiClient` records can be restricted to a single stack via the `stack_id` column: [1](#0-0) 

The generic API scoping logic in `BaseController` is meant to enforce this binding for every endpoint:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`require_permission` only checks that the permission string (`read:stack`) is present on the client, it does not check which stack the token is scoped to: [3](#0-2) 

`CCMenuController` overrides `authenticate_api_client` to also accept a raw query-string `token`, and — critically — overrides `stack` to look the stack up directly by `Stack.from_param!(params[:stack_id])` instead of calling the inherited, scope-aware `stacks.from_param!`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [4](#0-3) 

Because `require_permission :read, :stack` (declared at the top of the controller) only calls `check_permissions!(:read, :stack)`, and `stack` no longer goes through `current_api_client.stack_id`, any valid `read:stack` token — even one explicitly created with `stack_id` set to a single stack, such as the `here_come_the_walrus` fixture — will successfully authenticate and be able to fetch the CCMenu XML status for **any** stack, simply by changing `params[:stack_id]` in the request. [5](#0-4) 

This is compounded by `CCMenuUrlController`, which mints a `read:stack` `ApiClient` for embeddable CCMenu badge URLs without setting `stack:` on the created client at all, meaning that token is unscoped from creation: [6](#0-5) 

The binding that should hold is: `stack authorised by token == stack touched by request`. Before the divergence: a stack-scoped or CCMenu-minted token can only read the state of its associated stack (as enforced elsewhere, e.g. `StacksController#index`, tested at `test/controllers/api/stacks_controller_test.rb:217-223`). After the divergence (`CCMenuController#stack`), the same token can read the state of every stack in the Shipit instance, because the stack lookup ignores `current_api_client.stack_id`.

### Impact Explanation
This meets the High-severity bar of "unauthenticated read of stack state" per the impact taxonomy: a token meant to grant unauthenticated, embeddable read access to one project's CI dashboard status instead grants unauthenticated read access to the status (locked/unlocked, last build status/label, deploy activity) of every stack managed by the Shipit instance, including private/production stacks the token holder was never meant to see.

### Likelihood Explanation
CCMenu URLs are explicitly designed to be embedded in third-party CI dashboard tools and are not treated as highly sensitive by users (they are handed out for public status widgets). Any holder of one such URL — which requires no privileged access, session, or GitHub team membership, only possession of a leaked/shared CCMenu link — can trivially swap the `stack_id` query parameter to enumerate and read the status of other stacks. `ApiClient` IDs are sequential integers signed by `SimpleMessageVerifier`, but the token itself, once obtained for any one stack, is a valid `Authorization`/`token` credential for all stacks regardless of the id substituted in the URL path.

### Recommendation
Make `CCMenuController#stack` go through the same client-scoped lookup used elsewhere (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, and ensure `CCMenuUrlController#client` sets `stack:` on the created `ApiClient` so each CCMenu token is durably scoped to the single stack it was generated for.

### Proof of Concept
1. As an authenticated Shipit user, visit `/stacks/org/repo-a/env/ccmenu_url` to obtain a CCMenu URL of the form `.../api/stacks/org/repo-a/env/ccmenu.xml?token=<TOKEN>`. This creates (or reuses) a `read:stack` scoped `ApiClient` (per `CCMenuUrlController#client`, no `stack:` set) — or use any existing stack-scoped `ApiClient` token (e.g. `here_come_the_walrus`, scoped to stack `shipit`).
2. Send `GET /api/stacks/other-org/other-repo/other-env/ccmenu.xml?token=<TOKEN>` — substituting a different stack's identifiers in the path while reusing the same token.
3. Observe that `CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` (bypassing `current_api_client.stack_id` scoping) and returns HTTP 200 with the other stack's build status, despite the token never having been authorized for that stack.
