### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub "status" event to using a bare, repository-unscoped query (`Commit.where(sha: params.sha)`), while the webhook's authenticity is verified based on the *organization/repository that signed the payload* (`WebhooksController#verify_signature`, keyed off `params.dig('repository','owner','login')`). This breaks the equality that should hold: `repository authenticated by the webhook signature == repository whose commit state is mutated`. An attacker who legitimately controls (and can generate signed webhook events for) one onboarded repository can forge a "success" status for a commit SHA belonging to a completely different, unrelated stack/repository on the same Shipit instance, because commit SHAs are looked up globally rather than scoped to the repository named in the payload.

### Finding Description
Webhook signature verification is performed once per request, based on the organization derived from the (unauthenticated at that point) payload: [1](#0-0) [2](#0-1) 

This only proves that the request was signed by *some* organization's registered GitHub App secret for the `repository.owner.login`/`organization.login` named in the JSON body — it does not constrain which `Commit` records the handler is allowed to touch.

Most handlers correctly scope their side effects to the repository named in the payload via `Handler#stacks`, which resolves `Stack`s through `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 

`PushHandler` uses this scoped `stacks` helper: [4](#0-3) 

However, `StatusHandler` does **not** use `stacks`/`repository_name` at all. It queries `Commit` directly by SHA, globally, across every repository/stack in the installation: [5](#0-4) 

So the binding that should hold — `repository that signed/authenticated the event == repository whose commit is updated` — is never enforced for status events. The webhook's `repository` field is used only to select the verification key, not to constrain which commit rows get a new `Status` record.

### Impact Explanation
Commit status is a security-relevant signal consumed at deploy time: `Shipit::Api::DeploysController#create` uses `commit.deployable?` (backed by commit statuses) to gate deploys when CI is required: [6](#0-5) 

Because `StatusHandler` matches on raw SHA across the whole instance, an attacker who has legitimate push/webhook-triggering rights on **their own** onboarded repository (an unprivileged party with respect to any other team's stack) can send an authentically-signed GitHub `status` event for their own repo but set `sha` to a commit hash belonging to another team's stack, with `state: success`. This satisfies `commit.deployable?` for a commit the attacker never actually built/tested, allowing that commit to bypass required-CI gating and be deployed — an unauthorized deploy of arbitrary/malicious code onto infrastructure the attacker does not otherwise control. This matches the report's Critical impact bar ("unauthorized deploy").

### Likelihood Explanation
Commit SHAs are 40-hex identifiers that are typically public/discoverable (via GitHub commit history, PRs, CI logs, or the Shipit UI itself, which displays commit SHAs for all stacks the attacker can view). Generating a validly-signed webhook only requires the attacker to control any single repository/org already registered with the Shipit instance (a routine, low-privilege position in a shared internal deploy tool) — no access to the victim's repository, GitHub App secret, or Shipit session is needed. The only additional step is guessing/knowing a target SHA, which is realistic in shared-tooling environments.

### Recommendation
Scope `StatusHandler#process` (and any other handler that mutates records by attacker-suppliable identifiers) to the repository named in the signed payload, mirroring the `Handler#stacks`/`repository_name` pattern already used by `PushHandler`, e.g. constrain the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or join through `Stack -> Repository.from_github_repo_name(repository_name)` before applying the status update, so a webhook can only affect commits that belong to the repository it was actually signed for.

### Proof of Concept
1. Attacker owns/administers `attacker-org/attacker-repo`, which is legitimately onboarded as a Shipit stack (their own GitHub App webhook secret is valid).
2. Attacker looks up (via public commit history, PR, or Shipit UI) the SHA of an un-deployed/un-CI'd commit belonging to `victim-org/victim-repo`, a different stack on the same Shipit instance.
3. Attacker triggers (or crafts, since they hold the signing secret for their own org) a `status` webhook event:
   ```json
   {
     "repository": {"full_name": "attacker-org/attacker-repo", "owner": {"login": "attacker-org"}},
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
   signed with `attacker-org`'s valid `webhook_secret`.
4. `WebhooksController#verify_signature` succeeds (correct secret for `attacker-org`).
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches the victim commit regardless of repository, and calls `commit.create_status_from_github!(params)`, recording a fabricated "success" status on it.
6. `commit.deployable?` now reflects the forged status; a subsequent `POST /api/:stack/deploys` with `require_ci: true` for `victim-org/victim-repo` no longer raises the "Commit is not deployable" error, per [7](#0-6) , permitting deployment of a commit that never actually passed CI in the victim's repository.
