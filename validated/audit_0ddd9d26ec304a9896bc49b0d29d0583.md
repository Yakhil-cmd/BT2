### Title
Webhook Signature Verified Against Attacker-Chosen Organization While Handlers Act On a Different Repository Field — Cross-Organization Webhook Forgery Leading to Unauthorized Merges - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, a value read directly from the **unverified** JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [6](#0-5) . It then verifies `X-Hub-Signature` against `Shipit.github(organization: repository_owner).verify_webhook_signature` [7](#0-6) .

Once the signature check passes, `create` dispatches the **entire raw payload** to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) . Every handler determines which `Stack`/`Repository` to act on using a **different** field of the same payload — `payload.dig('repository', 'full_name')` [9](#0-8)  — which is never bound to, or cross-checked against, `repository.owner.login` used for signature verification.

This is the same class of bug as the reported `assert_healthy_or_healthier` issue: a value that gates a "healthy/valid" decision (`total_risk`/here: signature validity) is evaluated on one field, while the actual state that is acted upon (position exposure/here: the repository actually written to) is governed by a different, unchecked field. In Shipit's multi-tenant configuration — explicitly documented and shipped as `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md` "Using Multiple Github Applications" — each organization has its own independent `webhook_secret`, obtained via `github_app_config(organization)` [2](#0-1) . An attacker who is a legitimate member/owner of "Org-A" (and therefore legitimately possesses or can obtain Org-A's `webhook_secret`, since it's provisioned for their own org's GitHub App installation) can POST a forged webhook directly to `/webhooks` with:
- `repository.owner.login` = `"Org-A"` (so signature check authenticates against Org-A's own secret, which the attacker knows/can compute since it's their own org's secret)
- `repository.full_name` = `"Org-B/victim-repo"` (an entirely unrelated organization/repo hosted on the same Shipit instance)

The signature check passes (correctly signed with Org-A's secret), but handlers process the payload as if it came from Org-B, because `repository_name` in `Handler` reads `full_name`, not `owner.login`. The binding "organization that authenticated == repository that is written" is broken.

### Impact Explanation
Concretely reachable impact: forging a `status` event for a victim's PR head commit sets `Commit#create_status_from_github!`-equivalent state via the `status` handler, which calls `add_status`, triggering `stack.schedule_merges` when the new status is `pending` or `success` [3](#0-2) . This enqueues `ProcessMergeRequestsJob`, which — once `all_status_checks_passed?` is satisfied by the forged status — calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request(...)` using Shipit's **own GitHub App credentials for the victim org** [5](#0-4) [4](#0-3) . This results in an unauthorized merge on a repository the attacker does not control, satisfying the Critical criterion "unauthorized deploy, rollback or merge." It also allows forging `push` (queuing `GithubSyncJob`), `pull_request` (archiving/unarchiving review stacks), and `membership`/`commit_status` events against any other tenant's repository/stack state on the same Shipit instance.

### Likelihood Explanation
Requires only that the target Shipit instance is configured with the multi-organization schema (explicitly documented and supported as first-class functionality) and that the attacker is a legitimate member of at least one of the configured organizations, giving them a valid `webhook_secret` for signing. No GitHub App private key, `api_clients_secret`, or Shipit session/API token is needed — only direct HTTP access to the public `/webhooks` endpoint, which is unauthenticated by design (webhook delivery endpoint). This is a realistic scenario for any Shipit deployment servicing more than one organization.

### Recommendation
Verify the webhook signature using each configured organization's secret independently (or compute the signature over the payload for every configured org and confirm exactly one match), then use *that same matched* organization to derive `repository_owner`, and reject the payload if `repository.owner.login`/`organization.login` does not match the organization whose secret produced the valid signature. Alternatively, bind the two fields explicitly: after `verify_signature` succeeds for organization `O`, assert `params.dig('repository','owner','login') == O` (or `params.dig('organization','login') == O`) before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As a member of `OrgA` with knowledge of `OrgA`'s `webhook_secret` (their own org's Shipit-configured secret), craft a `status` (or `push`) webhook payload:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sha": "<victim PR head sha>",
  "state": "success",
  "context": "ci/required",
  "branches": [{ "name": "victim-branch" }]
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, payload)>` and `X-Github-Event: status`.
4. POST to `/webhooks`. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which succeeds [10](#0-9) .
5. The handler resolves the target stack via `payload.dig('repository','full_name')` = `"OrgB/victim-repo"` [11](#0-10) , applying the forged status to `OrgB`'s commit/stack despite the signature only proving knowledge of `OrgA`'s secret.
6. If a merge queue is pending on that PR, this forged status can complete `all_status_checks_passed?` and cause `ProcessMergeRequestsJob` to merge the PR in `OrgB/victim-repo` using Shipit's GitHub credentials.
