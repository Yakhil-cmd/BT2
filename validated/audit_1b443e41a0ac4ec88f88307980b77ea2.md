### Title
API Client `stack_id` Scope Bypass in CCMenu Endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a single stack (via `ApiClient#stack_id`) may only ever operate on that stack, by routing all stack lookups through the `stacks`/`stack` helper methods. `Shipit::Api::CCMenuController` overrides `stack` to bypass this scoping entirely, breaking the binding between "the stack an API token is authorized for" and "the stack the endpoint actually reads."

### Finding Description
`BaseController` defines the authorization-scoping primitive used by every other API controller: [1](#0-0) 

`current_api_client.stack_id?` restricts the visible stack set to the one stack the client was issued for (as exercised by the `StacksController` test "an api client scoped to a stack will only see that one stack"): [2](#0-1) 

`CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, never going through `stacks`, and additionally overrides `authenticate_api_client` to accept a bare query-string `token`: [3](#0-2) 

`require_permission :read, :stack` only checks that the client's `permissions` array contains `read:stack` — it never checks which stack the permission applies to: [4](#0-3) 

As a result, any `ApiClient` holding `read:stack` — including one that was deliberately scoped to a single stack via `stack_id` — can pass an arbitrary `stack_id` param and read the CCMenu status of any other stack in the installation. The existing test suite even demonstrates this without noticing it as a bug: a client authenticated with `authenticate!` (which is stack-scoped, see `here_come_the_walrus` fixture) is used to fetch an entirely unrelated, newly created stack (`foo/bar`) that it was never granted access to, and the request still succeeds: [5](#0-4) 

### Impact Explanation
This breaks the equality that should hold: `stack authorized by token == stack acted upon by endpoint`. An attacker who obtains any low-privilege `ApiClient` credential (even one deliberately restricted to a single stack, as configured via `Stack#api_clients` / `ApiClient#stack_id`) can enumerate `stack_id` params to read deploy state (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status) for every stack managed by the Shipit instance, not just the one it was authorized for. This matches the "unauthenticated/unauthorized read of stack state" High-impact category, since it lets a credential scoped to one repository/stack read the deploy state of unrelated repositories/stacks it was never granted access to — a cross-tenant information disclosure via the deployment platform.

### Likelihood Explanation
The bug requires only possession of any valid `ApiClient` token with the `read:stack` permission (a very common, low-privilege grant used for the CI status badge / CCMenu integration) and knowledge or brute force of another stack's `to_param` (owner/name/environment), which is often guessable or publicly known (e.g., visible in the same organization's other CCMenu URLs, GitHub repo names, or Shipit stack listings). No special network position or elevated credential is required beyond a token that is otherwise supposed to be narrowly scoped.

### Recommendation
Change `CCMenuController#stack` to use the inherited, scope-respecting `stacks` collection instead of calling `Stack.from_param!` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures the `stack_id` scoping enforced by `BaseController#stacks` (and thus the binding between the token's authorized stack and the stack actually rendered) cannot be bypassed by this controller's custom authentication path.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to Stack A (as done for fixture `here_come_the_walrus`, `stack: shipit`). [6](#0-5) 
2. Authenticate as this client (query-string token or basic auth) and issue:
   `GET /api/stacks/<Stack-B-owner>/<Stack-B-name>/<Stack-B-env>/cc.xml?token=<client_token>`
   where Stack B is a stack the client was never scoped to.
3. Observe that `CCMenuController#stack` resolves Stack B via `Stack.from_param!`, bypassing the `stacks` scope check, and returns Stack B's `lastBuildStatus`, `lastBuildLabel`, `activity`, and lock state — as already reproduced (unintentionally) by the existing test "stacks with no deploys render correctly," which fetches a brand-new, unrelated stack with a stack-authenticated client and receives a `200 OK` with full status payload. [5](#0-4)
