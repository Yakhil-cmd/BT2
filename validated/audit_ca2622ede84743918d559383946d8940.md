### Title
API-scoped ApiClient tokens can read CCMenu build status for any stack, not just the stack they are authorised for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method used elsewhere in the API to enforce per-token stack scoping, replacing it with an unscoped lookup. This breaks the binding between "the stack a token authorises" and "the stack the request actually touches."

### Finding Description
`Shipit::Api::BaseController` defines the standard, scoped way stacks are resolved for authenticated API requests: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a specific stack (`current_api_client.stack_id?`), and only falls back to `Stack.all` for unscoped ("global") clients. Every other API controller inherits this and therefore can only ever resolve a stack the token is authorised for.

`CCMenuController`, however, defines its own `stack` method that does **not** go through `stacks`: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly, so `require_permission :read, :stack` only checks that the token *possesses* the `read:stack` permission string — via `ApiClient#check_permissions!`, which never inspects `stack_id` at all: [3](#0-2) 
The permission check verifies *what* operation/scope class is allowed, but the controller never re-applies the *which stack* binding that `stacks`/`stack` in `BaseController` normally provides.

This is the same class of bug as the ACME TLS-SNI report: the system validates one identifier (the token owns `read:stack` and belongs to *some* stack) but acts on a different, unverified identifier supplied directly by the client (`params[:stack_id]`), because the code path that would re-bind "authorised stack" to "requested stack" is the one path that got skipped.

### Impact Explanation
A `read:stack`-scoped `ApiClient` token that is meant to be restricted to a single stack (e.g. `here_come_the_walrus` fixture, which has `stack: shipit`) can be replayed against `GET /api/:stack_id/cc_menu.xml` for **any other stack** on the Shipit instance, returning that stack's build/deploy status, last build label, and lock state — information the token was never granted access to. This matches the "High — unauthenticated/unauthorized read of stack state" impact category: cross-stack disclosure of deploy state through an authorization-scope confusion, without needing a Shipit session, GitHub credentials, or admin access — only an already-issued, narrowly-scoped API token.

### Likelihood Explanation
Any holder of a stack-scoped API token (which by design is meant to be handed out with reduced privilege, e.g. via `CCMenuUrlController`-style generated links, or through the `ApiClientsController` UI where an admin explicitly restricts a client to one stack) can trivially exploit this by changing the `stack_id` segment of the URL. No special conditions or races are required, and the flaw is purely in `CCMenuController#stack` overriding the safe default.

### Recommendation
Remove the custom `stack` override in `CCMenuController` and use the inherited, scoped `stack`/`stacks` helpers from `BaseController` (i.e., resolve via `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot query stacks outside their authorised `stack_id`.

### Proof of Concept
1. Create (or use) an `ApiClient` with `permissions: ['read:stack']` and `stack: <Stack A>` (mirrors the `here_come_the_walrus` fixture).
2. Using that client's `authentication_token` as HTTP Basic auth, request:
   `GET /api/<Stack B id-or-slug>/cc_menu.xml` where `Stack B` is a different, unrelated stack.
3. `require_permission :read, :stack` passes because the token has the `read:stack` permission string; `CCMenuController#stack` resolves `Stack B` directly via `Stack.from_param!`, bypassing the `stacks` scoping that would normally raise/`404` for stacks outside `current_api_client.stack_id`.
4. The response returns Stack B's CCMenu XML (build status, last build label/time, lock state) even though the token was only ever authorised for Stack A. [4](#0-3)

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
