### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by sha, `Commit.where(sha: params.sha)`, without verifying that `params.dig('repository','full_name')` matches the stack/repository owning that commit row. An attacker who controls a repository whose commit history shares shas with a victim's repository (e.g., a public fork, which reproduces identical shas for identical historical commits) can send a signed `status` webhook from their own repo/org and have Shipit attach that status to the victim's `Commit` row, corrupting `Commit#status`/`blocked?`/`deployable?` for the victim stack.

### Finding Description
The broken binding: the question's assumed invariant is `commit.status for stack S is written only from Status payloads whose payload['repository']['full_name'] == S.repository.full_name`. Tracing the code shows this is false: `Status.replicate_from_github!` is scoped only by `stack_id` derived from `commit.stack_id` [4](#0-3) , and `commit.create_status_from_github!` is invoked for *every* `Commit` row matching the sha in the entire Shipit instance, not the commit belonging to the webhook's originating repository [3](#0-2) .

`WebhooksController#verify_signature` only checks that the payload is validly signed for `repository_owner` (the org named in the payload itself), i.e. it authenticates *that the payload really came from that org's GitHub App/webhook secret* — it does not authenticate that the sha inside the payload belongs to that org's repository [5](#0-4) . An attacker who owns any GitHub organization/repo wired into `Shipit.github_teams`-independent `Shipit.github(organization:)` config (any onboarded org, or their own fork under an org with a configured GitHub App/webhook secret) can therefore produce a validly-signed `status` event for their own org while naming an arbitrary sha in the body.

Other handlers (`PushHandler`, presumably `CheckSuiteHandler`) use the `stacks` helper that filters via `Repository.from_github_repo_name(repository_name)` [1](#0-0) , correctly binding the payload to only the repository that authenticated it. `StatusHandler` does not use this helper at all, so the repository-binding guard that protects every other handler is absent here.

Exploit flow: attacker creates/uses a repository whose git history is identical to (or intersects with) the victim's repository (trivial via GitHub "fork", which preserves commit shas exactly), configures/uses a `status` webhook from that repo, and POSTs a `status` payload naming the victim's shared commit sha with `state: 'failure'`. Because the lookup is `Commit.where(sha:)` with no stack/repo filter, the victim stack's `Commit` row for that sha receives a new `Status` row scoped to the victim's `stack_id` (taken from `commit.stack_id`, not from the payload's repository) [4](#0-3) . This flips `Commit#status`/`state` per the failure/error > pending > success > unknown precedence shown by `#status hierarchy uses failures and errors, then pending, then successes, then Status::Unknown` [6](#0-5) , making that commit `blocked?`/non-`deployable?`.

Downstream, `Stack#next_commit_to_deploy` walks commits in id order and returns the first deployable one within `maximum_commits_per_deploy` via `deployable_commits` [7](#0-6) , so forging failure on the earliest undeployed commit causes it to skip to a later commit, and `trigger_continuous_delivery` deploys that different, attacker-influenced commit range [8](#0-7) .

### Impact Explanation
An unprivileged external attacker (owner of any repo whose commit history overlaps a victim's, most easily via a GitHub fork of a public victim repo) can write `Status` rows onto a victim stack's commits without ever authenticating as that repository, corrupting CI state and manipulating `Stack#next_commit_to_deploy`'s selection to change which commit range gets deployed by continuous delivery. This is a cross-repository write (a payload for repository A mutating repository B's commit/task state) and results in an unauthorized/altered deploy — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". Blast radius: any Shipit instance hosting a public repo with forks (extremely common), or any two onboarded repos sharing commit history (e.g. via cherry-pick/rebase reproducing identical shas), affecting every stack tracking the shared commits.

### Likelihood Explanation
Preconditions: the attacker's repository/org must have GitHub webhooks configured and pointed at the shared Shipit instance's `/webhooks` endpoint with a valid signing secret — this is standard for any repo the attacker controls that is itself onboarded to the same Shipit instance (or any org listed in `Shipit.github(organization:)`), which is a low-cost, self-service action (fork the victim's public repo into the attacker's own account, add it as a Shipit stack under the attacker's control, or use an existing sha collision by rebasing/cherry-picking identical commit content). No Shipit secrets, GitHub App private key, or victim credentials are required — only that the attacker's own webhook signs validly for their own repo. Reproducing exact shas for arbitrary historical commits is deterministic and trivial for forks; for non-fork repos it would require reproducing every hash input (tree, parents, timestamps, message), which is harder but feasible for early/shared history.

### Recommendation
In `StatusHandler#process`, scope commit lookup to the requesting repository using the existing `stacks` helper, e.g. only update commits whose `commit.stack_id` is in `stacks.pluck(:id)` (or `commit.stack.repository.full_name == payload.dig('repository','full_name')`), mirroring the pattern already used in `PushHandler`. Reject/ignore statuses for commits belonging to stacks not owned by the authenticated payload's repository.

4. 5. Assert the broken binding: `commit_a.reload.status.state == 'failure'` even though the payload's `repository.full_name` never matched `stack_victim.repository.full_name` — i.e. assert `Shipit::Status.where(commit: commit_a).last.stack_id == stack_victim.id` was created despite the payload naming a different repository.
