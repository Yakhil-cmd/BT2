### Title
Stale delegate grants silently reactivate after a position NFT round-trip, allowing unauthorized withdrawals - ([File: contracts/controller/src/storage/account.rs])

### Summary
The controller disables a delegate grant while a different address owns the position NFT, but does not invalidate the stored grant. If the NFT later returns to the original owner, `get_delegates` accepts the old `DelegateGrant` again because it is keyed only by `granted_by == current_owner`, with no transfer epoch, revocation nonce, or explicit reauthorization. A previously approved position manager can then call `withdraw` or `borrow` and choose an external recipient, moving account funds without any new authorization from the owner after the transfer back.

### Finding Description
`DelegateGrant` stores only the granting owner and delegate list; ownership changes invalidate the grant only by making the owner comparison fail, not by deleting or epoching the grant. [1](#0-0) 

`get_delegates` returns the stored list whenever `grant.granted_by == *owner`. It does not distinguish a grant made after the current ownership period from one created before an intervening NFT transfer. [2](#0-1) 

The account authorization check treats any listed delegate that is also an active position manager as equivalent to the current owner. [3](#0-2) 

Withdrawal then permits that delegate to select any external `to` recipient after passing `require_owner_or_delegate`; the recipient check only excludes the pool and controller. [4](#0-3) [5](#0-4) 

The same stale delegate can borrow and send the proceeds to an external recipient, subject to the position's final solvency checks. [6](#0-5) 

### Impact Explanation
A stale active position manager can extract all withdrawable collateral from an account whose NFT returns to the original owner. It can also borrow up to the position's risk limits and send the borrowed assets to itself. This is theft of user funds: the owner's current signature never authorizes the post-return withdrawal or borrow, and the revived grant can be materially outside the owner's intended current delegation.

### Likelihood Explanation
The path is reachable by an unprivileged, formerly delegated manager once the NFT returns to `granted_by`. That can happen through ordinary NFT sale/transfer workflows, custodial routing, marketplace settlement, or a crafted transfer flow that causes the position token to round-trip through the former owner. No privileged role, leaked key, upgrade, malformed parameter, or external-oracle manipulation is required. The attacker must previously have been delegated and must remain an active registered position manager, which limits the population of attackers but does not remove the policy-enforcement defect.

### Recommendation
Bind delegate grants to an ownership epoch that increments on every position NFT mint/transfer/burn or equivalent controller-visible ownership transition. Alternatively, clear `ControllerKey::Delegates(account_id)` whenever ownership changes, or require the current owner to reactivate a stored grant before it can authorize spending. Owner and integration tests should cover `owner -> intermediate owner -> owner` followed by delegate `withdraw` and `borrow`, and must require `NotAuthorized` unless the final owner explicitly re-grants.

### Proof of Concept
Conceptual transaction sequence:

1. Alice owns `account_id` and calls:
   `controller.add_delegate(alice, account_id, mallory)`, where `mallory` is an active position manager.
2. Alice transfers NFT `token_id == account_id` to Bob using `position_nft.transfer(alice, bob, token_id)`. The stored grant remains but reads inactive because `granted_by != bob`.
3. Bob transfers the same NFT back to Alice using `position_nft.transfer(bob, alice, token_id)` without calling `remove_delegate` or `add_delegate`.
4. `get_delegates(env, account_id, alice)` now returns Mallory because `grant.granted_by == alice`.
5. Mallory calls:
   `controller.withdraw(mallory, account_id, withdrawals, Some(mallory))`.
   `require_owner_or_delegate` passes, `require_external_recipient` permits Mallory's wallet, and the pool pays Mallory.
6. If collateral remains sufficient, Mallory can also call:
   `controller.borrow(mallory, account_id, borrows, Some(mallory))`
   and receive the borrowed assets.

```rust
/// Returns grants stamped by `owner`, or an empty list. Ownership changes
/// invalidate a previous owner's grants without deleting them.
pub(crate) fn get_delegates(env: &Env, account_id: u64, owner: &Address) -> Vec<Address> {
    get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
        .filter(|grant| grant.granted_by == *owner)
        .map(|grant| grant.delegates)
        .unwrap_or_else(|| Vec::new(env))
```

```rust
/// Accepts the owner or a registered, active manager delegated by that owner.
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
```

```rust
) -> Vec<HubPayment> {

    let mut account = storage::get_account(env, account_id);
```
