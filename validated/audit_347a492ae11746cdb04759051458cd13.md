### Title
Permissionless `coin_registry::new_currency<T>` allows front-running/squatting of any coin type's deterministic registry slot and treasury cap - (File: `crates/sui-framework/packages/sui-framework/sources/registries/coin_registry.move`)

### Summary
`sui::coin_registry::new_currency<T: key>()` is a fully `public fun` that only requires the type parameter `T` to have the `key` ability — it does **not** require a one-time-witness or any proof that the caller controls/publishes `T`. Because the resulting `Currency<T>` object address is deterministically derived from `registry.id` and `CurrencyKey<T>()` via `derived_object::claim`, and because derived-object claims are permanent (cannot be reclaimed even after deletion), any unprivileged caller can front-run the registration of an arbitrary, pre-existing coin type by calling `new_currency<T>()` before the legitimate publisher of `T` does. This is a direct analog of the Nayms "deterministically generated objectId can be front-run by preselected ids" bug: a deterministic id namespace exists, but nothing binds the id-claiming operation to an entity that is actually authorized to own that namespace slot.

### Finding Description [1](#0-0) 

`new_currency<T: /* internal */ key>` is documented as "This can be called from the module that defines `T` any time after it has been published," but this constraint is **only a comment** — the Move type system enforces nothing beyond `T: key`. Any struct with the `key` ability, from any already-published package (including third-party token contracts such as a bridged USDC/USDT wrapper struct), satisfies this bound. The function:

1. Checks `!registry.exists<T>()` [2](#0-1) 
2. Mints a real `TreasuryCap<T>` via `coin::new_treasury_cap(ctx)` [3](#0-2) 
3. Permanently claims the deterministic derived address for `Currency<T>` using `derived_object::claim(&mut registry.id, CurrencyKey<T>())` [4](#0-3) 

`derived_object::claim` marks the `(parent, key)` pair as `Claimed` in a dynamic field that is **never removed**, even if the derived object is later deleted: "Note: If the UID has been deleted through `object::delete`, this will always return true." [5](#0-4)  and the collision guard aborts with `EObjectAlreadyExists` on any second claim attempt [6](#0-5) .

The secure counterpart, `new_currency_with_otw<T: drop>`, correctly requires `sui::types::is_one_time_witness(&otw)` [7](#0-6) , which can only be satisfied once, by the module that declares `T`, at publish time. `new_currency` has no equivalent binding — it is the "off-chain trust assumption" analog from the Nayms report, except here the trust assumption is silently absent from the on-chain code entirely (no OTW, no `Publisher` capability, no address/module comparison against `T`'s defining package).

### Impact Explanation
Because the registry slot for `Currency<T>` is a single, permanently-claimed derived address per type `T`:
- An attacker can call `new_currency<T>()` for a type `T` belonging to a third party (e.g. a well-known wrapped stablecoin struct or any popular coin type not yet migrated to the registry) before the legitimate issuer registers it, permanently occupying the canonical registry slot for that coin type. Because `derived_object` claims are irrevocable (`EObjectAlreadyExists` on any future attempt, even after deletion), the legitimate issuer can **never** register the canonical `Currency<T>` metadata for their own token — a permanent denial-of-service against the coin's registry/metadata (harmful smart-contract behavior / permanent lock of expected registry functionality for that coin type).
- The attacker also receives a genuine `TreasuryCap<T>` for a type they do not own via `coin::new_treasury_cap(ctx)`. Since `Coin<T>`/`Balance<T>` fungibility depends only on the phantom type `T`, not on which `Supply<T>`/`TreasuryCap<T>` instance created it, if `T` already has coins in circulation from a legitimately-created treasury cap (e.g. from the older `coin::create_currency` path), the attacker's rogue `TreasuryCap<T>` can mint coins that are fully fungible with the existing supply of `T` — unauthorized minting/supply corruption for an existing asset. I was not able to fully verify the internal access controls of `coin::new_treasury_cap` in this pass (its source was not retrieved), so this secondary consequence should be confirmed by inspecting `sui::coin::new_treasury_cap`'s visibility and preconditions before treating it as fully confirmed; however, the registry-slot-squatting/permanent-DoS impact is directly confirmed by the code shown above.

### Likelihood Explanation
High. `new_currency` is a fully public, unprivileged entry point reachable from any PTB or Move module; the only constraint (`T: key`) is trivially satisfied by referencing any already-published struct type. No signer/capability/witness check restricts the caller to the actual owner of `T`. The only thing preventing an attacker today would be simply being first — a race any bot/MEV searcher can win against a soon-to-be-published or soon-to-be-migrated legitimate coin.

### Recommendation
Require proof of authority over `T` before allowing `new_currency<T>()` to claim the registry slot, mirroring `new_currency_with_otw`'s OTW check. Options:
- Require a `Publisher` object matching `T`'s defining package (as used elsewhere in the framework for module-scoped authorization), or
- Restrict `new_currency<T: key>` to require an OTW-like uniqueness proof as well, or
- Gate the permissionless variant so it can only be used for types with **no** pre-existing on-chain supply/treasury cap, and require any subsequent claim to first prove the caller holds an existing legitimate `TreasuryCap<T>`/`Publisher` for that type.

### Proof of Concept
1. Identify a coin type `T` (any struct with `key` ability) belonging to another team that has not yet called `coin_registry::new_currency<T>` or `new_currency_with_otw<T>`.
2. From an unprivileged account, submit a PTB calling `sui::coin_registry::new_currency<T>(registry, decimals, symbol, name, description, icon_url, ctx)`.
3. Observe: `derived_object::claim(&mut registry.id, CurrencyKey<T>())` succeeds and permanently marks that `(registry, CurrencyKey<T>())` pair as claimed [6](#0-5) ; the attacker receives a `TreasuryCap<T>`.
4. When the legitimate owner of `T` later attempts `new_currency<T>()` or `new_currency_with_otw<T>()` followed by `finalize_registration`, both paths call `derived_object::claim(&mut registry.id, CurrencyKey<T>())` for the same key and abort with `EObjectAlreadyExists`, permanently preventing legitimate registration of `T`'s canonical `Currency` object [8](#0-7) .

/// Creates a new currency.
///
/// Note: This constructor has no long term difference from `new_currency_with_otw`.
/// This can be called from the module that defines `T` any time after it has been published.
public fun new_currency<T: /* internal */ key>(
    registry: &mut CoinRegistry,
    decimals: u8,
    symbol: String,
    name: String,
    description: String,
    icon_url: String,
    ctx: &mut TxContext,
): (CurrencyInitializer<T>, TreasuryCap<T>) {
    assert!(!registry.exists<T>(), ECurrencyAlreadyExists);
    assert!(is_ascii_printable!(&symbol), EInvalidSymbol);

    let treasury_cap = coin::new_treasury_cap(ctx);
    let currency = Currency<T> {
        id: derived_object::claim(&mut registry.id, CurrencyKey<T>()),
        decimals,
        name,
        symbol,
        description,
        icon_url,
        supply: option::some(SupplyState::Unknown),
        regulated: RegulatedState::Unregulated,
        treasury_cap_id: option::some(object::id(&treasury_cap)),
        metadata_cap_id: MetadataCapState::Unclaimed,
        extra_fields: vec_map::empty(),
    };

    (CurrencyInitializer { currency, is_otw: false, extra_fields: bag::new(ctx) }, treasury_cap)
}

/// Claim a deterministic UID, using the parent's UID & any key.
public fun claim<K: copy + drop + store>(parent: &mut UID, key: K): UID {
    let addr = derive_address(parent.to_inner(), key);
    let id = addr.to_id();
    assert!(!df::exists(parent, Claimed(id)), EObjectAlreadyExists);
    df::add(parent, Claimed(id), ClaimedStatus::Reserved);
    object::new_uid_from_hash(addr)
}
