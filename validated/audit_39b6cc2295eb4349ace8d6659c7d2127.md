### Title
API-scoped `ApiClient.stack_id` binding bypassed in `CCMenuController#stack` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts stack-scoped API tokens to their assigned stack by resolving the requested stack through the `stacks` collection, which filters by `current_api_client.stack_id` when present [1](#0-0) . `Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly against the unscoped `Stack` model, ignoring the token's `stack_id` restriction [2](#0-1) . This breaks the binding "the stack a token authorizes == the stack it touches."

### Finding Description
The intended authorization model in the API layer is: an `ApiClient` may carry a `stack_id`, and if present, every stack lookup must be limited to that stack via `stacks = current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` and `stack = stacks.from_param!(params[:stack_id])` [1](#0-0) . Every other controller under `app/controllers/shipit/api/` (e.g. `StacksController`, `HooksController`) relies on this inherited, scoped `stack`/`stacks` helper to enforce the token/stack binding together with `require_permission`.

`CCMenuController` breaks this pattern:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

This calls `Stack.from_param!` on the class itself, not on the scoped `stacks` collection, so the `current_api_client.stack_id` restriction is never consulted. The controller only enforces `require_permission :read, :stack` [4](#0-3) , which merely checks that the string `"read:stack"` is present in `ApiClient#permissions` — a global capability check, not a per-stack check: `check_permissions!` just does `permissions.include?(required_permission)` [5](#0-4) .

This mirrors the `NukeFund.nuke()` class of bug: the code that authenticates/authorizes a principal (verifying `getApproved`/`isApprovedForAll` in one context) is checked against the wrong scope, and the entity actually acted upon (`burn`) is different from what was authorized. Here, the entity permitted (`current_api_client`'s assigned `stack_id`) and the entity actually read (`Stack.from_param!(params[:stack_id])`, attacker-controlled) diverge.

### Impact Explanation
Any holder of a valid `ApiClient` authentication token that is scoped to one stack (e.g., a "CCMenu Client" or any client an admin restricted to a single stack via `stack_id`, with `read:stack` permission) can read build/deploy status for **any** stack in the Shipit instance by simply changing the `stack_id` URL/query parameter, because `CCMenuController#stack` never applies the `stacks` scoping. This is an unauthenticated-relative-to-scope read of stack state/deploy status across stacks the token was never meant to see — matching the "High: unauthenticated read of stack state, task streams or deploy output" impact category, since it defeats the per-stack authorization boundary that `ApiClient.stack_id` is designed to enforce.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack`-scoped API token restricted to a single stack, no privileged account or write access is needed. Such tokens are routinely created and exposed (e.g., via `CCMenuUrlController#fetch`, which embeds `client.authentication_token` directly in a URL returned to any logged-in user for use with CI tooling) [6](#0-5) . Because the vulnerable code path is reached on every `GET` to the CCMenu XML endpoint and the bypass is a trivial parameter substitution, likelihood is high once a scoped token is obtained.

### Recommendation
Change `CCMenuController#stack` to resolve through the inherited, scoped lookup instead of the raw `Stack` model:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the override entirely (falling back to `BaseController#stack`) achieves the same fix, since `stacks` already applies the `current_api_client.stack_id` restriction defined in `BaseController` [1](#0-0) .

### Proof of Concept
1. As an authenticated Shipit user, visit `Shipit::CCMenuUrlController#fetch` for `stack_A`; this creates/reuses an `ApiClient` with `permissions: ['read:stack']` and returns a URL containing `client.authentication_token` [7](#0-6) . Assume (per intended design / an admin-restricted client) this token's `stack_id` is set to `stack_A.id`.
2. Use that token against the CCMenu API endpoint, but substitute a different stack's identifier: `GET /api/stacks/<stack_B_owner>/<stack_B_name>/<stack_B_env>/ccmenu.xml?token=<stack_A_token>`.
3. `authenticate_api_client` in `CCMenuController` successfully authenticates the token via `ApiClient.authenticate(params[:token])` [8](#0-7) .
4. `require_permission :read, :stack` passes because the client's `permissions` array contains `"read:stack"` globally [5](#0-4) .
5. `stack` resolves `stack_B` directly via `Stack.from_param!(params[:stack_id])`, ignoring that the token's `stack_id` was `stack_A.id` [3](#0-2) .
6. The response renders `stack_B`'s latest deploy/rollback status [9](#0-8) , disclosing deploy state for a stack the token was never authorized to access.
