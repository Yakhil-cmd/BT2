### Title
Uncaught `throw Error("not 1 template")` in `validateAuthentifiers` crashes every validating node - ([File: definition.js])

### Summary
`validateAuthentifiers()` in `definition.js` re-evaluates an address's stored definition every time that address signs a new unit. When the definition contains a `'definition template'` operator, the referenced template lookup throws a raw `Error` instead of returning a validation error through the callback chain if the query doesn't return exactly one row. Because this happens inside an async `conn.query()` callback, the throw is never caught by the validation try/catch and becomes an `uncaughtException`, which `network.js`'s global handler deliberately re-throws to crash the whole node process.

### Finding Description
Address definitions support the `'definition template'` op, which references another unit's `definition_template` payload: [1](#0-0) 

There are two separate code paths that evaluate this op:

1. `validateDefinition()`'s `evaluate()` — used only the *first* time an address's definition is established — properly validates the arguments and returns a callback error if `rows.length !== 1`: [2](#0-1) 

2. `validateAuthentifiers()`'s `evaluate()` — used on *every subsequent unit* signed by that address (and also for asset conditions) — repeats the same query but on failure does not call back with an error; it throws synchronously inside the DB callback: [1](#0-0) 

The query filters by `main_chain_index<=?` (the *new* unit's `last_ball_mci`) `AND +sequence='good' AND is_stable=1`, i.e., the result is evaluated against the state of the network as of the new unit's last ball — not the state at the time the definition was first accepted. If the referenced `definition_template` unit's author later gets double-spent so the template unit's `sequence` becomes non-`'good'` (e.g. `final-bad`), the row disappears from the result set. Any later unit signed by the address that references this template will make `rows.length !== 1`, triggering `throw Error("not 1 template")` inside the `conn.query` callback.

This throw occurs outside of any synchronous `try/catch` in the validation call stack (validation is asynchronous, callback-driven), so it becomes an unhandled/uncaught exception. `network.js` intentionally converts every uncaught exception into a full process crash: [3](#0-2) 

Because this occurs during unit validation — a step every full node performs when processing any newly received or posted unit — every full node (and the hub) that attempts to validate the affected unit will crash identically. This is a deterministic, remotely triggerable "poison unit" that a single unprivileged unit poster/author can craft.

### Impact Explanation
This is a network-wide Denial of Service: a single crafted, otherwise well-formed unit — signed by an address whose stored definition uses `'definition template'` — can crash every node that attempts to validate it, once the referenced template-defining unit has lost `sequence='good'` status (achievable by the same attacker double-spending it). Because the crash happens deterministically for all nodes evaluating the same definition/unit, it can be used to repeatedly halt confirmation of new units network-wide, matching "a network unable to confirm new units."

### Likelihood Explanation
Exploitation requires an attacker to:
1. Post a `definition_template` unit (`app: 'definition_template'`) from an address they control.
2. Use `'definition template'` referencing that unit inside an address B's definition, and use address B once so the definition is accepted while the template is still `sequence='good'` (this succeeds via `validateDefinition`'s proper checks).
3. Double-spend from the original template-posting address so the template unit's `sequence` flips away from `'good'`.
4. Sign and broadcast a new unit from address B.

All of these steps use only standard, unprivileged wallet/API operations (posting units, defining addresses, double-spending own outputs) — no special network position, node compromise, or peer trust is required. This makes the likelihood Medium-High for a determined attacker, though it requires a few coordinated steps and thus is not a purely trivial one-message DoS.

### Recommendation
In `definition.js`'s `validateAuthentifiers()` `evaluate()` function, replace the `throw Error("not 1 template")` on `rows.length !== 1` with a call to `cb2(false)` (i.e. treat it as authentifier-path failure/false) or propagate a proper validation error through `fatal_error`/`cb2`, consistent with how `validateDefinition()` already handles this case. More broadly, audit `definition.js` and `validation.js` for other `throw Error(...)` statements inside asynchronous `conn.query` callbacks reachable during ordinary unit validation, and convert them to callback-based error propagation so malformed/adversarial states cannot crash the process via the global `uncaughtException` handler.

### Proof of Concept
1. Attacker address `A` posts a `definition_template` unit `T` (`app: 'definition_template'`, valid payload).
2. Attacker defines address `B` with a definition `['definition template', [T, {...}]]` and uses `B` to author a unit while `T` is still `sequence='good'` and stable — this passes `validateDefinition`'s checks and address `B`'s definition is now bound.
3. Attacker crafts a second unit spending from `A`'s same input already spent by `T`, causing `T` to become non-serial and eventually be marked non-`'good'` sequence (e.g., `final-bad`) once resolved.
4. Attacker signs and broadcasts a new unit from address `B` (using the previously bound definition, so only `validateAuthentifiers` runs, not `validateDefinition`).
5. Every full node that validates this unit executes `definition.js`'s `validateAuthentifiers` → `evaluate()` → `'definition template'` case, gets `rows.length === 0` from the query (since `T` no longer has `sequence='good'`), and hits `throw Error("not 1 template")` inside the `conn.query` callback — crashing the node via the global `uncaughtException` handler in `network.js`.
