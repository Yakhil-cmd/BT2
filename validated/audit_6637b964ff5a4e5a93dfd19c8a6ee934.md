### Title
Webhook signature verified against attacker-chosen `repository.owner.login` while mutation targets attacker-chosen `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` directly from the unsigned/untrusted request body. `ClosedHandler#process` and `#review_stack` instead resolve the target `Repository` (and thus the `ReviewStack` to archive) using `params.repository.full_name`, a separate, independently attacker-controlled field in the same body. Because these two fields are never checked for consistency, an attacker who owns a repository under `attacker-org` (and therefore knows `attacker-org`'s webhook secret) can sign a payload where `repository.owner.login = attacker-org` but `repository.full_name = victim-org/victim-repo`, causing Shipit to archive/deprovision a `ReviewStack` belonging to a repository the attacker never authenticated for.

### Finding Description
Broken binding stated as an equality: the code assumes `params.dig('repository','owner','login')` (used to select the signing secret) `==` the owner encoded in `params.repository.full_name` (used to resolve the mutated `Repository`/`ReviewStack`). This equality is never enforced anywhere in the request path.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(signature, request.raw_post)`. `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — read straight from the JSON body, which the attacker fully controls before signing. [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) performs a straightforward HMAC-SHA1 compare of the raw body against the secret configured for whatever organization `Shipit.github(organization:)` was called with. It does not know or check what repository the body is actually about; it only validates "this body was signed by the secret of `repository_owner`'s org." [3](#0-2) 
- Once the signature passes, `Shipit::Webhooks.for_event(event)` dispatches to handlers with the same raw `params` (`app/controllers/shipit/webhooks_controller.rb:10-15`), including `Shipit::Webhooks::Handlers::PullRequest::ClosedHandler`. [4](#0-3) 
- `ClosedHandler#process` calls `review_stack.archive!` after checking `action == "closed"`. `repository` is computed via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — using `full_name`, not `owner.login`. `review_stack` wraps a `ReviewStackAdapter` scoped to `repository.review_stacks`. [5](#0-4) 
- `Repository.from_github_repo_name` simply splits `full_name` on `/` and does `find_by(owner:, name:)` — it has no relationship to whichever secret validated the signature. [6](#0-5) 
- `ReviewStackAdapter#archive!` looks up the stack by `environment` (`pr#{params.number}`) within the given scope, and if found and not already archived, calls `stack.remove_from_provisioning_queue`, `stack.deprovision`, and `stack.archive!(user, ...)` — a real, irreversible-effect mutation (deprovisioning infra, archiving the stack). [7](#0-6) [8](#0-7) 

Attacker request: attacker owns `attacker-org/some-repo`, knows the configured webhook secret for `attacker-org` (this is standard for any GitHub org/app owner, not a Shipit secret). Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request` and a JSON body:
```json
{
  "action": "closed",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "number": <real open PR number on victim-org/victim-repo>,
  "pull_request": { ... },
  "sender": { "login": "attacker" }
}
```
signed with `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)`.

Why existing guards fail:
- `verify_signature` only checks "was this exact body signed by the secret belonging to whatever org name appears at `repository.owner.login`" — it never cross-checks that value against `repository.full_name`'s owner segment.
- `drop_unhandled_event` and `check_if_ping` are unrelated to this check.
- The `ExplicitParameters` schema in `ClosedHandler` (`requires :repository { requires :full_name, String }`) only validates presence/type of `full_name`, not that it agrees with `repository.owner.login` used upstream for auth. [9](#0-8) 
- `Repository` model validations (`owner`/`name` format) only constrain character sets, not cross-field consistency with the authenticating org. [10](#0-9) 
- No code path re-derives `repository_owner` from `full_name` and compares it to the value used for signing.

### Impact Explanation
An attacker who controls a GitHub organization/repo (and thus its webhook secret, a value they legitimately possess as an org owner) can forge a signed webhook that is authenticated as coming from their own org but whose payload content — and consequently the `Repository`/`ReviewStack` resolved and mutated — belongs to an entirely different, victim organization. This lets the attacker archive and deprovision any `ReviewStack` on any tracked repository, for any PR number, as long as they can guess/know a real open PR number on the victim repo (publicly visible on GitHub). This is a cross-tenant authorization bypass: a payload authenticated under one organization's credentials mutates another organization's stack state — matching the "Critical: payload for one repository mutating another's stack" category. The same broken binding likely affects sibling handlers (`opened_handler.rb`, `reopened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `edited_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`) since they all derive `repository` from `params.repository.full_name` independently of `repository_owner`, though this question is scoped to `ClosedHandler`. The attack is trivially repeatable against arbitrary victim repositories/stacks, limited only by the attacker knowing a victim repo's `full_name` and an open PR number on it (both public GitHub information).

### Likelihood Explanation
Preconditions are modest: the victim repo must be configured in Shipit with review stacks enabled and have an active `ReviewStack` for a real PR number (readily achievable/observable since Shipit review-stack repos and open PRs are typically visible on GitHub). The attacker needs only an org/repo they control with a configured webhook secret — a standard capability for anyone who can create a GitHub org and add Shipit's GitHub App/webhook to it, requiring no Shipit credentials, session, or victim-org secret. Crafting and sending the forged HTTP POST is trivial (no rate limiting or additional checks block it). This makes the exploit low-cost and highly repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or before dispatch), after successfully verifying the signature for `repository_owner`, additionally require that `repository_owner` matches the owner segment parsed from `params.dig('repository','full_name')` (case-insensitively) before allowing the event to reach any handler; reject with `422` on mismatch. Alternatively, have each handler (or a shared base) re-derive the owning organization from `full_name` and assert equality with the value that was actually used to select the verifying secret before performing any state-mutating action like `archive!`/`unarchive!`.

### Proof of Concept
Minitest plan (e.g., in `test/controllers/webhooks_controller_test.rb` style, or a dedicated test):
```ruby
test "closed webhook signed by unrelated org cannot archive another org's review stack" do
  # Arrange: victim repository + active review stack for PR #42
  victim_repo = shipit_repositories(:shipit) # owner: 'shopify' (or similar victim org)
  victim_stack = create_review_stack(repository: victim_repo, environment: "pr42") # not archived

  # Attacker-controlled org has its own configured webhook secret 'attacker-org'
  Shipit.github(organization: 'attacker-org') # returns a GithubApp configured with a *different* secret than victim org

  body = {
    action: 'closed',
    repository: { full_name: "#{victim_repo.owner}/#{victim_repo.name}", owner: { login: 'attacker-org' } },
    number: 42,
    pull_request: { id: 1, number: 42, url: 'https://api.github.com/...', title: 't',
                     state: 'closed', additions: 1, deletions: 1,
                     head: { sha: 'abc', ref: 'feature' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    sender: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', ATTACKER_ORG_SECRET, body)}"

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  # Equality being validated: repository_owner ('attacker-org') used for signature
  # must equal owner segment of repository.full_name (victim org) — assert they differ:
  assert_not_equal 'attacker-org', victim_repo.owner

  post :create, body: body, as: :json

  # If vulnerable: request passes signature check (signed by attacker-org secret) and
  # victim_stack gets archived despite never being authenticated by victim org's secret.
  assert_response :ok
  assert victim_stack.reload.archived?, "victim ReviewStack should NOT be archived by a payload signed under a different org's secret"
end
```
This test demonstrates: signature verification succeeds using `attacker-org`'s secret (`repository_owner` binding), while the actual mutated record (`victim_stack`) belongs to a repository resolved from `full_name` under a different organization, proving the two values (`repository_owner` vs. `full_name`'s owner) are never checked for equality.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
