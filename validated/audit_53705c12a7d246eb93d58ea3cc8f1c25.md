Nested `["address", X]` reference lets the owner of an unrelated address permanently exceed `MAX_COMPLEXITY`/`MAX_OPS`, bricking the outer address - (File: definition.js)

### Summary
An address definition can include an `["address", X]` clause that pulls in the *current* definition of another, independently-controlled address `X` at evaluation time. Because `X`'s owner can redefine `X` at any later point (via a normal `has definition change` / key-change unit) without any coordination with, or consent from, the outer address's owner, the complexity/op-count of the outer address's definition is not fixed at creation time but is re-derived every time the outer address is used. This mirrors the Sherlock H-5 pattern: an "other module" (here, the independent owner of the referenced address) can unilaterally push a resource whose growth is checked only against a global cap (`maxSigners` in the report, `MAX_COMPLEXITY`/`MAX_OPS` here), with no mechanism for the victim (outer address owner) to prevent or reverse it.

### Finding Description
- `validateDefinition()`'s `evaluate()` function increments `complexity`/`count_ops` for every op and rejects if `complexity > constants.MAX_COMPLEXITY` or `count_ops > constants.MAX_OPS` [1](#0-0) .
- The `'address'` case dereferences another address's *currently disclosed* definition from the DB via `storage.readDefinitionByAddress()` and recursively evaluates it inline, adding its complexity to the outer evaluation [2](#0-1) .
- The same lazy re-resolution happens in the authentifier-evaluation path (`validateAuthentifiers`), which also recurses into `arrInnerAddressDefinition` fetched from storage [3](#0-2) .
- The code comment explicitly acknowledges this danger: "we need to re-validate the definition every time... 2. redefinition of a referenced address might introduce loops that will drive complexity to infinity 3. if an inner address was redefined by keychange but the definition for the new keyset not supplied before last ball, the address becomes temporarily unusable" [4](#0-3) .
- Definitions support "definition template" (`['definition template', [unit, params]]`), which similarly pulls in externally-controlled content (a template published by any unit) and re-evaluates it each time, adding to complexity [5](#0-4) .
- `MAX_COMPLEXITY` and `MAX_OPS` are fixed, global anti-spam constants, with no per-address override mechanism the outer address owner can use to "unstick" a definition once it becomes too complex [6](#0-5) [7](#0-6) .

**Attack/failure path:**
1. Alice creates address `A` with definition `["address", "B"]` (or `["and", [["sig",...],["address","B"]]]`), where `B` is controlled by Bob, an unrelated third party. At creation time `B`'s definition is simple (e.g., `["sig", pubkey]`), so total complexity of `A` is well under `MAX_COMPLEXITY`.
2. Later, Bob (who has no relationship to Alice and is not required to coordinate with her) redefines `B` — e.g. into a large nested `or`/`and` tree, or into a chain that itself references yet another address — using a normal, valid `has definition change`/keychange unit. This is entirely within Bob's rights over his own address `B`.
3. From that point forward, every time anyone tries to spend from `A` (or evaluate `A`'s definition, e.g. as an asset condition or witness list check), `validateDefinition`/`validateAuthentifiers` recursively evaluates `B`'s new definition inline, and the combined complexity/op count of `A`'s branch now exceeds `MAX_COMPLEXITY`/`MAX_OPS`.
4. Every unit spending from `A` is rejected with "complexity exceeded" / "number of ops exceeded", permanently since `B`'s definition is outside Alice's control and there is no owner-level override for `A` (analogous to admins having no control over the "eligibility address" in the Sherlock report). Funds on `A` are frozen unless Bob cooperates (or is somehow forced) to redefine `B` back to something simple — a trust assumption that, just like in the Sherlock finding, is neither documented nor enforced by the protocol.

This is structurally identical to the H-5 pattern: a resource cap (`maxSigners` vs. `MAX_COMPLEXITY`/`MAX_OPS`) is checked centrally at usage time, but the thing being capped (owners in the Safe vs. nested address complexity) can be grown by an independent, uncoordinated actor (another Safe module vs. the referenced address's real owner) without the victim's consent, leading to a permanent DoS/freeze with no recovery path.

### Impact Explanation
Funds held at address `A` can become permanently unspendable ("AA fund loss or freezing" / "network unable to confirm new units" from address `A`), with the root cause being an action by a completely independent actor (owner of the referenced address `B`) who has no privileged relationship to `A`. This qualifies as Medium/High impact per the analog criteria: concrete, unrecoverable freezing of funds triggered by an unprivileged, unrelated party's legitimate action on their own address.

### Likelihood Explanation
Likelihood is realistic but requires a specific setup: `A`'s definition must include `["address", B]` (or `"definition template"`) referencing an address not fully controlled by `A`'s owner (e.g. multi-party escrow/smart-address setups, shared wallets, or templates published by third parties), and `B`'s owner must later increase `B`'s definition complexity near/over the cap. This is a normal, permitted operation for `B`'s owner and requires no exploit — just an innocuous or malicious redefinition. Complexity of nested definitions is a well-known, commonly used feature (multisig/shared addresses), making this a plausible occurrence, especially adversarially (Bob deliberately griefing Alice) or accidentally (Bob upgrading his own multisig setup).

### Recommendation
- When an outer definition references another address via `["address", X]` or `"definition template"`, snapshot/cap the complexity contribution at the time of first use (or at the time `A`'s definition is created/disclosed) rather than re-deriving it from the live, mutable definition of `X` at every future evaluation.
- Alternatively, enforce a strict, address-owner-controlled complexity budget for referenced addresses (e.g., disallow definition changes to `X` that would push complexity of *any* address referencing `X` above the cap, or require that referencing addresses re-validate and explicitly re-consent to definition changes of referenced addresses before they take effect for them).
- At minimum, document the trust assumption clearly (referenced addresses must be either fully trusted or immutable) so wallet software can warn users before they build definitions that reference externally-controlled, mutable addresses.

### Proof of Concept
1. Bob creates address `B` with a small definition `["sig", {pubkey: PB}]`.
2. Alice creates address `A` with definition `["and", [["sig", {pubkey: PA}], ["address", "B"]]]`. This validates fine since total complexity/ops are small — confirmed by the evaluate() complexity accounting in `validateDefinition` [8](#0-7) .
3. Bob later submits a valid `address_definition_change` (or keychange) unit redefining `B` into a deeply nested definition (e.g., many `or`/`and` branches, or `B` in turn referencing address `C`, `C` referencing `D`, etc.) such that `B`'s standalone complexity/op count is itself under `MAX_COMPLEXITY`/`MAX_OPS`, but is intentionally sized so that `A`'s branch complexity (`A`'s own ops + `B`'s new ops, per the recursive `evaluate` in `definition.js:269-304`) exceeds `MAX_COMPLEXITY` (100) or `MAX_OPS` (2000).
4. Any subsequent unit spending from `A` fails validation with `"complexity exceeded at r.1"` or `"number of ops exceeded at r.1"` in `validateDefinition`'s `evaluate()` [1](#0-0) , and separately fails signature verification in `validateAuthentifiers`'s `'address'` case which re-evaluates the same live definition [3](#0-2) .
5. `A`'s funds are now permanently frozen: Alice cannot alter `B`'s definition, and Bob has no obligation (and possibly incentive not) to revert it, exactly analogous to the Safe being bricked by an uncooperative external module in the referenced report.
