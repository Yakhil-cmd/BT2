### Title
Untrusted skill description bypasses `Untrusted.String()` sanitization and reaches the terminal unsanitized via `.Raw()` → `frontmatter.Parse` in `gh skill search` - ([File: pkg/cmd/skills/search/search.go])

### Summary
`fetchDescriptions` in `pkg/cmd/skills/search/search.go` calls `content.Raw()` on an `iostreams.Untrusted` blob fetched from an attacker-controlled repository, feeds the raw bytes into `frontmatter.Parse`, and stores the extracted `Description` field as a plain (no-longer-`Untrusted`) `string`. That string is later written directly to `opts.IO.Out`/`opts.IO.ErrOut` in `renderTable`/`promptInstall` via `fmt.Fprintln`/`fmt.Fprintf`/`tableprinter`, without ever passing back through `Untrusted.String()` or `ContentOut`'s sanitizing writer.

### Finding Description
`discovery.FetchBlob` (`internal/skills/discovery/discovery.go:918-944`) fetches a git blob by SHA and returns it wrapped as `iostreams.Untrusted`, explicitly documented as needing sanitized display or raw round-tripping only [1](#0-0) .

In `pkg/cmd/skills/search/search.go`, `fetchDescriptions` calls `content.Raw()` to get the unsanitized bytes and passes them to `frontmatter.Parse`: [2](#0-1) 

`frontmatter.Parse` unmarshals the YAML frontmatter into a `Metadata` struct with a plain `string` `Description` field — no sanitization is applied to any field: [3](#0-2) 

This raw `Description` is copied into `skillResult.Description` (`enrichSkills`, `pkg/cmd/skills/search/search.go:406-413`) and then rendered directly to the terminal in two places without any escape-sequence stripping:
- `renderTable`, via `table.AddField(desc)` after only a length truncation: [4](#0-3) 
- `promptInstall`, via string concatenation and `fmt.Fprintln`/interactive picker options: [5](#0-4) 

Neither path routes the description through `Untrusted.String()` (the sanitizing method: `pkg/iostreams/untrusted.go:35-44`) or through `opts.IO.ContentOut` (the sanitizing writer for external content: `pkg/iostreams/iostreams.go:58-63`). The `Untrusted` wrapper's entire safety model relies on `.Raw()`/`.RawBytes()` being used only for non-terminal purposes (hashing, file writes, piping) [6](#0-5) , but here `.Raw()` output is parsed and its derived field re-enters the terminal-output path as an ordinary `string`, defeating the type-level invariant that only `Untrusted.String()` ever reaches `opts.IO.Out`.

Attacker input: any public GitHub repository containing a `SKILL.md` file discoverable via the GitHub Code Search API (`filename:SKILL.md`) with a `description:` YAML field containing ANSI escape/control sequences (e.g., terminal title injection `\x1b]0;...\x07`, cursor movement, or screen-clearing sequences). When a victim runs `gh skill search <term>` and this poisoned skill appears in the (non-interactive table or interactive picker) results, the escape sequences are written verbatim to the victim's terminal.

By contrast, other `.Raw()`/`.RawBytes()` call sites in the codebase are safe by design: `pkg/cmd/gist/view/view.go` writes `content.Raw()` only to `opts.IO.ContentOut` (which sanitizes unless an explicit `--allow-escape-sequences` opt-out is set) [7](#0-6) ; `pkg/cmd/gist/edit/edit.go` and `internal/skills/installer/installer.go` use `.Raw()` only for API round-trips and file writes, never for terminal printing [8](#0-7) [9](#0-8) .

### Impact Explanation
This allows an unprivileged, remote attacker who merely publishes a public repository with a crafted `SKILL.md` to inject arbitrary terminal escape/control sequences into a victim's terminal when the victim runs `gh skill search`. Depending on the victim's terminal emulator, this can be used for terminal title spoofing, clearing/overwriting displayed output to hide or spoof information, or (on vulnerable terminal emulators) more severe escape-sequence-based attacks. This matches the "terminal escape/control-sequence injection bypassing the Untrusted safety wrapper" impact class described in the question.

### Likelihood Explanation
High feasibility and fully attacker-controlled: no privileges, no victim interaction beyond running the ordinary `gh skill search <query>` command with results that include the attacker's public repo (which the attacker can nearly guarantee by choosing a matching skill name/query term, or by using `--owner`-style scoping is not needed since results are global code search). The bug is deterministic and repeatable for any query that surfaces the malicious skill.

### Recommendation
Keep `Description` (and other fields extracted from untrusted `SKILL.md` frontmatter) typed as `iostreams.Untrusted` end-to-end, or sanitize it immediately after `frontmatter.Parse` (e.g., `iostreams.NewUntrusted(result.Metadata.Description).String()`) before storing it in `skillResult`, so any later `fmt.Fprint`/`tableprinter.AddField` call sanitizes automatically. Avoid calling `.Raw()` and then handing the raw string to a general-purpose parser whose output re-enters a terminal-writing code path without carrying the `Untrusted` type forward.

### Proof of Concept
```go
func TestSkillSearch_DescriptionEscapeSequenceReachesTerminal(t *testing.T) {
    esc := "\x1b"
    maliciousFrontmatter := "---\nname: evil\ndescription: pwned" + esc + "]0;owned" + esc + "\\\n---\nbody"

    result, err := frontmatter.Parse(maliciousFrontmatter)
    require.NoError(t, err)

    // Description is a plain string with the escape sequence intact.
    assert.Contains(t, result.Metadata.Description, esc)

    // Simulate what renderTable/promptInstall do: write it straight to IO.Out.
    ios, _, out, _ := iostreams.Test()
    fmt.Fprintln(ios.Out, result.Metadata.Description)

    // Expected (currently failing): output should never contain the raw escape byte.
    assert.NotContains(t, out.String(), esc)
}
```
Expected: the assertion fails on current code (escape byte reaches `out`), confirming the sanitization invariant is bypassed for skill descriptions sourced via `content.Raw()` in `pkg/cmd/skills/search/search.go`.
