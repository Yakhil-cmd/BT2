### Title
Cross-organization webhook forgery lets any onboarded GitHub organization forge CI status for arbitrary commits in unrelated stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a GitHub webhook against using `repository_owner`, a field pulled straight from the unverified JSON body (`params.dig('repository','owner','login')`). Once that check passes, the actual handler that mutates state — `Shipit::Webhooks::Handlers::StatusHandler` — never re-checks that the event actually belongs to that organization/repository; it looks up commits globally by SHA (`Commit.where(sha: params.sha)`) across the entire Shipit instance and creates a GitHub status on them. This breaks the binding "organization that authenticated == repository/commit that is written."

### Finding Description
`verify_signature` in [1](#0-0)  resolves the signing secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived purely from the attacker-supplied payload: [2](#0-1) . The HMAC check only proves the request was signed with the webhook secret belonging to *whatever organization the attacker named in the body*, not that the body's other fields (repository/commit) actually belong to that organization.

Once the signature is accepted, dispatch goes straight to registered handlers with the raw parsed JSON: [3](#0-2) . For the `status` event, `StatusHandler#process` resolves the target purely by commit SHA, with no scoping to the organization/repository that was authenticated: [4](#0-3) . `Commit.create_status_from_github!` then persists a new status row that feeds directly into the commit's deployability computation: [5](#0-4)  and [6](#0-5) .

Because the base `Handler` class already demonstrates the intended scoping pattern — resolving `stacks` from `payload.dig('repository', 'full_name')` [7](#0-6)  — but `StatusHandler` deliberately bypasses `stacks` and queries `Commit` unscoped, this is a genuine binding break, not a hypothetical: the organization whose secret authenticated the request is never checked against the repository/stack that owns the commit being mutated.

Multi-tenant Shipit deployments configure a `webhook_secret` per organization, as shown in the fixture config listing multiple independent orgs each with their own secret: [8](#0-7) . Any organization admin who legitimately configures their own GitHub App integration knows (or can set) their own org's `webhook_secret` and can therefore produce a validly-signed webhook body of arbitrary content.

### Impact Explanation
An attacker who controls a GitHub organization that has been legitimately onboarded to a shared Shipit instance (and thus knows their own `webhook_secret`) can sign a forged `status` event payload:
- `repository.owner.login` = their own org (so `verify_signature` selects and validates against *their* secret)
- `sha` = the HEAD commit SHA of a completely unrelated, victim-owned stack tracked on the same instance
- `state` = `success`

Because `StatusHandler` looks up `Commit.where(sha: ...)` with no repository/organization scoping, this forges a green CI status on a commit belonging to a repository the attacker has no access to. If that stack has `continuous_deployment?` enabled and CI gating (`blocking_statuses`/`required_statuses`) rather than `ignore_ci?`, this can flip `deployable?` to true and trigger `schedule_continuous_delivery` — leading to an **unauthorized deploy** of that commit, bypassing the victim's actual CI requirements entirely. This matches the report's Critical impact bucket ("unauthorized deploy").

### Likelihood Explanation
Requires only that the attacker legitimately administers one GitHub organization already trusted by the shared Shipit instance (a realistic multi-tenant deployment scenario, evidenced by the multi-org secrets config file) and knows the victim's target commit SHA (visible via public GitHub API/UI in the vast majority of cases). No access to the victim's webhook secret, GitHub App, or repository is needed — only cross-tenant knowledge of a SHA and control of one's own org's secret, which the attacker legitimately possesses.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the `stacks` derived from `payload.dig('repository', 'full_name')` (as the base `Handler` class already provides), rather than querying `Commit` globally by SHA. Additionally, `verify_signature` should confirm that the organization used to resolve the webhook secret matches the organization embedded in `repository.full_name`, not just `repository.owner.login`, to prevent any handler from silently acting cross-organization.

### Proof of Concept
1. Attacker legitimately owns GitHub org `attacker-org`, added to the shared Shipit instance with `webhook_secret = S`.
2. Attacker crafts JSON body:
```json
{
  "sha": "<victim-stack-head-sha>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC check passes (attacker knows `S`).
5. `StatusHandler#process` runs `Commit.where(sha: "<victim-stack-head-sha>")` — matches the victim's commit regardless of organization — and calls `create_status_from_github!`, injecting a forged `success` status.
6. If the victim stack has continuous deployment enabled, `Commit#schedule_continuous_delivery` fires, deploying the victim's commit based on the forged status.
