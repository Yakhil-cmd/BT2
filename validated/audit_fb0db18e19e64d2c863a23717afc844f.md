### Title
Uncaught exception on malformed c-hash triggers global process crash — ([File: chash.js])

### Summary
`chash.isChashValid()` decodes an attacker-controlled address/hash string and then calls internal parsing helpers that `throw Error(...)` synchronously on any length mismatch. Only the initial decode call is wrapped in `try/catch`; the subsequent parsing is not. Because ocore installs a global `uncaughtException` handler that deliberately re-throws to crash the whole node process, any code path that reaches this unguarded throw from unprivileged, attacker-supplied data results in a full node crash — the same bug class as CVE-2020-35471 (Envoy mishandling malformed/truncated input causing a segfault instead of a graceful reject).

### Finding Description
`chash.js` validates encoded chashes (used for addresses, and other 32/48-char encoded hash fields) like this: [1](#0-0) 

The check on line 156-162 only guards the decode step (`base32.decode`/`Buffer.from(...,'base64')`). If decoding *succeeds* but yields a buffer whose bit-length is not exactly 160 or 288 (e.g. because the underlying decoder is lenient about invalid/padding characters and silently produces a shorter/longer buffer), the subsequent, unguarded call to `separateIntoCleanDataAndChecksum()` throws synchronously: [2](#0-1) 

This exception is not caught anywhere between `isChashValid()` and its callers (`isValidChash`/`isValidAddress`/`isValidAddressAnyCase` in `validation_utils.js`): [3](#0-2) 

These helpers are invoked deep inside unit/message validation (author addresses, output addresses, AA definitions, device addresses, etc.) for content supplied directly by an unprivileged unit poster. If it propagates as an uncaught exception, `network.js` explicitly turns any uncaught exception into a full process crash by design: [4](#0-3) 

This mirrors the Envoy bug class: a peer/attacker supplies malformed/inconsistent-length data (there, a truncated/oversized UDP datagram; here, a chash string that decodes to an unexpected bit length), and the software crashes instead of cleanly rejecting the input.

### Impact Explanation
If reachable, this is a full node-crash Denial of Service triggerable by any unprivileged party who can get a unit (or device/pairing message) containing a crafted address/hash string in front of validation code. Because the crash handler intentionally re-throws (`throw err`) to kill the process "to avoid ending up in an inconsistent state," every hub/full node that processes the malicious unit would crash and require manual restart, matching the "network unable to confirm new units" impact criterion if triggered widely.

### Likelihood Explanation
Likelihood is **uncertain and not fully proven** within the scope of this analysis. The vulnerable code path depends entirely on whether the underlying decoders (`thirty-two`'s `base32.decode` for 32-character chashes, or `Buffer.from(str, 'base64')` for 48-character chashes) can be coerced into returning a buffer whose length differs from the expected 20 or 36 bytes when fed a same-length-but-malformed string (e.g. embedded `=` padding, non-alphabet characters). I was not able to inspect the `thirty-two` package's decode implementation or fully trace every call site of the 288-bit (48-char) chash within the tool budget available, so I cannot confirm with certainty that a length mismatch is actually achievable from attacker input, only that **if** it is, there is no defense-in-depth catch and the process-wide crash handler will bring down the whole node. This should be treated as a code-hardening finding (missing try/catch around `separateIntoCleanDataAndChecksum`/`bin2buffer` in `isChashValid`) rather than a confirmed exploit chain.

### Recommendation
- Wrap the entire body of `isChashValid()` (not just the initial decode) in `try/catch`, returning `false` on any thrown error instead of letting it propagate.
- Audit `separateIntoCleanDataAndChecksum` and `mixChecksumIntoCleanData` to return an error value rather than `throw` when given attacker-reachable input.
- More generally, review other unguarded `throw Error(...)` statements in parsing helpers (`chash.js`, `object_hash.js`, `signature.js` PEM parsing) that are reachable from unit/message content, given that any uncaught exception during validation crashes the entire process by design (`network.js` uncaughtException handler).

### Proof of Concept
Not conclusively demonstrable without confirming the exact leniency behavior of the `thirty-two` base32 decoder and every 48-char chash call site; a full PoC would require crafting a base32/base64 string of the correct external length (32 or 48 chars) that nonetheless decodes to a buffer of the wrong bit-length, then submitting it as an address/hash field in a unit or device message so it reaches `isValidAddress`/`isValidChash` during validation, triggering the uncaught throw and process crash via `network.js`'s `uncaughtException` handler.
