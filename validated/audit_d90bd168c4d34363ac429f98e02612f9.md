### Title
API clients can impersonate arbitrary Shipit users via the unauthenticated `X-Shipit-User` header, forging attribution on deploys, rollbacks, locks, task triggers and merges - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::Api::BaseController#current_user` resolves the acting user solely from the client-supplied `X-Shipit-User` HTTP header, with no verification that the caller (identified only by an `ApiClient` token) is actually that user. Any holder of a valid `ApiClient` token can set this header to the login of any existing `User` (e.g., an admin or a member of a privileged GitHub team) and the resulting privileged action - deploy, rollback, lock, task trigger/abort, merge request - will be recorded and attributed to the impersonated user, not the true caller.

### Finding Description
`identify_user` looks up a `User` purely by matching the `X-Shipit-User` header value against `login`, with no cryptographic binding (no signature, no session, no OAuth check) tying that header to the authenticated `ApiClient`: [1](#0-0) 

Authentication of the request itself only verifies the `ApiClient` token via Basic Auth against `Shipit.api_clients_secret`: [2](#0-1) 

The two concepts are never cross-checked: `ApiClient#creator` (the user that generated the token) is not compared against the `X-Shipit-User` value used as `current_user`: [3](#0-2) 

This `current_user` value is then passed as the acting/authoring user into multiple privileged, trust-sensitive operations:
- Deploys: `stack.trigger_deploy(commit, current_user, ...)` [4](#0-3) 
- Rollbacks / task aborts: `active_task.abort!(aborted_by: current_user, ...)` and `deploy.trigger_rollback(current_user, ...)` [5](#0-4) 
- Stack locking: `stack.lock(params.reason, current_user)` [6](#0-5) 
- Task triggering/aborting: `stack.trigger_task(params[:task_name], current_user, ...)` and `task.abort!(aborted_by: current_user)` [7](#0-6) 
- Merge requests: `MergeRequest.request_merge!(stack, params[:id], current_user)` [8](#0-7) , which records the impersonated identity into the git merge commit message via `Merge-Requested-By` [9](#0-8) 

This mirrors the reported bug class: the request carries an authenticated credential (the `ApiClient` token, analogous to the flash-loan caller) that is authorized only to perform an operation (deploy/lock/merge on a stack), but a separate, unauthenticated payload field (`X-Shipit-User`, analogous to the unchecked `_receiver`) determines *whose identity* the operation is executed and attributed under. The binding that should hold - `ApiClient.creator == current_user used for the action` - is never enforced, so `authenticated_client ≠ acting_user` for any client with the relevant permission scope.

### Impact Explanation
Any party possessing a valid `ApiClient` token (which can be scoped narrowly, e.g. only `deploy:stack` for one specific stack) can forge the identity of any other `User` in the Shipit database for that operation. Consequences:
- Misattribution/spoofing of who performed a deploy, rollback, lock, or merge - undermining audit trails and any downstream logic or reporting that trusts `Task#user`/`MergeRequest#merge_requested_by`.
- If any authorization or trust decision elsewhere keys off the acting `User` (e.g., team-based checks against `Shipit.github_teams`, or notifications/ownership tied to the author), this impersonation escalates privilege by attributing the action to a user with more standing than the real caller, satisfying the "escalation into `Shipit.github_teams` authorization"-class High severity impact.
- It enables blaming/implicating an innocent user for a deploy/rollback/merge they never triggered, and defeats accountability controls Shipit exposes to teams that rely on `SHIPIT_USER`/author fields.

### Likelihood Explanation
Reachable by any actor holding a legitimate `ApiClient` credential, regardless of the specific permission scope granted (the impersonation happens in `current_user`, independent of `require_permission`). No GitHub write access, session, or webhook secret is required beyond the API token itself; only setting one HTTP header is needed, making exploitation trivial once any valid token is available (which is the expected way to call this API programmatically, e.g. via CI systems, so a compromised/leaked lower-privilege token yields high-value impersonation).

### Recommendation
Do not trust `X-Shipit-User` as an unauthenticated identity claim. Either bind API tokens 1:1 to a `User` and derive `current_user` from `ApiClient#creator`, or require that `X-Shipit-User` match `api_client.creator.login` (rejecting mismatches), or introduce a signed/verifiable per-user credential for on-behalf-of calls with explicit delegation records instead of a bare header lookup.

### Proof of Concept
1. Obtain any valid `ApiClient` authentication token scoped only to `deploy:stack` for stack `acme/webapp` (e.g., a CI token intentionally handed to a low-trust automation).
2. Send: `POST /api/stacks/acme/production/webapp/deploys` with `Authorization: Basic <base64(token)>` and header `X-Shipit-User: admin-login` and body `{"sha": "<commit>"}`.
3. `identify_user` resolves `current_user` to the `User` with login `admin-login` purely from the header [10](#0-9) , and `DeploysController#create` records the deploy as triggered by `admin-login` [4](#0-3) , even though the real caller only holds a low-privilege token and is not `admin-login`.
