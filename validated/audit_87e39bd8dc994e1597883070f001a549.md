### Title
Unbounded recursive traversal of circular shared-address signing paths causes indefinite hang / stack exhaustion - (File: wallet_defined_by_addresses.js)

### Summary
`readAllControlAddresses()` in `wallet_defined_by_addresses.js` recursively expands the set of "control addresses" (addresses that can sign for a shared/multisig address) by repeatedly querying `shared_address_signing_paths` and recursing on every newly discovered signer address, with no cycle/visited-set detection. This is directly analogous to the CVE-2014-7970 bug class: a tree/graph traversal that does not defend against a self-referential (cyclic) structure, leading to an unbounded loop.

### Finding Description
`readAllControlAddresses` takes a starting list of shared addresses, looks up their signer addresses via `shared_address_signing_paths`, and recurses with the newly found addresses as the next input, unioning results as it goes: [1](#0-0) 

There is no tracking of already-visited addresses passed into the recursive call — only `_.union` is applied to the *final results*, not to the *set of addresses fed into the next recursive query*. If a shared address `A`'s signer set includes shared address `B`, and `B`'s signer set includes `A` (a two-cycle in `shared_address_signing_paths`), each recursive call keeps rediscovering the other address and calls itself again indefinitely.

The entries in `shared_address_signing_paths` are populated from data supplied by a paired device (an unprivileged counterparty), via `handleNewSharedAddress` → `addNewSharedAddress`, which inserts rows straight from the message body’s `signers` map without any check that the resulting shared-address definition graph is acyclic: [2](#0-1) [3](#0-2) 

`handleNewSharedAddress` validates the definition tree itself via `Definition.validateDefinition` (which is depth/complexity bounded, see `MAX_COMPLEXITY`/`MAX_OPS` checks in `definition.js`), but that validation only walks the boolean-expression tree of a *single* address definition. It has no knowledge of, and cannot prevent, a second shared address elsewhere being defined so that its `shared_address_signing_paths` row points back to the first address as a "signer", because that relationship is established purely by the `signers` map supplied in the `new_shared_address` device message, not by anything enforced inside the address's own boolean definition (an `'address', X` leaf just names another address; nothing forbids `X`'s own registered "controlling" shared address ending up including the original address as a controller through the `shared_address_signing_paths` table).

Once such a two-cycle exists in the table, any code path that calls `readAllControlAddresses` (used e.g. by wallet balance/control-address enumeration logic in `wallet.js`) recurses forever, exhausting the call stack / event loop and hanging the node process for that operation.

This mirrors the pivot_root CVE: a self-referential relationship (there, `.`/`.` arguments; here, `A`↔`B` cross-referencing shared addresses) is not detected before the code performs an unbounded traversal, producing a denial-of-service loop.

### Impact Explanation
Reaching this bug requires only that a paired device (a normal, unprivileged wallet correspondent) sends crafted `new_shared_address` messages establishing a circular control relationship between two shared addresses. Once established, any subsequent operation that calls `readAllControlAddresses` (address/balance/control enumeration) on the victim wallet enters infinite recursion, hanging that operation and potentially the whole Node.js event loop/process. This can freeze the victim's wallet functionality — e.g., its ability to determine which addresses/private chains to forward, or block wallet-level checks that gate spending — effectively freezing funds held under shared addresses until the process is restarted, and preventing the wallet from completing operations tied to those addresses.

### Likelihood Explanation
The cycle can be constructed entirely by a correspondent device sending two `new_shared_address` messages that reference each other's addresses as signers — no special privileges, no need to broadcast a unit, no consensus involvement. `handleNewSharedAddress` performs structural validation of each individual definition but never checks the `shared_address_signing_paths` graph across multiple shared addresses for cycles, so nothing currently prevents this construction.

### Recommendation
In `readAllControlAddresses`, maintain a cumulative "already seen" set across recursive calls (not just at the end) and stop recursing into addresses already visited, e.g. pass an accumulator of visited addresses and filter `arrControlAddresses`/`arrControlDeviceAddresses` against it before recursing. Additionally, consider validating at `handleNewSharedAddress`/`addNewSharedAddress` time that inserting a new `shared_address_signing_paths` mapping does not create a cycle back to an address that (transitively) controls the new shared address.

### Proof of Concept
1. Device X creates shared address `A` whose `signers` map designates shared address `B` as a co-signer/member address (registered via `handleNewSharedAddress` → `shared_address_signing_paths` row: shared_address=A, address=B).
2. Device X (or a colluding second device) also creates shared address `B` whose `signers` map designates `A` as a co-signer/member address (shared_address=B, address=A).
3. Both `new_shared_address` messages are accepted by the victim's wallet since each individual definition passes `Definition.validateDefinition` in isolation.
4. Any later call to `wallet_defined_by_addresses.readAllControlAddresses(conn, [A], cb)` queries signers of `A` → gets `B`; recurses on `[B]` → queries signers of `B` → gets `A`; recurses on `[A]` → ... indefinitely, hanging the calling code path.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
