This confirms the mismatch: `Handler#stacks` (base class used by all webhook handlers, including push, status, check_suite, membership, pull_request, etc.) resolves the target repository purely from `payload.dig('repository', 'full_name')`, while `WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC against using a *different* field: `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`).### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but all handlers act on the repository named in `repository.full_name` — allowing cross-organization/cross-repository writes in multi-App deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the closest reachable analog to the `signId`/`uuid` mismatch: the field used to select and validate the cryptographic proof (which GitHub App/secret authenticated the request) is not the same field that is later trusted to decide which resource the request is allowed to act on.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration (and therefore the HMAC secret) using a value taken straight from the untrusted, attacker-suppliable JSON body: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Meanwhile, every webhook `Handler` subclass (push, pull_request opened/closed/labeled/reopened/unlabeled/assigned/edited, review-stack adapter, etc.) resolves the *actual repository to act on* from a completely different JSON field, `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Concrete example, `PushHandler`, which triggers `stack.sync_github` for every non-archived stack matching the branch, and `PullRequest::ClosedHandler`, which archives review stacks: [4](#0-3) [5](#0-4) 

`Shipit.github(organization:)` supports independently-configured GitHub Apps per organization, each with its own optional `webhook_secret` (documented in `docs/setup.md` and exercised by the multi-org fixture `secrets_double_github_app.yml`), and `verify_webhook_signature` explicitly treats an absent secret as automatically-valid: [6](#0-5) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

Because the org used for signature selection (`repository.owner.login`) and the repo used for the actual write (`repository.full_name`) are two independent, attacker-controlled JSON fields inside the very same unauthenticated request body, an attacker can craft a payload where:
- `repository.owner.login` = an organization configured in Shipit *without* a `webhook_secret` (or one the attacker already knows), so `verify_signature` passes trivially, and
- `repository.full_name` = `victim-org/victim-repo`, a completely different organization's tracked repository.

The controller only checks that the *first* organization is known and passes verification; it never confirms that this organization actually owns the repository named in `repository.full_name` that the handler subsequently acts on. This is the same class of bug as the `signId`/`uuid` split: one identifier is cryptographically checked, a different, unchecked identifier is the one actually consumed/acted upon.

### Impact Explanation
In a multi-organization Shipit deployment (a documented, supported configuration), this breaks the equality `organization that authenticated == repository that is written`, allowing an unauthenticated attacker (or one who only knows a weakly-secured/no-secret org's identity) to forge webhook events against stacks belonging to a completely different, unrelated organization. Depending on which event/handler is invoked this can: force `sync_github` refresh, archive review stacks, add/remove PR labels, or manipulate check/commit status — i.e. cross-repository/cross-organization writes performed with the app's own GitHub credentials, without the attacker ever needing that victim organization's secret.

### Likelihood Explanation
Requires the host to configure more than one GitHub App/organization (a first-class, documented feature, see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md` multi-org section) and at least one of those organizations to have `webhook_secret` unset (explicitly supported as "optional" per the setup docs) or otherwise known/guessable. Given `verify_webhook_signature` unconditionally returns `true` for orgs without a secret, exploitation only requires knowing that such an org is configured — no privileged token, session, or webhook secret needed for the *actual target* organization.

### Recommendation
After signature verification succeeds, re-derive the acting organization from `repository.full_name` (the field handlers actually use) and confirm it matches the organization (`repository.owner.login`/`organization.login`) whose secret verified the signature, rejecting the request otherwise. Equivalently, verify the webhook signature using the GitHub App configuration bound to the repository resolved by `full_name`, not a separately attacker-chosen `owner.login`/`organization.login` field.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgOne` (no `webhook_secret` set) and `OrgTwo` (tracks stack `OrgTwo/victim-repo`), matching `test/dummy/config/secrets_double_github_app.yml`.
2. Send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
No valid `X-Hub-Signature` is required since `OrgOne` has no `webhook_secret` — `verify_webhook_signature` returns `true` at [7](#0-6)  and `verify_signature` resolves `Shipit.github(organization: "OrgOne")` at [8](#0-7) .
3. `PushHandler#process` then resolves `Repository.from_github_repo_name("OrgTwo/victim-repo")` and invokes `stack.sync_github(expected_head_sha: ...)` on `OrgTwo`'s stack, an organization whose signing secret the attacker never satisfied.
