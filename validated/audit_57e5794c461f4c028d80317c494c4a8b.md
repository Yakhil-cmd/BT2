### Title
AA payment messages to fixed-denomination assets are silently dropped after state updates commit, causing permanent loss/freezing of AA-held funds - (File: aa_composer.js)

### Summary
`handleTrigger`'s `sendUnit` function in `aa_composer.js` filters out payment messages targeting fixed-denomination (indivisible) assets *after* the AA's state-update formula has already run and been persisted, causing the AA's internal (var-tracked) accounting to diverge permanently from actual on-chain balances, analogous to the reported ERC20 "return false" silent-transfer-failure pattern where accounting is updated but tokens never move.

### Finding Description
In `TalosBaseStrategy#collectProtocolFees`, `protocolFees0`/`protocolFees1` accounting is decremented regardless of whether the ERC20 `transfer()` call actually succeeds, since the return value is unchecked; if the token silently fails, the accounting says the fee was paid but the tokens stay trapped.

The analogous flaw in ocore exists in the AA (Autonomous Agent) response-composition pipeline. `handleTrigger`'s inner `sendUnit` builds the response unit's messages, and for payments referencing non-base assets it inspects `objAsset.fixed_denominations`: [1](#0-0) 

For fixed-denomination assets, the code deliberately does not call `completePaymentPayload` (which would allocate real spendable inputs/outputs) and instead defers, commenting "will skip it later": [2](#0-1) 

Later, after the AA's `executeStateUpdateFormula` (the `state` message, i.e. the oscript logic that updates the AA's own bookkeeping variables such as `var[$key] = var[$key] - trigger.data.amount;`) has already run against the yet-to-be-filtered message list, `sendUnit` filters out any payment messages for fixed-denomination assets and, if no messages remain, calls `handleSuccessfulEmptyResponseUnit(null)`, still treating the trigger as successfully processed: [3](#0-2) 

Because `assetInfos[asset].fixed_denominations` short-circuits before `completePaymentPayload`/`addOutputAddresses`/`completeMessage` run for that message, no `arrConsumedOutputs` entries and no actual unit outputs are ever produced for that asset — the "transfer" silently never happens, exactly like an ERC20 `transfer()` returning `false` without reverting. Yet the state-update formula (which typically decrements an internal balance variable representing what is "owed" to the trigger's sender, as seen in the withdrawal patterns used throughout the codebase, e.g. `var[$key] = var[$key] - trigger.data.amount;`) is executed and committed via `executeStateUpdateFormula`/`validateAndSaveUnit` regardless, since those steps occur after the payment-message construction but the eventual removal of the message only prevents inclusion in `messages`, not the state changes that already ran on the full `messages` list before filtering at line 1356: [4](#0-3) 

This mirrors the standard oscript withdrawal pattern seen in the sample AAs, where the developer trusts that a `payment` message paired with a `state` message to decrement the tracked balance is atomic: [5](#0-4) [6](#0-5) 

If the asset referenced in such a withdrawal case happens to be a fixed-denomination (indivisible) asset, the payment message is unconditionally stripped by ocore's own AA engine while the paired `state` decrement still executes and commits, permanently reducing the user's tracked balance without any coins ever leaving the AA.

### Impact Explanation
Any AA that is designed to hold and pay out fixed-denomination (indivisible) assets — a fully supported, documented asset type in ocore — can never actually send such assets out via a normal `payment` message; the framework silently discards the message while still committing the accompanying state changes. This causes direct, unrecoverable loss of user funds held by the AA (their internal balance is debited but they receive nothing), and permanently traps the underlying indivisible-asset coins inside the AA address with no path to withdraw them through the AA's oscript logic. This satisfies "AA fund loss or freezing."

### Likelihood Explanation
Likelihood is moderate-to-high for any AA author who defines a fixed-denomination asset (a supported, common asset configuration) and writes a withdrawal-style AA (a very common AA pattern, per the shipped sample scripts `a_bank_without_percent.oscript`, `order_book_exchange.oscript`, `sell_asset_for_bytes.oscript`) that pays out that asset type by combining a `payment` message with a `state` message decrementing a balance variable. No malicious actor is even required — a legitimate trigger sender attempting a normal withdrawal from such an AA triggers the bug, and the AA author has no straightforward way in oscript to detect or prevent it since the filtering happens deep inside `aa_composer.js`, invisible to the AA definition.

### Recommendation
`sendUnit` should reject (bounce) the entire trigger with an explicit error as soon as a `payment` message references a `fixed_denominations` asset, *before* `executeStateUpdateFormula`/state changes are committed, rather than silently filtering the message out post-hoc and treating the response as a successful empty response. Equivalently, disallow constructing AA responses that pay fixed-denomination assets at validation time (in `aa_validation.js`) so AA authors get a hard compile-time/definition-time error instead of a silent runtime fund loss, and ensure any code path that strips a payment message also invalidates/reverts any corresponding state changes that assumed the payment succeeded.

### Proof of Concept
1. Define an asset with `fixed_denominations: true` (a normal indivisible/NFT-like asset, supported per `validateAssetDefinition` in `validation.js`).
2. Deploy an AA modeled on the shipped `order_book_exchange.oscript` / `a_bank_without_percent.oscript` withdraw pattern:
```
if: "{trigger.data.withdraw AND trigger.data.asset AND trigger.data.amount AND trigger.data.amount <= var[$key]}"
messages: [
  { app: 'payment', payload: { asset: "{trigger.data.asset}", outputs: [{address: "{trigger.address}", amount: "{trigger.data.amount}"}] } },
  { app: 'state', state: "{ var[$key] = var[$key] - trigger.data.amount; }" }
]
```
3. Have a user deposit the fixed-denomination asset into the AA (credited to `var[$key]` by the AA's deposit logic) and then send a trigger requesting `withdraw` of that asset.
4. In `sendUnit`, the payment message for the fixed-denomination asset is skipped at `aa_composer.js:1327-1328` and later stripped entirely at `aa_composer.js:1356`; if it's the only message, `handleSuccessfulEmptyResponseUnit(null)` is invoked at `aa_composer.js:1360`, and the `state` decrement of `var[$key]` was already computed/committed via `executeStateUpdateFormula` prior to that filtering.
5. Result: the user's tracked `var[$key]` balance is reduced as if withdrawn, but no unit output ever transfers the indivisible asset coins to the user — the funds remain stuck in the AA address indefinitely with no oscript-level way to retry or recover them.
