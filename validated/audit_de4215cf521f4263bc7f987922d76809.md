### Title
Webhook Signature Binds Only the Organization, Not the Repository Being Acted On — Cross-Repository Write via Forged `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The reported bug class is a verification check that inspects one attribute of the caller (contract code size at call time) while the exploitable logic actually depends on a different, unverified attribute (code size during constructor execution). The same "verify A, but act on B" pattern exists in `shipit-engine`'s webhook pipeline: `WebhooksController#verify_signature` authenticates the HMAC signature against the GitHub *organization* derived from `repository.owner.login` (or `organization.login`), but the event handlers that mutate application state resolve the target `Stack`/`Repository` using the *separate* `repository.full_name` field from the same JSON body — with no check that the two agree.

### Finding Description
`WebhooksController#verify_signature` selects which `webhook_secret` to validate the HMAC against solely based on the organization name found in the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the tenant's own `github.<org>.webhook_secret` from `Shipit.secrets`, and `shipit-engine` explicitly supports multiple, independently-configured GitHub orgs/apps in one installation, each with its own secret: [3](#0-2) 

Once the signature passes, `WebhooksController#create` dispatches the entire parsed JSON body to the relevant `Handler`: [4](#0-3) 

Every handler resolves the `Stack`/`Repository` it will mutate using a *different* field of the same payload — `repository.full_name` — not the `repository.owner.login`/`organization.login` value that was used to select the signing secret: [5](#0-4) 

For example, the push handler enqueues a sync job against whatever stack matches `repository.full_name`: [6](#0-5) 

and the `status` event creates `Commit::Status` records keyed off `sha`/`state`/`context` from the payload for the commit belonging to the resolved stack (confirmed by test coverage of the `status` webhook path): [7](#0-6) 

Nothing ties the verified organization to the `repository.full_name` that is actually used to locate and mutate the `Stack`. This is the same class of defect as the report: the check is performed against one property of the request (the signing organization) while the security-relevant action is driven by an unverified, attacker-controlled property in the very same payload (`repository.full_name`).

### Impact Explanation
An attacker who is a legitimate administrator of *any* GitHub organization configured as a tenant in the same multi-tenant Shipit installation (a normal, unprivileged-with-respect-to-other-tenants setup step supported by `lib/shipit.rb#github_organizations`/`#github_app_config`) knows their own org's `webhook_secret`. They can:

1. Compute a valid `X-Hub-Signature` using their own org's secret.
2. Set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` selects and validates against the secret they know.
3. Set `repository.full_name` to a victim organization's repository (e.g., `"victim-org/prod-repo"`).

The signature check passes, and the handler then resolves and mutates the *victim's* `Stack` via `Repository.from_github_repo_name(repository.full_name)`. Depending on the event type this allows:
- Forging `status`/`check_suite` events that mark a specific victim commit `sha` as `success`, which feeds directly into `Commit#deployable?` and can make an otherwise-unreviewed commit eligible for Shipit's Continuous Delivery to auto-deploy it — an **unauthorized deploy**.
- Forcing sync/archive/unarchive actions on victim stacks and review stacks via the push/pull_request handlers.

This crosses the credential/repository boundary the webhook signature is supposed to enforce (tenant A's credentials being used to write tenant B's repository state), matching the "unauthorized deploy" / cross-repository-write impact tier.

### Likelihood Explanation
Likelihood is High for any Shipit deployment that hosts more than one GitHub organization/tenant (a documented, supported configuration — see `config/secrets.development.shopify.yml` and `lib/shipit.rb#github_organizations`). Any tenant admin can mount this attack against any other tenant on the same installation with nothing more than their own legitimate webhook secret and knowledge of the target repository's `full_name` and a commit sha (both public/discoverable via GitHub). No session, API token, or private key belonging to the victim is required.

### Recommendation
In `Handler#stacks`/`Handler#repository_name` (and every subclass that independently re-derives the repository from `params.repository.full_name`), cross-validate that the organization/owner used to select and verify the webhook signature (`repository.owner.login` / `organization.login`, as used in `WebhooksController#repository_owner`) matches the owner segment of `repository.full_name` before resolving or mutating any `Stack`/`Repository`. Reject the event (e.g., `head(422)`) if they diverge. Alternatively, bind the verification step itself to the exact `repository.full_name` (verify that the resolved `Repository`'s configured organization equals the one whose secret produced a valid signature) rather than trusting the caller-supplied owner field alone.

### Proof of Concept
1. Attacker administers `attacker-org`, which is configured in the Shipit instance with `github.attacker-org.webhook_secret = S`.
2. Attacker crafts a GitHub `status` webhook payload:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/tests",
     "repository": { "full_name": "victim-org/prod-repo", "owner": { "login": "attacker-org" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(S, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, which validates successfully using `S`.
5. `StatusHandler` resolves the target via `payload.dig('repository','full_name')` = `"victim-org/prod-repo"`, finds the real victim `Stack`, and creates a `success` `Status` for the specified `sha`.
6. If Continuous Delivery is enabled on the victim stack, `Commit#deployable?` now returns true for that commit, and Shipit auto-triggers a deploy of attacker-chosen code — an unauthorized deploy achieved purely with the attacker's own tenant credentials.

Note: I was unable to fully read `app/models/shipit/webhooks/handlers/status_handler.rb` and `check_suite_handler.rb` in this session (tool call failed on the final iteration), so the exact param schema of those two handlers is inferred from `test/controllers/webhooks_controller_test.rb` rather than directly confirmed; the core boundary-crossing defect, however, is fully confirmed via `WebhooksController` and the shared `Handler#repository_name` base method, which every handler (including `PushHandler`, all `PullRequest` handlers, and by the same pattern `StatusHandler`/`CheckSuiteHandler`) inherits.
