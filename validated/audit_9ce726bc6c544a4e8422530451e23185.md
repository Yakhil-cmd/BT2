## Analysis

The reference bug is a class of **conditional skip of a security check**: `_verifyUser()` normally is supposed to be gated by nonce handling, but a specific branch (smart-contract wallet) returns early and never reaches `_handleNonces()`. The strongest structurally identical pattern in Shipit is in the webhook signature-verification path: signature verification is supposed to gate *all* processing of an inbound webhook, but a specific configuration branch (an organization configured **without** a `webhook_secret`) causes the check to be skipped entirely, and the very same untrusted payload that bypassed verification is then used, unchanged, to select which GitHub organization "authenticated" the request and which repository/team/membership records get written.

### Root cause

`WebhooksController#verify_signature` picks which GitHub App config (and thus which secret) to verify against using an attacker-controlled field taken straight from the unauthenticated request body, **before** any signature has been checked: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` then **unconditionally accepts** the request if that organization has no `webhook_secret` configured: [3](#0-2) 

This is not a hypothetical misconfiguration — the setup docs and the shipped multi-organization example explicitly document the webhook secret as **optional per organization**: [4](#0-3) [5](#0-4) 

Once `verify_webhook_signature` returns `true` for that org, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` processes the fully attacker-supplied `params` hash with no further authentication: [6](#0-5) 

### The broken binding

`organization that authenticated (the org whose "secret" gated the request — trivially satisfied when unset) != the identity/repository/team that is actually written by the handler using the same forged payload`.

The `membership` webhook handler creates `Team` and `Membership` rows purely from the JSON body's `team` and `member` fields, with no cross-check against the organization used for signature selection: [7](#0-6) 

Because `User#authorized?` grants Shipit access based solely on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`: [8](#0-7) 

an attacker who can address any organization in the Shipit multi-org config that has no `webhook_secret` set can forge a `membership` event naming the configured authorization team's id/slug and their own GitHub login, causing Shipit to create a `Membership` record that grants them access — without ever having been a legitimate member of that team, and without ever presenting a valid signature.

### Title
Webhook signature check is trivially bypassable for GitHub organizations configured without a `webhook_secret`, allowing forged `membership` events to escalate into `Shipit.github_teams` authorization — ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` derives which organization's secret to check against from unauthenticated payload fields, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/unset — a state explicitly supported as "optional" by the multi-organization configuration schema. This lets an unprivileged attacker submit a completely forged webhook body directly to `POST /webhooks` claiming to originate from any configured organization that lacks a secret, bypassing authentication entirely. The same forged, unauthenticated payload is then handed to event handlers (e.g. the `membership` handler) which write `Team`/`Membership` records straight from attacker-controlled data, letting the attacker grant themselves membership in a team that gates Shipit's `Shipit.github_teams` authorization.

### Finding Description
- `verify_signature` reads `repository.owner.login` (or `organization.login`) from the raw, unverified request body to pick the GitHub App config used for verification: [1](#0-0) , [2](#0-1) .
- `verify_webhook_signature` skips HMAC comparison entirely when that org's `webhook_secret` is not configured: [3](#0-2) .
- The setup guide documents the webhook secret as optional, and the shipped multi-org secrets example shows organizations with commented-out/nil secrets as a supported configuration shape: [4](#0-3) , [5](#0-4) .
- Once the (bypassed) check passes, the full, attacker-controlled `params` are dispatched to event handlers with no further authentication: [6](#0-5) .
- The `membership` handler creates/removes `Team`/`Membership` records directly from the payload's `team`/`member` fields (behavior confirmed by tests exercising `POST /webhooks` with `X-Github-Event: membership`): [7](#0-6) .
- Team membership is the sole gate for authorization in `User#authorized?`: [8](#0-7) .

This mirrors the reference bug's structure exactly: a validation step (`_handleNonces()` / HMAC signature check) that is supposed to run unconditionally is skipped along one specific, real-world-reachable code path (smart-contract wallet / organization without a configured secret), and the caller proceeds to treat the unvalidated input as trusted, allowing replay/forgery (nonce reuse / membership forgery).

### Impact Explanation
An unprivileged network attacker who knows (or can enumerate) the name of any Shipit-configured GitHub organization that has no `webhook_secret` set can:
1. Forge arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`) with no credentials whatsoever.
2. Via the `membership` event, insert themselves into a `Team` whose id/slug matches an entry in `Shipit.github_teams`, directly escalating into Shipit's authorization group — this is explicitly listed as a valid High-impact outcome ("escalation into `Shipit.github_teams` authorization").
3. Via `status`/`push`/`check_suite` events, inject fabricated commit statuses/check runs that downstream deploy-safety logic (merge queue, deployability checks) relies on, potentially contributing to unauthorized merges/deploys of stacks belonging to organizations that *do* have secrets configured, since the handler-side repository resolution is independent of which org's secret gated the request.

### Likelihood Explanation
Requires only that the Shipit operator use the (explicitly documented and supported) multi-organization configuration with at least one organization left without a `webhook_secret` — a state the setup docs describe as optional, not discouraged. No GitHub credentials, Shipit session, or API token are needed by the attacker; a single unauthenticated HTTP POST to `/webhooks` suffices.

### Recommendation
Require a non-blank `webhook_secret` for every configured organization and fail closed (reject the request) rather than returning `true` when `webhook_secret` is absent. Additionally, do not let the payload's own `repository.owner.login`/`organization.login` field silently select "no verification" — if no secret is configured for the derived organization, the request should be rejected (422/401), not treated as pre-authenticated.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `victim-org` (has a `webhook_secret`) and `attacker-org` (no `webhook_secret`, per the documented optional setting).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "attacker-org" },
  "team": { "id": <id of the Shipit.github_teams entry>, "slug": "shipit-authorized-team", "name": "Shipit", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required because `repository_owner` resolves to `attacker-org`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally (see `github_app.rb:76-83`).
3. `MembershipHandler` creates a `Membership` linking `attacker-github-login`'s `User` to the targeted `Team` (as demonstrated by the equivalent test flow at `test/controllers/webhooks_controller_test.rb:129-173`).
4. The attacker's account now satisfies `User#authorized?` via `Shipit.github_teams`, achieving authorization escalation without ever authenticating through GitHub OAuth or presenting a valid webhook signature.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
