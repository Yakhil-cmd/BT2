### Title
Silent Error Swallow in `fillAllocated` Causes All Zeroed Treasury KAIA to Be Permanently Burnt Instead of Redistributed — (`File: blockchain/system/rebalance.go`)

---

### Summary

In `blockchain/system/rebalance.go`, the `fillAllocated` function returns `nil` instead of `err` when `GetAllocatedCount` fails. This causes `RebalanceTreasury` to silently proceed with an empty allocation map. At the KIP-103 or KIP-160 hard fork block, all zeroed treasury balances are wiped from state and the entire amount is counted as burnt — with zero KAIA distributed to the intended allocated addresses. There is no recovery path once the hard fork block is processed.

---

### Finding Description

`fillAllocated` at line 219 returns `nil` on the `GetAllocatedCount` error path instead of propagating the error:

```go
// blockchain/system/rebalance.go, line 215-233
func (result *rebalanceResult) fillAllocated(contract RebalanceCaller, state *state.StateDB) error {
    numNewbieBigInt, err := contract.GetAllocatedCount(nil)
    if err != nil {
        logger.Error("Failed to get AllocatedCount from TreasuryRebalance contract", "err", err)
        return nil   // ← BUG: should be `return err`
    }
    ...
}
``` [1](#0-0) 

Because `fillAllocated` returns `nil`, the caller in `RebalanceTreasury` never sees the error:

```go
if err = result.fillAllocated(caller, state); err != nil {
    return result, err   // never reached
}
``` [2](#0-1) 

Execution then continues with `result.After.Allocated` being an empty map. `totalAllocatedBalance()` returns 0.

**Validation 4** — the only guard that could catch this — is gated on `isKIP103`:

```go
if isKIP103 && totalZeroedAmount.Cmp(totalAllocatedAmount) < 0 {
    return result, ErrRebalanceNotEnoughBalance
}
``` [3](#0-2) 

With `totalAllocatedAmount == 0`, the condition `totalZeroedAmount < 0` is always false, so the guard never fires for either KIP-103 or KIP-160.

Execution then proceeds:

- **Execution 1**: All zeroed addresses have their balances set to `0` — KAIA is destroyed from those accounts.
- **Execution 2**: The allocated loop iterates over an empty map — no KAIA is distributed.
- **Remainder**: `totalZeroedAmount - 0 = totalZeroedAmount` is added to `result.Burnt`. [4](#0-3) 

The entire zeroed treasury balance is permanently burnt. The `FinalizeState` caller in `kaiax/system/impl/blockstate.go` only logs the error and does not revert state:

```go
rebalanceResult, err := bcsystem.RebalanceTreasury(state, m.Chain, header)
if err != nil {
    logger.Error("failed to execute treasury rebalancing. State not changed", "err", err)
} else {
    ...
}
``` [5](#0-4) 

Since `RebalanceTreasury` returns `nil` error (due to the silent swallow), the `else` branch executes and the corrupted state is committed.

---

### Impact Explanation

All KAIA held by zeroed treasury addresses is permanently destroyed at the hard fork block. The intended allocated recipients receive nothing. The total supply is reduced by the full zeroed amount rather than only the intended remainder. This is an unauthorized burn of system-managed KAIA funds with no recovery path — the state transition is irreversible once the fork block is finalized.

**Corrupted value**: `state.GetBalance(zeroedAddr)` → `0` for all zeroed addresses; `state.GetBalance(allocatedAddr)` → unchanged (should have been set to the allocated amount). `result.Burnt` = full zeroed balance instead of `zeroed - allocated`.

---

### Likelihood Explanation

The trigger requires `GetAllocatedCount` to fail at the exact hard fork block while the contract is in `Approved` status. This can occur if the rebalance contract is not correctly deployed at the configured address, if the contract's storage is corrupted, or if the ABI call reverts for any reason. The KIP-103 and KIP-160 hard forks have already executed on mainnet, but the same code path governs any future treasury rebalancing hard fork using the same mechanism. The bug is latent and would activate silently without any on-chain indication of the allocation failure.

---

### Recommendation

Change line 219 in `blockchain/system/rebalance.go` from `return nil` to `return err`:

```go
func (result *rebalanceResult) fillAllocated(contract RebalanceCaller, state *state.StateDB) error {
    numNewbieBigInt, err := contract.GetAllocatedCount(nil)
    if err != nil {
        logger.Error("Failed to get AllocatedCount from TreasuryRebalance contract", "err", err)
        return err   // propagate the error
    }
    ...
}
```

This ensures that any failure to read the allocation list causes `RebalanceTreasury` to return an error, which causes `FinalizeState` to log the failure and leave state unchanged — matching the intended behavior documented in the comment `"State not changed"`.

---

### Proof of Concept

1. Deploy a `TreasuryRebalanceV2` contract at the `Kip160ContractAddress` with zeroed addresses holding non-zero KAIA balances and allocated addresses registered, status set to `Approved`, and `rebalanceBlockNumber` set to block N.
2. Before block N, corrupt or replace the contract so that `getAllocatedCount()` reverts (e.g., deploy a contract at the same address that has no `getAllocatedCount` function).
3. Mine block N (the KIP-160 fork block).
4. `fillAllocated` calls `GetAllocatedCount`, which fails; it returns `nil`.
5. `RebalanceTreasury` proceeds: zeroed addresses are set to balance 0; allocated addresses are untouched; `result.Burnt` = full zeroed amount.
6. `FinalizeState` sees no error and commits the state.
7. Observe: zeroed addresses have balance 0; allocated addresses have their pre-fork balances (not the intended allocated amounts); total KAIA supply is reduced by the full zeroed amount. [6](#0-5) [7](#0-6) [5](#0-4)
