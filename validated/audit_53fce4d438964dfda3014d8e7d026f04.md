### Title
Author identity binding in `find_or_create_author_from_github_commit` is derived from unauthenticated commit-message text rather than a verified `MergeRequest#merge_requested_by` record - (File: app/models/shipit/user.rb)

### Summary
`Shipit::User.find_or_create_author_from_github_commit` binds a `Commit`'s `author_id` to whatever GitHub login appears after a `Merge-Requested-By:` trailer in the raw commit message, and does an unconditional `find_or_create_by_login!` on that string. This trusts free-text supplied by whoever authored the commit, with no cross-check against Shipit's own `MergeRequest` record (the only place that trailer is supposed to be generated), unlike the safer, DB-backed override in `Commit#identify_merge_request`.

### Finding Description
The broken binding is: `commit.author_id == User row of the person who actually pushed/authored that git commit`. `find_or_create_author_from_github_commit` breaks this by instead computing `commit.author_id == User.find_or_create_by_login!(regex_match_from_commit.message)`: [1](#0-0) 

This runs unconditionally inside `Commit.from_github`, which is the code path used whenever Shipit ingests a commit from GitHub (via sync jobs / push handling): [2](#0-1) 

There *is* a safer mechanism elsewhere in the same file — `Commit#identify_merge_request` — which only trusts `merge_requested_by` when it resolves an actual `Shipit::MergeRequest` row already stored in the database (created through `MergeRequest.request_merge!`, which requires a real Shipit session/user): [3](#0-2) [4](#0-3) 

But this safe override only fires `before_create` and only when `message_parser.pull_request?` resolves to a `MergeRequest` row that Shipit itself created (`stack.merge_requests.find_by(number: ...)`). If the commit doesn't match a `MergeRequest` Shipit already knows about (e.g., a direct push to the tracked branch, or a PR merged through the normal GitHub "Merge" button rather than Shipit's merge queue), the attribution set by `find_or_create_author_from_github_commit` is never corrected and stands as the final `author_id`.

Exploit flow: an attacker who can get a commit with the message trailer `Merge-Requested-By: <victim-login>` onto the branch that a Shipit `Stack` tracks (e.g., by having write access to that branch, or by a maintainer merging their PR via ordinary GitHub UI rather than through Shipit's merge queue) causes Shipit's ingestion (`Commit.from_github`) to call `find_or_create_by_login!(victim-login)`, which returns the victim's *existing* `Shipit::User` row — including their `github_access_token` and team memberships — and assigns it as `author_id` on the commit, with zero cross-check that the victim ever interacted with Shipit or approved anything.

Existing guards do not prevent this: webhook signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) only proves the payload came from GitHub, not that the commit *content* (message text) is trustworthy — GitHub faithfully relays whatever commit message the committer wrote. `force_github_authentication`, `User#authorized?`, and `require_permission!` guard Shipit's own UI/API actions, not commit ingestion from GitHub's API. Model validations on `Repository`/`Stack` don't touch commit messages.

### Impact Explanation
An attacker who can land a crafted commit message onto a tracked branch causes Shipit to record that a privileged user (e.g., a member of `Shipit.github_teams`) authored the commit, without that user's knowledge or consent. Since `author_id` feeds `stacks_contributed_to`, `repositories_contributed_to`, and any audit/attribution logic keyed on commit author, this allows falsifying who is credited with a change on that stack. This is repeatable per repository the attacker can get a crafted commit merged/pushed into. It does not, however, directly forge a webhook, bypass authentication for a Shipit session/API token, or itself trigger a `PTY.spawn` command or `deployable?` bypass — `deployable?` is driven by CI status/lock state, not by `author_id`. The severity is best characterized as unauthorized attribution/spoofing of commit authorship (a real integrity bug) rather than a full "unauthorized deploy/merge" or credential-exfiltration Critical, since no additional privileged action is shown to be unlocked solely by `author_id` in the reachable code paths reviewed.

### Likelihood Explanation
Exploitation requires the attacker's crafted commit message to actually land in the git history of a branch that a Shipit `Stack` is tracking — this needs either direct push access to that branch, or a maintainer merging the attacker's PR through the ordinary GitHub UI (bypassing Shipit's merge queue, where the trusted `MergeRequest#merge_requested_by` override would otherwise correct the author). Under the strict "unprivileged, own-fork-only" attacker model given in the rules, the attacker alone cannot get a commit onto the tracked branch of someone else's repository merely by opening a PR from their fork — a maintainer action or existing write access is required. This makes the finding real but conditioned on a merge/push happening outside Shipit's own merge-queue flow, which is a plausible but not fully attacker-controlled precondition.

### Recommendation
Do not trust the `Merge-Requested-By:` trailer parsed from arbitrary commit message text. Only trust it when it corresponds to a `Shipit::MergeRequest` row that Shipit itself created and validated (mirroring the check already done in `Commit#identify_merge_request`). Remove or gate the regex-based lookup in `User.find_or_create_author_from_github_commit` behind verification against `stack.merge_requests.find_by(number:).merge_requested_by`, falling back to the actual git author identity (`github_commit.author`/`github_commit.commit.author`) in all other cases.

### Proof of Concept
Add a minitest under `test/models/users_test.rb` (or `test/models/commits_test.rb`) style:
1. Create a privileged `Shipit::User` (`victim`) with `github_access_token` set and team membership.
2. Build a stubbed `github_commit` whose `commit.message` is `"Some change\n\nMerge-Requested-By: victim\n"` and whose actual `author`/`committer` GitHub identity is a different, attacker-controlled login.
3. Assert: `Shipit::User.find_or_create_author_from_github_commit(github_commit) == victim` — demonstrating `author_id` is bound to `victim.id` even though `github_commit.author.login != victim.login`.
4. Assert the equality claimed as safe (`commit.author_id == actual git author of the commit`) is false: `victim.login != github_commit.author.login`, proving the binding divergence.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
