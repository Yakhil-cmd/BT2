### Title
Webhook signature verification uses the payload's `repository.owner.login` while write-path handlers act on the payload's unrelated `repository.full_name` field, allowing cross-organization webhook forgery when any configured org omits a `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `lib/shipit.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to authenticate an incoming webhook based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), a field taken straight from the unauthenticated JSON body. `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every handler (push, status, check_suite, etc.) to locate the target `Stack`/`Repository` to act on, reads a *different* body field: `payload.dig('repository', 'full_name')`. In a multi-organization deployment where at least one configured GitHub organization has no `webhook_secret` set (an explicitly supported, documented configuration), signature verification for that organization is a no-op (`return true unless webhook_secret`). An attacker can therefore submit a forged webhook whose `repository.owner.login` names the secret-less organization (to trivially pass "verification") while `repository.full_name` names a completely different, secured organization's repository, causing Shipit to act (sync stacks, trigger `GithubSyncJob`, update commit statuses, refresh check runs, etc.) on that other repository's stacks without ever validating a signature tied to it.

### Finding Description
The binding that should hold is: **organization that authenticated == organization whose repository is written**. This engine breaks it.

- `verify_signature` picks the signing organization purely from attacker-supplied JSON, before any cryptographic check: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` trivially returns `true` whenever the selected organization has no `webhook_secret` configured, i.e., no HMAC check is performed at all for that org: [3](#0-2) 

- `Shipit.github(organization:)` resolves per-organization config from `secrets.github` keyed by org name in the multi-org schema, and raises `GithubOrganizationUnknown` only if the org name is not present at all — it does not require that org to have any relationship to the repository the payload claims to affect: [4](#0-3) 

- The documented setup explicitly allows a `webhook_secret` to be left blank per organization, and the sample multi-org config ships with `webhook_secret: # nil` for every org: [5](#0-4) [6](#0-5) 

- Once past `verify_signature`, every handler resolves the target `Stack` using `repository.full_name`, a field never checked against the organization used to select the (possibly no-op) signature check: [7](#0-6) 

- For example the push handler drives real `sync_github` behaviour on any stack found this way: [8](#0-7) 

Because HMAC verification, when it does execute, covers the whole raw body (so `repository.full_name` normally would be implicitly trusted along with `repository.owner.login`), the vulnerability only manifests when verification is skipped entirely for the attacker-chosen organization — i.e., exactly the secret-less-org case. In that case there is no cryptographic guarantee at all binding *any* field of the payload, including `repository.full_name`, to a legitimate GitHub sender.

### Impact Explanation
An attacker with no credentials can send a POST to `/webhooks` with `X-Github-Event: push` (or `status`, `check_suite`, `membership`, `pull_request`, etc.), setting `repository.owner.login` to any organization configured on the instance without a `webhook_secret`, and `repository.full_name` to the full name of a *different, secured* organization's repository that has a Stack in Shipit. This forged event will pass `verify_signature` trivially and reach the handler, which will act on the targeted repository's stacks — e.g., `PushHandler` calling `stack.sync_github(expected_head_sha: params.after)` for arbitrary attacker-chosen SHAs on any branch of the targeted stack, or `StatusHandler`/`CheckSuiteHandler` manipulating deploy-gating commit statuses/check runs used to decide whether a deploy is safe to ship. Since Shipit stacks can be configured for continuous deployment triggered by such state changes, this can lead to an unauthorized deploy — matching the Critical impact bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only network access to the public `/webhooks` endpoint (no session, token, or GitHub credentials) and a target deployment using the multi-organization GitHub config schema with at least one org lacking a `webhook_secret` — a configuration explicitly presented as valid/optional in this engine's own setup documentation and shipped sample config. No social engineering, TLS interception, or privileged access is needed.

### Recommendation
Do not let `repository.full_name` (or any other trust-sensitive payload field consumed by handlers) be independent of the organization whose secret validated the request. Options:
1. After signature verification, cross-check that the resolved `repository_owner`/`organization.login` used for verification matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches.
2. Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), removing the trivial-pass path entirely, or at minimum warn/refuse to boot when any org lacks one in multi-org mode.

### Proof of Concept
Given a multi-org `secrets.github` config such as:
```yaml
github:
  attacker_org:
    app_id: 1
    installation_id: 1
    webhook_secret: # blank/nil
  victim_org:
    app_id: 2
    installation_id: 2
    webhook_secret: "s3cr3t"
```
and a Stack backed by repository `victim_org/protected-repo`, send:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json
(no X-Hub-Signature header needed)

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker_org" },
    "full_name": "victim_org/protected-repo"
  }
}
```
`repository_owner` resolves to `attacker_org` [2](#0-1)  → `Shipit.github(organization: "attacker_org")` loads a `GitHubApp` with `webhook_secret` blank → `verify_webhook_signature` returns `true` unconditionally [3](#0-2)  → request passes → `PushHandler` resolves stacks via `repository.full_name = "victim_org/protected-repo"` [7](#0-6)  and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [8](#0-7) , without any signature ever having covered a request genuinely originating from `victim_org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
