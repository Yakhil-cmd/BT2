## Analog Found

### Title
Unchecked multiplication in indivisible-asset cap validation allows declared `cap` to bypass real minted supply - (File: validation.js)

### Summary
CVE-2018-19199 is an integer-overflow-via-unchecked-multiplication bug in uriparser's `UriQuery.c`, where a size/length value is computed by multiplying two attacker-influenced numbers without bounds checking, corrupting a buffer-size computation. `ocore` has a structurally identical unchecked-multiplication flaw in the indivisible-asset definition validator: `denomInfo.count_coins * denomInfo.denomination` is summed into `total_cap_from_denominations` without any bound on `count_coins`, and only `denomination` (not the product, and not `count_coins`) is checked against `constants.MAX_CAP`. [1](#0-0) 

### Finding Description
When an asset issuer posts an `asset` definition message with `fixed_denominations`/`denominations`, each `denomInfo.denomination` is bounded by `constants.MAX_CAP` (9e15) but `denomInfo.count_coins` is only checked with `isPositiveInteger`, which has **no upper bound**: [2](#0-1) 

The validator then computes `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` in plain JS double-precision arithmetic (JS numbers silently lose precision past `Number.MAX_SAFE_INTEGER = 9007199254740991`, analogous to the C integer overflow in the CVE) and only compares this **lossy sum** against `payload.cap` (which is itself capped at `MAX_CAP`): [3](#0-2) [4](#0-3) 

Critically, the exact same `denomination`, `count_coins` values (not the lossy sum) are persisted to `asset_denominations` and used verbatim during real issuance in `indivisible_asset.js`, where `issue_amount = count_coins_to_issue * denomination` is computed per-denomination and summed over the asset's lifetime as coins are actually issued: [5](#0-4) 

Because `count_coins` is unbounded, an attacker can choose denomination/count_coins pairs such that the true product for at least one denomination bucket individually or the true sum across buckets is far larger than `MAX_CAP`/the declared `payload.cap`, while the float-rounded `total_cap_from_denominations` used only for the definition-time equality check coincidentally (or by construction) matches a `cap` value ≤ `MAX_CAP`. The definition is accepted because the validator trusts the corrupted (rounded) sum rather than the true, uncapped per-denomination products that will later be honored coin-by-coin during issuance.

### Impact Explanation
This allows an asset issuer to define a "capped" indivisible asset whose advertised `cap` (relied upon by wallets/counterparties as the maximum total supply) does not reflect the real maximum issuable value, since the real per-denomination `count_coins * denomination` values stored in `asset_denominations` are unbounded and are honored exactly at issuance time (`indivisible_asset.js`). This is a supply-inflation class bug: the network and counterparties can be led to believe the asset's total supply is bounded by `cap`, while the issuer can mint substantially more value than that cap through the uncapped `count_coins` field, defeating the cap guarantee that other logic (private payment auto-destroy validation, uncapped/capped consistency checks, wallets showing "% of cap issued") depends on.

### Likelihood Explanation
Any unprivileged unit poster who is also an asset issuer can construct this asset definition message in a single unit; no privileged role, hub, or other party's cooperation is required. Constructing denomination/count_coins pairs to trigger float precision loss requires only basic arithmetic near `Number.MAX_SAFE_INTEGER` and is deterministic to compute in advance, so exploitation is straightforward. The bug is bounded by the fact that `denomination` itself is checked against `MAX_CAP`, so triggering a divergence requires `count_coins` large enough to push the product over `Number.MAX_SAFE_INTEGER` relative to `MAX_CAP`, which is unbounded and reachable.

### Recommendation
- Bound `denomInfo.count_coins` explicitly (e.g., `count_coins <= constants.MAX_CAP`), not merely `isPositiveInteger`.
- Validate `denomInfo.count_coins * denomInfo.denomination` for overflow/precision-loss before accumulating (e.g., verify the product is below `Number.MAX_SAFE_INTEGER`, or perform the multiplication using an arbitrary precision/BigInt-safe helper and reject if it exceeds `MAX_CAP`).
- Reject the asset definition if any single denomination's `count_coins * denomination` exceeds `constants.MAX_CAP`, in addition to checking the aggregate sum, since the total-supply guarantee depends on every individual bucket being safe, not just the (potentially lossy) sum.

### Proof of Concept
1. Attacker composes an `asset` definition message with `fixed_denominations: true`, `cap: <value> ≤ MAX_CAP`, and a `denominations` array containing entries where `denomination` is close to `MAX_CAP` (e.g. `9e15`) and `count_coins` is set to a value (e.g., `10`) such that the true product `count_coins * denomination` (`9e16`) exceeds `Number.MAX_SAFE_INTEGER`, causing JS float rounding when summed into `total_cap_from_denominations` in `validation.js` (line 2778).
2. Craft additional denomination buckets so the rounded `total_cap_from_denominations` equals the attacker-chosen `payload.cap` (satisfying the check at `validation.js:2790`), even though the true, unrounded per-denomination products sum to a much larger value.
3. Post the unit; validation accepts the asset definition since only the rounded sum is compared to `cap`.
4. Over time, issue coins from the oversized denomination bucket via `indivisible_asset.js` (`issueNextCoin`, lines 516–588), which honors the true (uncapped) `count_coins`/`denomination` values stored in `asset_denominations`, allowing total issued value to exceed the declared `cap`.
