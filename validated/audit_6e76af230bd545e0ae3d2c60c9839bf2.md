### Title
Missing slippage protection in `snowbridge-pallet-system-frontend::add_tip`/`register_token` swap-and-burn path allows sandwich extraction of tip value - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`snowbridge-pallet-system-frontend`, wired into the Asset Hub Westend production runtime (`AssetConversion` pallet as `type Swap`), swaps a user-supplied tip/fee asset for Ether via `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens` while explicitly passing `None` for `amount_out_min` ("No minimum amount required"). This is the direct FRAME analog of the reported `SwapperFTM`/`FujiVaultFTM` issue: a swap executed on behalf of the user with slippage checking disabled, letting anyone sandwich the AMM swap in the same block to extract value that should have gone to the user (and ultimately to the relayer tip / registration fee amount reported to Ethereum).

### Finding Description
In `swap_and_burn` [1](#0-0) , the pallet calls:

```rust
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
```

`None` is forwarded into `pallet_asset_conversion::Pallet::do_swap_exact_tokens_for_tokens`, whose min-out enforcement is entirely conditional on `Some`:

```rust
let amount_out = path.last().map(|(_, a)| *a).ok_or(Error::<T>::InvalidPath)?;
if let Some(amount_out_min) = amount_out_min {
    ensure!(amount_out >= amount_out_min, Error::<T>::ProvidedMinimumNotSufficientForSwap);
}
``` [2](#0-1) 

When `None` is supplied, this check is skipped entirely — functionally identical to the reported EVM pattern of hard-coding `amountOutMin = 0`. The AMM `swap` executes at whatever price the pool currently offers with no floor, exactly mirroring `IUniswapV2Router01.swapExactETHForTokens(0, ...)` in the reported bug.

`swap_and_burn` is reached from two dispatchable entry points on Asset Hub Westend:
- `add_tip(origin, message_id, asset)` — a plain signed extrinsic (`ensure_signed(origin)?`), with no privileged role required [3](#0-2) .
- `register_token(...)` when called by a non-root/non-"here" origin, via `swap_fee_asset_and_burn` → `swap_and_burn` [4](#0-3) .

The pallet is actually configured in the Asset Hub Westend runtime with `type Swap = AssetConversion;` [5](#0-4)  and is included in `construct_runtime!` as `SnowbridgeSystemFrontend: snowbridge_pallet_system_frontend = 36` [6](#0-5) , confirming real runtime wiring, not just test/mock code.

### Impact Explanation
`ether_gained` from the unguarded swap becomes the `amount` field forwarded in the `AddTip`/`RegisterToken` Transact call to BridgeHub [7](#0-6) [8](#0-7) . An attacker who observes a pending `add_tip`/`register_token` extrinsic in the transaction pool can sandwich the underlying `AssetConversion` pool swap (buy the output asset ahead of the victim's swap, let it execute at a worse price, then sell back), extracting the price-impact value that would otherwise have gone to the user as tip/registration-fee value. This is a value-siphoning bug matching the exact bug class of the report (missing slippage checks enabling sandwich extraction), though the value drained per call is bounded by pool depth and per-tx tip size rather than "most values" as in the EVM report's reward-harvesting case.

### Likelihood Explanation
Any signed account on Asset Hub Westend can call `add_tip` with an arbitrary fee asset amount, and any account can trigger `register_token`'s fee-swap path; no privileged role, governance, or compromised keys are needed. Exploitation requires only ordinary MEV/sandwich capability against a public AMM pool (`pallet-asset-conversion`) with a pending extrinsic in the pool — a routine capability for block producers/searchers on any chain with mempool visibility, and does not require flooding, forged inherents, or malicious collators/relayers beyond ordinary transaction ordering.

### Recommendation
Pass a caller-specified, non-`None` `amount_out_min` into `T::Swap::swap_exact_tokens_for_tokens` in `swap_and_burn`, e.g. add an `amount_out_min` (or basis-point slippage tolerance) parameter to `add_tip`/`register_token` that the pallet enforces via the existing `Error::<T>::ProvidedMinimumNotSufficientForSwap` path already present in `pallet_asset_conversion`, mirroring how `AssetConversion::swap_exact_tokens_for_tokens` extrinsic mandates a non-optional `amount_out_min` [9](#0-8) .

### Proof of Concept
No executable PoC was run; this analysis is based on static code review of the wired runtime configuration and pallet logic. A concrete integration reproduction would require: (1) deploying a local Asset Hub Westend test node/emulated chain with a funded `AssetConversion` pool for the tip asset/Ether pair, (2) submitting an `add_tip` extrinsic with a sizeable `tip_amount`, and (3) demonstrating via a preceding/following swap by a second account that `ether_gained` recorded in the `AddTip` Transact call is measurably lower than the pre-sandwich quote (`quote_price_exact_tokens_for_tokens`), with the sandwiching account's balance increasing by the corresponding amount. This was not executed here; deployment evidence is limited to the confirmed runtime wiring (`bridge_to_ethereum_config.rs`, `construct_runtime!`) shown above, and the guard-skip logic in `pallet_asset_conversion::do_swap_exact_tokens_for_tokens`.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
