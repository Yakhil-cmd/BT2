### Title
Cross-organization Team hijack via `github_id`-only lookup in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` resolves the `Team` record to mutate using only the attacker-influenced `team.id` field from the webhook payload, while the webhook signature that authorizes the request is verified against the *organization* field of that same payload. The organization that is cryptographically authenticated is never checked against the organization that owns the `Team` row being written to.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC with, based on a field taken from the JSON body itself: [1](#0-0) [2](#0-1) 

For a `membership` event, there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')`. This means the signature only proves the request was sent by *some* organization's installed GitHub App — specifically the org named in `organization.login` — using that org's own `webhook_secret`, looked up via `Shipit.github(organization:)`: [3](#0-2) 

Once the signature check passes, `MembershipHandler#process` looks up (or creates) the `Team` to mutate using **only** `github_id`, never re-checking that the team's `organization` matches the `organization.login` that was actually authenticated by the signature: [4](#0-3) 

Compare this with `Team.find_or_create_by_handle`, which correctly scopes lookups by `organization` + `slug`: [5](#0-4) 

The binding that should hold is:
`organization authenticated by the webhook signature == organization that owns the Team row being mutated`

`MembershipHandler` breaks this equality: it authenticates organization A (via A's webhook secret) but writes membership into whatever `Team` row already has a matching `github_id`, regardless of which organization created that row. `Team#add_member` simply appends the member with no additional check: [6](#0-5) 

This is the closest analog to the reported "improper storage management" bug class: just as `openLoan()` mutated a shared array using an insufficiently-scoped key (account address) without verifying prior ownership, `find_or_create_team!` mutates a shared `Team` record using an insufficiently-scoped key (`github_id`) without verifying the record belongs to the authenticated organization.

The member being added is also resolved without any organization scoping — `User.find_or_create_by_login!` fetches the user from GitHub via the app's default API client and creates/reuses a global `User` row keyed only by login: [7](#0-6) 

If that `Team` is one referenced in `Shipit.github_teams` (built from `oauth.teams` config), membership in it directly controls application-wide authorization via `User#authorized?`: [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
In a multi-organization Shipit deployment (multiple GitHub Apps/orgs configured under `secrets.github`, each with a distinct `webhook_secret`), an actor who is merely an admin of one of the *less privileged* configured organizations — not a Shipit user, not an `ApiClient` holder, not a member of `Shipit.github_teams` — can cause membership webhooks for their own org to be delivered and correctly signature-verified. If the `team.id` in that payload happens to collide with the `github_id` of an existing `Team` row that belongs to a *different, privileged* organization (e.g., one referenced by `Shipit.github_teams`), `find_or_create_by!(github_id: ...)` will match and mutate that privileged team instead of creating/updating a team scoped to the attacker's own org. This lets the attacker add an arbitrary GitHub login (any user, including themselves) as a member of the privileged team, thereby satisfying `User#authorized?` and gaining full authenticated access to the Shipit instance (escalation into `Shipit.github_teams` authorization) without ever holding a Shipit session, ApiClient token, or the privileged org's own webhook secret.

### Likelihood Explanation
Exploitability is gated by GitHub's team `id` being a GitHub-assigned, globally-unique, effectively non-attacker-controllable integer — the attacker cannot choose an arbitrary `team.id` for their own org's team to force a collision with a specific privileged team's `github_id`. This significantly limits practical exploitation to scenarios where an attacker already controls (or acquires control of) an org holding an old/low team ID that happens to coincide with a privileged team's ID, or where such a collision is otherwise engineered. The underlying code defect (missing organization-scoping on the lookup/write) is real and directly analogous to the reported bug class, but the root cause is a code-review-worthy trust boundary flaw rather than a scenario with an easily demonstrable, reliable exploitation path given GitHub's ID allocation. I was unable to fully verify whether any additional runtime constraint (e.g., uniqueness validation, application-level ID range checks) further limits or aggravates this, and no proof-of-concept beyond code-level tracing could be produced within available tools.

### Recommendation
- Scope the `Team` lookup/creation in `MembershipHandler#find_or_create_team!` by both `github_id` **and** `organization` (matching `params.organization.login`), analogous to `Team.find_or_create_by_handle`.
- After lookup, explicitly assert `team.organization == params.organization.login` before calling `team.add_member`/`team.members.delete`, and raise/drop the event otherwise.
- Consider adding a uniqueness validation on `Team` for `[organization, github_id]` or `[organization, slug]` to prevent silent cross-organization row reuse.

### Proof of Concept
Conceptual trace (no live GitHub access available to fully validate ID collision):
1. Shipit is configured with two GitHub Apps/orgs: `PrivilegedOrg` (referenced in `oauth.teams`, e.g. `PrivilegedOrg/admins`) and `AttackerOrg` (a separate, less-trusted org also installed on the same Shipit instance), each with its own `webhook_secret`.
2. A `Team` row already exists with `github_id: 12345, organization: "PrivilegedOrg", slug: "admins"` (created earlier via `Team.find_or_create_by_handle` / OAuth config sync).
3. The attacker, as an admin of `AttackerOrg`, creates/renames a team in `AttackerOrg` such that GitHub assigns (or the attacker otherwise causes) that team to have `id: 12345`, then adds a user (their own account or an accomplice's) to it.
4. GitHub sends a real, correctly-signed `membership` "added" webhook for `AttackerOrg`, with `team.id = 12345`, `organization.login = "AttackerOrg"`.
5. `WebhooksController#verify_signature` validates the HMAC using `AttackerOrg`'s webhook secret — passes, because the request genuinely came from `AttackerOrg`'s GitHub App installation.
6. `MembershipHandler#find_or_create_team!` runs `Team.find_or_create_by!(github_id: 12345) { ... }` and matches the existing `PrivilegedOrg/admins` row (organization is not part of the lookup).
7. `team.add_member(member)` adds the attacker-controlled user to `PrivilegedOrg/admins`.
8. That user now passes `User#authorized?` and logs into Shipit as a member of `Shipit.github_teams`, gaining full application access.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
