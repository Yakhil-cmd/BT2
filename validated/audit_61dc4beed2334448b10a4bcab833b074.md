## Title
Unlocked race between `storage.readUnitProps()` cache reads and `markMcIndexStable()` cache writes causes a crash-inducing exception (Dom0-style cache corruption DoS) - (File: storage.js)

### Summary
The bug class in CVE-2022-33744 is a classic TOCTOU (time-of-check/time-of-use) race on a shared in-memory index: a reader checks the structure, does something slow (I/O), then the structure is mutated by another path holding a different (or no) lock, leaving the reader's view inconsistent and crashing the process. ocore has an analogous pattern between `storage.readUnitProps()` (read path, invoked from unit validation for any posted unit) and `main_chain.markMcIndexStable()` (write path, invoked from stabilization) which mutate the same in-memory caches `assocStableUnits` / `assocUnstableUnits` without a shared lock guaranteeing atomicity across the check-then-fetch-then-recheck sequence.

### Finding Description
`readUnitProps()` in [1](#0-0)  first checks `assocStableUnits[unit]`/`assocUnstableUnits[unit]`. If absent, it issues an async DB query. When the query resolves, it re-checks the caches and, if a mismatch is found between the freshly queried row and what is now sitting in memory, it unconditionally `throw`s: [2](#0-1) 

This throw happens inside an async DB callback with no surrounding `try/catch`, so it is an uncaught exception that crashes the whole Node.js process for `full` (non-light) nodes.

The mutation side, `markMcIndexStable()`, moves units from `assocUnstableUnits` to `assocStableUnits` synchronously while iterating: [3](#0-2) 

`validation.validate()` only takes a per-author-address lock (`mutex.lock(arrAuthorAddresses, ...)`, [4](#0-3) ), not the `"write"` lock, while `readUnitProps()` is called deep inside validation and message/parent processing for units authored by *any* address, including addresses unrelated to the concurrently stabilizing chain. Meanwhile, `markMcIndexStable()` runs as part of `updateMainChain()`/`saveJoint()`'s write-lock-protected path, but the cache comparison performed by `readUnitProps()` for an in-flight, unlocked read is not synchronized against it: the check `if (assocStableUnits[unit])` (line 1502) can miss, the DB query starts, and by the time it resolves the unit has become stable and is now in `assocStableUnits` written by a different code path/tick, producing the `throw Error("different props: ...")` at line 1533, or the `throw Error("no unstable props of "+unit)` at line 1542 if it was concurrently forgotten/moved.

This is the same class of defect as the Xen rbtree bug: a shared indexing structure (rbtree there, `assocStableUnits`/`assocUnstableUnits` here) is read and later re-validated across an await/callback boundary while another code path is permitted to mutate it without both sides sharing one lock, and the inconsistency manifests as a crash.

### Impact Explanation
A crash of a full node's ocore process is a genuine Denial of Service: the node stops confirming/relaying/validating new units until manually restarted, exactly the "network unable to confirm new units" impact class called out in scope. Because `readUnitProps()` is on the hot path for validating parents, authors and messages of *any* posted unit (payments, AA triggers, asset transfers), an attacker does not need special privileges — merely posting units that reference/interact with units that are near their stabilization point can widen the race window and increase the odds of triggering the crash.

### Likelihood Explanation
This requires a specific, narrow timing window (a unit's stabilization completing in another async tick exactly between the initial cache-miss check and the DB-query callback in `readUnitProps()`), which is naturally rare under light network activity but becomes far more probable under sustained unit posting/validation throughput, similar to how the original Xen bug required "a small race window" repeatedly triggered by unprivileged guest activity. An adversary controlling their own unit-posting rate (multiple concurrent joints referencing units at/near their stability boundary) can deliberately widen exposure to this window.

### Recommendation
Ensure that all reads and writes of `assocStableUnits`/`assocUnstableUnits` that participate in this check-then-fetch-then-recheck pattern are performed under one consistent lock (e.g. always require the `"write"` lock, or a dedicated cache lock) so `readUnitProps()`'s cache check and its DB-driven cache update are atomic with respect to `markMcIndexStable()`'s mutation. Alternatively, replace the `throw Error(...)` consistency assertions in `readUnitProps()` with a graceful re-read/reconciliation path (re-check caches and return the up-to-date value) instead of crashing the process when a benign race is detected.

### Proof of Concept
1. Run a full ocore node under load with many pending/near-stabilizing units.
2. Have unit A trigger `main_chain.updateMainChain()` → `markMcIndexStable()` for a set of units including unit X, moving X from `storage.assocUnstableUnits` to `storage.assocStableUnits` ( [5](#0-4) ) mid-flight.
3. Concurrently, validation of an unrelated unit B (different author) calls `storage.readUnitProps(conn, X, cb)`; the initial synchronous check at [6](#0-5)  misses (X still unstable at check time), so the DB query fires.
4. Before the DB callback returns, step 2 completes and `assocStableUnits[X]` is populated by `markMcIndexStable`.
5. When the DB callback resolves for X (now `is_stable=1` in DB), the code hits the reconciliation branch at [7](#0-6) ; if the two representations of `props` differ even slightly (e.g., timing of `sequence`/`witnessed_level` updates that occur across multiple write steps of stabilization), it throws an uncaught `Error`, crashing the node process.
