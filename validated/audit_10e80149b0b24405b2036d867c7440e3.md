## Title
Merkle leaf/internal-node hash collision ("node-as-leaf") in `merkle.js` allows forging membership proofs used by `is_valid_merkle_proof()` in AA oscript and by the `in merkle` address-definition authentifier - ([File: merkle.js])

### Summary
`merkle.js` hashes a leaf as `hash(element)` and an internal node as `hash(childHashLeft + childHashRight)`, where both `element` and the concatenated child hashes are ordinary strings fed into the same `sha256`-then-base64 `hash()` function. Because the leaf-hashing step and the internal-node-hashing step operate on inputs of the same representation (plain strings, no domain separation or length prefix), an attacker who knows the two child hash values of any internal node in a real tree can pick `element = childHashLeft + childHashRight` and reuse the remaining upper-level siblings to produce a syntactically valid Merkle proof for a value (`element`) that was never an actual tree leaf. This is the same "node-as-leaf" class of bug as the reported Footium issue, where `abi.encode(_to,_amount)` (leaf) and `abi.encode(a,b)` (internal node) share the same encoding and thus collide.

This primitive is exposed to untrusted, attacker-controlled input in two places reachable from ordinary users:

1. **AA oscript `is_valid_merkle_proof()`** - both the `element` and the `proof` (including `siblings` and `index`) are evaluated from arbitrary trigger-supplied expressions, e.g. `trigger.data.element`, `trigger.data.proof`: [5](#0-4) 
An AA author commonly stores a whitelist/allowlist Merkle root in a state variable and checks membership with something like `is_valid_merkle_proof(trigger.data.value, trigger.data.proof) AND trigger.data.proof.root == var['root']`. Because both operands of the check come straight from the trigger sender, the sender can supply a crafted `element` equal to the concatenation of two known internal-node hashes (obtainable simply by rebuilding the same public leaf set with `merkle.getMerkleRoot`/`getMerkleProof`) plus a shortened `siblings` array taken from that internal node up to the root, and the check succeeds even though `value` was never one of the whitelisted leaves.

2. **Address-definition `in merkle` authentifier**, which verifies a caller-supplied serialized proof against a data-feed-published root: [6](#0-5) 
Here `element` is fixed by the address definition, but the attack still applies whenever a definition author lets the "expected value" or root be influenced by external, attacker-observable trees (e.g., federated/oracle-published sets), since the verification logic is identical.

Because leaves and internal nodes are indistinguishable at the byte level (both just concatenated strings hashed with the same function, no leaf/node prefix, no length constraint forcing a leaf-shaped input), any string equal to the raw concatenation of two legitimate sibling hashes is accepted as a legitimate leaf.

### Impact Explanation
An AA that uses `is_valid_merkle_proof` to gate privileged behavior (whitelist membership, airdrop eligibility, KYC/oracle-published sets, etc.) can be fooled into accepting a forged "leaf" that was never part of the committed set, as long as the attacker can observe (or reconstruct) any two sibling hash values inside the real tree — information that is normally public because users need it to build genuine proofs. This directly enables unauthorized approval of AA logic gated on Merkle membership (e.g., releasing funds, minting, or granting privileges to an address/value that was not actually included), i.e., AA fund loss / logic bypass.

### Likelihood Explanation
Exploitability depends entirely on AA design, but the vulnerable primitive (`merkle.js`) is a first-class, documented oscript feature (`is_valid_merkle_proof`) intended for exactly this kind of membership check, and the underlying weakness is already flagged in code comments as a known risk ("Node-as-Leaf issue might matter in some cases") yet left unmitigated. Any AA that follows the natural pattern of checking `is_valid_merkle_proof(trigger.data.value, trigger.data.proof)` against a stored root is affected, and building the forged element only requires public knowledge of the leaf set/tree structure — no cryptographic break is needed since the collision is a structural encoding collision, not a hash preimage attack.

### Recommendation
Add domain separation between leaf and internal-node hashing, e.g. prefix leaves with a distinct tag before hashing (`hash('0' + element)`) and internal nodes with another tag (`hash('1' + a + b)`), or otherwise ensure the hashed representation of a leaf can never be produced by concatenating two node hashes (e.g., include a length-prefixed encoding). Apply the fix consistently in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in `merkle.js` so that all three functions remain mutually consistent, and update all call sites (`formula/evaluation.js`'s `is_valid_merkle_proof`, `definition.js`'s `in merkle`) implicitly through the shared library.

### Proof of Concept
1. Build a real Merkle tree over a set of "whitelisted" leaves `L0..Ln` used by an AA (via `merkle.getMerkleRoot`), and let the AA store `root` as a whitelist commitment.
2. Locate any internal node in that tree whose two children hash to `h_L` and `h_R` (this information is derivable by anyone who can reconstruct the leaf set, exactly as legitimate users would to build their own proofs).
3. Craft `element = h_L + h_R` (raw string concatenation, matching the exact input `hash()` uses for internal nodes in `merkle.js` lines 9-20/84-102).
4. Build a `proof` object whose `siblings`/`index` correspond to the path from that internal node up to the root (i.e., skip the two real leaves and their immediate combination step).
5. Send an AA trigger with `data.value = element` and `data.proof = proof`. The AA's check `is_valid_merkle_proof(trigger.data.value, trigger.data.proof) && trigger.data.proof.root === var['root']` (evaluated via `formula/evaluation.js` lines 1768-1805) returns `true`, even though `element` was never a genuine leaf, allowing the attacker to bypass the intended whitelist/membership gate.

	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));

		arrHashes = arrOverHashes;

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
