### Title
Stale `Account.owner` lets a former NFT holder pass `require_owner_or_delegate` after transferring the position — (File: contracts/controller/src/account.rs)

### Summary
The Keycloak analog is a credential that stays valid after it should be dead: authentication succeeds for an entity that is no longer authorized. In the controller, `require_owner_or_delegate` and `is_owner_or_delegate` authenticate `caller` against the `owner` field stored inside the persisted `Account` struct, not against the live owner of the position NFT. `create_account_with` stamps `account.owner` once at mint time and nothing in `account.rs` ever rewrites it. Meanwhile the same file maintains a *separate*, correct notion of ownership: `require_account_owner` reads `storage::account_owner(account_id)`, i.e. the current NFT holder. So the codebase itself treats the two as different — the stale `Account.owner` is only kept around as the "credential" checked by the delegate/owner guard used on the `Migrate` and `Multiply` account guards in `load_or_create_account`.

### Finding Description
- `Account.owner` is written exactly once in `create_account_with` (`account.rs` lines 64–70) and is part of the account record persisted under `account_id`.
- `is_owner_or_delegate` returns `true` whenever `caller == owner` where `owner` is `&account.owner` (`account.rs` lines 121–127), and `require_owner_or_delegate` only panics when that check fails (lines 130–140).
- Delegate grants are also keyed by the stored owner: `get_delegates(env, account_id, owner)` uses `account.owner` (line 126), so delegates granted by the *previous* owner remain effective against the stale key after a transfer.
- The protocol's canonical ownership is the NFT: `require_account_owner` verifies `storage::account_owner(env, account_id) == caller` (lines 143–148), and `transfer`/`transfer_from` on the position NFT move the whole account to a new holder.
- The affected entrypoints are the ones routed through `load_or_create_account` with `AccountGuard::Migrate` / `AccountGuard::Multiply` (lines 99–110) — i.e. `migrate_from_blend` and the `multiply`/`flash_position`-style leverage strategies reachable by an unprivileged address with `caller.require_auth()`.

### Impact Explanation
After Alice sells or transfers her position NFT to Bob, `account.owner` still contains Alice's address. Alice (or a manager she delegated before the transfer, if it is still an active `position_manager`) can still satisfy `require_owner_or_delegate` on Bob's account through the `Migrate`/`Multiply` guards. On a Multiply-type path the attacker operates on the account's real collateral: supplying own funds is not required to pass the guard — the guard is what unlocks debt minting against the account's collateral — so the former owner can lever, swap, or migrate positions in ways that encumber or drain value belonging to the new NFT holder. That is theft of user funds / unauthorized debt minted against someone else's collateral, the direct analog of "authentication succeeds with an invalid credential."

### Likelihood Explanation
High if confirmed: NFT transfers are a supported, unprivileged flow (`position-nft transfer`/`transfer_from`), and the stale-credential condition then persists indefinitely since nothing rewrites `Account.owner`. Uncertainty: I could not exhaustively confirm in this pass that no hook (NFT transfer callback, `storage::set_account` writer, or strategy preamble) resynchronizes `account.owner` to the NFT owner, nor enumerate every entrypoint that reaches the `Multiply`/`Migrate` guards. The fact that `require_account_owner` exists as a separate live-owner check, and that `set_account_delegate` deliberately uses it rather than `account.owner`, strongly suggests the stale field is unintended — but a resync path I did not see would invalidate the finding.

### Recommendation
In `is_owner_or_delegate`, authenticate against `storage::account_owner(env, account_id)` (the live NFT owner) instead of `account.owner`, and key delegate lookups to that same live owner; or eliminate `Account.owner` entirely so there is a single ownership source of truth. Additionally, on NFT `transfer`/`transfer_from`, clear or re-key delegate grants so a previous owner's managers cannot carry authority into new ownership.

### Proof of Concept
1. Alice calls `supply` with `account_id = 0`, creating account `N` owned by Alice (`account.owner = Alice`).
2. Alice optionally calls `add_delegate(N, M)` where `M` is an active position manager.
3. Alice calls `position-nft.transfer(Alice → Bob, N)`. Bob is now `storage::account_owner(N)`.
4. Alice calls `multiply` (or `migrate_from_blend`) with `account_id = N`. `load_or_create_account` takes the `Multiply`/`Migrate` guard, `caller == account.owner` is still `Alice`, the auth check passes, and the strategy mints debt / repositions collateral on Bob's account.
5. Bob's account ends up encumbered by debt Alice chose; Alice profits via the strategy output (e.g. borrowed assets routed to herself).
