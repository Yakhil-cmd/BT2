### Title
Webhook signature is verified against the organization in `repository.owner.login`, but every event handler routes and mutates state using the unrelated `repository.full_name` field, allowing cross-tenant repository/stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository_owner` (`params.dig('repository','owner','login')`), but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` using a completely different, independently-controlled field: `payload.dig('repository', 'full_name')`. Because these two fields are never cross-checked, a payload can be crafted so it authenticates as organization "A" while all destructive actions are executed against a repository/stack belonging to organization "B".

### Finding Description
In a multi-tenant Shipit deployment, `Shipit.github(organization:)` maps an organization name to its own GitHub App config, including its own `webhook_secret` (`lib/shipit.rb` `github_app_config`/`github` methods). The webhook signature check picks which organization's secret to use like this: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is read from the JSON body itself: [2](#0-1) 

Once the signature is accepted, `create` blindly hands the entire parsed body to every registered handler with no further binding to `repository_owner`: [3](#0-2) 

Every handler, however, resolves the target `Repository` (and thus `Stack`/`ReviewStack`) from `repository.full_name`, a sibling but distinct JSON field: [4](#0-3) 

`Repository.from_github_repo_name` simply splits this string on `/` and looks up a repository row by `owner`/`name`, with no relation back to `repository.owner.login`: [5](#0-4) 

Because a JSON payload can set `repository.owner.login` to organization A's login (to select A's webhook secret for signature verification) while independently setting `repository.full_name` to `"B/some-other-repo"`, the signature-authenticated identity (A) and the identity whose data actually gets mutated (B) diverge — this is exactly the "organization authenticated versus the repository that is written" trust binding that is normally assumed to hold but is never enforced in code.

Concrete destructive paths reachable this way:
- `push` → `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for any stack under the forged `full_name`, enqueuing `GithubSyncJob` against a stack that has nothing to do with the authenticating organization: [6](#0-5) [7](#0-6) 
- `pull_request` closed → `ClosedHandler#process` calls `review_stack.archive!`, tearing down a `ReviewStack` belonging to a different tenant's repository: [8](#0-7) 
- `pull_request` opened → `OpenedHandler#process` can provision a new review stack under a repository chosen purely from `full_name`: [9](#0-8) 

### Impact Explanation
This breaks tenant isolation between GitHub organizations hosted by the same Shipit instance. An attacker who controls (or is an admin of) any single organization/App onboarded into `secrets.github` can forge a raw webhook body, sign it correctly with their own organization's `webhook_secret`, but point `repository.full_name` at any other organization's repository known to Shipit. This produces cross-repository writes: unsolicited GitHub syncs, archiving of another tenant's review stacks, or spurious provisioning of review stacks/deploys tied to a repository the attacker does not own. This matches the Critical-tier impact bucket ("cross-repository writes") defined for this engagement, since state belonging to a different, unauthorized repository is mutated as a direct result of the attacker's own signed request.

### Likelihood Explanation
Exploitability only requires: (1) a multi-tenant Shipit install with more than one organization configured under `secrets.github` (a documented, supported configuration per `docs/setup.md`), and (2) the attacker being an authorized user of one of those organizations' GitHub Apps (i.e., able to trigger/replay a webhook signed with their own org's secret, or simply POST directly to `/webhooks` with a manually computed HMAC using their own known secret). No GitHub App private key, `api_clients_secret`, or Shipit session is required — only knowledge of one tenant's own webhook secret, which that tenant legitimately possesses. This is a straightforward confused-deputy condition with no additional obstacles, making the likelihood high once multi-org hosting is in use.

### Recommendation
After verifying the signature, re-derive the acted-upon repository/stack scope strictly from the same organization identity that was cryptographically authenticated (`repository_owner`), and reject (or 422) any payload where `repository.full_name`'s owner segment does not match `repository_owner`/`organization.login`. Concretely, add a check in `WebhooksController#verify_signature` (or in `Handler#repository_name`) asserting `params.dig('repository','full_name')&.split('/')&.first&.casecmp?(repository_owner)` before dispatching to handlers, and fail closed if it does not.

### Proof of Concept
1. Configure two tenants in `secrets.github`: `orgA` (attacker-controlled, secret known to attacker) and `orgB` (victim, with an existing `Stack`/`ReviewStack` for `orgB/victim-repo`).
2. Attacker crafts a `pull_request` "closed" webhook body:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": { "...": "valid fields...", "head": {"sha":"x","ref":"y"}, "user":{"login":"attacker"}, "assignees":[], "labels":[] },
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Attacker computes `X-Hub-Signature` using `orgA`'s known `webhook_secret` (`OpenSSL::HMAC.hexdigest('sha1', orgA_secret, raw_body)`), matching what `verify_webhook_signature` in `lib/shipit/github_app.rb` checks.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'orgA')` and successfully verifies the signature against the attacker-known secret.
5. `Webhooks::Handlers::PullRequest::ClosedHandler#process` resolves `repository` via `Repository.from_github_repo_name('orgB/victim-repo')` and calls `review_stack.archive!`, archiving a review stack belonging to `orgB` — an organization the attacker never authenticated as.
