Confirmed: there is no check in the stake program (`programs/**`) referencing `epoch_reward_status` / `reward_interval`, meaning the native stake-program instructions (Split, Merge, MoveStake, MoveLamports, Withdraw, Deactivate, etc.) are **not** blocked or made aware of an in-progress partitioned epoch-reward distribution. The comment in `distribution.rs` asserting that "further state mutation [is] prevent[ed] by stake-program restrictions" is not backed by any such restriction found in the codebase.

### Title
Stale stake-delegation snapshot used during multi-block partitioned reward distribution can panic the validator - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
Partitioned epoch-reward distribution snapshots each stake account's `Stake` (delegation + credits_observed) once, at the calculation block, but replays that stale snapshot verbatim onto the *live* stake account up to many blocks later, at the actual distribution block. In between, ordinary user-submitted stake-program instructions (`Split`, `Merge`, `MoveStake`, `Withdraw`, `Deactivate`, etc.) are free to change the account's live delegation amount, because the stake program has no awareness of `Bank::epoch_reward_status`.

### Finding Description
`Bank::begin_partitioned_rewards` computes `PartitionedStakeReward`s (including a full, frozen copy of each stake's post-reward `Stake` struct) at the reward-calculation block and stores them in `self.epoch_reward_status` [1](#0-0) . Actual crediting of stake accounts is deferred and spread across up to `slots_per_epoch / 10` subsequent blocks via `distribute_partitioned_epoch_rewards` / `distribute_epoch_rewards_in_partition` [2](#0-1) .

When a partition is finally processed, `build_updated_stake_reward` fetches the account's **current** state from `stakes_cache_accounts`, but then unconditionally overwrites the delegation with the **stale, calculation-time** `Stake` value (`partitioned_stake_reward.inflation.stake`), only adding the reward lamports to the balance: [3](#0-2) 

When the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) is *not* active, the code instead asserts that the live delegation plus the reward equals the frozen delegation: [4](#0-3) 

This `assert_eq!` is a hard `panic!` in the validator's `Bank` — not a recoverable transaction error. It is only true if the stake account's `delegation.stake` did not change between the calculation block and this specific distribution block. Nothing enforces that invariant: the stake program (in `programs/`) contains no reference to `epoch_reward_status` / reward interval and does not reject `Split`, `Merge`, `MoveStake`, or `Withdraw` transactions while a partitioned reward distribution is in flight for that account. Any ordinary user (unprivileged) can submit such a transaction against their own stake account in one of the intervening blocks between the epoch-boundary calculation block and the later block that happens to contain their reward partition.

This is the structural analog of the Velodrome report: a state-changing, permissionless user action (`depositManaged`) is performed in the window between a reward-eligibility snapshot and reward payout, invalidating an assumption ("lock hasn't changed") the payout logic relies on. Here the assumption ("stake delegation hasn't changed since the reward snapshot") is likewise violated by ordinary, permitted user instructions, but instead of merely mis-crediting funds it trips a `debug_assert`/`assert_eq!` that aborts bank processing.

### Impact Explanation
A triggered `assert_eq!` panic inside `Bank::store_stake_accounts_in_partition` (called from `distribute_partitioned_epoch_rewards`, itself invoked once per block from the bank's slot-processing path) will crash any validator that processes that block, and because it is deterministic bank/consensus-critical logic, all validators that replay the same block will panic identically — this is a cluster-wide, epoch-boundary halt rather than an isolated node crash. This falls squarely in the accepted impact category "epoch-boundary halt."

### Likelihood Explanation
- Reward-distribution can span up to 10% of an epoch's slots (`get_reward_distribution_num_blocks` clamps to `slots_per_epoch / 10`) [5](#0-4) , giving a wide window (hundreds to thousands of blocks depending on cluster) during which any staker can submit a `Split`/`Merge`/`MoveStake`/`Withdraw` transaction that changes their own stake account's `delegation.stake` before their partition is processed.
- Any unprivileged staker knows in advance (partition assignment is a public, blockhash-seeded hash of their own pubkey, `hash_rewards_into_partitions`) roughly which block their reward will land in, making deliberate triggering straightforward. Even accidental triggering (a normal delegator restaking/splitting mid-epoch-boundary) is plausible.
- The panic path is gated by the `relax_post_exec_min_balance_check` feature flag being inactive; on clusters/epochs where that feature has not yet activated, the vulnerable `assert_eq!` path is live.

### Recommendation
Do not persist a frozen full `Stake` struct from calculation time and blindly overwrite the live account's delegation with it at distribution time. Instead, always recompute the post-reward delegation as `live_delegation.stake.saturating_add(reward)` (as effectively done in the `adjust_delegations_for_rent` branch) rather than asserting equality with a stale snapshot, and treat any accounts whose stake changed materially between calculation and distribution (e.g., via `Merge`, `Split`, `Withdraw`) via the existing `DistributionError` recoverable-burn path instead of an unconditional `assert_eq!` panic.

### Proof of Concept
1. Advance to an epoch boundary with enough active stake accounts that `get_reward_distribution_num_blocks` yields more than 1 distribution block (as exercised by `test_rewards_computation_and_partitioned_distribution_multi_blocks` [6](#0-5) ).
2. Identify a staker whose stake account is hashed into a partition scheduled for a later distribution block (`hash_rewards_into_partitions` in `runtime/src/bank/partitioned_epoch_rewards/epoch_rewards_hasher.rs`).
3. Before that block, submit a `Split` (or `Merge`/`MoveStake`) instruction from that staker's own authority against the stake account, changing its live `delegation.stake` amount — a fully permitted, unprivileged transaction with no relation to `epoch_reward_status`.
4. When the bank later processes that staker's partition, `build_updated_stake_reward` executes the `assert_eq!(expected_delegation, new_stake.delegation.stake, ...)` check in the non-`adjust_delegations_for_rent` path [7](#0-6) , which fails because the live delegation no longer matches the calculation-time snapshot plus reward, causing the bank to panic.

**Uncertainty:** I could not fully confirm at what specific block/slot the `relax_post_exec_min_balance_check` feature is currently activated on mainnet/testnet (i.e., whether the vulnerable `assert_eq!` branch is still reachable in production today), nor did I find/verify a runtime test that actually interleaves a live `Split`/`Merge` transaction with an in-flight partitioned distribution to conclusively reproduce the panic end-to-end — this would require a running validator/test harness (outside available static analysis) to confirm definitively.

    /// Process reward distribution for the block if it is inside reward interval.
    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
        }

        if height.saturating_add(1) >= distribution_end_exclusive {
            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("active", 0, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );

            assert!(matches!(
                self.epoch_reward_status,
                EpochRewardStatus::Active(EpochRewardPhase::Distribution(_))
            ));
            self.epoch_reward_status = EpochRewardStatus::Inactive;
            self.set_epoch_rewards_sysvar_to_inactive();
        }
    }

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
