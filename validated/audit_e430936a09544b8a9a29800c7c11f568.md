### Title
Signed messages (`signed_message.js` / `getSignedPackageHashToSign`) omit any network/chain identifier, enabling cross-network signature replay - (File: object_hash.js)

### Summary
Obyte units are network-scoped by an `alt` field that is baked into the unit's signing hash, but "signed messages" — the generic, network‑independent signature envelope used by AA triggers (`is_valid_signed_package`), prosaic/arbiter contracts, and device‑to‑device authentication — carry no such identifier. The hash that is actually signed for these objects, produced by `getSignedPackageHashToSign`, is derived purely from the message content, optional `last_ball_unit`, and `authors`, with no binding to a specific network/ledger instance (`alt`).

### Finding Description
`getUnitHashToSign` in `object_hash.js` signs a naked copy of the *unit*, which (via `getNakedUnit`/`cloneDeep`) still contains the unit's `alt` field, so ordinary unit signatures are implicitly bound to the network they were created for. [1](#0-0) 

By contrast, `getSignedPackageHashToSign` only clones the "signed package" object and strips `authentifiers`; it does not include, require, or reference any network/alt identifier: [2](#0-1) 

`signed_message.js`'s `validateSignedMessage` validates the object's shape (`signed_message`, `authors`, `last_ball_unit`, `timestamp`, `version`) and, when network‑aware, anchors it to a stable `last_ball_unit`, but does not check that the message (or the referenced `last_ball_unit`) belongs to the network the verifier is running on. When not network‑aware (no `last_ball_unit`, e.g. an offline/local signed message such as those produced by `signMessage()` without `bNetworkAware`), there is no chain-binding at all: [3](#0-2) [4](#0-3) 

Because Obyte address derivation (`objectHash.getChash160(definition)`) is independent of network — the same private key/definition produces the same address on mainnet, testnet, or any other deployment sharing the `ocore` codebase — a signed message crafted and signed for one network is byte-for-byte valid on another network that runs the same `ocore` validation logic. This is directly reachable by any unprivileged actor who obtains or is given a signed message (e.g., as an AA trigger payload consumed via `is_valid_signed_package`, or a prosaic/arbiter contract response) and replays it verbatim in a different Obyte-based network instance where the corresponding address also exists (e.g., copied wallet on testnet, or a differently configured private/permissioned deployment sharing address derivation).

The AA formula opcode `is_valid_signed_package` accepts an attacker-supplied `signed_package` object straight from `trigger.data` and validates it via `signed_message.validateSignedMessage`, with the only chain-anchoring being the optional `last_ball_unit` stability check — itself omittable by the caller when constructing the object, or satisfiable by referencing a stable unit that also exists (by content) in a different network with the same genesis/witness setup: [5](#0-4) 

### Impact Explanation
An AA that trusts `is_valid_signed_package(pkg, address)` results to authorize fund transfers, order execution, or state changes (a common pattern for off-chain "order"/"oracle" style signed authorizations, mirroring the reported `CrabNetting` order-signing bug) can be tricked into accepting a signature that the address owner produced for a *different* network/deployment, because the signed hash carries no chain/network identifier. This can lead to AA fund loss/misuse or unauthorized authorization replay across any two Obyte-compatible networks (e.g., mainnet vs. testnet, or two private deployments) that share the same address-derivation scheme, satisfying "AA fund loss" and "unauthorized spending"-class impact.

### Likelihood Explanation
Exploitation requires: (1) an AA (or contract flow) that accepts a `signed_message`/`signed_package` as trigger data and relies on `is_valid_signed_package`/`validateSignedMessage` for authorization, and (2) the same address/key material being valid/used across two networks. Given that testnet and mainnet Obyte deployments intentionally share the exact same address-derivation and validation code, and users frequently reuse the same seed/wallet across environments, this is a realistic occurrence for AA authors building order-book/off-chain-signing style contracts, mirroring exactly the reported analog. Likelihood is Medium since it depends on specific AA usage patterns of `is_valid_signed_package` combined with key reuse across networks.

### Recommendation
Include a network/chain identifier (e.g., `alt`) in the object hashed by `getSignedPackageHashToSign`, and require `validateSignedMessage` to check that identifier against the local node's configured network before accepting a signed package as valid. This mirrors the fix recommended in the reported analog (add chain id to the signed schema) and would prevent cross-network replay of signed messages/order-like authorizations.

### Proof of Concept
1. On network A (e.g. testnet), a user signs a message via `signMessage()`/`signed_message.js` without `bNetworkAware` (or with a `last_ball_unit` that also exists as a stable unit on network B, e.g., a shared early/genesis unit): the resulting object is `{signed_message, authors:[{address, definition, authentifiers}]}` with no network binding, per `getSignedPackageHashToSign` [2](#0-1) .
2. The address is `objectHash.getChash160(definition)`, identical on both networks since chash derivation is network-agnostic.
3. On network B, an attacker submits this exact `signed_package` object as `trigger.data.signed_package` to an AA using `is_valid_signed_package(trigger.data.signed_package, address)`; `validateSignedMessage` performs no network check and succeeds if the definition/signature/last_ball_unit checks pass [3](#0-2) .
4. The AA treats the replayed authorization (e.g., an "order" or "approval") as valid on network B even though it was only intended for network A, causing unauthorized state transition/fund movement.

function getUnitHashToSign(objUnit) {
	var objNakedUnit = getNakedUnit(objUnit);
	for (var i=0; i<objNakedUnit.authors.length; i++)
		delete objNakedUnit.authors[i].authentifiers;
	var sourceString = (typeof objUnit.version === 'undefined' || objUnit.version === constants.versionWithoutTimestamp) ? getSourceString(objNakedUnit) : getJsonSourceString(objNakedUnit);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
