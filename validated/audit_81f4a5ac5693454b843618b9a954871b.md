### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler routes the mutation using the unrelated `repository.full_name` field, allowing cross-repository forgery when any configured organization has no (or a guessable) webhook secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config to check the `X-Hub-Signature` against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1)  Every actual `Handlers::Handler` subclass, however, resolves the target `Repository`/`Stack` to mutate using a completely different field, `payload.dig('repository', 'full_name')`. [3](#0-2)  `PushHandler`, `StatusHandler`, and the `PullRequest::*Handler` classes all key off `params.repository.full_name` when deciding which stack to sync, archive/unarchive, or update. [4](#0-3) [5](#0-4) 

### Finding Description
This is the direct analog of the ERC20Pods `_removeAllPods` bug: a value used to authorize/checkpoint an operation (`balance` cached once, vs. the balance actually mutated per pod) is decoupled from the value that later iterations act on. Here the binding that should be an equality — "organization whose secret authenticated this request" == "repository/stack that gets written" — is never enforced, because two different JSON fields are used for the two purposes.

`/webhooks` is a public, unauthenticated Rails endpoint (`WebhooksController`, mounted at `<host>/webhooks` per the setup docs). [6](#0-5) [7](#0-6)  The only gate is `verify_signature`, which:
1. Looks up `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `repository.owner.login` (or `organization.login`) in the attacker-supplied JSON body. [2](#0-1) 
2. Calls `verify_webhook_signature`, which explicitly **returns `true` (verified) if no `webhook_secret` is configured for that organization**: `return true unless webhook_secret`. [8](#0-7) 
3. `Shipit.setup` docs describe `webhook_secret` as **optional** per organization, and the multi-organization example in the setup docs shows each org configured independently with its own (optional) `webhook_secret`. [9](#0-8) [10](#0-9) 

Once `verify_signature` passes (trivially, for any org lacking a secret), the `create` action dispatches the raw, fully attacker-controlled JSON to the matching event handler(s): `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [11](#0-10)  Nothing re-checks that `repository.full_name` (used by the handler) matches `repository.owner.login` (used for authentication). An attacker can therefore submit a payload where `repository.owner.login` names an organization with no configured `webhook_secret` (satisfying step 2 trivially) while `repository.full_name` names an entirely different, victim organization's repository whose `Stack` the attacker wants to manipulate.

### Impact Explanation
Because the authenticated "organization" and the acted-upon "repository" are never bound to each other, an unprivileged network attacker who never possesses any `webhook_secret`, GitHub App private key, or `ApiClient` token can:
- Trigger `PushHandler#process`, causing `stack.sync_github(expected_head_sha: params.after)` to run for an arbitrary victim stack with an attacker-chosen SHA. [12](#0-11) 
- Trigger `StatusHandler#process` to inject fabricated commit statuses (`commit.create_status_from_github!`) for arbitrary commits, which can be leveraged to make Shipit believe CI passed on a victim's commit, unlocking merge/deploy flows that are gated on commit status. [13](#0-12) 
- Trigger pull-request handlers to archive/unarchive victim review stacks (`stack.archive!`, `stack.unarchive!`) via `ReviewStackAdapter`, which schedules provisioning/deprovisioning and merges. [14](#0-13) [15](#0-14) 

This crosses a repository/authentication boundary: an entity that is only "authenticated" as (or completely unauthenticated for) organization A is able to cause writes against organization B's stacks — matching the "unauthorized deploy/merge, cross-repository writes" impact class.

### Likelihood Explanation
The `webhook_secret` field being optional is a documented, first-class supported configuration (not a misconfiguration edge case) — the setup docs explicitly label it "(optional)". [9](#0-8)  Any Shipit deployment with at least one organization lacking a `webhook_secret` (or one whose secret is weak/leaked) exposes every other configured organization's stacks to forgery through this field confusion, with zero prerequisites beyond crafting an HTTP POST.

### Recommendation
Bind the value used for authentication to the value used for authorization/action:
- In `WebhooksController#verify_signature`, additionally verify that `params.dig('repository', 'full_name')&.split('/')&.first` (or `organization.login`) equals `repository_owner`, rejecting mismatches.
- In `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`, cross-check the resolved repository's owner against the organization that was actually used to verify the signature (pass it down from the controller instead of re-deriving it independently), rejecting the event if they diverge.
- Consider making `webhook_secret` mandatory (or requiring an explicit opt-in flag to run without one) since its absence silently disables signature verification entirely.

### Proof of Concept
Assume a Shipit instance configured for multiple organizations, where `victim-org` has stacks tracked and a real `webhook_secret`, and `no-secret-org` is also configured (e.g., a newly onboarded/team-testing org) without a `webhook_secret` set, per the documented optional-field pattern. [10](#0-9) 

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything   # ignored: verify_webhook_signature returns true when no secret configured
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```

- `verify_signature` computes `repository_owner = "no-secret-org"`, loads its `GitHubApp`, and `verify_webhook_signature` short-circuits `true` because that org has no `webhook_secret`. [1](#0-0) [8](#0-7) 
- `create` dispatches to `PushHandler`, whose `stacks`/`repository_name` resolve `Repository.from_github_repo_name("victim-org/victim-repo")` — a repository unrelated to the organization used for authentication — and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack. [3](#0-2) [12](#0-11) 

I was unable to fully trace `Stack#sync_github`'s downstream trust checks (e.g., whether it independently re-verifies the SHA against GitHub before acting) within the indexed portion of `app/models/shipit/stack.rb`; the excerpts I retrieved show only surrounding lifecycle hooks, not the `sync_github`/`sync_github_if_necessary` method bodies. That may narrow but does not eliminate the equivocation-of-trust root cause identified above (the field-confusion between `repository.owner.login` and `repository.full_name` at the authentication boundary), since it affects `StatusHandler` and the PR-based archive/unarchive handlers identically. A full-repo Devin session could confirm the exact downstream consequences by reading the complete `Stack#sync_github` implementation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
