## Analysis

`WebhooksController#verify_signature` selects **which** GitHub App configuration (and therefore which `webhook_secret`) to validate a webhook against by reading the organization name straight out of the *unauthenticated* JSON body: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once the signature check passes, the actual event handlers (`PushHandler`, the `PullRequest::*Handler`s, `Handler#stacks`) determine **which stack/repository to act on** using a *different* field of the same payload, `repository.full_name`: [3](#0-2) 

Nothing ties `repository.owner.login` (used to pick the verification secret) back to `repository.full_name` (used to pick the target repository/stack). `Shipit.github_app.verify_webhook_signature` explicitly treats a missing `webhook_secret` as automatically verified: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

In a multi-organization Shipit deployment (`Shipit.github_organizations`, `github_app_config`, `lib/shipit.rb:170-200`), it's a documented, supported configuration to run some orgs without a `webhook_secret` (`docs/setup.md` describes it as optional). An attacker only needs to know (or trigger delivery for) an org that has no `webhook_secret` configured — no secret, session, `ApiClient` token or GitHub credential is required at all.

## The break

- **Equality that should hold:** organization whose signature was verified (`repository.owner.login`) == organization owning the repository actually acted upon (`repository.full_name`'s owner segment).
- **What the code does instead:** verification picks the app config from `owner.login`; the handlers independently trust `full_name` to resolve `Repository.from_github_repo_name` / `stacks`, with no cross-check.

## Exploit sketch

1. Shipit hosts orgs `open-org` (no `webhook_secret` configured) and `secured-org` (private, secured stacks).
2. Attacker POSTs to `/webhooks` with `X-Github-Event: pull_request`, `repository.owner.login = "open-org"` (any/garbage `X-Hub-Signature`, verification auto-passes because `open-org` has no secret) but `repository.full_name = "secured-org/private-repo"`.
3. `PullRequest::OpenedHandler#repository` resolves `Shipit::Repository.from_github_repo_name("secured-org/private-repo")`, and `ReviewStackAdapter#find_or_create!` provisions/archives/unarchives review stacks for `secured-org`'s repository — an unauthorized action on a repository never covered by any verified signature for that org.

Given the current toolset and information gathered, this analysis represents the strongest reachable instance of the reported bug class ("mapping/consistency not enforced across two identity fields updated independently") mapped onto Shipit's webhook trust boundary. Since this is analysis rather than an implementation task, I have not produced a plan — let me know if you'd like one to fix the binding (e.g., requiring `repository.full_name.split('/').first.casecmp(repository_owner) == 0` before dispatching handlers, or resolving the target repository from the already-verified `repository_owner` rather than from an independently-controlled `full_name`).

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
