### Title
Cross-repository status forgery via SHA-only matching in `StatusHandler#process` amplified by production environment gating - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves affected commits with `Commit.where(sha: params.sha)` [1](#0-0)  without any scoping to the repository that authenticated the inbound webhook. Because `verify_signature` only validates that the payload came from *some* configured GitHub organization/app [2](#0-1) , an attacker who controls a repository (and thus can produce a valid signature for their own repo's events) can cause statuses on any `Commit` record sharing that SHA — including commits belonging to a victim's stack in a completely different repository — to be updated.

### Finding Description
The broken binding is: `commit.stack.repository == payload.repository` is assumed but never enforced. In reality `StatusHandler#process` iterates `Commit.where(sha: params.sha)` globally across all stacks/repositories in the Shipit instance, and calls `commit.create_status_from_github!(params)` for each match [1](#0-0) . `create_status_from_github!` writes into `statuses.replicate_from_github!(stack_id, github_status)` [3](#0-2) , and via `add_status` this can trigger `stack.schedule_merges` and continuous-delivery scheduling once the state changes [4](#0-3) [5](#0-4) .

`verify_signature` derives the signing organization strictly from `params.dig('repository','owner','login')` in the attacker's own payload and validates the HMAC using that organization's GitHub App secret [2](#0-1) . This proves only that the webhook genuinely originated from a repository the attacker controls (or one where they can trigger a `status` event, e.g. via their own GitHub Actions run) — it does not, and structurally cannot, prove that the `sha` referenced in the payload is unique to that repository. Git commit SHAs are content-addressed; an attacker can reproduce an identical commit object (same tree, parents, author/committer identity and timestamps, message) in their own repository/fork to obtain the same SHA as a commit already present in a victim's `Stack`, then trigger a `status` webhook (e.g. via GitHub Actions on their own repo) with `context: github-actions` and `state: success`.

Because `StatusHandler` performs no repository/stack scoping, this forged status is applied to the victim's commit as well. If the victim's stack is configured as the production environment and requires the `github-actions` context (via `required_statuses`/CI configuration), this satisfies `Commit#deployable?` (`success? && !blocked?`) [6](#0-5)  and can trigger `schedule_continuous_delivery` -> `ContinuousDeliveryJob` [5](#0-4) , or conversely a forged failing/error status can force `blocked?` to block deploys on the production stack.

None of the existing guards prevent this: `verify_signature` authenticates the *sender repository*, not the *target commit/stack*; `drop_unhandled_event` only filters unsupported event types; there is no `ExplicitParameters` constraint tying `sha` to `repository.full_name`; and `Commit` has no unique-per-repository constraint blocking SHA collisions across stacks.

### Impact Explanation
An attacker who controls (or can trigger workflow runs in) any repository can mutate CI status on a commit belonging to an unrelated, victim-owned `Stack` — this is exactly the "payload for one repository mutating another's stack, commit" Critical category. If the victim stack is the production environment gated on the `github-actions` context, the attacker can force a ship (by faking success) or force a block/rollback (by faking failure/error) on production, i.e., an unauthorized deploy or denial of legitimate deploys. The attack is repeatable against any commit whose SHA the attacker can reproduce and is not limited to a single victim stack — any stack containing a commit with a colliding SHA is affected.

### Likelihood Explanation
The main precondition is producing a SHA collision between the attacker's own commit and the victim's commit — achievable in practice because git commit SHA is computed only from tree hash, parent hash(es), author/committer name+email+timestamp, and commit message; an attacker who can observe a target commit (e.g. a public/open-source victim repo, or a commit they can predict, such as a PR merge commit whose parents/tree are known) can reconstruct an identical commit object in their own repo and push/trigger CI to emit a `status` webhook for it. This requires no Shipit credentials, no GitHub team membership, and no privileged role — only ownership of a repository that has Shipit's GitHub App/webhook installed (which, per the threat model, "any internet user" satisfies by being able to install the app on their own repo or fork). The attack is fully repeatable at will.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run handler) to commits whose `stack.repository` matches the payload's `repository.full_name`/owner, e.g. join through `Stack`/`Repository` and filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repo_owner, name: repo_name })`, rather than matching by bare `sha` across the entire installation.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, out-of-scope path noted only for illustration — actual test to be added under `test/`):
1. Create `repository_a` (attacker-owned) and `repository_b` (victim-owned) `Shipit::Repository` records.
2. Create `stack_b` on `repository_b` with `environment: 'production'` and CI configuration requiring `github-actions` context (`required_statuses` includes `github-actions`).
3. Create a `Commit` with `sha: 'deadbeef...'` attached to `stack_b`, with no prior successful status (assert `commit_b.deployable?` is `false` before the attack).
4. Construct a `StatusHandler` payload with `sha: 'deadbeef...'`, `context: 'github-actions'`, `state: 'success'`, and `repository.owner.login` set to the attacker's org (simulating a webhook whose signature was validated against `repository_a`'s GitHub App secret, i.e. bypassing `verify_signature` in the test by calling the handler directly, per the "no live GitHub" rule).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new.process` (or `.call`) with these params.
6. Assert `commit_b.reload.deployable?` is now `true` (or that `blocked?` toggles for a failure-state variant), proving the status intended for `repository_a` mutated `stack_b`'s commit despite no relation between the two repositories — demonstrating the equality `commit.stack.repository == payload.repository` does NOT hold and the record was written for a repository that did not authenticate it.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
