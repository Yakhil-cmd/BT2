### Title
Unbounded, permanent growth of the global `aa_balances` table via dust payments of newly issued assets - (File: aa_composer.js)

### Summary
Any unprivileged unit poster can permanently grow the shared, node-wide `aa_balances` table by issuing a new asset (a cheap, permissionless operation) and sending a dust amount of it to one or more Autonomous Agent (AA) addresses. Each new `(address, asset)` combination that reaches an AA causes a new row to be inserted into `aa_balances`, and that row is never deleted for the lifetime of the node, even after the AA spends the balance back to zero. This mirrors the reported Deriverse pattern of "space reserved on interaction, deallocated only through a specific narrow path" — except in ocore's case there is no deallocation path at all.

### Finding Description
When an AA is triggered, `updateInitialAABalances()` in `aa_composer.js` reads the AA's current balances and, for every asset present in the trigger's outputs that isn't already tracked, executes an unconditional `INSERT INTO aa_balances (address, asset, balance) VALUES ...`: [1](#0-0) 

The same unconditional insertion path also exists when an AA is newly defined and already has pending balances from a non-AA sender, via `storage.insertAADefinitions()`: [2](#0-1) 

Once a row exists, all subsequent balance changes for that `(address, asset)` pair are performed with `UPDATE aa_balances SET balance=balance+? ...` — including in `updateFinalAABalances()` — never with a `DELETE`, even when the resulting balance is 0: [3](#0-2) 

A search of the entire codebase confirms there is no `DELETE FROM aa_balances` statement anywhere, so once created a row is permanent for the life of the node database. This differs qualitatively from other AA-related structures explicitly documented as short-lived, such as `aa_triggers`: [4](#0-3) 

Because asset issuance is permissionless and requires only paying the base-asset issuance/definition fee (`initial-db` `assets` table growth is itself unavoidable and separately fee-metered), and because payment outputs only need to satisfy `isPositiveInteger(output.amount)` with no minimum-value floor for non-`base` assets, an attacker can:
1. Issue one or more cheap custom assets (`payload.asset` new hash) - a normal, low-cost `asset` message.
2. Send a `payment` message with `amount: 1` (or any small positive integer) of a newly issued asset to any existing AA address (or many distinct AA addresses in outputs of a single unit).
3. Each distinct `(AA address, asset)` pair that has never received that asset before forces one permanent row into `aa_balances`, regardless of whether the AA immediately forwards/burns the funds and the balance returns to zero.

Because outputs are only fee-metered by their serialized byte size (`OUTPUT_SIZE`), not by the fact that they create a permanent DB row, the cost to the attacker of creating a permanent row is far smaller than the actual long-term storage cost imposed on every full node that must keep `aa_balances` forever (it participates in `checkBalances()` consistency checks across the whole table on every run): [5](#0-4) 

### Impact Explanation
An attacker who repeatedly issues new assets and dusts a large number of existing AA addresses (or a single popular AA with many distinct assets) can cause `aa_balances` to grow without bound, at a cost far below the true storage cost to every node. This degrades the performance of AA balance lookups (`readAABalances`), the periodic full-table `checkBalances()` consistency job, and general database/disk growth for every full node running ocore — a network-wide resource-exhaustion condition analogous to the reported spot-trading DoS, but here it is a core-protocol table with a genuinely missing (not merely optional) cleanup path.

### Likelihood Explanation
The attack requires only standard, unprivileged operations available to any wallet: issuing an asset and sending a payment. No special privileges, AA authorship, or node access are needed, and the per-row cost (roughly one output's byte fee) is cents-level, while the resulting row is permanent. This makes the attack straightforward and cheap to mount at scale, though the effect (DB bloat/perf degradation) accrues gradually rather than causing instantaneous denial of service.

### Recommendation
Add a cleanup path that deletes `aa_balances` rows once their balance returns to zero (e.g., in `updateFinalAABalances()` and in `insertAADefinitions()`'s balance-mirroring logic), instead of leaving zero-balance rows in place indefinitely. Alternatively, charge a proportional, non-refundable storage fee for creating a new `(address, asset)` balance row (similar to the existing `storage_size` fee charged to AAs for their own persistent state), so that the cost of permanent state creation is borne by whoever forces it into existence, rather than externalized to every full node's storage.

### Proof of Concept
1. Attacker issues a new asset `A` with `payload.asset` unique per attempt (cheap `asset` message).
2. Attacker composes a unit with a `payment` message for asset `A` sending `amount: 1` to a target AA address `X` (any live AA on the network).
3. On trigger handling, `updateInitialAABalances()` finds `A` not in `X`'s existing `aa_balances` rows and executes `INSERT INTO aa_balances (address, asset, balance) VALUES (X, A, 1)` — [6](#0-5) .
4. AA `X` processes the trigger and, in its response, forwards or burns the entire amount, driving the balance back to `0` via `UPDATE aa_balances SET balance=balance+?` in `updateFinalAABalances()` — [7](#0-6)  — but the row itself is never removed.
5. Repeat steps 1–3 with a new asset each time (or across many AA addresses in a single unit's outputs) to add an unbounded number of permanent rows to `aa_balances` for a cost proportional only to per-output byte fees, not to the permanent storage created.
