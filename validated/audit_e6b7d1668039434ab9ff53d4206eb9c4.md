### Title
Cross-organization webhook forgery: signature authenticates `repository.owner.login`, but writes act on unbound `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-tenant Shipit deployments (one `GitHubApp`/`webhook_secret` per GitHub organization), `WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` read straight out of the attacker-supplied JSON body, while every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `PullRequest` handlers, etc.) resolves the repository/stack to act on using a *different* field from the same body: `repository.full_name`. Because the signature only proves the payload was HMAC-signed with the secret belonging to whatever organization `repository.owner.login` claims, and nothing binds that value to `repository.full_name`, a party who legitimately controls the webhook secret for OrgA can forge a single payload where `owner.login == "OrgA"` (making the signature valid) but `full_name == "OrgB/some-repo"` (causing the handler to write to OrgB's stack).

### Finding Description
`verify_signature` computes the signing identity from the unverified payload: [1](#0-0) 
`repository_owner` is derived purely from `params.dig('repository', 'owner', 'login')`: [2](#0-1) 
`Shipit.github(organization: repository_owner)` looks up the per-organization `GitHubApp`/`webhook_secret` from config, as documented for multi-org setups: [3](#0-2) [4](#0-3) 

Once `verify_webhook_signature` succeeds (HMAC over the entire raw body, computed with OrgA's secret) all handlers dispatched from `create` resolve the *target* repository independently, using `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Nothing in `verify_signature` or in the handlers cross-checks that `repository.full_name` actually starts with `repository.owner.login`. Since both fields sit inside the same JSON body that is only integrity-protected as a whole by the HMAC of whichever secret the attacker holds (OrgA's), an attacker who owns/administers OrgA's GitHub App (and therefore knows OrgA's `webhook_secret`) can:
1. Craft a JSON body with `"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/target-repo"}`, plus valid `ref`/`after` fields for a `push` event.
2. Sign it with `HMAC-SHA1(OrgA_webhook_secret, body)` and set `X-Hub-Signature`.
3. `verify_signature` selects OrgA's `GitHubApp` (via `repository_owner` = `"OrgA"`), and the signature validates successfully.
4. `PushHandler` (or any other handler) then resolves the stack via `Repository.from_github_repo_name("OrgB/target-repo")`, and calls `stack.sync_github(expected_head_sha: ...)` — a write against OrgB's stack, triggered purely by OrgA's webhook credential.

This breaks the trust equality the engine implicitly relies on: **{organization that authenticated the request} == {repository/organization that gets written to}**. The engine verifies the former from an unauthenticated field and never re-derives or checks it against the latter.

### Impact Explanation
This is an unauthorized cross-repository/cross-tenant write: an entity holding a legitimate webhook secret for one onboarded GitHub organization can trigger `GithubSyncJob`, review-stack archive/unarchive actions, commit status writes, or membership/team mutations against a completely different organization's stacks that it has no authorization over, in an instance that hosts multiple organizations behind a single Shipit deployment. This matches the "cross-repository writes" Critical impact criterion, since the entity forging the payload is not a GitHub App/organization with any privilege on the targeted repository.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple GitHub organizations (an explicitly documented, supported configuration), and (b) the attacker to control (or compromise) the webhook secret of at least one onboarded organization — which is a much lower bar than repository write access, GITHUB_TOKEN, or admin credentials for the *victim* organization. No session, API token, or GitHub App private key for the target org is needed.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after signature verification, re-derive the authorized organization from the verified secret binding and assert that `repository.full_name`'s owner segment (or `organization.login` for org-scoped events) matches `repository_owner` exactly before dispatching to handlers; reject (422) on mismatch instead of trusting `full_name` unconditionally in `Handler#repository_name`.

### Proof of Concept
```ruby
# Config: multi-org deployment (see test/dummy/config/secrets_double_github_app.yml)
# OrgOne's webhook_secret is "orgone-secret" (known to the attacker who administers OrgOne's GitHub App)
# OrgTwo/target-repo is a stack the attacker has no access to.

payload = {
  ref: "refs/heads/master",
  after: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  repository: {
    full_name: "OrgTwo/target-repo",   # handler writes here
    owner: { login: "OrgOne" }         # controller authenticates against this org's secret
  }
}.to_json

signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "orgone-secret", payload)

post "/webhooks", params: payload, headers: {
  "X-Github-Event" => "push",
  "X-Hub-Signature" => signature,
  "Content-Type" => "application/json"
}
# => 200 OK, verify_webhook_signature passes using OrgOne's secret,
#    but PushHandler enqueues GithubSyncJob against OrgTwo/target-repo's stack.
```
