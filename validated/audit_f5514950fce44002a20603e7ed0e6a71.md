### Title
Cross-organization signature confusion allows a tenant's own webhook secret to forge webhooks for another tenant's repository, provisioning attacker-controlled ReviewStacks - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to validate a webhook against using `repository.owner.login` from the JSON body, while `OpenedHandler#repository` (and every other `pull_request` handler) later resolves the target `Repository` from the independent `repository.full_name` field. Because nothing enforces that `full_name`'s owner segment matches `repository.owner.login`, a caller who legitimately controls one tracked GitHub organization's webhook secret can forge a signed request naming a *different* tenant's repository in `full_name`, causing Shipit to provision a ReviewStack under the victim repository with attacker-controlled branch/sha.

### Finding Description
The broken binding is the assumption:
`org_whose_secret_verified_the_signature == org_that_owns_the_repository_the_handler_acts_on`

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (line 59-62) and calls `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp`, then verifies `X-Hub-Signature` against **that org's** `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
- Once verified, `WebhooksController#create` (line 10-15) passes the *entire raw JSON* — unchanged — to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.
- `OpenedHandler#repository` (app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54) independently reads `params.repository.full_name` and resolves it via `Shipit::Repository.from_github_repo_name`, which simply does `github_repo_name.downcase.split('/')` and a DB lookup (app/models/shipit/repository.rb:53-56) — with no reference back to `repository_owner`/the org whose secret was used for verification.
- `OpenedHandler`'s `ExplicitParameters` schema only `requires :repository { requires :full_name, String }` (lines 33-35) — it never requires or validates `repository.owner.login`, so that field is free-form and only used transiently for secret selection.
- `OpenedHandler#process` then calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which builds `stack_attributes` including `branch: params.pull_request.head.ref` (app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:87-90) — fully attacker-controlled.

Attacker's exact request: Shipit is deployed multi-tenant (`Shipit.github(organization:)` / `github_app_config`, confirmed by `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md` "Using Multiple Github Applications"). The attacker owns/administers `OrgOne` — a legitimately tracked org — and therefore knows `OrgOne`'s `webhook_secret` (they configured it when installing their own GitHub App). They POST directly to `/webhooks` with:
```json
{
  "action": "opened",
  "number": 2,
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "pull_request": { "head": { "ref": "attacker-branch", "sha": "..." }, ... }
}
```
signed with `HMAC-SHA1(OrgOne_webhook_secret, raw_body)` in `X-Hub-Signature`. `verify_signature` looks up `Shipit.github(organization: "OrgOne")`, validates successfully against the attacker's own known secret, and the request proceeds. `OpenedHandler` then resolves `repository` to `OrgTwo/victim-repo` (a repo the attacker does not own or control) and provisions a ReviewStack there using the attacker's branch/sha, if `review_stacks_enabled` + `provisioning_behavior_allow_all` (or matching label rules) are configured on that victim repository.

Existing guards do not catch this: `verify_signature` only proves the request was signed by *some* known org's secret, not that the secret's org matches the repository being acted upon; `drop_unhandled_event` and `ExplicitParameters` only validate shape/presence, not owner/full_name consistency; `Repository.from_github_repo_name` and `NullRepository` provide no cross-tenant check.

### Impact Explanation
An attacker who legitimately administers one Shipit-tracked GitHub organization can, using only their own known webhook secret, write a new `Stack`/`ReviewStack` record under a completely different tracked repository (a different tenant), with attacker-chosen `branch` and pull-request `head.sha`. If that stack is later provisioned/deployed (provisioning queue + deploy pipeline act on `branch`/`sha`), this results in an unauthorized deploy of attacker-controlled code against the victim repository's infrastructure — a cross-tenant write and unauthorized-deploy scenario, matching "a payload for one repository mutating another's stack... or an unauthorized deploy" (Critical). This is repeatable for every PR the attacker opens and against any repository whose `full_name` the attacker chooses, as long as `review_stacks_enabled`/provisioning behavior permits it on the victim side.

### Likelihood Explanation
Requires a genuinely multi-tenant Shipit deployment (multiple GitHub orgs configured under `secrets.github`, as documented and tested) and requires the attacker to administer (or otherwise know the webhook secret of) at least one tracked org — this is a real, supported, documented configuration, not a hypothetical one. Given that, the exploit costs a single crafted HTTP POST with a correctly computed HMAC using the attacker's own known secret; no GitHub API access, no privileged Shipit role, and no victim secret is needed. It is fully repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature`/`#create`, or centrally in `Shipit::Webhooks::Handlers::Handler`, enforce that the organization used to verify the signature matches the owner segment of `repository.full_name` (and reject if they diverge) before dispatching to any handler; alternatively, resolve `Shipit::Repository` in the controller using the already-verified `repository_owner` and pass the resolved repository (not raw payload) into handlers.

### Proof of Concept
minitest under `test/controllers/webhooks_controller_test.rb` (extending existing patterns):
```ruby
test "cross-org repository.full_name is not bound to the org whose secret verified the signature" do
  # victim repo tracked under "OrgTwo"
  victim = Repository.create!(owner: "orgtwo", name: "victim-repo",
                               review_stacks_enabled: true, provisioning_behavior: :allow_all)

  payload = {
    action: "opened",
    number: 2,
    pull_request: {
      id: 1, number: 2, url: "http://x", title: "x", state: "open",
      additions: 1, deletions: 1,
      head: { sha: "deadbeef", ref: "attacker-branch" },
      user: { login: "attacker" }, assignees: [], labels: []
    },
    repository: { owner: { login: "OrgOne" }, full_name: "orgtwo/victim-repo" },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", orgone_webhook_secret, payload)
  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = signature

  assert_difference -> { victim.review_stacks.count }, 1 do
    post :create, body: payload, as: :json
  end

  stack = victim.review_stacks.last
  assert_equal "attacker-branch", stack.branch  # binding org_of(secret) == org_of(full_name) is violated
end
```
Both sides of the claimed equality (`org whose secret verified signature` = `"OrgOne"` vs `org owning the mutated repository` = `"orgtwo"`) diverge, and the assertion on `stack.branch` demonstrates the resulting unauthorized write under the victim's repository.
