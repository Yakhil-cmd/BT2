### Title
Unserialized concurrent processing of private (indivisible) payment chains allows double-spend of the same hidden source output - (File: indivisible_asset.js / private_payment.js)

### Summary
The CVE analog describes a race condition: "installation and removal of such regions was not properly serialized," i.e., two concurrent operations against the same shared resource were allowed to interleave without a lock, corrupting state. In ocore, the private-payment save path (`private_payment.js` → `indivisible_asset.js`/`divisible_asset.js`) validates and inserts a private payment chain using a duplicate-check `SELECT` followed by `INSERT`/`UPDATE` statements inside its own DB transaction, but — unlike the public-unit path in `validation.js`, which explicitly serializes per-author validation with `mutex.lock(arrAuthorAddresses, ...)` — there is no mutex protecting the private-payment validate-and-save critical section across concurrent invocations that reference the same source output.

### Finding Description
For public units, `validate()` in [1](#0-0)  acquires `mutex.lock(arrAuthorAddresses, ...)` before validating/checking double-spends and writing, ensuring that concurrent units authored by the same address are processed serially, which is what allows `checkForDoublespends` in [2](#0-1)  to safely detect conflicts.

Private payments do not go through this code path. `validateAndSavePrivatePaymentChain` in [3](#0-2)  opens its own `db.takeConnectionFromPool()` + `BEGIN`/`COMMIT` transaction, performs a duplicate check query, and then calls into `indivisible_asset.js` or `divisible_asset.js` to insert/update the spend without any `mutex.lock` on a key derived from the private output being spent (e.g., `src_unit-src_message_index-src_output_index` or the asset). The actual spend commit occurs in `validateAndSavePrivatePaymentChain` in [4](#0-3) , which issues `UPDATE outputs SET ... is_spent=? ... WHERE ... AND is_spent=0` per chain element, and in `divisible_asset.js` at [5](#0-4) , which issues `UPDATE outputs SET is_spent=1 WHERE unit=? AND message_index=? AND output_index=?` without an `is_spent=0` guard at all.

Two private payment chains spending the same hidden output can be received concurrently, e.g., through `handleOnlinePrivatePayment` in [6](#0-5)  from two different peers/cosigners, or through `handleSavedPrivatePayments` which processes chains "in parallel" via `async.each` in [7](#0-6) . Each concurrent call obtains a fresh pooled connection, runs `initPrivatePaymentValidationState`/`validatePrivatePayment` (which reads `spend_proofs`, checks the source output, and validates the payment — see [8](#0-7)  and `initPrivatePaymentValidationState` at [9](#0-8) ) inside its own transaction, and neither validation step re-checks or locks a globally-shared "is this private output already claimed by a concurrently-in-flight chain" state before both transactions independently decide the payment is valid and commit. Because the source output is *private* (hidden), it is not covered by the on-chain `inputs` `UNIQUE(src_unit, src_message_index, src_output_index, is_unique)` constraint in the same way public double-spends are guarded and reconciled by `checkForDoublespends`+`acceptDoublespends` (which explicitly is gated by `mutex.lock(["private_write"])` only for the *doublespend-acceptance* bookkeeping in [10](#0-9) , not for the initial private-chain save path itself).

This mirrors CVE-2022-42334's root cause: a resource (here, the private output "slot") can be concurrently claimed by two racing consumers because the installation (spending) operation lacks serialization across the whole validate+write critical section, only individual SQL statements are atomic, not the multi-step check-then-act sequence across separate transactions/connections.

### Impact Explanation
If two conflicting private payment chains referencing the same hidden source output are received close together (e.g., a malicious payer sends the same private coin to two different recipients/devices, or replays it through two peers), both recipients' independent validate-and-save transactions can pass validation (each unaware of the other's uncommitted state) and commit, each believing they legitimately received the private funds. This is a double-spend of a private asset output causing one or both counterparties to accept funds that do not exist, i.e., unauthorized spending / inflation of usable private balance without any corresponding on-chain conflict resolution, since private outputs aren't visible to the wider network for cross-checking.

### Likelihood Explanation
Exploitability requires only that the payer construct and privately send two spend chains for the same hidden output to two different receiving parties (or to the same wallet via two network paths) close together in time — an unprivileged asset issuer/payment counterparty action fully within the "private-payment counterparty" reachable surface. `handleSavedPrivatePayments` explicitly processes multiple queued chains "in parallel" (`async.each`), and `handleOnlinePrivatePayment` handles each incoming private payment independently per call, increasing the likelihood of concurrent processing windows.

### Recommendation
Serialize private-payment chain validation and saving per conflicting resource (e.g., mutex-lock on a key derived from `asset` + `src_unit`/`src_message_index`/`src_output_index`, or per-output claim) for the entire duration of validate+write, analogous to the `mutex.lock(arrAuthorAddresses, ...)` used for public units in `validation.js`. Additionally, ensure the divisible-asset spend update in `divisible_asset.js` includes an `AND is_spent=0` guard (matching the indivisible path) and that a failed/zero-row update is treated as an error (double-spend) rather than silently succeeding.

### Proof of Concept
1. Payer constructs a private (hidden) divisible or indivisible asset output belonging to a source coin they control.
2. Payer builds two independent private payment chains spending the *same* source output: chain A to victim/device 1, chain B to victim/device 2.
3. Payer sends chain A directly to device 1 and, at approximately the same time, sends chain B to device 2 (or via two different hubs/peers), so that `network.handleOnlinePrivatePayment`/`handleSavedPrivatePayments` on each receiving node processes its chain concurrently on a separate DB connection.
4. Because `private_payment.js`'s `validateAndSavePrivatePaymentChain` ( [3](#0-2) ) and the underlying asset-specific save routines ( [4](#0-3) , [5](#0-4) ) do not hold a lock across the validate-then-write sequence keyed on the spent output, both device 1 and device 2 can independently validate their chain as OK (since neither sees the other's in-flight/uncommitted spend) and commit, each crediting the recipient with funds derived from the same source coin.

**Note on confidence**: I was not able to fully trace every intermediate call in `divisible_asset.js`'s `validateDivisiblePrivatePayment` (particularly whether `validatePayment`/`checkForDoublespends` performs any additional cross-connection defense for private assets beyond the `mutex.lock(["private_write"])` used only when *accepting* a detected doublespend). Given index size limits, some file contents may not be fully available; a full Devin session with complete file access would allow confirming whether any other layer (e.g., a global light/full-node private-payment mutex outside the reviewed files) already mitigates this race.

function initPrivatePaymentValidationState(conn, unit, message_index, payload, onError, onDone){
	conn.query(
		"SELECT payload_hash, app, units.sequence, units.version, units.is_stable, lb_units.main_chain_index AS last_ball_mci, lb_units.timestamp AS last_ball_timestamp \n\
		FROM messages JOIN units USING(unit) \n\
		LEFT JOIN units AS lb_units ON units.last_ball_unit=lb_units.unit \n\
		WHERE messages.unit=? AND message_index=?", 
		[unit, message_index], 
		function(rows){
			if (rows.length > 1)
				throw Error("more than 1 message by index");
			if (rows.length === 0)
				return onError("message not found");
			var row = rows[0];
			if (row.sequence !== "good" && row.is_stable === 1)
				return onError("unit is final nonserial");
			var bStable = (row.is_stable === 1); // it's ok if the unit is not stable yet
			if (row.app !== "payment")
				return onError("invalid app");
			try{
				if (objectHash.getBase64Hash(payload, row.version !== constants.versionWithoutTimestamp) !== row.payload_hash)
					return onError("payload hash does not match");
			}
			catch(e){
				return onError("failed to calc payload hash: "+e);
			}
			var objValidationState = {
				last_ball_mci: row.last_ball_mci,
				last_ball_timestamp: row.last_ball_timestamp,
				arrDoubleSpendInputs: [],
				arrInputKeys: [],
				bPrivate: true
			};
			var objPartialUnit = {unit: unit};
			storage.readUnitAuthors(conn, unit, function(arrAuthors){
				objPartialUnit.authors = arrAuthors.map(function(address){ return {address: address}; }); // array of objects {address: address}
				// we need parent_units in checkForDoublespends in case it is a doublespend

					objPartialUnit.parent_units = prows.map(function(prow){ return prow.parent_unit; });
					onDone(bStable, objPartialUnit, objValidationState);
				});
			});
		}
	);
