## Title
Webhook signature is scoped to an organization but the `status` event handler writes to any commit sha across all stacks/repositories - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController` authenticates an incoming GitHub webhook by selecting a per-organization app/secret from `repository_owner` (derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`) and validating the HMAC signature against the raw body [1](#0-0) . This proves only that *some* payload for that organization was signed by that organization's configured GitHub App secret. However, for the `status` event, the handler that actually mutates state, `StatusHandler`, ignores the repository/organization scope entirely and looks up commits globally by `sha`: [2](#0-1) 

### Finding Description
The binding that should hold is: *organization/repository the signature authenticates* == *repository whose commit state is written*. It does not hold for the `status` event.

- `verify_signature` picks the GitHub App/secret using `repository_owner`, which for a `status` webhook is `params.dig('repository', 'owner', 'login')` [3](#0-2) . This only proves the payload was legitimately signed for *that organization*.
- `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` [4](#0-3) .
- `StatusHandler#process` never consults `params.repository` (its own declared params schema doesn't even require a `repository` key) and instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . `Commit.where(sha:...)` is a global, cross-stack, cross-repository query on the `commits` table with no `stack_id`/repository filter.
- `create_status_from_github!` then updates the commit's status and, critically, triggers downstream effects: `Hook.emit(:commit_status/:deployable_status, ...)` and `stack.schedule_merges` when the new status is `pending` or `success` [6](#0-5) . A commit's deployability is gated by its status: `deployable?` requires `success? && !blocked?` [7](#0-6) , and `schedule_continuous_delivery` queues an actual deploy once a commit becomes deployable [8](#0-7) .

Because commit SHAs are content-addressed and identical across any fork/mirror/clone of a repository, any account able to trigger a signed `status` webhook from an organization Shipit trusts (e.g., the owner/maintainer of an unrelated, low-value repository or fork under that org, who can push commits and post arbitrary commit statuses via the GitHub Status API on their own repo) can forge a `status` payload whose `sha` matches a real commit belonging to a *different, security-sensitive* stack tracked by Shipit under the same organization. The webhook signature will validate (it is legitimately signed by GitHub for that organization), but `StatusHandler` applies the status to every `Commit` row in the entire database sharing that sha, regardless of which repository/stack it actually belongs to.

### Impact Explanation
This breaks the "organization that authenticated" vs "repository that is written" binding called out in the analog rules. By forging a successful CI status for a commit sha that also exists in a protected stack, an attacker can flip that commit's `deployable?` state to true, trigger `stack.schedule_merges`/`ContinuousDeliveryJob`, and cause an unauthorized deploy of a commit whose real CI never passed on the actual protected repository - matching the Critical "unauthorized deploy" impact category.

### Likelihood Explanation
Requires only that the attacker control (or have status-posting rights on) some repository under an organization already configured in Shipit, and that a target commit sha exist verbatim in both that repository and a protected stack's repository (trivially true for forks, mirrors, or shared history/cherry-picks/vendoring). No Shipit session, API token, or repository write access to the protected repo itself is needed - only the ability to post a GitHub status on any repo under a trusted org, which GitHub allows to any collaborator with `repo:status` scope.

### Recommendation
`StatusHandler` (and by extension any other handler relying on cross-stack lookups) must scope its query by the repository identified in the payload, e.g. resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and constrain `Commit.where(stack: repository.stacks, sha: params.sha)` instead of an unscoped `Commit.where(sha:)`, mirroring the pattern already used correctly in the pull-request handlers (`repository_name`/`stacks` helpers in `Handler`) [9](#0-8) .

### Proof of Concept
1. Attacker owns/maintains `org/low-value-repo` under an organization `org` that has a Shipit-configured GitHub App/webhook secret.
2. Attacker pushes a commit whose sha collides with (or is cherry-picked/shared from) a commit `abc123` that also exists in `org/protected-repo`, tracked as a Shipit stack.
3. Attacker uses the GitHub Statuses API on `org/low-value-repo` to set `state=success` for sha `abc123`; GitHub delivers a correctly-signed `status` webhook to Shipit for `org`.
4. `verify_signature` validates the signature using `org`'s secret and passes [10](#0-9) .
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123')`, which matches the commit row belonging to `org/protected-repo`'s stack, and calls `create_status_from_github!`, marking it `success` and potentially unlocking continuous delivery/merge for the protected stack [2](#0-1) .

        def process
          Commit.where(sha: params.sha).each do |commit|

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
