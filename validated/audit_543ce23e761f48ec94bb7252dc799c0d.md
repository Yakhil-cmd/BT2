### Title
Missing size validation on `prefix_base64` in modern `ViewState` JSON queries allows unbounded memory allocation on RPC nodes - ([File: chain/jsonrpc/src/api/query.rs])

### Summary
The legacy `QueryRequest` path (`path`/`data` positional args) caps decoded byte size at `QUERY_DATA_MAX_SIZE` (10KB) via `parse_bs58_data`, but the modern JSON schema for `QueryRequest::ViewState`/`RpcViewStateRequest` deserializes `prefix_base64` (and `after_key_base64`) directly into a `StoreKey` with no size bound before `validate_view_state_pagination` runs. An unprivileged caller can submit a `query`/`EXPERIMENTAL_view_state` JSON-RPC request with an arbitrarily large base64-encoded `prefix_base64` field, forcing the node to allocate and decode a large byte buffer per request.

### Finding Description
`RpcQueryRequest::parse` in `chain/jsonrpc/src/api/query.rs` only applies `QUERY_DATA_MAX_SIZE`/`parse_bs58_data` inside `parse_path_data`, the soft-deprecated "path/data" positional encoding [1](#0-0) . For the modern JSON encoding, `QueryRequest::ViewState` deserializes `prefix_base64` straight into `near_primitives::types::StoreKey` via serde [2](#0-1) , and the equivalent `RpcViewStateRequest` used by `EXPERIMENTAL_view_state` does the same [3](#0-2) .

The only validation applied to the parsed prefix, `validate_view_state_pagination`, checks `include_proof` vs. pagination conflicts and that `after_key` starts with `prefix` — it performs no length/size check on `prefix` or `after_key` at all [4](#0-3) . This function is called from both `RpcQueryRequest::parse` [5](#0-4)  and `RpcViewStateRequest::parse` [6](#0-5) .

Downstream, `TrieViewer::view_state` in `runtime/runtime/src/state_viewer/mod.rs` builds `query = trie_key_parsers::get_raw_prefix_for_contract_data(account_id, prefix)` and performs `iter.seek_prefix(&query)` / `iter.seek(...)` [7](#0-6) . Trie `seek`/`seek_prefix` cost is governed by actual matching trie depth, not by the raw byte length of the supplied key, so an oversized prefix does not translate into an unbounded *trie scan* — a non-matching multi-megabyte prefix will fail the descent quickly once it diverges from existing trie nodes. The genuinely unbounded cost here is the **allocation and base64 decode of the attacker-supplied byte vector itself** (and its retention through request parsing, `TrieKey` prefix construction, and IPC forwarding to the view-client actor), which scales linearly with the size the attacker chooses to send, with no cap in this code path.

### Impact Explanation
This does not cause unbounded trie/database scanning (the per-page item/byte caps `MAX_VIEW_STATE_PAGE_ITEMS`/`MAX_VIEW_STATE_PAGE_BYTES` already bound result-set size for paginated queries [8](#0-7) ), so it does not threaten protocol determinism, balances, or consensus. The realistic impact is resource consumption (memory allocation, decode CPU, IPC message size) on the RPC-serving node proportional to the size of `prefix_base64`/`after_key_base64` the attacker chooses to send, repeated per request. This is bounded ultimately by whatever HTTP body-size limit exists in front of the JSON-RPC server (not confirmed in the reviewed code), so severity depends on that external limit, which could not be verified within scope.

### Likelihood Explanation
Trivially reachable by any unprivileged client with network access to a public RPC endpoint — no signed transaction, account, or special permission is required, since `query`/`EXPERIMENTAL_view_state` are unauthenticated read-only RPC calls. The only gating factor is whether an HTTP payload-size limit is enforced upstream of `RpcQueryRequest::parse`/`RpcViewStateRequest::parse`, which was not found in `chain/jsonrpc/src/lib.rs` during this review.

### Recommendation
Add an explicit size cap (e.g., a small constant analogous to `QUERY_DATA_MAX_SIZE`) on `prefix` and `after_key` inside `validate_view_state_pagination` in `chain/jsonrpc/src/api/mod.rs`, applied uniformly to both the legacy and modern JSON `ViewState` paths, rejecting requests whose decoded prefix/after_key exceed a reasonable bound (state key prefixes have no legitimate use case beyond a few hundred bytes).

### Proof of Concept
Integration test in `chain/jsonrpc/jsonrpc-tests/tests/rpc_query.rs`: send `query`/`EXPERIMENTAL_view_state` requests with `prefix_base64` of increasing decoded size (1KB, 1MB, 10MB) against an arbitrary `account_id`, and assert that requests above a defined threshold are rejected with `RpcParseError` before reaching `TrieViewer::view_state`, rather than being accepted and processed.

const QUERY_DATA_MAX_SIZE: usize = 10 * 1024;

/// Parses base58-encoded data from legacy path+data request format.
fn parse_bs58_data(max_len: usize, encoded: String) -> Result<Vec<u8>, RpcParseError> {
    // N-byte encoded base58 string decodes to at most N bytes so there’s no
    // need to allocate full max_len output buffer if encoded length is shorter.
    let mut data = vec![0u8; max_len.min(encoded.len())];
    match bs58::decode(encoded.as_bytes()).into(data.as_mut_slice()) {
        Ok(len) => {
            data.truncate(len);
            Ok(data)
        }
        Err(bs58::decode::Error::BufferTooSmall) => {
            Err(RpcParseError("Query data size is too large".to_string()))
        }
        Err(err) => Err(RpcParseError(err.to_string())),
    }
}

/// Rejects view_state pagination arguments the trie viewer can't serve.
fn validate_view_state_pagination(
    prefix: &[u8],
    after_key: Option<&[u8]>,
    limit: Option<NonZeroU32>,
    include_proof: bool,
) -> Result<(), RpcParseError> {
    // TODO(#15612): a resumed page seeks with AccessOptions::NO_SIDE_EFFECTS, so it
    // doesn't record the trie path from the root and the proof can't chain back to
    // the state root. Until we record the seek's nodes, reject proof + pagination.
    if include_proof && (after_key.is_some() || limit.is_some()) {
        return Err(RpcParseError(
            "include_proof is not supported with paginated view_state \
             (after_key_base64 / limit)"
                .to_string(),
        ));
    }
    if let Some(after_key) = after_key {
        if !after_key.starts_with(prefix) {
            return Err(RpcParseError(
                "after_key_base64 must start with prefix_base64".to_string(),
            ));
        }
    }
    Ok(())
}
