### Title
Cross-stack CI status disclosure via unscoped `stack` lookup in `CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` authenticates an `ApiClient` token but resolves the target `Stack` with an unscoped lookup (`Stack.from_param!`), bypassing the per-token stack restriction (`ApiClient#stack_id`) that every other API controller enforces through `BaseController#stacks`/`#stack`. This breaks the binding "the stack a token authorizes" vs. "the stack the request actually touches," the exact analog class named in the report's rules.

### Finding Description
`Shipit::Api::BaseController` scopes stack access to the token's authorized stack when the `ApiClient` is bound to one: [1](#0-0) 

`ApiClient` supports being scoped to a single `stack` (`belongs_to :stack, optional: true`), and permission checks (`check_permissions!`) only validate the operation/scope string (e.g. `read:stack`), never which specific stack ID the token is bound to: [2](#0-1) 

`CCMenuController` overrides `authenticate_api_client` to accept a bare query-string `token`, and separately overrides `stack` to resolve directly against the global `Stack` collection instead of the token-scoped `stacks` method used elsewhere: [3](#0-2) 

Because `stack` calls `Stack.from_param!(params[:stack_id])` (not `stacks.from_param!(params[:stack_id])`), any `stack_id` supplied in the request is honored regardless of the authenticated `ApiClient`'s `stack_id` binding. `require_permission :read, :stack` only calls `check_permissions!('read', 'stack')`, which merely checks that `"read:stack"` is in the client's `permissions` array — it never compares `current_api_client.stack_id` to `params[:stack_id]`.

### Impact Explanation
A token created and scoped to Stack A (e.g., via `CCMenuUrlController`, which mints an `ApiClient` for the current user with `permissions: %w[read:stack]`) can be used to query `GET /api/*stack_id/ccmenu` for **any** stack B by supplying B's `stack_id` in the URL. This discloses another stack's deploy/task status, last build label/time and lock reason (`stack.deploys_and_rollbacks`, `stack.lock_reason`, etc. — rendered via `shipit/ccmenu/project`), i.e., unauthenticated-for-that-stack read of stack state. This matches the report's High-severity impact bucket: "unauthenticated read of stack state, task streams or deploy output" reached by escalating a token's authorized scope to an unauthorized stack.

### Likelihood Explanation
Exploitation requires only possession of *any* valid, minimally-permissioned CCMenu/API token (`read:stack`) — something routinely embedded in CI dashboards, IRC bots, or CCMenu clients, and often leaked via URLs/logs since the token is a GET query parameter. No privileged account, GitHub credentials, or webhook secret is needed; the attacker simply changes the `stack_id` path segment. This is a straightforward, low-effort parameter-substitution attack once any token scoped to one stack is known.

### Recommendation
In `Shipit::Api::CCMenuController#stack`, resolve the stack through the token-scoped `stacks` collection (as `BaseController` does), e.g. `stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot be used to read information about stacks outside its `stack_id` binding. Additionally, consider having `check_permissions!`/`require_permission` explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` for all stack-scoped endpoints, closing this class of bug at the authorization layer rather than relying on each controller's `stack` method to re-implement scoping correctly.

### Proof of Concept
1. As an authorized user, create an `ApiClient` scoped to Stack A: `POST /api_clients` with `permissions: [read:stack]`, then set its `stack_id` to Stack A (via `ApiClientsController#update`/DB, or via `CCMenuUrlController#client` if it is scoped to a stack in your deployment).
2. Obtain that client's `authentication_token`.
3. Issue: `GET /api/<stack-B-owner>/<stack-B-name>/<stack-B-env>/ccmenu.xml?token=<stack-A-scoped-token>`
4. Observe the response returns Stack B's build/deploy status (`assert_payload 'name', ...`), even though the token was only ever authorized for Stack A — confirmed by the fact that `CCMenuController#stack` (unlike `BaseController#stack`) never filters through `current_api_client.stack_id`.

Note: I could not find code in `app/**` that actively assigns a non-nil `stack_id` to `ApiClient` instances created by `CCMenuUrlController#client` (it currently omits `stack:` when calling `create_with`), so in the shipped default flow the CCMenu client itself is unscoped. However, `ApiClient` explicitly supports `belongs_to :stack, optional: true` and the app's own `ApiClientsController`/model allow any `ApiClient` (including ones with `stack_id` set through other flows or future features) to be used against `CCMenuController`; the vulnerable code path (`Stack.from_param!` bypassing `stacks`) is present regardless of how the scoped client was created, and I could not verify from the index whether other supported creation paths (e.g., programmatic API client creation with a `stack_id`) exist outside `app/**`/`lib/shipit/**`. A Devin session with full repo access would be needed to confirm all code paths that can produce a stack-scoped `ApiClient` and validate the PoC end-to-end against a running instance.

# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
  end

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
