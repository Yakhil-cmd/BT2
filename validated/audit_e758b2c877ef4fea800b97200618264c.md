### Title
Webhook signature verification selects the GitHub org's secret from an unauthenticated payload field, while event handlers act on a different, unbound field — allowing cross-organization forged events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, a value read straight out of the unauthenticated request body [1](#0-0) . That org name comes from `params.dig('repository', 'owner', 'login')` or, if absent, `params.dig('organization', 'login')` [2](#0-1) . Once a signature is accepted (or trivially accepted because that org has no `webhook_secret` configured — `verify_webhook_signature` returns `true` when `webhook_secret` is blank [3](#0-2) ), the entire raw payload is dispatched to handlers, which resolve the actual target repository/commit from a *different* payload field with no cross-check against the field used for authentication.

### Finding Description
`Handler#repository_name` (the base class used by `PushHandler`, `CheckSuiteHandler`, etc.) reads `payload.dig('repository', 'full_name')` to find the `Repository`/`Stack` to act on [4](#0-3) , which is independent of `repository.owner.login`/`organization.login` used earlier to select the verifying secret. `StatusHandler` is even less scoped: it matches `Commit.where(sha: params.sha)` across the *entire* database with no repository/org filter at all [5](#0-4) .

Shipit explicitly supports multiple GitHub organizations, each with its own (optional) `webhook_secret` — the shipped multi-org config fixture shows an org configured with `webhook_secret:` left blank [6](#0-5) . Because `verify_webhook_signature` short-circuits to `true` when the org's `webhook_secret` is unset, any request that claims (via `organization.login` or `repository.owner.login`) to originate from that unsecured org passes signature verification unconditionally — while the rest of the JSON body (which drives `repository.full_name` and `sha` lookups) is fully attacker-controlled and never re-validated against the authenticated org.

This breaks exactly the binding described in the rules as: *"an organization that authenticated versus the repository that is written."* The code implicitly assumes `repository.owner.login == repository.full_name`'s owner segment (true for genuine GitHub-generated payloads), but never enforces it, so a forged payload can decouple the two.

### Impact Explanation
An unprivileged external attacker (no Shipit session, API token, or GitHub write access required) who can post to the public `/webhooks` endpoint and pick an org with no configured `webhook_secret` (or a leaked/guessable one for a different org) can:
- Force `PushHandler`/`CheckSuiteHandler` to run `stack.sync_github` against **any repository tracked by the Shipit instance**, regardless of which org it belongs to, by putting the target's `full_name` in the body while satisfying the signature check with the unrelated, unsecured org's identity [7](#0-6) .
- Forge a `status` event for **any commit sha in the database**, since `StatusHandler` has no repository scoping, potentially flipping a commit's CI status to `success` and triggering continuous deployment on an unrelated stack — an unauthorized deploy.

This matches the required Critical/High impact bar (unauthorized deploy / cross-repository writes) via a boundary that requires no privileged credential.

### Likelihood Explanation
Requires only that the Shipit deployment hosts more than one GitHub organization and that at least one has no `webhook_secret` set (a state the engine's own config format explicitly allows and ships as an example), or that an attacker otherwise learns one org's secret. Given multi-tenant Shipit installations are a documented, supported configuration, this is a realistic misconfiguration rather than a theoretical edge case.

### Recommendation
After computing `repository_owner`/`organization` for secret selection, verify that the same value is consistent with the owner segment of `repository.full_name` used later by handlers, and reject the request otherwise. Additionally, `StatusHandler` (and any handler using `Commit.where(sha: ...)`) should scope lookups to the repository derived from the authenticated organization rather than a global, unscoped query. Consider also disallowing/loudly warning on `webhook_secret` being blank in production configurations.

### Proof of Concept
1. Configure (or find) a Shipit instance with two GitHub orgs, where `OrgTwo` has `webhook_secret: nil` (as in the shipped fixture) [6](#0-5) .
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": {"login": "OrgTwo"},
  "repository": {"owner": {"login": "OrgTwo"}, "full_name": "OrgTwo/anything"},
  "sha": "<sha of a commit belonging to a stack in OrgOne>",
  "state": "success"
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` and `verify_webhook_signature` returns `true` immediately because `OrgTwo`'s `webhook_secret` is blank [8](#0-7) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` unscoped and marks the `OrgOne` commit's status as success, potentially triggering `ContinuousDeliveryJob` and an unauthorized deploy on `OrgOne`'s stack [5](#0-4) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
