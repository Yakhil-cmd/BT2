### Title
CCMenu ApiClient minted without stack scoping grants cross-stack read access to CCMenu XML - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`Shipit::CCMenuUrlController#client` mints an `ApiClient` with `permissions: %w[read:stack]` but never sets `stack: stack`, so `stack_id` remains `nil`. Because `Shipit::Api::CCMenuController` resolves the target stack via `Stack.from_param!(params[:stack_id])` directly instead of the stack-scoping `stacks` helper used elsewhere in `Api::BaseController`, the resulting token is not restricted to any single stack and can be replayed against any stack's `cc_menu.xml`.

### Finding Description
The broken binding: `current_api_client.stack_id` should equal the single stack `stack.id` the CCMenu URL is being minted for, i.e. `client.stack_id == stack.id`. In practice, `CCMenuUrlController#client` (app/controllers/shipit/ccmenu_url_controller.rb:15-18) does:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

`stack:` is never passed, so `ApiClient#stack_id` is `nil` (`stack` is `belongs_to :stack, optional: true`, app/models/shipit/api_client.rb:8). The client is also memoized per-user by `name: 'CCMenu Client'`/`creator:`, so the same `ApiClient` record (and thus the same `authentication_token`) is reused across every stack the user visits `GET /stacks/:owner/:repo/:env/cc_menu_url` for.

Even setting aside the missing `stack:` assignment, `Shipit::Api::CCMenuController` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) overrides `stack` as:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This bypasses `Api::BaseController#stacks` (app/controllers/shipit/api/base_controller.rb:74-76), which is the only place that would restrict a stack-scoped `ApiClient` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`). `Api::BaseController#require_permission!` (line 82-84) only calls `current_api_client.check_permissions!(operation, scope)`, which checks the `permissions` array (`read:stack`) but never checks `stack_id` against the requested stack. So even if the bug in `CCMenuUrlController#client` were fixed to pass `stack:`, `CCMenuController` would still ignore that scoping because it never calls `stacks.from_param!`.

Attacker flow: an unprivileged, authenticated user with read access only to stack A visits `GET /stacks/:owner/:repo/:env/cc_menu_url` for stack A, minting/reusing their `CCMenu Client` `ApiClient` and receiving `token`. They then send `GET /api/stacks/:stackB/cc_menu.xml?token=<token>` for stack B (any stack, including ones they have no access to). `ApiClient.authenticate` (app/models/shipit/api_client.rb:24-27) only verifies the signed client id via `Shipit.api_clients_secret`—it performs no stack check—so the request succeeds and `show` renders stack B's deploy/task data.

### Impact Explanation
An authenticated but otherwise unprivileged user can obtain a single long-lived (non-expiring) token from a CCMenu URL for any stack they can view, and reuse that same token to read CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, deploy/rollback history) for every stack in the Shipit instance, including stacks they have no authorization to view. This is an unauthenticated-for-target-stack read of stack state, matching the "High: escalation ... unauthenticated read of stack state, task streams or deploy output" impact category. It is fully repeatable (the token does not expire and is reused across requests) and the blast radius spans every stack managed by the Shipit instance (cross-tenant read).

### Likelihood Explanation
Preconditions are minimal: any logged-in Shipit user with read access to at least one stack (the normal, lowest-privilege authenticated role) can trigger `fetch`. No GitHub secrets, webhook signing, or elevated Shipit role is required. The attacker only needs to know or guess/enumerate another stack's `:owner/:repo/:env` param to target it via `/api/stacks/:stackB/cc_menu.xml`. This is trivially reproducible with a single authenticated HTTP request followed by a second unauthenticated-context request bearing the leaked token.

### Recommendation
1. In `CCMenuUrlController#client`, scope the `ApiClient` to the specific stack, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')` so each stack gets its own scoped client/token.
2. Fix `Shipit::Api::CCMenuController#stack` to use the inherited scoping helper (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so stack-scoped `ApiClient`s are actually enforced.
3. Optionally add a validation/model-level check that CCMenu-issued clients must always have a non-nil `stack_id`.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (conceptual, no live GitHub required)
test "ccmenu url token is not scoped to the requesting stack" do
  stack_a = shipit_stacks(:shipit)                      # stack the user can access
  stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'bar'), branch: 'main', environment: 'other')

  session[:user_id] = @user.id  # authenticated, unprivileged user

  get :fetch, params: { owner: stack_a.repository.owner, repo: stack_a.repository.name, env: stack_a.environment }
  client = ApiClient.find_by(creator: @user, name: 'CCMenu Client')

  assert_nil client.stack_id  # binding violated: should equal stack_a.id

  token = JSON.parse(response.body)['ccmenu_url'][/token=([^&]+)/, 1]

  # Reuse token against an unrelated stack via the API controller
  api_get :show, params: { stack_id: stack_b.to_param, token: CGI.unescape(token) }, controller: 'shipit/api/ccmenu'
  assert_response :ok   # should have been :forbidden / :unauthorized for stack_b
end
```
