### Title
Bridge ERC20 Transfer Does Not Account for Fee-on-Transfer Tokens, Causing Counterpart Bridge Insolvency - (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` tokens from the user via `safeTransferFrom`, but for fee-on-transfer tokens the bridge actually receives fewer tokens than that nominal amount. The function then emits a `RequestValueTransfer` event with the original `_value` as `valueOrTokenId`. The counterpart bridge operator reads this event and calls `handleERC20Transfer` with the same `_value`, releasing the full `_value` from the counterpart bridge's reserves. Over repeated transfers, the counterpart bridge releases more tokens than were ever locked on the source side, draining its reserves and causing insolvency.

---

### Finding Description

In `requestERC20Transfer`, the bridge first pulls tokens from the caller:

```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

For a fee-on-transfer token with fee rate `f`, the bridge actually receives `(_value + _feeLimit) * (1 - f)` tokens, not `_value + _feeLimit`. [1](#0-0) 

`_requestERC20Transfer` then calls `_payERC20FeeAndRefundChange`, which calls `safeTransfer(feeReceiver, fee)` and `safeTransfer(from, feeRefund)`. Each of these also incurs the transfer fee, so the bridge's balance is reduced by the full nominal amounts (`fee` and `feeRefund`) while the recipients receive less. The bridge's net token balance after the full flow is approximately `_value*(1-f) - _feeLimit*f`, not `_value`. [2](#0-1) 

Despite this, `_requestERC20Transfer` emits `RequestValueTransfer` with `valueOrTokenId = _value` — the original nominal amount, not the actual amount held: [3](#0-2) 

The bridge operator on the counterpart chain reads this event and calls `handleERC20Transfer(_value, ...)`, which unconditionally transfers `_value` tokens to the recipient: [4](#0-3) 

The deficit per transfer is `(_value + _feeLimit) * f`. After N transfers, the counterpart bridge has released `N * _value` tokens but the source bridge only ever locked `N * (_value*(1-f) - _feeLimit*f)` tokens. The counterpart bridge will eventually be unable to fulfill withdrawals.

The same issue applies to the 1-step path via `onERC20Received` / `ERC20ServiceChain.requestValueTransfer`, which calls `transfer(bridge, _amount + _feeLimit)` before invoking `onERC20Received` with the original `_amount`: [5](#0-4) 

There is no guard in `BridgeTokens.registerToken` that prevents fee-on-transfer tokens from being registered: [6](#0-5) 

---

### Impact Explanation

The counterpart bridge (in lock mode) releases `_value` tokens per request, but the source bridge only ever locked `_value*(1-f) - _feeLimit*f` tokens. This is an unauthorized transfer of bridged assets: users on the destination chain can withdraw more tokens than were deposited on the source chain. The counterpart bridge's token reserves are drained at a rate proportional to the token's transfer fee, eventually reaching insolvency where legitimate withdrawals cannot be fulfilled.

---

### Likelihood Explanation

Any user can call `requestERC20Transfer` or `requestValueTransfer` with a registered fee-on-transfer ERC20 token. No privileged access is required. The bridge owner must have registered the token, but registration itself has no fee-on-transfer guard. The impact accumulates with every transfer, so even a single registered fee-on-transfer token is sufficient to trigger the insolvency path over time.

---

### Recommendation

In `requestERC20Transfer`, measure the actual balance change after `safeTransferFrom` and use that as the effective locked amount in the emitted event:

```solidity
function requestERC20Transfer(...) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)) - balanceBefore;
    // derive actual _value and _feeLimit from actualReceived proportionally, or revert if token is fee-on-transfer
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, actualFeeLimit, _extraData);
}
```

Alternatively, disallow fee-on-transfer tokens by checking that `actualReceived == _value + _feeLimit` and reverting otherwise.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token (e.g., 5% fee on every transfer) on the source chain.
2. Register it on the source bridge via `registerToken`.
3. Alice calls `requestERC20Transfer(token, bob, 100, 10)` (value=100, feeLimit=10).
   - Bridge calls `safeTransferFrom(alice, bridge, 110)` → bridge receives `110 * 0.95 = 104.5` tokens.
   - Bridge pays bridge fee (e.g., 5 tokens) to feeReceiver → bridge balance decreases by 5, feeReceiver gets `5 * 0.95 = 4.75`.
   - Bridge refunds `feeRefund = 10 - 5 = 5` to Alice → bridge balance decreases by 5, Alice gets `5 * 0.95 = 4.75`.
   - Bridge net balance: `104.5 - 5 - 5 = 94.5` tokens locked.
   - Event emits `valueOrTokenId = 100`.
4. Counterpart bridge operator calls `handleERC20Transfer(value=100)` → releases 100 tokens to Bob.
5. Deficit per transfer: `100 - 94.5 = 5.5` tokens.
6. After 18 such transfers, the counterpart bridge has released `1800` tokens but only `1701` were ever locked. The counterpart bridge is insolvent.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
