### Title
Cross-organization webhook forgery via decoupled signature-verification identity and event-processing identity - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). However, once the signature check passes, every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, and the individual pull-request handlers) independently resolves the *target* repository/stack to act on using a completely different field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. Because these two fields are never checked for consistency, an entity that only controls the webhook secret of Organization A can forge a payload whose `repository.owner.login` is `A` (so the HMAC verifies) but whose `repository.full_name` names a repository belonging to unrelated Organization B tracked by the same Shipit instance, causing Shipit to process the event as if it legitimately came from B.

### Finding Description
- `verify_signature` picks the app/secret to check against based on `repository_owner`: [1](#0-0) [2](#0-1) 

- The signature itself is verified purely as an HMAC over the whole raw body using the secret configured for that resolved organization: [3](#0-2) 

- After verification, the full parsed body is dispatched unmodified to handlers: [4](#0-3) 

- Handlers determine which local `Repository`/`Stack` to act on using `repository.full_name`, a field independent from `repository.owner.login` used for verification: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

- Shipit explicitly supports and documents hosting multiple, unrelated GitHub organizations on a single instance, each with its own webhook secret keyed by organization name: [9](#0-8) [10](#0-9) 

**Binding that should hold but doesn't:** the organization whose secret authenticated the HMAC (`repository_owner` == `params.dig('repository','owner','login')`) must equal the organization/repository the handler subsequently mutates state for (`payload.dig('repository','full_name')`). Before a malicious PR: Org A can only forge events for repositories under Org A because attackers normally don't know Org B's secret. After the crafted payload (owner.login = "OrgA", full_name = "OrgB/victim-repo", signed with OrgA's known webhook secret), the equality `authenticated_org == acted_on_repository_owner` is broken — Shipit processes the payload as an authentic OrgB event.

An actor with legitimate admin control of their own Organization A's GitHub App (a normal customer of a multi-tenant Shipit deployment) knows Org A's `webhook_secret` and can therefore compute a valid `X-Hub-Signature` for an arbitrary JSON body. Nothing forces `repository.owner.login` (used only to pick the verification key) to match `repository.full_name` (used to pick the target `Repository`/`Stack`) — they are independent, attacker-supplied keys in the same JSON document.

### Impact Explanation
By setting `repository.owner.login` to their own organization (to pass HMAC verification) and `repository.full_name` to another tenant's `owner/repo` string tracked by the same Shipit instance, an attacker who has no relationship to that other repository can inject arbitrary, fully-controlled webhook events against it:
- `PushHandler` will trigger `stack.sync_github` for the victim stack.
- Pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`) will create, archive, or unarchive Review Stacks for the victim repository using attacker-chosen PR numbers/branches (`params.pull_request.head.ref`), driving `ReviewStackProvisioningQueue` to provision and deploy against a real branch of the victim's repository.

This crosses a tenant/repository trust boundary that the signature check is supposed to enforce, enabling unauthorized triggering of deploy/provisioning workflows against a repository the attacker does not control — matching the "unauthorized deploy" / cross-repository-write impact class. This requires the target instance to be configured for multiple organizations (a documented, supported configuration), and requires the attacker to legitimately administer at least one of the other organizations' GitHub App on the same Shipit install.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented feature) where the attacker administers one tenant's GitHub App/webhook secret — a normal, unprivileged-relative-to-the-victim position, not requiring any Shipit session, API token, or the victim org's credentials. Crafting the forged payload only requires knowledge of one's own webhook secret, which every onboarded organization has.

### Recommendation
In `WebhooksController#verify_signature`, after resolving `repository_owner` and verifying the signature, re-validate that the same `repository_owner`/organization is the one referenced by `repository.full_name` (or `organization.login`) before dispatching to handlers — i.e., bind the verified organization identity to the specific repository the handlers will act on, rejecting payloads where they diverge.

### Proof of Concept
Not independently executable without full runtime access; based on static code review of `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, and the pull-request handlers cited above. Conceptually:
1. Attacker administers `OrgA`'s GitHub App on a shared Shipit instance that also hosts `OrgB/victim-repo`, and knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `pull_request` webhook JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"`, `action = "opened"`, and a real branch name of `OrgB/victim-repo` as `pull_request.head.ref`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature verifies successfully.
5. `Shipit::Webhooks.for_event('pull_request')` handlers run and resolve the target repository via `payload.dig('repository', 'full_name')` = `"OrgB/victim-repo"`, creating/provisioning a Review Stack for `OrgB`'s repository despite the request never being authenticated by `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
