### Title
Contract hash computed from unescaped, delimiter-joined fields allows boundary-shifting collisions that let a counterparty forge contract content behind an agreed hash - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js`'s `getHashSrc`/`getHash` and `prosaic_contract.js`'s `getHash`/`getHashV1` build the hash that uniquely identifies a peer-to-peer escrow/legal contract by concatenating free-text, attacker-controlled fields (`title`, `text`, party names, amounts, addresses) with either no separator at all or a fixed low-entropy delimiter string, without validating that the field values themselves cannot contain that delimiter or shift the field boundaries. This is the same class of bug as the reported Express `response.links()` issue: unsanitized user-controlled values are concatenated into a structurally significant string (there, an HTTP header; here, a hash pre-image) using characters that are not excluded from the untrusted input, allowing an attacker to make two semantically different payloads produce/parse as the same structural value.

### Finding Description
`getHashSrc` in `arbiter_contract.js` computes the pre-image of a contract's identifying hash as: [1](#0-0) 

For any contract dated on/before `NEW_HASH_DATE` (`2026-11-01`) — which is the branch currently in effect since today is before that date — the fields `title`, `text`, `creation_date`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, `asset` are joined with `""`, i.e. no separator whatsoever: [2](#0-1) 

Because `title` and `text` are attacker-supplied strings of arbitrary length with no length prefixing, escaping, or delimiter-exclusion check, an author of the contract offer can shift characters across the `title`/`text` boundary (e.g. `title="A", text="BC"` vs `title="AB", text="C"`) and still hash-verify to an identical `contract.hash`. Even the "fixed" branch that uses `exports.DELIMITER = "[|#|]"` at line 19-20/200 does not reject `title`/`text` values that themselves contain the delimiter substring, so the collision is still constructible there as well: [3](#0-2) 

The same root cause exists in `prosaic_contract.js`, where both hash versions concatenate `title + text + creation_date` with zero separator: [4](#0-3) 

This contrasts with the codebase's own hardened primitive, `getSourceString` in `string_utils.js`, which explicitly rejects any string containing the join character (`\x00`) precisely to prevent this class of ambiguity: [5](#0-4) 

`arbiter_contract.js` and `prosaic_contract.js` do not reuse this safe primitive for their hash, instead rolling their own unescaped concatenation — falling into exactly the pitfall `getSourceString` was designed to avoid.

`contract.hash` is the value both paired devices, cosigners, and (for arbiter contracts) the external arbiter rely on as the tamper-evident identifier of the agreed contract terms: it is generated on `createAndSend`, stored/keyed by hash, shared to cosigners, and referenced throughout dispute handling (`openDispute`, `appeal`) where the *encrypted* `title`/`text`/party-name content is sent to the arbiter for adjudication of the escrowed funds: [6](#0-5) [7](#0-6) 

### Impact Explanation
Because the hash does not uniquely bind the (title, text, party names, arbiter, amount, asset) tuple — different splits of these attacker-controlled fields collide — a malicious contract counterparty can present one payload during initial signing/acceptance (`respond`) and later have the arbiter or cosigners see a different logical title/text split that hashes identically. Since the arbiter's dispute ruling (which controls release of escrowed funds in a shared multisig address) is based on the decrypted `title`/`text`/party-name content sent at dispute time rather than on-chain validated data, this ambiguity can be leveraged to misrepresent contract terms while preserving a hash that both parties "agreed to," undermining trust in the escrow arbitration and enabling fraudulent fund release — i.e., unauthorized spending of the escrowed asset. This falls under "wallet and contract message handling," one of the explicitly in-scope reachable paths.

### Likelihood Explanation
Any unprivileged paired device that proposes or accepts an arbiter/prosaic contract can freely choose `title` and `text` content, so constructing a colliding pair requires no special privilege — only knowledge of the join logic (which is public in this open-source module). The old, delimiter-less branch (`join("")`) is the currently-active code path for all contracts created before `2026-11-01`, making exploitation trivial (no need to even worry about avoiding a delimiter string).

### Recommendation
Replace the ad-hoc string concatenation in `getHashSrc` (`arbiter_contract.js`) and `getHash`/`getHashV1` (`prosaic_contract.js`) with the existing collision-resistant `getSourceString`/`getJsonSourceString` primitives from `string_utils.js`/`object_hash.js`, which length/type-tag each field and reject values containing the join character, guaranteeing an unambiguous mapping from content to hash.

### Proof of Concept
1. Party A proposes an arbiter contract with `title = "Pay"`, `text = "100 now"`, and fixed `creation_date`, `payer_address`, `arbiter_address`, etc. (pre-`2026-11-01` branch, join with `""`).
2. Compute `hash1 = sha256(title + text + creation_date + ... )`.
3. Construct an alternate split `title2 = "Pay100"`, `text2 = " now"` with all other fields identical — `hash2 = sha256(title2 + text2 + creation_date + ...) === hash1` because the concatenation has no boundary marker.
4. Party A sends the benign-looking `objContract` (hash1 payload) for acceptance/signing, then later supplies the alternate title/text split (still validating against the same stored `hash`) to the arbiter during `openDispute`, misrepresenting the agreed terms while the hash-based identity check still passes.
