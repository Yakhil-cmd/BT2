### Title
Webhook Signature Verification Selects Organization From an Unverified Field While Handlers Act On a Different, Unbound Repository Field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / HMAC secret to check a webhook against using a field read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`), while the event handlers that actually act on the payload (creating jobs, syncing stacks, closing PRs, etc.) key off a *different* field of the same body (`repository.full_name`). Nothing binds these two fields together. Combined with the fact that `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as "signature check passes", an attacker can forge a webhook that is "authenticated" against any organization configured without a webhook secret, yet whose payload acts on a completely unrelated, fully-secured organization's repository.

### Finding Description
`repository_owner` is derived purely from the request body, not from any authenticated source: [1](#0-0) 

This value selects the GitHub App configuration/secret used for HMAC verification: [2](#0-1) 

`Shipit.github(organization:)` looks the org up in the multi-tenant `secrets.github` map (each org has its own independent config, including its own `webhook_secret`): [3](#0-2) 

Crucially, `verify_webhook_signature` unconditionally returns `true` whenever that organization's `webhook_secret` is blank, i.e. verification is a no-op for orgs onboarded without a configured secret: [4](#0-3) 

Once "verified" (or forcibly passed), the controller dispatches to handlers using the raw parsed JSON — the same attacker-controlled body: [5](#0-4) 

Every handler resolves the target repository/stack from `repository.full_name`, a field completely independent of `repository_owner`: [6](#0-5) [7](#0-6) 

Because the HMAC verification path only cares about `repository.owner.login` and the write path only cares about `repository.full_name`, an attacker can submit:
```json
{
  "repository": {
    "owner": { "login": "OrgWithNoWebhookSecret" },
    "full_name": "TargetOrg/target-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
`verify_signature` resolves `Shipit.github(organization: "OrgWithNoWebhookSecret")`, whose `webhook_secret` is blank, so verification short-circuits to `true` regardless of the (missing or garbage) `X-Hub-Signature` header. The `push` handler is then invoked, resolves the stack via `TargetOrg/target-repo` (a repository belonging to a completely different, fully-secured organization), and enqueues a sync/job against it.

This is exactly the class of binding break called out in the rules: **"an organization that authenticated versus the repository that is written."** The equality that should hold — `organization used to verify signature == owner of repository acted upon` — is never enforced; the two are independent, attacker-controlled JSON keys.

### Impact Explanation
This is a webhook authentication bypass: any organization onboarded into a multi-org Shipit deployment without a `webhook_secret` (an explicitly supported, optional configuration per `GitHubApp#initialize`, which does `@webhook_secret = @config[:webhook_secret].presence`) becomes a skeleton key allowing an unauthenticated internet client to inject arbitrary, unsigned webhook events that are processed as if verified — and have those events act on stacks/repositories belonging to *other*, properly secured organizations. Depending on the enabled handlers this can trigger `GithubSyncJob` (push), close/merge status transitions (pull_request handlers), archive/unarchive review stacks (label handlers), or fabricate commit statuses (status handler) for any tracked stack, all without possessing any of the credentials the engine is supposed to require (no `ApiClient` token, no webhook secret, no GitHub App key). This satisfies the required "authentication bypass" impact category.

### Likelihood Explanation
Exploitability depends only on the existence of at least one organization configured in `secrets.github` without a `webhook_secret` — which the engine's own configuration schema treats as a normal, optional setting (nothing enforces `webhook_secret` presence at load time). Any multi-tenant Shipit instance that onboards one lower-trust or "internal testing" GitHub App without a secret exposes this bypass for every other organization it hosts, since the org used for verification and the repository acted upon are never cross-checked. No credentials, session, or GitHub access are required by the attacker.

### Recommendation
In `WebhooksController#verify_signature`, after resolving the organization and verifying the signature, additionally verify that the resolved `repository_owner` matches the owner segment of `repository.full_name` (and, more importantly, require a webhook secret to be configured for every organization capable of triggering stack-affecting webhook events — refuse to process webhooks, or at least restrict handler side effects, for organizations with a blank `webhook_secret`). Alternatively, bind the handler's repository resolution to the same authenticated organization identity used in `verify_signature`, rather than re-reading an independent field from the unauthenticated body.

### Proof of Concept
1. Configure (or identify) a Shipit deployment with `secrets.github` containing at least two organizations, one of which has `webhook_secret` unset (this is an explicitly supported configuration, not a misconfiguration the engine rejects).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, and body:
```json
{
  "repository": {
    "owner": { "login": "OrgWithNoWebhookSecret" },
    "full_name": "SecuredOrg/production-app"
  },
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
3. `verify_signature` resolves the GitHub App for `OrgWithNoWebhookSecret`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is blank [4](#0-3) .
4. `PushHandler` is invoked with the full payload and resolves the stack via `repository.full_name = "SecuredOrg/production-app"` [7](#0-6) , enqueuing a `GithubSyncJob`/state change for a stack the attacker never authenticated against.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
