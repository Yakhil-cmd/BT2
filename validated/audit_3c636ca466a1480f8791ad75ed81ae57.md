### Title
`Pallet::set_pool_admin` in `pallet-asset-rewards` doesn't check that `new_admin` isn't the default/unspendable `AccountId` - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet_asset_rewards::Pallet::set_pool_admin` and its trait implementation `RewardsPool::set_pool_admin` let the current pool admin reassign a reward pool's `admin` field to an arbitrary `AccountId`, including `T::AccountId::default()` (the all-zero account, which nobody holds a private key for). Once this happens there is no recovery path: every privileged action on that pool (`set_pool_reward_rate_per_block`, `set_pool_admin` itself, `set_pool_expiry_block`) is gated purely by `pool_info.admin == *caller`, with no `ForceOrigin`/root override. This is the exact analog of the reported `MainToken.set_mint_multisig()` bug: a permission-holder setter that accepts a "zero"/unownable address as the new authority with no validation, permanently bricking that authority.

### Finding Description
`set_pool_admin` is exposed as extrinsic call index 5: [1](#0-0) 

which delegates to the trait method: [2](#0-1) 

The implementation only checks `pool_info.admin == *admin` (i.e., that the caller is currently the pool's admin) before overwriting `pool_info.admin = new_admin.clone()`. There is no `ensure!(new_admin != T::AccountId::default())` or any other exclusion of an unownable account. The `RewardsPool` trait definition itself documents no such invariant either: [3](#0-2) 

Once `admin` is set to the zero account, every other privileged pool operation fails permanently because they all gate on `pool_info.admin == *admin`: [4](#0-3) 

This is the direct structural analog to the reported `MainToken.set_mint_multisig()` issue: a setter for a privileged "authority" field (multisig / pool admin) accepts any address, including an unownable default/zero value, with no on-chain safeguard, causing irreversible loss of that authority.

By contrast, the repo's own `pallet-psm` explicitly defends against this exact class of bug for its analogous `full_admin`/`emergency_admin` fields by rejecting the `None` origin: [5](#0-4) 

This shows the maintainers are aware of and actively guard against "unownable authority" assignment elsewhere in the codebase, but the same protection is missing in `pallet-asset-rewards::set_pool_admin`.

I could not fully confirm from the index whether `T::CreatePoolOrigin` is configured as a fully permissionless (`EnsureSigned`) origin in the shipped runtimes (`asset-hub-rococo`, `asset-hub-westend`, `substrate/bin/node/runtime`, `staking-async` parachain runtime) — the grep found the identifier but the config values weren't retrieved before the tool budget ran out. This matters for the "real user entry / no privileged role" requirement: the caller of `set_pool_admin` must already be the pool's `admin` (there is no special governance/root requirement to *become* an admin — `create_pool`'s `admin` parameter is caller-supplied and any signed account meeting `CreatePoolOrigin` can create a pool and become its own admin). If `CreatePoolOrigin` is `EnsureSigned` (or any permissionless signed-origin filter) in a live runtime, this is directly reachable by an ordinary, non-privileged user acting on their own pool.

### Impact Explanation
A pool admin (an ordinary user who created their own reward pool, not a privileged/governance role) who mistakenly calls `set_pool_admin` with the default `AccountId` (or any address whose key is provably unknown) permanently loses the ability to:
- increase the reward rate (`set_pool_reward_rate_per_block`),
- extend the pool's expiry (`set_pool_expiry_block`),
- reassign the admin again (`set_pool_admin`).

There is no `ForceOrigin`/root escape hatch defined for these calls, so the pool becomes permanently unmanageable (frozen at its current reward rate/expiry, with no way to ever change it or recover the admin role). This matches the profile of the original report: irreversible loss of a privileged setter, not root/governance compromise. Given that funds inside the pool (staked/reward assets) are not directly stolen but pool governance is permanently bricked, this aligns with a Medium-severity, Substrate-analog of the reported Medium finding.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the pool's current admin (an ordinary signed account, not root) to call `set_pool_admin` with a bad value — either by mistake (fat-fingering a default/zero `AccountId`) or via front-end/tooling defaults that pre-fill an all-zero account. No attacker privilege is required beyond already being a pool admin, which any user can become by creating their own pool (assuming a permissionless `CreatePoolOrigin`, which I was unable to fully confirm in the runtime configs before running out of tool calls).

### Recommendation
In `RewardsPool::set_pool_admin` (and the dispatchable `Pallet::set_pool_admin`), add a check that `new_admin != T::AccountId::default()` (and/or disallow other well-known unownable IDs), returning a new error (e.g. `Error::<T>::InvalidAdmin`) before mutating `pool_info.admin`. Optionally, add a `ForceOrigin`-gated `force_set_pool_admin` recovery call, mirroring the pattern used elsewhere in the codebase (e.g. `pallet_nfts::force_collection_owner`, `pallet_assets::force_asset_status`) so that governance/root can recover bricked pools even if the safeguard is bypassed.

This test was not run against the actual harness (no terminal access in this environment); it is provided as the exact minimal integration test a Devin session with repo/terminal access would need to execute against `substrate/frame/asset-rewards` to confirm the finding (existing sibling tests at `substrate/frame/asset-rewards/src/tests.rs:745-827` show the harness and assertions needed already exist and can be extended directly).

**Guards that fail to catch this:** none — `set_pool_admin`'s only check is `ensure!(pool_info.admin == *admin, BadOrigin)` on the *current* admin identity; there is no validation whatsoever on `new_admin`'s value.

**Deployment status:** `pallet-asset-rewards` is wired into `asset-hub-rococo`, `asset-hub-westend`, `substrate/bin/node/runtime`, and the `staking-async` parachain runtime (confirmed via `CreatePoolOrigin` references in those files), so the pallet is live in shipped runtimes; I was unable to verify the exact `CreatePoolOrigin` filter value in those runtimes before the tool budget was exhausted, which is needed to fully confirm the "no privileged prerequisite" requirement for the *initial* admin assignment (pool creation) — this should be verified in a follow-up session with full repo access.
