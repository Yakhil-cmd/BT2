### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name` / `organization.login` — allowing cross-organization stack manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `webhook_secret` used to validate the HMAC signature based on `repository.owner.login` (or `organization.login`) taken from the JSON body itself, but the handlers that actually mutate state key off a *different* field of the same body — `repository.full_name` (for `Repository.from_github_repo_name`) in `Handler#stacks`, or `organization.login` alone for team/membership creation. Because the entire raw POST body is attacker-controlled and only its bytes (not its semantic consistency) are covered by the signature, an operator/attacker who legitimately controls the webhook secret for *one* onboarded GitHub organization can forge a payload whose "owner" field matches their own org (so verification passes) while its "full_name"/target field points at a *different* organization's repository/stack, causing the engine to act on that other stack.

### Finding Description
`WebhooksController#verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
It looks up which `GitHubApp` (and thus which `webhook_secret`) to use via: [2](#0-1) 
i.e. `repository_owner` is read straight from the untrusted, attacker-supplied JSON body (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`).

Once `verify_webhook_signature` succeeds (which only checks that the HMAC-SHA1 of the *entire raw body* matches the secret for that organization), the whole payload is dispatched unmodified to handlers: [3](#0-2) 

Handlers, however, determine *which stack/repository to mutate* using a different field of the same body — `repository.full_name`: [4](#0-3) 

Since Shipit supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret` (`config/secrets.yml` → `github.<org>.webhook_secret`, as documented in `docs/setup.md` "Using Multiple Github Applications"), the "identity that is cryptographically authenticated" (the org whose secret validated the signature, `repository.owner.login`) is not the same field as "the repository that is written" (`repository.full_name`). An attacker who is a legitimate GitHub App admin (or otherwise possesses the webhook secret) for *one* onboarded organization (`OrgA`) can craft a JSON body directly against the public `/webhooks` endpoint with:
- `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")`'s secret verifies the HMAC they compute themselves), and
- `repository.full_name = "OrgB/victim-repo"` (an unrelated onboarded stack).

`PushHandler`, `StatusHandler`, and `CheckSuiteHandler` all resolve their target purely from `repository.full_name` (via `Handler#stacks`) or `sha`, with no cross-check that `full_name`'s owner equals the verified `repository.owner.login`: [5](#0-4) [6](#0-5) 

`MembershipHandler` similarly trusts `params.organization.login` to create/attach `Team`/`GithubHook::Organization` records and add/remove members, again without confirming it matches the org whose secret verified the request: [7](#0-6) 

This is the direct structural analog of the reported bug class: the field that is cryptographically authenticated (`repository.owner.login`) is not the field that is actually acted upon (`repository.full_name` / target stack), exactly mirroring "an organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker controlling the webhook secret for any single onboarded GitHub organization in a multi-tenant Shipit deployment can inject forged events (`push`, `status`, `check_suite`, `membership`) that are attributed to and processed against a completely different organization's stacks:
- `push` → triggers `GithubSyncJob`/`stack.sync_github`, forcing Shipit to re-sync commits for a foreign stack from GitHub (using the *victim* org's own GitHub App credentials, since `stack.github_app` is looked up from `repository.owner`, not the attacker's org) — this can mark stacks as accessible/inaccessible and pull in new commits, potentially advancing state used by auto-deploy.
- `status` → forges commit statuses (`create_status_from_github!`) on commits belonging to any tracked stack, since `StatusHandler` matches purely by `sha` with no repository scoping at all — this can flip CI status used to gate deploys.
- `check_suite` → schedules check-run refreshes for foreign commits.
- `membership` → creates arbitrary `Team`/`GithubHook::Organization` records and manipulates `Membership` (add/remove members) for an organization the attacker doesn't control, which feeds into `Shipit.github_teams` authorization checks used by `force_github_authentication`.

This crosses the "escalation into `Shipit.github_teams` authorization" and "cross-repository writes" thresholds called out as in-scope High/Critical impacts, since it lets a party who only controls one org's webhook secret forge state changes (including CI status, which gates deploys, and team membership, which gates authorization) against a stack/org they were never granted access to.

### Likelihood Explanation
This requires the attacker to know a `webhook_secret` for at least one organization onboarded to the shared Shipit instance (a realistic scenario for the documented "Using Multiple Github Applications" multi-tenant setup, where different teams/orgs each configure their own GitHub App and are not necessarily mutually trusted). No GitHub write access, Shipit session, or `ApiClient` token is needed — only a raw HTTP POST to `/webhooks` with a body the attacker fully controls and self-signs. This is a plausible operational configuration explicitly supported and documented by the engine, not a hypothetical misconfiguration.

### Recommendation
- After verifying the signature, cross-check that the organization used to select the secret (`repository.owner.login` / `organization.login`) matches the actual owner encoded in `repository.full_name` before dispatching to handlers; reject mismatches.
- In `Handler#stacks`, scope the resolved `Repository`/`Stack` to the verified organization (pass the verified org down from the controller) rather than trusting `repository.full_name` alone.
- In `StatusHandler`, scope commit lookups to commits belonging to stacks under the verified organization instead of matching on `sha` globally.
- In `MembershipHandler`, verify `params.organization.login` equals the organization whose secret validated the webhook.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `github:` in `secrets.yml` (`OrgA` and `OrgB`), each with its own `webhook_secret`, and onboard a stack for `OrgB/victim-repo`.
2. As someone who administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft a JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and `X-Github-Event: push`, then POST directly to `https://<shipit-host>/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature (attacker knows `OrgA`'s secret), yet `PushHandler` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` via `repository.full_name` and enqueues `GithubSyncJob` for `OrgB`'s stack — confirmed by the resolution logic at `app/models/shipit/webhooks/handlers/handler.rb:32-38` and `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, and by `WebhooksControllerTest`'s use of `repository_owner` fixtures independent from the acted-upon commit/stack (`test/controllers/webhooks_controller_test.rb:42-59`, `109-127`), which shows these two fields are already handled independently in the existing code/tests.
