## Analog Found

### Title
Unconfirmed AA-defined asset spending accepts an unstable, non-ancestor attestor list, bypassing attestor revocation and enabling node disagreement - ([File: storage.js])

### Summary
The CVE describes Apache CXF trusting decrypted/introspected token state without checking whether that state has actually been revoked — a stale-authorization-state bypass. The analogous ocore bug is in `readAsset`'s `addAttestorsIfNecessary` helper: when validating a payment for a `spender_attested` asset whose definition is not yet confirmed before last ball (the AA-defined-asset fast path), the code drops all stability/causality filtering when looking up the asset's current attestor list, so a payment can be validated against an attestor list that is neither stable, nor before the relevant last ball, nor even an ancestor of the unit being validated.

### Finding Description
`storage.readAsset()` looks up the attestor list for a `spender_attested` asset via `addAttestorsIfNecessary()`: [1](#0-0) 

```js
function addAttestorsIfNecessary(byAA = false){
    if (!objAsset.spender_attested)
        return handleAsset(null, objAsset);
    const before_last_ball_cond = byAA ? "" : `AND main_chain_index<=${+last_ball_mci} AND is_stable=1`;
    conn.query(
        "SELECT unit FROM asset_attestors CROSS JOIN units USING(unit) \n\
        WHERE asset=? " + before_last_ball_cond + " AND sequence='good' ORDER BY "+ (conf.bLight ? "units.rowid" : "level") + " DESC LIMIT 1",
        [asset],
        ...
```

When `byAA` is `true`, `before_last_ball_cond` becomes an empty string, so the query only requires `sequence='good'` and picks the single row with the highest `level` (or `rowid` for light nodes). It does **not**:
- require `is_stable=1`,
- require `main_chain_index <= last_ball_mci`, or
- verify that the chosen `asset_attestors` unit is an ancestor of / included in the unit whose payment is being validated (unlike the normal, non-AA path elsewhere in the file which does apply `is_stable`/`main_chain_index` bounds, and unlike `filterAttestedAddresses`, which explicitly excludes attestations invalidated by a subsequent address-definition change).

So for a `spender_attested` asset that an AA has just defined (still unconfirmed/unstable), any subsequent `spender_attested` check performed while that AA is processing a payment picks an attestor list purely by `level DESC`, ignoring stability and DAG inclusion. Because "unstable" sequence and `level` ordering can be observed differently by different nodes depending on which competing/parallel `asset_attestors` units they have received and their current tips, two honest nodes can legitimately pick two different attestor lists for the same asset while validating the same AA trigger/payment.

### Impact Explanation
An asset definer (which can itself be an unprivileged AA, reachable by any user who triggers it) can, immediately after defining a `spender_attested` asset via an AA, post multiple competing `asset_attestors` updates in different, still-unstable DAG branches (e.g. one adding the attacker's own address as an attestor, one without). Because the lookup used for AA-triggered asset spends ignores stability and ancestry, different nodes validating the same trigger/response chain can disagree on whether the `spender_attested` condition is satisfied for the payment, i.e., whether the same input/output set is valid. This is a concrete **node-disagreement-on-validity** condition (as required by the task's Validate criteria), which can split which chain nodes consider stable/serial for the asset transfer, and can be leveraged to have some nodes accept a transfer that others reject — enabling loss of consensus around AA fund movements for that asset.

### Likelihood Explanation
The path requires only: (1) creating (or using) an AA that defines a `spender_attested` asset, and (2) triggering the AA to perform a payment in that asset while posting competing `asset_attestors` messages in parallel unstable units before the asset/attestor state becomes stable. No special privileges, hub/peer, or network-level position are needed — a single poster with an AA and a couple of triggering units is sufficient, matching an "AA trigger sender / asset issuer" threat actor.

### Recommendation
In `addAttestorsIfNecessary` (storage.js), when `byAA` is true, still constrain the attestor-list lookup to units that are causally included in / an ancestor of the unit under validation (as is done elsewhere with `graph.determineIfIncludedOrEqual`), and prefer deterministic tie-breaking (e.g., by unit hash) rather than raw `level`/`rowid` ordering over unstable, non-ancestor candidates. At minimum, require the chosen `asset_attestors` unit to be included in the DAG ancestry of the triggering/response unit so that all nodes converge on the same attestor list.

### Proof of Concept
1. Deploy an AA whose `init`/`messages` define a new asset `A` with `spender_attested: true`, `attestors: [addr1]`, in response to a trigger.
2. Trigger the AA to define `A` (unit U1, still unstable).
3. Before U1/`A` stabilizes, from the definer address (or another mechanism the AA exposes), post two conflicting `asset_attestors` messages for asset `A` on two different, mutually non-including branches of the DAG: one listing `[addr1]`, one listing `[addr1, attacker_addr]`.
4. Trigger the AA again to pay out asset `A` to `attacker_addr`, relying on `spender_attested` validation via `storage.readAsset(..., bAcceptUnconfirmedAA=true)`.
5. Depending on which branch/level a given node has best-parented at validation time, `addAttestorsIfNecessary(true)` in [4](#0-3)  picks a different `asset_attestors` unit (no `is_stable`/`main_chain_index` filter, no ancestry check), so some nodes accept the AA's payment message as satisfying `spender_attested` while others reject it — producing disagreement on the unit's validity/sequence.
