### Title
Cross-organization webhook forgery bypasses CI status checks and triggers unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the **same untrusted JSON body** whose signature is being checked, but none of the webhook handlers subsequently re-validate that the rest of the payload (in particular `repository.full_name`, or in the `status`/`push` handlers, the bare commit `sha`) actually belongs to that authenticated organization.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . This value is only used to look up *which secret* to check the HMAC against; the HMAC itself is computed over the full raw body, which is entirely attacker-supplied when the attacker is composing the request rather than relaying a genuine GitHub delivery.

Shipit explicitly supports multiple organizations, each with its own independent `webhook_secret` [3](#0-2) . An operator/admin of one configured organization (e.g. because they self-serviced a GitHub App install for their own org on a shared/multi-tenant Shipit instance) legitimately knows *their own* `webhook_secret`. Nothing binds that secret to the specific `repository.full_name` inside the payload — only to `repository.owner.login`.

Downstream handlers key off different, unverified payload fields:
- `Handlers::Handler#stacks` resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [4](#0-3) , a field independent from `repository.owner.login` used for signature selection.
- `StatusHandler#process` is even broader: it matches `Commit.where(sha: params.sha)` globally across **all** stacks/repositories with no organization/repository scoping at all [5](#0-4) , then calls `commit.create_status_from_github!(params)`.

So an attacker who legitimately controls Org A's `webhook_secret` can sign a POST to `/webhooks` where `repository.owner.login = "OrgA"` (satisfies signature lookup) while `repository.full_name` (for push/pull_request handlers) or the `sha` (for the status handler) references a completely different, victim-owned stack/commit.

### Impact Explanation
Forged `status` events let the attacker directly create a `success` `Status` record for an arbitrary commit SHA in any stack tracked by the Shipit instance. `Status#state` feeds `Commit#deployable?` [6](#0-5)  and `add_status` schedules merges/continuous delivery when the new status is `pending` or `success` [7](#0-6) . This bypasses `ci.require`/`ci.blocking` gating documented in the README and can trigger an unauthorized deploy or unblock a merge queue for a stack the attacker has no legitimate access to — matching the High/Critical "unauthorized deploy" impact bucket, since it breaks the equality binding "organization whose secret authenticated the request" == "repository/commit the payload is allowed to mutate."

### Likelihood Explanation
Requires only that the attacker control a legitimately configured organization's webhook secret on a multi-org Shipit deployment (a normal, documented configuration in `config/secrets.*.yml`) — no repository write access, GitHub App private key, or Shipit session/API token is needed. This is a realistic scenario for any Shipit instance onboarding multiple, mutually-untrusted GitHub organizations.

### Recommendation
After selecting the GitHub App/secret by `repository_owner`, verify that `repository.full_name`'s owner segment (and, for `StatusHandler`, the resolved commit's stack's repository owner) matches the same `repository_owner` used for signature verification, rejecting the webhook otherwise. Scope `StatusHandler#process` to commits belonging to repositories owned by the authenticated organization rather than a bare global `sha` match.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (attacker-controlled, secret known to attacker) and `orgB` (victim, has a stack tracking `OrgB/victim-repo`, commit `deadbeef` currently not deployable).
2. Attacker crafts payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required",
  "repository": {"owner": {"login": "orgA"}, "full_name": "OrgB/victim-repo"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")`, verifies successfully against the attacker's own known secret.
5. `StatusHandler#process` finds `Commit.where(sha: "deadbeef...")` in Org B's stack (no ownership check) and creates a `success` `Status`, potentially unblocking a deploy/merge for a repository the attacker does not control.
