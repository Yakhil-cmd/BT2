### Title
Unauthenticated `membership` webhook can add any Shipit user to a `Shipit.github_teams` team, bypassing the GitHub-team authorization gate - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` only rejects a webhook if the resolved `GitHubApp#webhook_secret` for the org named in the payload is present and the HMAC fails; when no secret is configured for that org, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, i.e. the endpoint accepts arbitrary unauthenticated payloads. `Shipit::Webhooks::Handlers::MembershipHandler` then treats the payload as ground truth and mutates `Team#members` directly, and `Team` membership is exactly what `User#authorized?` checks to gate the entire application. This breaks the binding "GitHub team membership claimed by a webhook" == "actual verified GitHub team membership," the same class of unrestricted/unauthenticated-input-directly-drives-privileged-state bug described in the report (an unauthenticated caller reaching privileged logic that assumed a trusted, verified path).

### Finding Description
`webhook_secret` is explicitly documented and shipped in example configs as optional/`nil`: [1](#0-0) [2](#0-1) 

When it is unset (the documented default), `verify_webhook_signature` skips all HMAC verification: [3](#0-2) 

`WebhooksController` selects which app config (and therefore secret) to check purely from the attacker-controlled payload (`repository.owner.login` or `organization.login`), before any content is trusted: [4](#0-3) 

Once past that gate, `MembershipHandler#process` unconditionally applies the payload's claimed team/member/action to the database - it looks up (or creates) a `Team` purely by the numeric `github_id` in the payload and adds/removes the named `member`: [5](#0-4) 

`Team#add_member` performs no additional verification against GitHub: [6](#0-5) 

This directly feeds the authorization check every controller relies on: [7](#0-6) [8](#0-7) 

So the equality the engine assumes is: *"a `membership: added` event received on `/webhooks`" == "a real GitHub team-membership change, cryptographically attested by GitHub."* Without a configured `webhook_secret` (a state the engine explicitly documents as acceptable), that equality does not hold - the handler cannot distinguish a genuine GitHub delivery from a forged POST, yet it writes directly into the exact table (`Membership`/`Team`) that gates access to every Shipit stack, deploy, rollback and API-client management action.

### Impact Explanation
An attacker who has completed a normal (unprivileged) GitHub OAuth login against the Shipit instance - creating an ordinary, unauthorized `Shipit::User` row - can:
1. Discover the numeric GitHub `id` of one of the `Team`s configured in `Shipit.github_teams` (team IDs are visible via the public GitHub API for teams in orgs the attacker can see, or simply already exist as a `Team` row from a prior sync).
2. POST a forged `X-Github-Event: membership` payload to `/webhooks` with `action: "added"`, `team.id` set to that team's `github_id`, and `member.login` set to their own Shipit login.
3. Because no `webhook_secret` is required to be configured, `verify_signature` passes and `MembershipHandler` adds them to that `Team`.
4. `User#authorized?` now returns `true` for the attacker, granting full access to stacks, deploys, rollbacks, task creation and `ApiClient` management - i.e., "escalation into `Shipit.github_teams` authorization," which the scope rules classify as High, and in practice enables an unauthorized deploy/rollback (Critical).

### Likelihood Explanation
This requires only: (a) the target Shipit instance leaving `webhook_secret` unset, which is the documented default/optional configuration shown in the project's own example secrets files, and (b) the attacker completing a normal OAuth login (no special privilege) and knowing/guessing a target team's numeric GitHub ID. No repository write access, API token, or session compromise is needed - only network access to `/webhooks`, which is meant to be internet-reachable by design.

### Recommendation
- Make `webhook_secret` mandatory rather than optional, and refuse to boot (or reject all webhook traffic) when it is blank, instead of silently returning `true` from `verify_webhook_signature`.
- In `MembershipHandler`, cross-check the claimed membership change against the live GitHub API (e.g. re-fetch team membership) before mutating `Team#members`, rather than trusting the webhook payload as sole source of truth for an authorization-relevant record.
- Consider deriving `Shipit.github_teams` membership only through `Team#refresh_members!` (an authenticated pull from GitHub) rather than allowing webhook-driven pushes to mutate it.

### Proof of Concept
1. Deploy Shipit with `github.webhook_secret` left `nil` (per `config/secrets.development.example.yml` / `docs/setup.md`).
2. As attacker, complete GitHub OAuth login to Shipit, obtaining an ordinary unauthorized `User` record with `login: "attacker"`.
3. Send:
```
POST /webhooks
X-Github-Event: membership

{
  "action": "added",
  "team": { "id": <github_id of a Team in Shipit.github_teams>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/X" },
  "organization": { "login": "<org>" },
  "member": { "login": "attacker" }
}
```
4. `verify_signature` passes (no secret configured), `MembershipHandler#process` runs `team.add_member(member)`, and `attacker`'s `User#authorized?` becomes `true`, granting full unauthenticated-relative-to-webhooks access to the Shipit application.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event

    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
