## Title
Validation-time `throw Error` inside a per-address mutex leaks the lock and crashes the node, hanging future units from the same address - ([File: validation.js])

### Summary
CVE-2018-2771 is a MySQL Server "Locking" bug in which a difficult-to-exploit, network-reachable condition causes the server to hang or crash (availability-only impact). `ocore`'s unit-validation pipeline has an analogous locking construct: `validation.js`'s `validate()` acquires a mutex keyed on the unit's author addresses (`mutex.lock(arrAuthorAddresses, ...)`, [1](#0-0) ) and only releases it via an explicit `unlock()` callback reached at the very end of the `async.series` chain ( [2](#0-1) ). Several code paths reachable while validating an attacker-supplied payment input execute `throw Error(...)` from *inside* asynchronous `conn.query` callbacks that run underneath that lock, e.g. `throw Error("spending a stable temp-bad output " + input.unit)` and `throw Error("more than 1 src output")` in the transfer-input handling ( [3](#0-2) ), and the "unreachable code" throws inside `checkForDoublespends` ( [4](#0-3) ). Because these throws occur inside a DB-driver callback (not inside any surrounding `try/catch`), they are uncaught exceptions that crash the whole Node.js process; and because the throw happens before `unlock()` is ever invoked, the address-keyed mutex lock is never released if the crash is instead caught by an outer handler (e.g. a domain or process-level guard in a hardened deployment) — leaving the address permanently locked and any subsequent unit from that same address queued forever in `mutex.js`'s `arrQueuedJobs` ( [5](#0-4) ). The periodic deadlock detector that would have surfaced this is explicitly disabled (`//setInterval(checkForDeadlocks, 1000);`, [6](#0-5) ), so the condition is silent.

### Finding Description
`validation.validate()` locks on the unit's author addresses for the full duration of validation and only releases the lock through the `unlock` callback returned by `mutex.lock` at the tail of the `async.series` pipeline: [1](#0-0) [7](#0-6) .

Within that locked region, `validateMessages` → `validateMessage` → `validateInlinePayload` → `validatePayment` → `validatePaymentInputsAndOutputs` processes each payment `input` supplied by the unit poster. For a `"transfer"` input, the code looks up the referenced source output and, if that output is already stable in the DAG and its `sequence` is `'temp-bad'`, it does not return a normal validation error — it throws: [8](#0-7) 

This throw executes inside the callback of `conn.query(...)`, i.e., asynchronously, with no enclosing `try/catch` anywhere on the call stack (the `async.series`/`async.forEachOfSeries` wrappers in `async.js` do not catch exceptions thrown inside callbacks). An uncaught exception thrown from inside an async I/O callback terminates the Node.js process (`process.on('uncaughtException')` is not shown to be installed for this path). Similarly, `checkForDoublespends` throws `"unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit` and `"double spending "+type+" without double spending address?"` under conditions derived from DB rows the attacker can influence by choosing what/how to double-spend: [9](#0-8) .

An unprivileged unit poster fully controls the shape of the payment input (`input.unit`, `input.message_index`, `input.output_index`, and the double-spend pattern), and can time submission of a spend against an output that is in the `'temp-bad'` sequence while it becomes stable — a state combination the validation code labels "unreachable"/asserts against but does not defensively reject with a normal `callback(err)` path. Reaching it turns a validation error into a process-fatal exception.

Because the mutex for the author address(es) was acquired before this point and is released only by the `unlock` callback that is never reached when the process throws, the practical effects are:
1. Full node crash (denial of service) — matching the CVE's "frequently repeatable crash (complete DOS)" impact — from a single crafted unit.
2. In deployments that wrap validation with a process-level exception guard instead of crashing (e.g., restarting the async chain while keeping the mutex module state), the address-keyed lock in `mutex.js` is never released, and every subsequent unit involving that author address queues indefinitely in `arrQueuedJobs` ( [5](#0-4) ), i.e., a "hang" — matching the CVE's alternate "hang" impact. The self-check that would flag this (`checkForDeadlocks`) is commented out ( [10](#0-9) ), so the frozen validation queue for that address persists silently, effectively freezing that address from getting new units confirmed (funds/AA-interaction freezing).

### Impact Explanation
This is a network-reachable, unauthenticated (no special privilege) trigger: any unit poster can submit a joint that is routed into `validation.validate()` from `network.handleJoint` ( [11](#0-10) ) or the composer's own save path ( [12](#0-11) ). Successful exploitation:
- Crashes the full ocore node process (complete denial of service for that node/hub), matching CVSS Availability:High.
- Or, in the lock-leak variant, permanently starves validation for the affected author address, meaning the network can never confirm new units from that address — directly matching the "network unable to confirm new units" acceptance criterion.

No confidentiality or integrity impact is claimed (matches CVE's C:N/I:N/A:H profile).

### Likelihood Explanation
Reaching the `"spending a stable temp-bad output"` throw requires an attacker to construct a transfer input whose source output has already been marked `is_stable` in the DAG while retaining sequence `'temp-bad'`, and to time submission accordingly (`AC:H` — high attack complexity, matching the CVE's own AC:H rating). This requires understanding of how `temp-bad` sequences are expected to resolve to `final-bad` once stable, and crafting a race/edge case against that expectation — difficult but not implausible given the asynchronous stabilization pipeline in `main_chain.js`. The "unreachable code" throws in `checkForDoublespends` similarly require a specific double-spend/state combination that the code's authors did not expect but did not defensively guard with a normal error return.

### Recommendation
- Replace every `throw Error(...)` inside async DB-callback code paths reachable from unit validation (`validatePaymentInputsAndOutputs`, `checkForDoublespends`, and similar "should never happen" assertions in `validateAuthor`) with a normal `callback(err)` / `cb(err)` invocation that surfaces as `ifUnitError`, so malformed/edge-case attacker input degrades to a rejected unit rather than a process crash.
- Ensure the address-keyed `mutex.lock` in `validation.js` is released via a `finally`-style guarantee (e.g., wrap the `async.series` in a try/catch that always calls `unlock()` before re-throwing or logging) so a defensive fix elsewhere cannot silently leak the lock.
- Re-enable and tune `mutex.checkForDeadlocks` (currently disabled at [6](#0-5) ) or add equivalent monitoring/alerting for locks held or queued beyond a sane threshold, so lock leaks are detected instead of silently freezing an address's ability to confirm units.
- Add unit tests that specifically construct `temp-bad`-then-stable source outputs and duplicate/malformed spend-proof address combinations to confirm these paths return validation errors instead of throwing.

### Proof of Concept
Conceptual PoC (requires DB-state timing, hence AC:H, consistent with the CVE):
1. Attacker crafts unit A with a payment output to address X, and gets it accepted with sequence `temp-bad` (e.g., by creating a genuine double-spend fork against a competing unit from X).
2. Attacker crafts unit B whose payment input is a `"transfer"` referencing unit A's output (`input.unit`, `input.message_index`, `input.output_index`), and submits/broadcasts B once A's output has become stable (`main_chain_index <= last_ball_mci`) while A's `sequence` column is still `'temp-bad'` (a state the validator asserts cannot coexist).
3. `validatePaymentInputsAndOutputs`'s transfer-handling `conn.query` callback hits: [8](#0-7) , throwing inside the mutex-locked (`arrAuthorAddresses`) validation of unit B, acquired at [1](#0-0) .
4. The uncaught exception either crashes the node process, or — if caught externally — leaves the per-address mutex entry in `arrLockedKeyArrays` permanently locked (`unlock` in [13](#0-12)  is never reached), causing all subsequent validations keyed on the same author address to queue forever in `mutex.js` ( [5](#0-4) ) with no automated detection since `checkForDeadlocks` is disabled ( [6](#0-5) ).

Note: exact reproduction of the precise DB race that produces a stable `temp-bad` row is timing-dependent and was not executed against a live node; the code path and its uncaught-throw-under-lock structure are confirmed directly from source.
