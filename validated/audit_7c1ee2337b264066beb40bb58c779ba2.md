### Title
Cross-repository forgery of commit statuses via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by verifying the HMAC signature against the GitHub App `webhook_secret` of the **organization named in the payload's own `repository.owner.login`/`organization.login`** field. [1](#0-0)  That check only proves the sender knows the webhook secret for *some* organization onboarded to this Shipit instance — it never verifies that the event's actual payload content (e.g. a commit SHA) belongs to that same organization's repository. `Shipit::Webhooks::Handlers::StatusHandler#process` then resolves the target purely by `Commit.where(sha: params.sha)`, a global, unscoped lookup across every stack/repository tracked by the whole Shipit installation. [2](#0-1) 

### Finding Description
The trust binding that should hold is: **organization authenticated (whose `webhook_secret` validated the signature) == repository/commit that gets written**. This binding is broken:

- `WebhooksController#verify_signature` computes `repository_owner` from the attacker-controlled JSON body (`params.dig('repository','owner','login')` or `organization.login`) and uses it only to pick which `webhook_secret` to HMAC-verify against. [3](#0-2)  An attacker who controls any organization/repo that has the Shipit GitHub App installed (a fully legitimate, low-privilege installation) knows that org's own `webhook_secret` and can therefore produce a validly-signed `status` event whose JSON body they fully control.
- Once verified, the event is dispatched purely by event type: `Shipit::Webhooks.for_event('status')` → `StatusHandler`, with no cross-check that the `repository` in the payload matches the commit being targeted. [4](#0-3) [5](#0-4) 
- `StatusHandler#process` performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — an unscoped, instance-wide lookup by SHA string only, unrelated to the `repository` field that was used for signing. [6](#0-5) 

Contrast this with `Handler#stacks`, which properly scopes by `Repository.from_github_repo_name(repository_name)` for other handlers (e.g. `PushHandler`), [7](#0-6)  but `StatusHandler` bypasses that scoping entirely and queries `Commit` directly by SHA with no stack/repository filter.

Because commit SHAs are 40-character hex strings that are frequently public (visible on GitHub commit URLs, PR pages, or Shipit's own public `merge_status` pages), an attacker does not need to guess them — they can simply target a known SHA belonging to a victim's stack while signing the forged payload with their own organization's webhook secret.

### Impact Explanation
This is a **cross-repository write**: an attacker with only unprivileged access to their own onboarded GitHub organization can inject arbitrary `Shipit::Status` records (`state`, `context`, `description`, `target_url`) onto a commit belonging to a completely different organization's stack. `Commit#deployable?` and `Commit#status` are derived directly from these statuses, [8](#0-7)  and `Commit#schedule_continuous_delivery` triggers `ContinuousDeliveryJob` when a commit becomes `deployable?` under continuous deployment. [9](#0-8)  Forging a `success` state for a required CI context on a targeted commit can therefore flip a blocked/pending commit to deployable and, on a stack with continuous deployment enabled, cause an **unauthorized deploy** of that victim stack — satisfying the Critical impact bar ("unauthorized deploy") defined in scope. At minimum it is a cross-repository, cross-tenant integrity violation of commit CI state.

### Likelihood Explanation
Likelihood is high for any multi-tenant/multi-organization Shipit deployment: the only requirement is that the attacker's own organization (any org, however minor) has the Shipit GitHub App installed, giving them a legitimate `webhook_secret` to sign their own forged requests. No access to the victim organization, its repository, or any Shipit session/API token is required — only knowledge of a target commit SHA, which is typically public.

### Recommendation
In `StatusHandler#process` (and any other handler resolving objects purely by attacker-supplied identifiers such as SHA), scope the lookup through the same repository binding used to select the webhook secret: resolve via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (as `Handler#stacks` already does) and restrict `Commit.where(sha: params.sha)` to `stack_id: repository.stacks.pluck(:id)` (or equivalent) before creating/mutating any status. Reject the event if the payload's `repository` does not correspond to a repository actually owned by the verified organization.

### Proof of Concept
1. Attacker creates/uses their own GitHub organization `attacker-org` and installs the Shipit GitHub App on it, obtaining a valid `webhook_secret` for `attacker-org` (fully legitimate, unprivileged action).
2. Attacker identifies a target commit SHA belonging to `victim-org`'s stack, e.g. from a public GitHub commit URL or Shipit's public `merge_status` page for that stack.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` using HMAC-SHA1 and sends it to `POST /webhooks` with header `X-Github-Event: status` and the correct `X-Hub-Signature`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org` from the body, fetches `attacker-org`'s webhook secret, and successfully verifies the (self-consistent) signature. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (belonging to `victim-org`'s stack), and calls `create_status_from_github!`, injecting a forged `success` status onto it — regardless of the fact the signed organization was `attacker-org`. [2](#0-1) 
7. If the victim stack has continuous deployment enabled and this was the last required blocking status, `Commit#schedule_continuous_delivery` fires `ContinuousDeliveryJob`, deploying the victim's stack without authorization. [9](#0-8)

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

module Shipit

            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
