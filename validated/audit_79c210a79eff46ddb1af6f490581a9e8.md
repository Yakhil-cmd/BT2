### Title
Batched private payment chain validation in `handlePrivatePaymentChains` aborts unrelated valid chains after the first failure - (File: wallet.js)

### Summary
The external report describes a batching flaw in SeaportProxy: multiple independent orders are processed in a loop, but a shared/aggregated resource (batched fees) is handled such that a failure related to one item causes the whole batch to be treated as failed, breaking the expectation that independent items succeed or fail on their own ("non-atomic" semantics). The analogous pattern in `ocore--023` is `handlePrivatePaymentChains` in `wallet.js`, which batches multiple independent private-payment chains sent together by a peer/counterparty and stops processing the entire batch as soon as any single chain errors, silently dropping validation of all subsequent (unrelated, potentially valid) chains in the same request.

### Finding Description
`handlePrivatePaymentChains` receives `body.chains`, an array of independent private-payment chains (`arrChains`), each potentially referring to unrelated units/assets/senders, and processes them with `async.eachSeries`: [1](#0-0) 

Inside the iterator, when `network.handleOnlinePrivatePayment` reports `ifError` or `ifValidationError` for a chain, the code calls `cb("an error")`: [2](#0-1) 

Passing a truthy value to the `async.eachSeries` iteratee callback causes the library to immediately stop iterating and invoke the final callback with that error — it does **not** continue processing the remaining items in `arrChains`. This means that if chain #1 in a batch of, say, 3 independent chains fails validation (e.g., malformed data, a stale/already-spent output, or any transient error), chains #2 and #3 are **never attempted**, even though they are logically unrelated private payments that could be perfectly valid on their own.

The final callback confirms this "stop on first failure" behavior: [3](#0-2) 

`cancelAllKeys()` removes all pending `eventBus` listeners for chains that were queued (`ifQueued`) but not yet resolved, and `callbacks.ifError(err)` is returned for the whole batch — none of the individually valid chains get saved, forwarded (`forwardPrivateChainsToOtherMembersOfOutputAddresses`), or acknowledged via `checkIfAllValidated`/`ifOk`. The sender of the batch receives a generic error for the entire batch rather than per-chain results.

This directly parallels the reported bug class: a loop over independent items where an issue tied to one item improperly propagates to abort processing of other unrelated items in the same batch, defeating the expectation that independent operations are evaluated and settled independently.

### Impact Explanation
Private payments in Obyte are sent peer-to-peer between wallets/devices (directly or via hub) as chains of hidden outputs, and a single wallet message can legitimately bundle several unrelated private-payment chains together (e.g. multiple textcoins, multiple outputs to different counterparties, or a payment plus its change/cosigner chain). Because `handlePrivatePaymentChains` aborts the entire batch on the first chain's error:
- A malicious or malfunctioning counterparty can craft one bad/malformed chain among several good ones to prevent the recipient wallet from ever validating and saving the legitimate remaining chains in that batch, causing denial of a legitimate private payment delivery (funds appear "in transit" but never surface in the recipient's wallet from that batch).
- Legitimate transient failures (e.g., `ifWaitingForChain` conditions manifesting as errors in edge cases, or race conditions among concurrent private-payment deliveries) on one chain can cause otherwise-valid, unrelated chains bundled in the same message to be dropped, leading to funds effectively becoming unspendable/undiscovered by the recipient until re-sent out-of-band, and no explicit re-request mechanism exists for chains that were valid but never reached the `ifOk` validation path (they were never saved to `unhandled_private_payments` either, since `savePrivatePayment` for online delivery is bypassed on this path).
- This is a fund-availability/DoS-style impact scoped to private-payment counterparties (as required by scope) rather than a purely network-level bug, since the exploitable code runs in the recipient's own wallet processing logic upon receiving a peer message.

This satisfies the "AA fund loss or freezing" / unauthorized denial of legitimate payment analog required by the validation criteria, expressed here as private-payment freezing/loss of delivery rather than smart-contract fund loss, since ocore has no non-atomic order-book construct to map to directly, but the "independent items batched together, one failure blocks the rest" root cause is the same as the External Report.

### Likelihood Explanation
Likelihood is moderate: the code path is reachable by any private-payment counterparty who can send a `private_payments` message with multiple chains in `body.chains` to a peer's wallet (this is normal wallet-to-wallet protocol traffic, not a privileged path). Triggering the abort condition requires only that one of the bundled chains fail validation (`ifError`/`ifValidationError`), which is straightforward to engineer deliberately (malformed payload, invalid spend proof, wrong denomination, etc.) or can occur incidentally in legitimate multi-chain sends under race/timing conditions.

### Recommendation
Change the iteration strategy in `handlePrivatePaymentChains` so failures in one chain do not prevent processing of the others:
- Use `async.each` (parallel, independent) instead of `async.eachSeries`, or explicitly catch each per-chain error inside the iteratee (never forward it as the `cb(err)` of the overall loop) and accumulate per-chain results.
- Track success/failure per chain and only report/forward the chains that validated successfully; still allow chains that failed to be reported distinctly to the caller instead of silently discarding the whole batch on the first error.
- Ensure `checkIfAllValidated`, saving, and forwarding logic run for all successfully-validated chains regardless of any other chain's outcome, mirroring the intended non-atomic behavior between logically-independent items.

### Proof of Concept
1. Peer A (private-payment counterparty) sends peer B a `private_payments` wallet message with `body.chains = [chainX, chainY, chainZ]`, where `chainX`, `chainY`, `chainZ` are three independent, unrelated private-payment chains (different assets/senders/outputs) all destined for wallet B.
2. `chainX` is deliberately malformed (e.g., mismatched `payload.denomination`/`output_index`, or containing a hash that fails `objectHash.getBase64Hash`), while `chainY` and `chainZ` are fully valid, well-formed private payments.
3. `handlePrivatePaymentChains` processes `arrChains` with `async.eachSeries`; on `chainX`, `network.handleOnlinePrivatePayment` (or the pre-check on hash) triggers `cb("an error")`.
4. `async.eachSeries` immediately stops; `chainY` and `chainZ` are never validated or saved via `validateAndSavePrivatePaymentChain`, and `callbacks.ifError(err)` is returned for the whole set.
5. Result: wallet B never records or surfaces the funds from `chainY`/`chainZ` from this batch, even though those chains were fully valid and unrelated to `chainX`'s defect — reproducing the "all failed although only one item should have failed" pattern from the External Report.
