### Title
Webhook signature is verified against the org named in the payload while event processing trusts unrelated payload fields to select the target repo/commit - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/secret to validate the HMAC signature against using an attacker-controlled field of the JSON body (`repository.owner.login` / `organization.login`), but the handlers that subsequently act on the very same body (`PushHandler`, `StatusHandler`) key off *different* fields (`repository.full_name`, or nothing at all) to decide which `Stack`/`Commit` to mutate. In a multi-organization Shipit deployment (explicitly documented and supported), this breaks the intended binding "the organization whose secret validated this request" == "the repository/commit this request is allowed to act on."

### Finding Description
`verify_signature` resolves the signing organization purely from the request body: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` then loads the GitHub App config for whatever org string the attacker put in the JSON, and `verify_webhook_signature` is defined as: [3](#0-2) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

So the org used for cryptographic verification is fully attacker-selectable via the JSON body itself, and if a Shipit instance has multiple orgs configured (a documented, supported topology, see `docs/setup.md` "Using Multiple GitHub Applications" and `lib/shipit.rb#github_organizations`), an attacker who legitimately controls (or is an app-admin of) *any one* of those orgs can either replay/produce a request whose signature validates for that org, or exploit an org whose `webhook_secret` happens to be blank (`return true unless webhook_secret`).

Once the signature check passes, `create` dispatches the *entire, attacker-supplied* JSON body to handlers that use unrelated fields: [4](#0-3) 

- `PushHandler` resolves the target stacks via `payload.dig('repository', 'full_name')` (in `Handler#repository_name`), a field completely independent from the one used for signature-org selection: [5](#0-4) [6](#0-5) 

- `StatusHandler` is worse: it doesn't even require a `repository` field and matches purely on `sha` across the whole `Commit` table, with no repository scoping at all: [7](#0-6) 

Nothing ties `repository_owner` (used to select the verifying secret) to `repository.full_name`/`sha` (used to select what gets mutated). An attacker can therefore submit `repository.owner.login = "my-own-org"` (satisfying/bypassing signature verification for their own org) while setting `repository.full_name` or `sha` to point at a `Stack`/`Commit` belonging to a completely different organization tracked by the same Shipit instance.

### Impact Explanation
This breaks the equality: `organization that authenticated the request` == `repository/commit the request is allowed to write to`. Concretely:
- Via `PushHandler`, an attacker can enqueue `stack.sync_github(expected_head_sha: <arbitrary sha>)` for any stack whose repository they can name, for any org configured on the instance — not just their own.
- Via `StatusHandler`, an attacker can forge a `success`/`failure` CI status (`commit.create_status_from_github!`) for *any* commit sha in the database regardless of repository, which feeds directly into `Stack#branch_status`, `MergeRequest` auto-merge scheduling, and continuous-delivery triggers (`Commit#add_status` -> `stack.schedule_merges`). This is a path to an unauthorized/forged deploy or merge decision on a stack the attacker has no legitimate relationship to, satisfying the "unauthorized deploy/rollback/merge" impact bar.

### Likelihood Explanation
Exploitability depends entirely on the deployment being multi-organization (explicitly documented as a supported configuration) and on the attacker controlling (or being able to sign for) at least one of the configured orgs, or on any one configured org lacking a `webhook_secret`. I could not verify from the index whether Shipit additionally restricts inbound webhook requests by source IP (e.g., GitHub's published webhook IP ranges) at the infrastructure layer outside this engine's code — that would be an out-of-repo mitigating control I cannot confirm or rule out. Within the engine's own code, there is no such restriction; the endpoint accepts any POST with a matching HMAC for the org named in the body.

### Recommendation
Cross-check that the organization used to select/verify the webhook signature is the same organization that owns the repository/commit being acted upon (e.g., derive the app/secret to use from a value that is independent of body content, and additionally assert `repository.full_name.split('/').first.downcase == repository_owner.downcase` before dispatching to handlers; scope `StatusHandler`'s lookup to the verified repository rather than a bare `sha`).

### Proof of Concept
Given a Shipit instance configured with two orgs, `attacker-org` (attacker knows/controls its GitHub App webhook secret) and `victim-org` (unrelated), and a target commit sha `abc123` belonging to a stack under `victim-org/victim-repo`:

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(body, attacker-org's webhook_secret)>

{
  "organization": { "login": "attacker-org" },
  "sha": "abc123",
  "state": "success"
}
```

`verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `attacker-org`'s app, and the signature validates (the attacker knows this secret). `StatusHandler#process` then executes `Commit.where(sha: "abc123").each { |c| c.create_status_from_github!(params) }`, forging a success status on the victim commit regardless of the org used to authenticate the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
