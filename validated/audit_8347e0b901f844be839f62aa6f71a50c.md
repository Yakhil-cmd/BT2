### Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login`, but every event handler acts on the repository named in `repository.full_name` - allowing an org with no (or a known) webhook secret to forge events against a different org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`). Every webhook handler, however, resolves the target `Stack`/`Repository` from a completely different field of the same JSON body: `repository.full_name` [1](#0-0) . These two fields are never checked for consistency.

### Finding Description
`verify_signature` computes the verification org like this: [2](#0-1) [3](#0-2) 

and `Shipit.github(organization: repository_owner).verify_webhook_signature` returns `true` unconditionally whenever that organization's `webhook_secret` is blank: [4](#0-3) 

The webhook secret is explicitly documented and shipped as **optional** per organization (`webhook_secret: # nil` in every sample secrets file, e.g. `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), so it is realistic for a Shipit deployment that manages several GitHub organizations to have at least one org configured without a secret.

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw parsed JSON to every registered handler for the event: [5](#0-4) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) inherits `Handler#stacks`/`#repository_name`, which looks up the target repository by `payload.dig('repository', 'full_name')` - a field that is completely independent of the `repository.owner.login`/`organization.login` field used for signature verification: [6](#0-5) [7](#0-6) 

This breaks the equality that should hold: `organization that authenticated the request == organization whose repository the handler mutates`. An attacker can craft a JSON body where `repository.owner.login` (or `organization.login`) names an organization configured on the same Shipit instance with a blank/known `webhook_secret`, while `repository.full_name` names a stack belonging to a different, properly-secured organization. Because `verify_webhook_signature` short-circuits to `true` for the unsecured org, the forged request is accepted, and the handler then acts on the victim organization's stack using attacker-supplied data (e.g. an arbitrary `after` SHA for `PushHandler`, which triggers `GithubSyncJob.perform_later` and fetches/append attacker-chosen commits into the victim stack's commit history via `Stack#sync_github`) [8](#0-7) .

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary: an unprivileged external attacker, without any valid credential for the targeted organization's GitHub App, can inject forged GitHub webhook events (push, status, check_suite, pull_request, membership, etc.) against any repository/stack hosted on the same Shipit instance, as long as any other configured organization lacks (or has a leaked) webhook secret. Concretely this enables unauthorized manipulation of a victim stack's commit/CI/status state (e.g. `StatusHandler` can create fabricated commit statuses, `CheckSuiteHandler` can fabricate check results) which can be used to satisfy `ci.require` gating and clear the way for an otherwise-blocked deploy - an unauthorized deploy/rollback path.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a documented, supported configuration) where at least one configured GitHub organization has `webhook_secret` unset - itself a documented "optional" setting. No authentication, session, or GitHub write access is required by the attacker; only knowledge that such an organization exists in the target's configuration (observable from `Shipit.github_teams`/public UI hints or by trial).

### Recommendation
Cross-check that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner of the repository the handler is about to act on (`repository.full_name`), rejecting the event if they differ. Additionally, consider making `webhook_secret` mandatory (or at minimum enforce it) whenever more than one GitHub organization is configured, since a blank secret degrades `verify_webhook_signature` to `true` for that entire organization.

### Proof of Concept
Given a Shipit instance configured with two orgs:
```yaml
github:
  unsecured-org:
    app_id: ...
    installation_id: ...
    webhook_secret: # blank
  secured-org:
    app_id: ...
    installation_id: ...
    webhook_secret: "supersecret"
```
and a stack for `secured-org/victim-repo` already registered in Shipit, an attacker (no credentials) sends:
```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-present-in-victim-repo>"
}
```
`verify_signature` resolves `repository_owner` to `"unsecured-org"` [3](#0-2) , whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of any `X-Hub-Signature` header [4](#0-3) . The request then reaches `PushHandler`, which resolves the target stack via `full_name` = `"secured-org/victim-repo"` [1](#0-0)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, triggering `GithubSyncJob` against the victim stack despite the attacker never possessing `secured-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
