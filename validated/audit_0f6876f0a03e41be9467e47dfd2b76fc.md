### Title
Commit author identity spoofing via unauthenticated `Merge-Requested-By:` commit message field - (File: app/models/shipit/user.rb)

### Summary
`Shipit::User.find_or_create_author_from_github_commit` extracts a username from the raw commit message via the `Merge-Requested-By: <login>` pattern (matching `MergeRequest::MERGE_REQUEST_FIELD`) and attributes commit authorship to that user with no check that the actual GitHub committer/pusher is that user. Any GitHub user who can get a commit ingested via `Shipit::GithubSyncJob` → `Shipit::Commit.create_from_github!`/`from_github` can forge authorship of any existing `Shipit::User` by simply writing that text into their own commit message.

### Finding Description
The broken binding is: `Commit#author` (i.e., `Commit.from_github(commit).author`) should equal the GitHub identity that actually authored/pushed the commit, but instead it equals whatever `login` string follows `Merge-Requested-By:` in the attacker-supplied commit message text.

Code path:
- `Commit.from_github` calls `User.find_or_create_author_from_github_commit(commit)` [1](#0-0) 
- That method matches the raw commit message against `/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/` and, on match, directly calls `find_or_create_by_login!(match_info[1])`, returning that user as `author` with **no verification** against the commit's actual GitHub author/committer identity: [2](#0-1) 
- `MergeRequest::MERGE_REQUEST_FIELD = 'Merge-Requested-By'` is the same literal used when Shipit itself legitimately writes this trailer into merge messages (`merge_message`) [3](#0-2) [4](#0-3) , but nothing prevents an attacker from writing that exact trailer into an arbitrary commit message themselves before Shipit ever creates a merge request for it.
- Ingestion path: `GithubSyncJob#append_commit` calls `stack.commits.create_from_github!(gh_commit)`, which calls `Commit.from_github` [5](#0-4)  and [6](#0-5) . `GithubSyncJob` is triggered normally by legitimate, correctly-signed push webhooks for a stack's tracked branch (no signature forgery required) — the attacker only needs the ability to get a commit with the forged message onto the branch that a stack tracks (e.g. their own branch/PR head on a repo they control, if that repo/branch is tracked as a stack or review-stack), which is well within an unprivileged GitHub user's capability for a fork/PR.
- None of the listed guards (`verify_signature`, `drop_unhandled_event`, `force_github_authentication`, `User#authorized?`, `require_permission!`, model validations) address this, because the vulnerable code operates purely on trusted-transport but attacker-controlled commit message *content*, not on webhook authenticity. The webhook/signature layer correctly proves "this really is a push event from GitHub for this repo"; it does nothing to validate free-text commit message content.

### Impact Explanation
A successful match causes `Commit#author` (and thus `authored_commits` association, `stacks_contributed_to`, and any downstream logic keyed off commit authorship) to be misattributed to an arbitrary existing `Shipit::User` (e.g., `victim-login`) chosen by the attacker, without that victim's involvement. This is a record-writing integrity/identity-binding bug: a `Commit` row for a repository is written with an author field that was never authenticated to correspond to that GitHub identity. The blast radius is limited to whatever consumes `Commit#author`/`authored_commits` for attribution — the search found no direct authorization gate (e.g., deploy/lock permission checks) keyed off `Commit#author` in this codebase; `merge_message` uses `merge_request.merge_requested_by`, a separate field, not `Commit#author`. Given the absence of a demonstrated privilege-escalation or unauthorized-action pathway strictly keyed off `Commit#author`, this is an audit/attribution-integrity bug rather than a proven Critical/High impact under the stated categories (unauthorized deploy/rollback/merge, RCE, secret exfiltration, cross-tenant mutation, auth bypass, or unauthenticated read).

### Likelihood Explanation
Low cost for the attacker (a normal commit message on a repo/branch they control), and the precondition (`victim-login` already exists as a `Shipit::User`) is easily satisfied for any active contributor. However, actually reaching `Commit.from_github` requires the forged commit to be synced onto a branch a Shipit `Stack` tracks, which typically means the attacker's commit must land on the target repository's tracked branch or be part of a PR/review-stack setup that syncs the attacker's branch directly — this is plausible for repositories using review-stacks/PR-based workflows but is configuration-dependent.

### Recommendation
In `find_or_create_author_from_github_commit`, only honor the `Merge-Requested-By:` trailer when it is verifiably tied to a Shipit-created merge (e.g., cross-check against `MergeRequest#merge_requested_by` for the associated PR/merge commit, as already done in `Commit#identify_merge_request`) rather than trusting free-text commit message content directly; do not use raw commit-message-derived logins to create/attribute a `User` record.

### Proof of Concept
Minitest plan (no live GitHub) under `test/models/commits_test.rb` or `test/models/users_test.rb`:
1. Create `victim = Shipit::User.create!(login: 'victim-login', github_id: 123, name: 'Victim')`.
2. Build a fake Octokit commit resource (as done elsewhere in `test/models/users_test.rb`) whose `commit.message` is `"Some change\n\nMerge-Requested-By: victim-login\n"` and whose actual `author`/`committer` sawyer resource represents `attacker-login` (different GitHub id).
3. Assert `Shipit::Commit.from_github(fake_commit).author.login == 'victim-login'` while the underlying `fake_commit.author.login == 'attacker-login'`, demonstrating `Commit#author != actual GitHub committer`, i.e., the equality `Commit#author.github_id == actual_pusher.github_id` fails.

```ruby
    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
```
