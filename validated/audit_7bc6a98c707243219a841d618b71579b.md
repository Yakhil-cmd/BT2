### Title
Webhook signature is verified against an attacker-chosen organization while the actual mutation (team membership) trusts a different, unverified organization field — allowing forged `membership` events to grant `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` picks *which* organization's webhook secret to verify a request against by reading an untrusted field out of the very payload it is about to authenticate, and if that organization has no `webhook_secret` configured the check is a no-op. The handler that actually performs the privileged mutation (`MembershipHandler`) then reads a *different* field from the same unverified JSON body to decide which `Team`/organization to modify. Because these two fields are never cross-checked, an attacker can pick a "throwaway" org for signature bypass while forging state changes for a completely different, real organization — including adding themselves to a team that backs `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the incoming payload: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login`, falling back to `organization.login` — both attacker-controlled JSON fields, unauthenticated at the point they are read. `Shipit.github(organization: repository_owner)` then looks up that organization's `GitHubApp`, whose `verify_webhook_signature` is: [3](#0-2) 

Note line 77: `return true unless webhook_secret`. Per the documented multi-org configuration format, `webhook_secret` is explicitly optional per organization: [4](#0-3) 

So for any configured organization that has not set a `webhook_secret`, signature verification is unconditionally bypassed regardless of the `X-Hub-Signature` header sent.

Meanwhile, `MembershipHandler` — which creates/mutates `Team` and `Membership` records — determines the organization to act on from a *separate*, still-unverified field of the same JSON body: [5](#0-4) 

`find_or_create_team!` looks the team up by `params.team.id` (a numeric GitHub team id) and only sets `team.organization` when creating a brand-new record; for an already-existing `Team` (e.g. the one backing `Shipit.github_teams`) it is found purely by `github_id`, completely independent of `repository_owner`/the org used for signature verification.

The broken binding is:
```
organization_used_for_signature_verification (repository.owner.login / organization.login)
   ==
organization_whose_Team/Membership_is_actually_mutated (params.organization.login / params.team.id)
```
Before the attack these two are supposed to be the same organization (the one GitHub actually sent the event for). An attacker can decouple them: set `repository.owner.login` (or top-level `organization.login`, whichever `repository_owner` picks up) to *any* organization X that is configured in Shipit but has no `webhook_secret` set, so `verify_signature` passes unconditionally — while placing the *real* target team's `id` in `team.id` and the victim org's login in the top-level `organization.login` used by `MembershipHandler`. `for_event`/`Webhooks.handlers` dispatches the whole raw, still-unverified body to the handler regardless of which sub-field was used for auth: [6](#0-5) [7](#0-6) 

This is the same trust class as the reported bug (a value used by one part of the flow that a different, security-relevant part of the flow never separately validates against the authenticated context) — here the "authenticated organization" is never bound to the "organization actually written."

### Impact Explanation
`Team.members` gates `User#authorized?`: [8](#0-7) 

which is enforced on every request by `Authentication#force_github_authentication`: [9](#0-8) 

An attacker who has authenticated once via the normal GitHub OAuth login (creating a legitimate `Shipit::User` row tied to their own `github_id`/`login`, requiring no privileged repo/org access) can forge a `membership` webhook `added` event naming their own login as `member.login` and the real required team's numeric `team.id`. Because signature verification is satisfied against an unrelated, secret-less organization, `MembershipHandler#process` adds them to `team.members`, satisfying `authorized?` and granting them full access to Shipit — an unauthenticated-webhook path into `Shipit.github_teams` authorization, i.e. escalation into the application's core authorization gate. This matches the accepted High-risk impact category directly.

### Likelihood Explanation
Exploitation requires only: (1) the target Shipit instance uses the multi-organization config form with at least one configured organization lacking a `webhook_secret` (explicitly supported/documented), and (2) knowledge of the numeric GitHub `team.id` for the team referenced by `Shipit.github_teams` (obtainable via the public GitHub API for any org whose teams are visible, or by observing legitimate webhook traffic/logs). No Shipit session, `ApiClient` token, or GitHub App private key is needed to reach `/webhooks`, since that endpoint is intentionally unauthenticated aside from the HMAC check this bug defeats.

### Recommendation
Do not let the payload itself choose which organization's secret is used to authenticate it. Instead:
- Bind the webhook endpoint to a specific, pre-registered organization (e.g. via URL path/route parameter tied to app configuration) rather than trusting `repository.owner.login`/`organization.login` from the body, or
- After verifying the signature for the resolved organization, require every handler to re-validate that all organization-identifying fields it consumes (`organization.login` in `MembershipHandler`, `repository.owner.login` elsewhere) equal the organization whose secret validated the request, rejecting mismatches.
- Additionally, stop silently treating an absent `webhook_secret` as "verification passes" (`lib/shipit/github_app.rb:77`); either require a secret for every configured organization or clearly fail closed with a hard configuration error at boot.

### Proof of Concept
1. Configure Shipit with two orgs: `victim-org` (has `Shipit.github_teams` mapped to a real team, `webhook_secret` set) and `throwaway-org` (configured, `webhook_secret` left blank per the documented optional field).
2. Attacker logs into Shipit normally via GitHub OAuth as `attacker-login` (no special privileges required), creating a `User` row.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <victim_required_team_github_id>, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/1" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-login" },
  "repository": { "owner": { "login": "throwaway-org" } }
}
```
   with an arbitrary/garbage `X-Hub-Signature` header.
4. `verify_signature` resolves `repository_owner` to `"throwaway-org"` (via `repository.owner.login`), whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally and the request is accepted.
5. `MembershipHandler#process` finds the existing `Team` by `github_id == victim_required_team_github_id` and calls `team.add_member(User.find_or_create_by_login!("attacker-login"))`, adding the attacker to the team backing `Shipit.github_teams`.
6. Attacker's subsequent requests to Shipit now pass `current_user.authorized?`, granting full authenticated access without ever being a real member of `victim-org`'s GitHub team.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
