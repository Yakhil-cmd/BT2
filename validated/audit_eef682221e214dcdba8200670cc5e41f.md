### Title
Webhook signature verification is scoped by an attacker-controlled `repository.owner.login`/`organization.login` field that is decoupled from the `repository.full_name` field actually used to select the Stack that gets written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), both fully attacker-controlled fields taken from the unauthenticated request body. The `create` action and every `Webhooks::Handlers::Handler` subclass, however, resolve the `Repository`/`Stack` to actually mutate using a *different* field, `repository.full_name`. Because Shipit explicitly supports multiple GitHub organizations each with their own (optional) `webhook_secret`, an attacker can pick an organization whose `webhook_secret` is unset/known and put it in `repository.owner.login`, while pointing `repository.full_name` at a completely different, properly-secured organization's repository, causing signature-checked writes to be applied to a repository that was never actually authenticated.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
The organization used to pick the verifying secret is derived purely from the JSON body the attacker submits, before any cryptographic check has occurred.

`GitHubApp#verify_webhook_signature` in [2](#0-1)  unconditionally returns `true` when no `webhook_secret` is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
Shipit explicitly documents multi-organization deployments where each org has its own, *optional* `webhook_secret` [3](#0-2)  and the setup guide labels the secret as optional [4](#0-3) .

Once `create` runs, it re-parses the raw body and dispatches to handlers using the event type only [5](#0-4) . Every handler determines the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

Concrete handlers such as `PushHandler` (`stack.sync_github`, which fetches and merges GitHub commit/state data) [7](#0-6) , and the pull-request handlers that create/archive/unarchive Review Stacks via `Repository.from_github_repo_name(params.repository.full_name)` [8](#0-7)  and [9](#0-8) , all key off `repository.full_name`.

**Binding broken:** the organization that is authenticated (`repository.owner.login`/`organization.login`, used to select the `webhook_secret`) ≠ the repository that is written (`repository.full_name`, used by every handler). These two fields live in the same attacker-controlled JSON body and are never cross-checked.

### Impact Explanation
An unprivileged attacker (anyone who can POST to `/webhooks`, no GitHub authentication or Shipit session required) who knows of, or controls, one organization configured in this Shipit instance without a `webhook_secret` (an explicitly supported, "optional" configuration) can forge arbitrary webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`) that pass signature verification trivially, while setting `repository.full_name` to point at a *different*, properly secured organization/repository's Stack. This results in cross-repository, unauthenticated writes: forged commit statuses, forged `sync_github` triggers, forged pull-request-driven Review Stack creation/archival, all against a repository the attacker never proved control of and whose org does enforce a webhook secret. This satisfies the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitation requires only knowledge that at least one configured GitHub organization on the target Shipit instance has no `webhook_secret` set — a state the documentation itself calls "optional" and thus a realistic misconfiguration in any multi-org install. No credentials, GitHub App keys, or Shipit sessions are required; the attacker sends a single crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Do not select the verifying `webhook_secret` from the same untrusted field that is decoupled from the actually-acted-upon repository. Concretely:
- Verify the signature using the organization/owner derived from `repository.full_name` (the same field handlers use to resolve the target Stack), not `repository.owner.login`/`organization.login`.
- Reject webhooks for organizations without a configured `webhook_secret` instead of treating them as automatically verified (`return true unless webhook_secret` is unsafe).
- Cross-validate that `repository.owner.login` and the owner portion of `repository.full_name` match before dispatching to handlers.

### Proof of Concept
Given a Shipit deployment configured with two organizations, e.g.:
```yaml
github:
  attacker-org:
    webhook_secret: # unset
    ...
  victim-org:
    webhook_secret: "s3cr3t"
    ...
```
An attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: push
Body:
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `repository_owner` resolves to `attacker-org`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` regardless of the (absent/garbage) `X-Hub-Signature` header.
- `create` dispatches to `PushHandler`, which resolves the target stacks via `payload.dig('repository', 'full_name')` = `victim-org/victim-repo`, and calls `stack.sync_github(expected_head_sha: params.after)` on the victim org's Stack — a write that was never actually signature-verified against `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
