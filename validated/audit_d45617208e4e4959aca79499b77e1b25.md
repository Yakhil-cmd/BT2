Cross-organization webhook confirms forged CI status onto any tracked repository's commit, bypassing merge/deploy CI gates - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `LSP8Burnable` report is about an inheritance mismatch that breaks the expected trust chain (a binding between an interface a caller expects and the implementation actually used, causing missing ERC-165 support). The strongest analog in Shipit is a mismatch between "the organization whose credentials authenticated the webhook" and "the repository the webhook handler actually writes to." `WebhooksController` verifies the HMAC signature using a `github_app` selected by `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , but `StatusHandler#process` writes a CI `Status` by looking up commits **globally by `sha`**, with no scoping to the org/repo whose signature was actually verified [3](#0-2) .

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GitHubApp` (and its `webhook_secret`) purely from the `repository.owner.login` field embedded in the same JSON payload being verified [1](#0-0) . Critically, `GitHubApp#verify_webhook_signature` treats an **unset** `webhook_secret` as automatically valid: `return true unless webhook_secret` [4](#0-3) . The `webhook_secret` is explicitly documented as optional per organization [5](#0-4) [6](#0-5) , and Shipit supports hosting multiple independent GitHub organizations side by side, each with its own app config keyed by org login [7](#0-6) .

The binding the engine relies on is:
`organization that authenticated the request` == `repository whose state is mutated by the handler`

This equality breaks because:
1. The signature check binds trust to `repository.owner.login` (or `organization.login`) only.
2. `StatusHandler#process` never re-derives or checks the repository at all — it does a global, cross-tenant lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Unlike other handlers (`PushHandler`, `PullRequest::*`) which resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and are thus scoped to the repo named in the payload [8](#0-7) , `StatusHandler` ignores `repository.full_name` entirely and matches by commit `sha` across the whole database.
3. `Status#state`, `target_url`, `description`, `context` are taken verbatim from the payload and written via `Status.replicate_from_github!`-equivalent (`create_status_from_github!`) with no call back to GitHub's API to confirm the status is real [9](#0-8) , confirmed by the existing test asserting the created `Status` fields equal the raw payload fields [10](#0-9) .

Consequently, an unprivileged party who controls (or merely names, if that org's `webhook_secret` is left unset — an explicitly supported/optional configuration) any organization configured in Shipit's `secrets.yml` can submit a `status` webhook whose signature is checked only against that org's app, while the `sha` inside the payload belongs to a commit that lives under a completely different, security-hardened organization/stack. `Commit.where(sha:)` will match it if the SHA happens to collide with (or simply is copied/guessed from, since commit SHAs of public/semi-public repos are often known) a commit tracked by another stack, and Shipit will attach a forged `success` status to that commit.

### Impact Explanation
Fabricated CI statuses feed directly into deploy and merge-queue gating logic: `Stack#deployment_checks_passed?` and `MergeRequest#reject_unless_mergeable!`/`StatusChecker` rely on `Status`/`check_runs` records to decide `ci_missing`/`ci_failing` [11](#0-10) , and `Status#enable_ci_on_stack`/`schedule_continuous_delivery` are triggered on creation [12](#0-11) . A forged `success` status can make an otherwise-failing or CI-less commit appear deployable or mergeable, enabling an **unauthorized deploy or merge** on a stack the attacker has no legitimate relationship to — matching the report's Critical/High impact bar defined by the rules (unauthorized deploy/merge via a broken trust binding).

### Likelihood Explanation
Requires only: (a) knowledge of an organization login configured in Shipit (org names are public), (b) that org either has no `webhook_secret` configured (explicitly supported/optional per the setup docs) or the attacker otherwise obtains a valid signature for their own tracked org, and (c) a target commit SHA that is also tracked in another stack (achievable by choosing a target repo with public commit history, since SHAs are 40-hex and easily copyable from GitHub). No Shipit session, API token, or repository write access is required — the `/webhooks` endpoint is intentionally public and unauthenticated aside from the per-organization signature check.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already do so) to the repository named in the same payload used for signature verification: reject/ignore the event if `payload.dig('repository','full_name')`'s owner does not match the `repository_owner` used to select the verifying `GitHubApp`, and restrict `Commit.where(sha:)` lookups to `stacks` derived from `Repository.from_github_repo_name(repository_name)` the same way `Handler#stacks` already does for other handlers. Additionally, treat a missing `webhook_secret` as a configuration warning rather than an automatic-pass condition, or at minimum ensure it cannot be used to forge writes against a different, secured organization's data.

### Proof of Concept
1. Configure/observe that Shipit hosts multiple GitHub orgs, and organization `orgA` has no `webhook_secret` set (an explicitly optional field per `docs/setup.md`).
2. Find a commit SHA belonging to a stack tracked under a different, secured organization `orgB` (e.g., from `orgB`'s public GitHub commit history).
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<orgB-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example.com",
  "repository": { "owner": { "login": "orgA" } }
}
```
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is blank [4](#0-3) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the `orgB` commit, attaching the forged `success` status to it [3](#0-2) , potentially unblocking a deploy or merge on `orgB`'s stack that the attacker never had access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
