### Title
Unchecked null dereference of `augmented_input` in address-definition input filters causes node crash - (File: definition.js)

### Summary
`definition.js`'s `evaluateFilter` function, used to evaluate `"has"`/`"has one"` conditions inside address/AA definitions, computes `augmented_input` from `objValidationState.arrAugmentedMessages` but only populates that structure when it is actually needed for asset-transfer conditions. If a unit author supplies a definition that uses an input filter with an `address` restriction (`"this address"`, `"other address"`, or a literal address) outside of the asset-augmentation path, `augmented_input` can be `null`, and the code immediately dereferences `.address` on it without a null check — mirroring the CVE-2023-3355 pattern of using an allocation/lookup result without checking whether it succeeded before dereferencing it.

`objValidationState.arrAugmentedMessages` is only ever assigned inside `augmentMessages`, which is invoked (indirectly through `validateAuthentifiers`) for the asset-condition branch of definition evaluation: [2](#0-1) 

When a plain (non-asset) address definition uses an `"input"` filter with a `filter.address` clause, `objValidationState.arrAugmentedMessages` is never populated for that evaluation, so `augmented_input` resolves to `null` and the very next line unconditionally reads `augmented_input.address`. In standard JavaScript this throws an uncaught `TypeError: Cannot read properties of null`, exactly analogous to the kernel bug's failure to check the return of `kmalloc()` before dereferencing the pointer — here the "allocation" is the conditional lookup that can yield `null`, and it is dereferenced without a guard.

### Impact Explanation
`validateAuthentifiers`/`evaluateFilter` runs during unit/AA-trigger validation, which is on the hot path for every node processing a newly posted unit whose address (or AA) definition contains such a filter. An uncaught `TypeError` thrown from deep inside the synchronous evaluation loop is not caught by the surrounding `try/catch` boundaries used elsewhere in validation and would propagate up, crashing the validating process (denial of service) or, depending on where it surfaces, leaving validation state inconsistent between nodes that happen to hit vs. not hit this code path (e.g., depending on cached `arrAugmentedMessages` state from a previous asset validation in the same call chain), which can translate into a node-vs-node disagreement on unit validity.

### Likelihood Explanation
Any unprivileged unit author can construct an address definition (or an AA that references such a definition) containing an `"has"`/`"has one"` input filter with an `address` restriction and post a unit whose authentifiers exercise that branch. No asset (`this_asset`) needs to be present, so the guard that would otherwise populate `arrAugmentedMessages` is bypassed, making the null path directly reachable from untrusted, attacker-controlled definition content.

### Recommendation
In `evaluateFilter` (and the equivalent output-filter logic), check `augmented_input` for `null`/`undefined` before accessing `.address`/`.amount`, falling back to the raw `input` object (as is already done at line 1333 via `{...(augmented_input || input), ...}`) instead of dereferencing the possibly-null variable directly. Wrap the whole `evaluateDefinition`/`evaluateFilter` traversal in a `try/catch` that maps unexpected exceptions to a validation error (`ifUnitError`) instead of letting them propagate and crash the process.

### Proof of Concept
1. Define an address (or AA base address) with a definition such as:
```
["and", [
  ["sig", {"pubkey": "<valid pubkey>"}],
  ["has", {"what": "input", "address": "this address"}]
]]
```
2. Post a unit signed by that address containing a payment message with an input of `type: "transfer"` (no asset, i.e., base asset) that satisfies the outer signature check.
3. During validation, `validateAuthentifiers` evaluates the `"has"` clause via `evaluateFilter`; since no `this_asset` is involved, `augmentMessages` is not invoked for this branch, `objValidationState.arrAugmentedMessages` is unset, `augmented_input` is `null`, and the line `augmented_input.address !== address` throws, crashing/erroring the validating node's process for that unit.
