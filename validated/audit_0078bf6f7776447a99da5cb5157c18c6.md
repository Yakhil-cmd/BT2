## Title
Trigger authors can bias the `timestamp` value seen by Autonomous Agents by choosing an unfavorable `last_ball_unit`, allowing manipulation of time-gated AA logic - (File: `formula/evaluation.js`, `validation.js`)

### Summary
The Sherlock report describes a Dutch-auction contract whose price depends on `block.timestamp`, which a miner can bias within a small window to get a better price. In `ocore`, oscript's `timestamp` keyword is the direct analog of `block.timestamp`: it returns `objValidationState.last_ball_timestamp`, i.e. the timestamp of whatever unit the trigger author chose as `last_ball_unit` for their own unit. Because a unit author has real latitude in selecting which stable unit to declare as `last_ball_unit` (subject only to loose monotonicity constraints), the value fed to `timestamp` in AA formulas is attacker-influenceable rather than a trustworthy "current time" — exactly the "timestamp dependency" bug class from the report, but expressed through last-ball selection instead of block production.

### Finding Description
`timestamp` in the oscript formula evaluator resolves to the last-ball timestamp of the posting unit, not real wall-clock time or the trigger's own timestamp: [1](#0-0) 

This same field also backs the `timestamp` operator used in address-definition authentifiers: [2](#0-1) 

`objValidationState.last_ball_timestamp` is populated purely from whichever `last_ball_unit` the unit references, not from any check that this is the *most recent* stable unit: [3](#0-2) 

The only constraints that bound the chosen `last_ball_unit`/`last_ball_mci` are:
- it must not "retreat" relative to what the unit's parents already used (`max_parent_last_ball_mci > last_ball_mci` fails): [4](#0-3) 
- it must already be included/known to the unit's own chosen parents (`max_parent_limci < last_ball_mci` fails): [5](#0-4) 

Crucially, these checks only bound `last_ball_mci` between `max_parent_last_ball_mci` and `max_parent_limci` — a range that can span many stable units/timestamps depending on which parent units the author (who fully controls parent selection when hand-composing a unit) picks. Separately, the unit's own `timestamp` field is checked against parents' timestamps and against wall-clock time: [6](#0-5) [7](#0-6) 

but this check is on the *unit's own* `timestamp` field, completely decoupled from `last_ball_timestamp` (the value oscript's `timestamp` actually returns). So an attacker composing a raw unit (not necessarily going through the default `composer.js`/`parent_composer.js` "pick latest" logic) can freely pick parents/last_ball to select an older (or newer, within the allowed window) valid `last_ball_unit`, thereby choosing the `timestamp` value their AA trigger will be evaluated against, independent of real elapsed time.

Many real AAs branch directly on `timestamp` for security-critical decisions, e.g. maturity/expiry gating and milestone release: [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker who can influence which stable unit is referenced as `last_ball_unit` for their own AA-triggering unit can:
- Bypass "wait for maturity date" / expiry checks (`timestamp < $expiry_ts`, `timestamp > $expiry_ts`) to prematurely trigger fund releases or ICO finish/milestone conditions, or to extend a fundraising window past its intended deadline.
- Force or avoid "blackswan"/data-feed-timing branches that were designed to protect funds during a specific window.
This can lead to unauthorized/early fund release from an AA, freezing of funds under wrong branch selection, or economic manipulation of any oscript AA that uses `timestamp` for auction-like or time-decayed logic (directly mirroring the reported Dutch-auction price manipulation).

### Likelihood Explanation
Exploitation requires the attacker to author a unit and deliberately choose an older/eligible `last_ball_unit` rather than the network-recommended latest one — something achievable by anyone who composes units directly against the DAG rather than through the standard wallet composer, since validation does not require `last_ball_unit` to be the most recent stable unit, only that it satisfy the loose monotonicity bounds shown above. This makes the manipulation reachable by any unposted AA trigger author, without needing to be a witness, hub, or otherwise privileged.

### Recommendation
Do not let AA/definition logic treat `timestamp` (last-ball timestamp) as a trustworthy "current time" for security-critical, narrow time windows. Where tighter timing guarantees are needed, either:
- tie the allowed `last_ball_unit` range tighter (e.g., require it to be within N MCI of the best known stable MCI at broadcast time), or
- expose and rely on `objUnit.timestamp` (bounded to be close to real time and monotonic vs. parents) instead of `last_ball_timestamp` for time-sensitive AA branches, and clearly document to AA authors that `timestamp` reflects the referenced last ball, not guaranteed "now".

### Proof of Concept
1. Author an AA whose logic includes `if (timestamp < $expiry_ts) bounce(...)` or `if (trigger.data.finish AND (... OR timestamp > $expiry_ts))` (pattern seen in `test/samples/futures_contract.oscript` and `test/ojson.test.js`'s `ico_with_milestones.oscript`).
2. Instead of using the standard composer (which picks the most recent valid last ball), hand-craft a unit whose `parent_units` are chosen such that `max_parent_limci` is large but reference an older `last_ball_unit`/`last_ball` satisfying `max_parent_last_ball_mci <= last_ball_mci <= max_parent_limci` (validated in `validation.js` lines 668-674 and 740-741).
3. Because `objValidationState.last_ball_timestamp` is set from this chosen `last_ball_unit` (`validation.js:738`) and `timestamp` in `formula/evaluation.js:1050-1052` simply returns that value, the AA evaluates the time-gated branch using the attacker-chosen (older) timestamp rather than real elapsed time, bypassing the intended maturity/expiry/milestone gate.
