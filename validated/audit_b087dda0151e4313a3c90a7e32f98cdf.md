### Title
Unhandled `throw Error` in private-payment duplicate-check crashes the node - ([File: private_payment.js])

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain` performs a duplicate-output check by querying the local `outputs` table and asserts that at most one row can match. When more than one row matches, it does `throw Error(...)` from inside a `db.query` result callback instead of routing the error through the `ifError` callback chain used everywhere else in this function. This is structurally identical to the OpenSIPS `anchor_lump`/`append_hf` bug class: a reachable, attacker-influenced code path performs an internal consistency assertion via `throw`/`abort()` instead of graceful error handling, and the resulting unhandled exception crashes the process.

### Finding Description
`validateAndSavePrivatePaymentChain` is invoked whenever a private-payment counterparty or paired device sends a private payment chain to a wallet/hub, via `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` (also reachable through `wallet.js`'s `handlePrivatePaymentChains`, which processes `body.chains` sent by a device peer). [1](#0-0) [2](#0-1) 

Inside the function, before delegating to `indivisible_asset.js`/`divisible_asset.js` for real validation, a "duplicate" check queries existing rows:
```
var sql = "SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?";
...
if (objAsset.fixed_denominations){ ... sql += " AND output_index=?"; ... }
conn.query(sql, params, function(rows){
    if (rows.length > 1)
        throw Error("more than one output "+sql+' '+params.join(', '));
    ...
``` [3](#0-2) 

Critically, for **divisible (non-fixed-denomination) private assets** the query has no `output_index` filter, so it matches every output row already stored for that `(unit, asset, message_index)` triple — and a single payment message can legitimately contain multiple outputs of the same asset. If the recipient has already partially stored outputs for that message (e.g., from an earlier delivery of the same chain, from a cosigner path, or from processing another element of a multi-output chain), the second invocation of this duplicate check will find `rows.length > 1` and `throw` synchronously inside the SQLite/MySQL query callback. This throw is not wrapped in any `try/catch` up the call stack (unlike the sibling `getBase64Hash` calls in the same file, which are explicitly wrapped in `try/catch`), so it becomes an uncaught exception.

`network.js` explicitly re-throws on `uncaughtException` to crash the process: [4](#0-3) 

### Impact Explanation
Any private-payment counterparty or paired device that can deliver (or re-deliver) a private payment chain for a divisible private asset with two or more outputs sharing the same `(unit, message_index)` can trigger this internal assertion and crash the recipient's `ocore` process (wallet or hub). This is a remote, unauthenticated (from the counterparty's perspective) denial-of-service against a node — consistent with "a network unable to confirm new units" / node crash impact class, directly analogous to the OpenSIPS `abort()`-on-malformed-input DoS.

### Likelihood Explanation
Likelihood is high in normal operation of asset-holders and cosigned/shared-address scenarios: the private-payment protocol allows re-delivery of the same chain (there is explicit "duplicate private payment" handling logic right below the throw, indicating the developers anticipated repeats), and multi-output divisible-asset payment messages are a normal use case. An attacker acting as a payment counterparty only needs to cause the recipient to receive/re-process a private divisible-asset payment whose message already has (or will have) a partially-stored output row before the second output element is validated, e.g. by sending the chain elements out of the normal order or twice.

### Recommendation
Replace the `throw Error(...)` at `private_payment.js:75` with a call to `transaction_callbacks.ifError(...)`, matching the error-handling convention used throughout the rest of the function (and the same file's own `catch` blocks for `objectHash.getBase64Hash` calls). Also reconsider whether `rows.length > 1` is actually an error condition for divisible assets, given the lack of `output_index` filtering — it may need to be handled as a normal multi-row case rather than an invariant violation.

### Proof of Concept
1. As a paired device / payment counterparty, prepare a private, divisible, is_private asset payment chain (`arrPrivateElements`) whose head element references a `unit`/`message_index` for which the recipient's `outputs` table will end up holding more than one row (e.g., by sending the chain once, allowing partial processing/insertion of some outputs for that message, then re-sending the same or an overlapping chain for the same `unit`/`message_index` before/while the first is finalized).
2. Deliver this via `handlePrivatePaymentChains` (device protocol) or directly via `network.handleOnlinePrivatePayment`, causing `privatePayment.validateAndSavePrivatePaymentChain` in `private_payment.js` to run its duplicate-check query.
3. Once the SQL result contains more than one row for that `(unit, asset, message_index)` (no `output_index` filter for divisible assets), the query callback executes `throw Error("more than one output " + sql + ...)` at `private_payment.js:75`, which is not caught anywhere in the call chain, propagating to Node's `uncaughtException` handler in `network.js`, which explicitly re-`throw`s to crash the process.
