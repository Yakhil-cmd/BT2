### Title
Session fixation on GitHub OAuth callback via missing `reset_session` - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`Shipit::GithubAuthenticationController#callback` writes `session[:user_id]` into the existing session without first calling `reset_session`, unlike `#logout` and the fresh-login path in `force_github_authentication` which both call `reset_session`. An attacker can pre-establish an unauthenticated session, plant that session cookie on a victim, and once the victim completes the OAuth callback the attacker's copy of the same cookie resolves to the victim's `current_user`.

### Finding Description
The broken binding: for the pre-auth session cookie `C`, `session[:user_id]` under `C` should differ before and after `#callback` executes for two different browser agents holding `C`, but instead `session[:user_id]_before(attacker, C) == session[:user_id]_after(victim's callback, C)` because it's literally the same server-side session record.

Code path:
- `GET /github/auth/github` establishes a session and issues a cookie (attacker captures/fixates this cookie, e.g. via a shared kiosk or by setting the session id in the victim's browser).
- The victim, using the same session cookie `C`, completes `GET/POST /github/auth/github/callback`.
- `app/controllers/shipit/github_authentication_controller.rb:13` — `session[:user_id] = sign_in_github(auth)` writes the victim's `User#id` into session `C` in place, with no `reset_session` call anywhere in `#callback`.
- `app/controllers/concerns/shipit/authentication.rb:40-42` — `find_current_user` resolves `current_user` purely from `session[:user_id]`, with no additional binding to a session id, IP, or user agent.
- The attacker, still holding cookie `C`, now resolves to the victim's `User` on any subsequent request (e.g., `stacks#index`, deploy actions), because `session[:user_id]` is looked up from the shared session store entry, not regenerated.

Contrast: `#logout` (`app/controllers/shipit/github_authentication_controller.rb:24`) and the stale-login branch of `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:23`) both call `reset_session` to rotate the session identifier — showing the engine is aware of session-fixation-style risk elsewhere, but the primary authentication upgrade path (`#callback`) omits it. No CSRF/session-binding middleware, `Devise`, or other mechanism in this engine regenerates the session id on privilege escalation.

### Impact Explanation
An attacker who successfully fixates a session on a victim gains full session hijacking after the victim authenticates: they become `current_user` as the victim, including the victim's `github_access_token`-backed authorization state and any Shipit deploy/rollback/merge privileges the victim has. Because `Stack` access is generally gated by team/permission checks against `current_user`, this allows the attacker to trigger deploys, rollbacks, or merges as the victim on any stack the victim can act on. This matches the "session fixation / forced OAuth completion" category explicitly called out as High severity.

### Likelihood Explanation
Requires `Shipit.github.oauth?` enabled (default authentication flow) and the default cookie-based `Rack::Session` store (no custom session-id regeneration middleware). The attacker must get their session cookie/value planted on the victim's browser — feasible in shared/kiosk environments, via a crafted link that sets a fixed session id (if the session store accepts client-supplied ids), or other cookie-planting techniques; genuine cross-origin cookie injection normally requires a session-fixation-friendly session backend (e.g., accepting arbitrary session ids from the client) — the exact feasibility depends on the deployed session store configuration, which is host-app-controlled and not fully verifiable from the engine code alone. Given standard Rails `ActionDispatch::Session::CookieStore`, the session id itself isn't attacker-choosable, which somewhat limits classic fixation (the attacker instead needs to share/leak the cookie value itself, e.g. via a public kiosk), but the code path itself is genuinely missing the standard defense-in-depth mitigation (`reset_session` on login) that Rails/OWASP recommend and that this engine already uses in `#logout` and the stale-login branch.

### Recommendation
Call `reset_session` (or otherwise regenerate the session id, preserving `omniauth.origin`/`return_url` before doing so) at the start of `Shipit::GithubAuthenticationController#callback`, before setting `session[:user_id]` and `session[:authenticated]`, mirroring the pattern already used in `#logout` and `force_github_authentication`.

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb
test ":callback does not rotate the session id (fixation)" do
  # simulate attacker pre-establishing an unauthenticated session
  get :callback  # no omniauth.auth set -> renders failed, but session is initialized
  pre_auth_session_id = @request.session.id

  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(raw_info: OmniAuth::AuthHash.new(
      id: 44, name: 'Victim', email: 'victim@example.com', login: 'victim',
      avatar_url: 'https://example.com', api_url: 'https://github.com/api/v3/users/victim'
    ))
  )
  @request.env['omniauth.auth'] = auth

  get :callback  # victim completes OAuth using the same (attacker-known) session

  assert_equal pre_auth_session_id, @request.session.id,
    "Session id should be rotated on login to prevent fixation"
  assert_equal User.find_by(login: 'victim').id, session[:user_id]
end
```
This asserts that the session identifier known to the attacker before authentication is unchanged after the victim authenticates in it, demonstrating the fixation binding.
