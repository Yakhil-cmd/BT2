### Title
Reentrancy in `_requestERC20Transfer` Allows Duplicate Bridge Nonce Emission and Double-Spend of Bridged ERC20 Assets — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`_requestERC20Transfer` makes external calls to the token contract before incrementing `requestNonce`. Neither `onERC20Received` nor `requestERC20Transfer` carries a `nonReentrant` guard. A malicious registered ERC20 token can re-enter `onERC20Received` during `safeTransferFrom`, emitting a `RequestValueTransfer` event with an attacker-controlled `_value` at nonce N before the original call emits a second event at nonce N+1. The counterpart bridge processes both nonces independently, resulting in unauthorized token minting or transfer.

### Finding Description

`requestERC20Transfer` first calls `safeTransferFrom` on the token contract, then calls `_requestERC20Transfer`: [1](#0-0) 

`_requestERC20Transfer` makes external calls to the token contract (`_payERC20FeeAndRefundChange` → `safeTransfer`, and optionally `burn`) **before** emitting the event and incrementing `requestNonce`: [2](#0-1) 

`onERC20Received` is `public` with no access control beyond `onlyRegisteredToken(msg.sender)`: [3](#0-2) 

`_payERC20FeeAndRefundChange` in `BridgeFee.sol` makes external `safeTransfer` calls to the token contract, creating the reentrant callback surface: [4](#0-3) 

By contrast, `handleKLAYTransfer` and `_requestKLAYTransfer` both carry `nonReentrant`: [5](#0-4) [6](#0-5) 

`BridgeFee.sol` even documents this dependency explicitly for the KLAY path but provides no equivalent protection for the ERC20 path: [7](#0-6) 

### Impact Explanation

**Attack trace (non-mintBurn mode):**

1. Operator registers `MalToken` (a malicious ERC20) on the bridge.
2. Attacker calls `requestERC20Transfer(MalToken, victim, 100, 0, "")`.
3. Bridge calls `MalToken.safeTransferFrom(attacker, bridge, 100)`.
4. Inside `transferFrom`, `MalToken` calls `bridge.onERC20Received(attacker, attacker, 1_000_000, 0, "")` — `msg.sender` is `MalToken` (registered), so `onlyRegisteredToken` passes.
5. `_requestERC20Transfer` runs: emits `RequestValueTransfer(ERC20, attacker, attacker, MalToken, 1_000_000, nonce=N, ...)`, then `requestNonce++` → N+1.
6. Control returns to `requestERC20Transfer`; the original `_requestERC20Transfer` runs: emits `RequestValueTransfer(ERC20, attacker, victim, MalToken, 100, nonce=N+1, ...)`, then `requestNonce++` → N+2.
7. Counterpart bridge operators handle nonce N → send 1,000,000 tokens to attacker.
8. Counterpart bridge operators handle nonce N+1 → send 100 tokens to victim.

Attacker deposited 100 tokens and received 1,000,000 tokens on the counterpart chain.

**In mintBurn mode:** step 5 calls `burn(1_000_000)` on the bridge's token balance. If the bridge holds sufficient tokens, the burn succeeds and the counterpart chain mints 1,000,000 tokens to the attacker.

The corrupted value is `requestNonce`: it is consumed twice at N and N+1 for a single deposit, and the `_value` field in the reentrant event is fully attacker-controlled.

### Likelihood Explanation

Exploitation requires a registered malicious ERC20 token, which requires operator privilege. Operators are semi-trusted actors. A compromised or colluding operator can register `MalToken` without any on-chain veto mechanism. Once registered, any user can trigger the reentrancy. The counterpart bridge's `handleERC20Transfer` has no mechanism to detect that two nonces originated from a single deposit transaction. [8](#0-7) 

### Recommendation

1. Add `nonReentrant` to both `onERC20Received` and `requestERC20Transfer` (inheriting from `BridgeTransfer` which already inherits `BridgeHandledRequests`/`BridgeFee`/`BridgeOperator` — add `ReentrancyGuard` to the inheritance chain).
2. Restructure `_requestERC20Transfer` to follow checks-effects-interactions: increment `requestNonce` **before** any external call.

```solidity
// Corrected order
requestNonce++;
uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
if (modeMintBurn) { ERC20Burnable(_tokenAddress).burn(_value); }
emit RequestValueTransfer(..., requestNonce - 1, ...);
```

### Proof of Concept

```solidity
contract MalToken is ERC20 {
    Bridge bridge;
    constructor(Bridge _bridge) { bridge = _bridge; }

    function transferFrom(address from, address to, uint256 amount) public returns (bool) {
        // Standard balance update
        _balances[from] -= amount;
        _balances[to] += amount;
        // Reentrant call: emit RequestValueTransfer with nonce N and value=1_000_000
        bridge.onERC20Received(from, from, 1_000_000, 0, "");
        return true;
    }
}

// Attack:
// 1. operator.registerToken(MalToken)
// 2. attacker.approve(bridge, 100)
// 3. bridge.requestERC20Transfer(MalToken, attacker, 100, 0, "")
//    -> safeTransferFrom triggers MalToken.transferFrom
//    -> MalToken calls bridge.onERC20Received(attacker, attacker, 1_000_000, 0, "")
//    -> RequestValueTransfer emitted: nonce=N, value=1_000_000
//    -> requestNonce becomes N+1
//    -> original _requestERC20Transfer runs
//    -> RequestValueTransfer emitted: nonce=N+1, value=100
// Counterpart bridge processes both nonces -> attacker receives 1_000_100 tokens
```

        if (feeReceiver != address(0) && fee > 0) {
