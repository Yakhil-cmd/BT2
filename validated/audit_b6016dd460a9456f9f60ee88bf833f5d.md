### Title
Operator-precedence bug in `OpenedHandler#provision?` bypasses `review_stacks_enabled=false` for `prevent_with_label` repositories, provisioning an unapproved branch's `shipit.yml` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with three provisioning-behavior checks using `&&`/`||` without parentheses grouping the leading `review_stacks_enabled` term. Ruby's `&&` binds tighter than `||`, so `review_stacks_enabled` only gates the `allow_all` disjunct, not `allow_with_label` or `prevent_with_label`. An attacker opening an unlabeled PR against a repository configured with `provisioning_behavior=:prevent_with_label` and `review_stacks_enabled=false` still triggers stack creation and provisioning from their own branch.

### Finding Description
The intended binding is: `provision? == (review_stacks_enabled? AND provisioning_behavior_matches?)` for every provisioning behavior. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to `&&` > `||` precedence, this parses as:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```
`review_stacks_enabled` is scoped only to the first clause. When `provisioning_behavior = :prevent_with_label` and no label is present on the PR, the third disjunct `(prevent_with_label? && !has_label?)` evaluates to `true` regardless of `review_stacks_enabled`, so `provision?` returns `true` even though review stacks are supposedly disabled for the repository.

Attack: attacker opens a PR (`action == "opened"`) with no labels against a repository they don't control the settings of but which is configured `provisioning_behavior=:prevent_with_label`, `review_stacks_enabled=false`. `respond_to_pull_request_opened?` -> `provision?` returns `true` [2](#0-1)  -> `ReviewStackAdapter#find_or_create!` creates a stack with `branch: params.pull_request.head.ref` (attacker-controlled) [3](#0-2)  -> `Shipit::ReviewStackProvisioningQueue.add(stack)` is invoked, queuing provisioning that will execute `shipit.yml` from the attacker's branch.

This matches the sibling `LabeledHandler` bug pattern (`archive?`/`unarchive?` also lack an explicit `review_stacks_enabled` check independent of the label-based clause) but here the more severe consequence is direct code execution via provisioning rather than archive/unarchive. No guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) intercepts this because the request is a syntactically valid, correctly-signed webhook for `action: "opened"`; the flaw is purely logical/business-level in `provision?`. Existing tests only exercise `prevent_with_label` with `review_stacks_enabled` defaulted to `true` [4](#0-3) , so this specific divergence (`review_stacks_enabled=false` + `prevent_with_label`) is untested and unguarded.

### Impact Explanation
An unapproved branch's `shipit.yml` steps are queued for execution against a repository whose operator explicitly disabled review-stack auto-provisioning (`review_stacks_enabled=false`). Since provisioning executes commands defined in the branch's `shipit.yml` on the deploy host, this is an unauthorized-deploy-equivalent primitive: code the operator never approved to run gets executed because of a stack that should never have been created. This is repeatable against any repository configured with `provisioning_behavior=:prevent_with_label` regardless of the `review_stacks_enabled` toggle, and the attacker only needs to open a PR without the block-label. Impact category: Critical (unauthorized deploy/execution of unapproved branch's steps).

### Likelihood Explanation
Requires the specific repository configuration `provisioning_behavior=:prevent_with_label` (an operator-chosen mode, presumably intended to allow provisioning by default and use a label to block it) combined with `review_stacks_enabled=false` (which the operator believes fully disables review-stack automation). Given `prevent_with_label` is a documented/supported behavior and `review_stacks_enabled` is a standard toggle in `repositories/settings.html.erb`, this misconfiguration combination is plausible in real deployments. The attacker needs only PR-opening ability, no elevated privileges. Cost is a single webhook-triggering action (open PR, no label).

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every disjunct:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix pattern to `LabeledHandler#archive?`/`unarchive?` and `UnlabeledHandler` if they have the analogous structure, since `respond_to_label_change?` already checks `review_stacks_enabled` separately there — but audit for consistency.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (or a new test file), add:
```ruby
test "does not create or queue stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  Shipit::ReviewStackProvisioningQueue.expects(:add).never

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: before fix, `Shipit::Stack.count` increases by 1, `stack.branch == payload["pull_request"]["head"]["ref"]` (attacker's ref), and `Shipit::ReviewStackProvisioningQueue.add` is called — demonstrating `review_stacks_enabled=false` did not prevent provisioning, i.e., the claimed binding (`review_stacks_enabled=false` implies "no provisioning") is broken.
