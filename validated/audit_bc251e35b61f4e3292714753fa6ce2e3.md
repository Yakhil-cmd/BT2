### Title
Cross-repository Status forgery enqueues `ContinuousDeliveryJob` for a victim stack via unscoped sha lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire `Commit` table, with no check that the commit's stack belongs to the repository that authenticated the webhook. An attacker who owns any repository tracked by Shipit can send a validly-signed `status` webhook for their own repo, but reference a `sha` that also exists as a commit in a victim stack from a completely different repository, causing a `Status` to be created for the victim commit and `Commit#schedule_continuous_delivery` to enqueue `ContinuousDeliveryJob` for the victim's `Stack`.

### Finding Description
The broken binding: `commit.stack.repository.full_name` (the repository actually owning the affected `Commit`) MUST equal `payload.dig('repository','full_name')` (the repository whose webhook signature was verified). This invariant is never checked.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-supplied payload (`params.dig('repository','owner','login')`). This only proves the request came from *some* repository/organization the attacker legitimately controls (their own) — it says nothing about which `sha`/`Commit` the payload is allowed to touch.
2. `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` (`app/models/shipit/webhooks.rb:19`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
   ```ruby
   def process
     Commit.where(sha: params.sha).each do |commit|
       commit.create_status_from_github!(params)
     end
   end
   ```
   Unlike the base `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), which scopes lookups via `Repository.from_github_repo_name(repository_name)`, `StatusHandler` never calls `stacks` or filters by `repository_name`/`payload.dig('repository','full_name')`. It queries `Commit.where(sha: params.sha)` globally, matching **any** commit in the database with that sha, regardless of which stack/repository it belongs to.
4. If a victim's tracked stack also has a `Commit` row with the same `sha` (e.g., a shared ancestor commit, a cherry-picked commit, or an attacker deliberately crafting a commit with an identical sha/tree in their own repo history), `commit.create_status_from_github!(params)` creates a `Status` row for that victim commit.
5. `Status`'s `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) calls `commit.schedule_continuous_delivery`, which (`app/models/shipit/commit.rb:281-287`) enqueues `ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)` for the **victim's** stack — even though the request was authenticated solely for the attacker's own repository.

None of the existing guards catch this: `verify_signature` authenticates the org/repo the request claims to originate from, not the target of the mutation; `ExplicitParameters` (`StatusHandler.params`) only validates the shape of `sha`/`state`/etc., not repository ownership; there is no `stacks`/repository scoping call anywhere in `StatusHandler`.

### Impact Explanation
An attacker with a validly-signed webhook for a repository they control can create `Status` records for, and trigger continuous-delivery evaluation of, a stack belonging to an entirely different, victim-owned repository — a payload authenticated for one repository mutating another's commit/stack. This lets the attacker manipulate deploy timing (repeatedly toggling `success`/`failure` to control exactly when `ContinuousDeliveryJob` fires for the victim stack) and, given a matching sha, influence which commit `Stack#next_commit_to_deploy` picks up for deployment. This is a cross-tenant write for a repository that did not authenticate the request, matching the Critical category "a payload for one repository mutating another's stack, commit... ". Repeatable per attacker-controlled webhook send; blast radius is any Shipit-tracked stack that shares a `Commit.sha` with an attacker-reachable repository.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment` enabled and has a `Commit` row whose `sha` also matches a commit reachable/known to the attacker (this is realistic for shared upstream history, forks, cherry-picks, or vendored/mirrored repos — a common Shipit deployment pattern). The attacker needs no victim secrets: they only need a legitimately signed webhook from their own tracked repository, which is standard unprivileged GitHub webhook behavior. Cost is a single POST request per toggle, fully repeatable and scriptable, requiring no elevated access at any layer.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the authenticated repository, mirroring `Handler#stacks`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `commit.stack.repository.full_name == repository_name` (the repository that authenticated the webhook) before any `Status` is created or `ContinuousDeliveryJob` is enqueued.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":status only affects commits belonging to the authenticated repository" do
  attacker_stack = shipit_stacks(:cyclimse) # owned by a different repo/org than :shipit
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)

  shared_sha = "deadbeef00"
  victim_commit = victim_stack.commits.create!(
    sha: shared_sha, message: "victim", author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now
  )

  request.headers['X-Github-Event'] = 'status'
  # payload authenticated only for the attacker's own repo (matches attacker_stack.repository)
  body = {
    sha: shared_sha, state: 'success', context: 'ci',
    repository: { full_name: attacker_stack.repository.full_name, owner: { login: attacker_stack.repository.owner } }
  }.to_json

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    post :create, body: body, as: :json
  end
  assert_equal 0, victim_commit.statuses.count
end
```
Before the fix, `assert_no_enqueued_jobs` fails because `ContinuousDeliveryJob.perform_later(victim_stack)` is enqueued and `victim_commit.statuses.count` is `1`, despite the webhook only being signed/authenticated for `attacker_stack`'s repository.
