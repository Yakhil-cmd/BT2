Confirmed: unlike other API controllers (e.g. `Api::StacksController`, which uses the base `stack` method), `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) overrides `BaseController#stack` and looks up `Stack.from_param!(params[:stack_id])` directly instead of going through the scoped `stacks` collection (`app/controllers/shipit/api/base_controller.rb:74-80`), which is the only place that filters by `current_api_client.stack_id`.

### Title
Stack-scoped API tokens can read CI/build status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` token can be created scoped to a single stack (`stack_id` set), which is meant to restrict that token's `read:stack` permission to only the stack it was issued for. The `Api::CCMenuController` bypasses this scoping, letting the token read the build/deploy status of *any* stack in the installation.

### Finding Description
`Shipit::ApiClient` supports scoping a token to one stack: `stacks` in `BaseController` returns `Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true, otherwise `Stack.all` [1](#0-0) . Every other API resource controller (e.g. `Api::StacksController#show`) relies on this scoped `stack`/`stacks` helper to resolve `params[:stack_id]`, so a stack-scoped token can never touch a stack outside its `stack_id`.

`Api::CCMenuController`, however, defines its own private `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `stacks` scoping method: [2](#0-1) . The `require_permission :read, :stack` before-action (from `require_permission!`) only checks that the token's `permissions` array contains `"read:stack"` — it never compares the requested stack to `current_api_client.stack_id` [3](#0-2) .

This breaks the binding: **the stack a token is authorized for != the stack the controller action actually touches**. A token created via `ApiClient.create_with(permissions: %w[read:stack], stack: stack_a)` — for example the token minted automatically by `CCMenuUrlController#client` for a specific stack (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) — can be replayed against `GET /api/stacks/:any_other_stack/ccmenu` and will successfully render that other stack's data, since `params[:stack_id]` is taken verbatim and resolved against `Stack.from_param!`, not against the caller's scoped `stacks`.

### Impact Explanation
This is an authorization-scope escalation: a token intentionally minted with the narrowest possible scope (single-stack, read-only, used for e.g. embeddable CI status widgets like CCMenu/CCTray clients) can be used to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock status, etc.) of every other stack in the Shipit instance, including private or sensitive ones. This matches the in-scope "escalation into ... unauthenticated read of stack state" impact category, since the attacker (holder of a narrowly-scoped, possibly leaked/embedded token — e.g. one embedded in a CI status badge URL) reads state for stacks the token was never authorized to see.

### Likelihood Explanation
Any holder of a valid but stack-scoped read-only API token (a fairly low-privilege credential, often embedded in third-party CI dashboard integrations via `CCMenuUrlController`) can trivially exploit this by simply changing the `stack_id` path segment of the CCMenu URL. No additional privileges, races, or timing are required.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so stack-scoped tokens are restricted the same way as in every other API controller.

### Proof of Concept
1. As an admin, create a stack-scoped `ApiClient` for `stack_a` with permission `read:stack` (e.g. via `CCMenuUrlController#fetch`, which does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` bound implicitly to that stack's CCMenu URL, or directly via the `api_clients` UI setting `stack: stack_a`).
2. Using that token's `authentication_token`, call `GET /api/stacks/<owner>/<stack_b_repo>/<stack_b_env>/ccmenu?token=<token>` for a *different* stack `stack_b` that the token was never scoped to.
3. Observe `Api::CCMenuController#stack` resolves via `Stack.from_param!(params[:stack_id])` [4](#0-3)  and returns a 200 with `stack_b`'s build/deploy status, even though `current_api_client.stack_id` is `stack_a.id`.
