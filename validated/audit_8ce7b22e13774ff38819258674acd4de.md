### Title
Non-constant-time hash-authentifier comparison enables timing-based preimage recovery for hash-locked addresses - (File: definition.js)

### Summary
`definition.js`'s `evaluate()` handler for the `hash` authentifier type verifies a spender-supplied secret against the address definition's committed SHA-256 hash using a plain `===` string comparison, which is not constant-time and can leak information about how many leading bytes of a guess match the true preimage, analogous to the MD5 password-comparison timing side channel described in ALPINE-CVE-2026-6478.

### Finding Description
Ocore address definitions support a `hash` authentifier clause of the form `['hash', {algo: 'sha256', hash: 'base64'}]`, which lets funds be locked to knowledge of a preimage whose SHA-256 digest equals the committed `hash` value [1](#0-0) . When a unit is posted, `validateAuthentifiers()`'s `evaluate()` function computes the SHA-256 digest of the attacker/spender-supplied authentifier string and compares it to the committed hash with JavaScript's `===` operator: [2](#0-1) 

`===` on strings in V8 performs a byte-by-byte comparison and returns as soon as a mismatch is found (and Base64-encoded digest strings are compared left-to-right), so the time taken to reject an incorrect guess is (weakly) correlated with the length of the matching prefix of the *encoded digest*, not the preimage itself, but because the digest is a deterministic function of the guessed preimage, an attacker who can also locally compute the digest for their own guesses and observe validation-rejection timing from a full node (e.g., via repeated `bad hash at path` rejections from a node they connect to, or via light-client history requests) can attempt to narrow down which candidate preimages produce hashes that are "closer" to the target under a byte-wise comparison. This mirrors the CVE's root cause: comparing a security-relevant hash/token with a non-constant-time comparator inside an authentication/authorization decision path (`sig`/`hash` case in `evaluate()`) that is directly reachable by any unprivileged unit poster who knows (or is guessing) the address's `hash`-authentifier secret and submits crafted units or signed messages for validation (the same code path is also invoked from `signed_message.js` for `hash` conditions in signed messages).

### Impact Explanation
If an attacker can practically extract enough timing signal, they can accelerate recovery of the preimage protecting a `hash`-authentifier address, ultimately enabling **unauthorized spending** of funds locked behind that hash condition — a direct funds-loss impact matching the "concrete unauthorized spending" bar in scope. This is the same class of harm as the CVE (credential/secret recovery via timing) applied to ocore's hash-authentifier mechanism instead of PostgreSQL's MD5 password check.

### Likelihood Explanation
Exploitability is constrained: SHA-256 hash-lock preimages are typically high-entropy secrets, and network jitter/validation-pipeline noise in a distributed multi-hop system makes a practical remote timing side channel considerably harder to exploit than a local timing oracle (as in the original PostgreSQL CVE, which is itself rated only Medium/6.5). Still, the root-cause code pattern — a raw `===`/non-constant-time comparison used to gate an authentifier/authorization decision reachable by any address that adopts a `hash` definition — is a legitimate, in-scope analog of the reported bug class, distinct from network-DoS or malicious-peer scenarios (it's exercised by ordinary unit/authentifier validation logic).

### Recommendation
Replace the `===` comparison in the `hash` case of `evaluate()` in `definition.js` with a constant-time comparison (e.g., decode both the computed digest and `args.hash` to `Buffer`s of equal fixed length and use `crypto.timingSafeEqual`), guarding against length mismatches before the call to avoid throwing.

### Proof of Concept
1. Create an address whose definition includes `['hash', {algo: 'sha256', hash: '<base64 target digest>'}]`.
2. As an attacker without the true preimage, submit many candidate authentifier values (or signed messages per `signed_message.js`) to a full node you control or observe, each producing a distinct SHA-256 digest.
3. Measure response latency for each rejected candidate at `definition.js:763` (`bad hash at path`) across repeated trials to statistically distinguish comparisons that are rejected on an earlier vs. later mismatching byte of the digest.
4. Use the leaked prefix-agreement signal to iteratively steer preimage search, reducing the effective search space compared to a fully constant-time verification, analogous to recovering an MD5-hashed password via PostgreSQL's timing channel in ALPINE-CVE-2026-6478. [3](#0-2)
