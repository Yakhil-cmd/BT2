### Title
Unbounded memory allocation via node/depth-only size check on incoming device messages allows DoS by a paired device - ([File: string_utils.js], [File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub()` gates all incoming device messages (pairing, text, private payment chains, contract messages, etc.) with a single anti-DoS check, `isTooDeeplyNestedOrHasTooManyNodes(json, 20, 100000)`, before dispatching to `doHandle()`. This check only counts object/array *nodes* and nesting *depth* — it never measures the byte/character length of string leaf values. A single oversized string value anywhere in the message JSON (e.g. inside `private_payment_chains` chain payload fields, `text` body, `object` body, or arbiter-contract fields) counts as one "node" regardless of its size, so the function offers no real protection against large-payload memory exhaustion, exactly mirroring the "dead config" pattern in the reported mcp-framework bug (a size-looking guard that never enforces size).

### Finding Description [1](#0-0) 
`handleMessageFromHub` runs this check on every message received from the hub (which relays messages originating from any paired device) before any further processing, then serializes/dispatches the message via `doHandle()`.

The check itself is: [2](#0-1) 
`isTooDeeplyNestedOrHasTooManyNodes` increments `nodeCount` only for array elements / object keys and recurses by `depth`; for any string, number, or boolean leaf it does nothing — no `length` accumulation at all. This is unlike the sibling function `isTooBigObj` (string_utils.js:286-323), which *does* track cumulative string `length` against a `lengthLimit`, but that stricter function is used only in the AA formula evaluator (`formula/evaluation.js`, e.g. `json_parse`, `concat`, `isTooBigObj` calls in `aa_composer.js`) — never for validating device-to-device/hub-relayed messages.

Consequently, a malicious paired device (or a device impersonating a hub relay of an "innocent" contact) can send a `hub/message` payload such as `{subject: "private_payment_chains", body: {chains: [[{unit:"...", payload:{asset:"...", inputs:[...], outputs:[...], hugeField: "<50MB string>"}}]]}}` or a `text`/`object` message with one giant string field. This passes the depth/node check trivially (few nodes, shallow depth) yet still causes:
- `JSON.parse`/hub message deserialization of the huge string,
- `JSON.stringify(arrPrivateElements)` when queuing to `unhandled_private_payments` [3](#0-2) ,
- `objectHash.getBase64Hash(objChains)` / `getBase64Hash(payload)` hashing of the oversized payload [4](#0-3) ,
- string `.replace()` regex passes over huge text bodies in the `"text"` case [5](#0-4) ,

all before any application-level `MAX_*` length constant (e.g. `MAX_AA_STRING_LENGTH`, `MAX_PROFILE_VALUE_LENGTH`) is ever consulted, because those constants are enforced only in AA formula evaluation and unit validation paths, not in the wallet/device message-handling path.

### Impact Explanation
Because the check exists and looks like a size-limiting guard, but does not actually bound the memory required to process a hub-relayed device message, a single crafted message from a correspondent/paired device (an actor explicitly reachable without special privileges — pairing is opt-in but any paired counterparty, e.g. in a private-payment or arbiter-contract flow, can send it) can force the receiving wallet node to allocate and repeatedly copy multi-megabyte-to-gigabyte strings (parse, stringify, hash), leading to memory exhaustion / crash of that wallet process (Denial of Service). This matches CWE-770 (Allocation of Resources Without Limits or Throttling) in the same way as the reported analog. It does not directly enable double-spend/inflation, but it can freeze the ability of the affected wallet to process new private payments/AA-related device coordination.

### Likelihood Explanation
Any paired device (already an accepted trust/threat boundary per policy) can trigger this with a single message; no race conditions or elevated privileges are required, and the flawed check is on the primary dispatch path for practically all device message subjects (`pairing`, `text`, `object`, `private_payment_chains`, arbiter/contract messages). The websocket-level `maxPayload` in `network.js` may impose an outer bound on directly connected peers, but device messages typically traverse an untrusted hub via store-and-forward (`outbox`/`device_messages` tables) rather than a single raw websocket frame size limit visible at this layer, so the effective cap on a single logical device message is not clearly enforced here.

### Recommendation
Add an explicit serialized-size check (using `isTooBigObj`'s `lengthLimit` semantics, or `JSON.stringify(json).length` against a configured `MAX_DEVICE_MESSAGE_LENGTH`) in `handleMessageFromHub` before dispatching to `doHandle()`, in addition to the existing depth/node check. Ensure the same size limit is enforced uniformly wherever device-relayed payloads are parsed, stringified, or hashed (`network.js` `handleOnlinePrivatePayment`/`handleSavedPrivatePayments`, `wallet.js` `handlePrivatePaymentChains`, arbiter contract handlers).

### Proof of Concept
Not independently executed against a running node (no filesystem/runtime access in this environment); the exploit path is derived from static code reading:
1. Attacker pairs with (or already is a correspondent of) the victim's wallet.
2. Attacker sends via the hub a `hub/message` justsaying with `body = {subject: "private_payment_chains", body: {chains: [[{unit: "<44-char b64>", message_index: 0, payload: {asset: "<44-char b64>", inputs: [{}], outputs: [{}], filler: "<huge, e.g. 100MB, string>"}}]]}}`.
3. `isTooDeeplyNestedOrHasTooManyNodes(json, 20, 100000)` in `wallet.js:65` passes (only a handful of nodes, shallow depth) regardless of the `filler` string size.
4. Downstream code paths (`objectHash.getBase64Hash`, `JSON.stringify` for caching/db-storage in `network.js:2395`) allocate/copy the full oversized string repeatedly, consuming memory proportional to attacker-controlled input with no cap, mirroring the reported `readRequestBody` memory-exhaustion pattern.

```javascript
function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
```
