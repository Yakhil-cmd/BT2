### Title
Unhandled exception during oscript/AA formula evaluation crashes the node - (File: formula/evaluation.js)

### Summary
`formula/evaluation.js` implements the recursive, callback-based `evaluate()` function that interprets AA formulas (used in `init`, `getters`, `state`, message `if`/`init` fields, and payment `amount`/`address` expressions). Throughout this function there are numerous raw `throw Error(...)` statements for conditions the author considered "impossible" (e.g. `throw Error("test evaluated to object " + res);` in the `ifelse` case, `throw Error('unrecognized op '+op);` in the default switch branch, `throw Error("unknown assignment op: " + assignment_op);`, etc.) alongside the intended error path, `setFatalError(...)`, which gracefully reports formula errors back to the caller so the trigger can be bounced. [1](#0-0) [2](#0-1) [3](#0-2) 

Because `evaluate()` is invoked asynchronously via callbacks (and even artificially yields the event loop every 100 recursive calls via `setImmediate`, see `formula/evaluation.js:126-129`), a `throw` executed inside one of these deep, asynchronous callback frames is not caught by any surrounding `try/catch` in the call chain that leads back to `aa_composer.handleTrigger`/`evaluateAA`/`replace` (`aa_composer.js:589-618`, `aa_composer.js:697-846`). It therefore becomes a Node.js "uncaught exception" that propagates to the single global handler in `network.js`: [4](#0-3) 

```js
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

which deliberately re-throws to kill the entire process. This mirrors the Aedes CVE-2020-13410 bug class (CWE-755, improper exception handling): a piece of attacker-supplied input that reaches a code path meant to write/process it, but instead of being handled as a validation failure, triggers an uncaught exception that crashes the whole service.

### Finding Description
`aa_composer.handleTrigger()` is invoked whenever a unit sends funds/data to an Autonomous Agent address — a path reachable by any unprivileged user simply by posting a payment/data unit to an AA address, i.e. acting as an "AA trigger sender". `handleTrigger` calls `evaluateAA()` → `formulaParser.evaluate()` (`aa_composer.js:589-615`) which recurses into `formula/evaluation.js`'s `evaluate()` to interpret the AA's `getters`, `init`, `state`, and message templates using attacker-influenced `trigger.data` and `params`. [5](#0-4) 

Inside `evaluate()`, most error conditions are correctly routed through `setFatalError()`, which safely propagates the error back through the callback chain to `handleTrigger`'s `bounce()` path (`aa_composer.js:1865-1867`). However, a handful of branches instead perform a synchronous `throw Error(...)` (e.g. `formula/evaluation.js:1472` "test evaluated to object", `2758` "unrecognized op", `1395` "unknown assignment op"). Since `evaluate` is a deeply nested asynchronous/CPS-style function that periodically defers execution with `setImmediate` (`formula/evaluation.js:126-129`), these `throw`s are not guaranteed to unwind synchronously into a `try/catch` that exists anywhere up the call stack at the moment of the throw — they surface as Node.js `uncaughtException` events. The single top-level `process.on('uncaughtException', ...)` handler in `network.js:4530-4543` deliberately re-throws to crash the node "to avoid ending up in an inconsistent state," meaning any reachable unguarded `throw` in the formula evaluator is a full node crash, remotely triggerable by any user able to post an AA trigger unit (which requires no special privilege — funding an AA address with a small trigger payment is enough).

This differs from a normal "logic bug returns wrong result" — it is specifically an improper-exception-handling issue: the code path exists to convert bad input into a controlled error/bounce (as `setFatalError` does everywhere else), but a subset of conditions bypass that mechanism and instead crash the process, exactly analogous to Aedes's `lib/write.js` not catching exceptions raised while writing a malformed packet and crashing the broker instead of failing that one operation.

### Impact Explanation
A crash of the ocore full node process is a denial of service: the node stops validating/writing new units and stops confirming/relaying transactions until manually restarted, satisfying the "network unable to confirm new units" bar from the validation criteria. Because AA triggers are processed identically by every full node validating the DAG (deterministic execution is required for consensus), a single crafted AA trigger unit that reaches one of the unguarded `throw` branches would crash every full node that processes it as it becomes part of the stabilized DAG, not just a single victim — this is a network-wide availability impact, not merely a local node inconvenience.

### Likelihood Explanation
Reaching one of these unguarded throws requires crafting specific formula expressions/AST shapes that hit an edge case not otherwise blocked by `setFatalError` checks or AA-definition-time static validation (`aa_validation.js`). This requires non-trivial understanding of the formula evaluator's internals and exact conditions under which the type checks preceding each `throw` fail to catch the value (e.g., is there any concrete formula construct producing a raw JS object as a boolean `ifelse` test bypassing the `wrappedObject`/`Decimal` normalization?). I was not able to confirm within the available tools/time whether AA-definition-time validation (`aa_validation.js`, not fully reviewed) already forecloses all such inputs, nor could I build/run a concrete formula that reaches one of these specific `throw` statements at runtime. This is a plausible but unconfirmed bug class match rather than a proven, reproduced crash.

### Recommendation
Audit every `throw Error(...)` inside `formula/evaluation.js`'s `evaluate()` (and any function it calls asynchronously) and replace them with `setFatalError(...)` calls (as used elsewhere in the same file) so that any unexpected/edge-case condition during formula evaluation is converted into a bounced AA response rather than an uncaught exception. Additionally, wrap the top-level `formulaParser.evaluate()` invocation sites in `aa_composer.js` (`evaluateAA`, `replace`, and the "case"/`if`/`init` evaluators) with defensive `try/catch` that route any synchronous throw into `bounce()`, so a single malformed formula construct cannot escalate into a full-node crash via the global `uncaughtException` handler.

### Proof of Concept
Not reproduced. A full PoC would require constructing a `getters`/`init`/`state` AA formula whose AST reaches one of the identified unguarded `throw` sites in `formula/evaluation.js` (e.g. the `ifelse` branch at `formula/evaluation.js:1469-1478`, or the assignment-operator branch at `formula/evaluation.js:1387-1399`) at runtime with attacker-controlled `trigger.data`, then submitting a trigger unit funding that AA and observing that the full node crashes with an uncaught exception instead of bouncing the trigger. This requires deeper interactive testing of the formula grammar/evaluator than was possible with the available read-only tools.
