### Title
Webhook organization spoofing allows unauthorized cross-organization status injection and deploy triggering — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *unverified* request body, while the actual `Handler` classes that mutate application state (create statuses, sync stacks, etc.) key off a different field of the same body: `repository.full_name`. Because these two fields are never cross-checked, and because a webhook secret is documented as optional per organization, an attacker can pick an organization configured without a `webhook_secret` to pass verification trivially, then point `repository.full_name` at a completely different (securely configured) organization's stack to inject fabricated GitHub events against it.

### Finding Description
The signature check binds "the organization whose secret is used to authenticate" to a value read straight out of the attacker-supplied JSON body, before that body is authenticated: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
``` [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a field the attacker fully controls in an unauthenticated POST.

If that organization has no `webhook_secret` configured (explicitly documented as "optional" — `docs/setup.md` line 30), `verify_webhook_signature` short-circuits to `true` unconditionally: [3](#0-2) 

Once "verified," `WebhooksController#create` dispatches the *entire* attacker-controlled body to every registered handler for the event, with no re-check that the acted-upon repository matches the organization used for authentication: [4](#0-3) 

Handlers resolve the target `Repository`/`Stack` purely from `repository.full_name`, independent of the field used to select the webhook secret: [5](#0-4) 

For example, the `StatusHandler` creates a `Status` for any commit matching the attacker-supplied `sha`, on any stack that happens to contain that commit sha — no ownership check to the "authenticated" organization at all: [6](#0-5) 

Creating a `Status` record auto-triggers continuous delivery evaluation: [7](#0-6) [8](#0-7) 

and, if the target stack has `continuous_deployment?` enabled and the forged commit/status make it "deployable," `Stack#trigger_continuous_delivery` will call `trigger_deploy`, actually shipping code: [9](#0-8) 

The binding broken is exactly the analog class described: **the organization authenticated by `verify_signature` (from `repository.owner.login`, tied to whichever org's secret happened to validate) is never equal to the organization/repository actually written to by the handlers (`repository.full_name`)**. This is structurally identical to the Merkl `disputer` bug: a piece of state (`disputer` set / `endOfDisputePeriod` passed) is checked in one place while a different, unsynchronized piece of state is what's actually consumed for the sensitive action.

### Impact Explanation
An unauthenticated network attacker who knows (or guesses) that any single organization configured in this Shipit instance's `secrets.github` has no `webhook_secret` set can forge `push`, `status`, `pull_request`, `check_suite`, or `membership` events for **any other organization/stack** hosted by the same Shipit instance — including ones that do have webhook secrets configured. This can inject fabricated CI "success" statuses that, combined with `continuous_deployment?`, cause an unauthorized deploy (`Stack#trigger_deploy`) to run without ever needing the target organization's credentials — a Critical/High impact per the rules ("an unauthorized deploy").

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (it's meant to be called by GitHub) and requires no session, API token, or secret to reach `WebhooksController#create`. The only precondition is that at least one configured GitHub organization in the deployment lacks a `webhook_secret`, which the setup docs explicitly present as an optional field, making this a realistic supported configuration, not a misuse of the engine.

### Recommendation
After selecting `github_app` from `repository_owner` and verifying the signature, additionally verify that `repository.full_name`'s owner segment (or `organization.login`) matches the organization whose secret validated the request, rejecting the webhook otherwise. Alternatively, require every configured GitHub App to have a non-blank `webhook_secret` (removing the `return true unless webhook_secret` bypass) so no organization can be used as a signature-free proxy for forging events against a different org's repositories.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`: `VictimOrg` (has `webhook_secret` set) hosting stack `VictimOrg/prod-app` with `continuous_deployment: true`, and `NoSecretOrg` (no `webhook_secret` configured, per the documented-optional setting).
2. Attacker sends an unauthenticated POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of latest commit on VictimOrg/prod-app>",
  "state": "success",
  "context": "ci/fake",
  "repository": { "full_name": "VictimOrg/prod-app", "owner": { "login": "NoSecretOrg" } }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner` = `"NoSecretOrg"`, loads that org's `GitHubApp`, and since it has no `webhook_secret`, `verify_webhook_signature` returns `true` with no valid `X-Hub-Signature` header required.
4. `StatusHandler` matches `Commit.where(sha: ...)` on `VictimOrg/prod-app`'s commit and calls `create_status_from_github!`, creating a `success` `Status`.
5. `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, which (if the commit is otherwise deployable) calls `Stack#trigger_continuous_delivery` → `trigger_deploy`, deploying `VictimOrg/prod-app` without the attacker ever possessing `VictimOrg`'s webhook secret or any Shipit credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
