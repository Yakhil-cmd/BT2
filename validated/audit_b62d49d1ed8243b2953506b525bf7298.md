### Title
Webhook signature verification is keyed on attacker-controlled `repository.owner.login`, letting an unsigned/wrongly-signed payload trigger a sync of a *different*, properly-secured repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the HMAC signature against by reading `repository.owner.login` straight out of the **unauthenticated** JSON body. The event handlers that actually mutate state (e.g. `PushHandler`) instead resolve the target `Repository`/`Stack` using a *different* field of the same body, `repository.full_name`, via `Repository.from_github_repo_name`. Because the field used to pick the verifying secret and the field used to pick the acted-upon repository are independent and both attacker-supplied, they are never required to agree, and if the organization named in `owner.login` has no `webhook_secret` configured, verification trivially passes for a payload whose `full_name` targets a completely different, secret-protected repository.

### Finding Description
`verify_signature` computes the app used for verification purely from payload content: [1](#0-0) 
`repository_owner` is read with no validation from the same unauthenticated JSON: [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Meanwhile, the actual write path (`Webhooks::Handlers::Handler#stacks` / `PushHandler#process`) determines *which* repository/stack to act on using `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 
`Repository.from_github_repo_name` does a straight `owner/name` split of `full_name` with no cross-check against whatever organization was used for signature verification: [6](#0-5) 

Equality that should hold but doesn't: *organization whose secret authenticated the request* == *organization that owns the repository being written to*. In a multi-organization deployment (`Shipit.github_app_config`/`Shipit.github_organizations`, `lib/shipit.rb:170-200`), an attacker can pick any organization slug that has no `webhook_secret` set (or is simply unknown/misconfigured on the Shipit side) for `repository.owner.login`, causing `verify_webhook_signature` to return `true` for free, while setting `repository.full_name` to `"protected-org/protected-repo"` — a repo belonging to an organization that *does* have a real `webhook_secret`. `Webhooks::for_event('push')` then runs `PushHandler`, which resolves the target repo via `full_name` alone and calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the target branch, enqueuing `GithubSyncJob` with an attacker-chosen `expected_head_sha`: [7](#0-6) 

This crosses the exact boundary called out in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
An unprivileged, unauthenticated attacker (no Shipit session, no `ApiClient`, no GitHub webhook secret for the targeted repo) can force `GithubSyncJob` to run against a stack belonging to a different, secured GitHub organization, injecting an arbitrary `expected_head_sha` and forcing commit ingestion/state changes (`append_commit`, `lock_reverted_commits!`, cache invalidation) for that repository's stacks — an unauthorized cross-repository state mutation that bypasses the webhook_secret protecting that repository. Other handlers keyed the same way (`pull_request`, `check_suite`, `membership`) are similarly reachable, extending the effective blast radius to PR-provisioned review stacks and stack archive/unarchive actions for repositories the attacker has no legitimate signing capability for.

### Likelihood Explanation
Exploitability is entirely conditioned on the Shipit deployment using the multi-organization github config schema (`Shipit.github_app_config`) with at least one configured organization lacking a `webhook_secret`, or an organization name that legitimately has no secret set by design/oversight. Given `docs/setup.md`/`config/secrets.*.yml` document `webhook_secret` as optional per organization, this is a realistic misconfiguration, not a purely theoretical one, and requires no privileged capability from the attacker — only knowledge of a valid but weakly/non-secured organization slug and the target repository's `full_name`.

### Recommendation
Bind the two lookups: resolve the target repository/organization from the *same, already-verified* signing context, or verify that `repository.full_name`'s owner matches `repository.owner.login`/the organization whose secret validated the signature before dispatching to handlers. At minimum, reject webhooks where the acted-upon repository's owner differs from the organization used to select the verifying `webhook_secret`, and treat "no `webhook_secret` configured" as a hard-fail (or restrict which repositories that unsecured org may claim) rather than an automatic pass.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub config: `orgA` (has `webhook_secret: real-secret`) owns tracked repo `orgA/protected-repo`; `orgB` is configured with no `webhook_secret` (or is any organization slug the server accepts without one).
2. POST to `/github/webhooks` with headers `X-Github-Event: push`, `X-Hub-Signature: sha1=anything` and JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/protected-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgB")`; since `orgB` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (invalid) `X-Hub-Signature` value.
4. `PushHandler` resolves the target via `repository.full_name` (`"orgA/protected-repo"`), finds `orgA`'s real stacks, and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, mutating `orgA`'s protected stack state without ever presenting `orgA`'s `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
