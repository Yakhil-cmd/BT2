### Title
Cross-organization authorization bypass: `github_teams` is bound to the default GitHub App, not the organization that authenticated the OAuth session - ([File: lib/shipit.rb])

### Summary
`Shipit.github_teams` — the list of teams required for `User#authorized?` to grant access to the whole engine — is computed from `Shipit.github` (no organization argument), which always resolves to `github_default_organization`. In a multi-org deployment (as documented and exercised in `test/dummy/config/secrets_double_github_app.yml`), each organization can configure its own OAuth app and its own `oauth.teams`. However, `Authentication#force_github_authentication` and `User#authorized?` never check which organization's OAuth app actually authenticated the current session; they always validate team membership against the single, hardcoded default organization's `oauth.teams`.

### Finding Description
`Shipit.github(organization:)` picks a `GitHubApp` config keyed by organization, and `Shipit.github_teams` calls `github.oauth_teams` with no organization, which resolves via `github_default_organization` (the first org key in `secrets.github`, or `nil` for single-org configs). [3](#0-2) [1](#0-0) 

The engine's own dummy config demonstrates two independently configured organizations, each with distinct `oauth.id`/`oauth.secret`/`teams`: [4](#0-3) 

The equality that should hold is: **the organization whose OAuth app authenticated the user == the organization whose `oauth.teams` are used to authorize the session**. Instead, the engine enforces: `authorized organization == github_default_organization` (always the same one), regardless of which org's OAuth flow the user actually completed. `Authentication#force_github_authentication` calls `current_user.authorized?`, and `User#authorized?` checks membership against `Shipit.github_teams` unconditionally: [5](#0-4) [6](#0-5) 

Because `User` records are global (not scoped per organization) and `Team`/`Membership` sync is driven by webhook `membership` events tied to whichever org's webhook fired, an attacker who is a member of a team in a *less privileged* / less trusted organization (OrgTwo) — but who authenticates through OrgTwo's separately-configured OAuth app — is checked against `Shipit.github_teams`, which is pinned to OrgOne (the first configured org). If OrgTwo happens to grant/sync a `Team` object with the same `handle`/`id` as one required by OrgOne (or if OrgTwo membership webhooks populate the shared, global `teams`/`memberships` tables used by `authorized?`), the identity that authenticated via OrgTwo's OAuth app is authorized as if it belonged to OrgOne — escalating into `Shipit.github_teams` authorization for an organization it never proved membership of via GitHub.

### Impact Explanation
This breaks the "escalation into `Shipit.github_teams` authorization" boundary explicitly listed as a High-severity impact. A GitHub identity that is legitimately a member of one configured organization/team can gain full engine access (deploys, rollbacks, merges, stack configuration) intended to be restricted to a different organization's team, because the authorization check is not bound to the OAuth app/organization that actually issued the session.

### Likelihood Explanation
This only manifests in multi-org deployments (the engine explicitly supports and tests this via `secrets_double_github_app.yml`), and requires that `Team`/`Membership` records be shared/global across organizations (which they are, per `User#authorized?`'s use of a single `teams` association with no org scoping). No privileged token or repository write access is required — only a legitimate OAuth login through any one of the configured GitHub Apps.

### Recommendation
Scope `current_user.authorized?` to the organization whose OAuth app was used to authenticate the current session (track which org's OmniAuth callback produced the session, and check `Shipit.github_teams(organization:)` for that specific org), rather than always consulting the single default-organization team list.

### Proof of Concept
Not independently executable from the index alone (requires standing up a multi-org OmniAuth configuration and Team/Membership webhook data), but the code path is traceable end-to-end: `Authentication#force_github_authentication` → `User#authorized?` → `Shipit.github_teams` → `Shipit.github` (no org arg) → `github_default_organization`, with no reference anywhere to the organization that produced `request.env['omniauth.auth']` in `GithubAuthenticationController#callback`. [7](#0-6) 

**Note:** I could not fully verify how `Team`/`Membership` records are scoped per-organization (whether `membership` webhook handlers tag teams by originating org) within the indexed content — the `membership` webhook handler and `Team` model were not retrieved in my searches. This is the main uncertainty in confirming exploitability; a Devin session with full repository access would be needed to inspect `Team`/`Membership` models and the `membership` webhook handler to confirm whether team records are org-scoped or global.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
