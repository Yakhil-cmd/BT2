### Title
Operator disabling `review_stacks_enabled` does not prevent PR review-stack re-provisioning via reopened webhook due to `&&`/`||` precedence bug in `unarchive?` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` intends to gate all review-stack provisioning behind `repository.review_stacks_enabled`, but Ruby operator precedence makes `&&` bind tighter than `||`, so the `review_stacks_enabled` check only applies to the `allow_all` branch. The `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`, letting an attacker who controls a labeled PR from a fork force stack unarchiving/creation and command execution on a repository where review stacks are explicitly disabled.

### Finding Description
The broken binding: the code intends `review_stacks_enabled == the gate applied to every provisioning_behavior branch`, but the actual binding is `review_stacks_enabled == the gate applied only to the allow_all branch`.

`app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb:70-75`:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
`&&` has higher precedence than `||`, so this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. If `review_stacks_enabled` is `false` but `provisioning_behavior` is `allow_with_label` and the attacker's PR carries the configured label, the second disjunct evaluates to `true` regardless of `review_stacks_enabled`, so `unarchive?` returns `true`.

Call chain: `process` (`reopened_handler.rb:41-45`) → `respond_to_pull_request_reopened?` (`:65-68`) → `unarchive?` → `stack.unarchive!` on `ReviewStackAdapter` (`review_stack_adapter.rb:37-50`), which calls `create!` if the stack is blank/nonexistent (`:72-85`) and always enqueues the stack via `Shipit::ReviewStackProvisioningQueue.add(stack)` (`:47`, `:82`), triggering provisioning/command execution.

Attacker action: fork the target repository (configured with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label`), open a PR, attach the configured provisioning label to their own PR, then close/reopen (or just open, via the analogous `OpenedHandler#provision?` bug) the PR. The `pull_request_reopened` webhook is a public event the attacker can trigger by their own repository action; no Shipit credentials are required. `verify_signature`/`GitHubApp#verify_webhook_signature` only verify the webhook came from GitHub for that repository — they do not enforce the `review_stacks_enabled` business rule, so they don't block this. The `ExplicitParameters` schema in the handler validates payload shape only, not authorization semantics.

### Impact Explanation
This causes stack creation (`ReviewStack.create!`) and enqueuing into `Shipit::ReviewStackProvisioningQueue`, which drives provisioning tasks that execute commands (deploy specs, hooks) against the target repository — effectively an unauthorized re-provisioning/command execution path for a repository whose operator explicitly disabled review stacks (`review_stacks_enabled == false`). This matches the Critical category: "a record written for a repository that did not authenticate it" and command execution that should not occur, scoped to any repository misconfigured with `allow_with_label`/`prevent_with_label` while `review_stacks_enabled` is false. It is repeatable against any such repository by any external contributor able to label their own PR.

### Likelihood Explanation
Requires the repository to be configured with `review_stacks_enabled = false` combined with `provisioning_behavior` set to `allow_with_label` (attacker needs to know/guess the label, but on their own fork PR they can attach any label freely) or `prevent_with_label` (no label needed at all — trivially satisfied by default). Attacker cost is minimal: open/close/reopen a PR on their own fork with an optional label. No secrets, sessions, or special permissions needed. This is fully attacker-controlled and repeatable.

### Recommendation
Fix operator precedence by grouping the intended logic explicitly, e.g.:
```ruby
def unarchive?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the identical fix to `OpenedHandler#provision?`, `LabeledHandler`, and `UnlabeledHandler` if they share the same pattern.

### Proof of Concept
```ruby
test "does NOT unarchive/provision when review_stacks_enabled is false, even with allow_with_label + label present" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # Binding under test: review_stacks_enabled(false) should equal the gate applied
  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Running this against the current implementation fails (stack is unarchived and re-queued for provisioning) because `unarchive?` short-circuits through the `allow_with_label?` disjunct without consulting `review_stacks_enabled`, confirming the vulnerability.
