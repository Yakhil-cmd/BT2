### Title
`Shipit::Api::CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, allowing a stack-scoped token to read any stack's status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stacks` scopes lookups to `current_api_client.stack_id` when the authenticated `ApiClient` is bound to a specific stack [1](#0-0) , and every other API controller (e.g. `Api::StacksController#stack`) correctly resolves via `stacks.from_param!` [2](#0-1) . `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing that scope [3](#0-2) . A token minted for one stack (e.g. via `CCMenuUrlController`) can therefore be replayed with a different `stack_id` in the URL to read another stack's CCMenu status.

### Finding Description
The invariant that should hold is: `current_api_client.stack_id == stack.id` whenever `current_api_client.stack_id?` is true (i.e., a stack-scoped token can only ever resolve `stack` to its own stack). This equality holds in `Api::StacksController` and generically in `BaseController#stack`, which delegates to the scoped `stacks` relation [1](#0-0) .

`Api::CCMenuController` breaks this: it defines its own `stack` private method as `Stack.from_param!(params[:stack_id])`, an unscoped, engine-wide lookup [3](#0-2) , shadowing the safe implementation inherited from `BaseController`. The only check performed before `show` runs is the permission check `require_permission :read, :stack` [4](#0-3) , which only verifies that the `ApiClient#permissions` array contains `read:stack` via `check_permissions!` [5](#0-4)  — it never compares `current_api_client.stack_id` to the requested `stack.id`.

Attacker flow:
1. Any authenticated Shipit user (even one with access to only their own stack) can call `GET /:stack_id/ccmenu.xml` via `CCMenuUrlController#fetch`, which lazily creates (or reuses) a generic `ApiClient` named `'CCMenu Client'` scoped to `permissions: %w[read:stack]` for that user, with no `stack` assignment restricting it [6](#0-5) , and returns a signed `token` (`ApiClient#authentication_token`, an `ActiveSupport::MessageVerifier`-signed decimal id) for that client [7](#0-6) .
2. Separately, or in the more direct case, an operator who creates a genuinely stack-scoped `ApiClient` (with `stack_id` set and only `read:stack` permission, intended to restrict a CI badge integration to one stack) still has that token accepted for `GET /api/stacks/<OTHER_stack_id>/ccmenu?token=<token>` because `CCMenuController#stack` never consults `current_api_client.stack_id`.
3. `ApiClient.authenticate(token)` verifies only the signature and re-derives the id via `SimpleMessageVerifier` (`find_by(id: message_verifier.verify(token).to_i)`) [8](#0-7)  — this correctly prevents tampering with the id itself, but does nothing to enforce the *stack* scope once the client record is loaded, because the controller's `stack` lookup ignores that scope entirely.
4. Result: the token holder can read the CCMenu status (latest deploy/rollback state) of any stack in the installation, not just the one the token was intended for.

This is a stack-scope authorization bypass, not a signature forgery: the `SimpleMessageVerifier`/decimal-id signing itself is sound (the id cannot be altered without invalidating the HMAC), but the controller's use of an unscoped `Stack.from_param!` instead of the scoped `stacks.from_param!` defeats the purpose of having `ApiClient#stack_id` scoping at all for this endpoint.

### Impact Explanation
An attacker holding any `read:stack`-permissioned API token (including the low-privilege, auto-provisioned "CCMenu Client" token any logged-in user can mint for a stack they can see) can enumerate/read CCMenu build status (latest deploy or rollback state, running/ended state) for arbitrary stacks across the installation, including stacks belonging to other repositories/teams they have no access to. This matches "High — unauthenticated/unauthorized read of stack state" since it is a cross-tenant read of stack task status data outside the token's intended scope. It does not by itself allow writes, deploys, or credential exfiltration, so it does not rise to Critical.

### Likelihood Explanation
Low attacker cost, fully repeatable: the attacker needs only one valid `read:stack`-scoped `ApiClient` token for any single stack (trivially self-service via `CCMenuUrlController#fetch` for any stack visible to them) and knowledge/guessing of another stack's numeric or slug id, which is enumerable since `Stack.from_param!` likely resolves by id or a predictable param. No GitHub secrets, webhook secrets, or elevated Shipit role are required — only a Shipit account with view access to at least one stack (or any operator-issued `read:stack` token).

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the scoped lookup like every other API controller: `@stack ||= stacks.from_param!(params[:stack_id])` (reusing `BaseController#stacks`, removing the override), so that `current_api_client.stack_id` scoping is enforced consistently for this endpoint too.

### Proof of Concept
minitest plan (`test/controllers/shipit/api/ccmenu_controller_test.rb`):
```ruby
test "ccmenu is rejected for a stack outside the token's scope" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocaine) # a different fixture stack

  api_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack: stack_a,
    permissions: %w[read:stack],
  )
  token = api_client.authentication_token

  # sanity: works for its own stack
  get "/api/stacks/#{stack_a.to_param}/ccmenu", params: { token: token }
  assert_response :success

  # exploit: same token used against a DIFFERENT stack must be rejected
  get "/api/stacks/#{stack_b.to_param}/ccmenu", params: { token: token }
  refute_equal 200, response.status, "token scoped to stack_a must not resolve stack_b"
  # binding under test: current_api_client.stack_id (stack_a.id) must equal
  # the resolved `stack.id`; currently stack.id == stack_b.id, violating it.
end
```
This currently fails (returns 200 with `stack_b`'s CCMenu XML) because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, confirming the vulnerability.
