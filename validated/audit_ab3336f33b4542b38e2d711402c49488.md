### Title
Quadratic CPU blow-up in AA definition validation via unbounded `_.cloneDeep(locals)` per traversed node before complexity/depth caps bound the cost - (File: aa_validation.js)

### Summary
`aa_validation.js`'s `validate()` function, reached from `validateAADefinition()`, performs an unconditional `_.cloneDeep(locals)` at *every single node* of the AA-definition JSON tree it walks (every array element and every object key), independent of whether that node contains a formula. The depth cap (`MAX_DEPTH = 100`) only bounds nesting *depth*, not the *width* of the structure or the size of `locals`, so an attacker can post a single unit containing an AA definition (or a `definition` message posting a new AA, reachable by any unpriviledged unit poster) that is wide-but-shallow and simultaneously inflates `locals` via the `getters` field, causing `O(n * size(locals))` deep-clone work before any of the existing complexity/ops/depth caps meaningfully bound it — mirroring the sqlparse `TokenList.__init__`/`str(self)` class of bug where the guarding limits are checked only after the expensive per-node materialization has already run.

Critically, **width is not bounded by `MAX_DEPTH`**: a flat array with tens of thousands of sibling elements at a single nesting level (e.g. a huge `outputs` array, a huge `messages` array wrapped in `cases`, or a large object with many keys) only increments `depth` by 1 per level regardless of how many siblings exist, yet each sibling triggers its own `_.cloneDeep(locals)` call (twice per node: once on entry to `validate`, once when constructing the child call). `locals` is populated from the AA's `getters` formula, whose size (number of functions/constants) is controlled by the attacker and only constrained by `constants.MAX_AA_STRING_LENGTH` per string and `MAX_COMPLEXITY`/`MAX_OPS` on formula complexity — not by the cost of *copying* the resulting `locals` object repeatedly.

Reachability: any unpriviledged unit poster can attach a `definition` app message defining a brand-new AA, which is validated inline during ordinary unit validation via `aa_validation.validateAADefinition`: [4](#0-3) 

This directly parallels the sqlparse advisory's root cause: a per-node/per-group operation (`str(self)` / here `_.cloneDeep(locals)`) that is `O(size of already-accumulated data)` rather than `O(1)`, executed once per tree node, so that a moderately sized attacker-controlled input (bounded individual string/array/object sizes) produces `O(n * L)` work — `n` tree nodes times `L` locals size — well before the `MAX_DEPTH`, `MAX_COMPLEXITY`, or `MAX_OPS` guards can reject it, because none of those guards account for the width of the JSON tree or the cost of repeatedly cloning `locals`.

### Impact Explanation
This is CPU-only amplification during unit validation, not a wallet/AA-fund-loss or double-spend primitive by itself. Excessive CPU consumption during `validateAADefinition` (invoked by every full node validating the unit, including on definitions embedded as inline `definition` app payloads) can degrade or stall validation throughput network-wide for units carrying such payloads, since `validation.js` calls this synchronously as part of ordinary unit validation before consensus decisions are made. Given the strict validation rubric (accept only concrete spending/double-spend/inflation/AA-fund-loss/freezing/stability-disagreement/confirmation-DoS outcomes), this analog's concrete effect is a node-validation-throughput degradation (a network struggling to validate/confirm new units carrying maliciously crafted AA definitions), rather than a fund-loss or consensus-divergence bug.

### Likelihood Explanation
Medium: the payload is fully attacker-constructible in a single unit (a `definition` message with a crafted `getters` formula plus a wide `messages`/`payload` tree), does not require any privileged role, and the guarding limits (`MAX_DEPTH=100`, `MAX_COMPLEXITY`, `MAX_OPS`) do not bound the width of the structure or the cost of `_.cloneDeep(locals)`, so the vulnerable code path is trivially reachable by any poster of a unit defining an AA.

### Recommendation
Avoid unconditional `_.cloneDeep(locals)` per tree node in `validate()`. Only clone `locals` when a formula assignment actually mutates it (e.g. right before/after `validateFormula` calls that can add bindings), and pass the same reference through pure structural recursion (arrays/objects) when no mutation occurs at that node. Additionally, add an explicit cap on the total number of nodes/keys/array-elements visited during `validate()` (analogous to `MAX_GROUPING_TOKENS` in the sqlparse fix), independent of depth, so wide-but-shallow AA definitions cannot bypass `MAX_DEPTH`.

### Proof of Concept
Conceptual construction (not executed, derived from code reading):
1. Craft an AA definition with a `getters` field defining many local functions/constants (bounded per-string by `MAX_AA_STRING_LENGTH`, but the aggregate `locals` object can still be made large), keeping `complexity == 0` as required by `validateDefinition` after the getters pass.
2. In the AA's `messages`/`payload` tree, include a very wide but shallow structure (e.g., a payload object or array with tens of thousands of keys/elements) so that `depth` stays well under `MAX_DEPTH = 100` while `count` (and thus the number of `_.cloneDeep(locals)` calls) scales with the width.
3. Post this AA definition via a `definition` app message in a single unit as an unprivileged user; `validation.js`'s `validateInlinePayload` invokes `aa_validation.validateAADefinition` on it during ordinary unit validation on every full node.
4. Because `validate()` deep-clones `locals` on every one of the tens-of-thousands of nodes, CPU cost scales with `n * size(locals)`, producing outsized validation latency compared to the unit's serialized size, before any existing cap (`MAX_DEPTH`, `MAX_COMPLEXITY`, `MAX_OPS`) rejects it.
