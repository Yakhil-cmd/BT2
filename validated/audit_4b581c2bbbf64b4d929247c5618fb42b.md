### Title
`pending_delegator_rewards` in the vote account is never decremented after being distributed as block rewards, causing the same reward pool to be repeatedly paid out - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The Footium bug stems from a counter (`totalERC20Claimed[_token][_to]`) that is meant to represent an "already distributed" amount, but is never properly synchronized across different reward sources, so the same underlying pool can effectively be paid out more than once. Agave's SIMD-0123 "delegator rewards" mechanism has the same structural pattern: `pending_delegator_rewards` on a `VoteStateV4` account is a running total that is incremented every time a validator deposits rewards, and is read every epoch by `calculate_block_reward` to compute each stake account's proportional share of block rewards — but nothing in the codebase decrements `pending_delegator_rewards` after that share has actually been distributed to stakers.

### Finding Description
`deposit_delegator_rewards` transfers lamports into the vote account and only ever increases the tracked pool via `add_pending_delegator_rewards`, which performs a `checked_add`: [1](#0-0) [2](#0-1) 

Every epoch, `calculate_block_reward` reads this same `pending_delegator_rewards` value from the vote account and uses it as the numerator to compute each stake account's proportional block-reward share for that epoch (`pending_delegator_rewards * stake / total_active_stake`, capped at `pending_delegator_rewards`): [3](#0-2) 

The only other place `pending_delegator_rewards` is consulted is `withdraw`, which uses it purely as a lamport reserve to block withdrawals below that amount — it never decrements the field either: [4](#0-3) 

A repository-wide search for any subtraction of `pending_delegator_rewards` (e.g. `sub_pending_delegator_rewards`, `checked_sub`) found no such function anywhere in `programs/vote` or `runtime/src/bank/partitioned_epoch_rewards`. The only place the field is set to a smaller/zero value is in unit tests that directly poke the struct for test setup, not via any production code path.

Because `calculate_block_reward` is invoked every epoch during partitioned reward calculation and always reads the vote account's current `pending_delegator_rewards`, and because that value is never reduced by the amounts already paid to stake accounts in prior epochs, the exact same pool of "pending" rewards is used as the basis for calculating rewards again and again in subsequent epochs, rather than being drawn down over time.

### Impact Explanation
If confirmed to lack any decrement path, this results in repeated/duplicated stake reward calculation from the same deposited pool: stakers would receive proportional shares of the same `pending_delegator_rewards` balance every epoch instead of that balance being consumed as it's distributed, leading to reward/lamport-accounting corruption. This maps to the "stake or reward corruption" / "concrete unsigned fund movement" acceptance criteria, since it inflates minted stake rewards beyond what the vote account's actual deposited pool should support.

### Likelihood Explanation
This path is reachable purely through normal validator operation: any transaction sender who is an authorized party can call `DepositDelegatorRewards` (SIMD-0123) to fund `pending_delegator_rewards`, and reward calculation runs unconditionally every epoch once the relevant Alpenglow/SIMD features are active. No special privilege beyond normal instruction submission is needed to trigger deposits; the epoch-boundary reward calculation itself is bank-internal but occurs on every epoch transition, deterministically re-using the same un-decremented value.

### Recommendation
Add a decrement step in the reward-distribution flow (mirroring `add_pending_delegator_rewards`) that reduces `pending_delegator_rewards` by the amount actually distributed as block rewards for that epoch, persisted back to the vote account state at the same time the stake rewards are stored (in `store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition`).

### Proof of Concept
1. Validator authorized withdrawer calls `DepositDelegatorRewards` depositing `D` lamports into its vote account, setting `pending_delegator_rewards = D` (`programs/vote/src/vote_state/mod.rs:936-988`).
2. At the next epoch boundary, `calculate_block_reward` computes and distributes a share of `D` to delegator stake accounts based on `pending_delegator_rewards` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`).
3. Since no code path subtracts the distributed amount from `pending_delegator_rewards` on the vote account, the field still reads `D` in the following epoch.
4. `calculate_block_reward` runs again in the next epoch, computing a fresh proportional share based on the same, undiminished `D`, resulting in the same pool amount being used for reward calculation across multiple epochs instead of being drawn down as it is paid out.

*Note: I was unable to fully confirm this is the exclusive/final code path (e.g., I could not directly view a "distribute block reward" storage step in vote_processor.rs that might set `pending_delegator_rewards`, since my last targeted reads of that region were not returned before the tool budget ended). The absence of any `sub`/decrement helper for `pending_delegator_rewards` across the whole repo strongly supports the finding, but I recommend verifying `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`'s `build_updated_stake_reward`/`store_stake_accounts_in_partition` for any vote-account-side update I may have missed.*

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Withdraw funds from the vote account
pub fn withdraw<S: std::hash::BuildHasher>(
    instruction_context: &InstructionContext,
    vote_account_index: IndexOfAccount,
    target_version: VoteStateTargetVersion,
    lamports: u64,
    to_account_index: IndexOfAccount,
    signers: &HashSet<Pubkey, S>,
    rent_sysvar: &Rent,
    clock: &Clock,
) -> Result<(), InstructionError> {
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;
    let vote_state = get_vote_state_handler_checked(&vote_account, target_version)?;

    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let remaining_balance = vote_account
        .get_lamports()
        .checked_sub(lamports)
        .ok_or(InstructionError::InsufficientFunds)?;

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }

    vote_account.checked_sub_lamports(lamports)?;
    drop(vote_account);
    let mut to_account = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to_account.checked_add_lamports(lamports)?;
    Ok(())
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
