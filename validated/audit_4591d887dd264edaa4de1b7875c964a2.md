### Title
Webhook signature verification keys off attacker-controlled `repository.owner.login`/`organization.login` instead of the repository actually acted upon, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using a field taken directly from the untrusted JSON payload (`repository.owner.login` or `organization.login`), but the handlers that actually mutate state (`PushHandler`, `StatusHandler`, `MembershipHandler`, etc.) act on a *different* payload field (`repository.full_name`, or in `StatusHandler`'s case, no repository scoping at all — only `sha`). There is no check binding "the organization whose secret validated this signature" to "the repository/stack that gets written to." An attacker who legitimately controls one Shipit-registered GitHub organization (and therefore knows that organization's own `webhook_secret`, which they configured when creating their GitHub App) can forge a payload that authenticates as their own org but names a different org's repository, causing writes to stacks they don't own. This mirrors the reported smart-contract bug class: `_executeTransaction` binds an identity (`signerAddress`) that is never actually checked by the downstream authorization logic (`onlyOwner` checks `msg.sender` instead) — here, the webhook pipeline binds a validated identity (the org whose secret matched) that is never checked against the identity actually written to (the repository named deeper in the same untrusted payload).

### Finding Description
`verify_signature` in the webhooks controller does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read straight from the JSON body — the same body whose signature is being checked — before the signature is validated. `Shipit.github(organization: repository_owner)` looks up a per-organization `webhook_secret` from `secrets.github`, supporting the documented multi-org configuration (`secrets.github.orgA.webhook_secret`, `secrets.github.orgB.webhook_secret`, etc.) as shown in `config/secrets.development.example.yml`:
```
github:
  somegithuborg:
    webhook_secret: ...
  someothergithuborg:
    webhook_secret: ...
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` only proves the raw body was HMAC-signed with the secret belonging to whatever organization `repository_owner` names — it proves nothing about which repository the rest of the payload describes:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Once the signature check passes, `Handler#stacks`/`#repository_name` re-derives the target repository from a *different* payload field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Nothing enforces `repository.full_name.split('/').first == repository_owner`. Because the attacker fully controls the JSON body (they only need a valid HMAC over their own chosen bytes, computed with their own org's secret, which they know), they can set `repository.owner.login` to their own org (so `verify_signature` picks their own org's secret and the HMAC checks out) while setting `repository.full_name` to `"other-org/other-repo"` (a stack belonging to a different organization hosted on the same Shipit instance).

This is exploitable across several handlers:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for any stack matching the forged branch/repo, letting the attacker drive GitHub sync for someone else's stack. [5](#0-4) 
- `StatusHandler#process` is even less scoped — it looks up commits by `sha` alone, with **no repository check whatsoever**, so a forged `status` event signed with the attacker's own org secret can write a fabricated CI status (`state`, `context`, `target_url`) onto any commit row in the entire Shipit database that happens to share that SHA, regardless of which org/repo it belongs to: [6](#0-5) 
- `MembershipHandler#process` creates/updates `Team` and `Membership` records keyed by `organization.login`/`team.id` from the same untrusted, only-partially-verified payload, letting an attacker add or remove members from a team object under a different `organization` name than the one whose secret validated the request. [7](#0-6) 

### Impact Explanation
This breaks the equality that should hold: `organization authenticated by verify_signature == organization/repository written to by the handler`. Concretely, an attacker who is a legitimate admin of Organization A (with their own GitHub App + `webhook_secret` registered on the shared Shipit instance, per the documented multi-org setup) can forge signed webhooks that write to Organization B's stacks:
- Trigger unwanted `GithubSyncJob`/deploy-pipeline state changes on another org's stack (`PushHandler`).
- Inject arbitrary/fake CI status onto another org's commits by SHA collision or SHA guessing, which can influence merge/deploy-readiness logic elsewhere in Shipit that trusts `Status` records (`StatusHandler`).
- Manipulate team/membership records tied to another organization's name (`MembershipHandler`), which feeds into `Shipit.github_teams` authorization checks used by `current_user.authorized?`.

This falls under the "High" bucket: escalation into `Shipit.github_teams` authorization and cross-organization interference with stack/task state, with a credible path toward unauthorized deploy influence, without needing any Shipit session, API token, or the target org's own secret — only knowledge of one's own org's `webhook_secret`, which every multi-tenant participant necessarily has.

### Likelihood Explanation
This requires the deployment to be configured with the documented multi-organization `secrets.github` layout (more than one org registered on the same Shipit instance) and requires the attacker to be a legitimate admin of at least one of those orgs — a normal, expected, unprivileged-relative-to-other-tenants position in a multi-tenant Shipit deployment. No social engineering, GitHub App private key, or target-org credentials are needed; the attacker only signs a payload with their own org's `webhook_secret` and points the embedded `repository.full_name`/`organization.login` at a different tenant.

### Recommendation
After computing `repository_owner` and verifying the signature, re-derive the repository/organization used by the handler from the *same* field that was authenticated (or require it to match). Concretely:
- Verify that `payload.dig('repository', 'full_name')` (used by `Handler#repository_name`) is prefixed by `repository_owner`/`organization.login` before dispatching to handlers, rejecting the webhook otherwise.
- Alternatively, pass the already-verified organization identity down to handlers and require every DB lookup (`Repository.from_github_repo_name`, `Team.find_or_create_by!`, `Commit.where(sha:)`) to be additionally scoped/cross-checked against that verified organization.
- For `StatusHandler` specifically, scope the `Commit` lookup by the commit's owning stack's repository/organization rather than by `sha` alone.

### Proof of Concept
1. Deployment configures two orgs in `secrets.github`: `orgA` (attacker-controlled) and `orgB` (victim), each with their own GitHub App/`webhook_secret`, per `config/secrets.development.example.yml`.
2. Attacker, as admin of `orgA`'s GitHub App, knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner == "orgA"`, loads `orgA`'s `GitHubApp`, and the HMAC validates successfully (attacker knows `orgA`'s secret) — [8](#0-7) .
6. `PushHandler#process` resolves `repository_name` from `repository.full_name` = `"orgB/victim-repo"`, finds `orgB`'s stacks, and calls `stack.sync_github` on them — [5](#0-4) , [4](#0-3)  — despite the request only ever being authenticated against `orgA`'s secret.
