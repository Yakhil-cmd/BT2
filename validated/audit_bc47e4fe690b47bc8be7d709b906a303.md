### Title
Independent per-recipient rounding in `earned_headers_commission_recipients` distribution allows total headers-commission payout to diverge from the paid-in amount - (File: `headers_commission.js`)

### Summary
`headers_commission.js` distributes the headers commission earned by a winning child unit among the addresses listed in that unit's `earned_headers_commission_recipients` array. The validation layer only guarantees that the *percentage shares* declared by the (unprivileged) unit author sum to exactly 100, but the actual byte amounts paid to each recipient are computed by rounding each recipient's share independently, rather than deriving the last recipient's amount as the remainder. This is the same rounding-error class as the referenced PartyDAO `votingPower` bug: individual rounded parts do not necessarily sum back to the total.

### Finding Description
Any unit author can attach an `earned_headers_commission_recipients` array to a multi-authored unit (or a single-authored unit that wants to redirect its commission), consisting of `{address, earned_headers_commission_share}` entries. Validation (`validation.js`, `validateHeadersCommissionRecipients`) enforces: [1](#0-0) 
that `earned_headers_commission_share` values are positive integers, addresses are sorted/valid, and the sum equals exactly 100 - but it does **not** constrain the number of recipients, nor tie recipients to actual unit authors.

When the unit later wins headers commission, the payout for each recipient is computed independently as: [2](#0-1) 
and, for the "faster"/verification path: [3](#0-2) 
`Math.round(full_amount * share / 100.0)` is applied separately to every recipient's share. Because `full_amount * share_i / 100` is not necessarily an integer for each `i`, each individual rounding can go up or down by up to 0.5, and — critically — there is no tracking of a running/consumed amount and no "last recipient gets the remainder" logic (unlike, e.g., `test/samples/send_all.oscript`, which explicitly implements "last output gets all remaining coins" as the correct pattern: [4](#0-3) ).

These per-recipient amounts are summed into `headers_commission_outputs`, which become new spendable inputs of base currency: [5](#0-4) 

By choosing shares that sum to exactly 100 but that individually produce `x.5`-type fractions against a chosen `headers_commission` (`full_amount`), and by using enough recipients (the recipients array size is not bounded independently of message/unit size limits, and can list arbitrary addresses not required to be unit authors), the accumulated rounding bias across all recipients can be made systematically positive, so the sum of the individually rounded payouts exceeds `full_amount`.

### Impact Explanation
`headers_commission_outputs` become spendable base-currency inputs (`type: "headers_commission"`), i.e. real bytes that can be spent by the recipient addresses. If the sum of rounded per-recipient payouts systematically exceeds the actual `headers_commission` paid by the payer unit, the protocol effectively mints extra base-currency out of thin air with each winning unit that uses a crafted `earned_headers_commission_recipients` list - a supply-inflation bug in the base asset, reachable by any ordinary unit poster (no special privilege, no witness/hub role required). Even absent inflation, negative bias would permanently strand/lose commission dust, and inconsistent rounding could also cause different nodes computing the same distribution to potentially disagree if any non-deterministic factor were introduced (though the arithmetic itself is deterministic across full nodes, so the primary risk here is per-unit inflation of aggregate `headers_commission_outputs`, not consensus divergence).

### Likelihood Explanation
Reachable by a completely unprivileged unit author: any user can multi-author a unit (or single-author while intentionally opting into an `earned_headers_commission_recipients` list) and craft the shares to bias cumulative rounding. Because `Math.round` (round-half-away-from-zero/round-half-up in JS) is used per-entry, an attacker fully controls the shares and thus fully controls the direction/magnitude of the rounding bias, subject only to unit-size limits capping how many recipients (and thus how much cumulative rounding error) can be packed into a single unit. This makes exploitation straightforward and repeatable across many winning units to accumulate inflation over time.

### Recommendation
Do not round each recipient's share independently. Instead, maintain a running total of already-distributed amount and compute each recipient's payout as `Math.round(full_amount * cumulative_share_up_to_and_including_this_recipient / 100.0) - amount_already_distributed`, giving the last recipient (in a fixed, deterministic order) the exact remainder `full_amount - sum_of_previous_amounts`. This guarantees the individual payouts always sum exactly to `full_amount`, eliminating any possibility of inflation or fund loss regardless of how shares are split among recipients. Apply the same fix in both the SQL path (MySQL `ROUND(...)`) and the in-memory JS path in `headers_commission.js`, keeping the two paths consistent (the code already cross-checks in-memory vs SQL results and would need updated logic in both).

### Proof of Concept
1. Craft a multi-authored unit (or a unit that carries `earned_headers_commission_recipients`) with, e.g., 20 recipient addresses (need not all be authors) whose `earned_headers_commission_share` values sum to exactly 100 but are individually chosen (e.g. many entries at values like 4.999→5 rounding boundaries relative to an anticipated `headers_commission`/`full_amount`) such that `Math.round(full_amount * share_i/100)` rounds up for a majority of entries.
2. Get this unit accepted as the winning child (`getWinnerInfo`) for a parent unit's headers commission, per the normal DAG/stability process in `calcHeadersCommissions` (`headers_commission.js:144-217`).
3. Observe that `SUM(amount)` inserted into `headers_commission_outputs` for that main_chain_index exceeds the `headers_commission` (`full_amount`) actually earned/paid by the parent unit — i.e., more spendable bytes are created than were paid in, confirmed by cross-referencing `headers_commission_outputs` totals against the source `units.headers_commission` value for the corresponding payer unit.
4. Repeat across multiple winning units to accumulate inflation of the base asset's circulating supply beyond `constants.TOTAL_WHITEBYTES`.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
