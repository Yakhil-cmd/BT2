### Title
Stack-scoped ApiClient can read the CI status of any other stack via `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` enforces that an `ApiClient` bound to a single stack (`stack_id`) can only act on that stack, by resolving the target `Stack` through the scoped `stacks` relation. `Api::CCMenuController` breaks this binding: it overrides `stack` to resolve directly through the unscoped `Stack.from_param!` class method, never checking `current_api_client.stack_id`.

### Finding Description
`Api::BaseController` defines the trust binding between an `ApiClient` and the stacks it is allowed to touch: [1](#0-0) 

`stacks` restricts the visible/actionable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and every other API controller (e.g. `Api::StacksController#stack`, `Api::HooksController#hooks`) resolves its target stack through this scoped `stacks` relation.

`Api::CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely: [2](#0-1) 

It calls the bare class method `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`. The `require_permission :read, :stack` before_action only checks that the token carries the `read:stack` string permission — it does not, and cannot, verify which specific stack the token is scoped to: [3](#0-2) 

So the equality the design intends is: `current_api_client.stack_id == stack.id` (when the client is scoped). `CCMenuController` never evaluates that equality — it substitutes `params[:stack_id]` unconditionally as the resolved stack, for any client holding `read:stack`.

This is directly analogous to the `Reserve.sol` bug class: a binding (`DAO` address vs. `msg.sender`, here `ApiClient.stack_id` vs. requested `stack_id`) is checked correctly in most code paths but silently skipped in one code path that was supposed to inherit the same guarantee.

### Impact Explanation
Any Shipit user can self-service create a stack-scoped, read-only `ApiClient` for exactly one stack via `CCMenuUrlController#fetch` (or the `ApiClientsController` UI), which is the documented mechanism for scoping down automation credentials to a single project: [4](#0-3) 

Using that legitimately-scoped, least-privilege token, the holder can query `GET /api/stacks/:stack_id/ccmenu` for **any other stack in the Shipit instance** — not just the one their token was scoped to — and read that stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, activity), as confirmed by the endpoint's own tests exercising `@stack.to_param` freely: [5](#0-4) 

This is an unauthorized cross-stack read of stack/deploy state via a token whose entire purpose is to be restricted to one stack — matching the "unauthenticated/unauthorized read of stack state" High-impact category, achieved purely by a credential that is legitimately possessed but scoped to a different, unrelated stack.

### Likelihood Explanation
High. No secret material, GitHub App keys, or session hijacking is required — only a token the requester already legitimately owns (e.g., a CCMenu token for their own stack), plus knowledge of another stack's `owner/repo/environment` identifier, which is often guessable/public (repo names, common environment names like `production`/`staging`). The request is a single unauthenticated-beyond-basic-auth GET.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped collection, consistent with the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override that bypasses `current_api_client.stack_id` scoping, and add a regression test asserting a stack-scoped `ApiClient` receives 404/403 when requesting `/ccmenu` for a stack outside its `stack_id`.

### Proof of Concept
1. As an authenticated Shipit user with access to `stack-a`, visit its CCMenu URL page; `CCMenuUrlController#fetch` creates (or reuses) a global `ApiClient` named "CCMenu Client" with `permissions: ['read:stack']` and no `stack_id`, OR use/administer an explicitly stack-scoped client (e.g. the `here_come_the_walrus` fixture pattern: `stack: shipit`, `permissions: ['read:stack']`) intended to only see `stack-a`.
2. Note the returned `authentication_token`.
3. Issue: `GET /api/stacks/other-owner/other-repo/production/ccmenu?token=<token>` for `stack-b`, a stack the token was never scoped/authorized for.
4. Observe `200 OK` with the CCMenu XML payload for `stack-b` (`lastBuildStatus`, `lastBuildLabel`, etc.), confirmed by `Api::CCMenuController#stack` resolving via unscoped `Stack.from_param!` rather than the client-scoped `stacks` relation used everywhere else in `Api::BaseController`.

```ruby
# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
```
