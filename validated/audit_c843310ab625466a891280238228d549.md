## Title
Immutable `pool_creator` address permanently locks accrued creator fees if it becomes frozen/blocklisted (Token‑2022) - (File: `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`, `programs/cp-swap/src/instructions/initialize.rs`, `programs/cp-swap/src/states/pool.rs`)

### Summary
`pool_creator` is recorded once at pool creation and can never be changed afterwards. Every swap accumulates `creator_fees_token_0`/`creator_fees_token_1` in the pool vaults, and the only two instructions capable of paying them out (`collect_creator_fee` and `collect_creator_fee_permissionless`) hard-code the destination to that same immutable `pool_creator` address, with no admin override, no alternate beneficiary, and no expiry/reclaim path. If that address later becomes untransferable (e.g. a Token‑2022 account frozen by a mint's freeze authority, or blocked under a `PermanentDelegate`/blocklist-style extension), the accrued creator fees become permanently stuck in the vault, mirroring the bond `FixedStrikeOptionTeller` bug class where a fixed, unblockable-at-creation-time receiver later becomes unable to receive funds.

### Finding Description
`PoolState::initialize` writes `pool_creator` from the `creator` account supplied at pool creation and this field is never updated by any other instruction: [1](#0-0) 

There is no admin instruction that can update `pool_creator` — the admin module only exposes config/status/fee-collection instructions, none of which touch `pool_creator`: [2](#0-1) 

Both fee-claim paths derive the payout destination directly from this immutable field. `collect_creator_fee` requires the `creator` to be the signer matching `pool_state.pool_creator`: [3](#0-2) 

`collect_creator_fee_permissionless` is callable by anyone, but still transfers exclusively to an ATA owned by `pool_creator`: [4](#0-3) [5](#0-4) 

The transfer call in both instructions has no fallback recipient if it reverts: [6](#0-5) 

Since `initialize_with_permission` lets the transaction `payer` set an arbitrary `creator` (unchecked account, distinct from the signer), an attacker can also deliberately target a `pool_creator` whose associated token account they know will be frozen/blocklisted later by the token's freeze authority: [7](#0-6) 

### Impact Explanation
Once the `pool_creator`'s token account for `vault_0_mint`/`vault_1_mint` cannot receive tokens (frozen by the mint's freeze authority, or a Token‑2022 mint extension such as default-account-state/permanent-delegate style restrictions), `transfer_checked` inside `transfer_from_pool_vault_to_user` reverts unconditionally. `creator_fees_token_0`/`creator_fees_token_1` are only zeroed after a successful transfer, so the fees remain permanently accounted for in the vault with no code path to redirect or reclaim them — a permanent freeze of accrued creator-fee funds, analogous to the Sherlock M-3 finding where a fixed, later-blocked receiver locks the option minter's funds.

### Likelihood Explanation
Pool creation via `initialize`/`initialize_with_permission` is permissionless and the `pool_creator` field is fixed forever at that point with no update mechanism, so any subsequent freeze/blocklist event on that specific token account (a realistic occurrence for regulated stablecoins like USDC/USDT on Token‑2022, or a mint deliberately configured with a freeze authority) is enough to trigger the permanent lock — no cooperation from the protocol admin is required, and no recovery instruction exists.

### Recommendation
Add a mechanism to change `pool_creator` (e.g., an admin- or self-initiated `update_pool_creator` instruction) or implement a pull/escrow-based creator-fee claim that lets a substitute address or the AMM admin redirect/reclaim stuck creator fees after a timeout, mirroring the "expiry + reclaim" recommendation from the referenced report.

### Proof of Concept
1. Call `initialize` (or `initialize_with_permission`) to create a pool where `token_0_mint`/`token_1_mint` is a Token‑2022 mint with a freeze authority, setting `creator` to an address the caller controls.
2. Perform swaps so `creator_fees_token_0`/`creator_fees_token_1` accrue in the vaults (see accounting in `PoolState::vault_amount_without_fee`): [8](#0-7) 
3. Freeze the `pool_creator`'s associated token account via the mint's freeze authority (external to this program, but a standard SPL Token‑2022 capability).
4. Call `collect_creator_fee_permissionless`; the `transfer_from_pool_vault_to_user` CPI reverts due to the frozen destination account, and `creator_fees_token_0`/`creator_fees_token_1` remain non-zero and unrecoverable indefinitely, since no other instruction can move or reset them.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
