### Title
Unauthenticated `membership` webhook lets any caller grant themselves `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` treats the webhook as valid whenever `webhook_secret` is not configured, since `GitHubApp#verify_webhook_signature` short-circuits to `true` in that case. `webhook_secret` is documented as optional, so this is a supported deployment configuration, not a misconfiguration outside scope. When the secret is unset, `MembershipHandler#process` blindly trusts the attacker-supplied `team.id` (the GitHub numeric team id) to locate an existing `Team` record and adds an attacker-chosen `member.login` to it via `Team#add_member`, without any check that the caller is actually authorized to modify that team's membership. Because `Shipit.github_teams` (used by `User#authorized?` to gate access to the whole app) is resolved purely by `Team` id, this lets an unauthenticated caller self-grant Shipit access/authorization.

### Finding Description
The bug class mirrors the H-02 pattern: a security-relevant side effect (adding a member to an authorization-bearing `Team`) is performed based on a field (`team.id` / `member.login`) that is never actually bound to a verified trust anchor when the optional `webhook_secret` is unset.

- `WebhooksController#verify_signature` calls `github_app.verify_webhook_signature(...)` and only `head(422)` if it explicitly returns `false`. [1](#0-0) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: `return true unless webhook_secret`. [2](#0-1) 
- `webhook_secret` is explicitly documented as optional in the setup guide ("Webhook secret (optional)"), confirming this is a supported, in-scope configuration. [3](#0-2) 
- Once past `verify_signature`, `WebhooksController#create` dispatches the raw parsed JSON to registered handlers with zero further authentication: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 
- `MembershipHandler#process` finds/creates a `Team` purely by the payload's numeric `github_id`, and unconditionally executes `team.add_member(member)` for `action == 'added'`, where `member` is created/fetched purely from the payload's `member.login`. [5](#0-4) 
- `Team#add_member` performs no additional authorization check; it just appends the member. [6](#0-5) 
- Application-wide authorization is gated solely on `Team` membership: `authorized? = Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`, and `Shipit.github_teams` resolves the configured team handles (e.g. `MyOrg/developers`) into these same `Team` records. [7](#0-6) [8](#0-7) 
- The membership test confirms `find_or_create_by_login!`/member creation is driven purely by the payload's `member.login`, with GitHub API used only to enrich the record (fetch the real profile of that login), not to prove the *caller's* identity or intent. [9](#0-8) 

The equality that should hold — "the authenticated request source == the entity permitted to mutate `Team` membership that feeds `Shipit.github_teams` authorization" — is not enforced whenever `webhook_secret` is unset. The `team.id`/`member.login`/`action` fields are acted on but covered by no verified signature in that configuration.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization (explicitly listed High-impact criterion). An attacker who knows (a) the Shipit instance's `/webhooks` endpoint and (b) the numeric GitHub `team.id` of a team referenced in `Shipit.github_teams` (discoverable via the public GitHub API for any org whose teams are visible, or via other reconnaissance) can:
1. POST an unsigned `membership` event with `action: 'added'`, `team: { id: <target_team_github_id>, ... }`, `organization: { login: <any> }`, `member: { login: <attacker's real GitHub login> }`.
2. Shipit creates/looks up that `User` by login (fetching their real GitHub profile via Shipit's own app credentials) and adds them to the authorization-bearing `Team`.
3. The attacker then completes the normal GitHub OAuth login flow with their real account; `sign_in_github` matches the same `User` record (by `github_id`), and `authorized?` now returns `true`, granting them full access to the Shipit instance (stacks, deploys, secrets exposed in the UI, etc.).

### Likelihood Explanation
The only precondition is that the Shipit deployment leaves `github.webhook_secret` unset — an explicitly documented, supported, optional configuration — and that the attacker knows a target team's numeric GitHub id, which is not treated as a secret by GitHub. No Shipit session, API token, or repository write access is required, satisfying the "unprivileged attacker" constraint.

### Recommendation
- Do not allow `verify_webhook_signature` to pass when `webhook_secret` is unset for security-sensitive events (at minimum `membership`); require a configured secret before processing events that affect authorization.
- In `MembershipHandler`, verify that the team identified by `params.team.id` actually belongs to the `params.organization.login` that authenticated the request (or otherwise cross-check the two), rather than trusting the numeric id in isolation.
- Consider re-validating `Shipit.github_teams` membership against GitHub directly (as `Team#refresh_members!` already does) rather than trusting webhook-driven mutations for authorization-critical `Team` records.

### Proof of Concept
1. Deploy Shipit with `github.webhook_secret` left blank (a documented, supported option) and `github.oauth.teams: ["MyOrg/developers"]`.
2. Determine the numeric GitHub `id` of the `developers` team in `MyOrg` (e.g. via `GET https://api.github.com/orgs/MyOrg/teams`, visible for public teams/orgs).
3. Send (no signature header needed):
```
POST /webhooks
X-Github-Event: membership

{
  "action": "added",
  "team": { "id": 4242, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/4242" },
  "organization": { "login": "MyOrg" },
  "member": { "login": "attacker-github-login" }
}
```
4. Shipit's `MembershipHandler` finds the existing `developers` `Team` by `github_id: 4242` and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
5. Attacker logs into Shipit via the normal `/github/auth/github` OAuth flow using their real `attacker-github-login` GitHub account; `authorized?` now returns `true`, granting full Shipit access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
