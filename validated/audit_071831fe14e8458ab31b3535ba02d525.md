### Title
Unbounded in-memory stdout/stderr capture in `cmd.Runner.Run` allows repo-content-driven memory exhaustion via exechook - ([File: pkg/cmd/cmd.go])

### Finding Description
`Exechook.Do` calls `h.cmdrunner.Run(ctx, worktreePath, env, h.command, h.args...)` [1](#0-0)  which delegates to `runWithStdin` in `pkg/cmd/cmd.go`. That function attaches `cmd.Stdout` and `cmd.Stderr` directly to `bytes.Buffer` objects with no size cap, no streaming, and no truncation: [2](#0-1) . The full output is accumulated in memory before being returned as strings, and is only trimmed of whitespace afterward [3](#0-2) .

Since `--exechook-command` is a documented, supported flag whose command is executed against the freshly-synced worktree (`worktreePath := h.getWorktree(hash)`) [4](#0-3) , any exechook script whose output size scales with the content of the repository (e.g., a script that greps, cats, or archives repo files as part of its normal logging/verification behavior) will have that entire output buffered in the git-sync process's memory. An attacker who controls repo content (pushes a very large tracked file/blob) can therefore drive the size of that buffered output arbitrarily high purely by growing repository content, without needing any special flags, secrets, or Pod access beyond push access to the synced ref.

This is a genuine implementation gap in git-sync's own `cmd.Runner`, not merely an exechook script misconfiguration — the Runner API provides no bounded/streaming alternative for callers, so any content-length-proportional command output is captured in full regardless of size.

### Impact Explanation
If a configured exechook command's output size is a function of repository content, an attacker who can push large content into the tracked ref can cause the git-sync process's memory usage to grow without bound, leading to an OOM kill of the container. This matches the "persistent stall/exhaustion" impact class (resource exhaustion / denial of service against the sync process), since the container will be killed and restarted by the kubelet, disrupting the sidecar's availability. The scoped claim that readiness may have already been marked true before the crash is plausible given hooks run after checkout, but I could not fully confirm the exact ordering of `setRepoReady`/readiness-marking relative to hook execution within the available context — this part remains unverified due to incomplete visibility into `main.go`'s sync loop ordering in the index.

### Likelihood Explanation
Exploitability requires the operator to have configured `--exechook-command` (or `--exechook-command`/`--exechook-args`) pointing at a script whose stdout/stderr size scales with repository content — this is a real, commonly-used pattern (e.g., verification/build scripts), not a contrived misconfiguration solely designed to be vulnerable. The core defect (unbounded `bytes.Buffer` capture with no cap) is unconditional in `cmd.Runner.Run`/`RunWithStdin` and applies to every invocation, including git-sync's own internal git command invocations, making the underlying design weakness broadly reachable whenever any invoked command emits large output tied to repo size.

### Recommendation
Bound the amount of stdout/stderr captured in `runWithStdin` (e.g., wrap `outbuf`/`errbuf` with a size-limited writer that truncates and marks truncation once a configurable cap, such as a few MB, is reached), or stream output to the log instead of fully buffering it in memory. Apply the same limit uniformly to `Run` and `RunWithStdin` so both exechook and internal git invocations are protected.

### Proof of Concept
Add a unit test in `pkg/cmd` that invokes `Runner.Run` with a shell command producing output whose size is parameterized by an input file (e.g., `sh -c "cat bigfile"` where `bigfile` is grown to hundreds of MB), and assert that either: (1) the returned stdout is capped at a fixed maximum length regardless of input size, or (2) memory allocated during `Run` does not scale linearly (unbounded) with the input file size. Example:
```go
func TestRunOutputIsBounded(t *testing.T) {
    dir := t.TempDir()
    big := filepath.Join(dir, "big.txt")
    os.WriteFile(big, bytes.Repeat([]byte("A"), 200*1024*1024), 0644) // 200MB
    r := NewRunner(testLogger)
    stdout, _, err := r.Run(context.Background(), dir, nil, "cat", "big.txt")
    if err != nil { t.Fatal(err) }
    if len(stdout) > maxCapturedOutputBytes {
        t.Fatalf("stdout not bounded: got %d bytes", len(stdout))
    }
}
```
This test currently fails against the existing implementation because `outbuf`/`errbuf` have no capacity limit.
