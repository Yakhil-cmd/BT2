Confirmed: line 1873-1876 of `aa_composer.js` shows that when no template branch (`if` condition) matches the incoming trigger, the AA "eats the received coins and sends no response" while state changes still commit — i.e., the payment is silently absorbed into `aa_balances` without any of the AMM's swap/invest logic running.

### Title
Uniswap-style AA reserves computed from raw `balance[asset]` can be manipulated by direct/no-op payments to the AA address - (File: `test/samples/uniswap_like_market_maker.oscript`, `aa_composer.js`)

### Summary
The bundled market-maker Autonomous Agent (AA) pattern computes swap/invest math directly from `balance[base]` / `balance[$asset]` (the AA's live aggregate balance, backed by the `aa_balances` table), analogous to how Caviar's `Pair.sol` computed reserves from `ERC20.balanceOf(address(this))`. Because ocore lets any unprivileged unit poster send a payment to an AA address that does not satisfy any of the AA's `if` branches, that payment is silently absorbed ("eat the received coins and send no response, state changes are still performed") while still increasing the AA's tracked `balance[asset]`/`balance[base]`. This lets an attacker inflate the "reserves" used by the constant-product formula in a later trade without going through the proportional-amount check enforced on `invest in MM`.

### Finding Description
`getTrigger` collects every payment output addressed to the AA into `trigger.outputs` [1](#0-0)  and `handleTrigger` always credits these outputs into `aa_balances` via `updateInitialAABalances` before any `if` condition of the AA template is evaluated [2](#0-1) . If none of the AA's message-case branches match, the filtered `messages` array is empty and the composer takes the "eat the received coins and send no response, state changes are still performed" path [3](#0-2) ; balances are still finalized (the trigger's outputs are already merged) even though no swap or invest logic ran.

The sample market-maker AA relies on `balance[$asset]` / `balance[base]` (the AA's raw aggregate token holdings) as its reserves for both the invest-ratio check and the constant-product swap formula: `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]; $bytes_balance = balance[base] - trigger.output[[asset=base]]; $p = $asset_balance * $bytes_balance;` [4](#0-3) . These reserves are never tracked with dedicated internal state variables updated only on `invest`/`divest`/`exchange` messages (the Uniswap V2-style mitigation), so any confirmed payment credited to `aa_balances`, whatever the reason, changes the perceived reserves for the next swap. In particular, a plain base-byte payment that fails all `if` conditions (e.g. an amount at or below `1e5`, or one that doesn't match "invest"/"divest"/"exchange" patterns while `mm_asset_outstanding` state hasn't been set yet) is still merged into `balance[base]` per the "eat the coins" branch, without going through the `invest`-branch's `$expected_asset_amount` ratio check.

### Impact Explanation
An attacker (any unprivileged unit poster) can shift the constant-product price of the AA's pool by donating bytes or the paired asset directly to the AA address in a way that avoids matching the `invest`/`divest`/`exchange` conditions, then immediately trade against the skewed reserves in a subsequent unit, extracting value from other liquidity providers/traders — the same "steal funds from third-party integrations relying on the price" impact described in the referenced Caviar finding, since `balance[asset]` here plays the role of Pair's manipulable reserve/price oracle.

### Likelihood Explanation
Medium: this specific AA is a documentation/test sample rather than a deployed production contract, but it demonstrates a pattern (using raw `balance[]` as AMM reserves without incremental, message-gated tracking) that any AA author following this template in production would inherit; and the underlying platform behavior (silent absorption of unmatched payments into `aa_balances`) at `aa_composer.js:1865-1877` is a genuine, reachable design mechanism triggered by an unprivileged trigger sender.

### Recommendation
Advise/require AA authors implementing AMM-style pools in oscript to track reserves in dedicated state variables (`var['reserve_base']`, `var['reserve_asset']`) that are updated only inside the `invest`/`divest`/`exchange` message branches, rather than reading `balance[asset]` directly, mirroring the Uniswap V2 `reserve0`/`reserve1` + `_update` mitigation recommended in the referenced report. Documentation for `balance[]` in AA guides should explicitly warn that it reflects total on-chain balance (including funds absorbed via unmatched/"eaten" triggers) and is unsuitable as a manipulation-resistant price/reserve source.

### Proof of Concept
1. Attacker observes the market-maker AA has `var['mm_asset_outstanding']` set (pool active).
2. Attacker sends a plain payment of `base` bytes to the AA's address with an amount that fails all `if` conditions in the template (e.g. exactly `1e5` bytes, failing the `> 1e5` checks used by "invest" and "exchange bytes to asset", while sending 0 of `$asset` so "exchange asset to bytes" and "divest" also don't match).
3. Per `aa_composer.js:1865-1877`, no branch's messages fire, but `updateInitialAABalances` already merged the payment into `aa_balances`, so `balance[base]` for the AA increases permanently with no compensating `mm_asset_outstanding` update.
4. Attacker sends a follow-up unit matching "exchange asset to bytes" (`trigger.output[[asset=$asset]] > 0`); the formula reads `$bytes_balance = balance[base] - trigger.output[[asset=base]]`, which is now inflated by step 2's donation, producing a skewed `$new_bytes_balance`/`$amount` that the attacker can exploit to extract more bytes than the pre-donation reserves would allow, at the expense of other LPs/traders.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
