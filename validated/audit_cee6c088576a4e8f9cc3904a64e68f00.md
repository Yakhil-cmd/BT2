### Title
Cross-organization webhook signature verification divergence allows forged `pull_request` events to overwrite another tenant's `PullRequest` record - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC verifier using `repository_owner`, which falls back to `params.organization.login` whenever `repository.owner.login` is absent from the payload [1](#0-0) . `EditedHandler`, however, resolves the target repository/stack solely from `params.repository.full_name`, a field the schema requires but that is independent of `repository.owner.login` [2](#0-1) [3](#0-2) . This lets a payload be authenticated with organization A's webhook secret while mutating a `PullRequest` belonging to organization B's stack.

### Finding Description
The broken binding: **verified-organization(request) == owner-of(params.repository.full_name)** is assumed by the controller but never enforced.

- `repository_owner` reads `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) .
- `verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the HMAC using that organization's `webhook_secret` [4](#0-3) . Shipit supports multiple independently configured GitHub orgs/apps, each with its own `webhook_secret`, selected via `github_app_config(organization)` [5](#0-4) , and `verify_webhook_signature` trivially returns `true` when that org's `webhook_secret` is blank [6](#0-5) .
- `EditedHandler`'s `ExplicitParameters` schema requires `repository.full_name` but not `repository.owner.login` [2](#0-1) , and the handler resolves the target `repository`/`stack`/`PullRequest` exclusively from `params.repository.full_name` [7](#0-6) , then writes `pull_request.update(github_pull_request: params.pull_request)` [8](#0-7) .

Exploit request: attacker crafts a JSON body with `organization: { login: "attacker-org" }` (an org for which they can forge/know the webhook secret, or whose configured secret is blank), omits `repository.owner.login`, but sets `repository: { full_name: "victim-org/victim-repo" }` and `action: "edited"`. `repository_owner` resolves to `"attacker-org"`, the signature check passes against attacker-org's verifier, yet `EditedHandler` looks up and updates the `PullRequest` belonging to `victim-org/victim-repo`'s stack.

No existing guard closes this gap: `drop_unhandled_event`/`check_if_ping` don't inspect organization/repository consistency; the `ExplicitParameters` schema only requires presence of fields, not cross-field consistency; there is no re-verification that the authenticated organization owns `repository.full_name`.

### Impact Explanation
The attacker can overwrite the `github_pull_request` cache column of a `Shipit::PullRequest` record belonging to a stack/repository they never authenticated for, using credentials/signature material tied to a different (possibly attacker-controlled) organization — this is a payload for one repository mutating another repository's stack data, matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. This write is repeatable against any repository whose `full_name` and PR `number` the attacker can guess.

However, I could not find any code path connecting `EditedHandler`'s write (`github_pull_request` JSON cache used for UI display) to `ContinuousDeliveryJob` or any deploy/commit-state trigger. The handler does not touch commit statuses, stack `HEAD`, or task creation, so the specific "auto-ship newly-green commits via ContinuousDeliveryJob" amplification asserted in the question is not substantiated by this handler alone — that part of the claimed chain does not hold as described.

### Likelihood Explanation
Requires: (1) the Shipit deployment to use the multi-organization GitHub config schema (`github_default_organization` non-nil) with at least one org's `webhook_secret` blank or an org whose secret the attacker knows/controls; (2) attacker knowledge of `victim-org/victim-repo` full name and a valid PR `number`. No authentication, session, or API token is needed — only `POST /webhooks` reachability. This is feasible for any internet-reachable Shipit instance running multi-org config with a lenient/blank secret on any one org.

### Recommendation
Verify signature using the organization actually referenced by `params.repository.full_name`'s owner (not a separately attacker-controlled `organization.login` fallback), or require that `repository.owner.login` be present and match `repository.full_name`'s owner before dispatch. Additionally, each handler should re-validate that the authenticated `repository_owner` matches the repository it operates on before performing any write.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure `Rails.application.credentials.github` with two orgs: `attacker-org` (blank `webhook_secret`) and `victim-org` (non-blank secret) — mirroring `secrets.test.json`'s multi-org format.
2. Create `shipit_stacks(:shipit)` under repository `victim-org/victim-repo`, and a `Shipit::PullRequest` with `number: 2`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, body `{ action: 'edited', number: 2, pull_request: {...forged title/state...}, repository: { full_name: 'victim-org/victim-repo' }, organization: { login: 'attacker-org' }, sender: { login: 'attacker' } }`, and a signature computed with an empty/known `attacker-org` secret (no `repository.owner.login` key present).
4. Assert response is `200 OK` (bypassing the intended per-repo secret) and assert `pull_request.reload.github_pull_request['title']` equals the attacker-forged title — proving the `victim-org` PullRequest record was mutated using `attacker-org`'s authentication material.
5. Assert on both sides of the binding: `WebhooksController#repository_owner` returned `'attacker-org'` while `EditedHandler#repository.full_name` resolved `'victim-org/victim-repo'` — demonstrating the divergence.

Note: the further claim that this write triggers `ContinuousDeliveryJob`/auto-deploy is not demonstrated by any code in `EditedHandler`; a PoC asserting that specific downstream effect would not pass, as no code path connects the `github_pull_request` cache update to deploy triggering.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
