### Title
Cross-tenant `Status#target_url` injection via sha-matched `StatusHandler` write - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits by `sha` alone across the entire database, with no scoping to the reporting repository, and writes the attacker-supplied `target_url` verbatim into any matching `Commit`'s `Status` row via `Status.replicate_from_github!`. This lets an attacker who controls a repository that shares a commit sha with a victim's tracked stack (e.g., via a fork sharing ancestor commits) push an arbitrary `target_url` string onto the victim's commit history, which is then rendered as a clickable CI link in the victim operator's UI.

### Finding Description
Binding claimed to hold: `Status#target_url` displayed to an operator of stack S == a URL genuinely produced by S's own CI provider for a commit that S's own repository authenticated via its GitHub webhook. This binding is broken.

Path:
- `WebhooksController#verify_signature` only validates that the HMAC signature matches the `webhook_secret` configured for `repository_owner` (`params.dig('repository','owner','login')`), i.e., it authenticates *which organization* sent the payload — not that the `sha` inside the payload belongs to that organization's repository [1](#0-0) .
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query is global across all stacks/tenants, not scoped to the repository that authenticated the webhook [2](#0-1) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` writes `target_url: github_status.target_url` (from `params`, i.e., attacker-supplied) directly onto the `Status` row tied to whatever `Commit`/`stack_id` matched by sha [3](#0-2) .
- The `StatusHandler` params schema only requires `target_url` be a `String` — no URL format, host allow-list, or scheme validation is applied [4](#0-3) . The `Status` model itself validates only `state` inclusion/presence; `target_url` has no validation at all [5](#0-4) .
- This value is rendered directly into an `href` in the operator-facing UI: `href="<%= status.target_url%>" target="_blank"` [6](#0-5) .

Attacker flow: attacker owns/administers a repository already onboarded to Shipit (satisfies "emit webhooks from a repository they own" per the rules), typically a fork of the victim's repository. Because forks share git ancestry, some commit shas are identical between the fork and the victim's upstream repo tracked by a different Shipit stack. The attacker sets a commit status (via GitHub's normal status API, using their own repo permissions) on that shared sha, with an attacker-chosen `target_url`. GitHub signs and delivers this webhook using the attacker's own organization's legitimately configured webhook secret — `verify_signature` passes because it only checks the attacker's own org/secret pairing, never that the sha is scoped to that org's repo. `StatusHandler` then matches the victim's `Commit` row (identical sha, different `stack_id`) and writes the attacker's `target_url` (and state/description/context) onto it.

Existing guards do not stop this: `verify_signature` authenticates the sender org but not the sha-to-repo relationship; `ExplicitParameters` schema only enforces types, not content; there is no model-level validation restricting `target_url` format or verifying the commit's actual repository ownership before write.

### Impact Explanation
This is a payload from one repository (attacker's) mutating another tenant's `Commit`/`Status` row — the write itself is the primary Critical finding (cross-repo state mutation without repository authentication of the target row). The `target_url` component adds a secondary vector: an operator of the victim stack, trusting the UI's rendered link on their own commit's status pill, is redirected to an attacker-chosen URL rather than their own CI provider's page, enabling phishing (e.g., a fake CI login page to harvest credentials, or a page designed to social-engineer an approval/merge action). This is layered on top of, and shares the exact same root cause as, the underlying cross-tenant write; it does not independently execute code or bypass authentication but it does expose attacker-controlled content to the victim's operators as if it were trusted, first-party CI content, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: attacker must own/administer a GitHub repository that (a) is already tracked/onboarded by the same Shipit instance (so a valid webhook with a real signature exists) and (b) shares at least one commit sha with the victim stack's tracked commit history — most straightforwardly satisfied by forking the victim's public repository, since unmodified ancestor commits retain identical shas. No Shipit secrets, sessions, or GitHub App credentials are needed; the attacker only needs ordinary push/status-setting rights on their own repository, which is explicitly within the stated unprivileged attacker capabilities. This is repeatable against any repository the attacker can fork and any commit sha shared with a tracked victim stack.

### Recommendation
Scope `Commit` lookup in `StatusHandler#process` (and analogous handlers) to the repository that authenticated the webhook, not by sha alone — e.g., join through `stack.repository` and filter by the `repository_owner`/`full_name` from the verified payload before calling `create_status_from_github!`. Additionally, validate `target_url` at the model or handler level (require `http`/`https` scheme, reasonable length, optionally restrict to expected CI hosts) before persisting or rendering it.

### Proof of Concept
```ruby
# test/models/status_cross_repo_test.rb
require 'test_helper'

module Shipit
  class StatusCrossRepoTest < ActiveSupport::TestCase
    test "a status webhook from repo A cannot write an attacker target_url onto repo B's commit sharing the same sha" do
      victim_stack = shipit_stacks(:shipit)
      victim_commit = shipit_commits(:first) # belongs to victim_stack, has a known sha

      attacker_payload = OpenStruct.new(
        sha: victim_commit.sha, # shared sha, e.g. via fork ancestry
        state: 'success',
        description: 'fake ci',
        context: 'ci/attacker',
        target_url: 'https://attacker.example.com/phish',
        created_at: Time.now
      )

      # Simulate StatusHandler#process resolving purely by sha, regardless of
      # which repository/organization actually authenticated the webhook.
      Commit.where(sha: attacker_payload.sha).each do |commit|
        commit.create_status_from_github!(attacker_payload)
      end

      victim_commit.reload
      status = victim_commit.statuses.last

      # Binding under test: status.target_url should equal a URL genuinely
      # produced by victim_stack's own CI, never the attacker-supplied string.
      refute_equal attacker_payload.target_url, status.target_url,
        "victim commit's Status#target_url was overwritten with attacker-controlled URL"
      assert_equal victim_stack.id, status.stack_id
    end
  end
end
```
This test demonstrates that, absent repository-scoped lookup, `status.target_url` ends up equal to the attacker-supplied string (`'https://attacker.example.com/phish'`) rather than any URL originating from the victim stack's own CI history, confirming the broken binding.
