## Title
Cross-organization webhook forgery via unauthenticated organization-selection binding break - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App / webhook secret to validate a webhook against using an unverified field taken directly from the request payload (`repository.owner.login` or `organization.login`), before the payload's authenticity has been established. Once that organization is selected, its `verify_webhook_signature` result gates the whole request — but the field used to pick the verification key (`repository_owner`) is never re-checked against the field the handlers actually act on (`repository.full_name`) inside `Shipit::Webhooks::Handlers::Handler#repository_name` and its subclasses (e.g. `PushHandler`). This is structurally the same class of bug as the ERC677 `transferAndCall` double-transfer: two different fields are supposed to represent "the same" authorized entity, but only one of them is checked, and the code path lets an attacker supply a value in the unchecked field that diverges from the one that was verified.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` runs `verify_signature` as a `before_action`: [1](#0-0) 

The org used to select the webhook secret is derived straight from the (still-unverified) payload: [2](#0-1) 

`GitHubApp#verify_webhook_signature` **unconditionally returns `true` when no `webhook_secret` is configured** for that resolved organization: [3](#0-2) 

Shipit explicitly supports (and documents) multi-organization configuration where each org can independently have a `webhook_secret` set or left blank: [4](#0-3) 

After `verify_signature` passes, `create` re-parses the same raw body and dispatches it to handlers keyed only by event type — it does **not** re-derive or cross-check the organization that was used for signature selection against the repository the handler will act on: [5](#0-4) 

Handlers such as `PushHandler` resolve their target purely from `repository.full_name` in the payload, via the shared `Handler#stacks`/`repository_name`: [6](#0-5) [7](#0-6) 

**Binding that should hold:** `organization used to select/pass signature verification == organization that owns the repository being written to by the handler`.

**Binding that actually holds:** the org used for verification is looked up from `repository.owner.login` (or `organization.login`) purely to pick a `Shipit::GitHubApp` config object; nothing forces that org's identity to match the repository the handler subsequently mutates, and if that org has no `webhook_secret` configured, `verify_webhook_signature` degenerates to an unconditional `true`, so *any* payload claiming to belong to that org — including one whose `repository.full_name` names a stack that actually belongs to a *different*, secret-protected org configured on the same Shipit instance — passes signature verification and is processed by the handler.

### Impact Explanation
If a deployment configures more than one GitHub organization (a pattern the engine explicitly documents/supports via `config/secrets.*.yml` with per-org `webhook_secret`), and at least one configured organization has no `webhook_secret` set (also explicitly documented as "optional"), an unauthenticated, unprivileged attacker can:
1. Send a POST to `/webhooks` with `X-Github-Event: push`, a forged `X-Hub-Signature` (or none), and a JSON body whose `repository.owner.login` matches the org with **no** secret, but whose `repository.full_name` matches a *stack belonging to a different org that does have secret protection*.
2. `verify_signature` resolves the GitHub App for the unsecured org and unconditionally returns `true`.
3. `PushHandler` then dispatches `sync_github`/deploy-triggering webhook logic against the stack matching the forged `repository.full_name`, which is the protected org's repository.

This lets an attacker with no credentials, no GitHub App private key, and no Shipit session trigger `GithubSyncJob` (and equivalently forge `status`, `check_suite`, `membership` events that create Teams/Users/Memberships) against repositories/stacks that should only be reachable by a signed webhook from a different, secret-protected organization — a cross-repository/cross-organization write achieved by exploiting the mismatch between the authenticated field (`repository_owner`, used only to pick a verification key) and the acted-upon field (`repository.full_name`, used by the handler).

### Likelihood Explanation
Requires the operator-supported configuration of multiple GitHub organizations with inconsistent `webhook_secret` presence (explicitly documented as legal/optional in `config/secrets.development.shopify.yml` and `docs/setup.md`). Given this is a supported, documented configuration, and no additional session/credential/App private key is needed by the attacker, likelihood is moderate to high in any multi-org deployment where at least one org's webhook secret is unset — a scenario the engine's own configuration examples show as normal.

### Recommendation
- Require a `webhook_secret` to be configured for every organization when more than one GitHub organization/app is configured (reject webhooks for orgs lacking a secret rather than trusting them unconditionally).
- After signature verification succeeds, re-validate that the `repository.full_name` (or `organization.login`) actually used by the dispatched handler belongs to the same organization whose secret validated the signature, rather than trusting the payload's `repository.owner.login` implicitly for both purposes.
- Consider failing closed (422) instead of `true` when `webhook_secret` is blank, at least whenever multiple GitHub orgs are configured.

### Proof of Concept
Given a Shipit instance configured with:
```yaml
github:
  secure-org:
    webhook_secret: "s3cr3t"
    ...
  open-org:
    webhook_secret: # left blank
    ...
```
And a stack `secure-org/protected-repo` deployed under `secure-org`:

1. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/protected-repo"
  }
}
```
2. `repository_owner` resolves to `"open-org"` → `Shipit.github(organization: 'open-org')` → `verify_webhook_signature` returns `true` unconditionally because `open-org` has no `webhook_secret`.
3. `PushHandler#process` resolves `stacks` from `repository.full_name == "secure-org/protected-repo"`, matching the real protected stack, and enqueues `GithubSyncJob` / triggers sync for a commit SHA the attacker fully controls — despite `secure-org`'s webhook secret never being checked.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
