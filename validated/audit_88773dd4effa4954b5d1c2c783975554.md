Confirmed: `definition.js`'s `'sig'` op validation only checks `isStringOfLength(args.pubkey, constants.PUBKEY_LENGTH)` with no dedup requirement across a `'r of set'`, and the `'r of set'` evaluator (both `validateDefinition` at [1](#0-0)  and `validateAuthentifiers` at [2](#0-1) ) purely counts how many of the `set` branches evaluate to true, without ever checking that the underlying signing authorities (pubkeys/addresses) referenced by those branches are distinct.

### Title
r-of-set / weighted-and multisig thresholds count satisfied branches, not distinct signing authorities, allowing a single key to fake an M-of-N threshold - (File: definition.js)

### Summary
Address definitions using `['r of set', {required, set}]` (or `['weighted and', ...]`) are ocore's mechanism for expressing "at least R of N independent signers/conditions must approve." The threshold-counting logic mirrors the sigstore-go flaw: it counts the number of *branches* (entries in `args.set`) that evaluate true, not the number of *distinct cryptographic authorities* behind those branches.

### Finding Description
`evaluate()` in `validateDefinition` walks each element of `args.set` and increments `count_options_with_sig` whenever a branch contains a `sig`/`hash`/`address` leaf: [3](#0-2) . There is no check anywhere in `validateDefinition` that the `pubkey` (for `sig`), `hash` value (for `hash`), or resolved `address` (for `address`) is unique across the `set` array — nothing analogous to the `arrCollectedWitnesses.indexOf(address) === -1` dedup pattern used elsewhere for witness counting (e.g. `storage.js` `determineWitnessedLevelAndBestParent`, `writer.js` `updateWitnessedLevelByWitnesslist`).

At authentication time, `validateAuthentifiers`'s `'r of set'` handler again just counts `arg_res` truths per branch and compares to `args.required`: [2](#0-1) . The `'sig'` leaf verifies the signature against `args.pubkey` at that specific `path` only, using `ecdsaSig.verify(objValidationState.unit_hash_to_sign, signature, args.pubkey)`: [4](#0-3) . If two (or more) branches in the same `set` reference the identical `pubkey`, the holder of that one private key can produce two authentifiers (`r.0`, `r.1`, etc.) over the same `unit_hash_to_sign` and satisfy both branches, because each branch is verified independently and success is counted per-branch, not per-unique-key.

This is structurally identical to the sigstore-go bug: the threshold ("R of N logs/witnesses/co-signers") is meant to defend against compromise of any single authority, but the implementation counts validation paths/entries rather than de-duplicated authorities, so one compromised/colluding key can satisfy multiple slots and defeat the "defense-in-depth" intent of the M-of-N definition.

### Impact Explanation
An address (e.g. a shared wallet, escrow, or private-payment counterparty address) can be defined by one party as `['r of set', {required: 2, set: [['sig',{pubkey:A}], ['sig',{pubkey:A}], ['sig',{pubkey:B}]]}]` — visually a "2 of 3" scheme suggesting two independent approvals are needed — while in reality holder of key `A` alone can satisfy `required=2` by signing twice, spending funds or authorizing AA triggers without the cooperation of key `B`. Counterparties who rely on the address definition metadata (visible on-chain / shared in wallet UIs) to believe a threshold is enforced (e.g. multi-party escrow, arbiter contracts, shared corporate wallets) could be deceived into trusting a definition that provides no real additional security, leading to unauthorized spending by a single party who was supposed to only be one-of-several required signers.

### Likelihood Explanation
Reachable directly by any unprivileged unit poster: anyone can define such an address (`definition.js` `validateDefinition` accepts it — there is no uniqueness constraint) and post a unit spending from it with duplicated leaf conditions in the `set`, satisfying `checkSerialAddressUse`/`validateAuthentifiers` in normal unit validation (`validation.js` `validateAuthor` → `Definition.validateAuthentifiers`). No special privilege, network position, or race condition is required — only that a legitimate-looking multisig address is set up this way and a counterparty is misled into treating it as a genuine multi-party threshold.

### Recommendation
When validating `'r of set'` / `'weighted and'` definitions, enforce that the resolved signing authorities (pubkeys for `sig`, hashes for `hash`, resolved addresses for `address`, and recursively for nested `and`/`or`/`r of set`) within a single `set` are pairwise distinct, rejecting definitions where the same authority appears in more than one branch. This should be enforced in `validateDefinition` in `definition.js` at the point where `'r of set'` and `'weighted and'` are validated (lines 147-233), analogous to how the codebase already deduplicates witness addresses when counting toward `MAJORITY_OF_WITNESSES`.

### Proof of Concept
1. Compose an address definition: `['r of set', {required: 2, set: [['sig', {pubkey: P}], ['sig', {pubkey: P}], ['sig', {pubkey: Q}]]}]` where `P` is a single attacker-controlled key and `Q` belongs to the intended second party. This passes `validateDefinition` (definition.js:147-185) with no distinctness check.
2. Compute the address `chash` from this definition and present it to a counterparty as a "2-of-3" shared/escrow address.
3. To spend, the attacker signs the same `unit_hash_to_sign` twice, submitting the same signature (or two independently valid signatures from the same key) under authentifier paths `r.0` and `r.1`.
4. `validateAuthentifiers`'s `'r of set'` handler (definition.js:692-711) evaluates both `r.0` and `r.1` as true via the `'sig'` leaf (definition.js:734-754), reaching `count(2) >= required(2)`, and the unit is accepted as validly authorizing the spend — despite key `Q` never having participated.
