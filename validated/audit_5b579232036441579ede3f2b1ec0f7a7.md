### Title
Cross-repository forgery of commit CI status via unscoped `StatusHandler` webhook processing - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController` verifies an inbound GitHub webhook's signature against the GitHub App belonging to the **organization that owns the repository in the payload** [1](#0-0) , but the `status` event handler that actually mutates data ignores that repository/organization entirely and updates **every** `Commit` row in the database whose `sha` matches the payload, regardless of which stack or repository it belongs to [2](#0-1) . This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/organization's `webhook_secret` to validate the signature against purely from the payload's own `repository.owner.login` (or `organization.login`) field [3](#0-2) . Once the signature is valid for *that* organization, the event is dispatched to handlers with no further repository scoping enforced by the controller [4](#0-3) .

Most handlers correctly re-scope to the originating repository via the shared `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')` [5](#0-4) , e.g. `PushHandler` and `CheckSuiteHandler` both operate only on `stacks` [6](#0-5) [7](#0-6) .

`StatusHandler` is the outlier: it does not call `stacks` at all and instead looks up commits system-wide purely by SHA:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [8](#0-7) 

Because a git SHA-1 is a content hash, any organization onboarded into Shipit (one with a valid GitHub App/webhook secret configured for at least one repository) can legitimately generate a signed `status` webhook whose `sha` happens to match a commit that also exists in a completely different stack/repository owned by a different organization — for example by pushing a byte-identical copy of a publicly known commit (same tree, parents, author/committer identities and timestamps, message) into a repository they control, then having their own CI/status integration report a status for it. GitHub will sign that webhook with the attacker-controlled organization's own `webhook_secret`, which passes `verify_signature` because verification only checks the org that owns the *payload's* repository — never checking whether that org actually owns the target `Commit` records being modified.

### Impact Explanation
This constitutes an unauthorized cross-repository write: an attacker who is merely an authorized contributor of one onboarded organization/repository can forge commit statuses on commits belonging to a totally unrelated stack/repository they have no access to. Commit statuses feed directly into CI-gating logic used for deploy/merge safety checks (`ci.require` / `required_statuses` in `DeploySpec`) [9](#0-8) . By forging a "success" state for a required status context on a target commit, the attacker can make an otherwise CI-blocked commit appear deployable/mergeable in a stack they don't control, resulting in an unauthorized deploy or merge — meeting the Critical "cross-repository writes" / "unauthorized deploy...or merge" bar.

### Likelihood Explanation
Exploitation requires: (1) being an authorized user/CI integration of at least one Shipit-onboarded organization (a low bar relative to the target stack, which the attacker need not have any access to), and (2) being able to produce a commit with an identical SHA to a target commit — feasible whenever the target commit's exact metadata is knowable (public/OSS commits, commits shared across mirrored/forked repos, or commits leaked via other status/webhook traffic). This is a real, if non-trivial, path; it does not require guessing any secret, since the attacker's own organization's `webhook_secret` is used to legitimately sign their own event.

### Recommendation
Scope `StatusHandler#process` (and any future handler) to the repository identified in the webhook payload, mirroring the pattern used by `PushHandler`/`CheckSuiteHandler`: restrict `Commit.where(sha: params.sha)` to commits whose `stack` belongs to `Repository.from_github_repo_name(repository_name)` (i.e., use the shared `stacks` scope) instead of a global, repository-agnostic lookup.

### Proof of Concept
1. Attacker is a member of Organization A, which has a Shipit-registered repository `A/repo` with a valid GitHub App/webhook secret.
2. Target Stack B lives in Organization B's repository `B/repo`, unrelated to A, with a commit `C` whose SHA and full metadata (tree, parents, author/committer identities, timestamps, message) are known to the attacker (e.g., `C` originated from a public upstream repo that both `A/repo` and `B/repo` share history with, or was disclosed via a PR/commit visible to the attacker).
3. Attacker reproduces commit `C` byte-for-byte in `A/repo` (same SHA) and has their CI/integration report a `success` status for it, causing GitHub to send a signed `status` webhook to Shipit with `repository.owner.login = A`, `sha = C.sha`, `state = success`.
4. `WebhooksController#verify_signature` validates the signature against Organization A's webhook secret and succeeds [10](#0-9) .
5. `StatusHandler#process` runs `Commit.where(sha: C.sha)`, which also matches commit `C` in Stack B, and writes the forged `success` status onto it [8](#0-7) , satisfying Stack B's required CI check and enabling an unauthorized deploy/merge of `C` in Stack B — a stack and organization the attacker has no legitimate access to.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
