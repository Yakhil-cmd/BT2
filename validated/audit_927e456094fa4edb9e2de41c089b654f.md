The reported issue is specific to Uniswap V3's `sqrtPriceX96` representation, where price must be squared and then rescaled by `10**(decimals0 - decimals1)` to get a token1/token0 exchange rate — a bug that arises because Uniswap V3 stores price as a normalized square-root ratio independent of token decimals.

Polkadot SDK's `pallet-asset-conversion` uses a constant-product AMM design where quotes (`quote_price_exact_tokens_for_tokens`, `get_amount_in`, `get_amount_out`) are computed directly from raw pool reserve balances rather than from a decimal-agnostic price ratio like `sqrtPriceX96`. [1](#0-0) [2](#0-1) 

Because reserves are stored and multiplied/divided as actual on-chain balances of each asset (which already implicitly reflect each asset's decimal precision, since `1 unit` of an 18-decimal asset and `1 unit` of a 6-decimal asset are just different-sized integers in their own reserve pools), there is no separate "price" value that needs external decimal rescaling — the arithmetic in `get_amount_in`/`get_amount_out` is self-consistent regardless of each token's decimals. [3](#0-2) 

I also checked `pallet-psm`, which does perform explicit decimal-aware conversions between assets of differing precision via `external_to_internal`/`internal_to_external`, using checked scaling factors bounded by `MAX_DECIMALS_DIFF`; this is a case where decimals actually matter, and the code explicitly accounts for the decimal difference rather than omitting it. [4](#0-3) 

Since Polkadot SDK's relevant pricing/AMM logic does not use a decimal-agnostic squared-price representation analogous to `sqrtPriceX96`, and the pallet that does perform explicit decimal conversion (`pallet-psm`) correctly accounts for decimal differences, there is no demonstrable analog of this Aloe II Borrower.sol bug class in this codebase.

				Equal => Ok(amount),

					let factor = Self::pow10(diff)?;
