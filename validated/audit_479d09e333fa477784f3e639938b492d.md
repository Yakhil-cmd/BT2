Confirmed root-cause binding: `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` is used for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the request body, while every event `Handler` (via `Handler#stacks`/`#repository_name`) resolves the target `Repository`/`Stack` from the *separate* `repository.full_name` field of that same body [1](#0-0) [2](#0-1) . Nothing ties these two fields together, so the equality "org whose secret authenticated the request == org owning the repository actually written to" is never enforced. In a multi-organization deployment (supported via `secrets.yml` with multiple GitHub Apps, e.g. `OrgTwo` in `test/dummy/config/secrets_double_github_app.yml`) an attacker who legitimately controls one onboarded organization's GitHub App (and therefore knows/can trigger its `webhook_secret`) can set `repository.owner.login` to their own org (so `Shipit.github(organization: repository_owner)` picks a secret they can produce a valid signature for) while setting `repository.full_name` to `otherorg/other-repo`, a stack belonging to a different, unrelated organization onboarded on the same Shipit instance. This lets them forge `push`, `pull_request`, `status`, `check_suite`, `membership`, etc. events against stacks/repositories they don't own, e.g. injecting fake commits via `PushHandler` → `Stack#sync_github`, fabricating passing CI `status`/`check_suite` payloads that feed `MergeRequest#all_status_checks_passed?` and `ProcessMergeRequestsJob#perform` → `MergeRequest#merge!`, causing an unauthorized cross-repository merge/deploy trigger. This does not require an `ApiClient` token, session, or GitHub App private key — only knowledge of one org's already-configured `webhook_secret`, which is exactly the "unprivileged relative to the victim org" attacker class the rules describe.

I was not able to fully trace every downstream handler (e.g. `status`, `check_suite`) to confirm each one lacks any additional cross-check against `repository.owner.login`; based on `Handler#repository_name` (used by all handlers) and the several `pull_request/*` handlers inspected, none of them consult `repository.owner.login` at all, only `repository.full_name`.

### Title
Webhook signature verified against payload's declared org while the target repository/stack is resolved from a separate unchecked field, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate `X-Hub-Signature` using `repository.owner.login` (falling back to `organization.login`) from the JSON body, but the event handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by push/pull_request/etc. handlers) resolve the affected `Stack`/`Repository` using the independent `repository.full_name` field. No code enforces that these two fields refer to the same organization/repository.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

Meanwhile every handler resolves the target repository/stack purely from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

The same pattern is repeated explicitly in `PullRequest::OpenedHandler#repository`, which looks up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` without any reference to `repository.owner.login` [5](#0-4) .

Because `Shipit.github(organization:)` supports per-organization GitHub Apps with independent `webhook_secret` values (as configured in `test/dummy/config/secrets_double_github_app.yml`) [6](#0-5) , an attacker who controls the GitHub App/webhook secret for Org A can send a webhook whose `repository.owner.login` = "OrgA" (so the signature validates against Org A's secret) but whose `repository.full_name` = "OrgB/some-repo" (a stack belonging to an unrelated organization B hosted on the same Shipit instance). `verify_signature` accepts the request, and the handler writes to Org B's stack.

### Impact Explanation
This breaks the equality "organization that authenticated the webhook == repository that is written," which is explicitly called out as a critical unprivileged-attacker binding in scope. Concretely, an attacker can:
- Forge `push` events to trigger `GithubSyncJob`/`Stack#sync_github` on a victim stack they don't control, injecting attacker-chosen commit metadata into a repository they have no legitimate write access to.
- Forge `status`/`check_suite` events to fabricate passing CI results on a victim's pull request, which feeds `MergeRequest#all_status_checks_passed?` and can cause `ProcessMergeRequestsJob` to auto-merge and deploy a PR that never actually passed CI — an unauthorized deploy/merge, matching the Critical impact bucket ("cross-repository writes... unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only that the attacker legitimately administers (or has otherwise obtained the webhook secret for) at least one organization/GitHub App already onboarded to the shared Shipit instance — a low bar in any multi-tenant deployment, and explicitly not one of the excluded privileged prerequisites (no `ApiClient` token, no session, no GitHub App private key, no repository write access to the *victim* repo).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handlers::Handler`), after selecting the GitHub App by `repository_owner`, verify that the resolved app/organization actually matches the owner segment of `repository.full_name` (and of any repositories referenced by nested objects, e.g. `pull_request.base.repo`) before dispatching to handlers. Reject the webhook if they diverge.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over this exact body and POSTs it to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully, and `PushHandler` looks up stacks for `OrgB/victim-repo`, syncing/triggering behavior on a stack the attacker does not own.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
