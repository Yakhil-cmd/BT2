### Title
`Api::CCMenuController` lets a stack-scoped `ApiClient` token read the build status of any other stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor that the rest of the API controllers inherit from `Api::BaseController`, bypassing the stack-scoping check that binds an `ApiClient` token to the single stack it was authorized for. This lets the holder of a stack-scoped, `read:stack`-only token retrieve CCMenu build-status XML (build status, last build label/time, activity, web URL) for **any** stack in the Shipit instance, not just the one the token was issued for.

### Finding Description
`Api::BaseController` implements the trust binding "a stack a token authorises" == "a stack it touches": [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

When an `ApiClient` has a `stack_id` set (i.e. it was created scoped to one particular stack, as `here_come_the_walrus` is in the fixtures [2](#0-1) , or as `CCMenuUrlController` does when minting a token [3](#0-2) ), every controller that calls `stack` should only ever be able to resolve the stack it was scoped to, regardless of what `params[:stack_id]` the caller supplies.

`Api::CCMenuController`, however, redefines `stack` and drops the scoping entirely: [4](#0-3) 

```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

It only checks `require_permission :read, :stack` [5](#0-4)  — i.e. that the token has the `read:stack` permission string somewhere in its `permissions` array — but never verifies that the specific stack being requested (`params[:stack_id]`) matches `current_api_client.stack_id`. It resolves the stack directly from `Stack.from_param!`, which looks up any stack in the whole install by its param (`owner/repo/environment`), with no scoping filter at all.

**Root cause, before/after equality check:**
- Intended binding: `current_api_client.stack_id (if present) == stack resolved and rendered`
- Actual binding in `CCMenuController#show`: `stack resolved and rendered == params[:stack_id]` (fully attacker-controlled), independent of `current_api_client.stack_id`.

This is the same bug class as the Forta finding: a scope/permission is correctly checked in isolation (the client has `read:stack`; a slashing-proposal is correctly frozen), but a second, narrower binding that should also gate the action (this token is scoped to *this* stack; *other* proposals are still open) is silently dropped in one particular code path, letting the actor act outside the intended boundary.

### Impact Explanation
Any `ApiClient` token that includes `read:stack` (this is even the sole permission on the `here_come_the_walrus` fixture and is the minimum permission minted automatically for every user's personal "CCMenu Client" via `CCMenuUrlController#client` [3](#0-2) ) can be used to read deploy/build state — `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl` (see `assert_payload` test coverage confirming these fields [6](#0-5) ) — for **every** stack configured in the Shipit instance, including stacks belonging to other repositories/teams that the token was never meant to see. This satisfies the "High - unauthenticated/under-scoped read of stack state or deploy output" impact bar: a token holder escalates from a single-stack authorization into instance-wide stack-state disclosure.

### Likelihood Explanation
High. Exploitation requires nothing beyond a valid, already-issued `read:stack` token (which is the lowest-privilege, most commonly distributed token type — every user gets one automatically for CCMenu integration) and knowledge/guessing of another stack's param (`owner/repo/environment`), which is visible in the Shipit UI to any authenticated user and often predictable. No write access, no signature forgery, and no session is required beyond the token itself.

### Recommendation
Make `Api::CCMenuController#stack` go through the same scoping helper as `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])` directly, so a stack-scoped `ApiClient` cannot resolve any stack other than the one it is bound to. Add a regression test asserting that a token scoped to stack A receives a 404/403 when `stack_id` in the request refers to stack B.

### Proof of Concept
1. As an authenticated Shipit user, create (or reuse) a stack-scoped `ApiClient`/CCMenu token for Stack A (`GET /:stack_id/ccmenu_url` → returns a `token` scoped via `stack:` when created directly, or use any client fixture with `stack_id` set and `read:stack` permission, e.g. `here_come_the_walrus`).
2. Call `GET /api/stacks/:stack_B_param/ccmenu.xml?token=<token-for-stack-A>` where `stack_B_param` is a different stack the token was never scoped to.
3. Observe that `Api::CCMenuController#authenticate_api_client` accepts the token (it only checks `ApiClient.authenticate(params[:token])`, no stack match), `require_permission :read, :stack` passes because the token carries `read:stack`, and `stack` resolves Stack B via unscoped `Stack.from_param!`, returning Stack B's CCMenu XML (build status/label/time) to the holder of Stack A's token — confirmed by the existing test structure in `test/controllers/api/ccmenu_controller_test.rb` which exercises `stack_id` directly against `@client` without ever asserting cross-stack denial.
