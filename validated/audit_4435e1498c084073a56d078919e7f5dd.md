### Title
Malicious Peer Can Panic a Snap-Syncing Node via Crafted `AccountRangeMsg` — (`File: node/cn/snap/sync.go`)

### Summary

`Syncer.OnAccounts` unconditionally calls `panic(err)` when RLP-decoding of a peer-supplied account blob fails, under the false assumption that the blobs were locally produced. A malicious peer that controls the advertised state root can supply a Merkle-proof-valid `AccountRangeMsg` whose account values are not valid RLP, bypassing the only guard (`VerifyRangeProof`) and crashing the node process.

### Finding Description

During snap sync, when a remote peer sends an `AccountRangeMsg`, the following call chain executes in the snap-handler goroutine (no `recover()` anywhere in the chain):

```
snap.Handle → HandleMessage → downloader.DeliverSnapPacket → Syncer.OnAccounts
```

Inside `OnAccounts`, after the Merkle range proof is verified:

```go
// node/cn/snap/sync.go:2287-2298
cont, err := statedb.VerifyRangeProof(root, req.origin[:], end, keys, accounts, proofdb)
if err != nil { ... return err }

accs := make([]account.Account, len(accounts))
for i, accBytes := range accounts {
    serializer := account.NewAccountSerializer()
    if err := rlp.DecodeBytes(accBytes, serializer); err != nil {
        panic(err) // We created these blobs, we must be able to decode them
    }
    accs[i] = serializer.GetAccount()
}
```

The comment is wrong: `accBytes` are **peer-supplied bytes**, not locally produced. `VerifyRangeProof` only checks that the key-value pairs are consistent with the Merkle proof rooted at `s.root`; it does not validate that the values are valid RLP-encoded Kaia accounts. A malicious peer can:

1. Build a trie whose leaf values are arbitrary bytes (not valid Kaia account RLP).
2. Compute the root of that trie.
3. Advertise a chain with higher TD whose pivot block carries that root as its state root.
4. When the syncing node issues `GetAccountRangeMsg`, respond with the crafted leaves and a valid Merkle proof for that root.
5. `VerifyRangeProof` passes (proof is internally consistent with the crafted root).
6. `rlp.DecodeBytes` fails → `panic(err)` fires in the snap-handler goroutine.

There is no `recover()` in `handleSnapPeer`, `snap.Handle`, or `HandleMessage`. The p2p server goroutine management also has no `recover()` (confirmed by search). An unrecovered panic in any goroutine terminates the entire Go process. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation

Any node performing snap sync (enabled when `SnapshotCacheSize > 0` and `snapSync == 1`) can be crashed by a single malicious peer that wins the sync-peer selection race. The crash terminates the node process entirely, preventing the node from ever completing synchronization until restarted. Repeated attacks keep the node permanently offline. This is a denial-of-service on the sync path with no protected-state or asset impact beyond availability.

### Likelihood Explanation

- Snap sync must be active (explicitly enabled via `--syncmode snap` or equivalent).
- The attacker must be a connected peer and must win the sync-peer selection (i.e., advertise the highest TD).
- No cryptographic key material or majority-validator collusion is required; any single peer can attempt this.
- The attack is repeatable: after the node restarts and re-enters snap sync, the same peer can crash it again.

### Recommendation

Replace the `panic` with a graceful error return that drops the offending peer, consistent with how `VerifyRangeProof` failures are handled immediately above:

```go
for i, accBytes := range accounts {
    serializer := account.NewAccountSerializer()
    if err := rlp.DecodeBytes(accBytes, serializer); err != nil {
        logger.Warn("Failed to decode account blob from peer", "index", i, "err", err)
        s.scheduleRevertAccountRequest(req)
        return fmt.Errorf("invalid account blob at index %d: %w", i, err)
    }
    accs[i] = serializer.GetAccount()
}
```

The caller (`HandleMessage`) already propagates errors to disconnect the peer, so returning an error here is sufficient.

### Proof of Concept

1. Run a Kaia node with snap sync enabled (`--syncmode snap`).
2. Operate a malicious peer that:
   - Builds a trie with one leaf: key = any 32-byte hash, value = `0xDEADBEEF` (not valid Kaia account RLP).
   - Computes the trie root `R`.
   - Advertises a status message with a block whose `StateRoot = R` and a TD higher than the victim's.
3. When the victim sends `GetAccountRangeMsg`, respond with:
   - `Hashes = [key]`, `Accounts = [0xDEADBEEF]`
   - A valid Merkle proof for `(key, 0xDEADBEEF)` against root `R`.
4. `VerifyRangeProof(R, ...)` passes; `rlp.DecodeBytes(0xDEADBEEF, serializer)` fails; `panic(err)` crashes the node. [4](#0-3) [5](#0-4) [6](#0-5)
