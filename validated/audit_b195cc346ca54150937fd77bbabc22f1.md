### Title
Stale `Account.owner` authorizes the previous NFT owner after a position transfer — (`contracts/controller/src/account.rs`)

### Summary
The Access Control bug class in CVE-2019-15137 is an authorization check evaluated against the wrong subject (the topic name instead of the permission expression). XOXNO Lending has the same shape: account-spending authority is checked against the `owner` field baked into the stored `Account` struct at creation, while true ownership lives in the position NFT. After a `position-nft::transfer`, the stored `account.owner` is never resynchronized, so `require_owner_or_delegate` keeps granting the previous owner full spending authority over an account they no longer own.

### Finding Description
`create_account_with` stamps `owner` into the `Account` struct once, at mint time, and no code path in `contracts/controller/src` rewrites it — there is no `set_account_owner` or transfer hook in `contracts/position-nft/src` that updates the controller copy (`contracts/controller/src/account.rs:62-73`).

All permissionless action entrypoints route through `require_owner_or_delegate`, which compares `caller` against that stale stored `owner` field (`contracts/controller/src/account.rs:115-140`):

```rust
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,   // == account.owner, set at mint
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
```

The delegate list is also keyed by the stale `owner` (`get_delegates(env, account_id, owner)`), so managers delegated by the seller keep authority too.

The codebase itself acknowledges the correct subject elsewhere: `require_account_owner` (used by `renew_account`, `add_delegate`, `remove_delegate`) reads the live NFT owner via `storage::account_owner(env, account_id)` rather than `account.owner` (`contracts/controller/src/account.rs:143-148`). The two helpers therefore disagree about who owns the account — exactly the "permission evaluated against a different identifier than the actual subject" defect from the advisory.

### Impact Explanation
An unprivileged address that sells or transfers a position NFT retains full spending authority over it. Via `controller::withdraw` and `controller::borrow` — both gated only by `require_owner_or_delegate` against `account.owner` per `scripts/permissionless_entrypoints.txt` — the previous owner can withdraw the buyer's collateral and draw debt against it, then keep the proceeds. That is direct theft of user funds and can also push the account into liquidation, destroying remaining value. Any delegates the seller registered before the transfer retain equivalent authority through the same stale key.

### Likelihood Explanation
NFT transfer is a normal, advertised feature of the position NFT, so the stale-owner state is reached through ordinary use — no privileged action, no timing race. A seller simply transfers the NFT and calls `withdraw` / `borrow` before or regardless of the buyer noticing; nothing in the authorize path re-reads NFT ownership for the action entrypoints.

### Recommendation
Stop trusting `account.owner` as the authorization subject. In `is_owner_or_delegate` / `require_owner_or_delegate`, resolve the owner through `storage::account_owner(env, account_id)` (the live NFT owner) the same way `require_account_owner` does, and key delegate storage under the account id rather than a possibly-stale owner address — or clear the delegate list on NFT transfer. Alternatively, add a controller-side hook on NFT transfer that restamps `account.owner`, though making the auth check read the canonical owner is simpler and removes the class entirely.

### Proof of Concept
1. Alice calls `controller::supply` with `account_id = 0`, minting account `A` with `account.owner = alice`, and deposits collateral.
2. Alice calls `position-nft::transfer` (or `transfer_from`) moving the NFT for account `A` to Bob. `account.owner` remains `alice`; no hook updates it.
3. Alice calls `controller::borrow(account_id = A, ...)` or `controller::withdraw(account_id = A, ...)`.
4. Inside, `require_owner_or_delegate(env, A, alice, &account.owner)` evaluates `alice == account.owner` → `true` (account.rs:121), so the call proceeds against Bob's collateral.
5. Alice receives the borrowed/withdrawn tokens; Bob's account is drained or left undercollateralized.

Note: I was unable to fully verify the absence of a transfer-time owner sync inside the position-NFT contract implementation beyond grep evidence (no `transfer`/hook symbols in `contracts/position-nft/src` outside `test.rs`, and no `set_account_owner` anywhere in `contracts/*/src`), which supports the finding but leaves a small residual uncertainty if the sync were implemented indirectly.
