### Title
Assets with `cosigned_by_definer: true` sent to an Autonomous Agent become permanently stuck - (File: `validation.js`, `aa_composer.js`)

### Summary
`ocore` explicitly forbids an AA from *defining* an asset with `cosigned_by_definer: true`, since "AA can't cosign" [2](#0-1) [3](#0-2) . However, this guard only restricts assets *issued by the AA*. It does nothing to prevent any regular user from defining an ordinary `cosigned_by_definer: true` asset and then sending units of that asset into an AA's balance via a normal (possibly multi-authored) payment. Once such funds are inside the AA, the AA can never move them back out, because every AA-authored payment message is subject to the same `cosigned_by_definer` check, and AA response units are structurally incapable of satisfying it.

### Finding Description
An asset definition may set `cosigned_by_definer: true`, requiring that every payment message spending that asset be signed by both the asset's `definer_address` and the spender:
```
if (objAsset.cosigned_by_definer && arrAuthorAddresses.indexOf(objAsset.definer_address) === -1)
    return callback("must be cosigned by definer");
``` [4](#0-3) 

This check applies uniformly to every payment message for the asset — both when a user deposits it into an AA (a regular unit, which can freely be multi-authored, so the user can add `definer_address` as a co-author and satisfy the requirement) and when the AA itself later tries to pay it back out.

The critical asymmetry is that AA-generated response units are hard-restricted to exactly one author — the AA address:
```
if (objValidationState.bAA && arrAuthors.length !== 1)
    throw Error("AA unit with multiple authors");
``` [1](#0-0) 

and outgoing AA payment messages are built with `authors: [{ address: address }]` (the AA's own address only) [5](#0-4) . There is no mechanism for an AA to add a second signer/author to its response unit, so it can never satisfy `arrAuthorAddresses.indexOf(objAsset.definer_address) === -1` for any `definer_address` other than itself.

`ocore`'s own validation explicitly documents awareness of this exact incompatibility, but only prevents an AA from *defining* such an asset itself:
```
if (payload.cosigned_by_definer !== false)
    return cb2("cosigned_by_definer must be false because AA can't cosign");
``` [3](#0-2) 
```
if (objValidationState.bAA) {
    if (payload.cosigned_by_definer !== false)
        return callback("cosigned_by_definer must be false because AAs can't cosign");
``` [6](#0-5) 

Nothing stops any ordinary (non-AA) address from defining an asset with `cosigned_by_definer: true` via a standard `asset` message [7](#0-6) , and nothing stops such an asset from being deposited into any AA's balance — the deposit-side payment message is authored by the depositing user(s), who can trivially include the definer as a co-author to satisfy the check. Once the coins sit in the AA's balance, `balance[asset]` will reflect them, and any AA-composed `payment` message attempting to move them elsewhere will always fail the `cosigned_by_definer` check at validation time, causing the AA response to bounce (`return cb("must be cosigned by definer")` analog inside `handleTrigger`'s message composition / validation path), with no way to ever complete the transfer.

### Impact Explanation
Any user (an unprivileged AA trigger sender) can create a `cosigned_by_definer: true` asset and send it to any target AA (e.g. as part of a trigger payment, or simply as a direct payment to the AA's address, cosigned by the definer to pass the deposit-side check). The AA has no built-in way of ever authorizing an outgoing payment for that asset, so those units are permanently locked in the AA's balance — a straightforward AA-fund-freezing bug for any AA that accepts arbitrary/attacker-specified assets as deposits (e.g. generic multi-asset exchange, wrapping, or vault-style AAs), and it can also be leveraged to grief an AA into perpetually bouncing responses if the AA's logic attempts (and fails) to forward such an asset out.

### Likelihood Explanation
Likelihood is high for any AA that accepts arbitrary user-chosen assets without restricting which asset definitions it will handle (which is common, since AAs generally read `trigger.data.asset` or iterate `balance[...]` for arbitrary asset strings). Creating the malicious asset and depositing it costs only the standard asset-definition and payment fees — no privileged access is required.

### Recommendation
When an AA is about to accept or forward an asset in a payment message (deposit or response), check `objAsset.cosigned_by_definer` for any asset the AA might issue payments for and refuse operations (or refuse to update/read balances for) assets with `cosigned_by_definer: true`, since the AA can structurally never emit a valid payment for them. Alternatively, extend AA-related documentation/tooling (and possibly protocol validation for triggers) to reject deposits of `cosigned_by_definer: true` assets into AA addresses, mirroring the existing restriction that already forbids AAs from *defining* such assets.

### Proof of Concept
1. User A defines an asset `X` with `cosigned_by_definer: true`, `definer_address = A`.
2. User A and User B (jointly authoring a unit, or User A sending to themselves then onward) send a `payment` message transferring units of `X` to AA address `Z`, with both `A` (definer) and the payer as co-authors — this passes `validatePayment`'s `cosigned_by_definer` check since `arrAuthorAddresses` includes `A`.
3. AA `Z`'s `balance[X]` now reflects the deposited units.
4. Any subsequent trigger that causes `Z` to attempt `{app: 'payment', payload: {asset: X, outputs: [...]}}` produces a response unit authored solely by `Z` (`authors: [{address: Z}]`), failing `objAsset.cosigned_by_definer && arrAuthorAddresses.indexOf(objAsset.definer_address) === -1` because `A` is not `Z` and cannot be added as a co-author of an AA response unit (`validateAuthors` enforces `arrAuthors.length !== 1` throws for AAs).
5. The response bounces indefinitely; the `X` units held at `Z` can never be withdrawn by any trigger.
