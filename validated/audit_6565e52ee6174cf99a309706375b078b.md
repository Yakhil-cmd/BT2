### Title
`review_stacks_enabled` is not enforced for `allow_with_label`/`prevent_with_label` provisioning due to `&&`/`||` precedence - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` intends `repository.review_stacks_enabled` to gate all review-stack auto-provisioning, but because `&&` binds tighter than `||` in Ruby, it only gates the `provisioning_behavior_allow_all?` branch. When `review_stacks_enabled == false` and `provisioning_behavior == 'allow_with_label'`, an attacker-controlled label on the pull request still causes `provision?` to return `true`, triggering `ReviewStack` creation via `ReviewStackAdapter#find_or_create!`. `ReopenedHandler#unarchive?` has the identical flaw.

### Finding Description
The broken binding: `repository.review_stacks_enabled == false` is expected to imply `provision? == false` for *every* repository, regardless of `provisioning_behavior`. In code: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby operator precedence, this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

The `review_stacks_enabled` flag only participates in the first disjunct. If `review_stacks_enabled == false`, `provisioning_behavior == 'allow_with_label'`, and `pull_request_has_provisioning_label?` is true (labels come straight from the webhook payload's `pull_request.labels` array, fully attacker-influenced content within their own PR), the second disjunct alone makes `provision?` true, and `respond_to_pull_request_opened?` proceeds to call `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack`, a `PullRequest` record, and enqueues `ReviewStackProvisioningQueue`, ultimately leading into the `Command`/deploy pipeline for that stack's environment. The same defect exists verbatim in `ReopenedHandler#unarchive?`: [2](#0-1) 

By contrast, `LabeledHandler` correctly ANDs `repository.review_stacks_enabled` as a top-level gate in `respond_to_label_change?`, outside of `archive?`/`unarchive?`: [3](#0-2) 

confirming the intended semantics and that `OpenedHandler`/`ReopenedHandler` diverge from it.

`pull_request_has_provisioning_label?`/`pull_request_label_names` trust the payload's label names verbatim: [4](#0-3) 

Existing guards do not prevent this: `WebhooksController#verify_signature` only authenticates that the webhook body genuinely originated from GitHub for the target repository/organization via HMAC — it says nothing about who added labels or what `review_stacks_enabled` is set to, so it does not close this gap. The `ExplicitParameters` schema only validates types/shape of `labels`, not their values.

The label-authorization aspect of the question (whether an unprivileged PR author can self-apply arbitrary labels on their own PR) is a GitHub-side permission model question outside this engine's code — GitHub generally restricts label mutation to users with triage/write access to the base repository, so it cannot be verified or refuted purely from this codebase. However, this does not change the underlying finding: the precedence bug independently breaks the `review_stacks_enabled` kill-switch for any actor capable of getting a matching label onto the PR (label author with write access, bot integrations, or GitHub Actions with a token), and is a genuine logic bug in the engine's own authorization/gating code.

### Impact Explanation
Any repository configured with `review_stacks_enabled: false` and `provisioning_behavior: 'allow_with_label'` (or `'prevent_with_label'`, via the third disjunct, which is unconditional on `review_stacks_enabled` too) will still provision (or fail to prevent provisioning of) `ReviewStack`s from pull request webhooks, contrary to the operator's explicit intent to disable review stacks. This causes stack/`PullRequest` records to be created and the provisioning queue populated for a repository whose administrator explicitly disabled the feature — an unauthorized deploy/provisioning action being taken against that repository's configuration. This matches "an unauthorized deploy... or a record written for a repository that did not authenticate it" under the Critical category, scoped to repositories using `allow_with_label`/`prevent_with_label` with `review_stacks_enabled: false`.

### Likelihood Explanation
Requires: `review_stacks_enabled == false`, `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`), and knowledge of `provisioning_label_name` (visible in the repository settings UI, `app/views/shipit/repositories/settings.html.erb`) combined with the ability to attach that label to a PR against the target repository. The webhook itself is a legitimate GitHub-signed event (no signature forgery needed) as long as the label/PR event genuinely occurs. Whether an *unprivileged* external contributor can add labels to their own PR depends on the target repository's GitHub permission settings, which is outside this engine and not verifiable here.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (existing suite location for this handler): create a `Shipit::Repository` fixture/record with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'ship-it'`. Build a payload with `pull_request.labels = [{ name: 'ship-it' }]` and `action: 'opened'`. Call `OpenedHandler.new.call(params)` (or `.process`) and assert that `Shipit::ReviewStack.where(environment: "pr#{number}")` now exists — i.e., a stack was created despite `review_stacks_enabled == false`. Assert both sides of the binding explicitly: `repository.review_stacks_enabled` is `false` while `Shipit::ReviewStack.exists?(environment: "pr#{number}")` is `true`, proving the flag was not honored.
