## Title
AA payments in custom assets ignore transferability/condition restrictions at composition time, causing permanent fund freezing - (File: `aa_composer.js`)

### Summary
This is a valid ocore analog to the external "non-compliant token" report. The Trail-of-Bits finding describes how Balancer proxies assume any integrated token behaves like a compliant ERC20 (accepts 0-value transfers, returns a boolean), and a non-compliant "custom token" can break that assumption and cause fund loss. In ocore, any account (including a malicious one) can define a custom **asset** with arbitrary `is_transferrable`, `cosigned_by_definer`, `spender_attested`, and `transfer_condition` properties, as validated in [1](#0-0)  and [2](#0-1) . Autonomous Agents that generically accept and later re-pay arbitrary user-supplied assets (a documented, supported pattern — see [3](#0-2)  and [4](#0-3) ) implicitly assume the asset is freely transferable like the base currency. `aa_composer.js`, which is responsible for composing AA response payments, does not verify this assumption before building a payment message.

### Finding Description
When an AA composes an outgoing payment message for a non-base asset, `completePaymentPayload`'s asset-loading step only checks two properties of the asset — `fixed_denominations` and `is_private` — before proceeding to actually build inputs/outputs: [5](#0-4) 

It never checks `objAsset.is_transferrable`, `objAsset.cosigned_by_definer`, `objAsset.spender_attested`, or `objAsset.transfer_condition`. These are exactly the properties that later gate whether the payment is actually valid, enforced in `validatePaymentInputsAndOutputs`: [6](#0-5) 

Because an AA author (`authors: [{ address: address }]`, single-signer with no cosigners) can never satisfy `cosigned_by_definer` for an asset it doesn't define, and can never satisfy an attacker-chosen `transfer_condition` that depends on facts the AA cannot control (e.g., a `seen`/`attested`/`in data feed` condition tied to the definer, or an `is_transferrable=false` restriction limited to the definer address), an AA that accepts a deposit in such an asset (crediting its internal balance/state, e.g. via `updateFinalAABalances`, [7](#0-6) ) can become permanently unable to ever construct a valid outgoing payment of that same asset. The deposit is nevertheless accepted and reflected in AA state/balance since the *incoming* payment into the AA is validated once, normally, by the sender — the AA composer has no way to know in advance, when accepting the trigger, that its own future payout branch will always fail.

### Impact Explanation
Any user who deposits such a maliciously (or simply non-cooperatively) defined asset into a generic AA pool/exchange/vault that supports arbitrary assets (the pattern is explicitly supported by oscript, see the market-maker and asset-creation samples) can cause:
- The AA's balance/state accounting for that asset to become permanently unspendable, since every attempt to pay it back out gets bounced by `completePaymentPayload`/`validatePaymentInputsAndOutputs`.
- Funds deposited by the attacker (and potentially other users pooled with the same asset, e.g. in an AMM) to be permanently frozen inside the AA, since the AA has no code path to detect or reject such an asset before crediting it.

This matches the "AA fund loss or freezing" impact category: it is a direct, deterministic consequence of the ocore composer's implicit assumption that any asset it is instructed to pay out behaves like the base currency (freely transferable by a single signer), which — just like the Balancer/ERC20 assumption — is not guaranteed by the underlying primitive (an ocore custom asset with `transfer_condition`/`cosigned_by_definer`/`is_transferrable=false`).

### Likelihood Explanation
Likelihood is Medium: it requires (1) an AA that accepts/pools arbitrary user-supplied assets (a documented, encouraged oscript pattern), and (2) an attacker to define (or already control) an asset with a restrictive `transfer_condition`/`cosigned_by_definer`/`is_transferrable` and then deposit it into such an AA. No special privileges beyond ordinary asset issuance and unit posting are required — asset definitions and AA triggers are both permissionless.

### Recommendation
- Short term: Document that AAs which generically accept arbitrary assets must explicitly check `asset[..].is_transferrable`, `spender_attested`, `cosigned_by_definer`, and refuse assets with a `transfer_condition` (or verify it is satisfiable by a single-author AA-signed unit) before crediting balances, since ocore does not protect them.
- Long term: Have `aa_composer.js`'s `completePaymentPayload` (around [8](#0-7)  ) proactively check `is_transferrable`, `cosigned_by_definer`, and the presence of a `transfer_condition` for any non-base asset being paid out by an AA, and bounce early with a clear error rather than silently accepting the deposit and later being unable to pay it back.

### Proof of Concept
1. Attacker defines an asset via a normal `asset` message with `is_transferrable: true` for their own address, `cosigned_by_definer: true` (only affects non-AA-issued assets; an ordinary account can set this), or a `transfer_condition` such as `['seen', {what:'input', address:'<attacker>', type:'issue'}]` — a condition the target AA's single-author, deterministically generated response unit can never satisfy.
2. Attacker sends a trigger unit to a pool/exchange AA (e.g. the pattern in `uniswap_like_market_maker.oscript`) depositing this custom asset; the AA's `trigger.output[[asset=$asset]]` credit path updates its internal state/balance as usual (`aa_composer.js` `updateFinalAABalances`).
3. When the AA (or another user) later triggers a withdrawal/payout of this asset, `completePaymentPayload` in `aa_composer.js` composes the payment (it does not check `cosigned_by_definer`/`transfer_condition`), but the resulting unit fails `validatePaymentInputsAndOutputs`'s condition/cosigning check in `validation.js`, so the payout branch can never complete — the asset balance is stuck in the AA permanently.
