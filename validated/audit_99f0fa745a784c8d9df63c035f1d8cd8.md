## Title
Unauthenticated / cross-organization forgery of commit statuses via `WebhooksController` breaks the "authenticated organization = repository written" binding, enabling unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

## Summary
`WebhooksController#verify_signature` selects the HMAC secret to check based on the organization named in the incoming payload (`repository.owner.login`, falling back to `organization.login`), and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization. The event is then dispatched to handlers with the *raw, attacker-controlled* JSON body. `Handlers::StatusHandler#process` writes a `Status` onto any `Commit` matched purely by the `sha` field of that payload, with no scoping to the repository/organization that (if at all) was authenticated. This breaks the equality "organization whose signature was verified == repository/stack whose commit is written," letting an external, unprivileged party forge CI results for any commit tracked by the Shipit instance, which can drive an unauthorized deploy through continuous delivery.

## Finding Description
Two independent gaps compound into the same binding violation:

1. **No default authentication.** `GitHubApp#verify_webhook_signature` returns `true` immediately `unless webhook_secret` [1](#0-0)  . The `webhook_secret` is explicitly documented and shipped as optional/nil in every default config (`test/dummy/config/secrets.yml`, `template.rb`, `docs/setup.md`) [2](#0-1) [3](#0-2) . So for the (documented, common) case where an organization has no `webhook_secret` configured, `WebhooksController#verify_signature` accepts **any** request for that organization with **any** or no `X-Hub-Signature` value [4](#0-3) .

2. **No repository scoping on write.** Even when a real, valid signature is required for one organization (e.g. in a multi-org deployment as documented in `docs/setup.md:182-209`), the org selected for signature verification is derived only from `repository.owner.login`/`organization.login` [5](#0-4) , while the handler that performs the actual write never re-checks that binding. `Handlers::StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [6](#0-5) 
This is a **global** lookup by `sha` across the entire `commits` table — it is not scoped to the `repository.full_name` in the payload, nor to the organization that produced the (possibly-verified) signature. Any organization/app whose webhook is accepted (including one with no secret at all) can therefore forge a state/description/context/target_url for a commit belonging to a completely different, unrelated stack/repository tracked by the same Shipit instance.

The binding broken, stated as an equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `repository/stack whose Commit#status is mutated by StatusHandler`

Before the attacker's request: only the real GitHub organization owning a commit can produce a status for it (via GitHub Actions/CI reporting to its own webhook). After the attacker's request: an unrelated party (or literally anyone, given a secret-less org) can set that same commit's status.

## Impact Explanation
`Commit#create_status_from_github!` feeds directly into `Commit#deployable?`/`#status` and can flip a commit from failing/pending CI to `success` [7](#0-6) . Since `deployable?` and continuous delivery scheduling react to `success`/`pending` transitions (`stack.schedule_merges if new_status.pending? || new_status.success?`), a forged "success" status on a victim stack's undeployed commit can make Shipit believe CI passed and either allow a human "Create deploy" click to proceed, or, on stacks with continuous deployment enabled, trigger an actual automatic deploy of code that never really passed the victim's CI checks. This matches the report's severity class ("unfair/incorrect distribution/outcome due to a broken binding") but maps onto this engine as an **unauthorized deploy** primitive — one of the explicitly accepted Critical impacts.

## Likelihood Explanation
High. The webhook endpoint is public and unauthenticated by design (it must accept unauthenticated POSTs from GitHub); the only gate is `verify_signature`. Any Shipit deployment following the documented default configuration (webhook secret optional, as shown in every shipped example config) has zero real verification for status/push/membership events targeting that organization. Even where a secret is configured, the `StatusHandler` lookup is unconditionally global, so cross-repository status forgery works with any valid webhook secret for any onboarded organization — no GitHub App private key, `ApiClient` token, or `Shipit` session is required, satisfying the "unprivileged attacker" constraint.

## Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than defaulting to "verified" when absent, in `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb`).
- Scope `Handlers::StatusHandler#process` (and any other handler using an unscoped `Commit`/global lookup) to the repository named in the same payload that was authenticated, e.g. restrict to `commit.stack.repository.github_repo_name == payload.dig('repository','full_name')`, mirroring the `stacks`/`repository_name` helper already defined on `Handler` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`).
- Add a regression test asserting that a status payload naming repository A cannot alter a commit's status when that commit belongs to repository B, even with a valid signature for A.

## Proof of Concept
Given a multi-tenant Shipit instance tracking `victim-org/victim-repo` (stack with an undeployed commit `SHA_V` currently `pending`/`failure`) and `attacker-org/attacker-repo` (an organization configured with **no** `webhook_secret`, per the documented default):

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (ignored, no secret configured for attacker-org)

{
  "sha": "SHA_V",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```

- `WebhooksController#repository_owner` resolves to `attacker-org` [5](#0-4) .
- `Shipit.github(organization: 'attacker-org').verify_webhook_signature` returns `true` unconditionally because `attacker-org` has no `webhook_secret` [1](#0-0) .
- `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which finds `Commit` by `sha == "SHA_V"` — regardless of the fact the payload's `repository.full_name` is `attacker-org/attacker-repo`, not `victim-org/victim-repo` — and writes a `success` status onto it [6](#0-5) .
- `victim-org/victim-repo`'s commit `SHA_V` is now marked `success`, potentially unblocking a deploy/merge that was never actually validated by the victim's real CI.

Note: I was unable to fully trace whether `Commit#create_status_from_github!`/`Status` validations impose any additional repository check (index size limits meant `app/models/shipit/status.rb` internals weren't retrieved), but the `StatusHandler.process` query itself is confirmed unscoped, which is sufficient to establish the binding break.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
