### Title
Cross-repository commit status forgery via unscoped `StatusHandler` webhook lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's `status` webhook handler updates a commit's CI status by looking up commits **only by SHA, with no repository/organization scoping**, even though the webhook signature that authorizes the request is verified against the organization derived from the payload's `repository.owner.login`. This breaks the binding: *"organization authenticated" == "repository written"*. An actor able to deliver a validly-signed `status` event for any organization/repository configured in the Shipit instance can flip the CI status of a commit belonging to a **completely different stack/repository**, as long as the SHA happens to match (a very plausible collision for mirrored/forked repos, cherry-picks, or shared history). This can force a target commit's status to `success`, which feeds directly into merge-queue gating and continuous-deployment triggers.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp`/secret to validate the signature against using the *organization derived from the payload*: `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1) 

Once the signature is validated for *that organization*, the raw payload is dispatched to handlers registered for the event type: [3](#0-2) 

The base `Handler` class provides a properly scoped `stacks` helper that filters by the repository named in the payload: [4](#0-3) 

Nearly every handler uses this repository-scoped lookup — for example `CheckSuiteHandler` scopes strictly to `stacks.where(branch: ...)`: [5](#0-4) 

However, `StatusHandler#process` bypasses this scoping entirely and queries `Commit` globally by SHA across **every stack in the Shipit instance**, then mutates its status: [6](#0-5) 

The equality that should hold is:
`organization authorized by signature (repository.owner.login in payload) == repository/stack whose commit gets its status mutated`

Before the attacker's request: commit status writes are gated only by whichever organization's secret happened to sign the request, with no cross-check that the commit being modified belongs to that organization's repository.
After the attacker's request: any commit in the database sharing the targeted SHA — regardless of which stack/repository it belongs to — has its status overwritten, because `Commit.where(sha: params.sha)` has no `stack_id`/`repository_id` filter.

This status write is not inert: `Commit#create_status_from_github!` → `add_status` re-evaluates `simple_state` transitions and can trigger `stack.schedule_merges` (feeding the merge-request pipeline) and `Hook.emit(:deployable_status, ...)`: [7](#0-6) 

`MergeRequest#reject_unless_mergeable!` and `#all_status_checks_passed?` rely directly on these `Status` records to decide whether a pull request in the merge queue is CI-green and eligible to merge: [8](#0-7) 

And `Status` records also trigger continuous-delivery scheduling via `after_commit :schedule_continuous_delivery`: [9](#0-8) 

### Impact Explanation
By forging (or otherwise legitimately delivering) a `status` webhook signed for organization/repository A, an attacker can inject a fabricated `success` status for a commit SHA that also exists in stack/repository B (owned by an unrelated organization), without ever needing repository write access, an `ApiClient` token, or B's webhook secret. Since `Status` rows drive `MergeRequest#all_status_checks_passed?`/`reject_unless_mergeable!` and continuous-delivery scheduling, this can push a commit through Shipit's merge queue or trigger an automated deploy that GitHub itself never certified as passing CI for that repository — an unauthorized merge/deploy crossing a repository trust boundary, matching the "cross-repository writes / unauthorized deploy or merge" impact bar.

### Likelihood Explanation
Exploitability depends on the operator having configured more than one GitHub organization in `Shipit.secrets.github` (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`) and on SHA collision/reuse across stacks (realistic for mirrored repos, monorepo splits, cherry-picked/rebased shared commits, or repos with shared upstream history). This narrows the practical blast radius versus a fully generic bypass, but the root cause — `StatusHandler` not scoping to `repository_name` while every sibling handler does — is a clear, code-level defect independent of any particular deployment quirk.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: restrict the `Commit` lookup to `stacks` (i.e., commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`), for example:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the invariant that the organization authorizing the webhook is the same repository whose commit state is mutated.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `OrgA` and `OrgB`, each tracking its own stack (as supported per `docs/setup.md` multi-org config).
2. Ensure a commit with SHA `deadbeef...` exists in both `OrgA/repo-a`'s stack and `OrgB/repo-b`'s stack (e.g., shared upstream history, fork, or cherry-pick — common in mirrored/monorepo setups).
3. Have GitHub (or an entity with only push access to `OrgA/repo-a`, no access to `OrgB/repo-b`) deliver a `status` webhook event for `OrgA/repo-a` with `sha=deadbeef...` and `state=success`, signed with `OrgA`'s webhook secret.
4. `WebhooksController#verify_signature` validates the signature against `OrgA`'s secret and passes.
5. `StatusHandler#process` executes `Commit.where(sha: 'deadbeef...')`, which matches the commit row belonging to `OrgB`'s stack, and calls `create_status_from_github!`, marking it `success` for `OrgB`'s repository even though no `OrgB`-authorized signal ever occurred.
6. If a pull request in `OrgB`'s merge queue is pending on that commit's CI status, `MergeRequest#reject_unless_mergeable!` now sees CI as passing and the PR can be merged/deployed without ever having a valid, repository-scoped status check.
