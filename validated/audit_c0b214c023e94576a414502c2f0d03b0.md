Confirmed: `Shipit::Api::CCMenuController#stack` overrides `BaseController#stack` and bypasses the `stacks` scoping method entirely, calling `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`.

### Title
Stack-scoped API client tokens can read CI status of any stack via the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
An `ApiClient` token can be scoped to a single `Shipit::Stack` via its `stack_id` association, meant to restrict the client to `read:stack`/etc. operations on only that stack. `Shipit::Api::BaseController#stack` enforces this by resolving the stack through the scoped `stacks` relation. `Shipit::Api::CCMenuController` overrides `#stack` to bypass this scoping, allowing any authenticated client (even one narrowly scoped to an unrelated stack) to read build/deploy status for arbitrary stacks.

### Finding Description
`Shipit::Api::BaseController` defines the trust binding between an `ApiClient` token and the stacks it is authorized to touch: [1](#0-0) 

`stacks` restricts the relation to `current_api_client.stack_id` when the client is scoped; `stack` then resolves `params[:stack_id]` only within that restricted relation, so a scoped client cannot address a stack outside its `stack_id`. Every other API controller (`StacksController`, `TasksController`, `MergeRequestsController`, `CommitsController`, `HooksController`) relies on this inherited `stack`/`stacks` implementation for authorization scoping.

`CCMenuController`, however, redefines `stack` to resolve directly against the unscoped `Stack` model: [2](#0-1) 

This method completely discards the `current_api_client.stack_id` restriction. `require_permission :read, :stack` only checks that `"read:stack"` is present in the token's `permissions` list — it never checks *which* stack the operation targets: [3](#0-2) 

The binding that breaks, expressed as an equality that should hold but doesn't:
`stacks_the_token_is_authorized_for == stacks_the_request_can_touch`

Before the flaw is exploited: `current_api_client.stack_id` (e.g. Stack A) equals the set of stacks reachable through `BaseController#stack`.
After hitting `CCMenuController#show`: the reachable stack is whatever `params[:stack_id]` names — any stack in the entire installation, because `Stack.from_param!` is unscoped. The test fixture confirms scoped clients exist precisely to be constrained this way: [4](#0-3) [5](#0-4) 

The existing CCMenu tests only exercise the token's own stack and never assert the scoping restriction, so the bypass is untested: [6](#0-5) 

### Impact Explanation
This grants unauthenticated-for-that-resource read access: a credential intentionally scoped to one repository/stack (e.g. issued to a low-trust integration such as a CI status badge or dashboard) can read `lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status, and activity for **every** stack in the Shipit installation, including private/unrelated repositories it was never granted access to. This matches the "High" impact category: escalation past the authorization boundary to unauthenticated read of stack state/build/deploy status across repositories the token was not provisioned for.

### Likelihood Explanation
High likelihood: exploitation requires only a single valid, low-privilege, stack-scoped API token (the exact kind Shipit's own documentation and UI encourage administrators to issue for limited-trust integrations) and a single unauthenticated-parameter HTTP GET with a different `stack_id`. No race conditions, timing, or special preconditions are needed — the scoping check is simply never invoked on this code path.

### Recommendation
Remove `CCMenuController`'s override of `#stack` (or reimplement it using the inherited `stacks` scope, e.g. `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot address stacks outside their assigned `stack_id`. Add a regression test asserting that a client scoped to Stack A receives a 404/403 when requesting CCMenu output for Stack B.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus`, scoped via `stack: shipit`).
2. As that client, issue: `GET /api/stacks/<owner-b>/<repo-b>/<env-b>/cc.xml?token=<clientA_token>` where `owner-b/repo-b/env-b` identifies an unrelated Stack B the client was never granted access to.
3. Observe `assert_response :ok` with the XML containing Stack B's `lastBuildStatus`, `webUrl`, etc. — proving the `stack_id` scoping enforced elsewhere (`test/controllers/api/stacks_controller_test.rb:217-223`) is not enforced for the CCMenu endpoint (`app/controllers/shipit/api/ccmenu_controller.rb:27-31` bypasses `app/controllers/shipit/api/base_controller.rb:74-80`).
