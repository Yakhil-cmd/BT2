### Title
Webhook signature verified against the org derived from `repository.owner.login`, but push-sync handler trusts the unrelated `repository.full_name` field to select the target stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, a value read out of the untrusted, attacker-supplied JSON payload itself (`params.dig('repository', 'owner', 'login')` or `organization.login`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` independently re-reads `payload.dig('repository', 'full_name')` to decide which `Repository`/`Stack` the event applies to. Nothing binds these two fields together, so a signature that is only valid for organization A's webhook secret can be replayed with a `repository.full_name` pointing at a stack belonging to a completely different, unrelated repository/organization B.

### Finding Description
The controller resolves the verifying secret from the payload before trusting the payload's content: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `repository.owner.login` (or `organization.login`) inside the same JSON body being verified. `Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/webhook secret configured for that specific organization (see multi-org config in `docs/setup.md`), and `verify_webhook_signature` performs an HMAC-SHA1 comparison over the raw body using that org's secret.

Separately, the generic handler base class used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. resolves the actual `Repository`/`Stack` to act on using a *different* field from the same payload: [3](#0-2) 

`repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the target stack) are never cross-checked against each other. The HMAC does cover the whole raw body, so an attacker cannot forge an arbitrary body without possessing *some* organization's configured `webhook_secret` — but once an attacker possesses (or is entitled to) the webhook secret for *any one* organization configured in `secrets.yml` (e.g., because they administer/own that org's GitHub App installation, a routine, unprivileged-relative-to-other-orgs capability in a multi-tenant Shipit deployment), they can craft a payload where:
- `repository.owner.login` == the organization whose secret they hold (so the HMAC verifies), and
- `repository.full_name` == `other-org/other-repo`, an arbitrary repository/stack hosted under a different organization also configured in the same Shipit instance.

This breaks the intended binding: *the organization that authenticated the request* should equal *the repository/stack that gets written to*. Instead, the authenticated org and the acted-upon repository are two independently attacker-controlled fields inside the same signed blob, with no engine-side equality check between them.

### Impact Explanation
Using this gap with the `push` event, `Shipit::Webhooks::Handlers::PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` for any stack whose repository matches the forged `full_name`, even though the request was only authenticated for a different, unrelated organization. This enqueues `GithubSyncJob`, which fetches commits from GitHub for that stack and appends them, and can trigger `CacheDeploySpecJob` and downstream deploy-spec caching for a repository outside of the org the attacker actually controls. Depending on which stacks exist cross-organization in the same Shipit deployment, this allows an attacker who only controls one tenant's webhook secret to force sync/cache activity — and by extension influence deployable commit tracking — for a stack belonging to a repository/org they have no legitimate relationship with, i.e., a cross-repository write triggered under someone else's binding, matching the "organization authenticated vs. repository written" boundary the task calls out.

### Likelihood Explanation
This requires the attacker to hold a valid `webhook_secret` for at least one organization configured in the Shipit instance (a realistic scenario for a multi-tenant/self-hosted Shipit deployment where multiple GitHub orgs each have their own `github` section under `config/secrets.yml`, as documented). No repository write access, API token, or Shipit session is required beyond that — only the ability to send an HTTP POST with a validly-signed body for their own org's secret while filling in someone else's `repository.full_name`. This is a plausible, code-reachable analog of the audit report's core pattern (a value trusted/acted-upon differs from the value actually validated), though full exploitability depends on the operator having configured more than one organization's secret in the same instance, which I could not further verify beyond the documented `docs/setup.md` multi-org example.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler`, enforce that `repository.owner.login`/`organization.login` (the value used to select the verifying secret) equals the owner segment of `repository.full_name` (the value used to resolve the target `Repository`/`Stack`) before processing the event, rejecting the request with `422` if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`, e.g. `orgA` (attacker-controlled webhook secret) and `orgB` (victim org with an existing stack for `orgB/victim-repo`).
2. Attacker crafts a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `orgA`'s `webhook_secret` over the exact raw JSON body and POSTs to `/github/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")` and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves the stack via `Repository.from_github_repo_name("orgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for `orgB`'s stack, despite the request only being authenticated for `orgA`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
