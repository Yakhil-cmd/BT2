### Title
Asset definer can arbitrarily replace the attestor list of a `spender_attested` asset, freezing previously-attested holders' funds - (File: `validation.js`, `storage.js`)

### Summary
This is the same bug class as the reported `StakingVault.setStakedAmountLimit` issue: an authority-controlled configuration value is changed with **no validation that the change is compatible with users who already relied on the old value**, and the strict enforcement check downstream then blocks legitimate, unrelated users from moving/using funds they already hold. In ocore, the analogous "limit" is the **attestor list of a `spender_attested` asset**. The asset definer can publish a new `asset_attestors` message that completely replaces the current attestor set, and the validation code only ever consults the *single latest* attestor-list unit. Holders who were validly attested under the old list, and who already hold balances of the asset, instantly lose the ability to transfer, receive change, or otherwise move those funds once the new list is stable — exactly analogous to users who already staked being unable to unstake after the limit is lowered.

### Finding Description
`spender_attested` assets require that every author (and, for non-transferrable/transfer checks, every output address) be attested by one of the asset's current attestors before a payment is accepted: [1](#0-0) 

For divisible-asset transfer inputs and private fixed-denomination inputs, the same check is applied against the *currently owned* coin's address: [2](#0-1) [3](#0-2) 

And even output addresses (e.g. change sent back to oneself) must be attested under the current list: [4](#0-3) 

The attestor list itself can be updated at any time by the asset definer through an `asset_attestors` message, and this update is validated with essentially no constraint besides "sender is the definer" and "list is well-formed" — there is no check that previously-attested, currently-holding addresses remain covered: [5](#0-4) [6](#0-5) 

Crucially, when the current attestor list is read for validation/composition, only the **single most-recent** `asset_attestors` unit is used — it is a full replacement, not an additive/merged set: [7](#0-6) 

and matching addresses against that (now-replaced) attestor set is what determines who is "attested": [8](#0-7) 

`asset_attestors` is also a valid AA message type, so an AA that manages a `spender_attested` asset can itself trigger such a replacement (e.g., in response to a trigger), making this reachable both from a plain single-authored unit poster (the definer) and from AA logic: [9](#0-8) 

This mirrors the `StakingVault.setStakedAmountLimit` bug exactly: a config value (`stakedAmountLimit` → attestor list) is mutated by its administrator (`auth` → asset definer) with no validation against existing state (already staked amount → already-attested existing holders), and a strict `require`/`return callback(...)` check downstream (`stakedAmount <= stakedAmountLimit` → `arrAttestedAddresses.indexOf(owner_address) === -1`) then permanently blocks legitimate unrelated users from acting on funds they already hold, with no way to remedy the situation unilaterally (a User in ocore cannot re-attest themselves; a staker in the report could at least reduce their own stake, but here the disenfranchised token holder is entirely dependent on the definer/attestor to be re-attested).

### Impact Explanation
Once a new `asset_attestors` unit stabilizes and drops/replaces the attestors that had attested an existing holder, that holder's coins of the asset become **permanently unspendable** — they can't be transferred, they can't be sent back to the holder as valid change, and they can't be issued further to that address, until (if ever) the same or a cooperating attestor re-attests them under the new list. This is a direct fund-freezing condition for the asset, equivalent to the "AA fund loss or freezing" class when the asset is managed by an AA (a common pattern for compliance/whitelisted tokens), and more broadly a denial of a previously-valid economic right over already-owned, stable outputs.

### Likelihood Explanation
The action requires nothing more than the asset definer (or an AA definer for an AA-managed asset) publishing a single, syntactically valid `asset_attestors` message — no special permission beyond being the asset's own definer, which is the expected and routine way attestor lists are maintained ("must subsequently publish and update the list of trusted attestors" per the schema comment). Any change of attestor set that doesn't happen to include every previously-attesting attestor, or that is used carelessly/maliciously, will trip this condition. Given attestor rotation and compliance-driven list changes are the expected use case for this feature, accidental triggering is realistic; deliberate use by a malicious/negligent definer is also possible.

### Recommendation
When a new `asset_attestors` list is validated/applied, do not simply replace the previous list outright when checking whether *already-attested existing holders* remain able to transact. Options:
- Track attestations against the historical list that was in effect when the attestation was made (similar to how `filterAttestedAddresses` already looks at `address_definition_changes` for staleness), instead of only the single latest attestor unit.
- Require that address-attestation checks succeed if the address was attested by *any* attestor list that was valid at the time the coin was created/received, not only the current one.
- At minimum, document/require that attestor-list changes should be additive-only (union) rather than a full replace, mirroring the fix pattern used for `stakedAmountLimit` (validate the new state against existing commitments before accepting the change).

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true`, initial `attestors: [X]` (`validateAssetDefinition`, `writer.js` inserts into `asset_attestors`).
2. Attestor `X` publishes an `attestation` message attesting `User1`.
3. Under this list, `User1` is attested (`filterAttestedAddresses` returns `User1`). `User1` receives/holds a balance of asset `A` via a normal payment.
4. Definer `D` later publishes a new `asset_attestors` message for asset `A` with `attestors: [Y]` (replacing `X`) — this passes `validateAttestorListUpdate` (`validation.js:2829-2848`) with no check against existing holders.
5. Once this unit stabilizes, `readAsset`'s `addAttestorsIfNecessary` (`storage.js:1917-1946`) resolves the current attestor set to `[Y]` only (the query picks the single latest `asset_attestors` unit).
6. `User1` attempts to send/transfer their existing balance of asset `A`. `filterAttestedAddresses` no longer includes `User1` (attested only by `X`, not `Y`), so:
   - Divisible transfer: `validation.js:2506` returns `"owner address is not attested"`.
   - Private fixed-denomination transfer: `validation.js:2432` returns `"owner address is not attested"`.
   - Even sending change back to self as an output on a payment fails at `validation.js:2634-2641` `"some output addresses are not attested"`.
7. `User1`'s previously legitimately-held, already-stable balance of asset `A` is now permanently frozen and cannot be moved unless attestor `Y` (or `X` again, via another list update by `D`) chooses to attest `User1` — a decision entirely outside `User1`'s control, exactly mirroring the original report's scenario where User2's already-staked tokens became unwithdrawable purely due to an administrator changing a limit with no regard for existing commitments.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
