### Title
Webhook organization used for signature verification is decoupled from the repository the handler acts on, allowing cross-repository status/push forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a webhook against using `repository_owner`, taken from the unauthenticated JSON body itself (`repository.owner.login`, falling back to `organization.login`). Once that signature check passes, the webhook handlers (`PushHandler`, `StatusHandler`, etc.) act on a completely different field of the same body — `repository.full_name` for push, or nothing at all for status (a bare `sha`) — to decide which `Stack`/`Commit` to mutate. The signature therefore proves only "this payload was signed with organization X's secret," but never proves that organization X owns the repository/commit the handler subsequently touches.

### Finding Description
In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

This is a per-organization lookup (`lib/shipit/github_app.rb`), meaning a Shipit instance configured with multiple GitHub Apps/organizations (documented in `docs/setup.md`, "Using Multiple Github Applications") has an independent `webhook_secret` per org. Critically, `webhook_secret` is optional and `verify_webhook_signature` returns `true` unconditionally when it is blank:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [3](#0-2) 

After signature verification succeeds for organization X (either because the attacker legitimately knows/controls X's secret, or because X's `webhook_secret` was left unset — the documented/templated default, see `config/secrets.development.shopify.yml`), the event is dispatched to handlers that resolve the *target* repository from a different, independently-controlled field in the same payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` uses this to trigger a `GithubSyncJob`/sync for any stack matching `full_name`: [5](#0-4) 

`StatusHandler` is even less scoped — it does not consult repository/organization at all, matching purely on commit SHA across the entire install:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 

Nowhere is `repository.owner.login`/`organization.login` (the value used to pick the verifying secret) cross-checked against `repository.full_name` or the commit's actual repository. The binding that should hold — *organization whose secret verified the signature* == *organization/repository the handler mutates* — is broken.

### Impact Explanation
An attacker who legitimately administers (or otherwise possesses the webhook secret for, including the common case of an unset/blank secret) any single GitHub organization onboarded to a shared, multi-tenant Shipit instance can forge a `status` or `push` webhook whose signature validates against their own organization, while its `repository.full_name` (push) or `sha` (status) targets a stack belonging to a completely unrelated victim organization/repository on the same instance. For `status`, this lets the attacker fabricate a passing CI status (`state: success`) for an arbitrary commit SHA belonging to the victim's stack, which can satisfy `ci.require`/`ci.blocking` gates used to authorize deploys and the merge queue — leading to an unauthorized deploy/merge on a repository the attacker has no legitimate access to. For `push`, it can force an out-of-band `GithubSyncJob` against a victim's stack. This crosses the "cross-repository writes / unauthorized deploy" bar (Critical).

### Likelihood Explanation
Requires a Shipit deployment configured with multiple organizations (an explicitly documented, supported configuration) and either the attacker's own organization's `webhook_secret` (which they may set themselves when installing their own GitHub App, since it's a config value chosen at app-creation time) or a organization on the instance whose `webhook_secret` was left blank (the templated/default state per `config/secrets.development.shopify.yml` and `template.rb`). Both conditions are realistic in shared/multi-tenant setups, making this moderately likely rather than purely theoretical.

### Recommendation
After signature verification selects an organization, require that `repository.owner.login` (or `organization.login`) match the organization owning the target repository/stack the handler is about to act on, for every handler — not just implicitly trust `repository.full_name` or bare `sha` lookups. For `StatusHandler` specifically, scope the `Commit` lookup by the verified repository/stack rather than matching SHA globally across all tenants.

### Proof of Concept
1. Configure (or observe) a multi-org Shipit instance where organization `attacker-org` has a known or blank `webhook_secret`, and victim commit `abcd123...` belongs to stack `victim-org/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "abcd123...",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Sign with `attacker-org`'s secret (or omit `X-Hub-Signature` entirely if that org's secret is unset).
4. `verify_signature` passes using `attacker-org`'s `GithubApp`; `StatusHandler#process` then matches `Commit.where(sha: "abcd123...")`, which belongs to `victim-org/victim-repo`, and creates a fabricated successful status on it, potentially unblocking a deploy/merge gated on that CI context.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
