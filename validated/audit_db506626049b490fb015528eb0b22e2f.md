The key facts needed are now in hand. Let me trace the exact code path.

**The truncation bug is real** — line 84 of `handler.go`:

```go

```

`uint8(256)` = `0`, so a message with `view.Round = 256` is stored under key `{N, 0}`.

**But the sender verification uses the full (untruncated) round:**

```go

```

**And the sig hash also truncates:**

```go
// recoverVRankPreprepareSender, line 219
sigHash := v.vrankPreprepareSigHash(msg.Block.NumberU64(), uint8(msg.View.Round.Uint64()), ...)
//                                                          ^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                                                          uint8(256) = 0
```

**`GetProposer(N, 256)` does NOT validate round ≤ MaxRound** — it uses plain modular arithmetic:

```go
// kaiax/valset/impl/getter_context.go, line 205
return qualified.At((prevIdx + int(round) + 1) % qualified.Len())
```

So `GetProposer(N, 256)` returns a valid validator address with no error. `MaxRound = 10` is only enforced in `HandleVRankCandidate` (line 136), **not** in `HandleVRankPreprepare`.

**The attack chain:**

1. Attacker is a validator and is `GetProposer(N, 256)` for target block N.
2. Attacker crafts a VRankPreprepare: `view.Round = 256`, `block.Hash = arbitrary_hash ≠ legitimate_hash`. Signs it over `vrankPreprepareSigHash(N, 0, arbitrary_hash)` (because `uint8(256) = 0`).
3. Candidate receives it: sig recovery uses round=0 → recovers attacker's address; sender check uses round=256 → `GetProposer(N, 256)` = attacker → **passes**. `markSeenPreprepare` stores `seenPreprepare[{N, 0}] = arbitrary_hash`.
4. Legitimate round-0 VRankPreprepare arrives with `real_hash ≠ arbitrary_hash`. `markSeenPreprepare` returns `conflictingView = true` → candidate silently drops it, never calls `BroadcastVRankCandidate`.
5. `EvaluateCandidates(N, 0)` sees no VRankCandidate from this candidate → includes it in `cfReport` → `cpMatrix.Increment(candidate, reporter)` → spurious CFS increment.

**Why this is not blocked:**

- No `view.Round > maxRound` guard in `HandleVRankPreprepare` (contrast with `HandleVRankCandidate` line 136).
- `GetProposer` accepts any round value without error.
- The sig hash and the sender-verification check use **different** round values (truncated vs. full), creating the exploitable mismatch.

**Constraint:** The attacker must be a single validator who is `GetProposer(N, 256)`. This is not majority-validator collusion — it is a single-node attack. With a validator set of size V, the attacker controls this for ≈1/V of all blocks, enabling a sustained CFS poisoning campaign against targeted candidates.

### Title
`uint8` truncation in `HandleVRankPreprepare` lets a single malicious validator poison `seenPreprepare[{N,0}]` via a round=256 message, suppressing VRankCandidate broadcasts and corrupting candidate CFS scores and KAIA reward allocation — (`kaiax/vrank/impl/handler.go`)

### Summary
`HandleVRankPreprepare` stores the seen-preprepare key using `uint8(view.Round.Uint64())`, silently truncating round 256 → 0. A validator who is `GetProposer(N, 256)` can send a crafted message that poisons `seenPreprepare[{N, 0}]` with a wrong block hash, causing the legitimate round-0 VRankPreprepare to be rejected as a conflicting view. Affected candidates never broadcast `VRankCandidate`, are marked absent in `cfReport`, and accumulate spurious CFS increments that corrupt their KAIA reward allocation.

### Finding Description

`HandleVRankPreprepare` applies `uint8()` to the 64-bit round field when building the `ViewKey` for `markSeenPreprepare`, but `verifyVRankPreprepareSender` passes the full 64-bit round to `GetProposer`. These two paths are inconsistent: [1](#0-0) 

The sig-hash computation also truncates: [2](#0-1) 

While sender verification uses the raw round: [3](#0-2) 

`GetProposer` performs no `round ≤ MaxRound` check — it accepts any round via modular arithmetic: [4](#0-3) 

`MaxRound = 10` is only enforced in `HandleVRankCandidate`, not here: [5](#0-4) [6](#0-5) 

### Impact Explanation

Once `seenPreprepare[{N, 0}]` is poisoned with a wrong hash, the legitimate round-0 VRankPreprepare triggers `conflictingView = true` and is silently dropped: [7](#0-6) 

The candidate never calls `BroadcastVRankCandidate`. `EvaluateCandidates` then includes it in `cfReport`: [8](#0-7) 

This increments `cpMatrix[candidate][reporter]`, raising the candidate's CFS score: [9](#0-8) 

A sufficiently elevated CFS score removes the candidate from the KAIA reward pool, constituting unauthorized redirection of reward assets.

### Likelihood Explanation

The attacker must be a single validator who is `GetProposer(N, 256)` for the target block. With a validator set of size V, this holds for ≈1/V of all blocks. The attack is repeatable across many blocks, enabling a sustained campaign. No majority collusion, no key compromise, and no cryptographic break is required — only a single malicious validator node sending a crafted P2P message.

### Recommendation

1. **Add a round-range guard at the top of `HandleVRankPreprepare`**, mirroring the check already present in `HandleVRankCandidate`:
   ```go
   if view.Round.Uint64() > maxRound {
       return vrank.ErrRoundOutOfRange
   }
   ```
2. **Use the full `uint64` round in `ViewKey`** (widen `ViewKey.R` from `uint8` to `uint64`), or assert that the round fits in `uint8` before truncating and return an error if it does not.
3. **Unify the round value** used in sig-hash computation and sender verification so both paths operate on the same (validated) value.

### Proof of Concept

```
Setup:
  - Validator set: [A, B, C, D] (size 4, RoundRobin)
  - GetProposer(N, 0)   = B  (legitimate round-0 proposer)
  - GetProposer(N, 256) = B  (256 % 4 = 0, same slot → same proposer)
    OR with a different set size where GetProposer(N, 256) = C (attacker)

Attack (attacker = C, proposer for round 256):
1. C crafts VRankPreprepare{block=blockN, view.Round=256, block.Hash=0xDEAD}
   sigHash = vrankPreprepareSigHash(N, uint8(256)=0, 0xDEAD)
   sig = Sign(sigHash, C.key)
2. C sends the crafted message to candidate X before B's round-0 message arrives.
3. X processes it:
   - recoverVRankPreprepareSender: sigHash uses round=0 → recovers C ✓
   - verifyVRankPreprepareSender: GetProposer(N, 256) = C → passes ✓
   - markSeenPreprepare({N, 0}, 0xDEAD) → stored
4. B's legitimate VRankPreprepare{view.Round=0, block.Hash=0xREAL} arrives.
   - markSeenPreprepare({N, 0}, 0xREAL): seenHash=0xDEAD ≠ 0xREAL → conflictingView=true
   - X drops the message, never broadcasts VRankCandidate.
5. EvaluateCandidates(N, 0) includes X in cfReport → CFS[X]++ → reward corrupted.
```
