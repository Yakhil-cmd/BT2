## Title
Webhook signature verified against organization derived from `repository.owner.login`, but event handlers route on the unbound `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from `params.dig('repository', 'owner', 'login')` (or `organization.login`), while the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) select the target `Repository`/`Stack` from a *different* JSON field, `payload.dig('repository', 'full_name')`. Both fields are attacker-controlled content inside the same signed JSON body; nothing in the engine enforces that they refer to the same repository/organization. This breaks the trust binding: `organization authenticated == repository written`.

### Finding Description
The webhook signature check picks the app/secret to verify with based on the payload itself, before any content has been validated: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once signature verification passes, `create` dispatches the same raw payload to registered handlers: [2](#0-1) 

Every handler (`PushHandler`, `StatusHandler`, etc.) resolves the target `Stack`/`Repository` not from `repository.owner.login` but from `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Each GitHub App organization has its own `webhook_secret` in `config/secrets.yml` (`docs/setup.md` "Using Multiple Github Applications" section confirms per-organization secrets are supported): [4](#0-3) 

Because `verify_webhook_signature` only checks that the request was signed with *some* valid app secret for *whatever organization the attacker names in `repository.owner.login`*, an attacker who is an admin of their own GitHub organization (and therefore legitimately possesses that organization's own `webhook_secret`, obtained by installing their own Shipit-compatible GitHub App on their org - no privileged Shipit access needed) can craft a payload where:
- `repository.owner.login` = attacker's own organization (secret known to attacker)
- `repository.full_name` = `"victim-org/victim-repo"` (an actual Stack tracked by this Shipit instance)

and sign the whole raw body with their own organization's `webhook_secret`. `verify_signature` succeeds because it only checks the signature against the app keyed by `repository_owner` (attacker's org). The `PushHandler`/`StatusHandler`/`CheckSuiteHandler`, however, look up `Repository.from_github_repo_name("victim-org/victim-repo")` and act on it — enqueuing `GithubSyncJob`, updating commit statuses, or refreshing check runs for a repository the attacker's signature was never actually bound to.

### Impact Explanation
This lets an unprivileged attacker (who only needs to control any GitHub organization that has a Shipit GitHub App/webhook secret configured, e.g. because they registered their own low-trust org with the Shipit instance) forge webhook events that are attributed to and acted upon for a completely different, victim organization's repository/stack. This can:
- Force `GithubSyncJob` to run for the victim stack with attacker-chosen `expected_head_sha` via the forged `push` event (`PushHandler#process`).
- Inject fabricated CI/commit statuses (`StatusHandler`) that Shipit uses to gate/approve deploys, potentially enabling an unauthorized deploy of a commit that never actually passed CI.
- Trigger `RefreshCheckRunsJob` and other side effects for a stack the attacker's key was never authorized against.

This matches the required High/Critical impact bar of enabling an unauthorized deploy/merge-relevant side effect by crossing a trust boundary between organizations.

### Likelihood Explanation
Likelihood is realistic in any Shipit deployment that configures multiple GitHub organizations (explicitly documented and supported per `docs/setup.md`). The attacker needs only to be an administrator of one such configured, low-trust organization (or any org whose app is installed) — they never need write access to the victim repository, a Shipit session, or any privileged Shipit credential. This is exactly the unprivileged-attacker class the analog rules target.

### Recommendation
- Bind the signature-verification organization to the repository being acted upon: after determining `repository_owner` and verifying the signature, re-derive/require that `repository.full_name`'s owner segment matches `repository_owner` before dispatching to handlers, or reject if they diverge.
- Prefer verifying against the `Repository`'s already-recorded GitHub `owner`/`id` (looked up from the local `Repository` record keyed by `full_name`) rather than trusting the payload's `owner.login` to pick the signing key.
- Additionally validate `repository.id` (GitHub's stable numeric ID) against the locally stored `Repository#github_id` rather than only the mutable `full_name` string, closing the same class of stale/attacker-controlled mapping issue described in the source report.

### Proof of Concept
1. Configure Shipit with two GitHub App orgs, `attacker-org` (attacker controls installation/secret) and `victim-org` (has a tracked `Stack` for `victim-org/victim-repo`), per the multi-org config format in `docs/setup.md`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, raw_body)>` using their own org's known secret.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature verifies successfully (line 25-30 of `webhooks_controller.rb`).
6. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` (`handler.rb` lines 32-38) and enqueues `stack.sync_github(expected_head_sha: "deadbeef...")` for the victim's stack, despite the signature never having been validated against `victim-org`'s secret. # frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
