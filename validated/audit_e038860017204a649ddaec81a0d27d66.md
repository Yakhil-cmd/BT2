### Title
Cross-tenant Commit status forgery via unscoped SHA lookup in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to update purely by `sha`, across the entire `Commit` table, with no check that the SHA belongs to the repository that authenticated the webhook. Any GitHub organization/repository configured in Shipit can emit a validly-signed `status` event for a SHA that happens to also exist as a queued `MergeRequest#head` commit in a completely different tenant's stack, and that status is applied to the victim's commit, which can flip `MergeRequest#all_status_checks_passed?` to true and trigger `Stack#schedule_merges`.

### Finding Description
The broken binding, stated explicitly: `commit.stack.repository.full_name` (the tenant whose `Commit` row is mutated) **should equal** `payload.dig('repository', 'full_name')` (the tenant whose webhook signature was actually verified by `WebhooksController#verify_signature`) — this is **false** in the code.

`WebhooksController#verify_signature` only proves the payload was signed by the GitHub App belonging to `repository_owner` derived from the *attacker's own* payload: [1](#0-0) 
This proves authenticity of the sender's org, not that the sender is authoritative for the SHA being referenced.

`StatusHandler#process` then does: [2](#0-1) 
`Commit.where(sha: params.sha)` is a global, unscoped query across every stack/repository in the Shipit install — it never uses the `Handler#stacks` helper (which scopes lookups through `Repository.from_github_repo_name(repository_name)`), unlike sibling handlers such as `CheckSuiteHandler`, which correctly scope through the repository before touching commits: [3](#0-2) [4](#0-3) 

`Commit#create_status_from_github!` then writes the status using the commit's own pre-existing `stack_id`, not anything derived from the webhook payload's repository: [5](#0-4) 

Test evidence confirms that a successful status transition enqueues merge-queue processing regardless of which app/context created it: [6](#0-5) 

Exploit flow:
1. Victim org has a stack with `merge_queue_enabled: true` and a queued `MergeRequest` whose `head` commit SHA is known (e.g., visible via the victim's public GitHub PR/commit history, or literally the same git object copied by the attacker into their own repo, since SHA1 is content-addressed and copying a real object is not a "collision").
2. Attacker owns a legitimate GitHub App/repo in Shipit (their own org/repo configured in Shipit), pushes/references a commit with that exact SHA in their own repository, and has GitHub emit (or crafts and self-signs, since they own the webhook secret for their own org) a `status` webhook with `state: "success"` for that SHA.
3. `verify_signature` succeeds because the signature is valid for the attacker's own org — it was never meant to authorize writes against another tenant's data.
4. `StatusHandler#process` matches the SHA globally and calls `create_status_from_github!` on the victim's `Commit` row, which lives on the victim's stack.
5. `add_status` (invoked from `create_status_from_github!`) sees the new status is `success` and schedules `ProcessMergeRequestsJob` / `stack.schedule_merges`, and `MergeRequest#all_status_checks_passed?` now sees a success status that never came from the victim's real CI.

No existing guard closes this gap: `verify_signature` authenticates the sender's org, not the target repository of the referenced SHA; `ExplicitParameters` validates payload shape only; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler#process`.

### Impact Explanation
An unprivileged attacker who controls only their own repository/org (already onboarded to Shipit, as any tenant would be) can inject a fabricated CI-success status onto an arbitrary commit SHA in a victim tenant's stack, as long as they know or can copy that SHA. Combined with `Stack#schedule_merges` / `MergeQueue`, this can cause an unauthorized merge of a pull request in the victim's repository whose real CI never ran, or otherwise falsify the deployability state of a commit used elsewhere (e.g., deploy gating). This is a cross-tenant write where a payload originating from one repository's authenticated context mutates another repository's `Commit`/`MergeRequest` state — matching the "Critical" category of "a payload for one repository mutating another's stack/commit ... or an unauthorized merge."

### Likelihood Explanation
Preconditions: victim stack has `merge_queue_enabled` and a pending `MergeRequest`; attacker needs any Shipit-onboarded repository (even one they fully control, e.g. a fork or unrelated public repo) and knowledge of the target SHA (trivial for public GitHub PRs, since `head.sha` is exposed via the PR API/UI). No secrets, sessions, or elevated roles are required — only the ability to emit a webhook backed by a real, attacker-owned GitHub App/repo installation, which is the baseline capability assumed for any Shipit tenant/attacker in this threat model. This is fully repeatable against any commit SHA the attacker can learn, for any repository connected to the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` (and any other handler bypassing `Handler#stacks`) so it only updates commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`, e.g. replace the global `Commit.where(sha: params.sha)` with a lookup restricted to `stacks.flat_map(&:commits).where(sha: params.sha)` (using the existing `Handler#stacks` helper), ensuring the authenticated repository from the webhook is the same repository that owns the commit being mutated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks belonging to two distinct repositories/orgs: `victim/repo` (with `merge_queue_enabled: true`) and `attacker/repo`.
2. Create a `Commit` with a fixed `sha` = `S` under `victim/repo`'s stack, and a `MergeRequest` on that stack with `head` pointing to that commit, `merge_status: 'pending'`.
3. Assert baseline: `merge_request.all_status_checks_passed?` is `false` (no status yet) — this is "before" state of the equality (`commit.stack.repository.full_name` = `victim/repo`, no status from `attacker/repo` exists).
4. POST a `status` webhook payload with `sha: S`, `state: 'success'`, and `repository.full_name = 'attacker/repo'`, `repository.owner.login = 'attacker'`, stubbing `GithubHook#verify_signature`/`Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (simulating a legitimately-signed webhook from the attacker's own org).
5. Assert after the request: `Commit.find_by(sha: S).stack` is still `victim/repo`'s stack (binding: `commit.stack.repository.full_name == 'attacker/repo'` is false, yet the write succeeded), the commit now has a `success` status, `merge_request.reload.all_status_checks_passed?` is `true`, and `ProcessMergeRequestsJob`/`schedule_merges` was enqueued for the victim's stack — proving a webhook authenticated for `attacker/repo` mutated `victim/repo`'s merge-readiness state.
