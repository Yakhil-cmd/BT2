### Title
Webhook signature verification is scoped to the wrong organization, allowing any onboarded GitHub organization to forge push/status events for repositories they do not own - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using an attacker-supplied field of the JSON body itself (`repository.owner.login`, falling back to `organization.login`), then hands the *entire, unvalidated* body to the event handlers. The handlers, in turn, resolve the target repository/commit from a *different* field of the same body (`repository.full_name` in `Handler#repository_name`, or, worse, no repository scoping at all in `StatusHandler`). Nothing ties the organization whose secret validated the signature to the repository that is actually acted upon, so a legitimately onboarded (but low-privileged/attacker-controlled) GitHub organization can sign a payload with its own webhook secret while pointing the payload's repository/commit fields at a victim organization's stack.

### Finding Description
`verify_signature` picks the app config purely from body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` loads the `GitHubApp` config (and `webhook_secret`) keyed by whatever organization name is embedded in the JSON payload, and `verify_webhook_signature` only proves the requester knows *that* organization's `webhook_secret`: [3](#0-2) 

The verified request body is then dispatched unchanged to handlers: [4](#0-3) 

Handlers resolve the target repository from `payload.dig('repository', 'full_name')`, a field completely independent of `repository.owner.login` used for signature routing: [5](#0-4) [6](#0-5) 

`PushHandler` uses this repository/stack resolution to trigger `stack.sync_github`: [7](#0-6) 

Worse, `StatusHandler` does not scope by repository at all — it updates *any* commit matching the given SHA anywhere in the installation: [8](#0-7) 

**Binding broken:** `organization authenticated (repository_owner used to select webhook_secret) == organization/repository actually written to (repository.full_name / global commit SHA lookup)`. Before an attacker's crafted request, these two would coincide for genuine GitHub-originated webhooks (GitHub always signs and reports payloads for the same repo). After the attacker's crafted request, they diverge: the signature check passes using organization A's secret, while the payload content dictates action on organization B's stack/commit.

### Impact Explanation
- Any organization/user who is legitimately onboarded onto a multi-tenant Shipit instance (i.e., they know their own org's `webhook_secret`, e.g. because they configured their own GitHub App per the multi-org config format shown in `config/secrets.development.shopify.yml`) can forge `push` events that cause `Repository.from_github_repo_name` to resolve to a **different** organization's repository and trigger `stack.sync_github` on it.
- More severely, `StatusHandler` performs no repository binding whatsoever (`Commit.where(sha: params.sha)`), so a signed request from any onboarded organization can flip the CI status of any commit SHA in the entire installation to `success`, provided the attacker can produce or claim a matching SHA. Since `required_statuses`/`blocking_statuses` gate whether a commit is `deployable?` (`app/models/shipit/commit.rb`, `app/models/shipit/deploy_spec.rb`), this can be used to make an otherwise-blocked, unreviewed commit appear deployable, enabling an unauthorized deploy — matching the report's "Critical: unauthorized deploy" impact bucket.
- This crosses a real trust boundary: authentication is anchored to one tenant's secret, but the write/action target is fully attacker-controlled data from the same request, with no cross-check.

### Likelihood Explanation
Exploitability requires only that the attacker's own organization be a legitimate, already-configured GitHub App tenant on the Shipit instance (a realistic scenario for any Shipit deployment serving multiple organizations, as explicitly supported and documented in `config/secrets.development.shopify.yml` / `README.md`). No repository write access, GitHub App private key, or `ApiClient` token is required — only the ability to send an HTTP POST to `/webhooks` with a valid HMAC for one's own tenant. This is a straightforward, deterministic exploitation path once the multi-tenant configuration is in use, not merely theoretical.

### Recommendation
After verifying the signature, re-derive `repository_owner`/`organization` strictly from the same trusted context used for verification, and reject (or drop) the event if the repository/commit the handler resolves does not belong to that same authenticated organization. Concretely:
- Pass the authenticated `repository_owner` into `Shipit::Webhooks.for_event(event)` handlers and have `Handler#stacks`/`Repository.from_github_repo_name` reject any repository whose owner does not match the authenticated organization.
- Fix `StatusHandler` to scope `Commit.where(sha: params.sha)` to commits belonging to repositories under the authenticated organization, instead of matching globally by SHA.

### Proof of Concept
1. Organization `attacker-org` is a legitimate tenant on the Shipit instance with its own GitHub App and known `webhook_secret_A` (multi-org config as in `config/secrets.development.shopify.yml`).
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully, because the attacker legitimately owns that secret.
5. `Shipit::Webhooks.for_event("push")` dispatches the full body to `PushHandler`, whose `stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` — a repository the attacker does not own — and calls `stack.sync_github(expected_head_sha: params.after)` on victim-org's stack.
6. For the `status` event variant, the same forged-signature trick lets the attacker call `Commit.where(sha: params.sha)` globally via `StatusHandler#process`, updating status for any matching commit across the whole install, independent of `repository` fields at all. [9](#0-8) [5](#0-4) [8](#0-7)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
