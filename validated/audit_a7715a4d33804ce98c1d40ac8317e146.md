### Title
Unvalidated encrypted-package field lengths (`iv`/`authtag`) crash the process via uncaught crypto exception - (File: device.js)

### Summary
`device.decryptPackage()` builds the AES-128-GCM IV and auth-tag directly from attacker-controlled base64 strings in an incoming device message and passes them straight into `crypto.createDecipheriv()` / `decipher.setAuthTag()` without validating their decoded byte length first. Node's native crypto bindings throw synchronous, uncaught exceptions ("Invalid IV length", "Invalid authentication tag length", etc.) for out-of-range lengths, and those two calls are not wrapped in a `try/catch` (only `decipher.final()` is). This mirrors CVE-2015-7855's root cause: a length field taken from an untrusted, non length-checked message field being handed to a low-level primitive that asserts/aborts on out-of-range input, causing a crash instead of a graceful validation error.

### Finding Description
`decryptPackage()` in [1](#0-0)  only checks that `iv`, `authtag`, and `encrypted_message` are *strings* — it never checks their decoded length: [2](#0-1) 

`iv` is decoded from base64 and fed to `crypto.createDecipheriv('aes-128-gcm', shared_secret, iv)`, and `authtag` is decoded and fed to `decipher.setAuthTag(authtag)`. Node's OpenSSL bindings validate IV/tag lengths internally and `throw` synchronously if they are wrong (e.g., an IV that is not 12 bytes, or an auth tag that is not 16 bytes, or a grossly oversized value). Only the later `decipher.final()` call, at [3](#0-2) , is guarded by `try/catch`; the `createDecipheriv` and `setAuthTag` calls that can also throw are not.

This is functionally the same bug class as CVE-2015-7855: `decodenetnum` in ntpd trusted a length embedded in an attacker-supplied packet and passed it into an internal routine that asserts on invalid lengths, crashing the daemon. Here, the "long/invalid data value" is the base64-decoded `iv`/`authtag` length inside a JSON message from a paired device, and the internal routine that "asserts" is the Node.js/OpenSSL GCM implementation.

If nothing higher up the call stack catches the exception, it becomes an uncaught exception. `network.js` installs a global handler that explicitly re-throws to crash the process: [4](#0-3) 

so any code path where `decryptPackage()` is invoked without an enclosing `try/catch` results in the whole node process terminating.

### Impact Explanation
A paired device (explicitly listed as an in-scope reachable actor) — or anyone able to relay a crafted encrypted-package JSON to a device/wallet/hub node that calls `decryptPackage()` — can send a message with a malformed `iv` or `authtag` (wrong decoded length) to force an uncaught synchronous exception. Combined with the global `uncaughtException` handler in `network.js` that re-throws to crash the process, this produces a remote, low-privilege, repeatable denial of service: the targeted node process terminates, which for a hub/witness node prevents it from continuing to relay, validate, or help confirm new units until it is manually restarted — matching the "network unable to confirm new units" impact bar in scope.

### Likelihood Explanation
The trigger requires only sending a small, valid-JSON encrypted-package object with a `dh.recipient_ephemeral_pubkey` value that matches one of the target's known keys (temp/prev-temp/permanent — normal for any legitimately paired correspondent) and a syntactically valid but wrong-length base64 `iv`/`authtag`. No cryptographic break, no privileged access, and no race condition are required — this is a straightforward, deterministic input-validation gap reachable by any paired correspondent (or anyone who can get a message routed to `decryptPackage`).

### Recommendation
Validate decoded lengths before use:
- Reject the package early if `Buffer.from(objEncryptedPackage.iv, 'base64').length !== 12` (or the expected IV size for the mode in use).
- Reject the package early if `Buffer.from(objEncryptedPackage.authtag, 'base64').length !== 16`.
- Wrap `crypto.createDecipheriv(...)` and `decipher.setAuthTag(...)` in the same `try/catch` that already guards `decipher.final()`, returning a normal error/log instead of allowing the exception to propagate.
- Audit all callers of `decryptPackage()` to ensure none can let an exception bubble up uncaught into the global `uncaughtException` handler in `network.js`.

### Proof of Concept
1. As a paired device (or anyone able to have a message routed to the victim's `decryptPackage`), send a message payload such as:
```json
{
  "iv": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA", // decodes to far more/less than 12 bytes
  "authtag": "AAAA",                                  // decodes to far less than 16 bytes
  "encrypted_message": "AAAA",
  "dh": {
    "sender_ephemeral_pubkey": "<attacker ephemeral pubkey b64>",
    "recipient_ephemeral_pubkey": "<victim's known temp/prev-temp/permanent pubkey b64>"
  }
}
```
2. Victim's `device.js` `decryptPackage()` computes `shared_secret` via ECDH and calls `crypto.createDecipheriv('aes-128-gcm', shared_secret, iv)` with the malformed `iv` — Node throws synchronously ("Invalid IV length") outside any `try/catch`.
3. The exception is uncaught, hits `process.on('uncaughtException', ...)` in `network.js`, which re-throws and terminates the process.

Note: I was not able to fully trace the exact call site in `wallet.js` that invokes `device.decryptPackage()` (only one match was found and its surrounding try/catch context could not be retrieved before the tool budget ran out), so it is not fully confirmed whether that specific call site adds its own exception handling. If it does wrap the call in `try/catch`, the crash would be contained there; however, `decryptPackage()` recurses into itself for nested encryption layers (`depth` up to 2), and any of those recursive invocations reproduce the same unguarded `createDecipheriv`/`setAuthTag` calls, so the underlying missing length validation is the root cause regardless of the outer call site's error handling.
