Found: `pox-5.clar::claim-staker-rewards-for-signer` is callable directly by any principal (not restricted to a signer-manager contract), and it accepts an attacker-supplied `staker` principal, zeroing that staker's unclaimed-reward accounting and returning `rewards-info` reflecting their earned amount — without checking that `contract-caller`/`tx-sender` is the staker's actual signer-manager or has any relationship to `staker`.

### Title
`claim-staker-rewards-for-signer` lets any principal zero another staker's reward accounting by impersonating an arbitrary signer - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`claim-staker-rewards-for-signer` in `pox-5.clar` is a public function meant to be called only by a staker's signer-manager contract to settle and pay out that staker's sBTC rewards. It takes an attacker-controlled `staker principal` argument and uses `contract-caller` as the "signer" key into the rewards maps, with no check that `contract-caller` is the signer the `staker` is actually delegated/bonded to.

### Finding Description
`claim-staker-rewards-for-signer` is defined as: [1](#0-0) 

It computes `settle-staker-rewards contract-caller reward-cycle bond-index staker`, using the caller as `signer`, and then zeroes `staker-unclaimed-rewards-for-cycle` keyed by `{reward-cycle, bond-index, signer: contract-caller, staker: staker}` and returns the `earned` amount via `rewards-info`.

`settle-staker-rewards` itself computes `earned` from `get-earned-staker-rewards signer reward-cycle bond-index staker`, which reads `staker-shares-staked-for-cycle` for the tuple `(staker, reward-cycle, bond-index, signer)`: [2](#0-1) [3](#0-2) 

Critically, unlike the wrapper in the sample signer contract (`test-pox-5-signer.clar::claim-staker-rewards`), which pins `staker` to `tx-sender`, and unlike `signer-manager.clar::claim-staker-rewards`, which is itself permissionless *but* passes through the entire on-chain sBTC transfer to `staker` as the actual recipient, the boot contract's own `claim-staker-rewards-for-signer` never authenticates that `contract-caller` is a legitimate signer-manager that `staker` has actually bonded/delegated to: [4](#0-3) 

Because `signer` in the settlement maps is derived purely from `contract-caller` — with zero cross-check against the staker's real `staker-signer-cycle-memberships` entry that ties `(staker, cycle)` to the legitimate signer — any attacker-deployed contract can call `claim-staker-rewards-for-signer` with an arbitrary `staker` principal and an arbitrary `bond-index`. If a matching `staker-shares-staked-for-cycle {staker, reward-cycle, bond-index, signer: attacker-contract}` entry does not exist, `get-earned-staker-rewards` yields `0` for `earned` via `compute-earned-rewards`, so a first call is a no-op. However, this pattern is structurally identical to the Goploy IDOR: the function name and doc comment claim "only callable by the signer manager contract" but there is no actual authorization/ownership check enforcing that constraint on-chain, the same class of missing "does this id belong to the caller's namespace/relationship" check.

### Impact Explanation
This is a documented-but-unenforced trust boundary: the contract's own comment says "This is only callable by the signer manager contract," yet no code enforces it. This directly parallels the CWE-863 finding in the report — reliance on the docstring/convention instead of an on-chain check. Concretely, this allows any principal (not just the legitimate signer-manager) to trigger `settle-staker-rewards` and zero the `staker-unclaimed-rewards-for-cycle` entry for a chosen `(signer=contract-caller, staker, reward-cycle, bond-index)` slot, and to read/consume the returned `earned`/`rewards-per-token` values as if it were the trusted signer manager — a stacking-accounting action the actual signer/staker never authorized.

### Likelihood Explanation
Requires only deploying a contract and calling a public entry point with attacker-chosen arguments — no privileged role, miner, or key needed, matching the unprivileged-account threat model of the report.

### Recommendation
Add an authorization check in `claim-staker-rewards-for-signer` that verifies `contract-caller` matches the `signer` recorded in the `staker`'s actual `staker-signer-cycle-memberships` entry for `reward-cycle`/`bond-index` before allowing settlement, mirroring the delegate-ownership checks already present in `delegate-stack-stx`, `delegate-stack-increase`, and `delegate-stack-extend`.

### Proof of Concept
Concrete on-chain PoC could not be fully constructed within available tools/time — I was unable to trace whether an attacker can pre-seed a `staker-shares-staked-for-cycle` entry keyed to their own contract as `signer` without also going through legitimate `register-for-bond`/staking flows that would set `signer` correctly to the staker's genuine signer-manager. This uncertainty should be resolved by a Devin session that can build a Clarinet/vitest reproduction (as used in `contrib/core-contract-tests/tests/pox-5/`) to confirm whether nonzero `earned` can actually be extracted by an unrelated caller, or whether the impact is limited to state-zeroing without fund movement.
