## Analysis

The Dinari `OrderProcessor` bug is rooted in an *external blacklist* that can turn an already-accepted, already-committed operation into a permanently unfulfillable one, with no recovery path (`cancelOrder` also targets the blacklisted `recipient`). The closest reachable analog in `ocore` is the **`spender_attested`** asset mechanism, which acts as a "whitelist" gate on every future transfer of an asset output — checked *at spend time*, not frozen at the time the funds were received.

For a `spender_attested` asset, the attestor list is defined by the asset issuer (`validateAssetDefinition`) and can be updated at any time via an `asset_attestors` message, restricted only to the asset definer: [1](#0-0) 

Every time an output of such an asset is later spent, the *owner address* is re-checked against the **current** attestor list (not the list at the time the output was created): [2](#0-1) [3](#0-2) 

And on the output side, sending to a non-attested address is rejected outright: [4](#0-3) 

Crucially, this same check applies to **Autonomous Agents**. When an AA composes and validates its response unit, it runs through the exact same `validation.validate` pipeline: [5](#0-4) 

If validation fails (e.g. because the AA's own address, or a recipient it is paying, is no longer attested), the AA bounces the trigger and its balance/state changes are rolled back: [6](#0-5) 

### Why this matches the bug class
- The asset issuer/attestor is a role explicitly allowed as an "attacker" persona (asset issuer) under the rules.
- An asset can legitimately hold `spender_attested = true`, and any address (including an AA that holds a balance of the asset, e.g., a DEX/exchange AA that received user deposits while attested) can be retroactively de-attested via `asset_attestors`.
- Once de-attested, **every stable output already owned by that address becomes permanently un-spendable**: the very same `owner address is not attested` check fires on every future attempt to move it, and there is no bypass, no "cancel", and no alternate recovery path in `ocore`, mirroring the Dinari bug where the recipient's blacklist status makes both `fillOrder` and `cancelOrder` revert forever.
- For an AA, this directly matches "AA fund freezing": the AA's own balance of that asset becomes permanently locked, and any further trigger that tries to move it will simply bounce (with the AA also paying a `bounce_fee` for every failed attempt, i.e., an ongoing drain), instead of a graceful failure or refund of the affected asset.

Note that unlike the Dinari case, `ocore` does not have a mid-flight "already committed off-chain trade" state — validation happens atomically before a unit can ever be accepted, so a single unit can't be "half executed." The realistic ocore-analog is therefore about **permanent freezing of already-owned, already-stable asset funds** due to a later revocable transfer-condition (`spender_attested`) rather than a failed one-shot fulfillment step.

### Title
Asset issuer can permanently freeze already-received asset funds (including AA-held funds) by revoking `spender_attested` attestation after the fact - (File: validation.js)

### Summary
An asset defined with `spender_attested: true` is validated against the *live* attestor list every time its outputs are spent, not against the list in force when the output was received. The attestor list is fully controlled by the asset definer and can be updated at any time via an `asset_attestors` message.

### Finding Description
`validatePaymentInputsAndOutputs` re-checks `objAsset.arrAttestedAddresses.indexOf(owner_address)` for every input being spent [2](#0-1) , using the attestor list as of the current `last_ball_mci` (fetched via `storage.filterAttestedAddresses`/`storage.loadAssetWithListOfAttestedAuthors`). Because the attestor list is dynamic and controlled solely by the asset definer (`validateAttestorListUpdate` requires only `objUnit.authors[0].address === objAsset.definer_address`) [1](#0-0) , a user (or an AA) that legitimately received and stabilized a payment while attested can later be silently de-attested, at which point that specific stable output can never again satisfy the spend-time check and becomes permanently frozen. The same check applies to AA response units, since `handleTrigger`'s `validateAndSaveUnit` runs the full `validation.validate` pipeline before saving [5](#0-4) ; a failure there causes the AA to `bounce` (state/balance rollback plus a bounce-fee loss) [6](#0-5) .

### Impact Explanation
- Any balance an address (user or AA) legitimately owns in a `spender_attested` asset can be frozen forever by the asset definer at any later point, with no on-chain mechanism to recover or bypass the block (no analog to `cancelOrder`).
- If the frozen address belongs to an AA acting as an operator/service (e.g., an exchange or custody AA), the AA's held asset balance becomes permanently locked, and any trigger attempting to move it repeatedly bounces, draining `bounce_fees` from user deposits with each attempt.
- This is a fund-freezing condition, not merely a UX inconvenience, matching the impact class of the referenced report (stuck funds, no recovery path).

### Likelihood Explanation
Requires the asset issuer (who legitimately controls the asset's attestor list by design) to update the attestor list after users/AAs have already received and stabilized funds. This is a normal, permitted on-chain action for that asset (`asset_attestors` message), requiring no special privilege beyond being the asset's definer — a role reachable by any unprivileged user who created the asset in the first place.

### Recommendation
- Consider snapshotting/caching attestation status at the time an output is created (or providing a defined grace period) rather than re-validating against the live attestor list at spend time.
- Provide an on-chain recovery/escape mechanism (e.g., allow de-attested holders to return funds to the definer, similar to `auto_destroy`, or require an explicit unlock path) so that funds cannot be indefinitely frozen by a unilateral attestor-list update.
- For AA-held balances of `spender_attested` assets, treat attestation loss as a distinguishable, recoverable error state rather than an unconditional bounce, so operators can react before permanent freezing occurs.

### Proof of Concept
1. Asset issuer defines asset `A` with `spender_attested: true` and an attestor list containing `attestor1`.
2. `attestor1` attests address `X` (a user address or an AA address holding a service balance).
3. `X` receives and stabilizes an output of asset `A` (passes the spend/output-attestation check at `validation.js:2630-2641`).
4. Asset issuer posts `asset_attestors` to remove `attestor1`/replace it with an attestor that never attests `X` again (`validation.js:2829-2848`).
5. `X` attempts to spend the previously received output of asset `A`; validation now fails at `validation.js:2504-2507` with "owner address is not attested", and the unit is rejected — for an AA, this manifests as a permanent bounce of any trigger attempting to move that balance (`aa_composer.js:910-945`).
6. The funds held at `X` remain permanently stuck with no cancellation or recovery path.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
