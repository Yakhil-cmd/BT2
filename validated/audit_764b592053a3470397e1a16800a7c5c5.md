### Title
Stake mutation (Split/Merge) between epoch-boundary calculation and restart-triggered recalculation causes cross-node reward divergence - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`recalculate_stake_rewards` (invoked only via `initialize_after_snapshot_restore` → `recalculate_partitioned_rewards_if_active`) recomputes unpaid `PartitionedStakeReward` amounts using the **live, current** `StakesCache` delegation for each stake account, while a validator that never restarts keeps the `all_stake_rewards` list frozen from the original epoch-boundary calculation. An attacker who mutates their own pending-reward stake account (Split/Merge) between the epoch boundary and a validator's restart can therefore cause restarted vs. non-restarted honest validators to compute different reward amounts for the identical rewarded_epoch and slot, producing different post-distribution account states and bank hashes.

### Finding Description
`recalculate_stake_rewards` at [1](#0-0)  fetches `stake_delegations` from `self.stakes_cache.stakes()` — i.e., the bank's *current* StakesCache at the moment of recalculation (post-restart), not a value frozen at the original epoch-boundary calculation. This is explicitly documented: "StakeRewards are recalculated from ... stake accounts from StakesCache" [2](#0-1) .

Inside `redeem_delegation_rewards`, the delegation used for the reward computation is taken directly from the passed-in (current) `stake_account`: `let stake = *stake_account.stake();` [3](#0-2) , and `calculate_block_reward` uses `delegation_effective_stake(delegation, rewarded_epoch, stake_history, ...)` where `delegation` is `stake_account.delegation()` from that same current stake account [4](#0-3) . `Split`/`Merge` stake instructions directly mutate `delegation.stake` while preserving `activation_epoch`, so a mutation executed by the attacker on their own account between the original calculation slot and a validator's restart slot changes the amount `delegation_effective_stake` returns for the *same past* `rewarded_epoch`.

By contrast, the developers explicitly recognized and fixed this exact class of drift for **vote-account** state (via `CachedVoteAccounts`, snapshotted per rewarded epoch, see `get_cached_vote_accounts`) [5](#0-4)  and for the **Alpenglow total delegated-stake denominator** (via `RewardEpochDelegatedStakes`, explicitly noted: "distribution_epoch_vote_accounts already includes updated stake activation values from after the new epoch calculation, so we need to use RewardEpochDelegatedStakes for the exact values at the end of the reward epoch") [6](#0-5) . No equivalent frozen snapshot exists for the per-account `stake_delegations` numerator used to compute an individual stake's own `inflation.stake_reward`.

A validator that never restarts keeps its `all_stake_rewards` (computed once at the epoch boundary in `calculate_rewards_for_partitioning`/`compute_new_epoch_caches_and_rewards`) unchanged for the rest of the distribution period; it is never recomputed from later StakesCache states. A validator that restarts mid-distribution calls `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards`, which **replaces** the outstanding reward list using the StakesCache as of the restart slot [7](#0-6) . If the attacker's Split/Merge transaction landed in a block between the epoch boundary and the restart slot, the recalculated reward for that pubkey (and any newly-created split-off pubkey, since `stake_delegations` covers the full current delegation set, not just originally-rewarded pubkeys) will differ from the frozen value still held by non-restarting nodes. Since distributed reward amounts are written into stake-account lamports/delegation and become part of consensus-critical account state (see `build_updated_stake_reward` in `distribution.rs`), this produces different resulting account states — and therefore different bank hashes — for the same slot across honest validators.

### Impact Explanation
This falls under cross-node state divergence / epoch-boundary consensus halt: honest validators that restart mid-epoch-rewards-distribution can compute and pay out different `PartitionedStakeReward` lamport amounts than validators that stayed continuously running, for the identical rewarded_epoch and distribution slot, leading to bank hash mismatch and chain halt/fork at the affected slot.

### Likelihood Explanation
Requires: (1) partitioned epoch rewards active with the attacker holding at least one not-yet-distributed stake reward, (2) at least one honest validator restarting/reloading from snapshot during the multi-block distribution window, and (3) the attacker submitting an ordinary, unprivileged Split/Merge instruction on their own stake account in that window — all attacker-controlled and requiring no special privilege. Validator restarts during live distribution windows (which can span many blocks/`num_partitions`) are a realistic operational occurrence, making this readily triggerable by a single unprivileged actor without needing to control which nodes restart.

### Recommendation
Freeze the per-account stake-delegation state (delegation.stake, activation/deactivation epoch) used for `redeem_delegation_rewards`/`calculate_block_reward` numerator computation at the original epoch-boundary calculation, analogous to `CachedVoteAccounts` and `RewardEpochDelegatedStakes`, rather than re-reading live `StakesCache` delegations during `recalculate_stake_rewards`. At minimum, persist and reuse the original `stake_delegations` snapshot (or the already-computed `all_stake_rewards` values for still-unpaid indices) across restarts instead of recomputing from mutated live state.

### Proof of Concept
Extend the existing `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` pattern in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`:
1. Set up a reward bank with two stake accounts under one vote account; advance to the epoch boundary so `all_stake_rewards` is computed with `unpaid_reward` for `unpaid_stake_pubkey` based on original `delegation.stake`.
2. Before simulating snapshot restore, apply a `Split` (via direct stake-account state manipulation, since the stake program processor isn't in this repo, or via a `stake_utils` helper) on `unpaid_stake_pubkey`'s stake account that reduces its `delegation.stake` by half, storing the mutated account via `bank.store_account_and_update_capitalization`.
3. Call `bank.recalculate_stake_rewards(&epoch_rewards_sysvar, &thread_pool)` and find the recalculated entry for `unpaid_stake_pubkey`.
4. Assert `unpaid_reward.inflation.stake_reward != recalculated_unpaid_reward.inflation.stake_reward` — showing the recalculated (post-restart) value diverges from what a non-restarting node would keep, violating the "same denominator/numerator used at original calculation" invariant for the stake-side numerator (the existing test only covers the AG total-stake denominator, not the per-account `delegation.stake`).

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }
