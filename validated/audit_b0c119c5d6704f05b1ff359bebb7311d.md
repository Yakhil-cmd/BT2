### Title
Cross-organization webhook confusion: signature is verified against `repository.owner.login`'s secret, but stack lookup trusts the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the HMAC against using `repository.owner.login` (falling back to `organization.login`), but every event handler resolves the target `Repository`/`Stack` using the separate `repository.full_name` field. Nothing in the code enforces that `full_name`'s owner segment matches `repository.owner.login`. In a multi-organization Shipit deployment (as documented and configured in `config/secrets.development.shopify.yml`), an attacker who legitimately controls one onboarded organization's GitHub App (and therefore knows/controls that org's `webhook_secret`) can forge a payload that authenticates as their own org while acting on a completely different, victim organization's repository/stack.

### Finding Description
`verify_signature` picks the GitHub App config to check the signature against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` returns the `GitHubApp` instance (and its `webhook_secret`) for *that org name*. `verify_webhook_signature` then just HMACs the raw body against that org's secret: [3](#0-2) 

This only proves the payload was signed by whichever org's secret matched `repository.owner.login` — it says nothing about which repository the rest of the payload claims to touch. Every `Handler` subclass, however, resolves the acted-upon repository from a *different* JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) 

`PushHandler` uses this to trigger `stack.sync_github`, and `PullRequest::ClosedHandler` uses `params.repository.full_name` to resolve `Shipit::Repository.from_github_repo_name` and archive review stacks: [6](#0-5) [7](#0-6) 

Because Shipit explicitly supports hosting several independently-configured GitHub organizations side by side, each with its own `webhook_secret` (as shown in the multi-org example config), an org administrator for org **A** — who legitimately possesses `webhook_secret` for org **A** (visible/rotatable by them in their own GitHub App settings) — can construct a raw JSON body where `repository.owner.login = "org-A"` (so `verify_signature` selects and validates against org A's secret) but `repository.full_name = "org-B/victim-repo"` (so the handler resolves and mutates org B's `Stack`/`Repository`, which they do not own). [8](#0-7) 

This exactly matches the analog class called out in the prompt: "an organization that authenticated versus the repository that is written" is not the same value, yet the code implicitly assumes they are.

### Impact Explanation
An attacker controlling org A's webhook secret can forge signed `push` events that make Shipit call `stack.sync_github(expected_head_sha: ...)` on org B's stacks, forcing Shipit to sync/consider arbitrary commit SHAs it will subsequently try to deploy for a repository the attacker does not control — a cross-organization interference with deploy/rollback state that does not require any credential belonging to org B. This satisfies the High/Critical bar of "cross-repository writes" / "unauthorized deploy" pathways, since `sync_github` drives which commits are eligible for deployment on the victim's stack.

### Likelihood Explanation
Requires the deployment to be configured for multiple organizations (a supported, documented configuration — see `config/secrets.development.shopify.yml`) and requires the attacker to be a legitimate admin of one of the *other* onboarded orgs (i.e., not privileged relative to Shipit itself, but privileged only within their own tenant/org). No `ApiClient` token, GitHub App private key, or Shipit session is needed — only a correctly-signed raw HTTP POST to `/webhooks` using a secret the attacker is entitled to know for their own org.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cross-validate that `repository.owner.login` (or `organization.login`) equals the owner segment of `repository.full_name` before dispatching to handlers, and reject the payload (422) if they diverge. Alternatively, derive the target `Repository` lookup solely from the same organization value that was used to select and verify the signing secret, rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit is configured with two orgs, `org-A` and `org-B`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` layout).
2. Attacker is an authorized administrator of `org-A`'s GitHub App and therefore knows `org-A`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "org-A" },
       "full_name": "org-B/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-A-webhook-secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-A")`, verifies the signature successfully against org A's secret [1](#0-0) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-B/victim-repo")` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on org B's stack [6](#0-5) , despite the attacker never being authenticated as, or authorized on, `org-B`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
