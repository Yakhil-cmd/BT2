### Title
Cross-repository status forgery causing unauthorized deploy via unscoped `Commit.where(sha:)` in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every other GitHub webhook handler in this engine scopes its writes to the repository that the webhook signature was verified for, by resolving `stacks` through `Repository.from_github_repo_name(repository_name)` in the base `Handler` class. `StatusHandler`, however, ignores this scoping entirely and updates commit status for **every** commit in the database that shares the reported SHA, regardless of which repository/organization the verified webhook actually belongs to.

### Finding Description
The webhook signature check in `WebhooksController#verify_signature` selects the GitHub App/secret to verify against using the organization derived from the incoming payload (`repository_owner`), and only proceeds if that specific organization's HMAC verification succeeds: [1](#0-0) 

This authenticates "this payload really came from GitHub for organization/repository X." Handlers are then expected to act only on data belonging to that same repository X. The base `Handler` class exposes exactly this scoping mechanism: [2](#0-1) 

`PushHandler` and `CheckSuiteHandler` correctly use this `stacks` scope (derived from the payload's `repository.full_name`, which is covered by the verified signature) before touching any records: [3](#0-2) [4](#0-3) 

`StatusHandler` does not. It only requires `sha` and `state` and never touches `repository`/`stacks` at all — it queries `Commit` globally, across every stack in the Shipit instance: [5](#0-4) 

Because Git commit SHAs are content-addressed and independent of which repository stores them, an attacker who owns or forks a public repository and later gets it tracked by any organization configured in this Shipit instance can:
1. Fork/mirror a target repository (or otherwise obtain a commit with an identical tree/parents/metadata, producing an identical SHA) into their own attacker-controlled repository, which is verified under the attacker's own (legitimately configured) organization webhook secret.
2. Send (or have GitHub send, e.g. via their own CI) a `status` webhook for that SHA with `state: "success"`, signed correctly for the attacker's own organization.
3. `WebhooksController#verify_signature` succeeds — the signature genuinely matches the attacker's organization's secret, i.e. the equality `verified_organization == payload.organization` holds.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the commit in the **victim's** stack too (any tracked repository whose commit history contains that SHA), because the write path never checks `verified_organization == commit.stack.repository.owner`.
5. `Status.after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` fire on the victim's commit: [6](#0-5) 
If the victim stack has `continuous_deployment` enabled, this schedules an actual deploy of that commit through `Stack#trigger_continuous_delivery`, entirely driven by a webhook the attacker legitimately triggered for their own, unrelated organization.

The broken binding is: **the organization whose webhook secret authenticated the request ≠ the repository (stack) whose commit record and deploy pipeline get mutated.** Every sibling handler enforces this equality via the `stacks` helper; `StatusHandler` alone omits it.

### Impact Explanation
This allows a cross-tenant, cross-repository write: a party who legitimately controls one organization/repository tracked by a shared Shipit instance can inject arbitrary CI status ("success"/"failure"/"error") onto commits belonging to a completely different, unrelated organization's stack, without ever having credentials or write access to that other repository. When the victim stack has continuous deployment enabled, this can trigger an **unauthorized deploy** of a specific commit — matching the "Critical" impact category (unauthorized deploy). Even without continuous deployment, it lets an outsider corrupt CI/status state (`enable_ci_on_stack`, `commit.statuses`) used to gate manual deploys and the merge queue for a repository they do not own.

### Likelihood Explanation
Likelihood depends on the Shipit instance tracking multiple organizations/repositories (a supported, documented configuration via `Shipit.github(organization:)`) and on the ability to obtain a commit with a matching SHA (trivial for public repos via fork/mirror, or for any repo whose commits become known, e.g. through PRs, forks, or public history). No secrets, sessions, or API tokens belonging to the victim are required — only a legitimately configured organization webhook that the attacker already controls. This is a realistic multi-tenant deployment scenario for this engine.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: restrict the commit lookup to `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) instead of querying `Commit` globally by SHA. Additionally, add a `repository` parameter requirement to `StatusHandler.params` so a missing/mismatched repository field fails parameter validation before any write occurs.

### Proof of Concept
1. Configure a Shipit instance with two organizations/repositories: `victim/app` (with `continuous_deployment: true`) and `attacker/app`, each with its own configured webhook secret (as per `docs/setup.md`).
2. As the attacker, fork or mirror `victim/app`'s public history into `attacker/app`, or otherwise obtain a commit whose SHA is already tracked as a commit in `victim/app`'s stack.
3. Trigger (or directly send, since the attacker owns the webhook secret for `attacker/app`) a `status` event:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<valid HMAC using attacker/app's own webhook_secret>
{
  "sha": "<sha shared with victim/app commit>",
  "state": "success",
  "context": "ci/attacker",
  "repository": { "owner": { "login": "attacker" }, "full_name": "attacker/app" }
}
```
4. `verify_signature` succeeds (valid signature for `attacker` org). `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which returns the commit in `victim/app`'s stack as well, creating a `success` `Status` on it.
5. If `victim/app` has continuous deployment enabled, `Commit#schedule_continuous_delivery` → `Stack#trigger_continuous_delivery` fires, deploying the commit — without any interaction with `victim/app`'s own GitHub App, webhook secret, or repository permissions.
