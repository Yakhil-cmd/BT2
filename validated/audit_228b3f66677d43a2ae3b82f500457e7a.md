### Title
Caller-supplied swap route can add unrelated wallet transfers to the signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept opaque route bytes and forward them to the configured swap router without validating that every account touched by the route is a protocol asset or trusted venue. An attacker can provide a route containing a malicious pool contract. During simulation, that contract can request a token transfer from the victim to the attacker; Soroban records it as a child of the victim’s existing authorization. If the victim signs the generated authorization tree, the malicious transfer executes even though it is unrelated to the lending operation.

### Finding Description
`swap_collateral` authorizes the caller and verifies ownership or delegation for `account_id`, then passes the caller-provided `swap` bytes into `withdraw_and_swap_from_supply`. The generic swap helper authorizes only the expected controller-to-router input transfer and invokes `execute_strategy`; it does not inspect the route payload or constrain the venue addresses inside it.

The route format addresses pool contracts through an address registry, and venue dispatch invokes the supplied pool address. Consequently, a route can place arbitrary third-party code below the victim’s authorization context. That code can call an unrelated token’s `transfer(victim, attacker, balance)`. Simulation represents this as an additional child authorization under the victim’s strategy invocation. Signing that tree authorizes both the expected swap input transfer and the unrelated wallet transfer.

The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree` demonstrates this behavior: simulation records `token.transfer(alice, attacker, WALLET_BALANCE)` beneath Alice’s `swap_collateral` authorization, and enforcing mode succeeds when that child invocation is signed.

### Impact Explanation
This enables theft of user funds. A victim can lose an arbitrary balance of a token that is not part of the lending market, in addition to authorizing the intended collateral swap. The stolen amount is not bounded by the swap input, route minimum output, account health checks, or protocol collateral. The attack requires the victim to sign the authorization tree generated for a malicious route, making it a phishing-style authorization capture rather than a direct unauthenticated drain.

### Likelihood Explanation
Likelihood is moderate. An unprivileged attacker only needs to induce the victim to submit a strategy call carrying malicious route bytes, for example through a compromised quote source, malicious frontend, or crafted transaction. The authorization tree is opaque to many users, and the extra token transfer can be difficult to distinguish from legitimate nested token movement. The attack cannot succeed if the wallet rejects or the user declines the additional child authorization, so it depends on social engineering and insufficient authorization review.

### Recommendation
Validate routes before exposing them to user authorization. At minimum, the router/controller boundary should reject venue and token addresses that are not part of an explicit protocol-maintained allowlist or otherwise carry a signed trusted-route commitment. Clients and wallets should also simulate the complete transaction, decode `swap` bytes, and reject authorization trees containing any child invocation other than the expected input-token transfer. For stronger protection, the strategy interface should accept a router-generated route identifier or commitment rather than arbitrary executable route bytes.

### Proof of Concept
1. Deploy a malicious contract exposing the venue function expected by the selected route opcode. The contract calls `token.transfer(victim, attacker, victim_balance)` for a valuable token unrelated to the lending markets.
2. Construct `swap` route bytes whose address registry contains that malicious contract as a pool and whose declared output still satisfies the route’s positive-minimum/output accounting.
3. Prompt the victim to call `swap_collateral(caller=victim, account_id=victim_account, current=USDC_market, amount=X, new=ETH_market, swap=malicious_route)`.
4. During simulation, the malicious venue executes beneath the controller/router call and records a child authorization for `transfer(victim, attacker, victim_balance)`.
5. If the victim signs the complete tree, the unrelated token moves to the attacker while the strategy can still return enough output to pass the controller’s positive-output and final risk checks.
