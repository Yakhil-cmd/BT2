## Title
Attacker-controlled arithmetic overflow forces a `VMLogicError::InconsistentStateError` down a fatal-error path, causing chunk-application `panic!` instead of a billed `FunctionCallError` - ([File: runtime/near-vm-runner/src/logic/errors.rs])

## Summary
`TryFrom<VMLogicError> for FunctionCallError` (`runtime/near-vm-runner/src/logic/errors.rs:412-423`) intentionally routes `VMLogicError::InconsistentStateError` into `VMRunnerError::InconsistentStateError`, which `function_call.rs` converts into `RuntimeError::StorageError(StorageError::StorageInconsistentState(..))`. In `chain/chain/src/runtime/mod.rs::apply_chunk`, any `StorageError` that is not `FlatStorageBlockNotSupported` or `MissingTrieValue` falls into a catch-all `panic!("{err}")`. If any *attacker-reachable* arithmetic in vm-logic produces `InconsistentStateError` instead of `HostError::IntegerOverflow`, an ordinary contract call could crash the chunk-producing node.

## Finding Description
- `errors.rs:412-423` (`TryFrom<VMLogicError> for FunctionCallError`) explicitly and by design treats `VMLogicError::InconsistentStateError` as a non-recoverable bug, not a chargeable contract failure: [1](#0-0) 
- `runtime/runtime/src/function_call.rs:303-305` converts this into `RuntimeError::StorageError(StorageError::StorageInconsistentState(...))`: [2](#0-1) 
- `chain/chain/src/runtime/mod.rs::apply_chunk` (lines 1266-1271) treats `StorageInconsistentState` (falling into the `_` arm) as fatal and panics the node: [3](#0-2) 

The only concrete production code path that constructs `InconsistentStateError` reachable from contract execution is `RecordedStorageCounter::get_storage_size` / `observe_size` (`runtime/near-vm-runner/src/logic/recorded_storage_counter.rs:19-40`), which does `self.last_observed_storage_size.checked_sub(self.initial_storage_size)`, erroring with `InconsistentStateError::IntegerOverflow` (not `HostError`) if the subtraction underflows: [4](#0-3) 

Everywhere else that performs attacker-influenceable arithmetic (gas accounting in `gas_counter.rs`, per-byte/per-item cost computations in `logic.rs`/`wasmtime_runner/logic.rs`) consistently uses `checked_add/checked_mul/checked_sub(...).ok_or(HostError::IntegerOverflow)`, which is billed gracefully via `FunctionCallError::HostError`: [5](#0-4) [6](#0-5) 

The `RecordedStorageCounter::last_observed_storage_size` is only ever advanced monotonically by `observe_size()`, which is called with the current recorded-storage-proof size after trie operations — this value is derived from internal trie bookkeeping, not directly from any transaction/contract-supplied number. I could not find a call path where a contract or transaction can force `last_observed_storage_size < initial_storage_size` under normal, correct trie bookkeeping (this would require a bug in the trie recording logic itself, not merely "pushing counters to boundary values" through host-call arguments). The other `InconsistentStateError` occurrences in `logic.rs` and `ext.rs` are similarly guard conditions for internal state consistency (e.g., unit-conversion failures like `self.size_limit.try_into()`), not directly reachable via crafted gas/storage counters that an attacker can push across the HostError/InconsistentStateError boundary through repeated ordinary host calls.

## Impact Explanation
If this path were reachable, an unprivileged attacker could crash a chunk producer with a single crafted contract call (`panic!` in `apply_chunk`), which is a liveness/node-crash class impact. However, based on the code inspected, all attacker-reachable arithmetic in the gas/storage-accounting hot paths (`gas_counter.rs`, `logic.rs` per-byte/per-item cost functions) is protected with `.ok_or(HostError::IntegerOverflow)`, which safely converts to a billed `FunctionCallError`, not `InconsistentStateError`. The one place producing `InconsistentStateError` from a `checked_sub` (`RecordedStorageCounter::get_storage_size`) is guarded by an invariant on internally-maintained monotonic bookkeeping rather than externally supplied values, so I did not find a concrete, reproducible attacker input that flips this into the fatal path.

## Likelihood Explanation
Low/unconfirmed. The design intentionally separates "guest-triggerable arithmetic issues" (routed through `HostError::IntegerOverflow`, billed) from "internal bugs / state corruption" (routed through `InconsistentStateError`, fatal). I was unable to locate a call sequence of ordinary host-function invocations that forces `RecordedStorageCounter`'s internal invariant (`last_observed_storage_size >= initial_storage_size`) to break, nor any other attacker-reachable arithmetic that raises `InconsistentStateError` instead of `HostError`. Without such a concrete reachable overflow, this remains a theoretical concern about defense-in-depth rather than a demonstrated vulnerability.

## Recommendation
As a hardening measure (not confirmed exploitable), consider auditing every constructor of `InconsistentStateError`/`VMLogicError::InconsistentStateError` (`recorded_storage_counter.rs`, and any others in `logic.rs`/`ext.rs`) to confirm none of the underlying values can ever be influenced, even indirectly, by an unprivileged caller through ordinary host-call sequences, and add debug-assertions/fuzzing around `RecordedStorageCounter` to guarantee `last_observed_storage_size` is monotonic under all execution paths (including re-entrant/promise/yield-resume flows).

## Proof of Concept
No working PoC was found. A follow-up unit/fuzz test plan (unconfirmed, exploratory) would be:
1. Fuzz `RecordedStorageCounter::observe_size` by simulating trie proof size sequences from realistic execution traces (including yield/resume and cross-contract promise callbacks) to check whether `last_observed_storage_size` can ever regress below `initial_storage_size` for a single receipt's `RecordedStorageCounter` instance.
2. Enumerate all `checked_add/checked_sub/checked_mul` call sites in `gas_counter.rs`, `logic.rs`, `wasmtime_runner/logic.rs`, `ext.rs`, and `recorded_storage_counter.rs`, and assert (via a static check or test) that arithmetic operating on attacker-influenced values (gas amounts, byte lengths, counts) always maps to `HostError`, while `InconsistentStateError` sites are provably restricted to values fully derived from internal, non-attacker-controlled state.

Given the current analysis, I could not establish a concrete attacker-controlled trigger for `InconsistentStateError` through ordinary transaction/contract-call activity; treat this as an area for further defensive verification rather than a confirmed vulnerability.

    /// Update the latest observed storage proof size and check if it exceeds the limit.
    /// Should be called after every trie operation.
    pub fn observe_size(&mut self, latest_storage_proof_size: usize) -> Result<(), VMLogicError> {
        self.last_observed_storage_size = latest_storage_proof_size;

        let current_size = self.get_storage_size()?;
        if current_size > self.size_limit {
            let limit_u64 = self.size_limit.try_into().map_err(|_| {
                VMLogicError::InconsistentStateError(InconsistentStateError::IntegerOverflow)
            })?;
            return Err(VMLogicError::HostError(HostError::RecordedStorageExceeded {
                limit: ByteSize::b(limit_u64),
            }));
        }

        Ok(())
    }

    /// Get the size of storage proof that has been recorded so far by this receipt.
    pub fn get_storage_size(&self) -> Result<usize, VMLogicError> {
        self.last_observed_storage_size
            .checked_sub(self.initial_storage_size)
            .ok_or(VMLogicError::InconsistentStateError(InconsistentStateError::IntegerOverflow))
    }
