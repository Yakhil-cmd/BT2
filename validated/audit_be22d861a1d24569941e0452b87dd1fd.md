### Title
Cross-Organization Authentication Confusion in Webhook Ingestion — signature verified against `repository.owner.login` while all processing keys off `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request's HMAC signature against using the organization login taken from the raw JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), while every `Handler` subsequently resolves the *repository/stack to act on* using a completely different field of the same attacker-controlled body: `payload.dig('repository', 'full_name')`. Because GitHub webhook payloads are attacker-authored JSON (the only protection is the HMAC), nothing enforces that these two fields describe the same repository/organization. This breaks the binding: `organization that authenticated == repository that is written`.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from body content: [1](#0-0) [2](#0-1) 

It then calls `Shipit.github(organization: repository_owner)` and verifies the signature using that organization's `webhook_secret`: [3](#0-2) 

Meanwhile, every webhook `Handler` (base class) resolves the target repository/stacks independently, from an unrelated JSON field: [4](#0-3) 

Since Shipit supports multi-tenant GitHub App configuration (`Shipit.github_app_config`, `Shipit.github_organizations`) each org has its own `webhook_secret`: [5](#0-4) 

An attacker who legitimately controls one configured organization ("attacker-org", with a GitHub App installed and thus knowledge of *their own* `webhook_secret`) can submit a POST to `/webhooks` where `repository.owner.login` (or `organization.login`) is set to `"attacker-org"` — making `verify_signature` compute/verify the HMAC against a secret the attacker legitimately possesses — while `repository.full_name` is set to `"victim-org/victim-repo"`. The signature check passes, and the handler then acts on `victim-org/victim-repo`'s `Stack`/`Commit` records.

`StatusHandler` is the most severe instance: it does not even scope to a repository/stack at all — it looks up `Commit.where(sha: params.sha)` globally across the entire Shipit instance and writes a fabricated CI status: [6](#0-5) [7](#0-6) 

This directly feeds `Commit#deployable?` and the continuous-delivery scheduling path: [8](#0-7) [9](#0-8) 

Other handlers (`PushHandler`, `CheckSuiteHandler`, `pull_request/*Handler`) are similarly reachable cross-organization via the `Repository.from_github_repo_name(repository_name)` lookup in the shared `Handler#stacks` helper, letting an attacker who authenticates as their own org trigger `sync_github`, archive review stacks, or schedule check-run refreshes on a victim's stack: [10](#0-9) [11](#0-10) 

### Impact Explanation
This crosses an authentication boundary: the request is validated as authentic for organization A (using A's own webhook secret, which the attacker legitimately controls) but is used to mutate state belonging to organization B (repository/stack lookup via `full_name`), which the attacker does not control and whose webhook secret they do not know. Concretely:
- `StatusHandler` lets an attacker forge a passing CI status for an arbitrary commit SHA in any tracked stack instance-wide, which combined with `continuous_deployment` and `deployable?` can trigger an **unauthorized automatic deploy** of a commit that never actually passed CI.
- `PushHandler`/`CheckSuiteHandler` can force `sync_github` or check-run refresh cycles on a victim stack, and `pull_request` handlers can archive/manipulate victim review stacks.

This matches the report's "Critical/High" bar: unauthorized deploy caused by a broken equality between the credential used to authenticate a request and the resource that credential is allowed to act on.

### Likelihood Explanation
Requires the attacker to be an onboarded tenant/organization in a multi-org Shipit deployment (they know their own `webhook_secret` because they configured it, not the victim's). Given the rule set explicitly treats "an organization that authenticated versus the repository that is written" as an in-scope unprivileged-attacker analog, and Shipit's own multi-tenant `github_app_config` design implies multiple independently-trusted organizations share one webhook endpoint and one `Repository`/`Commit` namespace, this is a realistic configuration, not a theoretical edge case.

### Recommendation
Bind the webhook signature verification to the same repository identity that handlers act on. Concretely: extract `repository.full_name` (or `organization.login` consistently used by every handler) once, verify the signature using the organization derived from that exact field, and then require every `Handler` to re-derive `organization/repository` from the same normalized field used for verification — or better, look up the owning organization from the already-persisted `Repository` record (trusted DB data) rather than from unauthenticated JSON, and reject the webhook if the signing organization does not match the organization owning the target repository.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` (multi-tenant `secrets.github` config).
2. Attacker, who legitimately knows `attacker-org`'s `webhook_secret`, crafts a `status` event body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (global, unscoped) and calls `create_status_from_github!`, writing a forged "success" CI status onto the victim's commit — potentially triggering `schedule_continuous_delivery` and an unauthorized deploy of that commit in `victim-org/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
