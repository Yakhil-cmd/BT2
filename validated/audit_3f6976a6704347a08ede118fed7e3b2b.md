The `readAsset` function in `storage.js` always fetches the **latest** attestor list unit (`ORDER BY level DESC LIMIT 1`) relative to `last_ball_mci`, meaning that at any moment, the asset definer can post a new `asset_attestors` message that supersedes the existing list, and this immediately affects the ability of all existing holders of the asset to move their coins.

### Title
Asset definer can freeze all holders of a `spender_attested` asset at will by updating the attestor list - (File: `validation.js`, `storage.js`)

### Summary
Assets created with `spender_attested: true` require every payer, payee, and issuer to be on a definer-controlled attestor whitelist at the time a payment is validated. The whitelist (`asset_attestors` message) can be replaced by the single `definer_address` at any time, with no timelock or restriction, and the change takes effect for all future spends of coins that were already issued and held by users before the change. This mirrors the reported bug class of a single privileged party being able to reconfigure a critical parameter post-hoc and lock users out of funds they already hold.

### Finding Description
When an asset is defined with `spender_attested=true`, every payment of that asset must have all input and output addresses present in the attestor-filtered address list computed at validation time, not at issue time: [1](#0-0) [2](#0-1) 

The attestor list used for this check is not fixed at asset creation — `storage.readAsset` always looks up the *latest* `asset_attestors` unit as of `last_ball_mci`: [3](#0-2) 

Updating this list is gated only by a check that the sole author of the `asset_attestors` message equals `objAsset.definer_address` — there is no cap on how often it can change, no grandfathering of previously-attested addresses, and no timelock: [4](#0-3) 

Because `filterAttestedAddresses` re-queries `attestations` against whatever `arrAttestorAddresses` is current at spend time, a definer can publish a new `asset_attestors` unit pointing to attestor addresses that will never attest anyone (e.g., addresses only the definer controls, or that are simply never used to publish attestations again): [5](#0-4) 

The result: users who received/hold this asset under the *old* attestor regime, and who were validly attested under it, become permanently unable to spend those existing outputs the moment the definer swaps the attestor list, since the check `arrAttestedAddresses.length === 0` (or per-output attestation check on outputs) now fails against the new list.

### Impact Explanation
This directly matches the "admin can brick user access to funds" bug class from the external report: a single privileged actor (here, the asset `definer_address`, reachable as an ordinary asset-issuing unit author) can, at any time and without any multi-party consent or delay, invalidate every existing holder's ability to transfer or spend an asset they legitimately hold. This is a fund-freezing DoS specific to a widely-used ocore primitive (attested/whitelisted assets), impacting any user who ever received such an asset.

### Likelihood Explanation
Low-to-medium: it requires the asset definer (equivalent to the "admin" in the external report) to be malicious or compromised, same likelihood class as the source report. No cooperation from other parties, hubs, or witnesses is required — a single `asset_attestors` unit posted by the definer suffices.

### Recommendation
- Require attestor-list changes to only add attestors, or provide an on-chain grace/timelock period during which old attestations remain valid for spending previously-issued outputs.
- Snapshot/grandfather attestation validity at output-creation time rather than re-checking against the current attestor list for previously issued/held coins.
- Document to asset issuers/users that `spender_attested` assets carry definer-controlled freeze risk, and consider surfacing this in the address/asset explorer UI so holders can evaluate this risk before acquiring the asset.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and initial attestor `X`.
2. `X` attests holder `U`'s address via an `attestation` message referencing `A`'s attestor set.
3. `U` receives/holds asset `A` outputs and can spend them (checked via `validation.js:2115-2122`).
4. `D` posts a new `asset_attestors` message for asset `A` naming attestor `Y` (an address `D` controls or that will never publish attestations) — accepted per `validation.js:2829-2848` since `D` is `definer_address`.
5. `storage.readAsset` now resolves the attestor set to `Y` only, per `storage.js:1917-1946`.
6. `U` attempts to spend previously-held `A` outputs; `filterAttestedAddresses` finds no attestation by `Y` for `U`, so `arrAttestedAddresses` is empty, and validation fails with "none of the authors is attested" (`validation.js:2118-2119`), freezing `U`'s funds indefinitely with no recourse.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
