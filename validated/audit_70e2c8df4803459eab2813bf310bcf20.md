### Title
Commit-status webhook handler writes to any commit in the database without scoping to the authenticated organization/repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up the target `Commit` purely by `sha`, with no check that the `sha` belongs to the repository/organization whose `webhook_secret` was used to authenticate the request. This breaks the equality that should hold between "organization that authenticated the webhook" and "repository (stack) that gets written to," mirroring the analog bug class described in the C4 report (funds/fields acted upon that are not covered by the value actually validated).

### Finding Description
`WebhooksController#verify_signature` authenticates the inbound webhook using the `webhook_secret` configured for the organization derived from the payload (`repository.owner.login` or `organization.login`): [1](#0-0) 

This only proves that the sender knows the `webhook_secret` for *that* organization; it says nothing about which `sha`/commit/stack the rest of the payload is allowed to reference.

The `status` event is then dispatched to `StatusHandler#process`, which resolves the record to mutate using `params.sha` alone, with no join/filter on repository or stack: [2](#0-1) 

Unlike other handlers (`PushHandler`, PR handlers) that scope lookups through `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` before touching any records: [3](#0-2) [4](#0-3) 

`StatusHandler` never calls `stacks`/`repository_name` at all. `Commit#sha` is not unique per organization in Shipit's schema — it's a global lookup across every stack tracked by the instance. So the binding that should hold is:

`organization authenticated (via webhook_secret) == organization owning the commit/stack written`

but the code only enforces "signature is valid for *some* configured organization," and then writes to whatever `Commit` row matches the attacker-supplied `sha`, regardless of which organization that commit's stack belongs to.

### Impact Explanation
An attacker who legitimately owns/administers **any** one organization configured in this Shipit instance (and therefore possesses a real, validly-issued `webhook_secret` for that org from GitHub) can sign a forged `status` webhook payload and target a `sha` belonging to a completely different organization's stack. Because `Commit.where(sha: params.sha)` is unscoped, the attacker can: [2](#0-1) 

- Forge a "success" CI status on a victim commit belonging to an unrelated, higher-privilege stack, potentially unblocking merge/deploy gating that consults commit statuses (`Commit#create_status_from_github!`) in that stack's pipeline.

This crosses an authentication boundary: proof-of-knowledge of Org A's secret is used to write state belonging to Org B, which fits the "unauthorized deploy/merge" impact bucket in scope.

### Likelihood Explanation
Exploitability requires only: (1) the attacker legitimately controls one organization/repository already onboarded to the same Shipit instance (a normal, unprivileged tenant of a multi-org Shipit deployment), and (2) knowledge of the target commit `sha` (public information visible on GitHub for any commit in the victim repo). No access to the victim's `webhook_secret`, GitHub App keys, or Shipit session/API token is required — only the attacker's own legitimately-issued webhook secret and the public git history of the target repository.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to commits belonging to stacks in the repository identified by the authenticated payload, e.g. join through `stacks`/`Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` (as done in `Handler#stacks`/`Handler#repository_name`) before writing any status, and reject/no-op if the resolved commit's repository does not match the organization that produced a valid signature.

### Proof of Concept
1. Attacker registers/owns Organization A in the target multi-org Shipit deployment, obtaining a real `webhook_secret` for Org A (`Shipit.github(organization: 'orgA').verify_webhook_signature` will succeed for payloads signed with this secret).
2. Attacker discovers (via public GitHub) a commit `sha` belonging to Organization B's repository, which is also tracked by the same Shipit instance as a stack.
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "<Org B's commit sha>",
  "state": "success",
  "context": "ci/forged",
  "description": "forged green build",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/attacker-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using Org A's real `webhook_secret` (`WebhooksController#verify_signature` succeeds because `repository_owner` resolves to `orgA`) and POSTs to `/github` with `X-Github-Event: status`.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, creating a forged "success" status on Organization B's commit, even though the signature only proved control of Organization A's secret.
