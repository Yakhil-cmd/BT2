### Title
Tool-representation mismatch in `_extract_field` lets a `Write` call bypass a block rule that correctly blocks the equivalent `Edit` call - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._check_condition` delegates field extraction to `_extract_field`, which maps the documented field name `new_text`/`new_string` to `tool_input.get('new_string', '')` for both `Write` and `Edit` tools. Since `Write` tool_input never contains a `new_string` key (it uses `content`), any block rule written against `field: new_text` silently evaluates against an empty string for `Write` calls while correctly evaluating the real content for `Edit` calls, letting semantically identical dangerous content bypass detection when delivered via `Write` instead of `Edit`.

### Finding Description
`RuleEngine._rule_matches` calls `_check_condition(condition, tool_name, tool_input, input_data)` for every configured condition, and `_check_condition` calls `_extract_field(condition.field, tool_name, tool_input, input_data)` to obtain the text to test against the rule's pattern: [1](#0-0) 

`_extract_field`'s docstring explicitly lists `new_text` as a supported, general field name: [2](#0-1) 

For `Write`/`Edit` tools, the implementation is: [3](#0-2) 

`tool_input.get('new_string', '')` only returns real content for `Edit` (whose tool_input schema uses `old_string`/`new_string`); for `Write`, whose tool_input schema uses `file_path`/`content`, this always evaluates to `''`. Since `_check_condition` only short-circuits to `False` when `field_value is None` (not when it's an empty string), an empty string is fed straight into the configured operator (e.g. `regex_match`, `contains`, `starts_with`), which will never match a non-empty pattern. Any block rule using `tool_matcher: "Write|Edit"` (or `"*"`) with `field: new_text`/`new_string` therefore silently and permanently fails to fire for `Write` calls while correctly firing for `Edit` calls with the exact same content. An attacker who can influence what content Claude writes (e.g., via prompt injection driving a `Write` tool call instead of an `Edit` call) can place the same dangerous payload that a rule is designed to block, and have it pass through unblocked purely because of the tool representation chosen, even though the rule's `tool_matcher` explicitly includes `Write`.

### Impact Explanation
This breaks the core invariant that "a matching block rule must reliably deny the protected operation." A project relying on hookify to block dangerous file content (secrets exfiltration markers, malicious code patterns, credential injection, etc.) across both `Write` and `Edit` will have that protection silently defeated whenever the tool used is `Write`, since the rule engine feeds an empty string into the matcher instead of the real content. This can lead to unauthorized file mutation with real content the operator believed was blocked, matching a "wrong-target mutation with real security impact" bounty class for Claude Code's local tool-guarding hooks.

### Likelihood Explanation
This is fully deterministic and requires no special privileges beyond what the hookify feature already assumes (a configured block rule with `field: new_text`/`new_string` and `tool_matcher` including `Write`). Any flow that causes Claude to perform a `Write` tool call with attacker-influenced content (e.g., prompt injection from untrusted repository/issue content instructing Claude to write a file rather than edit an existing one) reliably reproduces the bypass, since the field-extraction gap is unconditional and not dependent on race conditions or timing.

### Recommendation
In `_extract_field`, mirror the same fallback logic used for the `content` field when handling `new_text`/`new_string` for `Write`/`Edit`: return `tool_input.get('new_string') or tool_input.get('content', '')` (and similarly handle `old_text`/`old_string` consistently, returning `None`/empty appropriately per tool) so a rule targeting the "new content" concept behaves identically regardless of whether the tool used is `Write`, `Edit`, or `MultiEdit`. Additionally, consider treating an empty-string extraction that stems from a missing/unsupported field-tool combination as `None` (no match possible) rather than silently proceeding, to fail closed/loud instead of failing open.

### Proof of Concept
Unit test added to a test module exercising `RuleEngine`:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-secret-leak",
    enabled=True,
    event="file",
    tool_matcher="Write|Edit",
    conditions=[Condition(field="new_text", operator="contains", pattern="SECRET_TOKEN")],
    action="block",
)
engine = RuleEngine()

# Edit call with dangerous content - correctly blocked
edit_input = {
    "tool_name": "Edit",
    "tool_input": {"file_path": "x.txt", "old_string": "a", "new_string": "leak SECRET_TOKEN here"},
}
assert engine.evaluate_rules([rule], edit_input) != {}  # blocked as expected

# Equivalent Write call with identical dangerous content - bypasses the rule
write_input = {
    "tool_name": "Write",
    "tool_input": {"file_path": "x.txt", "content": "leak SECRET_TOKEN here"},
}
assert engine.evaluate_rules([rule], write_input) == {}  # BUG: not blocked, should be blocked
```
Expected: both calls should be denied; actual current behavior allows the `Write` call through, demonstrating the tool-representation bypass.
