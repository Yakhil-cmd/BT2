### Title
Signature verified against `repository.owner.login` while stack-mutating actions use `repository.full_name` - cross-tenant `ReviewStack` archive/unarchive - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC using `params.dig('repository', 'owner', 'login')` [1](#0-0) , while `LabeledHandler#repository` resolves the target `Repository` (and thus the `ReviewStack` to mutate) using the independent `params.repository.full_name` field [2](#0-1) . Because these two JSON fields are never cross-validated against each other, an attacker who owns a GitHub org/repo (and therefore its webhook secret) can send a validly-signed payload for their own org while setting `repository.full_name` to a victim org/repo, causing `stack.archive!`/`stack.unarchive!` to run against the victim's `ReviewStack`.

### Finding Description
The broken binding is: `organization_used_for_signature (params.repository.owner.login) == organization_owning_the_mutated_repository (Repository.from_github_repo_name(params.repository.full_name).owner)`. This equality is never enforced anywhere in the code.

Trace:
1. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes solely from `params.dig('repository', 'owner', 'login')` [3](#0-2) . It then verifies `X-Hub-Signature` against that organization's configured `webhook_secret` via `GitHubApp#verify_webhook_signature`, which HMACs the raw JSON body [4](#0-3) .
2. If verification succeeds, the entire raw JSON body -- including any `repository.full_name` value chosen by the attacker -- is handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) .
3. `LabeledHandler#repository` looks up the `Repository` model using `params.repository.full_name` [2](#0-1)  — a completely separate JSON field from the one used for signature verification.
4. `respond_to_label_change?`, `archive?`, and `unarchive?` then evaluate the victim repository's `review_stacks_enabled` and `provisioning_behavior_*` configuration together with the attacker-supplied `pull_request.labels` array [6](#0-5) .
5. `handle` calls `stack.archive!` or `stack.unarchive!` on the `ReviewStackAdapter` scoped to `repository.review_stacks` -- i.e., the victim's stacks [7](#0-6) .

Attacker request: POST `/webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature` computed with the attacker's own org webhook secret, and a JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`, `action = "labeled"`, `pull_request.state = "open"`, `pull_request.number` matching an existing review-stack PR, and `pull_request.labels` containing the victim's configured `provisioning_label_name`.

Existing guards do not catch this: `verify_signature` only checks that *some* valid signature exists for *the org named in `repository.owner.login`* — it never confirms that org matches the org embedded in `repository.full_name` that the handlers subsequently trust. `ExplicitParameters` schema only enforces types/presence, not cross-field consistency [8](#0-7) . `drop_unhandled_event` and `check_if_ping` are unrelated to this issue.

### Impact Explanation
A payload that is validly signed for the attacker's own organization can trigger `stack.archive!` (deprovisioning: destroying the review environment) or `stack.unarchive!` (re-provisioning: re-triggering a git checkout/deploy) on a review stack that belongs to a completely different tenant's repository. This is a payload for one repository mutating another's stack, matching the "Critical" impact category explicitly listed in the rules. The attack is repeatable against any victim repository whose `full_name` is known/guessable and which has `review_stacks_enabled` and a guessable `provisioning_label_name`; the attacker needs no privilege over the victim org, only ownership of any GitHub org/repo capable of emitting a signed webhook to the shared Shipit host.

### Likelihood Explanation
Preconditions: victim repository must have `review_stacks_enabled` and `provisioning_behavior_prevent_with_label` (or `allow_with_label`) configured with some `provisioning_label_name`, and an existing `ReviewStack`/PR-numbered review stack record. The label name is typically a short, human-readable string (e.g., "deploy", "preview") and is plausible to guess or brute force in a handful of attempts, as noted in the question. The attacker's cost is minimal: they only need to own any repository connected to the same Shipit instance (or any GitHub org configured in `Shipit.github_teams`/`config/secrets`) to obtain a valid webhook secret for signing, then craft an arbitrary JSON body with a mismatched `full_name`. No GitHub API access, session, or Shipit credentials for the victim org are required.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler's `repository` resolution), enforce that the organization used to select/verify the webhook secret matches the organization embedded in `repository.full_name` before any handler is allowed to mutate state. Concretely: parse `repository.full_name`'s owner segment and require it to equal `repository.owner.login` (reject with 422 on mismatch), or have `Shipit.github(organization:)` derive the organization exclusively from `repository.full_name` so the two can never diverge.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/labeled_handler_test.rb` style):
1. Create `victim_repo = shipit_repository(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: :prevent_with_label, provisioning_label_name: "deploy")` and an existing `ReviewStack`/stack for PR `#7` that is currently active (`archived?` == false).
2. Configure `Shipit.github(organization: "attacker-org")` with a known webhook secret; do NOT configure any secret usable for `"victim-org"` (or configure a different one) to prove the attacker never touches the victim's secret.
3. Build the JSON payload: `{ action: "labeled", number: 7, pull_request: { ..., number: 7, state: "open", labels: [{name: "deploy"}] }, repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" }, sender: {...} }`.
4. Sign the raw body with `attacker-org`'s webhook secret and set `X-Hub-Signature`.
5. `assert_equal "attacker-org", JSON.parse(body)["repository"]["owner"]["login"]` and `assert_equal "victim-org/victim-repo", JSON.parse(body)["repository"]["full_name"]` to state the mismatch explicitly.
6. POST to `/webhooks` with `X-Github-Event: pull_request`.
7. `assert_response :ok`.
8. Reload the victim stack and `assert victim_stack.archived?` (or `refute`, depending on `prevent_with_label` semantics), proving a request signed only by `attacker-org` flipped state on `victim-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
