### Title
Webhook signature verification selects the GitHub App/org config from an unauthenticated `repository.owner.login` field while all downstream handlers act on a separate, unvalidated `repository.full_name` / `organization.login` field — decoupling "org whose secret verified the payload" from "org/repo actually acted upon" - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` config (and thus which `webhook_secret`) to validate the request signature against by reading an attacker-controlled JSON field (`repository.owner.login`, falling back to `organization.login`) from the *same unauthenticated payload* it is about to verify. Every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, `MembershipHandler`, etc.), however, acts on a *different* field of that payload (`repository.full_name`, `organization.login` reused elsewhere, `sha`, `team.id`, …) without ever checking that it belongs to the organization whose secret validated the signature. This is structurally the same class of bug as the LSSVMPairETH issue: the entity used to satisfy the "authorization" check (`_feeRecipient` / here, "org selected for HMAC verification") is not the same entity that the effect is ultimately applied to (`_assetRecipient` / here, "repository or team actually mutated"), so the equality the code implicitly assumes (`verified-org == acted-on-repo/org`) does not hold.

### Finding Description
In a multi-org Shipit deployment (`docs/setup.md`'s "Using Multiple Github Applications" section, `config/secrets.*.yml` with per-org `github: {OrgOne: {...}, OrgTwo: {...}}`), each organization has its own `GitHubApp` instance with its own `webhook_secret`.

`verify_signature` in `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read straight out of the untrusted, attacker-supplied JSON body, and it is used solely to *select* which org's `webhook_secret` will validate the HMAC. Once `verified == true`, the raw, unmodified `params` object is dispatched to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

The base `Handler` resolves the affected repository from a *separate* field, `repository.full_name`, with no cross-check against `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` (and PR handlers, `CheckSuiteHandler`, etc.) then act on whatever `stacks`/`repository.full_name` resolves to:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

`MembershipHandler` similarly trusts `organization.login` from the payload to create/attach `Team` records that feed directly into `Shipit.github_teams` authorization:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [5](#0-4) 

Root cause: `verify_webhook_signature` only proves "this raw body was HMAC-signed with Org X's secret"; it says nothing about which repository/org the body's *content fields* claim to describe. The `repository_owner` field used to pick Org X and the `repository.full_name`/`organization.login` fields used by every handler are two independent, attacker-writable JSON keys inside the same signed blob — nothing forces them to refer to the same organization. Additionally, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank/unset (`return true unless webhook_secret`) — a state explicitly supported and documented as "optional" in `docs/setup.md`/`config/secrets.*.yml` (`webhook_secret: # nil`): [6](#0-5) [7](#0-6) 

This means: the binding the code should enforce is `organization(verified-by-signature) == organization(repository.full_name in payload)`. Concretely, in any Shipit instance configured for multiple GitHub organizations (a documented, supported configuration), an attacker who controls (or knows the webhook secret of, or whose org has a blank secret configured) *any one* of the configured organizations can forge a webhook body claiming `repository.owner.login = <OrgWithKnownOrBlankSecret>` (used only for signature selection) while setting `repository.full_name = <VictimOrg>/<victim-repo>` (used by every handler to find and mutate `Stack`/`Commit`/`Team` records). The signature check passes against the attacker's own org, but the mutation is applied to a completely unrelated organization's tracked repository/stack.

### Impact Explanation
This breaks the deployment-trust binding "GitHub organization authenticated via HMAC" vs "repository/organization actually written," matching the required High/Critical impact classes:
- `StatusHandler`/`CheckSuiteHandler` let the attacker inject forged commit statuses/check-run refresh triggers for commits belonging to a victim organization's stack, which can be used to fake CI approval used by Shipit's deploy safety checks — a path toward an unauthorized/forged deploy signal on a repository the attacker does not control.
- `PushHandler` triggers `stack.sync_github` for a victim stack using an attacker-forged `after` SHA.
- `MembershipHandler` creates/updates `Team` records keyed by attacker-controlled `organization.login` and `team.id`, and adds/removes members from teams — this directly touches `Shipit.github_teams` authorization data, matching the explicit High-severity "escalation into `Shipit.github_teams` authorization" criterion.

The severity is bounded by the precondition that a multi-org configuration exists and the attacker controls or knows the (possibly blank) `webhook_secret` of at least one configured organization — this is a real, documented, supported deployment mode (`docs/setup.md`, "Using Multiple Github Applications"), not a hypothetical misconfiguration outside the engine's own code.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub organizations (explicitly documented/supported), and (2) the attacker being able to produce a validly-signed body for at least one of those configured orgs — trivially true if that org's `webhook_secret` is left blank (explicitly supported: `webhook_secret: # nil`), or if the attacker is a legitimate member/admin of one org in a shared multi-tenant Shipit instance. No session, `ApiClient` token, or repository write access to the *victim* repository is needed — the whole point of the bug is that no such credential is required for the targeted org.

### Recommendation
After signature verification succeeds against `Shipit.github(organization: repository_owner)`, re-derive the acted-upon organization from the same trusted field (`repository_owner`) and require it to match the organization component of `repository.full_name` (and of `organization.login` for org-level events like `membership`) before dispatching to handlers. Alternatively, pass the verified `repository_owner`/`github_app` into each handler and have `Handler#repository_name`/`Repository.from_github_repo_name` reject any repository whose owner does not equal the organization that successfully verified the signature.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `OrgAttacker` (attacker-known/blank `webhook_secret`) and `OrgVictim` (real secret, tracks stack `OrgVictim/prod-app`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgVictim/prod-app" }
}
```
3. `repository_owner` resolves to `"OrgAttacker"`; `Shipit.github(organization: "OrgAttacker")` is used for HMAC verification, which the attacker satisfies (known/blank secret) — `X-Hub-Signature` need not relate to `OrgVictim` at all.
4. `verified == true`, so `PushHandler` runs on `params`, resolving `stacks` via `repository.full_name = "OrgVictim/prod-app"`, triggering `stack.sync_github(expected_head_sha: "deadbeef")` on the victim organization's tracked stack — despite the attacker never proving control of `OrgVictim`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
