Confirmed: `validateAATrigger` in `validation.js` only counts payment messages where `m.payload` exists (`m.app === 'payment' && m.payload`), so `objValidationState.count_primary_aa_triggers` is set based on outputs read from `m.payload.outputs` — a message with `app: 'payment'` but `payload_location: 'none'` (no `payload` field, as used for private-asset payments) is simply skipped by this loop and doesn't get counted. That means the dry-run code path's own `objJoint.unit.messages.filter(msg => msg.app === 'payment')` filter (network.js:1272-1274) is broader than what produced `count_primary_aa_triggers`, but since a payload-less private payment message never contributes to `count_primary_aa_triggers`, the trigger-count gate alone won't fire from *that* message. However, if the same unit also contains a second, normal public payment message to an AA address (which legitimately sets `count_primary_aa_triggers`), the `.filter(msg => msg.app === 'payment')` in the dry-run block still iterates over **all** payment messages in the unit, including the payload-less private one, and unconditionally does `msg.payload.outputs` — throwing `TypeError: Cannot read properties of undefined (reading 'outputs')` for that message.

### Title
Unhandled TypeError (NULL/undefined payload dereference) in AA dry-run trigger path crashes full nodes - (File: network.js)

### Summary
`handleJoint`'s `ifOk` callback in `network.js` performs an optional "dry run" of newly submitted AA triggers when `conf.bDryRunNewTriggers` is enabled. It builds `outputAddresses` by mapping over `payload.outputs` for every message with `app === 'payment'` in the unit, without checking that `payload` exists. A unit that legitimately mixes a public payment (that targets an AA address, thereby satisfying `objValidationState.count_primary_aa_triggers`) with a private-payment message (`payload_location: "none"`, which validly has no `payload` field on the public joint) passes full unit/joint validation but crashes the node when the dry-run block dereferences `msg.payload.outputs` on the payload-less message.

### Finding Description
`validation.js`'s `validateMessages`/inline-payload checks explicitly allow `payload_location !== "inline"` messages (e.g. `"none"`, used for private assets) to have no `payload` field at all [1](#0-0) . `validateAATrigger` (which sets `objValidationState.count_primary_aa_triggers`) only inspects payment messages that actually carry a `payload` (`if (m.app === 'payment' && m.payload)`), so payload-less payment messages are silently skipped when counting/finding AA-trigger outputs [2](#0-1) . Consequently a unit can validate successfully with `count_primary_aa_triggers >= 1` (from one public output to an AA address) while also containing an unrelated `app: 'payment'` message whose `payload_location` is `"none"` and which has no `payload` property.

After validation succeeds, `network.js`'s `ifOk` handler — reachable for both posted (`handlePostedJoint`) and network-received units — runs a "dry run" of the AA trigger when `conf.bDryRunNewTriggers && !conf.bLight && !objJoint.ball && objValidationState.count_primary_aa_triggers` are all true. The `.filter(msg => msg.app === 'payment')` step matches *every* payment message in the unit, including the payload-less one, and the `.reduce()` immediately does `msg.payload.outputs.map(...)` without any existence check, throwing a `TypeError` because `msg.payload` is `undefined`.

Because this callback is declared `async function` and is not wrapped in a try/catch by its caller, the thrown exception surfaces as an unhandled promise rejection. In modern Node.js this either directly crashes the process, or (if it slips through) the codebase's global `process.on('uncaughtException', ...)` handler explicitly `throw`s the error again to intentionally crash the process to avoid an inconsistent state [4](#0-3) . This is the direct analog of CVE-2025-32398: a single attacker-crafted (but validation-passing) unit dereferences a missing/NULL field deep in message processing, crashing the node the same way a malformed RPC packet null-derefs and crashes a P-Net IO device.

### Impact Explanation
Any full node (non-light, `conf.bDryRunNewTriggers` enabled) that receives or is asked to relay such a unit crashes when it reaches `ifOk`. This is triggerable by an ordinary, unprivileged unit poster — no special key or node-operator access is required — by simply crafting one unit that (a) has at least one public payment message paying an AA address, and (b) includes an additional `app: 'payment'` message using `payload_location: "none"` (the standard way private-asset payment messages are represented on public joints) without ever needing that private chain to actually validate first. Repeated posting of such units against a targeted node (or broadcast so it propagates network-wide before crashing recipients) causes a denial of service, matching "a network unable to confirm new units" if enough validating nodes have this flag/config path active.

### Likelihood Explanation
Requires `conf.bDryRunNewTriggers` to be truthy and the node to be a full (non-light) node processing a not-yet-balled unit — this is a conf-gated code path, so exploitability is contingent on that setting being enabled in the target deployment(s); I could not verify from the available index whether `bDryRunNewTriggers` defaults to `true` or is opt-in in `conf.js` (the file wasn't retrievable in full through the search index). If it is enabled by default or commonly enabled in production full nodes, likelihood is high since crafting the malformed-but-valid unit requires no privileges, just correct construction of a payload-less `payment` message alongside a public AA-targeting payment.

### Recommendation
In `network.js`, guard the dry-run output-address extraction against payload-less payment messages, e.g. filter on `msg.app === 'payment' && msg.payload` (mirroring the check already used in `validateAATrigger`) before accessing `msg.payload.outputs`, and wrap the whole dry-run block (or at minimum the `await` calls) in a try/catch that degrades gracefully (skip the dry run) instead of allowing an uncaught exception to propagate and crash the node.

### Proof of Concept
1. Ensure the target full node runs with `conf.bDryRunNewTriggers = true` and is not a light node.
2. Craft and post/broadcast a unit with two payment messages:
   - Message A: normal inline `app: 'payment'` message with an output to a known AA address (so `validateAATrigger` sets `objValidationState.count_primary_aa_triggers = 1`).
   - Message B: `app: 'payment'`, `payload_location: "none"`, with a correct `payload_hash` but no `payload` field (as is valid/required for messages whose payload is delivered out-of-band, e.g. private asset payments).
3. Ensure both messages pass `validation.js`'s hash/structure checks (message B needs no `payload` present at all, matching lines 227-233 of `validation.js`).
4. Submit the unit to the target node (via `handlePostedJoint` or normal broadcast). Once `validation.validate` calls back `ifOk`, the dry-run block executes `messages.filter(msg => msg.app === 'payment').reduce((acc, msg) => acc.concat(msg.payload.outputs...))`, throwing `TypeError: Cannot read properties of undefined (reading 'outputs')` on message B and crashing the node process.
