### Title
`provision?` operator-precedence bug lets `allow_with_label`/`prevent_with_label` bypass `review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses Ruby's `&&`/`||` precedence such that `review_stacks_enabled` only gates the `allow_all` branch, not the `allow_with_label` or `prevent_with_label` branches. Any repository configured with `provisioning_behavior: allow_with_label` or `prevent_with_label` will auto-provision `ReviewStack`s from attacker-controlled pull requests even if `review_stacks_enabled` is `false`.

### Finding Description
The claimed binding `repository.review_stacks_enabled == true` must hold before any `ReviewStack` is created for any `provisioning_behavior`. The actual code is: [1](#0-0) 

Due to `&&` binding tighter than `||`, this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So when `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, `review_stacks_enabled` is never consulted. `process` calls `respond_to_pull_request_opened?` which calls `provision?`, and on a true result immediately builds a `ReviewStackAdapter` and calls `find_or_create!`, creating and enqueueing a `Stack`/`ReviewStack` for provisioning: [2](#0-1) .

The `db/migrate/20201001125502_add_provision_pr_stacks_flag_to_repositories.rb` migration sets `review_stacks_enabled` default `false` and `provisioning_behavior` default `allow_all`, which is a safe combination by itself (since `allow_all` is properly gated). The vulnerable state only arises once an operator sets `provisioning_behavior` to `allow_with_label` or `prevent_with_label` — regardless of what they set (or believe they set) `review_stacks_enabled` to. The existing test suite (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`) never exercises `review_stacks_enabled: false` combined with `allow_with_label`/`prevent_with_label`, so this divergence is untested and unnoticed.

No other guard intercepts this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?`; there is no separate `review_stacks_enabled` check elsewhere in the call path, and webhook signature verification is orthogonal (it authenticates that GitHub sent the event, not what the payload logically implies).

### Impact Explanation
Any attacker who can open a pull request (or push a labeled PR) against a repository configured with `provisioning_behavior: allow_with_label` (and simply add the configured label) or `prevent_with_label` (by default, no label) causes an unauthorized `ReviewStack`/`Stack` to be created and queued for provisioning via `ReviewStackProvisioningQueue`, even though the operator has `review_stacks_enabled: false` and believes review-stack automation is fully disabled. Provisioning drives the standard Shipit task/deploy pipeline (`Command`/`PTY.spawn`-based tasks) against the PR's branch content, so this results in unauthorized execution of the provisioning pipeline against attacker-influenced branch/environment for that repository — matching the Critical "unauthorized deploy"/RCE-via-provisioning category. It is repeatable against any repository sharing this configuration and requires no elevated privileges beyond opening/labeling a PR.

### Likelihood Explanation
Requires a specific but plausible operator misconfiguration: `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` (a state an operator would reasonably believe fully disables automation, per the setting's name). The migration's default combination (`allow_all` + `review_stacks_enabled: false`) is not exploitable; exploitation requires the operator to have changed `provisioning_behavior` away from the default without enabling `review_stacks_enabled`. Given `review_stacks_enabled` sounds like a master switch, this is a realistic and low-cost misconfiguration for an attacker to find and exploit repeatedly.

### Recommendation
Fix operator precedence in `provision?` by explicitly parenthesizing so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest plan (place in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "review_stacks_enabled: false must block provisioning for every PROVISIONING_BEHAVIORS value" do
  repository = shipit_repositories(:shipit)
  Shipit::Repository::PROVISIONING_BEHAVIORS.each do |behavior|
    configure_provisioning_behavior(
      repository:,
      provisioning_enabled: false,
      behavior: behavior.to_sym,
      label: "pull-requests-label"
    )
    payload = payload_parsed(:pull_request_opened)
    payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

    assert_no_difference -> { Shipit::Stack.count }, "behavior=#{behavior} bypassed review_stacks_enabled=false" do
      OpenedHandler.new(payload).process
    end
  end
end
```
Binding assertion: for every `behavior`, `repository.review_stacks_enabled == false` implies `Shipit::Stack.count` unchanged. Expected: fails for `allow_with_label` and `prevent_with_label`, confirming the precedence bug bypasses the intended master switch.
