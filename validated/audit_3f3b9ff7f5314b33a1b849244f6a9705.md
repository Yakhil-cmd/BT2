### Title
CCMenu API endpoint bypasses stack-scoped `ApiClient` authorization, allowing cross-stack read of deploy/build state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a specific `stack_id`, e.g. via `here_come_the_walrus` fixture) can only resolve `stack` from the set of stacks it is bound to [1](#0-0) . `Shipit::Api::CCMenuController` overrides both `authenticate_api_client` and `stack`, resolving the requested stack directly via `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!` helper [2](#0-1) . This breaks the intended equality `token.authorized_stacks == stacks the token can query`.

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack` association (`belongs_to :stack, optional: true`) [3](#0-2) , and the fixture `here_come_the_walrus` demonstrates such a stack-scoped, `read:stack`-only token used in tests [4](#0-3) . The intended access boundary is implemented once, in `BaseController#stacks`/`#stack`: if `current_api_client.stack_id?` is true, only that one stack is in scope [1](#0-0) .

`CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, never consulting `current_api_client.stack_id` [5](#0-4) . Authorization for the action is checked only via `require_permission :read, :stack`, which validates the generic `read:stack` permission string, not the stack identity [6](#0-5) , [7](#0-6) . Consequently, a token that is scoped to stack A (and holds only `read:stack`) can pass `stack_id` for stack B in the request and CCMenuController will happily load and render stack B's data, because the `stack` lookup for this one controller is unscoped.

### Impact Explanation
This is an unauthorized cross-stack disclosure: an attacker holding a legitimately-issued but narrowly-scoped `ApiClient` token (e.g., a CI/CCTray integration token meant for one stack) can enumerate `stack_id` params and read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`, lock status) for any stack in the Shipit instance, including stacks/repositories they have no legitimate access to. This matches the "High - unauthenticated (here: unauthorized) read of stack state" impact category, since it escalates a stack-restricted credential into a global-read credential without ever crossing into privileged-account or `github_access_token` territory (which would be out of scope).

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (this is a supported, tested feature — see `stacks.from_param!` scoping and the `here_come_the_walrus` fixture) and exposes the CCMenu endpoint. No privileged account, GitHub App key, webhook secret, or session is required — only possession of any valid `ApiClient` authentication token (Basic auth header or `token` query param, both natively supported by this controller) [8](#0-7) . The bug is a straightforward one-line divergence from the pattern used everywhere else (`api/stacks_controller.rb`, `api/base_controller.rb`), making it easy to trigger by simply supplying a different `stack_id`.

### Recommendation
Remove the custom `stack` override in `CCMenuController` and use the inherited, scoped `stacks.from_param!(params[:stack_id])` from `BaseController` so that stack-scoped `ApiClient` tokens cannot access stacks outside their `stack_id`. If the query-string token authentication path is required (for CCTray widgets that can't send Basic auth headers), it should still route through the scoped `stacks` helper rather than `Stack.from_param!` directly.

### Proof of Concept
1. Create/observe a stack-scoped `ApiClient` bound to stack `A` with permission `read:stack` only (as in fixture `here_come_the_walrus`, bound to stack `shipit`) [4](#0-3) .
2. Authenticate to `GET /api/stacks/:stack_id/ccmenu` (`Shipit::Api::CCMenuController#show`) using that token, e.g., via Basic auth or `?token=<authentication_token>` [8](#0-7) .
3. Instead of `stack_id = A`, pass `stack_id = B` (a stack the token was never granted, e.g. `soc` or `cyclimse` from the fixtures).
4. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` unconditionally, bypassing the `current_api_client.stack_id` restriction enforced everywhere else [5](#0-4)  vs. [1](#0-0) .
5. `show` renders stack B's `lastBuildStatus`/`lastBuildLabel`/lock state to the caller, even though the token is scoped only to stack A [9](#0-8) .
