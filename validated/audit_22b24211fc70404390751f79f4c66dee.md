### Title
Webhook status/push forgery across GitHub organizations due to unbound `repository.owner.login` vs. `repository.full_name`/`sha` matching - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using an org name read out of the JSON body itself, but the handlers that actually act on the payload use a different field (or no repository scoping at all) to decide what to mutate. This lets an attacker who legitimately controls one tracked GitHub organization's webhook secret forge events that are authenticated as "their" org but that write to a different org's stacks/commits.

### Finding Description
`WebhooksController#verify_signature` derives the GitHub App config (and therefore the webhook secret used for HMAC verification) from the payload body: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — i.e. from attacker-supplied JSON, not from any GitHub-authenticated header. The signature is then verified with `Shipit.github(organization: repository_owner).verify_webhook_signature`, using per-organization `webhook_secret` values configured in `secrets.yml` (Shipit explicitly supports multiple independent GitHub Apps/orgs, see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`).

Once verification passes, the actual handlers determine *what* to write using a **different** field, or none at all:

- `Handler#repository_name` (base class used by push/check_suite handlers) reads `payload.dig('repository', 'full_name')` — a separate JSON field from the one used to pick the signing secret: [3](#0-2) 

- `StatusHandler#process` doesn't scope by repository at all — it matches purely on commit `sha` globally across the entire Shipit database: [4](#0-3) 

Nothing cross-checks that `repository.owner.login` (used to pick the trusted secret) is consistent with `repository.full_name` (used by `Handler#stacks`) or with the commit's actual owning repository (for `StatusHandler`). This breaks the binding: `organization authenticated by signature == organization whose repository/commits are written`.

An attacker who is a legitimate administrator of a GitHub App installation for **OrgA** (one of possibly many orgs configured in this single Shipit instance, per `Shipit.github(organization:)` multi-tenant support) knows OrgA's `webhook_secret`. They can craft and correctly HMAC-sign a payload where:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) → passes `verify_signature`, since it's genuinely signed with OrgA's secret.
- `repository.full_name = "OrgB/victim-repo"` and/or `sha = <a real commit sha tracked in OrgB's stack>` → drives the actual mutation performed by the handler, in an org the attacker does not control.

### Impact Explanation
This is most severe via `StatusHandler`, because it has zero repository scoping: `Commit.where(sha: params.sha)` matches any commit in the entire database regardless of which org/repo it belongs to [4](#0-3) . Shipit uses commit CI/status state (`commit_status` hook event, see `EVENTS` list in `app/models/shipit/hook.rb`) as part of its deployability gating for continuous deployment. An attacker signing with their own org's secret can forge a `status` event with `state: "success"` for a commit sha that happens to belong to a victim stack in a completely different, unrelated GitHub organization tracked by the same Shipit instance, marking that commit deployable and enabling an **unauthorized deploy** of unreviewed/failing code in a repository/org the attacker never had write access to.

`PushHandler`/`CheckSuiteHandler` are also affected via the `full_name` vs `owner.login` mismatch, though their blast radius is scoped by `Repository.from_github_repo_name(repository_name)` [5](#0-4) , still letting attacker-controlled org secrets trigger sync/check-run refresh actions against another org's stack.

### Likelihood Explanation
Requires the attacker to legitimately control the webhook secret of at least one GitHub organization/App that this Shipit instance is configured to trust (a realistic scenario for any Shipit deployment tracking multiple orgs, as explicitly supported and documented), plus knowledge that another org's repo/commit is also tracked by the same instance. No Shipit session, API token, or the victim org's credentials are needed — only the attacker's own org's webhook secret, which they legitimately hold.

### Recommendation
Do not let handlers act on payload fields (`repository.full_name`, `sha`, `organization.login`) that are outside the scope authenticated by `verify_signature`. Bind the verified organization to the write target: e.g. require that `repository.full_name`'s owner segment matches the `repository_owner` used to select the webhook secret, and have `StatusHandler` scope commit lookups through `Repository.from_github_repo_name(repository_name)`/`stacks` (as `PushHandler`/`CheckSuiteHandler` do) rather than a bare global `sha` match.

### Proof of Concept
1. Attacker is granted (or self-registers) a GitHub App installation for `OrgA`, which the target Shipit instance is configured to trust with `webhook_secret_A` (multi-org config as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<sha of a commit belonging to OrgB/victim-repo's tracked stack>",
  "state": "success",
  "context": "ci/tests",
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/attacker-repo"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `webhook_secret_A`, verification succeeds [1](#0-0) .
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` globally and marks the OrgB commit's status as `success` [4](#0-3) , potentially making an unreviewed OrgB commit deployable without any OrgB credentials.
