### Title
Signature verification keyed on `repository.owner.login` while `OpenedHandler` resolves the mutated repo from `repository.full_name` lets an attacker forge cross-org `pull_request` webhooks and create/mutate a `ReviewStack` on any repo Shipit tracks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to check against using `repository_owner` (`params.dig('repository','owner','login')`), but `PullRequest::OpenedHandler` (and the sibling PR handlers) resolve the repository/stack to mutate using an entirely independent field, `params.repository.full_name`. Because `GitHubApp#verify_webhook_signature` trivially returns `true` when the selected org has no `webhook_secret` configured, an attacker can name a no-secret org as `repository.owner.login` to pass verification while pointing `repository.full_name` at a different, secret-protected org's tracked repository, causing `OpenedHandler` to create/mutate that victim repo's `ReviewStack`.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`organization_used_to_verify_signature(params.repository.owner.login) == organization_that_owns(params.repository.full_name)`

Trace:
1. `WebhooksController#verify_signature` picks the app/secret purely from the claimed owner login: [1](#0-0) [2](#0-1) 

2. `Shipit::GitHubApp#verify_webhook_signature` **skips verification entirely** if that org has no configured secret: [3](#0-2) 

Multi-org config example shows `webhook_secret:` left blank per-org is a supported/expected configuration: [4](#0-3) 

3. Once `head(422)` isn't hit, `create` dispatches the raw JSON to `OpenedHandler.call(params)`. The handler **never re-derives or checks `repository_owner`** — it resolves the repository purely from `params.repository.full_name`: [5](#0-4) 

4. `ReviewStackAdapter#find_or_create!` then creates (or reuses) a `ReviewStack` scoped to that resolved repository, using attacker-controlled `pull_request.head.ref` as the branch and `params.number` as the environment key, with no cross-check against the org whose secret authenticated the request: [6](#0-5) [7](#0-6) 

Exploit flow: attacker configures/owns "OrgAttacker" (a Shipit-configured org with a blank `webhook_secret`, a common/documented configuration) and sends `POST /webhooks` with `X-Github-Event: pull_request`, body `action: "opened"`, `repository.owner.login: "OrgAttacker"`, `repository.full_name: "OrgVictim/victim-repo"` (a real repo tracked by Shipit whose org has a real, secret-protected webhook config), plus a fabricated `pull_request.head.ref`. `verify_signature` resolves `Shipit.github(organization: "OrgAttacker")`, finds no secret, and accepts *any* signature (or none). `OpenedHandler` then resolves `Shipit::Repository.from_github_repo_name("OrgVictim/victim-repo")` and provisions a `ReviewStack` for the victim repo — a payload that never touched OrgVictim's secret writes state under OrgVictim's repository.

Why existing guards fail: `drop_unhandled_event` only checks the event type exists in the registry, not repo/owner consistency. `verify_signature` never compares `repository_owner` to `repository.full_name`'s owner segment, and short-circuits to "verified" when the selected org has no secret. `ExplicitParameters` schemas (`requires :repository do requires :full_name, String end`) validate shape only, not provenance. No model validation ties an incoming webhook's authenticating org to the `full_name` used for `Repository.from_github_repo_name`.

On the "blocking_statuses" amplification the question raises: the same `full_name`-only resolution pattern is used by the `status` handler and other PR handlers (`labeled_handler.rb`, `reopened_handler.rb`, `closed_handler.rb`), so once a `ReviewStack` exists for the victim repo (via the `opened` cross-tenant write demonstrated above), subsequent forged `status` webhooks against the same no-secret owner trick can create/alter `Status` rows for the victim's commits, changing `Commit#blocked?`/`Stack` deploy-gating outcomes on a stack whose `blocking_statuses` are configured — but I did not trace the `status` handler's field-by-field logic in this session, so I cannot certify that exact downstream chain to the same standard as the `OpenedHandler` path above; the certain, directly-verified finding is the cross-tenant `ReviewStack` creation via `OpenedHandler`.

### Impact Explanation
An unauthenticated, unprivileged internet attacker can cause Shipit to create/mutate a `ReviewStack`, `PullRequest`, and enqueue provisioning jobs for a repository they do not control and whose webhook secret they never possessed, as long as any other org configured in the same Shipit instance lacks a `webhook_secret` (a supported/documented configuration shown in this repo's own example secrets files). This is a payload from one (attacker-named, unauthenticated) tenant mutating another tenant's stack/commit/task records — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. The attack is repeatable against any repository Shipit tracks and, combined with `blocking_statuses`-gated deploy logic, can be leveraged to influence deploy blocking state for the victim stack's `pr<number>` environment.

### Likelihood Explanation
Preconditions: (1) the Shipit instance is configured with more than one GitHub organization (or an org whose secret is left blank, which is the default in the provided example configs), (2) the target victim repository is already tracked by Shipit with review-stack auto-provisioning enabled (`review_stacks_enabled`, `provisioning_behavior_allow_all` or label-based). Attacker cost is a single unauthenticated HTTP POST with a hand-crafted JSON body — no GitHub credentials, no Shipit session, and no valid HMAC signature required when the selected org has no secret. This is fully repeatable and requires no timing dependency.

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret (`repository_owner`) matches the organization segment of `repository.full_name` (and of `organization.login` when present) before dispatching to any handler; reject the request otherwise. Additionally, treat an org with a blank/missing `webhook_secret` as a hard misconfiguration for any org used in production if signature enforcement is required for it, or require all configured orgs to define a secret when there's more than one org (multi-tenant mode), since the current code intentionally treats "no secret" as "always verified" per `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Under `test/controllers/shipit/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` if driving through the handler directly), using the fixture `test/dummy/config/secrets_double_github_app.yml` (OrgOne/OrgTwo, both with blank `webhook_secret` in the fixture — for a stronger PoC, stub OrgTwo's config with a real, non-blank `webhook_secret`):

1. Write the equality under test explicitly:
   `verified_org = "OrgOne"` (claimed `repository.owner.login`, no secret) vs.
   `mutated_repo_org = "OrgTwo"` (actual org of `repository.full_name` used by `OpenedHandler#repository`).
2. Configure a Shipit repository record for `"OrgTwo/victim-repo"` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
3. Forge a `pull_request` `opened` payload: `repository.owner.login = "OrgTwo"`? — actually to demonstrate the bypass, set `repository.owner.login = "OrgOne"` (no-secret org) and `repository.full_name = "OrgTwo/victim-repo"`.
4. `POST /webhooks` with header `X-Github-Event: pull_request`, an arbitrary/garbage `X-Hub-Signature`, and the JSON body above.
5. Assert `response.status == 200` (not 422) — proving verification passed despite an invalid signature and the mismatched owner.
6. Assert `Shipit::Repository.find_by(github_repo_name: "OrgTwo/victim-repo").review_stacks.count` increased by 1, and the new stack's `branch` equals the attacker-supplied `pull_request.head.ref` — proving OrgTwo's repository state was written by a request authenticated (or not-authenticated) under OrgOne.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
