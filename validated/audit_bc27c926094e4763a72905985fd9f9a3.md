### Title
Unvalidated attacker-controlled EC point buffer passed to native `secp256k1.ecdh` in `deriveSharedSecret` - (File: device.js)

### Summary
`decryptPackage()` accepts `objEncryptedPackage.dh.sender_ephemeral_pubkey` from any paired-device message with only a `typeof === 'string'` check, then feeds the raw base64-decoded bytes into the native secp256k1 binding's `ecdh()` function via `deriveSharedSecret()`, without validating the pubkey's length or curve-point validity beforehand.

### Finding Description
`decryptPackage` validates that `sender_ephemeral_pubkey` and `recipient_ephemeral_pubkey` are strings, but never checks that `sender_ephemeral_pubkey` decodes to a canonical 33-byte (compressed) or 65-byte (uncompressed) buffer, nor that it is a valid point on the secp256k1 curve, before calling `deriveSharedSecret(objEncryptedPackage.dh.sender_ephemeral_pubkey, priv_key)` [4](#0-3) [3](#0-2) . Inside `deriveSharedSecret`, the string is base64-decoded into an arbitrary-length `Buffer` and passed unchecked as the public-key argument to `ecdsa.ecdh(pubkey, privKey, ...)`, which is a native (non-JS) binding of libsecp256k1 [5](#0-4) . This is directly analogous to the CVE-2019-16227 pattern: attacker-controlled, insufficiently length/format-validated binary data is handed to a native memory-unsafe routine (`mdb_xcursor_init1`'s `memcpy` in lmdb vs. libsecp256k1's point-parsing/ECDH routine here), where malformed input can trigger out-of-bounds memory access rather than a clean JS-level error. Everywhere else in the codebase that touches secp256k1 pubkeys (e.g. `signature.js` `verify()`, `network.js` `hub/get_temp_pubkey`) first enforces `isStringOfLength(pubkey, constants.PUBKEY_LENGTH)` before any cryptographic call [6](#0-5) , but this exact discipline is missing for the `sender_ephemeral_pubkey` field consumed during package decryption.

### Impact Explanation
Any paired device (including a newly-approved pairing initiated with an attacker-controlled random string) can send a device message with a crafted `sender_ephemeral_pubkey` to force the recipient's `decryptPackage` to call the native ECDH routine with malformed input. Depending on the underlying native binding's parsing behavior for out-of-range/invalid points, this can cause a process crash (denial of service on the target wallet/hub/witness node) or, in the worst case matching the referenced CVE class, memory corruption in the native addon reachable purely from a received message, without requiring any prior authentication beyond an established device pairing.

### Likelihood Explanation
Device pairing is a normal, low-friction wallet feature, and any paired device — including one an attacker configures maliciously before pairing completes — can send arbitrary encrypted-package envelopes containing a crafted `dh.sender_ephemeral_pubkey` field, so the trigger conditions are easily attacker-controlled.

### Recommendation
Before calling `deriveSharedSecret`, validate that the decoded `sender_ephemeral_pubkey` buffer has the correct length (33 bytes compressed or 65 bytes uncompressed) and passes `ecdsa.publicKeyVerify()` from the secp256k1 library, rejecting the message otherwise — mirroring the `isStringOfLength(..., constants.PUBKEY_LENGTH)` checks already used elsewhere for pubkeys in `network.js` and `signature.js`.

### Proof of Concept
A paired device sends an `encrypted_package` object where `dh.sender_ephemeral_pubkey` is set to a base64 string decoding to a byte sequence that is not a valid encoded EC point (e.g., wrong length, or well-formed length but with an out-of-range X-coordinate/invalid prefix byte). Because `decryptPackage` only checks `typeof ... === 'string'` for this field [4](#0-3) , the malformed value flows unfiltered into `ecdsa.ecdh(pubkey, privKey, ...)` in `deriveSharedSecret` [5](#0-4) .

Note: I was unable to inspect the native secp256k1 addon's internal C source to confirm the exact memory-safety consequence of an invalid point (crash vs. exploitable corruption) since it is outside the scanned repository, and I could not find any additional pubkey-format validation performed earlier in the message-receipt pipeline (e.g., in `network.js`'s handling of encrypted device messages) — this should be verified with a Devin session that can trace the full inbound message path and test the native binding's behavior on malformed input.
