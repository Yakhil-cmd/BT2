### Title
Headers-commission split among multiple `earned_headers_commission_recipients` uses `Math.round` instead of round-down, allowing supply inflation via rounding surplus - ([File: headers_commission.js])

### Summary
### Finding Description
`calcHeadersCommissions()` distributes a unit's `headers_commission` (an integer amount of bytes fixed at unit-composition time) among the addresses listed in `earned_headers_commission_recipients`. Validation only guarantees that the recipient shares sum to exactly 100 (`validation.js` `validateHeadersCommissionRecipients`, checking `total_earned_headers_commission_share !== 100`), but it never constrains how the integer `full_amount` is split among recipients.

The split itself is computed with nearest-integer rounding, not round-down, both in the RAM path and in the SQL/DB-consistency path: [1](#0-0) [2](#0-1) 

and equivalently in the MySQL path: [3](#0-2) 

Each recipient's payout is `Math.round(full_amount * share / 100.0)` (or `ROUND(...)` in SQL, which uses standard/half-up rounding). Because `Math.round` rounds `.5` up, and because the shares are attacker-controlled (any unprivileged unit author can pick `earned_headers_commission_recipients` freely as long as the shares sum to 100 and addresses are sorted), an author can choose `full_amount` and per-recipient shares such that the fractional remainder for several/most recipients is exactly or just above `0.5`. In that case, every recipient's individually-rounded contribution rounds *up*, and the sum of all payouts to `headers_commission_contributions` (and subsequently `headers_commission_outputs`, which becomes spendable header-commission inputs — see `validation.js` input-balance check at lines 2611-2667 comparing `total_input` against `total_output + headers_commission + ...`) can exceed the single, fixed `headers_commission` amount that was actually deducted from the payer unit.

This is structurally the same rounding-composition flaw as the Origami report: the protocol's implicit invariant ("the sum of amounts paid out must never exceed the amount available/committed, i.e. round down") is violated because the actual arithmetic (`Math.round` per recipient, summed independently) can round the aggregate *up* instead of down, in the attacker's favor.

### Impact Explanation
Each header-commission-winning unit can mint at most a small rounding surplus (bounded by roughly `0.5 * number_of_recipients` bytes) that is not backed by any burned/relinquished output elsewhere in the DAG. While the per-unit surplus is small (limited by `MAX_AUTHORS_PER_UNIT = 16`, since `earned_headers_commission_recipients` size is effectively bounded by author count in the intended usage, i.e. up to a handful of bytes per winning unit), it is repeatable: an attacker who controls witness-adjacent nodes/authors can repeatedly win headers commissions across many main-chain indices, each time choosing recipient shares to maximize the rounding surplus. This is a genuine, if slow, unauthorized minting of currency — a supply-inflation bug — because the `headers_commission_outputs` table feeds directly into spendable `type='headers_commission'` inputs that are checked against `total_output` in the base-asset balance equation, with no cross-check that cumulative header-commission payouts equal cumulative header-commissions charged.

### Likelihood Explanation
Likelihood is Medium: exploitation requires no privileged access — any address can be listed as an `earned_headers_commission_recipients`, and any single/multi-authored unit can pick adversarial shares — but the gain per exploit is very small (sub-byte to a few bytes per winning unit) and requires the unit to actually win the headers-commission lottery (`getWinnerInfo`), so at internet scale the abuse is throttled by how often an attacker's units win headers commissions and by the small number of recipients allowed.

### Recommendation
Change the per-recipient split to consistently round down (`Math.floor`) for all but a designated "last" recipient, and assign that recipient the residual (`full_amount - sum_of_floors`) so that the total always exactly equals `full_amount`. Apply the same fix in both the RAM/JS path (`headers_commission.js` lines ~183 and ~202) and the SQL path (mysql query using `ROUND(...)`, line 51), replacing `ROUND()` with `FLOOR()` plus a residual-assignment step, and add a runtime assertion/test verifying `SUM(amount) per (unit, payer_unit) === full_amount` exactly.

### Proof of Concept
1. Author a multi-authored unit (or a single-authored unit specifying `earned_headers_commission_recipients` for another address) with two recipients, shares `50` and `50`.
2. Ensure `full_amount` (the `headers_commission` charged on the parent/payer unit) is an odd number, e.g. `149`.
3. When the unit wins the headers-commission lottery (`getWinnerInfo`), `calcHeadersCommissions()` computes for each recipient `Math.round(149 * 50 / 100) = Math.round(74.5) = 75`.
4. Total distributed = `75 + 75 = 150`, which is `1` byte more than the `149` bytes actually available from the payer unit's `headers_commission`, resulting in `headers_commission_outputs` crediting recipients with 1 more byte in total than was ever deducted anywhere in the system — an unbacked, minted byte.
5. Repeating this pattern across many won units (and with more recipients per unit, up to `MAX_AUTHORS_PER_UNIT`) accumulates real, unauthorized supply inflation over time. [4](#0-3)

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
