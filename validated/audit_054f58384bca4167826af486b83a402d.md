### Title
Ambiguous unsegmented string concatenation causes contract-hash collisions in prosaic/arbiter contract integrity commitments - (File: arbiter_contract.js, prosaic_contract.js)

### Summary
`arbiter_contract.js` and `prosaic_contract.js` compute the integrity hash of a private contract by concatenating multiple attacker/peer-controlled dynamic-length strings (title, text, party names, etc.) with no delimiter, then hashing the result. This is the JS analogue of Solidity's `abi.encodePacked()` multi-dynamic-argument collision: shifting characters across the boundary between two adjacent dynamic fields produces an identical concatenated byte string and therefore an identical hash for semantically different contract terms.

### Finding Description
`arbiter_contract.js` builds the hash source with `getHashSrc()`: [1](#0-0) 

The delimiter-protected branch (`.join(exports.DELIMITER)`) is only used when `contract.creation_date > exports.NEW_HASH_DATE`, and `exports.NEW_HASH_DATE` is set to `'2026-11-01'`: [2](#0-1) 

Since the current date is before `2026-11-01`, every contract created today falls into the vulnerable `.join("")` branch, which naively concatenates `title`, `text`, `creation_date`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, `asset` with no separator at all. Because `title` and `text` are both attacker-supplied free-form strings of arbitrary length, an attacker can move characters across the title/text boundary (e.g. `title="A", text="BC"` vs `title="AB", text="C"`) and produce byte-identical concatenations, and thus identical SHA-256 hashes, for two different contracts.

`prosaic_contract.js` has the same unconditional flaw, with no delimiter at all in either hashing function: [3](#0-2) 

This directly contrasts with the codebase's own canonical, collision-safe serializer `getSourceString()` in `string_utils.js`, which explicitly type-tags and delimits every field with `STRING_JOIN_CHAR` and rejects embedded delimiter bytes: [4](#0-3) 

`arbiter_contract.js` and other protocol-critical hashing code (unit hash, definition hash, ball hash in `object_hash.js`) correctly rely on `getSourceString`/`getJsonSourceString`, but the peer-to-peer contract modules bypassed that safe primitive and rolled their own naive concatenation.

### Impact Explanation
The resulting `contract.hash` is not just a display value — it is embedded on-chain as the integrity commitment for the private agreement and is used to gate fund release from the multisig escrow (shared) address: [5](#0-4) 

and to validate the on-chain signing unit against the expected contract: [6](#0-5) 

Because two different `(title, text, …)` tuples can produce the same `contract.hash`, a malicious counterparty can present one contract text to the honest peer for signing/escrow-address derivation while holding a different, colliding contract text to submit later (e.g., in `openDispute`'s `encrypted_contract` payload sent to the arbstore, or in the shared/private-asset release condition `CONTRACT_DONE_<hash>`/`CONTRACT_<hash>` data-feed keys). Both texts hash identically, so the on-chain/off-chain hash check cannot detect the substitution, which can lead to wrongful dispute outcomes or wrongful release/withholding of escrowed funds — i.e., an AA/escrow fund-loss or fund-freezing outcome tied to a private-payment/private-contract flow reachable by any counterparty in a `prosaic_contract`/`arbiter_contract` exchange (paired device flow), not a privileged actor.

### Likelihood Explanation
High likelihood: both peers in a prosaic or arbiter contract are mutually untrusted counterparties by design, `title`/`text` are always fully attacker-controlled free-text fields, and the vulnerable unsegmented concatenation path is the currently active code path for `arbiter_contract.js` (because `NEW_HASH_DATE` is a not-yet-reached future date) and is the only path for `prosaic_contract.js`. No special privileges, network position, or node compromise are required — only participation as the counterparty in a private contract negotiation over an existing paired-device channel.

### Recommendation
Use the existing collision-safe serializer instead of manual concatenation:
- In `arbiter_contract.js`'s `getHashSrc`, always compute the hash source via `string_utils.getSourceString` (or unconditionally use the already-implemented `exports.DELIMITER` join, and move `NEW_HASH_DATE` into the past/remove the legacy branch) so collisions cannot be engineered by shifting bytes across field boundaries.
- In `prosaic_contract.js`'s `getHash`/`getHashV1`, hash `{title, text, creation_date}` via `objectHash.getBase64Hash({title, text, creation_date})` (which uses `getSourceString`) instead of raw string concatenation.
- Ensure any similarly constructed hash inputs in these two files (e.g., `getContactsHash`) also use a proper structured/delimited encoding rather than ad hoc `join("|")`/concatenation of attacker-controlled fields.

### Proof of Concept
1. Peer A proposes an arbiter contract with `title="Deliver 1"`, `text="00 widgets"`, fixed `creation_date`, `payer_address`, `arbiter_address`, `payee_address`, `amount`, `asset`.
2. Peer A also privately prepares a colliding alternate contract with `title="Deliver 10"`, `text="0 widgets"` — note `"Deliver 1" + "00 widgets" === "Deliver 10" + "0 widgets"`.
3. Both tuples, when passed through `getHashSrc()`/`getHash()` in `arbiter_contract.js` (lines 194-207, using the currently-active `.join("")` branch since `Date.now() < NEW_HASH_DATE`), produce identical SHA-256 base64 hashes.
4. Peer A sends the first version to Peer B for signing/escrow setup (hash `H` embedded in the on-chain `data` message and in the `CONTRACT_`/`CONTRACT_DONE_` data-feed condition keys used by `deriveSharedAddress`), while later asserting the second version (also hashing to `H`) during dispute resolution via `openDispute`'s `encrypted_contract` payload, without either side being able to detect the substitution from the hash alone.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
