### Title
Global unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook signed by one org's GitHub App forge CI status for another org's commit, defeating `MergeRequest#all_status_checks_passed?` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies an incoming `status` webhook to **every** `Commit` row in the database that shares the same `sha`, with no check that the commit's `stack`/`repository` belongs to the same GitHub organization that signed the webhook [1](#0-0) . Because `sha` is only unique per `(stack_id, sha)` and not globally [2](#0-1) , a commit shared across repositories (e.g. via a fork tracked as a separate Shipit stack under a different, unrelated org) lets that unrelated org's genuinely-signed webhook write a `Status`/`CheckRun` onto the victim stack's commit, which `MergeRequest#all_status_checks_passed?` then reads as if it came from the victim's own CI.

### Finding Description
The binding that must hold is: **the org that signed the status webhook creating `head.statuses_and_check_runs` == the org owning `stack.repository` for this `MergeRequest`**.

- `WebhooksController#verify_signature` correctly authenticates that the payload was signed by *some* configured GitHub org (`Shipit.github(organization: repository_owner)` / `GitHubApp#verify_webhook_signature`) [3](#0-2) . In a multi-tenant Shipit deployment, each org has its own `github_app_config` and its own `webhook_secret` [4](#0-3) , so an org can only sign requests as itself — but this only proves *identity of the sender org*, it does not bind the payload to the *target repository/stack*.
- Once signature verification passes, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
This query is **global** across all stacks/repositories — it does not filter by `repository_owner`, `repository.full_name`, or any org/stack scoping tied to the verified signer.
- `Commit` rows are only unique per `(stack_id, sha)` [2](#0-1) , so the same git SHA can legitimately exist as separate `Commit` rows under multiple stacks (e.g. a victim's stack tracking `owner/repo` and an attacker's stack tracking their fork `attacker-org/repo`, which shares git history/SHAs with the upstream up to the point of divergence).
- `MergeRequest#all_status_checks_passed?`, `#any_status_checks_failed?`, and `#any_status_checks_missing?` all build a `StatusChecker` from `head.statuses_and_check_runs` [5](#0-4) , and `Commit#statuses_and_check_runs` is simply `statuses + check_runs` on that specific `Commit` row [6](#0-5) . There is no re-derivation from GitHub at merge time — `merge!` calls `reject_unless_mergeable!` → `any_status_checks_missing?`/`any_status_checks_failed?`, and if those return false the pending MergeRequest proceeds to `merge!` and calls the GitHub merge API [7](#0-6) .

**Exploit flow:** Attacker owns/administers `attacker-org`, which is already configured as a legitimate (but unrelated) tenant org in this multi-tenant Shipit instance (attacker knows their own org's `webhook_secret` since they control that org's GitHub App/webhook config). Attacker forks the victim's public repository into `attacker-org` and adds it as a Shipit stack (or otherwise causes Shipit to sync commits from the fork, e.g. via `GithubSyncJob`), so a `Commit` row with the victim's exact head SHA now also exists under `attacker-org`'s stack. Attacker then triggers (or forges) a `status` event for that SHA claiming `state: "success"` — this can even be a **real** GitHub webhook fired from the attacker's own fork/CI, correctly signed by `attacker-org`'s real secret, requiring no secret theft at all. `StatusHandler#process` matches `Commit.where(sha: ...)` and writes the success status onto **both** the attacker's own commit row and the victim's commit row for the shared SHA, since both rows have that SHA. The victim's `MergeRequest#all_status_checks_passed?` now reads this forged success status and the queued merge request proceeds to `merge!`, merging a PR that never had passing/complete CI, on a stack the attacker's org has no permission over.

Existing guards do not stop this: `verify_signature` only proves "this org signed this", `drop_unhandled_event` only filters unregistered event types, and there is no `Repository`/stack-ownership check inside `StatusHandler#process` or downstream in `Commit#create_status_from_github!`.

### Impact Explanation
An unprivileged party who controls an unrelated, separately-onboarded org on the same multi-tenant Shipit instance can inject fabricated CI status onto another tenant's commit and thereby cause an **unauthorized merge** of a pull request whose CI is actually missing or failing, on `stack.repository` belonging to a different, unrelated org (a payload for one repository mutating another's stack/merge). This matches the Critical impact category ("a payload for one repository mutating another's stack... or an unauthorized deploy, rollback or merge"). The blast radius spans all stacks in the shared Shipit installation that happen to track a commit with a colliding SHA (most straightforwardly achieved by forking the target repository), which is repeatable against any repository the attacker can fork and any commit SHA they can get Shipit to also track under their own tenant stack.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment where multiple distinct orgs are configured (`github_default_organization` present, per-org `webhook_secret`); (2) the target stack has `merge_queue_enabled`; (3) attacker is able to onboard/administer a Shipit stack for a fork of the victim's repository (or otherwise get a `Commit` row created for the shared SHA under a different org's stack) — this is exactly the kind of setup a self-service multi-tenant CI/CD platform like Shipit is designed to allow. No Shipit secrets, sessions, or GitHub App private keys are needed if the attacker relies on their own org's genuine webhook delivery. This is a low-cost, repeatable attack once the attacker has any second tenant org on the shared instance.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/check-suite handlers) to only update `Commit` rows whose `stack.repository` matches the `repository_owner`/`repository.full_name` verified by `verify_signature`, e.g. filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repo_name })` instead of a bare `sha` match, so a webhook can only ever mutate commits belonging to the same repository/org that signed it.

require 'test_helper'

module Shipit
  class MergeRequestStatusBindingTest < ActiveSupport::TestCase
    setup do
      @victim_stack = shipit_stacks(:shipit) # merge_queue_enabled, owned by "shopify"
      @attacker_stack = Stack.create!(
        repository: Repository.create!(owner: 'attacker-org', name: 'shopify-fork'),
        environment: 'production',
        branch: 'master'
      )
      @sha = 'a' * 40
      @victim_commit = @victim_stack.commits.create!(sha: @sha, message: 'shared history commit')
      @attacker_commit = @attacker_stack.commits.create!(sha: @sha, message: 'shared history commit')
      @merge_request = @victim_stack.merge_requests.create!(number: 42, head: @victim_commit)
    end

    test "status webhook signed by unrelated attacker org must not satisfy victim merge request's CI checks" do
      # Simulate a status webhook that is validly signed for 'attacker-org' (verify_signature passes for attacker's own org)
      Shipit::Webhooks::Handlers::StatusHandler.new.process(
        Params.new(sha: @sha, state: 'success', context: 'ci/attacker')
      )

      # BROKEN BINDING: attacker-signed status ends up on the victim's commit too
      assert @victim_commit.reload.statuses.exists?(state: 'success'),
        "attacker org's webhook wrote a status onto the victim's commit"

      # This forged status is enough to make reject_unless_mergeable! NOT reject for ci_missing/ci_failing
      refute @merge_request.reject_unless_mergeable!,
        "merge request should be rejected as ci_missing/ci_failing, but attacker-forged status made it appear mergeable"
    end
  end
end
```
Both sides of the equality diverge before/after: before the webhook, `head.statuses_and_check_runs` for the victim commit is empty (org binding holds vacuously — no cross-org data exists); after the attacker-signed webhook for `attacker-org`, `head.statuses_and_check_runs` includes a status whose signer (`attacker-org`) is not the org owning `stack.repository` (`shopify`/victim org), yet `reject_unless_mergeable!` returns `false` — proving the binding is broken and `merge!` can proceed.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end
