### Title
Unbounded per-address conflicting-unit scan during MC stabilization can stall stability advancement - (File: main_chain.js)

### Summary
`markMcIndexStable()`'s `handleNonserialUnits()` retrieves *every* unit at the newly-stabilizing MCI whose `sequence != 'good'` and, for each one, calls `findStableConflictingUnits()`, which itself issues a DB query and then iterates all matching competitor rows with `async.eachSeries` + `graph.compareUnitsByProps()`. Nothing bounds how many non-good (temp-bad/nonserial) units a single address, or a set of addresses, can accumulate at one MCI before this scan runs, mirroring the reported pattern of `_checkSolePlayer()`: settlement/finalization logic performs an O(n) or worse scan over attacker-inflatable state, gating the very state transition (stabilization) that must succeed for the DAG to progress.

### Finding Description
Any unprivileged unit poster can create many conflicting (double-spending) units from the same address(es), each individually valid to broadcast and cheap to construct (bounded only by unit fees). These units land in `unit_authors`/`units` with `sequence` set to `temp-bad` via `checkSerialAddressUse()` in `validation.js` [1](#0-0) . There is no cap in `checkSerialAddressUse`/`findConflictingUnits` on how many simultaneous conflicting (temp-bad) units an address may have pending [2](#0-1) .

When the main chain advances and that MCI stabilizes, every node must execute `markMcIndexStable()` → `handleNonserialUnits()`, which selects **all** units at that MCI with `sequence != 'good'` and then, for **each** of them, calls `findStableConflictingUnits()`: [3](#0-2) 

`findStableConflictingUnits()` runs a JOIN query for competitor units and then does `async.eachSeries` over the result rows, calling `graph.compareUnitsByProps()` (a further per-row comparison, sometimes requiring extra property reads) for each: [4](#0-3) 

This is directly analogous to `_checkSolePlayer()`: a per-settlement scan whose cost is proportional to the number of conflicting/attacker-controlled records (here, temp-bad units at a given MCI), with no participant/record cap, executed unconditionally as part of the mandatory stabilization pipeline that every full node must complete to advance `main_chain_index` and admit new units.

### Impact Explanation
Unlike the Solidity example, ocore has no fixed "gas" limit that reverts the transaction — instead, the cost manifests as increasingly expensive, serialized DB queries and comparisons executed synchronously (via `async.eachSeries`) inside the mandatory MCI-stabilization step that runs on **every node** before it can accept units built on top of that stability point. If an attacker floods many conflicting units from one or more addresses concentrated at a single MCI, `handleNonserialUnits()`'s row set and the nested `findStableConflictingUnits()` scans grow with attacker-controlled input, materially slowing or effectively stalling stabilization for that MCI across the network, which delays confirmation of all subsequent units built on it (an MC-progression bottleneck analogous to the reported `WaitingVRF` stuck state).

### Likelihood Explanation
Reachable by any unprivileged unit poster: the only requirement is the ability to post standard signed units, each individually valid to broadcast, that double-spend from the same address(es) so they accumulate `sequence='temp-bad'`/`nonserial` status. Cost is bounded by per-unit posting fees, not by protocol-side rate limiting of conflicting-unit accumulation per MCI, so the classification is on par with the referenced Medium-severity finding (requires volume of spam, but no privileged role or node compromise needed).

### Recommendation
1. Cap the number of concurrently pending (unstable, non-good-sequence) conflicting units allowed per address, rejecting/deprioritizing further double-spend attempts from the same address beyond a bound (similar to how `checkNoPendingDefinition` limits pending definition changes).
2. Bound or batch `findStableConflictingUnits()`'s work per MCI (e.g., cap `arrConflictingUnits`/rows processed, or parallelize/optimize the JOIN+per-row `compareUnitsByProps` scan) so its cost cannot grow unbounded with attacker-supplied double-spend volume.
3. Add fee/incentive-based throttling specifically for repeated double-spend attempts from a single address within a short MCI window.

### Proof of Concept
Conceptual (no live network access from this analysis):
1. From address `A`, construct and broadcast N distinct, individually-valid units that each spend the same output(s) (double-spends), so all but one land with `sequence='temp-bad'` per `checkSerialAddressUse()`.
2. Wait for the MCI containing these N temp-bad units to become the next unstable MC index eligible for stabilization.
3. When `markMcIndexStable()` runs for that MCI, `handleNonserialUnits()`'s query returns all N non-good units; `async.eachSeries` then calls `findStableConflictingUnits()` (and its nested `compareUnitsByProps`) once per unit, making the stabilization step's cost scale with N.
4. Increasing N (bounded only by fees paid) increases the wall-clock time to complete stabilization of that MCI on every node processing it, delaying confirmation of subsequent units — the DAG-progression analog of the reported stuck `WaitingVRF` state.

Note: this analysis is based on static code review of `main_chain.js` and `validation.js`; I was unable to execute/observe actual runtime timings or confirm the absence of any additional throttling elsewhere in the codebase not surfaced by search, so the exact magnitude of impact (how many conflicting units are needed to cause a meaningfully "stuck" state) is unverified and would need empirical benchmarking on a live/test network.

	function findStableConflictingUnits(objUnitProps, handleConflictingUnits){
		// find potential competitors.
		// units come here sorted by original unit, so the smallest original on the same MCI comes first and will become good, all others will become final-bad
		/*
		Same query optimized for frequent addresses:
		SELECT competitor_units.*
		FROM unit_authors AS this_unit_authors 
		CROSS JOIN units AS this_unit USING(unit)
		CROSS JOIN units AS competitor_units 
			ON competitor_units.is_stable=1 
			AND +competitor_units.sequence='good' 
			AND (competitor_units.main_chain_index > this_unit.latest_included_mc_index)
			AND (competitor_units.main_chain_index <= this_unit.main_chain_index)
		CROSS JOIN unit_authors AS competitor_unit_authors 
			ON this_unit_authors.address=competitor_unit_authors.address 
			AND competitor_units.unit = competitor_unit_authors.unit 
		WHERE this_unit_authors.unit=?
		*/
		conn.query(
			"SELECT competitor_units.* \n\
			FROM unit_authors AS this_unit_authors \n\
			JOIN unit_authors AS competitor_unit_authors USING(address) \n\
			JOIN units AS competitor_units ON competitor_unit_authors.unit=competitor_units.unit \n\
			JOIN units AS this_unit ON this_unit_authors.unit=this_unit.unit \n\
			WHERE this_unit_authors.unit=? AND competitor_units.is_stable=1 AND +competitor_units.sequence='good' \n\
				-- if it were main_chain_index <= this_unit_limci, the competitor would've been included \n\
				AND (competitor_units.main_chain_index > this_unit.latest_included_mc_index) \n\
				AND (competitor_units.main_chain_index <= this_unit.main_chain_index)",
			// if on the same mci, the smallest unit wins becuse it got selected earlier and was assigned sequence=good
			[objUnitProps.unit],
			function(rows){

					}
