### Title
Non-native fungible assets sent to a `pallet-child-bounties` child-bounty account are permanently unrecoverable - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
`pallet-bounties` was already patched (PR [11045](https://github.com/paritytech/polkadot-sdk/issues/10996)) to add a permissionless `reclaim_bounty_funds` extrinsic that sweeps *both* the native currency and any fungible assets configured via `T::TransferAllAssets` out of a closed bounty's derived account back to the treasury [1](#0-0) . However, this fix was applied only to the top-level bounty account (`bounty_account_id`). The tightly-coupled `pallet-child-bounties` pallet, which derives its *own* separate account per child bounty (`child_bounty_account_id`), was never given an equivalent sweep mechanism and only ever moves the native `Currency` balance, never any other asset kind [2](#0-1) .

### Finding Description
`pallet-child-bounties` only imports `frame_support::traits::Currency` (and related native-balance traits); it never imports `fungibles::*` or any `TransferAllAssets`-style trait, unlike the sibling `pallet-bounties`, which explicitly added `fungibles::{Create, Inspect, Mutate}` support for its reclaim path [3](#0-2)  versus [4](#0-3) .

When a child bounty is closed, `impl_close_child_bounty` moves out only the native free balance from the child bounty's derived account to the parent bounty's account, then deletes the `ChildBounty` storage entry: [5](#0-4) 

After that point, the `child_bounty_account_id(parent_bounty_id, child_bounty_id)` address is never referenced again by any extrinsic in either `pallet-child-bounties` or `pallet-bounties`. Crucially, the new `reclaim_bounty_funds` extrinsic added to `pallet-bounties` only operates on `Self::bounty_account_id(bounty_id)` (the parent bounty's own account), not on any child bounty account: [6](#0-5) 

Because `child_bounty_account_id` is a deterministic `PalletId`-derived address, any signed account can compute it off-chain and transfer arbitrary `pallet-assets`/`fungibles` tokens into it (e.g., via `pallet_assets::Pallet::transfer` or `transfer_keep_alive`), whether intentionally or as a normal payment mistakenly directed to what looks like a treasury-controlled sub-account. Once the child bounty is closed or claimed and its storage record removed, there is no dispatchable capable of moving any asset other than the native currency out of that account — the funds are permanently and irrecoverably locked, exactly mirroring the reported ERC-20-in-Treasury bug class (a "pot" account can receive a class of token that its owning pallet has no code path to withdraw).

### Impact Explanation
This is a direct FRAME analog of the reported issue: value that reaches an on-chain "pot" address becomes permanently stuck because the owning pallet only implements a withdrawal/sweep path for one asset type (native currency) and not others (arbitrary fungibles). This causes an irreversible freezing of funds for whichever party's assets land in the child bounty account, matching the report's classification. The severity is Low/Undefined Behavior, as it requires funds to arrive at a specific derived address that is not the primary intended path for those assets, and the loss is confined to whatever was sent there — it is not a broader mint/theft/authority-bypass bug.

### Likelihood Explanation
Likelihood is Low-Medium: exploitation requires no privileged role — any signed account holding pallet-assets tokens can compute the `child_bounty_account_id` and transfer tokens to it (a permitted, non-privileged extrinsic call), and the address remains "live" (never reaped by pallet-child-bounties) through the bounty's entire lifecycle and afterward. The main constraint is that this requires someone to actually send non-native fungible assets to that specific derived address, which is not the pallet's designed/primary flow, similar to how the original report's scenario depended on the protocol's fee-collection mechanism directing ERC-20 tokens into the Treasury.

### Recommendation
- Short term: Extend `pallet-child-bounties` with an equivalent permissionless sweep (mirroring `pallet-bounties::reclaim_bounty_funds`) that, for a child bounty no longer present in storage, transfers any residual native and configured fungible-asset balances from `child_bounty_account_id` back to the parent bounty account or treasury.
- Long term: Audit all other pallets that derive `PalletId`-based sub-accounts (e.g., staking pools, other bounty-like pallets) for the same gap between "native currency only" cleanup logic and the possibility of holding arbitrary fungible assets, and generalize the `TransferAllAssets` pattern introduced for `pallet-bounties` to these accounts as a shared utility.

### Proof of Concept
No runnable PoC was executed in this session (ask-only/analysis mode; no test harness was run). The finding is based on static code inspection:
- Confirmed `pallet-bounties::reclaim_bounty_funds` targets only `bounty_account_id`, not child bounty accounts [6](#0-5) .
- Confirmed `pallet-child-bounties` never imports or uses any `fungibles`/`TransferAllAssets` trait, only `frame_support::traits::Currency` [2](#0-1) .
- Confirmed `impl_close_child_bounty` only moves the native balance and then permanently removes the storage entry, with no further code path touching that account [5](#0-4) .

I was not able to fully inspect the bodies of `award_child_bounty` and `claim_child_bounty` in this session (tool call errors on the final iteration prevented reading those line ranges), so it is not 100% confirmed that no other code path in those functions references non-native assets — however, given the pallet's trait imports are limited to `Currency`/`ReservableCurrency` throughout the whole file, it is highly unlikely any such path exists. A background agent with full file access should verify `award_child_bounty`/`claim_child_bounty` bodies and write an integration test that (1) transfers a `pallet-assets` token to a computed `child_bounty_account_id`, (2) closes/claims the child bounty, and (3) asserts the asset balance remains stranded with no available extrinsic to recover it, to fully confirm and document the gap before submitting to the Parity bug bounty program.

		/// Reclaim funds stranded in a closed bounty's account back to the treasury.
		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
