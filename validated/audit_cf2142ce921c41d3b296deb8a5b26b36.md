## Analysis Summary

The zkSync report's core flaw is that a precompile's *identity/context-dependent* output differs between `call` and `delegatecall`, producing an incorrect result that could mislead a consumer contract. The polkadot-sdk analog to `pallet-revive` (the EVM-compatibility layer) is directly relevant here, since it explicitly ports Ethereum precompiles and has *already* had this exact bug class identified and patched for several precompiles via a `PrecompileDelegateDenied` guard checked with `env.is_delegate_call()` — see `substrate/frame/assets/precompiles/src/lib.rs` [1](#0-0) , `polkadot/xcm/pallet-xcm/precompiles/src/lib.rs` [2](#0-1) , and `substrate/frame/vesting/precompiles/src/lib.rs` [3](#0-2) , as documented in `prdoc/stable2606/pr_11715.prdoc` [4](#0-3) .

However, the built-in `System` precompile (fixed address `0x900`) exposes `ownCodeHash()`, which resolves identity via `env.caller()` but has **no** delegate-call guard, unlike its sibling precompiles.

### Title
`ownCodeHash()` in the pallet-revive System precompile returns the wrong account's code hash under `DELEGATECALL` - (File: `substrate/frame/revive/src/precompiles/builtin/system.rs`)

### Summary
The `System` precompile's `ownCodeHash()` function resolves "own" identity via `env.caller()`. Under a normal `CALL`, `caller()` correctly resolves to the calling contract's own account. Under `DELEGATECALL`, `caller()` instead resolves to the *delegating contract's own caller* (the original external caller), because the delegate-call frame stores `DelegateInfo { caller, callee }` and `caller()` returns that stored value rather than the delegating contract's identity. This mirrors exactly the class of bug in the referenced report: a precompile function whose output must be call-type-independent instead silently changes meaning under `delegatecall`.

For a `DELEGATECALL` into the precompile, the delegate-call machinery pushes a frame carrying `delegated_call: Some(DelegateInfo { caller: self.caller().clone(), callee: address })` where `caller` is the *pre-delegate-call* caller (the account that called the delegating contract), as constructed here: [7](#0-6) 

Because `top_frame().delegate` is now `Some`, `caller()` returns that stored `caller` field — the *original external caller* of the delegating contract, not the delegating contract itself. Consequently `ownCodeHash()` returns the code hash of an unrelated account (frequently a signed EOA with no code, i.e., the "empty" code hash) instead of the delegating contract's own code hash.

This is the precise pattern flagged in the reference finding: a precompile primitive whose semantics ("who am I") must be invariant across `call`/`staticcall`/`delegatecall` diverges specifically under `delegatecall`, because the implementation derives identity from a caller-tracking field that has different meaning depending on call type. Unlike the ERC20/XCM/vesting/asset-conversion precompiles, which were hardened against this exact confusion by rejecting delegate calls outright (`PrecompileDelegateDenied`), `System::ownCodeHash` has no such guard.

Reachability: any deployed contract on a pallet-revive-enabled chain (e.g. Asset Hub Westend, which bundles `pallet-revive`) can be instantiated by an unprivileged signer and issue a `DELEGATECALL` to the fixed precompile address `0x900` with the `ownCodeHash()` selector — no privileged role, governance, or off-chain trust assumption is required.

### Impact Explanation
`ownCodeHash()` is a read-only, non-mutating, non-value-transferring query, so this does not directly enable theft or unbacked issuance. Its impact is limited to **integrity of self-identity information**: any contract or library pattern that relies on `System.ownCodeHash()` to assert "I am running as code hash X" (e.g., an EIP-7702-style self-verification/whitelist check, or a delegate-callable library that gates behavior on the caller matching a known code hash) can be fed an incorrect, attacker-influenced result once invoked via `delegatecall` from an intermediary. This is analogous to the "Context" classification and Medium severity rationale used by the judge in the referenced report — a genuine EVM-compatibility violation of the precompile's documented semantics, without direct fund movement.

### Likelihood Explanation
Low-to-moderate. `ownCodeHash` must actually be consumed by a contract that both (a) allows itself to be delegate-called (or wraps this precompile in a delegate-callable library) and (b) makes a security- or logic-relevant decision based on the returned hash. This is a plausible but non-default usage pattern; precompiles are typically invoked with `call`/`staticcall` as noted in the original report, making the direct exploitation window narrow but real given `DELEGATECALL` to precompiles is otherwise a supported, first-class code path in pallet-revive (as evidenced by the framework's `Precompile` trait explicitly documenting delegate-call semantics in `prdoc/stable2506/pr_8262.prdoc` [8](#0-7) ).

### Recommendation
Add the same guard already used elsewhere in the codebase: reject delegate calls to `ownCodeHash` (and audit other `System` precompile branches that read `env.caller()` for the same issue), e.g.:
```rust
ISystemCalls::ownCodeHash(ISystem::ownCodeHashCall {}) => {
    frame_support::ensure!(
        !env.is_delegate_call(),
        pallet_revive::Error::<T>::PrecompileDelegateDenied,
    );
    ...
}
```
This matches the mitigation already applied to the ERC20 assets, XCM, asset-conversion, and vesting precompiles.

### Proof of Concept
Not executed against a live network. Reasoning is based on static code tracing through `substrate/frame/revive/src/precompiles/builtin/system.rs:82-88` and `substrate/frame/revive/src/exec.rs:2053-2090` and `:2398-2417`, confirming that `caller()` resolves differently depending on whether `top_frame().delegate` is populated (delegate-call path) versus not (direct-call path). A concrete reproduction would use the existing `CallSetup`/`Caller` fixture pattern already present in the repo's test suite (e.g., the `encode_delegate_call` helper pattern used in `substrate/frame/asset-conversion/precompiles/src/tests.rs:626-633` [9](#0-8) ) to delegatecall address `0x900` with the `ownCodeHash()` selector from a deployed contract and assert the returned hash does not equal the calling contract's own code hash. This exact harness pattern (`ICaller::delegateCallCall`) already exists in-repo for other precompiles but has not been applied as a regression test for `System::ownCodeHash`, so I could not execute it within this investigation — this should be verified with an actual test run before filing.

	fn delegate_call(
		&mut self,
		call_resources: &CallResources<T>,
		address: H160,
		input_data: Vec<u8>,
	) -> Result<(), ExecError> {
		// We reset the return data now, so it is cleared out even if no new frame was executed.
		// This is for example the case for unknown code hashes or creating the frame fails.
		*self.last_frame_output_mut() = Default::default();

		let top_frame = self.top_frame_mut();
		// Clone the contract info and apply pending storage changes so that
		// the child frame can correctly calculate storage deposit refunds.
		// See: <https://github.com/paritytech/contract-issues/issues/213>
		let mut contract_info = top_frame.contract_info().clone();
		top_frame.frame_meter.apply_pending_storage_changes(&mut contract_info);
		let account_id = top_frame.account_id.clone();
		let value = top_frame.value_transferred;
		if let Some(executable) = self.push_frame(
			FrameArgs::Call {
				dest: account_id,
				cached_info: Some(contract_info),
				delegated_call: Some(DelegateInfo {
					caller: self.caller().clone(),
					callee: address,
				}),
			},
			value,
			call_resources,
			self.is_read_only(),
			&input_data,
		)? {
			self.run(executable, input_data)
		} else {
			// Delegate-calls to non-contract accounts are considered success.
			Ok(())
		}
	}
