### Title
`StatusHandler#process` matches commits by SHA across all repositories, letting a forged status escalate to an unauthorized continuous deployment - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)`, without constraining the query to the repository named in the webhook payload, unlike sibling handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `EditedHandler`) which all resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record. Because `Commit#deployable?` and `Stack#trigger_continuous_delivery`/`ContinuousDeliveryJob` only look at `success?`/`blocked?`/`locked?` on the `Commit`, a `success` status attached via a same-SHA collision from an unrelated, attacker-controlled repository is sufficient to trigger a real deploy on the victim stack.

### Finding Description
The binding that should hold is: `params.dig('repository', 'full_name') == commit.stack.repository.full_name` for every `Commit` mutated by a `status` webhook. It does not hold, because: [1](#0-0) 

`process` iterates `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no filter on `payload.dig('repository', 'full_name')` (the `repository_name`/`stacks` helper defined on the base `Handler` class is never invoked here). Contrast this with the base class helper that other handlers use to scope by repository: [2](#0-1) 

and with `OpenedHandler`, which resolves `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before creating anything: [3](#0-2) 

`create_status_from_github!` creates a `Status` row scoped to `commit.stack_id` (the commit's own stack, whatever repository owns it) and `add_status` schedules continuous delivery on state transitions: [4](#0-3) [5](#0-4) [6](#0-5) 

`ContinuousDeliveryJob#perform` then unconditionally calls `stack.trigger_continuous_delivery` when `stack.continuous_deployment?` is true and the stack isn't occupied: [7](#0-6) 

which ultimately consults `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`), with no repository check at all — this predicate has no knowledge of which repository authenticated the webhook that flipped `success?` to true.

**Root cause**: `Commit` rows are unique per `stack_id`, but `sha` is not globally unique across stacks/repositories. `StatusHandler#process` treats `sha` as if it were a global, trustworthy key, silently fanning a single authenticated webhook out to every `Commit` row in the database sharing that SHA, regardless of which repository the webhook actually came from.

**Exploit flow**: The attacker needs a repository within an organization that Shipit already trusts (i.e., has a GitHub App/webhook secret configured, per `Shipit.github(organization: repository_owner)` in `verify_signature`) — this is the same precondition as the referenced prior finding on cross-repository SHA collisions. The attacker constructs a git commit object in their own repository with identical parent SHA, tree SHA, author, committer, timestamps and message as an existing undeployed commit X in the victim's stack (feasible against public source history, since all inputs to the SHA1 commit hash are visible via the GitHub API). Pushing that object reproduces the exact same `sha`. The attacker's own CI reports `success` for that SHA in their own repo; GitHub sends a genuinely signed `status` webhook (signed with the attacker's own trusted-org secret) to Shipit. `verify_signature` passes because it only checks the signature against the org owning the *webhook sender*, never checking that this org matches the org of the `Commit`/`Stack` being mutated. `StatusHandler#process` then finds commit X purely by `sha` match and creates a `success` `Status` on it, flipping `Commit#deployable?` to true and triggering `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → a `Deploy` for commit X on the victim's production stack.

**Why existing guards fail**: `verify_signature` authenticates *that* the sender is a legitimate GitHub org/repo Shipit knows about, but never authenticates that the sender's repository matches the repository of the records being touched by the handler's `process` method — that binding must be enforced inside each handler, and `StatusHandler` is the one handler in the codebase that omits it. `ExplicitParameters` validates the shape of the payload but not authorization scope. `drop_unhandled_event` and `check_if_ping` are irrelevant here.

### Impact Explanation
An attacker who controls a repository in any org already onboarded to Shipit can cause an unauthorized `Deploy` to be created for a commit on any other stack/repository in the same Shipit instance whose stack has `continuous_deployment: true`, purely by reproducing a target commit's SHA in their own repo and self-reporting CI success. This is a payload for one repository mutating another repository's stack/commit/deploy state, and results in an unauthorized deploy being triggered on infrastructure the attacker never had permission on — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy" category. Blast radius spans every stack configured with continuous deployment across every repository hosted by the Shipit instance.

### Likelihood Explanation
Requires: (1) the attacker to control a repository within an org that already has a legitimate GitHub App/webhook installation trusted by Shipit (this is the precondition inherited from the prior cross-repo SHA-collision finding, not newly introduced here); (2) the victim stack to have `continuous_deployment: true`; (3) the attacker to be able to reconstruct byte-identical git commit object fields for a target commit whose full metadata (tree, parent, author/committer identities and timestamps, message) is discoverable, which is straightforward for public repositories. No Shipit secrets, sessions, or API tokens are needed. This is repeatable against any stack/commit pair satisfying these conditions.

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to the repository named in the webhook payload, mirroring the pattern used by the other handlers, e.g. filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { id: Repository.from_github_repo_name(payload.dig('repository', 'full_name'))&.id })`, or reuse the base `Handler#stacks` helper to constrain the commit lookup to `stacks.commits.where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create two `Stack`/`Repository` fixtures: `victim_stack` (repository `"victim/repo"`, `continuous_deployment: true`) and `attacker_stack` (repository `"attacker/repo"`).
2. Create `commit_x = victim_stack.commits.create!(sha: "deadbeef"*5, ...)` with no statuses (undeployed, CI-unknown).
3. Before: assert `commit_x.deployable?` is `false` and `Deploy.where(stack: victim_stack, sha: commit_x.sha).count == 0`.
4. POST to `/webhooks` a `status` event payload with `sha: commit_x.sha`, `state: "success"`, and `repository.full_name: "attacker/repo"` (stubbing `verify_signature`/`GithubApp#verify_webhook_signature` to return true, simulating a genuinely signed webhook from the attacker's own trusted org).
5. Assert `commit_x.reload.statuses.count == 1` and `commit_x.deployable?` is now `true`, even though `payload.dig('repository','full_name') != victim_stack.repository.full_name`.
6. Call `victim_stack.trigger_continuous_delivery` (or run the enqueued `ContinuousDeliveryJob`) and assert a `Deploy` record was created for `commit_x` on `victim_stack`, proving the equality `params.dig('repository','full_name') == commit.stack.repository.full_name` was violated and directly caused an unauthorized deploy.
