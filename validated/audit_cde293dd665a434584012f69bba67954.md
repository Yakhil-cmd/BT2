### Title
Cross-organization webhook forges membership into arbitrary `Shipit.github_teams` team via `github_id` collision - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a `membership` webhook using `repository_owner`, which for this event falls back to `params.dig('organization', 'login')` — a value fully controlled by whoever sends the request. `MembershipHandler#find_or_create_team!` then keys the `Team` lookup purely on the numeric `team.id` (`github_id`) from the payload body, with no cross-check that this `github_id` actually belongs to the organization that signed the request.

### Finding Description
The binding the code implicitly assumes is: `organization that signed request (via webhook_secret)` == `organization owning the Team row keyed by github_id`. This is never enforced.

Path:
1. `WebhooksController#verify_signature` at [1](#0-0)  calls `Shipit.github(organization: repository_owner)` and verifies the signature using that organization's `webhook_secret`.
2. `repository_owner` falls back to `params.dig('organization', 'login')` when there's no `repository.owner.login` in the payload [2](#0-1) , which is exactly the shape of a `membership` event payload (it has `organization`, not `repository`).
3. `GitHubApp#verify_webhook_signature` does a valid, correct HMAC check [3](#0-2)  — but it only proves the request was signed by *the organization named in the payload itself* (attacker's own org, since attacker controls `organization.login` and has that org's real `webhook_secret` configured for their own org in Shipit).
4. `MembershipHandler#find_or_create_team!` looks up/creates the `Team` solely by `params.team.id` (the numeric GitHub team id) [4](#0-3) , with no comparison against `params.organization.login`. If an attacker guesses/observes a `github_id` belonging to a team in a *different*, privileged organization (already present in `Shipit.github_teams`), `find_or_create_by!` returns that existing `Team` record.
5. `team.add_member(member)` is then called with `member` being `User.find_or_create_by_login!(params.member.login)` — the attacker's own GitHub login [5](#0-4) .
6. `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , so the attacker is now authorized instance-wide.

This requires the attacker to own/administer a GitHub organization that is *also configured in Shipit's `github` secrets section* (i.e., Shipit must be multi-tenant with the attacker's org registered as one of the configured GitHub orgs) — this is a real, common deployment pattern for Shipit (supporting multiple orgs from one instance, as reflected in `test/dummy/config/secrets_double_github_app.yml`). The critical gap is that no code anywhere cross-validates that the `Team`'s `organization` column matches the signing organization before mutating membership. `find_or_create_by!(github_id: ...)` silently reuses cross-tenant rows.

No existing guard prevents this: `verify_signature` only proves "signed by org X," it does not prove "team belongs to org X"; `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence, not cross-org ownership; there is no `find_or_create_by!(github_id:, organization:)` scoping check.

### Impact Explanation
An attacker who administers any GitHub org configured as a tenant in Shipit's secrets can add themselves (or any GitHub login) as a member of a `Team` row that actually corresponds to a different, privileged organization's team — as long as they can determine/guess the numeric `github_id` of that team (these ids are often observable via GitHub's public API for organizations with public team info, or leaked in prior legitimate webhook logs). This grants `current_user.authorized?` across the entire Shipit instance, i.e., full authenticated access to deploy, rollback, and merge on stacks belonging to the impersonated organization. This matches "High/Critical: escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub organizations (multi-tenant), and the attacker must control one of them (or must know a `webhook_secret` for some org registered in Shipit — but per the threat model, the attacker owns their own org's app config in a self-service/multi-org Shipit setup). The attacker also needs the target team's numeric `github_id`, which is guessable/enumerable (sequential team IDs, or exposed via GitHub public API, or observed from previous webhook deliveries/logs). No Shipit secrets are required beyond the attacker's own org's real webhook secret, which they legitimately possess. This is feasible for a determined, unprivileged attacker in a multi-org Shipit deployment.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization`, and refuse to reuse/mutate a `Team` whose `organization` doesn't match `params.organization.login` (or better, cross-check that `params.organization.login` matches the `repository_owner`/verified signing org before processing). E.g.:
```ruby
team = Team.find_by(github_id: params.team.id)
if team && team.organization != params.organization.login
  raise ArgumentError, "organization mismatch for team #{params.team.id}"
end
team ||= Team.create!(github_id: params.team.id, github_team: params.team, organization: params.organization.login)
```

### Proof of Concept
Minitest integration test outline (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in `Shipit.github_config` — `org-a` (privileged, `webhook_secret: "secret-a"`) and `org-b` (attacker's own, `webhook_secret: "secret-b"`).
2. Create `Team.create!(github_id: 555, organization: 'org-a')` and add it to `Shipit.github_teams`.
3. POST `/webhooks` with `X-Github-Event: membership`, body `{"action":"added","team":{"id":555,"name":"x","slug":"x","url":"u"},"organization":{"login":"org-b"},"member":{"login":"attacker"}}`, signed with `secret-b` (org-b's real secret, which the attacker owns).
4. Assert response is `200 OK` (signature accepted because `repository_owner` resolves to `org-b`).
5. Assert `Team.find_by(github_id: 555).organization == 'org-a'` (binding LHS: org that signed = org-b; RHS: org owning `Team` row with that `github_id` = org-a — mismatch proven).
6. Assert `User.find_by(login: 'attacker').teams.exists?(id: Team.find_by(github_id: 555).id)` is `true`.
7. Assert `User.find_by(login: 'attacker').authorized?` is `true`, proving unauthorized escalation into `Shipit.github_teams`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
