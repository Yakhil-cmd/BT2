### Title
Cross-repository Status forgery via unscoped commit-sha lookup in `StatusHandler` breaks the "authenticated organization = repository written" binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature scheme in Shipit binds authenticity to the **organization** derived from the payload (`repository.owner.login`), which selects the `GitHubApp`/`webhook_secret` used to HMAC-verify the request. It never re-validates that the **repository/stack actually written to** by the event handler belongs to that same, authenticated organization. `StatusHandler` in particular resolves its write target purely by matching `sha` against *every* `Commit` row in the database, with no scoping to the repository or organization that produced the signed payload. This lets a webhook that is legitimately signed for one (attacker-controlled) organization/repository inject a forged CI status onto a commit that lives under a completely different, victim-owned stack, as long as the two repositories ever share an identical commit SHA (e.g., a fork of the target repo, or a cherry-picked/shared commit).

### Finding Description
`WebhooksController#verify_signature` picks the verification key using only the organization login extracted from the untrusted JSON body: [1](#0-0) [2](#0-1) 

The HMAC is only computed over the raw body against that organization's `webhook_secret`: [3](#0-2) 

Signature verification therefore certifies "this payload was produced by/for organization X" — it does **not** certify that any particular sub-field of the payload (like `repository.full_name` or `sha`) actually belongs to organization X's repositories. Handlers are expected to re-derive their write target from the payload and implicitly trust that GitHub only sends consistent payloads; Shipit's own code does not enforce this.

Every other pull_request/push handler at least re-derives the repository via `Repository.from_github_repo_name(params.repository.full_name)` before acting, e.g.: [4](#0-3) [5](#0-4) 

But `StatusHandler` skips this entirely and matches only on `sha`, globally, across the whole `commits` table: [6](#0-5) 

Once a matching `Commit` is found (regardless of which `Stack`/`Repository`/organization it belongs to), `create_status_from_github!` creates a `Status` record for it: [7](#0-6) 

Creating a `Status` has real side effects — it enables CI on the (victim's) stack and schedules continuous delivery for that commit: [8](#0-7) [9](#0-8) 

Statuses also feed the merge-queue's gating logic (`MergeRequest::StatusChecker`), which determines whether a pending merge request is allowed to proceed based on `required_statuses`/`ignored_statuses`: [10](#0-9) 

**The equality that should hold, but doesn't:**
`organization authenticated by verify_signature` == `organization owning the Stack/Commit that StatusHandler mutates`.

**Attack sequence:**
1. Shipit is configured (as documented) with a multi-organization `github` block, one entry per organization, each with its own `webhook_secret` — this is an explicitly supported configuration (`docs/setup.md`, "Using Multiple Github Applications").
2. Attacker controls/owns a repository under Organization A (their own GitHub org, correctly registered with Shipit) and forks or otherwise reproduces a commit that is byte-identical (and thus SHA-identical) to a commit that exists in a victim's tracked `Stack` under Organization B. This is realistic for public open-source forks, shared upstream commits, or cherry-picks that preserve authorship/timestamp metadata.
3. Attacker triggers a genuine GitHub `status` webhook for that commit under their own Org A repo (e.g., by wiring up any CI check that posts a commit status, which they fully control). GitHub signs this payload with Org A's real webhook secret.
4. `WebhooksController#verify_signature` resolves `repository_owner` = "OrgA" from the payload, fetches Org A's `webhook_secret`, and the signature verifies successfully — correctly, since this really is an Org A payload.
5. `StatusHandler#process` then runs `Commit.where(sha: params.sha)`, which returns **any** commit row across the whole installation with that SHA — including the victim's commit under Organization B's stack — and creates a forged `success` (or any other) `Status` on it.
6. That forged status can satisfy `MergeRequest::StatusChecker#required_statuses`/gate `enable_ci_on_stack`/`schedule_continuous_delivery`, causing an unauthorized merge or deploy on the victim's stack, entirely from a webhook the attacker legitimately triggered on their own, unrelated organization.

This is precisely the report's bug class: a signature verifies one identity/scope, while the code acts on a value (`sha`) that is not bound to, or cross-checked against, that verified scope — exactly analogous to the queue index in `EnforcedTxGateway` being fetched independently of what was actually signed.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. The consequence is an unauthorized merge or deploy on a stack the attacker does not control and was never authenticated against — meeting the High/Critical impact bar ("escalation into authorization... or an unauthorized deploy, rollback or merge"). No `ApiClient` token, GitHub App private key, or Shipit session is required; the attacker only needs their own legitimately-configured GitHub organization/repo (a normal, unprivileged setup step available to anyone who can get onboarded to a multi-org Shipit instance) and a colliding SHA.

### Likelihood Explanation
Likelihood is moderate rather than trivial: it requires (a) the deployment to use the documented multi-organization `github` configuration, and (b) a SHA collision between an attacker-controlled repo and a victim-controlled stack. (b) is not a cryptographic break — it is a realistic scenario for forks, mirrors, or shared/cherry-picked commits that preserve exact tree/parent/author/committer metadata, which is common in open-source and mono-repo-mirroring workflows. The `StatusHandler` code path itself, independent of any SHA-collision nuance, unconditionally demonstrates the missing binding: it never checks `params.repository.full_name` against the commit's actual stack/repository, which is the root cause regardless of how likely a particular collision is in a given deployment.

### Recommendation
- In `StatusHandler#process`, scope the `Commit` lookup to the repository identified by the verified payload, not merely by `sha`, e.g. filter commits by `stacks: { repository: { full_name: params.repository.full_name } }` (mirroring the pattern already used by `Handler#stacks`/`repository_name` and other handlers).
- More generally, add a shared guard in `Shipit::Webhooks::Handlers::Handler` that rejects/ignores any event whose `payload.dig('repository','owner','login')` does not match the organization that was actually used to verify the signature in `WebhooksController#verify_signature`, closing this class of binding gap for all current and future handlers, not just `StatusHandler`.

### Proof of Concept
Not independently executable from static analysis alone — the exploit depends on operator configuration (multi-org `github:` secrets) and an attacker producing/controlling a commit whose SHA collides with a commit tracked in a victim stack. Conceptually:
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled) and `OrgB` (victim), each with distinct `webhook_secret`s, per `docs/setup.md`'s multi-org example.
2. Under `OrgA`, push/fork a commit with identical tree/parent/author-date/committer-date/message to a commit already tracked as `shipit_commits` under an `OrgB` stack (SHA collision by construction).
3. Have GitHub send a `status` event for that commit under `OrgA`'s repo (e.g. any CI integration reporting `success`); this is signed with `OrgA`'s real secret and passes `WebhooksController#verify_signature`.
4. Observe, per `app/models/shipit/webhooks/handlers/status_handler.rb:21-23`, that `Commit.where(sha: params.sha)` matches the row belonging to `OrgB`'s stack and creates a `Status` there, potentially unblocking `OrgB`'s merge queue (`MergeRequest::StatusChecker`) or triggering `schedule_continuous_delivery` on a stack the attacker never had access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
