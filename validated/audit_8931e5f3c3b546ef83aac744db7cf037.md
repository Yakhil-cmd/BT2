### Title
Non-canonical boolean values in `enabled` frontmatter field are silently coerced to truthy strings, causing rules intended as disabled to remain active - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` only converts the literal strings `"true"`/`"false"` (after `.strip()`/`.lower()`) into Python booleans; any other value for `enabled` (e.g. `no`, `off`, `0`, `disabled`, or `true # comment`) is left as a raw non-empty string. Because non-empty strings are truthy in Python, `Rule.from_dict` and `load_rules`'s `if rule.enabled:` check treat these malformed values as enabled regardless of the author's intent, while the human-readable `/hookify:list` output (an LLM-interpreted view of the same raw text) is likely to describe such a value as disabled - creating a silent mismatch between displayed and enforced state.

### Finding Description
`extract_frontmatter` parses simple key/value frontmatter lines with a hand-rolled loop: [1](#0-0) 
Only `'true'` and `'false'` (case-insensitively, after quote/whitespace stripping) are coerced to `bool`. Any other literal - `yes`, `no`, `1`, `0`, `off`, `disabled`, or a value with a trailing comment such as `true # temporarily disabled` - falls through unchanged and is stored as a plain `str` in the `frontmatter` dict.

`Rule.from_dict` then does no additional validation or coercion: [2](#0-1) 

`load_rules` gates rule activation purely on Python truthiness: [3](#0-2) 

Since any non-empty string (including `"no"`, `"0"`, `"off"`) is truthy in Python, a rule author who writes `enabled: no` intending to disable a rule will actually leave it active and enforced by `RuleEngine.evaluate_rules`, which can block tool calls or inject `systemMessage` content on every matching `PreToolUse`/`PostToolUse`/`Stop`/prompt event.

The `/hookify:list` command, by contrast, is not deterministic code - it is an LLM-driven markdown command that reads the raw frontmatter text and semantically renders a ✅/❌ table: [4](#0-3) 
An LLM interpreting `enabled: no` is likely to render "❌ No" (matching human intent), while the actual enforcement path (`config_loader.py` + `rule_engine.py`) keeps the rule active. This produces exactly the inconsistency described: the tool that is supposed to reflect ground truth (`list.md`) disagrees with the tool that enforces it (`load_rules`).

Rule files (`.claude/hookify.*.local.md`) are ordinary repository content - they can be authored by `/hookify` (LLM-generated, normally emits canonical `true`), manually edited by a user, or introduced via a pull request/cloned repository containing a pre-existing `.claude/hookify.*.local.md`. A reviewer or user who edits/reviews such a file and sees `enabled: no`/`enabled: off` would reasonably believe the rule is inert, but it remains fully active.

### Impact Explanation
A rule that a user or reviewer believes is disabled (based on a non-canonical falsy value, and confirmed as "disabled" by the `/hookify:list` display) will silently continue to fire. Depending on the rule's `action`, this can:
- Continue injecting attacker/author-controlled `systemMessage` text into the agent's context on matching tool calls or Stop events (a persistent prompt-injection vector the user believed they had turned off).
- Continue to `deny` (`action: block`) legitimate tool calls the user thought they had re-enabled, causing unexpected denial-of-service on ordinary workflows.

This is a config-parsing correctness / deny-means-deny (or here, "disable-means-disable") violation: the enforced state silently diverges from the state displayed to and expected by the user.

### Likelihood Explanation
Highly reproducible and requires no special privilege: any rule file (self-authored, edited, or introduced via a PR/cloned repo) containing a non-canonical `enabled` value (`yes`, `no`, `1`, `0`, `off`, `disabled`, or `true # note`) triggers the mismatch deterministically on every `load_rules()` call. No parsing exceptions occur, so the failure is silent.

### Recommendation
Replace the ad-hoc string comparison in `extract_frontmatter` (or better, in `Rule.from_dict`) with an explicit boolean-coercion helper that recognizes a well-defined set of truthy/falsy tokens (`true/false/yes/no/1/0/on/off`, case-insensitive, comment-stripped) and raises/logs a clear parsing error for anything else instead of silently defaulting to a truthy string. Additionally, `load_rules`/`Rule.from_dict` should validate that `frontmatter.get('enabled')` is actually a `bool` (or coerced from a recognized token) before using it as a gate, and fail closed (treat as `False`, or reject the file) on unrecognized values rather than fail open via Python string truthiness.

### Proof of Concept
Unit/fuzz test against `extract_frontmatter`/`Rule.from_dict`:
```python
import pytest
from hookify.core.config_loader import extract_frontmatter, Rule

@pytest.mark.parametrize("raw_value,intended_bool", [
    ("no", False),
    ("off", False),
    ("0", False),
    ("disabled", False),
    ("true # temporarily disabled", False),  # trailing comment corrupts intent
    ("yes", True),
    ("1", True),
])
def test_enabled_coercion_matches_intent(raw_value, intended_bool):
    content = f"""---
name: test-rule
enabled: {raw_value}
event: bash
pattern: "rm -rf"
---

message
"""
    fm, msg = extract_frontmatter(content)
    rule = Rule.from_dict(fm, msg)
    # Fails today: rule.enabled is the raw non-empty string, always truthy
    assert bool(rule.enabled) == intended_bool
```
Expected: assertion fails for `no`, `off`, `0`, `disabled`, and the trailing-comment case, demonstrating `rule.enabled` stays truthy (a non-empty `str`) even though the author's intent - and `/hookify:list`'s likely LLM-rendered ✅/❌ status - is "disabled".
