## Analysis

The Balancer/AuraSpell report describes a class of bug: a pool exit or swap that has hardcoded/zero minimum-received parameters, letting the transaction execute at any post-manipulation price and exposing the caller to a sandwich attack. I found a direct structural analog in the Snowbridge system-frontend pallet. [1](#0-0) 

`Pallet::swap_and_burn` calls `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min = None`, explicitly commented "No minimum amount required" — this is functionally identical to Balancer's hardcoded `minAmountsOut = [0, 0]`. This helper is invoked from `swap_fee_asset_and_burn`, which is called by two public, signed extrinsics: `add_tip` (any signed account, arbitrary tip `Asset`) and `register_token` (any origin, arbitrary `fee_asset`) — both are real user entry points, not privileged calls. [2](#0-1) [3](#0-2) [4](#0-3) 

By contrast, `pallet-asset-conversion` (the underlying AMM) *does* implement proper slippage protection when `amount_out_min` is `Some`, enforcing `amount_out >= amount_out_min` before executing the swap — but the caller here deliberately opts out by passing `None`. [5](#0-4) 

### Title
Snowbridge `system-frontend` pallet swaps user tip/fee assets for Ether with no slippage protection, exposing `add_tip`/`register_token` callers to sandwich attacks - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`Pallet::swap_and_burn` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` forces the on-chain AMM (`pallet_asset_conversion`) to accept any output amount for the tip/fee-asset-to-Ether swap by passing `amount_out_min: None`. Any user calling the public extrinsics `add_tip` or `register_token` with a non-Ether fee asset has their entire tip/fee amount swapped at whatever price a front-runner has manipulated the pool to, with zero minimum-received guarantee.

### Finding Description
`swap_and_burn` is the sole path by which a user's tip/fee asset is converted into Ether before being burned for cross-chain teleport/reward accounting: [6](#0-5) 

It is reached from `swap_fee_asset_and_burn`, which is invoked unconditionally whenever the supplied `fee_asset`/tip asset differs from `T::EthereumLocation`: [4](#0-3) 

That function is called from two extrinsics reachable by any signed account with no privileged role required:
- `add_tip(origin, message_id, asset)` — `ensure_signed(origin)` only, `asset` fully attacker-controlled.
- `register_token(origin, asset_id, metadata, fee_asset)` — origin checked only against `RegisterTokenOrigin` for the *registered asset*, not the fee asset; `fee_asset` is attacker-controlled. [7](#0-6) [8](#0-7) 

The underlying `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens` supports an `Option<Balance>` `amount_out_min` and enforces it via `Error::<T>::ProvidedMinimumNotSufficientForSwap` when `Some` is provided: [9](#0-8) 

The `system-frontend` pallet deliberately always passes `None`, so this protection is bypassed for every tip/fee swap it performs — mirroring exactly the reported Balancer/Aura pattern of a hardcoded zero-slippage-protection exit that "forces users to exit... with no slippage protection."

### Impact Explanation
An MEV searcher observing a pending `add_tip`/`register_token` extrinsic in the mempool can:
1. Front-run: swap into the tip-asset/Ether pool to skew the price against the victim.
2. Let the victim's `swap_exact_tokens_for_tokens(..., None, ...)` execute at the manipulated price, receiving far less Ether than the fair-market rate for their tip amount.
3. Back-run: reverse the initial swap to restore the pool and realize the difference as risk-free profit extracted from the victim's tip.

The victim's entire tip/fee amount is consumed regardless of the resulting Ether output (`Self::swap_and_burn` unconditionally burns whatever `ether_gained` results), so the loss is a direct value transfer from the tipper to the sandwicher. Since the tip mechanism exists to incentivize relayers to deliver Ethereum-bound messages, an attacker can also degrade the effective bridge tip/reward economics network-wide by consistently sandwiching these swaps.

### Likelihood Explanation
High. `add_tip` is a normal user-facing extrinsic intended to be called frequently by anyone wanting to expedite bridge message delivery, with a fully attacker/user-controlled `asset` (arbitrary asset kind and amount). No special permissions, governance, or validator/relayer collusion is needed — only visibility into the pending extrinsic (mempool or block-builder MEV), which is standard for any signed extrinsic touching an on-chain AMM pool.

### Recommendation
Add an explicit, caller-supplied (or governance/pallet-config-derived conservative) `amount_out_min` parameter to `add_tip` and `register_token` (or compute one from a fresh on-chain quote plus a bounded tolerance) and thread it through `swap_and_burn`/`swap_fee_asset_and_burn` instead of hardcoding `None`, so `pallet_asset_conversion`'s existing `ProvidedMinimumNotSufficientForSwap` guard can actually protect callers.

### Proof of Concept
No PoC was executed. Evidence is based on static analysis of the reachable, permissionless dispatch path (`add_tip` → `swap_fee_asset_and_burn` → `swap_and_burn` → `Swap::swap_exact_tokens_for_tokens(.., None, ..)`) and comparison with `pallet_asset_conversion`'s slippage-check logic (`do_swap_exact_tokens_for_tokens`), which is bypassed here by construction. No mocked/privileged assumptions are required beyond the presence of a live `pallet_asset_conversion` pool for the tip asset / Ether pair, which is the pallet's designed normal-operation prerequisite (`T::Swap` config). Bounty program eligibility for the Snowbridge system-frontend pallet and its current live deployment status should be independently confirmed against Parity's live bounty scope before submission.

		/// Swaps a specified tip asset to Ether and then burns the resulting ether for
		/// teleportation. Returns the amount of Ether gained if successful, or a DispatchError if
		/// any step fails.
		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		/// If an `amount_out_min` is specified, it will return an error if it is unable to acquire

		/// Withdraws the `path[0]` asset from `sender`, deposits the `path[1]` asset to `send_to`,
		/// respecting `keep_alive`.
		///
		/// If successful, returns the amount of `path[1]` acquired for the `amount_in`.
		///
		/// WARNING: This may return an error after a partial storage mutation. It should be used
		/// only inside a transactional storage context and an Err result must imply a storage
		/// rollback.
		pub(crate) fn do_swap_exact_tokens_for_tokens(
			sender: T::AccountId,
			path: Vec<T::AssetKind>,
			amount_in: T::Balance,
			amount_out_min: Option<T::Balance>,
			send_to: T::AccountId,
			keep_alive: bool,
		) -> Result<T::Balance, DispatchError> {
			ensure!(amount_in > Zero::zero(), Error::<T>::ZeroAmount);
			if let Some(amount_out_min) = amount_out_min {
				ensure!(amount_out_min > Zero::zero(), Error::<T>::ZeroAmount);
			}

			Self::validate_swap_path(&path)?;

			if let Some(amount_out_min) = amount_out_min {
				ensure!(
					amount_out >= amount_out_min,
					Error::<T>::ProvidedMinimumNotSufficientForSwap
				);
			}
