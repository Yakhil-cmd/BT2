### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` allows a signed webhook for attacker's repository to write GitHub statuses onto another stack's commits - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Every other webhook handler resolves the target stacks through `Handler#stacks`, which maps the payload's `repository.full_name` to `Repository.from_github_repo_name` before touching any commit/stack record. `StatusHandler#process` skips this entirely and instead runs `Commit.where(sha: params.sha)` against the whole `commits` table, with no `stack_id`/repository predicate. Because `sha` is not unique across stacks (e.g. a fork shares ancestor commit shas with its upstream repo, each independently synced into its own `Shipit::Commit` rows), a validly-signed status webhook for a repository the attacker owns can write a `Status` onto a commit belonging to a stack the attacker does not own.

### Finding Description
Broken binding: `stack_id predicate present in Stack#commits.by_sha (scoped)` == `stack_id predicate present in StatusHandler#process's Commit.where(sha:) (absent)` — this equality does NOT hold.

Code path:
- `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves stacks strictly via `Repository.from_github_repo_name(repository_name)`, tying every other handler's DB writes to the webhook's `repository.full_name`. `PushHandler#process` demonstrates the pattern: `stacks.not_archived.where(branch:).find_each { ... }` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`).
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) instead calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a class-level, unscoped query. It never calls `stacks`, never checks `payload['repository']` against the commit's owning stack.
- `Shipit::Commit` (`app/models/shipit/commit.rb`) has no application-level or (per the question's premise) DB-level uniqueness constraint tying `sha` to a single stack; `sha` rows are created independently per stack as each stack syncs its own branch history (`self.from_github`, `create_from_github!`). Two different repositories/stacks (e.g. a public upstream repo and any fork of it) will legitimately contain `Commit` rows with identical `sha` values for shared ancestor commits — no hash collision is required, just ordinary git fork semantics.
- `create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:165-169`, `366-386`) persists a `Status`, emits `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)`, and can call `stack.schedule_merges`, all against whichever stack the matched `Commit` row belongs to — not necessarily the stack tied to the webhook's `repository` field.

Attack flow: attacker owns repository X (a fork of victim's public repository Y, or any repository sharing ancestor commits with Y). Both X and Y are configured as separate Shipit stacks and each has synced the shared history, so both stacks now hold a `Commit` row with the same `sha` S. Attacker triggers (or has GitHub deliver) a `status` event for repository X naming sha S — this webhook is signed with the app-wide GitHub webhook secret for a delivery attacker legitimately caused on their own repository, so `verify_signature`/`verify_webhook_signature` passes normally; nothing in that verification ties the signature to a specific repository or stack. `StatusHandler#process` then matches **both** the X commit row and the Y commit row (since it queries by `sha` alone) and writes the attacker-controlled status onto the victim's `Commit`, affecting `stack.deployable?`, `blocked?`, `schedule_merges`, and hook consumers for stack Y.

Existing guards do not catch this: `verify_signature` only proves the payload came from GitHub for the given delivery/repository, not that the `sha` inside belongs to that repository; `drop_unhandled_event`/`ExplicitParameters` only validate event routing and parameter shape, not stack scoping; there is no `stacks`/`repository` check inside `StatusHandler` itself, unlike `PushHandler`.

### Impact Explanation
A `Status` row is written (and deployability-affecting hooks/side effects fire) on a commit belonging to a stack the attacker's webhook does not target, purely because `sha` collides across stacks that share git history (trivial via forking a public repo). This is a genuine cross-tenant mutation: "a payload for one repository mutating another's stack/commit," matching the Critical impact category in scope. It is repeatable against any pair of stacks that share ancestor commits (any fork relationship, or any two Shipit-tracked repositories that happen to share commits, e.g. monorepo splits, cherry-picks, shared submodule history), and each repeated status delivery can flip a shared-ancestor commit's simple state, potentially unblocking/triggering `schedule_merges`/continuous delivery evaluation on the victim stack.

### Likelihood Explanation
Preconditions: (1) two Shipit stacks track repositories that share at least one ancestor commit sha (trivially achieved by attacker forking any public repo already tracked by Shipit), (2) attacker can cause a `status` webhook delivery for their own repository referencing that shared sha (e.g. via GitHub's status API on their own repo, which requires no special Shipit privilege — just push/write access to their own fork). No Shipit session, API token, or webhook secret is needed; the attacker only needs standard GitHub permissions over a repository they control. This is low-cost and fully repeatable, making the likelihood high wherever forks/shared history exist among Shipit-managed repos.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve the target stack(s) via `stacks` (derived from `payload['repository']['full_name']`) and restrict the commit lookup to `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`, or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create `stack_x` for repository `attacker/fork` and `stack_y` for repository `victim/upstream`.
2. Create `Shipit::Commit.create!(stack: stack_x, sha: 'deadbeef' * 5, ...)` and `Shipit::Commit.create!(stack: stack_y, sha: 'deadbeef' * 5, ...)` — same sha, different stacks (simulating shared fork history).
3. Assert the scoped API used elsewhere finds only one: `assert_equal 1, stack_x.commits.where(sha: 'deadbeef' * 5).count`.
4. Assert the unscoped query used by `StatusHandler` finds both: `assert_equal 2, Shipit::Commit.where(sha: 'deadbeef' * 5).count`.
5. Build a `status` webhook payload with `repository.full_name = 'attacker/fork'` and `sha = 'deadbeef' * 5`, `state: 'success'`; invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert `stack_y.commits.find_by(sha: 'deadbeef' * 5).statuses.reload.any?` is true — proving the victim stack's commit received a status even though the webhook's `repository` field only named the attacker's stack.
