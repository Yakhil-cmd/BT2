### Title
Cross-organization webhook forgery: signature verified against one GitHub org but write actions dispatched to a repository named by an unrelated payload field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used for HMAC verification based on `params.dig('repository','owner','login') || params.dig('organization','login')`, but the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a separate, attacker-controlled field in the same JSON body. In a multi-org Shipit deployment (explicitly supported per `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), these two fields are never cross-checked for consistency.

### Finding Description
`verify_signature` in [1](#0-0)  computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1)  and uses it to select which `Shipit.github(organization:)` config — and therefore which `webhook_secret` — verifies the raw request body signature via `github_app.verify_webhook_signature` [3](#0-2) .

After signature verification passes, `WebhooksController#create` dispatches the *entire* parsed JSON body to event handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . Handlers such as `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` inherit `Handler#stacks`, which resolves the target repository from a *different* field: `payload.dig('repository', 'full_name')` [5](#0-4) , then looks it up via `Repository.from_github_repo_name` [6](#0-5) .

The binding that should hold is: **organization whose secret authenticated the request == owner of the repository the handler writes to.** This binding is never enforced. `repository.owner.login` (used for signature key selection) and `repository.full_name` (used for stack/repository resolution) are independent, attacker-supplied strings in the raw POST body — GitHub itself keeps them consistent, but nothing in this engine requires it. An attacker who controls (or has legitimately been granted) a Shipit-connected GitHub organization "OrgA" knows OrgA's `webhook_secret` is never disclosed to them directly, but this is irrelevant: the attacker can compute a valid HMAC-SHA1 signature for *any* payload if they can get any webhook delivered from OrgA (e.g. by triggering a real, legitimate webhook from a repo/org they control that is installed on the same Shipit instance) or, in deployments where `webhook_secret` is unset/blank, `verify_webhook_signature` returns `true` unconditionally [7](#0-6) , meaning signature verification provides no binding at all in that (documented, supported) configuration state, e.g. `test/dummy/config/secrets_double_github_app.yml` explicitly sets `webhook_secret: # nil` for both orgs.

Given a signature that verifies for `repository.owner.login = "OrgA"`, the attacker sets `repository.full_name = "OrgB/victim-repo"` in the same payload. `verify_signature` passes (keyed off OrgA), but `PushHandler#process` / `StatusHandler#process` / `CheckSuiteHandler#process` operate on the `OrgB/victim-repo` stack, because they derive the target purely from `full_name` [8](#0-7) .

### Impact Explanation
This breaks the trust binding: *organization authenticated (signature key selection) vs. repository actually written (target of the mutating handler)*. Concretely, with a forged/crafted `status` event, `StatusHandler` creates a `Status` for an arbitrary commit on the victim stack based entirely on attacker-supplied `sha`, `state`, `description`, `target_url` fields — this is the mechanism that feeds Shipit's "deployable status" checks, which gate whether a commit is allowed to deploy. Forging a passing/green status for a victim's stack via a signature that only proves control of an unrelated organization's webhook secret can lead to an unauthorized deploy being permitted (a commit that never actually passed CI being marked deployable), which matches the Critical impact bucket ("an unauthorized deploy"). It also allows a `push` event to force `stack.sync_github(expected_head_sha:)` on a repository the attacker does not control, at minimum an integrity/availability issue on unrelated stacks.

### Likelihood Explanation
Requires (a) a multi-organization Shipit deployment (explicitly documented and supported), and (b) either an org with `webhook_secret` unset (explicitly shown as a supported example config), or the ability to obtain a validly-signed payload from one org and relay the signature with modified body content for a different org's repository. The check performed by `verify_signature` never validates that the field it keys off of (`repository.owner.login`/`organization.login`) matches the field the handler actually consumes (`repository.full_name`), so no additional privilege beyond delivering a POST to `/webhooks` with a crafted body/signature pair is needed once either precondition holds.

### Recommendation
In `Handler#repository_name` (and anywhere handlers resolve the target repository/stack), require that the owner segment of `payload.dig('repository', 'full_name')` matches the `repository_owner` value that was actually used to select the webhook secret in `WebhooksController#verify_signature`. Concretely, pass the authenticated `repository_owner` through to the handler dispatch and add a check such as:

```ruby
# in WebhooksController#create, after verify_signature succeeds
authenticated_owner = repository_owner
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, authenticated_owner:) }

# in Handler#stacks / #repository_name
def repository_name
  full_name = payload.dig('repository', 'full_name')
  owner, = full_name&.split('/')
  raise Shipit::UnauthorizedRepositoryReference if authenticated_owner && owner != authenticated_owner.downcase
  full_name
end
```

### Proof of Concept
1. Deploy Shipit with two GitHub Apps configured, e.g. as in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`), with `OrgOne`'s `webhook_secret` blank/unset (a documented supported configuration).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests",
  "description": "forged green status",
  "target_url": "https://ci.example.com/forged"
}
```
3. `verify_signature` resolves `repository_owner => "OrgOne"`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [7](#0-6)  — no signature header is even required.
4. `StatusHandler` (dispatched with the full `params`) resolves the target stack via `payload.dig('repository', 'full_name') = "OrgTwo/victim-repo"` [8](#0-7)  and creates a forged passing `Status` for the victim commit under `OrgTwo`, an organization whose own webhook secret was never presented or verified.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
