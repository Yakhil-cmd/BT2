### Title
Unvalidated `creator` account in `initialize_with_permission` allows permanent freezing of creator swap-fee revenue - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` accepts an arbitrary, unchecked `creator` account and stores it verbatim as `PoolState.pool_creator`, with no constraint tying it to the `payer`, a signature, or any ownership proof. This is the direct analog of the reported `ownedBy` issue: a value that is supposed to represent a legitimate owner/creator is fully attacker-controlled and later relied upon for privileged access, letting an unprivileged caller assign pool ownership to any address they choose, including addresses with no private key.

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared as: [1](#0-0) 
It is an `UncheckedAccount` with only a doc comment (`/// CHECK: creator of pool`) and no `constraint`, no `Signer`, and no relation enforced to `payer`. This value flows unchanged into pool state: [2](#0-1) 
and is persisted as `pool_creator` in `PoolState::initialize`: [3](#0-2) 

`pool_creator` subsequently gates all future creator-fee withdrawals. `collect_creator_fee` requires a `Signer` whose address equals `pool_state.pool_creator`: [4](#0-3) 
and `collect_creator_fee_permissionless` allows anyone to trigger a transfer, but the destination ATA authority is still fixed to `pool_creator`: [5](#0-4) 

Because `creator` is never validated to be a key-controlled account (e.g., it can be set to a PDA, a program ID, or any arbitrary pubkey with no corresponding private key), an attacker calling `initialize_with_permission` can set `pool_creator` to an address that can never sign a transaction. Swap activity on that pool accrues `creator_fees_token_0`/`creator_fees_token_1` in `PoolState` exactly as with any normal pool. Those accrued fees can only ever be released to the `pool_creator` address (via `collect_creator_fee`, which requires that address to sign, or `collect_creator_fee_permissionless`, which sends tokens into an ATA owned by that address). If `pool_creator` is an address with no private key, the tokens transferred into that ATA are permanently locked — nobody can ever produce a valid signature to `collect_creator_fee`, and even the permissionless path only deposits funds into an ATA that the "owner" can never move out of.

This mirrors the reported Gitcoin issue precisely: an `ownedBy`/`creator` parameter that is supposed to represent a legitimate, verifiable owner is accepted without any check that it corresponds to the actual party creating/funding the pool (`payer`), allowing an unprivileged caller to assign ownership/attribution to any address of their choosing.

### Impact Explanation
Creator swap fees are real economic value extracted from swappers/LPs trading in the pool. Because `pool_creator` can be set to a non-signable address, that accumulated fee revenue becomes permanently frozen and unrecoverable once collected into the associated token account of an uncontrollable address — a permanent freezing of user funds. This is reachable from a single transaction by any unprivileged caller with attacker-chosen accounts (`initialize_with_permission`), satisfying the Medium/High impact bar (permanent freezing of funds), consistent with the report's underlying bug class (unchecked ownership-attribution parameter).

### Likelihood Explanation
`initialize_with_permission` is a normal, permissionless-facing entrypoint (no signer or address constraint links `creator` to `payer`), so any account submitting the instruction with attacker-chosen `creator` value can trigger this at will, with no special privileges required.

### Proof of Concept
1. Attacker calls `initialize_with_permission` supplying `payer` = attacker's funded wallet, and `creator` = an arbitrary pubkey with no known private key (e.g., a random keypair's public key never used again, or a PDA derived from unrelated seeds/program) — see the unconstrained account definition: [1](#0-0) .
2. `pool_state.initialize(...)` stores this address as `pool_creator`: [6](#0-5) .
3. Users swap against the pool via `swap_base_input`/`swap_base_output`; `creator_fees_token_0`/`creator_fees_token_1` accumulate in `PoolState`.
4. Anyone calls `collect_creator_fee_permissionless`, which creates an ATA owned by the uncontrollable `creator` address and transfers the accumulated creator fees into it: [7](#0-6) .
5. Because no private key exists for the `creator` address, those tokens can never be moved out of that ATA — permanently frozen. `collect_creator_fee` (the signer-gated path) is also permanently inaccessible since `creator` can never sign: [4](#0-3) .

### Recommendation
Require `creator` in `InitializeWithPermission` to be validated against the actual party responsible for the pool — e.g., require it to be a `Signer`, or constrain it to equal `payer`, or require an explicit signed authorization/permission-account proof (similar to the `create_permission_pda` mechanism already present in the codebase) before it is persisted into `PoolState.pool_creator`.
