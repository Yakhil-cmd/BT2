### Title
Signature verified against `repository.owner.login`'s org while `OpenedHandler` provisions a `ReviewStack` for the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository_owner`, which reads `params.dig('repository','owner','login')`. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`, however, resolves the repository/stack it actually mutates from a completely different field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name`. Nothing in the controller or the handler enforces that these two attacker-supplied fields refer to the same repository, so a webhook that authenticates as a secret-less/unrelated org can still be routed to mutate a victim repository named only in `full_name`.

### Finding Description
The broken binding, as an equality that the code implicitly assumes but never checks:
`params.repository.owner.login` (used for authentication) == owner(`params.repository.full_name`) (used for authorization/mutation).

- `verify_signature` picks the signing `GitHubApp` with `Shipit.github(organization: repository_owner)` where `repository_owner` comes only from `params.dig('repository','owner','login')`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org has no configured `webhook_secret`: `return true unless webhook_secret`. [3](#0-2) 
- `OpenedHandler#repository` never reads `params.repository.owner`; it resolves the repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`. [4](#0-3) 
- The handler's `params do ... end` schema only requires `repository.full_name`; it does not require/validate `repository.owner.login` at all, so there is no schema-level cross-check between the two fields. [5](#0-4) 
- `process` calls `ReviewStackAdapter#find_or_create!`, which creates a brand-new `ReviewStack` under `repository.review_stacks` (the repository resolved from `full_name`) and enqueues it for provisioning if no stack for that PR environment exists yet. [6](#0-5) [7](#0-6) 

Exploit flow: attacker crafts a JSON body with `X-Github-Event: pull_request`, `action: "opened"`, `repository.owner.login = "orgA"` (an org configured in Shipit's `secrets.github` with no `webhook_secret`, so verification always returns `true`), and `repository.full_name = "orgB/victim-repo"` (a real tracked repository with `review_stacks_enabled` and a permissive `provisioning_behavior`). `verify_signature` authenticates the request trivially against `orgA`. `Shipit::Webhooks.for_event('pull_request')` then invokes `OpenedHandler.call(params)`, which resolves `orgB/victim-repo` and creates a new `ReviewStack` for the attacker-chosen PR number/branch (`params.pull_request.head.ref`), queuing it for provisioning — all without ever presenting a signature validated by `orgB`'s actual secret.

Existing guards do not prevent this: `drop_unhandled_event` and `check_if_ping` only gate on event type; `ExplicitParameters` schemas validate presence/type of fields, not cross-field consistency; there is no `Repository`-level or controller-level check binding `owner.login` to `full_name`'s owner segment. `ignore_ci` (`Commit#deployable?` at `app/models/shipit/commit.rb:227-229`) is orthogonal — it only affects whether a commit is deployable once a stack exists, not whether the forged provisioning itself succeeds. If a `ReviewStack` for that PR/environment already exists with `ignore_ci: true`, `find_or_create!` simply returns it unchanged (no additional mutation from `OpenedHandler` in that case, since `create!` unconditionally sets `ignore_ci: false`), so the CI-bypass amplification applies to already-existing review stacks or downstream continuous-deployment flows on the branch pushed by the attacker, not to the create path itself. [8](#0-7) 

### Impact Explanation
An attacker who controls only a webhook payload for an org with no configured secret can cause Shipit to create a `ReviewStack` and enqueue provisioning for a different, victim repository/org, matching the "payload for one repository mutating another's stack" Critical category. This is repeatable against any tracked repository with `review_stacks_enabled` and permissive `provisioning_behavior`, for arbitrary PR numbers/branches, as long as the attacker can name any org configured in `secrets.github` without a `webhook_secret` (or reachable via `github_default_organization` fallback) in `repository.owner.login`.

### Likelihood Explanation
Preconditions: (1) Shipit must have at least one configured GitHub org with no `webhook_secret` set (or a legacy single-org config with `secrets.github` present but no top-level `webhook_secret`), which the attacker can freely name in `repository.owner.login`; (2) the victim repository (named via `full_name`) must have `review_stacks_enabled` and a `provisioning_behavior` that provisions without requiring a label (`allow_all`) or the attacker crafts a PR label matching `provisioning_label_name`. Attacker cost is a single unauthenticated HTTP POST to `/webhooks`; no Shipit session, API token, or GitHub secret is required. Fully repeatable.

### Recommendation
In `Shipit::WebhooksController#verify_signature` (or in each handler), require that the org used to select the webhook secret matches the owner segment of `params.repository.full_name`, and reject the request (422) on mismatch. Better: derive both the signing org and the repository lookup from the same single canonical field, and validate `repository.owner.login` against `repository.full_name`'s owner in the shared `ExplicitParameters` schema or a common handler mixin before any `ReviewStackAdapter` mutation occurs.

### Proof of Concept
minitest plan (webhooks controller integration test, no live GitHub):
1. Configure `Rails.application.credentials.github` with two orgs: `orga` (no `webhook_secret` key) and `orgb` (with `webhook_secret: "s3cr3t"`).
2. Create `shipit_repositories(:orgb_repo)` with `owner: "orgb"`, `review_stacks_enabled: true`, `provisioning_behavior: "allow_all"`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body: `{"action":"opened","number":99,"pull_request":{...,"head":{"ref":"attacker-branch"}},"repository":{"owner":{"login":"orga"},"full_name":"orgb/orgb_repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `200`/`:ok` (not `422`) even though the signature was never validated against `orgb`'s secret — i.e., before/after equality check: `repository_owner ("orga") != Repository.from_github_repo_name("orgb/orgb_repo").owner ("orgb")`, yet the request was accepted.
5. Assert `Shipit::ReviewStack.exists?(repository: shipit_repositories(:orgb_repo), environment: "pr99")` is `true`, and `ReviewStackProvisioningQueue` contains the new stack — proving a repository (`orgb`) was mutated by a payload authenticated under a different org (`orga`)'s (non-)secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
