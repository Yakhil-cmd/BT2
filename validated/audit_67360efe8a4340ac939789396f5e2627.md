### Title
Deploy env-variable whitelist checked against the stack's cached HEAD spec, not the `shipit.yml` of the commit being deployed - (File: app/models/shipit/stack.rb)

### Summary
This is an analog of the `InsuranceFund#syncDeps()` bug class: a value (`vusd` in the original report, here the whitelist of permitted deploy environment-variable names) is read from a mutable, asynchronously-refreshed piece of state (`Governance`-set `vusd` / Shipit's `cached_deploy_spec`) at one point in time, and used again later, after it may have silently changed, to gate an action whose actual effect (withdrawal / process execution) is bound to a *different* version of that state (the `VUSDv2` balance / the target commit's own `shipit.yml`).

### Finding Description
An unprivileged-but-authenticated caller who only has `deploy:stack` permission (API) or Shipit deploy access (web) can trigger a deploy of *any* historical commit on the stack by specifying its `sha`/`until_commit_id`: [1](#0-0) [2](#0-1) 

The `env` hash the caller supplies is validated with `stack.filter_deploy_envs`, which is delegated straight to `cached_deploy_spec` — the `Stack`'s **cached, asynchronously-recomputed** deploy spec, built from whatever commit was HEAD the last time `CacheDeploySpecJob` ran: [3](#0-2) [4](#0-3) [5](#0-4) 

`cached_deploy_spec` is refreshed out-of-band by `CacheDeploySpecJob`, always against the **newest reachable commit**, independent of which commit is actually being deployed: [6](#0-5) 

Once the deploy is created, the (already-filtered) `env` is stored on the `Task`/`Deploy` record and later merged verbatim — with no re-validation — into the OS-level environment of the shell commands that are executed, which are instead derived from a **freshly loaded** `DeploySpec::FileSystem` built from the actual checked-out working directory of the commit being deployed (`@task.until_commit`, which can be an older/different commit than HEAD): [7](#0-6) [8](#0-7) 

The equality broken is:
`env keys permitted (validated against Stack#cached_deploy_spec.deploy_variables, i.e. HEAD's shipit.yml at last sync time)` ≠ `env keys actually spawned as OS environment variables when running the deploy_steps sourced from the shipit.yml of the specific until_commit being deployed`.

Because `deploy_variables` (the whitelist) can differ between commits — a repository owner can add, remove, or rename `deploy.variables` entries in `shipit.yml` over time — a caller who is authorized only to *trigger deploys* (not to write to the repository) can pick an older `until_commit` whose `shipit.yml` does **not** declare a given variable, while the *currently cached* HEAD spec still does declare it (or vice-versa: HEAD declares a variable the target commit's script never expected). The env value is accepted by the stale whitelist check and unconditionally injected as a real process environment variable into whatever deploy script the *target* commit executes.

### Impact Explanation
This lets a `deploy:stack`-scoped identity smuggle attacker-chosen values into the OS environment of the deploy host process for a `shipit.yml`/deploy script it does not have write access to author, because the permission check and the execution are bound to two different revisions of the same document. Depending on what the target commit's deploy script does with ambient environment variables (many shell deploy scripts read generic variables such as `PATH`, proxy variables, credential-file paths, `RUBYOPT`, `BUNDLE_*`, etc.), this can escalate from "run an approved deploy with approved variables" into "run an approved deploy with unapproved, attacker-controlled process environment," a command-injection-adjacent primitive on the deploy host. This aligns with the report's "High" bucket description of escalation through a broken deployment-trust binding, though the ultimate severity depends on what the specific `shipit.yml` scripts of older commits actually consume from the environment — the same "acknowledged, but relies on config discipline" caveat the original report received.

### Likelihood Explanation
Requires only an actor who already holds legitimate `deploy:stack` permission (a standard, lower-privileged capability distinct from repository write access) and the ability to choose an arbitrary historical `sha`/`until_commit_id`, both of which are ordinary, documented API/UI capabilities (`params.sha`, `deploy_params[:until_commit_id]`). No race condition, timing attack, or privileged credential is needed — simply a repository whose `shipit.yml` `deploy.variables` list has changed between commits, which is a routine occurrence for actively maintained projects.

### Recommendation
Validate `env` against the `deploy_variables` of the `DeploySpec` for the **commit actually being deployed** (`until_commit`), not the stack's asynchronously cached HEAD spec — i.e., load (or lazily compute) the spec for `until_commit` before calling `filter_deploy_envs`, or re-validate `task.env` against the freshly-loaded `deploy_spec` inside `TaskCommands#env` immediately before merging it into the command environment, rejecting/dropping any keys not declared by that commit's own `shipit.yml`.

### Proof of Concept
1. Repository's `shipit.yml` at an older commit `A` (say, from 3 releases ago) has no `deploy.variables` section (so no variables are declared/expected).
2. A later commit `B` (current HEAD) adds `deploy: variables: [{name: DEBUG_HOOK}]`; `CacheDeploySpecJob` recomputes `stack.cached_deploy_spec` from `B`.
3. An identity holding only `deploy:stack` API permission calls `POST /api/stacks/:id/deploys` with `sha: <commit A sha>` and `env: {DEBUG_HOOK: "<attacker value>"}`.
4. `Stack#build_deploy` calls `filter_deploy_envs({DEBUG_HOOK: ...})`, which delegates to `cached_deploy_spec` (built from `B`) — `DEBUG_HOOK` is on the whitelist, so it passes and is persisted on the `Deploy` record.
5. The `Deploy` task is executed against commit `A` (`until_commit = A`); `TaskCommands#env` merges `@task.env` — including `DEBUG_HOOK` — into the OS environment of the shell process that executes `A`'s deploy script, even though `A`'s own `shipit.yml` never declared or expected `DEBUG_HOOK`.
