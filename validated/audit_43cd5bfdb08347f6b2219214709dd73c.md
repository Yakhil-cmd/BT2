### Title
Comma-split inline-dict YAML parser in `extract_frontmatter` silently truncates `Condition.pattern`, causing enforced hookify regex to diverge from the pattern text a reviewer sees - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter`'s inline-dict branch splits list items on every literal comma (`item_text.split(',')`) with no regex/quote awareness, so any `pattern:` value containing a comma (a plain comma, or a common regex quantifier like `{2,4}`) is silently truncated before it ever reaches `Condition.pattern`. Because `configure.md` derives its user-facing rule description directly from the raw file's `pattern`/`message` text rather than from the parsed `Condition` object, the description shown to the user during rule review can differ from the actual regex `RuleEngine._regex_match` enforces at hook time.

### Finding Description
In `plugins/hookify/core/config_loader.py`, the inline-dict branch of `extract_frontmatter` treats any list item containing both `:` and `,` as a comma-separated `key: value` dict: [1](#0-0) 
For an item such as `- field: command, operator: regex_match, pattern: rm -rf, /etc`, the naive `split(',')` produces segments `["field: command", " operator: regex_match", " pattern: rm -rf", " /etc"]`. The trailing segment `" /etc"` has no `:` and is silently discarded, so the resulting dict is `{field: 'command', operator: 'regex_match', pattern: 'rm -rf'}` — the comma-bearing tail of the intended pattern is dropped without any warning. The same corruption occurs for entirely ordinary regex syntax such as quantifiers (`a{2,4}`), where the split breaks the pattern into `"a{2"` and `"4}"`, yielding an unterminated, likely-invalid regex.

This truncated value flows unchanged into `Condition.from_dict` and `Rule.from_dict`: [2](#0-1) 
and is what `RuleEngine._check_condition`/`_regex_match` actually compiles and matches against tool input at enforcement time: [3](#0-2) 

Meanwhile, `configure.md` never calls `extract_frontmatter` itself — the agent following the command simply reads the raw file and is instructed to produce a "Brief description from rule's message or pattern": [4](#0-3) [5](#0-4) 
Because this description is built from the literal on-disk text rather than the parsed `Condition.pattern`, it can present the full, untruncated pattern (e.g., "matches `rm -rf, /etc`") while the actual enforced regex compiled by `RuleEngine` is only the truncated fragment (e.g., `rm -rf`, or in the quantifier case, a broken/invalid regex that never matches at all due to `re.error` being swallowed). No validation step cross-checks the parsed `Condition.pattern` against what is shown to the user, and no allowlist/approval mechanism exists to catch the mismatch.

### Impact Explanation
This is a state-binding failure between the UI description a user relies on when enabling/re-enabling a hookify rule via `/hookify:configure` and the regex actually enforced by `RuleEngine`. Practical consequence: a hookify rule intended (and displayed) as blocking/warning on a specific dangerous pattern can silently enforce a narrower, or entirely broken (never-matching), regex — giving the user false confidence that a protection is active when it is not, or is weaker than believed. This does not directly grant command execution or secret disclosure by itself, but it undermines the guardrail hookify is meant to provide, which can allow subsequently dangerous commands/file edits to slip past a protection the user believes is enforced as described.

### Likelihood Explanation
Any rule file using the inline comma-separated dict syntax (`- field: x, operator: y, pattern: z`) with a pattern containing a comma — including ordinary regex constructs like `{m,n}` quantifiers or alternations with literal commas — trivially triggers the truncation. This requires only that such a `.claude/hookify.*.local.md` rule file exist in the working tree (e.g., introduced via repository content/PR or authored carelessly) and that `/hookify:configure` be used to review it; no special privileges are needed to author or exploit the parsing bug, and no existing check in `extract_frontmatter`, `Condition.from_dict`, or `configure.md` detects or prevents the mismatch.

### Recommendation
Replace the naive `split(',')` inline-dict parser in `extract_frontmatter` with a proper YAML parser (or at minimum a quote-aware/bracket-aware tokenizer) so pattern values containing commas are preserved intact. Additionally, have `configure.md`'s description-generation step source its text from the actually-parsed `Condition.pattern` (or validate consistency against it) rather than independently re-reading raw frontmatter text, so the displayed rule semantics can never diverge from what `RuleEngine` enforces.

### Proof of Concept
Unit test in `plugins/hookify/core/config_loader.py` test style:
```python
content = """---
name: test-rule
enabled: true
event: bash
conditions:
  - field: command, operator: regex_match, pattern: rm -rf, /etc
---
Dangerous command!
"""
fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)
assert rule.conditions[0].pattern == "rm -rf, /etc"  # FAILS: actual is "rm -rf"
```
Second PoC demonstrating quantifier corruption and enforcement failure:
```python
content2 = """---
name: test-quantifier
enabled: true
event: bash
conditions:
  - field: command, operator: regex_match, pattern: a{2,4}
---
msg
"""
fm2, msg2 = extract_frontmatter(content2)
rule2 = Rule.from_dict(fm2, msg2)
assert rule2.conditions[0].pattern == "a{2,4}"  # FAILS: actual is "a{2"
engine = RuleEngine()
result = engine.evaluate_rules([rule2], {"tool_name": "Bash", "tool_input": {"command": "aaaa"}})
# Expected block/warn per raw file's declared pattern "a{2,4}", but re.error on invalid
# pattern "a{2" causes _regex_match to silently return False -> rule never fires.
assert result == {}
```
These assertions demonstrate that `Condition.pattern` used by `RuleEngine._regex_match` at enforcement time diverges from the pattern text literally present (and displayable) in the rule file, confirming the parser differential.
