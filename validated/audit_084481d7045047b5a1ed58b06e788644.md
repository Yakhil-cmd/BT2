This confirms the multi-org setup: `Shipit.github(organization:)` supports per-organization webhook secrets when `config/secrets.yml` uses the multi-org schema documented in `docs/setup.md:182-209` and exemplified in `test/dummy/config/secrets_double_github_app.yml`. This is the exact binding-break needed.

### Title
HMAC verification keyed on `repository.owner.login` while handlers dispatch on `repository.full_name`, letting a webhook from one onboarded GitHub organization act on stacks belonging to another - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (`docs/setup.md:182-209`), each GitHub organization has its own `webhook_secret`, selected via `Shipit.github(organization:)` [1](#0-0)  . `WebhooksController#verify_signature` picks which organization's secret to verify the HMAC signature against solely from `repository.owner.login` (or `organization.login`) inside the untrusted, attacker-supplied JSON body [2](#0-1) . Once the signature is accepted, the actual event handlers (e.g. `PushHandler`, `Handler#stacks`) resolve the target `Stack`/`Repository` using a *different* field of the very same payload: `repository.full_name` [3](#0-2) [4](#0-3) . Nothing ties `repository.owner.login` (the field authenticating the request) to `repository.full_name` (the field determining which repository/stack is written to). This is directly analogous to the reported bug class: two related values (here, "authenticating organization" vs. "acted-upon repository") that must move together/be consistent are read from unchecked, independently-controlled inputs, and only one of them is checked (against the signature) while the other drives the actual state mutation.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` comes from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [5](#0-4) . In the multi-org configuration schema, each organization key in `secrets.github` has its own independent `webhook_secret` [6](#0-5) , so a party who legitimately controls a webhook for `OrgOne` (i.e., knows `OrgOne`'s `webhook_secret`, e.g. because they own a repo in `OrgOne` that is hooked to this Shipit instance) can compute a valid signature for `OrgOne`.

Handlers, however, never re-derive or cross-check `repository.owner.login`; they independently pull `repository.full_name` to select the `Stack`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) , and `PushHandler#process` uses this to look up and drive `stack.sync_github` [4](#0-3) . An attacker who legitimately signs a webhook as `owner.login = "OrgOne"` can freely set `repository.full_name = "OrgTwo/victim-repo"` in the same JSON body — the signature check never inspects `full_name`, and the handler never inspects `owner.login`. This breaks the intended binding: `organization that authenticated == repository that is written`.

### Impact Explanation
This allows an attacker who only controls one onboarded organization (or one repository within it) to forge push/status/check_suite events attributed to a completely different organization/repository managed by the same Shipit instance. Depending on handler, this can trigger `GithubSyncJob`/`sync_github` against a victim `Stack` with attacker-chosen `expected_head_sha`, or manipulate commit statuses (`status` event handler) or PR/review-stack state for a repository the attacker does not own, potentially causing unauthorized state changes that influence what commit gets deployed on a victim stack — an unauthorized-deploy-adjacent write across repository boundaries without ever needing write access to the victim repository.

### Likelihood Explanation
Requires that the operator run the multi-organization configuration (documented, supported, first-class feature) and that the attacker legitimately control a webhook-emitting repo/org in at least one onboarded organization — which is realistic for any Shipit instance servicing multiple, mutually-untrusted GitHub organizations. No `ApiClient` token, GitHub App key, or victim repo access is required, only the ability to hand-craft the JSON payload sent to a legitimately-signed webhook.

### Recommendation
When resolving the target repository/stack in handlers, cross-check that `payload.dig('repository', 'owner', 'login')` (or `organization.login`) matches the organization prefix of `payload.dig('repository', 'full_name')`, and reject the event otherwise. Alternatively, have `verify_signature` derive the signing organization strictly from `repository.full_name`'s owner segment so the same field used for authorization is the one used for dispatch.

### Proof of Concept
1. Configure Shipit with the multi-org schema: `OrgOne` and `OrgTwo`, each with distinct `webhook_secret`s, both onboarded with stacks in the datastore.
2. Attacker owns/administers a repo in `OrgOne` and has GitHub deliver (or can replay) a legitimately-signed webhook, so they know `OrgOne`'s `webhook_secret` (or can request GitHub to redeliver with attacker-controlled payload edits kept consistent with the HMAC by controlling the raw body before GitHub signs it, e.g. via a repo transfer/rename trick, or more directly: attacker runs their own small GitHub App/webhook proxy for their `OrgOne` repo and simply computes `HMAC-SHA1(OrgOne_secret, body)` themselves since they possess that secret from their own app installation config on `OrgOne`).
3. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha, e.g. an old/malicious commit already on OrgTwo/victim-repo>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
signed with `OrgOne`'s `webhook_secret` in `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgOne")` and successfully verifies the signature against `OrgOne`'s secret [8](#0-7) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/victim-repo")` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")` on the victim stack belonging to `OrgTwo` — despite the request only ever being authenticated as `OrgOne`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end
