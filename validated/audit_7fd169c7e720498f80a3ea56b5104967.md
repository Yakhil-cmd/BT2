### Title
Array-mutation-during-iteration in `foreach`/`map`/`filter`/`reduce` bypasses the length/count bound check — ([File: formula/evaluation.js])

### Summary
CVE-2016-2338 is a TOCTOU-style heap overflow where a size (`tags array length`) is captured once for a buffer allocation, then a callback invoked during serialization mutates the underlying array, growing it past the pre-computed bound. The oscript evaluator in `formula/evaluation.js` has the same class of bug: for `foreach`/`map`/`filter`/`reduce`, the element count is checked once against a declared `count` bound, and the array/object being iterated is used *by reference, not by copy*, while a user-supplied AA function body executes per element and can mutate that very same array through the shared `locals` bindings.

### Finding Description
For `foreach`/`map`/`filter`/`reduce`, the target collection is evaluated once into `res` and the bound is checked a single time before iteration begins: [1](#0-0) 

`res.obj` for arrays is used directly as `arrElements`, not cloned, because `'local_var'` returns the raw object reference from `locals` rather than a copy: [2](#0-1) 

The callback function (`func_expr`) is executed via `callFunction`, which copies the *same object references* (not deep-cloned values) for any local variable captured in `scopeVarNames` into the function's temporary scope, then swaps them into the shared `locals` object for the duration of the call: [3](#0-2) 

This reference-sharing (not copy-on-call) semantics is confirmed by the existing test showing a function mutating its caller's object argument in place: [4](#0-3) 

Because the same array reference (`locals[var_name].obj === res.obj === arrElements`) is reachable from inside the mapper/reducer function body, that function can call `delete($x, index)`, which directly splices the underlying array: [5](#0-4) 

The outer iteration is driven by `async.eachOfSeries(arrElements, ...)`: [6](#0-5) 

Since `arrElements` can shrink or otherwise be mutated *during* this same iteration (via the very callback function that operates on each element), the `arrElements.length > count` check performed once up front no longer reflects the actual state of the array while the loop continues to run — exactly analogous to the Psych `head` buffer being allocated from `tags.length` and then the `tags` array growing afterward through a crafted object's callback.

### Impact Explanation
This is reachable by any AA trigger sender who can cause an AA (own or a third party's, if its bytecode contains `foreach`/`map`/`filter`/`reduce` with a function operating on a shared local array) to execute this pattern. Because `map`/`filter`/`reduce` results are subsequently used to build state-variable updates, response messages (`bounce`, payments, asset issuance, etc.) inside AA definitions, a length/element-count mismatch during iteration can produce logically inconsistent intermediate arrays (`retValue`, `accumulator`) that no longer match the declared `count` guarantee the rest of the formula logic relies on. Because AA execution is otherwise required to be fully deterministic and self-consistent for every validating node, any place where an internal invariant (length checked once, but the underlying reference is still live and mutable) can silently diverge from the real array state is a correctness/soundness defect in state computation, which is the same "count vs. actual size" confusion at the root of the CVE.

### Likelihood Explanation
The trigger conditions require nothing more than being able to post a payment/trigger to an AA whose bytecode allows this pattern (or being the AA author who intentionally writes such logic) — no special privileges, no malicious peer/hub, no light client tricks. The `aa2UpgradeMci` gate simply requires the feature to be active; `foreach`/`map`/`filter`/`reduce` and closures capturing outer local arrays are ordinary oscript features exercised directly by unit posters interacting with AAs. This makes the precondition easy to construct.

### Recommendation
Deep-clone the collection (`res.obj`) into `arrElements` before starting the `async.eachOfSeries` iteration in the `foreach`/`map`/`filter`/`reduce` handler, so that any mutation performed by the invoked function (local or remote) inside the loop cannot affect the array/object currently being iterated. Re-validate that `count`/length invariants continue to hold against the frozen snapshot rather than the live, mutable reference, mirroring how `array`/`dictionary` literal evaluation already isolates newly built results via `string_utils.cloneDeep` before performing size checks (see `formula/evaluation.js:1130-1167`).

### Proof of Concept
Conceptual oscript inside an AA definition (state formula), assuming `aa2UpgradeMci` is active:
```
$x = [1, 2, 3];
$f = ($v) => {
    delete($x, 2);   // mutates the very array `foreach` is iterating, since $x is captured by reference
    $v
};
$sum = 0;
foreach($x, 3, $f);
```
Because `$x` is the same object reference used as `res.obj`/`arrElements` inside the `foreach` handler at `formula/evaluation.js:2345-2469`, invoking `$f` during iteration can splice `$x` mid-loop, changing its length after the one-time `arrElements.length > count` check at `formula/evaluation.js:2372-2373` has already passed — producing an inconsistent element list/accumulator relative to what the declared `count` bound was supposed to guarantee.
