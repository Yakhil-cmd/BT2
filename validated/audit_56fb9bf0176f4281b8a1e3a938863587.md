### Title
Webhook signature verification selects the GitHub App/secret from an unauthenticated `repository.owner.login`/`organization.login` field while event handlers act on a different, unbound `repository.full_name` or global `sha`, allowing a valid holder of any configured org's webhook secret to forge events for arbitrary repositories/commits - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* GitHub App config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), both of which are fields taken straight from the unauthenticated request body. Once verification passes, the event handlers (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc.) resolve the target `Repository`/`Stack`/`Commit` from *other*, independent fields of the same body (`repository.full_name`, or in `StatusHandler`'s case a global, unscoped `Commit.where(sha: ...)` lookup). Nothing binds "the org whose secret validated this payload" to "the repository/commit the payload is allowed to mutate."

### Finding Description
In a Shipit deployment configured with multiple GitHub Apps (one per organization, as supported by `Shipit.github(organization:)` and demonstrated by the multi-org fixture `test/dummy/config/secrets_double_github_app.yml`), each org owner independently knows their own `webhook_secret` (they created their own GitHub App). [1](#0-0) [2](#0-1) 

The verification step chooses the signing secret using `repository_owner`, itself read from the raw, unverified JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`). Because HMAC verification is computed over the *entire* raw body with the secret chosen this way, an attacker who legitimately controls one configured org's App (Org A) can construct an arbitrary JSON payload, set `repository.owner.login` (or `organization.login`) to `"Org A"` so the correct/known secret is selected, and sign it correctly - while setting every *other* field of the payload (branch, `after` SHA, `repository.full_name`, `check_suite.head_sha`, or plain `sha`) to reference an unrelated target repository/commit belonging to a different org/stack entirely.

Once past `verify_signature`, the handlers never re-check that the resolved target belongs to the org that authenticated the request:

- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` independently of the org used for signing: [3](#0-2) 

- `PushHandler#process` uses that unrelated `repository.full_name` to look up any stack and force a resync with an attacker-chosen `after` SHA: [4](#0-3) 

- `StatusHandler#process` is even less scoped: it doesn't consult `repository` at all and updates the CI status of **any** commit in the entire database that matches an attacker-supplied `sha`, regardless of which stack/repo/org it belongs to: [5](#0-4) [6](#0-5) 

This breaks the intended trust binding "the org whose secret authenticated this webhook == the repository/commit this webhook is allowed to affect." The report's overflow bug is a different bug class (DOS via unbounded array + narrow index), but the underlying "verified-signature scope vs. actually-acted-upon field" mismatch pattern is directly analogous and is explicitly called out as in-scope.

### Impact Explanation
A `status` event is used by `Commit#create_status_from_github!` to set commit CI state, which feeds `Commit#deployable?` and thus `required_statuses`/`blocking_statuses` gating in `deploy_spec.rb`. Because `StatusHandler` resolves the target commit purely by `sha` with no repository/org scoping, an attacker who legitimately owns any one org's GitHub App webhook secret in a shared/multi-tenant Shipit instance can forge a `success` status for a specific commit SHA belonging to a completely different team's stack, potentially causing that commit to satisfy CI requirements and become eligible for an **unauthorized deploy** - matching the "Critical: unauthorized deploy" impact bucket. `PushHandler` similarly allows forcing a `GithubSyncJob`/resync against an arbitrary stack using a forged `after` SHA that the attacker doesn't control the actual git history of.

### Likelihood Explanation
Requires the attacker to already legitimately administer at least one GitHub App/org configured on the same Shipit instance (a real but common scenario for a shared/central Shipit deployment across many teams/orgs), and to know that org's own `webhook_secret` - something they inherently know as the creator/owner of their own GitHub App. No compromise of another org's credentials, no `ApiClient` token, and no repository write access to the *victim* repo is required. This is a realistic misuse of otherwise-legitimate, low-privilege access relative to the rest of the shared instance.

### Recommendation
1. After selecting the GitHub App/secret via `repository_owner`, re-validate that every subsequent field the handler acts upon (`repository.full_name`'s owner, `organization.login`, commit lookups) is actually owned by that same, verified organization - reject the payload otherwise.
2. Scope `StatusHandler`'s commit lookup by repository (join through `Repository`/`Stack` derived from the verified org) instead of a bare, cross-tenant `Commit.where(sha: params.sha)`.
3. Scope `Handler#stacks`/`repository_name` resolution to repositories owned by the organization that produced a valid signature, rejecting cross-organization mismatches explicitly.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (as supported per `test/dummy/config/secrets_double_github_app.yml`).
2. As the (legitimate) owner/admin of `OrgA`'s GitHub App, obtain `OrgA`'s `webhook_secret` (you created it).
3. Craft a JSON body for a `status` event:
```json
{
  "sha": "<victim-stack-commit-sha-in-OrgB>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and `X-Github-Event: status`, then `POST` to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app, and the signature verifies successfully.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` - matching the victim commit belonging to `OrgB`'s stack regardless of the authenticating org - and calls `create_status_from_github!`, marking that unrelated commit as `success`, which can unblock deploy checks for a stack the attacker has no legitimate access to.
