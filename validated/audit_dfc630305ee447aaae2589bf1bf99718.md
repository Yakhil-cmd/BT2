### Title
`handleERC721Transfer()` Uses Unsafe `transferFrom` Instead of `safeTransferFrom` When Delivering Bridged ERC721 Tokens — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer()` delivers bridged ERC721 tokens to the recipient using the unsafe `IERC721.transferFrom()` instead of `safeTransferFrom()`. If the recipient `_to` is a contract that does not implement `IERC721Receiver`, the token transfer will silently succeed but the NFT will be permanently locked in that contract. The source-chain token has already been burned or locked, so the loss is irreversible.

---

### Finding Description

In `BridgeTransferERC721.sol`, the `handleERC721Transfer()` function is called by bridge operators to deliver an ERC721 token on the destination chain after a cross-chain transfer request. In the non-mintBurn (liquidity) mode, it executes:

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

The standard ERC721 `transferFrom` does **not** invoke `onERC721Received` on the recipient and does **not** verify that the recipient contract implements `IERC721Receiver`. This means if `_to` is a contract without `IERC721Receiver` support (e.g., a multisig, DAO, or any arbitrary contract), the call succeeds, the token is transferred into that contract, and it becomes permanently inaccessible.

By contrast, `BridgeTransferERC20.handleERC20Transfer()` correctly uses the safe wrapper:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [2](#0-1) 

The asymmetry is clear: ERC20 bridge delivery uses `SafeERC20.safeTransfer`, while ERC721 bridge delivery uses bare `transferFrom`. The `SafeERC20` library itself confirms the intent — it wraps calls to revert on failure: [3](#0-2) 

The ERC721 standard's own documentation in the codebase states that `transferFrom` is the **discouraged** method and `safeTransferFrom` should be used whenever possible: [4](#0-3) 

The `safeTransferFrom` variant performs the `_checkOnERC721Received` callback and reverts if the recipient does not return the correct magic value: [5](#0-4) 

None of the guards in `handleERC721Transfer` — `_lowerHandleNonceCheck`, `_voteValueTransfer`, `_setHandledRequestTxHash`, `_updateHandleNonce` — check whether `_to` is capable of receiving ERC721 tokens: [6](#0-5) 

---

### Impact Explanation

When a user initiates a cross-chain ERC721 transfer to a contract address that does not implement `IERC721Receiver`:

1. On the source chain, the token is burned (mintBurn mode) or locked in the bridge (liquidity mode).
2. Bridge operators observe the `RequestValueTransferEncoded` event and call `handleERC721Transfer` on the destination chain.
3. The nonce is consumed and the handle event is emitted — the bridge considers the transfer complete.
4. `transferFrom(address(this), _to, _tokenId)` succeeds silently — the ERC721 token is now owned by `_to` but permanently inaccessible.
5. The source-chain token is already gone. The NFT is permanently lost.

This constitutes an **unauthorized permanent loss of a bridged asset** triggered by a valid user action with no privileged access required.

---

### Likelihood Explanation

The `_to` address is entirely user-controlled, supplied in the original `requestERC721Transfer` or `requestValueTransfer` call on the source chain: [7](#0-6) 

Any user who sends a cross-chain ERC721 to a contract address (e.g., a multisig wallet, a DAO treasury, a DeFi protocol, or any contract not implementing `IERC721Receiver`) will trigger this path. This is a realistic and common scenario — many contracts hold assets but do not implement `IERC721Receiver`.

---

### Recommendation

Replace the unsafe `transferFrom` call in `handleERC721Transfer` with `safeTransferFrom`:

```solidity
// Before (unsafe):
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After (safe):
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

This mirrors the safe pattern already used for ERC20 delivery in `handleERC20Transfer`.

---

### Proof of Concept

1. Deploy a contract `NoReceiver` that does **not** implement `IERC721Receiver`.
2. On the source chain, call `requestERC721Transfer(nftAddress, NoReceiver.address, tokenId, "0x")`.
3. Bridge operators observe the event and call `handleERC721Transfer(..., NoReceiver.address, ..., tokenId, ...)` on the destination chain (liquidity mode, bridge holds the token).
4. The transaction succeeds. `nft.ownerOf(tokenId)` returns `NoReceiver.address`.
5. The NFT cannot be recovered — `NoReceiver` has no function to call `transferFrom` or `safeTransferFrom`.
6. The source-chain token is already locked/burned. The NFT is permanently lost.

The existing test `expectReceiveERC721` in `contracts/test/Bridge/bridge.test.ts` only tests delivery to an EOA (`user2.address`) and does not cover contract recipients, leaving this path untested: [8](#0-7)
