### Title
AA-issued reward funds can be permanently frozen if the payout asset's `spender_attested` list revokes the recipient - ([File: aa_composer.js])

### Summary
The Sherlock finding describes an ERC20-blacklist freezing a hard-coded reward recipient's claim. Obyte's AA (Autonomous Agent) analog is an asset defined with `spender_attested: true` (or a `transfer_condition`) whose attestor list can change over time, combined with an AA that unconditionally pays a reward to `trigger.address`. If the recipient's attestation is later revoked ("blacklisted"), every future attempt by that user to claim the reward causes the AA's response unit to fail validation and bounce, while the reward balance stays trapped inside the AA forever with no way to redirect payment to another address.

### Finding Description
When an AA composes a payment message, it only checks `spender_attested` for its own address as issuer/author, not for the destination address, at composition time: [1](#0-0) 

The real enforcement happens later, when the freshly composed response unit is fully validated via `validateAndSaveUnit`, which runs the standard payment validator. There, for any asset payment, if `objAsset.spender_attested` is true, every output address must currently be in the attested-address set, otherwise validation fails with `"some output addresses are not attested"`: [2](#0-1) 

A `transfer_condition` (evaluated via `Definition.evaluateAssetCondition`) is checked the same way and can likewise depend on external, mutable state (e.g., an oracle/data feed flag), effectively acting as a "blacklist" switch that the asset definer or an attestor controls: [3](#0-2) 

If this validation fails, `sendUnit` calls `bounce(err)` instead of finishing successfully: [4](#0-3) 

`bounce()` reverts all AA state changes and, on failure paths where the trigger amount is below `bounce_fees` or no messages remain, does not send back any bytes at all — the value the user sent to trigger the reward is consumed with nothing returned, and the reward output itself is never produced: [5](#0-4) 

Because the AA typically hard-codes the payout to `trigger.address` (as in the reward/AA sample patterns seen throughout the test AAs, e.g. sending back to `trigger.address`), there is no equivalent of the `_to` parameter that would let the eligible user redirect the payout to an unaffected address: [6](#0-5) 

The attestor list itself is dynamic and can be updated after the AA/asset was created, via `asset_attestors` messages, and is resolved to the "latest" list at validation time: [7](#0-6) [8](#0-7) 

### Impact Explanation
A user who is otherwise entitled to a reward from an AA (e.g., an airdrop, ICO refund, or milestone-payout AA) can be permanently denied that reward if the reward asset uses `spender_attested` (or a `transfer_condition`) and the attestor later removes/never grants the attestation for that specific address. Every subsequent attempt to claim causes the AA's response to bounce, the AA's internal state/balance for that reward is never released to the user, and the funds remain stuck in the AA balance indefinitely since the AA logic offers no alternate destination address. This matches the "AA fund loss or freezing" impact category.

### Likelihood Explanation
This requires the AA's payout asset to have been defined with `spender_attested: true` or a `transfer_condition`, and for the attestor (which could be the same operator running the AA, or an unrelated but authorized attestor for that asset) to withhold/revoke attestation for a specific address. This is a realistic and common asset design pattern for compliance-oriented tokens on Obyte, and is entirely reachable by a normal, unprivileged AA trigger sender — the freeze occurs purely as a side effect of the AA's own payout logic combined with the asset's attestation state, with no wrongdoing required from the triggering user.

### Recommendation
- When designing/auditing AAs that issue rewards in assets with `spender_attested` or `transfer_condition`, avoid unconditionally hard-coding the payout address to `trigger.address`. Allow the state layer to remember that a reward is "owed" and let the trigger optionally specify an alternate recipient address (analogous to the `_to` parameter recommended in the original report), retrying the payment to a different, currently-eligible address instead of silently bouncing and losing the claim opportunity.
- Alternatively, if a payment bounces specifically due to `"some output addresses are not attested"` or `"transfer or issue condition not satisfied"`, have the AA keep the reward accounted for in state (not reset it) so that the user can re-trigger with a different destination address once available, rather than the value being effectively unrecoverable through the original flow.

### Proof of Concept
1. An AA defines an asset with `spender_attested: true` and specifies `attestors` (its own address, or a trusted third party) as in the "asset" message pattern used in AA samples, e.g. `test/samples/ico_with_milestones.oscript`.
2. The attestor issues an `attestation` for user address `A`, making `A` eligible.
3. User `A` triggers the AA; the AA's response pays out the reward asset to `trigger.address` (`A`), which succeeds because `A` is in `filterAttestedAddresses` result at that mci.
4. Before `A` claims a second/future tranche (or before the first successful claim, if the attestor changes the list), the attestor publishes a new `asset_attestors` list that excludes `A` (analogous to blacklisting).
5. `A` triggers the AA again for the (still-owed) reward. `sendUnit` composes a payment message to `A`; `validateAndSaveUnit` → `validatePaymentInputsAndOutputs` finds `A` is not in the current attested set and returns `"some output addresses are not attested"` (`validation.js:2637-2638`).
6. `sendUnit` calls `bounce(err)` (`aa_composer.js:1409-1410`), reverting AA state changes; the reward amount is never sent to `A`, and there is no mechanism in the AA to redirect it elsewhere, permanently freezing that portion of the AA's balance from `A`'s perspective.
