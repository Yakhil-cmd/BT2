## Title
Malicious secondary-AA payee can force full reversion of a primary AA's entire response chain, freezing distributions to all other (honest) recipients - (File: `aa_composer.js`)

### Summary
When a primary AA (triggered by any user's unit) sends payment outputs to multiple addresses in the same response, and one of those addresses happens to be another AA ("secondary trigger"), `handleTrigger` chains execution into that address via `handleSecondaryTriggers`. If that secondary AA bounces (deliberately, by design of a malicious/hostile AA definition — something anyone can permissionlessly post), the framework does not isolate the failure to that one branch. Instead it calls `revert()`, which performs `ROLLBACK TO SAVEPOINT initial_balances`, undoing **all** balance and state changes made by the primary trigger's entire response chain — including payments and state updates that already succeeded for other, unrelated, honest recipients in the same batch.

### Finding Description
`handleSecondaryTriggers` iterates the set of addresses that received outputs from the just-produced response unit and, for every address that is itself an AA, recursively calls `handleTrigger` with `bSecondary = true`: [1](#0-0) 

The iteration uses `async.eachSeries`, which stops on the first error. If any one of the secondary AAs bounces, the error propagates and — at the top (non-secondary) level — `revert()` is invoked for the *whole* primary-trigger execution, not just the failing branch: [2](#0-1) 

`revert()` clears every response produced so far in this trigger chain (`arrResponses.splice`), discards all pending state-var changes, and rolls the database back to the savepoint taken before the primary trigger began processing: [3](#0-2) 

This is functionally the same bug class as the reported NFTX `distribute()`/`_sendForReceiver` issue: a single "receiver" is allowed to unilaterally cause failure/denial of service for the whole payout operation. In fact ocore's implementation is *more* exposed than the referenced Solidity code — NFTX at least isolates the external call with a low-level `.call()` so a reverting receiver only causes its own share to be skipped/forwarded to the treasury (`leftover` logic), while `loops` over other receivers continue. ocore's `handleSecondaryTriggers`/`revert()` path has no analogous isolation: any bounce by a downstream AA unwinds everything the primary AA (and any of its already-successful secondary AAs) did for that trigger.

Since AA definitions can be posted by anyone, unprivileged (validated generically via `aa_validation.validateAADefinition`, `definition.js`), an attacker can freely deploy an "always bounce" AA. Many real-world AA patterns pay out to addresses that are supplied or influenced by users — e.g. registered beneficiaries/referrers/depositors, or arbitrary addresses forwarded from `trigger.data`/state vars, exactly like NFTX's user/DAO-configurable `feeReceivers` list. If any one recipient in a multi-recipient AA's payout batch is (or later becomes) such a malicious AA, every future trigger of that distributor AA that tries to pay it will bounce the malicious AA and, via `revert()`, wipe out payments/state updates to *all* other honest recipients processed in the same trigger, and it will keep doing so deterministically each time the AA is fired.

### Impact Explanation
This causes freezing/denial of processing of AA funds: a distributor-style AA that includes even one attacker-controlled malicious AA among its payees can be made to permanently fail to complete its distribution logic, since the same deterministic set of outputs (including the malicious one) will be recomputed and re-bounced on every trigger. Honest co-recipients in the same batch lose their payouts every time (rolled back), and the primary AA's state changes for that run are also discarded — this matches the "AA fund loss or freezing" impact category, going beyond the original medium-severity finding because ocore's revert scope is chain-wide rather than per-recipient.

### Likelihood Explanation
Exploitability depends on the target AA design allowing outputs to attacker-influenceable/attacker-registerable addresses (a common pattern for referral/beneficiary/distribution AAs, directly analogous to the DAO-configurable `feeReceivers` in the referenced report). Anyone can permissionlessly define and register an "always bounce" AA as such an address, since AA definitions require no privilege to post. This makes the likelihood medium: it requires a specific but common application pattern (multi-recipient AA payouts to user-influenced addresses) rather than a universal ocore-core flaw.

### Recommendation
Do not let a bounce by one secondary/chained AA unwind the successful branches/siblings and the primary AA's own already-committed state changes in the same trigger chain. Consider isolating each secondary-trigger branch (similar to NFTX's low-level `.call()` + `leftover` pattern): if a specific secondary AA bounces, only that branch's effects should be discarded (with its funds already protected by `bounce_fees`), while sibling branches and the primary AA's completed processing remain committed. At minimum, document this atomicity behavior prominently for AA authors and provide a supported pattern (e.g., explicit "send only to non-AA/verified addresses" guidance, or a mechanism to pre-check whether a destination is an AA that will accept funds) so that distributor-style AAs are not silently exposed to indefinite DOS by a single malicious payee.

### Proof of Concept
1. Attacker posts an "autonomous agent" definition `M` whose only message logic unconditionally calls `bounce(...)` (e.g., no valid `messages`, or an `if` that is always true leading to `bounce`).
2. Attacker gets address `M` registered as one of several payees in a victim distributor AA `D` (e.g., as a referrer/beneficiary/depositor address, mirroring how `feeReceivers` entries are added in the referenced NFTX report).
3. Someone triggers `D`. `D`'s response includes payment outputs to several legitimate addresses plus `M`.
4. `sendUnit` -> `handleSecondaryTriggers` fires a secondary trigger for `M` (`aa_composer.js:1702-1757`); `M` bounces.
5. `async.eachSeries`'s error handler calls `revert()` at the non-secondary level (`aa_composer.js:1749`, `1759-1783`), rolling back to `SAVEPOINT initial_balances` — discarding the payments/state updates that were already produced for the legitimate co-recipients and for `D`'s own state in this trigger.
6. As long as `M` remains in `D`'s payee set, every subsequent trigger of `D` reproduces the same outcome, permanently blocking `D`'s distribution logic. [4](#0-3) [3](#0-2)

		conn.query("SELECT address, definition, mci, main_chain_index FROM aa_addresses LEFT JOIN units USING(unit) WHERE address IN(?) AND mci<=? ORDER BY address", [arrOutputAddresses, mci], function (rows) {
			if (rows.length > 0 && constants.bTestnet && mci < testnetAAsDefinedByAAsAreActiveImmediatelyUpgradeMci)
				rows = rows.filter(function (row) {
					if (row.main_chain_index && row.main_chain_index < mci) // previous definition is already stable
						return true;
					var len = storage.getUnconfirmedAADefinitionsPostedByAAs([row.address]).length;
					if (len > 0)
						console.log("not calling secondary trigger from unit " + objUnit.unit + " to AA " + row.address);
					return (len === 0);
				});
			if (rows.length === 0) {
				saveStateVars();
				addUpdatedStateVarsIntoPrimaryResponse();
				return onDone(objUnit, bBouncing ? error_message : false);
			}
			if (bBouncing)
				throw Error("secondary triggers while bouncing");
			async.eachSeries(
				rows,
				function (row, cb) {
					var child_trigger = getTrigger(objUnit, row.address);
					child_trigger.initial_address = trigger.initial_address;
					child_trigger.initial_unit = trigger.initial_unit;
					if ("max_aa_responses" in trigger && mci >= constants.pemCurvesFixMci) // propagate the cap set on the primary trigger to secondary triggers
						child_trigger.max_aa_responses = trigger.max_aa_responses;
					var arrChildDefinition = JSON.parse(row.definition);

					var child_trigger_opts = { ...trigger_opts };
					child_trigger_opts.trigger = child_trigger;
					child_trigger_opts.params = {};
					child_trigger_opts.arrDefinition = arrChildDefinition;
					child_trigger_opts.address = row.address;
					child_trigger_opts.bSecondary = true;
					child_trigger_opts.onDone = function (objSecondaryUnit, bounce_message) {
						if (bounce_message)
							return cb(bounce_message);
						cb();
					};
					handleTrigger(child_trigger_opts);
				},
				function (err) {
					if (err) {
						// revert
						if (bSecondary)
							return bounce(err);

						return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
					}
					saveStateVars();
					addUpdatedStateVarsIntoPrimaryResponse();
					onDone(objUnit, bBouncing ? error_message : false);
				}
			);
		});
	}
