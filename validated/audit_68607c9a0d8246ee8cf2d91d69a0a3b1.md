### Title
Webhook signature verification authenticates the organization named in an unverified payload field, while handlers act on a different unverified payload field — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In Shipit's multi-organization GitHub App mode, the `/webhooks` endpoint is shared across all configured organizations. The signature check selects *which* organization's `webhook_secret` to validate against using `repository.owner.login` (or `organization.login`) pulled straight out of the unverified JSON body, but the handlers that actually act on the payload key their target `Repository`/`Stack` lookup off a completely different, also-unverified field: `repository.full_name`. Nothing ties these two payload fields together, so a valid HMAC computed with one organization's secret can be replayed with a `repository.full_name` pointing at a `Stack` belonging to a different, unrelated organization.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to pick the verification secret entirely from the request body itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp`/secret for that organization key [3](#0-2) , and `Shipit.github_app_config` resolves it purely from `secrets.github` keyed by organization name [4](#0-3) .

Once the HMAC passes, the controller dispatches the *entire, unverified* JSON body to the registered handler for the event: [5](#0-4) 

The handler base class, however, resolves the target `Repository`/`Stack` using a **different** field of the same payload — `repository.full_name` — with no cross-check against the `repository.owner.login`/`organization.login` value that was used to select the verifying secret: [6](#0-5) 

`PushHandler`, for example, uses this `stacks` lookup to trigger `stack.sync_github` for any stack matching the branch in `repository.full_name`: [7](#0-6) 

The binding that is broken is: **organization that authenticated (`repository.owner.login` validated against that org's `webhook_secret`) ≠ repository that is written/acted upon (`repository.full_name` used for `Repository.from_github_repo_name`)**. Because Shipit supports multiple independently configured GitHub organizations sharing one `/webhooks` endpoint [8](#0-7) , any party who possesses (or can produce) a valid signature for *any one* configured organization's `webhook_secret` can craft a POST whose `repository.owner.login`/`organization.login` matches that organization (so it passes `verify_signature`), while setting `repository.full_name` to `some-other-org/some-other-repo` to drive handler logic against a stack that belongs to an organization they have no relationship to.

### Impact Explanation
This allows an attacker who has legitimate access to one low-trust organization's webhook configuration (or who has otherwise obtained that organization's `webhook_secret`) to forge events processed as if they came from a completely different, higher-trust organization's repository — an unauthorized cross-repository/cross-organization action. Depending on which handler is targeted this can force `GithubSyncJob` runs against foreign stacks (`push`), or drive other registered handlers (`status`, `pull_request`, `check_suite`, `membership`) against repositories/stacks outside the authenticating organization's trust boundary, since none of these handlers re-validate that the acted-upon repository belongs to the organization whose secret produced the signature.

### Likelihood Explanation
Exploitation requires possession of a `webhook_secret` for at least one organization configured in `secrets.github` (`config/secrets.yml`) — plausible in real deployments where multiple GitHub orgs, potentially with different trust levels/admins, share a single Shipit instance, as explicitly documented in "Using Multiple Github Applications." Anyone able to configure/read that org's webhook settings can compute a valid signature and target any other configured stack purely by changing the `repository.full_name` field of the JSON body they send to the shared `/webhooks` endpoint.

### Recommendation
After `verify_signature` succeeds, enforce that the resolved `repository_owner` (used to select the signing secret) matches the owner segment of `repository.full_name` (and any other repository/org identifiers used later by handlers) before dispatching to `Shipit::Webhooks.for_event`. Reject the webhook if these fields disagree.

### Proof of Concept
1. In a multi-org Shipit deployment, obtain (as an authorized admin/member) `orgA`'s `webhook_secret`.
2. Compute `signature = sha1_hmac(orgA_webhook_secret, body)` for a body such as:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": {"login": "orgA"},
    "full_name": "orgB/private-repo"
  }
}
```
3. POST to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<signature>`.
4. `verify_signature` looks up `Shipit.github(organization: "orgA")` (from `repository.owner.login`) and validates the HMAC successfully.
5. `PushHandler` then resolves `Repository.from_github_repo_name("orgB/private-repo")` and calls `stack.sync_github` for stacks under `orgB`, even though the request was never authenticated by `orgB`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
