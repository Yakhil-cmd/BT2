### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to update purely by `sha`, with no scoping to the repository that sent the webhook. Since a `sha` can legitimately exist on more than one repository/stack (forks, shared history, or shared commits pushed by different remotes), a validly-signed `status` webhook from repository A can mutate the `Status` of a same-sha commit belonging to an unrelated `victim_stack` tracking a different repository, and that corruption is then visible via `Shipit::Commit#deployable?` and `Shipit::UndeployedCommit#deploy_state` read paths (`stacks_controller#show`, `Api::UndeployedCommitsController`, `stacks_helper.rb`).

### Finding Description
Binding that should hold: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Status` row written as a result of a webhook. This binding is never checked.

Code path:
- `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches to `Shipit::Webhooks.for_event('status') => [Handlers::StatusHandler]` and calls `handler.call(params)`.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-38`) only verifies the HMAC against the `webhook_secret` configured for `repository_owner` (derived from the payload's own `repository.owner.login`). This proves the payload came from *some* GitHub organization/repo that Shipit trusts (the attacker's own repo, if they can trigger a real webhook there, e.g., by pushing a commit status via GitHub's Status API on a repository they own that has the Shipit GitHub App installed), but it says nothing about *which stack's commits* the payload is allowed to mutate.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This performs a global `Commit` lookup by `sha` only — no `stack_id`, no repository/organization filter — and mutates every matching commit across every stack/tenant. Contrast with `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which correctly scopes to `stacks...where(branch:)`, where `stacks` is repository-scoped by the `Handler` base class. `StatusHandler` has no equivalent scoping.
- `Commit#create_status_from_github!` → `Commit#add_status` → `statuses.replicate_from_github!` writes a `Status` row tied to `commit.stack_id`, changing `commit.state`/`commit.status`, which feeds directly into `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) and `UndeployedCommit#deploy_state` (`app/models/shipit/undeployed_commit.rb:18-31`).
- An unprivileged attacker who owns/administers *any* repository that has the Shipit GitHub App/webhook installed (their own fork or an unrelated repo in an organization already integrated with this Shipit instance) can trigger a real, validly-signed `status` event whose `sha` happens to also identify a commit tracked by `victim_stack` (fork-shared history, cherry-picked/rebased-identical commit, or a commit merged into both repos). That single legitimate webhook mutates `victim_stack`'s `Commit`'s `Status`, and subsequently `deployable?`/`deploy_state` on the victim stack report the attacker-controlled state (e.g., forged `success`) to the victim's own operator via the dashboard or `Api::UndeployedCommitsController`.
- None of the existing guards catch this: `verify_signature` authenticates the *sender org*, not the *target stack*; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` validates payload shape, not repository ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
A payload authenticated for one repository can write a `Status` record for another repository's stack/commit — this is a "payload for one repository mutating another's stack/commit" (Critical per the rules). The corrupted `deploy_state`/`deployable?` result is surfaced to the legitimate victim-stack operator through the dashboard (`stacks_controller#show`) and the API (`Api::UndeployedCommitsController`), and can cause them to manually trigger `stack.trigger_deploy` on a commit whose actual CI outcome was never verified for that stack, or believe a real failure is masked as success (or vice versa: an attacker could suppress a legitimate `success` by pushing a colliding `failure`/`error`, blocking the victim's deploy pipeline). This is repeatable against any stack/repository pair with a shared/colliding sha, and blast radius spans every tenant stack tracked by the same Shipit installation, since the lookup is entirely global.

### Likelihood Explanation
Preconditions: the attacker needs write access to at least one repository already integrated with the target Shipit instance (i.e., its org/app installation issues real, validly-signed webhooks), and a `sha` that is also tracked as a `Commit` under `victim_stack` — realistic via forks sharing history, shared upstream commits, or cherry-picks that preserve sha. No secrets, sessions, or special roles are required; the attacker only needs GitHub write access to their own repo and to cause GitHub to emit a real `status` webhook (e.g. by using a CI integration or the Status API on their own commit). This is a low-cost, repeatable attack limited only by the ability to find or engineer a colliding sha across repos in the same Shipit deployment.

### Recommendation
Scope `StatusHandler#process` to the repository asserted by the webhook payload, mirroring `PushHandler`: resolve the target stacks via `stacks.where(...)` filtered on the payload's `repository.full_name`/owner, then only touch commits belonging to those stacks' `stack_id`s, e.g.:
```ruby
def process
  Commit.joins(:stack).merge(stacks).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
where `stacks` is the `Handler`-provided repository-scoped stacks relation (as already used by `PushHandler`).

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new `status_handler_test.rb`):
```ruby
test ":status webhook from repository A must not mutate a same-sha commit belonging to repository B's stack" do
  attacker_stack = shipit_stacks(:shipit) # tracks "shopify/shipit-engine"
  victim_stack   = shipit_stacks(:cyclimse) # different repository/full_name

  shared_sha = "deadbeefcafebabefeedfacefeedfacefeedface"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")

  before_state = victim_commit.reload.state
  refute_equal 'success', before_state

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'
  payload = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_stack.repo_name, 'owner' => { 'login' => attacker_stack.repo_owner } }
  }.to_json

  post :create, body: payload, as: :json

  # Binding under test: victim_commit's deploy_state must reflect only inputs authorized for victim_stack.
  after_state = UndeployedCommit.new(victim_commit.reload, index: 0).deploy_state
  assert_equal before_state, victim_commit.state, "attacker-controlled webhook mutated an unrelated stack's commit"
  refute_equal 'allowed', after_state
end
```
This asserts both sides of the binding — `victim_commit.state`/`deploy_state` before and after the forged cross-repo webhook — and fails on current code because `StatusHandler` updates the commit regardless of which repository the webhook claims to be from.
