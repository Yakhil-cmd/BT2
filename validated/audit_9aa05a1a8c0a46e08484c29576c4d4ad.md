### Title
Webhook signature organization is derived from a different, unvalidated JSON field than the repository used for stack creation, allowing cross-tenant PR webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), while `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#repository` independently resolves the target `Shipit::Repository` from `params.repository.full_name`. Both fields live in the same attacker-controlled, unsigned JSON body with no cross-field validation tying them together, so an attacker who controls a legitimately configured `attacker-org` webhook secret can sign a payload whose `repository.owner.login` says `attacker-org` (satisfying `verify_signature`) but whose `repository.full_name` says `shopify/shipit-engine` (used to create/mutate a stack under a different tenant).

### Finding Description
The broken binding, stated as an equality that the code must (but does not) enforce:
`repository_owner` (used in `Shipit.github(organization: repository_owner)` for signature verification) `== owner-derived-from(params.repository.full_name)` (used in `Shipit::Repository.from_github_repo_name(params.repository.full_name)`).

Trace:
- `app/controllers/shipit/webhooks_controller.rb:24-30,59-62` computes `repository_owner` from `params.dig('repository','owner','login')` (fallback `params.dig('organization','login')`), then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [1](#0-0) [2](#0-1) .
- `GitHubApp#verify_webhook_signature` only checks the HMAC over the raw body against the secret configured for that one organization; it performs no check that the payload's other fields (e.g. `repository.full_name`) belong to that organization [3](#0-2) .
- Once signature passes, `Shipit::Webhooks.for_event('pull_request')` dispatches to `OpenedHandler#process`, which resolves the target repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [4](#0-3) , and never consults `repository.owner.login` or compares it to the signature-verifying organization.
- `Repository.from_github_repo_name` simply splits `owner/name` out of the string and does a DB lookup, with no relation to the verified organization [5](#0-4) .
- `ReviewStackAdapter#find_or_create!`/`create!` then creates a `ReviewStack`/`PullRequest` scoped to that (attacker-named) `Repository`'s `review_stacks` association [6](#0-5) , and `PullRequest#github_pull_request=` subsequently calls `stack.github_api.commit(...)` / `stack.commits.create_from_github!` using the **target stack's own** GitHub App token (i.e. the victim org's token, resolved via `Stack belongs_to :repository` → `Repository#github_app` → `Shipit.github(organization: owner)`), not the attacker's [7](#0-6) [8](#0-7) .

Root cause: two independent trust decisions ("who signed this?" vs. "which repo/tenant does this apply to?") are each read from separate, attacker-controlled JSON fields in the same unsigned body, with no assertion that they agree. `params dig('repository','owner','login')` and `params.repository.full_name` can be set to arbitrary, unrelated strings by whoever crafts the JSON payload before signing it with their own known secret.

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature: sha1=<HMAC(attacker-org secret, raw_body)>`, and JSON body containing `{"action":"opened","repository":{"owner":{"login":"attacker-org"},"full_name":"shopify/shipit-engine"},"pull_request":{...attacker-controlled...}}`. `verify_signature` picks `Shipit.github(organization: "attacker-org")`, validates successfully against the attacker's own known secret, and the request proceeds to `OpenedHandler`, which creates/mutates a `ReviewStack`/`PullRequest`/`Commit` under `shopify/shipit-engine`'s `Repository`, using `shopify`'s GitHub App token to fetch commit data referenced in the forged payload.

Existing guards do not stop this: `verify_signature` only checks HMAC validity for whichever org name the attacker put in the payload; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema only enforces types/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`; there is no `force_github_authentication`, `User#authorized?`, or `Shipit.github_teams` check on this unauthenticated webhook path.

### Impact Explanation
A successful request lets an attacker who legitimately controls one tenant's webhook secret (`attacker-org`) create arbitrary `Shipit::ReviewStack`/`Shipit::PullRequest`/`Shipit::Commit` records scoped to a completely different tenant's repository (e.g. `shopify/shipit-engine`), and cause that victim tenant's own GitHub App token to be used server-side to fetch commit data referenced in the forged payload (`stack.github_api.commit(...)`). This is a cross-tenant webhook forgery / authentication-bypass class issue matching the stated Critical category ("forged webhook accepted" and "a payload for one repository mutating another's stack, commit, task"). It is repeatable against any repository configured in Shipit as long as the attacker can send a correctly HMAC-signed body under their own org's secret, and the blast radius spans every tenant/org onboarded to the same multi-org Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment where the attacker legitimately owns/administers a GitHub App installation on their own org that is configured in Shipit (`github_app_config`), thus knowing that org's `webhook_secret`; (2) the target repository (e.g. `shopify/shipit-engine`) already exists as a `Shipit::Repository` record with `review_stacks_enabled` and an appropriate `provisioning_behavior`. Given those preconditions—explicitly permitted under the attacker model ("owns a webhook_secret-bearing GitHub App installation on their own org")—the attack cost is a single crafted HTTP POST with a correctly computed HMAC over attacker-chosen bytes, fully repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, derive the organization strictly from `repository.full_name` (not from `repository.owner.login`/`organization.login`) and require that the organization whose secret validated the signature matches the owner encoded in `repository.full_name` (and any other repository-identifying field used downstream). Reject the request (422) if they diverge. Alternatively, have each handler (e.g. `OpenedHandler`) receive/assert the verified organization from the controller and check it against `Repository#owner` before creating or mutating any record.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "pull_request opened webhook signed by attacker-org but naming shopify repo is rejected" do
  attacker_secret = Shipit.github(organization: 'attacker-org').send(:webhook_secret) # known to attacker as org owner
  shopify_repo = shipit_repositories(:shipit) # owner: 'shopify', name: 'shipit-engine'
  shopify_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  payload = JSON.parse(payload(:pull_request_opened))
  payload['repository']['owner'] = { 'login' => 'attacker-org' } # signing org
  payload['repository']['full_name'] = 'shopify/shipit-engine'   # target org (mismatch)
  body = payload.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = signature

  # Binding under test: repository_owner used for signature ('attacker-org')
  # must equal the owner encoded in repository.full_name ('shopify') for the
  # request to be allowed to mutate shopify's ReviewStack. They diverge here.
  repository_owner = payload.dig('repository', 'owner', 'login')          # 'attacker-org'
  full_name_owner  = payload.dig('repository', 'full_name').split('/').first # 'shopify'
  assert_not_equal repository_owner, full_name_owner

  assert_no_difference -> { Shipit::ReviewStack.count } do
    post :create, body:, as: :json
  end
  assert_response :unprocessable_entity # expected fix; currently returns :ok and creates the ReviewStack
end
```
This test currently fails against unfixed code (the `ReviewStack` gets created and the response is `:ok`), demonstrating the divergence is not caught.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
