## Confirmed analog: `WebhooksController` verifies the signature against the organization named in `repository.owner.login`, but every handler dispatches on the independently-attacker-controlled `repository.full_name` field

### Title
Webhook signing-organization/repository-of-record mismatch allows cross-repository status and team-membership forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository_owner`, which is taken straight from the untrusted JSON body (`params.dig('repository','owner','login')` or `organization.login`). Every event handler (`Handler#repository_name`, used by `PushHandler`, and the `sha`-based lookup in `StatusHandler`) instead resolves the repository/commit to act on from a *different* field of the same payload (`repository.full_name`, or a bare `sha` with no repository scoping at all). Because the attacker controls the entire raw POST body before it is signed, they can pick which org's secret is used to authenticate the request while independently choosing which repository/commit the effect lands on.

### Finding Description
The verified binding should be: `organization_whose_secret_signed_the_request == organization_that_owns_the_repository_being_mutated`. The code breaks this equality:

- Signature verification: `Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) 

- The generic handler base class resolves the repository to operate on from a completely separate field, `repository.full_name`: [2](#0-1) 

- `StatusHandler` doesn't even scope by repository — it looks up `Commit.where(sha: params.sha)` globally across the entire installation and writes a `commit_status` from attacker-supplied `state`/`description`/`target_url`/`context`: [3](#0-2) 

- `MembershipHandler` similarly trusts `organization.login` from the body to tag/create `Team` records and add/remove members, independent of which secret validated the request: [4](#0-3) 

Because the HMAC signature covers the raw bytes of the whole JSON body that the attacker constructs, the attacker never needs to "tamper" with an otherwise-legit GitHub payload — they build the payload themselves, set `repository.owner.login` (or `organization.login`) to an organization for which they legitimately hold a configured webhook secret (e.g., their own org in a multi-org `Shipit.github` config, per `config/secrets.development.example.yml`), sign it correctly, and set `repository.full_name` (or `sha`) to target a completely different, victim-owned repository/commit tracked by the same Shipit instance.

Before the change (intended model): a valid signature for org A implies the payload only affects repositories that belong to org A, because GitHub itself only emits payloads where `owner.login` and `full_name`'s owner segment agree.
After: Shipit's own webhook endpoint accepts self-authored payloads where these two fields can diverge, since nothing re-checks that `repository.full_name`'s owner matches `repository_owner` used for signing.

### Impact Explanation
- `StatusHandler` lets the attacker forge `commit_status` rows for **any** commit sha tracked by the Shipit instance (no repository scoping at all), potentially causing Shipit to consider commits deployable/blocked incorrectly and influencing `release_status` checks that gate deploys — an unauthorized-deploy vector.
- `PushHandler`/`Handler#stacks` lets the attacker trigger `sync_github` for any tracked stack whose repository full_name they choose, regardless of which org's secret signed the request.
- `MembershipHandler` lets an attacker who owns/administers webhook credentials for organization A add or remove `Shipit::Team` memberships tied to organization B's `login` string (teams are looked up/created by `github_id`, and membership grants influence `Shipit.github_teams` authorization checked in `Authentication#force_github_authentication` and `User#authorized?`), which is a path toward escalation into `Shipit.github_teams` authorization — a listed High-severity impact.

### Likelihood Explanation
Requires the attacker to control (or have installed) a GitHub App/webhook secret for at least one organization configured in the multi-org `Shipit.github` config (a realistic scenario for any organization that lets outside teams register their own repos/orgs against a shared Shipit instance, as the multi-org config format in `config/secrets.development.example.yml` supports). Once in possession of one valid secret, exploitation is a single crafted HTTP POST to the public `/webhooks` endpoint — no additional privileges, session, or `ApiClient` token needed.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, after signature verification, re-derive the repository/organization actually targeted by the payload (`repository.full_name`'s owner segment, or the resolved `Stack`/`Team`/`Commit`'s associated `Repository#owner`) and assert it equals `repository_owner` (the organization whose secret validated the signature) before dispatching to handlers. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Shipit is configured with `Shipit.github` containing at least two organizations, e.g. `attacker-org` (attacker holds/administers this GitHub App and therefore knows or can derive its `webhook_secret`) and `victim-org` (tracked stacks/commits belong here).
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha, e.g. currently pending>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit purely by sha (no org check) — and calls `create_status_from_github!`, writing a forged `success` status for `victim-org`'s commit, potentially unblocking a deploy gate that depends on that check.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

        "status=#{status}"
      ].join(' '))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
