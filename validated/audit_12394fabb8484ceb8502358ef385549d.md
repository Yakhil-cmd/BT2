### Title
Webhook Signature Bypass via Attacker-Controlled Organization Selection Enables Forged Cross-Repository Events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using a field taken directly from the unauthenticated request body, and `GitHubApp#verify_webhook_signature` trivially returns `true` when that organization has no `webhook_secret` configured. This lets an unauthenticated attacker forge a webhook payload that "authenticates" against an organization with a blank secret while carrying a `repository` payload for a completely different, legitimately-secured repository/stack, breaking the binding between the organization that authenticated and the repository that is actually written.

### Finding Description
`WebhooksController#verify_signature` picks the verifying `GitHubApp` using a value derived entirely from the untrusted JSON payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read via `params.dig('repository', 'owner', 'login')` (or the `organization` sub-object), both of which are attacker-supplied JSON fields, and this happens before any signature check occurs.

`Shipit.github(organization: repository_owner)` looks up the configured `GitHubApp` instance for that org, and `verify_webhook_signature` is defined as: [3](#0-2) 

Critically, `return true unless webhook_secret` means that if the organization resolved from the attacker-controlled field has no `webhook_secret` configured, signature verification is bypassed unconditionally — regardless of what signature header (if any) is sent. Shipit's own documented configuration explicitly allows a `webhook_secret` to be left blank per organization: [4](#0-3) 

Once `verify_signature` passes (trivially, because of the blank-secret org), `WebhooksController#create` dispatches the event to registered handlers using the full, attacker-controlled JSON body: [5](#0-4) 

Handlers (e.g. `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, the `pull_request/*` handlers) look up the target `Repository`/`Stack` from the `repository.full_name` (or similar) field of that same payload — a field that is never cross-checked against the organization that was actually used to pass the signature check. Because the organization used for the trivially-passing signature check (`repository.owner.login`) is a completely separate field from the repository identity acted upon by the handlers (`repository.full_name`), an attacker can set `repository.owner.login` to the blank-secret organization while setting the rest of the `repository` payload (owner/name used for the actual DB lookup) to any other repository/stack configured in the Shipit instance, including ones belonging to organizations that do have a real, secret-protected webhook configuration.

This is exactly the "organization that authenticated versus the repository that is written" trust binding: the equality `organization_used_for_signature == organization_owning_the_repository_being_mutated` does not hold, and the engine never enforces it.

### Impact Explanation
This is an authentication-bypass primitive for GitHub webhook processing: any unauthenticated network attacker who knows (or can guess/enumerate) the login of one blank-secret-configured organization in a multi-org Shipit deployment can forge arbitrary webhook events (push, status, check_suite, pull_request, membership, etc.) that reference any other repository/stack tracked by that Shipit instance. Depending on which handler is targeted this can be used to: inject fake commit statuses that unblock the merge queue, spoof `pull_request`/`check_suite` events driving review-stack provisioning, or trigger `GithubSyncJob`s — all without possessing any Shipit session, API token, or the target repository's actual webhook secret. This matches the Critical/High impact bar (authentication bypass leading to unauthorized manipulation of stack/deploy state).

### Likelihood Explanation
Exploitability depends on a specific but explicitly-supported deployment configuration: at least one organization entry in `Shipit.github` config with no `webhook_secret` set. This is not a hypothetical misconfiguration — the shipped example secrets file (`config/secrets.development.shopify.yml`) and `docs/setup.md` both treat `webhook_secret` as optional ("If you've set a webhook secret ... you should copy it here"), so multi-org installations that forget or intentionally skip setting a secret for one org are directly exposed. No credentials, sessions, or repository write access are required to exploit it — only knowledge of the blank-secret org's login and the target repository's `full_name`.

### Recommendation
Do not allow "no secret configured" to silently mean "trust unconditionally." Options:
- Require `webhook_secret` to be present for every configured organization at boot (fail-fast if missing), or
- If a blank secret is explicitly desired, still verify that the organization derived for verification purposes matches the organization that owns the repository referenced in the payload for the specific event before handlers act on it, or
- At minimum, tie the resolved `github_app`/organization used for verification to a subsequent authorization check that the acted-upon `repository.full_name` actually belongs to that same organization/installation before any handler mutates state.

### Proof of Concept
1. Configure Shipit with two orgs: `secure-org` (real `webhook_secret`) owning stack `secure-org/prod-app`, and `blank-org` (no `webhook_secret` set).
2. Send `POST /webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` header, and body:
```json
{
  "repository": {
    "owner": { "login": "blank-org" },
    "full_name": "secure-org/prod-app",
    "name": "prod-app"
  },
  "after": "<attacker-chosen sha>",
  "ref": "refs/heads/main"
}
```
3. `repository_owner` resolves to `blank-org`; `Shipit.github(organization: 'blank-org').verify_webhook_signature` returns `true` unconditionally because `blank-org` has no `webhook_secret`.
4. `PushHandler` processes the event using `repository.full_name` = `secure-org/prod-app`, enqueueing a `GithubSyncJob`/updating commit/status state for the `secure-org` stack — despite the request never being signed by `secure-org`'s (or any) real webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
