### Title
Unsanitized Peer-Controlled Contract Title/Status Injected into Trusted Chat "text" Stream Bypasses Tag-Stripping Filter - (File: wallet.js)

### Summary
`wallet.js` treats the `"text"` event stream as a channel that must have specific control tags (`(prosaic-contract:...)`, `(arbiter-contract-offer:...)`, `(arbiter-contract-event:...)`, `(arbiter-dispute:...)`) stripped out before being handed to the UI, because the wallet GUI treats these bracketed tags as trusted markers that trigger rich, actionable rendering (contract/dispute cards with Accept/Decline buttons wired to real signing flows). However, this stripping is only applied on the raw incoming `"text"` device-message path. Other code paths that synthesize `"text"` events from peer-supplied data (e.g., the contract `title` field echoed back in a `prosaic_contract_response` status message) emit directly to `eventBus.emit("text", ...)` without ever passing through the same sanitizer, so an attacker can embed one of the four tag formats inside `objContract.title` and have it delivered to the victim's UI as if it were a trusted system-generated tag.

### Finding Description
In `wallet.js`, the `case "text":` handler for message subject `"text"` explicitly strips the four privileged tag patterns before emitting to the UI event bus: [1](#0-0) 
This confirms the wallet core considers these bracketed, base64-payload tags to be a privileged, UI-interpretable syntax that must never reach the renderer unsanitized when it originates from arbitrary peer chat text.

Contrast this with the `prosaic_contract_offer` and `prosaic_contract_response` handlers. The offer handler validates structural fields (hash, addresses, date format) but does not restrict the *content* of `title`/`text` (they are free-form strings up to 1000/unbounded chars per schema): [2](#0-1) 
The response handler then re-emits a `"text"` event built directly from the stored, peer-controlled `objContract.title`, with no equivalent stripping of the four tag patterns: [3](#0-2) 

Because `objContract.title` was supplied by the remote peer in the original `prosaic_contract_offer` message and is only checked for non-emptiness and a matching hash (computed over attacker-chosen title/text/date, see `prosaic_contract.getHash`), an attacker can set `title` to a string containing, e.g., `(prosaic-contract:<attacker-base64-JSON>)`. When the contract is later accepted/declined and the wallet emits `contract "<title>" accepted`, the injected tag flows straight into the trusted `"text"` event stream — the same stream that is normally sanitized specifically to prevent this class of tag injection.

This is structurally analogous to the reported Angular Language Service issue: a downstream renderer (`client.ts`/the wallet GUI) treats certain content it receives as fully trusted/interpretable (there `isTrusted: true` Markdown with `command:` URIs; here bracketed contract/dispute tags that spawn actionable UI), while the upstream producer (`server/src/handlers/hover.ts` / here `wallet.js`) fails to consistently escape/strip the special syntax before it reaches that trusted sink — in one path it does sanitize (the raw `"text"` subject handler), but in a sibling path building synthetic text from attacker-influenced fields it does not.

### Impact Explanation
If the wallet UI (outside ocore, in the GUI layer) parses these tags out of `"text"` events to render interactive contract/dispute cards (as the existence of the dedicated stripping logic implies), a successful injection lets a malicious contract counterparty display a forged contract/dispute UI element to the victim under the guise of an innocuous status update. Depending on how the GUI resolves the tag payload (e.g., re-fetching by hash vs. trusting embedded fields), this could mislead the user into approving a shared-address contract or arbiter dispute they did not actually agree to, resulting in unauthorized fund commitment/loss through the normal wallet contract-acceptance flow. This satisfies the "AA/contract fund loss" bar since prosaic/arbiter contracts drive shared-address definitions and payment authorization within ocore.

### Likelihood Explanation
The trigger is reachable by any paired device counterparty that legitimately negotiates a prosaic contract with the victim (a normal wallet interaction) — no special privileges beyond being a correspondent are required, matching the "AA trigger sender / private-payment counterparty" reachability the scope permits. The only precondition is choosing a `title` string that embeds one of the four bracket patterns, which passes all existing validation in the `prosaic_contract_offer` handler.

### Recommendation
Apply the same tag-stripping regex used in the `case "text":` handler to any peer-supplied string (`title`, `text`, or other free-form fields) before it is ever passed to `eventBus.emit("text", ...)`, regardless of which code path constructs the message. Centralize this sanitization in a single helper function used by every emitter of `"text"` events, and additionally consider rejecting/escaping any occurrence of the tag-marker patterns at contract-offer validation time rather than relying on stripping later.

### Proof of Concept
1. Attacker pairs with victim's wallet and sends a `prosaic_contract_offer` message where `title` = `` contract (prosaic-contract:BASE64_OF_ATTACKER_JSON) `` and `text`/`creation_date`/`hash` are crafted to satisfy `prosaic_contract.getHash` validation in: [4](#0-3) 
2. Victim's wallet stores the offer via `prosaic_contract.store(body)` and, at some point, the contract is accepted or declined (by either party), triggering the `prosaic_contract_response` handler.
3. The handler emits: [5](#0-4) 
embedding the attacker's crafted `(prosaic-contract:...)` tag verbatim into the `"text"` event, without the sanitization applied at: [6](#0-5) 
4. The wallet GUI's chat renderer, which is designed to trust these tags only from the sanitized `"text"` path, parses and renders the injected tag as an actionable contract/dispute UI element.

Note: Full confirmation of end-user impact (i.e., exactly how the GUI renders/acts on these tags) requires the wallet GUI source, which is outside this ocore repository and not indexed here; this analysis is based on the sanitization logic and data flow present in `wallet.js` itself.
