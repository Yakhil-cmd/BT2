This confirms the vulnerability. The `Handler` base class provides a `stacks` helper method that scopes lookups via `Repository.from_github_repo_name(repository_name)&.stacks`, tying results to the payload's `repository.full_name` [1](#0-0) . `CheckSuiteHandler` correctly uses this scoped `stacks` method before matching commits by sha [2](#0-1) . However, `StatusHandler#process` bypasses this scoping entirely and queries the global `Commit` table directly by `sha` alone: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .

### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits globally by `sha` without scoping to the webhook's originating repository/stack, unlike sibling handlers (e.g. `CheckSuiteHandler`) that scope via `Repository.from_github_repo_name`. Because `sha` is not unique across the `commits` table (only unique per `stack_id, sha` per the DB index), a legitimately-signed status webhook from org A can mutate a `Shipit::Commit` belonging to org B's stack if both commits share the same sha.

### Finding Description
The broken binding: `webhook_secret(org A) == tenant_boundary(Commit belonging to stack in org A's repository)` is expected, but the actual code enforces only `webhook_secret(org A) == signature_valid`, with no join back to `repository_owner`/`repository.full_name` when resolving which `Commit` rows to mutate.

Code path: `WebhooksController#create` verifies the HMAC signature using `Shipit.github(organization: repository_owner).verify_webhook_signature` [4](#0-3) , which correctly authenticates that the payload came from GitHub for org A (using org A's real `webhook_secret`, unknown to the attacker). It then dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) . The signature check only proves the payload originated from GitHub for org A's repository — it says nothing about which `Commit` rows the handler may touch. `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no `repository`/`stack` scoping at all [3](#0-2) . The `commits` table's uniqueness constraint is `(sha, stack_id)`, not `sha` alone [6](#0-5) , so the same sha legitimately exists once per stack, and nothing prevents two unrelated repositories/stacks from containing a commit with an identical sha (e.g., two independent empty commits with identical tree/parent/author/committer/timestamp).

Attacker flow: the attacker owns/administers a repository under org A that is legitimately configured as a Shipit-tracked stack (this is normal Shipit usage — the attacker is only privileged over their own repo/org, not org B). They craft an empty commit (`git commit --allow-empty -m ''`) on their own branch/repo such that its sha collides with a commit sha that already exists in org B's stack (attacker can observe org B's public commit shas and reverse-engineer matching empty-commit parameters, or more practically, engineer their own repo's history to intentionally reuse a target sha they already know from org B's public repo). They then trigger (via their own CI, GitHub Actions, or a manual `POST /repos/:owner/:repo/statuses/:sha` GitHub API call — using their own token/App on their own repo, entirely within their own repo permissions) a real `status` webhook from GitHub for org A's repository, referencing that colliding sha. GitHub signs this webhook with org A's genuine `webhook_secret`, which `verify_signature` accepts since it correctly matches org A. `StatusHandler#process` then finds *every* `Commit` row across *all* stacks/tenants whose `sha` matches — including org B's commit — and calls `create_status_from_github!` on it, mutating org B's commit status, potentially flipping `deployable?`/CI gating state for org B's stack, all without ever presenting any credential belonging to org B.

Existing guards fail here specifically because: `verify_signature` validates repository ownership of the *signature*, not of the *record being mutated*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate `state`/`sha` presence and type, not repository identity; and unlike `CheckSuiteHandler`, `StatusHandler` never calls the `stacks` helper that would scope to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [1](#0-0) .

### Impact Explanation
A payload authenticated only for org A's repository mutates a `Shipit::Commit`/its `statuses` collection belonging to org B's stack — a payload for one repository mutating another's commit, matching the Critical category explicitly listed in scope. This can corrupt CI state used for `deployable?` gating (`stack.ignore_ci? || (success? && !blocked?)`) [7](#0-6) , potentially forging a `success` status on org B's commit to unblock/trigger an unauthorized deploy, or forging a `failure`/`error` to block org B's legitimate deploys — a denial-of-service on CI gating that also crosses into deploy-authorization impact. The blast radius spans every Shipit-tracked repository sharing this Shipit instance, since the query is completely unscoped and repeatable against any sha collision the attacker can arrange.

### Likelihood Explanation
Preconditions: attacker needs to control (or push to) at least one Shipit-tracked repository/stack under any org (a very low bar — many Shipit deployments track a large number of internal/external repos), and needs a commit sha collision with the target commit in org B. With `git commit --allow-empty -m ''`, the resulting sha is fully determined by tree, parent, author, committer, and timestamps — an attacker targeting a specific victim commit (e.g., the well-known empty initial commit of a repo, or any commit whose tree/parent/timestamps are public knowledge) can reproduce byte-identical commit metadata to force a matching sha in their own repo, requiring only local git operations and no GitHub secrets. Delivering the status webhook costs nothing beyond normal GitHub API/CI usage on their own repository. This is repeatable at will against any known target sha in any co-tenant stack.

### Recommendation
Scope `StatusHandler#process` to the stacks belonging to the webhook's own repository, mirroring `CheckSuiteHandler`, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, using the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) instead of the global `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (e.g. in `test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, using existing fixtures):
1. Create two `Shipit::Repository`/`Shipit::Stack` records under different `owner` values (e.g. `org-a/repo-a`, `org-b/repo-b`), each with its own `github_app`/`webhook_secret` configured (mirroring `test/dummy/config/secrets_double_github_app.yml`).
2. Create a `Shipit::Commit` under each stack with an identical `sha` value (`"deadbeef00000000000000000000000000000000"`), representing the collided empty-commit sha.
3. Build a `status` webhook payload referencing `org-a/repo-a`'s repository info and the colliding `sha`, sign it with org A's `webhook_secret`.
4. `POST` the payload to `/webhooks` with `X-Github-Event: status` and the valid org-A `X-Hub-Signature`.
5. Assert: `assert_response :ok`; `assert_difference('commit_a.statuses.count', 1)` for org A's commit (expected/legitimate); AND `assert_difference('commit_b.reload.statuses.count', 1)` for org B's commit — proving org B's commit was mutated by a webhook signed only with org A's secret, with no credential belonging to org B ever presented.
