Confirmed exploitable analog: the webhook signature verification key (`repository_owner`/`organization.login`) is not cryptographically bound to the repository fields (`repository.full_name`) that handlers actually act on.

### Title
Webhook signature verification is bound to an attacker-controlled organization field that diverges from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's secret to verify the HMAC signature against using `repository_owner`, a value read straight from the (unverified at that point) JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0)  That same raw body is later re-parsed and dispatched to handlers that resolve the target `Stack`/`Repository` using an entirely different field, `repository.full_name`. [2](#0-1)  Because Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret` [3](#0-2) , the signature only proves the payload was signed by *the organization named in `repository.owner.login`* — it proves nothing about the organization embedded in `repository.full_name`. These two fields are never cross-checked.

### Finding Description
The binding that should hold is:
`organization whose secret validated the HMAC == organization owning the repository the handlers write to`

In practice the engine implements:
`Shipit.github(organization: params.dig('repository','owner','login'))` for verification, vs.
`Shipit::Repository.from_github_repo_name(params.dig('repository','full_name'))` for the write path.

An attacker who legitimately controls a GitHub App installation on Organization A (i.e., knows/controls Org A's `webhook_secret`, a normal, non-privileged capability of any org admin who onboarded their own org into a multi-org Shipit deployment) can craft an arbitrary raw POST body where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` looks up Org A's `GitHubApp` and the HMAC — computed by the attacker with Org A's own secret — validates), and
- `repository.full_name` = `"OrgB/some-private-repo"` (a completely different, victim organization's repository that Shipit also manages).

`verify_signature` passes because the HMAC matches Org A's secret over the raw body. `WebhooksController#create` then re-parses the same body and dispatches it to handlers, all of which resolve the target exclusively via `repository.full_name`: `PushHandler` [4](#0-3) , the pull-request handlers (`EditedHandler`, `LabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`), and `ReviewStackAdapter`, all of which key off `params.repository.full_name` / `params.dig('repository','full_name')`. [2](#0-1) [5](#0-4) 

This lets an attacker who controls one organization's webhook secret forge webhook events (push notifications that trigger `GithubSyncJob`, PR labeled/reopened events that archive/unarchive review stacks, status/check-run events, etc.) against a stack belonging to a *different, unrelated organization*, entirely bypassing that victim organization's own webhook secret.

### Impact Explanation
This breaks the credential/repository binding the app relies on: proof of possessing Org A's webhook secret is treated as authorization to mutate state for Org B's repositories/stacks. Concretely this permits unauthorized cross-repository actions such as forcing `GithubSyncJob` runs (which can trigger continuous-deployment pipelines) on a victim stack, or archiving/unarchiving/mutating review-stack state for a repository the attacker does not own, without ever needing that repository's own webhook secret. This lines up with the "cross-repository writes" / "unauthorized deploy" impact class for this engine, since `sync_github` → `trigger_continuous_delivery` can result in an unintended deploy being kicked off for a repo/environment the attacker doesn't control.

### Likelihood Explanation
Likelihood is limited to deployments configured with `Shipit.github` supporting multiple organizations (the documented multi-org config in `docs/setup.md`), and requires the attacker to control (or know) at least one organization's webhook secret in that shared Shipit instance — a bar met by any org admin who onboarded their own org's GitHub App into a shared/multi-tenant Shipit installation. No repository write access, Shipit session, or ApiClient token to the victim organization is required — only crafting a raw HTTP POST to `/webhooks` with a forged signature computed from a secret the attacker legitimately possesses for their own org.

### Recommendation
Cross-check that the organization used to select and verify the webhook signature (`repository.owner.login` / `organization.login`) matches the organization implied by `repository.full_name` before dispatching to handlers, and reject the webhook otherwise. Alternatively, resolve the target repository/stack strictly through the same organization value used for signature verification rather than through an independently-read `full_name` field.

### Proof of Concept
1. Attacker controls Org A's GitHub App/webhook secret in a Shipit instance configured for multiple organizations (`Shipit.github(organization: 'OrgA')`).
2. Attacker crafts a `push` webhook JSON body: `{"ref":"refs/heads/main","after":"<sha>","repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: 'OrgA')`, and the HMAC validates successfully. [6](#0-5) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('OrgB/victim-repo')`, matching the victim's stack, and calls `stack.sync_github(expected_head_sha: ...)`, mutating/triggering CD for `OrgB`'s stack despite the signature only proving possession of `OrgA`'s secret. [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
