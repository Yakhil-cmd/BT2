### Title
Cross-organization webhook signature confusion allows forging events for repositories owned by a different GitHub org - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). But the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, pull-request handlers, etc.) resolve the target `Repository`/`Stack` from a *different* field: `payload.dig('repository', 'full_name')`. These two fields are never checked for consistency, so the "organization that authenticated" and the "repository that is written" are not the same binding.

### Finding Description [1](#0-0) 

`verify_signature` picks the GitHub App config via `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against that app's `webhook_secret`: [2](#0-1) 

`repository_owner` is read from `repository.owner.login` in the JSON body.

Separately, `Handler#repository_name`/`Handler#stacks` resolve the actual mutated entity from `repository.full_name`: [3](#0-2) 

`Repository.from_github_repo_name` splits that string on `/` to find `owner`/`name` and returns its `stacks`: [4](#0-3) 

Both `repository.owner.login` and `repository.full_name` are attacker-controlled top-level fields of the JSON body, and the HMAC covers the raw body — so the signature does prove "this exact byte sequence was sent by whoever holds `webhook_secret` for org X" — but it does not prove that org X actually owns the repository named in `repository.full_name`. In a multi-tenant Shipit deployment (the engine explicitly supports configuring several GitHub orgs, each with its own `webhook_secret`, e.g. `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml` show two independent org entries), a party who legitimately administers one configured org's GitHub App (and thus its `webhook_secret`) can craft a payload where:
- `repository.owner.login` = their own org (so `verify_signature` picks *their* webhook secret and the HMAC passes), while
- `repository.full_name` = `"other-org/some-repo"` (a repository belonging to a different, unrelated org also configured on the same Shipit instance).

`PushHandler#process` then looks up stacks for `other-org/some-repo` and calls `stack.sync_github(expected_head_sha: params.after)`, and other handlers (pull_request, status, check_suite, membership, etc.) similarly key off `repository.full_name`/`repository`/`organization` sub-objects independently of which secret validated the request. This is the shipit-engine analog of the `stETH` bug class: the field that is verified (`repository.owner.login`, used to select the signing key) is not the field that is acted upon (`repository.full_name`, used to select the mutated `Stack`), exactly the "organization that authenticated versus the repository that is written" binding called out as in-scope.

### Impact Explanation
An attacker who legitimately controls one tenant org's GitHub App installation (and therefore its `webhook_secret`) — which is not a Shipit credential, Shipit session, or repository write access on the *target* repo — can forge webhook deliveries that are processed as if they originated from GitHub for a *different* organization's repositories hosted on the same Shipit instance. Depending on which handler fires, this can trigger unauthorized `GithubSyncJob`s, forged commit `status`/`check_suite` updates that affect deployability checks (`app/models/shipit/webhooks/handlers/status_handler.rb`, `check_suite_handler.rb`), or membership/team mutations (`membership_handler.rb`) against stacks owned by a repository the attacker has no relationship with — a cross-repository/cross-organization write, which maps to the "cross-repository writes" Critical impact category, and can influence whether a deploy is considered safe (deployable status), touching the "unauthorized deploy" category as well.

### Likelihood Explanation
Requires the attacker to be an administrator of *some* GitHub org configured as a Shipit tenant (not the target org), which the rules classify as an unprivileged attacker relative to the victim organization/repository — no Shipit session, `ApiClient` token, or GitHub App private key for the *target* org is needed. This is realistic in any Shipit deployment serving multiple independent GitHub organizations (a supported and documented configuration, per `secrets_double_github_app.yml`).

### Recommendation
Bind the verification identity to the acted-upon identity: after computing `repository_owner` for signature selection, re-derive the same value from `repository.full_name` (or `organization.login`) and assert they match before dispatching to handlers; alternatively, have handlers resolve/scope the target repository strictly by the same organization key that was used to select the signing secret, rejecting the payload if `repository.full_name`'s owner segment does not equal `repository_owner`.

### Proof of Concept
1. Configure Shipit with two tenant orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who administers `OrgA`'s GitHub App, craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC_SHA1(OrgA_webhook_secret, raw_body)`.
4. POST to the webhooks endpoint with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret [5](#0-4) .
6. `PushHandler` resolves `repository_name` as `"OrgB/victim-repo"` [6](#0-5)  and enqueues `GithubSyncJob` for `OrgB`'s stacks with an attacker-chosen `expected_head_sha`, despite the attacker never having proven any relationship with `OrgB`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
