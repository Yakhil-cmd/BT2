### Title
CCMenuController#stack bypasses ApiClient stack scoping, allowing any CCMenu token to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` resolves the target stack via `Stack.from_param!(params[:stack_id])` against the unscoped `Stack` relation, completely bypassing the `current_api_client.stack_id` scoping guard that `Api::BaseController#stack` normally enforces. Combined with `CCMenuUrlController#fetch` minting a token via a per-user (not per-stack) `find_or_create_by!` lookup, a token obtained for one stack can be replayed against `GET /api/stacks/:other_stack/cc.xml` to read another stack's deploy status.

### Finding Description
The intended binding is: for any request handled with a stack-scoped `ApiClient`, `stack.id == current_api_client.stack_id` (or `current_api_client.stack_id` is absent, in which case any stack is permitted by design). `Api::BaseController` implements this correctly: [1](#0-0) 

`stacks` is filtered to `current_api_client.stack_id` when present, and `stack` is resolved from that filtered relation. `Api::CCMenuController`, however, overrides `stack` and skips this scoping entirely: [2](#0-1) 

`Stack.from_param!(params[:stack_id])` queries the full, unscoped `Stack` table regardless of what `current_api_client.stack_id` is, so `stack.id == current_api_client.stack_id` no longer holds — any authenticated `ApiClient` (any valid token, scoped or not) can fetch `cc.xml` for an arbitrary stack by simply changing `params[:stack_id]`.

This is compounded by how the token is minted. `CCMenuUrlController#fetch` creates the `ApiClient` via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — keyed only on `creator` and `name`, with no `stack:` attribute set: [3](#0-2) 

so the resulting client's `stack_id` is `nil` (unscoped) in the database already. Even setting that aside, `CCMenuController#stack`'s bypass means scoping would be ineffective regardless of whether the client had a `stack_id` set.

`require_permission :read, :stack` only checks the `read:stack` permission string on the client — it never checks which stack the permission applies to: [4](#0-3) [5](#0-4) 

**Exploit flow:** An authenticated user (attacker with only read access to one stack's settings, e.g. Stack A) clicks "Fetch URL" in the CCMenu settings widget, which calls `CCMenuUrlController#fetch` and receives a token minted against `ApiClient.authenticate`. The attacker then issues `GET /api/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_branch>/cc.xml?token=<token>` for any other stack B in the installation. `CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`, and `stack` resolves stack B unscoped, rendering stack B's deploy/build status.

### Impact Explanation
Any valid CCMenu token (obtained legitimately for one stack, or leaked, since CCMenu URLs are designed to be pasted into external tools) grants read access to build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state) for every stack managed by the Shipit instance, not just the stack it was issued for. This is a cross-stack unauthorized read of deploy status, repeatable against any stack in the installation by simply substituting the `stack_id` route parameter, with no per-stack authorization check.

### Likelihood Explanation
No special Shipit configuration is required. The only precondition is possessing any valid CCMenu (or other) `ApiClient` token with `read:stack` permission — obtainable by any user who can view a single stack's settings page and click "Fetch URL," or through any leaked CCMenu URL (these URLs are explicitly designed to be shared with external monitoring tools). The attacker cost is a single authenticated GET request; the bypass is deterministic and repeatable against every stack in the installation.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or make it consistent with `BaseController`) so it uses the scoped `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!`, and set `stack:` on the `ApiClient` created in `CCMenuUrlController#fetch` so each CCMenu token is durably scoped to the stack it was generated for.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token minted for one stack cannot read another stack's build status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")

  client = ApiClient.create!(creator: shipit_users(:walrus), name: "CCMenu Client",
                              permissions: %w[read:stack], stack: stack_a)

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: stack returned by CCMenuController#stack == current_api_client.stack_id
  assert_response :forbidden # or :not_found — currently returns 200 with stack_b's data
end
```
