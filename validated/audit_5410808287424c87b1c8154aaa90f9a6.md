### Title
Users can front-run pending bad-debt liquidations to redeem zTokens before `socialize-debt` write-down, shifting the loss onto remaining depositors - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
In `liquidate()`, when a borrower's collateral is fully seized and unpaid debt remains, the market calls `socialize-debt-asset` → vault `socialize-debt`, which writes down the vault's `lindex` (the share-price index used by all zToken holders) proportionally to the loss. Because `liquidate()` is a normal, mempool-visible transaction and `redeem()` in the corresponding vault uses the *current* `lindex`/`total-assets` at call time with no cooldown or "bad-debt-pending" lock, a zToken holder who observes an imminent bad-debt liquidation can front-run it with `redeem()` and exit at the pre-loss share price, leaving remaining zToken holders to absorb the loss (and a *larger* loss than the case, since the same absolute `debt-reduction` is applied to a now-smaller `total-assets`).

### Finding Description
When a position has no collateral left to cover its debt, `liquidate()` triggers bad-debt socialization via `socialize-debt-asset`, which calls the vault's `socialize-debt`: [1](#0-0) [2](#0-1) 

The vault's `socialize-debt` reduces the shared `lindex` (share-price index) for *all* zToken holders in that vault, proportionally to the loss relative to the current `total-assets`: [3](#0-2) 

Meanwhile, `redeem()` computes the payout using `convert-to-assets-preview`, which is derived from the current (not-yet-written-down) `lindex`/`total-assets`, and has no delay, cooldown, or "pending bad debt" check: [4](#0-3) 

Because `liquidate()` (which is a permissionless, publicly callable transaction visible in the mempool before mining) and `redeem()` share the same underlying state (`assets`, `lindex`, `total-borrowed`), an attacker watching the mempool for a liquidation that will trigger `bad-debt-socialized: true` can submit a `redeem()` transaction with higher priority/fee to land first in the same block (or an earlier block). This is the same ordering-dependence bug class as the Casimir report: a user with knowledge of an imminent, unavoidable loss event exits the shared pool at the pre-loss valuation before the loss is realized on-chain, and the loss is then socialized only among the remaining zToken holders (who had no way to react in time).

### Impact Explanation
This is a shared-pool socialization attack between two unprivileged principals: the front-running redeemer (attacker) extracts full pre-loss value from the vault's shared `assets`/`lindex` state, and the remaining zToken holders (victims) bear a disproportionately larger loss than they would have absent front-running, because the same absolute `debt-reduction` is now divided among a smaller `old-total-assets` base: [5](#0-4) 
This is a temporary/permanent freezing and theft of value for the remaining depositors (their entitled share of `total-assets` is reduced below what it should have been), satisfying the "temporary freezing of funds" / socialized-loss impact class for an in-scope lending-pool analog of the reported unstake-frontrunning bug.

### Likelihood Explanation
Any market participant can observe pending `liquidate()` transactions (or the on-chain state indicating a position has zero collateral and outstanding debt, making bad-debt socialization inevitable) in the mempool, and race it with a `redeem()` call on the corresponding vault. No special privilege, flashloan, or DAO action is required — only mempool visibility and normal transaction fee bumping, which is realistic on any public chain including Stacks.

### Recommendation
Introduce a mechanism analogous to the Casimir fix: do not allow `redeem()` (or at least large `redeem()`s) to be fulfilled using a share price that has not accounted for known-pending bad debt, e.g., by:
- Snapshotting/accruing bad-debt write-downs atomically before allowing redemption in the same block/period as a liquidation that will produce `bad-debt-socialized: true`, or
- Adding a redemption queue/delay so `redeem()` requests cannot be created and fulfilled within the same block/period in which a socialization event occurs, or
- Having `liquidate()` pre-emptively mark the vault "loss pending" so `redeem()` reverts or is capped until socialization completes.

### Proof of Concept
1. Borrower's position has zero collateral remaining and outstanding debt in `debt-aid`'s vault (e.g., `v0-vault-usdc`); this is publicly observable on-chain.
2. Any actor submits `liquidate(borrower, ...)`; this transaction sits in the mempool and, upon confirmation, will call `vault-socialize-debt`, reducing `lindex` for `v0-vault-usdc` per [3](#0-2) .
3. Attacker, holding zUSDC, observes this pending transaction and submits `redeem()` with a higher fee/priority so it lands in an earlier or the same block before the liquidation's socialization write-down, per [4](#0-3) .
4. Attacker's `redeem()` executes at the old, pre-loss `lindex`, receiving full value.
5. `liquidate()` then executes, computing `new-lindex` using `old-total-assets` that no longer includes the attacker's withdrawn assets, so the fixed `debt-reduction` is spread over a smaller base — the remaining zUSDC holders take a proportionally larger loss than if the attacker had not exited first.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
