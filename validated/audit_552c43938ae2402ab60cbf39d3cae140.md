### Title
Cross-Organization Status Forgery via Signature/Repository-Binding Mismatch in `WebhooksController` and `StatusHandler` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multiple GitHub organizations, each with its own GitHub App and `webhook_secret` [1](#0-0) . The webhook signature check authenticates the request against the organization derived from `repository.owner.login` (or `organization.login`) in the JSON body [2](#0-1) , but the handler that acts on the payload for `status` events resolves the target purely by commit SHA, with **no repository or organization scoping at all** [3](#0-2) . This is the same bug class as the `YakSwapCell._swap` report: a field that is acted upon (`sha` → arbitrary `Commit` row) is never covered by what the verified signature actually attests to (that the sender knows organization X's secret).

### Finding Description
1. `verify_signature` picks the `GitHubApp` (and thus the HMAC secret) to check against using `repository_owner`, i.e. `params.dig('repository', 'owner', 'login')` — a value taken from the **unverified** request body itself, before the signature is checked [4](#0-3) .
2. Once the HMAC passes (proving only that the sender knows *organization X's* `webhook_secret`, e.g. an org the attacker themselves administers and configured in Shipit per `docs/setup.md`), the raw JSON is dispatched to handlers unchanged [5](#0-4) .
3. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` **globally across the entire database**, with no filter on `repository`/`stack`/organization, and calls `create_status_from_github!` on every match [3](#0-2) . Unlike `PushHandler` and `CheckSuiteHandler`, which scope through `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`) [6](#0-5) [7](#0-6) , `StatusHandler` never checks `payload['repository']['full_name']` at all.
4. Commit SHAs are public GitHub metadata, trivially discoverable for any repository tracked by a shared Shipit instance.

The equality the design implicitly relies on — "organization whose secret authenticated the request" == "organization/repository whose state is mutated" — is broken: the signature only proves *an* organization's secret was known, while the effect (writing a `Status` row) is applied to any `Commit` in the database that happens to share that SHA, regardless of which organization/repository it belongs to.

### Impact Explanation
An entity that legitimately administers **any one** GitHub organization configured in this multi-tenant Shipit instance (and thus knows only that org's `webhook_secret`) can forge a `status` webhook (`X-Github-Event: status`) with a `sha` belonging to a **different** organization's repository/stack. Since `Commit#create_status_from_github!` writes CI status directly, this can:
- Satisfy `merge.require` / `ci.require` checks used by `MergeRequest#all_status_checks_passed?` (via `StatusChecker`) [8](#0-7) , causing `ProcessMergeRequestsJob` to auto-`merge!` a pull request in a repository the attacker does not control — an **unauthorized merge**.
- Satisfy deploy-blocking CI requirements, enabling an **unauthorized deploy** of a stack belonging to another organization.

This crosses an authentication/organization boundary and results in cross-repository/cross-organization state mutation and unauthorized merge/deploy, matching the Critical impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to control a GitHub organization that is one of the (potentially many) tenants configured under `secrets.github` in a shared Shipit deployment, and to know that tenant's own `webhook_secret` — something they legitimately possess as the administrator of their own org's GitHub App installation. No access to any other organization, no Shipit account, and no privileged Shipit credentials are required to target a different tenant's stacks. This is realistic wherever Shipit is deployed as a shared/multi-org instance (explicitly supported and documented, e.g. `config/secrets.development.shopify.yml`).

### Recommendation
- In `StatusHandler` (and any other handler that doesn't already do so), scope lookups through `Handler#stacks`/`repository_name` (`payload.dig('repository', 'full_name')`) instead of a bare `Commit.where(sha:)` global lookup, mirroring `PushHandler`/`CheckSuiteHandler`.
- In `WebhooksController#verify_signature`, ensure the organization used to select the verifying secret is cross-checked against the organization implied by every payload field subsequently trusted (e.g., verify that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` before dispatching to handlers).

### Proof of Concept
1. Deploy Shipit configured with two GitHub organizations, `victim-org` and `attacker-org`, each with its own `webhook_secret` (multi-org config as in `config/secrets.development.shopify.yml`).
2. Attacker administers `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker looks up a public commit SHA `S` belonging to a pull request/commit tracked by a stack in `victim-org`.
4. Attacker POSTs to `/webhooks` with:
   - `X-Github-Event: status`
   - `X-Hub-Signature` computed with `attacker-org`'s `webhook_secret`
   - Body: `{"sha": "S", "state": "success", "context": "ci/required", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"}}`
5. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies successfully against `attacker-org`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the victim's commit (owned by `victim-org`), and creates a `success` status on it — with no check that `S` belongs to `attacker-org/some-repo`.
7. If this satisfies `victim-org`'s required CI contexts, `ProcessMergeRequestsJob` merges the pull request, or the corresponding deploy proceeds, entirely orchestrated by the `attacker-org` actor.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
