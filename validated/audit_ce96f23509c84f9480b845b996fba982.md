## Title
`address_definition_change` performs an immediate, single-step, irreversible authority transfer for an address, with no acceptance/verification step analogous to a safe two-step ownership transfer - (File: `validation.js`, `definition.js`, `writer.js`)

### Summary
The reported bug is about `WardenPledge` silently losing the two-step `Owner.transferOwnership` safeguard by inheriting `Ownable` instead, so a single bad call can hand control to an inoperable address with no way to recover. The analogous risk in `ocore` is the `address_definition_change` message: it lets the current signer of an address replace that address's entire authentication/definition in **one on-chain step**. Once the message stabilizes, the new `definition_chash` becomes final and controls the address forever, with no requirement that the corresponding definition be known to be satisfiable, and no "pending"/"accept" stage that could be rolled back if the new authority turns out to be wrong or unusable.

### Finding Description
`address_definition_change` is validated in `validateInlinePayload` and only checks that the payload has the right shape and that `definition_chash` is a syntactically valid address/chash: [1](#0-0) 

The corresponding definition-level checks in `definition.js` (`has definition change`/`seen definition change`) likewise only validate that the changed address and new chash are *syntactically* valid addresses, not that the referenced definition is known or satisfiable: [2](#0-1) 

The change is persisted as a plain, single-step record with no counterpart "acceptance" record: [3](#0-2) 

The only safeguard that exists is serialization (you cannot post more units from the address while a definition change is still pending/unstable), which prevents *conflicting* changes, but does nothing to prevent an *erroneous* change from becoming final: [4](#0-3) 

Once the unit carrying `address_definition_change` becomes stable, `readDefinitionChashByAddress`/`readDefinitionByAddress` treat the new chash as the address's authoritative definition for all future signature/authentifier checks, with no fallback to the old definition and no window for the "new owner" to prove the definition is revealable/usable before the change takes final effect: [5](#0-4) 

This is structurally the same class of gap as the reported issue: the ecosystem's UX and design imply that changing control of an address is a deliberate, verifiable act (analogous to `Owner`'s two-step `transferOwnership`), but the actual on-chain mechanism is a single irreversible commit, comparable to `Ownable`'s one-step `transferOwnership`, without any built-in requirement to prove the new definition is workable before it becomes final.

### Impact Explanation
Any wallet holder, AA-referenced address, or shared-address cosigner who posts an `address_definition_change` unit that resolves to a chash whose definition is mistyped, unknown, or otherwise unsatisfiable (e.g. copy-paste error building the chash from a template, wrong `hash160` parameter, or a definition referencing a key that was never generated) permanently and irrecoverably loses the ability to sign for that address once the unit stabilizes. Because the address might also be referenced as a shared-address cosigner, an asset `definer_address`/attestor, or inside AA/asset conditions via `'address'`/`'has definition change'` expressions, its funds and any dependent contractual logic (arbiter contracts, asset transfer/issue conditions relying on that address) become frozen with no recovery path, matching the "AA fund loss or freezing" / control-loss impact class.

### Likelihood Explanation
This does not require an attacker; it can occur from ordinary user error by any address owner, since the message is fully within reach of a single unprivileged unit poster and requires no cooperation from any other party. The absence of any verification step or explicit warning that the change is final and irreversible increases the likelihood that a user (or buggy wallet client composing the `definition_chash`) will trigger it without realizing the consequences, mirroring the "perceived safeguard that doesn't exist" framing of the original finding.

### Recommendation
- Where a definition change is user-initiated and not required to be atomic (e.g. via wallet UX), require the new definition (not just its chash) to be revealed/attached and validated as satisfiable (or at minimum locally simulated) before allowing the change to be broadcast.
- Consider introducing an optional two-step protocol at the wallet layer (analogous to `Owner.transferOwnership`/`acceptOwnership`): compose the change, but only finalize/broadcast it after independently confirming the new definition can be evaluated with sample authentifiers.
- Surface a prominent, explicit warning in `composeDefinitionChangeJoint` callers that `address_definition_change` is final and irreversible once stable, and encourage dry-run validation via `Definition.validateDefinition` prior to signing.

### Proof of Concept
1. Address `A` is controlled by key `K1`.
2. The owner composes an `address_definition_change` message for `A` with `definition_chash` computed from a definition array that references a public key `K2` for which the corresponding private key was never generated/saved (e.g., due to a tooling bug or copy-paste error), using `composeDefinitionChangeJoint` in `composer.js` (lines 85-87).
3. `validateInlinePayload` (`validation.js:1719-1745`) and `Definition.validateDefinition`'s `has definition change`/`seen definition change` handling (`definition.js:352-368`) only check chash format, not that a satisfying definition/key exists.
4. The unit is broadcast and eventually stabilizes; `writer.js:184-192` records the change and `storage.readDefinitionChashByAddress` (`storage.js:754-768`) now returns the new chash as final.
5. No authentifier for the new definition can ever be produced (since `K2`'s private key doesn't exist), so address `A` and any funds/outputs/conditions still directed to it become permanently unspendable, with no two-step "accept" mechanism having existed to prevent or reverse the mistake.

function readDefinitionChashByAddress(conn, address, max_mci, handle){

	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}
