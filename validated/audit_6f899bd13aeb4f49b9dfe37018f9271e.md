### Title
Missing overflow (`MAX_BALANCE`) guard when applying final AA balance deltas — (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s `handleTrigger` flow enforces an overflow guard (`MAX_BALANCE`) when adding the trigger's incoming payment to an AA's balance in `updateInitialAABalances`, but the corresponding final-balance update performed later in the same trigger's processing, `updateFinalAABalances`, applies deltas from consumed outputs and outgoing payment messages with plain `+=`/`-=` and never re-checks the `MAX_BALANCE` bound. This is the same "bounded-then-unbounded" arithmetic inconsistency pattern described in the referenced report (`Calc.boundedAdd` used to avoid overflow in one place, plain arithmetic used later on the same class of value).

### Finding Description
`MAX_BALANCE` is defined specifically to keep AA balances within a range that avoids precision loss beyond `Number.MAX_SAFE_INTEGER`: [1](#0-0) 

`updateInitialAABalances` explicitly checks every balance increment against `MAX_BALANCE` and flags `bOverflow` (causing the trigger to bounce with `"balance overflow"` once `mci >= constants.pemCurvesFixMci`): [2](#0-1) 

However, `updateFinalAABalances`, which is invoked later in the same trigger-handling path to apply the net deltas from the AA's own consumed/produced outputs (including assets the AA itself issues, or bytes it receives via its own response messages), updates `objValidationState.assocBalances[address][asset]` and `byte_balance` with plain `+=` and never re-validates against `MAX_BALANCE`: [3](#0-2) 

Because `objValidationState.assocBalances` is the same in-memory structure read by the oscript formula evaluator's `balance[...]` accessor for subsequent AA logic (e.g. in secondary triggers or bounce handling) and is also the value persisted to the `aa_balances` table, an unguarded increase here can push the tracked balance past the same threshold the initial check was explicitly designed to prevent, silently reintroducing precision-loss risk that the `MAX_BALANCE` guard exists to avoid.

### Impact Explanation
If an AA's own issuance/payment logic combined with a large trigger payment pushes the post-response balance above `MAX_BALANCE` without the guard firing, the AA's tracked balance (both in `objValidationState.assocBalances` used by subsequent oscript evaluations and the persisted `aa_balances.balance` row) can diverge from the true on-chain, output-derived balance. This is exactly the class of drift the periodic `checkBalances` consistency check is designed to catch, and a hard mismatch there causes a hard `throw Error("checkBalances failed...")`, i.e. a node crash/consistency failure: [4](#0-3) 

A persistent state divergence for the affected AA address can result in the AA's own future triggers being processed inconsistently across nodes (since balance-dependent formulas would evaluate differently depending on whether the in-memory or DB-derived balance is used), which is a node-disagreement/AA-fund-freezing outcome, not merely a resource/DoS issue.

### Likelihood Explanation
Reaching `MAX_BALANCE` requires an AA to accumulate a balance close to `2**63 - 1 - MAX_MESSAGES_PER_UNIT * MAX_CAP`, so likelihood is low in practice — similar to the referenced report's own assessment that the analogous Solidity issue is unlikely to be reached but still represents a real gap in defense-in-depth once the bounded check was intentionally added elsewhere in the same call path.

### Recommendation
Apply the same `MAX_BALANCE` bound check (or an equivalent safe-arithmetic helper) inside `updateFinalAABalances` whenever `assocDeltas[asset]` or `byte_balance` increases, and bounce/reject the trigger consistently in that case as `updateInitialAABalances` already does, so the guard added specifically to avoid `Number` precision-loss/overflow is enforced uniformly across all balance-mutating code paths for the same trigger.

### Proof of Concept
1. Have an AA whose current `aa_balances` balance for an asset is already near `MAX_BALANCE` (attacker can build this up over many prior triggers, or via a single large trigger that is just under the `updateInitialAABalances` threshold).
2. Send a trigger unit that (a) causes `updateInitialAABalances` to pass (post-trigger balance still `<= MAX_BALANCE`), and (b) whose AA response logic issues/receives additional units of the same asset via a `payment` message targeting the AA's own address (processed in `updateFinalAABalances`), pushing `assocBalances[address][asset]` past `MAX_BALANCE`.
3. Because `updateFinalAABalances` performs `objValidationState.assocBalances[address][asset] += assocDeltas[asset]` without any bound check, the trigger succeeds and the in-memory/DB balance now exceeds the value the `MAX_BALANCE` guard was designed to prevent, risking later precision loss/consistency mismatches surfaced by `checkBalances`.
