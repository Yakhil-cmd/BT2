### Title
`OpenedHandler#provision?` operator-precedence bug creates review stacks when `review_stacks_enabled` is false and behavior is `prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends every provisioning path to require `repository.review_stacks_enabled` to be `true`, but Ruby's `&&`/`||` precedence causes the third clause `(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` to be evaluated independently of `review_stacks_enabled`. An attacker who can open a pull request without the provisioning label against a repository configured with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false` can therefore trigger creation of a `Shipit::ReviewStack`/`Shipit::Stack` even though administrators explicitly disabled review stacks.

### Finding Description
The claimed binding is: `provision?` result == `repository.review_stacks_enabled`. Given `review_stacks_enabled = false`, the expected result of `provision?` is `false` for all behaviors, since review stacks are supposed to be a global on/off switch.

The code is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

`&&` binds tighter than `||` in Ruby, so this parses as:
```
(review_stacks_enabled && provisioning_behavior_allow_all?) ||
(provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
Only the first disjunct is gated by `review_stacks_enabled`. The second and third disjuncts — `allow_with_label` and `prevent_with_label` — are entirely independent of `review_stacks_enabled`.

With `review_stacks_enabled = false`, `provisioning_behavior_prevent_with_label? = true`, and no label on the PR, `pull_request_has_provisioning_label?` returns `false` (since `pull_request_label_names.include?(repository.provisioning_label_name)` is `false` when the label list doesn't contain `nil`/the configured label) [2](#0-1) , making the third disjunct `true`. `provision?` therefore returns `true`, and `respond_to_pull_request_opened?` allows `process` to call `ReviewStackAdapter#find_or_create!`, which creates a new `Shipit::ReviewStack` (a `Shipit::Stack` subtype) via `scope.create!(stack_attributes)` [3](#0-2) , adds it to the provisioning queue, and persists a `Shipit::PullRequest` record — despite `review_stacks_enabled` being `false`.

Attacker path: any GitHub user opens a PR on a repository they control (or forks) that is tracked by Shipit and configured this way, with no label attached. The `pull_request.opened` webhook is processed by `OpenedHandler#process` [4](#0-3) . No repository ownership check beyond `Repository.from_github_repo_name(params.repository.full_name)` is required, and webhook signature verification only authenticates that the payload came from GitHub for that specific repo, not that the repo owner enabled provisioning — `verify_signature`/`GitHubApp#verify_webhook_signature` guard against forged payloads but do nothing to enforce the `review_stacks_enabled` business rule, so they do not prevent this divergence.

Before/after check: expected `provision?` == `review_stacks_enabled` == `false` in all cases; actual `provision?` == `true` under the `prevent_with_label` configuration with no label present — confirming the binding is broken.

The existing test suite documents this exact behavior as intentional (test `"create stacks for repos what prevent_with_label when label is absent"`) but only exercises it with `provisioning_enabled: true` (the default) [5](#0-4) ; it never asserts the case `review_stacks_enabled: false` combined with `prevent_with_label`, which is exactly the gap that causes the divergence.

### Impact Explanation
An attacker can force creation of an unwanted `Shipit::ReviewStack`/`Shipit::PullRequest`/`Shipit::Stack` record and enqueue it for provisioning on a repository whose administrators explicitly turned off review-stack auto-provisioning (`review_stacks_enabled = false`). This is a write for a repository whose owner did not authorize this behavior via the disabled toggle — matching the Critical criterion "a payload for one repository mutating another's stack ... or an unauthorized deploy." It is repeatable against any repository configured with `prevent_with_label` and `review_stacks_enabled=false` by simply opening PRs without the label; each PR opened creates a new stack in the provisioning queue, which could trigger downstream provisioning/deploy jobs depending on `ReviewStackProvisioningQueue` consumers.

### Likelihood Explanation
Requires only: (1) the repository is tracked by Shipit, (2) `provisioning_behavior` is set to `prevent_with_label`, and (3) `review_stacks_enabled` is `false`. No secrets, tokens, or elevated privileges are needed — the attacker merely opens a PR without the configured label on a repo they can PR against (their own fork or a repo they have PR rights to). The attack is trivially repeatable with each new PR.

### Recommendation
Fix operator precedence by parenthesizing the first clause and gating the whole expression on `review_stacks_enabled`:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Expected (binding held): `Shipit::Stack.count` unchanged, since `repository.review_stacks_enabled == false`.
Actual (bug present): `Shipit::Stack.count` increases by 1, demonstrating `provision?` returns `true` even though `review_stacks_enabled` is `false`.
