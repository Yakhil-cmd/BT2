### Title
Global `handleJoint` mutex held across a full AA dry-run evaluation blocks all unit validation network-wide - (File: network.js)

### Summary
`network.js`'s `handleJoint()` acquires the process-wide `handleJoint` mutex before calling `validation.validate()`, and only releases it after `writer.saveJoint()` completes. When `conf.bDryRunNewTriggers` is enabled and the freshly-validated unit triggers a primary AA, the `ifOk` handler performs a full, synchronous-from-the-lock's-perspective AA execution via `aa_composer.dryRunPrimaryAATrigger()` *while still holding the `handleJoint` lock*, before ever calling `writer.saveJoint()` or releasing the lock. ### Finding Description
`handleJoint()` wraps the entire validate→save pipeline in `mutex.lock(['handleJoint'], ...)`, and the lock is only released via `unlock()` deep inside the `ifOk`/`writer.saveJoint` completion callback: [3](#0-2) [4](#0-3) 

Inside the `ifOk` callback — before `writer.saveJoint()` is even invoked — the code performs, for every AA address paid by the incoming unit, an `await db.query(...)` followed by `await aa_composer.dryRunPrimaryAATrigger(...)`: [5](#0-4) 

`dryRunPrimaryAATrigger()` opens a *new* DB connection, begins its own transaction, and runs the full oscript/ojson AA evaluation pipeline (`handleTrigger`), including arbitrary formula evaluation, data-feed lookups, and secondary AA chains, before rolling back and releasing that connection: [6](#0-5) 

This is architecturally analogous to the CVE-2025-38525 root cause: a heavyweight, unbounded operation (`rxrpc_assess_MTU_size()` → IP routing) is invoked from a code path that is holding a lock/context (`hardirq disabled`) that the rest of the system depends on completing quickly. Here, `dryRunPrimaryAATrigger()` (potentially involving nested/secondary AA evaluation, arbitrarily complex oscript formulas up to the AA complexity limit, and multiple DB round-trips) is executed while the global `handleJoint` mutex is held — the same mutex that gates *every other unit's validation* (`validation.js` line 357 uses per-author-address locks, but `composer.js`, `divisible_asset.js`, `indivisible_asset.js` getSavingCallbacks and `joint_storage.purgeUncoveredNonserialJointsUnderLock()` all also acquire `handleJoint`): [7](#0-6) [8](#0-7) 

Any unprivileged unit poster can trivially reach this path: simply broadcast a unit that pays an existing AA address (triggering `objValidationState.count_primary_aa_triggers`), and the receiving/relaying node will run a full AA dry-run under the global lock before it can process/save the unit or unlock to let any other pending unit (from any peer) proceed.

### Impact Explanation
While `handleJoint` is held, no other unit — from any peer — can complete validation or be saved anywhere in the codebase that shares this lock (`composer.js`, `divisible_asset.js`, `indivisible_asset.js`, `joint_storage.js`, and `main_chain.js`'s stability advancement path, which explicitly documents relying on `handleJoint` lock ordering to avoid deadlocks). A remote, unprivileged attacker who repeatedly posts units triggering AAs with expensive-but-legal computation (nested/secondary AA calls, data-feed lookups, loops up to the complexity cap) can serialize and stall the node's entire unit-processing pipeline, effectively preventing the network node from confirming new units in a timely manner — matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
This requires no special privileges: any address can be turned into an AA (public), and any unit poster can send a payment that triggers that AA (`count_primary_aa_triggers`). The dry-run path is gated only by `conf.bDryRunNewTriggers`, `!conf.bLight`, and the presence of `objJoint.ball` being falsy — conditions readily satisfiable for freshly-relayed (non-catchup) units. The attacker fully controls the AA definition (deploying their own AA ahead of time) and the trigger payload, giving them significant control over how expensive the dry run is, up to the platform's complexity/response limits.

### Recommendation
Move the `bDryRunNewTriggers` dry-run evaluation outside the `handleJoint`-locked critical section — e.g., perform it either before acquiring the lock (on a copy of validated data) or after `unlock()` is called, or use a separate, non-blocking lock/queue for dry-run pre-checks so it cannot stall unrelated unit validation. Alternatively, apply the same complexity/time budget enforcement to dry-run trigger evaluation as is enforced for stable-MCI trigger execution, and consider skipping dry-run entirely for triggers targeting AAs with already-known high average execution cost.

### Proof of Concept
1. Attacker deploys an AA definition at address `A` with a computationally expensive but within-limits chain (e.g., multiple secondary AA hops or expensive oscript formulas/data-feed reads).
2. Attacker (or anyone) posts and broadcasts many units in quick succession, each paying `A` (a primary trigger) from freshly generated addresses.
3. Each such unit arrives at `handleJoint()`, acquires the global `handleJoint` mutex, and — before `writer.saveJoint()` — executes `aa_composer.dryRunPrimaryAATrigger()`, which independently reruns the same AA evaluation logic used for real execution.
4. While each dry run executes, `handleJoint` remains locked, so all concurrently-arriving units (from any peer, including honest users' legitimate payments) queue behind it in `mutex.js`'s `arrQueuedJobs`, delaying confirmation of unrelated units.
5. Repeating this with many crafted units causes sustained node-wide validation stalls.

Note: I was unable to fully verify from the indexed code whether `conf.bDryRunNewTriggers` defaults to `true` or `false` in the shipped `conf.js` — this configuration file's content was not found in the indexed corpus, so confirmation of default-enablement (and thus real-world exposure) requires manual inspection of `conf.js` in a full checkout.
