### Title
Webhook signature verification is scoped to the wrong repository field, allowing cross-organization/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and which `webhook_secret`) validates an inbound webhook's HMAC using `repository_owner`, a field taken from the payload's `repository.owner.login` (or `organization.login`). However, the actual event handlers that mutate state (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, all `PullRequest::*Handler`s, etc.) resolve the target `Repository`/`Stack` from a completely different field: `repository.full_name`. Nothing ties these two fields together, so the organization whose secret authenticated the request is not necessarily the organization/repository that gets acted upon.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` picks the verifying `GitHubApp` like this: [1](#0-0) 

Concretely: [2](#0-1) [3](#0-2) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, and Shipit supports one `webhook_secret` **per organization** in multi-org installs: [4](#0-3) 

Once the signature check passes (or is skipped, e.g. because that organization has no `webhook_secret` configured — a state explicitly shown as a valid setup in the example config), the raw, un-revalidated JSON payload is handed to every handler for the event: [5](#0-4) 

But the handlers resolve the *actual* repository/stack to act on from a different key in the same payload, `repository.full_name`, with no cross-check against `repository.owner.login`: [6](#0-5) [7](#0-6) 

The equality that should hold — `organization authenticated by verify_signature == organization owning the repository the handler writes to` — is never enforced. An attacker who can get a webhook accepted for *any* configured GitHub organization (including one intentionally left without a `webhook_secret`, which the shipped example config documents as a normal configuration) can set `repository.owner.login` to that org while setting `repository.full_name` to an entirely different, protected org's repository. The `PushHandler` will then invoke `stack.sync_github(expected_head_sha:)` for stacks under that unrelated repository, `StatusHandler` will create commit statuses for it, and the `PullRequest::*` handlers will mutate its review-stack/pull-request state — all without ever validating a signature scoped to that repository's real organization.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose credentials authorized this webhook" and "the repository whose Shipit state gets modified." In a multi-org Shipit deployment (the documented `github: {OrgOne: {...}, OrgTwo: {...}}` schema), a request that authenticates against one organization's (possibly secret-less) app can force `GithubSyncJob`s, forged commit statuses, and PR/review-stack state changes against stacks belonging to a completely different organization the attacker has no relationship with. This crosses a repository trust boundary reachable by an unauthenticated network attacker (no Shipit session, API token, or the target organization's secret is required), matching the "unauthorized deploy" / cross-repository-write impact class.

### Likelihood Explanation
Exploitability depends only on the target Shipit instance being configured with multiple GitHub organizations, at least one of which either has no `webhook_secret` set (a state the shipped example configuration itself demonstrates) or whose secret the attacker can otherwise obtain independent of the target org. No interaction with the target organization's own webhook secret is needed, since the vulnerable code path lets the attacker choose *which* organization's app validates the request via the `repository.owner.login` field, decoupled entirely from which repository is acted upon.

### Recommendation
In `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`, derive the repository/organization used both for signature verification and for resolving the acted-upon `Repository`/`Stack` from the *same* trusted field, and reject the webhook if `repository.owner.login` does not match the owner encoded in `repository.full_name`. Alternatively, pass the verified organization from the controller into each handler and have `Handler#stacks`/`#repository_name` scope lookups to that verified organization only.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (no `webhook_secret`) and `OrgB` (with a stack for `OrgB/private-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/private-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler#process` resolves the target via `repository.full_name`, finds the `OrgB/private-repo` stacks, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — despite the request never being authenticated against `OrgB`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
