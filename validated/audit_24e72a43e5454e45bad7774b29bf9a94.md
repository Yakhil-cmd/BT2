### Title
CCMenuController bypasses ApiClient stack-scoping, letting a token authorized for one stack read the CI/deploy status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` restricts stack lookups to the set of stacks an `ApiClient` token is authorized for, but `Api::CCMenuController` overrides that lookup with an unscoped query, breaking the binding "the stack a token authorizes == the stack a request can touch."

### Finding Description
`Api::BaseController#stacks` and `#stack` implement the intended trust boundary: if an `ApiClient` is scoped to a specific stack (`stack_id?` true), lookups are limited to `Stack.where(id: current_api_client.stack_id)`, otherwise all stacks are visible: [1](#0-0) 

`Api::CCMenuController`, however, redefines `stack` to query `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `stacks` scoping method (and thus `current_api_client.stack_id?`): [2](#0-1) 

The controller still authenticates the request and enforces the `read:stack` permission scope via `require_permission :read, :stack`: [3](#0-2) 

but `require_permission!` only checks that the token has the generic `read:stack` permission string — it never re-validates the specific stack ID against `current_api_client.stack_id`: [4](#0-3) 

So a token that was created scoped to Stack A (`ApiClient#stack_id` = A, meant to only ever see Stack A per the `stacks` scoping contract used everywhere else in the API) can be used against `CCMenuController#show` with `stack_id` in the URL pointing at Stack B, and the controller will happily resolve and render Stack B's data because it never consults `current_api_client.stack_id`.

### Impact Explanation
This breaks the authorization binding "stack a token authorizes vs stack it touches." A stack-scoped API token — intentionally narrowed by an administrator so it can only interact with one stack — can be used to read another stack's deploy/CI status (last build status, last build label/time, running state) via the CCMenu XML endpoint. This is an unauthorized cross-stack read of stack state that the scoping mechanism was explicitly designed to prevent.

### Likelihood Explanation
Exploitation requires only possession of a valid, but narrowly-scoped, `ApiClient` authentication token (obtainable via the normal CCMenu query-string or Basic-Auth flow already supported by this controller) and knowledge/guessing of another stack's `to_param` (owner/name/environment), which is not secret. No privileged access or additional social engineering is needed beyond having a legitimately-issued restricted token — exactly the population of users this scoping feature is meant to constrain.

### Recommendation
Have `Api::CCMenuController#stack` reuse the base `stacks` (scoped) collection instead of an unscoped `Stack.from_param!`, e.g. `stacks.from_param!(params[:stack_id])`, so stack-scoped tokens cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. As an admin, create an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (a stack-scoped token).
2. Obtain its `authentication_token` (via `ApiClient#authentication_token`).
3. Send `GET /api/<stack_B_owner>/<stack_B_name>/<stack_B_env>/ccmenu.xml?token=<token>` (or via Basic Auth) where `stack_id` param refers to Stack B, not Stack A.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, ignores the client's `stack_id` restriction, and returns Stack B's CI/build status in the XML response — despite the token only being authorized for Stack A.
