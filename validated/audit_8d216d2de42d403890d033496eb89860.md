After thorough analysis of the Kaia bridge contracts, I found a native analog to the reported bug class.

---

### Title
Unchecked ERC721 `transferFrom` Return in `requestERC721Transfer` Allows Unauthorized Cross-Chain Token Claim — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

### Summary

`BridgeTransferERC721.requestERC721Transfer` calls `IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId)` without any revert-or-return-value guard. If the registered ERC721 token does not revert on a failed transfer (e.g., a non-standard token that silently no-ops), the bridge emits a `RequestValueTransferEncoded` event and increments `requestNonce` even though no token was actually deposited. The counterpart bridge operators then process that event and deliver a real token to the attacker on the other chain.

### Finding Description

`BridgeTransferERC20` correctly imports and applies `SafeERC20`:

```solidity
// BridgeTransferERC20.sol L22, L29, L133
import "../../libs/openzeppelin-contracts-v2/contracts/token/ERC20/SafeERC20.sol";
using SafeERC20 for IERC20;
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
``` [1](#0-0) [2](#0-1) 

`BridgeTransferERC721` has no equivalent protection. The deposit path is:

```solidity
// BridgeTransferERC721.sol L128-131
function requestERC721Transfer(...) public {
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId); // ← bare call, no revert check
    _requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
}
``` [3](#0-2) 

`_requestERC721Transfer` then unconditionally emits the cross-chain event and increments `requestNonce`:

```solidity
// BridgeTransferERC721.sol L93-105
emit RequestValueTransferEncoded(..., requestNonce, ...);
requestNonce++;
``` [4](#0-3) 

The same bare `transferFrom` appears on the withdrawal side of `handleERC721Transfer` (non-mint-burn mode), where the nonce and handled-request state are committed **before** the transfer executes:

```solidity
// BridgeTransferERC721.sol L49-70
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);
// state already mutated ↑
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId); // ← bare call
``` [5](#0-4) 

### Impact Explanation

**Deposit side (`requestERC721Transfer`, non-mint-burn mode):** An attacker calls `requestERC721Transfer` with a registered non-reverting ERC721 token they do not own or have not approved. The `transferFrom` silently no-ops; the bridge emits `RequestValueTransferEncoded` and increments `requestNonce`. Bridge operators on the counterpart chain observe the event and call `handleERC721Transfer`, which transfers a real token from the counterpart bridge's liquidity pool to the attacker. The attacker receives a bridged ERC721 without depositing anything, draining the counterpart bridge's token holdings.

**Withdrawal side (`handleERC721Transfer`, non-mint-burn mode):** If the token's `transferFrom` silently fails, the nonce and `handleNoncesToBlockNums` state are permanently consumed but the recipient never receives the token — a permanent loss of the bridged asset.

### Likelihood Explanation

- `requestERC721Transfer` is `public` with no access control; any address can call it.
- The token must be registered by the bridge owner (`onlyRegisteredToken`), which limits the attack surface to tokens the owner has whitelisted.
- Non-standard ERC721 tokens that do not revert on failed `transferFrom` are uncommon but exist (custom game tokens, early NFT contracts, tokens with optional-revert patterns).
- In mint-burn mode the deposit attack is blocked because `ERC721Burnable.burn` reverts when the bridge does not own the token; the vulnerability is specific to non-mint-burn deployments. [6](#0-5) 

### Recommendation

Mirror the ERC20 bridge's `SafeERC20` pattern for ERC721. Use `safeTransferFrom` (which checks `onERC721Received` and reverts on failure) instead of bare `transferFrom` in both `requestERC721Transfer` and `handleERC721Transfer`:

```solidity
// deposit
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);

// withdrawal
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

`safeTransferFrom` in the OpenZeppelin ERC721 implementation always reverts on failure, eliminating the silent-no-op risk. [7](#0-6) 

### Proof of Concept

1. Bridge owner registers a non-standard ERC721 token `T` whose `transferFrom` does not revert on failure (e.g., returns silently when the caller is not approved).
2. Attacker calls `Bridge.requestERC721Transfer(T, attacker, tokenId, "")` without owning or approving `tokenId`.
3. `T.transferFrom(attacker, bridge, tokenId)` silently no-ops; the bridge does not receive the token.
4. `_requestERC721Transfer` emits `RequestValueTransferEncoded(ERC721, attacker, attacker, T, tokenId, requestNonce, ...)` and increments `requestNonce`.
5. Counterpart bridge operators observe the event and call `handleERC721Transfer` on the counterpart chain.
6. Counterpart bridge executes `IERC721(ctT).transferFrom(address(this), attacker, tokenId)`, transferring a real counterpart token from the bridge's holdings to the attacker.
7. Attacker has received a bridged ERC721 token without depositing anything; repeated calls drain the counterpart bridge's entire ERC721 liquidity. [3](#0-2) [8](#0-7)

    function safeTransferFrom(address from, address to, uint256 tokenId) public {

    }

    /**
     * @dev Safely transfers the ownership of a given token ID to another address
     * If the target address is a contract, it must implement `onERC721Received`,
     * which is called upon a safe transfer, and return the magic value
     * `bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))`; otherwise,
     * the transfer is reverted.
     * Requires the msg.sender to be the owner, approved, or operator
     * @param from current owner of the token
     * @param to address to receive the ownership of the given token ID
     * @param tokenId uint256 ID of the token to be transferred
     * @param _data bytes data to send along with a safe transfer check
     */
    function safeTransferFrom(address from, address to, uint256 tokenId, bytes memory _data) public {
        transferFrom(from, to, tokenId);
        require(_checkOnERC721Received(from, to, tokenId, _data), "ERC721: transfer to non ERC721Receiver implementer");
    }
