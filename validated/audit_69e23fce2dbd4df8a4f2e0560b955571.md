### Title
Cross-organization stack/commit hijack via `check_suite` webhook `repository.full_name` mismatch with signature-verified `repository.owner.login` - (File: `app/models/shipit/webhooks/handlers/handler.rb`, `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `payload.dig('repository','owner','login')` (falling back to `payload.dig('organization','login')`). `Handler#stacks` independently resolves the target repository from `payload.dig('repository','full_name')`. These two fields are never cross-checked, so an attacker who only knows organization A's `webhook_secret` can sign a request whose `repository.owner.login` is `"orgA"` while `repository.full_name` is `"orgB/some-repo"`.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`repository_owner` (used to pick the `webhook_secret` in `WebhooksController#verify_signature`) MUST equal the owner encoded in `repository.full_name` (used by `Handler#stacks` / `Repository.from_github_repo_name`) — but nothing enforces `payload['repository']['owner']['login'] == payload['repository']['full_name'].split('/').first`.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the raw body against `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 
- `Handler#stacks` (base class used by `CheckSuiteHandler`) resolves the target repository from a completely different field, `payload.dig('repository','full_name')`, via `Repository.from_github_repo_name`, which just splits the string on `/` and does a `find_by(owner:, name:)`. [2](#0-1) [3](#0-2) 
- `CheckSuiteHandler#process` then uses that mis-scoped `stacks` relation to filter by `head_branch` and calls `schedule_refresh_check_runs!` on matching commits by `head_sha`. [4](#0-3) 

Attacker request: an unprivileged owner of organization A's own repo/app installation crafts a `check_suite` payload with `repository.owner.login = "orgA"` (or an `organization.login = "orgA"` sub-object, satisfying the owner fallback) and signs it with org A's `webhook_secret` (which they legitimately possess for their own org's app). They set `repository.full_name = "orgB/target-repo"`, `check_suite.head_branch` to org B's tracked branch, and `check_suite.head_sha` to a real commit SHA of org B's stack. `verify_signature` authenticates the request (org A's secret matches org A's owner field), but `stacks` resolves against `orgB/target-repo`, and `schedule_refresh_check_runs!` is invoked for org B's commit — a job that will hit GitHub's API using Shipit's org-B-scoped installation token/actor context, triggered entirely by an org-A-authenticated request.

None of the existing guards catch this: `verify_signature` only checks the HMAC against whatever `repository_owner` the attacker chooses to declare, not against `repository.full_name`; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `CheckSuiteHandler` only requires `head_sha`/`head_branch` inside `check_suite`, with no repository-consistency validation; and `Repository.from_github_repo_name` performs no ownership/authorization check tying the resolved repository back to the signature-verified organization.

### Impact Explanation
An unauthenticated-for-org-B attacker can cause Shipit to enqueue `RefreshCheckRunsJob`/GitHub API work (`schedule_refresh_check_runs!`) against an arbitrary tracked commit belonging to a different organization/repository than the one whose secret was used to authenticate the request. This is a payload for one repository (org A) mutating/triggering action on another organization's stack and commit (org B) — matching the "payload for one repository mutating another's stack, commit, task" Critical impact category. It is repeatable against any repository/branch/commit combination the attacker can guess or observe (e.g. public commit SHAs), for any organization configured in Shipit's multi-org `github` config, as long as the attacker controls at least one org's `webhook_secret` (their own).

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub organizations (the documented "Using Multiple Github Applications" mode) so that a `webhook_secret` legitimately known to an attacker (their own org's) differs from the secret protecting the target org B. The attacker's cost is just sending one crafted, self-signed HTTP POST to `/webhooks` — no session, no API token, no GitHub App key. Feasibility is high: `repository.owner.login`/`organization.login` and `repository.full_name` are both attacker-controlled JSON fields, and the only requirement is guessing/knowing an existing branch name and commit SHA tracked by Shipit for org B's stack (obtainable from public GitHub repos or Shipit's own public stack pages).

### Recommendation
In `Handler#stacks` (or in `WebhooksController`), derive the target repository consistently with the field used for signature verification — i.e., validate that `payload.dig('repository','full_name')` starts with the same owner as `repository_owner` (`payload.dig('repository','owner','login')` / `organization.login`) before resolving `Repository.from_github_repo_name`, rejecting the event (or scoping `Repository.from_github_repo_name` lookup) if they diverge. Ideally, pass the already-verified `repository_owner` into the handler and have `stacks` cross-check it against the owner embedded in `full_name`.

### Proof of Concept
Minitest plan (e.g. in `test/models/shipit/webhooks/handlers/check_suite_handler_test.rb`, illustrative — actual file is under `test/`, out of scope to write here but described for the fix's validation):
1. Configure `Shipit.github` with two orgs, `orga` and `orgb`, each with distinct `webhook_secret`s.
2. Create `Repository` `orgb/target-repo` with a `Stack` on branch `master`, and a `Commit` with a known `sha`.
3. Build a `check_suite` JSON payload: `repository.owner.login = "orga"`, `repository.full_name = "orgb/target-repo"`, `check_suite.head_branch = "master"`, `check_suite.head_sha = <that commit's sha>`.
4. Sign the raw body with `orga`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: check_suite` and the resulting `X-Hub-Signature`.
5. Assert response is `:ok` (signature accepted under org A) AND assert `schedule_refresh_check_runs!` (or `RefreshCheckRunsJob`) was enqueued/invoked for org B's commit — i.e. `assert_enqueued_with(job: RefreshCheckRunsJob, args: [commit_id: orgb_commit.id])`, proving org A's credentials triggered action on org B's commit.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
