## Title
Cross-chain replay of `offer_signer_capability()` due to missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` — (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`account.move` defines two off-chain signed "proof challenge" structs used to authorize delegation of account capabilities: `RotationCapabilityOfferProofChallengeV2` and `SignerCapabilityOfferProofChallengeV2`. The rotation-capability variant was explicitly hardened by adding a `chain_id` field, with an inline comment stating this "prevents replaying the challenge message" [1](#0-0) . The signer-capability variant, `SignerCapabilityOfferProofChallengeV2`, was never given the same fix and still contains only `sequence_number`, `source_address`, and `recipient_address` [2](#0-1) .

### Finding Description
`offer_signer_capability()` builds this struct and verifies the caller-supplied signature against it via `verify_signed_message`, without any chain-id binding: [3](#0-2) 

Compare this to the sibling function `offer_rotation_capability()`, which builds `RotationCapabilityOfferProofChallengeV2` and explicitly includes `chain_id: chain_id::get()` in the signed struct: [4](#0-3) 

Because Aptos account addresses are derived from public keys deterministically and independently of `chain_id`, the same account (same address, same auth key, same or predictable `sequence_number`) commonly exists on multiple networks (e.g., devnet/testnet/mainnet, or two mainnet-compatible chains sharing genesis tooling). A signature over `SignerCapabilityOfferProofChallengeV2 { sequence_number, source_address, recipient_address }` is valid on any chain where these three fields match — there is no domain separator tying the signature to a specific network. This is the exact bug class from the external report: a signed authorization message lacking `chain_id` can be replayed on a different chain to re-apply an action the user only intended for one chain.

### Impact Explanation
An attacker who observes/obtains a `SignerCapabilityOfferProofChallengeV2` signature that a user generated to offer signer capability to a specific `recipient_address` on one chain can replay that exact signature via `offer_signer_capability()` on a different chain where the source account happens to exist with the same authentication key and sequence number. This grants the same `SignerCapability` delegation on the unintended chain. Since `SignerCapability` allows the holder to obtain a `signer` for the source account (used broadly for resource-account-style control in Move), an attacker-controlled or unintended `recipient_address` gaining this on a chain the user never intended is a high-impact account-takeover-adjacent primitive — a wrong-signer-set / wrong-chain-context admission failure at the exact class described in the Admission Impact Gate ("Authenticator ... or approval validation accepting the wrong signing material or wrong approval set" / "Replay ... chain-id ... binding failure that lets an attacker reuse or rebind a transaction").

### Likelihood Explanation
The `RotationCapabilityOfferProofChallengeV2` fix — adding `chain_id` with an explicit comment about preventing replay — is strong internal evidence that the Aptos team already recognized this exact bug class for capability-offer proof challenges, but the fix was not mirrored onto `SignerCapabilityOfferProofChallengeV2`. This makes the vulnerability a real, provable local inconsistency rather than a purely theoretical one. The precondition (same account existing at the same address, same auth key, matching sequence number on two networks) is realistic for freshly created/low-activity accounts and multi-network deployments common in the Aptos ecosystem (e.g., testnet vs. mainnet address reuse, or forked chains).

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2`, populate it with `chain_id::get()` in `offer_signer_capability()`, and bump/migrate the struct akin to how `RotationCapabilityOfferProofChallengeV2` was versioned, ensuring old off-chain-signed challenges without chain binding are rejected.

### Proof of Concept
1. Alice owns account `A` at address `addr_A` with public key `pk_A`, existing identically (same address/auth key/sequence_number = 0) on both Chain 1 and Chain 2 (e.g., two Aptos-compatible networks or before/after a fork).
2. Alice signs `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: addr_A, recipient_address: bob_addr }` intending to authorize `offer_signer_capability` only on Chain 1 (e.g., a testnet dApp flow).
3. An attacker captures this signature (e.g., from a public testnet transaction, mempool, or a dApp backend) and submits a transaction calling `offer_signer_capability(alice, sig_bytes, ED25519_SCHEME, pk_A, bob_addr)` on Chain 2.
4. Because the challenge struct has no `chain_id`, `assert_valid_rotation_proof_signature_and_get_auth_key`-equivalent verification in `verify_signed_message` (via `ed25519::signature_verify_strict_t`) succeeds identically on Chain 2, and `account_resource.signer_capability_offer.for` is set to `bob_addr` on Chain 2 as well — even though Alice never intended this delegation there.

Note: I was not able to locate/verify the exact body of `verify_signed_message` in the indexed portion of `account.move` (only its call site and the analogous inline ed25519/multi-ed25519 verification block for `RotationCapabilityOfferProofChallengeV2` were retrievable) [5](#0-4) . If it were confirmed that `verify_signed_message` independently mixes in a chain-bound domain separator, this finding would not hold; based on available evidence (the struct definition itself lacking `chain_id`, and the explicit contrast with `RotationCapabilityOfferProofChallengeV2`), the vulnerability appears real. A Devin session with full repo access should confirm `verify_signed_message`'s implementation before treating this as fully confirmed.

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
