Based on the investigation, I found a concrete analog vulnerability. It doesn't map to a rate-limiting bug directly, but the report's underlying theme — "the API accepts requests without an integrity check" — maps to a real broken trust binding in the webhook signature verification path.

### Title
Webhook signature verification silently no-ops when `webhook_secret` is unset, letting unauthenticated payloads add arbitrary users to `Shipit.github_teams` - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the resolved organization, and `WebhooksController#verify_signature` selects that organization purely from attacker-supplied JSON fields (`repository.owner.login` / `organization.login`) in the unauthenticated request body. This breaks the binding "GitHub identity that authenticated the webhook delivery = entity the handler mutates," because when no secret is configured the "authentication" step performs no cryptographic check at all, yet `MembershipHandler` still executes privileged writes (team creation/membership) directly from that same self-reported, unauthenticated payload.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/secret to validate against solely from the incoming body: [1](#0-0) [2](#0-1) 

The actual verification is delegated to `GitHubApp#verify_webhook_signature`, which is a no-op when the org has no `webhook_secret` configured: [3](#0-2) 

`docs/setup.md` explicitly documents the webhook secret as optional ("Webhook secret (optional): Fill it with some randomly generated string...") [4](#0-3) , and the shipped `config/secrets.development.example.yml` template ships with `webhook_secret:` left blank [5](#0-4) , so this is a first-class, engine-endorsed configuration state, not a misuse of the host application.

Once verification passes (or is skipped), `WebhooksController#create` dispatches the raw, self-reported JSON straight to registered handlers with no further identity check: [6](#0-5) 

`MembershipHandler#process` trusts `params.team`, `params.organization.login`, and `params.member.login` from that same unauthenticated payload to create a `Team` record (if unknown) and add/remove any GitHub-resolvable login as a member: [7](#0-6) 

`Team` membership is exactly the trust anchor `Authentication#force_github_authentication`/`User#authorized?` rely on to gate access to the whole application: [8](#0-7) [9](#0-8) 

So the binding being violated is: **"organization that authenticated the webhook delivery" (nothing, when `webhook_secret` is blank) ≠ "entity whose team-membership state the handler writes" (arbitrary, attacker-chosen via `params.team`/`params.member.login`)**. Before the attacker's request, membership state reflects genuine GitHub org membership; after it, an attacker with zero credentials (no session, no `ApiClient` token, no `webhook_secret`, no GitHub App key, no repository access) can insert themselves into any `Shipit.github_teams`-gated team already known to Shipit (`Team.find_or_create_by!(github_id: params.team.id)` — reusing an existing team's `github_id` is sufficient; the member login is resolved live via `Shipit.github.api.user(login)`, so any real GitHub login works).

### Impact Explanation
This is escalation into `Shipit.github_teams` authorization: an attacker who is not a member of any authorized team can add an account they control to a team that gates the entire authentication concern, bypassing `User#authorized?`. Once in an authorized team, the attacker's `github_access_token`-based session unlocks stack browsing, deploy triggering, lock/unlock, and any other UI action reserved for authorized users — this is a listed High-impact category ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Likelihood is high specifically in deployments that leave `webhook_secret` unset, which the engine's own setup docs and example config present as an acceptable, supported configuration [4](#0-3) . In that state, the `/webhooks` endpoint is public (`ActionController::Base`, no Shipit session or `ApiClient` auth), so exploitation requires only network access.

### Recommendation
- Do not treat a missing `webhook_secret` as "verification passed." Require a secret to be configured before accepting any webhook write, or explicitly gate privileged handlers (especially `MembershipHandler`) behind a mandatory signature check independent of per-org optional configuration.
- Cross-validate that the organization used to select the verifying secret (`repository_owner`) is the same organization the handler subsequently mutates, rather than trusting the raw JSON body twice for two different purposes.

### Proof of Concept
1. Configure Shipit with a GitHub App for `orgA` but leave `webhook_secret` blank (as `config/secrets.development.example.yml` ships by default).
2. Send an unauthenticated `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <existing Shipit.github_teams team's github_id>, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "orgA" },
  "member": { "login": "<attacker-controlled-github-login>" }
}
```
3. `verify_webhook_signature` returns `true` (no secret configured), `MembershipHandler` runs, and the attacker's GitHub login is added to the `Team` record backing `Shipit.github_teams`.
4. Attacker completes GitHub OAuth login; `User#authorized?` now returns `true` for them, granting access to the Shipit application.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
