### Title
Webhook signature verification is keyed to `repository.owner.login` while handlers act on the unverified `repository.full_name` / `sha` fields, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization GitHub App configuration, `WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to validate the inbound signature against using `repository.owner.login` (or `organization.login`) taken straight from the unauthenticated JSON body. Once that specific check passes, every webhook handler (`PushHandler`, `StatusHandler`, etc.) acts on **different** fields of the same attacker-controlled body — `repository.full_name` and `sha` — without ever confirming they belong to the organization whose secret was used to authenticate the request. An attacker who can produce a valid signature for *any one* configured organization (including one with no `webhook_secret` set, which is an explicitly supported configuration) can forge a payload naming an entirely different, unrelated tracked repository/commit and have Shipit act on it.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is derived purely from the request body, not from any authenticated source: [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config block from `secrets.github` and, critically, `GitHubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` as automatically valid: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

This multi-organization schema, with `webhook_secret` explicitly optional/nil per org, is a documented and supported configuration: [4](#0-3) 

Once `verify_signature` passes (using whichever org's secret matched `repository.owner.login`), the actual handlers key off completely independent fields to decide what to modify:

- `Handler#stacks`/`#repository_name` resolves the target `Repository` via `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

- `PushHandler#process` triggers `stack.sync_github` for every not-archived stack on that branch: [6](#0-5) 

- `StatusHandler#process` is even more direct: it looks up commits **globally by `sha` with no repository/org scoping at all** and writes the state, description, target_url and context straight from the payload: [7](#0-6) 

The binding that should hold is:
`organization whose secret authenticated the request (repository.owner.login / organization.login)` == `organization/repository the handler is permitted to mutate (repository.full_name, sha's owning repository)`.

Because the JSON body is entirely attacker-supplied prior to any authentication decision, nothing forces these two to refer to the same repository. An attacker can set `repository.owner.login` to an organization configured with no (or a known/leaked) `webhook_secret`, while setting `repository.full_name` (for push-type events) or `sha` (for status events, which isn't even scoped by repository) to a target belonging to an entirely different, unrelated organization tracked by the same Shipit instance.

### Impact Explanation
This breaks repository isolation in a multi-tenant Shipit deployment (multiple GitHub orgs sharing one instance, as explicitly documented in `config/secrets.development.shopify.yml` and `docs/setup.md`). The most severe consequence is via `StatusHandler`: an attacker can inject a forged `success` (or any) `Status` for an arbitrary existing commit SHA in a target stack they do not control, with no repository/org check whatsoever (`Commit.where(sha: params.sha)` is unscoped). Since Shipit's deploy safety checks (`Commit#deployable?`, required/blocking statuses) are ultimately driven by `Status` rows, this can be leveraged to make an otherwise-failing or unreviewed commit appear deployable, resulting in an unauthorized deploy of another organization's stack — a cross-repository/cross-organization write with deploy-integrity impact. `PushHandler` similarly allows forcing `GithubSyncJob`/`sync_github` for an unrelated stack.

### Likelihood Explanation
Exploitability depends entirely on the deployment being configured with the multi-organization `github:` schema and at least one configured organization having a blank/no `webhook_secret` (an explicitly supported and documented option) or a secret otherwise known to the attacker (e.g., leaked, or belonging to a less-trusted org onboarded to the same instance). No GitHub App private key, no `ApiClient` token, no Shipit session, and no repository write access are required — only the ability to send an HTTP POST to `/webhooks` with a crafted `X-Github-Event` and JSON body, and a valid signature for any one weakly-configured tenant org.

### Recommendation
Verify that the field(s) used to select the authenticating secret (`repository.owner.login` / `organization.login`) are consistent with the field(s) the handler subsequently acts on (`repository.full_name`'s owner segment, and the repository owning any `sha` looked up). Concretely:
- In `StatusHandler`, scope the `Commit` lookup by the stack's repository (derived from the same verified `repository.full_name`), not a bare global `sha` lookup.
- In `WebhooksController`/`Handler`, after signature verification, assert that `repository.full_name`'s owner matches the `repository_owner` used to select the webhook secret before dispatching to handlers.
- Do not treat a blank `webhook_secret` as "always verified" for multi-organization configurations; require an explicit secret per tenant org, or reject unsigned payloads outright when running in multi-org mode.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, e.g. `org-a` (no `webhook_secret` set) and `org-b` (tracked stack/repository the attacker wants to target).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # accepted: org-a has no webhook_secret, GitHubApp#verify_webhook_signature returns true unconditionally
{
  "repository": { "owner": { "login": "org-a" } },
  "sha": "<sha of a commit belonging to org-b's tracked stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, calls `Shipit.github(organization: "org-a").verify_webhook_signature(...)`, which returns `true` because `org-a` has no configured `webhook_secret` ( [8](#0-7) ).
4. `StatusHandler#process` then runs `Commit.where(sha: params.sha)` — matching the org-b commit regardless of `repository.owner.login` — and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto org-b's commit ( [7](#0-6) ).
5. This forged status can satisfy `required_statuses`/`deployable?` checks on org-b's stack, enabling deploys that should not have been allowed.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
