### Title
Rollover in `register-for-bond` fails to decrement old bond's `protocol-bonds-total-staked`, double-counting staked sats across two bonds - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond`'s rollover path adds the new bond's `sats-total` to `protocol-bonds-total-staked` for the new `bond-index` while never subtracting the old bond's `amount-sats` from the old `bond-index`'s entry, and the old bond's `protocol-bond-memberships` entry is overwritten (not decremented from its own total) only via `map-set` at the end of the function. The code's own inline comment confirms this is deliberate: the old bond's per-cycle shares are not torn down on rollover.

### Finding Description
The equality that should hold is: for each `bond-index`, `protocol-bonds-total-staked[bond-index] == sum of amount-sats over all principals whose protocol-bond-memberships entry currently points at bond-index`.

In `register-for-bond` (stackslib/src/chainstate/stacks/boot/pox-5.clar:642-841):
- `current-total-staked` is read for the **new** bond's first-reward-cycle via `get-total-shares-staked-for-cycle` (line 704).
- `old-sbtc` is computed from `get-staker-custodied-sbtc tx-sender`, and `roll-sbtc tx-sender old-sbtc new-sbtc` (line 784) moves only the *net difference* of sBTC — this only manages the sBTC custody balance, not the bond bookkeeping maps.
- `protocol-bond-memberships` for `tx-sender` is overwritten via `map-set` (lines 786-792) to point at the new `bond-index`, which implicitly "deletes" the old bond's membership record for that staker (the map is keyed by `principal`, so there is only ever one entry per staker).
- `protocol-bonds-total-staked` is only updated for the **new** bond (`(+ current-total-staked sats-total)`, lines 793-795) — there is no corresponding decrement of the **old** bond's `protocol-bonds-total-staked` entry.
- The comment at lines 796-798 explicitly states this is intentional: *"A roll-over from an ending bond ADDS the new bond's shares but does NOT tear down the old bond's per-cycle shares/delegation (unlike `update-bond-registration`, which removes then re-adds)."*

Because `verify-bond-rollover-window` only gates on *when* the rollover can occur (the L1 unlock window) and `bond-overlaps-new-position?` only rejects overlapping bond *terms* (not overlapping bookkeeping), neither guard causes the old bond's `protocol-bonds-total-staked` to be decremented. If any cycles for the old bond had not yet been "settled"/cleared independently of this map (e.g., if a reward-weight or signing-weight computation elsewhere reads `protocol-bonds-total-staked[old-bond-index]` for cycles where the staker's membership row has already been overwritten), the old bond's total-staked would still include the departed staker's `amount-sats`, while the new bond's total also includes it — double counting the same custodied value across two bond indices' totals.

I was not able to fully verify, within the available iterations, every downstream reader of `protocol-bonds-total-staked` (e.g., how `get-total-sbtc-staked-for-bond`, reward-distribution, or signing-weight logic consume this map, and whether some other decrement path exists elsewhere in the ~3500-line contract that reconciles this before/after prepare-phase). The explicit code comment strongly suggests the divergence is real and intentional-by-design rather than accidental, but I could not confirm whether this design choice is actually exploitable to double-count *reward payouts* (as opposed to just an internal accounting total that may not directly gate fund movement) without tracing `get-total-sbtc-staked-for-bond` and the reward-distribution functions that consume `protocol-bonds-total-staked`.

### Impact Explanation
If confirmed, this would allow the same custodied sBTC/STX to be counted in two different bonds' `protocol-bonds-total-staked` totals simultaneously, inflating the denominator/numerator used for reward-weight or signing-weight calculations for one or both bonds, which matches the "double-counting a commitment or reward" Critical category. However, without confirming how `protocol-bonds-total-staked` is consumed downstream (whether it directly gates STX/sBTC payout amounts, or is merely an informational/administrative counter), I cannot confirm the magnitude or exploitability of the impact.

### Likelihood Explanation
Preconditions: attacker must have an existing non-overlapping bond membership nearing its L1 unlock window, and call `register-for-bond` for a new bond during that window — both of which are ordinary, unprivileged actions available to any staker. If the divergence is real and consumed by reward logic, it would be repeatable per rollover.

### Recommendation
On rollover, explicitly decrement `protocol-bonds-total-staked` for the old `bond-index` by the old membership's `amount-sats` (and correspondingly reconcile any old per-cycle signer-delegation entries), mirroring what `update-bond-registration` already does when it "removes then re-adds." Add a Clarity/Rust invariant test that sums `protocol-bonds-total-staked` across bonds against the sum of `amount-sats` in `protocol-bond-memberships` after a rollover and asserts equality.

### Proof of Concept
1. Set up two non-overlapping protocol bonds (`bond-index` A and B, B's first cycle ≥ A's end cycle) via `setup-bond`, allowlisting the same staker for both.
2. Staker calls `register-for-bond` for bond A with `sats-total = X` sBTC; assert `protocol-bonds-total-staked[A] == X`.
3. Advance to A's L1 unlock window (per `verify-bond-rollover-window`).
4. Staker calls `register-for-bond` for bond B with `sats-total = Y`, rolling over from A.
5. Assert `protocol-bond-memberships[staker].bond-index == B` (A's per-staker record is gone).
6. Assert `protocol-bonds-total-staked[A]` and `protocol-bonds-total-staked[B]` — if `protocol-bonds-total-staked[A]` still equals `X` (not decremented) while `protocol-bonds-total-staked[B] == Y`, and no other staker is in A, the sum `X + Y` exceeds the actual singular custodied sBTC amount reconciled via `get-total-sbtc-staked-for-bond`, demonstrating the double count. **Note: I was unable to trace `get-total-sbtc-staked-for-bond`'s exact definition or confirm which downstream reward computation consumes `protocol-bonds-total-staked[A]` for already-vacated stakers, so this PoC should be run against the actual contract to confirm real fund/reward impact before treating this as fully confirmed.**
