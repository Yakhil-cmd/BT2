### Title
PR-label-derived environment variables silently override control variables (e.g. `GIT_SSH_COMMAND`) in `TaskCommands#env`/`RollbackCommands`, causing silent rollback no-ops - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` converts every pull-request label name into an environment variable (`"#{LABEL}" => "true"`) with no allowlist, and this hash is merged unfiltered into `TaskCommands#env`/`RollbackCommands#env`, which is passed straight to `Command.new(..., env:, ...)` and ultimately `PTY.spawn`. An attacker who can attach a label such as `GIT_SSH_COMMAND` to the pull request backing a review stack can force any git subprocess spawned by a rollback (or deploy) step to use `GIT_SSH_COMMAND=true`, making git's ssh invocation a no-op that always exits `0`.

### Finding Description
The intended binding is: `GIT_SSH_COMMAND` seen by the git subprocess `Command#start` spawns == the ssh command the Shipit operator configured (normally absent/real `ssh`). This binding is broken because `ReviewStack#env` unconditionally maps every PR label into an env-var override: [1](#0-0) 

That `env` is `Stack#env`, which flows into `StackCommands#env` and `TaskCommands#env` via unconditional merges: [2](#0-1) 

`RollbackCommands` inherits `env` from `DeployCommands`/`TaskCommands` and only adds `'ROLLBACK' => '1'`: [3](#0-2) 

`TaskCommands#perform` builds each rollback step as `Command.new(command_line, env:, chdir:)`, and `Command#start` passes `@env` (after `.stringify_keys`) directly to `PTY.spawn`: [4](#0-3) [5](#0-4) 

Labels reach the stack via `LabelCapturingHandler#capture_labels`, which persists `params.pull_request.labels` verbatim onto `stack.pull_request.labels` with no name filtering: [6](#0-5) 

**Why existing guards don't stop this:** the only allowlist mechanism in this codebase, `EnvironmentVariables#permit` / `filter_rollback_envs`, is applied solely to the explicit, user-supplied `env` parameter accepted by `RollbacksController#create` (`rollback_params[:env]` limited to `@stack.rollback_variables`): [7](#0-6) 

It is never applied to `@stack.env`/label-derived variables, so a label name can inject any key, including control variables consumed by git (`GIT_SSH_COMMAND`, also `GIT_ASKPASS`) or the shell, into the exact env hash used to spawn rollback/deploy commands. `verify_signature`/`GitHubApp#verify_webhook_signature` are irrelevant here because the label event is a legitimately-signed GitHub webhook for a real PR action — no forgery is required.

**Exploit flow:** attacker opens/owns a PR that already has (or is eligible for, per the repository's provisioning behavior) an active `ReviewStack` → attacker (or a collaborator able to label PRs in that flow) adds the label `GIT_SSH_COMMAND` → GitHub sends a legitimately-signed `labeled` webhook → `LabelCapturingHandler` persists the label → next rollback (operator-triggered or `continuous_deployment` auto-triggered) builds `RollbackCommands#env`, which contains `'GIT_SSH_COMMAND' => 'true'` → any rollback step invoking git over ssh silently no-ops and reports success.

### Impact Explanation
Any git-based operation (fetch/checkout/submodule update) executed as part of a rollback (or deploy) step for the affected review stack silently succeeds without doing real work, because `GIT_SSH_COMMAND=true` replaces the real ssh transport. This can cause Shipit to believe a rollback completed correctly while the stale/attacker-favored commit remains live — an unauthorized/incorrect deploy state for that stack. The blast radius is scoped to the stack whose pull request received the label (the review stack tied to that PR), but the same unfiltered mechanism also allows overriding other process-level variables consumed by the shell/git toolchain (e.g., `GIT_ASKPASS`), broadening the class of injectable control variables beyond just `GIT_SSH_COMMAND`.

### Likelihood Explanation
Preconditions: a review stack must be active for the PR (`deploy_spec.supports_rollback?` true, review stacks enabled with a provisioning behavior that creates/keeps a stack for the PR), and the actor must be able to attach the `GIT_SSH_COMMAND` label to that PR. No Shipit credentials, webhook secret, or API token are required — labeling happens on GitHub itself and produces a normally-signed webhook. Cost is a single GitHub label action; the effect persists on every subsequent rollback/deploy of that stack until the label is removed, making it trivially repeatable against any repository/PR where review stacks and rollback are enabled.

### Recommendation
Do not let pull-request labels (or any other operator/attacker-influenced free text) become environment variable keys that are merged unfiltered into command environments. In `ReviewStack#env`, restrict label-derived keys to an explicit allowlist (similar to `deploy_variables`/`rollback_variables` and `EnvironmentVariables#permit`), and additionally block/deny any key that collides with reserved/control variable names used by git or the shell (`GIT_SSH_COMMAND`, `GIT_ASKPASS`, `PATH`, `LD_PRELOAD`, `BUNDLE_*`, `RUBYOPT`, `GITHUB_TOKEN`, etc.), or merge label-derived env with lower precedence so it can never override reserved keys set by `Commands#base_env`/`TaskCommands#env`.

### Proof of Concept
Add a minitest under `test/lib/shipit/rollback_commands_test.rb` (or extend `test/lib/shipit/task_commands_test.rb`):

```ruby
test "#perform's rollback Command env inherits attacker-labeled GIT_SSH_COMMAND" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["GIT_SSH_COMMAND"]  # simulates LabelCapturingHandler#capture_labels
  rollback = stack.trigger_continuous_delivery # or build a Rollback fixture whose deploy_spec supports_rollback?

  commands = Shipit::RollbackCommands.new(rollback).perform

  spawned_env = commands.first.env
  assert_equal "true", spawned_env["GIT_SSH_COMMAND"],
    "expected label-derived value to have overridden the operator-configured ssh command (nil/absent)"
end
```

Both sides of the binding to assert:
- Expected (intended binding): `spawned_env["GIT_SSH_COMMAND"]` should be `nil`/absent (Shipit operator never configures a `GIT_SSH_COMMAND`, so real `ssh` is used).
- Actual (after label injection): `spawned_env["GIT_SSH_COMMAND"] == "true"`, proving the equality is broken and the git subprocess would silently no-op instead of invoking real ssh.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env

    end
