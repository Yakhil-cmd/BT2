### Title
Webhook Signature Verification Selects the Signing Organization From a Different Field Than the One Used to Locate the Target Repository/Stack — Cross-Organization Webhook Forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the request against using `repository.owner.login` (falling back to `organization.login`), while every webhook `Handler` locates the `Repository`/`Stack` to actually mutate using the unrelated `repository.full_name` field from the very same, attacker-controlled JSON body. Because the HMAC only proves "this body was signed with organization X's secret," and never binds `owner.login` to `full_name`, anyone who legitimately controls a webhook secret for *any* organization configured on the Shipit instance can forge events for *any other* repository/stack it manages.

### Finding Description
The verification flow is:
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`verify_webhook_signature` simply HMACs the raw body with the secret belonging to the organization selected above:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Once verification passes, every handler resolves the affected repository independently, from a *different* field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`repository.owner.login` (used to pick the signing key) and `repository.full_name` (used to pick the mutated repository/stack) are two independent, attacker-supplied JSON fields with no cross-check tying them together. Shipit explicitly supports multi-organization GitHub App configuration, each with its own `webhook_secret`, as shown in the packaged secrets templates: [5](#0-4) 

**Binding broken (equality that should hold but doesn't):**
`organization whose secret authenticated the signature (repository.owner.login)` == `repository/stack that is actually written to (repository.full_name)`.

Before the attacker's request: only events genuinely signed by organization X's real secret should be able to mutate stacks/repositories belonging to organization X.
After the attacker's request: an attacker who legitimately possesses (or knows) the webhook secret for organization A — e.g., because they registered their own GitHub App/org pointed at the same Shipit instance, a normal self-service configuration step, not a privileged Shipit credential — can compute a valid HMAC over a forged body where `repository.owner.login = "orgA"` (used only for key selection) but `repository.full_name = "victim-org/victim-repo"` (used for the actual write). The signature check passes (it's genuinely signed by orgA's secret), yet the handler dispatch operates on victim-org's stack.

This is separately compounded by `verify_webhook_signature` unconditionally returning `true` when an organization has no `webhook_secret` configured at all: [6](#0-5) 
— meaning any organization entry left without a secret (a state the setup docs treat as optional) provides an unauthenticated key-selection target as well.

### Impact Explanation
An attacker who controls a signing secret for *any one* organization served by the Shipit instance can forge `push`, `status`, `check_suite`, `pull_request`, or `membership` events against *any other* repository/stack managed by that instance. Depending on the handler this enables:
- Forged `status` events writing fake commit statuses used to gate CI/deploy readiness [7](#0-6) 
- Forged `push` events enqueuing `GithubSyncJob` with an attacker-chosen `expected_head_sha` for the victim stack
- Forged `pull_request` events archiving/unarchiving/provisioning review stacks belonging to the victim repository
- Forged `membership` events creating arbitrary teams/users

This constitutes cross-repository writes and can lead to an unauthorized deploy/rollback path (e.g., forged green commit status feeding a `continuous_deployment`-enabled stack), which falls under the Critical impact bucket for this engine.

### Likelihood Explanation
The prerequisite is that the Shipit deployment configures more than one GitHub organization (a documented, supported configuration) and that the attacker controls or can obtain the webhook secret for at least one of them — this is realistic in any multi-tenant/self-service Shipit deployment where organizations are onboarded independently, or in any deployment where at least one org config has a blank `webhook_secret` (explicitly called out as "optional" in the setup docs). No repository write access, GitHub App private key, Shipit session, or `ApiClient` token is required — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a body signed by a secret the attacker legitimately possesses for their own organization entry.

### Recommendation
Cross-check the organization/repository fields used for signature-key selection against the field(s) later used to resolve the target `Repository`/`Stack`, e.g., verify that `repository.full_name`'s owner segment matches `repository.owner.login` (or `organization.login`) before dispatching to handlers, and reject the request otherwise. Additionally, require every configured GitHub App entry to have a non-blank `webhook_secret` (removing the `return true unless webhook_secret` bypass), and/or verify the signature using the secret associated with the resolved target repository's actual owner rather than a value taken from the unauthenticated payload.

### Proof of Concept
1. Configure (or possess) a legitimate Shipit GitHub App entry for organization `attacker-org` with a known `webhook_secret`.
2. Craft a JSON body for a `status` (or `push`) event where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"` (a repository backing a real Stack on the target Shipit instance)
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` selects `attacker-org`'s app via `repository_owner` and successfully verifies the signature against the forged body.
6. `StatusHandler`/`PushHandler` resolves the target via `payload.dig('repository','full_name')` = `victim-org/victim-repo`, and creates/mutates state (commit status, sync job, etc.) for the victim's stack — all without ever possessing `victim-org`'s webhook secret.
