## Title
Missing reentrancy guard on `stake`/`stake-update`/`update-bond-registration` allows reentrant re-entry through an attacker-controlled signer-manager trait call before staking state is finalized - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s `stake`, `stake-update`, and `update-bond-registration` all invoke `signer-manager-validate-stake` — a `contract-call?` into a caller-supplied `<signer-manager-trait>` contract — *before* the functions finish writing `staker-info`, `protocol-bond-memberships`, per-cycle share maps, and (for `stake`) before `roll-sbtc`'s external `sbtc-token transfer` and `total-sbtc-staked` update [1](#0-0) . This is structurally the same bug class as BabylonCore's `participate`: an external call to attacker-controllable code happens ahead of state-changing effects that establish invariants (locked totals, membership uniqueness).

### Finding Description
`signer-manager` is a trait reference chosen by `tx-sender`, so its code is fully attacker-controlled — analogous to the ERC-721 receiver hook in the BabylonCore report. In `stake`, this call happens after some `asserts!`/`try!` checks but before `roll-sbtc` (which itself calls `sbtc-token transfer` and only afterwards updates `total-sbtc-staked`), before `add-staker-to-signer-cycles`, and before `map-set staker-info` [2](#0-1) . The same ordering appears in `stake-update` (`signer-manager-validate-stake` at L1117 precedes `remove-staker-from-cycles`, `add-staker-to-signer-cycles`, and `map-set staker-info`) [3](#0-2) , and in `update-bond-registration` (`signer-manager-validate-stake` at L884 precedes `settle-rewards`, `remove-staker-from-bond-cycles`/`add-staker-to-bond-cycles`, and `map-set protocol-bond-memberships`) [4](#0-3) .

Critically, the contract authors clearly recognize this exact reentrancy vector and added an explicit guard, `validate-no-reentrancy`, to `register-signer`, `unstake`, and `grant-signer-key` — all of which are annotated "ensure no reentrancy through signer-manager trait calls" [5](#0-4) . `stake`, `stake-update`, and `update-bond-registration` never call `validate-no-reentrancy` even though they are the very functions that call into the trait *before* their own critical state mutations, exactly the same code shape the guard was designed to protect. The CHANGELOG independently confirms this general concern: "revoking a grant... previously... leaving a deprecated or buggy manager free to keep accumulating delegated STX and re-enter the signer set" [6](#0-5) , showing the maintainers were actively hardening against signer-manager reentrancy elsewhere but the guard placement is inconsistent across the entry points that share this callback pattern.

### Impact Explanation
If reentrancy is reachable through `signer-manager-validate-stake` (e.g. a malicious signer-manager's callback re-enters `stake`/`stake-update` on the same `tx-sender` before the outer call's `map-set staker-info` / `add-staker-to-signer-cycles` / `roll-sbtc` totals commit), an attacker could re-enter to double-count the same locked STX or sBTC across cycle-membership maps (`staker-signer-cycle-memberships`, `signer-shares-staked-for-cycle`, `total-shares-staked-for-cycle`) or corrupt `total-sbtc-staked` relative to actual custodied sBTC, breaking the equality between STX/sBTC actually locked and the amount counted toward reward-cycle totals and signer weight — a double-counting/unbacked-reward-share condition (Critical, per the rules' "double-counting a commitment or reward").

### Likelihood Explanation
Exploitation requires only an unprivileged staker who deploys their own contract implementing `signer-manager-trait` (a normal, permissionless workflow already exercised throughout the reference `signer-manager.clar`/`test-pox-5-signer.clar` contracts) and calls `stake`/`stake-update`/`update-bond-registration` through it. No admin, miner, or other-user key is required — matching the in-scope "stacking action the staker/signer never authorised" criterion, since the double-write occurs entirely within one attacker-controlled transaction.

### Recommendation
Add `(try! (validate-no-reentrancy))` to `stake`, `stake-update`, and `update-bond-registration` immediately before the `signer-manager-validate-stake` call, consistent with `register-signer`, `unstake`, and `grant-signer-key`, so that the trait callback cannot re-enter any pox-5 stacking-state-mutating entry point before the outer call's maps/vars are committed.

### Proof of Concept
I was not able to fully verify reachability of actual reentrancy here (i.e., confirm within the available context that Clarity's `contract-call?` execution model permits a nested call back into `pox-5` from inside `signer-manager-validate-stake` to succeed rather than being blocked at the VM/consensus layer, and I could not locate/read the body of `signer-manager-validate-stake` or `validate-no-reentrancy` themselves in the indexed content). This is a structural code-shape match (attacker-controlled trait call preceding state commitment, with the developers' own comments/guard confirming the risk class) rather than a demonstrated end-to-end exploit trace. A definitive PoC would require reading `validate-no-reentrancy`'s implementation and `signer-manager-validate-stake`'s call graph in full, and constructing a signer-manager contract whose `validate-stake` callback calls back into `stake`/`stake-update` — recommend a Devin session with full repository access to confirm whether the guard's absence on these three entry points is actually exploitable or is otherwise mitigated (e.g., by Clarity's call-stack/asset-map semantics).

        ;; grant must still be active.
        (try! (verify-signer-key-grant signer
            (unwrap! (get-signer-info signer) ERR_SIGNER_NOT_FOUND)
        ))

        ;; the start-burn-ht must result in the next reward cycle, do not allow stakers
        ;;  to "post-date" their transaction
        (asserts! (is-eq first-reward-cycle specified-reward-cycle)
            ERR_INVALID_START_BURN_HEIGHT
        )

        ;;  lock period must be in acceptable range.
        (asserts! (check-pox-lock-period num-cycles) ERR_INVALID_NUM_CYCLES)

        ;; Cannot already be STX-only staking. Re-extending an existing stake
        ;; goes through `stake-update`, not a second `stake` call.
        (asserts! (is-none (get-staker-info tx-sender)) ERR_ALREADY_STAKED)

        ;; A roll-over from an existing bond is allowed when the bond's term
        ;; ends no later than this stake's first reward cycle. Already-active
        ;; bonds are rejected (overlap). Same shape as the
        ;; `register-for-bond` gate.
        (asserts!
            (not (bond-overlaps-new-position? existing-membership first-reward-cycle))
            ERR_ALREADY_STAKED
        )

        ;; A roll-over from an ending bond may only happen once that bond's
        ;; L1 collateral would have unlocked -- the same window an L1 bond
        ;; holder has to redirect their BTC. Keeps parity with the
        ;; `register-for-bond` gate so a bond's STX / sBTC can't be released
        ;; ahead of the bond's L1 unlock height.
        (try! (verify-bond-rollover-window existing-membership))

        ;;  the Staker must have sufficient total funds (locked + unlocked).
        ;;  On a roll-over the staker's STX is still locked by the ending
        ;;  bond; the node-side handler extends that lock to the new amount,
        ;;  so checking only `stx-get-balance` (unlocked) would falsely fail.
        (asserts! (>= total-balance amount-ustx) ERR_INSUFFICIENT_STX)

        ;; Refund any sBTC custodied for the rolled-over bond (zero-target
        ;; net transfer). No-op when there is no existing bond, or when the
        ;; existing bond is an L1 lock.
        (try! (roll-sbtc tx-sender old-sbtc u0))

        (try! (add-staker-to-signer-cycles tx-sender signer first-reward-cycle
            num-cycles amount-ustx true
        ))

        (map-set staker-info tx-sender {
            amount-ustx: amount-ustx,
            first-reward-cycle: first-reward-cycle,
            num-cycles: num-cycles,
            signer: signer,
        })

        ;; If this was a roll-over from a bond, clear the bond membership so
        ;; `unstake-sbtc` / `update-bond-registration` can no longer reach
        ;; the old bond. The old bond's reward shares and signer delegation
        ;; stay through its term; only the management pointer is gone.
        (map-delete protocol-bond-memberships tx-sender)

        (let ((result {
                signer: signer,
                staker: tx-sender,
                amount-ustx: amount-ustx,
                num-cycles: num-cycles,
                first-reward-cycle: first-reward-cycle,
                unlock-burn-height: (reward-cycle-to-burn-height unlock-cycle),
                unlock-cycle: unlock-cycle,
            }))
            (print (merge { topic: "stake" } result))
            (ok result)
        )

**File:** CHANGELOG.md (L98-98)
```markdown
* Re-check the signer key grant at every pox-5 new-stake entry point (`register-for-bond`, `update-bond-registration`, `stake`, `stake-update`), so revoking a grant with `revoke-signer-grant` now disables an already-registered signer manager from accepting any new stake. Previously revocation only blocked future `register-signer` calls, leaving a deprecated or buggy manager free to keep accumulating delegated STX and re-enter the signer set; its existing obligations still settle and wind down as the backing bonds/stakes expire.
```
