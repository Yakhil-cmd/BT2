### Title
Cross-organization webhook signature confusion allows forging Shipit events (status/push) for a victim repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App secret to verify the HMAC signature against using a payload field (`repository.owner.login` / `organization.login`), but the handlers that subsequently act on the request use a *different* payload field (`repository.full_name`) to decide which `Stack`/`Repository` to mutate. Because the two fields are never cross-checked, an attacker who legitimately controls one configured GitHub organization's webhook secret can sign a payload whose `owner.login` matches their own org (so the signature check passes) while `repository.full_name` points at a victim organization's repository, letting them inject arbitrary events (pushes, commit statuses, PR events) against a stack they do not own.

### Finding Description
`Shipit.github(organization:)` supports multiple independent GitHub App configurations, each with its own `webhook_secret`, keyed by organization name (`github_app_config`/`TOP_LEVEL_GH_KEYS`): [1](#0-0) 

`WebhooksController#verify_signature` picks the app/secret to validate against by reading the organization out of the untrusted payload itself, then verifies the raw body against that org's secret: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` only proves the raw body was HMAC-signed with *that selected org's* secret — it says nothing about whether the `repository` object embedded in the same body actually belongs to that org: [4](#0-3) 

After the signature check passes, the entire parsed body is handed unmodified to every registered handler for the event: [5](#0-4) 

The equality the engine implicitly (and incorrectly) relies on is:
`organization used to select/verify the webhook secret == organization/repository the handler subsequently writes to`

This equality is never enforced. `repository_owner` (used for verification) and `repository.full_name`/`repository.owner.login` (used by the push/status/pull_request handlers under `app/models/shipit/webhooks/handlers/**` to look up the target `Stack`/`Repository`) are read independently from the same attacker-controlled JSON body, with no code tying them together beyond "did HMAC(body, secret_for(field_A)) match", which is trivially true for a body an attacker fully controls and signs with a secret they legitimately possess (their own org's webhook secret).

### Impact Explanation
An operator running Shipit with the documented multi-organization GitHub App configuration (`github_app_config`, keyed per-org secrets in `lib/shipit.rb`) is exposed to cross-tenant event injection: an attacker who has a legitimate GitHub App installation on *any* one of the configured organizations (i.e., knows/controls that org's `webhook_secret`, which is not a privileged Shipit credential — it's a value they set on their own org's GitHub App settings) can send a correctly-HMAC-signed webhook whose `repository`/`organization` owner field is set to their own org (so verification succeeds and it is routed to the correct config), while other repository-identifying fields in the same body are altered to reference a victim organization/repository tracked by the same Shipit instance. Handlers keyed off those repository fields (status updates gating deployability checks, push events triggering `GithubSyncJob`, PR label/merge events) will then execute against the victim's `Stack`. Because Shipit's deploy-gating logic relies on webhook-delivered commit statuses to determine whether a commit is "deployable," this can be leveraged to spoof a passing CI status for a victim's commit and enable an unauthorized deploy — matching the Critical "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitation requires the deployment to use the multi-organization GitHub App configuration path (`github_app_config`) and requires the attacker to control a legitimate GitHub App installation (and therefore webhook secret) on at least one of the organizations configured on that Shipit instance — a much lower bar than compromising the target/victim organization's own secret, private key, or an `ApiClient` token. This is a realistic scenario for any Shipit instance shared across multiple orgs/teams with differing trust levels.

### Recommendation
After `verify_webhook_signature` succeeds, cross-validate that the organization used to select the verifying secret matches the organization actually referenced by `repository.full_name`/`repository.owner.login` inside the same payload before dispatching to handlers, and reject the request (422) on mismatch. Alternatively, resolve the target `Stack`/`Repository` strictly through the same `repository_owner` value that was authenticated, rather than re-deriving it independently inside each handler.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, e.g. `OrgAttacker` and `OrgVictim`, each with its own `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. Attacker legitimately owns `OrgAttacker`'s GitHub App and therefore knows `OrgAttacker`'s `webhook_secret`.
3. Attacker crafts a `push` (or `status`) event JSON body where `organization.login` / `repository.owner.login` == `"OrgAttacker"`, but `repository.full_name` == `"OrgVictim/victim-repo"`.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(body, OrgAttacker_webhook_secret)` and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` computes `repository_owner == "OrgAttacker"`, loads `Shipit.github(organization: "OrgAttacker")`, and the signature check passes since the attacker legitimately signed with that org's secret.
6. `Shipit::Webhooks.for_event('push')` handlers receive the full body and resolve the target stack via `repository.full_name == "OrgVictim/victim-repo"`, causing Shipit to process the forged event (e.g., enqueue `GithubSyncJob`, or record a forged commit status) against a repository the attacker has no access to.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
