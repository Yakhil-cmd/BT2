### Title
Webhook signature key is selected by an unauthenticated `repository.owner.login` field that is never itself covered against the resolved payload's `repository.full_name`, allowing a secret holder for one org to forge events against a repository of another org - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, before the signature has been checked at all. The event handlers, however, resolve the target `Stack`/`Repository` using a different field of that same unverified body: `repository.full_name` (via `Shipit::Webhooks::Handlers::Handler#repository_name` and `Repository.from_github_repo_name`). Because the field used to select the verification secret (`repository.owner.login`) is never cross-checked against the field used to select the acted-upon repository (`repository.full_name`), a party who legitimately possesses the `webhook_secret` for organization A (e.g., a GitHub organization admin who installed the Shipit GitHub App and can see/rotate that secret, or who has otherwise obtained it for their own org's legitimate use) can sign a payload where `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")`'s secret is used for HMAC verification) while `repository.full_name = "org-b/target-repo"` points at a stack belonging to a different organization "org-b" that Shipit also manages.

### Finding Description
- The controller's `verify_signature` before_action resolves the signing key using the payload itself: [1](#0-0) [2](#0-1) 
It calls `Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository', 'owner', 'login')` — a field taken from the raw, not-yet-verified body — and uses that organization's `webhook_secret` to check `X-Hub-Signature`.

- Once verification "passes" (using org A's secret), `create` hands the exact same raw JSON to the handlers: [3](#0-2) 

- The handlers resolve the affected `Stack` using a *different* field of the same payload, `repository.full_name`, with no re-validation that it corresponds to the organization whose secret validated the signature: [4](#0-3) [5](#0-4) 

- `PushHandler`, for example, directly triggers a git-fetch/deploy sync on whatever stack the payload names: [6](#0-5) 

The binding that should hold is: *the organization whose secret authenticated the request* == *the organization that owns the repository being acted upon*. Because `owner.login` and `full_name` are independent, attacker-controlled fields of the same unauthenticated JSON body, and only `owner.login` participates in the HMAC check, this equality is never enforced. Before the fix, an attacker who is a legitimate secret-holder for org A can craft `owner.login: "org-a"` + `full_name: "org-b/target-repo"`; after "verification" the handler blindly acts on `org-b/target-repo`.

### Impact Explanation
This breaks the trust boundary between "organization that authenticated" and "repository that is written," matching the required analog class. A user who is a legitimate GitHub App/webhook_secret holder for their own organization (an "unprivileged attacker" with respect to any other org's stacks) can forge `push`, `status`, or `check_suite` webhook deliveries that are accepted as authentic for stacks belonging to a completely different organization, causing unauthorized `GithubSyncJob`/`RefreshCheckRunsJob`/`RefreshStatusesJob` triggers, forged commit statuses, or CI check states to be recorded against another org's stack — state that can gate merges and deploys. This is a cross-repository/cross-organization write achieved purely by crafting an unauthenticated JSON body, satisfying the Critical/High bar of "cross-repository writes" / unauthorized effect on stack state via a credential the engine itself issued for a different scope.

### Likelihood Explanation
Requires only that the attacker control (or know the `webhook_secret` of) at least one organization onboarded to the same Shipit instance — a realistic multi-tenant scenario since Shipit is commonly deployed to serve multiple orgs/repos from one instance (see `config/secrets.development.shopify.yml` showing multiple orgs configured under one `github:` key). No GitHub write access, no Shipit session, and no `ApiClient` token are needed — only an HTTP POST to `/webhooks` with a self-crafted, self-signed body.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after determining `repository_owner` from `owner.login` and verifying the signature, cross-check that the same payload's `repository.full_name` (or `organization.login` for org-scoped events) is actually owned by that verified organization before dispatching to handlers — e.g., derive the owner strictly from `full_name.split('/').first` (single source of truth) rather than trusting a second, independent `owner.login` field, or explicitly assert `full_name.split('/').first.downcase == repository_owner.downcase` before calling handlers.

### Proof of Concept
1. Attacker is a legitimate admin of GitHub org `org-a`, which is configured in Shipit with `webhook_secret_a`.
2. Attacker also knows/targets a Shipit stack `org-b/target-repo` (org B is a different tenant on the same Shipit instance).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_a, body)>` using the known `webhook_secret_a`.
5. POST to `/webhooks` with header `X-Github-Event: push`.
6. `verify_signature` calls `Shipit.github(organization: "org-a")` → verifies signature successfully with `webhook_secret_a`.
7. `create` parses the same body and dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("org-b/target-repo")` and triggers `stack.sync_github(expected_head_sha: "deadbeef...")` on org B's stack — an action the attacker was never authorized to trigger for org B.     def verify_signature
```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
