### Title
`StatusHandler` applies GitHub commit-status webhooks by SHA alone, without checking that the signed payload's repository/organization actually owns the target commit - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook by looking up the GitHub App/secret for the *organization named in the payload* (`repository_owner`), then verifying the HMAC over the raw body. [1](#0-0)  That check only proves "this payload was really sent by GitHub for org X." It says nothing about which *stack/repository* the payload is entitled to mutate. `Shipit::Webhooks::Handlers::StatusHandler`, however, ignores the repository entirely and updates every commit in the database that happens to share the reported SHA:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

Its parameter schema doesn't even require a `repository` key, [3](#0-2)  unlike every other handler (`PushHandler`, `CheckSuiteHandler`, the `PullRequest` handlers), which all scope their effect through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any stack. [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
This is the same trust-binding bug as `depositFor()`: the code checks one identity/scope (the *organization* whose signature validated the request) but then acts on a different, broader scope (*any* commit row in the whole installation matching a SHA), never re-verifying that the acted-upon resource belongs to the authenticated party.

The equality that should hold is:
```
organization_that_signed(payload) == repository_owner(commit_being_mutated)
```
`verify_signature` only enforces `organization_that_signed(payload) == repository_owner(payload)`, and `StatusHandler.process` never checks `repository_owner(payload) == repository_owner(commit)` — it mutates by `sha` match across the whole `commits` table, regardless of which stack/repository owns that commit. [2](#0-1) 

Git commit SHAs are content hashes and are frequently identical across forks and mirrors of the same repository/commit history. An attacker who legitimately controls their own GitHub organization/repository (with the Shipit GitHub App installed there, giving them a valid webhook signature for their own org) can:
1. Fork or mirror the victim's tracked repository into their own org (SHAs are preserved).
2. Trigger (or directly send, since they control the app installation for their org) a `status` webhook event for a commit SHA that also exists in the victim's stack, with `state: "success"` and any `context`.
3. Because `verify_signature` only checks that the payload's `repository_owner` matches the org whose secret produced a valid signature - the attacker's own org - the request passes verification.
4. `StatusHandler#process` then looks up `Commit.where(sha: params.sha)` across the entire installation and calls `create_status_from_github!` on every match, including the victim's commit in a completely unrelated stack. [2](#0-1) 

`create_status_from_github!` feeds into `Commit#add_status`, which recomputes the commit's CI status and, on a state transition to `success`/`pending`, calls `stack.schedule_merges`. [7](#0-6)  This is the exact mechanism the merge queue and CI-gated deploys rely on to decide a commit is safe to merge/deploy.

### Impact Explanation
By forging a `success` status for a specific SHA, an unprivileged attacker (who only needs push/webhook access to their own unrelated GitHub org, not any privilege in the victim's org or Shipit instance) can artificially satisfy the victim stack's CI/status gating, unblocking the merge queue (`stack.schedule_merges`) or downstream deploy-readiness checks for a commit that never actually passed CI in the victim repository. This falls under "an unauthorized deploy, rollback or merge" impact (Critical), since it lets an outsider manipulate the trust signal (`Status`) that Shipit's merge/deploy automation depends on, entirely from a different, attacker-controlled GitHub organization/repository.

### Likelihood Explanation
This does not require any Shipit session, `ApiClient` token, or GitHub App/webhook secret belonging to the victim — only that the attacker operates their own GitHub org with the Shipit app installed (a legitimate self-service capability in multi-org Shipit deployments, and the documented "Using Multiple GitHub Applications" configuration). [8](#0-7)  Forking a public repository to obtain matching SHAs is trivial, and no per-repository scoping exists anywhere in `StatusHandler`. The only friction is guessing/observing a target SHA (visible from the victim's own public commit history if the tracked repo is public, or from prior events).

### Recommendation
`StatusHandler` should scope its lookup to the repository asserted (and signature-verified) in the payload, matching the pattern used by every other handler:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
using `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (as `Handler#stacks` already provides) to ensure a status can only be applied to commits belonging to the same repository whose organization's signature validated the request.

### Proof of Concept
1. Attacker creates GitHub org `attacker-org`, installs the Shipit GitHub App there (self-service, per `docs/setup.md` multi-org config), and receives a valid `webhook_secret` for `attacker-org`.
2. Attacker forks the victim's tracked repository `victim-org/app` into `attacker-org/app`; commit SHA `abc123...` is identical in both repos.
3. Attacker uses the GitHub Statuses API (on their own fork, which they own) to set a `success` status on SHA `abc123...`, or crafts the equivalent webhook body directly and signs it with `attacker-org`'s `webhook_secret`:
   ```json
   {
     "sha": "abc123...",
     "state": "success",
     "context": "ci/attacker",
     "repository": {"full_name": "attacker-org/app", "owner": {"login": "attacker-org"}}
   }
   ```
4. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature` computed with `attacker-org`'s secret.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, which also matches the commit tracked under `victim-org/app`'s stack, and creates a `success` `Status` on it, potentially triggering `stack.schedule_merges` for the victim's stack. [2](#0-1) [7](#0-6)

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
