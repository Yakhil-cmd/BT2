### Title
`review_stacks_enabled` gate bypassed by operator precedence in `provision?` allows label-controlled forced provisioning - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` and `provisioning_behavior` with `&&`/`||` without parentheses, so Ruby's operator precedence only scopes `review_stacks_enabled` to the `allow_all?` branch. When a repository is configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled: false`, the second and third clauses are still evaluated independently of `review_stacks_enabled`, allowing a PR author to force `provision?` to return `true` simply by adding/removing the configured label on their own pull request.

### Finding Description
The intended binding is: `provision? == true` should require `repository.review_stacks_enabled == true` in all cases (operators disable review-stack provisioning at the repository level; provisioning behavior only further restricts *which* PRs are provisioned when enabled). The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. If `review_stacks_enabled` is `false` but `provisioning_behavior` is `allow_with_label` (or `prevent_with_label`), the outcome of `provision?` is determined solely by `pull_request_has_provisioning_label?`, which is computed from `pull_request_label_names`: [2](#0-1) 

`pull_request_label_names` is sourced entirely from the webhook payload's `pull_request.labels` array, which the PR author controls by adding/removing labels via the GitHub API on their own PR — no Shipit privilege is required. The webhook signature/`ExplicitParameters` schema only validate payload shape, not the semantic binding between `review_stacks_enabled` and behavior branches, so they don't prevent this.

Exploit flow:
1. A repository maintainer/operator sets `review_stacks_enabled = false` (intending to disable PR-driven stack provisioning) but leaves `provisioning_behavior = allow_with_label` and a `provisioning_label_name` configured (e.g., stale config, or a value that survived toggling the checkbox off in the settings UI, since the UI at `app/views/shipit/repositories/settings.html.erb` does not couple the "Dynamically provision" checkbox with hiding/clearing the behavior/label fields — both are independently persisted via `update_params` in `RepositoriesController`).
2. An attacker opens a PR against that repository and, whenever they want provisioning to occur, adds the label matching `provisioning_label_name` to their own PR (or has it present at "opened" time).
3. `OpenedHandler#process` calls `provision?`, which evaluates true due to the precedence bug, and `ReviewStackAdapter#find_or_create!` provisions a stack and (per repository config) executes deploy tasks for that PR's branch/SHA.
4. The attacker can also remove the label to suppress provisioning, and re-add it on a fresh `opened` event pathway (e.g., closing/reopening or new PR) to control timing.

No existing guard closes this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that GitHub sent the payload (doesn't restrict payload content); `ExplicitParameters` only validates types/presence of `labels[].name`, not their values; `force_github_authentication` and `User#authorized?` are irrelevant to webhook-driven code; `Repository` validations don't touch `provisioning_behavior`/`review_stacks_enabled` interaction.

### Impact Explanation
An unprivileged PR author on any repository misconfigured this way (operator-disabled review stacks + `allow_with_label`/`prevent_with_label` behavior configured) can force Shipit to create a `ReviewStack`/`Stack` and run provisioning/deploy tasks against their own branch and commit SHA, entirely by manipulating labels they fully control. This is an authorization-gate bypass leading to unauthorized stack creation and task execution (deploy pipeline execution) for that repository — matching the Critical category ("an unauthorized deploy... or a record written for a repository that did not authenticate it" via execution of provisioning tasks that the operator explicitly intended to disable). The blast radius is scoped to repositories with this specific configuration combination; it is repeatable at will by the attacker for every PR they open against such a repository.

### Likelihood Explanation
Requires a specific repository configuration: `review_stacks_enabled = false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (with a `provisioning_label_name` set). This is a plausible real-world state because the settings UI does not enforce mutual exclusivity or clear dependent fields, and an operator toggling the checkbox off while leaving the dropdown/label configured is a natural misconfiguration. Attacker cost is trivial (label add/remove on their own PR, a capability inherent to opening PRs), and the exploit is fully repeatable and precisely timed by the attacker as claimed in the question.

### Recommendation
Fix the boolean grouping to explicitly gate all branches behind `review_stacks_enabled`:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to any sibling handlers with the identical pattern (`Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler` — all matched in the initial grep and warrant the same review).

### Proof of Concept
minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style, using existing `configure_provisioning_behavior` helper):

```ruby
test "does NOT create stacks when review_stacks_enabled is false, even if allow_with_label matches" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # operator disabled review stacks
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "toggling attacker-controlled label does not affect provisioning when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )

  payload_without_label = payload_parsed(:pull_request_opened)
  payload_without_label["pull_request"]["labels"] = []
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload_without_label).process
  end

  payload_with_label = payload_parsed(:pull_request_opened)
  payload_with_label["pull_request"]["number"] += 1
  payload_with_label["pull_request"]["labels"] = [{ "name" => "pull-requests-label" }]
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload_with_label).process
  end
end
```
Both assertions on `review_stacks_enabled == false` vs. `provision? == true/false` should hold `provision? == false` after the fix; on current code, the second test's second block fails (`Stack.count` increases), demonstrating the bypass.
