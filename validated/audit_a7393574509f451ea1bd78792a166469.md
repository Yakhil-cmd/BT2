## Analysis

The Sherlock report describes a griefing pattern: a counterparty who retains unilateral control over a resource that another (unprivileged) party's funds depend on can destroy/revoke that resource, permanently freezing the victim's funds with no recourse.

The closest reachable analog in `ocore` is the **spender-attested asset** mechanism, where the asset **definer** unilaterally controls the attestor whitelist that governs whether *other users'* already-held asset outputs remain spendable.

- Only the asset definer may update the attestor list: [1](#0-0) .
- On every subsequent transfer, `validatePaymentInputsAndOutputs` re-checks that all recipient/output addresses are attested by the *current* attestor list before allowing the transfer: [2](#0-1) .
- The same current-attestor-list check gates issuance and outgoing spends generally, via `spender_attested`/`arrAttestedAddresses`: [3](#0-2) .
- Asset creation itself fixes `issued_by_definer_only`/`spender_attested` flags, and attestor list validation is defined in `validateAttestorListUpdate`/`checkAttestorList`: [4](#0-3) .

Because attestation status is evaluated against the *current* (mutable) attestor list rather than being tied immutably to the moment a holder received the asset, a malicious definer can post a new `asset_attestors` unit dropping the attestor who originally certified a holder's address. That holder's previously-received asset units (already paid for, already in their wallet, already used as collateral or committed in an ongoing multi-step protocol built on top of this asset) instantly become untransferable, because `validatePaymentInputsAndOutputs` will reject any output to that now-unattested address. This is structurally the same bug class as the report: a third party (definer/attestor set owner) who is not the fund owner can unilaterally revoke a precondition the victim's spend depends on, freezing the victim's assets indefinitely, purely for griefing purposes, with the victim (an ordinary asset holder posting a payment unit) having no way to countermand it.

## Verdict

### Title
Asset definer can revoke attestor list to permanently freeze other holders' already-issued asset funds - (File: `validation.js`)

### Summary
For `spender_attested` assets, the definer alone controls the attestor whitelist via `asset_attestors` messages, and every subsequent transfer of that asset re-validates the *current* attestor list against the spending/output addresses rather than the attestation state at the time the holder acquired the asset.

### Finding Description
`validateAttestorListUpdate` permits only the asset's `definer_address` to publish a new attestor list for the asset [5](#0-4) . Whenever a holder later tries to spend/transfer units of that asset, `validatePaymentInputsAndOutputs` calls `storage.filterAttestedAddresses` and rejects the payment if any output address is not attested by the *current* attestor set: [2](#0-1) . There is no mechanism that "locks in" attestation for addresses that already legitimately received the asset while a previous attestor list was active — a subsequent, definer-controlled attestor-list change retroactively invalidates the spendability of funds an unrelated, unprivileged holder is already sitting on. Because posting a new `asset_attestors` unit is a normal, single-authored, unprivileged unit (subject only to the "definer must be the author" check), the definer can grief any holder at will, at any time, permanently, and the holder — who has no privileged role in the asset and cannot counter the definer's unit — cannot restore spendability of their own already-received funds.

### Impact Explanation
Any holder of a `spender_attested` asset (which may represent a token backing a larger financial protocol built with AAs — e.g., a share/voucher/collateral token used as input to an AA case, similar in spirit to the LP position used as loan collateral in the report) can have their holdings permanently frozen by the definer at any later time, purely by dropping the attestor that certified them. This is a direct, concrete, unauthorized freezing of another party's funds with no way for the victim (or any liquidator/relying AA) to unfreeze or recover, satisfying "AA fund loss or freezing" / "concrete unauthorized ... freezing" from the validation criteria.

### Likelihood Explanation
This requires only that (a) an asset is created with `spender_attested: true` (a documented, first-class asset feature used to build permissioned/KYC'd tokens or asset-gated AAs), and (b) the definer, at any point after some other user is holding/relying on the asset, republishes an `asset_attestors` list omitting the attestor that certified that user. Both actions are ordinary, unprivileged unit postings requiring no special network position — only definer authorship, which is a normal role assumed when creating the asset. No node collusion, no timing race, and no p2p/network condition is needed.

### Recommendation
Do not re-evaluate attestation against the *live* attestor list for every future transfer of already-issued asset units. Instead, snapshot/pin the attestor(s) that validated a given output at the time it was created (e.g., record which attestor attested the recipient as of issuance/transfer time), so that later changes to the definer's attestor whitelist cannot retroactively strip spendability from funds a user already legitimately holds. Alternatively, restrict `asset_attestors` updates to only add attestors (never remove), or require a grace/timelock period plus advance notice before an attestor removal can affect already-held balances.

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true` and initial `attestors: [X]` (validated in `validateAssetDefinition`, `validation.js:2725-2827`).
2. Attestor `X` attests holder `H`'s address (via an `attestation` message).
3. `D` transfers/issues units of asset `A` to `H`; `validatePaymentInputsAndOutputs` passes because `H` is attested by current attestor `X` (`validation.js:2630-2642`).
4. `H`'s address is now used elsewhere as collateral/input in a larger multi-step protocol (e.g., an AA case that expects `H` to later transfer asset `A` back or onward).
5. `D` posts a new `asset_attestors` unit for asset `A` with `attestors: [Y]` (excluding `X`). This is accepted because only the definer-authorship check applies (`validation.js:2829-2848`).
6. `H` now attempts to transfer/spend their asset `A` units (e.g., to repay/redeem in the dependent protocol). `filterAttestedAddresses` finds `H` is not attested by the new list `[Y]`, and `validatePaymentInputsAndOutputs` rejects the payment (`validation.js:2637-2638`).
7. `H`'s asset `A` balance is now permanently frozen — unusable in any protocol relying on it — purely due to `D`'s unilateral, unprivileged, post-hoc attestor-list change.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
