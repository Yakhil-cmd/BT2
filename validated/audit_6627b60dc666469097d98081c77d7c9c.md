### Title
Webhook signature is verified against the wrong organization's secret, letting a whitelisted GitHub organization forge events for any repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports multi-tenant GitHub App configs keyed by organization (`Shipit.github_app_config`) [1](#0-0) . `WebhooksController#verify_signature` picks which organization's `webhook_secret` to check the HMAC against by reading `repository_owner`, which is derived from the JSON body itself (`repository.owner.login`, falling back to `organization.login`), not from any URL-scoped or otherwise trusted identifier [2](#0-1) . Once the signature is accepted, the actual event handlers (e.g. `PushHandler`) look up the target `Stack`/`Repository` from a *different* field of the same body, `repository.full_name` [3](#0-2) [4](#0-3) .

### Finding Description
This mirrors the Vesting bug class: two values that are supposed to represent "the same thing" (the account whose HMAC secret is checked vs. the account/repository whose state is mutated) are read from two independently-attacker-controllable inputs, and only one of them is bound by the verified signature.

- `verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.
- The signature itself is a valid HMAC-SHA1 over the *entire raw body* using that organization's configured secret — so a request only proves "the sender knows organization X's `webhook_secret`", not "the payload content actually describes organization X's repositories."
- After the signature check passes, every handler resolves the repository to act on via `payload.dig('repository', 'full_name')` (`Handler#repository_name` / `#stacks`) [3](#0-2) .
- Nothing ties `repository.owner.login` to `repository.full_name`; they are two independent keys in the same attacker-supplied JSON. An operator who legitimately controls one configured GitHub organization/App in a Shipit deployment that hosts several organizations (`Shipit.github_organizations`, `TOP_LEVEL_GH_KEYS`) knows that organization's `webhook_secret` [5](#0-4) . They can sign a fully custom JSON body with their own org's secret, set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` picks their own secret and the HMAC matches), but set `repository.full_name` to `victim-org/victim-repo`.

**Equality broken:** `organization authenticated (repository.owner.login, covered only implicitly)` ≠ `repository written (repository.full_name, used by handlers)`.

Before the attack: only GitHub, holding the real per-org `webhook_secret`, can produce a signature valid for a given org, and GitHub always sets `repository.full_name` truthfully for events on that org's own repos.
After the attack: an entity possessing organization A's secret (a legitimate, but lower-privileged, party in a multi-org Shipit instance) can produce a signature that is valid for org A while targeting `full_name` belonging to org B's stacks — something no in-band binding prevents in this code path.

### Impact Explanation
`PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for any matching stack of the forged `full_name` repository [4](#0-3) . `CheckSuiteHandler`, `StatusHandler`, and `pull_request` handlers similarly key off `stacks`/`repository_name` from the payload to update commit statuses, check-run results, or trigger CI-gated behaviors that feed into deploy/merge decisions (`continuous_deployment`, merge queue). This can cause unauthorized state changes / deploy triggers on a repository the forging party does not control, crossing a cross-repository trust boundary in a multi-tenant Shipit deployment — matching the "cross-repository writes" / "unauthorized deploy" impact bucket.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (the `github_organizations`/per-org `webhook_secret` schema) and for the attacker to already be a legitimate operator/admin of one such configured organization (i.e., they know that org's `webhook_secret`, which they were entitled to for their own webhooks). It does not require compromising GitHub, stealing another org's secret, an `ApiClient` token, or the `api_clients_secret`. Likelihood is Medium: it is limited to multi-tenant deployments and to parties already trusted with one organization's webhook secret, but requires no other privilege.

### Recommendation
Bind the field used to select the verification secret to the field used to determine the mutated resource: derive `repository_owner` from `repository.full_name`'s owner segment consistently, or — better — after selecting `github_app` and verifying the signature, additionally assert that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request (422) on mismatch. Ideally, resolve the acting organization from a per-organization endpoint/route rather than a payload field.

### Proof of Concept
Given a Shipit deployment configured with two organizations, `attacker-org` (webhook_secret known to the attacker as its legitimate admin) and `victim-org` (unrelated):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(body, attacker-org's webhook_secret)>

body = {
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },   // used by verify_signature -> picks attacker-org's secret, passes
    "full_name": "victim-org/victim-repo"   // used by Handler#stacks / #repository_name to pick the target
  }
}
```

`verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC (computed by the attacker with the known secret) validates [6](#0-5) . `PushHandler#process` then resolves `stacks` for `victim-org/victim-repo` via `Repository.from_github_repo_name(repository_name)` [3](#0-2)  and triggers `sync_github` for those stacks, even though the request was never actually authorized by `victim-org`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
