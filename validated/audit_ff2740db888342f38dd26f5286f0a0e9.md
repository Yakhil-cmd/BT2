### Title
Webhook signing organization is not bound to the repository the payload writes to, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to verify a webhook against using an attacker-supplied field of the very payload it is about to verify, while the handlers that actually mutate application state key off a *different* field of the same payload. Nothing ties the two together, so anyone who legitimately knows one organization's `webhook_secret` (e.g. an admin of a second GitHub App installation registered on the same Shipit instance under the "Multiple GitHub Applications" configuration) can forge a signed webhook whose signature validates for "their" organization but whose effective content targets a completely different organization's repository/stack.

### Finding Description
`verify_signature` computes `repository_owner` straight from the untrusted JSON body and uses it to pick the `GitHubApp`/secret to verify against: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves this string to a per-organization config block (each with its own independently-configured `webhook_secret`) when the "Multiple GitHub Applications" schema is used: [3](#0-2) 

The signature itself is a plain HMAC of the raw body against that resolved secret, with no binding to any specific field inside the body other than being byte-for-byte covered by the HMAC: [4](#0-3) 

Crucially, once verification passes, the dispatched handlers locate the target `Stack`/`Repository` using a *different* JSON field — `repository.full_name` — not `repository.owner.login`/`organization.login` used for signature routing: [5](#0-4) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the stack acted upon) are independent, uncorrelated strings in the same attacker-controlled JSON body, an attacker can construct a payload where:
- `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) — selects orgA's secret for verification, which the attacker knows because they legitimately administer orgA's GitHub App installation and set its `webhook_secret`.
- `repository.full_name = "orgB/victim-repo"` — a stack belonging to a completely different, unrelated organization tracked by the same Shipit instance.
- A signature computed correctly with orgA's `webhook_secret` over this exact crafted body.

`verify_signature` accepts this because it only checks that the HMAC matches orgA's secret; it never checks that the organization whose secret validated the request actually owns the repository the handlers act on.

### Impact Explanation
This breaks the equality the "Multiple GitHub Applications" feature is supposed to enforce: `organization authenticating the webhook == repository/organization the webhook payload is allowed to mutate`. Concretely:

- Via `PushHandler`, an attacker can force `stack.sync_github(expected_head_sha:)` on any stack belonging to any other organization configured on the instance, using an arbitrary attacker-chosen `after` sha: [6](#0-5) 
- Via `StatusHandler`, an attacker can inject a forged commit status (e.g. a fabricated `success` state) onto any commit by `sha`, regardless of which organization actually owns that commit's repository: [7](#0-6) 

Since Shipit deploy/merge gating relies on commit statuses and synced refs, this can enable an unauthorized deploy/merge decision on a repository the attacker does not control and was never granted write access to — a cross-organization/cross-repository write achieved purely by knowing one (their own) organization's webhook secret.

### Likelihood Explanation
This requires the Shipit instance to be configured with the multi-organization GitHub App schema, and the attacker to already know a valid `webhook_secret` for at least one configured organization — realistic for anyone who is an admin of that GitHub App's settings (the setup documentation explicitly tells the admin to keep this value "in clear on the side"). No GitHub-side signature bypass is required; the attack works entirely by mismatching two independent fields inside a single, otherwise-validly-signed payload.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner`/organization from the same field the handlers use to locate the stack (`repository.full_name`'s owner segment or `organization.login`), and reject the request (`head(422)`) unless the two agree. Alternatively, resolve the target `Stack`/`Repository` first, and require it to belong to the same organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` per the multi-org schema.
2. As an administrator of `orgA`'s GitHub App, obtain `orgA`'s `webhook_secret`.
3. Craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches orgA's `GitHubApp`, and the HMAC matches — the request passes verification (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
6. `create` dispatches to `PushHandler`, which looks up the stack via `repository.full_name` = `"orgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `sync_github` on a stack the attacker does not own, using an attacker-controlled sha.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
