### Title
Instantaneous-utilization interest rate is frozen into a shared per-block index cache, letting one caller's momentary deposit/withdraw distort accrual for every other user of the vault - (File: mainnet/contracts/vault/v0-vault-stx.clar, mainnet/contracts/market/v0-4-market.clar)

### Summary
`next-index`/`next-liquidity-index` in each vault (e.g. `v0-vault-stx.clar`) compute the compounding multiplier for the *entire* elapsed period since `last-update` using `interest-rate()`, which is derived from the **instantaneous** `utilization()` = `calc-utilization(get-available-assets, total-debt)` at the moment the accrual call executes. [1](#0-0) 

The market contract wraps this in `accrue-and-cache`, which persists the resulting `{index, lindex}` in `index-cache` keyed only by `{timestamp: stacks-block-time, aid}` — not by caller — so whichever transaction is first to touch a vault in a block determines the accrual applied to that vault for the remainder of the block, consumed by every subsequent unrelated caller's borrow/repay/collateral/health-check operations. [2](#0-1) 

### Finding Description
`interest-rate()` reads `utilization()`, which is a live read of `get-available-assets()` and `total-debt()` at call time, not a time-weighted average. [3](#0-2) 
That rate is then applied via `calc-multiplier-delta` over `time-delta = stacks-block-time - last-update`, which can span the entire time since the vault's last touch (potentially long if the vault is idle), and the resulting index/lindex are written to persistent vault state (`var-set index`, `var-set lindex`) the first time `vault-accrue`/`accrue-and-cache` runs in a block. [4](#0-3) 

Because a depositor (or a large withdraw/redeem) directly moves `assets`/`available-assets`, an attacker can, within a single atomic transaction, temporarily push utilization to an extreme (near 0% or near 100%) immediately before triggering the vault's first accrual of the block (e.g. via `borrow`, `collateral-add`, or any operation that calls `accrue-and-cache`), then reverse the position later in the same transaction. The distorted rate is baked into the persisted `index`/`lindex` for the *entire elapsed period*, and is also cached at the market layer for every other unrelated caller in that block. [5](#0-4) 

This is a shared-state hazard between unrelated principals: the caching key is `{timestamp, aid}`, global to the vault, not scoped to the caller. [6](#0-5) 

### Impact Explanation
Existing borrowers in the vault would have their debt compounded using an artificially depressed or inflated rate (permanent freeze/loss of accrued yield for suppliers, or inflated debt for borrowers), and depositors' `lindex`-based redemption value is similarly skewed — an unprivileged attacker harming other, unrelated principals' positions through a shared cached index. This falls under "High: theft of unclaimed yield" (suppliers permanently lose interest owed to them if the rate is depressed) or, if debt is inflated, contributes to under-collateralization risk for other borrowers.

### Likelihood Explanation
Requires the attacker to be first (or race) to trigger the vault's block accrual after supplying/withdrawing enough capital to swing utilization meaningfully, and depends on the interest-rate curve's sensitivity (`points-ir` interpolation) and the elapsed `time-delta` being large enough to matter. I was **not able to fully verify** within the available context whether `total-debt`/`get-available-assets` can be moved enough by a single depositor without hitting caps (`cap-supply`/`cap-debt`), nor whether `vault-accrue`'s real (non-preview) update path recomputes using the exact same instantaneous values I traced in `next-index`/`next-liquidity-index`, since the actual public `accrue` entry point content in `v0-vault-stx.clar` was not retrieved before the tool budget ran out. This uncertainty limits my confidence in the exact exploit mechanics and magnitude.

### Recommendation
Use a time-weighted or twice-updated utilization snapshot (accrue up to the pre-transaction state before applying new deposits/withdraws in the same block), or make the per-block index cache caller-invariant by validating that utilization inputs used for rate computation are taken before any state-mutating operation in the same transaction. Consider also bounding the maximum multiplier applied per accrual call to reduce the blast radius of a single-block utilization spike.

### Proof of Concept
Not independently verified — the concrete PoC would require confirming the real `accrue`/`deposit`/`redeem` entry points' exact ordering relative to `next-index`/`next-liquidity-index` calls, which I could not complete before the tool budget was exhausted. A verifying engineer should: (1) locate the public `accrue` and `deposit`/`redeem` functions in `v0-vault-stx.clar`, (2) confirm whether a same-transaction deposit-then-withdraw can change `get-available-assets`/`total-debt` before the block's first `accrue-and-cache` call, and (3) measure the resulting index deviation versus a scenario without the attacker's transaction.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
