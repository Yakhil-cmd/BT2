### Title
Atomic Oracle Price Manipulation via Unstable Data Feed Reads in AA Trigger Execution - (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
Any AA that prices assets, mints shares, or computes payouts using `data_feed[[...]]` in its oscript is exposed to the same "atomic oracle update" exploitation class described in the external report. In ocore, `data_feed` reads performed during actual AA trigger processing (not just estimation) are configured with `unstable_opts = bAA = true`, which makes `readDataFeedValue()` include **not-yet-stable** data-feed messages authored by the oracle address, as long as the feed unit's `latest_included_mc_index` is below the current trigger's mci. This lets an oracle (or an attacker acting as their own oracle for a self-referential AA parameter) post a new price and have it consumed by an AA trigger almost immediately, without any minimum staleness/epoch enforced by the platform.

### Finding Description
The `data_feed` operator in `formula/evaluation.js` calls `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, objValidationState.last_ball_timestamp, ...)`, passing `bAA` as the `unstable_opts` argument. [1](#0-0) 

Inside `readDataFeedValue`, when `unstable_opts` is truthy, the function scans `storage.assocUnstableMessages` for `data_feed` messages authored by the target oracle address whose `latest_included_mc_index` falls within `[min_mci, max_mci]`, picking the "last" (highest level) candidate — without requiring the feed unit itself to be final/stable: [2](#0-1) 

There is no enforced minimum age, epoch, or averaging window between when a data feed value is posted and when it can be consumed by an AA trigger — the only constraints are `min_mci`/`max_mci` filters supplied by the AA author and DAG causal ordering (the feed unit must be an ancestor of the trigger unit). This mirrors the `LPManager` issue: an oracle-driven price can be updated and immediately acted upon within the same tight sequence of DAG units, with no cooldown comparable to `maxOracleAge` epochs recommended in the report.

### Impact Explanation
Any AA implementing pool/vault-style logic (minting shares, exchanging assets, or paying out bytes/tokens) based on `data_feed` values — such as the pattern shown in the repository's own test fixture that exchanges bytes for assets using `GBYTE_USD_MA` data feeds — can be manipulated by an actor who controls or colludes with the oracle address to: (1) post a favorable price, (2) trigger the AA to add liquidity/mint shares/buy at that price, (3) post an updated price, and (4) trigger the AA again to redeem/sell at the new price, all within a very short DAG sequence, before the feed values are subjected to any statistical smoothing. This can drain AA-held funds (base bytes or custom assets), i.e., concrete AA fund loss.

### Likelihood Explanation
Exploitability depends entirely on the AA author's oscript design — any AA that trusts a single, instantaneous `data_feed` read (without their own epoch/TWAP logic) is vulnerable, and ocore's `data_feed`/`readDataFeedValue` machinery provides no built-in staleness protection to prevent it. Given how common oracle-price-dependent AA templates are (as evidenced by the repository's own test fixtures using `data_feed` for pricing decisions), likelihood is high for any deployed AA lacking custom mitigations.

### Recommendation
At the AA-authoring level (oscript), implement price epochs analogous to the report's recommendation: track min/max observed prices over a rolling window (e.g., of duration comparable to `maxOracleAge`), update these bounds on every state-changing operation, and use the worst-case bound (highest for minting/depositing, lowest for redeeming/withdrawing) rather than the single latest `data_feed` value. At the platform level, consider exposing a documented minimum feed age or optional "require stable" flag for `data_feed` reads used in fund-affecting logic, so AA authors can opt into safer semantics without hand-rolling epoch tracking.

### Proof of Concept
1. Deploy an AA (e.g., a liquidity/exchange AA similar to the one in the test fixture using `data_feed[[oracles=oracle_address, feed_name='PRICE']]`) that computes minted shares/payout amounts directly from a single `data_feed` read. [3](#0-2) 
2. As the oracle address (or a colluding oracle), post a `data_feed` unit with a low `PRICE`.
3. Immediately post a trigger unit (child of the feed unit) to the AA to deposit/add liquidity — `readDataFeedValue` picks up the low, still-unstable price via the `bIncludeUnstableAAs` branch. [4](#0-3) 
4. Post a new `data_feed` unit with a high `PRICE`.
5. Immediately post a second trigger unit to withdraw/remove liquidity — the AA reads the new high price for the payout calculation.
6. The attacker profits from the price differential extracted from the AA's held funds, with no epoch or staleness check preventing the sequence.

	var bIncludeUnstableAAs = !!unstable_opts;
	var bIncludeAllUnstable = (unstable_opts === 'all_unstable');
	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
			if (!objUnit.bAA && !bIncludeAllUnstable)
				continue;
			if (objUnit.sequence !== 'good')
				continue;
			if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)
