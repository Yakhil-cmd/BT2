Based on my review of the in-scope pox-5.clar L1 lockup verification logic, I found a concrete deduplication-scope issue, though I was unable to fully trace the calling function (likely `register-for-bond`/`stake`) before running out of tool iterations — this limits full confidence in the finding. I present it with that caveat noted in the Likelihood section.

### Title
L1 Bitcoin lockup outpoints are deduplicated only within a single call, allowing the same BTC lock to be credited to multiple stacking registrations - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`verify-l1-lockups` and its fold helper `validate-l1-lockup` build a `seen-outpoints` accumulator that starts empty on every invocation and is discarded once the call returns. There is no persisted, contract-wide map recording which Bitcoin `(txid, output-index)` outpoints have already been credited toward a staker's sats commitment.

### Finding Description
`verify-l1-lockups` initializes the fold accumulator with `seen-outpoints: (list)` on each call: [1](#0-0) 

`validate-l1-lockup` only rejects an outpoint if it appears twice *within the same accumulator* (i.e., within the same list of outputs passed in one transaction): [2](#0-1) 

Nowhere in the code I inspected (lines ~1900–2130) is there a `define-map` that records already-consumed outpoints across separate transactions/calls. Each call to `verify-l1-lockups` re-derives the sats sum purely from proof data (Bitcoin header + merkle proof + script match) supplied fresh by the caller, with duplicate-detection scoped only to the list passed in that single call.

This means the same real Bitcoin lockup UTXO (one on-chain lock of sats) could, in principle, be submitted again in a later, separate call to credit sats a second time — breaking the equality that `amount-sats` credited on Stacks must equal sats actually and singularly locked on Bitcoin.

### Impact Explanation
If reachable from a public entry point without additional persisted-outpoint bookkeeping, this would let a staker double-count a single Bitcoin lockup as backing for two separate bond/stake registrations, inflating `amount-sats` used in reward-share and stake-weight accounting (`get-total-shares-staked-for-cycle`, `calculate-bond-rewards`) without a second real BTC lock. That maps to "sats credited by an L1 proof that were never locked on Bitcoin" / "double-counting a commitment," a Critical-impact class per the rules.

### Likelihood Explanation
I could not confirm, within the remaining tool budget, whether the public function that calls `verify-l1-lockups` (not shown in the excerpts I retrieved) additionally records consumed outpoints in a persistent map elsewhere in the ~2900-line `pox-5.clar` file, or whether it otherwise constrains reuse (e.g., via a one-time bond-registration flag tied to the bond, or the `staker` field being consumed once). Without seeing that call site and the full contract's map definitions, I cannot assert with certainty that this is exploitable end-to-end — only that the deduplication logic shown here is scoped per-call and not globally persisted, which is the necessary condition for the bug class to apply. This should be verified against the full contract source before treating it as confirmed.

### Recommendation
Add a persistent map (e.g., `used-l1-outpoints: {txid: (buff 32), output-index: uint} -> bool`) that is checked and updated whenever a lockup outpoint is accepted in `validate-l1-lockup`/`verify-l1-lockups`, rejecting any outpoint already recorded from a prior call, in addition to the existing intra-call `seen-outpoints` check.

### Proof of Concept
Conceptual sequence (pending confirmation of the exact public caller):
1. Staker locks `N` sats in a valid timelock UTXO on Bitcoin matching `construct-lockup-output-script` for their bond.
2. Staker calls the pox-5 entry point that invokes `verify-l1-lockups` with this UTXO's Bitcoin proof, registering bond A and being credited `N` sats.
3. Staker calls the same entry point again (e.g., for bond B, or a second stake), submitting the identical Bitcoin proof/outpoint. Because `seen-outpoints` resets to `(list)` for each new call, `validate-l1-lockup` does not detect the reuse, and `N` sats are credited again without any new Bitcoin lock.
