### Title
Webhook organization used for signature verification is decoupled from the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's webhook secret to check the HMAC signature against using `repository_owner`, a value read from the untrusted, unverified JSON body. Every webhook handler, however, resolves the target `Stack`/`Repository` from a *different* field of that same body: `repository.full_name`. Because these two fields are never cross-checked, an attacker can pick an organization/App config that has no `webhook_secret` configured (or whose secret they possess) to satisfy signature verification, while pointing `repository.full_name` at a completely different, victim-owned repository whose stacks get acted upon.

### Finding Description
`verify_signature` computes the organization solely from the JSON body: [1](#0-0) [2](#0-1) 

and uses it to fetch the corresponding `GitHubApp` and its `webhook_secret`, then compares the signature against that org's secret: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` and skips verification entirely `unless webhook_secret` is configured for that organization (webhook secrets are documented as **optional** per org in `docs/setup.md`).

Meanwhile, every registered event handler (e.g. `PushHandler`) resolves the actual `Repository`/`Stack` to act on from `repository.full_name`, a sibling field in the very same untrusted payload, independent of `repository.owner.login`: [4](#0-3) [5](#0-4) 

Since `repository.owner.login` (verification target) and `repository.full_name` (mutation target) are two independent, attacker-supplied JSON leaves that are never checked for consistency, the binding "organization that authenticated == repository that is written" is broken. This satisfies the rule's explicit named analog: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
If any organization configured in `Shipit.github` config has no `webhook_secret` set (an explicly optional setting), or if the attacker otherwise knows/derives one org's secret, they can forge a POST to `/webhooks` with:
- `X-Github-Event: push`
- `repository.owner.login` = the no-secret (or attacker-known-secret) org
- `repository.full_name` = `<victim-org>/<victim-repo>` (any real repository tracked by the instance)
- `ref` / `after` = attacker-chosen branch/SHA

`verify_signature` will pass trivially (no secret configured for the claimed org), and `PushHandler#process` will then call `stack.sync_github(expected_head_sha: params.after)` on the victim stack, forcing a resync/deploy pointer to an attacker-chosen commit SHA — an unauthorized deploy trigger against a repository the attacker never proved control of.

### Likelihood Explanation
Exploitability depends on at least one configured GitHub App/org having a blank `webhook_secret` (explicitly optional in setup docs) or a leaked/guessable secret for any one org on a multi-org instance — a realistic misconfiguration in shared/multi-tenant Shipit deployments, since the webhook endpoint is unauthenticated by design (it's meant to be called by GitHub) and requires no session or API token.

### Recommendation
Bind signature verification to the same repository identity that handlers act on: derive the verifying organization from `repository.full_name`'s owner segment (or otherwise cryptographically tie `owner.login` to `full_name`), and reject any event where they disagree. Additionally, consider requiring `webhook_secret` to be mandatory for all configured organizations so that a per-org opt-out cannot be leveraged to forge events for other orgs' repositories.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-without-webhook-secret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` resolves `Shipit.github(organization: "org-without-webhook-secret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` short-circuits to `true` regardless of the (even absent/garbage) `X-Hub-Signature` header. `PushHandler` then resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, mutating/deploying a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
