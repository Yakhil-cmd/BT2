### Title
Webhook signature is validated against the organization derived from `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field, letting a webhook "authenticated" for org A forge deploy-triggering events for org B's repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App's `webhook_secret` to validate the HMAC signature against solely from `repository.owner.login` (falling back to `organization.login`), while every event handler (`Handler#stacks`/`#repository_name`, used by `PushHandler`, `StatusHandler`, etc.) resolves the target `Repository`/`Stack` to write to from the independent `repository.full_name` field of the same payload. Nothing binds these two fields together, so a signature that is valid for organization A does not guarantee the mutated repository belongs to organization A.

### Finding Description
`verify_signature` selects the signing secret like this: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `github_app` config for that org and calls `verify_webhook_signature`, whose HMAC-secret check is a no-op when `webhook_secret` is blank: [3](#0-2) 

The sample multi-org configuration explicitly allows `webhook_secret` to be `nil` per organization: [4](#0-3) 

Meanwhile, every handler resolves the actual `Stack`/`Repository` it mutates from a *different* payload field, `repository.full_name`, not from `repository.owner.login`: [5](#0-4) 

`PushHandler` uses that mismatched resolution to enqueue a GitHub sync for the resolved stack using an attacker-supplied `after` SHA: [6](#0-5) 

`StatusHandler` likewise creates a `Status` record for any commit matching an attacker-chosen `sha`, independent of which org's signature check ran: [7](#0-6) 

This breaks the intended binding `organization_that_authenticated == repository_that_is_written`. Concretely: for any org B configured in Shipit with a blank/absent `webhook_secret` (or one whose secret an attacker otherwise controls), an unprivileged sender can submit a payload where `repository.owner.login` = `B` (so `verify_signature` trivially passes, e.g. via the `return true unless webhook_secret` short-circuit) while `repository.full_name` = `"A/some-repo"`, an entirely different, already-registered stack under a different organization A. The handler then operates on stack A using data the "authentication" step never actually vouched for.

If a stack has `continuous_deployment` enabled, a forged `status` event marking a real commit `success` for the required CI context makes that commit `deployable?` and schedules `ContinuousDeliveryJob`, which will `trigger_deploy` it — deploying a commit whose actual CI status was never verified: [8](#0-7) [9](#0-8) [10](#0-9) 

The equivalent `push` path forces `Stack#sync_github(expected_head_sha:)` on an arbitrary registered stack, which can also feed into continuous delivery once new commits/statuses are recorded.

### Impact Explanation
This crosses the exact "authenticated organization vs. written repository" boundary the scan targets: the org whose (possibly absent) secret gated the request is not the org whose stack gets mutated. The reachable consequence — an unauthorized deploy triggered by a forged CI-status webhook bypassing actual CI verification — matches the Critical impact bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Medium-High: it requires (a) at least one organization configured in the Shipit instance with a blank `webhook_secret` (explicitly supported/shown in the sample config) or a leaked/guessable secret for any one org, and (b) the target stack to already exist in Shipit and have `continuous_deployment` enabled. No GitHub write access, `ApiClient` token, or session is needed — only the ability to POST to the public `/webhooks` endpoint, which is unauthenticated by design.

### Recommendation
Bind the field used for signature-org selection to the field used for repository resolution: verify the signature using the organization/owner derived from the *same* `repository.full_name` (or explicitly assert `repository.owner.login == repository.full_name.split('/').first`) before dispatching to handlers, and reject the request if the two disagree. Additionally, disallow (or at least strongly warn against) a blank `webhook_secret` for any configured organization, since it makes `verify_webhook_signature` unconditionally return `true`.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` (has `webhook_secret` set) and `org-b` (has `webhook_secret: nil`) — the latter is explicitly supported per `config/secrets.development.shopify.yml`.
2. Register/track a stack for `org-a/target-repo` with `continuous_deployment: true` in Shipit.
3. POST to `/webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, and JSON body:
```json
{
  "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/target-repo" },
  "organization": { "login": "org-b" },
  "sha": "<real sha of an undeployed commit on org-a/target-repo>",
  "state": "success",
  "context": "<the ci context org-a/target-repo requires>"
}
```
4. `verify_signature` resolves `repository_owner` to `org-b`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) signature header.
5. `StatusHandler#process` resolves the commit purely by `sha` and creates a `Status` with state `success` for it, on the real `org-a/target-repo` stack.
6. If that CI context was the last one blocking `deployable?`, `Commit#schedule_continuous_delivery` fires `ContinuousDeliveryJob`, and `Stack#trigger_continuous_delivery` deploys the commit on `org-a/target-repo` — an unauthorized deploy triggered without ever presenting valid credentials for `org-a`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
