### Title
Unchecked `count_coins` Integer Overflow in Fixed-Denomination Asset Cap Validation - (File: validation.js)

### Summary
`validateAssetDefinition()` in `validation.js` computes an asset's total capped supply via `denomInfo.count_coins * denomInfo.denomination` without ever bounding `count_coins` itself, unlike `denomination` and `cap`, which are explicitly capped at `constants.MAX_CAP`. Because JavaScript numbers are IEEE-754 doubles, an attacker-controlled `count_coins` can be chosen so that the multiplication silently loses precision (an "integer overflow"-class defect, analogous to the unchecked size arithmetic in the FFmpeg DXA demuxer from CVE-2024-36613), letting a crafted asset-definition unit pass cap-consistency checks that were meant to bind the real, enforced coin supply.

### Finding Description
In `validateAssetDefinition`: [1](#0-0) 
`denomInfo.denomination` is validated against `constants.MAX_CAP`, but `denomInfo.count_coins` is only checked with `isPositiveInteger`, which merely requires `Math.floor(x) === x && x > 0` — no upper bound at all: [2](#0-1) 
`total_cap_from_denominations` is then accumulated with plain `+=` and compared for exact equality against `payload.cap`: [3](#0-2) 

The same unchecked multiplication pattern is repeated at issuance time in `validateIndivisibleIssue`, which re-derives the expected issue size from the DB-stored `count_coins` and the message's `denomination`: [4](#0-3) 

Because `count_coins` has no ceiling, an attacker who authors an `asset` message (a message type any unprivileged unit poster can send) can pick `denomination` (bounded by `MAX_CAP`) and `count_coins` (unbounded) such that `count_coins * denomination` overflows/rounds in floating point to a value that coincidentally satisfies `payload.cap !== total_cap_from_denominations` as an exact match, even though the true, full-precision product differs from the declared/enforced cap. This lets the definition validator accept an asset whose "declared" and "enforced" caps diverge from the value a wallet, block explorer, or downstream consumer would compute using correct arithmetic (or using a different but equally valid double rounding path, e.g. summing terms in a different order across `MAX_DENOMINATIONS_PER_ASSET_DEFINITION` entries), producing disagreement about how much of the asset can validly be issued.

### Impact Explanation
This falls into "asset issuance and transfer conditions" — a category explicitly in scope. If exploited, it can undermine the invariant that an asset's cap (as declared in its definition and relied upon by every node/wallet) matches what validation logic will actually permit to be issued, which is the mechanism this code exists to guarantee. In the worst case this enables supply-inflation-class disagreement: a fixed-denomination asset whose real issuable total silently diverges from its advertised `cap`.

### Likelihood Explanation
Reaching this code requires only posting a normal `asset` definition message, which every unprivileged author can do — no privileged role, hub, or peer trust is required. However, exploiting floating-point rounding to obtain a *useful* (attacker-favorable) mismatch between `total_cap_from_denominations` and the true product requires carefully engineered numbers near the edge of double precision (~2^53), which is a non-trivial but not implausible crafting exercise, especially since `MAX_DENOMINATIONS_PER_ASSET_DEFINITION` entries can be combined to amplify rounding error. I was not able to fully confirm within available context whether a further downstream check (e.g., a serial-number-vs-count_coins bound enforced elsewhere, such as in `indivisible_asset.js`) independently limits the number of distinct issuances per denomination; if such a bound exists and is computed identically, the practical exploitability of turning this arithmetic inconsistency into realized supply inflation would be reduced to a definition/consumer disagreement rather than an outright overspend.

### Recommendation
- Bound `denomInfo.count_coins` by `constants.MAX_CAP` (or another explicit ceiling) the same way `denomination` and `cap` are bounded, in `validation.js` around line 2769-2778 and in the parallel check in `aa_validation.js` (lines ~272-284).
- Perform the cap-consistency arithmetic using an overflow-safe method (e.g., BigInt, or explicit range checks before multiplication) rather than raw `*`/`+=` on JS numbers.
- Apply the same fix to `validateIndivisibleIssue` (validation.js:2207-2226), so the enforced per-issue amount check cannot rely on the same unchecked multiplication.

### Proof of Concept
1. Author and broadcast a unit containing an `asset` message with `fixed_denominations: true` and `denominations` such as:
   `[{ denomination: D, count_coins: C }]`, where `D` is chosen close to `constants.MAX_CAP` and `C` is chosen (via search) so that `C * D` in double-precision floating point rounds to a value `X` that the attacker also sets as `payload.cap`.
2. `validateAssetDefinition` (validation.js:2778, 2790) accepts the definition because `total_cap_from_denominations === payload.cap` holds under IEEE-754 rounding, even though the exact mathematical product `C * D` (as would be computed by any full-precision consumer, e.g. a BigInt-based wallet or explorer) differs from `X`.
3. Subsequent issuance messages are validated against the same rounded arithmetic in `validateIndivisibleIssue` (validation.js:2224), so the network accepts issuance amounts consistent with the rounded (not true) cap, creating a persistent, unresolvable disagreement between the unit's declared cap semantics and its real enforced value across implementations that use different-precision arithmetic.
