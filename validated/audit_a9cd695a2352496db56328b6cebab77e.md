### Title
Unauthenticated `X-Shipit-User` header lets any API-token holder forge the acting identity for deploys, rollbacks, locks, task aborts, and merges - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Shipit::Api::BaseController` authenticates the caller via a signed `ApiClient` token, but derives the *acting user* attribution from a plain, unsigned request header (`X-Shipit-User`) that is not covered by that authentication at all.

### Finding Description
Authentication in the API is a two-part binding:
1. `authenticate_api_client` verifies a signed `ApiClient` token (via `ApiClient.authenticate`) and grants scope-based permissions (`read:stack`, `deploy:stack`, `lock:stack`, etc.). [1](#0-0) 
2. `current_user`, however, is resolved independently from the caller-supplied `X-Shipit-User` header, with no signature, no relation to the authenticated `ApiClient`, and no verification that the named login is actually the caller: [2](#0-1) 

This is exactly the pattern in the external report: a field that is *acted upon* by privileged operations (`recipient` in the report; `X-Shipit-User` here) is never covered by the trust boundary that is supposed to gate the action (the burn's caller-based accounting in the report; the signed `ApiClient` token here). The equality that should hold — "the identity attributed to an action == the identity that authenticated the request" — is broken: any holder of a `deploy:stack`/`lock:stack` scoped `ApiClient` token can set `current_user` to an arbitrary `Shipit::User` record simply by sending that header, because `identify_user` performs an unauthenticated lookup by login.

This forged `current_user` is then passed as the authoritative actor into sensitive, audited operations across multiple controllers:
- `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- `deploy.trigger_rollback(current_user, ...)` and `active_task.abort!(aborted_by: current_user, ...)` [4](#0-3) 
- `stack.lock(params.reason, current_user)` [5](#0-4) 
- `task.abort!(aborted_by: current_user)` and `stack.trigger_task(..., current_user, ...)` [6](#0-5) 
- `MergeRequest.request_merge!(stack, params[:id], current_user)` [7](#0-6) 

### Impact Explanation
This does not itself grant new permissions (the `require_permission` scope checks are still enforced against the `ApiClient`), so it does not directly meet the "escalation into `Shipit.github_teams` authorization" bar on its own unless `MergeRequest.request_merge!` or downstream logic uses `current_user`'s team membership/authorization to make a merge/deploy decision rather than merely for attribution — I was not able to fully verify this before running out of tool calls, since I could not inspect the full body of `MergeRequest#request_merge!` or `Stack#trigger_deploy`/`trigger_task`/`trigger_rollback` to confirm whether `current_user`'s `authorized?`/team membership is consulted as an authorization gate (as opposed to just being stored as `commit.author`/`locked_by` attribution for audit/UI purposes).

### Likelihood Explanation
Any party holding a valid `ApiClient` token with `deploy:stack` (or `lock:stack`) permission — which is intentionally a narrower-scoped credential meant for automation, not necessarily a trusted human operator — can trivially set this header on every request with no additional privilege needed.

### Recommendation
Do not trust `X-Shipit-User` as an identity assertion by itself. Options:
- Remove header-based user identification for privileged actions, or restrict it to `UnlimitedApiClient`/internal-only callers.
- Bind the header value to the requesting `ApiClient`'s `creator`, or require it to be verified separately (e.g., only accepted when the `ApiClient` itself is scoped as "acting-on-behalf-of" that user).
- If `MergeRequest.request_merge!` or any trigger method treats `current_user` as an authorization decision point (not just attribution), require that identity to satisfy `Shipit.github_teams` membership checks before proceeding.

### Proof of Concept
Given a valid `ApiClient` token `T` scoped only to `deploy:stack` for stack `S` (e.g., a CI bot's token), an attacker with access to `T` can:
```
POST /api/stacks/:owner/:repo/:branch/deploys
Authorization: Basic <base64(T)>
X-Shipit-User: admin-login
{ "sha": "<sha>" }
```
`identify_user` looks up `User` by `admin-login` unauthenticated [8](#0-7) , and `DeploysController#create` records the deploy as triggered by that user [3](#0-2) , misattributing the action in audit trails, notifications, and any UI/logic keyed off `Deploy#user`.

Note: I was unable to fully confirm within the available tool budget whether any authorization decision (as opposed to pure audit attribution) depends on this spoofed `current_user`, which is necessary to reach the Critical/High bar required by the rules. If Devin engineering wants a definitive verdict, `MergeRequest#request_merge!` in `app/models/shipit/merge_request.rb` and `Stack#trigger_deploy`/`#trigger_task`/`#lock` in `app/models/shipit/stack.rb` should be reviewed for any `current_user.authorized?`/team-membership checks.
