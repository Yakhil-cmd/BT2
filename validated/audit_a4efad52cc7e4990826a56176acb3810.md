### Title
P2P-Delivered `StakingInfo` Accepted Without Content Validation, Enabling Reward Misdirection — (`datasync/downloader/queue.go`)

---

### Summary

During fast-sync and the staking-info recovery path, `P2PStakingInfo` received from a remote peer is written directly to the local database without any content validation. A malicious-but-registered peer can inject fabricated staking info (arbitrary node addresses, reward addresses, staking amounts, treasury fund addresses) that is then used verbatim for KAIA reward distribution.

---

### Finding Description

The external bug class is: *consuming external data without checking its validity/freshness before acting on it*. The Kaia analog is in the fast-sync staking-info delivery pipeline.

**Root cause 1 — `queue.DeliverStakingInfos` has a no-op validator:** [1](#0-0) 

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil   // ← always passes, no content check
}
```

Compare this to `DeliverReceipts`, which validates the receipt root hash against the header before accepting data: [2](#0-1) 

No equivalent check exists for staking info. The `P2PStakingInfo` fields — `CouncilNodeAddrs`, `CouncilRewardAddrs`, `CouncilStakingAmounts`, `KEFAddr`, `KIFAddr` — are accepted as-is.

**Root cause 2 — `SyncStakingInfo` recovery checks only `BlockNum`, not content:** [3](#0-2) 

```go
if d.stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum {
    logger.Error("failed to receive expected block", ...)
    return
}
d.stakingModule.PutStakingInfoToDB(stakingInfo.BlockNum, staking.ToStakingInfo(stakingInfo))
```

The block number is verified, but the actual content of the staking info is never cross-checked against the local canonical state (e.g., by re-reading the AddressBook contract at that block's state root).

**Accepted data flows directly into reward distribution:**

`GetStakingInfo` reads from the database (populated by `PutStakingInfoToDB`) and returns it without re-validation: [4](#0-3) 

That `StakingInfo` is then used by `specWithProposerAndFunds` and `assignStakingRewards` to determine where KAIA block rewards are sent: [5](#0-4) 

The `KEFAddr`, `KIFAddr`, and `RewardAddrs` fields from the peer-supplied staking info are used directly as transfer destinations.

---

### Impact Explanation

A malicious peer that is registered with the downloader can respond to a `StakingInfoRequestMsg` with fabricated `P2PStakingInfo` containing:
- Attacker-controlled `CouncilRewardAddrs` — redirecting per-block validator rewards
- Attacker-controlled `KEFAddr` / `KIFAddr` — redirecting treasury fund allocations (KEF/KIF receive a fixed percentage of every block's minted KAIA)

This constitutes **unauthorized reward distribution** affecting KAIA and system-managed treasury funds — a direct match to the allowed impact gate.

---

### Likelihood Explanation

- Applies to nodes performing fast-sync (pre-Kaia hardfork) or using the `SyncStakingInfo` recovery RPC
- Requires a registered peer (semi-trusted, not fully privileged)
- The `TODO-Kaia-Snapsync update validation logic` comment confirms the gap is known but unresolved
- The attack window is the entire fast-sync period, which can span thousands of blocks

---

### Recommendation

In `queue.DeliverStakingInfos`, implement content validation analogous to `DeliverReceipts`: re-derive the expected staking info from the local state at the requested block's root and compare it against the peer-supplied data before accepting it.

For the `SyncStakingInfo` recovery path, after receiving a `P2PStakingInfo`, verify its content by calling `GetStakingInfo` locally (which reads from the canonical state) and comparing the result field-by-field before calling `PutStakingInfoToDB`.

---

### Proof of Concept

1. Node A begins fast-sync and requests staking info for block `N` (a staking-interval boundary).
2. Malicious peer B responds with a `P2PStakingInfo{BlockNum: N, CouncilRewardAddrs: [attacker], KEFAddr: attacker, KIFAddr: attacker, CouncilStakingAmounts: [large_value]}`.
3. `queue.DeliverStakingInfos` calls `validate(...)` → returns `nil` unconditionally.
4. `commitFastSyncData` calls `d.stakingModule.PutStakingInfoToDB(N, staking.ToStakingInfo(fabricated))`. [6](#0-5) 

5. For all subsequent blocks in `[N+1, N+StakingInterval)`, `GetStakingInfo` returns the fabricated info from the database. [4](#0-3) 

6. `FinalizeState` distributes block rewards to attacker-controlled addresses for every block in that interval.
