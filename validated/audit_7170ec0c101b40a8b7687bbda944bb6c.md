### Title
Webhook signature verification binds to `repository.owner.login` while stack lookup binds to `repository.full_name`, letting a payload for a no-secret/known-secret org sync an unrelated organization's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC against using `repository.owner.login`, but `Handlers::Handler#stacks` (used by `PushHandler#process`) resolves the target `Stack` using `repository.full_name`, a separate field in the same attacker-controlled JSON body. In any Shipit deployment configured with multiple GitHub organizations (the documented "Using Multiple Github Applications" setup), an attacker who controls (or can trivially satisfy) the `webhook_secret` for one configured organization — including the common case of an org configured with a blank `webhook_secret` — can sign an arbitrary raw body and set `repository.full_name` to point at a different organization's private repository/stack, causing an unauthorized `GithubSyncJob` to run for that other tenant's stack.

### Finding Description
Binding claimed and broken: `organization_that_verified_signature` (derived from `params.dig('repository','owner','login')`) `== organization_owning_full_name` (derived from `payload.dig('repository','full_name')`, used downstream). These two values are read from independent fields of the same unsigned JSON body and are never compared to each other.

- `WebhooksController#repository_owner` reads `params.dig('repository', 'owner', 'login')` from the parsed body and feeds it into `Shipit.github(organization: repository_owner)`; the resulting `GitHubApp` instance's `verify_webhook_signature` HMACs the *entire raw body* against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization has no configured `webhook_secret`: [3](#0-2) .
- Once verification passes, `WebhooksController#create` parses the same raw body again and dispatches it, unmodified, to registered handlers: [4](#0-3) .
- `Handlers::PushHandler#process` calls `stacks...find_each { |stack| stack.sync_github(...) }`: [5](#0-4) .
- `Handler#stacks`/`#repository_name` resolve the target `Repository` purely from `payload.dig('repository', 'full_name')`, with no reference to `repository.owner.login` or to which organization's secret verified the request: [6](#0-5) .
- `Stack#sync_github` enqueues `GithubSyncJob.perform_later(stack_id: id, ...)`: [7](#0-6) .

Because both `owner.login` and `full_name` are read from the same single JSON object the attacker fully controls, and because the HMAC only certifies "these bytes were signed with organization X's secret" without pinning X to the repository the payload actually claims to mutate, an attacker can craft: `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/private-repo"`, sign (or, if `OrgA` has no `webhook_secret` configured, need not even sign) the raw body, and have `verify_signature` pass for `OrgA` while the handler acts on `OrgB`'s stack. None of the listed guards (`drop_unhandled_event`, `ExplicitParameters` schema, `force_github_authentication`, `require_permission!`, model validators) check this cross-field consistency — `ExplicitParameters` only validates `ref`/`after` presence for `PushHandler`, not the relationship between `owner.login` and `full_name`.

### Impact Explanation
A successful request causes Shipit to enqueue `GithubSyncJob` for an arbitrary organization's stack the attacker did not authenticate for, which fetches commits via that stack's own `github_api`/token and appends them to the stack's commit history, potentially unlocking auto-deploys or merge queue behavior gated on branch head state — this is a cross-tenant write (`repository.full_name`'s owner) triggered by a payload authenticated only for a different tenant (`repository.owner.login`), matching the Critical category "a payload for one repository mutating another's stack." It is repeatable against any stack whose repository the attacker can name, for every push (or any other handled event, e.g. `status`, `check_suite`, `pull_request`) as long as one configured organization's secret is available to the attacker (most severely, an org with a blank `webhook_secret`).

### Likelihood Explanation
Exploitation requires: (1) the Shipit instance uses the multi-organization GitHub App configuration documented in `docs/setup.md`, and (2) at least one configured organization has a blank/misconfigured `webhook_secret`, or the attacker otherwise possesses a valid secret for some organization on the instance (e.g., they administer that org's own GitHub App installation). Given the "known/no `webhook_secret`" precondition explicitly permitted by the question, this is a low-cost, fully repeatable attack: a single crafted HTTP POST with a valid `X-Github-Event` header and a `full_name` naming any tracked repository. In single-organization deployments (the default single `github:` block, no per-org keys), `Shipit.github` ignores the `organization:` argument entirely and always resolves the one configured app/secret, so the divergence is not exploitable there — the risk is confined to multi-org installations.

### Recommendation
Bind signature verification and stack resolution to the same field. Concretely, in `WebhooksController`, derive the verifying organization from `repository.full_name`'s owner segment (the same value `Handler#repository_name`/`Repository.from_github_repo_name` will use) instead of `repository.owner.login`, or alternatively have `Handlers::Handler#stacks` cross-check that the resolved `Repository`'s owner matches the organization that verified the signature (pass it down from the controller) before acting. Additionally, treat organizations with a blank `webhook_secret` as unverifiable by default (fail closed) rather than silently returning `true` in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:

```ruby
test "push payload with mismatched owner/full_name orgs syncs the unverified org's stack" do
  # Configure two orgs; OrgA has a blank/no webhook_secret (permissible per GitHubApp#verify_webhook_signature).
  Shipit.stubs(:github).with(organization: 'OrgA').returns(
    Shipit::GitHubApp.new('OrgA', { webhook_secret: nil })
  )

  other_stack = shipit_stacks(:shipit) # belongs to "OrgB/private-repo" in fixtures/stub
  Shipit::Repository.stubs(:from_github_repo_name).with('OrgB/private-repo').returns(other_stack.repository)

  request.headers['X-Github-Event'] = 'push'
  payload = JSON.parse(payload(:push_master))
  payload['repository']['owner']['login'] = 'OrgA'          # verified org (no secret)
  payload['repository']['full_name']       = 'OrgB/private-repo' # acted-upon org
  expected_head_sha = payload['after']

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: other_stack.id, expected_head_sha:]) do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok
end
```

Assertions on both sides of the equality:
- Before: `organization_verifying_signature = 'OrgA'` (no/blank secret ⇒ `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-77`), while `organization_owning_target_stack = 'OrgB'` (from `full_name`, resolved in `app/models/shipit/webhooks/handlers/handler.rb:36-38`) — they differ.
- After: response is `:ok` (not `422`) and a `GithubSyncJob` is enqueued for `OrgB`'s stack — proving the mismatch was never caught and the sync happened despite the two organizations diverging.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
