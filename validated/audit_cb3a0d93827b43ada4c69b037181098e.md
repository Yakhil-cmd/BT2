### Title
CCMenu-issued API token is not scoped to a stack and `Api::CCMenuController#stack` bypasses the client's stack scope entirely, allowing unauthorized cross-stack `cc.xml` reads - ([File: app/controllers/shipit/ccmenu_url_controller.rb], [File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, which never sets `stack:` on the client, so the resulting token has `stack_id == nil`. Separately, `Api::CCMenuController#stack` resolves the target stack with `Stack.from_param!(params[:stack_id])` directly instead of the stack-scoped `stacks.from_param!` helper defined in `Api::BaseController`. Both facts independently mean the token authorizes reading `cc.xml` for any stack, not just the one the user requested the URL for.

### Finding Description
The binding the UI/feature implies is: `token.authorized_stack.id == stack.id` at issuance time in `app/controllers/shipit/ccmenu_url_controller.rb:8-9,15-18` (i.e., the CCMenu URL for stack A should only ever expose stack A's `cc.xml`). The actual code breaks this binding in two independent ways:

1. **Client is never stack-scoped.** In `CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`), the `find_or_create_by!` clause only matches on `creator` and `name`, and no `stack:` attribute is passed to `create_with`. The created/found `ApiClient` therefore always has `stack_id = nil`.
2. **`Api::BaseController#stacks`** (`app/controllers/shipit/api/base_controller.rb:74-76`) implements the intended scoping: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. Because the CCMenu client's `stack_id` is nil, this resolves to `Stack.all` for any consumer that uses this helper.
3. **`Api::CCMenuController#stack`** (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) does not even use the `stacks` helper - it calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` class, so even if the client's `stack_id` were correctly set, this specific controller would still ignore it.

`require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`) only calls `current_api_client.check_permissions!('read', 'stack')` (`app/models/shipit/api_client.rb:38-45`), which checks the `permissions` array (`["read:stack"]`) and has no notion of which stack the token is bound to. `require_permission!` never receives or checks `stack.id` against `current_api_client.stack_id`.

**Exploit flow:**
1. Attacker is an authenticated low-privilege Shipit user (owner of Stack A, a repo they legitimately administer/view, not a member of `Shipit.github_teams` for Stack B).
2. Attacker visits Stack A's settings page and triggers `GET /ccmenu/A_owner/A_repo/A_branch` → `CCMenuUrlController#fetch`, receiving a URL like `.../api/stacks/A_owner/A_repo/A_branch/ccmenu?token=<T>`.
3. Attacker substitutes Stack B's `stack_id` in the URL: `GET /api/stacks/B_owner/B_repo/B_branch/ccmenu?token=<T>`.
4. `Api::CCMenuController#authenticate_api_client` authenticates `<T>` successfully (`ApiClient.authenticate` only validates the signed client id, not the stack). `require_permission :read, :stack` passes because permissions include `read:stack`. `stack` resolves via `Stack.from_param!(params[:stack_id])` to Stack B, unscoped. The controller renders Stack B's `cc.xml`, exposing Stack B's last build status/label/time/webUrl - state the attacker was never granted via team membership.

No existing guard intercepts this: `verify_signature`/webhook checks are irrelevant (this is an authenticated API path), `ExplicitParameters` is not used here, and `User#authorized?`/GitHub team checks are never consulted for API-token requests - authorization is delegated entirely to `ApiClient#permissions` and (intended, but broken) `stack_id` scoping.

### Impact Explanation
Any authenticated low-privilege user who can view at least one stack can self-mint a token that reads `cc.xml` (last build status, label, time, web URL) for **every** stack in the Shipit instance, including stacks whose repositories/teams they have no access to. This is a repeatable, per-request escalation past repository/team-based authorization (`Shipit.github_teams`) into unauthenticated-equivalent read of stack build state for arbitrary tenants, matching the "High" impact category (escalation into `Shipit.github_teams` authorization / unauthorized read of stack state). The blast radius is instance-wide: a single click on "Fetch URL" for any one stack yields a token usable against all stacks.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs a normal Shipit session and view access to at least one stack (their own repository added to Shipit), which is the baseline the audit assumes is available to any authenticated low-privilege user. No secrets, no privileged role, and no GitHub-side action are required - just one authenticated GET to `/ccmenu/*stack_id` followed by substituting `stack_id` in the resulting token URL. This is trivially repeatable against arbitrary stacks and requires no special Shipit or GitHub configuration beyond having more than one stack registered.

### Recommendation
- In `CCMenuUrlController#client`, scope client lookup/creation to the specific stack, e.g. `find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')` and pass `stack: stack` into `create_with`, ensuring `ApiClient#stack_id` is always set to the requested stack.
- In `Api::CCMenuController#stack`, use the inherited `stacks.from_param!(params[:stack_id])` (the `BaseController`'s stack-scoped resolver) instead of calling `Stack.from_param!` directly on the class, so a stack-scoped client cannot resolve a different stack.
- Add a regression test asserting that a CCMenu token minted for stack A returns 404/not-found when used against stack B's `ccmenu` endpoint.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (conceptual addition)
test "a ccmenu token minted for stack A cannot read stack B's cc.xml" do
  stack_a = shipit_stacks(:shipit) # owned/viewable by @user, not in Shipit.github_teams for team_b
  stack_b = Stack.create!(repository: Repository.new(owner: "restricted", name: "repo"), branch: "main")

  # Simulate CCMenuUrlController#fetch for stack_a
  get :fetch, params: { stack_id: stack_a.to_param } # via CCMenuUrlController, not shown here
  token = ApiClient.find_by(creator: @user, name: 'CCMenu Client').authentication_token

  # Binding under test: client.stack_id should equal stack_a.id
  client = ApiClient.find_by(creator: @user, name: 'CCMenu Client')
  assert_equal stack_a.id, client.stack_id # EXPECTED after fix; currently nil -> FAILS

  # Attempt to read stack_b's cc.xml with the token minted for stack_a
  get :show, params: { stack_id: stack_b.to_param, token: token }
  assert_response :not_found # EXPECTED after fix; currently :ok -> vulnerability confirmed
end
```
This demonstrates the token issued for `stack_a` currently succeeds (`:ok`) against `stack_b`, proving the stack-scope binding is broken.
