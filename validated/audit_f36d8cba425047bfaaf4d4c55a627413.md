## Finding

### Title
Reward tokens are permanently lost during zero-stake periods due to `last_update_block` advancing without accruing `reward_per_token_stored` - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards` implements the same Synthetix-style "reward-per-token" accounting pattern described in the external report for `BlueberryStaking.sol`. When `total_tokens_staked` is zero, `reward_per_token()` returns the stored value unchanged (correctly skipping accrual), but the caller `update_pool_rewards()` unconditionally advances `last_update_block` to the current block regardless of whether any tokens were staked. Since the pool's reward budget is bounded by a fixed `expiry_block` and a `reward_rate_per_block`, any block range during which `total_tokens_staked == 0` is a period where reward tokens accrue against the clock but are never attributed to `reward_per_token_stored`, permanently skipping that window. This mirrors exactly the reported Blueberry defect: "if no tokens are deposited, the timestamp is still updated, causing all rewards during this period to be lost."

### Finding Description
`reward_per_token` short-circuits when nobody has staked: [1](#0-0) 

But every call site (`stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, `set_pool_expiry_block`) calls `update_pool_and_staker_rewards` / `update_pool_rewards`, which unconditionally sets `last_update_block` to "now": [2](#0-1) 

Reachable, no-privilege signed extrinsics `stake` and `unstake` are what mutate `total_tokens_staked` and trigger this update path: [3](#0-2) [4](#0-3) 

Reachable sequence (all via ordinary, non-privileged signed transactions once a pool exists):
1. Pool is created by the pool admin (`CreatePoolOrigin`) with `reward_rate_per_block` and `expiry_block` set; `last_update_block = 0`, `total_tokens_staked = 0`.
2. Staker A calls `stake`, accrual begins, `last_update_block` tracks correctly while `total_tokens_staked > 0`.
3. Staker A fully `unstake`s all tokens (a normal, permissionless action), bringing `total_tokens_staked` back to `0`. This call correctly finalizes `reward_per_token_stored` and `last_update_block` up to that point.
4. Time passes (`N` blocks) with `total_tokens_staked == 0` — nobody is required to be malicious; this can happen naturally (e.g., low liquidity / temporary full exit).
5. Staker B later calls `stake`. Because `total_tokens_staked` was `0` at the *start* of this call, `reward_per_token()` returns the unchanged `reward_per_token_stored` — correct, since no one should be credited for the empty period. However, `update_pool_rewards` still advances `last_update_block` to the current block, silently discarding the `N` blocks that elapsed while the pool was empty.

Because the pool's reward emission is bounded in time by `expiry_block` (not extended to compensate for empty periods) and pre-funded by the admin/community via `deposit_reward_tokens`, the `reward_rate_per_block * N` worth of tokens that "should" have been reserved for the dead window is neither attributed to any staker's `reward_per_token_stored` accrual, nor is the pool's timeline extended to make it up later. This is a permanent, unrecoverable accounting loss under normal use, matching the invariant violated in the source report: the reward clock keeps advancing during periods with a `totalSupply`/`total_tokens_staked` of zero, and the pallet has no mechanism to skip/rewind `last_update_block` for empty periods.

Unlike the Blueberry contract, the pallet does provide `cleanup_pool`, letting the admin reclaim the pool's remaining reward-asset balance and delete the pool entirely — but only when `PoolStakers` is empty, and this action destroys the pool (no way to just "pause the clock" and continue the same pool later). It also requires *admin* privilege and voluntary, unprompted action at exactly the right moment; it is not a resolution to the underlying accounting flaw, only a costly way to fully terminate the incentive program to avoid additional loss.

### Impact Explanation
Reward tokens deposited by the pool admin into the pool's dedicated account (`pool_info.account`) become permanently stranded for any block range in which `total_tokens_staked` is zero, since:
- `reward_per_token_stored` is never advanced for that window (by design, since nobody is owed anything at that instant), and
- `last_update_block` is unconditionally advanced past that window, so the window can never later be "recovered" retroactively even if a staker returns, and
- the pool's `expiry_block` is a fixed ceiling that does not get extended to compensate.

This directly causes a loss of value for the pool admin/community who funded the incentive program, and understates the true rewards available to stakers relative to what the emission schedule implies, without requiring any privileged action from the party triggering the loss (any staker fully unstaking, followed by a delay before restaking, is enough).

### Likelihood Explanation
High likelihood in practice: any pool can transiently reach a state where all stakers withdraw simultaneously (e.g., during market stress, or simply because a single/small staker base fully exits) — this requires only ordinary, permissionless `stake`/`unstake` calls, not privileged pool administration or any adversarial precondition beyond normal usage. The longer the empty period, the larger the loss, exactly as characterized in the original report.

### Recommendation
`update_pool_rewards` should not advance `last_update_block` past the current block when `total_tokens_staked` is (or was) zero for the intervening period; specifically, the reward-per-token computation and the timestamp advance should be coupled so that no block range is skipped without being either (a) correctly excluded from the reward-rate schedule (e.g., by tracking the last non-zero-supply timestamp separately and reserving unspent rewards), or (b) extending `expiry_block` to compensate for zero-supply gaps, similar to the recommended fix referenced in the Blueberry remediation (PR#29): "The timestamp should not be updated for a token if there is none of that token deposited/staked."

			let staker = ensure_signed(origin)?;

			// Always start by updating staker and pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			T::AssetsFreezer::increase_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

			let mut new_pool_info = pool_info.clone();
