### Title
Unrestricted `asset_attestors` list replacement by asset definer permanently freezes previously-attested holders' funds - ([File: validation.js, storage.js])

### Summary
An asset created with `spender_attested: true` requires every payment input/output author to be on the asset's current attestor list. The attestor list is not append-only or versioned per-holder; `storage.readAsset`/`filterAttestedAddresses` always resolve to the single latest `asset_attestors` unit. The asset's `definer_address` can post a new `asset_attestors` message at any time, as many times as desired, with `onlyOwner`-like unilateral control analogous to `UXDController.setRedeemable`, instantly and irreversibly dropping any attestor (and therefore any previously-attested holder) not included in the new list.

### Finding Description
The asset is defined once with `spender_attested`/initial `attestors` in `validateAssetDefinition` (`validation.js`), and afterwards the definer alone may update the attestor list via a standalone `asset_attestors` message, validated in `validateAttestorListUpdate`: [1](#0-0) 
This function only checks that the sender is `objAsset.definer_address` and that the new list is well-formed (`checkAttestorList`) — there is no restriction on how often the list may change, no requirement to include previously-approved attestors, and no grandfathering of holders already attested under an older list.

When resolving which attestor list is authoritative, `storage.readAsset` looks up only the most recent `asset_attestors`-bearing unit for the asset: [2](#0-1) 

`filterAttestedAddresses` then checks holder addresses strictly against `objAsset.arrAttestorAddresses` (the latest list) and requires the attestation itself to be newer than any subsequent `address_definition_change` for that holder: [3](#0-2) 

Finally, `validatePayment` enforces that every author of a transfer be present in `arrAttestedAddresses` before allowing the transfer/issue to proceed: [4](#0-3) 

Because the "authoritative" attestor set is a single mutable pointer entirely controlled by the definer (exactly like the privileged, repeatedly-callable `setRedeemable`), a definer can swap out the attestor set to exclude specific attestors (and thus their previously-attested users) at will, even long after those users acquired and were validly attested to hold the asset.

### Impact Explanation
Any holder of a `spender_attested` asset who was legitimately attested under an older attestor list becomes unable to satisfy `validatePayment`'s `objAsset.arrAttestedAddresses` check the moment the definer republishes a new `asset_attestors` list that omits the attestor who vouched for them. Their asset balance becomes permanently locked/frozen (cannot be transferred or spent) unless the definer chooses to re-include a compatible attestor and the user obtains a fresh attestation — a scenario structurally identical to the reported bug ("old UXD can't be redeemed... need a migration contract"), except here funds are simply frozen with no migration path defined by the protocol at all. This is a fund-freezing issue reachable by any user who merely holds such an asset, triggered by a single privileged party's unit.

### Likelihood Explanation
Any asset issuer choosing `spender_attested: true` can perform this at will with a single, cheaply composed `asset_attestors` unit (`composer.js`), requiring no cooperation from holders and no special conditions — the change takes effect for all existing holders as soon as the unit is stable.

### Recommendation
Preserve backward compatibility for holders already attested under a prior list: either (a) do not allow "shrinking" the attestor set for addresses previously vouched for by a since-removed attestor without an explicit migration mechanism, or (b) evaluate `filterAttestedAddresses` against the attestor list that was current when the holder's attestation was made rather than only the newest list, or (c) require the previous attestors to co-sign/approve any attestor-list update. At minimum, document this trust assumption clearly since it currently allows an asset definer to unilaterally freeze arbitrary holders' balances at any time.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true`, `attestors: [X]` (`validateAssetDefinition`, `validation.js:2725-2827`).
2. Attestor X attests holder H's address; H legitimately receives/holds asset A (validated per `filterAttestedAddresses`).
3. Definer posts an `asset_attestors` message replacing the list with `attestors: [Y]` (excluding X) — accepted per `validateAttestorListUpdate` (`validation.js:2829-2847`) with no restriction beyond definer authorship.
4. `storage.readAsset` now resolves `arrAttestorAddresses = [Y]` (`storage.js:1917-1946`).
5. H attempts to transfer/spend asset A; `filterAttestedAddresses` (`storage.js:1960-1974`) no longer finds H attested (since attestor X is no longer in the list), so `validatePayment` (`validation.js:2115-2122`) rejects with "none of the authors is attested" — H's funds are frozen indefinitely.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
