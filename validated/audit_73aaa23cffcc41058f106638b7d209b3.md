### Title
`Team.find_or_create_by!(github_id:)` is not scoped by `organization`, and the `teams` table has no unique constraint on `github_id` at all — ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The `shipit_teams` (`teams`) table's only unique index is `["organization", "slug"]`; there is no unique index — scoped or unscoped — on `github_id`. `MembershipHandler#find_or_create_team!` looks up `Team` purely by `github_id`, so a `membership` webhook payload whose `team.id` matches an already-persisted team's `github_id` will resolve to that existing `Team` record regardless of the `organization.login` value in the payload.

### Finding Description
The binding the question asks me to check is: `uniqueness(github_id in Shipit teams table)` == `uniqueness(team identity across organizations as GitHub models it)`. Tracing the schema at [1](#0-0)  shows the `teams` table only has `t.index ["organization", "slug"], name: "index_teams_on_organization_and_slug", unique: true` — there is no unique (or any) index on `github_id` alone. The lookup path is `Team.find_or_create_by!(github_id: params.team.id) do |team| team.github_team = params.team; team.organization = params.organization.login end` in [2](#0-1) . `find_or_create_by!` first runs `find_by(github_id: ...)` with no `organization` filter; if a row is found, the block (which would set `organization`) never runs, and the pre-existing team's `organization`/`members` association is what gets mutated by the subsequent `team.add_member(member)` / `team.members.delete(member)` calls at [3](#0-2) .

So the two sides of the equality diverge: on GitHub, team ids are globally unique per-org-team (collision-free), but Shipit's schema does not encode any constraint tying `github_id` to `organization`, and the finder code does not add that filter either. If any Team row already exists in Shipit's DB with `github_id = X` (created from Organization A's earlier legitimate membership event), then any `membership` webhook — even one nominally addressed to a different `organization.login` — that carries `team.id = X` will resolve to that same Team row and mutate its `memberships`.

### Impact Explanation
This confirms the root-cause piece of the cross-tenant Team/Membership escalation: the ORM-level lookup used to resolve incoming webhooks to a `Team` record has no organizational scoping, and the database provides no independent safety net (no unique index on `github_id`, scoped or otherwise) that could have masked or prevented this. Whether this is independently exploitable by an unprivileged attacker still depends on the ability to get a `membership` event accepted at all — that is gated by `GitHubApp#verify_webhook_signature` / the webhook secret checks in `Shipit::WebhooksController`, which I was not able to fully re-trace in this pass (ran out of tool budget before reading `app/controllers/shipit/webhooks_controller.rb` and `lib/shipit/github_app.rb` in full). If that upstream signature gate is bypassable or the webhook secret is shared/global across organizations (as established in a prior/companion audit in this chain), then this `github_id`-only, unscoped lookup is the mechanism that lets a payload nominally signed for/addressed to attacker-controlled Organization A silently attach or remove members on a Team belonging to victim Organization B — an authorization-boundary violation matching the "escalation into `Shipit.github_teams` authorization" / cross-tenant record mutation category.

### Likelihood Explanation
Confirmed at the model/schema layer: `teams` has no unique constraint on `github_id`, and the handler queries by `github_id` alone. Full exploitability by a fully unprivileged attacker (no webhook secret, no API token) hinges on whether a `membership` webhook can be delivered/accepted for an arbitrary or attacker-influenced `organization` value in the first place — I could not verify `verify_signature`/`GitHubApp#verify_webhook_signature` behavior in this pass, so I cannot independently confirm the full end-to-end exploit chain here; that portion should be validated against the specific webhook-signature-verification question in this audit series.

### Recommendation
Scope the lookup to the organization asserted in the payload, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and add a corresponding unique DB index/migration on `["organization", "github_id"]` (or at minimum validate that an existing record with a matching `github_id` but different `organization` raises instead of silently reusing the row).

### Proof of Concept
```ruby
# test/models/team_test.rb (schema/model proof, no live GitHub)
test "find_or_create_by!(github_id:) is not scoped by organization" do
  team_a = Shipit::Team.create!(github_id: 42, organization: 'org-a', slug: 'core')

  # Simulate MembershipHandler#find_or_create_team! logic for org-b claiming the same github_id
  resolved = Shipit::Team.find_or_create_by!(github_id: 42) do |t|
    t.organization = 'org-b'
    t.slug = 'other'
  end

  assert_equal team_a.id, resolved.id
  assert_equal 'org-a', resolved.organization # unchanged: cross-org collision resolved to org-a's team
end

test "teams table has no unique index scoped to (or including) github_id alone" do
  indexes = ActiveRecord::Base.connection.indexes(Shipit::Team.table_name)
  github_id_only = indexes.select { |i| i.unique && i.columns == ['github_id'] }
  org_scoped = indexes.select { |i| i.unique && i.columns.include?('github_id') && i.columns.include?('organization') }

  assert_empty github_id_only
  assert_empty org_scoped
end
```
This demonstrates both halves of the claimed binding are false: `github_id` is not DB-unique on its own, and `find_or_create_by!(github_id:)` performs no organization scoping, so a colliding/attacker-supplied `team.id` resolves to a pre-existing team from a different organization.
