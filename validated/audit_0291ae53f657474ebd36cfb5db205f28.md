## Analysis

The Move bug's root cause is: a map is populated from validator-submitted (attacker-controllable) registration keys via a raw insertion (`vec_map::insert`), and when that key collides with an existing entry, the insertion **aborts/panics**, permanently blocking a critical system transition (`try_create_next_committee` / end-of-epoch).

The closest analog in this codebase is `BLSPubkeyToRankMap::new` in `runtime/src/epoch_stakes.rs`, which builds the BLS-pubkey-to-rank map used for Alpenglow certificate verification and consensus. This map is keyed by validator-supplied data (`bls_pubkey_compressed`, `node_pubkey`), and rows with duplicate BLS pubkeys or duplicate node pubkeys are filtered out entirely before computing `total_stake`: [1](#0-0) 

Critically, after filtering out duplicate-keyed entries, the code computes the sum of the remaining stakes and then does: [2](#0-1) 

`NonZero::new(total_stake).expect("total stakes should not be 0")` — an explicit `panic!` if every valid, staked, BLS-registered vote account happens to be excluded by the duplicate-BLS-pubkey/duplicate-node-pubkey filter. There is an existing test that reproduces exactly this panic condition: [3](#0-2) 

This function is invoked lazily and deterministically from `bls_pubkey_to_rank_map()`, called from consensus-critical code paths (`votor/src/consensus_pool.rs`, `runtime/src/bank.rs`, `runtime/src/validated_block_finalization.rs`, `runtime/src/validated_reward_certificate.rs`): [4](#0-3) 

Because `bls_pubkey` is set via a normal, unprivileged `VoteAuthorize::VoterWithBLS` authorize transaction (attacker-chosen bytes, only constrained by proof-of-possession of the corresponding secret key — an attacker can always generate a fresh BLS keypair and its own PoP, but can also simply **reuse the compressed BLS public key bytes of an existing large-stake validator**, since PoP verification is done at authorize-time against the submitted key itself, not against uniqueness across validators), a low-stake attacker can register a new vote account whose BLS pubkey (or node pubkey, if node identities are permitted to collide) matches that of the dominant staked validator. This causes both entries to be excluded from the filtered set. If the affected validator holds the overwhelming majority of BLS-registered stake (a very plausible situation, e.g. a devnet/testnet with a small validator set, or in a permissioned/bootstrap network), `total_stake` after filtering becomes `0`, triggering the panic deterministically on every validator that computes `bls_pubkey_to_rank_map()` for that epoch — since epoch stakes and vote-account state are consensus data, all validators compute the same result and crash simultaneously.

I could not fully verify within the remaining budget (i) whether PoP verification is bound to global uniqueness of BLS keys elsewhere in the vote program (which would prevent this collision path outright), and (ii) the exact set of call sites where this panic is unconditionally reached versus reached only behind a `Result`/`catch_unwind` boundary in `bls_sigverify`. These would need to be confirmed by reading `programs/vote/src/vote_state/mod.rs` (BLS authorize instruction) and `bls-sigverify/src/bls_sigverifier.rs` more closely, and by tracing whether `bls_pubkey_to_rank_map()` calls in `runtime/src/bank.rs` are wrapped in graceful error handling or execute directly in the bank-processing hot path (which would turn a panic into a validator crash / cluster halt).

### Title
Validator-Controlled BLS/Node Pubkey Collisions Can Zero Out Filtered Stake and Trigger a Deterministic Panic in `BLSPubkeyToRankMap::new` - (File: `runtime/src/epoch_stakes.rs`)

### Summary
`BLSPubkeyToRankMap::new` filters out any vote-account entry whose BLS pubkey or node pubkey collides with another entry, then panics via `.expect("total stakes should not be 0")` if the remaining filtered stake sums to zero. Because BLS pubkeys are attacker-influenced (set via a normal authorize transaction) and node pubkeys are validator identity addresses that are not guaranteed globally unique by the vote program, an unprivileged actor can craft a collision against the dominant staked validator's entry, causing all (or all remaining) valid entries to be excluded and the total filtered stake to become zero.

### Finding Description
This mirrors the reported Move bug class: a map/aggregation built from attacker-influenced registration data uses an operation (insert/filter followed by an invariant check) that aborts the entire operation on a name collision, rather than gracefully rejecting only the colliding registration. In the Move code this manifested as `vec_map::insert` aborting; here it manifests as an `.expect()` panic after duplicate-key filtering zeroes out the aggregate stake.

### Impact Explanation
`bls_pubkey_to_rank_map()` is consumed by consensus-critical code (`votor/src/consensus_pool.rs`, `runtime/src/bank.rs`, `runtime/src/validated_block_finalization.rs`, `runtime/src/validated_reward_certificate.rs`). Because epoch stakes/vote account state are part of consensus state, all validators would compute the same input and hit the same panic deterministically — a transaction-triggered, cluster-wide halt (matches the "Analog Scan" acceptance criterion for a transaction-triggered cluster halt), analogous to how the Move bug prevented all validators from completing the epoch transition.

### Likelihood Explanation
Likelihood depends on stake concentration: this is most severe in small validator sets (bootstrap/devnet/testnet, or permissioned early-mainnet-like configurations) where one validator holds the bulk of BLS-registered stake, since the attacker only needs to zero out the *filtered* stake, not all stake. In highly decentralized, large validator sets this is harder to trigger but not impossible if the top-N BLS-registered validators can be targeted collectively. I was not able to fully confirm the exact PoP/uniqueness constraints enforced at BLS-authorize time in the remaining scope, which affects how easily an attacker can produce a colliding key against a target validator's public BLS key.

### Recommendation
Do not panic on zero filtered stake. Instead, when duplicate BLS/node pubkeys cause the filtered stake to reach zero, fall back to an empty/degenerate `BLSPubkeyToRankMap` (matching the already-existing `is_empty()` accessor) and have callers handle the empty-map case gracefully, exactly as the Move fix restricted registration to prevent the colliding scenario in the first place (i.e., also consider enforcing global uniqueness of `bls_pubkey` at authorize-time in the vote program).

### Proof of Concept
1. Bootstrap/target network where validator `V` holds a large majority of BLS-registered stake, with BLS pubkey `B_V`.
2. Attacker creates a new vote account `A` with minimal stake and sets `VoteAuthorize::VoterWithBLS` using the same compressed BLS pubkey bytes `B_V` (with attacker's own valid proof-of-possession over that reused key, since PoP is not required to be checked against global registry uniqueness).
3. At epoch boundary, `BLSPubkeyToRankMap::new` counts `bls_pubkey_counts[B_V] == 2`, filtering out both `V`'s and `A`'s entries from `keys_stake_entry_with_compressed`.
4. If `V` was the only/majority BLS-valid staked entry, `total_stake` sums to `0`, and `NonZero::new(0).expect("total stakes should not be 0")` panics — reproducing the exact condition already codified in the existing test `test_multiple_vote_accounts_panics`: [3](#0-2) .
