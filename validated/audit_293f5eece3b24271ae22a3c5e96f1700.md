### Title
Cleartext Logging of Private Payment Chain Contents (blinding factors, addresses, amounts) - ([File: indivisible_asset.js])

### Summary
The bug class from the SaltStack advisory (cmdmod logging credentials to info/error log level) maps onto `ocore`'s handling of private (indivisible) asset payment chains. Full plaintext contents of private payment chains — including per-output `blinding` factors, recipient `address`, and `amount` — are written to `console.log` during normal processing of a private payment received from any counterparty over the wire, not just in a debug path.

### Finding Description
`validateAndSavePrivatePaymentChain` in `indivisible_asset.js` logs the complete chain and every output right before persisting it: [1](#0-0) [2](#0-1) 

This function is reached from `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`, invoked whenever an unprivileged private-payment counterparty (or a paired device) sends a `private_payment` message via `wallet.handlePrivatePaymentChains`: [3](#0-2) 

The private-payment security model relies on the `blinding` value and `address` being disclosed only to the intended parties over an end-to-end encrypted device channel (see the field deletion when constructing hidden payloads in `buildPrivateElementsChain`): [4](#0-3) 

The `console.log("saving private chain "+JSON.stringify(arrPrivateElements))` call defeats this by placing the full un-hidden chain (with `blinding`, `address`, `amount`) into the process's standard log stream. Similarly, `forwardPrivateChainsToOtherMembersOfOutputAddresses` logs the full `arrChains` object, and `emitNewPrivatePaymentReceived` logs `assocAmountsByAsset`: [5](#0-4) [6](#0-5) 

Any process, log-forwarding integration, crash reporter, or log-aggregation pipeline (common in Node.js deployments where `console.log` is captured to files or shipped to third-party services) that has visibility into the node's stdout/log output gains the blinding factors and full transaction graph for private assets — data that is supposed to be secret to preserve the privacy guarantee and unlinkability of private-asset transfers.

### Impact Explanation
Exposure of `blinding` and output `address`/`amount` breaks the confidentiality guarantee of private (indivisible) asset payments (CWE-312/CWE-522, matching the SaltStack advisory's classification). An entity with access to the log stream (e.g., through a compromised or misconfigured logging/monitoring integration, not requiring hub-operator or node-root privilege) can de-anonymize private payment chains, learn who paid whom and how much, and reconstruct the full private-asset transfer graph that the encrypted device-messaging design intends to keep confidential. This does not directly let an attacker create unauthorized spends, but it is a concrete, unauthorized information-disclosure of transaction-sensitive secrets tied to the private-payment protocol, consistent with the "Cleartext Storage of Sensitive Information" bug class and CWE mapping in the advisory.

### Likelihood Explanation
The logging occurs unconditionally on every successful private-payment chain validation/save, triggered simply by any counterparty sending a valid `private_payment` device message. No special privilege is required by the sender to cause the log write to occur on the receiving node; the only requirement for exploitation is the ability to observe that node's logs, which is common in production Node.js deployments using log shipping, error/telemetry integrations, or shared hosting.

### Recommendation
Remove or redact the `console.log` statements in `validateAndSavePrivatePaymentChain` (and the analogous ones in `forwardPrivateChainsToOtherMembersOfOutputAddresses` / `emitNewPrivatePaymentReceived`) that print `blinding`, `address`, or full private-element/chain contents. If diagnostic logging is required, log only non-sensitive identifiers (e.g., `unit`, `message_index`) and never `blinding` or plaintext output `address`/`amount` for private assets.

### Proof of Concept
1. Configure a full node with any external log aggregation/monitoring hook on stdout (a realistic, common Node.js deployment pattern).
2. From any wallet/device, send a private-asset payment (indivisible asset) to the node's address via the standard `private_payments`/`private_payment` device-message flow.
3. Observe the node's log output produced by `console.log("saving private chain "+JSON.stringify(arrPrivateElements))` in `indivisible_asset.js:243` and `console.log("inserting output "+JSON.stringify(output))` at line 272 — the log contains the private `blinding` value, recipient `address`, and `amount` for the transferred output, which under the protocol design should only be known to the sender/recipient/cosigners via the encrypted device channel.
