### Title
No Minimum Transfer Value Enables Cost-Asymmetric Spam to Drain Bridge Operator Funds and Block Legitimate Transfers — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The Kaia service-chain bridge accepts KLAY transfer requests with no lower bound on the transferred value beyond `msg.value > _feeLimit`. When `feeOfKLAY = 0` (the contract default), a single wei satisfies the guard. Because the bridge operator's Go daemon (`SubBridge`) must submit one `handleKLAYTransfer` transaction on the parent chain per request, an attacker can cheaply flood the service chain with dust requests and force the operator to pay parent-chain gas for every one of them. The sequential nonce ordering of the bridge means the operator cannot skip spam nonces without permanently blocking all higher-nonce legitimate transfers.

---

### Finding Description

**On-chain request side — no minimum value guard**

`_requestKLAYTransfer` in `BridgeTransferKLAY.sol` contains only one value check:

```solidity
require(msg.value > _feeLimit, "insufficient amount");   // line 109
``` [1](#0-0) 

`_feeLimit` is set to `feeOfKLAY`, which is initialised to `0` in `BridgeFee.sol` and remains `0` unless operators explicitly change it:

```solidity
uint256 public feeOfKLAY = 0;
``` [2](#0-1) 

With `feeOfKLAY = 0`, the guard reduces to `msg.value > 0`, so a 1-wei deposit is accepted and increments `requestNonce`.

The ERC-20 path has the same property — the only guard is `require(_value > 0, "zero ERC20 token amount")`, meaning 1 token-unit is sufficient: [3](#0-2) 

**Off-chain handling side — one parent-chain tx per request, no skip allowed**

The `SubBridge` daemon's `handleRequestValueTransferEvent` submits exactly one `HandleKLAYTransfer` (or `HandleERC20Transfer`) transaction on the parent chain for every event it dequeues: [4](#0-3) 

The `loop()` goroutine calls `processingPendingRequestEvents` every second and on every new event, draining the sorted pending queue in nonce order: [5](#0-4) 

The pending-event queue is created with `bridgepool.UnlimitedItemSortedMap` — there is no cap on how many events can accumulate: [6](#0-5) 

**Sequential nonce ordering creates a lose-lose situation**

`_updateHandleNonce` advances `lowerHandleNonce` only when a contiguous prefix of nonces has been handled (up to a window of 200): [7](#0-6) 

`_lowerHandleNonceCheck` rejects any nonce below `lowerHandleNonce`: [8](#0-7) 

If the operator skips a spam nonce, `lowerHandleNonce` never advances past it, and every legitimate transfer with a higher nonce is permanently blocked on-chain. The value-transfer recovery (`vt_recovery.go`) will also keep re-queuing unhandled events (up to `maxPendingTxs = 1000` at a time), compounding the pressure: [9](#0-8) 

The `ChildChainEventHandler.ProcessRequestEvent` adds every observed event to the counterpart bridge's pending queue with no value filter: [10](#0-9) 

---

### Impact Explanation

| Asset / State | Effect |
|---|---|
| Bridge operator's KAIA (parent chain) | Drained by gas costs of N `handleKLAYTransfer` txs, one per spam request |
| Legitimate bridged KAIA / ERC-20 | Stuck: `lowerHandleNonce` cannot advance past unhandled spam nonces, so higher-nonce legitimate transfers cannot be settled |
| Bridge liveness | Operator faces a binary choice: pay unbounded gas or halt all pending legitimate transfers |

The blocking of legitimate bridged-asset settlement is a protected-state impact (bridged assets cannot be withdrawn/transferred), not merely a gas-cost issue.

---

### Likelihood Explanation

- The service chain is designed to be low-cost; 1-wei KLAY transfers are valid and cheap.
- `feeOfKLAY = 0` is the contract default and is common in practice.
- Even with a non-zero fee, the fee accrues to `feeReceiver`, not to the bridge operator; the operator still pays parent-chain gas per handle tx.
- No rate-limiting, no minimum-value enforcement, and an unlimited pending queue exist anywhere in the path from `requestKLAYTransfer` to `handleRequestValueTransferEvent`.
- The attack requires only a funded address on the service chain and knowledge of the bridge contract address — both are publicly available.

---

### Recommendation

1. **Enforce a minimum transfer value** in `_requestKLAYTransfer` and `_requestERC20Transfer` that is large enough to cover the expected parent-chain gas cost of the corresponding `handle*Transfer` call:
   ```solidity
   uint256 public minTransferValue = 0;
   require(msg.value.sub(_feeLimit) >= minTransferValue, "below minimum transfer value");
   ```
2. **Ensure the bridge fee covers parent-chain execution cost.** Document and enforce that `feeOfKLAY` must be set to at least the expected gas cost of `handleKLAYTransfer` on the parent chain.
3. **Add a per-address rate limit** in the Go daemon (`processingPendingRequestEvents`) so that a single address cannot monopolise the pending queue.
4. **Cap the pending-event queue** (`UnlimitedItemSortedMap`) to a bounded size to prevent unbounded memory and processing growth.

---

### Proof of Concept

```
// Service chain (cheap)
for i in range(10_000):
    bridge.requestKLAYTransfer{value: 1 wei}(attacker, 0, "")
    // Each call: ~21 000 gas at ~1 gwei = ~0.000021 KAIA
    // Total cost: ~0.21 KAIA

// Parent chain (expensive) — bridge operator is forced to submit:
for nonce in range(10_000):
    bridge.handleKLAYTransfer(txHash, attacker, attacker, 1, nonce, blockNum, "")
    // Each call: ~80 000 gas at ~250 gwei = ~0.02 ETH (or equivalent parent-chain cost)
    // Total operator cost: ~200 ETH equivalent

// If operator stops at nonce K < 10_000:
//   lowerHandleNonce stays at K
//   All legitimate transfers with nonce > K are permanently blocked on-chain
```

The attacker spends ~0.21 KAIA; the operator is forced to spend orders of magnitude more, or sacrifice all pending legitimate transfers.

func (bi *BridgeInfo) loop() {
	ticker := time.NewTicker(time.Second)
	defer ticker.Stop()

	logger.Info("start bridge loop", "addr", bi.address.String(), "onChildChain", bi.onChildChain)

	for {
		select {
		case <-bi.newEvent:
			bi.processingPendingRequestEvents()

		case <-ticker.C:
			bi.processingPendingRequestEvents()

		case <-bi.closed:
			logger.Info("stop bridge loop", "addr", bi.address.String(), "onChildChain", bi.onChildChain)
			return
		}
	}
}

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}

func (cce *ChildChainEventHandler) ProcessRequestEvent(ev IRequestValueTransferEvent) error {
	addr := ev.GetRaw().Address

	handleBridgeAddr := cce.subbridge.bridgeManager.GetCounterPartBridgeAddr(addr)
	if handleBridgeAddr == (common.Address{}) {
		return fmt.Errorf("there is no counter part bridge of the bridge(%v)", addr.String())
	}

	handleBridgeInfo, ok := cce.subbridge.bridgeManager.GetBridgeInfo(handleBridgeAddr)
	if !ok {
		return fmt.Errorf("there is no counter part bridge info(%v) of the bridge(%v)", handleBridgeAddr.String(), addr.String())
	}

	// TODO-Kaia need to manage the size limitation of pending event list.
	handleBridgeInfo.AddRequestValueTransferEvents([]IRequestValueTransferEvent{ev})
	return nil
}
