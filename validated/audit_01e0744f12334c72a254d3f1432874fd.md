### Title
Webhook signature verification keyed on `repository.owner.login` while event processing acts on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to check the `X-Hub-Signature` against using `repository_owner`, a value read directly from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`). Once verification passes, the event handler that actually decides what gets written (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`) reads a *different* field from that same untrusted body: `payload.dig('repository', 'full_name')`. The signature never covers a binding between "which org's secret validated this request" and "which repository this request is allowed to mutate."

### Finding Description [1](#0-0) 

`verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(...)`. `repository_owner` is taken from the request body itself, not from any authenticated source:

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`GitHubApp#verify_webhook_signature` in [2](#0-1)  explicitly short-circuits to `true` when no `webhook_secret` is configured for that organization:

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

The setup documentation marks `webhook_secret` as **optional**: [3](#0-2) . This is a normal, documented configuration state for a Shipit GitHub App, not a deviation from documented deployment.

After the (possibly vacuous) signature check passes, the actual handler dispatch resolves the target `Repository`/`Stack` using a completely separate field from the same attacker-controlled payload: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack whose branch matches: [5](#0-4) .

**The broken equality:** the organization whose (possibly absent) secret authenticated the request (`repository.owner.login`, checked in the controller) is never bound to the repository whose stacks get mutated (`repository.full_name`, read independently in the handler). An attacker only needs to name, in the `repository.owner.login` field, any organization configured on the Shipit instance with a blank `webhook_secret` — while setting `repository.full_name` to the full name of an entirely different, victim repository that does have real stacks configured (potentially under an org that *does* have a webhook secret, which the attacker never needs to know). The unsigned/unauthenticated field decides "is this accepted," the independent field decides "what does it act on."

### Impact Explanation
This lets an unauthenticated, unprivileged attacker directly POST to `/webhooks` and drive `Stack#sync_github` for any stack tracked by Shipit, as long as the Shipit installation has at least one configured GitHub organization without a `webhook_secret` (a documented-optional, common single-tenant setup). Forcing `sync_github(expected_head_sha:)` on arbitrary stacks can corrupt commit/deploy state and, for stacks with `continuous_deployment` enabled, drive `ContinuousDeliveryJob`/deploy triggering off attacker-fabricated commit data — an unauthorized deploy path, matching the Critical impact category ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
No credentials, session, API token, or knowledge of any webhook secret are required — only that some organization configured on the instance has `webhook_secret` unset (explicitly permitted by setup docs), which is a realistic and common deployment state, especially for single-organization installs where operators skip the "optional" secret field. The endpoint is unauthenticated by design (webhook ingress) and the payload shape is entirely attacker-controlled JSON.

### Recommendation
Bind the identity used for signature verification to the identity used for resolving the target repository/stack: verify the signature using the organization that actually owns the `repository.full_name` being acted upon (or reject payloads where `repository.owner.login` doesn't match the owner segment of `repository.full_name`). Additionally, do not treat a missing `webhook_secret` as "verification passes" — either require a secret for every configured organization or fail closed when the secret is absent, rather than defaulting to trust.

### Proof of Concept
1. Configure Shipit with two orgs: `attacker-org` (no `webhook_secret`) and `victim-org` (has stacks, may or may not have a secret).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of any (or no) `X-Hub-Signature` header.
4. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `repository_name` resolves to `victim-org/victim-repo`, syncing/mutating stacks belonging to `victim-org` — a repository the attacker never authenticated for.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
