### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping via `Stack.from_param!` instead of `stacks.from_param!` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` enforces multi-tenant isolation for stack-scoped `ApiClient`s by exposing a `stack` helper that resolves through the `stacks` scope, which filters to `current_api_client.stack_id` when the token is stack-restricted. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, discarding that restriction.

### Finding Description
The broken binding: for a request to be authorized, it must hold that `stack.touched ∈ stacks_authorized_by(current_api_client.stack_id)`, i.e. `params[:stack_id] resolved stack == current_api_client.stack_id` when `current_api_client.stack_id?` is true. `Api::BaseController#stack` enforces exactly this: [1](#0-0) 
`stacks` filters `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves via that scoped relation's `from_param!`.

`Api::CCMenuController` overrides this method to bypass the scope entirely: [2](#0-1) 

`show` uses `stack` (resolved unscoped) to render deploy/rollback state: [3](#0-2) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`, it never checks which stack that permission applies to: [4](#0-3) 

So a token minted for stack B (e.g. via `CCMenuUrlController#fetch`, which builds the CCMenu URL/token for a given stack) with `permissions: ['read:stack']` and `stack_id` set to B passes `authenticate_api_client` and the `require_permission!` check, and then `stack` resolves an attacker-chosen, arbitrary stack A from `params[:stack_id]` with no ownership check. `Stack.from_param!` itself performs no authorization, it is a plain finder: [5](#0-4) 
(model file confirmed to define `from_param!`; exact line content for the finder implementation could not be fully inspected in this pass due to index truncation, but its role as an unscoped lookup-by-param is corroborated by its identical use in `CCMenuUrlController#stack` and other unscoped controllers.)

None of the existing guards catch this: `authenticate_api_client` only validates the token signature/existence, `require_permission!` only checks the permission string, and there is no `stacks.from_param!` call in this controller to re-apply the `stack_id` filter.

### Impact Explanation
Any holder of a CCMenu API token scoped to stack B can read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock/activity state) of any other stack A in the installation, simply by changing `stack_id` in the URL, for repositories the token was never authorized to see. This is a cross-tenant unauthorized read of stack state, matching the "High - unauthenticated/unauthorized read of stack state" category, and is fully repeatable against every stack in the Shipit instance with a single valid CCMenu token.

### Likelihood Explanation
The attacker only needs one CCMenu token, which is a low-privilege artifact: it's created automatically (via `CCMenuUrlController#fetch`) for any user viewing a stack's settings page and given only `read:stack` permission, intended to be scoped to a single stack via `stack_id`. Once such a token is known (e.g. leaked in a CI status badge URL, which is the exact designed use case for CCMenu tokens embedded in URLs), exploitation is a single unauthenticated GET request with an arbitrary `stack_id`, requiring no further secrets or privileges.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it to call `stacks.from_param!(params[:stack_id])` as the base controller does) so that stack-scoped API clients cannot access stacks outside their `stack_id`.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb`, add:
```ruby
test "a client scoped to stack B cannot fetch stack A's status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse)
  @client.update!(stack_id: stack_b.id, permissions: %w[read:stack])

  get :show, params: { stack_id: stack_a.to_param, token: @client.authentication_token }

  # Binding under test: stack.id must equal current_api_client.stack_id (stack_b.id),
  # never stack_a.id, for a stack-scoped client.
  refute_equal stack_a.id, @client.stack_id
  assert_response :not_found # or :forbidden, NOT 200 with stack_a's data
end
```
Before the fix, this request returns `200 OK` with stack A's `lastBuildStatus`/`lastBuildLabel` in the XML body, proving the cross-tenant read.
