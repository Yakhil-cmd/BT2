### Title
Webhook signature is bound to `repository.owner.login`, but all handlers act on the unverified `repository.full_name` field, allowing an authenticated organization's signature to be replayed against a different repository/stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The `WebhooksController` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')`, but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the actual stack/repository to act on using a completely different, unverified field: `payload.dig('repository', 'full_name')`. Because these two fields are never cross-checked, a webhook payload that authenticates as one organization's repository can still cause writes against a stack belonging to an entirely different repository, breaking the equality "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload and fetches the corresponding GitHub App config to verify the HMAC signature: [1](#0-0) [2](#0-1) 

The verification only guarantees that `repository.owner.login` (or `organization.login`) matches an organization whose secret correctly signed the raw body. However, once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire, unconstrained* payload to handlers: [3](#0-2) 

Every handler resolves the target stacks via `repository_name`, which reads `payload.dig('repository', 'full_name')` — a separate JSON field never compared against the `owner.login` value used for signature selection: [4](#0-3) 

For example, `PushHandler` (and equivalents for status, check_suite, pull_request, membership, etc.) acts purely on this unverified `full_name`: [5](#0-4) 

Compounding this, `verify_webhook_signature` short-circuits to `true` whenever the configured organization has no `webhook_secret` set — a state that Shipit's own documented setup config explicitly allows: [6](#0-5) [7](#0-6) 

This mirrors the Aave-v3 "isolation mode" bug class: a single restrictive/authenticating attribute (Morpho's Aave position / here, `repository.owner.login`) is checked, but the actual operative state (Aave collateral status / here, the repository actually written to via `full_name`) is a separate value that the check never constrains. An attacker only needs the signing organization's `owner.login` to be *any* configured (and ideally secretless) organization — the repository actually mutated is chosen independently.

### Impact Explanation
An unprivileged, unauthenticated network attacker (no Shipit session, no `ApiClient` token) can submit a forged webhook whose `repository.owner.login` satisfies signature verification (trivial if any configured org has no `webhook_secret`, which is a documented default), while setting `repository.full_name` to point at a completely unrelated stack's repository. This lets the attacker drive `stack.sync_github(expected_head_sha: ...)` (push), create/delete `Membership`/`Team`/`User` records (membership event), post arbitrary commit `Status` records that influence deployability checks (status event), or manipulate `PullRequest`/`ReviewStack` lifecycle (pull_request events) for a stack the attacker's "authenticated" organization has no relationship to. Because commit statuses and sync state directly gate whether a stack is deployable, this is a cross-repository write that can influence an unauthorized deploy decision on a target repository the attacker does not control.

### Likelihood Explanation
The likelihood is high in any multi-organization Shipit deployment where at least one configured GitHub organization has no `webhook_secret` (an explicitly supported, documented configuration per `config/secrets.development.shopify.yml`), since verification for that organization is unconditionally bypassed. Even where all organizations have secrets configured, the architecture still permits any org's correctly-signed webhook to carry an arbitrary `repository.full_name` unrelated to that org, meaning a compromised or malicious member of Org A's webhook flow (or a GitHub-side full_name/owner mismatch) can affect Org B's stacks without additional privilege.

### Recommendation
Bind the field used for signature-organization selection to the field used for handler dispatch: after selecting `repository_owner` and verifying the signature, re-derive the repository/stack strictly from a repository whose `owner.login` matches the same organization used for verification, rejecting (422) any payload where `repository.full_name`'s owner segment does not equal the verified `repository_owner`. Additionally, treat a missing `webhook_secret` as a configuration error rather than an automatic pass in `Shipit::GithubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure (or observe) Shipit with two GitHub orgs: `secretless-org` (no `webhook_secret`) and `victim-org` (any secret).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "secretless-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "attacker-chosen-sha"
}
```
3. `verify_signature` calls `Shipit.github(organization: "secretless-org")`, whose `verify_webhook_signature` returns `true` unconditionally per [8](#0-7) .
4. `PushHandler.call(params)` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` per [4](#0-3)  and invokes `stack.sync_github(expected_head_sha: "attacker-chosen-sha")`, mutating a stack that has no relation to `secretless-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
