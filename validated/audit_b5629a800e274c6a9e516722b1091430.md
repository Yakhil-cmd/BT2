### Title
Cross-organization webhook forgery via secret-selection field mismatch in `WebhooksController#verify_signature` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
On a multi-tenant Shipit instance configured with per-organization GitHub Apps (each with its own `webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml`), the webhook signature is verified against a secret chosen from the payload field `repository.owner.login` (or `organization.login`), while every event handler resolves the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`. Nothing binds these two fields together, so an attacker who legitimately controls one organization's webhook secret can forge a signature that is "valid" while pointing all actionable payload data at a completely different, unrelated organization/repository hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` selects the GithHub App/secret used for HMAC verification like this: [1](#0-0) 

using: [2](#0-1) 

which reads `params.dig('repository', 'owner', 'login')` (or falls back to `params.dig('organization', 'login')`) — both are attacker-controlled fields in the raw JSON body of the request, read *before* the signature has been checked.

Meanwhile, every webhook `Handler` resolves which `Stack`/`Repository` to act on using a *different* field: [3](#0-2) 

`repository_name` comes from `payload.dig('repository', 'full_name')`, not `repository.owner.login`.

`Shipit.github(organization:)` supports genuinely independent secrets per organization: [4](#0-3) 

In a real GitHub-originated webhook, `repository.owner.login` and the owner portion of `repository.full_name` are always consistent. But nothing in the engine enforces that equality — the code only checks:

`HMAC(secret_for(repository.owner.login), raw_body) == X-Hub-Signature`

while handlers act on `repository.full_name`. Because the entire body (including `full_name`) is attacker-authored before signing, an attacker who is a legitimate administrator of *their own* GitHub App/org on the shared Shipit instance (and therefore knows their own org's `webhook_secret`) can send a payload where:
- `repository.owner.login` = "attacker-org" (used to pick the verification secret, which the attacker legitimately possesses)
- `repository.full_name` = "victim-org/victim-repo" (used by the handler to locate and act on the target stack)

The signature will verify successfully (it is a valid HMAC for attacker-org's secret over this exact body), yet the event will be processed as if it originated from `victim-org/victim-repo`.

This is a direct analog of the reported bug class: the binding that should hold — *"the organization whose secret authenticated the request" == "the repository being written to"* — is broken, exactly the way the audited contract broke *"contract whose storage backs execution" == "contract whose constructor set the state"*.

### Impact Explanation
Concretely reachable handlers include:
- `StatusHandler#process` — creates a `Status` on any `Commit` matching an attacker-chosen `sha` in the victim's stacks via `commit.create_status_from_github!(params)`: [5](#0-4)  Forged "success" CI statuses can satisfy `required_statuses`/`deployable?` gating used by continuous delivery, potentially causing Shipit to auto-trigger a deploy of a commit that never actually passed the victim's real CI — an unauthorized deploy.
- `PushHandler#process` — enqueues `stack.sync_github(expected_head_sha:)` for the victim's stacks matching the forged branch: [6](#0-5) 
- Pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, etc.) similarly resolve stacks via `Repository.from_github_repo_name(repository_name)` and can create/archive Review Stacks or process merge/label logic for a repository the attacker does not own.

This crosses an organizational/repository trust boundary using only a credential the attacker legitimately holds for an unrelated org on the same installation, matching the Critical impact bucket ("cross-repository writes" / "an unauthorized deploy").

### Likelihood Explanation
This is only exploitable on **multi-organization** Shipit deployments, i.e., where `secrets.github` is configured as a map of multiple organizations each with distinct `webhook_secret`s (a supported, documented configuration — see `test/dummy/config/secrets_double_github_app.yml`). In this configuration, the attacker needs no privileged access to Shipit itself, no `ApiClient` token, and no access to the victim organization — only legitimate ownership/administration of a *different* GitHub App/org that is also configured on the same shared Shipit instance. This is a realistic scenario for any shared/multi-tenant Shipit deployment serving several customer organizations. On single-organization deployments (the common case, where `github_default_organization` is `nil`), `Shipit.github(organization:)` ignores the argument and always uses the single configured secret, so this specific cross-org confusion does not apply there — but push/status/pull_request handlers still always resolve via `repository.full_name` regardless, so the underlying field-mismatch defect exists in the code independent of deployment topology.

### Recommendation
- Verify the webhook signature first without depending on any payload-derived organization selection when only a single secret is configured, and for multi-org configurations, cryptographically bind the field used to select the secret to the field used to identify the target repository: after verifying with the secret picked from `repository.owner.login`, assert `payload.dig('repository', 'full_name')` actually belongs to that same owner (e.g., `full_name.split('/').first.casecmp?(repository_owner)`) before dispatching to any handler, rejecting the request otherwise.
- Alternatively, since GitHub webhooks also convey the installation/App identity in headers (`X-GitHub-Hook-Installation-Target-ID`), prefer verifying against the specific installation the webhook claims to be from and cross-check that resolved organization against the repository actually referenced in `params`.
- Add a regression test asserting that a payload with mismatched `repository.owner.login` and `repository.full_name` owner is rejected even if signed with a valid secret for the `owner.login` value.

### Proof of Concept
Assume a Shipit instance configured per `secrets_double_github_app.yml` with two orgs, `OrgOne` (attacker-administered) and `OrgTwo` (victim), each having their own `webhook_secret`. Attacker knows `OrgOne`'s `webhook_secret` because they configured that GitHub App themselves.

1. Attacker crafts a `status` webhook body:
```json
{
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged"
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, body)`.
3. POST to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the HMAC matches → verification succeeds (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which resolves the target commit purely by `sha` (global across all stacks) and creates a forged `success` status on it (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), independent of which org's secret was used to authenticate.

Note: full confirmation that `Commit.where(sha:)` and continuous-delivery gating would immediately trigger an actual deploy would require exercising `Stack#trigger_continuous_delivery`/`deployable?` end-to-end, which was not fully traced in this pass; this is flagged as an area for the engineer to verify experimentally when validating remediation.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
