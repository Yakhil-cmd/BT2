### Title
Unbounded scan of an AA's unspent outputs when composing payments allows cheap griefing that can freeze AA responses - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `completePaymentPayload()` builds the `inputs` array for an AA-issued payment by loading **all** unspent outputs owned by the AA for the requested asset with no `LIMIT` clause, then iterating them one-by-one in JavaScript until the target amount is reached. Unlike the divisible-asset coin-selection used for normal wallets (`inputs.js`), which explicitly caps the query with `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2`, the AA output-selection queries have no such cap for custom (non-base) assets. Anyone can cheaply send the AA many tiny-value outputs of a custom asset (there is no dust-floor filter for assets, only for the base asset), inflating the number of rows the AA must read and iterate every time it later needs to pay out that asset — exactly the "cheap for attacker, expensive for victim on next operation" pattern described in the TRST-M-3 report (subaccount array grown cheaply, then copied from storage to memory in full on `requestSubAccount`).

### Finding Description
`completePaymentPayload()` defines `readStableOutputs()` and `readUnstableOutputsSentByAAs()`: [1](#0-0) [2](#0-1) 

Both queries select **every** unspent output of the AA's address for the given asset (`WHERE address=? AND asset=... AND is_spent=0 ...`), with **no `LIMIT`**. The only anti-dust protection is the base-asset floor `amount>=FULL_TRANSFER_INPUT_SIZE`, which is applied only `"IS NULL AND amount>=..."` i.e. only for the base byte asset, not for custom assets: [3](#0-2) 

The results are then consumed unbounded by `iterateUnspentOutputs()`, which pushes every row into `payload.inputs` until `total_amount` reaches `target_amount`: [4](#0-3) 

Contrast this with the equivalent, properly-bounded logic used for ordinary wallets in `inputs.js`, which explicitly limits the number of candidate rows fetched per query to avoid runaway iteration: [5](#0-4) 

Because a custom asset can have essentially negligible byte cost per output, an attacker can pay a normal (small) unit fee to send the AA hundreds or thousands of 1-unit outputs of a custom asset it holds/uses. Nothing in `readStableOutputs`/`readUnstableOutputsSentByAAs` filters these out, and nothing caps how many are pulled into memory and iterated on every subsequent AA response that needs to send that asset — the entire query result set is read from storage into memory and looped over each time, mirroring the reported bug class ("the entire… array will be copied from storage to memory").

### Impact Explanation
Every AA that pays out a custom asset (e.g., token AAs, DEX/vault-style AAs) is reachable by any unprivileged unit poster. By pre-seeding the AA's output set with a large number of tiny outputs of the relevant asset, an attacker forces:
- A full, unbounded per-trigger DB scan and in-memory iteration over all such outputs each time the AA composes a payment in that asset.
- The generated `payload.inputs` array to potentially exceed `MAX_MESSAGES_PER_UNIT`/`MAX_INPUTS_PER_PAYMENT_MESSAGE`, making the resulting unit invalid and causing the AA to bounce the trigger (fees paid, response not delivered) — i.e., the AA becomes unable to reliably pay out that asset, a concrete AA fund freeze/loss of service for all its users, not just the attacker.

This satisfies the "AA fund loss or freezing" acceptance criterion, and is reachable purely by posting ordinary payment units to the AA's address — no privileged role required.

### Likelihood Explanation
Medium-High: sending many tiny custom-asset outputs to a known AA address is trivial and cheap (bounded only by ordinary unit fees), and any AA that issues/holds a divisible custom asset and later pays it out (a very common AA pattern, e.g., token vending/redemption AAs) is affected. No special timing or privileged access is needed — this is directly reachable by any address able to post a payment unit.

### Recommendation
- Add a `LIMIT` to `readStableOutputs()` and `readUnstableOutputsSentByAAs()` in `aa_composer.js` analogous to `inputs.js`'s `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2`, and stop iterating/issue as soon as the input cap is hit (falling back to issuing new coins or bouncing gracefully instead of scanning unbounded rows).
- Apply an analogous minimum-value ("dust") floor for outputs denominated in custom assets, not only the base asset, so cheap dust outputs cannot be used to bloat the count of usable inputs.
- Order rows so that the largest-denomination/most-valuable outputs are consumed first (as `inputs.js` does via `ORDER BY amount DESC`), reducing the number of inputs needed to satisfy a target amount even when dust exists.

### Proof of Concept
1. Deploy or use an existing AA that holds/pays out a divisible custom asset `X` (e.g., a token AA that redeems `X` for bytes on request).
2. From an unprivileged address, repeatedly send payment units to the AA's address consisting of many outputs of asset `X`, each of amount `1` (minimum representable unit), up to hundreds/thousands of outputs, paying only the standard byte fee for the unit size (no per-output "dust" floor blocks this since the floor in `readStableOutputs`/`readUnstableOutputsSentByAAs` only applies when `asset` is null/base).
3. Trigger the AA to send out asset `X` to a legitimate address in an amount requiring assembly from its unspent outputs.
4. Observe that `completePaymentPayload()`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` fetch **all** unspent `X` outputs owned by the AA (no `LIMIT`), and `iterateUnspentOutputs()` keeps appending inputs until the target amount is met — potentially exceeding `MAX_MESSAGES_PER_UNIT`, causing `sendUnit`/`completePaymentPayload` to fail and the trigger to bounce, denying legitimate withdrawal/payment requests in that asset going forward.
