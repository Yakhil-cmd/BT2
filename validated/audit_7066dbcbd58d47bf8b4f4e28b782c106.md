## Analog Found

### Title
Missing `return` after exception handling causes duplicate/concurrent processing of a private payment chain, breaking the `saved_private` mutex serialization guarantee - (File: `network.js`)

### Summary
The BlueZ CVE-2020-27153 root cause is a "redundant" event (a disconnect MGMT event) reaching a cleanup routine (`disconnect_cb`) a second time because the code path lacked a guard against re-entry, causing the same resource to be freed twice. `network.js`'s `handleSavedPrivatePayments()` has the structurally identical flaw: an exception-handling branch performs its own cleanup/completion action but fails to `return`, so the same iteration item falls through into a second, independent completion path that performs the *same* completion callback again. This double-invocation defeats the mutex-based serialization that the rest of the private-payment pipeline depends on for safety.

### Finding Description
In `validateAndSave()` inside `handleSavedPrivatePayments`: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

When `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (an attacker-controlled private payload can be crafted to make hashing throw), the `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which asynchronously deletes the row and, once the DELETE completes, calls the `async.each` iteratee callback `cb()`. Critically, there is **no `return`** after this call, so execution falls through and immediately invokes `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same `arrPrivateElements`. That function opens its own DB transaction, validates the chain, and on `ifOk`/`ifError` calls `deleteHandledPrivateChain(...)` **again** with the same `cb`: [2](#0-1) 

So `cb` — the `async.each` per-item completion callback — is invoked twice for one item, and `deleteHandledPrivateChain` (with its own DB round trip) is invoked twice concurrently.

`handleSavedPrivatePayments` is wrapped by `mutex.lock(["saved_private"], ...)`, and the batch's final `async.each` completion callback calls `unlock()`: [3](#0-2) [4](#0-3) 

Because `cb` fires prematurely (from the catch-block path) while the fall-through call to `validateAndSavePrivatePaymentChain` is still running its own async validation/DB transaction, `async.each`'s final callback — and therefore `unlock()` — can fire before that second, still in-flight validation completes. This releases the `saved_private` lock early, permitting a **new, concurrent** invocation of `handleSavedPrivatePayments` (triggered by another queued private payment, another peer message, etc.) to run its own transaction in parallel with the still-executing "leftover" `validateAndSavePrivatePaymentChain` call.

This matters because `private_payment.js`'s duplicate-acceptance defense is a plain SELECT-then-INSERT check with no additional row locking, relying entirely on serialized execution to be race-free: [5](#0-4) 

If two `validateAndSavePrivatePaymentChain` calls for the same or related private output execute concurrently (made possible by the premature unlock), both can pass the "is this a duplicate" SELECT check before either commits its INSERT, so both proceed to insert `outputs`/`inputs` rows for what should be a single private payment.

### Impact Explanation
Breaking the `saved_private` mutex serialization directly undermines the duplicate/double-accept protection for private payment chains that the codebase relies on being single-threaded. A malicious private-payment counterparty who sends a crafted private payload that throws during `objectHash.getBase64Hash` (reachable via `handleOnlinePrivatePayment` → `unhandled_private_payments` → `handleSavedPrivatePayments`) can reliably trigger this fall-through, opening a race window in which the wallet's local ledger can register the same private output as validated/saved through two concurrent transactions — corrupting local private-asset accounting (duplicate crediting) or creating disagreement between the node's recorded private-payment state and the true one, undermining confidence in "double-spend of a stable output" protections for private assets.

### Likelihood Explanation
The trigger condition (an object that causes `objectHash.getBase64Hash` to throw) is attacker-controlled content inside a private payment message sent by any correspondent/counterparty — no privileged position is required, matching the rule scope ("private-payment counterparty ... can reach"). The race window depends on timing between two async DB operations, which is plausible in a busy node processing multiple private payments, though it is a race and not deterministic on every attempt.

### Recommendation
Add a `return;` after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave()` (network.js, around line 2476) so execution does not fall through to invoke `privatePayment.validateAndSavePrivatePaymentChain` a second time for the same item, and audit other `try/catch` + fall-through patterns nearby for the same missing-`return` class of bug.

### Proof of Concept
1. As a paired correspondent, send a `private_payment` justsaying whose head element's `payload` cannot be hashed by `objectHash.getBase64Hash` (e.g., embed a value type unsupported by the hashing routine, such as a function or a payload with `NaN`/circular references reachable through the payload JSON structure) so that the hashing call inside `validateAndSave()` throws.
2. This causes `deleteHandledPrivateChain(...)` to run, and, due to the missing `return`, `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` is also invoked on the same data.
3. Simultaneously (or shortly after), have the counterparty send another private payment referencing the same or an overlapping private output/asset so a second `handleSavedPrivatePayments` cycle runs.
4. Because `cb` fired early from the catch-block branch, `unlock()` on `saved_private` can fire while the fall-through `validateAndSavePrivatePaymentChain` transaction is still open, letting the second cycle's transaction interleave and pass the duplicate-check SELECT in `private_payment.js` before the first transaction commits, resulting in duplicate `outputs`/`inputs` rows for the same private payment.
