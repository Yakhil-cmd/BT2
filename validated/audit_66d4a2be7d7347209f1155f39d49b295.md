### Title
Merkle proof forgery via zero-sibling proofs and missing leaf/node domain separation - (File: merkle.js, definition.js, formula/evaluation.js)

### Summary
`merkle.js` hashes leaves and internal nodes with the exact same function and no domain-separation prefix, and `verifyMerkleProof` accepts a proof whose `siblings` array has length 0 without ever requiring it to match the real tree depth. [1](#0-0) [2](#0-1)  Both production consumers of this verification (the `'in merkle'` authentifier in address definitions and the `is_valid_merkle_proof` formula op used by AAs) call `verifyMerkleProof` on attacker/user-supplied proof data without checking that `siblings.length` corresponds to the tree's real depth or is non-zero when the committed root came from a multi-leaf tree. [3](#0-2) [4](#0-3) 

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree by repeatedly computing `hash(arrHashes[i] + arrHashes[hash2_index])` for internal nodes and `hash(element)` for leaves — using the identical `sha256` function with no leaf/node prefix. [5](#0-4)  Consequently, for a committed root `R` of any multi-leaf tree, `R` itself equals `hash(hashA + hashB)` where `hashA`/`hashB` are the hashes of the root's two immediate children.

`verifyMerkleProof(element, proof)` iterates `proof.siblings` (length may legitimately be 0) and simply checks `hash(element) === proof.root` when siblings is empty. [6](#0-5)  Nothing enforces that the supplied `siblings.length` matches the actual depth of the tree that produced `proof.root`. An attacker who knows (or can derive/leak, e.g. from any other legitimate proof, or simply from the public list of committed elements) the two hash values immediately below the root can set:
- `element := hashA + hashB` (the concatenated base64 strings of the root's children)
- `proof := { root: R, siblings: [], index: anything }`

`hash(element)` then equals `hash(hashA+hashB) = R`, so `verifyMerkleProof` returns `true` even though `element` was never a genuine leaf of the tree — a classic second-preimage/node-as-leaf forgery, explicitly flagged but left unmitigated in the code's own comment `// Node-as-Leaf issue might matter in some cases`. [7](#0-6) 

This is reachable from two attacker-controlled entry points:
1. **Address authentifier `'in merkle'`**: a unit author supplies `assocAuthentifiers[path]` (`serialized_proof`) as part of an authentication path; it is deserialized and passed straight to `verifyMerkleProof` with no length/format checks, then the resulting `proof.root` is checked against a data feed value. [3](#0-2)  If an address definition uses `'in merkle'` against a data feed whose committed root is derived from a multi-element set (e.g., a whitelist, an allocation table, etc.), a forged zero-sibling proof lets an unauthorized party satisfy this authentifier.
2. **`is_valid_merkle_proof` formula op in AAs**: trigger data supplies both `element` and `proof`; post-fix code only bounds `siblings.length <= 50` and requires non-empty strings, but does not reject `siblings.length === 0` nor validate it against the real tree depth. [8](#0-7)  An AA that trusts `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` against a previously stored/known root to authorize a payout, unlock funds, or grant a privileged action can be tricked by any trigger sender into treating a forged internal-node concatenation as a valid leaf.

### Impact Explanation
Where `'in merkle'` gates spending authority in an address definition, or where an AA formula gates a fund transfer/state change on `is_valid_merkle_proof`, this forgery allows an attacker to satisfy the check without ever being a legitimate member of the committed set — leading to unauthorized spending from the address or AA fund loss, both explicitly in the accepted-impact list.

### Likelihood Explanation
Exploitability depends on an author/AA designer actually using `'in merkle'` or `is_valid_merkle_proof` with a multi-leaf, security-critical root (e.g., whitelist/allowlist/allocation membership) rather than a single-leaf root. Given these primitives exist specifically to support such use cases (data feed-published merkle roots, AA-driven allowlists), and the attacker only needs to know two internal hash values (often derivable from the public element set or from any other valid proof for that tree), the likelihood of a practical exploit for any deployed contract relying on this pattern is credible.

### Recommendation
- Add domain separation to `merkle.js`: hash leaves with a distinct prefix (e.g., `hash("0"+element)`) and internal nodes with a different one (e.g., `hash("1"+left+right)`), so a leaf hash can never collide with an internal node hash.
- In `verifyMerkleProof`, and in both consumers (`definition.js` `'in merkle'` and `formula/evaluation.js` `is_valid_merkle_proof`), reject proofs whose `siblings.length` is 0 (or otherwise inconsistent) whenever the expected tree has more than one leaf, and/or require an explicit expected proof length parameter to be checked, mirroring the recommended fix in the referenced report (`require(proof.siblings.length > 0/expected, ...)`).

### Proof of Concept
1. Build a set of elements `E = [e0, e1, e2, e3]` and compute `root = merkle.getMerkleRoot(E)` — this is what gets published to a data feed or stored as an AA state var.
2. Independently compute the tree: `h0=hash(e0), h1=hash(e1), h2=hash(e2), h3=hash(e3)`, `left=hash(h0+h1)`, `right=hash(h2+h3)`, so `root === hash(left+right)`.
3. Construct forged input: `element_forged = left + right`, `proof = { root: root, siblings: [], index: 0 }`.
4. Call `merkle.verifyMerkleProof(element_forged, proof)` — it returns `true`, even though `element_forged` is not a genuine element of `E`.
5. Feed this forged `(element_forged, serialized_proof)` pair into either the `'in merkle'` authentifier path (`definition.js:1004-1020`) or the `is_valid_merkle_proof` formula call (`formula/evaluation.js:1768-1807`) to bypass membership checks tied to `root`.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
