### Title
CCMenuController#stack bypasses `stacks` scope, allowing an ApiClient scoped to one stack to read any other stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController#stacks` restricts stack visibility to `Stack.where(id: current_api_client.stack_id)` whenever an `ApiClient` is scoped to a specific stack, and every other stack-facing controller (e.g. `Api::StacksController`) resolves its target record via `stacks.from_param!(...)`. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, so a client explicitly scoped to stack A can still fetch build status data for stack B.

### Finding Description
The intended binding is: for a given `current_api_client`, the set of stacks any `Api::*Controller` action can read or act on must equal `stacks(current_api_client)`, i.e. `Stack.where(id: current_api_client.stack_id)` when `stack_id` is set.

`Api::BaseController` defines: [1](#0-0) 

`Api::StacksController` honors this by calling `stacks.from_param!(params[:id])`: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to resolve directly against the unscoped `Stack` model, entirely skipping the `stacks` helper: [3](#0-2) 

`require_permission :read, :stack` only checks that the client's `permissions` array contains the string `"read:stack"` — it performs no per-stack scoping: [4](#0-3) 

Attacker flow: attacker (or any party holding a legitimately-issued token for an `ApiClient` scoped to stack A, e.g. an app given CI-badge access to one stack) sends `GET /stacks/B/ccmenu.xml?token=<their token>` (or via Basic Auth). `CCMenuController#authenticate_api_client` accepts the token exactly as `BaseController` would, but `#stack` looks up stack B unconditionally with `Stack.from_param!`, returning HTTP 200 with stack B's `deploys_and_rollbacks.last`, lock status, branch, and last build label/status — data belonging to a stack the client was never granted access to. The same token against `Api::StacksController#index` would correctly exclude stack B via `stacks.where(id: current_api_client.stack_id)`.

No other guard intervenes: `verify_signature`/webhook checks are irrelevant here (this is a normal authenticated API GET), `ExplicitParameters` schemas don't validate stack ownership, and `check_permissions!` is scope-string-based only, not per-record.

### Impact Explanation
An `ApiClient` explicitly scoped to one stack can read CI/build state (build name, last build status/label/time, lock status) of any other stack in the installation via `CCMenuController#show`, regardless of the `stack_id` restriction placed on its token. This is a cross-tenant/cross-stack unauthorized read of stack state, matching the High-severity category ("escalation ... unauthenticated read of stack state"). It is fully repeatable against any stack ID in the system by iterating `params[:stack_id]`; there is no write or credential exposure, so it does not rise to Critical.

### Likelihood Explanation
Preconditions: attacker only needs any valid `ApiClient` token that has `read:stack` permission and a non-nil `stack_id` (i.e., a token intentionally scoped to a single stack — a common configuration for giving external CI badges/dashboards limited access). No GitHub secrets, session, or elevated role is required. The attack is a single unauthenticated-in-effect HTTP GET with a different `stack_id`/`id` path param; cost is negligible and fully repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` helper instead of the raw `Stack` model, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override entirely so it inherits `BaseController#stack`, ensuring parity with `StacksController` and closing the scope-bypass.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (illustrative)
test "ApiClient scoped to stack A cannot read stack B via ccmenu, matching StacksController#index scoping" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")
  client = ApiClient.create!(creator: shipit_users(:walrus), name: "scoped",
                              stack_id: stack_a.id, permissions: %w[read:stack])

  # Side 1: StacksController#index enforces stacks(current_api_client) == [stack_a]
  @request.env['HTTP_AUTHORIZATION'] =
    ActionController::HttpAuthentication::Basic.encode_credentials(client.authentication_token, '')
  get :index, controller: 'shipit/api/stacks' # via StacksController
  ids = JSON.parse(response.body).map { |s| s['id'] }
  refute_includes ids, stack_b.id
  assert_includes ids, stack_a.id

  # Side 2: CCMenuController#show bypasses the same scoping for stack_b
  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }
  assert_response :ok   # VULNERABLE: should be 404/403, matching stacks(current_api_client) exclusion
end
```
This demonstrates the two sides of the equality diverge: `StacksController#index` correctly excludes stack B for the stack-A-scoped client, while `CCMenuController#show` returns 200 for the same client against stack B.
