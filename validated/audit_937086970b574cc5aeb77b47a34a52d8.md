## Analog Found

### Title
Unbounded iteration over `storage.assocUnstableMessages` in `dataFeedExists()`/`readDataFeedValue()` enables AA-trigger processing DoS - (File: `data_feeds.js`)

### Summary
The external report flags `Pool.totalAssets()`/`Pool.onGoingLoans()` for looping over an attacker-growable array on every call, risking a gas-based DoS. The equivalent pattern in ocore is the full, unfiltered iteration over the global in-memory map `storage.assocUnstableMessages` performed inside `dataFeeds.dataFeedExists()` and `dataFeeds.readDataFeedValue()` every time an AA evaluates a `data_feed`/`in_data_feed` oscript expression against unstable data. This map grows with every unstable unit on the DAG that carries a `data_feed`, `definition`, `system_vote`, or `system_vote_count` message, and any unprivileged unit poster can add entries to it.

### Finding Description
`storage.assocUnstableMessages` is populated for **every** unit (no AA/authorization requirement) whose messages include `data_feed`, `definition`, `system_vote`, or `system_vote_count`, as soon as the unit is written: [1](#0-0) 

Entries are removed only when the unit's MCI becomes stable, in `main_chain.js`'s `saveUnstablePayloads()`: [2](#0-1) 

Until that stabilization happens, `dataFeeds.dataFeedExists()` (used to evaluate `in_data_feed` in AA formulas) does a `for (var unit in storage.assocUnstableMessages)` over the **entire map**, regardless of how many of the entries are actually relevant to the requested oracle addresses — the address/oracle filter (`_.intersection`) is applied only after entering the loop body: [3](#0-2) 

The same unbounded, full-map scan pattern exists in `readDataFeedValue()` (used for `data_feed[[...]]`) when unstable data is requested: [4](#0-3) 

This is structurally identical to the reported `Pool.totalAssets()` issue: a function reachable by ordinary, unprivileged actions (any address can post a `data_feed` message, and any AA trigger sender can cause an AA to evaluate `data_feed`/`in_data_feed`) iterates a collection whose size is controlled by cumulative, attacker-influenceable activity (number of currently-unstable units carrying these message types) rather than being bounded by a fixed constant.

### Impact Explanation
AA trigger execution (`handleTrigger` in `aa_composer.js`, invoked deterministically by every full node during stabilization/validation) is consensus-critical, synchronous code. If an attacker floods the DAG with many low-value units containing `data_feed` messages (a completely permissionless action) faster than they stabilize (stabilization requires witness-level advancement across ~12 witnesses), `storage.assocUnstableMessages` can grow substantially before those units are pruned from the map. Every subsequent `data_feed`/`in_data_feed` evaluation by any AA (triggered by any address sending a payment/data to that AA) then pays the full O(n) cost of scanning the bloated map, on every node in the network. Because this happens inside the deterministic unit-processing/stabilization pipeline, sustained flooding degrades throughput of AA-trigger processing network-wide, which can slow or stall the network's ability to timely confirm new units under load — matching the "network unable to confirm new units" impact bucket.

### Likelihood Explanation
Likelihood is Medium: posting `data_feed` messages requires no special privilege or asset ownership and is a normal, cheap operation (subject only to standard byte-fee costs), and many AAs commonly use `data_feed`/`in_data_feed` with `unstable_opts`/`bAA` context for fast oracle reads. Sustained flooding to keep many units simultaneously unstable requires ongoing spam but no capital lock-up or special access, similar to the "unlikely but possible" framing acknowledged for the original report (Nemeos' reply calling their case "extremely unlikely").

### Recommendation
- Maintain per-oracle-address indices into `assocUnstableMessages` (e.g., keyed by author address) instead of iterating the whole map for every lookup, so the cost scales with the number of unstable messages from the *relevant* oracle(s) rather than the whole network's unstable set.
- Apply the address/`arrAddresses` filter (`_.intersection`) as an early key lookup rather than inside the per-entry loop body.
- Consider capping how many unstable data-feed-carrying units can be outstanding simultaneously, or accelerating pruning of stale/superseded entries for the same oracle+feed_name pair.

### Proof of Concept
1. Attacker (or several colluding addresses) posts a large number of low-cost units, each containing a `data_feed` message (e.g., `{app: 'data_feed', payload: {foo: 1}}`), from many distinct oracle-looking addresses, faster than the DAG's witness levels advance enough to stabilize them.
2. Each such unit adds an entry to `storage.assocUnstableMessages` per [1](#0-0) , and these accumulate because stabilization removal only happens once MC advances past their MCI, per [5](#0-4) .
3. Concurrently, any AA whose oscript references `data_feed[[oracles=..., ...]]` with `unstable_opts` set, or `in_data_feed` with `bAA` true, triggers `readDataFeedValue`/`dataFeedExists`, both of which fully iterate `storage.assocUnstableMessages` per [6](#0-5)  and [7](#0-6) , regardless of whether the queried oracle addresses are actually present.
4. As the attacker keeps the unstable set large, every AA trigger evaluation across the network incurs growing linear cost, degrading throughput of unit validation/AA processing for all nodes.
