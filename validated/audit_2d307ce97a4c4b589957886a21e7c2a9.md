### Title
Stack-Scoped API Token Bypasses Stack Authorization in `CCMenuController#stack` (Cross-Stack IDOR) - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack via `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` helper used everywhere else in the API. Because `ApiClient#check_permissions!` only checks the permission name (`read:stack`) and never checks which stack the token is bound to, a token minted for one stack can be replayed against any other stack in the Shipit instance to read its build/deploy status.

### Finding Description
The equality that Shipit's API is supposed to enforce is: **the stack a token authorizes == the stack the request touches**. This is implemented via `Shipit::Api::BaseController#stacks`: [1](#0-0) 

`stacks` restricts the resolvable set of records to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and every other controller (e.g. `StacksController#stack`) resolves the requested record through this scoped relation: [2](#0-1) 

`CCMenuController`, however, overrides `stack` and looks the record up directly against the unscoped `Stack` model: [3](#0-2) 

Authorization for the action is enforced only by `require_permission :read, :stack`, which in turn calls `current_api_client.check_permissions!(:read, :stack)`. This method has no notion of *which* stack is being requested — it only checks that the string `"read:stack"` is present in the client's `permissions` array: [4](#0-3) 

So the binding "token authorizes stack X" is asserted only by the generic permission string, while the actual record fetched ("stack the request touches") is picked independently from `params[:stack_id]` with no scoping check — exactly the class of bug described in the external report, where a value that is trusted/accepted by one code path (a generic operation:scope check) is substituted for a different, unchecked value (an arbitrary stack id) at the point where data is actually used.

Stack-scoped tokens of this kind are specifically designed for this endpoint and to be embedded in plain URLs (query string), making them the most likely tokens to leak (browser history, CI logs, referrer headers, reverse proxies): [5](#0-4) 

### Impact Explanation
Any holder of a valid, stack-scoped `read:stack` API token (e.g. a CCTray/CI dashboard URL legitimately generated for stack A) can query `GET /api/stacks/:stack_id/ccmenu` for **any other stack B** in the same Shipit deployment and receive that stack's deploy state: last build status/label/time and web URL. This breaks tenant/stack isolation and constitutes an unauthorized read of stack deploy state across stacks the token was never authorized for — matching the "unauthenticated/unauthorized read of stack state ... deploy output" High-impact category, since the whole point of `ApiClient#stack_id` scoping (verified elsewhere, e.g. in `StacksController`) is defeated for this one controller.

### Likelihood Explanation
Exploitation requires only a single valid, stack-scoped API token, which is by design distributed as a bare URL query parameter (`?token=...`) intended for low-trust consumption by CI dashboard tools — precisely the credential type most likely to leak. No repository write access, GitHub App credentials, or session is required; only possession of one legitimately-issued, narrowly-scoped token is needed to pivot to reading arbitrary stacks.

### Recommendation
Change `CCMenuController#stack` to resolve the record through the scoped `stacks` relation (as `BaseController#stack` and `StacksController#stack` already do), i.e. `@stack ||= stacks.from_param!(params[:stack_id])`, so that clients scoped to `stack_id` cannot resolve stacks outside that scope.

### Proof of Concept
1. Legitimately obtain a CCMenu URL/token for `stack_id = "org/repoA/production"` via `CCMenuUrlController#fetch` (or any other means a stack-scoped `read:stack` token can leak).
2. Send `GET /api/stacks/org/repoB/production/ccmenu?token=<stolen-token>` for an unrelated stack `repoB` the token was never authorized for.
3. `authenticate_api_client` accepts the token (it's a valid `ApiClient`), `require_permission :read, :stack` passes because the client has `read:stack` in `permissions`, and `stack` resolves `repoB` directly via `Stack.from_param!`, bypassing the `stacks` scoping — the response returns `repoB`'s deploy status even though the token is bound to `repoA`.
