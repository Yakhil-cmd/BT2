### Title
Webhook signature verification keys off an attacker-controlled `organization` field that is decoupled from the `repository` the handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the inbound signature against using a value taken straight from the unauthenticated JSON body, while the event handlers that actually mutate state (create stacks' commits, users, teams, statuses, etc.) key off a *different* field of that same body. These two fields are never checked for consistency, so the "organization that authenticated" is not bound to the "repository that is written."

### Finding Description
`verify_signature` derives the signing organization like this: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')` — both fully attacker-controlled request-body fields, since the payload is only parsed after the raw body has been (attempted to be) verified against whatever organization the attacker chooses to name.

The actual work performed by handlers uses a *different* field, `repository.full_name`: [3](#0-2) 

Nothing forces `repository.full_name`'s owner to equal the `repository_owner`/`organization.login` used for signature selection. An attacker can pick any organization name they want for the "authenticating" side while pointing `repository.full_name` at a completely different, victim-owned repository.

Critically, signature verification is a no-op whenever the selected organization has no `webhook_secret` configured: [4](#0-3) 

Multi-organization installations are supported and each organization's config (including `webhook_secret`) is looked up independently by the string the attacker supplies: [5](#0-4) 

The setup docs explicitly describe `webhook_secret` as **optional**, so it is realistic for at least one configured organization to have none: [6](#0-5) 

Putting this together: an attacker crafts a POST to `/webhooks` with `X-Github-Event: push` (or `status`, `check_suite`, `membership`, `pull_request`, etc.), sets `organization.login` (or `repository.owner.login`) to any organization configured in Shipit that has no `webhook_secret` (verification trivially returns `true`), and sets `repository.full_name` to an arbitrary victim repository already tracked by Shipit. Because `Handler#stacks` resolves stacks purely from `repository.full_name`, the forged event is dispatched against the victim stack, even though the "authenticated" organization is unrelated to it.

### Impact Explanation
This breaks the equality "organization whose signature was verified == organization owning the repository the handler mutates." Concretely, an unauthenticated attacker (no Shipit session, `ApiClient` token, or GitHub write access to the victim repo) can:
- Trigger `GithubSyncJob` with a spoofed `expected_head_sha`/push event on a victim stack via `PushHandler`, forcing Shipit to fetch/append commits and refresh the deploy spec cache on a repository they don't control.
- Forge `status`/`check_suite` events to flip commit statuses/check-run state used to gate deploys.
- Forge `membership` events, which create/delete `Team`/`Membership`/`User` records outright based on payload content, as shown by `WebhooksControllerTest`'s membership tests.

This can influence deploy readiness signals and stack synchronization for a repository the attacker has no rights to, which lines up with the "unauthorized deploy/rollback" and "escalation into authorization" impact classes, contingent on at least one configured organization lacking a webhook secret (an explicitly documented, supported configuration).

### Likelihood Explanation
Likelihood depends on deployment configuration: it requires (a) a multi-organization `secrets.github` setup, and (b) at least one configured organization with `webhook_secret` unset — both of which are documented, supported, non-default-but-plausible configurations (the setup guide marks the secret "optional"). In a single-organization installation this specific bypass path doesn't apply the same way, since the config lookup falls back to the single top-level config regardless of the attacker-supplied organization string. This is therefore configuration-dependent rather than universally exploitable, which lowers likelihood relative to a Critical always-on bypass.

### Recommendation
Bind the field used for signature-key selection to the field used for repository resolution: derive the “authenticating organization” from the same `repository.full_name` (or equivalently, require `repository.owner.login == organization.login` when both are present and reject otherwise). Additionally, do not treat an absent `webhook_secret` as “verification not required” — either require every configured organization to set a `webhook_secret`, or fail closed on missing secrets in production, rather than returning `true` unconditionally in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `victim-org` (tracked stacks, has a `webhook_secret`) and `attacker-org` (no `webhook_secret` set).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": { "login": "attacker-org" },
  "repository": { "full_name": "victim-org/victim-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/main"
}
```
(omit `repository.owner.login` so `repository_owner` falls back to `organization.login`).
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even missing) `X-Hub-Signature` header.
4. `PushHandler`/`Handler#stacks` resolves the target via `payload.dig('repository','full_name')` = `victim-org/victim-repo`, dispatching a `GithubSyncJob` against the victim's real stack — despite the request never being authenticated for `victim-org`. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
