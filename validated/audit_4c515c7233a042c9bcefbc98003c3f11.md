### Title
Account-Creation Denial-of-Service via Pre-funding Dust Deposits - (File: programs/system/src/system_processor.rs)

### Summary
The System Program's `create_account` handler rejects a `CreateAccount` (and `CreateAccountWithSeed`) instruction outright if the destination account already holds *any* lamports, returning `SystemError::AccountAlreadyInUse`. Because any unprivileged party can transfer arbitrary dust amounts of lamports to any public key via a plain `Transfer` instruction, an attacker can pre-fund a victim's intended account address before the victim's `CreateAccount` transaction lands, permanently forcing that transaction to fail. This mirrors the LeXscrow issue where a minor, unsolicited deposit flips a balance-based guard and causes a legitimate operation to revert.

### Finding Description
`create_account` in `system_processor.rs` performs the following check before allocating/assigning and transferring lamports into the "to" account: [1](#0-0) 

```
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ...
            return Err(SystemError::AccountAlreadyInUse.into());
        }
```

Any account with `lamports() > 0` is treated as "already in use", regardless of whether it has data or an owner other than the default (uninitialized) system-owned empty account. Since lamports can be sent to *any* address by an unprivileged `Transfer` instruction (which has no target-account restrictions), an attacker who knows (or can derive, e.g., a PDA or a seed-derived/vanity address) the address a victim intends to `CreateAccount` on can simply transfer 1 lamport to that address ahead of time. When the victim's `CreateAccount` transaction executes, the guard trips and the instruction — and therefore the whole transaction — fails with `AccountAlreadyInUse`, even though the account was never legitimately initialized.

Notably, Agave already recognizes this exact class of problem and has an alternate path, `create_account_allow_prefund`, explicitly documented as "Create a new account without checking for 0 lamports... Intended for use where account has already had rent paid in whole or in part before creation": [2](#0-1) 

This confirms the general `CreateAccount` path (used pervasively across the ecosystem, including many programs' CPI-driven account initialization flows) still has the zero-lamports precondition and is not protected against griefing via dust pre-funding.

### Impact Explanation
This is a denial-of-service primitive reachable by any unprivileged transaction sender against any other user or protocol relying on `SystemInstruction::CreateAccount`/`CreateAccountWithSeed` for deterministic account initialization (e.g., PDAs, seed-derived accounts, vanity keypairs generated client-side before submission). An attacker who can predict or observe the target address (which is common — addresses are frequently derived via `create_with_seed`/PDA derivation, or observable in a still-pending transaction/mempool) can send a trivial lamport transfer to permanently block the victim's account creation at that address, forcing repeated failures until the victim adopts a workaround (e.g., changing seed/address). This does not cause fund loss or consensus divergence, but it is a persistent, cheap, unprivileged DoS against a very widely used builtin instruction.

### Likelihood Explanation
High feasibility: transferring lamports to an arbitrary address requires only a standard `Transfer` instruction with no special privilege, and the cost to the attacker is the dust amount plus a normal transaction fee. The main constraint is that the attacker must know the target address before the victim's `CreateAccount` transaction is confirmed, which is realistic for seed-derived/PDA addresses that are deterministic and often derivable off-chain, or observable while a transaction is in flight.

### Recommendation
Adopt the same non-griefable check used by `create_account_allow_prefund` for the general `create_account` path: instead of rejecting whenever `lamports() > 0`, only reject when the account is genuinely initialized (i.e., has non-empty data or is owned by a non-system, non-default program), and allow pre-existing lamports to be treated as partial/full rent pre-payment rather than a hard failure condition.

### Proof of Concept
1. Victim client derives a target address `T` via `Pubkey::create_with_seed(base, seed, owner)` (or a PDA) intending to submit `SystemInstruction::CreateAccount { lamports, space, owner }` targeting `T`.
2. Attacker observes/derives `T` (deterministic derivation, or sees the victim's pending transaction) and submits an ordinary `SystemInstruction::Transfer` sending 1 lamport to `T` before the victim's transaction is processed.
3. When the victim's `CreateAccount` instruction executes, `create_account` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, failing the victim's transaction: [3](#0-2) 
4. The victim cannot recover using the same address/seed; the account creation at `T` is permanently blocked as long as the dust lamports remain (and the attacker can immediately re-fund it if the victim tries to first drain and retry, indefinitely repeating the DoS at negligible cost).

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
