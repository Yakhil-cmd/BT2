### Title
Webhook signature is verified against an attacker-selectable organization while the event is applied to a repository named by a separate, unverified payload field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments (`config/secrets.yml` with multiple top-level GitHub App entries, e.g. `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using a payload field, while the handler that actually acts on the event resolves the target `Stack`/`Repository` using a *different*, independently-controlled payload field. These two fields are never checked for consistency.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the request body itself, not from any authenticated/trusted source: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — both fully attacker-controlled JSON fields in the raw POST body. `Shipit.github(organization: repository_owner)` then looks up the matching app config/`webhook_secret` for that org via `Shipit.github_app_config`: [3](#0-2) 

The signature check only proves the request was HMAC-signed with *some* configured organization's `webhook_secret` — namely the one named inside the payload. It does not prove that the org that owns the secret is the actual owner of the repository being mutated.

Every event handler, however, resolves the target repository/stack using a completely different field, `repository.full_name`, via `Handler#stacks`/`#repository_name`: [4](#0-3) 

For example `PushHandler` triggers a GitHub sync for any not-archived stack matching that `full_name`/branch: [5](#0-4) 

And `StatusHandler` writes a commit status sourced entirely from attacker-supplied `state`/`context`/`description` onto any `Commit` whose `sha` matches, regardless of which org's secret validated the request: [6](#0-5) 

**The broken binding**: `organization whose webhook_secret authenticated the request` ≠ `organization that owns the repository named in repository.full_name that the handler mutates`. An operator running Shipit with more than one configured GitHub App (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and `README.md`'s multi-org example) installs one App per org they administer. Anyone who controls one of those orgs (e.g. legitimately installed the App on their own `OrgAttacker`) can compute a valid `X-Hub-Signature` for `OrgAttacker`'s known `webhook_secret`, then set `repository.owner.login = "OrgAttacker"` (satisfying `verify_signature`) while setting `repository.full_name = "OrgVictim/some-tracked-repo"` (which is what handlers actually act on). Nothing ties these two fields together.

### Impact Explanation
This allows an attacker who administers any one of the multiple GitHub orgs configured in a shared Shipit instance to forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that are applied to repositories/stacks belonging to a *different* organization they do not control:
- Forged `status` events let the attacker set arbitrary commit statuses (state/context/description) on victim commits via `Commit#create_status_from_github!`, which can satisfy `ci.require` gating and trigger unauthorized continuous deployment/merges for stacks with `continuous_deployment` enabled.
- Forged `push` events can force `GithubSyncJob`/`stack.sync_github` to run against victim stacks.
- Forged `pull_request`/`check_suite` events can manipulate review-stack provisioning/archival and check-run refresh for repos the attacker does not own.

This is a cross-organization write / unauthorized-deploy-adjacent primitive (satisfies "cross-repository writes" / "unauthorized deploy" impact criteria), reachable by an unprivileged external attacker who need only control one org configured on the shared instance — no Shipit session, API token, or the victim org's secret is required.

### Likelihood Explanation
Requires the deployment to use the multi-organization `secrets.yml` schema (explicitly documented and supported: `docs/setup.md` lines 182-209, `README.md` multi-org config) and for the attacker to be an admin of at least one of the configured GitHub orgs/Apps sharing the instance — a realistic scenario for shared internal Shipit installations serving multiple teams/orgs. No other authentication is required; the attacker only needs to construct a raw HTTP POST with a correctly computed `X-Hub-Signature` using their own known `webhook_secret`.

### Recommendation
After selecting the app/secret via `repository_owner` and verifying the HMAC, enforce that the organization used for signature verification actually matches the owner of `repository.full_name` (or `organization.login`) used by the handlers to resolve the target stack/repository — reject the webhook if they diverge. Alternatively, resolve the target `Repository`/`Stack` first, derive its owning organization from Shipit's own records, and use that (not attacker-supplied `repository.owner.login`) to select the verification secret.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. as in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`), each with its own `webhook_secret`.
2. Attacker administers `OrgOne`'s GitHub App installation and therefore knows `OrgOne`'s `webhook_secret` (e.g. via their own repo's legitimate webhook deliveries).
3. Attacker crafts a `status` (or `push`) webhook payload:
   ```json
   {
     "sha": "<victim-commit-sha-tracked-by-Shipit>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgOne")`, verifies successfully against the attacker-known secret, and the request proceeds.
6. `StatusHandler#process` (unaware of which org authenticated the request) finds the `Commit` by `sha` and calls `create_status_from_github!`, writing a forged status onto `OrgTwo/victim-repo`'s commit — potentially satisfying `ci.require` and enabling an unauthorized continuous deploy for a stack the attacker does not administer.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
