### Title
Webhook signature verified against attacker-chosen org while stack/commit resolution uses unrelated `repository.full_name` field, allowing cross-org `RefreshCheckRunsJob` invocation with victim's GitHub credentials - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/check_suite_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification based on `params.dig('repository','owner','login')`, while `Handler#stacks` (used by `CheckSuiteHandler#process`) resolves the target repository/stack using the independently attacker-controlled `payload.dig('repository','full_name')`. Since both fields are read from the same unauthenticated JSON body with no cross-check that they refer to the same repository, an attacker can pass verification under an organization with no `webhook_secret` while pointing the check-suite payload at a victim organization's real repo/branch/commit, causing `RefreshCheckRunsJob` to run using the victim's GitHub App credentials.

### Finding Description
The broken binding, stated explicitly: the code implicitly assumes `params.dig('repository','owner','login') == owner_of(params.dig('repository','full_name'))`, i.e., that the org used to verify the signature is the same org that owns the stack/commit being mutated. This is never enforced.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and looks up `Shipit.github(organization: repository_owner)` to verify `X-Hub-Signature` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/unset: `return true unless webhook_secret` [3](#0-2) . Multi-org setups keep `webhook_secret: nil` per org in example/dummy configs, which is a supported, documented configuration [4](#0-3) [5](#0-4) .
- Once verification passes, `WebhooksController#create` dispatches to handlers with the raw parsed `params` [6](#0-5) .
- `Handler#stacks` resolves the repository using a completely different field, `payload.dig('repository', 'full_name')`, with no reference to `repository.owner.login`: `Repository.from_github_repo_name(repository_name)&.stacks` [7](#0-6) .
- `CheckSuiteHandler#process` uses `stacks.where(branch: params.check_suite.head_branch)` and then calls `schedule_refresh_check_runs!` on matching commits by `sha` [8](#0-7) , which enqueues `RefreshCheckRunsJob` with `commit_id` [9](#0-8) .
- The job later calls `commit.refresh_check_runs!`, which uses `stack.github_api` — the GitHub API client scoped to the stack's own owning repository/organization (Y), not the organization (X) used for signature verification.

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: check_suite` and body:
```json
{
  "repository": { "full_name": "Y/real-repo", "owner": { "login": "X" } },
  "check_suite": { "head_sha": "<Y's real commit sha>", "head_branch": "<Y's real branch>" }
}
```
where `X` is any organization configured in Shipit's multi-org `github:` secrets with a blank `webhook_secret` (a documented, supported configuration), and `Y` is the victim organization owning a real, tracked stack/commit. Because `verify_signature` only checks the payload against org `X`'s (non-existent) secret — which always "verifies" — and never checks that `X` matches the owner embedded in `repository.full_name`, the request passes authentication. `CheckSuiteHandler#process` then resolves stacks purely from `repository.full_name = "Y/real-repo"`, finds Y's real commit by SHA, and calls `schedule_refresh_check_runs!`, enqueuing `RefreshCheckRunsJob`, which will execute using Y's GitHub App/API credentials.

Existing guards do not prevent this: `drop_unhandled_event` only screens for known event types; the `ExplicitParameters` schema for `CheckSuiteHandler` only requires the shapes of `check_suite.head_sha`/`head_branch`, with no cross-field validation of `repository.owner.login` vs `repository.full_name`; `Repository` model validations only constrain `owner`/`name` character sets, not consistency between webhook fields; there is no code anywhere that compares `repository_owner` (used for verification) to the owner segment of `repository.full_name` (used for stack lookup).

### Impact Explanation
An attacker with no relationship to organization Y (no session, no API token, no webhook secret) can cause a job to run against Y's real stack that consumes Y's own GitHub API credentials (`stack.github_api`) to write/update `CheckRun` records for Y's commits, entirely triggered by a request that authenticated as a different, attacker-influenceable organization X. This is a payload for one organization/repository causing a job to execute against another organization's stack and commit data — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any tracked repository/stack/commit combination as long as any configured multi-org entry has a blank `webhook_secret` (or the attacker can otherwise pass verification for some org X), and the blast radius spans every organization configured under `Shipit.github(organization:)` in a multi-org deployment.

### Likelihood Explanation
Preconditions: Shipit must be configured for multiple GitHub organizations (the documented `github:` multi-org schema), and at least one configured organization must have `webhook_secret` unset/blank — a state the shipped example configs (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`) explicitly show as valid/default. No secrets, tokens, or privileged roles are required from the attacker; only knowledge of a target org/repo name, an existing branch name, and a commit SHA (all public GitHub metadata) is needed. The attack is a single unauthenticated HTTP POST and is trivially repeatable.

### Recommendation
In `Handler#stacks` (and every handler resolving `Repository.from_github_repo_name`), verify that the repository owner segment of `payload.dig('repository','full_name')` matches the organization that was used to authenticate the webhook (`repository_owner` in `WebhooksController`). Concretely, pass the verified `repository_owner` into the handler and assert `Repository.from_github_repo_name(repository_name)&.owner == repository_owner` before returning any stacks; otherwise treat the webhook as unauthorized for that repository. Alternatively, derive the repository lookup solely from the verified organization rather than trusting `repository.full_name` independently.

### Proof of Concept
Minitest plan (controller test, no live GitHub calls, following existing patterns in `test/controllers/webhooks_controller_test.rb`):
```ruby
test ":check_suite verified under org X should not schedule RefreshCheckRunsJob for org Y's stack" do
  # Arrange: stack belongs to org "Y" (existing fixture, e.g. shipit_stacks(:shipit))
  victim_stack = shipit_stacks(:shipit) # owned by repo Y/real-repo
  commit = victim_stack.commits.last

  # Explicit binding under test:
  #   repository_owner_used_for_verification == owner_of(repository.full_name)
  repository_owner_for_verification = "X" # org with blank webhook_secret in test config
  owner_of_full_name = "Y" # victim_stack.repository.owner

  refute_equal repository_owner_for_verification, owner_of_full_name

  request.headers['X-Github-Event'] = 'check_suite'
  body = {
    repository: { full_name: "#{owner_of_full_name}/real-repo", owner: { login: repository_owner_for_verification } },
    check_suite: { head_sha: commit.sha, head_branch: victim_stack.branch }
  }.to_json

  # Assert both sides of the binding: verification org (X) != mutated stack's owning org (Y),
  # yet the job is enqueued for Y's commit — proving the binding is not checked.
  assert_enqueued_with(job: RefreshCheckRunsJob, args: [commit_id: commit.id]) do
    post :create, body:, as: :json
    assert_response :ok
  end
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
