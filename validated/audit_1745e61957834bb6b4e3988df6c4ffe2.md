Confirmed: neither `assocKnownBadUnits` (set in `purgeJointAndDependencies` and `collectQueriesToPurgeDependentJoints`) nor `assocKnownBadJoints` (set in `checkIfNewJoint` and `saveKnownBadJoint`) are ever deleted from, unlike `assocUnhandledUnits` which is purged hourly by `purgeOldUnhandledJoints`.### Title
Unbounded in-memory growth of `assocKnownBadUnits`/`assocKnownBadJoints` from attacker-controlled unit/joint validation failures - (File: joint_storage.js)

### Summary
`joint_storage.js` maintains process-lifetime, unbounded in-memory maps `assocKnownBadUnits` and `assocKnownBadJoints` that are populated every time a posted unit or joint fails validation. Unlike the sibling cache `assocUnhandledUnits`, which is periodically purged, these two maps are never evicted, so any unprivileged unit poster can grow them indefinitely by repeatedly submitting distinct invalid units/joints, producing an unbounded memory leak analogous to the referenced iText reference-table memory-leak CVE (an internal bookkeeping table that accumulates entries without cleanup as attacker-supplied input is processed).

### Finding Description
`joint_storage.js` declares three module-level caches: [1](#0-0) 

`assocUnhandledUnits` is bounded by `purgeOldUnhandledJoints()`, which deletes entries older than 1 hour: [2](#0-1) 

However, `assocKnownBadUnits` and `assocKnownBadJoints` have no equivalent purge routine anywhere in the codebase. They are written to in three places:
- `purgeJointAndDependencies()`, called whenever `validation.validate()` reports `ifUnitError` for a freshly posted/received unit (via `network.js`'s `handleJoint`): [3](#0-2) 
- `collectQueriesToPurgeDependentJoints()`, which cascades the bad-unit marking to every dependent unit chained off the bad one: [4](#0-3) 
- `saveKnownBadJoint()`, called for `ifJointError` (structural/joint-level errors): [5](#0-4) 

These are invoked directly from `network.js`'s `handleJoint`, which is the entry point for any unit reaching the node — whether posted locally (`bPosted`) or received from a peer: [6](#0-5) 

Each key is a 44-character unit hash (or joint hash) and the value is a truncated error string (up to 200 chars via `truncate()`): [7](#0-6) 

Because unit content (parents, timestamp, messages, payload) is entirely attacker-controlled, an actor can trivially mint an unlimited stream of syntactically-distinct-but-invalid units/joints (e.g., failing signature checks, bad definitions, or invalid payment structure) and post them to the node (via the `post_joint`/light `post_unit` API path or normal joint broadcast). Every failure adds a permanent entry to these two `{}` objects, which are never garbage collected, unlike `storage.js`'s `assocCachedUnits`/`assocUnstableUnits` family which are actively shrunk by `shrinkCache()`: [8](#0-7) 

By contrast, `assocKnownBadUnits`/`assocKnownBadJoints` have no such counterpart, and `initUnhandledAndKnownBad()` on startup even deliberately skips reloading old known-bads from the DB ("ignore old known-bads"), confirming the in-memory known-bad map was intended to be a small/rolling set but in practice grows without bound during the process's uptime: [9](#0-8) 

### Impact Explanation
This is a pure availability/reliability issue: continuous submission of invalid units (something any unprivileged node/peer/AA author can do without spending funds, since invalid units are rejected before any balance impact) causes the node's memory usage to grow monotonically for the life of the process. Over time this leads to increased GC pressure, degraded validation throughput, and eventually process OOM, which can affect a node's ability to validate/relay/confirm new units — matching the "network unable to confirm new units" impact class from the validation rubric.

### Likelihood Explanation
High reachability: any single peer or unprivileged local submitter can trigger `ifUnitError`/`ifJointError` paths simply by constructing invalid but distinct units, no special privileges, keys, or coordination required. The only limiting factor is that `handleJoint` requires each unit to be syntactically parseable enough to reach `validation.validate`, which is trivial to satisfy while still failing later checks (e.g. bad author signature or invalid definition), so an attacker can generate effectively unlimited unique failing units cheaply and continuously.

### Recommendation
Add TTL-based eviction for `assocKnownBadUnits` and `assocKnownBadJoints` mirroring `purgeOldUnhandledJoints()` (e.g., a `setInterval`-driven purge based on `known_bad_joints.creation_date`), or cap their size with an LRU-style eviction similar to `MAX_ITEMS_IN_CACHE` used in `storage.js`'s `shrinkCache()`. At minimum, these in-memory maps should be treated purely as fast-path short-term caches (say, evicted after minutes) and rely on the `known_bad_joints` DB table for long-term "is this a known bad unit" lookups.

### Proof of Concept
1. Attacker repeatedly crafts syntactically-valid-but-signature/definition-invalid units, each with a distinct random `unit` hash (e.g., varying the `parent_units`/`last_ball_unit`/nonce fields so each hashes uniquely), and posts them via the node's normal unit submission path (`post_joint`) or broadcasts them as a peer.
2. Each submission flows into `network.js`'s `handleJoint` → `validation.validate` → `ifUnitError`/`ifJointError` → `joint_storage.purgeJointAndDependenciesAndNotifyPeers` / `saveKnownBadJoint`.
3. Each call adds one permanent entry to `assocKnownBadUnits` or `assocKnownBadJoints` (never deleted).
4. Repeating step 1 indefinitely (e.g., thousands of times per hour) causes the two associative arrays to grow without bound, consuming heap memory until the node experiences degraded performance or crashes with an out-of-memory error, disrupting the operator's ability to keep validating/confirming the network's units.
