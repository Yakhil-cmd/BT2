### Title
Cross-repository status forgery advances unrelated `MergeRequest` to `merge!` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's originating repository matches the `Commit`'s owning stack/repository. Because git commit objects are content-addressed, an attacker who controls any other Shipit-registered repository can reproduce the exact same commit object (and therefore the exact same sha) as the head of their PR against the victim repository, then legitimately trigger a `status` webhook from their own repo that GitHub signs correctly. That webhook's `success` status is applied to the victim's `Commit` row, which can push a queued `MergeRequest` through `all_status_checks_passed?` and into `merge!`.

### Finding Description
The broken binding, stated explicitly: the code implicitly assumes
`webhook.repository.full_name == commit.stack.repository.full_name`
but the actual code enforces only
`webhook.repository.owner.login == organization_whose_app_secret_signed_the_request`.

These are not the same binding. `StatusHandler#process` does: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no join/filter on `params.repository` at all. The `Commit` table has a `(sha, stack_id)` unique index, explicitly allowing the *same* sha to exist as a row in multiple stacks: [2](#0-1) 

The only gate before this handler runs is `WebhooksController#verify_signature`, which validates the HMAC signature against the secret configured for `Shipit.github(organization: repository_owner)` — i.e., it authenticates *which organization/app installation* sent the webhook, not that the `sha` inside the payload belongs to that organization's repository: [3](#0-2) [4](#0-3) 

Exploit flow: the attacker opens a PR against the victim repo (unprivileged action), noting the head commit's sha (public). Since git commits are content-addressed, the attacker fetches that exact commit object and pushes it as the head of a branch in a second repository they own and that they have separately onboarded into the same Shipit instance (so it has a legitimate GitHub App/webhook secret). The attacker then creates a `success` commit status via GitHub's Status API on their own repo/sha (an action they are fully authorized to do, since they own that repo). GitHub signs and delivers the resulting `status` webhook correctly for the attacker's org. `verify_signature` passes because the signature really is valid for that org. `StatusHandler#process` then finds the `Commit` row(s) with that sha — including the victim's stack's `Commit` for the queued PR head — and writes a `success` `Status` to it via `commit.create_status_from_github!`. This triggers `Status#schedule_continuous_delivery` → `ProcessMergeRequestsJob` (confirmed pattern in `test/models/commits_test.rb:763-777`), which calls `merge_request.refresh!` → `all_status_checks_passed?` → `StatusChecker.new(head, head.statuses_and_check_runs).success?` now true → `merge_request.merge!` → `stack.github_api.merge_pull_request`, merging the victim's PR without any interaction with the victim repository itself.

None of the existing guards catch this: `verify_signature` authenticates organization-level webhook provenance, not sha-to-repository ownership; there is no `ExplicitParameters` constraint tying `params.repository` to the `Commit`'s stack in `StatusHandler`; and `all_status_checks_passed?`/`StatusChecker` operate purely on `Status` rows already persisted, trusting that they were correctly attributed to the right repository.

### Impact Explanation
An attacker can cause `Shipit::MergeRequest#merge!` to invoke `stack.github_api.merge_pull_request` for a pull request in a victim repository they do not control, using only a status webhook fired from a repository they legitimately own. This is an unauthorized merge triggered by a payload from one repository mutating another repository's `Commit`/`MergeRequest` state — matching the Critical impact category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The attack is repeatable against any queued PR in any repository sharing the Shipit instance, as long as the attacker can reproduce an identical commit object, and generalizes across all tenants hosted by the same Shipit deployment.

### Likelihood Explanation
Preconditions: victim stack must have `merge_queue_enabled?` true and a pending `MergeRequest`; the attacker needs write/status permission on some other repository already registered with the same Shipit instance (their own repo, or a repo in an org they control that onboards to Shipit). Reproducing an identical commit sha is not a cryptographic collision — it is normal git behavior (content-addressed objects), so the attacker only needs to fetch/copy the victim's public commit object into their own repo, which is low-cost and fully repeatable. No secrets, sessions, or privileged roles are required.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous `CheckSuiteHandler`) to the repository/stack derived from the webhook payload, e.g., resolve `stacks` by `params.repository.full_name` first and then look up `stack.commits.where(sha: params.sha)`, mirroring the branch-scoped pattern already used in `CheckSuiteHandler#process`. Reject or ignore statuses whose payload repository does not match the commit's owning stack.

### Proof of Concept
Minitest plan (models/webhook handler level, no live GitHub):
1. Create two stacks/repos in fixtures: `victim_stack` (merge_queue_enabled: true) and `attacker_stack`, each with a `Commit` row sharing the identical `sha` value (simulating the content-addressed collision).
2. Create a pending `MergeRequest` on `victim_stack` whose `head` is the shared-sha `Commit`.
3. Post a `status` webhook payload (`sha` = shared sha, `state` = "success", `repository.full_name` = `attacker_stack`'s repo) through `Shipit::Webhooks::Handlers::StatusHandler.new(params).process` (or via the controller with signature stubbed for the attacker's org only).
4. Assert `victim_stack`'s `Commit#statuses` gained a `success` status though the request never referenced `victim_stack`.
5. Expect `Shipit.github.api.expects(:merge_pull_request)` to be called after enqueuing/running `ProcessMergeRequestsJob.perform_now(victim_stack)`, asserting `merge_request.reload.merge_status == 'merged'` (or that `merge!` was invoked) with no direct interaction with the victim PR/repo in the test.
