### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` corrupts victim stack's CI state and can trigger auto-ship/block on continuous-deployment-enabled stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table, with no filter on the repository/stack that authenticated the webhook, then writes a status onto every matching `Commit` row via `commit.create_status_from_github!`. Since a git SHA is content-addressed and identical commits legitimately exist in multiple repositories (e.g., forks sharing history with an upstream), an attacker who controls any repository onboarded to the same Shipit instance can produce a genuine, correctly-signed `status` webhook for a SHA that also exists in a victim stack, and have that status attached to the victim's `Commit`, using the victim stack's `stack_id`.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack_id == repository_that_authenticated(payload)`, but no code enforces this equality.

- `Shipit::WebhooksController#verify_signature` only checks that the payload was HMAC-signed with the webhook secret belonging to `repository_owner` (derived from `params.dig('repository','owner','login')` in the *attacker's own* payload): [1](#0-0) . This proves only that the *sender's* org/repo is who it claims to be — it says nothing about which stack the SHA belongs to.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is global across all stacks/repositories in the Shipit instance — it is not scoped by `repository_name`/`stacks` the way other handlers are (compare `Handler#stacks`, which does scope by `Repository.from_github_repo_name(repository_name)`): [3](#0-2) .
- `Commit#create_status_from_github!` writes the status using the commit's own `stack_id`, not any ID derived from the attacker's payload: [4](#0-3) , and `add_status` reloads and recomputes `status`, firing `deployable_status` hooks and calling `stack.schedule_merges` on state transitions: [5](#0-4) .
- `Commit belongs_to :stack`: [6](#0-5) , and a new commit's continuous delivery is scheduled from `schedule_continuous_delivery`, gated only on `deployable? && stack.continuous_deployment? && stack.deployable?`: [7](#0-6) . `deployable?` is computed from `status`/`statuses_and_check_runs`, which is exactly what `StatusHandler` mutates.

**Exploit flow:** Attacker forks (or otherwise shares commit history with) the victim's tracked repository, and also owns/administers a separate repository that is legitimately onboarded to the same Shipit instance (satisfying "attacker can push to a fork and emit webhooks from a repository they own"). Because a shared commit has an identical SHA-1 in both repositories, the attacker sets a commit status (`context: ci/integration`, `state: failure`) on their own repo via the GitHub API — a normal, legitimate action for a repo owner. GitHub sends a real, correctly-HMAC-signed `status` webhook for the attacker's repo to Shipit. `verify_signature` passes (it is genuinely signed for the attacker's org). `StatusHandler#process` then finds *all* `Commit` rows with that SHA — including the one belonging to the unrelated victim stack — and writes the `failure` status onto it, flipping the victim's cached CI status for that commit. If `ci/integration` is a status the victim's stack treats as required (or blocking), this can block a ship that should have proceeded, or — on the flip side, by sending a `success` for a SHA in a continuous_deployment-enabled victim stack — push a previously-blocked/pending commit toward deployability and trigger `ContinuousDeliveryJob` to ship it.

Existing guards do not prevent this: `verify_signature` authenticates the *sender*, not the *target record*; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not ownership; there is no `stacks`/`Repository.from_github_repo_name` scoping applied in `StatusHandler` the way `Handler#stacks` provides for other handlers.

### Impact Explanation
A payload authenticated for repository/org A causes a write against a `Commit`/`Status` record belonging to stack B's repository, satisfying the "payload for one repository mutating another's stack/commit" Critical criterion. On a continuous_deployment-enabled victim stack, this can force an unwanted ship (via a forged `success`) or block a legitimate deploy/merge (via a forged `failure`) for commits the victim never sanctioned in that state. The attack is repeatable against any stack that shares commit history (via forks, cherry-picks, or identical rebase results) with a repository the attacker controls, and works against the shared-SHA space broadly, not one victim in isolation.

### Likelihood Explanation
Preconditions: (1) attacker owns/administers at least one repository already onboarded as a Shipit stack (so they can emit a genuinely-signed webhook), and (2) that repository shares at least one commit SHA with the victim's tracked repository (trivially true for public forks of the same upstream, or for commits cherry-picked/rebased identically across repos). No secrets, sessions, or GitHub App keys are required — the attacker relies on GitHub itself to sign the webhook for their own repo. Cost is low (fork + `POST` a status via GitHub API to their own repo) and the action is repeatable at will for every shared SHA.

### Recommendation
Scope `StatusHandler#process` (and any other bare-SHA handler) to the repository that authenticated the webhook, e.g., restrict the `Commit` lookup to `stacks` derived from `Repository.from_github_repo_name(repository_name)` (as `Handler#stacks` already provides), instead of a global `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb` style, or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks/repositories, `victim_repo`/`victim_stack` (continuous_deployment: true, required `ci/integration` context) and `attacker_repo`/`attacker_stack`, each with a `Commit` row sharing the same `sha` value (simulating a shared/forked commit).
2. Assert baseline: `victim_stack.commits.find_by(sha: shared_sha).state == 'pending'` (or whatever pre-state), and `victim_stack.deployable_commits` does not include it / stack is not about to auto-ship.
3. POST a `status` webhook payload for `attacker_repo` (`repository.owner.login` = attacker org, correctly signed for that org) with `sha: shared_sha, context: 'ci/integration', state: 'failure'`.
4. Assert `victim_stack.commits.find_by(sha: shared_sha).state == 'failure'` (or equivalently `.statuses.where(context: 'ci/integration').last.state == 'failure'` with `stack_id == victim_stack.id`), proving the victim's record changed even though the webhook only authenticated `attacker_repo`.
5. Repeat with `state: 'success'` and assert `ContinuousDeliveryJob` gets enqueued for `victim_stack` (via `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])`) purely from the attacker-repo-signed webhook.

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      end
