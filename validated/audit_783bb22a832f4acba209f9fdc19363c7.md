### Title
Webhook signature is verified against `repository.owner.login` while stack resolution is keyed on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which reads `repository.owner.login` (falling back to `organization.login`) from the *same attacker-controlled JSON body* that the HMAC covers. Once the signature check passes, every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`) independently re-reads `repository.full_name` from that same body to decide which `Repository`/`Stack` to act on. Nothing ties these two fields together, so a payload can be crafted where the "owner" used for authentication and the "owner" embedded in `full_name` used for the actual write diverge.

### Finding Description
This mirrors the `SynthToken` bug class: the code appears to bind a security-relevant read to one variable/field, but the value that is actually consumed downstream comes from a different, unguarded field, so the two silently diverge.

- Signature verification selects the GitHub App/secret via: [1](#0-0) 
using [2](#0-1) 
which reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) — both are attacker-supplied fields inside the raw JSON body whose HMAC is verified with `verify_webhook_signature`.

- Every default handler (push, pull_request, status, check_suite, membership) resolves the target repository/stack via a completely different field: [3](#0-2) 
which does `payload.dig('repository', 'full_name')` and looks up `Repository.from_github_repo_name`: [4](#0-3) 

Because HMAC-SHA1 authenticates the raw byte string of the whole payload but the code only *derives meaning* from two independently-parsed JSON fields (`repository.owner.login` vs `repository.full_name`), there is no requirement that `full_name` actually starts with `owner.login`. An attacker who can obtain a validly signed payload for organization `A` (e.g., is a legitimate, authorized webhook sender for org `A`, which Shipit already trusts to deliver events for org `A` repos) can put `repository.owner.login = "A"` (so the signature check picks org `A`'s secret and passes) while setting `repository.full_name = "B/some-other-repo"`. The push/pull_request/status/check_suite/membership handlers will then operate on stacks belonging to repository `B`, an organization the attacker was never authorized to send events for.

Binding broken (as an equality that should hold but doesn't):
`organization that authenticated the request (repository.owner.login / organization.login)` == `repository that is actually written to (repository.full_name)`

Before the attacker's request: these two fields are always consistent, because GitHub itself constructs both from the same underlying repository object.
After the attacker's crafted payload: `repository.owner.login` (used to pick the trusted `webhook_secret`) and the owner encoded in `repository.full_name` (used to pick the `Stack` to mutate) can point to two different organizations, yet the signature still validates.

### Impact Explanation
This allows a party who is validly authorized to deliver webhooks for one GitHub organization to inject a payload that causes Shipit to act on stacks belonging to an entirely different organization/repository it never registered a webhook for — e.g., triggering `GithubSyncJob`/deploy sync (`push` handler), forging PR state transitions (`pull_request` handlers, including provisioning/unarchiving review stacks), forging commit statuses, or manipulating team membership. This is a cross-repository/cross-organization write achieved purely by controlling JSON body content while reusing a legitimately-issued signature, i.e., an unauthorized write across the repository trust boundary the signature is supposed to enforce.

### Likelihood Explanation
Requires the attacker to already be capable of generating a validly-signed webhook body for at least one organization Shipit trusts (a bar the engine's design assumes is only met by GitHub itself, but the check only validates the raw byte signature — not that the signed fields are self-consistent). Given that bar, crafting the divergent `owner.login` / `full_name` fields is trivial (plain JSON body construction), making exploitation straightforward once the authentication bar is cleared.

### Recommendation
Do not derive the trust-establishing organization from a field independently re-read by handlers. Instead:
- Derive the webhook secret's organization from the same canonical value used for repository resolution (`repository.full_name`'s owner segment), or
- After verifying the signature, cross-check that `repository.owner.login` (or `organization.login`) is consistent with the owner portion of `repository.full_name`, rejecting the request (422) if they differ.

### Proof of Concept
1. Attacker legitimately controls webhook delivery for org `A` in Shipit (has valid `webhook_secret_A`).
2. Attacker crafts a `push` JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<forced-sha>",
  "repository": {
    "owner": { "login": "A" },
    "full_name": "B/victim-repo"
  }
}
```
3. Computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "A")` (from `repository_owner`), verifies successfully against `webhook_secret_A`.
5. `PushHandler` (via `Handler#repository_name`) resolves `Repository.from_github_repo_name("B/victim-repo")` and syncs/deploys stacks under organization `B`, which the attacker never had permission to send events for.
