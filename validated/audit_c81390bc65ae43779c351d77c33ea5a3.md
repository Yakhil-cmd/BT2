### Title
Field-boundary collision in `getHashSrc` allows forging arbiter contract content under an identical hash - (File: `arbiter_contract.js`)

### Summary
`arbiter_contract.js` computes the identifier/signature-anchor of a private arbitration contract (`getHash`) by concatenating free-form, attacker/peer-controlled string fields (`title`, `text`, party names, etc.) with a fixed separator and hashing the result. Because the separator itself is not forbidden inside the concatenated fields, two different sets of field values can produce byte-identical concatenated strings and therefore identical hashes — the same "truncate/split via unescaped delimiter" bug class as CVE-2023-27522 (where an unescaped special character let one party's parsed message differ from what was actually sent).

### Finding Description
`getHashSrc()` builds the hash source for a prosaic (arbiter) contract like this: [1](#0-0) 

For contracts created after `NEW_HASH_DATE`, the fields are joined with `exports.DELIMITER = "[|#|]"` [2](#0-1)  — but none of `title`, `text`, `my_party_name`/`peer_party_name` are validated to reject the delimiter sequence before being included in the hash source. `title` and `text` are free-text fields stored directly from the contract-creation payload with only length/type constraints enforced at the DB schema level (`VARCHAR(1000)`/`TEXT`), not at the application/hash level. `getHash()` simply SHA-256/base64-hashes that source string: [3](#0-2) 

Because the join is a plain string concatenation with a fixed separator string, an attacker fully controls where the separator sequence appears. This lets an attacker construct two distinct field assignments whose concatenations are byte-identical, e.g.:
- Set A: `title = "Loan for $500[|#|]"`, `text = "repay in 30 days"`
- Set B: `title = "Loan for $500"`, `text = "[|#|]repay in 30 days"`

Both produce the same string `"Loan for $500[|#|][|#|]repay in 30 days" + DELIMITER + ...` once the remaining fixed fields are appended, so `getHash()` returns the same value for materially different contract text/title splits. Since the hash is what is shared with the peer, propagated to cosigners via `arbiter_contract_shared`/`arbiter_contract_update` [4](#0-3) , and used as the primary key `wallet_arbiter_contracts.hash` that both the peer and the arbiter rely on to identify "the agreed contract" [5](#0-4) , a counterparty can present a re-split (differently worded) version of the contract to the arbiter or the other party while both share the identical, ostensibly-integrity-protecting hash.

This mirrors the CVE-2023-27522 bug class exactly: an unescaped separator allows the same serialized bytes/hash to be produced from — and therefore reinterpreted as — two different logical messages, defeating the receiver's ability to trust that the hash uniquely commits to one specific set of field values.

### Impact Explanation
Arbiter contracts govern spending out of a `shared_address` multisig funded by the counterparties, with the arbiter's decision (`resolution_unit`) determining fund disbursement (`me_is_payer`, `amount`, `asset` fields participate in the very same hash). If a party can construct alternate title/text splits that hash identically, they can:
- Show the arbiter (or the counterparty at signing time) one version of the contract terms while having previously agreed under the identically-hashed but differently split content, creating room to dispute or mis-resolve arbitration and cause the shared funds to be released to the wrong party — i.e., unauthorized/disputed spending of jointly held funds.
- Undermine `getContactsHash`-style trust assumptions where the hash is treated as a non-repudiable commitment to the exact agreed text.

This falls within “private payment counterparty … wallet and contract message handling” scope explicitly allowed in the rules, and the impact category is unauthorized fund disposition via a broken integrity commitment.

### Likelihood Explanation
Both `title` and `text` are attacker-supplied when creating an offer (`createAndSend`) and are stored verbatim; the only gate on the delimiter appearing inside them is its low probability of accidental occurrence, not an active check — the DELIMITER string `"[|#|]"` is unusual enough to avoid accidental collisions but trivially insertable by any contract creator (payer or payee) who wants to exploit the collision, requiring no cooperation from the victim and no upgrade/protocol interaction. The only mitigating factor is that this code path (`NEW_HASH_DATE = '2026-11-01'`) is not yet active in production — the vulnerable "new hash" branch and its separator become effective only for contracts created after that date, so present likelihood is low until then, but the introduced logic is otherwise reachable, deterministic, and requires no special privileges.

### Recommendation
Before concatenating fields for hashing, reject (or escape/length-prefix) any field that contains the `DELIMITER` sequence, analogous to how `getSourceString` rejects the `STRING_JOIN_CHAR` in each field: [6](#0-5) . Alternatively, switch `getHashSrc` to use `string_utils.getSourceString`/`getJsonSourceString`, which already enforce this invariant and are used elsewhere in the codebase precisely to avoid this class of bug, e.g. in unit/message hashing: [7](#0-6) .

### Proof of Concept
1. Party A creates contract offer 1 with `title = "Deal terms[|#|]"`, `text = "pay 100"`, fixed `creation_date`, `arbiter_address`, `amount`, `asset`, party addresses/names.
2. Party A independently computes `getHashSrc`/`getHash` for offer 2 with `title = "Deal terms"`, `text = "[|#|]pay 100"` and the same remaining fields.
3. Both `getHash()` calls in `arbiter_contract.js:205-207` [3](#0-2)  return an identical base64 SHA-256 digest because the concatenated `getHashSrc` strings are byte-identical, despite `title`/`text` differing.
4. Party A sends offer 1 to the counterparty for acceptance/signature, then later presents offer 2's rendering (different title/text split) to the arbiter during a dispute — both bear the same `hash`, so the arbiter/`wallet_arbiter_contracts` record keyed by `hash` cannot distinguish which version was actually agreed.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
