### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with `Commit.where(sha: params.sha)`, with no scoping to the repository that authenticated the webhook. Since `sha` is only indexed together with `stack_id` (not globally unique) [1](#0-0) , any commit row in any stack whose SHA matches the attacker's payload SHA gets a new `Status` written against it, regardless of which repository actually owns that commit.

### Finding Description
The broken binding: the code assumes `Commit.where(sha: params.sha) == commits belonging to the repository that signed this webhook`, but in reality `Commit.where(sha: params.sha)` returns **all** commit rows across **all** stacks/repositories sharing that SHA — an unrelated invariant.

`StatusHandler#process`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This contrasts with the base `Handler` class, which explicitly provides a repository-scoped `stacks` helper derived from `payload.dig('repository', 'full_name')` for exactly this purpose [3](#0-2) , but `StatusHandler` does not use it.

`commit.create_status_from_github!` writes the status keyed to the commit's *actual* `stack_id`, not the webhook's repository:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [4](#0-3) 

`WebhooksController#verify_signature` only proves the payload was signed by GitHub for the organization named in `payload['repository']['owner']['login']` [5](#0-4) ; it does **not** verify that the `sha` field actually belongs to that repository's history. Since git SHAs are content-addressed, an attacker-controlled repository (a fork, a repo sharing history, or one seeded with an identical tree/commit) can legitimately emit a signed `status` event carrying a SHA that is identical to a commit tracked by a victim's Shipit stack.

Exploit flow:
1. Attacker owns/controls `attacker/repo`, which shares (or is engineered to share) a commit SHA with the victim's tracked stack (e.g., via fork, cherry-pick, or common upstream history).
2. Attacker triggers a genuine, correctly-signed GitHub `status` webhook from `attacker/repo` with `context: ci/lint`, `state: failure`, `sha: <shared-sha>`.
3. `verify_signature` passes because the signature is valid for `attacker/repo`'s organization.
4. `StatusHandler#process` matches the victim's `Commit` row by bare SHA (unscoped) and calls `create_status_from_github!`, writing a `Status` to the victim's commit under the victim's `stack_id`.
5. If `ci/lint` is in the victim stack's `required_statuses`/`blocking_statuses`, this flips `commit.deployable?`/`commit.blocked?` for the victim, affecting `schedule_continuous_delivery`, `schedule_merges`, and downstream deploy/merge decisions [6](#0-5) [7](#0-6) .

No existing guard prevents this: `verify_signature` authenticates the *sender repository*, not the *SHA's ownership*; `ExplicitParameters` only validates the shape of `sha`/`state`/`context` as strings, not their repository binding.

### Impact Explanation
An attacker with no privileges beyond controlling their own repository can write `Status` records into a victim stack's commit that they do not own, by exploiting the fact that `StatusHandler` performs a global, unscoped SHA lookup instead of using the repository-scoped `stacks`/`Repository.from_github_repo_name` pattern used elsewhere in the handler hierarchy. This can flip `deployable?`/`blocked?` for the victim, causing an unauthorized block of deploys/merges (or, with a forged `success` payload, unblocking them) — a cross-tenant state mutation matching the Critical category "a payload for one repository mutating another's stack, commit, task." This is repeatable against any stack that shares a commit SHA with an attacker-controlled repository.

### Likelihood Explanation
Requires the attacker to control a GitHub repository that authenticates with Shipit's GitHub App for some organization (any org configured in `Shipit.github_teams`/`Shipit.github_apps`), and to obtain a commit SHA collision with the victim's tracked commit — achievable via a fork of the victim repo, shared upstream history, or cherry-picked/rebased commits that preserve SHAs. This requires no secrets, no Shipit session, and only a single crafted push/status event, making it low-cost and repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository/stacks that authenticated the webhook, mirroring `Handler#stacks`, e.g. resolve `stacks` via `payload.dig('repository', 'full_name')` and restrict `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))` (or join through `stack.repository`) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status for a SHA shared with a different repository does not affect the unrelated stack" do
  victim_stack = shipit_stacks(:shipit) # repository X
  attacker_repo = create_repository(full_name: 'attacker/repo')
  shared_sha = 'a' * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')
  # simulate attacker owning an unrelated repo whose commit table also has this sha via their own stack
  attacker_stack = create_stack(repository: attacker_repo)
  attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit')

  before = victim_commit.reload.deployable?

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/lint',
    'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  after = victim_commit.reload.deployable?
  assert_equal before, after, "attacker/repo's status must not affect victim stack's commit"
end
```
This asserts the binding `victim_commit.deployable?` before == after processing an attacker-signed webhook for an unrelated repository sharing the same SHA; under current code the assertion fails because `StatusHandler#process` writes a status to the victim's commit regardless of repository.
