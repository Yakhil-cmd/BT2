### Title
Webhook organization-selection and signature-skip-on-blank-secret allow forged `membership` events to grant unauthorized `Shipit.github_teams` access - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and thus which webhook secret) to validate a payload against by reading `repository.owner.login` / `organization.login` **directly from the unverified JSON body**, and `GithubApp#verify_webhook_signature` unconditionally returns `true` when that configuration's `webhook_secret` is blank/nil. Because Shipit's own documented multi-org configuration format explicitly allows `webhook_secret` to be left `nil` per organization, an attacker can forge a webhook body naming an org that has no secret configured and have it processed with zero HMAC validation. This lets an unauthenticated caller drive event handlers such as the `membership` handler, which creates `Team`/`Membership` records that directly feed `User#authorized?` — i.e. `Shipit.github_teams` authorization — without ever holding a Shipit session, an `ApiClient` token, or the real webhook secret.

### Finding Description
`repository_owner` is computed from the parsed (but not-yet-verified) request body: [1](#0-0) 

`verify_signature` uses that attacker-influenced value to select the `github_app` whose secret will be used to check the signature: [2](#0-1) 

`GithubApp#verify_webhook_signature` treats a blank/nil `webhook_secret` as "always verified": [3](#0-2) 

Shipit's own shipped configuration templates document `webhook_secret` as legitimately nullable per organization, both for single-org and multi-org setups: [4](#0-3) [5](#0-4) 

Once "verified" (trivially, for the no-secret org), the raw body is dispatched to all registered handlers for the event: [6](#0-5) 

The `membership` event handler (exercised by the controller test suite) creates `Team` and `Membership` rows purely from payload content, on behalf of any `member.login` the attacker supplies: [7](#0-6) [8](#0-7) 

`Membership`/`Team` records created this way are exactly what `User#authorized?` checks to grant access to the entire Shipit UI/session flow: [9](#0-8) 
and what gates every authenticated controller via `force_github_authentication`: [10](#0-9) 

**The binding broken (eMode analog):** the organization whose signing-secret policy is "authenticated" for a request (selected from `repository.owner.login`/`organization.login`) is not the same thing the code actually trusts and acts on — it never re-derives or re-checks that the org used to grant "verified" status matches an org that genuinely requires/possesses a secret, and the downstream handler blindly writes team/membership state from the same unverified payload. This is structurally identical to the eMode bug: a security-relevant lookup (`getReserveConfigurationData` for the wrong/base config vs. `getEModeCategoryData`) is performed against the wrong/insufficiently-privileged data source, silently disabling the intended protection (HMAC signature enforcement) for a subset of configured tenants.

### Impact Explanation
Note this depends on a real Shipit deployment configuring at least one GitHub org/App entry with a blank `webhook_secret` — a state the engine's own example/documentation configs present as valid (`webhook_secret: # nil`), not merely an undocumented misconfiguration. Under that condition:
- Any unauthenticated internet client can POST a forged `membership` (or other) event to `/webhooks`, naming itself and effectively self-granting membership in any `Team` matching one of `Shipit.github_teams`.
- Because `User#authorized?` is driven solely by that `Membership`/`Team` state, the attacker (using their own legitimate GitHub OAuth login against Shipit's own `github_authentication_controller` to establish a session with a matching `login`) escalates from an unauthorized/anonymous account into full `Shipit.github_teams` authorization, matching the High-severity bullet "escalation into `Shipit.github_teams` authorization."
- This requires no `ApiClient` token, no session, no webhook secret, no GitHub App private key, and no repository write access — only knowledge that an org with a blank secret is configured, and control of a valid GitHub login of the attacker's choosing.

### Likelihood Explanation
Likelihood is conditioned entirely on operator configuration (at least one org configured with no `webhook_secret`), which the engine ships as a documented, apparently-supported option rather than rejecting at boot or requiring a secret. Given the sherlock report's own framing (an entire security mechanism silently downgraded because the wrong/insufficiently-scoped check is consulted), and that Shipit explicitly ships example configs with blank secrets, this is a realistic, not purely theoretical, deployment state.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization at boot/initialization time, and fail closed (reject the webhook, do not treat as verified) when it is missing, rather than short-circuiting to `true`.
- Do not select the signature-verification policy (which org's secret to check) from unverified payload fields; if multi-tenant routing by org is required, verify the signature against all configured secrets (or bind the webhook route to a specific org) before trusting any field from the body.
- Add a startup/deploy-time check (e.g., in `lib/shipit/engine.rb`) that warns/errors if any configured organization lacks a `webhook_secret`.

### Proof of Concept
1. Operator configures Shipit per the shipped example with an org entry that has `webhook_secret:` left blank (as shown in `config/secrets.development.example.yml`).
2. Attacker signs into Shipit via the normal GitHub OAuth flow (`github_authentication_controller#callback`) using their own GitHub account, login `evil-user`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com"},
  "organization": {"login": "<org-with-blank-secret>"},
  "member": {"login": "evil-user"}
}
```
No `X-Hub-Signature` header is required to pass validation because `verify_webhook_signature` returns `true` for that org.
4. `Shipit::Webhooks.for_event('membership')` handler creates/updates the `Team` and adds `evil-user` as a `Membership`.
5. If `"Ouiche Cooks"`/`ouiche-cooks` matches a team configured in `Shipit.github_teams`, `evil-user`'s next login now satisfies `User#authorized?` and gains full access to the Shipit application.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?

        end
      else

      end
    end
```
