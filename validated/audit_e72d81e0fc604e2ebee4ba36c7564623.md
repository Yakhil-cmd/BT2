## Title
Webhook signature verified against `repository.owner.login` but Stack lookup keyed on `repository.full_name`, enabling cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
The webhook signature-verification step authenticates the request against the GitHub organization named in `repository.owner.login`, while the downstream handler resolves the target `Repository`/`Stack` to act on using the completely separate `repository.full_name` field from the same JSON body. In a multi-tenant Shipit deployment (one Shipit instance backing multiple GitHub Apps/organizations, as documented and tested in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately controls one organization's GitHub App installation can send a hand-crafted webhook payload whose `repository.full_name` names a repository belonging to a *different* organization, while `repository.owner.login` still names their own org. The signature check passes (it is only verified against the attacker's own, legitimately-known webhook secret), but the write action is performed against the other org's tracked repository/stack.

## Finding Description
`WebhooksController#verify_signature` selects which GitHub App config to use for HMAC verification purely from the payload itself: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This proves only that *someone who knows the webhook secret configured for `repository.owner.login`'s GitHub App* sent the raw body — i.e., it authenticates the org identified by `repository.owner.login`.

The event handler that actually performs the write, however, resolves the target repository using a *different* field, `repository.full_name`, and never cross-checks it against `repository.owner.login`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `owner/name` straight out of `full_name` and looks the `Repository` up by that owner/name pair, independent of `repository.owner.login`: [4](#0-3) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the branch matching `params.ref`, which is exactly the write path exercised by the report's underlying bug class: a value that is signature-verified (`repository.owner.login`) diverges from the value that is actually acted upon (`repository.full_name`) — the same "verified field vs. acted-upon field" inconsistency as `priceTarget` in the `StabilizerNode.stabilize` report, where `stabilizeToPeg` gated one calculation but a different, uncoupled calculation of `priceTarget` was used downstream. [5](#0-4) 

Concretely, a JSON payload like:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "OrgOne/private-repo",
    "owner": { "login": "OrgTwo" }
  }
}
```
signed with `OrgTwo`'s legitimately-known webhook secret passes `verify_signature` (because `repository_owner` resolves to `OrgTwo`), yet `PushHandler` operates on stacks belonging to `Repository` `OrgOne/private-repo` because `repository_name` is taken from `full_name`.

## Impact Explanation
This breaks the equality that should hold for every webhook: `organization that authenticated == repository that is written`. Instead, the org whose secret authenticated the request (`repository.owner.login`) can diverge from the repository whose `Stack`s are subsequently synced/mutated (`repository.full_name`). Any tenant who legitimately controls a GitHub App installation on their own organization (an unprivileged actor relative to other tenants) can trigger `GithubSyncJob`/`sync_github` and other handler side effects against another organization's tracked repository/stack records, which is a cross-repository write — the impact class explicitly listed as Critical in the scope rules ("cross-repository writes").

## Likelihood Explanation
Exploitability requires only: (1) the target Shipit instance to be multi-tenant, i.e. configured with more than one GitHub organization/App in `Shipit.github` (a supported and documented configuration, evidenced by `test/dummy/config/secrets_double_github_app.yml` and the multi-org `secrets.development.shopify.yml` sample), and (2) the attacker to control any one of those orgs' webhook delivery (which they legitimately do, as an org admin can always trigger webhooks for their own installed app). No GitHub App private key, no `webhook_secret` of the victim org, and no privileged Shipit account are needed — only the attacker's own org's webhook secret, which they are entitled to know. This satisfies the "unprivileged attacker" and "no privileged credential" constraints in the rules.

## Recommendation
After successfully verifying the HMAC signature, cross-check that `repository.owner.login` (the org whose secret authenticated the payload) matches the owner portion of `repository.full_name` before resolving/acting on any `Stack`. Reject (422) any webhook where these two fields disagree, mirroring how `_shouldAdjustSupply` and `stabilize` should have used one consistent source of truth for `priceTarget` in the referenced report.

## Proof of Concept
1. Configure Shipit with two GitHub App organizations, `OrgOne` and `OrgTwo` (as supported per `test/dummy/config/secrets_double_github_app.yml`), each tracking their own repositories/stacks.
2. As an attacker who administers `OrgTwo`'s GitHub App (and therefore legitimately knows `OrgTwo`'s `webhook_secret`), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker sha>",
     "repository": { "full_name": "OrgOne/target-repo", "owner": { "login": "OrgTwo" } }
   }
   ```
3. Compute `X-Hub-Signature` as `sha1=HMAC(OrgTwo_webhook_secret, raw_body)` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"OrgTwo"`, fetches `Shipit.github(organization: "OrgTwo")`, and verifies successfully since the signature does match `OrgTwo`'s secret over the exact raw body — [1](#0-0) .
5. `PushHandler#process` runs, resolving `stacks` via `Repository.from_github_repo_name("OrgOne/target-repo")` — [3](#0-2)  — and triggers `sync_github` for `OrgOne`'s stack even though the request was only authenticated for `OrgTwo`.

Note: I was not able to fully trace every downstream side effect of `sync_github`/`GithubSyncJob` (e.g., whether it performs further GitHub API calls that would fail against a repo the `OrgTwo` app token can't access, which could partially mitigate real-world impact for handlers requiring GitHub API round-trips). Handlers that mutate local Shipit state directly from payload data (e.g., `PushHandler` enqueuing `GithubSyncJob` with an attacker-chosen `expected_head_sha`) do not require any further GitHub API authorization to have already caused the enqueue/DB-level effects described above.
