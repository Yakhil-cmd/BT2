## Analysis

This confirmed the required binding-break analog: in a multi-organization Shipit deployment (`Shipit.github_organizations` returns multiple keys under `secrets.github`), incoming webhooks are verified against the wrong identity source relative to what the webhook payload is actually allowed to mutate.

`WebhooksController#verify_signature` selects which org's `webhook_secret` to HMAC-verify against using `repository_owner`, which is read straight from the unauthenticated, attacker-suppliable JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), before any signature check occurs: [1](#0-0) [2](#0-1) 

But the handler that actually acts on that payload resolves the target repository/stack from an entirely different field, `repository.full_name`, with no cross-check that it belongs to the same organization that was used to select the verification secret: [3](#0-2) 

`Shipit.github(organization:)` raises `GithubOrganizationUnknown` only if the org key is absent from `secrets.github`; if it exists but has a blank/misconfigured `webhook_secret`, `GitHubApp#verify_webhook_signature` short-circuits to `true`: [4](#0-3) [5](#0-4) 

So the equality that should hold — *organization whose secret authenticated the request* == *organization owning the repository the handler mutates* — is never enforced. An attacker who controls (or knows a misconfigured/secret-less) organization onboarded into the same Shipit instance can craft `repository.owner.login` = that weak org (satisfying `verify_signature`) while setting `repository.full_name` = a victim repo belonging to a different, properly-secured organization. Handlers such as the `push` handler (enqueuing `GithubSyncJob`, which trusts `stack_id` derived from `repository_name`) or the `membership`/`pull_request` handlers will then process the forged event against the victim stack, all without ever possessing the victim org's real webhook secret.

This is a direct structural analog of the DYAD report's pattern: a privileged check is anchored to a field (`repository.owner.login`) that is disjoint from the field actually driving the state mutation (`repository.full_name`), letting an unprivileged party satisfy the guard cheaply while affecting a target the guard was never actually validating.

### Title
Webhook signature verification keys off `repository.owner.login` while handlers act on the unrelated `repository.full_name`, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization config used to compute the expected HMAC based on `repository_owner`, extracted from the unverified JSON body before the signature is checked: [6](#0-5) 
Every webhook handler, however, resolves the `Repository`/`Stack` to mutate using `payload.dig('repository', 'full_name')`, a completely separate JSON field that is not constrained to match `repository.owner.login`: [7](#0-6) 
Because Shipit supports multiple GitHub organizations sharing one instance (`Shipit.github_organizations`, `github_app_config`), and per-org `webhook_secret` is optional (verification is skipped entirely when blank): [8](#0-7) [5](#0-4) 
an attacker can pass verification using one (weak/no-secret) org's identity while the payload's `full_name` targets a repository under a different, correctly-secured organization.

### Impact Explanation
This breaks the authentication boundary the webhook signature is supposed to enforce: it lets an unprivileged external party inject forged GitHub events (push, membership, pull_request, commit_status, check_suite, etc.) against stacks/repositories belonging to organizations they have no legitimate credentials for, as long as any other org on the same Shipit instance is weakly configured. Consequences include triggering `GithubSyncJob` to append attacker-chosen commit metadata to a victim stack, forging commit statuses that gate deploy eligibility, or creating/removing team memberships (`Membership`) tied to `Shipit.github_teams` authorization — i.e., escalation into repository state and authorization data without possessing the victim org's webhook secret.

### Likelihood Explanation
Requires only that the Shipit instance be configured for multiple GitHub organizations and that at least one has a missing/blank `webhook_secret` (or the attacker otherwise knows that org's secret) — a configuration Shipit itself supports and does not warn against. No repository write access, session, or API token is needed; only an HTTP POST to the public webhooks endpoint.

### Recommendation
Verify that the organization derived from `repository.owner.login`/`organization.login` (used to pick the signing secret) matches the organization portion of `repository.full_name` before dispatching to handlers, and reject the request otherwise. Additionally, disallow/log a hard error when an onboarded organization has no `webhook_secret` configured, rather than silently skipping verification.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `weak-org` (no `webhook_secret`) and `victim-org` (has `stacks` and a real `webhook_secret`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "weak-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "weak-org")`; since it has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — no valid signature is required.
4. `create` dispatches to the push handler, which computes `repository_name` from `full_name` = `"victim-org/victim-repo"`, locates the real victim `Stack`, and enqueues `GithubSyncJob`, causing the victim stack to sync against attacker-influenced webhook data despite the request never being signed by `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
