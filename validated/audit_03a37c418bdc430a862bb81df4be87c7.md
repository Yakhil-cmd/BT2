### Title
Unchecked ERC20 `transfer()` success flag in `ERC20Transactor` allows real balance/`AssetsInHolding` credit mismatch, stranding real tokens in the `TransfersCheckingAccount` - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move ERC20 tokens between a user and a shared `TransfersCheckingAccount` by calling the Solidity `IERC20::transfer` ABI through `pallet_revive::bare_call`, and treat the operation as fully successful as soon as the call does not revert and the ABI-decoded return value is `true` [1](#0-0) . Exactly like the Aave report's `AAVE.withdraw` call, the code assumes the boolean/`amount` requested was moved 1:1 into (or out of) the checking account, without verifying the checking account's real balance delta. Because ERC20 `transfer` only returns a boolean (never the actual amount moved), and non-standard tokens (fee-on-transfer/deflationary) are freely usable here (any `AccountKey20` address is accepted, confirmed by the `non_existent_erc20_will_error` / `smart_contract_not_erc20_will_error` tests exercising arbitrary EVM addresses), the internal XCM `AssetsInHolding` credit created via `Erc20Credit(amount)` can diverge from the real token balance actually held by `TransfersCheckingAccount`.

### Finding Description
`withdraw_asset_with_surplus` calls `transfer(checking_address, amount)` from the user and, on `true`, immediately constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` [2](#0-1) . `Erc20Credit` is a bare in-memory counter with no `Drop`/reversal logic tied to the real ERC20 balance [3](#0-2) . If the token contract is fee-on-transfer (or otherwise moves less than `amount` while still returning `true`), the checking account's real balance increases by less than `amount`, but the runtime's XCM holding register believes it has a full `amount` credit.

When that credit is later spent via `deposit_asset_with_surplus`, the code again calls `transfer(beneficiary, amount)` from the checking account using the amount recorded in the (now incorrect) `AssetsInHolding`, not the real balance actually available [4](#0-3) . Since the checking account's real balance is short by the fee taken on the way in, this outbound `transfer` call reverts (insufficient real ERC20 balance), and `deposit_asset_with_surplus` returns `Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))`. The real tokens that *did* arrive at `TransfersCheckingAccount` during the withdraw step remain there — there is no code path that reconciles or refunds the checking account's actual balance against the fictitious `Erc20Credit`, so those tokens become permanently stuck in `TransfersCheckingAccount`, exactly mirroring the Aave report's "stuck aToken in intermediary contract" pattern, but here with `TransfersCheckingAccount` as the intermediary and a fee-on-transfer/non-standard ERC20 as the "underlying asset."

This is reachable by any unprivileged, signed user: `pallet_xcm::execute` is a normal signed extrinsic, and the test suite confirms `ERC20Transactor` accepts arbitrary `AccountKey20` contract addresses supplied by the caller for `withdraw_asset`/`deposit_asset` (e.g. `withdraw_and_deposit_erc20s`, `non_existent_erc20_will_error`) with no allowlist/registration step visible in the transactor itself [5](#0-4) . Anyone can permissionlessly deploy an ERC20-like contract (via `pallet_revive`) with fee-on-transfer semantics and immediately drive this code path through a local `PolkadotXcm::execute` program.

### Impact Explanation
The impact is fund lock/loss of the user's own tokens (their real ERC20 balance gets stranded in `TransfersCheckingAccount` with no recovery path once the mismatched `deposit_asset` step reverts), and, over repeated use by multiple holders of the same fee-charging token, a progressive divergence between the checking account's real balance and the sum of outstanding `AssetsInHolding` credits the runtime believes are backed by it. This does not directly let an attacker steal a third party's already-settled balance (the underlying ERC20 contract's own balance checks still gate the final transfer), so this is a fund-freezing/accounting-integrity issue rather than a direct unauthorized-mint. Given the Wise-Lending precedent was rated Medium for an analogous "unchecked return value → stuck residual tokens in the wrapper contract" pattern, this should also be classified Medium.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to use (or deploy) an ERC20 contract with non-1:1 transfer semantics (fee-on-transfer/deflationary), which is a common, well-known token pattern, not a contrived edge case. No privileged role, governance, or third-party cooperation is needed — a signed user deploying a contract via `pallet_revive` and calling `PolkadotXcm::execute` is sufficient to trigger the flawed accounting path.

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus`, snapshot the checking account's real ERC20 balance before and after the `transfer` call and use the **actual delta** (not the requested `amount`) to construct `Erc20Credit`. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's actual balance increase matches what was debited from holding, and on partial success, credit back any residual amount to the source's `AssetsInHolding` rather than silently leaving it in `TransfersCheckingAccount`. This mirrors the recommended balance-before/balance-after check pattern from the original Aave finding.

### Proof of Concept
No PoC was executed. Reasoning is based on static analysis of `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and its usage/tests in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`. A concrete integration test would: (1) deploy a fee-on-transfer ERC20 contract via `pallet_revive` `bare_instantiate`, (2) fund an account with it, (3) execute an XCM program via `PolkadotXcm::execute` doing `withdraw_asset` followed by `deposit_asset` of the same nominal amount for that token, and (4) assert that `deposit_asset` fails while `TransfersCheckingAccount`'s real ERC20 balance (queried via `Revive as fungibles::Inspect`) remains non-zero/stuck after the extrinsic completes. I was not able to execute this in the current session (no filesystem/terminal access), and I could not fully verify whether `ERC20Matcher`/`assets_common::ERC20Matcher` imposes any allowlist beyond matching on `AccountKey20` junctions — this should be confirmed by inspecting `cumulus/parachains/runtimes/assets/common/src/lib.rs` before finalizing severity.

struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}
