Based on further verification of `app/models/shipit/webhooks/handlers/handler.rb`, `push_handler.rb`, `status_handler.rb`, and `check_suite_handler.rb`, I found a concrete binding break matching the reported bug class.

### Title
Webhook signing-organization is never bound to the repository/commit actually mutated by status events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) is used to authenticate an inbound webhook based on `repository_owner`, a value read straight out of the untrusted JSON body. `Shipit::Webhooks::Handlers::StatusHandler#process`, however, never re-checks that field: it looks up commits purely by `sha` across the entire database and applies the status to whatever stack that commit belongs to, with zero reference to `repository`/`organization`. The GitHub organization that "authenticates" the request is not the same entity as the repository whose commit history gets written, exactly mirroring the sherlock finding's pattern of computing a privilege (duration multiplier / here: which secret validates the request) from one entity while applying the effect to another (receiver's lock / here: an unrelated repository's commit).

### Finding Description
`verify_signature` computes the signing org from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks the `webhook_secret` for that specific organization (Shipit explicitly supports hosting multiple, independently configured GitHub orgs/Apps, each with its own `webhook_secret`, per `docs/setup.md` and `config/secrets.development.example.yml`). Once the HMAC checks out for *that* org's secret, the raw JSON body is dispatched unchanged to the handlers: [3](#0-2) 

`StatusHandler#process` then resolves the target purely by `sha`, with no scoping to the repository/organization that authenticated the request: [4](#0-3) 

Compare this with `Handler#stacks`, which other handlers (`PushHandler`, `CheckSuiteHandler`) do use to scope to a specific repository via `payload.dig('repository', 'full_name')`: [5](#0-4) 

`StatusHandler` bypasses that scoping entirely. Since `sha` is a globally-unique enough value but is matched with a simple `Commit.where(sha:)`, an attacker who legitimately owns/administers a Shipit-configured organization (org A, with its own valid `webhook_secret`) can sign a forged `status` webhook whose `repository.owner.login` is org A (so it authenticates), but whose `sha`/`state`/`context` target a commit that belongs to a completely different tracked repository/organization (org B) hosted on the same Shipit instance.

**Equality that should hold but doesn't:** `organization that produced a valid signature == organization whose commit/stack is mutated`. Before the attack: org A's secret only lets org A push status updates for org A's commits. After the crafted request: org A's secret lets the attacker write CI status onto any commit of any other tracked repository (org B, org C, ...) in the same Shipit deployment.

### Impact Explanation
`Commit#create_status_from_github!` persists a `Status` that feeds directly into `Commit#deployable?`/`required_statuses` checks used by `DeploysController`/`Stack#build_deploy` to gate deploys. By forging a `state: "success"` status for a required CI context on a victim repository's commit, an attacker who only controls a different, unrelated org onboarded to the same multi-tenant Shipit instance can make an otherwise-blocked commit appear deployable, enabling an unauthorized deploy of that commit on the victim's stack — a cross-repository write that crosses the organizational trust boundary the webhook signature is supposed to enforce.

### Likelihood Explanation
Any Shipit instance configured for more than one GitHub organization is directly enabled by the documented multi-org config format; the only requirement is administrative control of any one onboarded org's GitHub App (`webhook_secret`), not the victim org's. Because `StatusHandler` performs no per-repository scoping at all, exploitation requires only crafting one JSON POST with a valid HMAC for the attacker's own org and an arbitrary target `sha`.

### Recommendation
In `StatusHandler#process` (and any other handler that doesn't currently call `stacks`), scope the lookup to `stacks` (derived from `repository.full_name`) the same way `PushHandler`/`CheckSuiteHandler` do, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, so a commit is only updated if it belongs to a stack under the repository that the verified organization actually owns.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with distinct `webhook_secret`s (supported multi-org configuration).
2. As the administrator of `org-a` (attacker), compute `sha256`/`sha1` HMAC of a crafted JSON body using `org-a`'s `webhook_secret`.
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" },
  "sha": "<commit sha belonging to org-b/victim-repo>",
  "state": "success",
  "context": "required-ci-check"
}
```
4. `verify_signature` authenticates the request using `org-a`'s secret and succeeds.
5. `StatusHandler#process` finds the commit by `sha` regardless of repository and creates a passing `Status` on `org-b/victim-repo`'s commit, potentially unblocking a deploy that org-b never authorized.
