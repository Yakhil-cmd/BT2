### Title
Webhook signature verification is scoped to `repository.owner.login`, not to the `repository.full_name` that handlers actually act on — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App/secret to validate a webhook against using one field of the untrusted JSON body (`repository.owner.login` / `organization.login`), but every webhook handler subsequently resolves the target `Repository`/`Stack` using a *different* field of that same untrusted body (`repository.full_name`). The signature only proves "this body was signed with the secret associated with organization X"; it never proves that the `repository.full_name` embedded in the body actually belongs to organization X. This is the same class of bug as the Magnetar report: an address/field is verified for one purpose (approval/authorization) while a *different, unverified* field of the same payload is what actually gets acted upon.

### Finding Description
The signature check derives the verification key purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the JSON body the request itself provides (`params.dig('repository', 'owner', 'login')`). `Shipit.github(organization: repository_owner)` looks up the GitHub App/secret configured for that organization login, and `verify_webhook_signature` just checks the HMAC of the raw body against that secret.

Every default handler, however, resolves *which repository/stack to mutate* using a completely separate field of the same JSON body: [3](#0-2) [4](#0-3) [5](#0-4) 

Nothing ties `repository.owner.login` (the value that selected the verification secret) to `repository.full_name` (the value that selects the DB row that gets archived, unarchived, updated, or has statuses/checks refreshed). Because Shipit is designed to host many organizations/repositories behind one engine, and the secret lookup is keyed by organization login taken from the body itself, an actor who legitimately controls the webhook secret for *their own* onboarded organization can hand-craft a JSON body whose `repository.owner.login` is their own org (so the signature check passes with their own known secret) while `repository.full_name` names a completely different, victim organization's repository. The handler layer trusts `full_name` unconditionally and will operate on the victim's `Stack`/`Repository`.

This breaks the intended binding:
`organization that authenticated (repository.owner.login → secret used) == repository that gets written (repository.full_name → Repository.from_github_repo_name)`

### Impact Explanation
Any Shipit engine deployment that services more than one GitHub organization (the documented, supported multi-tenant use case — see the `secrets_double_github_app.yml`-style multi-app configuration) is affected. An attacker who is a legitimate admin of *any one* onboarded organization (i.e., knows/controls that org's webhook secret) can forge webhook events that are processed as if they came from GitHub for an *arbitrary other organization's* repository/stack, because the resolution of the acted-upon repository never re-checks the authenticated organization. Depending on which handler is targeted this reaches: forcing archive/unarchive of review stacks for repos the attacker does not own, injecting fabricated `check_suite`/`status` events (which the fixture-confirmed `RefreshCheckRunsJob`/`RefreshStatusesJob` pipeline consumes to mark commits deployable), or triggering `membership`-style handlers that create/delete `Team`/`Membership`/`User` records — directly escalating into `Shipit.github_teams`-based authorization for a stack the attacker never had rights to. Faking CI-green state to make a victim's commit satisfy `ci.require` and enter Shipit's merge queue/continuous-deployment path crosses into "unauthorized deploy or merge," which the rules classify as Critical impact.

### Likelihood Explanation
Low-to-Moderate. Exploitation requires the attacker to control at least one legitimate organization/webhook secret already onboarded onto the same Shipit instance as the victim — a realistic scenario for any Shipit deployment shared across multiple teams/orgs (the exact multi-org configuration the engine explicitly supports), but not available to a fully unauthenticated internet attacker with zero relationship to the Shipit instance.

### Recommendation
Do not derive the verification identity purely from attacker-suppliable payload fields, and do not let handlers trust `repository.full_name` unconditionally once the signature validity is established. After computing which organization's secret validated the signature, cross-check that `repository.full_name`'s owner segment (or the `Repository`/`Stack`'s configured GitHub organization) matches the organization whose secret actually verified the request; reject the webhook otherwise.

### Proof of Concept
1. Attacker is a legitimate admin of `attacker-org`, which is onboarded to the shared Shipit instance and therefore knows/controls the webhook secret Shipit associates with `attacker-org` (`Shipit.github(organization: 'attacker-org')`).
2. Attacker crafts a JSON body for, e.g., a `pull_request` `closed` event:
   ```json
   {
     "action": "closed",
     "number": 1,
     "pull_request": { ... },
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
3. Attacker computes `X-Hub-Signature` over this body using `attacker-org`'s known secret and POSTs it to `/webhooks` with `X-Github-Event: pull_request`.
4. `WebhooksController#verify_signature` looks up the secret for `repository_owner == "attacker-org"`, verifies successfully (it's the attacker's own valid secret), and the request proceeds.
5. `PullRequest::ClosedHandler` resolves `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` → `victim-org/victim-repo`, and calls `review_stack.archive!` on the victim's stack — an action the attacker was never authorized to perform on `victim-org`'s repository.

Note: the exact shared/per-org secret topology (`lib/shipit/github_app.rb`) could not be fully inspected in this pass; the finding is confirmed at the controller/handler level (the binding break between `repository.owner.login` and `repository.full_name`), but whether a given deployment configures per-organization distinct secrets or one shared App-level secret affects how easily an attacker obtains a usable secret — this should be verified against the live `secrets.yml`/`github_app.rb` configuration in a full session.
