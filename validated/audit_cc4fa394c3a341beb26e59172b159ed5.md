### Title
Missing `type` (ClientDataType) validation in WebAuthn assertion verification allows registration-ceremony signatures to be accepted as transaction-assertion signatures - (File: `types/src/transaction/webauthn.rs`)

### Summary
`PartialAuthenticatorAssertionResponse::verify` and `verify_arbitrary_msg` deserialize `CollectedClientData` from the attacker-supplied `client_data_json` but never inspect the `ty` field (`ClientDataType::Get` vs `ClientDataType::Create`). Only the `challenge` field is compared against the expected transaction digest, and the signature is checked over `authenticator_data || SHA-256(client_data_json)`. Because `ty` is part of the signed JSON blob but is never validated by the verifier, any client-data JSON with `"type":"webauthn.create"` (registration ceremony) that otherwise carries a matching challenge and a valid signature over that exact JSON blob will pass verification just as well as a proper `"type":"webauthn.get"` (assertion) blob would.

### Finding Description
The verification logic lives in `PartialAuthenticatorAssertionResponse::verify`: [1](#0-0) 

Step-by-step:
1. `collected_client_data` is parsed from `self.client_data_json` — this includes the `ty` field, but `ty` is never read anywhere in the function.
2. `challenge_bytes` is extracted and compared against the expected transaction digest via `verify_expected_challenge_from_message_matches_actual`.
3. `verification_data` (the actual signed payload) is `authenticator_data || SHA256(client_data_json)`.
4. The signature is verified over `verification_data` using the account's registered secp256r1 public key.

The identical pattern exists in `verify_arbitrary_msg`: [2](#0-1) 

Nowhere in this file, nor in `types/src/transaction/authenticator.rs` (the caller of this verification during `SignedTransaction::verify_signature`), is `collected_client_data.ty` checked against `ClientDataType::Get`. A grep across the whole indexed codebase for `ClientDataType::Get`/`ClientDataType::Create` usage found the enum referenced only in the test file `api/src/tests/webauthn_secp256r1_ecdsa.rs`, where the test helper hardcodes `ty: ClientDataType::Get` when constructing valid test data — it is never asserted or enforced by production code. [3](#0-2) 

This confirms the WebAuthn ceremony-type binding invariant (assertion vs. registration signature) is not enforced anywhere in the transaction-admission signature-verification path.

### Impact Explanation
Since the signature is computed over `authenticator_data || SHA256(client_data_json)`, a signature produced during a WebAuthn *registration* ceremony (`ClientDataType::Create`) with a client-data JSON whose `challenge` field happens to equal the SHA3-256 digest of a target `RawTransaction` would be accepted by `verify()`/`verify_arbitrary_msg()` as valid proof of transaction authorization, because the code path does not distinguish between the two ceremony types. This weakens the intended domain separation between registration and assertion ceremonies that WebAuthn's `type` field is designed to enforce, and could allow a differently-purposed signature to be repurposed/rebound as a transaction authenticator if such cross-ceremony signatures can be produced or obtained (e.g., via authenticators/tooling that allow signing arbitrary "create" client data with attacker-chosen `challenge`).

### Likelihood Explanation
Exploitability depends on whether an attacker can actually obtain a `ClientDataType::Create` signature whose `challenge` matches an intended raw-transaction digest — this typically requires control over, or the ability to make, a WebAuthn authenticator produce a "create" ceremony with an attacker/controller-chosen challenge and the correct account's private key material bound to the credential, i.e., the private key must still be the legitimate account's key. Since the underlying signing key material and signature scheme are unaffected, the missing check is a defense-in-depth / domain-separation gap rather than a key-recovery bug, but it is a genuine binding-invariant violation at the transaction-admission boundary as described in the exploit question.

### Recommendation
Add an explicit check in both `verify` and `verify_arbitrary_msg` in `types/src/transaction/webauthn.rs` that `collected_client_data.ty == ClientDataType::Get`, returning an error otherwise, before performing challenge and signature verification.

### Proof of Concept
Using the existing test scaffolding in `api/src/tests/webauthn_secp256r1_ecdsa.rs`, construct `CollectedClientData` with `ty: ClientDataType::Create` instead of `ClientDataType::Get` (keeping the same valid `challenge` computed from the target `RawTransaction`), sign the resulting `client_data_json` normally, and call `PartialAuthenticatorAssertionResponse::verify(&raw_txn, &any_public_key)`: [1](#0-0) 
The absence of any `ty` check in this function means `verify()` will return `Ok(())` exactly as it does in the existing passing test `verify_partial_authenticator_assertion_response` — confirming that a `Create`-typed client-data blob is accepted identically to a `Get`-typed one. [4](#0-3)

    pub fn verify<T: Serialize + CryptoHash>(
        &self,
        message: &T,
        public_key: &AnyPublicKey,
    ) -> Result<()> {
        let collected_client_data: CollectedClientData =
            serde_json::from_slice(self.client_data_json.as_slice())?;
        let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())
            .map_err(|e| anyhow!("Failed to decode challenge bytes {:?}", e))?;

        // Check if expected challenge and actual challenge match. If there's no match, throw error
        verify_expected_challenge_from_message_matches_actual(message, challenge_bytes.as_slice())?;

        // Generates binary concatenation of authenticator_data and hash(client_data_json)
        let verification_data = generate_verification_data(
            self.authenticator_data.as_slice(),
            self.client_data_json.as_slice(),
        );

        // Note: We must call verify_arbitrary_msg instead of verify here. We do NOT want to
        // use verify because it BCS serializes and prefixes the message with a hash
        // via the signing_message function invocation
        match (&public_key, &self.signature) {
            (
                AnyPublicKey::Secp256r1Ecdsa { public_key },
                AssertionSignature::Secp256r1Ecdsa { signature },
            ) => signature.verify_arbitrary_msg(&verification_data, public_key),
            _ => Err(anyhow!(
                "WebAuthn verification failure, invalid key, signature pairing"
            )),
        }
    }
