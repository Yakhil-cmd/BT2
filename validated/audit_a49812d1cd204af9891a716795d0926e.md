### Title
Cross-organization commit status forgery via globally-scoped `StatusHandler` breaks the authenticated-organization ↔ written-repository binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The reported Uniswap issue is a bug class about a trust binding that is *checked for one thing* (WETH/token pair existence) but *acted on for another* (the actual swap execution), letting an attacker substitute a different, attacker-controlled state for the one that was implicitly assumed. The same class of bug exists in Shipit's webhook pipeline: the HMAC signature verification binds trust to "organization X sent this event," but `StatusHandler` writes to commit records without re-checking that the target commit actually belongs to a repository owned by that same organization X.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's webhook secret to validate the payload against, using the organization/repository owner embedded in the payload itself: [1](#0-0) [2](#0-1) 

Every Shipit organization installed as a separate GitHub App has its own `webhook_secret` [3](#0-2) 

So the invariant the signature check is *supposed* to establish is: "this event genuinely originated from organization X's GitHub App, therefore any writes it triggers should be confined to repositories owned by X." Most handlers preserve this invariant by scoping their side effects through `Handler#stacks`, which resolves the target `Repository` from the same `repository.full_name` field used to pick the verifying organization: [4](#0-3) 

`StatusHandler`, however, does not use `stacks`/`repository_name` at all. It looks up commits **globally by SHA**, with no repository or organization filter: [5](#0-4) 

Because `Commit#sha` is not guaranteed unique per-repository (and is fully attacker-known/guessable for public repos, or brute-forceable given git's use of the same object namespace conventions across many mirrored/forked repos), any organization that has a legitimately configured GitHub App on this Shipit instance can send a `status` webhook whose `repository.owner.login` is its own org (satisfying `verify_signature`), while its `sha`/`state`/`context` values target a commit belonging to a **completely different organization's stack**. `StatusHandler#process` will happily write/update that commit's status regardless of which organization actually authenticated the request.

This breaks exactly the binding called out in scope: *"an organization that authenticated versus the repository that is written."* Before an attacker's crafted request: `verified_org == written_repository.owner` holds for all handlers. After: for `StatusHandler`, `verified_org` can be any org with an app configured on the instance while `written_repository.owner` can be any other org's repository whose commit SHA is guessed/known.

### Impact Explanation
Commit statuses directly gate deployability in Shipit — `ci.require`/`ci.hide`/`ci.allow_failures` in `shipit.yml` determine whether a commit is safe to deploy, and CI status is the mechanism by which continuous delivery / manual deploy checklists decide a commit is green: [6](#0-5) 

By forging a `success` status with a `context` matching another stack's required CI check (e.g., `ci/tests`) against a target commit SHA in a completely unrelated, unaffiliated organization's repository, an attacker who only controls their own (also-configured) GitHub organization/app can make an otherwise-unvetted commit in someone else's repository appear CI-green in Shipit, enabling an **unauthorized deploy** of that commit. This matches the in-scope Critical impact bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires: (1) the attacker organization to already have a valid, distinctly-configured GitHub App/webhook secret on the same Shipit instance (a normal, unprivileged tenant of a multi-org Shipit deployment — not a privileged Shipit account, GITHUB_TOKEN, or API client token), and (2) knowledge of a target commit SHA in another org's repository, which is trivial since commit SHAs are public on GitHub (visible via PRs, pushes, the GitHub API, etc.). No repository write access, GitHub App private key, or Shipit session is required — only the ability to send a webhook to Shipit's public `/github/webhook` endpoint signed with the attacker's own legitimate (and separately configured) organization secret.

### Recommendation
`StatusHandler#process` should resolve and filter target commits through the same repository/organization scoping used elsewhere (`Handler#stacks`), e.g., by joining through `Commit -> Stack -> Repository` and requiring `repository.full_name == payload.dig('repository', 'full_name')` (the same value used for `verify_signature`), instead of matching bare `sha` across all repositories in the installation.

### Proof of Concept
1. Shipit instance hosts two orgs, `victim-org` and `attacker-org`, each with its own GitHub App/`webhook_secret` configured (as shown in `config/secrets.*.yml`).
2. Attacker controls `attacker-org`'s GitHub App and can therefore send correctly-HMAC-signed webhooks for `attacker-org`.
3. Attacker learns the SHA of an undeployed commit `abc123` on `victim-org/some-repo` that is currently failing/missing a required `ci/tests` status.
4. Attacker POSTs a `status` event to `/github/webhook` with:
   - `repository.owner.login = "attacker-org"` (so `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` validates against attacker-org's secret and succeeds),
   - `sha = "abc123"`, `state = "success"`, `context = "ci/tests"`.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches `Commit.where(sha: "abc123")` globally, finds the `victim-org` commit, and calls `create_status_from_github!`, marking it CI-green in Shipit even though the webhook was never sent by (or signed for) `victim-org`.
6. The victim commit can now pass Shipit's CI-required gate and be deployed by anyone with normal deploy privileges on the victim stack, achieving an unauthorized-deploy precondition purely through a cross-tenant signature/scope confusion.
