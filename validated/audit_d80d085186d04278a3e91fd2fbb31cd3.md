### Title
Webhook signature verification org selection is decoupled from the repository the handler writes/deploys to, allowing cross-tenant status/commit forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, which is read directly from the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), not from any value the signature itself certifies as authoritative: [1](#0-0) [2](#0-1) 

The equality that should hold is:
`organization whose webhook_secret authenticated the request == organization that owns the resource the handler subsequently mutates`

In a multi-tenant deployment (multiple GitHub orgs configured under `secrets.github`, each with its own `webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml`), an attacker who administers *their own* org's GitHub App (and therefore legitimately knows *their own* `webhook_secret`) can POST a crafted JSON body directly to the shared `/webhooks` endpoint. They set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` picks their own `GitHubApp` and the HMAC they compute with their own secret passes: [3](#0-2) 

But the actual handlers never re-check that `repository.owner.login` matches `repository.full_name`'s owner; they derive the repository purely from `repository.full_name` inside the same attacker-controlled JSON body: [4](#0-3) 

Worst case is `StatusHandler`, which doesn't even scope by repository — it matches by commit `sha` across the *entire* database: [5](#0-4) 

So an attacker who only controls one small, unrelated org/repo in a multi-tenant Shipit install can forge a `status` webhook, correctly signed with their own org's secret, but set `sha` to a commit that belongs to a *different, victim* org's stack. `Commit#create_status_from_github!` will create a CI status record for that foreign commit, driven entirely by attacker-supplied `state`/`context`/`description`. `PushHandler`/`CheckSuiteHandler` have the analogous issue via `repository.full_name`, letting the attacker trigger `stack.sync_github` or `schedule_refresh_check_runs!` on a stack/repository outside their own org, using only their own org's webhook credentials.

This is exactly the class of bug in the report generalized to Shipit's trust model: a value that gates a permission check (the org used to fetch the signing secret) is not the same value later dereferenced to decide what gets mutated (the repository/commit acted upon), and nothing enforces they stay in sync.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," directly matching an accepted analog category. Concretely: any org onboarded into a shared multi-org Shipit instance can forge CI status ("success") for commits belonging to a completely different tenant's repository/stack, and Shipit gates deploy eligibility on commit status. This can enable an unauthorized deploy of a commit that never actually passed CI in the victim's real repository — meeting the "unauthorized deploy" Critical-impact criterion. It also allows triggering `GithubSyncJob`/check-run refreshes against a foreign org's stack without any credential belonging to that org, which is a cross-repository write into state (`Commit`, `Status`) it should not be able to influence.

### Likelihood Explanation
Requires only that the attacker administers (or is a collaborator in) any single organization/repository configured in the same multi-tenant Shipit deployment (i.e., has legitimate access to their own org's `webhook_secret`, which is normal for anyone setting up their own GitHub App integration) — no Shipit session, `ApiClient` token, or victim-org credential is needed. The request is a plain, unauthenticated-to-Shipit HTTP POST with a correctly computed HMAC using a secret the attacker legitimately possesses. Only multi-org Shipit deployments (which the engine explicitly supports and documents, e.g. `secrets_double_github_app.yml`) are affected.

### Recommendation
After `verify_signature` succeeds, bind the verified organization to the rest of the request: re-derive the acting organization strictly from `repository_owner`/`organization` used for verification, and reject (or scope) any handler action whose target repository's owner does not match the verified organization. Concretely:
- In `Handler#repository_name`/`#stacks`, only resolve repositories/stacks that belong to the organization that authenticated the request (pass the verified organization through from the controller into `Handler.call`).
- In `StatusHandler`, restrict `Commit.where(sha: params.sha)` to commits whose stack's repository owner equals the verified organization, not a global lookup.
- Consider making the org/owner used for signature verification and the org used for all subsequent DB lookups the exact same trusted value, computed once and passed explicitly, rather than re-reading independent fields from the same untrusted JSON payload in different places.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately knows `attacker-org`'s `webhook_secret` (they administer that GitHub App).
3. Attacker finds/guesses a commit `sha` belonging to a stack under `victim-org` (e.g. via public GitHub commit history) and POSTs to `/webhooks`:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" },
  "organization": { "login": "attacker-org" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
with header `X-Github-Event: status` and `X-Hub-Signature` computed as `sha1=HMAC(attacker_webhook_secret, raw_body)`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and the signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit globally — and calls `create_status_from_github!`, creating a forged "success" CI status on the victim's commit despite the attacker never authenticating against `victim-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
