### Title
Cross-tenant status fan-out via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table instead of scoping to the stacks belonging to the reporting `repository.full_name`, unlike `PushHandler` and `CheckSuiteHandler` which correctly use `Handler#stacks`. Since `sha` is not globally unique (the unique index is `[sha, stack_id]`), a legitimate, correctly-signed GitHub status webhook from one repository can mutate commit status state on unrelated stacks/tenants that happen to share the same commit sha (e.g., a common template's initial commit).

### Finding Description
The broken binding: the set of commits mutated by `StatusHandler#process` should equal `{commits belonging to the stack(s) of repository.full_name}` (1 stack, as PushHandler enforces via `stacks.not_archived.where(branch:)`), but instead equals `Commit.where(sha: params.sha)` — every commit row in the database with that sha, across every stack/tenant [1](#0-0) .

`Handler#stacks` exists specifically to scope handler logic to the repository named in the payload: [2](#0-1)  and `PushHandler` correctly consults it: [3](#0-2) , as does `CheckSuiteHandler` (`stacks.where(branch:)` before touching commits) [4](#0-3) . `StatusHandler` skips this scoping entirely.

Schema confirms sha is not globally unique — only unique per `stack_id`, meaning multiple stacks legitimately can, and do, share identical shas (e.g. shared bootstrap/template commit): `add_index :commits, %i(sha stack_id), unique: true`.

Attack flow: `WebhooksController#create` verifies the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e., it authenticates that the payload genuinely originates from GitHub for the named `repository_owner`/repo [5](#0-4) . This check validates authenticity of the sender, not scope of effect. An attacker who owns a GitHub repository (unprivileged, no Shipit secrets needed) can legitimately post a real commit `status` via the GitHub API on their own repo. GitHub signs and delivers this webhook correctly for that repo/org, passing `verify_signature`. The payload's `sha` is attacker-controlled (any commit sha in their repo's history, including a widely-shared template/bootstrap commit). `StatusHandler#process` then finds and mutates **every** `Commit` row across the DB with that sha, regardless of which stack/repo it belongs to [6](#0-5) , calling `commit.create_status_from_github!(params)` on unrelated tenants' commits.

None of the existing guards prevent this: `verify_signature` only checks the sender is authentic for their own org; `drop_unhandled_event`/`check_if_ping` are unrelated; the `ExplicitParameters` schema only validates payload shape, not repository scope; there is no `require_permission!`/`stacks` check in `StatusHandler` at all.

### Impact Explanation
A single forged (but authentically-signed, self-owned) status webhook mutates `Status`/commit state for every unrelated stack sharing that commit sha, not just the reporting repository. `Commit#create_status_from_github!` (via `add_status`) can trigger continuous-delivery job scheduling (`schedule_continuous_delivery`), merge-request processing, and hook emission on stacks the attacker doesn't own and never authenticated against. This is a payload for one repository mutating another's stack/commit data — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). Blast radius scales with the number of stacks sharing the colliding sha (the scenario specifies 10, but any shared bootstrap/template sha across N tenants is affected), and is fully repeatable per request.

### Likelihood Explanation
Requires: (1) at least two `Shipit::Stack`s (belonging to different, unrelated GitHub repositories/organizations) that contain a `Commit` with an identical `sha` — realistic for repos scaffolded from the same template/boilerplate with an initial empty commit; (2) attacker owns any GitHub repository connected to the same Shipit instance and can set a commit status on a commit sha they control. No Shipit credentials, API tokens, or webhook secrets are needed — the attacker uses their own legitimately signed webhook. Feasibility is high for organizations that provision many repos from shared templates; the attack is trivially repeatable (attacker can keep sending status updates).

### Recommendation
Scope `StatusHandler#process` to the reporting repository's stacks, mirroring `PushHandler`/`CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the inherited `Handler#stacks` (which resolves `Repository.from_github_repo_name(repository_name)`), so only commits belonging to the stack(s) of the payload's `repository.full_name` are mutated.

### Proof of Concept
Minitest plan (e.g. `test/models/webhooks/handlers/status_handler_test.rb`):
```ruby
test "process only updates commits belonging to the reporting repository's stacks" do
  shared_sha = "6d9278037b872fd9a6690523e411ecb3aa181355"

  repo_a = Shipit::Repository.create!(owner: "acme", name: "app-a")
  repo_b = Shipit::Repository.create!(owner: "acme", name: "app-b")
  repo_c = Shipit::Repository.create!(owner: "acme", name: "app-c")

  stack_a = Shipit::Stack.create!(repository: repo_a, environment: "production", branch: "main")
  stack_b = Shipit::Stack.create!(repository: repo_b, environment: "production", branch: "main")
  stack_c = Shipit::Stack.create!(repository: repo_c, environment: "production", branch: "main")

  [stack_a, stack_b, stack_c].each do |stack|
    stack.commits.create!(sha: shared_sha, message: "template init", authored_at: Time.now, committed_at: Time.now)
  end

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/travis",
    "repository" => { "full_name" => "acme/app-a" },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Broken binding under test: mutated stacks == {stack_a} (the payload's repository), not all 3.
  assert_equal 1, Shipit::Status.where(state: "success", context: "ci/travis").count,
    "Only the reporting repository's stack should receive the status"
  refute stack_b.commits.find_by(sha: shared_sha).statuses.exists?(state: "success")
  refute stack_c.commits.find_by(sha: shared_sha).statuses.exists?(state: "success")
end
```
Given current code, `Shipit::Status.where(state: 'success').count` will be `3` instead of `1`, demonstrating the cross-tenant fan-out.
