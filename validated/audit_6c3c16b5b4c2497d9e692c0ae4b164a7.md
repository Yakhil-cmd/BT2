### Title
Unfunded excess-payment refund drains real pool custody without debiting the cash book - (File: contracts/pool/src/ops/repay.rs)

### Summary
The kernel bug class is a resource leak on an error path: resources acquired earlier are not released when an error is hit. The XOXNO Lending analog is a custody leak on a refund edge path: `ops::repay::apply` (and identically `ops::recapitalize::apply`) computes an "overpayment" from the *declared* inbound amount rather than the measured receipt, and refunds the excess via `transfer_out(payer, overpayment)` without debiting `cash` or passing `require_reserves`. An unprivileged caller who never transferred any tokens can declare a large repay on a market with zero debt; `current_debt_ceil` is zero so `resolve_repay` takes the full-close branch with `net_repay == 0`, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and the entire declared amount is paid out of the pool's real token custody while the cash book is untouched.

### Finding Description
- `contracts/pool/src/ops/repay.rs`: `repay` resolves the repay against declared `amount`; when the position has no debt, `net_repay == 0` and `overpayment == declared amount`. The overpayment is refunded with `transfer_out(payer, overpayment)` — a real token transfer — but the refund is derived from the declared argument, not from a measured balance increase, and it does not reduce the `cash` ledger.
- `contracts/controller/src/strategies/legs.rs:50-57` and `common/src/token.rs:16-31` show the intended pattern: `transfer_amount_measured` snapshots the pool balance before/after the inbound `transfer` so only a *real* receipt is credited. The pool's refund paths bypass that measurement.
- `contracts/pool/tests/flows.rs:3378-3483` (`assert_unfunded_refund_drained_custody`, `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`) and `flows.rs:3578-3611` (`test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`) pin the behavior: custody drains to zero, `cash` still reports the paid-out funds as present, and subsequent supplier withdrawals pass the pool's own `require_reserves`/`PoolInsolvent` guards only to fail inside the SAC transfer with balance error 10.

### Impact Explanation
Two impacts compose. First, direct theft: an unprivileged address calls `repay` (or `recapitalize`) on a debt-free market declaring `amount = pool balance`, pays nothing, and receives the entire custody as a "refund". Second, even when the declared amount is only partially unfunded, the cash book overstates custody afterward: `Cache::require_reserves` reads the book, so the market reports itself solvent while exits revert inside the token transfer — permanently freezing suppliers' funds for the drained market.

### Likelihood Explanation
Fully permissionless. `repay` and `recapitalize` are public pool/controller entrypoints; the attacker only needs to pick a hub market with no open borrows on their position (trivially satisfiable — any fresh account) and declare an amount up to the pool's token balance. No privileged role, no oracle manipulation, no racing required.

### Recommendation
Measure the inbound payment on every settlement leg: snapshot `pool` balance of the asset before pulling tokens and cap both `net_repay` and the refund at the measured receipt (`post - pre`), as `transfer_amount_measured` already does for controller-funded legs. Equivalently, never compute `overpayment` from the user-declared `amount` — compute it as `measured_receipt - net_repay` — and route the refund through the same `cash`-debiting path or explicitly assert the pool holds the unfunded excess.

### Proof of Concept
Already encoded in-repo:

```rust
// contracts/pool/tests/flows.rs:3590-3610
let custody_before = token.balance(&t.pool);
// Nothing transferred in, no debt to retire: the whole amount is "excess".
let credited = t
    .client()
    .repay(&payer, &t.ract(0, custody_before))
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
// payer ends with `custody_before`; pool balance == 0; cash book unchanged
assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
```

And the follow-on freeze (`flows.rs:3408-3483`): after custody is drained via `recapitalize(&hub, &payer, &custody)`, a legitimate supplier's `withdraw` clears `require_reserves` (book still shows cash) then fails in the SAC transfer with contract error 10, leaving suppliers unable to exit.
