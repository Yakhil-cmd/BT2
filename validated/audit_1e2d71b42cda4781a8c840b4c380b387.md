## Title
Webhook signature authenticates the sending GitHub App/organization, but every handler writes to a stack keyed off a different, unauthenticated payload field (`repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . Once the signature is accepted, `Shipit::Webhooks::Handlers::Handler#stacks` resolves the target `Stack` using a completely different field, `payload.dig('repository', 'full_name')` [3](#0-2) . These two fields are never cross-checked against each other.

## Finding Description
Shipit supports multiple GitHub App configurations, one per organization/domain, each with its own `webhook_secret` [4](#0-3) . `verify_webhook_signature` just does an HMAC compare against whichever secret was picked [5](#0-4) .

The binding that should hold is: *the organization whose secret validated the signature* == *the repository whose Stack is written to by the handler*. Instead:
- The secret-selection field is `repository.owner.login` (used only inside `WebhooksController#repository_owner`) [2](#0-1) .
- The write target is `repository.full_name`, read independently in `Handler#repository_name` and used to look up a `Repository`/`Stack` via `Repository.from_github_repo_name` [3](#0-2) .

An attacker who owns/administers their own GitHub App installation (and therefore legitimately knows its `webhook_secret`, which is attacker-supplied when they configure their own org in Shipit's multi-app secrets, e.g. as illustrated by the `OrgTwo` entry in the secrets file [6](#0-5) ) can craft an arbitrary webhook body where `repository.owner.login` equals their own org (so `verify_signature` picks their own known secret and the HMAC passes) while `repository.full_name` is set to an unrelated victim `owner/repo` that Shipit tracks under a different, victim-controlled GitHub App. Because the signature check and the stack-resolution logic consult different, non-cross-validated fields of the same unsigned-until-verified JSON body, the request is accepted as "authentically from OrgAttacker" but acted upon as if it concerned `victim-org/victim-repo`.

Concretely:
- `PushHandler#process` resolves stacks via `Handler#stacks` (i.e. `full_name`) and calls `stack.sync_github(expected_head_sha: params.after)` for any matching, non-archived stack on the matching branch [7](#0-6) , which enqueues a `GithubSyncJob` for the victim stack [8](#0-7) .
- `status` events create `Status` records on a matched commit for the "state"/"context"/"target_url" values taken straight from the payload, as shown by the controller test that verifies a `Status` gets created purely off `sha`/`state`/`context` fields merged with `repository_params` [9](#0-8) .

Since `ci.require`/`ci.blocking` gating and continuous delivery in Shipit rely on `Commit`/`Status` state to decide whether a deploy can auto-trigger, forging a `status` event for a victim's tracked commit (while passing signature verification under one's own, unrelated org) breaks the equality: **"organization whose credential authenticated the request" == "repository whose deployable/CI state was written."**

## Impact Explanation
This crosses the required boundary for a valid finding: an attacker with no privileges on the victim repository/stack, and no legitimate Shipit-issued credential for it, can cause writes (fake CI status, forced sync/resync) against a victim's Stack purely because Shipit conflates the field used for authentication (`owner.login`) with the field used for authorization/target-resolution (`full_name`). If continuous delivery is enabled and gated on required statuses, this can lead to an unauthorized deploy being triggered off a forged status — matching the "High: escalation... unauthorized deploy" impact bucket, since it is a real deploy/rollback trigger crossing an authentication boundary, not merely rate-limiting/DoS.

## Likelihood Explanation
The only prerequisite is that the Shipit installation is configured with more than one GitHub App/organization (a documented, supported configuration shown by the `secrets_double_github_app.yml` fixture) and that the attacker controls/administers one of those orgs' GitHub Apps (which is a normal, low-privilege setup step, not "repository write access" on the victim or possession of any Shipit-issued secret). No Shipit session, ApiClient token, or victim-org secret is required, so this satisfies the "unprivileged attacker" requirement.

## Recommendation
Bind the field used to select the verification secret to the field used to resolve the target stack: after verifying the signature, additionally verify that `repository.full_name`'s owner segment matches the `repository.owner.login`/organization actually used to pick the secret (or better, derive both from a single, verified value), rejecting the webhook if they diverge.

## Proof of Concept
1. Shipit is configured with two GitHub Apps: `OrgAttacker` (secret known to the attacker, who administers that App) and `OrgVictim` (secret unknown to the attacker, hosting a tracked `Stack` for `OrgVictim/app`).
2. Attacker crafts a `status` (or `push`) webhook JSON body with:
   - `repository.owner.login = "OrgAttacker"`
   - `repository.full_name = "OrgVictim/app"`
   - `sha` = a real commit SHA on the victim's tracked branch, `state = "success"`, `context` = the CI check context required by `OrgVictim/app`'s `shipit.yml`.
3. Attacker signs the raw JSON body with `OrgAttacker`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly, `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and successfully verifies the HMAC [1](#0-0) .
5. `StatusHandler` (via `Handler#stacks`) resolves the stack using `full_name = "OrgVictim/app"` and creates/updates a `Status` on the victim's commit as if GitHub itself reported the CI result [3](#0-2) .
6. If `OrgVictim/app`'s continuous delivery is enabled and gated on that status context, this forged status can trigger an automatic, unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
