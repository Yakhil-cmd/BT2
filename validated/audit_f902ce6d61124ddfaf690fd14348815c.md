### Title
Cross-tenant webhook signature bypass via organization/repository field mismatch — attacker's unsecured tenant org forges mutating events against any other tenant's repository - ([File: app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb], [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which tenant's `webhook_secret` to check against using `repository_owner`, a value read independently from `organization.login`/`repository.owner.login` in the attacker-supplied JSON body, while `UnlabeledHandler` (and sibling pull_request handlers) resolve the actual mutated repository from the unrelated `repository.full_name` field. Nothing binds these two fields together, so an attacker who controls any Shipit-configured org lacking a `webhook_secret` can supply that org's name for signature selection while pointing `repository.full_name` at a different, fully-secured tenant's repo, bypassing that tenant's signature entirely and mutating its stacks.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner == owner segment of repository.full_name`, but no validation enforces `params.dig('organization','login') == params.dig('repository','full_name').split('/').first`.

Path:
- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's config has no `webhook_secret` set: `return true unless webhook_secret` [3](#0-2) . So any signature header (or none) is accepted for that org.
- After passing `verify_signature`, `create` dispatches the full raw params to every registered handler for the event, including `UnlabeledHandler` [4](#0-3) .
- `UnlabeledHandler`'s param schema only requires `repository.full_name`; it never requires or cross-checks `repository.owner.login` against the value used for signature verification [5](#0-4) .
- `UnlabeledHandler#repository` resolves the real target using `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) , and `Repository.from_github_repo_name` does a plain DB lookup by the owner/name parsed from that string, with zero relation to which org's secret validated the request [7](#0-6) .
- `handle` then calls `stack.archive!` or `stack.unarchive!` on the resolved (victim) repository's review stack [8](#0-7) .

Attacker request: a raw HTTP POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` needed, and a JSON body such as:
```json
{
  "action": "unlabeled",
  "number": 1,
  "organization": {"login": "attacker-org"},
  "repository": {"full_name": "secured-org/secured-repo"},
  "pull_request": { "...": "valid schema fields, state: open, head.ref, labels, etc." },
  "sender": {"login": "attacker"}
}
```
Because `repository.owner.login` is omitted, `repository_owner` falls back to `organization.login` = `"attacker-org"`, an org the attacker controls that is registered in Shipit but has no `webhook_secret` configured yet. `verify_signature` then trivially passes for any signature. The event is then dispatched, and `UnlabeledHandler` resolves and mutates `secured-org/secured-repo`'s review stack — a repository belonging to an entirely different, securely-configured tenant — using data that was never authenticated by that tenant's secret.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is registered, not payload consistency [9](#0-8) ; `verify_signature`'s `GithubOrganizationUnknown` rescue only fires if the org name is entirely unknown to Shipit, not when it is known-but-unsecured [10](#0-9) ; and the `ExplicitParameters` schema for `UnlabeledHandler` never requires or compares `repository.owner.login`.

### Impact Explanation
An attacker who administers any Shipit-tenant org lacking a `webhook_secret` can archive, unarchive, or otherwise mutate review stacks under any other repository/tenant reachable by name via `Repository.from_github_repo_name`, without ever satisfying that victim tenant's own webhook signature. This is a payload from one org mutating another org's stack — explicitly a Critical-severity category in this audit's rubric. The blast radius is instance-wide: every tenant repository is reachable, and the attack is fully repeatable per request/repository by only changing `repository.full_name` in the JSON body.

### Likelihood Explanation
Preconditions: the Shipit instance must host at least one tenant org configured without a `webhook_secret` (explicitly named in the question as a realistic onboarding-in-progress state), and the attacker must control (own/administer) that org so they can freely POST to `/webhooks` claiming to be it. No GitHub secrets, session, or API token are required — only knowledge of the victim repository's `owner/name`, which is public information. Cost is a single crafted HTTP POST; the attack is trivially repeatable against any repository name.

### Recommendation
Bind signature verification to the same organization that owns the target repository referenced by the payload: derive `repository_owner` strictly from `repository.full_name`'s owner segment (or validate that `repository.owner.login`, `organization.login`, and the owner segment of `repository.full_name` are all identical) before selecting which `GitHubApp` config to verify against. Additionally, do not treat an org configured without a `webhook_secret` as automatically verified — require an explicit opt-in flag for "unsecured" orgs, and reject webhook payloads whose declared repository owner doesn't match the org actually authenticated.

### Proof of Concept
Minitest plan (functional test on `Shipit::WebhooksController`):
1. Configure two orgs in `Shipit.stubs(:github_app_config)` / credentials fixture: `secured-org` with a real `webhook_secret`, and `attacker-org` with no `webhook_secret`.
2. Create `shipit_repositories(:secured_repo)` with `owner: "secured-org", name: "secured-repo"`, provisioning behavior `allow_with_label`, and an existing non-archived review stack for PR #1.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body: `{"action"=>"unlabeled","number"=>1,"organization"=>{"login"=>"attacker-org"},"repository"=>{"full_name"=>"secured-org/secured-repo"}, "pull_request"=>{...state: "open", labels: []...}, "sender"=>{"login"=>"attacker"}}`.
4. Assert response is `:ok` (equality check: `repository_owner` used for `verify_signature` == `"attacker-org"`, while the repository actually mutated == `"secured-org/secured-repo"` — these differ, proving the missing binding).
5. Assert `Shipit::Repository.find_by(owner: "secured-org", name: "secured-repo").review_stacks.find_by(pull_request_number: 1).archived?` is `true`, demonstrating the victim tenant's stack was mutated without its own `webhook_secret` ever being checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
