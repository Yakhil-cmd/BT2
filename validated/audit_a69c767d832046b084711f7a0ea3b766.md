### Title
Missing `is_spent=0` guard allows race-condition double-spend of private divisible asset outputs - (File: divisible_asset.js)

### Summary
`validateAndSaveDivisiblePrivatePayment()` in `divisible_asset.js` validates a private-payment input against the current DB state and then, in a separate step, unconditionally marks the referenced source output as spent, with no re-check that the output is still unspent at write time. This is the same check-then-use gap pattern as JLSEC-2026-212 (validate under one privilege/connection context, then act under another without re-verifying the checked condition).

### Finding Description
`validateDivisiblePrivatePayment()` performs the double-spend/serial checks (via `validation.validatePayment` → `checkInputDoubleSpend`) inside the caller-supplied `conn`, and only then does `validateAndSaveDivisiblePrivatePayment()`'s `ifOk` callback build and execute the write queries: [1](#0-0) 

```
if (type === "transfer"){
    conn.addQuery(arrQueries, 
        "UPDATE outputs SET is_spent=1 WHERE unit=? AND message_index=? AND output_index=?",
        [src_unit, src_message_index, src_output_index]);
}
```

Note the `UPDATE` has no `AND is_spent=0` condition, and the paired `INSERT INTO inputs` is a plain `INSERT` (not `INSERT OR IGNORE` / `INSERT IGNORE`) using `is_unique = bStable ? 1 : null`, so for unstable inputs `is_unique` is `NULL` and the `UNIQUE KEY bySrcOutput(src_unit, src_message_index, src_output_index, is_unique)` constraint does **not** prevent a second row with the same `(src_unit, src_message_index, src_output_index)` when `is_unique IS NULL` (SQL treats NULLs as distinct). [2](#0-1) 

This is exactly the "check" (`checkInputDoubleSpend` / spend-proof and output lookups) versus "use" (`INSERT`/`UPDATE` in `arrQueries`) gap. Each private payment chain is processed under its own connection/transaction, `db.takeConnectionFromPool` + `BEGIN`/`COMMIT`, in `private_payment.js`: [3](#0-2) 

`network.js`'s `handleSavedPrivatePayments()` explicitly iterates unhandled private payments **in parallel** (`async.each`, "handle different chains in parallel"), with only a coarse `saved_private` mutex around the whole batch, not around individual output rows: [4](#0-3) 

If the same source output is referenced by two concurrently-processed private payment deliveries of an unstable (`bStable=false`) divisible private-asset coin (e.g., resent via hub and directly, or via two paired devices/cosigners), both transactions can pass their independent `checkInputDoubleSpend` read (each sees a consistent but stale view, since neither has committed yet) and then both execute the unconditional `UPDATE outputs SET is_spent=1 ...` and `INSERT INTO inputs ...`, succeeding without constraint violation because `is_unique IS NULL` for both.

Contrast with `indivisible_asset.js`, which guards the analogous write with `AND is_spent=0` and uses `INSERT "+db.getIgnore()+"`, closing this exact race: [5](#0-4) [6](#0-5) 

### Impact Explanation
A private divisible-asset output can be recorded as spent twice by two different transfer chains before it becomes stable, letting a private-payment counterparty (or two of the user's own paired devices, or a hub relaying duplicate deliveries) get two independent, internally-consistent "spend" records for the same coin. Since the private layer stores the actual amounts/addresses/blinding that other nodes never see, this can desynchronize wallets' private ledgers, allow the same coin to be presented as unspent input to two different payments, and ultimately cause fund loss or duplication once one of the two spends resolves to stable while the other silently succeeded locally — a private double-spend / fund-loss condition for the counterparty holding the sat output.

### Likelihood Explanation
Requires the race window to be hit: two deliveries of a private-payment chain referencing the same unstable output processed on different DB connections at close to the same time. This is plausible via normal protocol paths — `handleOnlinePrivatePayment`/`handleSavedPrivatePayments` process private payments potentially received from the hub and directly from peers, or from multiple paired devices, and `handleSavedPrivatePayments` explicitly parallelizes processing of different chains. No privileged access is needed; a private-payment counterparty naturally triggers this by resending/duplicating delivery, which is a normal, unprivileged interaction in the private payment protocol.

### Recommendation
- Add `AND is_spent=0` to the `UPDATE outputs SET is_spent=1 ...` query in `divisible_asset.js`'s `validateAndSaveDivisiblePrivatePayment`, and check the affected row count; treat 0 rows affected as an error ("output already spent").
- Change the `INSERT INTO inputs` in the same function to use `INSERT "+db.getIgnore()+"` (as done in `indivisible_asset.js`) or otherwise make it idempotent/rejecting on conflict.
- Alternatively/additionally, serialize processing of private payment chains that reference the same `(src_unit, src_message_index, src_output_index)` via a mutex key, closing the check-then-use window between validation and write.

### Proof of Concept
1. Attacker/counterparty A holds an unstable (`is_stable=0`) private divisible-asset output O.
2. A crafts two valid private-payment chains, chain1 and chain2, both spending O as their input, sent to two different recipients (or the same recipient via two delivery paths — direct peer + hub, or via two paired devices).
3. Both chains arrive and get queued (`unhandled_private_payments`), then `handleSavedPrivatePayments()` processes them concurrently via `async.each`, each acquiring its own pooled connection and running its own `BEGIN...COMMIT` transaction in `private_payment.js`.
4. Within each transaction, `divisible_asset.js`'s `validateDivisiblePrivatePayment` → `checkInputDoubleSpend` queries the `inputs` table; since neither transaction has committed yet, both see no conflicting row and both validations pass.
5. Both transactions then execute `INSERT INTO inputs (...) VALUES (..., is_unique=NULL, ...)` (no conflict, since `is_unique IS NULL` bypasses the `bySrcOutput` unique constraint) and `UPDATE outputs SET is_spent=1 WHERE unit=... ` (no `is_spent=0` guard, so it always "succeeds" regardless of current state) and both commit successfully.
6. Result: output O is recorded as spent by two distinct transfer chains at the private layer, corrupting the private ledger and enabling fund loss/duplication for the involved parties.
