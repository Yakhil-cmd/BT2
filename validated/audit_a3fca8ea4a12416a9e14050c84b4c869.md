## Title
Attacker-Controlled Organization Selects the Webhook-Signature Verification Key While the Actual Written Object Is Taken From a Different, Unverified Payload Field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-GitHub-organization deployments, `WebhooksController#verify_signature` picks *which* `GitHubApp` (and therefore which `webhook_secret`) is used to authenticate an inbound webhook based on an **unverified** field of the request body (`repository.owner.login`, falling back to `organization.login`). The object actually mutated by the subsequent handler (e.g. the GitHub `team.id` / `organization.login` used by `MembershipHandler` to grant team membership) is read from a **separate** field of the *same still-unverified* body. Because these two fields are never required to agree, and because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization's `webhook_secret` is blank (a documented, valid configuration state), an attacker can pick an org with no configured secret purely to short-circuit verification, while steering the payload's `organization`/`team` fields at a *different, secured* organization whose `Team` id is one of `Shipit.github_teams`.

### Finding Description
`WebhooksController` runs `verify_signature` as a `before_action`, selecting the verification key like this: [1](#0-0) 

`repository_owner` is derived straight from the raw, not-yet-verified JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config only when the install is actually multi-organization (`github_default_organization` non-nil, i.e. top-level `github:` keys are org names, as documented under "Using Multiple Github Applications"): [3](#0-2) 

`GitHubApp#verify_webhook_signature` unconditionally passes when that organization's `webhook_secret` is blank — an explicitly documented, supported configuration (`webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (bypassed), the controller dispatches the *entire same body* to handlers: [6](#0-5) 

`MembershipHandler` never consults `repository_owner`/`repository.owner.login` at all — it trusts `organization.login` and `team.id` straight from the body to create/find a `Team` and grant membership: [7](#0-6) 

`User#authorized?` grants Shipit access purely based on membership in a `Team` whose `id` is in `Shipit.github_teams`: [8](#0-7) 

**The broken equality:** the code implicitly assumes
`organization used to select verification key (repository_owner)` == `organization/team actually written by the handler (params.organization.login / params.team.id)`.
Nothing enforces this. An attacker crafts a single JSON body containing:
- a `repository.owner.login` (or top-level `organization.login`, since `repository` is checked first) equal to some org configured in Shipit's multi-org `github:` block that has **no `webhook_secret` set** — this is only used by `verify_signature` to pick the (secret-less) app, causing signature check to trivially pass regardless of the `X-Hub-Signature` header sent;
- a `team.id` and `organization.login` matching a **real, secured** organization's GitHub team that is present in `Shipit.github_teams`;
- a `member.login` of the attacker's choice.

Because `MembershipHandler` ignores the `repository` key entirely and only reads `organization`/`team`/`member`, the attacker's forged, effectively-unsigned request causes Shipit to add an arbitrary GitHub login as a member of a security-relevant `Team`.

### Impact Explanation
This grants unauthenticated escalation into `Shipit.github_teams` authorization — explicitly listed as a valid High-impact analog. Once the attacker-chosen login is a `Team` member matching `Shipit.github_teams`, that login (or any account the attacker controls with that login) passes `User#authorized?` and gains full access to the Shipit application (viewing stacks/tasks, triggering deploys, rollbacks, locking stacks, etc.), all without ever presenting a valid GitHub-issued webhook signature for the targeted organization. The same organization-vs-payload divergence also lets an attacker inject spoofed `push`/`status`/`check_suite` events (via `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) that reference a `repository.full_name` unrelated to the org used to bypass verification, since those handlers likewise never cross-check `repository_owner`.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance running the documented multi-organization `github:` configuration (a supported, documented feature exercised by `test/dummy/config/secrets_double_github_app.yml`), and (2) at least one configured organization having no `webhook_secret` set, which is the documented default/optional state shown in `config/secrets.development.example.yml`. No GitHub App private key, `webhook_secret`, `api_clients_secret`, or existing Shipit session is required — only knowledge of a target Team's numeric GitHub `id` (obtainable via GitHub's public org/team APIs for orgs with visible teams) and the name of an org in the multi-org config lacking a secret.

### Recommendation
- Require `webhook_secret` to be present for every configured organization when multi-organization mode is used; refuse to boot or fail closed if any organization's `webhook_secret` is blank.
- After signature verification, cross-check that the organization used to select the verifying `GitHubApp` matches the organization/repository actually referenced by the event payload (e.g., verify `team.organization`/`repository.owner.login` equals `repository_owner` used for verification) before dispatching to handlers.
- Do not allow `GitHubApp#verify_webhook_signature` to silently return `true` when `webhook_secret` is unset in a multi-org context; only permit that behavior in single-app mode.

### Proof of Concept
Given a Shipit deployment with multi-org config where `OrgNoSecret` has no `webhook_secret` and `OrgTarget` is a real org whose Team (github id `123`) is listed in `Shipit.github_teams`:

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything

{
  "action": "added",
  "team": { "id": 123, "name": "Deployers", "slug": "deployers", "url": "https://x" },
  "organization": { "login": "OrgTarget" },
  "member": { "login": "attacker-login" },
  "repository": { "owner": { "login": "OrgNoSecret" } }
}
```

- `repository_owner` resolves to `"OrgNoSecret"` (`app/controllers/shipit/webhooks_controller.rb:59-62`), so `Shipit.github(organization: "OrgNoSecret")` is used and its `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`) since that org has no secret.
- `MembershipHandler` then processes the body using `params.organization.login == "OrgTarget"` and `params.team.id == 123`, adding `attacker-login` as a member of the real `Deployers` team (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`).
- If `attacker-login` subsequently authenticates via GitHub OAuth to Shipit, `User#authorized?` returns true because of this forged membership (`app/models/shipit/user.rb:80-82`), granting unauthorized application access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
