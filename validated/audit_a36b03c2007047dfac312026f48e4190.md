### Title
Stack-scoped API tokens can read build/deploy status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single `Stack` via `stack_id`, and this scope is meant to be the authorization boundary enforced by `Api::BaseController#stacks`/`#stack`. `Api::CCMenuController` re-implements its own `stack` finder that ignores this scoping and resolves `Stack.from_param!(params[:stack_id])` directly, so a token authorized only for stack A can be used to read CI/deploy status for any other stack in the instance, exactly analogous to the reported bug class where a resource keeps a stale/incorrect authorization binding instead of being re-checked against the current authority.

### Finding Description
`Api::BaseController` defines the intended authorization boundary for stack-scoped API clients: `stacks` restricts the queryable set of stacks to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` only within that restricted relation [1](#0-0) . This is the mechanism validated by the test "an api client scoped to a stack will only see that one stack" [5](#0-4) , and is backed by the `here_come_the_walrus` fixture, an `ApiClient` scoped to the `shipit` stack [6](#0-5) .

`Api::CCMenuController`, which serves build/deploy status (`lastBuildStatus`, `lastBuildLabel`, etc.) for CI dashboard tooling, overrides `stack` to bypass this scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [7](#0-6) 

The only permission gate applied is the coarse, non-record-scoped `require_permission :read, :stack` [3](#0-2) , which is enforced by `ApiClient#check_permissions!`, an operation/scope string check that has no notion of *which* stack it applies to [4](#0-3) . As a result, the equality that should hold — "stack a token authorizes" == "stack a token touches" — is broken for this one controller: any client possessing `read:stack` permission, even one deliberately scoped to a single low-sensitivity stack, can substitute any other `stack_id` in the URL and receive that stack's CI/lock/deploy status.

### Impact Explanation
This matches the High-impact category "unauthenticated read of stack state, task streams or deploy output" relative to the token's actual authorization: a stack-scoped `ApiClient` — the mechanism the engine specifically ships to let integrators mint narrowly-scoped tokens (see `CCMenuUrlController`, which creates read:stack-only clients for CCMenu use) — silently gains read access to every other stack's build/lock/deploy status. `CCMenuUrlController#client` itself demonstrates the intended narrow-scoping use case being defeated, since it mints a `read:stack` client for a specific stack but the resulting token can be replayed against arbitrary `stack_id`s [8](#0-7) .

### Likelihood Explanation
High. No special privileges beyond possession of any `read:stack`-scoped token are required, and the endpoint is designed to be reachable via a bare query-string token (no session, no basic auth headers needed) [9](#0-8) . Exploitation is a single GET request with a different `stack_id` value.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the scoped `stacks` relation from `Api::BaseController` instead of `Stack.from_param!`, mirroring `OutputsController` and other controllers that correctly inherit the scoped lookup, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Mint (or obtain) an `ApiClient` scoped to `stack_id: A` with only `read:stack` permission (the exact configuration `CCMenuUrlController` creates).
2. Using that client's `authentication_token`, request `GET /api/stacks/:other_stack_param/ccmenu.xml?token=<token>` where `:other_stack_param` refers to a different stack B that the token was never scoped to.
3. Observe that `Api::CCMenuController#show` returns stack B's build/lock/deploy status, even though `stacks.from_param!` in `Api::BaseController` would have raised `ActiveRecord::RecordNotFound` for the same request against any other in-scope controller such as `OutputsController`.
