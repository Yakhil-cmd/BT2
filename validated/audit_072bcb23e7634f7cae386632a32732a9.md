### Title
Race condition in main-chain stability promotion allows a node crash via unhandled exception - ([File: main_chain.js])

### Summary
`main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag()` returns its "stable" result to the caller **before** the code that actually performs the stability promotion (marking the MCI stable, re-reading fresh unit props, executing AA triggers) has run. The promotion work is deferred behind a separately-acquired `'handleJoint'` mutex lock and re-reads the on-chain state from scratch. Between the early result callback and the deferred promotion, the underlying DAG state can change (a normal consequence of other, concurrently arriving units), so the assumption the deferred code relies on (`objEarlierUnitProps.is_on_main_chain === true`) can become false. When that happens, the code `throw`s inside an `async` callback that nobody awaits, producing an unhandled rejection that is reachable purely by posting ordinary units.

Because `handleResult(bStable, true)` fires immediately, the calling `validate()` transaction is free to proceed and to release/relock the shared `'handleJoint'` mutex (this is exactly the deadlock-avoidance trick documented in the comment). This creates a window in which other units continue to be processed and the main chain can be rebuilt/reorganized before the deferred promotion body re-reads `objEarlierUnitProps` from a fresh connection. If, by the time the deferred code runs, `earlier_unit` is no longer `is_on_main_chain` (e.g., because a concurrently processed unit changed the best-parent chain), the code does a bare `throw Error(...)` inside an `async` function that is invoked as a plain callback — its returned promise is never awaited or wrapped, so the exception becomes an unhandled rejection/uncaught exception rather than being surfaced through any `ifError`/`ifTransientError` callback.

### Impact Explanation
An unhandled exception thrown from deep inside asynchronous DAG/stability-processing code is a process-level crash for a full/non-light node (Node.js terminates on unhandled promise rejections by default in the versions this project targets, and the surrounding code has no `.catch`/try-wrap at this call site). Because `determineIfStableInLaterUnitsAndUpdateStableMcFlag` is on the hot path of ordinary unit validation (`validateParents`), any full node that validates units is exposed. A crash of validating nodes prevents the network from confirming new units for as long as the affected nodes stay down — directly matching the "network unable to confirm new units" impact bucket, and is the closest in-scope analog to the CVE's "server crash ... triggered during session promotion."

### Likelihood Explanation
Reaching the vulnerable branch requires only ordinary, unprivileged unit posting: any user/peer can submit units whose parents make an unstable `last_ball_unit` "stable in view of parents" (a routine event on a busy DAG), which is exactly the trigger condition in `validateParents`. Causing the specific race (the main chain moving `earlier_unit` off `is_on_main_chain` between the initial determination and the deferred re-check) requires a concurrently arriving best-parent-changing unit — achievable by an attacker racing two unit submissions, or simply likely to occur under natural network conditions with competing branches near the tip. This makes the bug likely under normal load and reliably triggerable by a motivated poster who controls the timing of two units.

### Recommendation
- Do not deliver the "stable" result to the caller until the promotion has either been fully committed or is guaranteed not to fail; alternatively, deliver only a provisional signal and make callers treat it strictly as "will retry," never as a final outcome.
- Wrap the deferred promotion body (including `storage.readUnitProps`'s callback) in proper error handling so that a stale `is_on_main_chain` state produces a benign no-op/log instead of an uncaught `throw`, since the comment right above it ("the stability point moved while we were waiting for the lock") already acknowledges this is an expected race — the `is_on_main_chain` check should be handled the same defensive way as the MCI-moved check on the line just above it, not with a hard `throw`.
- Ensure any `async function` passed as a bare callback into non-promise-aware helpers (`storage.readUnitProps`, `storage.readLastStableMcIndex`) is either awaited or has its rejection explicitly caught, so a coding mistake here cannot crash the whole process.

### Proof of Concept
Conceptual/timing-based PoC (cannot be fully deterministic without live network control, but the mechanics are directly inferable from the code):
1. Attacker posts unit `U1` whose `last_ball_unit` (`X`) is not yet marked stable locally but is stable in view of `U1`'s parents. This drives `validation.js` into `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, X, U1.parent_units, false, cb)`.
2. Inside `main_chain.js`, `determineIfStableInLaterUnits` returns `bStable = true`; `handleResult(true, true)` fires immediately, releasing the outer `'handleJoint'` lock path in `validate()`/`network.js`.
3. Before the deferred code (`mutex.lock(['handleJoint'], ...)` → `storage.readUnitProps(db, X, ...)`) executes, attacker's second, concurrently-crafted unit `U2` (on an alternate branch with higher witnessed level) is processed and shifts the best-parent chain so that `X` is no longer `is_on_main_chain`.
4. When the deferred continuation for `U1` finally runs and reads fresh props for `X`, `objEarlierUnitProps.is_on_main_chain` is `false`, hitting `throw Error("earlier unit is no longer on main chain")` inside the un-awaited `async` callback, producing an unhandled rejection that crashes the node process.
