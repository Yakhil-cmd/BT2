### Title
Cross-organization webhook forgery when any configured GitHub organization omits `webhook_secret`, allowing unauthenticated writes to arbitrary stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's secret to use for HMAC verification from an **unauthenticated** field of the incoming JSON body (`repository.owner.login`/`organization.login`), while the event handlers (e.g. `PushHandler`) resolve which `Stack`/`Repository` to act on from a **different, independently-controlled** field of the same body (`repository.full_name`). These two fields are never bound to each other. If any organization configured in `Shipit.github` has no `webhook_secret` set (documented as "optional"), `verify_webhook_signature` unconditionally returns `true` for that organization, letting an attacker submit an entirely unsigned/forged payload that claims `repository.owner.login` = the secret-less org while `repository.full_name` names a stack belonging to any other (fully secured) organization.

### Finding Description
`verify_signature` computes the org to check against from attacker-supplied JSON, not from any verified identity: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success: [3](#0-2) 

Meanwhile, the actual side effect (which `Stack`s get synced/mutated) is resolved from a completely separate field, `repository.full_name`, with no re-check that it matches the organization used for signature verification: [4](#0-3) [5](#0-4) 

This breaks the equality that should hold: `organization verified by signature == organization owning the repository being written to`. Instead the engine enforces only `organization named in unverified JSON field A == org whose secret was used`, and separately `repository named in unverified JSON field B == repository/stack mutated`, with no link between A and B. Because Shipit explicitly supports multiple GitHub orgs sharing one instance (`Shipit.github_organizations`, `config.github.<org>.webhook_secret`) and documents the secret as optional per org (`docs/setup.md`), a real multi-tenant deployment can have one org configured without a secret while other orgs (and their stacks) are fully secured — yet the endpoint is shared (`/webhooks`), so a forged, unsigned request naming the unsecured org unlocks writes against any repository/stack known to the instance.

### Impact Explanation
An unauthenticated attacker (no Shipit session, no GitHub App key, no repository write access) can queue `GithubSyncJob` (via `push`), archive/unarchive review stacks, create teams/users, or otherwise trigger handler side effects (`PushHandler`, `PullRequest::*Handler`, `MembershipHandler`) against stacks that belong to organizations they have no relationship to, as long as the deployment has at least one org without a `webhook_secret`. This is a cross-organization write achieved purely by exploiting the mismatch between the field used for authentication and the field used for authorization/targeting — matching the required "Critical: cross-repository writes" impact bar.

### Likelihood Explanation
Requires only that the operator has configured multi-org GitHub webhooks with at least one org left without a secret — an explicitly documented and supported configuration (`webhook_secret: # nil` in `config/secrets.development.example.yml`, "optional" in `docs/setup.md`). No credentials, tokens, or GitHub access are needed; the attacker only needs network access to `POST /webhooks` with a custom `X-Github-Event` header and JSON body.

### Recommendation
Bind the org used for signature verification to the org that will actually be acted upon: derive both `repository_owner` and the acting `Repository`/`Stack` from the same trust boundary, and reject events where the resolved repository's actual owner (looked up from Shipit's own `Repository` record, not from the payload) does not match the organization whose secret validated the signature. Alternatively, disallow (or loudly warn/deny by default) `webhook_secret` from being blank per organization, and additionally verify that `repository.full_name`'s owning org equals `repository_owner` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `secure-org` (has `webhook_secret: s3cr3t`) and `open-org` (no `webhook_secret` set).
2. Attacker sends, without any signature header:
```
POST /webhooks
X-Github-Event: push
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "full_name": "secure-org/victim-repo",
    "owner": { "login": "open-org" }
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "open-org")` and `verify_webhook_signature` returns `true` unconditionally because `open-org` has no `webhook_secret` (`lib/shipit/github_app.rb:76-77`).
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("secure-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `push_handler.rb:12-17`) and enqueues `GithubSyncJob` against the victim stack — despite the request never being validated against `secure-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
