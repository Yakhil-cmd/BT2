### Title
`MembershipHandler#process` binds `Team.github_id` lookup to the wrong organization, allowing cross-organization team-membership escalation - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `params.team.id` (the GitHub team ID) and, if found, does not verify that the team's stored `organization` matches the `organization.login` that was used to select the `webhook_secret` in `verify_signature`. Because GitHub team IDs are globally unique and Shipit supports multi-organization configs (`Shipit.github_app_config`/`Shipit.github(organization:)`), an attacker who controls a legitimate organization "A" configured in Shipit can sign a `membership` event as org A while naming org B's existing `Team.github_id`, causing `team.add_member(member)` to run against org B's team with an attacker-chosen `member.login`.

### Finding Description
The broken binding, stated as an equality that the code assumes but never checks: `params.organization.login` (verified via `webhook_secret` for that org in `WebhooksController#verify_signature` / `GitHubApp#verify_webhook_signature`) **must equal** the `organization` column of the `Team` record matched by `params.team.id` in `Shipit::Team`. No code enforces this.

Path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`). For a `membership` event, `repository` is optional in the payload, so `repository_owner` resolves to `params['organization']['login']`, i.e., whatever organization the attacker declares. [1](#0-0) [2](#0-1) 
- It then calls `Shipit.github(organization: repository_owner)` and verifies the signature using that organization's own `webhook_secret` (`GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`). If the attacker owns/administers organization "A" (installed the Shipit GitHub App on it, knows its `webhook_secret`), the signature check passes for a payload claiming `organization.login = "A"`, regardless of what `team.id` is inside the same payload. [3](#0-2) 
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... team.organization = params.organization.login ... }` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-42`). The block only executes on **creation**; if a `Team` with that `github_id` already exists (e.g., previously created for org B via `Team.find_or_create_by_handle` or a prior legitimate `membership` webhook from B), `find_or_create_by!` returns the existing record untouched — org B's team, organization column still `"B"`. [4](#0-3) 
- `process` then executes `team.add_member(member)` (for `action == 'added'`) where `member = User.find_or_create_by_login!(params.member.login)` — the attacker's own GitHub login, fully attacker-controlled. `Team#add_member` unconditionally appends the member (`app/models/shipit/team.rb:41-43`). [5](#0-4) 

Existing guards fail to close this gap:
- `verify_signature` authenticates *that the request came from some organization the signer controls*, not that the `team.id` referenced belongs to that organization.
- `ExplicitParameters` schema on `MembershipHandler` only validates types/presence of `action`, `team.id/name/slug/url`, `organization.login`, `member.login` — it never cross-checks `team.id` ownership. [6](#0-5) 
- `drop_unhandled_event` and `check_if_ping` are unrelated gates that don't help here.

Exploit flow: attacker administers org "A" with the Shipit GitHub App installed (so `Shipit.github_app_config('A')` exists and the attacker, as org owner, set/knows `webhook_secret` for A — this is legitimate self-configuration of their own org, not a stolen secret). They discover/know the `github_id` of a `Team` belonging to org "B" already present in `Shipit::Team` (e.g., a team referenced in `Shipit.github_teams` used for authorization). They POST to `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with org A's `webhook_secret`, and body: `{"action":"added","team":{"id":<B's github_id>,"name":...,"slug":...,"url":...},"organization":{"login":"A"},"member":{"login":"<attacker_github_login>"}}`. The signature check passes (org A's secret), `find_or_create_team!` returns B's pre-existing `Team` row, and `team.add_member(member)` inserts a `Membership` linking the attacker's `User` to B's `Team`.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization: `User#authorized?` (`app/models/shipit/user.rb:80-82`) grants access to any Shipit UI/controller gated by `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`) purely based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, with no re-verification against live GitHub team membership at authorization time. If org B's team is one of the teams configured in `Shipit.github_teams`, the attacker becomes an authorized Shipit user without ever being a real member of org B's GitHub team, gaining whatever privileges that grants (deploy/rollback/merge authorization elsewhere in the app that gates on `authorized?` or team membership). This matches the "High: escalation into `Shipit.github_teams` authorization" category, and is repeatable against any `Team.github_id` known to the attacker as long as they control at least one org configured in the multi-org Shipit deployment.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured in the multi-organization mode (`secrets.github` keyed by org, per `Shipit.github_app_config`) — a single-org deployment (`github_default_organization` nil) does not exhibit this specific cross-org path since there'd be only one `webhook_secret`. (2) The attacker must control/administer at least one organization ("A") onboarded into that Shipit instance with the GitHub App installed (a legitimate, low-privilege action open to any org owner who onboards their own org). (3) The attacker must know or guess the target `Team`'s `github_id` (GitHub team IDs are discoverable via the GitHub API for teams the attacker can see, or via `Shipit::Team` slugs/handles surfaced by the app, e.g. `lib/tasks/teams.rake`). (4) A `Team` row for org B must already exist in the Shipit DB (created via prior legitimate sync or webhook). Given these, the attack is a single crafted, signed HTTP POST — no live GitHub interaction, no secrets beyond the attacker's own org's `webhook_secret`, and is fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after finding an existing `Team` by `github_id`, assert that `team.organization.casecmp(params.organization.login).zero?` before permitting `add_member`/`members.delete`; raise/log and reject the event on mismatch. More robust: scope the lookup by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login.downcase)`), and separately verify that `params.organization.login` matches the `repository_owner`/signing organization already established by the controller — i.e., enforce `team.organization == request-signing organization` as an explicit check inside the handler rather than relying implicitly on it.

### Proof of Concept
Minitest plan (webhooks controller test, no live GitHub):
1. Fixtures: create org "A" and org "B" GitHub app configs in test credentials (multi-org secrets), each with distinct `webhook_secret`.
2. Pre-create `team_b = Shipit::Team.create!(github_id: 999, organization: 'b', slug: 'secret-team', name: 'Secret Team', api_url: 'https://example.com')`.
3. Build payload: `{ action: 'added', team: { id: 999, name: 'Secret Team', slug: 'secret-team', url: 'https://example.com' }, organization: { login: 'a' }, member: { login: 'attacker' } }.to_json`.
4. Compute `signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', org_a_webhook_secret, payload)`.
5. `@request.headers['X-Github-Event'] = 'membership'; @request.headers['X-Hub-Signature'] = signature`.
6. `post :create, body: payload, as: :json` → `assert_response :ok`.
7. Assert the binding is violated: `assert_equal 'a', ??? ` — before: expected equality `team_b.organization == 'a'` is false (`team_b.organization == 'b'`); after: `assert team_b.reload.members.exists?(login: 'attacker')` is true — i.e., org A's signed request successfully added a member to org B's team, proving `params.organization.login` (the verified/signing org) diverged from `Team#organization` (the team's true owning org) yet the write still occurred.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
