## Analog Found

### Title
Auto-destroy asset outputs are still counted as spendable AA balance, letting an AMM/swap AA overvalue its reserve — ([File: aa_composer.js])

### Summary
The Defibox report describes a swap contract that trusted an incompatible token's reported balance/behavior, causing the pool's internal accounting to diverge from what could actually be redeemed, draining ~4,863 EOS. In `ocore`, an AA-based swap/AMM contract is exposed to a structurally identical class of bug: the asset property `auto_destroy` makes outputs sent to the asset's definer address permanently unspendable, but the AA balance bookkeeping used by `balance[asset]` in oscript formulas does not subtract these destroyed amounts — it keeps counting them as live, spendable balance.

### Finding Description
When an asset is defined with `auto_destroy: true`, any output sent to the asset's `definer_address` is intentionally treated as destroyed/burned: `pickDivisibleCoinsForAmount` and `pickIndivisibleCoinsForAmount` explicitly remove the definer's own address from the list of spendable addresses [1](#0-0) , and the AA's own output-selection logic in `sendUnit` explicitly returns an empty output set for such outputs when the AA is the definer: [2](#0-1) [3](#0-2) 
The protocol validator also independently rejects any attempt to spend such destroyed outputs: [4](#0-3) 

However, the AA balance-accounting functions that feed the `balance[asset]` oscript getter never apply this exclusion. `updateInitialAABalances` unconditionally adds every `trigger.outputs[asset]` amount to the AA's tracked balance: [5](#0-4) . Likewise `updateFinalAABalances` sums every payment output addressed to the AA, including auto-destroyed ones, into `assocDeltas` and then into `objValidationState.assocBalances`: [6](#0-5) .

This means `balance[asset]` (and hence `assocBalances`/`aa_balances`) reports a value that includes coins the AA can never actually move again, while the output-selection code (`readStableOutputs`/`readUnstableOutputsSentByAAs`) silently pretends those coins don't exist when constructing outgoing payments. The two subsystems are incompatible: one assumes "balance == what I can spend", the other enforces "definer's auto-destroy outputs are not spendable."

### Impact Explanation
Any AMM/exchange-style AA that prices trades using `balance[asset]` — exactly the pattern used in ocore's own reference implementation, `test/samples/uniswap_like_market_maker.oscript`, e.g. `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` and the constant-product formula `$p = $asset_balance * $bytes_balance` [7](#0-6)  — will compute exchange rates and payouts from an inflated reserve figure whenever the traded/share asset it is the definer of has `auto_destroy: true`. An attacker who sends that asset back to the AA inflates the reported reserve without contributing any spendable liquidity, skewing the invariant used to price the other side of the swap (e.g., base bytes or a second asset) and allowing extraction of real, spendable funds in exchange for a smaller real contribution — a direct fund-loss/insolvency analog to the Defibox/EMOON pool imbalance, and reachable purely by an unprivileged trigger sender interacting with a deployed AA.

### Likelihood Explanation
This requires an AA to both act as the definer of an asset with `auto_destroy: true` and price trades based on `balance[asset]` for that asset — a plausible, even encouraged, combination for share-token/LP-token designs (auto_destroy is a natural way to "burn" returned LP shares), and the pattern of using `balance[asset]` directly for pricing is exactly what ocore's own sample AMM code demonstrates. No special privileges are needed by the attacker; they simply need to send the auto-destroy asset to the AA, which is standard, permitted interaction. The gap exists at the protocol/AA-composer level (`aa_composer.js`), not in any single dapp's logic, so every AA reusing this documented pattern inherits the flaw.

### Recommendation
Make `balance[asset]` semantics consistent with actual spendability: in `updateInitialAABalances` and `updateFinalAABalances` in `aa_composer.js`, when the target asset has `auto_destroy === true` and `definer_address === address` (the AA itself), exclude those output amounts from the balance delta the same way `readStableOutputs`/`readUnstableOutputsSentByAAs` exclude them from spend selection, or expose a separate "spendable balance" distinct from "gross received balance" so AA authors relying on `balance[asset]` for pricing/invariant logic are not silently given an inflated figure. At minimum, document this discrepancy prominently and update the sample AMM (`uniswap_like_market_maker.oscript`) with an explicit warning/guard against using `balance[asset]` for auto-destroy assets it defines.

### Proof of Concept
1. Deploy an AMM-style AA (as in `test/samples/uniswap_like_market_maker.oscript`) that defines a share asset with `auto_destroy: true`, `is_transferrable: true`, and prices trades of another asset against bytes using `balance[$asset]`/`balance[base]` in its constant-product formula.
2. An attacker sends a payment of the auto_destroy asset back to the AA (which is that asset's `definer_address`).
3. Per `aa_composer.js:474-490` and `aa_composer.js:556-582`, `assocBalances[address][asset]` (and thus `balance[asset]` visible to oscript) increases by the received amount, even though `aa_composer.js:1140-1172` guarantees this exact amount can never be selected as a spendable input by the AA again.
4. The attacker then performs a swap in the opposite direction; the AA computes the new price/payout using the inflated `balance[asset]`, permitting the attacker to withdraw more real (spendable) reserve (e.g., bytes) than the true, spendable liquidity justifies, mirroring the Defibox incident where a token's non-standard balance semantics broke the swap contract's invariant and caused a shortfall the operator had to cover from reserves.
