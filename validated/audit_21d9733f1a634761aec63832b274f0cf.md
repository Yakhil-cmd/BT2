Confirmed root cause: this is a genuine cross-organization signature/repository binding break in the multi-org GitHub App configuration.

### Title
Webhook secret selection uses `repository.owner.login` while the acted-upon repository is resolved from `repository.full_name`, allowing an org with no/weak `webhook_secret` to forge events for a repository owned by a different, protected organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to verify the HMAC against based on `repository.owner.login` extracted from the (unverified at this point) JSON body [1](#0-0) , [2](#0-1) . But the value actually used to locate the `Repository`/`Stack` that the event handlers act on is `repository.full_name`, a separate, independently-controlled field of the same payload [3](#0-2) [4](#0-3) .

### Finding Description
In a multi-organization deployment (`Shipit.github_organizations` with several GitHub Apps, each with its own optional `webhook_secret`, as documented) [5](#0-4) , `Shipit::GitHubApp#verify_webhook_signature` **short-circuits to `true` when no `webhook_secret` is configured for that organization**:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [6](#0-5) 

The organization whose secret (or lack thereof) is used is derived from `repository.owner.login` in the raw body, read before any signature check [1](#0-0) . The equality that must hold is:

`organization authenticated via repository.owner.login == organization actually written via repository.full_name`

An attacker who knows (or can enumerate) that some configured org, e.g. `orgA`, has no `webhook_secret` set can send a forged webhook body where:
- `repository.owner.login = "orgA"` (selects the app config with no secret → verification always passes), and
- `repository.full_name = "orgB/some-repo"` (the org whose stack the attacker actually wants to affect, protected by a real secret).

`Handler#stacks` resolves the target purely from `repository.full_name` via `Repository.from_github_repo_name` [3](#0-2) , with no cross-check against `repository.owner.login` or the org used for signature verification. Handlers like `PushHandler` then call `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to `orgB` [7](#0-6) , and other handlers (`status`, `check_suite`, `membership`, `pull_request`) act similarly using attacker-supplied data, all without the org that "authenticated" the request having any real relationship to the org being written.

### Impact Explanation
This breaks the trust boundary between "which org's secret validated this webhook" and "which org's stack/repository state gets mutated." It enables unauthenticated (with respect to `orgB`'s real secret) triggering of `GithubSyncJob`, commit status writes, check-suite refreshes, and membership/team mutations against repositories owned by an organization other than the one whose (absent) secret was checked — effectively an authentication bypass for webhook-driven state changes on `Stack` and `Commit` records for any organization in a multi-org deployment where at least one configured org lacks a `webhook_secret`.

### Likelihood Explanation
Requires a multi-org Shipit deployment (`github_default_organization` present, multiple orgs configured) where at least one org omits `webhook_secret` — explicitly documented as optional in `docs/setup.md` ("Webhook secret (optional)") [8](#0-7)  and in the example secrets files [9](#0-8) . No credentials, session, or `ApiClient` token are needed — only an HTTP POST to `/webhooks` with a crafted JSON body and any (or no) matching `X-Hub-Signature` header, since verification for the unsecured org always returns `true`.

### Recommendation
Bind signature verification and target resolution to the same field: verify using the organization derived from `repository.full_name` (the same value used by `Repository.from_github_repo_name`) rather than `repository.owner.login`, and/or reject webhooks whose `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, consider making `webhook_secret` mandatory (or refusing verification, not silently passing) for any organization configured in a multi-org setup, since a missing secret currently disables authentication for that org's identity entirely.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `orgA` (no `webhook_secret`) and `orgB` (`webhook_secret: real-secret`), with `orgB/target-repo` tracked as a Shipit stack.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "attacker-controlled-sha",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")` → `webhook_secret` is blank → `verify_webhook_signature` returns `true` unconditionally, regardless of the (even absent/garbage) `X-Hub-Signature` header [10](#0-9) .
4. `PushHandler#process` resolves `Repository.from_github_repo_name("orgB/target-repo")` and enqueues `GithubSyncJob` against `orgB`'s real, secret-protected stack [7](#0-6) , achieving an unauthenticated state mutation on an organization whose webhook secret was never checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
