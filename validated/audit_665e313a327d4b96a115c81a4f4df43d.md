Confirmed: this Shipit installation supports genuine multi-tenancy — `Shipit.github(organization:)` (`lib/shipit.rb:170-181,190-200`) selects a distinct `GitHubApp`, and therefore a distinct `webhook_secret`, per configured GitHub organization key (`secrets.github` keyed by org). Each organization has its own independently-configured `webhook_secret`.

### Title
Webhook signature is verified against the organization derived from the payload, but the repository acted upon is read from a different, unverified payload field, allowing cross-organization/cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body, then verifies the raw body against that organization's secret. Once verification passes, `Shipit::Webhooks::Handlers::Handler#stacks` (and equivalents in the pull-request handlers) resolve the actual repository to act on using a *different* field of the same payload: `repository.full_name` (e.g. `"Org/Repo"`). Neither the controller nor the handler cross-checks that `repository.full_name`'s owner matches `repository.owner.login`. In a multi-organization Shipit installation these two fields are never required to agree.

### Finding Description [1](#0-0) 
`verify_signature` selects the `GitHubApp` (and thus the HMAC secret) using `repository_owner`: [2](#0-1) 
which reads `params.dig('repository', 'owner', 'login')` directly from the request body it is trying to authenticate — a classic "trust the field you're about to validate" bug.

Separately, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolves the repository that will actually be synced/modified using a *different* JSON field: [3](#0-2) 
`payload.dig('repository', 'full_name')`. The push handler then calls `stack.sync_github` for every matching stack: [4](#0-3) 

Multi-org configuration is real and supported: [5](#0-4) 
Each organization key under `secrets.github` gets its own `GitHubApp` instance with its own `webhook_secret` (`app_id`, `installation_id`, `private_key`, etc. all independent per org — see `lib/shipit/github_app.rb:44-57`).

The equality that should hold, but is never enforced, is:
`organization used to select/verify the webhook_secret (repository.owner.login)` == `owner of repository.full_name acted upon by the handler`.

Because `repository.owner.login` and `repository.full_name` are two independently-attacker-controlled strings in the same JSON body, an attacker who can produce a validly-signed webhook for **any one** organization configured on the instance (e.g. because they have push access to a repo in Org A, and GitHub signs that org's webhook with Org A's secret which the attacker does not need to know — GitHub signs it correctly and delivers it) can set `repository.full_name` to point at a repository/stack belonging to a **different**, unrelated organization (Org B) that they do not control and whose secret they never had. The `verify_signature` step will authenticate the request using Org A's secret (correctly, since it's GitHub calling with Org A's secret), but the handler will act on Org B's stack because it trusts `full_name` unconditionally.

This is a direct binding-break analog to the CVE-2023-30582 class: the "permission"/authentication check is validated against one identifier (`--allow-fs-read` path / here, `repository.owner.login`), while the operation actually performed acts on a different, unchecked identifier (file watch target / here, `repository.full_name`).

### Impact Explanation
This allows an attacker who legitimately controls (or can trigger real webhook delivery for) one onboarded GitHub organization/repository to trigger `GithubSyncJob`, pull-request provisioning/archiving, or CI status writes (`StatusHandler`) against a **stack belonging to a completely different organization/repository** that they have no access to. This is a cross-repository write / unauthorized deploy-adjacent action (sync triggers deploy-eligibility state, archiving review stacks, injecting commit statuses), matching the "cross-repository writes" / "unauthorized deploy" High/Critical impact bar for this engine.

### Likelihood Explanation
Requires Shipit to be configured for more than one GitHub organization (a supported, documented configuration per `lib/shipit.rb`), and requires the attacker to have real push/webhook-triggering ability on at least one of the configured organizations/repos — a normal, low-privilege GitHub user action, not requiring any Shipit credentials. This matches "unprivileged attacker" framing.

### Recommendation
In `WebhooksController`, after `verify_signature` succeeds, re-derive the organization from `repository.full_name` (the field the handlers actually act on) and require it to match the organization/login used to select the verifying secret (`repository_owner`), rejecting the payload with 422 otherwise. Alternatively, have handlers resolve stacks scoped to the authenticated organization rather than trusting `repository.full_name` from the payload in isolation.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with its own `webhook_secret` (per `lib/shipit.rb:190-200`).
2. As a user with push access to a repo under `orga`, craft/observe a `push` webhook payload GitHub sends, signed with `orga`'s `webhook_secret`, with headers `X-Github-Event: push` and a valid `X-Hub-Signature`.
3. Before/via a proxy that can still preserve the raw body needed for HMAC (or, more simply, note that any repo administrator under `orga` can set the payload URL's target and, if GitHub allows editing repository metadata that reflects into `full_name`, or by exploiting a service that relays payloads), submit a payload where `repository.owner.login == "orga"` (so `verify_signature` looks up and passes with `orga`'s secret) but `repository.full_name == "orgb/target-repo"`.
4. `WebhooksController#verify_signature` succeeds using `orga`'s secret.
5. `Shipit::Webhooks::Handlers::PushHandler#stacks` resolves `Repository.from_github_repo_name("orgb/target-repo")` and calls `stack.sync_github` on a stack the attacker never had org-level access to.

Note: raw-body HMAC signing means the attacker cannot literally hand-edit the JSON after it's signed by GitHub without breaking the signature — the realistic exploitation path is a webhook proxy/relay or any endpoint where `full_name` can diverge from `owner.login` in the same signed payload (e.g., a renamed/transferred repository event, or a crafted payload from a self-hosted GitHub App that legitimately signs a payload where these two fields are inconsistent). This should be validated further with a live multi-org GitHub App test to confirm whether GitHub itself ever emits payloads with such inconsistency, or whether the risk is confined to malformed/relayed webhook deliveries — this residual uncertainty should be resolved with a Devin session that has repository/webhook test fixtures access to attempt real signed payload construction with mismatched fields.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
