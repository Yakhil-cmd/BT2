This is confirmed and directly analogous to the H-02 bug class. Multi-org Shipit deployments (documented in `docs/setup.md` "Using Multiple Github Applications") configure a distinct `webhook_secret` per organization, keyed by organization name. The `WebhooksController` verifies the signature using a secret selected by one field (`repository.owner.login` / `organization.login`), but every event `Handler` subsequently acts on a *different* field (`repository.full_name`) to resolve the actual `Stack`/`Repository` to mutate.

### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, enabling cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate `X-Hub-Signature` using `repository_owner`, computed from the payload's `repository.owner.login` (or `organization.login`) field: [1](#0-0) 

But every `Handler` subclass resolves the `Stack`/`Repository` to act on using a completely different, independently-attacker-controlled field, `repository.full_name`: [2](#0-1) 

Since Shipit explicitly supports "Using Multiple GitHub Applications" with per-organization `webhook_secret`s configured centrally by the operator (`docs/setup.md`), an actor who legitimately controls the webhook secret for **one** configured organization (e.g. an org admin who set up the GitHub App/webhook for their own org) can forge a signed payload where `repository.owner.login` equals their own organization (so the signature check passes against their own secret) while `repository.full_name` names a stack belonging to an entirely different, victim organization configured on the same Shipit instance. [3](#0-2) [4](#0-3) 

### Finding Description
The binding that should hold is: **organization that authenticated the request == organization/repository the request is written against**. Instead:

- `verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, then verifies `X-Hub-Signature` with that org's `webhook_secret`.
- Handlers (`PushHandler`, `StatusHandler`, `PullRequest::OpenedHandler`, `PullRequest::LabeledHandler`, etc.) never look at `repository.owner.login` at all — they resolve the target `Repository`/`Stack` purely via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. [5](#0-4) [6](#0-5) 

Because these two fields are never cross-checked, a payload can carry an `owner.login` that matches the signer's own org/secret while `full_name` points to any other org's repository tracked by the same Shipit instance.

### Impact Explanation
An attacker who administers/controls the GitHub App webhook configuration for one organization onboarded to a shared, multi-tenant Shipit instance can forge signed webhook deliveries "as if" they came from GitHub for a **different** organization's repositories:
- Forge `status` events to inject fabricated CI status (`Commit#create_status_from_github!`) on a victim's commits, which can flip `deployable?`/CI-gating checks used to allow deploys.
- Forge `push` events to force `GithubSyncJob` to sync/append specific commits for a victim stack (`Stack#sync_github`), controlling `expected_head_sha`.
- Forge `pull_request` events (`opened`/`labeled`/`reopened`) to provision, archive, or unarchive review stacks for a victim repository via `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter`.

Manipulating CI status/gating for another org's commits and triggering sync/deploy-adjacent state changes maps to the report's "unauthorized deploy" impact class, since it undermines the CI/status trust boundary Shipit relies on to gate deploys.

### Likelihood Explanation
Requires only that the target Shipit instance be configured with more than one GitHub organization (an explicitly documented, supported configuration), and that the attacker controls the webhook secret for any one of those orgs (which they set themselves when installing/configuring the app for their org). No repository write access, `ApiClient` token, or session on the victim org is needed — only knowledge of one's own org's already-known webhook secret, which is not privileged with respect to the victim organization.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), cross-check that the organization derived from `repository.full_name` (the one actually acted upon) matches `repository_owner` (the one whose secret validated the signature), rejecting the webhook (HTTP 422) on mismatch — analogous to requiring `tokenData.owner == inputParams.onBehalf` in the referenced BendDAO fix.

### Proof of Concept
1. Configure Shipit with two orgs, `AttackerOrg` and `VictimOrg`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-app schema); `VictimOrg/victim-repo` has a tracked `Stack`.
2. Attacker (who set up `AttackerOrg`'s webhook and thus knows its `webhook_secret`) crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(AttackerOrg_webhook_secret, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` computes `repository_owner == "AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and the signature verifies successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's real stack — despite the request never being authenticated for `VictimOrg`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
