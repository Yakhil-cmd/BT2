### Title
Webhook organization used for signature verification diverges from the repository the payload is allowed to mutate - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App configuration (and therefore the HMAC `webhook_secret`) to verify a payload against using `repository_owner`, which is read from the payload itself (`repository.owner.login`, falling back to `organization.login`). Every webhook handler, however, resolves which `Stack`/`Repository` to act on using a *different*, independently attacker-controlled field of the same payload: `repository.full_name`. Because these two fields are never cross-checked, a signature that is valid for organization A can be replayed with a `repository.full_name` pointing at a repository belonging to organization B, causing Shipit to accept and process a forged event against a stack it was never authorized to touch.

### Finding Description
Shipit supports hosting multiple GitHub organizations, each configured with its own GitHub App / `webhook_secret` (`Shipit.github_app_config`, `Shipit.github_organizations`, see also the multi-org test fixture `test/dummy/config/secrets_double_github_app.yml`) [1](#0-0) .

Incoming webhooks are authenticated like this:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The signature is thus checked against the `webhook_secret` belonging to whatever organization the *attacker puts in* `repository.owner.login`. If the attacker legitimately controls a GitHub organization that Shipit is also configured for (e.g. they have their own onboarded GitHub App installation, as multiple orgs are explicitly supported), they know or can obtain a valid signature for that organization's secret.

Once past `verify_signature`, every handler resolves the target `Repository`/`Stack` using a completely separate field of the same JSON body — `repository.full_name` — with no re-validation against `repository.owner.login`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` (and all `pull_request/*` handlers) call into this same `stacks`/`repository_name`/`params.repository.full_name` resolution path [4](#0-3) [5](#0-4) .

This breaks the binding: **organization authenticated (via `repository.owner.login`/`organization.login`) ≠ repository that is actually written (via `repository.full_name`)**. Nothing in `WebhooksController` or `Handler` enforces that `repository.full_name` starts with `repository_owner`.

### Impact Explanation
An attacker who controls (or is a legitimate, low-privilege member of) any single GitHub organization that is configured in Shipit's multi-tenant `github` secrets can forge webhook payloads that are correctly signed for their own organization, but whose `repository.full_name` targets a stack belonging to an entirely different, unrelated organization/repository already onboarded to Shipit. Depending on the event type this can:
- Trigger `GithubSyncJob`/`stack.sync_github` on a foreign stack (`PushHandler`) — spurious re-syncs, resource consumption, and state churn on a repository the attacker has no rights to.
- Drive pull-request lifecycle transitions (`opened`, `closed`, `labeled`, `reopened`) on foreign review stacks, causing archiving/unarchiving, provisioning, or deprovisioning of infrastructure for a repository/organization the attacker does not own.

This is a cross-repository/cross-organization write performed without the corresponding organization's authorization, matching the "cross-repository writes" / "unauthorized deploy" impact category in a multi-tenant Shipit deployment.

### Likelihood Explanation
Exploitability requires the attacker to have at least one legitimately configured (even low-privilege) GitHub organization/webhook-secret in the same Shipit instance — this is realistic for any Shipit deployment that hosts multiple organizations/tenants, which the engine explicitly supports (`Shipit.github_organizations`, `Shipit.github_app_config`). No repository write access, `ApiClient` token, or GitHub App private key for the *victim* organization is required — only control of one's own onboarded organization's webhook signing secret and the ability to send an HTTP POST to the shared `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` (or in the shared `Handler` base class), require that the `owner` embedded in `repository.full_name` match `repository_owner` (or `organization.login`) before dispatching to handlers, rejecting the request (422) on mismatch. Equivalently, `Handler#repository_name`/`#stacks` should be constructed with the already-authenticated organization scope rather than trusting an independent field of the unauthenticated-context payload.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (multi-org config as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sends it to the shared `POST /webhooks` endpoint with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and verifies successfully because the attacker legitimately holds that secret [6](#0-5) .
5. `PushHandler#process` then resolves `stacks` via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, matching real stacks belonging to `victim-org`, and enqueues `stack.sync_github(...)` for them despite the request never having been signed by `victim-org` [3](#0-2) [7](#0-6) .

Note: I was unable to fully read `app/models/shipit/webhooks/handlers/status_handler.rb` and `check_suite_handler.rb` before the tool budget ran out, so I cannot confirm with the same level of detail whether forged CI-status events could be used to influence `MergeRequest#merge!` (auto-merge) on a foreign stack; that would be a natural extension of this same root cause and is worth checking, but the push/pull_request handler path above is independently confirmed and sufficient to demonstrate the vulnerability.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
