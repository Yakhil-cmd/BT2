### Title
Remote unit poster can crash the whole ocore node via reachable `throw Error` in double-spend validation - (File: validation.js)

### Summary
`checkForDoublespends()` in `validation.js` contains `throw Error(...)` statements that are assumed to be "unreachable" invariants but are executed inside asynchronous DB-query callbacks during normal unit validation of attacker-supplied, unprivileged units. A synchronous `throw` inside such a callback is not caught by any surrounding `try/catch` and propagates to Node's `process.on('uncaughtException', ...)` handler in `network.js`, which deliberately **re-throws** to crash the process. This mirrors the CVE-2026-19401 bug class (a specially crafted, remotely-sent message reaching a crash point through a code path meant to be unreachable/defensive), except here it is reachable by any ordinary unit-posting client, not a privileged peer.

### Finding Description
`checkForDoublespends` iterates over DB rows describing conflicting spends of the same input/spend-proof and asserts invariants that "must" hold, e.g.: [1](#0-0) [2](#0-1) 

Both `throw Error("conflicting "+type+" spent from another address?")` and `throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit)` are reached from within `conn.query(...)` result callbacks — asynchronous code executed on the Node.js event loop, not inside the outer `try` blocks of `validation.js`'s `validate()` function.

`checkForDoublespends` is called by `validatePaymentInputsAndOutputs` for ordinary payment inputs [3](#0-2)  and by `validateSpendProofs` for spend-proof messages [4](#0-3) , both of which are exercised for every unit any unprivileged client posts to the network (`handleJoint` → `validation.validate` in `network.js`) [5](#0-4) .

When such a throw fires, it is not caught anywhere in the call chain because `db.query` callbacks execute outside the synchronous `try/catch` scope of `validate()`. It surfaces as an uncaught exception, and the top-level handler intentionally re-throws to terminate the process: [6](#0-5) 

This means a crafted double-spend scenario (an attacker posting two conflicting units for the same input/spend-proof under carefully arranged conditions so the "impossible" address-mismatch or unreachable-sequence condition is hit) causes the entire node process — not merely a subrequest handler — to crash, exactly analogous to how NSD's crafted-cookie-count message crashes a server child on an unexpected code path.

### Impact Explanation
A crash of the whole ocore node process is far more severe than the referenced NSD bug's "one debug child crashes" scenario, since ocore has no separate serve-child/restart-with-isolation model for this control-flow path in the same sense — a hit here brings down validation service and P2P handling for the entire process, denying transaction confirmation/service until restart. Repeated triggering from any client posting units is a network-availability denial (nodes unable to validate/confirm new units while repeatedly restarting), which matches the required high-severity impact category ("a network unable to confirm new units").

### Likelihood Explanation
Reaching the exact "impossible" states requires crafting specific double-spend conditions (e.g., two units from different authors both claiming to spend the same input/spend-proof, with database state arranged so the graph-inclusion/sequence checks disagree with the address-matching assumption). This is non-trivial to construct with certainty from the available code alone — the SQL `WHERE` filters already constrain matched rows to the same address in most call sites, so I could not fully confirm a concrete unauthenticated reachability path to the first `throw` without deeper trace of every caller's SQL predicates and the exact DB schema constraints (e.g., whether `address` is indexed together with the double-spend key in all cases). This should be treated as **moderate-to-uncertain likelihood** pending deeper verification of the SQL predicates in each `doubleSpendWhere` construction (payment inputs, spend proofs, headers-commission/witnessing inputs) to confirm whether the address column can realistically diverge from the querying unit's authors in a reachable scenario.

### Recommendation
- Replace the two "impossible" `throw Error(...)` statements in `checkForDoublespends` (validation.js:1673 and 1688) with graceful `cb2(unit_error)` / rejection paths that mark the unit invalid rather than crashing the process, since any invariant violation reachable from network input must be treated as untrusted input, not an internal bug.
- More broadly, audit all `throw Error(...)` calls reachable from within `conn.query` callbacks in `validation.js` (and similar asynchronous validation code) that are fed by attacker-controlled unit data, and either convert them to unit-error callbacks or ensure they cannot be reached by unprivileged, remotely-supplied data.
- Consider isolating per-connection/per-unit validation work so an unexpected exception invalidates only the offending unit's validation, rather than crashing the entire process via the global `uncaughtException` handler.

### Proof of Concept
A fully deterministic PoC could not be constructed from static analysis alone within the available tooling — it requires reproducing a specific database state (conflicting `inputs`/`spend_proofs` rows with mismatched `address` vs. the querying unit's `authors`, and a specific main-chain/sequence relationship) to drive execution into the `throw` branches of `checkForDoublespends`. This would need to be validated by a background Devin session with test-database and node-runtime access to confirm reachability empirically before treating this as a confirmed exploit (as opposed to a defense-in-depth/logic-invariant concern).
