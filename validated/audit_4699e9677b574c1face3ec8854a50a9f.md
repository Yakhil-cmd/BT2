Unvalidated P2P Staking Info Accepted During Fast Sync Persistently Corrupts Reward Distribution Database — (`File: datasync/downloader/queue.go`)

---

### Summary

During fast sync, the downloader fetches staking information from remote peers and writes it directly to the local database with no content validation. The `DeliverStakingInfos` validate callback is an explicit no-op (`// TODO-Kaia-Snapsync update validation logic`), while the equivalent callbacks for block bodies and receipts both verify cryptographic commitments against the block header. A malicious peer assigned a staking-info fetch request can respond with fabricated `P2PStakingInfo` — arbitrary node IDs, reward addresses, staking amounts, KEF/KIF treasury addresses — and the data is persisted unconditionally. For any chain still operating before the Kaia hardfork, `GetStakingInfo` reads the DB entry first and returns it without falling back to state, so the corrupted record is used for every subsequent reward distribution computation at the affected block interval.

**Root cause — no-op validate in `DeliverStakingInfos`**

`datasync/downloader/queue.go:953-966` defines the delivery handler for staking info:

```go

Compare with the receipt and body handlers, which both reject data that does not match the header commitment:

- `DeliverReceipts` (`queue.go:936-937`): `types.DeriveReceiptsRoot(...) != header.ReceiptHash → errInvalidReceipt`
- `DeliverBodies` (`queue.go:884-885`): `types.DeriveTransactionsRoot(...) != header.TxHash → errInvalidBody`

Staking info has no equivalent commitment field in the block header, so the validate hook is the only place content integrity could be enforced — and it is permanently bypassed.

**Write path — fabricated data reaches persistent storage**

After `DeliverStakingInfos` accepts the data, `commitFastSyncData` (`downloader.go:1881-1884`) and `commitPivotBlock` (`downloader.go:1896-1898`) call:

```

`PutStakingInfoToDB` (`kaiax/staking/impl/schema.go:73-74`) writes directly to the chain key-value store with no further checks.

If the DB entry exists (even if fabricated), it is returned immediately and cached. The state-based fallback is never reached.

**Attacker-controlled fields in `P2PStakingInfo`** (`kaiax/staking/p2p_staking_info.go:31-47`):

- `CouncilNodeAddrs` — validator node IDs
- `CouncilRewardAddrs` — addresses that receive staking rewards
- `CouncilStakingAmounts` — staking weights used for proposer selection and reward proportions

### Impact Explanation

For a chain operating before the Kaia hardfork (or a node fast-syncing historical pre-Kaia blocks):

1. **Reward address substitution**: An attacker sets `CouncilRewardAddrs` to attacker-controlled addresses. Every staking reward computed from the corrupted interval is credited to the wrong addresses. This is an unauthorized redirect of KAIA staking rewards.
2. **Treasury address substitution**: Replacing `KEFAddr`/`KIFAddr` redirects KEF/KIF treasury allocations.
3. **Staking weight manipulation**: Inflating or zeroing `CouncilStakingAmounts` distorts proposer selection probabilities and reward proportions across all validators for the affected interval.
4. **Persistent corruption**: The corrupted entry is cached and never re-derived from state for pre-Kaia blocks, so the damage persists across restarts until the DB entry is manually deleted.

For post-Kaia blocks, `GetStakingInfo` reads from state directly and the DB is not consulted, so the impact is limited to pre-Kaia intervals.

---

### Likelihood Explanation

During fast sync, the downloader assigns staking-info fetch requests to any idle peer in the connected peer set (`datasync/downloader/peer.go:226-244`). An attacker needs only to:

1. Run a Kaia node that passes the standard handshake (correct genesis hash, network ID, chain ID — all public).
2. Connect to a victim node that is performing fast sync.
3. Be assigned at least one staking-info fetch request (automatic, based on peer capacity).
4. Respond with a well-formed `P2PStakingInfo` carrying fabricated fields for the correct `BlockNum`.

No privileged keys, no governance access, and no majority-validator collusion are required. The attack is reachable from the default unprivileged attacker profile.

---

### Recommendation

1. **Derive a commitment**: Compute a deterministic hash of the canonical `StakingInfo` fields (node IDs, reward addresses, staking amounts, treasury addresses) at the source block and store it in the block header or a verifiable side-channel. Validate incoming P2P staking info against this commitment in `DeliverStakingInfos`, mirroring the receipt and body validation pattern.

2. **State re-derivation on import**: In `commitFastSyncData` and `commitPivotBlock`, after the state sync completes for the pivot block, re-derive staking info from the canonical state and overwrite any peer-supplied value before persisting.

3. **Remove the no-op TODO**: Replace `// TODO-Kaia-Snapsync update validation logic` with an actual check or, at minimum, refuse to persist peer-supplied staking info until a validation strategy is implemented.

4. **`SyncStakingInfo` recovery**: Verify the recovered staking info against the canonical state at `stakingInfo.BlockNum` before calling `PutStakingInfoToDB`.

func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
