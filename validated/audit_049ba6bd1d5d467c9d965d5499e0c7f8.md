### Title
Origin spoofing of `AllowFromEthereumFrontend` allows any AssetHub account to invoke `FrontendOrigin`-gated `snowbridge_pallet_system_v2` calls on BridgeHub - (File: system-parachains/bridge-hubs/bridge-hub-polkadot/src/bridge_to_ethereum_config.rs)

### Summary
`AllowFromEthereumFrontend::contains` (and thus `FrontendOrigin = EnsureXcm<AllowFromEthereumFrontend>`) only checks that the *final computed* XCM origin equals `(1, [Parachain(ASSET_HUB_ID), PalletInstance(SystemFrontendPalletInstance)])`. It does not verify that this origin was actually produced by `snowbridge_pallet_system_frontend`'s own internal message construction. Because AssetHub allows any signed account to call `pallet_xcm::send` with an arbitrary raw XCM program, and BridgeHub's `Barrier` unconditionally computes the effective origin from a leading `DescendOrigin` instruction without any additional authorization check, any signed AssetHub account can forge that exact origin and dispatch privileged `FrontendOrigin`-gated calls on `snowbridge_pallet_system_v2`.

### Finding Description
On BridgeHub, `AllowFromEthereumFrontend` is a pure location-equality check: [1](#0-0) 

It is used as `FrontendOrigin = EnsureXcm<AllowFromEthereumFrontend>` to gate privileged `snowbridge_pallet_system_v2` dispatchables (e.g. `register_token`, `add_tip`) that are supposed to be reachable only via the legitimate flow: `snowbridge_pallet_system_frontend` on AssetHub builds an XCM program that descends its own origin to `PalletLocation = SystemFrontendPalletLocation` before issuing a `Transact` to BridgeHub: [2](#0-1) 

The check, however, only inspects the *location value* delivered to `EnsureXcm`, and `EnsureXcm` accepts any `pallet_xcm::Origin::Xcm(location)` whose location satisfies the `Contains` predicate — it does not verify provenance (i.e., that only the frontend pallet's own logic could have produced a message that descends into that specific `PalletInstance`).

On AssetHub, `pallet_xcm::Config::SendXcmOrigin` explicitly allows any local signed account to send arbitrary XCM programs: [3](#0-2) 

This uses the same `XcmRouter`/`XcmpQueue` channel to BridgeHub as the frontend pallet's internal sender: [4](#0-3) 

On BridgeHub, the `Barrier` wraps the permission rules in `WithComputedOrigin`, which computes the effective origin by applying leading `DescendOrigin`-style instructions (up to depth 8) *before* checking the barrier rules, and then allows `AllowTopLevelPaidExecutionFrom<Everything>` — i.e., any origin, as long as the message pays its own execution: [5](#0-4) 

Crucially, `DescendOrigin` is a raw XCM instruction that is not gated by the `Aliasers`/`TrustedAliasers` permission system (that system only gates the separate `AliasOrigin` instruction; the code comment even notes `AliasChildLocation` is merely "equivalent to `DescendOrigin`", implying `DescendOrigin` itself is unconditionally permitted): [6](#0-5) 

The `OriginConverter` tuple resolves a `Transact{origin_kind: OriginKind::Xcm, ...}` instruction to `pallet_xcm::Origin::Xcm(location)` via `XcmPassthrough`, matching whatever the computed origin is: [7](#0-6) 

**Exploit flow**: A signed AssetHub account calls `PolkadotXcm::send` (or `PolkadotXcm::execute` combined with `InitiateTransfer`/similar patterns) targeting BridgeHub with a self-crafted XCM program:
```
[
  WithdrawAsset(fees), PayFees/BuyExecution(fees),
  DescendOrigin([PalletInstance(SystemFrontendPalletInstance)]),
  Transact { origin_kind: OriginKind::Xcm, call: <encoded snowbridge_pallet_system_v2 call> },
]
```
When this arrives at BridgeHub via XCMP, the message's base origin is `(1, [Parachain(ASSET_HUB_ID)])` (cryptographically guaranteed by the channel), but the `DescendOrigin` instruction — fully attacker-controlled content — appends `PalletInstance(SystemFrontendPalletInstance)`, producing exactly `(1, [Parachain(ASSET_HUB_ID), PalletInstance(SystemFrontendPalletInstance)])`. This is indistinguishable from a genuine message emitted by `snowbridge_pallet_system_frontend`'s own dispatch logic, and passes `AllowFromEthereumFrontend::contains` and thus `FrontendOrigin`.

### Impact Explanation
An attacker who is merely a signed AssetHub account — with none of the local authorization enforced by `snowbridge_pallet_system_frontend::Config::RegisterTokenOrigin` (asset-ownership checks via `LocalAssetOwner`/`ForeignAssetOwner`) — can directly invoke `FrontendOrigin`-gated calls on `snowbridge_pallet_system_v2` at BridgeHub, e.g. `register_token` to register arbitrary/unowned asset locations as Ethereum-bridged tokens, or `add_tip` to manipulate relayer reward/tip state, entirely bypassing the intended local authorization gate that exists specifically to prevent this.

### Likelihood Explanation
The attack requires only: (1) a signed AssetHub account with funds to pay local XCM execution/delivery fees, (2) knowledge of `SystemFrontendPalletInstance`'s numeric index (public constant, `bp_asset_hub_polkadot::SystemFrontendPalletInstance`), and (3) constructing a standard `DescendOrigin` + `Transact` XCM program via the already-permissioned `pallet_xcm::send`/`execute` extrinsics. No governance, root, or relayer privilege is needed, and the pattern is fully repeatable.

### Recommendation
Do not rely solely on location equality for `FrontendOrigin`. Either (a) restrict `AllowFromEthereumFrontend`/`EnsureXcm` to only accept messages whose origin descent chain is cryptographically tied to the frontend pallet's dispatch (e.g., require `AliasOrigin`-based authorization gated by `Aliasers`, or a dedicated `UniversalOrigin`/signed-message scheme instead of a bare `DescendOrigin`), or (b) restrict AssetHub's `SendXcmOrigin` so arbitrary signed accounts cannot embed `DescendOrigin` into pallet-instance junctions destined for privileged remote calls, or (c) add an explicit `SafeCallFilter`/pre-dispatch check on BridgeHub that rejects `Transact` calls into `snowbridge_pallet_system_v2`'s `FrontendOrigin`-gated extrinsics unless additional in-payload authentication (e.g., a MAC/nonce known only to the frontend pallet) is present.

### Proof of Concept
xcm-emulator test (extending `integration-tests/emulated/tests/bridges/bridge-hub-polkadot/src/tests/snowbridge_v2_outbound_edge_case.rs` style tests):
1. On `AssetHubPolkadot`, as `AssetHubPolkadotReceiver` (an unprivileged signed account with no asset ownership), call `PolkadotXcm::send` with `dest = SiblingBridgeHub` and a hand-built `Xcm` program: `WithdrawAsset`/`BuyExecution` for fees, then `DescendOrigin([PalletInstance(bp_asset_hub_polkadot::SystemFrontendPalletInstance::get())])`, then `Transact{origin_kind: OriginKind::Xcm, call: <encoded snowbridge_pallet_system_v2::Call::register_token(...)>}`.
2. On `BridgeHubPolkadot::execute_with`, assert that `EthereumSystemV2::register_token` (or `add_tip`) succeeded / emitted `RegisterToken`/`TipProcessed` events, despite the caller never passing through `snowbridge_pallet_system_frontend::Config::RegisterTokenOrigin`'s asset-ownership check.
3. Assert this contradicts the invariant enforced by `register_usdt_not_from_owner_on_asset_hub_will_fail` / `register_relay_token_from_asset_hub_user_origin_will_fail` (which expect `BadOrigin` for the same unauthorized caller when going through the legitimate frontend extrinsic) — showing the BridgeHub-side gate can be bypassed entirely via the forged `DescendOrigin`.
