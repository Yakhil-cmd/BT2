### Title
Unfunded `repay`/`recapitalize` refund drains pool custody without debiting the cash book, so the tracked funding overstates real balance and later claimants cannot be paid - (File: contracts/pool/src/cache/cash.rs)

### Summary
The bug class is "pay out a fixed claim from a funding pot that does not actually cover all claims; whoever claims first wins, later claimants get nothing." In XOXNO Lending, the pool's reserve check (`Cache::require_reserves`) reads the *accounting* cash book, not the token balance. `repay` and `recapitalize` refund the caller from pool custody *without* debiting that book — correct only if the controller actually transferred the declared amount in first. An unprivileged direct caller to `pool.recapitalize(hub_asset, payer, declared_amount)` can transfer zero tokens and still be refunded the full declared amount in real tokens, draining custody while the book still reports the cash as present.

### Finding Description
- `Cache::debit_cash` / `require_reserves` at `contracts/pool/src/cache/cash.rs:15-41` gate withdrawals on `self.cash >= amount` — the book, not `token.balance(pool)`. The test at `contracts/pool/tests/flows.rs:3404-3406` states this explicitly: "the book, not the balance, so it admits exits that then fail inside the SAC transfer."
- `contracts/pool/README.md:334-335`: "`repay` and **`recapitalize`** refund from pool cash without debiting it, correct only because the controller transferred the full amount in first." A direct pool caller is under no such obligation.
- `contracts/pool/tests/flows.rs:3408-3483` demonstrates the flow end-to-end: `client.recapitalize(&hub, &payer, &custody)` with no inbound transfer pays `payer` the entire pool token balance (`token.balance(&t.pool) == 0`) and leaves `state.cash` unchanged.
- Afterward, a supplier's `withdraw` passes `require_reserves` (the book says funds exist) and fails inside the SAC `transfer` with `BalanceError = 10` (`flows.rs:3454-3472`) — the exact OpenQ shape: the schedule of supplier claims exceeds real funding, and late claimants are stuck.

### Impact Explanation
Theft of user funds and freezing of funds: the first mover (the unfunded-refund caller, or racing withdrawers) takes real tokens; remaining suppliers hold supply shares whose claims exceed custody and their exits revert in the token transfer. `recapitalize` is permissionless and listed in-scope, so a single unprivileged address triggers this with one call and no deposit.

### Likelihood Explanation
One transaction: call `pool.recapitalize` (or the analogous `repay` excess-refund path) directly with a positive `amount` and no token transfer. The refund path transfers `declared − used` from pool custody to the payer while crediting/debiting only the measured receipt — measured receipt is zero, so the entire declared amount leaves as a refund. No privileged role, oracle manipulation, or timing race is required.

### Recommendation
Measure the inbound token delta inside the refund paths (balance-before/after around the op) and refund only `declared − min(declared, measured_receipt)`, or debit the cash book for any refund so `require_reserves` reflects true custody. Alternatively, gate `recapitalize`/`repay` refund legs to the trusted controller caller. Caveat: I could not read `contracts/pool/src/ops/recapitalize.rs`/`repay.rs` directly (index excerpts only), so the exact refund computation site should be confirmed there, but the behavior is proven by `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`.

### Proof of Concept
1. Supplier deposits `10_000_000_000` units via the normal supply path; pool `cash` book equals custody.
2. Attacker calls `pool.recapitalize(hub_asset, attacker_payer, custody_amount)` sending no tokens.
3. Pool transfers the full token balance to `attacker_payer`; `token.balance(pool) == 0`; `state.cash` still `>= deposit`.
4. Supplier calls `withdraw` (via controller `withdraw` → pool withdraw leg): `require_reserves` passes on the stale book, `burn_supply` runs, and the call aborts inside SAC `transfer` with `BalanceError` — supplier's funds are unrecoverable while the book claims solvency. Any later withdrawer hits the same wall; whoever exited first took the last real tokens.

This mirrors the existing test at `contracts/pool/tests/flows.rs:3408-3483` which already encodes steps 1–4.
