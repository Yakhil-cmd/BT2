### Title
Webhook organization authentication does not bind to the repository whose data is written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify a webhook's HMAC signature using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1)  However, the handlers that actually act on the payload (e.g. `Shipit::Webhooks::Handlers::Handler#stacks`, `ReviewStackAdapter#repo_name`) resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a *separate* field of the same unsigned-until-verified JSON body that is never cross-checked against `repository.owner.login`. [3](#0-2) [4](#0-3) 

### Finding Description
The HMAC signature only proves that the payload was produced by *an* organization's GitHub App installation whose `webhook_secret` matches — specifically the one selected via `repository.owner.login` (or `organization.login`). It does not prove that `repository.full_name` (owner + repo) inside the same JSON body belongs to that same organization. Since `verify_webhook_signature` verifies the raw HTTP body against a secret chosen from one field, but downstream code operates on a different field of that same body, `repository.owner.login` and `repository.full_name`'s owner segment are never required to match.

The equality that should hold and is broken:
`organization authenticated (repository.owner.login, used to pick webhook_secret and pass HMAC)` ≠ `organization whose Stack/Repository is actually looked up and mutated (repository.full_name)`.

An attacker who is a legitimate collaborator/admin on **any** GitHub organization that has the Shipit GitHub App installed (i.e., controls a valid `webhook_secret` for OrgA, which they can trigger simply by causing GitHub to send a real webhook, e.g. opening a PR in an OrgA repo) can, before the signature is checked, craft an HTTP POST to `/webhooks` where:
- `repository.owner.login` = `OrgA` (so `Shipit.github(organization: 'OrgA')` is used, and the attacker signs the body with OrgA's real secret since they control an OrgA repo/webhook delivery and can replay/modify a raw POST they legitimately have signing access to via the same App... )
- `repository.full_name` = `OrgB/some-repo` (a repository under a *different*, unrelated organization that also uses this Shipit instance)

Because `verify_signature` only checks the signature against OrgA's secret (matched via `repository.owner.login`), and the `push_handler`/`pull_request` handlers resolve the affected `Stack` via `repository.full_name` without ever re-verifying that `full_name`'s owner equals `repository.owner.login`, the request is accepted and acted upon against `OrgB`'s stack.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written." Depending on the webhook event handled (`push`, `pull_request`, `check_suite`, `status`), this allows an attacker who is a member of any org configured on the shared Shipit instance to inject synthetic `push`/`status`/`check_suite` events that get attributed to a target stack owned by a different organization, potentially:
- Triggering `GithubSyncJob` for a foreign stack (`push` handler), causing sync operations against a repository the attacker does not control.
- Creating/updating commit `Status` records or `check_suite` state on a foreign stack's commits, which downstream CI-gating logic (`ci.require`) uses to decide whether to allow deploys — enabling an unauthorized deploy by forging passing CI status on a stack outside the attacker's own organization.

This qualifies under "High - escalation into `Shipit.github_teams` authorization ... unauthorized deploy" and potentially "Critical - unauthorized deploy" since forged commit statuses can unblock CI gating for a deploy on a stack the attacker doesn't own.

### Likelihood Explanation
Requires the attacker to have legitimate control of a GitHub organization/app installation that is one of potentially multiple orgs configured under `Shipit.github` multi-org config (`test/dummy/config/secrets_double_github_app.yml` shows this is a supported real configuration with distinct `OrgTwo` etc.), plus knowledge of a target stack's `repository.full_name` in another org on the same Shipit instance. [5](#0-4)  This is realistic for shared/multi-tenant Shipit deployments serving several GitHub organizations, a documented supported use case.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler`, validate that `payload.dig('repository', 'full_name')`'s owner segment matches `repository_owner` (the org whose secret validated the signature) before dispatching to handlers. Reject (422) any webhook where these two fields disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App/webhook secret (supported per `test/dummy/config/secrets_double_github_app.yml`).
2. As a member of `OrgA` with a real installed webhook secret, craft a `push` event JSON body:
   ```json
   { "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }, "after": "<attacker-controlled sha>" }
   ```
3. Sign the raw body with OrgA's `webhook_secret` and send `X-Hub-Signature`, `X-Github-Event: push` to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`) and successfully verifies the signature against OrgA's secret. [1](#0-0) 
5. `PushHandler`/`Handler#stacks` looks up `Repository.from_github_repo_name('OrgB/target-repo')` using `full_name`, not `owner.login`, and enqueues `GithubSyncJob` for OrgB's stack. [3](#0-2)
