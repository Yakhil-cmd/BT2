### Title
Uncaught exception in oscript formula evaluation from an AA trigger can crash every full node - ([File: formula/evaluation.js])

### Summary
The s2n-quic advisory describes a crash triggered by a single malformed/empty network input that the endpoint's parser doesn't defensively handle, taking the endpoint down. In `ocore`, the equivalent single-attacker-controlled input is an **oscript formula attached to a payment/data message sent to an Autonomous Agent (AA)**. The formula interpreter in `formula/evaluation.js` contains several `throw Error(...)` statements inside the asynchronous `evaluate()` state machine that are not guarded by any `try/catch` at the call sites in `aa_composer.js`. Because these throws happen inside callback chains driven by `async.eachSeries`/`setImmediate`, a JS exception thrown there is **not** caught by the synchronous caller and becomes a Node.js `uncaughtException`. `network.js` installs a global handler that intentionally **re-throws and crashes the whole process** on any uncaught exception: [1](#0-0) 

This mirrors the s2n-quic pattern: a normal, unprivileged network participant (here, anyone who can send a payment/trigger to a public AA) can supply data that reaches an unhandled code path and brings down the endpoint (here, the whole ocore node process, including hubs and witnesses that process the unit).

### Finding Description
When an AA is triggered, `handleTrigger()` in `aa_composer.js` evaluates the AA's `messages`/getters/case-formulas via `formulaParser.evaluate()`: [2](#0-1) 

None of these call sites wrap `formulaParser.evaluate(...)` in a `try/catch`; they only handle the `(err, res)` callback contract. Inside the formula evaluator (`formula/evaluation.js`), several branches assume that after normalizing `wrappedObject` to `true` and handling `Decimal`, a resulting value can never still be `typeof 'object'`, and fall back to an unconditional `throw`: [3](#0-2) 

The equivalent unguarded `throw Error("unknown type ...")`/`throw Error("unrecognized ...")` pattern recurs throughout `evaluate()` (e.g. `to_lower`/`to_upper` fallthrough at line 2006, `has_only`/`starts_with` fallthrough at line 2051, `substring` type-fallthrough at lines 2083/2105, the `replace()` walker's `throw Error('unknown type of value in ' + name)` at line 872 of `aa_composer.js`). Any of these is reachable purely from the content of an AA definition and/or the values supplied in a trigger's `data`/`params`, both of which are fully attacker-controlled by whoever posts the triggering unit.

Because these evaluations run inside nested `async.eachSeries` callbacks (as seen throughout `formula/evaluation.js`, e.g. lines 1130-1167, 1957-1982, 2010-2054), a `throw` executed from one of these callback frames unwinds only up to the immediate callback invocation - it is not caught by `handleTrigger`'s or `validate()`'s outer logic, and surfaces as a Node `uncaughtException`.

### Impact Explanation
`network.js`'s global handler explicitly re-throws to "crash the process to avoid ending up in an inconsistent state": [1](#0-0) 

If a crafted AA definition (or a crafted trigger sent to an existing, already-deployed AA whose logic reaches one of these `else`/default `throw` branches with attacker-controlled data) causes this code path to execute during validation/execution on **every full node, hub, and witness** that processes the unit, the process crashes network-wide as the unit propagates. This satisfies the "network unable to confirm new units" bar in scope: a single posted unit can take down the nodes needed to reach stability/consensus for that and subsequent units, which is a materially different (and worse) outcome than a normal `bounce()`/validation error, which is designed to be handled gracefully without state corruption.

### Likelihood Explanation
Reachability requires only:
1. Deploying (or using an existing) AA whose `messages`/getters use formulas whose branches can, for certain crafted trigger `data`/`params`, produce a value that is a plain object/null at one of the unguarded `throw` sites (e.g., feeding into `ifelse`'s `test` expression, or a string-transform op on an unexpected operand type).
2. Sending one payment/trigger unit to that AA with the crafted `data`.

Both steps are available to any unprivileged unit poster / AA trigger sender, matching the in-scope actor list. I was not able to fully confirm, within the available search iterations, a concrete minimal oscript formula that provably drives `res` to a plain object (rather than `null`/boolean/string/Decimal/wrappedObject) at the `ifelse` site specifically — this requires tracing every `evaluate()` case's possible outputs, which is beyond what the code-search tool could establish with certainty. I'm flagging this explicitly as an open verification item; the surrounding evidence (multiple unguarded `throw`-on-unexpected-type branches, all reachable from attacker-supplied trigger data, all lacking `try/catch` at call sites, combined with a process-crashing `uncaughtException` handler) is strong circumstantial support for the bug class matching the s2n-quic analog, but exact PoC formula/input was not conclusively derived.

### Recommendation
- Wrap all `formulaParser.evaluate()` invocations in `aa_composer.js` (and `definition.js`'s formula-based address conditions) in `try/catch`, converting caught exceptions into `bounce()`/validation errors instead of allowing them to escape as uncaught exceptions.
- Replace all internal `throw Error(...)` "should never happen" branches inside `formula/evaluation.js`'s `evaluate()` (and the `replace()` walker in `aa_composer.js`) with `setFatalError(...)`/`cb(err)` style soft failures, consistent with the rest of the evaluator's error handling, since these branches are reachable with attacker-controlled formula inputs rather than being truly unreachable invariants.
- Audit whether the `uncaughtException` handler in `network.js` should distinguish between "core network/database corruption" (where crashing is appropriate) and validation-path exceptions that should instead be converted to per-unit validation failures.

### Proof of Concept
Not able to provide a fully verified minimal PoC formula within the current investigation; further work should focus on constructing an AA definition + trigger `data` payload that drives one of the identified unguarded `throw` branches in `formula/evaluation.js` (e.g., the `ifelse`/`to_lower`/`substring` fallthrough branches at [3](#0-2)  and [4](#0-3) ) and confirming via a local node that the resulting exception is uncaught and triggers the `process.on('uncaughtException')` crash path in `network.js`.
