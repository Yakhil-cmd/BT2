### Title
Unbounded memory/CPU consumption from unbounded chat-text processing in `handleMessageFromHub` "text" handler - ([File: wallet.js])

### Summary
`wallet.js`'s device-chat "text" message handler runs four global, backreference-free regex replacements over an attacker-controlled string with no upper bound on the string's length, mirroring the CWE-400 pattern in the Apache James advisory where unbounded-size input is fed into a text-conversion routine with no size cap, causing disproportionate memory/CPU consumption per message.

### Finding Description
Any paired device (or the hub relaying a message) can trigger `handleMessageFromHub` via the `"handle_message_from_hub"` event. Before any subject-specific processing, the handler only checks structural bounds, not string length: [1](#0-0) 

For the `"text"` subject, the body is only checked to be a non-empty string — its length is never capped — and then four separate global regex replacements are chained on it: [2](#0-1) 

`isTooDeeplyNestedOrHasTooManyNodes` (used both here and in the hub's `hub/deliver` check) only limits object nesting depth and node/key counts; it does **not** limit the byte length of an individual string field: [3](#0-2) [4](#0-3) 

Consequently, a single string leaf (the chat `body`) can be made arbitrarily large (bounded only by whatever transport-level limits exist, which are optional and hub-configured via `max_message_length`, not enforced by the wallet-side handler itself). That oversized string is then run through four `.replace(/\(...:.+?\)/g, '')` calls, each of which scans the whole string and allocates a new string of comparable size. This is directly analogous to the Apache James JMAP HTML-to-text bug: attacker-controlled content of unbounded size is fed to a text-transformation routine with no size ceiling, causing unbounded memory allocation (and repeated allocation across the four sequential `.replace()` calls) per single message, and this repeats for every message the attacker sends.

### Impact Explanation
A paired device (or a party able to relay a `hub/message`/`hub/deliver` payload to a wallet) can force the receiving wallet process to allocate memory proportional to an attacker-chosen string size, several times over (once per `.replace()` call), for every "text" message sent. Repeated messages of this kind can exhaust available memory or degrade responsiveness of the wallet node, matching the "network unable to confirm new units" / node-availability impact class this analysis targets (denial of service against a single node/wallet instance) rather than any fund-loss or consensus-disagreement issue.

### Likelihood Explanation
Reachability is straightforward: any paired correspondent device can send a `"text"` chat message with an arbitrarily large `body` field, and the handler unconditionally processes it (`isTooDeeplyNestedOrHasTooManyNodes` does not gate string length, and there is no explicit `MAX_MESSAGE_LENGTH`-style check for chat bodies in the wallet's own message handler). The regexes used are not classic catastrophic-backtracking patterns (they use lazy `.+?` without nested quantifiers), so the primary risk is linear-but-large memory allocation multiplied by four passes, rather than exponential CPU blowup — this somewhat limits severity compared to a true ReDoS, but the unbounded-size acceptance itself is the root cause shared with the James advisory.

### Recommendation
Enforce an explicit maximum length on chat/text message bodies (and generally on any string field) inside `handleMessageFromHub`, similar to the size caps already used elsewhere (`MAX_AA_STRING_LENGTH`, `device_hub`/`device_name` length checks in `device.js`). Reject or truncate `body` before running the four `.replace()` calls, and consider extending `isTooDeeplyNestedOrHasTooManyNodes` (or adding a companion check) to also bound the maximum length of any single string value, not just nesting depth/node count.

### Proof of Concept
1. Pair two devices (attacker device ↔ victim wallet).
2. From the attacker device, construct a `hub/message` (or direct `handle_message_from_hub`) payload with `subject: "text"` and `body` set to a very large string (e.g., tens/hundreds of MB), for example composed of many `"("` characters to also maximize regex-scan work, though even a plain large string suffices since length is never checked.
3. Send it to the victim's device via the hub (subject to only `isTooDeeplyNestedOrHasTooManyNodes(json, 20, 100000)`, which only checks depth/node count, not string size, and passes for a single large string leaf).
4. Observe the victim wallet process in `wallet.js` `case "text":` execute four global `.replace()` calls over the full oversized string, each allocating a new string of comparable size, with no ceiling — repeatable per message to amplify memory pressure.

```javascript
function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
```
