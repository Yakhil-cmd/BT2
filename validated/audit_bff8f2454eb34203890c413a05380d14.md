## Analysis

`WebhooksController#verify_signature` selects **which** organization's HMAC `webhook_secret` to verify the raw request body against by reading `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`): [1](#0-0) 

That check only proves the request was signed with the secret belonging to *whatever organization the attacker put in that field* — it says nothing about which repository/stack the event handlers will actually mutate. The base `Handler` class (used by `PushHandler`, all `PullRequest::*Handler`s, etc.) resolves the target `Repository`/`Stack` from a **different** JSON path, `payload.dig('repository', 'full_name')`: [2](#0-1) 

`PushHandler` then syncs the resolved stack using the attacker-supplied `after` SHA: [3](#0-2) 

`StatusHandler` writes a commit status keyed purely on `params.sha`, with no relation at all to the owner used for signature verification: [4](#0-3) 

`GitHubApp#verify_webhook_signature` performs a plain HMAC compare over the raw body using the secret picked for the `repository_owner` value: [5](#0-4) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the record acted on) are two independent, attacker-controlled fields inside the same signed JSON body, there is nothing that binds them together. In a multi-org Shipit deployment — which is an explicitly documented and supported configuration (`config/secrets.development.shopify.yml`, `docs/setup.md`) — each organization has its own `webhook_secret`: [6](#0-5) 

### Title
Webhook organization used for signature verification is decoupled from the repository the handler mutates, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature using the webhook secret of the organization named in `repository.owner.login`/`organization.login`, but the event handlers (`PushHandler`, `StatusHandler`, the `PullRequest::*` handlers, etc.) resolve the actual `Repository`/`Stack`/`Commit` to mutate from the unrelated `repository.full_name` (or bare `sha`) field of the same payload. These two fields are never cross-checked.

### Finding Description
The equality that should hold is: *organization whose secret authenticated the request == organization owning the repository/stack that gets written*. Because the controller and the handlers each independently `dig()` different fields out of the same attacker-controlled JSON body, an attacker who possesses the `webhook_secret` for **one** organization configured on a shared Shipit instance can sign a payload claiming `repository.owner.login = "OrgA"` (to pick OrgA's secret and pass HMAC verification) while setting `repository.full_name = "OrgB/victim-repo"` (or, for `status` events, simply any `sha` belonging to any tracked commit) so that the corresponding handler acts on OrgB's stacks/commits — an organization whose secret the attacker never had.

### Impact Explanation
This breaks the org-scoped trust boundary of webhook secrets: possessing a legitimately-issued, narrowly-scoped credential for one GitHub organization/App integration is sufficient to force writes into any other organization/repository tracked by the same Shipit instance. Concretely this enables:
- Forcing `GithubSyncJob`/`stack.sync_github` with an attacker-chosen `after` SHA on a victim stack (`PushHandler`).
- Injecting fabricated/successful CI `Status` records on arbitrary tracked commits (`StatusHandler`), which can satisfy `ci.require`/`ci.blocking` checks in `shipit.yml` and enable continuous deployment or auto-merge to run against attacker-chosen commits — an unauthorized deploy.
- Creating/archiving/unarchiving review stacks belonging to unrelated repositories (`PullRequest::*Handler`s), which run the `shipit.yml`-defined provisioning/deprovisioning steps for a repo the attacker doesn't control.

This maps to the in-scope Critical impact "cross-repository writes ... or an unauthorized deploy."

### Likelihood Explanation
Requires the attacker to hold the `webhook_secret` of at least one organization configured on the target Shipit instance (e.g. as a legitimate admin of their own org's GitHub App integration that happens to share a Shipit deployment with other orgs). No access to the *target* organization's secret, GitHub credentials, or Shipit session/API token is needed. Multi-org configuration is a first-class, documented Shipit feature, not a misconfiguration.

### Recommendation
Bind the organization used to select the verification secret to the same identifier used by the handlers to resolve the target record. Concretely, `WebhooksController#verify_signature`/`repository_owner` should derive from `repository.full_name`'s owner segment (or the `Repository` record ultimately resolved), and handlers should re-verify that the resolved `Repository#owner` matches the organization whose secret validated the signature, before performing any writes.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs: `OrgA` (attacker-controlled, `webhook_secret = SECRET_A`) and `OrgB` (victim, `webhook_secret = SECRET_B`, unknown to attacker), with `OrgB/victim-repo` tracked as a stack.
2. Craft a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
   }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, body)` and POST to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` reads `repository.owner.login = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check passes using `SECRET_A`.
5. `PushHandler` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — a write against OrgB's stack performed using only OrgA's credential.

      verified = github_app.verify_webhook_signature(

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
