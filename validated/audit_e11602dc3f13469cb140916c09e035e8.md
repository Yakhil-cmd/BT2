### Title
Cross-organization webhook signature confusion allows forged CI status and unauthorized continuous deployment - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an incoming payload against using an attacker-controlled field of that same payload (`repository.owner.login`), while `Shipit::Webhooks::Handlers::Handler#stacks` resolves the actual repository/stack to act on using a *different* attacker-controlled field of the same payload (`repository.full_name`). Nothing binds these two fields together, so in a multi-organization Shipit deployment an attacker who controls (or has a weak/blank webhook secret for) one onboarded GitHub organization can forge a webhook whose `owner.login` authenticates against that org, but whose `repository.full_name` points at a stack belonging to a completely different, victim organization.

### Finding Description
`verify_signature` picks the `GitHubApp` instance — and therefore the HMAC secret used for verification — from the request body itself: [1](#0-0) 

`repository_owner` is read straight from the untrusted JSON payload: [2](#0-1) 

Meanwhile, every webhook handler resolves the target `Repository`/`Stack` using a *different* field of the same payload, `repository.full_name`, with no cross-check against `repository_owner`: [3](#0-2) 

Shipit explicitly documents and supports a multi-org configuration where each GitHub organization has its own, independently configured `webhook_secret` (which can be left blank/`nil`): [4](#0-3) [5](#0-4) 

`GitHubApp#verify_webhook_signature` **short-circuits to `true`** whenever `webhook_secret` is blank for the org being checked: [6](#0-5) 

**The broken binding:** `organization authenticated (repository.owner.login) == organization/repository written to (repository.full_name)`. Before the attack, this equality always holds for genuine GitHub-originated webhooks because GitHub sets both fields consistently for the actual repository that fired the event. After the attack, an attacker who can reach the shared `/github/webhooks` endpoint (unauthenticated, only gated by the HMAC signature check) submits a hand-crafted payload where:
- `repository.owner.login` = an organization onboarded in Shipit with a blank or attacker-known `webhook_secret` (satisfying `verify_signature`), and
- `repository.full_name` = `victim-org/victim-repo`, an entirely different, unrelated tracked stack.

Because `verify_signature` never checks that the `repository.owner.login` matches `repository.full_name`'s owner, and handler resolution never re-validates the authenticated organization, the forged event is processed against the victim's stack as if it legitimately came from GitHub for that repository.

### Impact Explanation
The most damaging reachable handler is `StatusHandler`, which writes GitHub commit-status webhook data directly onto `Commit` records for any commit matching the given SHA, regardless of which stack/org the commit's stack actually belongs to: [7](#0-6) 

Creating a `success` `Status` record triggers `schedule_continuous_delivery`, which is unconditional on the source of the status: [8](#0-7) 

If the victim stack has `continuous_deployment` enabled, this can advance/trigger `Stack#trigger_continuous_delivery` → `trigger_deploy`, producing an **unauthorized deploy** on the victim's stack, satisfying the "Critical: unauthorized deploy" impact criterion: [9](#0-8) [10](#0-9) 

`PushHandler` is similarly reachable and forces a `sync_github` call against arbitrary tracked stacks using an attacker-chosen `expected_head_sha`: [11](#0-10) 

### Likelihood Explanation
This requires the deployment to use the documented multi-organization GitHub App configuration (an unprivileged attacker does not need write access to Shipit or GitHub credentials for the victim org — only the ability to be, or control, one of the *other* onboarded organizations, or to know that org's blank/weak `webhook_secret`, which the documented example config explicitly sets to `nil` by default). The webhook endpoint is unauthenticated apart from this signature check, and no additional session, API token, or GitHub write access to the victim repo is required, matching the required unprivileged-attacker threat model.

### Recommendation
Bind webhook signature verification to the resolved target repository/stack, not to attacker-supplied metadata used only for secret selection:
- After parsing the payload, resolve the target `Repository`/`Stack` first (via `repository.full_name`), then verify the signature using the `webhook_secret` configured for **that repository's actual, pre-configured organization** (e.g., stored on the `Repository`/`Stack` record or derived from an authoritative mapping), not from the untrusted `repository.owner.login` field of the same payload.
- Alternatively, reject the webhook if `repository.owner.login` does not match the owner segment of `repository.full_name`, and additionally ensure the resolved stack actually belongs to the organization whose secret was used to verify the signature.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `OrgAttacker` (webhook_secret left blank, as shown in `config/secrets.development.example.yml`) and `OrgVictim` (real repo tracked as `OrgVictim/app`, `continuous_deployment: true`).
2. Attacker POSTs to `/github/webhooks`:
```
X-Github-Event: status
Body (raw JSON):
{
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgVictim/app" },
  "sha": "<sha of a commit on OrgVictim/app tracked by Shipit>",
  "state": "success",
  "context": "ci/forged"
}
```
No `X-Hub-Signature` header value needs to be valid, because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `OrgAttacker`'s `webhook_secret` is blank.
3. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and passes.
4. `StatusHandler#process` finds `Commit.where(sha: ...)` under `OrgVictim/app`'s stack and creates a `success` `Status`.
5. `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` triggers an unauthorized deploy on `OrgVictim/app`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
