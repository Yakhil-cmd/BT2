The reported bug class—missing `await` on an asynchronous validation call (`verifyIntent`, `verifyQuote`) causing an unauthorized action to proceed—is a JavaScript/TypeScript Promise-execution pattern where a Promise body starts executing eagerly and the caller can race ahead unless it's awaited. This does not map onto nearcore's actual transaction/action validation paths, which are implemented as synchronous Rust functions rather than async futures that are polled independently of being awaited.

Searches across the relevant validation code paths confirm this: transaction signature/access-key validation in `runtime/runtime/src/verifier.rs` (`validate_transaction`, `validate_verify_and_charge_transaction`) and `core/primitives/src/transaction.rs` (`ValidatedTransaction::new`) are plain synchronous functions that return `Result`, not futures [1](#0-0) [2](#0-1) . Stateless-validation signature checks (chunk endorsements, contract deploys/accesses/witness signatures) in `chain/client/src/stateless_validation/validate.rs` are likewise synchronous and their return values are checked with `if !...verify(...)` before propagating errors [3](#0-2) [4](#0-3) . Where async code does exist (e.g., `RpcHandlerActor::process_tx` in `chain/client/src/rpc_handler.rs`), validation results are propagated with `?` or explicit early returns, not silently discarded [5](#0-4) .

Additionally, Rust's `Future` model is fundamentally different from JavaScript's: a `Future` does nothing until polled, and the compiler emits `unused_must_use`-style warnings for un-awaited futures, so a silently-bypassed validation of this exact shape is structurally unlikely and no such instance was found in the reachable transaction/receipt/action-validation code searched.
