### Title
Webhook signature verification keyed on `repository.owner.login` while event processing trusts unrelated `repository.full_name`/`organization.login` fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The external report's root cause is a trust binding mismatch: the check used to gate an action (`getLatestPrice`/sequencer status) is not bound to the actual state the action needs to certify (epoch expiry correctness). The equivalent binding in this engine is: **the GitHub organization whose secret is used to verify a webhook's HMAC signature MUST equal the organization/repository whose data the webhook payload is trusted to write.** `WebhooksController#verify_signature` selects the verifying secret using one payload field (`repository.owner.login` / `organization.login`), while the handlers (`Handler#repository_name`, `MembershipHandler`) act on a *different, independently-controlled* field of the same attacker-supplied JSON body, with no cross-check that they agree.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the raw JSON body and uses it purely to select which `GitHubApp` (and therefore which `webhook_secret`) to verify the signature against: [1](#0-0) [2](#0-1) 

This is only meaningful in the multi-org configuration mode documented in `docs/setup.md`, where each organization is configured with its own independent `webhook_secret` (`config/secrets.development.example.yml`). In that mode, anyone who legitimately controls one configured org's GitHub App (and therefore knows/can produce a valid signature with that org's `webhook_secret`) can craft an arbitrary raw JSON POST to `/webhooks`.

The verification step only checks `repository.owner.login` (or `organization.login`) against *that* org's secret. It never verifies that the rest of the payload — specifically `repository.full_name` used by `Handler#repository_name`, or `organization.login` used by `MembershipHandler` — actually refers to a repository/org belonging to the same organization that was used to authenticate the signature: [3](#0-2) 

`PushHandler` resolves the target `Stack`s purely from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`: [4](#0-3) [5](#0-4) 

`MembershipHandler` similarly trusts `params.organization.login` from the same JSON body to attach/detach a `User` to a `Team`, which is precisely the mechanism gating `current_user.authorized?` in `Shipit::Authentication`: [6](#0-5) [7](#0-6) 

Nothing forces `repository.owner.login` (used for signature selection) to equal `repository.full_name`'s owner segment, or `organization.login` in a `membership` event to equal the org whose secret validated the payload. Both fields are attacker-controlled parts of the same unauthenticated-until-verified raw JSON body; the equality `verified_org == acted_on_org` is assumed but never enforced in code.

The equality that should hold and is broken: `organization used to select webhook_secret for HMAC verification == organization/repository the handler mutates`. Before the attacker's request, only payloads genuinely signed by org X's GitHub App can affect org X's stacks/teams. After the attacker's crafted request (signed with org X's known secret but `repository.full_name`/`organization.login` set to org Y), the same signature check passes while data belonging to org Y is mutated.

### Impact Explanation
This crosses the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" boundaries explicitly listed as in-scope Critical/High impacts:
- Via `MembershipHandler`, an attacker who controls one configured organization can add an arbitrary `User` (their own Shipit account, once logged in via OAuth) to a `Team` object whose `organization` field is spoofed to match an org referenced by `Shipit.github_teams`, thereby satisfying `current_user.authorized?` and gaining access to stacks/deploys that should require legitimate GitHub org membership of a *different* organization.
- Via `PushHandler`/`Handler#repository_name`, an attacker can trigger `stack.sync_github` for a `Stack` belonging to a repository outside the org whose secret was used, i.e. a cross-repository write into another org's `Repository`/`Stack` state (commit sync, and downstream CI-status writes via `StatusHandler`, which affects `deployable?` gating used by `DeploysController#create`).

This requires the multi-organization webhook configuration to be in effect (each org has its own distinct `webhook_secret`), which is a documented, supported configuration mode of this engine, not a misuse of the documented single-tenant deployment.

### Likelihood Explanation
Requires the operator to run Shipit in the documented multi-organization mode with at least two orgs configured with independent webhook secrets, and requires the attacker to legitimately control (or have leaked) one such org's webhook secret — a realistic scenario for any org admin among many onboarded orgs, or if one org's secret leaks. No repository write access, GitHub App private key, or `ApiClient` token is needed; only the ability to sign an HTTP POST to the public `/webhooks` endpoint with a known secret.

### Recommendation
Cross-validate the payload's org/repository fields against the org used to select and verify the webhook secret before dispatching to handlers: reject the webhook (422) unless `repository.owner.login`/`organization.login` used in `verify_signature` matches the actual owner encoded in `repository.full_name`, and pass the verified organization into each `Handler` so it can additionally confirm any nested `organization.login` (e.g., in `MembershipHandler`) equals the verified organization before persisting `Team`/`Membership`/`Repository` changes.

### Proof of Concept
1. Operator configures Shipit for two orgs, `org-a` and `org-b`, each with a distinct `webhook_secret` (per `docs/setup.md` multi-org schema).
2. Attacker legitimately administers the GitHub App for `org-a` and thus knows `org-a`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: membership`, a valid `sha1=` HMAC computed with `org-a`'s secret, and a JSON body:
   ```json
   {
     "action": "added",
     "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999"},
     "organization": {"login": "org-b"},
     "member": {"login": "attacker-shipit-login"}
   }
   ```
4. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('organization','login')` → `"org-b"`... **however** note that with only `organization.login` present (no `repository` key), `repository_owner` resolves to `"org-b"`, so this particular membership case actually is validated against `org-b`'s secret already because both fields are the same key. The genuinely exploitable variant uses the `push`/`status` events where `repository.owner.login` (verification key) and `repository.full_name` (handler's target key) are two independently-set JSON fields that can be made to disagree, e.g.:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "deadbeef...",
     "repository": {
       "owner": {"login": "org-a"},
       "full_name": "org-b/target-repo"
     }
   }
   ```
   signed with `org-a`'s secret. `verify_signature` uses `owner.login = "org-a"` to fetch `Shipit.github(organization: "org-a")` and verifies successfully; `PushHandler#repository_name` then reads `full_name = "org-b/target-repo"` and calls `Repository.from_github_repo_name("org-b/target-repo")`, triggering `stack.sync_github` for `org-b`'s stack despite the request never being signed by `org-b`.

Because I could not execute this against a running instance, I was unable to empirically confirm the exact runtime behavior in Rails' JSON parsing/OmniAuth pipeline for split owner/full_name fields, or whether any additional validation exists elsewhere in the request pipeline (e.g. Rack middleware) that I did not locate in the indexed files; the code paths cited above are the concrete, file-verified root cause supporting this analog.
