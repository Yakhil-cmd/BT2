### Title
Unlocked `storage.resetMemory()` call from `light/dry_run_aa` races with the "write" mutex, exposing stale in-memory unit-cache objects to concurrent validation/writer code - ([File: network.js])

### Summary
The CVE describes a use-after-invalidation bug: `idpf_get_link_ksettings` read a `vport` pointer/derived state without the lock that protects it, so a concurrent reset could free/replace the underlying object while it was being dereferenced, crashing the kernel. The equivalent "shared resource mutated outside its owning lock while other paths hold a reference to the old object" pattern exists in `network.js`'s handling of the `light/dry_run_aa` command, which calls `storage.resetMemory()` outside of the `mutex.lock(["write"])` that every other cache-mutating code path (`writer.js`, `main_chain.js`, `storage.js`) uses to serialize access to the same in-memory caches (`assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`, `assocUnstableMessages`, `assocStableUnitsByMci`).

### Finding Description
`light/dry_run_aa` is a public, unauthenticated light-client command reachable by any peer: [1](#0-0) 

When `constants.COUNT_WITNESSES === 1` (single-witness/dev/test network configuration), after running the dry-run trigger it unconditionally calls:
```
db.executeInTransaction(function (conn, onDone) {
    storage.resetMemory(conn, onDone);
});
```
`resetMemory()` wipes and rebuilds the entire in-memory unit-cache state: [2](#0-1) 

Crucially, this call is **not** wrapped in `mutex.lock(["write"])`. Every other writer that mutates these same caches (`storage.assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`, `assocStableUnitsByMci`) — e.g. `writer.saveJoint`, `main_chain.updateMainChain`, `main_chain.markMcIndexStable`, `storage.shrinkCache` — takes the `"write"` mutex first: [3](#0-2) [4](#0-3) [5](#0-4) 

Numerous hot-path functions across the codebase hold direct object references into these caches and dereference nested fields (`.parent_units`, `.main_chain_index`, `.is_free`, etc.) without re-checking existence between async steps, e.g. `storage.forgetUnit` / `fixIsFreeAfterForgettingUnit`: [6](#0-5) 

and `main_chain.js`'s main-chain rebuild logic that walks `storage.assocUnstableUnits[unit].parent_units`: [7](#0-6) [8](#0-7) 

Because `resetMemory()` (invoked from an unauthenticated light request) deletes all keys of `assocUnstableUnits`/`assocStableUnits`/`assocBestChildren`/`assocStableUnitsByMci` and then asynchronously repopulates them via `initUnstableUnits`/`initStableUnits` (multi-step DB reads) while holding **no** lock, a concurrent unit validation or main-chain update that is mid-flight (holding a stale reference to an object that just got `delete`d from the association map, or iterating `for (var unit in storage.assocUnstableUnits)` while entries are being wiped/rebuilt) can observe an inconsistent or partially-rebuilt cache. This mirrors the idpf root cause precisely: a getter/reader path bypasses the lock that guards the mutable shared state, so a concurrent reset invalidates objects the reader still holds pointers to.

### Impact Explanation
A successful race causes the node's core validity caches (`assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`, `assocStableUnitsByMci`) to become internally inconsistent while units are actively being validated, main-chain-updated, or stabilized. Depending on timing this can:
- Throw uncaught `Error`s from the many defensive `throw Error(...)` assertions scattered through `storage.js`/`main_chain.js` that assume cache consistency (e.g. `"no unstable props of "+unit`, `"trying to forget stable unit "+unit`), crashing the node process and halting confirmation of new units — a network-availability impact.
- Cause `is_free`/`main_chain_index`/stability bookkeeping to be computed from half-reset state, potentially leading nodes to disagree on unit validity/stability (the exact failure classes this analog rubric treats as in-scope: "node disagreement on validity or stability" / "a network unable to confirm new units").

### Likelihood Explanation
The trigger requires `constants.COUNT_WITNESSES === 1`, i.e. it is only reachable in single-witness (developer/test) network configurations, not on mainnet. Given that constraint, any light client can repeatedly send `light/dry_run_aa` requests concurrently with normal unit posting/validation traffic to attempt to win the race window between `resetUnstableUnits`/`resetStableUnits`'s synchronous `delete` loops and the asynchronous re-population, without needing any special privilege.

### Recommendation
Wrap the `storage.resetMemory()` call triggered from `light/dry_run_aa` (and any other unlocked callers) in the same `mutex.lock(["write"])` used by `writer.saveJoint`, `main_chain.updateMainChain`/`markMcIndexStable`, and `storage.shrinkCache`, so cache resets are always serialized with respect to normal validation/writing. Alternatively, gate this reset path so it cannot run concurrently with in-flight validations (e.g., only allow it when the write lock is free and take it explicitly before calling `resetMemory`).

### Proof of Concept
Not independently reproducible from the index alone — confirming an actual crash/inconsistency requires running an ocore node configured with `constants.COUNT_WITNESSES === 1` (test/dev network), then concurrently (a) issuing many `light/dry_run_aa` requests, and (b) posting/validating real units, to win the race window inside `storage.resetMemory()`'s unlocked delete/rebuild cycle. This would need to be validated with a running instance (e.g., in a Devin session), which is outside the scope of static index-based analysis.
