Found the vulnerability: the `AddressRegistrar::register` function in `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs` computes an exact `required_deposit` for storage, checks `given_deposit >= required_deposit`, but on the success path (the `Entry::Vacant` branch) never returns the excess `given_deposit - required_deposit` to the caller — it is only refunded on the collision/`Entry::Occupied` failure path.

### Title
Excess attached deposit is not refunded on successful registration in `AddressRegistrar::register` - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
`AddressRegistrar::register` is a `#[payable]` method reachable from any unprivileged account (directly, or via the Wallet Contract's `rlp_execute` flow used to register eth-implicit accounts). It computes the exact storage cost (`required_deposit`) needed to store the new `address -> account_id` mapping and rejects the call only if `given_deposit < required_deposit`. When the deposit exceeds the requirement and the address is not yet registered, the vacant branch stores the entry and returns `Some(address)` **without ever transferring back the surplus** `given_deposit - required_deposit`. This mirrors the reported `buyToken()` bug class: a function computes an exact required amount but silently retains any amount attached beyond it on the success path.

### Finding Description [1](#0-0) 
The function derives `required_deposit` from the byte cost of storing the entry and panics only if the caller attached less than that. [2](#0-1)  On the vacant (success) path, the entry is inserted and the address returned, with no refund logic at all. [3](#0-2)  Only the collision (`Entry::Occupied`) branch explicitly creates a promise to transfer `given_deposit` back to `predecessor_account_id`, confirming the developers were aware that unspent deposit must be actively refunded — but they only implemented this for the failure branch, not for the success branch where `given_deposit` may still exceed `required_deposit`.

This function is reachable from any unprivileged NEAR account by directly calling `register`, and is also invoked programmatically from the Wallet Contract's `address_check_callback` flow for eth-implicit account registration checks [4](#0-3) , so a relayer or user funding a registration call with more than the exact storage cost permanently loses the difference into the registrar contract's balance.

### Impact Explanation
Any caller (user or relayer) who attaches more than the exact required storage deposit to a successful `register` call permanently loses the excess NEAR to the `AddressRegistrar` contract's balance — the tokens are not burned, but they are unauthorized state change from the caller's perspective (their balance is deducted, but the extra amount is not accounted for or returned, and there is no mechanism for the caller to reclaim it after the fact). This is a fund-loss bug for unprivileged users of a contract that is part of the nearcore wallet-contract ecosystem, not a validator/node-only issue.

### Likelihood Explanation
Likelihood is moderate: it requires a caller to overestimate/overpay the storage deposit, which is plausible for relayers/wallets that round up gas/storage estimates for safety margin (exactly the scenario the original report describes for ETH). Since the exact byte cost formula (`20 + account_id.len()`) is not trivial for external callers to always compute perfectly, over-attachment is a realistic occurrence.

### Recommendation
In the `Entry::Vacant` success branch of `register`, compute `given_deposit.saturating_sub(required_deposit)` and, if greater than zero, create a promise transferring that surplus back to `env::predecessor_account_id()`, mirroring the refund logic already present in the `Entry::Occupied` branch.

### Proof of Concept
1. Caller attaches `given_deposit = required_deposit + X` yoctoNEAR (X > 0) and calls `register(account_id)` where `account_id` is not yet registered.
2. Execution reaches the `Entry::Vacant` branch: the mapping is stored, `Some(address)` is returned, and the call succeeds.
3. No transfer action is generated back to the caller for the surplus `X`; the registrar contract's balance is increased by the full `given_deposit`, while only `required_deposit` was actually needed to cover storage staking costs.
4. Compare this to the `Entry::Occupied` branch [5](#0-4) , which explicitly refunds the entire deposit on failure — proving the contract's intended design was to return unneeded funds, but this was omitted for the success/overpayment case.

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
