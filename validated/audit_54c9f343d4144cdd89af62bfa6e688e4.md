### Title
`ERC20Transactor` does not skip zero-value transfers before calling into the ERC20 contract, causing legitimate XCM programs to fail on tokens that revert on zero-value transfers - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` always invoke the underlying ERC-20 contract's `transfer(to, value)` for whatever `amount` was matched from the XCM `Asset`, including `amount == 0`. Every comparable transfer path in this same codebase (`pallet-assets::do_transfer`/`transfer_and_die`, `pallet-balances` `Currency::transfer`, `pallet-vesting::vested_transfer`, `pallet-contracts`/`pallet-revive`'s internal `transfer`) explicitly special-cases `amount.is_zero()` as a no-op to avoid unnecessary side effects or failures. `ERC20Transactor` has no such guard, so a real ERC-20 contract that reverts on zero-value transfers (a documented pattern for some tokens) will make the whole XCM instruction — and hence the surrounding XCM program — fail with `XcmError::FailedToTransactAsset`.

### Finding Description
`ERC20Transactor` is wired into production XCM configuration for Asset Hub Westend as one of the `AssetTransactors`: [1](#0-0) 

Any asset whose XCM `AssetId` resolves to an `AccountKey20` (an EVM/`pallet-revive` contract address) is matched by `ERC20Matcher` and routed to this transactor. Both entry points unconditionally build an ABI-encoded `transfer` call and dispatch it via `pallet_revive::Pallet::<T>::bare_call`, with no zero-amount short-circuit: [2](#0-1) [3](#0-2) 

Compare this to the pattern used everywhere else in the codebase for the exact same class of operation: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

All of these treat a zero amount as an intentional no-op — `pallet-revive::exec::transfer` even documents this explicitly ("This is a no-op for zero `value`, avoiding events to be emitted for zero balance transfers."). `ERC20Transactor` is the outlier: it forwards `amount == 0` straight into the target contract's `transfer` function.

The entry point is a normal, unprivileged, signed user action: `pallet_xcm::execute` (or a routed reserve-transfer/teleport XCM program) containing `WithdrawAsset`/`DepositAsset` instructions for an `AccountKey20`-keyed asset. The existing test `smart_contract_not_erc20_will_error` demonstrates exactly this call path (a signed user submitting `PolkadotXcm::execute` with `withdraw_asset`/`deposit_asset` on an `AccountKey20` asset, hitting `ERC20Transactor`): [8](#0-7) 

If the referenced contract is an ERC-20 implementation that reverts when `value == 0` (a real-world, documented ERC-20 behavior — the same class of token this bug report calls out, e.g. old LEND-style tokens), any XCM program that ends up transacting a zero amount of that asset will unconditionally fail at the `did_revert()` check: [9](#0-8) 

A zero amount can arise not only from a directly user-supplied `Fungible(0)` asset, but also as a byproduct of fee/rounding computations upstream in XCM execution (e.g., dust/rounding in reserve-backed transfers or asset-conversion swaps) that legitimately produce a zero-remainder leg for one of several assets bundled in a single XCM program.

### Impact Explanation
This is a denial-of-service on the specific XCM instruction/program involving the affected ERC-20 asset, not a fund-theft or issuance bug. Concretely:
- A user or protocol-constructed XCM program (e.g., a reserve-backed transfer bundling multiple assets, one of which nets to zero) that includes a zero-amount leg on an ERC-20 asset whose contract reverts on zero transfers will have that instruction fail with `XcmError::FailedToTransactAsset`, aborting/rolling back or trapping the rest of the program depending on where in the XCM instruction sequence the failure occurs.
- This mirrors the original report's core issue (`lenderAcceptBid` always reverting because `amountToProtocol` could be zero) — a legitimate value transfer path becomes unusable purely because it doesn't skip the zero-value case, and the failure mode is entirely dependent on third-party (attacker-uncontrolled at the pallet level) ERC-20 token semantics.
- Impact is bounded to the specific asset/program in question; there is no cross-account fund loss and no unbacked issuance. This aligns with the Medium severity of the original finding rather than Critical/High.

### Likelihood Explanation
Reachability requires no privileged role: any signed account can submit `pallet_xcm::execute` with a crafted `WithdrawAsset`/`DepositAsset` referencing an `AccountKey20` asset, exactly as already exercised by the existing test `smart_contract_not_erc20_will_error`. The only additional precondition is that the referenced ERC-20 contract reverts on `value == 0` — which is attacker-controlled if the attacker deploys their own such contract and registers/uses it as the XCM asset, or is naturally triggered against any already-integrated ERC-20 whose implementation happens to revert on zero-value transfers. Likelihood of accidental triggering (e.g., via rounding to zero in a multi-asset reserve transfer) is plausible but was not proven in a live cross-chain fee-rounding path within this investigation.

### Recommendation
Add an early `if amount.is_zero() { return Ok(...) }` guard (mirroring `pallet-assets::functions::transfer_and_die`, `pallet-balances::Currency::transfer`, and `pallet-revive::exec::transfer`) to both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `ERC20Transactor`, short-circuiting before constructing/dispatching the `IERC20::transferCall`.

### Proof of Concept
- Program/severity rationale: Entry point is the unprivileged `pallet_xcm::execute` extrinsic wired into production Asset Hub Westend XCM config (`AssetTransactors` includes `ERC20Transactor`), matching the "real user entry" requirement.
- Failed guard: `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` lack the `amount.is_zero()` short-circuit present in every sibling transfer implementation in this codebase.
- Deployment evidence: `ERC20Transactor` is compiled into `asset-hub-westend-runtime`'s `AssetTransactors` tuple (production config), not test-only code.
- PoC execution status: **Not executed.** I was not able to run a concrete integration test in this session (read-only analysis only). A minimal reproduction would extend the existing `smart_contract_not_erc20_will_error` test in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`, deploying a `pallet-revive` fixture ERC-20 contract that reverts when `value == 0`, then submitting `PolkadotXcm::execute` with `withdraw_asset`/`deposit_asset` for that contract's address with amount `0`, and asserting the XCM execution fails with `FailedToTransactAsset("ERC20 contract reverted")` even though a zero-value transfer should be a semantic no-op. This was not run; the analysis is based on static code review of the transactor and the existing analogous test scaffolding.

#[test]
fn smart_contract_not_erc20_will_error() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 10_000_000_000_000u128;

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));

		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let (code, _) = compile_module("dummy").unwrap();

		let Contract { addr: non_erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.build_and_unwrap_contract();

		let wnd_amount_for_fees = 1_000_000_000_000u128;
		let erc20_transfer_amount = 100u128;
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: non_erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.build();
		// Execution fails but doesn't panic.
		assert!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(2_500_000_000, 120_000),
		)
		.is_err());
	});
