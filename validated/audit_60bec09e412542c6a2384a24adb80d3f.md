### Title
Integer overflow in `denomInfo.count_coins * denomInfo.denomination` bypasses asset cap consistency check - ([File: validation.js])

### Summary
`validateAssetDefinition()` in `validation.js` computes the declared supply cap of a fixed-denomination asset by summing `count_coins * denomination` for each denomination entry supplied by the asset issuer, then compares the result against `payload.cap` for equality. Neither `count_coins` nor the accumulated `total_cap_from_denominations` is bounded to a value that is safely representable in a JS double (`Number.MAX_SAFE_INTEGER = 2^53-1`), so a single unprivileged asset-issuing unit can trigger an integer-overflow-class precision-loss bug (CWE-190 analog) that makes the equality check pass for a cap value that does not correspond to the actual product of `count_coins` and `denomination`.

### Finding Description
In `validateAssetDefinition()`: [1](#0-0) 

`denomInfo.denomination` is bounded (only conditionally, post-`pemCurvesFixMci`) by `constants.MAX_CAP`: [2](#0-1) 

but `denomInfo.count_coins` is validated only with `isPositiveInteger()`, which has **no upper bound at all**: [3](#0-2) 

`isPositiveInteger` merely checks `Number.isInteger`-style finiteness (`Math.floor(value) === value`), which is trivially true for any large double, even ones far beyond `Number.MAX_SAFE_INTEGER` (doubles above 2^53 are always "integral" due to lost fractional precision, but they are no longer exact integers).

The vulnerable computation is:
```
total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;
```
An attacker can pick `count_coins` and `denomination` values whose true product vastly exceeds `Number.MAX_SAFE_INTEGER` (e.g. both close to `constants.MAX_CAP`, ~9×10^15, giving a product on the order of 10^31). The JS engine silently rounds this product to the nearest representable double. The attacker can then also choose `payload.cap` to be a value that, after equivalent floating-point rounding, is bitwise identical to the computed (imprecise) `total_cap_from_denominations`, satisfying: [4](#0-3) 

This is structurally the same bug class as the `liblz4` CVE-2021-3520 referenced in the report: an integer/size computation derived from attacker-controlled length-like fields overflows its safe representable range, and the resulting corrupted/truncated value is then used to pass a downstream consistency/bounds check that the code assumes is exact.

### Impact Explanation
This lets an asset issuer post a `fixed_denominations` asset definition unit whose stated `cap` is internally inconsistent with the true `count_coins × denomination` supply implied by its own denomination table, while still passing on-chain validation. Depending on how downstream issuance/spend logic (denomination-count tracking, private-asset output validation, and fixed-denomination redemption) relies on `count_coins` vs. `cap` for enforcing the maximum issuable supply, this can be leveraged to create a supply-inflation condition for the asset (units are considered valid by every node applying the same deterministic check, since the floating-point rounding is deterministic across all validating nodes) — i.e., a network-wide agreement on an asset supply invariant that doesn't match its declared cap.

### Likelihood Explanation
Reachable by any single unprivileged unit author defining a new asset (`asset definition` message) — no special privileges, hub, AA, or peer compromise required. Because JS `Number` overflow behavior (silent rounding, not an exception) is deterministic and identical on every validating node (all nodes use the same double-precision arithmetic), all full nodes would agree the unit is valid, so this is not merely a client-side quirk — it is a consensus-safe way to create an inconsistent asset definition.

### Recommendation
- Bound `denomInfo.count_coins` to `constants.MAX_CAP` (or another safe ceiling) the same way `denomInfo.denomination` and `payload.cap` are bounded, unconditionally (not gated by `pemCurvesFixMci`).
- Reject denomination entries or the whole definition if `denomInfo.count_coins * denomInfo.denomination` (or the running `total_cap_from_denominations`) exceeds `Number.MAX_SAFE_INTEGER`, e.g. by checking each factor and the accumulated sum against `constants.MAX_CAP` before multiplying, or by using a safe/bigint-based multiplication and range check instead of native JS `*`.
- Audit all other places performing arithmetic on attacker-supplied "amount/denomination/count" fields validated only by `isPositiveInteger`/`isNonnegativeInteger` (which impose no upper bound) for the same overflow pattern.

### Proof of Concept
Not independently executed in this session (index/ask-only mode); conceptual PoC based on confirmed code paths:
1. Author (unprivileged) posts a unit containing an `asset` definition message with `fixed_denominations: true` and:
   - `denominations: [{ denomination: D, count_coins: C }]` where `D` and `C` are each ≤ `constants.MAX_CAP` but `D * C` exceeds `Number.MAX_SAFE_INTEGER` (e.g. `D = 100000000`, `C = 100000000000000` roughly, tuned so `D*C` rounds to a specific double).
   - `cap: X` where `X` is chosen so that, after IEEE‑754 double rounding of `D*C`, `X === D*C` in JS numeric equality despite the true mathematical product of `D` and `C` differing from `X`.
2. `validateAssetDefinition()` accepts the unit because `payload.cap !== total_cap_from_denominations` evaluates to `false` due to floating-point rounding, even though the true `count_coins`-implied supply differs from the declared `cap`. [5](#0-4) 

Note: I was unable to fully trace, within this session, the downstream code that consumes `count_coins` per denomination (issuance/spend paths for fixed-denomination private assets) to confirm the exact mechanism by which this cap/count mismatch is converted into concrete unauthorized issuance or double-spend of value; this would need further investigation (e.g., in `storage.js`/`inputs.js`/private-payment output validation) to fully close the loop from "inconsistent definition accepted" to "coins spent beyond cap."
