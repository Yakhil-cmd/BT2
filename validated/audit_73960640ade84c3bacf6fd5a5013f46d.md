## Title
Webhook signature verification is bound to the wrong field, letting an attacker with a valid secret for *any* configured GitHub organization forge state/push/PR events against *any other* repository tracked by the same Shipit instance, enabling unauthorized commit-status injection and deploy triggers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The external report's bug class — "the code that acts never checks the identity the caller actually authenticated as" — maps directly onto Shipit's webhook trust boundary. `WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on one payload field (`repository.owner.login`, falling back to `organization.login`), while the event handlers act on an entirely different, unrelated payload field (`repository.full_name`, or for `status` events, nothing at all — just the raw `sha`). Because both fields live inside the same attacker-controlled JSON body that is only integrity-protected as a whole (not individually bound), an operator/attacker who legitimately knows the webhook secret for *one* onboarded GitHub organization can forge a signature that is valid for a payload whose *acted-upon* fields reference a completely different organization/repository/commit.

### Finding Description
`WebhooksController#verify_signature` looks up the signing secret using the repository (or organization) owner login taken straight from the untrusted JSON body, then verifies the raw body against that secret: [1](#0-0) [2](#0-1) 

This only proves that the *whole byte string* was signed by whoever holds the secret for the organization named by `repository.owner.login`/`organization.login`. It does **not** prove that the other, semantically-important fields in that same body ("which repo/commit does this event apply to") actually belong to that organization — GitHub itself guarantees that consistency for real events, but nothing in Shipit re-checks it for a body it just accepted as "signed by org X."

Downstream handlers key their side effects off a *different* field:
- `Handler#stacks` / pull-request handlers resolve the target repository via `payload.dig('repository', 'full_name')`: [3](#0-2) [4](#0-3) 
- `PushHandler#process` syncs whichever stacks match that resolved repository/branch, calling `stack.sync_github`: [5](#0-4) 
- `StatusHandler#process` is even less scoped: it updates the CI status of **every** `Commit` row anywhere in the database matching the given `sha`, with no repository/organization check at all: [6](#0-5) 

Multi-organization deployments are an explicitly documented, supported configuration, each with its own independent `webhook_secret`: [7](#0-6) [8](#0-7) 

**The broken equality**: the organization whose secret authenticated the request `≠` the repository/commit the handlers actually write to. `verify_signature` authenticates "sender = org X" while `PushHandler`/`StatusHandler`/PR handlers act on "target = whatever `repository.full_name` or `sha` says," and nothing forces those to be the same organization.

### Impact Explanation
In a multi-org Shipit install (an explicitly supported topology), an org that has legitimately been onboarded — and therefore whose administrator legitimately possesses that org's `webhook_secret` — can forge signed webhook bodies that:
- Set a fabricated `status`/commit_status (e.g. `state: "success"`) on any commit hash tracked by any *other* org's stack, since `StatusHandler` does no repository scoping at all. Commit CI-status state feeds into deployability checks used to gate/trigger automatic deploys, so this can be used to falsify a "green CI" signal on a stack the attacker has no legitimate access to, contributing to an unauthorized deploy.
- Trigger `GithubSyncJob`/`sync_github` on an arbitrary victim stack via a forged `push` event whose `repository.full_name` points at that victim's repo while `repository.owner.login` points at the attacker's own (legitimately onboarded) org.
- Create/archive/label review-stack pull requests for a victim repository via the `pull_request` handlers, which also resolve target repository from `repository.full_name` independent of the signing org.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
