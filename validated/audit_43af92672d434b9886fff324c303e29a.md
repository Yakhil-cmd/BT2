## Analysis

The claimed binding: `TaskCommands#env['GIT_ASKPASS']` (or `GITHUB_TOKEN`) after `.merge(deploy_spec.machine_env)` must equal the trusted value set by `Commands#base_env`, i.e. `deploy_spec.machine_env['GIT_ASKPASS'] ≠ Commands#base_env['GIT_ASKPASS']` must always hold true in the final merged hash.

Tracing `TaskCommands#env` [1](#0-0) , the merge order is: `Commands#base_env` (sets `GITHUB_TOKEN`, `GIT_ASKPASS`) [2](#0-1) , then `@stack.env`, then task metadata, **then `.merge(deploy_spec.machine_env)`**, then `.merge(@task.env)`. Since later `merge` calls win, any key in `deploy_spec.machine_env` overwrites the base env, including `GIT_ASKPASS`/`GITHUB_TOKEN`.

`deploy_spec.machine_env` reads `config('machine', 'environment')` from the parsed `shipit.yml` [3](#0-2) , and for review stacks that `shipit.yml` is read from the checked-out branch, which is `params.pull_request.head.ref` — a branch fully controlled by the PR author's fork [4](#0-3) . There is no allow-list, reserved-key check, or `EnvironmentVariables#permit` call applied to `machine_env` anywhere — `permit` is only used for `deploy_variables`/`rollback_variables`/task `variables`, not for `machine_env` [5](#0-4) [6](#0-5) .

Once `GIT_ASKPASS` is overridden, `Command#start` spawns the process with this env via `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` [7](#0-6) , and any subsequent `git` invocation that hits an HTTPS credential prompt (e.g. `git fetch`/`git clone` over HTTPS, or any git command in the deploy/task steps) will invoke the attacker-controlled `GIT_ASKPASS` script instead of the trusted `lib/snippets/git-askpass` [8](#0-7) , which normally echoes `GITHUB_TOKEN` to git only. An attacker-controlled `GIT_ASKPASS` binary run in-process gets `GITHUB_TOKEN` (and any other trusted env vars) as its own environment and can exfiltrate them (e.g., write to a file, curl them out), or `GITHUB_TOKEN` itself can be directly overwritten to a value the attacker controls to manipulate what token subsequent git commands would present (less impactful) — but the more severe direction is overriding `GIT_ASKPASS` to a script path that captures/exfiltrates the legitimate `GITHUB_TOKEN` that's still present in the process environment.

This matches a real, reachable, unauthenticated-fork-PR path: an attacker opens a PR from a fork with a `shipit.yml` containing:
```yaml
machine:
  environment:
    GIT_ASKPASS: /path/attacker/writes/during/deploy/steps
```
combined with a deploy/task step (also attacker-controlled via `shipit.yml`'s `deploy.override`/`tasks`) that writes an executable to that path before any `git` command from `TaskCommands`/`DeployCommands` runs, and then triggers any git operation in a later step of the same task (all steps run with the same merged `env`) — capturing `GITHUB_TOKEN` when the askpass script fires.

I found no guard (`EnvironmentVariables#permit`, reserved-key validation, or ordering fix) preventing `deploy_spec.machine_env` from clobbering `base_env`'s `GITHUB_TOKEN`/`GIT_ASKPASS`. Whether this is currently exploitable end-to-end also depends on whether review-stack task execution actually invokes an HTTPS git credential prompt after the `machine_env`-controlled step runs and whether write access to the target path exists — I was not able to fully verify a complete PTY-spawn chain that triggers the askpass prompt from a task step (as opposed to the initial `clone`/`fetch`, which occurs in `StackCommands`/`TaskCommands#clone`/`checkout`, using `env` too, computed the same way per-task). Given time constraints, I could not trace every task/deploy execution ordering scenario with full certainty, but the core structural flaw — `deploy_spec.machine_env` from an untrusted `shipit.yml` unconditionally overwriting reserved credential keys in the merged env — is confirmed in code.

### Title
`TaskCommands#env` allows fork-authored `shipit.yml` `machine.environment` to overwrite `GITHUB_TOKEN`/`GIT_ASKPASS` - (File: lib/shipit/task_commands.rb)

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` — sourced from the `shipit.yml` on the checked-out (possibly fork-authored) branch — after `Commands#base_env`, which sets the trusted `GITHUB_TOKEN` and `GIT_ASKPASS`. Because no reserved-key filtering is applied to `machine_env`, a PR author can define `machine.environment.GIT_ASKPASS` or `GITHUB_TOKEN` in their fork's `shipit.yml` and have it silently override the trusted values for every command spawned via `PTY.spawn` during that task/deploy.

### Finding Description
Broken binding: `deploy_spec.machine_env['GIT_ASKPASS'] == Commands#base_env['GIT_ASKPASS']` is expected to hold (i.e., fork config cannot equal/override the trusted value), but no code enforces this.

`TaskCommands#env` builds the final environment as:
```ruby
super.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)
``` [1](#0-0) 
`super` resolves to `Commands#env` → `base_env`, which sets `GITHUB_TOKEN` and, if `Shipit.use_git_askpass?`, `GIT_ASKPASS` [9](#0-8) . `deploy_spec.machine_env` reads directly from the parsed `shipit.yml` config with no key restriction [3](#0-2) , and for a `ReviewStack` this `shipit.yml` is checked out from `branch: params.pull_request.head.ref`, i.e. the PR author's own branch/fork [4](#0-3) . `Hash#merge` gives precedence to `deploy_spec.machine_env`, so any key collision (`GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`) overwrites the trusted value. This merged env is passed unmodified into `Command.new(..., env:)` and ultimately into `PTY.spawn(unbundled_env, ...)` [10](#0-9) .

The only sanitization mechanism in the codebase, `EnvironmentVariables#permit`, is applied to `deploy_variables`/`rollback_variables`/task `variables` [5](#0-4) [6](#0-5) , but is never applied to `machine_env`, so this specific merge is unguarded.

### Impact Explanation
If `GIT_ASKPASS` is overwritten with an attacker-supplied script path (written by an earlier attacker-controlled deploy/task step from the same `shipit.yml`), that script executes in-process during any subsequent `git` HTTPS credential prompt with access to the real `GITHUB_TOKEN` still present in the spawned process's environment, enabling exfiltration of the app's GitHub token for that repository/organization. This matches "exfiltration of `GITHUB_TOKEN`" (Critical).

### Likelihood Explanation
Requires: (1) review stacks enabled for the target repository, (2) `Shipit.use_git_askpass?` true (or overriding `GITHUB_TOKEN` directly), (3) attacker's `shipit.yml` on their own PR branch defining `machine.environment.GIT_ASKPASS`/`GITHUB_TOKEN`, and (4) a subsequent git HTTPS operation within the same task execution context. Attacker cost is low (just push a `shipit.yml` to their own fork/branch), but full end-to-end triggering (getting an HTTPS git credential prompt to fire mid-task after the attacker's askpass script is written) was not fully traced/confirmed within available context — this remains a structural weakness confirmed at the merge-order level, but exact exploitation timing/ordering needs runtime verification.

### Recommendation
In `TaskCommands#env` (and any other `Commands` subclass merging `deploy_spec.machine_env`), filter `deploy_spec.machine_env` through an explicit deny-list/allow-list before merging — e.g. reject any keys present in `Commands#base_env`/reserved keys (`GITHUB_TOKEN`, `GIT_ASKPASS`, `GITHUB_DOMAIN`), or reverse the merge order so `machine_env` is merged first and trusted keys are applied last and cannot be overridden.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES

      self
    end
