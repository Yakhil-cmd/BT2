### Title
Permanent address bricking via unsatisfiable `address_definition_change` payload — ([File: validation.js])

### Summary
Ocore addresses can rewrite their own spending condition ("definition") via an `address_definition_change` message. Similar to the HOPR Safe `guard`, the *new* definition takes exclusive control of the address, and any *future* change (including one intended to undo a mistake) must itself be authorized under the currently-active definition. If a signer sets a new definition that can never be satisfied, the address (and all funds/assets controlled by it) is permanently and irreversibly frozen, exactly mirroring the "broken guard bricks Safe" bug class: a single authorized action installs a self-referential gatekeeper that blocks its own repair path.

### Finding Description
`address_definition_change` messages are accepted with only syntactic checks — the payload’s `definition_chash` merely has to look like a valid address/chash; there is no semantic check that the *new* definition is ever satisfiable: [1](#0-0) 

The chash of the new definition is recorded, and it becomes effective going forward: [2](#0-1) 

Crucially, every unit signed by the address — including any subsequent `address_definition_change` meant to fix a bad definition — must pass `validateAuthentifiers()` against the *currently active* definition: [3](#0-2) [4](#0-3) 

The code base is aware that redefinition can render an address non-functional, but frames it as merely "temporary": [5](#0-4) 

That "temporary" assumption only holds if the new definition is well-formed and eventually satisfiable (e.g., a valid keyset that just hasn't disclosed its definition yet). Nothing in `validateDefinition()` (the structural checker for `sig`/`hash`/`and`/`or`/`not`/etc. op trees) proves logical satisfiability of the tree — e.g. a mis-typed `pubkey`, a `hash` whose preimage nobody holds, a self-referential `address` op, or an always-failing boolean combination will validate structurally yet never be satisfiable by any authentifier set. Once such a definition is installed via `address_definition_change`, there is no privileged/recovery path in ocore analogous to a "module" bypassing the guard — every future author signature on that address (including one attempting to install yet another `address_definition_change`) is evaluated against this now-permanently-broken definition and will fail, exactly like the `Safe.execTransaction()` guard check reverting for every path except pre-authorized modules, except ocore's design has no module-equivalent bypass at all.

This is functionally identical to the HOPR finding: a single authorized entity (there: signer at Safe threshold=1; here: whoever currently controls the definition, which for shared/multi-sig addresses backed by `wallet_defined_by_addresses.js` can require as little as one signature depending on the definition's `and`/`or`/threshold structure) can — by mistake or maliciously — install a "guard" (the new definition) that revokes the very authority needed to undo it.

### Impact Explanation
Any funds, assets, or AA balances controlled by the affected address become permanently unspendable/frozen — a direct "AA fund loss or freezing" / user-fund-freezing outcome. Because `address_definition_change` is available to any address (personal, shared/multi-sig, or an address used as an AA's counterpart in module-like patterns), the blast radius extends to any wallet using this ocore primitive, not just a niche configuration.

### Likelihood Explanation
No special privilege beyond being an authorized signer of the address's *current* definition is needed — an unprivileged unit poster acting on their own address, or one signer in a multi-sig/shared-address setup whose combination of authentifiers currently satisfies the definition, can trigger this. It can happen accidentally (typo in `pubkey`/`hash`, unintended `and` of unrelated conditions) or maliciously (a compromised or rogue co-signer intentionally installs a definition they know is unsatisfiable, e.g. referencing a `hash` with no known preimage), paralleling the "accidental" vs. "malicious signer" scenarios in the original report.

### Recommendation
- Before committing an `address_definition_change`, attempt to determine whether the proposed definition tree contains any authentifiable path at all under realistic assumptions (e.g., disallow definitions whose top-level boolean structure can be statically proven unsatisfiable, or that reference nonexistent/foreign authentifier types without any `sig`/`hash` leaf reachable by the changer).
- Consider requiring that a definition change be accompanied by a proof/demo signature set that would satisfy the *new* definition (i.e., validate the new definition is satisfiable by the party proposing it) before accepting the change as final.
- For shared/multi-sig addresses created via `wallet_defined_by_addresses.js`, warn or block definitions where a single signing path (or subset below full consensus) can unilaterally install a replacement definition that excludes the other cosigners' ability to ever change it back.

### Proof of Concept
1. Create address `A` with definition `['sig', {pubkey: P1}]` (single key).
2. The holder of `P1` posts a unit containing `address_definition_change` with a new `definition_chash` computed from a definition such as `['sig', {pubkey: '<garbage-base64-that-is-not-a-valid-point>'}]` or `['hash', {hash: '<some-hash-nobody-can-preimage>'}]`.
3. `validateInlinePayload()` accepts the change because it only checks that `definition_chash` is a syntactically valid chash — it never attempts to verify the new definition is satisfiable (see `validation.js:1719-1746`).
4. Once stable, any future unit from address `A` — including one attempting to submit a corrective `address_definition_change` — must satisfy the new, broken definition through `Definition.validateAuthentifiers()` (`validation.js:1243-1254`, `definition.js:1443-1465`), which will always fail (bad signature / unsolvable hash), permanently freezing every asset held at `A`.
