### Title
No vulnerability found for this question.

### Summary
The behavior described — an old proof for a block still within `BlockToRoot`'s retained window being usable even after revocation on the relay chain at a later block — is a documented, intentional design characteristic of the `pallet-remote-proxy`, not a missing check or logic flaw.

### Finding Description
`Pallet::do_remote_proxy` looks up the storage root for the exact `block` number specified in `RemoteProxyProof::RelayChain { proof, block }` via a `binary_search_by` against `BlockToRoot`, which retains up to `MaxStorageRootsToKeep` recent relay block-to-root mappings. [1](#0-0)  If the requested `block` is still present in that bounded window, the proof is verified against the corresponding historical storage root, and if the trie proof resolves to a valid `ProxyDefinition` matching the caller, the call succeeds — regardless of whether the relay chain has since revoked that proxy in a later block. [2](#0-1) 

This is explicitly called out in the pallet's module documentation: "when configuring `MaxStorageRootsToKeep` it should be considered that the lifetime of a proxy will be `MaxStorageRootsToKeep` in the past... The reason for this is that the caller will be able to provide an old `proof` at which the proxy was still available." [3](#0-2)  The pallet author explicitly acknowledges the replay-of-stale-but-once-valid-proof behavior as a known consequence of the design, bounded deterministically by `MaxStorageRootsToKeep`.

### Impact Explanation
Not applicable — this is documented, intended behavior with a bounded worst-case window (`MaxStorageRootsToKeep`), not an unbounded or unintended state transition.

### Likelihood Explanation
Not applicable in the sense of an unforeseen bug; the window is explicit and bounded by configuration, and the runtime integrators are informed via doc comments to size `MaxStorageRootsToKeep` accordingly. There is no missing freshness check being bypassed — the freshness bound *is* `MaxStorageRootsToKeep`, by design.

### Recommendation
Not applicable — no code change is warranted for this specific claim, since the pallet's docs already instruct integrators that `MaxStorageRootsToKeep` bounds the reusability window of an old proof and that this must be considered when configuring the pallet. If tighter freshness guarantees are desired, that would be a design change (e.g., requiring monotonically increasing "latest known good" block acceptance) rather than a bug fix, and is out of scope for this audit.

### Proof of Concept
Not applicable — `pallets/remote-proxy/src/tests.rs::remote_proxy_works` already demonstrates that proofs anchored to blocks outside the retained `BlockToRoot` window are rejected with `Error::UnknownProofAnchorBlock` [4](#0-3) , confirming the freshness boundary is exactly `MaxStorageRootsToKeep`, as documented, and not bypassable beyond that documented window.
