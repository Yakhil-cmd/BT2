Confirmed: this codebase has a design where L1-locked bonds (`is-l1-lock: true`) contribute their `sats-total` to `protocol-bonds-total-staked` (via `get-total-shares-staked-for-cycle`) without ever moving actual sBTC into the pox-5 contract's sBTC balance — `new-sbtc` is explicitly set to `u0` on the L1 path [1](#0-0) , and `roll-sbtc tx-sender old-sbtc new-sbtc` is called with `new-sbtc = 0` for L1 lockups [2](#0-1) . Meanwhile `get-rewards` computes the distributable pool as `current-balance - total-staked-sbtc - cur-reserve`, where `current-balance` is the contract's live sBTC token balance read via `contract-call? sbtc-token get-balance` [3](#0-2) .

### Title
Bond target-yield payouts computed from `total-sats` that are never backed by custodied sBTC allow signer/staker reward theft from the shared pool - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`calculate-bond-rewards` pays each active bond `target-yield = total-sats * target-rate / 10000 / 50`, where `total-sats` is `get-total-shares-staked-for-cycle` for that bond [4](#0-3) . For L1-lock bond registrations, `sats-total` is added to `protocol-bonds-total-staked` [5](#0-4)  and to per-cycle bond shares via `add-staker-to-bond-cycles` [6](#0-5) , but no sBTC is ever transferred into the contract for that membership (`new-sbtc` is `u0` on the L1 path, and `roll-sbtc` moves 0 sats) [1](#0-0) [2](#0-1) .

### Finding Description
This mirrors the ElasticSwap bug class: a distribution/valuation formula mixes an internally-tracked size (`total-sats`, used to size a payout) with an externally-verifiable but economically-unbacked quantity, letting a party inflate their claim on a shared pool relative to their actual contribution. Concretely, `get-rewards` = `sbtc-token.get-balance(pox-5) - total-staked-sbtc - reserve-balance` is meant to represent sBTC that has arrived as *rewards* (e.g., signer earnings deposited by miners/protocol) net of principal custodied for bond stakers. But `total-staked-sbtc`/`total-sats` is populated identically for both (a) L2 bonds, where `sats-total` sBTC really was pulled into custody via `roll-sbtc`, and (b) L1 bonds, where `sats-total` is merely a self-reported/proven amount of *Bitcoin* locked off-chain — no sBTC ever enters the pox-5 contract for that portion. Since `calculate-bond-rewards` uses this same `total-sats` figure to size the bond's *target-yield* claim on the shared `gross-accrued-rewards` pool [7](#0-6) , an L1-locked bond earns yield proportional to its claimed sats even though it contributed zero sBTC principal risk/custody to the contract, at the expense of the shared reward pool (which is otherwise meant to be funded by external protocol sBTC deposits per `FundRewards`/`get-new-rewards` semantics) [8](#0-7) .

The equality broken: reward payout should be proportional to sBTC value actually locked/custodied by the protocol for that bond; instead it is proportional to a self-attested sats figure that, for the L1 path, is never backed by sBTC held by pox-5.

### Impact Explanation
This falls under "High: signing weight or reward slots exceeding locked value" — an L1 bond's `total-sats` contributes to the reward-yield calculation identically to an L2 (real-custody) bond, so the L1 bond receives sBTC rewards disproportionate to any sBTC actually secured in the contract, diluting the payouts that legitimately-custodied (L2) bonds and stx-only stakers would otherwise receive from the same `gross-accrued-rewards` pool.

### Likelihood Explanation
Uncertain/low confidence: this requires that the L1 lockup path (native Bitcoin timelock verified via merkle proof) is intended by design to be equivalent in reward-earning power to an actual sBTC-custody bond — if that equivalence is an intentional design decision (i.e., the protocol explicitly wants to reward native BTC-locked bonds the same as sBTC-custodied bonds because both represent locked BTC value backing signers), then this is not a bug but expected tokenomics. I was not able to fully verify from the available code/tests whether the reward pool (`gross-accrued-rewards`) is sized/funded with the expectation that L1-bond obligations are already "priced in" externally (e.g., minted separately per L1 lock) or whether it's a shared pool funded independently of L1 vs L2 composition. Given this ambiguity and that it does not clearly demonstrate a call sequence an unprivileged attacker can use to unilaterally break an equality beyond what bond setup/allowlisting (admin-gated) already permits, I cannot confirm this as a concrete, admin-independent exploit within the stated scope with high confidence.

### Recommendation
Clarify and, if unintended, separate the reward-accrual accounting so `total-sats` used in `calculate-bond-rewards`'s target-yield formula only reflects sats value actually custodied as sBTC by the contract (or maintain a distinct `total-l1-sats`/`total-l2-sats` split with different reward treatment), rather than a single unified counter (`protocol-bonds-total-staked`) that comingles proven-but-uncustodied L1 BTC lockups with actual on-contract sBTC custody used in `get-rewards`'s principal subtraction.

### Proof of Concept
Not established with certainty — flagging as an analog worth verifying rather than a confirmed exploit, given the uncertainty above about whether L1/L2 bonds are intentionally meant to earn identical yield rates.
