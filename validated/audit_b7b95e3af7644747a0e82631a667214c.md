### Title
Session fixation on GitHub OAuth callback allows forced-login session hijacking - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` writes the freshly authenticated user's identity directly into the existing session (`session[:user_id]`, `session[:authenticated]`) without first calling `reset_session`. `#logout` does call `reset_session`, but `#callback` — the point where privilege actually changes from anonymous to authenticated — does not. This breaks the binding: "the GitHub identity that authenticated == the session the server hands back to the browser" should imply a session created/rotated specifically for that authenticated identity, not a session ID that could have been chosen or observed prior to authentication.

### Finding Description
The OAuth callback flow is:
1. Omniauth completes the GitHub handshake and populates `request.env['omniauth.auth']`.
2. `sign_in_github(auth)` resolves/creates the `Shipit::User` from `auth.extra.raw_info` [1](#0-0) .
3. The controller sets `session[:user_id]` and `session[:authenticated] = true` on the **existing** Rails session, then redirects [2](#0-1) .

No `reset_session` (or `request.session.exclude?` / cookie rotation) precedes this write. Compare with `#logout`, which explicitly calls `reset_session` on logout [3](#0-2) . This asymmetry is the root cause: de-authentication rotates state, but authentication does not.

Because Rails' cookie/session middleware only issues a new session identifier when `reset_session` is called (or when the store is configured to rotate on every request, which is not the case here — session store is the standard cookie/ActionDispatch session store per `test/dummy/config/initializers/session_store.rb`), an attacker who can get a victim's browser to use a session ID chosen (or known) before authentication will find that session promoted to "authenticated" status after the victim completes the real GitHub OAuth login. This is the classic session-fixation pattern, and it maps directly onto the report's "rug vector": the entity that is cryptographically verified (GitHub identity via OAuth) is not the same entity the binding is actually keyed on (the pre-existing session cookie), and the mismatch is exploitable by an unprivileged attacker with no credentials of their own.

### Impact Explanation
This falls under the engine's own explicitly listed High-impact category: "session fixation / forced OAuth completion." A successful fixation lets the attacker access the application as the victim once the victim completes GitHub login — i.e. unauthenticated read/write of stack state, triggering deploys/rollbacks/merges, and viewing task output/streams, all under the victim's authorization level. It does not require any pre-existing Shipit session, ApiClient token, webhook secret, or repository access from the attacker — only that the attacker can plant a session identifier in the victim's browser before the OAuth completion (e.g., via a shared/cached cookie jar, a session ID accepted from a URL/query parameter by the underlying session middleware, or a network position that can set cookies for the app's domain before the login completes).

### Likelihood Explanation
Medium-to-High as an analog: the code path is unconditionally reachable by any user going through the (public, credential-free) `/callback` route, and the missing `reset_session` is a straightforward, provable omission by direct comparison with `#logout` in the same file. Real-world exploitability depends on how the host application allows an attacker to fixate a session ID before OAuth completion (e.g., cookie scoping, shared subdomains, or a session store that accepts attacker-supplied IDs) — a factor of the surrounding Rails app/session configuration rather than this engine, but the engine-side vulnerability (failing to rotate the session on privilege elevation) is unambiguous and squarely in scope (`app/controllers/shipit/github_authentication_controller.rb`).

### Recommendation
Call `reset_session` (or equivalent session ID rotation, e.g. `request.session_options[:renew] = true` or regenerate via the session store) at the start of `#callback`, before writing `session[:user_id]` and `session[:authenticated]`, mirroring the defensive pattern already used in `#logout`. Preserve `omniauth.origin` (`return_url`) across the reset, since it is read from `request.env` before the session write and is unaffected by `reset_session`.

### Proof of Concept
1. Attacker visits the target Shipit instance without logging in and obtains/plants a session cookie value `S` in the victim's browser (e.g., via a network MITM setting a cookie for the app's domain, a shared computer, or an app-level session-fixation primitive such as a session ID accepted from a request parameter by the underlying session store).
2. Attacker lures the victim (who already has session cookie `S` set) into visiting `/auth/github` and completing the GitHub OAuth login flow normally.
3. `GithubAuthenticationController#callback` fires: it resolves the victim's GitHub identity and does `session[:user_id] = sign_in_github(auth); session[:authenticated] = true` on the *same* session `S` — no `reset_session` occurs [4](#0-3) .
4. Attacker, still holding session cookie `S`, now sends requests to the Shipit instance and is treated as the authenticated victim, since `session[:user_id]`/`session[:authenticated]` under `S` now point at the victim's `User` record.

Note: I could not fully verify from the indexed code how the host session store/cookie configuration is set in production deployments (only the test dummy config was available: `test/dummy/config/initializers/session_store.rb`), so the exact fixation delivery mechanism (cookie scoping vs. parameter-based session IDs) depends on deployment specifics outside this engine's own code; the in-scope, provable defect is the missing session rotation in `#callback` itself.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
