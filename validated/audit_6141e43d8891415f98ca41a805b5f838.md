### Title
CCMenu endpoint bypasses `ApiClient#stack_id` scoping, letting a token authorized for one stack read task/deploy state of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
Every `Shipit::Api::BaseController` subclass is expected to resolve the current stack through the `stacks`/`stack` helpers, which restrict the visible `Stack` set to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a single stack. `CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, which resolves *any* stack in the system, entirely ignoring the client's `stack_id` scope.

### Finding Description
`BaseController#stacks` and `BaseController#stack` enforce the authorization binding "the set of stacks a token authorizes == the set of stacks it can touch": [1](#0-0) 

`CCMenuController` is the only controller under `app/controllers/shipit/api/` that redefines `stack` instead of using the inherited scoped helper, resolving the stack directly against the global `Stack` relation: [2](#0-1) 

All sibling controllers (`TasksController`, `DeploysController`, `RollbacksController`, `LocksController`, `OutputsController`, `MergeRequestsController`, `ReleaseStatusesController`, `CommitsController`) rely exclusively on the scoped `stack`/`stacks` from `BaseController`, e.g.: [3](#0-2) 

Before the attacker's request: an `ApiClient` created with `stack: my_stack` (e.g. via `Api::StacksController` create flow, or the built-in `CCMenuUrlController` which explicitly scopes tokens to `read:stack` and a single stack: `app/controllers/shipit/ccmenu_url_controller.rb:15-18`) can only see `Stack.where(id: current_api_client.stack_id)` through every other endpoint (`stacks` in `base_controller.rb:74-76`).

After the attacker's request: hitting `GET /api/stacks/:stack_id/ccmenu.xml?token=<their own stack-scoped token>` with an arbitrary `stack_id` for a *different* stack returns that other stack's deploy/rollback history (`stack.deploys_and_rollbacks.last`) rendered via the `shipit/ccmenu/project` view, because `CCMenuController#stack` never checks `current_api_client.stack_id`.

Root cause equality broken: `{stacks visible to token} == {id: current_api_client.stack_id}` holds everywhere except `CCMenuController`, where it degrades to `{stacks visible to token} == Stack.all`.

### Impact Explanation
This is an unauthenticated-read-scope escalation: a token deliberately minted with `read:stack` permission and pinned to a single stack (the exact use case the built-in `CCMenuUrlController` implements) can be used to read the task/deploy status of any stack in the Shipit instance, including private/internal repositories the token's creator was never granted access to. This matches the "unauthenticated read of stack state, task streams or deploy output" High-impact category, since the effective authorization boundary (`stack_id` binding on the `ApiClient`) is bypassed.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token (which is explicitly designed to be low-privilege and is even exposed client-side via `CCMenuUrlController#fetch`, embedding the token in a URL) can trivially exploit this by changing the `stack_id` in the URL path — no additional credentials, GitHub identity, or elevated permission are required.

### Recommendation
Change `Api::CcmenuController#stack` to reuse the inherited, scoped `stacks` collection from `BaseController` instead of calling `Stack.from_param!` against the unscoped `Stack` relation, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so the `stack_id` binding on `ApiClient` is enforced consistently with every other API endpoint.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_a` with `permissions: ['read:stack']` and `stack: stack_a` (as `CCMenuUrlController#client` does).
2. As the holder of that token, request `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` where `stack_b` is a different, unrelated stack.
3. Observe that `CCMenuController#stack` resolves `stack_b` via `Stack.from_param!(params[:stack_id])` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) with no `stack_id` check, and the response renders `stack_b`'s latest deploy/rollback status — despite the token only being authorized for `stack_a`.
