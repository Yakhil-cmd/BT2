### Title
Global, repository-unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a webhook signed by one organization's secret write a GitHub status onto a commit belonging to a completely different organization's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the request body was signed by *some* configured `GitHubApp`'s `webhook_secret`, selected by the `repository.owner.login`/`organization.login` value in the attacker-controlled JSON payload. Unlike `CheckSuiteHandler`, which scopes its work through `stacks` (derived from `repository.full_name`), `StatusHandler#process` runs `Commit.where(sha: params.sha)` against the entire `commits` table with no repository/stack filter, so any commit anywhere in Shipit whose SHA matches the attacker-chosen value gets a status written, regardless of which organization's key signed the request.

### Finding Description
The broken binding, stated explicitly: `organization_that_signed(payload) == organization_owning(Commit.find_by(sha: payload.sha).stack)` is asserted implicitly by the design but never enforced in code — the two sides are computed independently and never compared.

Trace:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` from `params.dig('repository','owner','login')` — attacker-controlled body content — and calls `Shipit.github(organization: repository_owner)` to pick the `GitHubApp`, then verifies HMAC over the raw body with that org's `webhook_secret`. This only proves "org C's key signed this body"; it says nothing about which commit row the handler will touch. [1](#0-0) 
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query across all stacks/organizations. [2](#0-1) 
- Contrast with `CheckSuiteHandler#process`, which correctly restricts the mutation to stacks belonging to the repository named in the payload via the shared `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) before touching any commit. [3](#0-2) [4](#0-3) 

Exploit flow: Attacker owns org C and registers a `GithubApp`/webhook secret for their own org in Shipit (a legitimate, unprivileged configuration act any GitHub org owner can do). Git commit SHA1s are content-addressed, not globally namespaced by repository — an attacker can copy the exact tree/parents/author/committer/timestamps/message of a real, public commit that already exists in org A's Shipit-tracked repository (created earlier by `GithubSyncJob`/push events) to reproduce an identical SHA under their own org C repository, or simply reuse a SHA they already know is present in org A's `commits` table. They then send `POST /webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login` is `org-c` and `sha` equal to org A's existing commit SHA, and a valid `X-Hub-Signature` computed with org C's own `webhook_secret`. `verify_signature` succeeds (org C's secret matches org C's own signed body). `StatusHandler#process` then finds and mutates org A's `Commit` row, creating an attacker-controlled `Status` (e.g., forged `"success"` state, arbitrary `context`/`description`/`target_url`) on a commit belonging to a stack the attacker has no relationship to.

None of the listed guards prevent this: `verify_signature` authenticates provenance of the *body*, not the *target row*; `drop_unhandled_event` only filters unknown event types; `ExplicitParameters` only validates payload shape (`sha` is `String`); there is no `force_github_authentication`/`User#authorized?`/`require_permission!` check in this unauthenticated webhook path; `Repository`/`Stack` model validators don't run at read time; `stacks` scoping exists in `Handler` but `StatusHandler` simply doesn't use it.

### Impact Explanation
Statuses feed directly into deploy-readiness logic: `Stack#branch_status`/`merge_status` iterate `undeployed_commits` and their `status.simple_state`, and required/blocking status checks gate whether a stack is considered mergeable/deployable. [5](#0-4) 
An attacker who registers their own org C app can inject an arbitrary CI status onto any commit in any other organization's Shipit-tracked stack whose SHA they can reproduce or already know, without ever authenticating against org A's or org B's secret. This is a payload for one repository (org C) mutating another organization's commit/stack state — squarely the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against arbitrary commits/stacks across every tenant hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker only needs (a) their own GitHub org/account with a Shipit `GithubApp` registered for it (self-service, unprivileged) and (b) knowledge of a target SHA already present in another org's `commits` table (trivially discoverable — Shipit stack/commit pages expose SHAs, or the attacker can compute it by replicating a public commit's exact metadata since GitHub commits from public repos are visible to anyone). No secrets belonging to org A/B, no session, no API token, and no `Shipit.github_teams` membership are required. This is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
Scope `StatusHandler#process` through the same repository-derived `stacks` helper used elsewhere (e.g., resolve `stacks` from `payload.dig('repository','full_name')`, then `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent join), so a verified webhook can only mutate commits belonging to stacks under the repository/organization that actually signed the request.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create three `GithubApp`/org fixtures: `org_a`, `org_b`, `org_c`, each with a distinct `webhook_secret`.
2. Create `Stack`/`Repository` fixtures for `org_a` (`org-a/repo-a`) and `org_c` (`org-c/repo-c`), and a `Commit` under `org_a`'s stack with `sha: "deadbeef..."`.
3. Build a status webhook JSON body with `repository.owner.login == "org-c"`, `repository.full_name == "org-c/repo-c"`, `sha == "deadbeef..."` (the org A commit's SHA), `state: "success"`.
4. Sign the raw body with `org_c`'s `webhook_secret` and set `X-Hub-Signature`.
5. `assert_difference -> { shipit_commits(:org_a_commit).statuses.count }, 1 do post :create, body: body, as: :json end` — assert the request returns `:ok` and a `Status` row is created on **org A's** commit even though only **org C's** secret verified the request, demonstrating `organization_that_signed != organization_owning_commit`.
