## Title
Fork PR author's `machine.environment` in `shipit.yml` is merged unfiltered into `PTY.spawn` env for `ruby`/`bundle` dependency-install steps under `allow_all` review stacks - ([File: app/models/shipit/deploy_spec.rb])

## Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim with no allow-list, unlike `deploy_variables`/`rollback_variables`/task `variables` which are always passed through `EnvironmentVariables#permit`. `TaskCommands#env` merges this unfiltered hash into the environment used by `Command.new`, which `Command#start` feeds straight into `PTY.spawn`. For an `allow_all` review-stack repository, the fork PR author's branch is checked out and its `shipit.yml` is read by `DeploySpec::FileSystem`, so the PR author fully controls `machine.environment`, including keys like `DYLD_INSERT_LIBRARIES`.

## Finding Description
The broken invariant is the implicit claim that `TaskCommands#env`'s process environment is restricted the same way user-facing `deploy`/`rollback`/task variables are (i.e., `env == filter(env, whitelist)`). In reality:

- `DeploySpec#machine_env` at [1](#0-0)  returns `config('machine', 'environment') || {}` with no filtering.
- `TaskCommands#env` merges it directly: [2](#0-1) .
- Contrast this with `filter_deploy_envs`/`filter_rollback_envs`, which explicitly call `EnvironmentVariables.with(env).permit(...)` against a whitelist defined in `shipit.yml`'s `deploy.variables`/`rollback.variables`: [3](#0-2) . `EnvironmentVariables#permit` raises `NotPermitted` for any non-whitelisted key [4](#0-3) , but this guard is never applied to `machine_env`.
- `Command#start` passes the merged env straight to `PTY.spawn`, only merging on top of the unbundled base env and `PATH`: [5](#0-4) .
- `install_dependencies` builds the `bundle`/`ruby` dependency command with this same `env`: [6](#0-5) , and `BundlerDiscovery` auto-discovers `bundle install` for repos with a `Gemfile` [7](#0-6) .
- For review stacks under `allow_all`, `OpenedHandler` creates a `ReviewStack` whose `branch` is taken directly from the attacker-controlled `pull_request.head.ref` via `ReviewStackAdapter#stack_attributes`: [8](#0-7) , gated only by `provisioning_behavior_allow_all?` [9](#0-8) . `DeploySpec::FileSystem` then loads `shipit.yml` from that checked-out branch (the PR author's fork content), and `machine.environment` from that file becomes `machine_env`.

Exploit flow: an unprivileged GitHub user opens a PR against an `allow_all`-configured repository with a `shipit.yml` containing:
```yaml
machine:
  environment:
    DYLD_INSERT_LIBRARIES: /path/to/attacker.dylib
```
When the review stack task runs `install_dependencies` (auto-detected `bundle install`/ruby invocation), `DYLD_INSERT_LIBRARIES` is present in the env passed to `PTY.spawn`, and on a macOS deploy host the dynamic loader preloads the attacker's dylib into the `ruby`/`bundle` process, giving code execution in the context of the Shipit deploy host user.

No existing guard closes this: `verify_signature`/webhook auth only gates that the webhook is genuinely from GitHub, not what's inside the PR's file content; `EnvironmentVariables#permit`/whitelist mechanisms exist for `deploy.variables`, `rollback.variables`, and task `variables`, but are never applied to `machine.environment`; `machine_env` is documented in `README.md` as attacker-configurable content by design (the feature intentionally lets the repo's `shipit.yml` set arbitrary env vars) — meaning this is largely a feature/trust-boundary issue rather than a broken filter, but it is real code-execution-relevant behavior specific to `allow_all` review stacks where the "repo" content is attacker-supplied.

## Impact Explanation
If exploitable on the deploy host's OS (macOS, given `DYLD_INSERT_LIBRARIES`), this results in arbitrary code execution in the process running `bundle install`/ruby dependency steps, under the Shipit deploy host's user account — a Critical RCE per the target's own severity classification. It is repeatable against any repository configured with `provisioning_behavior: allow_all` and review stacks enabled, and blast radius is limited to stacks/deploy hosts of that specific repository's task execution context (shared host state, secrets in the process environment, etc., are all exposed to the injected dylib).

## Likelihood Explanation
Preconditions are non-trivial but realistic: (1) the target repository must have `review_stacks_enabled` and `provisioning_behavior` set to `allow_all` (an operator-chosen config, explicitly documented as "ALL Pull Requests dynamically provision stacks"), and (2) the Shipit deploy/task-execution host must run on macOS (or another OS honoring the specific loader-preload variable used) for the dylib injection to actually execute. `machine.environment` being attacker-controllable in `shipit.yml` is intentional/documented behavior of the review-stacks + `allow_all` feature — the README explicitly states "All the content of the `shipit.yml` `machine.environment` key" becomes script env vars. This is a known/accepted trust model: `allow_all` review stacks execute arbitrary attacker-supplied shell commands (`dependencies.override`, `deploy.override`, etc.) from the PR's `shipit.yml` on the deploy host by design — injecting env vars is a strictly weaker capability than the already-inherent ability to run arbitrary shell steps that `allow_all` grants. Given the operator already accepts "PR author's `shipit.yml` runs arbitrary commands on the deploy host" as the operating model for `allow_all`, this specific env-var vector doesn't introduce a new privilege boundary crossing beyond what `allow_all` already grants.

## Recommendation
This is not a distinct code-level bug beyond the accepted `allow_all` threat model, but if tightened: (1) apply an explicit allow-list (similar to `EnvironmentVariables#permit`) to `machine.environment` keys, rejecting dangerous loader/interpreter variables (`DYLD_INSERT_LIBRARIES`, `LD_PRELOAD`, `RUBYOPT`, etc.) by default; (2) strip such variables in `Command#unbundled_env`/`BASE_ENV` construction regardless of source; (3) document clearly to operators that `allow_all` is equivalent to granting arbitrary command execution to any PR author and should only be used for trusted contributors.

## Proof of Concept
Not applicable as a standalone vulnerability distinct from the intended `allow_all` design — see Likelihood Explanation. If desired for documentation purposes, a minitest could assert:
```ruby
test "[allow_all] machine.environment DYLD_INSERT_LIBRARIES reaches install_dependencies command env" do
  stack = shipit_stacks(:review_stack) # branch = attacker-controlled fork ref
  DeploySpec::FileSystem.any_instance.stubs(:machine_env).returns('DYLD_INSERT_LIBRARIES' => '/tmp/evil.dylib')
  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  command = Shipit::TaskCommands.new(task).install_dependencies.first
  assert_equal '/tmp/evil.dylib', command.env['DYLD_INSERT_LIBRARIES']
end
```
This confirms the equality `command.env['DYLD_INSERT_LIBRARIES'] == deploy_spec.machine_env['DYLD_INSERT_LIBRARIES']` holds unfiltered, matching the described code path, but does not by itself demonstrate a boundary violation beyond what `allow_all` already permits (arbitrary shell command execution via `dependencies.override`/`deploy.override`).

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
