### Title
`Team.find_or_create_by!(github_id:)` in `MembershipHandler#process` grants trusted-team `Membership` without re-validating the reporting organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, and the `find_or_create_by!` block that sets `team.organization` only executes on the creation path, never on the found path. [1](#0-0)  If a `Team` row with a matching numeric `github_id` already exists for a different, currently-trusted organization referenced in `Shipit.github_teams`, `team.add_member(member)` inserts a `Membership` for that trusted `Team` regardless of which organization actually reported the event. [2](#0-1)  `User#authorized?` then treats this membership as sufficient for access. [3](#0-2) 

### Finding Description
Binding claimed: `Membership` row for a team in `Shipit.github_teams` == a membership GitHub *currently* reports for that team. Traced code shows this binding is not enforced.

- `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }`. [1](#0-0)  The block only runs when ActiveRecord creates a *new* record; if a `Team` row already exists with that `github_id`, the block never executes, so the pre-existing `organization`/`slug`/`name` on the found row are left untouched even though the *current* payload's organization differs.
- `Team#add_member` performs no organization check at all: `members.append(member) unless members.include?(member)`. [4](#0-3) 
- `User#authorized?` grants access purely by `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, i.e., by the local `Team` primary key being in the configured trusted set — it has no dependency on the team's `organization` field being current. [3](#0-2) 

Signature verification is per-organization: `WebhooksController#verify_signature` selects the `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`, where for `membership` events `repository_owner` falls back to `params.dig('organization','login')`. [5](#0-4)  In a multi-organization deployment, `Shipit.github` resolves a distinct config (and `webhook_secret`) per configured organization key via `github_app_config`, raising `GithubOrganizationUnknown` for orgs Shipit doesn't know about. [6](#0-5)  This means the attacker's own organization must be one of the multi-tenant orgs configured in Shipit's `github:` secrets (as documented for "Using Multiple GitHub Applications"), and the resulting webhook will carry a genuinely valid HMAC signature for that org — the signature check does not, and cannot, verify that `params.team.id` actually still belongs to the organization asserted in the payload.

Given the premise stipulated in the question (a stale `Team` row retaining a previously-assigned/reused `github_id` for a currently-trusted organization, and the attacker's own distinct organization has a live `membership` webhook targeting the same Shipit host), the attacker's genuine GitHub organization membership addition produces a validly signed `membership`/`added` webhook with `team.id` equal to the stale trusted id. `find_or_create_team!` returns the stale trusted `Team` row unmodified, and `add_member` inserts the attacker into it, flipping `authorized?` to true without any live reconciliation against GitHub's current team roster or organization ownership.

None of the existing guards prevent this: `verify_signature` only proves the payload came from *some* organization Shipit trusts enough to have a webhook secret for — it says nothing about whether the `team.id` inside the payload is still owned by that organization. `drop_unhandled_event`/`ExplicitParameters` schema only validate shape/types, not cross-organization consistency. `force_github_authentication`/`require_permission!` are unrelated to this ingestion path.

### Impact Explanation
The attacker gains a `Membership` row on a `Team` that is part of `Shipit.github_teams`, which is used exclusively for authorization gating across the entire Shipit instance (`force_github_authentication`, `User#authorized?`). [7](#0-6)  Once `authorized?` is true, the attacker gains full application access as a logged-in Shipit user — able to view/trigger stacks, deploys, and tasks across all repositories managed by the instance, not scoped to their own organization. This matches the "escalation into `Shipit.github_teams` authorization" High-impact category. The action is repeatable for any stale/colliding `github_id` and is not limited to one repository — it compromises tenant isolation in multi-organization Shipit deployments.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment where more than one GitHub organization's webhooks feed the same Shipit host, (2) an existing local `Team` row whose `github_id` was assigned to a now-different GitHub team (via ID reuse/migration or a prior stale record never cleaned up), (3) that stale row's organization still listed in `Shipit.github_teams`, and (4) the attacker's own (different, trusted-by-Shipit-config) organization having a live `membership` hook. Preconditions 2 is unusual under normal GitHub ID allocation but is exactly the scenario the audit question stipulates as a given; the code contains no defense against it regardless of how it arises (e.g., could also occur via manual `Team` fixture edits, migrations, or admin error). No secrets are needed beyond what the attacker's own legitimate organization membership already grants them (a genuine `membership`/`added` GitHub event is emitted automatically when they're added to any team in their org).

### Recommendation
Scope the team lookup/creation and the add/remove operations by both `github_id` and `organization` (and ideally `slug`), e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and update `organization`/`name`/`slug` unconditionally on every event (not only on creation). Additionally, treat an organization mismatch on a found record as a hard error (raise/log and drop the event) rather than silently reusing the stale row, and consider revalidating team membership against the GitHub API before trusting `added` events for teams already tied to `Shipit.github_teams`.

```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership event with a github_id collision does not grant trusted-team membership across organizations" do
  trusted_team = Shipit::Team.create!(github_id: 42, organization: 'trusted-org', slug: 'core', name: 'Core')
  Shipit.stubs(:github_teams).returns([trusted_team])

  attacker = Shipit::User.find_or_create_by_login!('attacker')

  payload = {
    action: 'added',
    team: { id: 42, name: 'Evil Team', slug: 'evil-team', url: 'https://api.github.com/teams/42' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call

  trusted_team.reload
  # Binding under test: organization on the found Team row should equal the reporting org
  assert_equal 'attacker-org', trusted_team.organization  # FAILS: remains 'trusted-org'
  # And membership/authorization should not have been granted for a foreign org's event
  refute trusted_team.members.reload.include?(attacker)   # FAILS: attacker was added
  refute attacker.authorized?                              # FAILS: becomes true
end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
