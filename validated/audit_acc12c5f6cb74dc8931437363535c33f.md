Confirmed: `asset-hub-rococo` has `ForeignAssets`, `PoolAssets`, `Utility`, and `Multisig` pallet instances wired into `construct_runtime!`, and its `ProxyType::NonTransfer` filter does not deny them.

### Title
`ProxyType::NonTransfer` proxy on Asset Hub Rococo fails open, letting a delegate transfer `ForeignAssets`/`PoolAssets` funds - ([File: cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs])

### Summary
`asset-hub-rococo`'s `InstanceFilter<RuntimeCall>` implementation for `ProxyType::NonTransfer` is a deny-list that only excludes `Balances`, `Assets`, `NftFractionalization`, `Nfts`, and `Uniques` [1](#0-0) . It omits `ForeignAssets` and `PoolAssets`, two pallet-assets instances that move a delegator's asset balances exactly like `Assets` does. This is the same bug class as the AlekSIS advisory: a permission/allow-list that "fails open" when a new resource (asset instance, OAuth scope) is added but the enforcement list is not updated, so the missing check silently grants access. The sibling runtime `asset-hub-westend` was patched to add `ForeignAssets`, `PoolAssets`, `AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, etc. to its `NonTransfer` deny-list [2](#0-1) , and `substrate/frame/staking-async/runtimes/parachain/src/lib.rs` documents the exact same fix having been applied there, referencing PR 12922 [3](#0-2) [4](#0-3) . `asset-hub-rococo` was not updated with the same fix.

### Finding Description
A user calls `pallet_proxy::proxy` (or `proxy_announced`) as a delegate holding a `ProxyType::NonTransfer` grant on `asset-hub-rococo`. `do_proxy` builds a filtered origin and calls `def.proxy_type.filter(c)` to decide whether the wrapped call is allowed [5](#0-4) . Because `ProxyType::NonTransfer::filter` on this runtime only pattern-matches `Balances`, `Assets`, `NftFractionalization`, `Nfts`, `Uniques` [1](#0-0) , a `RuntimeCall::ForeignAssets(pallet_assets::Call::transfer{..})` or `RuntimeCall::PoolAssets(pallet_assets::Call::transfer{..})` does not match any excluded arm and the filter evaluates `true`, granting the call. `ForeignAssets` and `PoolAssets` are both configured as live `pallet_assets` instances in this runtime, so the calls are dispatchable and move real balances of the proxied account.

The pallet-proxy documentation makes the intended invariant explicit: `NonTransfer` "can execute any call that does not transfer funds or assets" [6](#0-5) , which is violated for the two omitted instances - directly analogous to `ClientProtectedResourceMixin` allowing "arbitrary scopes if no allowed scopes are specifically set" in the AlekSIS report: a security-relevant enumeration (excluded pallet calls / allowed OAuth scopes) was not kept in sync with the actual set of resources, so the default behavior (allow) applies to unlisted items instead of denying them.

### Impact Explanation
An account holding only a `NonTransfer` proxy grant (a lesser-privileged, non-transfer delegation intended to prevent asset movement) can transfer the proxied account's `ForeignAssets` or `PoolAssets` balances to itself or any address, defeating the entire purpose of the `NonTransfer` restriction and enabling theft of the delegator's foreign/pool asset holdings. This matches the report's CWE-863 (Incorrect Authorization) class and is a Medium-severity access-control bypass, consistent with the severity already assigned to the analogous, already-fixed instance in `staking-async-parachain`/`asset-hub-westend`.

### Likelihood Explanation
High reachability, no privileged role needed: any account can be granted (or can itself grant, if self-controlling a `NonTransfer` proxy for another arrangement) a `NonTransfer` proxy via the standard, permissionless `pallet_proxy::add_proxy` flow, and then dispatch `pallet_proxy::proxy` with a `ForeignAssets`/`PoolAssets` transfer call as the wrapped `RuntimeCall`. The attacker needs only normal signed-extrinsic capability and the two-pallet configuration present in this runtime; no governance, sudo, or additional privilege is required.

### Recommendation
Add `RuntimeCall::ForeignAssets { .. }` and `RuntimeCall::PoolAssets { .. }` (and any other value-moving calls already covered on `asset-hub-westend`, such as `AssetConversion`, `Revive`, `PolkadotXcm`, `Vesting::vested_transfer`, `Indices::transfer`/`force_transfer`) to the `NonTransfer` deny-list in `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs`, mirroring the already-applied fix in `asset-hub-westend` and `staking-async-parachain`. Consider converting deny-list proxy filters to allow-lists, or adding a runtime test that asserts every asset-transferring pallet instance is denied under `NonTransfer`, to prevent this drift when new pallet instances are added.

### Proof of Concept
I was not able to execute a live reproduction (no filesystem/terminal access in this mode). The failed-guard evidence is the direct textual comparison between the unpatched filter match arm on `asset-hub-rococo` [7](#0-6)  and the patched arm on `asset-hub-westend` [8](#0-7) , plus confirmation via `grep_search` that `ForeignAssets`, `PoolAssets`, `Utility`, and `Multisig` are all wired as live pallet instances in `asset-hub-rococo`'s `construct_runtime!`. A minimal integration reproduction would: (1) construct the `asset-hub-rococo` runtime test mock, (2) call `Proxy::add_proxy(delegator, delegate, ProxyType::NonTransfer, 0)`, (3) have `delegate` call `Proxy::proxy(delegator, None, Box::new(RuntimeCall::ForeignAssets(pallet_assets::Call::transfer{ id, target: delegate, amount })))`, and (4) assert the call dispatches successfully and the delegator's `ForeignAssets` balance decreases — this was not run here and is left for the background engineering agent with full repo/test access to confirm empirically.
