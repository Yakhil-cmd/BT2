### Title
Cross-Repository Commit Status Forgery via Globally-Scoped Webhook Handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` binds an inbound webhook to "the organization/app installation that authenticated the request" by deriving `repository_owner` from the payload and checking the signature with that organization's `webhook_secret` [1](#0-0) . However, `StatusHandler#process`, which is dispatched once that check passes, never re-validates that the commit it mutates belongs to the repository/stack that the webhook actually originated from. It performs a *global* lookup by SHA across the entire `commits` table and writes a GitHub-reported CI state onto whatever row matches: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This breaks the binding: `organization authenticated == repository written`.

### Finding Description
`Handler` (the base class all webhook handlers inherit from) already provides a repository-scoping mechanism via `stacks`, which resolves `Repository.from_github_repo_name(repository_name)` using `payload.dig('repository', 'full_name')` [3](#0-2) . `PushHandler` and `CheckSuiteHandler` correctly use this scoped `stacks` relation before touching any commit [4](#0-3) [5](#0-4) .

`StatusHandler`, however, does not use `stacks`/`repository_name` at all — it queries `Commit` globally by `sha` only [6](#0-5) . The controller's `verify_signature` only authenticates *which organization/app installation* sent the payload (via `repository_owner`, itself derived from `params.dig('repository','owner','login')`) [7](#0-6) ; it never constrains which `Commit`/`Stack` row the handler is permitted to mutate. Because git commit SHAs are content-addressed and identical across clones/forks that share history, any commit that exists verbatim in two different repositories tracked by Shipit (e.g., a public upstream repo and a fork, or two repos within the same GitHub organization/app installation) will collide on `sha`. A `status` webhook whose signature is valid for the org that owns Repo X will still cause `Commit.where(sha: ...)` to match — and mutate the CI status of — the identically-shaed commit row that actually belongs to Repo Y's stack, even though the attacker has no access to Repo Y.

### Impact Explanation
Commit CI status (`Status`) records are what Shipit uses to compute a commit's deployability gating. By forging a passing/successful status for a commit that belongs to a stack the attacker does not control, an attacker can flip the deploy-readiness state of a commit in a repository/stack they have no write access to, enabling an authorized-looking deploy to proceed on a commit that never actually passed the real repository's CI. This is a concrete cross-repository write / unauthorized-deploy-enabling primitive achieved purely through a normal, validly-signed webhook from a repository the attacker legitimately controls — no `ApiClient` token, GitHub App private key, or Shipit session is required.

### Likelihood Explanation
Requires: (1) push/commit access to some GitHub repository whose organization has the Shipit GitHub App installed (a low privilege bar — any org member with a personal/fork repo under that org, or any org that shares the same multi-tenant Shipit deployment), and (2) a commit SHA collision with a target commit, trivially achievable by forking/cloning a repo that shares history with the target (the SHA is identical by construction, no cryptographic collision needed). No elevated Shipit privileges, tokens, or secrets are needed — only a normal signed GitHub webhook.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: resolve the target `Stack`/`Repository` via `stacks` (derived from `payload.dig('repository', 'full_name')`) and restrict the `Commit` lookup to commits belonging to that repository's stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, instead of an unscoped, instance-wide `Commit.where(sha:)`.

### Proof of Concept
1. Attacker has push access to `attacker-org/fork-repo`, a fork of `victim-org/victim-repo` (a repo tracked by the same Shipit instance) that shares commit history, so commit `abc123...` exists identically in both.
2. Attacker triggers (or GitHub naturally emits) a `status` webhook for `attacker-org/fork-repo` reporting `sha=abc123..., state=success, context=ci/tests` — correctly signed with `attacker-org`'s installation webhook secret.
3. `WebhooksController#verify_signature` validates the signature for `attacker-org` and passes it to `StatusHandler` [8](#0-7) .
4. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, which also matches the `Commit` row belonging to `victim-org/victim-repo`'s stack, and calls `create_status_from_github!`, marking that victim commit as CI-passing even though the attacker never had access to `victim-org/victim-repo` [2](#0-1) .

      verified = github_app.verify_webhook_signature(

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
