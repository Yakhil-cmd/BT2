### Title
Missing cosigner-authorization check on device "sign" requests allows any paired correspondent to solicit signatures for arbitrary addresses/units - (File: wallet.js)

### Summary
The `"sign"` message handler in `handleMessageFromHub` (wallet.js) is reached by any already-paired correspondent device without verifying that the sender is actually a legitimate cosigner of the target address. The authorization check that used to enforce this was explicitly commented out.

### Finding Description
In `wallet.js`, inside `handleMessageFromHub` → `doHandle()`, the `"sign"` case validates message shape (valid address, signing path regex, well-formed unsigned unit, private-payload hash consistency) but performs no check that `from_address` (the sender, derived from the device-message signature) is actually one of the recorded cosigners of `body.address`. This is visible directly in the `ifLocal` callback of `findAddress`: [1](#0-0) 

The comment explicitly documents that the authorization check was removed: [2](#0-1) 

By contrast, the `ifRemote` branch of the same handler *does* enforce that the requester is a listed cosigner before forwarding the signing request to the real signer: [3](#0-2) 

This asymmetry means: when the target address is hosted locally (`ifLocal`), **any** correspondent device that has ever been paired with the victim wallet (an "authenticated" peer per the hub/device-message signature checks in `device.js`) can send an arbitrary `unsigned_unit` and `signing_path` for **any** local address of the victim — including addresses that are part of shared/multisig contracts the sender is not part of — and the victim's wallet will immediately fire the `signing_request` UI event: [4](#0-3) 

The wider message dispatcher already permits several subjects from non-correspondents at all (`pairing`, `my_xpubkey`, `wallet_fully_approved`), and any legitimately paired device is treated as fully trusted for `sign`: [5](#0-4) 

The only remaining gate before the actual unit is signed is a UI confirmation dialog the end user must click through; there is no protocol-level authorization proving the requester is one of the address's cosigners, unlike what the `extended_pubkeys`/cosigner table (`wallet_signing_paths` / `shared_address_signing_paths`) was designed to enforce, and unlike the check still present for the remote-forward path.

This matches the reported bug class of "authenticated but not authorized" API/message handling: the device is authenticated (paired, signature-verified message) but the handler fails to verify that this particular device is authorized to request signing operations on the specific address/contract in question — directly analogous to HAX CMS's `Operations.php` endpoints checking authentication but not resource-level authorization.

### Impact Explanation
An attacker who has been paired with the victim at any point (e.g., a stale/former contact, a temporarily-approved contact, or someone who tricked the user into pairing) can repeatedly send crafted `unsigned_unit`/`signing_path` combinations for any of the victim's addresses, including shared multisig addresses that the attacker is not a legitimate party to. If the victim (relying on wallet UI) approves a signing request believing it originates from a legitimate multisig cosigner or counterparty (there is no protocol assurance of this), funds controlled by shared/multisig addresses can be spent to attacker-chosen outputs — this is a path toward unauthorized spending of funds. Even absent user approval, the lack of authorization allows an unauthorized device to probe wallet address ownership/definitions and to spam signing-request UI prompts for addresses it has no relationship to, undermining the security guarantee that only legitimate cosigners can solicit cooperative signatures.

### Likelihood Explanation
Exploitation only requires that the attacker device be a correspondent (paired) with the victim device — this is a very low bar (pairing secrets are often shared broadly, e.g., for chat, arbiter contracts, or one-time bootstrap flows), and no cryptographic proof of cosigner status is required to reach the vulnerable code path. The main mitigating factor is the manual UI confirmation step performed by the human user before the request unit is actually signed, which reduces but does not eliminate the practical risk (social engineering, confusing UI, automation-assisted wallets, or users who habitually approve requests are all realistic vectors).

### Recommendation
Restore (and generalize) the authorization check removed in the `ifLocal` branch of the `"sign"` handler: before emitting `signing_request`, verify that `from_address` is a known cosigner of `body.address` — e.g., check `wallet_signing_paths`/`extended_pubkeys` for simple shared wallets and `shared_address_signing_paths` for shared addresses — mirroring the check already retained in the `ifRemote` branch (`other_device_addresses.includes(from_address)`). If multilateral (non-cosigner) signing flows are a legitimate use case (as the comment suggests, e.g., prosaic/arbiter contract flows), gate those explicitly via the contract tables (`prosaic_contracts`/`wallet_arbiter_contracts`) rather than allowing an unauthenticated-for-this-address bypass for all `"sign"` requests.

### Proof of Concept
1. Device B pairs with Device A (victim) via a normal pairing exchange (`pairing` subject, no cosigner relationship established).
2. Device A owns/hosts a shared (multisig) address `ADDR_SHARED` for which B is not a cosigner.
3. Device B crafts a `"sign"` device message to A: `{address: ADDR_SHARED, signing_path: "r.0.0", unsigned_unit: {authors:[{address: ADDR_SHARED}], messages:[{app:'payment', payload:{asset:null, inputs:[...], outputs:[{address: B_ADDRESS, amount: N}]}}]}}`.
4. Because the check `SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?` is commented out in `wallet.js` (`ifLocal` callback, lines ~332-340), A's wallet accepts the message, validates it structurally, and immediately raises a `signing_request` UI prompt for the user of A, with no indication that B is not a legitimate cosigner of `ADDR_SHARED`.
5. If the user of A approves (a realistic outcome given the UI provides no cosigner-verification signal), a partially-signed unit spending from the shared address is produced and forwarded toward completion, potentially completing a spend if enough legitimate signatures can also be obtained/coerced.
