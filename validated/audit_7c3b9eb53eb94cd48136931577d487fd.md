### Title
Cross-tenant `check_suite` webhook mutates victim stack's commits via unbound `repository.owner.login`/`repository.full_name` fields - ([File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`, while `Handler#stacks`/`Handler#repository_name` (used by `CheckSuiteHandler#process`) scope the mutation using `payload.dig('repository', 'full_name')`. Because these are two independent, attacker-controlled fields in the same JSON body and are never checked for consistency, an attacker who owns a GitHub org can sign a payload with their own valid `webhook_secret` while setting `repository.full_name` to a victim's `owner/repo`, causing Shipit to schedule check-run refresh jobs against the victim's stack/commits.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner == repository_name.split('/').first`, but this equality is never enforced.

- `WebhooksController#verify_signature` at [1](#0-0)  computes `repository_owner` via [2](#0-1)  (`params.dig('repository','owner','login')`) and looks up `Shipit.github(organization: repository_owner)` to fetch that org's `webhook_secret`, then verifies the HMAC signature against the raw POST body using that secret.
- `CheckSuiteHandler#process` at [3](#0-2)  calls `stacks`, which is defined in the base `Handler` class using a *different* field: [4](#0-3)  — `Repository.from_github_repo_name(payload.dig('repository','full_name'))`.

Since the attacker constructs the entire raw JSON body themselves (this is a webhook endpoint reachable by anyone who can `POST /webhooks`), they can set `repository.owner.login = "attacker-org"` (so the signature check succeeds using the attacker's own legitimately-configured `webhook_secret` for `attacker-org`) while independently setting `repository.full_name = "victim-org/victim-repo"`. The controller only verifies the signature is valid for `attacker-org`'s secret; it never checks that `full_name` starts with `attacker-org/`. `CheckSuiteHandler` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and runs `stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)` against the victim's `Stack` rows — a write/job-scheduling action for a repository/tenant the request never authenticated as.

None of the existing guards catch this: `verify_signature` only checks the HMAC against `repository_owner`, not `full_name`; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema in `CheckSuiteHandler` (`requires :check_suite do requires :head_sha; requires :head_branch end`) only validates presence/type of `head_sha`/`head_branch`, not any relationship between `repository.owner.login` and `repository.full_name`; and `Repository#from_github_repo_name` performs no ownership check against the signer.

### Impact Explanation
An attacker who owns any GitHub org configured in Shipit (or, more generally, controls `repository_owner` to any org whose `webhook_secret` they know — including their own) can trigger `RefreshCheckRunsJob`/commit-state mutations (`schedule_refresh_check_runs!`) against an arbitrary victim `Stack`'s commits, keyed only by guessing/knowing a victim's `sha` + `head_branch`. This is a cross-tenant write: a payload authenticated for one repository mutates state belonging to another repository/stack, matching the "Critical" category ("a payload for one repository mutating another's stack, commit, task or team"). The scoped impact is limited to check-run refresh scheduling and commit check-run state, which the audit notes feeds into deployability checks that later processes (e.g., rollback/deploy gating) may trust — so the blast radius extends to influencing deploy/rollback safety signals for the victim stack, not merely local noise. Repeatable indefinitely against any known victim stack whose branch/sha are known or guessable.

### Likelihood Explanation
Preconditions: attacker needs a Shipit-configured GitHub org of their own (or any org's `webhook_secret`) so `verify_signature` succeeds — this is a normal, low-cost precondition for "any GitHub user who can... emit webhooks from a repository they own," as stated in scope. No Shipit session, API token, or team membership is required. The attacker crafts a raw JSON body themselves and computes the correct HMAC-SHA1 signature using their own known secret, then POSTs directly to `/webhooks`. This requires no live GitHub interaction — it's a direct HTTP POST fully reproducible in a minitest controller test.

### Recommendation
Enforce that the `full_name`'s owner segment matches the verified `repository_owner` before dispatching to handlers — e.g., in `WebhooksController#create` or `verify_signature`, assert `params.dig('repository', 'full_name')&.split('/')&.first&.casecmp?(repository_owner)` (or equivalent) and reject (422) otherwise. Alternatively, have `Handler#repository_name` derive from the already-verified `repository_owner` instead of re-reading `full_name` independently.

### Proof of Concept
Minitest plan (controller test, no live GitHub, following patterns in `test/controllers/webhooks_controller_test.rb`):

1. Create two orgs configured in `Shipit.github` config: `attacker-org` (with a known `webhook_secret`, e.g. stub via `Shipit.github(organization: 'attacker-org')`) and a victim stack from fixtures, e.g. `shipit_stacks(:shipit)` whose repository owner is `Shopify` and branch is `master`, with an existing commit `shipit_commits(:first)` whose `sha` is known.
2. Build a `check_suite` JSON payload (based on `test/fixtures/payloads/check_suite_master.json`) but set:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "Shopify/shipit-engine"` (or the victim's repo full name)
   - `check_suite.head_branch = "master"` (victim stack's branch)
   - `check_suite.head_sha = shipit_commits(:first).sha`
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload_body)`.
4. `POST :create` with this body and header, event `check_suite`.
5. Assert:
   - `assert_response :ok` (signature accepted, i.e., `repository_owner == "attacker-org"` verified successfully against attacker's own secret).
   - `assert_enqueued_with(job: RefreshCheckRunsJob, args: [...])` scoped to the victim commit/stack (`Repository.from_github_repo_name("Shopify/shipit-engine")`'s stack) — demonstrating `repository_owner` ("attacker-org") ≠ the owner segment of `repository_name`/`full_name` ("Shopify") yet the job was scheduled against the victim's `Stack`/`Commit`.

This demonstrates both sides of the equality (`repository_owner` vs. owner-segment of `repository.full_name`) diverge and the divergence is never checked before the mutating job is enqueued.
