### Title
Webhook signature check keys off `repository.owner.login` while event handlers key off `repository.full_name`, letting an unauthenticated attacker forge GitHub webhooks for any stack when a second, secret‑less GitHub App org is configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to validate the request against using an attacker-supplied JSON field, `repository.owner.login` (falling back to `organization.login`). `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected app has no `webhook_secret` configured. Every webhook `Handler` then determines the *actual* target repository/stack via a **different, unrelated** field: `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb`). These two fields are never checked for consistency, so the "organization whose credentials authenticated the request" and "the repository that gets written to" are two independently attacker-controlled values.

end

The instance supports multiple GitHub App orgs, each with its own optional `webhook_secret` (`test/dummy/config/secrets_double_github_app.yml` shows a real, documented topology with one org's `webhook_secret` set to `nil`). This is not a hypothetical: an operator with two GitHub Apps installed (common for orgs that host both internal and open-source repos) can easily have one org configured without a webhook secret (e.g., during initial setup, or an org intentionally left unauthenticated because it was believed to carry no sensitive stacks).

**Binding broken (before vs. after the attacker's request):**
- Before: `organization authenticated == repository written` is expected to hold, because both should derive from the same GitHub-signed payload.
- After: `repository_owner` (used to pick the signing org / `webhook_secret`) and `repository_name` = `full_name` (used to pick the `Stack`/`Repository` acted upon) are independent JSON fields with no cross-validation. An attacker sets `repository.owner.login` to the org lacking a `webhook_secret` and `repository.full_name` to `victim-org/victim-repo`. `verify_webhook_signature` short-circuits to `true` (no secret configured for that org), the controller proceeds, and the handler resolves and mutates the victim stack using `repository.full_name`.

### Impact Explanation
This crosses the "unauthenticated, no session/token/GitHub credential" boundary called for by the rules and produces cross-repository writes / unauthorized deploys:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching branch on the forged stack, enqueuing a `GithubSyncJob` that can drive continuous deployment to an attacker-chosen `after` SHA. [4](#0-3) 
- `StatusHandler#process` lets an attacker fabricate a passing CI `status` for an arbitrary commit on the victim stack (`commit.create_status_from_github!(params)`), which feeds directly into `MergeRequest#reject_unless_mergeable!` / `all_status_checks_passed?` used to gate automatic merges. [5](#0-4) [6](#0-5) 
- `CheckSuiteHandler#process` similarly schedules refreshes for arbitrary commits/branches on the victim stack. [7](#0-6) 

Because the `repository` used to select a `Stack` is not the same value that was actually authenticated, this satisfies the "Critical: cross-repository writes / unauthorized deploy" bar in the rules.

### Likelihood Explanation
Requires only network access to the public `webhooks` endpoint (no session, no `ApiClient` token, no GitHub credentials) plus knowledge/discovery that the Shipit instance has ≥2 GitHub App orgs configured where at least one lacks a `webhook_secret` — a configuration explicitly modeled in the repo's own test fixtures (`test/dummy/config/secrets_double_github_app.yml`), and plausible in real multi-org deployments where a secondary/auxiliary org's app was registered without setting a webhook secret. `GithubOrganizationUnknown` is the only other failure path, so any org name valid in `Shipit.github_organizations` unlocks the bypass.

### Recommendation
- Verify the webhook signature using the **same** repository/organization identity that the handler will subsequently act upon; do not let `repository.owner.login` diverge from `repository.full_name`.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations with no configured secret in production; require every configured GitHub App to have a non-blank `webhook_secret`, or reject payloads whose signing organization doesn't match the repository owner segment of `full_name`.
- Add signature-secret configuration validation at boot for all `Shipit.github_organizations`.

### Proof of Concept
1. Configure Shipit with two GitHub App orgs: `OrgA` (has `webhook_secret` set) and `OrgB` (no `webhook_secret`, as in `test/dummy/config/secrets_double_github_app.yml`).
2. `OrgA` owns the victim repo `orga/victim-repo`, with a Shipit `Stack` for it.
3. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any garbage value), and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "orga/victim-repo" }
}
```
4. `repository_owner` resolves to `"OrgB"`; `Shipit.github(organization: "OrgB").verify_webhook_signature(...)` returns `true` because `OrgB`'s `webhook_secret` is `nil` — no valid signature is required.
5. `PushHandler` resolves `repository_name` from `full_name` = `"orga/victim-repo"`, finds the real victim `Stack`, and enqueues `GithubSyncJob` with the attacker-chosen `expected_head_sha`, all without any valid signature from `OrgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
