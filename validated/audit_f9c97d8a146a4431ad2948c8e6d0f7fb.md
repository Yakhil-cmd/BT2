### Title
Webhook organization used for signature verification is not bound to the repository the payload actually targets, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository_owner`, a value read directly out of the untrusted, attacker-controlled JSON body (`params.dig('repository', 'owner', 'login')`). The event handlers that subsequently act on the same body (e.g. `PushHandler`) instead resolve the target `Repository`/`Stack` from a *different* field of the same body, `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb`). Nothing enforces that `repository.owner.login` (the value that selected the signing secret) and the owner segment of `repository.full_name` (the value that selects which repository is written to) refer to the same organization.

### Finding Description
Shipit supports hosting multiple GitHub Apps, one per GitHub organization, configured under `github.<org>` in `secrets.yml` (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Using Multiple GitHub Applications"). `Shipit.github(organization:)` looks up the App config (and its `webhook_secret`) purely by an organization name string: [1](#0-0) 

The webhook entry point authenticates the request by picking the secret for `repository_owner`, which is parsed straight from the incoming JSON body, and then verifies the raw body against that secret: [2](#0-1) [3](#0-2) 

Once the signature check passes (because it matches whatever organization's secret the attacker legitimately possesses), `create` hands the exact same parsed body to every handler for the event: [4](#0-3) 

Handlers do not re-derive the repository from `repository.owner.login` (the field that gated authentication). They instead use `repository.full_name`: [5](#0-4) 

and, for pushes, use that repository to look up `Stack`s and trigger a sync from GitHub: [6](#0-5) 

The binding that should hold is: `organization that authenticated the request == organization that owns the repository being written to`. Concretely, this should be `repository.owner.login == full_name.split('/').first`. The code never checks this equality. Since the attacker fully controls the JSON body used both to compute `repository_owner` for secret selection and `repository.full_name` for the actual write target, these two fields can be set independently in a single forged payload.

Any org administrator who has installed the Shipit GitHub App on their own organization (a normal, legitimate, unprivileged action relative to *other* tenants' repositories) knows that organization's `webhook_secret`. They can craft a webhook body where `repository.owner.login` is their own org (so `verify_signature` picks their own known secret and the HMAC matches), but `repository.full_name` names a repository belonging to a different organization hosted on the same Shipit instance. `verify_signature` passes, and the handler acts on the victim organization's `Stack` (e.g., enqueuing `GithubSyncJob`, which fetches from GitHub and can drive deploys/rollbacks for that stack).

### Impact Explanation
This crosses a repository-write trust boundary between tenants of the same Shipit instance: an actor authenticated only for organization A can inject webhook events that are processed as if they came from, and about, organization B's repository, triggering syncs and downstream deploy-pipeline actions (`GithubSyncJob`, review-stack provisioning, PR/label state mutation, etc.) for a repository they do not control. This matches the "cross-repository writes" / "unauthorized deploy" high-impact category, since the write target (`Stack`/`Repository`) is decoupled from the credential that was actually verified.

### Likelihood Explanation
Exploitability only requires legitimate installation of the Shipit GitHub App / webhook on one organization configured in a multi-org Shipit deployment (a supported, documented configuration) — no privileged Shipit account, session, or API token is needed. The attacker fully controls the raw JSON body they sign, so decoupling `repository.owner.login` from `repository.full_name` is trivial.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after), enforce that the organization used to select the verifying `GitHubApp`/secret matches the owner of `repository.full_name` (and of any other repository-identifying fields consumed downstream) before dispatching to handlers — e.g., reject the request if `repository_owner` does not case-insensitively equal `params.dig('repository','full_name')&.split('/')&.first`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using OrgA's known `webhook_secret` over this exact raw body and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner => "OrgA"`, calls `Shipit.github(organization: "OrgA")`, and the signature verifies successfully against the attacker's own secret.
5. `PushHandler#process` (via `Handler#repository_name` = `payload.dig('repository','full_name')` = `"OrgB/victim-repo"`) looks up and syncs the victim's `Stack`, enqueuing `GithubSyncJob` for a repository the attacker never authenticated for.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
