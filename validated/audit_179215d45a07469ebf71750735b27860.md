### Title
Missing position-map storage entries are conflated with empty maps, letting a half-expired account act as debt-free or collateral-free - ([File: contracts/controller/src/storage/account.rs])

### Summary
The Linux bcache bug class is a validity check that covers only the "error" variant while a distinct "absent/NULL" variant slips through and is dereferenced or acted upon. The direct analog in XOXNO Lending is the pair of position-map loaders `get_supply_positions` / `get_debt_positions`: a missing persistent entry (`Option::None`, the "NULL" case) is silently converted into an empty `Map` rather than being distinguished from a genuinely empty position. Because `SupplyPositions` and `BorrowPositions` are separate persistent storage keys whose writes deliberately do not renew TTL, the two entries can have different expiry times, so an account can be loaded in a half-present state.

### Finding Description
`get_supply_positions` and `get_debt_positions` both call `get_user(...)`, which returns `Option`, and then apply `.unwrap_or_else(|| Map::new(env))` — collapsing "entry absent" into "entry empty" (`storage/account.rs:63-73`). The file's own header documents that "position-map writes do not" renew user TTL while metadata and delegate writes do (`storage/account.rs:1-2`), and `write_side_map` removes the key entirely when a map becomes empty (`storage/account.rs:94-105`), so existence of each key is an independent persistent-storage TTL object. `renew_user_account` renews each key only if present (`storage/account.rs:258-272`), so once one map lapses it is never restored, while the sibling map can keep being renewed by later writes (`set_supply_positions`/`set_debt_positions` write one side only).

Every downstream consumer then computes on a corrupted account:

- `try_get_account`/`get_account` assemble the account from whichever maps happen to load (`storage/account.rs:146-162`), so a lapsed `BorrowPositions` entry yields a `debt_free()` account.
- `calculate_account_risk_totals_body` returns `health_factor = i128::MAX` when `total_debt == Wad::ZERO` (`risk/totals.rs:203-207`).
- `require_post_pool_risk_gates` is skipped for debt-free accounts (per `docs/reference/endpoints.md` and `risk/params.rs` semantics), so `withdraw` on the still-present supply map executes with no health-factor or LTV gate.
- Conversely, a lapsed `SupplyPositions` entry makes an account with real debt appear collateral-free (`weighted_collateral = 0`, HF = 0), making it liquidatable/bad-debt-eligible while its real collateral is unreachable.

A TTL differential arises because position-map writes don't renew and the two maps are written at different times: `borrow` writes only `BorrowPositions` (after `renew_user_account`), but subsequent operations that write `SupplyPositions` (Credit-mode liquidation on a receiver, `update_account_threshold` writes via `set_supply_positions`, supply top-ups) renew only that side, while a pure-debt account whose debt map expires is then seen as debt-free on its next `withdraw`/`repay` call — which itself only touches the surviving map.

The strongest single-address path: an account supplies collateral, borrows, then goes inactive until `BorrowPositions` expires while `SupplyPositions` is still live (or is re-stamped/renewed by an unrelated `update_account_threshold(has_risks=false)` call — permissionless, `risk/params.rs:124-144` — which calls `renew_user_account` at `params.rs:176` but only renews keys that still exist). The owner then calls `withdraw` for the full supply; the account loads as debt-free, the post-pool risk gates are skipped, and the pool pays out collateral while the real debt shares are orphaned.

### Impact Explanation
Theft of user funds / protocol insolvency. Withdrawing collateral against an evaporated debt record leaves the pool holding unbacked supply shares: the borrowed tokens were already disbursed, and there is no `DebtPositionRaw` left to collect or liquidate. `clean_bad_debt` cannot target the position because the debt map is gone, and the account appears healthy (`get_health_factor` = `i128::MAX`). The symmetric expiry direction lets a liquidator seize an account whose collateral entry lapsed — permanent loss of the borrower's collateral value at liquidation terms.

### Likelihood Explanation
Exploitation requires a specific persistent-entry expiry skew, which requires extended inactivity of exactly one of the two keys — a real condition under Soroban TTL semantics, amplified because position-map writes explicitly skip TTL renewal while `renew_user_account` skips absent keys (so a lapsed key can never recover). The attacker needs only their own account; no privilege is required. The window is narrower than a pure logic bug since it depends on ledger-time expiry, which supports Medium rather than High.

### Recommendation
Distinguish "absent" from "empty" in the position-map loaders, mirroring the `IS_ERR_OR_NULL` fix: make `get_supply_positions`/`get_debt_positions` return `Option<Map<..>>`, and have account loaders (`try_get_account`, `get_account`, `get_account_borrow_only`) fail closed with `AccountNotFound`/`AccountNotInMarket` when `AccountMeta` exists but a position map entry that should exist is missing — or, simpler, persist a presence flag/positions-generation counter alongside `AccountMeta` (written with `set_user`, which renews) recording which sides exist, and panic if a recorded side's map fails to load. Additionally, renew both position-map keys on every account operation that touches either, so the two entries can never drift in TTL.

### Proof of Concept
1. Attacker calls `supply` then `borrow` on their own account (same `HubAssetKey` or different hubs).
2. Attacker stays inactive until the `ControllerKey::BorrowPositions(account_id)` persistent entry expires while `ControllerKey::SupplyPositions(account_id)` remains live (or anyone calls `update_account_threshold(caller, false, [account_id])` beforehand, which renews only existing keys via `renew_user_account` at `params.rs:176`).
3. Attacker calls `withdraw(account_id, entries)` for the full collateral. `storage::get_debt_positions` returns `Map::new` (`account.rs:71-73`), `account.debt_free()` is true, `calculate_account_risk_totals` reports `i128::MAX` HF (`totals.rs:203-207`), the post-pool risk gate is skipped, and the pool transfers out the collateral.
4. Result: pool cash is disbursed, no debt record remains to liquidate or socialize — permanent protocol insolvency equal to the outstanding borrow plus accrued interest.
