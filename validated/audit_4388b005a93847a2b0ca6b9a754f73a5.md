## Title
CCMenu API token issued for one stack grants read access to any stack's CCMenu status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

## Summary
`Shipit::CCMenuUrlController#fetch` mints an `ApiClient` that is never bound to the stack whose CCMenu URL was requested, and `Shipit::Api::CCMenuController` resolves the target stack with an unscoped `Stack.from_param!(params[:stack_id])` instead of the token-scoped `stacks` helper used elsewhere in the API. As a result, a CCMenu token pasted into any dashboard authorizes reading the build/deploy status of every stack in the Shipit instance, not just the one it was generated for.

## Finding Description
The claimed binding is: `stack_touched_by_request ∈ authorized_stacks(token)`, where `authorized_stacks(token)` should be `{ current_api_client.stack_id }` when generated per-stack.

Tracing the code:
- `CCMenuUrlController#fetch` creates the client with `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` attribute is ever set. [1](#0-0) 
- Because `stack_id` is never assigned, `current_api_client.stack_id` is `nil` for every CCMenu client, and this single client (keyed only by `creator`+`name`) is reused/shared across all of that user's stacks.
- Even setting that aside, `Shipit::Api::CCMenuController` overrides the shared `stack` finder used elsewhere and does not use the token-scoped `stacks` collection at all:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 
compared to `Shipit::Api::BaseController#stack`, which correctly scopes: `@stack ||= stacks.from_param!(params[:stack_id])`, where `stacks` is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. [3](#0-2) 

- `authenticate_api_client` in the CCMenu controller only checks `ApiClient.authenticate(params[:token])`, and `require_permission :read, :stack` only checks the generic `read:stack` string is in `permissions` — neither check restricts which stack ID may be requested. [4](#0-3) 
- `ApiClient#check_permissions!` merely verifies the permission string exists in the `permissions` array; it has no per-stack scope check. [5](#0-4) 

Attacker flow: an operator visits their stack's settings page, clicks "Fetch URL", and pastes the resulting URL (e.g. `https://shipit.example.com/api/stacks/*/ccmenu?token=XYZ`) into a shared/third-party CI dashboard. Anyone who can see that URL (a non-privileged observer with no Shipit session, no secrets) can send `GET /api/stacks/<any-other-org>/<any-other-repo>/<any-branch>/ccmenu?token=XYZ` with the same token and an arbitrary `stack_id` path segment, and the request succeeds because `stack` is resolved unscoped.

## Impact Explanation
This is an unauthenticated (relative to the target stack) read of stack build/deploy status for any stack in the Shipit instance — matching the High severity category "unauthenticated read of stack state, task streams or deploy output." The blast radius is instance-wide: a single leaked/observed CCMenu token exposes the last deploy status, lock state, and merge status of every stack managed by that Shipit installation, across all repositories/tenants, and is fully repeatable (no rate limiting bypass needed, just changing the path segment per request).

## Likelihood Explanation
No special Shipit configuration is required beyond a normal operator having generated one CCMenu URL for any stack. The attacker only needs to observe that URL once (e.g., it's designed to be pasted into third-party dashboards, so it commonly ends up in less-trusted locations). From there, forging additional requests is trivial (just changing `stack_id` in the path) and requires no secrets, sessions, or GitHub credentials. This is low-cost and highly feasible.

## Recommendation
Bind the `ApiClient` created in `CCMenuUrlController#fetch` to the specific stack (`.find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`), and change `Shipit::Api::CCMenuController#stack` to use the scoped `stacks.from_param!(params[:stack_id])` (as `BaseController#stack` does) instead of unscoped `Stack.from_param!`, so a token can only ever resolve the stack it was issued for.

## Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (existing suite already exercises token auth):
```ruby
test "a token minted for one stack cannot read another stack's ccmenu status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  # Simulate CCMenuUrlController#fetch's client creation for stack_a
  client = ApiClient.create!(permissions: %w[read:stack], creator: shipit_users(:walrus), name: 'CCMenu Client')

  get :show, params: { stack_id: stack_a.to_param, token: client.authentication_token }
  assert_response :ok

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }
  assert_response :ok # currently passes -- should be :not_found/:forbidden since token was scoped to stack_a
end
```
Both assertions currently pass with `:ok`, demonstrating that the same token reads status for two unrelated stacks, violating the `stack_touched ∈ authorized_stacks(token)` binding.
