### Title
Cross-org team membership tampering via `MembershipHandler` when `github_id` collides with a `Team` under a different organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook against `repository_owner`, which for `membership` events falls back to `params.dig('organization','login')`, i.e. the *sending* org's own webhook secret [1](#0-0) . `MembershipHandler#find_or_create_team!` then looks up a `Team` solely by `github_id: params.team.id`, and only sets `team.organization` on first creation [2](#0-1) . If a `Team` row with that `github_id` already exists (created earlier under a different organization), `find_or_create_by!` returns the existing row unchanged and `team.add_member`/`team.members.delete` mutate that row's memberships, without ever re-checking that the authenticating org matches `team.organization`.

### Finding Description
Binding claimed: `verify_signature` org (ORG_A, from `params.dig('organization','login')`) == org of the `Team` row mutated by `add_member`/`members.delete` (should be ORG_A, but is actually ORG_B, unchanged since creation).

Trace:
1. Attacker owns/administers a GitHub organization ORG_A and has configured it in Shipit (a real, valid `webhook_secret` exists for ORG_A) - this is normal, unprivileged Shipit onboarding, not a stolen secret.
2. Attacker sends `POST /webhooks` with `X-Github-Event: membership`, a payload containing only `organization.login = "ORG_A"` (no `repository` key), `team.id = <github_id of a Team row that already exists in Shipit's DB for ORG_B>`, `action: "added"`, and `member.login = <arbitrary username>`, signed with ORG_A's real webhook secret.
3. `repository_owner` resolves to `"ORG_A"` via the fallback [1](#0-0) , and `verify_signature` succeeds because the signature is legitimately computed with ORG_A's own secret [3](#0-2) .
4. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [2](#0-1) . Since a `Team` row with that `github_id` already exists (created earlier for ORG_B), the block (`team.organization = params.organization.login`) is **not** executed — `find_or_create_by!` only runs the block on creation. The returned `team` object still has `organization == "ORG_B"`.
5. `team.add_member(member)` or `team.members.delete(member)` executes against that ORG_B team's `memberships` association [4](#0-3) , with no reference to the authenticating org at all.

Root cause: authentication is performed at the org level (via `repository_owner`), but the object mutated is selected purely by an attacker-supplied numeric `team.id`, with no validation that the authenticated org equals `team.organization`.

Existing guards checked: `verify_signature` only proves the payload was signed by *some* org secret matching the org named in the payload — it says nothing about which `Team` record gets mutated. `drop_unhandled_event` and `ExplicitParameters` schema validate payload shape only (`requires :team { requires :id, Integer ... }`), not cross-org identity. No model validation ties `add_member`/`members.delete` back to the currently authenticating org.

### Impact Explanation
An attacker who legitimately controls their own GitHub org (and thus its real Shipit webhook secret) can add or remove arbitrary Shipit `User` records from an unrelated organization's `Team`, without ever authenticating as or being a member of that target organization. Since `User#authorized?` gates deploy access on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) , and `Shipit.github_teams` config maps to these `Team` records, this can escalate an arbitrary GitHub user into a privileged Shipit team used for deploy authorization — a genuine cross-tenant authorization write. This matches "escalation into `Shipit.github_teams` authorization" (High) or, if the target team gates deploy/merge actions, "unauthorized deploy" territory (Critical), depending on how the victim team is used.

### Likelihood Explanation
Preconditions are non-trivial: the attacker needs (a) a real onboarded organization in Shipit with a valid webhook secret (feasible for any org admin, since Shipit's org onboarding is not itself gated by anything the attacker doesn't control), and (b) knowledge of the exact numeric `github_id` of an existing `Team` row for the target org that Shipit has already synced (via `Team.find_or_create_by_handle`/`fetch_and_create_from_github`, or via a prior legitimate `membership` webhook). GitHub team IDs are not secret but are also not trivially guessable/enumerable by an outsider without existing access; the attacker must discover or brute-force this integer. Given that constraint, the attack is fully repeatable once the ID is known — no rate limiting, no re-verification per request.

### Recommendation
In `MembershipHandler#find_or_create_team!`, always validate (not just set-on-create) that `team.organization == params.organization.login` before performing `add_member`/`members.delete`; raise/drop the event if they don't match. Alternatively, look up `Team` by the compound key `(github_id, organization)` rather than `github_id` alone, and reject membership events whose `organization.login` disagrees with the team's recorded organization.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership event cannot mutate a team belonging to a different organization" do
  team = Shipit::Team.create!(organization: "org-b", github_id: 999, name: "victim", slug: "victim", api_url: "https://api.github.com/teams/999")
  member = Shipit::User.create!(login: "attacker-controlled-user")

  payload = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'victim', 'slug' => 'victim', 'url' => team.api_url },
    'organization' => { 'login' => 'org-a' }, # attacker's own org, verified via org-a's real secret
    'member' => { 'login' => member.login },
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).process

  team.reload
  assert_equal "org-b", team.organization # organization unchanged, as expected
  assert_includes team.members, member    # BUG: org-a's signed request mutated org-b's team membership
end
```
This demonstrates: signature verified against `org-a`; `team.organization` remains `org-b` (unchanged since creation, as the question hypothesizes); yet `add_member` still executes against that `org-b` team — the two org values never match, confirming the broken binding.
