## Analysis

The Float Protocol incident is a classic "manipulate spot price, then mint/burn LP shares at the manipulated price" attack against an AMM-derived share-pricing mechanism that has no TWAP/oracle protection. The `ocore` repository ships a reference implementation of exactly this pattern as an AA blueprint: `test/samples/uniswap_like_market_maker.oscript`, which is parsed/validated as a normal autonomous agent by `formula/evaluation.js` and `formula/validation.js`. Because `balance[asset]` in oscript always reflects the instantaneous, un-averaged balance of the AA (there is no built-in TWAP primitive for AA state, only spot `balance[]` and one-shot `data_feed[[...]]` oracle reads), any AA — including this documented reference pattern — that prices LP-share issuance/redemption off `balance[]` inherits the exact same "spot-price manipulation → mispriced share mint/burn" flaw that hit Float Protocol. ### Title
Spot-balance-priced LP share issuance/redemption without TWAP allows flash-swap-style value extraction - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The AMM/market-maker AA blueprint shipped in the repo prices LP share issuance (`invest`) and redemption (`divest`) directly off the AA's current spot balances (`balance[$asset]`, `balance[base]`), with no time-weighted average price and no oracle cross-check, mirroring the exact root cause of the Float Protocol Hypervisor incident.

### Finding Description
The `invest` case computes `$current_ratio = $asset_balance / $bytes_balance` from the AA's live balances (balances minus the current trigger's own output) and issues LP shares (`$issue_amount`) proportional to `$investor_share_of_prev_balance * var['mm_asset_outstanding']`. [4](#0-3)  The `divest` case pays out a proportional share of the *current* spot balances (`balance[$asset]`, `balance[base]`) based on `$mm_asset_amount / var['mm_asset_outstanding']`. [5](#0-4)  The two swap cases move the pool along a zero-fee constant-product curve (`$p = $asset_balance * $bytes_balance`) with no exchange fee deducted (explicitly noted by the "we can deduct exchange fees here" comment, left unimplemented). [6](#0-5) 

Because oscript's `balance[...]` selector only exposes the instantaneous AA balance — there is no TWAP accumulator and `data_feed[[...]]` values are only used elsewhere as one-shot oracle reads, not as a pool-price safety check — any trigger sender who can post a sequence of units to the AA within a short window (before other participants react) can shift `$current_ratio`/`$p` with a large swap, then immediately `invest`/`divest` at the distorted ratio, then reverse the swap, netting value out of other liquidity providers' deposited balances. This is structurally identical to the Float Protocol bug: "critical functions lacked TWAP/oracle validation and slippage protection" over a manipulable spot price used to price share mint/burn.

### Impact Explanation
Any AA author who deploys this reference pattern (or a variant, which is common for AMM-style AAs on the platform) exposes depositors' pooled bytes/asset balance to extraction by a single well-capitalized trigger sender, without needing any privileged role — only the ability to post successive ordinary payment units to the AA's address. This is a direct AA fund-loss vector reachable by an unprivileged AA trigger sender.

### Likelihood Explanation
No flash loan primitive is required, unlike the original incident, but the attack merely requires enough working capital to execute a swap → invest/divest → reverse-swap sequence, and the zero-fee, TWAP-less design specifically removes the friction (trading fees, price averaging) that would normally make such round-trips unprofitable. Given this pattern is a documented, ready-to-copy blueprint in the codebase, likelihood of real-world adoption (and thus exploitation) is non-trivial.

### Recommendation
Any AMM-style AA (including this reference sample, if used as a template for production AAs) should price share issuance/redemption using a time-weighted or multi-block average of pool balances/ratios rather than instantaneous `balance[...]`, and/or require a minimum elapsed time or MCI gap between large balance-shifting swaps and LP mint/burn operations, and should reintroduce a non-zero swap fee so round-trip manipulation is not free.

### Proof of Concept
1. Attacker sends a large `base`-asset payment to the AA to trigger the "exchange bytes to asset" case, sharply skewing `$asset_balance`/`$bytes_balance` away from fair value. [2](#0-1) 
2. In a follow-up unit, attacker (or a colluding address) sends an `invest` trigger; `$current_ratio` is computed off the now-skewed balances, so `$issue_amount` of the LP asset (`$mm_asset`) is minted at a distorted rate relative to fair value. [4](#0-3) 
3. Attacker reverses the initial swap ("exchange asset to bytes") to restore balances close to the pre-attack ratio. [3](#0-2) 
4. Attacker then `divest`s the minted LP shares, redeeming a share of the (now-restored, fair-valued) pool balances — extracting value that came from existing LPs' deposited balance rather than from the attacker's own swap round-trip, because the mint price in step 2 did not reflect a fair/averaged price. [5](#0-4)
