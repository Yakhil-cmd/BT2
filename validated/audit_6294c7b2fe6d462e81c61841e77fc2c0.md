This CVE concerns the Linux kernel's eBPF verifier failing to propagate a `changes_pkt_data` property across calls to global BPF subprograms, which allows use of stale/invalidated packet pointers inside the kernel's own verifier and BPF execution engine. This bug class is intrinsic to the Linux kernel's in-kernel BPF bytecode verifier — a static analysis tool that tracks pointer safety through a call graph of BPF instructions.

Polkadot SDK contains nothing resembling this component. There is no BPF verifier, no packet-pointer tracking, and no analogous "helper call invalidates a previously-checked pointer, but that invalidation isn't propagated through inter-procedural calls" pattern in FRAME pallets, the XCM executor, pallet-revive/contracts, or the PolkaVM-based virtualization crate. The search results returned only superficially-related tracing/call-tracking code (e.g., `pallet-revive`'s `CallTracer` in [1](#0-0)  and PVM subcall isolation tests in [2](#0-1) ), none of which involve a verifier tracking property propagation across a call graph to prevent use of invalidated memory references — the actual root cause of CVE-2024-58098.

There is no real user-reachable entry point in Polkadot SDK where an attacker-controlled payload could trigger this specific class of bug (stale pointer reuse due to missing inter-procedural static-analysis propagation), since the SDK does not implement or embed a BPF-style bytecode verifier of this kind.

fn counter_in_subcall(program: &[u8]) {

	let execution = instance.prepare(b"do_subcall").unwrap();

			match syscall_symbol {
				b"read_counter" | b"increment_counter" | b"exit" => {
					make_handler(&mut counter)(execution, syscall_symbol, a0, a1, a2, a3, a4, a5)
				},
