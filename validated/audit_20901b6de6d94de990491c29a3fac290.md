## Analog Found

### Title
Disabled Scope-Restriction Allows Indirect (Guest-Level) Device Correspondents to Send Arbitrary Privileged Device Messages - (File: wallet.js)

### Summary
The your_spotify CVE stems from a "guest-level" public-token holder being able to reach a privileged endpoint (`/me`) that should only be reachable with full-trust tokens, because the endpoint failed to restrict what a guest-scoped credential could retrieve. ocore has a structurally identical trust-scoping bug in its device-messaging layer: `correspondent_devices.is_indirect` marks a device as a *limited-trust, non-paired* correspondent (added automatically when a peer names it as a "cosigner" in a wallet-creation offer), yet the code path that is supposed to restrict indirect correspondents to a narrow whitelist of message subjects is commented out, so an indirect correspondent is treated identically to a fully paired, fully trusted correspondent for every device-message subject.

### Finding Description
`device.addIndirectCorrespondents()` inserts a device as a correspondent with `is_indirect=1` without any pairing handshake/`pairing_secret` verification — the caller only supplies `device_address`, `pubkey`, `hub`, `name` taken from an untrusted peer's `create_new_wallet` offer: [1](#0-0) [2](#0-1) 

The message that seeds `other_cosigners` is attacker-controlled and only self-consistency (pubkey → device_address hash) is validated, not any relationship to the victim: [3](#0-2) 

`device.js`'s hub-message dispatcher looks up whether the sender is `is_indirect` and forwards that flag (`bIndirectCorrespondent`) into `handle_message_from_hub`: [4](#0-3) 

But the intended restriction — that indirect correspondents may only be trusted for a small whitelist of subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`) — is dead code, commented out in `wallet.js`: [5](#0-4) 

Because this check never executes, `bIndirectCorrespondent` is effectively ignored for the rest of `handleMessageFromHub`'s big `switch(subject)`, which includes highly privileged subjects such as `"sign"` (co-signing arbitrary units, including private payloads), `"new_shared_address"`, `"private_payments"`, `"arbiter_contract_offer"`, and `"text"`: [6](#0-5) 

The "guest" analogy is direct: `is_indirect` correspondents are the ocore equivalent of your_spotify's "public/guest token" holders — meant to be granted only a narrow slice of functionality — yet, due to the disabled scope check, they receive full-trust processing identical to a device the user actually paired with over an authenticated pairing_secret exchange (`handlePairingMessage`): [7](#0-6) 

### Impact Explanation
An attacker who gets a victim to approve a (plausible-looking) multi-cosigner wallet-creation offer becomes an `is_indirect` correspondent of the victim's device without ever completing the normal pairing/authentication flow. From that point on the attacker's device is trusted for every device-message subject, not just wallet-setup subjects. This can be leveraged to send bogus `"sign"` requests, forged `"new_shared_address"` definitions, or `"private_payments"`/contract messages that the victim's wallet will process as though they came from a genuinely paired, mutually-verified device — potentially leading to signing of attacker-crafted units, disclosure/redirection of private payment chains, or funds routed to attacker-controlled shared addresses. This maps to unauthorized fund-signing / AA-fund-loss-class impact reachable purely from a device-message a private-payment/wallet counterparty can send.

### Likelihood Explanation
Requires the victim to accept a wallet-creation offer naming the attacker as a cosigner (a normal, expected user interaction in multisig wallet setup), after which no further user action is needed — the disabled restriction applies to all subsequent messages from that device address automatically. Given wallet cosigning flows are a first-class, commonly-used feature, the precondition is realistic for socially-engineered or curiosity-driven wallet-share invitations.

### Recommendation
Re-enable and properly scope the indirect-correspondent restriction that was commented out in `wallet.js`'s `handleMessageFromHub`, ensuring `bIndirectCorrespondent` devices are rejected for all subjects outside the strict whitelist required for wallet bootstrapping, and require indirect correspondents to complete real pairing (pairing_secret exchange) before being granted full-trust status for signing, shared-address, or private-payment message subjects.

### Proof of Concept
1. Attacker crafts a `create_new_wallet` justsaying/device message to the victim, with `wallet_definition_template` naming a multisig set that includes the victim and an attacker-controlled `other_cosigners` entry (self-consistent pubkey/device_address the attacker actually controls, arbitrary `hub`/`name`).
2. Victim's UI shows the wallet-creation prompt (per intended UX) and the user approves it, calling `approveWallet()`, which calls `device.addIndirectCorrespondents(arrOtherCosigners, …)`, inserting the attacker's device as `is_indirect=1` in `correspondent_devices` — no pairing_secret ever exchanged.
3. Attacker's device now sends a `"sign"` (or `"new_shared_address"`, `"private_payments"`, etc.) device message to the victim. Because the commented-out check in `wallet.js:92-93` never runs, `handleMessageFromHub` processes it with full trust, identical to a properly paired correspondent, despite the correspondent never having proven possession of a pairing secret tied to the victim's trust relationship.
