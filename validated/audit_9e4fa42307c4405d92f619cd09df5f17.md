### Title
CCMenu token authorizes reading every stack, not just the stack it was generated for - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token that is presented to the user as "the CCMenu URL/token for stack X," but the `ApiClient` record it creates is never bound to that stack. Because `ApiClient#stack_id?` is false for this client, every downstream `read:stack`-gated API endpoint treats it as globally scoped, so the token grants read access to every stack (and their task/deploy output) in the Shipit installation, not just the one shown to the user.

### Finding Description
`CCMenuUrlController#fetch` builds a URL containing an authentication token for a specific stack: [1](#0-0) 

The `client` method that generates this token does:
```ruby
@client ||= ApiClient.create_with(permissions: %w[read:stack])
                     .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
```
Note that `stack:` is never passed, so the created/found `ApiClient` has `stack_id == nil`, and it is memoized per `(creator, name)` — meaning the *same* client/token is reused across every stack that user requests a CCMenu URL for.

Compare this to `Api::BaseController`, which is the actual authorization boundary every API request (including `Api::OutputsController`, `Api::TasksController`, `Api::StacksController`) goes through: [2](#0-1) 

`stacks` only restricts the queryable set to a single stack `if current_api_client.stack_id?`. Because the CCMenu client's `stack_id` is `nil`, `stack_id?` is `false`, so `stacks` resolves to `Stack.all`, i.e. unrestricted.

This breaks the binding "the stack a token authorizes == the stack it touches": the UI/URL implies the token is scoped to one stack (`api_stack_ccmenu_url(stack_id: stack.to_param)`), but the underlying `ApiClient.check_permissions!` check only validates the `read:stack` permission string and never re-validates that the `stack_id` in the URL matches the client's own `stack_id` (because there isn't one to compare against). The token is therefore a de-facto global `read:stack` credential.

Endpoints reachable with this single leaked/shared token and only `read:stack` permission include:
- `Api::StacksController#index/#show` — enumerate/read every stack in the installation.
- `Api::OutputsController#show` — read the full output of any task/deploy on any stack: [3](#0-2) 
- `Api::TasksController#index/#show` — list/read every task belonging to any stack: [4](#0-3) 
- `Api::CommitsController`, `Api::MergeRequestsController` (all declare `require_permission :read, :stack` with no further binding).

This is directly analogous to the referenced bug class: a value that is checked/displayed at one granularity (per-stack CCMenu link) diverges from the value actually enforced at execution time (an unscoped `ApiClient`), just as `StreamingFeeModule` accepted a zero-fee state that its own `accrueFee` invariant could never re-enter.

### Impact Explanation
CCMenu tokens are, by design, meant to be embedded in third-party CI dashboard/status-monitoring tools (CCTray-style aggregators), which is a lower-trust consumption context than a Shipit session. Because the token is unscoped, any such consumer (or anyone who obtains one CCMenu URL) gains read access to task/deploy chunk output, stack listing, and commit/merge-request data for **every** stack managed by that Shipit instance — including stacks/repositories the requesting user was never intended to expose via that integration. This satisfies the "High - unauthenticated [w.r.t. stack-scoping] read of stack state, task streams or deploy output" impact bucket: the credential crosses a repository/stack boundary it was never meant to authorize.

### Likelihood Explanation
Any authenticated Shipit user who visits a stack's CCMenu link generates this token; no privileged action is required beyond normal use of an existing feature. The mistake is a straightforward omission (`stack:` not passed to `create_with`/`find_or_create_by!`), and the resulting token is handed out via a URL specifically intended for external consumption, increasing the chance of exposure/leakage relative to interactively-typed session credentials.

### Recommendation
Scope the CCMenu `ApiClient` to the target stack, and key uniqueness on `(creator, stack, name)` instead of `(creator, name)`:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')
end
```
This restores the invariant that `ApiClient#stack_id?` is true and `Api::BaseController#stacks` scopes the token to exactly the stack for which it was generated, matching what is displayed/implied to the user.

### Proof of Concept
1. As User A, request the CCMenu URL for `stack-1` (`GET /stacks/stack-1/ccmenu_url`). This creates `ApiClient(creator: A, name: 'CCMenu Client', stack_id: nil, permissions: ['read:stack'])` and returns a token `T`.
2. Using `T` (Basic Auth), call `GET /api/stacks` — the response lists **all** stacks in the installation, not just `stack-1`.
3. Call `GET /api/stacks/stack-2/tasks/:id/output` for an unrelated stack `stack-2` that User A never requested a CCMenu link for — the request succeeds and returns the task's deploy output, because `stacks` resolves to `Stack.all` for this client.
