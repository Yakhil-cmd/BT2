### Title
Unauthenticated stack-status disclosure via forged `referrer` param in `MergeStatusController#check` - (File: `app/controllers/shipit/merge_status_controller.rb`)

### Summary
`MergeStatusController#check` is exempted from `force_github_authentication` and, unlike `#show`, never checks `current_user.logged_in?`. It resolves the target `Stack` purely from `params[:referrer]`, parsed by `ReferrerParser`, with no comparison to the real HTTP `Referer` header. Any unauthenticated internet client can therefore submit an arbitrary `referrer=https://github.com/<owner>/<repo>/pull/<n>` string and read the merge/build status of any stack configured in the Shipit instance.

### Finding Description
The claimed binding is: `referrer_parser.repo_owner/repo_name` (derived from `params[:referrer]`) should equal the repository the *actual* browser request originated from, i.e. `request.referer`'s owner/repo. In code, `referrer_parser` only reads `params[:referrer]`: [1](#0-0) 
and `ReferrerParser#initialize` regex-matches whatever string is handed to it, with no correlation to `request.referer`: [2](#0-1) 

`stack` resolves using `referrer_parser.repo_owner`/`repo_name` when `params[:stack_id]` is absent, scanning across *all* repositories/stacks known to the instance: [3](#0-2) 

Critically, `check` is one of the actions that skips the authentication filter entirely: [4](#0-3) 
and unlike `show` (which guards with `return render('logged_out') unless current_user.logged_in?`, line 15), `check` performs **no** login check before computing and returning `stack_status`: [5](#0-4) 

Attacker request: `GET /merge_status/check?referrer=https://github.com/<any-owner>/<any-repo>/pull/1&branch=<branch>` (or `.json`) with no session cookie, no API token. This satisfies the `check` action's requirements (no `force_github_authentication`, no `logged_in?` gate) and returns the merge status (`ok`/503 with status text, or JSON `{stack_status: ...}`) of whichever stack matches the attacker-chosen owner/name/branch — regardless of whether the attacker has any relationship to that repository, and regardless of the real `Referer` header the client sent (or omitted).

Existing guards do not stop this: `force_github_authentication` is explicitly skipped for `check`; `ExplicitParameters`/model validators only validate format of stored records, not this read path; `current_user.authorized?`/`require_permission!` are never invoked for `check`.

### Impact Explanation
Any unauthenticated party can enumerate/poll the merge/build status (`success`, `pending`, `failure`, etc., via HTML `ok`/503 or JSON) of any stack across any repository/org configured on the Shipit instance, with no credentials. This is unauthenticated read of stack state, repeatable against arbitrary owner/repo/branch combinations by simply varying the `referrer` string — matching the "High – unauthenticated read of stack state" category. It is not scoped to the requester's real originating repository at all since the binding to `request.referer` never exists.

### Likelihood Explanation
Trivial and fully repeatable: no Shipit session, no API token, no GitHub team membership, no secrets required. The attacker only needs network access to the Shipit host and knowledge/guesses of `owner/repo` names configured as stacks. Cost is a single unauthenticated HTTP GET per probe.

### Recommendation
Add the same `current_user.logged_in?` (or full authentication) gate to `#check` that `#show` already has, or remove `check`/`show` from `skip_authentication` and instead authorize based on `current_user.stacks_contributed_to`/team membership for the resolved stack. Do not resolve a stack for unauthenticated requests.

### Proof of Concept
```ruby
# test/controllers/merge_status_controller_test.rb
test "GET check is accessible without any session and leaks arbitrary stack status" do
  session.delete(:user_id) # no Shipit session at all
  get :check, params: { referrer: 'https://github.com/Shopify/shipit-engine/pull/42', branch: 'master' }, format: :json
  assert_response :success # or :service_unavailable, but a response is returned — no auth redirect
  body = JSON.parse(response.body)
  assert body.key?('stack_status') # status of shipit-engine stack disclosed unauthenticated
end
```
This demonstrates that `check` returns stack status data without `session[:user_id]` present, in contrast to `show`, confirming the authentication asymmetry rooted in `skip_authentication only: %i[check show]` combined with the missing `logged_in?` guard in `#check`.
