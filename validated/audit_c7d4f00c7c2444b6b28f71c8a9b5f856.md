### Title
Cross-organization webhook forgery — signature is verified against `repository.owner.login`/`organization.login` but handlers act on `repository.full_name` (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook based on `repository.owner.login` (falling back to `organization.login`), while the handlers that actually mutate state (e.g. `PushHandler`, `MembershipHandler`) resolve the target `Repository`/`Team` from a *different* field of the very same JSON body — `repository.full_name` or `organization.login` used independently to create/attach `Team` records. Nothing ties these fields together, so the field that is cryptographically bound to the signature is not the field that determines which repository/organization gets acted upon.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This chooses which per-organization `webhook_secret` (Shipit supports one GitHub App/secret per organization — see the multi-org config block) is used to HMAC-verify the raw payload. [3](#0-2) 

The signature check itself only proves *some* payload byte-for-byte matches an HMAC computed with the secret belonging to whatever organization name was read out of `repository.owner.login`/`organization.login` — it does not constrain any other field in that same JSON body:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [4](#0-3) 

Downstream, `Handler#stacks` and `Handler#repository_name` resolve the target repository from `repository.full_name`, not from `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

Because `full_name` and `owner.login` are two independent JSON keys under `repository`, an org that legitimately owns its own GitHub App/`webhook_secret` entry in Shipit's multi-org config can produce a validly-signed payload where `repository.owner.login` (or `organization.login`) is its own org name (so the signature check picks its own secret and passes) while `repository.full_name` names a repository belonging to a different, victim organization. `PushHandler` will then call `stack.sync_github` on the victim stack it resolves via `full_name`, and `MembershipHandler` similarly binds team membership using `params.team`/`params.organization` fields independently of the field used for signature-secret selection, allowing team/organization data to be forged relative to what was actually authenticated. [6](#0-5) [7](#0-6) 

This is the direct analog of the reported bug class: a value used to compute/authorize an action (`repository.full_name`, `organization.login` used for team creation) is never cross-checked against the value that was actually covered by the trust-establishing check (`repository.owner.login` used to pick the webhook secret) — same "field acted upon vs field verified" split as the oracle answer never being range-checked against the field actually trusted.

### Impact Explanation
`MembershipHandler` writes `Team`/`Membership` records keyed by `params.team.id` and `params.organization.login` [8](#0-7) , and Shipit's own login authorization is gated on `Shipit.github_teams` membership (per `docs/setup.md`'s `github.oauth.teams` restriction). An org holding its own legitimately-configured webhook secret could forge `membership` events naming a `team.id`/`organization.login` belonging to a privileged team it does not own, letting it add arbitrary GitHub users (including attacker-controlled accounts) into `Shipit.github_teams`-authorized teams, which is an authorization-escalation path into `Shipit.github_teams`. Similarly, `push`/`status`/`check_suite` events can be forged to reference a victim organization's repository (`full_name`), forcing unauthorized `sync_github`, status changes, and check-run refreshes against stacks the forging org does not own — reading/mutating another organization's stack state without ever presenting that organization's own webhook secret.

### Likelihood Explanation
This requires the Shipit instance to be configured for multiple GitHub organizations (the documented multi-org config format), and requires the attacker to control one legitimately-registered organization's GitHub App/webhook secret — a credential normal, low-privileged tenant organizations possess by design in that deployment model. No GITHUB_TOKEN, `api_clients_secret`, or Shipit session is needed; only the attacker's own organization's webhook secret, which is not privileged with respect to other tenants' repositories.

### Recommendation
Bind the signature-verification identity to the same field used for repository/team resolution: require that `repository.owner.login` equals the owner segment of `repository.full_name`, and for `membership`/`team` events, verify `organization.login` matches the org whose secret validated the signature before creating/updating `Team` records. Reject the webhook if these fields disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.example.yml` multi-org format).
2. As an admin of `attacker-org`'s GitHub App, craft a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<malicious_sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Sign the raw body with `attacker-org`'s `webhook_secret` and send it with header `X-Hub-Signature: sha1=<hmac>`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature validates successfully. [1](#0-0) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` from `repository.full_name` and invokes `stack.sync_github(expected_head_sha: "<malicious_sha>")` on the victim's stack, despite the request only ever being authenticated against `attacker-org`'s secret. [6](#0-5)
