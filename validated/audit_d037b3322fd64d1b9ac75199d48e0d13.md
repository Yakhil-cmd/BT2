### Title
Webhook signature is verified against the organization named in the payload, not the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the `X-Hub-Signature` against based on `repository_owner`, a value read straight out of the untrusted, attacker-supplied JSON body. `Webhooks.for_event` handlers (e.g. `PushHandler`, `StatusHandler`) then act on a different field of that same body - `repository.full_name` - to look up the `Stack`/`Commit` to mutate. Nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository being written to.

### Finding Description
`verify_signature` computes the signing organization purely from body content: [1](#0-0) [2](#0-1) 

It calls `Shipit.github(organization: repository_owner)`, which in a multi-org Shipit deployment picks the per-organization config (and thus the per-organization `webhook_secret`) keyed by that attacker-controlled string: [3](#0-2) 

The signature is verified only against *that* organization's secret: [4](#0-3) 

Once verification passes, the raw payload is dispatched unmodified to handlers: [5](#0-4) 

Handlers resolve the target `Repository`/`Stack` using a *different* field of the same payload - `repository.full_name` - via `Repository.from_github_repo_name`, with no check that it matches `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold but doesn't is:
`organization whose secret signed the request == owner of repository.full_name that the handler mutates`

In a Shipit instance configured for multiple GitHub organizations (`Shipit.github_organizations`, `secrets.github` keyed by org), each org has its own `webhook_secret`: [9](#0-8) 

An attacker who controls a GitHub App/organization ("OrgA") that is also configured on the same Shipit instance (a legitimate, low-privilege tenant) knows OrgA's `webhook_secret`. They can build a `push` or `status` payload whose `repository.owner.login` is `"OrgA"` (satisfying `verify_signature`, since it's HMAC'd with the secret they legitimately possess) while `repository.full_name` (and, for the `status` event, the `sha`) references a completely different, victim organization/repository ("OrgB/victim-repo") that Shipit also tracks. The signature check passes because it's validated against OrgA's secret, but `PushHandler`/`StatusHandler` act on OrgB's stack/commit because they read `full_name`/`sha` instead of `owner.login`.

### Impact Explanation
This is an authentication-binding bypass: an attacker with only their own tenant's webhook secret can forge events attributed to a different repository they have no access to.
- Via `PushHandler`, they can queue `GithubSyncJob` (`stack.sync_github`) for an arbitrary victim `Stack`, forcing Shipit to re-sync/re-fetch commits and invalidate cached deploy specs for a repository they don't own - unauthorized manipulation of stack state.
- Via `StatusHandler`, they can inject a forged commit status (`commit.create_status_from_github!`) for a real commit on a victim repository, e.g. marking a required CI context as `success`. Given Shipit's `ci.require` gating governs whether a commit is deployable, this can be used to make an otherwise-blocked commit deployable, i.e. contribute to an unauthorized deploy.

This matches the "escalation into authorization" / "unauthorized deploy" class of high-impact findings, since it lets a lower-privileged, unrelated tenant influence deploy-gating state or resync of a stack belonging to another organization on the same Shipit instance.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance is configured with multiple GitHub organizations (the "Using Multiple GitHub Applications" mode documented in `docs/setup.md`), and (2) the attacker legitimately controls one of the configured organizations (knows its `webhook_secret`) while another organization's repositories are also tracked by the same instance. This is a realistic multi-tenant self-hosted Shipit configuration, and requires no repository write access or Shipit session - only knowledge of a webhook secret for one's own (unrelated) tenant, which is explicitly not excluded by the exclusion rules (those exclude only *the target's own* `webhook_secret`/session, not an attacker's own tenant secret in a multi-org setup).

### Recommendation
In `WebhooksController#verify_signature`, after determining the organization used to validate the signature, cross-check it against the owner encoded in `repository.full_name` (and `organization.login` where relevant) before dispatching to handlers - reject the webhook if they disagree. Equivalently, handlers should derive the owning organization from the same trust-anchored value (`repository_owner` used for verification) rather than independently trusting `repository.full_name`.

### Proof of Concept
Preconditions: Shipit configured with `secrets.github` containing both `OrgA` (attacker's own GitHub App/org, secret known to attacker) and `OrgB` (victim org with a tracked `Stack` for `OrgB/victim-repo`).

1. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`, using the webhook secret they legitimately know for their own `OrgA` GitHub App.
3. POST to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies the signature against `OrgA`'s secret - succeeds.
5. `Webhooks.for_event('push')` invokes `PushHandler`, which looks up stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack - despite the request never being signed by `OrgB`.

Note: I could not execute this against a running instance; the analysis is based on static code review of the cited files. Direct confirmation of end-to-end exploitability (e.g., whether `ci.require` gating can be fully satisfied via `StatusHandler`, and exact deploy-trigger mechanics) would benefit from a full Devin session with access to run the app and its test suite.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
