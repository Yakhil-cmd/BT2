### Title
Cross-repository Status forgery via missing repository scope in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` across the *entire* database, with no repository/stack scoping, unlike `CheckSuiteHandler#process` which restricts writes to `stacks.where(branch: ...)` derived from the payload's `repository.full_name`. A `status` webhook that is validly signed for one GitHub organization/repository can therefore create a `Status` (and trigger all its side effects) on a `Commit` belonging to a completely different stack, as long as the `sha` values collide across repositories.

### Finding Description
The broken binding: for `CheckSuiteHandler`, `repository_name (payload.dig('repository','full_name')) == stack.repository.full_name` is enforced for every `stack` before any write [1](#0-0) , because `process` filters via `stacks.where(branch: params.check_suite.head_branch)` [2](#0-1) . For `StatusHandler`, this binding does not exist at all: the params schema only requires `:sha` and `:state` (no `repository` requirement, no call to `stacks`/`repository_name`), and `process` queries `Commit.where(sha: params.sha)` globally, then calls `commit.create_status_from_github!(params)` for every matching commit regardless of which stack/repository it belongs to [3](#0-2) .

`create_status_from_github!` writes a `Status` row tied to `commit.stack_id` and mutates commit/stack state (`add_status`, `Hook.emit(:commit_status/deployable_status, ...)`, `stack.schedule_merges`) [4](#0-3) [5](#0-4) .

Existing guards do not close this gap:
- `verify_signature` in `WebhooksController` validates the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e. per-organization/App-installation secret, not per-repository [6](#0-5) . Any repository that shares a GitHub App installation/organization webhook secret with a victim's repository can produce a legitimately signed `status` event (e.g. the attacker's own repo in the same org/installation, or CI reporting a status on the attacker's fork).
- `drop_unhandled_event` and `check_if_ping` are irrelevant to this path.
- `ExplicitParameters` schema for `StatusHandler` never requires `repository`, so nothing forces the payload to even carry repository info, let alone check it.
- No model validation ties `Commit#sha` uniqueness to a repository; the same `sha` string can legitimately exist as separate `Commit` rows under different stacks (e.g., forked repositories, shared history, or cherry-picked/rebased commits), and `Commit.where(sha:)` matches all of them.

Attacker flow: attacker owns/controls a repository within an organization whose GitHub App/webhook secret Shipit trusts. They cause (via GitHub CI reporting a real `status` event for their own repo, or by using the GitHub Statuses API on their own repo) a `status` webhook with `sha` equal to a commit sha that also exists in a victim stack's `commits` table (trivial when repos share history via fork/mirror, or by crafting a commit whose sha they can predict/reuse). Shipit's `WebhooksController` verifies the signature (valid, since it's a real webhook from a repo in the org), `StatusHandler.call` runs, and `Commit.where(sha: ...)` returns the victim's commit too — the attacker's status payload (`state`, `description`, `target_url`, `context`) is written onto the victim stack's commit, potentially forcing `success` status and firing `stack.schedule_merges`, `deployable_status` hooks, and continuous-delivery scheduling for a repository the attacker never authenticated against.

### Impact Explanation
A single crafted/triggered webhook lets an attacker mutate `Status` records — and downstream deploy/merge scheduling — for a `Stack`/`Commit` belonging to another repository/tenant, without ever authenticating against that repository. This matches "a payload for one repository mutating another's stack/commit" under the Critical category: it can force a commit to appear `success` and trigger `stack.schedule_merges` / continuous deployment scheduling for a victim stack. The attack is repeatable against any commit sha reachable in the shared `commits` table (e.g., shared upstream history across repos in the same org/installation), and blast radius spans all stacks whose commits share a sha with an attacker-influenced repo.

### Likelihood Explanation
Preconditions: the attacker needs a repository under the same GitHub organization/App installation trusted by Shipit (so `verify_webhook_signature` passes), and a commit `sha` that collides with a commit already tracked in a victim `Stack` (realistic for forks, mirrors, template repos, or shared monorepo history). No Shipit credentials, session, or API token are required — this is purely a webhook-signature-valid, cross-repository confusion inside `StatusHandler`. Cost to the attacker is low (control of one repo in the org, ability to trigger a `status` webhook).

### Recommendation
Add a `requires :repository { requires :full_name, String }` clause to `StatusHandler`'s params, and scope the commit lookup through `stacks` (as `CheckSuiteHandler` does), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack: stacks)`, ensuring `repository_name == stack.repository.full_name` is enforced before any `Status` is created.

```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "StatusHandler writes a Status onto a commit belonging to another repository" do
          victim_stack = shipit_stacks(:shipit)
          shared_sha = "deadbeefcafebabefeedfacecafebabecafebabe"
          victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), authored_at: Time.now, committer: shipit_users(:walrus), committed_at: Time.now, message: "victim commit")

          attacker_repo = Repository.create!(owner: "attacker-org", name: "attacker-repo")
          # attacker's own commit that happens to share the sha (fork/shared history)

          payload = {
            "sha" => shared_sha,
            "state" => "success",
            "repository" => { "full_name" => "attacker-org/attacker-repo" }
          }

          assert_difference -> { victim_commit.reload.statuses.count }, 1 do
            StatusHandler.new(payload).process
          end
          assert_equal "success", victim_commit.reload.state
        end
      end
    end
  end
end
```

```ruby
# Contrast: CheckSuiteHandler performs no cross-tenant write for the same shape
module Shipit
  module Webhooks
    module Handlers
      class CheckSuiteHandlerCrossTenantTest < ActiveSupport::TestCase
        test "CheckSuiteHandler does not touch a stack whose branch/repository doesn't match" do
          victim_stack = shipit_stacks(:shipit)
          shared_sha = "deadbeefcafebabefeedfacecafebabecafebabe"
          victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), authored_at: Time.now, committer: shipit_users(:walrus), committed_at: Time.now, message: "victim commit")

          payload = {
            "check_suite" => { "head_sha" => shared_sha, "head_branch" => victim_stack.branch },
            "repository" => { "full_name" => "attacker-org/attacker-repo" } # no such repository/stack exists
          }

          RefreshCheckRunsJob.expects(:perform_later).never
          CheckSuiteHandler.new(payload).process
        end
      end
    end
  end
end
```

The first test demonstrates `StatusHandler#process` mutates a `Status` on `victim_commit` despite the payload's `repository.full_name` belonging to the attacker, because no `stacks`/`repository_name` scoping exists. The second test shows `CheckSuiteHandler#process`, using `Handler#stacks` derived from `repository_name`, finds no matching stack (since `Repository.from_github_repo_name("attacker-org/attacker-repo")` doesn't resolve to `victim_stack`'s repository) and performs no cross-tenant job/write, confirming the asymmetry is specific to `StatusHandler#process`'s missing guard.
