## Finding

### Title
CCMenu API token scoped to one stack can be used to read the deploy/CI status of *any* stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method used by `BaseController` in a way that drops the stack-scoping check that is supposed to bind an `ApiClient` token to a single, specific stack. Any holder of a valid, stack-scoped CCMenu token can therefore read the deploy/CI status (`show` action) of any other stack in the installation, not just the one the token was minted for.

### Finding Description
`Shipit::Api::BaseController` restricts which stacks an authenticated `ApiClient` can act on by scoping the `Stack` relation to the client's `stack_id` before resolving the `:stack_id` param: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is the intended binding: `current_api_client.stack_id (the stack the token authorises) == stack resolved from params[:stack_id] (the stack touched by the action)`.

`Shipit::Api::CCMenuController` inherits from `BaseController` and only requires the coarse-grained `read:stack` permission (which is a capability check, not a stack-identity check - `ApiClient#check_permissions!` only compares `operation:scope` strings, it never compares `stack_id`): [2](#0-1) 

However, `CCMenuController` redefines `stack` itself, bypassing the scoped `stacks` helper entirely and resolving the stack directly from the unscoped `Stack` relation: [3](#0-2) 

```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

Because `stack` no longer goes through `stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), the token's stack scope is never consulted when resolving which stack's data to render. This is the exact analog of the reported bug class: two code paths compute a value with and without a required restriction applied (here, the stack_id scope check), and the path actually used to authorize/serve the request (`CCMenuController#stack`) is the one missing the restriction, while the "correct" restricted path (`BaseController#stack`/`stacks`) exists but is unused for this controller.

These scoped, low-privilege tokens are specifically minted by the (non-API) `CcmenuController#fetch` action for embedding in third-party CI/CD status-radiator tools, and are stack-scoped by design: [4](#0-3) 

### Impact Explanation
An attacker who legitimately possesses (or has obtained/leaked) a CCMenu token for stack A — a token whose entire purpose is read-only exposure of one stack's build status to external tools — can supply a different `stack_id` in the request path and read the deploy/CI status output (`Stack#deploys_and_rollbacks`, last build status/label/time, web URL, lock state) of any other stack in the Shipit instance, including stacks the token holder has no authorized visibility into. This is an authorization-scope escalation: the token authorizes stack A, but the request can be made to touch stack B. Per the stated impact categories, this is unauthenticated (relative to the target stack)/unauthorized read of stack state that the presented credential was never scoped to grant.

### Likelihood Explanation
Exploitation requires only possession of any single valid CCMenu token (`read:stack`, scoped to one stack) — a credential that is, by design, meant to be embedded in external dashboards/status-radiator tools and is not itself a high-privilege secret. No repository write access, session, or elevated permission is needed; the attacker only needs to change the `stack_id` path/query parameter of the request while reusing their own valid token.

### Recommendation
Have `Shipit::Api::CCMenuController#stack` resolve through the scoped `stacks` helper (as `BaseController#stack` does) instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Remove the private override entirely and rely on the inherited `BaseController#stack`, or add an explicit assertion that `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`. Add a regression test asserting that a token scoped to stack A returns 404/403 when `stack_id` in the request refers to stack B.

### Proof of Concept
1. As a legitimate user, request a CCMenu URL for Stack A: `GET /stacks/A/ccmenu` (via `CcmenuController#fetch`), which creates a read-only `ApiClient` scoped to Stack A and returns a URL such as `.../api/stacks/A/ccmenu.xml?token=<A_TOKEN>`. [5](#0-4) 
2. Using `A_TOKEN`, request Stack B's CCMenu endpoint instead: `GET /api/stacks/B/ccmenu.xml?token=<A_TOKEN>`.
3. `authenticate_api_client` succeeds (token A is valid) and `require_permission :read, :stack` succeeds (token A has `read:stack`). [6](#0-5) 
4. `stack` resolves `Stack.from_param!('B')` directly (ignoring that the token's `stack_id` is A), and the response renders Stack B's latest deploy/build status - confirming cross-stack read despite the token only authorizing Stack A.
