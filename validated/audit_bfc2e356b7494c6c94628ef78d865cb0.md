## Title
Cross-Repository Commit Status Forgery via Unscoped `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb](app/models/shipit/webhooks/handlers/status_handler.rb))

### Summary
The webhook signature check authenticates *which GitHub organization* a payload came from, but the event handlers that act on the payload do not verify that the *repository the payload claims to belong to* is actually the repository whose data is mutated. In particular, `StatusHandler` updates commit-status records purely by SHA, with no repository/stack scoping at all, breaking the binding "organization that authenticated == repository that is written."

### Finding Description
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC against using the payload's `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

Once the signature is accepted, the raw JSON body is dispatched unchanged to handlers: [3](#0-2) 

Most handlers scope their effect through `repository_name = payload.dig('repository', 'full_name')`: [4](#0-3) 

`StatusHandler`, however, does not use `repository_name`/`stacks` at all — it looks up commits **globally by SHA** and writes a status to every match: [5](#0-4) 

In a Shipit deployment configured for multiple GitHub organizations (a documented, supported setup with per-organization `webhook_secret`s): [6](#0-5) 
each org's admin legitimately knows only their own org's `webhook_secret`. The signature check only proves "this payload's HMAC matches OrgA's secret" — it proves nothing about the `sha`, `state`, `context`, or any other field in the body, since Octokit-style webhooks sign the whole raw body but Shipit never cross-checks that the signed organization actually owns the repository/commit the handler mutates.

An admin/maintainer of a repository in OrgA (an "unprivileged" actor with respect to any other tenant/org on the same Shipit instance) can:
1. Reconstruct a git commit object with byte-identical tree/parents/author/committer/message/timestamps as a target commit that is tracked by a stack belonging to a *different* organization (feasible when the target repository's commit is public, or otherwise known/predictable), producing an identical SHA1 in a repo they control under OrgA.
2. Configure/trigger a real `status` webhook from that OrgA repository (which GitHub signs with OrgA's real `webhook_secret`), with `state: "success"`.
3. `verify_signature` authenticates the payload against OrgA's secret and passes it through, because `repository_owner` resolves to OrgA.
4. `StatusHandler#process` ignores `repository.full_name` entirely and calls `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, writing a forged "success" status onto the *other organization's* commit record — one the attacker has no access to and never authenticated for.

### Impact Explanation
Commit statuses feed Shipit's mergeability/deployability checks (`deployable_status`, `merge_status`) used to gate deploys and merges for stacks the attacker does not own. Forging a "success" status on an unrelated organization's commit can unblock or trigger an unauthorized deploy/merge decision on a repository outside the attacker's authenticated organization, satisfying the "unauthorized deploy, rollback, or merge" / "cross-repository writes" impact bar.

### Likelihood Explanation
Exploitation requires: (a) a Shipit instance configured for multiple GitHub organizations sharing one deployment (a documented supported configuration), (b) the attacker being a legitimate low-privilege member/admin of one tenant organization able to trigger a real webhook signed with that org's secret, and (c) constructing a commit with a colliding SHA against a known/public target commit. This is a non-trivial but concrete and reproducible chain that requires no possession of another tenant's secret, no `ApiClient` token, and no privileged Shipit account — only the credentials an ordinary tenant already legitimately has for their own org.

### Recommendation
In `Handler#stacks` / `StatusHandler#process`, scope commit lookups to the repository declared in the same payload (`repository.full_name`) and additionally verify that this repository's owner matches the `repository_owner`/organization used to authenticate the webhook, rejecting payloads where the two disagree. Apply the same repository ownership cross-check inside `WebhooksController#verify_signature` for all events, not just implicitly relying on individual handlers to filter correctly.

### Proof of Concept
```
1. Deploy Shipit with multi-org github config: OrgA (webhook_secret=S_A) and OrgB (webhook_secret=S_B).
2. Attacker controls a repo under OrgA and knows S_A (their own webhook secret).
3. Target: a commit `abc123...` belonging to a stack under OrgB/some-private-repo.
4. Attacker crafts/replicates a git commit with identical tree/parents/metadata under their OrgA repo, producing sha == abc123....
5. Attacker triggers (or forges, having S_A) a `status` event payload:
   { "sha": "abc123...", "state": "success", "context": "ci",
     "repository": { "full_name": "OrgA/attacker-repo", "owner": {"login": "OrgA"} } }
   signed with HMAC-SHA1(S_A, raw_body) in X-Hub-Signature.
6. POST /webhooks -> verify_signature resolves Shipit.github(organization: "OrgA"), validates OK.
7. StatusHandler#process runs `Commit.where(sha: "abc123...")` — matches OrgB's commit record — and writes
   a forged "success" status onto it, despite the attacker having no relationship to OrgB.
``` [7](#0-6) [8](#0-7)

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
