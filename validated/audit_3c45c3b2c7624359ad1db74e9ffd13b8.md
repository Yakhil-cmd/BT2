## Finding

An `ApiClient` scoped to a single stack (`stack_id` set) can still create, read, update, and delete **global** hooks via `/api/hooks`, which receive events from *every* stack in the Shipit instance — breaking the binding between "the stack a token authorizes" and "the stacks whose data the token can actually touch."

### Root cause

`ApiClient` supports scoping to a single stack via `stack_id`, and `Api::BaseController#stacks`/`#stack` correctly enforce that scope for stack-nested resources: [1](#0-0) 

However, `Api::HooksController` derives the hook's `stack_id` purely from the URL params, not from `current_api_client.stack_id`: [2](#0-1) 

The route table exposes both a stack-nested hooks resource and a top-level, unscoped one that maps to the same controller: [3](#0-2) 

When called via `/api/hooks` (no `stack_id`), `HooksController#stack_id` returns `nil`, and `hooks.create(params)` builds a hook with `stack_id: nil`, i.e. a "global" hook: [4](#0-3) 

Global hooks are delivered for **every** stack's events, because `Hook.deliver` selects `for_stack(stack_id)`, which matches `stack_id IN (nil, stack_id)`: [5](#0-4) [4](#0-3) 

The only authorization check on `HooksController` is the generic, non-stack-scoped `write:hook`/`read:hook` permission: [6](#0-5) 

Nothing in `require_permission`/`check_permissions!` considers `current_api_client.stack_id`: [7](#0-6) 

### Binding broken

`current_api_client.stack_id` (the stack the token is supposed to be limited to, as enforced everywhere else via `Api::BaseController#stacks`) ≠ the set of stacks whose task/deploy events the token can register to receive or read once it holds `read:hook`/`write:hook` and calls the non-nested `/api/hooks` route.

### Impact

An attacker holding a stack-scoped `ApiClient` token (e.g. one issued for CI integration on a single, low-sensitivity stack) that also carries `read:hook`/`write:hook` permissions can:
- `POST /api/hooks` with `delivery_url` pointing to an attacker-controlled server and `events: [deploy, rollback, ...]`, causing Shipit to push deploy/task status, output links, and commit metadata for **every** stack in the instance to the attacker — an unauthorized read of stack state / task and deploy output across repositories the token was never meant to access.
- `GET /api/hooks` to enumerate all other global hooks (delivery URLs, event subscriptions) configured for the whole instance.

This matches the High-severity criterion "unauthenticated/unauthorized read of stack state, task streams or deploy output" via a cross-stack authorization escalation, reachable with nothing more than a legitimately-issued, narrowly-scoped API token (no webhook secret, no GitHub App key, no privileged account required beyond the scoped token itself).

### Recommendation

`Api::HooksController` should reject or scope hook creation/listing to `current_api_client.stack_id` when the client is stack-scoped — e.g., raise `ApiClient::InsufficientPermission` (or 404) if a scoped client attempts to hit the global `/api/hooks` route or list/manage hooks with `stack_id: nil`.

### Uncertainty

I could not fully trace which real-world `ApiClient` fixtures/configurations combine `stack_id` scoping with `write:hook`/`read:hook` permissions in this codebase's default setup (the sample fixtures I found, e.g. `here_come_the_walrus`, only grant `read:stack`). Whether this is exploitable in a given deployment therefore depends on whether operators issue stack-scoped tokens with hook permissions — the code itself contains no restriction preventing that combination, but I did not locate a concrete first-party example of it being granted by default. A full confirmation would require running the controller test suite / exercising `ApiClient.create!(stack:, permissions: %w[write:hook])` against `/api/hooks`, which requires execution access I don't have here.
