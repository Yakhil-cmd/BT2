### Title
Cross-repository status/commit forgery via organization-scoped webhook signature bound to an unscoped commit lookup - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify an inbound webhook against using an **attacker-influenced field of the payload itself** (`repository.owner.login` / `organization.login`), then delegates to handlers that act on **a different, unscoped field** (`Commit.where(sha:)` with no repository/stack filter at all). This breaks the binding "the organization that authenticated" == "the repository/commit that is written," analogous to the Node.js report's `path.resolve()` (verification) vs. `Buffer.from()` (actual write) desync caused by trusting a value that was validated for one purpose but consumed for another.

### Finding Description
`WebhooksController#verify_signature` picks the verifying `GitHubApp` instance like this: [1](#0-0) 
where `repository_owner` is read straight out of the untrusted JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to whichever `GitHubApp` config entry matches that login (relevant in the documented multi-organization setup where each org has its own distinct `webhook_secret`, see `docs/setup.md` "Using Multiple Github Applications"). The signature check therefore only proves that *some* configured organization's secret produced this payload — it says nothing about which repository or commit the payload's other fields refer to.

Once the signature is accepted, the `status` handler acts on the payload with **no repository scoping whatsoever**: [3](#0-2) 
`Commit.where(sha: params.sha)` searches every commit across every stack/repository tracked by the Shipit instance, not just commits belonging to the organization that produced a valid signature. The base `Handler` class does define a `repository_name`/`stacks` scoping helper derived from `payload.dig('repository', 'full_name')`, used by other handlers (`PushHandler`, `CheckSuiteHandler`), but `StatusHandler` never applies it: [4](#0-3) 

**Binding broken:** `organization authenticated by verify_signature (repository.owner.login)` ≠ `repository/commit actually mutated (Commit.where(sha:) — unscoped)`.

### Impact Explanation
An entity that legitimately controls a GitHub App/organization already tracked by a shared Shipit instance (e.g., a customer/team onboarded under the documented multi-org configuration, who therefore knows their own org's `webhook_secret`) can forge a `status` webhook payload:
- valid HMAC signed with *their own* org's `webhook_secret` so `verify_signature` passes,
- but with `sha` set to a commit SHA belonging to a **different organization's/repository's stack** also tracked by the same Shipit instance.

`StatusHandler` will then create a fabricated `Status` (`create_status_from_github!`) on that unrelated commit with attacker-chosen `state`, `context`, and `description`. Because `ci.require` in `shipit.yml` gates deploys/continuous delivery purely on the presence of matching commit statuses, an attacker can inject a spoofed passing status for a victim commit they have no access to, satisfying CI requirements and enabling an unauthorized deploy on a stack/repository outside their authorization — a cross-repository write into another organization's deploy pipeline using credentials the attacker legitimately holds only for their own, unrelated organization.

### Likelihood Explanation
Requires the deployment to be configured with more than one GitHub organization (an explicitly documented and supported configuration), and requires the attacker to already control (or have compromised) one of the lower-trust organizations onboarded to the shared Shipit instance — no access to the victim organization, no `ApiClient` token, and no Shipit session is needed to send the forged webhook itself, only knowledge of a secret they legitimately possess for their own org's App.

### Recommendation
Bind the verified webhook signature to the same repository/organization identity that handlers subsequently use to look up commits/stacks. Concretely: after signature verification, re-derive and enforce that the resolving `repository_owner` matches `payload.dig('repository', 'full_name')`'s owner, and scope `StatusHandler#process` (and any other handler consuming `sha`/commit identifiers) through the same `stacks`/`repository_name` scoping helper already used by `PushHandler` and `CheckSuiteHandler`, rather than a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Shipit is configured per `docs/setup.md`'s "Using Multiple Github Applications" with `OrgAttacker` and `OrgVictim`, each with its own GitHub App and distinct `webhook_secret`.
2. Attacker controls `OrgAttacker`'s GitHub App config and therefore knows `OrgAttacker`'s `webhook_secret`.
3. Attacker looks up (via normal, unauthenticated read of public commit data, or a prior legitimate webhook they observed) a commit `sha` currently deployable in `OrgVictim/victim-repo`'s Shipit stack, which has `ci.require` set in its `shipit.yml`.
4. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgAttacker/irrelevant-repo" }
}
```
   with `X-Hub-Signature` computed using `OrgAttacker`'s `webhook_secret` over the raw body.
5. `verify_signature` resolves `Shipit.github(organization: "OrgAttacker")` and accepts the signature.
6. `StatusHandler#process` runs `Commit.where(sha: "<victim-commit-sha>")`, finds the victim's commit regardless of organization, and calls `commit.create_status_from_github!`, injecting a spoofed passing status that can satisfy `ci.require` and unblock continuous delivery/deploy for `OrgVictim`'s stack — despite the attacker never having any credential or access tied to `OrgVictim`.
