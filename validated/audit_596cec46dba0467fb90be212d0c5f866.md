### Title
Stack-scoped ApiClient tokens can read the state of arbitrary stacks via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports an optional `stack` association used to restrict a token to a single stack, enforced centrally in `Api::BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` with an unscoped lookup, breaking that binding and letting any stack-scoped token read any stack's CI/deploy status.

### Finding Description
`Shipit::ApiClient` can be bound to a single `stack` (`belongs_to :stack, optional: true`), as shown by the `here_come_the_walrus` fixture (`stack: shipit`, `permissions: ['read:stack']`). [2](#0-1) 

The engine enforces this per-token stack restriction centrally: `Api::BaseController#stacks` narrows the queryable set to `Stack.where(id: current_api_client.stack_id)` when the token has a `stack_id`, and `#stack` looks the requested stack up through that scoped relation (`stacks.from_param!(params[:stack_id])`). [3](#0-2) 

This scoping is exactly what the `stacks_controller_test.rb` test "an api client scoped to a stack will only see that one stack" verifies for `#index`. [4](#0-3) 

However, `Api::CCMenuController` does not inherit that scoped lookup. It overrides `#stack` with a direct, unscoped query:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

The only authorization check applied to this action is `require_permission :read, :stack`, which merely calls `current_api_client.check_permissions!(:read, :stack)` — a check against the token's static `permissions` array, with no reference to which specific stack the token is bound to. [6](#0-5) [1](#0-0) 

Consequently, a token that authorizes `read:stack` on stack A only (its `stack_id` binding) is treated as authorizing `read:stack` on any stack whose id/slug is supplied in the URL, because the code path that would restrict the query to the token's own stack (`stacks.from_param!`) is bypassed for this one controller. The equality that should hold — "stack a token authorises == stack a token touches" — is broken specifically for `GET /api/stacks/*stack_id/ccmenu`.

### Impact Explanation
This is an unauthenticated-relative-to-scope read of stack state: a token that was deliberately restricted (by whoever set up the `stack` association on the `ApiClient` record, e.g., to hand a narrowly scoped credential to a CCMenu dashboard/CI widget for one project) can be replayed against the `ccmenu` route for any other stack in the Shipit instance to obtain that stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc.), which the token holder was never meant to see. This matches the listed High-impact category "unauthenticated read of stack state, task streams or deploy output" relative to the token's own authorized scope.

### Likelihood Explanation
Any holder of a stack-scoped, `read:stack`-permissioned `ApiClient` token — which is by design a low-privilege, narrowly-scoped credential meant for read-only status reporting — can trivially trigger this by changing the `stack_id` segment of the CCMenu URL to another stack's identifier. No other credential, session, or write access is required beyond possessing that one legitimately-issued, narrowly-scoped token.

### Recommendation
Remove the `stack`/`authenticate_api_client` override's unscoped lookup in `Api::CCMenuController` and reuse the inherited, properly scoped `Api::BaseController#stack` (backed by `#stacks`, which already applies `current_api_client.stack_id` restriction) instead of calling `Stack.from_param!` directly.

### Proof of Concept
1. An operator creates a stack-scoped `ApiClient` for stack `org/repo-a/production` with permission `read:stack` only (as in fixture `here_come_the_walrus`, `stack: shipit`) and hands its `authentication_token` to a third party for embedding a CCMenu widget for that one stack.
2. The third party (or anyone who obtains this narrowly-scoped token) issues `GET /api/stacks/org/other-repo/other-env/ccmenu` using Basic auth with that same token.
3. `Api::CCMenuController#authenticate_api_client` authenticates the token successfully; `require_permission :read, :stack` passes because the token's `permissions` includes `read:stack`; `#stack` resolves via unscoped `Stack.from_param!`, returning `org/other-repo/other-env` regardless of the token's `stack_id`.
4. The response renders the CCMenu XML status for `org/other-repo/other-env`, a stack the token was never authorized to see.
