### Title
Global `Shipit.github_teams` only enforces the first configured org's team restriction across all orgs in multi-org mode - ([File: lib/shipit.rb])

### Summary
In multi-GitHub-App (multi-org) configurations, `Shipit.github_teams` derives its list of allowed teams from `Shipit.github` with no organization argument, which always resolves to `github_default_organization` — the *first* key under `secrets.github`. `User#authorized?` and `force_github_authentication` then apply this single, first-org-only team list uniformly to every stack and repository regardless of which configured GitHub organization actually owns them, so a second (or further) org's stricter `oauth.teams` restriction is never evaluated.

### Finding Description
The intended binding is: `current_user.authorized?` for a stack under organization `O` should equal "current_user is a member of a team listed in `O`'s `github.oauth.teams`". The actual code computes:

- `Shipit.github_teams` = `github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }` [1](#0-0) 
- `github` with no `organization:` argument resolves via `github_default_organization`, which is `secrets.github.keys.first` unless the legacy single-org schema is used [2](#0-1) 

So `Shipit.github_teams` is a single, global, memoized array built exclusively from the **first** organization block in `secrets.github`, no matter how many organizations are configured (as documented in `docs/setup.md`'s "Using Multiple Github Applications" section, which shows two orgs each with independent `oauth.teams` lists — out of scope to cite as vulnerable code, but it establishes the expected multi-org semantics).

`User#authorized?` then checks membership against this single global list:
```
@authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
``` [3](#0-2) 

`force_github_authentication`, the single global gate applied to every controller action in the engine, uses this same `authorized?` check with no per-stack or per-repository organization scoping:
```
elsif Shipit.authentication_disabled? || current_user.logged_in?
  unless current_user.authorized?
    ...forbidden...
``` [4](#0-3) 

Nowhere in the request path (stacks, tasks, deploys, rollbacks, merges) is `current_user.authorized?` re-evaluated against the organization that owns the specific `Repository`/`Stack` being acted on — it's a single global boolean computed once per request and reused for all resources.

Concretely, an operator who configures:
```
github:
  OrgOne:
    oauth: { teams: [OrgOne/public-contractors] }   # broad/loose team
  OrgTwo:
    oauth: { teams: [OrgTwo/core-admins] }          # narrow/sensitive team
```
intends members of `OrgOne/public-contractors` to be excluded from `OrgTwo`'s stacks. But `Shipit.github_teams` only ever returns `Team` objects for `OrgOne/public-contractors` (the first hash key), so `OrgTwo/core-admins` is never consulted. Any GitHub user who is a member of `OrgOne/public-contractors` — after completing the normal (non-privileged) OAuth login flow available to any GitHub user Shipit invites to authenticate — passes `authorized?` globally and can then browse, deploy, and roll back **`OrgTwo`'s** stacks and tasks through the normal UI/API routes, since none of those routes re-check organization-specific team membership.

### Impact Explanation
Any authenticated Shipit user (a member of only the first-configured org's team) gains full access to trigger deploys, rollbacks, and merges on stacks that belong to a second, supposedly more restricted organization, because the second organization's `oauth.teams` restriction is silently never enforced. This is a full authorization-boundary bypass across tenants that share one Shipit instance but expect independent team-based access control per GitHub organization — matching "escalation into `Shipit.github_teams` authorization" and, once the user reaches stack actions, "an unauthorized deploy, rollback" against a repository/org they were never granted access to.

### Likelihood Explanation
Preconditions: the Shipit operator must use the documented multi-org configuration schema (`secrets.github` with organization names as top-level keys, each with its own `oauth.teams`) — this is a supported, documented configuration, not a misconfiguration. Attacker cost is minimal: any GitHub user who is a member of the first-listed org's configured team (a legitimate, low-privilege team membership, e.g. "public-contractors") can log in normally and immediately gets `authorized? == true` engine-wide. No secrets, tokens, or additional privileges are required beyond completing the standard OAuth login already available to them.

### Recommendation
Scope authorization per organization: compute the allowed team set from the specific organization that owns the resource being accessed (e.g., `Shipit.github(organization: repository_org).oauth_teams`) rather than from `Shipit.github` (unscoped/first-org). `User#authorized?` should accept (or a controller-level check should pass) the organization of the target stack/repository, and `force_github_authentication` needs a per-resource authorization check in addition to (or instead of) the current global one.

### Proof of Concept
```ruby
# test/models/users_test.rb (conceptual addition)
test "authorized? ignores the second org's team restriction in multi-org mode" do
  secrets = ActiveSupport::OrderedOptions.new
  secrets.merge!(YAML.load_file('test/dummy/config/secrets_double_github_app.yml'))
  secrets.deep_symbolize_keys!
  Shipit.stubs(:secrets).returns(secrets)

  org_one_team = Shipit::Team.create!(organization: 'OrgOne', slug: 'public-contractors', github_id: 1)
  org_two_team = Shipit::Team.create!(organization: 'OrgTwo', slug: 'core-admins', github_id: 2)

  Shipit.github(organization: 'OrgOne').stubs(:oauth_teams).returns(['OrgOne/public-contractors'])
  Shipit.github(organization: 'OrgTwo').stubs(:oauth_teams).returns(['OrgTwo/core-admins'])

  user = shipit_users(:bob)
  user.teams << org_one_team # user only belongs to OrgOne's loose team, NOT OrgTwo's admins

  # Binding under test: authorized? for OrgTwo's resources should require OrgTwo/core-admins membership
  assert_equal ['OrgOne/public-contractors'], Shipit.github_teams.map(&:handle) # only first org considered
  assert user.authorized? # BUG: true, even though user has no OrgTwo/core-admins membership
ensure
  Shipit.unstub(:secrets)
end
```
This demonstrates that `Shipit.github_teams` (and therefore `User#authorized?` and `force_github_authentication`) never includes `OrgTwo`'s configured team, so membership scoped to `OrgOne` alone satisfies the global authorization gate for all resources, including those under `OrgTwo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end
```
