### Title
Permanent market freeze via `scaled_to_original` overflow during accrual — every pool verb accrues first, so a whale book at sustained high utilization bricks repay, withdraw, and liquidation forever - ([File: common/src/rates/scaling.rs](common/src/rates/scaling.rs))

### Summary
Analog of CVE-2022-42929 (a single crafted action causes a denial of service that persists beyond restart): a sufficiently large debt position makes the market's accrued RAY value exceed `i128::MAX` *before* the borrow-index ceiling engages. Because `global_sync` runs `accrue_step` — which calls `scaled_to_original(borrowed, borrow_index)` — at the head of every state-changing entrypoint, the resulting `MathOverflow` panic bricks `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `update_indexes`, and `recapitalize` on that market permanently. All supplier and borrower funds in the market are frozen forever; the panic is state-driven, so no retry, restart, or TTL bump can clear it.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60` computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)`, and `scaled_to_original` (`common/src/rates/scaling.rs:14`) is a plain `Ray::mul` that panics with `GenericError::MathOverflow` on overflow — it does not saturate. `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY` (10^36), but the *value* `borrowed × borrow_index` hits `i128::MAX` far earlier: the ceiling is ~170× the raw-asset value, so ~1 billion whole 18-decimal tokens of debt at index ×170 overflows while the index is still far under its cap (`docs/reference/formulas.md:432-437` confirms this ordering). `global_sync` (`contracts/pool/src/interest.rs:20-33`) invokes `accrue_step` before any user action, and `Cache::load` path is shared by every verb, so once `borrowed_scaled × borrow_index ≥ i128::MAX`, every subsequent call to that market reverts inside accrual. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`) demonstrates exactly this: `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW`, and `last.borrow_index < MAX_BORROW_INDEX_RAY`.

### Impact Explanation
Permanent freezing of user funds and protocol insolvency, matching two accepted impact classes. Suppliers cannot withdraw (their cash sits in the market's shared pool balance), borrowers cannot repay, and liquidators cannot liquidate — so both honest collateral and outstanding debt are locked for the lifetime of the contract. Bad debt in the frozen market can never be socialized (`clean_bad_debt` accrues first), and `recapitalize` cannot inject backing. Unlike a pause, no governance flag or upgrade-light path exists to skip the accrual head; only a contract upgrade would unlock the market.

### Likelihood Explanation
Medium. The trigger is fully permissionless: `supply` and `borrow` are open entrypoints, caps are set high enough to admit whale books (`max_cap_for_decimals` allows ~170 billion whole tokens), and utilization can be pushed near max by a single borrower. The blocker is economic, not structural — the attacker must source on the order of 1B whole tokens of an 18-decimal asset and keep utilization high for the years of compounding needed to grow the index past ~170× (the test uses a steep 175%-APR curve). Accrual then advances via the permissionless `update_indexes`, so the freeze can be triggered by anyone once the book is ripe. The docs acknowledge the cliff as an arithmetic limit, but no mitigation prevents reaching it, so it stands as a real reachable state.

### Recommendation
Saturate rather than panic on the accrual-path unscale: make `scaled_to_original` calls inside `accrue_step`/`calculate_supplier_rewards` use `mul_div_floor_saturating`-style bounded arithmetic, or clamp `borrowed_original`/`supplied_original` to a `MAX_RAY_VALUE` sentinel so `update_borrow_index` reaches `MAX_BORROW_INDEX_RAY` (where accrual legitimately stops) before the value overflows `i128`. Alternatively, enforce entry caps low enough per asset that `max_scaled × MAX_BORROW_INDEX_RAY < i128::MAX`, so the index ceiling is always reached first.

### Proof of Concept
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))      // 175% max APR curve
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
let principal = BILLION * 10i128.pow(18);            // 1e27 raw = 1e36 ray? -> cliff domain
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;                     // 98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// advance years until accrual panics
if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
assert_contract_error(failed, errors::MATH_OVERFLOW);
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY);   // cap never engaged

// market permanently frozen:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause chain: `pool::interest::global_sync` → `accrue_step` → `scaled_to_original(borrowed, borrow_index)` → `Ray::mul` panic at `i128` overflow — reached before the `MAX_BORROW_INDEX_RAY` cap can stop accrual, and unavoidable on every subsequent entrypoint.
