### Title
Fee-on-Transfer ERC20 Token Causes Bridge Undercollateralization and Unauthorized Cross-Chain Asset Minting — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` assume the bridge receives exactly `_value + _feeLimit` tokens from the caller. For fee-on-transfer ERC20 tokens, the bridge receives less than that amount, yet emits `RequestValueTransfer` with the full caller-supplied `_value`. Counterpart bridge operators observe this event and call `handleERC20Transfer(_value)`, minting or transferring `_value` tokens to the recipient — more than were actually deposited. In lock/unlock mode (`modeMintBurn = false`) this silently undercollateralizes the bridge with every transfer; in mint/burn mode the burn step reverts, but the fee and refund transfers have already consumed tokens the bridge does not fully hold.

---

### Finding Description

In `requestERC20Transfer`:

```solidity
// BridgeTransferERC20.sol line 133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

The bridge pulls `_value + _feeLimit` from the caller. For a fee-on-transfer token with rate `r`, the bridge actually receives `(_value + _feeLimit) × (1 − r)`. No balance-before/after check is performed. `_requestERC20Transfer` then calls `_payERC20FeeAndRefundChange` and emits `RequestValueTransfer` with the original `_value`:

```solidity
// BridgeTransferERC20.sol lines 97-106
emit RequestValueTransfer(
    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,          // ← caller-supplied, not actual received amount
    requestNonce,
    fee,
    _extraData
);
```

The counterpart bridge operators read this event and call `handleERC20Transfer` with `_value`, which transfers or mints `_value` tokens to the recipient:

```solidity
// BridgeTransferERC20.sol lines 68-72
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
```

The same flaw exists in the 1-step path: `ERC20ServiceChain.requestValueTransfer` transfers `_amount + _feeLimit` to the bridge and then calls `onERC20Received(msg.sender, _to, _amount, _feeLimit, ...)`, which passes the caller-supplied `_amount` directly into `_requestERC20Transfer` without verifying actual receipt.

`_payERC20FeeAndRefundChange` compounds the issue: it attempts to transfer `fee` to `feeReceiver` and `feeRefund` back to `from` from the bridge's balance, but each of those outgoing transfers also incurs the token's transfer fee, further depleting the bridge's actual holdings below what the accounting assumes.

There is no `nonReentrant` guard on `requestERC20Transfer` or `onERC20Received` (unlike `BridgeTransferKLAY._requestKLAYTransfer` which is explicitly `nonReentrant`), leaving an additional surface for a malicious token's `transfer`/`transferFrom` hook to re-enter.

---

### Impact Explanation

**Lock/unlock mode (`modeMintBurn = false`):** The source bridge holds `_value × (1 − r) − _feeLimit × r` tokens per request but has committed to pay `_value` on the counterpart chain. After N requests the bridge is short by `N × (_value × r + _feeLimit × r)` tokens. When users bridge back, `handleERC20Transfer` calls `safeTransfer(_to, _value)` and reverts once the bridge's balance is exhausted — freezing all pending withdrawals and stranding bridged assets.

**Mint/burn mode (`modeMintBurn = true`):** The `burn(_value)` call will revert because the bridge's actual balance after fee and refund payouts is `_value × (1 − r) − _feeLimit × r < _value`. This makes every deposit attempt fail, but the fee and refund transfers have already executed, consuming tokens the bridge did not fully receive.

In both modes the `RequestValueTransfer` event is emitted with an inflated `_value`, so counterpart operators will attempt to mint/transfer more tokens than were deposited — an unauthorized cross-chain asset issuance.

---

### Likelihood Explanation

The bridge owner must register a fee-on-transfer token via `registerToken` (onlyOwner). This is a prerequisite, but it is not an unlikely one: fee-on-transfer tokens are common (e.g., reflection tokens, tokens with protocol fees), and `registerToken` performs no validation of token behavior — only that the counterpart address is non-zero. Once registered, any unprivileged user can trigger the undercollateralization by calling `requestERC20Transfer` or `requestValueTransfer` on the token contract. The bridge contract itself has no mechanism to detect or reject fee-on-transfer tokens.

---

### Recommendation

1. **Measure actual received amount** using a balance-before/after pattern in `requestERC20Transfer` and `onERC20Received`:
   ```solidity
   uint256 balBefore = IERC20(_tokenAddress).balanceOf(address(this));
   IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
   uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balBefore);
   require(actualReceived >= _value.add(_feeLimit), "fee-on-transfer token not supported");
   ```
2. **Emit `RequestValueTransfer` with the actual net value** (after fee deduction), not the caller-supplied `_value`.
3. **Add `nonReentrant`** to `requestERC20Transfer` and `onERC20Received` to match the protection already present on the KLAY path.
4. **Document and enforce** that only standard ERC20 tokens (no transfer fees, no rebasing) may be registered.

---

### Proof of Concept

**Setup:** Deploy a fee-on-transfer ERC20 token `FeeToken` that deducts 5% on every `transfer`/`transferFrom`. Register it on both the source and counterpart bridges via `registerToken`. Set `modeMintBurn = false`.

**Steps:**

1. Alice approves the source bridge for `1.05 × 10^18` (value=1e18, feeLimit=0.05e18).
2. Alice calls `requestERC20Transfer(feeToken, bob, 1e18, 0.05e18, "")`.
3. Bridge calls `safeTransferFrom(alice, bridge, 1.05e18)`. Due to 5% fee, bridge receives `1.05e18 × 0.95 = 0.9975e18`.
4. `_payERC20FeeAndRefundChange` attempts to transfer `feeLimit = 0.05e18` back to Alice (assuming zero bridge fee). Bridge loses `0.05e18`, retaining `0.9975e18 − 0.05e18 = 0.9475e18`.
5. `RequestValueTransfer` is emitted with `_value = 1e18`.
6. Counterpart bridge operators call `handleERC20Transfer(..., 1e18, ...)`. Counterpart bridge transfers `1e18` tokens to Bob.

**Result:** Source bridge holds `0.9475e18` tokens but has paid out `1e18` on the counterpart chain. Deficit per transfer: `0.0525e18`. After ~19 such transfers the source bridge is fully drained and all subsequent `handleERC20Transfer` calls on the source chain revert, permanently freezing bridged assets.     function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
