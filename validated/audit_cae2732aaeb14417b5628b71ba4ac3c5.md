### Title
`RuleEngine.evaluate_rules` uses case-sensitive equality on `rule.action`, silently downgrading non-canonical "block" rules to warnings - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine.evaluate_rules` classifies a rule as blocking only if `rule.action == 'block'` (exact, case-sensitive string equality), and `Rule.from_dict` copies the frontmatter `action` value verbatim without normalization. Any rule file whose `action` value deviates from the exact lowercase literal `block` (e.g. `Block`, `BLOCK`, or a quoted value with embedded whitespace like `" block "`) is silently treated as a warning-only rule instead of a blocking rule. Note: the question cites `plugins/pr-review-toolkit/agents/type-design-analyzer.md`, but that file is an unrelated agent prompt with no `RuleEngine`/`Rule.from_dict` logic; the actual implementation lives in `plugins/hookify/core/rule_engine.py` and `plugins/hookify/core/config_loader.py`.

### Finding Description
Rule files (`.claude/hookify.*.local.md`) are parsed by `extract_frontmatter` and turned into `Rule` objects by `Rule.from_dict`: [1](#0-0) 
The `action` field is taken directly from frontmatter with no `.strip()`/`.lower()` normalization: `action=frontmatter.get('action', 'warn')`.

`RuleEngine.evaluate_rules` then partitions matching rules using exact string equality: [2](#0-1) 
Any value not exactly equal to the literal `'block'` (e.g. `Block`, `BLOCK`, or a value that preserves internal whitespace when quoted, since `extract_frontmatter` only strips outer whitespace and quote characters, not interior whitespace) falls into the `else` branch and is appended to `warning_rules` instead of `blocking_rules`: [3](#0-2) 
Because `blocking_rules` only gates the `permissionDecision: deny` response, a rule that is syntactically and semantically labeled as blocking in the config file produces only a `systemMessage` warning at runtime, and the tool call proceeds: [4](#0-3) 

This logic is invoked from the live PreToolUse hook path: [5](#0-4) 

### Impact Explanation
A rule file that a user/team authors (or that is planted in a shared/checked-in `.claude/` directory) with `action: Block`, `action: BLOCK`, or a quoted value with stray internal whitespace appears to enforce a hard block (per the documented contract in `plugins/hookify/README.md`, "`block`: Prevents operation from executing"), but is silently downgraded to a non-blocking warning. This breaks the "deny means deny" invariant: a dangerous tool call (e.g. `rm -rf`, credential exfiltration command) that the operator believes is hard-blocked is instead allowed to execute, with only a cosmetic warning message shown. This is a real enforcement-bypass defect in the actual guardrail mechanism, not a documentation issue.

### Likelihood Explanation
The bug triggers on ordinary, easily-produced input variance (case differences or quoted whitespace) in a config file format that is hand-authored or generated by the `/hookify` command/LLM analysis. No privilege beyond writing/committing a `.claude/hookify.*.local.md` file is required, and rules are loaded automatically on the very next tool use (per README, no restart needed), so exploitation is deterministic and repeatable once such a file is present.

### Recommendation
Normalize `action` at parse time and/or comparison time, e.g. in `Rule.from_dict`: `action=str(frontmatter.get('action', 'warn')).strip().lower()`, and validate it against an explicit allowlist (`{'warn', 'block'}`), rejecting/logging unknown values loudly (fail-closed to `block` or raise a warning) instead of silently treating anything non-`'block'` as `warn`.

### Proof of Concept
Unit/fuzz test against `RuleEngine.evaluate_rules` and `Rule.from_dict`:
```python
import pytest
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

@pytest.mark.parametrize("action_variant", ["Block", "BLOCK", " block", "block ", "BlOcK"])
def test_block_action_case_whitespace_variants_should_still_block(action_variant):
    rule = Rule(
        name="block-rm",
        enabled=True,
        event="bash",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"rm\s+-rf")],
        action=action_variant,
        message="dangerous",
    )
    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /"},
    }
    result = engine.evaluate_rules([rule], input_data)
    # Expected (intended): permissionDecision == "deny"
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", (
        f"action={action_variant!r} was downgraded to warning instead of blocking"
    )
```
Running this against current `rule_engine.py`/`config_loader.py` fails: for every variant other than the exact lowercase `'block'`, `evaluate_rules` returns only `{"systemMessage": ...}` with no `permissionDecision: deny`, confirming the block-to-warn downgrade.
