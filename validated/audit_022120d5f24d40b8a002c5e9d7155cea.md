### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but handlers act on the independent `repository.full_name` field — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to verify the HMAC signature with based on `repository.owner.login` (or `organization.login`) in the JSON body, then hands the *same raw payload* to event handlers, all of which resolve the actual `Repository`/`Stack` to act on using a **different** field: `repository.full_name`. These two fields are never cross-checked, so a party who legitimately controls a webhook secret for one organization onboarded to a Shipit instance can forge a payload whose `repository.owner.login` selects their own (verifiable) secret while `repository.full_name` points at a repository belonging to a different organization/stack on the same instance.

### Finding Description
The signature check:
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`verify_webhook_signature` HMACs the raw body against the secret configured for the org selected above:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Once verification succeeds, the controller dispatches the *entire raw payload* to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

But the base `Handler` class — used by every event handler (push, pull_request, etc.) — resolves the target repository/stack from a completely separate field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

This is used directly by `PushHandler`, which triggers a sync against whichever stack matches `full_name`:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

The same pattern (`Repository.from_github_repo_name(params.repository.full_name)`) is repeated across the pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `edited_handler.rb`, `reopened_handler.rb`), which can archive/unarchive review stacks and update pull requests. [7](#0-6) [8](#0-7) 

**Binding broken:** `verified_organization(repository.owner.login) == acted_repository(repository.full_name)` is assumed but never enforced. Shipit explicitly supports configuring multiple GitHub organizations, each with its own `webhook_secret`, on a single instance (see the multi-org example in `config/secrets.development.example.yml`), so this is a normal, documented deployment shape rather than a misconfiguration. [9](#0-8) 

**Before the attack:** Org A is legitimately onboarded to the shared Shipit instance and knows/controls its own `webhook_secret`. Org B, unrelated to Org A, has its own stacks/repositories tracked by the same instance with a different secret. Org A has no write access to Org B's stacks.

**After the attack:** Org A sends a POST to `/webhooks` with `X-Github-Event: push`, `repository.owner.login` (or `organization.login`) = `"OrgA"`, and `repository.full_name` = `"OrgB/target-repo"`, signing the raw body with `OrgA`'s own secret. `verify_signature` selects and validates against `OrgA`'s secret (which matches, since Org A crafted and signed the body), so the request passes. `PushHandler` then resolves stacks via `repository.full_name` = `OrgB/target-repo` and calls `stack.sync_github(expected_head_sha: ...)` on Org B's stack — an action Org A was never authorized to trigger.

### Impact Explanation
This lets an actor with legitimate, org-scoped webhook credentials for their own organization force actions (repo sync, pull-request/review-stack archive/unarchive, deployable-status updates) against stacks belonging to a completely different organization hosted on the same Shipit instance. Depending on continuous-delivery configuration, a forced `sync_github` can feed into auto-deploy pipelines, and forged `pull_request`/`status` events can manipulate merge/deployable state — an unauthorized cross-repository write triggered without any credential tied to the target organization/repository.

### Likelihood Explanation
Medium: requires the attacker to legitimately control (or compromise) one organization's webhook secret on a shared, multi-org Shipit deployment — not zero-privilege, but far short of the credentials the target org/repo actually requires (no GitHub token, no repo write access to the victim repo, no Shipit session). Multi-org configuration is an explicitly documented and supported setup, not a misuse of the engine.

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the organization portion of `repository.full_name` used by the handlers before dispatching the event; reject (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same verified owner field rather than trusting an independent, unauthenticated field within the same payload.

### Proof of Concept
1. Configure Shipit with two organizations, each with a distinct `webhook_secret` (as supported by `config/secrets.*.yml`).
2. As an operator/attacker of `OrgA`, craft a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1 of raw body using OrgA's webhook_secret>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` selects `Shipit.github(organization: "OrgA")` and successfully verifies the signature using OrgA's secret [10](#0-9) .
5. `PushHandler` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and calls `sync_github` on OrgB's stack, without any credential belonging to OrgB [5](#0-4) [6](#0-5) .
