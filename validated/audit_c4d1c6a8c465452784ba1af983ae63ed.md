### Title
Unauthenticated crash of full node via `throw Error(err)` in witnessing/headers_commission input validation - (File: `validation.js`)

### Summary
In `validatePaymentInputsAndOutputs`, when a unit spends a `witnessing` or `headers_commission` main-chain input, the amount is computed by calling `mc_outputs.calcEarnings` (or `paid_witnessing.calcWitnessEarnings`) with an `ifError` callback that unconditionally does `throw Error(err)` instead of returning a normal validation error via `cb(err)`. Because this callback runs inside the async validation flow (not inside a try/catch that funnels into the joint-error handling), the thrown exception propagates as an uncaught exception and, per the global handler in `network.js`, `process.on('uncaughtException', ...)` re-throws to deliberately crash the whole node process. Any unprivileged unit poster who can get a unit accepted for validation (i.e. anyone who can post a unit to the network) can reach this code path by including a `witnessing` or `headers_commission` payment input. ### Finding Description
`validatePaymentInputsAndOutputs` handles `headers_commission` and `witnessing` inputs identically: after bounds-checking `from_main_chain_index`/`to_main_chain_index` against `objValidationState.last_ball_mci` and the type-specific `getMaxSpendableMciForLastBallMci`, it calls:
```
var calcFunc = (type === "headers_commission") ? mc_outputs.calcEarnings : paid_witnessing.calcWitnessEarnings;
calcFunc(conn, type, input.from_main_chain_index, input.to_main_chain_index, address, {
    ifError: function(err){
        throw Error(err);
    },
    ifOk: function(commission){ ... }
});
``` [1](#0-0) 

For the `witnessing` type, `paid_witnessing.calcWitnessEarnings` calls `callbacks.ifError("not enough stable MC units after to_main_chain_index")` whenever the number of stable main-chain units it finds in the queried MCI window is not exactly `COUNT_MC_BALLS_FOR_PAID_WITNESSING+2`:
```
function calcWitnessEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	conn.query(
		"SELECT COUNT(1) AS count FROM units WHERE is_on_main_chain=1 AND is_stable=1 AND main_chain_index>=? AND main_chain_index<=?", 
		[to_main_chain_index, to_main_chain_index+constants.COUNT_MC_BALLS_FOR_PAID_WITNESSING+1], 
		function(count_rows){
			if (count_rows[0].count !== constants.COUNT_MC_BALLS_FOR_PAID_WITNESSING+2)
				return callbacks.ifError("not enough stable MC units after to_main_chain_index");
			mc_outputs.calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks);
		}
	);
}
``` [2](#0-1) 

This "not enough units" state is intended to be unreachable given the earlier bound `input.to_main_chain_index > max_mci` check (where `max_mci = getMaxSpendableMciForLastBallMci(last_ball_mci) = last_ball_mci - 1 - COUNT_MC_BALLS_FOR_PAID_WITNESSING`), but it depends on the assumption that every MCI in that window still has exactly one row with `is_on_main_chain=1 AND is_stable=1` at validation time on the validating node. Any divergence between the node's locally stored MC/unit rows for that historical range and what the composer/attacker assumed (e.g. reorg edge cases, retrievable-mci pruning boundaries, light/partial nodes, or races on catch-up) results in `ifError` firing, which is turned into an unguarded `throw`. Since `validate()` runs this deep inside nested async callbacks (not inside the `try{...}catch` block that funnels other errors to `ifJointError`/`ifUnitError`), the exception is not caught by `validation.js`'s own error machinery — it propagates all the way up to Node's `uncaughtException` handler in `network.js`, which explicitly re-throws to kill the process:
```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [3](#0-2) 

This mirrors the reported bug class: a normal, authenticated/unprivileged caller (any unit poster) triggers a codepath meant to signal a benign/expected error condition, but that error path is wired to an unconditional `throw` rather than a graceful validation failure, taking down the entire server process with a single crafted request.

### Impact Explanation
A successful trigger crashes the full node process entirely (denial of service for the whole node, not just the offending connection/unit), matching the "network unable to confirm new units" / process-crash impact category. Because `handleJoint`/`validate` is invoked for every unit received from peers and every unit submitted by wallets, any node running this code that receives such a unit (from a peer forwarding it, or directly from a light wallet) can be crashed, without requiring any signature bypass, double-spend, or privileged role — merely a syntactically valid unit with a `witnessing` (or, depending on further review, `headers_commission`) payment input whose from/to MCI range interacts unexpectedly with the local database state.

### Likelihood Explanation
Likelihood is Medium: the normal bounds checks in `validatePaymentInputsAndOutputs` (`to_main_chain_index > max_mci`, `from_main_chain_index < next_spendable_mc_index`) are designed to make the "not enough stable MC units" condition unreachable in the common case, so a bare-minimum malformed input alone will usually be rejected earlier with an ordinary `cb(...)` error rather than reaching `calcWitnessEarnings`. However, the invariant that `count_rows[0].count === COUNT_MC_BALLS_FOR_PAID_WITNESSING+2` always holds for any legally-bounded window is enforced only implicitly by MC/stability bookkeeping, and the code itself acknowledges fragility around MCI bookkeeping edge cases (pruning, catch-up, retrievable-MCI boundaries) elsewhere in the codebase. Regardless of the exact trigger condition, the fundamental design flaw — routing an "error" callback into an unconditional `throw` deep inside async validation, uncaught by the joint-error machinery, and then deliberately re-thrown by the global `uncaughtException` handler to kill the process — is a genuine crash-on-error design defect independent of how hard it is to hit the specific edge case.

### Recommendation
- Change the `ifError` callbacks passed to `mc_outputs.calcEarnings` / `paid_witnessing.calcWitnessEarnings` inside `validatePaymentInputsAndOutputs` to call `cb(err)` (a normal validation failure resulting in `ifUnitError`/`ifTransientError`) instead of `throw Error(err)`.
- Audit all other `throw Error(...)` calls inside deeply nested async validation callbacks reachable from unit/AA-trigger/asset processing to ensure genuinely externally-triggerable conditions cannot reach an unguarded `throw`, reserving `throw` strictly for conditions that are truly programmer invariants unreachable from network input.
- Consider making the global `uncaughtException` handler avoid an unconditional process kill for errors clearly originating from remote-triggerable validation code, or at minimum ensure validation-time errors are always caught before they can reach that handler.

### Proof of Concept
Conceptual (exact field values require replicating the "not enough stable MC units" condition against a live database, which requires code-execution access not available to static analysis):
1. Construct a unit with a single `payment` message whose `payload.inputs` includes an entry `{ type: "witnessing", from_main_chain_index: X, to_main_chain_index: Y, address: <author or explicit address> }`, satisfying all of the earlier structural/bounds checks in `validation.js` (`from <= to`, `to <= last_ball_mci`, `to <= getMaxSpendableMciForLastBallMci(last_ball_mci)`, no overlap with previously spent ranges).
2. Choose `Y` (`to_main_chain_index`) such that, on the specific node processing the unit, the count of `is_on_main_chain=1 AND is_stable=1` rows for MCIs in `[Y, Y+COUNT_MC_BALLS_FOR_PAID_WITNESSING+1]` is not exactly `COUNT_MC_BALLS_FOR_PAID_WITNESSING+2` (e.g., by targeting the boundary of the node's stable/retrievable MC bookkeeping).
3. Broadcast/post the unit to the target node.
4. `validatePaymentInputsAndOutputs` reaches the `witnessing` branch, calls `paid_witnessing.calcWitnessEarnings`, which invokes `callbacks.ifError(...)` → `throw Error(err)` in `validation.js:2591`, which is not caught anywhere in the validation call chain and reaches `network.js`'s `uncaughtException` handler, which re-throws and crashes the node process.
