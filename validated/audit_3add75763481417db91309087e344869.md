### Title
`StatusHandler#process` matches commits by SHA only, allowing an attacker-controlled repository's webhook to schedule continuous delivery for an unrelated stack - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no scoping to the repository that emitted the webhook, unlike the base `Handler#stacks` helper which explicitly scopes lookups by `repository_name` from the payload. Because signature verification only proves control of the sending organization's `webhook_secret`, not ownership of the specific commit SHA across all tenants, an attacker who controls a repository/stack that shares a commit SHA with a victim stack (e.g. a fork, mirror, or shared upstream history) can write a `Status` row onto the victim commit and trigger `ContinuousDeliveryJob` for the victim stack.

### Finding Description
The broken binding: the organization that signed this webhook request must equal the organization owning every stack whose commit gets a new `Status` and whose `schedule_continuous_delivery` fires. That equality does not hold here.

Path:
1. `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` using `repository_owner` taken from the attacker's own payload (`payload.dig('repository', 'owner', 'login')`), so it verifies only that the request is authentically signed by org A - the attacker's own onboarded org/repo. [1](#0-0) 
2. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This queries the entire `commits` table for any row matching the SHA, with no filter on `stack_id`/`repository_name`, unlike the `Handler#stacks` helper which exists precisely to scope handlers to the repository named in the payload. [2](#0-1) [3](#0-2) 
3. `Commit#create_status_from_github!` creates a `Status` on whatever commit matched, regardless of which stack it belongs to. [4](#0-3) 
4. `Status` has `after_commit :schedule_continuous_delivery, ..., on: :create`, which calls `commit.schedule_continuous_delivery`. [5](#0-4) 
5. `Commit#schedule_continuous_delivery` only checks `deployable?`, `stack.continuous_deployment?`, `stack.deployable?` - all properties of the victim stack itself, and none re-verify which organization's webhook produced this status - and enqueues `ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)` for the victim stack B. [6](#0-5) 

Attacker's exact request: attacker owns/controls a Shipit-onboarded repository A (any repo whose org is configured in Shipit with a `webhook_secret`, which the attacker can trigger through normal GitHub API/UI actions such as setting a commit status on their own repo/fork). If any commit SHA in A's history collides with a commit SHA already recorded for victim stack B's commits table - plausible via forks, mirrors, shared upstream commits, or cherry-picks that preserve tree/parent/metadata - GitHub delivers a correctly-signed `status` webhook for repo A's SHA. `verify_signature` passes because it only checks org A's secret. `StatusHandler` then matches the SHA against **all** commits in the database, including B's, and writes a status + schedules B's continuous delivery job.

Existing guards do not stop this: `verify_signature` only binds the request to org A, not to the affected stack; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema only validates field shapes; none of these check that the commit being mutated belongs to a stack whose repository matches `repository_name` in the payload - which is exactly what `Handler#stacks` was built for but `StatusHandler` does not use.

### Impact Explanation
A payload authenticated only for repository/tenant A can create a `Status` record for, and schedule `ContinuousDeliveryJob` against, an unrelated tenant B's stack - a cross-tenant payload mutating another repository's stack/commit and triggering an unauthorized deploy pipeline run, matching the Critical "payload for one repository mutating another's stack/commit... or an unauthorized deploy" category. This is repeatable per matching SHA and is not limited to a single victim stack - any stack sharing a colliding SHA with an attacker-controlled repo is affected.

### Likelihood Explanation
Preconditions: attacker must control (or have push/webhook-triggering rights on) a repository/org already onboarded into Shipit (so its `webhook_secret` is valid), and a commit SHA must exist in both the attacker's repo and the victim's stack's `commits` table. This is realistic in fork/mirror scenarios, monorepo split scenarios, or when multiple stacks track branches of the same upstream - common in real deployments where many stacks are configured for different environments/services sharing history. The attacker's cost is low (standard GitHub actions on their own repo); no Shipit or GitHub secrets are required.

### Recommendation
Scope `StatusHandler#process` (and any other handler doing direct model lookups) using the `repository_name` from the payload, mirroring the `Handler#stacks` pattern - e.g. restrict `Commit.where(sha: params.sha)` to `commits` belonging to stacks under `Repository.from_github_repo_name(repository_name).stacks`, so a status can only be applied to commits belonging to the repository that actually signed the webhook.

### Proof of Concept
```ruby
test "status webhook for repo A schedules continuous delivery for stack B via SHA collision" do
  stack_a = shipit_stacks(:shipit) # owned by org A, tracked
  stack_b = shipit_stacks(:cyclimse) # owned by org B, continuous_deployment enabled, deployable

  shared_sha = "deadbeef" * 5

  commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared")
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared")
  stub_stack_b_deployable(stack_b) # deployable?/continuous_deployment?/deployable? stubbed true

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "repository" => { "full_name" => stack_a.github_repo_name, "owner" => { "login" => stack_a.organization } }
  }

  assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [stack_b]) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload) # signed & verified against org A only
  end
end
```
This asserts `ContinuousDeliveryJob` is enqueued with `stack_b` even though the verified signature belonged only to `stack_a`'s `webhook_secret`, confirming the broken binding.
