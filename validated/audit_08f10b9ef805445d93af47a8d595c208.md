### Title
AA price/state decisions can be based on non-finalized "unstable" oracle data feeds, enabling timed extraction of AA funds - (File: data_feeds.js, formula/evaluation.js)

### Summary
The reported Balancer `SafeguardPool.sol` issue is about a price/peg flag that a permissionless caller can flip and then immediately act on (front-run), moving AA/pool funds using a price snapshot that the caller effectively chose. The analogous bug class in `ocore` is that `data_feed[[...]]`/`in_data_feed[[...]]` formulas used inside Autonomous Agents (AAs) are allowed to read oracle values from units that are **not yet stabilized** on the main chain, only causally included. Since an unprivileged AA trigger sender fully controls when and against which DAG state (via `last_ball`/`min_mci`) their trigger unit is composed, they can choose to act on a specific, not-yet-final oracle post that benefits them, in the same way the report describes front-running a peg toggle.

### Finding Description
When an AA formula evaluates `data_feed[[...]]` or `in_data_feed[[...]]`, it calls `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists` with `unstable_opts`/`bAA` set to true for AA execution: [1](#0-0) [2](#0-1) 

Inside `readDataFeedValue`, when `bIncludeUnstableAAs` is true, the function scans `storage.assocUnstableMessages` — i.e., data-feed messages from units that are only causally included (not yet marked stable in the DB) — and picks a candidate purely by DAG ordering (`latest_included_mc_index`, `level`), not by economic finality: [3](#0-2) 

The equivalent boolean-condition search (`in data feed`/`in_data_feed`) has the same unstable-search branch: [4](#0-3) 

Because a trigger unit's `last_ball_mci`/`min_mci` window is chosen by the unit's own author at composition time, an unprivileged AA trigger sender can watch the DAG for a favorable (but not yet finalized) oracle post and immediately author a trigger that references it, "locking in" that value for the AA's fund-moving logic before the price/state is economically final. AA templates that use `data_feed` to gate payouts (e.g. `futures_contract.oscript`, `option_contract.oscript`) illustrate exactly this pattern of price-gated fund release: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any AA that uses `data_feed`/`in_data_feed` to determine payout amounts, asset conversion rates, or "peg"/threshold-like state transitions is exposed to a party who can time their trigger against a specific not-yet-final oracle update. This mirrors the report's core risk: value extracted from the AA's pooled funds can exceed what would be justified by the true, settled price, because the AA's balance/exchange-rate logic reacts to a price snapshot chosen by the beneficiary of the transaction rather than to a canonically finalized value. This is a genuine AA fund-loss/drain vector, not merely a UX quirk.

### Likelihood Explanation
Any unprivileged unit poster/AA-trigger sender can trigger this without special privileges — they only need to observe unstable units in the DAG (via a full node) and time their trigger unit's authoring, choosing `last_ball`/`min_mci` accordingly. No collusion with witnesses or hubs is required, and the mechanism (`readDataFeedValue`'s unstable-inclusion branch) is a documented, always-on code path for every AA using `data_feed`/`in_data_feed`, so the likelihood is high for any AA relying on price/peg-like data feeds without its own additional safeguards (deviation checks, TWAPs, minimum confirmation depth via `min_mci`).

### Recommendation
For AAs (and any core helper functions used by them) that gate fund-moving decisions on `data_feed`/`in_data_feed`, avoid resolving values from `storage.assocUnstableMessages` (the not-yet-stable branch in `readDataFeedValue`/`dataFeedExists`) when the outcome directly controls payouts, or require AA authors to enforce a `min_mci` buffer/staleness/deviation check comparable to the `_balancesSafeguard()` mitigation mentioned in the original report. Documentation for `data_feed`/`in_data_feed` should explicitly warn AA authors that unstable-oracle inclusion allows the trigger sender to select which of several near-simultaneous oracle posts is used, and that price-sensitive AAs must add their own deviation/finality safeguards.

### Proof of Concept
1. An oracle address posts a `data_feed` unit `U1` with a favorable price for feed `PRICE`; `U1` is broadcast but not yet on a stabilized MCI (only causally included in the tips).
2. An AA `X` contains logic such as `if (data_feed[[oracles=ORACLE, feed_name='PRICE']] > threshold) { pay out N }` (pattern shown in `futures_contract.oscript`/`option_contract.oscript`).
3. An attacker, watching the DAG, immediately composes and posts a trigger unit `T` to `X` whose `last_ball`/`min_mci` window includes `U1` (via `readDataFeedValue`'s unstable-inclusion path, `data_feeds.js:211-273`), guaranteeing `data_feed[[...]]` resolves to the favorable value once `T` stabilizes and `handleTrigger`/`evaluateAA` runs.
4. Because the AA's final execution (`aa_composer.handleTrigger`) only occurs at MCI stabilization but the price is fixed by whichever unstable data feed unit was causally reachable from `T`'s `last_ball` at composition time, the attacker effectively selects the price used for their own payout, extracting more value from `X`'s balances than a finalized/averaged price would justify.
