### Title
Permissionless `pallet_assets::create` lets an attacker pre-empt an `AssetId`, causing `force_create`/`ForceOrigin` governance asset creation to always revert with `InUse` - ([File: substrate/frame/assets/src/lib.rs])

### Summary
The Maia report describes governance being blocked from registering a canonical "ecosystem token" because an unprivileged attacker can pre-register the same identifier first, tripping an "already exists"-style guard that the privileged call also checks. `pallet-assets` has a structurally identical pattern: a permissionless `create` extrinsic and a privileged `force_create` extrinsic that share the same "not already in use" existence check on `T::AssetId`.

### Finding Description
`Pallet::create` is a public, signed extrinsic gated only by `T::CreateOrigin` (in AssetHub runtimes this is `AsEnsureOriginWithArg<EnsureSigned<AccountId>>`, i.e. any signed account, subject to paying `AssetDeposit`), and the caller supplies the `id: T::AssetIdParameter` themselves: [1](#0-0) 

Both `create` and the privileged `force_create`/`do_force_create` (restricted to `ForceOrigin`) perform the exact same existence check before inserting the `Asset` storage item: [2](#0-1) [3](#0-2) 

If a `NextAssetId` allocator (`AssetIdAllocator`) is *not* configured to constrain `id` (i.e. `Config::AssetIdAllocator = ()`, which returns `None` from `next()`), then `create`'s `ensure!(id == next_id, ...)` branch is skipped entirely, and any signed account can pick **any** unused `id` value, including one that governance intends to later `force_create` for a specific purpose (e.g. a well-known/canonical asset id, or an id derived from a location that governance has not yet registered). Once the attacker's `create` succeeds, `Asset::<T,I>::contains_key(&id)` is `true`, and the subsequent governance `force_create` for that same `id` unconditionally reverts with `Error::InUse`: [4](#0-3) 

This mirrors the Maia bug's `getLocalTokenFromUnderlying[_ecoTokenGlobalAddress]` check that reverted `addEcosystemToken()`: a low-privilege actor front-runs an id/slot that governance planned to occupy, and the privileged call is permanently DoS'd for that identifier because the check treats "already occupied by anyone" the same as "already occupied by the intended token."

Note: recent work in this repo (`pallet-assets: allow force_create to set an arbitrary asset id when auto-increment is enabled`, PR 12378) and `NextAssetId`/`AssetIdAllocator` introduce a mechanism to reserve an id range for forced/deliberate assignment (`force_create_can_use_arbitrary_id` test), which is precisely the kind of mitigation this class of bug needs. However, this only helps when `AssetIdAllocator` is actively configured with a reserved range; for any config using `()` (unconstrained) — the default for `TestDefaultConfig` per the prdoc — the front-running window remains open. [5](#0-4) [6](#0-5) 

### Impact Explanation
Any parachain/asset-hub-like runtime that (a) allows public, signed `pallet_assets::create` with attacker-chosen ids and (b) does not configure a reserved/allocator range for ids that governance intends to `force_create` later is exposed to a permanent DoS on registering that specific asset id — governance cannot ever complete the intended `force_create` for that identifier without redeploying under a new id (analogous to Maia's confirmed, but disputed-severity, Medium-severity DoS finding). This is a config-dependent risk rather than a universal vulnerability in shipped AssetHub runtimes, since concrete deployments may already set a non-trivial `AssetIdAllocator`/`NextAssetId` policy that reserves the ids governance cares about.

### Likelihood Explanation
Requires: (1) a runtime configuring `pallet-assets` with a permissionless `CreateOrigin` and an unconstrained (or partially constrained) `AssetIdAllocator`, and (2) the attacker being able to guess/know the specific `id` governance will later want (e.g. it derives from a well-known location or a documented convention, similar to how the attacker in the original report knew the ecosystem token's global address in advance). I could not fully verify, within the remaining tool budget, whether the shipped `asset-hub-westend`/`asset-hub-rococo` runtime configs currently leave the id space fully open for such attacks or whether they've already deployed the `AssetIdAllocator` reservation added by PR 12378 — this needs to be checked in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` and `asset-hub-rococo/src/lib.rs`'s `impl pallet_assets::Config for Runtime` block, which the search did not return contents for before the iteration budget ran out.

### Recommendation
- Ensure any `pallet-assets` instance whose `force_create`/privileged asset ids matter for governance uses a non-trivial `AssetIdAllocator` (e.g. `AutoIncAssetId`) with a reserved low/high id range dedicated to forced creation, as already implemented via `NextAssetId`/`force_create_can_use_arbitrary_id`.
- Where ids are derived from external data (locations, symbols) rather than sequential integers, `force_create` should be able to override/reclaim an id that was created by an ordinary `create` call but has zero supply/no deposit significance yet — mirroring the community-suggested Maia mitigation ("allow override if total supply is zero") rather than an unconditional `InUse` revert.

#[test]
fn force_create_can_use_arbitrary_id() {
	build_and_execute(|| {
		// Enable auto increment with the next id at `50`, reserving the `0..50` range for
		// deliberate, forced assignment.
		pallet::NextAssetId::<Test>::put(50);

		// A forced id below the sequence is allowed and leaves the sequence untouched.
		assert_ok!(Assets::force_create(RuntimeOrigin::root(), 10, 1, false, 1));
		assert!(Asset::<Test>::contains_key(10));
		assert_eq!(pallet::NextAssetId::<Test>::get(), Some(50));

		// A forced id cannot collide with a currently-live asset.
		assert_noop!(
			Assets::force_create(RuntimeOrigin::root(), 10, 1, false, 1),
			Error::<Test>::InUse
		);

		// A forced id at or beyond the sequence advances `NextAssetId` past it, so the sequence
		// never later collides.
		assert_ok!(Assets::force_create(RuntimeOrigin::root(), 60, 1, false, 1));
		assert!(Asset::<Test>::contains_key(60));
		assert_eq!(pallet::NextAssetId::<Test>::get(), Some(61));

		// A subsequent sequential `create` picks up from the advanced sequence.
		assert_noop!(Assets::create(RuntimeOrigin::signed(1), 50, 1, 1), Error::<Test>::BadAssetId);
		Balances::make_free_balance_be(&1, 100);
		assert_ok!(Assets::create(RuntimeOrigin::signed(1), 61, 1, 1));
		assert_eq!(pallet::NextAssetId::<Test>::get(), Some(62));

		// Forcing exactly the next id also advances the sequence.
		assert_ok!(Assets::force_create(RuntimeOrigin::root(), 62, 1, false, 1));
		assert_eq!(pallet::NextAssetId::<Test>::get(), Some(63));
	});
}
