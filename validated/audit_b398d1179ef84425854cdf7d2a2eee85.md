### Title
Unhandled exception in `definition template` authentifier evaluation can crash/abort validation during signature verification - ([File: definition.js])

### Summary
`definition.js`'s `validateAuthentifiers()` evaluates address/spending-condition trees while actually checking signatures for a posted unit. Its `'definition template'` branch calls `replaceInTemplate()` and `JSON.parse()` on attacker-influenced data without a `try/catch`, unlike the structurally-identical branch in `validateDefinition()` (used only when *defining* a new address), which does wrap the same calls in `try/catch` and safely converts a `NoVarException` into a normal validation error.

### Finding Description
`validateDefinition()`'s `'definition template'` case explicitly guards against malformed templates/params: [1](#0-0) 
Here, `replaceInTemplate(arrTemplate, params)` is wrapped in `try { ... } catch(e) { if (e instanceof NoVarException) return cb(e.toString()); else throw e; }`, so an exception (e.g., a param referenced in the template but not supplied, or a param not supplied but referenced) is converted into a normal `cb(error)` rejection.

By contrast, the equivalent branch inside `validateAuthentifiers()` — the function that is actually invoked to verify signatures/authentifiers when a unit is posted and spends funds — has no such protection: [2](#0-1) 
```
case 'definition template':
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) ...",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            var template = rows[0].payload;
            var arrTemplate = JSON.parse(template);
            var arrFilledTemplate = replaceInTemplate(arrTemplate, params);   // NOT wrapped in try/catch
            evaluate(arrFilledTemplate, path, cb2);
        }
    );
    break;
```
`replaceInTemplate()` throws a `NoVarException` whenever a template variable (`"$name"`) is not present in the caller-supplied `params` object, and throws a generic `Error("unknown type")` for unexpected value types: [3](#0-2) 

Because `params` in this authentifier-evaluation path is taken directly from the definition supplied by the unit's author (`args[1]` from the `arrDefinition`/authentifier tree being evaluated for THIS unit, or from an inner/referenced address's definition reached via `'address'`/nested `'or'`/`'and'` evaluation), an attacker who posts a unit (or references an address whose definition uses `'definition template'`) can craft `params` that intentionally omit a variable the template expects. This throws synchronously inside the `conn.query` callback of `sqlite_pool.js`'s `query()` wrapper.

This mirrors CVE-2024-11696's root cause exactly: an unhandled exception thrown while validating one signature-tree branch escapes the normal `cb`/`cb2` error-propagation chain used throughout `validateAuthentifiers`'s `'or'`/`'and'` combinators (`async.eachSeries` over sibling branches, lines 651–691), which never call their `cb3()` continuation when a sibling branch throws instead of invoking the callback: [4](#0-3) 
An uncaught throw inside one branch of an `'or'`/`'and'` combinator halts the `async.eachSeries` iteration for *all other, unrelated* branches/authors in that same evaluation without properly failing or succeeding them through the callback contract — the exact "exception in one item disrupts unrelated validation" pattern described in the advisory.

### Impact Explanation
Depending on how the resulting synchronous throw propagates up through `mutex.lock`/`async.series` in `validation.js`'s top-level `validate()` (`validation.js:357-493`) and into the caller (network message handler or `aa_composer.js`'s `validateAndSaveUnit`), the outcome is either:
- an uncaught exception that crashes the validating node process (handled generically by `process.on('uncaughtException')` in `network.js:4530-4543`, which re-throws to crash the process), or
- if any intermediate layer treats the thrown error non-fatally (e.g. an outer generic `try/catch` that maps any exception to "ok"/skip), a bypass of authentifier verification for that unit.

I was not able to fully trace, within the available index, every intermediate synchronous call frame between `sqlite_pool.js`'s query callback and `validation.js`'s `validate()` to conclusively determine whether the exception is always fatal (crash/DoS) or can, in some call path, be swallowed such that the signature check is treated as passed. Given the scan rules explicitly reject "no-impact" and "network-DoS-only" findings, and I could not confirm a concrete unauthorized-spending/double-spend/AA-fund-loss outcome (as opposed to a crash), I cannot assert this rises to the required Medium+ impact with confidence.

### Likelihood Explanation
Reaching this code path requires an address (author's own or referenced via `'address'`/`'or'`/`'and'`) whose definition uses `'definition template'` with a `definition_template` unit that is stable and before last ball — a legitimate, fully attacker-controllable oscript feature. Any ordinary unit poster can create such a definition and reference a template with mismatched params, so the trigger condition is easy to reach.

### Recommendation
Wrap the `JSON.parse(template)` and `replaceInTemplate(arrTemplate, params)` calls in `definition.js`'s `validateAuthentifiers()` `'definition template'` case (lines 802-819) in a `try/catch`, mirroring the handling already present in `validateDefinition()` (lines 330-339), converting `NoVarException`/parse errors into a normal `cb2(false)` (or an appropriate error signal) instead of letting them throw uncaught inside the `conn.query` callback.

### Proof of Concept
Not confirmed end-to-end (would require live process tracing across `sqlite_pool.js` → `mutex.lock`/`async.series` in `validation.js` → network/AA caller to determine whether the exception crashes the node or is silently swallowed as "pass"). Conceptually:
1. Post a unit A defining address `T` with `["definition template", ["<templateUnit>", {"$name": "value"}]]` where `<templateUnit>`'s stored template does not reference `$name` (or where a required template variable is intentionally omitted from `params`) so `replaceInTemplate` throws `NoVarException`.
2. Post/relay a spending unit B whose author uses `T`'s definition (directly or via nested `'address'`), causing `validateAuthentifiers()` to evaluate the `'definition template'` branch during real signature verification, hitting the unguarded `replaceInTemplate` call and throwing uncaught inside the `conn.query` callback. function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}

function NoVarException(error){
	this.error = error;
	this.toString = function(){
		return this.error;
	};
}
