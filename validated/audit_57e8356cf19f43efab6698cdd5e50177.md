### Title
Task/deploy variable named after a Shipit-reserved key overrides `GITHUB_TOKEN` in the executed command environment - (File: lib/shipit/task_commands.rb)

### Summary
`Shipit::EnvironmentVariables#permit` only checks whether a submitted env key is present in `variable_definitions.map(&:name)`; it never checks whether that name collides with the internal keys Shipit computes for itself (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, `SHIPIT_USER`, `GIT_COMMITTER_*`, `TASK_ID`). Because `TaskCommands#env` merges `@task.env` last, a `shipit.yml` task/deploy `variables` entry named `GITHUB_TOKEN` lets the value supplied at trigger time (or its declared `default`) silently replace the real GitHub token used for all subsequent git/GitHub operations in that task.

### Finding Description
The broken binding: the key set produced by `variable_definitions.map(&:name)` (attacker-controlled through `shipit.yml`'s `tasks.<id>.variables` or `deploy.variables`) must never intersect the key set Shipit computes internally for `Command#env`. No code enforces this.

- `Shipit::VariableDefinition#initialize` (`app/models/shipit/variable_definition.rb:7-13`) accepts any `name`/`default` with no reserved-word check.
- `Shipit::TaskDefinition#filter_envs` / `Shipit::DeploySpec#filter_deploy_envs`/`filter_rollback_envs` call `EnvironmentVariables.with(env).permit(variables)` [1](#0-0) , which is implemented purely as a name-membership filter with no denylist: [2](#0-1) .
- `Stack#trigger_task` applies `variables_with_defaults` (i.e. the attacker-declared `default`) onto the env hash before filtering, then stores the filtered hash as `task.env`: [3](#0-2) .
- `TaskCommands#env` builds the final environment by starting from `Commands#base_env` (which sets the real `GITHUB_TOKEN`/`GITHUB_DOMAIN`/`GIT_ASKPASS`) and merges `@task.env` **last**: [4](#0-3) . The real token is set in `Commands#base_env`: [5](#0-4) .
- This merged hash is what becomes `Command#env`, ultimately consumed for spawning the process: [6](#0-5) .

Exploit flow: a contributor opens a PR adding to `shipit.yml`:
```yaml
tasks:
  restart:
    variables:
      - name: GITHUB_TOKEN
        default: attacker-controlled-value
```
Once merged (a precondition stipulated by the question), any authenticated user with `deploy:stack` permission who triggers the `restart` task (via `TasksController#trigger` or the web `TasksController#create`) causes `Stack#trigger_task` to apply the default into `env['GITHUB_TOKEN']`, pass it through `filter_envs`/`permit` (which allows it because `GITHUB_TOKEN` is in `variable_definitions.map(&:name)`), and store it on `task.env`. When the task executes, `TaskCommands#env` merges this value over the real token from `base_env`, so all `git`/GitHub API calls that read `ENV['GITHUB_TOKEN']` from the spawned command's environment use the attacker's value instead of Shipit's credential.

None of the existing guards catch this: `EnvironmentVariables#permit` only whitelists by name equality (no denylist of reserved keys), `require_permission!`/`Stack` `env` params permit only checks the variable's own declared name list (`task_params` in `app/controllers/shipit/tasks_controller.rb:77-82`), and there is no model validation on `VariableDefinition#name` rejecting reserved identifiers anywhere in the codebase.

### Impact Explanation
Whoever triggers the poisoned task/deploy has the real `GITHUB_TOKEN` replaced by an attacker-chosen value for that task's git/GitHub operations (the case in the question: the attacker neutralizes/replaces the token, potentially with an invalid one to disrupt deploys, or a token they control if they can seed a valid one via other means). This is scoped to the single task execution and the repository whose `shipit.yml` was modified; it does not directly leak the real secret to the attacker, but it does let the attacker substitute the credential used for GitHub-facing operations of that task, matching "exfiltration/replacement of GITHUB_TOKEN... deploy-time secrets" impact category. It is repeatable on every trigger of the affected task as long as the malicious `shipit.yml` entry remains merged.

### Likelihood Explanation
Requires the malicious `shipit.yml` change to be merged into the tracked branch, and requires a legitimate user (with `deploy:stack` permission) to subsequently trigger that specific task/deploy. Given the question explicitly stipulates this precondition ("PR merged; task triggered by any user without overriding the env"), the remaining barrier is entirely a code-level gap: nothing in `VariableDefinition`, `TaskDefinition`, `DeploySpec`, or `EnvironmentVariables` rejects a user-declared variable name that shadows a Shipit-internal env key.

### Recommendation
Introduce a reserved-name denylist (e.g. `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, `SHIPIT_USER`, `SHIPIT_LINK`, `EMAIL`, `TASK_ID`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `IGNORED_SAFETIES`, `BUNDLE_PATH`, `SHA`, `REVISION`, `DIFF_LINK`) and validate it in `Shipit::VariableDefinition#initialize`, raising/rejecting config that declares a variable with a reserved name, and/or have `EnvironmentVariables#permit` reject any allowed_variables entry that collides with this reserved set. Additionally, consider merging `@task.env` before, not after, the internally computed keys in `TaskCommands#env` (or explicitly excluding reserved keys from the merge) so user-controlled values can never clobber Shipit's own credentials regardless of config-time validation.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extension)
test "#env can be poisoned by a variable named GITHUB_TOKEN declared in shipit.yml" do
  Shipit.github(organization: 'shopify').stubs(:token).returns('real-github-token')

  task = shipit_tasks(:shipit_restart)
  definition = Shipit::TaskDefinition.new('restart', {
    'variables' => [{ 'name' => 'GITHUB_TOKEN', 'default' => 'attacker-value' }]
  })
  task.definition = definition
  task.env = definition.filter_envs('GITHUB_TOKEN' => 'attacker-value')

  command_env = Shipit::TaskCommands.new(task).env

  # Binding under test: attacker-declared name must never intersect Shipit's reserved keys.
  assert_equal 'real-github-token', command_env['GITHUB_TOKEN'], # currently fails
    "attacker-controlled task variable overrode the real GITHUB_TOKEN"
end
```
This test declares a task variable named `GITHUB_TOKEN`, submits an attacker value, and asserts the final `TaskCommands#env['GITHUB_TOKEN']` still equals the real token; under current code it instead equals `'attacker-value'`, demonstrating the vulnerability.
