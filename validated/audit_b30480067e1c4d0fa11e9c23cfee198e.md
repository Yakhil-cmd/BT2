### Title
Cross-org webhook confusion: signature verified against `repository.owner.login` while stack lookup uses unrelated `repository.full_name`, letting an attacker's own signed webhook drive `sync_github` on a victim's stack - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `payload.dig('repository', 'owner', 'login')` (or `organization.login`). Separately, `Handler#stacks`/`PushHandler#process` resolves the target `Repository`/`Stack` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`. These two fields are independent, attacker-controlled JSON values in the same POST body and are never cross-validated, so a signature that is valid for organization A can be paired with a `repository.full_name` pointing at organization B's repo/stack.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`payload.dig('repository','owner','login')` (the identity the HMAC signature authenticates) **must equal** the owner encoded in `payload.dig('repository','full_name')` (the identity whose stacks get mutated). Nothing in the code enforces this.

Path:
- `app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature`) computes `repository_owner` via `repository_owner` method at line 59-62, which reads `params.dig('repository','owner','login')` (fallback `organization.login`), and verifies the raw HMAC signature against `Shipit.github(organization: repository_owner).verify_webhook_signature`.
- `app/models/shipit/webhooks/handlers/handler.rb:32-38` (`stacks`/`repository_name`) reads `payload.dig('repository', 'full_name')` — a completely separate JSON field — to find the `Repository` via `Repository.from_github_repo_name`.
- `app/models/shipit/webhooks/handlers/push_handler.rb:12-23` (`process`/`branch`) then filters `stacks.not_archived.where(branch:)` using attacker-supplied `params.ref`, and calls `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen `after` value.

Exploit: an attacker who legitimately controls an organization/repo that is configured in Shipit (has a real webhook_secret shared between their GitHub org and this Shipit instance) can produce a validly-signed POST to `/webhooks`. They craft the JSON body so that `repository.owner.login` = their own org (satisfying `verify_signature`) while `repository.full_name` = `"victim-org/victim-repo"` and `ref` = the victim stack's deployed branch, and `after` = any SHA of their choosing. `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` in `PushHandler` only requires `:ref` and `:after`, it does not require or validate `repository.owner.login` against `repository.full_name`. The signature check therefore authenticates "a message signed by org A" but the code proceeds to act on org B's `Repository`/`Stack` records, invoking `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on a stack the attacker does not own.

### Impact Explanation
This is a payload for one repository (attacker's own, legitimately signed) mutating another repository's stack state (`Repository`/`Stack` belonging to the victim), matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." `sync_github` seeds the victim stack's sync/merge machinery with an attacker-chosen `after` SHA rather than one derived from an event the victim's repository actually authorized, which can influence downstream deploy/merge logic (e.g., which commit is considered head, what gets synced/merged) for a stack across organizational tenant boundaries. The attack is repeatable against any stack whose `owner/name` (`full_name`) and target `branch` the attacker can guess or discover (both are non-secret, publicly visible GitHub identifiers), so the blast radius spans all stacks configured in a multi-tenant Shipit instance, not just the attacker's own.

### Likelihood Explanation
Preconditions: the attacker needs to be a legitimate Shipit "tenant" for at least one organization — i.e., they must possess (or be able to produce) a validly signed webhook for *some* org configured in `Shipit.secrets.github` (per `lib/shipit.rb#github_app_config`), which is realistic in any multi-tenant Shipit deployment where multiple GitHub orgs share a single Shipit instance and each org owner can configure/send their own webhooks. Beyond that, the attacker only needs to know the victim's `owner/name` and deployed branch name (both public GitHub information), and craft an HTTP POST — no GitHub secrets, sessions, or API tokens for the victim are required. This is a self-contained code defect (missing cross-check), not merely a configuration mistake, so it is feasible and repeatable per request.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`/`PushHandler`), assert that the organization used to verify the signature (`repository_owner`) matches the owner segment of `payload.dig('repository', 'full_name')` before dispatching to handlers; reject the request (e.g., `head(422)`) on mismatch. Alternatively, derive the `Repository`/`Stack` lookup exclusively from the same identity that was cryptographically verified, rather than from an independent, unauthenticated field in the payload.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or a new push handler test), no live GitHub:
1. Create a `victim` `Repository`/`Stack` fixture with `owner: "victim-org"`, `name: "victim-repo"`, `branch: "master"`, distinct from an `attacker` org configured with its own `webhook_secret` in `Shipit.secrets.github`.
2. Build a push payload: `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/master"`, `after = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"`.
3. Compute `X-Hub-Signature` using `attacker-org`'s configured `webhook_secret` over the exact raw JSON body (mirroring `GitHubApp#verify_webhook_signature`).
4. POST to `/webhooks` with `X-Github-Event: push` and the computed signature.
5. Assert `response` is `:ok` (signature accepted) and assert (via mocking/expectation on `Stack#sync_github`, e.g. `Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: "deadbeef...")`) that the victim's stack's `sync_github` is invoked with the attacker-chosen SHA — demonstrating `repository_owner` (signed identity = attacker-org) ≠ owner encoded in `repository.full_name` (acted-upon identity = victim-org), yet the action proceeds.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
