### Title
AA Signature-Replay Protection Bypass via Hex/Base64 Re-encoding in `is_valid_sig` — ([File: formula/evaluation.js])

### Summary
The oscript primitive `is_valid_sig(message, pem_key, signature)` accepts the `signature` argument in **either** hexadecimal or Base64 encoding and treats both as equally valid before verification. Because the platform does not canonicalize the signature string before it is (necessarily, by AA authors) used as a replay/anti-double-use key in AA state, the *same* underlying signature bytes can be submitted twice, encoded differently, and both submissions verify successfully while looking like two distinct, never-before-seen values. This is the same root cause as the Telnyx advisory: a signature that has more than one valid textual encoding is treated as “different” by a replay-detection mechanism even though it is cryptographically identical, defeating single-use/anti-replay logic built on top of it.

### Finding Description
`is_valid_sig` in the AA evaluation engine only checks the *format* of the signature, not its canonical encoding: [1](#0-0) 
```
evaluate(sig, function (evaluated_signature) {
    ...
    if (!ValidationUtils.isValidHexadecimal(evaluated_signature) && !ValidationUtils.isValidBase64(evaluated_signature))
        return setFatalError("bad signature string in is_valid_sig", { arr }, false, cb);
```
Both hex and Base64 branches are accepted, and `signature.verifyMessageWithPemPubKey` (and the secp256k1 PEM path) simply picks whichever decoding matches and verifies the decoded bytes: [2](#0-1) 
```
var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
...
return verify.verify({key: pem_key}, signature, encoding);
``` [3](#0-2) 
```
var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
var sigBytes = Buffer.from(signature, encoding);
...
return ecdsaVerify(compactSig, hash, pubkey);
```
A single valid ECDSA/RSA signature over a fixed message therefore has (at least) two distinct valid string representations reachable directly from AA trigger data (`trigger.data.*`, fully attacker-controlled): its hex form and its Base64 form. Both pass `is_valid_sig` with `true`.

AA authors commonly implement one-time-use vouchers, coupons, whitelists, oracle attestations, or "claim" tokens by (a) verifying a signature with `is_valid_sig`, and (b) recording the *signature string itself* (or a hash of the raw string as supplied) in a persistent state variable to prevent the same signed message/voucher from being redeemed twice, e.g. `var['used_' || signature]`. Because ocore performs no canonicalization of `signature` before or after verification, an attacker who has one valid signature can re-encode the same signature bytes (hex→base64 or vice versa) and present it again. The `is_valid_sig` check re-verifies successfully (it is the same signature), but the AA's own anti-replay state lookup treats it as a brand-new, unseen key — exactly mirroring the Telnyx flaw where equivalent Base64/Base64URL encodings of the same signature were hashed and treated as distinct requests despite passing the underlying signature check.

### Impact Explanation
Any AA whose oscript logic relies on the raw `is_valid_sig`/`is_valid_signed_package` signature string (directly, or via `sha256` on it) as a single-use/anti-replay token can be tricked into processing the same authorization twice. Depending on the AA's business logic this leads to:
- Double redemption of a signed voucher/withdrawal authorization → AA fund loss.
- Double registration/whitelisting from a single signed attestation → bypass of a one-time gate that guards spending or minting logic.

This satisfies the "concrete AA fund loss/freezing" bar because the vulnerability is directly reachable by any unprivileged AA trigger sender supplying `trigger.data` and does not require a malicious node/hub/peer.

### Likelihood Explanation
Likelihood is bounded by the fact that this requires a specific (but common) AA-authoring pattern: recording the raw signature string as the de-dup key instead of first normalizing it (e.g., always re-encoding to a canonical hex or Base64 form, or storing a hash of the verified *message* rather than of the *signature bytes-as-submitted*). Any AA following this pattern is directly exploitable by a single attacker holding one valid signature, with no privileged access needed — matching "AA trigger sender" reachability from the "Validate" rules.

### Recommendation
- In `is_valid_sig`/`is_valid_signed_package`/`vrf_verify`, canonicalize the accepted signature string (e.g., always decode then re-encode to one fixed format such as hex) before returning control to oscript, or expose a canonicalized copy of the signature to the AA so any dedup logic naturally operates on one encoding.
- Alternatively, document explicitly (and, if feasible, enforce) that `is_valid_sig` must not be used to build anti-replay dedup keys directly from the signature argument; AA authors should hash the signed *message plus a nonce* instead.
- Consider narrowing accepted encodings to a single canonical form (as already done via `isValidBase64`'s round-trip check elsewhere in `validation_utils.js`) rather than accepting two independently valid encodings for the same bytes.

### Proof of Concept
1. AA `state_var` stores set of already-claimed vouchers:
```
{
  init: `{
    $sig = trigger.data.sig;
    $pubkey = trigger.data.pubkey;
    $msg = trigger.data.msg;
  }`,
  messages: [{
    if: `{
      $ok = is_valid_sig($msg, $pubkey, $sig);
      $ok AND var['used_' || $sig] == null
    }`,
    ...
    // on success: bState.var['used_' || $sig] = 1; then pay out reward
  }]
}
```
2. Attacker obtains one signature over `$msg` from the trusted signer, submits it hex-encoded in trigger #1 → `is_valid_sig` returns `true`, AA pays out and stores `var['used_<hex>'] = 1`.
3. Attacker submits trigger #2 with the *same* signature bytes but Base64-encoded (`Buffer.from(hexSig,'hex').toString('base64')`). `is_valid_sig` returns `true` again (it is the same valid signature, just re-encoded), but `var['used_<base64>']` was never set, so the replay guard does not trigger — the AA pays out a second time for the same authorization. function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
