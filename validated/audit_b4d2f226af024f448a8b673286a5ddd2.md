### Title
Webhook signature bypass when `webhook_secret` is blank allows forged `membership` events to grant unauthorized `Shipit.github_teams` access - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The external report's root cause is that a risk parameter (`staleAfter`) is trusted with no bound/validation, letting a party abuse a legitimate-looking-but-unchecked value to break an economic binding. The analogous binding in this engine is: **the GitHub organization used to select/verify the webhook signature (`repository_owner`, taken from attacker-supplied JSON) must equal the organization whose data the handler actually mutates**, and separately, **the webhook signature must actually be cryptographically bound to the payload before any handler executes privileged writes** (team membership grants). Neither constraint is enforced: signature verification is fully skipped when an org's `webhook_secret` is unset, and the field used to select which app/secret verifies the request (`repository.owner.login`) is never checked against the field the handlers use to decide what to write (`repository.full_name`, or in `membership`, `organization.login`/`team.id`).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate against using an attacker-controlled JSON field: [1](#0-0) [2](#0-1) 

The actual signature check is: [3](#0-2) 

`return true unless webhook_secret` means that for any organization configured **without** a `webhook_secret` (a supported, documented configuration — shown as `webhook_secret: # nil` in both `docs/setup.md` and the test fixture `test/dummy/config/secrets_double_github_app.yml`), signature verification is a no-op: `verified` becomes `true` for an arbitrary unsigned/attacker-crafted POST body, with no HMAC, no shared secret, and no GitHub identity check at all.

Downstream, `MembershipHandler#process` trusts the same unauthenticated payload to create teams and grant/revoke memberships purely from JSON fields: [4](#0-3) 

`User#authorized?` gates access based solely on team membership matching `Shipit.github_teams`: [5](#0-4) 

Because `params.team.id`, `params.organization.login`, and `params.member.login` are attacker-controlled strings/integers with no cross-check against the org that "authenticated" the request (there isn't one, since the signature check is skipped), an attacker who already has (or creates, via the OAuth flow) a Shipit `User` record can forge a `membership` webhook naming their own `login` as `member.login` and a `team.id` equal to one of `Shipit.github_teams`, causing `Membership` to be created and `authorized?` to return `true` for that account — an authorization escalation into `Shipit.github_teams` without ever being a real member of that GitHub team.

This is the same class of bug as the report: a value that gates a privileged operation (`staleAfter` gating price staleness / `webhook_secret`+`repository_owner` gating webhook trust) is either unvalidated or, worse, silently permissive when unset, and the field used for the trust decision (`repository_owner`) is never bound to the field the business logic acts on (`repository.full_name`, `organization.login`, `team.id`).

### Impact Explanation
If any configured GitHub App/org in `Shipit.github` config has no `webhook_secret` set (an explicitly supported configuration per the docs), any unauthenticated network client can POST arbitrary `membership`, `push`, `status`, or `check_suite` payloads to `/webhooks`, bypassing the signature check entirely. The `membership` path directly escalates a Shipit user into `Shipit.github_teams` authorization — one of the explicitly listed valid "High" impacts.

### Likelihood Explanation
The likelihood depends on deployment configuration: it requires at least one configured organization to have a blank `webhook_secret`. This is not a hypothetical edge case — the engine's own documentation (`docs/setup.md`) and fixtures show `webhook_secret:` as an optional field that can legitimately be left blank, and the code path explicitly special-cases this ("Workaround"/fallback `return true unless webhook_secret`) rather than rejecting the request. No secret, token, GitHub App key, or repository write access is needed by the attacker — only a Shipit account (obtainable via normal OAuth login) and knowledge of a target team's numeric `id`.

### Recommendation
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank; either require `webhook_secret` to be present for every configured organization, or fail closed (reject with 422) when it is absent instead of returning `true`.
- Bind the organization used for signature verification to the organization/repository the handler is permitted to mutate — verify that `repository.full_name`'s owner matches `repository_owner`, and that `membership` events' `organization.login` matches the app config actually used to verify the signature, before trusting `team`/`member` fields.
- Add validation in `MembershipHandler` so team-membership mutations require the request to have passed real signature verification (i.e., reject rather than silently proceed when `verified` was only true because `webhook_secret` was absent).

### Proof of Concept
1. Deploy Shipit with a GitHub App entry configured with `webhook_secret:` left blank (as shown in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), which is a documented, supported configuration.
2. As any authenticated (non-privileged) Shipit `User`, `POST /webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": { "id": <id of a team in Shipit.github_teams>, "name": "T", "slug": "t", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "<attacker-github-login>" }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "victim-org").verify_webhook_signature(...)`, which returns `true` because `webhook_secret` is nil for that org config (`lib/shipit/github_app.rb:77`).
4. `MembershipHandler#process` runs unchecked, creating a `Membership` linking the attacker's `User` to the targeted team (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
5. The attacker's account now satisfies `User#authorized?` (`app/models/shipit/user.rb:80-82`) via `Shipit.github_teams`, granting access gated on org-team membership without ever being a member of the real GitHub team.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
