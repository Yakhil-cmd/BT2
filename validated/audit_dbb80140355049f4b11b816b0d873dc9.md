### Title
Webhook organization used for HMAC verification is never bound to the organization of the repository whose stack is mutated - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check based on `params.dig('repository','owner','login')`, while `ReopenedHandler#repository` resolves the actual `Repository`/`ReviewStack` to mutate from the unrelated `params.repository.full_name` field of the very same, still-unauthenticated JSON body. Nothing asserts these two fields name the same organization, so a request whose signature validates for organization A can still target and mutate a `ReviewStack` that belongs to organization B.

### Finding Description
The intended binding is: `org verified by HMAC (params.repository.owner.login)` == `org owning the ReviewStack unarchived (owner parsed from params.repository.full_name)`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [1](#0-0) .
- `Shipit.github` resolves per-organization config via `github_app_config(organization)` only when the instance is in multi-org mode (`github_default_organization` non-nil); each organization can have its own, independently-set `webhook_secret` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` explicitly bypasses signature checking entirely when that organization's `webhook_secret` is blank: `return true unless webhook_secret` [3](#0-2) . A `webhook_secret: null` config is treated as a normal, supported value in this codebase's own fixtures [4](#0-3) .
- After the controller-level check passes, `ReopenedHandler#process` calls `stack.unarchive!` where `stack` is built from `repository.review_stacks`, and `repository` is resolved from a **different** payload field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) . `from_github_repo_name` simply splits `"owner/name"` from `full_name` and looks the repository up directly, independent of `repository.owner.login` [6](#0-5) .
- The `ExplicitParameters` schema for `ReopenedHandler` only requires `repository.full_name`; it does not require or constrain `repository.owner.login` at all [7](#0-6) .

Exploit flow (multi-org Shipit deployment, which the codebase explicitly supports): the attacker crafts a raw JSON body with `repository.owner.login = "org-with-no-webhook-secret"` and `repository.full_name = "victim-org/victim-repo"`, POSTs it to `/webhooks` with header `X-Github-Event: pull_request` and any `X-Hub-Signature` value (irrelevant, since `verify_webhook_signature` short-circuits to `true` for an organization with a blank `webhook_secret`). `verify_signature` passes because it only checked the (attacker-chosen) `repository.owner.login` organization's secret, never the organization actually being mutated. `ReopenedHandler` then resolves and unarchives victim-org's real, provisioning-enabled `ReviewStack` via `ReviewStackAdapter#unarchive!` [8](#0-7) .

No existing guard closes this gap: `drop_unhandled_event` only checks the event type is registered [9](#0-8) ; the `ExplicitParameters` schema never requires or cross-checks `repository.owner.login`; and no code anywhere compares the organization used for signature verification against the organization owning the resolved `Repository`.

### Impact Explanation
An attacker who can name (or already knows exists) any organization configured on the shared Shipit instance with a blank `webhook_secret` can forge unsigned/unverifiable webhook deliveries that mutate the state (`archive!`/`unarchive!`, and by the same pattern also `create!`/provisioning-queue enqueue) of a `ReviewStack` belonging to a completely different organization's repository, without ever authenticating to that organization's boundary. This is a payload nominally scoped to organization A mutating organization B's stack state — matching the Critical "payload for one repository mutating another's stack" category. The same disjoint-field pattern (`repository.owner.login` vs `repository.full_name`) exists across all `pull_request` handlers (`LabeledHandler`, `OpenedHandler`, `ClosedHandler`, etc.), so the blast radius is not limited to `reopened` events alone.

### Likelihood Explanation
The vulnerability requires a multi-organization Shipit deployment where at least one configured organization has `webhook_secret` unset/blank (a state the codebase itself demonstrates as a legitimate, non-error configuration). It does not require any Shipit session, API token, GitHub App key, or `webhook_secret` value from the attacker — the attacker only needs to know (or discover, e.g. via error messages/`GithubOrganizationUnknown` behavior, or by simply trying common/likely organization names) the name of one such loosely-configured organization on the instance. Given that per-organization webhook secrets are an opt-in, easy-to-misconfigure detail, and the code offers no cross-field validation whatsoever, this is a low-cost, fully repeatable attack against arbitrary target repositories on the same instance.

### Recommendation
Bind the two identities before trusting the payload: in `WebhooksController`, resolve the target `Repository`/organization once (e.g., from `repository.full_name`), and use that same organization exclusively both for HMAC secret selection and for handler dispatch; reject the request if `repository.owner.login` (when present) does not match the owner segment of `repository.full_name`. Additionally, do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for organizations expected to be signature-protected — require an explicit signature validation, treating a blank secret as a configuration error, not an implicit bypass.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (no live GitHub):
1. Stub `Shipit.stubs(:github_organizations).returns(%w[org-a org-b])` and configure `Shipit.github(organization: "org-a")` to have a blank `webhook_secret` (so `verify_webhook_signature` returns true unconditionally), while `Shipit.github(organization: "org-b")` has a real, secret `webhook_secret` unknown to the "attacker".
2. Create `repository = shipit_repositories(:org_b_repo)` (owner `"org-b"`) with `review_stacks_enabled = true`, `provisioning_behavior = :allow_all`, and an existing archived `ReviewStack` (`assert stack.archived?`).
3. POST to `:create` with `X-Github-Event: pull_request`, an arbitrary `X-Hub-Signature`, and a JSON body: `{"action" => "reopened", "repository" => {"owner" => {"login" => "org-a"}, "full_name" => "org-b/org_b_repo"}, "pull_request" => {...}, "sender" => {"login" => "attacker"}}`.
4. Assert (left side of binding = organization verified = `"org-a"`; right side = organization owning mutated stack = `"org-b"`) that these differ, and assert `response` is `:ok` and `stack.reload.archived?` is now `false` — proving the org-A-signed (or signature-less) request unarchived org-B's `ReviewStack`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
