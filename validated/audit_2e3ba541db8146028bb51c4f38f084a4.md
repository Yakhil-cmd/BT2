### Title
Cross-organization commit-status forgery via unscoped `Commit.where(sha:)` lookup breaks the "authenticated organization" ↔ "repository being written" binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, a value taken from the untrusted JSON payload (`repository.owner.login` or `organization.login`). Once the signature check passes, the actual write performed by `StatusHandler#process` looks up target records with `Commit.where(sha: params.sha)` — a **global, unscoped** query that ignores which organization/repository the verified signature was actually issued for. On a Shipit instance configured to serve multiple GitHub organizations (as documented in `config/secrets.development.shopify.yml` and `docs/setup.md`), any org admin who legitimately owns a webhook secret for their own org can forge a `status` webhook event that is valid for *their* org, but whose `sha` matches a commit belonging to a completely different organization's stack, and inject an arbitrary CI status for it.

### Finding Description
`WebhooksController#verify_signature` derives the signing key from attacker-controlled payload fields: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` only proves that whoever crafted the raw body knows the secret associated with the org resolved by `repository_owner`: [3](#0-2) 

Shipit explicitly supports hosting webhooks for multiple, independent GitHub organizations on one instance, each with its own `webhook_secret`: [4](#0-3) 

Once the signature check has been satisfied (proving only "this body was signed by *some org's* secret"), `WebhooksController#create` dispatches the entire payload to the event handler without re-checking that the payload's content is scoped to that same organization/repository: [5](#0-4) 

The base `Handler` class does provide a repository-scoped helper (`stacks`, scoped via `Repository.from_github_repo_name(repository_name)`): [6](#0-5) 

But `StatusHandler#process` does **not** use this scoping helper at all. It queries commits globally by SHA across the entire database, then writes an attacker-supplied status directly onto them: [7](#0-6) 

This is the binding break: the equality that should hold is `organization authenticated by verify_signature == organization owning the repository/commit actually written by the handler`. Because `repository_owner` (used to pick the verification key) and `sha` (used to select the write target) are two independent, both attacker-controlled fields inside the same self-signed payload, an attacker who legitimately controls their *own* org's webhook secret can satisfy `organization_authenticated = orgA` while making `commit_written ∈ orgB`, as long as they know or can enumerate a SHA belonging to orgB's stack (SHAs are public git commit hashes, visible on GitHub, PRs, CI logs, etc., and are not secrets).

Contrast:
- Before the attacker's forged request: signature verification and the record being mutated are implicitly assumed to belong to the same organization (this is the property the code is trying to enforce).
- After the forged request: `verify_signature` passes using orgA's key, yet `Commit.where(sha:)` mutates a commit that belongs to orgB, entirely bypassing any organization/repository boundary.

`CheckSuiteHandler` also exhibits a related but less severe issue — it does use the `stacks` scoping helper (based on `repository.full_name`), but that scoping field is likewise not covered by the org used for signature-key-selection independently, so cross-org confusion for check-suite refreshes is possible if `repository.full_name`'s owner differs from `repository.owner.login`. `StatusHandler` is the most direct and severe instance because it has no repository/stack scoping whatsoever.

### Impact Explanation
`Commit#create_status_from_github!` persists attacker-controlled `state`, `description`, `target_url`, and `context` as a `Status` on any commit reachable by SHA, irrespective of which org/repository it belongs to. Shipit's deploy-gating logic (`ci.require`, deployable checks in `app/models/shipit/stack.rb` / `Commit`) consults these `Status` records to decide whether a commit is safe to deploy. By forging a "success" status for a targeted victim commit that the attacker does not own, an attacker with only their own (unrelated) org's webhook secret can satisfy another organization's CI gating requirements and enable an **unauthorized deploy** of that commit through Shipit's UI/API — directly matching the "unauthorized deploy" impact category. This requires no privileged access to the victim org, no `ApiClient` token, and no GitHub credentials for the victim repository — only a webhook secret for an org they legitimately administer on the same shared Shipit instance.

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment (explicitly documented/supported configuration), (2) the attacker administering at least one org configured on that instance (and thus knowing/controlling that org's `webhook_secret`, which they set up themselves when creating their GitHub App), and (3) knowledge of a target commit SHA in the victim org (commit SHAs are not secret — publicly visible on GitHub, in PRs, CI logs, Slack notifications, etc.). Given these are realistic conditions for shared/internal Shipit instances serving several teams/orgs, likelihood is medium-to-high.

### Recommendation
- In `StatusHandler` (and ideally in the shared `Handler` base class for all handlers), always scope the lookup through the verified organization/repository — e.g. require that the commit's stack's repository matches `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and reject if it doesn't.
- Make `verify_signature` bind the authenticated organization to the request in a way handlers are forced to use (e.g., pass the resolved organization/repository down to `Handler.call`), rather than letting each handler independently re-derive scoping (or omit it, as `StatusHandler` does).
- Audit every handler under `app/models/shipit/webhooks/handlers/**` to confirm each one scopes its writes to `stacks`/`Repository.from_github_repo_name` derived from the same field used for signature verification, and add a regression test asserting an org-A-signed payload cannot mutate org-B's commits/stacks.

### Proof of Concept
1. Shipit instance is configured with two orgs, e.g. `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema).
2. Attacker legitimately administers `orgA`'s GitHub App and therefore knows `orgA`'s `webhook_secret`.
3. Attacker learns (via public GitHub, PR link, CI logs, etc.) a commit SHA `abc123` that belongs to `orgB`'s stack.
4. Attacker crafts a `status` event payload:
   ```json
   {
     "sha": "abc123",
     "state": "success",
     "context": "ci/tests",
     "description": "forged success",
     "target_url": "https://attacker.example/fake",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/irrelevant-repo" }
   }
   ```
5. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
6. `WebhooksController#verify_signature` resolves `repository_owner == "orgA"`, fetches `Shipit.github(organization: "orgA")`, and the HMAC check passes because the attacker legitimately knows `orgA`'s secret.
7. `WebhooksController#create` dispatches to `StatusHandler`, whose `process` executes `Commit.where(sha: "abc123").each { |commit| commit.create_status_from_github!(params) }` — matching and mutating `orgB`'s commit despite the signature only proving knowledge of `orgA`'s secret.
8. The forged "success" status is now attached to `orgB`'s commit, potentially satisfying `orgB`'s `ci.require` deploy gate.

Note: I was not able to fully verify, within the available context, the exact deploy-gating check in `app/models/shipit/stack.rb`/`app/models/shipit/commit.rb` that consumes `Status` records (grep confirmed matches on `ci`/`required`/`deployable` but I could not read the full method bodies before the tool budget ran out). The core binding-break vulnerability in `status_handler.rb`'s unscoped `Commit.where(sha:)` combined with `webhooks_controller.rb`'s payload-derived signature-key selection is confirmed directly from source, and is sufficient on its own to demonstrate cross-organization status forgery.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
