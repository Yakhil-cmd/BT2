### Title
Unbounded `count_coins` in indivisible asset denominations causes integer-precision overflow in cap validation - (File: validation.js)

### Summary
`validateAssetDefinition` in `validation.js` computes a declared total cap for indivisible (fixed-denomination) assets by summing `count_coins * denomination` for each denomination entry, but `count_coins` is checked only with `isPositiveInteger` (no upper bound), unlike `denomination`, which is bounded by `MAX_CAP` — and even that bound is only conditionally enforced depending on `pemCurvesFixMci`. This mirrors the TensorFlow `CalculateTensorSize` bug class (`count * size` overflow, CWE-190), except here the "overflow" manifests as floating-point precision loss/collision because ocore represents amounts as JS doubles rather than fixed-width integers.

### Finding Description
In `validateAssetDefinition` (validation.js), for asset definitions with `fixed_denominations: true`: [1](#0-0) 
```
for (var i=0; i<payload.denominations.length; i++){
    var denomInfo = payload.denominations[i];
    ...
    if (!isPositiveInteger(denomInfo.denomination))
        return callback("invalid denomination");
    if (denomInfo.denomination > constants.MAX_CAP && (objValidationState.last_ball_mci >= constants.pemCurvesFixMci || ...))
        return callback("denomination exceeds MAX_CAP");
    ...
    if ("count_coins" in denomInfo){
        if (!isPositiveInteger(denomInfo.count_coins))
            return callback("invalid count_coins");
        total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;
    }
    ...
}
```
`isPositiveInteger` (validation_utils.js) only checks `isFinite(value) && Math.floor(value)===value && value>0` — it imposes **no upper bound**, so `count_coins` can be any representable integer (including very large ones near `Number.MAX_VALUE`, as long as `Math.floor(x)===x`, which is trivially true for any float above 2^53 since all such floats are already "integers" in IEEE-754 representation).

Because JavaScript numbers are IEEE-754 doubles with only 53 bits of integer precision, `denomInfo.count_coins * denomInfo.denomination` can silently lose precision once the product exceeds `2^53` (~9.007e15), producing a rounded value that no longer reflects the true `count_coins × denomination` product — this is the direct analog to `count * size` overflowing in the TensorFlow report. The result `total_cap_from_denominations` is then compared for exact equality against `payload.cap` (itself bounded to `MAX_CAP`, 9e15, i.e., right at the edge of safe-integer precision): [2](#0-1) 
```
if (bHasUncappedDenominations && payload.cap)
    return callback("has cap but some denominations are uncapped");
if (total_cap_from_denominations && !payload.cap)
    return callback("has no cap but denominations are capped");
if (total_cap_from_denominations && payload.cap !== total_cap_from_denominations)
    return callback("cap doesn't match sum of denominations");
```
An attacker (any unit poster defining an asset) can choose a `count_coins`/`denomination` pair whose exact mathematical product exceeds `MAX_CAP`/`Number.MAX_SAFE_INTEGER` but whose IEEE-754-rounded product happens to equal a value ≤ `MAX_CAP` (i.e., collides with a legally declared `payload.cap`). This passes the equality check even though the true number of coins that can eventually be issued (`count_coins`, enforced via `max_issued_serial_number` in `asset_denominations`, see `indivisible_asset.js`) times `denomination` is actually larger than the declared/validated cap, because each individual issued coin's `amount` field is written directly as `denomination` (not reconstructed via multiplication) and validated independently against `MAX_CAP`, while the *aggregate* enforcement of the cap relies on this vulnerable summation performed only once at asset-definition time.

### Impact Explanation
If the declared cap check can be defeated by a crafted `count_coins`/`denomination` pair that collides under floating-point rounding, the true total number of coins mintable for the asset (bounded in the DB by `count_coins` via `asset_denominations.max_issued_serial_number`) can numerically exceed the cap that other nodes/wallets believe was validated — a supply-inflation class issue for that asset, undermining any downstream logic (AAs, exchanges, wallets) that trusts `asset.cap` as an upper bound on total issuable supply.

### Likelihood Explanation
This requires an attacker to author a unit defining an indivisible asset with `fixed_denominations: true` and craft `denominations` entries whose `count_coins * denomination` product experiences floating point rounding that coincidentally matches a chosen `payload.cap` value — a reachable path for any unpriviledged unit poster, but finding an exact rounding collision that also satisfies `denomination <= MAX_CAP` and `count_coins` being a "positive integer" per the loose check requires careful numeric construction and is not guaranteed to always be exploitable to a meaningfully large discrepancy. I was not able to fully verify a concrete end-to-end numeric example within the available tool budget (i.e., a specific `count_coins`/`denomination` pair reproducing the collision and a downstream state where a spendable output beyond the "true" cap becomes stable), so likelihood assessment is not fully confirmed to be High.

### Recommendation
Bound `count_coins` in `validateAssetDefinition` (and the analogous AA asset-definition validator in `aa_validation.js`) the same way `denomination` and `cap` are bounded — reject any `count_coins` (and the resulting product) greater than `constants.MAX_CAP`, and compute `total_cap_from_denominations` using an arithmetic method immune to floating-point precision loss (e.g., reject if `count_coins * denomination` exceeds `Number.MAX_SAFE_INTEGER`, or use `BigInt` for the summation and comparison), removing any legacy code path that skips the `MAX_CAP` bound based on `pemCurvesFixMci`.

### Proof of Concept
Not independently reproduced within the available investigation budget; the flaw is demonstrated structurally in the code: [3](#0-2) 
No upper bound exists for `count_coins` while `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` is done in double-precision, then compared for exact equality with `payload.cap` (` [4](#0-3) `). A concrete numeric collision (e.g., choosing `count_coins` and `denomination` such that their product, when rounded to the nearest representable double, equals an attacker-chosen `payload.cap ≤ 9e15`) would need to be constructed and tested against a live node to confirm exploitability; this was not completed due to tool-call limits.
