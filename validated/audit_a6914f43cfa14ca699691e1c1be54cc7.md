### Title
AA capped-asset issuance check omits sequence/stability filter, permanently freezing issuance after a non-good "issue" input - (File: aa_composer.js)

### Summary
When an autonomous agent (AA) issues a capped asset, `issueAsset()` in `aa_composer.js` decides whether the cap has already been issued by checking for the mere existence of any `type='issue'` row for that asset, without restricting to `sequence='good'` units. This is the same bug class as the reported Solidity issue: a "settled/done" indicator is derived from a side-effect (a DB row) that can be created without the corresponding successful state transition ever completing, and there is no code path to reset or retry once that indicator is set — permanently blocking the intended follow-up action.

### Finding Description
The AA composer's issuance routine for capped assets is: [1](#0-0) 

```js
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
```

This query has **no `sequence='good'`/`is_stable` filter**. Compare this to the properly-guarded equivalent used by the `asset[...].is_issued` getter elsewhere in the codebase: [2](#0-1) 

```js
if (field !== 'is_issued')
    return cb(!!objAsset[field]);
if (objAsset.is_private)
    return cb(false); // not issued if private
conn.query("SELECT 1 FROM inputs CROSS JOIN units USING(unit) WHERE type='issue' AND asset=? AND (main_chain_index<=? AND is_stable=1 AND sequence='good' " + (bAA ? "OR is_aa_response=1" : "") + ") LIMIT 1", [asset, mci], function(rows){
    cb(rows.length > 0);
});
```

The getter correctly excludes non-good/non-stable rows when reporting whether an asset was issued, but the actual issuance gate in `issueAsset()` does not. If the unit carrying the AA's own `type='issue'` input for a capped asset ever ends up with `sequence` other than `'good'` (e.g. `temp-bad`/`final-bad` due to a conflict resolved against it, similar to how any unit's sequence can change during stabilization, see `main_chain.js`'s handling of non-serial units), the `inputs` row nonetheless remains in the table: [3](#0-2) 

Once such a row exists, every subsequent attempt by the AA to issue the capped asset via `issueAsset()` will match `SELECT 1 FROM inputs WHERE type='issue' AND asset=?`, hit `rows.length > 0`, and return `'already issued'`. There is no code anywhere in `aa_composer.js` that re-checks `sequence`/`is_stable` before treating the asset as issued, and no mechanism to clear or retry the state — this exactly mirrors the reported pattern where a "done" flag is set from a side effect while the state that should legitimately gate future action (a properly-validated stable/good issuance) is never verified, and the only path forward is blocked forever.

### Impact Explanation
Because the capped-asset cap can only ever be issued once (`serial_number` must be `1` for capped assets, see `validation.js`), this defect permanently and irreversibly freezes the AA's ability to ever issue its own capped asset. Any AA logic that depends on eventually minting the capped supply (e.g., initial funding of a token economy, vault backing, liquidity bootstrapping) becomes permanently unusable — funds sent to the AA in anticipation of issuance are effectively locked/frozen, since the AA can never issue the asset it was designed to create. This matches the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Reachability requires a scenario in which the response unit carrying the AA's issue input is later found not to be in `sequence='good'` (e.g., propagated as a competitor unit is resolved as the "winning" one on the same address at parent-selection time, or the response's inputs conflict due to a race at stabilization). This is not an everyday occurrence, but it is entirely governed by normal DAG/parent-selection consensus mechanics that any unprivileged actor's units on the network can influence (posting competing units), not by any privileged/administrative access. Given that the check is unconditionally missing the `sequence`/`is_stable` filter that the equivalent getter deliberately includes, this is a genuine code defect reachable through ordinary posted units, not a purely theoretical or malicious-node-only condition.

### Recommendation
Add the same `sequence='good'` (and `is_stable`/`is_aa_response`, matching the AA execution phase) filtering to the "already issued" check in `issueAsset()` in `aa_composer.js` that is already used in the `is_issued` getter in `formula/evaluation.js`, so that only a confirmed, good, previously-committed issuance blocks future issuance attempts; non-good rows must be ignored, letting the AA retry issuance.

### Proof of Concept
1. Define a capped asset via an AA definition message with `cap` set and issued by the AA.
2. Have the AA compose and send a message issuing the capped asset (`issueAsset()` adds a `type='issue'` input, `serial_number=1`).
3. Arrange (via ordinary unit posting/parent selection, no privileged access) for that particular response unit to resolve with `sequence != 'good'` at stabilization (per the non-serial-unit resolution logic in `main_chain.js`), while its `inputs` row for `type='issue' AND asset=X` remains in the `inputs` table.
4. Trigger the AA to attempt issuance again: `issueAsset()`'s unfiltered `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` finds the stale row and returns `'already issued'`, `cb2('already issued')`, causing the caller to bounce with `'not enough funds for ... of asset ...'` permanently on every future attempt, even though the asset's supply was never actually, validly issued.
