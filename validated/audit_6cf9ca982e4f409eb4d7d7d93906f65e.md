### Title
Cross-organization webhook forgery: signature verified against payload's `repository.owner`, but write target selected by payload's independent `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate the HMAC signature purely from the attacker-supplied field `params.dig('repository','owner','login')` (via `repository_owner`), while every webhook handler (`Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) independently resolves the entity to write to from the unrelated field `payload.dig('repository','full_name')`. These two payload fields are never checked for consistency, so the organization whose secret authenticated the request is not bound to the repository/stack that is actually mutated.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` picks a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization when Shipit is configured for multiple GitHub orgs:
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [2](#0-1) 

Once the signature is accepted, the handler dispatch resolves the affected `Repository`/`Stack` from a completely separate JSON field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` and `StatusHandler` then act on whatever stacks/commits that `repository_name` resolves to:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 
```ruby
def process
  Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
end
``` [5](#0-4) 

The binding that should hold is: `organization authenticated (repository.owner.login used for HMAC) == organization owning the repository actually written (owner segment of repository.full_name)`. Nothing enforces this equality — the two fields are read independently and never cross-checked.

**Attack scenario (before/after):**
- Before: an operator running one Shipit instance with `Shipit.github` configured for two tenant organizations, `org-a` and `org-b`, each with its own webhook secret known to that org's own webhook administrator. A GitHub org admin for `org-a` legitimately knows `org-a`'s webhook secret (they entered it themselves when wiring up GitHub's webhook delivery to Shipit) but has no access to `org-b`'s stacks, commits, or secrets.
- Attack: that `org-a` admin crafts an arbitrary JSON body where `repository.owner.login = "org-a"` (so `verify_signature` selects and validates against `org-a`'s known secret) but `repository.full_name = "org-b/some-repo"`. They compute a valid `X-Hub-Signature` with `org-a`'s secret and POST it to the shared `/webhooks` endpoint with `X-Github-Event: push` (or `status`).
- After: `verify_signature` passes (org-a's secret matches), then `PushHandler`/`StatusHandler` resolve `repository_name` to `org-b/some-repo`, and call `stack.sync_github(...)` or inject a fabricated commit status on `org-b`'s commits — mutating a stack that belongs entirely to `org-b`, whose secret was never presented.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out in scope. Consequences on a multi-tenant Shipit instance:
- Forged `status` webhooks can flip a commit's CI state to `success`, satisfying `Commit#deployable?`/blocking-status checks (`ci.require`/`ci.blocking`), enabling an unauthorized deploy of an org-b stack whose safety checks were never actually satisfied by real CI — this is a cross-tenant integrity break feeding directly into deploy authorization decisions.
- Forged `push` webhooks can force `stack.sync_github` to run against org-b's stack using attacker-chosen `after` SHA values, causing cross-repository state writes the attacking org has no legitimate access to.

This satisfies the required "Critical — cross-repository writes / unauthorized deploy" bar, since it is entirely mediated by data the attacker fully controls (the JSON body) combined with a secret they legitimately possess for their own tenant.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (the `secrets.github` keyed-by-organization schema in `lib/shipit.rb`), and (2) the attacker being a legitimate webhook operator/admin for at least one of the configured organizations sharing the instance — not a privileged Shipit user, not requiring an `ApiClient` token, session, or repository write access to the *victim* org. This is a realistic scenario for any Shipit instance shared across multiple tenants/orgs, which the multi-org config code path explicitly supports.

### Recommendation
After `verify_signature` succeeds, re-derive/enforce that the organization used to select the webhook secret matches the owner segment of `repository.full_name` (or, more robustly, key handler lookups off the same verified organization rather than a separately-trusted field). Reject the request (422) if `repository.owner.login` (or `organization.login`) does not match the owner prefix of `repository.full_name`.

### Proof of Concept
1. Configure `secrets.github` with two orgs, `org-a` and `org-b`, each with a distinct `webhook_secret`.
2. As the legitimate GitHub webhook admin for `org-a`, compute:
```ruby
payload = {
  "ref" => "refs/heads/main",
  "after" => "<attacker chosen sha already known to exist on org-b/some-repo>",
  "repository" => { "owner" => { "login" => "org-a" }, "full_name" => "org-b/some-repo" }
}.to_json
sig = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_webhook_secret, payload)
```
3. `POST /webhooks` with header `X-Github-Event: push`, `X-Hub-Signature: <sig>`, body = `payload`.
4. `verify_signature` succeeds using `org-a`'s secret (matched via `repository_owner` = `"org-a"`).
5. `PushHandler#process` resolves `repository_name` = `"org-b/some-repo"` and invokes `stack.sync_github(expected_head_sha: ...)` on a stack the attacker's org has no association with — demonstrating the cross-organization write.
