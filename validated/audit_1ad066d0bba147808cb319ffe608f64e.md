### Title
`StatusHandler#process` updates commits by bare SHA across all repositories/stacks, and `PullRequest::OpenedHandler#provision?` provisions review stacks even when `review_stacks_enabled` is false — ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` with no repository/stack scoping, so any webhook-emitting party who can get GitHub to deliver a `status` event referencing a SHA that is also present in a victim's stack (e.g. shared fork history) will have that status applied to the victim's commit. This is amplified because `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` has a Ruby operator-precedence bug that provisions review stacks even when `repository.review_stacks_enabled` is `false`, in the `allow_with_label`/`prevent_with_label` provisioning modes.

### Finding Description
The broken binding: **the set of commits updated by a `status` webhook should equal the set of commits belonging to the repository that authenticated the webhook** — i.e. `commit.stack.repository == payload.repository`. Instead, `StatusHandler#process` computes:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This ignores the `repository`/`stacks` scoping helper that the base `Handler` class already provides (`stacks`, scoped via `Repository.from_github_repo_name(repository_name)`), which other handlers (opened/labeled) do use. [2](#0-1) 

`Commit#sha` is only unique per `(stack_id, sha)` (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally, so the same SHA legitimately exists as separate `Commit` rows across unrelated stacks (e.g. shared git history between a fork and upstream, or between two stacks tracking the same repository history). `StatusHandler` will match and mutate **all** of them, regardless of which repository's webhook signature validated the request. `add_status` then evaluates transitions and can trigger `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)` for the victim stack: [3](#0-2) 

Signature verification (`WebhooksController#verify_signature`) only checks that the payload was HMAC-signed for the org named in `payload.repository.owner.login` — it does not check that the `sha` belongs to that repository, and does not restrict `StatusHandler` to only the commits owned by the signing repository. [4](#0-3) 

The amplifying bug: `provision?` in `OpenedHandler` intends `review_stacks_enabled` to gate all provisioning behaviors, but Ruby operator precedence (`&&` binds tighter than `||`) makes it:
```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
``` [5](#0-4) 

So with `review_stacks_enabled == false` and `provisioning_behavior` set to `allow_with_label` (label present) or `prevent_with_label` (label absent), a review stack is still provisioned — contrary to the intended global disable switch. (Note: `LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` at the top level, so only the "opened" provisioning path is affected.) [6](#0-5) 

### Impact Explanation
An attacker who can cause GitHub to deliver a legitimately-signed `status` webhook (e.g., by setting a commit status via the GitHub API on a repository/fork where the Shipit GitHub App is installed, for a SHA shared with a victim's stack through common git history) can flip CI status (`success`/`failure`/`pending`) for `review/approved` (or any context) on a victim stack's commit that it never authenticated. Combined with the `provision?` precedence bug, a victim repository configured with `review_stacks_enabled = false` can still have review stacks provisioned and their required-status gating satisfied by a forged status, leading to an unauthorized deploy/merge decision on a stack the attacker does not control. This matches "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge" (Critical).

### Likelihood Explanation
Preconditions: (1) the attacker needs a repository/fork on which the shared multi-tenant GitHub App/webhook is installed so GitHub will sign and deliver a `status` event to Shipit; (2) the target SHA must also exist as a `Commit` row in the victim stack — realistic for forks or repositories with shared ancestry; (3) the victim repository must have `review/approved` (or another attacker-settable context) among its `required_statuses`/`blocking_statuses`, and, for the provisioning bypass, `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`. This does not require any Shipit secret or session — only the ability to set a GitHub status on a repo where the app is installed, which is a normal, low-privilege GitHub capability. It is repeatable against any stack sharing history with an attacker-accessible repository.

### Recommendation
Scope `StatusHandler#process` to only commits belonging to the repository that authenticated the webhook (e.g., `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or filter through the `stacks`/`repository` helper already defined on `Handler`), instead of `Commit.where(sha: params.sha)` unscoped. Separately, fix the `provision?` precedence bug in `opened_handler.rb` by explicitly parenthesizing: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status for one repository must not affect a commit from a different stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit) # or a stack with review_stacks_enabled false
  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_stack = Shipit::Stack.create!(repository: attacker_repository, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    "sha" => shared_sha, "state" => "success", "context" => "review/approved",
    "repository" => { "full_name" => attacker_repository.github_repo_name }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # BEFORE: victim_commit.reload.status.state must equal its prior state ("unknown"/"pending")
  # AFTER (bug): victim_commit.reload.status.state == "success" even though the webhook
  # authenticated only attacker_repository, proving cross-repository mutation.
  assert_not_equal "success", victim_commit.reload.status.state
end
```
Second test for the precedence bug: create a `Repository` with `review_stacks_enabled: false`, `provisioning_behavior: "allow_with_label"`, fire a `pull_request.opened` webhook whose PR carries the provisioning label, and assert `repository.review_stacks.count` remains `0` (fails today because `provision?` still returns true).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
