### Title
Webhook signature verification is a no-op when an organization has no `webhook_secret` configured, allowing unauthenticated forged GitHub events to be processed as trusted - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as "always verified" instead of "cannot be verified," so `WebhooksController#verify_signature` accepts any payload for organizations whose config omits the secret, regardless of what `X-Hub-Signature` (if any) is sent.

### Finding Description
`WebhooksController#create` dispatches the raw, attacker-supplied JSON body to handlers only after `verify_signature` passes: [1](#0-0) 

`verify_signature` picks which `GitHubApp` (and therefore which secret) to check against using a field taken straight from the unauthenticated request body: [2](#0-1) 

The actual check is: [3](#0-2) 

`return true unless webhook_secret` means that for any organization configured without a `webhook_secret`, the signature comparison is skipped entirely and the request is treated as if it had been correctly signed - the equality the system is supposed to enforce ("organization that authenticated" == "organization whose repository is written") degenerates to "any payload claiming to belong to that organization is authenticated," because nothing actually checks provenance.

Once past this gate, handlers act directly on attacker-controlled fields with real side effects, e.g. `PushHandler` triggers a GitHub sync for the target stack based solely on the payload's `ref`/`after`: [4](#0-3) 

If the affected stack has `continuous_deployment` enabled, a synced commit can be picked up by the continuous-delivery scheduler and deployed without any legitimate GitHub-side action ever having occurred: [5](#0-4) 

### Impact Explanation
This breaks the binding between "the party GitHub actually authenticated via HMAC" and "the repository/stack whose state is mutated." For any organization run without a configured `webhook_secret` (a state the documentation itself presents as optional, not a misconfiguration - "If you've set a webhook secret during the App creation, you should copy it here"), an unauthenticated network attacker can POST arbitrary JSON to `/webhooks/github`, forge `repository.owner.login`/`organization.login` to select that organization, and have Shipit process the event as a genuine GitHub notification. Depending on handler and stack settings this can trigger `sync_github` and, for continuously-deployed stacks, an unauthorized deploy of an existing commit - matching the "unauthorized deploy" Critical-impact bar.

### Likelihood Explanation
No credentials, tokens, or GitHub App keys are required - only knowledge that a target organization is configured without `webhook_secret`, which is a supported (documented-as-optional) configuration. The endpoint is unauthenticated by design (it's the GitHub webhook receiver), so the only barrier the engine is expected to enforce is HMAC verification, which this code path silently disables.

### Recommendation
Require `webhook_secret` to be present for any organization the app authenticates webhooks for, and fail closed (return `false`/422) rather than `true` when it is absent, e.g.:
```ruby
def verify_webhook_signature(signature, message)
  return false if webhook_secret.blank?

  algorithm, signature = signature.to_s.split("=", 2)
  return false unless algorithm == 'sha1'

  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```
Additionally, cross-check the resolved organization/repository against the stack actually targeted before allowing a handler to mutate state.

### Proof of Concept
1. Configure (or identify) an organization entry under `secrets.github` that omits `webhook_secret` (valid per current docs/setup).
2. Send `POST /webhooks/github` with header `X-Github-Event: push` and a body such as:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha of an existing commit in the target repo>",
  "repository": { "owner": { "login": "<that organization>" }, "full_name": "org/repo" }
}
```
No `X-Hub-Signature` header, or an arbitrary one, is required.
3. `verify_signature` calls `Shipit.github(organization: "org").verify_webhook_signature(nil, body)`, which returns `true` unconditionally because `webhook_secret` is blank.
4. `PushHandler#process` runs and calls `stack.sync_github(expected_head_sha: ...)` for every matching stack/branch, potentially triggering a real deploy for continuously-deployed stacks - all without any authentic GitHub signature ever being validated.
