The Sherlock report describes a Solidity/Uniswap-specific issue: the `Swap.sol::swapTokensMulti` function in the Derby Finance contracts used Uniswap's `Quoter` (a gas-inefficient, non-view-safe helper never intended for on-chain price validation) instead of properly enforced minimum-output slippage protection, exposing users to frontrunning/sandwiching.

Searching for the closest Polkadot SDK analog — `pallet-asset-conversion`, the FRAME AMM/DEX pallet — shows the opposite of the reported flaw: slippage protection is a first-class, enforced parameter in every swap path:

- `swap_exact_tokens_for_tokens` and `swap_tokens_for_exact_tokens` extrinsics take explicit `amount_out_min` / `amount_in_max` parameters and are checked against `Error::<T>::ProvidedMinimumNotSufficientForSwap` before any transfer occurs. [1](#0-0) 
- The same enforcement is done on the credit-based swap path. [2](#0-1) 
- The `Swap`/`SwapCredit` traits require `amount_out_min`/`amount_in_max` as part of their API surface, so callers (e.g. the `pallet-revive` precompile) cannot omit slippage bounds. [3](#0-2) 
- The precompile interface explicitly forwards `amountOutMin`/`amountInMax` from EVM-style contract callers into the pallet call, and there are dedicated tests confirming a swap with an unreachable `amountOutMin` reverts (`swap_fails_with_insufficient_output`). [4](#0-3) [5](#0-4) 
- Test `swap_should_not_work_if_too_much_slippage` explicitly verifies this guard in the FRAME pallet unit tests. [6](#0-5) 
- Even the read-only quote runtime API (`quote_price_exact_tokens_for_tokens`, analogous to Uniswap's Quoter) documents that it is informational only and that on-chain protection must come from `amount_out_min`/`amount_in_max`, and was further hardened (PR `prdoc/stable2606/pr_11761.prdoc`) to reject quotes the pool couldn't actually fulfill. [7](#0-6) [8](#0-7) 

There is no reachable code path in `pallet-asset-conversion` (or its precompile) where a user-facing swap extrinsic executes without an enforced minimum-output/maximum-input check, so the underlying invariant violated in the Solidity report (missing slippage bound) does not have a demonstrable analog here. Additionally, the original report itself is fundamentally a pure frontrunning/economic-attack class finding, which is explicitly out of scope per the analog-scan exclusion criteria even if a superficially similar pattern existed.

```text
title: 'asset-conversion-pallet: quote respects minimum balance'

doc:
  - audience: [Runtime Dev, Runtime User]
    description: |
      Quote functions (`quote_price_exact_tokens_for_tokens`, `quote_price_tokens_for_exact_tokens`)
      now return `None` when the computed output exceeds what the pool can actually withdraw while
      staying alive.

      Swap execution withdraws from pools with `Preserve` preservation, meaning the pool must retain
      at least `min_balance`. The quote functions did not account for this, so they could return a
      price for a swap that would fail at execution.

      Both quote functions now check the output against `reducible_balance(Preserve, Polite)` — the
      same preservation level the swap uses.

crates:
  - name: pallet-asset-conversion
    bump: patch
```
