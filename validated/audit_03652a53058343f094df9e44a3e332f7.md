### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while push processing is bound to `repository.full_name`, allowing an attacker's own registered organization to trigger a sync/deploy for a stack they don't own - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC signature against using `repository_owner`, which is read from the JSON body itself (`params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`). Once verified, `create` re-parses the same raw body and dispatches it to handlers (e.g. `PushHandler`), which independently determine the target repository via `payload.dig('repository', 'full_name')` in `Handler#repository_name`. These two fields are never cross-checked against each other.

### Finding Description
The trust binding that should hold is: *the GitHub organization whose secret validated the signature* == *the repository/stack that the handler acts on*. In `verify_signature`: [1](#0-0) 

the organization used to fetch the correct `github_app`/webhook secret is taken entirely from attacker-controlled JSON (`repository.owner.login`). Meanwhile the actual object acted upon is resolved separately in the base handler: [2](#0-1) 

and consumed by, e.g., `PushHandler#process`: [3](#0-2) 

Because both `repository.owner.login` and `repository.full_name` live in the same attacker-supplied JSON body and are read independently, nothing enforces that the owner segment of `full_name` matches `owner.login`. An attacker who has legitimately registered their own organization/repository in Shipit (and therefore knows a valid webhook secret for that org, e.g. as configured in `github_hooks` fixtures/config) can sign a payload with their own secret while setting `repository.full_name` to a victim's `owner/repo`. `verify_signature` will fetch and validate against the attacker's own org's secret successfully, and the request will proceed to `create`, where the handler resolves the *victim's* repository/stack via `full_name` and executes `stack.sync_github(expected_head_sha:)` on it.

### Impact Explanation
This breaks the equality "organization that authenticated (`repository.owner.login`) == repository that is written (`repository.full_name`)" required by scope. If the targeted stack has continuous deployment enabled, forcing a sync via a forged webhook can advance/trigger deploy eligibility for a stack the attacker does not control, constituting an unauthorized-deploy-adjacent write performed with credentials (webhook secret) that belong to a different, unrelated organization. This matches the "unauthorized deploy" / cross-repository impact category.

### Likelihood Explanation
Requires only that the attacker control (own) some organization/repository already registered with Shipit (an ordinary, low-privilege prerequisite — any team can add their own repo/stack), and knowledge of their own webhook secret, which is intrinsic once they've configured the webhook. No access to the victim's secret, `GITHUB_TOKEN`, or Shipit session is needed, satisfying "unprivileged attacker."

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, cross-validate that `repository.owner.login` (the identity that produced a valid signature) matches the owner segment of `repository.full_name` used by handlers before dispatching, or better, have handlers only trust the same organization identity that was used to select the verifying `github_app`, rejecting payloads where they diverge.

### Proof of Concept
1. Attacker registers `attacker-org/some-repo` as a Shipit stack and thus has a valid webhook secret for `attacker-org`.
2. Attacker crafts a `push` webhook JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/main", "after": "<victim head sha>"}`.
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known webhook secret over this exact raw body.
4. POST to `/github/webhooks`. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `github_app`, and successfully verifies the signature attacker computed.
5. `create` dispatches to `PushHandler`, which resolves `repository_name` = `"victim-org/victim-repo"` via `Handler#repository_name`, looks up the victim's stacks, and calls `stack.sync_github(expected_head_sha:)`, potentially advancing/triggering deploy eligibility on the victim's stack — despite the request never having been signed by anyone with access to `victim-org`'s webhook secret.

**Uncertainty / unverified items:** I was unable to retrieve `lib/shipit.rb`'s `Shipit.github(organization:)` implementation and `Stack#sync_github` internals before the tool budget ended, so I cannot fully confirm (a) exactly how organization-to-secret mapping is configured/scoped in this deployment (single global GitHub App vs. per-org secrets) and (b) whether `sync_github` alone (without additional GitHub-side state, e.g. commit statuses) is sufficient to actually trigger an unauthorized deploy versus only refreshing commit history. If the host application configures Shipit with a single global GitHub App/secret shared by all organizations (common for a single-tenant install), this specific analog may not hold, since then there is no distinct "attacker org secret" to exploit. Confirming this requires reading `lib/shipit.rb` and `Stack#sync_github`, which the index did not return in time — a Devin session with full repository access would be needed to confirm this conclusively.
