### Title
Cross-organization Team hijack via `Team.find_or_create_by!(github_id:)` skipping `organization` reassignment - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `params.team.id` (GitHub's numeric team id) and only sets `team.organization`/`team.github_team` inside the `find_or_create_by!` creation block, which Rails does not execute when a row already exists. [1](#0-0)  Consequently, if an attacker's own (legitimately-signed) `membership` webhook names a `team.id` that collides with an existing victim `Team`'s `github_id`, the handler resolves to the victim's row and adds the attacker-specified `member` to it, regardless of the `organization.login` in the current payload. [2](#0-1) 

### Finding Description
Broken binding: the code implicitly assumes `params.organization.login == team.organization` for every processed event, but that equality is never checked or enforced on the `find` path — only on `create`.

Path:
- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)`, and for a `membership` event (no `repository` key), `repository_owner` resolves to `params.dig('organization', 'login')` — i.e., the **attacker's own** organization. [3](#0-2)  In a multi-tenant Shipit deployment ("Using Multiple Github Applications"), each org has its own `webhook_secret`. [4](#0-3)  So a webhook signed with the attacker's own org's secret verifies successfully — this is a legitimate signature for the attacker's org, not a forged signature for the victim's org.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login; team.github_team = params.team }`. [1](#0-0)  Because `find_or_create_by!` only runs the block on INSERT, if a `Team` row with that `github_id` already exists (e.g., victim org's team, created earlier via a legitimate `membership` webhook or `Team.find_or_create_by_handle`), the found record's `organization` field is **never compared against or overwritten by** `params.organization.login`.
- `team.add_member(member)` is then called on the returned (victim's) `Team`, inserting a `Membership` for `member = User.find_or_create_by_login!(params.member.login)` — a user the attacker fully controls (an arbitrary GitHub login of the attacker's choosing). [5](#0-4) 

Exact request: attacker's org (already onboarded to the shared Shipit instance with its own GitHub App/webhook secret) sends a `membership` `added` event with `team.id` equal to the victim's team's `github_id` (an integer, discoverable/guessable or obtained from public GitHub API team listings) and `member.login` set to any login the attacker wants added.

Why existing guards fail: `verify_signature` only proves the payload came from the organization named in the payload itself (`repository_owner`), not that the `team.id` inside the payload actually belongs to that organization — GitHub's own numeric team IDs are global and not org-scoped by this code. There is no comparison of `team.organization` to `params.organization.login` before `add_member` runs.

### Impact Explanation
An attacker who controls any organization onboarded to the same multi-tenant Shipit instance can inject an arbitrary `Membership` (attacker-chosen GitHub login) into another organization's `Team` row purely by guessing/observing that team's numeric `github_id`. If the victim's `Team` is one of the teams configured in `Shipit.github_teams` (used by `User#authorized?` to gate access) — [6](#0-5)  — this becomes escalation into `Shipit.github_teams` authorization: the injected user gains `authorized?` truthy status and thus web/API access to the victim organization's stacks, deploys, and task streams. This matches the High severity category ("escalation into `Shipit.github_teams` authorization"), and if the compromised access is subsequently used to trigger deploys/merges on the victim's stacks, escalates toward Critical impact ("unauthorized deploy, rollback or merge"). It is repeatable against any victim team whose `github_id` is known, and cross-tenant (attacker's own signed webhook mutates another tenant's data).

### Likelihood Explanation
Preconditions: (1) the Shipit instance must be multi-tenant, i.e., host multiple GitHub organizations each with their own configured `webhook_secret`/GitHub App (a documented, supported configuration). [4](#0-3)  (2) The attacker must control (own or administer) one such onboarded organization so they can trigger a real `membership` webhook with a chosen `team.id`/`member.login` — GitHub team IDs are integers and are exposed via the GitHub API for teams the attacker can see, and org team IDs are not secret. (3) A victim `Team` row must already exist in the DB with the guessed `github_id` (created by an earlier legitimate membership event or `Team.find_or_create_by_handle`). Given these, the attack is a single crafted webhook with no stolen secrets — moderate likelihood, entirely dependent on the multi-tenant deployment model being in use.

### Recommendation
Scope the `Team` lookup by both `github_id` and the organization asserted in the verified payload, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and raise/reject (rather than silently proceed) if a `Team` with that `github_id` exists under a different `organization`. Additionally, always reassign `team.github_team`/`team.organization` on every event (not only on creation) so drift is corrected, and add an explicit guard: `raise ArgumentError, 'team org mismatch' if team.organization.present? && team.organization != params.organization.login`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (illustrative)
require 'test_helper'

module Shipit
  class MembershipHandlerCrossOrgTest < ActiveSupport::TestCase
    test "membership event from attacker org cannot inject member into victim org's team" do
      victim_team = Shipit::Team.create!(github_id: 999, organization: 'victim', slug: 'core', name: 'Core')

      payload = {
        'action' => 'added',
        'team' => { 'id' => 999, 'name' => 'Core', 'slug' => 'core', 'url' => 'https://example.com' },
        'organization' => { 'login' => 'attacker' }, # different org, signed with attacker's own webhook_secret
        'member' => { 'login' => 'evil-user' }
      }

      Shipit::User.expects(:find_or_create_by_login!).with('evil-user').returns(Shipit::User.create!(login: 'evil-user', name: 'evil-user'))

      Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

      victim_team.reload
      # Binding under test: params.organization.login ('attacker') == team.organization ('victim')?
      refute_equal 'attacker', victim_team.organization  # organization was NOT overwritten
      # But the membership still lands on the victim's team:
      assert victim_team.members.exists?(login: 'evil-user'),
             "attacker-controlled member was added to victim org's team despite organization mismatch"
    end
  end
end
```
This demonstrates that `params.organization.login` (`'attacker'`) never matches `team.organization` (`'victim'`) yet `team.add_member(member)` still executes against the victim's row.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end
