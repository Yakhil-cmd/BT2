### Title
Unescaped Newline in Data-Feed Value Corrupts Adjacent `unit` Field Parsing in Key/Value Store - ([File: data_feeds.js])

### Summary
`data_feeds.js` stores data-feed lookup entries as newline-delimited strings and later reconstructs the individual fields by naively calling `.split('\n')`. Because the data-feed *value* originates directly from an oracle-controlled `data_feed` message payload and is never checked for embedded `\n` bytes before being concatenated with the `unit` hash, an oracle can inject a literal newline into its posted value to corrupt the parsing of the adjacent `unit` field for any AA/light client that later queries that feed with `what='unit'` (or without specifying an explicit `feed_value`).

### Finding Description
When a data-feed message is stabilized, `addDataFeeds()` in `main_chain.js` writes an entry keyed by address/feed_name/mci whose *value* is the concatenation of the feed value and the unit hash, separated by a bare `\n`: [1](#0-0) 

No check exists anywhere in this path (or in the message payload prior to it) that rejects a `\n` character inside the feed value string, unlike the explicit `STRING_JOIN_CHAR` (`\x00`) guard used elsewhere for hash-string construction: [2](#0-1) 

On lookup, `readDataFeedByAddress()` retrieves this concatenated string and blindly splits it on `\n`, assuming exactly two parts (value, unit): [3](#0-2) 

If the oracle posts a feed value containing an embedded `\n` (e.g., `"120\nFAKEUNIT_HASH_LOOKING_STRING"`), the stored KV entry becomes `..."120\nFAKEUNIT_HASH_LOOKING_STRING\n<realUnit>"`. When any AA later evaluates `data_feed[[oracles=..., feed_name=..., what='unit']]` (or a plain lookup without `feed_value`, which uses this same value/unit concatenation path), `data.value.split('\n')` yields more than two parts: `arrParts[0]` becomes only the truncated value up to the first `\n`, and `arrParts[1]` — which the code trusts as `objResult.unit` — becomes an attacker-chosen string fragment instead of the real unit hash that authored the feed: [4](#0-3) 

The oracle address is itself explicitly listed and trusted by an AA definition (`oracles=[...]`), but the `oracles` parameter can be a *dynamic* oscript expression (e.g. derived from `trigger.data` as seen in tests), meaning an AA’s trust in "this data feed was authored by this unit" can be redirected by an ordinary trigger sender toward an attacker-controlled address, after which that address (the "oracle") can post a single data-feed unit whose value silently forges the `unit` identifier an AA formula receives from `what='unit'`.

### Impact Explanation
Any AA logic that uses `data_feed[[..., what='unit']]` result as an identifier — e.g. to compare against `trigger.unit`, to fetch further unit/definition/asset details via `unit[...]`, or to gate a payout on "this specific unit provided proof X" — can be tricked into operating on a forged/truncated string instead of the genuine unit hash. Depending on how the AA logic uses that value (a realistic and common oscript pattern for oracle price-feed and proof-verification AAs), this can lead to unauthorized fund release, bypass of proof-of-unit checks, or corrupted state, i.e., AA fund loss stemming from a data-integrity violation triggerable by an unprivileged data-feed poster.

### Likelihood Explanation
Reaching the sink requires only posting a standard `data_feed` message (no special permission) with a string value containing a `\n` character, and having an AA that is configured (directly or via a dynamic `oracles=` expression fed by trigger data) to trust that address as an oracle for `what='unit'`/no-value lookups. No length or character-set validation currently blocks `\n` in feed values, so the injection itself is trivial; the overall exploitability depends on the specific AA’s use of the returned unit string, which varies per AA design.

### Recommendation
- Reject data-feed values (and feed names) that contain the delimiter character (`\n`) at message validation time, consistent with the existing `\x00` (`STRING_JOIN_CHAR`) rejection pattern in `string_utils.js`.
- In `readDataFeedByAddress`, avoid storing/parsing `value` and `unit` as a single delimited string; store them as separate KV fields (or length-prefixed/escaped) so a malicious value can never shift field boundaries.
- Add regression tests posting a data-feed value containing `\n` and asserting the reader returns the correct, unmodified `unit`.

### Proof of Concept
1. Attacker-controlled address `ORACLE_ADDR` is (directly or via a dynamic `oracles=` expression driven by trigger data) trusted as an oracle by a target AA.
2. Attacker posts a `data_feed` unit from `ORACLE_ADDR`:
```
{ "app": "data_feed", "payload": { "price": "100\nAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=" } }
```
3. `addDataFeeds()` stores key `dfv\nORACLE_ADDR\nprice\n<strMci>` with value `"100\nAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=\n<realUnitHash>"`.
4. Any AA formula evaluating `data_feed[[oracles=ORACLE_ADDR, feed_name='price', what='unit']]` calls `readDataFeedByAddress`, which does `data.value.split('\n')`, returning `arrParts[1]` = `"AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA="` (attacker-chosen) instead of `<realUnitHash>`.
5. Any AA logic that trusts this forged "unit" string for further processing (e.g., `unit[[unit=that_value]].some_field`, or comparisons) operates on attacker-controlled data instead of the genuine authoring unit.
