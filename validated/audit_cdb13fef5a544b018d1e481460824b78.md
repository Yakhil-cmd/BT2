### Title
Webhook signature verification authenticates a different GitHub organization than the repository the dispatched handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the inbound HMAC against using `repository_owner`, derived from `payload.dig('repository', 'owner', 'login')` (or `organization.login` as fallback). But the actual event handlers dispatched afterwards resolve the target `Stack`/`Repository` using a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so the identity that is cryptographically authenticated (the org whose secret verified the signature) is not the identity that is actually written to. This is the same class of bug as H-1: a value used to authorize/select context is read from storage/payload separately from the value the state-changing operation actually operates on, letting an attacker "target" someone else's resource while authenticating as themselves.

### Finding Description
- `WebhooksController#verify_signature` picks the verification secret via: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization: repository_owner)` looks up the `GithubApp`/`webhook_secret` config keyed by `repository_owner`, and `verify_webhook_signature` does a straightforward HMAC-SHA1 compare against `request.raw_post`: [3](#0-2) 

- Once verification passes, `create` dispatches the *entire raw payload* to all registered handlers for the event, with no re-derivation or cross-check against `repository_owner`: [4](#0-3) 

- Every handler (`PushHandler`, `StatusHandler`, etc.) resolves the target `Stack` via the base `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely different key of the same JSON object than the one used for signature verification: [5](#0-4) 

- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on every matching stack resolved from that repository: [6](#0-5) 

- `StatusHandler#process` writes CI statuses onto any `Commit` matching `params.sha`, independent of which org owns the repo the commit belongs to: [7](#0-6) 

- `Repository.from_github_repo_name` blindly looks up whatever `owner/name` string is embedded in `full_name`: [8](#0-7) 

**The break as an equality:** the engine implicitly assumes `repository_owner (verification key) == repository.full_name's owner (target of the mutation)`. Because Shipit is multi-tenant (one `GithubApp`/`webhook_secret` per organization, per `Shipit.github(organization:)`), and the controller reads both values from the *same untrusted JSON body* the attacker fully controls, an attacker who has legitimately installed the Shipit GitHub App on **their own** organization (a normal, unprivileged onboarding step, not requiring access to the victim) knows their own `webhook_secret`. They can POST directly to `/webhooks` (bypassing GitHub's relay entirely) with:
- `repository.owner.login = "attacker-org"` (or `organization.login = "attacker-org"`) so `verify_signature` selects and successfully validates against the attacker's own known secret,
- `repository.full_name = "victim-org/victim-repo"` so the dispatched handler resolves and mutates the victim's `Stack`/`Commit` records.

Before the attack: `repository_owner` and the repo acted upon are only ever equal for legitimate GitHub-originated webhooks, because GitHub itself guarantees `repository.owner.login` and `repository.full_name` are consistent. After the attack: an attacker-crafted raw HTTP request breaks that assumed consistency, since Shipit never validates that the two fields agree, only that *some* valid signature exists for *some* organization.

### Impact Explanation
This lets an unprivileged attacker with no access to the victim's GitHub org, repo, or Shipit account force state changes on the victim's stacks:
- Via `PushHandler`, enqueue `GithubSyncJob` for the victim's stack with an attacker-chosen `expected_head_sha`, forcing an out-of-band sync against arbitrary refs.
- Via `StatusHandler`, forge CI/check statuses (`state`, `context`, `description`, `target_url`) on the victim's commits, which Shipit's deployability gating (CI status gating referenced in the engine's README) relies upon — potentially unblocking an unauthorized deploy of a commit that never actually passed CI.

This crosses an organizational trust boundary (attacker authenticates as org A but writes to org B's data) and can lead to an unauthorized deploy, satisfying the "High"/"Critical" impact bar (escalation/unauthorized deploy via forged CI status; cross-repository writes via forged push/sync events).

### Likelihood Explanation
Requires only that: (1) the attacker legitimately installs/onboards the Shipit GitHub App on any organization they control (a normal, unprivileged setup step, not a privileged Shipit account), and (2) they can send a raw HTTP POST to the public `/webhooks` endpoint (no GitHub relay needed, no Shipit session, no `ApiClient` token). Both conditions are trivially satisfiable by any external actor who is a legitimate tenant of a multi-org Shipit deployment, making this realistically exploitable without insider access.

### Recommendation
Bind the signature-verification identity to the identity actually acted upon:
- After computing `repository_owner` for secret selection, re-derive the owner from `repository.full_name` (or vice versa) and reject the request (422) if they don't match.
- Alternatively, have every `Handler` (and `Handler#repository_name`) require and validate the owning organization/App identity that successfully verified the signature, rather than trusting `full_name` from the raw payload independently.

### Proof of Concept
1. Attacker installs the Shipit GitHub App on `attacker-org` (a legitimate, unprivileged onboarding action), obtaining/knowing `attacker-org`'s `webhook_secret` from their own GitHub App/organization settings.
2. Attacker crafts a raw JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefcafefeed0000000000000000000000",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, raw_body)>` and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s known secret, and the HMAC matches — verification passes (see [9](#0-8) ).
5. `create` dispatches to `PushHandler`, which resolves `repository_name = "victim-org/victim-repo"` via `Handler#repository_name` (see [10](#0-9) ), finds `victim-org`'s stacks, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on them, all despite the request having authenticated solely as `attacker-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
