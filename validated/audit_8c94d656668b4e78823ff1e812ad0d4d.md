### Title
`StackStxOp::check` fails to reject out-of-range `num_cycles` (warns instead of returning `Err`) - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::check` validates `num_cycles` with an `if` block that only logs a `warn!` and does not `return Err(...)`, so execution falls through and the function returns `Ok(())` even when `num_cycles == 0` or `num_cycles > POX_MAX_NUM_CYCLES`. This lets a burnchain-crafted stacking op with an invalid lock duration be accepted by consensus code and forwarded to the `.pox-5` PoX-locking logic.

### Finding Description
The broken equality is: **"an accepted `StackStxOp` implies `0 < num_cycles <= POX_MAX_NUM_CYCLES`"**. This invariant is supposed to be enforced in `check()`: [1](#0-0) 

Lines 405-410 detect the invalid condition and emit a `warn!`, but there is no `return Err(op_error::...)` inside that `if` block — control simply proceeds to the signer-key check and then `Ok(())` at line 418. Compare this to the `stacked_ustx == 0` check immediately above it, which correctly does `return Err(op_error::StackStxMustBePositive)`: [2](#0-1) 

**Attacker's exact call / exploit flow:** An unprivileged attacker with their own BTC/STX crafts a `PreStxOp` + `StackStxOp` pair via `BurnchainTransaction`, setting the `num_cycles` byte in the OP_RETURN payload (offset 16) to `0` (or to a value `> POX_MAX_NUM_CYCLES`, e.g. 97). `StackStxOp::parse_from_tx` (lines 270-350) decodes this value verbatim into `data.num_cycles` via `StackStxOp::parse_data` (lines 176-230) with no bounds validation at parse time — only `check()` is meant to reject it. Because `check()` doesn't return an error for this case, the malformed op is treated as valid by whatever caller invokes `.check()` before forwarding the op's fields (`stacked_ustx`, `num_cycles`, `reward_addr`, `signer_key`) into the `.pox-5` stacking entry points.

**Why this matters:** `num_cycles` is a hard consensus-level input into the PoX-5 lock/reward-cycle math (used to compute `unlock_burn_height`/`lock-period` and the number of reward cycles the STX is committed for). If `num_cycles = 0` reaches pox-5's Clarity logic unguarded, this could produce a lock whose unlock-cycle equals its first-reward-cycle (i.e., a phantom/never-materializing lock), or if pox-5 does perform its own guard, the burnchain op is simply dropped/rejected downstream — the outcome depends entirely on whether `.pox-5`'s own Clarity-side validation (which is out of scope per the rules, since `pox.clar`/`pox-2.clar`/`pox-3.clar` are excluded and I could not fully verify pox-5.clar's redundant checks within tool-call budget) re-validates `num_cycles` independently.

### Impact Explanation
If `.pox-5` (or `pox-locking` Rust glue) does **not** independently re-validate `num_cycles` before computing unlock height, this is Critical: a `num_cycles = 0` op could be recorded as an active stacking commitment representing STX that is never actually locked for even one cycle (unlock-cycle == first-reward-cycle), i.e., unlocking value that was never meaningfully locked, while still consuming a reward slot/commitment record. A `num_cycles` far above `POX_MAX_NUM_CYCLES` would be High (freezing beyond any staker-permitted duration) if the value is used directly in unlock-height arithmetic without a second clamp.

### Likelihood Explanation
Preconditions are trivial for an unprivileged attacker: they only need to author a valid Bitcoin `PreStxOp`+`StackStxOp` pair from their own UTXOs (standard, publicly documented op format) and set the `num_cycles` byte to 0 or an out-of-range value; no privileged role, signer key, or victim interaction is required. The bug in `check()` is unconditional (not phase- or state-dependent), so it is repeatable per stacking transaction the attacker chooses to submit.

### Recommendation
Add `return Err(op_error::StackStxMustBePositive)` (or an equivalent new `op_error` variant, e.g. `StackStxInvalidCycles`) inside the `if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES` block in `StackStxOp::check` at stackslib/src/chainstate/burn/operations/stack_stx.rs:405-410, mirroring the pattern already used for `stacked_ustx == 0` a few lines above.

### Proof of Concept
Rust unit test in `stackslib/src/chainstate/burn/operations/stack_stx.rs` tests module:
```rust
#[test]
fn test_check_rejects_invalid_num_cycles() {
    let sender = StacksAddress::from_string("ST2QKZ4FKHAH1NQKYKYAYZPY440FEPK7GZ1R5HBP2").unwrap();
    let reward_addr = PoxAddress::Standard(
        StacksAddress::new(C32_ADDRESS_VERSION_MAINNET_SINGLESIG, Hash160([0x01; 20])).unwrap(),
        None,
    );
    let mut op = StackStxOp::new(&sender, &reward_addr, 100, 0, None, None, None);
    // Assert LHS/RHS of invariant "check() Ok implies 0 < num_cycles <= POX_MAX_NUM_CYCLES"
    assert!(op.check().is_err(), "num_cycles=0 must be rejected, but check() returned Ok");

    op.num_cycles = POX_MAX_NUM_CYCLES + 1;
    assert!(op.check().is_err(), "num_cycles > POX_MAX_NUM_CYCLES must be rejected, but check() returned Ok");
}
```
Running this against the current code will show both assertions fail (i.e., `check()` returns `Ok(())`), confirming the vulnerability as described. A follow-up integration test would additionally need to trace the accepted op through the sortition-DB/coordinator processing into `.pox-5`'s stacking handler to confirm whether a redundant Clarity-side check masks the impact — this second step could not be completed within the available tool budget, so the downstream materialization (Critical vs. mitigated-by-Clarity) remains unverified.

```rust
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
```
