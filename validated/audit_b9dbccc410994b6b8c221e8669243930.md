### Title
Unsafe ERC721 `transferFrom` in Bridge Allows Silent Transfer Failure Leading to Unauthorized Cross-Chain Minting — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721` calls raw `IERC721.transferFrom()` without verifying success. Unlike the ERC20 path (which uses `SafeERC20`), there is no equivalent safe wrapper for ERC721. If a registered non-standard ERC721 token silently fails its `transferFrom` (no revert, no return value), the bridge still emits `RequestValueTransfer`, increments `requestNonce`, and the counterpart bridge will mint or release the token on the other chain — without the original token ever being locked.

---

### Finding Description

`BridgeTransferERC20` and `BridgeFee` both declare `using SafeERC20 for IERC20` and use `safeTransfer`/`safeTransferFrom` throughout: [1](#0-0) [2](#0-1) 

`BridgeTransferERC721`, however, imports no safe wrapper and calls raw `IERC721.transferFrom()` in two places:

**Deposit path** (`requestERC721Transfer`, line 129):
```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
``` [3](#0-2) 

**Withdrawal path** (`handleERC721Transfer`, line 69):
```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [4](#0-3) 

If the token's `transferFrom` does not revert on failure (non-standard ERC721), execution continues past the call. In the deposit path, `_requestERC721Transfer` is still called, which emits `RequestValueTransfer` and increments `requestNonce`: [5](#0-4) 

The counterpart bridge operators observe this event and call `handleERC721Transfer` on the other chain, minting or releasing the token to the recipient — even though the original token was never transferred to the bridge.

---

### Impact Explanation

- **Deposit path**: An attacker holding a non-standard ERC721 token (or no token at all, if `transferFrom` is a no-op) can trigger a cross-chain mint/release on the counterpart chain without locking the original token. This is an unauthorized mint of a bridged asset.
- **Withdrawal path**: If `transferFrom` silently fails during `handleERC721Transfer`, the bridge consumes the handle nonce and emits `HandleValueTransfer`, permanently marking the request as handled, but the recipient never receives the token. The nonce is burned and the asset is lost.

Both cases corrupt the bridge's custody invariant: *tokens minted/released on the counterpart chain must equal tokens locked on this chain*.

---

### Likelihood Explanation

Requires a registered non-standard ERC721 token whose `transferFrom` does not revert on failure. Token registration requires owner/operator privileges (`registerToken`), but the bridge is explicitly designed to support arbitrary ERC721 tokens. Non-standard ERC721 implementations exist in the wild. Once such a token is registered, any user can trigger the deposit-path exploit without further privilege.

---

### Recommendation

Replace raw `IERC721.transferFrom()` calls with `safeTransferFrom()` (which checks `onERC721Received` on the recipient) or add explicit ownership verification after the transfer:

```solidity
// Instead of:
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);

// Use:
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);

// Or verify custody after transfer:
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
require(IERC721(_tokenAddress).ownerOf(_tokenId) == address(this), "transfer failed");
```

Apply the same fix to the withdrawal path in `handleERC721Transfer`.

---

### Proof of Concept

1. Deploy a non-standard ERC721 token whose `transferFrom` is a no-op (does not revert, does not change ownership).
2. Owner registers this token in the bridge via `registerToken`.
3. Attacker calls `requestERC721Transfer(tokenAddress, attackerOtherChainAddr, tokenId, "")`.
4. `IERC721(tokenAddress).transferFrom(attacker, bridge, tokenId)` silently does nothing — attacker still owns the token.
5. `_requestERC721Transfer` emits `RequestValueTransfer` and increments `requestNonce`.
6. Counterpart bridge operators observe the event and call `handleERC721Transfer` on the other chain.
7. Counterpart bridge mints/releases the ERC721 token to the attacker's address on the other chain.
8. Attacker now holds the token on both chains. Repeat indefinitely. [6](#0-5)
