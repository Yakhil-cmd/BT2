### Title
`ProxyType::NonTransfer` falsely claims superset of `ProxyType::Auction`, letting a NonTransfer proxy reach `Registrar::swap` it is explicitly denied — ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
This is the same authorization-integrity bug class as BIT-gitlab-2020-13266 (a principal with restricted permissions can widen another principal's permission record without the check verifying that the new permission set is actually a subset of what the truster granted). In `pallet-proxy`, `add_proxy`/`remove_proxy` issued *through* an existing proxy are authorized solely via `ProxyType::is_superset`, not by re-checking `ProxyType::filter` call-by-call [1](#0-0) . Parity itself found and fixed exactly this defect for `NonTransfer`/`Governance` on Asset Hub Westend [2](#0-1) , but the relay-chain runtimes (`polkadot/runtime/westend`, `polkadot/runtime/rococo`, and `substrate/frame/staking-async/runtimes/rc`) still contain an un-fixed instance of the identical pattern between `ProxyType::NonTransfer` and `ProxyType::Auction`.

### Finding Description
In `polkadot/runtime/westend/src/lib.rs` (and identically in rococo and the staking-async `rc` runtime), `is_superset` declares `NonTransfer` a superset of **every** other `ProxyType`: [3](#0-2) 

But `NonTransfer::filter` explicitly *excludes* `Registrar::swap` (only `register`/`deregister`/`reserve` are allowed, with a comment confirming the exclusion is intentional): [4](#0-3) 

Meanwhile `ProxyType::Auction::filter` allows the entire `Registrar` call family, including `swap`, with no exclusion: [5](#0-4) 

`pallet_proxy::do_proxy` only re-derives permission for `add_proxy`/`remove_proxy` by checking `is_superset`, never by diffing the two filters call-by-call: [6](#0-5) 

Because `NonTransfer::filter` also admits raw `RuntimeCall::Proxy(..)` calls, a delegate holding only a `NonTransfer` proxy can:
1. Call `Proxy::proxy(real, None, Proxy::add_proxy{ delegate: attacker, proxy_type: Auction, delay: 0 })` on behalf of `real`. `is_superset(NonTransfer, Auction)` returns `true`, so this passes the origin filter in `do_proxy` and installs a new `Auction` proxy entry for `real`.
2. Call `Proxy::proxy(real, Some(Auction), Registrar::swap{ .. })`. `Auction::filter` admits the entire `Registrar` pallet, so the call dispatches with `Signed(real)` origin — reaching `Registrar::swap`, a call the `NonTransfer` filter comment explicitly says must be denied.

This is structurally identical to the CVE's root cause: a permission-check for "grant/modify another principal's permission record" (`is_superset`) is decoupled from the actual permission set (`filter`), so a restricted actor can escalate itself/others to a nominally-different-but-effectively-broader permission class.

### Impact Explanation
A `NonTransfer` proxy delegate (who is deliberately denied direct access to `Registrar::swap`) can dispatch `Registrar::swap` on behalf of the delegator by round-tripping through a self-granted `Auction` proxy. `swap` mutates a parachain's registrar-tracked identity/manager records; combined with a compromised or malicious `NonTransfer` delegate this is an unauthorized-dispatch / permission-integrity violation matching the "insecure authorization allows updating permissions under conditions the check should have denied" pattern of the reported CVE. Actual monetary/state impact depends on `swap`'s full precondition set (para manager identity, pending swap request matching, etc.), which I could not fully verify in this session — this bounds the severity below the already-accepted `Governance` variant of this same class of bug (fixed at Medium/patch-level per `pr_12769`), and I flag it for review rather than asserting Critical/High impact.

### Likelihood Explanation
No privileged role, governance, or stolen keys are required — only a normal `NonTransfer` proxy relationship that already exists in production runtimes wherever `Auction`/`NonTransfer` proxy types coexist (Polkadot/Kusama/Westend/Rococo relay chains, and the new staking-async `rc` runtime). The escalation path uses only ordinary signed extrinsics (`Proxy::proxy`, `Proxy::add_proxy`) that are always reachable and fee-paying. Discovery required only reading the `filter`/`is_superset` pair, exactly as Parity's own regression test (`proxy_type_superset_relation_matches_call_filters`) does for Asset Hub.

### Recommendation
Remove `(ProxyType::NonTransfer, ProxyType::Auction) => true` implicitly caused by the blanket `(ProxyType::NonTransfer, _) => true` arm, and instead enumerate exactly the subsets `NonTransfer` denies nothing extra for (mirroring the fix pattern in `pr_12769`). Add a lattice-consistency regression test analogous to `proxy_type_superset_relation_matches_call_filters` [7](#0-6)  to `polkadot/runtime/westend`, `polkadot/runtime/rococo`, and `substrate/frame/staking-async/runtimes/rc`, so this class of bug cannot silently reappear on any other lattice edge.

### Proof of Concept
Not executed against a live network. A minimal integration test (following the existing `substrate/frame/proxy/src/tests.rs` harness and the `staking_proxy_can_manage_staking_operator`/`pure_proxy_stash_can_delegate_to_staking_operator` pattern already present) would:
1. Configure `Test`/mock runtime with Westend's real `ProxyType` enum and `filter`/`is_superset` impl (or run this directly against `westend-runtime`).
2. `Proxy::add_proxy(real, delegate, ProxyType::NonTransfer, 0)`.
3. `Proxy::proxy(delegate, real, None, Box::new(Proxy::add_proxy{ delegate, proxy_type: ProxyType::Auction, delay: 0 }))` — expect `Ok` / `ProxyExecuted{result: Ok(())}`.
4. `Proxy::proxy(delegate, real, Some(ProxyType::Auction), Box::new(Registrar::swap{ .. }))` — expect the call to *not* be filtered out (`ProxyExecuted{result: Ok(..)}` or a `Registrar`-internal error, but not `CallFiltered`), proving `Registrar::swap` was reached despite `NonTransfer::filter` explicitly denying it.

I was not able to actually run this reproduction in this session (no code execution available), so step 4's exact dispatch outcome (pass/fail on `swap`'s own preconditions) is unverified — only the origin-filter bypass (steps 2–3, backed directly by the `is_superset`/`filter` code shown above) is established with certainty from source inspection.

/// `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `ProxyType::is_superset`, so a
/// proxy type that *declares* itself a superset of another must also *admit* every call that other
/// type admits. Otherwise the "smaller" type is reachable as an escalation: the declared superset
/// can grant itself the subset proxy and thereby gain permissions its own filter denies.
///
/// This checks that property across the whole lattice rather than a single pair, so the class of
/// bug cannot silently reappear on another edge.
#[test]
fn proxy_type_superset_relation_matches_call_filters() {
	use frame_support::traits::InstanceFilter;

	let calls = representative_proxy_calls();

	for superset in all_proxy_types() {
		for subset in all_proxy_types() {
			if !superset.is_superset(&subset) {
				continue;
			}

			for call in calls.iter() {
				if subset.filter(call) {
					assert!(
						superset.filter(call),
						"lattice violated: {superset:?} declares itself a superset of {subset:?}, \
						 but rejects {call:?} which {subset:?} admits",
					);
				}
			}
		}
	}
}
