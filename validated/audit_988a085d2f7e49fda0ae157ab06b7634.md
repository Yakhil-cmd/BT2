## Title
Malicious AA address referenced as a payment recipient can force a permanent revert/DoS of the calling AA - ([File: aa_composer.js])

### Summary
The reported bug (factory owner reverting `claimFees` push payments to DoS every deployed token) maps to an analogous "forced revert blocks everyone" pattern in ocore's Autonomous Agents (AA) engine. When an AA sends an output to an address that turns out to be another AA, this triggers a **secondary AA trigger**. If that secondary AA bounces (deliberately, via its own logic), the **entire primary AA response is reverted** — including all unrelated payments and state changes intended for other, legitimate parties in the same trigger.

### Finding Description
In `handleSecondaryTriggers`, every output address of a response unit that is itself an AA is invoked as a secondary trigger via `handleTrigger`: [1](#0-0) 

If any secondary AA bounces, the error propagates and the *whole* primary trigger, not just the secondary branch, is unwound: [2](#0-1) 

`revert()` rolls back **all** balance/state changes accumulated so far in the entire trigger chain (all previously executed secondary AAs, all payments), then calls `bounce()` on the primary trigger: [3](#0-2) 

This is the same "push, and let a third party's revert block everyone" shape as the reported bug: a value that a contract sends to some address (chosen by legitimate business logic, e.g. "current highest bidder", "current owner", "referral address") is a push. If that address happens to be (or is deliberately deployed as) an AA that always bounces, then every future trigger of the paying AA that tries to send to it will cause the *entire* transaction — including payouts and state updates meant for completely unrelated, honest counterparties in the same unit — to be discarded and bounced.

Unlike the smart-contract report where the offending party is a privileged "factory owner", here the attacker does not need any special privilege: any user can get their own address stored as a payout recipient through completely ordinary interaction with the target AA (e.g., by placing the highest bid in an auction AA, becoming a registered "owner" in a marketplace AA such as `test/samples/things_registry_and_marketplace.oscript`, or being recorded as counterparty in a payment-channel style AA). Once their address is deployed as an AA whose `init`/logic unconditionally calls `bounce(...)`, every subsequent trigger that needs to pay out to that stored address is guaranteed to revert.

### Impact Explanation
This can permanently freeze funds and operation of an AA: any future user's legitimate trigger to the AA (e.g. a new, higher bid, a purchase, a channel close) fails because the payout logic must also refund/pay the attacker's poisoned address in the same unit. Because `revert()` unwinds the *whole* primary trigger (all secondary AAs and their balance updates), no one interacting with that AA afterward can obtain their funds or state changes — an availability/fund-freezing impact analogous to the original report's "every token holder blocked from claiming fees."

### Likelihood Explanation
Likelihood is low-to-medium: it requires (1) an AA design pattern where a stored address (attacker-controlled) is later paid out to, and (2) the attacker to get that address recorded through normal use before defining it as an always-bouncing AA. Many published AA templates in this codebase follow exactly this pattern (auctions, marketplaces, escrow/channel AAs), so the preconditions are commonly met.

### Recommendation
- When composing a payment message whose destination could later resolve to an arbitrary/attacker-influenced address, avoid triggering a synchronous secondary-AA call that can unwind the whole primary response; consider isolating the failure of a single secondary trigger (e.g., only rolling back that branch and its costs, not the entire trigger chain), or requiring the AA logic to defensively swallow known failure states via a low-level `payment`-only message (which doesn't chain-trigger) rather than dynamic addresses that can become AAs.
- At minimum, AA authors should be warned that any output address they don't fully control (winner/owner/counterparty state variables) can become a griefing vector because it can later be defined as a bouncing AA, freezing the entire contract for future users.

### Proof of Concept
1. Deploy AA `M` (auction/marketplace-style) that stores the winning bidder's address in state and, on a later trigger, sends a refund/payout to that stored address as part of its response (as in `test/samples/things_registry_and_marketplace.oscript`, sending change/price back to prior owner).
2. Attacker becomes the current stored "winner"/"owner" address through ordinary use.
3. Attacker deploys an `autonomous agent` at that exact address (chash160 of a definition they control, or simply defines the AA at that address before it is otherwise used) whose logic unconditionally calls `bounce('griefing')`.
4. Any subsequent legitimate trigger of AA `M` that must pay the attacker's address triggers `handleSecondaryTriggers` → the malicious AA bounces → `revert()` unwinds the entire primary trigger's payments and state changes, per [2](#0-1)  and [3](#0-2) , denying service to all subsequent honest users of `M`.
