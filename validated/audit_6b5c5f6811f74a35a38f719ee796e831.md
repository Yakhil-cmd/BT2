### Title
Caller-selected swap routes can redirect signed authorization into arbitrary wallet-token transfers - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller swap strategies pass caller-controlled route data to the configured router and place that router call inside the caller's authorization context. Because venue addresses in the route are not restricted by the controller, a malicious route can include a contract that requests an unrelated `token.transfer(victim, attacker, amount)`. Soroban simulation records that transfer as a child authorization under the victim's controller call. If the victim signs the simulated authorization tree without inspecting every child, the malicious transfer executes together with an otherwise valid swap.

### Finding Description
`multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` all funnel attacker-influenced `StrategySwap` bytes into `swap_tokens`. `swap_tokens` snapshots balances, grants the router one exact controller-token transfer authorization, then invokes `router.execute_strategy(&controller, &amount_in, swap)` without validating what contracts the route reaches [1](#0-0) . The controller's post-call checks only bound the controller's input-token spend and require positive measured output [2](#0-1) ; they do not constrain additional authorization children requested during route execution.

This is demonstrated by `rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. A router-selected rogue pool calls `token::Client::transfer(&victim, &to, &amount)` from inside its swap callback [3](#0-2) . Simulation records that wallet transfer as a child invocation beneath the victim's `swap_collateral` authorization [4](#0-3) . In enforcing mode, an honest root-only authorization tree rejects the transfer, but a tree containing the malicious child executes it and drains the victim's unrelated token balance [5](#0-4) .

The same exposure exists on the normal `swap_collateral` path: after authenticating the caller and account owner/delegate, the controller withdraws collateral and sends the caller-provided route through `withdraw_and_swap_from_supply` [6](#0-5) .

### Impact Explanation
A malicious venue can steal any wallet token and amount included in the simulated authorization tree, independent of the amount being swapped and independent of whether that token is listed by the protocol. The test demonstrates complete theft of an unrelated wallet token while the swap still produces the expected collateral output [7](#0-6) .

The malicious transfer can also target protocol-held balances if those holdings are represented by an address whose authorization is already being supplied for the transaction. The authorization is scoped to the top-level caller's signed tree, so pool or other-user funds are not directly exposed merely by submitting a malicious route.

### Likelihood Explanation
Exploitation requires the victim to execute an attacker-supplied route and sign the authorization tree produced by simulation. Wallets or clients that present only the top-level `swap_collateral`, `swap_debt`, `multiply`, or equivalent call—without requiring review of every nested authorization—can make the malicious child difficult to notice. No privileged protocol role, leaked key, upgrade, or oracle manipulation is required to construct the route.

The likelihood is moderated by Soroban authorization enforcement: the attack fails if the victim signs only the honest top-level invocation without the malicious child. It is therefore a user-interaction phishing-style authorization expansion rather than an unauthenticated direct drain.

### Recommendation
Do not rely on users or wallets to detect arbitrary authorization children generated by an opaque route.

- Restrict route venue addresses to protocol-reviewed venue adapters/pools, or otherwise prevent route-controlled contracts from invoking token transfers unrelated to the swap.
- Where Soroban supports it, constrain the invoked route so no additional caller-authorization children can be recorded beneath the controller operation.
- At minimum, make authorization-tree validation part of the contract-facing API contract: reject or clearly surface any signed tree containing children other than the expected strategy input transfer.
- Add regression coverage for every public strategy that accepts `StrategySwap`, not only `swap_collateral`, using a rogue route hop that attempts an unrelated wallet-token transfer.

### Proof of Concept
1. Victim Alice holds a supplied USDC position and an unrelated token `WALLET`.
2. Attacker deploys a venue-compatible contract whose swap function calls:

   `WALLET.transfer(alice, attacker, alice_wallet_balance)`

3. Attacker constructs a `StrategySwap` route that passes through this malicious venue while still delivering enough legitimate output token for the controller's post-swap checks.
4. Alice submits `swap_collateral(caller=alice, account_id, current=USDC, from_amount, new=ETH, swap=malicious_route)` through transaction simulation.
5. Simulation succeeds because the route provides valid output, but the recorded authorization tree contains an extra child:

   `WALLET.transfer(alice, attacker, alice_wallet_balance)`

6. Alice signs the simulated authorization tree without noticing the additional child.
7. The malicious transfer executes inside the route, the swap still returns positive ETH, final account checks pass, Alice's wallet balance becomes zero, and the attacker receives the unrelated wallet token.

This sequence is implemented by the regression fixture: simulation records the malicious transfer under Alice's `swap_collateral` authorization and drains the unrelated token [4](#0-3) , while enforced signing shows the transfer succeeds precisely when that malicious child is included [8](#0-7) .

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
