### Title
Webhook signature is verified against `repository.owner.login`, but stack/repository resolution trusts the unrelated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, computed from `params.dig('repository','owner','login')` (fallback `organization.login`). [1](#0-0) 
Once verified, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the entire raw JSON body to the handler, unfiltered and re-parsed by field name, not re-validated against the org that signed the request. [2](#0-1) 

Every handler that resolves which `Repository`/`Stack` to mutate keys off `payload.dig('repository','full_name')` (or `params.repository.full_name`), a field that is never checked to belong to the organization whose secret validated the signature: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
`Shipit.github(organization: X)` looks up a distinct `GithubApp`/`webhook_secret` per GitHub organization, as documented for multi-org setups. [7](#0-6) 
The equality the code is supposed to enforce is: **"the org whose secret signed this delivery" == "the repository whose stacks get written."** Instead the controller uses `repository.owner.login`/`organization.login` purely to pick which secret to verify with, while every handler independently re-reads `repository.full_name` to decide which `Repository` (and therefore which `Stack`s, `PullRequest`s, `Commit`s, `ReviewStack`s) to mutate. Nothing forces `full_name`'s owner segment to match `repository.owner.login`/`organization.login`. In a Shipit instance configured with multiple GitHub organizations (as the docs explicitly support), an attacker who legitimately controls one onboarded organization (`org-attacker`, with its own known `webhook_secret`) can craft a webhook whose `X-Hub-Signature` is computed with `org-attacker`'s secret while setting `repository.owner.login`/`organization.login` to `org-attacker` (so it verifies) but `repository.full_name` to `victim-org/victim-repo` (any repository Shipit tracks). The signature check passes, and the handler acts on the victim repository.

### Impact Explanation
Depending on the event type this reaches: `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for the victim stack's branch, and the `pull_request` handlers create/archive/unarchive review stacks and mutate `PullRequest` records for a repository the attacker does not own. This is a cross-repository write/state manipulation driven entirely by an unprivileged, self-controlled GitHub organization's credentials, meeting the "cross-repository writes" bar defined in scope.

### Likelihood Explanation
Requires only that the target Shipit instance be configured with more than one GitHub organization (a documented, supported configuration) and that the attacker owns/administers one of those organizations (enough to receive/craft webhook deliveries and read its own `webhook_secret`, which is not a privileged Shipit credential). No `ApiClient` token, `api_clients_secret`, GitHub App private key, or Shipit account is needed.

### Recommendation
In `verify_signature`, after locating `github_app`, also assert that `repository_owner` matches the owner segment of `params.dig('repository','full_name')` (and that `organization` matches when present) before dispatching to handlers; alternatively, have `Shipit::Webhooks::Handlers::Handler#repository_name` reuse the same, already-authenticated `repository_owner`/`organization` value instead of independently trusting `repository.full_name` from the unauthenticated-per-field payload.

### Proof of Concept
1. Admin configures Shipit with two orgs in `secrets.yml`: `victim-org` (secret `S_v`) and `attacker-org` (secret `S_a`), per the documented multi-org setup. [7](#0-6) 
2. Attacker owns/administers `attacker-org`'s GitHub App installation and therefore knows `S_a`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: push`, body:
```json
{"ref":"refs/heads/main","after":"<attacker-chosen-sha>","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"}}
```
signed with `X-Hub-Signature: sha1=HMAC(S_a, body)`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates successfully since the signature was made with `S_a`. [8](#0-7) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` for the victim's stack, even though the request was never signed by `victim-org`'s secret. [3](#0-2) [4](#0-3)
