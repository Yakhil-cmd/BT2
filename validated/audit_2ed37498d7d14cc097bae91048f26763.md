## Title
Delayed `GlobalContractDistribution` receipt can permanently error out chunk application after multiple reshardings, mirroring a "single malfunctioning adapter permanently DOS'ing processing" pattern - ([File: core/primitives/src/receipt.rs])

### Summary
The external report describes a class of bug where a loop that must successfully process every item in a fixed set (adapters) has no way to skip/quarantine a single item that fails, so one bad item blocks the whole pipeline forever. The closest reachable analog in this nearcore snapshot is `Receipt::receiver_shard_id` for `ReceiptEnum::GlobalContractDistribution`, used inside congestion-control receipt forwarding (`runtime/runtime/src/congestion_control.rs`), which returns a hard `Err` if the receipt's `target_shard` cannot be resolved to a shard in the current layout via `ShardLayout::resolve_to_current_shard`.

### Finding Description
`Receipt::receiver_shard_id` [1](#0-0)  special-cases `GlobalContractDistribution` receipts: if the receipt's `target_shard` is not part of the current shard layout, it calls `shard_layout.resolve_to_current_shard(target_shard)`. If that returns `None` (i.e., the shard cannot be resolved through the split history), the function returns `Err(EpochError::ShardingError(...))` instead of silently skipping or dropping the receipt.

This function is called from `ReceiptSinkV2::forward_from_buffer_to_shard`, using `?` to propagate the error [2](#0-1) , which in turn converts into a `RuntimeError` that bubbles up out of chunk application (`runtime/runtime/src/lib.rs`). A `GlobalContractDistribution` receipt that gets delayed (e.g., due to compute-limit saturation) is a persistent piece of state that is deterministically re-processed on every subsequent block attempt until it is fully applied — exactly analogous to the vault always retrying the same broken adapter on every rebalance. If `resolve_to_current_shard` cannot map the stale `target_shard` (e.g., after several resharding generations, or if shard-layout/split history retention is insufficient), every future attempt to apply the chunk for that shard fails with the same error, which is a chain-halting condition for that shard rather than a one-off, gracefully-skipped failure.

A regression/repro test explicitly encodes and defends against this exact scenario: it saturates compute so a `GlobalContractDistribution` receipt is pushed to the delayed queue across *two* resharding events, then asserts the chain does **not** stall when the delayed receipt is finally processed [3](#0-2) . The test comment states directly: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations."* [4](#0-3) 

This confirms the bug class is a recognized concern in this exact area of the codebase (delayed receipts + resharding + shard-id resolution), matching the report's bug class: a single "item" (receipt) whose processing depends on an external/derived mapping (shard split history) can permanently break the processing loop for everyone if that mapping ever fails to resolve, with no adapter-removal/skip mechanism equivalent to the vault's proposed "bypass failed adapter calls" fix.

### Impact Explanation
If `resolve_to_current_shard` fails to resolve a legitimately-delayed `GlobalContractDistribution` receipt's `target_shard` (e.g., due to shard-layout/split-history retention limits, or additional resharding generations beyond what history covers), the resulting `Err` propagates out of `forward_from_buffer_to_shard`/chunk application. Because the receipt remains in state (delayed/buffered) and is deterministically retried on every subsequent chunk application attempt, this becomes a permanent, self-reinforcing failure: the shard (and potentially the whole chain, since produced/validated blocks depend on successful chunk application) cannot make further progress — a chain stall analogous to the reported vault DOS, where the "malfunctioning adapter" (unresolvable target shard) blocks every future rebalance (chunk application) attempt.

### Likelihood Explanation
The current repo already contains defensive code (`resolve_to_current_shard`) and a dedicated regression test asserting no stall occurs across two resharding generations, suggesting the immediate two-generation case has been hardened. However, I was not able to fully verify from the available index (1) how many generations of shard-split history `resolve_to_current_shard`/`get_shard_layout_history` actually retain, or (2) whether history retention could ever be exceeded (e.g., via garbage collection, config changes, or more resharding events than history depth) such that `None` is returned in production. This uncertainty means I cannot conclusively confirm the vulnerability is exploitable today versus already mitigated — the test in `global_contracts_distribution.rs` is written specifically to catch a regression of this class, which indicates the developers consider it a real risk that requires ongoing testing rather than a fully closed issue.

### Recommendation
Given the residual uncertainty, it would be prudent to review `ShardLayout::resolve_to_current_shard` and `get_shard_layout_history` (`core/primitives/src/shard_layout/mod.rs`, `v3.rs`, `chain/epoch-manager/src/lib.rs`) to confirm there is a hard, provable bound on shard-split history depth relative to the maximum time a `GlobalContractDistribution` receipt can remain delayed (including through congestion-driven delays across many epochs/reshardings), and add an explicit non-panicking fallback (e.g., drop/rewrite the receipt) instead of returning `Err` up through chunk application if resolution can ever fail for a legitimately old receipt.

### Proof of Concept
No standalone PoC was constructed; the existing test `test_...` in `test-loop-tests/src/tests/global_contracts_distribution.rs` (lines 100–186) already reproduces the exact scenario (deploy global contract → saturate compute so the distribution receipt is delayed across two resharding events → drain delayed queue → assert chain does not stall), which is the concrete analog to the reported bug class.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }
