### Title
Unhandled-property NULL/undefined-property dereference in oscript `unit[...]` evaluation crashes AA-processing nodes - (File: formula/evaluation.js)

### Summary
The CVE class is a NULL-pointer dereference in a header/frame parser (`ff_vc1_parse_frame_header_adv`) that is reachable by feeding a crafted, partially-formed structure and dereferencing an optional field without a presence check, crashing the process. The closest reachable analog in ocore is in the `unit` oscript operator handler in `formula/evaluation.js`, which reads an arbitrary, attacker-chosen unit object from the DB/joint store and unconditionally iterates `objUnit.messages` without checking that the field exists.

### Finding Description
In the `case 'unit':` handler of the oscript evaluator, any AA trigger (or `bounce`/getter formula) can request an arbitrary on-chain unit by hash via `unit[HASH]`: [1](#0-0) 

After fetching the joint with `storage.readJoint`, the code does:
```
for (let m of objUnit.messages)
    if (m.app === "temp_data")
        delete m.payload.data;
``` [2](#0-1) 

`objUnit.messages` is only guaranteed to exist for *serial* units with full content. Per `validation.js`, a unit can legitimately be persisted and later served as "nonserial and stripped off content", in which case it carries only `content_hash` and a restricted whitelist of fields that explicitly excludes `messages`: [3](#0-2) 
```
if (hasFieldsExcept(objUnit, ["unit", "version", "alt", "timestamp", "authors", "witness_list_unit", "witnesses", "content_hash", "parent_units", "last_ball", "last_ball_unit"]))
    return callbacks.ifJointError("unknown fields in nonserial unit");
```
Such content-hash-only units are valid, final, "good"-sequence units that can be stored and retrieved by `storage.readJoint`. When one of these units is looked up via the `unit[...]` oscript function, `objUnit.messages` is `undefined`, and `for (let m of objUnit.messages)` throws a `TypeError: objUnit.messages is not iterable` — an uncaught exception thrown from inside an asynchronous DB callback (`storage.readJoint`'s `ifFound`), which is outside of the AA formula evaluator's own catch/`setFatalError` machinery. This is analogous to the CVE's pattern: an optional/absent field is dereferenced without a presence check while parsing a structure supplied by an untrusted, attacker-influenced source (here: a unit hash chosen by whoever composes the AA-triggering unit/formula).

### Impact Explanation
Because the throw occurs asynchronously inside a DB callback rather than synchronously inside the formula's own try/catch-guarded evaluation loop, it is not caught by the AA formula's `setFatalError`/`fatal_error` mechanism and will propagate as an uncaught exception on the Node.js process handling unit/AA validation. Any full node (validator) processing a unit that triggers an AA whose oscript/definition contains a `unit[...]` reference to a stripped nonserial unit hash will crash or throw during validation of that unit. Since unit/AA validation is part of the consensus-critical path executed by every node when it receives a new unit, a crash there can stop the affected node from confirming further units (denial of service against validators), and if only some nodes crash while others handle the exception differently, it risks node disagreement on validity of the unit that references such content. This satisfies the "network unable to confirm new units / node disagreement on validity" impact bar.

### Likelihood Explanation
Reachability requires only: (1) a unit whose content has previously been legitimately stripped to `content_hash` form and stored (a normal, expected occurrence for nonserial units), and (2) any address (including any user) posting a unit/AA trigger whose AA definition or bounce/getter formula contains `unit['<hash-of-stripped-unit>']` followed by any `.messages`-touching selector or simply relying on this code path being exercised (the vulnerable loop executes unconditionally inside `ifFound`, before any user-controlled selector is applied). No special privilege, hub/peer position, or network-level MITM is required — an ordinary AA author can compose such a formula and any user can send the triggering unit. This makes the trigger low-effort and fully reachable from the "unprivileged unit poster / AA author / AA trigger sender" surface allowed by the rules.

### Recommendation
Guard the loop with a presence/type check before iterating, e.g.:
```js
if (Array.isArray(objUnit.messages))
    for (let m of objUnit.messages)
        if (m.app === "temp_data")
            delete m.payload.data;
```
Additionally, audit all other consumers of `storage.readJoint`/cached joints in `formula/evaluation.js` and `validation.js` that assume `objUnit.messages` exists, since nonserial (`content_hash`-only) units are a documented, valid unit shape lacking that field.

### Proof of Concept
1. Identify or create (over time, naturally) a stable unit `U` that becomes nonserial and is stored/served in stripped `content_hash` form (per `validation.js:181-188`), so its stored joint has no `messages` field.
2. Author or trigger an AA whose formula (definition `init`/`messages`/`bounce_fees`, or a getter) evaluates `unit['U']` — e.g. `$u = unit['U'];` — which is a fully allowed formula per `formula/validation.js`'s `'unit'` op validation.
3. Send a unit invoking this AA (any user, no special role needed).
4. On the validating node, when the trigger is processed, `formula/evaluation.js`'s `case 'unit':` handler loads `U`'s joint via `storage.readJoint`, and executes `for (let m of objUnit.messages)` where `objUnit.messages` is `undefined`, throwing an uncaught `TypeError` inside the async DB callback and crashing/hanging the node's unit-processing pipeline.
