## Analysis

I verified the actual `Barrier` type for asset-hub-kusama and compared it against sibling configs that explicitly wrap the same filter with a recursive variant. [1](#0-0) 

Compare this to `bridge-hub-polkadot` and `bulletin-polkadot`, which wrap the identical filter in `DenyRecursively<...>`: [2](#0-1) [3](#0-2) 

`asset-hub-kusama`, `asset-hub-polkadot`, `bridge-hub-kusama`, `coretime-*`, `collectives-polkadot`, `people-*`, and `encointer` all use the **plain, non-recursive** `DenyReserveTransferToRelayChain` in their `Barrier`.

### Why this matters
`DenyReserveTransferToRelayChain` (from `xcm-builder`) inspects only the top-level instruction slice of the message passed to `ShouldExecute::should_execute`, matching `DepositReserveAsset`/`TransferReserveAsset`/`InitiateReserveWithdraw` whose `dest`/`reserve` is the Relay Chain. The XCM `Barrier` is invoked exactly once, at the start of `execute_xcm`, for the top-level program. Instructions that embed a *nested* `Xcm` program which is executed **locally on the same chain later** — `SetAppendix` and `SetErrorHandler` — are not scanned by this pattern match, and critically, when the executor later runs the appendix/error-handler queue (after the main instruction list completes or errors), it does **not** re-invoke `Barrier::should_execute`. This is precisely the gap that `DenyRecursively` was introduced to close, and its selective application (present on `bridge-hub-polkadot`/`bulletin-polkadot`, absent on `asset-hub-kusama` and most other chains) confirms both that the underlying non-recursive filter is bypassable and that the fix was not uniformly rolled out.

Note on the question's exact proof idea (`InitiateTransfer{remote_xcm: ...}` to a sibling): the `remote_xcm` payload of `InitiateTransfer` is *not* executed locally on Asset Hub — it is forwarded and executed at the destination under the destination chain's own `Barrier`. That specific vector is therefore not a bypass of Asset Hub Kusama's own filter as scoped to this file; it would depend on the destination chain's configuration, which is out of scope here. The concrete, in-scope bypass is via **`SetAppendix`/`SetErrorHandler`**, which do execute locally on Asset Hub Kusama and are demonstrably not covered by the plain filter.

### Title
DenyReserveTransferToRelayChain is not applied recursively, allowing SetAppendix/SetErrorHandler to smuggle a reserve transfer to the Relay Chain - (File: system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs)

### Summary
Asset Hub Kusama's `Barrier` wraps `DenyReserveTransferToRelayChain` directly instead of `DenyRecursively<DenyReserveTransferToRelayChain>`, unlike `bridge-hub-polkadot`/`bulletin-polkadot`. Because the deny filter only scans the top-level instruction slice and the XCM executor never re-invokes the `Barrier` when running the appendix/error-handler queues, a signed user can call `pallet_xcm::execute` with a message that embeds `DepositReserveAsset{dest: Parent}`/`TransferReserveAsset{dest: Parent}`/`InitiateReserveWithdraw{reserve: Parent}` inside a `SetAppendix` (or `SetErrorHandler`) instruction to bypass the deny check.

### Finding Description
`Barrier = TrailingSetTopicAsId<DenyThenTry<DenyReserveTransferToRelayChain, (...)>>` [4](#0-3)  is checked once, at the start of `execute_xcm`, against the outer instruction list. The filter's `should_execute` pattern-matches specific top-level `Instruction` variants targeting `Location::parent()`; it does not descend into the `Xcm` payloads nested inside `SetAppendix`/`SetErrorHandler`. Those nested programs are queued by the executor and run after the main list finishes/fails, without a second `Barrier` call. An attacker calling `pallet_xcm::execute` with `[WithdrawAsset(..), SetAppendix(Xcm(vec![DepositReserveAsset{ dest: Parent, .. }])), ClearOrigin, ..other top-level instructions with no denied pattern..]` passes the top-level scan (no denied instruction appears at top level), and the reserve-transfer-to-relay instruction still executes when the appendix runs.

### Impact Explanation
The chain-level invariant "no reserve transfer to the Relay Chain via this Barrier" is bypassed for local, signed-user-controlled XCM execution, allowing KSM (or other reserve assets) to be reserve-transferred to the Relay Chain despite the explicit deny rule, undermining the intended reserve-transfer routing/accounting assumptions this filter is meant to enforce.

### Likelihood Explanation
Fully attacker-controlled: any signed account can call `pallet_xcm::execute` with an XCM program of their own construction using only their own withdrawn assets, no privileged origin or governance action required, and it is deterministically repeatable on every execution.

### Recommendation
Wrap the filter as `DenyRecursively<DenyReserveTransferToRelayChain>` in `asset-hub-kusama`'s (and equivalently `asset-hub-polkadot`'s, `bridge-hub-kusama`'s, and other affected chains') `Barrier`, matching the pattern already used in `bridge-hub-polkadot`/`bulletin-polkadot`, so nested programs in `SetAppendix`/`SetErrorHandler` (and other embedding instructions) are also scanned.

### Proof of Concept
xcm-emulator integration test on Asset Hub Kusama:
1. Fund a test account with KSM.
2. Call `PolkadotXcm::execute` with message: `WithdrawAsset(ksm_asset) -> SetAppendix(Xcm(vec![DepositReserveAsset{ assets: All, dest: Location::parent(), xcm: Xcm(vec![]) }])) -> DepositAsset{ assets: All, beneficiary: local_account }`.
3. Assert the extrinsic succeeds (Barrier does not reject it) — proving the top-level `DenyThenTry<DenyReserveTransferToRelayChain, ...>` did not fire.
4. Assert that a reserve-transfer XCM was actually routed/sent to the Relay Chain (e.g. via `XcmpQueue`/`UMP` outbound message assertion or `Sent`/`AssetsTrapped` events), proving the denied operation executed via the appendix.
5. Contrast with a second test using the same message but with `DepositReserveAsset{dest: Parent}` placed directly at the top level (not inside `SetAppendix`) and assert it is correctly rejected — demonstrating the filter works for top-level but not nested placement.
