### Title
Webhook org used for signature verification is decoupled from the repository actually mutated, letting a payload verified under one org's `webhook_secret` (or an org with no secret configured) create a `Shipit::ReviewStack`/`Shipit::User` for a repository tracked under a different org - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb, app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb)

### Summary
`WebhooksController#verify_signature` selects the `webhook_secret` to validate against using `params.dig('repository','owner','login')` [1](#0-0) , while every `pull_request` handler resolves the actual `Shipit::Repository` to mutate using a completely independent field, `params.repository.full_name` [2](#0-1) . Because both fields are attacker-controlled JSON body content and are never cross-validated, a request whose signature is verified under org A's (or an unconfigured/blank-secret) org can still target and mutate a repository actually tracked under org B, and `Shipit::User.find_or_create_by_login!` will seed a brand-new `Shipit::User` row purely from the attacker-chosen `sender.login`/`pull_request.user.login` with no check that this identity ever authenticated against the org that validated the request.

### Finding Description
Binding claimed to hold: `repository_owner` (the org whose `webhook_secret` verified the request in `verify_signature`) must equal the owner segment of `params.repository.full_name` (the repository actually resolved and mutated by the handler), and the `login` used to create/find a `Shipit::User` must belong to an identity that has interacted with that same org.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is not configured (`return true unless webhook_secret`) [4](#0-3) ; `docs/setup.md` explicitly documents the webhook secret as "optional" per org, so a multi-org Shipit deployment can legitimately have one org with no secret set.
- `OpenedHandler#repository` (and every other pull_request handler, plus `Handler#stacks`) resolves the target `Shipit::Repository` using `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) [5](#0-4)  - `owner` here is a separate JSON path (`repository.full_name`) never compared to `repository.owner.login` used above.
- `ExplicitParameters` schemas for `OpenedHandler`/`ClosedHandler` only require `repository.full_name` and `sender.login` as strings - no schema element ties them to `repository.owner.login` or to the org resolved during signature verification [6](#0-5) .
- Given `repository.provisioning_behavior_allow_all?`, `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!` → `create!`, which creates a real `ReviewStack` and does `stack.build_pull_request.update!(github_pull_request: params.pull_request)` [7](#0-6) .
- `PullRequest#github_pull_request=` assigns `self.user = User.find_or_create_by_login!(github_pull_request.user.login)` and does the same for assignees [8](#0-7) ; separately, `ReviewStackAdapter#user` memoizes `Shipit::User.find_or_create_by_login!(params.sender["login"])` for use in `archive!`/`unarchive!` [9](#0-8) .
- `User.find_or_create_by_login!` simply calls `Shipit.github.api.user(login)` to fetch a public profile by login string and persists it — there is no check anywhere that this login belongs to a member of, or has interacted with, the org whose `webhook_secret` validated the request [10](#0-9) .

Attacker request: POST `/webhooks` with `X-Github-Event: pull_request`, a valid signature for org `attacker-org` (which either the attacker legitimately controls in a multi-org Shipit deployment, or which has no `webhook_secret` configured at all, requiring zero secret knowledge), body containing `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `sender.login = "arbitrary-chosen-login"`, `action: "opened"`, and forged `pull_request` fields (title, head.sha/ref, additions/deletions, labels). `victim-org/victim-repo` is a real Shipit-tracked repository with `provisioning_behavior_allow_all`.

Result: `verify_signature` passes (verified against `attacker-org`'s secret or lack thereof), but the handler creates a `ReviewStack` and `PullRequest` for the real `victim-org/victim-repo`, and creates `Shipit::User` rows keyed on the attacker-chosen login with data pulled by `Shipit.github.api.user(login)` — none of which was authenticated by the org (`victim-org`) that actually owns the mutated repository.

Existing guards do not close this gap: `verify_signature` never re-checks that the org it validated against matches the owner segment of `repository.full_name`; `drop_unhandled_event` and the `ExplicitParameters` schemas only validate shape/presence, not cross-field consistency; `force_github_authentication`/`User#authorized?`/`require_permission!` apply to the OAuth session/API-client path, not to webhook-created records; `Repository.from_github_repo_name` and model validations only validate the `owner`/`name` format, not that they match the org that authenticated the webhook.

### Impact Explanation
An attacker who controls (or can find) any single org configuration in the Shipit deployment with a blank/absent `webhook_secret` — a state the engine's own documentation calls "optional" — gains the ability to forge `pull_request` (and other) webhook events for **any other tracked repository in the same Shipit instance**, regardless of that other repository's own `webhook_secret`. This creates real `Shipit::ReviewStack`/`Shipit::PullRequest`/`Shipit::User` records from entirely attacker-controlled data, and (with `provisioning_behavior_allow_all`) queues the forged stack for provisioning via `ReviewStackProvisioningQueue.add(stack)`, i.e. triggers real deploy/provisioning workflows against the victim repository. This is repeatable against arbitrary repositories tracked by the same Shipit instance and matches the Critical category "a payload for one repository mutating another's stack... or an unauthorized deploy."

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (`config/secrets.yml` keyed by org, as shown in `secrets_double_github_app.yml`), and (2) at least one configured org with no `webhook_secret` set — a documented, allowed configuration, not a hardening default. Given that, the attack needs no session, no API token, and no knowledge of any real secret; it is a single unauthenticated HTTP POST, fully repeatable against any repository tracked by the instance. If every configured org has a properly set, unguessable `webhook_secret`, this specific path is not reachable (the attacker cannot pass `verify_signature` for any org, satisfying the "no webhook_secret held" constraint), so exploitability is conditional on that operational gap rather than being universally exploitable.

### Recommendation
In `WebhooksController#verify_signature`, after establishing which org's secret validated the signature, require that the org derived from `params.repository.full_name` (or `params.repository.owner.login`) matches; reject (422) the request if they differ. Additionally, make `webhook_secret` mandatory (fail closed) rather than defaulting `verify_webhook_signature` to `true` when unset, and have handlers assert `Shipit::Repository.from_github_repo_name(params.repository.full_name).owner == repository_owner` before creating any `Stack`/`PullRequest`/`User` records.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Configure two orgs, `attacker-org` (no `webhook_secret`) and `victim-org` (with a `webhook_secret` the test never uses/knows).
2. Create a real `Shipit::Repository` with `owner: "victim-org"`, `name: "victim-repo"`, `provisioning_behavior: "allow_all"`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no/invalid `X-Hub-Signature`, and a body: `{"action":"opened","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"totally-unverified-login"},"pull_request":{...forged fields...}}`.
4. Assert `Shipit.github(organization: "attacker-org").verify_webhook_signature` is what gets called (equality LHS: org validated = `"attacker-org"`), while `Shipit::Repository.from_github_repo_name(params.repository.full_name).owner` equals `"victim-org"` (equality RHS) — assert these differ.
5. Assert response is `:ok` (not `422`), `assert_difference 'Shipit::ReviewStack.count', 1` for the `victim-org/victim-repo` scope, and `assert_difference 'Shipit::User.count', 1` with the created user's `login == "totally-unverified-login"`, proving a record was written for a repository/org that never authenticated the request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
