### Title
CCMenu controller bypasses `stack_id`-scoped `ApiClient` authorization, allowing cross-repository stack read - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolution method with an unscoped `Stack.from_param!(params[:stack_id])` lookup, discarding the `current_api_client.stack_id`-based scoping that `Shipit::Api::BaseController#stacks`/`#stack` normally enforces. Combined with `require_permission!` only checking the token's `permissions` array (never its `stack_id`), a `read:stack` token issued for one stack can read the CCMenu XML (build status/deploy output) of any other stack, including one belonging to an unrelated repository.

### Finding Description
The broken binding: `current_api_client.stack_id == stack.id` is asserted implicitly by `BaseController#stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) at [1](#0-0) , but `CCMenuController` redefines `stack` to bypass that scope entirely: [2](#0-1) .

`require_permission :read, :stack` only invokes `current_api_client.check_permissions!(operation, scope)`, which checks `permissions.include?("read:stack")` and nothing about which stack the token is bound to: [3](#0-2) . `ApiClient` does have an optional `stack_id`/`belongs_to :stack` association meant to scope a token to one stack: [4](#0-3) , and this is honored generically via `stacks`/`stack` in `BaseController`, but `CCMenuController#stack` shadows that method with an unscoped lookup: [5](#0-4) .

Exploit flow: an operator issues a `read:stack` token scoped to `stack_id = A` (stack in repo X) for use with a CCMenu client. That token, because of the `CCMenuController#stack` override, can instead be used to request `GET /api/stacks/:owner/:repo/:branch/ccmenu.xml` (or the `stack_id` param equivalent) for any other stack `B` belonging to an unrelated repository Y, and will receive `200 OK` with `B`'s build status/deploy output, since `check_permissions!` never compares `A` to `B`.

The existing tests only cover permission-missing (403) and same-stack success cases; they never exercise a token scoped to a *different* stack against `CCMenuController`, so the divergence is not caught: [6](#0-5) .

### Impact Explanation
An attacker (or misconfigured integration) holding a legitimate `read:stack` `ApiClient` token scoped to their own stack can read the CI/deploy status (build label, last build status/time, web URL) of any other stack in the Shipit instance, including stacks belonging to unrelated repositories/tenants. This is an unauthenticated-for-that-resource read of stack state, matching the High severity category ("unauthenticated read of stack state, task streams or deploy output"). It is repeatable against any `stack_id`/`to_param` value the attacker can guess or enumerate, and is not limited to review stacks — it affects any stack reachable through this controller.

Note: this requires the attacker to already possess *some* valid `read:stack` `ApiClient` token (scoped to a different stack) — it is not exploitable by a fully unauthenticated internet user with no token at all, which narrows the practical blast radius relative to a pure auth-bypass finding, but still crosses a repository/tenant boundary the token was never granted.

### Likelihood Explanation
Preconditions: the attacker must possess a valid `read:stack` API token (any Shipit operator can create narrowly-scoped tokens intending them to be stack-specific via `stack_id`, and would reasonably assume that scoping is enforced everywhere `read:stack` permission is checked). No GitHub secrets, webhook secrets, or session are required — only an already-issued, narrowly-scoped API credential. Given that Shipit's own model supports (and presumably documents) per-stack token scoping via `belongs_to :stack, optional: true`, this is a realistic operational configuration, and the attack is a single unauthenticated-relative-to-target HTTP GET, fully repeatable.

### Recommendation
Remove the `CCMenuController#stack` override (or reimplement it using the inherited, scoped `stacks`/`stack` resolution from `BaseController`) so that `current_api_client.stack_id` scoping is honored, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`. Additionally, consider hardening `ApiClient#check_permissions!` (or `require_permission!`) to also validate stack identity when `stack_id` is present, so future controllers cannot silently bypass the scoping by overriding `stack`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot read an unrelated stack's ccmenu xml" do
  other_stack = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: 'main')
  @client.update!(stack_id: @stack.id, permissions: ['read:stack'])

  get :show, params: { stack_id: other_stack.to_param }

  # Binding under test: current_api_client.stack_id (== @stack.id) should equal stack.id (other_stack.id) for access to be granted.
  assert_not_equal @client.stack_id, other_stack.id
  assert_response :forbidden # currently fails: controller returns 200 with other_stack's data
end
```
This demonstrates that a token whose `stack_id` is `@stack.id` can successfully retrieve CCMenu XML for `other_stack`, whose id differs, because `CCMenuController#stack` never consults `current_api_client.stack_id`.
