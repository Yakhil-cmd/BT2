### Title
Non-deterministic selection of "latest" attestor list for `spender_attested` assets can cause node disagreement on payment validity - ([File: storage.js])

### Summary
`readAsset()`/`addAttestorsIfNecessary()` in `storage.js` picks the "current" attestor list for a `spender_attested` asset by ordering all `asset_attestors` update units for that asset by `level DESC LIMIT 1`, without any deterministic tie-breaker. Because `level` in the DAG is not a total order (sibling units can share the same level), two different `asset_attestors` update units authored by the asset definer at the same level can be resolved to "the latest list" differently on different nodes, producing disagreement about whether a given spender is attested — i.e., whether a payment in the `spender_attested` asset is valid.

### Finding Description
The attestor list of a `spender_attested` asset is not a single fixed value; it can be repeatedly replaced by the asset definer using an `asset_attestors` message [1](#0-0) , which is validated only for being single-authored and signed by the current definer [2](#0-1) . Each such unit inserts a full new attestor-list snapshot into `asset_attestors`, keyed by `(unit, message_index, attestor_address)` [3](#0-2) .

When a payment against such an asset needs to be validated, `storage.readAsset()` looks up "the latest list of attestors" with:
```
SELECT unit FROM asset_attestors CROSS JOIN units USING(unit)
WHERE asset=? ... AND sequence='good' ORDER BY level DESC LIMIT 1
``` [4](#0-3) 

This query only orders by DAG `level`. `level` is *not* a strict total order over stable, sequence-good units: two units by the same author (or different authors) can legitimately share the same `level` if neither is an ancestor of the other. Since `asset_attestors` updates do not spend any inputs, two conflicting attestor-list-update units issued by the definer at the same level will both be `sequence='good'` and both become stable (there is no double-spend conflict to make one of them non-serial). In that case, `ORDER BY level DESC LIMIT 1` with no secondary sort key (e.g., `unit`) is ambiguous: relational engines (MySQL/MyRocks/SQLite) do not guarantee a deterministic row order for ties unless an explicit tie-breaker is specified, and the physical/insertion order of otherwise-identical-level rows can differ between independently operating full nodes (they receive and persist units in different real-time order even though they ultimately agree on stability).

As a result, two honest full nodes can select two different units as "the latest attestor list" for the same asset at the same `last_ball_mci`, and thus compute two different `arrAttestorAddresses` sets in `readAsset`/`loadAssetWithListOfAttestedAuthors` [5](#0-4) . This directly feeds into payment validation:
```
if (objAsset.spender_attested){
    ...
    if (objAsset.arrAttestedAddresses.length === 0)
        return callback("none of the authors is attested");
    if (bIssue && objAsset.arrAttestedAddresses.indexOf(issuer_address) === -1)
        return callback("issuer is not attested");
}
``` [6](#0-5) 

A payment authored by an address that is attested under list A but not under list B will validate as "good" on nodes that picked list A, and as invalid on nodes that picked list B.

### Impact Explanation
This causes a concrete node disagreement on the validity of a unit — a category explicitly in scope. Full nodes can permanently diverge on whether a specific unit spending a `spender_attested` asset is valid, which is a consensus-safety violation: some nodes will treat the funds as spent (and later outputs as spendable), others will treat the spend as invalid, leading to disagreement about balances and potentially about stability of the DAG segment containing it. For an issuer relying on `spender_attested` to restrict who may hold/spend a regulated or KYC-gated asset, this can also translate into unauthorized transfer being accepted on part of the network while rejected elsewhere.

### Likelihood Explanation
Triggering the divergence requires only that the asset definer (who, by protocol, is free to update the attestor list at will) issue two `asset_attestors` update units that end up at the same DAG `level` and both become stable/serial — an entirely permitted, unprivileged-from-the-network's-perspective sequence (the definer is the payload poster the "Rules" section allows analyzing, i.e., an "AA author"/asset issuer acting through ordinary unit posting). No malicious peer, hub, or network-level manipulation is required; it can occur through ordinary, even accidental, concurrent posting from two devices/processes controlling the definer address, and a hostile definer could deliberately engineer it to selectively defraud counterparties who observe different lists.

### Recommendation
Make the "latest attestor list" selection fully deterministic across all nodes: order by `main_chain_index` (or another canonical, network-agreed sequencing field) first, and only if truly tied, break ties with a deterministic key such as the `unit` hash, i.e.:
```
ORDER BY main_chain_index DESC, unit DESC LIMIT 1
```
(or, for light clients, an equivalent deterministic ordering guaranteed the same across peers) so that every node that has processed the same set of stable units necessarily selects the same "latest" attestor list.

### Proof of Concept
1. Definer `D` creates a `spender_attested` asset with attestor list `[A]`.
2. `D`, using two devices/processes that are not coordinated, concurrently composes and broadcasts two `asset_attestors` units that both build on the same parent set (or otherwise end up at the same DAG `level`): `U1` sets attestors to `[A]`, `U2` sets attestors to `[B]`. Neither unit spends any input, so neither is marked non-serial by double-spend detection; both become stable and `sequence='good'`.
3. Address `A` is attested (has an `attestations` row) but `B` is not (or vice versa). `A` then issues/spends the asset in unit `P`.
4. On validating `P`, `storage.readAsset()` executes `... ORDER BY level DESC LIMIT 1` over `{U1, U2}`. Because `level(U1) == level(U2)`, different full nodes (which received/stored `U1`/`U2` in different real-time order) can return different rows for this query, causing some nodes to use list `[A]` (accepting `P` as valid, since `A` is attested) and others to use list `[B]` (rejecting `P`, since `A` is not attested under that list).
5. The network ends up with a persistent disagreement on whether `P` is a valid unit, violating consensus.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
