### Title
Global `Commit.where(sha:)` in `StatusHandler#process` allows cross-repository Status pollution - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone, system-wide, and calls `commit.create_status_from_github!(params)` on every match regardless of which repository the `status` webhook payload names. Since GitHub commit SHAs are content-addressed and not globally unique across unrelated repositories (e.g. forks sharing history, or independently-created commits with identical content), an attacker who controls a repository containing a commit whose SHA also exists in a `Commit` row belonging to an unrelated stack can inject a signed `status` event for their own repo and have it applied to the victim's `Commit`/`Status` records.

### Finding Description
The claimed binding — `commit.stack.repository == Repository.from_github_repo_name(payload['repository']['full_name'])` — is **not enforced** for the `status` event.

Compare the two sibling handlers:
- `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:14-16`) correctly scopes via `stacks.where(branch: ...)`, where `stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) is `Repository.from_github_repo_name(repository_name)&.stacks`, i.e. bound to `payload['repository']['full_name']`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) instead does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a bare `Commit` class-level query with no join/filter on `stack.repository`, and it never calls the `stacks` helper. Any `Commit` row anywhere in the database sharing that SHA — belonging to any stack, in any repository, owned by any tenant — receives a new `Status` row.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only authenticates that the payload was signed by the GitHub App installation for `repository_owner` (the org named in the payload); it says nothing about which specific `Commit` rows the handler is permitted to touch. Because attacker owns their own fork/org and GitHub will sign the webhook with that installation's key, `verify_signature` passes even though the resulting `Commit.where(sha:)` mutation crosses tenant boundaries. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not repository scoping.

Attack: attacker forks `victim/prod` (or independently creates a repo whose initial commits share SHAs with `victim/prod`, e.g. via a common upstream template), registers the fork as a Shipit stack under their own org, pushes to a branch to trigger a `status` webhook for a shared SHA, which GitHub signs with the attacker's own installation. `StatusHandler#process` then creates/updates `Status` rows on the `Commit` belonging to `victim/prod`'s stack as well, potentially with attacker-controlled `state`, `description`, `target_url`, `context` — capable of driving `commit.state` to `success`, unlocking continuous deployment/merge logic (`ProcessMergeRequestsJob`, `schedule_continuous_delivery`) on `victim/prod` purely from attacker-fork activity.

### Impact Explanation
This is a cross-tenant write: a payload authenticated only for attacker's own repository mutates `Status` (and downstream `Commit#state`/deploy-eligibility) records belonging to a different, unrelated repository/stack that the attacker does not control. This matches the Critical impact category "a payload for one repository mutating another's stack, commit, task or team" and can produce "an unauthorized deploy, rollback or merge" since forged `success` statuses can satisfy `required_statuses`/CD gating on the victim stack. It is repeatable at will by the attacker against any repository sharing a known/discoverable SHA (trivial via shared-history forks or template repos), and blast radius spans all Shipit tenants that happen to share commit history with attacker-controlled repos.

### Likelihood Explanation
Preconditions are cheap and entirely attacker-controlled: fork a public repo, register the fork as a Shipit stack (no special Shipit privilege needed beyond normal onboarding), push to trigger a real signed webhook. No Shipit secrets, sessions, or maintainer roles are required — GitHub itself signs the webhook for the attacker's own installation. The only constraint is finding/engineering a shared SHA, which is straightforward when forking or using a common template/bootstrap commit.

### Recommendation
Scope `StatusHandler#process` to the payload's repository, mirroring `CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) so only commits belonging to the repository named in `payload['repository']['full_name']` can be mutated.

### Proof of Concept
Minitest plan (controller or handler test, no live GitHub):
1. Create two stacks `victim_stack` (repo `victim/prod`) and `attacker_stack` (repo `attacker/evil`).
2. Create `Commit` rows with the identical `sha` value on both stacks: `victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)` and `attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)`.
3. Stub webhook signature verification as in existing tests (`GithubHook.any_instance.stubs(:verify_signature).returns(true)` / `verify_signature` bypass).
4. POST to `/webhooks` with `X-Github-Event: status` and a JSON body whose `sha` equals `shared_sha` and `repository.full_name` equals `"attacker/evil"`.
5. Assert:
   - `assert_difference -> { attacker_commit.statuses.count }, 1` (expected/legitimate write), AND
   - `assert_no_difference -> { victim_commit.statuses.count }` — this assertion currently **fails** against `Commit.where(sha:)`, proving `victim_commit` (bound to `victim/prod`, not named in the payload) incorrectly receives a `Status` row, confirming the broken binding `commit.stack.repository == payload['repository']['full_name']`.
