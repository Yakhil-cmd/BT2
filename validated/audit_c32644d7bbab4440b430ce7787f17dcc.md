### Title
Cross-organization Team hijack via `Team.find_or_create_by!(github_id:)` in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` locates a `Shipit::Team` solely by the integer `github_id` from the webhook payload, with no check that the `organization` whose GitHub App verified the request's signature matches the `organization` column already stored on that `Team` row. In a multi-organization Shipit deployment (`docs/setup.md`, "Using Multiple Github Applications"), a genuinely-signed `membership` webhook from an unrelated, attacker-controlled organization can add an arbitrary GitHub user to a pre-existing `Team` that belongs to a different organization, including teams enumerated in `Shipit.github_teams`.

### Finding Description
The broken binding is: `verifying_organization` (the org whose `webhook_secret` validated `X-Hub-Signature`, derived from attacker-controlled `params.dig('organization','login')`) **should equal** `Team.find_by(github_id: params.team.id).organization` (the org that legitimately owns that pre-existing `Team` row), but the code never checks this.

Path:
- `WebhooksController#verify_signature` resolves the signing key via `Shipit.github(organization: repository_owner)`, and for `membership` events `repository_owner` falls back to `params.dig('organization', 'login')` [1](#0-0) . This login is entirely attacker-supplied JSON, only constrained by whichever org's `webhook_secret` the attacker uses to sign the request.
- `Shipit.github(organization:)` selects the `GitHubApp`/secret purely by that org name and raises `GithubOrganizationUnknown` only if the org is not configured at all [2](#0-1) .
- Once signature verification passes for the attacker's own configured organization, `MembershipHandler#process` runs `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . The `find` half of `find_or_create_by!` matches only on `github_id`; the block (which sets `organization`) executes only on creation, never on lookup. If a `Team` row with that `github_id` already exists — from any organization — it is returned unchanged, and `team.add_member(member)` is called on it [4](#0-3) , [5](#0-4) .

Attacker request: a `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with the attacker's own legitimately-configured organization's `webhook_secret`, and a JSON body `{"action":"added","team":{"id":1,...},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"}}`, where `1` is the `github_id` of a pre-existing `Team` (e.g. seeded from `Shipit.github_teams`) belonging to an unrelated organization.

Existing guards fail to close the gap: `verify_signature` only proves the request was legitimately signed by *some* configured org, not that it's authorized to mutate *this* team; `drop_unhandled_event` and the `ExplicitParameters` schema on `MembershipHandler` only validate shape/types of `team.id`, `organization.login`, `member.login`, not cross-referencing against the `Team#organization` column [6](#0-5) ; there is no `require_permission!`/`authorized?` check performed inside the webhook processing pipeline.

### Impact Explanation
A successful request appends an attacker-controlled GitHub login as a `member` of a `Team` record it did not authenticate for, via `Shipit::Membership` creation. If that `Team` is one enumerated by `Shipit.github_teams` (used in `User#authorized?` at [7](#0-6) ), the attacker's GitHub identity becomes an authorized Shipit user, escalating into `Shipit.github_teams` authorization — matching the High severity category defined in the rules. The attack is repeatable for any `github_id` that collides with a pre-existing `Team` row, and blast radius spans any tenant/organization sharing this Shipit instance whose team ids are guessable/low integers.

### Likelihood Explanation
Requires: (1) Shipit configured with multiple GitHub Apps/organizations (a documented, supported deployment mode), (2) attacker controls one of those configured organizations and therefore possesses a valid `webhook_secret` for it, and (3) a target `Team` row pre-exists with a `github_id` the attacker can guess (feasible since GitHub team ids are small sequential integers for early teams). Given those preconditions — which the question states as given — the exploit is a single crafted, correctly-signed HTTP POST with no other privilege required, and is deterministically repeatable.

### Recommendation
Scope the `Team` lookup in `MembershipHandler#find_or_create_team!` to the verified organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally validate in `WebhooksController#verify_signature` (or in the handler) that the organization implied by the signing GitHub App matches `params.organization.login` before dispatching to handlers, so cross-organization payloads cannot mutate another organization's `Team`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual)
test "membership webhook from unrelated org cannot mutate another org's team" do
  victim_team = shipit_teams(:shopify_developers) # github_id: e.g. 1, organization: "shopify"

  # Attacker-owned org "evilcorp" has its own valid webhook config/secret in secrets.github
  request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'http://x' },
    organization: { login: 'evilcorp' },
    member: { login: 'attacker' }
  }.to_json

  Shipit.github(organization: 'evilcorp').stubs(:verify_webhook_signature).returns(true) # simulate genuinely-signed request

  assert_no_difference -> { Team.count } do
    assert_difference -> { victim_team.memberships.count }, 1 do
      post :create, body: payload, as: :json
    end
  end

  # Broken binding demonstrated:
  assert_equal 'shopify', victim_team.organization # side A: team's real org
  # side B: org that actually authenticated this write was 'evilcorp' — never checked
  assert victim_team.members.exists?(login: 'attacker')
end
```
This asserts that `Membership` creation succeeds against `shopify`'s team despite the signature having been verified against `evilcorp`'s webhook secret, confirming `github_id` equality alone authorized the write.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
