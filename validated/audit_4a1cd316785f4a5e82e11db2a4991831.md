## Analysis Result

I mapped the reported bug class (**a verified authorization boundary that omits one code path acting on the same resource**) to the strongest reachable analog in this engine: **an `ApiClient` scoped to a single stack can read the CI/deploy status of any other stack**, because `Api::CCMenuController` resolves `stack` independently of the scoping logic that every other API controller relies on.

### Title
Stack-scoped `ApiClient` token can read any stack's build/deploy status via CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a specific `stack_id`) can only ever resolve `stack`/`stacks` to the stack it was scoped to [1](#0-0) . `Api::CCMenuController` overrides `stack` to bypass this scoping entirely, resolving directly from the global `Stack` table using the client-supplied `params[:stack_id]` [2](#0-1) .

### Finding Description
The binding that should hold is: `requested_stack.id == current_api_client.stack_id` (when the client is scoped). `BaseController#stacks` enforces this by scoping the `Stack` relation to `current_api_client.stack_id` before looking up the requested id [1](#0-0) . `CCMenuController`, however, only checks the coarse permission bit (`read:stack`) via `require_permission :read, :stack` [3](#0-2)  and then independently resolves `stack` with `Stack.from_param!(params[:stack_id])`, never consulting `current_api_client.stack_id` [4](#0-3) . `ApiClient#check_permissions!` only validates that the permission string is present in the client's permission list; it has no notion of which stack is being touched [5](#0-4) .

Before the request: `client.stack_id == stack_shipit.id`, and the client is only ever expected to touch `stack_shipit`.
After a request to `Api::CCMenuController#show` with `params[:stack_id]` set to any other stack: the equality is broken — `stack` resolves to the arbitrary stack, while `current_api_client.stack_id` is silently ignored, and the response renders that other stack's latest deploy/rollback status [6](#0-5) .

Root cause: `CCMenuController` re-implements resource resolution instead of reusing `BaseController#stacks`/`#stack`, dropping the scope enforcement that `Api::StacksController` and other API controllers rely on (confirmed correctly working in `test/controllers/api/stacks_controller_test.rb`, e.g. "an api client scoped to a stack will only see that one stack") [7](#0-6) .

### Impact Explanation
A deliberately narrowly-scoped `ApiClient` (created by an administrator specifically to expose only one stack's CI status to a third party/CCMenu widget, per the `stack_id` scoping feature documented via the `Stack` association [8](#0-7) ) can be used to enumerate and read deploy/rollback status of every other stack in the Shipit instance — an unauthorized read of stack state and deploy output beyond the token's granted scope.

### Likelihood Explanation
Exploitation only requires possession of any valid, single-stack-scoped `read:stack` token and iterating `stack_id` values in the URL; no additional secrets, git access, or elevated privileges are needed once such a scoped token exists.

### Recommendation
Change `Api::CCMenuController#stack` to reuse `stacks.from_param!(params[:stack_id])` (as `BaseController#stack` does) instead of querying `Stack.from_param!` directly, so a client's `stack_id` scope is always enforced.

### Proof of Concept
1. Admin creates an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (intended to give a CI dashboard read-only access to Stack A only).
2. Using that client's Basic-Auth token (or `?token=` param, since `CCMenuController#authenticate_api_client` also accepts a raw `params[:token]` [9](#0-8) ), request `GET /api/stacks/:stack_b_id/ccmenu.xml` where `stack_b_id` refers to Stack B (a different, unrelated stack).
3. The response renders Stack B's latest deploy/rollback status via `shipit/ccmenu/project`, despite the token being scoped only to Stack A.
