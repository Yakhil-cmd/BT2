### Title
Stack-scoped API tokens can read any stack's CI status via `CCMenuController` bypassing stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes every stack lookup through the `stacks` collection, which is restricted to the `ApiClient`'s authorized stack when one is set. `Shipit::Api::CCMenuController` overrides the `stack` accessor with its own implementation that queries `Stack.from_param!` directly, ignoring the token's stack scope entirely, so any client holding a `read:stack`-permission token can fetch the CI status of every stack, not just the one it was authorized for.

### Finding Description
`BaseController#stacks` and `#stack` implement the trust binding "a token authorizes access to a specific stack": [1](#0-0) 

`current_api_client.stack_id?` gates the query to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a stack (`ApiClient belongs_to :stack, optional: true`): [2](#0-1) 

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely and query `Stack.from_param!(params[:stack_id])` directly against the unrestricted `Stack` relation, using only the coarse `require_permission :read, :stack` check (which only verifies the string `"read:stack"` is present in `permissions`, independent of `stack_id`): [3](#0-2) 

This is the same class of bug reported in the external report (redundant/inconsistent reimplementation of a base feature): a subclass reimplements the "current stack" resolution instead of reusing the parent's authorization-aware `stack` accessor, silently dropping the authorization check that binds an `ApiClient`'s token to a single stack.

The equality that should hold is: *stack(s) the token is authorized for == stack(s) the endpoint acts on*. Before the request: an `ApiClient` created via `CCMenuUrlController#client` (or any admin-issued stack-scoped `ApiClient`) has `stack_id = A` and permission `read:stack`. After hitting `GET /api/stacks/:stack_id/ccmenu?token=...` with `stack_id = B` (any other stack), the request succeeds because `CCMenuController#stack` never checks that `B` is in the client's authorized `stacks` collection — only that `"read:stack"` is present in `permissions`.

### Impact Explanation
Any holder of a `read:stack`-scoped API token — including a low-privilege token a user can self-issue for a single stack through `CCMenuUrlController#fetch` — can enumerate and read CI/deploy status (`Stack#deploys_and_rollbacks`, build name/status/label) for every stack in the Shipit instance, not just the one the token was issued for. This is an unauthenticated (token-only, no Shipit session) cross-stack read of stack state/deploy output, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High. `CCMenuUrlController#fetch` lets any authenticated Shipit user mint a `read:stack` token for one stack via the UI/route without any special privilege: [4](#0-3) 

The attacker then simply substitutes a different `stack_id` in the CCMenu API URL — no signature, secret, or additional permission is needed, since `CCMenuController#stack` performs no scoping check at all.

### Recommendation
Remove the custom `stack` method in `Shipit::Api::CCMenuController` and rely on the inherited, scope-aware `BaseController#stack` (i.e., `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient` tokens cannot be used to query stacks outside their authorized scope.

### Proof of Concept
1. As a logged-in user with access to Stack A, call `GET /stacks/:A/ccmenu_url` (`CCMenuUrlController#fetch`) to obtain `{"ccmenu_url": ".../api/stacks/A/ccmenu?token=<TOKEN>"}`. `<TOKEN>` corresponds to an `ApiClient` with `permissions: ["read:stack"]`.
2. Send `GET /api/stacks/B/ccmenu?token=<TOKEN>` for an arbitrary other stack `B` that the client was never scoped to.
3. Because `Shipit::Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the request succeeds and returns Stack B's build name/status/label — demonstrating the token's stack scope was never enforced.
