### Title
Cross-organization commit-status forgery bypasses CI gating — repository/stack written is not bound to the GitHub organization whose signature was verified (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a payload against using an **unauthenticated** field taken from the same JSON body (`repository.owner.login` / `organization.login`), and `StatusHandler#process` then writes a `Status` for **any** commit in the entire Shipit instance matched purely by `sha`, with no check that the commit's repository belongs to the organization whose secret validated the request. Any customer organization onboarded to a shared Shipit instance can therefore forge CI/commit-status events for another organization's stacks.

### Finding Description
`WebhooksController#verify_signature` picks the `github_app` (and thus the HMAC secret) to verify against using `repository_owner`, which is derived directly from the untrusted request body: [1](#0-0) [2](#0-1) 

Because Shipit supports multiple independently-configured GitHub organizations, each with its own `webhook_secret`/app credentials, an attacker who legitimately administers **one** onboarded organization ("Org A") knows a valid secret for Org A. They can craft a `status` webhook payload where `repository.owner.login` is set to `"Org A"` (so `verify_signature` selects Org A's secret and the HMAC check passes) while the actual `sha` field references a commit belonging to a completely unrelated stack/repository owned by a different organization ("Org B") on the same Shipit instance.

`StatusHandler#process` then resolves the target purely by commit SHA, globally, with **no repository/stack scoping at all**: [3](#0-2) 

This is unlike other handlers (e.g. `PushHandler`, `Handler#stacks`) which scope work to `Repository.from_github_repo_name(repository_name)`: [4](#0-3) 
`StatusHandler` never uses this scoping, so `Commit.where(sha: params.sha)` can match commits belonging to any stack in the entire installation, including ones from Org B that Org A has no relationship to.

`commit.create_status_from_github!(params)` persists attacker-controlled `state`, `context`, `description`, `target_url` as a `Status` record, which directly feeds CI-gating logic: [5](#0-4) [6](#0-5) 
A forged `state: "success"` for a `context` matching a stack's `required_statuses` will satisfy `Status#required?`/CI gating, and `enable_ci_on_stack`/`schedule_continuous_delivery` can then unblock continuous deployment or merge-queue merges for that unrelated stack.

**Binding broken (equality that should hold but doesn't):**
`organization whose secret authenticated the request` == `organization owning the repository/commit that is written`.
Before the attack, `verify_signature` establishes trust only in "this body was sent by someone holding Org A's secret." After the attack, the body's `sha` writes state for a commit in Org B's stack — a repository never authenticated by Org A's secret.

### Impact Explanation
This allows an unprivileged (relative to the victim organization) but Shipit-onboarded attacker to write arbitrary, unauthenticated CI/commit-status data (`success`/`failure`, context, description, URL) into another organization's stack that they have no access or relationship to. Because required CI statuses gate continuous deployment (`Status#required?`, `commit.schedule_continuous_delivery`) and merge-queue merges (`MergeRequest#reject_unless_mergeable!`, which checks `all_status_checks_passed?`), this can be used to trigger or unblock an **unauthorized deploy** or an **unauthorized merge** on a victim's stack — a cross-organization write that meets the "Critical: unauthorized deploy, rollback or merge / cross-repository writes" bar.

### Likelihood Explanation
Requires only that the attacker control (or have legitimate access to) any one GitHub organization already onboarded to the shared Shipit instance with a known webhook secret — no access to the victim organization, no `ApiClient` token, and no privileged Shipit account is needed. The victim commit `sha` is public information (visible on GitHub or in a public Shipit stack page), so constructing the forged payload requires no insider knowledge of Org B.

### Recommendation
- In `WebhooksController#verify_signature`, after successfully verifying the signature for the resolved organization, re-derive the target repository (`repository.full_name`) and assert it actually belongs to that same verified organization before dispatching to handlers.
- In `StatusHandler#process` (and any other handler that resolves records solely by `sha`/global identifiers), scope the lookup to the repository identified in `payload['repository']['full_name']`, consistent with `Handler#stacks`/`Handler#repository_name`, rather than querying `Commit` unscoped by stack/repository.

### Proof of Concept
1. Attacker legitimately controls GitHub org `attacker-org`, which is a customer organization onboarded to the shared Shipit instance with its own `github.attacker-org.webhook_secret` (per the documented multi-org configuration).
2. Attacker identifies a public commit `sha` belonging to `victim-org/victim-repo`, a stack on the same Shipit instance whose `shipit.yml` requires CI context `ci/circleci` for deploy/merge.
3. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"},
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/circleci",
  "description": "forged",
  "target_url": "https://evil.example"
}
```
4. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly.
5. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: "attacker-org")`, verifies successfully, and dispatches to `StatusHandler`.
6. `StatusHandler#process` executes `Commit.where(sha: "<victim commit sha>")`, finds the victim's commit (regardless of its stack/organization), and calls `create_status_from_github!`, creating a `success` `Status` for `ci/circleci` on `victim-org/victim-repo`'s commit — satisfying that stack's required CI check without any interaction from `victim-org`.
