Based on my research, this is the strongest analog I could substantiate: a mismatch between the GitHub organization whose secret authenticates the webhook signature and the repository that is actually written to by the event handler, in Shipit's multi-tenant GitHub App configuration.

### Title
Webhook signature verification is bound to `repository.owner.login`, while event handlers act on `repository.full_name` from the same attacker-controlled payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization deployments, `Shipit.github(organization: repository_owner)` selects which organization's `webhook_secret` is used to verify the inbound webhook's HMAC signature, using `repository.owner.login` from the JSON body. The handlers that actually process the event (e.g., `Handlers::PushHandler`, `Handlers::StatusHandler`) look up the target `Repository`/`Stack` using `repository.full_name` from the very same JSON body. Because the attacker fully controls the raw JSON payload they sign, they can set these two fields to different organizations/repositories.

### Finding Description
`WebhooksController#verify_signature` derives the verifying organization purely from payload content: [1](#0-0) [2](#0-1) 

That organization name is used to select the app config (and therefore the `webhook_secret` used for HMAC verification) via `Shipit.github`: [3](#0-2) 

The signature itself is verified with plain HMAC-SHA1 over the raw body using that organization's secret: [4](#0-3) 

Once verification passes, `create` dispatches the entire parsed payload to registered handlers for the event type: [5](#0-4) [6](#0-5) 

Handlers such as `PushHandler`/`StatusHandler` resolve the target `Repository` (and therefore the `Stack` to update) using `repository.full_name`, not `repository.owner.login`: [7](#0-6) 

The binding that should hold is: `organization authenticated by webhook_secret == organization that owns the repository being written to`. Because both values originate from the same attacker-supplied JSON body, and the signature is a keyed HMAC over that whole body computed by whoever holds the corresponding `webhook_secret`, any tenant organization holding a legitimately configured GitHub App on this Shipit instance can compute a valid signature for a payload whose `repository.owner.login` matches their own org (so verification picks their known secret) while `repository.full_name` names an entirely different organization's repository. `verify_signature` never checks that `repository.owner.login` and the owner embedded in `repository.full_name` agree.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding. A tenant who legitimately controls one GitHub organization's webhook secret in a multi-org Shipit deployment can forge `push`/`status`/`check_suite` events that get accepted as authentic and then dispatched against a *different* organization's stacks (e.g., triggering `GithubSyncJob`, updating commit statuses, or affecting merge-queue state for a repository/stack they do not own). That is a cross-tenant/cross-repository write performed without the target organization's consent, matching the Critical impact category "cross-repository writes."

### Likelihood Explanation
Exploitation requires the attacker to control (or have configured) at least one legitimately registered GitHub organization/app on the same multi-tenant Shipit instance — i.e., they must already be a trusted tenant, not an anonymous attacker with no relationship to the deployment. This is a real but narrower attacker model than a fully unauthenticated outsider; it is only reachable when the deployment uses the per-organization `github:` secrets schema (`TOP_LEVEL_GH_KEYS` absent at the top level, see `Shipit.github_app_config`) with more than one tenant organization configured.

### Recommendation
After `verify_signature` succeeds, cross-check that the organization used to select the webhook secret (`repository_owner`) matches the owner segment actually embedded in `repository.full_name` (and any `organization.login` field) before dispatching to handlers; reject the request if they diverge.

### Proof of Concept
1. Deploy Shipit with the multi-org `github:` secrets schema, with `OrgA` and `OrgB` both installed (`Shipit.github_organizations` returns both).
2. As the administrator/owner of `OrgA`, obtain `OrgA`'s `webhook_secret` (legitimately, since they installed the app for their own org).
3. Craft a `push` event JSON body with `repository.owner.login = "OrgA"` (so `WebhooksController#repository_owner` resolves to `OrgA`, and `Shipit.github(organization: "OrgA")` is used for verification) but `repository.full_name = "OrgB/victim-repo"`.
4. Compute `X-Hub-Signature: sha1=...` over that exact raw body using `OrgA`'s known `webhook_secret`, per `GitHubApp#verify_webhook_signature`.
5. POST to `/webhooks`; `verify_signature` passes because it only checks the signature against `OrgA`'s secret. `PushHandler` then resolves and acts on the `OrgB/victim-repo` repository via `Repository.from_github_repo_name`, even though the request was never signed by `OrgB`. [8](#0-7)

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
