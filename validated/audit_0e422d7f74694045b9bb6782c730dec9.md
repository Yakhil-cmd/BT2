Based on my investigation, this is a genuine binding-break analog to the reported bug class ("field acted on vs. field verified"): the webhook signature verification key is selected using `repository.owner.login`, but the actual repository the payload writes to is resolved from `repository.full_name` — and nothing ties the two together to the same trusted app config.

### Title
GitHub webhook signature verified against `repository.owner.login`-selected app while write target is resolved from unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), while the actual repository whose stacks get mutated is looked up later, independently, via `payload.dig('repository', 'full_name')` in `Handler#repository_name`. These are two different fields read from the same attacker-controlled JSON body, and neither is cross-checked against the other after signature verification.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, per [2](#0-1) .

The HMAC (`OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message)`) is computed over the **entire raw body** (`message = request.raw_post`) using the secret belonging to whichever org name is in `repository.owner.login`, per [3](#0-2) . That part is sound in isolation — the whole payload is covered by the signature, so an attacker without a valid `webhook_secret` for `repository.owner.login` cannot forge a signature that will pass.

However, this only holds in a **multi-organization deployment** (documented and supported, see `docs/setup.md` "Using Multiple Github Applications", and `Shipit.github(organization:)` lookup) where the operator has configured more than one GitHub App, each with its own `webhook_secret`. In that configuration, the binding the engine relies on is:

`organization whose secret validated the signature == organization owning the repository whose Stacks get mutated`

But the actual repository target used to mutate state is resolved completely independently downstream, in `Handler#repository_name`/`#stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Nothing enforces that `repository.full_name`'s owner segment matches the `repository.owner.login` that was used to select the verifying app/secret. Since a legitimate webhook delivery from GitHub for organization A's installation will always have consistent `repository.owner.login` and `repository.full_name`, this is not exploitable purely by a third party crafting an arbitrary body (they still need org A's valid `webhook_secret` to pass `verify_webhook_signature`). But it means: **anyone holding a valid webhook secret for one configured GitHub App/organization can forge a signed payload whose `repository.full_name` points at a repository/stack belonging to a *different* configured organization**, and have it processed as authentic by handlers such as `PushHandler` (which queues `GithubSyncJob`/`stack.sync_github` against whatever `Stack` matches `full_name`, see [5](#0-4) ) or `MembershipHandler` (which mutates `Team`/`User` membership using `organization.login` taken from the same unverified-relative-to-owner payload, see [6](#0-5) ).

This breaks the intended equality: `organization authenticated (secret used to verify signature) == repository/organization actually written to`.

### Impact Explanation
This requires possession of a valid `webhook_secret` for *some* configured GitHub App in the instance's `secrets.yml` — that is a real credential boundary, not "no attacker capability." Given the "unprivileged-attacker" framing in the rules (no Shipit session/API token/GitHub App private key/etc. required), and that a compromised or leaked `webhook_secret` for one tenant/org should not grant the ability to trigger syncs, membership changes, or deploy-affecting jobs against a *different* organization's repositories, this crosses from "High" (unauthenticated write across the trust boundary of one org into another) toward cross-tenant writes. In a single-organization deployment (the common case) this collapses to a non-issue since there is only one `webhook_secret` and `repository_owner` always matches; the exposure is specific to the documented multi-org configuration.

### Likelihood Explanation
Likelihood is Medium: it requires (a) the operator to run Shipit with multiple GitHub Apps configured (a supported but non-default setup), and (b) the attacker to already hold a valid `webhook_secret` for at least one of those orgs (e.g., a leaked secret for a lower-trust org). Given both, forging a `repository.full_name` pointing at a higher-trust org's repository is a simple JSON body edit — no cryptographic bypass needed since the attacker's own valid secret produces a correct signature over their crafted body.

### Recommendation
After `verify_signature` succeeds, assert that the organization implied by the payload's `repository.full_name` (or `organization.login` for org-level events) matches the `repository_owner` whose secret was used to verify the signature, before invoking any handler. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` and `orgB`, each with distinct `webhook_secret`s, per the multi-app format in `docs/setup.md`.
2. As an attacker who has obtained `orgA`'s `webhook_secret` (but not `orgB`'s), craft a `push` event JSON body with `repository.owner.login = "orgA"` and `repository.full_name = "orgB/some-repo"`.
3. Compute `X-Hub-Signature` using `orgA`'s `webhook_secret` over the raw body.
4. POST to `/webhooks`. `verify_signature` selects `Shipit.github(organization: "orgA")` and successfully verifies the signature ( [7](#0-6) ).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/some-repo")` ( [4](#0-3) ) and enqueues `GithubSyncJob` for `orgB`'s stack — an action that should have required `orgB`'s own webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
