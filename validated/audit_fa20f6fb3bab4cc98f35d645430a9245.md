### Title
Webhook signature is verified against the organization named in an unauthenticated payload field, while downstream handlers act on a different, uncross-checked repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the `X-Hub-Signature` against using `repository_owner`, a value read straight out of the still-unauthenticated JSON body. Once verification succeeds, the `create` action dispatches the raw, parsed body to event handlers that resolve the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`, without ever re-checking that this repository belongs to the organization whose secret was used to authenticate the request. This breaks the intended binding "organization whose webhook_secret authenticated the request == repository the handlers act on."

### Finding Description
`verify_signature` computes the verifying organization before trust in the payload is established: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — fields fully controlled by whoever sends the POST, since HMAC verification has not happened yet at the time this value is read. `Shipit.github(organization: repository_owner)` looks up a per-organization config entry (each org can have its own distinct `webhook_secret`, `private_key`, etc.): [3](#0-2) 

After `verify_signature` passes, `create` parses the body again and dispatches to handlers using the *entire* raw payload: [4](#0-3) 

The base `Handler` and concrete handlers (e.g. `PushHandler`, pull-request handlers) resolve the target repository from `payload.dig('repository', 'full_name')`, a field that is never compared to the `repository.owner.login` value used to select the signing organization: [5](#0-4) [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` splits `owner/name` straight out of that `full_name` field and looks up the local `Repository`/`Stack` records with no relation back to `repository_owner`: [8](#0-7) 

So the equality the engine relies on is: `organization used to select webhook_secret (repository.owner.login) == organization that owns the repository the handler mutates (repository.full_name)`. Nothing enforces this. An attacker who legitimately controls (or is an authorized admin of) one org configured in Shipit's multi-org `github:` block — and therefore knows/controls that org's `webhook_secret` — can send a payload whose `repository.owner.login`/`organization.login` names *their own* org (so signature verification succeeds using their known secret) while `repository.full_name` names an entirely different, victim organization's repository tracked by the same Shipit instance (see multi-org config shape): [9](#0-8) 

### Impact Explanation
This lets an authenticated-but-wrong-tenant sender forge webhook-driven state transitions (deploys via `GithubSyncJob`, pull-request/review-stack provisioning, commit `status` updates, `check_suite` refresh, team `membership` changes) for a repository outside the organization whose secret they used, i.e. a cross-repository/cross-tenant write driven by a forged event. This is only exploitable in the specific case where the Shipit instance is configured with multiple GitHub organizations each defining an independent `webhook_secret` (the documented multi-org config schema); a single-org deployment collapses `repository_owner` and the only configured secret, eliminating the mismatch. Given the tools/context available, I could not execute end-to-end against a live multi-org deployment to confirm exploitation beyond static code-path analysis — this should be validated with an actual multi-org test fixture.

### Likelihood Explanation
Requires: (1) the operator to run Shipit with the multi-organization `github:` config (each org with its own webhook_secret), and (2) the attacker to already be a legitimate admin/holder of the webhook_secret for at least one configured org. This is a real but narrow scenario — it is not exploitable by a fully unprivileged outsider with no relationship to any configured organization, since some org's secret must be known.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after choosing `github_app` by `repository_owner`, re-validate that every repository referenced inside the payload (via `full_name`, and any embedded `organization.login`) actually belongs to that same `repository_owner` before invoking handlers; reject the request otherwise.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` (attacker-controlled, webhook_secret `SECRET_A` known to attacker) and `org-b` (victim, tracked in Shipit, e.g. `org-b/prod-repo`).
2. Attacker crafts a JSON push payload: `{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/prod-repo"}, "ref": "refs/heads/master", "after": "<sha>"}`.
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(SECRET_A, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'org-a')`, verifies successfully against `SECRET_A`.
5. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name('org-b/prod-repo')` and triggers `GithubSyncJob`/deploy sync for the victim org's stack, despite the signature having only proven authorship by `org-a`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
