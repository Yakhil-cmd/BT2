### Title
Webhook signature verification bypass when `webhook_secret` is unset for an organization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank/nil, meaning any organization configured in `Shipit.secrets.github` without a `webhook_secret` entry accepts unsigned/forged webhook payloads. `WebhooksController#verify_signature` relies solely on this method's boolean result to gate processing, so a forged payload flows straight into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.

### Finding Description
The broken binding: `verify_webhook_signature(signature, message) == true` should imply `HMAC-SHA1(webhook_secret, message) == signature`, but when `webhook_secret` is nil, `true` is returned with signature and message never compared at all — the equality `verified == (signature is authentic)` fails to hold.

Code path:
1. `GitHubApp#initialize` sets `@webhook_secret = @config[:webhook_secret].presence` — if the org's config in `Shipit.secrets.github` omits `webhook_secret` (or it's blank), `@webhook_secret` is `nil`. [1](#0-0) 
2. `verify_webhook_signature` starts with `return true unless webhook_secret`, short-circuiting before any HMAC/`SecureCompare` check. [2](#0-1) 
3. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` using the attacker-supplied `repository.owner.login` from the JSON body, then calls `verify_webhook_signature` and only `head(422)` if it returns falsey. [3](#0-2) 
4. `repository_owner` is read straight from unauthenticated JSON body content: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [4](#0-3) 
5. `#create` then parses the raw body and dispatches to real handlers (e.g. `PushHandler`, `CheckSuiteHandler`) with zero further authentication. [5](#0-4) 

Exploit: an internet attacker sends `POST /webhooks` with `X-Github-Event: push` (or `pull_request`, `check_suite`, etc.) and a body whose `repository.owner.login` names a real organization configured in Shipit but whose `webhook_secret` was left unset in the deployment's credentials/secrets. No `X-Hub-Signature` header, or an arbitrary one, is required. `verify_webhook_signature` returns `true` unconditionally, and the handler processes the forged payload against that org's real stack.

No other guard intercepts this: `drop_unhandled_event` only filters by event type, not authenticity; `check_if_ping` only handles the ping event; there is no `ExplicitParameters` schema or additional signature check downstream in the handlers themselves.

### Impact Explanation
Any org whose `webhook_secret` is nil/unset in `Shipit.secrets.github` config becomes fully open to forged webhooks. An attacker can drive real handlers (`PushHandler`, `CheckSuiteHandler`, `OpenedHandler`, etc.) against that organization's genuine stacks — e.g., trigger `Stack#sync_github`, spoof check-run/CI statuses used for merge/deploy gating, or otherwise manipulate stack state — with zero proof of GitHub origin. This is repeatable indefinitely and applies to every stack under that misconfigured organization, matching "authentication bypass (forged webhook ... accepted)" and potentially "an unauthorized deploy, rollback or merge" if webhook-driven state feeds those decisions.

### Likelihood Explanation
This requires the specific operator misconfiguration of omitting `webhook_secret` for one organization entry while other orgs may be properly configured (multi-org secrets schema, `github_app_config`/`TOP_LEVEL_GH_KEYS`). Given that precondition, exploitation cost is trivial: a single unauthenticated HTTP POST with a crafted JSON body, no secrets, tokens, or GitHub session needed. It is entirely plausible for an operator to configure multiple `Shipit.github_teams` orgs and forget/omit `webhook_secret` for one, since the code silently accepts this as "no verification needed" rather than failing closed.

### Recommendation
Fail closed instead of open: if `webhook_secret` is blank for a configured organization, `verify_webhook_signature` should return `false` (or the app should refuse to boot/serve webhooks for that org) rather than bypassing verification. Only single-tenant/legacy deployments with no `webhook_secret` configured anywhere should be allowed unsigned webhooks, and that should be an explicit, documented opt-in rather than an implicit per-org fallback keyed off blank config.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
