### Title
Cross-stack read via `Api::CCMenuController` bypassing ApiClient stack scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` re-implements stack resolution instead of using the scope-aware helper defined in `BaseController`, so a `read:stack` `ApiClient` token that is scoped to one stack can be used to read the CI/build status of any other stack.

### Finding Description
`Shipit::Api::BaseController#stack` resolves the target stack through the scope-restricted `stacks` helper: `@stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` and `@stack ||= stacks.from_param!(params[:stack_id])`. [1](#0-0) 

Every other API resource controller (`StacksController`, `DeploysController`, `TasksController`, etc.) inherits this `stack` method unmodified, so an `ApiClient` scoped to `stack_id: X` can never load a stack it wasn't authorized for — the permission check (`check_permissions!`) only validates the operation/scope string, and the actual stack-object boundary is enforced solely by this `stacks` filter. [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass that scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

It still declares `require_permission :read, :stack`, which only checks that the token has the generic `read:stack` permission string, not that the token is authorized for the specific stack being requested. [4](#0-3) 

The fixture data shows this stack-scoped-token pattern is a real, supported configuration (`ApiClient` can `belongs_to :stack, optional: true`, and `here_come_the_walrus` is created with `stack: shipit`): [5](#0-4) [6](#0-5) 

The route confirms the endpoint takes an arbitrary `stack_id` path segment independent of the authenticated token's own scope: `get '/ccmenu' => 'ccmenu#show', as: :ccmenu` under `scope '/stacks/*stack_id'`. [7](#0-6) 

**Binding broken:** `current_api_client.stack_id (the stack a token authorises) == stack_id param (the stack it touches)` — holds for every other controller via `BaseController#stacks`, but is broken in `CCMenuController`, which resolves any `stack_id` unconditionally via `Stack.from_param!`.

### Impact Explanation
Any holder of a valid, stack-scoped `read:stack` API token (e.g. the "CCMenu Client" tokens minted per-user by `CCMenuUrlController`, or any stack-scoped token created via the `api_clients` UI/API) can enumerate and read the CI/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`, lock status) of every other stack in the Shipit instance, not just the stack it was authorized for. This is an unauthorized read of stack state across the intended authorization boundary, matching the "High — unauthenticated/out-of-scope read of stack state" impact class.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack` token scoped to a single stack — a low-privilege, commonly-issued credential (e.g. shared for CI dashboard aggregators via `CCMenuUrlController#fetch`). No repository write access, GitHub credentials, or session is required; the attacker simply changes the `stack_id` path segment of the `/api/stacks/:stack_id/ccmenu` request.

### Recommendation
Remove the `stack` override in `app/controllers/shipit/api/ccmenu_controller.rb` and rely on the inherited, scope-aware `BaseController#stack` (i.e., resolve via `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot resolve stacks outside their `stack_id` scope.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to Stack A with permission `read:stack` (as `here_come_the_walrus` fixture demonstrates is a supported configuration: `belongs_to :stack, optional: true`).
2. Authenticate to `GET /api/stacks/<Stack-A-owner>/<Stack-A-repo>/<Stack-A-env>/ccmenu` — succeeds as expected.
3. Using the same token, request `GET /api/stacks/<Stack-B-owner>/<Stack-B-repo>/<Stack-B-env>/ccmenu`.
4. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks` helper, the request succeeds and returns Stack B's build/deploy status XML, even though the token was never authorized (`stack_id`) for Stack B.
