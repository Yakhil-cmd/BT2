### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach an incoming GitHub `status` webhook to purely by `sha`, with no scoping to the reporting repository/stack. Because the `commits` table only enforces uniqueness on `(sha, stack_id)` rather than globally on `sha`, the same SHA can legitimately exist as separate `Commit` rows in different `Stack`s (different repositories) within the same GitHub organization, and a validly-signed webhook for one repository will write a `Status` into every stack that has a matching-SHA commit.

### Finding Description
The broken binding: the question asserts `stack_that_evaluates(all_status_checks_passed?) == repository_that_authenticated(status_write)`. Tracing the code shows this equality does **not** hold.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, i.e. it authenticates at the **organization** level only, using `params.dig('repository','owner','login')`. It never checks that the `sha` in the payload actually belongs to the specific `repository.full_name` that signed the request.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does:
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This query is global across the entire `commits` table — not scoped by `stack_id`, `repository_id`, or the payload's `repository.full_name`.
- `Commit#create_status_from_github!` → `Status.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:23-33`) creates the `Status` using `commit.stack_id` — the **matched commit's own stack**, not any stack tied to the webhook's originating repository.
- The `commits` table index is `add_index :commits, %i(sha stack_id), unique: true` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming `sha` is only unique *per stack*, not globally — the same SHA can and does exist as distinct `Commit` rows in multiple stacks (e.g. shared history between related repos/forks/review-stacks tracked as separate `Stack`s in the same org).

Attacker flow: the attacker has legitimate (but limited/unprivileged w.r.t. the victim) write access to Repository A (a different repo in the same GitHub org as the victim's Repository B, both of which Shipit tracks as separate `Stack`s). The attacker pushes/obtains a commit object whose SHA is identical to a commit already present as `Commit` in the victim's Stack B (e.g., by fetching and re-pushing the exact same git object, or via shared ancestor history between forks/branches). The attacker then sets a `success` commit status via the real GitHub Status API on Repository A for that SHA. GitHub sends a correctly-signed `status` webhook (signed with Repo A's org secret, which is the same org secret Shipit already trusts) to `POST /webhooks`. `StatusHandler#process` finds **both** the Stack A commit and the Stack B commit sharing that SHA and writes a `success` `Status` onto both — including the victim's Stack B commit, without the attacker ever touching Repo B, holding a Shipit session, an `ApiClient` token, or the `webhook_secret`.

Existing guards do not stop this: `verify_signature` only binds trust to the organization, not the specific repository; `drop_unhandled_event` and `check_if_ping` are irrelevant; `ExplicitParameters` schema on `StatusHandler` requires only `sha`/`state`/etc., no repository field is required or cross-checked; there is no model validation tying `Status#stack_id`/`Commit#sha` uniqueness across stacks, by design (index is `(sha, stack_id)` unique, explicitly permitting cross-stack sha reuse).

### Impact Explanation
An attacker with only ordinary write access to one repository/stack in a Shipit-managed GitHub organization can inject a forged `success` `Status` record onto an unrelated victim stack's commit, as long as a SHA collision (real or engineered by re-pushing the same git object) exists between the two. This can flip `MergeRequest#all_status_checks_passed?` to `true` for a queued PR the attacker has no access to, causing `ProcessMergeRequestsJob` to call `merge_request.merge!`, resulting in an **unauthorized merge** of a stack the attacker doesn't control — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The attack is repeatable against any pair of stacks in the same org that the attacker can align a SHA with, and is not limited to a single victim repository.

### Likelihood Explanation
Preconditions: Shipit must manage multiple `Stack`s under a single GitHub organization (very common), the attacker must have ordinary (non-maintainer) write access to at least one of those repos (e.g. a contributor with push access to a low-sensitivity internal repo), and a matching-SHA `Commit` row must exist in the victim's stack (achievable deterministically by re-pushing a known git object with an identical SHA into the attacker-controlled repo, not requiring any hash collision attack). No Shipit secret, session, or API token is needed — only ordinary GitHub write access to a different repo. This is a low-cost, deterministic, repeatable attack path once org-wide multi-stack management is in place.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to the reporting repository: pass the payload's `repository.full_name` through to the handler and filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })` (or equivalent), so a status can only be attached to commits belonging to the stack(s) whose GitHub repository actually emitted the event.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
    test "a status webhook for repo A must not flip all_status_checks_passed? for repo B's merge request" do
      stack_a = shipit_stacks(:shipit)                # attacker-writable repo/stack
      stack_b = shipit_stacks(:cyclimse)               # victim repo/stack, different repository

      shared_sha = "deadbeef" * 5

      commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
      commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

      merge_request = shipit_merge_requests(:cyclimse_first) # queued PR on stack_b
      merge_request.update!(head: commit_b, merge_status: 'pending')

      # Binding under test, stated explicitly before tracing:
      # stack_that_evaluates(all_status_checks_passed?) == stack_b
      # repository_that_authenticated_the_write == stack_a's repository (attacker-owned)
      refute merge_request.reload.all_status_checks_passed?

      # Attacker-authenticated webhook payload for repo A only
      params = Webhooks::Handlers::StatusHandler.const_get(:Params).new(
        sha: shared_sha, state: "success", description: nil, target_url: nil, context: "ci/attacker", created_at: Time.now.to_s
      ) rescue OpenStruct.new(sha: shared_sha, state: "success", context: "ci/attacker", created_at: Time.now)

      Webhooks::Handlers::StatusHandler.new(params).process

      # Assert the two sides of the binding no longer match: repo B's MR flips
      # even though only repo A's webhook was authenticated.
      assert merge_request.reload.all_status_checks_passed?, "status intended for repo A leaked into repo B's merge request"
    end
  end
end
```
This demonstrates that a `Status` write authenticated only for repository A's organization/webhook is applied to a `Commit` belonging to an unrelated stack B, flipping `all_status_checks_passed?` for the victim's queued `MergeRequest` and enabling `ProcessMergeRequestsJob` to call `merge!` on a repository the attacker never touched.
