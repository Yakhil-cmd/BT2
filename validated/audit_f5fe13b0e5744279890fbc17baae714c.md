### Title
Cross-repository forged commit status via unscoped `StatusHandler` webhook processing - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook handler applies GitHub commit-status updates by looking up commits **only by SHA**, with no check that the SHA belongs to the repository/organization whose webhook signature was actually verified. This breaks the required binding: `organization that authenticated == repository that is written`. Any Shipit-registered GitHub organization/repository can forge a `status` event referencing a commit SHA that belongs to a completely different, unrelated stack/organization on the same Shipit instance, and inject an arbitrary CI status for it. Because commit statuses feed directly into deploy/merge gating (`required`/`blocking` statuses), this allows an attacker who controls one tenant's webhook credentials to unlock deploys or merges for a repository they have no access to.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to use for HMAC verification based on a field taken from the **same unauthenticated JSON body** that is about to be verified: [1](#0-0) 

The org used to select/verify the secret is `params.dig('repository', 'owner', 'login')`: [2](#0-1) 

Once the signature check passes for *some* organization, the controller dispatches to `Shipit::Webhooks.for_event(event)` handlers with the raw parsed `params`, unmodified. The `status` event handler processes the payload **without ever checking which repository/organization it belongs to**: [3](#0-2) 

`Commit.where(sha: params.sha)` is a global, unscoped lookup across every stack/repository tracked by the Shipit instance. Compare this with every other handler (`PushHandler`, `PullRequest::*Handler`, etc.), which route through `Handler#stacks`/`Handler#repository_name`, scoping to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [4](#0-3) 

`StatusHandler` inherits from `Handler` but never uses `stacks`/`repository_name` — it directly calls `Commit.create_status_from_github!` for any commit anywhere in the database matching the attacker-chosen SHA: [5](#0-4) 

Git commit SHAs are not secrets — they are visible in any public (or otherwise-accessible) commit history, PR page, or CI log of the target repository. An attacker who legitimately owns/administers a *different* GitHub organization/repository already configured in this Shipit instance (and therefore can register a real webhook with a real signature for their own org) can send a `status` webhook whose `repository` field names their own org (so signature verification succeeds) but whose `sha` is copied from a victim stack's commit. `StatusHandler` will happily record a fabricated status (`state: success`, arbitrary `context`/`target_url`/`description`) against that victim commit.

This is the same "check acts on a field never bound to the verified context" bug class as the reentrancy analog: the signature verifies *authorization for organization A's payload*, but the state mutation (`create_status_from_github!`) is performed using a *different, unverified field* (`sha`) that is never checked to belong to organization A.

Separately (and compounding the issue further), `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the resolved organization: [6](#0-5) 

Since `webhook_secret` is an explicitly-supported "nil" configuration value (see the example secrets file), any multi-tenant Shipit deployment that has even one organization without a configured secret allows a **fully unauthenticated** caller to hit this same unscoped `StatusHandler` code path, by simply setting `repository.owner.login` to that unsecured org while setting `sha` to a commit belonging to any other, fully-secured organization's stack.

### Impact Explanation
Commit statuses are consumed by `StatusChecker` to decide whether a commit is deployable and whether pull requests pass CI for the merge queue (`MergeRequest#all_status_checks_passed?` / `#any_status_checks_failed?`, and `Stack#deployable?` chains). Forging a passing status (or a blocking/required status) on another organization's commit can:
- Unlock/trigger an unauthorized deploy of a commit that never actually passed CI, and
- Unlock an unauthorized merge in another organization's merge queue.

This matches the in-scope Critical impact category "an unauthorized deploy, rollback or merge," and (via the unscoped, cross-tenant write) also constitutes a cross-repository write, achieved purely by an attacker who controls their own tenant's webhook signing material — no `ApiClient` token, `github_access_token`, or privileged Shipit account is required.

### Likelihood Explanation
Likelihood is high in any multi-tenant Shipit deployment (multiple GitHub orgs configured, as explicitly supported by `config/secrets.development.shopify.yml` and `lib/shipit/github_app.rb`'s per-organization config): any organization admin who can register a webhook for their own repository already has all the credentials needed (their own `webhook_secret`) to pass `verify_signature`. Forging the `sha` field is trivial since commit SHAs are not confidential. The additional unauthenticated path (nil `webhook_secret` on any tenant) further increases likelihood since it is a documented, apparently-supported configuration.

### Recommendation
Bind the state mutation to the same authenticated context used for verification:
- In `StatusHandler#process`, scope the `Commit` lookup through `stacks`/`Repository.from_github_repo_name(payload.dig('repository','full_name'))` exactly as the other handlers do, rejecting/ignoring statuses whose SHA does not belong to a commit tracked by that specific repository.
- Enforce that the repository/organization used to select the verifying `webhook_secret` (`repository.owner.login`) is the same repository referenced by `repository.full_name` before any handler executes, ideally by re-deriving one from the other rather than trusting two independent, unauthenticated fields.
- Require `webhook_secret` to be present for all configured organizations (or explicitly document/gate the "no secret" mode as insecure/test-only), removing the unconditional `return true` fallback in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Operator runs a multi-tenant Shipit instance tracking, among others, `victim-org/victim-repo` (with a properly configured `webhook_secret`) and `attacker-org/attacker-repo` (owned/administered by the attacker, who therefore knows `attacker-org`'s `webhook_secret`).
2. Attacker looks up a real commit SHA `S` from `victim-org/victim-repo` (visible via any public commit link, PR, or CI log).
3. Attacker sends a `status` webhook to `POST /webhooks` with:
   - `X-Github-Event: status`
   - `X-Hub-Signature` computed with `attacker-org`'s webhook secret over the raw body
   - Body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"}, "sha": "S", "state": "success", "context": "ci/required-check", ...}`
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, verifies successfully against `attacker-org`'s real secret.
5. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the victim's commit (unscoped to any repository), and calls `create_status_from_github!`, recording a forged passing status on `victim-org/victim-repo`'s commit — potentially satisfying a `required`/`blocking` status and unlocking a deploy or a merge-queue merge for `victim-org` that the attacker has no access to.

Note: full confirmation of exact downstream `StatusChecker`/merge-queue gating logic for `required`/`blocking` statuses could not be fully traced in this pass due to index scope limits; if further verification of that exact gating path is needed, a Devin session with full repository access would be required to inspect `StatusChecker` and `Commit#create_status_from_github!` in full.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",

      ].join(' '))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
