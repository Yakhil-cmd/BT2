## Finding

### Title
Cross-stack authorization bypass in CCMenu API endpoint — stack-scoped ApiClient can read any stack's build status (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via the optional `stack` association [1](#0-0) , and this scope is meant to be enforced centrally by `Api::BaseController#stacks`/`#stack`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped [2](#0-1) . `Api::CCMenuController`, however, overrides `stack` to look up `Stack.from_param!(params[:stack_id])` directly, bypassing the scoped `stacks` relation entirely [3](#0-2) .

### Finding Description
The binding broken is: **the stack a token authorizes ≠ the stack it touches**.

`Api::BaseController` is the shared authentication/authorization layer for all `Api::*` controllers. When an `ApiClient` has a `stack_id` set, every controller that calls the inherited `stack` helper is restricted to that one stack:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController` inherits `BaseController` (and thus its `authenticate_api_client`/Basic-Auth path via `super`) [4](#0-3) , but it redefines `stack` to resolve the target stack unconditionally from `params[:stack_id]`, without ever consulting `current_api_client.stack_id?`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

The route is nested per-stack: `GET /api/stacks/*stack_id/ccmenu` [6](#0-5) , so a caller supplies an arbitrary `stack_id`. The controller only enforces `require_permission :read, :stack` [7](#0-6) , which checks that the permission string `read:stack` is present on the client — a global check independent of which stack is being accessed — see `ApiClient#check_permissions!` [8](#0-7) . Nothing in the request path re-validates that `stack.id == current_api_client.stack_id`.

By contrast, `Api::StacksController` correctly reuses the inherited, scoped `stack`/`stacks` methods [9](#0-8) , and this scoping is explicitly tested: "an api client scoped to a stack will only see that one stack" [10](#0-9) . `Api::CCMenuController` has no equivalent test and no equivalent enforcement.

### Impact Explanation
An `ApiClient` record deliberately scoped to a single stack (`stack_id` set, `permissions` including `read:stack`) — the intended trust boundary for e.g. CI dashboard integrations — can be replayed with Basic Auth against `/api/stacks/<any-other-stack>/ccmenu` to read that other stack's build/deploy status, last build label, and activity, even though the token was never authorized for that stack. This is an unauthorized cross-stack read of deploy/CI state, matching the "High — unauthenticated/unauthorized read of stack state" impact category, achieved purely by an authorization-scope confusion rather than any credential theft.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` Basic Auth credential (a credential explicitly designed to be handed to lower-trust integrations, e.g., CI dashboards) can exploit this with a single unmodified HTTP request by substituting a different `stack_id` in the URL — no additional privilege, signature forgery, or race condition is required.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and rely on the inherited, scope-aware `BaseController#stack`/`#stacks` (or explicitly re-implement the same `current_api_client.stack_id?` check) so that a stack-scoped token can only resolve to its authorized stack.

### Proof of Concept
1. Admin creates (or the app creates, e.g. via `CCMenuUrlController#client`) an `ApiClient` with `stack: stack_a`, `permissions: ['read:stack']`.
2. Attacker obtains this token (e.g., from a CI dashboard config that legitimately uses it for `stack_a`).
3. Attacker issues `GET /api/stacks/other-owner/other-repo/other-env/ccmenu` with `Authorization: Basic base64(token)`.
4. `Api::CCMenuController#authenticate_api_client` authenticates the token via `super` (Basic Auth) [4](#0-3) ; `require_permission :read, :stack` passes because the client globally has `read:stack` [8](#0-7) ; `stack` resolves `other-owner/other-repo/other-env` unconditionally [5](#0-4) .
5. Response renders CCMenu XML for the unauthorized stack, disclosing its deploy/build state.
