### Title
Unbounded dust-account creation imposes unbounded TTL-renewal cost on the keeper and can freeze positions — (`contracts/controller/src/positions/supply.rs`)

### Summary
The Across report's bug class — many cheap actions on a low-cost path that force expensive, unavoidable work on a high-cost executor — maps directly onto XOXNO Lending: `supply(caller, account_id = 0, spoke_id, assets)` mints a brand-new account (position NFT + persistent controller entries) for any positive deposit, with no minimum amount. A single unprivileged address can create an unbounded number of dust accounts at minimal cost. Each account creates persistent entries (`AccountMeta`, `SupplyPositions`, NFT `Owner`/`Balance`/enumeration) that the keeper scans and renews via the position-NFT counter, so the renewal/operational cost grows linearly with spam, and if renewal does not keep up, real users' position entries archive and their funds are frozen until restored.

### Finding Description
- `process_supply` treats `account_id == 0` as "create a new account" and calls `load_or_create_account`, which mints an NFT and writes `AccountMeta` plus position maps — for any positive amount, down to a single raw unit of the token. There is no minimum-supply floor on the account-opening path; the only lower bound is `SupplyRoundsToZeroShares`, which a 1-unit deposit at index ≈ 1 RAY never trips. [1](#0-0) [2](#0-1) 
- Each minted account writes persistent keys on both contracts: `NFTStorageKey::Owner(token_id)`, `Balance(owner)`, enumeration entries on the NFT (`mint` → `sequential_mint` + `extend_user_persistent_ttl`), and `AccountMeta`/`SupplyPositions`/`Delegates` on the controller. [3](#0-2) [4](#0-3) 
- Per-user entries have finite TTL windows (30 days on OZ `Owner`, 120 days on controller account keys) and must be renewed. The keeper renews account state by scanning the position-NFT counter — an O(accounts) sweep whose cost grows without bound as accounts accumulate, exactly mirroring the "executor pays for spam leaves" asymmetry. [5](#0-4) 
- `renew_account` requires the account owner, so only the keeper's counter-scan covers arbitrary accounts; spammed attacker accounts still consume keeper scan/renew budget. [6](#0-5) 
- `clean_bad_debt` cannot remove these accounts — they carry no debt — and account deletion via `withdraw` requires the owner's auth, so the attacker alone decides when (or whether) the entries die. Ids are never reused. [7](#0-6) 

### Impact Explanation
Temporary freezing of funds plus sustained operational-cost griefing. If the keeper's renewal budget cannot cover the enlarged account set (or its scan becomes economically/rate-limit infeasible), persistent `AccountMeta`/`SupplyPositions`/NFT `Owner` entries archive; every subsequent controller call on those accounts — withdraw, repay, liquidate, `clean_bad_debt` — fails until someone pays archival restore, freezing the collateral of any legitimate account caught in the lapse. Even absent archival, the attacker externalizes a permanently growing renewal bill and state footprint onto the protocol operator for the price of dust deposits, the same lose-lose shape as the Across refund-leaf spam (execute at a loss, or leave entries to expire).

### Likelihood Explanation
Medium. The attack requires no privilege, no timing, and no market condition — only `supply` calls with `account_id = 0` and token dust; the in-repo PoC `poc_single_actor_spams_unbounded_dust_accounts` demonstrates 64 accounts minted by one actor for 64 raw units. Cost per account is one token unit plus tx fees, while each account creates multiple persistent entries needing renewal every ~30/120 days forever. The mitigating factor is that harm materializes only if keeper renewal actually falls behind, so the direct on-chain loss is bounded to temporary freezing rather than theft.

### Recommendation
- Require a minimum first-deposit USD value (or minimum scaled shares well above zero, e.g. via a `min_open_position` check against `price_wad`) when `account_id == 0`, analogous to `min_borrow_collateral_usd` on the debt side — a "minimum deposit value" floor, the same fix the report suggests.
- Alternatively let `clean_bad_debt`-style permissionless cleanup (or a new `close_dust_account` entrypoint) remove accounts whose total supply value sits below a dust threshold, so spammed accounts are cheaply deletable by anyone.
- Cap the keeper's per-user renewal scope or make account entries share a hub-level TTL structure rather than per-account keys.

### Proof of Concept
Already present in the repo at `tests/test-harness/tests/controller/supply.rs:313-344`: one actor loops `ctrl.supply(&attacker, &0u64, &1u32, &[(hub_asset, 1)])`, minting N distinct persistent accounts for N raw units of USDC — `assert!(id > 0, "1-unit deposit must be accepted (no dust floor)")`. Extending it, each created id shows up in the NFT `TokenIdCounter` scan range the keeper iterates for `AccountMeta`/`SupplyPositions`/`Owner` renewal, so renewal cost scales linearly with N while the attacker's cost is N dust units. [8](#0-7)

    finalize_position_flow(
        env,
        acct_id,
        &account,
        &mut cache,
        PositionSides::Supply,
        false,
    );
    acct_id

fn poc_single_actor_spams_unbounded_dust_accounts() {
    let mut t = LendingTest::new().with_market(usdc_preset()).build();

    let attacker = t.get_or_create_user("attacker");
    let usdc = t.resolve_market("USDC");

    const N: u64 = 64;
    usdc.token_admin.mint(&attacker, &(N as i128));
    let asset = usdc.asset.clone();

    let ctrl = t.ctrl_client();
    let mut created: u64 = 0;
    let mut last_id: u64 = 0;
    for _ in 0..N {
        let dust = vec![&t.env, (hub_asset(asset.clone()), 1i128)];
        let id = ctrl.supply(&attacker, &0u64, &1u32, &dust);
        assert!(id > 0, "1-unit deposit must be accepted (no dust floor)");

        assert!(id > last_id, "each supply(id=0) must mint a new account id");
        assert!(
            ctrl.account_exists(&id),
            "spammed account persists in storage"
        );
        last_id = id;
        created += 1;
    }

    assert_eq!(
        created, N,
        "one actor created {N} distinct accounts with dust deposits"
    );
}
