### Title
Unchecked accrued-value overflow permanently freezes an oversized lending market - ([File: common/src/rates/scaling.rs])

### Summary

Accruing a large borrow position can overflow `i128` while converting scaled debt into its current RAY-denominated value. Because every state-changing market operation performs interest accrual before applying the requested action, the overflow blocks repayment, withdrawal, liquidation, recapitalization, and further index updates for the affected market. This is an arithmetic-validation analogue of CVE-2014-0144: attacker-influenced market sizes can drive a conversion outside the representable domain, after which the market cannot process an ordinary recovery action.

### Finding Description

Positions store RAY-scaled shares. Accrual converts those shares through `scaled_to_original`, which evaluates `scaled.mul(env, index)` and raises `MathOverflow` when the product no longer fits in `i128`. [1](#0-0) 

The pool's mutation flow runs `interest::global_sync` before each mutation, so the overflow occurs before the requested borrow, repayment, withdrawal, liquidation, or settlement logic can execute. [2](#0-1) 

The code admits balances up to the token-to-RAY conversion bound, but that bound only guarantees that the initial rescale succeeds. It does not bound `scaled_amount * borrow_index`; accrued values can become unrepresentable before the configured borrow-index ceiling is reached. [3](#0-2) 

The committed regression test demonstrates the condition: an 18-decimal market holding roughly one billion tokens at 98% utilization eventually raises `MathOverflow` during index accrual while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [4](#0-3) 

The same test then confirms that both `withdraw` and `repay` fail with `MathOverflow` because they accrue first. [5](#0-4) 

### Impact Explanation

Once the accrued product exceeds `i128::MAX`, every protected path that synchronizes the market reverts before transferring or mutating state. Suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot clear the account through the normal liquidation path. The failure is not caused by temporary liquidity shortage and does not leave a smaller partial-exit path; the same accrual expression is evaluated by each recovery entrypoint. The affected market is therefore permanently frozen absent a privileged contract change.

This qualifies as permanent freezing of user funds and a contract unable to operate for that market.

### Likelihood Explanation

The trigger requires an unusually large admitted market and a large outstanding borrow, so it is conditional rather than universally reachable. However, the exposed `supply` and `borrow` paths can create the precondition when market caps and liquidity permit it, and `update_indexes` lets an unprivileged caller execute the accrual that crosses the boundary. No oracle manipulation or leaked privilege is required.

The issue is therefore realistic for markets configured near the supported numeric domain or for attacker-controlled assets with sufficient minted supply, but it is not a generic low-cost attack against small markets.

### Recommendation

Prevent accrual from entering an unrepresentable state:

- Enforce a market-level invariant that the largest stored scaled supply/debt value multiplied by the next index remains below the RAY arithmetic limit.
- Cap or reject new supply/borrow before the scaled position can later overflow under the maximum permitted index.
- Clamp accrual at `MAX_BORROW_INDEX_RAY` before performing position-value multiplication, rather than allowing the multiplication itself to become the failure point.
- Add a recovery path that writes down or settles a market without first evaluating the overflowing accrued value.
- Extend the existing extreme-amount regression coverage to assert that every recovery verb remains callable before the arithmetic boundary.

### Proof of Concept

A committed test already reproduces the failure:

1. Create an 18-decimal market with caps lifted.
2. Supply `1_000_000_000 * 10^18` base units to that market.
3. Supply sufficient collateral in another market and borrow approximately 98% of the first market's principal.
4. Submit the permissionless `update_indexes` path repeatedly as interest accrues.
5. The first accrual whose scaled debt value exceeds `i128::MAX` panics with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`.
6. Subsequent `withdraw` and `repay` calls also panic with `MathOverflow` because they perform the same accrual first. [6](#0-5)

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
