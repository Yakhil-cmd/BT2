### Title
Webhook signature verified against one GitHub organization while the event is applied to a repository named by an unverified payload field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore the HMAC `webhook_secret`) used to authenticate an inbound webhook based on `repository_owner`, a value pulled straight out of the JSON payload. The event handlers that subsequently act on the payload look up the target `Stack`/`Repository` using a *different* payload field, `repository.full_name`. Nothing ties these two fields together, so a payload can be crafted so that the signature check passes against Organization A's secret while the mutation is applied to a repository belonging to Organization B.

### Finding Description
`verify_signature` computes the organization used to fetch the correct `GitHubApp` purely from the request body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and `Shipit.github(organization: repository_owner)` returns the `GitHubApp` instance configured for that org key, whose `webhook_secret` is then used in `verify_webhook_signature`: [3](#0-2) 

Shipit explicitly supports hosting multiple GitHub organizations behind a single instance, each with its own App/secret — this is a documented, first-class configuration (`docs/setup.md`, "Using Multiple Github Applications"), so this is not an out-of-scope/unsupported deployment shape. Each org's webhook secret is legitimately known to that org's own GitHub App owner.

Once the signature check passes, `create` dispatches the entire raw JSON payload to every registered handler for the event type, with no re-binding of the payload to the organization that was authenticated: [4](#0-3) 

The base `Handler` class (and most concrete handlers such as `PushHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`) locate the target repository/stack using `repository.full_name`, a wholly independent field from the `repository.owner.login` used for authentication: [5](#0-4) 

Concretely: `verify_webhook_signature` binds trust to `organization = payload['repository']['owner']['login']`, but the mutation binds action to `repository = payload['repository']['full_name']`. The equality the code implicitly (and incorrectly) assumes is:
`organization_that_signed(payload) == organization_owning(repository_acted_on(payload))`
There is no code enforcing this equality — an attacker who legitimately controls Organization A (and therefore genuinely knows Organization A's `webhook_secret`, since they configured/installed that GitHub App themselves) can sign a payload with Organization A's secret while setting `repository.full_name` to `"OrgB/some-repo"`. The signature check succeeds (correct secret for the login field it inspects), but the handler that runs afterward operates on OrgB's `Stack`.

Before the attacker's request: only webhooks genuinely originating from GitHub for a given org's repos can affect that org's stacks, because signature validation and the object being mutated are assumed to be the same tenant.
After the forged request: an operator of any one tenant Organization A configured on the shared Shipit instance can make authenticated-looking webhook calls that mutate state belonging to Organization B's stacks (sync commits, capture PR labels, archive/unarchive review stacks, etc.), despite never having been granted any access to Organization B's repository or Shipit stack.

### Impact Explanation
This breaks the tenant/organization isolation that the multi-org GitHub App feature is supposed to provide. The most consequential handler is `PushHandler`, which calls `stack.sync_github(expected_head_sha:)` for the target repository/branch found via the attacker-controlled `repository.full_name` and `ref` fields — this drives which commits Shipit considers deployable and can feed into automatic/continuous delivery pipelines for a stack the attacker does not own. Other affected handlers (`LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`) archive/unarchive review stacks and mutate pull request label state for repositories that belong to a different, unrelated tenant. This is a cross-tenant write into another organization's Shipit-managed state, meeting the "cross-repository writes" / "unauthorized deploy pipeline manipulation" impact bar, achievable by an attacker who only needs legitimate control of one org onboarded to the shared Shipit instance — no Shipit session, ApiClient token, or GitHub write access to the victim's own repository is required.

### Likelihood Explanation
Exploitability requires the deployment to run Shipit's documented multi-organization configuration (`config/secrets.yml` keyed by org name, each with its own `webhook_secret`) — a supported, documented mode of operation, not a misconfiguration. Any org owner behind that shared instance can trivially construct the forged payload (their own real webhook secret plus attacker-chosen `repository.full_name`/`ref`/`after` values) and POST it to `/webhooks`. No race condition, timing, or privileged access is needed beyond being one of the (possibly many) legitimate tenant organizations on the instance.

### Recommendation
Bind the field used to select the verification secret to the same field the handlers use to resolve the target repository — verify signatures per-repository (or verify that `repository.owner.login` matches the owner segment of `repository.full_name`) before dispatching to handlers. Alternatively, resolve the GitHub App/organization from the already-trusted `Repository`/`Stack` record (looked up by `repository.full_name`) rather than from an unauthenticated field in the payload, and reject the webhook if that repository's configured organization does not match the organization whose secret validated the signature.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `docs/setup.md`), each with at least one repository/stack tracked (`OrgA/repoA`, `OrgB/repoB`).
2. As the legitimate owner/admin of `OrgA`'s GitHub App, obtain `OrgA`'s real `webhook_secret` (this is knowledge an attacker in this scenario legitimately has).
3. Craft a `push` event JSON body: `{"ref": "refs/heads/main", "after": "<attacker-chosen-sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/repoB"}}`.
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the HMAC check succeeds using the legitimately-known `OrgA` secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/repoB")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — mutating `OrgB`'s stack despite the request only being authenticated as `OrgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
