## Title
Authorization Bypass via Ambiguous Prefix Matching in Address-Definition Path Gating - (File: definition.js)

### Summary
`pathIncludesOneOfAuthentifiers()` in `definition.js` decides whether a signer "claims" a particular branch of an address definition (an `'address'` op referencing another address) by testing whether an actual authentifier path string is a *character prefix* of the branch path, with no path-segment boundary check: [1](#0-0) 

```
function pathIncludesOneOfAuthentifiers(path, arrAuthentifierPaths, bAssetCondition){
	...
	for (var i=0; i<arrAuthentifierPaths.length; i++){
		var authentifier_path = arrAuthentifierPaths[i];
		if (authentifier_path.substr(0, path.length) === path)
			return true;
	}
	return false;
}
```

Because signing paths are built as dotted numeric indices (`r`, `r.0`, `r.1`, `r.10`, `r.1.0`, ...), a short path such as `"r.1"` is a literal string prefix of an unrelated sibling path such as `"r.10"`, `"r.11"`, ... `"r.19"`. This is the same class of bug as the Spring Boot Actuator issue: a security decision is made on a *path prefix match* instead of exact/segment-bounded matching, so an endpoint (here, an "address" branch) declared under a path that collides textually with another already-authenticated path is treated as if it were itself authorized.

and analogously in the structural definition evaluator via `needToEvaluateNestedAddress`: [3](#0-2) 

`arrAuthentifierPaths` is simply `Object.keys(assocAuthentifiers)` — every authentifier path actually supplied by the author for this unit: [4](#0-3) 

If an address definition contains an `'or'`/`'r of set'` with 11+ members, the branch at index 1 gets path `r.1` while the branch at index 10 gets path `r.10`. If the author supplies a genuine authentifier at `r.10` (satisfying that sibling branch, e.g. simply a `sig`), the gate check for the completely different `r.1` branch, `pathIncludesOneOfAuthentifiers("r.1", ["r.10", ...])`, incorrectly returns `true` because `"r.10".substr(0,3) === "r.1"`. This causes the evaluator to descend into and evaluate the `'address'` reference at `r.1` even though the author never signed for that branch.

### Impact Explanation
If the referenced/nested address at the colliding branch has a definition that can be satisfied by state that is *not* controlled by a private key the payer possesses — e.g. `'in data feed'`, `'seen address'`, `'has'` output/input conditions, or a currently-true `timestamp`/data-feed condition — then evaluating that branch (which should never have been reachable without a real per-path authentifier) can return `true` purely from public/attacker-influenceable state. Combined with a top-level `'or'` this lets the whole authorization succeed without the intended real signature for that branch, enabling unauthorized use of the address's spending conditions — i.e., a form of authentication bypass reachable purely by any unit poster who can (a) define such an address (asset issuer/AA author/private-payment counterparty) and (b) supply an authentifier at any sibling index whose string is a prefix collision (e.g. `r.10`–`r.19`, `r.100`–`r.199`, etc.).

### Likelihood Explanation
Exploitability requires the attacker to control (or induce) the address definition structure (easy — definitions are attacker-authored oscript for any wallet/shared address/asset condition) and requires ≥11 branches under one `'or'`/`'r of set'`/`'and'` node so that two-digit index collisions occur, which is within `MAX_COMPLEXITY`/`MAX_OPS` limits. This is a self-contained condition an attacker fully controls when constructing their own address, making the likelihood of triggering the code path high; the constraint is designing an address whose colliding branch is satisfiable by public state, which is a standard oscript pattern (e.g., "sig OR data-feed dead-man-switch").

### Recommendation
Change `pathIncludesOneOfAuthentifiers` to compare path segments with a boundary check (e.g. `authentifier_path === path || authentifier_path.substr(0, path.length + 1) === path + '.'`) instead of a raw string prefix comparison, eliminating numeric-index prefix collisions between sibling branches.

### Proof of Concept
1. Construct address `A` with definition:
```
['or', [
  ['sig', {pubkey: PUBKEY_0}],          // r.0
  ['address', OTHER_ADDR],              // r.1  -- e.g. OTHER_ADDR's definition = ['in data feed', [[ORACLE], 'price', '>', 0]]
  ['sig', {pubkey: PUBKEY_2}], ... up through
  ['sig', {pubkey: PUBKEY_10}]          // r.10
]]
```
2. Author a unit spending from `A`, supplying only `authentifiers = {"r.10": <valid sig for pubkey_10's path>}` — note `r.1` is left unsigned.
3. During `validateAuthentifiers`, `arrAuthentifierPaths = ["r.10"]`. When evaluating the `r.1` branch (`['address', OTHER_ADDR]`), `pathIncludesOneOfAuthentifiers("r.1", ["r.10"])` returns `true` due to the string-prefix collision, so the evaluator descends into `OTHER_ADDR`'s data-feed condition instead of short-circuiting with `cb2(false)`.
4. If the oracle's `price` data feed is currently `>0` (trivially true / attacker-postable if attacker also controls the oracle address), branch `r.1` evaluates to `true`, satisfying the outer `'or'` and authorizing the spend — without ever providing the signature the branch's design intended to require, and without needing `PUBKEY_10`'s key to correspond to a co-signer of that specific branch.
