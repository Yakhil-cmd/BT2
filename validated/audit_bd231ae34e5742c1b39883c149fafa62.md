### Title
Cross-organization webhook forgery triggers unauthorized deploy via unscoped `status` event handling - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` is used to validate an inbound webhook's HMAC signature based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), but the handler that subsequently mutates state (`StatusHandler`) never checks that field — it looks up commits globally by `sha` alone. In a multi-organization Shipit deployment, if *any* configured organization has no `webhook_secret` set (a documented, supported configuration), an attacker can forge a `status` webhook that authenticates as that unprotected organization while actually writing a `success` status onto a commit belonging to a completely different, properly-secured organization's stack — triggering an unauthorized continuous-deployment run.

### Finding Description
`WebhooksController#verify_signature` resolves the signing organization solely from the payload, not from anything cryptographically bound to the actual signature: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GitHubApp` instance whose secret is looked up per-organization, and verification is a no-op when that organization's secret is blank: [3](#0-2) 

Per-organization `webhook_secret: # nil` is a documented, valid configuration for multi-org installs: [4](#0-3) [5](#0-4) 

Once the signature check passes (trivially, for the org with no secret), the full JSON payload is dispatched to every registered handler for the event, unmodified: [6](#0-5) 

`StatusHandler` does not reference `repository` at all — it resolves target commits purely by `sha`, across the entire `Commit` table, with no organization or repository scoping: [7](#0-6) 

Creating that `Status` record enables CI on the stack and schedules continuous delivery: [8](#0-7) 

which, if the target stack has `continuous_deployment: true` and the commit becomes the next deployable commit, results in a real deploy being triggered: [9](#0-8) 

The equality that should hold but doesn't: `organization authenticated by verify_signature (via repository.owner.login / organization.login and its configured webhook_secret)` == `organization/stack whose commit is written by the handler`. `StatusHandler` (and, to a lesser extent, `PushHandler`/`CheckSuiteHandler`, which key off `repository.full_name` instead of `repository.owner.login`) never enforces this equality.

### Impact Explanation
This lets an unauthenticated external attacker who knows only the public commit SHA of a target stack (trivially obtainable from GitHub) forge a `status` webhook that is authenticated as any organization in the multi-org config with a blank `webhook_secret`, yet writes a fabricated "success" CI status onto a commit belonging to an entirely different, properly-secured organization/stack. If that stack has continuous deployment enabled, this results in an unauthorized deploy — matching the Critical impact category ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (1) a multi-organization Shipit configuration (explicitly documented/supported), (2) at least one configured organization without a `webhook_secret` (a documented default), and (3) knowledge of a target commit's SHA (public information via GitHub). No `ApiClient` token, session, GitHub App private key, or the target organization's actual `webhook_secret` is needed. This is realistic for any installation onboarding multiple orgs where not every org has bothered to configure a webhook secret.

### Recommendation
Bind the authenticated organization from `verify_signature` to the request context (e.g., store it after verification) and have every webhook handler validate that the repository/stack it is about to mutate belongs to that authenticated organization before making any writes — including `StatusHandler`, which currently performs no repository/organization check whatsoever. Additionally, consider requiring a non-blank `webhook_secret` for every configured organization when more than one organization is configured.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgA` (no `webhook_secret` set) and `OrgB` (real `webhook_secret`, hosting a stack `production` with `continuous_deployment: true`).
2. Attacker looks up the current HEAD commit SHA of `OrgB/repo` via the public GitHub API.
3. Attacker sends:
   ```
   POST /webhooks
   X-Github-Event: status
   X-Hub-Signature: sha1=anything
   {
     "repository": { "owner": { "login": "OrgA" } },
     "sha": "<OrgB HEAD sha>",
     "state": "success",
     "context": "<required CI context for OrgB stack>"
   }
   ```
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
5. `StatusHandler.call(params)` runs `Commit.where(sha: params.sha)`, finds the `OrgB` commit, and creates a `success` `Status` on it.
6. `Status#schedule_continuous_delivery` fires; if the commit is now deployable, `OrgB`'s `production` stack is deployed without any legitimate action from `OrgB` or its GitHub App.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
