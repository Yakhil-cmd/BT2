### Title
Stack-scoped ApiClient token authorizes reading any stack's CCMenu status, not just the stack it was issued for - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) mints an `ApiClient` scoped to a single stack via the `stack: <the requesting stack>` association and only the `read:stack` permission, expecting that token to authorize reads for that one stack only, mirroring how `Api::BaseController#stacks`/`#stack` enforce that scoping everywhere else. `Api::CCMenuController`, however, defines its own `stack` method that ignores the client's `stack_id` binding and loads any stack the caller names in `params[:stack_id]`.

### Finding Description
`Api::BaseController` is the intended trust boundary: a token authorizes exactly the stack recorded in `ApiClient#stack_id`, enforced by [1](#0-0) 
`CCMenuUrlController#client` creates exactly this kind of scoped client, tied to one stack with only `read:stack`: [2](#0-1) 
But `Api::CCMenuController` overrides both `authenticate_api_client` (to accept the token via query string) and `stack`, and the overridden `stack` method drops the scoping entirely, resolving whatever stack the caller specifies: [3](#0-2) 
The permission check only validates the permission name `read:stack` (via `require_permission :read, :stack` → `ApiClient#check_permissions!`), not which stack the token is bound to: [4](#0-3) 
So the equality that should hold — "stack a token authorizes" == "stack a token touches" — is broken: any valid CCMenu token (bound to stack A) can be replayed with an arbitrary `stack_id` to read the merge status, build activity, and last build info of any other stack B in the installation.

### Impact Explanation
This is an unauthenticated (bearer-token, but out-of-scope-stack) read of another stack's state — merge status, deploy activity, deploy id/time, and stack URL — matching the "unauthenticated read of stack state" High-severity category. CCMenu tokens are handed out per-stack (e.g., embedded in third-party CI tray tools) and are not treated as sensitive-for-other-stacks credentials, so leakage of one such token (which is routinely embedded in a URL) discloses build/deploy state for every stack on the Shipit install, not just the one it was issued for.

### Likelihood Explanation
Any user with access to a single stack can call `CCMenuUrlController#fetch` for that stack, obtain a valid `token`, and then issue an unauthenticated `GET /api/stacks/:other_stack_id/ccmenu.xml?token=...` request for any other stack — no special privilege, race, or session is required beyond having any one valid CCMenu token. The bypass is a straightforward parameter substitution.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or make it call `super`) so it inherits `Api::BaseController#stacks`/`#stack`, ensuring the `stack_id` scoping recorded on the `ApiClient` is enforced identically to the rest of the API surface.

### Proof of Concept
1. As a legitimate user with access to Stack A, visit its settings page to trigger `CCMenuUrlController#fetch`, obtaining a `ccmenu_url` containing `token=<A-scoped-token>`.
2. Using that token, request `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=<A-scoped-token>` for a Stack B the attacker has no access to.
3. `Api::CCMenuController#authenticate_api_client` accepts the token (it is a valid `ApiClient`), and `Api::CCMenuController#stack` loads Stack B directly from `params[:stack_id]`, so the response discloses Stack B's `lastBuildStatus`, `activity`, `lastBuildTime`, `lastBuildLabel`, and `webUrl` — data the token was never authorized to access.
