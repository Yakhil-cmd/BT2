## Title
Cross-organization webhook signature confusion allows a malicious multi-tenant GitHub App owner to trigger syncs/deploys on repositories belonging to other organizations - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
When Shipit is configured to serve multiple GitHub organizations via distinct GitHub Apps (the documented "Using Multiple Github Applications" setup, each with its own `webhook_secret`), `WebhooksController#verify_signature` selects which organization's secret to validate the HMAC signature against using an attacker-supplied field of the very payload being verified: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. The actual repository that downstream handlers act on is derived independently from `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Because these two payload fields are never cross-checked against each other, an attacker holding a legitimately signed webhook secret for OrgA can freely set `repository.full_name` to `"OrgB/some-repo"` while keeping `repository.owner.login` (or `organization.login`) as `"OrgA"`, causing the signature check to pass against OrgA's secret while the handler processes state changes for OrgB's stacks.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body, and is used to pick which `GitHubApp` (and thus which `webhook_secret`) validates the signature via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

This multi-app-per-organization configuration is a first-class, documented feature: [4](#0-3) 

Once signature verification passes, handlers are dispatched with the raw parsed body and never re-derive the organization from the field that was actually verified. Instead, `Handler#stacks`/`#repository_name` resolve the target repository purely from `payload.dig('repository', 'full_name')`: [5](#0-4) 

`PushHandler#process`, for example, uses that repository's stacks to trigger `stack.sync_github(expected_head_sha:)` for any matching branch: [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` and looks up `owner`/`name` independently of anything checked during signature verification: [7](#0-6) 

**Binding broken (as an equality):** the organization whose GitHub App/secret authenticated the request (`repository_owner` used in `Shipit.github(organization: repository_owner)`) is never required to equal the organization that owns the repository the handler subsequently writes to (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`). The report's bug class — a value used to authorize an action being a different value than what's actually acted upon (analogous to `gasleft()` never being checked against what is consumed) — maps directly onto this: the field used to select/verify the signing secret and the field used to select the target repository are two independent, attacker-controlled JSON keys in the same unauthenticated-until-verified payload, with no equality assertion between them.

### Impact Explanation
An attacker who legitimately controls (or has compromised) the webhook secret for one tenant organization configured in this multi-org Shipit instance can forge webhooks that pass signature verification for their own org while manipulating `repository.full_name` to name a stack belonging to a completely unrelated, unaffiliated organization. Depending on which webhook event/handler is targeted, this can:
- Force out-of-band `GithubSyncJob`s / deploy triggers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`) against a victim organization's stack that the attacker has no authorization for, i.e., cross-repository/cross-tenant writes to state (`sync_github`, statuses, check runs) they should never be able to influence.
- Since Shipit deploys are ultimately driven off synced commit/status state, this can indirectly enable unauthorized deploy triggering against a victim's repository, satisfying the Critical "cross-repository writes / unauthorized deploy" bar for a multi-tenant instance.

This only applies to the documented multi-organization GitHub App configuration; single-org deployments are not affected because there's only one secret to validate against regardless of what `repository_owner` resolves to.

### Likelihood Explanation
Requires the operator to run Shipit in the documented multi-tenant mode (multiple GitHub Apps/orgs sharing one Shipit instance) and requires the attacker to control (as a legitimate tenant) the webhook secret of at least one of the configured organizations — a realistic scenario for a SaaS/shared Shipit deployment where multiple customer organizations each install their own App. No GitHub write access to the victim repo, no Shipit session, and no `ApiClient` token are needed — only knowledge of one tenant's own webhook secret, which that tenant is expected to know.

### Recommendation
After signature verification succeeds against the organization selected by `repository_owner`, re-validate that every subsequent handler's resolved repository (`payload.dig('repository', 'full_name')`, and any `organization.login` field) belongs to that same verified organization before dispatching to handlers — e.g., assert `repository.full_name.split('/').first == repository_owner` (case-insensitively) in `WebhooksController` and reject the request (422) otherwise.

### Proof of Concept
1. Operator configures Shipit with two orgs, `OrgA` and `OrgB`, each with a distinct GitHub App and `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. Attacker is a legitimate holder of `OrgA`'s `webhook_secret` (e.g., an org owner who set up their own App/installation).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret.
6. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on a stack owned by `OrgB`, which the attacker never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
