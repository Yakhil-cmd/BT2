### Title
StatusHandler#process writes GitHub status webhooks to Commit rows across all repositories, not just the verified payload's repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike every other handler that filters through `stacks` (repository-scoped). Signature verification in `WebhooksController#verify_signature` only proves the request came from the org owning the payload's `repository`, not that the sha belongs to that repository, so an attacker who owns any repo and can produce a colliding sha (e.g. via a forked/shared-history commit) can push a `Status` onto any victim `Commit` sharing that sha.

### Finding Description
The binding that must hold is: `repository_name` in the verified payload (`attacker/evil`) **must equal** `commit.stack.repository.full_name` for every `Commit` row mutated by the handler. In the actual code this equality is never checked.

Path: `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the JSON body and dispatches to handlers for the `status` event. Before that, `verify_signature` (lines 24-49) only checks the HMAC signature using `Shipit.github(organization: repository_owner)` — i.e., it verifies the payload was signed by the org named in `payload['repository']['owner']['login']`, which for the attacker is `attacker`. This proves authenticity of *who sent the payload*, not that the `sha` field actually belongs to that repository.

`StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha`, with no `stacks` or repository filter at all. Compare this to sibling handlers which correctly scope via `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-34, `Repository.from_github_repo_name(repository_name)&.stacks`):
- `PushHandler#process` uses `stacks.not_archived.where(branch:)`.
- `CheckSuiteHandler#process` uses `stacks.where(branch: ...)` before touching commits.

`StatusHandler` is the outlier that never calls `stacks`/`repository_name`.

`Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (app/models/shipit/status.rb:24-33) does `find_or_create_by!(stack_id:, state:, ...)` — it writes the status using the *victim's* `stack_id` (taken from the matched `Commit`), not the attacker's. This mutates a victim tenant's `Commit`, marking it e.g. `success`, purely because the attacker independently produced/copied a commit with an identical sha and emitted a signed status event from their own, unrelated, attacker-owned repository.

None of the existing guards prevent this: `verify_signature` authenticates the sending org for the payload's own named repository, not the sha's ownership; the `ExplicitParameters` schema in `StatusHandler.params` only validates types/presence of `sha`, `state`, etc., with no repository binding; there is no `Repository` or `Stack` validation that ties a `sha` to a single owning repo (git shas are content-addressed and can be identical across independent repositories, e.g. shared history/forks/cherry-picks/empty commits with same tree+parents+timestamp).

### Impact Explanation
Any GitHub status event (`success`/`failure`/`error`/`pending`) sent from an attacker-controlled repository for a sha that also exists in a victim's tracked `Commit` history writes a `Status` row into the victim's `Commit`, potentially flipping `Commit#status`/`deployable?` to `success`. Since `deployable?` and CI-gating (`stack.ignore_ci?`, `blocking_statuses`, `schedule_continuous_delivery`) key off `Status`, this can enable an unauthorized deploy/merge decision on a victim stack triggered from a completely unrelated, attacker-owned repository — a cross-repository/cross-tenant write, matching the "Critical - a payload for one repository mutating another's stack, commit ... or an unauthorized deploy" category.

### Likelihood Explanation
Preconditions: the victim stack must already contain a `Commit` row with the exact same sha as one the attacker can generate signed events for. Since git SHAs are derived purely from tree contents, parent shas, author/committer identity and timestamps (not from the repository URL), an attacker can reproduce an identical sha in their own repo by copying an existing public/forked commit (git fetch/cherry-pick preserving parents and timestamps, or reusing an identical empty-tree commit) — this requires no privileged access, no secrets, and is entirely achievable by "any GitHub user who can push to a fork." The attacker only needs to own one repo registered with a Shipit-known GitHub org/app installation to pass `verify_signature`, and GitHub will deliver signed `status` webhooks for any repo it owns. This is a low-cost, repeatable attack against any victim commit whose sha the attacker can reconstruct.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the verified payload's repository, analogous to other handlers:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `repository_name == commit.stack.repository.full_name` before any `Status` write occurs.

### Proof of Concept
Minitest integration test (webhook controller / handler test) — pseudocode:
```ruby
test "status webhook for unrelated repository does not mutate victim commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")

  attacker_repo_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'attacker' } }
  }

  # signed with attacker org's own webhook_secret, verify_signature passes
  post shipit.github_authenticated_webhooks_path,
       params: attacker_repo_payload.to_json,
       headers: signed_headers_for('attacker', attacker_repo_payload.to_json)

  victim_commit.reload
  assert_empty victim_commit.statuses, "attacker-controlled repo must not be able to create a Status on victim's commit"
end
```
Both sides of the binding to assert: `payload['repository']['full_name']` (`attacker/evil`) vs. `victim_commit.stack.repository.full_name` (`shipit/shipit` or victim's real repo) — before the fix these mutate the same `Commit` despite mismatching; after applying the recommended `stacks`-scoped fix, `victim_commit.statuses` stays empty since `attacker/evil` has no matching `Stack`.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
