## Analysis

The Sherlock finding describes a process (liquidation) that becomes permanently stuck when a required piece of externally-supplied data (an oracle-signed price) fails to arrive within the process's built-in time window, with no code path to recover or restart, resulting in permanently frozen user funds.

The closest reachable analog in `ocore` is the `data_feed[[...]]` mechanism used by Autonomous Agents, which is exactly the pattern the official reference AA templates rely on for time/oracle-gated fund release, and which has no fallback release path if the oracle never posts. [1](#0-0) [2](#0-1) 

### Title
AA funds can be permanently frozen when a required `data_feed` value is never posted by the oracle, with no fallback release path - (File: formula/evaluation.js, test/samples/futures_contract.oscript)

### Summary
An AA whose payout logic gates a payment behind `data_feed[[...]]` (asking for an oracle-posted exchange rate/outcome) has no way to release the deposited funds if the oracle never posts the requested feed value. Any trigger sender who deposited funds into such an AA before the maturity condition is met has no alternative branch to reclaim funds, because `data_feed` aborts (bounces) the whole response when the value is absent, and the message/case selection logic in the AA (as in the official `futures_contract.oscript` / `option_contract.oscript` templates) provides no other case that becomes `true` if the oracle stays silent.

### Finding Description
In `formula/evaluation.js`, the `data_feed` operator calls `dataFeeds.readDataFeedValue(...)` and, when no matching feed exists, invokes the `ifnone` handling; if `ifnone` is not `abort`-safe or absent, it calls `cb("data feed " + feed_name + " not found")`, which propagates as a fatal error and bounces the AA response: [3](#0-2) 

The official reference templates for time-locked financial AAs (futures and option contracts) encode exactly this pattern: after the maturity `timestamp`, the only success branch requires `data_feed[[oracles=..., feed_name='GBYTE_USD_MA_2019_04_30']]` (or `GBYTE_USD`) to resolve; the comment even acknowledges "`data_feed` will abort if the exchange rate not posted yet": [4](#0-3) [5](#0-4) 

Unlike the audited Solidity code, there is no protocol-level timeout mechanism, no alternate "expired -> refund" case, and no way for the AA trigger sender to force resolution if the designated oracle address stops posting `GBYTE_USD`/`GBYTE_USD_MA` (or any custom feed name) forever. The AA holds the deposited bytes in its balance with no reachable message case that can spend them out, since every case's `if` condition either requires the never-arriving feed value or requires state variables (`var['winner']`, `var['blackswan']`) that are themselves gated by the same feed.

This mirrors the reported bug class precisely: a protocol-level construct (here, `data_feed`/`in_data_feed` evaluation used by AA payout logic) depends on a single external party (the oracle) posting data, and the fund-holding logic has no time-bound fallback that lets depositors recover funds if that data never arrives.

### Impact Explanation
If the designated oracle stops publishing the specific `feed_name` referenced by an AA (due to going offline, being decommissioned, or simply never being economically incentivized to publish, similar to the "no economic incentive for the liquidator" scenario in the original report), all bytes and derived assets (`usd_asset`, `gb_asset`, `yes_asset`, `no_asset`) held by that AA become permanently unspendable. Users who deposited funds to obtain these assets, and users still holding the assets, lose access to the underlying value forever — a direct instance of "AA fund loss or freezing."

### Likelihood Explanation
This is not a hypothetical edge case: it is the literal, documented behavior of Obyte's own reference AA templates for futures and option contracts, meaning any developer copying this officially-provided pattern (or any AA relying on `data_feed` to gate a maturity/settlement payout without a hard expiry+refund branch) inherits this risk. Any oracle downtime, decommissioning, or lack of incentive to keep posting after the relevant date is sufficient to trigger permanent freezing — no malicious actor is required.

### Recommendation
- Add a hard-expiry fallback branch to templates (and encourage/require it in AA design guidance) that allows depositors to reclaim funds if `timestamp` exceeds a "final" deadline and the required `data_feed` value has still not been posted, instead of relying solely on `data_feed[[...]]` succeeding.
- Consider adding an `ifnone` parameter usage recommendation/lint warning in AA validation tooling (`definition.js` / `formula/evaluation.js` consumers) when `data_feed` is used without a corresponding `ifnone` or timeout/refund case, to reduce the chance that funds get irrecoverably locked in AAs that follow this exact reference pattern.

### Proof of Concept
1. Deploy `futures_contract.oscript` as-is (or a close variant) as an AA.
2. Trigger `define_usd`/`define_gb` to create `usd_asset` and `gb_asset`.
3. Send ≥1e5 bytes to the AA to mint `usd_asset`/`gb_asset` (case 2), so the AA now holds real byte value.
4. Let time pass beyond `1556668800` (maturity) without the oracle `X55IWSNMHNDUIYKICDW3EOYAWHRUKANP` ever posting `GBYTE_USD_MA_2019_04_30`, and without a blackswan condition being met (`GBYTE_USD_MA` staying ≥ 25 or oracle silent on that feed too).
5. Attempt to redeem `usd_asset`/`gb_asset` back to bytes via case 4 (`{trigger.output[[asset!=base]]...}`): the `else` branch executes `data_feed[[oracles=..., feed_name='GBYTE_USD_MA_2019_04_30']]`, which aborts because the feed was never posted, bouncing every redemption attempt.
6. The bytes deposited in step 3 remain permanently locked in the AA balance, with no other case able to release them.
