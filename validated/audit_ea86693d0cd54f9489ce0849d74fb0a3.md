### Title
Webhook signature verification is keyed to an attacker-controlled organization field that is never bound to the repository the event actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate a webhook against using `repository_owner`, a value read directly out of the unauthenticated JSON body [1](#0-0) , [2](#0-1) . In a multi-organization Shipit deployment (supported via `secrets.github` keyed by org, see `Shipit.github_app_config`), each org can have its own `webhook_secret`, and that secret is optional — if it is blank, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, i.e. no signature is required at all for that org [3](#0-2) . This exactly matches the required bug class from the prompt: "an organization that authenticated versus the repository that is written."

### Finding Description
The verification step and the event-processing step consume two *different* fields of the same attacker-supplied JSON payload, with no cross-check that they agree:

- Verification binds to `params.dig('repository','owner','login')` (fallback `organization.login`) purely to pick a `GitHubApp` config/secret [2](#0-1) .
- Once `head(422)` isn't triggered, `create` re-parses the same raw body and dispatches to handlers [4](#0-3) .
- Handlers such as `PushHandler` resolve the target `Stack`/`Repository` using `payload.dig('repository', 'full_name')` — a completely separate field, never checked against `repository_owner` used in the verification step [5](#0-4) , [6](#0-5) .
- `Repository.from_github_repo_name` splits `full_name` into `owner/name` and does a straight DB lookup, with no relationship enforced to the `GitHubApp` organization that was used to verify the request [7](#0-6) .

Since a legitimate GitHub-generated webhook always has `repository.owner.login` and `repository.full_name` pointing at the same repo, this divergence is normally impossible. But because the webhook endpoint is unauthenticated by design (protected only by the HMAC check) and the entire JSON body is attacker-supplied on the wire, an attacker can deliberately desynchronize these two fields: set `repository.owner.login` (and/or `organization.login`) to an organization that is configured in Shipit with a **blank `webhook_secret`** (a supported, documented configuration — see the `OrgTwo` fixture with `webhook_secret: # nil` [8](#0-7) ), while setting `repository.full_name` (and any other repository identifiers consumed by handlers) to point at a **different, sensitive** organization's repository that does have a `webhook_secret` configured.

Because `verify_webhook_signature` short-circuits to `true` when the *resolved* org's secret is blank [9](#0-8) , the request sails through `verify_signature` without needing any valid HMAC at all. The subsequent handler then acts on `repository.full_name`, which the attacker set to the victim org's repo, triggering `stack.sync_github` for that Stack [10](#0-9) , or archiving/unarchiving review stacks, updating commit statuses, capturing PR labels, or manipulating team memberships for the target org, depending on the event type — all without ever supplying a valid signature for the org that actually owns the affected repository/stack.

### Impact Explanation
This crosses the "cross-repository writes" bar for a valid Critical-tier analog per the rules: an attacker with no credentials can forge webhook events (push syncs, review-stack archive/unarchive, commit-status writes, PR label captures, team/membership churn) against a repository belonging to an organization whose webhook secret they never possessed, merely by knowing (or guessing) that *some other* configured org in the same Shipit instance has no `webhook_secret` set. The equality that should hold — "the organization whose signature authenticated this request" == "the organization that owns the repository being written to" — is never enforced; only the former is checked, and the latter is taken from a sibling field of the same untrusted payload.

### Likelihood Explanation
This requires (a) a multi-org Shipit deployment (documented and tested via `secrets_double_github_app.yml`), and (b) at least one configured org with no `webhook_secret`. The setup docs explicitly mark `webhook_secret` as "(optional)" [11](#0-10) , so this is not a misconfiguration edge case but a supported, encouraged-as-simple configuration. Any operator running Shipit for several GitHub orgs, where even one org's webhook secret is left unset (e.g., a low-stakes staging org), exposes every other org's repositories to this cross-org forgery. No authentication, token, or network position is needed — only knowledge of the target's `full_name` and any second org name that is unsecured.

### Recommendation
Bind the verified organization to the object being acted upon: after `verify_signature` succeeds, require that `repository_owner` (or `organization.login`) used for verification equals the owner portion of `repository.full_name` before dispatching to handlers, and reject (422) on mismatch. Additionally, consider making `webhook_secret` mandatory for all configured GitHub Apps (or at minimum, refuse silently-permissive verification once more than one organization is configured), so a per-org opt-out of signature checking cannot be leveraged to bypass verification for a different org's payload content.

### Proof of Concept
1. Deploy Shipit configured with two orgs, e.g. `OrgOne` (has `webhook_secret` set, owns a protected stack `orgone/critical-service`) and `OrgTwo` (configured but `webhook_secret` left blank), mirroring the fixture at `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any junk value), and a JSON body where:
   - `organization.login` / `repository.owner.login` = `"OrgTwo"` (so `Shipit.github(organization: "OrgTwo")` resolves the blank-secret app),
   - `repository.full_name` = `"orgone/critical-service"`,
   - `ref` = `"refs/heads/master"`, `after` = attacker-chosen SHA.
3. `verify_signature` calls `Shipit.github(organization: "OrgTwo").verify_webhook_signature(...)`, which returns `true` unconditionally because `OrgTwo`'s `webhook_secret` is blank [9](#0-8) .
4. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("orgone/critical-service")` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgOne`'s protected stack [10](#0-9) , despite the attacker never possessing `OrgOne`'s `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
