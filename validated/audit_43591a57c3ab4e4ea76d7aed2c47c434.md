## Analysis

The Sherlock report describes a griefing pattern: a payment function trusts an external allow/deny list (USDC blacklist) controlled by a third party, and if the intended recipient gets excluded from that list, the transfer permanently reverts with no fallback, freezing funds meant for that specific address.

The `ocore` analog to a third‑party‑controlled allow list is the `spender_attested` asset feature, where an asset definer designates a set of `attestors` who must publicly attest an address before that address is allowed to receive (or spend) the asset. This attestor list can be changed by the definer at any time via an `asset_attestors` message, and validation strictly enforces it on every payment's output addresses.

### Where the enforcement lives

`validatePayment` requires that if an asset has `spender_attested` set, all *input* (spending) authors must be attested: [1](#0-0) 

More importantly for output/recipient freezing, `validatePaymentInputsAndOutputs` additionally requires **every output address** to be attested before the payment is considered valid: [2](#0-1) 

The attestor list itself is fully controlled by the asset's `definer_address`, who can add or remove attestors (and thus indirectly de‑attest any address) at will via the `asset_attestors` message: [3](#0-2) 

`filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` are what actually determine, at validation time, whether a given address is currently on the "allow list": [4](#0-3) 

### AA (vault-like) reachability

An Autonomous Agent that acts as a vault/exchange for a `spender_attested` asset (tracking user balances in AA state and paying out on a withdrawal trigger) composes its payout message the same way any payment is composed, then goes through the same asset/attestation lookups before sending: [5](#0-4) 

If any output address fails the attestation check, unit composition/validation fails and the AA `bounce()`s the trigger. Crucially, `bounce()` only refunds whatever was attached to the *current* triggering unit (`trigger.outputs`); it has no way to return balances that were already deposited into the AA's internal state in earlier transactions: [6](#0-5) 

## Title
Attestor (allow-list) revocation on a `spender_attested` asset permanently freezes an address's funds held by an AA vault - (File: `validation.js`, `aa_composer.js`)

### Summary
An asset with `spender_attested: true` requires every output address of a payment to be currently attested by one of the asset's attestors, a list fully controlled by the asset's definer. An AA that custodies such an asset for users (e.g., a vault/exchange AA tracking per-user balances in state variables and paying out on a withdrawal trigger) is vulnerable to the same "blacklist" griefing class described in the external report: if the definer/attestor de-attests (or never (re-)attests) a specific user's address after that user has deposited funds, every future withdrawal payout to that address will fail asset validation and the AA's trigger will bounce, with no mechanism to redirect the payout to a different address or otherwise release the trapped balance.

### Finding Description
- `validatePaymentInputsAndOutputs` enforces `storage.filterAttestedAddresses` against **all output addresses** of a `spender_attested` asset payment, rejecting the unit if any output address is not currently attested [2](#0-1) .
- The attestor list for the asset is unilaterally controlled by `objAsset.definer_address`, who can publish a new `asset_attestors` message at any time to add or drop attestors (and thereby drop attested addresses) [3](#0-2) .
- When an AA composes an outgoing payment in such an asset (e.g. a vault paying out a user's tracked balance on withdrawal), it loads the current attested-address list and will fail to build the unit if the recipient is not attested, causing `bounce(err)` [5](#0-4) .
- `bounce()` only returns whatever base/asset amounts were attached to the *current* trigger unit; it has no path to refund balances that live in the AA's persistent state (`var[...]`) from prior deposits [6](#0-5) .
- Because the state-update formula for a bounced trigger is rolled back, the internal accounting decrement for the withdrawal never happens either, so the balance stays recorded in the AA — but every subsequent withdrawal attempt from that address will bounce the same way for as long as the address remains un-attested. There is no code path in `ocore` allowing the AA (or the user) to redirect payment of a `spender_attested` asset to an alternate address on the fly.

### Impact Explanation
Any AA holding balances of a `spender_attested` asset for multiple users is exposed to permanent freezing of an individual user's funds whenever the asset's definer/attestors revoke that user's attestation — intentionally (targeted griefing/censorship) or inadvertently (attestor list rotation). Because attestation is external to the AA's own logic and can change at any block, an AA author cannot fully defend against it purely in oscript without adding an explicit alternate-address/rescue mechanism, and most vault-style AAs written against `spender_attested` assets do not anticipate this. This matches "AA fund loss or freezing" impact criteria.

### Likelihood Explanation
Requires (1) an AA that custodies a `spender_attested` asset with per-address internal accounting and (2) the asset's definer/attestor to change the attestor list to exclude a specific depositor's address after they have deposited. Both conditions are realistic: `spender_attested` is a documented, supported asset feature intended for exactly this kind of compliance/whitelisting control, and attestor list updates are a normal, unrestricted, single-signature operation available to the definer at any time. No special privileges beyond being the asset's definer (a role any user can create for themselves, or convince integrators to use) are needed to trigger the freeze against a chosen victim address.

### Recommendation
- AA authors building custodial/vault logic on top of `spender_attested` assets should provide an explicit "change payout address" / rescue path that lets a depositor supply an alternative, currently-attested address to receive their tracked balance, rather than hard-coding `trigger.address` as the sole payout destination.
- Consider adding a getter/message in vault-style AA templates to snapshot attestation status at deposit time and warn against relying on the definer/attestor's continued cooperation, or documenting this systemic risk prominently for `spender_attested` asset integrators.

### Proof of Concept
1. Definer publishes an asset `X` with `spender_attested: true` and an initial attestor list `A1`.
2. `A1` attests address `U` (the depositor).
3. AA `V` implements a vault: on receiving `X` from `U`, it credits `var['balance_' || trigger.address]` with the deposited amount (a payment message with `spender_attested` asset only checks the *sender's* attestation at deposit time, per `validatePayment`, see [1](#0-0) ).
4. Definer publishes a new `asset_attestors` message dropping `U`'s attestation (e.g., replacing `A1` with a list that no longer attests `U`), which is unrestricted per `validateAttestorListUpdate` [3](#0-2) .
5. `U` sends a withdrawal trigger to `V` requesting payout of `var['balance_' || trigger.address]` in asset `X` to `trigger.address` (`U`).
6. `V`'s `sendUnit` attempts to compose the payment; `storage.loadAssetWithListOfAttestedAuthors` shows `U` is no longer attested, `completePaymentPayload`/output-address attestation check fails, and the trigger bounces [5](#0-4) ; [2](#0-1) .
7. Because bounce only refunds the current trigger's attached outputs (not the previously credited `var['balance_' || trigger.address]`), `U`'s tracked balance inside `V` remains permanently unreachable as long as `U` stays un-attested — indefinitely, at the definer's discretion.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
