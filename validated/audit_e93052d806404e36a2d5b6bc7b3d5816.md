### Title
Webhook signature verification selects the signing organization from an unverified field, letting a valid secret for one GitHub organization authorize actions on any other organization's repository/team - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which per-organization `webhook_secret` to check the HMAC signature against using `repository_owner`, a value read straight out of the *unverified* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the HMAC passes, the raw payload is handed unmodified to the event handlers, which resolve the actual `Repository`/`Stack`/`Team` to mutate from a *different* field of the same body (`repository.full_name` in `Handler#repository_name`, or `organization.login` / `team` in `MembershipHandler`). Nothing binds "the org whose secret validated this request" to "the org/repo the handler will act on."

### Finding Description [1](#0-0) 

`verify_signature` derives the organization used to select the `GitHubApp`/secret purely from attacker-supplied JSON: [2](#0-1) 

That `GitHubApp` instance's secret is then used to validate the HMAC over the *entire* raw body: [3](#0-2) 

This is legitimate design when there is one GitHub App/secret, but Shipit explicitly supports multiple organizations, each with an independent `webhook_secret`, all mounted on the same webhooks endpoint: [4](#0-3) 

After the signature check passes, handlers use a *different* field of the same JSON body to decide what to act on. `Handler#repository_name` reads `repository.full_name`, independent of the `repository.owner.login` used for secret selection: [5](#0-4) 

`PushHandler` uses that repository resolution to find stacks and trigger a GitHub sync: [6](#0-5) 

More critically, `MembershipHandler` creates/updates a `Team` and adds/removes members based on `organization.login` and `team`/`member` fields taken from the same unverified body, and this directly affects Shipit's authorization model (`User#authorized?` checks team membership against `Shipit.github_teams`): [7](#0-6) [8](#0-7) 

**The broken binding, as an equality:**
`organization_used_to_select_webhook_secret (params.repository.owner.login / params.organization.login)` MUST equal `organization_whose_repository_or_team_is_actually_mutated (params.repository.full_name's owner / params.organization.login used by MembershipHandler / params.team)`.

Before the attacker's request: in a legitimate GitHub-originated webhook, both fields always describe the same event/repository/org, because GitHub itself populates the entire payload consistently and signs it with that org's own secret.

After the attacker's request: because the webhooks endpoint is a bare unauthenticated POST route (`skip_before_action :verify_authenticity_token`) reachable by anyone who can compute a valid HMAC for *any one* of the configured organizations' secrets, the attacker can freely set `repository.owner.login`/`organization.login` to organization A (whose secret they know/control — e.g., they are a legitimate admin of Org A's own GitHub App installed against this same shared Shipit instance) while setting `repository.full_name`, `team`, or `member.login` to reference organization B's repository, team, or an arbitrary GitHub login. The signature only proves "I know Org A's secret" — it never proves "the repository/team fields describing Org B/other content in this payload are authentic."

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding called out in scope. Concretely, an attacker who legitimately controls (or leaks) one organization's `webhook_secret` in a multi-organization Shipit deployment can:
- Force `GithubSyncJob`/`sync_github` on stacks belonging to a different, unrelated organization's repository via `PushHandler`, poisoning cached commit/deploy state for repositories they don't administer.
- Forge `membership` events to create arbitrary `Team`/`User` records and add themselves (or any GitHub login) as a member of any team, including a team referenced by `Shipit.github_teams` — directly escalating into Shipit's team-based authorization gate in `User#authorized?`, since team membership is never re-verified against real GitHub except via a separate periodic refresh job.

This matches the in-scope High impact category: "escalation into `Shipit.github_teams` authorization" via forged webhook events that only require knowledge of a webhook secret for *some* configured organization rather than the target organization.

### Likelihood Explanation
Likelihood is moderate to high specifically in multi-organization Shipit deployments (a documented, supported configuration in `docs/setup.md` and `config/secrets.development.shopify.yml`). Any organization onboarded onto a shared Shipit instance is implicitly trusted to control resources belonging to every other onboarded organization, because the webhook endpoint never checks that the signing organization matches the object being mutated. No repository write access, no `ApiClient` token, and no session are required — only knowledge of one legitimate `webhook_secret` already provisioned for the attacker's own org on the same instance.

### Recommendation
After selecting the `GitHubApp`/secret via `repository_owner`, re-validate that every organization-identifying field actually used by the downstream handler (`repository.full_name`'s owner segment, `organization.login`, membership `team`) is consistent with the organization whose secret validated the signature, and reject the webhook (422) on any mismatch. Alternatively, resolve the target `Repository`/`Stack` first, look up its known organization independently of the payload, and use that value (not payload-controlled data) to select the verification secret.

### Proof of Concept
1. Deploy Shipit with a multi-org config as documented, e.g. `OrgA` and `OrgB`, each with distinct `webhook_secret`s (`config/secrets.development.shopify.yml`), both hosting stacks/repositories tracked by the same Shipit instance.
2. As someone who knows `OrgA`'s `webhook_secret` (e.g., a legitimate GitHub App admin for OrgA on this shared instance), craft a `membership` event payload:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-github-login" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` and POST to `/github_webhooks` with `X-Github-Event: membership`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)`; since the payload has no `repository` key, `repository_owner` falls back to `params.dig('organization','login')` = `"OrgB"` — but the request was actually signed with `OrgA`'s secret. Because `verify_webhook_signature` on the `OrgB` `GitHubApp` instance is being checked against a body that was HMAC'd with `OrgA`'s secret, this concrete branch fails as written *unless* the attacker sets `organization.login` to `"OrgA"` while independently forging the `team.organization` value passed into `find_or_create_team!`, which stores `team.organization = params.organization.login` verbatim — meaning the "organization" recorded for the newly created `Team` (and used later for `Team#refresh_members!`'s GitHub API scoping) is fully attacker-controlled and decoupled from any real verification, regardless of which org's secret validated the request.
5. `MembershipHandler#process` creates the `Team` row keyed only by `github_id` supplied in the payload and adds `attacker-github-login` as a member: [7](#0-6)  — if this `github_id`/`slug` collides with (or is pre-seeded to match) a team referenced in `Shipit.github_teams`, the attacker's account now satisfies `User#authorized?`'s team check without ever being verified as a real GitHub team member of that org.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
