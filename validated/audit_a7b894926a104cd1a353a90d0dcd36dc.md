## Analysis

The compound-share bug class described in the report is about a value that is *trusted implicitly* to always match a particular invariant, when in fact an attacker can manipulate the untrusted side of that invariant to break the security check downstream. The closest reachable analog in this engine is in the webhook signature verification flow, where the **field used to select/authenticate the signing secret** and the **field used by the event handlers to decide what repository/stack to act on** are the *same untrusted, attacker-controlled JSON body*, with no cross-check between them.

### Root cause [1](#0-0) 

`WebhooksController#verify_signature` picks *which* GitHub App/organization's `webhook_secret` to validate the incoming signature against using `repository_owner`, which is read straight out of the **unverified** request body: [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` then resolves to a `GitHubApp` instance whose `webhook_secret` is per-organization, as configured in `secrets.yml` for multi-org installs: [3](#0-2) [4](#0-3) [5](#0-4) 

The signature check only proves that *some* known `webhook_secret` (selected by an attacker-controlled field inside the very payload being verified) matches the payload's HMAC. It does **not** prove that the organization owning that secret is the same organization whose repository/commit/PR data the downstream handlers subsequently act on (`params.dig('repository', ...)`, `sha`, `full_name`, etc., consumed by handlers such as the push/status/PR handlers referenced in `app/models/shipit/webhooks/handlers/**`).

### The broken binding

`organization authenticated by webhook_secret` == `organization/repository whose Stack/Commit/PR records get mutated by the handler`

Both sides of this equality are derived from the **same single untrusted JSON body** the attacker controls, so nothing forces them to agree. An attacker who legitimately administers **any** GitHub organization onboarded to this Shipit instance (and therefore knows that organization's `webhook_secret`, since app owners configure it themselves) can:

1. Craft an arbitrary webhook JSON payload (e.g., `push`, `status`, `check_suite`, `pull_request`) whose top-level `repository.owner.login` (or `organization.login`) is set to **their own** organization — this is the value `verify_signature` uses to select the secret, so the HMAC they compute with their own known secret verifies successfully.
2. Populate the rest of the payload (`repository.full_name`, `sha`, PR data, etc.) with values belonging to a **completely different** stack/repository tracked by the same Shipit instance.
3. Because `verify_signature` never checks that the `repository_owner` used to pick the secret matches the repository being described elsewhere in the payload, the forged event is accepted and dispatched to `Shipit::Webhooks.for_event(event)` handlers, which act on the attacker-chosen repository data.

This lets an attacker who only controls their own low-privilege organization's webhook forge status/push/PR events for arbitrary other repositories hosted on the same shared Shipit instance — a cross-repository write, matching the specified High/Critical impact bar.

### Recommendation
`WebhooksController#verify_signature` should re-derive the organization strictly from data that can be authenticated independently of the payload content used for the HMAC (e.g. bind the secret lookup to a per-endpoint/per-org webhook URL instead of a payload field), or, at minimum, after verifying the signature, assert that the `repository`/`organization` fields used by the handlers belong to the same organization whose secret validated the signature, rejecting the request otherwise.

### Proof of Concept (conceptual)
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC using AttackerOrg's known webhook_secret>

{
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": {
     "owner": { "login": "AttackerOrg" },   // used only to select the verifying secret
     "full_name": "VictimOrg/victim-repo"   // used by the handler to locate the Stack/Commit
  }
}
```
`verify_signature` succeeds (secret for `AttackerOrg` matches), but the `status` handler updates `VictimOrg/victim-repo`'s commit/CI status, which can unblock or trigger deploys for a stack the attacker never had access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
