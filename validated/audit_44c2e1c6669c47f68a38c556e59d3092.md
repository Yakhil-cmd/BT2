## Finding: `CCMenuController#stack` bypasses ApiClient stack-scoping, allowing cross-stack reads

### Title
Stack-scoped API token can read any stack's build status via the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The bug-class from the external report — a value checked at one point (quorum computed against a fixed reference) diverging from the value actually acted upon at execution time — maps in shipit-engine to a broken binding between **the stack(s) an `ApiClient` token is authorized for** and **the stack it is actually allowed to touch**. `Api::BaseController` enforces this binding centrally, but `Api::CCMenuController` re-implements stack resolution and skips it.

### Finding Description
`Api::BaseController` defines the authoritative, scope-respecting stack lookup: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the `ApiClient` is scoped to a single stack; otherwise, any stack. Every other API controller that needs a stack (e.g. deploys, tasks, hooks) inherits `stack` from `BaseController`, so a token bound to stack A can never resolve `params[:stack_id] = B`.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It resolves the stack via `Stack.from_param!(params[:stack_id])` directly against the `Stack` model, ignoring `current_api_client.stack_id`. Authentication is still performed through the same generic mechanism (query-string token or HTTP Basic, both accepting any valid `ApiClient`): [3](#0-2) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` *permission string* — it never checks that the requested stack matches the token's authorized `stack_id`: [4](#0-3) 

Stack-scoped `ApiClient`s are a normal, documented feature (fixture example): [5](#0-4) 

**Binding broken:** `token.stack == requested_stack` is enforced in `BaseController#stack` but not in `CCMenuController#stack`. Before the request: the token's authorized stack set is `{A}`. After hitting `GET /api/stacks/B/ccmenu`: the controller reads and renders data for stack `B ∉ {A}`.

### Impact Explanation
An attacker holding any valid `ApiClient` credential that is scoped to a single stack (e.g. `here_come_the_walrus`, permission `read:stack`, `stack: shipit`) can query `GET /api/stacks/<other-stack>/ccmenu` and obtain that other stack's name, last build status/label/time, and web URL — data the token was never authorized to see: [6](#0-5) 

This is an unauthorized cross-repository/cross-stack read of deploy/task state, matching the in-scope "unauthorized read of stack state ... " impact category. It does not require possessing the target stack's own secret — only any valid, less-privileged `ApiClient` token.

### Likelihood Explanation
High. Any organization operating multiple stacks and issuing narrowly-scoped `ApiClient` tokens (a documented, intended use case per the fixtures and `stacks` scoping logic) is exposed. Exploitation requires only a single unprivileged, stack-scoped credential and one HTTP GET to a predictable route (`GET /api/stacks/:stack_id/ccmenu`), no privileged access or session.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the inherited `stacks.from_param!(params[:stack_id])`) so that CCMenu lookups are subject to the same `current_api_client.stack_id` scoping enforced everywhere else in `Api::BaseController`.

### Proof of Concept
1. Create two stacks, `org/repo-a` and `org/repo-b`.
2. Create an `ApiClient` scoped to `repo-a` only, with permission `read:stack` (mirrors fixture `here_come_the_walrus`).
3. Authenticate with that token and request:
   `GET /api/stacks/org/repo-b/ccmenu?token=<token>`
4. The response returns `repo-b`'s build status/name/URL via `shipit/ccmenu/project.xml`, even though the token is only authorized for `repo-a`.
   Compare with any other scoped endpoint (e.g. `GET /api/stacks/org/repo-b`), which is correctly rejected with 404/`stacks.from_param!` scoping via `Api::BaseController#stack`.
