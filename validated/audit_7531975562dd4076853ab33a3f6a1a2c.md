### Title
Unvalidated `creator` account in `initialize_with_permission` permanently freezes accumulated creator fees - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` accepts `creator` as an `UncheckedAccount` with no ownership, signer, or non-default-address requirement, and stores it directly as `pool_state.pool_creator`. If a pool is created with `creator` set to the system program ID or `Pubkey::default()` (an address that has no corresponding keypair), all creator fees ever accrued by that pool become permanently unclaimable, since both fee-collection paths depend on that stored address being either a valid signer or a valid ATA owner that can later move funds.

### Finding Description
In `Initialize` (regular pool creation), `creator` is a `Signer<'info>` [1](#0-0) , which practically prevents it from being the zero/default address because no one can produce a valid signature for it.

In `InitializeWithPermission`, however, `creator` is declared as an `UncheckedAccount` with only a `CHECK: creator of pool` comment and no constraint at all: [2](#0-1) . It is never required to sign, never checked against `Pubkey::default()`, and never checked to be owned by any particular program. This value is passed straight into `pool_state.initialize(...)` as the pool's `pool_creator` field: [3](#0-2) .

Once `pool_creator` is set to an address nobody controls (e.g. `11111111111111111111111111111111` or the all-zero pubkey), the fees that accumulate for the creator in `pool_state.creator_fees_token_0` / `creator_fees_token_1` become permanently stuck:

- `collect_creator_fee` requires `creator` to be a `Signer` whose key equals `pool_state.load()?.pool_creator`: [4](#0-3) . No one can produce a signature for the system-program address or the zero address, so this path can never succeed.
- `collect_creator_fee_permissionless` lets anyone trigger the transfer, but the destination ATA's authority is fixed to `pool_state.pool_creator`: [5](#0-4) [6](#0-5) . This only moves the tokens into an ATA owned by an uncontrollable address — it does not return them to anyone able to spend them, it merely relocates the frozen funds from the pool vault into an equally inaccessible ATA.

Because the accompanying `permission` PDA check in `InitializeWithPermission` only gates who may act as `payer` (i.e., who may create the pool) [7](#0-6) , it does not constrain the `creator` field at all — any permissioned payer can set `creator` to an arbitrary, uncontrolled address in a single transaction.

### Impact Explanation
Any creator fee that accrues on a pool created via `initialize_with_permission` with a bad `creator` address (e.g. `Pubkey::default()`/system program) is permanently and irrecoverably frozen — no admin, owner, or protocol-level function can move `pool_state.creator_fees_token_0/1` out because both collection instructions are hard-gated on `pool_state.pool_creator`. This is a permanent freezing of LP/creator funds accumulated inside the pool.

### Likelihood Explanation
The precondition is a single call to `initialize_with_permission` by any account already holding a `permission` PDA (created by admin via `create_permission_pda`), which is an attacker/creator-chosen, single-transaction action requiring no privileged signer beyond what the feature is explicitly designed to allow untrusted pool creators to do. The `creator` field is entirely attacker-controlled data with zero validation, so triggering the freeze is trivial once a permission PDA exists — this can also happen accidentally due to a client/integration bug that passes a wrong/default pubkey.

### Recommendation
Add an explicit constraint in `InitializeWithPermission` requiring `creator.key() != Pubkey::default()` (and ideally reject known non-signable system addresses), mirroring the "fail early" fix pattern from the referenced report. Consider also validating that `creator` is not one of the reserved program IDs (System Program, Token Program, etc.) that can never sign a transaction.

### Proof of Concept
1. Attacker/creator obtains (or already has) a `Permission` PDA for their `payer` pubkey via `create_permission_pda`.
2. Attacker calls `initialize_with_permission` with `creator = Pubkey::default()` (or `11111111111111111111111111111111`), a valid `amm_config`, and legitimate token mints/vault seeds — all other constraints in `InitializeWithPermission` are satisfiable by any caller with token balances.
3. `pool_state.initialize(...)` stores `pool_creator = Pubkey::default()` [3](#0-2) .
4. Normal swaps against this pool accrue `creator_fees_token_0`/`creator_fees_token_1` in `PoolState`.
5. Any attempt to call `collect_creator_fee` fails permanently because no signer can match `pool_creator == Pubkey::default()` [4](#0-3) .
6. Calling `collect_creator_fee_permissionless` merely moves the fees into an ATA owned by `Pubkey::default()`, which likewise has no controlling keypair to later withdraw the tokens [6](#0-5)  — funds remain frozen indefinitely.
