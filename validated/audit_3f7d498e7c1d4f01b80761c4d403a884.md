### Title
Attacker-named route venues graft arbitrary token transfers into the victim's signed auth tree, stealing unrelated wallet funds - ([File: contracts/swap-aggregator/src/venues/mod.rs])

### Summary
The swap router dispatches each hop to whatever pool/token contract addresses the `swap_xdr` payload names, with no venue allowlist. Any third-party contract invoked inside a hop runs below the caller's `require_auth` entry, and a token transfer it makes from the caller is recorded as a child of that entry in the simulated auth tree. A victim who signs a controller strategy (`swap_collateral`, `multiply`, `swap_debt`, `repay_debt_with_collateral`) or a direct `execute_strategy` carrying an attacker-supplied route therefore authorizes the rogue pool to drain unrelated tokens from their wallet — the analog of WesHacks embedding a link to attacker-controlled injected JavaScript.

### Finding Description
The external report's bug class is "project code embeds a reference to attacker-controlled external content that executes malicious code in the user's trust context." In XOXNO Lending the corresponding shape is the payload-named venue call. `dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs:23-40` invokes whichever pool address the payload's `assets` registry names; the router "keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-165`). The controller's `swap_tokens` (`contracts/controller/src/strategies/swap.rs:34-38`) authorizes only the exact input transfer, but that grant does not constrain what the malicious hop contract does once on the stack: a rogue pool can call `token.transfer(victim, attacker, amount)` on any wallet token, which the host attaches to the victim's own authorization entry. The test harness demonstrates this end-to-end: `RogueHopPool::swap` transfers the victim's unrelated wallet token to the attacker when invoked as a hop pool inside `swap_collateral` (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-71,111-125`).

### Impact Explanation
Theft of user funds exceeding the routed amount. Neither the router's `min_out` check nor the controller's `RouterOverspend`/`NoSwapOutput` and final health-factor gates bound the theft: the rogue transfer targets a token the protocol never listed, paid straight from the victim's wallet, while the swap itself can still deliver a fair output and pass every measured-delta and risk check (`contracts/controller/src/strategies/swap.rs:41-54`). The threat model states the bound directly: "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md:159-161`).

### Likelihood Explanation
An unprivileged attacker deploys a malicious pool contract and gets its route bytes in front of the victim (phishing quote, malicious frontend, tampered `routeXdr`) — the same user-interaction vector as the CVE (CVSS UI:R). Exploitation needs the victim to sign an auth tree that contains the grafted child transfer; the protocol's own mitigation is externalized to clients ("a client must decode the route it signs and refuse an authorization tree with any other child"), so any signer that trusts simulated auth without decoding the payload is exposed. Severity: High.

### Recommendation
Enforce an on-chain venue/pool allowlist in the router (e.g., governance-curated pool registry consulted by `dispatch_hop`), or constrain hop calls to adapters pinned to known pool implementations rather than arbitrary payload addresses. At minimum, the controller and router SDKs should refuse auth trees with children beyond the single expected input transfer, as the threat model already prescribes for clients.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:1-165`: registers `UnlistedPoolRouter`/`RogueHopPool`, gives Alice 77 770 units of an unlisted wallet token, routes `swap_collateral(USDC → ETH)` through the rogue pool, and the pool's `swap` executes `token.transfer(alice, attacker, amount)` inside the hop. In enforcing mode the call succeeds exactly when Alice's signature covers the grafted child transfer — demonstrating wallet theft via an attacker-named venue.
