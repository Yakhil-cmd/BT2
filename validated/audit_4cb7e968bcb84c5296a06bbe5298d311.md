### Title
Delimiter-less legacy contract-hash construction in `arbiter_contract.getHashSrc` allows hash/signature collision between different contract terms - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` builds the cryptographic commitment (`contract.hash`) that binds a peer-to-peer arbiter contract offer/acceptance/dispute to its substantive terms (title, text, creation date, party names, arbiter, amount, asset). For contracts whose `creation_date` is not strictly after `NEW_HASH_DATE` ('2026-11-01') — which is **every contract created today, 2026-09-15, and for the next ~1.5 months** — the hash source is built by simply joining the fields with an **empty string** (`.join("")`), with no delimiter separating adjacent free-text fields. This is structurally the same defect as the reported Permit2 `witnessTypeString` bug: the digest that is supposed to uniquely and completely commit to the contract's structured data is ambiguous about field boundaries, so different sets of field values can produce an identical digest.

### Finding Description [1](#0-0) 

```js
function getHashSrc(contract) {
	...
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
```

The "new" branch at least joins with a dedicated `exports.DELIMITER = "[|#|]"` (still user-controllable text could embed the delimiter itself, but that's a secondary concern). The "old" branch — which is the **default/active** branch for any contract created on or before `2026-11-01` (i.e., right now) — joins with `""`. `contract.title` and `contract.text` are fully attacker-controlled free-text strings supplied by whichever peer initiates the offer (`createAndSend`), with no length or content restriction preventing them from containing arbitrary substrings.

Because the join has no separator, the string `title + text` is exactly the same whether the peer sends `title="AB", text="C"` or `title="A", text="BC"`. This is unlike the properly-typed `object_hash.getSourceString`/`getJsonSourceString` used elsewhere in the codebase for unit/definition/device-message hashing, which always type-prefix and null-separate every field (see [2](#0-1)  and [3](#0-2) ) precisely to avoid this class of ambiguity. `getHashSrc` bypasses that safe, generic hashing infrastructure and hand-rolls a bespoke, under-specified serialization — the exact root cause pattern flagged in the Permit2 report (a hand-written "typestring"/serialization that doesn't fully and unambiguously bind all the struct's semantic content).

This hash is trusted as an integrity commitment in multiple places:
- Peer-to-peer offer validation: `body.hash !== arbiter_contract.getHash(body)` in the `arbiter_contract_offer` device-message handler [4](#0-3) .
- On-chain binding via `contract_text_hash` embedded in a DAG "data" message tied to the shared multisig address [5](#0-4) .
- Arbiter dispute resolution, where the arbiter/arbstore recomputes `expectedContractHash` from decrypted contract content plus dispute-request fields and trusts it if it matches `body.contract_hash` [6](#0-5) .

### Impact Explanation
Because two different sets of (title, text, party names) can produce an identical `contract.hash`, a dishonest counterparty in an arbiter contract can:
1. Present the honest peer with an offer whose `title`/`text` split hides a different actual meaning than what the recomputed hash would suggest to the arbiter/arbstore later (field-boundary shifting attack), or
2. Later invoke `arbiter_dispute_request` with a substituted `contractContent`/`title`/`text` split that still satisfies `expectedContractHash === body.contract_hash` even though the substantive content differs from what the counterpart actually reviewed and (indirectly) agreed to via the same-looking hash.

Since the arbiter's dispute decision determines how the shared-address escrow funds are released (payer vs payee), a party that can make the arbiter operate on manipulated contract text while passing the hash check can bias or falsify the basis for the arbiter's fund-release decision, resulting in unauthorized diversion of escrowed funds.

### Likelihood Explanation
The vulnerable branch is not a legacy/rare fallback — it is the **default, active behavior today** (2026-09-15 < `NEW_HASH_DATE` = 2026-11-01), so every arbiter contract created right now uses the collision-prone `join("")` construction. No node, hub, or network-level compromise is needed: the attack is purely between the two contracting peers (and the arbiter), squarely within "wallet and contract message handling" reachable by any paired device / private counterparty. Constructing colliding strings from free-text `title`/`text` fields (and pairwise-swappable `payer_name`/`payee_name`) is straightforward string manipulation with no cryptographic difficulty.

### Recommendation
Replace the ad hoc string concatenation in `getHashSrc`'s legacy branch with an unambiguous, self-describing encoding — e.g., always use `exports.DELIMITER` (or better, reuse `object_hash.getSourceString`/`getJsonSourceString`, which type-prefix and separate every field, exactly as already done for units, definitions, and device messages) for both branches, regardless of `creation_date`. If backward compatibility for already-existing hashes is required, restrict the legacy branch to read-only verification of pre-existing contracts and force all newly created contracts (regardless of date) onto the safe, delimiter-based/generic hashing scheme immediately rather than gating it on a future cutover date.

### Proof of Concept
1. Peer A crafts two offers with identical `creation_date`, `arbiter_address`, `amount`, `asset`, `payer_name`/`payee_name`, but:
   - Offer 1: `title = "Loan of 100"`, `text = "USD due in 30 days"`
   - Offer 2: `title = "Loan of 100USD"`, `text = "due in 30 days"`
   Both produce identical `getHashSrc` output (`"Loan of 100" + "USD due in 30 days"` === `"Loan of 100USD" + "due in 30 days"`), hence identical `contract.hash`.
2. Peer A sends Offer 1 to Peer B via `arbiter_contract_offer`; Peer B accepts and signs, with the shared address and on-chain `contract_text_hash` bound to this common hash [5](#0-4) .
3. Later, during a dispute, Peer A submits `arbiter_dispute_request` with `contractContent` corresponding to Offer 2's title/text split; `expectedContractHash` still equals `body.contract_hash` [6](#0-5) , so the check at [7](#0-6)  passes even though the arbiter is now reviewing different contract text than what Peer B actually agreed to, potentially skewing the arbiter's fund-release decision.
