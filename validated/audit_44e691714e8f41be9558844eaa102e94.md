### Title
`ReopenedHandler#unarchive?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors, provisioning review stacks on disabled repos when combined with an unauthenticated (secret-less) webhook - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler#unarchive?` uses `a && b || c || d` where Ruby's operator precedence causes `review_stacks_enabled` to gate only the `allow_all` branch, not the `allow_with_label` or `prevent_with_label` branches. When combined with `GitHubApp#verify_webhook_signature` accepting any payload for an organization configured with a blank `webhook_secret`, an unprivileged attacker can forge a `pull_request` `action=reopened` webhook that provisions a `ReviewStack` for a repository whose administrator explicitly disabled review stacks.

### Finding Description
The intended invariant is: **for any repository R, if `R.review_stacks_enabled == false`, then `ReopenedHandler#unarchive?` must return `false` regardless of `provisioning_behavior`.**

The actual code is: [1](#0-0) 

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` is only ANDed into the first disjunct. If `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, the method can return `true` even when `review_stacks_enabled == false`, breaking the stated invariant. `process` then calls `stack.unarchive!` unconditionally when `respond_to_pull_request_reopened?` is true: [2](#0-1) 

This handler is reachable from the unauthenticated `POST /webhooks` endpoint once `Shipit::WebhooksController#verify_signature` passes: [3](#0-2) 

`verify_signature` resolves the `GitHubApp` for `repository.owner.login` from the forged payload and delegates to `verify_webhook_signature`: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If the organization's config entry has no `webhook_secret` set (`@webhook_secret = @config[:webhook_secret].presence`, which is `nil`/blank), `verify_webhook_signature` returns `true` unconditionally — no HMAC check is performed at all — so an attacker with zero secrets can submit an arbitrary JSON body for that organization.

**Exploit flow:** Precondition — Shipit is configured with the multi-org `github:` schema and at least one configured organization has no `webhook_secret` (an existing, documented fallback for backward compatibility, per `docs/setup.md`'s "Using Multiple GitHub Applications" section). The victim repository belongs to that organization, has `review_stacks_enabled = false`, and `provisioning_behavior` set to `prevent_with_label` (a very plausible admin choice: "block review stacks by default, unless our own team applies a label"). The attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request`, a forged body `{"action":"reopened","number":N,"pull_request":{...,"head":{"ref":<attacker-controlled branch>,"sha":<attacker-controlled sha>},"labels":[]},"repository":{"full_name":"<victim-org>/<victim-repo>"},"sender":{...}}` with no matching label. `verify_signature` passes trivially (no secret configured). `ReopenedHandler#unarchive?` evaluates `(false && prevent_with_label?) || (false && has_label) || (true && !false)` → `true`, and `stack.unarchive!` runs, moving an archived (or newly built) `ReviewStack` back into `deprovisioned`/`awaiting_provision` state despite the repository administrator's explicit `review_stacks_enabled = false` setting — confirmed by the existing test suite's `assert_pending_provision` helper used for the `allow_with_label`/`prevent_with_label` cases, none of which set `review_stacks_enabled` to `false`, so this divergence is untested: [5](#0-4) [6](#0-5) 

No other guard intercepts this: `drop_unhandled_event` only checks the event type is handled, `ExplicitParameters` (the `params do ... end` schema) only validates shape/types, not authorization; and `Repository#review_stacks_enabled` is never re-checked outside `unarchive?`.

### Impact Explanation
This causes a `ReviewStack` provisioning task (`ReviewStackProvisioningQueue`/`ProvisioningHandler::Base`) to run for a repository whose administrator disabled review-stack auto-provisioning specifically to avoid untrusted code execution from external PRs. Provisioning ultimately runs the repository's `shipit.yml`/deploy tasks against the attacker-supplied branch/SHA via `Command`/`PTY.spawn`, which is the RCE-class path this audit targets — although I could not fully trace `ProvisioningHandler::Base`/`ReviewStackProvisioningQueue` internals within the remaining tool budget to confirm exactly which commands execute and whether any additional CI-status or file-content gating exists before task execution. The write is scoped to the exact repository named in the forged payload (matched via `Repository.from_github_repo_name(params.repository.full_name)`), so it does not cross into unrelated organizations' stacks, but it does violate that specific repository's own `review_stacks_enabled = false` configuration — a control the admin relied on. Repeatable on every request against any repository under a secret-less organization that uses `allow_with_label`/`prevent_with_label`.

### Likelihood Explanation
Requires: (1) Shipit configured with the documented multi-org `github:` schema where at least one org has no `webhook_secret` (an accepted, documented fallback, not itself a code defect), and (2) a victim repository in that org with `review_stacks_enabled = false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`. Given precondition (1), the attacker's cost is a single unauthenticated HTTP POST with a fully forged JSON body — no GitHub account interaction is even required since the request never touches real GitHub. This is fully repeatable and requires no elevated privileges.

### Recommendation
Fix the operator-precedence bug in `unarchive?` by explicitly parenthesizing so `review_stacks_enabled` gates all three provisioning behaviors:
```ruby
def unarchive?
  repository.review_stacks_enabled? && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Separately (out of scope of this specific handler but relevant), consider requiring `webhook_secret` to be present for every configured organization in the multi-org schema, or at minimum warn/refuse to boot when it's missing, to close the signature-bypass precondition this exploit chain relies on.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb (new test)
test "does NOT unarchive/provision stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :prevent_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = [] # attacker sends no label

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # Binding under test:
  # repository.review_stacks_enabled (false) must equal
  # whether unarchive? actually ran (stack.archived?)
  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Before the fix, `unarchive?` returns `true` and this assertion fails (`stack.archived?` becomes `false`), proving the divergence between the declared `review_stacks_enabled = false` and the actual provisioning behavior.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
