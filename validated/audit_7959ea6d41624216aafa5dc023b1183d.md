### Title
Unhandled throw in `countVotes()` can permanently halt main-chain stabilization - (File: main_chain.js)

### Summary
`main_chain.js`'s `countVotes()` is invoked unconditionally as part of MC stabilization whenever a subject is queued in `voteCountSubjects` for a just-stabilized MCI [1](#0-0) . Several branches inside it end in a bare `throw Error(...)` rather than a recoverable callback error, mirroring the external report's root cause pattern: a core, permissionlessly-triggerable path (`propose()` → `getPastVotes()`) that unconditionally reverts under conditions the system itself can produce, blocking essential functionality for every participant.

### Finding Description
`countVotes(conn, mci, subject, ...)` is executed as part of `advanceMcStability`'s per-MCI post-processing, once for each subject accumulated in `voteCountSubjects`, right before `updateRetrievable()`/commission calculation/AA-trigger processing continue [2](#0-1) .

For the `op_list` subject, after tallying `op_votes` balances into `op_rows` (ordered by balance, `LIMIT constants.COUNT_WITNESSES`), the code does:
```
if (ops.length !== constants.COUNT_WITNESSES)
    throw Error(`wrong number of voted OPs: ` + ops.length);
``` [3](#0-2) 

For numerical subjects (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`), if no row satisfies the median-accumulation condition, the function again throws:
```
if (value === undefined)
    throw Error(`no median value for ` + subject);
``` [4](#0-3) 

And an unrecognized subject also throws:
```
default:
    throw Error("unknown subject in countVotes: " + subject);
``` [5](#0-4) 

`ops.length` is bounded by the number of *distinct* `op_address` values that received votes within the dynamically-expanding `since_timestamp` window [6](#0-5) [7](#0-6) . If fewer than `constants.COUNT_WITNESSES` distinct addresses have been voted for in that window (e.g., sparse voting, or votes concentrated on already-fewer than 12 candidates), `ops.length` will be less than `COUNT_WITNESSES` and the function throws unconditionally — there is no fallback or graceful degradation. The same applies to the numerical-subject median calculation: if the voter set's balances/timestamps do not produce a satisfying accumulation, `value` stays `undefined` and the function throws.

Because `countVotes` is `await`ed directly inside `advanceMcStability`'s stabilization sequence with no surrounding `try/catch` visible in the reviewed code path, an uncaught exception here would propagate out of the MC-stabilization routine that every full node executes identically once the relevant MCI becomes stable. Since all nodes evaluate the same deterministic vote data for the same MCI, the crash/exception is not a per-node quirk — it reproduces on every node reaching that MCI, which is functionally equivalent to the reported governance bug: the code "cannot be" successfully executed once a specific (attacker- or organically-reachable) state is hit, permanently blocking a core protocol operation (main-chain stabilization progressing) for the whole network.

### Impact Explanation
If triggered, this uncaught throw occurs inside the core MC-stabilization pipeline that runs on every node for every newly-stable MCI. An exception here would abort processing of that MCI's stabilization on all nodes simultaneously (since the vote tallies are derived from consensus data, not local state), which matches the "network unable to confirm new units" impact category: the DAG cannot advance past the affected MCI, since_timestamp/vote-count logic will re-throw identically on retry, and the deterministic nature of the calculation means there's no divergent-node workaround — this is a full network liveness failure, not a single-node crash.

### Likelihood Explanation
`op_list`/numerical system votes are cast via ordinary, permissionless `system_vote` unit messages, and vote-count triggering (`system_vote_count`) is itself an ordinary application message type validated/composed like other message apps (present in `validation.js`, `composer.js`, `writer.js`). This means any address can cast (or withhold) votes such that, by the time a `system_vote_count` unit becomes stable, the aggregated `op_votes`/`numerical_votes` data yields fewer than `COUNT_WITNESSES` distinct candidates or an unsatisfiable median — a state reachable by ordinary usage patterns (e.g., an early/thin-voting period, or votes deliberately split across few candidates) without needing any privileged access. I was not able to fully trace the exact validation constraints in `validation.js` on `system_vote`/`system_vote_count` payloads (subject whitelist, minimum voters, etc.) within the available tool budget, so I cannot rule out that some of these edge conditions are pre-filtered elsewhere; this should be verified directly against `validation.js`'s `system_vote`/`system_vote_count` handling before treating likelihood as certain.

### Recommendation
Replace the bare `throw Error(...)` calls in `countVotes()` (lines ~1862, ~1901, ~1906) with defensive handling that cannot halt consensus: e.g., skip updating `system_vars` for that subject/MCI when the vote data is insufficient (falling back to the previous value), and log a warning instead of throwing. Ensure `countVotes()` is called within a `try/catch` in `advanceMcStability` regardless, so that any unexpected error is converted into a well-defined consensus rule rather than an uncaught exception that halts the node.

### Proof of Concept
1. Cast `op_votes` (via `system_vote` units) for fewer than `constants.COUNT_WITNESSES` distinct `op_address` values (or such that only a subset accumulate sufficient balance to appear within the `since_timestamp` window) prior to a `system_vote_count` unit for subject `op_list` becoming stable.
2. When `advanceMcStability` processes the MCI at which this vote count runs, `countVotes()` computes `op_rows`/`ops` with `ops.length < constants.COUNT_WITNESSES`.
3. `main_chain.js:1861-1862` throws `Error("wrong number of voted OPs: " + ops.length)`, which is unhandled in the calling stabilization sequence, aborting MC stabilization for that MCI on every node that reaches it. [8](#0-7)
