### Title
Stale delegation snapshot in partitioned epoch-reward distribution can trigger a consistency-assertion panic when an unprivileged staker splits/merges/withdraws their stake between reward calculation and reward payout - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
The bug report describes a classic "claim vs. transfer" race: a value-bearing state transition (claiming rewards) is computed from data captured at one point in time, but is applied later against the live/current state, and an intervening state-changing action by an unprivileged party (a normal transfer/trade) desynchronizes the two. In agave, the structural analog is the multi-block **partitioned epoch rewards** pipeline: stake rewards are *calculated* once from a stake-account snapshot, but *distributed* (credited) in later blocks by re-reading the stake account from the live `StakesCache`, and the distribution code asserts that the two must still agree.

### Finding Description
Reward calculation happens once per epoch boundary via `calculate_stake_rewards_and_commissions`, which snapshots each delegated stake account and produces a `PartitionedStakeReward` containing a `stake` (the delegation state including `delegation.stake`) as it existed at calculation time [1](#0-0) .

Distribution of these rewards is spread across up to `num_partitions` subsequent blocks. On each distribution block, `store_stake_accounts_in_partition` re-fetches the account from the **live** `stakes_cache` (not the calculation-time snapshot) and calls `build_updated_stake_reward` [2](#0-1) .

Inside `build_updated_stake_reward`, when the `relax_post_exec_min_balance_check` ("adjust_delegations_for_rent") feature is not active, the code computes `expected_delegation` from the **freshly loaded live stake** plus the previously computed `stake_reward`, and asserts it must equal `new_stake.delegation.stake`, which comes from the **stale, calculation-time** `partitioned_stake_reward.inflation.stake`: [3](#0-2) 

If the stake authority performs an ordinary, unprivileged stake-program instruction (`Split`, `Merge`, `Withdraw`, `Deactivate`) on that account between the calculation block and its assigned distribution block, the live delegation amount diverges from the value baked into the stale `PartitionedStakeReward`, and `expected_delegation != new_stake.delegation.stake` — triggering the `assert_eq!` panic at distribution time [4](#0-3) .

There is a `recalculate_partitioned_rewards_if_active` path intended to keep the partitioned rewards consistent with the current `StakesCache` (used, per its doc comment, when the bank recomputes rewards mid-distribution) [5](#0-4) , and its own comment flags that downstream commission accounting derived from it "should NOT be used ever" because it can't reflect intermediate account mutations correctly [6](#0-5) . I was not able to fully confirm from the available index whether `recalculate_partitioned_rewards_if_active` is invoked unconditionally on every new bank in the normal (non-fork) block-production path, or only on specific events such as bank-forking/reprocessing; this is a gap in verification given the tool budget, and would need to be checked directly against `runtime/src/bank.rs` call sites before treating this as a confirmed, always-reachable bug versus one that only manifests in specific fork-replay scenarios.

### Impact Explanation
If reachable, the `assert_eq!` panic in `build_updated_stake_reward` fires deterministically for every validator processing the same block containing the mismatched stake account, because reward calculation/distribution is part of consensus-critical bank state transition. A deterministic panic hit by all validators simultaneously constitutes an epoch-boundary chain halt, which is one of the explicitly in-scope impact categories (rather than a single-node crash).

### Likelihood Explanation
Likelihood depends entirely on whether `recalculate_partitioned_rewards_if_active` is invoked on the normal per-block path to keep the distribution state in sync with any legitimate stake-account mutation (Split/Merge/Withdraw) that lands during the multi-block distribution window. If it is not called on every block, any unprivileged staker can trivially trigger the divergence by issuing a normal `Split`/`Merge`/`Withdraw` instruction on their own stake account during the reward-distribution window that follows every epoch boundary — a window that spans many blocks for larger validator sets. This does not require any special privilege, mempool front-running, or timing precision beyond "act before your account's assigned partition index is processed."

### Recommendation
Verify all call sites of `recalculate_partitioned_rewards_if_active` in `runtime/src/bank.rs` and confirm it (or an equivalent resync) executes on every block during an active distribution, for every fork, not just specific recovery paths. If it does not, either (a) recompute/resync the `stake_reward`'s embedded delegation from the live `StakesCache` immediately before applying it in `build_updated_stake_reward` instead of asserting equality, or (b) replace the `assert_eq!` with a graceful `Err(DistributionError::...)` path (mirroring the existing `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState` handling) so a stale/mutated delegation degrades to a burned/skipped reward rather than panicking the whole validator.

### Proof of Concept
Conceptual reproduction (not fully verified against the exact runtime call graph in this session):
1. At an epoch boundary, an account with the `relax_post_exec_min_balance_check` feature inactive earns a nonzero stake reward; `calculate_stake_rewards_and_commissions` snapshots `stake.delegation.stake = X` into `PartitionedStakeReward.inflation.stake`.
2. Before this account's assigned partition/distribution block is processed (there can be many intervening blocks for a large validator set), the stake authority submits an ordinary `Split` (or `Merge`/`Withdraw`) instruction that changes the live `StakesCache` delegation to `X' != X`.
3. On the distribution block for that partition, `store_stake_accounts_in_partition` → `build_updated_stake_reward` loads the *live* account (delegation `X'`), computes `expected_delegation = X' + stake_reward`, but compares it against `new_stake.delegation.stake` taken from the *stale* snapshot (`X + stake_reward`), per [4](#0-3) .
4. The `assert_eq!` fails, panicking bank processing for every validator that reaches this block, consistent with the deterministic panic being an epoch-boundary halt.

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }
