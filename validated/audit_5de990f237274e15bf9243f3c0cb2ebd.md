### Title
Webhook signature verification key is selected from an unauthenticated field that differs from the field event handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / `webhook_secret` used to validate the HMAC signature from a value taken directly out of the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`), before that signature has been checked. But the code path that actually acts on the event — `Handler#stacks`/`Handler#repository_name` used by e.g. `PushHandler` — reads a *different* field of the same unverified body, `repository.full_name`, to decide which `Stack` gets mutated (triggering `stack.sync_github`). This is the same class of bug as the Napier report: a value trusted as "ground truth" for a security decision (which secret authenticates the request) is not the same value that determines what gets written (which repository/stack is acted upon), and both values come from the same untrusted input.

### Finding Description
`verify_signature` computes the org used to select the webhook secret purely from payload contents: [1](#0-0) [2](#0-1) 

The actual authorization decision — whether the signature is checked at all — is delegated to `GitHubApp#verify_webhook_signature`, which short-circuits to `true` whenever the selected app config has no `webhook_secret` set: [3](#0-2) 

Multi-organization Shipit deployments are an explicitly documented/supported configuration, where each organization has its own independent `webhook_secret` entry (some of which can legitimately be left blank, as shown in the sample config files): [4](#0-3) 

Once (or if) the request passes `verify_signature`, `WebhooksController#create` dispatches the *entire raw payload* to the registered handler for the event type: [5](#0-4) 

Handlers such as `PushHandler` never re-derive or cross-check the organization/owner used for signature verification. They independently pull `repository.full_name` out of the same payload to find the `Stack`(s) to mutate: [6](#0-5) [7](#0-6) 

So the binding that should hold is:
`organization used to authenticate the request (repository.owner.login / organization.login)` == `organization/repository actually written to (repository.full_name)`.

Nothing in the engine enforces this equality. Both are read from the same attacker-supplied JSON body, and they are read in two unrelated code paths (controller vs. handler) that never compare notes. For a Shipit instance configured for multiple organizations where at least one configured organization has no `webhook_secret` (a state the shipped example config files actively demonstrate as normal/expected), an unauthenticated caller can:

1. Set `repository.owner.login` (or `organization.login`) to the name of the organization that has no `webhook_secret` configured — `verify_webhook_signature` returns `true` unconditionally for that org, regardless of the `X-Hub-Signature` header sent.
2. Set `repository.full_name` (and other event-specific fields) inside the same JSON body to point at a completely different, victim organization/repository that *does* have real stacks configured in this Shipit instance.
3. Because the handler layer only ever looks at `repository.full_name` (never at the org used for step 1), the forged event is processed as if it were a legitimate webhook for the victim repository.

### Impact Explanation
Depending on which event/handler is targeted, this crosses the "unauthenticated read/write of stack state" boundary called out as accepted High impact (unauthenticated triggering of `GithubSyncJob`, forged `status`/`commit_status`, forged `check_suite`, forged `membership` events, etc., for a stack the attacker does not control and for which they hold no GitHub credentials). It does not on its own grant `GITHUB_TOKEN`/RCE, but it does let an unauthenticated party manufacture state-changing GitHub events (e.g., forcing sync attempts, fabricating commit statuses, or team/membership changes) against arbitrary repositories tracked by the instance, as long as the instance has ≥2 configured GitHub orgs and at least one of them lacks a `webhook_secret`.

### Likelihood Explanation
This requires a specific, but not exotic, deployment shape: multi-organization Shipit configuration with a mix of secured and unsecured (`webhook_secret: nil`) org entries. The shipped example secrets files (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`) show this exact pattern as a supported configuration, and nothing in setup docs warns that leaving one org's `webhook_secret` blank in a multi-org install undermines signature verification for *all* other orgs' repositories. This is a real, reachable design gap rather than a purely theoretical one, though its blast radius is bounded by requiring that specific configuration state (an org entry present with no secret) to exist.

### Recommendation
- Do not let the value used to select the verification key be independent of the value the handler subsequently trusts. After parsing the payload, derive the organization from the same authoritative field the handler will use (`repository.full_name`'s owner segment, or `repository.owner.login` consistently) and verify the signature using that org's secret before any handler processing.
- Remove (or make configuration-time fatal) the `return true unless webhook_secret` short-circuit in `GitHubApp#verify_webhook_signature` for any multi-org configuration; require every configured org to have a non-blank `webhook_secret`, or globally reject payloads whose owner does not match a securely-configured org.
- Add a check in `Handlers::Handler` (or in the controller before dispatch) asserting that `payload.dig('repository','owner','login')` equals the org whose secret validated the request, rejecting mismatches outright.

### Proof of Concept
Given a Shipit instance configured with two orgs in `secrets.yml`:
```yaml
github:
  attacker-org:
    app_id: ...
    webhook_secret:        # left blank
  victim-org:
    app_id: ...
    webhook_secret: "real-secret"
```
An unauthenticated attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`repository_owner` resolves to `attacker-org` [2](#0-1) , `Shipit.github(organization: 'attacker-org')` loads a `GitHubApp` with `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally [3](#0-2) . The request then reaches `PushHandler`, which resolves `repository_name` to `"victim-org/victim-repo"` and calls `stack.sync_github` on every non-archived stack matching that repo/branch [6](#0-5) [7](#0-6)  — despite the attacker never having proven knowledge of `victim-org`'s real webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
