### Title
Webhook signature verification is bound to an attacker-chosen organization while the handlers act on an unrelated repository, allowing HMAC bypass for any org whose secret is unset - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to use for HMAC verification from an unauthenticated payload field, but the event handlers that actually locate and mutate a `Stack`/`Repository` use a *different* payload field that is never cross-checked against the field used for verification. This breaks the "organization authenticated versus repository written" binding.

### Finding Description
`verify_signature` derives the verifying organization purely from the JSON body itself, before any signature check has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login` (or `organization.login`) — both attacker-controlled fields in an unauthenticated POST to the webhooks endpoint.

The resolved `GitHubApp#verify_webhook_signature` trivially returns `true` whenever that organization has no `webhook_secret` configured: [3](#0-2) 

An unset `webhook_secret` is not an error state — it is the documented default in every shipped config template, including the multi-organization example used for exactly this scenario: [4](#0-3) [5](#0-4) 

Meanwhile, once `create` proceeds past this (now-bypassed) check, every event handler resolves the target `Stack` using a **different** field — `repository.full_name` — with no re-validation that it belongs to the organization that was actually used to verify the signature: [6](#0-5) [7](#0-6) 

So the binding "signature verified for organization X" ⇒ "action performed on repository belonging to organization X" does not hold: verification is keyed off `repository.owner.login`, but the mutating logic is keyed off the independent `repository.full_name` field.

### Impact Explanation
In any deployment using the documented multi-organization config (`docs/setup.md`, "Using Multiple Github Applications") where at least one configured organization has no `webhook_secret` (the shipped default), an unauthenticated attacker can:

1. Set `repository.owner.login` (or `organization.login`) to the organization with no `webhook_secret` — signature check passes unconditionally, no valid `X-Hub-Signature` needed.
2. Set `repository.full_name` to `<secured-org>/<real-repo>` — an actual repository backed by a `Stack` under an organization that *does* have a real `webhook_secret`.
3. The handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves that real `Stack`/`Commit` via `full_name` and performs privileged writes, e.g.: [8](#0-7) [9](#0-8) 

`StatusHandler` in particular lets the attacker forge a `state: success` commit status on any commit of the target repository. If that repository relies on required CI statuses to gate deployability/merge (a core Shipit CI-gating feature) or has continuous deployment enabled, this forged status can make an otherwise-blocked commit deployable, producing an unauthorized deploy/merge — entirely bypassing the webhook secret protecting that organization.

### Likelihood Explanation
No credentials, session, or repository write access are required — only an unauthenticated HTTP POST to the public webhooks endpoint. The only precondition is a multi-organization Shipit installation where one configured organization has no `webhook_secret`, which is exactly the state shown by every shipped configuration template (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) and by the documented multi-org setup guide.

### Recommendation
Verify the webhook signature against the organization that actually owns the resolved `repository.full_name`/target `Stack`, not the organization named in `repository.owner.login`/`organization.login`. Alternatively, require a non-blank `webhook_secret` for every configured organization (fail closed rather than `return true unless webhook_secret`), and reject any payload whose `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
Given a Shipit deployment configured with two GitHub orgs as in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne` has a real `webhook_secret`, `OrgTwo` has none):

```
POST /webhooks
X-Github-Event: status
(no X-Hub-Signature header required)

{
  "sha": "<sha-of-a-commit-on-OrgOne/critical-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/critical-repo"
  }
}
```

- `verify_signature` calls `Shipit.github(organization: "OrgTwo")`, whose `verify_webhook_signature` returns `true` unconditionally because `OrgTwo`'s `webhook_secret` is nil.
- `StatusHandler#process` finds the commit via `Commit.where(sha: params.sha)` (scoped to `OrgOne/critical-repo` through its `Stack`) and calls `commit.create_status_from_github!(params)`, forging a passing status for a repository actually protected by `OrgOne`'s (unused) webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
