### Title
Attacker-controlled commit message spoofs commit authorship via `Merge-Requested-By:` field - ([File: app/models/shipit/user.rb])

### Summary
`Shipit::User.find_or_create_author_from_github_commit` trusts a `Merge-Requested-By: <login>` marker embedded in the raw commit message body to determine `Commit#author`, with no verification that the named login actually authored or requested the merge. Any GitHub user who can get a commit message onto a stack's tracked branch (e.g. via a PR whose commit text is preserved through a squash-merge) can force `Commit.last.author` to resolve to an arbitrary existing `Shipit::User`.

### Finding Description
Binding claimed broken: `Commit#author == the GitHub identity that actually authored/committed the code`. Actual code: [1](#0-0) 

`Commit.from_github` calls this method directly when materializing commits fetched from GitHub during a sync: [2](#0-1) 

The regex source is `MergeRequest::MERGE_REQUEST_FIELD` (`"Merge-Requested-By"`), the same string Shipit itself writes into merge commit messages when `MergeRequest#merge!` performs a GitHub merge: [3](#0-2) 

but `find_or_create_author_from_github_commit` has no way to distinguish a commit message produced by Shipit's own trusted merge flow from one crafted by an external contributor. The commit message is arbitrary text supplied by whoever authored the git commit (or PR description) — nothing about `verify_signature`/`GitHubApp#verify_webhook_signature` in `WebhooksController` authenticates the *content* of a commit message; it only authenticates that the HTTP payload came from GitHub for the configured organization/app: [4](#0-3) 

`PushHandler#process` triggers a full `sync_github` for any stack tracking the pushed branch once the webhook signature is valid: [5](#0-4) 

Exploit flow: an attacker opens a pull request against the tracked repository and includes a commit whose message body contains a line `Merge-Requested-By: victim-login`. If the PR is merged with the "squash and merge" GitHub option (which by default concatenates the constituent commit messages into the squashed commit), the malicious line survives into the commit that lands on the tracked branch. GitHub then sends a legitimately-signed `push` webhook; `PushHandler` syncs the branch, `Commit.from_github` runs, the regex matches, and `find_or_create_by_login!('victim-login')` is invoked, permanently recording the victim as `Commit#author` for a commit they never wrote.

### Impact Explanation
This causes commit (and by extension deploy) provenance to be forged: `Commit#author` is used throughout the UI/audit trail (e.g., `stacks_contributed_to`, `repositories_contributed_to`) to attribute code changes and deploy responsibility to a Shipit user. An attacker can make it appear that an arbitrary existing GitHub/Shipit user authored code they never touched, which can be used to falsely implicate a victim in a deploy, evade personal accountability, or (if any downstream authorization/notification logic keys off commit author) influence who is credited or blamed. The attack is repeatable against any tracked repository where a maintainer performs a squash-merge without scrubbing the resulting commit message.

### Likelihood Explanation
Preconditions: the target repository must be tracked by an existing Shipit stack, and the malicious commit text must actually survive into the commit that lands on the tracked branch — this normally requires a maintainer to merge the attacker's PR (commonly via squash-merge, which preserves original commit messages by default). The attacker does not need any Shipit credentials, GitHub org membership, or write access to the tracked repo directly; they only need PR-contribution ability plus a maintainer performing a routine merge action. This makes the attack moderately likely wherever squash-merge is the default/common workflow, and low-cost to attempt repeatedly.

### Recommendation
Do not derive commit authorship from freeform commit message text. Only apply the `Merge-Requested-By` override when the commit is actually the recorded `merge_commit` of a `MergeRequest` created through Shipit's own `MergeRequest.request_merge!` flow (i.e., trust `merge_request.merge_requested_by`, which is already used in `Commit#identify_merge_request`, rather than re-parsing the message in `User.find_or_create_author_from_github_commit`). Remove or restrict the regex-based lookup in `user.rb` to a context where the message is known to have been generated by Shipit itself, not arbitrary contributor text.

### Proof of Concept
Minitest plan (in `test/models/commits_test.rb` style, not adding it here per instructions, but outlining assertions):
1. Create a `Shipit::Stack` tracking a branch, and a victim `Shipit::User` with `login: 'victim-login'` who has no relation to the test commit.
2. Stub/build a GitHub commit object (`Sawyer::Resource`-like) whose `commit.message` is `"Some innocuous PR title\n\nMerge-Requested-By: victim-login\n"` and whose `author`/`committer` correspond to the attacker's own GitHub account.
3. Call `Shipit::Commit.from_github(github_commit)` (as would happen from `Stack#sync_github` after a `push` webhook).
4. Assert: `commit.author == victim_user` (equal to the victim's `Shipit::User` row) even though `github_commit.author.login` is the attacker's login — demonstrating `Commit#author != actual GitHub committer/author`, breaking the claimed binding.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
