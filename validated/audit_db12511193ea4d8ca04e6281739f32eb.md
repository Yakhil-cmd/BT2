### Title
Crafted swap routes can hide unauthorized wallet transfers inside a victim-signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints accept caller-supplied opaque swap routes and forward them to the configured router without restricting the pool addresses encoded in the route. A malicious venue contract can invoke a token transfer from the victim during route execution, causing Soroban simulation to attach that unrelated wallet transfer beneath the victim’s original controller authorization. If a crafted interface induces the victim to sign the resulting authorization tree, the attacker can steal wallet assets unrelated to the lending operation while the strategy itself still succeeds. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`swap_collateral` authenticates `caller` and checks that the caller owns or delegates the target account, but accepts arbitrary `swap` bytes and passes them into the router call. [5](#0-4)  The same pattern exists in `swap_debt`, `repay_debt_with_collateral`, `multiply`, and its optional `convert_swap`, so multiple user-facing strategy entrypoints can carry the malicious route. [6](#0-5) [7](#0-6) [8](#0-7) 

The controller only constrains its own authorization to one exact input-token transfer to the configured router; it does not inspect the route’s pool addresses or constrain what code executes below the victim’s top-level authorization. [9](#0-8)  The router extracts `hop.pool` directly from the supplied asset list and dispatches it to the selected venue adapter. [3](#0-2)  Venue dispatch measures router input and output deltas, but it does not prevent the invoked pool contract from making additional authorization-requiring calls against the original user. [10](#0-9) 

The repository’s threat model explicitly documents that a route can place third-party code below the caller’s authorization and that a token transfer made by that code is recorded as a child of the caller’s authorization entry. [4](#0-3)  The included regression test demonstrates an attacker pool performing `token.transfer(victim, attacker, amount)` during a `swap_collateral` route and shows that the operation succeeds when the victim signs the poisoned tree. [11](#0-10) [12](#0-11) 

### Impact Explanation
This permits theft of arbitrary token balances held by the victim, including assets not listed by the lending protocol and assets unrelated to the requested collateral swap. The attacker deploys the malicious pool, prepares the route, and causes the victim to sign a transaction whose authorization tree includes the hidden transfer. [13](#0-12)  The stolen amount is bounded by the victim’s token balance and signed authorization tree, not by `amount`, the declared minimum output, account collateral, or final health checks. [4](#0-3) 

### Likelihood Explanation
Exploitation requires user interaction because the victim must sign the authorization tree containing the extra transfer, matching the UI-spoofing bug class. The attack is nevertheless practical because the route is opaque XDR supplied to `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply`, and a wallet or frontend that presents only the high-level lending action can obscure the malicious child authorization. [1](#0-0) [14](#0-13)  The route only needs to satisfy measured swap output and final account risk, so it can behave like a fair swap while simultaneously stealing an unrelated wallet token. [15](#0-14) [16](#0-15) 

### Recommendation
Do not allow arbitrary user-supplied pool addresses inside production routes. Enforce a governance-managed venue/pool allowlist before executing route hops, or replace arbitrary pool addresses with registered pool identifiers that cannot introduce attacker-deployed code. [3](#0-2)  At the client boundary, decode every route and reject any simulated authorization tree containing children other than the expected token input pull for a direct router call, or no user child invocation for controller strategy calls. [4](#0-3) 

### Proof of Concept
1. The victim owns an existing funded account and holds `WALLET_TOKEN`, which need not be a lending asset. [17](#0-16) 
2. The attacker deploys a venue-compatible pool contract whose swap entrypoint performs the expected pool interaction but additionally calls `WALLET_TOKEN.transfer(victim, attacker, amount)`. [18](#0-17) 
3. The attacker encodes a `StrategySwap` naming the malicious contract as the hop pool and gives the victim a `controller.swap_collateral(victim, account_id, USDC, amount, ETH, malicious_swap)` transaction. [1](#0-0) [3](#0-2) 
4. Soroban simulation records the rogue token transfer as a child beneath the victim’s `swap_collateral` authorization. [19](#0-18) 
5. A crafted interface presents the action as an ordinary collateral swap and the victim signs the returned tree. The malicious pool receives `WALLET_TOKEN` while returning enough `ETH` for the router and controller checks to pass. [12](#0-11) 
6. The transaction completes with the attacker holding the victim’s unrelated wallet funds. [20](#0-19)

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)
        .unwrap_or_else(|| panic_with_error!(env, Error::ZeroOutput));
    if received <= 0 {
        panic_with_error!(env, Error::ZeroOutput);
    }

    let after_in = ctx.input_balance();
    let spent = before_in
        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);
    }

    received

    assert_eq!(s.wallet(&s.alice), 0);
