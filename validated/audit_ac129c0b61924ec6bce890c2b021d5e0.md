### Title
Webhook signature verification uses `repository.owner.login` while payload handlers act on the unrelated `repository.full_name`/`commit sha` fields, letting a webhook sender for one GitHub organization forge state for stacks belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/webhook secret validates the HMAC signature by reading `repository.owner.login` (or `organization.login`) out of the attacker-supplied JSON body itself, then verifies the signature against that org's `webhook_secret`. But once the signature check passes, the individual event handlers (`PushHandler`, `StatusHandler`, etc.) resolve the affected `Stack`/`Commit` using a completely different, independently-controlled field: `repository.full_name` (and, for status events, only `sha`). Nothing binds the field used to pick the verifying secret to the field used to pick the victim record.

### Finding Description
`repository_owner` is computed purely from the untrusted payload before the signature is checked, and is used only to look up which org's app/secret to validate against: [1](#0-0) [2](#0-1) 

Once `verify_signature` passes for `organization: repository_owner`, the raw parsed JSON is handed to the registered handlers unchanged: [3](#0-2) 

Every handler resolves the target `Stack` via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a field never used during signature verification and with no cross-check against `repository.owner.login`: [4](#0-3) 

`StatusHandler` goes further and doesn't even use `repository_name`/`full_name` at all — it matches solely on commit `sha` across the entire `Commit` table, and writes a GitHub-originated status onto whatever stack that commit belongs to: [5](#0-4) 

`PushHandler` similarly triggers a `sync_github` for any not-archived stack whose branch matches, scoped only by the attacker-chosen `repository.full_name`: [6](#0-5) 

In a multi-organization Shipit deployment (the config schema explicitly supports per-org `webhook_secret`/`app_id`/`oauth`), `Shipit.github(organization:)` looks up a distinct `GitHubApp`/secret per org key: [7](#0-6) 

This is exactly the binding break called out in scope: **"an organization that authenticated versus the repository that is written."** An attacker who legitimately controls (or administers webhooks for) OrgA — and therefore knows OrgA's `webhook_secret` because they are the one who would configure it when installing Shipit's GitHub App on their own org — can construct an arbitrary JSON body where `repository.owner.login` = `"OrgA"` (so `verify_signature` validates the HMAC using OrgA's secret, which the attacker can compute correctly) while `repository.full_name` refers to `OrgB/victim-repo`, a stack that has nothing to do with OrgA. Since the HMAC covers the whole raw body and the attacker fully controls that body's contents before signing it with their own known secret, this signature is valid per `verify_webhook_signature`: [8](#0-7) 

The `status` handler is the most severe path because it needs no repository match at all — only a `sha`. Commit shas of a victim's public/private repos are frequently discoverable (public repos, PR pages, CI logs, etc.), letting the attacker post fabricated CI `status` entries directly onto a victim stack's tracked commits.

### Impact Explanation
Commit statuses gate whether a commit is deployable via `ci.require`/`ci.blocking` configuration (`Stack#required_statuses`/`blocking_statuses`, delegated from `Commit`): [9](#0-8) 

By forging a `status` webhook event that is validly signed under an organization the attacker administers, but targets a commit sha belonging to a different, victim-owned stack, the attacker can inject fake "success" CI statuses that satisfy `ci.require`, unblocking a deploy that should not be permitted — an unauthorized deploy of code that never actually passed CI. This matches the in-scope Critical impact: **"an unauthorized deploy."** The `push` path similarly allows forcing `sync_github` refresh cycles against arbitrary stacks outside the attacker's org, an integrity/availability effect on a victim's stack sync state.

### Likelihood Explanation
The likelihood is bounded by the requirement that the Shipit deployment be configured with per-organization GitHub Apps/webhook secrets (`Shipit.github_organizations`/`github_app_config`), a documented and supported configuration mode. Any legitimate tenant organization admin — an otherwise unprivileged actor with respect to *other* organizations' stacks — can exploit this without any additional credentials beyond their own org's webhook secret, which they configure themselves. No `ApiClient` token, GitHub App private key, or session is required; only the ability to send an arbitrary POST to `/webhooks` with a body they sign using their own org's known secret.

### Recommendation
After parsing the payload and verifying the signature, re-derive `repository_owner` (or an explicit organization identifier) from the same trusted source used to select the verifying secret, and enforce that every handler's target `Stack`/`Commit`/`Repository` lookup is scoped to that verified organization — e.g., pass the verified `organization` into `Handler.call` and require `Repository#owner` to match it before resolving `stacks`/`commit`, rejecting the event otherwise.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret` values (per `config/secrets.*.yml` schema shown in `template.rb`).
2. As an administrator of `OrgA` (attacker), craft a `status` webhook JSON body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/attacker-repo"},
  "sha": "<sha of a commit belonging to OrgB's tracked stack>",
  "state": "success",
  "context": "ci/circleci",
  "target_url": "https://example.com"
}
```
3. Sign the raw JSON body with `HMAC-SHA1(OrgA_webhook_secret, body)` and send it as `X-Hub-Signature`, with `X-Github-Event: status`, to `POST /webhooks`.
4. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully.
5. `StatusHandler#process` finds `Commit.where(sha: params.sha)` — matching the victim `OrgB` commit — and calls `create_status_from_github!`, injecting a fabricated passing CI status onto a stack the attacker never authenticated against.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
