### Title
Permissionless `initialize` can front-run `initialize_with_permission` for the same pool PDA, permanently locking out the whitelisted creator and creator-fee entitlement - (File: programs/cp-swap/src/instructions/initialize.rs, programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize` (fully permissionless) and `initialize_with_permission` (gated by a `Permission` PDA) both target the exact same deterministic `pool_state` PDA, derived only from `amm_config`, `token_0_mint`, and `token_1_mint` [3](#0-2) . Because `create_pool` can be invoked by anyone and only checks that the PDA is still owned by the System Program before creating it [4](#0-3) , an attacker can front-run a whitelisted market maker's `initialize_with_permission` call by submitting a plain `initialize` for the same mint pair first.

### Finding Description
`initialize_with_permission` is meant to let an approved `Permission`-holding `payer` create a pool with `enable_creator_fee = true` and a `pool_creator` set to a chosen `creator` account [5](#0-4) . `initialize` is the open, permissionless path that always sets `enable_creator_fee = false` and `pool_creator = creator` (the arbitrary caller) [6](#0-5) .

Since the `pool_state`, `token_0_vault`, `token_1_vault`, `lp_mint`, and `observation_state` PDAs for both instructions are derived from the identical seed set (`amm_config`, `token_0_mint`, `token_1_mint`) [3](#0-2) , and `create_pool` is reachable by any signer with no `Permission` check inside `initialize` itself, an attacker who observes an intended `initialize_with_permission` transaction in the mempool (or simply predicts a popular pair being onboarded) can submit `initialize` first for the same `(amm_config, token_0_mint, token_1_mint)` triple. Once the PDA is created and owned by the program, the subsequent legitimate `initialize_with_permission` call for the same pair fails permanently, since `create_pool`'s `pool_account_info.owner != &system_program::ID` check rejects re-initialization [7](#0-6) , and `#[account(init, ...)]` on `lp_mint`/`observation_state` would also fail on the already-initialized derived accounts.

This exactly mirrors the report's bug class: an unprivileged actor can call an unauthorized/less-restricted creation path to claim a resource address that a privileged flow was going to use exclusively, permanently DoS-ing the privileged flow (`setGaugeAndPositionManager`'s once-only guard ↔ `create_pool`'s owner-based once-only guard).

### Impact Explanation
The attacker permanently prevents the whitelisted/`Permission`-gated creator from ever initializing that specific (config, token0, token1) pool via `initialize_with_permission`. Since `pool_creator` and `enable_creator_fee` are set once at `initialize` time and never updated elsewhere (only read by `collect_creator_fee` / `collect_creator_fee_permissionless` via `pool_state.load()?.pool_creator` [8](#0-7) [9](#0-8) ), the attacker becomes the permanent `pool_creator` and `enable_creator_fee` is permanently stuck at `false` for that mint pair/config, denying the intended whitelisted party any creator-fee entitlement for that pool — an insolvent/misallocated fee-ledger outcome and an unauthorized privileged effect (attacker gains the `pool_creator` role reserved for `Permission` holders).

### Likelihood Explanation
High: the attack requires only a single permissionless `initialize` transaction with deterministic, publicly-derivable PDAs, no special privileges, and can be triggered proactively for any (amm_config, mint0, mint1) tuple, or reactively by front-running an observed `initialize_with_permission` transaction.

### Recommendation
Restrict `initialize`'s reachable PDA space so it cannot collide with pools intended for `initialize_with_permission` (e.g., require an explicit `Permission`/allow-list check before permissionless creation for mint pairs flagged as "restricted", or make the two flows write to disjoint PDA seed spaces), and/or add a check in `initialize` that rejects creation if a `Permission` PDA exists for that mint pair reserved for a specific creator.

### Proof of Concept
1. Attacker observes (or predicts) that `token_0_mint`/`token_1_mint` will be onboarded by a `Permission`-holding market maker via `initialize_with_permission`.
2. Attacker derives the same `pool_state`, `token_0_vault`, `token_1_vault`, `lp_mint`, `observation_state` PDAs using `amm_config`, `token_0_mint`, `token_1_mint` (same seeds as in `initialize_pool_instr`) [10](#0-9) .
3. Attacker calls `initialize` first with minimal `init_amount_0`/`init_amount_1`, becoming `pool_creator` with `enable_creator_fee=false` [11](#0-10) .
4. The whitelisted market maker's later `initialize_with_permission` call for the same triple reverts because `create_pool` sees the PDA already owned by the program [7](#0-6) , permanently blocking the intended permissioned pool setup.

pub fn create_pool<'info>(
    payer: &AccountInfo<'info>,
    pool_account_info: &AccountInfo<'info>,
    amm_config: &AccountInfo<'info>,
    token_0_mint: &AccountInfo<'info>,
    token_1_mint: &AccountInfo<'info>,
    system_program: &AccountInfo<'info>,
) -> Result<AccountLoad<'info, PoolState>> {
    if pool_account_info.owner != &system_program::ID {
        return err!(ErrorCode::NotApproved);
    }

    let (expect_pda_address, bump) = Pubkey::find_program_address(
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
        ],
        &crate::id(),
    );

    if pool_account_info.key() != expect_pda_address {
        require_eq!(pool_account_info.is_signer, true);

        payer.to_account_info(),
        system_program.to_account_info(),
        pool_account_info.clone(),
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
            &[bump],
        ],
        PoolState::LEN,
    )?;
