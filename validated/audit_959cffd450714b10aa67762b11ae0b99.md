### Title
Webhook organization used for signature verification is decoupled from the organization whose stack is mutated, enabling cross-tenant forged pushes - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the raw request body against using `repository.owner.login` from the untrusted JSON payload, while `PushHandler#process` (via `Handler#stacks`/`repository_name`) resolves the stack to mutate using the unrelated `repository.full_name` field from the same payload. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured, an attacker can pick any org name with no configured secret for `repository.owner.login` while naming a real, different organization's repository in `repository.full_name`, causing an unsigned/unauthenticated body to trigger `GithubSyncJob` for that other organization's stack.

### Finding Description
The claimed binding is: **organization whose secret verified the request bytes (X) == organization owning the stack that gets mutated (Y)**. Tracing the code shows this binding is never enforced.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` purely from the payload: `params.dig('repository', 'owner', 'login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`), then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(header, raw_post)`. [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected organization's config has no `webhook_secret`: `return true unless webhook_secret` (`lib/shipit/github_app.rb:76-83`). `webhook_secret` is optional per the documented config schema (`docs/setup.md:119`, `config/secrets.development.example.yml:11`), so this is a real, supported configuration state, not a hypothetical. [3](#0-2) 

- Independently, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolve the affected repository/stack using a **different** payload field: `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and `PushHandler#process` iterates `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`). [4](#0-3) [5](#0-4) 

Nothing in `WebhooksController`, `Handler`, or `PushHandler` cross-checks that the org used to select/pass signature verification (`repository.owner.login`) matches the owner embedded in `repository.full_name`. An attacker crafts one JSON body where these two fields disagree: `repository.owner.login = "X"` (a configured org, e.g. a secondary org in a multi-org `secrets.yml`, with no `webhook_secret` set) and `repository.full_name = "Y/real-repo"` (a real repository belonging to a different, victim organization `Y` that does have a tracked `Stack`). `verify_signature` calls `Shipit.github(organization: "X")`, gets `webhook_secret` nil, and `verify_webhook_signature` returns `true` even with no `X-Hub-Signature` header at all. `drop_unhandled_event` does not block `push`, `check_if_ping` does not apply, and the `ExplicitParameters` schema for `PushHandler` only requires `ref`/`after` (`app/models/shipit/webhooks/handlers/push_handler.rb:7-10`), with no owner/full_name consistency requirement. `PushHandler#process` then looks up `Y`'s stack by `repository.full_name` and calls `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` for `Y`'s stack (as directly demonstrated by the existing test `":push with the target branch queues a GithubSyncJob"` at `test/controllers/webhooks_controller_test.rb:23-32`, which shows the exact enqueue behavior once verification is bypassed). [6](#0-5) [7](#0-6) 

### Impact Explanation
The unauthenticated request causes `Shipit::GithubSyncJob` to be enqueued and run against organization `Y`'s real `Stack` (`app/jobs/shipit/github_sync_job.rb`), fetching commits from GitHub and appending them to `Y`'s stack, which can trigger continuous-deployment logic (`sync_github_if_necessary`, `after_commit` hooks in `app/models/shipit/stack.rb:86-94`) and downstream deploys — matching the Critical category "a payload for one repository mutating another's stack ... or an unauthorized deploy." This is repeatable against any tracked stack in `Y` (or any other tenant) as long as the payload's `repository.full_name` names it, and requires no session, API token, or GitHub secret. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
The precondition is that at least one configured GitHub App organization (in a multi-org `github:` config, per `docs/setup.md:181-209`) or the single configured app (per `docs/setup.md:60-105`, `config/secrets.development.example.yml:8-16`) has no `webhook_secret` set — an explicitly supported and documented configuration state, common in self-hosted/dev setups and plausible for auxiliary orgs in multi-tenant installs. Given that, the attacker cost is a single unauthenticated `POST /webhooks` with a crafted JSON body and no signature header; the attack is trivially repeatable against arbitrary stacks by varying `repository.full_name`. [3](#0-2) [10](#0-9) 

### Recommendation
In `WebhooksController#verify_signature` and/or `Shipit::Webhooks::Handlers::Handler`, derive the organization used for both signature verification and stack resolution from the **same** trusted field, and reject requests where `repository.owner.login` does not match the owner encoded in `repository.full_name`. Additionally, reconsider `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` fallback — it silently disables authentication for any organization without a configured secret; consider making `webhook_secret` mandatory (fail-closed) or requiring an explicit "allow unsigned" opt-in per organization instead of a default bypass.

### Proof of Concept
Add a test to `test/controllers/webhooks_controller_test.rb`:
```ruby
test "push with mismatched owner/full_name bypasses signature and syncs victim stack" do
  # Configure org "attacker-org" with no webhook_secret, org "shopify" (victim, owning @stack) with one.
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', {}) # no webhook_secret => verify_webhook_signature always true
  )

  request.headers['X-Github-Event'] = 'push'
  # No X-Hub-Signature header at all.
  parsed_body = JSON.parse(payload(:push_master))
  parsed_body['repository']['owner']['login'] = 'attacker-org'
  # repository.full_name still points at the victim's real tracked repo (@stack's repository)
  expected_head_sha = parsed_body['after']

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: @stack.id, expected_head_sha:]) do
    post :create, body: parsed_body.to_json, as: :json
  end
  assert_response :ok
end
```
Assert on both sides of the binding: (a) `Shipit.github(organization: 'attacker-org').verify_webhook_signature(nil, raw_body)` returns `true` (no secret configured for X = "attacker-org"), and (b) `GithubSyncJob` is enqueued with `stack_id: @stack.id` where `@stack.repository.owner` (Y = "shopify" per `push_master.json`) differs from X = "attacker-org" — demonstrating `WEBHOOK_PROVENANCE` (X == Y) is violated while the job still executes against Y's stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

**File:** app/jobs/shipit/github_sync_job.rb (L18-49)
```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
