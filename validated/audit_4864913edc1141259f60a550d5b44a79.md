### Title
API client stack-scope bypass in `CCMenuController#stack` — token authorizing one stack can read state of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` restricted to a specific stack (`stack_id` set) can only see that stack, by resolving the target stack through the scoped `stacks` relation. `Shipit::Api::CCMenuController` overrides `#stack` to load the stack directly from the request parameter, bypassing that scoping entirely, so a token that is only supposed to authorize one stack can be used to read the CCMenu status of every stack.

### Finding Description
The base controller binds "the stack a token authorizes" to "the stack that is actually touched" through the `stacks`/`stack` helper methods: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is the mechanism that makes an `ApiClient` created with a `stack_id` (e.g. `here_come_the_walrus` in fixtures, or the client generated per-stack by `CCMenuUrlController`) only able to resolve `params[:stack_id]` against its own stack.

`CCMenuController`, however, redefines `#stack` without going through the scoped `stacks` relation: [2](#0-1) 

```
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` only checks that the client's `permissions` array contains `read:stack` — it never checks that the resolved `stack` belongs to the client's authorized scope: [3](#0-2) 

```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
```

So the equality that should hold — `current_api_client.stack_id (authorized stack) == stack (stack actually touched)` — is broken specifically in `CCMenuController#show`: any client holding only `read:stack`, regardless of its `stack_id` binding, can pass an arbitrary `stack_id` param and read that other stack's CCMenu XML (name, activity, last build status/label/time, web URL).

This is structurally analogous to the referenced report's bug class: a field that is genuinely consulted by the recipient logic (`params[:stack_id]`) is never checked against the credential that's supposed to constrain it (`current_api_client.stack_id`), just as `_lzWithdraw` never included the composed message that `data.unwrap` was supposed to gate.

Note: `CCMenuUrlController#fetch` deliberately mints a scoped `read:stack`-only `ApiClient` per stack precisely so that CCMenu tokens are stack-restricted: [4](#0-3) 

This demonstrates the stack-scoping guarantee was intended to be meaningful for this exact endpoint, yet the endpoint itself doesn't enforce it.

### Impact Explanation
An attacker who obtains (or is legitimately issued) a CCMenu token scoped to Stack A — e.g. leaked via a CI dashboard URL, browser history, log, or a compromised low-privilege integration — can use that same token to read build/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for every other stack in the Shipit instance, including stacks that they were never granted read access to. This is an unauthorized read of stack state across the intended per-token authorization boundary, matching the "High" impact category of escalation into unauthenticated/unauthorized read of stack state.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token/CCMenu token with `read:stack` permission — no privileged account, no repository write, no webhook secret, and no `api_clients_secret` is needed (an attacker already legitimately holding one scoped CCMenu URL/token, which is a normal, low-trust artifact distributed to CI-status consumers, is enough). The request itself is a single unauthenticated (from Shipit's perspective, other than the token) GET with a different `stack_id` parameter, which is trivial to attempt.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` helper (as `BaseController#stack` does), e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a client bound to `stack_id` cannot resolve any stack outside that scope, restoring the intended one-token-one-stack binding for the CCMenu endpoint.

### Proof of Concept
1. Obtain (or, as the stack owner, create via `CCMenuUrlController#fetch`) a CCMenu token scoped to Stack A (`ApiClient` with `stack_id: A.id`, `permissions: ['read:stack']`).
2. Issue: `GET /api/stacks/:any_other_stack_id/ccmenu.xml?token=<TOKEN_SCOPED_TO_A>`
3. Observe the response returns Stack B's (or any other stack's) build status XML with `200 OK`, despite the token only being authorized for Stack A — demonstrated structurally by the existing test `"stacks with no deploys render correctly"`, which shows `CCMenuController#stack` resolves an arbitrary, unrelated stack via `Stack.from_param!` with no scoping check tied to `@client`'s `stack_id`: [5](#0-4)
