### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but event handlers act on the unrelated `repository.full_name` field from the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-tenant Shipit deployments, `Shipit.github(organization:)` resolves a distinct `GitHubApp` config (and thus a distinct `webhook_secret`) per organization key in `secrets.github` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to validate the HMAC against using `repository_owner`, itself read straight out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`) [2](#0-1) . Once the signature check passes, `Webhooks.for_event(event)` handlers act on a *different* field of the same payload, `repository.full_name`, to resolve the actual `Repository`/`Stack` to operate on [3](#0-2) , and the same pattern repeats in every pull-request handler (`repository.full_name` -> `Repository.from_github_repo_name`) [4](#0-3) . Nothing ties `repository_owner` (the field covered by the signature check) to the owner segment inside `repository.full_name` (the field the handlers actually operate on).

### Finding Description
The trust binding that should hold is:
`organization whose secret authenticated the request == owner of the repository/stack that gets mutated`.

Instead the code produces:
`organization named in repository.owner.login (used only to pick the HMAC secret) != owner segment embedded in repository.full_name (used to look up and mutate Stacks/Repositories)`.

Because the HMAC covers the raw JSON body (`OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message)` in `GitHubApp#verify_webhook_signature`) [5](#0-4) , the signature only proves the body was produced with *some* organization's secret — it does not constrain which repository name can appear inside that body. An entity that legitimately administers a GitHub App for **their own** organization "A" in this Shipit instance (and therefore knows `secrets.github[:a][:webhook_secret]`) can craft an arbitrary JSON payload where:
- `repository.owner.login` = `"A"` (or `organization.login` = `"A"`) — satisfies `verify_signature`, which does `Shipit.github(organization: "A")` and validates the HMAC with A's own secret [6](#0-5) .
- `repository.full_name` = `"B/target-repo"` — a repository belonging to a completely unrelated tenant "B".

`PushHandler` then resolves `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from `payload.dig('repository', 'full_name')` [3](#0-2)  and `app/models/shipit/webhooks/handlers/push_handler.rb" start="12" end="17"`, enqueuing `stack.sync_github(expected_head_sha: params.after)` -> `GithubSyncJob` for a repository owned by tenant B, even though the signature only proved control of tenant A's secret. `Repository.from_github_repo_name` parses `owner/name` directly from the untrusted field [7](#0-6) . The same disconnect exists in the pull-request handlers (`opened`, `closed`, `reopened`, `labeled`, `unlabeled`), all of which resolve `Repository.from_github_repo_name(params.repository.full_name)` and can archive/unarchive/create review stacks and act as an arbitrary user via `params.sender["login"]` in `ReviewStackAdapter#user` [8](#0-7) .

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" impact bar: a tenant with a legitimately-provisioned webhook secret for its own organization can trigger `GithubSyncJob` (fetching commits and appending them to a Stack, which feeds `CacheDeploySpecJob` and downstream deploy machinery) against another tenant's Stack, and can archive/unarchive/create review-stacks belonging to another tenant's repository, purely by mismatching two fields inside a payload it forges from scratch. This is an unprivileged-relative-to-victim escalation: the attacker's privilege is scoped to their own org's webhook secret, yet the code lets them act on stacks outside that scope.

### Likelihood Explanation
Requires only: (1) a Shipit deployment configured for multiple organizations (the `secrets.github` multi-key schema in `lib/shipit.rb#github_app_config`), and (2) the attacker being a legitimate administrator/owner of one of those organizations' own GitHub App integration (i.e., knowing only their own org's `webhook_secret`, never the victim org's). No repository write access, no victim-org secret, and no session/API token for Shipit itself is needed — only the ability to POST directly to `/webhooks` with a self-signed body.

### Recommendation
After `verify_signature` succeeds, bind the authenticated organization to every subsequent lookup: pass `repository_owner` (or the whole authenticated `GitHubApp`/organization) down into `Shipit::Webhooks.for_event(event)` handlers, and have `Handler#repository_name` (and each pull-request handler's `repository` method) reject/ignore events where the owner segment of `repository.full_name` does not match the organization whose secret validated the signature.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github = { a: { webhook_secret: "secretA", ... }, b: { webhook_secret: "secretB", ... } }`, with Stack `victim-org/victim-repo` belonging to tenant "b".
2. As an entity that only knows `secretA` (e.g., the legitimate operator of tenant "a"'s own GitHub App), craft:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "a" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=` + `HMAC-SHA1(secretA, raw_body)`.
4. `POST /webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "a")` and validates successfully against `secretA` [6](#0-5) .
5. `PushHandler#process` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` [9](#0-8)  and enqueues `GithubSyncJob` for tenant b's stack — triggered by a party who never possessed `secretB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
