### Title
Flash loan spends a victim receiver's standing token allowance to the pool - (File: contracts/pool/src/ops/flash.rs)

### Summary
The bug class is "permissionless function consumes a third party's pre-existing token approval by letting the caller pick the funding account." XOXNO Lending's pool flash loan maps directly onto it: `flash_loan` accepts a caller-chosen `receiver`, pays out principal to that address, invokes its `execute_flash_loan` callback, and then pulls `principal + fee` out of the receiver using its **stored token allowance** to the pool via `transfer_from` — with no proof that the receiver intended to take this particular loan.

### Finding Description
`Controller::process_flash_loan` is reachable by any unprivileged caller (`require_authorized_caller` authenticates only the caller), and forwards the caller-supplied `receiver` to the pool (`contracts/controller/src/strategies/flash_loan.rs`, `pool_flash_loan_call` at line 32). The pool then executes `apply` in `contracts/pool/src/ops/flash.rs`:

1. `asset.transfer(&pool, &receiver, &amount)` pays out principal (line 60).
2. `invoke_receiver` calls `execute_flash_loan` on the receiver (lines 62–64, 150–162).
3. `collect_repayment` asserts `asset.allowance(receiver, pool) >= amount + fee` and pulls `transfer_from(pool, receiver, pool, total_repayment)` (lines 173–179).

The only thing standing between a third party's allowance and a forced repayment is the allowance check itself — the exact same root cause as the UXD `rebalance(account)` report: the function spends `receiver`'s approval, not `msg.sender`'s. A flash-receiver contract that grants a standing/max allowance to the pool (a common pattern to avoid re-approving each loan) and whose `execute_flash_loan` returns successfully for a foreign `initiator`/`data` can be forced by anyone to take flash loans repeatedly. Each call pays the victim `amount` and claws back `amount + fee`, so the victim loses `fee` per invocation, credited to protocol revenue via `book_fee`/`add_protocol_revenue` (lines 124–128). The attacker can loop this until the victim's allowance or balance is exhausted, at zero cost beyond gas.

Differences from a generic token pull that bound, but do not eliminate, the issue:
- `receiver` must be a WASM contract (`require_wasm_receiver`, line 49), so plain user wallets are not victimizable.
- The victim's `execute_flash_loan` must not revert for attacker-chosen `initiator`/`data`. Receivers that only validate the asset/pool, or that treat any invocation as "a loan I must repay," qualify.

### Impact Explanation
Involuntary token loss for any contract holding an allowance to the pool: the attacker burns the victim's approved funds as protocol fees. This is theft of user funds (the victim's balance decreases; neither the victim nor the attacker receives the fee, but the loss is real and repeatable). Bounded per-call to `fee`, but unbounded in aggregate up to the victim's balance and allowance, matching Medium severity.

### Likelihood Explanation
Requires a deployed contract that (a) grants the pool a persistent token allowance and (b) implements a permissive `execute_flash_loan`. Both are plausible for integrated flash-receiver contracts, especially since the allowance pattern is the documented repayment mechanism — but it is not guaranteed for every receiver, hence not High.

### Recommendation
Bind the repayment to the callback's own decision rather than pre-existing allowance: e.g., require the receiver to `transfer` principal + fee back inside the callback (balance-delta check like `transfer_amount_measured` instead of `transfer_from`), or pass an authorization/nonce so that only the receiver's own initiation can consume its allowance. At minimum, document that `execute_flash_loan` must authenticate `initiator` and that standing allowances to the pool are unsafe.

### Proof of Concept
1. Victim contract `V` integrates as a flash receiver and calls `token.approve(pool, u128::MAX)` once for convenience; `V.execute_flash_loan` validates the asset and repays by relying on the pool's pull (does not check `initiator`).
2. Attacker (any address) calls `controller.flash_loan(caller=attacker, hub_asset, amount=X, receiver=V, data=arbitrary)` with `fee(X) > 0`.
3. Pool transfers `X` to `V`, invokes `V.execute_flash_loan(initiator=attacker, ...)`, which returns normally.
4. `collect_repayment` checks `allowance(V, pool) >= X + fee` (true due to max approval) and pulls `X + fee` from `V`. Balance assertions pass; fee is booked as protocol revenue.
5. `V` is down `fee` despite never initiating a loan. Attacker repeats until `V`'s allowance or balance is drained.
