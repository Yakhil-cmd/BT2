### Title
Webhook events are authenticated against `repository.owner.login`/`organization.login` but processed against the independent, unverified `repository.full_name` field, letting a signature verified (or trivially skipped) for one organization write to stacks of a completely different repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a webhook against using an attacker-controlled field of the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`), while every event `Handler` resolves the entity to mutate (`stacks`) from a *different* attacker-controlled field of the same unverified body (`repository.full_name`). Nothing binds these two fields together, so the organization whose credential is checked is not necessarily the repository whose `Stack`/`PullRequest`/`Commit` records get written.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the webhook secret used for HMAC verification) purely from the payload: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Every default handler, however, resolves the repository/stacks to act on from a *different* payload key, `repository.full_name`, via the base `Handler` class: [3](#0-2) 

Nothing in `verify_signature` or in `Handler#stacks` enforces that `repository.owner.login` (used to select the signing secret) matches the owner encoded in `repository.full_name` (used to select which `Stack`s get mutated). Both are simply attacker-supplied JSON fields inside the same unsigned-at-check-time request body, so an attacker can set them to different organizations/repositories.

Crucially, `GitHubApp#verify_webhook_signature` is a no-op when no webhook secret is configured for that organization: [4](#0-3) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

The engine's own setup docs and secrets templates explicitly document the webhook secret as *optional*: [5](#0-4) [6](#0-5) 

So on any deployment where at least one configured GitHub organization has no `webhook_secret` set (which the shipped templates present as a normal, supported configuration), `verify_webhook_signature` always returns `true` for events claiming to belong to that organization - regardless of the actual `X-Hub-Signature` header. An unauthenticated attacker can then POST an arbitrary JSON body to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) set to the org that has no webhook secret configured (satisfies `verify_signature`), and
- `repository.full_name` set to `<victim-org>/<victim-repo>` - any repository tracked by Shipit, including ones belonging to fully-secured organizations.

`Handler#stacks` then resolves `Stack`s for that arbitrary `full_name`, and the concrete handler mutates real records for the victim repository:
- `PushHandler#process` triggers `stack.sync_github` [7](#0-6) 
- `StatusHandler#process` creates a `Status` on an arbitrary commit [8](#0-7) 
- `PullRequest::LabeledHandler`/`UnlabeledHandler` archive/unarchive review stacks [9](#0-8) 
- `CheckSuiteHandler` enqueues `RefreshCheckRunsJob` for the victim stack.

The equality this breaks: `organization_authenticated_by(verify_signature) == organization_that_owns(repository_written_by_handler)`. Before the flaw is exploited these are supposed to always match (both derived from a legitimately-delivered GitHub webhook for the same repository); after exploitation they can be arbitrarily different, because the two fields are read independently from the same unverified/weakly-verified payload.

### Impact Explanation
`StatusHandler` writing forged commit statuses onto a victim stack's commits is the most serious consequence: Shipit's CI gating (`ci.require`, `merge.require`) and continuous-deployment/merge-queue logic (`MergeRequest#any_status_checks_failed?`, `StatusChecker`) rely on `Commit#statuses`/`create_status_from_github!` records being authentic GitHub data. Forging a `success` status for a commit that never actually passed CI can let a merge-queue PR or continuous-delivery pipeline consider a stack deployable/mergeable when it should not be, i.e. an **unauthorized deploy/merge** condition - which matches the accepted High-impact category "escalation into `Shipit.github_teams` authorization ... or an unauthorized deploy, rollback or merge" listed in the scan rules. Other handlers (push/pull_request/check_suite) allow unauthenticated manipulation of stack archival state and cached commit/PR metadata for any repository Shipit tracks, entirely without holding any credential for that repository's real organization.

### Likelihood Explanation
Exploitability depends only on the deployment having at least one configured GitHub organization without a `webhook_secret` (explicitly presented as optional/normal in the engine's own `docs/setup.md` and `config/secrets.*.yml` templates), which is a realistic and even encouraged configuration for e.g. a low-risk sandbox org in a multi-org Shipit install. Once that condition holds, the attack requires no credentials, no session, and no GitHub App access at all - just an HTTP POST to the public `/webhooks` endpoint, which is unauthenticated by design (`WebhooksController` skips `Shipit::Authentication`). This makes it a zero-credential exploit path, higher likelihood than most analogs in this codebase.

### Recommendation
Bind the signature-verification identity to the same value the handler will act on: derive `repository_owner` and the `Repository`/`Stack` lookup from the *same* verified field, and reject events where `repository.full_name`'s owner segment does not match the organization whose secret was used to verify the signature. Additionally, treat a missing/blank `webhook_secret` as "verification cannot succeed" (fail closed) rather than "verification is skipped" in `GitHubApp#verify_webhook_signature`, or require every configured organization to have a non-blank webhook secret before accepting webhooks for it.

### Proof of Concept
1. Deploy Shipit with two configured GitHub organizations: `sandbox-org` (no `webhook_secret` configured) and `victim-org` (secured, with commit statuses gating deploys for `victim-org/app`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "sandbox-org" },
    "full_name": "victim-org/app"
  }
}
```
No `X-Hub-Signature` header is required to match anything real, since `sandbox-org` has no webhook secret configured, so `verify_webhook_signature` returns `true` unconditionally.
3. `WebhooksController#verify_signature` passes (using `sandbox-org`'s "verification", which is a no-op).
4. `StatusHandler#process` resolves `Commit.where(sha: ...)` for the commit belonging to `victim-org/app` (via `Handler#stacks`/`repository_name` = `repository.full_name`) and creates a forged `success` status record on it, potentially unblocking merge-queue/CI-gated deploy logic for `victim-org/app` despite the attacker having no relationship with `victim-org` whatsoever.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
