### Title
Signer weight can be double-counted / signer weight can exceed locked STX because pox-5's `stake` and `register-for-bond` validate sufficiency against `stx-account`'s combined "locked + unlocked" balance, while the node-side `pox_rollover_v5` path never re-checks that this amount is backed by *available* funds - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`, `pox-locking/src/pox_5.rs`)

### Summary
`pox-5.clar`'s `stake` and `register-for-bond` accept `amount-ustx` and only check `(>= total-balance amount-ustx)` where `total-balance` is `(stx-account tx-sender)`'s `locked + unlocked` sum [1](#0-0) , and the same pattern (with the explicit justification comment) appears in `register-for-bond` [2](#0-1) . This is structurally identical to the H-10 bug class: a single, instantaneous "canonical" reading of state (here, "locked+unlocked" STX) is trusted as proof of sufficient committed value, without validating that the "locked" portion is actually the specific, ending pox-5 position that will be rolled over — as opposed to an unrelated lock (e.g. a PoX-4 lock, or a still-active bond that the overlap check happens to pass) that will never actually be released to back the new commitment.

### Finding Description
When the on-chain `stx-account` shows `locked > 0`, the node-side special-case handler `handle_lockup_pox_v5` takes the "already locked" branch and calls `pox_rollover_v5` instead of `pox_lock_v5` [3](#0-2) . Unlike the fresh-lock path (`pox_lock_v5`), which explicitly calls `snapshot.can_transfer(lock_amount)` against the account's *unlocked* balance before locking [4](#0-3) , the rollover branch is documented as simply carrying the lock forward and rescheduling it, with the amount "go[ing] up or down," while trusting that "the contract returns ok" as sufficient proof of legitimacy [5](#0-4) .

The Clarity-side gate that is supposed to make this safe is the `total-balance >= amount-ustx` check using `stx-account`'s `locked + unlocked` sum [6](#0-5) . This check only proves the staker's account has *some* combination of locked and unlocked STX equal to `amount-ustx` — it does not prove that the "locked" component is the same, ending pox-5 position being rolled over, nor that it will be uniquely committed to the new stake. If a staker has an unrelated pre-existing lock from any other pox version (or even a slightly-mismatched pox-5 position that only needs to satisfy the "no-overlap" check `bond-overlaps-new-position?`), `stx-account`'s locked amount is fungible in the eyes of this check, exactly like `slot0` being trusted as a stable/valid liquidity metric in the Ichi bug — a live snapshot is treated as validated, committed collateral without confirming its provenance.

Because `pox_rollover_v5` (per its doc comment) is trusted unconditionally on `Ok` results and doesn't itself re-derive/verify `amount_ustx` against the actual freed collateral, the resulting locked amount recorded in the account's `STXBalance` can diverge from the STX genuinely available to back the new commitment.

### Impact Explanation
If the "locked" balance counted by `total-balance` in the Clarity check is not the exact terminating position being rolled over, a staker's claimed `amount-ustx` — which directly feeds `signer-manager-validate-stake` and reward/signer-weight bookkeeping (`add-staker-to-signer-cycles`, `add-staker-to-bond-cycles`) — can exceed the STX actually freed and re-committed to pox-5. This produces "signing weight or reward slots exceeding locked value," which the rules classify as High impact, and in the case where the same locked STX effectively backs two different commitments (an old lock plus the new pox-5 stake), it constitutes double-counting a commitment (Critical).

### Likelihood Explanation
This requires an unprivileged staker with any existing STX lock (which is a completely ordinary, permissionless state to be in — e.g. having previously stacked under an earlier PoX version, or having a non-overlapping earlier pox-5 bond) to call `stake`/`register-for-bond` with an `amount-ustx` computed from `locked + unlocked`, exploiting the fact that `pox_rollover_v5` trusts the contract's arithmetic instead of independently re-verifying available balance. No admin, miner, or other user's key is required.

### Recommendation
The Rust-side rollover handler (`pox_rollover_v5`/`handle_lockup_pox_v5`) should independently verify that the STX being (re)locked is actually backed by currently-available or currently-in-the-same-position-being-rolled-over funds — analogous to the `can_transfer` check used in the fresh-lock path — rather than trusting the Clarity contract's `locked + unlocked >= amount-ustx` check as sufficient proof. The Clarity contract should also tie the `amount-ustx` sufficiency check specifically to the ending position's locked amount (plus any genuinely unlocked STX), not to the account's total locked balance from any source.

### Proof of Concept
Full exploitation requires tracing `pox_rollover_v5`'s implementation (not available in the reviewed excerpt) to confirm it does not perform an independent balance check equivalent to `can_transfer`. Based on the available code:
1. Staker locks STX under an older PoX version (e.g. pox-4), producing `locked > 0` via `stx-account`.
2. Staker calls pox-5 `stake`/`register-for-bond` with `amount-ustx` set to `locked + unlocked` (their full balance) [7](#0-6) ; the `total-balance >= amount-ustx` check passes trivially.
3. Node-side handling sees `already_locked = true` and takes the `pox_rollover_v5` branch [8](#0-7) , which (per its doc comment) reschedules/updates the lock amount without re-validating against genuinely unlocked funds.
4. Signer weight / reward-slot bookkeeping is credited with `amount-ustx`, which may exceed what is truly, uniquely committed.

This PoC is incomplete without the body of `pox_rollover_v5`, which was not retrieved before the tool budget ended; confirming the exact mechanics (whether it re-checks unlocked balance for the delta) would require reading `pox-locking/src/pox_5.rs` beyond line 420 and the remainder of `pox-5.clar` beyond line 1000.

    // A staker rolling from one bond/stake position into another is already
    // locked; carry the lock forward instead of acquiring a fresh one (which
    // would fail with `PoxAlreadyLocked`). A first-time call locks fresh.
    let already_locked = {
        let mut snapshot = global_context.database.get_stx_balance_snapshot(&staker)?;
        snapshot.has_locked_tokens()?
    };

    let lock_result = if already_locked {
        pox_rollover_v5(
            &mut global_context.database,
            &staker,
            unlock_height,
            locked_amount,
        )
        .map(|_| ())
    } else {
        pox_lock_v5(
            &mut global_context.database,
            &staker,
            locked_amount,
            unlock_height,
        )
    };
