### Title
Webhook signature verification uses `repository.owner.login` while every event handler acts on `repository.full_name` — cross-organization event forgery in multi-tenant `Shipit.github` configs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App / `webhook_secret` used to validate the HMAC signature based on `repository.owner.login` (or `organization.login`) taken straight from the untrusted JSON body, while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Repository`/`Stack` it actually mutates from a *different* field of the same untrusted body, `repository.full_name`. Nothing enforces that these two fields refer to the same organization/repository. Combined with the fact that `GitHubApp#verify_webhook_signature` unconditionally returns `true` when an organization's `webhook_secret` is unset (a state the shipped default configs explicitly allow, e.g. `webhook_secret: null`), this breaks the trust binding "the organization whose secret authenticated the request" == "the repository the request is allowed to act on."

### Finding Description
`before_action :verify_signature` selects the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

The chosen organization is passed to `Shipit.github(organization: repository_owner)`, which loads that organization's `GitHubApp` (with its own `webhook_secret`), and `verify_webhook_signature` is called against the raw body: [3](#0-2) 

Critically, `return true unless webhook_secret` — if the organization resolved from `repository.owner.login` has no `webhook_secret` configured (the shipped default templates literally set `webhook_secret: null`/blank), **any** signature (or none) is treated as verified, regardless of the actual body contents: [4](#0-3) [5](#0-4) 

Once signature verification passes, `create` dispatches the same raw payload to the event handlers: [6](#0-5) 

Every handler, however, resolves the repository to act on from `repository.full_name`, not `repository.owner.login`: [7](#0-6) [8](#0-7) [9](#0-8) 

So the equality that must hold for the security model to work is:
`organization(repository.owner.login used to pick webhook_secret)` == `organization(repository.full_name used by the handler to pick the Repository/Stack)`.

Nothing in `WebhooksController` or `Handler` enforces this. An attacker can set `repository.owner.login` to an organization configured in `Shipit.github` (as documented for multi-org deployments, `docs/setup.md`) that has a blank `webhook_secret`, while setting `repository.full_name` to `victim-org/victim-repo` — a completely unrelated, properly-secured repository tracked by the engine. `verify_signature` will verify (trivially, since that org has no secret), and the handler (e.g. `PushHandler`, `StatusHandler`) will then act on the victim repository's stacks/commits.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely:
- `Handlers::StatusHandler` calls `commit.create_status_from_github!(params)` for any commit matching `params.sha`, letting the forged event mark an arbitrary commit's CI context as `success`. If the target stack's `shipit.yml` uses `ci.require`/deployable checks and has continuous deployment enabled, this can make an otherwise CI-failing/malicious commit `deployable?`, leading to an **unauthorized deploy** — one of the explicitly listed valid impacts.
- `Handlers::PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` for any stack of the spoofed repository, letting an attacker force GitHub sync/refresh operations on stacks they don't own.
- `Handlers::PullRequest::*Handler`s can create/archive/unarchive review stacks and mutate PR metadata for repositories entirely disconnected from the organization whose (absent) secret was "verified."

The root cause is not "the app wasn't mounted as documented" — it is that the code path deliberately supports multiple organizations with independent secrets (`docs/setup.md`, `lib/shipit.rb#github_app_config`), and the security check for *which* secret to use is derived from a field disjoint from the field the business logic trusts to select the target repository.

### Likelihood Explanation
Requires only an unauthenticated HTTP POST to the mounted webhooks endpoint (`config/routes.rb`); no session, `ApiClient` token, or GitHub credential of any kind is needed. The precondition — at least one configured organization with no `webhook_secret` — is not a hardening failure of "the host app not mounting the engine as documented"; it is the literal default committed in this repo's own config templates (`config/secrets.development.shopify.yml`, `docs/setup.md`), and a state operators are likely to leave temporarily or permanently for internal/low-risk orgs in a multi-org Shipit install. Given that, exploitation likelihood is moderate-to-high wherever multi-org config is used with a not-fully-secured tenant.

### Recommendation
- Require `repository.owner.login` (or `organization.login`) used for signature-org selection to be structurally tied to the repository actually acted upon: after selecting the signing organization, re-validate that `repository.full_name.split('/').first == repository_owner` before invoking handlers, or better, derive the acting repository/stack lookup itself from the same field validated during signature selection.
- Do not allow `verify_webhook_signature` to silently succeed when `webhook_secret` is blank; instead, reject (`head 422`) events for organizations without a configured secret, or make `webhook_secret` mandatory in `GitHubApp#initialize`/`Shipit.github_app_config`.
- Log/alert when `repository.owner.login` and the owner segment of `repository.full_name` diverge, since this should never legitimately happen for genuine GitHub webhook payloads.

### Proof of Concept
1. Configure Shipit with two organizations, per `docs/setup.md`'s "Using Multiple Github Applications": `org-empty` (no `webhook_secret` set) and `victim-org` (has stacks tracking `victim-org/victim-repo`, with `webhook_secret` set and CI-gated continuous deployment).
2. As an unauthenticated attacker, POST to the engine's webhooks endpoint with headers `X-Github-Event: status` and any/garbage `X-Hub-Signature`, and body:
```json
{
  "sha": "<malicious commit sha on victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "org-empty"}, "full_name": "victim-org/victim-repo"}
}
```
3. `WebhooksController#verify_signature` computes `repository_owner = "org-empty"`, loads that org's `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally because `org-empty`'s `webhook_secret` is blank — request passes.
4. `Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, marking the malicious commit on `victim-org/victim-repo` as passing CI, even though the attacker never possessed `victim-org`'s webhook secret.
5. If `victim-org`'s stack has continuous deployment enabled and this status satisfies `ci.require`, the malicious commit becomes deployable, resulting in an unauthorized deploy of attacker-influenced code.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
