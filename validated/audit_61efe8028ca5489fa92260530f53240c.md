### Title
Arbiter contract hash uses unescaped delimiter join, allowing field-boundary smuggling that changes contract terms without changing the contract hash - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` computes the identity hash of an arbiter contract by naively joining caller-controlled strings with a fixed delimiter and hashing the result, exactly the anti-pattern described in the Req advisory (unescaped interpolation of attacker-influenced strings into a structured, delimiter-separated format). Because `title` and `text` are free-form strings supplied by the contract offeror/peer and are never checked for the delimiter sequence, a malicious counterparty can craft `title`/`text` values that contain the delimiter itself, shifting field boundaries so that two semantically different contracts (different amount, address, arbiter, or asset) hash to the same `contract.hash`.

### Finding Description
`getHashSrc()` builds the hash source by joining several fields — including title, text, creation_date, payer/payee addresses, arbiter_address, amount, and asset — with a fixed delimiter and no escaping: [1](#0-0) 

The delimiter is a fixed, publicly known string: [2](#0-1) 

`title` and `text` are attacker/peer-controlled free text with no validation against containing the delimiter (unlike `string_utils.getSourceString`, which explicitly rejects the `\x00` join character in strings to prevent exactly this kind of ambiguity): [3](#0-2) 

`arbiter_contract.js` performs no equivalent check before joining, so a `title` or `text` value containing the literal substring `"[|#|]"` shifts subsequent array elements into the position of earlier ones from the hashing function's perspective (or vice versa), letting two different `(title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset)` tuples produce an identical joined string and therefore an identical SHA-256 hash.

This hash is treated as the canonical, security-relevant identifier for the contract everywhere in the module: it is the primary lookup key (`getByHash`), the value embedded in the on-chain data message (`payload.contract_text_hash`) that binds a posted unit to the negotiated terms, and it is fed into the shared-address definition as a data-feed key (`"CONTRACT_" + contract.hash`) used to release funds: [4](#0-3) [5](#0-4) 

Because the joined-and-hashed fields include the financial terms (amount, asset, addresses, arbiter), an attacker who controls `title`/`text` (the offeror side of a peer-to-peer arbiter contract, i.e., a paired device correspondent) can construct a contract whose displayed/stored title and text absorb characters that were meant to delimit the *following* financial fields, causing the resulting hash to also match a second, differently-parameterized contract. The wallet's `store()` function uses `INSERT OR IGNORE` keyed effectively by this hash, so a colliding hash from a peer-provided contract can silently fail to overwrite/insert distinguishable records, or a receiving party's local `getByHash` can be tricked into associating on-chain proofs (`contract_text_hash`, the `CONTRACT_<hash>` data-feed key, the shared-address definition) with terms different from what was actually negotiated and displayed.

### Impact Explanation
The arbiter contract's `hash` is the sole cryptographic binding between the human-readable/negotiated contract terms (title, text, amount, addresses, arbiter) and the on-chain artifacts that gate fund release (`contract_text_hash` in the payment-locking data message, and the `CONTRACT_<hash>` data-feed key referenced by the shared address's spending conditions). If the hash can be made to collide across different financial terms via delimiter injection in `title`/`text`, a malicious counterparty can present, sign, or dispute a set of terms that do not match what the honest party believes was agreed to, while both hash to the same identifier used to authorize the shared address and unlock payment. This can lead to fund loss or a shared-address definition inconsistency between the two parties (node disagreement about what the contract actually was), which are within the accepted impact categories (AA/contract fund loss or freezing, and disagreement over agreed obligations/validity).

### Likelihood Explanation
Any paired-device counterparty who is offered, or who offers, an arbiter contract fully controls the `title` and `text` fields sent in the `arbiter_contract_offer`/`arbiter_contract_shared` device messages. No validation rejects the delimiter substring `"[|#|]"` in these fields before it is joined and hashed, so the attack requires nothing more than crafting a text field — reachable by the "paired device" actor class explicitly in scope.

### Recommendation
Reject (or escape) values containing the `DELIMITER` substring in `title`, `text`, and any other free-form field before joining in `getHashSrc()`, mirroring the approach already used in `string_utils.getSourceString()`, which throws if a string contains the join character. Alternatively, switch `getHashSrc`/`getHash` to use the length-prefixed/type-tagged `getSourceString`/`getJsonSourceString` utilities (which are collision-resistant against exactly this class of ambiguity) instead of a raw delimiter-joined string.

### Proof of Concept
1. Peer A (attacker) offers an arbiter contract where `title = "Invoice"`, and `text` is crafted to end with the sequence `"[|#|]"+<attacker_creation_date>+"[|#|]"+<attacker_payer_address>+"[|#|]"+...` such that the remaining declared fields (payer_address, payee_address, amount, asset) in the actual `objContract` differ from a second, "real" contract, yet after `.join(exports.DELIMITER)` the two produce byte-identical strings.
2. `getHash()` computes `sha256(getHashSrc(contract))`, producing the same `hash` for both parameter sets: [6](#0-5) 
3. The colliding hash is used as `contract_text_hash` in the on-chain data message and as the `CONTRACT_<hash>` data-feed key in the shared-address spending definition, so verification code that only checks the hash (not the fully reconstructed terms) accepts terms inconsistent with what was actually negotiated/displayed to the counterparty.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
