### Title
Unattested output address causes an entire merged AA payment message to fail, bouncing (and blocking) payouts to all other legitimate recipients - ([File: validation.js])

### Summary
For a `spender_attested` asset, `validatePaymentInputsAndOutputs` in `validation.js` rejects a **whole** payment message if even one output address in it is not on the attested list, and `aa_composer.js` unconditionally merges all payment outputs for the same asset into a single message before sending. This means an AA that is supposed to distribute funds of a `spender_attested` asset to many recipients (e.g. a bounty/reward-splitting AA) can be fully DoS'd - and its whole response unit bounced - if just one recipient in the batch is not (or is no longer) on the attestor's whitelist, exactly the "one bad actor blocks the whole batch claim" bug class described in the report.

### Finding Description
`validatePaymentInputsAndOutputs` checks attestation of all output addresses at once, all-or-nothing: [1](#0-0) 

If `objAsset.spender_attested` is true, `storage.filterAttestedAddresses` is used to filter output addresses that are attested, and if the count doesn't match the total number of output addresses, the **entire payment message fails validation** with `"some output addresses are not attested"` - there is no mechanism to accept the attested outputs and simply drop/skip the unattested one.

In `aa_composer.js`, when an AA composes its response, all `payment` messages for the same asset are unconditionally merged into a single message (and outputs to the same address merged) before the outputs get validated and the unit is built and saved: [2](#0-1) [3](#0-2) 

Because of this merge step, an AA author has **no way to isolate per-recipient payments** into separate units/messages to protect other recipients from a single bad address - the framework recombines everything for the same asset into one payment payload, which is then validated as a unit: [4](#0-3) 

If `validateAndSaveUnit` fails (as it will when one output address is unattested), the whole trigger is bounced: [5](#0-4) 

This is structurally identical to the reported bug class: a loop/aggregate operation over multiple recipients where one recipient failing a per-address gate (blacklist in the Solidity report / lack of attestation here) causes the entire batch operation to revert, denying service to all other otherwise-eligible recipients.

### Impact Explanation
When an AA is designed to pay out a `spender_attested` asset to multiple addresses in one trigger response (e.g., splitting a bounty/reward/dividend among several winners), the loss of attestation for (or malicious non-attestation of) just one recipient address causes:
- The entire response unit to fail `validateAndSaveUnit` and the trigger to `bounce`, per `aa_composer.js:1405-1411`.
- All state changes for that trigger to be reverted (AA "fund loss/freezing" from the affected users' perspective: legitimate, attested recipients cannot receive their share because of one third party's attestation status), and only bounce fees are deducted from the trigger's payment.
- Because `mergeMessagesAndOutputs` forcibly merges same-asset outputs into a single message, this cannot be avoided by the AA author structuring outputs into independent messages - the framework itself removes any isolation.

This is a Medium/High severity denial-of-service specific to AAs that use `spender_attested` assets for multi-recipient payouts (common in KYC-gated or regulated asset use-cases combined with reward-splitting logic), matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an AA design that pays a `spender_attested` asset to multiple addresses in a single trigger response, and (b) at least one recipient in that batch losing/never having attestor approval (attestation is controlled off-chain/by a third-party attestor and can change or simply never be granted for a given address, e.g., a newly generated address, a device address, or one deliberately not attested by the attestor). Any user/trigger sender can supply an arbitrary `trigger.address` or cause the AA to compute output addresses that include an unattested address (e.g., referral/reward addresses), triggering this DoS without requiring any privileged access.

### Recommendation
- In `validatePaymentInputsAndOutputs` (`validation.js`), when `objAsset.spender_attested` is true, do not reject the whole message when some output addresses are unattested; instead, either (a) allow the AA/composer to omit/skip unattested outputs before the message is finalized, or (b) surface a distinguishable, actionable error that lets the AA logic branch and pay only attested recipients.
- Alternatively, allow AA authors to send outputs to different addresses of a `spender_attested` asset as independent, non-merged payment messages/units so a failure for one address does not block others; this requires exempting `spender_attested` assets from the unconditional merge in `mergeMessagesAndOutputs` (`aa_composer.js`).
- At minimum, document this all-or-nothing attestation semantics prominently so AA authors avoid combining payouts to third-party-controlled addresses of `spender_attested` assets in a single response.

### Proof of Concept
1. Define an asset `A` with `spender_attested: true` and an attestor list that attests addresses `X` and `Y` but not `Z`.
2. Deploy an AA that, on trigger, sends a `payment` message with asset `A` to three output addresses: `X`, `Y`, and `Z` (e.g., splitting a bounty/reward three ways based on trigger data supplied by an unprivileged trigger sender).
3. Send a trigger causing the AA to attempt this payout. During response composition, `aa_composer.js` builds/merges the single payment message with all three outputs and calls `validateAndSaveUnit`.
4. `validatePaymentInputsAndOutputs` computes `arrAttestedOutputAddresses` via `storage.filterAttestedAddresses` over `[X, Y, Z]`; since `Z` is not attested, `arrAttestedOutputAddresses.length !== arrOutputAddresses.length`, so validation fails with `"some output addresses are not attested"` (`validation.js:2634-2639`).
5. `sendUnit`'s `validateAndSaveUnit` callback receives this error and calls `bounce(err)` (`aa_composer.js:1408-1410`), reverting the AA's state changes for this trigger and refunding (minus bounce fees) instead of paying out to `X` and `Y`, even though they are legitimately attested.

	// non-payment messages are left intact.
	function mergeMessagesAndOutputs(messages) {
		const arrMergedMessages = [];
		const assocMergedMessagesByAsset = Object.create(null);
		for (let message of messages) {
			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
