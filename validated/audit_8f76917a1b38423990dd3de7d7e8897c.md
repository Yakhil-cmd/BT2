### Title
Stale shared liquidity-index cache lets a socialized bad-debt write-down be bypassed within the same block - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`market.clar` caches each vault's borrow/liquidity indexes in a block-scoped map (`index-cache`) keyed only by `{timestamp: stacks-block-time, aid}` [1](#0-0) . This cache is shared across every transaction that lands in the same block, not just calls within a single transaction. `vault-socialize-debt`, which performs a discrete write-down of a vault's liquidity index when bad debt is socialized, is invoked directly on the vault and never goes through `accrue-and-cache` [2](#0-1) . As a result, once any transaction in a block has primed `index-cache` for an asset, a later, unrelated transaction in the *same* block that consumes the cache (e.g. via `resolve-ztoken`, which errors if no cache entry exists rather than recomputing) will use the pre-write-down index rather than the true, just-devalued one [3](#0-2) .

### Finding Description
`accrue-and-cache` only refreshes a vault's indexes from `vault-accrue` on a cache miss; any subsequent call in the same block (`stacks-block-time` unchanged) is served the cached struct unconditionally [1](#0-0) . This design assumes indexes only move with elapsed time, which is safe for ordinary interest accrual (zero time delta ⇒ same index regardless of call order). However `vault-socialize-debt` performs an out-of-band mutation of a vault's liquidity index to absorb bad debt — a discrete write-down unrelated to elapsed time — and it bypasses `index-cache` entirely, writing straight to the vault contract's own state [2](#0-1) .

`resolve-ztoken`, used for pricing zToken collateral/debt, reads the index solely from the cache via `get-cached-indexes` and fails if there is no entry — it never independently re-verifies freshness against the vault's live state [3](#0-2) . The cache map is ordinary contract storage, so an entry set by transaction A (which accrues/caches a vault's index before or unrelated to the socialization event) persists and is visible to transaction B later in the same block. If a bad-debt event socializes a loss into a vault's liquidity index between A and B, B still reads A's cached, pre-write-down index for that `aid` because the cache key does not account for the socialization event, only for the timestamp.

Concretely: attacker (a third-party user, not the liquidator or the DAO) transacts immediately after a `socialize-debt` call lands in the same block, using the affected zToken as collateral or debt. Because `resolve-ztoken` serves the stale, higher, pre-write-down index from `index-cache`, the attacker's health check overstates their zToken collateral value (or understates their zToken debt value), letting them borrow more than the post-loss backing actually supports, or avoid a liquidation that should now trigger. The victims are the vault's other suppliers/zToken holders, whose true, reduced claim is masked for the remainder of the block, letting the attacker extract value the vault no longer actually has — a shared cache primed by one caller (or by the socialization event) and consumed unmodified by another, causing harm to depositors distinct from the caller. This is the same root defect as the Kashi report: a price/index cache that is not correctly invalidated by a state-changing event within the same block, letting a stale cached value be leveraged by an unrelated actor to their advantage.

### Impact Explanation
Because the exploited window lets an unrelated party borrow/withdraw against a zToken index that has not yet reflected an actual on-chain loss, this can result in direct extraction of value from the vault's remaining suppliers beyond what the vault can honestly back — i.e., protocol insolvency / theft of supplier funds, which maps to the Critical impact tier (direct theft of user funds at rest, or protocol insolvency).

### Likelihood Explanation
The likelihood of exercising the exact race depends on how often `socialize-debt` fires (typically during a liquidation that fully cannot cover debt) and on an unrelated actor being able to land a following transaction referencing the same `aid` within the same block — both are realistic on a network with predictable, sub-second/low-latency block production, and the attacker does not need any special privilege, whitelist, or DAO access to trigger it; they simply need to observe/predict a socialization event and follow it in the same block with an ordinary borrow/collateral-valuation transaction.

### Recommendation
Invalidate or bypass the cached index whenever `vault-socialize-debt` (or any other non-time-based index mutation) executes — either by having `vault-socialize-debt` also update `index-cache` for the affected `aid`/timestamp, or by having `accrue-and-cache`/`get-cached-indexes` always re-fetch fresh indexes from the vault instead of trusting a same-timestamp cache entry when a write-down has occurred in the interim.

### Proof of Concept
1. User X's position becomes undercollateralized; a liquidator calls the market's liquidation path, which triggers `vault-socialize-debt` on vault V, writing down V's liquidity index in the vault contract directly (bypassing `index-cache`) [2](#0-1) .
2. Earlier in the same block (or via the same liquidation transaction's own prior accrual step), `index-cache` for vault V at the current `stacks-block-time` was already populated with the pre-write-down index via `accrue-and-cache` [1](#0-0) .
3. Attacker Y submits a transaction later in the same block that uses zToken-V as collateral for a new borrow; `resolve-ztoken` prices zToken-V using `get-cached-indexes`, which returns the stale, higher, pre-write-down index rather than the vault's real, just-reduced backing [3](#0-2) .
4. Y's health check passes at an inflated collateral valuation, letting Y borrow more than the vault's true post-loss state supports, extracting value from V's remaining suppliers who are unrelated to Y's transaction.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
