### Title
CCMenu token generated for one stack authorizes unauthenticated read access to every stack in the installation - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`Shipit::CCMenuUrlController#fetch` mints a per-user `ApiClient` ("CCMenu Client") to embed as a `token` query parameter in a stack-specific CCMenu URL (`/ccmenu/*stack_id`). The URL's path implies the token is scoped to that one stack, but the underlying `ApiClient` is never bound to a `stack_id`, and `Api::CCMenuController` looks up the target stack with an unscoped `Stack.from_param!(params[:stack_id])` instead of the client-scoped `stacks.from_param!` used elsewhere in the API. The binding that should hold — "the stack a token authorizes == the stack the token can touch" — is broken: the same token is valid for reading the CI/deploy status of any stack in the Shipit installation, not just the one the CCMenu URL was generated for.

### Finding Description
The verified/expected side of the binding is the stack encoded in the CCMenu URL path (`api_stack_ccmenu_url(stack_id: stack.to_param)`), generated per-stack in `CCMenuUrlController#fetch`: [1](#0-0) 

The actual side is the `ApiClient` record backing the token. It is created with only `permissions: %w[read:stack]` and `creator: current_user`, without ever setting `stack_id`: [2](#0-1) 

Because `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` keys only on `creator` and `name`, the exact same `ApiClient` row (and therefore the exact same signed `token`) is reused across every stack that user ever generates a CCMenu URL for.

`Api::CCMenuController` then resolves the stack directly via `Stack.from_param!`, bypassing the client-scoping helper (`stacks.from_param!`) used by every other API controller (e.g. `Api::BaseController#stack`, `Api::StacksController`): [3](#0-2) [4](#0-3) 

`ApiClient#check_permissions!` only checks the `permissions` array (`read:stack`), never the `stack_id` scope: [5](#0-4) 

Even setting aside the `Stack.from_param!` bypass, the token itself has `stack_id` nil, so even the standard `stacks` scoping method (`current_api_client.stack_id? ? Stack.where(id: ...) : Stack.all`) would resolve to `Stack.all` — the token was never actually restricted to a single stack despite the per-stack URL semantics implied by the feature.

### Impact Explanation
CCMenu/CCTray URLs are designed to be embedded in third-party, often publicly displayed or loosely-secured dashboard widgets (build radiators, status boards) — this is the entire purpose of the feature. A team member who shares or embeds a CCMenu URL for one non-sensitive stack unknowingly hands out a token that is valid to unauthenticated-caller access (no Shipit session, just the token) for reading `latest_deploy` state (last build status/label, activity, `webUrl`) of every other stack in the Shipit installation, including stacks the user has no intention of exposing. This satisfies the "unauthenticated read of stack state" High-impact criterion: the caller supplies only the leaked/shared token, no session, no elevated GitHub identity, and gains cross-stack read access beyond the scope the feature was designed to grant.

### Likelihood Explanation
Any authenticated Shipit user (ordinary team member, not privileged) can trigger this by simply using the "CCMenu URL" feature that already exists in the stack settings UI (`app/views/shipit/stacks/settings.html.erb`) for a stack they have access to. No attacker-side exploitation complexity or repeated action is required — a single legitimate use of the feature produces an over-scoped, reusable credential. Likelihood is high in any installation where CCMenu/CCTray URLs are used and shared externally (their documented use case).

### Recommendation
1. Bind the generated `ApiClient` to the specific `stack` it was created for (`ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(...)`), and include `stack_id` in the `find_or_create_by!` lookup key so a distinct token is minted per stack.
2. Change `Api::CCMenuController#stack` to use the scoped `stacks.from_param!(params[:stack_id])` (inherited from `Api::BaseController`) instead of the unscoped `Stack.from_param!`, so `ApiClient#stack_id` scoping is actually enforced.
3. Enforce `current_api_client.stack_id` scope checks even for tokens with `stack_id` nil originating from single-stack-purpose flows like CCMenu, rather than relying on `Stack.all` fallback.

### Proof of Concept
1. As any authenticated Shipit team member, visit `Stack A`'s settings page and generate its CCMenu URL, obtaining `GET /api/<owner>/<repoA>/<envA>/ccmenu?token=T`.
2. Note `T` is the `authentication_token` of the shared `ApiClient` named `"CCMenu Client"` created for that user, with `permissions: ["read:stack"]` and `stack_id: nil`. [2](#0-1) 
3. Without any additional authentication, request `GET /api/<owner>/<repoB>/<envB>/ccmenu?token=T` for an arbitrary other `Stack B` in the same installation.
4. `Api::CCMenuController#authenticate_api_client` verifies `T` successfully (it is a valid, unexpired signed `ApiClient` token) and `require_permission :read, :stack` passes because the client has `read:stack`. [6](#0-5) 
5. `stack` resolves `Stack B` via unscoped `Stack.from_param!`, and the response renders `Stack B`'s latest deploy/build status — a stack the token was never intended to expose. [7](#0-6)

  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end
