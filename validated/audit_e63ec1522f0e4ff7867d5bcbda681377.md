## Title
Webhook signature is verified against an attacker-chosen organization while the write target is taken from an unverified `repository.full_name` field, enabling cross-organization webhook forgery in multi-tenant deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to check the inbound `X-Hub-Signature` against using `repository_owner`, a value read straight from the untrusted JSON body (`repository.owner.login` or `organization.login`) [1](#0-0) . Every event handler, however, resolves the actual `Stack`/`Repository` to mutate using a *different* field of that same body, `repository.full_name` [2](#0-1) . In a multi-organization Shipit deployment (the documented `github: { org_a: {...}, org_b: {...} }` schema) an attacker who legitimately controls one configured organization (and therefore knows its `webhook_secret`) can sign a payload whose `repository.owner.login` points at their own org (so `Shipit.github(organization: repository_owner)` picks their own, known secret and the HMAC check passes) while `repository.full_name` points at a victim organization's repository, causing the handler layer to act on the victim's stack.

### Finding Description
Verification and action operate on two different, independently attacker-controllable fields of the same unauthenticated-until-verified JSON body:

- Verification binding: `Shipit.github(organization: repository_owner)` → `webhook_secret` of `repository_owner`, computed in `repository_owner` at `app/controllers/shipit/webhooks_controller.rb:59-62`.
- Action binding: `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, used by every `Handler` subclass (`PushHandler`, `pull_request` handlers, etc.) at `app/models/shipit/webhooks/handlers/handler.rb:33-38`.

Because `Shipit.github` supports the multi-org config schema (`github_app_config`/`github_default_organization` in `lib/shipit.rb:170-200`), a Shipit instance can host multiple independent organizations, each with its own `webhook_secret`, each self-service-configurable by that organization's own GitHub App admin. Nothing in `verify_signature` or in the handler layer forces `repository.owner.login` (the field the secret-selection/signature check trusts) to match `repository.full_name` (the field that actually selects the object to write). An attacker who owns/administers "attacker-org" (and thus knows its `webhook_secret`) can:
1. Build a payload with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`.
2. Sign the full raw body with `attacker-org`'s known `webhook_secret` using the standard `sha1=` HMAC scheme (`lib/shipit/github_app.rb:76-83`).
3. POST it to the shared, unauthenticated `/webhooks` endpoint (`app/controllers/shipit/webhooks_controller.rb:10-15`).

`verify_signature` picks `attacker-org`'s config, the HMAC matches, and the request passes with `verified = true`. `create` then dispatches to the registered handlers for the event, which resolve the target repository/stack from `repository.full_name`, i.e. the victim's stack, entirely bypassing the victim organization's own `webhook_secret`.

This breaks the intended equality: *organization the signature authenticates == repository the handlers write to*. Before the attack these are always equal for genuine GitHub deliveries (GitHub always sets `repository.owner.login` and `repository.full_name` consistently and signs with the receiving installation's actual secret). After the attacker's crafted request, the two diverge while still passing verification.

### Impact Explanation
Depending on which event/handler is targeted, this permits cross-organization/cross-repository state changes without ever knowing the victim's `webhook_secret`:
- `push` → `PushHandler` enqueues `GithubSyncJob` for the victim stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which can trigger a resync of commits and, if continuous delivery is enabled on that stack, an automatic deploy.
- `pull_request` handlers can archive/unarchive/provision review stacks belonging to the victim repository (`app/models/shipit/webhooks/handlers/pull_request/*_handler.rb`).
- `status`/`check_suite` handlers can inject arbitrary commit statuses/check-run state into the victim's commit history, which Shipit's merge/deploy gating relies on.

This is a cross-repository/cross-organization write performed by an entity that never authenticated as, or was granted access to, the victim organization — matching the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (documented and supported: `config/secrets.development.example.yml:18-38`) where the attacker is a legitimate admin of one of the hosted organizations (i.e., they can configure their own GitHub App's `webhook_secret` and freely POST to it) but not of the victim organization. No Shipit session, `ApiClient` token, or the victim's credentials are needed — only the attacker's own, self-controlled webhook secret and the ability to POST to the public `/webhooks` endpoint.

### Recommendation
After signature verification, re-derive the organization from the same trusted field used for the HMAC check and require it to match the owner of `repository.full_name` used by handlers (e.g., verify `payload.dig('repository','full_name')` starts with `repository_owner + '/'`), or better, verify the signature against the `webhook_secret` of the organization that actually owns `repository.full_name`, rejecting the request if these disagree.

### Proof of Concept
1. Deploy Shipit with two configured organizations, `attacker-org` (secret `S_A`, known to the attacker) and `victim-org` (hosting a real `Stack` for `victim-org/victim-repo`).
2. Craft a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner == "attacker-org"`, loads `attacker-org`'s config, and the HMAC matches ⇒ verification passes (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `PushHandler` resolves the stack via `repository.full_name == "victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:33-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and enqueues `GithubSyncJob` against the victim's stack, without ever using `victim-org`'s own `webhook_secret`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
