### Title
`StatusHandler#process` queries `Commit` globally by `sha`, bypassing repository-scoped `Handler#stacks`, allowing a `status` webhook for one repository to write a CI status onto a commit belonging to another repository's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::Handler#stacks` scopes all repository-derived data to `Repository.from_github_repo_name(payload repository).stacks`, and `PushHandler`/`CheckSuiteHandler` correctly use this scope. `StatusHandler#process`, however, ignores `stacks` entirely and runs `Commit.where(sha: params.sha)` unscoped, then calls `commit.create_status_from_github!(params)` on whatever `Commit` rows match, regardless of which repository the webhook `repository` block names.

### Finding Description
The binding that should hold for every handler is: `handler-mutated Commit/Stack ∈ Repository.from_github_repo_name(payload['repository']['full_name']).stacks`. `CheckSuiteHandler` respects this (`stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }`, [1](#0-0) ), and `PushHandler` respects it too ( [2](#0-1) ). `StatusHandler#process` breaks it: [3](#0-2) 
It never calls `self.stacks` (which is defined in the base `Handler` as `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, [4](#0-3) ), and never references `repository_name`/`payload['repository']` at all — the `repository` field in the `status` payload is entirely decorative for authorization purposes.

`Commit#sha` is not globally unique per repository in the schema — commits sharing identical git history (e.g. forks) genuinely share the same SHA across independent `Repository`/`Stack` rows in Shipit's database, since git SHAs are content-addressed and preserved across forks. `Commit.where(sha:)` therefore can match a `Commit` belonging to a stack that has nothing to do with the repository named in the incoming webhook payload. The subsequent `commit.create_status_from_github!(params)` writes a `CommitStatus` (state, description, target_url, context, created_at — all attacker-controlled fields from `params`) using `commit.stack_id`, i.e., the *victim's* stack, not the stack derived from the payload's `repository` field.

Exploit flow: An attacker who has (or can obtain, e.g. via a fork within an org where the Shipit GitHub App is installed org-wide) a genuinely-signed `status` event delivery for their own repository, where the commit `sha` happens to coincide with a commit already tracked under a victim's `Stack` (trivially true for forked history), causes Shipit to write a forged status (e.g. `state: "success"` on a required CI context) onto the victim's commit. This can satisfy `required_statuses`/`blocking_statuses` checks used to gate deploys, enabling an unauthorized deploy of a commit that never actually passed the victim's real CI.

`verify_signature` (`app/controllers/shipit/webhooks_controller.rb`) validates only that the HMAC matches the webhook secret configured for the payload's declared `repository.owner.login`/GitHub App organization — it authenticates that GitHub genuinely delivered *some* event for that org/app installation, but it does not, and cannot, guarantee that the `sha` inside the body only overlaps with commits belonging to stacks under that same repository. Because `StatusHandler` never consults `stacks`, this signature check provides no protection against the cross-repository sha collision described here.

### Impact Explanation
An attacker-controlled `status` payload for a repository they legitimately control (or one that shares webhook delivery with the target org) can mutate `CommitStatus` records belonging to an unrelated `Stack`/`Repository` they do not own or control, because the write path (`Commit.where(sha:)` → `commit.create_status_from_github!`) is keyed purely by `sha`, not by the authenticated repository. This is a cross-tenant write: "a payload for one repository mutating another's stack, commit" — matching the Critical impact category. If the forged status is a required CI context, this can enable an unauthorized deploy of a commit that never passed real checks, which also falls under "an unauthorized deploy" in the Critical category. The attack is repeatable against any commit sha that is shared between an attacker-reachable repository and a victim's tracked stack (most naturally via forks, which share full git history).

### Likelihood Explanation
Preconditions: (1) the target commit sha must already exist as a `Commit` row under a victim `Stack` (created via normal sync of a tracked branch), and (2) the attacker must be able to get a validly-signed `status` webhook delivered to the Shipit host referencing that same sha for a repository they control — realistically via forking a tracked repository within scope of the same GitHub App installation (org-wide app installs make this straightforward, since forks inherit identical commit SHAs for shared history). The attacker needs no Shipit credentials, no `webhook_secret`, and no maintainer/team access — GitHub itself computes and sends the valid signature for legitimate events on the attacker's own (or forked) repo. This is a purely code-level architectural flaw in `StatusHandler`, independent of secrets.

### Recommendation
Scope `StatusHandler#process` through `self.stacks` like the other handlers, e.g. iterate `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, so a status event can only mutate commits belonging to stacks under the repository named in its own `payload['repository']['full_name']`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`-style, illustrative):
```ruby
test "StatusHandler does not mutate commits outside the payload's own repository stacks" do
  victim_repo  = shipit_repositories(:shipit)
  victim_stack = victim_repo.stacks.first
  shared_sha   = "deadbeefcafefeed0000000000000000000000"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                committer: shipit_users(:walrus), message: "shared",
                                                authored_at: Time.now, committed_at: Time.now)

  attacker_repo  = Shipit::Repository.create!(owner: "attacker", name: "fork")
  attacker_stack = attacker_repo.stacks.create!(environment: "production", branch: "master")
  # no Commit row needs to exist for attacker_stack — the vulnerable query is global.

  payload = {
    "sha" => shared_sha, "state" => "success", "context" => "ci/required",
    "repository" => { "full_name" => "attacker/fork" }
  }

  # Binding under test: handler-derived stacks scope
  scoped_stacks = Shipit::Repository.from_github_repo_name("attacker/fork").stacks
  assert_not_includes scoped_stacks, victim_stack   # left side of equality: attacker's own stacks

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # Right side: StatusHandler wrote into victim_stack anyway, proving the scope was bypassed
  assert_equal "success", victim_commit.reload.status.state
end
```
This demonstrates that `scoped_stacks` (what `Handler#stacks` would return for the attacker's payload) excludes `victim_stack`, yet `StatusHandler#process` still writes a status onto `victim_commit`, proving the architecture-level scoping binding is violated.
