### Title
Broken Access Control in Signing-Request Handling Lets Any Paired Correspondent Request Signatures on Local Addresses They Do Not Co-Sign - (File: wallet.js)

### Summary
`wallet.js`'s `handleMessageFromHub` processes the `"sign"` subject sent by any already-paired correspondent device. When the target address resolves locally (`findAddress` → `ifLocal`), the code explicitly skips the authorization check that would confirm the requester is actually a listed cosigner of that address, and instead unconditionally calls `callbacks.ifOk()` and emits a `"signing_request"` event to the wallet UI/automation layer. [1](#0-0) 

### Finding Description
The `"sign"` message type is meant for two legitimate use cases: multisig cosigning of the same address across devices, and multilateral signing of a shared/dumb contract. The handler validates the message's structural integrity (address format, signing path regex, unit hash consistency, private-payload hash matching) and confirms the message is authentic (i.e., signed by the sender's device key, which is checked earlier in `handleMessageFromHub`/`device.js` before this point). But those checks are equivalent to the "CSRF token" style control described in the reference bug class — they only prove the message came from *some* known, paired correspondent, not that the correspondent is *authorized* to request a signature on the specific local address.

The authorization check that should gate this — verifying the sender is one of the actual cosigners of the address — is present only as a comment:

Because of this, **any device that is merely a correspondent** (paired via the normal pairing flow, which does not imply any financial relationship) can send a `"sign"` request naming one of the victim's own local addresses (`my_addresses`) or a shared address the victim locally controls, and the victim's wallet will process it as if it were a legitimate cosigning/multilateral-signing request — emitting `"signing_request"` to the UI/automation layer with a fully attacker-crafted `objUnit` (for the `signed_message` branch) or attacker-crafted unsigned unit (for the on-chain unit branch, after unit-hash validation).

This mirrors the reported bug class precisely: a sensitive, data/asset-affecting operation is reachable by a low-privileged party (here, any paired correspondent, analogous to a "receptionist"-level user) whose request is authenticated (signature valid) but not authorized (no check that the sender is entitled to request this specific signing operation on this specific address).

### Impact Explanation
- For the `signed_message` path (lines 340–349), the attacker-controlled `objUnit.signed_message` bypasses the DAG/unit validation pipeline entirely (`hasFieldsExcept(objUnit, ["signed_message","authors","version"])` short-circuits straight to `eventBus.emit("signing_request", ...)`), meaning any automation/headless signer that trusts `signing_request` for addresses it locally controls can be tricked into producing a valid signature over attacker-chosen content under the victim's identity/address — a spoofed attestation, contract commitment, or authorization message.
- For the on-chain unit path, an attacker can push a spending unit (subject to unit validation) to the victim's wallet UI as a "multisig cosigning" request even though the attacker was never included as a legitimate cosigner, increasing the chance of the victim (or an automated signer policy) approving an unintended/malicious spend from a shared address.
- This is a genuine broken-access-control condition: authentication (signature/pubkey validity) is conflated with authorization (cosigner membership), exactly matching the reported bug class.

### Likelihood Explanation
Reachable by any peer that has completed the (lightweight) device pairing handshake — pairing secrets are often shared casually (QR codes, chat links) and do not imply any trust relationship regarding a specific address. No special privilege beyond "paired correspondent" is required, and the malicious message is a simple wallet-protocol message (`"sign"`), not requiring any node compromise, hub compromise, or race condition.

### Recommendation
Restore and enforce the previously-commented authorization check before emitting `signing_request`/proceeding with a local "sign" request: verify that `from_address` is actually among the recognized cosigners/signers for the given `address` and `signing_path` (e.g., via `wallet_signing_paths`/`shared_address_signing_paths`/`extended_pubkeys`) before calling `callbacks.ifOk()` and emitting the event, for both the `signed_message` branch and the on-chain unit branch.

### Proof of Concept
1. Attacker device A pairs with victim device B through the normal pairing flow (attacker only needs to be a correspondent, not a cosigner of any of B's addresses).
2. Attacker sends B a device message:
```
{
  subject: "sign",
  body: {
    address: "<B's own or shared address B locally controls>",
    signing_path: "r",
    unsigned_unit: {
      version: "...",
      authors: [{ address: "<address>", authentifiers: {} }],
      signed_message: "<attacker-chosen content, e.g. an attestation or authorization text>"
    }
  }
}
```
3. `handleMessageFromHub` → case `"sign"` validates format/hash consistency, resolves the address via `findAddress` to `ifLocal` (since it is B's own/local address), and — because the cosigner check is commented out — immediately calls `callbacks.ifOk()` and emits `eventBus.emit("signing_request", objAddress, address, objUnit, ...)`, presenting/auto-processing a signing request for attacker-chosen content under B's identity, even though A was never a legitimate cosigner for that address.
