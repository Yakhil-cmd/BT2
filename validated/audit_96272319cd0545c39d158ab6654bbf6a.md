### Title
Cross-organization commit-status forgery bypasses CI gating — webhook signature only authenticates the payload's claimed owner, not the repository being written ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against an *attacker-controlled field inside the JSON body itself* (`repository.owner.login`, or `organization.login`), then hands the same raw payload to a handler that resolves what to write using a *different* field of that same body (or, for `status` events, no repository scoping at all). Any principal onboarded to the Shipit instance as one GitHub organization (i.e. with a valid `webhook_secret` for their own org) can forge a signed `status` webhook whose `sha` belongs to a commit in a completely different, unrelated stack/repository, and mark it as a passing CI status — bypassing that stack's `ci.require`/`ci.blocking` deploy gate.

### Finding Description
`WebhooksController#verify_signature` derives which GitHub App/secret to use for HMAC verification purely from data inside the untrusted request body: [1](#0-0) [2](#0-1) 

The signature check only proves "this body was HMAC-signed with the secret belonging to the organization named in `repository.owner.login`/`organization.login`." It does **not** prove that every other field inside that same body (e.g. `repository.full_name`, or in the `status` event, `sha`) actually pertains to that organization's repositories — that binding is never re-checked downstream.

`StatusHandler`, which processes `status` webhook events used to record CI state for gating deploys, does not scope the lookup by repository/organization at all — it resolves purely by commit SHA across the entire instance: [3](#0-2) 

Compare this to `Handler#stacks`, which is scoped by `repository.full_name` taken from the same untrusted body: [4](#0-3) 

Even where a handler does scope by `repository.full_name`, that field is a sibling field in the same body as `repository.owner.login`; nothing forces them to agree, and the signature only certifies the org secret used to sign the *whole* body — a legitimate holder of *any* onboarded org's `webhook_secret` can put whatever they want into `repository.full_name` or `sha`. For `StatusHandler` specifically, there isn't even a repository field checked — the handler will apply the status to `Commit.where(sha: params.sha)` regardless of which repository that commit belongs to.

This breaks exactly the binding called out in scope: *"an organization that authenticated versus the repository that is written."* The organization identity verified by the signature (`repository_owner` field, matched against that org's `webhook_secret`) is not the same entity as the repository/commit actually mutated by the handler.

### Impact Explanation
Commit CI status is used by Shipit to gate deploys (`ci.require` / `ci.blocking` in `shipit.yml`, documented in `README.md` and implemented via `Commit#create_status_from_github!` / `Stack` deployability checks, referenced in `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb`). An attacker who is a legitimate tenant of the same multi-org Shipit deployment (i.e., they possess their *own* organization's `webhook_secret`, which is a normal, unprivileged onboarding artifact and not itself a Shipit session/API token) can:
1. Sign a forged `status` payload with their own org's `webhook_secret`.
2. Set `sha` to a commit SHA belonging to a victim organization's repository/stack.
3. Set `state: "success"` for a required CI context.

This satisfies the victim stack's CI requirement gate and can enable an unauthorized deploy of a commit that never actually passed the victim's real CI — a cross-organization write and an unauthorized-deploy precondition, matching the in-scope Critical impact category ("cross-repository writes" / "an unauthorized deploy").

### Likelihood Explanation
Requires only knowledge of one legitimate, unprivileged org's webhook secret (which any onboarded organization holder has by design) and the target commit SHA (public GitHub data). No Shipit session, `ApiClient` token, or GitHub App private key is needed — the webhook endpoint is unauthenticated aside from the HMAC check, and that check is keyed on attacker-supplied body content rather than a trusted, out-of-band organization identifier (e.g., URL path, installation ID resolved server-side).

### Recommendation
- Resolve the organization used for signature verification from a server-trusted source (e.g., a per-organization webhook URL/installation ID configured server-side) rather than from a field inside the request body being verified.
- In every handler, cross-check that the repository/commit being mutated actually belongs to the same organization whose secret validated the signature — e.g., `StatusHandler` should verify the resolved `Commit`'s stack/repository owner matches the verified `repository_owner`, not just match by bare `sha`.
- Prefer GitHub's `X-GitHub-Hook-Installation-Target-ID`/delivery metadata (or a configured per-org secret bound to the route) over payload-derived identity for secret selection.

### Proof of Concept
1. Attacker onboards (or already controls) GitHub organization `attacker-org` in the multi-tenant Shipit instance, giving them `attacker-org`'s legitimate `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"` [2](#0-1)  and validates successfully against `attacker-org`'s real secret [1](#0-0) .
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the victim's commit — and calls `create_status_from_github!`, marking it green regardless of `attacker-org` having no relation to that commit's repository [3](#0-2) .
6. The victim stack's `ci.require` check now sees a passing status for that commit, enabling deploy of a commit that never passed real CI.
