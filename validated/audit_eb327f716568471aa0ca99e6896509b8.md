### Title
Webhook organization used for signature verification is decoupled from the repository the event payload writes to, enabling cross-tenant forgery of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`), while every webhook `Handler` subsequently resolves the target `Stack`/`Repository` to act on using a *different* field of the same payload, `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). In a multi-organization Shipit deployment (a first-class, documented configuration — see `docs/setup.md` "Using Multiple Github Applications"), an attacker who legitimately controls one tenant organization's GitHub App secret can craft a raw webhook body whose `repository.owner.login` matches their own org (so the HMAC verifies against their own known `webhook_secret`) while `repository.full_name` names a repository belonging to a different, victim organization also hosted on the same Shipit instance. Because the whole raw body is attacker-authored before signing, the two fields need not be internally consistent the way a genuine GitHub-issued payload always is.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) computes `repository_owner` via:
  ```ruby
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
  ```
  and uses it purely to pick which `Shipit.github(organization: repository_owner)` app (and therefore which `webhook_secret`) to verify the `X-Hub-Signature` against (`lib/shipit/github_app.rb#verify_webhook_signature`).
- Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the appropriate handler(s) with the full JSON body.
- Every handler descends from `Shipit::Webhooks::Handlers::Handler` (`app/models/shipit/webhooks/handlers/handler.rb`), whose `#stacks` method resolves target stacks with:
  ```ruby
  Repository.from_github_repo_name(repository_name)&.stacks
  def repository_name
    payload.dig('repository', 'full_name')
  end
  ```
- `repository.owner.login` (used for auth) and `repository.full_name` (used for the actual write target) are two independent fields inside the same attacker-supplied JSON body. Since the HMAC signature covers only the raw bytes as a whole and Shipit never cross-checks that `full_name` starts with `owner.login/`, an attacker who is a legitimate admin of Org A (and therefore knows Org A's `webhook_secret`, since they configured the GitHub App used for Org A per the multi-org setup docs) can sign a payload where `repository.owner.login = "OrgA"` (verifies fine) but `repository.full_name = "OrgB/victim-repo"` (a repository belonging to Org B, tracked by the same Shipit instance but administratively unrelated to the attacker).
- This is analogous to the H-14 pattern: a field the protocol/engine treats as authoritative for one purpose (auth/maturity gating) is disjoint from the field actually acted upon (redeem target / write target), letting an unprivileged party (relative to the victim) trigger state changes on assets they do not control.

### Impact Explanation
Depending on which event/handler is exercised against the victim repository's stacks, this crosses the "cross-repository writes" / "unauthorized deploy" bar explicitly listed as Critical/High impact:
- A forged `status` event lets the attacker mark arbitrary commits on Org B's tracked repository as `success`/`failure`, directly manipulating `Commit#deployable?` gating used by `Stack#trigger_deploy`/continuous delivery.
- A forged `push` event can enqueue `GithubSyncJob` for Org B's stack, and combined with forged status events, can cause an unreviewed commit to satisfy CI requirements and be picked up by `continuous_deployment`, resulting in an unauthorized deploy of that stack.
- A forged `pull_request`/`membership` event can create `PullRequest`/`Stack`/`Team`/`User` records scoped to Org B's repository from data entirely controlled by the Org A attacker.

This satisfies the "cross-repository writes" / "unauthorized deploy" Critical/High bar because the attacker never needed any credential, session, or permission tied to Org B — only legitimate control of their own, unrelated Org A's webhook secret.

### Likelihood Explanation
Requires only that the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker is (or becomes) a legitimate admin/owner of any one tracked organization — a much weaker requirement than compromising the victim organization. No Shipit session, `ApiClient` token, `api_clients_secret`, GitHub App private key, or victim-repo write access is needed, satisfying the "unprivileged attacker" scope of this scan.

### Recommendation
In `WebhooksController#verify_signature`/`Shipit::Webhooks::Handlers::Handler`, cross-validate that the organization used to select the verifying `webhook_secret` (`repository.owner.login`/`organization.login`) matches the owner segment of `repository.full_name` actually used to resolve the target `Repository`/`Stack` before any handler mutates state. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit for two GitHub organizations, `OrgA` and `OrgB`, per `docs/setup.md` "Using Multiple Github Applications" (distinct `webhook_secret`s).
2. As an attacker who administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft a raw JSON webhook body for a `status` event:
   ```json
   {
     "sha": "<victim commit sha in OrgB/victim-repo>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` (`sha1=` HMAC) and POST it to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature.
5. `Shipit::Webhooks::Handlers::Handler#stacks`/the `status` handler resolves the target repository via `repository.full_name` = `"OrgB/victim-repo"`, creating/updating a `Status` on the victim's commit despite the attacker having no relationship to `OrgB`.

The precise downstream mutation performed by each individual handler for a given event type should be re-verified against those two files before treating the deploy/CI-status impact chain as fully proven.)
